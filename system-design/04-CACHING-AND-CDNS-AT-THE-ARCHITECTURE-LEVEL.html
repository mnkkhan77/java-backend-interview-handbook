CHAPTER 04 — CACHING & CDNS AT THE ARCHITECTURE LEVEL

Volume 2 — Scaling the Infrastructure Layer · Chapter 4 of 12

Load Balancing & DNS (Chapter 03) solved the problem of getting a request to a healthy instance quickly — but it never questioned whether that instance should have to do any real work at all once the request arrives. Caching is the layer that asks exactly that question, at every point along the request path: can this answer be served from somewhere cheaper and closer than the system of record, because it was already computed, or already fetched, recently enough that computing it again would be wasted work? Done well, caching is the single highest-leverage lever available for cutting both latency and infrastructure cost at the same time. Done carelessly, it is also one of the most reliable ways to serve a user data that is confidently, silently wrong — which is exactly why this chapter spends as much time on invalidation and staleness as it does on the caching patterns themselves.

1. MOTIVATION

Every layer discussed in Chapter 03 assumed that once a request reached a healthy instance, that instance would do genuine work to answer it — run a query, call a downstream service, compute a result — and that this work was unavoidable. In practice, an enormous fraction of real-world traffic is redundant in a very specific sense: the same question, or something close enough to the same question, is being asked again before the answer has had any real chance to change. A product page's price does not change between two requests ninety milliseconds apart; a user's profile picture does not change between two page loads in the same session; the HTML, CSS, and JavaScript bundle for a web application is often byte-for-byte identical for every single visitor until the next deploy. Recomputing, re-fetching, or re-querying for an answer that has not changed is pure waste — wasted database load, wasted compute, wasted network transfer, and wasted latency the user has to sit through for no benefit.

Caching is the architectural answer to that waste: store the result of expensive work somewhere cheap and fast to read, and serve subsequent identical (or equivalent) requests from that stored copy instead of redoing the work. The payoff compounds in a way few other optimizations do, because it attacks cost and latency simultaneously rather than trading one for the other — a cache hit is both cheaper to serve than a database round trip and faster to return, which is why caching strategy sits near the top of almost every real system design discussion, right alongside the load-balancing decisions from Chapter 03.

The catch, and the reason this chapter cannot simply say "cache everything, everywhere," is that a cache is a second, separate copy of the truth, and copies of the truth can drift out of sync with the original. Every caching decision is therefore really a trade-off between freshness and efficiency: a cache you never invalidate is maximally fast and maximally wrong eventually; a cache you invalidate so aggressively that it rarely has a chance to serve a hit gains you nothing over not caching at all. This chapter's central job is giving you the vocabulary and judgment to place that trade-off deliberately, layer by layer, rather than accidentally.

2. HISTORICAL BACKGROUND

2.1 HTTP Caching and the Proxy Cache Era (1994-1998)

Caching was built into the web's core protocol almost from the start. HTTP/1.0 (1996) defined the Expires header, letting an origin server tell any downstream cache exactly when a response could be safely reused without re-asking the server. Around the same time, dedicated forward/proxy caching software like Squid (first released in 1996, evolving from the earlier Harvest project) let organizations and ISPs cache popular web content at a shared point, so that a hundred employees requesting the same page did not each generate a separate round trip to the origin across the slow, expensive internet links of the era. This was caching solving a bandwidth and latency problem for a web that was, by today's standards, almost entirely static.

2.2 The Flash Crowd Problem and the Birth of the CDN (1998-2000)

As the web grew, a specific failure mode became common and painful: a site would be mentioned somewhere widely read (the "Slashdot effect," named for the tech news site whose linked sites would frequently buckle under the resulting traffic spike), and the sudden flood of simultaneous requests for the same content would overwhelm an origin server that had been running comfortably under normal load seconds earlier. MIT researchers Tom Leighton and Danny Lewin, working on algorithms for distributing web traffic efficiently, founded Akamai in 1998 specifically to solve this at internet scale: instead of one origin server handling every request from every geography, Akamai built a globally distributed network of edge servers that cached and served content from locations physically close to end users, absorbing flash-crowd traffic before it ever reached the origin at all. This is the conceptual birth of the Content Delivery Network (CDN) as a distinct category of infrastructure.

2.3 Distributed In-Memory Caching for the Application Layer (2003-2008)

CDNs solved caching for content served to the public internet, but a parallel problem was growing inside data centers: as Web 2.0 applications (social networks, user-generated content platforms) scaled, their databases became the bottleneck, hammered by repeated reads for the same frequently-accessed rows. In 2003, Brad Fitzpatrick (also the creator of LiveJournal) built Memcached specifically to offload this read pressure — a simple, distributed, in-memory key-value store designed to sit between the application and the database, caching query results so the database only had to do the expensive work once per change, not once per read. Facebook's widely-cited internal scaling work on Memcached in the following years (eventually serving trillions of requests across thousands of servers) proved the pattern could scale to the largest web properties on earth, cementing "application-level distributed cache in front of the database" as a standard architectural layer, not a niche optimization.

2.4 CDNs Expand From Static Assets to Dynamic Content and Edge Compute (2010s-Present)

Early CDNs were almost exclusively used for genuinely static, rarely-changing assets — images, stylesheets, JavaScript bundles, video. Over the 2010s, CDN providers (Akamai, Cloudflare, Fastly, and the hyperscalers' own offerings) extended the same edge-distribution model to dynamic, per-request content: intelligent caching of API responses with short, carefully chosen TTLs; edge-side request routing and security filtering; and eventually full programmable compute running directly at the edge (Cloudflare Workers, AWS Lambda@Edge/CloudFront Functions), letting application logic — not just cached bytes — execute physically close to the user. This is the architectural lineage this chapter sits at the end of: the same core idea (serve from somewhere closer and cheaper than the origin) that started with static HTML in the 1990s now spans everything from a product thumbnail to a personalized, computed API response.

3. PROBLEM STATEMENT

Strip away the specific technologies and the problem caching exists to solve is this:

Given that producing a piece of data (a computed result, a database row, a rendered page, a static asset) is expensive relative to how often that data actually changes, how do you store and reuse a copy of that data to avoid redoing the expensive work — while guaranteeing that anyone reading the cached copy is never misled by data that is now wrong, for longer than the system has explicitly agreed to tolerate?

That second half of the problem statement is the part that is genuinely hard, and it has a famous name in the field: a line widely attributed to Phil Karlton holds that "there are only two hard things in computer science: cache invalidation and naming things." The reason invalidation earns that reputation is structural, not incidental. A cache, by definition, exists outside the single system of record that updates get written to — which means every write path in your system needs to somehow also notify every cache that might be holding a now-stale copy of what it just changed, across however many layers and however many physically distributed cache nodes exist. Miss even one of those notification paths, and some fraction of readers will see outdated data indefinitely, with no error, no exception, and no obvious signal that anything is wrong — just a quietly incorrect answer served with full confidence.

This problem also has several genuinely distinct sub-problems that are easy to conflate, mirroring the discovery/selection/health/state breakdown Chapter 03 used for load balancing: population (how does data get into the cache in the first place — proactively, or only on demand?), placement (which layer of the request path — browser, edge, application, none — should hold this particular piece of data?), invalidation (how and when does a cached copy get removed or refreshed once the underlying data changes?), and consistency tolerance (exactly how stale is this specific piece of data allowed to be before staleness becomes a correctness bug rather than an acceptable trade-off?). The remainder of this chapter is organized around giving each of these sub-problems a precise, separately-reasoned answer, because treating "caching" as one undifferentiated decision is exactly how invalidation bugs get introduced.

4. THEORY

4.1 Cache-Aside (Lazy Loading)

In the cache-aside pattern, the application itself owns the logic: on a read, it checks the cache first; on a cache miss, it reads from the underlying data store, then explicitly writes the result into the cache before returning it, so the next read for that key is a hit. On a write, the application updates the data store and — critically — either invalidates (deletes) or updates the corresponding cache entry, rather than letting the stale version linger. This is by far the most common pattern in application-level caching precisely because it requires no special infrastructure beyond a plain key-value cache: the cache itself can be a completely "dumb" store that knows nothing about where its data comes from, with all the intelligence living in application code. The cost of that simplicity is that every call site touching this data has to remember to participate correctly in both the read-miss-populate path and the write-invalidate path, which is a discipline that can quietly erode as a codebase grows.

4.2 Read-Through

Read-through caching moves the population logic from the application into the cache layer itself: the application only ever talks to the cache, and the cache, on a miss, knows how to fetch the missing value from the underlying data store itself (via a configured loader function), populate itself, and return the result — the application code never sees a miss as a distinct case it has to handle. This centralizes the "how do we fetch on a miss" logic in one place instead of scattering it across every call site that happens to read this data, which is valuable when many different parts of a codebase read the same cached entity and you want a single, consistently-correct loading path. The trade-off is that it requires a cache technology (or caching library) that actually supports a pluggable loader, rather than the plain get/put interface cache-aside can work with.

4.3 Write-Through

Write-through caching changes where the write path's responsibility sits: every write goes to the cache first, and the cache itself is responsible for synchronously writing that value through to the underlying data store before the write is considered complete. The practical effect is that the cache and the data store are never allowed to disagree — a successful write guarantees both are updated — which eliminates the entire class of invalidation bugs where a write succeeds but the corresponding cache entry is forgotten. The cost is write latency: every write now pays for both the cache write and the underlying store write before it can be acknowledged, so write-through is the right call specifically when read consistency matters more than minimizing write latency, and reads of this data vastly outnumber writes (so the extra write-path cost is amortized across many fast reads).

4.4 Write-Behind (Write-Back)

Write-behind caching takes the opposite trade-off from write-through: a write is applied to the cache immediately and acknowledged as complete right away, while the actual write to the underlying data store happens asynchronously, shortly afterward, often batched together with other pending writes. This makes writes extremely fast from the caller's perspective, and batching can also meaningfully reduce load on the underlying store (many small writes coalesced into fewer, larger ones). The real cost is a genuine durability and consistency risk: if the cache node fails before the asynchronous write-behind flush completes, that write is lost entirely, with no record of it ever having happened in the system of record. Write-behind is therefore the right call only when the underlying store has very limited write capacity relative to demand (making batching valuable enough to justify the risk) and some bounded amount of data loss on a cache failure is an acceptable, explicitly accepted trade — never a default choice for data with a strict durability requirement.

4.5 Invalidation Strategies

Having chosen a population pattern, you still need a strategy for deciding when a cached entry stops being trustworthy. Three strategies cover the overwhelming majority of real systems:

  • TTL (time-to-live) expiration. Every cached entry is stamped with an expiration time when written, and is treated as a miss (and re-fetched) once that time passes, regardless of whether the underlying data actually changed. This is simple, requires no coordination with the write path at all, and bounds staleness to a known maximum window — but it is a blunt instrument: data that changed the instant after being cached stays wrong for the full TTL, and data that never changed gets needlessly re-fetched the instant the TTL expires.
  • Event-driven invalidation. The write path explicitly notifies the cache (or publishes an event that cache nodes subscribe to) the moment the underlying data changes, so the cache entry is deleted or updated immediately rather than waiting for a TTL to elapse. This gives much tighter freshness guarantees than TTL alone, but it requires every single write path that can change this data to correctly participate in invalidation — miss one code path (a batch job, an admin tool, a direct database migration) and that path's writes silently bypass the cache, leaving stale data behind with no TTL to eventually correct it.
  • Versioned / content-addressed keys. Instead of invalidating an existing key, the cache key itself encodes a version or a content hash of the underlying data (a build hash in a static asset's filename, a row's updated-at timestamp embedded in its cache key), so a change to the data naturally produces a new key rather than requiring the old one to be explicitly deleted. Old entries simply age out of the cache via normal eviction, never needing active invalidation at all. This sidesteps the entire "did every write path remember to invalidate" problem, at the cost of needing a reliable, cheap way to compute that version/hash, and some duplication (the old entry lingers, unused, until evicted).

This is exactly why cache invalidation earns its "hard problem" reputation from Section 3: TTL alone trades away freshness for simplicity, event-driven invalidation trades away simplicity (and completeness risk) for freshness, and versioned keys solve the completeness problem only by changing what "invalidation" even means. Real production systems very often combine all three — a versioned key as the primary mechanism, a moderate TTL as a safety net against any invalidation event that was missed, and event-driven invalidation layered on top for the specific entries where staleness windows need to be tight.

5. INTERNAL WORKING

5.1 The Full Request Path: Browser → CDN Edge → Application Cache → Database

A single request in a realistic modern deployment can be satisfied — or not — at any of four successive layers, each cheaper and faster than the one after it, and each with its own cache lifetime and invalidation mechanism:

  1. Browser cache. The browser itself may already hold a valid cached copy of the response, governed entirely by the Cache-Control and ETag/Last-Modified headers the origin sent on a previous response — if the cached copy is still fresh per those headers, the browser never issues a network request at all, which is the cheapest possible "hit" because it costs zero network round trips.
  2. CDN edge. If the browser does make a request (cache miss, or the resource requires revalidation), it is routed — per Chapter 03's GeoDNS/anycast mechanics — to a nearby CDN point of presence (PoP). The edge node checks its own cache; a hit is served directly from the edge, never reaching your infrastructure at all. A miss triggers the CDN to fetch from an origin shield (a single, consolidated caching layer the CDN maintains between its many edge PoPs and your actual origin, explained fully in Section 5.2) or your origin directly.
  3. Application-level distributed cache. Requests that do reach your application (because the CDN could not serve them from cache — often because the content is dynamic, personalized, or simply not cacheable at the edge) typically check a shared, distributed, in-memory cache (Redis, Memcached) before touching the database, using one of the patterns from Section 4. This is the layer java/21-CACHING-STRATEGIES.html covers in full implementation depth — this chapter is concerned with where this layer sits and what role it plays, not its internal mechanics.
  4. Database. Only a request that misses at every preceding layer ever reaches the system of record, which is exactly the point: each layer above exists specifically to shrink the volume of traffic the next, more expensive layer has to absorb.

The practical consequence of this layering is that a single cache-hit-ratio number is almost never the right thing to optimize in isolation — a 60% hit ratio at the CDN edge combined with an 80% hit ratio at the application cache layer means the database only ever sees roughly 0.4 × 0.2 = 8% of original client traffic, and improving either layer's ratio compounds with the other. This multiplicative relationship is the quantitative justification for treating caching as a layered strategy rather than a single decision made once.

5.2 Origin Shielding

A naive CDN deployment lets every edge PoP independently fetch from the origin on its own cache miss — which means a globally popular piece of content that just expired can trigger dozens of simultaneous "cache miss" requests hitting the origin at once, one from each PoP, exactly the flash-crowd problem CDNs exist to prevent, just relocated one layer inward. Origin shielding solves this by designating one specific caching layer (a single PoP, or a dedicated shield node) as the only one allowed to talk to the origin directly; every other edge PoP that misses locally fetches from the shield instead of the origin. The shield itself caches the result, so the origin sees at most one request per unique piece of content per shield-cache-lifetime, no matter how many edge PoPs around the world are simultaneously asking for it. This is the single most important architectural lever for keeping origin load low and predictable under global traffic.

5.3 Cache Stampede (Thundering Herd) and How It's Mitigated

A closely related failure mode can occur at any caching layer, not just the CDN: when a single, very popular cache entry expires, every concurrent request for that key can simultaneously miss and simultaneously attempt to regenerate it — dozens or hundreds of redundant, expensive recomputations or database queries hitting the backing store at exactly the same instant, for data that only actually needed to be computed once. Three mitigations are standard:

  • Request coalescing (single-flight). The cache layer recognizes that a regeneration for a given key is already in flight and makes every other concurrent request for that same key wait on the same in-flight result, rather than independently triggering their own regeneration.
  • Locking. The first request to miss acquires a short-lived lock (often itself stored in the cache) before regenerating; other concurrent requests that see the lock held either wait briefly and retry, or fall back to serving the just-expired (stale) value rather than all independently hammering the backing store.
  • Stale-while-revalidate. The cache serves the just-expired value immediately (so no request has to wait at all) while asynchronously triggering exactly one background refresh — users get a fast response using slightly stale data for the brief refresh window, and the backing store sees only one regeneration request instead of many. This pattern is directly expressible as an HTTP Cache-Control: stale-while-revalidate directive at the CDN/browser layer, and is a common pattern to implement manually at the application cache layer as well.

6. MATHEMATICS

Caching's quantitative core is simple, but the numbers it produces are exactly what justifies (or fails to justify) a given caching investment in a real capacity-planning conversation.

6.1 Cache Hit Ratio

hit_ratio = cache_hits / (cache_hits + cache_misses)

This single number is the key health metric for any cache, at any layer, precisely because every other benefit caching provides — latency reduction, backend load reduction, cost reduction — is a direct function of it. A cache with a 10% hit ratio is mostly overhead (the cost of checking it and maintaining it) for very little benefit; a cache with a 95% hit ratio is doing almost all of the system's real work.

6.2 Blended Latency

blended_latency = (hit_ratio × cache_latency) + (miss_ratio × origin_latency)

This formula is why even a moderate hit ratio produces an outsized latency win: if a cache hit takes 2ms and an origin round trip (database query, or cross-region origin fetch) takes 200ms, a 90% hit ratio produces a blended latency of (0.9 × 2) + (0.1 × 200) = 21.8ms — a roughly 9x improvement over always paying the 200ms cost, even though one in ten requests still pays the full price. This is also exactly why pushing the hit ratio from 90% to 99% matters disproportionately at scale: the same formula gives (0.99 × 2) + (0.01 × 200) = 3.98ms, more than a 5x further improvement from what looks like a small percentage-point change.

6.3 Backend Load Reduction and the Multiplicative Effect of Layers

backend_traffic_fraction = (1 - hit_ratio_layer1) × (1 - hit_ratio_layer2) × ... × (1 - hit_ratio_layerN)

As noted in Section 5.1, hit ratios at successive layers multiply together (via their respective miss ratios) to determine what fraction of original traffic reaches the final, most expensive layer. This is the formal justification for caching at multiple layers rather than trying to push one single layer's hit ratio arbitrarily high: a CDN hit ratio of 70% and an application cache hit ratio of 80% together reduce database-bound traffic to (1 − 0.7) × (1 − 0.8) = 0.06, i.e. 6% of original traffic — each layer only needs to be moderately effective for the combination to be highly effective.

6.4 Popularity Skew (Zipf-like Distributions) and Working Set Size

Real-world access patterns for cacheable content are almost never uniform — a small fraction of keys (a popular product, a trending article) account for a disproportionate share of all requests, a pattern commonly approximated by a Zipf-like distribution where the frequency of the k-th most popular item is roughly proportional to 1/k. The practical consequence is that a cache does not need to hold every possible key to achieve a high hit ratio — it needs to hold the comparatively small "working set" of currently-popular keys, which is exactly what an LRU (least-recently-used) or LFU (least-frequently-used) eviction policy is designed to approximate without needing to know the true popularity distribution in advance. This is also the mathematical reason cache sizing conversations focus on "does the working set fit in the cache" rather than "does the entire dataset fit in the cache" — for most real workloads, the former is a vastly smaller, and vastly cheaper, bar to clear.

Two operational concerns are specific to this stack and worth internalizing as first-class production concerns, not afterthoughts. First, purge-on-deploy: when an application deploys a change to any content a CDN or application cache might be holding, the deploy pipeline needs an explicit step that invalidates the affected cache entries (via the CDN's purge API, and/or an application-level cache-clear call) — relying purely on TTL expiration to eventually surface a deploy's changes means users can see old behavior for however long the TTL allows, which is rarely acceptable for anything beyond the most cosmetic of changes. Second, cache warming: a cold cache (freshly deployed instance, newly restarted Redis cluster, a CDN PoP that just came online) has a hit ratio near zero until traffic naturally populates it, which means the full, un-cached cost of every request briefly lands on the layer below — for high-traffic systems, this is addressed by proactively pre-populating the cache with known-popular keys before fully routing production traffic to the new instance, rather than letting it "warm up" purely reactively under live load.

9. JAVA / SPRING PERSPECTIVE

Spring gives you caching building blocks at the same two distinct points in the stack that Chapter 03 identified for load balancing, and it is worth being equally precise here about what each one actually buys you — and, just as importantly, where it does not help at all.

9.1 Spring's Cache Abstraction: @Cacheable, @CacheEvict, @CachePut

Spring's caching annotations implement the cache-aside pattern from Section 4.1 declaratively, at the method level, backed by a pluggable cache provider (Redis, Caffeine, or others — again, java/21-CACHING-STRATEGIES.html is where the provider-level mechanics live). @Cacheable checks the cache before executing the annotated method, and populates it with the method's return value on a miss. @CacheEvict removes an entry, typically annotated on the method that updates or deletes the underlying data, implementing the explicit invalidation half of cache-aside. @CachePut always executes the method and updates the cache with its result, useful when you want a write to refresh the cache rather than simply invalidate it.

At the architecture-decision level, what this abstraction buys you is genuinely significant: it turns "add caching to this method" into a one-line annotation instead of hand-written get/check/populate boilerplate scattered through your service layer, and it makes the cache-aside contract (check cache, populate on miss, invalidate on write) consistent and auditable across an entire codebase rather than reimplemented slightly differently at every call site. What it deliberately does not help with is everything Section 3 and Section 4.5 identified as the hard part: it will not tell you whether a given piece of data should be cached at all, what TTL is appropriate, or whether some other, un-annotated write path (a batch job, a direct SQL migration, another microservice writing to the same table) needs to also trigger the same eviction — those remain architecture decisions the annotations simply execute, not decisions they make for you. It is also worth knowing a specific, commonly-surprising implementation detail: Spring's caching annotations work via a dynamic proxy wrapping the bean, so a method calling another @Cacheable method on this (self-invocation, bypassing the proxy) silently skips caching entirely — a frequent source of "why isn't this being cached" confusion that has nothing to do with cache configuration and everything to do with how Spring AOP proxies work. 

// Illustrative: cache-aside expressed declaratively via Spring's
// caching abstraction — the method body never mentions the cache at all.

@Service
public class ProductService {

    @Cacheable(value = "products", key = "#productId")
    public Product getProduct(String productId) {
        return productRepository.findById(productId)   // only runs on a miss
            .orElseThrow();
    }

    @CacheEvict(value = "products", key = "#product.id")
    public void updateProduct(Product product) {
        productRepository.save(product);                // write path invalidates
    }                                                     // the stale cache entry
}

9.2 Spring Cloud Gateway Response Caching

Spring Cloud Gateway (introduced in Chapter 03 as the L7 gateway layer) can also cache entire HTTP responses at the gateway tier itself, via its LocalResponseCache filter — honoring standard Cache-Control response headers to decide what's cacheable and for how long. This is architecturally distinct from both the CDN layer (which sits outside your infrastructure entirely, closer to the client) and the application-level distributed cache (which caches internal data, not full HTTP responses) — it is a third, narrower caching point specifically for whole-response reuse at your own edge, useful when a gateway fronts multiple backend services and many of their responses are cacheable but you do not want (or cannot justify the cost of) a full third-party CDN in front of every one of them.

9.3 Integrating a Spring Boot Application With a CDN

A Spring Boot application participates in CDN caching primarily by controlling what headers its responses carry, since the CDN makes its caching decisions based entirely on those headers (Section 7.2's "browser cache" step applies the identical logic). A controller serving cacheable content sets Cache-Control explicitly (e.g., max-age, and whether the response is public and thus cacheable by a shared CDN cache versus private and only cacheable by the end user's own browser) and typically an ETag or Last-Modified value, letting the CDN (and the browser) issue a cheap conditional revalidation request (If-None-Match) instead of re-downloading unchanged content. The second integration point is the deploy pipeline's purge step described in Section 8: when a deploy changes content a CDN might be holding, the pipeline calls the CDN provider's purge API for the affected paths (or uses versioned/content-addressed URLs per Section 4.5, which sidesteps the need to purge at all, since a new deploy naturally produces new URLs rather than requiring old ones to be invalidated). 

// Illustrative: a controller explicitly setting cache headers so the
// CDN (and browser) know exactly how long this response is reusable.

@GetMapping("/api/catalog/{id}")
public ResponseEntity<Product> getProduct(@PathVariable String id) {
    Product product = productService.getProduct(id);
    return ResponseEntity.ok()
        .cacheControl(CacheControl.maxAge(Duration.ofMinutes(5)).cachePublic())
        .eTag(product.getVersion())            // enables cheap If-None-Match revalidation
        .body(product);
}

10. BEST PRACTICES

  • Pick the invalidation strategy to match the data's actual change frequency and staleness tolerance — don't default to one TTL everywhere. Per Section 4.5, rarely-changing, high-value data deserves event-driven invalidation or versioned keys; frequently-churning, low-stakes data is often fine with a short TTL and no further machinery at all.
  • Prefer versioned/content-addressed cache keys for anything you control the URL for. Sidestepping invalidation entirely (Section 4.5) by changing the key whenever the content changes eliminates an entire category of "forgot to invalidate" bugs, and is why static asset pipelines almost universally fingerprint filenames with a content hash.
  • Protect every layer against cache stampede on your hottest keys. Request coalescing, locking, or stale-while-revalidate (Section 5.3) turn a predictable traffic spike at expiration time into a non-event — this is cheap insurance that is easy to skip until the one popular key that didn't have it causes an incident.
  • Treat the cache-hit-ratio as a first-class, continuously monitored metric at every layer, not just at deploy time. Per Section 6, hit ratio is the one number that determines nearly every other benefit caching provides — a silent regression in hit ratio (a bad deploy that changed a cache key's shape, an eviction policy that's too aggressive for the current working set) is a latency and cost regression hiding behind a metric nobody is watching.
  • Always pair a purge-on-deploy step with any cache layer your deploy pipeline can affect. Per Section 8, relying purely on TTL expiration to surface a deploy's changes trades a known, bounded deploy process for an unbounded, TTL-dependent rollout window that users experience as inconsistent behavior.

11. COMMON MISTAKES

  • Caching data without ever deciding how it gets invalidated. "We'll add a TTL and figure out invalidation later" very often means invalidation never actually gets figured out — Section 3's point about cache invalidation being genuinely hard is exactly why it needs to be decided deliberately, up front, as part of the caching decision itself, not deferred.
  • Forgetting a write path when wiring up event-driven invalidation. A batch job, an admin tool, a direct database migration, or another service writing to shared data are all common blind spots — per Section 4.5, event-driven invalidation is only as reliable as the completeness of every write path that participates in it.
  • Caching error responses or empty results without a deliberately short, separate TTL. Blindly applying the same long TTL used for successful responses to a transient failure (a downstream timeout, a momentarily empty result set) can turn a brief blip into a sustained outage, where a cached "no data" or error response keeps being served long after the underlying condition has cleared — negative caching is legitimate and often valuable, but it needs its own, usually much shorter, TTL.
  • Caching personalized or user-specific responses at a shared CDN layer without a correct Vary header. If the CDN cache key doesn't account for whatever makes the response differ per user (an auth cookie, an Accept-Language header), one user's personalized response can be served to a completely different user — a serious correctness and privacy bug, not just a staleness inconvenience.
  • Treating the cache as the source of truth during an incident. When cache and database disagree, the database is authoritative by construction — debugging "why does the UI show the wrong value" by trusting whatever the cache currently holds, rather than checking the underlying store first, wastes time chasing the wrong layer.
  • Sizing a cache for the whole dataset instead of the actual working set. Per Section 6.4, popularity skew means most real workloads achieve a high hit ratio with a cache far smaller than the full dataset — over-provisioning cache memory to hold data that is rarely re-requested is wasted spend that an LRU/LFU eviction policy was already handling correctly without the extra capacity.

12. PERFORMANCE CONSIDERATIONS

Every performance property of a caching layer traces back to the hit-ratio and blended-latency relationships from Section 6 — the practical question is always which levers actually move the hit ratio, and at what cost.

  • Eviction policy shapes the effective hit ratio under memory pressure. LRU (evict the least-recently-used entry) is the common default and works well when recent access predicts future access; LFU (evict the least-frequently-used entry) can outperform it when a smaller set of consistently-popular keys should survive occasional bursts of one-off traffic to unrelated keys. The wrong policy for a given access pattern can leave a cache that's technically "full" but still thrashing — evicting entries that would have been reused soon in favor of ones that won't be.
  • A cold cache briefly exposes the full, un-cached cost of every request. Per Section 8's cache-warming point, a freshly deployed cache node or CDN PoP starts at a 0% hit ratio — for latency- or cost-sensitive systems, this window needs to be accounted for explicitly (gradual traffic ramp, proactive warming) rather than assumed away.
  • A distributed application-level cache still costs a network hop. Redis or Memcached are vastly cheaper than a database round trip, but they are not free — for extremely hot, small, rarely-changing data, an additional local (in-process) cache layer in front of the distributed cache can shave off even that network hop, at the cost of a slightly more complex invalidation story (now two cache layers need to agree on freshness instead of one).
  • TTL length is a direct trade between hit ratio and staleness window, not a free parameter. A longer TTL increases hit ratio (fewer re-fetches) but widens the worst-case staleness window; a shorter TTL tightens freshness at the direct cost of more cache misses and more load on the layer beneath — this dial should be set deliberately per data type (Section 10), not left at a single framework default across an entire system.

13. SECURITY CONSIDERATIONS

A cache sits directly on the path of every cacheable request, which makes it, like the load-balancing layer in Chapter 03, both a natural place to absorb abuse and a surface that can itself be exploited if misconfigured.

  • Cache poisoning via unkeyed inputs. If a CDN or reverse-proxy cache key does not account for every input that affects the response (a header, a query parameter), an attacker can craft a request that causes a malicious or incorrect response to be cached under a key that legitimate users subsequently hit — serving the poisoned response to every user who requests that same cache key afterward. The defense is ensuring the cache key genuinely captures every input the response actually varies on, which is exactly the same discipline the Vary header mistake in Section 11 is a special case of.
  • Caching authenticated or user-specific content at a shared layer. Content that differs per user (account details, personalized recommendations, anything behind authentication) must either be marked private (cacheable only by the end user's own browser, never a shared CDN cache) or excluded from shared caching entirely — caching it as public at a CDN risks serving one user's private data to another, a severe confidentiality failure rather than a mere correctness bug.
  • Purge API access control. The ability to invalidate cache entries, particularly at a CDN, is itself a capability worth protecting — an attacker (or a misconfigured, overly-permissive internal tool) able to trigger arbitrary purges can force a flood of cache misses straight through to the origin, effectively weaponizing your own cache-invalidation mechanism as a denial-of-service vector against your origin.
  • Stale security-relevant data. Authorization decisions, feature flags, or access-control data cached with too long a TTL (or missed by an event-driven invalidation path, per Section 11) can mean a revoked permission or a disabled account continues to appear valid for however long the stale cache entry survives — security-sensitive data generally warrants shorter TTLs and more rigorous invalidation coverage than ordinary content, precisely because the cost of staleness here is a security gap, not just an inconvenience.

14. INTERVIEW QUESTIONS

JUNIORQ1. A teammate says "just cache it" every time an endpoint is slow, including ones already backed by a single, cheap primary-key lookup. When does that instinct actually pay off, and when does it just add invalidation risk for no real benefit?

ROI: ★★★★★ · Frequency: Extremely High

Caching pays off when the same answer is requested far more often than the underlying data actually changes — the redundancy is in the requests, not in the work itself. A single cheap primary-key lookup against an already-fast index gains little from a cache in front of it, and gains a new failure mode (staleness, plus an invalidation path to maintain) for latency that was already acceptable. The actual test is comparing request volume against change frequency for that specific piece of data: a cache only buys real latency and backend-load reduction when the thing being cached is both genuinely expensive to recompute and read vastly more than it changes. "Cache it" as a reflex, with neither condition checked, trades a known, bounded query cost for an unmeasured invalidation liability.

JUNIORQ2. You inherit a service that uses cache-aside everywhere. A bug report says a product's price is still wrong on the storefront minutes after being corrected in the admin panel. Walk through where in the cache-aside flow that bug most likely lives.

ROI: ★★★★★ · Frequency: Extremely High

Cache-aside has two separate responsibilities that both have to be implemented correctly: the read path populates the cache on a miss, and the write path is responsible for explicitly invalidating or updating the cache entry after the underlying store is written. A price staying wrong after a correction means the write path updated the database but didn't correctly evict or refresh the cached entry for that product — either the invalidation call is missing from this particular write path entirely (a common gap when multiple code paths can write price, e.g. an admin tool versus the main service), or it's invalidating the wrong cache key because of a key-shape mismatch between the read and write sides. The fix is tracing every path that can change price and confirming each one calls the same invalidation logic, not just the one you assumed was the only writer.

JUNIORQ3. Your cache shows a 40% hit ratio and someone on the team calls that "basically broken." Is that actually broken, and what would you check before agreeing or disagreeing?

ROI: ★★★★★ · Frequency: Extremely High

Hit ratio alone doesn't tell you whether a cache is healthy — it has to be judged against what's achievable for that specific access pattern. 40% could be bad (a key-shape bug causing near-misses, a TTL too short for the data's actual change frequency, or a working set that doesn't fit the allocated cache size), or it could be close to the ceiling for a genuinely flat, non-skewed access pattern where most keys really are requested once. Before agreeing it's broken: check the theoretical hit ratio implied by the data's actual popularity distribution (Zipf-skewed data should support a much higher ratio than 40%; near-uniform access might not), check whether cache keys are computed consistently across call sites, and check whether eviction is thrashing because the working set exceeds the cache's capacity. Only after ruling those out would a 40% ratio actually justify re-architecting rather than retuning.

JUNIORQ4. A static marketing site with global traffic is served entirely from one origin region, and users on the other side of the world say it feels sluggish. Before reaching for a CDN as the fix, what would you confirm, and what specifically does putting one in front change?

ROI: ★★★★★ · Frequency: Extremely High

First confirm the sluggishness is actually network/distance latency rather than origin processing time or payload size — a quick check is comparing time-to-first-byte from a nearby region against a far one for the same request. If it's distance, a CDN helps by serving cached copies from an edge PoP physically close to the requesting user instead of routing every request back to the single origin region, cutting round-trip time and also absorbing traffic spikes (the original flash-crowd problem CDNs were built for) before they ever reach the origin. It does not help if the page is dynamic or personalized in a way that defeats edge caching, or if the real bottleneck is origin compute time rather than network distance — in those cases a CDN adds a layer without addressing the actual cause.

JUNIORQ5. Two services cache the same kind of data — one uses a 5-second TTL, the other a 6-hour TTL. Both are defensible. What makes each the right call for its own data, and what's the actual cost of getting this dial wrong in either direction?

ROI: ★★★★★ · Frequency: Extremely High

TTL sets the maximum window a cached value can be served after the underlying data changed without anyone checking — it's a direct trade between hit ratio and worst-case staleness, not a universal setting. A 5-second TTL fits data where staleness has real, fast-moving cost (inventory counts near zero, a live auction price) and where request volume is high enough that even a few seconds of caching still yields a meaningful hit ratio. A 6-hour TTL fits data that changes rarely and where brief staleness is a non-issue (a product description, a category list). Getting it wrong in one direction (too short) sacrifices hit ratio and backend-load reduction for freshness nobody needed; getting it wrong the other way (too long) means a change takes up to the full TTL to become visible anywhere, which for business-sensitive data becomes a correctness complaint, not just a tuning issue.

JUNIORQ6. Your event-driven invalidation has worked flawlessly for a year. Then a support ticket reports stale data that's impossible to reproduce on demand — it clears itself after a few hours. What's your working theory, and how do you confirm it without adding new logging first?

ROI: ★★★★★ · Frequency: High

"Clears itself after a few hours" is the key clue: that's consistent with a TTL eventually expiring and refreshing the entry, which strongly suggests one specific write path isn't triggering the event-driven invalidation at all, and a background TTL (if one exists as a safety net) is the only thing eventually correcting it. The likely culprit is a write path outside the main application flow — a batch job, an admin backdoor, a direct database migration, or another service writing to the same table — that was never wired into the invalidation event. To confirm without new logging: check whether a TTL safety net exists on this cache entry and what its duration is (if it roughly matches the "clears itself" window, that's strong confirmation), and audit everything that can write to this data against everything that triggers the invalidation event, since the mismatch is almost certainly there rather than in the invalidation logic itself being flaky.

JUNIORQ7. A write-heavy service is considering switching from write-through to write-behind purely to cut write latency. What do you need to know about this specific data before signing off, and what failure scenario would you insist the team explicitly accept first?

ROI: ★★★★★ · Frequency: High

Before signing off, you need the data's actual durability requirement: write-behind acknowledges a write after only updating the cache, flushing to the underlying store asynchronously (often batched) afterward — faster, but it means a cache node failure between acknowledgment and flush loses that write permanently, with no record it ever happened. That's acceptable for data where some bounded loss is explicitly tolerable (ephemeral counters, non-critical telemetry) and unacceptable for anything with a real durability expectation (financial records, anything a user would expect to survive a crash). The scenario to force an explicit sign-off on, in concrete terms, isn't "there's some risk" — it's "if the cache node dies right now, here's exactly how much recent data is gone and who finds out and how," because a quantified, named failure mode gets a real decision; an abstract acknowledgment of risk gets forgotten.

JUNIORQ8. A piece of content just went viral, and despite being CDN-cached, the origin is getting hammered with what looks like one request per edge location worldwide, simultaneously. What's happening, and what single architectural piece is missing?

ROI: ★★★★☆ · Frequency: Medium-High

Without an origin shield, every edge PoP that misses its own local cache independently fetches from the origin — so the moment a popular item's cache entry expires or is first requested, every PoP around the world serving a nearby user effectively treats it as its own separate first-time miss, generating one origin request per PoP simultaneously. That's the exact flash-crowd problem CDNs exist to prevent, just relocated one layer inward. The missing piece is an origin shield: a single consolidated caching layer between all the edge PoPs and the real origin, so the origin sees at most one request per unique content per shield-cache-lifetime no matter how many edge PoPs are asking for it, with every other PoP's miss resolved against the shield instead.

JUNIORQ9. A response is served with Cache-Control: private, max-age=300, and a teammate is confused why it's still re-fetched on every request from a different user, even within the 5-minute window. What's actually happening?

ROI: ★★★★★ · Frequency: High

private restricts caching to the requesting client's own browser specifically — it explicitly forbids any shared intermediate cache (a CDN, a shared proxy) from storing and reusing the response for a different user. A different user making a request is, by definition, a cache miss from that other user's own browser's perspective, since browser caches are per-client and not shared; the max-age=300 window only governs how long that one browser can reuse its own cached copy, it never makes the response reusable across different users at any shared layer. The confusion usually comes from conflating "cached for 5 minutes" with "cached and shared for 5 minutes" — the private directive is precisely what prevents the second half.

JUNIORQ10. A method annotated @Cacheable is still hitting the database on every call in production, even with the same arguments passed repeatedly. Before suspecting the cache provider, what are the two most common causes you'd rule out first?

ROI: ★★★★☆ · Frequency: Medium-High

First: self-invocation — @Cacheable works via a dynamic proxy wrapping the bean, so if this method is being called from another method on the same bean (via this, not through the proxy), the call bypasses the caching interception entirely and silently never hits the cache, regardless of configuration. Second: the cache key isn't actually stable across calls — if the method's argument is a complex object without a correct equals/hashCode, or the SpEL key expression references a field that varies in some way not obvious at a glance (e.g. a timestamp embedded in a request object), every call computes a technically-different key and therefore always misses. Both produce the identical symptom of "caching configured correctly but apparently doing nothing," and neither is a cache-provider problem, which is why they're worth ruling out before suspecting Redis or Caffeine itself.

JUNIORQ11. A popular cached endpoint's TTL expires and, for about half a second, your database sees a huge spike of identical queries for the exact same key before settling back down. Diagnose what's happening and name the cheapest fix that requires no new infrastructure.

ROI: ★★★★☆ · Frequency: Medium-High

This is a cache stampede: when a single, very popular entry expires, every concurrent request for that key misses at the same instant and each independently attempts to regenerate it, producing a burst of redundant, identical queries against the backing store for data that only needed to be computed once. The cheapest fix with no new infrastructure is request coalescing (single-flight) or a short-lived lock: the first request to miss regenerates the value while every other concurrent request for that same key waits on (or is served) the one in-flight result instead of independently re-querying. If even that brief wait is undesirable, stale-while-revalidate serves the just-expired value immediately to everyone while exactly one background request refreshes it — no request waits at all, at the cost of serving slightly stale data for that refresh window.

JUNIORQ12. During an incident, the UI shows a value that doesn't match what's in the database, and someone on the call insists "the cache is probably just more up to date, let's trust it." How do you respond, and why?

ROI: ★★★★☆ · Frequency: Medium-High

That reasoning has it backwards: the database is the system of record by construction, and the cache is a secondary, disposable copy optimized purely for fast reads — it can be evicted, lost, or stale, and is never authoritative when it disagrees with the underlying store. "The cache might be more current" is only true in the narrow case of write-behind caching with an unflushed write still pending, which is a specific, nameable scenario you'd check directly (is there a pending async flush for this key) rather than a general excuse to trust the cache over the database during an incident. The default assumption during any cache/database disagreement should be that the cache is wrong until proven otherwise, because trusting whichever layer is more convenient to check first wastes time chasing the wrong side of the discrepancy.

MIDQ13. Compare cache-aside and read-through. When would you prefer one over the other?

ROI: ★★★★★ · Frequency: High

Both populate the cache on a miss, but cache-aside puts that logic in the application (every call site handles the miss itself), while read-through puts it in the cache layer via a configured loader (the application only ever calls the cache). Read-through is preferable when many different call sites read the same entity and you want one centralized, consistently-correct loading path; cache-aside is preferable when you want a simple key-value cache with no special loader support, or need fine-grained control over the fetch logic per call site.

MIDQ14. Why would a team choose write-through over cache-aside for a particular dataset?

ROI: ★★★★☆ · Frequency: Medium-High

Write-through guarantees the cache and the underlying store can never disagree after a successful write, eliminating the entire class of "forgot to invalidate" bugs cache-aside is exposed to. It's the right call when read correctness matters more than write latency and reads vastly outnumber writes, so the extra synchronous write-path cost is amortized across many fast reads.

MIDQ15. Explain versioned/content-addressed cache keys and why they sidestep the invalidation problem.

ROI: ★★★★★ · Frequency: High

Instead of invalidating an existing key when the underlying data changes, the cache key itself encodes a version or content hash of the data, so a change naturally produces a new key rather than requiring the old one to be explicitly deleted. This avoids needing every write path to correctly participate in invalidation — old entries simply age out via normal eviction, never needing active invalidation at all. The trade-off is some duplication, since the old entry lingers unused until evicted.

MIDQ16. Why does hit ratio improve latency disproportionately as it approaches 100%?

ROI: ★★★★★ · Frequency: High

Blended latency is (hit_ratio × cache_latency) + (miss_ratio × origin_latency). Because origin_latency is typically much larger than cache_latency, the miss_ratio term dominates the formula even at a fairly high hit ratio — moving from 90% to 99% hit ratio cuts the miss_ratio term by 10x, producing a disproportionately large improvement in blended latency relative to the size of the percentage-point change.

MIDQ17. How do request coalescing, locking, and stale-while-revalidate each address cache stampede differently?

ROI: ★★★★★ · Frequency: High

Request coalescing makes every concurrent request for the same expired key wait on a single in-flight regeneration rather than triggering their own. Locking has the first request acquire a short-lived lock before regenerating, with others waiting or falling back to the stale value. Stale-while-revalidate serves the just-expired value immediately to every request while triggering exactly one background refresh — it's the only one of the three that never makes any request wait at all, at the cost of briefly serving known-stale data.

MIDQ18. Why is a multi-layer caching strategy (CDN + application cache) more effective than optimizing one layer alone?

ROI: ★★★★★ · Frequency: High

Hit ratios at successive layers multiply together via their miss ratios to determine the fraction of traffic reaching the final, most expensive layer: (1 − hit_ratio_CDN) × (1 − hit_ratio_app). A 70% CDN hit ratio combined with an 80% application cache hit ratio reduces database-bound traffic to just 6% of original traffic — each layer only needs to be moderately effective for the combination to be highly effective, which is a better return than pushing one single layer toward an extreme hit ratio alone.

MIDQ19. A user reports seeing another user's personalized dashboard data on a page you know is served through a shared CDN cache. Before touching any application code, what's the first header you'd check, and why would a misconfiguration there produce exactly this symptom?

ROI: ★★★★★ · Frequency: High

Check the Vary header first. It tells a shared cache which request headers (an auth cookie, an Accept-Language header, anything that makes the response differ per requester) must be factored into the cache key. If it's missing or incomplete for a response that actually varies per user, the CDN computes the same cache key for requests that should have produced different responses, caches the first user's personalized response under that shared key, and serves it to the next user who hits the same key — exactly the symptom reported, and a severe confidentiality failure, not a staleness bug. The fix is ensuring the cache key (via a correct Vary header, or a CDN-specific per-user partitioning mechanism) genuinely captures every input the response varies on, not just the ones that were obvious when the endpoint was first built.

MIDQ20. Why is self-invocation a common gotcha with Spring's @Cacheable?

ROI: ★★★★☆ · Frequency: Medium-High

Spring's caching annotations work via a dynamic proxy wrapping the bean. A method calling another @Cacheable method on this bypasses that proxy entirely, so the call never goes through the caching interception logic — caching is silently skipped, which is a frequent source of confusion since it has nothing to do with cache configuration and everything to do with how Spring AOP proxies are applied.

MIDQ21. Why should negative caching (caching an error or empty result) typically use a shorter TTL than normal successful responses?

ROI: ★★★★☆ · Frequency: Medium-High

Applying the same long TTL to a transient failure or momentarily-empty result can turn a brief blip into a sustained outage, where the cached negative result keeps being served long after the underlying condition has cleared. A deliberately short, separate TTL for negative results lets the system recover quickly once the real condition resolves, while still protecting the backing store from being hammered during the failure itself.

MIDQ22. You're about to cut production traffic over to a freshly restarted Redis cluster that's completely empty. What happens in the first few seconds if you just flip traffic over immediately, and what would you do differently?

ROI: ★★★★☆ · Frequency: Medium-High

A cold cache starts at a 0% hit ratio, so flipping traffic over immediately means every request briefly misses and falls through to the database — the full un-cached cost of the entire traffic volume lands on the database all at once, which can itself trigger a load-related incident, especially if the database's capacity planning assumed the cache was already absorbing most read traffic. The better approach is cache warming: proactively pre-populating the new cluster with known-popular keys (from the working set the old cluster was serving, if available) before routing full production traffic to it, or ramping traffic gradually rather than an instant cutover, so the database never sees the full, un-cached volume spike all at once.

MIDQ23. Why is LRU not always the best eviction policy?

ROI: ★★★★☆ · Frequency: Medium-High

LRU assumes recent access predicts future access, which holds for many workloads, but it can underperform LFU when a smaller set of consistently-popular keys should survive an occasional burst of one-off traffic to unrelated keys — a pure LRU policy would evict a genuinely hot key simply because a flurry of cold, one-time requests happened to touch other keys more recently.

MIDQ24. A team wants to put a third-party CDN in front of an internal API gateway that fronts a dozen backend services, purely to get response caching. What cheaper option would you push them to evaluate first, and what would make the CDN still the right call despite the extra cost?

ROI: ★★★★☆ · Frequency: Medium-High

Push them to evaluate Spring Cloud Gateway's own response-caching filter first — it caches whole HTTP responses at the gateway tier itself, honoring standard Cache-Control headers, for effectively zero added infrastructure since the gateway is already in the request path. That covers the case where the goal is reducing redundant backend calls within your own infrastructure. A third-party CDN is still the right call despite the extra cost specifically when the benefit needed is one a gateway-tier cache can't provide: serving cached content from edge locations physically close to geographically distributed end users (cutting network latency the gateway's own single location can't touch), or absorbing traffic volume before it ever reaches your infrastructure at all during a spike. If the real goal is just avoiding repeat backend work for traffic already inside your network, the gateway-tier cache gets most of the benefit at a fraction of the cost and complexity.

MIDQ25. Why does purge-on-deploy matter, and what's the risk of skipping it?

ROI: ★★★★★ · Frequency: High

Without an explicit purge step in the deploy pipeline, a deployed change to cached content only surfaces once the existing cache entries' TTLs naturally expire — meaning users can see stale, pre-deploy behavior for up to the full TTL window. Explicitly purging (or using versioned URLs that sidestep purging entirely) makes a deploy's effects visible immediately and predictably instead of depending on however long a TTL happens to be configured for.

MIDQ26. What's the difference between a cache's "working set" and its total possible dataset, and why does this matter for sizing?

ROI: ★★★★☆ · Frequency: Medium-High

Real access patterns are typically skewed (Zipf-like), with a small fraction of keys accounting for most requests. The "working set" is that comparatively small set of currently-popular keys, which is all a cache actually needs to hold to achieve a high hit ratio — sizing a cache for the entire dataset, rather than the working set, is usually wasted memory spend that an LRU/LFU eviction policy was already handling correctly.

SENIORQ27. A product page's price is occasionally shown stale to users for several minutes after a price change. Diagnose the likely cause and propose fixes.

ROI: ★★★★★ · Frequency: High at senior level

The most likely cause is a TTL-based invalidation strategy with a TTL long enough to produce a multi-minute staleness window, with no event-driven invalidation layered on top to shorten it for this specific, business-sensitive field. Fixes: add event-driven invalidation on the price-update write path (evict or refresh the specific cached entry the instant the price changes, rather than waiting for the TTL), audit every write path that can change price (admin tools, batch imports, not just the primary service) to ensure all of them participate in that invalidation, and consider a much shorter TTL as a safety net in case any invalidation path is ever missed. If the staleness is happening at the CDN layer specifically, the fix also needs to include a CDN purge call on price update, not just an application-cache eviction.

SENIORQ28. Design the caching strategy for a product catalog page: what belongs at the CDN layer, what belongs at the application cache layer, and why?

ROI: ★★★★★ · Frequency: High at senior level

Static assets (images, CSS, JS) belong at the CDN with long TTLs and versioned/content-addressed URLs, since they rarely change and can be invalidated for free by deploying a new URL. The catalog page's rendered HTML, if largely identical across users, can also be CDN-cached with a short-to-moderate TTL plus event-driven purge on catalog updates. Per-user elements (personalized recommendations, cart contents, pricing tied to a loyalty tier) must not be cached at the shared CDN layer at all — those belong in the application-level distributed cache, keyed per-user or per-session, where cache-aside with a moderate TTL and explicit invalidation on the relevant write paths is appropriate. The dividing line is always: can this specific piece of content be safely shared across different users without a Vary-header or cache-key mistake leaking one user's data to another.

SENIORQ29. Why might write-behind caching be the wrong choice even when write throughput is the dominant concern?

ROI: ★★★★☆ · Frequency: Medium-High at senior level

Write-behind's async flush means a cache node failure between the acknowledged write and the actual flush to the underlying store results in permanently lost data, with no record of the write ever having happened. For any data with a genuine durability requirement — financial transactions, audit records, anything a user would reasonably expect to survive a crash — that risk is unacceptable regardless of how much write throughput is gained. Write-behind is the right choice specifically when the backing store's limited write capacity justifies batching AND the data's durability requirement explicitly tolerates bounded loss — not simply whenever write throughput is the stated priority.

Interview Gold Point: Push further by asking what "bounded loss" actually means in practice — a strong answer quantifies it (e.g., "at most N seconds of writes, or the current unflushed batch size") rather than leaving it as an abstract risk, since that number is exactly what a stakeholder needs to explicitly sign off on before write-behind is an acceptable trade for this specific dataset.
SENIORQ30. How would you detect a silent cache hit-ratio regression in production, and what would you check first?

ROI: ★★★★★ · Frequency: High at senior level

Hit ratio needs to be an alerted, continuously monitored metric per cache/layer, not something only checked reactively when latency complaints arrive — by the time users notice, the regression has likely been silently inflating backend load and latency for a while. If an alert fires, I'd check first whether a recent deploy changed the shape of cache keys (a refactor that altered a method's parameters under @Cacheable, changing effective keys and causing what looks like universal misses), second whether eviction pressure increased (a growth in the working set size outpacing cache capacity), and third whether an upstream change altered request patterns in a way that genuinely reduced natural cache-ability (e.g., more personalized responses that were previously cacheable and shared).

SENIORQ31. Explain the trade-off between a long TTL and event-driven invalidation for a specific piece of data, and how you'd decide between them.

ROI: ★★★★★ · Frequency: High at senior level

A long TTL is operationally simpler (no coordination needed with every write path) but produces a correspondingly wide worst-case staleness window. Event-driven invalidation tightens that window dramatically but is only as reliable as the completeness of every write path's participation — a single missed path (a batch job, a direct migration) leaves stale data with no TTL safety net to eventually correct it unless one is layered in anyway. The decision should follow the actual cost of staleness for this specific data: cosmetic, rarely-noticed data can tolerate a long TTL alone; anything where staleness causes a real user-facing or business-logic problem (pricing, inventory, permissions) warrants event-driven invalidation, usually still paired with a moderate TTL as a safety net rather than relying on event-driven invalidation's completeness alone.

SENIORQ32. A CDN purge API is called on every single content update, including very minor ones, and the team is seeing origin load spikes right after each purge. Explain why, and how you'd address it.

ROI: ★★★★☆ · Frequency: Medium-High at senior level

Purging removes the cached entry at the CDN, so the next request for that content is guaranteed to be a miss that travels all the way to the origin (through the origin shield, Section 5.2) — if purges happen frequently and affect popular content, this effectively forces a cache-stampede-like spike every single time, since many concurrent users requesting that content right after a purge all miss simultaneously. Addressing it: batch or debounce purges for rapidly-changing content rather than purging on every single update, rely on versioned/content-addressed URLs for content where that's feasible (sidestepping purging entirely, per Section 4.5), and ensure the origin shield plus stampede protections (request coalescing or stale-while-revalidate) are actually in place so a post-purge miss burst collapses into a single origin fetch rather than many simultaneous ones.

SENIORQ33. Why can "cache everything aggressively" actively hurt a system, beyond the risk of serving stale data?

ROI: ★★★★☆ · Frequency: Medium-High at senior level

Beyond staleness risk, over-caching adds real operational cost and complexity that doesn't pay for itself: caching data with a low natural reuse rate wastes cache memory capacity that could otherwise hold the genuinely hot working set (Section 6.4), diluting the effective hit ratio for data that actually benefits from caching. It also multiplies the invalidation surface area — every additional cached entity is one more thing every relevant write path must remember to invalidate correctly — increasing the odds of exactly the kind of missed-invalidation bug Section 3 identifies as the hard part of caching, for marginal or no latency benefit if that data was rarely going to be re-requested anyway.

STAFFQ34. Design the full caching architecture for a global e-commerce platform's product catalog, covering the browser through the database, including invalidation strategy and failure handling.

ROI: ★★★★★ · Frequency: High at staff level

Browser: short max-age plus ETag-based revalidation on catalog pages, so repeat views are cheap without serving indefinitely stale data. CDN edge with an origin shield (Section 5.2): cache rendered catalog pages and static assets, with static assets using content-addressed URLs (no invalidation ever needed) and dynamic catalog HTML using a moderate TTL plus an explicit purge call wired into the catalog-update pipeline, batched/debounced per Q32's reasoning to avoid self-inflicted stampedes. Application-level distributed cache (Redis): cache-aside for individual product records and computed aggregates (e.g., category listings), keyed per product/category with event-driven invalidation triggered by the product-update service's write path, backed by a moderate TTL safety net in case any write path is missed, and request-coalescing/stale-while-revalidate protection on the handful of highest-traffic product keys. Failure handling: if Redis is unavailable, cache-aside should degrade to reading directly from the database rather than failing the request outright (treating the cache as a performance optimization, never a dependency the request cannot survive without) — with monitoring that makes this degraded mode visible immediately, since database load will spike the instant the cache stops absorbing it. The staff-level framing: every layer gets its own invalidation mechanism matched to its own staleness tolerance and failure mode, rather than one invalidation strategy applied uniformly across all of them.

Interview Gold Point: Explicitly call out that the database must remain able to survive a full cache outage at reduced (not zero) capacity — a design where the application simply crashes or 500s when Redis is unreachable has quietly made a performance optimization into a hard dependency, which is a design smell worth naming directly.
STAFFQ35. A team wants to cache authenticated, per-user API responses at the CDN layer to reduce origin load. Evaluate this proposal.

ROI: ★★★★★ · Frequency: High at staff level

This needs to be evaluated as a security decision first and a performance optimization second. Caching per-user content at a shared CDN layer is only safe if the cache key genuinely and completely captures whatever makes the response differ per user (correctly scoped by an opaque per-user identifier in the key, with a correct Vary or equivalent CDN-specific per-user caching feature, and marked appropriately so it's never served across users) — getting this wrong, even in one edge case, risks serving one user's private data to another, a severe confidentiality failure, not a staleness bug. Many CDN providers offer purpose-built mechanisms for this (edge-side includes, per-user cache partitioning) rather than relying on generic Vary header semantics, which is the safer path if this pattern is pursued. The honest recommendation: unless the team has a specific, well-tested mechanism for safely partitioning per-user cache entries at the CDN, the lower-risk path is caching per-user data only at the application-level distributed cache (which is already correctly scoped per user by construction) and reserving CDN caching for genuinely shared, non-personalized content — origin load from authenticated traffic is better addressed by scaling the application cache layer than by taking on this specific class of security risk at the edge.

STAFFQ36. How would you reason about the right TTL for a piece of data when there's no clear business requirement stating an acceptable staleness window?

ROI: ★★★★☆ · Frequency: Medium-High at staff level

Absent an explicit requirement, I'd derive a reasonable default from the data's actual observed change frequency and the cost of being wrong in each direction: if the data changes on the order of hours and being briefly stale carries low cost, a TTL on the order of minutes is a safe, conservative starting point that still captures most of the available caching benefit. I'd treat this as a hypothesis to validate, not a final answer — instrument the actual hit ratio and the actual observed staleness-related complaints (support tickets, bug reports) after deploying it, and adjust the TTL based on real data rather than guessing once and leaving it unexamined indefinitely. The staff-level point is recognizing that "no explicit requirement" is not the same as "no requirement" — someone, somewhere, has an implicit expectation about freshness, and the engineering job is making that implicit expectation explicit and then measuring against it, rather than picking an arbitrary number and hoping it's right.

STAFFQ37. Your system's database can handle its current load comfortably without any caching at all. Is caching still worth introducing? Argue both sides.

ROI: ★★★★☆ · Frequency: Medium-High at staff level

For: caching still reduces latency for end users directly (per Section 6.2's blended-latency math, even a comfortably-loaded database's round trip is slower than a cache hit), and it buys headroom against future growth or traffic spikes before the database becomes the bottleneck — introducing it proactively, while load is low, is cheaper and lower-risk than retrofitting it under production pressure during an incident. Against: every cache introduced is additional operational surface area and additional invalidation complexity (Section 3's hard problem) for a system that doesn't currently need the load relief it provides — premature caching can introduce staleness bugs and operational overhead for a benefit (database load reduction) the system doesn't yet require, violating a reasonable "don't add complexity you can't yet justify" engineering discipline. The staff-level resolution: if the primary motivation is latency rather than load, a narrowly-scoped cache for the specific slow, high-traffic endpoints that actually matter to user-perceived latency is usually justified; a broad, speculative caching layer added purely because "caching is generally good practice," with no specific latency or load problem it's solving, is the version of this decision worth pushing back on.

STAFFQ38. Design a strategy to safely roll out a change to a widely-used cached entity's shape (e.g., adding a required field) across a system with many services reading from the same distributed cache.

ROI: ★★★★★ · Frequency: Medium-High at staff level

The core risk is that old cached entries (in the previous shape) will still be present and read by newly-deployed code expecting the new shape, and vice versa for services not yet deployed with the new code reading newly-shaped entries written by already-deployed services — a classic rolling-deploy compatibility problem, now compounded by the cache persisting data across the deploy boundary rather than being freshly created per request. The safest approach is changing the cache key itself to include a schema version (a direct application of Section 4.5's versioned-key pattern) whenever the shape changes, so old and new shapes simply exist under different keys rather than colliding — every service reads and writes only the key version matching its own currently-deployed code's expectations, and old-version entries harmlessly age out via normal eviction once no service is reading them anymore. This avoids needing a flag-day cutover or complex dual-read/dual-write logic, at the cost of a brief period of reduced effective hit ratio while both key versions coexist during the rollout.

MIDQ39. What is the difference between a public and private directive in a Cache-Control header, and why does it matter for CDN caching specifically?

ROI: ★★★★☆ · Frequency: Medium-High

public indicates the response may be cached by any cache, including a shared CDN cache serving many different users. private indicates the response may only be cached by the end user's own browser, never a shared intermediate cache. This matters directly for CDN caching because marking per-user or sensitive content as public by mistake can cause a shared CDN to cache and serve one user's response to other users entirely — the directive is a security boundary, not just a caching hint.

MIDQ40. Why does java/21-CACHING-STRATEGIES.html's Redis/Caffeine implementation detail matter less at the architecture level than the decision of where in the request path a cache sits?

ROI: ★★★☆☆ · Frequency: Medium

Which specific cache technology is used (Redis vs. Caffeine vs. Memcached) is largely an implementation detail that can be swapped without changing the architecture's fundamental shape, as long as the chosen technology supports the access pattern needed. The architectural decisions that actually determine whether a system behaves correctly and performs well — which pattern (cache-aside, read-through, write-through, write-behind), which layer (browser, CDN, application), and which invalidation strategy — are independent of that implementation choice and are what this chapter focuses on; getting those architectural decisions wrong isn't fixed by picking a "better" caching library.

JUNIORQ41. A client keeps re-downloading a multi-megabyte asset in full on every request even though the content hasn't changed in weeks, and the response headers show no ETag or Last-Modified. What are you losing by not setting one, concretely, and how would you quantify the fix's impact before shipping it?

ROI: ★★★★☆ · Frequency: Medium-High

Without an ETag (or Last-Modified), the client has no cheap way to ask "has this changed since I last fetched it" — every request either re-downloads the full body or relies purely on a TTL-based freshness window that, once expired, also forces a full re-download regardless of whether the content actually changed. Adding an ETag lets the client send it back via If-None-Match on a subsequent request, and if the content hasn't changed the server replies with a lightweight 304 Not Modified instead of the full body, letting the client safely keep its existing cached copy. To quantify the fix's impact before shipping: compare the asset's actual change frequency against its request volume — for content requested often but rarely changed, the bandwidth and latency saved by collapsing most revalidations into 304s instead of full re-downloads can be estimated directly as (unchanged-fetch count) × (asset size), which is usually the number that gets this prioritized.

MIDQ42. Why is it important to distinguish between the CDN layer and GeoDNS (from Chapter 03), given that both involve routing requests based on geography?

ROI: ★★★★☆ · Frequency: Medium-High

GeoDNS decides, at the DNS resolution step, which data center or origin a request is ultimately bound for — a coarse, infrequently-changing decision made before a single packet reaches your infrastructure. A CDN's edge network intercepts and serves a large fraction of requests using its own independent routing (often anycast-based) before they ever need to reach the origin at all, and can answer directly from cache without any involvement from the origin-bound routing decision GeoDNS made. They're complementary, different layers, not two names for the same mechanism.

SENIORQ43. How would you measure whether a proposed new cache layer is actually worth its added complexity before building it?

ROI: ★★★★☆ · Frequency: Medium-High at senior level

Instrument the candidate data's actual read/write ratio and request volume first, and estimate the expected hit ratio from its natural popularity distribution (Section 6.4) rather than assuming a high hit ratio — a dataset with a flat, non-skewed access pattern or a very high write-to-read ratio may never achieve a hit ratio good enough to justify the added invalidation surface area. Then project the blended-latency and backend-load improvement (Section 6.2/6.3) using that realistic estimated hit ratio, and weigh it explicitly against the ongoing cost of correctly maintaining invalidation across every write path — if the projected improvement is marginal and the write paths are numerous or hard to fully enumerate, the honest answer is often that this specific cache isn't worth building yet.

MIDQ44. What's a practical reason to use Caffeine (or another local, in-process cache) in addition to a distributed cache like Redis, rather than relying on Redis alone?

ROI: ★★★★☆ · Frequency: Medium-High

A distributed cache still costs a real network round trip per access, which, while far cheaper than a database query, is not free. For extremely hot, small, rarely-changing data accessed on nearly every request, an additional local in-process cache layer in front of the distributed cache can eliminate even that network hop — at the cost of a more complex invalidation story, since now both the local and distributed layers need to agree on freshness rather than just one.

STAFFQ45. A staff engineer on another team argues caching should always be added at the lowest layer possible (closest to the database) rather than higher layers (CDN/edge), to keep the system "simple." How do you respond?

ROI: ★★★★★ · Frequency: Medium-High at staff level

That framing conflates "fewer layers" with "simpler," but the two aren't the same thing — caching only close to the database still requires every request to traverse the network, the load balancer, and the application layer before it can possibly hit a cache, forfeiting the latency and backend-load benefits that Section 6.3's multiplicative hit-ratio math shows come specifically from catching requests as early and cheaply as possible. The actual complexity cost of caching comes from invalidation coverage and staleness tolerance (Section 3), which exists at every layer regardless of how many layers you choose to use — consolidating to one layer doesn't eliminate that cost, it just concentrates all of a system's caching risk and benefit into a single point. The better framing is matching each layer to the kind of content it's genuinely suited for (static/shared content at the CDN, since its staleness tolerance and invalidation needs are usually simplest there; dynamic/per-user data at the application layer, where correctness-sensitive invalidation is easier to coordinate with the write path) rather than optimizing for layer count as a proxy for simplicity.

JUNIORQ46. Redis goes down in production for eight minutes. In a well-designed cache-aside implementation, what should the user-facing impact be, and what does it mean about your architecture if the answer is instead "the site went down"?

ROI: ★★★★☆ · Frequency: Medium-High

In a well-designed cache-aside implementation, every cache-miss code path is exactly what runs when the cache is entirely unavailable, so the application should fall back to reading directly from the database rather than failing the request — users should see degraded latency (every request now pays the full database round-trip cost instead of a cache hit) and the database should see a real load spike, but the site itself should stay up. If the actual answer is "the site went down," that means the cache was quietly treated as a hard dependency somewhere — a call site with no fallback path, a connection pool that blocks or throws instead of degrading, or a database that genuinely cannot survive its normal load without the cache absorbing most of it — which is a design smell worth fixing regardless of how rare a full Redis outage is expected to be, since a cache's entire value proposition is being a performance optimization the system can survive losing, not a dependency it can't.

MIDQ47. Why might caching an aggregate/computed value (e.g., a category's total product count) be riskier to invalidate correctly than caching a single entity (e.g., one product)?

ROI: ★★★★☆ · Frequency: Medium-High

A single entity has one clear, enumerable write path that changes it directly. An aggregate value depends on potentially many underlying entities changing (any product being added, removed, or changed in that category), so every one of those underlying write paths now also needs to trigger invalidation of the aggregate — multiplying the invalidation surface area described in Section 3, and making it considerably easier to miss one contributing write path and leave the aggregate quietly wrong.

SENIORQ48. How would you design cache invalidation for data that's updated by an external, third-party webhook rather than your own application's write path?

ROI: ★★★★☆ · Frequency: Medium-High at senior level

Treat the webhook receiver as just another write path that must participate in invalidation, exactly like an internal service's write endpoint — the webhook handler should trigger the same event-driven invalidation (or cache update) that any other change to this data would trigger, rather than being treated as a separate, exempt case. Because webhook delivery itself can be unreliable (delayed, duplicated, or occasionally dropped by the third party), this specific data also benefits from a shorter TTL safety net than data updated exclusively through fully-reliable internal write paths, since a missed or delayed webhook is a more plausible failure mode here than a bug in your own code.

MIDQ49. What's the risk of caching a paginated API response using only the page number as part of the cache key, without accounting for the underlying dataset changing?

ROI: ★★★★☆ · Frequency: Medium-High

If items are added to or removed from the underlying dataset between cache population and the TTL expiring, a cached page can show duplicate items (an item that shifted from page 2 to page 1 appears on both, if page 1 was already cached) or skip items entirely (the reverse shift) — the cache key being "correct" with respect to the page number alone doesn't make the cached content consistent with the current true ordering. This is usually addressed with either a short TTL appropriate to how frequently the dataset actually changes, or a cursor/version-based pagination scheme that's inherently more stable under concurrent modification than raw page-number offsets.

STAFFQ50. You're asked to reduce database load by 90% for a read-heavy service without changing database hardware. Walk through how caching contributes to that target, and what else might be required.

ROI: ★★★★★ · Frequency: High at staff level

A 90% reduction in database-bound traffic corresponds, per Section 6.3's multiplicative formula, to needing the combined miss ratio across all caching layers in front of the database to be roughly 0.1 — achievable, for example, with a CDN/application-cache combination like 70% and 67% hit ratios respectively ((1-0.7)×(1-0.67)≈0.1), rather than needing any single layer alone to hit an extreme 90%+ figure. I'd start by instrumenting the actual current hit ratios at each existing layer to see how far short of that combined target the system currently sits, then prioritize whichever layer has the most achievable improvement headroom — often the application-level cache, since it's usually the easiest to extend coverage on without touching client-facing behavior. If caching alone can't close the gap (e.g., because a meaningful fraction of traffic is genuinely uncacheable — highly personalized, or write-heavy data), the remaining options are read replicas (spreading read load across additional database copies) or reducing query cost itself (indexing, query optimization) — caching is usually the highest-leverage first lever precisely because of the math in Section 6.3, but it's not guaranteed to close an arbitrary target gap alone if the workload's actual cacheable fraction is lower than the target requires.

Interview Gold Point: A strong answer explicitly states the math rather than hand-waving "we'll add caching and it'll probably work" — naming the required combined miss ratio up front, and treating the 90% target as something to validate against instrumented, current hit ratios rather than assumed achievable by caching alone, is exactly the kind of quantitative rigor that distinguishes a staff-level answer from a mid-level one on this question.

16. SUMMARY

  • Caching avoids redundant, expensive work by storing and reusing a previous result; the core trade-off in every caching decision is freshness versus efficiency, and cache invalidation is genuinely one of the hardest problems in the field because a cache is a copy of the truth living outside the system of record.
  • Cache-aside, read-through, write-through, and write-behind each place population and write responsibility differently, trading write latency, implementation simplicity, and data-loss risk against each other — there is no universally correct pattern, only the right one for a given data's read/write ratio and durability requirement.
  • TTL, event-driven invalidation, and versioned/content-addressed keys are the three standard invalidation strategies, and real production systems typically combine all three rather than relying on any single one alone.
  • A real request's path typically crosses browser cache, CDN edge (with an origin shield protecting the origin from redundant simultaneous misses), application-level distributed cache, and finally the database — hit ratios at each layer multiply together, so moderate improvements at multiple layers compound into a dramatic reduction in traffic reaching the database.
  • Cache stampede, cache poisoning via unkeyed cache keys, and caching personalized content at a shared layer are recurring, serious failure modes that require deliberate mitigation (request coalescing, correct Vary/cache-key scoping, private-vs-public cache-control directives) rather than being left as implicit assumptions.
  • Spring's @Cacheable/@CacheEvict/@CachePut implement cache-aside declaratively at the application layer, Spring Cloud Gateway can cache whole responses at the edge of your own infrastructure, and a Spring Boot controller integrates with a CDN primarily by setting correct Cache-Control/ETag headers and participating in a deploy pipeline's purge step — none of which replaces the architectural judgment of deciding what to cache, where, and for how long.
