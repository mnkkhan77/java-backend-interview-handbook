CHAPTER 03 — LOAD BALANCING & DNS

Volume 2 — Scaling the Infrastructure Layer · Chapter 3 of 12

CAP Theorem & Consistency Models (Chapter 02) taught you how to reason about trade-offs once a system has already been split across multiple nodes — but it never explained how a single incoming request finds its way to any particular node in the first place, or how a fleet of identical instances is kept from collapsing the moment one of them gets slow or dies. That is the job of load balancing and DNS: the unglamorous, utterly load-bearing layer that sits between "my service has five replicas" and "a client's request actually lands on a healthy one of them." Nearly every production outage post-mortem touches this layer somewhere — a bad health check that never fires, a sticky session that pins a user to a dead instance, a DNS TTL that is too long to fail over quickly — so a precise mental model here pays for itself the first time you are paged.

1. MOTIVATION

Imagine you have built a service, proven it works, and now need it to survive real traffic: thousands of concurrent users, occasional traffic spikes, and the certainty that any individual machine will eventually fail, slow down, or need to be taken offline for a deploy. The single-instance mental model — one process, one IP address, one point of failure — breaks down immediately at this scale. You need multiple instances of the same service running simultaneously, which immediately raises a new, unavoidable question: given many interchangeable instances, which one should handle this specific request, right now?

Answering that question badly is expensive in very visible ways. Send every request to the same instance and you have not scaled at all — you have just added idle, wasted machines next to a single bottleneck. Send requests to an instance that has already crashed and users see errors instead of your product. Send a user's first request to instance A and their second request, which depends on in-memory state from the first, to instance B and the application breaks in a way that is maddening to reproduce. Load balancing is the discipline of distributing requests across a fleet so that capacity is actually used, failures are invisible to users, and the system behaves as one coherent service rather than a loose bag of machines.

DNS sits one layer above this and is just as easy to under-think. Before a client's request can be load-balanced across your fleet, the client has to resolve a hostname to an IP address at all — and that resolution step is itself a decision point: which data center should this user's traffic even be routed toward? Treating DNS as "just a lookup that happens before the real system design starts" is a common and costly interview mistake, because DNS misconfiguration (overly long TTLs, no geographic awareness, no health-aware failover) directly undermines every load-balancing decision made downstream of it. This chapter treats both as one continuous pipeline, because in a real deployment, that is exactly what they are.

2. HISTORICAL BACKGROUND

2.1 DNS: Solving Name Lookup at Internet Scale (1983-1987)

The Domain Name System was introduced by Paul Mockapetris in 1983 (RFC 882/883, later refined in RFC 1034/1035) to solve a scaling problem that had nothing to do with load balancing originally: the early ARPANET resolved hostnames using a single, centrally-maintained flat text file (HOSTS.TXT) that every machine downloaded from one server. As the network grew, that approach became unworkable — one file, one point of failure, no delegation of authority. DNS replaced it with a distributed, hierarchical, cacheable lookup system: authority for a domain could be delegated down a tree (root servers, then top-level-domain servers, then a domain's own authoritative servers), and answers could be cached for a configurable duration, so most lookups never had to travel far. That hierarchical-plus-cacheable design is still the exact shape of DNS today, and it is also precisely what makes DNS usable as a (coarse) load-balancing and failover tool decades later.

2.2 Hardware Load Balancers and the Rise of the Dedicated Appliance (1990s)

As web traffic grew through the 1990s, a new failure mode appeared: a single web server, however powerful, could not keep up with a popular site's traffic, and simply running several web servers behind round-robin DNS (an early, crude load-balancing trick — return a different IP for the same hostname on each DNS query) turned out to be fragile, because DNS had no concept of "is this server actually healthy right now." This drove the emergence of dedicated hardware load balancers — purpose-built appliances (F5's BIG-IP, Cisco's LocalDirector, and others) that sat in front of a server farm, actively health-checked each backend, and distributed TCP connections intelligently. These devices operated primarily at the transport layer (Layer 4), which is why "L4 load balancer" and "hardware load balancer" became near-synonyms for a long stretch of infrastructure history.

2.3 Software Load Balancers and the Shift to Commodity Infrastructure (2000s-2010s)

Dedicated hardware appliances were expensive, difficult to scale elastically, and a poor fit for the virtualized and later containerized infrastructure that started dominating the 2000s and 2010s. Software load balancers emerged to fill that gap: HAProxy (2000) and later nginx (2004, originally built as a web server, later widely adopted as a reverse proxy and load balancer) proved that commodity servers running the right software could match or exceed purpose-built hardware for most workloads, at a fraction of the cost and with far more operational flexibility — they could be versioned, configured as code, and scaled horizontally like any other service. This shift is what made load balancing a software-engineering concern rather than a purely network-operations one, and it is the direct ancestor of every application-layer (L7) load balancer discussed later in this chapter.

2.4 Cloud-Managed Load Balancing and the Service Mesh Era (2010s-Present)

Public cloud providers absorbed load balancing into managed services — AWS's Elastic Load Balancer family (Classic, then Application Load Balancer and Network Load Balancer), Google Cloud Load Balancing, Azure Load Balancer — removing the operational burden of running and patching the load-balancing layer yourself. In parallel, the rise of microservices and container orchestration (Kubernetes, from 2014 onward) introduced a new problem: load balancing was no longer just "client traffic into the data center," it was also "service A's traffic to service B," happening constantly, internally, between dozens or hundreds of services. This gave rise to the service mesh pattern (Envoy, originally built at Lyft and released in 2016, became the de facto standard data-plane proxy; Istio and Linkerd built control planes around it), which pushes a lightweight load-balancing proxy (a "sidecar") next to every single service instance, handling internal east-west traffic with the same rigor previously reserved for external north-south traffic.

3. PROBLEM STATEMENT

Strip away the specific technologies and the problem load balancing and DNS jointly solve is this:

Given a pool of interchangeable (or near-interchangeable) service instances spread across machines, racks, availability zones, or even continents, how do you route each incoming request to a healthy instance, in a way that spreads load fairly, survives individual instance and even entire data-center failures, and does so without the client needing any awareness of which specific instance it ultimately talks to?

This problem statement has several components that are easy to conflate but are actually distinct sub-problems, and keeping them separate is the difference between a vague answer and a precise one in an interview: discovery (how does a client, or a load balancer, even learn what instances currently exist and where they are?), selection (given several healthy candidates, which one gets this particular request, and by what algorithm?), health detection (how do we know an instance has stopped being a valid candidate, ideally before it causes user-visible errors?), and state (does this request depend on having been routed to the same instance as a previous request from the same client, and if so, how does that constraint interact with the goal of spreading load freely?).

DNS and load balancers solve these sub-problems at different granularities and different timescales. DNS makes a coarse-grained, relatively slow-changing decision — typically "which data center or region should this client's traffic even be directed toward" — because DNS answers are cached by clients and intermediate resolvers for a duration measured in minutes, which makes DNS a poor tool for fast, fine-grained failover but a perfectly good tool for geographic routing and coarse disaster recovery. Load balancers make a fine-grained, fast-changing decision — "which specific instance, of the ones already narrowed down by DNS, handles this specific request, right now" — informed by near-real-time health and load signals that would be far too volatile to encode in a DNS record. Understanding that division of labor is the single most important conceptual takeaway of this chapter.

4. THEORY

4.1 DNS Resolution, Mechanically

When a client needs to reach api.example.com, it does not usually ask a single authoritative server directly. A typical resolution path is: the client's stub resolver asks a recursive resolver (often run by the client's ISP, or a public one like Cloudflare's 1.1.1.1 or Google's 8.8.8.8); the recursive resolver, if it does not already have a cached answer, asks a root server which TLD server is authoritative for .com, then asks that TLD server which name server is authoritative for example.com, then finally asks that authoritative name server for the actual A (IPv4) or AAAA (IPv6) record for api.example.com. Every answer along this chain carries a TTL (time to live), instructing resolvers how long they may cache that answer before asking again. This caching is what makes DNS scale to the entire internet without every single request round-tripping to an authoritative server — and it is also exactly what makes DNS a blunt instrument for fast failover: an intermediate resolver that cached a dead IP for a 300-second TTL will keep handing that dead IP to clients for up to five minutes, regardless of how quickly you update the record.

4.2 DNS-Based Load Balancing and GeoDNS

The simplest DNS-based load-balancing technique is round-robin DNS: configure multiple A records for the same hostname, and the authoritative server returns them in rotating (or random) order, so successive resolutions spread client traffic across multiple IPs. This is coarse and has no health awareness whatsoever — a dead IP keeps being handed out until someone manually removes the record — but it costs nothing and requires no additional infrastructure, which is why it still shows up for very simple multi-region setups.

GeoDNS is a more deliberate evolution of the same idea: the authoritative DNS server inspects the resolver's (and by extension, approximately, the client's) geographic location or network origin, and returns a different IP address depending on where the request is coming from — typically the IP of the nearest or best-performing regional deployment. This is the mechanism behind "a user in Singapore gets routed to the Singapore data center, a user in Frankfurt gets routed to the Frankfurt one" without either user's client needing any special logic — the routing decision is made entirely at the DNS layer, before a single TCP packet reaches your infrastructure. Many managed DNS providers (Route 53 with latency-based or geolocation routing policies, Cloudflare, NS1) also layer in health checks on top of GeoDNS, so an unhealthy region can be automatically removed from the pool of answers a given query might receive — narrowing, though not eliminating, the "stale cached answer" problem described above, since it still only takes effect once the TTL expires for clients who already cached the old answer.

It is worth being explicit about where DNS-based routing stops and CDN edge routing begins, because the two are easy to conflate: DNS (GeoDNS included) decides which data center or origin a request is ultimately bound for, while a CDN's edge network (covered in full in Chapter 04 — Caching & CDNs at the Architecture Level) intercepts and serves a huge fraction of requests before they ever need to reach your origin at all, using its own independent anycast-based routing. This chapter does not re-teach CDN edge mechanics; just hold onto the fact that in a real deployment, GeoDNS and a CDN's edge network are two different, complementary routing layers, not the same thing wearing two names.

A useful way to internalize the difference: an L4 load balancer is making a decision roughly equivalent to "which phone line do I connect this call to," based only on caller ID and which number was dialed — it cannot listen to what the caller actually says. An L7 load balancer is more like a receptionist who actually answers the call, listens to the request ("I need the billing department"), and routes accordingly — but that requires actually opening and reading the conversation, which costs more work per call. This is precisely why L4 load balancers are faster and cheaper per connection, while L7 load balancers are more capable but more expensive per request — there is no universally "better" choice, only the right choice for what the routing decision actually needs to see.

The judgment call an interviewer is really testing with these options is whether you understand that "which algorithm" is a question with a context-dependent answer, not a single universally correct one: round robin is the right default specifically because it is simple and usually good enough; least connections earns its added bookkeeping cost specifically when request duration is uneven; latency-aware algorithms earn their additional measurement overhead specifically when raw connection count fails to correlate with actual instance health or speed.

4.5 Health Checks

A load balancer's routing decisions are only as good as its knowledge of which instances are actually healthy, so health checking is not an optional add-on — it is the mechanism that makes every algorithm in Section 4.4 actually safe to use in production. Two broad styles exist: passive health checks infer health from real traffic (an instance that starts returning errors or timing out on live requests gets marked unhealthy), and active health checks have the load balancer independently probe each instance on a fixed interval (an HTTP GET to a dedicated health endpoint, or a simple TCP connect) regardless of whether real traffic is currently flowing to it.

Active health checks typically need several tunable parameters to behave well in practice: an interval (how often to check), a timeout (how long to wait for a response before considering that single check a failure), and threshold counts for both directions — an unhealthy threshold (how many consecutive failures before removing an instance from rotation) and a healthy threshold (how many consecutive successes before adding a recovered instance back). These thresholds exist specifically to avoid flapping: an instance experiencing one transient blip should not be yanked out of rotation and immediately put back in on a single probe's result, because that kind of oscillation itself becomes a source of instability and uneven load distribution.

5. INTERNAL WORKING

5.1 Sticky Sessions and the Tension With Statelessness

Many load-balancing algorithms assume that any healthy instance is equally valid for any request — an assumption that breaks the moment an application keeps per-user state in an instance's local memory (an in-process session object, a local cache keyed by user, an in-memory shopping cart) rather than in a shared external store. When that assumption breaks, the load balancer needs sticky sessions (also called session affinity): a mechanism — commonly a cookie the load balancer sets and reads, or a consistent-hashing scheme over a client identifier — that routes a given client's subsequent requests back to the same instance that handled its first request.

Sticky sessions solve the immediate symptom but introduce a structural tension with everything else this chapter is built around. First, they undermine even load distribution: if one instance happens to accumulate a disproportionate number of "sticky" long-lived users, no load-balancing algorithm can rebalance that instance's load away from it without breaking those users' sessions. Second, and more seriously, they undermine horizontal scaling and failure tolerance: if the instance a client is stuck to dies, that client's session-dependent state dies with it, and no other instance can serve that client correctly until it re-authenticates or otherwise rebuilds its state — the opposite of the resilience load balancing exists to provide in the first place. This is precisely why the dominant modern practice is to design services to be stateless at the instance level — pushing session state into a shared, externally accessible store (Redis, a database, or a signed token the client itself carries, like a JWT) — so that literally any healthy instance can serve literally any request, and sticky sessions become an optimization (for cache locality, say) rather than a correctness requirement. When you see sticky sessions used purely to paper over an application that was never designed to be stateless, that is a design smell worth calling out explicitly in an interview.

5.2 A Request's Full Path Through a Real Deployment

Pulling DNS and every layer of load balancing together, here is what actually happens, step by step, when a user's browser requests https://app.example.com/orders/42 against a realistic modern production deployment:

  1. DNS resolution: the client's resolver queries the authoritative DNS for app.example.com. If GeoDNS is configured, the answer returned depends on the client's apparent location — say, the client is in Europe and receives the IP address fronting the European deployment, not the one fronting US-East.
  2. Edge / CDN layer: the request first reaches a CDN point of presence close to the client. If this were a cacheable static asset, the CDN might answer directly and nothing downstream of this step would ever see the request (full mechanics in Chapter 04). For a dynamic, per-user API call like this one, the CDN passes the request through toward the origin.
  3. L7 load balancer / API gateway (e.g., an ALB, nginx, or Spring Cloud Gateway instance): TLS is terminated here, the request's path (/orders/42) and headers are inspected, and the request is routed to the correct backend service pool — possibly after authentication, rate limiting, or request transformation at this layer.
  4. Service mesh sidecar: inside the cluster, the request reaches a specific service instance's sidecar proxy (e.g., Envoy in an Istio mesh), which applies the fine-grained, fast-changing load-balancing algorithm (Section 4.4) across the currently healthy pods for that service, informed by continuous health and latency signals gathered at second-by-second granularity.
  5. The service instance itself finally receives and processes the request, possibly making further internal calls to other services — each of which repeats step 4's sidecar-mediated load-balancing decision independently.

Notice the pattern across this entire path: routing decisions get progressively more fine-grained and more frequently re-evaluated as the request moves closer to the actual service instance. DNS decides something that might not change for minutes or hours; the L7 gateway decides something that can change between consecutive requests; the service mesh sidecar re-evaluates essentially continuously. This layered, decreasing-granularity structure is not an accident of how the industry's tooling happened to evolve — it reflects a genuine engineering trade-off: the closer a layer sits to the actual workload, the cheaper and faster it is to gather accurate health/load signals, and the more that layer should be trusted with fine-grained decisions; the farther a layer sits (DNS being the farthest), the more expensive accurate, fast signal propagation becomes, so that layer is best used for coarse, slow-changing decisions instead.

6. MATHEMATICS

Load balancing is lighter on formalism than, say, consensus algorithms, but a few quantitative relationships come up constantly in both interviews and real capacity planning.

6.1 Little's Law and Why "Least Connections" Works

Little's Law, a basic result from queueing theory, states: 

L = λ × W

L = average number of requests "in flight" (active connections) at an instance
λ = average arrival rate of requests to that instance
W = average time each request takes to be processed

This gives a precise justification for the least-connections algorithm from Section 4.4: for a given arrival rate λ, the number of active connections L an instance accumulates is directly proportional to how long each request takes to process (W). An instance currently handling slow requests will have a higher connection count even if it is receiving requests at the same rate as every other instance — which is exactly the signal least-connections uses to avoid piling more work onto an already-overloaded instance, and exactly why round robin, which ignores W entirely, can leave load unevenly distributed when request duration varies.

6.2 Weighted Distribution

For weighted round robin or weighted least connections across N instances with weights w1, w2, ..., wN, the expected fraction of traffic instance i should receive is: 

fraction_i = w_i / (w1 + w2 + ... + wN)

This is the formula behind capacity-proportional traffic shifting during a canary deployment: if a new version is given weight 1 and the stable version weight 99 out of a total of 100, roughly 1% of traffic reaches the canary — and ramping the canary's weight up over time is exactly how a gradual, low-risk rollout is implemented at the load-balancing layer.

6.3 Health Check Failure Probability and False Positives

If a single health check probe has some independent probability p of a spurious failure (a transient network blip unrelated to the instance's real health), and an unhealthy threshold of k consecutive failures is required before removing an instance from rotation, the probability of a false ejection purely from transient noise is approximately p^k — which shrinks extremely fast as k increases. This is the quantitative reason production systems almost never eject an instance on a single failed probe: going from k=1 to k=3 can turn, say, a 2% chance of spurious failure per check into roughly a 0.0008% chance of three consecutive spurious failures, at the cost of slightly slower reaction time to a genuinely dead instance — the same false-positive-vs-reaction-time trade-off engineers tune explicitly when configuring health check thresholds.

The Actuator health-check integration deserves a closer look because it is where "application code" and "infrastructure load balancing" meet directly. A naive health endpoint that simply returns HTTP 200 unconditionally tells an external load balancer nothing useful — it will happily keep routing traffic to an instance that is technically running but cannot reach its database. A properly configured Actuator setup distinguishes liveness (is the process itself still running and not deadlocked — used by an orchestrator like Kubernetes to decide whether to restart the container) from readiness (is this instance currently able to correctly serve traffic — used by a load balancer to decide whether to include it in rotation at all), which maps precisely onto the healthy/unhealthy state machine from Section 7.3: a load balancer's active health check should poll the readiness endpoint, not liveness, because an instance can be very much "alive" while still being the wrong target for new traffic (e.g., it lost its database connection, or it is still warming up a cache after startup).

10. BEST PRACTICES

  • Keep DNS TTLs short for anything involved in failover, long for anything that is not. A short TTL (seconds to low minutes) on a failover-relevant record trades a small amount of constant DNS query volume for dramatically faster recovery when you need to redirect traffic away from a failed region — treating TTL as a dial you never think about is exactly how a five-minute outage turns into a thirty-minute one.
  • Match the health check to what "healthy" actually means for this service. A bare TCP connect check only proves a process is listening on a port, not that it can serve a correct response; prefer an application-level check (Section 9's readiness endpoint pattern) that actually exercises the dependency most likely to fail silently.
  • Default to statelessness and treat sticky sessions as an optimization, not a crutch. Per Section 5.1, pushing session state into a shared store lets any instance serve any request, which is what makes every load-balancing algorithm in Section 4.4 — and every failure-recovery story in this chapter — actually work as advertised.
  • Choose the load-balancing algorithm based on your actual traffic shape, not habit. Round robin by default; least connections or latency-aware specifically when request cost or instance performance is uneven (Section 4.4 and the Little's Law justification in Section 6.1) — defaulting to the most sophisticated option everywhere adds operational complexity without a corresponding benefit when traffic is already uniform.
  • Tune health check thresholds deliberately, not with framework defaults left unexamined. The false-positive-vs-reaction-time trade-off in Section 6.3 is a real dial with real consequences in both directions — flapping instances in and out of rotation is its own outage class, distinct from the slow-failover problem too-long a threshold causes.

11. COMMON MISTAKES

  • Assuming DNS failover is instantaneous. Clients and intermediate resolvers that already cached an old answer will keep using it until that cached TTL expires, regardless of how quickly the authoritative record is updated — a very common gap between "we fixed the DNS record" and "users stopped seeing errors."
  • Conflating L4 and L7 capabilities. Expecting an L4 load balancer to route based on URL path, or assuming it is inspecting cookies/headers, leads to designs that simply cannot work at that layer — if path- or header-based routing is required, the load balancer has to operate at L7, full stop.
  • Treating a health check that always returns 200 as a real health check. This defeats the entire purpose described in Section 9 — an instance that cannot reach its database or downstream dependency keeps receiving traffic it cannot correctly serve, because the shallow check never reflects that reality.
  • Relying on sticky sessions to paper over a stateful application design. This reintroduces single points of failure per user and undermines even load distribution (Section 5.1) — it is treating a symptom (session breaks on failover) rather than the underlying cause (session state was never externalized).
  • Forgetting that a service mesh sidecar's load-balancing decisions and the external L7 gateway's decisions are separate, independently-configured layers. Tuning retry/timeout/algorithm settings at only one of these layers while assuming it governs the whole request path (Section 8's stacked diagram) is a frequent source of "why is this still timing out, I already fixed the gateway config" confusion.

12. PERFORMANCE CONSIDERATIONS

Every performance property of the load-balancing/DNS layer traces back to the same trade-off introduced in Section 4.3: the more a layer inspects about a request, the more capability it gains and the more work (and latency) it costs to do so.

  • L4 vs L7 overhead. L4 load balancing adds minimal latency because it never parses the application payload or terminates TLS; L7 load balancing adds measurably more overhead per request because it must terminate TLS, parse the HTTP request, and often re-encrypt before forwarding — a cost that is almost always worth paying for the routing flexibility it buys, but one that should be accounted for explicitly in latency budgets at very high request volumes.
  • Connection reuse matters more than algorithm choice at high throughput. Establishing a new TCP (and especially TLS) connection per request is expensive; keep-alive connection pooling between the load balancer and backend instances, and between clients and the load balancer, typically has a larger impact on overall throughput than which specific algorithm from Section 4.4 is selected.
  • Health check frequency is itself a load source. Very frequent active health checks across a large fleet add real, continuous request volume to every instance purely for health-checking purposes — interval and timeout values (Section 4.5) need to balance fast failure detection against the aggregate load the checks themselves generate.
  • DNS caching reduces load balancer-facing traffic, but unevenly. Because DNS answers are cached per-TTL by resolvers serving potentially large populations of clients, actual traffic distribution across regions returned by round-robin or GeoDNS can be lumpier than the "even split" the configuration implies, especially with a small number of large ISP resolvers caching the same answer for many users at once.

13. SECURITY CONSIDERATIONS

The load-balancing and DNS layer sits directly on the path of every request a system receives, which makes it both a natural enforcement point for security controls and, if misconfigured, a natural attack surface.

  • DNS as an attack surface. DNS spoofing and cache poisoning attacks attempt to trick a resolver into caching a fraudulent answer, redirecting traffic to an attacker-controlled destination; DNSSEC (DNS Security Extensions) mitigates this by cryptographically signing DNS records so resolvers can verify authenticity, and is worth calling out explicitly as the standard mitigation when DNS integrity comes up in an interview.
  • TLS termination point as a trust boundary. Wherever TLS is terminated (Section 4.3's L7 note) is the point where traffic becomes plaintext to whatever sits behind it — this makes the choice of termination point a genuine security decision, not just a performance one: terminating at the edge and re-encrypting for internal hops (common with a service mesh's mTLS between sidecars) keeps traffic encrypted end-to-end across the internal network, while terminating once and trusting the internal network implicitly is a weaker posture that many zero-trust architectures now explicitly reject.
  • Load balancers as a natural place to absorb volumetric attacks. Because the load-balancing/edge layer sits in front of everything else, it is also the natural place to implement DDoS mitigation and connection-rate limiting before malicious traffic ever reaches application instances — most managed cloud load balancers and CDNs bundle this protection by default, which is one more reason routing all external traffic through that layer rather than exposing backend instances directly is a near-universal best practice.
  • Health check endpoints themselves should not leak information. A readiness endpoint (Section 9) that returns detailed internal dependency status (database hostnames, internal error stack traces) to an unauthenticated caller is a genuine information-disclosure risk if that endpoint is reachable from outside the trusted network — it should be reachable by the load balancer/orchestrator performing the check, not exposed publicly with full detail.

14. INTERVIEW QUESTIONS

JUNIORQ1. A junior dev asks why you can't just run five instances of a service and have each client pick one at random itself, instead of putting a load balancer in front of them. What is the load balancer actually providing that ad hoc client-side selection wouldn't?

ROI: ★★★★★ · Frequency: Extremely High

A client picking randomly has no way to know which instances currently exist (instances get added and removed by deploys and autoscaling constantly) and no way to know which ones are currently healthy — it would keep sending some fraction of requests to dead or overloaded instances with no mechanism to stop. A load balancer solves both problems centrally: it maintains a live view of which instances exist and are healthy (via service discovery and health checks), and applies a real distribution algorithm so load is spread deliberately rather than by chance. Client-side random selection also pushes a non-trivial amount of logic and failure-handling into every single calling client, instead of solving the problem once, centrally, for every caller.

JUNIORQ2. You lower a DNS TTL right before a planned migration. Why, and what's the downside of leaving TTLs very low permanently?

ROI: ★★★★★ · Frequency: Extremely High

You lower the TTL so that once the migration happens and the DNS record is updated to point at the new destination, resolvers and clients around the internet that cached the old answer expire that cache quickly and pick up the new one — a long TTL means a dead or outdated IP keeps being handed out for as long as that TTL duration, regardless of how fast you fixed the record. The downside of running very low TTLs permanently is the trade-off going the other direction: every resolver has to re-query the authoritative server far more often, which increases load on your DNS infrastructure and adds a small amount of latency to every cache-miss lookup, for a benefit (fast failover) that most records never actually need day to day — which is why the discipline is to keep TTLs short specifically on failover-relevant records and longer everywhere else, not to minimize every TTL in the zone by default.

JUNIORQ3. Ops wants to cut load balancer latency by swapping an ALB (L7) for a Network Load Balancer (L4) in front of an API that currently routes by URL path. What breaks, and why can't an L4 balancer just do the same routing more cheaply?

ROI: ★★★★★ · Frequency: Extremely High

Path-based routing breaks entirely, because an L4 load balancer only sees transport-layer information — source/destination IP and port, protocol — and has no visibility into the HTTP request itself; it structurally cannot know a URL path exists, let alone route on it. An L7 load balancer can route on path, host, headers, or cookies specifically because it terminates the connection and parses the actual application request, which is also exactly why it costs more overhead per request. The latency win from switching to L4 is real, but it's not a free optimization here — it requires either moving the path-based routing decision somewhere else in the stack (inside the application, or a different L7 layer), or redesigning the API so routing no longer needs to inspect the request at all.

JUNIORQ4. Your service has wildly uneven request costs — some endpoints finish in 5ms, others take 2 seconds — and it's currently on plain round robin. What's actually going wrong, and which algorithm(s) would you reach for instead?

ROI: ★★★★★ · Frequency: High

Round robin's fairness is about request count, not processing time — it hands out an equal number of requests to every instance regardless of how expensive each one turns out to be, so an instance unlucky enough to get several of the slow requests ends up doing far more real work than one that got the fast ones, even though both received "equal" treatment by the algorithm's own definition. Least connections fixes this directly by routing to whichever instance currently has the fewest active connections, which correlates with how much work is actually in flight rather than how many requests were historically assigned. If instance capacity also varies (not just request cost), weighted least connections combines both signals; a latency-aware algorithm goes further by reacting to measured response time directly rather than connection count as a proxy for it.

JUNIORQ5. A teammate suggests skipping health checks entirely since "our instances basically never crash." What silently breaks without them, and what's the actual mechanism that would catch the failures that do happen?

ROI: ★★★★★ · Frequency: Extremely High

"Basically never crash" isn't the same as "never stops serving correct responses" — an instance can hang, lose its database connection, exhaust a thread pool, or sit mid-deploy while still technically being a running process, and without health checks the load balancer has no way to distinguish that from a perfectly healthy instance; it keeps sending real users to it, producing exactly the user-visible errors a health check exists to prevent. The mechanism is either active checks (the load balancer independently probes a dedicated endpoint on a schedule) or passive checks (inferring health from real traffic outcomes like error rates and timeouts) — most production systems run both, because an instance that merely hasn't crashed is not the bar that actually matters.

JUNIORQ6. A teammate proposes enabling sticky sessions to fix a bug where users randomly get logged out. What are you actually signing up for by doing that, beyond "it fixes the symptom"?

ROI: ★★★★☆ · Frequency: High

Sticky sessions pin a client to one specific backend instance (usually via a cookie) so its requests keep landing where its session data already lives, and yes, that stops the random-logout symptom. What you're also signing up for: that instance's load can no longer be freely rebalanced without breaking sessions pinned to it, and if that specific instance dies — a crash, a deploy, a scale-down — every client stuck to it loses its session state along with it, which is the exact failure the random logouts were already a symptom of, just with a smaller blast radius. It's a reasonable short-term mitigation, but it treats the symptom (session breaks on reroute) rather than the cause (session state was never externalized), and the bug tends to resurface the next time an instance goes away.

JUNIORQ7. A PM asks why users in Singapore sometimes get routed to your US data center even though a Singapore region has been live for weeks. Where do you look first, and what's actually controlling that routing decision?

ROI: ★★★★☆ · Frequency: Medium-High

Look first at the GeoDNS configuration and at cached DNS answers — GeoDNS is what's supposed to return a different IP for the same hostname depending on the resolver's geographic origin, pointing clients toward the nearest regional deployment, so if Singapore users are reaching the US, either the Singapore region was never added to the GeoDNS policy, or a resolver serving those users cached the US answer before the Singapore region went live and hasn't re-queried yet (the TTL hasn't expired). The routing decision itself happens entirely at the DNS layer, before a single packet reaches your infrastructure — no amount of fixing the load balancer or the application in the Singapore region changes anything if GeoDNS itself is still handing out the wrong IP, or a cached answer is still in circulation.

JUNIORQ8. Your team is debating whether round-robin DNS is "good enough" load balancing for a two-region setup, to avoid standing up a separate load balancer fleet. What's the specific failure mode that makes this a bad bet?

ROI: ★★★★☆ · Frequency: Medium-High

Plain round-robin DNS has zero health awareness — if one region's backend dies, its IP keeps being handed out in rotation to new resolvers until someone manually edits the record, and any resolver that already cached that dead IP keeps using it until the TTL expires regardless. It also has no insight into real-time load or connection counts, so it can't shift traffic away from a region that's struggling but not fully down. The specific bet you'd be making is that nothing ever needs fast, health-aware failover — which is exactly the bet an active load balancer exists so you don't have to make.

JUNIORQ9. Your pods show as "Running" in Kubernetes, but the load balancer keeps sending them traffic even though they can't reach the database. What health-check distinction is misconfigured here?

ROI: ★★★★☆ · Frequency: High

This is a liveness/readiness mix-up — "Running" reflects liveness, which only answers "is this process still up and not deadlocked," and an orchestrator uses it to decide whether to restart a container; it says nothing about whether the instance can actually serve a correct response. Readiness is the separate signal that specifically answers "can this instance correctly serve traffic right now," and it's what the load balancer's health check should be polling instead — a readiness endpoint that actually exercises the database connection would correctly flag the instance as not-ready the moment that connection drops, pulling it out of rotation instead of letting it keep failing real requests.

JUNIORQ10. You're deciding whether to put routing, auth, and rate-limiting logic in nginx or in a Spring Cloud Gateway service. What does choosing the latter actually buy you operationally, beyond "it's written in Java"?

ROI: ★★★☆☆ · Frequency: Medium

Spring Cloud Gateway is a reactive L7 reverse proxy that routes by predicates like path or host and applies filters for authentication, rate limiting, and request rewriting — functionally the same role nginx plays. What it actually buys you is that routing and filter logic is written and versioned as ordinary Spring code and configuration, reviewable and testable the same way as the rest of your application, rather than a separate vendor-specific config language and deployment pipeline that a different team or tool typically owns — the trade-off being one more JVM-based service to run and scale instead of a lighter-weight dedicated proxy.

MIDQ11. Why is "least connections" often a better algorithm than round robin for real-world traffic?

ROI: ★★★★★ · Frequency: High

Round robin assumes every request costs roughly the same amount of processing time, so sending each instance an equal count of requests produces an equal load. When request duration varies significantly, that assumption breaks — an instance handling several slow requests can be overloaded even while receiving the same request count as an idle instance. Least connections avoids this by routing to whichever instance currently has the fewest active connections, which — per Little's Law — correlates directly with how much processing time is currently tied up on that instance.

MIDQ12. Explain the layered load-balancing stack in a typical production deployment — what decision does each layer make?

ROI: ★★★★★ · Frequency: High

DNS/GeoDNS makes a coarse, slow-changing decision about which region or data center a client's traffic is even directed toward. A CDN edge layer decides whether a request can be answered from cache without reaching the origin. An external L7 load balancer/gateway terminates TLS and routes to the correct service pool by path/host, applying authn and rate limiting. An internal load balancer or service mesh sidecar makes the fine-grained, continuously-updated decision of which specific healthy instance of a service handles this request. Decisions get more granular and more frequently re-evaluated at each successive layer.

MIDQ13. Why is DNS a poor mechanism for fast failover, even with health checks attached to it?

ROI: ★★★★★ · Frequency: High

DNS answers are cached by resolvers and clients for the duration of the record's TTL. Even if the authoritative server updates its answer the instant it detects a failure, any resolver or client that already cached the old answer will keep using it until that cached TTL expires — which can be minutes, depending on configuration. Health checks attached to DNS can stop new lookups from receiving a bad answer, but they cannot retroactively invalidate answers already cached elsewhere on the internet.

MIDQ14. Why are sticky sessions in tension with horizontal scalability?

ROI: ★★★★★ · Frequency: High

Sticky sessions pin a client to one specific instance, which means that instance's load can't be freely redistributed without breaking that client's session, undermining even load distribution as the sticky population grows unevenly across instances. Worse, if the sticky instance fails, the client's session-dependent state is lost along with it — no other healthy instance can pick up where it left off — which directly contradicts the resilience and elasticity goals horizontal scaling exists to provide. The standard fix is to externalize session state into a shared store so any instance can serve any request.

MIDQ15. When would you choose an L4 load balancer over an L7 load balancer, given that L7 can do everything L4 can plus more?

ROI: ★★★★☆ · Frequency: Medium-High

When raw throughput and minimal latency overhead matter more than content-aware routing, and the routing decision genuinely does not require inspecting the application payload — for example, balancing raw TCP/UDP traffic for a non-HTTP protocol, or a scenario where TLS passthrough (rather than termination) is required for end-to-end encryption guarantees. L4's lower overhead, from never parsing or terminating the application protocol, is a real and sometimes decisive advantage at very high connection volumes even though it sacrifices L7's routing flexibility.

MIDQ16. What is the "power of two choices" idea in latency-aware load balancing, and why is it preferred over checking every instance's latency on every request?

ROI: ★★★★☆ · Frequency: Medium-High

Instead of measuring and ranking every instance's current latency/load on every single request (which itself adds overhead and coordination cost that scales with pool size), the load balancer randomly samples a small number of instances — commonly two — and picks the better of just that small sample. This captures most of the benefit of true latency-aware routing at a fraction of the measurement cost, and empirically performs close to an exhaustive comparison while scaling far better to large instance pools.

MIDQ17. How does Spring Cloud LoadBalancer differ from a traditional external load balancer like an ALB or nginx?

ROI: ★★★★☆ · Frequency: Medium-High

Spring Cloud LoadBalancer is a client-side library: it runs inside the calling service's own process, resolves a logical service name to a current list of healthy instances via service discovery, and picks one per call using a pluggable strategy — no separate proxy process sits in the request path. An external load balancer like an ALB or nginx is a separate, centralized component that every client's traffic physically passes through. Client-side load balancing avoids that centralized hop's latency and potential bottleneck, at the cost of needing load-balancing logic embedded in every calling service.

MIDQ18. Why should a load balancer's active health check call a dedicated readiness endpoint rather than just checking if the TCP port is open?

ROI: ★★★★★ · Frequency: High

A TCP connect check only proves a process is listening on a port — it says nothing about whether that process can actually produce a correct response. A service can accept TCP connections while its database connection pool is exhausted, a critical downstream dependency is unreachable, or it hasn't finished warming up. A proper readiness endpoint actively verifies the dependencies that matter for correct operation and reports accordingly, giving the load balancer a signal that actually correlates with "this instance can serve a correct response right now."

MIDQ19. Explain why health check thresholds (consecutive failures/successes) exist instead of ejecting an instance after a single failed probe.

ROI: ★★★★☆ · Frequency: High

A single failed probe could easily be a transient network blip unrelated to the instance's actual health, not a genuine failure. Ejecting on one failure risks "flapping" — repeatedly removing and re-adding a perfectly healthy instance based on noise, which is itself a source of instability and uneven load distribution. Requiring several consecutive failures before ejecting (and several consecutive successes before re-admitting) trades a small amount of reaction-time delay for a large reduction in false-positive ejections, since the probability of several consecutive spurious failures shrinks multiplicatively.

MIDQ20. What's the difference between active and passive health checks?

ROI: ★★★★☆ · Frequency: Medium-High

Active health checks have the load balancer independently probe each instance on a fixed schedule, regardless of whether real traffic is currently flowing to it. Passive health checks instead infer health from the outcomes of real production traffic — an instance that starts returning errors or timing out on actual requests gets flagged unhealthy without any separate probe traffic being generated. Many production systems use both together, since active checks can catch problems before real traffic is affected, while passive checks catch issues an active probe's specific request pattern might not exercise.

MIDQ21. Why would you use consistent hashing as a load-balancing algorithm instead of round robin?

ROI: ★★★★☆ · Frequency: Medium-High

When you need the same client, session key, or cache key to consistently land on the same backend instance — for cache locality, or to maintain session affinity without a separate sticky-session cookie mechanism — consistent hashing deterministically maps a key to an instance while minimizing how much traffic gets redistributed when instances are added or removed. Round robin provides no such consistency; the same client's consecutive requests could land anywhere. The mechanics of the hashing scheme itself belong to Chapter 06's treatment of consistent hashing — here it's simply one algorithm choice among several.

MIDQ22. What does TLS termination at a load balancer actually mean, and why does it matter for L7 routing?

ROI: ★★★★☆ · Frequency: Medium-High

TLS termination means the load balancer decrypts incoming encrypted traffic itself, rather than passing it through still encrypted to the backend. This is a prerequisite for L7 routing decisions, because the load balancer cannot inspect a request's path, headers, or cookies while that data is still encrypted — it needs the plaintext request to make content-based routing decisions at all. After inspecting (and routing) the request, the load balancer may forward it to the backend either in plaintext over a trusted internal network, or re-encrypted (e.g., via mTLS in a service mesh).

MIDQ23. What happens to in-flight requests when an instance is marked unhealthy and removed from the load-balancing pool?

ROI: ★★★★☆ · Frequency: Medium-High

Being marked unhealthy stops the load balancer from routing new requests to that instance, but it does not automatically do anything about requests already in flight to it — those typically run to completion, time out, or fail depending on what actually made the instance unhealthy. This is why graceful shutdown/deregistration procedures matter separately: a well-behaved deployment process deregisters an instance from the load balancer's pool and waits for in-flight requests to drain before actually terminating the instance, rather than relying solely on reactive health-check detection after the fact.

MIDQ24. Why do production systems often run a CDN, an external L7 load balancer, AND a service mesh, rather than picking just one?

ROI: ★★★★☆ · Frequency: Medium-High

Each solves a different-granularity version of the routing problem at a different point in the request path: the CDN offloads cacheable traffic before it ever reaches the origin (reducing load and latency for a large fraction of requests); the external L7 load balancer handles edge-facing routing, TLS termination, and coarse service-pool selection for traffic that does reach the origin; and the service mesh handles the much more dynamic, internal east-west traffic between dozens or hundreds of microservices, where instance pools change constantly as pods scale up/down. No single layer is well-suited to all three jobs simultaneously.

MIDQ25. How would you design a health check for a service that depends on a database, without making every request slow?

ROI: ★★★★☆ · Frequency: Medium-High

Run the dependency check (e.g., a lightweight connection validation query) on the load balancer's own health-check schedule, separate from and independent of actual user-facing request processing — a cached or periodically-refreshed health status that the health endpoint simply returns, rather than re-verifying the database connection synchronously on every single health probe (which would itself add load) or, worse, on every single user request. The health endpoint should be cheap and fast specifically because it may be polled frequently.

SENIORQ26. Your service uses sticky sessions, and users intermittently get logged out or lose their shopping cart during deploys. Diagnose the likely cause and propose a fix.

ROI: ★★★★★ · Frequency: High at senior level

During a rolling deploy, instances are taken down and replaced one at a time; any client stuck, via sticky session, to an instance being terminated loses access to whatever state lived only in that instance's memory — exactly the failure mode Section 5.1 describes. The underlying cause is that session state was never externalized, so sticky sessions are being relied on for correctness rather than as a pure performance optimization. The fix is to move session state (cart contents, auth session) into a shared external store (Redis, a database, or a signed client-side token like a JWT) so any instance can correctly serve any request regardless of which one a client previously hit — at which point sticky sessions become optional and deploys stop causing data loss.

SENIORQ27. A region-wide outage requires failing traffic over to a secondary region. Walk through what has to happen at the DNS layer, and what could go wrong.

ROI: ★★★★★ · Frequency: High at senior level

The authoritative DNS record for the affected hostname needs to be updated to point at the secondary region's IP (or, if using a managed DNS failover policy, the provider's own health check needs to detect the primary region's failure and automatically switch the answer). What can go wrong: if the record's TTL was set long (hours), clients and intermediate resolvers that already cached the primary region's answer will keep sending traffic there for up to that TTL duration, regardless of how fast the DNS record itself was updated — meaning a huge fraction of users experience the outage far longer than the "time to update DNS" would suggest. This is exactly why failover-critical DNS records should be configured with short TTLs well before an incident occurs, since you cannot retroactively shrink a TTL that was already cached by resolvers around the internet at the moment you actually need fast failover.

Interview Gold Point: Explicitly mention that DNS-based failover alone is rarely sufficient for a hard SLA — pair it with health-check-aware DNS (so the failover is automatic, not manually triggered) and design the application layer to tolerate the failover window gracefully (e.g., idempotent retries, graceful degradation) rather than assuming DNS failover will be instantaneous for every client.
SENIORQ28. You're seeing uneven load across instances despite using round robin. What are the possible causes, and how would you diagnose which one applies?

ROI: ★★★★★ · Frequency: High at senior level

First, check whether request cost is actually uniform — round robin's fairness guarantee is about request count, not processing time, so if some requests are far more expensive than others (per Little's Law in Section 6.1), equal counts can still produce unequal load; the fix there is switching to least connections or a latency-aware algorithm. Second, check for connection reuse/keep-alive effects — if clients maintain long-lived connections and the load balancer only balances at connection-establishment time rather than per-request, a small number of long-lived, high-volume connections can concentrate disproportionate load on whichever instances happened to receive them. Third, check whether sticky sessions are active and causing an uneven population of "stuck" clients to accumulate on specific instances. Diagnosing which applies means instrumenting per-instance request count, per-request latency distribution, and connection lifetime, rather than guessing.

SENIORQ29. Design the health-check strategy for a service mesh sidecar versus an external, edge-facing load balancer — should they use the same thresholds and intervals?

ROI: ★★★★☆ · Frequency: Medium-High at senior level

No — they are solving the problem at different granularities, per Section 5.2, and should be tuned accordingly. A service mesh sidecar sits extremely close to its target instance, can afford frequent, low-latency health checks, and should react quickly since the blast radius of a bad decision is limited to internal traffic between a small set of services. An external, edge-facing load balancer is making a coarser, less frequently re-evaluated decision, often across a larger pool, and overly aggressive thresholds there risk flapping a backend service pool in and out of rotation based on signals that are less reliable at that distance and frequency. The general principle, consistent with Section 5.2's "closer layers get finer, faster decisions" pattern, is tighter thresholds and shorter intervals the closer the health check sits to the actual workload.

SENIORQ30. A new L7 gateway is added in front of an existing fleet that already does client-side load balancing via Spring Cloud LoadBalancer. What double-balancing concerns should you watch for?

ROI: ★★★★☆ · Frequency: Medium-High at senior level

The two layers are making independent decisions that can interact in non-obvious ways: the gateway picks a service pool/instance based on its own health view, and then, if that instance makes further internal calls, Spring Cloud LoadBalancer makes its own independent instance selection based on a potentially different (client-side) view of instance health, which might be staler or fresher than the gateway's. Watch for retry amplification — if both layers independently retry on failure without coordination, a single failing downstream instance can multiply into far more retry traffic than intended. Also watch for inconsistent health views causing the gateway to route to a service pool it believes is healthy while that pool's internal client-side balancer is still routing some fraction of calls to an instance the gateway's own health check would have already excluded, if it had visibility into it.

SENIORQ31. How would you decide whether a given routing requirement belongs at the DNS layer, the external L7 gateway layer, or the service mesh layer?

ROI: ★★★★★ · Frequency: High at senior level

Map the requirement to the granularity and timescale it actually needs, per Section 5.2's pattern. If the decision is "which geographic region/data center" and changes rarely (minutes to hours), it belongs at DNS. If the decision requires reading the application request itself — path, host, headers, cookies — and needs to apply uniformly to all external traffic entering the system (authn, global rate limiting, TLS termination), it belongs at the external L7 gateway. If the decision is about continuously re-evaluated, fine-grained routing between specific instances of an internal service, informed by fast-changing internal health/latency signals, and needs features like per-call retries, circuit breaking, or mTLS between services, it belongs at the service mesh sidecar layer. Pushing a mesh-layer decision up to DNS (far too coarse and slow) or a DNS-layer decision down to the mesh (unnecessary complexity, since the mesh has no natural concept of "client geography") are both common mismatches worth explicitly avoiding.

SENIORQ32. What's the risk of using "least connections" in a system where some requests hold a connection open for a very long time (e.g., long-polling or streaming)?

ROI: ★★★★☆ · Frequency: Medium-High at senior level

Least connections assumes connection count correlates with current load, but a long-lived streaming or long-polling connection counts as exactly one connection for the entire duration it's open, even though it may consume comparatively little active processing most of that time. This can cause the algorithm to systematically avoid routing new requests to instances that happen to be hosting several long-lived-but-idle connections, while overloading instances with many short-lived-but-actually-busy connections — the opposite of what least connections is meant to achieve. A latency-aware or custom weighted algorithm that accounts for actual resource consumption, rather than raw connection count, is usually a better fit when long-lived connections are common.

SENIORQ33. Walk through the trade-offs of terminating TLS at the external L7 gateway versus terminating it at each individual service instance.

ROI: ★★★★☆ · Frequency: Medium-High at senior level

Terminating at the gateway centralizes certificate management (one place to rotate/renew certs rather than every instance), simplifies L7 routing (the gateway needs the plaintext request to route by path/header anyway), and offloads the CPU cost of TLS handshakes from application instances. The trade-off is that traffic between the gateway and backend instances travels in plaintext unless explicitly re-encrypted, which is a weaker security posture on an internal network that isn't fully trusted, and it also means the gateway is a single point that, if compromised, sees all traffic unencrypted. Terminating per-instance (or re-encrypting via mTLS in a service mesh) preserves encryption further into the system at the cost of more certificate management surface and additional CPU overhead distributed across every instance.

STAFFQ34. You're asked to design the load-balancing and DNS strategy for a service that must meet a 30-second RTO (recovery time objective) during a full regional failure. What specific decisions does this constraint force, at every layer?

ROI: ★★★★★ · Frequency: High at staff level

A 30-second RTO rules out relying on default or long DNS TTLs entirely — the TTL on any record involved in regional failover must be set well under that budget (seconds, not minutes), accepting the added DNS query volume that comes with it, because a client or resolver that cached a longer TTL simply cannot meet the RTO no matter how fast the backend recovers. It also forces automated, health-check-driven DNS failover rather than a manual runbook step, since a human-in-the-loop update process realistically cannot execute reliably within 30 seconds under incident pressure. At the load-balancer layer, it requires that the secondary region already have warm, ready capacity (not cold-started on failure, since warming up instances and passing health checks itself could consume a meaningful fraction of the 30-second budget), and health check intervals/thresholds throughout the stack need to be tuned tightly enough to detect the primary region's failure well within a fraction of the 30 seconds, leaving the remaining budget for DNS propagation and in-flight request draining. The staff-level judgment is recognizing that a tight RTO is a system property requiring every layer in Section 8's stack to be pre-provisioned and tuned coherently toward that number — it cannot be achieved by fixing any single layer in isolation.

Interview Gold Point: Point out explicitly that RTO commitments made without accounting for DNS TTL and caching behavior are a common gap between what a design document promises and what actually happens during a real incident — a strong staff-level answer connects the abstract RTO number directly back to a concrete TTL value and a concrete automated failover trigger, rather than treating "failover" as a single undifferentiated step.
STAFFQ35. A team proposes moving all session state to sticky sessions instead of externalizing it to Redis, arguing it's simpler and avoids a network hop per request. How do you evaluate this trade-off?

ROI: ★★★★★ · Frequency: High at staff level

The proposal trades a real, bounded performance cost (an extra network hop to Redis per request needing session data) for an unbounded, harder-to-quantify reliability and operability cost: every deploy, scale-down event, or instance failure now risks user-visible session loss (Section 5.1), load can no longer be freely rebalanced across instances without breaking sticky clients, and the system becomes meaningfully harder to reason about during incidents ("which instance is this specific user's session on" becomes operationally relevant in a way it otherwise wouldn't be). The honest framing for the team: sticky sessions do not actually eliminate the need to handle session state carefully, they just relocate the failure mode from "occasional network latency" to "occasional data loss during routine infrastructure events," and the latter is a materially worse trade for most production systems. If the latency of an external store is the genuine concern, the better answer is usually optimizing that path (connection pooling, a colocated cache, request-scoped caching) rather than abandoning externalized state altogether — unless the specific workload can tolerate session loss on failover, which should be an explicit, documented decision rather than an implicit side effect of choosing sticky sessions for convenience.

STAFFQ36. How would you design load balancing for a system with extremely heterogeneous request costs — some requests take 5ms, others take 5 seconds — across a mixed fleet of instance sizes?

ROI: ★★★★★ · Frequency: Medium-High at staff level

Neither plain round robin nor plain least connections is sufficient alone here: round robin ignores both request cost and instance capacity entirely, and plain least connections ignores instance capacity differences, so a weighted least-connections algorithm (Section 4.4), with weights reflecting real measured capacity per instance type rather than just nominal specs, is the right starting point. Given the extreme request-cost variance, I'd also push toward separating request classes at the routing layer itself where feasible — routing known-expensive request types (e.g., by path, at the L7 gateway) to a dedicated pool sized and tuned for that cost profile, rather than mixing cheap and expensive requests into the same undifferentiated pool and hoping a single algorithm's load signal captures the difference well enough. On top of that, a latency-aware algorithm with real-time response-time sampling gives the system a feedback loop that adapts to request-cost variance the static weighting alone cannot anticipate. The staff-level insight is that extreme heterogeneity is often better solved partly by architecture (separating workload classes) than by leaning entirely on an increasingly sophisticated single load-balancing algorithm to compensate for mixing them.

STAFFQ37. Your organization runs a global, multi-region, multi-cloud deployment. Design the DNS and load-balancing strategy for both normal operation and disaster recovery, and justify the trade-offs.

ROI: ★★★★★ · Frequency: High at staff level

For normal operation: GeoDNS (or a managed latency-based routing policy) directs each client to its nearest healthy region across both clouds, with short-to-moderate TTLs balancing DNS query volume against responsiveness to regional health changes. Each region runs its own full stack from Section 8 — external L7 gateway, internal load balancing, service mesh — so regions are independently operable and a failure in one does not cascade into another. For disaster recovery: the DNS layer needs automated health-check-driven failover (not manual), the surviving region(s) need pre-provisioned, warm capacity sized to absorb failed-over traffic (cold-starting capacity during an active incident both costs time against the RTO and risks a second failure from an under-provisioned scramble), and the design needs to account explicitly for multi-cloud specifics — cross-cloud network latency if any internal east-west traffic must cross cloud boundaries during a partial failure, and the fact that managed load-balancer/health-check behavior and configuration surface genuinely differ between cloud providers, so failover logic cannot assume identical semantics on both sides. The key trade-off to name explicitly: more regions and warm standby capacity directly reduce RTO and blast radius but increase steady-state cost and operational surface area (more independent stacks to monitor and keep consistent) — the right amount of redundancy is a business decision informed by the actual cost of downtime, not a default to maximize.

STAFFQ38. How would you detect and respond to a "gray failure" — an instance that is technically passing health checks but serving degraded results to a subset of requests?

ROI: ★★★★★ · Frequency: High at staff level

Gray failures are specifically dangerous because they exist in the blind spot of a binary healthy/unhealthy health check model (Section 4.5/7.3) — the check passes, so the instance stays in rotation, while real users experience intermittent degradation the health check's specific probe pattern doesn't happen to exercise. Detecting this requires moving beyond binary active health checks toward continuous passive signal monitoring on real traffic: per-instance error rate, latency percentiles (not just averages, which can hide a degraded tail), and ideally a canary-style synthetic transaction that exercises the same code path real degraded requests are hitting, rather than a shallow liveness ping. The response needs automated, graduated action rather than only a binary in/out-of-rotation decision — for example, automatically reducing an instance's traffic weight (not removing it entirely) when its passive error/latency signals degrade past a threshold, which limits blast radius while avoiding a hard cutover that might be premature if the signal turns out to be noise. The staff-level point: a health-check system designed only around "is this instance up or down" is structurally incapable of catching gray failures — catching them requires deliberately investing in richer, continuous, traffic-derived signal, not just tightening existing binary thresholds.

Interview Gold Point: Mention circuit breakers (often implemented at the service mesh sidecar layer) as a complementary mechanism — they let individual callers independently detect and back off from a gray-failing dependency based on their own observed error rates, providing a second, decentralized layer of defense that doesn't depend on the central load balancer's health check catching the problem first.
MIDQ39. What is the purpose of the healthy threshold (as opposed to the unhealthy threshold) in a health check configuration?

ROI: ★★★★☆ · Frequency: Medium-High

The healthy threshold requires a certain number of consecutive successful probes before an instance that was previously marked unhealthy is re-admitted to the load-balancing pool. This guards against prematurely re-adding an instance that has only just barely recovered, or is recovering intermittently (e.g., still finishing a restart or cache warm-up) — admitting it back too eagerly on a single success risks immediately routing real traffic to an instance that fails again moments later, causing the same flapping behavior the unhealthy threshold is designed to prevent in the opposite direction.

MIDQ40. Why do some load balancers support "connection draining" (or "deregistration delay") when removing an instance from rotation?

ROI: ★★★★☆ · Frequency: Medium-High

Connection draining allows requests already in flight to an instance being removed from rotation to complete normally, while simply not sending it any new requests, instead of abruptly severing active connections the moment the instance is deregistered. This matters most during planned events like deploys or scale-down, where abruptly cutting off in-flight requests would cause avoidable user-visible errors that graceful draining, combined with a reasonable timeout, prevents.

JUNIORQ41. Your managed cloud load balancer's IP address can change without notice. Why would pointing your custom domain at it with a CNAME, instead of an A record, save you from a recurring DNS headache?

ROI: ★★★☆☆ · Frequency: Medium

An A record maps your hostname directly to a specific IP address, so if the load balancer's underlying IP changes, your A record is now stale and someone has to notice and update it. A CNAME instead maps your hostname to the load balancer's own stable hostname (which the cloud provider maintains and keeps pointed at whatever IP is currently correct), so the indirection absorbs the IP change for you — your zone file never needs to know or care that the IP underneath changed at all. This is exactly why cloud providers hand out a hostname, not a bare IP, for their managed load balancers: it's designed to be CNAME'd, not pinned to with an A record.

MIDQ42. Why might a team deliberately choose NOT to use the most sophisticated load-balancing algorithm available to them?

ROI: ★★★★☆ · Frequency: Medium-High

More sophisticated algorithms (latency-aware sampling, weighted least connections with dynamically adjusted weights) require additional measurement, bookkeeping, and tuning, which adds operational complexity and additional failure modes of their own — a misconfigured or buggy sophisticated algorithm can perform worse than simple round robin. When traffic is already uniform in cost and instances are homogeneous in capacity, round robin achieves the same practical outcome with far less complexity and far less that can go wrong, which is a legitimate engineering reason to prefer it, not just a default born of inertia.

SENIORQ43. How does autoscaling interact with load balancing, and what failure mode can occur if the two are not coordinated well?

ROI: ★★★★☆ · Frequency: Medium-High at senior level

Autoscaling adds or removes instances based on load signals (CPU, request queue depth, custom metrics), and the load balancer needs to discover and health-check newly added instances before routing traffic to them, and stop routing to instances being scaled down before they terminate. A common failure mode is a new instance receiving a full share of traffic immediately upon registration, before it has finished warming up (JIT compilation, connection pool initialization, cache population) — producing a burst of slow responses or errors right when the system most needed the new capacity to help. The fix is typically a warm-up period (gradual traffic ramp-up for newly registered instances, sometimes called "slow start") combined with readiness checks that genuinely reflect warm-up completion, not just process liveness.

MIDQ44. What's the difference between a forward proxy and a (reverse) load balancer, conceptually?

ROI: ★★★☆☆ · Frequency: Medium

A forward proxy sits in front of clients and makes requests on their behalf to external servers, typically to provide anonymity, caching, or policy enforcement for the client side. A reverse proxy/load balancer sits in front of servers and distributes incoming client requests among them, on behalf of the server side — clients are generally unaware a reverse proxy/load balancer exists at all, whereas a forward proxy is often explicitly configured by the client.

SENIORQ45. If a load balancer itself becomes a bottleneck or single point of failure, how do you scale and harden the load-balancing layer itself?

ROI: ★★★★★ · Frequency: Medium-High at senior level

Run multiple load balancer instances behind a layer that can distribute across them without reintroducing a single point of failure — commonly DNS round robin or an anycast IP across several load balancer instances/nodes at the outermost edge, or a cloud provider's managed load balancer service, which is itself internally redundant across multiple availability zones without the caller needing to manage that redundancy directly. The general principle is that "the load balancer" should never actually be a single process or machine in a serious production deployment — it should be a redundant, horizontally-scaled layer in its own right, which is exactly why managed cloud load-balancer products are popular: they handle this redundancy transparently rather than requiring every team to re-solve it themselves.

MIDQ46. Why is it important that a load balancer's algorithm and a backend service's statelessness be designed together, rather than independently?

ROI: ★★★★☆ · Frequency: Medium-High

A sophisticated load-balancing algorithm assumes it is free to route any request to any healthy instance based purely on load/latency signals; if the backend secretly depends on request affinity (undocumented in-memory state), the "optimal" routing decision from the algorithm's perspective can actually break application correctness. Conversely, a genuinely stateless backend gives the load balancer maximum freedom to optimize purely for load distribution without any correctness constraint limiting its choices. Designing them together means explicitly deciding, as part of the application's architecture, whether affinity is required at all — rather than discovering the dependency the hard way when a "better" algorithm change causes a correctness regression.

STAFFQ47. How would you migrate a large, stateful monolith with sticky-session dependencies to a stateless, horizontally load-balanced architecture with zero downtime?

ROI: ★★★★★ · Frequency: Medium-High at staff level

Start by cataloguing exactly what state currently lives in-instance and why — session data, in-memory caches, in-flight long-running operations — rather than assuming it's purely session cookies, since hidden in-memory dependencies are the most common source of a "stateless" migration that still breaks under load. Externalize session state first (to Redis or a signed token) while keeping sticky sessions enabled as a safety net, so the system behaves identically from the user's perspective during the transition but is no longer functionally dependent on affinity. Once externalized state is verified correct under real traffic (monitoring for any residual correctness issues that only show up when requests land on a different instance than usual), gradually disable sticky session affinity — ideally behind a feature flag or gradual rollout percentage, not a single cutover — so that any remaining hidden affinity dependency surfaces as a contained, observable issue affecting a small traffic percentage rather than a full outage. Only once affinity is confirmed unnecessary should load-balancing algorithm changes (enabling least-connections, more aggressive autoscaling, freer rebalancing) be introduced, since those changes are exactly the ones that will aggressively expose any remaining affinity assumption that externalizing session state alone didn't fully address.

MIDQ48. What role does a load balancer typically play in rate limiting, and why might rate limiting at this layer not be sufficient on its own?

ROI: ★★★★☆ · Frequency: Medium-High

An L7 load balancer or gateway is a natural place to enforce coarse, edge-level rate limits (per-IP, per-API-key, global request-rate caps) before traffic reaches backend services at all, protecting the whole fleet from being overwhelmed. It's often not sufficient alone because meaningful rate limiting frequently needs finer-grained context the edge layer may not have — per-user business logic (e.g., a specific expensive operation type needing a tighter limit than general API traffic), or limits that need to be enforced consistently across multiple edge load balancer instances, requiring a shared, centralized counter (e.g., in Redis) rather than per-instance local counting, which the full treatment of rate limiting and backpressure (Chapter 08) covers in depth.

JUNIORQ49. Your gateway config defines two named upstream blocks — one for /api/orders, one for /api/users — each listing a different set of instances. What is that grouping actually for, and why not just list every instance once, globally?

ROI: ★★★☆☆ · Frequency: Medium

A backend pool (or upstream) is the named group of instances that a specific routing rule is allowed to send matching traffic to — defining separate pools for orders and users lets each service scale, deploy, and fail independently, with the gateway only ever routing order traffic to order instances and user traffic to user instances. Listing every instance in one global pool would mean the gateway has no way to express "this request type only goes to that specific subset of instances," which breaks the moment two services behind the same gateway aren't interchangeable — which, in any system with more than one logical service, they never are.

SENIORQ50. How would you reason about whether to put rate limiting, authentication, and load balancing all in one gateway layer versus splitting them across separate components?

ROI: ★★★★☆ · Frequency: Medium-High at senior level

Combining them in one layer (e.g., a single Spring Cloud Gateway tier handling routing, auth, and rate limiting together) reduces operational surface area and request hops, and is reasonable when the concerns are tightly coupled to the routing decision itself (e.g., rejecting unauthenticated requests before they consume any backend capacity at all). Splitting them into separate, composable components can be preferable when different concerns need to evolve, scale, or be owned by different teams independently — for example, a security team owning authentication policy separately from a platform team owning load-balancing configuration — or when one concern (heavy rate-limit counter lookups against a shared store) has a meaningfully different performance profile that benefits from being isolated rather than coupled into the same request path as lighter-weight routing logic. There isn't a universally correct answer; the decision should follow organizational and performance boundaries, not default to either extreme.

16. SUMMARY

  • DNS and load balancing solve the same underlying problem — routing a request to a healthy destination — at very different granularities and timescales: DNS makes coarse, slow-changing, cacheable decisions (often geographic), while load balancers make fine-grained, continuously re-evaluated decisions about specific instances.
  • Layer 4 load balancers see only transport-level information (IPs, ports) and are fast and cheap; Layer 7 load balancers terminate and read the actual application request, enabling content-based routing at a higher per-request cost — neither is universally better, the choice depends on what the routing decision actually needs to see.
  • Load-balancing algorithms (round robin, least connections, weighted variants, consistent-hashing-based, latency-aware) each make a different assumption about traffic uniformity; picking the right one means matching the algorithm to the actual shape of your request cost and instance capacity, not defaulting to the most sophisticated option available.
  • Health checks, tuned with deliberate thresholds and intervals, are what make every load-balancing algorithm safe in practice — a load balancer is only as good as its knowledge of which instances are actually capable of serving a correct response.
  • Sticky sessions trade correctness convenience for real tension with horizontal scalability and failure tolerance; externalizing session state so any instance can serve any request is the standard, more resilient alternative.
  • In production, these concerns stack into a layered pipeline — DNS/GeoDNS, CDN edge, external L7 gateway, internal load balancer, service mesh sidecar — with routing decisions becoming more granular and more frequently re-evaluated the closer a layer sits to the actual workload; Spring Cloud Gateway, Spring Cloud LoadBalancer, and Spring Boot Actuator's health endpoints map directly onto specific layers of that same stack.
