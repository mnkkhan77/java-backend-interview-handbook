CHAPTER 05 — DATABASE REPLICATION & SHARDING

Volume 3 — Data at Scale · Chapter 5 of 12

CAP Theorem & Consistency Models (Chapter 02) taught you the vocabulary for what a distributed data system is allowed to promise a client, and Caching & CDNs (Chapter 04) showed how to keep hot, derived copies of data close to where it is read. This chapter is where those ideas become concrete, operational mechanics: how do you actually keep multiple copies of the *same* data in sync across machines (replication), and how do you split *different* pieces of data across machines so no single node has to hold or serve all of it (sharding)? Almost every "design a system that scales to millions of users" interview question eventually collapses into exactly these two mechanical questions, asked back to back — and the candidates who stand out are the ones who can explain not just that replication and sharding exist, but precisely which failure mode each specific topology and strategy trades away, and why a real production system almost always needs both at once.

1. MOTIVATION

A single database server, however powerful, runs into three distinct ceilings as an application grows, and it is worth naming them separately because each one calls for a different fix. First, a read-capacity ceiling: one machine can only answer so many queries per second before its CPU, memory, or disk I/O saturates, no matter how well-indexed the schema is. Second, an availability ceiling: if that one machine is the only copy of the data, its failure — a disk dying, a kernel panic, a botched deployment — takes the entire application down with it, and there is no way to serve even a stale answer while it recovers. Third, a write-capacity and storage ceiling: at some point the total volume of writes, or the total volume of data at rest, exceeds what any single machine's disks and write path can hold or absorb, regardless of how many read replicas you add, because read replicas still each store a full copy of the same data and none of them can accept writes faster than the single leader processing them can.

Replication — keeping multiple copies of the same data on different machines — directly addresses the first two ceilings: more copies means more machines available to serve reads, and means the data survives the loss of any single machine. Sharding (also called partitioning) — splitting the data itself into disjoint subsets, each held by a different machine or group of machines — directly addresses the third: no single machine needs to store or process writes for data it was never assigned. These are genuinely different problems with genuinely different failure modes, and a production system almost always needs both simultaneously: each shard is itself replicated for availability, so a real large-scale data tier looks like several independent replica sets, one per shard, not one giant replicated blob or one giant un-replicated partition.

The interview-signal reason to master this chapter precisely is that "how would you scale this database" is one of the most reliable ways an interviewer separates a candidate who has only read about distributed databases from one who has operated them. The honest, specific answer is never just "add replicas" or "shard it" — it is a reasoned walk through which topology, which consistency trade-off (Chapter 02's vocabulary, now applied), and which sharding key actually fit the access pattern described, including naming the failure modes each choice accepts. That reasoning, not the vocabulary alone, is what this chapter builds.

2. HISTORICAL BACKGROUND

2.1 Master-Slave Replication in Commercial and Open-Source RDBMSs (1990s–2000s)

Replication did not begin as a distributed-systems research idea — it began as a pragmatic feature bolted onto relational databases that were never designed to be distributed at all. Oracle, and later open-source databases like MySQL (with binary-log, or "binlog," replication shipped in MySQL 3.23 in the late 1990s) and PostgreSQL (with write-ahead log, or WAL, shipping added in the mid-2000s), gave operators a way to designate one server the "master" (today more commonly called the leader or primary) and stream its sequential log of changes to one or more "slave" servers (today, followers or replicas), which replayed those changes to maintain an eventually-identical copy. The original motivating use case was not elastic web-scale read traffic — it was disaster recovery and offline reporting: a warm standby to fail over to, and a replica that nightly batch-reporting jobs could hammer without slowing down the production primary.

2.2 The Dot-Com Read-Scaling Era (Late 1990s–2000s)

As web applications grew an audience far larger than their write volume (a classic blog, forum, or early social site is read orders of magnitude more often than it is written to), engineers repurposed replication for a new primary purpose: horizontal read scaling. Route writes to the single leader, and load-balance reads across a growing pool of read replicas. This pattern — still extremely common today, and the direct ancestor of Section 9's Spring routing-datasource pattern — let a single logical database serve far more read traffic than one machine's hardware could, at the cost of replication lag (Section 4.3) becoming a real, user-visible phenomenon for the first time, since replicas were now directly in the request path rather than only used for offline recovery or batch jobs.

2.3 Multi-Master Experiments and Their Painful Lessons (2000s)

Engineers soon wanted more than read scaling — they wanted write availability across multiple data centers, so a regional outage would not take writes down everywhere. This led to multi-leader (multi-master) replication products (MySQL multi-master setups, Oracle GoldenGate, early Lotus/Domino-style replication for groupware). The lesson the industry learned the hard way was that allowing writes to the same logical record at two different leaders simultaneously creates write conflicts that someone — the database, or the application — must resolve, and most early multi-master tooling resolved conflicts crudely (last-writer-wins by timestamp) or not at all, silently corrupting data under real concurrent load. This painful history is exactly why multi-leader replication remains a deliberately narrower-scoped tool today, as Section 4.1 details, rather than the default choice it once looked like it might become.

2.4 Dynamo and the Leaderless, Partitioned Era (2007)

Amazon's 2007 Dynamo paper (already introduced in Chapter 02 for its CAP/AP implications) is also the pivotal moment for this chapter's subject, because Dynamo fused replication and sharding into a single mechanism for the first time at this scale: data was both partitioned across a ring of nodes (via consistent hashing, the subject of Chapter 06) and replicated to N nodes per partition, with no single leader coordinating either decision. This leaderless, quorum-based design (Section 4.1) directly inspired Cassandra and Riak, and permanently changed the industry's mental model: replication and sharding stopped being treated as two unrelated features and started being treated as two faces of the same underlying partitioned-replica-set architecture.

2.5 Sharding Goes Mainstream, and Gets Automated (2008–2015)

Through the mid-2000s, sharding a relational database meant manual application-level bookkeeping: engineers hand-wrote the logic deciding which physical database held which user's data, and lived with the operational pain of resharding by hand when a shard outgrew its hardware. Two parallel developments changed this. First, purpose-built sharded NoSQL databases (MongoDB's built-in auto-sharding, 2010; Cassandra's token-ring partitioning) made partitioning a first-class, largely automatic database feature rather than an application concern. Second — and more relevant to this book's Java/Spring-heavy audience — proxy-based sharding layers for relational databases emerged: YouTube built and open-sourced Vitess in 2010 specifically to shard MySQL behind a proxy that let application code keep speaking ordinary SQL against what looked like one logical database; Citus (originally a startup, later a Postgres extension acquired by Microsoft) did the equivalent for PostgreSQL. Both are covered concretely in Section 9.

2.6 Globally-Distributed, Auto-Sharded, Strongly-Consistent Systems (2012–Present)

Google's Spanner paper (2012) and its descendants (CockroachDB, YugabyteDB) represent the current frontier: systems that automatically shard data by key range, automatically replicate and rebalance those shards across data centers and continents, and still offer strong consistency guarantees — using synchronized-clock infrastructure (briefly touched on in Chapter 02) to make globally-ordered transactions practical despite the coordination cost Chapter 02's PACELC framework predicts such consistency must pay. These systems do not eliminate the fundamental trade-offs this chapter covers; they automate and hide much of the manual operational work earlier generations of engineers did by hand, which is precisely why understanding the underlying mechanics still matters — automation that you cannot reason about when it fails is a liability, not a convenience.

3. PROBLEM STATEMENT

Chapter 02 answered a narrower, prior question: given that replicas exist, what guarantee can a client rely on when it reads from one? This chapter answers the two mechanical questions that come before that one is even relevant:

(1) How do you keep multiple copies of the same data consistent enough to be useful, across machines connected by an unreliable network, while deciding how quickly a write on one copy must become visible on the others? (2) How do you split one logical dataset across many machines so that no single machine must store or process all of it, while still letting the application find and query any given piece of data efficiently, and while being able to change that split later without taking the system down?

These two questions are related but genuinely distinct, and conflating them is a common source of imprecise system-design answers. Replication's problem is fan-out: the same logical record exists in N places, and the question is how writes propagate and how reads choose among those N places. Sharding's problem is partition assignment: a given record exists in exactly one shard (or one shard group), and the question is which shard owns which keys, and how that ownership can be changed later as data grows unevenly. A real production data tier answers both questions at once — each shard is itself a replicated group of machines — which is precisely why Section 8's production architecture shows replication and sharding composed together rather than as alternatives.

This chapter does not re-derive which consistency guarantee a replica is allowed to promise under a network partition — Chapter 02 already owns that theory in full, and Section 4.1 below leans on it directly rather than restating it. It also does not re-derive the mechanics of a consistent-hashing ring — Chapter 06 owns that mechanism in full; this chapter treats consistent hashing only as one specific, named technique for answering the hash-based sharding question in Section 4.4. What this chapter does own is everything mechanical in between: the concrete replication topologies, the concrete sharding strategies, what happens internally when they operate and when they fail, and the very real operational pain of resharding a system that is already serving production traffic.

4. THEORY

4.1 Replication Topologies

There are exactly three structural answers to "which node(s) may accept a write," and each has a distinct, nameable failure mode.

TopologyHow Writes FlowPrimary StrengthPrimary Failure Mode
Single-leader (master-slave / primary-replica)Exactly one node (the leader) accepts writes; it ships its change log to one or more followers, which apply changes in the same order and only serve readsSimple to reason about — there is only ever one authoritative order of writes, so there is nothing to reconcileThe leader is a single point of failure for writes; if it dies, a failover (manual or automatic election) is required, and any writes not yet shipped to the newly promoted follower before the old leader died can be lost

Note precisely how this maps onto Chapter 02's vocabulary: single-leader replication, configured to block a write until a majority of followers acknowledge it, is a CP-leaning design — it refuses to let two leaders exist and will sacrifice write availability during a leader failure rather than risk two authoritative answers. Multi-leader and leaderless designs are both structurally AP-leaning — they accept writes on more than one node to preserve availability, and pay for that with the conflict-reconciliation machinery Section 5 describes. This chapter is about the mechanics of implementing whichever side of that trade-off Chapter 02 already taught you how to choose.

4.2 Synchronous vs. Asynchronous Replication

Independently of topology, every replication link has to answer one more question: does the leader wait for a follower to confirm it has received a write before telling the client the write succeeded?

  • Synchronous replication — the leader waits for (typically) at least one follower to acknowledge the write before acknowledging it to the client. This guarantees that an acknowledged write is durable on at least two machines, so a leader crash immediately after acknowledging a write cannot silently lose it. The direct cost is latency: every write now waits on a network round trip to the follower, and — critically — if that follower becomes unreachable, the leader can no longer accept writes at all unless it is explicitly configured to fail open, which defeats the durability guarantee it existed to provide.
  • Asynchronous replication — the leader acknowledges the write to the client immediately, then ships it to followers in the background, without waiting. Writes are fast and the leader's availability is not coupled to any follower's health. The direct cost is a durability gap: if the leader crashes after acknowledging a write but before shipping it to any follower, that write is lost permanently from the follower's (and, after failover, the whole system's) point of view, even though the client was already told it succeeded.
  • Semi-synchronous replication — a practical middle ground many production MySQL and PostgreSQL deployments use: the leader waits for acknowledgment from at least one follower (not all of them) before confirming the write, while the remaining followers replicate asynchronously. This bounds the worst-case data loss to "whatever the single synchronous follower also missed" while avoiding the full latency and availability cost of waiting on every follower.

This is, again, exactly Chapter 02's PACELC framing made concrete at the replication-link level: synchronous replication buys durability (a consistency-adjacent property) by spending latency; asynchronous replication buys latency by risking data loss (a durability failure, which is its own distinct cost from a stale-read consistency failure, though both stem from the same underlying "coordination costs time" trade-off).

4.3 Replication Lag and the Read-Your-Writes Problem

Even with a correctly functioning single-leader, asynchronously-replicated system, there is always some non-zero delay — replication lag — between a write committing on the leader and that same write becoming visible on a given follower. Lag can be milliseconds under light load or balloon to seconds or minutes under heavy write volume, follower resource contention, or network congestion between data centers. Lag itself is often tolerable — most reads do not care about sub-second staleness — but it produces one specific, user-visible failure that Chapter 02 named precisely: a client that just wrote through the leader, then immediately reads from a lagging follower, can fail to see its own write — a direct violation of read-your-writes consistency (Chapter 02, Section 4.4), even though the system as a whole is behaving exactly as its asynchronous-replication design intended.

The standard mitigations, all variations on "route the read somewhere that is guaranteed not to be stale relative to this specific client's last write," are: route the read-after-write request back to the leader directly for some short window after a write; track a logical write timestamp or log position per client and only route that client's next read to a follower whose replicated position has caught up past it; or route all reads for a given user consistently to the same follower ("sticky sessions") combined with monitoring that follower's lag. None of these fixes make replication synchronous — they narrow where the staleness is allowed to surface, which is a cheaper and usually sufficient fix for the specific user-facing symptom.

4.4 Sharding Strategies

Once a dataset is too large (in storage or write throughput) for one replica set to hold, it must be split across multiple replica sets — shards. The central design decision is the function that maps a record to its owning shard.

These are not always mutually exclusive in practice — a real system can use range-based sharding at a coarse level (tenant or region) and hash-based sharding within each coarse range, or use a directory specifically to handle the exceptions a pure hash or range function cannot (e.g., manually relocating one unusually large customer's shard). The strategy should be chosen by asking which access pattern (point lookups, range scans, uneven key distribution) the application actually needs served efficiently, not by which strategy sounds most sophisticated.

4.5 Resharding, Rebalancing, and the Hot-Shard / Hot-Key Problem

A sharded system is never finished being sharded. Shards grow unevenly as some tenants, regions, or key ranges accumulate more data or traffic than others, and the original shard count eventually stops being enough regardless of strategy. Resharding is the process of changing the assignment of keys to shards — splitting one overloaded shard into two, merging underused shards, or increasing the total shard count — while the system continues serving live traffic. The central operational challenge is that resharding necessarily moves data between machines, and any key being moved must remain correctly readable and writable throughout that move, without the application ever seeing an inconsistent or doubled-up view of it (Section 5.4 covers the internal mechanics of doing this safely).

A closely related but distinct problem is the hot shard (or hot key): even a theoretically well-balanced sharding strategy can end up with one shard receiving disproportionate load, because real-world traffic is rarely uniform — a celebrity user's profile, a viral post, a single large enterprise tenant, or (as Section 4.4 noted) a sequential key's "current" range can all concentrate traffic on one shard far beyond what resharding the rest of the system would fix, because the problem is not too few shards overall but one specific key or narrow range being disproportionately popular. Common mitigations: key salting (appending a random or rotating suffix to an overly popular key so its writes spread across multiple physical shards, with reads fanning out across the salted variants); adding a caching layer in front of the hot shard specifically (Chapter 04's subject, applied surgically); splitting the specific hot range further, even if the rest of the system's shards remain coarser; and load-aware rebalancing that tracks actual request volume per shard, not just data volume, and moves ranges to equalize load rather than only equalizing storage size.

5. INTERNAL WORKING

5.1 How Single-Leader Log-Shipping Replication Actually Works

Internally, a single-leader relational database does not replicate by re-running SQL statements on each follower independently (an early approach called statement-based replication, now mostly abandoned because non-deterministic statements — NOW(), auto-increment ordering under concurrency — can produce different results on different replicas). Modern systems replicate the write-ahead log (WAL) or binary log (binlog) — the same durable, sequential log the leader already writes to disk before applying any change, originally for crash recovery. Each follower maintains a connection to the leader, streams new log entries as they are appended, and replays them in the exact same order the leader applied them, which guarantees the follower reaches the identical state the leader was in at that log position — this is also precisely why replication lag (Section 4.3) is measurable in concrete units: "how many log bytes, or how many seconds, is this follower's replay position behind the leader's write position."

5.2 Conflict Detection and Resolution in Multi-Leader Replication

When two leaders each accept a write to the same logical record before either has received the other's write, the system has a genuine conflict once both writes eventually arrive at each leader via cross-replication. Detecting this requires each write to carry enough metadata to tell whether it causally depends on the other (in which case there is no real conflict — just apply them in causal order) or is truly concurrent (a real conflict, same as Chapter 02 Section 5.2's leaderless discussion, and often implemented with the same vector-clock-style mechanism). Resolution strategies, from crudest to most careful: last-writer-wins by timestamp (simple, but silently discards one of the two writes, which is unacceptable for some data); deterministic merge functions defined per data type (e.g., for a numeric counter, add both deltas instead of picking one write as the winner); and exposing the conflict to the application to resolve with domain knowledge, exactly as Dynamo's original shopping-cart design did (Chapter 02, Section 5.2) — multi-leader replication inherits this same conflict-resolution burden, it does not avoid it.

5.3 Routing and Reconciliation in Leaderless Replication

In a leaderless, quorum-based design, the internal machinery handling a single write request involves several moving parts working together: the client (or a coordinator node acting for it) sends the write to all N replicas owning that key in parallel, counts acknowledgments, and considers the write successful once W have confirmed, without waiting for the remaining N−W. If one of the N target replicas is temporarily unreachable, many such systems use sloppy quorum and hinted handoff: a different, reachable node temporarily accepts and stores the write "on behalf of" the unreachable one, holding a "hint" to forward it once the original node recovers — trading strict quorum membership for continued write availability. Reads work symmetrically, querying R replicas and reconciling their answers (by version or vector clock) before returning, with any detected staleness triggering the read-repair process Chapter 02 Section 5.2 already described.

5.4 Resharding a Live System Without Downtime

Moving a key range from one shard to another while the system keeps serving traffic for that exact range is the single hardest operational sequence this chapter covers, and production systems converge on a similar pattern regardless of database technology:

  1. Dual-write phase: the application (or a proxy/router) begins writing every new or updated record in the range being moved to both the old shard and the new shard, while all reads still go to the old shard — this ensures no write is lost once the cutover happens, at the cost of temporary write amplification.
  2. Backfill phase: a background job copies all pre-existing data in the range from the old shard to the new shard, typically in small batches to avoid overwhelming either shard's I/O capacity, while the dual-write phase continues to keep the new shard current with live traffic arriving concurrently with the backfill.
  3. Verification phase: a reconciliation job compares the old and new shard's contents for the migrated range (often via checksums or row counts per sub-range) and confirms they match before anything depends on the new shard being authoritative.
  4. Cutover phase: reads (and, shortly after, writes) are switched to the new shard, typically range by sub-range rather than all at once, so any problem surfaces on a small slice of traffic rather than the whole migrated range at once; the old shard's copy is kept briefly as a rollback safety net before being decommissioned.

Notice that this sequence is the same structural shape as the zero-downtime CP-to-AP data-store migration pattern from Chapter 02's interview questions: dual-write, reconcile, verify, cut over — resharding is, mechanically, a special case of "migrate live data between two stores without losing anything or serving inconsistent answers," applied to two shards of the same logical database instead of two different database technologies.

6. MATHEMATICS

6.1 Quantifying Replication Lag

Replication lag is measured directly as the gap between the leader's current write position and a given follower's current replay position in the shared log: 

lag(follower) = leader_log_position - follower_applied_log_position

(commonly expressed in bytes of log, or converted to an estimated
time delay using the follower's observed replay throughput)

This is the metric every production replication setup should alert on directly (Section 12), because it is the one number that tells you, concretely, how stale a read from that specific follower could be right now — which is exactly the number Section 4.3's read-your-writes mitigations need in order to decide whether a given follower is safe to route a specific client's read to.

6.2 Why Naive Hash-Mod Sharding Breaks on Resharding

With the simplest possible hash-based scheme, shard = hash(key) mod N, changing N (adding or removing shards) changes the assignment for most keys, not just a proportional few. For a near-uniformly distributed hash function, the fraction of keys that must move when N changes to N' is: 

fraction_of_keys_that_move ≈ 1 - min(N, N') / max(N, N')

Example: N = 4 → N' = 5
fraction ≈ 1 - (4/5) = 0.20   →  only 20% move... but that is
                                  the BEST case (adding exactly
                                  one shard to a small N).

Example: N = 4 → N' = 8 (doubling)
fraction ≈ 1 - (4/8) = 0.50   →  50% of ALL keys must move,
                                  even though only new capacity
                                  was added, none was removed.

In the general case of mod N hashing, almost every key's target bucket changes whenever N changes, because the modulus operation has no structural relationship between the old and new assignment — this is precisely the problem consistent hashing (Chapter 06) is purpose-built to solve, bounding the fraction of keys that must move to roughly 1/N instead of the near-total reshuffling shown above, by assigning keys and nodes to positions on a ring rather than to a raw modulus. This chapter treats that fix as Chapter 06's mechanism to explain in full; the point to take from this section is precisely why naive modulus-based sharding is operationally painful enough that an alternative was worth inventing.

6.3 Shard Capacity Planning

Given a dataset growing at rate G (e.g., gigabytes per day) and a per-shard comfortable capacity ceiling C (chosen well below the hardware's absolute limit, to leave headroom for the time it takes to detect the need for resharding and execute it), the number of shards needed by a future time horizon t (in days), starting from a current total size S0, is: 

shards_needed(t) = ceil( (S0 + G × t) / C )

Worked example: S0 = 2 TB, G = 50 GB/day, C = 500 GB per shard,
planning horizon t = 180 days:

shards_needed(180) = ceil( (2000 GB + 50 × 180) / 500 )
                    = ceil( (2000 + 9000) / 500 )
                    = ceil(11000 / 500)
                    = ceil(22) = 22 shards

The practical lesson from this formula is less about the arithmetic and more about timing: because Section 5.4's resharding process takes real time and engineering effort to execute safely, capacity planning should trigger a resharding project well before C is reached on any shard, not at the moment it is reached — treating C as a hard alarm threshold rather than the actual deadline.

9. JAVA / SPRING PERSPECTIVE

9.1 Read/Write Routing with Spring Data JPA and a Routing DataSource

The most common way replication surfaces directly in Java code is a DataSource that transparently routes to the leader or to a replica based on whether the current transaction is read-only. Spring provides AbstractRoutingDataSource specifically for this: it is given a map of logical keys to real DataSource beans, and resolves which one to use per call by consulting a thread-local "current lookup key" your code sets. The natural hook for setting that key is @Transactional(readOnly = true), since Spring already tracks that flag per transaction: 

public class ReplicaRoutingDataSource extends AbstractRoutingDataSource {
    @Override
    protected Object determineCurrentLookupKey() {
        // TransactionSynchronizationManager exposes the readOnly flag
        // Spring already set from @Transactional(readOnly = true).
        boolean readOnly = TransactionSynchronizationManager.isCurrentTransactionReadOnly();
        return readOnly ? "replica" : "leader";
    }
}

// Registration: one DataSource pointing at the leader, one (or a
// load-balanced pool) pointing at read replicas, selected per-call
// by the routing logic above — application code never changes.
@Bean
public DataSource routingDataSource(DataSource leaderDs, DataSource replicaDs) {
    ReplicaRoutingDataSource routing = new ReplicaRoutingDataSource();
    Map<Object, Object> targets = new HashMap<>();
    targets.put("leader", leaderDs);
    targets.put("replica", replicaDs);
    routing.setTargetDataSources(targets);
    routing.setDefaultTargetDataSource(leaderDs);  // fail safe to leader
    return routing;
}

@Transactional(readOnly = true)
public List<Order> listRecentOrders(Long customerId) {
    // Routed to a replica — fine for this query, but note Section 4.3's
    // read-your-writes caveat: if this is called immediately after a
    // write in the SAME user flow, route that specific call to the
    // leader instead, or this method risks missing the user's own write.
    return orderRepository.findRecentByCustomer(customerId);
}

The critical discipline this pattern requires, and the thing interviewers probe for, is explicitly identifying the read-after-write call sites in a flow and routing those specifically back to the leader (or to a replica known to be caught up) rather than trusting @Transactional(readOnly = true) blindly everywhere — exactly the read-your-writes mitigation Section 4.3 described, now expressed as a concrete annotation choice per method.

9.2 Hibernate Multi-Tenancy as a Sharding-Adjacent Pattern

Hibernate's multi-tenancy support — implemented via a CurrentTenantIdentifierResolver (determines which tenant the current request belongs to) and a MultiTenantConnectionProvider (resolves that tenant identifier to the correct physical connection) — is worth recognizing as structurally the same problem as directory-based sharding (Section 4.4), scoped to one tenant per database or schema instead of one key range per shard. In schema-per-tenant mode, every tenant's data lives in its own schema within one physical database, isolated logically but sharing hardware; in database-per-tenant mode, each tenant gets an entirely separate physical database, which is sharding by tenant ID taken to its most isolated extreme — maximum blast-radius isolation (one tenant's load or corruption cannot affect another's) at the cost of the same resharding-adjacent operational overhead Section 5.4 describes whenever tenants must be moved or consolidated for load-balancing.

9.3 Vitess and Citus: Sharding Proxies a Java Shop Reaches For

For teams already committed to MySQL or PostgreSQL who need the write-scaling and storage-scaling benefits of sharding (Section 1) without hand-rolling the routing layer, directory, and resharding tooling themselves, Vitess (for MySQL) and Citus (a PostgreSQL extension/distributed coordinator) are the production-proven tools of choice. Both present application code — including a Spring Data JPA repository layer, via an ordinary JDBC driver connection — with what looks like a single logical database, while internally handling shard routing, cross-shard query fan-out for range or aggregate queries, and much of the resharding sequence from Section 5.4 as an operational, largely automated workflow rather than application-level code the Java team must write and maintain by hand. The trade-off worth naming explicitly in an interview: adopting one of these tools buys you Section 5.4's hardest operational sequence "for free," at the cost of an added infrastructure dependency and some SQL feature limitations (certain cross-shard joins or transactions are restricted or forbidden) that a single, unsharded database would not impose.

10. BEST PRACTICES

  • Choose the sharding key based on the dominant access pattern, not convenience. A key that makes point lookups fast but forces every range query or report into a cross-shard scatter-gather (Section 4.4) will quietly become a performance and cost problem the moment analytics or reporting needs grow.
  • Monitor replication lag as a first-class metric, with alerting thresholds tied to real user impact. Section 6.1's lag formula is only useful if it is actually measured continuously and alerted on before it causes a visible read-your-writes failure, not discovered after a support ticket.
  • Plan capacity and trigger resharding well before a shard hits its ceiling, not at the ceiling. Section 6.3's capacity math assumes the resharding project itself takes real calendar time to execute safely (Section 5.4) — treat the capacity threshold as a trigger to start planning, not a deadline to start executing.
  • Design the sharding key and strategy to avoid predictable hot shards from day one. Sequential or timestamp-based keys under range-based sharding (Section 4.4) are a well-known, avoidable mistake — prefer a hash-based or composite key when write concentration is a foreseeable risk, rather than retrofitting key salting after a hot shard is already in production.
  • Treat the shard map / config store as its own strongly-consistent subsystem. As Section 8 noted, an inconsistent view of which shard owns which key is a correctness bug for every component that relies on it, even in an otherwise AP-leaning system.
  • Build and rehearse the dual-write/backfill/verify/cutover sequence before you need it under pressure. Section 5.4's resharding process has several places a mistake can cause data loss or inconsistency; practicing it on a non-critical shard before the first time it is needed on a hot, customer-impacting one is far cheaper than debugging it live.

11. COMMON MISTAKES

  • Assuming "we added read replicas" automatically means "we scaled writes." Replicas scale read capacity only; every write still funnels through the single leader (or, in multi-leader/leaderless designs, still has to be coordinated and conflict-resolved) — a write-heavy workload needs sharding, not more replicas, and conflating the two is a common early-design error.
  • Choosing asynchronous replication for data where any loss is unacceptable, without realizing it. Section 4.2's durability gap is easy to overlook until the first leader crash loses an acknowledged write — financial or audit-trail data should be evaluated explicitly against this risk, not defaulted into whatever replication mode a database ships with.
  • Treating "eventually consistent replicas" and "read-your-writes consistent replicas" as the same thing. As Section 4.3 and Chapter 02 both emphasize, eventual consistency alone makes no promise that a user sees their own write — this requires an explicit routing mechanism, not an assumption.
  • Picking a sharding key that looks evenly distributed in sample data but concentrates in production. A key that is uniform across a test dataset can still correlate strongly with real-world popularity (a small number of large tenants, a few viral content items) once live traffic arrives, producing the hot-shard problem Section 4.5 describes despite a seemingly sound original design.
  • Underestimating naive rehashing's blast radius when adding shards. Section 6.2's math is not a theoretical curiosity — a team that scales from 4 to 8 shards using plain mod N hashing without consistent hashing (Chapter 06) will genuinely move roughly half of all keys, generating an enormous, often unplanned-for burst of backfill traffic.
  • Running the dual-write phase of a resharding migration (Section 5.4) without a reconciliation/verification step. Skipping verification means any bug in the dual-write logic (a dropped write, a race condition) is discovered only after cutover, when the old shard's safety net is no longer being kept current — turning a detectable, recoverable issue into silent, permanent data loss.

12. PERFORMANCE CONSIDERATIONS

  • Synchronous replication's latency cost scales with the number and geographic spread of followers it waits on — waiting for acknowledgment from a follower in a distant region adds that region's round-trip time to every single write, which is why most production systems use semi-synchronous replication (Section 4.2) to bound this cost to one nearby follower rather than every replica.
  • Cross-shard queries (range scans or aggregates under hash-based sharding) pay a scatter-gather tax proportional to the number of shards queried and the slowest shard's response time — a query's latency is bounded by its slowest participating shard, the same "wait for the slowest" dynamic Chapter 02 described for quorum reads, now happening across shards instead of replicas.
  • Resharding's backfill phase competes for I/O with live production traffic on both the source and destination shard, which is why Section 5.4's backfill is typically rate-limited and run in small batches rather than as a single bulk copy — an unthrottled backfill can itself cause a production incident on the very shard it is trying to relieve.
  • A hot shard's impact is not limited to that shard — in topologies where a routing/proxy layer maintains a shared connection pool or thread pool across all shards, one overloaded shard can exhaust shared resources and degrade latency for queries to otherwise healthy shards, which is why per-shard resource isolation (separate connection pools, circuit breakers per shard) is a meaningful production safeguard, not just a tidiness preference.
  • Replica read load is not infinitely scalable by simply adding more followers — every additional follower is one more target the leader's replication stream must serve, and at a large enough fan-out the leader's own replication bandwidth, not the followers' query capacity, becomes the bottleneck, which is why very large read-scaling deployments often introduce a replication hierarchy (followers replicating from other followers) rather than fanning every follower out directly from one leader.

13. SECURITY CONSIDERATIONS

  • Replication streams must be encrypted in transit. The WAL/binlog stream between leader and follower (Section 5.1) carries every row of data ever written, often across data centers or even across cloud regions over the public internet — leaving this stream unencrypted exposes the entire dataset to interception, not just the subset a single query would have returned.
  • Read replicas widen the access-control surface, not just the read-capacity. Every additional replica is an additional machine holding a full (or near-full) copy of the data, and must be governed by the same access controls, patching discipline, and audit logging as the leader — a replica compromised through weaker security hygiene than the leader is just as damaging a breach as compromising the leader itself.
  • Geo-sharding by region has direct data-residency and compliance implications. If a sharding key or directory (Section 4.4) determines which physical region a given customer's data lives in, that same mechanism is enforcing (or failing to enforce) regulatory requirements like GDPR data-residency rules — a bug in shard-assignment logic, or a resharding migration (Section 5.4) that moves a customer's shard across a regulatory boundary without explicit review, is a compliance incident, not merely an availability or performance one.
  • Resharding and migration tooling typically requires elevated, cross-shard administrative privileges. The dual-write/backfill/cutover tooling from Section 5.4 usually needs write access to both the source and destination shard simultaneously, and often to the shard map itself — this tooling and its credentials should be scoped, audited, and time-limited specifically because a compromised or misused migration script has the blast radius of multiple shards at once, not one.

14. INTERVIEW QUESTIONS

JUNIORQ1. A new engineer says "we need to shard the database" when what's actually happening is reads timing out during traffic spikes, while write volume and total data size are nowhere near a single machine's limits. What would you tell them instead, and why does conflating replication and sharding matter here?

ROI: ★★★★★ · Frequency: Extremely High

Reads timing out under spiky traffic is a read-capacity and availability problem, which replication (read replicas, load-balanced reads) directly addresses by adding more machines that can serve the same data. Sharding solves a different ceiling entirely — write throughput and total storage exceeding one machine — and reaching for it here adds resharding complexity, cross-shard query limitations, and a much harder-to-reverse architectural commitment for a problem it doesn't actually fix. Conflating the two means paying the heavier tool's cost without getting the benefit the symptom actually calls for.

JUNIORQ2. Your single-leader database's leader dies mid-deploy. The on-call engineer promotes a follower in under a minute and writes resume — but a customer reports their order from thirty seconds before the failure has vanished. Explain exactly what happened, and whether the on-call response was wrong.

ROI: ★★★★★ · Frequency: Extremely High

The on-call response was correct, not wrong — the vanished order is a separate, expected consequence of how replication was configured, not a failover mistake. If replication to followers was asynchronous, the leader could have acknowledged that write to the client before shipping it to any follower, and the newly promoted follower never received it, so promoting it permanently drops that already-acknowledged write. The actual fix for this gap isn't a faster failover — it's synchronous or semi-synchronous replication (Section 4.2), which ensures an acknowledged write is durable on at least one follower before the client is told it succeeded, so a subsequent leader crash can't silently lose it.

JUNIORQ3. A monitoring dashboard shows replication lag bouncing between 50ms and 4 seconds throughout the day with no clear pattern. Is that worth paging someone over, and what would make you escalate it versus leave it alone?

ROI: ★★★★★ · Frequency: Extremely High

Lag bouncing within a few seconds with no sustained upward trend is usually normal background noise from varying write volume, and shouldn't by itself trigger a page — most reads tolerate sub-second-to-low-single-digit-second staleness fine. What's actually worth escalating is a sustained upward trend (lag that keeps climbing rather than oscillating back down, suggesting the follower can't keep up with current write volume and will eventually fall arbitrarily far behind) or any spike that crosses the specific staleness tolerance a dependent feature actually needs. The useful alert distinguishes "is lag currently high" from "is lag trending worse" — the second predicts a real future problem, the first often just describes a momentary, self-correcting blip.

JUNIORQ4. A user updates their profile picture, refreshes the page, and still sees the old one for a few seconds before it updates. Support says "it's just a caching issue." Is that the right diagnosis, and what would you check to confirm or rule it out?

ROI: ★★★★★ · Frequency: Extremely High

It might be caching, but it's at least as likely to be a read-your-writes violation from replication lag, and the two need different fixes, so "just caching" shouldn't be accepted without checking. If the read after the update is served from a read replica, and the write just went to the leader, the replica may simply not have caught up yet — the symptom (brief staleness that clears itself) looks identical to a short-TTL cache. The way to tell them apart: check whether a cache layer with a TTL sits in this specific path at all, and separately check the replica's lag at the moment of the request; the fastest confirming test is forcing that one read to hit the leader directly and seeing whether the problem disappears regardless of any cache TTL.

JUNIORQ5. You're asked to pick a replication topology for a new service, and the first instinct in the room is multi-leader because "it sounds the most available." What question would you ask before agreeing, and what are the other two options you'd compare it against?

ROI: ★★★★☆ · Frequency: High

Ask whether this service genuinely needs to accept low-latency writes from multiple independent regions simultaneously — that's the only thing multi-leader buys over the alternatives, and it costs you conflict resolution (Section 4.1, Section 5.2) in exchange. Compare it against single-leader (simplest, one true order of writes, but a leader failure briefly blocks writes until failover) and leaderless/quorum (no failover process at all, since quorum math absorbs node loss directly, but more complexity lives in the client/coordinator). For most services without a genuine, validated multi-region concurrent-write requirement, single-leader with solid failover and read replicas is the right default — "sounds the most available" is not the same claim as "is the right trade-off for this workload."

JUNIORQ6. A team wants zero added write latency from replication and is leaning toward fully asynchronous. What would you ask them to confirm they actually understand before signing off, and what failure scenario would you make them say out loud?

ROI: ★★★★★ · Frequency: Extremely High

Confirm they understand the concrete data-loss window this choice opens, not just the latency it saves. Make them state the failure scenario explicitly: "the leader acknowledges a write to the client, crashes before shipping it to any follower, and a follower gets promoted — that acknowledged write is gone permanently, even though the client was already told it succeeded." Then ask them to name, in concrete terms, how much of that kind of loss is actually acceptable for this data; if the honest answer is "none," asynchronous replication is the wrong choice regardless of how much they want the latency profile, and semi-synchronous replication is almost certainly the compromise they actually need.

JUNIORQ7. A dataset needs to be split across machines, and the obvious first idea in the room is "just hash the primary key." What would make you push back and ask about the access pattern first, and what alternatives would you weigh it against?

ROI: ★★★★★ · Frequency: Extremely High

Push back because hash-based sharding buys even distribution at the direct cost of range queries — if the dominant access pattern involves range scans (date ranges, sorted pagination), hashing destroys key ordering and turns every such query into a scatter-gather across every shard instead of a handful of contiguous ones. Weigh it against range-based sharding (keeps range queries cheap, but risks hot shards on sequential keys) and directory-based sharding (maximum flexibility to place individual keys anywhere, at the cost of a lookup dependency on every request). The right choice follows from which queries actually dominate real production traffic, not from which strategy is conceptually simplest to reach for first.

JUNIORQ8. A range-sharded system assigns new signups to shards by ascending user ID. Six months in, one shard is handling nearly all write traffic while the others sit almost idle. Diagnose the cause and propose a fix that doesn't require abandoning range-based sharding entirely.

ROI: ★★★★☆ · Frequency: High

Because keys are assigned in increasing order and ranges are assigned to shards in order, every newly created record — which always has the newest, highest ID — lands on whichever shard currently owns the tail end of the range, concentrating all new write traffic onto that single shard regardless of total shard count. A fix that keeps range-based sharding's benefits elsewhere: deliberately distribute new signups across a rotating set of "currently active" shards (round-robin or hash-prefixed) rather than strictly appending to the single newest range, so write load for new records is spread across multiple shards while older, settled ranges keep the range-query benefits that motivated this strategy in the first place.

JUNIORQ9. After switching from range-based to hash-based sharding specifically to fix a hot-shard problem, a dashboard query for "orders from the last 24 hours" that used to hit one shard now times out under load. What changed, and what are your options?

ROI: ★★★★☆ · Frequency: High

Hashing deliberately destroys ordering, so records that used to be adjacent (recent orders, clustered by time) are now scattered across every shard — a query that used to target one contiguous range now has to fan out to all shards and merge results, multiplying both load and latency compared to what it used to cost. Options: maintain a separate, purpose-built index or materialized view for this specific time-range access pattern instead of querying the hash-sharded data directly, accept and explicitly parallelize/cap the scatter-gather cost if it's infrequent enough to tolerate, or use a hybrid key that preserves some time-based locality for this query while still hashing enough to keep write distribution even.

JUNIORQ10. One shard in your hash-sharded cluster is running at 90% CPU while the other eleven sit around 20%, even though the hash function is confirmed to distribute keys uniformly. What's the likely explanation, given that the hash is working correctly?

ROI: ★★★★☆ · Frequency: High

A uniform hash guarantees roughly equal key count per shard, not equal traffic per shard — a hot shard despite correct, uniform hashing almost always means the real-world access pattern is skewed (one or a few keys on that shard are disproportionately popular: a viral item, an oversized tenant), not that the hashing itself is broken. Mitigations: key salting to spread a single hot key's load across multiple physical shards, a cache layer in front of that specific hot key, or explicitly isolating a known outsized key onto its own dedicated shard (Section 4.5, Q29) rather than treating it as just another hashed key among many.

JUNIORQ11. Your team needs to double the number of shards on a system that's live and serving production traffic around the clock, with no acceptable maintenance window. What makes this fundamentally harder than provisioning the new shards and updating a config value?

ROI: ★★★★☆ · Frequency: Medium-High

A config change can tell the system a new shard exists, but it does nothing to move the existing data that now belongs on it — resharding has to actually relocate data to its new owning shard while the system keeps serving reads and writes against data that might be mid-move, which is a fundamentally different problem from adding capacity. This is why resharding follows a deliberate dual-write, backfill, verify, cutover sequence (Section 5.4) instead of a single atomic switch: skipping or rushing any one of those phases risks silently losing or serving stale data for whatever happened to be migrating at that moment, under live traffic, with no maintenance window to safely absorb the mistake.

JUNIORQ12. A startup's single database has been fine for two years, and leadership asks why engineering wants to invest in replication and sharding now rather than waiting until there's an actual outage. What's the technical argument for acting before the ceiling is hit?

ROI: ★★★★☆ · Frequency: Medium-High

A single, un-replicated, un-sharded database faces three separate ceilings — read capacity, availability (it's a single point of failure), and write-capacity/storage — and for a growing application each is a question of when, not if, it gets hit. The argument for acting early is that replication and sharding are both safer and cheaper to design and validate with headroom to spare than to retrofit reactively during or immediately after an outage, when there's no time to test a migration carefully and every decision is made under pressure. "It's been fine for two years" describes the ceiling's distance, not its absence — and the lead time needed to address it safely doesn't shrink just because the team waits longer to start.

JUNIORQ13. A team is debating fully synchronous replication (wait for every follower) versus fully asynchronous (wait for none) and treats it as a binary choice. What are they missing, and when would it actually matter?

ROI: ★★★★☆ · Frequency: Medium

They're missing semi-synchronous replication, the practical middle ground most production MySQL and PostgreSQL deployments actually use: the leader waits for acknowledgment from just one follower (not all of them) before confirming the write, bounding worst-case data loss to whatever that single synchronous follower also missed, without paying the full latency and availability cost of waiting on every follower. It matters whenever the all-or-nothing framing would otherwise force a bad trade: fully async accepts the data-loss risk a durability-sensitive system can't tolerate, while fully synchronous-to-everyone creates the W=N write-availability fragility where one slow follower can stall every write — semi-synchronous sidesteps both failure modes for the common case where "durable on at least two machines" is the actual requirement, not "durable on all of them."

MIDQ14. Walk through exactly why a multi-leader replication setup can produce a write conflict that single-leader replication structurally cannot.

ROI: ★★★★★ · Frequency: High

In single-leader replication, there is only ever one node authorized to accept writes, so there is only ever one true order of operations — no two writes can be "concurrent" from the system's point of view, since they are all serialized through that one leader. In multi-leader replication, two different leaders can each accept a write to the same record before either leader has received the other's write via cross-replication, meaning both writes are genuinely concurrent and neither has a natural claim to being "first" — this is a conflict that exists because there are two independent points of write authorization, a situation single-leader replication never creates by design.

MIDQ15. Compare the write-availability characteristics of single-leader versus leaderless replication during a node failure.

ROI: ★★★★☆ · Frequency: High

In single-leader replication, if the leader itself fails, writes are unavailable until a failover (manual or automatic election) completes — a real, if often brief, write outage. In leaderless replication, no single node's failure blocks writes at all, because a write only needs W out of N replicas to acknowledge it; as long as enough replicas remain reachable to satisfy W, writes continue uninterrupted with no failover process required.

MIDQ16. Why can't you just configure synchronous replication to every follower and call the durability problem solved?

ROI: ★★★★☆ · Frequency: Medium-High

Waiting for every follower to acknowledge before confirming a write couples the leader's write availability to the availability of every single follower — if even one follower is slow or unreachable, writes stall or fail entirely, even though the leader and most followers are perfectly healthy. This is the same W=N write-availability trap Chapter 02 described for quorum systems, applied to replication: maximizing durability this way concentrates fragility into the single least-available follower.

MIDQ17. Describe two concrete mitigations for the read-your-writes problem caused by replication lag, and the trade-off each one makes.

ROI: ★★★★★ · Frequency: High

First, route the read-after-write request back to the leader for a short window after the write — simple and reliable, but adds load to the leader exactly for the traffic pattern read replicas exist to offload. Second, track a per-client log position or version and only route that client's subsequent reads to a replica proven to have caught up past it — avoids extra leader load, but requires plumbing a version/position token through the client or session, adding implementation complexity.

MIDQ18. Why does directory-based sharding introduce an extra point of failure or bottleneck that range-based and hash-based sharding avoid?

ROI: ★★★★☆ · Frequency: Medium-High

Range-based and hash-based sharding can both be computed locally by any client simply by applying a known function to the key — no network call is required to determine ownership. Directory-based sharding requires consulting an external lookup table on (or near) every request, meaning that directory service's availability and latency become a dependency for every single request in the system, rather than a pure, local computation.

MIDQ19. Explain the dual-write phase of a live resharding migration, and what specifically can go wrong if it's implemented incorrectly.

ROI: ★★★★★ · Frequency: High

During dual-write, the application (or a proxy) writes every new or updated record in the range being migrated to both the old and new shard simultaneously, so no write is lost once cutover happens later. If this is implemented incorrectly — for example, if a write to the new shard fails silently while the write to the old shard succeeds, or if the two writes aren't properly ordered relative to concurrent backfill copying the same key — the new shard can end up missing or holding stale data for some keys, which a verification step (comparing both shards) is specifically meant to catch before cutover makes the new shard authoritative.

MIDQ20. Given N=6 shards using naive hash(key) mod N and you need to add 2 more shards (N'=8), roughly what fraction of keys will need to move?

ROI: ★★★★☆ · Frequency: Medium-High

Using fraction ≈ 1 - min(N, N')/max(N, N') = 1 - 6/8 = 1 - 0.75 = 0.25, roughly 25% of all keys would need to move — a significant, disruptive fraction for adding only two shards, which is exactly the operational pain that motivates using consistent hashing instead.

MIDQ21. In a leaderless, quorum-based cluster, one replica goes down for ten minutes during routine maintenance. Writes keep succeeding the whole time with no visible impact. What mechanism is making that possible, and what does it actually do with the writes meant for the down replica?

ROI: ★★★★☆ · Frequency: Medium-High

Hinted handoff is almost certainly the mechanism: when a write's quorum can't reach the down replica, another currently-reachable replica temporarily accepts and stores that write on the down replica's behalf, holding it as a "hint" to forward once the original replica comes back online. This lets the cluster keep satisfying the write quorum (W out of N) without waiting for the down node, preserving write availability through the entire maintenance window — once the replica returns, the hinted writes are forwarded to it so it catches up on exactly what it missed, without needing a full anti-entropy repair for that window.

MIDQ22. Why is statement-based replication (replaying SQL statements on each replica) considered less reliable than log-shipping (WAL/binlog) replication?

ROI: ★★★★☆ · Frequency: Medium

Some SQL statements are non-deterministic — functions like NOW(), or operations whose result depends on execution order under concurrency (like certain auto-increment behaviors) — and can produce different results if re-executed independently on each replica. Log-shipping replication instead streams and replays the exact, already-applied low-level changes from the leader's write-ahead log, guaranteeing every replica reaches the identical resulting state rather than independently re-deriving it.

MIDQ23. How would you decide between schema-per-tenant and database-per-tenant when implementing Hibernate multi-tenancy?

ROI: ★★★★☆ · Frequency: Medium-High

Schema-per-tenant shares one physical database across tenants (cheaper to operate, faster to provision a new tenant, but tenants share hardware resources and a bug or heavy load from one tenant can affect others). Database-per-tenant gives each tenant a fully separate physical database (maximum isolation — a noisy or misbehaving tenant can't degrade another's performance, and per-tenant backup/restore or data-residency placement is simpler), at the cost of higher operational overhead per tenant and the same resharding-adjacent complexity as moving shards when rebalancing tenants across hardware.

MIDQ24. Why should @Transactional(readOnly = true) not be trusted blindly to route every read to a replica?

ROI: ★★★★★ · Frequency: High

A method marked read-only is a perfectly safe candidate for replica routing in isolation, but if that read happens immediately after a write in the same logical user flow (e.g., saving a profile update, then reloading the profile to show a confirmation), routing it to a possibly-lagging replica risks violating read-your-writes consistency (Section 4.3) even though nothing about the annotation itself is incorrect — the fix is identifying those specific read-after-write call sites and routing them to the leader or a known-caught-up replica instead.

MIDQ25. What's the purpose of the verification/reconciliation phase in a resharding migration, and what would you compare between the old and new shard?

ROI: ★★★★☆ · Frequency: Medium-High

Verification confirms the new shard's copy of the migrated range actually matches the old shard's before anything is allowed to depend on the new shard as authoritative, catching bugs in the dual-write or backfill logic before they cause real data loss. Common comparisons include row counts per sub-range, checksums over sub-ranges of data, and spot-checking individual records, often done incrementally rather than as one giant comparison to keep the check itself from overwhelming either shard.

MIDQ26. Why does Vitess or Citus let application code keep using ordinary SQL even though the underlying data is sharded?

ROI: ★★★★☆ · Frequency: Medium-High

Both act as a proxy/coordinator layer sitting between the application and the physical shards: the application connects to what looks like one logical MySQL or PostgreSQL database, and the proxy internally determines which shard(s) a given query needs to hit, routes single-shard queries directly, and fans out and merges results for queries that must touch multiple shards — the sharding mechanics from Sections 4 and 5 are implemented once, in the proxy, instead of being re-implemented in every application service that touches the data.

MIDQ27. A shard's storage is approaching its planned capacity ceiling. Why shouldn't resharding wait until the ceiling is actually reached?

ROI: ★★★★☆ · Frequency: Medium-High

Resharding (Section 5.4) is a multi-phase process — dual-write, backfill, verify, cutover — that takes real engineering time to plan and execute safely, and rushing it under the pressure of an already-full shard increases the risk of skipping safety steps like verification. Capacity planning (Section 6.3) should treat the ceiling as a trigger to start the resharding project with headroom to spare, not as the deadline by which it must already be finished.

MIDQ28. What specifically makes vector clocks useful for conflict detection in a multi-leader or leaderless replication setup?

ROI: ★★★★☆ · Frequency: Medium

A vector clock tracks, per replica, which version of a record each node has seen and produced, letting the system distinguish writes that causally depend on one another (and therefore have a clear "later" write that should win) from writes that are genuinely concurrent, with neither depending on the other — a true conflict with no natural resolution by ordering alone. Without this distinction, a system is forced to either over-apply a crude tiebreaker like last-writer-wins to every disagreement (silently discarding legitimate concurrent writes) or treat every disagreement as equally ambiguous even when some actually have a clear causal resolution.

SENIORQ29. You're designing the data tier for a multi-tenant SaaS product where a handful of enterprise customers generate 100x the data and traffic of a typical customer. How would you shard this data?

ROI: ★★★★★ · Frequency: High at senior level

A pure hash-based sharding scheme keyed on tenant ID would distribute small tenants evenly, but a single large enterprise tenant's traffic would still be entirely concentrated on whichever one shard its hash lands on — the hash function distributes tenants, not the traffic each tenant generates, so uneven tenant sizes directly produce the hot-shard problem (Section 4.5) regardless of how uniform the hash looks on paper. The better design uses a directory-based approach (Section 4.4) specifically for the large-tenant tail: most small-to-medium tenants are hash-sharded normally across a shared pool of shards, while any tenant that exceeds a defined size/traffic threshold is explicitly assigned its own dedicated shard (or shard group) via the directory, isolating its load from affecting smaller tenants and allowing it to be scaled or resharded independently as it continues to grow.

Interview Gold Point: Name the detection mechanism, not just the fix — propose monitoring per-tenant load (not just per-shard load) so a tenant crossing the "needs its own shard" threshold is caught by an automated alert and migrated proactively via Section 5.4's dual-write sequence, rather than discovered reactively after it has already degraded other tenants sharing its shard.
SENIORQ30. A junior engineer proposes using the customer's email address directly as the sharding key for a hash-based scheme, since it's unique and available everywhere. What would you push back on?

ROI: ★★★★☆ · Frequency: Medium-High at senior level

The immediate technical concern is mutability: a customer's email address can change, and a sharding key that can change after a record is created means that record would need to move shards whenever that key changes — not a problem a stable surrogate ID (like an internal customer ID, generated once and immutable) ever has. The second concern is that email addresses, as personally identifiable information, embedding them directly into infrastructure-level routing logic (the hash of the key is effectively derived from the email, and may appear in logs, shard-map entries, or routing metadata) raises a data-handling concern that an opaque internal ID avoids entirely. The right fix is to shard on a stable, internally-generated, non-PII identifier, and look up that identifier from the email only at the application layer when needed.

SENIORQ31. How would you design monitoring and alerting specifically for replication lag across a fleet of read replicas serving a high-traffic read path?

ROI: ★★★★★ · Frequency: High at senior level

Track per-replica lag continuously using Section 6.1's log-position-gap metric, converted to an estimated time delay, and alert on at least two distinct thresholds: a lower "degraded" threshold (e.g., lag exceeding a couple seconds) that should trigger investigation but not necessarily remove the replica from rotation, and a higher "unsafe" threshold tied to the specific read-your-writes and staleness tolerances the application actually needs, at which point the routing layer should automatically stop sending traffic to that replica until it catches back up. Equally important is alerting on the *rate of change* of lag, not just its absolute value — a replica whose lag is steadily climbing under sustained load is a capacity problem worth catching well before it crosses the hard threshold, versus a replica with a brief, self-correcting lag spike from a momentary load burst.

SENIORQ32. Compare the operational cost of recovering from a failed leader in a single-leader system versus recovering from a lost replica in a leaderless quorum system.

ROI: ★★★★☆ · Frequency: Medium-High at senior level

A failed leader in a single-leader system requires an active failover process — electing or manually promoting a new leader, redirecting all write traffic to it, and reconciling any writes that were in flight at the moment of failure — a discrete, visible event with a real (if ideally brief) write-unavailability window, as Section 4.1 describes. A lost replica in a leaderless quorum system typically requires no equivalent active process at all: as long as enough of the remaining N-1 replicas still satisfy W and R, reads and writes continue uninterrupted, with hinted handoff (Section 5.3) quietly covering for the missing node until it returns or is permanently replaced — the operational cost here is lower-urgency and more gradual (eventually re-replicating data to restore full redundancy) rather than an acute failover event.

SENIORQ33. Your team wants to shard an existing, already-live, single-database application for the first time. What's your overall approach, and what order would you do things in?

ROI: ★★★★★ · Frequency: High at senior level

Start by choosing the sharding key based on the dominant access pattern and expected growth skew (Section 4.4 and Q29's reasoning), and validate that choice against real production query logs before committing, since this decision is expensive to reverse later. Next, introduce the routing/proxy layer (Section 8) in front of the still-single, unsharded database first, so all application code is already going through the abstraction that will later route to multiple shards — this decouples "teach the application to be shard-aware" from "actually split the data," letting the first, riskier code change be validated against the exact same single database before any data movement happens. Only once the routing layer has been running safely against the single database for a representative period should the actual first split be performed, using the dual-write/backfill/verify/cutover sequence (Section 5.4) to move an initial subset of data onto a second shard — deliberately starting with a smaller, lower-risk slice of data rather than the full migration, to validate the whole mechanism under real production conditions before relying on it for the bulk of the migration.

Interview Gold Point: Explicitly separate "introduce the abstraction" from "move the data" as two distinct, independently-validatable steps — this sequencing is the single biggest risk-reduction move in a first-time sharding migration, and naming it unprompted signals real migration experience rather than textbook knowledge.
SENIORQ34. How would you evaluate whether a workload actually needs multi-leader replication, versus single-leader replication with good read-scaling and a solid failover story?

ROI: ★★★★☆ · Frequency: Medium-High at senior level

Multi-leader replication's entire justification is accepting local writes in multiple regions without blocking on cross-region coordination — so the question to ask is whether the workload genuinely needs low-latency writes from multiple geographically distant locations simultaneously, and whether its data model can tolerate the conflict-resolution burden (Section 5.2) that comes with it. Many workloads that seem to want multi-leader actually only need single-leader replication with regional read replicas and a solid automated-failover story (fast leader re-election, synchronous replication to at least one standby) — this avoids conflict-resolution complexity entirely and is usually the better default unless write latency from multiple active regions is a hard, validated requirement, not an assumed one.

SENIORQ35. Design the replication and sharding strategy for an inventory system where overselling the last unit of a product is unacceptable, referencing Chapter 02's CAP framing.

ROI: ★★★★★ · Frequency: High at senior level

Per Chapter 02's per-service CAP analysis, inventory count is a CP-leaning concern — a stale read that allows overselling is a direct, visible correctness and business failure, so this data should use single-leader replication with synchronous (or at least semi-synchronous) acknowledgment to prevent accepting a decrement that could be lost on leader failure, and should route the final decrement operation through the leader rather than any replica, even at the latency cost. For sharding, the natural key is the product (or SKU) ID, which also conveniently means the one invariant that matters most — "don't oversell this specific SKU" — only ever needs coordination within a single shard, never across shards, as long as the sharding key correctly isolates each product's inventory count to one shard rather than splitting a single product's stock count across multiple shards.

Interview Gold Point: Call out explicitly that choosing the sharding key so the business invariant that matters most never needs a cross-shard transaction is a design principle in its own right — cross-shard transactions are expensive and often only partially supported by sharded systems, so a sharding key that keeps your hardest consistency requirement single-shard is doing real architectural work, not just distributing load.
SENIORQ36. A production incident report says "replication lag spiked to 10 minutes during a bulk data import job, causing widespread stale reads." How would you prevent this specific recurrence?

ROI: ★★★★☆ · Frequency: Medium-High at senior level

A bulk import generates a large burst of writes on the leader, which must all be shipped and replayed on every follower — if the import's write rate exceeds what followers can replay in real time, lag grows throughout the import and only drains afterward, exactly matching the incident description. The fix is rate-limiting or batching the bulk import's write rate to stay within followers' sustained replay capacity (treating replication lag as a backpressure signal the import job actively monitors and throttles against, not an ambient property it ignores), combined with routing reads for the data being bulk-imported specifically to the leader during the import window if read-your-writes matters for that data, rather than relying on replicas that are known to be falling behind during exactly this operation.

SENIORQ37. Why is "we sharded the database" not sufficient justification, on its own, for why a system can scale writes indefinitely?

ROI: ★★★★☆ · Frequency: Medium at senior level

Sharding only removes the ceiling imposed by a single machine's write capacity — it does not remove every other ceiling in the system. A hot shard (Section 4.5) can still bottleneck write throughput for a specific key or tenant regardless of total shard count; the routing/proxy layer itself (Section 8) can become a bottleneck under enough aggregate traffic; and cross-shard coordination, if the application's invariants require it, can scale far worse than per-shard writes do. "Sharded" answers "can we add more machines to hold more data and absorb more aggregate writes," not "have we eliminated every possible bottleneck," and an interviewer probing this question is checking whether the candidate conflates the two.

SENIORQ38. How would you design a system to support moving a single large, hot tenant to its own dedicated shard without any downtime for that tenant?

ROI: ★★★★★ · Frequency: Medium-High at senior level

This is Section 5.4's resharding sequence applied to a directory-based routing scenario rather than a pure hash range: begin dual-writing that tenant's new and updated records to both the shared shard and the new dedicated shard, backfill the tenant's existing historical data from the shared shard to the dedicated one in rate-limited batches so as not to further overload the already-hot shared shard, verify the dedicated shard's data matches before relying on it, then update the directory entry for that tenant's ID to point reads (and shortly after, writes) at the new dedicated shard. The one addition specific to a hot tenant is prioritizing the backfill's rate limit against the shared shard's current load headroom rather than a fixed schedule, since the whole point of the migration is relieving that shard, not adding to its load during the move.

SENIORQ39. What's the argument for keeping a sharding key separate from a database's primary key, even when they could technically be the same value?

ROI: ★★★★☆ · Frequency: Medium at senior level

A primary key's job is uniquely identifying a row within its table; a sharding key's job is determining which physical shard a row lives on, and these two concerns can have different ideal properties — a primary key often benefits from being sequential for index locality and simplicity, while Section 4.4 showed sequential keys are specifically bad for even shard distribution. Keeping them conceptually separate (even if, in a simple system, they happen to share a value) lets you change the sharding strategy or key derivation later (e.g., switching from a raw ID to a hash of a composite key) without needing to also change the primary key and every foreign-key relationship depending on it.

SENIORQ40. How would you communicate the operational risk of a multi-leader replication design to a stakeholder who only hears "it lets us write from every region, so let's always use it"?

ROI: ★★★★☆ · Frequency: Medium at senior level

Reframe the benefit against its concrete cost in terms the stakeholder can weigh: "yes, every region can accept writes locally with low latency, but that also means two users in different regions can edit the same record at nearly the same time, and the system will have to automatically guess which edit should win, or merge them — for some data, like a document's last-saved text, that's a real, visible, occasionally-wrong outcome a user might notice, not a purely internal technical detail." This grounds the trade-off in a specific, imaginable user-facing scenario (an edit silently overwritten or merged) rather than the word "conflict," letting the stakeholder make an informed call about whether that specific data genuinely needs multi-region write availability badly enough to accept that occasional downside.

STAFFQ41. Your organization runs a dozen services, each independently deciding its own sharding key and strategy with no coordination. As a staff engineer, what risk does this create, and how would you address it?

ROI: ★★★★★ · Frequency: High at staff level

The immediate risk is that any feature requiring data from multiple of these services for the same logical entity (a customer, an order) now has to reconcile a dozen different, uncoordinated sharding schemes — a report or workflow that needs to efficiently fetch "everything related to customer X" across services may find that X's data is scattered unpredictably differently in each service's shard layout, forcing expensive cross-shard, cross-service fan-out everywhere such a query is needed. The staff-level fix is not mandating one single sharding key for every service (different services legitimately have different dominant access patterns), but establishing a shared convention for the handful of entities that span many services — most commonly, standardizing on customer/tenant ID as a first-class sharding dimension wherever a service's data is naturally scoped to a customer, specifically so that cross-service, per-customer operations stay efficient, while leaving services free to choose a different key for data that is genuinely not customer-scoped.

Interview Gold Point: Frame this as an architectural governance problem, not a technical one — propose a lightweight review step (not a heavyweight approval process) specifically for new services' sharding-key choices when they touch a small number of designated "span many services" entities, so the coordination cost is paid only where it actually matters, not on every new service regardless of relevance.
STAFFQ42. A postmortem reveals that a resharding migration silently dropped a small percentage of writes during the dual-write phase for several weeks before being caught. How do you evaluate what went wrong at a process level, not just a code level?

ROI: ★★★★★ · Frequency: High at staff level

The code-level bug (whatever specifically caused some dual-writes to fail silently) is almost always the less interesting half of this postmortem; the more important question is why the verification/reconciliation step (Section 5.4) that exists specifically to catch exactly this class of problem either wasn't run, wasn't run continuously throughout the weeks-long dual-write window, or wasn't alerting loudly enough to be noticed. A resharding migration that runs for weeks needs continuous, not one-time, reconciliation checks — the risk of silent drift is proportional to how long dual-write runs before cutover, so a long-running migration needs correspondingly more frequent, automated verification with alerting, not a single manual check performed once near the end. The process-level fix is treating "how will we continuously verify correctness throughout this migration, and who gets paged if it drifts" as a required, reviewed part of any resharding plan before it starts, not an afterthought added only after an incident reveals its absence.

STAFFQ43. How would you decide, as a staff-level technical decision, whether to adopt a managed sharding proxy like Vitess or Citus versus building a custom routing/sharding layer in-house?

ROI: ★★★★☆ · Frequency: Medium-High at staff level

Frame the decision around which parts of Sections 4, 5, and 8's mechanics your team would otherwise have to build, operate, and keep correct indefinitely: a managed proxy has already solved query routing, cross-shard fan-out, and much of the resharding sequence, and adopting it trades a dependency and some SQL feature restrictions for not having to build and maintain that machinery — a strong default for most teams, since correctly implementing online resharding (Section 5.4) in-house is a substantial, easy-to-get-subtly-wrong undertaking. The case for building in-house is narrower: genuinely unusual sharding requirements the proxy doesn't support well, an access pattern so specific that a custom router can meaningfully outperform a general-purpose one, or an organization already operating at a scale where the proxy itself becomes the bottleneck described in Section 12. A staff engineer's job here is making sure "we want full control" isn't quietly substituting for "we haven't actually hit a limitation the managed option can't handle" before committing to the significantly larger ongoing maintenance burden of the custom path.

STAFFQ44. Your company is considering moving a mature, single-leader-replicated, unsharded financial ledger system to a sharded, multi-region, multi-leader architecture for latency reasons. What's your position?

ROI: ★★★★★ · Frequency: High at staff level

Push back on evaluating this purely as a latency win without weighing it against what a financial ledger specifically cannot tolerate: multi-leader replication's conflict-resolution burden (Section 5.2) is fundamentally at odds with a ledger's need for a single, unambiguous, auditable order of transactions — a scenario where two leaders accept conflicting balance-affecting writes concurrently and must later reconcile them is close to the worst possible failure mode for financial correctness, regardless of how rare the conflict rate might be in practice. The staff-level recommendation is usually to solve the latency problem a different way for this specific data: keep the ledger single-leader (CP-leaning, per Chapter 02) for its actual write path, but address regional read latency with regional read replicas serving read-only balance/history queries, and address regional write latency, if it's truly a hard requirement, by sharding the ledger by a key that keeps each shard's writes local to one region's leader (e.g., sharding by account's home region) rather than by introducing multi-leader conflict risk into the same shard — getting most of the latency benefit without taking on conflict-resolution risk for the one dataset where that risk is least acceptable.

Interview Gold Point: Distinguish the two different "multi-region" solutions explicitly — region-affinity sharding (each shard still single-leader, but different shards' leaders live in different regions, so each region's local writes are genuinely local with no conflict risk) versus true multi-leader replication (the same shard accepting writes from multiple leaders) — conflating these two is a common staff-level interview trap, and naming the distinction unprompted is a strong signal.
STAFFQ45. How would you build organizational confidence to approve a resharding migration on your company's most critical, highest-traffic dataset, where any mistake is highly visible?

ROI: ★★★★☆ · Frequency: Medium-High at staff level

Build confidence incrementally and demonstrably rather than asking for trust up front: first, execute and document the full dual-write/backfill/verify/cutover sequence (Section 5.4) successfully on a lower-risk, lower-traffic dataset, treating it explicitly as a dry run whose outcome (including any problems found and fixed) becomes the evidence base for the harder migration. Second, for the critical migration itself, propose cutting over in small, reversible increments (a narrow key range or a single low-risk shard first) rather than the whole dataset at once, with an explicit, tested rollback path at every increment, so that even a worst-case mistake has a small, contained blast radius and a known recovery procedure rather than being an all-or-nothing bet on a dataset the whole business depends on. The organizational ask becomes "approve the next small, reversible increment, with contained risk and a track record of previous increments succeeding," which is a fundamentally easier and more honest approval to grant than "trust us with the whole migration at once."

16. SUMMARY

  • Replication (keeping multiple copies of the same data) and sharding (splitting different data across machines) solve genuinely different scaling ceilings — read capacity and availability versus write capacity and storage — and a real production system composes both, with each shard independently replicated.
  • The three replication topologies — single-leader, multi-leader, leaderless/quorum — map directly onto Chapter 02's CP/AP framing, and each carries a distinct, nameable failure mode: failover unavailability, write conflicts, or reconciliation complexity, respectively.
  • Synchronous versus asynchronous replication is a direct durability-versus-latency trade-off, and replication lag — the unavoidable gap even in a correctly-functioning asynchronous setup — causes read-your-writes violations that require deliberate routing mitigations, not an assumption that "eventual" is always fast enough.
  • Range-based, hash-based, and directory-based sharding each optimize for a different access pattern (range queries, even distribution, or flexible custom placement respectively) and each carries a specific, well-known failure mode — sequential-key hot shards, scatter-gather range queries, or a critical-path lookup dependency.
  • Resharding a live system safely follows a consistent dual-write, backfill, verify, cutover sequence regardless of underlying technology, and hot shards/hot keys are a distinct problem from insufficient shard count, requiring targeted mitigations like key salting or surgical splitting rather than wholesale resharding.
  • As a Java/Spring engineer, these mechanics surface directly in routing-DataSource read/write split configuration, Hibernate multi-tenancy design, and the decision of whether to adopt a proven sharding proxy like Vitess or Citus rather than building the routing and resharding machinery in-house.
