SECTION 1 - TESTING PHILOSOPHY

Q1. What is the testing pyramid, how does the "testing trophy" differ, and what should you actually test in a frontend?

ROI: ★★★★★ Frequency: Extremely High

Short Answer

The classic testing pyramid says: lots of fast unit tests at the bottom, fewer integration tests in the middle, very few slow E2E tests at the top. Kent C. Dodds' testing trophy reshapes this for modern frontend: a base of static analysis (TypeScript + ESLint), a small layer of unit tests, and the largest layer being integration tests — because they give the best confidence-per-effort — topped by a thin slice of E2E. The practical rule: "write tests that resemble how your software is used," so favor integration-style component tests over testing tiny implementation units in isolation.

Detailed Answer

The pyramid optimizes for speed and cost: unit tests are cheap and fast, E2E tests are expensive and brittle, so you write many of the former and few of the latter. It is still a useful mental model, but taken literally it pushes people to unit-test every function and mock everything around a component — which produces tests that pass while the app is broken.

The trophy reframes the goal as confidence, not test count. Its four tiers, bottom to top:

  • Static — TypeScript and ESLint catch a whole class of bugs (typos, wrong types, undefined access) before a test even runs. Nearly free.
  • Unit — pure functions, reducers, utilities, complex custom hooks. Fast and precise, but low on integration confidence.
  • Integration — render a component (or a small tree) and test it the way a user would, mocking only the true boundaries (usually the network). This is where the trophy says to spend most effort.
  • E2E — a real browser driving the real app (Cypress/Playwright). Highest confidence, slowest, most flaky; keep to critical happy paths.

What to actually test in a frontend: user-visible behavior — "when I type an email and click submit, I see a success message"; conditional rendering; form validation; error and loading states; and the wiring between components and data. What to avoid testing: internal state variable names, whether a specific hook was called, CSS classes, and third-party library internals.

Project Example

On a checkout flow we deleted a swathe of shallow unit tests that asserted "setState was called with X" and replaced them with a handful of integration tests: render the cart, mock the /api/checkout endpoint with MSW, click "Pay", and assert the confirmation screen appears. The suite got smaller, faster to reason about, and — critically — it started catching real regressions (a broken prop wiring) that the old mocked unit tests had happily ignored.

Senior Engineer Perspective

Interviewers use this to see whether you test for confidence or for a coverage number. A junior answer recites "many unit, few E2E." A senior answer names the trophy, explains why integration tests dominate in frontend (components are mostly glue, and users don't call your functions — they click buttons), and cites the guiding principle: "the more your tests resemble the way your software is used, the more confidence they give you." Bonus: mention that static analysis is the cheapest tier and often skipped in this conversation.

Q2. What is React Testing Library's core philosophy — "test behavior, not implementation"?

ROI: ★★★★★ Frequency: Extremely High

Short Answer

RTL's guiding principle is that tests should interact with a component the way a user does — find elements by their visible text and accessible roles, click and type on them, and assert on what appears — rather than reaching into internals like state, props, or instance methods. Tests coupled to behavior survive refactors; tests coupled to implementation break the moment you rename a state variable or restructure the component, even though nothing user-facing changed.

Detailed Answer

This is a deliberate reaction against Enzyme, the previous dominant tool, which exposed wrapper.state(), wrapper.instance(), and shallow() rendering. Those APIs let you assert on implementation details, so tests were tightly coupled to how a component worked. Refactoring class components to hooks, or splitting one component into two, would break hundreds of tests without any behavioral change — the definition of brittle.

RTL removes those escape hatches on purpose. It gives you a rendered DOM and query functions that mirror how users and assistive technology perceive the page. There is no .state(), no way to read a hook's value directly, no shallow rendering. If you cannot express your test in terms of what the user sees and does, that is usually a signal to test behavior at a different level.

Two clarifications interviewers like:

  • "Behavior" means observable output: rendered text, roles, values, what happens on interaction — not "did this function get called." (Callback props are a legitimate exception: verifying onSubmit fired with the right data is testing a contract, not an internal.)
  • This does not mean "never mock." You still mock the network boundary. The principle is about not asserting on a component's private wiring.

Code Example

// Implementation-focused (brittle) — Enzyme style
// expect(wrapper.state("count")).toBe(1);   // breaks if you rename state

// Behavior-focused (resilient) — RTL style
import { render, screen } from "@testing-library/react";
import userEvent from "@testing-library/user-event";

test("increments the visible count", async () => {
  render(<Counter />);
  // Find by what the user sees, act like a user, assert on output.
  await userEvent.click(screen.getByRole("button", { name: /increment/i }));
  expect(screen.getByText("Count: 1")).toBeInTheDocument();
});

Senior Engineer Perspective

The phrase to land is "the test should not know how the component is built." Explain the payoff concretely: you can convert a class to a hook, memoize a child, or split a component, and a good RTL test stays green. Common trap: candidates who reach for container.querySelector('.my-class') everywhere — that reintroduces implementation coupling through CSS selectors. Mention that querying by role/label also nudges you toward accessible markup as a side benefit, and that testing a callback prop fired correctly is fine because it is part of the component's public contract.

SECTION 2 - UNIT TESTING WITH JEST

Q3. What are the Jest basics — describe/it/expect, matchers, and setup/teardown?

ROI: ★★★★☆ Frequency: High

Short Answer

describe groups related tests; it (alias test) defines a single test; expect(value) returns an assertion object you chain a matcher onto (toBe, toEqual, toContain, etc.). The lifecycle hooks — beforeEach, afterEach, beforeAll, afterAll — run setup and teardown so each test starts from a clean, predictable state.

Detailed Answer

A few matcher distinctions interviewers probe:

  • toBe vs toEqual — toBe uses Object.is (reference/primitive equality); toEqual does a deep recursive comparison. Use toBe for primitives and toEqual for objects/arrays. toStrictEqual is stricter still (checks undefined keys and types).
  • Async assertions — either await a promise then assert, or use await expect(promise).resolves.toBe(...) / .rejects.toThrow(...).
  • Negation — expect(x).not.toBe(y).
  • jest-dom matchers — @testing-library/jest-dom adds DOM-aware matchers like toBeInTheDocument(), toHaveTextContent(), toBeDisabled(), which read far better than manual node checks.

Setup/teardown scope matters: beforeEach/afterEach run around every test (good for resetting mocks and clearing state); beforeAll/afterAll run once for the whole describe block (good for expensive one-time setup like starting a mock server). Prefer beforeEach for isolation — shared mutable state that leaks between tests is the number-one cause of "passes alone, fails in the suite" flakiness.

Code Example

describe("cart totals", () => {
  let cart;

  beforeEach(() => {
    cart = createCart();            // fresh state per test
  });

  it("starts empty", () => {
    expect(cart.items).toEqual([]); // deep equality for arrays/objects
    expect(cart.total).toBe(0);     // primitive: reference equality
  });

  it("adds an item and sums the price", () => {
    cart.add({ id: 1, price: 9.99 });
    expect(cart.items).toContain(expect.objectContaining({ id: 1 }));
    expect(cart.total).toBeCloseTo(9.99); // avoid float === traps
  });

  it("rejects a negative quantity", () => {
    expect(() => cart.add({ id: 2, qty: -1 })).toThrow(/quantity/i);
  });
});

Senior Engineer Perspective

The classic gotcha is toBe vs toEqual on objects — using toBe on two equal-looking objects fails because they're different references. Also mention toBeCloseTo for floats (never toBe on 0.1 + 0.2). On lifecycle, a strong answer stresses test isolation: reset mocks in beforeEach (or set clearMocks: true in config) so one test's mock state can't bleed into the next. Knowing that test and it are aliases, and that test.each exists for table-driven tests, signals real familiarity.

Q4. How do you mock with jest.fn, jest.mock, and mock a module?

ROI: ★★★★★ Frequency: Extremely High

Short Answer

jest.fn() creates a standalone mock function you can configure (mockReturnValue, mockResolvedValue) and assert on (toHaveBeenCalledWith). jest.mock('module') replaces an entire imported module with an auto-mock (or a factory you supply), so the code under test uses your fake instead of the real dependency. jest.spyOn(obj, 'method') wraps a real method so you can observe or override it while optionally keeping the original behavior.

Detailed Answer

Three tools for three jobs:

  • jest.fn() — a fake function. Pass it as a callback/prop and assert it was called: expect(onSave).toHaveBeenCalledWith({ id: 1 }). Configure its return with mockReturnValue / mockResolvedValue / mockImplementation.
  • jest.mock(path) — replaces a module. Jest hoists this call to the top of the file, above imports, which is why the factory can't reference outer variables that aren't prefixed with mock. Use it to stub an API client, an analytics SDK, or next/navigation.
  • jest.spyOn — best when you want to watch a real method and restore it later. Combine with mockRestore() in teardown.

Hygiene is the real topic. Mocks accumulate call history across tests. Use mockClear() (clears calls), mockReset() (clears calls + implementation), or mockRestore() (restores original, spies only). Setting clearMocks: true in the Jest config auto-clears between tests. Over-mocking is the deeper danger: if you mock everything, your test verifies your mocks, not your app.

Code Example

// 1) A plain mock function passed as a prop/callback
const onSubmit = jest.fn();
render(<Form onSubmit={onSubmit} />);
// ...interact...
expect(onSubmit).toHaveBeenCalledTimes(1);
expect(onSubmit).toHaveBeenCalledWith({ email: "a@b.com" });

// 2) Mock a whole module (factory is hoisted above imports)
jest.mock("../api/userClient", () => ({
  getUser: jest.fn().mockResolvedValue({ id: 1, name: "Ada" }),
}));
import { getUser } from "../api/userClient";

test("loads the user", async () => {
  const user = await getUser("1");
  expect(user.name).toBe("Ada");
  expect(getUser).toHaveBeenCalledWith("1");
});

// 3) Spy on a real method, then restore it
const spy = jest.spyOn(console, "error").mockImplementation(() => {});
// ...assert something logged an error...
spy.mockRestore();

Senior Engineer Perspective

Two facts separate strong candidates. First, the hoisting rule: jest.mock is moved above imports, so a factory referencing an out-of-scope variable throws unless the variable name starts with mock. Second, mock cleanup: know the difference between mockClear, mockReset, and mockRestore, and that leaking mock state causes order-dependent test failures. The senior meta-point: prefer mocking at the network boundary (MSW) over mocking your own modules, so you mock less and test more of the real integration.

Q5. How do you mock timers, dates, and fetch?

ROI: ★★★★☆ Frequency: High

Short Answer

For timers, call jest.useFakeTimers() and drive the clock forward with jest.advanceTimersByTime(ms) or jest.runAllTimers(), so debounce/throttle/setTimeout logic runs instantly and deterministically. For dates, fake timers can also freeze "now" (jest.setSystemTime(...)). For fetch, you can stub global.fetch = jest.fn() — but the better modern approach is to intercept at the network layer with MSW (see Q13).

Detailed Answer

Fake timers replace setTimeout, setInterval, and (in modern mode) Date. This is how you test a debounced search without waiting a real 400ms. Remember two things: always restore with jest.useRealTimers() in teardown, and when combining fake timers with user-event, pass userEvent.setup({ advanceTimers: jest.advanceTimersByTime }) so events and the fake clock stay in sync.

Freezing dates makes "expires tomorrow" or "created just now" tests deterministic. With modern fake timers: jest.useFakeTimers().setSystemTime(new Date("2026-07-11")). This prevents flaky tests that pass in the morning and fail at midnight.

Mocking fetch directly works but is fragile: you rebuild request/response shapes by hand, and every test re-stubs fetch.mockResolvedValueOnce(...). It couples the test to the fact that you use fetch (not axios), and it's easy to forget to assert the URL/method. MSW solves all of this by intercepting the actual network request, so your app code runs unchanged.

Code Example

// Fake timers for a debounced callback
test("debounce fires once after the delay", () => {
  jest.useFakeTimers();
  const fn = jest.fn();
  const debounced = debounce(fn, 300);

  debounced();
  debounced();
  jest.advanceTimersByTime(299);
  expect(fn).not.toHaveBeenCalled(); // still within the window
  jest.advanceTimersByTime(1);
  expect(fn).toHaveBeenCalledTimes(1);

  jest.useRealTimers();              // always restore
});

// Freeze "now" for deterministic date logic
jest.useFakeTimers().setSystemTime(new Date("2026-07-11T00:00:00Z"));
expect(isExpired("2026-07-10")).toBe(true);

// Quick-and-dirty fetch stub (prefer MSW instead)
global.fetch = jest.fn().mockResolvedValue({
  ok: true,
  json: async () => ({ id: 1, name: "Ada" }),
});

Senior Engineer Perspective

The trap with fake timers is deadlock: if you await something that only resolves after a timer, but never advance the clock, the test hangs. Mention the user-event + fake-timers coordination (advanceTimers option) because it bites people constantly. On dates, freezing the system time is the professional move over monkey-patching Date.now. And be ready to say why you'd reach for MSW over a hand-rolled fetch mock — the follow-up almost always goes there.

SECTION 3 - COMPONENT TESTING (RTL)

Q6. What is the difference between getBy, queryBy, and findBy queries?

ROI: ★★★★★ Frequency: Extremely High

Short Answer

They differ on two axes: throwing behavior and async. getBy* returns the element or throws if it's missing (use when it should exist). queryBy* returns the element or null without throwing (the only correct way to assert something is absent). findBy* returns a Promise that retries until the element appears or times out (use for async/appearing elements). Each has an *AllBy variant for matching multiple elements.

Detailed Answer

QueryNo matchMatchAsync / retriesUse for
getByThrowsElementNoAssert element exists now
queryByReturns nullElementNoAssert element is absent
findByRejects (after timeout)Promise<Element>Yes (waitFor built in)Element appears after async work
getAllByThrowsElement[]NoMultiple elements exist
queryAllByReturns []Element[]NoZero-or-more, no throw
findAllByRejectsPromise<Element[]>YesMultiple appear async

The single most common mistake is using getBy to check that something is gone — getBy throws when there's no match, so the test errors instead of asserting cleanly. To assert absence you must use queryBy with .not.toBeInTheDocument(). Conversely, using queryBy where you expect an element is worse for debugging: you get a null-dereference error instead of RTL's helpful "unable to find an element" message with a DOM dump.

findBy is essentially getBy wrapped in waitFor, defaulting to a 1000ms timeout and polling as the DOM changes. It's the idiomatic way to wait for data to load.

Code Example

import { render, screen } from "@testing-library/react";

test("query selection", async () => {
  render(<Profile userId="1" />);

  // Present immediately -> getBy (throws if missing = clear failure)
  expect(screen.getByRole("heading", { name: /profile/i })).toBeVisible();

  // Absent -> queryBy (returns null, does NOT throw)
  expect(screen.queryByText(/error/i)).not.toBeInTheDocument();

  // Appears after async fetch -> findBy (awaits, retries)
  expect(await screen.findByText("Ada Lovelace")).toBeInTheDocument();
});

Senior Engineer Perspective

The decision tree an interviewer wants to hear: "Is it there now? getBy. Am I checking it's NOT there? queryBy. Will it appear after async work? findBy." The disqualifying answer is wrapping getBy in a try/catch to test absence. Bonus depth: findBy accepts a waitFor options object for custom timeout, and you should never mix getBy inside a manual waitFor when findBy already does that job more readably.

Q7. Why is getByRole preferred, and what is Testing Library's recommended query priority?

ROI: ★★★★★ Frequency: Extremely High

Short Answer

getByRole is preferred because it queries the DOM the way assistive technology does — by accessibility role and accessible name — so a passing test is also evidence that the element is reachable by screen-reader users. Testing Library publishes a priority order: prefer queries everyone can use (role, label, placeholder, text), then semantic queries, and only fall back to getByTestId when nothing else works. The rule of thumb: query the way a user (sighted or not) finds the element, not by DOM structure or CSS.

Detailed Answer

The recommended priority, highest to lowest:

  1. Accessible to everyone
    • getByRole — the top choice; e.g. getByRole('button', { name: /submit/i }). Combines role + accessible name.
    • getByLabelText — the best choice for form fields (matches a real <label>).
    • getByPlaceholderText — a fallback when there's no label.
    • getByText — for non-interactive content (paragraphs, divs, spans).
    • getByDisplayValue — for the current value of a filled-in input.
  2. Semantic (HTML5/ARIA attributes) — getByAltText (images), getByTitle.
  3. Test IDs — getByTestId, an escape hatch for elements with no accessible role or stable text (e.g. a purely visual wrapper).

Why role wins: it forces accessible markup (a real <button>, an <h1>, a labeled input) and it's resilient — text can change with copy edits, but the role of "the submit button" is stable. Roles come from semantic HTML for free (<button> = button, <a href> = link, <input type="checkbox"> = checkbox) or from explicit ARIA. The { name } option matches the accessible name, computed from label, aria-label, or text content.

getByTestId should be rare. It couples the test to a data-testid attribute that has no user meaning — fine as a last resort, but if you find yourself reaching for it constantly, your markup probably lacks semantics.

Code Example

// Preferred: role + accessible name
screen.getByRole("button", { name: /save changes/i });
screen.getByRole("textbox", { name: /email/i });   // input with a label
screen.getByRole("heading", { level: 1, name: /dashboard/i });

// Great for forms: match the visible label
screen.getByLabelText(/password/i);

// Non-interactive content
screen.getByText(/welcome back/i);

// Last resort only — no role or stable text available
screen.getByTestId("chart-canvas");

// Helpful during authoring: prints all available roles for the DOM
// screen.logTestingPlaygroundURL();  or  logRoles(container);

Senior Engineer Perspective

Say the priority list and the reason: "querying by role tests accessibility for free." A strong candidate notes that overusing getByTestId is a smell that signals non-semantic markup, and that the name option maps to the ARIA accessible-name computation. Practical tip worth mentioning: screen.getByRole('...') with a wrong name prints every available role, and Testing Library's "Testing Playground" helps pick the right query — showing you actually author tests, not just recite theory.

Q8. What is the difference between user-event and fireEvent, and which should you use?

ROI: ★★★★☆ Frequency: High

Short Answer

fireEvent dispatches a single raw DOM event (e.g. one change event). user-event simulates a full user interaction: typing a character fires keydown, keypress, input, and keyup, respects disabled elements, moves focus, and so on. Prefer @testing-library/user-event — it's higher fidelity and catches bugs fireEvent misses. In v14+ it's async, so you await its methods after calling userEvent.setup().

Detailed Answer

fireEvent.change(input, { target: { value: 'abc' } }) sets the value and fires one event in one shot. But a real user typing "abc" produces a stream of key and input events per character, and many components rely on that (masking, per-keystroke validation, onKeyDown handlers). user-event's type() reproduces that sequence, so it exercises the component the way production does.

Other realism user-event adds:

  • Won't "click" or "type" into a disabled element (fireEvent will happily fire the event anyway).
  • click fires pointerdown/mousedown/focus/mouseup/click, and moves focus like a browser.
  • Rich helpers: tab(), keyboard(), selectOptions(), upload(), clear(), hover().

The v14 API change: you call const user = userEvent.setup() once (ideally before render), then await user.click(...). The methods return Promises, so forgetting await produces "not wrapped in act(...)" warnings or flaky assertions. fireEvent is still fine for events with no user-interaction equivalent (e.g. scroll, mouseOver on a non-interactive element, or firing a synthetic event a library dispatches).

Code Example

import { render, screen } from "@testing-library/react";
import userEvent from "@testing-library/user-event";

test("filling and submitting a form", async () => {
  const user = userEvent.setup();      // v14+: set up once
  const onSubmit = jest.fn();
  render(<LoginForm onSubmit={onSubmit} />);

  await user.type(screen.getByLabelText(/email/i), "a@b.com"); // per-keystroke events
  await user.type(screen.getByLabelText(/password/i), "secret1");
  await user.click(screen.getByRole("button", { name: /log in/i }));

  expect(onSubmit).toHaveBeenCalledWith({ email: "a@b.com", password: "secret1" });
});

// fireEvent still fits low-level / non-interaction events:
// fireEvent.scroll(window, { target: { scrollY: 500 } });

Senior Engineer Perspective

The headline: "user-event simulates a real user; fireEvent dispatches one raw event — default to user-event." Show you know the v14 async migration (setup() + await), because that's a frequent source of act() warnings and flaky suites. A concrete example of the difference wins points: fireEvent can "click" a disabled button and mask a bug, whereas user-event refuses, matching real browser behavior. Note that fireEvent is still the right tool when there's no user gesture equivalent.

Q9. How do you test asynchronous UI with findBy and waitFor?

ROI: ★★★★★ Frequency: Extremely High

Short Answer

Use findBy* to wait for an element to appear after async work (it polls until found or times out). Use waitFor(callback) to wait for an arbitrary assertion or condition to become true — for example, that a mock was called or an element disappeared (waitForElementToBeRemoved is the purpose-built version). Prefer findBy for the common "data loads and renders" case; reach for waitFor only when there's no element to query for directly.

Detailed Answer

Async UI is where most flaky tests are born. The golden rule: never use fixed setTimeout to wait — always wait for a condition. RTL's async utilities poll the DOM using a MutationObserver and resolve as soon as the condition is met (default timeout ~1000ms).

  • findByText('Ada') — the idiomatic "wait for loaded content." Equivalent to waitFor(() => getByText('Ada')) but more readable.
  • waitFor(() => expect(mock).toHaveBeenCalled()) — for non-DOM conditions. Keep the callback tiny and side-effect-free; it may run many times. Don't put multiple unrelated assertions or state changes inside it.
  • waitForElementToBeRemoved(() => screen.queryByText(/loading/i)) — the correct way to assert a spinner/toast disappeared.

Common failure modes to name: (1) forgetting to await the async query, causing the test to finish before the assertion runs; (2) "not wrapped in act()" warnings from state updates that happen after the test body ends — usually fixed by awaiting a findBy so RTL flushes the update; (3) using getBy immediately after render for data that hasn't arrived yet, which throws.

Code Example

test("shows a spinner, then the loaded user", async () => {
  render(<UserCard id="1" />);

  // Loading state is synchronous
  expect(screen.getByText(/loading/i)).toBeInTheDocument();

  // Wait for the fetched content to appear
  expect(await screen.findByRole("heading", { name: /ada lovelace/i }))
    .toBeInTheDocument();

  // And for the spinner to go away
  await waitForElementToBeRemoved(() => screen.queryByText(/loading/i));
});

test("waitFor for a non-DOM condition", async () => {
  const onLoad = jest.fn();
  render(<Widget onLoad={onLoad} />);
  await waitFor(() => expect(onLoad).toHaveBeenCalledTimes(1)); // keep it minimal
});

Senior Engineer Perspective

The strongest signal is "wait for a condition, never a fixed delay." Interviewers probe the findBy vs waitFor choice: use findBy when you're waiting for an element (it's cleaner), waitFor when you're waiting for a non-DOM fact. Warn against the anti-pattern of a bloated waitFor callback with side effects or several assertions — since it re-runs, side effects fire repeatedly and a late assertion masks which condition actually failed. Connecting act() warnings to un-awaited async updates shows real debugging experience.

Q10. How do you test a custom hook with renderHook?

ROI: ★★★★☆ Frequency: High

Short Answer

Hooks can only run inside a component, so use renderHook from @testing-library/react (it moved there from the old react-hooks-testing-library). It renders a tiny host component that calls your hook and exposes the latest return value on result.current. To trigger updates, call the hook's functions inside act(...); to test dependency changes, use the rerender and initialProps options; and wrap in a provider via the wrapper option when the hook needs Context.

Detailed Answer

renderHook(callback) returns { result, rerender, unmount }. result.current always reflects the hook's most recent return, so after an action you read the updated value there. Any call that causes a state update must be wrapped in act() so React flushes it before you assert (async updates use await act(...) or a waitFor on result.current).

Two important nuances:

  • Props/dependencies — pass initialProps and re-run with rerender(newProps) to test how the hook responds to changing inputs (e.g. a useDebounce(value) when value changes).
  • Context — supply a wrapper component so hooks that call useContext (custom store hooks, useQuery needing a QueryClientProvider) have their provider.

A caveat worth voicing: don't over-test trivial hooks in isolation. If a hook is only meaningful inside a component, an integration test of that component often gives more confidence. Reserve renderHook for genuinely reusable, logic-heavy hooks (a state machine, a debounce, a pagination controller).

Code Example

import { renderHook, act, waitFor } from "@testing-library/react";

test("useCounter increments", () => {
  const { result } = renderHook(() => useCounter(5));

  expect(result.current.count).toBe(5);
  act(() => result.current.increment());   // state update must be in act()
  expect(result.current.count).toBe(6);
});

test("useDebounce reacts to prop changes", () => {
  const { result, rerender } = renderHook(
    ({ value }) => useDebounce(value, 300),
    { initialProps: { value: "a" } }
  );
  rerender({ value: "ab" });               // simulate a new input
  // ...advance fake timers, then assert result.current...
});

// Hook that needs a provider
const wrapper = ({ children }) => (
  <QueryClientProvider client={queryClient}>{children}</QueryClientProvider>
);
const { result } = renderHook(() => useUser("1"), { wrapper });
await waitFor(() => expect(result.current.isSuccess).toBe(true));

Senior Engineer Perspective

Know that renderHook now ships in @testing-library/react (the standalone hooks library is deprecated) — naming the wrong package dates you. The act() requirement around state-changing calls is the most common gotcha. And the mature caveat scores points: testing a hook in isolation is right for reusable logic, but for a hook that's inseparable from one component, an integration test better reflects real usage — a direct application of the "test the way it's used" principle.

Q11. How do you test a component that depends on Context or a Redux store?

ROI: ★★★★☆ Frequency: High

Short Answer

Wrap the component in its required providers at render time. The clean, reusable approach is a custom render function that wraps children in all your app providers (Redux <Provider>, theme, router, query client) and re-exports everything from RTL. For Redux, create a real store per test with a known preloaded state rather than mocking the store — that tests the actual reducer/selector wiring. Pass different context values or preloaded state to exercise different scenarios.

Detailed Answer

Context: render the component inside the matching <Context.Provider value={...}>. Passing an explicit value lets you drive the component into any state (e.g. an "authenticated" vs "logged out" auth context) without touching internals.

Redux: the recommended pattern (from the Redux docs) is a custom render that builds a fresh store with configureStore({ reducer, preloadedState }) and wraps children in <Provider store={store}>. Prefer this over mocking useSelector/useDispatch: a real store means your selectors, reducers, and connected component all run, so the test verifies real behavior. You can dispatch actions before or during the test and assert on the resulting UI. Only mock the store if you specifically need to isolate a purely presentational connected component.

A single test-utils module that re-exports a custom render keeps every test terse — you render(<Cart />, { preloadedState }) and get all providers for free. This is one of the highest-leverage patterns in a real test suite.

Code Example

// test-utils.tsx — a custom render with all app providers
import { render } from "@testing-library/react";
import { Provider } from "react-redux";
import { configureStore } from "@reduxjs/toolkit";
import rootReducer from "../store/rootReducer";

export function renderWithProviders(
  ui,
  { preloadedState, store = configureStore({ reducer: rootReducer, preloadedState }) } = {}
) {
  const Wrapper = ({ children }) => <Provider store={store}>{children}</Provider>;
  return { store, ...render(ui, { wrapper: Wrapper }) };
}
export * from "@testing-library/react";  // re-export screen, etc.

// A test using a real store with preloaded state
import { renderWithProviders, screen } from "../test-utils";

test("shows items from the store", () => {
  renderWithProviders(<Cart />, {
    preloadedState: { cart: { items: [{ id: 1, name: "Book" }] } },
  });
  expect(screen.getByText("Book")).toBeInTheDocument();
});

// A plain Context provider wrap
render(
  <AuthContext.Provider value={{ user: { name: "Ada" }, isAuthed: true }}>
    <Navbar />
  </AuthContext.Provider>
);

Senior Engineer Perspective

The key insight is "use a real store, mock the network — not the store." Building a fresh configureStore with preloadedState per test keeps tests isolated and exercises real reducers/selectors, which is far more valuable than stubbing useSelector. The custom-render / test-utils pattern signals you've maintained a real suite. Follow-up traps: needing a fresh store per test to avoid cross-test leakage, and wrapping in a router (MemoryRouter) or QueryClientProvider when the component also depends on those.

Q12. What is snapshot testing — its pros, cons, and when does it earn its keep?

ROI: ★★★☆☆ Frequency: Medium

Short Answer

A snapshot test serializes a component's rendered output to a .snap file on the first run and, on later runs, fails if the output differs. Pros: cheap to write and catches unintended UI changes. Cons: large snapshots are unreadable, break constantly on legitimate changes, and developers "just press u" to update them without reviewing — so they rot into noise. They earn their keep for small, stable, serializable output (a formatted string, a design-system icon, an error object), not for big component trees.

Detailed Answer

Snapshots test "did the output change" rather than "is the output correct" — an important distinction. On the first run Jest writes the serialized tree; thereafter any diff is a failure you review and either fix or accept with jest --updateSnapshot (-u).

The failure mode is cultural: on a large component, any real change produces a huge diff, and because updating is one keystroke, teams reflexively accept snapshots without reading them. At that point the test provides zero protection — it rubber-stamps whatever the code currently does. Large snapshots also review poorly in PRs.

Better practices:

  • Prefer inline snapshots (toMatchInlineSnapshot()) for small output — the expected value lives in the test, so it's reviewable and diffs are local.
  • Keep them small and focused; snapshot a single formatted value, not an entire page.
  • For visual regressions, use image snapshots via Playwright/Chromatic/Percy, not DOM snapshots — they catch actual rendering changes DOM snapshots miss.
  • Assert explicit, meaningful expectations (getByRole + toHaveTextContent) for anything behavioral; reserve snapshots for stable structural output.

Code Example

// Whole-tree snapshot (use sparingly — brittle, review-hostile)
import { render } from "@testing-library/react";
test("Button renders", () => {
  const { container } = render(<Button variant="primary">Save</Button>);
  expect(container).toMatchSnapshot();
});

// Better: inline snapshot for small, stable output
test("formats currency", () => {
  expect(formatCurrency(1999, "USD")).toMatchInlineSnapshot(`"$19.99"`);
});

Senior Engineer Perspective

The nuanced take interviewers reward: "snapshots test change, not correctness, and they only add value if people actually review the diffs." Call out the press u to update anti-pattern by name. Show range by distinguishing DOM snapshots (Jest) from visual/image snapshots (Chromatic/Percy/Playwright) — the latter catch CSS regressions the former can't. Recommending inline snapshots for small values and explicit assertions for behavior demonstrates you've felt the pain of a rotten snapshot suite.

Q13. What is MSW (Mock Service Worker), and why is it better than mocking fetch?

ROI: ★★★★★ Frequency: Extremely High

Short Answer

MSW intercepts requests at the network layer — via a Service Worker in the browser and a request interceptor in Node for tests — and responds with handlers you define per endpoint. Because it operates below your app code, your components use their real data-fetching (fetch, axios, React Query) completely unchanged. That's the advantage over stubbing global.fetch: no rewiring the fetch shape, one set of handlers reused across tests, Storybook, and even local dev, and you test the real integration rather than a hand-built fake response.

Detailed Answer

Directly mocking fetch (or jest.mock-ing your API client) has real downsides:

  • You couple tests to the transport — swap fetch for axios and every mock breaks.
  • You reconstruct Response objects (ok, status, json()) by hand, easy to get subtly wrong.
  • Mocks live per test, so there's lots of duplication and drift.
  • You never exercise the actual request-building and response-parsing code, so bugs there go untested.

MSW inverts this. You declare handlers by URL and method (http.get('/api/user/:id', resolver)) that return real Response objects via the HttpResponse helper. In Jest you start a Node server in beforeAll, resetHandlers() in afterEach (so per-test overrides don't leak), and close() in afterAll. Individual tests override a handler with server.use(...) to simulate errors, empty states, or slow responses. The same handlers can back your Storybook stories and even a browser dev mode, so mocks stay consistent everywhere.

Note: MSW v2 moved to the http/graphql namespaces and the web-standard Response (HttpResponse), replacing v1's rest and (req, res, ctx) signature — worth knowing since lots of tutorials still show the old API.

Code Example

// handlers.ts
import { http, HttpResponse } from "msw";

export const handlers = [
  http.get("/api/user/:id", ({ params }) =>
    HttpResponse.json({ id: params.id, name: "Ada Lovelace" })
  ),
];

// server.ts (Node, for Jest)
import { setupServer } from "msw/node";
import { handlers } from "./handlers";
export const server = setupServer(...handlers);

// jest.setup.ts
beforeAll(() => server.listen());
afterEach(() => server.resetHandlers()); // undo per-test overrides
afterAll(() => server.close());

// a test that overrides one endpoint to simulate an error
import { http, HttpResponse } from "msw";
import { server } from "./server";

test("shows an error state on 500", async () => {
  server.use(
    http.get("/api/user/:id", () =>
      HttpResponse.json({ message: "boom" }, { status: 500 })
    )
  );
  render(<UserCard id="1" />);            // real fetch runs, MSW intercepts
  expect(await screen.findByText(/something went wrong/i)).toBeInTheDocument();
});

Senior Engineer Perspective

The one-liner: "MSW mocks the network, not your code, so components run their real fetching path." Emphasize the lifecycle discipline — listen/resetHandlers/close — and per-test server.use() overrides for error and edge cases, since forgetting resetHandlers is a classic source of leaking state. Bonus points for the reuse story (same handlers in tests, Storybook, and dev) and for knowing the v2 API (http + HttpResponse) versus the older v1 rest/ctx style.

Q14. What does code coverage tell you — and what does it not?

ROI: ★★★★☆ Frequency: High

Short Answer

Coverage measures which lines/branches/functions/statements were executed while tests ran — Jest reports all four via Istanbul. It's a useful signal for finding untested code (0% coverage is a real gap). But it says nothing about whether your assertions are meaningful: you can hit 100% coverage with tests that assert nothing. High coverage means "the code ran," not "the code is correct." Chase confidence, not a coverage percentage.

Detailed Answer

The four metrics:

  • Statements — each statement executed.
  • Branches — each side of every if/ternary/&& taken. The most informative, because untested branches are where bugs hide.
  • Functions — each function called.
  • Lines — each line run (close to statements).

What it can't see: assertion quality. A test that renders a component and never checks anything will still mark all those lines "covered." Coverage also can't tell you about missing cases you never wrote a test for at all (it only measures code you have), nor about integration correctness, race conditions, accessibility, or visual bugs.

Chasing 100% is usually a net negative — the last 10-20% (error branches, defensive guards) is expensive and often tested with low-value tests written purely to move the number. A pragmatic policy: set a reasonable threshold (e.g. 70-80%) via coverageThreshold to catch regressions, exclude generated/config files, and read coverage as a map of gaps to investigate, not a scoreboard. Mutation testing (e.g. Stryker) actually measures assertion quality by changing code and checking whether tests fail — a better proxy for "do the tests catch bugs."

Code Example

// jest.config.js
module.exports = {
  collectCoverage: true,
  coverageReporters: ["text", "lcov"],
  collectCoverageFrom: [
    "src/**/*.{ts,tsx}",
    "!src/**/*.d.ts",
    "!src/**/*.stories.tsx",     // exclude noise from the denominator
  ],
  coverageThreshold: {
    global: { branches: 75, functions: 80, lines: 80, statements: 80 },
  },
};

// This test gives 100% coverage of add() but asserts NOTHING useful:
test("covers add", () => {
  add(2, 3);                     // executed -> "covered", but no expect()
});
// Coverage: 100%. Confidence: 0%.

Senior Engineer Perspective

The maxim to deliver: "coverage tells you what code ran, not whether it's correct." Give the killer example — a test with no expect still scores 100%. Argue against a blanket 100% mandate (diminishing returns, incentivizes low-value tests) while defending a sensible threshold to catch regressions. Naming branch coverage as the most useful metric, and mutation testing (Stryker) as the real measure of assertion strength, shows depth beyond the standard talking points.

Q15. What is end-to-end testing with Cypress and Playwright, and when should you use it?

ROI: ★★★★☆ Frequency: High

Short Answer

E2E tests drive a real browser against the running app (real or realistically-stubbed backend), clicking through complete user journeys — login, checkout, signup — exactly as a user would. Cypress and Playwright are the two dominant tools. They give the highest confidence but are the slowest and most flaky, so you reserve them for a handful of business-critical happy paths, not exhaustive coverage. Everything cheaper (unit, integration/RTL) should catch the rest.

Detailed Answer

E2E complements, not replaces, component tests. RTL renders a component in jsdom (a simulated DOM, no real browser, no real navigation); E2E launches Chromium/Firefox/WebKit and exercises routing, real network, cookies, redirects, and cross-page flows that jsdom can't. Use E2E to answer "can a user actually complete the core journey end to end," and to smoke-test after deploys.

AspectCypressPlaywright
OriginCypress.io, 2017Microsoft, 2020
BrowsersChromium, Firefox, WebKit(exp.)Chromium, Firefox, WebKit — first-class
Execution modelRuns in the browser event loopOut-of-process via CDP/drivers
ParallelismPaid dashboard / pluginsBuilt-in, free, fast
LanguagesJavaScript/TypeScriptTS/JS, Python, Java, .NET
WaitingAutomatic retry-abilityAuto-waiting + web-first assertions
MomentumMature, great DX/time-travel UIFast-growing, now often the default

Both auto-wait for elements (reducing flakiness versus manual sleeps), record videos/screenshots on failure, and support network stubbing. Playwright's built-in free parallelism, true multi-browser support, and multi-language bindings have made it the common new-project choice; Cypress remains beloved for its interactive time-travel debugger and developer experience. Keep the E2E suite small and stable — flaky E2E that everyone ignores is worse than none.

Code Example

// Playwright
import { test, expect } from "@playwright/test";

test("user can log in", async ({ page }) => {
  await page.goto("/login");
  await page.getByLabel("Email").fill("a@b.com");
  await page.getByLabel("Password").fill("secret1");
  await page.getByRole("button", { name: /log in/i }).click();
  await expect(page.getByRole("heading", { name: /dashboard/i })).toBeVisible();
});

// Cypress (equivalent flow)
it("user can log in", () => {
  cy.visit("/login");
  cy.findByLabelText("Email").type("a@b.com");
  cy.findByLabelText("Password").type("secret1");
  cy.findByRole("button", { name: /log in/i }).click();
  cy.findByRole("heading", { name: /dashboard/i }).should("be.visible");
});

Senior Engineer Perspective

Frame E2E by cost/confidence: highest confidence, highest cost and flakiness, so cover only critical journeys and let RTL handle breadth — a direct callback to the testing trophy from Q1. Note that both tools share Testing-Library-style queries (getByRole), so the accessible-query habit transfers. On tool choice, the current honest answer is "Playwright has become the default for new projects — free parallelism, true cross-browser, multi-language — while Cypress still wins on interactive DX." Mention that E2E should run against seeded/stubbed data for determinism, not a shared mutable environment.

Q16. Vitest vs Jest — what's the difference and how do you choose today?

ROI: ★★★★☆ Frequency: High

Short Answer

Jest is the long-standing, battle-tested test runner ubiquitous in the React/CRA world. Vitest is a newer, Vite-native runner with a nearly Jest-compatible API (describe/it/expect, same matchers) that's dramatically faster in Vite projects because it shares Vite's transform pipeline and needs no Babel/ts-jest transpile step, plus first-class ESM and TypeScript support and instant HMR-style watch mode. The current guidance: if your app is built with Vite, use Vitest; if you're on Next.js/CRA/webpack with an established Jest setup, Jest is still perfectly fine.

Detailed Answer

The API overlap is deliberate — Vitest was designed as a near drop-in replacement, so most Jest tests run with minimal changes (RTL, jest-dom, and MSW all work with either). Key differences:

AspectJestVitest
Config / transformBabel or ts-jest; separate configReuses your vite.config & plugins
ESM supportHistorically awkward (needs flags)Native ESM first
Speed (Vite apps)Slower (extra transpile)Much faster; instant watch
Mocking APIjest.fn/mock/spyOnvi.fn/mock/spyOn (same shape)
GlobalsOn by defaultOpt-in (globals: true) or import
Ecosystem maturityLargest; most docs/pluginsNewer but growing fast

Practical migration notes: replace the jest namespace with vi (or enable a Jest-compat alias), and either set globals: true or import describe/it/expect from vitest. Both use jsdom/happy-dom for the DOM environment and pair with React Testing Library identically. Vitest's headline win is speed and zero-config alignment with a Vite toolchain — no maintaining a parallel Babel/ts-jest config that can drift from how the app actually builds.

Why Jest still holds ground: it's the default in Next.js and many enterprise codebases, has the deepest ecosystem and documentation, and there's little reason to migrate a large, working, webpack-based suite. The choice is mostly dictated by your build tool, not by one being "better."

Code Example

// Nearly identical test — only the mock namespace changes.

// Jest
import { render, screen } from "@testing-library/react";
const onClick = jest.fn();
test("calls onClick", () => {
  render(<Button onClick={onClick}>Go</Button>);
  screen.getByRole("button").click();
  expect(onClick).toHaveBeenCalled();
});

// Vitest
import { describe, it, expect, vi } from "vitest";  // or globals: true
import { render, screen } from "@testing-library/react";
const onClick = vi.fn();                            // vi instead of jest
it("calls onClick", () => {
  render(<Button onClick={onClick}>Go</Button>);
  screen.getByRole("button").click();
  expect(onClick).toHaveBeenCalled();
});

Senior Engineer Perspective

The mature framing is "choose by toolchain, not hype": Vitest for Vite projects (speed, native ESM/TS, shared config), Jest for established webpack/Next.js suites. Show you know the API is intentionally near-identical (vi mirrors jest), so migration is mechanical and RTL/MSW/jest-dom carry over. Interviewers like hearing that the testing approach — behavior over implementation, integration-first, MSW at the boundary — is identical regardless of runner; the runner is an implementation detail, and switching one doesn't change how you write good tests.
