SECTION 1 - RULES & useState

Q1. What are the Rules of Hooks, and why does call order matter?

ROI: ★★★★★ Frequency: Extremely High

Short Answer

There are two rules: only call hooks at the top level (never inside conditions, loops, or nested functions), and only call them from React function components or custom hooks. They matter because React does not identify hooks by name — it identifies them by call order. React keeps an ordered list of hook "slots" per component instance, and on every render it walks that list in the same sequence. Break the order and React hands you the wrong state.

Detailed Answer

Internally, a component's hooks are stored as a linked list attached to its fiber. There is no key like "count" or "user" — the first useState you call is slot 0, the second is slot 1, and so on. On the next render React resets a pointer to the head of the list and reads slots back in the exact order you call them.

Why conditional hooks break this

If you wrap a hook in an if, then on renders where the condition is false, one slot is skipped. Every hook after it shifts by one position, so React returns state that belongs to a different hook. This is why the linter rule react-hooks/rules-of-hooks is effectively non-negotiable.

  • Top level only — no hooks inside if, for, while, ternaries, or callbacks.
  • Function components / custom hooks only — not class components, not plain utility functions, not event handlers.
  • Order must be identical on every render — the count and sequence of hook calls must be stable.

The correct pattern is to always call the hook unconditionally and put the condition inside the hook logic, or to split into two components so each renders a fixed set of hooks.

Code Example

// WRONG — hook order changes between renders
function Profile({ userId }: { userId?: string }) {
  if (userId) {
    const [user, setUser] = useState(null); // slot 0 only sometimes exists
  }
  const [theme, setTheme] = useState("light"); // slot shifts!
  // ...
}

// RIGHT — always call unconditionally, branch inside
function Profile({ userId }: { userId?: string }) {
  const [user, setUser] = useState<User | null>(null);
  const [theme, setTheme] = useState("light");

  useEffect(() => {
    if (!userId) return;      // condition lives INSIDE the hook
    fetchUser(userId).then(setUser);
  }, [userId]);
  // ...
}

Project Example

A classic bug: a settings panel that conditionally called useMemo only when a feature flag was on. When the flag toggled at runtime, every hook below it read the wrong slot and the form silently reset. Moving the flag check inside the memo factory fixed it instantly.

Senior Engineer Perspective

Interviewers want to hear "call order / slot-based storage", not just "the linter says so". If you can explain why React can't use names (it would need a compiler pass or explicit keys, which hurts composition), you demonstrate you understand the reconciler, not just the API. A strong follow-up: "Could early return before a hook break the rules?" — yes, because it skips subsequent hooks on some renders. The React Compiler (React 19) auto-memoizes but does not relax these rules; the linear model still holds.

Q2. How does useState work — functional updates, lazy initialization, and batching in React 18?

ROI: ★★★★★ Frequency: Extremely High

Short Answer

useState returns a value and a setter. The setter can take either a new value or an updater function prev => next, which is the correct form whenever the next state depends on the previous one. Pass a function to useState for lazy initialization when the initial value is expensive to compute. In React 18, all state updates — including those inside promises, timeouts, and native events — are automatically batched into a single re-render.

Detailed Answer

Functional updates

State setters are asynchronous with respect to the current render: the count variable in scope is a snapshot. Calling setCount(count + 1) three times in a row all read the same stale count and only bump it once. The updater form setCount(c => c + 1) queues each update against the latest queued value, so three calls bump it three times.

Lazy initialization

The initializer argument runs on every render but its result is only used on the first. If it's expensive (parsing localStorage, building a big structure), pass a function instead — React only calls it once, on mount.

Batching in React 18

Before React 18, updates were only batched inside React event handlers. Updates in setTimeout, promises, or async callbacks each triggered their own render. React 18's automatic batching groups all of them, regardless of source. You can opt out with flushSync if you truly need a synchronous DOM update between two state changes.

Code Example

// Functional updates — required when next depends on prev
function Counter() {
  const [count, setCount] = useState(0);

  const addThree = () => {
    setCount(c => c + 1);   // queued: 0 -> 1
    setCount(c => c + 1);   // queued: 1 -> 2
    setCount(c => c + 1);   // queued: 2 -> 3  ✅ result is 3
    // setCount(count + 1) x3 would all read 0 and land on 1
  };
  return <button onClick={addThree}>{count}</button>;
}

// Lazy init — parse runs once, not on every render
const [prefs, setPrefs] = useState(() =>
  JSON.parse(localStorage.getItem("prefs") ?? "{}")
);

// React 18 automatic batching — ONE re-render, not two
setTimeout(() => {
  setLoading(false);
  setData(payload);   // batched together in React 18
}, 0);

Senior Engineer Perspective

The trap here is claiming setState is "synchronous" or that it "returns the new value" — it does neither. A senior answer connects functional updates to closures: setCount(count + 1) fails in loops and rapid handlers precisely because count is captured. Expect the follow-up "when would you use flushSync?" — the honest answer is "almost never; only when you must read layout between two updates," because it forces a synchronous render and hurts performance.

Q3. Why can't you call hooks conditionally, and how do you handle logic that really is conditional?

ROI: ★★★★ Frequency: High

Short Answer

You can't because it changes the number/order of hook calls between renders and desyncs React's slot list. When logic genuinely needs to be conditional, keep the hook call unconditional and put the branch inside it, use conditional values as arguments, or extract the conditional part into a separate child component that either mounts or doesn't.

Detailed Answer

The most common patterns for "conditional hooks":

  • Branch inside the effect: always call useEffect, and return early inside it if the condition is false.
  • Conditional query enabling: data libraries expose an enabled flag (e.g. TanStack Query's enabled: !!id) so the hook always runs but does nothing until ready.
  • Component split: render {isOpen && <Modal />}. The parent's hook set is stable; the child mounts/unmounts, and its hooks are consistent for its own lifetime.

The component-split approach is usually the cleanest because "this feature only exists sometimes" is naturally expressed as "this component sometimes renders."

Code Example

// Instead of conditionally calling a hook, conditionally render the component
function Page({ showChart }: { showChart: boolean }) {
  return (
    <div>
      <Header />
      {showChart && <Chart />}   {/* Chart owns its own hooks safely */}
    </div>
  );
}

Senior Engineer Perspective

The tell of a junior answer is trying to be clever with useState wrapped in a helper that's "sometimes" called. Seniors reach for the component boundary because it also localizes state lifetime and cleanup. Mentioning the enabled pattern signals you've used a real data layer, not just raw effects.

SECTION 2 - useEffect DEEP DIVE

Q4. Explain the full mental model of useEffect: when does it run across mount, update, and unmount?

ROI: ★★★★★ Frequency: Extremely High

Short Answer

useEffect runs after the browser has painted the committed render. On mount it runs the effect once. On each subsequent commit, if any dependency changed, React first runs the previous effect's cleanup, then runs the new effect. On unmount it runs cleanup one final time. The dependency array is what decides whether an update re-runs the effect at all.

Detailed Answer

Stop thinking of effects as "lifecycle methods". The right mental model is: an effect synchronizes an external system with your current render's props and state. Every render produces a snapshot of values, and the effect describes what should be true of the outside world for that snapshot.

The three dependency-array modes

DepsWhen the effect runs
[a, b]After mount, and after any commit where a or b changed (by Object.is).
[]Only after the initial mount (and cleanup only on unmount).
omittedAfter every single commit. Almost always a mistake.

Ordering within a commit

React commits the DOM, the browser paints, then effects fire. For an update, the sequence is: run last render's cleanup → run this render's effect. This "cleanup then re-run" is why subscriptions and event listeners don't leak: each run undoes the previous one.

Code Example

useEffect(() => {
  console.log("effect runs with roomId =", roomId);
  const conn = createConnection(roomId);
  conn.connect();

  return () => {
    console.log("cleanup for roomId =", roomId);
    conn.disconnect();
  };
}, [roomId]);

// Mount (roomId="a"): "effect runs a"
// Update to "b":       "cleanup a" then "effect runs b"
// Unmount:             "cleanup b"

Project Example

A chat feature keyed on roomId: when the user switches rooms, the effect cleans up the old socket and opens a new one automatically. No manual "did roomId change?" comparison is needed — the dependency array is that comparison.

Senior Engineer Perspective

The phrase to land is "synchronization, not lifecycle." Interviewers probe whether you know effects run after paint (that's why useLayoutEffect exists for pre-paint work). A great follow-up answer: the cleanup captures the values from the render that created it — the closure over roomId in the example logs "a" on cleanup even though the component is heading to "b". That closure behavior is the root of most effect confusion.

Q5. What is a stale closure in useEffect, and how do you fix it?

ROI: ★★★★★ Frequency: Extremely High

Short Answer

A stale closure happens when an effect (often one with [] deps) captures a value from its first render and keeps using that frozen value even after state changes. The fixes, in order of preference: add the value to the dependency array; use the functional updater form so you never read stale state; or, for values you deliberately don't want to re-subscribe on, store them in a ref that you keep current.

Detailed Answer

Because each render creates fresh function closures over that render's variables, an effect that runs only on mount closes over the mount-time values forever. A setInterval callback set up with [] deps will keep seeing count === 0 no matter how many times you increment.

  • Add the dep — correct but re-runs the effect (tears down and rebuilds the interval each tick, usually undesirable here).
  • Functional updater — setCount(c => c + 1) never reads the captured count, so the stale value is irrelevant. Best fix for counters.
  • Ref mirror — keep the latest value in a ref (latest.current = value) updated each render; read latest.current inside the effect. Use when you want the freshest value without re-subscribing.

Code Example

// BUG — captures count = 0 forever, logs 0 every second
useEffect(() => {
  const id = setInterval(() => console.log(count), 1000);
  return () => clearInterval(id);
}, []); // eslint-disable-line — the classic smell

// FIX A — functional updater, no stale read needed
useEffect(() => {
  const id = setInterval(() => setCount(c => c + 1), 1000);
  return () => clearInterval(id);
}, []);

// FIX B — ref mirror keeps latest value without re-subscribing
const countRef = useRef(count);
useEffect(() => { countRef.current = count; });
useEffect(() => {
  const id = setInterval(() => console.log(countRef.current), 1000);
  return () => clearInterval(id);
}, []);

Senior Engineer Perspective

Never say "just disable the exhaustive-deps lint rule" as your primary answer — that's the exact move that hides stale closures. Interviewers love watching a candidate reason about why the interval sees 0: because the closure was built once. Mentioning the ref-mirror pattern (the basis of libraries' useEvent / useEffectEvent) shows depth. React's experimental useEffectEvent formalizes exactly this "read latest, don't re-subscribe" need.

Q6. Why does my useEffect loop forever? Walk through debugging it.

ROI: ★★★★★ Frequency: Extremely High

Short Answer

An effect loops when it updates state that (directly or indirectly) is one of its own dependencies, or when a dependency is a value re-created on every render — an object, array, or function literal — so Object.is always sees it as "changed". The fix is to remove the self-triggering update, or stabilize the offending dependency with useMemo/useCallback, or move it out of the render.

Detailed Answer

The loop mechanics: effect runs → calls setState → triggers re-render → dependency looks different → effect runs again → forever. There are three recurring culprits.

Culprit 1 — the effect sets state it depends on

Reading a value, deriving from it, and setting state, with that value in deps.

Culprit 2 — a new object/array/function in deps every render

useEffect(fn, [{ id }]) or [options] where options = {} is defined in the component body. A fresh reference each render means the dep is never equal.

Culprit 3 — a non-memoized callback prop in deps

Parent passes onDone={() => ...} (new function each render); child lists it in deps.

Debug procedure: (1) log inside the effect to confirm it's re-firing; (2) log each dependency's identity; (3) find which one changes every render; (4) either stop creating it fresh, memoize it, or drop it from deps if it doesn't belong there.

Code Example

// LOOP 1 — sets a dep it reads
useEffect(() => {
  setTotal(items.reduce((s, i) => s + i.price, 0)); // total isn't a dep, but...
}, [items, total]); // total in deps + setTotal each run = infinite loop
// FIX: don't store derived data — compute during render (see Q13),
// or drop `total` from deps: }, [items]);

// LOOP 2 — new object identity every render
const filters = { status: "open" };          // fresh object each render
useEffect(() => { fetchTasks(filters); }, [filters]); // never equal -> loops
// FIX: useMemo(() => ({ status: "open" }), []) or depend on [status]

// LOOP 3 — unstable callback prop
useEffect(() => { subscribe(onData); }, [onData]); // onData new each parent render
// FIX: wrap onData in useCallback in the parent

Project Example

A dashboard that took a config object prop and fetched on [config] hammered the API on every parent render. The parent was building config inline in JSX. Wrapping it in useMemo (keyed on the actual scalar inputs) stopped the storm without touching the child.

Senior Engineer Perspective

This is a live-debugging favorite. Interviewers want a procedure, not a guess: confirm it loops, then isolate the unstable dependency by identity. The senior insight is that the real root cause is usually "we're depending on a reference we recreate every render" — and that the deeper fix is often not memoizing harder but restructuring (depend on primitives, or don't store derived state). Blaming the linter for "making me add the dep" is a red flag; the linter surfaced a real reference-identity problem.

Q7. Why do effects run twice in React 18 StrictMode, and what does it teach you?

ROI: ★★★★ Frequency: High

Short Answer

In development only, StrictMode intentionally mounts each component, runs its effects, runs cleanup, and mounts again — so effects fire twice. It's a stress test that surfaces effects which aren't resilient to being set up and torn down repeatedly (leaked subscriptions, duplicate requests, missing cleanup). It does not happen in production, and the correct response is to write proper cleanup, not to suppress the double-run.

Detailed Answer

React's concurrent features can mount, unmount, and remount components (for example, when restoring state on tab switching). StrictMode simulates that up front so you build effects that survive a remount. If your effect is a correct "setup / cleanup" pair, running it twice is harmless: connect → disconnect → connect leaves exactly one live connection.

The symptoms of an effect that fails the test: two network requests on load, two socket connections, a subscription registered twice. The fix is almost always adding or correcting the cleanup function, or moving one-time non-idempotent work (like an analytics "session start" event) outside the effect or guarding it appropriately.

Code Example

// Passes the StrictMode double-invoke because cleanup undoes setup
useEffect(() => {
  const controller = new AbortController();
  fetch(`/api/users/${id}`, { signal: controller.signal })
    .then(r => r.json())
    .then(setUser)
    .catch(err => { if (err.name !== "AbortError") throw err; });

  return () => controller.abort(); // second mount aborts the first request
}, [id]);

Senior Engineer Perspective

The wrong instinct — "I'll add a useRef guard so it only runs once" — is a trap answer that hides the real weakness. Seniors say: "The double-run is a feature; if it breaks my effect, my cleanup is wrong." Mentioning AbortController for fetches and disconnect for sockets shows you build idempotent, self-cleaning effects. Note it's dev-only and gated by <StrictMode>.

Q8. useEffect vs useLayoutEffect — when do you reach for each?

ROI: ★★★★ Frequency: High

Short Answer

Both have identical APIs and dependency semantics. The difference is timing: useEffect runs asynchronously after the browser paints; useLayoutEffect runs synchronously after the DOM mutation but before paint. Default to useEffect. Reach for useLayoutEffect only when you must read layout (measure a node) and synchronously re-render before the user sees a flicker.

Detailed Answer

 useEffectuseLayoutEffect
TimingAfter paint (async)Before paint (sync, blocking)
Blocks visual update?NoYes
Use forData fetching, subscriptions, logging, most side effectsMeasuring DOM, positioning tooltips/popovers, preventing flicker
SSRFineWarns — no DOM on the server

Because useLayoutEffect blocks painting, overusing it hurts responsiveness. The canonical valid use: measure an element's size/position and adjust another element synchronously so the user never sees the intermediate state (e.g., a tooltip that must flip above the trigger when there's no room below).

Code Example

// Measure then reposition before paint — no visible jump
function Tooltip({ targetRect }: { targetRect: DOMRect }) {
  const ref = useRef<HTMLDivElement>(null);
  const [flipUp, setFlipUp] = useState(false);

  useLayoutEffect(() => {
    const el = ref.current;
    if (!el) return;
    const { height } = el.getBoundingClientRect();
    setFlipUp(targetRect.bottom + height > window.innerHeight);
  }, [targetRect]);

  return <div ref={ref} className={flipUp ? "above" : "below"} />;
}

Senior Engineer Perspective

Interviewers listen for "before vs after paint" and the SSR warning. A subtle senior point: because useLayoutEffect is synchronous and blocking, it can starve React's concurrent rendering and cause jank if misused. If your only reason is "it feels more reliable," that's the junior answer — reliability isn't the difference, paint timing is.

Q9. How do you correctly clean up subscriptions, timers, and listeners?

ROI: ★★★★ Frequency: High

Short Answer

Return a cleanup function from useEffect that reverses whatever the effect set up: clear the timer, remove the listener, unsubscribe, close the socket, or abort the request. React runs it before each re-run and on unmount. Every effect that creates an ongoing resource must have a matching cleanup, or you leak.

Detailed Answer

The mental checklist: "what does this effect start, and how do I stop exactly that instance?" The cleanup closes over the specific resource from that render, so it always tears down the right one. Common pairs:

  • addEventListener ↔ removeEventListener (same function reference!)
  • setInterval/setTimeout ↔ clearInterval/clearTimeout
  • subscribe() ↔ the returned unsubscribe()
  • new WebSocket ↔ socket.close()
  • fetch ↔ AbortController.abort()

A subtle listener bug: passing an inline arrow to both add and remove removes nothing, because they're different function references. Define the handler once.

Code Example

useEffect(() => {
  const onResize = () => setWidth(window.innerWidth); // one stable reference
  window.addEventListener("resize", onResize);
  const id = setInterval(tick, 1000);

  return () => {
    window.removeEventListener("resize", onResize); // same ref -> actually removed
    clearInterval(id);
  };
}, []);

Senior Engineer Perspective

Interviewers may hand you code with a memory leak and ask you to spot it. The two classic ones: no cleanup at all (listener accumulates on every mount), and add/remove with different function references. Tie this back to StrictMode (Q7): a correct cleanup is exactly what makes an effect survive the dev double-invoke.

SECTION 3 - MEMOIZATION HOOKS

Q10. useMemo vs useCallback — what's the difference and when do they actually help?

ROI: ★★★★★ Frequency: Extremely High

Short Answer

useMemo caches the result of a computation; useCallback caches a function definition. In fact useCallback(fn, deps) is just useMemo(() => fn, deps). Both recompute only when their dependencies change. They genuinely help in two cases: skipping an expensive calculation, and preserving a stable reference so a memoized child (React.memo) or a dependency array doesn't see a "change" every render. Everywhere else they add cost, not value.

Detailed Answer

When useMemo helps

  • The computation is genuinely expensive (sorting/filtering thousands of rows, heavy transforms).
  • The result is an object/array passed as a prop to a React.memo child, or used in a dependency array — you need referential stability.

When useCallback helps

  • The function is passed to a React.memo child that would otherwise re-render on every parent render.
  • The function is a dependency of another hook (useEffect/useMemo) and must stay stable to avoid re-running it.

When they DON'T help (and hurt)

Memoizing a trivial calculation, or memoizing a callback passed to a plain (non-memoized) child, buys nothing — the child re-renders anyway — while adding a closure, a deps array, and a cache slot. Memoization has real overhead; wrapping everything "just in case" makes code slower and noisier.

Code Example

// useMemo — skip expensive work + stable reference for a memoized child
const sortedRows = useMemo(
  () => [...rows].sort((a, b) => a.score - b.score),
  [rows]
);

// useCallback — stable handler so <Row> (React.memo) doesn't re-render
const handleSelect = useCallback((id: string) => {
  setSelected(id);
}, []); // no deps -> identity never changes

const Row = React.memo(function Row({ onSelect }: RowProps) {
  return <button onClick={() => onSelect(row.id)} />;
});

// POINTLESS — child isn't memoized, so it re-renders regardless
const noop = useCallback(() => {}, []); // just overhead here

Project Example

A virtualized table rendered 10k memoized rows. Every keystroke in an unrelated search box re-rendered all rows because the row's onClick was a fresh closure. Wrapping the handler in useCallback and the row in React.memo cut re-renders to just the changed rows. But we only did it after profiling proved the cost — not preemptively.

Senior Engineer Perspective

The senior differentiator is knowing that both hooks are useless without the corresponding React.memo boundary or dependency-array consumer — a memoized callback handed to a non-memoized child does nothing. Also expect: "The React Compiler (React 19) auto-memoizes — does that make these obsolete?" Largely yes for hand-written cases, but you should still understand referential equality because the compiler's whole job is automating it, and legacy code is everywhere. Never claim "useMemo makes it faster" as a blanket truth.

Q11. What does referential equality have to do with re-renders?

ROI: ★★★★ Frequency: High

Short Answer

React compares props and dependencies with Object.is (reference equality for objects). Objects, arrays, and functions created during render are brand-new references every time, even if their contents are identical. That fresh identity is why React.memo children re-render, why useEffect deps "change" unexpectedly, and why memoization exists — to preserve a stable reference across renders.

Detailed Answer

Primitives (string, number, boolean) compare by value, so "open" === "open" is stable across renders for free. But {} !== {} and () => {} !== () => {}. Three places this bites you:

  • React.memo does a shallow prop compare; a new object/function prop defeats it.
  • Dependency arrays re-fire effects/memos when a reference changes (the infinite-loop cause from Q6).
  • Context value — a new provider value object re-renders all consumers (Q12).

Practical guidance: depend on primitives where possible (list [status] not [filters]), and only memoize the references you actually pass across a memo boundary or into a deps array.

Code Example

function Parent({ query }: { query: string }) {
  // New object EVERY render — defeats React.memo on Child
  const style = { padding: 8 };

  // Stable across renders unless `query` changes
  const params = useMemo(() => ({ q: query, page: 1 }), [query]);

  return <Child style={style} params={params} />;
}

Senior Engineer Perspective

This underlies most "why is this re-rendering / looping" questions. The strongest answers reframe the fix as "depend on primitives" rather than "memoize harder" — memoization is a patch over a reference-identity problem, and sometimes the cleaner fix is to not create the object in render at all. Knowing it's Object.is (not ===, which differs for NaN and -0) is a nice precision point.

SECTION 4 - useRef, useContext & useReducer

Q12. What is useRef for beyond accessing the DOM?

ROI: ★★★★★ Frequency: Extremely High

Short Answer

useRef gives you a mutable container — { current: value } — that persists across renders and, crucially, does not trigger a re-render when you change it. Two uses: (1) attaching to a DOM node via the ref attribute, and (2) storing any mutable instance value you want to survive renders without being render output — timer IDs, previous values, the latest state for a stale-closure fix, or a "has this run" flag.

Detailed Answer

The defining property: mutating ref.current is invisible to React's render cycle. Use state when a value should appear on screen and cause a re-render; use a ref when a value is bookkeeping the render doesn't need.

 useStateuseRef
Triggers re-render on change?YesNo
Value persists across renders?YesYes
Read during render?Yes, safelyAvoid — mutation during render is impure
Use forAnything shown in UIDOM nodes, timers, previous values, flags

Because writing a ref doesn't re-render, don't read a ref during rendering to produce output — the UI won't update when it changes. Read/write refs in effects and event handlers.

Code Example

// 1) DOM access — focus an input on mount
function SearchBox() {
  const inputRef = useRef<HTMLInputElement>(null);
  useEffect(() => { inputRef.current?.focus(); }, []);
  return <input ref={inputRef} />;
}

// 2) Mutable instance value — store a timer id (no re-render needed)
function Stopwatch() {
  const timerRef = useRef<number | null>(null);
  const start = () => {
    timerRef.current = window.setInterval(tick, 1000);
  };
  const stop = () => {
    if (timerRef.current) clearInterval(timerRef.current);
  };
  // ...
}

// 3) Previous value pattern
function usePrevious<T>(value: T) {
  const ref = useRef<T>();
  useEffect(() => { ref.current = value; });
  return ref.current; // last render's value
}

Senior Engineer Perspective

The line to say: "state is for what you render; refs are for what you remember." A common trap is candidates using refs to avoid re-renders for values that should be visible — that just breaks the UI. Expect the follow-up on forwardRef/useImperativeHandle for exposing a child's imperative API (though React 19 lets you pass ref as a normal prop, softening forwardRef). Also note initializing a ref lazily with an expensive object should be guarded (if (!ref.current) ref.current = ...) since useRef has no lazy-init form.

Q13. How does useContext work, and what are its re-render pitfalls?

ROI: ★★★★★ Frequency: Extremely High

Short Answer

useContext reads the nearest matching Provider's value and subscribes the component to it. When the provider's value changes (by Object.is), every consumer re-renders — there's no partial subscription. The main pitfalls: passing a fresh object as value every render (re-renders all consumers constantly), and putting too much unrelated state in one context so unrelated updates cascade.

Detailed Answer

Context is a dependency-injection / broadcast mechanism, not a state manager and not a performance optimization. Key behaviors:

  • Consumers re-render when the provider value's reference changes — regardless of whether they use the part that changed.
  • React.memo does not stop a re-render caused by context; the consumer subscribes directly.
  • Providing an inline object (value={{ user, setUser }}) creates a new reference every render, so wrap it in useMemo.

Mitigations for the "everything re-renders" problem: memoize the value; split into multiple contexts (a stable-dispatch context + a value context is a common pattern, since dispatch never changes); or reach for a library (Redux Toolkit, Zustand, Jotai) that supports selector-based subscriptions when the state is large and hot.

Code Example

const AuthContext = createContext<AuthValue | null>(null);

function AuthProvider({ children }: { children: React.ReactNode }) {
  const [user, setUser] = useState<User | null>(null);

  // Memoize so consumers don't re-render on unrelated parent renders
  const value = useMemo(() => ({ user, setUser }), [user]);

  return <AuthContext.Provider value={value}>{children}</AuthContext.Provider>;
}

function useAuth() {
  const ctx = useContext(AuthContext);
  if (!ctx) throw new Error("useAuth must be used within AuthProvider");
  return ctx;
}

Project Example

A theme + auth + locale mega-context re-rendered the entire app on every auth token refresh. Splitting it into separate contexts (and memoizing each value) meant a token refresh only touched components reading auth, cutting render churn dramatically.

Senior Engineer Perspective

The trap answer is "use context to avoid prop drilling and for global state" without acknowledging the all-consumers-re-render cost. Seniors say context is great for low-frequency, widely-read values (theme, current user, locale) but poor for high-frequency state (form fields, cursor position) — that's where selector-based stores win. Bonus: useContext does not support selectors natively, which is precisely the gap external state libraries fill.

Q14. useReducer vs useState — when do you switch?

ROI: ★★★★ Frequency: High

Short Answer

Use useState for independent, simple values. Switch to useReducer when state is complex or when the next state depends on the previous one through many related transitions — multiple sub-values that update together, or state whose updates follow clear "actions". A reducer centralizes update logic in one pure function, making transitions testable and predictable, and the dispatch reference is stable so it's cheap to pass down.

Detailed Answer

Signals it's time to reach for useReducer:

  • Several pieces of state change together in response to one event (e.g., a fetch: set loading, clear error, then set data or error).
  • Update logic is branching and spread across many handlers — a reducer pulls it into one place.
  • You want to log/replay/test transitions, or the next state is a function of the current one in non-trivial ways.

dispatch is guaranteed stable across renders, so passing it through context or to memoized children never causes re-renders — a real advantage over passing many setX functions. The reducer must be a pure function of (state, action).

Code Example

type State = { status: "idle" | "loading" | "done" | "error"; data?: User; error?: string };
type Action =
  | { type: "FETCH" }
  | { type: "SUCCESS"; data: User }
  | { type: "FAILURE"; error: string };

function reducer(state: State, action: Action): State {
  switch (action.type) {
    case "FETCH":   return { status: "loading" };
    case "SUCCESS": return { status: "done", data: action.data };
    case "FAILURE": return { status: "error", error: action.error };
    default:        return state;
  }
}

function UserCard({ id }: { id: string }) {
  const [state, dispatch] = useReducer(reducer, { status: "idle" });

  useEffect(() => {
    dispatch({ type: "FETCH" });
    fetchUser(id)
      .then(data => dispatch({ type: "SUCCESS", data }))
      .catch(e => dispatch({ type: "FAILURE", error: String(e) }));
  }, [id]);
  // render based on state.status
}

Senior Engineer Perspective

Don't say "useReducer is for large state" — the real criterion is how state changes (coordinated transitions / action semantics), not size. A single boolean toggled many ways can justify a reducer; three unrelated values rarely do. Mention that reducer + context is the built-in "Redux-lite" pattern, and that dispatch's stable identity is an underrated performance and ergonomics win.

SECTION 5 - WHEN NOT TO USE useEffect

Q15. When should you NOT use useEffect?

ROI: ★★★★★ Frequency: Extremely High

Short Answer

Don't use an effect to transform data for rendering (compute it during render instead), to handle a user event (put that logic in the event handler), or to reset/adjust state based on props (derive it, or use a key to reset). Effects are for synchronizing with external systems. If no external system is involved, you probably don't need an effect.

Detailed Answer

1. Deriving state — just compute during render

Storing derived data in state and syncing it with an effect creates a redundant render and a source-of-truth split. Compute it inline (memoize only if expensive).

2. Responding to user events — use the handler

"When the user submits, send analytics and POST." That's caused by an event, not by rendering. Put it in onSubmit, not in an effect watching a flag. Effects run because the component rendered, which loses the "why did this happen" information.

3. Resetting state when a prop changes — use a key

To reset all state when, say, userId changes, render the component with key={userId}. React remounts it fresh — no effect that watches the prop and calls a pile of setters.

4. Data fetching — move to a query library (see Q16)

Code Example

// ANTI-PATTERN — deriving state in an effect (extra render, bug-prone)
const [fullName, setFullName] = useState("");
useEffect(() => { setFullName(first + " " + last); }, [first, last]);

// FIX — compute during render
const fullName = first + " " + last;

// ANTI-PATTERN — event logic hidden in an effect
useEffect(() => {
  if (submitted) sendAnalytics(); // why did this fire? unclear
}, [submitted]);

// FIX — do it where the event happens
function handleSubmit() {
  sendAnalytics();
  postForm();
}

Project Example

A form kept a filteredItems state synced from items + search via an effect. It double-rendered and occasionally showed stale results for one frame. Replacing it with a computed const filtered = items.filter(...) during render removed the bug and a whole state variable.

Senior Engineer Perspective

This question separates people who "reach for useEffect reflexively" from those who understand it. The mental test the React docs teach: "Is this caused by a particular event, or by the component simply being displayed/synchronized?" Event → handler. Display/external sync → effect. Deriving state in effects is the single most common React anti-pattern, and naming the key-reset trick signals real fluency.

Q16. How do you fetch data with hooks, and why is useEffect the wrong long-term home for it?

ROI: ★★★★★ Frequency: Extremely High

Short Answer

You can fetch in useEffect — with an AbortController, an ignore flag to drop stale responses, loading/error state, and re-fetch on dependency change. But doing it by hand means re-implementing caching, deduplication, retries, race-condition handling, and revalidation in every component. That's why production apps move fetching to a data library like TanStack Query (React Query) or SWR, or to server components / a router loader.

Detailed Answer

The problems with raw effect-based fetching:

  • Race conditions — a slow request for the old id can resolve after the new one; you need to ignore stale responses.
  • No caching or dedup — two components asking for the same data fire two requests.
  • No revalidation — stale-while-revalidate, refetch-on-focus, polling all become manual.
  • Waterfalls — fetching in child effects after parents mount serializes requests.

TanStack Query solves all of these with a cache keyed by queryKey, automatic dedup, background refetch, and built-in loading/error state. The enabled option cleanly handles conditional fetching (Q3). In app-router / RSC setups, fetching moves to the server (or a route loader) entirely, and effects aren't involved.

Code Example

// Hand-rolled — note the race-condition guard and cleanup
function useUser(id: string) {
  const [state, setState] = useState<{ loading: boolean; data?: User }>({ loading: true });

  useEffect(() => {
    let ignore = false;               // guard against stale responses
    const controller = new AbortController();
    setState({ loading: true });

    fetch(`/api/users/${id}`, { signal: controller.signal })
      .then(r => r.json())
      .then(data => { if (!ignore) setState({ loading: false, data }); });

    return () => { ignore = true; controller.abort(); };
  }, [id]);

  return state;
}

// Production — TanStack Query handles cache, dedup, retries, race conditions
function useUserQuery(id: string) {
  return useQuery({
    queryKey: ["user", id],
    queryFn: ({ signal }) => fetch(`/api/users/${id}`, { signal }).then(r => r.json()),
    enabled: !!id,
  });
}

Senior Engineer Perspective

Interviewers want to see you know the manual version's pitfalls (especially the race condition — this is the classic follow-up) and that you wouldn't ship it. Saying "I'd reach for TanStack Query / SWR, or fetch on the server with RSC / a router loader" shows current, production-grade judgment. The React docs themselves recommend against manual effect fetching for exactly these reasons. A red flag is defending hand-rolled fetching as "simpler" without mentioning caching, dedup, or races.

Q17. What's the difference between useEffect deps missing vs. an empty array vs. no array?

ROI: ★★★ Frequency: Medium

Short Answer

No array at all → the effect runs after every render. An empty array [] → runs only once on mount (cleanup on unmount). A populated array [a, b] → runs on mount and whenever a listed value changes. "Missing deps" usually means you have an array but left out a value the effect actually uses — that causes stale closures, and the exhaustive-deps lint rule flags it.

Detailed Answer

FormBehaviorTypical use
no arrayEvery renderRare; usually a bug
[]Mount only + unmount cleanupOne-time setup that reads nothing reactive
[a, b]Mount + when a or b changesSync with specific reactive values

The trap is using [] while the effect reads props/state — it "works" on mount but silently uses stale values forever (Q5). The lint rule exists to force you to either list every used reactive value or restructure (functional updater, ref, or move the value out). Don't blind-disable it; treat a warning as "you have a stale-closure or reference-identity issue to resolve."

Senior Engineer Perspective

The nuance seniors add: an empty array isn't "run once because I want it once" — it's a claim that the effect depends on nothing reactive. If that claim is false, you have a bug, not a shortcut. The right way to "run truly once with fresh values" is often a functional updater or a ref, not lying to the deps array.

Q18. How do you share stateful logic between components without duplication?

ROI: ★★★★ Frequency: High

Short Answer

Write a custom hook — a function named useSomething that calls other hooks and returns values. It lets you reuse logic (subscriptions, form handling, fetching) without sharing state: each component that calls the hook gets its own independent state. Custom hooks replaced the old render-props and higher-order-component patterns for logic reuse.

Detailed Answer

A custom hook is just a function that (a) starts with use so the linter enforces the Rules of Hooks inside it, and (b) uses one or more built-in hooks. Crucially, extracting logic into a hook does not share state between callers — every call site gets a fresh, isolated instance of that hook's state. What's shared is the behavior, not the data.

Good custom-hook candidates: useLocalStorage, useDebounce, useMediaQuery, useOnlineStatus, form logic, and wrappers around a data layer. Keep them focused and return a stable, ergonomic API.

Code Example

function useDebounce<T>(value: T, delay = 300): T {
  const [debounced, setDebounced] = useState(value);

  useEffect(() => {
    const id = setTimeout(() => setDebounced(value), delay);
    return () => clearTimeout(id); // cancel on change/unmount
  }, [value, delay]);

  return debounced;
}

// Each component gets its OWN debounced state — logic shared, state isolated
function Search() {
  const [text, setText] = useState("");
  const debounced = useDebounce(text, 400);
  useEffect(() => { if (debounced) runSearch(debounced); }, [debounced]);
  return <input value={text} onChange={e => setText(e.target.value)} />;
}

Senior Engineer Perspective

The most common misconception is that a custom hook shares state across components — it doesn't; it shares logic, and each caller has independent state. If you need shared state, that's context or an external store, not a plain custom hook. Interviewers also probe naming: the use prefix isn't cosmetic — it's what lets the linter and React apply the Rules of Hooks. Mentioning that custom hooks superseded HOCs/render props for cross-cutting logic dates your knowledge to modern React.
