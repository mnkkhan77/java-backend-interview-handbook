CHAPTER 80 — REFLECTION

Volume 4 — AI Agents & MCP · Chapter 3 of 10

Planning (Chapter 79) gave your agent the ability to decompose a goal into an ordered sequence of steps before acting. But a plan is a bet made with incomplete information, and the first attempt at executing any step of it — writing the SQL, drafting the email, calling the tool — is frequently wrong in some fixable way. Reflection is the discipline of teaching an agent to notice that its own output is flawed, articulate why, and use that critique to produce a better second attempt, all without a human in the loop. It is the mechanism that turns a single-shot generator into something that behaves like it is capable of self-correction.

1. MOTIVATION

Every engineer who has used an LLM for anything non-trivial has lived through this exact sequence: ask for code, get code that almost compiles; ask for a summary, get a summary that misses the one detail that mattered; ask for a plan, get a plan with a step that silently assumes a precondition that isn't true. The instinctive fix, the one every beginner reaches for first, is to paste the broken output back in and say "that's wrong, try again" — and it usually works noticeably better than the first attempt. That single, almost embarrassingly simple observation is the entire seed of this chapter: a model re-examining and criticizing its own prior output, then producing a revision, reliably outperforms a model asked to get it right in one shot.

This matters enormously for the reader's journey toward production AI Engineering because it is the difference between an agent that is a novelty and an agent you can trust to run unattended. A planning system (Chapter 79) tells an agent what to do next; it says nothing about whether what the agent just did was any good. Without reflection, an agent architecture is purely open-loop: generate, act, move on, and hope. Every real production agent — a coding agent that must not ship code with a syntax error, a customer-support agent that must not fabricate a refund policy, a data-extraction agent that must not silently drop a required field — needs a closed loop where the system can catch its own mistakes before they become the user's problem or, worse, an irreversible side effect (Chapter 79's discussion of tool actions and the ReAct-style act/observe cycle becomes directly relevant here).

Reflection is also the conceptual bridge into two topics later in this volume: Agent Memory (Chapter 81), because a reflective agent needs somewhere to store the lessons it draws from its own mistakes so it doesn't repeat them within the same task, and Multi-Agent Orchestration (later in this volume), because one of the cleanest ways to implement reflection in production is to split "do the work" and "judge the work" into two distinct agent roles that talk to each other. If you only take one idea from this chapter into the rest of the book, take this: self-correction is not free intelligence, it is an engineered control loop, and like every control loop you have built in distributed systems, it has a sensor (the critique), an actuator (the revision step), and — critically — it needs a termination condition, or it will spin forever burning tokens.

2. HISTORICAL BACKGROUND

2.1 Self-Correction Long Before LLMs

The idea that a system should check and improve its own output did not begin with language models — it is one of the oldest ideas in engineering. Control theory has used feedback loops (measure the error, correct toward the target) since long before computing existed. In software specifically, you already know several ancestors of this pattern: a compiler's multi-pass optimization, where a first pass produces naive code and later passes rewrite it against measured properties; test-driven development, where a failing test is the "critique" that drives the next code change; and code review itself, where a second party (or the same author, later, with fresh eyes) reads a draft and flags problems before it ships. All of these share the same skeleton — produce, evaluate, revise — that this chapter formalizes for LLM-based agents.

2.2 Chain-of-Thought and Self-Consistency (2022)

The first LLM-era precursor to reflection was not reflection at all — it was chain-of-thought prompting, the discovery that asking a model to "think step by step" before giving a final answer measurably improved accuracy on reasoning tasks. This established something important for everything that follows: a model's first token of output does not have to be its best possible answer, and spending more inference-time computation on intermediate text before committing to a final answer buys real accuracy. Shortly after, self-consistency pushed this further: generate several independent reasoning chains for the same question and take the majority answer. This was an early, crude form of self-evaluation — not "is this answer right?" but "do independent attempts agree?" — and it is the direct ancestor of the "generate multiple candidates, pick the best" family of reflection strategies covered later in this chapter.

2.3 Self-Refine and Reflexion (2023)

Two papers, released within months of each other in 2023, gave this chapter its name and its core mechanism. Self-Refine showed that a single LLM, using nothing but prompting, could act as its own critic: generate an output, prompt the same model to critique that output against the task requirements, then prompt it again to produce a revised output incorporating the critique — repeated for a small, fixed number of rounds. No fine-tuning, no external reward model, no additional training data. The result was a consistent quality improvement across tasks ranging from code generation to dialogue response generation, purely from this generate-critique-revise loop.

Reflexion (Shinn et al., 2023) extended the idea specifically to agents operating over multiple steps in an environment, and coined the framing that has stuck ever since: "verbal reinforcement learning." Instead of updating numeric weights the way traditional reinforcement learning does after a failure (the mechanism covered mathematically in earlier chapters on gradient descent), Reflexion has the agent write a natural-language reflection about what went wrong on a failed attempt — "I called the search tool with too broad a query and got irrelevant results; next time I should narrow the query using the specific entity name" — and stores that reflection in a memory buffer that gets included in the prompt of the next attempt. The "learning signal" is a sentence in English, not a gradient. This is a profound shift for engineers coming from classical ML: the entire adaptation mechanism runs at inference time, in-context, with zero weight updates.

2.4 Grounded Critique and Tool-Verified Reflection (2023–present)

The failure mode discovered quickly after Self-Refine and Reflexion became popular was that an LLM critiquing its own output with nothing but its own judgment is unreliable — it can be overly agreeable ("this looks good!" on flawed output), or it can "correct" something that was already right into something wrong. The field's response was to ground the critique in something external and checkable wherever possible: run the generated code against a unit test suite and feed back the actual stack trace; run the generated SQL against the database and feed back the actual error or row count; ask a retrieval system whether a claimed fact is supported by a document. This is the same instinct that produced Retrieval-Augmented Generation (Volume 3) applied to self-critique — trust a verifiable signal over the model's own opinion whenever one is available. This grounded/ungrounded distinction is the single most important engineering decision in this entire chapter, and Section 5 builds the internal mechanism around it directly.

Why this history matters to you as an engineer: notice the trajectory — every generation of this idea moved critique from "purely inside the model's head" toward "grounded in something outside the model that can actually be checked." That is the same trajectory the whole book series follows: raw model output is never trusted alone; it is progressively grounded by retrieval (Volume 3), tools (Chapter 79 and this chapter), and, later, guardrails and evaluation (Volume 5). Reflection without external grounding is a useful but bounded technique — remember that when you design your own agent's critique step.

3. PROBLEM STATEMENT

Strip away the research history and state the engineering problem precisely:

Given a single-pass generation from an LLM that has some fixed, non-trivial probability of being wrong, incomplete, or off-requirement, build a mechanism that detects the flaw and produces a corrected version — using bounded, predictable compute — without requiring a human to review every output.

Three constraints inside that sentence are easy to skip past and each one drives a real design decision later in this chapter:

  • "has some fixed, non-trivial probability of being wrong" — this is not a hypothesis, it is the starting assumption inherited directly from everything the "What Is Intelligence" and "Hallucinations" chapters established: an LLM is correct on average, not on every instance. Reflection exists specifically because that baseline error rate is real and worth spending extra compute to reduce.
  • "using bounded, predictable compute" — a reflection loop that is allowed to run forever is not a solution, it is a new failure mode (a runaway cost and latency bug). Every real reflection implementation must answer, explicitly, "how many rounds, at most, and what stops it early?"
  • "without requiring a human to review every output" — if a human has to check every response anyway, you don't need reflection, you need a review UI. Reflection is specifically the technique for closing the loop automatically, reserving human review for the cases the automated loop cannot resolve with confidence.

It is worth being explicit about what reflection is not, because the two are constantly confused in casual usage. Planning (Chapter 79) decides a sequence of future actions before any of them run. Reflection evaluates an action or output after it exists — whether that's after the entire task, after a single tool call, or after a single draft answer — and feeds a judgment back into what happens next. A sophisticated agent typically has both: a plan for what to attempt, and a reflection step wrapped around each attempt (or around the whole run) that can revise the plan, retry a step, or escalate to a human when the attempt fails its own check.

4. THEORY

4.1 The Generate–Critique–Refine Loop

Hold one picture in your head for the rest of this chapter: reflection is a three-role loop, and understanding it as three roles (even when one physical model plays all three) is the key mental model.

RoleJobAnalogy From Your Engineering Life
Actor / GeneratorProduces a candidate output or takes an actionA developer writing a first draft of a pull request
Critic / EvaluatorJudges the candidate against the task's requirements and produces a specific, actionable critiqueA code reviewer leaving inline comments, not just "LGTM" or "no"
RefinerProduces a new candidate incorporating the critiqueThe same developer pushing a follow-up commit addressing review comments

The critical design insight is that the Critic's job is not to output a single bit ("good" or "bad") — a bare pass/fail signal gives the Refiner nothing to work with and tends to produce shallow, cosmetic edits. A useful critique names what specifically is wrong and, ideally, why, the same way a good code review comment says "this will throw an NPE if user is null, add a check" rather than "this is bad." Section 5 turns this into a concrete step-by-step mechanism.

4.2 Grounded vs. Ungrounded Reflection

This is the single most consequential distinction in the whole topic, introduced historically in Section 2 and worth stating as a formal mental model now:

  • Ungrounded reflection: the critic is the same (or another) LLM, judging purely from its own internal sense of quality, with no external source of truth to check against. Useful for style, clarity, completeness against stated instructions, tone — anything where "good" is a matter of judgment the model is plausibly well-calibrated about because it has seen enormous amounts of well-written and poorly-written text.
  • Grounded reflection: the critique comes from, or is checked against, something outside the model's own opinion — a unit test result, a compiler error, a schema validator, a retrieved document, a calculator, a database query result. Useful, and strongly preferred, for anything with an objectively checkable answer — code correctness, factual claims, numeric computation, adherence to a schema.

A useful analogy: ungrounded reflection is a writer re-reading their own essay and improving the phrasing; grounded reflection is a writer's essay being run through a spell-checker and a fact-checking database. Both make the essay better, but only one of them can actually catch a factually wrong date. Production reflection systems almost always want grounded critique wherever a verifier can exist, and fall back to ungrounded, judgment-based critique only where no verifier is possible.

4.3 Reflection Granularity: Where in the Loop Does It Happen?

Reflection is not one fixed point in an agent's execution — it can be inserted at multiple granularities, and production systems often use more than one simultaneously:

  • Within a single response — draft an answer, critique it, revise it, then return only the final version to the user (this is Self-Refine's original scope).
  • After a single tool call — an agent calls a tool, observes the result, and reflects on whether the result actually satisfies what the current plan step needed before deciding to proceed, retry with different arguments, or replan (this is the "Observation" half of the ReAct loop mentioned in Chapter 79, now given a formal evaluation step).
  • After an entire task attempt — the agent completes a multi-step task, an evaluator determines success or failure against the original goal, and — if it failed — a Reflexion-style verbal lesson is written and carried into a fresh attempt at the same task.

5. INTERNAL WORKING

Here is the mechanism made concrete, as a sequence of steps an engineer could actually implement and reason about at the edges.

  1. Generate a candidate. The Actor produces an output — a draft answer, a piece of code, a tool call, an entire task attempt. This step is identical to a normal, non-reflective agent call.
  2. Select a critique mechanism. Before critiquing, decide: is there a grounded verifier available (run the code, execute the query, validate against a schema, check a retrieved source)? If yes, run it and capture its raw output (a stack trace, a validation error, a mismatch). If no verifier exists, fall back to prompting a critic (the same model or a separate one) with the original task requirements and the candidate, asking specifically for concrete defects, not a vibe check.
  3. Produce a structured critique. Whatever the source, normalize the critique into something the next step can act on deterministically: at minimum, a pass/fail verdict, and if failed, a list of specific issues. This is exactly the kind of thing you constrain with structured output (covered in Volume 2) rather than leaving as free text you then have to re-parse with another LLM call.
  4. Decide: stop, retry, or escalate. This is the step most naive implementations skip, and it is the one that prevents runaway loops. The decision needs at least three explicit exit conditions checked every round: (a) the critique passed — return the current candidate; (b) a maximum iteration count has been reached — stop and either return the best candidate seen or escalate to a human/fallback; (c) the critique this round is not meaningfully different from the critique last round — the loop has stalled and continuing will not help, so stop and escalate rather than burn more tokens chasing the same unresolved issue.
  5. Refine. If continuing, the Refiner receives the original task, the previous candidate, and the structured critique, and produces a new candidate specifically addressing the named issues — not a full restart from a blank prompt, which tends to lose whatever the previous attempt got right.
  6. Loop back to step 2 with the new candidate, up to the bound set in step 4.

Now the edge cases a senior engineer is expected to have thought through:

  • The critic is wrong. An ungrounded critic can flag a correct answer as flawed (false positive) or wave through a genuinely broken one (false negative). This is why grounded critique is preferred whenever available, and why ungrounded critique should be treated as a heuristic signal, not ground truth — never wire an ungrounded critic directly into an action with irreversible side effects without an additional check.
  • Sycophantic self-agreement. When the same model plays both Actor and Critic, it has an observed tendency to rubber-stamp its own work, especially as conversation history grows and the model has effectively "committed" to its earlier answer. Using a separate critic call with a deliberately adversarial system prompt ("find every flaw, do not be agreeable") measurably reduces this; using a genuinely different model as critic reduces it further.
  • Oscillation. A refine step can "fix" issue A by reintroducing issue B that a previous round already fixed, and the loop bounces between two bad states indefinitely. The stall-detection check in step 4(c) — comparing this round's critique to the previous round's — is the direct defense against this.
  • Cost blowup. Every round is at minimum one extra full model call (critique) plus one more (refine) — a naive 3-round reflection loop can 5-7x the token cost and latency of a single call. Section 12 treats this quantitatively.
  • Reflecting on the wrong thing. A critique that focuses on surface issues (grammar, formatting) while missing the substantive one (the SQL query joins the wrong table) gives false confidence. This is why structured, requirement-specific critique prompts ("does this satisfy requirement 3 exactly, yes or no, and why") outperform generic "review this" prompts.

6. MATHEMATICS — THE INTUITION, KEPT LIGHT

Reflection does not require new mathematics beyond what earlier chapters already gave you — there are no new gradients or loss functions here, because no weights are updated during reflection. That single fact is worth dwelling on: reflection is entirely an inference-time technique, whereas the "dial-turning" mechanism from the Neural Networks and "What Is Intelligence" chapters describes training-time learning. The useful framing is closer to search and optimization than to gradient descent.

Think of the space of all possible outputs for a task as a landscape again, exactly as in the loss-landscape picture from earlier chapters — except now the "downhill direction" at any point is not computed by calculus, it is estimated by the critic looking at the current candidate and saying, in effect, "move this way." Each round of reflection is one step of a noisy, LLM-guided local search: start from an initial candidate, use a (possibly noisy or wrong) critique to estimate an improving direction, take a step, repeat. This is closer in spirit to hill-climbing with a noisy oracle than to gradient descent — and like any local-search algorithm, it can plateau, oscillate, or get stuck, which is exactly why Section 5's stall-detection and iteration-bound logic exist.

One quantity is worth being precise about, because it directly drives cost modeling in Section 12: if a single generation has probability p of being acceptable, and each reflection round independently has some probability q of converting an unacceptable output into an acceptable one (a simplification — real rounds are correlated, not independent — but useful for intuition), then after n rounds the probability the loop has NOT yet produced an acceptable output shrinks roughly geometrically: (1 - p) × (1 - q)^n. This is why even a modest per-round improvement probability compounds into a meaningfully lower end-to-end failure rate after two or three rounds — and also why rounds beyond three or four typically show steeply diminishing returns, since (1-q)^n is already small by then and the remaining failures tend to be the hard cases reflection alone cannot fix.

Two production details that only show up once you deploy this for real: first, the escalation path is not optional — a reflection loop with no human-review fallback simply turns a visible failure into a silent one, since it will eventually hit its round limit and must return something. Second, every round's critique and decision should be logged as structured, queryable data (not just free text buried in a trace), because the pattern of what your agent's critic keeps flagging is one of the highest-signal sources for improving your prompts, your tool set, and your retrieval quality over time — it is, in effect, a continuously generated bug report about your own system.

9. JAVA / SPRING PERSPECTIVE

Spring AI does not ship a class literally named Reflection — this is a design pattern you compose from the primitives Volume 2 already introduced, and recognizing that composition is the actual skill being tested when this topic comes up in a Spring AI context.

The natural building block is Spring AI's Advisor abstraction — the same AOP-flavored interceptor mechanism used for memory and logging around a ChatClient call. A reflection loop is most cleanly implemented as an Advisor (or a small chain of them) that wraps the underlying call, inspects the response, and — if it fails a check — re-invokes the chain with an augmented prompt containing the critique, up to a configured bound: 

@Component
public class SelfCritiqueAdvisor implements CallAdvisor {

    private final ChatClient criticClient;
    private static final int MAX_ROUNDS = 2;

    public SelfCritiqueAdvisor(ChatClient.Builder builder) {
        // A separate, adversarially-prompted client acting purely as critic
        this.criticClient = builder
            .defaultSystem("""
                You are a strict reviewer. Given a task and a candidate answer,
                respond ONLY with structured JSON: {"pass": boolean, "issues": [...]}.
                Do not be agreeable. Find concrete, specific defects if they exist.
                """)
            .build();
    }

    @Override
    public ChatClientResponse adviseCall(ChatClientRequest request, CallAdvisorChain chain) {
        ChatClientResponse response = chain.nextCall(request);
        String candidate = response.chatResponse().getResult().getOutput().getText();

        for (int round = 0; round < MAX_ROUNDS; round++) {
            Critique critique = criticClient.prompt()
                .user(u -> u.text("Task: {task}\nCandidate: {candidate}")
                            .param("task", request.prompt().getContents())
                            .param("candidate", candidate))
                .call()
                .entity(Critique.class);           // structured output (Volume 2)

            if (critique.pass()) {
                return response;                   // grounded stop condition
            }

            // Refine: re-run the original chain with the critique appended
            ChatClientRequest refined = request.mutate()
                .prompt(p -> p.augmentUserMessage(msg ->
                    msg + "\n\nPrior attempt had issues: " + critique.issues()
                          + "\nProduce a corrected version."))
                .build();
            response = chain.nextCall(refined);
            candidate = response.chatResponse().getResult().getOutput().getText();
        }
        return response; // budget exhausted — caller decides escalation policy
    }
}

record Critique(boolean pass, java.util.List<String> issues) {}

Notice how directly this maps onto Section 5's mechanism: the criticClient is a deliberately separate ChatClient instance (mitigating the sycophancy problem from Section 5), the critique is captured as a typed record via Spring AI's structured-output support rather than parsed by hand from free text, and MAX_ROUNDS is the explicit, code-level answer to "how many rounds, at most" that Section 3 insisted every implementation must have. For the grounded variant of reflection — running actual code or a real query as the verifier instead of an LLM critic — the same Advisor shape applies, except the "critic" step is a plain Java call to your test runner, your SQL validator, or a tool defined through Spring AI's tool-calling support (covered in Volume 2 and extended for agents in this volume), with the raw execution error fed back as the "issues" text instead of an LLM's opinion. Whenever a verifier can be expressed as ordinary, deterministic Java code, prefer it — it is cheaper, faster, and strictly more trustworthy than another model call.

10. BEST PRACTICES

  • Prefer grounded critique over model-judged critique wherever a verifier can exist. If the output is code, run it. If it is a claim, check it against retrieved evidence. Reserve LLM-as-critic for genuinely subjective dimensions — tone, clarity, completeness against open-ended instructions.
  • Always set a hard maximum round count, and treat it as a first-class configuration value, not a magic number buried in a prompt — it directly determines your worst-case latency and cost per request.
  • Use a structurally separate critic — a different system prompt at minimum, ideally a different (even cheaper) model — to reduce the self-agreement bias described in Section 5.
  • Make the critique structured and specific, not a free-text vibe check. Force the critic to answer against explicit, itemized requirements ("does this satisfy constraint 2? yes/no, why") so the refiner has something concrete to act on.
  • Detect stalls, not just round limits. If round n's critique repeats round n-1's unresolved issue, stop and escalate rather than continuing to spend tokens on a loop that isn't converging.
  • Log every round. The critique history is a diagnostic asset — treat it the way you would treat structured application logs, not disposable scratch text.
  • Always define an escalation path for when the loop exhausts its budget without passing — returning the best-effort output with an explicit low-confidence flag, or routing to a human queue, is not optional in a production system.

11. COMMON MISTAKES

  • Letting the same model critique itself with the same conversational context, then treating a pass as reliable. Self-agreement bias (Section 5) is well documented; a critique from the same context that produced the answer is the weakest form of evidence you can act on.
  • Unbounded reflection loops. "Keep refining until it's good" with no round cap is a latent incident — one edge case where the critic never says pass turns into an unbounded-cost, unbounded-latency request.
  • Treating a bare pass/fail critique as sufficient. Without specific, itemized issues, the refine step has nothing concrete to act on and tends to make cosmetic changes rather than fixing the actual defect.
  • Reflecting on everything, uniformly. Applying a 3-round reflection loop to every single request, including trivial ones a base model already handles well, multiplies cost and latency for no measurable quality gain — reflection should be applied selectively, gated by task risk or a cheap initial confidence signal.
  • Confusing reflection with planning. Some teams build an elaborate "critique" step that is really just re-planning in disguise (deciding what to do differently) without ever actually evaluating whether the last output met the requirement — conflating the two makes both harder to debug independently.
  • No stall detection. Oscillating between two flawed states for the full round budget wastes the entire cost of reflection while producing no improvement — always compare successive critiques, not just check the round counter.

12. PERFORMANCE CONSIDERATIONS

Reflection is a direct, mechanical multiplier on cost and latency, and it needs to be budgeted the same way you would budget retries against a slow downstream service.

  • Token cost scales linearly with rounds. A single-pass call costs roughly one generation's worth of tokens; a reflection loop with n rounds costs, at minimum, n generations plus n critiques — a 2-round grounded reflection can easily be 3-4x the token cost of the single-pass baseline, and an ungrounded loop with a separate critic model can be higher still.
  • Latency compounds sequentially unless you specifically parallelize independent parts (e.g., generating several candidates concurrently and critiquing them in parallel, a variant closer to self-consistency than to iterative refinement). A naive sequential 3-round loop can turn a 2-second response into an 8-10 second one — unacceptable for a synchronous user-facing endpoint, often fine for an asynchronous background agent task.
  • Grounded verifiers are usually far cheaper than LLM critics. Running a unit test or a schema validator costs milliseconds of CPU, not another model call — this is a strong practical reason, independent of accuracy, to prefer grounded critique whenever it is available.
  • Diminishing returns set in fast. As the geometric intuition in Section 6 suggested, most of the achievable quality gain typically shows up in the first one or two rounds; a fixed budget of 2-3 rounds is a reasonable default starting point to tune from, not an arbitrary number.
  • Gate reflection by risk, not uniformly. Cheap, low-stakes generations (a casual chat response) rarely justify the cost of a full reflection loop; high-stakes ones (generated code that will run, a financial calculation, an action with a side effect) usually do. Building this gating logic into the orchestrator is itself a cost-optimization decision worth making explicit, mirroring the "match model size to task difficulty" principle from earlier in the series.

13. SECURITY CONSIDERATIONS

Reflection's security surface is narrower than, say, tool calling or retrieval, but it is not empty, and it is honest to say where it helps and where it offers a false sense of safety.

  • Reflection is not a defense against prompt injection. If untrusted content (a retrieved document, a tool result) manipulated the actor's output, an ungrounded critic reading the same poisoned context can be manipulated the same way — it has no special immunity. Grounded, execution-based verification (does the generated SQL actually only touch permitted tables, does the generated code pass a security linter) is meaningfully more robust here than another LLM opinion, because it checks an objective property rather than asking a model already exposed to the same untrusted input for its judgment.
  • The critique channel itself can leak sensitive intermediate reasoning. Reflection traces — the "issues" text, the verbal lessons stored à la Reflexion — often contain more candid, less filtered content than the final output (an internal draft may reference sensitive data more freely than the polished response). If these traces are logged, cached, or ever surfaced to end users for transparency, apply the same data-handling and redaction discipline you would to any other log containing potentially sensitive content.
  • Do not treat self-verification as sufficient for security-critical or destructive actions. An agent that reflects on whether a generated database migration "looks correct" is still not a substitute for real authorization checks, dry-run execution, and human approval gates for irreversible actions — reflection reduces the rate of accidental mistakes, it is not an access-control mechanism, and it should never be the only safeguard placed in front of a genuinely dangerous tool call.

14. INTERVIEW QUESTIONS

JUNIORQ1. In one sentence, what is "reflection" in the context of an AI agent?

ROI: ★★★★★ · Frequency: Extremely High

Reflection is the pattern of an agent evaluating its own prior output or action, producing a specific critique of what is wrong with it, and using that critique to generate an improved attempt, typically repeated for a bounded number of rounds.

JUNIORQ2. How is reflection different from planning?

ROI: ★★★★☆ · Frequency: High

Planning decides a sequence of future actions before any of them are executed. Reflection evaluates an action or output after it has already been produced and decides whether to accept it, retry it, or revise it. A mature agent typically uses both: a plan to decide what to attempt, and reflection wrapped around each attempt (or the whole run) to catch and correct mistakes.

MIDQ3. What is the difference between "grounded" and "ungrounded" reflection, and when would you use each?

ROI: ★★★★★ · Frequency: Extremely High

Grounded reflection checks the candidate output against an external, verifiable signal — running tests, executing a query, validating a schema, checking retrieved evidence. Ungrounded reflection relies purely on a model's own judgment with nothing external to check against. Grounded reflection should be preferred whenever an objective verifier can exist (code correctness, factual claims, numeric results); ungrounded reflection is appropriate for genuinely subjective qualities like tone, clarity, or open-ended completeness where no automated verifier is possible.

MIDQ4. Why is it risky to let the same model, in the same context, both generate an answer and critique it?

ROI: ★★★★☆ · Frequency: High

The model has an observed tendency toward self-agreement or sycophancy — having just produced an answer, it is biased toward validating rather than genuinely challenging it, especially within the same conversational context. Mitigations include using a structurally separate critic call with an explicitly adversarial system prompt, using a different model entirely as the critic, and preferring grounded, execution-based verification wherever possible instead of relying on the model's self-assessment.

SENIORQ5. Design a bounded reflection loop for a code-generation agent. What are the explicit stop conditions, and why does each one matter?

ROI: ★★★★★ · Frequency: High at senior level

At minimum three stop conditions: (1) the grounded verifier — running the generated code against the actual test suite or compiler — passes, in which case return immediately; (2) a hard maximum round count is reached, bounding worst-case latency and cost, after which the loop returns the best candidate seen with a flagged confidence marker rather than looping indefinitely; (3) stall detection — if the current round's failure output (e.g., the same stack trace or the same failing test) is materially unchanged from the previous round, stop early and escalate, because continuing is unlikely to converge and will only burn additional tokens. Preferring the compiler/test suite as the verifier over an LLM critic is important here specifically because code correctness is objectively checkable, making grounded reflection both cheaper and more trustworthy than a model's opinion.

Interview Gold Point: Explicitly say that an unbounded "keep refining until it's good" loop is not a partial solution but a latent production incident — it converts a rare edge case where the critic never passes into unbounded cost and latency. Naming stall detection separately from the round-count cap (two different failure modes, two different defenses) is what distinguishes a senior answer from a mid-level one here.
SENIORQ6. How would you decide, per request, whether to run a reflection loop at all, given that it multiplies cost and latency?

ROI: ★★★★☆ · Frequency: Medium-High at senior level

Gate reflection by the risk and reversibility of the task rather than applying it uniformly: low-stakes, easily-reversible outputs (casual conversational responses) rarely justify the added cost, while high-stakes or side-effecting actions (generated code that will execute, financial calculations, database-mutating tool calls) usually do. This can be implemented as an explicit risk classification step in the orchestrator, or by using a cheap initial confidence heuristic (e.g., the model's own stated uncertainty, or a lightweight grounded check) to decide whether the full reflection loop is warranted, keeping the common case fast and reserving the multiplied cost for cases where correctness matters most.

STAFFQ7. A team reports their reflection loop "usually improves quality but occasionally makes correct answers worse." Diagnose likely causes and propose a fix.

ROI: ★★★★★ · Frequency: High at staff level

Likely causes: an ungrounded critic hallucinating defects in an already-correct answer (false positives from Section 5), causing an unnecessary and potentially harmful revision; or oscillation, where the refine step "fixes" a flagged issue by reintroducing a different problem an earlier round had already resolved. The fix has two parts: first, wherever a grounded verifier can exist, replace or supplement the ungrounded critic with it, since an objective check cannot flag a correct answer as wrong the way a model's opinion can; second, add stall/regression detection that compares each new candidate not just against the immediately preceding critique but tracks whether previously-resolved issues have resurfaced, and if so, stops the loop and returns the best-scoring candidate across all rounds rather than blindly trusting the final one. This also argues for keeping every candidate and its critique in the loop's history, not just the most recent one, so "best of all rounds" is actually computable.

STAFFQ8. How does reflection interact with agent memory (the next chapter), and why does Reflexion specifically frame its correction signal as "verbal reinforcement learning"?

ROI: ★★★★☆ · Frequency: Medium at staff level

Reflexion writes its critique of a failed attempt as a natural-language lesson and stores it in a memory buffer that is included in the prompt context of the agent's next attempt at the same or a similar task — the "learning" happens entirely in-context, at inference time, with zero weight updates, which is what "verbal" contrasts against traditional reinforcement learning's numeric gradient updates. This only works, however, if there is somewhere durable to put that lesson so it survives past the current call — which is precisely the problem agent memory (Chapter 81) solves. Without a memory mechanism, every reflection is scoped to a single task attempt and its lessons evaporate the moment the context window is cleared or the task ends; with memory, an agent can accumulate reusable, cross-task lessons from its own past mistakes, which is what starts to make repeated agent behavior improve over time without any fine-tuning.

16. SUMMARY

  • Reflection is the generate–critique–refine loop that lets an agent detect and correct flaws in its own output without requiring a human to review every response — it complements planning (Chapter 79) rather than replacing it.
  • The most important design distinction is grounded critique (checking output against an external, verifiable signal like tests, execution, or retrieval) versus ungrounded critique (a model's own judgment) — prefer grounded wherever a verifier can exist.
  • A production reflection loop must have explicit, bounded stop conditions: pass, maximum rounds, and stall detection — an unbounded loop is a latent cost and latency incident, not a solution.
  • Reflection happens entirely at inference time with no weight updates; Reflexion's "verbal reinforcement learning" framing captures this — the correction is a stored natural-language lesson, not a gradient.
  • In Spring AI, reflection is naturally implemented as a Advisor (or chain of them) wrapping a ChatClient call, using a structurally separate critic client and Spring AI's structured-output support to keep the critique typed and actionable rather than free text.
  • Reflection reduces the rate of accidental mistakes but is not a security control — it offers little defense against prompt injection and must never be the sole safeguard in front of an irreversible or destructive tool action.
