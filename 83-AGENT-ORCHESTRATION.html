CHAPTER 83 — AGENT ORCHESTRATION

Volume 4 — AI Agents & MCP · Chapter 6 of 10

The Tool Usage chapter gave a model the ability to call a single function and read back a result — one request, one tool call, one response. Real work is rarely one call deep: an agent that books a trip must search flights, check a calendar, compare prices, and confirm availability, deciding after every step what to do next based on what it just learned. Agent Orchestration is the discipline of building the control loop that makes that sequence of decisions safe, bounded, observable, and correct — the difference between a demo that calls a tool once and a system trusted to run unattended for minutes or hours.

1. MOTIVATION

Every chapter so far in this volume has been building toward a single moment: the moment where a model stops answering one question and starts running a process. Tool Usage taught you how a model can request that a function be executed on its behalf. But a single tool call is still, structurally, a request/response pair — the model asks, your code answers, the model finishes. The moment you need the model to call a tool, look at the result, decide whether that result is good enough, and call another tool (possibly a different one, possibly the same one with different arguments, possibly several in parallel) — you have left the world of a single function call and entered the world of a loop with judgment embedded in it. That loop is what "orchestration" means in this chapter, and it is the mechanism underneath every product you have heard described as an "AI agent": a coding assistant that edits multiple files and re-runs tests until they pass, a research agent that searches, reads, and re-searches until it has enough evidence, a customer support agent that looks up an order, checks a policy, and only then decides whether to issue a refund.

This matters concretely for your career trajectory because orchestration is where most of the engineering in AI Engineering actually lives. Prompting a model well is a skill; wiring a model's own output back into itself as the next input, safely, with limits on cost and time and failure blast radius, is software architecture — the exact kind of discipline a Spring Boot backend engineer already has muscle memory for, just aimed at a new, probabilistic dependency. Get orchestration wrong and you get infinite loops that burn budget, agents that take destructive actions because nothing stopped them, and systems that are impossible to debug because "what actually happened" is scattered across dozens of unlogged model calls. Get it right and you have something genuinely new: software that adapts its own execution path at runtime based on what it discovers, without you having hand-coded every branch.

It is also the direct prerequisite for the next chapter. Multi-Agent Systems (Chapter 84) is, mechanically, "what happens when you have more than one orchestration loop and they need to coordinate with each other." If the single-loop mental model built in this chapter is shaky, multi-agent systems will look like magic instead of like the composition they actually are.

2. HISTORICAL BACKGROUND

2.1 Workflow Engines: Orchestration Before LLMs Existed

Orchestration as a general engineering problem predates language models by decades. Business process engines (BPMN tools like Camunda and Activiti), workflow orchestrators (Apache Airflow, AWS Step Functions), and durable execution frameworks (Temporal, Cadence) were all built to solve a structurally similar problem: coordinate a sequence of steps, some of which can fail, some of which branch based on runtime data, over a duration long enough that the calling process cannot simply block and wait. If you have ever defined a Step Functions state machine or an Airflow DAG, you have already built an orchestrator — it just orchestrated deterministic tasks (run this Lambda, then this Spark job, then send this notification) rather than model calls whose next step is decided by the model itself. Agent orchestration inherits this entire lineage of ideas — retries, timeouts, checkpointing, human-approval gates — and adds exactly one new, hard problem: the branching logic is not written by an engineer, it is generated by the LLM at runtime, from natural-language reasoning about the current state.

2.2 The ReAct Paper and the Birth of the "Agent Loop"

The specific pattern most agent orchestration is built on traces back to a 2022 research paper introducing ReAct (Reason + Act). Its insight was simple but pivotal: instead of asking a model to either "think step by step" (pure reasoning, no real-world grounding) or "just call a tool" (pure action, no visible reasoning), interleave the two explicitly. The model is prompted to produce a thought (why it's about to do something), then an action (a tool call), then it is given an observation (the tool's result), and the cycle repeats. This Thought → Action → Observation loop, repeated until the model decides it has enough information to produce a final answer, is the direct ancestor of essentially every agent framework built since — LangChain's agent executors, LlamaIndex's agent loops, and the tool-calling loops built into modern Spring AI applications all implement some variant of this same cycle, even when the "thought" step is now implicit inside the model rather than printed as text.

2.3 The AutoGPT / BabyAGI Moment: Autonomy Without Guardrails

In 2023, a wave of experimental projects (AutoGPT, BabyAGI, and similar) pushed the ReAct loop to its logical extreme: give a model a high-level goal, a set of tools, and let it decide, entirely on its own, how many loop iterations to run and when it was "done." These projects were enormously important for what they revealed rather than for what they shipped: unattended, unbounded agent loops burned enormous amounts of API budget, wandered off-task, occasionally invented sub-goals that had nothing to do with the original request, and rarely reached a satisfying conclusion for tasks of any real complexity. The lesson the industry took from this — the one baked into every serious orchestration framework since — is that autonomy without structural limits is not a feature, it is a liability. Production agent orchestration since then has been a steady walk back from "let the model decide everything" toward "give the model bounded, well-scoped decisions inside an orchestration structure an engineer designed and can reason about." Plan-and-execute architectures, explicit state machines, and graph-based orchestration (which you will meet in this chapter and see formalized further in later chapters on planning and multi-agent design) are all direct responses to the AutoGPT-era failure mode.

3. PROBLEM STATEMENT

Given a goal, a model, and a set of tools, build a control loop that repeatedly lets the model decide the next action, executes that action safely, feeds the result back to the model, and terminates — correctly, within bounded cost and time — once the goal is satisfied or no longer worth pursuing.

Unpack that sentence and you find every hard sub-problem this chapter has to address. "Repeatedly lets the model decide" means you need a loop structure — and a decision about how much freedom the model has at each step (pick any tool vs. pick from a constrained menu; free-form next step vs. following a plan laid out in advance). "Executes that action safely" means you need the same reliability engineering as any external call — timeouts, retries, idempotency — plus a new concern this volume's Tool Usage chapter introduced: validating that what the model asked for is a request you are willing to actually perform. "Feeds the result back" means managing a growing context (tying directly back to the Context Windows and Memory chapters — every loop iteration adds tokens, and that growth is not free). And "terminates — correctly, within bounded cost and time" is the problem AutoGPT-era projects mostly failed to solve: an orchestrator needs an explicit answer to "how do we know when to stop," because an LLM left to decide this entirely on its own will sometimes loop far longer than a human would, and sometimes stop before actually finishing.

Notice that none of this is really about making the model smarter. It is about wrapping a smart-but-unreliable decision-maker in an engineering harness that constrains how it is allowed to act, not what it is allowed to think. That framing is the single most useful lens for this entire chapter.

4. THEORY

4.1 The Agent Loop as a State Machine

The cleanest mental model for agent orchestration is not "a smart program" — it is a state machine whose transition function happens to be an LLM call. A classic state machine has a fixed set of states and a fixed, engineer-written function that decides the next state given the current one. An agent loop has a fixed set of state slots — the running transcript, the tools available, an iteration counter, a budget — and the transition decision ("call this tool with these arguments" or "stop and answer") is produced by the model reading that state and generating text. Everything else about how you would engineer a state machine still applies: you still want an explicit set of terminal states, you still want to reject illegal transitions, you still want observability into every transition taken. You have simply replaced a `switch` statement with a model inference call as the thing that picks the next edge in the graph.

4.2 Orchestration Patterns: A Spectrum From Rigid to Free

There is no single "correct" orchestration pattern — different tasks call for different amounts of model autonomy. It helps to see them as points on one spectrum, from most constrained to least:

A practical orchestration engineer's job is almost always to pick the least amount of model freedom that still gets the task done — not the most. This inverts the instinct of someone excited by what LLMs can do; the more autonomy you hand the loop, the harder it becomes to bound cost, prevent unwanted actions, and debug failures.

4.3 Orchestrator vs. Choreography

Borrow a distinction from distributed systems: in orchestration, one central component (the orchestrator) knows the whole process and tells each participant what to do next; in choreography, each participant reacts to events independently with no central conductor. Single-agent loops are almost always orchestrated — there is one controlling loop deciding what happens next. Multi-agent systems (next chapter) can be built either way: a supervisor agent orchestrating worker agents, or several agents reacting to a shared event stream with no single conductor. Understanding this distinction now means Chapter 84 will feel like a natural extension of a pattern you already know, not a new paradigm.

5. INTERNAL WORKING

Walk through exactly what happens, mechanically, inside a single-loop tool-calling orchestrator handling a request like "find the cheapest flight from Lahore to Istanbul next Friday and check if I'm free that day."

  1. Initialize state. The orchestrator builds the initial context: system instructions, the user's goal, the list of available tools with their schemas (as covered in Tool Usage), and resets an iteration counter and a token/cost budget.
  2. Invoke the model. The model receives the current transcript and tool definitions and produces either (a) a final answer, or (b) one or more tool call requests with arguments, exactly as described in the Tool Calling mechanism from the previous chapter.
  3. Validate the requested action before executing it. This is the step most naive implementations skip. The orchestrator checks: is this tool actually registered? Do the arguments match the schema? Does this specific call violate a policy (e.g., a "book_flight" tool being called before a "search_flights" tool has ever run in this session)? A well-built orchestrator rejects invalid or policy-violating calls and feeds the rejection back to the model as an observation, rather than either crashing or blindly executing.
  4. Execute the action with production discipline. Call the underlying tool (an internal method, an HTTP call, a database query) with the same reliability engineering you would apply to any external dependency — timeout, retry with backoff for transient failures, and a clear distinction between "the tool ran and returned an error" (a valid observation to hand back to the model) versus "the tool call itself failed to execute" (an infrastructure failure that may need different handling, like aborting the loop).
  5. Append the observation to the transcript. The tool's result — the list of flights found, or the calendar availability — is serialized and appended as a new message so the next model call can see it. This is exactly where context growth becomes a real engineering concern (see Performance Considerations below).
  6. Check loop-continuation conditions. Before calling the model again, the orchestrator checks: has the iteration counter exceeded its maximum? Has the cost/token budget been exceeded? Has a wall-clock timeout been hit? Any "yes" here forces termination regardless of what the model would have wanted to do next — this is the structural guardrail that AutoGPT-era loops lacked.
  7. Repeat from step 2 until the model produces a final answer with no further tool calls, or a termination condition in step 6 fires.
  8. Finalize. On successful completion, the orchestrator returns the final answer (and, in production systems, a structured trace of every action taken, for auditability). On forced termination, it returns a clearly labeled partial result or failure — never silently presenting an incomplete loop as if it were a confident final answer.

The edge cases worth reasoning through yourself, because interviewers ask about exactly these: what happens if the model requests two tool calls in the same turn that touch the same resource (e.g., two conflicting flight bookings)? What happens if a tool call succeeds but its result is enormous — do you truncate it, summarize it, or store it externally and hand the model a reference? What happens if the model repeats the exact same tool call three times in a row — is that a sign of a stuck loop, and should the orchestrator detect and break that pattern itself rather than trusting the model to notice?

6. MATHEMATICS

Agent orchestration does not need new mathematics so much as it needs you to apply cost and probability reasoning you already have, aimed at loop behavior instead of a single call. Two intuitions carry almost all of the useful math here.

6.1 Expected Cost of a Loop

If each loop iteration costs roughly c tokens (prompt + completion, growing slightly each turn because the transcript accumulates), and the loop terminates after a random number of iterations N, then expected total cost is proportional to E[N] × average(c). Because the transcript grows with each iteration, c itself is not constant — it increases roughly linearly with iteration count for a naive implementation that never trims history, meaning total cost for an N-iteration loop grows closer to O(N²) in tokens than O(N) unless you actively manage context (summarizing or truncating older tool observations, a technique bridging directly to the Memory and Context Engineering chapters). This quadratic-ish growth is the mathematical reason "just let it loop until done" is a dangerous default: a task that unexpectedly needs 20 iterations instead of 5 does not cost 4x more, it can cost far more than that.

6.2 Termination as a Probability Problem

Think of each iteration as having some probability p that the model judges the task complete and stops. If that probability were constant every turn (a simplification, but a useful one), the number of iterations until termination follows a geometric distribution, and the expected number of iterations is 1/p. This gives you a concrete, quantitative reason to set a hard maximum iteration count rather than trusting the model's own stopping judgment alone: even a modest per-turn continuation probability produces a long tail where a small fraction of runs loop far longer than the mean — exactly the behavior worth engineering a hard ceiling against, the same way you'd cap retries on a flaky network call rather than trusting "it'll eventually succeed."

8. PRODUCTION ARCHITECTURE

An orchestration loop that only exists inside a single request-handling thread is fine for a chat UI where the user is watching and can wait. Production agent orchestration usually needs to survive longer than a single HTTP request, be resumable after a crash, and be observable by someone other than the person who wrote it.

Three architectural decisions recur in every real deployment of this shape. First, persist run state after every step, not just at the end — a crash mid-loop should resume from the last completed step, not restart the whole task and re-execute already-completed side effects. Second, separate the orchestration loop from the tool execution layer as distinct components with their own retry/timeout policies — a slow downstream API should not force you to also re-run an expensive model call. Third, make the step log a first-class artifact, not an afterthought written to a log file no one reads — when an agent takes an unexpected action in production, the very first question anyone asks is "show me exactly what it saw and decided at each step," and if that trace does not exist, you cannot answer it.

9. JAVA / SPRING PERSPECTIVE

Spring AI gives you the building blocks for the loop described in Section 5 without forcing you to hand-roll message formatting or tool-call parsing yourself. A ChatClient, configured with tool callbacks (registered via @Tool-annotated methods or a FunctionCallback/ToolCallback implementation, as introduced in the Tool Usage chapter), will automatically perform the "call model → detect tool call → execute → feed result back → call model again" cycle internally for straightforward cases. But that automatic loop is intentionally minimal — it does not know your business rules about which tools are allowed after which, it does not enforce an iteration ceiling for open-ended tasks, and it does not persist state across a server restart. That is exactly the gap an orchestration layer you write fills in.

A realistic shape for a bounded orchestration loop built on Spring AI looks like this: 

@Service
public class TravelAgentOrchestrator {

    private final ChatClient chatClient;
    private static final int MAX_ITERATIONS = 8;

    public TravelAgentOrchestrator(ChatClient.Builder builder,
                                    ToolCallbackProvider tools) {
        this.chatClient = builder
                .defaultToolCallbacks(tools)
                .build();
    }

    public AgentRunResult run(String goal, String conversationId) {
        List<Message> transcript = new ArrayList<>();
        transcript.add(new SystemMessage(ORCHESTRATION_POLICY));
        transcript.add(new UserMessage(goal));

        for (int iteration = 0; iteration < MAX_ITERATIONS; iteration++) {
            ChatResponse response = chatClient.prompt()
                    .messages(transcript)
                    .call()
                    .chatResponse();

            auditLog.record(conversationId, iteration, response);

            if (!hasPendingToolCalls(response)) {
                return AgentRunResult.completed(response.getResult()
                        .getOutput().getContent());
            }
            // Spring AI's tool-calling support executes the requested
            // tool(s) and appends the observation automatically when
            // using .call() with registered callbacks; explicit
            // orchestration layers intercept here to apply policy
            // checks (allowed tool? rate limited? requires approval?)
            // before letting execution proceed.
            transcript = mergeWithLatestExchange(transcript, response);
        }
        return AgentRunResult.incomplete("Max iterations reached",
                transcript);
    }
}

Notice what this code is doing that a raw ChatClient.call() would not do on its own: it owns the iteration ceiling, it persists an audit trail per step, and it returns a distinct, explicitly-labeled "incomplete" result rather than letting a runaway loop return whatever half-finished text the model happened to produce last. Advisors (covered in Volume 2) are the natural place to slot in cross-cutting orchestration concerns — a custom CallAroundAdvisor can enforce per-step token budgets or inject policy reminders into the transcript without cluttering the orchestration loop's core logic, the same way an AOP interceptor keeps logging out of your business methods. For workflows that need explicit branching structure rather than an open-ended loop, graph-oriented orchestration libraries (in the Java ecosystem, projects modeled on the graph-of-nodes pattern popularized by LangGraph) compose naturally with Spring AI's ChatClient as the "brain" inside individual graph nodes, while Spring's own state machine facilities or a workflow engine like Temporal can own the durable, resumable execution of the graph itself.

10. BEST PRACTICES

  • Always set a hard iteration ceiling and a hard cost/token budget, independent of what the model "wants." Treat these as non-negotiable circuit breakers, the same way you would cap retries on a flaky downstream call.
  • Validate every model-requested action against an explicit allow-list and policy layer before executing it — never execute a tool call purely because the model asked for it; the model's request is an input to your authorization logic, not a bypass of it.
  • Persist the full step-by-step trace, not just the final answer. The trace is your primary debugging and audit tool once this runs unattended in production; treat it with the same seriousness as request logging in any other backend service.
  • Prefer the least autonomous pattern that solves the task — a fixed pipeline over plan-and-execute, plan-and-execute over an open-ended loop — and only grant more model freedom when the task's variability genuinely demands it.
  • Detect and break repetition explicitly. If the same tool is called with materially identical arguments more than once or twice in a row, treat that as a stuck-loop signal and intervene (abort, ask for clarification, or escalate) rather than trusting the model to notice on its own.
  • Design for resumability from the start. Any orchestration loop expected to run longer than a single request/response cycle should checkpoint state after each step so a crash or deploy does not silently lose or duplicate work.

11. COMMON MISTAKES

  • No hard stop condition beyond "the model will know when it's done." This was the defining failure of early autonomous-agent experiments and remains the single most common production incident source in agent systems.
  • Trusting the model's stated plan without re-checking state after each step. A plan made at step 1 can become invalid by step 4 if an earlier tool call returned unexpected data; orchestrators that blindly execute a fixed plan without re-evaluating lose exactly the adaptability that justified using an agent loop in the first place.
  • Letting context grow unbounded across iterations. Appending every raw tool result to the transcript forever eventually exceeds the context window (covered in depth in that chapter) or silently degrades quality as older, more relevant information gets pushed out or drowned in noise — summarizing or truncating stale observations is not optional at scale.
  • Conflating "tool execution failed" with "tool execution succeeded but returned bad news." A search that legitimately finds zero results is a valid observation to hand back to the model; a network timeout calling that search API is an infrastructure failure that may warrant a different response (retry, abort, alert) — collapsing both into the same generic error path confuses the model and hides real outages from your monitoring.
  • Executing side-effecting tools (payments, deletions, sends) with the same trust level as read-only tools. Every orchestrator should distinguish reversible, read-only actions from irreversible, side-effecting ones, and gate the latter behind stricter validation or human approval — this is a direct extension of the tool-risk classification introduced in the Tool Usage chapter.
  • Building the orchestration loop as unstructured code scattered across the request handler. Without a clear state model (Section 4.1), the loop's logic becomes as unmaintainable as a codebase full of untracked global mutable state — a mistake Java engineers already know to avoid, just not yet applied to this new context.

12. PERFORMANCE CONSIDERATIONS

Orchestration multiplies every per-call cost and latency concern from earlier chapters by the number of loop iterations, which makes it the point in the stack where inattention to cost becomes most expensive in practice.

  • Latency compounds sequentially. Each loop iteration is a full model round trip plus tool execution time; a five-iteration loop with a 2-second model call and 500ms tool calls is already over 12 seconds end to end — plan your product experience (streaming intermediate steps to the user, async completion with a callback/webhook) around this rather than assuming synchronous request/response.
  • Token cost grows faster than iteration count if the transcript is never pruned, as shown in Section 6.1 — actively summarizing or externalizing old tool observations (storing full results in a database and giving the model a short reference/id instead of the raw payload) is a direct, measurable cost lever, not a nicety.
  • Parallelize independent tool calls within a single iteration when the model requests multiple non-conflicting actions at once (e.g., checking three different flight providers) rather than serializing them — this is ordinary concurrent-programming discipline applied to agent execution, and most modern tool-calling APIs support returning multiple tool calls in a single model response specifically to enable this.
  • Cache aggressively at the tool layer. Repeated or near-duplicate tool calls within or across runs (the same flight search, the same document lookup) are strong caching candidates, and unlike caching a raw LLM completion, caching a deterministic tool's result carries none of the risk of serving a stale, non-reproducible generation.
  • Match loop depth to task, not to a single global default. A classification-style agent task might legitimately need one iteration; a research task might need fifteen. Hard-coding one iteration ceiling for every use case either starves complex tasks or lets simple ones run needlessly long tail cases — size the ceiling per task type.

13. SECURITY CONSIDERATIONS

Agent orchestration inherits every security concern from the Tool Usage chapter and sharpens them, because a loop gives an attacker (or a confused model) more chances to compound a bad decision across steps rather than just one. A prompt-injected instruction buried in a tool's output (a poisoned search result, a malicious webpage the agent reads) does not just risk corrupting one response — it can steer every subsequent iteration of the loop, since that poisoned content becomes part of the transcript the model reasons from going forward. This is the reason validating and sanitizing tool outputs before they re-enter the loop matters as much as validating the initial tool call: an orchestrator that treats every observation as trusted context is one injected search result away from being redirected toward unintended actions several steps downstream.

The other orchestration-specific security surface is runaway resource consumption as a denial-of-service vector: a malicious or malformed input that pushes the loop toward its maximum iteration count on every request, at full model and tool cost, is a viable attack against your budget even without ever producing an unsafe output — the hard ceilings recommended in Section 10 are a security control as much as a cost control. Finally, every side-effecting tool call executed inside a loop should carry the same authorization context (whose permissions is this action running under?) as if a human had triggered it directly — an orchestration loop is not a trusted internal process just because the request that started it came from an authenticated user; each step should still be checked against that user's actual authority to perform it.

14. INTERVIEW QUESTIONS

JUNIORQ1. What is the difference between a single tool call and agent orchestration?

ROI: ★★★★★ · Frequency: Extremely High

A single tool call is one request/response pair: the model asks for a function to be run, gets the result, and finishes. Agent orchestration is a loop: the model's tool call result is fed back into the model, which can then decide to call another tool, and this repeats until the model produces a final answer or an engineer-defined limit stops it. Orchestration is what turns isolated tool calls into a multi-step process.

JUNIORQ2. Name the three steps of the ReAct loop pattern.

ROI: ★★★★☆ · Frequency: High

Thought (the model reasons about what to do next), Action (the model requests a tool call), and Observation (the tool's result is returned to the model). This cycle repeats until the model has enough information to give a final answer.

MIDQ3. Why do production agent orchestrators need a hard maximum iteration count instead of trusting the model to know when to stop?

ROI: ★★★★★ · Frequency: Extremely High

Early autonomous-agent experiments (AutoGPT-style projects) demonstrated that models left to decide their own stopping point can loop far longer than intended, burning cost and drifting off-task, because the model has no built-in, reliable notion of "this is taking too long." Treating loop continuation probabilistically, even a modest per-iteration chance of not stopping produces a long tail of runs that loop excessively — the same reasoning that justifies capping retries on a flaky network call applies here: bound the worst case explicitly rather than hoping the average case holds.

MIDQ4. What is the difference between plan-and-execute and single-loop ReAct orchestration, and when would you choose one over the other?

ROI: ★★★★☆ · Frequency: High

In single-loop ReAct, the model decides one action at a time, seeing results as it goes. In plan-and-execute, the model first produces an explicit multi-step plan, which is then executed (with optional re-planning if a step fails). Plan-and-execute is preferable when you need the plan to be inspectable or approvable before any action is taken (e.g., a human reviewing a proposed sequence of financial transactions), while single-loop ReAct suits tasks where the right next step genuinely depends on information only available after seeing prior results.

SENIORQ5. Why does unbounded context growth across loop iterations become a cost and quality problem, and how would you mitigate it?

ROI: ★★★★★ · Frequency: High at senior level

Every iteration appends the previous tool result to the transcript, so token cost per call grows with iteration count, pushing total cost for an N-iteration loop toward worse-than-linear growth in tokens processed. Beyond cost, an ever-growing transcript risks exceeding the context window or diluting the model's attention across increasingly irrelevant older observations, degrading decision quality. Mitigations include summarizing or truncating stale tool observations, storing large results externally and passing the model a reference/id instead of the raw payload, and periodically compressing the running transcript — the same techniques covered in the Memory and Context Engineering chapters, applied specifically to agent loop state.

SENIORQ6. How should an orchestrator handle a tool call that fails due to a network timeout versus one that succeeds but returns an unhelpful result (e.g., zero search results)?

ROI: ★★★★☆ · Frequency: Medium-High

These are fundamentally different failure classes and should not share an error path. A zero-result search is a valid, informative observation — it should be fed back to the model as normal context so it can adapt its next action (try a different query, broaden criteria, or report the negative result). A network timeout is an infrastructure failure independent of the task's logic; it typically warrants a bounded retry with backoff at the tool-execution layer, and if retries are exhausted, either surfacing a clearly-labeled infrastructure error to the model (distinct from "no results found") or aborting the loop and alerting, depending on how critical that tool is to the task. Collapsing both into a generic "tool error" observation confuses the model's reasoning and hides real outages from monitoring.

SENIORQ7. What does it mean to say an orchestration loop is "resumable," and why does that matter in production?

ROI: ★★★★☆ · Frequency: Medium at senior level

Resumability means the orchestrator persists its state (transcript, iteration count, last completed step, any side effects already performed) after every step, so that if the process crashes, is redeployed, or the request times out mid-loop, execution can pick up from the last checkpoint rather than restarting the entire task from scratch. This matters because restarting from scratch risks duplicating already-completed side-effecting actions (e.g., re-sending a confirmation email, re-charging a payment) and wastes the cost already spent on completed model calls. It is the same durable-execution concern that motivates workflow engines like Temporal, applied to agent loops specifically.

Interview Gold Point: Tie resumability explicitly to idempotency of side-effecting tools — mention that resumability alone is not enough if a resumed step might re-execute a non-idempotent action; the orchestrator needs to track which side effects have already committed, not just which model calls have completed, before deciding what is safe to re-run.
STAFFQ8. A team wants to give their support agent full autonomy to decide, at every step, which of forty available tools to call next, with no engineer-defined structure beyond the tool list itself. As a staff engineer, how do you evaluate this design, and what would you propose instead?

ROI: ★★★★★ · Frequency: High at staff level

Full open-ended autonomy across a large tool surface maximizes the model's decision space at exactly the layer where mistakes are hardest to prevent and audit — the history of early autonomous-agent projects shows this pattern reliably produces wandering, cost overruns, and occasional unsafe actions as the tool count and task complexity grow. The staff-level response is to push back on "maximum autonomy" as the default and instead ask what the task actually requires: classify the forty tools by risk (read-only vs. side-effecting), constrain which tools are reachable at which stage of the interaction (e.g., a refund tool should not be callable before an order-lookup tool has run in the same session), and consider whether the task decomposes into a graph or plan-and-execute structure where the model's freedom is scoped per-node rather than global. Propose starting with the least autonomous pattern that plausibly solves the observed task variety, instrumenting it heavily, and only widening the model's freedom in response to measured limitations — not granting maximum autonomy up front on the assumption that more freedom equals better outcomes.

16. SUMMARY

  • Agent orchestration is the control loop that turns individual tool calls (Chapter 82) into a multi-step process: call model, validate the requested action, execute it, feed the result back, and repeat until a stopping condition is reached.
  • It descends directly from pre-LLM workflow orchestration (Airflow, Step Functions, Temporal) and from the ReAct pattern, with the AutoGPT-era failures teaching the industry that unbounded model autonomy is a liability, not a feature.
  • Orchestration patterns range from fixed pipelines through single-loop ReAct and plan-and-execute to full graph-based state machines — always prefer the least autonomous pattern that solves the task.
  • Hard iteration ceilings, cost/token budgets, and explicit stop conditions are non-negotiable engineering controls, not optional polish — they are the direct fix for the failure mode that defined early autonomous agents.
  • Context growth across iterations is a real, measurable cost and quality problem; summarizing or externalizing stale tool observations is essential at any meaningful loop depth.
  • In Spring AI, ChatClient with registered tool callbacks provides the mechanical loop, but production-grade policy enforcement, persistence, auditability, and iteration limits are an orchestration layer you build deliberately around it.

Every concept from this chapter — bounded autonomy, explicit state, hard limits, auditable traces — reappears there, just distributed across more than one decision-maker.
