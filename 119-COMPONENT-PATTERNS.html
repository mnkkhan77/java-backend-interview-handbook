SECTION 1 - COMPOSITION PATTERNS

Q1. What does "composition over inheritance" mean in React, and why does React strongly favour it?

ROI: ★★★★★ Frequency: Extremely High

Short Answer

React components reuse behaviour by containing or combining other components and by receiving children/props — not by subclassing. React deliberately offers no first-class inheritance mechanism for components because composition is more flexible, avoids fragile base-class hierarchies, and maps cleanly onto the "UI is a function of props" mental model. When you need to share non-visual logic, you extract a custom hook rather than a base class.

Detailed Answer

In classical OOP you might reach for inheritance to share behaviour: a Dialog extends a Modal extends a Overlay. React explicitly steers you away from this. The React team has stated they have never found a use case where inheritance across components was superior to composition.

The three levers of composition

  • Containment — a generic component (a Card, a Panel) does not know its children ahead of time and simply renders props.children.
  • Specialization — a specific component renders a generic one with preset props (a WelcomeDialog renders a Dialog with a fixed title). This is what inheritance would have given you, done with composition instead.
  • Logic reuse via hooks — shared stateful behaviour (useToggle, usePagination) lives in a function, not a superclass.

Why this wins: inheritance couples the child to the internal structure of the parent class (the "fragile base class" problem). Composition couples only to a public prop contract, which is far easier to reason about and refactor. It also composes without limit — you can wrap, slot, and nest freely, whereas a class can only extend one parent.

Code Example

// Containment: the generic component doesn't know what goes inside
function Card({ title, children }: { title: string; children: React.ReactNode }) {
  return (
    <section className="card">
      <h3>{title}</h3>
      <div className="card-body">{children}</div>
    </section>
  );
}

// Specialization: instead of `class UserCard extends Card`, we compose
function UserCard({ user }: { user: User }) {
  return (
    <Card title={user.name}>
      <Avatar src={user.avatar} />
      <p>{user.bio}</p>
    </Card>
  );
}

Project Example

On a dashboard I built, every metric widget shared a chrome (title bar, loading skeleton, error state, refresh button). The junior instinct was a BaseWidget class the others extend. Instead we made a <Widget> that took title, onRefresh and children, and each concrete widget (RevenueWidget, UsersWidget) composed it. Adding a new widget became a five-line file, and changing the chrome touched exactly one component.

Senior Engineer Perspective

The interviewer wants to hear you say the words "custom hook" for logic reuse and "children / props" for markup reuse — many candidates conflate the two. A common trap follow-up: "But what if two components share a huge amount of logic AND markup?" The senior answer is a compound/headless component plus a hook, not a base class. Also flag that "composition" in React does not mean React.Children gymnastics by default — reach for the simplest lever (children) first.

Q2. Explain the container/presentational (smart/dumb) component split. Is it still relevant?

ROI: ★★★★☆ Frequency: High

Short Answer

The pattern splits a component into a container that owns data-fetching and state, and a presentational component that only receives props and renders UI. It was hugely popular in the class-component era (circa 2015, popularised by Dan Abramov) to separate concerns and make presentational components easy to test and reuse. Hooks largely dissolved the hard rule: you can now colocate logic in a custom hook without a wrapper component, so the strict split is less emphasized today, though the underlying principle — separate data concerns from rendering — is still sound.

Detailed Answer

The original motivation: in the class era there was no clean way to reuse stateful logic, so people isolated it into "container" classes and kept a pool of pure, props-only "presentational" components that were trivial to test and Storybook.

AspectContainerPresentational
ConcernHow things work (data, state)How things look (markup, styles)
Data sourceFetches, subscribes, dispatchesReceives via props
StateOwns app/server stateAt most UI-local state
ReusabilityLow (tied to a feature)High (generic)

Why it faded

Dan Abramov himself added a note to his original article saying he no longer recommends splitting it as a rule, precisely because Hooks let you extract stateful logic without an artificial container component. Today the equivalent is: a leaf component that renders, plus a useUsers() hook it calls, plus data libraries like TanStack Query that make "container" boilerplate disappear.

What survives is the discipline: keep components that talk to the network or a store thin, keep rendering components easy to test with plain props, and don't scatter fetch calls through your JSX tree.

Code Example

// OLD: explicit container + presentational split
function UserListContainer() {
  const [users, setUsers] = useState<User[]>([]);
  useEffect(() => { fetchUsers().then(setUsers); }, []);
  return <UserList users={users} />;        // presentational
}
function UserList({ users }: { users: User[] }) {
  return <ul>{users.map(u => <li key={u.id}>{u.name}</li>)}</ul>;
}

// MODERN: logic lives in a hook, no wrapper component needed
function useUsers() {
  return useQuery({ queryKey: ['users'], queryFn: fetchUsers });
}
function UserList() {
  const { data: users = [], isLoading } = useUsers();
  if (isLoading) return <Spinner />;
  return <ul>{users.map(u => <li key={u.id}>{u.name}</li>)}</ul>;
}

Senior Engineer Perspective

Say clearly that the pattern is not "wrong," it's just no longer a mandate — that nuance separates seniors from candidates repeating a 2016 blog post as gospel. The trap: interviewers may ask "so is the split useless now?" No — the boundary is still valuable at scale (a design-system component library should stay presentational/props-only so it's portable and Storybook-able). What changed is you rarely create a component solely to hold state; hooks do that job.

Q3. What is a Higher-Order Component (HOC)? Build one, and discuss its pros and cons.

ROI: ★★★★☆ Frequency: High

Short Answer

A Higher-Order Component is a function that takes a component and returns a new component with extra props or behaviour injected — withAuth(Dashboard). It was the dominant cross-cutting-concern pattern before hooks (think connect() from React-Redux). It still appears for wrapping/enhancing (analytics, error boundaries, theming) but for pure logic sharing hooks have replaced it because HOCs cause wrapper hell, prop-name collisions and opaque prop origins.

Detailed Answer

An HOC is just the decorator pattern for components. It never mutates the input component; it composes a new one around it.

Pros

  • Can wrap the rendering of a component (add a boundary, inject a provider, conditionally render) — something hooks alone cannot do because a hook can't decide to render a different tree around its caller.
  • Works with any component, including third-party ones you can't edit.
  • Good for cross-cutting structural concerns applied uniformly.

Cons

  • Wrapper hell — withA(withB(withC(X))) bloats the tree and the React DevTools view.
  • Prop collisions — two HOCs both inject a data prop.
  • Opaque source — you can't tell where a prop came from by reading the component.
  • Static methods and refs need manual forwarding (hoist-non-react-statics, forwardRef).

Rule of thumb: if the concern is "share stateful logic," use a hook. If the concern is "wrap the component's render output or lifecycle uniformly," an HOC (or a wrapper component) can still be the right tool.

Code Example

// A typed HOC that injects the current user and gates rendering
function withAuth<P extends object>(
  Wrapped: React.ComponentType<P & { user: User }>
) {
  function WithAuth(props: P) {
    const user = useCurrentUser();          // could also come from context
    if (!user) return <Redirect to="/login" />;
    return <Wrapped {...props} user={user} />;
  }
  // preserve a readable name in DevTools
  WithAuth.displayName = `withAuth(${Wrapped.displayName ?? Wrapped.name})`;
  return WithAuth;
}

const ProtectedDashboard = withAuth(Dashboard);

Project Example

We migrated a legacy app off connect() HOCs to useSelector/useDispatch. The win was visible immediately: the DevTools tree lost three or four Connect(...) wrappers per screen, and props that had mysteriously appeared "from Redux" now had an explicit hook call at the top of the component. We kept exactly one HOC — withErrorBoundary — because that one genuinely needs to wrap the render tree.

Senior Engineer Perspective

The strongest answer names a concrete legacy HOC (connect, withRouter, Relay's createFragmentContainer) and explains that the whole ecosystem moved to hook equivalents. Expect the follow-up "so are HOCs dead?" — say no: React.memo and forwardRef are technically HOCs, and render-wrapping concerns still fit them. Bonus points for mentioning ref forwarding and static hoisting as the classic HOC footguns.

Q4. What is the render props pattern? How does it compare to HOCs and hooks?

ROI: ★★★★☆ Frequency: High

Short Answer

A render prop is a component that takes a function as a prop (often children) and calls that function with internal state to decide what to render. It inverts control: the reusable component owns behaviour, the consumer owns markup. It solved the same logic-sharing problem as HOCs without wrapper hell, but hooks have superseded it for most cases because hooks share logic without adding any nesting at all.

Detailed Answer

Before hooks, if you had reusable stateful logic (mouse position, form state, a toggle) you needed a way to hand that state to arbitrary JSX. Render props did that by passing a function down and invoking it with the state.

Compared to HOCs, render props keep the prop origin explicit (you see the function receiving the values right there in JSX) and avoid name collisions. The downside is the "pyramid of doom" when you nest several render-prop components, and creating a new closure on every render (a minor perf concern).

Hooks made both patterns mostly obsolete for logic reuse: a useMousePosition() hook returns the same values with zero extra tree nesting. But render props are far from dead — they shine when the reusable component needs to control where and whether to render, e.g. virtualization libraries, <Formik>, Downshift, headless charting (Recharts <ResponsiveContainer>), and the "children as a function" idiom (covered later).

Code Example

// Render-prop component: owns the logic, defers the markup
function MousePosition({ children }: {
  children: (pos: { x: number; y: number }) => React.ReactNode;
}) {
  const [pos, setPos] = useState({ x: 0, y: 0 });
  useEffect(() => {
    const handler = (e: MouseEvent) => setPos({ x: e.clientX, y: e.clientY });
    window.addEventListener('mousemove', handler);
    return () => window.removeEventListener('mousemove', handler);
  }, []);
  return <>{children(pos)}</>;
}

// Consumer decides the markup
<MousePosition>
  {({ x, y }) => <p>Cursor at {x}, {y}</p>}
</MousePosition>

// The hook equivalent — no nesting
function useMousePosition() { /* same effect */ return pos; }

Senior Engineer Perspective

The clean narrative interviewers love: "HOCs and render props were two solutions to the same problem — sharing stateful logic — each with a nesting/opacity tax; hooks solved it without a tax." Then the nuance: render props are still the right tool when the library must drive rendering, which a hook can't. If you only recite "hooks replaced render props," you'll get dinged on the follow-up "then why does Formik/react-window still use them?"

Q5. What is the "children as a function" pattern, and when is it preferable to plain children?

ROI: ★★★☆☆ Frequency: Medium

Short Answer

It's render props using the children prop specifically: instead of passing JSX, you pass a function and the component calls it with internal state. You reach for it when the parent has data or state that the child markup needs but the parent shouldn't dictate how that data is rendered.

Detailed Answer

Plain children is static JSX — the parent renders whatever you handed it. children-as-a-function is dynamic — the parent computes values (a virtualized row index, a scroll offset, form field state) and passes them into your function so your markup can use them. It reads slightly more naturally than a named render prop because the function sits between the component's tags.

Use it when the values genuinely originate in the parent and vary per render — list virtualization (react-window gives you an index and style), a <Toggle> handing down on and toggle, or data-fetch wrappers handing down data/loading/error. Avoid it when static children work — it's more indirection than needed for simple cases.

Code Example

type ToggleApi = { on: boolean; toggle: () => void };

function Toggle({ children }: { children: (api: ToggleApi) => React.ReactNode }) {
  const [on, setOn] = useState(false);
  return <>{children({ on, toggle: () => setOn(v => !v) })}</>;
}

// Consumer fully controls markup, gets state injected
<Toggle>
  {({ on, toggle }) => (
    <button aria-pressed={on} onClick={toggle}>
      {on ? 'ON' : 'OFF'}
    </button>
  )}
</Toggle>

Senior Engineer Perspective

Mention the two costs: a new function identity each render (usually irrelevant, but it can defeat memoization if the child is expensive) and reduced readability when nested. Interviewers sometimes ask why not just use a hook — the answer is the same as render props: use the function-child form when the component must control the surrounding render (like a virtualized window), not merely hand you values.

SECTION 2 - REUSE PATTERNS

Q6. Build a compound component (e.g. Tabs or Accordion) using Context. Why is this pattern powerful?

ROI: ★★★★★ Frequency: Extremely High

Short Answer

Compound components are a set of components that work together and share implicit state through Context, exposing an expressive, HTML-like API: <Tabs><Tab/><TabPanel/></Tabs>. The parent holds the state; the children read/update it via a shared context instead of prop drilling. It's powerful because the consumer composes the pieces freely (order, wrapping, extra markup) while the components coordinate behind the scenes — flexible API, zero prop-passing boilerplate.

Detailed Answer

Think of native HTML: <select> and <option> are meaningless apart but coordinate implicitly. Compound components bring that ergonomics to React. The wrapper (Tabs) owns the active-index state and provides it via Context; sub-components (TabList, Tab, TabPanel) consume it. The consumer never manually wires "which tab is active" between pieces.

Benefits

  • Flexible layout — the consumer can wrap tabs in a div, add icons, reorder, insert anything, without the component breaking.
  • Clean API — no giant config object of tabs={[...]}; structure is expressed as JSX.
  • Encapsulation — shared state stays internal.

The main trade-off is that free composition means you must handle cases like a Tab rendered outside a Tabs — throw a clear error from the context hook. Also, deeply-nested consumers still work because Context ignores tree depth.

Code Example

import { createContext, useContext, useState, useId } from 'react';

type TabsCtx = { active: string; setActive: (id: string) => void };
const TabsContext = createContext<TabsCtx | null>(null);

function useTabs() {
  const ctx = useContext(TabsContext);
  if (!ctx) throw new Error('Tabs.* must be used inside <Tabs>');
  return ctx;
}

function Tabs({ defaultTab, children }: { defaultTab: string; children: React.ReactNode }) {
  const [active, setActive] = useState(defaultTab);
  return (
    <TabsContext.Provider value={{ active, setActive }}>
      <div className="tabs">{children}</div>
    </TabsContext.Provider>
  );
}

function TabList({ children }: { children: React.ReactNode }) {
  return <div role="tablist">{children}</div>;
}

function Tab({ id, children }: { id: string; children: React.ReactNode }) {
  const { active, setActive } = useTabs();
  return (
    <button
      role="tab"
      aria-selected={active === id}
      onClick={() => setActive(id)}
    >
      {children}
    </button>
  );
}

function TabPanel({ id, children }: { id: string; children: React.ReactNode }) {
  const { active } = useTabs();
  if (active !== id) return null;
  return <div role="tabpanel">{children}</div>;
}

// Attach as namespaced API — nice discoverability
Tabs.List = TabList;
Tabs.Tab = Tab;
Tabs.Panel = TabPanel;

// Usage
<Tabs defaultTab="profile">
  <Tabs.List>
    <Tabs.Tab id="profile">Profile</Tabs.Tab>
    <Tabs.Tab id="billing">Billing</Tabs.Tab>
  </Tabs.List>
  <Tabs.Panel id="profile">Profile content</Tabs.Panel>
  <Tabs.Panel id="billing">Billing content</Tabs.Panel>
</Tabs>

Project Example

Our design system shipped <Accordion>, <Menu> and <Tabs> exactly this way. Product teams loved that they could drop a tooltip or a badge next to a tab label without us adding a tabBadge prop for every new need — free composition removed a whole class of feature requests. The useTabs() guard caught a real bug where someone rendered a stray <Tab> in a Storybook story outside the provider.

Senior Engineer Perspective

Two follow-ups are almost guaranteed. First: "How do children get the state — do you use React.cloneElement?" Older tutorials cloned children to inject props; the modern, robust answer is Context, because cloneElement breaks the moment a child is nested one level deeper. Say that explicitly. Second: "How do you handle accessibility?" Mention roles (tablist/tab/tabpanel), aria-selected, roving tabindex and arrow-key navigation — real compound components own the a11y so consumers don't have to.

Q7. What are prop getters, and what problem do they solve?

ROI: ★★★☆☆ Frequency: Medium

Short Answer

A prop getter is a function a component (or hook) exposes that returns a bundle of props you spread onto your own element — <button {...getToggleButtonProps()}>. It lets a headless component wire up behaviour (event handlers, ARIA attributes, ids) onto your markup while safely composing with any props/handlers you also pass. It's the pattern behind Downshift and most headless UI libraries.

Detailed Answer

The problem: a headless component gives you full control of markup, but it still needs to attach handlers and accessibility attributes to specific elements. If it just told you "add onClick={toggle} and aria-expanded and id and role yourself," you'd get it wrong and it wouldn't compose with your own onClick.

A prop getter solves this by returning all those props as one object and merging in anything you pass — most importantly composing event handlers so both the library's handler and yours run. You spread it; the component keeps ownership of behaviour; you keep ownership of markup.

Code Example

function useToggle() {
  const [on, setOn] = useState(false);
  const toggle = () => setOn(v => !v);

  // Prop getter: merges caller props, composes onClick
  function getTogglerProps<T extends { onClick?: (e: any) => void }>(props?: T) {
    return {
      'aria-pressed': on,
      ...props,
      onClick: (e: React.MouseEvent) => {
        props?.onClick?.(e);   // run the caller's handler first
        toggle();              // then our behaviour
      },
    };
  }
  return { on, getTogglerProps };
}

// Consumer keeps their own onClick AND gets toggle behaviour
const { on, getTogglerProps } = useToggle();
<button {...getTogglerProps({ onClick: () => console.log('clicked') })}>
  {on ? 'On' : 'Off'}
</button>

Senior Engineer Perspective

The insight interviewers probe: why not just return the handlers directly? Because you'd lose handler composition and force the consumer to remember every ARIA attribute. Prop getters centralise "correct wiring" while preserving consumer overrides. Name-drop Downshift (Kent C. Dodds popularised the term) and note the modern relative: Radix/React Aria's useX hooks return prop bundles for the same reason.

Q8. What is the "slots via props" pattern for passing JSX into components?

ROI: ★★★☆☆ Frequency: Medium

Short Answer

When a component needs several distinct regions of custom content — not one generic children — you accept JSX through named props: header, footer, sidebar. These are React's answer to Vue/Web-Component "named slots." Because props can hold any ReactNode, you just pass elements.

Detailed Answer

children handles the single-hole case. But a <Layout> with a header, main area and sidebar has three holes. Rather than parse children looking for special components, you expose named props that each take JSX. This is explicit, type-safe (each prop is ReactNode), and avoids the fragility of inspecting children by type.

Two competing conventions exist: named-prop slots (shown below) and compound-component slots (<Card.Header>). Prop slots are simpler and better when the set of regions is fixed and small; compound components win when you want free composition and ordering. Both are valid — choose by how flexible the layout must be.

Code Example

type ShellProps = {
  header: React.ReactNode;
  sidebar?: React.ReactNode;
  children: React.ReactNode;   // the "default slot"
};

function AppShell({ header, sidebar, children }: ShellProps) {
  return (
    <div className="shell">
      <header>{header}</header>
      {sidebar && <aside>{sidebar}</aside>}
      <main>{children}</main>
    </div>
  );
}

<AppShell
  header={<TopBar user={user} />}
  sidebar={<NavMenu />}
>
  <Dashboard />
</AppShell>

Senior Engineer Perspective

A subtle follow-up: "Why pass a rendered element and not a component reference?" Passing header={<TopBar/>} lets the consumer close over props at the call site; passing headerComponent={TopBar} defers rendering but forces you to funnel props through. Prefer element props for slots unless you need to control render timing. Also mention that named-prop slots make DevTools cleaner than children-sniffing with React.Children.map, which is brittle and discouraged.

Q9. Explain controlled vs uncontrolled components and the "control props" pattern.

ROI: ★★★★★ Frequency: Extremely High

Short Answer

A controlled component's value lives in the parent's state and is passed down via a value prop with an onChange callback — React is the single source of truth. An uncontrolled component manages its own internal state and you read it via a ref (or defaultValue). The control props pattern lets a reusable component support both: it uses internal state by default but defers to a value prop when one is supplied — exactly how <input> itself behaves.

Detailed Answer

ControlledUncontrolled
Source of truthReact state (parent)The DOM / internal state
Read valuevalue propref.current.value
Set initialvaluedefaultValue
EnablesValidation, formatting, conditional disabling on each keystrokeSimplicity, less re-render, easy integration with non-React code

When designing your own component (a custom <Toggle>, <Combobox>, <Rating>), the control props pattern makes it flexible: consumers who don't care pass nothing and get sensible internal behaviour; consumers who need to drive it pass value + onChange. You detect which mode you're in by whether value is undefined. This is the same "controllable" contract React's built-in inputs use, and it's what libraries like Radix and MUI implement.

Gotcha: never switch a component between controlled and uncontrolled at runtime (going from value={undefined} to value="x") — React warns because it can't tell which source of truth to trust.

Code Example

// A controllable Toggle: works controlled OR uncontrolled
function Toggle({
  value,                       // controlled value (optional)
  defaultValue = false,        // uncontrolled initial
  onChange,
}: {
  value?: boolean;
  defaultValue?: boolean;
  onChange?: (next: boolean) => void;
}) {
  const [internal, setInternal] = useState(defaultValue);
  const isControlled = value !== undefined;
  const on = isControlled ? value : internal;

  const toggle = () => {
    const next = !on;
    if (!isControlled) setInternal(next);  // only manage state when uncontrolled
    onChange?.(next);                       // always notify
  };

  return <button aria-pressed={on} onClick={toggle}>{on ? 'On' : 'Off'}</button>;
}

// Uncontrolled: <Toggle defaultValue />
// Controlled:   <Toggle value={isOn} onChange={setIsOn} />

Project Example

Our design-system <DatePicker> shipped as controllable. Simple forms used it uncontrolled and read the value on submit; the complex booking flow needed to reset the date when the destination changed, so it drove the picker with value/onChange. One component, two integration styles, no forked code path — that's the payoff of the control props pattern.

Senior Engineer Perspective

Interviewers use this to test whether you understand "single source of truth." The killer follow-up is the controlled↔uncontrolled switch warning — be ready to explain that you must decide the mode once (guard with value !== undefined captured consistently). Bonus: for large forms, note that fully controlled inputs re-render on every keystroke, which is why libraries like React Hook Form lean uncontrolled (refs) for performance and only subscribe where needed.

Q10. What is the provider pattern, and how do you design a good one?

ROI: ★★★★☆ Frequency: High

Short Answer

The provider pattern wraps React.createContext in a dedicated <XProvider> component that owns the state and exposes a custom useX() hook for consumers. It encapsulates the context so consumers never touch createContext directly, gives you a single place for logic, and lets the hook throw a helpful error if used outside the provider.

Detailed Answer

A naive Context usage scatters useContext(ThemeContext) everywhere and exposes the raw context object. The provider pattern packages three things together:

  • A private context (not exported).
  • A Provider component that holds state/logic and memoizes its value.
  • A useX() hook that reads the context and guards against misuse.

Key design points: memoize the value (an object literal in the value prop re-renders every consumer on each parent render), and consider splitting state and dispatch into two contexts so components that only dispatch don't re-render when state changes. For heavy global state, this pattern is how you build a lightweight store without Redux.

Code Example

const ThemeContext = createContext<ThemeCtx | null>(null);   // private

export function ThemeProvider({ children }: { children: React.ReactNode }) {
  const [theme, setTheme] = useState<'light' | 'dark'>('light');

  // memoize so consumers don't re-render on unrelated parent renders
  const value = useMemo(
    () => ({ theme, toggle: () => setTheme(t => (t === 'light' ? 'dark' : 'light')) }),
    [theme]
  );

  return <ThemeContext.Provider value={value}>{children}</ThemeContext.Provider>;
}

export function useTheme() {
  const ctx = useContext(ThemeContext);
  if (!ctx) throw new Error('useTheme must be used within <ThemeProvider>');
  return ctx;
}

Senior Engineer Perspective

The classic gotcha they hunt for: forgetting to memoize the context value, which silently re-renders the whole subtree. Mention it unprompted. Next-level answer: Context is not a state manager — it has no selector, so any value change re-renders all consumers; for high-frequency updates use useSyncExternalStore, split contexts, or a real store (Zustand/Redux Toolkit). Also note the state/dispatch split as a cheap optimization.

Q11. What principles guide designing a good component API?

ROI: ★★★★☆ Frequency: High

Short Answer

Aim for an API that's hard to misuse and easy to compose: prefer composition (children/slots) over a pile of boolean props, keep props orthogonal, mirror native HTML conventions (value/onChange, disabled), forward ...rest and refs to the root element, provide sensible defaults, and make illegal states unrepresentable with discriminated union prop types.

Detailed Answer

Concrete principles

  • Composition over configuration — a growing list of showHeader, headerColor, headerIcon booleans is a smell; accept a header slot instead.
  • Follow platform conventions — name callbacks onX, use value/defaultValue, support disabled — so the API feels familiar.
  • Spread rest props & forward refs — let consumers pass className, data-*, aria-* and get a ref to the DOM node.
  • Make impossible states impossible — model variants with unions so TypeScript rejects invalid combinations rather than validating at runtime.
  • Sensible defaults — the zero-config usage should already be correct and accessible.
  • Controllable where it matters — support controlled/uncontrolled for stateful inputs.

Code Example

// Discriminated union makes illegal prop combos a compile error
type ButtonProps =
  | { variant: 'link'; href: string; onClick?: never }
  | { variant: 'button'; onClick: () => void; href?: never };

// Forward rest + ref so consumers can extend the root element
const Button = React.forwardRef<HTMLButtonElement, ButtonProps &
  React.ButtonHTMLAttributes<HTMLButtonElement>>(
  ({ variant, className, ...rest }, ref) => (
    <button ref={ref} className={`btn btn--${variant} ${className ?? ''}`} {...rest} />
  )
);

Senior Engineer Perspective

This question separates people who've maintained a component library from those who've only consumed one. Strong signals: mentioning ref forwarding and rest-prop spreading (so your component drops into any layout), discriminated unions for variants, and the "boolean prop explosion" anti-pattern. Tie it back to earlier patterns: compound components and slots are how you achieve "composition over configuration."

SECTION 3 - STRUCTURE & BOUNDARIES

Q12. What is an error boundary, and why are they still class components in 2024/2025?

ROI: ★★★★★ Frequency: Extremely High

Short Answer

An error boundary is a component that catches JavaScript errors thrown during rendering, in lifecycle methods, and in constructors of its child tree, then renders a fallback UI instead of crashing the whole app. They must be class components because the catching mechanism — static getDerivedStateFromError and componentDidCatch — has never been given a hook equivalent. In practice you use the react-error-boundary library so you write it once.

Detailed Answer

Without a boundary, a render-time error unmounts the entire React tree (since React 16), leaving a blank page. A boundary scopes the blast radius: wrap a widget and only that widget shows a fallback while the rest of the app keeps working.

Two methods

  • static getDerivedStateFromError(error) — returns new state to render the fallback (runs during render, must be pure).
  • componentDidCatch(error, info) — side effects like logging to Sentry.

What they do NOT catch

Event handlers, asynchronous code (setTimeout, promises), server-side rendering, and errors thrown in the boundary itself. For event handlers you use a normal try/catch. This surprises many candidates.

Why still classes

The React team has said a hooks-based API is planned but not shipped; there is no useErrorBoundary to define a boundary. So either write the class or — the pragmatic choice — use react-error-boundary, which wraps the class and adds onReset, resetKeys, a FallbackComponent prop, and a useErrorBoundary() hook for imperatively triggering/resetting from child function components.

Code Example

class ErrorBoundary extends React.Component<
  { fallback: React.ReactNode; children: React.ReactNode },
  { hasError: boolean }
> {
  state = { hasError: false };

  static getDerivedStateFromError() {
    return { hasError: true };            // render fallback next
  }
  componentDidCatch(error: Error, info: React.ErrorInfo) {
    logToSentry(error, info.componentStack);   // side effect
  }
  render() {
    return this.state.hasError ? this.props.fallback : this.props.children;
  }
}

// Preferred in real apps — react-error-boundary
import { ErrorBoundary } from 'react-error-boundary';

<ErrorBoundary
  FallbackComponent={ErrorFallback}
  onReset={() => queryClient.clear()}
  resetKeys={[userId]}
>
  <Dashboard />
</ErrorBoundary>

Project Example

We wrapped each independent dashboard widget in its own boundary so a failing third-party chart couldn't take down billing data next to it. Each fallback offered a "Retry" button wired to resetErrorBoundary, and resetKeys tied to the selected date range so navigating away auto-cleared a stuck error. Pairing it with Sentry via componentDidCatch gave us component stacks, not just JS stacks.

Senior Engineer Perspective

The must-know trap: error boundaries do NOT catch errors in event handlers or async code — say this before they ask. Second signal: where you place boundaries — one at the app root for a global crash screen, plus granular ones around risky/independent subtrees. Third: mention that boundaries and Suspense are the same architectural idea (declarative fallback for an exceptional child state) — errors vs pending. Knowing that react-error-boundary exists signals real-world experience.

Q13. What is Suspense, and how does it act as a "boundary"?

ROI: ★★★★☆ Frequency: High

Short Answer

<Suspense fallback={...}> is a boundary that declaratively shows a fallback (a spinner/skeleton) while any component inside it is "suspended" — waiting on a lazy-loaded chunk or, with a Suspense-enabled data source, on data. Like error boundaries catch thrown errors, Suspense catches thrown promises, letting you express loading states structurally instead of threading isLoading flags through every component.

Detailed Answer

Mechanically, a suspending component throws a promise; the nearest Suspense boundary catches it, renders the fallback, and re-renders the children when the promise resolves. The two mainstream triggers today are React.lazy (code-splitting) and frameworks / libraries that support Suspense for data (Next.js App Router with RSC, TanStack Query's useSuspenseQuery, Relay).

Why it's powerful: loading state becomes composable and hoistable. You decide the granularity by where you place boundaries — one big fallback for a whole page, or many small ones for independent regions that stream in. React 18's concurrent features (startTransition, streaming SSR) build directly on Suspense so the UI stays responsive while content loads.

Code Example

// Nested boundaries give independent loading regions
<Suspense fallback={<PageSkeleton />}>
  <Header />
  <Suspense fallback={<WidgetSkeleton />}>
    <SlowRevenueWidget />      {/* streams in on its own */}
  </Suspense>
</Suspense>

// Combine with an error boundary — the two-boundary sandwich
<ErrorBoundary FallbackComponent={ErrorFallback}>
  <Suspense fallback={<Spinner />}>
    <Profile userId={id} />   {/* uses useSuspenseQuery */}
  </Suspense>
</ErrorBoundary>

Senior Engineer Perspective

Show you know the pairing idiom: wrap Suspense in an ErrorBoundary so success/pending/error are all declarative. Watch for the trap "can I use Suspense for data fetching in any app?" — only with a Suspense-aware source; you can't just wrap a raw fetch in an effect. Bonus depth: mention useTransition to avoid a fallback flashing when updating already-visible content, and RSC streaming where Suspense boundaries define HTML flush points.

Q14. What are portals, and why are they the right tool for modals and tooltips?

ROI: ★★★★☆ Frequency: High

Short Answer

ReactDOM.createPortal(children, domNode) renders children into a DOM node outside the parent's DOM hierarchy while keeping them in the React tree. This escapes CSS problems — overflow: hidden clipping, z-index stacking contexts, and transform containment — that plague modals, tooltips, dropdowns and toasts, which need to visually sit above everything regardless of where they're declared.

Detailed Answer

If you render a modal inside a deeply nested card that has overflow: hidden or its own stacking context, the modal gets clipped or trapped behind other content no matter how high its z-index. A portal moves the actual DOM output to, say, a <div id="modal-root"> at the end of <body>, sidestepping all ancestor CSS.

Crucially, the portal content is still logically inside the React tree: it keeps its place in the component hierarchy, so Context still flows in, and events bubble through the React tree (not the DOM tree) — a click inside a portalled modal bubbles to the React parent that rendered the portal, which can surprise people expecting DOM-based bubbling.

You still owe accessibility: focus trapping, role="dialog", aria-modal, restoring focus on close, and Escape handling. Portals solve the DOM-placement problem, not the a11y problem — which is why most teams use Radix Dialog / React Aria rather than hand-rolling.

Code Example

import { createPortal } from 'react-dom';

function Modal({ open, onClose, children }: {
  open: boolean; onClose: () => void; children: React.ReactNode;
}) {
  if (!open) return null;
  return createPortal(
    <div className="overlay" onClick={onClose}>
      <div className="dialog" role="dialog" aria-modal="true"
           onClick={(e) => e.stopPropagation()}>
        {children}
      </div>
    </div>,
    document.getElementById('modal-root')!    // node outside the app root
  );
}

Senior Engineer Perspective

The killer follow-up: "If it's rendered in body, does a click inside bubble to the component that rendered it?" Yes — event bubbling follows the React tree, not the DOM tree. Candidates who don't know this write buggy outside-click handlers. Also expect "why not just a high z-index?" — because a z-index only competes within its stacking context; an ancestor transform or overflow:hidden defeats it, and a portal is the robust fix.

Q15. How does lazy loading with React.lazy and Suspense work, and what are the pitfalls?

ROI: ★★★★☆ Frequency: High

Short Answer

React.lazy(() => import('./X')) defers loading a component's code until it first renders, producing a separate bundle chunk. You must render it inside a <Suspense> boundary that provides a fallback while the chunk downloads. It's the primary route- and feature-level code-splitting tool, cutting initial bundle size.

Detailed Answer

React.lazy takes a function returning a dynamic import() and returns a component that suspends until the module resolves. The bundler (Vite, webpack) sees the dynamic import and splits that module into its own chunk. The most common use is route-based splitting so each page loads on demand.

Pitfalls

  • Must be a default export — lazy expects the module's default; for named exports, re-map in the import.
  • Needs a Suspense boundary — otherwise React throws.
  • Chunk-load failures — after a deploy, old clients may request a hashed chunk that no longer exists; wrap in an error boundary and offer a reload.
  • Waterfalls — lazy-loading too granularly creates sequential fetches; prefetch on hover/intent for likely-next routes.
  • Don't lazy-load tiny components — the network round-trip costs more than the bytes saved.

Code Example

import { lazy, Suspense } from 'react';

// Route-level split; note the named-export re-map trick
const Settings = lazy(() => import('./Settings'));
const Reports  = lazy(() =>
  import('./Reports').then(m => ({ default: m.Reports }))  // named export
);

<ErrorBoundary FallbackComponent={ChunkErrorFallback}>
  <Suspense fallback={<PageSkeleton />}>
    <Routes>
      <Route path="/settings" element={<Settings />} />
      <Route path="/reports"  element={<Reports />} />
    </Routes>
  </Suspense>
</ErrorBoundary>

Project Example

An admin app had a heavy charting library only used on one analytics page. Lazy-loading that route dropped the initial bundle by ~40%. We added a hover-prefetch on the nav link so the chunk was usually warm by the time users clicked, and wrapped it in an error boundary that showed "A new version is available — reload" after we hit stale-chunk errors following deploys.

Senior Engineer Perspective

Two follow-ups distinguish seniors. First, the stale-chunk problem after deployment — knowing it exists and that an error boundary + reload (or route-revalidation) is the fix shows production scars. Second, prefetching strategy: lazy alone creates a loading gap; smart teams prefetch on intent (hover, viewport, or after idle). In Next.js, note this is handled by the framework (route segments, next/dynamic) rather than raw React.lazy.

Q16. What is state colocation, and how do you solve prop drilling without over-reaching for global state?

ROI: ★★★★★ Frequency: Extremely High

Short Answer

State colocation means keeping state as close as possible to where it's used — push it down to the component that needs it, or lift it only as high as the nearest common ancestor. Prop drilling (threading a prop through many intermediate components that don't use it) is a symptom, and the fix ladder is: colocate/lift → component composition (children/slots) → Context (for truly cross-cutting values) → a state library (for high-frequency or app-wide state). Jumping straight to global state is the anti-pattern.

Detailed Answer

The colocation principle

Global state that only one leaf uses causes unnecessary re-renders and coupling. Ask "who reads this?" and place it at their nearest common ancestor — often much lower than the app root. Colocated state re-renders a smaller subtree and keeps components portable.

The prop-drilling fix ladder

  • Composition first — a lot of drilling disappears if you pass JSX as children/slots instead of passing data down to build that JSX. The intermediate component just renders children and never sees the prop.
  • Context — for values that are genuinely cross-cutting and low- frequency: theme, current user, locale, auth. Not for everything.
  • State libraries — Zustand/Jotai/Redux Toolkit for app-wide, frequently-updated, or selector-driven state; TanStack Query for server state, which shouldn't live in your global client store at all.

A key modern distinction: much of what people call "global state" is actually server state (fetched data). Moving it to TanStack Query/RTK Query eliminates a huge amount of drilling and manual caching, leaving only genuine UI state to manage.

Code Example

// PROBLEM: drilling `user` through Layout & Sidebar that don't use it
<Layout user={user}>
  <Sidebar user={user} />      // Sidebar only forwards it onward
</Layout>

// FIX 1 — composition: pass rendered JSX as children, no drilling
function Layout({ children }: { children: React.ReactNode }) {
  return <div className="layout">{children}</div>;
}
<Layout>
  <Sidebar>
    <UserBadge user={user} />   // built at the top, where `user` already lives
  </Sidebar>
</Layout>

// FIX 2 — Context for a truly cross-cutting value
const user = useCurrentUser();   // reads from AuthProvider, no drilling

Senior Engineer Perspective

The mistake juniors make is treating "prop drilling → put it in Redux/Context" as the only move. Seniors reach for composition first — Michael Jackson's "just pass children" insight — because it removes drilling without any new machinery or re-render cost. Be ready for "when is Context the wrong choice?": when the value changes often, since Context re-renders all consumers with no selector. And separate server state from client state — conflating them is the root cause of most bloated global stores.
