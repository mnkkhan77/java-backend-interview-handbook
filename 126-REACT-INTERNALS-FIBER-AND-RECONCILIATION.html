SECTION 1 - VIRTUAL DOM & RECONCILIATION

Q1. What is the Virtual DOM really, and what is the common misconception about it?

ROI: ★★★★★ Frequency: Extremely High

Short Answer

The Virtual DOM (VDOM) is just a tree of plain JavaScript objects (React elements) describing what the UI should look like. The common misconception is that the VDOM is inherently "fast" or that diffing is faster than touching the DOM. It is not — the real DOM is not slow to read/write; it is slow to lay out and paint. The VDOM's actual value is a declarative programming model plus batched, minimal mutations, not raw speed.

Detailed Answer

When you write JSX, Babel compiles it into React.createElement (or the newer jsx() runtime) calls. Each call returns a lightweight object — the React element — with fields like type, props, and key. This tree of objects is what people casually call the "Virtual DOM." It is cheap to create and cheap to compare because it lives entirely in memory as JS objects.

The misconception

Many candidates say "the VDOM is faster than the DOM." That is wrong and interviewers pounce on it. Direct, targeted DOM operations (e.g. el.textContent = "x") are extremely fast. What is expensive is layout thrashing, reflow, repaint, and doing many uncoordinated writes interleaved with reads. React's win is that it computes the minimal set of DOM operations and applies them in one coordinated commit, avoiding redundant and interleaved work. The abstraction also lets you describe UI as a pure function of state — UI = f(state) — which is the real productivity win.

Element vs. Fiber vs. DOM node

  • React element: immutable description created on every render (the "VDOM").
  • Fiber: a mutable internal work object that persists across renders and holds state, effects, and pointers.
  • DOM node: the actual host instance in the browser.

The VDOM is the input to reconciliation; fibers are the machinery; DOM nodes are the output.

Code Example

// JSX
const el = <button className="primary" onClick={fn}>Save</button>;

// Compiles (modern automatic runtime) to roughly:
import { jsx as _jsx } from "react/jsx-runtime";
const el = _jsx("button", {
  className: "primary",
  onClick: fn,
  children: "Save",
});

// The resulting element is just a plain object:
// {
//   $$typeof: Symbol(react.element),
//   type: "button",
//   key: null,
//   props: { className: "primary", onClick: fn, children: "Save" },
// }

Project Example

In a dashboard that re-renders a large table on every keystroke of a filter input, the VDOM does not make this free. If each render produces 5,000 elements, React still diffs 5,000 nodes. The perf fix (virtualization, memoization, keys) exists precisely because the VDOM is not magic — you still pay for the tree you produce.

Senior Engineer Perspective

The interviewer wants to hear that you understand the VDOM is a strategy, not a performance guarantee. A strong follow-up trap: "So would hand-written DOM code be faster?" The honest senior answer is yes, hand-optimized imperative code can beat React for a specific case — React trades a small, predictable overhead for maintainability and a correct declarative model. Frameworks like Svelte and Solid skip the VDOM entirely by compiling to fine-grained updates, which proves the VDOM is a design choice, not a law of physics.

Q2. What is reconciliation and what heuristics does React's diffing algorithm use?

ROI: ★★★★★ Frequency: Extremely High

Short Answer

Reconciliation is the process of comparing the newly rendered element tree with the previous one to determine the minimal set of updates. A general tree-diff is O(n³), which is unusable, so React uses an O(n) heuristic based on two assumptions: (1) elements of different types produce different trees, and (2) developers can hint stable identity across renders with keys.

Detailed Answer

The two core heuristics

  • Different element type ⇒ tear down and rebuild. If the type changes (<div> → <span>, or <Profile> → <Feed>), React unmounts the old subtree entirely (destroying its state and DOM) and builds the new one from scratch. It does not try to match children across different parent types.
  • Same type ⇒ reuse the node, patch props. If the type is identical, React keeps the same DOM node / component instance, updates only the changed attributes, and recurses into children. Component state is preserved.

Diffing lists of children

Without keys, React compares children by position/index. If you insert an item at the front of a list, every subsequent element now sits at a shifted index, so React sees "type matches at each position" and mutates all of them instead of just inserting one. Keys break this positional assumption by giving each child a stable identity, letting React match old and new children by key regardless of position.

Why the tradeoff is acceptable

The heuristic can be "wrong" (it may rebuild a subtree that a perfect diff would have preserved), but in practice UI trees rarely move a component to a fundamentally different type or position, so the O(n) approximation is both fast and good enough.

Code Example

// Same type: node reused, only className patched. Input keeps focus/value.
// render A:
<div className="a"><input /></div>
// render B:
<div className="b"><input /></div>   // patch className only

// Different type: full teardown. The <input> is destroyed and recreated,
// so its internal DOM state (focus, uncontrolled value) is LOST.
// render A:
<div><input /></div>
// render B:
<span><input /></span>  // unmount div subtree, mount span subtree

Project Example

A classic bug: conditionally swapping a wrapper element between <div> and <section> around a form. Users report that the form resets mid-typing. The cause is the type change forcing a teardown. The fix is to keep the wrapper type stable and toggle a class, or to lift the swapped part so the stateful subtree stays under a constant-type parent.

Senior Engineer Perspective

Interviewers love to ask "why is the diff O(n) and not O(n³)?" The senior answer names the assumptions explicitly. A deeper follow-up: "Can two components of the same type but different logical meaning get incorrectly reused?" Yes — this is the "state leaking between screens" bug, and the deliberate fix is to give them a different key to force remount, or a different type. Understanding that key can force a remount even for the same type is a senior-level insight.

Q3. Why do keys matter at the algorithm level — not just "React warns me"?

ROI: ★★★★★ Frequency: Extremely High

Short Answer

Keys give list children a stable identity independent of their position. During child reconciliation React builds a map from key to the previous fiber, so it can match, move, insert, and delete by identity in O(n) instead of assuming position equals identity. Using the array index as a key throws this benefit away and can corrupt component state when the list reorders.

Detailed Answer

How keyed reconciliation runs

React first walks old and new children together as long as keys match in order (the fast common path — appends at the end). When it hits a mismatch, it builds a Map<key, oldFiber> of the remaining old children. Then for each remaining new child it looks up its key in that map: a hit means "move/reuse the existing fiber and its state," a miss means "create a new fiber." Anything left in the map at the end is deleted. That is how it achieves single moves instead of cascading patches.

Why index keys are dangerous

With key={index}, identity is tied to position. Prepend an item and every existing item's key shifts. React now maps old fiber at key 0 (formerly item A) onto new item at key 0 (now item B), so it reuses A's state/DOM for B. The visible symptom is inputs, checkboxes, or animations showing the wrong row's data. Index keys are only safe for static lists that never reorder, insert, or delete.

Code Example

// BAD: state follows position, not identity.
{items.map((item, i) => (
  <TodoRow key={i} todo={item} />   // reorder => wrong row keeps focus/checkbox
))}

// GOOD: state follows the logical item.
{items.map((item) => (
  <TodoRow key={item.id} todo={item} />
))}

// Force a remount on purpose by changing the key:
<UserProfile key={userId} id={userId} />
// switching userId unmounts old profile + mounts fresh (clears internal state)

Project Example

A chat app rendered messages with key={index}. When a new message arrived at the top (newest-first), the "message being edited" textarea suddenly showed a different message's text — because editing state stayed pinned to index 0. Switching to key={message.id} fixed it instantly with zero other changes.

Senior Engineer Perspective

The nuance that separates seniors: keys are local to their sibling list (they need only be unique among siblings, not globally) and they are a reconciliation hint, never rendered to the DOM. A great follow-up to nail: "When is changing a key a feature, not a bug?" Answer: intentionally resetting a subtree's state — e.g. remounting a form when the selected record changes, or restarting an animation. Also mention that a truly stable business ID beats Math.random() or index-derived keys, which either remount everything every render or misalign state.

SECTION 2 - FIBER ARCHITECTURE

Q4. What is the Fiber architecture and why did it replace the stack reconciler?

ROI: ★★★★★ Frequency: High

Short Answer

Fiber (shipped in React 16) is a reimplementation of the reconciler that represents the work as a linked-list tree of "fiber" objects instead of relying on the JavaScript call stack. The old "stack reconciler" processed the whole tree in one deep, synchronous, recursive pass that could not be paused. Fiber makes rendering incremental and interruptible: React can do a unit of work, yield to the browser, and resume — the foundation for prioritization, time-slicing, and concurrency.

Detailed Answer

The problem with the stack reconciler

The pre-16 reconciler used recursion. Once it started reconciling a large tree, the call stack was in control and there was no way to stop partway, check whether something more urgent (like user input) arrived, and come back. A big update could block the main thread long enough to drop frames and make typing feel janky.

What Fiber changes

Fiber turns recursion into iteration over a data structure React controls. Each element gets a fiber node, and the tree is linked via child, sibling, and return (parent) pointers. Because React manually walks these pointers in a loop, it can stop after any single fiber, hand control back to the browser via the scheduler, and continue later exactly where it left off — the loop's position is saved in a variable, not buried in the native stack.

What it enabled

  • Splitting work into units and yielding between them (time-slicing).
  • Assigning priority so urgent updates preempt low-priority ones.
  • Aborting in-progress renders (e.g. when newer state arrives) without corrupting the DOM, because nothing is committed until render completes.

Code Example

// Conceptual work loop (simplified from React internals):
function workLoopConcurrent() {
  // keep working until we run out of fibers OR the browser needs the thread
  while (workInProgress !== null && !shouldYield()) {
    workInProgress = performUnitOfWork(workInProgress);
  }
}

function performUnitOfWork(fiber) {
  const next = beginWork(fiber);     // process this fiber, create child fibers
  if (next === null) completeUnitOfWork(fiber); // no child => complete + go to sibling
  return next;                       // return next fiber to process (or null)
}

Project Example

On a search page that renders a heavy results grid, typing used to feel laggy because each keystroke's re-render blocked input. Under Fiber + concurrent features, wrapping the results update in useTransition lets React keep the input responsive and render the expensive grid at lower priority, pausing it whenever new keystrokes arrive.

Senior Engineer Perspective

A key trap: "Fiber made React async/multithreaded." No — JavaScript is still single-threaded, and Fiber's render can still be synchronous. Fiber makes work divisible and schedulable on the same thread. The 16.x release shipped the Fiber data structure and incremental rendering internally, but concurrency features were gated and only became broadly usable in React 18. Being precise about that timeline signals real depth.

Q5. What exactly is a fiber node?

ROI: ★★★★ Frequency: High

Short Answer

A fiber is a mutable JavaScript object that represents one unit of work and corresponds to one element/component instance. It stores what to render (type, pendingProps), the component's persisted state (hooks via memoizedState), tree pointers (child, sibling, return), scheduling info (lanes, flags), and a link (alternate) to its counterpart in the other tree.

Detailed Answer

Unlike React elements (which are immutable and recreated every render), fibers persist across renders and are reused/mutated. That persistence is what lets a component keep its state and effects between renders.

Important fields on a fiber:

FieldPurpose
typeThe component function/class or host tag ("div").
keyReconciliation identity among siblings.
stateNodeThe associated instance: DOM node, class instance, or root.
child / sibling / returnTree links: first child, next sibling, parent.
pendingProps / memoizedPropsIncoming props vs. props from the last committed render.
memoizedStateFor function components, the head of the hooks linked list.
updateQueueQueued state updates / effects to process.
lanesPriority bitmask for pending work on this fiber.
flags (effectTag)What DOM effect to perform at commit (Placement, Update, Deletion).
alternatePointer to this fiber's counterpart in the other (current / WIP) tree.

Code Example

// Shape of a fiber (heavily simplified):
const fiber = {
  type: MyComponent,        // or "div"
  key: null,
  stateNode: null,          // DOM node or class instance
  return: parentFiber,
  child: firstChildFiber,
  sibling: nextSiblingFiber,
  pendingProps: { color: "red" },
  memoizedProps: { color: "blue" },
  memoizedState: firstHook, // linked list of hooks
  updateQueue: null,
  lanes: 0b0000000000000000000000000010000,
  flags: 0b0000000000000010, // Update
  alternate: workInProgressCounterpart,
};

Project Example

When you inspect a component in React DevTools and see its hooks and props, DevTools is reading the fiber's memoizedState and memoizedProps. Understanding that "the thing that remembers my state between renders is a fiber, not the element" is exactly what demystifies why moving a hook or changing an element's type wipes state.

Senior Engineer Perspective

The name "fiber" comes from cooperative-multitasking fibers/coroutines — lightweight units of work that yield voluntarily. The interviewer may probe the element-vs-fiber distinction: elements are throwaway descriptions produced by your render function; fibers are React's long-lived internal representation. State lives on the fiber; that is why an element being recreated every render does not lose your useState value.

Q6. What is double buffering — the current tree vs. the work-in-progress tree?

ROI: ★★★★ Frequency: High

Short Answer

React keeps two fiber trees. The current tree reflects what is on screen. When an update happens, React builds a work-in-progress (WIP) tree by cloning fibers from current. All rendering work mutates the WIP tree only. On a successful commit, React atomically swaps the pointer so the WIP tree becomes the new current tree. Each fiber links to its counterpart via alternate, so the two trees can be reused instead of reallocated.

Detailed Answer

Why two trees

This is the same idea as graphics double buffering: you draw the next frame off-screen and flip it in one operation so the user never sees a half-drawn frame. Because rendering under Fiber can be interrupted or thrown away, React must never mutate the tree that is currently on screen mid-render. All in-progress work lives on the WIP tree; if the render is aborted, React simply discards the WIP tree and the on-screen current tree is untouched — no torn UI.

The alternate pointer

Each current fiber has an alternate pointing to its WIP counterpart and vice versa. Instead of allocating brand-new fibers every render, React reuses the alternate as the WIP fiber (a technique it calls "cloning" via createWorkInProgress). After commit, the roles flip: last render's current becomes next render's WIP buffer.

The single flip that makes the WIP tree "current" is root.current = finishedWork, performed during commit between the mutation and layout sub-phases.

Code Example

// Reusing the alternate as the work-in-progress fiber (conceptual):
function createWorkInProgress(current, pendingProps) {
  let wip = current.alternate;
  if (wip === null) {
    wip = createFiber(current.type, pendingProps, current.key);
    wip.stateNode = current.stateNode; // share the real DOM node
    wip.alternate = current;
    current.alternate = wip;
  } else {
    wip.pendingProps = pendingProps;
    wip.flags = 0; // reset effect flags for the new render
  }
  wip.child = current.child;
  wip.memoizedState = current.memoizedState;
  return wip;
}

// After a successful render, the commit flips the pointer:
// fiberRoot.current = finishedWorkInProgressTree;

Project Example

This is why an interrupted concurrent render never shows a "half-updated" screen. If a user types while a low-priority useDeferredValue render is in flight, React can throw away that WIP tree and start over — the visible current tree was never touched, so there is no flicker or inconsistent intermediate state.

Senior Engineer Perspective

The insight interviewers want: the two-tree design is what makes interruptible rendering safe. A good follow-up: "Why can't React just mutate one tree incrementally?" Because a partially-mutated single tree would either be visible to the user (tearing) or unrecoverable if the render is cancelled. Double buffering gives an atomic swap and clean rollback. Note the DOM node itself (stateNode) is shared between the two fibers — only the fiber bookkeeping is duplicated, not the heavy host objects.

SECTION 3 - RENDERING PHASES

Q7. What is the difference between the render phase and the commit phase?

ROI: ★★★★★ Frequency: High

Short Answer

The render phase builds the WIP tree by calling components and computing what changed. It is pure, can be paused, resumed, restarted, or discarded, and must have no side effects. The commit phase applies the computed changes to the real DOM and runs effects. It is synchronous, cannot be interrupted, and is where side effects (DOM mutations, layout effects, passive effects) actually happen.

Detailed Answer

Render phase (interruptible, must be pure)

React walks fibers, calls each component function (running its hooks), and diffs against the current tree, tagging fibers with effect flags (Placement, Update, Deletion). Nothing is written to the DOM yet. Because this phase may run more than once for a single visible update (React can restart it), your render must be side-effect free — this is exactly why Strict Mode double-invokes components in development: to surface impure render logic.

Commit phase (synchronous, three sub-phases)

  • Before mutation: e.g. getSnapshot for useSyncExternalStore; snapshots for class getSnapshotBeforeUpdate.
  • Mutation: apply DOM insertions/updates/deletions; run useLayoutEffect cleanups; the root.current pointer is flipped here.
  • Layout: run useLayoutEffect setups and refs synchronously (DOM is updated but browser has not painted yet).

useEffect (passive effects) runs after paint, asynchronously, so it does not block the browser from showing the frame.

Code Example

function Box() {
  // RENDER PHASE: called here. Keep pure. May run 0..N times per update.
  const [w, setW] = React.useState(0);

  // COMMIT / LAYOUT: runs synchronously before paint. Use for DOM reads
  // that must be consistent with the mutation (e.g. measuring layout).
  React.useLayoutEffect(() => {
    const rect = ref.current.getBoundingClientRect();
    setW(rect.width); // sync reflow-safe update, no visible flicker
  });

  // COMMIT / PASSIVE: runs after paint. Use for non-visual side effects.
  React.useEffect(() => {
    analytics.track("box_shown");
  }, []);

  const ref = React.useRef(null);
  return <div ref={ref}>{w}</div>;
}

Project Example

A tooltip that measures an element and repositions itself must use useLayoutEffect, not useEffect — measuring in a passive effect happens after paint, so the user sees the tooltip flash in the wrong spot for one frame before it jumps. Understanding which phase runs before vs. after paint is the difference between a smooth and a janky component.

Senior Engineer Perspective

The trap: "Why can't I do side effects during render?" Because the render phase may be run speculatively and thrown away — a network call or a ref mutation there could fire multiple times or against a tree that never commits. A senior candidate connects this to Strict Mode's intentional double-render and double-effect in dev, and explains that useLayoutEffect blocking paint is a deliberate tradeoff: correctness of visual layout at the cost of a synchronous, potentially janky step, so it should be used sparingly.

Q8. How does the work loop enable interruptible rendering?

ROI: ★★★★ Frequency: Medium

Short Answer

React processes fibers one at a time in a loop (performUnitOfWork). In concurrent mode the loop checks shouldYield() after each unit; if the current time-slice (about 5ms) is exhausted or the browser needs the thread, React saves its position in the workInProgress pointer, yields, and schedules a callback to resume. Because the loop state is a variable — not the native call stack — it can pause and resume across browser tasks.

Detailed Answer

begin work and complete work

The loop has two halves. beginWork descends: it processes a fiber, reconciles its children, and returns the first child to work on next. When a fiber has no child, completeUnitOfWork runs: it "completes" the fiber (for host components, it creates/prepares the DOM instance and bubbles effect flags up), then moves to the sibling, or up to the parent if there is no sibling. This traversal visits every fiber without recursion.

Yielding

Between units, concurrent React consults the scheduler. The scheduler uses a deadline model — historically approximated with MessageChannel to schedule a macrotask (not requestIdleCallback, which proved too unreliable). If the deadline passes, shouldYield() returns true, the loop breaks, and control returns to the browser so it can paint and handle input. React resumes from the saved workInProgress fiber later.

Legacy/synchronous rendering uses the same loop but never yields (workLoopSync), which is why pre-concurrent React could block the thread.

Code Example

// Concurrent vs sync loops share performUnitOfWork; only yielding differs.
function workLoopSync() {
  while (workInProgress !== null) {
    workInProgress = performUnitOfWork(workInProgress); // never yields
  }
}

function workLoopConcurrent() {
  while (workInProgress !== null && !shouldYield()) {
    workInProgress = performUnitOfWork(workInProgress); // yields per time-slice
  }
  // if workInProgress !== null here, schedule a continuation and return
}

Project Example

Rendering a 10,000-row report client-side used to freeze the tab for a second. Marking the report update as a transition lets the concurrent work loop render it in ~5ms slices, yielding between slices so the browser keeps painting a loading indicator and responding to a Cancel click. The total work is the same; it is just chopped up so the main thread is never hostage.

Senior Engineer Perspective

Be precise: yielding happens only during the render phase. The commit phase always runs to completion synchronously — you cannot have a half-committed DOM. A sharp follow-up: "Does yielding make total render faster?" No, it makes the app more responsive by not monopolizing the thread; wall-clock render time may even be slightly longer due to scheduling overhead. That responsiveness-vs-throughput tradeoff is the whole point of concurrency.

Q9. How are hooks stored on a fiber, and why do the Rules of Hooks exist at this level?

ROI: ★★★★★ Frequency: High

Short Answer

Hooks are stored as a singly linked list on the fiber's memoizedState, appended in call order during render. React identifies which hook is which purely by call order, not by name. That is why hooks must be called unconditionally at the top level — conditional or looped calls would shift the order and make React read the wrong slot for the wrong hook.

Detailed Answer

The linked list

On the first render (mount), each hook call creates a hook object { memoizedState, queue, next } and links it after the previous one; the head is stored on fiber.memoizedState. On subsequent renders (update), React walks that same list in order, returning the next hook each time a hook is called. There is a cursor pointing at the "current hook." No keys, no names — position in the list is the identity.

Why the Rules of Hooks are not arbitrary

If you wrote if (cond) useState(), then on renders where cond is false the list has one fewer node. React's cursor would then hand the next hook the state that belonged to a different hook — e.g. your effect's closure ends up reading a piece of state, or a useState receives another hook's queue. The result is corrupted state and crashes. The lint rule eslint-plugin-react-hooks enforces the constraint statically because the runtime has no way to recover.

How React knows mount vs update

React swaps the internal "dispatcher" (a set of hook implementations) depending on whether the fiber is mounting or updating, so useState resolves to mountState or updateState accordingly. Calling a hook outside a component's render means no dispatcher is set, which is why you get "Invalid hook call."

Code Example

// The hooks list built during render — order IS the identity:
function Profile() {
  const [name, setName] = useState("");   // hook #0
  const [age, setAge]   = useState(0);    // hook #1
  useEffect(() => {}, [name]);            // hook #2
}
// fiber.memoizedState ->
//   { state: "", queue, next ->
//     { state: 0,  queue, next ->
//       { deps: [name], next: null } } }

// WHY THIS BREAKS:
function Bad({ show }) {
  if (show) useState("x"); // hook #0 exists only sometimes
  const [count, setCount] = useState(0); // slot shifts between renders!
}

Project Example

A teammate wrapped a useMemo in an early-return guard to "skip work when data was missing." Intermittently the component crashed with "rendered fewer hooks than expected." The linked-list model explains it exactly: the early return changed how many hooks ran between renders. The fix was to always call the hook and put the condition inside it.

Senior Engineer Perspective

Interviewers use this to test whether you understand hooks mechanically or just cargo-cult the rules. Strong signals: naming that identity is by index/order, that state lives on the fiber (so it survives re-renders but is wiped on unmount/remount or key change), and that custom hooks are just functions that borrow the calling component's hook list — which is why a custom hook must also obey the same ordering rules. A subtle point: two components using the same custom hook each get their own hooks on their own fibers; there is no shared state unless you add it via context or an external store.

SECTION 4 - SCHEDULING, CONCURRENCY & OPTIMIZATION

Q10. What is batching, and what changed with automatic batching in React 18?

ROI: ★★★★★ Frequency: Extremely High

Short Answer

Batching means grouping multiple state updates into a single re-render for efficiency. Before React 18, batching happened only inside React event handlers; updates in promises, setTimeout, or native events each triggered a separate render. React 18's automatic batching extends batching to all contexts (as long as you use createRoot), so multiple setState calls anywhere collapse into one render.

Detailed Answer

Before React 18

React batched updates that occurred within its synthetic event handlers because it controlled the entry point. But an update inside a fetch().then() or setTimeout escaped that boundary, so two updates caused two renders — extra work and potential intermediate states.

React 18 automatic batching

With createRoot, React batches updates regardless of where they originate — event handlers, promises, timeouts, native handlers. It schedules the work and processes queued updates together in one render pass. This is generally a pure win: fewer renders, no visible intermediate states.

Opting out

If you genuinely need a synchronous, flushed update between two updates (rare — usually third-party DOM integration), flushSync forces React to commit immediately. Overusing it defeats batching and hurts performance.

ContextLegacy (ReactDOM.render)React 18 (createRoot)
React event handlerBatchedBatched
setTimeout / PromiseNOT batchedBatched
Native / addEventListenerNOT batchedBatched

Code Example

// React 18 with createRoot: ONE render, not two.
function handleClick() {
  setCount(c => c + 1);
  setFlag(f => !f);          // batched together => single re-render
}

// Also batched in React 18 (was TWO renders pre-18):
fetch("/api").then(() => {
  setCount(c => c + 1);
  setFlag(f => !f);          // still one render in v18
});

// Force a synchronous flush when you truly must:
import { flushSync } from "react-dom";
flushSync(() => setCount(c => c + 1)); // commits now
doDomMeasurementThatNeedsUpdatedDom();

Project Example

After upgrading a checkout flow to React 18, a bug where a loading spinner flashed twice disappeared — previously two updates inside a payment promise caused two renders and two intermediate paints. Automatic batching collapsed them into one, and the UI became visibly smoother with zero code changes.

Senior Engineer Perspective

The classic trap is the functional-updater question: "Why does setCount(count + 1); setCount(count + 1) only add 1?" Because both reads capture the same stale count from the render's closure; batching then applies both to the same base. Using the updater form setCount(c => c + 1) queues both against the latest value and adds 2. A senior also notes that automatic batching requires createRoot — an app still on legacy ReactDOM.render won't get it — and that flushSync is an escape hatch, not a habit.

Q11. What are lanes and priorities in concurrent React?

ROI: ★★★★ Frequency: Medium

Short Answer

Lanes are React's internal priority model, implemented as a 31-bit bitmask where each bit (or group of bits) is a "lane" representing a class of work — e.g. synchronous/discrete input, default, transition, and idle. Each update is assigned a lane based on its urgency; the scheduler renders the highest-priority pending lanes first and can interrupt lower-priority work when something more urgent arrives.

Detailed Answer

Why a bitmask

Lanes replaced the older "expiration time" model. A bitmask lets React represent a set of pending priorities on a fiber and combine/compare them with cheap bitwise operations. Multiple updates of different priorities can be batched or separated by lane. When React picks work, it selects the set of lanes to render and leaves lower-priority lanes for later passes.

Priority tiers (conceptual)

  • Discrete / sync: clicks, typing, key presses — must feel instant, highest priority.
  • Default: normal updates like data arriving from a fetch.
  • Transition: updates marked with startTransition/useTransition — non-urgent UI that can be interrupted.
  • Idle / offscreen: lowest, e.g. prerendering hidden content.

How the API maps to lanes

useTransition and startTransition mark updates as transition-lane work so a fast, urgent update (like the input value) can preempt an expensive transition render. useDeferredValue similarly schedules a lower-priority "deferred" copy of a value. You never touch lanes directly, but these hooks are the developer-facing surface of the lane model.

Code Example

function Search() {
  const [query, setQuery] = React.useState("");
  const [results, setResults] = React.useState([]);
  const [isPending, startTransition] = React.useTransition();

  function onChange(e) {
    setQuery(e.target.value);            // urgent lane: keeps input snappy
    startTransition(() => {               // transition lane: interruptible
      setResults(computeExpensiveList(e.target.value));
    });
  }

  return (
    <>
      <input value={query} onChange={onChange} />
      {isPending && <Spinner />}
      <List items={results} />
    </>
  );
}

Project Example

On a filter-as-you-type analytics view, the input froze whenever the chart recomputed. Wrapping the chart-data update in startTransition put it on the transition lane, so React kept the keystroke updates on the urgent lane and interrupted/restarted the chart render on each new character — the input stayed at 60fps while the chart caught up slightly behind.

Senior Engineer Perspective

You are not expected to recite the exact 31 lanes, but you should convey the model: priority as a bitmask, urgent updates preempting transitions, and the developer APIs (useTransition, useDeferredValue) that ride on it. A sharp follow-up: "How is a transition different from a debounce?" A debounce delays firing the update on a timer and still blocks once it fires; a transition fires immediately but renders at low priority and is interruptible, so the urgent UI never blocks. That distinction is a strong senior signal.

Q12. How is a state update actually scheduled, from setState to a painted screen?

ROI: ★★★★ Frequency: Medium

Short Answer

Calling a state setter creates an update object, enqueues it on the fiber's update queue with a lane, and calls scheduleUpdateOnFiber. React marks the path from that fiber to the root as having pending work, then asks the scheduler to run a render at the appropriate priority. The scheduler eventually invokes the work loop (render phase), then React commits, and the browser paints.

Detailed Answer

The lifecycle of one update:

  1. Dispatch: setState(x) (really the hook's dispatch) creates an update { lane, action, next } and appends it to the hook's circular update queue.
  2. Schedule: scheduleUpdateOnFiber assigns a lane and walks return pointers up to the FiberRoot, OR-ing the lane into each fiber's childLanes so React knows which paths have work.
  3. Ensure a render is scheduled: React asks the Scheduler package to run a callback at a priority matching the lane (sync work may run before paint via a microtask-like flush; transitions run via the concurrent scheduler).
  4. Render phase: the work loop builds the WIP tree, replaying the update queue to compute new state, and diffs to tag effects.
  5. Commit phase: React applies DOM mutations, flips root.current, runs layout effects, then passive effects after paint.

A key optimization: if, during render, the new state computed for a fiber is identical (via Object.is) and nothing else changed, React can bail out and skip re-rendering that subtree (see next question).

Code Example

// What a hook dispatch roughly does:
function dispatchSetState(fiber, queue, action) {
  const lane = requestUpdateLane(fiber);       // pick priority
  const update = { lane, action, next: null };
  enqueueUpdate(queue, update);                // append to circular queue
  scheduleUpdateOnFiber(fiber, lane);          // mark root, ask scheduler to render
}

// Eager bailout: if the new state equals the current, skip the render.
const current = queue.lastRenderedState;
const next = typeof action === "function" ? action(current) : action;
if (Object.is(next, current)) {
  // no scheduled render needed
}

Project Example

A component called setStatus("idle") on every websocket heartbeat even though status was already "idle." Profiling showed no re-renders — React's Object.is bailout at dispatch time recognized the value was unchanged and skipped scheduling entirely. Knowing this prevented a "premature optimization" PR to guard the call manually.

Senior Engineer Perspective

Interviewers probe whether you know updates are asynchronous and queued, not applied immediately. The updater form matters because updates are replayed against the base state in order during render. Another nuance: even after a dispatch-time bailout on the setter, if the component re-renders for another reason, React still runs the component function but can bail out of updating children. Distinguishing "the component function re-ran" from "the DOM was updated" is a mature distinction that avoids false conclusions when profiling.

Q13. How do bailouts and internal memoization avoid re-rendering?

ROI: ★★★★ Frequency: Medium

Short Answer

During beginWork, if a fiber's props and state are unchanged and it has no pending update in the current lanes, React bails out: it clones the existing children without re-rendering them (bailoutOnAlreadyFinishedWork). React.memo, useMemo, and useCallback help create the referential stability that lets these bailouts fire, so unrelated subtrees are skipped entirely.

Detailed Answer

The two levels of bailout

  • Whole-subtree bailout: if a fiber has no work in the current lanes and its props are referentially equal, React reuses its child fibers as-is and does not descend — the entire subtree is skipped.
  • Component-level bailout: even when a parent re-renders, a child wrapped in React.memo is skipped if its props are shallowly equal to last time. Without memo, a child re-renders whenever its parent does, regardless of prop equality.

Why referential stability matters

Bailouts compare props by identity (shallow). If a parent passes a new object/array/function literal every render, the child's props are "different" each time and the bailout can't fire. useMemo/useCallback preserve the same reference across renders so memoized children can bail out. This is why "just wrap everything in memo" often does nothing — the props keep changing identity upstream.

State bailout

If a useState/useReducer update produces a value Object.is-equal to the current, React bails out of that update. If it is the only pending update, the component won't even re-render.

Code Example

const Child = React.memo(function Child({ config, onSave }) {
  return <button onClick={onSave}>{config.label}</button>;
});

function Parent({ label }) {
  const [n, setN] = React.useState(0);

  // WITHOUT these, config/onSave are new refs each render => memo useless.
  const config = React.useMemo(() => ({ label }), [label]);
  const onSave = React.useCallback(() => save(), []);

  return (
    <>
      <button onClick={() => setN(n + 1)}>{n}</button>
      <Child config={config} onSave={onSave} />  {/* bails out on n change */}
    </>
  );
}

Project Example

A settings page re-rendered a heavy <PermissionMatrix> on every keystroke in an unrelated name field. The matrix was already React.memo-wrapped, but a columns array was rebuilt inline each render, defeating the bailout. Memoizing columns with useMemo restored the bailout and dropped the matrix's renders to zero for name edits.

Senior Engineer Perspective

The senior message: memoization is about enabling bailouts, and bailouts propagate — skipping a fiber skips its whole subtree, which is where the real savings come from. Two important caveats: (1) React.memo does a shallow prop compare, so a stable-reference-but-deeply-changed object still bails incorrectly — pass a custom comparator or restructure props; (2) the React 19 Compiler auto-memoizes, potentially removing the need for manual useMemo/useCallback — a forward-looking candidate mentions this as the direction of travel while still explaining the underlying mechanism.

Q14. How does Context propagation work internally, and why can it be a performance trap?

ROI: ★★★★ Frequency: High

Short Answer

When a Context Provider's value changes (by Object.is), React does a special traversal from the provider down, finding every consumer of that context and marking it for an update — bypassing the normal bailout that would otherwise skip unchanged subtrees. So every consumer re-renders when the value's reference changes, even components that only use one field of the value. That's the trap: an unstable or coarse-grained value re-renders the whole consumer set.

Detailed Answer

Propagation mechanism

Context does not rely on prop drilling through the tree. Each consumer fiber records a dependency on the context object during render. When the provider commits a new value, React runs propagateContextChange: it walks the subtree and, for any fiber depending on that context, schedules an update and marks the path so the work loop reaches it — even if intermediate components would have bailed out. This is why a React.memo wrapper does not stop a context-driven re-render of a consumer.

The performance trap

  • Unstable value: <Ctx.Provider value={{ user, theme }}> creates a new object every render, so every consumer re-renders every time the provider renders, regardless of whether the data changed. Fix: memoize the value.
  • Over-broad context: putting many unrelated fields in one context means a change to any field re-renders all consumers. Fix: split into multiple contexts by change frequency.

Mitigations

Memoize the provider value; split contexts (e.g. separate ThemeContext and AuthContext); or use an external store (Zustand, Redux, or useSyncExternalStore) with selectors so components subscribe to slices and only re-render when their slice changes.

Code Example

// TRAP: new object each render => every consumer re-renders.
<AppContext.Provider value={{ user, theme, setTheme }}>

// BETTER: memoize so identity is stable across unrelated renders.
const value = React.useMemo(
  () => ({ user, theme, setTheme }),
  [user, theme, setTheme]
);
<AppContext.Provider value={value}>{children}</AppContext.Provider>

// BEST for high-churn state: split contexts by update frequency.
<AuthContext.Provider value={authValue}>
  <ThemeContext.Provider value={themeValue}>
    {children}
  </ThemeContext.Provider>
</AuthContext.Provider>

Project Example

An app kept the current user, feature flags, and a live "unread count" in one context object. Every websocket-driven unread-count tick re-rendered the entire authenticated app. Splitting the volatile count into its own context (and memoizing the rest) cut re-renders by ~95% — the count badge updated in isolation while the rest of the tree stayed put.

Senior Engineer Perspective

The interviewer is testing whether you know context is not a state manager and has no built-in selector granularity. Strong points to raise: context propagation deliberately bypasses memoization for consumers; the value comparison is Object.is on the whole value; and the standard senior fixes are memoizing the value, splitting contexts, or reaching for an external store with selectors when you need slice-level subscriptions. Mentioning useSyncExternalStore as the concurrency-safe way to subscribe to external stores (avoiding tearing) shows current, internals-level awareness.
