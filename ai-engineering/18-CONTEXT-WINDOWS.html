CHAPTER 18 — CONTEXT WINDOWS

Volume 1 — AI Foundations · Chapter 15 of 22

Vector Mathematics (Chapter 17) gave you the geometry that makes an embedding meaningful — direction, magnitude, similarity, the coordinate space a model reasons in. But geometry alone does not tell you how much a model can actually look at before it produces a single token. Every prompt, every retrieved document, every turn of chat history, every tool definition you hand to a model has to fit inside one fixed, finite, expensive resource: the context window. This chapter is where "how much can the model see right now" stops being an afterthought and becomes a first-class engineering constraint you will budget, measure, and design around for the rest of this series.

1. MOTIVATION

Every Spring Boot engineer has, at some point, hit a resource ceiling that forced a design change: a connection pool that maxed out under load, a JVM heap that needed tuning, a database row limit that made a naive "just load everything" query fall over. Context windows are that same category of constraint, transplanted into AI Engineering — except this ceiling is not a tunable infrastructure parameter you can raise with a config change. It is a property of the model itself, fixed at training and architecture time, and it governs literally everything you will build in Volumes 2 through 6.

Here is why this chapter cannot wait: almost every non-trivial AI feature you will design involves cramming more information into a single model call than naive intuition suggests will fit. A customer support copilot needs the current ticket, several turns of prior conversation, three retrieved knowledge-base articles, and a system prompt describing tone and tool access — all at once, in one call, before the model produces a single word of output. If you do not understand precisely what a context window is, how it is consumed, and what happens when you exceed it, you will write code that works perfectly in your five-message demo and then silently degrades, truncates, or errors out the moment a real user has a long conversation or your retrieval step returns a slightly larger document than usual.

This matters even more because context windows are not just a capacity limit — they are an attention economy. Later in this chapter you will see the "lost in the middle" phenomenon: a model can technically fit 100,000 tokens in its window and still pay uneven attention to what is inside it, favoring the beginning and the end over the middle. Understanding the context window is therefore not just about "does it fit" — it is about "does the model actually use what I put in there, and where should I put it so that it does." Every chapter downstream of this one — Retrieval-Augmented Generation, Chat Memory, Prompt Engineering, Agents — is, underneath, a discipline built to manage this one finite resource wisely.

2. HISTORICAL BACKGROUND

2.1 Before Attention: Memory That Decayed

Before the Transformer architecture (covered in an earlier chapter in this volume), sequence models like Recurrent Neural Networks (RNNs) and their improved successor, Long Short-Term Memory networks (LSTMs), processed text one token at a time, carrying forward a fixed-size "hidden state" vector as a summary of everything seen so far. In principle, this hidden state could represent memory of unlimited length — there was no hard architectural wall. In practice, it was a leaky bucket: each new token compressed and partially overwrote the running summary, and gradients used during training to reinforce long-range dependencies shrank exponentially the further back in the sequence they had to travel — the vanishing gradient problem. The practical result was that RNN/LSTM-based models "forgot" information from more than a few dozen to a few hundred tokens back, no matter how the architecture was tuned. There was no explicit "context window" number to configure; there was a soft, leaky memory that degraded with distance.

2.2 The Transformer Trade: Explicit Window, Explicit Cost

The 2017 Transformer architecture solved the leaky-memory problem with a very different design: instead of compressing history into one running hidden state, self-attention lets every token directly look at every other token in the input, regardless of distance, with no decay from position alone. This was a genuine breakthrough for long-range recall. But it traded one problem for a new, very concrete one: computing attention between every pair of tokens costs compute and memory that grows quadratically with the number of tokens (formalized in Section 6). This is precisely why, unlike RNNs, Transformer-based models ship with a hard, published, architectural number: the maximum context length — a wall the model was built and trained against, not a soft degradation.

2.3 The Race to Extend the Window

Once context length became a marketed, comparable specification, the industry moved through it quickly. Early GPT-2 shipped with a 1,024-token window. GPT-3 doubled that to 2,048, and its "-16k"/"-32k" successors pushed further using techniques like better positional encodings. By the mid-2020s, commercial models routinely advertised 100,000+ token windows, with some providers pushing past one million tokens. This did not happen just by "training on more tokens" — it required real architectural work:

TechniqueCore IdeaWhat It Bought
Better positional encodings (RoPE, ALiBi)Encode token position in a way that generalizes to positions rarely or never seen during trainingModels could be evaluated at longer lengths than they were fully trained on without collapsing

Why this history matters to you as an engineer: a bigger advertised context window is not automatically a better one. Two models can both claim "200,000 tokens" while having very different effective recall inside that window, because they got there through different trade-offs (some sacrifice attention fidelity for length via sparsity; others pay full quadratic cost). This is why benchmarking a model's actual long-context behavior on your workload — not trusting the marketing number — remains a real engineering task, one you will revisit when this series covers evaluation.

3. PROBLEM STATEMENT

Strip away the marketing numbers and the history, and the engineering problem a context window forces you to solve is precise and unavoidable:

Every model call has a single, fixed, shared token budget that must simultaneously hold the system instructions, the conversation history, any retrieved or injected knowledge, the user's current input, AND leave enough room for the model's own output — and if the sum exceeds that budget, something must be cut, and you, not the model, must decide what.

Notice the phrase "you, not the model." A context window is not a smart, self-managing cache — it has no built-in notion of "this part of the conversation is more important than that part." If you exceed the limit, the API call fails outright, or (depending on the client/library) older content gets silently truncated from one end. Either way, an engineering decision about what to drop, what to summarize, and what to keep has to be made by your application, deliberately, before the call is made — or it will be made for you, badly, by whatever default truncation behavior your client library happens to implement.

This reframes a whole category of downstream problems you will meet in this series. Retrieval-Augmented Generation (Volume 3) is, from this chapter's point of view, mostly a context-window budgeting problem: which of your thousands of private documents are worth spending your limited token budget on for this specific query? Chat memory (Volume 2) is a context-window budgeting problem across time: which turns of a long-running conversation still deserve a seat in the window, and which should be summarized or dropped? Multi-agent orchestration (Volume 4) frequently exists specifically to avoid ever putting an entire problem's worth of context into one window at all, splitting it across multiple calls instead. Once you see context windows as a budgeting problem, the shape of nearly the entire rest of this book becomes visible.

4. THEORY

4.1 What a Context Window Actually Is

A context window is the maximum number of tokens — the sub-word units covered conceptually in earlier chapters on tokenization and embeddings — that a model can process as input and generate as output in a single call, combined. It is not measured in characters, words, or "messages" the way a chat UI might display them; it is measured strictly in the model's own tokenizer units, and different models tokenize the same text differently, so a 500-word paragraph might be 650 tokens in one model's tokenizer and 720 in another's.

The cleanest working analogy for a Java engineer: think of the context window as a fixed-size arena allocator, not a growable ArrayList. You get one contiguous block of a known, fixed capacity at the start of the call. Everything you want the model to consider — instructions, history, retrieved facts, the current question — has to be laid out inside that one block before the call begins. There is no "expand and copy" operation available mid-call the way there is with a resizable collection. If it does not fit, it does not go in, full stop.

4.2 Context Length vs. Effective Context

This is the single most important theoretical distinction in this chapter, and the one most engineers get wrong the first time they design a long-context feature. Context length is the architectural, published maximum — the size of the arena. Effective context is how much of that arena the model actually uses well when producing an answer. These are not the same number, and the gap between them is not a bug you can patch — it is a structural property of how attention is trained and distributed.

The most-cited symptom of this gap is the "lost in the middle" effect: when relevant information is placed near the very beginning or the very end of a long context, models retrieve and use it reliably; when the same information is placed in the middle of a long context, retrieval accuracy measurably drops, even though the information is technically well within the advertised window. Intuitively, this mirrors something you already know from human cognition — reading a very long email, you remember the opening line and the closing ask far better than a fact buried in paragraph 14 — except here it is a measurable, model-specific curve you can benchmark, not just an analogy.

4.3 The Sliding Window Mental Model

For a single, self-contained model call, the context window is simply "the whole input, all at once" — there is no sliding involved. Sliding becomes relevant the moment you have an ongoing conversation that grows across many calls. Picture a physical window frame of fixed width sliding along a very long scroll of text representing the full conversation history: as new turns are added on the right, and the frame's width cannot grow, something has to leave from the left (or be compressed) to keep the visible portion within the frame's fixed size. This "sliding window" framing is exactly how conversational memory management (formalized in Volume 2's Memory chapter) has to work in practice, and it is the mental model this chapter's Internal Working section will make mechanical.

4.4 Prefill vs. Decode: Two Different Relationships to the Window

A model interacts with its context window in two distinct phases, and conflating them is a common source of confused intuitions about latency and cost (both formalized further in Sections 6 and 12):

  • Prefill — the model processes your entire input (system prompt, history, retrieved context, user turn) in one pass, computing attention across all of it before producing the first output token. This is where context length directly, heavily affects latency: a bigger input means a bigger one-time computation before anything comes back.
  • Decode — the model then generates output tokens one at a time, and each new token still has to attend back across the entire context (input plus everything generated so far). This is where a cached representation of the context — the KV cache, introduced mechanically in Section 5 — becomes essential to keeping generation fast.

5. INTERNAL WORKING

Now make the theory mechanical. Here is what actually happens, step by step, from the moment your application assembles a prompt to the moment tokens start streaming back.

5.1 Step 1 — Tokenization and Budget Accounting

Before anything reaches the model's neural network, every piece of text you plan to send — system prompt, chat history, retrieved documents, the current user message — is converted into tokens by the model's specific tokenizer. This is the first place a context-window bug can be born: application code that estimates size in words or characters, rather than actually tokenizing (or using an accurate token-count estimator), routinely under- or over-estimates how much room is left, because tokenization ratios vary by language, by content type (code tokenizes differently from prose), and by model family.

5.2 Step 2 — Assembly Into One Ordered Sequence

All of those token streams are concatenated, in a specific order determined by your application (and, for chat-style models, wrapped with role markers distinguishing system/user/assistant turns), into one single flat sequence of tokens that must not exceed the model's maximum context length. There is no separate "channel" for system instructions versus retrieved documents versus chat history at the hardware level — they are all just tokens in one sequence, competing for the same fixed-size slot. This is precisely why ordering and placement (Section 4.2's "lost in the middle") matters so much: the model does not receive a labeled bundle of "important system rules" and "less important background text" — it receives one sequence and has learned, from training data patterns, to weight positions unevenly.

5.3 Step 3 — Positional Encoding

Because self-attention on its own has no inherent sense of order (it can look at any token regardless of position, as covered in the Transformers chapter), each token's position within the sequence is injected via a positional encoding scheme (absolute position embeddings in older models; relative schemes like RoPE — Rotary Position Embeddings — in most modern ones). This step is what lets the model tell "the user's question, asked just now" apart from "a similar-looking sentence from twelve turns ago." It is also the exact mechanism that determines how gracefully — or how badly — a model handles positions longer than anything it saw during training, which is why context-length extension (Section 2.3) is fundamentally about re-engineering this step, not just "letting more tokens through."

5.4 Step 4 — Full Self-Attention Across the Window (Prefill)

With tokens embedded and positionally encoded, the model computes self-attention: for every token, a weighted look at every other token in the sequence (subject to causal masking, so a token cannot attend to tokens that come after it — the model can only look backward in time, never forward, matching how it will later have to generate left-to-right). This all-pairs computation is what makes the window a hard architectural boundary rather than a soft configuration knob: the attention mechanism itself, and the matrices it was trained with, are sized for a maximum sequence length. Feed it more tokens than that and there is no well-defined computation to fall back to — this is why providers return an explicit error, rather than a degraded answer, when you exceed the stated limit.

5.5 Step 5 — The KV Cache and Autoregressive Decoding

Once prefill computes attention over the full input once, generating the first output token, the model does not want to recompute attention over the entire input again from scratch for every subsequent token — that would be wastefully redundant. Instead, it caches the intermediate "key" and "value" projections for every token already processed — the KV cache — and each new generated token only needs to compute its own query against that cache plus append its own key/value to it. This is why decode latency per additional output token stays roughly proportional to context length (each new token still attends across the whole growing cache) rather than needing to redo the full quadratic computation every single step. It is also why the KV cache, not the model weights alone, frequently becomes the dominant consumer of GPU memory at long context lengths and large batch sizes — a fact with direct production consequences covered in Section 12.

5.6 Step 6 — What Happens at the Boundary

When your assembled sequence would exceed the maximum context length, one of a few things happens, and which one depends entirely on your client/library, not the model:

  • Hard rejection — the API call fails with an explicit error (most production-grade clients and providers behave this way by default; this is the safest failure mode because it is loud and catchable).
  • Silent truncation — some client libraries or self-managed pipelines will quietly drop the oldest messages (or, worse, truncate from an arbitrary point) to fit, which can silently remove a system instruction, an important early clarification, or a piece of retrieved evidence without any error being raised.
  • Application-managed compaction — the correct production pattern (detailed in Sections 8–10): your own code proactively summarizes, drops, or re-ranks content before the boundary is ever hit, so the model never sees a raw truncation event at all.

6. MATHEMATICS — INTUITION FIRST, FORMALISM WHERE IT HELPS

You do not need to derive attention mathematics from scratch here — that belongs to the Transformers chapter. What you do need, as an engineer who will be asked to justify latency and cost numbers, is the shape of two specific growth curves.

6.1 Why Attention Cost Grows Quadratically

Self-attention computes a relevance score between every pair of tokens in the sequence. If your sequence has n tokens, the number of pairs to score is proportional to n × n, written as O(n²). Double your context length, and the core attention computation for prefill does not double — it roughly quadruples. This is the single fact that explains why context windows did not simply grow to "infinite" the moment someone wanted them to: naively, a 10x longer window is not 10x more expensive, it is closer to 100x more expensive for the attention step alone. 

Sequence length (n)     Pairwise attention scores (∝ n²)     Relative cost
────────────────────    ─────────────────────────────────    ─────────────
  1,000 tokens                  ~1,000,000                        1x
  4,000 tokens                 ~16,000,000                       16x
 16,000 tokens                ~256,000,000                      256x
 64,000 tokens              ~4,096,000,000                     4096x

This is precisely why the engineering techniques in Section 2.3 (sparse attention, FlashAttention's memory-efficient exact computation, ring attention's parallelization) exist — they attack this curve directly, either by not computing every pair, or by computing every pair much more efficiently, or by spreading the computation across more hardware.

6.2 KV Cache Memory: Linear, But Not Small

Unlike the attention computation itself, the KV cache's memory footprint grows linearly with sequence length — but the constant factor involves the number of layers and attention heads in the model, so it adds up fast. A useful mental formula, without needing exact model internals: 

KV cache size  ≈  2 × (num_layers) × (num_heads × head_dim) × (sequence_length) × (bytes_per_value) × (batch_size)

  the leading 2  → one cache for Keys, one for Values
  num_layers     → every transformer layer keeps its own cache
  sequence_length → grows as the conversation/context grows
  batch_size     → serving many concurrent requests multiplies this directly

The concrete number matters less here than the shape: this is a straight line that keeps climbing as context length grows, and it climbs faster when you serve many concurrent long-context requests at once — which is exactly why context length interacts directly with a production system's maximum concurrency, not just with a single user's latency (formalized in Section 12).

6.3 Token Budgeting Arithmetic

The arithmetic you will actually do as an application engineer is simpler than the internals above, and it is worth internalizing as a habit, not a one-off calculation: 

available_for_input  =  max_context_length  −  reserved_output_tokens

prompt_budget        =  available_for_input
                          − tokens(system_prompt)
                          − tokens(tool/function definitions)
                          − tokens(retrieved_context)
                          − tokens(conversation_history)
                          ≥ tokens(current_user_turn)   ← must hold, or something must be cut

Every production system that talks to a model performs some version of this subtraction before every call — whether that logic is explicit and deliberate, or accidental and buried inside a client library's default truncation behavior.

Two architectural details matter here that are easy to miss. First, the Token Budget Manager has to run before retrieval finalizes how many chunks to return and before chat memory decides how many turns to include — budgeting is not a final validation step, it is an input to the earlier decisions, or you end up computing expensive retrieval and then throwing most of it away. Second, this whole pipeline runs on every request of a multi-turn conversation, not once at session start, because the budget changes shape as history and retrieved content change from turn to turn.

The practical Java pattern looks like a pipeline of small, testable decisions rather than one giant prompt-building method: 

// Illustrative shape, not a full working example — the point is the ORDER of decisions,
// which mirrors the Section 8 architecture: budget first, then select, then assemble.

int maxContextTokens   = model.getMaxContextLength();      // architectural constant for this model
int reservedForOutput  = 1500;                              // leave room for the answer
int availableForInput  = maxContextTokens - reservedForOutput;

int systemPromptTokens = tokenCounter.count(systemPrompt);
int toolDefTokens      = tokenCounter.count(toolDefinitions);
int remainingBudget     = availableForInput - systemPromptTokens - toolDefTokens;

List retrieved = vectorStore.similaritySearch(
        SearchRequest.query(userMessage).withTopK(8));
List trimmedRetrieved = tokenBudgetSelector.selectWithinBudget(
        retrieved, remainingBudget * 0.6);          // e.g. reserve ~60% of what's left for RAG context

int afterRetrieval = remainingBudget - tokenCounter.count(trimmedRetrieved);
List trimmedHistory = chatMemory.getWithinBudget(conversationId, afterRetrieval);

Prompt prompt = promptBuilder
        .system(systemPrompt)
        .documents(trimmedRetrieved)
        .messages(trimmedHistory)
        .user(userMessage)
        .build();

ChatResponse response = chatClient.prompt(prompt).call().chatResponse();

Notice this is exactly the Section 6.3 arithmetic, expressed as Java control flow. This is the mindset shift for this chapter specifically: a senior Spring engineer treats availableForInput the way they would treat an available connection-pool slot or a remaining rate-limit quota — a resource you check and allocate deliberately, not one you discover you've exhausted only when a call fails in production.

10. BEST PRACTICES

  • Always reserve output tokens explicitly, before budgeting input. A call that fills the entire context window with input and leaves no room for a complete answer will produce a response that gets cut off mid-sentence — a subtle, ugly failure mode that is easy to miss in testing with short prompts.
  • Count tokens with the actual model's tokenizer, not word count or character count as a proxy. Estimates based on "roughly 4 characters per token" are fine for rough dashboards, but budget-critical decisions (will this fit) need real counts, because the error compounds across system prompt, tools, history, and retrieval simultaneously.
  • Put the most important instructions and the most important facts near the beginning or the end of the assembled context, not buried in the middle. This is a direct, actionable response to the "lost in the middle" effect from Section 4.2 — for example, restate the user's core question or the critical constraint immediately before the final user turn, even if it was already stated earlier in the conversation.
  • Summarize or compact aggressively rather than truncating blindly. A short, model-generated summary of turns 1–8 of a conversation usually preserves more useful signal per token than the raw, verbatim text of those same turns — treat summarization as a first-class memory-management strategy, not a fallback.
  • Cap retrieval, don't just retrieve "the top K you feel like." Decide the RAG token budget mathematically (Section 6.3), and let the retrieval layer return exactly as many chunks as that budget allows, re-ranked by relevance — dumping every semi-relevant chunk in "just in case" wastes budget that could have gone to conversation history or output length.
  • Take advantage of prompt caching where your provider supports it. Many providers can cache and reuse the processing of a stable prefix (e.g., a fixed system prompt and tool definitions) across repeated calls, meaningfully cutting prefill latency and cost for the unchanging portion of your context.

11. COMMON MISTAKES

  • Assuming a bigger context window means the retrieval/history problem is "solved." A 200,000-token window does not mean you should stop being disciplined about what you put in it — Section 4.2's effective-context gap means stuffing the window with marginally relevant content can actively dilute the model's attention on the parts that matter, even though everything "fits."
  • Letting conversation history grow unbounded across a long-running session. Without an explicit windowing or summarization policy, a chat feature that works fine in a five-minute demo will, days into real usage, either hit a hard context-length error or start silently losing early turns via unmanaged client-side truncation.
  • Forgetting that tool/function definitions consume real tokens too. Agentic systems (Volume 4) that register many tools can burn a surprisingly large, easy-to-overlook chunk of the budget on tool schemas alone, before a single word of actual conversation is sent.
  • Treating token counting as optional because "the request usually just works." This is a classic works-in-dev, breaks-in-production trap: your test conversations are short, your test documents are small, and the first time a real user pastes a long document or has an unusually long conversation, the call fails in a way you never exercised.
  • Re-sending the entire chat history on every single turn without ever compacting it, purely because it's simpler to implement. This is not just a correctness risk (eventual overflow) — it is a direct, compounding cost and latency problem, since every turn now re-processes an ever-larger prefill, covered concretely in Section 12.

12. PERFORMANCE CONSIDERATIONS

Context window size is one of the most direct levers on latency, throughput, and cost that you will control as an AI engineer — more direct, in many systems, than the choice of model itself.

  • Time-to-first-token scales with input length. Because prefill (Section 5.4) has to process the entire input before generating the first output token, a call with a large system prompt, long history, and several retrieved documents will have a noticeably longer time-to-first-token than a short one — this is felt directly by users as "the assistant is thinking" delay, and it grows non-linearly with context length due to the O(n²) attention cost from Section 6.1.
  • Per-token decode cost grows with context length too, just more gently. Each generated token still attends across the full KV cache (Section 5.5), so a long-context conversation generates each subsequent token slightly slower than a short one — the effect is smaller than prefill's, but it compounds over long streamed responses.
  • KV cache memory competes directly with serving concurrency. Because KV cache size grows with both sequence length and batch size (Section 6.2), a provider or self-hosted deployment serving many simultaneous long-context requests can hit GPU memory limits well before hitting compute limits — this is why some providers cap concurrent long-context requests more aggressively than short-context ones, and why self-hosting a model with very long context support requires provisioning memory, not just raw compute.
  • Cost is (almost always) billed per token, on both sides of the window. Input tokens and output tokens are typically priced separately, and a design that habitually resends large, redundant context on every turn (Section 11) pays that cost every single turn — this is the single most common avoidable line item in a production AI system's bill, and it is fixed entirely by the budgeting and compaction discipline from Sections 8–10.
  • Prompt caching changes the economics of a stable prefix. If your system prompt and tool definitions do not change between calls, provider-side prompt caching can turn a large fraction of your input tokens into a much cheaper, much faster "cache hit" on repeated calls — a lever worth designing your prompt structure around (stable content first, variable content last) specifically to make caching effective.

13. SECURITY CONSIDERATIONS

Context windows have a real, specific security surface, and it grows precisely as your application relies on them more heavily for RAG and multi-turn memory.

  • The context window is where prompt injection actually lands. As covered conceptually in an earlier chapter, a model cannot cleanly distinguish trusted instructions from untrusted data within one flat token sequence — and because a large context window can comfortably hold long retrieved documents or tool outputs, it is exactly the retrieved-document or history slot in Section 7.1's anatomy diagram where an attacker-controlled instruction is most likely to be smuggled in, sometimes deliberately placed away from the beginning/end where a human reviewer is most likely to skim.
  • Long-lived chat memory can leak across sessions or tenants if isolation is sloppy. A chat memory store keyed incorrectly (shared session identifiers, caching bugs, or a memory advisor pulling from the wrong conversation ID) can inject one user's prior conversation — potentially containing sensitive information — into another user's context window. In a multi-tenant system, this is a data-leakage bug with the same severity as a broken row-level security policy in a database.
  • Very large contexts make manual review impractical. A system that stuffs tens of thousands of tokens of retrieved content into a window makes it functionally impossible for a human to review everything the model actually saw before it acted — this is a real argument for keeping retrieved-context budgets deliberately tight and auditable, not just "as large as the window allows," especially for any pipeline where the model's output can trigger a real-world action (Volume 4).

This chapter's security surface is narrower than, say, the Guardrails or Prompt Injection chapters later in this series — a context window is a resource-management mechanism, not an authorization mechanism — but it is honest to note that resource limits and security boundaries are not the same thing, and treating "it fits in the window" as any kind of safety signal is a mistake worth naming explicitly here.

14. INTERVIEW QUESTIONS

JUNIORQ1. What is a context window, and what unit is it measured in?

ROI: ★★★★★ · Frequency: Extremely High

A context window is the maximum amount of input plus output a model can process in a single call. It is measured in tokens — the model's own sub-word units — not in words or characters, and different models tokenize the same text into different numbers of tokens.

JUNIORQ2. What happens if the total tokens you send exceed a model's maximum context length?

ROI: ★★★★☆ · Frequency: High

The call either fails outright with an explicit error from the API/provider, or — depending on the client library — gets silently truncated from one end before being sent. Well-designed production systems avoid both outcomes by proactively budgeting and compacting content before the limit is ever reached.

MIDQ3. Explain the difference between "context length" and "effective context," and why the distinction matters in practice.

ROI: ★★★★★ · Frequency: Extremely High

Context length is the architectural maximum number of tokens a model can accept. Effective context is how well the model actually uses information at different positions within that maximum — in practice, models tend to attend more reliably to content near the beginning and end of a long context than content buried in the middle (the "lost in the middle" effect). It matters because a model can technically fit relevant information within its window and still fail to use it correctly, so simply "fitting" is not the same as "being retrievable" — placement and compaction strategy matter even when raw capacity is not the bottleneck.

MIDQ4. Why does attention cost grow quadratically with sequence length, and what techniques have been used to soften that cost?

ROI: ★★★★☆ · Frequency: High

Self-attention computes a relevance score between every pair of tokens in the sequence, so the number of pairwise computations grows proportionally to the square of the sequence length. Techniques that soften this include sparse or windowed attention (not scoring every pair), memory-efficient exact-attention implementations like FlashAttention (reducing memory traffic without changing the math), and parallelization schemes like ring attention that spread the computation across multiple accelerators.

MIDQ5. What is a KV cache, and why does it matter for context-window-heavy applications?

ROI: ★★★★☆ · Frequency: Medium-High

The KV cache stores the key and value projections computed for every token already processed, so that generating each new output token only requires a fresh computation for that one token against the cache, rather than recomputing attention over the entire sequence from scratch. It matters because its memory footprint grows with both sequence length and batch size, meaning long-context, high-concurrency workloads can become memory-bound on the KV cache well before they become compute-bound.

SENIORQ6. Design a strategy for managing context window budget in a customer-support chat application with long-running conversations and a RAG knowledge base. What do you prioritize, and what do you sacrifice first when the budget is tight?

ROI: ★★★★★ · Frequency: High at senior level

Reserve output tokens first, then allocate remaining budget with explicit priority: system prompt and tool definitions (small, fixed, non-negotiable), then the current user turn (must always fit), then a capped, re-ranked set of retrieved knowledge-base chunks (cut before history, since retrieval can be re-run and re-ranked per turn), then conversation history (summarize older turns into a compact rolling summary rather than dropping them raw, preserving continuity while shrinking token cost). When budget is tight, sacrifice raw retrieved-chunk count and raw history length first — via summarization and re-ranking — never the system prompt's safety/behavior instructions, and never silently truncate the current user turn.

Interview Gold Point: Explicitly mention that this budgeting logic must run per-request, not once per session, because the shape of history and retrieval results changes every turn — and mention prompt caching for the stable prefix (system prompt, tool defs) as a concrete latency/cost optimization layered on top of the budgeting logic itself.
SENIORQ7. A stakeholder proposes solving all context-management problems by switching to a model with a 1-million-token context window and simply stuffing everything in. What is your technical response?

ROI: ★★★★☆ · Frequency: Medium-High at senior level

A larger nominal window does not eliminate the "lost in the middle" effect — effective retrieval accuracy at very long context lengths is typically still measurably lower for information placed away from the start/end, so correctness is not guaranteed to improve. It also does not eliminate cost or latency concerns: prefill cost scales roughly quadratically with input length, so filling a 1-million-token window on every call is dramatically more expensive and slower than a well-curated, budgeted context of a few thousand tokens containing only the genuinely relevant content. The better response is to keep disciplined retrieval, ranking, and summarization regardless of window size, using the larger window as headroom for edge cases and safety margin, not as a substitute for context engineering.

STAFFQ8. How would you build observability and alerting around context-window usage for a platform serving many AI features across an organization?

ROI: ★★★★☆ · Frequency: Medium at staff level

Instrument every model call to log input token count broken down by component (system prompt, tool defs, retrieved context, history, current turn), output token count, and whether any compaction/truncation occurred, tagged per feature/team. Alert on rising near-limit rates (calls consistently using >80-90% of available input budget, a leading indicator of imminent failures as conversations or documents grow slightly), on unexpected truncation events (a signal that a compaction policy is missing or broken), and on cost/latency percentiles correlated with input length, so a team can see when their feature's context footprint is quietly growing. Strategically, this data also informs platform-level decisions — e.g., building a shared, reusable chat-memory/summarization advisor rather than letting every team hand-roll (and mis-handle) their own truncation logic.

JUNIORQ9. What does "reserving output tokens" mean, and why must it be done before you count how much input you can send?

ROI: ★★★★★ · Frequency: Extremely High

Reserving output tokens means subtracting a fixed number of tokens from the model's max context length up front, and treating only what remains as available for input. It has to happen first because input and output share the exact same budget — if you fill the window with input and only then discover how much room is left for the answer, you risk leaving too little room, and the model's response gets cut off mid-sentence instead of failing loudly.

JUNIORQ10. At a high level, what's the difference between a "sliding window" memory strategy and a "summarization" memory strategy for chat history?

ROI: ★★★★★ · Frequency: Extremely High

A sliding window keeps the most recent N turns verbatim and simply drops older turns once the window is full — cheap to implement, but anything dropped is gone entirely. Summarization instead compresses older turns into a shorter, model-generated summary that is kept in the prompt in place of the raw text — more expensive to produce, but it preserves the gist of dropped content instead of losing it outright.

JUNIORQ11. Why can't you always just request the maximum number of retrieved documents your vector store will return?

ROI: ★★★★☆ · Frequency: High

Every retrieved document consumes real tokens out of the same shared budget as the system prompt, history, and output reservation. Requesting more documents than your remaining token budget allows means something else has to be cut to make room, or the call fails outright — and past a certain point, adding more marginally relevant documents can dilute the model's attention on the documents that actually answer the question.

JUNIORQ12. What is prompt caching, described in plain terms?

ROI: ★★★★☆ · Frequency: High

Prompt caching lets a provider reuse the internal computation it already did for a piece of text it has seen before, as long as that text appears again as an identical prefix at the start of a new request. In practice, this means a stable system prompt and tool definitions that don't change between calls can be processed once and reused cheaply on every subsequent call, instead of being fully recomputed every time.

JUNIORQ13. Besides the user's current message, name at least three other things that typically consume tokens in a chat request.

ROI: ★★★★☆ · Frequency: High

The system prompt/persona instructions, tool or function definitions registered for the call, retrieved context from a RAG pipeline, and prior conversation history all consume tokens from the same shared budget as the current user message — and the reserved space for the model's own output counts against that same total as well.

JUNIORQ14. What is context overflow, and what is the simplest way an application can detect it before actually sending the request?

ROI: ★★★★☆ · Frequency: High

Context overflow is the situation where the total assembled tokens — system prompt, history, retrieved context, current turn, plus reserved output — exceeds the model's maximum context length. The simplest detection is to tokenize (or accurately estimate) every component before assembling the final prompt and sum the counts against the known maximum, catching the problem locally instead of waiting for the API to reject the call.

JUNIORQ15. What does "provider-agnostic" mean when talking about context-window management code?

ROI: ★★★☆☆ · Frequency: Medium

It means the budgeting and compaction logic is written against configuration values (max context length, reserved output, tokenizer) rather than hard-coded assumptions about one specific model or provider, so the same code can correctly manage a call to a small-window model and a large-window model without being rewritten for each one.

JUNIORQ16. Why might two different models that both advertise a "128,000 token" context window still behave differently on the same long prompt?

ROI: ★★★★☆ · Frequency: Medium-High

The advertised number is the architectural maximum — how much technically fits — not a guarantee of how well the model uses everything inside that limit. Models reach long context lengths through different underlying techniques (some trade off attention fidelity for length via sparsity, others pay the full cost), so their effective context and their "lost in the middle" behavior can differ noticeably even with an identical advertised maximum.

JUNIORQ17. What does it mean to "chunk" a request across multiple model calls, at a basic level?

ROI: ★★★☆☆ · Frequency: Medium

It means splitting a task that is too large to fit in a single context window — for example, summarizing a very long document — into smaller pieces that each fit comfortably within the window, processing each piece with its own model call, and then combining the partial results into a final answer.

JUNIORQ18. Why do tool/function definitions count against the context budget even if the model doesn't end up calling any of them?

ROI: ★★★★☆ · Frequency: Medium-High

Tool definitions have to be included in the input every single call so the model knows what tools are available and how to call them correctly — they are tokenized and sent as part of the prompt regardless of whether the model chooses to invoke a tool in its response, so they consume real input budget on every request, not just the ones where a tool is actually used.

JUNIORQ19. Give one simple way to reduce token usage for a long conversation without losing all prior history.

ROI: ★★★★☆ · Frequency: High

Replace the oldest turns with a short, model-generated summary of what was discussed, while keeping the most recent few turns verbatim — this keeps the token footprint small while still preserving the gist of everything that happened earlier in the conversation.

JUNIORQ20. Why does putting the most important instruction right before the final question sometimes help, even if it was already stated earlier in the prompt?

ROI: ★★★★☆ · Frequency: High

Because of the "lost in the middle" effect, models attend more reliably to content near the very start or very end of the context than to content buried in the middle. Restating a critical instruction immediately before the current question puts it in a high-attention position, increasing the odds the model actually follows it, even though it is technically redundant with an earlier mention.

JUNIORQ21. What is the risk of blindly concatenating every document a retrieval step returns into the prompt?

ROI: ★★★★☆ · Frequency: High

You can silently exceed the context budget once retrieval returns a larger-than-usual set of documents, and even when everything technically fits, dumping in marginally relevant documents "just in case" wastes token budget that could have gone to conversation history or output length, and can dilute the model's attention away from the documents that actually matter.

JUNIORQ22. What does "near-limit request" mean in the context of production monitoring?

ROI: ★★★☆☆ · Frequency: Medium

It refers to a request whose assembled token count is close to the model's maximum context length — for example, using more than 80-90% of the available input budget. Tracking the rate of near-limit requests is useful because it is a leading indicator: a feature trending toward more near-limit requests over time is likely to start hitting hard overflow errors soon, even if it hasn't yet.

JUNIORQ23. If a model call fails with a context-length-exceeded error, what is the first thing you should check in your code?

ROI: ★★★★☆ · Frequency: High

Check whether every component being sent (system prompt, tool definitions, retrieved context, history, current turn) is actually being counted and budgeted against the model's real maximum context length — the most common cause of an unexpected overflow is a component that was never included in the token-counting logic in the first place, such as tool definitions or a recently added retrieval step.

JUNIORQ24. In plain language, what happens in the "map" step and the "reduce" step of map-reduce summarization?

ROI: ★★★★☆ · Frequency: Medium-High

In the map step, a long document is split into chunks that each fit the context window, and each chunk is summarized independently and in parallel. In the reduce step, those individual chunk summaries are combined — either concatenated and summarized again in one more call, or merged progressively — to produce one final summary of the whole document.

JUNIORQ25. Why is it a bad idea to store and resend a chat's full raw history forever with no compaction?

ROI: ★★★★★ · Frequency: Extremely High

The history will eventually exceed the context window as the conversation grows, causing hard failures or silent truncation, and even before that point, every additional turn makes every subsequent call more expensive and slower to process, because the entire growing history is re-processed on every single call.

JUNIORQ26. How is a model's context window different from, say, a database's storage capacity?

ROI: ★★★☆☆ · Frequency: Low-Medium

A database persists data indefinitely across many separate queries and can be scaled by adding more storage. A context window is a per-call, transient limit — nothing survives past a single model invocation unless your application explicitly re-sends it on the next call, and its size cannot be increased by provisioning more of anything; it is fixed by the model's architecture.

JUNIORQ27. Give one concrete example of "graceful degradation" when a request would otherwise exceed the context window.

ROI: ★★★★☆ · Frequency: Medium-High

Instead of letting the call fail, the application could automatically drop or summarize the oldest conversation turns, or reduce the number of retrieved documents included, so the call still succeeds with slightly less context rather than erroring out entirely and giving the user nothing.

JUNIORQ28. Why doesn't upgrading a RAG application's model from an 8K-token window to a 128K-token window automatically make its answers better?

ROI: ★★★★★ · Frequency: High

A bigger window only raises the ceiling on how much can technically fit — it does not improve retrieval quality, does not fix the "lost in the middle" effect, and does not guarantee the model will use additional context correctly. If the retrieval step still returns the wrong or low-quality documents, giving the model room for more of them just means more irrelevant content competing for attention.

JUNIORQ29. What is a "rolling summary" in the context of conversation memory?

ROI: ★★★★☆ · Frequency: Medium-High

A rolling summary is a single, continuously updated summary of everything discussed so far that gets older, isn't kept verbatim. Each time older turns are about to fall out of the window, they get folded into the existing summary (rather than a fresh summary being generated from scratch each time), so the conversation's history is compressed into one compact, evolving block of text kept alongside the most recent raw turns.

MIDQ30. Walk through a worked example: how would you divide a 32,000-token context window across system prompt, tool definitions, retrieved context, history, current turn, and output for a support-bot?

ROI: ★★★★★ · Frequency: Extremely High

Start by reserving output, then allocate the remainder by priority, leaving a safety margin rather than spending every last token:

Total context length:              32,000 tokens
Reserved for output:                4,000 tokens  (~12.5%)
──────────────────────────────────────────────────
Available for input:               28,000 tokens

  System prompt & persona:            500 tokens  (~1.8% of input)
  Tool/function definitions:        1,500 tokens  (~5.4%)
  Retrieved context (RAG, capped):  8,000 tokens  (~28.6%)
  Conversation history (windowed): 12,000 tokens  (~42.9%)
  Current user turn:                  500 tokens  (~1.8%)
  ────────────────────────────────────────────────
  Sum so far:                      22,500 tokens
  Safety margin (unallocated):      5,500 tokens  (~19.6% held back)

The unallocated margin matters as much as the explicit line items — token counts are estimates until the exact request is tokenized, and leaving headroom absorbs small miscounts, tokenizer differences, and the occasional unusually long retrieved chunk without tipping the call into overflow.

MIDQ31. Compare a fixed-size sliding window strategy to a summarization-based compression strategy for chat memory. What failure mode does each have?

ROI: ★★★★★ · Frequency: High

A sliding window's failure mode is total, silent information loss: once a turn falls out of the window, it is gone completely, so a user who references something they said many turns ago will find the assistant has no memory of it at all, with no signal that anything was dropped. Summarization's failure mode is subtler and arguably worse in some cases: the summary is a lossy, model-generated compression, so a specific detail (an exact number, a precise preference, a stated constraint) can get smoothed over or omitted during summarization without any obvious signal either — the assistant appears to remember the conversation but actually holds a slightly wrong version of it.

MIDQ32. What is a hybrid recent-turns-plus-summary memory strategy, and why is it usually preferred over a pure sliding window?

ROI: ★★★★★ · Frequency: High

It keeps the most recent K turns verbatim (preserving exact wording and nuance for anything the user just said) while folding everything older into a single rolling summary that stays in the prompt as compact background context. It is usually preferred over a pure sliding window because it avoids total information loss for older turns — the gist survives even after the raw text is dropped — while still spending most of the token budget on the highest-value, most-recent, most-literally-relevant content.

MIDQ33. What does "semantic" or "importance-based" turn retention mean, and how might you implement it?

ROI: ★★★★☆ · Frequency: Medium-High

Instead of deciding what to keep purely by recency (as a sliding window does), importance-based retention scores each turn by some measure of significance — for example, whether it contains a stated user preference, a decision, a constraint, or a fact the user is likely to reference again — and preferentially keeps high-scoring turns even if they are old, while letting low-scoring recent turns (small talk, acknowledgments) drop first. A simple implementation tags turns at write time (e.g., a lightweight classifier or heuristic flags "user stated a preference/constraint") and the memory manager retains flagged turns outside the normal recency window, folding only the unflagged ones into the rolling summary.

MIDQ34. Explain concretely how the "lost in the middle" effect should change where you place a retrieved document versus a system instruction in your assembled prompt.

ROI: ★★★★★ · Frequency: Extremely High

Because attention is least reliable in the middle of a long context, non-negotiable system instructions (safety rules, output format requirements) should sit at the very start of the prompt where they are consistently well-attended, and the single most decision-relevant piece of retrieved content should sit at the very end, right before the user's question, since end-of-context position is the other reliably high-attention zone. Less critical retrieved documents — useful background but not decisive — are the right candidates to place in the middle of the assembled context, precisely because that is the position where being partially ignored does the least damage.

MIDQ35. Does a larger context window make RAG obsolete? Explain your reasoning.

ROI: ★★★★★ · Frequency: Extremely High

No. RAG's job is not merely "get content to fit" — it is selecting the small subset of a much larger knowledge base that is actually relevant to a given query. Even with a million-token window, most real knowledge bases (a company's full documentation, a codebase, a legal corpus) are far larger than any window, so something still has to decide what to include. A bigger window changes RAG's economics (you can afford more chunks, less aggressive re-ranking, coarser chunking) but does not remove the need for retrieval, and stuffing an entire large corpus into a window regardless still costs more in latency and money, and still suffers from "lost in the middle," than retrieving a focused, ranked set of chunks.

MIDQ36. As context windows grow, how should retrieval strategy — chunk size, number of chunks, re-ranking — change?

ROI: ★★★★☆ · Frequency: High

With more available budget, you can afford larger chunks (less aggressive splitting means less loss of surrounding context per chunk) and a higher top-K before re-ranking, giving the re-ranker a larger candidate pool to choose from. But re-ranking becomes more important, not less: the larger the number of chunks you could include, the more valuable it is to have a strong second-stage ranker cut that pool down to the genuinely best few before assembly, rather than relying on window size alone to "fit everything and let the model sort it out" — which reintroduces the lost-in-the-middle problem at scale.

MIDQ37. Explain the mechanics of prompt caching: what makes a prefix "cacheable," and what invalidates the cache?

ROI: ★★★★★ · Frequency: High

A prefix is cacheable when it is byte-for-byte identical to a prefix the provider has already processed and cached for you recently, and it appears at the very start of the new request in the same position. This is why system prompts and tool definitions — content that rarely changes between calls — are the natural candidates: they can sit first in the assembled sequence and stay stable across many requests. The cache is invalidated by any change earlier in the sequence than the cached portion — even a single-character edit to the system prompt, a reordered tool definition, or inserting something (like a timestamp or a variable) before the stable content — because the cache is keyed on exact prefix match, not semantic similarity.

MIDQ38. How would you structure a prompt specifically to maximize cache-hit rate across many requests?

ROI: ★★★★★ · Frequency: High

Order the prompt so the most stable, least-frequently-changing content comes first (system prompt, persona, tool definitions, any fixed few-shot examples), followed by content that changes more often (retrieved context, which varies per query), and finally the most volatile content last (conversation history and the current user turn). This ordering means the largest possible prefix stays identical across consecutive calls, so the provider can reuse the cached computation for that entire stable prefix and only needs to freshly process the smaller, variable tail of the request.

MIDQ39. What metrics would you track to measure the cost/latency benefit of prompt caching in production?

ROI: ★★★★☆ · Frequency: Medium-High

Cache-hit rate (the fraction of requests that got a cache hit on their stable prefix), the average number of tokens served from cache versus freshly processed per request, time-to-first-token split by cache-hit versus cache-miss requests, and cost attributable to cached versus uncached input tokens if the provider bills them at different rates. Tracking these over time also surfaces regressions quickly — a sudden drop in hit rate usually means something changed earlier in the prompt than it should have.

MIDQ40. Describe a multi-document context assembly pattern for answering a question that requires synthesizing information from five separate retrieved documents.

ROI: ★★★★☆ · Frequency: Medium-High

Each retrieved document is wrapped with a clear delimiter and light metadata (a source label, and optionally a relevance score) so the model can distinguish where one document ends and the next begins and can cite its source; documents are ordered by relevance with the most relevant either first or last per the lost-in-the-middle guidance rather than in arbitrary retrieval order; and the assembled block is capped to a fixed token budget with a clear rule (e.g., include documents in ranked order until the budget is exhausted, don't truncate mid-document) so a single unusually long document can't silently crowd out the other four.

MIDQ41. How would you design context assembly for a multi-turn conversation that also needs to reference documents retrieved in earlier turns?

ROI: ★★★★☆ · Frequency: Medium

Rather than re-including every document retrieved in every prior turn (which grows unbounded), track a small, deduplicated "working set" of documents referenced so far, keyed by document ID, and refresh it each turn: drop documents no longer relevant to the current question, add newly retrieved ones, and cap the working set's total token cost the same way you'd cap history. This treats retrieved documents as their own budget line that persists across turns but is actively pruned, rather than accumulating alongside conversation history unmanaged.

MIDQ42. What context window differences typically exist across providers, and why does this matter for portability?

ROI: ★★★★☆ · Frequency: High

Providers differ in maximum context length (ranging from a few thousand to millions of tokens), in tokenizer implementation (the same text produces different token counts on different tokenizers), in whether and how they support prompt caching, and in default truncation/error behavior when a limit is exceeded. This matters for portability because code that hard-codes one provider's max length or estimates tokens with the wrong tokenizer will miscalculate budgets the moment you swap providers or run a multi-provider fallback strategy, producing either false overflow errors or, worse, real ones that weren't caught locally.

MIDQ43. Sketch, in pseudocode, a provider-agnostic interface for computing "available input budget" that works whether the underlying model has an 8K or 200K window.

ROI: ★★★★☆ · Frequency: Medium-High

interface ModelContextProfile {
    int maxContextLength();
    int recommendedOutputReserve();
    TokenCounter tokenCounter();   // provider-specific tokenizer, hidden behind this interface
}

int availableInputBudget(ModelContextProfile profile, int outputReserveOverride) {
    int reserve = outputReserveOverride > 0
            ? outputReserveOverride
            : profile.recommendedOutputReserve();
    return profile.maxContextLength() - reserve;
}

// Callers never branch on provider identity; they ask the profile for its
// own numbers and tokenizer, so swapping profile.forModel("gpt-x")
// for profile.forModel("claude-y") changes the budget math automatically.

The key design point is that nothing above the interface knows or cares which provider it's talking to — all provider-specific facts (max length, tokenizer, recommended reserve) are encapsulated behind ModelContextProfile, so budgeting logic is written once and reused across every provider that implements the interface.

MIDQ44. What would you monitor in production to catch context-overflow issues before users report them?

ROI: ★★★★★ · Frequency: High

Track the distribution of input-token-utilization percentage per request (input tokens used ÷ available input budget) per feature, and watch the tail — p95/p99 — for a trend climbing toward 100%, not just the average. Also log every truncation or compaction event explicitly, even successful ones, so you can see how often the system is being forced to intervene, and alert if that rate rises sharply, since a rising compaction rate on an unchanged feature usually means real usage patterns (longer conversations, larger documents) are shifting.

MIDQ45. Design an alert: what threshold and signal would you use to catch a chat feature whose context usage is trending toward the limit?

ROI: ★★★★☆ · Frequency: Medium-High

Alert when the rolling p95 of input-token-utilization for a given feature crosses a threshold like 85% of available input budget over a sustained window (e.g., 30 minutes), rather than alerting on any single request, since a single long conversation is expected and not itself a problem. Pair it with a secondary, higher-severity alert on the actual overflow/truncation-event rate crossing a small non-zero threshold, since that signal means the first alert's warning has already started translating into real, user-visible degradation.

MIDQ46. How should an application handle a context-overflow error at request time? List the graceful degradation options.

ROI: ★★★★★ · Frequency: High

In roughly increasing order of user-visible disruption: (1) drop or further compress low-priority context first — e.g., trim the retrieved-document set to fewer, higher-ranked chunks; (2) summarize older conversation turns more aggressively than the normal policy, trading fidelity for guaranteed fit; (3) if the current user turn itself is unusually long, ask the user to shorten it or split it, rather than silently dropping part of what they just said; (4) as a last resort, surface a clear, actionable error rather than sending a request you know will fail or silently mangling context the user can't see was cut.

MIDQ47. Explain how you would "chunk" a task like summarizing a 300-page document across multiple model calls when it doesn't fit in one context window.

ROI: ★★★★★ · Frequency: High

MIDQ48. What is hierarchical summarization, and how does it differ from flat map-reduce summarization?

ROI: ★★★★☆ · Frequency: Medium-High

Flat map-reduce summarizes every chunk independently and then combines all chunk summaries in a single final reduce step. Hierarchical summarization instead combines chunk summaries progressively, in a tree: groups of chunk summaries are merged into intermediate summaries, groups of those are merged again, and so on until one final summary remains. It differs mainly when the number of chunks is large enough that even the concatenated chunk summaries wouldn't fit in one context window for a single flat reduce step — hierarchical summarization avoids that by never needing to combine more content at once than fits comfortably in a window.

MIDQ49. Why might map-reduce summarization lose information that a human summarizer wouldn't, and how can you mitigate that?

ROI: ★★★★☆ · Frequency: Medium

Because each chunk is summarized in isolation, the model summarizing chunk 3 has no awareness of what was said in chunk 1 or chunk 12 — it cannot recognize that a detail is a repeated theme, a contradiction, or a callback to something mentioned much earlier, the way a human reading the whole document linearly would. Mitigations include carrying a short running summary forward as extra context into each subsequent chunk's summarization call (so later chunks are summarized with awareness of earlier ones), overlapping chunk boundaries slightly so no detail sits entirely on a hard cut, and using a final reduce pass that is explicitly instructed to look for and reconcile cross-chunk connections rather than just concatenating.

MIDQ50. How does reserving budget for structured output (e.g., a function call with a large JSON schema response) change your context budgeting math compared to reserving budget for free-text output?

ROI: ★★★★☆ · Frequency: Medium-High

A structured/JSON response is typically less token-efficient per unit of information than free text (field names, punctuation, and required schema structure all cost tokens beyond the actual data), and its size is often more predictable and closer to a fixed floor — a schema with 20 required fields has a minimum plausible token cost you can estimate in advance. This means the output reservation for a structured-output call should be sized against the schema's worst-case field count and typical value lengths, not against a generic "leave some room for an answer" heuristic, since an under-reserved structured response is especially bad: a JSON payload truncated mid-object is usually unparseable, unlike truncated prose which is at least partially readable.

MIDQ51. When a model call includes many tool/function definitions, how would you decide which tools to include if you can't fit them all?

ROI: ★★★★☆ · Frequency: Medium-High

This keeps the tool-definition budget bounded and predictable regardless of how many tools the system has registered in total, and avoids the common anti-pattern of registering every available tool on every call "just in case."

MIDQ52. What's the risk of not accounting for the tokens consumed by a tool's output (not just its definition) in a multi-step agent loop?

ROI: ★★★★★ · Frequency: High

Tool outputs (search results, file contents, API responses) get appended back into the context for the next step of the loop, and unlike tool definitions, their size is often unpredictable and can be large — a single tool call that returns a big log file or a large search result set can consume a disproportionate share of the remaining budget. Without budgeting for this, an agent loop that runs for many steps can silently accumulate tool outputs until a later step overflows, often on a step that has nothing to do with the tool call that actually caused the bloat, making the failure confusing to debug.

MIDQ53. Explain why silent truncation is more dangerous than a hard error, using a concrete example of what could go wrong.

ROI: ★★★★★ · Frequency: High

A hard error is loud, catchable, and forces the application to handle it explicitly — nothing wrong reaches the user silently. Silent truncation, by contrast, can drop content from either end without raising any signal: for example, if a client library truncates from the beginning of a long request to fit, a critical system instruction stated once at the start of the conversation (e.g., "never quote a price without confirming current inventory") can be quietly removed, and the model will proceed normally — producing a confident, well-formed, but policy-violating answer, with no error anywhere in the logs to indicate why.

MIDQ55. What's the tradeoff between summarizing history aggressively versus keeping more raw history?

ROI: ★★★★☆ · Frequency: High

Aggressive summarization keeps token cost low and leaves more budget for retrieval and output, but risks losing exact wording, specific numbers, or subtle nuance the user might expect the assistant to still recall precisely. Keeping more raw history preserves fidelity but costs more tokens per call (both in money and prefill latency) and increases the risk of hitting the context limit sooner as the conversation continues — the right balance usually depends on the domain: a legal or medical assistant should lean toward preserving raw specifics longer; a casual conversational assistant can summarize more aggressively with less risk.

MIDQ56. How would you decide, per turn, whether to re-run retrieval or reuse previously retrieved documents already in context?

ROI: ★★★★☆ · Frequency: Medium

Re-run retrieval when the current turn's topic has meaningfully shifted from the working set of already-retrieved documents (detectable via a similarity check between the new query and the existing retrieved set, or a lightweight topic-change classifier), and reuse the existing set when the turn is a clear follow-up on the same topic — this avoids both the latency/cost of unnecessary re-retrieval and the risk of the context growing unbounded with redundant documents from re-running retrieval on every single turn regardless of relevance.

MIDQ57. Why can compacting context (e.g., summarizing history) sometimes hurt cache-hit rate, and how would you balance the two goals?

ROI: ★★★★☆ · Frequency: Medium

Prompt caching relies on an identical stable prefix across calls; if the compaction step rewrites or re-summarizes history on every turn (producing a slightly different summary text each time), that portion of the prompt keeps changing and can never benefit from caching even if it sits early in the sequence. The balance is to keep the summary stable across multiple turns rather than regenerating it every turn — only re-summarize when the window of "recent raw turns" actually needs to shift, and place the more genuinely dynamic content (the current turn) after the summary in the sequence, so the summary itself can still serve as a stable, cacheable prefix segment between regenerations.

SENIORQ68. Design a graceful-degradation strategy for a single-call context overflow: rank fallback options from least to most disruptive to the user experience.

ROI: ★★★★★ · Frequency: High at senior level

SENIORQ69. Design a request-chunking strategy for summarizing a 2-million-token document with a model that has a 128K context window, including how you'd stitch partial results together.

ROI: ★★★★☆ · Frequency: Medium-High at senior level

2 million tokens at, say, a ~100K per-chunk budget (leaving room for instructions and output) means roughly 20 chunks at the leaf level — too many to reduce in one flat pass without the concatenated chunk summaries themselves overflowing, so use hierarchical reduction: summarize the 20 leaf chunks in parallel (map), then merge those 20 summaries in groups of ~5 into 4 intermediate summaries (first reduce level), then merge those 4 into one final summary (second reduce level). To preserve cross-chunk coherence, overlap leaf chunks slightly at their boundaries (e.g., a few hundred tokens of shared context between adjacent chunks) and carry forward a short "running context" note into each chunk's summarization call describing what's been covered so far, so chunk 15's summary can recognize it's continuing a thread from chunk 12 rather than treating every chunk as fully independent.

SENIORQ70. Compare flat map-reduce summarization to hierarchical summarization for a very large document set. When would you choose one over the other, and what does each cost in latency/calls?

ROI: ★★★★☆ · Frequency: Medium-High at senior level

Flat map-reduce costs N map calls plus 1 reduce call, and is simpler to implement and reason about, but only works when the concatenation of all N chunk summaries still fits in one context window for that final reduce call — fine for tens of chunks, breaks down for hundreds. Hierarchical summarization costs N map calls plus multiple reduce levels (roughly log-base-branching-factor of N additional calls), adds latency because reduce levels are sequentially dependent on each other (though each level's calls can run in parallel with each other), but scales to arbitrarily many chunks without any single call ever needing to fit more than its configured budget. Choose flat map-reduce for moderate-sized documents where you know the chunk count is bounded and small; choose hierarchical whenever the corpus size is large, unpredictable, or expected to grow, since it degrades gracefully rather than hitting a hard second-stage overflow.

SENIORQ71. A structured-output call with a large JSON schema and many required fields keeps truncating mid-JSON on long inputs. Diagnose the root cause and propose a fix.

ROI: ★★★★★ · Frequency: High at senior level

The most likely root cause is an output-token reservation sized for typical free-text answers, not for the actual worst-case size of the JSON schema being requested — as input grows (more history, more retrieved context), less budget remains for output, and if the reservation wasn't sized against the schema's real minimum footprint, the model runs out of output tokens mid-object. The fix is to compute a schema-aware output reservation (estimate token cost from the required field count, typical value lengths, and nesting depth) rather than a flat generic reserve, and enforce it as a hard floor: if available input budget plus that floor would exceed the context window, trim input further rather than letting the output reservation shrink below the schema's realistic minimum. Additionally, favor providers/APIs with native structured-output enforcement (which can guarantee well-formed output up to the token limit) over prompting-based JSON, since a native mode fails more predictably at the boundary than a prompted one.

SENIORQ82. Explain how you would benchmark "effective context" for a candidate model before adopting it for a long-context production feature, beyond trusting the advertised max length.

ROI: ★★★★☆ · Frequency: Medium-High at senior level

Run a needle-in-a-haystack style evaluation specific to your domain: insert a known fact at varying positions (start, 25%, 50%, 75%, end) within realistic-length filler content matching your actual use case (e.g., real support tickets or real documents, not generic text), at multiple total lengths up to and beyond your expected production usage, and measure retrieval accuracy at each position/length combination rather than trusting a single aggregate benchmark score. Also test with realistic, domain-relevant "distractor" content rather than purely random filler, since a model's ability to find a needle among genuinely similar-looking distractors is a better proxy for production behavior than its ability to find one among obviously irrelevant text.

SENIORQ83. Design a fallback chain for when a model call fails due to context overflow: what do you try first, second, third, and when do you give up?

ROI: ★★★★☆ · Frequency: Medium-High at senior level

First, retry once with an automatic compaction pass applied (tighter retrieval, more aggressive history summarization) — this resolves the large majority of overflow cases without any user-visible change. Second, if still over budget, drop to a reduced-feature mode (e.g., disable a subset of lower-priority tools, or shrink the output reservation to the schema/format's realistic minimum) and retry. Third, if the current user turn itself is exceptionally large (a big pasted document), surface a specific, actionable message asking the user to shorten or split their input, rather than continuing to retry blindly. Give up and return a clear error only after these options are exhausted, and cap the total number of retry attempts explicitly so a persistently oversized request can't loop indefinitely consuming latency and cost with no chance of success.

SENIORQ84. How would you handle context budgeting for a multi-modal prompt that includes images or documents whose token cost isn't known until after some preprocessing step?

ROI: ★★★★☆ · Frequency: Medium at senior level

Budget conservatively using the provider's published worst-case token cost formula for that media type (many providers publish a token-cost estimate based on image resolution/dimensions before you actually send it), reserving that estimated cost against the input budget before finalizing how much room remains for retrieved text context and history. After the actual preprocessing/encoding step, re-verify the real token cost against the estimate and, if the estimate was low, trigger the same overflow-handling fallback chain used for text (Q83) rather than assuming multi-modal content's cost is negligible or fixed — image and document token costs frequently vary more between inputs than equivalent-length text does, so treating them as budget-worthy from the start avoids a class of overflow bugs that's easy to miss if development testing only used small sample images.

STAFFQ85. Architect a context-budget-aware multi-turn agent system for a platform that must support dozens of tools, long-running tasks, and multiple concurrent models with different context sizes. Describe the major components.

ROI: ★★★★★ · Frequency: Medium at staff level

┌───────────────────────────────────────────────────────────────┐
│  Task State Store  (outside any single model's context window)  │
│  - full task history, all tool outputs, all sub-agent results    │
│  - source of truth; grows unbounded, lives independently of      │
│    any one model call                                            │
└───────────────────────────┬───────────────────────────────────┘
                            ▼
┌───────────────────────────────────────────────────────────────┐
│  Model Context Profile Registry                                  │
│  - per-model max length, tokenizer, output reserve, caching info │
└───────────────────────────┬───────────────────────────────────┘
                            ▼
┌───────────────────────────────────────────────────────────────┐
│  Context Assembler (per step, per model)                         │
│  - queries Task State Store for a BUDGETED, RANKED slice          │
│    (relevant recent steps, relevant tool outputs, pinned facts)  │
│  - applies provider-agnostic ordering: stable→variable            │
│  - enforces schema/output reservation for the step's action type  │
└───────────────────────────┬───────────────────────────────────┘
                            ▼
┌───────────────────────────────────────────────────────────────┐
│  Model Call → result written back to Task State Store             │
└───────────────────────────────────────────────────────────────┘

The core architectural decision is that the model's context window is treated purely as a transient working set, never as the system of record — full task history lives in the external Task State Store, and every step re-derives a fresh, budgeted, model-appropriate slice of it. This is what makes the system work uniformly across concurrent models with wildly different window sizes: swapping which model handles a given step only changes how much of the state store gets pulled into that step's context, not the architecture of the loop itself.

STAFFQ86. Walk through debugging a production incident: a customer complains the assistant "forgot" an instruction given at the very start of a long support conversation, resulting in an incorrect and costly action.

ROI: ★★★★★ · Frequency: Medium at staff level

Start by reconstructing exactly what the model actually received on the request where the incorrect action occurred — not what the application intended to send, but the literal assembled prompt or, at minimum, logged component-level token counts and a flag for whether compaction fired on that request. Form and test three hypotheses in order of likelihood: (1) the instruction was in a portion of history that a sliding-window or summarization policy dropped or compressed by the time of the problematic turn — check the memory manager's logs for whether that specific turn was still in the raw window or had already been folded into a summary, and if summarized, inspect whether the summary preserved the instruction's substance; (2) the instruction was present in the sent context but positioned in a low-attention "middle" zone, consistent with lost-in-the-middle, especially likely if it was only stated once, early, and never reinforced near the end of the context on later turns; (3) the instruction was present and well-positioned, but the model's action was actually driven by a different, contradicting piece of context (e.g., a later turn or retrieved document that implicitly overrode it) — in which case the bug isn't a context-window issue at all, just an instruction-following or prompt-design issue that happens to look like one. Once root-caused, the durable fix is almost always to make the constraint durable across the whole conversation rather than stated-once-and-hoped: pin it as an importance-retained fact (Q60/Q74) and/or reinforce it near the end of context on every subsequent turn, plus add the invariant-check safeguard from Q78 so a future silent-drop is caught before it reaches the model, not after a customer reports the consequence.

Interview Gold Point: Stress that reconstructing the actual sent prompt (not the intended one) is the single highest-leverage first step — most context-window incidents are eventually traced to a gap between what engineers assumed was being sent and what was actually assembled and dispatched, and without that reconstruction every subsequent hypothesis is just guessing.
STAFFQ87. Your company's AI features must run across five model providers with context windows ranging from 8K to 2M tokens, each with different pricing, caching, and truncation behaviors. Design the architecture that lets feature teams write context-management logic once.

ROI: ★★★★☆ · Frequency: Medium at staff level

Build a shared internal platform library — not a convention or a wiki page, an actual dependency every team imports — that owns three things: a ModelContextProfile abstraction per provider (max length, tokenizer, caching capability, recommended output reserve), a standard ContextAssembler that implements the priority-allocation and stable-first ordering logic once against that abstraction, and standard instrumentation emitted automatically by the assembler (component-level token counts, utilization, compaction events) so every team gets observability for free rather than needing to build it themselves. Feature teams then interact only with a high-level API — "here are my candidate content pieces with priorities, here's my target model" — and never touch raw token budgeting or provider-specific truncation quirks directly. Critically, provider-specific behavior (how each provider signals overflow, how each implements caching) is isolated entirely inside the adapter layer beneath the shared library, so onboarding a sixth provider means writing one new adapter, not touching every feature team's code.

STAFFQ88. Design an organization-wide policy and tooling standard for context-window governance: what would you mandate every team's AI feature implement, and how would you enforce it?

ROI: ★★★★☆ · Frequency: Low-Medium at staff level

Mandate: (1) every model call routes through the shared context-assembly library rather than hand-rolled prompt string concatenation, verified via a static-analysis/lint rule that flags direct provider SDK calls bypassing the library; (2) every feature declares an explicit output-token reservation and a maximum acceptable input-utilization target, reviewed as part of that feature's design/launch checklist; (3) every feature emits the standard token/utilization/compaction metrics from day one, enforced by requiring those metrics to appear in a dashboard before a feature is allowed to go to general availability; (4) any feature handling long-running or multi-turn interactions must document its memory-management policy (sliding window, summarization, hybrid, or explicit "not applicable, single-shot only") as part of its design review, so the decision is deliberate rather than accidental. Enforcement leans on automation (lint rules, required dashboards, launch checklists gating GA) rather than relying on teams remembering a written policy, since a policy that isn't enforced by tooling degrades the moment the org scales past the size where everyone knows everyone.

STAFFQ89. A staff engineer proposes eliminating conversation summarization entirely now that the company has moved to a 1M-token context model, reasoning "we can just keep everything." Evaluate this proposal.

ROI: ★★★★★ · Frequency: Medium at staff level

On cost: keeping full raw history means every turn re-processes an ever-larger prefill, and because attention cost scales roughly quadratically, a conversation that grows toward the 1M ceiling becomes dramatically more expensive per turn than a bounded, summarized one — the proposal trades a one-time engineering cost (maintaining summarization) for a compounding, unbounded operational cost. On latency: time-to-first-token scales with input length, so users in very long, un-summarized conversations would experience steadily increasing response latency as the conversation continues, a real user-experience regression that gets worse the longer someone stays engaged — perversely punishing your most engaged users hardest. On correctness: "fits in the window" is not "reliably attended to" — the lost-in-the-middle effect doesn't disappear at 1M tokens, so raw, unsummarized turns 50-950 in a very long conversation are not guaranteed to be used correctly even though they're technically present, meaning the proposal may not even deliver the fidelity benefit it's implicitly promising. On security: a much larger, entirely raw history retained and resent every turn increases the blast radius of any context-leakage or prompt-injection issue (Section 13), since more of the raw, potentially sensitive conversation is present and forwarded on every single call. The right recommendation is not to eliminate summarization but to relax its threshold — summarize less aggressively, later, since the larger window affords more raw-history headroom before compaction is needed — while keeping the underlying discipline intact.

Interview Gold Point: This question tests whether the candidate treats "context window size" as a substitute for engineering discipline or as one input to it — the strongest answers explicitly reframe the proposal from a binary (summarize or don't) to a tunable threshold decision, showing they understand summarization's role isn't solely "make it fit."
STAFFQ90. Design the end-to-end system for a customer support case requiring synthesis of a 500-page policy manual, a 200-turn conversation history, and live retrieved ticket data, for a model with a 200K context window, while keeping cost and latency within SLA.

ROI: ★★★★☆ · Frequency: Medium at staff level

The 500-page policy manual is never sent whole — it's pre-indexed for retrieval (Volume 3), and only the top few ranked, relevant sections (a few thousand tokens) enter context per query, refreshed each turn based on the current question, not resent statically. The 200-turn conversation is handled by the hybrid memory strategy: a rolling summary covering the bulk of older turns, plus the last 10-15 turns kept verbatim, plus a small pinned set of any explicitly stated case-critical facts (account details, prior commitments made to the customer) that must never be summarized away. Live ticket data is treated as its own small, high-priority, always-fresh allocation (pulled fresh each turn, capped tightly, since it's usually a small structured record rather than free text). Putting worked numbers on a 200K window with an 8K output reserve: roughly 3-5K for policy retrieval, 15-20K for conversation memory (summary + recent turns + pinned facts), 1-2K for live ticket data, leaving very generous headroom relative to the 200K ceiling — the SLA risk here is less about raw capacity and more about prefill latency from repeatedly re-processing the growing summary and retrieved content every turn, which argues strongly for structuring the prompt with the stable policy-retrieval and system-prompt content first specifically to make it cacheable, since this conversation will span many turns and many calls to the same stable prefix.

STAFFQ91. How would you design an automated regression-testing framework that catches context-budget related regressions before they reach production?

ROI: ★★★★☆ · Frequency: Low-Medium at staff level

Add a CI check that tokenizes and measures every fixed prompt component (system prompts, tool definitions, few-shot examples) on every pull request touching those files, and fails the build if any component's token count grows beyond a configured threshold or by more than a configured percentage from the previous baseline — catching, for example, an accidental 3x system-prompt bloat before it ever reaches a real user. Pair this with the parameterized small-window/large-window test suite from Q58 run in CI, plus a synthetic long-conversation and large-retrieval-set integration test that asserts compaction fires correctly and the final assembled request stays under budget, all run automatically rather than depending on manual pre-release testing. Track these token-count baselines over time in the same dashboard used for production monitoring, so a slow, incremental drift across many small PRs (none individually alarming) is still visible in aggregate before it becomes a production incident.

STAFFQ92. Describe how you would lead a postmortem and a durable fix for a case where a shared "budget manager" library had a bug that dropped the reserved-output budget to zero under specific input shapes, causing truncated answers across multiple product teams simultaneously.

ROI: ★★★★☆ · Frequency: Low-Medium at staff level

Frame the postmortem around blast radius first: because the bug lived in a shared library, the incident review needs to identify every team/feature that consumes that library's output-reservation logic, not just the team that first reported it, and confirm each was checked for silent impact (truncated answers that were technically "successful" responses might never have triggered an error-rate alert). Root-cause the specific input shape that zeroed the reservation (likely an edge case in the subtraction/allocation arithmetic — e.g., a component whose token count was mis-measured as larger than actual available budget, driving the reserve calculation negative and clamped to zero rather than raising an error). The durable fix has two layers: first, the immediate bug fix plus a regression test encoding the exact input shape that triggered it; second, and more importantly at staff level, a structural safeguard so this class of bug can't recur silently — add a hard assertion in the shared library itself that refuses to proceed (fails loudly) if the computed output reservation ever falls below a sane minimum floor, rather than allowing zero or negative reservations to silently pass through arithmetic and produce a truncated call. Close the loop by adding the specific metric ("output reservation size actually applied per request") to the shared library's standard instrumentation, so a future regression of this shape is caught by a dashboard anomaly within minutes rather than discovered through accumulated customer complaints across several teams.

16. SUMMARY

  • A context window is the fixed, finite number of tokens a model can process as input and output in a single call — an architectural boundary enforced by self-attention's design, not a tunable setting.
  • Context length (the advertised maximum) and effective context (how well the model actually uses positions within that maximum) are different things — the "lost in the middle" effect means fitting content is not the same as the model reliably attending to it.
  • Attention cost grows roughly quadratically with sequence length during prefill, while KV cache memory grows linearly with both sequence length and concurrent batch size during decode — these two curves together explain most of the latency, throughput, and cost behavior you will observe.
  • Because the window has no built-in notion of "important" versus "disposable" content, every production system needs an explicit budgeting and compaction strategy — reserving output tokens, capping retrieval, summarizing or windowing history — or that decision gets made badly by default truncation behavior.
  • Spring AI exposes this as composable, testable pieces — ChatModel/ChatClient for the call itself, Advisors and ChatMemory for injecting and trimming history, TokenTextSplitter and vector-store query limits for keeping retrieval budget-aware — rather than requiring hand-rolled string concatenation.
  • A bigger context window is not automatically a better one: it raises the ceiling on what can technically fit, but disciplined context engineering — what you put in, where you put it, and what you leave out — remains the actual engineering skill, at any window size.
