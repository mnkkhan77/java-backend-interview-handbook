CHAPTER 61 — MCP DEEP DIVE

Volume 4 — AI Agents & MCP · Chapter 8 of 10

Chapter 60 gave you multiple agents coordinating toward a shared goal — planners, workers, critics, all exchanging messages. But every one of those agents still needed to reach outside itself: read a file, query a database, call an internal API, search the web. Multi-agent orchestration answers "how do agents talk to each other"; it says nothing about "how does any single agent talk to the *rest of the world* without every team hand-rolling a bespoke, brittle integration for every tool." That is the exact gap the Model Context Protocol (MCP) was built to close, and understanding it deeply — not just "it's like a plugin system" — is what separates engineers who bolt tools onto agents from engineers who build agent platforms.

1. MOTIVATION

By the time you reach this chapter you already know, from the Tool Calling chapter in Volume 2, that a model can be given a list of function signatures and asked to emit a structured call to one of them instead of free text. That mechanism is real, it works, and Spring AI exposes it cleanly through @Tool-annotated methods and ToolCallback registration on a ChatClient. So why does an entire chapter — indeed, an entire protocol backed by a specification, an SDK ecosystem, and adoption from every major model provider — need to exist on top of something that already works?

Because "it works for one team, one codebase, one model provider" is a very different claim from "it works across an organization, across dozens of tools, across multiple AI applications, maintained by different teams, talking to different models." Tool calling as you learned it in Volume 2 is a local integration pattern: you write Java methods, you annotate them, you wire them into your Spring context, and your application's model sees them. That is correct and sufficient for a single application. The moment you have five different AI applications inside your company — a support copilot, a code review agent, an internal search assistant, a data analyst agent, a DevOps agent — and each one needs access to overlapping capabilities (read from the ticketing system, query the internal knowledge base, look up a customer record, run a Kubernetes command), you face a combinatorial integration problem: N applications × M tools, each pairing hand-built, each with its own auth handling, its own schema conventions, its own bugs.

This is precisely the shape of a problem the software industry has solved before, repeatedly, and each time the solution was the same idea wearing different clothes: stop building N×M point-to-point integrations and build one standard interface that any client can speak and any provider can implement. USB replaced a drawer of proprietary cables. ODBC/JDBC replaced hand-rolled per-database client libraries. LSP (the Language Server Protocol) replaced every IDE needing its own bespoke integration with every programming language's tooling. MCP is that same move applied to AI applications talking to tools, data sources, and systems. If you have ever implemented a JDBC driver, or consumed one, you already have the correct mental model for what MCP is trying to be for AI-tool integration — and this chapter builds on that instinct deliberately.

For your career trajectory specifically: as you move from "engineer who calls an LLM API" toward "AI Engineer who designs the systems around models," MCP is one of the few pieces of this stack that is genuinely infrastructure-shaped rather than application-shaped. Getting it right once, at the platform level, pays off across every agent your organization builds afterward — which is exactly why it deserves a deep dive rather than a paragraph in the tool-calling chapter.

2. HISTORICAL BACKGROUND

2.1 Before MCP: Bespoke Function Calling

When OpenAI introduced function calling in mid-2023, and other providers followed with their own tool-calling formats, the industry got a real capability (a model can request a structured action) but not a standard for where those function definitions come from or how the actual execution happens. Every team wrote its own glue: a hardcoded list of Python or Java functions, manually kept in sync with a JSON schema describing their parameters, manually wired to whatever execution backend the function needed to reach. This worked, but it did not scale past a single application's boundary. If Team A built a "search internal wiki" tool for their support bot, Team B building a code assistant had no way to discover or reuse it — they re-implemented their own wiki search integration from scratch, with their own auth handling and their own subtly different schema.

2.2 Adjacent Prior Art: Plugins and Extensions

The first attempt at a shared answer was the "plugin" model — ChatGPT Plugins (announced early 2023) let a model call out to a third-party HTTP API described by an OpenAPI-like manifest. This was directionally correct (a standard description format, discoverable by a model) but it was tightly coupled to one vendor's product, assumed a public HTTP endpoint (poor fit for internal, local, or stateful tools like a local filesystem or a database connection pool), and had a thin, one-shot request/response model with no strong story for long-running sessions, streaming results, or the tool surface changing dynamically during a conversation.

2.3 The Emergence of MCP

Anthropic introduced the Model Context Protocol in November 2024 as an open specification, explicitly framed as solving the N×M integration problem rather than as a proprietary feature of one product. The protocol was deliberately built on top of an existing, already-standardized transport idea — JSON-RPC 2.0 — rather than inventing a new wire format, which is itself a lesson worth internalizing: good infrastructure standards reuse boring, well-understood primitives underneath and add value in the layer that is actually novel (here: the vocabulary of tools, resources, prompts, and how an AI client and a capability server negotiate them). Within roughly a year, MCP saw adoption across multiple model providers and a large ecosystem of community and vendor-built MCP servers (for GitHub, Slack, Postgres, filesystems, Google Drive, and many more), which is the strongest practical evidence that the "shared standard" bet was the correct one — the alternative universe, where every provider kept its own incompatible tool-calling dialect, was actively getting worse before MCP arrived.

2.4 Why "Protocol" and Not "Library"

It matters that MCP is a protocol — a specification for messages exchanged over a transport — rather than a library you import. A library ties you to a language and a process boundary. A protocol lets an MCP server written in Python, TypeScript, or Java speak to an MCP client written in a completely different language and process, running on a different machine, built by a different team, as long as both sides implement the spec correctly. This is the same reason HTTP outlived any particular web server implementation, and it is why Spring AI's MCP support (covered in Section 9) is a client/server implementation of an external spec, not a Spring-invented abstraction.

3. PROBLEM STATEMENT

Define a single, vendor-neutral, language-neutral contract by which an AI application (the "host," containing one or more "clients") can discover, invoke, and receive results from external capabilities — tools, data resources, and reusable prompts — exposed by independent "servers," without either side needing to know the other's implementation details in advance.

Unpack that carefully, because every clause is load-bearing. "Discover" means the AI application does not need the tool list hardcoded at build time — it can ask a running server "what can you do?" and get back machine-readable schemas at runtime. "Invoke... without either side needing to know implementation details" means the host application never needs a Python import or a Java classpath dependency on the server's internals — it only needs to speak the protocol. "Independent servers" means the team that owns the Postgres database, or the ticketing system, or the internal deployment pipeline, can build and own the MCP server for that system, versioned and deployed separately from any of the AI applications that consume it — this is the same separation of concerns you already value in microservice architecture, applied to AI capabilities specifically.

Notice what MCP explicitly does not try to solve: it does not decide which tool the model should call (that is still the model's reasoning, informed by the tool descriptions — a topic that connects back to Prompt Engineering and forward to Agent Architectures in the next chapter), and it does not replace your authentication or authorization system (it defines how credentials and scopes are transported and negotiated at the protocol level, but your organization still owns the actual identity and access policy). MCP is deliberately narrow in scope: it standardizes the wire contract for context exchange between AI applications and capability providers, nothing more, nothing less. That narrowness is a design virtue, not an omission — a protocol that tried to also standardize agent reasoning, orchestration, and security policy would have failed to gain adoption the way MCP has.

4. THEORY

4.1 The Three Roles: Host, Client, Server

MCP defines three participants, and confusing them is the single most common source of misunderstanding when engineers first encounter the spec.

  • Host — the AI application itself: your Spring Boot service, an IDE like Claude Code, a desktop chat app. The host owns the conversation with the end user and the connection to the LLM.
  • Client — a component living inside the host that maintains a 1:1 stateful connection to exactly one MCP server. A host with three MCP servers configured runs three clients internally, one per server. The client speaks the protocol; the host decides what to do with the results.
  • Server — an independent process (or remote service) that exposes capabilities — tools, resources, and prompts — over the protocol. A server knows nothing about the LLM, the conversation, or the host's business logic; it only knows how to answer protocol requests.

The analogy that makes this click for a backend engineer: think of the host as your Spring Boot application, the client as a DataSource/connection pool object, and the server as the actual database. Your application code doesn't talk raw TCP to Postgres — it talks to a DataSource, which manages a connection following a standard protocol (the Postgres wire protocol) to a server process that has no idea your application even exists beyond the current session. MCP clients and servers relate the same way, just for "tools and context" instead of "rows and transactions."

4.2 The Three Capability Primitives

A server can expose three distinct kinds of capability, and the distinction between them matters enormously for how a model is expected to use each one:

PrimitiveWho Decides to Use ItAnalogyExample
ToolsThe model, autonomously, based on the conversationA method call with side effects or a lookupcreate_jira_ticket(title, description), run_query(sql)
ResourcesThe host application (or the user), typically attached deliberately as contextA file handle / URI you read fromfile:///project/README.md, postgres://schema/orders_table
PromptsThe user, selected explicitly (often as a slash command / template)A parameterized, reusable prompt templateA "summarize this incident" template a server ships pre-written

This three-way split maps directly onto a distinction you already reasoned about in the Prompt and PromptTemplate chapters: not all context belongs in the same bucket. Tools are for the model to reach for when it decides it needs an action or a lookup. Resources are for context that a human or the host explicitly decides is relevant background (much like retrieved documents in RAG, but sourced live from a system rather than a vector store). Prompts are reusable, curated interaction patterns that a server author wants to hand the user directly, bypassing the model's own judgment about when to use them.

4.3 Sampling: The Direction Nobody Expects

The theoretical piece that surprises most engineers on first read is sampling — the ability for a server to ask the host's LLM to generate a completion, flowing in the opposite direction from tools. Why would a tool server ever need to call the model? Because some server-side logic is itself best expressed as "ask an LLM to do a sub-task" — for example, a code-review MCP server that wants to summarize a diff using the same model the host is already paying for and authenticated against, rather than bundling its own separate model credentials. Sampling keeps the human/host in control (the host can inspect and approve the sampling request before it goes to the model, and approve the result before it goes back to the server) while letting server authors compose LLM calls into their own capability logic without owning a model integration themselves. This is an advanced, less commonly implemented part of the spec, but understanding it exists prevents the common misconception that MCP messages only ever flow "host asks server for stuff."

5. INTERNAL WORKING

5.1 Connection Lifecycle

Every MCP session, regardless of transport, follows the same lifecycle, and knowing it precisely is what lets you debug a broken integration instead of guessing:

  1. Transport connect. The client establishes the underlying channel — for a local server this is typically spawning a subprocess and connecting to its stdin/stdout (the stdio transport); for a remote server it is an HTTP connection, historically using Server-Sent Events for the server-to-client stream and now converging on a Streamable HTTP transport that supports both plain request/response and streaming over a single endpoint.
  2. Initialize handshake. The client sends an initialize request declaring its protocol version and its own capabilities (e.g., "I support sampling callbacks"). The server responds with its protocol version and the capabilities it supports (tools? resources? prompts? does its tool list change at runtime?). This is a negotiation, not an assumption — a client and server that disagree on protocol version can fail gracefully or fall back, rather than silently misbehaving.
  3. Initialized notification. The client confirms the handshake is complete and normal operation can begin.
  4. Discovery. The client calls tools/list, resources/list, and/or prompts/list as relevant. Each returns machine-readable descriptions — for tools, this is a name, a human-readable description (which is itself effectively a piece of prompt engineering, since the model reads it to decide when to invoke the tool), and a JSON Schema describing the expected arguments.
  5. Invocation. During the actual conversation, when the model decides (or the host decides, for resources) that a capability is needed, the client sends tools/call (or resources/read, or prompts/get) with the concrete arguments. The server executes and returns a result — which can be plain text, structured content, an error, or in newer versions of the spec, a request for additional user input mid-call (elicitation).
  6. Change notifications. If the server's capability set can change at runtime (a plugin loads a new tool, a resource becomes unavailable), it can send list_changed notifications so the client refreshes its view without needing to poll.
  7. Teardown. The client closes the connection; for stdio this typically also terminates the server subprocess.

5.2 What Actually Happens on a Tool Call — End to End

Trace a single user request through the whole system, because this is where the mental model solidifies. Say a user asks a support copilot, "What's the status of ticket SUP-4521?"

  1. The host's ChatClient-equivalent orchestration layer sends the conversation, plus the list of currently available tools (aggregated from every connected MCP server, converted into whatever tool-calling format the underlying model expects), to the LLM.
  2. The model's response is not natural language — it is a structured request: "call tool get_ticket_status with argument {"ticket_id": "SUP-4521"}." This is the exact same mechanism you learned in the Tool Calling chapter; MCP has not changed how the model itself signals a tool call.
  3. The host looks up which MCP client owns a tool named get_ticket_status (it was registered during discovery in step 4 of the lifecycle above) and forwards a tools/call JSON-RPC request to that client.
  4. The client sends the request over its transport to the ticketing MCP server. The server — a completely independent process, possibly maintained by the platform team that owns the ticketing system, with its own database connection and its own auth token — executes the actual lookup.
  5. The server returns a JSON-RPC response containing the result (formatted as content blocks — text, and optionally structured JSON if the tool declares a structured output schema).
  6. The host's orchestration layer inserts that result back into the conversation as a tool result message and sends the updated conversation back to the model.
  7. The model now generates the final natural-language answer to the user, grounded in the real ticket data it just received.

The critical insight this trace reveals: the model never talks to the MCP server directly. The model only ever talks to the host via the normal chat completion API; the host's orchestration layer is the one translating between "the model's tool-call intent" and "an actual MCP protocol message." This matters for reasoning about failure modes — if a tool call hangs, times out, or returns malformed data, that is squarely the host/client's problem to handle (retry, fall back, surface an error to the model as a tool result so it can react), not something the model has any visibility into beyond whatever result text it is eventually shown.

5.3 Edge Cases Worth Reasoning Through

  • What if two servers expose a tool with the same name? The host must namespace or disambiguate (commonly by prefixing with the server name) before presenting the merged tool list to the model — the protocol does not solve naming collisions for you across servers.
  • What if the server's tool list changes mid-conversation? A well-behaved client listens for list_changed and re-fetches, but a host that already sent a stale tool list to the model in an earlier turn may see the model attempt to call a now-removed tool — the host must handle that as a normal tool-execution error.
  • What if a tool call never returns? The client must enforce its own timeout; MCP does not mandate one. A hung filesystem or database-backed server can otherwise stall an entire agent turn indefinitely.
  • What if the server crashes mid-session (stdio transport)? The client detects the closed pipe and must decide whether to restart the subprocess transparently or surface a hard failure — this is exactly the kind of resilience logic you already design for flaky downstream dependencies.

6. MATHEMATICS

MCP is a protocol and integration architecture, not a statistical or learned system, so this section is intentionally light rather than padded with irrelevant formalism — unlike the Attention or Vector Mathematics chapters, there is no gradient, distribution, or optimization objective native to MCP itself. The one quantitative lens genuinely worth building intuition for is combinatorial cost, because it is the entire economic argument for the protocol's existence.

Without a shared protocol, connecting N AI applications to M tool-providing systems requires, in the worst case, a custom integration for every pairing that actually needs to exist — bounded above by N × M integrations, each independently built, tested, authenticated, and maintained. With a shared protocol, each application implements the client side of the spec once, and each system implements the server side once, for a bound of N + M total integration efforts — every application can then reach every server that exists, and every new server built afterward is immediately usable by every existing application, with zero additional integration work on either side.

Notice the organizational shape this enables, which is the real production payoff: the team that owns a system is the team that owns and operates the MCP server exposing it, the same way the Ops team owns the deployment tooling API and the Sales Engineering team owns the CRM integration. The AI application team consumes these servers as dependencies, exactly as they would consume any other internal service — with a service-level agreement, a health check, versioning, and an on-call rotation belonging to the owning team, not the consuming team. This is a direct structural improvement over the pre-MCP world where the AI application team would have had to build and maintain bespoke integration code against the CRM's raw API themselves, duplicating logic the CRM team already understands better.

Two production concerns deserve explicit mention here because they are easy to underweight when a demo is the only thing that has been tested: transport choice and process supervision. Stdio-transport servers, spawned as local subprocesses, are appropriate for local development or single-tenant desktop tools (an IDE integration, a CLI agent) but do not fit a multi-tenant server-side deployment well — you do not want to spawn a new OS process per user session. For server-side production hosts, remote MCP servers over Streamable HTTP, deployed as their own scalable services behind the gateway, are the correct shape, and they need the same health checks, autoscaling, and graceful-degradation planning as any other internal HTTP service.

9. JAVA / SPRING PERSPECTIVE

Spring AI treats MCP as a first-class integration surface on both sides of the connection — you can build a Spring Boot application that acts as an MCP client consuming external servers, and you can build a Spring Boot application that acts as an MCP server exposing your own Java methods to any MCP-compliant host, including hosts that are not Java applications at all.

9.1 Spring AI as an MCP Client

On the consuming side, Spring AI's MCP client starter auto-configures one or more MCP client connections from your application.yml — declaring stdio-based servers (a command to launch) or HTTP/SSE-based remote servers by URL — and exposes the tools those servers advertise as ordinary ToolCallback instances. This is the crucial architectural point: from the point of view of your ChatClient call, an MCP-provided tool and a locally defined @Tool-annotated Java method are indistinguishable — both end up as callbacks in the same tool list passed to .tools(...) on the ChatClient fluent API. This is exactly the abstraction discipline the Tool Calling chapter set you up to expect: the model-facing contract for "a tool" does not care whether the implementation is three lines of local Java or a network call to a server another team owns. 

// application.yml (conceptual shape)
spring:
  ai:
    mcp:
      client:
        stdio:
          connections:
            filesystem:
              command: npx
              args: ["-y", "@modelcontextprotocol/server-filesystem", "/data"]
        sse:
          connections:
            ticketing:
              url: https://internal-mcp.example.com/ticketing

// Java: the resulting tools flow into ChatClient exactly like local @Tool methods
ChatResponse response = chatClient.prompt()
    .user("What's the status of ticket SUP-4521?")
    .toolCallbacks(mcpToolCallbackProvider.getToolCallbacks())
    .call()
    .chatResponse();

9.2 Spring AI as an MCP Server

On the providing side, Spring AI lets you expose existing Spring-managed beans as MCP tools with the same @Tool annotation style you already use for local tool calling — the same method, annotated the same way, can be registered into an embedded MCP server so that other applications (a Claude Desktop instance, another team's Spring Boot host, a non-Java host entirely) can discover and call it over the protocol, without those consumers ever touching your Java classpath. 

@Service
public class TicketingTools {

    private final TicketRepository ticketRepository;

    public TicketingTools(TicketRepository ticketRepository) {
        this.ticketRepository = ticketRepository;
    }

    @Tool(description = "Look up the current status of a support ticket by its ID")
    public TicketStatus getTicketStatus(String ticketId) {
        return ticketRepository.findById(ticketId)
            .map(Ticket::toStatus)
            .orElseThrow(() -> new TicketNotFoundException(ticketId));
    }
}

// Spring Boot MCP server starter auto-registers @Tool beans and exposes them
// over stdio or Streamable HTTP, generating the JSON Schema from the method
// signature automatically — the same mechanism used for local tool calling,
// just fronted by a protocol endpoint instead of an in-process call.

The design lesson worth internalizing here mirrors something you already know from building REST APIs versus internal service classes: the same business logic (fetching a ticket) can be exposed through multiple transport layers (a REST controller, an internal method call, now an MCP tool) without duplicating the logic itself. MCP support in Spring AI is best understood as "one more transport binding" for tool logic you would likely be writing anyway, not a parallel universe of AI-specific code.

10. BEST PRACTICES

  • Write tool descriptions for the model, not for yourself. The description on an MCP tool is effectively a micro prompt the model reads to decide when and how to call it — vague descriptions ("gets data") produce unreliable invocation; specific ones ("Look up the current status, assignee, and priority of a support ticket given its ticket ID, e.g. SUP-4521") produce reliable invocation. This is the Prompt Engineering chapter's lessons applied at the tool-schema layer.
  • Version your MCP servers deliberately. A tool's name and parameter schema is a contract every consuming host has baked into its model's context; changing a parameter's meaning silently is a breaking change exactly like changing a public API's contract, and should be treated with the same discipline (additive changes, deprecation windows, new tool names for incompatible changes).
  • Scope credentials per server, not per host. A CRM MCP server should hold and manage its own downstream CRM credentials, scoped as narrowly as the use case requires — the host application should never need direct CRM credentials just because it happens to be the thing initiating the call.
  • Prefer remote (HTTP-based) servers for anything multi-tenant or production-facing, and reserve stdio-based local servers for developer tooling, single-user desktop hosts, or local development — this maps directly to the process-supervision concern raised in Section 8.
  • Treat tool results as untrusted input to the model, the same way you treat retrieved documents in RAG — a compromised or buggy server can return adversarial content that lands directly in the model's context (this connects directly to Section 13).
  • Keep the tool surface small and purposeful per server. A server exposing forty loosely related tools makes the model's tool-selection problem harder and increases the chance of the wrong tool being picked; group tightly by domain (ticketing, not "general utilities").

11. COMMON MISTAKES

  • Confusing MCP with a replacement for tool calling itself. MCP does not change how a model decides to call a tool or how tool-call messages are formatted for the model — it standardizes how the host discovers and executes the tool once the model has decided. Teams that expect MCP to somehow improve model reasoning about when to call a tool are solving the wrong layer's problem.
  • Running a stdio MCP server per user request in a server-side production app. Spawning an OS process per incoming HTTP request to talk to a local MCP server does not scale and reintroduces exactly the kind of per-request resource cost that connection pooling was invented to eliminate for databases — use a persistent remote server for multi-tenant workloads instead.
  • Exposing overly broad tools "for flexibility," like a single generic run_sql(query) tool with no guardrails. This collapses the security and reliability benefits of narrow, well-described tools into a single high-blast-radius capability — see Section 13.
  • Forgetting that tool list discovery has a cost. Every MCP server connected to a host adds tokens to every single model call (the tool schemas are sent with every request, not just once) — connecting a dozen servers "just in case" quietly inflates prompt size and cost across your entire application, a direct callback to the Context Window and Performance discussions elsewhere in this series.
  • Trusting server-provided tool descriptions and results unconditionally. A misbehaving or malicious third-party MCP server can craft descriptions that manipulate the model's behavior (a form of prompt injection at the tool-definition layer, not just the tool-result layer) — vet third-party servers the way you would vet any dependency with code-execution-adjacent capability.
  • Treating protocol version mismatches as unlikely edge cases. As the spec evolves, a client built against an older protocol version talking to a newer server (or vice versa) is a realistic production scenario, not a hypothetical — skipping the initialize handshake's capability negotiation and assuming a fixed feature set leads to confusing runtime failures.

12. PERFORMANCE CONSIDERATIONS

MCP introduces a genuine extra network hop and process boundary compared to a purely local tool call, and every performance conversation about it should start from that fact honestly rather than pretending the abstraction is free.

  • Added latency per call. A local @Tool method call is a Java method invocation — nanoseconds to microseconds of overhead beyond the work itself. An MCP tool call over Streamable HTTP adds a network round trip, JSON-RPC serialization/deserialization, and whatever latency the server's own downstream dependency (its database, its API) adds. For latency-sensitive agent loops calling many tools in sequence, this compounds — five sequential MCP tool calls at 100ms each is half a second of pure protocol overhead before counting the actual work or the model's own inference time between calls.
  • Token cost of tool schemas. As noted in Common Mistakes, every connected server's tool (and resource, and prompt) definitions are typically included in every model request that might need them, consuming context window and driving per-request token cost linearly with the number of connected servers and their tool counts — this is a direct, measurable cost lever, not a theoretical one, and it connects to the cost-optimization instincts built in the Context Engineering chapter.
  • Connection and session overhead. Establishing a fresh MCP session (handshake, discovery) per request is wasteful; production hosts should maintain persistent, pooled connections to remote MCP servers across requests, analogous to how you would never open a fresh JDBC connection per query in a well-built Spring application.
  • Parallelizable vs. sequential tool calls. When a model requests multiple independent tool calls in one turn, the host's orchestration layer can dispatch them concurrently rather than sequentially — this is an application-level decision MCP does not make for you, and it is often the single biggest lever available for reducing end-to-end agent turn latency.
  • Server-side scaling is now your problem too. Because a shared MCP server may be called concurrently by many different host applications and many different conversations within each host, the server itself needs the same load testing, connection pooling to its own downstream systems, and autoscaling posture as any other shared internal service — a slow or saturated MCP server becomes a shared bottleneck across every AI application that depends on it.

13. SECURITY CONSIDERATIONS

MCP has a real and non-trivial security surface, precisely because it is designed to let a model-driven system take actions and read data through a standardized, discoverable interface — the standardization that makes it powerful is the same property that makes a security mistake here reusable across every host that connects to a compromised or careless server.

  • Confused deputy risk. A host application typically authenticates once to an MCP server (say, with a service-level API key), and the server then acts on behalf of whichever end user's conversation triggered the call. If the server does not separately verify that the requesting end user is authorized for the specific data or action being requested, the host's broad credential can be used to bypass per-user authorization entirely — this is the same "confused deputy" problem long studied in classical access control, now showing up at the tool-invocation layer.
  • Prompt injection via tool results and resources. Content returned from an MCP server — a file's contents, a database row, a ticket description — flows directly into the model's context exactly like retrieved documents in RAG. If that content was authored or influenced by an untrusted party (a customer-submitted ticket description, a third-party document), it can contain text crafted to hijack the model's subsequent behavior, precisely the mechanism described in the Prompt Engineering and earlier Security discussions in this series, now with an additional entry point.
  • Malicious or compromised third-party servers. Because MCP servers are often installed from community or vendor sources (an npm package, a Docker image), connecting to one is a supply-chain decision with the same weight as adding any other third-party dependency — a malicious server can exfiltrate data passed to it, misreport tool descriptions to manipulate model behavior, or return crafted results, and none of that is prevented by the protocol itself.
  • Overly powerful tools as a blast-radius problem. A tool like run_sql(query) or execute_shell_command(cmd) exposed without strict sandboxing effectively hands the model (and, transitively, whatever crafted its most recent input) the ability to perform arbitrary destructive actions — the fix is the same discipline you already apply to any privileged internal API: narrow, purpose-specific tools, parameterized rather than free-form where possible, with server-side authorization checks that do not simply trust the host.
  • Sampling as a new trust boundary. Because sampling lets a server request an LLM completion from the host, a malicious server could attempt to use the host's model access for its own purposes (cost abuse, generating content the server itself couldn't) — well-implemented hosts require explicit user or policy approval before honoring sampling requests, rather than auto-approving them.

Being honest about scope: MCP's security model deliberately leans on the host and the server implementer for policy enforcement rather than baking in a full authorization framework itself — much as HTTP does not itself decide who is allowed to call an API, only how the call is structured. Treat every MCP server connection with the same seriousness as adding a new privileged dependency to a production system, because that is exactly what it is.

14. INTERVIEW QUESTIONS

JUNIORQ1. What problem does MCP solve that plain tool/function calling does not?

ROI: ★★★★★ · Frequency: Extremely High

Tool/function calling defines how a model requests a structured action, but says nothing about where that tool's implementation lives or how different applications can share it. MCP standardizes the transport and discovery layer so that a tool (or data resource, or prompt template) built once, as an independent server, can be reused by any compliant AI application, instead of every application hand-building and re-implementing the same integration.

JUNIORQ2. Name the three roles defined by MCP and briefly describe each.

ROI: ★★★★☆ · Frequency: High

Host: the AI application itself (owns the conversation and the LLM connection). Client: a component inside the host maintaining a 1:1 session with one server. Server: an independent process exposing tools, resources, and/or prompts over the protocol, with no knowledge of the host's business logic or the LLM.

MIDQ3. What are the three capability primitives MCP servers can expose, and how do they differ in who decides to use them?

ROI: ★★★★★ · Frequency: Extremely High

Tools are invoked at the model's discretion during reasoning, like a function call with side effects or a lookup. Resources are pieces of context (files, database rows, documents) typically attached deliberately by the host or user, similar to retrieved context in RAG. Prompts are reusable, parameterized templates a server author ships for the user to explicitly select, bypassing the model's own judgment about when to use them.

MIDQ4. Walk through what happens, step by step, from a user's question to a final answer, when that answer requires an MCP tool call.

ROI: ★★★★★ · Frequency: High

The host sends the conversation plus available tool schemas to the LLM; the model returns a structured tool-call request (not natural language); the host's orchestrator maps the requested tool name to the owning MCP client and sends a tools/call JSON-RPC request over that client's session; the MCP server executes the actual logic and returns a JSON-RPC result; the host appends that result to the conversation as a tool message and sends the updated conversation back to the model; the model then produces the final natural-language answer. The model itself never communicates with the MCP server directly — only with the host.

SENIORQ5. When would you choose a stdio-based MCP server versus a remote HTTP-based one, and why does it matter for a production Spring Boot application?

ROI: ★★★★★ · Frequency: High at senior level

Stdio transport spawns the server as a local subprocess communicating over stdin/stdout — it fits local development, single-user desktop hosts, or IDE integrations well, but does not fit multi-tenant, server-side production deployments, since you would need to spawn and manage a process per session/user, which does not scale and reintroduces the per-request resource overhead that connection pooling exists to eliminate. Remote servers over Streamable HTTP are the correct shape for production Spring Boot hosts: they can be deployed, scaled, and health-checked as independent services, support persistent pooled connections across requests, and can be owned/operated by the team responsible for the underlying system, matching normal internal-service architecture.

SENIORQ6. How does Spring AI unify locally-defined tools and MCP-provided tools from the perspective of a ChatClient call?

ROI: ★★★★☆ · Frequency: Medium-High

Spring AI's MCP client auto-configuration converts the tools discovered from each connected MCP server into ordinary ToolCallback instances, the same abstraction produced by local @Tool-annotated methods. Both flow into the same tools(...)/tool-callback list passed to a ChatClient call, so from the model-facing contract's perspective there is no distinction between "a Java method three lines away" and "a tool served by a remote MCP server owned by another team" — the orchestration and prompt-construction logic is identical either way.

Interview Gold Point: Explicitly name the architectural benefit this buys: teams can migrate a tool from "local Java method" to "shared MCP server" (or vice versa) without changing any calling code in the host application, because the abstraction boundary (ToolCallback) is stable across that change — this is the same value proposition as an interface/implementation split, applied to tool provisioning.
SENIORQ7. What is a "confused deputy" risk in an MCP deployment, and how would you mitigate it?

ROI: ★★★★☆ · Frequency: Medium at senior level

A host typically authenticates to an MCP server with a single, broad service credential, then triggers tool calls on behalf of many different end users through many different conversations. If the server trusts that host-level credential as sufficient authorization for any requested action, without separately verifying that the specific end user driving the current conversation is authorized for that specific data or action, an attacker (or a misused conversation) can leverage the host's broad access to bypass per-user authorization — the server has become a "confused deputy" acting with more authority than the actual requester should have. Mitigation: propagate end-user identity/claims through to the server (not just host-level credentials) and enforce authorization at the server, per call, based on that identity — never assume host-level authentication implies per-user authorization.

STAFFQ8. A stakeholder asks: "Why should we adopt a shared protocol like MCP instead of just having each team build direct integrations to the systems they need?" Make the engineering and organizational case.

ROI: ★★★★★ · Frequency: High at staff level

Direct, per-team integrations scale as roughly N applications × M systems in the worst case — every new AI application re-implements integration, auth, and schema handling for every system it needs, and every new system requires bespoke work from every consuming team. A shared protocol reduces this to roughly N + M: each application implements the client side once and gains access to every compliant server; each system's owning team implements the server side once and it becomes usable by every current and future AI application without further integration work. Organizationally, this also lets ownership follow domain expertise correctly — the team that understands the CRM or the deployment pipeline best builds and operates the MCP server for it, versioned and secured independently, rather than every AI application team reverse-engineering and duplicating that system's API surface themselves. The trade-off worth naming honestly: it introduces a network hop and a shared dependency surface that must be operated with production rigor (health checks, versioning, authz, observability) — the case for adopting it holds once you have more than a small, fixed number of application-to-system pairings, which is realistically almost every organization building more than one AI application.

JUNIORQ9. What is JSON-RPC 2.0, and why did MCP build on top of it rather than defining its own wire format?

ROI: ★★★★★ · Frequency: Extremely High

JSON-RPC 2.0 is a lightweight, transport-agnostic remote procedure call spec: every message is a JSON object with a method name, optional params, and (for requests) an id used to match a later response. MCP reuses it wholesale rather than inventing a new format because it is already standardized, has mature parser libraries in every language, and cleanly separates "what the message means" from "how it travels" — the same JSON-RPC envelope works unchanged over stdio pipes or an HTTP connection, so MCP only had to define its own vocabulary of methods (initialize, tools/list, tools/call, etc.) on top of an already-solved transport-independent message format.

JUNIORQ10. JSON-RPC defines three message shapes. Name them and say how MCP uses each.

ROI: ★★★★☆ · Frequency: High

Request (carries an id, expects a matching response) — e.g. tools/call. Response (carries the same id back, either a result or an error) — the server's reply to a request. Notification (has no id, and the sender expects no reply) — e.g. notifications/progress or notifications/tools/list_changed, used for fire-and-forget signals in either direction. The presence or absence of an id is the entire distinguishing feature, and it is why a client must never block waiting for a "response" to a message it sent as a notification.

JUNIORQ11. What is the practical difference between a "request" and a "notification" in MCP, and why does that difference matter for a client implementation?

ROI: ★★★★☆ · Frequency: Medium-High

A request carries an id and obligates the receiver to send back exactly one response (result or error); a notification has no id and the receiver is not expected — and must not — reply. This matters because a client's transport layer has to route incoming messages by id to whichever pending call is awaiting them, while notifications need a separate, non-blocking handler path (e.g., updating a locally cached tool list on list_changed) — conflating the two paths is a common source of hung clients waiting on a response that was never going to arrive.

JUNIORQ12. What does the initialize handshake actually accomplish, and what happens if a client skips it?

ROI: ★★★★★ · Frequency: High

initialize is the first request a client sends after connecting; it declares the client's protocol version and which optional MCP features it supports, and the server replies with its own version and supported features, plus basic server metadata. A client that skips it (or ignores the response) is guessing about the server's capabilities instead of knowing them — it might call resources/list on a server that doesn't implement resources at all, or assume progress notifications are supported when they aren't, producing failures that look like server bugs but are really unhandled capability mismatches on the client side.

JUNIORQ13. Describe the stdio transport in one sentence, and name the kind of deployment it's a poor fit for.

ROI: ★★★★★ · Frequency: Very High — asked in nearly every MCP-focused interview

In the stdio transport, the client spawns the MCP server as a local child process and exchanges JSON-RPC messages over that process's stdin and stdout. It is a poor fit for any multi-tenant, server-side production deployment, since you would need to spawn and supervise one OS process per concurrent user/session, which does not scale the way a shared, pooled remote connection does.

Interview Gold Point: Frame it as a proximity-trust model — stdio works precisely because the server is co-located with and spawned by the host, which is also why it needs a weaker authentication story than a remote server ever could.
JUNIORQ14. What is Streamable HTTP, at a high level, and what transport did it replace in the MCP spec?

ROI: ★★★★☆ · Frequency: High, especially in recent interviews

Streamable HTTP is MCP's remote transport: the client POSTs JSON-RPC messages to a single HTTP endpoint, and the server can respond either with a plain JSON body or, when it needs to stream multiple messages (progress notifications, then a final result), by upgrading that same response to a Server-Sent Events stream. It replaced an earlier, more rigid transport that required a long-lived SSE connection opened up front for all server-to-client messages — Streamable HTTP folds request/response and streaming into one endpoint, which is friendlier to ordinary HTTP infrastructure like load balancers and proxies.

Interview Gold Point: Streamable HTTP negotiates within a single POST/response pair whether the reply is plain JSON or an SSE upgrade — client and server don't have to pre-agree, which is exactly why it removed the older transport's need to open a long-lived connection before you even know whether streaming is needed.
JUNIORQ15. When a server describes a tool, what does the JSON Schema attached to it actually tell the model, and who writes it?

ROI: ★★★★☆ · Frequency: Medium-High

The schema tells the model exactly what arguments the tool accepts — parameter names, types, which are required, and any constraints (enum values, string formats) — the same way a Java method signature tells a compiler what it needs. In most MCP server frameworks this schema is generated automatically from the server's own function/method signature (Spring AI does this from an annotated Java method's parameter types; Python's FastMCP does it from type hints), so the server author writes ordinary typed code and the schema is a byproduct, not something hand-authored as raw JSON.

JUNIORQ16. What kinds of content can a tool's result actually contain?

ROI: ★★★☆☆ · Frequency: Medium

A tool result is a list of content blocks, not a single string — commonly plain text, but the spec also allows image content (base64-encoded with a MIME type), audio content, and embedded resource content (effectively handing back a resource by reference or inline). A single tool call can return a mix — for example, a chart-generation tool returning both a text summary and an image block — and the host is responsible for presenting each block type appropriately back to the model or the user.

JUNIORQ17. A resource is identified by what, and can you give two example resource identifiers?

ROI: ★★★★☆ · Frequency: Medium-High

A resource is identified by a URI, and the scheme is left open for the server author to define meaningfully — file:///project/README.md for a filesystem server, or postgres://schema/orders_table for a database server, are both valid MCP resource URIs. The client doesn't need to understand the scheme's semantics; it only needs to pass the URI back to resources/read on the same server that advertised it.

JUNIORQ18. How is a prompt primitive different from a tool, in terms of who triggers it?

ROI: ★★★★☆ · Frequency: Medium

A tool is invoked at the model's own discretion, mid-reasoning, based on what it decides the conversation needs. A prompt is a reusable, parameterized template that a server author ships and that the user (or host UI) selects explicitly — much like a slash command — bypassing the model's judgment entirely about whether and when to use it. The model may still be involved in filling in the prompt's arguments, but the decision to invoke that particular template comes from the user, not from autonomous model reasoning.

JUNIORQ19. Why do tools/list, resources/list, and prompts/list support pagination, and how does a client use it?

ROI: ★★★☆☆ · Frequency: Medium

A server might expose hundreds or thousands of resources (every file in a large repository, every row-backed record in a database), and returning them all in a single response would be wasteful or outright unworkable. These list operations return a page of results plus an opaque cursor; a client that wants the next page passes that cursor back in a follow-up request. Cursors are opaque to the client by design — it must never attempt to construct or interpret one itself, only pass back exactly what the server gave it.

JUNIORQ20. What is the MCP Inspector, and when would you reach for it?

ROI: ★★★★☆ · Frequency: Medium-High

The MCP Inspector is a standalone developer tool that acts as a generic MCP client with a UI — you point it at a server (stdio command or remote URL) and it lets you manually walk through the handshake, list and invoke tools/resources/prompts, and inspect the raw JSON-RPC traffic in both directions. It's the first tool to reach for when a server you're building behaves unexpectedly against a real host, because it isolates whether the problem is in your server's protocol implementation versus in the host application's orchestration logic.

JUNIORQ21. What's a very common first mistake when writing a stdio-based MCP server, related to logging?

ROI: ★★★★★ · Frequency: Very High — a classic "gotcha" question

Writing log or debug output to stdout. In the stdio transport, stdout is the exclusive channel carrying JSON-RPC messages back to the client — a single stray print("debug: got here") line corrupts the message stream and the client will fail to parse it (or worse, silently desynchronize). The fix is mechanical but easy to forget: send all logging to stderr (or to MCP's own logging capability, via notifications/message), never to stdout, in a stdio server.

Interview Gold Point: This is one of the single most common real-world MCP bugs reported by server authors — nearly every "my client can't parse anything from this server" report traces back to an accidental print statement landing on stdout instead of stderr.
JUNIORQ22. Is MCP tied to a particular programming language or model provider?

ROI: ★★★☆☆ · Frequency: Low-Medium

No — that neutrality is the entire point. MCP is a protocol specification, not a library, so a server can be written in Python, TypeScript, Java, Go, or anything else that can speak JSON-RPC over the supported transports, and a client/host can be built independently in a different language, and still interoperate correctly as long as both sides implement the spec. The same is true on the model side: MCP doesn't assume any particular LLM provider, since the protocol only governs how the host talks to servers, not how the host talks to its model.

MIDQ23. Walk through, field by field, what a client actually sends in the initialize request.

ROI: ★★★★☆ · Frequency: Medium-High

The initialize request's params typically include: protocolVersion (the specific MCP version the client speaks), a capabilities object declaring which optional client-side features it supports (e.g., whether it can service sampling requests, whether it supports a roots list), and a clientInfo object (name and version of the implementation, useful for server-side logging/debugging). The server's response mirrors this shape back — its own protocolVersion, its capabilities (tools? resources? prompts? does any of them support list_changed notifications?), and serverInfo — so both sides walk away from one round trip knowing exactly what the other supports.

MIDQ24. What does it mean for capabilities to be negotiated rather than assumed, and why is that a deliberate design choice?

ROI: ★★★★★ · Frequency: High

Negotiation means neither side hardcodes an assumption about what the other supports — the client only signals sampling support if it can actually service a sampling request, and the server only advertises resources.listChanged if it will actually emit that notification. This lets the spec evolve additively: a client built against an older MCP version can still talk to a newer server by simply not declaring (and the server not depending on) capabilities that didn't exist yet, rather than the whole connection failing outright over a version mismatch on a single unused feature.

MIDQ25. What is the client expected to do if the server responds to initialize with a protocol version it doesn't support?

ROI: ★★★★☆ · Frequency: Medium

The spec expects the client to check the server's declared protocolVersion against the versions it knows how to speak; if there's no compatible version, the correct behavior is to fail the connection cleanly (and typically surface a clear error to whoever configured that server) rather than proceed and hope the mismatch doesn't matter. Silently continuing risks the client sending method calls or expecting response shapes the server's actual version doesn't implement, which produces confusing runtime errors far from the actual root cause.

MIDQ26. How does a client discover what capabilities a specific server offers beyond what the capability flags in initialize indicate?

ROI: ★★★★☆ · Frequency: Medium-High

The coarse capabilities object in the initialize response tells the client which primitive categories exist at all (tools, resources, prompts) but not their contents — for that, the client calls the corresponding list method (tools/list, resources/list, prompts/list) after the handshake completes. Only after receiving that list does the client know the actual tool names, schemas, and descriptions it can present to the model, or the actual resource URIs it can offer the host/user.

MIDQ27. What triggers a tools/list_changed notification, and what must a well-behaved client do when it receives one?

ROI: ★★★★☆ · Frequency: Medium

A server sends notifications/tools/list_changed whenever its tool set changes at runtime — a plugin loads dynamically, a feature flag toggles a tool's availability, a dependent system's schema changes and the server updates its own tool definition to match. A well-behaved client treats this as a cache invalidation signal: it re-issues tools/list to refresh its local view before the next model turn, rather than continuing to hand the model a stale tool list that may now include tools the server will reject.

MIDQ28. Explain the message framing used by the stdio transport — how does a reader know where one JSON-RPC message ends and the next begins?

ROI: ★★★☆☆ · Frequency: Medium

Stdio framing uses newline-delimited JSON: each individual JSON-RPC message is serialized on a single line and terminated with a newline character, with no length-prefixing or other framing needed. This is simple to implement in any language (read a line, parse it as JSON) but does impose a constraint worth knowing: the JSON itself must not contain a literal, unescaped newline, which is automatically satisfied by any conformant JSON serializer since newlines inside strings are escaped as \n.

MIDQ29. What is resources/subscribe used for, and how does a client find out when a subscribed resource changes?

ROI: ★★★★☆ · Frequency: Medium

resources/subscribe lets a client register interest in a specific resource URI so it doesn't have to poll resources/read repeatedly to notice changes. When the underlying data changes — a file is edited, a database row is updated — the server sends a notifications/resources/updated notification carrying that URI, and the client can then decide whether to re-read it immediately or lazily, and whether to re-surface it to the model or the user.

MIDQ30. What is a resource template, and why would a server prefer one over a flat list of resources?

ROI: ★★★☆☆ · Frequency: Medium

A resource template is a URI pattern (using RFC 6570 URI template syntax, e.g. file:///{path} or postgres://{schema}/{table}) that describes a parameterized family of resources rather than enumerating every concrete instance. A server backing a large or dynamic dataset — every row in a growing database, every file in a repository that changes constantly — would rather advertise the template once than emit (and keep in sync) a full resources/list of every current instance, letting the client construct concrete URIs to resources/read on demand instead.

MIDQ31. What is the completion capability (completion/complete) and what problem does it solve for prompt or resource-template arguments?

ROI: ★★★★☆ · Frequency: Medium

completion/complete lets a client ask a server "given that the user has typed this much of an argument value, what are plausible completions?" — the same UX problem a shell's tab-completion or an IDE's autocomplete solves. It's most useful for prompt arguments or resource-template variables where the valid values come from the server's own domain data (e.g., completing a partially-typed ticket ID or table name) that the client has no independent way to know.

MIDQ32. What is elicitation, and how is it different from sampling?

ROI: ★★★★★ · Frequency: High — a newer spec feature, increasingly asked

Elicitation lets a server, mid-tool-call, ask the host to collect a specific piece of additional information directly from the end user before the server can finish — for example, a booking tool that needs the user to confirm a date range it wasn't given. Sampling, by contrast, asks the host's LLM to generate a completion on the server's behalf, not the human. Both flow in the "server asks host for something" direction that surprises engineers used to thinking of MCP as one-directional, but elicitation targets the human in the loop while sampling targets the model.

MIDQ33. Describe the shape of a sampling/createMessage request and the key piece of host-side policy around it.

ROI: ★★★★☆ · Frequency: Medium-High

A sampling/createMessage request from a server includes the messages it wants the model to see, optional modelPreferences (hints like "prefer a fast/cheap model" or "prefer the highest-capability model available," since the server doesn't know or control which model the host actually uses), and constraints like maxTokens. The key host-side policy point: a well-implemented host does not auto-forward this to the model — it treats it as requiring explicit approval (a user prompt, or a pre-configured policy) before honoring it, because otherwise any connected server could silently spend the host's model budget or extract completions for its own purposes.

Interview Gold Point: Because modelPreferences are hints, not guarantees, a server should never assume a specific model actually served the request — server-side logic (and any prompt sent via sampling) should be written defensively, tolerant of whichever model the host's policy actually selected.
MIDQ34. What is the "roots" primitive, and when would a host actually declare one to a server?

ROI: ★★★☆☆ · Frequency: Low-Medium

Roots let a host tell a server which directories (or, more generally, which URI-scoped boundaries) it should consider in scope for the current session — for example, a code-editing host declaring the currently open project's folder as a root to a filesystem MCP server, so the server knows not to wander outside it. It's a scoping mechanism supplied by the host at connection time, distinct from authorization (which governs what the server will allow), used mainly for filesystem-shaped or workspace-shaped servers.

MIDQ35. What's the difference between a tool's unstructured content result and a structured output declared via outputSchema?

ROI: ★★★★☆ · Frequency: Medium-High

By default, a tool's result is a list of content blocks (text, image, etc.) meant primarily for a human or the model to read directly. A tool that declares an outputSchema additionally returns a structuredContent object validated against that schema — machine-parseable data a host's orchestration code can consume programmatically (say, to drive a UI widget or feed a downstream computation) without needing to parse or regex the model-facing text representation.

MIDQ36. List the standard tool annotations (readOnlyHint, destructiveHint, idempotentHint, openWorldHint) and explain what each is telling the host.

ROI: ★★★★★ · Frequency: High

readOnlyHint signals the tool doesn't modify any state, so a host can treat it as safe to call more liberally (or auto-approve without confirmation). destructiveHint flags that the tool can cause hard-to-reverse effects (deleting data, sending an email) and should get extra scrutiny or explicit user confirmation. idempotentHint indicates repeated identical calls have the same effect as one call, which matters directly for whether a host's retry logic is safe to use after a timeout. openWorldHint signals the tool interacts with an open-ended external system (the public internet, an unbounded search space) rather than a fixed, enumerable domain, which affects caching and result-freshness assumptions.

MIDQ37. Why is idempotentHint significant specifically for how a host implements retries after a network timeout?

ROI: ★★★★☆ · Frequency: Medium-High

If a tools/call request times out, the host genuinely doesn't know whether the server received and executed it before the timeout or never got it at all. Blindly retrying is safe only if the operation is idempotent — re-running create_ticket("Server down") after an ambiguous timeout could create two duplicate tickets if the original request actually did succeed. A host that respects idempotentHint can safely auto-retry tools marked idempotent and must instead surface an ambiguous-failure state (or require explicit user confirmation before retrying) for tools that aren't.

MIDQ38. What is notifications/progress used for, and what three pieces of information does it typically carry?

ROI: ★★★☆☆ · Frequency: Medium

It's a fire-and-forget notification a server can send during a long-running tool call to report incremental progress rather than leaving the client staring at silence until the final result. It typically carries a progressToken (correlating it to the specific in-flight call, supplied by the client in the original request if it wants progress updates), a progress value, and optionally a total, letting a host render something like a percentage or a step counter to the user while the underlying work continues.

MIDQ39. What must a server do when it receives notifications/cancelled for an in-flight request?

ROI: ★★★☆☆ · Frequency: Medium

It should make a best-effort attempt to stop the underlying work as soon as practical — cancel a downstream database query, abort a long-running computation — and must not send a response for the cancelled request's original id, since the client has already indicated it's no longer waiting for one. Cancellation is advisory rather than guaranteed instantaneous (a server can't always interrupt work mid-flight cleanly), but ignoring it entirely defeats the purpose of giving hosts a way to abandon calls the user no longer cares about.

MIDQ40. What is the _meta field that shows up in various MCP message objects, and what is it for?

ROI: ★★★☆☆ · Frequency: Low-Medium

_meta is a reserved, freeform object that implementations can attach to requests, responses, or other MCP objects to carry information outside the protocol's own defined semantics — for example, a client attaching a trace/correlation identifier for its own observability pipeline, or a progressToken living inside a request's _meta. It exists precisely so that hosts and servers can extend messages with their own metadata without the spec needing to anticipate every possible extension field in advance, and any implementation encountering an unrecognized _meta field should simply ignore it rather than error.

MIDQ41. At a conceptual level, what problem does MCP's OAuth 2.1-based authorization framework solve, and why didn't the original spec need it as urgently?

ROI: ★★★★★ · Frequency: High at senior level

Remote, multi-tenant MCP servers reachable over the network need a real authorization story — who is allowed to connect, and on whose behalf — the same as any other internet-facing API, which a purely local stdio server (trusted by virtue of being spawned directly by the host on the same machine) mostly sidesteps. The authorization spec defines how an MCP client obtains and presents an access token to a remote server using standard OAuth 2.1 flows, rather than each server inventing its own bespoke auth scheme, extending MCP's "reuse boring, standard primitives" philosophy from transport (JSON-RPC) to identity (OAuth).

Interview Gold Point: Notice the asymmetry this creates in practice: a stdio server trusted purely by proximity to the host process can get away with a weaker identity story than a remote server ever could — which is itself a reason for extra caution, not less, before promoting a stdio-only server to a remote deployment without revisiting its auth model.
MIDQ42. What is Dynamic Client Registration, and why does it matter for an MCP client connecting to a server it has never talked to before?

ROI: ★★★☆☆ · Frequency: Medium

Dynamic Client Registration (an existing OAuth extension MCP's auth spec leans on) lets a client register itself with an authorization server programmatically at connection time, rather than requiring a human to manually provision OAuth client credentials for every new MCP server in advance. This matters because MCP is explicitly designed for a client to discover and connect to servers it has never seen before — requiring manual, out-of-band credential provisioning for every new server would defeat that discoverability.

MIDQ43. Why does MCP's authorization flow require PKCE even in flows where the client might otherwise be considered "confidential"?

ROI: ★★★☆☆ · Frequency: Low-Medium

PKCE (Proof Key for Code Exchange) binds the authorization code to the specific client instance that initiated the flow via a locally-generated secret, preventing a stolen authorization code from being redeemed by a different party. MCP mandates it broadly because many MCP clients run as installed desktop apps, CLI tools, or embedded components without a securely stored client secret the way a traditional confidential server-side web app has — treating every client as potentially public and requiring PKCE unconditionally is simpler and safer than trying to classify clients into confidential versus public and applying different rules.

MIDQ44. If a host connects to two MCP servers that each expose a tool literally named search, how should the host handle the collision?

ROI: ★★★★☆ · Frequency: Medium-High

The protocol itself does not deduplicate or namespace tool names across servers — that responsibility sits with the host. In practice, a host typically prefixes or qualifies each tool name with its owning server's identifier before presenting the merged list to the model (e.g., docs_search vs crm_search), and maintains an internal mapping from the qualified name back to the correct (server, original tool name) pair so it can route a model's tool-call request to the right client.

MIDQ45. What problem is the MCP Registry meant to solve for the broader ecosystem?

ROI: ★★★☆☆ · Frequency: Medium

As the number of community- and vendor-built MCP servers grew, there was no canonical, trustworthy place to discover "what servers exist for X" or verify who actually published a given server — the same discovery-and-trust gap package registries (npm, PyPI, Maven Central) solve for code dependencies. An MCP registry provides a searchable catalog of servers with associated metadata (publisher, version, capabilities) so hosts and engineers can find and vet servers without relying purely on word of mouth or an unverified link — though, as with any package registry, listing in it is not by itself a security guarantee about a given server's behavior.

MIDQ46. How would you compare MCP's tool discovery model to a bespoke, hardcoded internal function-calling registry your team already built for one application?

ROI: ★★★★☆ · Frequency: Medium-High

A hardcoded internal registry is fully static at deploy time — the list of available functions and their schemas is baked into the application binary/config, and adding a new one requires a code change and redeploy of that specific application. MCP's tools/list is queried live at connection time (and can change further via list_changed), meaning a new capability added to a server becomes available to every already-deployed host the moment that host reconnects or refreshes, with zero code change on the consuming side — the tradeoff is the added indirection of a schema fetched over the wire rather than known at compile time, which is exactly the discoverability MCP was built to provide.

MIDQ47. A tool call to a remote MCP server returns after 8 seconds when it usually returns in 200ms. What in the MCP spec itself governs this, and what is actually the host's responsibility?

ROI: ★★★★☆ · Frequency: Medium-High

The MCP spec itself does not mandate any timeout — a slow or hung tool call is left entirely to the client/host to police. This means every production host must implement its own timeout policy per call (and ideally per-server, since a Postgres-backed server and a public-web-search server have very different latency profiles), decide what to do when a timeout fires (cancel via notifications/cancelled and surface an error to the model, or retry if the tool is known idempotent), and monitor server-side latency independently, because the protocol gives you no built-in safety net here.

SENIORQ48. Why did a later MCP spec revision remove support for JSON-RPC batch requests, and what does that removal say about how the spec evolves?

ROI: ★★★☆☆ · Frequency: Low-Medium — niche but revealing

JSON-RPC 2.0 natively supports sending an array of requests in one batch and receiving an array of responses, and MCP initially inherited that for free. In practice it added complexity (partial failures inside a batch, ambiguous ordering/cancellation semantics, and streaming responses over Streamable HTTP didn't compose cleanly with batched requests) without a strong enough real-world use case to justify it, so a later revision dropped it. The lesson for reading any protocol's changelog: inheriting a feature from an underlying standard for free doesn't obligate you to keep it if it doesn't earn its complexity once the protocol is actually exercised in production.

Interview Gold Point: This is a good instinct-check question — a candidate who says "batching sounds efficient, why remove it" without weighing how it interacts with streaming and cancellation semantics is reasoning about protocol features in isolation from how they're actually used.
SENIORQ49. You're asked to add a required, non-optional parameter to a widely-used tool's schema. Walk through why that's a breaking change and how you'd actually ship it.

ROI: ★★★★★ · Frequency: High at senior/staff level

Every host currently connected to that server has already cached the old schema and may have models mid-conversation that were told the old, smaller argument set — a model calling the tool the old way will now fail schema validation the moment the change goes live, with no warning to the host beyond a sudden error. The safe path mirrors API versioning discipline generally: add the new parameter as optional with a sensible default first (non-breaking), give existing callers a deprecation window if you eventually want to force it, or ship a new tool name entirely (e.g. create_ticket_v2) for a truly incompatible shape change, and only retire the old one after consumers have measurably migrated off it.

SENIORQ50. What's the architectural difference between a server's implementation version and the MCP protocolVersion it declares, and why do interviewers care that candidates keep them separate?

ROI: ★★★★☆ · Frequency: Medium-High

protocolVersion identifies which revision of the MCP specification itself the endpoint implements (governing what methods, capabilities, and message shapes are legal) — it changes rarely and is negotiated during initialize. The server's own implementation version (its serverInfo.version) tracks that particular server's own release history (bug fixes, new tools, schema tweaks) and can change constantly, independent of the protocol version underneath it. Conflating the two leads to wrong reasoning — assuming a server's frequent version bumps imply protocol incompatibility, or assuming a stable protocol version means the server's actual tool contracts haven't changed.

SENIORQ51. Design a host-side gateway that aggregates 50 internal MCP servers behind a single connection point for every AI application in the company. What are the core design decisions?

ROI: ★★★★★ · Frequency: Very High — a common staff-level system-design prompt

Core decisions: (1) namespacing — every tool/resource/prompt name must be disambiguated by owning server before being exposed onward, since collisions across 50 independently-developed servers are a near-certainty; (2) a central capability/tool catalog so consuming applications don't have to independently discover and connect to 50 servers themselves — the gateway does discovery once and exposes an aggregated, cached view, refreshed on list_changed; (3) per-server credential and auth-scope management, so the gateway (not each application) holds and rotates the actual downstream credentials; (4) per-server circuit breaking and timeout isolation, so one slow or down server doesn't stall calls to the other 49; (5) centralized observability — the gateway is a natural place to emit per-tool-call traces, latency, and cost attribution across every application that shares it. The tradeoff to name explicitly: the gateway becomes a shared dependency and a single point of failure/bottleneck if not built with the same production rigor as the servers it fronts.

SENIORQ52. How would you sandbox an MCP server that needs filesystem or shell access, so that a compromised or buggy server can't affect the rest of the host machine?

ROI: ★★★★★ · Frequency: High

Run the server as its own isolated process with the minimum OS-level privileges it actually needs — a dedicated low-privilege user, a container with a read-only root filesystem and only the specific directories it needs mounted (ideally matching the roots the host has declared to it), network egress restricted to only the downstream systems it legitimately talks to (blocking arbitrary outbound connections closes off a common data-exfiltration path for a compromised server), and resource limits (CPU/memory/file descriptors) so a runaway or malicious process can't starve the host machine. None of this is mandated by the MCP spec itself — it's operational discipline layered on top, exactly the same discipline you'd apply to any other third-party code granted execution rights on a machine you operate.

SENIORQ53. What is the "tool poisoning" / "rug-pull" attack pattern specific to MCP, and why is it hard to defend against with a one-time review?

ROI: ★★★★☆ · Frequency: Medium-High, rising

A server can be reviewed and approved when a host first connects to it, with tool descriptions that look completely benign — but because tool descriptions and schemas are fetched live via tools/list (and can change further via list_changed) rather than being fixed at approval time, a malicious or compromised server can later silently swap in a manipulated description crafted to influence the model's behavior (a form of prompt injection embedded in the tool's own metadata, not its results) after the one-time human review already happened. Defending against it requires either pinning and diffing the exact tool definitions you approved (alerting on any change) rather than trusting updates blindly, or treating every tool description, not just tool results, as untrusted input subject to the same scrutiny as retrieved documents.

Interview Gold Point: Ask specifically whether the candidate distinguishes this from ordinary prompt injection via tool results — tool-poisoning targets the tool definition itself, a strictly earlier and more foundational trust boundary than the data a tool later returns.
SENIORQ54. What is the DNS rebinding concern that was raised against early SSE-based local MCP servers, and how does it work?

ROI: ★★★☆☆ · Frequency: Low-Medium, niche security trivia

A local MCP server bound to localhost for a desktop host implicitly trusts that only local processes can reach it. DNS rebinding defeats that assumption: a malicious webpage in the user's browser causes a DNS name to first resolve to an attacker's server (to pass an initial same-origin-style check) and then re-resolve, after the browser has cached permission, to 127.0.0.1 — letting the malicious page's script make requests that land on the local MCP server as if they were legitimate local traffic. The mitigation is for local HTTP-based servers to validate the Host/Origin header strictly and refuse requests that don't match an expected value, rather than trusting "the request reached my local port" as sufficient proof of legitimacy.

SENIORQ55. Why is "the server returned a plausible-looking result" not sufficient grounds to trust a tool result, even from a server you built yourself?

ROI: ★★★★☆ · Frequency: Medium-High

A tool result flows directly into the model's context the same way retrieved RAG content does, and a "plausible-looking" result can still be wrong (a stale cache, a downstream system silently failing over to degraded data) or actively adversarial if the underlying data source itself accepts untrusted input (a customer-submitted ticket description containing injected instructions, a webpage a search tool retrieved). Building the server yourself only guarantees the protocol layer is correct — it says nothing about the trustworthiness of whatever data source that server is faithfully relaying, which is why treating tool results as untrusted input to the model is a blanket rule, not a case-by-case judgment call.

SENIORQ56. A destructive tool like delete_record or send_email is exposed via MCP. What layered controls would you put around it, beyond the destructiveHint annotation alone?

ROI: ★★★★★ · Frequency: High

The annotation itself is only advisory metadata a well-behaved host can choose to honor — it enforces nothing on its own. Real layering needs: server-side authorization checks that verify the specific requesting end user (not just the host's service credential) is entitled to that specific action, independent of whatever the host claims; a host-side policy that requires explicit human confirmation before executing any tool flagged destructive, surfaced to the actual user in the loop rather than auto-approved; audit logging at the server for every invocation with enough context to reconstruct who/why after the fact; and, where feasible, splitting an overly broad destructive capability into narrower, harder-to-misuse variants (a soft-delete/archive tool with a separate, more heavily gated hard-delete) rather than one generic destructive endpoint.

SENIORQ57. How would you structure integration tests for an MCP server you're shipping, versus unit tests for its underlying business logic?

ROI: ★★★★☆ · Frequency: Medium-High

Unit tests target the actual business logic directly (call the Java method or Python function behind the tool with various inputs, assert on the return value) exactly as you would for any other code, independent of MCP entirely. Integration/contract tests target the protocol surface itself: spin up the server, drive it through a real (or scripted) client — the MCP Inspector or a lightweight test client using the SDK — and assert on the actual JSON-RPC exchange: does tools/list return the schema you expect, does tools/call with valid/invalid arguments behave per the schema, does the server correctly reject a request before initialize completes, does it handle cancellation correctly. The protocol layer needs its own tests precisely because schema-generation-from-code and transport handling are exactly the surfaces a purely unit-tested business-logic suite won't exercise.

SENIORQ58. What does contract testing buy you specifically when a tool's schema is generated automatically from your method signature (as in Spring AI or FastMCP)?

ROI: ★★★☆☆ · Frequency: Medium

Auto-generation guarantees internal consistency (the schema always matches the actual method signature) but says nothing about whether that generated schema is still what every consuming host expects — a seemingly innocuous refactor (renaming a parameter, widening an enum, changing a return type's shape) will regenerate a different schema automatically, silently breaking every host that cached the old one, without your code ever "looking" broken from a unit-test perspective. A contract test that snapshots the generated tools/list output and fails on unintended diffs catches exactly this class of accidental breaking change before it reaches a real host.

SENIORQ59. How would you propagate distributed tracing context across a host → MCP client → MCP server call chain, given that MCP doesn't natively define trace propagation?

ROI: ★★★☆☆ · Frequency: Medium

Since the spec doesn't define a standard tracing header the way HTTP has traceparent, the pragmatic approach is to carry your existing trace/span identifiers inside the _meta field of the request (and read them back out of the corresponding response's _meta on the server side), following whatever your organization's existing tracing convention is (W3C Trace Context values serialized as strings work fine inside a JSON field). This lets a single user-facing request be traced end-to-end — host receives request, forwards as tools/call, server processes and calls its own downstream dependency — the same way you'd already expect for any other internal RPC hop, just carried through a channel (_meta) the spec deliberately left open for exactly this kind of extension.

Interview Gold Point: Point out explicitly that this is a convention your team invents, not something MCP mandates — a strong answer names that gap honestly rather than implying the spec already solved distributed tracing.
SENIORQ60. Why does connecting a dozen MCP servers "just in case" have a cost that isn't obvious from a demo, and how would you actually measure it in production?

ROI: ★★★★☆ · Frequency: Medium-High

Every connected server's tools (and often resources/prompts) get folded into the tool-schema payload sent with every single model call, not just calls that end up using them — so twelve servers each averaging ten tools is 120 tool schemas riding along on every turn of every conversation, inflating prompt tokens (and therefore cost and latency) whether or not the model ever calls any of them. To measure it, instrument token counts attributable specifically to the tool-schema portion of the request separately from the conversation content, and track it per connected server so you can identify which servers are earning their token cost versus which are dead weight that should be disconnected or made available on-demand rather than always-on.

SENIORQ61. What's the tradeoff between exposing many narrow, single-purpose tools versus one flexible, parameterized tool from a single server?

ROI: ★★★★☆ · Frequency: Medium-High

Many narrow tools (get_ticket_status, create_ticket, close_ticket) each carry a small, precise schema and description, making the model's tool-selection problem easier and each tool's blast radius small and easy to reason about individually — but a large number of them inflates the schema payload sent with every call and can still overwhelm the model's selection accuracy past a certain count. One flexible tool (run_ticket_operation(op, params)) reduces schema count but pushes the "which operation, with which shape of params" decision back into free-form reasoning the model is more likely to get subtly wrong, and collapses distinct authorization/audit boundaries into one endpoint. Most production servers land closer to the narrow end, grouped tightly by domain, accepting the token cost as the price of reliability.

SENIORQ62. How should a host decide whether to dispatch multiple tool calls requested by the model in a single turn concurrently or sequentially?

ROI: ★★★★☆ · Frequency: Medium

If the calls are genuinely independent (no call's result is needed as input to another, and they don't contend for the same limited downstream resource in a way that matters), dispatching them concurrently is a pure latency win the protocol doesn't preclude — MCP itself doesn't serialize calls for you, that's an orchestration-layer decision. The host does need to consider: whether the target server(s) can actually handle concurrent load without degrading (a shared server called from many hosts already needs this, but a single host firing five parallel calls at a fragile local stdio server can still overwhelm it), and whether any call has side effects whose ordering the model implicitly assumed even though it issued them "in parallel" from a message-format point of view.

SENIORQ63. What's the actual mechanism (not just the outcome) by which a compromised third-party MCP server could exfiltrate data, given that servers "have no idea" about the host's business logic?

ROI: ★★★★☆ · Frequency: Medium-High

A server doesn't need to understand the host's business logic to exfiltrate data — it only needs to see whatever arguments the model passes into its tool calls, and whatever context it can convince the host to hand it (e.g., via a resource read). If a user's conversation contains sensitive data and the model, in the course of using a tool, passes some of that data as an argument (a customer's PII in a "summarize this record" call, say), a malicious server simply logs or forwards that argument to an external endpoint under its control — no exploit needed, just faithfully doing what any server is allowed to do with the arguments it legitimately receives. This is why vetting what data ever reaches a third-party server's tool arguments matters as much as vetting the server's declared behavior.

SENIORQ64. Compare MCP's approach to authorization with how you'd typically secure an internal REST API, and identify the one place MCP explicitly leaves policy up to you.

ROI: ★★★★☆ · Frequency: Medium-High

Both rely on the same underlying primitives — OAuth 2.1 bearer tokens for authenticating a caller to a remote endpoint — so the transport-level authentication story is genuinely similar to securing an internal REST API. What MCP explicitly does not do, by design, is decide the actual authorization policy: which specific user is allowed to invoke which specific tool with which specific arguments is left entirely to the server implementation, the same way HTTP itself doesn't decide who can call a given REST endpoint. A server that authenticates the caller correctly via OAuth but then executes any requested tool call for any authenticated caller has solved authentication without ever having implemented authorization — a distinction worth being precise about in an interview.

SENIORQ65. How would you migrate an existing in-house tool-calling framework (hardcoded per-application function registries) to MCP without a big-bang rewrite?

ROI: ★★★★★ · Frequency: High at senior/staff level

Start at the boundary, not the center: pick one already-well-understood, already-owned system (say, the ticketing integration) and wrap its existing business logic in a thin MCP server, without touching the logic itself — this is a transport/exposure change, not a rewrite, mirroring the "same business logic, new binding" lesson from wrapping a Java method as both a REST controller and an MCP tool. Run the MCP server alongside the existing hardcoded integration in the consuming application (feature-flagged) until you've validated parity, then cut over that one application's tool-calling path to the MCP client, and repeat system by system. The payoff compounds specifically because each successive system, once wrapped, becomes available to every other application without repeating the integration work — which is also the argument for prioritizing the systems with the most future reuse potential first, not the easiest one.

Interview Gold Point: The "pick the most-reused system first" prioritization is the detail that separates a staff-level migration plan from a merely correct one — it's the same sequencing logic that makes the N+M argument actually materialize sooner rather than later.
SENIORQ66. Should an organization write custom MCP servers for every internal system, or can existing REST/OpenAPI-described APIs be exposed as MCP servers automatically?

ROI: ★★★★☆ · Frequency: Medium-High, increasingly common

Auto-generating an MCP server from an existing OpenAPI spec is a real and increasingly common shortcut — tooling exists to translate OpenAPI operations directly into MCP tools with schemas derived from the API's own request/response shapes, which is attractive because it requires no new server code for APIs that are already well-described. The tradeoff: a mechanically generated tool set inherits the REST API's own tool-selection ergonomics (verbose parameter names, an operation the API author designed for a human developer reading docs, not a model reading a description at inference time), whereas a hand-written MCP server lets you write descriptions and parameter shapes optimized specifically for how a model actually reasons about when to call something. A reasonable default: auto-generate as a fast starting point for internal APIs, but hand-tune the descriptions (and potentially the tool boundaries) for any tool that ends up seeing real production traffic.

SENIORQ67. How would you approach rate limiting for an MCP server that's shared across many host applications and, transitively, many end users?

ROI: ★★★☆☆ · Frequency: Medium

Rate limiting needs to happen at more than one granularity to be meaningful: per calling host/application (so one misbehaving or unusually chatty application can't starve the server for everyone else), and ideally per end user if the server has enough identity information to attribute calls that granularly (propagated via the authorization token, not just the host's own service credential — tying back to the confused-deputy concern). Because MCP itself defines no rate-limiting mechanism, this is implemented the same way you'd rate-limit any other shared internal service — token buckets or sliding windows at the server's own request-handling layer, with a clear, structured error response (not a silent timeout) so calling hosts can distinguish "you're being throttled" from "something is actually broken" and react accordingly (backoff, surface to the user, or queue).

SENIORQ68. What observability signals would you want emitted specifically at the MCP client/server boundary, beyond generic application logging?

ROI: ★★★★☆ · Frequency: Medium

Per-tool-call latency and error rate, broken out by server and by individual tool name (not just "MCP calls" in aggregate, since a slow run_query tool and a fast get_status tool on the same server have very different normal baselines); token cost attributable to tool schemas versus actual tool-call results, since both consume context but only one is unavoidable overhead; connection-level health per server (is the stdio subprocess alive, is the remote HTTP server responding to health checks); and counts of protocol-level events that indicate friction — capability negotiation failures, cancelled calls, list_changed notification frequency (a server whose tool set churns constantly might indicate an unstable integration worth investigating).

SENIORQ69. What's the risk of a host blindly trusting a server's self-reported tool annotations (readOnlyHint, destructiveHint, etc.) without any independent verification?

ROI: ★★★★☆ · Frequency: Medium-High

Annotations are declared by the server itself, with nothing in the protocol verifying they're accurate — a malicious or simply buggy server can mark a genuinely destructive tool as readOnlyHint: true to bypass whatever extra confirmation step a host applies to destructive-flagged tools. A host that treats annotations as advisory-but-unverified for untrusted or unfamiliar servers (applying stricter default confirmation policies to any server outside an explicitly vetted allowlist, regardless of what it claims about its own tools) is meaningfully safer than one that fully trusts every server's self-description.

Interview Gold Point: A good moment to note that MCP's trust model, much like TLS's, secures the channel and the message format — it does not, and cannot, verify that what a participant says about itself is true.
SENIORQ70. How does the "openWorldHint" annotation affect caching decisions a host or an intermediate layer might otherwise want to make?

ROI: ★★★☆☆ · Frequency: Medium

A tool interacting with a closed, enumerable domain (say, looking up one of a fixed set of internal product SKUs) is a reasonable candidate for result caching, since the space of possible answers is bounded and mostly stable. A tool marked openWorldHint (a web search, a query against an unbounded or rapidly changing external system) signals that caching identical-looking calls is unsafe to assume correct, because the "same" query against an open-ended domain can legitimately return different, equally valid results moment to moment — a caching layer that ignores this hint risks serving a model stale or simply wrong information under the guise of an optimization.

SENIORQ71. What's the significance of JSON Schema draft version compatibility when a tool's schema needs to work across multiple model providers?

ROI: ★★★☆☆ · Frequency: Low-Medium

Not every model provider's tool-calling implementation supports the full JSON Schema specification identically — some support only a practical subset (basic types, enums, required arrays) and choke on or silently ignore more advanced constructs (complex conditionals, certain string format keywords) depending on which draft and which subset their own tool-calling layer was built against. A server whose generated schemas rely on advanced JSON Schema features that work fine against one provider's model can produce confusing failures or degraded tool-selection accuracy against another — worth explicitly testing a server's actual generated schemas against every model provider a host might realistically route through, rather than assuming schema validity in the abstract implies compatibility everywhere.

SENIORQ72. A host wants to expose only a subset of a connected server's tools to the model for a given conversation (not all of them). Does MCP support this natively, or is it the host's problem?

ROI: ★★★☆☆ · Frequency: Medium

MCP's tools/list simply returns everything the server is willing to expose to that client session — there's no protocol-level mechanism for the client to ask for a filtered subset per conversation. Selective exposure (only show the model tools relevant to the current task, to keep the token cost down and reduce tool-selection error) is entirely an orchestration-layer decision the host makes after receiving the full list — filtering, ranking, or dynamically choosing which subset of the aggregated tool list to actually pass to a given ChatClient call, based on the host's own logic (the conversation's topic, a per-session policy, etc.).

SENIORQ73. How would you reason about whether a given MCP server needs to be stateful across calls (maintaining session-scoped memory) versus fully stateless?

ROI: ★★★☆☆ · Frequency: Medium

Statelessness (each tools/call is handled independently, with any needed context passed explicitly as arguments) is simpler to reason about, easier to scale horizontally, and safer under retries — the same argument that favors stateless services generally. A server does legitimately need session-scoped state when the underlying capability is inherently stateful — a database transaction spanning multiple tool calls, a multi-step wizard-like interaction the server itself is tracking progress through — but that state should be tied to the MCP session lifecycle explicitly (cleaned up on disconnect) rather than assumed to persist indefinitely, and a server author should default to stateless unless the capability genuinely requires otherwise.

SENIORQ74. What single design property of MCP most directly enables a tool to be migrated from a local Java method to a remote server (or vice versa) without changing any calling code?

ROI: ★★★★★ · Frequency: High

The stability of the tool-calling abstraction boundary — a ToolCallback (or equivalent construct in another SDK) — as the single contract the host's orchestration code depends on, regardless of whether the concrete implementation behind it is a three-line local method or a network call to an MCP server. Because both a local @Tool method and an MCP-provided tool are converted into the same callback shape before reaching the ChatClient call, the migration is purely a wiring change (swap what constructs the callback) rather than a change to any code that consumes it — the exact same value an interface/implementation split provides anywhere else in software.

Interview Gold Point: Tie this back explicitly to dependency inversion — the host depends on an abstraction (the callback contract), and both the local method and the remote MCP server depend on that same abstraction, not on each other, which is exactly what makes the swap invisible to calling code.
SENIORQ75. Why is "the model never talks to the MCP server directly" a security-relevant property, not just an architectural detail?

ROI: ★★★★☆ · Frequency: Medium-High

Because every tool-call request the model produces still passes through the host's own orchestration layer before reaching a server, the host retains a mandatory interception point to apply policy — authorization checks, confirmation prompts for destructive actions, rate limiting, logging — on every single call, no matter how many servers are connected or what a given server's own trustworthiness looks like. If the model could reach servers directly, none of that host-mediated policy enforcement would have anywhere to attach; the architecture's insistence on host-mediated calls is precisely what makes centralized security controls possible at all.

SENIORQ76. How would you evaluate whether an MCP server you didn't build is safe to connect to production, beyond just reading its source code once?

ROI: ★★★★☆ · Frequency: Medium-High

A one-time source read establishes a baseline but doesn't protect against the tool-poisoning/rug-pull risk (the server changing its behavior or tool descriptions after approval) or supply-chain compromise of a dependency the server itself pulls in later. A more durable process: pin the server to a specific, hash-verified version/build rather than "latest," diff its declared tools/schemas on every version bump before allowing an upgrade, run it with the sandboxing and least-privilege controls described earlier regardless of how trustworthy it looks, and monitor its actual runtime behavior (unexpected network egress, anomalous latency, anomalous argument patterns in what it's being called with) rather than trusting the one-time review to hold indefinitely.

SENIORQ77. What tradeoff is a team accepting when they choose to expose a single generic MCP tool (e.g. call_internal_api(endpoint, method, body)) that proxies arbitrary calls to an internal API surface, instead of purpose-built tools per operation?

ROI: ★★★★☆ · Frequency: Medium

The generic proxy tool is fast to ship (one tool covers an entire API surface with no per-operation server code) but collapses every distinct operation's authorization, description quality, and blast radius into a single undifferentiated capability — the model has to correctly reason, from a generic description alone, about which endpoint/method/body shape is appropriate for the current task, with far less guidance than a purpose-built get_customer_order(order_id) tool would provide, and a host has no way to apply different confirmation policy to a read operation versus a destructive one funneled through the same generic tool. It's a reasonable stopgap for rapid prototyping, but it trades away almost everything (tool-selection reliability, fine-grained authorization, meaningful destructiveHint annotations) that purpose-built tools were designed to provide.

STAFFQ78. You're asked to set the versioning and deprecation policy for every internal MCP server your organization operates. What would that policy actually contain?

ROI: ★★★★★ · Frequency: High at staff level

At minimum: a rule that any change to a tool's required parameters, return shape, or observable side effects is treated as a breaking change requiring either a new tool name or a formally announced deprecation window (with a fixed sunset date communicated to known consumers, not silently applied); a distinction, enforced in review, between additive changes (new optional parameter, new tool added to an existing server) which can ship without notice, and anything else; a requirement that every server publish (in its own description or an accompanying registry entry) which protocolVersion range and which of its own implementation versions are currently supported, so consuming hosts can make informed upgrade decisions; and an owning-team accountability model — the team operating a given server is responsible for honoring this policy for that server, the same way any internal API's owning team is responsible for its own compatibility contract. The organizational payoff of writing this down explicitly, rather than leaving it to each team's judgment, is that consuming hosts can build automation (schema diffing, contract tests) against a policy that's actually guaranteed rather than merely hoped for.

STAFFQ79. A skeptical staff engineer argues: "MCP just adds a network hop and an extra abstraction layer for something we could call directly." Steelman their position, then make the actual counter-argument.

ROI: ★★★★★ · Frequency: Very High — the single most common staff pushback question

The steelman is real and shouldn't be dismissed: for a single application with a small, stable, fully-owned set of tools, MCP genuinely does add latency (a network hop and JSON-RPC serialization versus an in-process method call), operational surface (a server to deploy, version, and monitor separately), and cognitive overhead (engineers now need to understand a protocol, not just call a function) — for that narrow case, direct integration is legitimately simpler and faster. The counter-argument is about where the organization actually sits on the N-applications-by-M-systems curve: the moment a second AI application needs any of the same capabilities, or a system's owning team wants to expose it to teams they don't control, the combinatorial cost of N direct integrations outgrows the fixed cost of standardizing once — and most organizations building more than one AI application cross that threshold quickly, whether or not they've noticed. The honest answer isn't "MCP is always better," it's "the case for MCP strengthens directly with the number of application-to-system pairings you actually have or expect to have."

Interview Gold Point: A candidate who only gives the pro-MCP argument without engaging the steelman honestly is missing the exact kind of nuanced tradeoff reasoning staff-level system-design interviews are designed to surface.
STAFFQ80. How would you decide, for a specific internal capability, whether it should be exposed as an MCP tool at all, versus kept as an internal method only the owning application calls?

ROI: ★★★★☆ · Frequency: Medium-High

The deciding question isn't "can this be a tool" (almost anything can) but "does more than one AI-application-shaped consumer plausibly need this, now or in a reasonably foreseeable future, and is the owning team willing to operate it with the reliability and versioning discipline a shared dependency demands." A capability that's genuinely single-consumer and unlikely to stay that way is better left as a local method or a plain internal service call — turning it into an MCP server prematurely adds an operational and versioning surface (health checks, a compatibility contract, monitoring) that only pays for itself once real reuse materializes, and a team should be honest that "we might need this elsewhere someday" is a weak justification on its own without a second concrete consumer already in view.

STAFFQ81. Describe how you'd design the failure-handling contract between a host and a critical, shared MCP server so that the server's downtime degrades gracefully instead of taking down every dependent application.

ROI: ★★★★★ · Frequency: High

Per-server circuit breaking at the host's orchestration layer, so repeated failures/timeouts against one server stop being retried immediately and instead fail fast (returning a clear error the model can react to — "the ticketing system is currently unavailable" — rather than hanging the whole conversation turn); a fallback behavior defined per tool where one makes sense (serving a cached last-known-good result for a read-only tool, versus no sensible fallback for a genuinely destructive action); health-check-driven routing if multiple redundant instances of the server exist; and treating the server's own SLA and on-call ownership as a first-class part of the dependency, the same as you would for any other shared internal service a critical path depends on — a shared MCP server without an operational ownership model is a single point of failure wearing a protocol-compliant costume.

STAFFQ82. What organizational failure mode does a strong MCP adoption actually prevent, that a technically-correct-but-organizationally-naive rollout would not?

ROI: ★★★★☆ · Frequency: Medium-High

The technical protocol alone doesn't prevent the "everyone builds their own MCP server for the same underlying system" failure mode — without an organizational decision about who owns building and operating the canonical server for each system (CRM, ticketing, internal search), teams will independently re-implement competing MCP servers for the same capability, recreating the exact N×M duplication problem MCP was adopted to eliminate, just now expressed as multiple non-canonical MCP servers instead of multiple non-canonical direct integrations. Preventing this requires a deliberate governance decision — the team that owns a system also owns the one sanctioned MCP server exposing it, published somewhere discoverable (an internal registry) — layered on top of the protocol, not implied by adopting the protocol itself.

STAFFQ83. How would you reconcile MCP's "servers know nothing about the host's business logic" design principle with a legitimate need for a tool's behavior to differ by which application is calling it (e.g., different default page sizes, different formatting)?

ROI: ★★★☆☆ · Frequency: Medium

The cleanest reconciliation is to push that variation into parameters the calling host supplies explicitly on each call (an argument controlling verbosity or page size) rather than the server trying to infer or special-case behavior based on which host it thinks is calling — the moment a server starts branching its logic on "which application is this," it has broken the principle that made it independently reusable in the first place, and re-coupled itself to specific consumers exactly like the bespoke integrations MCP was meant to replace. Where genuinely host-specific configuration is unavoidable, it belongs in how that host is configured to call the tool (default arguments the host's orchestration layer supplies), not in server-side logic that inspects caller identity to change behavior.

STAFFQ84. You're evaluating whether to adopt a third-party MCP server that solves a real business need but comes from an unfamiliar vendor with no long operating history. What's your actual decision framework, beyond "read the code once"?

ROI: ★★★★☆ · Frequency: Medium-High

Treat it exactly like onboarding any other third-party dependency with execution and data-access rights, using the same procurement/security diligence you'd apply to a new SaaS vendor with API access to sensitive systems — provenance and maintenance signal (is it actively maintained, does it have a real security disclosure process), the actual blast radius of what it's being granted (scope its access as narrowly as the use case allows regardless of how much you trust the vendor, per least-privilege), a sandboxed trial period with monitoring before it touches production data, and an explicit answer to "what's our rollback plan if this vendor's server is later found compromised or simply abandoned" before you build anything hard-to-unwind on top of it. The MCP-specific addition to that general framework is watching for the tool-poisoning pattern — pin and diff its tool definitions across versions rather than trusting a point-in-time review to hold.

STAFFQ85. How does the existence of MCP change how you'd structure a team responsible for "AI platform" work at a company with many product teams building AI features?

ROI: ★★★★☆ · Frequency: Medium

It creates a natural split between two responsibilities that used to be entangled: a platform team can own the host-side concerns that benefit every AI application (the orchestration framework, the MCP client infrastructure, cross-cutting policy like the confirmation-before-destructive-tool-call pattern, observability), while individual system-owning teams own the MCP servers exposing their own domain (a distinct, much smaller scope of work than building a whole application's AI integration). This is a meaningfully different shape than a world without MCP, where the platform team would otherwise be pulled into building or reviewing bespoke point-to-point integration code for every system every product team's AI feature happens to need, since there was no clean interface for other teams to expose their own systems' capabilities independently.

STAFFQ86. A production incident: a shared MCP server starts returning malformed JSON-RPC responses intermittently under load, and multiple downstream AI applications start failing in different, confusing ways. How do you reason about where to look first, and what does this incident suggest about your architecture in hindsight?

ROI: ★★★★★ · Frequency: High — an incident-review-style staff question

First isolate whether it's the server's own logic degrading under load (a downstream dependency it calls timing out and the server not handling that gracefully before serializing a response) versus a transport-layer issue (partial writes on the stdio stream, or a proxy/load balancer in front of a Streamable HTTP deployment mishandling the streaming response shape under concurrent load) — the MCP Inspector or direct traffic capture against the server in isolation, replicated under synthetic load, separates these quickly. In hindsight, "multiple downstream applications fail in different confusing ways" is itself the signal worth internalizing: a shared server without per-consuming-application circuit breaking and without contract-level response validation on the client side (rejecting malformed responses explicitly and surfacing a clear "upstream server error," rather than each host's parsing code failing idiosyncratically) turns one server's degradation into an incident shaped differently for every team depending on it, which is exactly the operational cost of a shared dependency that the N+M efficiency argument doesn't mention up front.

Interview Gold Point: The strongest answers name the missing safety net explicitly — response validation at the client and per-application circuit breaking — rather than just diagnosing this one incident and stopping there.
STAFFQ87. How would you decide, as a staff engineer, whether your organization should build a custom internal successor/fork to MCP rather than adopting the open spec as-is?

ROI: ★★★☆☆ · Frequency: Low-Medium

This is very rarely the right call, and the bar should be set high on purpose: you'd only consider it if you had a requirement genuinely incompatible with the open spec's design (not merely "our first implementation of the spec was awkward," which is a solvable engineering problem, not a spec problem) and were willing to give up every ecosystem benefit that comes from standardization — every community and vendor MCP server, every host application built against the standard client SDKs, all of it becomes unusable or requires an adapter layer the moment you fork. In practice, almost every "we need something MCP doesn't do" situation is better solved by using MCP's own extension points (the _meta field, capability negotiation for optional features) or by contributing the missing capability back to the open spec's evolution, since the entire value proposition this chapter has been building toward — N+M instead of N×M — depends on staying on the shared standard rather than becoming your own bespoke island again.

STAFFQ88. What's the deepest reason MCP standardizes the wire contract but deliberately refuses to standardize authorization policy, and why would baking in a full authz framework have likely hurt adoption?

ROI: ★★★★☆ · Frequency: Medium-High

Authorization policy is inherently organization-specific — what "this user is allowed to call this tool" means depends on each company's own identity system, role model, and compliance requirements, none of which a protocol spec can anticipate or should try to own without either being too rigid for most adopters or so configurable it stops being a simple, learnable standard. A protocol that tried to also mandate a specific authorization model would have forced every adopter to either fit their existing identity infrastructure awkwardly into the spec's assumptions or fork/extend it immediately, undermining the exact "everyone speaks the same thing" property that makes standardization valuable in the first place — the same reason HTTP defines how a request is structured but not who's allowed to call which endpoint, leaving that correctly to the application layer.

STAFFQ89. You need to make the case, quantitatively, for why a company with 6 AI applications and 15 internal systems should invest in MCP servers now rather than later. What's the actual argument, and what's the honest caveat?

ROI: ★★★★★ · Frequency: High at staff level

At 6 applications and 15 systems, a fully-connected direct-integration world is bounded by up to 90 point-to-point integrations if every application eventually needs every system, versus 6 + 15 = 21 total integration efforts (one client-side integration per application, one server-side integration per system) under a shared protocol — and critically, every new application added afterward costs 1 more integration effort under MCP versus up to 15 more direct integrations without it, so the gap only widens as the company grows. The honest caveat: this argument assumes real, materializing reuse across applications and systems — if in practice each application only ever needs 2-3 systems and that never changes, the realized savings are much smaller than the theoretical N×M-versus-N+M ceiling suggests, so the pitch should be grounded in your organization's actual and expected reuse pattern, not the worst-case combinatorial bound alone.

Interview Gold Point: A candidate who leads with the raw N×M-vs-N+M formula without immediately caveating it against actual observed reuse is reciting the argument from earlier in the chapter, not applying it — watch for whether they self-correct to the honest caveat unprompted.
STAFFQ90. How would you audit, across an entire organization, whether MCP adoption is actually delivering its intended benefit versus having become a compliance checkbox with servers nobody reuses?

ROI: ★★★★☆ · Frequency: Medium

Look past "how many MCP servers exist" (a vanity metric that a compliance-driven rollout will happily inflate) to "how many distinct consuming applications does each server actually have," "how often does a newly built application reuse an existing server versus needing a new one built," and "how many servers exist that have exactly one consumer" (a strong signal of unrealized reuse potential, or of a server that should never have been split out from its one consumer in the first place). An organization where most servers have exactly one consumer has paid MCP's operational tax (versioning discipline, a server to run, a registry entry to maintain) without collecting its actual payoff, which is a legitimate finding to bring back to leadership rather than assuming adoption itself equals success.

STAFFQ91. What's the strongest argument against over-standardizing too early — i.e., building a dozen MCP servers for internal systems before any second AI application actually exists to consume them?

ROI: ★★★☆☆ · Frequency: Medium

Building the server side of the protocol ahead of real demand means guessing at the tool boundaries, descriptions, and schema shapes a not-yet-built second consumer will actually need, with no real usage feedback to correct course — exactly the same risk as building a public API ahead of any real external consumer, where the first correction typically comes only after a consumer arrives and reveals the original design's wrong assumptions. It's usually better sequencing to let a second genuine consumer's needs pull the first server into existence (or at minimum, into its production-hardened form) rather than pushing servers out speculatively — the N+M efficiency argument is real, but it's an argument for building the second and later servers cheaply, not for front-loading server-building before the M side of the equation has any actual N greater than one.

STAFFQ92. Two teams both want to expose "customer data" as an MCP server, with slightly different views of what fields matter. How would you resolve this as the staff engineer arbitrating the decision?

ROI: ★★★★☆ · Frequency: Medium

Resist the instinct to let both ship separate servers "for now" — that's the exact non-canonical-duplication failure mode adoption governance is supposed to prevent, and it compounds the moment a third team needs customer data and has to guess which of two servers is authoritative. The right resolution is establishing a single canonical customer-data server, owned by whichever team is closer to the actual system of record (not whichever team asked first), designed with both consuming teams' actual field requirements gathered upfront as input to its tool/resource design — and if the two use cases are different enough to genuinely warrant different shapes, that's better solved as two distinct tools or resource views on one canonically-owned server than as two independently-operated servers with drifting data semantics for what should be the same underlying entity.

STAFFQ93. What's the long-term risk of MCP's own ecosystem success — many high-quality, widely-adopted third-party servers — and how should a mature organization's dependency policy account for it?

ROI: ★★★★☆ · Frequency: Medium-High

Ecosystem success means it becomes tempting to depend on external, vendor- or community-maintained MCP servers for increasingly business-critical capabilities, which reintroduces classic third-party dependency risk (a maintainer abandoning a widely-used server, a vendor changing pricing or terms, a supply-chain compromise in a popular package) at exactly the moment organizations are least prepared for it because "it's just an MCP server, not really our system" feels lower-stakes than it is. A mature policy treats any externally-maintained MCP server powering a production path with the same vendor-risk diligence as any other critical third-party dependency — contingency plans for the maintainer disappearing, pinned and audited versions, and an honest inventory of which production capabilities actually depend on servers the organization doesn't control.

STAFFQ94. If you were asked to bet on how MCP itself will need to evolve based on where its current design leaves the most friction, what would you point to and why?

ROI: ★★★★☆ · Frequency: Medium

The areas this chapter has already flagged as "still maturing" are the honest answer, not speculation dressed as certainty: authorization and identity propagation at scale (today's OAuth-based framework is a solid start but per-organization identity federation across many servers is still largely bespoke), discovery and trust at scale as the registry ecosystem matures (moving from "a searchable catalog exists" to verified, reputationally-scored publishers, the way established package registries eventually grew), and tooling for the versioning/compatibility discipline this chapter argues for (automated schema-diffing and compatibility checking as a standard part of the server-authoring toolchain, rather than a discipline each team has to invent for itself). None of these are flaws in the current spec so much as the natural next layer any successful infrastructure standard grows once real-world scale exposes where hand-waving is currently doing the work that tooling and convention should.

STAFFQ95. In one sentence each, articulate what MCP is not trying to be, and why an interviewer asking a staff candidate this question is really testing for architectural judgment, not protocol trivia.

ROI: ★★★★★ · Frequency: High — a strong closing question in staff loops

MCP is not an authorization framework, not an agent-orchestration framework, not a guarantee of server trustworthiness, not a caching layer, and not a replacement for the model's own tool-calling mechanism — it is narrowly a wire contract for discovering and invoking tools, resources, and prompts across a host/client/server boundary. An interviewer asking this is testing whether a candidate understands that a protocol's power comes precisely from what it deliberately leaves to the layers above and below it — the same discipline that makes HTTP, JSON-RPC, or TCP successful standards — because an engineer who thinks MCP alone solves security, orchestration, or reliability will make exactly the wrong architectural bets when those concerns inevitably surface in a real system built on top of it.

Interview Gold Point: This is a strong chapter-closing question precisely because it forces a candidate to state the protocol's boundaries crisply — naming which sibling layer (tool selection, agent orchestration, multi-agent coordination) actually owns each of those concerns is itself worth volunteering if the interviewer presses further.

16. SUMMARY

  • MCP exists to solve the N×M integration problem: without a shared protocol, connecting many AI applications to many tool-providing systems requires a combinatorial explosion of bespoke integrations; MCP reduces this to roughly N + M by standardizing the contract both sides implement once.
  • The protocol defines three roles — host, client, server — and three capability primitives — tools (model-invoked), resources (host/user-attached context), and prompts (user-selected templates) — each with a distinct decision-maker for when it is used.
  • The full lifecycle (transport connect, initialize handshake, discovery, invocation, change notifications, teardown) matters for debugging real failures, and the model itself never talks to an MCP server directly — only the host's orchestration layer does.
  • In Spring AI, MCP-provided tools and locally defined @Tool methods both resolve to the same ToolCallback abstraction consumed by ChatClient, and Spring Boot applications can act as MCP clients, MCP servers, or both.
  • Production deployments should favor remote, pooled, independently-owned MCP servers over ad hoc local stdio processes, and must budget for the real latency and token-cost overhead the protocol adds compared to a purely local tool call.
  • MCP's security model deliberately leaves authorization policy, credential scoping, and trust decisions about third-party servers to the host and server implementers — treat every MCP server connection with the same rigor as adding a new privileged dependency, because confused-deputy risk and prompt injection via tool results are real, not hypothetical, attack surfaces.
