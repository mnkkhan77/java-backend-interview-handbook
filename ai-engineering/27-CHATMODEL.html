CHAPTER 27 — CHATMODEL

Volume 2 — Spring AI · Chapter 2 of 15

The previous chapter drew the shape of Spring AI as a whole — the portable, provider-agnostic layer that keeps your business logic from being welded to one vendor's SDK. This chapter opens the box and looks at the single interface that entire idea is built on: ChatModel. Everything you will do in the rest of this volume — the fluent ChatClient API, Advisors, memory, tool calling, structured output — is a layer of convenience sitting on top of this one contract between your Java code and a large language model. Understand ChatModel deeply now, and every chapter after this one will read as "a nicer way to call the thing you already understand," instead of new magic.

1. MOTIVATION

Somewhere in nearly every Spring AI codebase you will ever work on, there is a moment where a request comes in, gets turned into a prompt, and something has to actually go talk to a model. That "something" needs to be a single, stable Java type — an interface you can inject, mock, wrap, and swap — or your application ends up hard-wired to whichever provider's SDK you happened to reach for on day one. ChatModel is that type. It is the thinnest possible seam between "my application" and "a large language model," and getting comfortable with it is the single highest-leverage thing you can do before moving on to the more ergonomic APIs later in this volume.

Here is why this specific interface deserves its own chapter rather than a paragraph inside "Spring AI Architecture." As a backend engineer, you have almost certainly built an abstraction over a payment gateway, a messaging system, or a search index — a PaymentGateway interface with a Stripe implementation and a mock implementation for tests. ChatModel is that exact pattern, applied to language models, but with a twist that makes it more consequential than most integration interfaces you have written: the "provider" underneath it is not a deterministic service with a fixed response schema. It is a probabilistic text generator whose output shape, latency, and cost characteristics differ meaningfully between OpenAI, Anthropic, Google, Azure, Ollama, and every other backend Spring AI supports. Designing a single Java contract that is honest about that variability, while still hiding the vendor-specific plumbing, is a genuinely hard interface-design problem — and Spring AI's answer to it is worth studying closely, because the same tension (unify without lying about the differences) recurs constantly in AI Engineering.

Practically, you need this chapter because almost every advanced feature later in this book — retrieval-augmented generation, tool calling, agentic loops, memory-backed conversations — is implemented, under the hood, as code that constructs a Prompt, calls a ChatModel, and inspects a ChatResponse. When something breaks three layers up in an Advisor chain or a RAG pipeline, the fastest way to debug it is to drop back down to this exact interface and ask: what prompt actually went out, and what response actually came back? If you only ever learn the fluent ChatClient sugar, you will not have that debugging reflex. This chapter builds it.

2. HISTORICAL BACKGROUND

Before frameworks like Spring AI existed, calling a large language model from a Java backend meant one of two things, and both were painful in their own way.

2.1 The Raw HTTP Client Era

The first approach — and still the one many teams started with in 2023, when OpenAI's chat completions API became the dominant integration point — was to write a plain HTTP client by hand: a RestTemplate or WebClient bean, a hand-rolled DTO matching OpenAI's JSON request/response schema (messages, role, content, temperature, max_tokens), manual JSON serialization with Jackson, manual handling of streaming via server-sent events, and manual retry/backoff logic for rate limits. This worked, and for a single-provider prototype it was even reasonable. The problem surfaced the moment a team needed to do any of the following: switch providers because of cost or latency, run the same business logic against two providers for an A/B test, add a local model (via Ollama) for a privacy-sensitive path, or write a unit test that did not require a live network call. Every one of those needs meant touching business logic that had no business knowing what a "chat completion" JSON payload looked like.

2.2 Provider SDKs, and Why They Weren't Enough

The natural next step was official or community Java SDKs per provider (an OpenAI Java client, an Anthropic Java client, and so on). These removed the hand-rolled JSON mapping, but they did not remove the coupling problem — each SDK has its own request builder shape, its own response types, its own way of representing a conversation, its own streaming abstraction (some use callbacks, some use Iterator, some integrate with reactive types and some don't). A service class built against the OpenAI Java SDK's ChatCompletionCreateParams is just as locked in as one built against raw HTTP — the lock-in moved, it did not disappear. This is the same lesson the "Historical Background" chapter on intelligence itself taught about bottlenecks: they relocate, they rarely vanish on their own.

2.3 The Framework Answer: A Vendor-Neutral Port

Spring AI's answer follows a pattern Spring engineers already trust deeply: define a narrow, stable interface (a "port," in hexagonal-architecture language) that represents the capability your application actually needs — "generate a response given a conversation" — and let framework-provided adapters translate that narrow interface into whatever shape each provider's API demands. ChatModel is that port. OpenAiChatModel, AnthropicChatModel, OllamaChatModel, VertexAiGeminiChatModel, and the rest are the adapters. This is precisely the same shape as Spring Data's Repository abstraction sitting in front of JPA, MongoDB, and Redis implementations — you have already internalized this pattern from a different corner of the framework, which is exactly why Spring AI chose it rather than inventing something novel.

EraWhat Business Logic Depended OnCost of Switching Providers

Why this history matters to you: the value of ChatModel is not "it is more convenient to type." It is that it moves the vendor-coupling cost out of your business logic and into a single, small, intentionally isolated place — the same architectural instinct behind every abstraction you have ever put in front of a database driver or a cloud SDK.

3. PROBLEM STATEMENT

Reduced to its essence, ChatModel exists to solve one precise engineering problem:

Define a single, provider-agnostic Java contract for "send a conversation, get back a generated response," that is expressive enough to carry provider-specific tuning (temperature, model name, max tokens) without forcing every caller to know which provider is underneath.

Unpack the tension inside that sentence, because it is the whole design problem. On one side, you want uniformity: a UserService that summarizes support tickets should not care whether the underlying model is GPT-4o, Claude, or a locally hosted Llama model — it should depend on one Java type. On the other side, you cannot pretend the providers are identical: OpenAI supports a presence_penalty parameter Anthropic does not expose the same way; Anthropic has a distinct notion of a top-level system message rather than treating it as just another message in the list; some providers support native structured-output enforcement, others do not. A design that ignores these differences either lies to the caller (silently dropping parameters) or collapses into a "lowest common denominator" so thin it is useless for real tuning.

Spring AI resolves this tension with a layered options model: a shared, provider-neutral ChatOptions contract for the handful of parameters virtually every provider supports (model name, temperature, max tokens, stop sequences), plus provider-specific option classes (OpenAiChatOptions, AnthropicChatOptions, and so on) that extend the neutral contract with vendor-specific knobs. This means your code can be 90% portable and still reach for the remaining 10% of provider-specific control when a feature genuinely requires it — you opt into coupling explicitly, rather than having it forced on you implicitly by using the wrong abstraction level from the start.

4. THEORY

4.1 The Core Mental Model: A Pure, Stateless Function

The cleanest way to hold ChatModel in your head is as a stateless, side-effect-free (from your application's point of view) function with the following shape: 

ChatResponse call(Prompt prompt)

A Prompt goes in; a ChatResponse comes out. There is no session, no hidden conversational memory inside the ChatModel itself — every previous turn of a conversation the model needs to "remember" must be explicitly included as messages inside the Prompt you pass in on every single call. This is a deliberate and important design choice, and it mirrors something you already know from HTTP: a well-designed REST endpoint is stateless, and the caller carries whatever context is needed on each request. ChatModel is stateless in exactly that sense. Conversational "memory" — remembering what the user said three turns ago — is a concern that belongs one layer up, in Advisors and the ChatClient (covered in the next two chapters), never inside ChatModel itself.

4.2 The Four Building-Block Types

Four types make up almost everything you need to understand about the ChatModel contract:

TypeWhat It RepresentsAnalogy
Message (and its subtypes SystemMessage, UserMessage, AssistantMessage, ToolResponseMessage)One turn in a conversation, tagged with a roleOne line of dialogue in a transcript, labeled with who said it
PromptAn ordered list of Messages plus optional ChatOptions for this specific callThe entire transcript-so-far you hand the model, plus your instructions for how to respond (tone, length, model choice)
ChatResponseThe model's reply, wrapped with metadata (token usage, finish reason)An HTTP response object: a body plus headers describing what happened
GenerationOne candidate reply inside a ChatResponse (usually there is exactly one)One of possibly several draft answers a model could have produced for the same prompt

Notice the asymmetry: a Prompt holds a list of messages (the whole conversation so far), but a ChatResponse holds a list of Generations (possible replies to that one prompt), each of which internally wraps a single new AssistantMessage. Most of the time you will only ever look at the first generation — multiple generations exist to support providers that can return several candidate completions for the same request (useful for "generate 3 options and let the user pick" style features) — but the type shape is honest about that possibility rather than hiding it.

4.3 Messages Have Roles, and Roles Are Not Decoration

The distinction between SystemMessage, UserMessage, and AssistantMessage is not a labeling convenience — it materially changes how the underlying model weighs the content. A SystemMessage carries the standing instructions for the whole conversation ("you are a customer support assistant for Acme Corp; never discuss pricing for competitors"); a UserMessage carries what the human actually said; an AssistantMessage carries what the model said previously, fed back in so the model has continuity across turns. Getting this role assignment wrong — for instance, jamming your system instructions into a UserMessage — does not throw a compile error, and it may even appear to work in casual testing, but it systematically weakens how reliably the model follows your standing instructions once real, varied user input starts competing for its attention. This is the same "prediction as a proxy for understanding" mechanism explored in the Transformers and foundational chapters: the model has learned, from its training data, different statistical expectations for text tagged as system guidance versus text tagged as user chatter, and role assignment is how you invoke that learned distinction correctly.

5. INTERNAL WORKING

Walk through exactly what happens, step by step, between your code calling chatModel.call(prompt) and a ChatResponse landing back in your hands. This is the sequence every debugging session eventually reduces to, so it is worth internalizing precisely.

  1. Prompt assembly. Your application code builds a Prompt — typically a SystemMessage plus one or more UserMessage/AssistantMessage pairs representing history, plus an optional ChatOptions instance for this call (model name override, temperature, max tokens).
  2. Dispatch to the concrete implementation. The ChatModel bean injected into your service is, at runtime, a concrete class like OpenAiChatModel or AnthropicChatModel, auto-configured by Spring Boot based on which Spring AI starter is on the classpath and which provider properties are set. Your code never names this concrete class — it depends only on the ChatModel interface, exactly the same discipline as coding against List instead of ArrayList.
  3. Options merging. The implementation merges three layers of configuration, in order of increasing precedence: framework defaults, the auto-configured defaults from your application.yml (spring.ai.openai.chat.options.*), and any per-call ChatOptions you attached directly to the Prompt. This layered precedence is exactly analogous to how Spring resolves property sources generally — more specific always wins.
  4. Translation to the provider's wire format. The implementation converts the provider-neutral Prompt/Message structure into that provider's exact HTTP request shape — OpenAI's messages array with role/content fields, Anthropic's separate top-level system field plus a messages array, and so on. This is the single place all provider-specific serialization logic lives, and it is exactly the seam described in Section 3.
  5. Network call. An HTTP client (Spring AI implementations typically use Spring's RestClient/WebClient under the hood) sends the request. This is where authentication headers, base URLs, connection and read timeouts, and provider-specific rate-limit headers are handled — configuration surface you control through Spring Boot properties or by supplying your own customized HTTP client beans.
  6. Streaming vs. blocking branch. If you called the blocking call(Prompt) method, the implementation waits for the full response body. If instead you called the reactive stream(Prompt) method (present on implementations that also satisfy the StreamingChatModel contract), the implementation opens a server-sent-events connection and emits a Flux<ChatResponse>, with each element representing an incremental token chunk as it arrives — this is the mechanism behind visibly "typing" chat UIs.
  7. Response parsing. The provider's JSON response is parsed back into provider-neutral Generation objects, each wrapping an AssistantMessage, plus response metadata: token usage counts, the model actually used (which can differ from what you requested if the provider silently routed to a different snapshot), and a finish reason — did the model stop naturally, hit the max-token limit, get cut off by a stop sequence, or invoke a tool call?
  8. Return to caller. The assembled ChatResponse is handed back to your code, which typically reads response.getResult().getOutput().getText() to get the plain string reply, while still having the option to inspect the finish reason or token usage for logging, cost tracking, or retry logic.

Two edge cases are worth reasoning through explicitly, because they trip up engineers who only think of this as "a function that returns a string."

  • What if the finish reason is "length" (truncated by max tokens)? The response you get back is syntactically valid text but may be semantically incomplete — a JSON structure cut off mid-object, a sentence cut off mid-thought. ChatModel will not raise an exception for this; it is your responsibility to inspect the finish reason and decide whether to retry with a higher token budget or treat a truncated response as a failure.
  • What if the provider call fails outright (network error, rate limit, invalid API key)? Spring AI implementations translate provider-specific failure modes into a consistent exception hierarchy so your retry and error-handling logic does not need per-provider branching — but the underlying failure (a 429 rate limit versus a 401 auth failure versus a network timeout) still has very different correct responses, so inspecting the underlying cause still matters for anything beyond a generic retry.

6. MATHEMATICS

ChatModel itself is a plumbing interface, not a mathematical mechanism — the mathematics of attention, softmax sampling, and token probabilities belongs to the Transformers and Tokenization chapters. What genuinely needs a mathematical mental model here is the handful of numeric knobs exposed through ChatOptions, because engineers frequently set them by superstition rather than understanding, and that produces subtly wrong production behavior.

6.1 Temperature, Intuitively

At the final step of generating each token, the model does not simply output "the single most likely next word." It computes a full probability distribution over its entire vocabulary — tens of thousands of candidate tokens, each with some probability of being the "right" continuation. Temperature is a single scalar that reshapes that distribution before a token is sampled from it. A temperature near zero sharpens the distribution dramatically, pushing almost all probability mass onto the single most likely token — the output becomes close to deterministic and repetitive. A higher temperature flattens the distribution, giving lower-probability tokens a meaningfully higher chance of being chosen — output becomes more varied and creative, but also more prone to wandering off into implausible territory. There is no "correct" temperature in the abstract; it is a dial you set based on the task: near zero for structured data extraction or code generation where you want the single most reliable answer, moderate-to-high for creative writing or brainstorming where variety is the point.

6.2 Max Tokens as a Hard Budget, Not a Suggestion

maxTokens is not a soft hint — it is a hard ceiling on how many tokens the model is allowed to generate for this call, enforced by the provider, and it directly caps your cost per request since output tokens are billed (typically at a materially higher per-token rate than input tokens — the Tokenization and cost chapters cover this precisely). The mathematics here is simple but consequential: a prompt asking for a long structured JSON response with a maxTokens budget too small to hold it will be silently truncated mid-structure, producing invalid JSON that passes no syntactic check. Sizing this budget correctly requires a rough mental estimate of output length in tokens (a reasonable rule of thumb across many English-language models is roughly 0.75 words per token, i.e. about 4 characters per token), sized with headroom, not sized to the exact expected length.

6.3 Top-p as an Alternative Lens on the Same Distribution

topP (nucleus sampling) is a second way of controlling the same underlying probability distribution, and providers typically recommend tuning one or the other, not both aggressively at once. Where temperature reshapes the whole distribution's sharpness, top-p truncates it: it keeps only the smallest set of highest-probability tokens whose cumulative probability reaches the threshold p, and samples only from that reduced set, discarding the long tail of unlikely tokens entirely regardless of temperature. Intuitively: temperature controls how "confidently" the model commits to likely tokens; top-p controls how large a pool of "plausible enough" tokens is even allowed to be considered.

Notice the streaming path still terminates in the exact same ChatResponse type per chunk — Spring AI does not introduce a separate "streaming response" shape. This uniformity is what lets Advisors (next chapters) wrap both blocking and streaming calls with the same cross-cutting logic.

Two production patterns are worth calling out explicitly. First, multi-model routing: many real systems keep more than one ChatModel bean alive at once — a fast, cheap model for high-volume, low-stakes classification tasks, and a stronger, more expensive model reserved for tasks that genuinely need it — selected via Spring's @Qualifier the same way you would choose between two DataSource beans. Second, resilience wrapping: because a model provider is, from your application's point of view, just another remote dependency with rate limits and occasional outages, teams wrap ChatModel calls with the same circuit breakers, retry-with-backoff, and timeout policies they would put around any third-party API — the difference, as the foundational chapters stressed, is that you additionally need output-level validation, because a "successful" HTTP call can still return a bad answer.

9. JAVA / SPRING PERSPECTIVE

This is where the interface stops being theory and becomes code you will actually write. A minimal, realistic Spring Boot service that depends on ChatModel: 

@Service
public class SupportReplyDrafter {

    private final ChatModel chatModel;

    public SupportReplyDrafter(ChatModel chatModel) {
        this.chatModel = chatModel; // depends on the INTERFACE, never OpenAiChatModel directly
    }

    public String draftReply(String ticketBody) {

        SystemMessage systemMessage = new SystemMessage(
            "You are a support assistant for Acme Corp. Be concise, " +
            "polite, and never promise refunds without escalation."
        );
        UserMessage userMessage = new UserMessage(ticketBody);

        ChatOptions options = OpenAiChatOptions.builder()
            .model("gpt-4o-mini")
            .temperature(0.3)
            .maxTokens(400)
            .build();

        Prompt prompt = new Prompt(List.of(systemMessage, userMessage), options);

        ChatResponse response = chatModel.call(prompt);

        return response.getResult().getOutput().getText();
    }
}

Nothing in this class imports anything from an OpenAI-specific package except the options builder — and even that is only needed because this particular call wants provider-specific tuning; a version using only ChatOptions.builder() would be fully provider-neutral. Swapping to Anthropic in production is a configuration and bean-wiring change, not a rewrite of SupportReplyDrafter.

Auto-configuration is what makes this "just work" with minimal ceremony. Adding the spring-ai-openai-spring-boot-starter dependency and setting spring.ai.openai.api-key in application.yml (backed by an environment variable, never a literal in source control) is enough for Spring Boot to auto-configure and expose a fully wired OpenAiChatModel bean implementing ChatModel — the same "starter + properties + auto-configuration" pattern you already trust for DataSource, RedisTemplate, or a Kafka ProducerFactory. 

spring:
  ai:
    openai:
      api-key: ${OPENAI_API_KEY}
      chat:
        options:
          model: gpt-4o-mini
          temperature: 0.7

Streaming looks structurally similar but returns a reactive type, because Spring AI's streaming-capable implementations also satisfy StreamingChatModel: 

@GetMapping(value = "/chat/stream", produces = MediaType.TEXT_EVENT_STREAM_VALUE)
public Flux<String> streamReply(@RequestParam String question) {
    Prompt prompt = new Prompt(new UserMessage(question));
    return chatModel.stream(prompt)
            .map(chatResponse -> chatResponse.getResult().getOutput().getText());
}

For testing, the interface pays for itself immediately: a unit test for SupportReplyDrafter injects a mock ChatModel (Mockito's mock(ChatModel.class)) and stubs call(any(Prompt.class)) to return a hand-built ChatResponse — no network call, no API key, no non-determinism, and it runs in milliseconds as part of your normal test suite. This is precisely the exact-match-testable seam the foundational "What Is Intelligence" chapter warned you not to expect at the model's actual output — but here, one layer up, at the interface boundary, ordinary deterministic unit testing works exactly the way you are used to.

10. BEST PRACTICES

  • Always code against ChatModel, never a concrete provider class, even in a single-provider project — the discipline costs nothing today and saves a painful refactor the day you need to switch or A/B test providers.
  • Externalize API keys and model names to configuration, never hardcode them — use application.yml properties backed by environment variables or a secrets manager, so promoting to a different environment or rotating a key never requires a code change or redeploy of business logic.
  • Set an explicit maxTokens on every production call rather than relying on provider defaults — an unbounded or overly generous default is both a cost risk and a latency risk under load.
  • Always inspect the finish reason before trusting a response as complete, especially for any workflow parsing structured output — a "length" finish reason means the payload was clipped, and treating it as a normal successful answer is a silent correctness bug.
  • Prefer provider-neutral ChatOptions by default; drop to a provider-specific options class only when a feature genuinely requires a vendor-specific knob, and comment why when you do, so the coupling is a visible, intentional decision rather than an accident of copy-pasted sample code.
  • Log token usage from ChatResponseMetadata on every call in production — it is your primary lever for cost observability and capacity planning, and retrofitting it after a surprise bill is far more painful than building it in from day one.

11. COMMON MISTAKES

  • Injecting the concrete provider class (OpenAiChatModel) instead of the ChatModel interface, usually because an IDE auto-import grabbed the concrete type first — this quietly defeats the entire point of the abstraction and is easy to miss in code review unless reviewers are specifically watching for it.
  • Putting system-level instructions inside a UserMessage out of habit or convenience, which weakens how reliably the model honors standing behavioral constraints once real user input starts competing with them for attention.
  • Treating call(Prompt) as safe to invoke repeatedly inside a tight loop without any rate-limit or backoff awareness — providers will throttle or reject bursts, and the failure surfaces as an exception deep in a batch job rather than gracefully.
  • Assuming the response is always complete and well-formed, especially when parsing JSON or code out of the reply, without checking the finish reason or wrapping the parse in a validation step.
  • Never rebuilding conversation history correctly — because ChatModel is stateless, forgetting to include prior turns as messages in a new Prompt produces a model that appears to have amnesia between calls, which engineers new to the interface frequently mistake for a bug in the framework rather than a missing piece of their own code.
  • Copy-pasting a provider-specific options builder from documentation into shared business logic, quietly making a supposedly provider-neutral service depend on one vendor's SDK on the classpath, undermining the exact swappability the interface was designed to protect.

12. PERFORMANCE CONSIDERATIONS

ChatModel is a thin layer, so it adds negligible overhead of its own — the performance story here is entirely about how you use the interface, not the interface itself.

  • Latency is dominated by the network round trip and generation time, not by Spring AI's dispatch logic. A blocking call() holds a thread for the full duration of generation, which can range from under a second to many seconds depending on model size and response length — under load, this makes thread-pool sizing on synchronous web tiers a real capacity-planning concern, and is a strong argument for reactive/streaming paths on latency-sensitive endpoints.
  • Streaming reduces perceived latency, not total latency. Time-to-first-token can be dramatically better with stream() than waiting for the full call() response, which matters enormously for interactive chat UIs even though the total wall-clock time to finish generating is roughly unchanged.
  • Every token, input and output, costs money and time — output tokens especially. Trimming unnecessary conversation history, summarizing long context instead of resending it verbatim on every call, and setting a disciplined maxTokens are direct cost and latency levers, not micro-optimizations.
  • Connection reuse and timeout tuning matter at scale. The underlying HTTP client's connection pool, and its read/connect timeout settings, should be tuned deliberately for your traffic pattern — a default that is fine for a demo can silently become a bottleneck or a source of cascading timeouts under real concurrent load.

13. SECURITY CONSIDERATIONS

ChatModel itself is a narrow transport-and-mapping interface, so its direct security surface is modest — but two concerns are genuinely its responsibility rather than a later layer's, and are worth being explicit about rather than padding this section artificially.

  • API key handling. The credentials your ChatModel implementation uses to authenticate to a provider are high-value secrets — treat them exactly as you would a database password: never in source control, never logged, rotated through a secrets manager, and scoped with the narrowest provider-side permissions available.
  • Everything that ends up inside a Prompt is untrusted input from the model's perspective, including your own application data. As covered in the foundational chapters, a model has no hard-coded, tamper-proof separation between "instruction" and "data" the way a parameterized SQL query does — so any user-supplied text or externally retrieved content assembled into a UserMessage is a potential prompt-injection vector the moment it reaches ChatModel.call(). This interface is exactly where that risk becomes concrete: whatever you construct a Prompt from is what the model sees, unfiltered by anything ChatModel itself does for you. Sanitization, instruction hardening, and injection defenses are the responsibility of layers around ChatModel (Advisors and guardrails, covered later), not something the interface provides on its own — and it is important not to assume otherwise.

14. INTERVIEW QUESTIONS

JUNIORQ1. What is ChatModel in Spring AI, and what problem does it solve?

ROI: ★★★★★ · Frequency: Extremely High

ChatModel is Spring AI's core, provider-agnostic interface for sending a conversation (a Prompt) to a large language model and getting back a generated response (a ChatResponse). It solves the vendor lock-in problem: business logic depends only on this one Java interface, while framework-provided implementations like OpenAiChatModel or AnthropicChatModel handle the provider-specific request/response translation underneath, so switching providers is a configuration change, not a code rewrite.

JUNIORQ2. Is ChatModel stateful — does it remember previous messages in a conversation automatically?

ROI: ★★★★☆ · Frequency: High

No. ChatModel is stateless by design — each call to call(Prompt) is independent. If a conversation needs history, the caller must explicitly include all relevant prior messages inside the Prompt passed to every call. Conversational memory is handled one layer up, typically through Advisors, not inside ChatModel itself.

MIDQ3. Walk through what a Prompt and a ChatResponse actually contain.

ROI: ★★★★★ · Frequency: Extremely High

A Prompt holds an ordered list of Message objects (typically a SystemMessage for standing instructions plus UserMessage/AssistantMessage for the conversation turns) and an optional ChatOptions object for per-call tuning like model name, temperature, or max tokens. A ChatResponse holds a list of Generation objects — each wrapping a new AssistantMessage — plus response metadata such as token usage and finish reason. In practice you usually read response.getResult().getOutput().getText() to get the single generated reply as a plain string.

MIDQ4. What is the difference between SystemMessage, UserMessage, and AssistantMessage, and why does the distinction matter?

ROI: ★★★★☆ · Frequency: High

They tag each turn of the conversation with a role the model was trained to weigh differently. SystemMessage carries standing behavioral instructions for the whole interaction; UserMessage carries what the human said; AssistantMessage carries what the model said previously, fed back in to preserve continuity across turns. Mixing these up — for example, putting system-level instructions into a UserMessage — does not cause an error, but it measurably weakens how reliably the model follows those instructions once real, varied user content is present, because the model has learned different statistical expectations for each role during training.

MIDQ5. What happens if a response's finish reason indicates it was cut off by the max token limit, and why does this matter for structured output?

ROI: ★★★★☆ · Frequency: Medium-High

ChatModel does not raise an exception for this — you get back a syntactically normal ChatResponse whose text may be semantically incomplete, such as JSON truncated mid-object. It is the caller's responsibility to inspect the finish reason in the response metadata and decide whether to retry with a larger token budget or reject the response as invalid. Silently trusting any non-exceptional response as "complete" is a common source of intermittent parsing failures in production.

SENIORQ6. How would you design a Spring service that needs to route between a cheap/fast model and an expensive/strong model depending on task difficulty, while keeping business logic testable and provider-agnostic?

ROI: ★★★★★ · Frequency: High at senior level

Expose two ChatModel beans in the application context — for example a @Primary bean backed by a fast/cheap model and a second bean disambiguated with @Qualifier backed by a stronger model — both still typed as the plain ChatModel interface. Business services depend on ChatModel injected by qualifier, or on a thin routing component that picks between the two based on a task-difficulty signal, keeping the decision logic centralized and testable in isolation. For unit tests, both beans can be mocked via Mockito without any network dependency, since the services only ever see the interface. This mirrors the familiar pattern of qualifying multiple DataSource beans for a primary/read-replica split.

Interview Gold Point: Mention that this pattern also enables a gradual migration or A/B test between providers with zero business-logic changes — swap which bean is wired to which qualifier, or route a percentage of traffic between them — which is exactly the strategic flexibility the interface abstraction was built to preserve, and is the kind of forward-looking answer that distinguishes a senior response from a merely correct one.
SENIORQ7. Explain the difference between the provider-neutral ChatOptions and a provider-specific options class like OpenAiChatOptions. When would you reach for the latter, and what's the trade-off?

ROI: ★★★★☆ · Frequency: Medium-High

ChatOptions exposes the small set of tuning parameters virtually every provider supports in some form — model name, temperature, max tokens, stop sequences — keeping code fully portable across providers. Provider-specific option classes extend that base with vendor-only capabilities that don't have a neutral equivalent. You reach for the provider-specific class only when a feature genuinely needs a capability the neutral contract doesn't expose, and doing so is a conscious trade: you gain access to that capability but reintroduce a compile-time dependency on that provider's Spring AI module in that call site, which should be treated as an explicit, reviewed exception rather than the default style.

STAFFQ8. A junior engineer proposes injecting OpenAiChatModel directly everywhere "since we're only ever going to use OpenAI." How do you respond, and is there ever a legitimate case for their approach?

ROI: ★★★★★ · Frequency: High at staff level

The default answer is no — inject ChatModel even in a single-provider system, because the cost of the discipline is essentially zero (one interface type instead of a concrete class) while the cost of not doing it compounds silently: every call site becomes a future migration point the day the business needs a second provider for cost, latency, data residency, or vendor-risk reasons, and unit tests lose the ability to mock cleanly without pulling in provider-specific test scaffolding. The legitimate exception is a call site that intentionally and permanently needs a provider-specific capability with no neutral equivalent — in that narrow case, depending on the concrete class (or the provider-specific options type) is a conscious, documented decision, not an accident of convenience. The staff-level framing is to treat "provider independence" as a default posture you deviate from deliberately, not a rule you either always or never follow.

16. SUMMARY

  • ChatModel is Spring AI's narrow, stable, provider-agnostic contract for turning a Prompt into a ChatResponse — the exact same "port and adapter" pattern you already trust from Spring Data's repository abstractions.
  • It is deliberately stateless: no conversation memory lives inside it, so every call must carry whatever prior context the model needs, explicitly, as messages in the Prompt.
  • Message roles (SystemMessage, UserMessage, AssistantMessage) are not cosmetic — they change how reliably a model honors instructions, because the model was trained on text where those roles carried different statistical weight.
  • A layered options model (ChatOptions plus provider-specific extensions like OpenAiChatOptions) lets you stay portable by default while still opting explicitly into vendor-specific tuning when a feature truly requires it.
  • Production use of ChatModel looks like any other unreliable remote dependency — resilience wrapping, multiple qualified beans for multi-model routing, careful token-budget and timeout tuning — plus the AI-specific addition of always checking the finish reason before trusting a response as complete.
  • Because business logic depends only on the interface, testing collapses back to ordinary, deterministic unit testing with a mocked bean — the model's own non-determinism never has to leak into your test suite at this layer.
