CHAPTER 28 — CHATCLIENT

Volume 2 — Spring AI · Chapter 3 of 15

The previous chapter gave you ChatModel — the thin, portable interface Spring AI uses to talk to any large language model provider without your business logic knowing or caring which one. That thinness is exactly the problem this chapter solves. A raw ChatModel call is a single request/response round trip with no memory of what was said a moment ago, no built-in way to attach a system persona, no structured-output conversion, and no clean place to hang cross-cutting concerns like logging, retrieval augmentation, or guardrails. ChatClient is the fluent, ergonomic, extensible layer Spring AI builds directly on top of ChatModel to turn that raw prediction function into something you would actually want to call from a real Spring Boot service — and understanding it well is the single highest-leverage skill in this entire volume, because almost every other Spring AI feature (Advisors, memory, RAG, tool calling) is delivered to your application code through a ChatClient.

1. MOTIVATION

Imagine you are handed a raw ChatModel bean and asked to build a customer support assistant feature for a Spring Boot application. Within the first hour you will discover a cluster of small but real problems that have nothing to do with the model's intelligence and everything to do with plumbing. You need to prepend a system prompt describing the assistant's persona and constraints on every single call — but you don't want to repeat that string in twenty different service methods. You need to interpolate runtime values (the customer's name, their order ID, today's date) into a prompt template without hand-rolling string concatenation and worrying about injection-style bugs. You need the model's free-text answer converted into a typed Java record so the rest of your codebase can work with it like any other DTO, not scrape it with regular expressions. You need to log every prompt and response for observability, and you'd like that logging to live in exactly one place rather than sprinkled through every controller. And eventually you'll want to bolt on conversation memory, retrieval-augmented context, and tool calling — all without rewriting the calling code every time you add a capability.

Every one of those needs is a solved problem in traditional Spring Boot — you already have @Valid for validation, Jackson for typed conversion, AOP and interceptors for cross-cutting logging, and the Strategy pattern for swappable behavior. ChatClient exists precisely because Spring AI's designers recognized that LLM application code has the same shape of plumbing needs, and gave Java engineers a single, fluent, Spring-idiomatic entry point that already knows how to do all of it — instead of forcing every team to reinvent a bespoke wrapper around ChatModel, which is exactly what happened, repeatedly and divergently, before this abstraction existed.

This matters for your journey toward production AI Engineering because ChatClient is not a convenience you can skip past — it is the object every Advisor (Chapter 30), every memory strategy (Chapter 31), every RAG pipeline (Volume 3), and every tool-calling agent (Volume 4) attaches itself to. Learn its fluent API shallowly now, and every later chapter in this volume will feel like magic you can't debug. Learn it deeply — request spec, response spec, the advisor chain, structured output conversion — and every later chapter becomes "one more thing configured on the ChatClient I already understand."

2. HISTORICAL BACKGROUND

2.1 Before Spring AI: The Hand-Rolled Wrapper Era

Before Spring AI existed (and even now, in codebases that predate its adoption), Java teams calling an LLM provider typically wrote one of two things. The first was a thin HTTP client — built on RestTemplate, then later WebClient — that serialized a hand-written request DTO matching the provider's REST schema (a list of role/content message objects, a model name, a temperature) and deserialized the provider's JSON response into another hand-written DTO. This worked, but it tightly coupled business logic to one vendor's wire format: switching from OpenAI to Anthropic, or even just testing against a local model, meant touching every call site.

The second pattern, once teams felt that pain, was an internal "AI service" facade — usually a single Spring @Service class with methods like askQuestion(String prompt) or summarize(String text) that hid the vendor SDK behind an interface. This is a perfectly reasonable instinct — it is the Strategy/Facade pattern you already know — but every team built its own version, with its own inconsistent handling of system prompts, conversation history, retries, and JSON-mode structured output. There was no shared vocabulary, no shared testing approach, and no way to plug in a community-built capability (say, a retrieval-augmented generation strategy) without rewriting it against your team's bespoke facade.

2.2 The Python Ecosystem's Head Start

While this was happening in Java shops, the Python ecosystem — driven by libraries like LangChain — had already converged on a recognizable shape: a "chain" or "chat" object that could be configured with a system message, memory, retrieval, and output parsers, then invoked with a fluent or chained call style. Spring AI's designers were explicit that they wanted Java and Spring Boot developers to have an equivalently ergonomic, idiomatic entry point — but built on Spring's own conventions (auto-configuration, builder beans, dependency injection) rather than a direct port of a Python API. ChatClient is the result: conceptually a close cousin of what LangChain calls a chat chain, but expressed as a fluent Java builder that feels at home next to WebClient and RestClient.

2.3 The Spring Precedent: RestTemplate → WebClient → RestClient

There is a direct, illuminating precedent inside Spring itself for exactly this kind of evolution, and it is worth naming because it predicts how you should think about ChatClient. Spring started with RestTemplate — a synchronous, imperative HTTP client. As reactive programming matured, Spring introduced WebClient — a fluent, chainable builder supporting both blocking and reactive styles. Later, recognizing that many teams wanted WebClient's fluent ergonomics without committing to reactive types everywhere, Spring introduced RestClient — a synchronous fluent client with the same builder-based request/response spec pattern. ChatClient's API shape — a builder that produces a client, a fluent request spec with .system()/.user()-style methods, and a response spec with .content()/.entity()/.chatResponse() terminal operations — is a deliberate echo of that same maturity curve, and if you have ever used WebClient.get().uri(...).retrieve().bodyToMono(...), the shape of chatClient.prompt().user(...).call().content() should already feel familiar in its bones.

Every intuition you have about WebClient's builder ergonomics transfers almost directly.

3. PROBLEM STATEMENT

Stated precisely, ChatClient exists to solve this engineering problem:

Provide a single, fluent, provider-agnostic entry point for constructing a chat interaction — system context, user input, runtime parameters, conversation history, and cross-cutting behavior — and for converting the model's raw response into the shape the calling code actually needs (plain text, a typed Java object, or a reactive stream), without the calling code ever touching the underlying ChatModel, message DTOs, or provider wire format directly.

Unpack that sentence and you get the exact list of responsibilities ChatClient takes on so your service layer does not have to: assembling a Prompt (the ordered list of system/user/assistant messages plus options) from ergonomic method calls instead of manual list-building; running that prompt through a configurable, ordered chain of interceptors (Advisors) before and after the model call; delegating the actual network round trip to a ChatModel so the client itself stays provider-agnostic; and converting the model's raw ChatResponse into whatever terminal shape the caller asked for — a String, a ChatResponse, a strongly-typed Java record via structured output conversion, or a Flux for streaming.

Notice what is deliberately not in that responsibility list: ChatClient does not decide which model to call, does not implement retries or circuit breaking itself (that belongs to the underlying ChatModel/HTTP client configuration, as covered in the ChatModel chapter), and does not hard-code any single provider's request format. It is an orchestration and ergonomics layer, not a networking layer and not a model. Keeping that boundary crisp in your head is what will let you correctly reason about where a given piece of AI-application logic belongs as your systems grow.

4. THEORY

4.1 The Core Mental Model: A Fluent Prompt Builder With an Interceptor Pipeline

The cleanest way to hold ChatClient in your head is as two things bolted together, both of which you already understand separately. The first half is a fluent builder for a Prompt — the same conceptual job as a SQL query builder or WebClient's request spec: instead of manually constructing a List<Message> containing a SystemMessage and a UserMessage and wiring in a ChatOptions object by hand, you chain readable method calls (.system(...), .user(...), .options(...)) that build that structure for you. The second half is an ordered interceptor pipeline — conceptually identical to a servlet filter chain or a chain of AOP advice — that every request and response passes through on the way to and from the model, giving you one place to attach memory, retrieval, logging, or safety checks without ever touching the calling code.

4.2 Builder vs. Client: Two Distinct Objects With Two Distinct Lifecycles

A subtlety that trips up almost every engineer meeting this API for the first time is that there are two different objects in play, with two different, deliberate lifecycles. ChatClient.Builder is the configuration-time object: you (or Spring Boot's auto-configuration) use it once, typically at application startup, to set defaults — a default system prompt, a default set of Advisors, default ChatOptions — and then call .build() to produce an immutable ChatClient. The ChatClient itself is the request-time object: it is thread-safe, intended to be created once and reused (typically as a field in a @Service), and every call to .prompt() on it starts a brand-new, independent request without mutating any shared state. This mirrors exactly how you already treat a WebClient instance versus each individual `.get()`/`.post()` request built from it — build the client once, issue many independent requests from it.

4.3 Request Spec and Response Spec

Calling chatClient.prompt() returns a request spec — a mutable builder scoped to this one call, on which you attach a system message, a user message (optionally with template parameters), runtime ChatOptions overrides, one-off Advisors, and (for tool-calling scenarios covered in a later chapter) tool definitions. Calling a terminal method like .call() or .stream() on that request spec triggers the actual pipeline execution and returns a response spec, on which you choose the shape you want the answer in: .content() for a plain String, .chatResponse() for the full ChatResponse object (metadata, token usage, finish reason, and all), or .entity(SomeRecord.class) for automatic conversion into a typed Java object. This two-spec design — build the request, then choose how to consume the response — is precisely the same shape as WebClient's .retrieve() followed by .bodyToMono(...) or .toEntity(...), and recognizing that parallel will make the API feel far less novel than it first appears.

4.4 Structured Output as a First-Class Concept

One theoretical point deserves emphasis because it is easy to underestimate: .entity(Class) is not string parsing bolted on afterward. Under the hood, Spring AI uses the target type's shape to construct format instructions that get woven into the prompt sent to the model (telling it, in effect, "respond as JSON matching this schema"), and then parses the model's response back into that Java type, typically via Jackson. This means structured output is a collaboration between prompt construction and response parsing — both ends of the ChatClient pipeline — not a feature that lives in only one place. Understanding this now will make the "Structured Output" chapter later in this volume click immediately rather than feeling like unrelated new material.

5. INTERNAL WORKING

Walk through what actually happens, step by step, when your code executes a call like: 

String answer = chatClient.prompt()
        .system("You are a concise, factual support assistant.")
        .user("What is our refund policy for digital goods?")
        .call()
        .content();
  1. Request spec assembly. .prompt() creates a fresh, empty request spec, pre-populated with any defaults configured on the ChatClient.Builder at startup (default system text, default Advisors, default options). .system(...) and .user(...) append or override the corresponding messages on that spec. If .user(u -> u.text("...").param("key", value)) is used instead of a plain string, Spring AI resolves the template placeholders against the supplied parameters at this stage, before anything is sent anywhere.
  2. Prompt materialization. When a terminal method (.call() or .stream()) is invoked, the request spec is converted into an immutable Prompt object — an ordered list of Message instances (typically a SystemMessage followed by one or more UserMessage/AssistantMessage entries for multi-turn context) plus a resolved ChatOptions instance merging defaults with any per-call overrides.
  3. Advisor chain entry (the "before" pass). The materialized prompt is handed to the configured chain of Advisors, executed in order. Each Advisor is given the chance to inspect and modify the request before it proceeds — this is the mechanism a conversation-memory Advisor uses to inject prior turns, and the mechanism a retrieval Advisor uses to inject retrieved context, both covered in depth in dedicated later chapters. Advisors are chained the same way servlet filters are: each one calls onward to the next, forming a pipeline rather than a flat list of independent hooks.
  4. Delegation to ChatModel. After the last Advisor's "before" logic runs, the (possibly modified) prompt reaches the underlying ChatModel implementation, which performs the actual network call to the provider — this is exactly the mechanism covered in the previous chapter, and ChatClient deliberately knows nothing about HTTP, authentication, or provider-specific JSON at this point.
  5. Response arrival. The provider returns a completion, which the ChatModel wraps into a provider-agnostic ChatResponse containing one or more Generation results, token usage metadata, and a finish reason.
  6. Advisor chain exit (the "after" pass). The ChatResponse travels back out through the same Advisor chain in reverse, giving each Advisor a chance to observe or modify the response — a logging Advisor typically does its work here, and a memory Advisor persists the new assistant turn here.
  7. Response spec conversion. The final ChatResponse is wrapped in a response spec. Calling .content() extracts the text of the first (or top) Generation; calling .entity(SomeType.class) instead parses that text against the requested Java type using the format instructions that were woven into the prompt back in step 2; calling .chatResponse() hands back the whole object untouched.

Reasoning about edge cases becomes mechanical once you internalize this pipeline. What happens if the model's response isn't valid JSON when you called .entity(...)? Parsing fails at step 7, and you get a conversion exception — which means .entity(...) calls need the same defensive error handling you'd apply to any external deserialization, not blind trust. What happens if an Advisor throws partway through the chain? The call fails before ever reaching the model (if it was a "before" failure) or after a successful model call but before your code sees the response (if it was an "after" failure) — which is exactly why Advisors that call external systems (a vector store, a memory store) need their own timeout and failure handling, discussed further in the Advisors chapter. What happens with .stream() instead of .call()? The same pipeline runs, but the terminal response spec returns a Flux of incremental chunks instead of a single materialized answer, and any "after" Advisor logic that needs the full text (like persisting a memory turn) has to be written to aggregate the stream first — a detail that catches teams off guard the first time they combine streaming with memory.

6. MATHEMATICS

ChatClient itself introduces essentially no new mathematics beyond what the previous chapter already covered for the underlying model call — it is an orchestration and ergonomics layer, not a computational one. The one place where a little quantitative thinking is genuinely useful is in reasoning about the token cost of the pipeline you build, because every message a request spec assembles (system text, injected memory turns, injected retrieved context, format instructions for structured output) is additive token cost before the model ever generates a single token of response.

If S is the token count of your system prompt, M is the token count of injected memory/history, R is the token count of any retrieved context an Advisor injects, and U is the token count of the current user turn, then the effective input token count for a single ChatClient call is approximately: 

Input tokens ≈ S + M + R + U (+ format-instruction overhead if using .entity())

This is not a formula you need to compute by hand in application code — providers report exact usage on the returned ChatResponse's metadata — but the additive structure matters conceptually: every Advisor you add to a ChatClient's pipeline is a candidate to grow M or R without bound if left unchecked (an unbounded memory Advisor that replays an entire conversation history, for instance), and that growth is linear in the number of turns unless you actively manage it with truncation, summarization, or windowing — the exact subject of the Memory chapter later in this volume. The mathematics that matters here is less about the model and entirely about the accounting discipline of a pipeline you, the engineer, are assembling.

Two production-shaped decisions fall directly out of this diagram. First, the ChatClient bean (or, more precisely, the ChatClient.Builder it's built from) is typically configured once, centrally, in a @Configuration class — default system prompt, default Advisors, default retry-relevant ChatOptions — so that every service consuming it inherits consistent baseline behavior instead of each team re-deciding persona and safety defaults independently. 9. JAVA / SPRING PERSPECTIVE

Spring Boot's autoconfiguration, once you add a Spring AI model starter (for example the OpenAI or Anthropic starter) to your dependencies, exposes a ready-to-inject ChatClient.Builder bean out of the box — you do not have to hand-construct a ChatModel and wire it yourself unless you need multiple, differently-configured clients. A typical production wiring looks like this: 

@Configuration
class ChatClientConfig {

    @Bean
    ChatClient supportChatClient(ChatClient.Builder builder,
                                  VectorStore vectorStore,
                                  ChatMemory chatMemory) {
        return builder
                .defaultSystem("""
                    You are a concise, factual customer support assistant.
                    Never invent policy details you are not given as context.
                    """)
                .defaultAdvisors(
                        MessageChatMemoryAdvisor.builder(chatMemory).build(),
                        QuestionAnswerAdvisor.builder(vectorStore).build(),
                        new SimpleLoggerAdvisor()
                )
                .defaultOptions(
                        OpenAiChatOptions.builder()
                                .temperature(0.2)
                                .maxTokens(600)
                                .build()
                )
                .build();
    }
}

@Service
class SupportAssistantService {

    private final ChatClient chatClient;

    SupportAssistantService(@Qualifier("supportChatClient") ChatClient chatClient) {
        this.chatClient = chatClient;
    }

    SupportAnswer answer(String question, String customerId) {
        return chatClient.prompt()
                .user(u -> u.text("Customer question: {question}")
                            .param("question", question))
                .advisors(a -> a.param(ChatMemory.CONVERSATION_ID, customerId))
                .call()
                .entity(SupportAnswer.class);
    }

    Flux answerStreaming(String question, String customerId) {
        return chatClient.prompt()
                .user(question)
                .advisors(a -> a.param(ChatMemory.CONVERSATION_ID, customerId))
                .stream()
                .content();
    }
}

record SupportAnswer(String reply, boolean escalateToHuman, String category) {}

Map this back onto Java idioms you already trust: ChatClient.Builder plays exactly the role a RestClient.Builder or WebClient.Builder plays — a configuration-time factory you use once per logical client and then discard. The ChatClient instance itself is thread-safe and stateless between calls, so injecting it as a singleton field is correct and idiomatic, the same as you would with a JdbcTemplate or a RestClient. .defaultAdvisors(...) is the direct Spring AI analogue of registering global HandlerInterceptors or AOP aspects: cross-cutting behavior configured once, applied to every request automatically. .entity(SupportAnswer.class) is the AI-era equivalent of Jackson deserializing a REST response body into a DTO — the difference is that the "wire format" being parsed was itself shaped by instructions Spring AI wove into the outgoing prompt, which is why the Structured Output chapter treats this feature with real care rather than as an incidental convenience.

It is also worth being precise about what stays out of ChatClient's job description within this API surface: multi-provider failover, request-level circuit breaking, and rate-limit backoff are configured at the ChatModel/HTTP client layer (Chapter 27's territory, often via Spring Retry or Resilience4j wrapping the underlying client), not inside the fluent builder itself. Keeping this boundary in mind prevents a common design mistake — trying to implement retry logic as a custom Advisor, when it almost always belongs one layer lower, closer to the actual network call.

10. BEST PRACTICES

  • Build ChatClient instances once, as singletons, never per-request. Constructing a new client (or worse, a new ChatClient.Builder) inside a request-handling method throws away the whole point of the builder/client split and risks losing consistently-applied defaults.
  • Push persona and safety instructions into defaultSystem() at the builder level, not into every call site. Centralizing this means a single audited string governs behavior across the whole application, instead of drifting copies scattered across services.
  • Prefer .user(u -> u.text(template).param(...)) over manual string concatenation for any prompt containing runtime data. This keeps the template readable, keeps parameter substitution explicit and auditable, and is the natural place to reason about prompt-injection risk (Section 13) since every interpolation point is visible in one call.
  • Use .entity(Type.class) whenever the caller needs a specific shape, rather than parsing .content() yourself. Hand-rolled regex or substring extraction against free-text model output is exactly the kind of brittle code that structured output conversion exists to eliminate.
  • Name and qualify multiple ChatClient beans explicitly when your application legitimately needs more than one persona or pipeline (e.g., a support assistant client and an internal-tools client with different Advisors) — do not overload a single client's defaults to serve two very different jobs.
  • Keep Advisor ordering intentional and documented. Because the chain executes in order on the way in and reverse order on the way out, subtle bugs (a logging Advisor that logs pre-redaction content because it runs before a redaction Advisor) come directly from careless ordering.

11. COMMON MISTAKES

  • Confusing ChatClient.Builder with ChatClient and rebuilding on every request. This silently discards any Advisor state that expects a stable pipeline (like memory keyed to a conversation) and wastes cycles reconstructing an object meant to be built once.
  • Assuming .entity(Type.class) guarantees a valid object with no failure handling. The model can still return malformed or incomplete JSON despite format instructions; calls to .entity(...) need the same try/catch discipline you would apply to any external deserialization, not blind trust that the model "always follows instructions."
  • Forgetting that .stream() changes how "after" Advisor logic must be written. An Advisor written assuming a single, complete response (like a memory-persisting Advisor) can silently do the wrong thing — persisting a partial chunk, or persisting nothing — if it isn't adapted to aggregate a streamed response first.
  • Putting business logic that belongs in the model layer into a custom Advisor, or vice versa. Retry/backoff belongs near the ChatModel/HTTP layer; prompt enrichment, memory, and structured logging belong in Advisors. Mixing these responsibilities makes both layers harder to test in isolation.
  • Interpolating raw, untrusted user text directly into the system message instead of the user message. This blurs the (already soft) line between "trusted instruction" and "untrusted content" that Chapter 01's discussion of prompt injection warned about, and makes injection attacks materially easier to construct.
  • Letting default Advisors silently grow unbounded context. A memory Advisor with no windowing/summarization strategy attached will, turn by turn, grow the token cost of every subsequent call — a mistake that is invisible in a demo with three turns and expensive in production with three hundred.

12. PERFORMANCE CONSIDERATIONS

ChatClient itself adds negligible CPU or memory overhead relative to the network round trip it wraps — building a Prompt object and running it through a handful of Advisors is microseconds of work compared to the hundreds of milliseconds to multiple seconds a model call typically takes. The real performance surface it controls is how much work the pipeline does before and after that network call, and that surface is entirely under your design control:

  • Every Advisor in the chain is on the critical path of the call's latency unless explicitly written to run asynchronously off the hot path. A retrieval Advisor performing a slow vector search, or a memory Advisor performing a slow database read, directly adds to end-to-end response time — measure and budget for this the same way you would budget for a downstream service call in any REST endpoint.
  • Structured output via .entity(...) adds a small but real prompt-size cost for the format instructions woven in, and a small parsing cost on the way out — negligible for most payloads, but worth knowing about when reasoning precisely about token budgets on very high-volume endpoints.
  • Streaming via .stream() changes perceived latency, not total cost. It does not reduce total tokens generated or total compute, but it lets your application start rendering output to a user well before the full response is complete — a major user-experience lever for chat-style UIs, and a decision that should be made explicitly per endpoint rather than defaulted everywhere.
  • Reusing a single, well-configured ChatClient bean avoids repeated setup cost (building default Advisor lists, resolving default options) on every request — another reason the singleton-bean pattern from Section 10 is not just idiomatic but materially faster under load.

13. SECURITY CONSIDERATIONS

ChatClient has a real, non-trivial security surface precisely because it is the assembly point where trusted instructions (your system prompt, your Advisor configuration) and untrusted content (user input, retrieved documents, tool outputs) are combined into a single prompt handed to the model. As covered in the foundational discussion of intelligence and again in the Hallucinations material, a model does not have a tamper-proof, structural distinction between "instruction" and "data" the way a parameterized SQL query does — so anything that flows into .user(...) or into content an Advisor injects is a potential prompt-injection vector, and ChatClient is exactly where that combination happens.

Two concrete disciplines follow directly from this. First, keep the boundary between your system message and user-supplied content explicit and narrow — build system instructions from constants you control, and treat every value flowing through .param(...) as untrusted input deserving the same suspicion you'd apply to any field bound from an HTTP request body. Second, if you write custom Advisors that inject external content (retrieved documents, tool results, prior conversation turns pulled from storage), remember that content is being placed into the same prompt the model cannot cleanly distinguish from your instructions — this is precisely why RAG-focused Advisors and tool-calling pipelines (Volumes 3 and 4) need explicit sanitization and framing (clearly delimiting "here is reference material, not instructions" in the constructed prompt) rather than naive concatenation. ChatClient does not solve this for you automatically; it simply gives you one well-defined place to solve it correctly, instead of many scattered, inconsistent places.

14. INTERVIEW QUESTIONS

JUNIORQ1. What is the difference between ChatModel and ChatClient in Spring AI?

ROI: ★★★★★ · Frequency: Extremely High

ChatModel is the low-level, provider-agnostic interface for sending a single Prompt and getting back a ChatResponse — it is analogous to a thin HTTP client. ChatClient is a higher-level, fluent API built on top of a ChatModel that adds ergonomic prompt construction (system/user messages, templating), a configurable Advisor pipeline for cross-cutting concerns like memory and retrieval, and convenient response conversion (plain text, typed objects, streaming). Application code should almost always talk to ChatClient, not directly to ChatModel.

JUNIORQ2. What is the difference between ChatClient.Builder and ChatClient itself?

ROI: ★★★★☆ · Frequency: High

ChatClient.Builder is a configuration-time object used to set defaults (default system prompt, default Advisors, default options) and is typically used once to produce an immutable ChatClient via .build(). The resulting ChatClient is the request-time object — thread-safe, meant to be created once (usually injected as a singleton bean) and reused across many independent .prompt() calls.

MIDQ3. Walk through what happens internally between calling .prompt().user("...").call().content() and getting a String back.

ROI: ★★★★★ · Frequency: Extremely High

A request spec is created (seeded with builder-level defaults), the user message is attached and any template parameters resolved. Calling .call() materializes an immutable Prompt and runs it forward through the configured Advisor chain, where each Advisor can inspect or modify the request. The final prompt is delegated to the underlying ChatModel, which performs the network call and returns a ChatResponse. That response travels back out through the Advisor chain in reverse, and finally .content() extracts the text of the top generation from the resulting response spec.

MIDQ4. Why would you use .entity(SomeRecord.class) instead of parsing .content() yourself with a JSON library?

ROI: ★★★★☆ · Frequency: High

Because .entity(...) is not just post-hoc parsing — Spring AI uses the target type to generate format instructions that get woven into the outgoing prompt itself, increasing the odds the model actually returns a matching shape, and then handles the deserialization consistently (typically via Jackson). Hand-rolling this yourself means re-deriving format instructions and duplicating parsing/error-handling logic that Spring AI already provides in one tested place.

SENIORQ5. How does the Advisor chain in ChatClient compare architecturally to a servlet filter chain or Spring AOP, and why does ordering matter?

ROI: ★★★★★ · Frequency: High at senior level

Both are pipelines of interceptors executed in a defined order, each with the opportunity to inspect/modify a request before it reaches the "real" handler (a controller method, or here, the actual model call) and to inspect/modify the response on the way back out. Ordering matters for the same reason it matters in a filter chain: an Advisor that must see raw content (e.g., a redaction Advisor) needs to run before an Advisor that logs or persists content, or the wrong version of the data gets logged/stored. Similarly, a memory Advisor injecting prior turns should generally run before a retrieval Advisor that needs the fully-formed conversational context to decide what to retrieve.

Interview Gold Point: Explicitly say that ChatClient is deliberately not responsible for retries, circuit breaking, or provider failover — that belongs one layer down, at the ChatModel/HTTP client level — and that a common design mistake is trying to implement resiliency logic as a custom Advisor when it belongs closer to the network call. This shows you understand the abstraction's boundaries, not just its happy path.
SENIORQ6. Your team added a conversation-memory Advisor to a production ChatClient and, weeks later, noticed steadily rising latency and cost per request on long-running conversations. Diagnose and propose a fix.

ROI: ★★★★★ · Frequency: High at senior level

An unbounded memory Advisor replays the full conversation history into every prompt; as a conversation grows, so does the input token count on every subsequent call, driving up both latency (more tokens to process before generation starts) and cost (billed per input token). The fix is to bound the memory strategy: apply a sliding window over recent turns, periodically summarize older turns into a condensed form, or cap total injected tokens explicitly — all trade-offs between context fidelity and cost that should be tuned deliberately, not left to unbounded default behavior.

SENIORQ7. When would you configure multiple distinct ChatClient beans in one application, rather than one shared client?

ROI: ★★★★☆ · Frequency: Medium-High

When different features genuinely need different personas, safety constraints, Advisor pipelines, or even different underlying models/providers — for example, a customer-facing support assistant with strict grounding via a QuestionAnswerAdvisor and conservative temperature, versus an internal developer-tools assistant with tool-calling enabled and a different system prompt. Forcing both use cases through one client's shared defaults either compromises one use case's safety posture or bloats the shared configuration with conditional logic that belongs at the bean-definition level instead.

STAFFQ8. A stakeholder proposes building the team's own in-house fluent wrapper around ChatModel instead of adopting ChatClient, arguing it gives "more control." How do you respond?

ROI: ★★★★★ · Frequency: High at staff level

The instinct is understandable but historically this is precisely the fragmented, hand-rolled-facade pattern that predated Spring AI and that ChatClient was built to standardize — every team ends up reinventing inconsistent handling of system prompts, memory, structured output, and cross-cutting logging, with no shared vocabulary or community-supported extension points (Advisors). A staff-level response acknowledges the legitimate underlying concern (control over specific behavior) and shows that ChatClient already provides the needed extension points for it — custom Advisors for pipeline behavior, `ChatOptions` for provider-specific tuning, multiple named beans for differentiated personas — without sacrificing the ecosystem benefits of a standard abstraction: consistent testing patterns, community Advisors (memory, RAG), and forward compatibility as Spring AI evolves. The recommendation is to extend ChatClient via its designed seams, not to fork its responsibilities into a bespoke wrapper.

JUNIORQ9. How do you create a ChatClient without going through Spring Boot autoconfiguration, given only a ChatModel instance?

ROI: ★★★★☆ · Frequency: High

You wrap the ChatModel with ChatClient.create(chatModel) for a client with no defaults, or ChatClient.builder(chatModel).build() if you want to configure defaults (system prompt, advisors, options) before building. Spring Boot's autoconfiguration simply does the latter for you and exposes a pre-wired ChatClient.Builder bean so application code rarely needs to call these factory methods directly.

JUNIORQ10. What does .prompt() return, and what can you chain onto it?

ROI: ★★★★★ · Frequency: Extremely High

.prompt() returns a ChatClientRequestSpec — a mutable builder-style object representing the request being assembled. From it you can chain .system(...), .user(...), .advisors(...), .options(...), and .tools(...) before terminating the chain with either .call() (synchronous) or .stream() (reactive).

JUNIORQ11. What is the difference between .system(...) and .user(...) in the fluent chain?

ROI: ★★★★★ · Frequency: Extremely High

.system(...) sets the system message — instructions about the assistant's role, tone, and constraints that typically stay stable across a conversation or feature. .user(...) sets the user message — the actual input/question for this specific turn. Both accept a plain string or a lambda for template-style parameterization, e.g. .user(u -> u.text("Summarize: {doc}").param("doc", text)).

JUNIORQ12. What does .call() return, and what conversion methods does it expose?

ROI: ★★★★★ · Frequency: Extremely High

.call() returns a ChatClientResponseSpec, a terminal object offering several extraction methods: .content() for the plain-text response, .chatResponse() for the full ChatResponse including metadata like token usage and finish reason, and .entity(Class) / .entity(ParameterizedTypeReference) for binding the output directly to a Java type.

JUNIORQ13. How does Spring Boot autoconfiguration make a ChatClient.Builder available for injection?

ROI: ★★★★☆ · Frequency: High

When a provider starter (e.g. spring-ai-openai-spring-boot-starter) is on the classpath along with the required API key property, autoconfiguration registers a ChatModel bean and a corresponding ChatClient.Builder prototype bean. Application code simply declares a ChatClient.Builder constructor parameter, calls .build() once (typically inside a @Bean method or in a component's constructor), and keeps the resulting ChatClient as a field for reuse.

JUNIORQ14. What is the difference between .call() and .stream()?

ROI: ★★★★★ · Frequency: Extremely High

.call() blocks until the full response is available and returns it as a single value. .stream() returns a reactive Flux (e.g. Flux<String> from .stream().content()) that emits response chunks as they arrive from the model, which is what you want for a typing-effect UI or any scenario where perceived latency matters more than having the whole answer at once.

JUNIORQ15. Can you send a prompt with no system message at all?

ROI: ★★★☆☆ · Frequency: Medium

Yes — .system(...) is optional on a per-call basis. If the ChatClient bean was built with a default system prompt via the builder, that default still applies unless explicitly overridden; if there is no default and no per-call .system(...), the request is sent with only the user message.

JUNIORQ16. What does .content() return if the model produces an empty or refusal response?

ROI: ★★★☆☆ · Frequency: Medium

It still returns a String — possibly empty or containing the model's refusal text — because .content() simply extracts whatever text is in the top generation's message. It does not throw just because the content is empty or unhelpful; distinguishing "empty" from "refused" from "genuinely answered" is application-level logic your code must add on top.

JUNIORQ17. How would you inject and store a ChatClient in a Spring service class?

JUNIORQ25. What is the difference between ChatClientRequestSpec and ChatClientResponseSpec?

Yes. A built ChatClient is immutable and stateless with respect to individual requests — each .prompt() call creates an independent request spec, so concurrent callers do not interfere with each other. JUNIORQ29. How do you get a typed list back from the model instead of a single object, using .entity()?

MIDQ30. How do default advisors configured on ChatClient.Builder interact with advisors added per-request via .advisors(...)?

ROI: ★★★★★ · Frequency: Extremely High

Default advisors set via defaultAdvisors(...) at builder time become part of every request produced by that ChatClient. Per-request .advisors(...) calls add additional advisors on top for that call only — they do not replace the defaults. The combined set is ordered and executed as a single chain, so where the per-request advisor is added relative to the defaults determines whether it runs before or after them.

MIDQ31. What happens internally when .entity() fails to parse the model's raw output into the target type?

ROI: ★★★★☆ · Frequency: High

Spring AI's structured output converter attempts to deserialize the model's text (expected to be JSON, per the format instructions injected into the prompt) into the target type via Jackson; if the text isn't valid JSON or doesn't match the expected shape, deserialization throws an exception that propagates out of the .entity() call. This is a real operational risk with smaller or less-compliant models, which is why some teams add their own repair/retry logic around entity extraction rather than assuming it always succeeds.

MIDQ32. How do you combine a default system prompt set at builder time with a per-request override?

ROI: ★★★★☆ · Frequency: High

Calling .system(...) on the request spec for a specific call replaces the system message for that call only; it does not merge with or append to the builder-level default — the last one set wins for that request. If you actually want to extend rather than replace the default, you need to explicitly compose the text yourself (e.g., default text plus additional per-call instructions concatenated before calling .system(...)).

A per-call .advisors(...) is appropriate when a parameter (like which conversation ID a memory advisor should key off of) is only known at request time, or when a single call site needs an extra advisor (e.g., a stricter content filter) that shouldn't apply everywhere.

MIDQ53. Where should retry logic live for a flaky model call — inside the fluent chain per call, or elsewhere?

Retries belong at the ChatModel/HTTP client layer (or a resilience wrapper around it, like a Resilience4j retry policy configured on the underlying RestClient/WebClient), not hand-coded inside every ChatClient fluent chain. Baking retry loops into individual call sites duplicates logic, makes behavior inconsistent across the app, and conflates transient transport failures with genuine application-level errors that shouldn't be retried.

MIDQ54. What's the tradeoff of one shared ChatClient bean with heavy default advisors versus several lighter beans for different endpoints?

ROI: ★★★★☆ · Frequency: High

One heavy shared bean maximizes consistency and minimizes configuration duplication, but means every call pays the cost (latency, complexity) of advisors that not every endpoint actually needs — e.g., a health-check-style endpoint doesn't need a RAG advisor firing on every call. Several lighter, purpose-built beans give each endpoint exactly the pipeline it needs at the cost of some duplicated configuration and more beans to keep track of. The right balance usually groups endpoints by actual behavioral need rather than defaulting to either extreme.

MIDQ55. How would you test that a ChatClient's default system prompt is actually being applied, without mocking away the whole client?

ROI: ★★★☆☆ · Frequency: Medium

Mock only the underlying ChatModel.call(Prompt), capture the Prompt argument passed to it (via an ArgumentCaptor), and assert that its system message text matches (or contains) the expected default. This verifies the builder-level default actually reached the outgoing prompt, which a test that only checks the final response text would not catch.

MIDQ56. How would you propagate a request-scoped user id into a per-request advisor context parameter?

ROI: ★★★☆☆ · Frequency: Medium

chatClient.prompt()
    .advisors(a -> a.param("userId", currentUserId()))
    .user(question)
    .call()
    .content();

.advisors(a -> a.param(key, value)) attaches arbitrary context values to the request that any advisor in the chain can read — this is the standard mechanism for threading request-scoped data (user id, tenant id, conversation id) into advisors without changing the advisor's own construction or the bean's shared configuration.

MIDQ57. Why can't you mutate the defaults on an already-built ChatClient instance?

ROI: ★★★☆☆ · Frequency: Medium

A built ChatClient is deliberately immutable so that it can be safely shared and reused as a singleton across concurrent requests without synchronization — if defaults could be mutated post-construction, one request's customization could leak into or race with another's. Any change to defaults requires going back to a ChatClient.Builder (or a mutated copy via .mutate()/clone()) and building a new client, keeping configuration changes explicit and localized.

MIDQ58. How would you cleanly vary the system prompt based on a feature flag, without building a new ChatClient per call?

ROI: ★★★★☆ · Frequency: High

Keep one shared ChatClient bean with a neutral or minimal default, and pass the flag-dependent prompt text as a per-request .system(...) override chosen in your service logic (e.g., a switch on the flag value picking one of a few pre-defined prompt constants). This keeps the expensive-to-construct client singleton stable while letting the actual persona vary cheaply per call.

MIDQ59. Can you chain .entity() extraction on top of a .stream() call?

ROI: ★★★☆☆ · Frequency: Medium

No — structured entity conversion requires the complete response text to validate and deserialize it against the target type, which is fundamentally incompatible with a chunked, in-progress stream. .entity(...) is only available off .call(); if you need both streaming UX and eventual structured data, the common pattern is to stream a human-readable summary while separately issuing a non-streamed .call().entity(...) request for the structured payload.

SENIORQ60. Design a ChatClient configuration strategy for an application with five distinct AI features (support bot, summarizer, SQL copilot, code assistant, voice assistant). How many beans, and how do you factor shared versus feature-specific configuration?

ROI: ★★★★★ · Frequency: High at senior level

Start from a shared base builder (perhaps exposed as a package-private factory or a ChatClient.Builder post-processor) that carries genuinely universal defaults — a logging advisor, org-wide safety instructions, common retry/timeout options — then derive five distinct ChatClient beans from it via .mutate()/clone(), each layering its own system prompt, tools, and feature-specific advisors (memory for the support bot, a QuestionAnswerAdvisor for grounding the SQL copilot against schema docs, none of that for the stateless summarizer). The key discipline is keeping the shared base intentionally small — only what every feature truly needs — so that feature owners aren't fighting inherited defaults that don't fit their use case.

SENIORQ61. A junior developer is calling chatClientBuilder.build() inside a @RestController handler method on every request. What's wrong, and what is the cost?

ROI: ★★★★★ · Frequency: Extremely High at senior level

Rebuilding the client per request throws away the entire point of the builder/client split: ChatClient is meant to be constructed once and reused, since it's immutable and thread-safe by design. Rebuilding per request adds needless object-allocation and configuration-resolution overhead on every single request (advisor list assembly, options merging), and — more subtly — if the builder's defaults are themselves resolved from mutable external state (like a config bean fetched anew each time), you can get inconsistent behavior across "identical" requests. The fix is to build the client once, in a constructor or @Bean method, and inject/store the built instance as a field.

Interview Gold Point: Note that this is functionally the "new Random() per method call" anti-pattern, transplanted to Spring AI — recognizing the general shape of the mistake (conflating a one-time factory step with a per-invocation step) signals architectural maturity beyond rote Spring AI trivia.
SENIORQ62. How would you design integration tests for ChatClient-based services that need to be deterministic yet still exercise the real advisor pipeline?

ROI: ★★★★☆ · Frequency: High at senior level

Keep the real ChatClient, real advisor chain, and real memory/retrieval stores in the test, but substitute a deterministic stub or recorded-response ChatModel at the very bottom of the stack — for example, one that returns a fixed ChatResponse for a given input hash, or replays a previously captured real response ("VCR"-style fixture). This exercises every layer your code actually controls (prompt assembly, advisor ordering, entity conversion) while removing the one genuinely non-deterministic component (the live model), giving you fast, repeatable tests that still catch regressions in your own configuration.

SENIORQ63. Discuss the trade-offs of using .entity() for structured output versus relying on explicit JSON-mode or tool-calling for guaranteed schema compliance.

ROI: ★★★★☆ · Frequency: High at senior level

.entity() is convenient and works by injecting format instructions into the prompt, but ultimately relies on the model choosing to comply — it is a best-effort mechanism, not a hard guarantee, and less capable models can still emit malformed output. Provider-level JSON mode (when available) or presenting the target shape as a tool/function call tends to give stronger structural guarantees at the API level, at the cost of being less portable across providers and sometimes more restrictive in how the model can respond (e.g., no natural-language preamble). A senior-level answer weighs required reliability against portability: use .entity() for typical cases, but reach for JSON mode or tool-calling-as-schema when a downstream system cannot tolerate any malformed output.

SENIORQ64. How do you support different ChatOptions per user tier (e.g., free vs. premium gets a better model) using one shared ChatClient bean?

ROI: ★★★★☆ · Frequency: High at senior level

Keep a single bean with sensible baseline defaults, and resolve tier-specific ChatOptions in the service layer based on the authenticated user's tier, passing them via per-request .options(...). This keeps tier logic visible and testable in application code (where it's easy to reason about and evolve) rather than hidden inside the bean's construction, and avoids needing N beans for N tiers when the only difference is a couple of option fields.

SENIORQ65. How would you instrument a ChatClient bean for observability — latency, token counts, error rate per call site — without polluting every call site with metrics code?

ROI: ★★★★☆ · Frequency: High at senior level

Push the cross-cutting concern into a default advisor that wraps every call: it can record start/end timestamps for latency, read ChatResponse usage metadata for token counts, and catch/tag exceptions for error-rate metrics, tagging each recorded metric with a call-site identifier passed through as an advisor context param (e.g., a feature name). This keeps instrumentation centralized in one place while still letting metrics be broken down per feature, and it means new call sites get observability "for free" just by using the shared bean.

SENIORQ66. Design a fallback strategy for when .call().entity() throws or times out. How does this differ from designing retries at the ChatModel layer?

ROI: ★★★★☆ · Frequency: High at senior level

ChatModel-layer retries address transient transport failures (a dropped connection, a 5xx, a rate limit) and are agnostic to what the request even means. A fallback for .entity() failure is an application-level decision about degraded behavior when the model responded but didn't produce a valid structured shape — options include retrying once with an explicit repair instruction, falling back to the raw text response with a "structured extraction failed" flag for the caller to handle, or returning a safe default object. These sit at different layers and should be designed independently: retrying a malformed-but-successful response as if it were a network failure wastes a retry budget on a problem retries won't necessarily fix.

SENIORQ67. How would you architect a centralizing "PromptService" wrapper around ChatClient to standardize default system prompts and advisor stacking across a large codebase, while still allowing per-feature customization?

ROI: ★★★★★ · Frequency: High at senior level

Define a small internal factory/API (not a god-class) that exposes a method like forFeature(FeatureConfig config) returning a pre-configured ChatClient, built by cloning a shared base builder and layering the feature's own system prompt, advisors, and options. Centralize only what genuinely benefits from consistency — mandatory guardrail advisors, audit logging, org-wide safety text — and expose clear, typed extension points (a builder-style FeatureConfig) for what varies per team, rather than a single giant configuration class with conditional branches. The goal is that teams get consistent baseline behavior automatically while still owning their feature's persona and tools.

SENIORQ68. What are the thread-safety implications of using a ChatClient bean inside a reactive WebFlux application versus a traditional blocking MVC app?

ROI: ★★★☆☆ · Frequency: Medium-High at senior level

The ChatClient bean itself is equally safe to share in both models since it's immutable and each .prompt() call is independent. The difference is in how you consume the terminal result: in WebFlux you should exclusively use .stream() or wrap .call()'s blocking work appropriately (e.g., via Mono.fromCallable scheduled on a bounded elastic scheduler) to avoid blocking a Netty event-loop thread, whereas in blocking MVC calling .call() directly is fine since each request already runs on its own dedicated worker thread.

SENIORQ69. When migrating from a hand-rolled ChatModel-based client to ChatClient, what regressions or behavior changes should you watch for?

ROI: ★★★★☆ · Frequency: High at senior level

The most common surprise is that default advisors you configure (memory, retrieval) now silently inject additional context into every prompt, which can change model behavior in ways the old hand-rolled client never did — teams sometimes see responses become longer, slower, or subtly different in tone and mistakenly suspect a model regression when it's really new advisor-injected context. Also watch for differences in default option values (temperature, max tokens) between what the old client hard-coded and what the new builder's defaults resolve to, and verify that structured-output parsing (if newly using .entity()) has equivalent or better error handling than whatever bespoke JSON parsing it replaces.

SENIORQ70. How would you design a canary or A/B test between two different ChatClient configurations (different system prompts or models) in production?

ROI: ★★★★☆ · Frequency: Medium-High at senior level

Stand up both configurations as separate named ChatClient beans (or one bean plus a per-request options/system override chosen by the experiment logic), route a percentage of traffic to each via your existing feature-flag/experimentation framework, and make sure every call is tagged (via an advisor context param or logging) with which variant served it so downstream evaluation and metrics can be sliced by variant. Because LLM outputs are non-deterministic and quality is often subjective, the evaluation plan (what metric decides a winner — task success rate, user thumbs-up rate, cost per resolved query) needs to be defined before the experiment starts, not after looking at the outputs.

SENIORQ71. How do you guard against prompt injection at the ChatClient integration layer, specifically around how untrusted input is composed into .user(...)?

ROI: ★★★★☆ · Frequency: High at senior level

At the ChatClient level, the main discipline is never concatenating untrusted external content directly into the same string that carries system-level instructions — keep the system message (your trusted instructions) and the user message (untrusted input) as distinct fluent calls rather than string-building one blob, since some models weight system-role content more heavily against injected instructions embedded in user content. Beyond that, deeper mitigations (input sanitization advisors, output validation) are typically implemented as Advisors layered onto the chain rather than logic embedded in the call site itself — the ChatClient-level contribution is mainly disciplined message-role separation and not trusting .entity() output as if it were pre-validated just because it deserialized successfully.

SENIORQ72. How do you handle backward compatibility when changing a builder-level default system prompt that many call sites implicitly rely on?

ROI: ★★★☆☆ · Frequency: Medium-High at senior level

Treat the default system prompt as a versioned, shared contract: before changing it, audit which call sites rely on the current default implicitly (versus setting their own explicit .system(...) per call, which would be unaffected). Where feasible, introduce the new prompt behind a differently-named bean or a feature flag first, measure behavioral impact on the affected features, and only retire the old default once consumers have been migrated or explicitly opted in — silently changing a shared default out from under many call sites is how one team's prompt tweak becomes another team's unexplained regression.

SENIORQ73. Describe an approach to caching identical or near-identical ChatClient requests to reduce cost. Where should this caching live?

ROI: ★★★★☆ · Frequency: High at senior level

Caching is best implemented as an advisor wrapped around the call (checking a cache keyed on a normalized representation of the fully-assembled prompt before delegating downstream, and populating it with the response afterward) rather than scattered ad hoc caching logic in individual services — this way every feature using that ChatClient bean benefits consistently. Key design decisions include what to key on (exact prompt text is safest but has poor hit rates; semantic/embedding-based near-duplicate matching improves hit rate but risks returning a stale or subtly wrong cached answer for a "similar but different" question), and a sensible TTL given that a cached answer can become stale as underlying data changes.

SENIORQ74. How would you handle a multi-turn tool-calling conversation through the fluent API when the model requests a tool call mid-stream?

ROI: ★★★☆☆ · Frequency: Medium at senior level

ChatClient's .tools(...) mechanism handles the typical request/response tool-calling loop synchronously under .call() — the framework detects the tool-call request in the model's response, invokes your registered tool method, and re-submits the result to the model automatically, so application code usually doesn't need to manage that loop by hand. Tool calling mixed with true token-level .stream() is a more delicate case since a tool call typically needs to interrupt the stream, execute, and resume — where supported, this is handled by the framework's streaming tool-execution path, but teams should verify their specific model/provider combination's tool-calling-while-streaming support rather than assuming full parity with the blocking path.

SENIORQ75. How would you design contract tests to catch silent schema drift in .entity() output when the underlying model provider is upgraded?

ROI: ★★★☆☆ · Frequency: Medium at senior level

Maintain a small suite of representative prompts with known-good expected entity shapes (and, where relevant, expected value ranges or required fields), run them against the live provider on a schedule or as part of a pre-upgrade validation pipeline, and assert both successful deserialization and semantic sanity (not just "it parsed"). This is distinct from your regular unit tests (which mock the model) — it's specifically meant to catch the case where a model version upgrade silently changes output formatting habits in a way that breaks structured extraction for real users.

SENIORQ76. What's the operational risk of a single overloaded ChatClient bean being the sole dependency for many unrelated microservice endpoints?

ROI: ★★★★☆ · Frequency: Medium-High at senior level

Configuration sprawl and blast radius: as more unrelated features pile conditional logic onto one bean's defaults (special-casing behavior per caller), the bean becomes hard to reason about and any change risks unintended side effects on features whose owners didn't even know they depended on that shared configuration. It also concentrates operational risk — if that one bean's default advisor chain has a bug or the underlying model has an outage, every dependent feature fails simultaneously rather than in isolation. The fix generally isn't "never share a bean" but rather keeping the shared surface intentionally narrow and well-documented, splitting genuinely distinct use cases into their own beans as outlined in the multi-feature configuration strategy.

SENIORQ77. How would you structure default vs. per-call advisor configuration to support an instant "safe mode" kill switch that disables retrieval/memory app-wide?

ROI: ★★★★☆ · Frequency: Medium-High at senior level

Rather than hard-coding advisors directly into defaultAdvisors(...) at builder time, resolve the actual advisor list from a runtime-configurable source (a feature-flag-backed supplier consulted when the request is constructed, or advisors that internally check a flag and no-op when disabled) so a single configuration flip can strip retrieval/memory behavior from every call without a redeploy. This requires designing the bean construction to consult that dynamic source rather than freezing the advisor list permanently at application startup.

SENIORQ78. What do you need to account for when load-testing a ChatClient-backed feature — streaming vs. blocking, cold-start of advisor state?

ROI: ★★★☆☆ · Frequency: Medium at senior level

Blocking (.call()) load tests should measure end-to-end latency and thread/connection-pool saturation under concurrency, since each in-flight request holds a thread until the full response returns. Streaming (.stream()) load tests need different metrics — time-to-first-token versus total completion time, and backpressure behavior under many concurrent subscribers. Also account for any advisor with warm-up cost or state that fills up over the test run (a memory advisor's backing store growing, a cache advisor's hit rate improving over time) — a short load test can under- or over-estimate steady-state performance if it doesn't run long enough for that state to stabilize.

SENIORQ79. How would you design ChatClient bean scoping to support multi-tenant customization (different tenants need different system prompts/options) without one bean per tenant?

ROI: ★★★★☆ · Frequency: Medium-High at senior level

Keep a single shared bean with tenant-agnostic baseline defaults, and resolve tenant-specific system prompt text and options at request time from a tenant configuration store (database, config service), applying them via per-request .system(...) and .options(...) based on the current tenant context. One bean per tenant doesn't scale operationally (bean count grows with customer count, and every configuration change requires touching N beans); resolving tenant differences dynamically per request keeps the bean count constant while still allowing full customization.

SENIORQ80. When .entity() fails schema validation, do you retry with a repair prompt, fall back to raw text, or fail the request? Justify your choice.

ROI: ★★★★☆ · Frequency: High at senior level

There is no universally correct answer — it depends on how the structured output is consumed downstream. If the structured shape feeds an automated process with no human in the loop (e.g., populating a database record), failing loudly (or retrying once with a repair instruction, then failing) is safer than silently returning a degraded raw-text fallback that downstream code isn't expecting. If a human ultimately reads the response and structure was only a convenience (e.g., a suggested action alongside free text), falling back to raw text with a flag can preserve a usable response instead of a hard failure. The senior-level insight is recognizing that this is a product/reliability decision informed by the consumer, not a fixed rule.

SENIORQ81. How would you audit-log the exact prompt sent by ChatClient — after defaults and advisors are applied — for compliance, without adding logging code to every call site?

ROI: ★★★★☆ · Frequency: Medium-High at senior level

A logging advisor placed at (or near) the end of the advisor chain sees the fully-assembled Prompt right before it's handed to the ChatModel, which is exactly the point where "what was actually sent" is known — logging there (to an audit-appropriate sink, with any necessary redaction of sensitive fields) as a default advisor captures every call from that bean automatically. Placing it early in the chain instead would risk logging a pre-advisor-modification version of the prompt, which is not what compliance audits usually need.

SENIORQ82. Compare the cost/latency implications of chaining multiple sequential ChatClient calls (classify, then summarize) versus one call with a more complex structured entity.

ROI: ★★★☆☆ · Frequency: Medium at senior level

Two sequential calls pay for two full round trips (network latency twice, and the second call's input tokens include however much of the first call's output gets carried forward) but each step is simpler and easier to validate/debug independently. A single call with a richer .entity() target type (e.g., a record containing both a classification field and a summary field) pays for one round trip and can be cheaper and faster overall, but asks more of the model in one shot and makes partial failure harder to isolate (if the summary portion is wrong, you can't easily tell whether the classification portion was also compromised). The right choice depends on whether the two steps are genuinely independent (favoring separate calls, especially if one is cacheable or reusable) or tightly coupled (favoring one combined call).

SENIORQ83. How do you decide whether fluent-API glue code belongs in shared default configuration (builder) versus should stay explicit per call site?

ROI: ★★★★☆ · Frequency: Medium-High at senior level

Push something into shared defaults when it's genuinely invariant across call sites and its absence would be a bug everywhere (logging, mandatory safety instructions, a shared memory store) — that's where centralization pays off in consistency. Keep something explicit at the call site when it varies meaningfully per feature or is important for a reader of that specific code to see without having to go look up the bean's configuration elsewhere (a feature's particular system prompt nuance, a one-off options tweak). The failure mode to avoid in both directions is: too much in defaults makes behavior at any given call site opaque and hard to debug; too little in defaults means inconsistent, copy-pasted behavior across the app.

SENIORQ84. Describe a strategy to gradually deprecate a ChatClient bean's default configuration when introducing a v2 persona, without breaking existing call sites.

ROI: ★★★☆☆ · Frequency: Medium at senior level

Introduce the v2 configuration as a new, separately-named bean (or a clearly versioned qualifier) rather than mutating the existing bean's defaults in place, migrate call sites to the new bean incrementally, and monitor each migrated call site's behavior before proceeding to the next. Only once all call sites have moved (or a deliberate deadline has passed with stakeholders informed) should the old bean actually be removed — silently swapping the existing shared bean's defaults in place effectively force-migrates every caller simultaneously with no ability to roll back one caller independently of the rest.

STAFFQ85. Forty microservices in your organization each independently configure their own ChatClient beans with copy-pasted defaults. Propose an architecture to consolidate governance without recreating a monolith.

ROI: ★★★★★ · Frequency: High at staff level

Extract the copy-pasted configuration into a shared internal library (a thin "AI platform starter") that each service depends on, exposing a small typed configuration surface (mandatory guardrail advisors, audit logging, standard timeout/retry policy, org-approved model options) applied automatically via autoconfiguration, while leaving persona-specific concerns (system prompt, feature-specific tools) to each service's own code. STAFFQ86. Design a company-wide "ChatClient factory" library that enforces mandatory guardrail advisors and audit logging while still letting teams customize personas. What's your extension model?

ROI: ★★★★★ · Frequency: High at staff level

Expose a builder-of-builders: teams call something like PlatformChatClients.forFeature("support-bot"), which internally starts from a base ChatClient.Builder with mandatory advisors already attached in a fixed position in the chain (e.g., guaranteed to run first/last regardless of what the team adds), then returns a further-customizable builder-like object exposing only the safe extension points — add your own system prompt, add your own tools, add your own *additional* advisors that compose around the mandatory ones rather than replacing them. ROI: ★★★★☆ · Frequency: Medium-High at staff level

Signals that you actually need more than that include: teams independently reinventing the same non-trivial glue code (caching, entity-repair retries) that should clearly be shared; a recurring need to swap providers/models organization-wide in a way current bean wiring makes painful; or compliance requirements (consistent audit trails, guaranteed guardrails) that can't be reliably enforced through convention alone. ROI: ★★★★☆ · Frequency: Medium-High at staff level

Combine static and runtime signals: a lint rule or architectural test (e.g., ArchUnit) that flags ChatClient.Builder.build() being called outside of designated configuration classes catches the per-request-rebuild anti-pattern at code-review time before it ships; runtime metrics on ChatClient bean creation counts (which should be roughly constant, one per bean per application startup) versus request volume (which should not correlate 1:1 with new client construction) catch it in already-deployed code. For bypassing shared defaults, code review checklists plus periodic audits of production prompt logs (from the centralized audit-logging advisor) against the expected mandatory-advisor footprint are more reliable than trusting self-reported compliance, since the whole point of the misuse is that it's easy to do silently.

STAFFQ90. What's the governance trade-off in standardizing on .entity() for structured output across all AI features versus letting teams choose ad hoc JSON parsing?

ROI: ★★★☆☆ · Frequency: Medium at staff level

Standardizing gives you one place to improve error handling, one consistent behavior when structured extraction fails, and easier auditing of which features rely on structured output at all — valuable when you need to reason about reliability organization-wide. The cost is reduced flexibility for teams with genuinely unusual needs (a feature needing streaming structured output token-by-token, or a schema too dynamic for a fixed Java type), who may be tempted to work around the standard rather than extend it cleanly. The staff-level call is usually to standardize as the strong default while defining an explicit, reviewed escape hatch for documented exceptions, rather than either a rigid mandate or a free-for-all.

STAFFQ91. How would you architect disaster recovery for a ChatClient-dependent platform if the primary model provider has an outage? Where does failover logic live relative to ChatClient configuration?

ROI: ★★★★☆ · Frequency: Medium-High at staff level

Provider failover is a ChatModel-layer concern architecturally (routing to a secondary provider's ChatModel implementation when the primary is unhealthy), but ChatClient-level configuration needs to be designed so that swap is actually feasible in practice — meaning system prompts, options, and expected output shapes shouldn't be so tightly coupled to one provider's specific quirks that a secondary provider's ChatClient can't serve the same request shape acceptably. Practically this means maintaining a secondary ChatClient bean pre-configured against a backup provider, a health-check-driven router in front of both, and periodically testing the failover path (not just building it and hoping) since an untested failover path at 2am during an actual outage is a common way disaster recovery plans fail in practice.

STAFFQ92. A staff engineer proposes replacing many individual ChatClient beans with one mega-bean whose configuration is resolved dynamically per call via a strategy pattern. Evaluate the proposal and give your recommendation.

ROI: ★★★★★ · Frequency: High at staff level

The proposal trades compile-time clarity for runtime flexibility: one mega-bean with a strategy-resolved configuration can reduce bean-declaration boilerplate and make cross-cutting changes easier to apply uniformly, but it also means you can no longer tell what a given feature's ChatClient configuration is by reading its dependency graph — you have to trace through the strategy resolution logic at runtime, which is a real cost for debugging, onboarding, and static analysis (an ArchUnit-style audit of "which advisors does the support bot use" gets much harder). The pragmatic recommendation is usually a middle ground: keep distinct, explicitly-named beans for genuinely distinct use cases (readable, testable, greppable), but use a shared factory/strategy internally to eliminate the copy-paste between them — getting the flexibility benefit of the strategy pattern in how beans are built, without sacrificing the clarity benefit of each feature having its own discoverable bean.

  • ChatClient is Spring AI's fluent, provider-agnostic entry point built on top of ChatModel, giving application code ergonomic prompt construction, a pluggable Advisor pipeline, and flexible response conversion (text, typed objects, streams).
  • Its API shape deliberately mirrors Spring's own WebClient/RestClient evolution: a builder for configuration-time defaults, an immutable client for reuse, and a request-spec/response-spec pair around each call.
  • Internally, every call assembles a Prompt, runs it forward through an ordered Advisor chain, delegates to the underlying ChatModel, and runs the response back through that same chain in reverse — structurally identical to a servlet filter chain or AOP advice.
  • Structured output via .entity(Type.class) is a two-sided feature: it shapes the outgoing prompt with format instructions and parses the incoming response against your Java type — not simple post-hoc string parsing.
  • ChatClient should be built once as a singleton per logical persona/use case; retries and provider resiliency belong one layer down at the ChatModel, not inside the client's Advisor pipeline.
  • Because it is the seam where trusted instructions and untrusted content are combined into one prompt, ChatClient is also where prompt-injection risk must be actively managed — through careful message boundaries and Advisor-level sanitization, not left to the model.
