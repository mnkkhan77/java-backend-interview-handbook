CHAPTER 38 — OBSERVABILITY

Volume 2 — Spring AI · Chapter 13 of 15

The MCP Integration chapter gave your application the ability to reach out — through a standard protocol — to tools, resources, and other agents it does not own. That is a strict increase in the number of moving parts between a user's question and a final answer: a model call, a tool discovery round trip, one or more remote tool invocations, and a synthesis step, potentially chained across several MCP servers you do not control. The moment you have that many hops, "it worked in my local test" stops being useful information, because you cannot know which hop was slow, wrong, expensive, or silently degraded without instrumenting the system to tell you. Observability is the discipline that turns "the agent gave a bad answer" from a mystery into a five-minute investigation.

1. MOTIVATION

Every earlier chapter in this volume has been about making your Spring Boot application do more with AI — call a model, hold a conversation, retrieve context, call tools, talk to MCP servers. This chapter is about something different and, for anyone who intends to run this in production, more important: knowing what actually happened after it happened. Traditional backend observability was built around a comfortable assumption you have relied on for years — a request either succeeds or throws, and when it throws, a stack trace tells you exactly which line of code is at fault. AI-infused systems break that assumption in a specific, uncomfortable way: the most expensive, most damaging failures are the ones that return HTTP 200 with a perfectly well-formed, confident, wrong answer.

Concretely, once your application is calling a foundation model, you now have a component whose behavior can drift across model provider updates you did not request, whose cost varies token-by-token with every user's phrasing, whose latency is dominated by a network call to infrastructure you don't operate, and whose correctness cannot be checked with a simple equality assertion. If you cannot answer, for any given production request, questions like "which model version answered this," "how many tokens did this cost," "how long did the retrieval step take versus the generation step," "did a tool call fail and get silently retried," and "is this week's average response quality worse than last week's" — you are not running an AI system, you are running a black box with a Spring Boot label on it. Observability is what converts the box back into an inspectable system.

There is a second, more strategic reason this chapter sits here, right before Testing (Chapter 39) and the closing chapters of this volume. Testing an LLM-backed feature with pre-production test suites alone was already shown, in earlier chapters, to be necessary but insufficient — the space of real user inputs is larger than any test suite you will write. Observability is the mechanism that closes that gap: it is testing that never stops, running continuously against real traffic, catching the failure modes your test suite never imagined because it is watching the actual distribution of what users say, not the distribution you guessed at design time.

2. HISTORICAL BACKGROUND

2.1 From Log Files to the Three Pillars

Backend observability did not arrive fully formed. Early systems had exactly one tool: the log file, grepped by hand after something broke. As systems grew distributed, this stopped scaling — a single user request might touch a dozen services, and no single log file contained the whole story. The industry converged, over roughly two decades, on what became known as the three pillars of observability: logs (discrete, timestamped events, good for "what exactly happened at this moment"), metrics (aggregated numeric time series, good for "how is the system behaving on average, right now, and is it trending"), and traces (the causal chain of spans showing how a single request propagated across services, good for "where did the time and the failure actually happen inside this one request"). Tools like Prometheus (metrics), the ELK stack (logs), and Zipkin/Jaeger (traces) each grew up to serve one pillar, and Micrometer emerged in the Java ecosystem specifically to give Spring Boot applications a single, vendor-neutral instrumentation API that could export to any of these backends.

2.2 OpenTelemetry: One Instrumentation Standard

The next major shift was consolidation. Each observability vendor originally shipped its own proprietary instrumentation agent, which meant switching vendors meant re-instrumenting your entire codebase. OpenTelemetry (OTel), formed by merging two earlier projects (OpenTracing and OpenCensus), became the industry-standard, vendor-neutral specification and SDK for producing traces, metrics, and logs, with a well-defined wire protocol (OTLP) that any backend can ingest. Spring's own observability story — Micrometer for metrics and Micrometer Tracing for distributed traces — is designed to bridge cleanly into OpenTelemetry, so a Spring Boot application can be instrumented once and shipped to Prometheus, Grafana, Zipkin, Jaeger, Datadog, or any OTLP-compatible backend without touching business code.

2.3 The Missing Fourth Pillar: LLM-Specific Observability

None of the three pillars above were designed with "a single request can cost a variable amount of money depending on how many tokens the model decided to generate" in mind, nor with "the same input can legitimately produce a different output on every call" in mind. As LLM-backed applications went into production starting around 2022–2023, teams discovered that standard APM dashboards — request count, latency, error rate — were necessary but silent on the questions that actually mattered for AI features: token consumption and cost per request, prompt and completion content for debugging quality regressions, which retrieved documents fed into a given answer, and whether a chain of tool calls terminated correctly or looped. This gap produced a new category of purpose-built tooling (LangSmith, Langfuse, Traceloop/OpenLLMetry, Arize Phoenix, among others) built specifically to capture prompts, completions, token usage, and evaluation scores as first-class observability data — and it produced a standardization effort inside OpenTelemetry itself: the GenAI semantic conventions, a set of standard span and attribute names (prefixed gen_ai.*) so that "which model," "how many input tokens," and "how many output tokens" are captured the same way regardless of vendor. Spring AI's own observability support, covered in depth later in this chapter, is built directly on top of this convention.

This means an AI-specific request shows up in the exact same Grafana dashboard, the exact same trace waterfall in Zipkin, and the exact same alerting pipeline as everything else your platform team already operates — you are extending existing infrastructure, not standing up a second one.

3. PROBLEM STATEMENT

Given a production system whose core component (a foundation model call) is non-deterministic, has variable and non-trivial per-request cost, and can fail silently by returning a plausible-but-wrong answer — instrument that system so that engineers can, after the fact and in real time, reconstruct exactly what happened, how much it cost, how long each stage took, and whether the output was trustworthy, without re-running the request.

Unpack the constraints in that statement, because each one rules out an approach that would work fine for ordinary CRUD services. "Non-deterministic" means you cannot debug by simply re-running the same request in a debugger and expecting the same trace — you must capture enough context at the time of the original call that you never need to reproduce it. "Variable, non-trivial per-request cost" means cost itself becomes a first-class metric you must track per request, per user, and per feature, the same way you would track latency — this did not exist as a concern for a typical REST endpoint. "Fails silently with a plausible-but-wrong answer" means your instrumentation cannot rely purely on exceptions and HTTP status codes as the failure signal; you need to capture the actual prompt and response content (subject to the privacy constraints covered in Section 13) so a human, or an automated evaluator, can judge quality after the fact.

There is a second, structural half of this problem that is easy to under-scope: a real AI feature, as built across this volume, is a pipeline — retrieval, prompt construction, advisor chain, the model call itself, possibly one or more tool invocations, and response post-processing. Observability must attribute latency and cost to the correct stage of that pipeline, not just to the endpoint as a whole, or you will be staring at "this request took 4 seconds" with no way to tell whether 3.8 of those seconds were the vector search, the model, or a flaky downstream tool.

4. THEORY

4.1 The Three Pillars, Refreshed for This Domain

You already know logs, metrics, and traces conceptually from ordinary backend work — the theory does not change, only the payload does.

  • Logs in an AI context capture discrete events with rich, often large payloads: the exact prompt sent, the exact completion received, which advisor modified the request, which tool was invoked with what arguments. Spring AI's SimpleLoggerAdvisor exists specifically to produce this kind of log entry for every ChatClient call.
  • Metrics capture numeric time series you aggregate and alert on: request count, latency percentiles, token counts (prompt and completion, tracked separately because they are priced and behave differently), error rate, and cost. These are cheap to store and query at high volume precisely because they are aggregated — you lose the individual request's content, in exchange for being able to ask "is p95 latency degrading this week" cheaply across millions of requests.
  • Traces capture the causal, hierarchical shape of a single request as a tree of spans — one span for the incoming HTTP request, a child span for retrieval, a child span for the model call, a child span for each tool invocation. A trace answers "where, inside this one specific slow or failed request, did the time actually go," which no amount of aggregated metrics can answer on its own.

4.2 The Fourth Pillar: Evaluation Signal

An AI-specific addition sits alongside the three classical pillars: quality/evaluation telemetry — a numeric or categorical signal representing "was this response good," produced either by an automated judge (an LLM-as-judge pattern, covered in depth in the Evaluation chapters of this series), a heuristic (did the response contain a refusal, did structured output parse successfully), or explicit user feedback (a thumbs up/down button). This is not optional polish; without it, your logs and traces can tell you the system was fast and cheap while it was quietly producing wrong answers, because "fast, cheap, and 200 OK" says nothing about correctness. Mature AI observability platforms treat this evaluation signal as a metric you can slice by model version, prompt version, or retrieval configuration — the same way you would slice error rate by deployment version in ordinary APM.

4.3 Spans, Traces, and Context Propagation — Mental Model

A span is a single named, timed unit of work with a start time, an end time, a set of key-value attributes ("tags"), and a parent-child relationship to other spans. A trace is simply the full tree of spans that share one root — the entire life of one incoming request, end to end, across every internal hop. The mechanism that makes this tree assembleable after the fact, even across network calls to other services, is context propagation: a trace ID and the current span ID are carried along — inside the current thread via a context object, and across process boundaries via HTTP headers (typically the traceparent header defined by the W3C Trace Context standard) — so that a span created deep inside a tool call, in a different service, still knows which trace it belongs to and which span is its parent. Micrometer Tracing and OpenTelemetry both implement this propagation automatically for common transports (Spring's RestClient/WebClient, message brokers, and so on), which is precisely why Spring AI's instrumentation "just works" as part of an existing trace rather than starting an unconnected trace of its own.

4.4 Cardinality — the Concept That Will Bite You If You Skip It

Cardinality is the number of distinct values a given tag/attribute can take. A tag like http.status has low cardinality (a handful of values); a tag like user.id or, critically for this chapter, the full prompt text, has effectively unbounded cardinality. Metrics backends like Prometheus create a new, separately-stored time series for every unique combination of tag values, so attaching a high-cardinality value (a full prompt, a user ID, a session ID) as a metric tag can silently multiply your storage and query cost by orders of magnitude or crash your metrics backend outright — this single concept explains why Spring AI's Observation API deliberately separates low-cardinality key values (safe for metrics: model name, operation type, provider) from high-cardinality key values (safe only for traces/logs, never for metrics: the actual prompt content, token-level detail).

5. INTERNAL WORKING

Walk through what actually happens, mechanically, when a Spring AI application configured with observability makes one ChatClient call inside a request that already has tracing enabled (the default in a Spring Boot application with the Actuator and Micrometer Tracing starters on the classpath).

  1. A trace is already in flight. The incoming HTTP request was intercepted by Spring's tracing instrumentation, which created a root span and stored the current Observation/trace context in a thread-local (or reactor context, for WebFlux) so that anything called from within this request can find it.
  2. Your controller calls chatClient.prompt().user(question).call().content(). Internally, Spring AI's ChatClient does not call the model directly — it goes through an Advisor chain (the same Advisor abstraction covered in the Advisors chapter). Each advisor in the chain — memory, retrieval augmentation, logging, your own custom advisors — gets a chance to inspect or modify the request before it reaches the model, and the response before it returns to the caller.
  3. An Observation is opened for the chat client call. Spring AI wraps the call in a Micrometer Observation, using a purpose-built ChatClientObservationConvention that knows how to translate a chat request/response pair into observation key-values — this is the integration point that makes the AI-specific call look, to Micrometer, like any other observed operation (a database query, an HTTP client call) that your existing tracing and metrics backends already know how to render.
  4. The underlying ChatModel call is separately observed. Because the Advisor chain can retry, branch, or call the model more than once (for example, during tool-calling loops), the actual model invocation gets its own nested Observation/span via ChatModelObservationConvention, distinct from the outer ChatClient span. This nesting is what lets a trace waterfall show "the ChatClient call took 2.1s, of which the underlying model call took 1.9s, and the memory-advisor lookup took 0.2s" as separate, attributable spans.
  5. Low-cardinality attributes are attached as tags on both the span and any generated metrics — gen_ai.system (the provider, e.g. openai), gen_ai.request.model, gen_ai.response.model (these can differ if the provider silently routes to a different underlying model version), and the operation name. High-cardinality attributes — the actual prompt and completion text, if you have opted in to capturing them — are attached only to the trace span's detailed view or to a log record, never to the metrics time series, for the cardinality reason explained in Section 4.4.
  6. Token usage is read off the model response's metadata — every ChatResponse carries a ChatResponseMetadata object with a Usage object exposing prompt tokens, generation (completion) tokens, and total tokens, as reported by the provider. Spring AI's observation support surfaces these as observation key-values (gen_ai.usage.input_tokens, gen_ai.usage.output_tokens) so a Micrometer meter can aggregate them into token-consumption metrics without you writing any counting code yourself.
  7. The Observation closes, emitting to every registered ObservationHandler. A TracingObservationHandler turns it into a span exported via OTLP (to Zipkin, Jaeger, or an OpenTelemetry Collector); a MeterObservationHandler turns it into Micrometer counters/timers exported to Prometheus or another metrics backend. Both happen from the exact same instrumentation call site — you do not write separate code for "log this" and "trace this" and "meter this."
  8. If the model call throws (timeout, rate limit, malformed response), the Observation is marked as an error, the exception is attached to the span, and standard Micrometer error-count metrics increment — this is the one failure mode that behaves exactly like ordinary APM, because it is an actual exception, not a silent wrong answer.

The edge case worth reasoning through yourself: what happens during streaming responses (ChatClient.stream())? The Observation's span cannot close until the last chunk has been emitted, because token counts and final response metadata are only known once the stream completes — this means a streaming call's span duration reflects "time to fully drain the stream," not "time to first token," and if you care about perceived latency (a UX metric that matters a great deal for chat interfaces) you need a separate, custom-instrumented measurement for time-to-first-token, since the standard span will not give it to you for free.

6. MATHEMATICS

Observability for AI systems needs very little formal mathematics, but the handful of ideas it does need are used constantly and are worth being precise about.

6.1 Percentiles, Not Averages

The average (mean) latency of your model calls is one of the least useful numbers you can report, because LLM latency distributions are heavily right-skewed: most calls finish quickly, but a meaningful tail takes far longer (provider-side queuing, longer generations, retries). Reporting only the mean hides that tail completely. Instead, observability systems report percentiles: p50 (median — half of requests are faster than this), p95 and p99 (95%/99% of requests are faster than this — these numbers surface the tail your users actually experience during the worst moments). Micrometer computes these via histogram-based Timer instruments attached to each Observation, and the formula intuition is simple: sort all observed latencies, and the p-th percentile is the value at position p/100 × N in that sorted list (implementations approximate this with bounded-memory histograms rather than storing every raw value, since storing every raw value at production scale is not memory-feasible).

6.2 Cost as a Linear Function of Tokens

Per-request cost is not mysterious — it is a simple linear function most providers price directly: 

cost(request) = (prompt_tokens  × price_per_input_token)
              + (completion_tokens × price_per_output_token)

The reason this belongs in an observability chapter rather than a pure finance spreadsheet is that prompt_tokens and completion_tokens are exactly the two numbers your instrumentation is already capturing per request via Usage metadata (Section 5). Once you are emitting those two numbers as metrics tagged by model and by feature/endpoint, computing running cost is a Grafana query, not a new engineering effort — this is the single highest-leverage dashboard most teams build in their first week of running an AI feature in production, because it is the earliest warning of a runaway agent loop or an unexpectedly verbose system prompt.

6.3 Sampling Math for Traces

Tracing every single request in full detail (especially with high-cardinality prompt/completion content attached) is expensive to store and, at high volume, unnecessary. Sampling trades completeness for cost: if you sample at rate r (say, 10% = 0.1), you retain full traces for a random r fraction of requests while still counting all requests toward aggregate metrics (metrics and traces are typically decoupled for exactly this reason — you never want to lose your error-rate metric just because you are only tracing 1 in 10 requests). A common refinement is tail-based sampling: buffer a trace's spans temporarily and decide whether to keep it only after seeing whether it errored or exceeded a latency threshold — guaranteeing that the requests most worth debugging are never the ones a flat random sample happened to drop.

Two design decisions in this architecture recur across almost every real deployment. First, PII redaction happens at the Collector, not in every individual service — centralizing it means you enforce one redaction policy instead of trusting every team to remember to scrub before exporting. Second, the "quality" pipeline on the bottom is deliberately decoupled from the real-time metrics pipeline: automated LLM-as-judge evaluation is itself a model call, with its own latency and cost, so it runs asynchronously against a sampled subset of production traffic rather than blocking the user-facing request.

9. JAVA / SPRING PERSPECTIVE

Spring AI's observability is not a bolt-on — it is built directly on the same io.micrometer.observation API that Spring Boot Actuator already uses for HTTP server requests, RestClient calls, and R2DBC/JDBC queries. If your application already has spring-boot-starter-actuator plus a Micrometer Tracing bridge (micrometer-tracing-bridge-otel, typically) and a metrics registry (micrometer-registry-prometheus) on the classpath, Spring AI's ChatClient and ChatModel calls are observed automatically the moment you inject an ObservationRegistry bean — no extra annotation is required on your own code. 

// build.gradle / pom.xml dependencies (conceptually):
//   spring-boot-starter-actuator
//   micrometer-tracing-bridge-otel
//   micrometer-registry-prometheus
//   opentelemetry-exporter-otlp   (or a Zipkin exporter)

@Configuration
class ObservabilityConfig {

    // ObservationRegistry is auto-configured by Spring Boot when Actuator
    // + Micrometer are on the classpath; injecting it here is enough for
    // Spring AI's ChatClient/ChatModel beans to pick it up automatically.

    @Bean
    ObservationRegistryCustomizer<ObservationRegistry> addTraceIdLogging() {
        // Example customizer: attach any cross-cutting handler you need,
        // e.g. a handler that copies trace/span IDs into MDC for log
        // correlation, so every log line for a request carries the same
        // trace_id a Zipkin/Jaeger trace uses.
        return registry -> registry.observationConfig()
            .observationHandler(new ObservationTextPublisher());
    }
}

@Service
class SupportAssistant {

    private final ChatClient chatClient;

    SupportAssistant(ChatClient.Builder builder) {
        this.chatClient = builder
            .defaultAdvisors(new SimpleLoggerAdvisor()) // logs request/response
            .build();
    }

    public String answer(String question) {
        ChatResponse response = chatClient.prompt()
            .user(question)
            .call()
            .chatResponse();

        Usage usage = response.getMetadata().getUsage();
        log.info("model={} promptTokens={} completionTokens={} totalTokens={}",
            response.getMetadata().getModel(),
            usage.getPromptTokens(),
            usage.getGenerationTokens(),
            usage.getTotalTokens());

        return response.getResult().getOutput().getText();
    }
}

A few Spring AI-specific mechanics worth naming precisely, because interviewers and code reviewers will expect the correct vocabulary:

  • SimpleLoggerAdvisor is a ready-made Advisor (from the Advisors chapter's family of CallAdvisor/StreamAdvisor implementations) that logs the outbound request and inbound response of every ChatClient call it wraps — the fastest way to get human-readable request/response logs without writing a custom advisor.
  • ChatClientObservationConvention and ChatModelObservationConvention are the extension points that decide which key-values get attached to the ChatClient-level and the underlying ChatModel-level Observations respectively — implement a custom convention when you need to add your own low-cardinality tags (for example, a feature.name tag identifying which product feature triggered the call) without touching every call site.
  • ChatResponseMetadata / Usage (in org.springframework.ai.chat.metadata) is the standard, provider-agnostic surface for reading token counts and the actual model identifier that answered — because Spring AI normalizes this across providers, your dashboards and cost calculations don't need provider-specific branches.
  • Actuator's /actuator/metrics and /actuator/prometheus endpoints expose everything above without you writing a controller — the same endpoints you already use for JVM heap and HTTP metrics now also expose gen_ai.*-derived counters and timers.

This is the same design philosophy this series keeps returning to: Spring AI treats "observing a model call" as a specialization of "observing any external dependency," using the exact same Observation abstraction Spring Boot already applies to your database and HTTP clients — you are not learning a second observability stack, you are learning what tags a familiar one now carries.

10. BEST PRACTICES

  • Always tag metrics and traces with model name, model version, and prompt/feature version. Without this, you cannot answer "did the provider's silent model update at 3am cause this week's quality drop" or "did prompt v14 regress cost versus v13" — both are routine production questions.
  • Track token usage and cost as first-class metrics from day one, not as an afterthought computed from a billing invoice at month-end. Per-feature, per-user cost attribution is the earliest and cheapest warning system for a runaway agent loop or a prompt regression that suddenly triples token usage.
  • Separate low-cardinality tags (safe for metrics) from high-cardinality payloads (safe only for traces/logs), exactly as Spring AI's Observation conventions do — never let a full prompt string become a metric tag.
  • Correlate logs, traces, and metrics via a shared trace ID propagated into your logging MDC, so a single click from a trace waterfall takes you straight to the exact log lines for that request.
  • Sample intelligently, not uniformly — keep 100% of error and high-latency traces (tail-based sampling), and only randomly downsample the "boring," fast, successful traffic.
  • Instrument time-to-first-token separately from total response time for any streaming/chat UX, since users perceive the former, not the latter, and standard span duration measures the latter.
  • Build a continuous, sampled evaluation pipeline (Section 4.2) alongside classical observability — a system can be fast, cheap, and error-free while still being wrong, and only quality telemetry catches that.

11. COMMON MISTAKES

  • Logging or tagging with raw prompt/completion text as a metrics label. This explodes cardinality (Section 4.4) and can crash or bankrupt a metrics backend; prompt/completion content belongs in traces or dedicated log storage, never in a Prometheus label.
  • Treating "no exception thrown" as "the request succeeded." A malformed structured-output response, a hallucinated fact, or a tool call that silently returned stale data all complete without throwing — this is precisely why quality/evaluation telemetry (Section 4.2) is not optional.
  • Only monitoring the outer request latency, not per-stage latency. Without child spans for retrieval, each model call, and each tool call, "this endpoint is slow" gives you no actionable next step — as the trace waterfall in Section 7.1 demonstrated.
  • Shipping full prompts and completions to a third-party trace/log backend without redaction. This is both a security issue (Section 13) and, in regulated industries, a compliance violation if the prompt contains customer PII or regulated data.
  • Forgetting that streaming responses distort duration-based metrics. A naive span-duration metric for a streamed chat response measures "time to fully drain the stream," which can look artificially slow compared to perceived UX, misleading whoever is reading the dashboard.
  • Ignoring provider-side model drift because dashboards only track your own deploys. If you don't tag and monitor gen_ai.response.model, a provider's silent version bump behind a stable model alias can change behavior with no corresponding entry in your own deployment history to investigate.

12. PERFORMANCE CONSIDERATIONS

Observability itself has a cost, and it is worth being honest about the trade-offs rather than instrumenting everything unconditionally.

  • Tracing overhead is small but non-zero — creating spans, propagating context, and serializing/exporting them consumes CPU and adds a small amount of latency per request, which is why high-throughput systems sample rather than trace every request at 100%.
  • Capturing full prompt/completion payloads multiplies storage cost fast. A chat feature at meaningful scale can generate gigabytes of prompt/completion text per day; decide deliberately what fraction of traffic gets full-payload capture versus metrics-only visibility, and set retention windows accordingly (you rarely need full-text traces older than a few weeks).
  • Synchronous evaluation adds latency you usually cannot afford. Running an LLM-as-judge quality check inline, before responding to the user, doubles your model-call latency and cost for every request — this is why quality evaluation, as shown in Section 8's architecture, almost always runs asynchronously against sampled traffic rather than in the request's critical path.
  • Token/cost metrics are nearly free to compute because the numbers are already present in the response metadata (Section 5) — there is essentially no performance argument against tracking them, only an implementation-effort one, which is small.
  • Batching and buffering exporters matters at scale. Sending one network call per span/metric to your Collector will itself become a bottleneck; production exporters batch spans and metrics before sending, trading a small amount of export latency for a large reduction in network overhead.

13. SECURITY CONSIDERATIONS

Observability data is, itself, a security and privacy surface that is easy to overlook because it feels like "internal engineering plumbing" rather than user data — but a trace that captures a full prompt containing a customer's account number, medical detail, or an internal system prompt with embedded credentials is exactly as sensitive as the request that produced it, and it is now duplicated into a third-party observability backend with its own access controls, retention policy, and export logs.

  • Redact before export, not after. PII scrubbing should happen as close to the source as possible — ideally in an OpenTelemetry Collector processor or a custom ObservationFilter — so raw sensitive content never leaves your infrastructure boundary in the first place.
  • Treat system prompts as secrets in traces, the same way you treat API keys as secrets in logs. A system prompt often encodes business logic, guardrail instructions, or proprietary process detail — leaking it through an over-permissive trace viewer is a real, if underappreciated, information-disclosure risk, and it directly enables the prompt-injection and prompt-extraction attacks covered in earlier chapters.
  • Apply the same access control to your observability backend that you apply to production databases. A trace viewer with prompt/completion capture enabled is, functionally, a searchable archive of everything users have told your AI feature — it deserves the same RBAC and audit logging as any datastore holding user content.
  • Watch for injected content surfacing in your own telemetry. If an attacker's prompt-injection payload gets logged verbatim and later rendered unescaped in an internal observability dashboard, you have created a second-order injection surface (e.g., stored XSS in a web-based trace viewer) — treat observability tooling as untrusted-content-rendering surfaces too.
  • Be honest that this is a moderate, not extreme, security surface. Observability data is a confidentiality and compliance concern, not typically a direct remote-code-execution vector — the bulk of the security burden in an AI system still sits with input validation, guardrails, and sandboxing covered in dedicated later chapters; this chapter's job is narrowly to make sure your telemetry pipeline doesn't become the leak.

14. INTERVIEW QUESTIONS

JUNIORQ1. What are the three classical pillars of observability, and what does each one answer?

ROI: ★★★★★ · Frequency: Extremely High

Logs (discrete timestamped events — "what exactly happened"), metrics (aggregated numeric time series — "how is the system behaving on average, and is it trending"), and traces (the causal tree of spans for one request — "where inside this specific request did time/failure occur"). Each is optimized for a different question and a different storage/query trade-off.

JUNIORQ2. Why isn't "the request returned HTTP 200 with no exception" sufficient evidence that an AI feature worked correctly?

ROI: ★★★★☆ · Frequency: High

Because an LLM can produce a fluent, well-formatted, confident answer that is factually wrong or based on a misread of retrieved context — this completes successfully at the HTTP and exception-handling level while still being a functional failure. Standard error-rate monitoring cannot catch this; it requires a separate quality/evaluation signal.

MIDQ3. What is cardinality, and why does it matter specifically when instrumenting LLM calls?

ROI: ★★★★★ · Frequency: Extremely High

Cardinality is the number of distinct values an attribute/tag can take. Metrics backends like Prometheus create a separate stored time series per unique tag-value combination, so attaching a high-cardinality value — a full prompt string, a user ID, a session ID — as a metric tag can multiply storage/query cost by orders of magnitude or crash the backend. This is why prompt/completion content belongs only in traces or logs, never as a metric label, and why Spring AI's Observation conventions explicitly separate low-cardinality and high-cardinality key-values.

MIDQ4. How would you compute the cost of a given LLM request from telemetry alone, without calling the provider's billing API?

ROI: ★★★★☆ · Frequency: High

Cost is a linear function of token usage: (prompt_tokens × price_per_input_token) + (completion_tokens × price_per_output_token). Since token counts are already reported per response via the model's usage metadata (Spring AI exposes this as a Usage object on ChatResponseMetadata, with prompt, generation, and total token counts), you multiply by the known per-token pricing for that model and tag the result by model/feature to get per-request and aggregate cost, no billing API call required.

SENIORQ5. Design the observability strategy for a production RAG + tool-calling agent. What would you trace, what would you meter, and what would you sample?

ROI: ★★★★★ · Frequency: High at senior level

Trace the full request as a span tree: retrieval (with vector store and top-k as tags), each advisor in the chain, each model call as its own span (since tool-calling can trigger multiple sequential model calls), and each tool invocation with success/failure and latency. Meter, per feature and per model: request count, latency percentiles (p50/p95/p99, not mean), token usage split into input/output, error rate, and tool-call failure rate — all tagged with low-cardinality values only (model name, model version, feature name), never raw prompt content. Sample with a tail-based strategy: retain 100% of error and high-latency traces, and randomly downsample fast, successful traffic to control storage cost, while keeping metrics unsampled (all requests counted) since metrics are cheap regardless of volume.

Interview Gold Point: Add that you would run a separate, asynchronous quality-evaluation pipeline against a sampled subset of production traffic (LLM-as-judge or rubric-based scoring) precisely because a fast, cheap, error-free trace tells you nothing about correctness — and that this evaluation pipeline must not sit in the user-facing request's critical path, since it is itself a model call with its own latency and cost.
SENIORQ6. A user reports that an agent-based feature "felt slow" yesterday around 3pm, but your average latency dashboard shows nothing unusual. How do you investigate?

ROI: ★★★★☆ · Frequency: Medium-High

Averages hide right-skewed tail latency, which is exactly the kind of distribution LLM and tool-call latency produces — a handful of very slow requests can be invisible in a mean while being exactly what one specific user experienced. Pivot to p95/p99 latency around 3pm, filter traces by time window and, if you have user/session tagging on traces (not metrics, to avoid cardinality blowup), find that user's specific trace. Walk the span waterfall for that trace to identify which stage — retrieval, a specific model call, or a specific tool invocation — accounted for the outlier duration, then check whether it correlates with a provider-side incident, a tool dependency timeout, or an unusually long generation (high output token count).

STAFFQ7. A platform team wants to standardize AI observability across a dozen microservices, some using different model providers. What architecture and standards would you push for, and why?

ROI: ★★★★★ · Frequency: High at staff level

Push for OpenTelemetry as the wire-level standard and the GenAI semantic conventions (gen_ai.* attribute names) as the attribute schema, so every service — regardless of provider or even language — emits comparable telemetry that a single set of dashboards and alerting rules can consume. In the Spring/Java services specifically, standardize on Spring AI's Observation-based instrumentation (via a shared, organization-wide ChatClientObservationConvention/ChatModelObservationConvention customization) so every team gets consistent low-cardinality tagging (feature name, model, prompt version) without re-inventing it per service. Route all telemetry through a central OpenTelemetry Collector that performs PII redaction once, centrally, rather than trusting a dozen teams to redact correctly and independently. Keep token/cost metrics and quality-evaluation scores as first-class, cross-team-comparable metrics from day one, since these become the basis for capacity planning and vendor/model comparisons across the whole platform, not just per-service debugging.

STAFFQ8. How does observability change the way you would think about testing an AI feature (previewing the relationship to the next chapter)?

ROI: ★★★★☆ · Frequency: Medium at staff level

Pre-production test suites can only exercise inputs someone anticipated writing a test for, but the real distribution of user inputs to an LLM-backed feature is unbounded — so testing alone is necessarily incomplete for this class of system. Observability, especially the quality/evaluation telemetry pillar, functions as continuous testing against the real, live input distribution: it catches regressions and failure modes a static test suite never imagined, feeds real production failures back into the test suite (turning "surprises in production" into "regression tests going forward"), and gives you the evidence needed to know whether a prompt or model change actually improved things rather than just feeling like it did. A staff engineer treats testing and observability as one continuous feedback loop, not two separate disciplines owned by two separate teams.

JUNIORQ9. What is a Micrometer Observation, and what does Observation.NOOP mean for performance when no handlers are registered?

ROI: ★★★★☆ · Frequency: High

An Observation is Micrometer's unified representation of "one unit of work worth observing" — it carries a name, a context of key-values, a start/stop lifecycle, and notifies every registered ObservationHandler on start, stop, and error. When an ObservationRegistry has no handlers registered (for example, Actuator and Micrometer Tracing are not on the classpath), Micrometer returns Observation.NOOP — a no-op implementation whose start/stop calls do essentially nothing. This means Spring AI's instrumentation call sites are always present in the code, but cost almost nothing when observability isn't configured, which is why enabling full tracing and metrics later requires no code changes at all.

JUNIORQ10. What is an ObservationRegistry, and how does a Spring AI ChatClient obtain one?

ROI: ★★★☆☆ · Frequency: Medium

The ObservationRegistry is the central object that holds the configured set of ObservationHandlers and observation-level configuration (predicates, filters, conventions). Spring Boot auto-configures one automatically once Actuator plus a Micrometer registry/tracing bridge are on the classpath, and registers it as a bean. Spring AI's autoconfiguration picks up that bean and wires it into the ChatClient and ChatModel implementations without any explicit developer action — you get instrumentation "for free" the moment the dependencies are present, and a no-op registry otherwise.

MIDQ11. How does the Observation API differ from the older AOP-based @Timed annotation approach to metrics?

ROI: ★★★☆☆ · Frequency: Medium

@Timed is a single-purpose annotation that only produces a Micrometer Timer metric around a method call, using Spring AOP proxying. The Observation API is a unified abstraction that simultaneously drives metrics, traces, and any other registered handler (custom logging, alerting hooks) from one instrumentation call site, and it works at arbitrary granularity inside a method — not just "around this whole method" — which is exactly what Spring AI needs to create nested spans for retrieval, the model call, and each tool invocation within a single ChatClient.call() invocation.

MIDQ12. Name the two ObservationHandler implementations that turn a Spring AI Observation into a trace and into metrics, respectively, and explain how both fire from the same instrumentation.

ROI: ★★★★☆ · Frequency: High

TracingObservationHandler converts the Observation into a span, attaches it to the current trace context, and exports it (via Micrometer Tracing's OTel bridge) to a tracing backend. MeterObservationHandler converts the same Observation's duration and key-values into Micrometer Timer/Counter instruments, exported to a metrics backend like Prometheus. Because both handlers are registered on the same ObservationRegistry and are notified from the same observation.start()/stop() lifecycle call, Spring AI code never has to call "log this," "trace this," and "meter this" separately — one instrumented call site feeds every pillar.

JUNIORQ13. What is an Observation.Context, and how does it relate to low- and high-cardinality key-values?

ROI: ★★★★☆ · Frequency: High

The Observation.Context is the mutable data container attached to an Observation for its lifetime — it holds the request/response objects being observed plus two separate collections of key-values: low-cardinality (bounded, safe to become metric tags — model name, provider, operation type) and high-cardinality (unbounded, safe only for trace spans and logs — prompt text, completion text). ObservationConvention implementations read from the context to populate these two collections, and MeterObservationHandler deliberately only reads the low-cardinality set when building metric tags, which is the actual mechanism enforcing the cardinality discipline described elsewhere in this chapter.

MIDQ14. How would you add a custom low-cardinality tag — say, feature.name — to every ChatClient observation without editing every call site?

ROI: ★★★★☆ · Frequency: High

Implement a custom ChatClientObservationConvention (typically by extending DefaultChatClientObservationConvention) that overrides getLowCardinalityKeyValues() to append your tag — reading it from a value stored in the request context, a thread-local, or a request-scoped bean — then register it either as a bean that Spring AI's autoconfiguration picks up, or explicitly via ChatClient.Builder.defaultRequest(...) combined with an ObservationRegistryCustomizer. Because the convention is applied uniformly by the framework at every call, you get the tag on every trace and every metric without touching individual service methods.

MIDQ15. If Micrometer Tracing and Actuator are not on the classpath, does a Spring AI application fail to start, or does anything else break?

ROI: ★★★☆☆ · Frequency: Medium

Nothing breaks. Spring AI's Observation calls are always present, but with no handlers registered the ObservationRegistry falls back to Observation.NOOP (Q9), so the calls execute as near-zero-cost pass-throughs. The application starts and functions identically from a business-logic perspective — you simply get no traces, no metrics, and none of the token/cost visibility described in this chapter, which is precisely why "we'll add observability later" is a viable but risky deferral: it costs nothing to enable early, and costs you blind production debugging to skip.

JUNIORQ16. What's the difference between ChatClientObservationConvention and ChatModelObservationConvention, and why does Spring AI need both?

ROI: ★★★★☆ · Frequency: High

ChatClientObservationConvention governs the outer span/metric for a whole ChatClient call, including the Advisor chain (retrieval, memory, logging). ChatModelObservationConvention governs the inner span/metric for the actual model invocation only. They're separate because one ChatClient call can trigger more than one underlying model call — most obviously during a tool-calling loop — so the framework needs an outer span representing "the whole logical request" and one inner span per actual model round trip, which is what lets a trace waterfall show two chat.model spans nested under one chat.client span.

MIDQ17. Why does a tool-calling loop that makes two sequential model calls produce two separate chat.model spans rather than one longer one?

ROI: ★★★★☆ · Frequency: High

Because each round trip to the model is a distinct, separately-timed unit of work with its own token usage, its own latency, and potentially its own outcome (one call might error while the retry succeeds). Collapsing them into a single span would hide exactly the information a debugging engineer needs — for instance, whether the first call's latency was dominated by the model deciding to invoke a tool versus the second call's latency being dominated by synthesizing a final answer from the tool's result. Keeping them separate, nested under the outer chat.client span, preserves that attribution.

MIDQ18. Explain gen_ai.system, gen_ai.request.model, and gen_ai.response.model — why do you need both a request and a response model attribute?

ROI: ★★★★★ · Frequency: Extremely High

gen_ai.system identifies the provider (e.g. openai, anthropic). gen_ai.request.model is the model identifier your code asked for; gen_ai.response.model is the model identifier the provider actually reports having used. These can legitimately differ — providers sometimes route a stable alias to a different underlying model version behind the scenes — and capturing both is the only way to detect that kind of silent drift, since your own deployment history won't show any change corresponding to a quality or latency shift caused by the provider's routing decision.

MIDQ19. What should you know about the stability of the OpenTelemetry GenAI semantic conventions before building dashboards on top of the raw gen_ai.* attribute names?

ROI: ★★★☆☆ · Frequency: Medium

As of this writing, the GenAI semantic conventions are still marked experimental/evolving within OpenTelemetry — attribute names, especially around prompt/completion content capture and tool-calling attributes, have changed shape as the spec matures. Building dashboards and alerts directly against raw attribute names without an abstraction layer means a spec revision (or a Spring AI version bump that follows it) can silently break your queries. A defensive pattern is to normalize onto your own stable internal metric/attribute names at the dashboard layer, or pin your OTel/Spring AI versions deliberately and review the changelog before bumping.

MIDQ20. Why are prompt tokens and completion (generation) tokens tracked as separate numbers rather than one combined "tokens used" figure?

ROI: ★★★★☆ · Frequency: High

Most providers price input and output tokens differently — output tokens are typically several times more expensive per token than input tokens — so a combined total is useless for cost calculation. The two numbers also behave differently operationally: prompt tokens grow with context size (retrieved documents, conversation history, system prompt), while completion tokens grow with how verbose the model chooses to be, which is a signal of its own (a sudden jump in completion tokens with the same prompt size often indicates a prompt regression or a model behavior change worth investigating on its own).

MIDQ21. What operational discipline is required to keep a token-to-cost pricing table accurate over time?

ROI: ★★★☆☆ · Frequency: Medium

Provider pricing changes independently of your deploys, and different models from the same provider are priced differently, so the per-token price table your cost dashboard multiplies against must be versioned and updated out-of-band from application releases — typically as external configuration (a small database table or config service) rather than a hard-coded constant, keyed by gen_ai.system plus gen_ai.response.model. Treat stale pricing data as a silent-but-real bug class: your dashboard will keep producing numbers, they'll just be quietly wrong.

SENIORQ22. Design cost attribution for a multi-tenant SaaS product where several customer organizations share the same Spring AI service.

ROI: ★★★★★ · Frequency: High at senior level

Attach a low-cardinality tenant.tier (e.g. free/pro/enterprise, a handful of values) as a metric tag for aggregate per-tier cost dashboards, but keep the actual high-cardinality tenant.id off metrics entirely — put it on trace spans and on a separate, purpose-built cost-ledger event stream (a Kafka topic or dedicated table written from a custom ObservationHandler) that is not a Prometheus time series. Aggregate per-tenant cost asynchronously from that ledger, not from the metrics backend, so you get exact per-tenant billing data without ever creating one Prometheus series per tenant.

Interview Gold Point: Mention that this ledger doubles as the enforcement point for per-tenant budget caps — a scheduled job or streaming aggregation can compare running spend against a tenant's plan limit and raise an alert or throttle before the tenant's bill becomes a support incident.
MIDQ23. Are embedding model calls observed the same way chat model calls are in Spring AI?

ROI: ★★★☆☆ · Frequency: Medium

Yes — Spring AI applies the same Observation-based pattern to EmbeddingModel calls via an EmbeddingModelObservationConvention, producing spans and metrics tagged with the embedding model name, provider, and dimensionality, with token usage captured the same way as chat calls. This matters because embedding calls happen on every RAG ingestion and every retrieval query, often at far higher volume than chat calls, so their aggregate cost and latency deserve the same dashboard treatment rather than being an invisible line item hidden inside a "retrieval" span.

MIDQ24. What does a VectorStoreObservationConvention typically tag a retrieval span with, and why are those specific tags chosen?

ROI: ★★★★☆ · Frequency: Medium-High

Typically the vector store implementation name (e.g. pgvector, pinecone), the collection/index name, and the requested top_k — all low-cardinality and directly useful for answering "is retrieval slow because of this specific index" or "did we change top_k and did that change latency or answer quality." The actual query embedding vector and the retrieved document IDs/content are deliberately kept off the low-cardinality tag set for the same cardinality reason prompts are — they belong in a trace's detailed payload or a log, not a metric label.

SENIORQ25. Walk through the full span hierarchy you would design for a production RAG-plus-tool-calling pipeline, naming each span and its key tags.

ROI: ★★★★★ · Frequency: High at senior level

Root: http.server.request (path, status). Child: chat.client (feature name, prompt version). Its children, in call order: advisor.retrieval-augmentation (vector store, top_k, doc count returned), advisor.chat-memory (conversation id — kept off metrics), one or more chat.model spans (provider, request/response model, input/output tokens) — more than one if the model requests tools — and, sibling to those, one tool.call span per tool invocation (tool name, success/failure, latency). This mirrors exactly the waterfall structure shown earlier in this chapter, and each span's low-cardinality tags roll up into per-stage latency and error-rate metrics without needing a second instrumentation pass.

Interview Gold Point: Add that you'd also give the outer chat.client span a derived attribute for total token count and estimated cost at close time, computed by summing the child chat.model spans — this lets a single trace answer "what did this exact request cost" without a separate query.
MIDQ26. What is an ObservationFilter, and what's a concrete use case for one in an AI observability pipeline?

ROI: ★★★★☆ · Frequency: High

An ObservationFilter is a hook that can inspect and mutate an Observation.Context before it's handed to handlers — every registered filter runs on every observation. A concrete use case is PII redaction: a filter that scans the high-cardinality prompt/completion key-values for patterns like email addresses, account numbers, or credit-card-shaped strings and replaces them with a redaction marker before the context ever reaches TracingObservationHandler, guaranteeing raw sensitive content never leaves the process boundary even if a downstream Collector-level redaction step is misconfigured.

SENIORQ27. Should PII redaction for LLM telemetry happen in application-level ObservationFilters, at the OpenTelemetry Collector, or both — what are the tradeoffs?

ROI: ★★★★★ · Frequency: High at senior level

Collector-level redaction centralizes policy — one processor configuration enforced consistently across every service, easy to audit and update without redeploying application code — but it means raw content briefly exists in the exporter and the network hop to the Collector, and it requires every team to trust the same shared processor. Application-level ObservationFilter redaction guarantees content never leaves the process at all, which matters for the strictest compliance regimes, but is easy to implement inconsistently across a dozen teams. The pragmatic answer is defense in depth: filter obviously sensitive patterns (structured PII you can regex reliably) at the application layer as a backstop, and rely on the Collector for the primary, centrally-governed policy, since content that isn't obviously structured PII (free-text customer complaints, say) is easier to catch with a shared, tunable Collector processor than a hundred bespoke regexes scattered across services.

MIDQ28. What is an ObservationPredicate, and when would you use one to suppress observation entirely rather than filter its content?

ROI: ★★★☆☆ · Frequency: Medium

An ObservationPredicate decides, before an Observation even starts, whether it should be observed at all — returning false makes it a no-op for that call. A typical use is suppressing observation of internal health-check or warm-up calls to a ChatModel (some teams issue a lightweight "ping" completion to keep a connection pool warm) so they don't pollute latency percentiles and cost dashboards with synthetic traffic that isn't representative of real user requests.

SENIORQ29. Production cost jumped 5x overnight with no corresponding traffic increase. Walk through how you'd diagnose this using the telemetry described in this chapter.

ROI: ★★★★★ · Frequency: High at senior level

Start at the cost-per-feature dashboard (built from token metrics tagged by feature and model, Section 6.2) to isolate which feature's cost rose, ruling out a platform-wide issue if only one feature spiked. Check whether average completion tokens per request rose for that feature — a common cause is a prompt or retrieval change that now stuffs far more context into every call, or a model that started generating longer, more verbose completions after a provider-side update (check gen_ai.response.model for a silent version change). If completion tokens per request look flat, check the trace waterfall for evidence of a tool-calling loop firing more model round trips per request than before — a runaway agent loop multiplies cost by request count of model calls, not by tokens per call, and would be invisible in a per-call token metric alone but obvious in a "model calls per trace" count.

Interview Gold Point: Note that this is exactly why "model calls per outer chat.client span" is worth tracking as its own metric, not just total tokens — it's the single fastest signal for catching an agent loop before it becomes a five-figure bill.
MIDQ30. What is TestObservationRegistry, and why would you write a test against your own observability instrumentation rather than trusting it works?

ROI: ★★★☆☆ · Frequency: Medium

TestObservationRegistry is Micrometer's in-memory test double for an ObservationRegistry that lets a test assert exactly which observations were started, what key-values they carried, and whether they completed successfully or with an error — without standing up a real tracing or metrics backend. You'd write such a test because instrumentation is code, and code silently regresses: a refactor that accidentally drops a custom ChatClientObservationConvention from the builder chain, or removes a tag, produces no compile error and no functional test failure, only a quietly worse production dashboard weeks later — asserting on the observation itself catches that class of regression before it ships.

SENIORQ31. Why does streaming fundamentally complicate both span-duration measurement and the reporting of token usage?

ROI: ★★★★☆ · Frequency: High

The Observation's span can only close once the stream is fully drained, because final response metadata — including the completion token count — is typically only available after the last chunk arrives (some providers include a usage payload only on the terminal chunk). This means span duration measures "time to fully consume the stream," not the perceived latency a chat UI actually delivers to a user, which is dominated by time-to-first-token. It also means any dashboard slicing "latency" for streaming versus non-streaming endpoints together is comparing two different things unless you separately instrument TTFT, since a fast-to-first-token but slow-to-finish stream will look identical to a genuinely slow non-streaming call in the aggregate span-duration metric alone.

MIDQ32. Concretely, how would you instrument time-to-first-token separately from total Observation span duration?

ROI: ★★★☆☆ · Frequency: Medium-High

Record a timestamp when the stream subscription is established (or the request is sent) and a second timestamp the moment the first chunk arrives in your Flux<ChatResponse> subscriber, then emit the delta as a custom Micrometer Timer — a separate meter from the framework's own span-duration timer, tagged the same way (model, feature) so it can sit alongside it on a dashboard. This has to be custom instrumentation because the standard ChatModelObservationConvention only knows the observation's start and stop boundaries, not an intermediate "first chunk received" event.

SENIORQ33. Compare head-based and tail-based trace sampling, and explain specifically why an OpenTelemetry Collector is usually required to implement tail-based sampling well.

ROI: ★★★★★ · Frequency: High at senior level

Head-based sampling decides whether to keep a trace at the moment it starts, before its outcome is known — cheap and simple, but by definition it samples uniformly at random and cannot preferentially keep the errored or slow traces you most want to debug. Tail-based sampling defers the keep/drop decision until the trace is complete, so it can check "did this error, did it exceed a latency threshold" and keep those with much higher probability than routine successful traffic. Implementing tail-based sampling requires buffering every span of a trace somewhere until the whole trace finishes, which single application instances generally can't do reliably for traces that fan out across services — this is exactly the job an OpenTelemetry Collector (or a dedicated sampling processor tier) is built for: it aggregates spans centrally, applies the tail-based policy once the trace is complete, and only then forwards the decision to your backend.

Interview Gold Point: Point out the storage math: if 1% of requests error and you tail-sample to keep 100% of errors plus 5% of successes, you retain far fewer total traces than a flat 10% head sample while guaranteeing you never lose the trace for an incident you'll actually need to investigate.
MIDQ34. What's the difference between trace context propagation and baggage propagation, and when would you use baggage in a Spring AI pipeline?

ROI: ★★★☆☆ · Frequency: Medium

Trace context propagation (the W3C traceparent header) carries only the trace ID and current span ID needed to assemble the span tree. Baggage is a separate, general-purpose key-value mechanism that also propagates across the same hops but carries arbitrary business context you want available anywhere downstream — for example, a tenant.tier or experiment.variant value set once at the entry point and automatically available to a low-cardinality tagging convention deep inside a tool call in another service, without threading it through every method signature by hand.

SENIORQ35. A user reports a wrong answer, but there's no exception anywhere in the logs. Using only traces and metrics — no re-running the request — how do you reconstruct what went wrong?

ROI: ★★★★★ · Frequency: High at senior level

Locate the specific trace (via trace ID if you have log-trace correlation via MDC, or by timestamp/user tag on the trace itself). Walk the span waterfall: check the retrieval span's tags and, if captured, the retrieved document set — a common root cause is retrieval returning stale or irrelevant documents, which a fast, error-free retrieval span won't reveal unless you look at what it actually returned. Check the chat.model span's captured prompt (if high-cardinality capture is enabled for this trace) to see exactly what context the model was given, and compare gen_ai.response.model against what you expect — a silent provider-side model swap is a frequent, otherwise-invisible cause of a quality regression with no error signal at all.

Interview Gold Point: Mention that this is the strongest practical argument for capturing full prompt/completion content on at least a sampled fraction of traffic — without it, this exact investigation dead-ends at "the trace shows it was fast and error-free," which answers nothing about why the answer was wrong.
SENIORQ36. How specifically does observability let you catch a provider silently changing the model behind a stable alias, and what would you alert on?

ROI: ★★★★☆ · Frequency: High

Track gen_ai.response.model as a metric dimension (it's low-cardinality — a handful of concrete model versions) alongside your requested gen_ai.request.model alias, and alert on a change in the distribution of response-model values for a given request-model alias over a short window — for example, if 100% of responses for alias gpt-4o were reporting one specific dated snapshot last week and a new snapshot value starts appearing this week, that's a provider-side rollout worth knowing about proactively, before a user-facing quality complaint forces you to investigate reactively.

MIDQ37. Why is it risky to tag a metric with a tool call's arguments (e.g. tool.args), even though tool names themselves are usually safe low-cardinality tags?

ROI: ★★★★☆ · Frequency: Medium-High

The tool name is drawn from a small, fixed set defined by your application (low cardinality, safe for metrics), but the tool's arguments are model-generated free text or structured values that vary per call and can be effectively unbounded — a search-tool query argument or an order-ID argument behaves exactly like a user prompt for cardinality purposes. The same rule that keeps prompt text off metrics applies here: tool name goes on the metric tag, tool arguments go only on the trace span's detailed attributes or a log.

SENIORQ38. How would you integrate Resilience4j circuit-breaker and retry metrics with your Spring AI Observation-based telemetry so a trace shows the full retry story?

ROI: ★★★★☆ · Frequency: Medium-High

Resilience4j already publishes its own Micrometer metrics (circuit breaker state, retry attempt counts) onto the same MeterRegistry Spring AI's MeterObservationHandler writes to, so both show up side by side in the same Prometheus/Grafana instance without extra wiring. For trace-level visibility, wrap the retry-decorated model call so each retry attempt creates its own child span (or an event on the parent chat.model span) tagged with an attempt number — otherwise a trace shows only the final successful call's duration and hides that it took three attempts and a circuit-breaker half-open probe to get there, which is exactly the kind of degraded-but-not-failed behavior worth surfacing.

MIDQ39. A structured-output call (using Spring AI's structured output converter) fails to parse the model's JSON but the call itself doesn't throw an exception the caller notices. How do you make this failure mode visible in telemetry?

ROI: ★★★★☆ · Frequency: Medium-High

Wrap the parsing step itself in its own small Observation, or at minimum increment a dedicated Micrometer counter (e.g. gen_ai.structured_output.parse_failure, tagged by model and feature) whenever the converter has to fall back, repair, or the parse otherwise doesn't cleanly succeed on the first attempt — since a caught-and-repaired parse failure is functionally a quality signal even though it never surfaces as an exception to calling code. Without this, "did structured output ever fail to parse" is invisible in both logs (no exception) and standard error-rate metrics (no HTTP error), which is exactly the "plausible but subtly wrong" failure mode this chapter's Section 4.2 describes.

SENIORQ40. Design tracing and alerting for a service that routes requests to a primary model and falls back to a secondary model on failure.

ROI: ★★★★☆ · Frequency: High

Give the routing decision its own low-cardinality tag (gen_ai.route = primary/fallback) on the outer span and on the resulting metrics, so latency, cost, and error-rate dashboards can be sliced by route — a fallback model is often slower, cheaper or more expensive, or lower quality, and conflating the two routes hides that. Alert specifically on fallback-route volume as a rate metric: a sudden spike in fallback usage is itself an incident signal (the primary provider is degraded) even if overall error rate looks fine because the fallback is successfully absorbing the failures — without a route tag, that entire incident is invisible to a dashboard that only tracks aggregate success rate.

MIDQ41. What are exemplars, and how do they help you go from "this Prometheus metric spiked" to "here's the exact trace that caused it"?

ROI: ★★★☆☆ · Frequency: Medium

An exemplar is a sampled trace ID attached to a specific metric data point (typically on a histogram bucket) at the moment it was recorded, supported by Prometheus's native histogram/exemplar storage and surfaced in Grafana as a clickable point on a latency or error graph. Practically, this means when you're staring at a p99 latency spike on a dashboard, you can click directly into one of the actual traces that contributed to that data point instead of separately searching your tracing backend by timestamp and hoping you find the right request — it closes the gap between "the aggregate metric" and "the individual trace" pillars.

SENIORQ42. What concrete alerting thresholds would you set up for a production RAG agent, and why those specific signals?

ROI: ★★★★★ · Frequency: High at senior level

Cost-rate alert (spend per minute/hour exceeding a rolling baseline by some multiple) catches runaway loops and prompt regressions fastest, since cost reacts before most other signals. Latency p95/p99 alert (not mean, per Section 6.1) catches degraded provider or tool performance. Error-rate alert on both the model call and each tool call separately, since a healthy overall error rate can hide one consistently-failing tool. Token-count anomaly alert (completion tokens per request deviating sharply from a rolling baseline) catches verbosity regressions before they show up purely as cost. And a fallback-route or retry-rate alert (Q40/Q38) catches upstream provider degradation that hasn't yet become a hard failure. Each of these is chosen because it fires meaningfully earlier than "users are complaining," which is the failure mode a good alerting design is trying to avoid.

MIDQ43. Describe the mechanics of correlating a log line with a specific trace via MDC.

ROI: ★★★★☆ · Frequency: High

An ObservationHandler (or, more commonly, Micrometer Tracing's built-in log correlation support) copies the current trace ID and span ID from the active tracing context into SLF4J's MDC (Mapped Diagnostic Context) at the start of each request/span, so every log statement emitted during that scope automatically includes those IDs if your log pattern references them (e.g. %X{traceId} in a Logback pattern). This is what makes "click a trace in Zipkin, then pivot straight to the matching application log lines in your log aggregator" possible — both are keyed by the same ID without any manual correlation logic in your business code.

SENIORQ44. What does a classical APM dashboard (request count, latency, error rate) get right for an AI feature, and what does it fundamentally miss?

ROI: ★★★★☆ · Frequency: High

It gets infrastructure health right — an AI feature is still an HTTP endpoint backed by a service, and knowing its request volume, latency distribution, and hard-error rate is necessary and directly reusable, which is exactly why Spring AI plugs into the same Micrometer/Actuator stack rather than building a parallel one (Section 9). What it fundamentally misses is everything this chapter's fourth pillar covers: per-request cost as a first-class, highly variable number; correctness, since a 200 OK response can still be a wrong answer; and non-determinism, since the same request can legitimately behave differently on repeat calls, which breaks the implicit APM assumption that a given endpoint's behavior is stable enough that "it's erroring more than usual" is the main thing worth watching for.

SENIORQ45. Design telemetry specifically aimed at catching and limiting an agent that can loop indefinitely, repeatedly calling tools without converging on an answer.

ROI: ★★★★★ · Frequency: High at senior level

Track "model calls per outer chat.client span" and "tool calls per outer span" as histograms, not just counts — a healthy distribution clusters around a small number (often 1–3), and a request landing far out on that histogram's tail is a strong runaway-loop signal worth alerting on directly, independent of whether it eventually terminates or hits a hard iteration cap. Enforce a hard maximum tool-call-round cap in code (a circuit breaker on the agent loop itself, not just on individual tool calls) and tag any request that hits that cap with a distinct agent.loop_capped=true low-cardinality attribute, so you can measure how often the safety net actually fires — a nonzero, growing rate of capped requests is itself an early warning that something in the prompt or tool design is encouraging non-convergent behavior, even before any single incident is expensive enough to notice from cost alone.

Interview Gold Point: Tie this back to Q29's cost-spike scenario — a "model calls per trace" histogram is the metric that turns that reactive, after-the-fact investigation into a proactive alert that fires before the bill does.
MIDQ46. If the underlying HTTP client to the model provider silently retries a request under the hood, how do you make that retry visible rather than have it hide inside one span's duration?

ROI: ★★★☆☆ · Frequency: Medium

A retry that happens entirely inside the HTTP client layer, below Spring AI's own Observation, will indeed just inflate the outer span's duration with no separate attribution unless you add instrumentation at that layer too — either by configuring the HTTP client's own interceptor to emit a child span per attempt, or by exposing a retry-count attribute on the final response that gets attached to the chat.model span as a custom key-value. Without this, a request that "took 4 seconds because of two silent retries" looks identical in a trace to "took 4 seconds because the model was genuinely slow once" — two very different operational stories that call for different fixes.

SENIORQ47. Explain the architecture and reasoning for running quality/evaluation telemetry as an asynchronous, sampled pipeline rather than inline with the user-facing request.

ROI: ★★★★★ · Frequency: High at senior level

An LLM-as-judge evaluation is itself a model call, so running it synchronously before responding to the user doubles the request's latency and cost for every single request — a cost that scales with production traffic rather than with how much evaluation signal you actually need. Instead, sample a fraction of production traces (weighted toward flagged or unusual traces via the same tail-based logic used for tracing) into a queue or event stream, score them asynchronously against a separate evaluation service, and write the resulting quality score back as a metric tagged by model/prompt version — decoupled from the request's critical path entirely, at the cost of the evaluation signal lagging real time by however long the async pipeline takes to catch up.

MIDQ48. What criteria would you use to decide what fraction of production traffic gets full prompt/completion content capture versus metrics-only visibility?

ROI: ★★★★☆ · Frequency: Medium-High

Weigh storage/compliance cost against debugging value: 100% capture gives you the ability to fully reconstruct any past request but multiplies storage cost and expands your PII exposure surface to every request rather than a subset (Section 12/13). A common pragmatic split is metrics-only for 100% of traffic (cheap, low risk), full-content capture for a random sample (a few percent, enough to catch systemic issues and feed the async eval pipeline), and full-content capture forced to 100% for any request that errors or that a user explicitly flags with feedback — mirroring the tail-based sampling logic used for latency in Q33, applied to content capture instead.

SENIORQ49. What does "right to be forgotten" (GDPR-style deletion requests) imply for a trace store that has been capturing user prompts?

ROI: ★★★★☆ · Frequency: Medium-High

If prompt/completion content in your traces can contain personal data, then a deletion request obligates you to be able to find and purge that specific user's captured content from the trace/log store, not just from your primary application database — which most tracing backends were not originally designed to support efficiently, since they're optimized for time-ordered ingestion and retrieval, not per-user deletion. Practically, this pushes teams toward either tagging traces with a user/session identifier specifically to make targeted deletion possible, aggressively short retention windows for full-content traces (Section 12 already recommends a few weeks) so the problem shrinks on its own, or routing anything containing personal data to a separate store with proper data-subject-request tooling rather than the general-purpose tracing backend.

MIDQ50. What specific responsibilities does the OpenTelemetry Collector take on in a Spring AI observability pipeline, beyond simply forwarding data?

ROI: ★★★☆☆ · Frequency: Medium

Batching (aggregating many small span/metric exports into fewer, larger network calls to reduce overhead — Section 12), PII redaction as a centrally-governed processor (Q27), tail-based sampling decisions that require seeing a complete trace (Q33), protocol translation (accepting OTLP and re-exporting in a backend-specific format if needed), and fan-out to multiple destinations simultaneously — a trace can go to both a general tracing backend like Jaeger and a specialized LLM evaluation platform like Langfuse from the same Collector pipeline, without your application code knowing or caring how many downstream consumers exist.

SENIORQ51. Two prompt versions are running as a canary. How would you structure tags and dashboards to compare their cost and quality fairly?

ROI: ★★★★☆ · Frequency: High

Attach a prompt.version low-cardinality tag (a handful of values — v13, v14) to every relevant span and metric at the point the prompt is constructed, so it flows through to token/cost metrics, latency, and — critically — the async quality-evaluation score, all sliceable by that one dimension. Compare cost-per-request, latency, and quality score side by side, filtered to the same time window and, ideally, the same traffic segment (random assignment, not "v14 only ran during off-peak hours," which would confound the comparison) — the same rigor you'd apply to any other A/B test, just with cost and an LLM-judge quality score as additional metrics beyond the usual conversion/engagement numbers.

MIDQ52. Give the intuition for why p99 latency, not mean latency, is the number a staff engineer asks for first when investigating an LLM-backed feature.

ROI: ★★★★☆ · Frequency: High

Mean latency is pulled toward the bulk of fast, ordinary requests and can look perfectly healthy even while a meaningful minority of requests — often the ones involving a tool call, a longer generation, or provider-side queuing — take several times longer. p99 latency specifically answers "how bad is the worst 1% of experience," which is usually where user complaints originate, since a fast average with a bad tail means most users are fine but a nontrivial number are having a genuinely poor experience that the average is actively hiding from whoever only looks at that one summary number.

SENIORQ53. The retrieval span shows consistently fast latency, but answer quality has degraded over the past week according to your eval pipeline. What would you check?

ROI: ★★★★☆ · Frequency: Medium-High

Fast retrieval says nothing about relevance — check whether the documents actually being retrieved (visible in traces with content capture enabled, or in retrieval-specific logging) have drifted, which can happen if the underlying corpus changed (new documents pushed the old, correct ones further down similarity rankings), if the embedding model was silently updated by the provider, or if a re-indexing job introduced stale or duplicate entries. Also check gen_ai.response.model for a silent model swap (Q36) independent of retrieval entirely, since degraded generation quality with unchanged retrieval quality points at the model call itself rather than the RAG pipeline's retrieval stage.

STAFFQ54. As the staff engineer responsible for observability governance across a dozen teams building Spring AI features, how do you prevent gen_ai.* attribute schema drift between teams?

ROI: ★★★★★ · Frequency: High at staff level

Publish and version an internal schema — effectively a thin org-specific extension of the OpenTelemetry GenAI semantic conventions covering exactly which custom low-cardinality tags (feature name, prompt version, tenant tier) are standard and what values they may take — as a shared library artifact (a small Spring Boot starter providing a pre-built ObservationRegistryCustomizer) rather than a wiki page teams are expected to remember to follow. Enforce it with a lightweight contract test each service runs in CI, using TestObservationRegistry (Q30), asserting the expected tags are present on a sample call — schema drift caught in CI before merge is categorically cheaper than schema drift discovered when someone's cross-team dashboard silently stops working.

Interview Gold Point: Add that you'd own this the same way a platform team owns a shared logging format — as a small piece of internal infrastructure with an explicit owner, a changelog, and a deprecation policy, not as an informal convention that erodes the moment the person who set it up moves teams.
SENIORQ55. Explain mechanically how a single Observation's start/stop lifecycle becomes an aggregated Micrometer Timer with percentile output, across potentially millions of requests.

ROI: ★★★★☆ · Frequency: Medium-High

Each Observation's stop() call hands its duration and low-cardinality key-values to MeterObservationHandler, which looks up (or creates, on first occurrence of a given tag combination) a Timer instrument in the MeterRegistry keyed by the observation's name plus that exact set of tag values, then records the duration into it. The Timer itself maintains a bounded-memory histogram (not every raw sample) that a Prometheus-backed registry can later expose as pre-computed percentile buckets on scrape, which is how thousands of individual, ephemeral Observations become one stable, queryable p95/p99 time series per tag combination without unbounded memory growth.

STAFFQ56. You need to build a cost dashboard for product managers, not engineers. What would you deliberately simplify away from the engineering-facing telemetry?

ROI: ★★★★☆ · Frequency: Medium-High

Drop per-model, per-provider technical dimensions (gen_ai.system, request vs. response model) in favor of business-meaningful dimensions — feature name, customer tier, time period — and present cost as dollars-per-day-per-feature and cost-per-active-user rather than tokens or Prometheus rate expressions. Surface trend and anomaly ("cost is up 40% week over week for Feature X") rather than raw time series, since a PM's actionable question is "should we be worried and about what," not "what's the exact shape of the p99 curve." The underlying data source is identical to the engineering dashboard — same token/cost metrics from Section 6.2 — only the aggregation and presentation layer changes for the audience.

SENIORQ57. How would you detect retrieval or embedding drift over time purely from observability signals, without a labeled evaluation dataset?

ROI: ★★★★☆ · Frequency: Medium-High

Track proxy signals that correlate with retrieval quality even without ground truth: the distribution of similarity scores returned by the vector store (a downward drift in typical top-1 similarity score for the same query mix suggests the corpus or embeddings have drifted relative to what users are asking), the rate at which the RAG pipeline falls back to a "no relevant documents found" path, and downstream completion-token counts (a model padding out answers with hedging or generic content is a mild signal that retrieved context stopped being useful). None of these prove a quality regression on their own, but a sustained trend across several of them together is a strong enough signal to trigger a manual quality audit or an eval-pipeline run targeted at that feature specifically.

STAFFQ58. Your organization is migrating from one model provider to another. What must your observability layer preserve so historical dashboards and alerts remain meaningful across the migration?

ROI: ★★★★☆ · Frequency: Medium-High at staff level

Because Spring AI normalizes token usage, latency, and error handling behind provider-agnostic abstractions (ChatModel, Usage, ChatResponseMetadata — Section 9), the metric and span shapes themselves don't need to change; what does need explicit handling is the gen_ai.system/gen_ai.request.model tag values changing, which will make Prometheus treat old-provider and new-provider traffic as genuinely distinct time series (correctly so, since they are different systems). Run both providers side by side behind the route tag from Q40 during the migration window so cost and quality dashboards can compare them directly, and update the pricing table (Q21) for the new provider before cutover, not after — a stale pricing table during a migration is a near-guaranteed source of a confusing "cost dashboard looks wrong" incident in week one.

SENIORQ59. Describe the second-order security risk of a prompt-injection payload being captured verbatim in your telemetry and later rendered in an internal trace-viewing dashboard.

ROI: ★★★★☆ · Frequency: Medium-High

If an attacker's injected prompt content contains something like an HTML/script payload and your trace viewer renders captured prompt/completion text without escaping it, you've turned your own observability tooling into a stored-XSS vector — an engineer innocently viewing a trace to debug an unrelated issue could have that payload execute in their authenticated session against your internal tools. The fix is to treat any user- or model-influenced content flowing into your telemetry pipeline as untrusted input at the rendering layer, the same discipline you'd apply to displaying it anywhere else — HTML-escape by default in the trace viewer, and don't assume "it's just internal engineering tooling" exempts it from the same input-handling rules as user-facing surfaces.

MIDQ60. What is the W3C traceparent header, and why does its propagation matter specifically when a tool call goes out to an MCP server running as a separate process or service?

ROI: ★★★★☆ · Frequency: Medium-High

traceparent is the standardized HTTP header carrying the current trace ID, parent span ID, and sampling flags across a network hop, defined by the W3C Trace Context specification and implemented automatically by Micrometer Tracing/OpenTelemetry for common Spring HTTP clients. Without it being propagated to an MCP server invoked as a tool call, that server's own spans (if it's instrumented) would start a brand-new, disconnected trace instead of appearing as a child of the calling request — breaking exactly the kind of end-to-end waterfall view (Section 7.1) that makes a multi-hop agent pipeline debuggable as one story rather than several unrelated fragments you have to manually stitch together by timestamp.

SENIORQ61. Design the span and metric strategy for a request where a tool call itself invokes another Spring AI-backed service, which makes its own model call.

ROI: ★★★★☆ · Frequency: Medium-High

As long as trace context propagates across that hop (Q60), the downstream service's own chat.client/chat.model spans appear as children of the tool.call span in the calling service's trace automatically — no special cross-service coordination code is needed beyond ensuring both services are configured with the same tracing backend/exporter target. The one thing worth deliberately designing is cost and token attribution: decide whether the downstream service's token usage should roll up into the calling feature's cost dashboard (usually yes, since from a product perspective it's one logical request) or be attributed separately to the downstream service's own budget — this is a tagging and aggregation-query decision, not an instrumentation one, since the raw span data supports either view.

STAFFQ62. You're asked to build a cost-governance system that can actually cap spend per team, not just report it after the fact. Describe the telemetry-driven guardrails you'd put in place.

ROI: ★★★★★ · Frequency: High at staff level

Reporting-after-the-fact (dashboards, alerts) is necessary but insufficient for a hard cap — you need an enforcement point that can act before the spend happens. Stream token/cost events (from the same Usage metadata already captured per request) into a fast aggregation store (a sliding-window counter per team, e.g. Redis-backed) that a request-time check can query cheaply before allowing a call to proceed; when a team's rolling spend crosses a threshold, degrade gracefully rather than hard-failing — route to a cheaper model, shorten context, or queue non-urgent requests — and always emit a distinct low-cardinality budget.action=throttled tag when this fires, so the throttling itself shows up on the same dashboards and doesn't look like an unexplained latency or error-rate anomaly to whoever's on call.

Interview Gold Point: Emphasize the design principle: enforcement has to be near-real-time and request-scoped (a counter check), while the rich, high-cardinality cost analysis (per-user, per-feature breakdowns) stays in the slower, asynchronous metrics/dashboard pipeline — trying to make the dashboard pipeline itself the enforcement mechanism is both too slow and, per Section 4.4, structurally the wrong place to put a request-blocking decision.
SENIORQ63. Given a fixed monthly storage budget for full-content trace capture, how would you reason mathematically about the right sampling rate?

ROI: ★★★★☆ · Frequency: Medium-High

Estimate average captured-trace size (prompt + completion text, span metadata) and multiply by expected daily request volume to get storage-per-day at 100% capture; divide your budget's storage-per-day allowance by that figure to get a baseline sampling rate r. Then don't apply r uniformly (Q33) — reserve a portion of the budget for guaranteed 100% capture of errors and tail-latency requests (typically a small fraction of total volume but disproportionately valuable), and apply a lower random rate to the remaining "boring" successful traffic so the blended average storage cost still lands within budget while concentrating capture where debugging value is highest.

MIDQ64. Why is it important that metrics count 100% of requests even when traces are sampled at, say, 10%?

ROI: ★★★★☆ · Frequency: High

Metrics are cheap to store precisely because they're pre-aggregated — a Timer or Counter's memory footprint doesn't grow with request volume, only with the number of distinct tag combinations — so there's no real cost argument for sampling them. If you sampled metrics the same way you sample traces, your error-rate and latency-percentile numbers would themselves become statistically noisy estimates rather than exact counts, undermining the one pillar you specifically rely on for "is something wrong right now" alerting. Decoupling the two lets you sample traces aggressively for storage reasons while keeping the alerting-critical metrics exact.

SENIORQ65. A tool's failure rate metric spiked for six hours yesterday but no alert fired. How would you run this as a postmortem on your alerting design itself?

ROI: ★★★★☆ · Frequency: Medium-High

Check whether an alert rule existed for that specific metric at all — per-tool failure rate is easy to omit if alerting was only ever set up on the aggregate model-call error rate, which a single failing tool among several can dilute below any reasonable threshold. If a rule existed, check its threshold and window: a rate-based alert with too long an averaging window can smooth over a real six-hour spike, and a percentage-based threshold set relative to low baseline traffic can require an implausibly large absolute failure count to fire. The fix is almost always adding (or lowering the granularity of) alert rules per meaningful dimension — per tool, not just per model — which is the same lesson as Q42's design principle, learned the expensive way instead of proactively.

STAFFQ66. Design an internal shared library/starter that standardizes ObservationConvention customizations across a dozen Spring AI microservices, rather than asking every team to configure it themselves.

ROI: ★★★★★ · Frequency: High at staff level

Package a Spring Boot autoconfiguration module that ships a default ChatClientObservationConvention/ChatModelObservationConvention pair pre-wired with the org's standard low-cardinality tags (feature name resolved from a required application property, prompt version resolved from a convention on PromptTemplate metadata, tenant tier from a request-scoped bean interface each service must implement), plus a pre-built ObservationFilter for baseline PII redaction and a TestObservationRegistry-based contract test teams can drop into their own CI. Ship it as a versioned internal artifact with its own changelog and deprecation policy (Q54), and make it the default dependency new services pull in rather than an opt-in — the goal is that a team building their fifth Spring AI service in the org gets correct, consistent observability by depending on one starter, not by re-reading this chapter and reimplementing it from scratch.

Interview Gold Point: Note the organizational tradeoff explicitly: this trades some per-team flexibility for consistency, and the right way to handle a team with a genuinely unusual need is an documented extension point in the starter (a way to add extra tags without forking the convention), not an exception that lets them opt out of the shared schema entirely.
SENIORQ67. How does having rich AI-specific observability change your incident-response runbook compared to a typical REST API outage?

ROI: ★★★★☆ · Frequency: Medium-High

A typical REST outage runbook starts with "is it erroring or is it slow" and follows a fairly linear path through infrastructure layers. An AI feature incident runbook needs an earlier branch: "is it erroring/slow, or is it succeeding but producing bad output" — and the second path requires pulling in trace content, token/cost trends, and the async quality-eval score trend rather than infrastructure metrics alone, since none of those would flag a quality-only incident. A mature runbook explicitly lists both branches and the specific dashboards/queries for each, rather than assuming the on-call engineer will think to check quality telemetry only after infrastructure metrics come back clean — under incident pressure, people default to the runbook they're handed, not the one they'd ideally improvise.

MIDQ68. What does the gen_ai.operation.name attribute capture, and why is it a useful low-cardinality tag even in a service that only does chat completions today?

ROI: ★★★☆☆ · Frequency: Medium

It captures the kind of GenAI operation being observed — chat, embeddings, image generation, and so on — as a small, fixed-vocabulary tag. Even a service that only performs chat completions today benefits from tagging it explicitly rather than assuming context, because the moment that service adds an embedding call (for a new RAG feature, say) or a moderation call, your existing dashboards keep working correctly by operation type instead of silently mixing two different kinds of calls into one undifferentiated "requests" metric that no longer means what it used to.

SENIORQ69. Argue both sides: capturing full completion content on 100% of production traffic versus only a sampled fraction.

ROI: ★★★★☆ · Frequency: Medium-High

For 100%: no debugging investigation ever dead-ends at "we didn't happen to capture that one" (the exact gap that made Q35's investigation hard), and your async eval pipeline gets a complete, unbiased population to sample from rather than a sample-of-a-sample. Against 100%: storage cost scales linearly and can become the single largest line item in your observability spend at real traffic volume, every captured request is additional PII/compliance surface area (Section 13, Q49) regardless of whether it ever gets looked at, and most of that captured content is never actually queried, since the majority of requests are unremarkable. The pragmatic resolution most teams land on is the tiered approach from Q48 — sampled by default, forced to 100% specifically for error and flagged traffic — which captures nearly all the debugging value at a fraction of the storage and compliance cost of blanket full capture.

STAFFQ70. Without a labeled ground-truth evaluation dataset, design a weak-signal alerting system that could plausibly catch a silent quality regression using only telemetry you already collect for other reasons.

ROI: ★★★★★ · Frequency: Medium-High at staff level

Combine several independently-weak proxy signals into one composite alert rather than trusting any single one: a sustained rise in refusal-pattern rate (detected with a cheap heuristic classifier over captured completions, not a full LLM judge), a sustained shift in completion-length distribution (much shorter or much longer than the rolling baseline, both of which correlate with degraded behavior in practice), a rise in structured-output parse-repair rate (Q39), and a rise in follow-up-question rate in multi-turn conversations (a proxy for "the first answer didn't satisfy the user"). None of these alone proves a quality regression, but two or three moving in the same direction at once, on the same model/prompt version, is a strong enough correlated signal to trigger a targeted, synchronous eval-pipeline run rather than waiting for the next scheduled async evaluation cycle to catch it.

Interview Gold Point: Frame this explicitly as buying time, not replacing evaluation methodology — the composite alert's job is to shorten detection latency between "something degraded" and "someone starts investigating," while the actual root-cause diagnosis still depends on the deeper evaluation and testing disciplines covered in this series' dedicated chapters.
SENIORQ71. How would you track the cost and context-window pressure of a growing multi-turn conversation across a single session, using the chat-memory advisor's span?

ROI: ★★★★☆ · Frequency: Medium-High

Tag the advisor.chat-memory span (or a custom metric alongside it) with the cumulative prompt token count for that conversation turn — since chat memory means each new turn's prompt includes prior conversation history, prompt tokens grow monotonically within a session even if the user's new message is short. Aggregate this as a per-session metric (keeping the actual session ID off the low-cardinality metric tags, per Section 4.4, and instead bucketing by a coarse "turn number" or "context utilization percentage" range) to catch sessions approaching context-window limits before they hit a hard truncation or error, and to see cost-per-session growing in a way that a per-request-only view would never surface, since no single turn in a long conversation looks expensive on its own.

MIDQ72. Token usage metrics are missing entirely for a subset of requests in production. What would you check first?

ROI: ★★★★☆ · Frequency: Medium-High

First, whether those requests use a custom or less-common ChatModel implementation that doesn't fully populate Usage metadata on its ChatResponseMetadata — not every provider integration reports every field identically, and a partial implementation can silently return null/zero usage rather than throwing. Second, whether the affected requests are specifically streaming calls (Q31) that errored or were cancelled mid-stream before the terminal chunk carrying usage data ever arrived — a client disconnect partway through a stream is a legitimate reason for missing usage data. Cross-checking the affected subset against gen_ai.system/gen_ai.operation.name tags usually narrows it to one of these two causes quickly.

SENIORQ73. You've written a custom Advisor for domain-specific request rewriting. How do you give it its own span in the trace waterfall, consistent with the framework's built-in advisors?

ROI: ★★★★☆ · Frequency: Medium-High

Wrap the advisor's core logic in an explicit Observation — obtain the current ObservationRegistry (injected as a bean), call Observation.createNotStarted("advisor.my-custom-name", registry), populate low-cardinality key-values relevant to what the advisor does, and run the advisor's logic inside observation.observe(...) (or the manual start/stop/scope API for more control). Because this runs while the outer chat.client Observation is still open, Micrometer's context propagation automatically nests your new span as a child of it, so it appears in the waterfall exactly like advisor.retrieval-augmentation does, with no special registration beyond using the same registry.

STAFFQ74. Should a Spring AI-based organization build in-house LLM observability tooling or adopt a specialized platform like Langfuse or LangSmith? What factors would drive that decision?

ROI: ★★★★★ · Frequency: High at staff level

Building in-house makes sense when the organization already has significant Prometheus/Grafana/OTel investment and platform expertise, since Spring AI's instrumentation plugs into that stack for free (Section 9) — the marginal work is mostly dashboards, alerting rules, and the async eval pipeline, not new plumbing. Adopting a specialized platform makes sense when the priority is fast time-to-value on LLM-specific UX (prompt playgrounds, built-in eval scoring UIs, dataset curation for regression testing) that would otherwise be significant in-house product-engineering effort, or when the team lacks existing observability platform ownership entirely. A common and often correct middle path is both: keep infrastructure-level metrics and traces in the existing Micrometer/OTel stack (Section 8's architecture diagram already shows this split), and route a sampled subset of traces specifically to a specialized LLM eval platform for the workflows — prompt iteration, dataset-based regression testing — that general-purpose observability tooling doesn't do well.

SENIORQ75. Why is context-window utilization (tokens used relative to the model's maximum context) worth tracking as its own observability signal, separate from raw token counts?

ROI: ★★★★☆ · Frequency: Medium-High

Raw prompt token counts are only meaningful relative to the model's actual context limit — 8,000 tokens is trivial for a 128k-context model but critical for a 8k-context one — so a utilization percentage, computed by dividing observed prompt tokens by the known context limit for gen_ai.response.model, is what actually predicts risk of truncation, degraded long-context recall (a well-documented phenomenon where models attend less reliably to content in the middle of a very long context), or an outright context-length error. Tracking this as a distinct metric, especially for chat-memory-heavy multi-turn features (Q71), gives you an early warning well before requests start hitting hard context-length failures in production.

SENIORQ76. How would you attach a reliable prompt.version tag without scattering version-string literals across dozens of call sites in the codebase?

ROI: ★★★★☆ · Frequency: Medium-High

Centralize prompt version as metadata on the PromptTemplate or prompt-construction component itself — for example, a small wrapper that loads prompt templates from versioned resource files (or a prompt-management service) and exposes the resolved version alongside the rendered template — then have your custom ChatClientObservationConvention read that version off the request context rather than requiring every call site to manually set a tag. This keeps prompt versioning a property of the prompt-authoring layer, where it naturally belongs and where a change to it is a one-line diff, rather than a manually-maintained string duplicated at every place a prompt happens to be used.

MIDQ77. What's the difference between a Micrometer Timer and a DistributionSummary, and which applies to latency versus token counts?

ROI: ★★★☆☆ · Frequency: Medium

A Timer is specifically for measuring durations — it records elapsed time and exposes count, total time, and percentile/histogram data over that time dimension. A DistributionSummary is the general-purpose equivalent for any other numeric quantity you want the same percentile/histogram treatment for — token counts per request being the canonical example in this domain, since "what's the p95 completion-token count" is exactly as useful a question as "what's the p95 latency," but token count isn't a duration, so it uses DistributionSummary rather than Timer.

SENIORQ78. How would a runaway tool-calling loop reveal itself in span nesting depth and count metrics, distinct from how it would show up in cost metrics alone?

ROI: ★★★★☆ · Frequency: Medium-High

Cost metrics show the loop only in aggregate, after the fact, as an elevated total spend that requires investigation to attribute (Q29). The trace itself, if you can find one while the incident is live, shows it immediately and unambiguously: an abnormally long, flat sequence of alternating chat.model and tool.call spans under one outer chat.client span, often visibly failing to converge (the same tool called repeatedly with similar arguments). A "model calls per trace" or "tool calls per trace" histogram (Q45) is what turns this from something you'd only notice by opening one specific trace into something an alert can catch across all traffic automatically, since the histogram's tail lights up the moment loop behavior starts happening at any meaningful rate.

STAFFQ79. Design a multi-region observability rollup where different regions must sample or redact differently for regulatory compliance reasons.

ROI: ★★★★☆ · Frequency: Medium-High at staff level

Run a regional OpenTelemetry Collector tier per data-residency zone, each configured with region-specific redaction/retention processors (Q27) enforcing that region's requirements — an EU region collector, for instance, might apply stricter redaction and shorter retention on full-content capture than a region without equivalent constraints. Export fully redacted, aggregate-only metrics (never raw content) to a global rollup tier for org-wide dashboards, while keeping any full-content trace data region-local and never forwarded cross-region — this way the org still gets a single global view of cost, latency, and error trends, without any regional compliance boundary being violated by content that should never have left its region of origin in the first place.

SENIORQ80. How would you validate that your Observation-based instrumentation itself isn't introducing a memory or backpressure problem under sustained streaming load?

ROI: ★★★★☆ · Frequency: Medium

Load-test the streaming path specifically (not just non-streaming calls) while monitoring JVM heap and the exporter's own internal queue/buffer metrics — a Collector-bound exporter that batches spans before sending (Section 12) can build an unbounded backlog if export throughput falls behind span-creation rate during a sustained high-concurrency streaming spike, since each open stream keeps its Observation's context alive for the stream's full duration rather than the brief lifetime of a typical request. Confirm the exporter has bounded queue size and a defined backpressure/drop policy (most OTel exporters do, but defaults vary), and treat "instrumentation-induced OOM under load" as a real, testable failure mode rather than an assumption that observability overhead is always negligible.

MIDQ81. What does tagging by "operation type" (chat, embedding, image generation, moderation) buy you once a single service runs several kinds of model calls?

ROI: ★★★☆☆ · Frequency: Medium

It keeps aggregate dashboards meaningful as the service's capability grows — without an operation-type tag, "average latency" or "total tokens" silently becomes a blend of fundamentally different workloads (a millisecond-scale moderation check averaged in with a multi-second chat completion), which distorts every derived percentile and cost figure. With the tag, you can slice cleanly: chat latency stays comparable to chat latency, embedding cost stays comparable to embedding cost, and adding a new operation type to the service in the future doesn't quietly corrupt an existing dashboard that was implicitly built assuming only one kind of call existed.

SENIORQ82. p99 latency looks fine today, but p50 has crept up gradually over several weeks. How do you investigate a slow drift rather than a sudden spike?

ROI: ★★★★☆ · Frequency: Medium-High

A gradual p50 rise with a stable p99 suggests the typical-case request got slower, not that a new tail of pathological requests appeared — check for changes that would affect every request roughly equally: a growing average conversation/context length across the user base (Q75, gradually pushing more tokens into every prompt), a retrieval corpus that's grown larger without a corresponding index optimization, or a provider-side change to typical response verbosity. Because this is a trend rather than an incident, the right tool is a longer-window dashboard (weeks, not the usual hours) sliced by the same dimensions used elsewhere in this chapter — model version, feature, prompt version — to find which slice's median actually moved versus which stayed flat, narrowing the causal search before it becomes a guessing exercise.

STAFFQ83. Build the business case for investing engineering time in AI-specific observability tooling. What ROI would you present to leadership?

ROI: ★★★★☆ · Frequency: Medium-High at staff level

Frame it in terms leadership already budgets around: cost containment (a runaway-loop or prompt-regression detector, Q29/Q45, that catches a cost anomaly in minutes instead of at month-end billing reconciliation, is a directly quantifiable savings), incident time-to-resolution (a trace waterfall that turns a multi-hour blind debugging session into a five-minute root-cause lookup, Section 1), and risk reduction (catching a silent quality regression, Q70, before it becomes a customer-facing incident or a compliance issue, versus discovering it from a support ticket volume spike). The honest caveat worth including: the instrumentation itself is largely already free (Spring AI's Observation support requires no extra work beyond dependencies already needed for standard Actuator observability) — the actual investment being requested is in dashboards, alerting rules, and the async evaluation pipeline built on top of it, which is a much smaller ask than "build an AI observability platform from scratch" and should be presented as such.

SENIORQ84. Your agent architecture queues requests for async, batched processing rather than handling them synchronously within one HTTP request. How do you preserve trace correlation across that async boundary?

ROI: ★★★★☆ · Frequency: Medium-High

The automatic thread-local/reactor-context trace propagation that works within one synchronous or reactive request (Section 4.3) does not survive a message being placed on a queue and picked up by a separate worker process later — you have to propagate the trace context explicitly, by serializing the current trace ID (and, if relevant, baggage) into the queued message's headers/metadata at enqueue time, then re-hydrating an Observation context from those headers when the worker picks the message up, so the worker's spans attach as children of the original request's trace instead of starting a disconnected new one. Most messaging integrations Spring supports (Kafka, RabbitMQ) have existing Micrometer Tracing instrumentation that does exactly this automatically if it's on the classpath and configured — but it's worth explicitly verifying for a custom queue implementation rather than assuming it's handled.

MIDQ85. How does an Actuator health/readiness check differ in purpose from the metrics/traces covered throughout this chapter?

ROI: ★★★☆☆ · Frequency: Medium

A health/readiness endpoint answers a binary, present-tense question — "can this instance currently serve traffic" — typically used by an orchestrator (Kubernetes, a load balancer) to make routing and restart decisions, and it should be cheap and fast to evaluate. The metrics and traces this chapter covers answer a much richer, trend-and-detail-oriented question — "how has this system behaved over time and why did this specific request behave the way it did" — aimed at humans investigating, not machines making a pass/fail routing decision. A model provider being slow or expensive doesn't necessarily mean your service should fail its readiness check and get pulled from rotation, which is exactly why these are deliberately separate concerns with separate endpoints rather than one conflated signal.

SENIORQ86. Without a full evaluation pipeline in place yet, what lightweight "hallucination proxy" signals could you instrument and alert on today?

ROI: ★★★★☆ · Frequency: Medium-High

For a RAG feature specifically, a cheap and fairly reliable proxy is tracking how often the model's completion appears to introduce claims not traceable to the retrieved context — approximated cheaply (without a full LLM judge) by checking for named entities or numbers in the completion that don't appear anywhere in the retrieved documents passed into that same call, tagged and counted as a rate metric. Other proxies worth combining, echoing Q70's composite approach: unusually high confidence language ("definitely," "certainly") co-occurring with a low retrieval-similarity score for the same request, and a rising rate of user-initiated follow-up corrections in multi-turn conversations. None of these is a rigorous hallucination detector, but as an early, always-on warning layer sitting ahead of a proper evaluation pipeline, a rising trend on any of them is a legitimate trigger to prioritize building that pipeline sooner.

STAFFQ87. Who should own the observability attribute schema across an organization with many teams building Spring AI features, and what does that ownership concretely involve?

ROI: ★★★★☆ · Frequency: Medium-High at staff level

A platform/infrastructure team, not any individual product team, should own the shared schema — the same way a platform team typically owns the organization's logging format or its base Docker images — because the schema's value comes specifically from being consistent across teams, and no single product team is incentivized to maintain that consistency for everyone else's benefit. Concretely, ownership means: publishing and versioning the schema definition, shipping the enforcement tooling (the shared starter from Q66 and the CI contract test), reviewing and approving proposed extensions when a team has a genuinely new need, and running the deprecation process when the underlying OpenTelemetry GenAI conventions themselves change (Q19/Q93) so individual teams aren't each independently tracking upstream spec churn.

SENIORQ88. Frame the tradeoff between 100% trace capture and sampling in terms of the cost of a missed catastrophic failure versus the cost of over-collection.

ROI: ★★★★☆ · Frequency: Medium-High

Over-collection's cost is continuous and certain — storage, compliance surface, and export overhead scale with every request you fully capture, whether or not you ever look at it (Q69). Under-sampling's cost is discrete and probabilistic — it only materializes on the rare occasion a genuinely catastrophic request happens to fall outside your sample and you need exactly that trace to understand an incident. The resolution isn't choosing one extreme; it's making the sampling policy itself risk-aware rather than uniformly random, which is precisely what tail-based sampling (Q33) achieves — by keeping 100% of errors and anomalies (where catastrophic failures overwhelmingly live) while sampling down the "boring" traffic, you get close to the debugging value of 100% capture at a small fraction of its storage cost, converting a binary tradeoff into a much better Pareto point.

MIDQ89. How would you write a test that regression-proofs your observability instrumentation itself, so a refactor can't silently drop a tag or a span?

ROI: ★★★☆☆ · Frequency: Medium

Using TestObservationRegistry (Q30), register it in place of the real registry for a test-scoped ChatClient, make a call against a mocked or stubbed model response, and assert against the registry's recorded observations — that an observation with the expected name was started and stopped successfully, and that it carries the specific low-cardinality key-values (feature name, prompt version) your custom convention is supposed to attach. Run this as an ordinary part of your test suite so a future refactor that accidentally drops the custom ObservationConvention registration, or changes a tag's key/value, fails CI the same way a functional regression would — rather than only being discovered when a downstream dashboard quietly stops populating in production.

SENIORQ90. Where in the Advisor chain's execution order does the chat.client Observation actually open and close, relative to individual advisors mutating the request and response?

ROI: ★★★★☆ · Frequency: Medium-High

The outer chat.client Observation wraps the entire advisor chain invocation — it opens before the first advisor runs and closes after the last advisor has finished processing the (possibly model-augmented) response, meaning it captures the full end-to-end latency including every advisor's own work, not just the model call itself. Individual advisors that want their own visibility into just their slice of that time (retrieval, memory lookup) need to open their own child Observation inside their own logic, exactly as described in Q73 — the framework doesn't automatically give every advisor its own span for free, only the ones Spring AI ships with (retrieval augmentation, chat memory) do, because those specific advisors were explicitly instrumented by the framework authors.

STAFFQ91. Design a single-pane-of-glass dashboard architecture for engineering leadership covering cost, latency, quality, and reliability across many AI features built by different teams on Spring AI.

ROI: ★★★★★ · Frequency: High at staff level

The foundation has to be the standardized schema from Q54/Q87 — without every team's feature emitting the same feature.name, prompt.version, cost, and quality-score dimensions consistently, a cross-feature rollup dashboard is either impossible or misleading. Structure the dashboard itself in tiers: a top-level view aggregating cost, p95 latency, error rate, and quality score to one row per feature (echoing the PM-facing simplification from Q56, but for an engineering leadership audience that also wants the technical dimensions available), with drill-down from any row into that feature's own detailed dashboards (the trace waterfalls, per-model breakdowns, and alerting this chapter builds throughout). Feed it from the same underlying Micrometer/OTel pipeline every team already exports to (Section 8), not a separate reporting pipeline requiring teams to double-instrument — and pair it with a lightweight weekly automated digest (biggest cost movers, quality-score regressions, new fallback-route activity) so leadership gets the signal without needing to actively query the dashboard themselves.

Interview Gold Point: Emphasize that this whole design only works because Spring AI observability was built on Micrometer/Actuator from day one (Section 9) — a leadership rollup spanning a dozen teams' worth of independently-built AI features is a governance and schema problem, not a new instrumentation problem, precisely because the underlying plumbing was already unified.
SENIORQ92. Why might your trace-sampling rate and your log-sampling rate legitimately differ for the same AI feature?

ROI: ★★★★☆ · Frequency: Medium-High

Traces and logs have different storage economics and different consumption patterns — a trace is a structured, queryable unit naturally suited to statistical sampling because a dashboard aggregating "10% of traces" still produces a valid, if noisier, percentile estimate (Q64), whereas logs are often consulted for a specific known request (via trace-ID correlation, Q43) rather than aggregated statistically, so sampling them can mean the specific log line an engineer needs for a specific incident simply doesn't exist. A common pattern is sampling traces more aggressively than logs, or keeping logs at a coarser granularity (structured summary lines) at 100% while only full-content, high-detail logs are sampled — the right rates are a genuinely separate decision per pillar, not one number applied uniformly across both.

STAFFQ93. The OpenTelemetry GenAI semantic conventions are still evolving. How do you future-proof your instrumentation layer against attribute names changing underneath you?

ROI: ★★★★☆ · Frequency: Medium-High at staff level

Don't let dashboards, alerting rules, and downstream consumers query raw gen_ai.* attribute names directly at scale — introduce a thin normalization layer (a Collector processor, or your own ObservationConvention wrapper) that maps whatever the current upstream spec calls a field onto your organization's own stable internal attribute names, so a spec revision, or a Spring AI version bump that follows it, requires updating one mapping layer rather than hunting down every dashboard and alert query across every team that happened to reference the old raw name directly. Pin Spring AI and OTel dependency versions deliberately, review the GenAI conventions changelog before bumping either, and treat this exactly like any other unstable external API dependency — because, at this point in the ecosystem's maturity, that's precisely what it is.

STAFFQ94. Zooming out: why is observability, more than any other topic in this volume, the discipline that determines whether an AI feature is actually safe to leave running unattended in production?

ROI: ★★★★★ · Frequency: High at staff level

Every other chapter in this volume — retrieval, advisors, tool calling, MCP — adds capability, and capability without visibility is precisely what makes a system dangerous to operate unattended: a more capable agent that can retrieve documents, call tools, and chain multiple model calls together has more ways to fail expensively, silently, and non-reproducibly than a simple single-call chatbot, exactly because non-determinism and plausible-but-wrong output mean the traditional safety net of "it'll throw an exception if something's wrong" doesn't apply (Section 3). Observability is what converts that expanded capability back into something a human can trust running without direct supervision — cost guardrails that catch a runaway loop before it becomes a five-figure bill (Q29, Q45, Q62), trace waterfalls that turn an opaque bad-answer report into a five-minute root-cause investigation (Q35), and quality telemetry that catches a silent regression before a customer does (Q70, Q86). A team that ships tool-calling agents without this instrumentation hasn't avoided the failure modes this chapter describes; they've simply chosen not to be able to see them until a customer, or an invoice, tells them.

16. SUMMARY

  • AI systems fail differently from ordinary services — the costliest failures are confident, well-formed, wrong answers that never throw an exception — so observability must go beyond the classical logs/metrics/traces trio to include a fourth pillar: quality/evaluation telemetry.
  • Cardinality discipline is the single most important operational rule in this chapter: low-cardinality values (model name, provider, feature) belong on metrics; high-cardinality payloads (prompts, completions) belong only in traces and logs.
  • Spring AI's observability is not a parallel system — it is built directly on Micrometer's Observation API already powering Spring Boot Actuator, using ChatClientObservationConvention and ChatModelObservationConvention to emit standard, OpenTelemetry-GenAI-aligned gen_ai.* attributes and metrics automatically.
  • Token usage, exposed uniformly across providers via ChatResponseMetadata's Usage object, is the foundation for near-free, real-time cost tracking — no billing API call required.
  • Tracing overhead, storage cost, and synchronous evaluation latency are real trade-offs; production systems sample intelligently (100% of errors/tail latency, downsampled routine traffic) rather than capturing everything unconditionally.
  • Observability data is itself sensitive — prompts, completions, and system prompts routed through third-party observability backends deserve the same redaction discipline and access control as the production data they represent.
