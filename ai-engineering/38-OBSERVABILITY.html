CHAPTER 38 — OBSERVABILITY

Volume 2 — Spring AI · Chapter 13 of 15

The MCP Integration chapter gave your application the ability to reach out — through a standard protocol — to tools, resources, and other agents it does not own. That is a strict increase in the number of moving parts between a user's question and a final answer: a model call, a tool discovery round trip, one or more remote tool invocations, and a synthesis step, potentially chained across several MCP servers you do not control. The moment you have that many hops, "it worked in my local test" stops being useful information, because you cannot know which hop was slow, wrong, expensive, or silently degraded without instrumenting the system to tell you. Observability is the discipline that turns "the agent gave a bad answer" from a mystery into a five-minute investigation.

1. MOTIVATION

Every earlier chapter in this volume has been about making your Spring Boot application do more with AI — call a model, hold a conversation, retrieve context, call tools, talk to MCP servers. This chapter is about something different and, for anyone who intends to run this in production, more important: knowing what actually happened after it happened. Traditional backend observability was built around a comfortable assumption you have relied on for years — a request either succeeds or throws, and when it throws, a stack trace tells you exactly which line of code is at fault. AI-infused systems break that assumption in a specific, uncomfortable way: the most expensive, most damaging failures are the ones that return HTTP 200 with a perfectly well-formed, confident, wrong answer.

Concretely, once your application is calling a foundation model, you now have a component whose behavior can drift across model provider updates you did not request, whose cost varies token-by-token with every user's phrasing, whose latency is dominated by a network call to infrastructure you don't operate, and whose correctness cannot be checked with a simple equality assertion. If you cannot answer, for any given production request, questions like "which model version answered this," "how many tokens did this cost," "how long did the retrieval step take versus the generation step," "did a tool call fail and get silently retried," and "is this week's average response quality worse than last week's" — you are not running an AI system, you are running a black box with a Spring Boot label on it. Observability is what converts the box back into an inspectable system.

There is a second, more strategic reason this chapter sits here, right before Testing (Chapter 39) and the closing chapters of this volume. Testing an LLM-backed feature with pre-production test suites alone was already shown, in earlier chapters, to be necessary but insufficient — the space of real user inputs is larger than any test suite you will write. Observability is the mechanism that closes that gap: it is testing that never stops, running continuously against real traffic, catching the failure modes your test suite never imagined because it is watching the actual distribution of what users say, not the distribution you guessed at design time.

2. HISTORICAL BACKGROUND

2.1 From Log Files to the Three Pillars

Backend observability did not arrive fully formed. Early systems had exactly one tool: the log file, grepped by hand after something broke. As systems grew distributed, this stopped scaling — a single user request might touch a dozen services, and no single log file contained the whole story. The industry converged, over roughly two decades, on what became known as the three pillars of observability: logs (discrete, timestamped events, good for "what exactly happened at this moment"), metrics (aggregated numeric time series, good for "how is the system behaving on average, right now, and is it trending"), and traces (the causal chain of spans showing how a single request propagated across services, good for "where did the time and the failure actually happen inside this one request"). Tools like Prometheus (metrics), the ELK stack (logs), and Zipkin/Jaeger (traces) each grew up to serve one pillar, and Micrometer emerged in the Java ecosystem specifically to give Spring Boot applications a single, vendor-neutral instrumentation API that could export to any of these backends.

2.2 OpenTelemetry: One Instrumentation Standard

The next major shift was consolidation. Each observability vendor originally shipped its own proprietary instrumentation agent, which meant switching vendors meant re-instrumenting your entire codebase. OpenTelemetry (OTel), formed by merging two earlier projects (OpenTracing and OpenCensus), became the industry-standard, vendor-neutral specification and SDK for producing traces, metrics, and logs, with a well-defined wire protocol (OTLP) that any backend can ingest. Spring's own observability story — Micrometer for metrics and Micrometer Tracing for distributed traces — is designed to bridge cleanly into OpenTelemetry, so a Spring Boot application can be instrumented once and shipped to Prometheus, Grafana, Zipkin, Jaeger, Datadog, or any OTLP-compatible backend without touching business code.

2.3 The Missing Fourth Pillar: LLM-Specific Observability

None of the three pillars above were designed with "a single request can cost a variable amount of money depending on how many tokens the model decided to generate" in mind, nor with "the same input can legitimately produce a different output on every call" in mind. As LLM-backed applications went into production starting around 2022–2023, teams discovered that standard APM dashboards — request count, latency, error rate — were necessary but silent on the questions that actually mattered for AI features: token consumption and cost per request, prompt and completion content for debugging quality regressions, which retrieved documents fed into a given answer, and whether a chain of tool calls terminated correctly or looped. This gap produced a new category of purpose-built tooling (LangSmith, Langfuse, Traceloop/OpenLLMetry, Arize Phoenix, among others) built specifically to capture prompts, completions, token usage, and evaluation scores as first-class observability data — and it produced a standardization effort inside OpenTelemetry itself: the GenAI semantic conventions, a set of standard span and attribute names (prefixed gen_ai.*) so that "which model," "how many input tokens," and "how many output tokens" are captured the same way regardless of vendor. Spring AI's own observability support, covered in depth later in this chapter, is built directly on top of this convention.

Why this history matters to you as an engineer: Spring AI did not invent a parallel observability universe for AI. It deliberately plugged its instrumentation into the same Micrometer Observation API that already powers Spring Boot Actuator's metrics and traces for your database calls, your HTTP clients, and your message queues. This means an AI-specific request shows up in the exact same Grafana dashboard, the exact same trace waterfall in Zipkin, and the exact same alerting pipeline as everything else your platform team already operates — you are extending existing infrastructure, not standing up a second one.

3. PROBLEM STATEMENT

Given a production system whose core component (a foundation model call) is non-deterministic, has variable and non-trivial per-request cost, and can fail silently by returning a plausible-but-wrong answer — instrument that system so that engineers can, after the fact and in real time, reconstruct exactly what happened, how much it cost, how long each stage took, and whether the output was trustworthy, without re-running the request.

Unpack the constraints in that statement, because each one rules out an approach that would work fine for ordinary CRUD services. "Non-deterministic" means you cannot debug by simply re-running the same request in a debugger and expecting the same trace — you must capture enough context at the time of the original call that you never need to reproduce it. "Variable, non-trivial per-request cost" means cost itself becomes a first-class metric you must track per request, per user, and per feature, the same way you would track latency — this did not exist as a concern for a typical REST endpoint. "Fails silently with a plausible-but-wrong answer" means your instrumentation cannot rely purely on exceptions and HTTP status codes as the failure signal; you need to capture the actual prompt and response content (subject to the privacy constraints covered in Section 13) so a human, or an automated evaluator, can judge quality after the fact.

There is a second, structural half of this problem that is easy to under-scope: a real AI feature, as built across this volume, is a pipeline — retrieval, prompt construction, advisor chain, the model call itself, possibly one or more tool invocations, and response post-processing. Observability must attribute latency and cost to the correct stage of that pipeline, not just to the endpoint as a whole, or you will be staring at "this request took 4 seconds" with no way to tell whether 3.8 of those seconds were the vector search, the model, or a flaky downstream tool.

4. THEORY

4.1 The Three Pillars, Refreshed for This Domain

You already know logs, metrics, and traces conceptually from ordinary backend work — the theory does not change, only the payload does.

  • Logs in an AI context capture discrete events with rich, often large payloads: the exact prompt sent, the exact completion received, which advisor modified the request, which tool was invoked with what arguments. Spring AI's SimpleLoggerAdvisor exists specifically to produce this kind of log entry for every ChatClient call.
  • Metrics capture numeric time series you aggregate and alert on: request count, latency percentiles, token counts (prompt and completion, tracked separately because they are priced and behave differently), error rate, and cost. These are cheap to store and query at high volume precisely because they are aggregated — you lose the individual request's content, in exchange for being able to ask "is p95 latency degrading this week" cheaply across millions of requests.
  • Traces capture the causal, hierarchical shape of a single request as a tree of spans — one span for the incoming HTTP request, a child span for retrieval, a child span for the model call, a child span for each tool invocation. A trace answers "where, inside this one specific slow or failed request, did the time actually go," which no amount of aggregated metrics can answer on its own.

4.2 The Fourth Pillar: Evaluation Signal

An AI-specific addition sits alongside the three classical pillars: quality/evaluation telemetry — a numeric or categorical signal representing "was this response good," produced either by an automated judge (an LLM-as-judge pattern, covered in depth in the Evaluation chapters of this series), a heuristic (did the response contain a refusal, did structured output parse successfully), or explicit user feedback (a thumbs up/down button). This is not optional polish; without it, your logs and traces can tell you the system was fast and cheap while it was quietly producing wrong answers, because "fast, cheap, and 200 OK" says nothing about correctness. Mature AI observability platforms treat this evaluation signal as a metric you can slice by model version, prompt version, or retrieval configuration — the same way you would slice error rate by deployment version in ordinary APM.

4.3 Spans, Traces, and Context Propagation — Mental Model

A span is a single named, timed unit of work with a start time, an end time, a set of key-value attributes ("tags"), and a parent-child relationship to other spans. A trace is simply the full tree of spans that share one root — the entire life of one incoming request, end to end, across every internal hop. The mechanism that makes this tree assembleable after the fact, even across network calls to other services, is context propagation: a trace ID and the current span ID are carried along — inside the current thread via a context object, and across process boundaries via HTTP headers (typically the traceparent header defined by the W3C Trace Context standard) — so that a span created deep inside a tool call, in a different service, still knows which trace it belongs to and which span is its parent. Micrometer Tracing and OpenTelemetry both implement this propagation automatically for common transports (Spring's RestClient/WebClient, message brokers, and so on), which is precisely why Spring AI's instrumentation "just works" as part of an existing trace rather than starting an unconnected trace of its own.

4.4 Cardinality — the Concept That Will Bite You If You Skip It

Cardinality is the number of distinct values a given tag/attribute can take. A tag like http.status has low cardinality (a handful of values); a tag like user.id or, critically for this chapter, the full prompt text, has effectively unbounded cardinality. Metrics backends like Prometheus create a new, separately-stored time series for every unique combination of tag values, so attaching a high-cardinality value (a full prompt, a user ID, a session ID) as a metric tag can silently multiply your storage and query cost by orders of magnitude or crash your metrics backend outright — this single concept explains why Spring AI's Observation API deliberately separates low-cardinality key values (safe for metrics: model name, operation type, provider) from high-cardinality key values (safe only for traces/logs, never for metrics: the actual prompt content, token-level detail).

5. INTERNAL WORKING

Walk through what actually happens, mechanically, when a Spring AI application configured with observability makes one ChatClient call inside a request that already has tracing enabled (the default in a Spring Boot application with the Actuator and Micrometer Tracing starters on the classpath).

  1. A trace is already in flight. The incoming HTTP request was intercepted by Spring's tracing instrumentation, which created a root span and stored the current Observation/trace context in a thread-local (or reactor context, for WebFlux) so that anything called from within this request can find it.
  2. Your controller calls chatClient.prompt().user(question).call().content(). Internally, Spring AI's ChatClient does not call the model directly — it goes through an Advisor chain (the same Advisor abstraction covered in the Advisors chapter). Each advisor in the chain — memory, retrieval augmentation, logging, your own custom advisors — gets a chance to inspect or modify the request before it reaches the model, and the response before it returns to the caller.
  3. An Observation is opened for the chat client call. Spring AI wraps the call in a Micrometer Observation, using a purpose-built ChatClientObservationConvention that knows how to translate a chat request/response pair into observation key-values — this is the integration point that makes the AI-specific call look, to Micrometer, like any other observed operation (a database query, an HTTP client call) that your existing tracing and metrics backends already know how to render.
  4. The underlying ChatModel call is separately observed. Because the Advisor chain can retry, branch, or call the model more than once (for example, during tool-calling loops), the actual model invocation gets its own nested Observation/span via ChatModelObservationConvention, distinct from the outer ChatClient span. This nesting is what lets a trace waterfall show "the ChatClient call took 2.1s, of which the underlying model call took 1.9s, and the memory-advisor lookup took 0.2s" as separate, attributable spans.
  5. Low-cardinality attributes are attached as tags on both the span and any generated metrics — gen_ai.system (the provider, e.g. openai), gen_ai.request.model, gen_ai.response.model (these can differ if the provider silently routes to a different underlying model version), and the operation name. High-cardinality attributes — the actual prompt and completion text, if you have opted in to capturing them — are attached only to the trace span's detailed view or to a log record, never to the metrics time series, for the cardinality reason explained in Section 4.4.
  6. Token usage is read off the model response's metadata — every ChatResponse carries a ChatResponseMetadata object with a Usage object exposing prompt tokens, generation (completion) tokens, and total tokens, as reported by the provider. Spring AI's observation support surfaces these as observation key-values (gen_ai.usage.input_tokens, gen_ai.usage.output_tokens) so a Micrometer meter can aggregate them into token-consumption metrics without you writing any counting code yourself.
  7. The Observation closes, emitting to every registered ObservationHandler. A TracingObservationHandler turns it into a span exported via OTLP (to Zipkin, Jaeger, or an OpenTelemetry Collector); a MeterObservationHandler turns it into Micrometer counters/timers exported to Prometheus or another metrics backend. Both happen from the exact same instrumentation call site — you do not write separate code for "log this" and "trace this" and "meter this."
  8. If the model call throws (timeout, rate limit, malformed response), the Observation is marked as an error, the exception is attached to the span, and standard Micrometer error-count metrics increment — this is the one failure mode that behaves exactly like ordinary APM, because it is an actual exception, not a silent wrong answer.

The edge case worth reasoning through yourself: what happens during streaming responses (ChatClient.stream())? The Observation's span cannot close until the last chunk has been emitted, because token counts and final response metadata are only known once the stream completes — this means a streaming call's span duration reflects "time to fully drain the stream," not "time to first token," and if you care about perceived latency (a UX metric that matters a great deal for chat interfaces) you need a separate, custom-instrumented measurement for time-to-first-token, since the standard span will not give it to you for free.

6. MATHEMATICS

Observability for AI systems needs very little formal mathematics, but the handful of ideas it does need are used constantly and are worth being precise about.

6.1 Percentiles, Not Averages

The average (mean) latency of your model calls is one of the least useful numbers you can report, because LLM latency distributions are heavily right-skewed: most calls finish quickly, but a meaningful tail takes far longer (provider-side queuing, longer generations, retries). Reporting only the mean hides that tail completely. Instead, observability systems report percentiles: p50 (median — half of requests are faster than this), p95 and p99 (95%/99% of requests are faster than this — these numbers surface the tail your users actually experience during the worst moments). Micrometer computes these via histogram-based Timer instruments attached to each Observation, and the formula intuition is simple: sort all observed latencies, and the p-th percentile is the value at position p/100 × N in that sorted list (implementations approximate this with bounded-memory histograms rather than storing every raw value, since storing every raw value at production scale is not memory-feasible).

6.2 Cost as a Linear Function of Tokens

Per-request cost is not mysterious — it is a simple linear function most providers price directly: 

cost(request) = (prompt_tokens  × price_per_input_token)
              + (completion_tokens × price_per_output_token)

The reason this belongs in an observability chapter rather than a pure finance spreadsheet is that prompt_tokens and completion_tokens are exactly the two numbers your instrumentation is already capturing per request via Usage metadata (Section 5). Once you are emitting those two numbers as metrics tagged by model and by feature/endpoint, computing running cost is a Grafana query, not a new engineering effort — this is the single highest-leverage dashboard most teams build in their first week of running an AI feature in production, because it is the earliest warning of a runaway agent loop or an unexpectedly verbose system prompt.

6.3 Sampling Math for Traces

Tracing every single request in full detail (especially with high-cardinality prompt/completion content attached) is expensive to store and, at high volume, unnecessary. Sampling trades completeness for cost: if you sample at rate r (say, 10% = 0.1), you retain full traces for a random r fraction of requests while still counting all requests toward aggregate metrics (metrics and traces are typically decoupled for exactly this reason — you never want to lose your error-rate metric just because you are only tracing 1 in 10 requests). A common refinement is tail-based sampling: buffer a trace's spans temporarily and decide whether to keep it only after seeing whether it errored or exceeded a latency threshold — guaranteeing that the requests most worth debugging are never the ones a flat random sample happened to drop.

Two design decisions in this architecture recur across almost every real deployment. First, PII redaction happens at the Collector, not in every individual service — centralizing it means you enforce one redaction policy instead of trusting every team to remember to scrub before exporting. Second, the "quality" pipeline on the bottom is deliberately decoupled from the real-time metrics pipeline: automated LLM-as-judge evaluation is itself a model call, with its own latency and cost, so it runs asynchronously against a sampled subset of production traffic rather than blocking the user-facing request.

9. JAVA / SPRING PERSPECTIVE

Spring AI's observability is not a bolt-on — it is built directly on the same io.micrometer.observation API that Spring Boot Actuator already uses for HTTP server requests, RestClient calls, and R2DBC/JDBC queries. If your application already has spring-boot-starter-actuator plus a Micrometer Tracing bridge (micrometer-tracing-bridge-otel, typically) and a metrics registry (micrometer-registry-prometheus) on the classpath, Spring AI's ChatClient and ChatModel calls are observed automatically the moment you inject an ObservationRegistry bean — no extra annotation is required on your own code. 

// build.gradle / pom.xml dependencies (conceptually):
//   spring-boot-starter-actuator
//   micrometer-tracing-bridge-otel
//   micrometer-registry-prometheus
//   opentelemetry-exporter-otlp   (or a Zipkin exporter)

@Configuration
class ObservabilityConfig {

    // ObservationRegistry is auto-configured by Spring Boot when Actuator
    // + Micrometer are on the classpath; injecting it here is enough for
    // Spring AI's ChatClient/ChatModel beans to pick it up automatically.

    @Bean
    ObservationRegistryCustomizer<ObservationRegistry> addTraceIdLogging() {
        // Example customizer: attach any cross-cutting handler you need,
        // e.g. a handler that copies trace/span IDs into MDC for log
        // correlation, so every log line for a request carries the same
        // trace_id a Zipkin/Jaeger trace uses.
        return registry -> registry.observationConfig()
            .observationHandler(new ObservationTextPublisher());
    }
}

@Service
class SupportAssistant {

    private final ChatClient chatClient;

    SupportAssistant(ChatClient.Builder builder) {
        this.chatClient = builder
            .defaultAdvisors(new SimpleLoggerAdvisor()) // logs request/response
            .build();
    }

    public String answer(String question) {
        ChatResponse response = chatClient.prompt()
            .user(question)
            .call()
            .chatResponse();

        Usage usage = response.getMetadata().getUsage();
        log.info("model={} promptTokens={} completionTokens={} totalTokens={}",
            response.getMetadata().getModel(),
            usage.getPromptTokens(),
            usage.getGenerationTokens(),
            usage.getTotalTokens());

        return response.getResult().getOutput().getText();
    }
}

A few Spring AI-specific mechanics worth naming precisely, because interviewers and code reviewers will expect the correct vocabulary:

  • SimpleLoggerAdvisor is a ready-made Advisor (from the Advisors chapter's family of CallAdvisor/StreamAdvisor implementations) that logs the outbound request and inbound response of every ChatClient call it wraps — the fastest way to get human-readable request/response logs without writing a custom advisor.
  • ChatClientObservationConvention and ChatModelObservationConvention are the extension points that decide which key-values get attached to the ChatClient-level and the underlying ChatModel-level Observations respectively — implement a custom convention when you need to add your own low-cardinality tags (for example, a feature.name tag identifying which product feature triggered the call) without touching every call site.
  • ChatResponseMetadata / Usage (in org.springframework.ai.chat.metadata) is the standard, provider-agnostic surface for reading token counts and the actual model identifier that answered — because Spring AI normalizes this across providers, your dashboards and cost calculations don't need provider-specific branches.
  • Actuator's /actuator/metrics and /actuator/prometheus endpoints expose everything above without you writing a controller — the same endpoints you already use for JVM heap and HTTP metrics now also expose gen_ai.*-derived counters and timers.

This is the same design philosophy this series keeps returning to: Spring AI treats "observing a model call" as a specialization of "observing any external dependency," using the exact same Observation abstraction Spring Boot already applies to your database and HTTP clients — you are not learning a second observability stack, you are learning what tags a familiar one now carries.

10. BEST PRACTICES

  • Always tag metrics and traces with model name, model version, and prompt/feature version. Without this, you cannot answer "did the provider's silent model update at 3am cause this week's quality drop" or "did prompt v14 regress cost versus v13" — both are routine production questions.
  • Track token usage and cost as first-class metrics from day one, not as an afterthought computed from a billing invoice at month-end. Per-feature, per-user cost attribution is the earliest and cheapest warning system for a runaway agent loop or a prompt regression that suddenly triples token usage.
  • Separate low-cardinality tags (safe for metrics) from high-cardinality payloads (safe only for traces/logs), exactly as Spring AI's Observation conventions do — never let a full prompt string become a metric tag.
  • Correlate logs, traces, and metrics via a shared trace ID propagated into your logging MDC, so a single click from a trace waterfall takes you straight to the exact log lines for that request.
  • Sample intelligently, not uniformly — keep 100% of error and high-latency traces (tail-based sampling), and only randomly downsample the "boring," fast, successful traffic.
  • Instrument time-to-first-token separately from total response time for any streaming/chat UX, since users perceive the former, not the latter, and standard span duration measures the latter.
  • Build a continuous, sampled evaluation pipeline (Section 4.2) alongside classical observability — a system can be fast, cheap, and error-free while still being wrong, and only quality telemetry catches that.

11. COMMON MISTAKES

  • Logging or tagging with raw prompt/completion text as a metrics label. This explodes cardinality (Section 4.4) and can crash or bankrupt a metrics backend; prompt/completion content belongs in traces or dedicated log storage, never in a Prometheus label.
  • Treating "no exception thrown" as "the request succeeded." A malformed structured-output response, a hallucinated fact, or a tool call that silently returned stale data all complete without throwing — this is precisely why quality/evaluation telemetry (Section 4.2) is not optional.
  • Only monitoring the outer request latency, not per-stage latency. Without child spans for retrieval, each model call, and each tool call, "this endpoint is slow" gives you no actionable next step — as the trace waterfall in Section 7.1 demonstrated.
  • Shipping full prompts and completions to a third-party trace/log backend without redaction. This is both a security issue (Section 13) and, in regulated industries, a compliance violation if the prompt contains customer PII or regulated data.
  • Forgetting that streaming responses distort duration-based metrics. A naive span-duration metric for a streamed chat response measures "time to fully drain the stream," which can look artificially slow compared to perceived UX, misleading whoever is reading the dashboard.
  • Ignoring provider-side model drift because dashboards only track your own deploys. If you don't tag and monitor gen_ai.response.model, a provider's silent version bump behind a stable model alias can change behavior with no corresponding entry in your own deployment history to investigate.

12. PERFORMANCE CONSIDERATIONS

Observability itself has a cost, and it is worth being honest about the trade-offs rather than instrumenting everything unconditionally.

  • Tracing overhead is small but non-zero — creating spans, propagating context, and serializing/exporting them consumes CPU and adds a small amount of latency per request, which is why high-throughput systems sample rather than trace every request at 100%.
  • Capturing full prompt/completion payloads multiplies storage cost fast. A chat feature at meaningful scale can generate gigabytes of prompt/completion text per day; decide deliberately what fraction of traffic gets full-payload capture versus metrics-only visibility, and set retention windows accordingly (you rarely need full-text traces older than a few weeks).
  • Synchronous evaluation adds latency you usually cannot afford. Running an LLM-as-judge quality check inline, before responding to the user, doubles your model-call latency and cost for every request — this is why quality evaluation, as shown in Section 8's architecture, almost always runs asynchronously against sampled traffic rather than in the request's critical path.
  • Token/cost metrics are nearly free to compute because the numbers are already present in the response metadata (Section 5) — there is essentially no performance argument against tracking them, only an implementation-effort one, which is small.
  • Batching and buffering exporters matters at scale. Sending one network call per span/metric to your Collector will itself become a bottleneck; production exporters batch spans and metrics before sending, trading a small amount of export latency for a large reduction in network overhead.

13. SECURITY CONSIDERATIONS

Observability data is, itself, a security and privacy surface that is easy to overlook because it feels like "internal engineering plumbing" rather than user data — but a trace that captures a full prompt containing a customer's account number, medical detail, or an internal system prompt with embedded credentials is exactly as sensitive as the request that produced it, and it is now duplicated into a third-party observability backend with its own access controls, retention policy, and export logs.

  • Redact before export, not after. PII scrubbing should happen as close to the source as possible — ideally in an OpenTelemetry Collector processor or a custom ObservationFilter — so raw sensitive content never leaves your infrastructure boundary in the first place.
  • Treat system prompts as secrets in traces, the same way you treat API keys as secrets in logs. A system prompt often encodes business logic, guardrail instructions, or proprietary process detail — leaking it through an over-permissive trace viewer is a real, if underappreciated, information-disclosure risk, and it directly enables the prompt-injection and prompt-extraction attacks covered in earlier chapters.
  • Apply the same access control to your observability backend that you apply to production databases. A trace viewer with prompt/completion capture enabled is, functionally, a searchable archive of everything users have told your AI feature — it deserves the same RBAC and audit logging as any datastore holding user content.
  • Watch for injected content surfacing in your own telemetry. If an attacker's prompt-injection payload gets logged verbatim and later rendered unescaped in an internal observability dashboard, you have created a second-order injection surface (e.g., stored XSS in a web-based trace viewer) — treat observability tooling as untrusted-content-rendering surfaces too.
  • Be honest that this is a moderate, not extreme, security surface. Observability data is a confidentiality and compliance concern, not typically a direct remote-code-execution vector — the bulk of the security burden in an AI system still sits with input validation, guardrails, and sandboxing covered in dedicated later chapters; this chapter's job is narrowly to make sure your telemetry pipeline doesn't become the leak.

14. INTERVIEW QUESTIONS

JUNIORQ1. What are the three classical pillars of observability, and what does each one answer?

ROI: ★★★★★ · Frequency: Extremely High

Logs (discrete timestamped events — "what exactly happened"), metrics (aggregated numeric time series — "how is the system behaving on average, and is it trending"), and traces (the causal tree of spans for one request — "where inside this specific request did time/failure occur"). Each is optimized for a different question and a different storage/query trade-off.

JUNIORQ2. Why isn't "the request returned HTTP 200 with no exception" sufficient evidence that an AI feature worked correctly?

ROI: ★★★★☆ · Frequency: High

Because an LLM can produce a fluent, well-formatted, confident answer that is factually wrong or based on a misread of retrieved context — this completes successfully at the HTTP and exception-handling level while still being a functional failure. Standard error-rate monitoring cannot catch this; it requires a separate quality/evaluation signal.

MIDQ3. What is cardinality, and why does it matter specifically when instrumenting LLM calls?

ROI: ★★★★★ · Frequency: Extremely High

Cardinality is the number of distinct values an attribute/tag can take. Metrics backends like Prometheus create a separate stored time series per unique tag-value combination, so attaching a high-cardinality value — a full prompt string, a user ID, a session ID — as a metric tag can multiply storage/query cost by orders of magnitude or crash the backend. This is why prompt/completion content belongs only in traces or logs, never as a metric label, and why Spring AI's Observation conventions explicitly separate low-cardinality and high-cardinality key-values.

MIDQ4. How would you compute the cost of a given LLM request from telemetry alone, without calling the provider's billing API?

ROI: ★★★★☆ · Frequency: High

Cost is a linear function of token usage: (prompt_tokens × price_per_input_token) + (completion_tokens × price_per_output_token). Since token counts are already reported per response via the model's usage metadata (Spring AI exposes this as a Usage object on ChatResponseMetadata, with prompt, generation, and total token counts), you multiply by the known per-token pricing for that model and tag the result by model/feature to get per-request and aggregate cost, no billing API call required.

SENIORQ5. Design the observability strategy for a production RAG + tool-calling agent. What would you trace, what would you meter, and what would you sample?

ROI: ★★★★★ · Frequency: High at senior level

Trace the full request as a span tree: retrieval (with vector store and top-k as tags), each advisor in the chain, each model call as its own span (since tool-calling can trigger multiple sequential model calls), and each tool invocation with success/failure and latency. Meter, per feature and per model: request count, latency percentiles (p50/p95/p99, not mean), token usage split into input/output, error rate, and tool-call failure rate — all tagged with low-cardinality values only (model name, model version, feature name), never raw prompt content. Sample with a tail-based strategy: retain 100% of error and high-latency traces, and randomly downsample fast, successful traffic to control storage cost, while keeping metrics unsampled (all requests counted) since metrics are cheap regardless of volume.

Interview Gold Point: Add that you would run a separate, asynchronous quality-evaluation pipeline against a sampled subset of production traffic (LLM-as-judge or rubric-based scoring) precisely because a fast, cheap, error-free trace tells you nothing about correctness — and that this evaluation pipeline must not sit in the user-facing request's critical path, since it is itself a model call with its own latency and cost.
SENIORQ6. A user reports that an agent-based feature "felt slow" yesterday around 3pm, but your average latency dashboard shows nothing unusual. How do you investigate?

ROI: ★★★★☆ · Frequency: Medium-High

Averages hide right-skewed tail latency, which is exactly the kind of distribution LLM and tool-call latency produces — a handful of very slow requests can be invisible in a mean while being exactly what one specific user experienced. Pivot to p95/p99 latency around 3pm, filter traces by time window and, if you have user/session tagging on traces (not metrics, to avoid cardinality blowup), find that user's specific trace. Walk the span waterfall for that trace to identify which stage — retrieval, a specific model call, or a specific tool invocation — accounted for the outlier duration, then check whether it correlates with a provider-side incident, a tool dependency timeout, or an unusually long generation (high output token count).

STAFFQ7. A platform team wants to standardize AI observability across a dozen microservices, some using different model providers. What architecture and standards would you push for, and why?

ROI: ★★★★★ · Frequency: High at staff level

Push for OpenTelemetry as the wire-level standard and the GenAI semantic conventions (gen_ai.* attribute names) as the attribute schema, so every service — regardless of provider or even language — emits comparable telemetry that a single set of dashboards and alerting rules can consume. In the Spring/Java services specifically, standardize on Spring AI's Observation-based instrumentation (via a shared, organization-wide ChatClientObservationConvention/ChatModelObservationConvention customization) so every team gets consistent low-cardinality tagging (feature name, model, prompt version) without re-inventing it per service. Route all telemetry through a central OpenTelemetry Collector that performs PII redaction once, centrally, rather than trusting a dozen teams to redact correctly and independently. Keep token/cost metrics and quality-evaluation scores as first-class, cross-team-comparable metrics from day one, since these become the basis for capacity planning and vendor/model comparisons across the whole platform, not just per-service debugging.

STAFFQ8. How does observability change the way you would think about testing an AI feature (previewing the relationship to the next chapter)?

ROI: ★★★★☆ · Frequency: Medium at staff level

Pre-production test suites can only exercise inputs someone anticipated writing a test for, but the real distribution of user inputs to an LLM-backed feature is unbounded — so testing alone is necessarily incomplete for this class of system. Observability, especially the quality/evaluation telemetry pillar, functions as continuous testing against the real, live input distribution: it catches regressions and failure modes a static test suite never imagined, feeds real production failures back into the test suite (turning "surprises in production" into "regression tests going forward"), and gives you the evidence needed to know whether a prompt or model change actually improved things rather than just feeling like it did. A staff engineer treats testing and observability as one continuous feedback loop, not two separate disciplines owned by two separate teams.

16. SUMMARY

  • AI systems fail differently from ordinary services — the costliest failures are confident, well-formed, wrong answers that never throw an exception — so observability must go beyond the classical logs/metrics/traces trio to include a fourth pillar: quality/evaluation telemetry.
  • Cardinality discipline is the single most important operational rule in this chapter: low-cardinality values (model name, provider, feature) belong on metrics; high-cardinality payloads (prompts, completions) belong only in traces and logs.
  • Spring AI's observability is not a parallel system — it is built directly on Micrometer's Observation API already powering Spring Boot Actuator, using ChatClientObservationConvention and ChatModelObservationConvention to emit standard, OpenTelemetry-GenAI-aligned gen_ai.* attributes and metrics automatically.
  • Token usage, exposed uniformly across providers via ChatResponseMetadata's Usage object, is the foundation for near-free, real-time cost tracking — no billing API call required.
  • Tracing overhead, storage cost, and synchronous evaluation latency are real trade-offs; production systems sample intelligently (100% of errors/tail latency, downsampled routine traffic) rather than capturing everything unconditionally.
  • Observability data is itself sensitive — prompts, completions, and system prompts routed through third-party observability backends deserve the same redaction discipline and access control as the production data they represent.

Next chapter: Testing (Chapter 39) picks up exactly where this chapter's Staff-level closing question pointed — because a foundation model cannot be pinned down with exact-match assertions, and because observability alone can only tell you what already happened in production, you need a deliberate, statistical, rubric- and regression-based testing discipline built specifically for non-deterministic systems, one that turns real production failures surfaced by this chapter's telemetry into permanent, automated regression coverage going forward.
