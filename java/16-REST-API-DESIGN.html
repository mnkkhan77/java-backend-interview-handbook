SECTION 1 - REST FUNDAMENTALS

Q1. What is REST and what are its core architectural constraints?

ROI: ★★★★★ Frequency: Very High

Short Answer

REST (Representational State Transfer) is an architectural style, defined by Roy Fielding, for building distributed systems on top of HTTP. It is not a protocol and not a framework. A system is RESTful when it obeys a set of constraints; in return you get scalability, evolvability and visibility.

The six constraints are:

  • Client-Server - separation of concerns; UI and data storage evolve independently.
  • Stateless - each request carries everything the server needs; the server stores no client session between requests.
  • Cacheable - responses must declare whether they can be cached (via headers like Cache-Control).
  • Uniform Interface - the cornerstone: resources identified by URIs, manipulated through representations, self-descriptive messages, and HATEOAS.
  • Layered System - a client cannot tell whether it talks to the origin server or an intermediary (gateway, proxy, load balancer).
  • Code on Demand (optional) - the server may ship executable code (e.g. JavaScript) to extend the client.

Statelessness is the one most worth stressing: because no server holds session state, any node can serve any request, which is exactly what lets you scale horizontally behind a load balancer. State that must persist (the user's auth) travels in a token (see the JWT chapter), not a server-side session.

Interview Gold Point

Many candidates confuse "stateless" with "no database". Application state (resource data) absolutely lives on the server and in the DB; what must not live there is client session state. Saying this distinction out loud signals seniority.

Q2. What is the Richardson Maturity Model, and what actually makes an API "RESTful"?

ROI: ★★★★☆ Frequency: Medium

Short Answer

The Richardson Maturity Model grades how closely an HTTP API follows REST, in four levels:

  • Level 0 - The Swamp of POX: one endpoint, one verb (usually POST), RPC-over-HTTP (e.g. SOAP-style).
  • Level 1 - Resources: distinct URIs per resource, but still one verb everywhere.
  • Level 2 - HTTP Verbs: proper use of GET/POST/PUT/DELETE and meaningful status codes. This is where most "REST" APIs in industry sit, and it is genuinely good enough.
  • Level 3 - Hypermedia Controls (HATEOAS): responses include links telling the client what it can do next.

Pragmatically, an API is considered RESTful when it reaches Level 2: noun-based resource URIs, correct verbs, correct status codes, statelessness and cacheability. Level 3 is the academic ideal but rare in practice because client tooling rarely consumes the links.

Interview Favorite

A strong line: "Most production APIs, including those at large companies, are Level 2. HATEOAS is theoretically pure but adds payload weight and complexity that few clients use - so I treat it as optional rather than a failure." This shows judgement, not dogma.

SECTION 2 - HTTP METHODS & STATUS CODES

Q3. Explain the semantics of GET, POST, PUT, PATCH and DELETE.

ROI: ★★★★★ Frequency: Very High

Short Answer

MethodPurposeBody?Typical success code
GETRead a resource or collection; no side effectsNo200
POSTCreate a subordinate resource / trigger a processYes201 (or 200/202)
PUTFull replace of a resource at a known URI (or create-at-id)Yes (full)200 / 204 / 201
PATCHPartial update of a resourceYes (partial/diff)200 / 204
DELETERemove a resourceNo204 (or 200)

Key distinctions: PUT replaces the entire resource - omitted fields are typically cleared - whereas PATCH modifies only the supplied fields. PUT is also used to create a resource when the client controls the identifier (e.g. PUT /users/42); POST is used when the server assigns the id (e.g. POST /users returning Location: /users/42). 

@RestController
@RequestMapping("/api/v1/orders")
public class OrderController {

    @PostMapping
    public ResponseEntity<OrderDto> create(@Valid @RequestBody CreateOrderRequest req) {
        OrderDto created = orderService.create(req);
        URI location = URI.create("/api/v1/orders/" + created.id());
        return ResponseEntity.created(location).body(created); // 201 + Location header
    }

    @GetMapping("/{id}")
    public ResponseEntity<OrderDto> get(@PathVariable Long id) {
        return ResponseEntity.ok(orderService.findById(id)); // 200
    }

    @DeleteMapping("/{id}")
    public ResponseEntity<Void> delete(@PathVariable Long id) {
        orderService.delete(id);
        return ResponseEntity.noContent().build(); // 204
    }
}

Common Mistake

Using POST for everything (a Level 0 anti-pattern) or using GET with side effects. A GET must never mutate state - crawlers, prefetchers and proxies will replay GETs freely, and that has caused real production data loss.

Q4. What is the difference between safe and idempotent methods?

ROI: ★★★★★ Frequency: High

Short Answer

  • Safe = read-only; calling it does not change server state. (GET, HEAD, OPTIONS)
  • Idempotent = calling it N times has the same effect on server state as calling it once. The response may differ, but the resulting state must not.
MethodSafeIdempotent
GET / HEADYesYes
OPTIONSYesYes
PUTNoYes
DELETENoYes
POSTNoNo
PATCHNoNot guaranteed

Why it matters: idempotency is what makes safe retries possible. If a client times out on a PUT or DELETE, it can resend with no harm. POST is not idempotent - two POSTs create two resources - which is exactly why idempotency keys exist (see Q13). PATCH is idempotent only if its semantics are a full-value set (e.g. JSON Merge Patch with absolute values); a relative operation like {"op":"increment","by":1} is not.

Interview Gold Point

"DELETE is idempotent even though the second call returns 404." Deleting twice still ends in the same state (resource gone). The differing status code does not break idempotency - idempotency is about state, not the response code. Saying this catches a subtlety most candidates miss.

Q5. Walk through the HTTP status code families and when you use them.

ROI: ★★★★★ Frequency: Very High

Short Answer

FamilyMeaningCommon codes
2xxSuccess200 OK, 201 Created, 202 Accepted, 204 No Content
3xxRedirection / caching301 Moved Permanently, 304 Not Modified
4xxClient error (the caller must fix the request)400, 401, 403, 404, 409, 422, 429
5xxServer error (not the caller's fault)500, 502, 503, 504

The senior signal here is precision: never return 200 with an {"error": ...} body, and never blanket-return 500 for validation failures. The status line is part of your API contract - clients, gateways and monitoring all branch on it. A spike of 5xx pages the on-call engineer; a spike of 4xx points at a misbehaving client. Conflating them poisons observability.

Common Mistake

Returning 200 OK for failures "to keep the frontend simple". This breaks caching, retries, alerting and any standard HTTP client. The status code is data - use it correctly.

Q6. When do you use 201 vs 200, 400 vs 422, 401 vs 403, and 404 vs 409?

ROI: ★★★★★ Frequency: High

Short Answer

  • 201 vs 200: 201 Created when a request created a new resource (return a Location header). 200 OK for a successful read or an update that returns a body. Use 204 No Content when the update/delete succeeds but there is nothing to return.
  • 400 vs 422: 400 Bad Request = the request is malformed or unparseable (broken JSON, wrong type, missing required field). 422 Unprocessable Entity = the syntax is fine but the request fails business/semantic validation (e.g. "end date before start date", "email already in a pending state"). Many teams use 400 for both; using 422 for semantic rules is the cleaner, more senior choice.
  • 401 vs 403: 401 Unauthorized = you are not authenticated (no/invalid credentials) - "who are you?". 403 Forbidden = you are authenticated but not allowed - "I know who you are, you still can't". (See the Spring Security chapter.)
  • 404 vs 409: 404 Not Found = the resource does not exist. 409 Conflict = the request conflicts with current state - duplicate creation, or an optimistic-lock version mismatch (stale update). 409 is the natural code for "this changed under you, refetch and retry".

Interview Favorite

On security, some teams deliberately return 404 instead of 403 to avoid leaking the existence of a resource to unauthorized users (resource enumeration). Mentioning this trade-off - correctness vs information disclosure - is a strong senior touch.

SECTION 3 - RESOURCE & URI DESIGN

Q7. What are the conventions for naming resources and designing URIs?

ROI: ★★★★☆ Frequency: High

Short Answer

  • Use nouns, not verbs. The verb is the HTTP method. GET /users/42, not GET /getUser?id=42.
  • Use plural collection names. /orders, /orders/42, /orders/42/items.
  • Nest to express ownership, but stop at one or two levels. /users/42/orders is fine; /users/42/orders/9/items/3/reviews is a smell - reference the leaf directly via /reviews/3.
  • Lowercase, hyphen-separated path segments: /purchase-orders, not /purchaseOrders or /purchase_orders.
  • Query params for filtering/sorting/paging, not for identity: /orders?status=PAID&sort=-createdAt.
  • Use sub-resources for relationships and reserve a few "controller" style endpoints for non-CRUD actions when truly needed (e.g. POST /orders/42/cancel).
GET    /api/v1/customers              # list customers
POST   /api/v1/customers              # create a customer
GET    /api/v1/customers/42           # read one
PUT    /api/v1/customers/42           # replace
PATCH  /api/v1/customers/42           # partial update
DELETE /api/v1/customers/42           # delete
GET    /api/v1/customers/42/orders    # that customer's orders

Common Mistake

Action verbs in the path (/createUser, /deleteOrder). The only widely accepted exception is non-CRUD domain actions that do not map to a verb, modelled as a POST to a sub-resource: POST /accounts/42/transfers.

Q8. What are the API versioning strategies and their trade-offs?

ROI: ★★★★★ Frequency: Very High

Short Answer

Three mainstream approaches:

StrategyExampleProsCons
URI path/api/v1/ordersExplicit, easy to test in a browser/curl, easy routing & cachingNot "pure" REST (URI should identify a resource, not a version); duplicates routes
Custom / Accept headerAccept: application/vnd.acme.v2+jsonClean URIs; version negotiation is content-drivenHarder to test/debug; easy to forget; weaker cache keys
Query parameter/orders?version=2Simple to addPollutes the query string; clumsy caching; easy to omit

URI versioning is the most common in industry because it is unambiguous and cache-friendly. The purist choice is media-type (header) versioning, which keeps the resource URI stable. Whatever you pick, the real goal is backward compatibility: prefer additive, non-breaking changes (new optional fields, new endpoints) so you rarely need to bump the major version at all. Bump the version only on breaking changes, and support N-1 for a deprecation window.

Interview Gold Point

"The best version bump is the one you never make." Adding fields, never removing or repurposing them, and treating unknown fields as ignorable on the client lets a v1 API evolve for years. This shows you understand evolution, not just syntax.

SECTION 4 - PAYLOADS & ERROR HANDLING

Q9. How do you design pagination - offset vs cursor/keyset?

ROI: ★★★★★ Frequency: High

Short Answer

Offset/limit pagination (?page=3&size=20 or ?offset=40&limit=20) is simple and allows jumping to any page. But it has two problems at scale: it is slow on large offsets (OFFSET 1000000 still scans and discards a million rows), and it suffers from drift - if rows are inserted/deleted while paging, items get skipped or repeated.

Cursor / keyset pagination passes an opaque cursor that encodes the last seen sort key (e.g. ?after=eyJpZCI6MTIzfQ&limit=20). The query becomes WHERE (created_at, id) < (:lastTs, :lastId) ORDER BY created_at DESC, id DESC LIMIT 20, which uses the index directly - O(limit), not O(offset). It is stable under inserts and the right default for large, frequently-changing or infinite-scroll datasets. The cost: you cannot jump to "page 47".

AspectOffsetCursor/Keyset
Random page accessYesNo (next/prev only)
Performance on deep pagesDegradesConstant
Stable under writesNo (drift)Yes
Best forSmall, admin tables, page numbersFeeds, logs, large/live data

Interview Favorite

The "drift" point wins this question. Saying "offset pagination double-counts or skips rows when the underlying data changes between pages, so for a live feed I default to keyset" demonstrates you have actually paginated production data.

Q10. How do you design filtering and sorting query parameters?

ROI: ★★★☆☆ Frequency: Medium

Short Answer

  • Filtering: field-named query params - GET /orders?status=PAID&customerId=42. For ranges, use suffixes or paired params: ?createdAfter=2026-01-01&amountGte=100.
  • Sorting: a sort param with a sign or direction - ?sort=-createdAt,name (descending createdAt, then ascending name). Spring Data's Pageable accepts ?sort=createdAt,desc natively.
  • Field selection / sparse fieldsets: ?fields=id,name,total to trim payload size.
  • Whitelist every filterable and sortable field server-side. Never feed a raw client field directly into a SQL ORDER BY or dynamic query - that is an injection vector (see the SQL chapter).
@GetMapping("/orders")
public Page<OrderDto> search(
        @RequestParam(required = false) OrderStatus status,
        @PageableDefault(size = 20, sort = "createdAt",
                         direction = Sort.Direction.DESC) Pageable pageable) {
    return orderService.search(status, pageable);
}

Common Mistake

Allowing arbitrary sort/filter fields straight from the client. Always map to an allow-list of known columns; reject unknown fields with 400. Convenience here becomes a SQL-injection or performance footgun in production.

Q11. How do you design a consistent error response format?

ROI: ★★★★★ Frequency: High

Short Answer

Every error from your API should share one machine-readable shape so clients can parse failures uniformly. The standard is RFC 7807 (Problem Details for HTTP APIs), served as Content-Type: application/problem+json: 

{
  "type": "https://api.acme.com/errors/insufficient-funds",
  "title": "Insufficient funds",
  "status": 422,
  "detail": "Account 42 balance 10.00 is below the requested 50.00",
  "instance": "/api/v1/accounts/42/transfers",
  "traceId": "a1b2c3d4"
}

Spring Boot 3 ships ProblemDetail and supports this natively. Centralize error mapping in a single @RestControllerAdvice (see the Spring Boot chapter for @ControllerAdvice) so you never scatter error formatting across controllers: 

@RestControllerAdvice
public class GlobalExceptionHandler {

    @ExceptionHandler(InsufficientFundsException.class)
    public ProblemDetail handle(InsufficientFundsException ex) {
        ProblemDetail pd = ProblemDetail.forStatusAndDetail(
                HttpStatus.UNPROCESSABLE_ENTITY, ex.getMessage());
        pd.setTitle("Insufficient funds");
        pd.setType(URI.create("https://api.acme.com/errors/insufficient-funds"));
        pd.setProperty("traceId", MDC.get("traceId"));
        return pd;
    }
}

Always include a correlation/trace id so a support ticket maps to a log line (see distributed tracing in the Microservices chapter). Never leak stack traces or SQL to clients.

Interview Gold Point

Mentioning RFC 7807 / application/problem+json by name immediately signals you have designed real public APIs. Bonus: note that error type should be a stable, documented URI clients can branch on - more reliable than parsing the human-readable detail string.

Q12. How do you handle request validation in a REST API?

ROI: ★★★★☆ Frequency: Medium

Short Answer

Validate at the edge, declaratively, and return a structured 400/422 listing every field error at once (not one at a time). In Spring, use Bean Validation (Jakarta Validation) annotations on the request DTO plus @Valid on the controller parameter: 

public record CreateUserRequest(
        @NotBlank String name,
        @Email String email,
        @Min(18) int age) {}

@PostMapping("/users")
public ResponseEntity<UserDto> create(@Valid @RequestBody CreateUserRequest req) { ... }

A failed @Valid throws MethodArgumentNotValidException, which you map in the advice to a problem+json body whose errors array lists each rejected field and message. Distinguish two layers: syntactic/format validation (annotations, 400) and semantic/business validation (service layer, often 422), e.g. "this coupon is expired" - a rule annotations cannot express.

Common Mistake

Returning only the first validation error. Clients (and forms) want all errors in one response. Aggregate field errors into a list so the user fixes everything in one round trip.

SECTION 5 - ADVANCED API DESIGN

Q13. What are idempotency keys and why are they needed for POST?

ROI: ★★★★★ Frequency: High

Short Answer

POST is not idempotent, so a client that times out and retries a "create payment" call risks charging the customer twice. The fix is an idempotency key: the client generates a unique key (e.g. a UUID) and sends it in a header on the POST: 

POST /api/v1/payments
Idempotency-Key: 7c9e6679-7425-40de-944b-e07fc1f90ae7

The server stores the key together with the result of the first successful request (typically in Redis or a dedicated table). On a retry with the same key, it skips re-processing and replays the original response. This is exactly how Stripe and other payment APIs make POST safely retryable.

Key implementation points:

  • Persist key -> (status, response body) with a TTL (e.g. 24h).
  • While the first request is in flight, lock the key so concurrent retries get 409 or wait, not a double-process.
  • Optionally hash the request body and reject reuse of the same key with a different body (400) - protects against accidental key reuse.

Interview Gold Point

Tie it back: "GET/PUT/DELETE are idempotent by HTTP semantics, so retries are inherently safe; POST is not, so I add an idempotency key for any create that has financial or side-effecting impact." That sentence connects Q4 to a real production pattern and is a strong senior answer.

Q14. How do you implement rate limiting and what does the API return?

ROI: ★★★★☆ Frequency: Medium

Short Answer

Rate limiting protects the service from abuse and noisy neighbours and enforces quotas. Common algorithms (covered in the System Design chapter) are token bucket, leaking bucket, fixed window and sliding window; token bucket is the usual default because it allows bursts up to capacity.

When a client exceeds its quota, return 429 Too Many Requests, and tell the client how to behave: 

HTTP/1.1 429 Too Many Requests
Retry-After: 30
X-RateLimit-Limit: 100
X-RateLimit-Remaining: 0
X-RateLimit-Reset: 1718553600
  • Retry-After - seconds (or a date) to wait before retrying; well-behaved clients honour it with backoff.
  • X-RateLimit-Limit / -Remaining / -Reset - let clients self-throttle before hitting the limit.

Enforce it at the gateway/edge where possible (API Gateway, NGINX, a filter), backed by a shared store like Redis so the limit is global across instances - not per-node in-memory, which a horizontally scaled service would multiply.

Interview Favorite

Stress the shared counter: "In-memory rate limiting breaks the moment you scale to N pods, because each enforces the limit independently - the effective limit becomes N times the intended one. I keep the counter in Redis."

Q15. Explain HATEOAS, HTTP caching (ETag) and content negotiation.

ROI: ★★★★☆ Frequency: Medium

Short Answer

HATEOAS (Hypermedia As The Engine Of Application State) is REST Level 3: responses embed links describing valid next actions, so the client discovers transitions instead of hard-coding URLs. 

{
  "id": 42,
  "status": "PENDING",
  "_links": {
    "self":   { "href": "/orders/42" },
    "cancel": { "href": "/orders/42/cancel" },
    "pay":    { "href": "/orders/42/payment" }
  }
}

Caching with ETag: the server returns an ETag (a hash/version of the representation). The client caches it and on the next read sends If-None-Match. If unchanged, the server responds 304 Not Modified with no body, saving bandwidth. For state-changing requests, ETag + If-Match gives optimistic concurrency: a stale write fails with 412 Precondition Failed (or 409). Cache-Control (e.g. max-age, no-store, private) governs how long and where a response may be cached. 

GET /orders/42
If-None-Match: "v7"          --> 304 Not Modified (empty body) if still version 7

Content negotiation: the client states what it wants via Accept (e.g. application/json vs application/xml) and describes its body via Content-Type; the server selects a representation or returns 406 Not Acceptable. This is also the mechanism behind media-type API versioning (Q8).

Interview Gold Point

The ETag + If-Match concurrency angle is gold: "ETags do double duty - 304 for caching on reads, and 412/409 optimistic locking on writes, so two clients can't silently clobber each other." This links REST to the optimistic-locking discussion in the JPA chapter.

Interview Favorite

"They are not mutually exclusive." A mature system commonly exposes REST/GraphQL at the edge for clients and uses gRPC internally between services. Saying you choose per-boundary, not per-religion, signals architectural maturity.

SECTION 7 - CONDITIONAL REQUESTS, PATCH SEMANTICS & CONCURRENCY

Q17. How do If-Match, If-None-Match and If-Modified-Since work for optimistic concurrency on writes?

ROI: ★★★★★ Frequency: High

Short Answer

Q15 introduced ETag for caching reads. The same mechanism, applied to writes, gives you optimistic concurrency without a database lock: the client first GETs the resource and receives an ETag (a version fingerprint, e.g. "v7"). When it later updates the resource, it sends that ETag back as a precondition on the write: 

PUT /api/v1/accounts/42
If-Match: "v7"

The server compares the supplied value against the resource's current ETag. If they match, the update proceeds and a new ETag ("v8") is issued. If someone else updated the resource in between, the current ETag is now "v8", the precondition fails, and the server rejects the write with 412 Precondition Failed - without applying it - so the client never silently clobbers a change it never saw. This is the HTTP-native expression of the same idea as JPA's @Version optimistic locking (see the JPA chapter): the client is forced to refetch, look at what changed, and retry.

HeaderSent onMeaningFailure code
If-None-MatchGET"send the body only if it changed since this ETag"304 Not Modified
If-None-Match: *POST/PUT"only create if a resource at this URI does not already exist"412 Precondition Failed
If-MatchPUT/PATCH/DELETE"only apply if the resource is still at this exact version"412 Precondition Failed
If-Modified-SinceGETweaker, timestamp-based version of If-None-Match (second-resolution only)304 Not Modified
If-Unmodified-SincePUT/PATCH/DELETEweaker, timestamp-based version of If-Match412 Precondition Failed

Prefer ETag-based preconditions over date-based ones whenever you can compute a real fingerprint: Last-Modified only has second-level resolution, so two updates within the same second are indistinguishable, while an ETag (hash or version counter) is exact. A W/"..." prefix marks a weak ETag - equivalent for caching purposes but not guaranteed byte-identical - versus a strong ETag with no prefix, which must be byte-for-byte identical to match.

Interview Gold Point

"If-None-Match: * on a POST/PUT is how you implement create-if-absent without a race: the server only creates the resource if nothing exists yet at that URI, and returns 412 if a concurrent request beat it there." This is a detail most candidates never mention and immediately separates a strong answer.

Q18. What is the difference between JSON Merge Patch and JSON Patch for implementing PATCH?

ROI: ★★★★☆ Frequency: Medium

Short Answer

HTTP deliberately does not define the shape of a PATCH body - that is left to the media type. Two IETF standards fill that gap, and picking one (rather than inventing an ad hoc partial-update JSON shape) keeps your PATCH semantics unambiguous to clients and tooling.

JSON Merge Patch (RFC 7396), media type application/merge-patch+json, sends a partial object that is merged key by key into the target; a key set to null means "delete this field". Simple to produce and consume, but it cannot express array element operations precisely (an array is replaced wholesale, not patched element-by-element) and it cannot distinguish "leave this field alone" from "field wasn't in my object" versus a client that serializes absent fields as null by mistake. 

PATCH /api/v1/users/42
Content-Type: application/merge-patch+json

{ "email": "new@acme.com", "nickname": null }

JSON Patch (RFC 6902), media type application/json-patch+json, sends an ordered array of explicit operations addressed by JSON Pointer paths - far more expressive, including precise array index operations and a test operation that can assert a field's current value before applying the rest (a field-level optimistic-concurrency check, complementary to If-Match from Q17). 

PATCH /api/v1/users/42
Content-Type: application/json-patch+json

[
  { "op": "test",    "path": "/email", "value": "old@acme.com" },
  { "op": "replace", "path": "/email", "value": "new@acme.com" },
  { "op": "remove",  "path": "/nickname" },
  { "op": "add",     "path": "/roles/-", "value": "REVIEWER" }
]

Idempotency note (ties back to Q4): Merge Patch is idempotent because it sets absolute values. JSON Patch is idempotent only if every operation is idempotent by construction - replace is, but add to an array or a test-guarded sequence generally is not, since replaying the same array-append twice appends twice.

Common Mistake

Inventing a custom, undocumented "partial update" JSON shape instead of adopting one of these two standards. Doing so forces every client to hand-read your prose docs instead of using an off-the-shelf JSON Patch/Merge Patch library, and it is a tell that the API wasn't designed with PATCH semantics in mind at all.

Q19. How does RFC 7807 Problem Details relate to the custom error formats teams already use?

ROI: ★★★★☆ Frequency: Medium

Short Answer

Q11 introduced RFC 7807 as the standard error envelope. In practice, almost every team already has some homegrown error shape (an errorCode, a validationErrors array, a requestId) that predates or sits alongside it. The right relationship is not "replace your format with 7807" but "put your format's extra fields inside 7807's envelope as extension members", since the spec explicitly allows adding arbitrary additional properties beyond type/title/status/detail/instance. 

{
  "type": "https://api.acme.com/errors/validation-failed",
  "title": "Validation failed",
  "status": 422,
  "detail": "3 fields failed validation",
  "instance": "/api/v1/users",
  "traceId": "a1b2c3d4",
  "errors": [
    { "field": "email", "code": "INVALID_FORMAT", "message": "not a valid email address" },
    { "field": "age",   "code": "MIN_VALUE",       "message": "must be at least 18" }
  ]
}

This gets you both worlds: generic HTTP tooling, gateways and even other teams' unrelated clients can parse the standard members (status, title) without knowing anything about your domain, while your own SDKs and frontend read the extension members (errors, traceId) for rich, field-level detail. Treat the type URI as a stable part of your public contract, not a debugging string - clients legitimately branch (switch/if) on it, so renaming or repurposing a type value is a breaking change subject to the same deprecation discipline as an endpoint (see Q35).

Interview Favorite

"7807 is a base envelope, not a replacement for your domain-specific error detail." Saying this shows you understand it as an interoperability layer rather than a rigid schema you're locked into.

Q20. How much do teams actually adopt HATEOAS in practice, and when is it worth it?

ROI: ★★★☆☆ Frequency: Medium

Short Answer

Full HATEOAS - a client that discovers what it can do next purely by following links in the response, with no hard-coded routes - is rare in production, for concrete reasons: client SDKs are usually generated from a static OpenAPI contract (Q39), not from following hypermedia links at runtime; embedding _links on every response adds payload weight; and frontend frameworks need routes at build time anyway (a React Router config doesn't discover itself from an API response). For a typical CRUD backend serving a known frontend, the cost outweighs the benefit, which is why most production APIs deliberately stop at Richardson Level 2 (Q2).

Where hypermedia genuinely earns its keep is state-machine-heavy resources: an order, a support ticket, a loan application - anything whose valid next actions differ by current state. Embedding the currently-valid transitions in the response means the client renders "Cancel" and "Pay" buttons based on what the server says is legal right now, instead of duplicating the state-machine's transition rules in frontend code (which inevitably drifts out of sync with the backend's actual rules). 

{ "id": 42, "status": "PENDING",
  "_links": {
    "self":   { "href": "/orders/42" },
    "cancel": { "href": "/orders/42/cancel" },
    "pay":    { "href": "/orders/42/payment" }
  }
}

A lighter-weight alternative many teams use instead of full HATEOAS: return an explicit status enum plus an allowedTransitions array, and document the full state machine in OpenAPI/prose rather than making link discovery the mechanism. It gives most of the same benefit (client doesn't hard-code transition rules) with far less machinery.

Interview Gold Point

"I reach for hypermedia specifically for workflow/state-machine resources, not as a blanket architectural rule - for plain CRUD, Level 2 with good docs is the pragmatic choice." This shows judgment rather than dogma about REST purity.

SECTION 8 - ASYNCHRONOUS & LONG-RUNNING OPERATIONS

Q21. How do you design an endpoint for an operation that cannot complete synchronously?

ROI: ★★★★★ Frequency: High

Short Answer

When an operation (report generation, video transcoding, a large bulk import) can take seconds to minutes, holding the client's connection open until it finishes is unreliable - proxies, load balancers and the client's own HTTP stack all have timeouts you don't control. The standard pattern: the initiating request returns immediately with 202 Accepted and a Location header pointing at a status resource; the client polls that resource until it reports completion. 

POST /api/v1/reports
--> 202 Accepted
    Location: /api/v1/reports/jobs/abc123
    Retry-After: 5

GET /api/v1/reports/jobs/abc123
--> 200 OK
    { "status": "RUNNING", "progress": 40 }

GET /api/v1/reports/jobs/abc123
--> 200 OK
    { "status": "DONE", "resultUrl": "/api/v1/reports/jobs/abc123/download" }

Use Retry-After on the 202 itself to tell the client how soon it's reasonable to poll again, so well-behaved clients don't hammer the status endpoint. Once the job is done, some designs 303-redirect the status GET to the actual result resource rather than embedding a resultUrl field - either is fine as long as it's documented consistently.

Common Mistake

Returning 200 immediately with a fake "success" body while the real work happens asynchronously behind the scenes. 202 exists precisely to say "accepted, not yet done" - using 200 for this misleads every client and monitoring tool that reasonably assumes 200 means the operation actually completed.

Q22. How do you model an async operation as a first-class "job" resource rather than a status blob?

ROI: ★★★★☆ Frequency: Medium

Short Answer

A stronger version of Q21's pattern treats the operation itself as a resource with its own lifecycle, not just an opaque status field bolted onto the original request. GET /jobs/{id} returns a status enum (PENDING/RUNNING/SUCCEEDED/FAILED/CANCELLED), timestamps, and links to the job's inputs and outputs; POST /jobs/{id}/cancel (or DELETE /jobs/{id}) supports cancellation; GET /jobs?status=RUNNING&createdBy=42 gives operational visibility into everything currently in flight, which an opaque per-request status field never can.

This composability - a job can be queried, listed, filtered and cancelled like any other resource, with the same pagination (Q9) and filtering (Q10) conventions as everything else in the API - is what separates a well-designed async API from a one-off status blob wired to a single endpoint. On failure, store a structured error (shaped like Q11/Q19's problem+json) on the job resource itself, so the failure reason survives past the moment it happened and is visible to anyone querying the job later, not just whoever was polling at the time.

Interview Gold Point

"I treat the job as a resource, not the original request as having a hidden second life." This reframing - job-as-resource - is exactly the kind of API-design maturity interviewers are listening for here.

Q23. How do you design webhooks: delivery guarantees, signature verification and idempotent receivers?

ROI: ★★★★★ Frequency: High

Short Answer

A webhook inverts Q21's pattern: instead of the client polling, your server pushes an event to a URL the client registered, the moment something happens. Designing the sender side well means addressing four things:

  • Delivery guarantee: no distributed system can promise exactly-once delivery over an unreliable network. Document "at least once" honestly, and design receivers to cope (below) rather than pretending exactly-once is achievable.
  • Retries: on a non-2xx response or a timeout, retry with exponential backoff and jitter, up to a capped number of attempts; after exhausting retries, dead-letter the event and alert/disable the endpoint rather than retrying forever against a broken receiver.
  • Signature verification (HMAC): sign the raw request body with a shared secret and send the signature as a header, so the receiver can verify the payload is authentic and untampered without needing mutual TLS.
  • Event identity: include a unique event id and timestamp in the payload so a receiver can detect and drop a duplicate or unreasonably stale delivery.
// Sender: sign the raw body
String signature = "sha256=" + hmacSha256Hex(sharedSecret, rawRequestBody);
// sent as header: X-Signature: sha256=...

// Receiver: verify before trusting the payload
boolean valid = MessageDigest.isEqual(
    hmacSha256(sharedSecret, rawRequestBody).getBytes(),
    receivedSignatureBytes);
if (!valid) return ResponseEntity.status(401).build();

On the receiver side: verify the signature before doing anything else, respond 2xx quickly and process the actual work asynchronously off the request thread (a slow receiver just causes the sender to retry or time out, compounding load), and be idempotent - store processed event ids and skip a duplicate delivery of the same id. This mirrors the idempotency-key pattern from Q13, applied to inbound events instead of outbound client requests.

Interview Gold Point

"Webhooks need the same idempotency discipline as payments - the receiver, not just the sender, has to assume duplicates will happen and dedupe on event id." Connecting this back to Q13's idempotency-key pattern signals you see the general principle, not just this one feature.

Q24. When would you use Server-Sent Events (SSE) instead of polling or webhooks?

ROI: ★★★☆☆ Frequency: Medium

Short Answer

Polling (Q21) and webhooks (Q23) both deliver a final result or discrete events. When a client instead needs a continuous stream of incremental updates - a progress bar, a live log tail, chat messages, price ticks - three options exist: keep polling (simple but wasteful and laggy, since the update rate is bounded by the poll interval); Server-Sent Events (SSE), a single long-lived HTTP response with Content-Type: text/event-stream that the server keeps writing data: ...\n\n frames to; or WebSockets, a full-duplex protocol upgrade.

SSE is the natural fit when the data only flows server-to-client: it rides on plain HTTP/1.1 (no protocol upgrade, so it passes through standard proxies and load balancers more easily than WebSockets often do), the browser's EventSource API handles auto-reconnect for you, and Spring supports it directly via SseEmitter (MVC) or Flux<ServerSentEvent<T>> (WebFlux). Reach for WebSockets only when the client also needs to push data back over the same connection (a chat message going both directions, collaborative editing) - that bidirectionality is the one thing SSE cannot do.

Common Mistake

Reaching for WebSockets by default for anything "real-time". If the data only flows one way (server to client), SSE is simpler to implement, simpler to operate, and fits far more naturally into an existing HTTP-based REST API than standing up a separate WebSocket protocol.

Q25. How do you choose between synchronous, 202+poll, webhook and streaming patterns for a given operation?

ROI: ★★★★☆ Frequency: Medium

Short Answer

A decision framework, from simplest to most involved:

  • Synchronous: the operation reliably completes in well under a second (ordinary CRUD) - just return the result directly.
  • 202 + poll (Q21/Q22): the operation is long but client-initiated, and the client is willing to ask "done yet?" without running any infrastructure of its own - reports, imports, batch inference.
  • Webhook (Q23): the event happens on the server's own schedule, not in response to a specific client request, and the consumer already runs a reachable HTTP endpoint - payment settled, order shipped, common in B2B integrations and platforms with a developer ecosystem.
  • SSE/streaming (Q24): the client needs continuous incremental updates during the operation, not just a final result - a live progress bar or log tail.

Mature platforms (Stripe, GitHub) commonly expose both polling and webhooks for the same class of event: the webhook is the low-latency push, and a periodic reconciliation poll/list call is the fallback for the (rare, but real) lost delivery. Recommending both, and telling clients to treat webhooks as best-effort with polling as a safety net, is the senior answer here.

Interview Favorite

"Webhooks are a latency optimization on top of an eventually-consistent poll/list endpoint, not a replacement for one." That framing shows you design for the failure mode (a lost webhook delivery), not just the happy path.

SECTION 9 - BULK OPERATIONS, FILES & COMPLEX QUERIES

Q26. What are the trade-offs of batch/bulk endpoints versus one request per resource?

ROI: ★★★★☆ Frequency: Medium

Short Answer

When a client needs to create or update many resources at once (importing 10,000 rows), one-request-per-resource is simple and stays purely within standard REST semantics, but pays N round trips of network, auth and validation overhead. A batch endpoint amortizes that cost: 

POST /api/v1/orders/batch
Content-Type: application/json

{ "items": [ {"sku":"A1","qty":2}, {"sku":"B7","qty":1}, ... ] }

but complicates the contract: what single HTTP status represents "3 succeeded, 2 failed" (see Q27)? What caps the batch size so one request can't blow memory or time out (reject anything over, say, 100 items with 400)? Before building one, weigh whether the real bottleneck is round trips (favors a batch endpoint) or is already mitigated by HTTP/2 connection multiplexing letting many small parallel requests share one connection cheaply (an argument for not building bulk endpoints prematurely, since they add real design and operational surface).

Common Mistake

Building a bulk endpoint before confirming the bottleneck is actually round-trip count and not something else (like per-item processing time, which a batch endpoint doesn't fix at all). Measure first.

Q27. How do you report partial success in a batch API - what is 207 Multi-Status?

ROI: ★★★★☆ Frequency: Medium

Short Answer

A batch call is neither cleanly a success nor a failure as a whole - some items succeed, some don't. 207 Multi-Status (originally defined for WebDAV, now widely reused for REST batch APIs) is the correct top-level status: it signals "the batch was processed, see the body for per-item outcomes" rather than falsely implying total success (200/201) or total failure (4xx/5xx) when the reality is mixed. 

HTTP/1.1 207 Multi-Status

{
  "results": [
    { "id": 1, "status": 201, "location": "/orders/1" },
    { "id": 2, "status": 422, "error": { "title": "Invalid amount" } }
  ]
}

Guarantee the results array's order matches the request array's order, so the client can zip results back to the original items positionally without needing a separate correlation id per item (though including one doesn't hurt for clarity).

Interview Gold Point

Explicitly naming 207 by number and RFC origin (WebDAV, RFC 4918) is a strong signal - most candidates either don't know a "partial success" status code exists at all, or invent a 200 with a mixed-results body, which loses the "something here failed" signal for any generic HTTP-status-aware tooling.

Q28. Should a batch endpoint be transactional (all-or-nothing) or best-effort?

ROI: ★★★★☆ Frequency: Medium

Short Answer

Two fundamentally different contracts, and the endpoint must commit to one and document it explicitly:

  • Transactional: the whole batch runs in one database transaction - either everything commits or everything rolls back, and the client gets a single top-level status with no partial results. Simpler for the client to reason about, but a single bad row fails the entire batch, and large transactions hold locks longer as batch size grows.
  • Best-effort: each item is processed independently; partial success is the normal case and is reported per-item via Q27's 207 shape.

Silently mixing the two - or leaving it undocumented - is a real production hazard: a client that assumes atomicity (because most batch APIs feel like they should be atomic) may build duplicate-recovery logic on top of an endpoint that actually applied half the batch, and that recovery logic then double-applies the succeeded half on retry. State the contract in the docs and in the response shape itself, not just in a comment.

Common Mistake

Assuming "batch" implies "atomic" without checking. Many production batch APIs (including cloud provider bulk APIs) are best-effort by default specifically because true atomicity across many independent writes doesn't scale.

Q29. How do you design file uploads in a REST API?

ROI: ★★★☆☆ Frequency: Medium

Short Answer

Two common approaches, depending on file size:

  • Direct multipart POST: multipart/form-data straight to your API, simplest to implement, fine for small files (avatars, documents under a few MB), but ties the raw bytes to your application server's request handling and memory, which doesn't scale to large files or high upload volume.
  • Pre-signed URL (two-step): the client POSTs metadata only, the server returns a pre-signed upload URL (S3/GCS-style) plus a resource id, the client PUTs the actual bytes directly to object storage, then confirms completion via a callback or a final POST. This takes your app server entirely out of the data path - it never touches the file bytes - which is the standard approach for anything beyond small files.
POST /api/v1/documents
--> 201 Created
    { "id": "d1", "uploadUrl": "https://storage.../d1?signature=...", "expiresIn": 900 }

PUT https://storage.../d1?signature=...   (client uploads bytes directly to storage)

POST /api/v1/documents/d1/complete        (client confirms; server verifies + kicks off processing)

Validate Content-Length/Content-Type up front, and treat anything beyond "bytes received" (virus scanning, transcoding, indexing) as an async step using the Q21 202-pattern - "uploaded" is not the same event as "processed and usable".

Interview Gold Point

"Uploaded and processed are two different states, and the API should expose both explicitly rather than conflating them." This distinction, plus recognizing when to take the app server off the data path with pre-signed URLs, is the senior signal here.

Q30. When do you use a POST-based search endpoint instead of GET with query parameters?

ROI: ★★★☆☆ Frequency: Medium

Short Answer

GET with query parameters (Q10) is semantically correct for search, but hits practical limits once criteria get rich: URL length limits (roughly 2-8KB depending on client/proxy/server), awkward encoding of nested boolean logic or geospatial bounds, and no request body to carry a structured query. The pragmatic escape hatch is a POST-based search endpoint: 

POST /api/v1/orders/search
Content-Type: application/json

{
  "filters": { "status": ["PAID","SHIPPED"], "amount": {"gte": 100} },
  "sort": [{"field":"createdAt","direction":"desc"}]
}

Be explicit about the trade-off this makes: the request is not HTTP-cacheable (proxies don't cache POST bodies), and it isn't safe/idempotent by method semantics even though it conceptually only reads data - so authorize it against the same read-scope as the equivalent GET, not a write-scope, and document clearly that despite the verb, this is a query, not a mutation. This is a well-precedented pattern - Elasticsearch's own _search endpoint uses POST for exactly this reason - so it's a pragmatic response to the "search violates REST purity" critique, not a design smell.

Common Mistake

Forgetting to document (and enforce, in authorization) that a POST search endpoint is read-only in effect. A code reviewer or security scanner that only looks at the HTTP verb will assume every POST is a write, unless you say otherwise.

SECTION 10 - RATE LIMITING ALGORITHMS & TRAFFIC MANAGEMENT

Q31. Compare token bucket, leaky bucket, fixed window and sliding window rate limiting algorithms.

ROI: ★★★★☆ Frequency: Medium

Short Answer

Q14 covered rate limiting's response contract (429, Retry-After); this is the algorithm choice behind it:

AlgorithmHow it worksBurst handlingNotes
Token bucketBucket holds up to N tokens, refilled at a fixed rate; each request consumes oneAllows bursts up to bucket capacityMost common default; simple to reason about and implement (Redis Cell / a Lua script)
Leaky bucketRequests queue and are processed ("leak out") at a constant rate regardless of arrival patternSmooths bursts into a steady output rateAdds queuing latency; drops/rejects when the queue is full
Fixed window counterCount requests in a hard clock-aligned window (e.g. per minute)Boundary-burst problem: 2x the limit can slip through at a window edgeCheapest to implement (Redis INCR + EXPIRE)
Sliding window (log/counter)Tracks timestamps (log) or interpolates between adjacent fixed windows (counter)Smooths out the fixed-window boundary problemMore accurate, more memory/CPU per check (Redis sorted sets for the log variant)

Token bucket is the pragmatic default for a public API because it explicitly allows short bursts (a client that's been idle can spend up to the bucket's full capacity in one burst) while still enforcing a long-run average - which matches how real client traffic actually behaves. Sliding window is worth the extra cost specifically when the fixed-window boundary exploit (batching requests at the edge of two adjacent windows to briefly double your effective rate) is a real concern, e.g. for a security-sensitive endpoint like login.

Interview Gold Point

Naming the fixed-window boundary problem specifically - "a client can send up to 2x the limit by timing requests at the tail of one window and head of the next" - is the detail that separates candidates who've only read the algorithm names from those who've actually reasoned about their failure modes.

Q32. What rate-limit response headers does a well-designed API return, and why on every response?

ROI: ★★★☆☆ Frequency: Medium

Short Answer

Beyond the 429 itself (Q14), a well-designed API returns quota headers on every response, not only when a client gets rejected, so well-behaved clients can throttle themselves before ever hitting the wall: 

HTTP/1.1 200 OK
RateLimit-Limit: 100
RateLimit-Remaining: 37
RateLimit-Reset: 42

There are two overlapping conventions in the wild: the long-standing de facto X-RateLimit-Limit/-Remaining/-Reset (used by GitHub, Twitter and many others), and the newer IETF draft standard RateLimit-Limit/-Remaining/-Reset without the X- prefix. Neither has full industry consensus yet - pick one, document it clearly, and be consistent across every endpoint. Where API tiers exist (free/pro/enterprise), the limit a client sees in these headers should automatically reflect their actual tier's quota, so a client library can adapt its throttling without hard-coding tier-specific numbers.

Common Mistake

Only sending rate-limit headers on the 429 response itself. By then the client has already been rejected - the headers are far more useful proactively, on successful responses, so a well-behaved client can back off before it ever gets throttled.

Q33. How do you design multi-tier rate limits (per-key, per-IP, per-tenant) with graceful degradation?

ROI: ★★★☆☆ Frequency: Medium

Short Answer

Real systems layer several limiters, each protecting a different thing: a coarse per-IP or per-anonymous-key limit at the edge defends against abuse before auth even runs; a per-API-key/per-user limit enforces fair use of the shared service; and a per-tenant aggregate limit (see Q49) prevents one noisy tenant's many individually-under-quota users from collectively starving a shared downstream resource (a DB, a third-party API) that every tenant relies on.

"Graceful degradation" means that as the system nears capacity, it should shed load selectively rather than fail uniformly: prefer rejecting or delaying lower-priority traffic (background sync, analytics polling) over user-facing requests, and prefer serving a slightly stale cached response over a hard failure where staleness is tolerable. This is the bulkhead idea from the Microservices/resilience chapters, applied at the API-contract layer rather than the infrastructure layer.

Interview Gold Point

"Rate limiting isn't one number - it's a layered set of limits, each protecting a different failure mode, from edge abuse up to shared-resource contention." That framing shows you've thought about limits as a system property, not a single config value.

Q34. What is the difference between 429 and 503 for signaling backpressure, and how should clients react to each?

ROI: ★★★★☆ Frequency: Medium

Short Answer

Both tell a client to slow down, but they mean different things and should be handled differently:

  • 429 Too Many Requests: this specific client used more than their quota allows. It is client-attributable, and the accompanying Retry-After/rate-limit-reset headers (Q32) are meaningful and specific to that client's own window.
  • 503 Service Unavailable: the service overall is over capacity or shedding load - not this client's fault specifically. It may come from a load balancer's health check tripping, or the app deliberately returning it once a concurrency/queue-depth threshold is crossed (a bulkhead pattern). Any Retry-After here is a generic, system-level hint, not a personalized quota reset.

Client-side implication: back off with exponential backoff and jitter for both, but honor the specific reset time given on a 429, while treating a 503's retry hint as more conservative and generic, since the server gave no client-specific information about when capacity will free up.

Interview Favorite

"429 says 'you personally used too much'; 503 says 'the service overall is over capacity, and it's not about you specifically.'" A crisp one-line distinction like this is exactly what interviewers are listening for on this question.

SECTION 11 - VERSIONING EVOLUTION, DEPRECATION & TRACEABILITY

Q35. How do you communicate API deprecation and sunset to consumers?

ROI: ★★★★☆ Frequency: Medium

Short Answer

Signal deprecation in-band, in the HTTP response itself, not only in a changelog nobody reads: 

HTTP/1.1 200 OK
Deprecation: true
Sunset: Sat, 31 Dec 2026 23:59:59 GMT
Link: <https://docs.acme.com/migrate-v2>; rel="sunset"

Deprecation marks "this still works today, but is deprecated". Sunset (RFC 8594) gives the actual hard date after which it stops working. A Link header with rel="sunset" points at a migration guide so the signal is actionable, not just informational. Combine this with proactive, out-of-band communication - emailing API-key owners, a dashboard banner - and critically, log and alert on real server-side traffic still hitting the deprecated field/endpoint, so you know actual usage before you remove it. Never trust "surely nobody uses this anymore" without the telemetry to back it up; sunsetting a still-used endpoint without warning is one of the most consumer-hostile things an API team can do.

Interview Gold Point

Naming the Deprecation and Sunset headers by name (and RFC 8594 for Sunset) shows you've actually operated a versioned public API through a deprecation cycle, not just read about versioning strategies (Q8) in the abstract.

Q36. What is a checklist for backward-compatible schema evolution without a version bump?

ROI: ★★★★☆ Frequency: Medium

Short Answer

Extending Q8's "the best version bump is the one you never make" - concrete rules that keep a v1 contract alive:

  • Add new fields and endpoints - never require them on existing clients.
  • Never remove or rename a field or endpoint in place; add the replacement, deprecate the old one (Q35), run both during the deprecation window.
  • Never change a field's type or meaning in place (e.g. status going from a string enum to an integer code) - that silently breaks every existing deserializer.
  • Never make an optional field required.
  • Widening an enum is only safe if clients are contractually required to tolerate unknown values gracefully - state that expectation explicitly in the docs as part of the contract, don't assume it.
  • Pagination/envelope shape changes count as breaking too - treat the response envelope itself (Q46) as part of the versioned contract, not just individual field values.

Anything outside this list is a breaking change and needs the version bump, deprecation window and migration communication from Q8/Q35 - not a silent in-place edit.

Common Mistake

Treating "adding a required field" as a minor, safe change because it "just adds more data". From an existing client's point of view, a newly-required field it never sends is indistinguishable from a breaking validation change - it will start failing requests it used to make successfully.

Q37. What is the role of correlation/request-id headers at the API boundary?

ROI: ★★★☆☆ Frequency: Medium

Short Answer

Every response - success or error - should carry a correlation id (X-Request-Id, or the W3C standard traceparent header used by distributed tracing systems) generated at the edge if the client didn't already supply one, echoed back to the client, and logged alongside the request server-side. On an error, it belongs in the RFC 7807 body as the traceId extension member from Q11/Q19.

This is what turns "the API returned an error for me around 3pm" into an actual, findable log line, and lets a client attach the same id when filing a support ticket instead of the support engineer having to reconstruct which of thousands of requests around that time was theirs. This chapter's scope stops at the HTTP-contract surface - the header's name, its presence on every response, and its slot in the error body; how that id propagates across service hops as a distributed trace (spans, sampling, exporters) is the Microservices/observability chapters' job.

Interview Favorite

"A correlation id on every response is cheap to add and disproportionately valuable in production support - it's the single header I'd never ship an API without." A simple, confident line like this lands well because it's true and easy to defend.

Q38. How do you manage multiple concurrent API versions in one codebase without it rotting?

ROI: ★★★☆☆ Frequency: Medium

Short Answer

Once v1 and v2 run side by side during a deprecation window (Q8/Q35), the risk is the two turning into a maintained parallel implementation that silently drifts. Guardrails:

  • Route both versions to the same internal domain/service layer, and fork only at the thin controller/DTO-mapping layer - business logic should never be duplicated per version.
  • Contract-test both versions independently in CI against their own OpenAPI specs (Q40), so a change made to fix v2 can't silently break v1 underneath it.
  • Track per-version traffic (the same telemetry from Q35) so you know, with evidence, when v1 usage has dropped enough to actually retire it - not just when it feels like enough time has passed.

The target state: supporting an old version should look like a thin adapter over shared internals, not a second implementation someone has to remember to keep in sync by hand.

Common Mistake

Copy-pasting the v1 controller to create v2's, then fixing bugs in only one of them going forward. This is exactly how "supporting two versions" quietly turns into "maintaining two products".

SECTION 12 - OPENAPI, CONTRACT-FIRST DEVELOPMENT & SDK GENERATION

Q39. What are the trade-offs between contract-first and code-first OpenAPI generation?

ROI: ★★★★☆ Frequency: Medium

Short Answer

Q16 introduced springdoc-openapi generating docs from annotated code - that's the code-first approach: fast to start, and the spec tracks what the code actually accepts reasonably well (modulo incomplete/wrong annotations), but the contract itself is only discovered after the implementation exists, which makes it hard to review the API shape before writing code, and hard for a separate client/frontend team to start integration work early.

Contract-first flips the order: the OpenAPI YAML is written by hand (or in a design tool) as the source of truth first, server-side interface stubs are generated from it (e.g. via openapi-generator) that the implementation must satisfy, and client SDKs are generated from that same file for every consumer. This forces an explicit design review of the shape before any code exists, lets client teams start against a mock server immediately, and guarantees the client and server are working from literally the same schema, not two hand-written approximations of it.

Recommend contract-first for public/partner APIs and any cross-team internal API where the contract itself is the expensive-to-change asset; code-first for a small internal service owned start-to-finish by one team, where the extra process overhead of maintaining a separate spec file doesn't pay for itself.

Interview Gold Point

"Contract-first isn't about purity - it's useful specifically when the contract crosses a team or organizational boundary, because that's where an out-of-sync assumption between client and server actually costs real time." Framing it as a boundary-driven choice, not a universal best practice, reads as senior.

Q40. What is consumer-driven contract testing and how does it relate to OpenAPI?

ROI: ★★★★☆ Frequency: Medium

Short Answer

Contract tests catch a gap unit tests miss entirely: does the real running server actually conform to what it publishes, and does a real client actually only rely on what's promised? Two complementary techniques:

  • Provider-side schema validation: fire real requests at the running service and validate each response against the OpenAPI schema (tools like Dredd, schemathesis, or REST-assured combined with a swagger/OpenAPI request-validator). This catches drift between the annotations/spec and actual runtime behavior that a code review would miss.
  • Consumer-driven contracts (Pact-style): the consumer team publishes the exact request/response interactions its code actually relies on; the provider's CI replays those interactions against its own code before every deploy, and fails the build if a provider-side change would break a real, currently-registered consumer.

The consumer-driven approach is the more powerful of the two at scale: it catches a breaking change before release rather than after, and it scales to many consumer teams without the provider team having to manually track "who calls what" - the consumers themselves declare their reliance, and the tooling enforces it.

Interview Favorite

"Consumer-driven contracts shift the 'did I just break someone' question from a Slack message after the fact to a failing CI build before the deploy even ships." That's the concrete payoff worth stating out loud.

Q41. How do you document async patterns like 202+poll and webhooks in OpenAPI?

ROI: ★★★☆☆ Frequency: Low-Medium

Short Answer

OpenAPI models standard request/response CRUD cleanly, but async patterns (Section 8) need explicit conventions since the spec has no native "this response points at that other endpoint" construct: for the 202+poll pattern (Q21), document both the initiating operation's 202 response and the polling resource's GET as separate paths, and describe the relationship between them in prose/examples, since the Location header's target isn't something OpenAPI can express as a typed link on its own.

For webhooks (Q23), OpenAPI 3.1 added first-class top-level webhooks: support - the payload shape your service will POST to a consumer's callback URL can now be described the same way as any normal path, letting consumers validate and generate types for incoming webhook payloads, not just outgoing API calls. Pre-3.1 tooling used the less standardized callbacks keyword nested under an operation for roughly the same purpose - worth knowing the history if you're working against an older OpenAPI 3.0 toolchain.

Common Mistake

Leaving async/webhook behavior entirely out of the OpenAPI spec because "it doesn't fit the normal request/response shape". A partial spec that only covers the synchronous CRUD surface leaves exactly the trickiest part of the API (the async contract) undocumented and untestable by the tooling in Q40.

Q42. How do you keep OpenAPI documentation from drifting out of sync with the running code?

ROI: ★★★☆☆ Frequency: Medium

Short Answer

Docs rot the moment they're maintained by hand, separately from the code path they describe. Three guardrails, in increasing order of rigor:

  • Prefer code-first generation (Q39) for the base shape, or contract-first with generated server stubs, so a mismatch becomes a compile error rather than a stale doc nobody notices.
  • Add the provider-side schema-validation contract test from Q40 to CI, so any response that violates the published schema fails the build - not just a manual QA pass that may or may not happen.
  • Diff the generated OpenAPI spec between pull requests (openapi-diff-style tooling) and require explicit review/approval on any detected breaking change, turning "did we just silently break v1" from a code-review guess into an automated CI gate.

Interview Gold Point

Mentioning spec-diffing in CI as a breaking-change gate is a detail most candidates miss entirely - it directly operationalizes the backward-compatibility checklist from Q36 instead of leaving it as a manual discipline someone has to remember to apply.

SECTION 13 - API GATEWAY / BFF PATTERN & CLIENT-SHAPED CONTRACTS

Q43. What is the Backend-for-Frontend (BFF) pattern at the API-design level?

ROI: ★★★★☆ Frequency: Medium

Short Answer

This is a different concern from the infrastructure-level API Gateway covered in the Microservices chapter (routing, TLS termination, service mesh). Here, the question is purely about contract shape: different client families - a native mobile app, a web SPA, a partner integration - genuinely want different response shapes from the same underlying domain data. A BFF is a thin API layer, one per client family, that aggregates and reshapes calls to one or more backend services into exactly what that specific client needs: fewer round trips (mobile especially benefits, given higher-latency networks), fields trimmed to only what that UI actually renders, and protocol translation where useful (e.g. the mobile BFF speaks GraphQL to the app while calling REST/gRPC services internally).

Contrast this with exposing one generic REST API to every client and letting each hand-roll its own aggregation and field-trimming client-side - simpler to operate (one contract to maintain) but pushes over-fetching, under-fetching and multi-call orchestration cost onto every consuming client. The trade-off worth naming explicitly: a BFF is an extra service to own, deploy and version per client family - justify it once client needs have genuinely diverged, not reflexively by default for every project.

Interview Gold Point

"A BFF is a contract-shaping decision, not an infrastructure decision - it can sit entirely behind an existing API gateway, and the two solve different problems." Making that separation explicit avoids the common confusion between this pattern and ch.19's gateway.

Q44. How do sparse fieldsets and field expansion (?fields=, ?expand=) work as a lighter-weight alternative to a BFF?

ROI: ★★★☆☆ Frequency: Medium

Short Answer

When client divergence is only "which fields/relations does this client need", not a fully different shape, a lighter mechanism than a full BFF often suffices:

  • Sparse fieldsets (extends Q10): GET /orders/42?fields=id,total,status trims the response to reduce payload size for bandwidth-constrained clients.
  • Field expansion (the inverse problem - avoiding client-side N+1 calls): GET /orders/42?expand=customer,items embeds related resources inline instead of forcing the client to follow separate URIs per relation, which is similar in spirit to what GraphQL gives natively, bolted onto plain REST.

Guardrails matter here as much as the feature itself: whitelist which fields/relations are selectable/expandable server-side (the same injection/performance concern as Q10's sort/filter allow-list), cap expansion depth so a client can't accidentally trigger serialization of a huge object graph, and treat expand as a real server-side performance concern - a naive implementation that lazy-loads each expanded relation independently just relocates the N+1 query problem from the client to the server instead of eliminating it.

Common Mistake

Implementing ?expand= by lazily fetching each relation one at a time per request. That "fixes" the client's N+1 problem by creating the exact same N+1 problem inside your own service against the database.

Q45. How should API design differ for mobile, web and partner/public consumers?

ROI: ★★★☆☆ Frequency: Medium

Short Answer

The same underlying domain operation can reasonably be exposed through different contracts for different consumer types:

  • Mobile: minimize round trips and payload size (metered, higher-latency networks, battery cost) - favor fewer, richer endpoints and app-specific shaping, which is exactly what a BFF (Q43) is built for.
  • Web/SPA: typically has better, cheaper connectivity, and benefits most from standard browser HTTP caching - favor staying closer to plain REST with ETags (Q15) over heavy custom aggregation.
  • Partner/public API: stability and long-term backward compatibility matter far more than payload optimization, since partners integrate once and rarely revisit the integration - favor a conservative, well-versioned (Q8/Q35), thoroughly documented (Q39) generic contract over anything client-specific, since a bespoke BFF per external partner doesn't scale.

Recognizing that a deliberately different contract per consumer type is a design choice - not an inconsistency to be "fixed" into one universal shape - is the senior signal on this question.

Interview Favorite

"The same 'get order' operation can legitimately be three different API shapes for three different consumers - the domain logic underneath is shared, the contract on top isn't." A clean line like this closes the question well.

Q46. Envelope vs bare array/object for collection responses - which do you use, and why does consistency matter more than the choice?

ROI: ★★★☆☆ Frequency: Medium

Short Answer

Two competing conventions for a collection endpoint's response body:

  • Bare array: [ {...}, {...} ] - minimal, but leaves no room for pagination metadata (total count, next cursor) without inventing out-of-band headers for it.
  • Enveloped: { "data": [...], "meta": {"total": 532, "nextCursor": "..."}, "_links": {...} } - gives pagination (Q9) and hypermedia (Q20) metadata an obvious home, at the cost of clients needing to unwrap data everywhere, and some client codegen tooling deserializing it less cleanly into a plain list type.

Recommend enveloped for any collection endpoint that paginates - which is most of them - since the metadata needs somewhere to live; a bare single-resource GET is fine either convention. The actual mistake is not which one you pick, it's mixing both conventions across different endpoints of the same API - a client library has to special-case "is this endpoint's list response wrapped or not" per endpoint, which is exactly the kind of inconsistency that erodes trust in an API's design.

Common Mistake

Different teams within the same company shipping some endpoints with a bare array and others enveloped, with no shared convention. Consistency across the whole surface matters more than which specific convention wins.

Interview Gold Point

"The tenant id in the URL or header is a routing convenience for the client - the tenant id in the auth token's claims is the actual security boundary." Drawing that line clearly is what separates a correct answer from a subtly exploitable one.

Q48. What are the data isolation implications of multi-tenancy for endpoint and schema design?

ROI: ★★★☆☆ Frequency: Medium

Short Answer

The API-level tenant identification from Q47 only matters if it's backed by real isolation at the data layer - otherwise it's theater. Three common isolation models, and how each shows up in the design:

  • Shared schema, tenant_id column: cheapest to operate, but every query must filter by tenant_id, and a single missed WHERE clause is a cross-tenant data leak. Mitigate with a global query filter (a Hibernate @Filter, or a repository-level interceptor applied uniformly) rather than relying on every developer remembering it by convention on every query.
  • Schema-per-tenant: stronger isolation, but migrations must run per-schema and connection routing gets materially more complex.
  • Database-per-tenant: strongest isolation, and it conveniently simplifies "delete all of a tenant's data" for offboarding/compliance requests, at the highest operational overhead.

Whichever model is chosen, the endpoint contract itself should look identical to the client - tenant scoping is a server-side implementation concern, not something that should leak into the API shape beyond the tenant-identification mechanism from Q47.

Common Mistake

Relying on "every repository method remembers to filter by tenant_id" as the only isolation mechanism in a shared-schema design. One missed filter, in one query, in one code path, is a real cross-tenant data breach - enforce it structurally (a global filter/interceptor), not by convention.

Q49. How do you design rate limiting and quotas per tenant versus per user?

ROI: ★★★☆☆ Frequency: Low-Medium

Short Answer

Extending Q33's multi-tier limits with the multi-tenant case specifically: apply the rate limiter's key at the tenant level, not just per API key or per individual user, for any limit meant to protect shared infrastructure. Otherwise a tenant with 500 users, each individually well under their own personal quota, can still collectively overwhelm a shared downstream resource (a database, a third-party API) that the whole platform depends on.

Design tiered quotas that map to the tenant's commercial plan (free/pro/enterprise), and expose the tenant's current usage through a self-serve endpoint (GET /tenants/{id}/usage) so customers can see how close they are to their limit proactively - discovering a quota only via a wave of 429s in production is a materially worse experience for a paid API product than a visible usage dashboard.

Interview Gold Point

"The rate limit key should match the unit that's actually sharing the constrained resource - if that unit is the tenant, not the individual user, the limiter has to key on tenant." That's the precise reasoning interviewers want here, not just "add a limit per tenant" as a rule of thumb.

Q50. How do you design tenant-scoped versus global/admin endpoints in a multi-tenant API?

ROI: ★★★☆☆ Frequency: Low-Medium

Short Answer

Most endpoints are naturally tenant-scoped - everything under a single tenant's own data. But every multi-tenant API also needs a small set of endpoints that deliberately cross tenant boundaries: platform admin operations (list all tenants, support-tooling impersonation, cross-tenant billing/analytics). Keep these under a clearly separate namespace (/api/v1/admin/..., or an entirely separate internal-only API surface) with its own, stricter authorization (mentioned only in passing here - the authz mechanics are ch.12's territory), and ideally its own rate limits and audit logging, since accidentally exposing a "list everything across tenants" endpoint under the same contract surface as ordinary tenant-scoped routes is a real, recurring source of production data breaches.

The API-design takeaway: tenant scoping should be the default, requiring a deliberate, distinctly-named escape hatch to cross it - never the reverse, where crossing tenant boundaries is the default and scoping is something a developer has to remember to add.

Common Mistake

Building the "admin, cross-tenant" version of an endpoint by adding an optional query parameter to the normal tenant-scoped endpoint (e.g. ?allTenants=true) instead of a distinctly namespaced, separately authorized route. That pattern has caused real breaches when the parameter's authorization check was missed or bypassed.

SECTION 15 - CONTRACT-BOUNDARY SECURITY & DATA SHAPE

Q51. How does CORS work at the API-design level, and what does it actually protect against?

ROI: ★★★★☆ Frequency: Medium

Short Answer

CORS (Cross-Origin Resource Sharing) is a browser-enforced policy, not a server-side access control on its own - a non-browser client (curl, a mobile app, a server-to-server call) ignores it entirely. It's still part of your API's contract with browser-based clients and needs deliberate design. For a "non-simple" request (a custom header, a method other than GET/POST/HEAD, a JSON content type), the browser first sends a preflight OPTIONS asking which origins/methods/headers are allowed; the server answers with Access-Control-Allow-Origin, -Methods, -Headers, and, if cookies/credentials are involved, Access-Control-Allow-Credentials: true - which specifically forbids pairing with a wildcard * origin, so a credentialed response must echo back one specific allowed origin. 

Access-Control-Allow-Origin: https://app.acme.com
Access-Control-Allow-Methods: GET, POST, PATCH, DELETE
Access-Control-Allow-Headers: Content-Type, Authorization
Access-Control-Allow-Credentials: true
Access-Control-Max-Age: 3600

Design guidance: maintain an explicit allow-list of origins - never * for any endpoint that reads authenticated or sensitive data - and cache the preflight response via Access-Control-Max-Age to avoid paying the extra round trip on every request. Remember what CORS actually protects against: a malicious page in the victim's own browser trying to call your API using the victim's cookies/session. It is not what stops a malicious server from calling your API directly - that's real authentication/authorization (see the Spring Security chapter), which CORS does not replace.

Interview Gold Point

"CORS is a browser-side safety mechanism protecting the user, not a server-side authorization mechanism protecting the API." Stating this distinction clearly heads off the most common misconception interviewers probe for on this topic.

Q52. What is mass assignment, and how do you prevent it at the API boundary?

ROI: ★★★★☆ Frequency: Medium

Short Answer

Mass assignment is binding a client's raw request body directly onto a domain/entity object that has more settable fields than the client should ever be allowed to control - for example, a PATCH /users/42 body that includes {"role": "ADMIN"} getting bound straight onto the JPA User entity, simply because the entity happens to have a role setter, even though no legitimate UI ever exposed that field to the caller. 

// Vulnerable: entity deserialized directly from the request body
@PatchMapping("/users/{id}")
public User update(@PathVariable Long id, @RequestBody User body) {
    return userRepository.save(body); // "role" rides along if present in the JSON
}

// Fixed: a dedicated DTO that only exposes what a client may set
public record UpdateUserRequest(String name, String email) {}

@PatchMapping("/users/{id}")
public UserDto update(@PathVariable Long id, @Valid @RequestBody UpdateUserRequest req) {
    return userService.updateProfile(id, req); // role is structurally not settable here
}

The fix: never deserialize a request body directly into a persistence entity; always bind into a purpose-built request DTO that declares only the fields a client is actually permitted to set for that specific operation, and map DTO to entity explicitly. Any entity field absent from the DTO cannot be set from the wire - structurally, not by convention or code-review vigilance. This composes naturally with the request-validation pattern from Q12, since the DTO is already exactly where @Valid annotations live.

Interview Gold Point

"The DTO boundary isn't just about validation - it's the single structural control that prevents mass assignment, because a field that doesn't exist on the DTO literally cannot be bound from client input." Tying request DTOs to security, not just to clean code, is the senior framing here.

Q53. Soft delete vs hard delete - what does DELETE actually do to the row, and what should GET return afterward?

ROI: ★★★☆☆ Frequency: Medium

Short Answer

DELETE /orders/42 returning 204 (Q3/Q4) doesn't dictate what actually happens to the underlying row - two implementations, with different contract implications:

  • Hard delete: the row is physically removed. A subsequent GET correctly returns 404 - the resource is genuinely gone, and the contract is simple with no recovery path.
  • Soft delete: a deletedAt/status=DELETED flag is set and the row is retained, supporting recovery, audit trails and retention/compliance requirements. This complicates the read contract: should a GET after a soft-delete still return 404 (arguably correct from the client's perspective - "this resource no longer exists to you"), or 410 Gone - a status specifically meaning "this used to exist here and is now permanently gone", distinct from 404's "never existed or not found"?

Whichever convention is chosen, apply it consistently across the API, and remember that every collection/list/filter endpoint (Q9/Q10) must explicitly exclude soft-deleted rows by default - a frequently missed spot that leaks "deleted" data back into list views, mirroring exactly the tenant-filter discipline from Q48 (a query that forgets one WHERE clause).

Common Mistake

Implementing soft delete at the persistence layer but forgetting to add the exclusion filter to every list/search endpoint, so "deleted" records reappear the moment someone lists or filters instead of fetching by id directly.

Q54. What defensive limits (input size, timeouts, abuse prevention) belong at the API-contract level?

ROI: ★★★☆☆ Frequency: Medium

Short Answer

Beyond field-level validation (Q12), a hardened contract also bounds how much resource any single request can consume, independent of who's making it:

  • Request body size: reject oversized payloads early, before they reach business logic (e.g. Spring's multipart/servlet container size limits), with 413 Payload Too Large.
  • Batch/page size caps: cap array/batch sizes (Q26) and enforce a hard server-side maximum page size (Q9) regardless of what a client requests in ?limit=, rejecting an unreasonable value with 400 rather than letting a single query starve the database.
  • Request timeouts: bound how long a slow client or a slow downstream dependency can hold a connection/thread, tying into the rate-limiting/backpressure discussion in Q33-34.
  • Nested payload depth: reject deeply nested JSON with a max-depth check - a cheap but real denial-of-service vector via parser stack depth that field-level validation alone won't catch.

None of this replaces authentication or authorization; it's the contract-level discipline that keeps any single request - authenticated or not - from being disproportionately expensive to serve.

Interview Gold Point

"These limits protect the service from cost, not from unauthorized access - they're a different axis from authn/authz entirely, and both need to be designed deliberately." Making that distinction explicit shows you're not conflating two separate concerns under one "security" umbrella.

SECTION 16 - REST vs GraphQL vs gRPC: A DECISION FRAMEWORK

Q55. Beyond the basic comparison table, how do you actually decide between REST, GraphQL and gRPC for a given client?

ROI: ★★★★☆ Frequency: Medium

Short Answer

Q16 gave the comparison table; this is the decision process behind it, asked in order:

  1. Who is the primary consumer? The public internet/third parties (favors REST, for ubiquity, caching and tooling every client already has); your own diverse frontend clients with varied, evolving data-shape needs (favors GraphQL, or a BFF over REST per Q43); or your own services talking to each other at high volume and low latency (favors gRPC).
  2. Does HTTP-layer caching matter for this traffic? REST's GET-based caching (CDN, browser, reverse proxy - Q15) is a real, hard-to-replicate advantage that GraphQL (mostly POST) and gRPC (binary, not HTTP-cacheable) both give up.
  3. How strong a schema-evolution story do you need? gRPC's Protobuf IDL and GraphQL's schema both give strong compile-time contracts and codegen out of the box; REST's is only as strong as your own OpenAPI discipline (Q39-42).

On migration: teams rarely do a flag-day rewrite from one style to another. In practice, a GraphQL or gRPC layer gets added alongside an existing REST API for the specific consumer that benefits (a new mobile client, a new internal service), rather than migrating the whole surface - because existing REST consumers (public partners, legacy integrations) have no reason to move and every reason to be left alone, which is exactly the backward-compatibility discipline from Q8/Q35 applied at the protocol-choice level rather than the field level.

Interview Gold Point

"I don't migrate a whole API from REST to GraphQL - I add GraphQL for the specific consumer whose needs justify it, and leave the REST surface alone for everyone else." This answer shows you think about protocol choice per-consumer, not as an all-or-nothing platform decision.

Q56. How do you aggregate or federate multiple backend services behind one client-facing contract?

ROI: ★★★☆☆ Frequency: Medium

Short Answer

As a system decomposes into more services, a single logical client request - "render an order detail page" - may need data owned by several different services (orders, inventory, customer). Client-facing options, roughly in order of increasing power and complexity:

  • Expose the services as-is and let the client make multiple calls - simplest to build, but pushes aggregation and partial-failure handling onto every client.
  • Build a BFF/aggregation layer (Q43) that fans out server-side and returns one composed response - centralizes the fan-out and partial-failure logic once, at the cost of an extra hop and an extra service to maintain.
  • Adopt GraphQL federation (Apollo Federation / GraphQL Mesh-style) where each service publishes its own subgraph and a gateway stitches them into one unified schema, letting the client query across service boundaries in a single round trip with no team hand-writing the aggregation logic.

Federation is powerful but adds real operational complexity of its own - schema composition, cross-service query planning, and versioning a schema that now spans team boundaries. The pragmatic guidance: reach for a hand-written BFF first, and only invest in federation tooling once you have enough services and teams that the coordination cost of hand-written aggregation genuinely outweighs the federation tooling's own overhead.

Interview Favorite

"Federation solves a coordination problem, not a technical one - it's worth it exactly when enough independent teams need to compose data without a single team owning all the aggregation code." That framing shows you evaluate it as an organizational trade-off, not just a technology choice.

Q57. When is it reasonable to expose REST, GraphQL and gRPC from the same backend at once, and how do you avoid duplicated business logic?

ROI: ★★★☆☆ Frequency: Medium

Short Answer

It's common and reasonable for one backend domain to be reachable through more than one contract simultaneously, each serving a different consumer per Q45/Q55: gRPC between the service and its internal siblings for low-latency calls, REST at the public edge for partners/webhooks/third-party integrators who expect ubiquitous HTTP+JSON tooling, and GraphQL for the company's own web/mobile frontends that need flexible, aggregated queries.

The risk to actively manage: business logic must live in exactly one shared internal layer (domain/application services), with each protocol's API surface acting as a thin adapter that only translates its wire format to and from that shared layer. The mistake to avoid is implementing the same business rule three times - once per protocol adapter - which drifts subtly out of sync the moment one gets updated and the others don't (a discount rule fixed in the REST controller but never ported to the gRPC service, for instance).

Interview Gold Point

"The protocol is a client-facing concern; the domain logic underneath should not know, or care, which contract style is being spoken above it." That closing line ties Section 15 back to the whole chapter's central theme - the HTTP/REST contract is a boundary decision, not where the business logic itself should live.

QUICK REVISION SHEET

  • REST constraints (6): Client-Server, Stateless, Cacheable, Uniform Interface, Layered System, Code-on-Demand (optional). Statelessness enables horizontal scaling.
  • Richardson Maturity: L0 RPC -> L1 resources -> L2 verbs+status (industry norm) -> L3 HATEOAS.
  • Methods: GET read, POST create (server id), PUT full replace / create at known id, PATCH partial, DELETE remove.
  • Safe = no state change (GET/HEAD/OPTIONS). Idempotent = same state after N calls (GET, PUT, DELETE, HEAD). POST & PATCH not guaranteed.
  • Status codes: 200 OK, 201 Created (+Location), 204 No Content, 304 Not Modified, 400 malformed, 401 not authenticated, 403 not allowed, 404 missing, 409 conflict/stale version, 422 semantic validation, 429 rate limited, 5xx server.
  • URIs: plural nouns, lowercase-hyphenated, shallow nesting, query params for filter/sort/page, methods carry the verb.
  • Versioning: URI (common, cache-friendly), header/media-type (purist), query (avoid). Best version bump = none; prefer additive changes.
  • Pagination: offset (random access, drifts, slow deep pages) vs cursor/keyset (stable, O(limit), no jump) - keyset for live/large data.
  • Errors: RFC 7807 problem+json, central @RestControllerAdvice, include traceId, never leak stack traces.
  • Validation: Bean Validation + @Valid at the edge (400/422), return all field errors at once.
  • Idempotency key: header (UUID) stored with first result; replays make POST safely retryable (payments).
  • Rate limit: 429 + Retry-After + X-RateLimit-* headers; shared (Redis) counter, enforce at the edge.
  • Caching/concurrency: ETag + If-None-Match -> 304; ETag + If-Match -> 412/409 optimistic locking. Cache-Control governs lifetime.
  • Content negotiation: Accept / Content-Type; 406 if unsupported; basis of media-type versioning.
  • Docs: OpenAPI/Swagger via springdoc-openapi - auto-generated, interactive, drives SDK codegen.
  • REST vs GraphQL vs gRPC: REST for public CRUD + caching; GraphQL for flexible client queries; gRPC for fast internal service-to-service. Often combined per boundary.
  • Conditional writes: If-Match/If-Unmodified-Since -> 412 on stale version (optimistic concurrency); If-None-Match: * -> create-if-absent.
  • PATCH bodies: JSON Merge Patch (RFC 7396, simple, absolute values, idempotent) vs JSON Patch (RFC 6902, ops array, precise, not always idempotent).
  • Async patterns: 202 + Location + poll for long-running ops; model as a job resource; webhooks (HMAC-signed, at-least-once, idempotent receiver) for server-initiated events; SSE for one-way streaming.
  • Bulk/batch: cap batch size; 207 Multi-Status for partial success; state explicitly whether transactional or best-effort.
  • Rate limit algorithms: token bucket (bursty, common default), leaky bucket (smooths), fixed window (boundary-burst flaw), sliding window (accurate, costlier). 429 = client quota; 503 = system overload.
  • Deprecation: Deprecation + Sunset (RFC 8594) + Link headers; monitor real usage before removing anything. Never remove/rename/retype a field in place - add and deprecate instead.
  • OpenAPI: code-first (fast, drifts less from code) vs contract-first (design-reviewed, drives SDKs/mock servers); back it with provider schema validation and/or consumer-driven (Pact) contract tests in CI.
  • BFF / client-shaped contracts: one thin aggregation layer per client family (mobile/web/partner), distinct from ch.19's infrastructure gateway; sparse fieldsets/?expand= as a lighter alternative.
  • Multi-tenancy: identify tenant via path/header/subdomain but trust the auth token's claim; enforce isolation structurally (global query filter), not by convention; separate, stricter-scoped admin/cross-tenant endpoints.
  • Contract-boundary security: CORS protects the browser/user, not the API itself; prevent mass assignment via dedicated request DTOs, never bind entities directly; soft vs hard delete changes what GET returns afterward (404 vs 410).
