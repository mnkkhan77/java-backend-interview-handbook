15 - DESIGN PATTERNS INTERVIEW HANDBOOK

Design patterns are proven, reusable solutions to recurring design problems. For a Senior Software Engineer they matter for two reasons: interviewers test them directly, and — more importantly — the entire Spring framework is built on them, so understanding patterns explains why Spring works the way it does. Patterns fall into three families: * Creational — how objects are created (Singleton, Factory, Builder, Prototype) * Structural — how objects are composed (Adapter, Decorator, Proxy, Facade) * Behavioural — how objects interact (Strategy, Observer, Template Method, Command) A strong candidate does not just recite definitions — they say where the pattern appears in the JDK or Spring, and when NOT to use it. Patterns are tools, and over-engineering with patterns you do not need is a real anti-pattern.

SECTION 1 - CREATIONAL PATTERNS

Q1. What Are Design Patterns and Why Use Them?

ROI: ★★★★☆ Frequency: High

A design pattern is a named, reusable solution to a problem that recurs across many designs. They are not code you copy — they are templates for how to structure classes and objects.

Their value is communication and proven structure: saying "use a Strategy here" instantly conveys intent to any engineer, and the pattern comes with known trade-offs so you avoid reinventing (and re-breaking) the wheel.

Interview Gold Point

The mature answer adds a caveat: patterns add indirection and abstraction, which is cost. Apply them when the flexibility is actually needed, not pre-emptively. "Make it work, make it right, make it fast" — patterns belong to the "make it right" step, not premature design.

Q2. Explain the Singleton Pattern and How to Make It Thread-Safe

ROI: ★★★★★ Frequency: Extremely High

A Singleton ensures a class has exactly one instance with a global access point — used for shared, stateless resources like configuration or connection pools. The challenge is making creation thread-safe without paying a lock cost on every access.

Double-Checked Locking

public class Config {
    private static volatile Config instance;
    private Config() {}

    public static Config getInstance() {
        if (instance == null) {                 // 1st check (no lock)
            synchronized (Config.class) {
                if (instance == null)           // 2nd check (locked)
                    instance = new Config();
            }
        }
        return instance;
    }
}

The volatile keyword is essential — without it, another thread could see a partially constructed object due to instruction reordering.

Interview Gold Point

The cleanest thread-safe Singleton in Java is an enum: enum Config { INSTANCE; }. The JVM guarantees a single instance and handles serialization and reflection attacks for free. Also note: a Spring bean is a singleton per container by default — a different, framework-managed concept.

Q3. Factory vs Abstract Factory

ROI: ★★★★☆ Frequency: High

The Factory Method hides object creation behind a method, so callers ask for a product by type without using new directly. The Abstract Factory goes one level up: it creates families of related objects (e.g. a UI toolkit that produces matching buttons, checkboxes and menus for a given theme). 

// Simple factory method
interface Notification { void send(String msg); }

class NotificationFactory {
    static Notification create(String type) {
        return switch (type) {
            case "EMAIL" -> new EmailNotification();
            case "SMS"   -> new SmsNotification();
            default -> throw new IllegalArgumentException(type);
        };
    }
}

Interview Favorite

The benefit is decoupling: callers depend on the Notification interface, not concrete classes, so adding a new channel does not touch existing call sites. Spring's BeanFactory is a large-scale factory.

Q4. Explain the Builder Pattern

ROI: ★★★★★ Frequency: Very High

The Builder constructs complex objects step by step, avoiding the "telescoping constructor" problem (constructors with many parameters, half of them optional). It produces readable, immutable objects. 

User user = User.builder()
    .name("Alice")
    .email("alice@example.com")
    .age(30)
    .build();

Interview Gold Point

Mention real-world Builders you have used: Lombok's @Builder, StringBuilder, Java's Stream.Builder, and the fluent builders all over Spring (e.g. HttpSecurity, WebClient.builder()). It shines when an object has many optional fields and you want it immutable once built.

Q5. What Is the Prototype Pattern?

ROI: ★★★☆☆ Frequency: Medium

The Prototype pattern creates new objects by cloning an existing instance rather than constructing from scratch — useful when object creation is expensive, or when you want a configured template copied many times.

In Java this maps to Cloneable/clone(), though copy constructors or copy factory methods are usually clearer and avoid clone()'s well-known pitfalls (shallow copy, broken contracts).

Interview Favorite

Spring's prototype scope is named after this pattern: each request for the bean yields a fresh instance, unlike the default singleton scope.

SECTION 2 - STRUCTURAL PATTERNS

Q6. Explain the Adapter Pattern

ROI: ★★★★☆ Frequency: High

An Adapter converts the interface of one class into another that a client expects — the software equivalent of a travel power-plug adapter. Use it to make incompatible or third-party code work with your existing interfaces without modifying either side.

Interview Gold Point

JDK examples: Arrays.asList() adapts an array to a List, and the old InputStreamReader adapts a byte stream to a character stream. The key signal is "I have class A but my code needs interface B".

Q7. Explain the Decorator Pattern

ROI: ★★★★☆ Frequency: High

A Decorator adds behaviour to an object at runtime by wrapping it in another object that implements the same interface. It is the composition-based alternative to subclass explosion: instead of BufferedGzipEncryptedStream, you wrap layers. 

InputStream in = new BufferedInputStream(
                     new GZIPInputStream(
                         new FileInputStream("data.gz")));

Interview Favorite

The entire java.io stream library is the textbook Decorator example. Each wrapper adds one capability (buffering, compression) while keeping the same InputStream interface, so they compose freely.

Q8. Explain the Proxy Pattern

ROI: ★★★★★ Frequency: Very High

A Proxy is a stand-in that controls access to a real object — adding lazy loading, access control, caching, or cross-cutting logic without the caller knowing. The proxy implements the same interface as the real subject.

Interview Gold Point

This is the most important pattern for Spring developers: Spring AOP, @Transactional, @Cacheable, and lazy-loaded Hibernate entities all use proxies (JDK dynamic proxies for interfaces, CGLIB for classes). This is also why calling an @Transactional method from within the same class bypasses the proxy — the famous "self-invocation" problem.

Q9. Explain the Facade Pattern

ROI: ★★★☆☆ Frequency: Medium

A Facade provides a single, simplified interface to a complex subsystem. Clients talk to the facade instead of wiring together many low-level classes themselves, which reduces coupling.

Interview Favorite

A typical Spring @Service often acts as a facade: one placeOrder() method hides the coordination of repositories, payment gateways and notification senders behind a clean API.

SECTION 3 - BEHAVIOURAL PATTERNS

Q10. Explain the Strategy Pattern

ROI: ★★★★★ Frequency: Very High

The Strategy pattern defines a family of interchangeable algorithms behind a common interface and lets you swap them at runtime. It replaces sprawling if/else or switch blocks with polymorphism. 

interface PaymentStrategy { void pay(double amount); }

class PaymentService {
    void checkout(PaymentStrategy strategy, double amount) {
        strategy.pay(amount);   // behaviour chosen by caller
    }
}
// new PaymentService().checkout(new PaypalStrategy(), 99.0);

Interview Gold Point

In Spring you rarely hand-code this — inject a List<PaymentStrategy> or a Map<String, PaymentStrategy> and Spring wires every implementation automatically. That combination of Strategy + dependency injection is a very strong senior answer.

Q11. Explain the Observer Pattern

ROI: ★★★★☆ Frequency: High

The Observer pattern lets one subject notify many dependent observers automatically when its state changes — a publish/subscribe relationship. Observers can be added or removed without changing the subject.

Interview Favorite

Spring's ApplicationEvent / ApplicationListener (and @EventListener) is Observer in action. At an architectural scale, Kafka pub/sub is the same idea distributed across services — tie this back to the event-driven content in your Microservices chapter.

Q12. Explain the Template Method Pattern

ROI: ★★★★☆ Frequency: Medium-High

The Template Method defines the skeleton of an algorithm in a base class, deferring specific steps to subclasses. The overall sequence is fixed; only the variable steps are overridden.

Interview Gold Point

Spring's many *Template classes — JdbcTemplate, RestTemplate, TransactionTemplate — embody this: the boilerplate (open connection, handle errors, close) is fixed, and you supply only the variable bit (the SQL, the row mapper). That is also why they are called "templates".

SECTION 4 - PATTERNS IN PRACTICE

Q13. Where Does Spring Use Design Patterns?

ROI: ★★★★★ Frequency: Extremely High

This is a favourite "do you really understand the framework" question. Strong answer:

Pattern Where in Spring
Singleton Default bean scope
Factory BeanFactory / ApplicationContext
Proxy AOP, @Transactional, @Cacheable, lazy entities
Template Method JdbcTemplate, RestTemplate
Strategy Injected interface implementations
Observer ApplicationEvent / @EventListener
Builder HttpSecurity, WebClient.builder()

Interview Gold Point

Tie it together: "Spring's whole programming model is patterns — dependency injection is the Inversion of Control principle, beans are managed singletons, and AOP is built on proxies." This shows you understand the framework, not just its annotations.

Q14. What Are the SOLID Principles?

ROI: ★★★★★ Frequency: Very High

SOLID is five object-oriented design principles that lead to maintainable, loosely-coupled code — the foundation that makes patterns work:

  • S — Single Responsibility: a class should have one reason to change
  • O — Open/Closed: open for extension, closed for modification
  • L — Liskov Substitution: subtypes must be usable through their base type
  • I — Interface Segregation: many small interfaces beat one fat one
  • D — Dependency Inversion: depend on abstractions, not concretions

Interview Gold Point

Connect D directly to Spring: dependency injection is the Dependency Inversion Principle in practice — your classes depend on interfaces, and the container supplies the concrete implementation. Giving a concrete example for each letter beats reciting the acronym.

Q15. When Should You NOT Use a Design Pattern?

ROI: ★★★★☆ Frequency: Medium-High

When the flexibility it buys is not needed. Patterns add layers of abstraction and indirection, which makes simple code harder to read and debug. Introducing a Strategy for a value that will never change, or a Factory for a single concrete type, is over-engineering.

The senior mindset: start with the simplest code that works, and refactor toward a pattern only when a real, repeated need for flexibility appears — not in anticipation of one that may never come (YAGNI: "You Aren't Gonna Need It").

Interview Gold Point

Demonstrating restraint impresses senior interviewers more than naming twenty patterns. The strongest candidates know patterns deeply and know when plain, direct code is the better engineering choice.

SECTION 5 - MORE STRUCTURAL PATTERNS

Q16. Explain the Bridge Pattern

ROI: ★★★☆☆ Frequency: Medium

Bridge decouples an abstraction from its implementation so the two can vary independently. Unlike Adapter, which patches an existing mismatch after the fact, Bridge is designed in up front to avoid a combinatorial explosion of subclasses when there are two independent dimensions of variation — for example shape × renderer, or notification channel × message format. 

interface Renderer { void renderCircle(double radius); }

class VectorRenderer implements Renderer {
    public void renderCircle(double radius) { System.out.println("Vector circle r=" + radius); }
}
class RasterRenderer implements Renderer {
    public void renderCircle(double radius) { System.out.println("Raster circle r=" + radius); }
}

abstract class Shape {
    protected final Renderer renderer;   // the "bridge"
    protected Shape(Renderer renderer) { this.renderer = renderer; }
    abstract void draw();
}

class Circle extends Shape {
    private final double radius;
    Circle(Renderer renderer, double radius) { super(renderer); this.radius = radius; }
    void draw() { renderer.renderCircle(radius); }
}

Without Bridge you would need VectorCircle, RasterCircle, VectorSquare, RasterSquare and so on — N × M classes. With Bridge you need only N + M, because the shape hierarchy and the rendering hierarchy vary independently through the shared Renderer reference.

Interview Gold Point

JDBC is a textbook Bridge: java.sql.Connection is the abstraction your code programs against, and each vendor (PostgreSQL, MySQL) supplies the implementation, so your code varies independently of whichever driver is on the classpath.

Q17. Explain the Composite Pattern

ROI: ★★★★☆ Frequency: High

Composite lets you treat individual objects and compositions of objects uniformly through a shared interface, typically to model part-whole tree structures such as files and folders, UI components, or an org chart. 

interface FileSystemNode { long size(); }

class FileNode implements FileSystemNode {
    private final long bytes;
    FileNode(long bytes) { this.bytes = bytes; }
    public long size() { return bytes; }
}

class Directory implements FileSystemNode {
    private final List<FileSystemNode> children = new ArrayList<>();
    void add(FileSystemNode node) { children.add(node); }
    public long size() {
        return children.stream().mapToLong(FileSystemNode::size).sum();
    }
}

Client code calls .size() on a FileNode or a Directory identically — that uniformity is the entire point of Composite: the caller never needs an instanceof check to know whether it is holding a leaf or a branch.

Interview Favorite

Composite pairs naturally with Iterator (to walk the tree) and Visitor (to apply an operation across heterogeneous node types without polluting the node classes). Swing/AWT's Component/Container hierarchy is a classic real-world Composite.

Q18. Explain the Flyweight Pattern

ROI: ★★★☆☆ Frequency: Low-Medium

Flyweight minimizes memory usage by sharing common, immutable state (the intrinsic state) across many logical objects, while context-specific data (the extrinsic state) is passed in by the caller rather than stored per instance.

The pattern is most valuable when you would otherwise create an enormous number of nearly-identical objects — the classic textbook example is rendering characters in a text editor, where each glyph shares the same font/shape data and only its position differs per occurrence.

Interview Gold Point

Integer.valueOf(int) is the most commonly cited JDK Flyweight: values from -128 to 127 are cached and shared, which is exactly why == comparison of boxed Integers appears to work "by accident" inside that range and silently breaks outside it. String literals are interned into a shared pool for the same reason.

SECTION 6 - COMMAND & CHAIN OF RESPONSIBILITY

Q19. Explain the Command Pattern

ROI: ★★★★☆ Frequency: High

Command encapsulates a request — an action plus its parameters — as an object, so it can be queued, logged, undone, or passed around like any other value. It decouples the invoker (a button, a scheduler) from the receiver (the object that actually performs the work). 

interface Command { void execute(); void undo(); }

class AddTextCommand implements Command {
    private final StringBuilder doc;
    private final String text;
    AddTextCommand(StringBuilder doc, String text) { this.doc = doc; this.text = text; }
    public void execute() { doc.append(text); }
    public void undo() { doc.setLength(doc.length() - text.length()); }
}

class CommandInvoker {
    private final Deque<Command> history = new ArrayDeque<>();
    void run(Command cmd) { cmd.execute(); history.push(cmd); }
    void undoLast() { if (!history.isEmpty()) history.pop().undo(); }
}

Interview Gold Point

java.lang.Runnable is effectively a minimal Command with no undo. Java's ExecutorService and Spring's @Async/TaskExecutor both operate on Command-shaped objects: a request represented as a first-class object that can be scheduled independently of whoever created it.

Q20. Explain the Chain of Responsibility Pattern

ROI: ★★★★☆ Frequency: High

Chain of Responsibility passes a request along a chain of handlers until one handles it (or all decline), decoupling the sender from any specific receiver. Each handler decides independently whether to process the request and/or forward it to the next link. 

abstract class SupportHandler {
    protected SupportHandler next;
    SupportHandler setNext(SupportHandler next) { this.next = next; return next; }
    void handle(Ticket t) {
        if (canHandle(t)) resolve(t);
        else if (next != null) next.handle(t);
        else throw new IllegalStateException("Unhandled: " + t);
    }
    abstract boolean canHandle(Ticket t);
    abstract void resolve(Ticket t);
}

Interview Favorite

Servlet Filters — and Spring Security's filter chain / interceptor chain — are Chain of Responsibility in production: each filter decides to process the request, short-circuit it, or call chain.doFilter() to pass it along. This is one of the most commonly asked "name a real pattern in the framework you use daily" questions.

SECTION 7 - STATE, ITERATOR & MEDIATOR

Q21. Explain the State Pattern

ROI: ★★★★☆ Frequency: Medium-High

State lets an object change its behaviour when its internal state changes, by delegating state-specific behaviour to separate state objects rather than branching on an enum or flag everywhere that behaviour is needed.

Structurally it looks like Strategy — both wrap interchangeable behaviour behind a common interface — but the intent differs: Strategy is chosen by the client and stays fixed for a call, while State is switched internally by the context itself as it progresses through its own lifecycle (for example an order moving from NEW to PAID to SHIPPED to DELIVERED, each state permitting different transitions).

Interview Gold Point

The differentiator interviewers listen for: "Strategy is picked by the caller; State is switched internally by the object as it transitions through its own lifecycle." Order/workflow status fields are the textbook real-world use case, and State is a clean alternative to a giant switch on an OrderStatus enum scattered across the codebase.

Q22. Explain the Iterator Pattern

ROI: ★★★☆☆ Frequency: Medium

Iterator provides a way to access the elements of a collection sequentially without exposing its underlying representation. Java bakes this directly into the language: Iterable/Iterator is why the for-each loop works uniformly on any collection, regardless of whether it is backed by an array, a linked list, or a tree.

Interview Favorite

Every java.util.Collection is Iterable, and a for-each loop is literally syntactic sugar over iterator()/hasNext()/next(). Fail-fast behaviour (ConcurrentModificationException) is also an Iterator-pattern concern: mutating a collection while iterating invalidates the iterator's internal cursor.

Q23. Explain the Mediator Pattern

ROI: ★★★☆☆ Frequency: Low-Medium

Mediator centralizes how a set of objects communicate, so each object refers only to the mediator instead of directly to its peers — replacing a tangle of many-to-many references with a single hub-and-spoke structure.

Interview Gold Point

Mediator and Facade both reduce coupling by introducing an intermediary, but the intent differs: Facade simplifies a one-directional call into a subsystem, while Mediator coordinates bidirectional communication among a set of peer objects. Spring's ApplicationEventPublisher can act as a loose Mediator between otherwise-unrelated beans.

SECTION 8 - MEMENTO, VISITOR & INTERPRETER

Q24. Explain the Memento Pattern

ROI: ★★★☆☆ Frequency: Medium

Memento captures and externalizes an object's internal state so it can be restored later, without violating encapsulation — the object itself controls what goes into the memento and how it is restored; outside code only ever holds an opaque token.

Interview Gold Point

Command + Memento is a common combination for full undo/redo stacks: Command decides what and when to undo, Memento is how the prior state gets captured and restored. A JSON or serialized snapshot is often used as a pragmatic stand-in for a hand-rolled Memento class.

Q25. Explain the Visitor Pattern

ROI: ★★★★☆ Frequency: Medium-High

Visitor lets you define a new operation over a family of related classes without modifying those classes, by having each class accept() a visitor and double-dispatch to the matching visit() overload. It is the classic way to add operations to a fixed class hierarchy — for example an AST of Expr types — without touching every node class each time a new operation is needed.

Common Mistake

Visitor trades one flexibility for another: adding a new operation is easy (write one new visitor), but adding a new node type is hard, because every existing visitor must be updated. If a hierarchy grows node types often but operations rarely, Visitor is the wrong tool — that trade-off is exactly what modern Java's sealed types and pattern matching are used to sidestep (see Q42).

Q26. Explain the Interpreter Pattern

ROI: ★★☆☆☆ Frequency: Low

Interpreter defines a grammar for a simple language and represents each grammar rule as a class, so an expression tree can be built and evaluated by composing those classes. It is the least commonly asked GoF pattern in general interviews, but it explains how simple rule engines, Spring Expression Language (SpEL), and regex engines are structured internally.

Interview Gold Point

Do not over-invest here; a one-paragraph definition plus "SpEL and a cron-expression parser are Interpreter-shaped" is normally enough depth for this question. Building a full Interpreter for anything beyond a toy grammar is rare in application code — most teams reach for an existing parser or expression library instead.

SECTION 9 - NULL OBJECT & DATA-ACCESS PATTERNS

Q27. Explain the Null Object Pattern

ROI: ★★★★☆ Frequency: Medium-High

Null Object replaces a null reference with an object that implements the expected interface but does nothing (or something safely neutral), eliminating scattered if (x != null) checks at every call site. 

interface Logger { void log(String msg); }

class NullLogger implements Logger {
    public void log(String msg) { /* intentionally does nothing */ }
}

Interview Gold Point

Contrast this directly with Optional (see Q28): Null Object is for behaviour — an object you can still safely call methods on — while Optional is for values, a container you must explicitly unwrap. Both beat returning a raw null, and they solve overlapping but distinct problems.

Q28. Null Object vs Optional — Which Should You Use?

ROI: ★★★★☆ Frequency: Medium-High

java.util.Optional is the modern, standard-library-idiomatic tool for "this value may be absent," designed primarily as a return type that forces the caller to explicitly handle absence via map/orElse/ifPresent rather than risk a silent NullPointerException.

Null Object instead gives you a real, callable substitute object, useful when the "nothing" case still needs to behave like a normal collaborator across multiple method calls — for example a NullLogger that silently swallows every log call, so calling code never needs a null check before logging.

Optional Null Object
Represents an absent value Represents a do-nothing behaviour
Used as a return type Used as a field/collaborator
Caller must unwrap explicitly Caller calls it like any real object

Common Mistake

Do not store Optional in a field or use it as a method parameter — it is designed as a return-type-only tool. Using it as a field or parameter is a widely-flagged code smell.

Q29. Explain the Repository Pattern

ROI: ★★★★★ Frequency: Extremely High

Repository mediates between the domain/business layer and the data-mapping layer, presenting a collection-like interface for accessing domain objects — the caller thinks in terms of "a collection of Users," not SQL or persistence mechanics. 

interface UserRepository {
    Optional<User> findById(Long id);
    List<User> findByStatus(Status status);
    User save(User user);
}

Interview Gold Point

Spring Data JPA's JpaRepository/CrudRepository is a direct implementation of this pattern at the framework level: you declare an interface, and Spring generates the implementation at runtime via a dynamic proxy (tie this back to Q8's Proxy pattern). This chapter covers the pattern's shape; the JPA query-derivation mechanics themselves belong to the JPA/Hibernate chapter.

Q30. Explain the DAO Pattern (Data Access Object)

ROI: ★★★★☆ Frequency: High

DAO abstracts and encapsulates all access to a specific data source, exposing simple, persistence-shaped methods — insert, update, delete, findById — that hide the underlying JDBC/SQL calls from the rest of the application. 

interface UserDao {
    User findById(long id);
    void insert(User user);
}

class JdbcUserDao implements UserDao {
    private final JdbcTemplate jdbcTemplate;
    JdbcUserDao(JdbcTemplate jdbcTemplate) { this.jdbcTemplate = jdbcTemplate; }
    public User findById(long id) {
        return jdbcTemplate.queryForObject(
            "SELECT * FROM users WHERE id=?", new UserRowMapper(), id);
    }
    public void insert(User user) { /* ... */ }
}

Interview Favorite

DAO is older and lower-level than Repository: DAO exposes CRUD around one data source, while Repository speaks in domain/collection terms and can aggregate multiple data sources behind one clean abstraction. See Q31 for the precise contrast.

Q31. Repository vs DAO — What's the Real Difference?

ROI: ★★★★★ Frequency: High

Repository DAO
Domain/collection-oriented Persistence/technology-oriented
Can span multiple data sources Tied to one data source/table
Domain-Driven Design vocabulary Classic Java EE / persistence vocabulary

In practice, a typical Spring Boot codebase often uses the two terms interchangeably, because Spring Data literally names its interfaces *Repository while behaving very DAO-like for simple cases. The distinction matters most when the domain model does not map 1:1 onto tables — that is when a true Repository earns its keep by hiding joins and aggregation behind one clean domain-shaped method.

Interview Gold Point

A precise senior answer: "DAO is about how data is accessed; Repository is about how the domain thinks about its data." Interviewers asking this are checking whether you understand DDD-flavoured architecture, not just Spring Data annotations.

SECTION 10 - UNIT OF WORK, SPECIFICATION & DEPENDENCY INJECTION

Q32. Explain the Unit of Work Pattern

ROI: ★★★☆☆ Frequency: Medium

Unit of Work tracks a set of changes — inserts, updates, deletes — made during a business transaction and commits them together as one atomic batch, rather than writing to the database after every individual change. It coordinates multiple repository operations so they either all succeed or all roll back.

In a Spring/JPA application, the Hibernate persistence context (EntityManager/Session) already implements Unit of Work for you: it tracks dirty entities and flushes them together at transaction commit, which is exactly why @Transactional plus JPA's automatic dirty checking works without calling save() after every mutation.

Interview Gold Point

When asked "what pattern is JPA's persistence context," the strong answer is Unit of Work: it batches changes and defers writes until flush/commit, which is also why forgetting @Transactional on a method that mutates a managed entity can silently lose the change — no flush ever happens.

Q33. Explain the Specification Pattern

ROI: ★★★☆☆ Frequency: Low-Medium

Specification encapsulates a business rule or predicate as a reusable, combinable object, so that logic like "is this order eligible for free shipping" is a first-class object you can combine with and()/or()/not() rather than duplicating boolean logic across services. 

interface Specification<T> {
    boolean isSatisfiedBy(T candidate);
    default Specification<T> and(Specification<T> other) {
        return c -> this.isSatisfiedBy(c) && other.isSatisfiedBy(c);
    }
}

Interview Favorite

Spring Data JPA's org.springframework.data.jpa.domain.Specification<T> is a direct framework implementation of this pattern, letting you compose dynamic, type-safe WHERE clauses (Specification.where(spec1).and(spec2)) instead of building fragile string-concatenated JPQL.

Q34. Dependency Injection as a Named Design Pattern

ROI: ★★★★★ Frequency: Extremely High

This is distinct from Q13, which surveys where Spring itself uses patterns. Here the question is purely about DI as a classic pattern in its own right, independent of any framework. DI is a specialization of Inversion of Control: instead of a class constructing or looking up its own collaborators, they are supplied — "injected" — from outside, by a constructor, a setter, or directly onto a field.

Constructor Injection Setter Injection Field Injection
Fields can be final Fields must be mutable Fields must be mutable
Easiest to unit test (plain new) Testable, more ceremony Needs reflection/container in tests
Dependencies mandatory & visible Good for optional dependencies Dependencies hidden from API
Recommended default Use for genuinely optional deps Avoid

Constructor injection is generally preferred: it allows final fields, guarantees the object is never in a partially-wired state, and makes unit testing trivial (just call new with mocks). Setter injection suits genuinely optional dependencies that may be reconfigured after construction. Field injection is the most concise to write, but it hides dependencies from the class's public API, prevents final fields, and requires a DI container (or reflection) even for a plain unit test.

Interview Gold Point

This is the same conclusion the Spring Core chapter reaches framework-side; the point here is that it is true independent of Spring — it is a general OOP design principle (Dependency Inversion, one of the SOLID letters — see Q14) that Spring merely automates.

Q35. Dependency Injection vs Service Locator

ROI: ★★★★☆ Frequency: Medium-High

Service Locator is the alternative to DI for decoupling a class from concrete implementations: instead of receiving a dependency, the class actively asks a central registry for it, for example ServiceLocator.get(PaymentGateway.class).

The key downside of Service Locator is that dependencies become hidden inside method bodies instead of visible in the constructor signature — you must read the implementation to know what a class actually needs, and unit tests require the locator itself to be set up or mocked, not just the collaborator. DI wins because dependencies are declared, not discovered.

Common Mistake

JNDI lookups (new InitialContext().lookup(...)) in old Java EE code are a classic Service Locator smell candidates still bring up. The point of contrasting it is to demonstrate you understand why the industry moved to DI, not just that you can spell it.

SECTION 11 - ANTI-PATTERNS EVERY SENIOR ENGINEER SHOULD NAME

Q36. What Is a God Object (God Class)?

ROI: ★★★★★ Frequency: High

A God Object is a class that has accumulated far too many responsibilities — it knows about and controls large parts of the system, violating Single Responsibility so thoroughly that almost every change to the codebase touches it. Symptoms: thousands of lines, dozens of unrelated fields and methods, and a name like Manager, Helper, or Util that never says no to a new method.

Why it hurts: merge conflicts concentrate on it, tests become slow and brittle because mocking it requires stubbing unrelated concerns, and no single engineer can hold its behaviour in their head, so bugs hide in the interactions between its many responsibilities.

Interview Gold Point

The fix is almost always Extract Class / Extract Interface guided by Single Responsibility: split by responsibility — for example an OrderManager into OrderValidator, OrderPricer and OrderNotifier, each with one reason to change.

Q37. What Is an Anemic Domain Model?

ROI: ★★★★☆ Frequency: Medium-High

An Anemic Domain Model is a set of "domain" objects that are pure data holders — fields plus getters/setters, no behaviour — with all business logic instead living in separate service classes that operate on that data from the outside. It looks object-oriented but behaves like procedural code wearing OOP syntax: objects cannot protect their own invariants because they have no behaviour to enforce them.

Contrast with a Rich Domain Model, where an Order object exposes addLineItem()/cancel() and enforces its own invariants internally — for example "cannot cancel a shipped order" — rather than trusting every calling service to remember the rule.

Interview Gold Point

Anemic models are not automatically wrong — many CRUD-shaped Spring Boot services are perfectly fine anemic, because there is genuinely little behaviour to encapsulate. The senior distinction is recognizing when a domain has real business rules being duplicated across services (a smell) versus genuinely simple data (no smell at all).

Q38. What Is Spaghetti Code?

ROI: ★★★☆☆ Frequency: Medium

Spaghetti Code describes tangled, unstructured control flow — deeply nested conditionals, jumps between unrelated methods, and implicit dependencies between distant parts of the code — that make it practically impossible to trace what happens for a given input without stepping through a debugger.

Why it hurts: it defeats reasoning by inspection; adding a feature requires understanding far more of the surrounding code than should be necessary, and every fix risks an unrelated regression elsewhere in the tangle.

Common Mistake

Spaghetti code is often what a God Object's internals actually look like once you open it up — the two anti-patterns frequently coexist. Strategy, State and Chain of Responsibility, which replace giant conditional chains with polymorphism, are the standard pattern-based remedies.

Q39. What Is the Golden Hammer Anti-Pattern?

ROI: ★★★☆☆ Frequency: Medium

Golden Hammer — "if all you have is a hammer, everything looks like a nail" — is over-relying on one familiar tool, pattern, or technology for every problem, regardless of fit. Examples: wrapping every single class in a Factory and a Builder out of habit, or reaching for microservices and a message broker for a problem three well-organized classes would solve.

Why it hurts: it adds unnecessary complexity and cognitive overhead, and it signals that the choice was driven by familiarity and comfort rather than the problem's actual requirements.

Interview Gold Point

This anti-pattern is directly opposite to Q15's "when should you NOT use a pattern." Citing Golden Hammer by name when discussing over-engineering is a strong, concrete way to show you have internalized that lesson rather than just reciting YAGNI.

Q40. What Is Singleton Overuse?

ROI: ★★★★☆ Frequency: Medium-High

Singleton overuse is reaching for global, shared, mutable state via Singleton for things that should really be scoped, injected dependencies — for example a single static Cache, ConfigHolder, or Logger that every class reaches for directly instead of receiving through its constructor.

Why it hurts: it hides dependencies (a class secretly depends on global state that never appears in its constructor signature), makes unit testing painful because you cannot substitute a mock without resetting global state between tests, and, if the Singleton holds mutable fields, reintroduces the exact concurrency hazards Spring's stateless-singleton-bean discipline is designed to avoid.

Common Mistake

The fix is almost always to let a DI container manage the single instance as a bean and inject it, rather than hand-rolling a static getInstance() — you keep the "one instance" benefit while regaining testability and explicit dependencies. Recall Q2's caveat: a Spring singleton bean and a GoF Singleton are related but distinct ideas.

SECTION 12 - MODERN JAVA VS CLASSIC PATTERNS

Q41. How Do Lambdas Replace Classic Strategy and Command Boilerplate?

ROI: ★★★★★ Frequency: High

Prior to Java 8, Strategy and Command both required a named interface plus a concrete class (or a verbose anonymous inner class) per behaviour. Functional interfaces and lambdas let you pass the behaviour itself as a value with no class boilerplate at all — Runnable, Comparator, Function<T,R>, and any custom single-method interface become one-line Strategies. 

// Classic
interface PaymentStrategy { void pay(double amount); }
class PaypalStrategy implements PaymentStrategy {
    public void pay(double amount) { /* ... */ }
}
checkout(new PaypalStrategy(), 99.0);

// Modern
checkout(amount -> System.out.println("Paying via PayPal: " + amount), 99.0);

The pattern's structural intent — swap interchangeable behaviour at runtime — is unchanged; what disappears is the ceremony of a named class per behaviour. This is why interviewers now ask "would you still write a Strategy class here, or a lambda?" The mature answer: keep a real class when the behaviour carries meaningful state or needs to be independently unit-tested and reused by name; use a lambda for a small, inline, throwaway behaviour.

Interview Gold Point

Command benefits the same way: a Runnable or a Supplier<T> passed straight into ExecutorService.submit(...) is Command without a class. Do not over-claim, though — a lambda's "undo" story is weaker, since it is just a function, not an object you can introspect or serialize. Command-with-undo (Q19) still wants a real class when history or inspection matters.

Q42. How Do Sealed Types + Pattern Matching Replace What Visitor Used to Do?

ROI: ★★★★☆ Frequency: Medium-High

Visitor's whole reason to exist (Q25) is adding new operations over a fixed, closed family of types without an instanceof/cast chain and without touching every type each time. A sealed interface with pattern-matching switch (covered in depth in the Java Language Features chapter) gives the compiler that same "closed set of types" guarantee directly, and lets you write the operation as one exhaustive switch instead of a whole hierarchy of visit() overloads scattered across visitor classes. 

sealed interface Expr permits NumberExpr, AddExpr {}
// switch (expr) { case NumberExpr n -> ...; case AddExpr a -> ...; }
// compiler enforces exhaustiveness -- no default needed, no missing-case bugs

The trade-off flips relative to Visitor: adding a new operation is now just writing a new switch method (easy either way), but adding a new permitted type forces the compiler to flag every non-exhaustive switch across the codebase — usually exactly the safety net you want for a genuinely closed, rarely-changing hierarchy such as an AST, a small state machine, or a JSON value type.

Interview Gold Point

The synthesis answer interviewers want: "Visitor was a workaround for the language not having a closed, exhaustively-checked union type. Sealed types plus pattern matching give you that directly, so for new code targeting Java 17+, reach for sealed interfaces before reaching for Visitor." Do not re-derive the switch-pattern mechanics here — just make the connection.

SECTION 13 - APPLIED "WHICH PATTERN WOULD YOU USE HERE" SCENARIOS

Q43. Scenario: Add Cross-Cutting Logging and Retry to 20 Existing Service Methods Without Touching Their Code

ROI: ★★★★★ Frequency: High

This is the single most common scenario-style pattern question. The naive answer — "edit all 20 methods" — is wrong by construction, since the whole point of the prompt is "without touching them."

Answer: Decorator (wrap each service behind an object implementing the same interface that adds logging/retry around delegated calls), or at framework scale, Proxy via Spring AOP (an @Around advice matched by a pointcut over all 20 methods). Both share the same underlying mechanism — wrap and intercept — but differ in scale: hand-write a Decorator for a handful of classes you control directly; reach for AOP/proxies when the concern spans many beans and hand-wrapping each one is impractical.

Interview Gold Point

Naming both Decorator and Proxy/AOP, and explicitly saying why you would pick one over the other, is what distinguishes a senior answer from an "I know what Decorator is" answer.

Q44. Scenario: Support New Payment Methods Without Modifying Checkout Code

ROI: ★★★★★ Frequency: High

Answer: Strategy for the interchangeable pay() behaviour, paired with Factory — or Spring's List<PaymentStrategy>/Map<String, PaymentStrategy> auto-wiring, see Q10 — to select the right implementation at runtime. This satisfies Open/Closed directly: checkout() never changes, you only add a new PaymentStrategy implementation.

Interview Favorite

A strong answer explicitly says "Open/Closed" and "this is the DI-and-Strategy combination from Q10," tying the scenario back to both a SOLID principle and a specific earlier answer rather than describing it as if from scratch.

Q45. Scenario: Build Undo/Redo for a Document Editor

ROI: ★★★★☆ Frequency: Medium-High

Answer: Command — each edit action is an object with execute()/undo() — combined with Memento when an action's inverse cannot be cheaply computed and state must be snapshotted instead (see Q19, Q24). An invoker keeps a stack of executed commands and/or mementos to walk backward and forward through history.

Common Mistake

Candidates often name only Command and stop. The stronger answer recognizes that not every action is easily reversible by re-running inverse logic — for example "replace selection with pasted text" of unknown prior content — and for those, the Command stores a Memento of the prior state instead of trying to compute an undo.

Q46. Scenario: Traverse a Mixed Tree of Files and Folders Uniformly

ROI: ★★★★☆ Frequency: Medium

Answer: Composite — FileNode and Directory implement the same node interface so client code needs no instanceof checks — combined with Iterator to walk the tree without exposing whether it is implemented as a list, a recursive structure, or something else (see Q17, Q22).

Interview Gold Point

If the traversal also needs to apply different operations — compute size, print a listing, search — without modifying the node classes each time, that is the cue to add Visitor (Q25) on top. Composite + Iterator + Visitor is a very common three-pattern combination in tree-shaped domains.

Q47. Scenario: Notify Multiple Independent Systems When an Order's Status Changes

ROI: ★★★★★ Frequency: High

Answer: Observer — the Order (subject) publishes a status-changed event, and independent listeners (email service, analytics, inventory) subscribe without the Order knowing who or how many are listening (see Q11). In Spring this is literally ApplicationEventPublisher + @EventListener; at distributed scale the same shape becomes a Kafka topic with independent consumers — same pattern, different infrastructure.

Interview Gold Point

A senior answer flags the trade-off: in-process Observer (Spring events) is synchronous by default and fails together with the publisher unless made @Async, whereas an event broker decouples failure and timing at the cost of eventual consistency. The choice belongs to your architecture chapter, but naming the trade-off here shows you know the pattern's limits.

Q48. Scenario: Let Customers Configure Which Retry/Caching Policy Applies to Their Account at Runtime

ROI: ★★★★☆ Frequency: Medium

Answer: Strategy for the swappable policy itself, wrapped in a Decorator (or Proxy) that applies whichever policy is currently configured for that customer around the underlying call. The policy varies by data — the customer's tier — so it cannot be hardwired at compile time the way a single AOP pointcut usually is.

Common Mistake

Candidates sometimes reach straight for "just use AOP" here. The deciding detail is that AOP pointcuts are normally static — matched by class/method, decided at proxy-creation time — so per-customer runtime variation needs the policy itself to be an injected or looked-up Strategy object, with the Decorator/Proxy layer applying whichever one is selected for that request.

Q49. Scenario: Add a New Notification Channel to an Existing Notification System Every Few Months

ROI: ★★★★☆ Frequency: Medium

Answer: Factory Method to construct the right Notification implementation from a type string or enum (see Q3), with each channel implementing a common interface. Open/Closed again: adding a channel like WhatsApp means adding one new class and one new factory branch (or a registered supplier in a Map<String, Supplier<Notification>>), never editing existing channels.

Interview Gold Point

Mentioning the Map<String, Supplier<Notification>> registry variant — register once at startup, look up by key, no switch statement to edit at all — is a strong, concrete upgrade over the switch-based Factory shown in Q3, and it directly demonstrates Open/Closed in code rather than just naming the principle.

SECTION 14 - PATTERNS AS THEY SHOW UP INSIDE REAL FRAMEWORKS

Q50. Spring's BeanFactory: Factory + Singleton Combined

ROI: ★★★★★ Frequency: High

BeanFactory is simultaneously a Factory — it constructs objects on request so callers never call new for a managed type — and a Singleton registry, since by default it hands back the same shared instance for singleton-scoped beans. The two patterns are not in tension; they compose: the factory decides how to build something, and separately decides whether to cache and reuse that instance or build a fresh one each time.

Interview Gold Point

A precise way to say this: "the factory pattern answers how an object gets built; the scope (singleton vs prototype) answers how often. Spring's container composes both, which is why getBean() can return either a cached shared instance or a brand-new one depending on the bean's declared scope, through the exact same factory API."

Q51. JDBC's DriverManager as Factory Method

ROI: ★★★★☆ Frequency: Medium

DriverManager.getConnection(url) is a Factory Method: callers never construct a concrete Connection implementation directly; instead they hand the driver manager a URL, and it selects and returns the correct vendor-specific Connection implementation — PostgreSQL, MySQL, and so on — that happens to be registered on the classpath. The calling code stays coupled only to the java.sql.Connection interface.

Interview Favorite

This is a good "pattern in the JDK, not just Spring" example to keep in your back pocket, since interviewers sometimes explicitly ask for one that is not from Spring.

Q52. java.util.Collections' Unmodifiable Wrappers as Decorator

ROI: ★★★★☆ Frequency: Medium

Collections.unmodifiableList(list) — and its Set/Map siblings — wraps an existing collection in a new object implementing the same interface that delegates all read operations through and throws UnsupportedOperationException on any mutating call. It adds a capability (immutability enforcement) at runtime without altering the original list's class, which is exactly Decorator's definition (see Q7).

Common Mistake

The wrapper only protects against mutation through the wrapper reference itself — the original underlying list is still mutable, and changes made directly to it are visible through the "unmodifiable" view. This is a frequently-missed gotcha worth stating unprompted.

Q53. java.util.Comparator as a Living Strategy Example

ROI: ★★★★☆ Frequency: Medium

Comparator<T> is Strategy in its purest JDK form: it is a swappable algorithm — how to order two elements — passed into a context (Collections.sort, List.sort, Stream.sorted) that has no idea what comparison logic it is running. Since Java 8, Comparator.comparing(...).thenComparing(...) lets you compose Strategies fluently instead of writing a full class per ordering.

Interview Gold Point

Pointing at Comparator — rather than only business-flavoured examples — shows you recognize the pattern in code you use every day, reinforcing Q41's broader point about lambdas subsuming classic Strategy boilerplate.

SECTION 15 - CHOOSING & COMBINING PATTERNS

Q54. How Do You Decide Which Pattern to Use When You Don't Immediately Recognize the Problem?

ROI: ★★★★★ Frequency: High

Rather than pattern-matching from memory, work from the symptom back to the family. "Too many similar classes differing only in one behaviour" points to Strategy. "An object needs to look and act differently as it moves through stages" points to State. "Client code has a long if/instanceof chain over related types" points to polymorphism generally, and often to Visitor or a sealed-type switch specifically, depending on which side changes more often — types or operations (see Q42). "I need to add behaviour without touching existing classes" points to Decorator or Proxy, depending on whether the addition is about capability (Decorator) or access control/interception (Proxy).

Interview Gold Point

Say the reasoning out loud in the interview rather than jumping straight to a name — walking from symptom to pattern family, and naming the runner-up you considered and rejected (and why), demonstrates judgment, not just recall.

Q55. What Pattern Combinations Should You Expect to See Together in a Real Codebase?

ROI: ★★★★☆ Frequency: Medium-High

Combination Typical Use
Factory + Singleton BeanFactory-style registries
Composite + Iterator + Visitor Tree-shaped domains (files, ASTs, UI trees)
Command + Memento Undo/redo systems
Strategy + Decorator Runtime-configurable cross-cutting behaviour
Strategy + Dependency Injection Spring-style pluggable algorithms
Observer + Mediator Event-driven coordination hubs
Template Method + Strategy Fixed skeleton with one pluggable step

Interview Favorite

Patterns are rarely used in isolation in real systems; naming a combination unprompted, rather than only ever naming single patterns, is one of the clearest signals of hands-on experience versus textbook memorization.

Q56. Where Does This Chapter's Scope End and Architecture-Level Patterns Begin?

ROI: ★★★★☆ Frequency: Medium

Everything in this chapter is a class/object-level (GoF-style) design pattern — it governs how objects within a single process or application are structured and collaborate. Distributed, architecture-level patterns — Circuit Breaker, Saga, CQRS, API Gateway, Bulkhead, Strangler Fig — solve a different class of problem: coordinating state and failure across independent services over a network, and belong to the Microservices and System Design chapters, not here.

Interview Gold Point

A candidate who can draw this line clearly — "GoF patterns organize code within a process; architecture patterns organize services across a network" — signals seniority in itself. Conflating the two, for example calling Circuit Breaker a "GoF pattern," is a common tell of shallow preparation.

QUICK REVISION SHEET

  • Three families: Creational, Structural, Behavioural
  • Singleton → one instance; prefer enum or double-checked + volatile
  • Factory hides creation; Abstract Factory creates families
  • Builder → complex/immutable objects with many optional fields
  • Adapter converts interfaces; Decorator adds behaviour by wrapping
  • Proxy controls access — the heart of Spring AOP / @Transactional
  • Strategy → swap algorithms (great with DI); Observer → pub/sub events
  • Template Method → fixed skeleton, variable steps (JdbcTemplate)
  • SOLID: SRP, Open/Closed, Liskov, Interface Segregation, Dependency Inversion
  • Dependency Injection = Dependency Inversion in practice
  • Don't over-engineer — patterns are tools, not goals (YAGNI)
  • Bridge decouples abstraction from implementation; Composite treats parts and wholes uniformly; Flyweight shares immutable state to save memory
  • Command encapsulates a request as an object (undo/redo, queuing); Chain of Responsibility passes a request along handlers (Servlet filters)
  • State switches behaviour internally as an object's lifecycle progresses, unlike Strategy, which is chosen externally by the caller
  • Visitor adds operations to a fixed hierarchy without touching it; sealed types + pattern matching now cover much of that ground in modern Java
  • Repository = domain/collection-shaped data access; DAO = persistence/technology-shaped CRUD; Unit of Work batches changes into one atomic commit (JPA's persistence context)
  • Constructor injection > setter > field injection for testability and immutability — Dependency Injection is Dependency Inversion in practice, independent of Spring
  • Name anti-patterns by name: God Object, Anemic Domain Model, Spaghetti Code, Golden Hammer, Singleton overuse
  • Scenario questions: Decorator/Proxy for cross-cutting concerns, Strategy+Factory for pluggable behaviour, Command+Memento for undo/redo, Observer for fan-out notifications
  • GoF patterns organize code within a process; Circuit Breaker/Saga/CQRS are architecture-level patterns for distributed systems (out of this chapter's scope)
