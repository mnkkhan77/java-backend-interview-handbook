SECTION 1 - NOSQL FUNDAMENTALS

Q1. What Is NoSQL And Why Did It Emerge?

ROI: ★★★★★ Frequency: Very High

Short Answer

NoSQL ("Not Only SQL") is a family of databases that relax the rigid relational model - fixed schemas, normalized tables and joins - in favour of flexible data models that scale horizontally across commodity machines.

It emerged in the mid-2000s when companies like Google, Amazon and Facebook hit the limits of a single relational server. The pain points were concrete:

  • Scale - relational databases scale vertically (bigger box); web-scale workloads needed to scale horizontally across many cheap nodes.
  • Schema rigidity - rapidly evolving products did not want a migration for every new field.
  • Unstructured / semi-structured data - JSON-like documents, logs and graphs do not map cleanly to tables.
  • Throughput - high write volumes where the cost of joins and strict ACID became a bottleneck.

The key insight: you trade some of the relational guarantees (rich joins, strict consistency) for scalability and a data model that fits your access patterns.

Interview Gold Point

Never say "NoSQL is faster than SQL". It is not inherently faster - it is differently optimized. The correct framing is: NoSQL optimizes for horizontal scale and access-pattern-shaped data at the cost of joins and strong consistency. Saying that signals senior judgement.

Interview Favorite

Interviewers love "give me a real example for each". Redis for a session cache (see the caching content in the System Design chapter), MongoDB for a product catalog, Cassandra for IoT/event ingestion, Neo4j for a "people you may know" feature. Concrete examples beat definitions.

Q3. SQL vs NoSQL - When Do You Choose Which?

ROI: ★★★★★ Frequency: Extremely High

Short Answer

Choose based on data shape, access patterns, consistency needs and scale - not hype. Most real systems use both (polyglot persistence).

DimensionSQL (Relational)NoSQL
SchemaFixed, enforcedFlexible / dynamic
ScalingVertical (mostly)Horizontal (built-in)
JoinsFirst-classLimited / avoided by design
TransactionsStrong ACIDVaries (often eventual / limited)
Best whenComplex relationships, strong consistency, reportingHigh scale, evolving schema, access-pattern-shaped data

Pick SQL when you have well-defined relationships, need multi-table transactions and strong consistency - banking, orders, inventory ledgers. Pick NoSQL when the schema evolves quickly, you need to scale out, or the data is naturally a self-contained document or simple key lookup.

The relational contrast (normalization, joins, ACID) is covered in depth in the SQL & Database Design chapter - this chapter is the complement to it.

Common Mistake

Saying "use NoSQL because it scales" without naming the access pattern. NoSQL scales because it avoids joins and lets you shard - but only if your data model matches your queries. If you need ad-hoc joins and reporting, NoSQL becomes painful. Always tie the choice to the read/write pattern.

SECTION 2 - CONSISTENCY MODELS

Q4. What Is The Difference Between ACID And BASE?

ROI: ★★★★☆ Frequency: High

Short Answer

ACID is the relational guarantee model; BASE is the philosophy many distributed NoSQL systems adopt to favour availability and scale.

ACIDBASE
AtomicityBasically Available
ConsistencySoft state
IsolationEventually consistent
Durability(prioritizes availability over strict consistency)

ACID guarantees every transaction is all-or-nothing, leaves the database in a valid state, is isolated from other transactions and survives crashes. BASE accepts that in a large distributed system the data may be temporarily inconsistent ("soft state") but will converge ("eventually consistent"), in exchange for staying available and scalable.

Note: MongoDB is ACID-compliant at the single-document level by default, and supports multi-document ACID transactions since 4.0 (see Q16). So "NoSQL = no ACID" is outdated.

Interview Gold Point

The senior nuance: ACID vs BASE is a spectrum, not a binary. Modern databases let you tune it - in MongoDB you choose write concern and read preference per operation (Q16), effectively dialing where you sit between strong and eventual consistency.

Q5. How Does The CAP Theorem Apply To NoSQL?

ROI: ★★★★☆ Frequency: High

Short Answer

CAP states that during a network Partition a distributed system can guarantee only Consistency or Availability, not both. Since partitions are unavoidable in a distributed store, you are really choosing between CP and AP when the network splits.

  • CP (Consistency + Partition tolerance) - reject reads/writes that cannot be made consistent. MongoDB leans CP: during a partition the primary side stays consistent, the minority side cannot accept writes.
  • AP (Availability + Partition tolerance) - keep serving and reconcile later. Cassandra leans AP with tunable consistency.

CAP is covered in full in the Microservices chapter (it is central to the database-per-service pattern). For NoSQL the practical takeaway is: read the docs to learn where your store sits, because that decision is baked into its replication design.

Common Mistake

Treating CAP as "pick 2 of 3 always". Partition tolerance is not optional in a distributed system - you only sacrifice C or A while a partition is happening. The rest of the time you can have both. Stating it as a runtime trade-off, not a permanent one, is the senior answer.

Q6. What Is Eventual Consistency And What Are Its Trade-offs?

ROI: ★★★★☆ Frequency: High

Short Answer

Eventual consistency means that if no new writes occur, all replicas will eventually return the same value - but for a short window after a write, different replicas may return stale data.

Trade-offs:

  • Pro - high availability and low latency; reads can be served by any replica without coordination.
  • Con - stale reads. A user may update their profile and momentarily see the old value if they read from a lagging secondary.
  • Con - conflict resolution. Concurrent writes to different replicas need a strategy (last-write-wins, vector clocks, application merge).

You mitigate it where it matters: in MongoDB, read from the primary (read preference) or require majority write concern for the data that must be read-your-own-write consistent (e.g. payment status), while letting low-stakes data (e.g. view counts) stay eventually consistent.

Interview Favorite

The killer example: "Why is your Amazon order count sometimes off for a second?" - eventual consistency. Showing you know which data tolerates staleness (analytics, counters) versus which must be strongly consistent (balances, inventory) is exactly the judgement interviewers screen for.

SECTION 3 - MONGODB BASICS

Q7. What Are Documents, Collections And BSON In MongoDB?

ROI: ★★★★★ Frequency: Very High

Short Answer

These are MongoDB's core building blocks:

  • Document - a single record stored as a JSON-like structure with fields, nested objects and arrays. It is the unit of storage and roughly maps to a "row".
  • Collection - a group of documents, roughly maps to a "table". Collections are schema-flexible: documents in the same collection can have different fields.
  • BSON - "Binary JSON", the binary-encoded format MongoDB actually stores and transmits. It extends JSON with extra types (ObjectId, Date, Decimal128, Binary, 64-bit int) and is faster to traverse and more compact than text JSON.

Example document: 

{
  "_id": ObjectId("64f0a1c2e13b9a0012ab34cd"),
  "name": "Nasir Khan",
  "email": "nasir@growth-loop.io",
  "roles": ["ADMIN", "USER"],
  "address": {
    "city": "Bengaluru",
    "country": "IN"
  },
  "createdAt": ISODate("2026-06-16T10:00:00Z")
}

Notice the nested address object and the roles array embedded directly in the record - in a relational model these would be separate tables joined at query time.

Interview Gold Point

Be precise: JSON is what you read/write at the API level, BSON is what is stored on disk and on the wire. The driver converts between them. Mentioning that BSON adds typed values like Date and Decimal128 (not in plain JSON) signals you understand the storage layer.

Q8. What Is The _id Field In MongoDB?

ROI: ★★★★☆ Frequency: High

Short Answer

_id is the mandatory primary key of every MongoDB document. It is unique within a collection, automatically indexed, and immutable once set.

  • If you do not supply one, MongoDB generates an ObjectId - a 12-byte value containing a 4-byte timestamp, a 5-byte random value (machine/process) and a 3-byte incrementing counter.
  • Because the first 4 bytes are a timestamp, ObjectIds are roughly time-ordered - you can sort by _id to get near-insertion order and even extract the creation time.
  • You may use your own value (a UUID, an email, a natural key) as _id as long as it is unique.

Interview Favorite

The bonus point: an ObjectId is not sequential like an auto-increment integer. That is deliberate - sequential keys create a write hotspot when sharding (all inserts hit the same shard). ObjectId's randomness spreads writes. Connecting _id design to shard distribution is a strong senior signal.

SECTION 4 - DATA MODELING

Q10. Embedding vs Referencing - When Do You Denormalize?

ROI: ★★★★★ Frequency: Very High

Short Answer

This is the single most important MongoDB design decision. You either embed related data inside the parent document or reference it by storing its _id.

Embed WhenReference When
Data is read together (read locality)Data is read independently
One-to-few relationshipOne-to-many / many-to-many (unbounded)
Child has no life of its ownChild is shared or queried on its own
You want a single atomic read/writeDocument would grow unbounded (16MB limit)

Embed example (order + items together): 

{
  "_id": ObjectId("..."),
  "customer": "Nasir",
  "items": [
    { "sku": "A1", "qty": 2, "price": 19.99 },
    { "sku": "B7", "qty": 1, "price": 9.50 }
  ],
  "total": 49.48
}

Reference example (order points to a shared customer): 

{
  "_id": ObjectId("..."),
  "customerId": ObjectId("64ab..."),
  "items": [ /* ... */ ]
}

Denormalize (embed/duplicate) when reads dominate and the data is read together; normalize (reference) when data is large, shared, or grows without bound. Remember the hard limit: a single BSON document cannot exceed 16MB.

Interview Gold Point

The rule of thumb interviewers want: "embed for read performance, reference to avoid duplication and unbounded growth." Then mention the 16MB document cap as the hard constraint that forces referencing for true one-to-many relationships like comments on a viral post.

Q11. How Do You Model One-to-Many And Many-to-Many In MongoDB?

ROI: ★★★★☆ Frequency: High

Short Answer

One-to-many:

  • One-to-few (a person's few addresses) - embed as an array.
  • One-to-many (a blog post's comments) - embed if bounded, otherwise reference: store postId on each comment document in a separate collection.
  • One-to-squillions (server log lines for a host) - always reference from the "many" side; never embed an unbounded array in the parent.

Many-to-many (students ↔ courses): store an array of references on one or both sides, depending on which way you query most. 

// student document
{ "_id": 1, "name": "Ana", "courseIds": [101, 102] }

// course document
{ "_id": 101, "title": "Algorithms", "studentIds": [1, 5, 9] }

There is no join table. You hold arrays of _ids on the side you read from, and resolve them with a second query or $lookup in an aggregation.

Common Mistake

Embedding an unbounded "many" (e.g. all comments inside the post). It looks clean until the post goes viral, the document blows past 16MB, and every read drags megabytes over the wire. Match the cardinality to the strategy: few = embed, many = reference.

Q12. What Is The Schema-Design Mindset Shift From Relational?

ROI: ★★★★☆ Frequency: Medium

Short Answer

In relational design you normalize first (3NF), eliminate duplication, then write joins to assemble data. In MongoDB you do the opposite: you start from the queries and shape documents so the data you read together lives together.

  • Relational: "What is the cleanest normalized structure?" Schema first, queries follow.
  • MongoDB: "What are my read/write patterns?" Queries first, schema follows.
  • Duplication is acceptable (and sometimes desirable) if it saves a join on a hot read path - you trade storage and write complexity for read speed.
  • Schema is enforced by the application (or optional JSON Schema validation), not the engine.

This is why the SQL & Database Design chapter teaches normalization as the goal, while here denormalization is a deliberate, justified tool.

Interview Favorite

Say it crisply: "Relational optimizes for storage and integrity; MongoDB optimizes for the query." Add that you still validate at the application layer so flexibility does not become chaos - that balance is what separates a senior from someone who just dumps unstructured blobs.

SECTION 5 - QUERYING & PERFORMANCE

Q13. What Do Basic CRUD And Queries Look Like In MongoDB?

ROI: ★★★★☆ Frequency: High

Short Answer

MongoDB queries are expressed as documents - the filter is itself a JSON-like object. 

// Create
db.users.insertOne({ name: "Ana", age: 30, city: "Pune" })

// Read - find all users in Pune older than 25
db.users.find({ city: "Pune", age: { $gt: 25 } })

// Read - projection (only name + email), sorted, limited
db.users.find({ city: "Pune" }, { name: 1, email: 1, _id: 0 })
        .sort({ age: -1 })
        .limit(10)

// Update
db.users.updateOne(
  { name: "Ana" },
  { $set: { city: "Mumbai" }, $inc: { age: 1 } }
)

// Delete
db.users.deleteOne({ name: "Ana" })

Operators are prefixed with $: comparison ($gt, $lt, $in), logical ($and, $or), and update operators ($set, $inc, $push). The projection document selects fields (1 = include, 0 = exclude).

Interview Gold Point

A frequent gotcha: updateOne with $set updates only the listed fields, but passing a whole document without $set replaces the entire document (losing other fields). Knowing the difference between modify and replace semantics shows real hands-on experience.

Q14. How Do Indexes Work In MongoDB And Why Do They Matter?

ROI: ★★★★★ Frequency: Very High

Short Answer

Like in relational databases, indexes are B-tree structures that let MongoDB locate documents without scanning the whole collection. Without an index, a query does a COLLSCAN (full collection scan) - fine for small data, fatal at scale.

  • Single-field index - on one field: db.users.createIndex({ email: 1 }).
  • Compound index - on multiple fields, order matters: db.users.createIndex({ city: 1, age: -1 }). It supports queries on city, or city + age, but not age alone (the "prefix rule").
  • Other types - multikey (on array fields), text, geospatial, hashed (for sharding), TTL (auto-expire documents).
  • _id is always indexed automatically.

You diagnose query performance with explain(): an IXSCAN stage means the index is used; a COLLSCAN means it is not. 

db.users.find({ city: "Pune", age: { $gt: 25 } }).explain("executionStats")

Common Mistake

Forgetting the compound-index prefix rule and over-indexing. Indexes speed reads but slow writes and consume RAM - every write must update every index. The senior answer: index to match your actual query patterns (verified with explain()), not "just in case". This mirrors the indexing discussion in the SQL & Database Design chapter.

Q15. What Is The Aggregation Pipeline?

ROI: ★★★★★ Frequency: Very High

Short Answer

The aggregation pipeline is MongoDB's framework for data processing and analytics - the equivalent of SQL's GROUP BY, joins and transformations. Documents flow through an ordered array of stages, each transforming the stream and passing it to the next.

Common stages: $match (filter, like WHERE), $group (aggregate), $sort, $project (reshape, like SELECT), $lookup (left join to another collection), $unwind (flatten arrays), $limit.

Example - total revenue per city for completed orders: 

db.orders.aggregate([
  { $match: { status: "COMPLETED" } },
  { $group: {
      _id: "$city",
      totalRevenue: { $sum: "$total" },
      orderCount: { $sum: 1 }
  }},
  { $sort: { totalRevenue: -1 } },
  { $limit: 5 }
])

This is the SQL equivalent of SELECT city, SUM(total), COUNT(*) FROM orders WHERE status='COMPLETED' GROUP BY city ORDER BY 2 DESC LIMIT 5.

Interview Gold Point

Performance tip worth dropping: put $match and $sort as early as possible so they can use indexes and shrink the dataset before expensive stages like $group or $lookup. Stage ordering is to aggregation what query plans are to SQL.

SECTION 6 - SCALING & SPRING

Q16. Explain Replica Sets, Sharding, Transactions, Write/Read Concern And Spring Data MongoDB.

ROI: ★★★★★ Frequency: Very High

Short Answer

This bundle covers how MongoDB achieves high availability, scale and durability, plus how you use it from Spring.

Replica Set (high availability) - a group of mongod nodes holding the same data: one primary (takes all writes) and one or more secondaries (replicate the primary's oplog). If the primary fails, an automatic election promotes a secondary. This gives failover and redundancy. Secondaries can also serve reads (eventual consistency).

Sharding (horizontal scale) - partitions a collection across multiple shards by a shard key, so data and load spread across machines. Each shard is itself usually a replica set. Used when one server cannot hold the data or handle the write throughput. Choosing a good shard key (high cardinality, even distribution, matches query pattern) is critical to avoid hotspots.

Write concern & read preference - how you tune consistency vs latency:

  • Write concern - how many nodes must acknowledge a write. w:1 = primary only (fast, less durable); w:"majority" = majority of nodes (durable, survives failover).
  • Read preference - where reads go. primary (strong/fresh) vs secondaryPreferred (scale reads, may be stale).

Multi-document transactions - MongoDB always had atomic single-document writes, but multi-document ACID transactions arrived in 4.0 (2018) for replica sets (and 4.2 for sharded clusters). This was a big deal because it removed the last "but it's not ACID" objection - you can now update several documents atomically when you genuinely need it. The guidance is still to model so you rarely need them.

Spring Data MongoDB - gives you a repository abstraction just like Spring Data JPA (covered in the Spring Data JPA / Hibernate chapter). You extend MongoRepository and derived query methods are generated for you: 

@Document(collection = "users")
public class User {
    @Id
    private String id;          // maps to _id
    private String name;
    private String city;
    private int age;
    // getters / setters
}

public interface UserRepository extends MongoRepository<User, String> {
    List<User> findByCity(String city);
    List<User> findByCityAndAgeGreaterThan(String city, int age);
}

@Service
public class UserService {
    private final UserRepository repo;
    public UserService(UserRepository repo) { this.repo = repo; }

    public List<User> usersInCity(String city) {
        return repo.findByCity(city);   // generates the Mongo query
    }
}

For anything beyond derived queries you use MongoTemplate (criteria queries, aggregations, bulk ops).

Breadth (mention these for range): Redis is an in-memory key-value store, ideal for caching, sessions and rate limiting - the caching strategy details (cache-aside, TTL, eviction) are in the System Design chapter. Cassandra is a wide-column store built for massive write-heavy, multi-datacenter workloads with tunable (AP-leaning) consistency. Naming the right tool for each job shows polyglot-persistence maturity.

Interview Gold Point

Tie it together: "Replica sets give me availability, sharding gives me scale, write concern and read preference let me dial consistency per operation, and transactions are there for the rare cases my document model can't make atomic." That one sentence demonstrates you understand the whole operational picture, not just the API.

SECTION 7 - WIDE-COLUMN, KEY-VALUE & GRAPH DATABASES DEEP DIVE

Q17. How Do You Design Partition Keys vs Clustering Keys In Cassandra?

ROI: ★★★★☆ Frequency: Medium-High

Short Answer

Cassandra's primary key splits into two very different jobs. The partition key decides which node(s) own the data - it is hashed to a token, and the token ring determines placement. The clustering key decides the sort order of rows within a partition - it has nothing to do with distribution, only with how rows are physically ordered on disk inside that one partition. 

CREATE TABLE sensor_readings (
    sensor_id   text,
    reading_time timestamp,
    temperature double,
    PRIMARY KEY ((sensor_id), reading_time)
) WITH CLUSTERING ORDER BY (reading_time DESC);

Here sensor_id is the partition key - all readings for one sensor land on the same node(s), and reading_time is the clustering key - readings are stored pre-sorted, newest first, so "give me the last 100 readings for sensor X" is a cheap sequential read.

Cassandra is query-first, more strictly than MongoDB even: it has no ad-hoc secondary filtering (without ALLOW FILTERING, which is an anti-pattern at scale), so every query must supply the full partition key. This forces you to design one table per query shape, sometimes duplicating the same data into several tables keyed differently.

Common Mistake

Picking a partition key with too little cardinality (e.g. just country) creates a "wide partition" - one node ends up holding a huge, slow-to-compact slice of data. If a natural key is too coarse, add a bucketing component, e.g. PRIMARY KEY ((sensor_id, day), reading_time), to keep partitions bounded in size.

Q18. What Is Tunable Consistency In Cassandra (Quorum Reads/Writes)?

ROI: ★★★★☆ Frequency: Medium-High

Short Answer

Cassandra lets you choose a consistency level per query, independent of the replication factor (RF) configured on the keyspace. Common levels: ONE, QUORUM (majority of replicas: floor(RF/2)+1), LOCAL_QUORUM (quorum within the local datacenter only), and ALL.

The classic strong-consistency guarantee is: if R + W > RF (R = replicas contacted on read, W = replicas contacted on write), then every read is guaranteed to see the most recent write, because the read and write sets must overlap on at least one up-to-date replica. With RF=3, QUORUM writes (W=2) plus QUORUM reads (R=2) gives 2+2=4 > 3, so you get strong consistency without waiting on every single replica.

In a multi-datacenter deployment, LOCAL_QUORUM is the practical default - it avoids the latency of waiting on a quorum that spans a cross-continent link, at the cost of only guaranteeing consistency within that DC.

Interview Gold Point

This is the wide-column analogue of MongoDB's write concern / read preference (Q16 and Q41) - both let you dial where a specific operation sits between "fast and eventually consistent" and "slow and strongly consistent". Drawing that parallel across two different databases is a strong senior signal.

Q19. Why Are Cassandra Writes Cheap But Reads And Deletes (Tombstones) Tricky?

ROI: ★★★★☆ Frequency: Medium-High

Short Answer

Cassandra's storage engine is an LSM-tree (log-structured merge-tree). A write is appended to a commit log (for durability) and to an in-memory memtable - there is no read-before-write, no in-place update, no random disk seek. That is what makes writes extremely cheap and fast, even at huge sustained volume: it is a sequential append, full stop.

Memtables periodically flush to immutable files on disk called SSTables. Over time, one logical row's data can be spread across many SSTables (written at different times). A read has to check the memtable and potentially several SSTables, merging what it finds - this is read amplification, mitigated by bloom filters (skip SSTables that can't contain the key) and background compaction (merging SSTables together).

Deletes make this worse before it gets better: a delete does not remove data in place (it can't - SSTables are immutable), it writes a tombstone marker recording "this data is deleted as of time T". Reads must still scan past tombstones until compaction physically purges them (after gc_grace_seconds, default 10 days, to give time for the delete to replicate everywhere before it is permanently forgotten). A delete-heavy workload can accumulate so many tombstones that range scans start failing outright ("tombstone overwhelm").

Interview Gold Point

The one-liner interviewers want: "in Cassandra, a delete is actually a special kind of write, and it makes future reads more expensive until compaction cleans it up." That single sentence shows you understand the LSM-tree trade-off, not just the CQL syntax.

Q20. When Does Redis Make Sense As A Primary Database, Not Just A Cache?

ROI: ★★★★☆ Frequency: Medium-High

Short Answer

Redis is usually introduced as "the cache", but it is a full key-value database with persistence (RDB snapshots and/or an AOF - append-only file - log), replication, and a clustered mode (hash-slot based sharding) - and it supports far more than strings: Lists, Sets, Sorted Sets, Hashes, Streams, HyperLogLog and Bitmaps, plus modules like RedisJSON and RediSearch.

Good primary-store use cases: real-time leaderboards (sorted sets give O(log N) ranked inserts and range queries for free), rate limiters and counters, distributed locks (RedLock), lightweight pub/sub or Streams-based event processing, and session state where Redis is the source of truth rather than a cache in front of something else.

The caveat that keeps it from being a general-purpose primary database: your data set needs to fit comfortably in RAM (or you pay a lot for it), and its durability model (AOF fsync policy trade-offs) is weaker than a WAL-backed disk store like MongoDB or Postgres. Financial ledgers and anything needing rich ad-hoc queries still belong in an ACID store.

Common Mistake

Assuming "Redis = cache" is a permanent architectural fact rather than the most common use case. If the access pattern is simple (key/structure-based) and latency is paramount, Redis-as-database is a legitimate, common production choice - the caching material in the System Design chapter covers the cache-in-front-of-a-database pattern specifically; this question is about Redis owning the data outright.

Q21. When Does A Graph Database (Neo4j) Genuinely Beat Relational/Document?

ROI: ★★★★☆ Frequency: Medium

Short Answer

A graph database earns its place when the core value of the feature is deep, multi-hop traversal where the number of hops is unbounded or unknown ahead of time - fraud rings connected through shared devices/cards/addresses three or four hops out, "people you may know" (friends of friends, not already connected), recommendation paths, knowledge graphs.

In SQL, an N-hop traversal needs N self-joins (or a recursive CTE), and cost grows badly as both N and the data volume grow. In Neo4j, relationships are stored as physical pointers directly on the node - "index-free adjacency" - so walking to a neighbor is a pointer hop whose cost depends on the size of the local neighborhood you explore, not on the size of the whole database.

The nuance interviewers are checking for: most relationships in a normal application (an order belongs to a customer) are one hop, and a plain foreign key/reference (relational or Mongo) handles that perfectly well - reaching for a graph database "because the data has relationships" is a common overreach. Reach for it specifically when unbounded-depth traversal is the primary access pattern, not an occasional nice-to-have.

Interview Gold Point

MongoDB's $graphLookup aggregation stage (Q45) gives you a lightweight recursive traversal inside a document database for moderate-depth hierarchies (org charts, comment threads) - mentioning that you'd reach for that before standing up an entire separate graph database, unless the traversal is genuinely the product's core feature, shows calibrated judgement rather than reflexively naming the "correct-sounding" database for every relationship.

Q22. Wide-Column vs Document - How Do You Choose Between Two NoSQL Types That Both Seem To Fit?

ROI: ★★★☆☆ Frequency: Medium

Short Answer

Both families can store large volumes of semi-structured records, but they diverge sharply on query flexibility versus write scale.

DimensionWide-Column (Cassandra)Document (MongoDB)
Query flexibilityLow - one table per query shape, modeled up frontHigh - secondary indexes, ad-hoc queries, aggregation framework
Write scaleExtremely high (LSM-tree, linear scale-out, multi-DC)High, but joins/aggregations cost more under load
NestingFlat rows, dynamic columnsRich nested objects/arrays
Best fitTime-series, IoT ingestion, messaging - known, few query shapesCatalogs, content, evolving query patterns

Choose Cassandra when the workload is extremely write-heavy, needs to scale linearly across many nodes and datacenters, and the query patterns are known, few, and stable - you are willing to denormalize the same data into several purpose-built tables. Choose MongoDB when query patterns are varied or still evolving, documents are naturally nested, and you need secondary indexes or aggregations without pre-modeling every access path as a dedicated table.

Interview Favorite

A concrete framing that lands well: "if I can enumerate every query my product needs today, Cassandra's query-first modeling is a strength, not a limitation. If my product team is still figuring out what the UI needs to show, MongoDB's flexibility to add a secondary index or an aggregation later is worth more than Cassandra's raw write throughput."

SECTION 8 - MONGODB INDEXING DEEP DIVE

Q23. What Is The ESR Rule For Compound Index Field Order?

ROI: ★★★★★ Frequency: Very High

Short Answer

ESR stands for Equality, Sort, Range - the recommended order for fields in a compound index, matched against how your query actually filters/sorts/ranges.

  • Equality fields first - fields matched with an exact value. These let MongoDB seek directly to the relevant slice of the index.
  • Sort fields next - if the query sorts on a field, putting it next in the index means MongoDB can return results already in that order, avoiding an expensive in-memory sort.
  • Range fields last - fields matched with $gt/$lt/$in etc. Once the index starts ranging over a field, the ordering guarantee for any fields after it is lost, so ranges must come after equality and sort fields, not before.

Example: filter { status: "COMPLETED" }, sort by { createdAt: -1 }, range on { total: { $gt: 100 } } → the ideal index is: 

db.orders.createIndex({ status: 1, createdAt: -1, total: 1 })

Get the order wrong (say, range before sort) and MongoDB falls back to an in-memory sort, which is capped at 32MB by default and is a very common production performance cliff once a collection grows.

Interview Gold Point

ESR is the MongoDB-specific version of a general truth about B-tree indexes: exact-match filters narrow the range fastest, sort order should come from the index whenever possible, and open-ended ranges should be applied last since they can't preserve ordering for subsequent fields. Framing it that way shows you understand the mechanism, not just a mnemonic.

Q24. What Is A Covered Query?

ROI: ★★★★☆ Frequency: High

Short Answer

A query is covered when every field it needs - the filter, the projection, and any sort - is present in the index itself, so MongoDB can answer entirely from the index without ever fetching the actual document. That means no FETCH stage in the query plan, just an IXSCAN. 

db.users.createIndex({ city: 1, name: 1 })

db.users.find(
  { city: "Pune" },
  { city: 1, name: 1, _id: 0 }
)

Because the query only asks for city and name (and explicitly excludes _id, which is not part of this index), the index alone can satisfy it. In explain("executionStats"), a covered query shows totalDocsExamined: 0 - that field is the tell-tale sign.

Interview Gold Point

Leaving _id in the projection by accident is the single most common reason a query that "should" be covered isn't - _id is always indexed on its own, but that doesn't make it part of this compound index, so it forces a document fetch. Always exclude it explicitly when chasing a covered query.

Q25. What Are Text Indexes In MongoDB?

ROI: ★★★☆☆ Frequency: Medium

Short Answer

A text index is a special index type built for full-text search across string fields - it supports $text queries with stemming, stop-word removal, and relevance scoring via { $meta: "textScore" }. 

db.articles.createIndex({ title: "text", body: "text" })

db.articles.find(
  { $text: { $search: "mongodb aggregation" } },
  { score: { $meta: "textScore" } }
).sort({ score: { $meta: "textScore" } })

A collection can have only one text index (though it can be compound across several fields, with per-field weights to bias relevance). Text indexes are fine for basic in-app search, but they lack fuzzy matching, faceting, and the relevance tuning of a dedicated search engine or MongoDB Atlas Search (Q49).

Q26. What Are TTL Indexes And When Do You Use Them?

ROI: ★★★★☆ Frequency: High

Short Answer

A TTL (time-to-live) index is a single-field index on a Date field with an expireAfterSeconds option - a background process periodically sweeps and deletes documents once they age past that threshold, with no application-level cron job required. 

db.sessions.createIndex(
  { lastActiveAt: 1 },
  { expireAfterSeconds: 1800 }   // 30 minutes
)

Typical uses: session data, email-verification/reset tokens, short-lived cache-like collections, and rolling log retention. Two things to keep in mind: the sweep runs on a background cycle (roughly every 60 seconds), so deletion is not instant, and TTL only works on a top-level Date field (or an array of Date values, in which case it expires once the earliest date passes).

Interview Gold Point

TTL indexes are the built-in alternative to writing your own archiving/expiry job (Q53) - use them for true "this data becomes worthless after time X" cases, and use archiving instead when the data must be retained somewhere, just not in the hot collection.

Q27. What Is The Difference Between Partial And Sparse Indexes?

ROI: ★★★☆☆ Frequency: Medium

Short Answer

Both shrink an index by excluding some documents, but they differ in flexibility.

  • Sparse index - excludes documents that do not have the indexed field at all. Saves space when a field is rare, but its interaction with sorts and certain queries (which expect every document to be represented) can be surprising.
  • Partial index - indexes only documents matching an arbitrary filter expression, e.g. only ACTIVE orders:
db.orders.createIndex(
  { customerId: 1, createdAt: -1 },
  { partialFilterExpression: { status: "ACTIVE" } }
)

Partial indexes are a strict superset of what sparse indexes can do (a "field exists" filter is just one possible partialFilterExpression), so modern guidance is to prefer partial indexes over sparse ones in almost every case - they are smaller, keep writes faster, and can express any predicate, not just field existence.

Q28. What Is A Wildcard Index And When Is It Useful?

ROI: ★★★☆☆ Frequency: Medium

Short Answer

A wildcard index indexes all fields (or all fields under a given subtree path) without you knowing their names in advance: 

db.products.createIndex({ "attributes.$**": 1 })

This is aimed at highly variable, user-defined schemas - for example a product catalog where each category has wildly different attribute fields (screen size for phones, thread count for bedsheets) and you cannot predict which attribute a customer will filter on next.

The trade-off: a wildcard index is larger than a targeted one, does not support covered queries, and has weaker compound-query behavior. Whenever you do know the shape of a common query, a specific compound index (following the ESR rule, Q23) will always outperform a wildcard index for that query.

Q29. How Do You Read A MongoDB explain() Plan In Depth?

ROI: ★★★★★ Frequency: Very High

Short Answer

explain("executionStats") returns a tree with three broad sections:

  • queryPlanner - the winningPlan (the stage tree MongoDB actually executed) and rejectedPlans (other index candidates that were considered and scored lower).
  • executionStats - nReturned, totalKeysExamined, totalDocsExamined, executionTimeMillis, and per-stage breakdowns.
  • serverInfo - version/host metadata, rarely interesting for tuning.

Key ratios to check: totalKeysExamined close to nReturned means the index is precise (little wasted scanning); totalDocsExamined: 0 with an IXSCAN means the query is covered (Q24); a top-level COLLSCAN stage means no usable index existed at all; a SORT stage (as opposed to getting sorted order for free from an IXSCAN) means an expensive in-memory sort happened.

Interview Gold Point

Senior habit worth stating out loud: always check rejectedPlans, not just winningPlan. When you add a new index and the query still isn't using it, rejectedPlans tells you it existed and was considered but scored worse - usually because an existing index already matched the query "well enough" from the planner's cost model, which points you toward dropping the redundant old index rather than assuming the new one is broken.

SECTION 9 - MONGODB SCHEMA DESIGN PATTERNS

Q30. What Is The Bucket Pattern And When Do You Use It?

ROI: ★★★★☆ Frequency: High

Short Answer

The Bucket pattern groups many small, related time-series-style readings into one document per time "bucket" (per hour, per sensor, per day) instead of writing one document per individual data point. 

{
  "sensorId": "S-42",
  "hour": ISODate("2026-09-03T10:00:00Z"),
  "readings": [
    { "ts": ISODate("2026-09-03T10:00:03Z"), "value": 21.4 },
    { "ts": ISODate("2026-09-03T10:00:08Z"), "value": 21.6 }
  ],
  "count": 2,
  "sum": 43.0
}

This drastically cuts the number of documents (and index entries) compared to one document per reading, reducing both storage overhead and index size, while keeping range-by-time queries cheap since a bucket already groups data by time window. Precomputed count/sum fields (tying into the Computed pattern, Q32) let you answer averages without re-scanning every reading.

Interview Gold Point

Modern MongoDB (5.0+) automates this exact idea with native time-series collections - mentioning that the Bucket pattern is what time-series collections implement under the hood for you shows you understand the mechanism, not just the feature name.

Q31. What Is The Subset Pattern?

ROI: ★★★☆☆ Frequency: Medium

Short Answer

When an embedded array would grow very large - thousands of reviews on a popular product - but the common-path read only ever needs the most recent or most relevant few, the Subset pattern keeps only that small subset embedded in the parent document, and moves the full collection to a separate, independently-queried collection referenced by the parent's _id.

This keeps the hot, frequently-loaded parent document small and fast, while still supporting a "see all reviews" page as a secondary, less-frequent query against the full reviews collection - the best of both embedding (fast common read) and referencing (unbounded growth handled safely).

Q32. What Is The Computed Pattern?

ROI: ★★★★☆ Frequency: High

Short Answer

The Computed pattern precomputes and stores an expensive-to-calculate value at write time, instead of recalculating it via an aggregation on every read. 

// on every completed order:
db.dailyStats.updateOne(
  { day: "2026-09-03" },
  { $inc: { totalRevenue: order.total, orderCount: 1 } },
  { upsert: true }
)

A dashboard then reads the small dailyStats document directly instead of running a $group aggregation over the entire (potentially huge) orders collection on every page load.

The trade-off is consistency risk: the computed field can drift if some update path forgets to maintain it. Mitigate with a periodic reconciliation job that recomputes and corrects the field from source data, or by driving the increment from the same write path that creates the source record (ideally in the same transaction, if the invariant is critical enough to justify one, tying back to Q34).

Q33. What Are Polymorphic Collections?

ROI: ★★★☆☆ Frequency: Medium

Short Answer

A polymorphic collection stores documents of different "shapes" or types together, when they are queried and displayed together, using a discriminator field to distinguish them. 

{ "_id": 1, "userId": 9, "type": "COMMENT", "postId": 55, "text": "Nice!", "createdAt": ... }
{ "_id": 2, "userId": 9, "type": "LIKE",    "postId": 55,                  "createdAt": ... }
{ "_id": 3, "userId": 9, "type": "FOLLOW",  "targetUserId": 4,             "createdAt": ... }

All three share common fields (userId, createdAt) but carry different extra fields depending on type. A single query ("all notifications for this user, newest first") fetches all of them in one pass with one index - no UNION across separate tables the way a relational schema would need.

In Spring Data MongoDB, model this with a common base class and @TypeAlias-annotated subclasses so the driver deserializes each document into the right POJO based on the discriminator field automatically.

Common Mistake

Letting a polymorphic collection turn into an ungoverned dumping ground with no shared contract. Keep the common fields consistent and indexed, and consider $jsonSchema validation with a oneOf-style rule per type so the flexibility doesn't drift into chaos (Q52's schema-governance pitfall).

SECTION 10 - TRANSACTIONS, CHANGE STREAMS & SHARDING DEEP DIVE

Q34. What Actually Happens Inside A Multi-Document Transaction, And What Does It Cost?

ROI: ★★★★★ Frequency: Very High

Short Answer

A multi-document transaction takes locks across every document/collection it touches, buffers its writes, and - if the collections span multiple shards - coordinates a two-phase commit across those shards. On WiredTiger it also holds a consistent snapshot of the data for the duration of the transaction, so other operations don't see partial results.

That mechanism is not free: transactions increase latency, hold resources (and locks) longer than an equivalent single-document write, and on a sharded cluster add real cross-shard coordination overhead - meaningfully more expensive than a single-shard write. MongoDB's own guidance is to keep transactions short-lived (a 60-second default limit) and low in operation count.

When you genuinely need one: an invariant spans two separate documents that cannot reasonably be merged into one - e.g. debiting one account document and crediting another, or decrementing inventory in one collection while creating an order in another, where "half-done" would corrupt business state.

When to avoid one: redesign the schema first. If the invariant-holding fields can be embedded into a single document (Q10), MongoDB's built-in single-document atomicity already gives you the guarantee for free, and you never pay the transaction tax at all. A senior answer treats transactions as an escape hatch, not the default tool.

Interview Gold Point

The strongest answer to "when do you use Mongo transactions" is not a list of APIs - it's "as rarely as good schema design allows, and only when the invariant truly cannot be pushed into a single document."

Q35. What Are Change Streams And How Do They Relate To CDC?

ROI: ★★★★☆ Frequency: High

Short Answer

Change streams let an application subscribe to real-time data changes - inserts, updates, deletes, replaces - on a collection, a database, or an entire deployment, without polling. They are built on top of the same oplog that replica sets already use for replication. 

const changeStream = db.orders.watch(
  [ { $match: { operationType: { $in: ["insert", "update"] } } } ],
  { fullDocument: "updateLookup" }
);
changeStream.on("change", (event) => {
  console.log(event.operationType, event.documentKey, event.fullDocument);
});

Each change event carries the operation type and the affected document's key; adding fullDocument: "updateLookup" also fetches the current full document on updates. Typical uses: cache invalidation, triggering downstream workflows, real-time UI updates, and feeding changes into a message broker.

This is conceptually MongoDB's native flavor of Change Data Capture - the source-side primitive. If those changes need to flow reliably at scale into Kafka or other downstream systems, that pipeline (connectors, delivery guarantees, ordering) is the territory the Event-Driven Architecture / CDC chapter owns; change streams are the tap you open, not the whole plumbing.

Q36. What Criteria Determine A Good Shard Key, And What Is The Monotonic-Key Pitfall?

ROI: ★★★★★ Frequency: Very High

Short Answer

A good shard key needs three things: high cardinality (many distinct values, so data can actually spread across many shards), even distribution of both data volume and load (a field can be high-cardinality yet still skewed - e.g. "country" has many values, but 80% of traffic is one country), and it should match your dominant query pattern so most queries can be routed to one shard instead of scattered to all of them.

The classic pitfall is choosing a monotonically increasing field - an auto-incrementing id, or a plain insertion timestamp - as the shard key. Every new insert then has the current highest value, which always routes to the same shard (the one owning the current top of the range), creating a permanent hot shard and defeating the entire point of sharding. This is the same underlying problem as the ObjectId hotspot from Q8, just one layer up - at the collection-sharding level instead of the single-node index level. 

// mitigation: hash the otherwise-monotonic field
db.events.createIndex({ createdAt: "hashed" })
db.adminCommand({ shardCollection: "app.events", key: { createdAt: "hashed" } })

Alternative mitigations: a hashed shard key (spreads writes evenly at the cost of losing range-query locality) or a compound shard key combining a coarse, evenly-distributed bucket with the monotonic field.

Q37. What Roles Do Chunk Splitting/Balancing And mongos Play In A Sharded Cluster?

ROI: ★★★★☆ Frequency: High

Short Answer

A sharded collection's key range is divided into chunks. When a chunk grows past a size threshold, MongoDB automatically splits it into two smaller chunks. A background balancer process then migrates chunks between shards so data (and, in recent versions, actual disk usage) stays roughly even across the cluster.

mongos is the stateless query router applications actually talk to - it is not a data-holding node itself. It consults the config servers for the current chunk-to-shard mapping, routes a query to the specific shard(s) that can answer it (or, if the query doesn't include the shard key, to every shard - a "scatter-gather" query, which is why matching the shard key to your dominant query pattern, Q36, matters so much), and merges the results back into a single response. Application code never talks to an individual shard directly.

Common Mistake

Forgetting that a query without the shard key becomes scatter-gather across every shard - it still works, but throws away the entire performance benefit of sharding for that query. If a query pattern regularly needs to scatter-gather, that's a signal the shard key choice (or the schema) needs revisiting, not that you should just accept the cost.

SECTION 11 - CONSISTENCY TUNING & OPERATIONS

Q38. How Do You Combine Write Concern And Read Preference For A Specific Consistency-vs-Availability Trade-off?

ROI: ★★★★★ Frequency: Very High

Short Answer

Write concern and read preference are per-operation (or per-collection) knobs, not one global setting - the senior move is choosing the combination that fits what that specific piece of data actually needs.

CombinationBehaviourUse For
w: "majority" + read preference primary (or readConcern "majority")Strongest consistency, higher latency, less read scalabilityPayments, inventory holds, anything that must never be stale
w: 1 + read preference secondaryPreferredMaximum throughput/availability, eventual consistency, some rollback risk on failoverView counts, activity feeds, analytics
w: "majority" write, then immediate readConcern "majority" read"Read your own write" - guarantees you see what you just wroteUser updates their profile and the UI re-reads it immediately

The mistake to avoid is treating this as one deployment-wide decision. A single application legitimately uses strong settings for its order-total field and relaxed settings for its "last seen" timestamp on the very same document, because the two fields have entirely different staleness tolerances.

Q39. How Does Connection Pooling Work In Spring Data MongoDB?

ROI: ★★★☆☆ Frequency: Medium

Short Answer

The underlying MongoClient maintains a connection pool (default max pool size of 100) shared across the whole application; Spring Data MongoDB's repositories and MongoTemplate both just ride on that one client and its pool. 

spring.data.mongodb.uri=mongodb://host:27017/app?maxPoolSize=200&minPoolSize=10&maxIdleTimeMS=60000

Under load, pool exhaustion shows up as "waiting for a connection" timeouts rather than database-level errors - tune maxPoolSize/minPoolSize/maxConnectionIdleTime relative to how many app instances you run and how many total connections your MongoDB deployment allows. This is the exact same category of concern as sizing a HikariCP pool for JDBC - the mental model transfers directly from the Spring Data JPA material.

Q40. How Do You Use The Database Profiler To Find Slow Queries?

ROI: ★★★★☆ Frequency: High

Short Answer

The profiler records operations exceeding a slow-op threshold into the system.profile collection. It has three levels: 0 (off), 1 (log only slow ops), 2 (log every operation - useful for local debugging, far too heavy for production). 

db.setProfilingLevel(1, { slowms: 50 })

db.system.profile.find({ millis: { $gt: 100 } })
      .sort({ ts: -1 })
      .limit(20)

In production, level 1 with a sane slowms threshold (plus mongod's own slow-query log line, which gives you the same information without the extra write overhead level 2 adds to every operation) is the practical default. On MongoDB Atlas, the Performance Advisor and built-in Profiler UI surface this without needing to query system.profile by hand.

Q41. What Are The Most Common MongoDB Schema/Query Anti-Patterns?

ROI: ★★★★★ Frequency: Very High

Short Answer

A short list interviewers listen for:

  • Unbounded arrays - embedding comments/log entries/audit trail directly with no cap, causing constant document growth and eventually hitting the 16MB limit (Q10, Q11).
  • Deeply nested documents (5+ levels) - hard to query, index, or update; positional update operators ($, $[]) get awkward past one or two levels of nesting.
  • Missing indexes on high-cardinality query fields - the classic surprise COLLSCAN in production; always validate new query paths with explain() (Q29) before shipping.
  • Case-sensitivity assumptions - MongoDB string comparisons are case-sensitive and byte-order by default. A "case-insensitive email lookup" needs a collation or a normalized lowercase duplicate field, not a bare $regex with the i flag, which cannot use a standard index efficiently.

Interview Gold Point

All four of these anti-patterns share one root cause: designing the document shape without first pinning down the actual read/write pattern (Q12). Every fix above is really just "go back and match the schema to the query" in a different guise.

SECTION 12 - REAL-WORLD MIGRATION & DECISION-MAKING

Q42. A Relational Schema Is Struggling Under A Specific Access Pattern - Walk Through Whether/How You'd Move It To MongoDB.

ROI: ★★★★★ Frequency: Very High

Short Answer

This is a synthesis question, and the strongest answers do not start with "yes, migrate" - they start by interrogating whether migration is even the right fix.

  • 1. Name the actual pain, with numbers. Is it a schema-rigidity problem (constant migrations for new fields), a read-latency problem (a page load needs a 6-table join), a write-throughput problem (can't keep up with insert volume), or - very common - a data-modeling mistake that a targeted index or a schema change could fix within SQL first?
  • 2. Design the target document shape around the dominant read path - using embed-vs-reference (Q10) and the schema patterns from this chapter (Bucket, Subset, Computed, Q30-Q32), not a literal one-table-to-one-collection port.
  • 3. Plan the cutover carefully - dual-write to both stores, backfill the rest with an ETL/migration script, verify with shadow reads comparing old vs new results, then flip reads over gradually, keeping the old system as a fallback for a defined window.
  • 4. Decide what stays relational. Financial ledgers, anything needing genuine multi-table joins or ad-hoc reporting, usually stays in SQL. Real migrations almost always end up polyglot (Q44), not "replace SQL wholesale".

Interview Gold Point

The signal interviewers are screening for is restraint: a senior engineer's first instinct is to ask "is this actually a NoSQL problem, or a modeling/indexing problem I could fix where the data already lives?" before reaching for a migration.

Q43. What Are The Most Common Pitfalls When Migrating To MongoDB?

ROI: ★★★★☆ Frequency: High

Short Answer

The recurring mistakes when teams move to MongoDB without adjusting their mental model:

  • Porting the normalized shape 1:1 - keeping the same multi-collection layout and doing app-level joins for everything ends up slower than the original SQL, because you lost the relational query planner's join optimization without gaining Mongo's read-locality benefit.
  • No schema governance - flexible schema is a feature until nobody agrees what a document should look like. Use $jsonSchema validators or a versioned convention (Q50) so the collection doesn't drift into inconsistent shapes.
  • Ignoring the 16MB document limit and array-growth limits when directly porting a parent/children table pair into an embedded array without checking cardinality.
  • Assuming transactions "just work" the same way - multi-document ACID transactions exist (Q34) but are meant to be the exception in a well-modeled schema, not the default pattern carried over from relational habits.
Q44. What Does A Realistic Polyglot Persistence Architecture Look Like?

ROI: ★★★★☆ Frequency: High

Short Answer

A concrete example - an e-commerce platform: Postgres for orders/payments/inventory (multi-table joins, strong ACID, reporting), MongoDB for the product catalog (variable attributes per category, read-heavy, denormalized for the product page), Redis for session/cart state and rate limiting, Atlas Search/Elasticsearch for product search, and Cassandra or a time-series store for clickstream/event analytics.

The architectural discipline this requires: each service/bounded context owns its own datastore - the same database-per-service principle from the Microservices chapter - and cross-store consistency is handled through events or change streams/CDC (Q35) rather than attempting a distributed transaction across fundamentally different database technologies.

Interview Gold Point

Naming the right store for each concern, and explicitly calling out that consistency between them is eventual and event-driven (not a cross-database transaction), is what separates "I've heard of five databases" from "I've actually designed a system with five databases".

SECTION 13 - ADVANCED AGGREGATION & QUERYING

Q45. What Do $facet, $bucket And $graphLookup Do In The Aggregation Pipeline?

ROI: ★★★★☆ Frequency: High

Short Answer

Three stages that go beyond the basic $match/$group/$sort toolkit from Q15:

  • $facet - runs several independent aggregation sub-pipelines against the same input in a single pass. A product listing page can get paginated results, category facet counts, and a price histogram in one round trip instead of three separate queries.
  • $bucket / $bucketAuto - groups documents into ranges (e.g. price bands $0-50, $50-100...), like a histogram, in one stage instead of a chain of $match+$group per bucket.
  • $graphLookup - performs a recursive traversal within an aggregation, e.g. "find every report under this manager, however many levels deep". It is a lightweight, in-database version of what a graph database does, useful for moderate-depth hierarchical data already living in MongoDB.
db.employees.aggregate([
  { $match: { name: "Nasir" } },
  { $graphLookup: {
      from: "employees",
      startWith: "$_id",
      connectFromField: "_id",
      connectToField: "managerId",
      as: "allReports"
  }}
])

A genuinely graph-heavy workload (unbounded depth, high fan-out, relationship-first product) still belongs in a dedicated graph database (Q21) - $graphLookup is for the common case of a moderately deep tree already sitting in a document collection.

Q46. What Is The Difference Between $out And $merge, And Why Use Them?

ROI: ★★★☆☆ Frequency: Medium

Short Answer

Both write an aggregation's output into a collection instead of returning it to the client, but they differ in how.

  • $out - replaces the entire target collection with the pipeline's output. Simple, but always a full recompute.
  • $merge - can insert, update, or merge into an existing collection, so you can incrementally refresh a materialized view rather than recomputing everything from scratch every run.
db.rawEvents.aggregate([
  { $match: { day: "2026-09-03" } },
  { $group: { _id: "$city", total: { $sum: "$amount" } } },
  { $merge: { into: "dailyStats", whenMatched: "merge", whenNotMatched: "insert" } }
])

A common pattern: a nightly or hourly aggregation of raw event data into a pre-aggregated dailyStats collection using $merge (tying directly into the Computed pattern, Q32), so dashboards query the small pre-aggregated collection instead of scanning millions of raw events on every page load.

Q47. What Are The Rules And Gotchas Of Multikey Indexes On Arrays?

ROI: ★★★☆☆ Frequency: Medium

Short Answer

Any index on a field holding an array automatically becomes a multikey index - MongoDB creates one index entry per array element, so find({ tags: "sale" }) can match any document whose tags array contains that value.

The key restriction: you cannot create a compound index with more than one array field, because MongoDB would need to index every combination of elements across both arrays - a cross-product it disallows outright.

A separate correctness gotcha: to match multiple conditions against the same array element (not different elements each satisfying one condition), use $elemMatch: 

// WRONG - can match two different elements, one per condition
db.products.find({ "variants.size": "L", "variants.color": "red" })

// RIGHT - both conditions must hold on the same array element
db.products.find({
  variants: { $elemMatch: { size: "L", color: "red" } }
})

Common Mistake

Forgetting $elemMatch and getting silent false positives - a product with a red XL variant and a separate blue L variant will incorrectly match a naive { "variants.size": "L", "variants.color": "red" } query. This is one of the most common production data bugs in array-heavy MongoDB schemas.

Q48. When Does $lookup Become A Performance Problem, And What's The Fix?

ROI: ★★★★☆ Frequency: High

Short Answer

$lookup is MongoDB's left-outer-join equivalent, and it is not free - depending on the shape of the query it can be a per-document lookup into the foreign collection, which reintroduces exactly the join cost the document model was meant to avoid, once it's on a hot, high-QPS read path.

The idiomatic MongoDB answer to "my $lookup is slow" is usually not "tune the $lookup" - it's "should this data have been embedded or denormalized in the first place" (Q10). Reserve $lookup for reporting, analytics pipelines, and admin views where the query volume is low and flexibility matters more than raw speed, not for the request path a customer waits on.

SECTION 14 - DATA MODELING EDGE CASES

Q50. How Do You Handle Schema Evolution/Versioning In MongoDB?

ROI: ★★★★☆ Frequency: High

Short Answer

MongoDB doesn't enforce a schema at the engine level (unless you add $jsonSchema validation), so document shape drifts as the application evolves - old-shape and new-shape documents will coexist in the same collection.

  • Add a schemaVersion field to documents and branch application logic (or a migration script) based on it.
  • Write "tolerant reader" code that defaults missing fields rather than assuming every document matches the latest shape.
  • Run background migration jobs that lazily upgrade documents on read or write, instead of a risky big-bang migration across a huge collection.

Contrast with relational: a SQL ALTER TABLE mostly forces one consistent shape immediately (or as an online DDL operation). MongoDB's flexibility means the migration can be gradual - but that same flexibility is exactly what causes the "no schema governance" pitfall (Q43) if nobody enforces discipline around it.

Q51. How Do You Model Hierarchical/Tree Data In MongoDB?

ROI: ★★★★☆ Frequency: High

Short Answer

Four common strategies, each trading off write cost against query flexibility:

Parent referencesEach node's parent _idCheap writesDescendant/subtree queries need recursion ($graphLookup, Q45)

Q52. How Do You Model Multi-Tenancy In MongoDB?

ROI: ★★★★☆ Frequency: High

Short Answer

Three approaches, in increasing order of isolation and operational cost:

  • Shared collection + tenantId field - simplest and most efficient (one deployment, one connection pool), but every single query must filter by tenantId - enforce this at the data-access layer, and put tenantId first in every compound index. A missed filter here is a cross-tenant data leak, not just a bug.
  • Database-per-tenant / collection-per-tenant - strongest isolation, a tenant can be resized/backed-up/deleted independently, easier to meet strict compliance requirements, but operational overhead multiplies with tenant count and cross-tenant analytics gets harder.
  • Hybrid - shared collections for small tenants, dedicated databases for large/enterprise tenants paying for isolation - a common real-world compromise.

Interview Gold Point

The senior framing: multi-tenancy is a spectrum from "cheap and shared" to "isolated and expensive", and production systems often run both ends simultaneously segmented by tenant tier, not a single one-size-fits-all choice.

Q53. How Do You Implement Soft Deletes And Archiving In MongoDB?

ROI: ★★★☆☆ Frequency: Medium

Short Answer

Soft delete - add a deletedAt/isDeleted field instead of physically removing the document, keeping audit/referential history intact. Every query must exclude deleted documents - enforce this with a partial index ({ partialFilterExpression: { deletedAt: { $exists: false } } }, Q27) and/or a default filter in the repository layer, not by hoping every call site remembers.

Archiving - periodically move old/inactive documents out of the hot collection into a cold _archive collection (or a cheaper storage tier), keeping the primary collection - and its indexes - small and fast, with a fallback query path to the archive collection for the rare historical lookup.

A TTL index (Q26) is effectively the automatic version of a hard delete after a retention window; combine it with archiving first if the data must be retained somewhere, just not in the hot collection.

SECTION 15 - OPERATIONS, MONITORING & SECURITY

Q54. How Does Backup/Restore And Point-In-Time Recovery Work In MongoDB?

ROI: ★★★☆☆ Frequency: Medium

Short Answer

mongodump/mongorestore give portable logical backups, but are slower and resource-heavy on large data sets. Filesystem or volume snapshots on a replica set give fast physical backups, consistent as long as journaling is enabled when the snapshot is taken.

Point-in-time recovery restores a base snapshot, then replays the oplog (the same replication log secondaries consume) up to a specific timestamp - letting you recover to "just before the bad deploy ran a bad update", not merely to the last nightly backup.

MongoDB Atlas automates continuous backups with point-in-time restore built in; self-managed clusters need to build this snapshot-plus-oplog-replay pipeline themselves.

Q55. What Are The MongoDB-Specific Security Basics?

ROI: ★★★☆☆ Frequency: Medium

Short Answer

Authentication (SCRAM by default; x.509 or LDAP/Kerberos in Enterprise), role-based authorization (built-in roles like read, readWrite, dbAdmin, or custom roles scoped to specific actions/collections), TLS for data in transit, encryption at rest (the WiredTiger encrypted storage engine, or filesystem/volume-level encryption), and field-level (client-side) encryption for specific sensitive fields that must stay encrypted even from database administrators.

The general security practices - least privilege, secrets management, network segmentation - are covered in depth in the Security chapter. The Mongo-specific piece is mainly operational discipline: never run with auth disabled outside local dev, and scope roles per service (a reporting service gets a read-only role, never the application's read-write credentials).

Q56. Why Does MongoDB Capacity Planning Center On The "Working Set"?

ROI: ★★★★☆ Frequency: High

Short Answer

MongoDB's WiredTiger storage engine performs best when the working set - the actively-used indexes and documents - fits in RAM. Once it doesn't, cache misses turn into disk reads and performance falls off a cliff rather than degrading gradually.

Capacity planning therefore means sizing RAM to roughly cover your hot indexes plus hot data - not your total data set size - and watching cache eviction/page-fault metrics as leading indicators, so you catch the trend before you actually hit the cliff, not after.

This is also why over-indexing (Q14, Q41) is a real cost, not just a write-latency nuisance: every additional index competes for the exact same RAM budget as your hot data, so an unnecessary index can push your genuinely important data out of cache.

Q57. What Do You Monitor In MongoDB, And With What Tools?

ROI: ★★★★☆ Frequency: High

Short Answer

mongostat gives a real-time per-second view of ops/sec (insert/query/update/delete), connections, memory, and replication lag - effectively "top" for MongoDB. mongotop breaks down read/write time per collection, useful for spotting a runaway collection before it becomes a full incident.

Key metrics worth alerting on: replication lag (secondaries falling behind means stale reads and elevated failover risk), connection count approaching the pool/server limit, cache eviction rate, queued reads/writes (ticket exhaustion under WiredTiger's concurrency control), and slow-query counts surfaced by the profiler (Q40).

On Atlas, most of this is a built-in dashboard (the Real-Time Performance Panel plus Performance Advisor's missing-index suggestions). Self-managed deployments typically wire mongostat/mongotop output and the profiler into Prometheus/Grafana, following the same observability practices covered in the Observability chapter.

SECTION 16 - SPRING DATA MONGODB IN DEPTH

Q58. When Do You Use MongoTemplate Instead Of MongoRepository?

ROI: ★★★★☆ Frequency: High

Short Answer

MongoRepository (derived query methods, just like Spring Data JPA) is enough for straightforward CRUD and simple filters - fast to write, low ceremony. MongoTemplate gives you the full Criteria API, the aggregation framework (Aggregation.newAggregation(...)), bulk operations, and direct access to update operators ($inc, $push) that don't map cleanly onto a derived method name. 

@Repository
public class OrderStatsRepository {
    private final MongoTemplate template;
    public OrderStatsRepository(MongoTemplate template) { this.template = template; }

    public List<RevenueByCity> revenueByCity() {
        Aggregation agg = Aggregation.newAggregation(
            Aggregation.match(Criteria.where("status").is("COMPLETED")),
            Aggregation.group("city").sum("total").as("totalRevenue"),
            Aggregation.sort(Sort.Direction.DESC, "totalRevenue")
        );
        return template.aggregate(agg, "orders", RevenueByCity.class).getMappedResults();
    }
}

Practical pattern: use repositories for the majority of simple lookups, and inject MongoTemplate (or a custom repository fragment, Q59) for anything involving aggregation, dynamic/optional filters, or bulk writes.

Q59. How Do You Write Custom Repository Implementations And Use @Query?

ROI: ★★★☆☆ Frequency: Medium

Short Answer

@Query lets you write a raw Mongo-shaped query directly on a repository method when a derived method name would be unreadable or simply impossible - for example a deeply nested field condition: 

public interface UserRepository extends MongoRepository<User, String> {
    @Query("{ 'city': ?0, 'age': { $gt: ?1 } }")
    List<User> findAdultsInCity(String city, int minAge);
}

For genuinely custom logic - dynamic Criteria built from optional filters, direct MongoTemplate access - implement a custom fragment interface and its implementation, then have the main repository extend both MongoRepository and that fragment: 

public interface UserRepositoryCustom {
    List<User> searchDynamic(UserSearchCriteria criteria);
}

public class UserRepositoryCustomImpl implements UserRepositoryCustom {
    private final MongoTemplate template;
    // build Criteria dynamically based on which fields in criteria are non-null
}

public interface UserRepository extends MongoRepository<User, String>, UserRepositoryCustom { }

Spring Data stitches the custom fragment into the repository proxy automatically - the same composition pattern used for custom Spring Data JPA repositories.

Q60. How Do Auditing And Optimistic Locking Work In Spring Data MongoDB?

ROI: ★★★★☆ Frequency: High

Short Answer

@EnableMongoAuditing plus @CreatedDate/@LastModifiedDate (and @CreatedBy/@LastModifiedBy with an AuditorAware bean) auto-populate timestamp and author fields on save - mirroring how JPA auditing works. 

@Document(collection = "orders")
public class Order {
    @Id private String id;
    @CreatedDate private Instant createdAt;
    @LastModifiedDate private Instant updatedAt;
    @Version private Long version;
    // ...
}

@Version on a numeric field gives optimistic locking: MongoRepository.save() includes the current version in its update filter and increments it on success, so a concurrent save() based on a stale in-memory version fails with an OptimisticLockingFailureException instead of silently overwriting a concurrent update - the exact same concept as JPA's @Version, applied to documents instead of rows.

Q61. How Do You Test MongoDB Code With Testcontainers vs Embedded Mongo?

ROI: ★★★★☆ Frequency: High

Short Answer

Testcontainers' MongoDBContainer spins up a real, disposable mongod in Docker for integration tests - the preferred approach today, because it behaves exactly like production MongoDB: correct aggregation behavior, real index behavior, and (if configured as a single-node replica set) real transaction support. 

@Testcontainers
class OrderRepositoryIT {
    @Container
    static MongoDBContainer mongo = new MongoDBContainer("mongo:7.0");

    @DynamicPropertySource
    static void mongoProperties(DynamicPropertyRegistry registry) {
        registry.add("spring.data.mongodb.uri", mongo::getReplicaSetUrl);
    }
    // ...
}

The older Flapdoodle "embedded Mongo" approach downloads and runs a real mongod binary without Docker - useful when Docker isn't available in CI, but it has historically lagged behind newer MongoDB versions and makes replica-set/transaction testing awkward.

The gotcha that trips teams up the first time they add transaction-touching tests: transactions require replica-set mode, so a plain single-node mongod (the default in some setups) will reject them - the test container (or embedded instance) needs to be started in single-node replica-set mode specifically.

Q62. How Do You Stream Large Result Sets From Spring Data MongoDB Without Running Out Of Memory?

ROI: ★★★☆☆ Frequency: Medium

Short Answer

A raw find() returns a cursor that fetches results in batches (the driver negotiates a batch size, commonly 101 documents for the first batch, then configurable) rather than loading the whole result set into memory at once. However, a Spring Data repository method that returns List<T> still materializes everything into memory - it just drains the cursor for you. 

public interface EventRepository extends MongoRepository<Event, String> {
    Stream<Event> findByDayGreaterThanEqual(LocalDate day);
}

try (Stream<Event> events = eventRepository.findByDayGreaterThanEqual(cutoff)) {
    events.forEach(this::process);
}

For genuinely large result sets, use a Stream<T> return type (or Query.stream() with MongoTemplate) inside a try-with-resources block, so the underlying cursor stays open only as long as you are actively consuming it, and elements are processed one at a time instead of all being held in memory.

This mirrors the identical "don't materialize a huge List" concern from JDBC/JPA streaming (Spring Data JPA chapter) - cursor-based batching is what makes it safe to iterate millions of documents without an OutOfMemoryError, as long as the calling code actually streams rather than collects into a list.

  • NoSQL - flexible schema + horizontal scale, trades joins and strict consistency.

  • Eventual consistency - replicas converge; tolerate it for counters, not for balances.
  • Document / Collection / BSON - record / table-equivalent / binary JSON stored on disk.
  • _id - mandatory, unique, indexed PK; ObjectId is time-ordered + random (good for sharding).
  • Embed vs reference - embed for read locality & one-to-few; reference for unbounded / shared (16MB cap).
  • Mindset shift - relational models the data; MongoDB models the query.
  • Indexes - single & compound; prefix rule; verify with explain() (IXSCAN good, COLLSCAN bad).
  • Aggregation - staged pipeline ($match → $group → $sort); push $match early.
  • Replica set - primary + secondaries, automatic failover = HA.
  • Sharding - partition by shard key for horizontal scale; pick a high-cardinality key.
  • Write concern / read preference - per-operation knobs between strong and eventual consistency.
  • Transactions - multi-document ACID since Mongo 4.0; single-document was always atomic.
  • Spring Data MongoDB - MongoRepository + derived queries; MongoTemplate for advanced ops.
  • Breadth - Redis = caching (System Design chapter), Cassandra = wide-column write-heavy.
  • Cassandra - partition key picks the node, clustering key sorts within it; model one table per query.
  • Tunable consistency - R + W > RF gives strong reads in Cassandra; LOCAL_QUORUM for multi-DC.
  • Cassandra writes/deletes - LSM-tree makes writes cheap (append-only); deletes are tombstones, purged only at compaction.
  • Redis as primary DB - rich data structures + persistence/replication, but the data set must fit in RAM.
  • Graph DB (Neo4j) - wins when traversal depth is unbounded/unknown (index-free adjacency); overkill for one-hop relationships.
  • ESR rule - order compound indexes Equality, Sort, Range.
  • Covered query - index alone answers it; totalDocsExamined: 0 in explain().
  • Partial index beats sparse index in modern MongoDB; wildcard index for unpredictable field names; TTL index for auto-expiry.
  • Schema patterns - Bucket (time-series), Subset (large arrays), Computed (pre-aggregated), Polymorphic (discriminator field).
  • Multi-doc transactions - real cost (locks, cross-shard 2PC); prefer redesigning the schema to avoid needing them.
  • Change streams - real-time watch() on the oplog; the source-side primitive for CDC, not a replacement for the pipeline.
  • Shard key - high cardinality, matches the query pattern, avoid monotonic keys (hot shard); mongos routes via chunk metadata, balancer keeps chunks even.
  • Migration decisions - name the specific pain before moving off SQL; real systems usually end up polyglot, not "replace SQL wholesale".
  • Advanced aggregation - $facet (multi-view), $bucket (histogram), $graphLookup (recursive traversal), $merge (incremental materialized view).
  • $lookup is not free - reserve it for reporting/admin views, not high-QPS request paths; denormalize instead where it matters.
  • Multi-tenancy - shared collection + tenantId (indexed first) vs DB-per-tenant for isolation; soft delete + partial index over hard delete.
  • MongoDB ops - working set must fit RAM; mongostat/mongotop/profiler for visibility; oplog replay for point-in-time recovery.
