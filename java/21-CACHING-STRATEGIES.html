21 - CACHING STRATEGIES INTERVIEW HANDBOOK

Almost every backend system that survives real traffic ends up leaning on a cache somewhere, and interviewers know it. Caching questions are popular precisely because they look simple on the surface ("just put it in Redis") but reward candidates who can reason about the trade-offs: what happens on a miss, what happens when the cached value is wrong, what happens when ten thousand requests miss at the exact same millisecond. A senior engineer is expected to go past "I added @Cacheable" and speak fluently about eviction policies, consistency, and failure modes. For a Senior role you should be able to confidently discuss: * Why caching helps (latency, load, cost) and what it costs you in return (staleness, complexity) * The core patterns: cache-aside, write-through, write-behind, write-around * How to invalidate a cache correctly, not just how to populate one * When an in-process cache (Caffeine) is enough and when you need a distributed one (Redis) * Caffeine's admission policy and Redis's data structures and persistence model * Cache stampede and how production systems avoid it * Spring's caching abstraction and how to wire multi-level (L1/L2) caching * Consistency trade-offs in distributed caches, eviction policy choice, and what to monitor This chapter treats caching as a system design tool, not a Spring annotation. Interviewers usually follow up by asking you to design a cache for a specific hot path (a product page, a user session, a leaderboard) and then attack your design with "what if this key gets read a million times a second the moment it expires?" or "what if two instances disagree on the value?" Being ready for those follow-ups is the real goal of this chapter.

SECTION 1 - FUNDAMENTALS

Q1. Why Caching Matters

ROI: ★★★★★ Frequency: Very High

Short Answer

Caching exists to trade a small amount of correctness risk (staleness) for a large amount of speed and headroom. There are three distinct benefits, and a strong answer names all three rather than just "it's faster."

Latency reduction. Reading a value from memory (or from Redis over a fast local network) is orders of magnitude cheaper than a disk-backed query, a join across several tables, or a call to a downstream service. Shaving a database round trip off a hot read path can turn a 40ms response into a 2ms one, and for a page that fires a dozen such reads, that difference compounds into the user-perceived latency budget.

Load reduction. Every request served from cache is a request the system of record never sees. This is arguably the more important benefit at scale: it is not just about making one request faster, it is about protecting your database from a traffic pattern it was never sized for. A cache with a 95% hit ratio means your database only has to handle 5% of the actual traffic, which is often the difference between a database that comfortably keeps up and one that falls over during a spike.

Cost. Fewer database reads means you can run a smaller, cheaper database tier (or fewer read replicas), and for anything backed by a metered external API, a cache directly cuts your bill. Cost is a legitimate driver on its own, independent of latency.

None of this is free. A cache introduces a second source of truth that can disagree with the first, and every caching decision is really a decision about how much staleness you can tolerate and for how long.

Interview Gold Point

State it as "cheaper, faster, safer" - faster responses, less load on the source of truth, lower infrastructure cost - and then immediately volunteer the cost: staleness and added complexity. Interviewers want to see that you reach for a cache deliberately, not reflexively, because you understand what you are giving up.

Q2. Cache-Aside (Lazy Loading) Pattern

ROI: ★★★★★ Frequency: Very High

Short Answer

Cache-aside (also called lazy loading) is the pattern where the application code owns the cache directly, rather than the caching layer sitting transparently in front of the database. On a read, the application first checks the cache; on a hit it returns the cached value; on a miss it reads from the database, stores the result in the cache, and then returns it. On a write, the application updates the database and then removes the corresponding cache entry rather than trying to update it in place.

This is the most common caching pattern in practice because it is simple, it only caches data that is actually requested (lazy population, so you never waste memory on cold data), and it is resilient to cache failures: if the cache is down, every request just falls through to the database and behaves as if there were no cache at all, which degrades gracefully instead of breaking the system.

The trade-offs are a guaranteed miss on the very first request for any key (which can matter for "cold start" scenarios), a brief inconsistency window between when the database changes and when the stale cache entry is evicted, and the fact that every write path in the codebase must remember to invalidate the cache, which is easy to miss in a large system with multiple write entry points. 

public Product getProduct(String id) {
    Product cached = cache.get(id);
    if (cached != null) {
        return cached; // cache hit
    }
    Product fromDb = productRepository.findById(id); // cache miss
    cache.put(id, fromDb, Duration.ofMinutes(10));
    return fromDb;
}

public void updateProduct(Product product) {
    productRepository.save(product); // write to source of truth
    cache.evict(product.getId());    // invalidate, don't update in place
}

Common Mistake

Updating the cache directly on write instead of deleting it. That looks like an optimization ("save a future read!") but it opens a race: if two writes interleave, or a slow read that started before the write finishes populates the cache after the write's cache-update, you can permanently strand a stale value. Delete-then-let-the-next-read-repopulate is simpler and safer, and it is the pattern almost every production system actually uses.

Q3. Write-Through vs Write-Behind vs Write-Around

ROI: ★★★★☆ Frequency: High

Short Answer

These three patterns answer the same question - "where does a write go first?" - with different priorities.

Write-through. The application writes to the cache, and the cache synchronously writes through to the database before the write is considered complete. The cache is always warm and consistent with the database, which is attractive, but every write now pays the latency of both the cache write and the database write.

Write-behind (write-back). The application writes to the cache only, and the cache asynchronously flushes the change to the database later, often batched. Writes are extremely fast because the caller does not wait on the database at all. The risk is data loss: if the cache crashes before the flush happens, that write is gone, so this pattern needs a durable buffer (a persistent queue or log) behind it to be safe, and it is usually reserved for workloads that can tolerate a small durability risk in exchange for very high write throughput.

Write-around. The application writes directly to the database and does not touch the cache at all. The cache only gets populated on a subsequent read (effectively cache-aside applied to the write path). This keeps the cache free of write-heavy, rarely-read data, but the first read after a write is guaranteed to miss, so it is a poor fit if the same record is read again immediately after being written.

Pattern Write latency Durability risk Best for
Write-through Higher (writes both) Low Read-heavy data that must stay consistent
Write-behind Lowest Higher (needs durable buffer) Very high write volume, brief loss tolerable
Write-around Same as plain DB write Low Write-heavy, rarely re-read data

Interview Favorite

The one-line comparison to use: "write-through keeps the cache warm at the cost of write latency, write-behind keeps writes fast at the cost of durability risk, write-around keeps the cache clean at the cost of a guaranteed miss on the next read." Naming the specific cost of each, not just the benefit, is what signals real experience.

SECTION 2 - INVALIDATION & DEPLOYMENT MODELS

Q4. Cache Invalidation Strategies (TTL, Explicit Eviction, Versioning)

ROI: ★★★★★ Frequency: Very High

Short Answer

Cache invalidation is famously one of the two hard problems in computer science, and interviewers ask it because "how do you populate a cache" is easy but "how do you make sure it never lies to you" is where the design actually lives. There are three complementary strategies, and a mature design usually combines more than one.

TTL (time-to-live) expiration. Every entry gets a maximum lifetime after which it is automatically removed or treated as expired. This is the simplest strategy and it bounds the worst-case staleness window even if you forget to invalidate explicitly, but it does not give you immediate consistency - a value can be wrong for up to the length of the TTL.

Explicit eviction (invalidate-on-write). The write path actively deletes (or updates) the affected cache key the moment the source of truth changes. This gives you near-immediate consistency, but it requires discipline: every place in the codebase that can mutate the underlying data has to remember to evict the right key, which gets harder as the number of write paths and services grows.

Versioning / cache-busting. Instead of deleting an old entry, you change the key itself, typically by embedding a version number or a content hash (user:v3:123, or a hashed filename for a static asset). The old entry is simply never looked up again and eventually falls out via TTL or normal LRU pressure. This is the standard approach for CDN-cached static assets (app.a1b2c3.js) because it sidesteps the need to actively purge anything - a new deploy just produces new keys. 

// TTL: bound staleness even if invalidation is missed
cache.put("product:" + id, product, Duration.ofMinutes(10));

// Explicit eviction: invalidate the instant the source changes
productRepository.save(product);
cache.evict("product:" + product.getId());

// Versioning: new deploy -> new key -> old entries just age out
String cacheKey = "user:v3:" + userId;

Common Mistake

Relying on TTL alone and calling invalidation "solved." A five-minute TTL means every write can be visibly stale for up to five minutes, which is fine for a product description and not fine for an account balance. The senior answer picks the strategy per data type: TTL as a safety net everywhere, explicit eviction for anything where correctness after a write matters, and versioning for immutable/versioned content like static assets.

Q5. In-Process vs Distributed Caching (Caffeine vs Redis)

ROI: ★★★★★ Frequency: Very High

Short Answer

This is a deployment-topology decision, and it is one of the first things worth clarifying when someone says "let's just cache it."

An in-process cache (Caffeine, Guava) lives inside the JVM heap of a single application instance. Reads are nanosecond-scale because there is no network hop and no serialization. The catch is that it is local: with five instances behind a load balancer, you effectively have five independent caches that can disagree with each other, and the cache is wiped every time that instance restarts or is redeployed.

A distributed cache (Redis, Memcached) runs as a separate service that every instance talks to over the network. All instances see the same data, so there is one consistent view across the fleet, and the cache survives an individual app instance restarting or being redeployed. The cost is a network round trip per access (still much faster than a database, but not free) and an extra piece of infrastructure to run, monitor, and fail over.

Use an in-process cache for small, extremely hot, per-instance data where a little inconsistency across nodes is tolerable - parsed configuration, compiled regular expressions, a feature-flag snapshot, or as the L1 layer in front of a distributed L2 (see Q11). Use a distributed cache when you need every instance to agree, when the cached data set is too large to duplicate in every instance's heap, or when the cache needs to survive deploys and restarts, such as user sessions or shopping carts.

Aspect In-Process (Caffeine) Distributed (Redis)
Latency Nanoseconds, no network Sub-millisecond, one network hop
Consistency across instances None (each instance independent) Single shared view
Survives restart/deploy No, wiped Yes
Capacity Bounded by one instance's heap Bounded by the cluster
Best for Small, very hot, per-node data Shared state, sessions, large datasets

Interview Gold Point

The framing that lands well: "in-process is the fastest cache you'll ever use, but it only knows about itself; distributed is the one source of shared truth across the fleet." Many production systems use both at once, which is exactly the multi-level pattern covered in Q11.

Q6. Caffeine Eviction & the W-TinyLFU Admission Policy

ROI: ★★★★☆ Frequency: High

Short Answer

Caffeine is the standard in-process Java cache, and it supports two independent eviction triggers plus a smarter-than-LRU admission policy underneath.

Size-based eviction bounds the cache by a maximum size or a maximum total weight (useful when entries vary a lot in memory footprint), evicting entries once the bound is exceeded. Time-based eviction comes in two flavors: expireAfterWrite removes an entry a fixed duration after it was inserted or updated regardless of how often it is read, while expireAfterAccess removes an entry a fixed duration after its last read, so a frequently accessed entry keeps renewing its lifetime.

Under the hood, Caffeine's default eviction policy is W-TinyLFU (Windowed Tiny Least Frequently Used), not plain LRU. Plain LRU has a well-known weakness: a burst of one-time-use keys (a large sequential scan, a batch job reading everything once) can flush out genuinely hot data simply because those cold keys were the most recent. W-TinyLFU keeps a compact frequency sketch (a Count-Min Sketch) of recently seen keys and uses it to decide whether a newly arriving key is popular enough to be admitted at all, ahead of evicting an existing entry with a stronger frequency history. A small admission window (LRU-like) absorbs bursts of new arrivals so genuinely emerging hot keys are not permanently locked out. The net effect is near-optimal hit ratios at very low memory and CPU overhead, which is why Caffeine consistently outperforms a naive LRU cache in benchmarks. 

Cache<String, Product> cache = Caffeine.newBuilder()
        .maximumSize(10_000)                 // size-based eviction
        .expireAfterWrite(Duration.ofMinutes(10)) // time-based eviction
        .recordStats()                       // exposes hit/miss/eviction metrics
        .build();

Product product = cache.get(id, key -> productRepository.findById(key));
// cache.get with a loading function also coalesces concurrent
// requests for the same missing key into a single load (see Q9)

Interview Favorite

Naming "W-TinyLFU" specifically, instead of saying "it's basically LRU," is a strong differentiator - it signals you have actually read how the library you use every day works. The one-line summary: "W-TinyLFU decides who gets in using frequency, then evicts using a windowed recency scheme, which makes it resistant to one-off scans that would poison a plain LRU cache."

SECTION 3 - REDIS DEEP DIVE

Q7. Redis Data Structures & Common Use Cases

ROI: ★★★★☆ Frequency: High

Short Answer

Redis is often described as a "key-value store," but the reason it is so widely used is that the value can be one of several rich data structures, each suited to a different access pattern, not just an opaque blob.

A string is the simplest type and covers plain cached values, serialized JSON blobs, and atomic counters via INCR (rate limiting, view counts). A hash stores field-value pairs under one key, which is a natural fit for representing an object (a user profile) where you want to read or update a single field without deserializing and re-serializing the whole record. A list is an ordered sequence, useful for a simple queue or a bounded "recent items" feed. A set stores unique unordered members and is ideal for membership checks and tag-like relationships (does this user have this role). A sorted set (ZSet) associates each member with a numeric score and keeps them ordered by that score, which powers leaderboards, priority queues, and sliding-window rate limiters. Redis also offers bitmaps for compact boolean flags at scale and HyperLogLog for approximate distinct-count cardinality (unique visitor counts) in a fixed, tiny memory footprint.

Structure Shape Typical use case
String Single value Simple cache entry, atomic counters (INCR)
Hash Field -> value map Object representation (user profile), partial updates
List Ordered sequence Simple queue, recent-activity feed
Set Unique unordered members Membership checks, tags, deduplication
Sorted Set Members ordered by score Leaderboards, sliding-window rate limits
HyperLogLog Probabilistic set Approximate unique-visitor counts at low memory

Interview Gold Point

The signal to send: "Redis isn't just a cache, it's a data-structure server, and picking the right structure often removes the need for application-side logic." A leaderboard implemented with a sorted set is a single ZADD/ZRANGE pair instead of an application maintaining sort order itself.

Q8. Redis Persistence: RDB vs AOF

ROI: ★★★☆☆ Frequency: Medium

Short Answer

Redis is in-memory, so persistence is about what happens if the process restarts or crashes, and Redis gives you two mechanisms that trade durability against performance and restart speed.

RDB (snapshotting) periodically writes the entire dataset to a compact binary file at a configured interval (for example, every 5 minutes if at least 100 keys changed). It produces small files, restarts quickly because it just loads one file, and has minimal performance overhead during normal operation. The downside is a durability gap equal to the snapshot interval: a crash right before a scheduled snapshot loses every write since the last one.

AOF (append-only file) logs every write command as it happens and replays the log on restart. With fsync set to everysec you lose at most one second of writes on a crash, and with always you lose essentially nothing at the cost of write throughput. The trade-off is a much larger file and a slower restart, since Redis has to replay the whole command log (mitigated by periodic AOF rewriting/compaction).

In practice, many teams enable both: RDB for fast, compact backups and quick restarts, AOF for tighter durability, and Redis merges them sensibly on restart. It is also worth remembering that if Redis is purely a disposable cache in front of a real database, persistence may deliberately be turned off or relaxed, because the source of truth already exists elsewhere and losing the cache on restart is just a cold-start cost, not data loss.

Aspect RDB (snapshot) AOF (append log)
File size Small, compact Larger, grows until rewritten
Durability Can lose the whole interval As low as ~1s (or none with fsync always)
Restart speed Fast (load one file) Slower (replay commands)
Runtime overhead Low Higher (writes every command)

Common Mistake

Assuming Redis is durable "like a database" without ever checking the persistence configuration or testing an actual restart/recovery. If Redis is holding anything you cannot afford to lose (sessions acting as the only session store, a rate-limiter's state that must survive a failover), you must consciously configure and test AOF, not just trust the defaults.

Q9. Cache Stampede / Thundering Herd & Mitigations

ROI: ★★★★★ Frequency: Very High

Short Answer

A cache stampede (thundering herd) happens when a single hot key expires and a large number of concurrent requests all miss at the same instant. Instead of one request recomputing the value, every one of those requests falls through to the database or origin service simultaneously, and a load that was previously smoothed out by the cache suddenly arrives at the source of truth all at once - often enough to take it down. This is one of the more dangerous caching failure modes precisely because the cache, which exists to protect the backend, becomes the trigger for overwhelming it.

There are several standard mitigations, usually combined. Locking / mutex: only the first request that misses acquires a lock (in Redis, a SET key value NX PX ttl) and recomputes the value; every other concurrent request either waits briefly and retries the cache, or is served a slightly stale value while the recompute is in flight. Request coalescing: within a single process, collapse concurrent loads for the same missing key into one in-flight computation that all callers await (Caffeine's loading cache does this automatically). TTL jitter: instead of a flat 10-minute TTL for every key, randomize it (for example 10 minutes plus or minus 2 minutes) so a batch of keys populated together does not all expire in the same instant. Probabilistic early recomputation: as a key's TTL approaches expiry, refresh it early with a probability that increases the closer it gets to expiring, so it is very unlikely that every request arrives after the hard deadline. Stale-while-revalidate: serve the (slightly) stale value immediately while asynchronously refreshing it in the background, trading a bounded amount of staleness for a guarantee that the backend never sees a stampede. 

// Distributed lock via Redis SET NX (only one caller recomputes)
Boolean acquired = redis.opsForValue()
        .setIfAbsent("lock:product:" + id, "1", Duration.ofSeconds(5));

if (Boolean.TRUE.equals(acquired)) {
    Product fresh = productRepository.findById(id);
    cache.put("product:" + id, fresh, jitteredTtl());
    redis.delete("lock:product:" + id);
    return fresh;
} else {
    // another request is already recomputing; serve stale or brief-wait
    return cache.getStale("product:" + id);
}

Interview Gold Point

The phrase that shows you have seen this in production: "the danger isn't the cache miss, it's the coordinated miss." A good design deliberately decorrelates expirations with jitter and ensures only one request ever pays the cost of a recompute, which is the difference between a cache that protects your database and one that occasionally attacks it.

SECTION 4 - SPRING & ARCHITECTURE

Q10. Spring's Caching Abstraction (@Cacheable, @CacheEvict, @CachePut, CacheManager)

ROI: ★★★★★ Frequency: Very High

Short Answer

Spring's caching abstraction lets you declare caching behavior with annotations instead of hand-writing cache-aside logic, and the same annotations work unchanged regardless of which cache implementation sits underneath - a ConcurrentMapCacheManager for quick tests, a CaffeineCacheManager for in-process, or a RedisCacheManager for distributed.

@Cacheable wraps a method with cache-aside behavior: on invocation, Spring computes a key (from the arguments, or an explicit SpEL expression), checks the named cache, returns the cached value on a hit, and otherwise runs the method body and stores its return value before returning it. @CachePut always executes the method, but writes the result into the cache afterward - it is used on write operations where you want to keep the cache warm with the fresh value rather than simply skip work on a hit. @CacheEvict removes an entry (or, with allEntries = true, clears the whole cache) and is typically placed on the method that deletes or invalidates the underlying record.

Under the hood this all works through a Spring AOP proxy, which matters for two very common gotchas: calling an @Cacheable method from another method in the same class bypasses the proxy entirely (self-invocation), so the caching annotation is silently ignored, and by default a thrown exception is not cached, but the method also does not get a "negative cache" entry, so a failing dependency can be hammered by every retry. 

@Service
public class ProductService {

    @Cacheable(cacheNames = "products", key = "#id")
    public Product getProduct(String id) {
        return productRepository.findById(id).orElseThrow();
    }

    @CachePut(cacheNames = "products", key = "#product.id")
    public Product updateProduct(Product product) {
        return productRepository.save(product); // cache stays warm
    }

    @CacheEvict(cacheNames = "products", key = "#id")
    public void deleteProduct(String id) {
        productRepository.deleteById(id);
    }
}

@Bean
public CacheManager cacheManager() {
    CaffeineCacheManager manager = new CaffeineCacheManager("products");
    manager.setCaffeine(Caffeine.newBuilder()
            .maximumSize(5_000)
            .expireAfterWrite(Duration.ofMinutes(10)));
    return manager;
}

Common Mistake

Caching a method that has side effects, returns non-deterministic data, or is called from within the same class (self-invocation) and expecting the annotation to fire. Also common: forgetting @EnableCaching on a configuration class, after which every caching annotation is silently a no-op and nobody notices until a load test reveals the database is taking full traffic.

Q11. Multi-Level Caching (L1 Caffeine + L2 Redis)

ROI: ★★★★☆ Frequency: High

Short Answer

Multi-level caching combines the strengths of Q5's two options instead of picking one: a small, fast in-process cache (L1, Caffeine) sits in front of a shared distributed cache (L2, Redis), which in turn sits in front of the database. The read path checks L1 first, falls through to L2 on an L1 miss, and falls through to the database only on a miss at both levels; on the way back up, the value is written into L2 and then L1 so subsequent reads on that instance are served at L1 speed.

The benefit is that the overwhelming majority of reads for genuinely hot keys never leave the JVM heap (L1 absorbs them at nanosecond latency with zero network cost), while L2 still gives every instance a consistent shared view and protects the database even for keys that are not hot enough to earn a spot in any single instance's small L1.

The hard part is L1 invalidation: because each instance's L1 is independent, a write on one instance does not automatically clear the stale entry sitting in another instance's L1. Production systems handle this either by keeping L1 TTLs short enough that staleness is bounded to a few seconds, or by publishing an invalidation message (Redis pub/sub, or a lightweight Kafka topic) that every instance subscribes to and uses to evict the key from its own L1 the moment a write happens anywhere in the fleet. 

public Product getProduct(String id) {
    Product v = l1Cache.getIfPresent(id);          // L1: Caffeine
    if (v != null) return v;

    v = l2Cache.get("product:" + id, Product.class); // L2: Redis
    if (v != null) {
        l1Cache.put(id, v);
        return v;
    }

    v = productRepository.findById(id);             // source of truth
    l2Cache.set("product:" + id, v, Duration.ofMinutes(10));
    l1Cache.put(id, v);
    return v;
}

// On write, evict locally AND broadcast so every instance's L1 clears too
redisTemplate.convertAndSend("cache-invalidate", "product:" + id);

Interview Gold Point

The trade-off to name unprompted: multi-level caching buys you the best of both latency profiles, but it means accepting a bounded window where different instances can briefly disagree, since L1 is only ever eventually consistent with L2. Say explicitly how you bound that window - short TTL, or an active invalidation broadcast - because "it's eventually consistent" alone sounds like hand-waving without a concrete mechanism attached.

Q12. Cache Consistency in Distributed Systems

ROI: ★★★★☆ Frequency: High

Short Answer

Once a cache is shared across services or instances, "the cache might be wrong" stops being a hypothetical and becomes a design constraint you must actively bound. There are two broad approaches to keeping a cache in line with its source of truth.

Write-invalidate. On every write to the source of truth, delete the corresponding cache entry rather than trying to update it. The next read is a guaranteed miss that repopulates from the fresh source. This is simpler and safer under concurrent writes because there is no "which write wins" race inside the cache itself - the cache is just empty until someone reads it again.

Write-update. On every write, push the new value directly into the cache. This keeps the cache warm (no forced miss), but it is riskier: if two writes to the same key are in flight concurrently, the slower one can finish last and overwrite the cache with a now-outdated value, even though the database itself ended up correct. Write-invalidate avoids this class of bug entirely, which is why it is the more common default.

A related, subtler race affects cache-aside: a read that misses, fetches from a (possibly lagging) database replica, and writes that stale value into the cache after a concurrent write's invalidation has already run - permanently stranding the stale value until the TTL expires. The standard fix is the "double-delete" pattern: delete the cache key before the write, perform the write, then delete it again a short delay afterward, which catches and clears out any stale value a straggling read managed to insert in between.

Ultimately, a cache is a deliberate trade of strict consistency for performance. The realistic goal is never "the cache is always exactly right," it is "the cache is wrong for a bounded, known amount of time, and that bound is small enough for the business requirement it serves."

Common Mistake

Assuming the cache and the database will always agree and being surprised when a race condition proves otherwise. The senior answer names the specific race (concurrent write vs. stale read repopulating the cache), names the fix (write-invalidate, plus double-delete for the replica-lag case), and states the staleness bound in plain terms rather than promising perfect consistency.

SECTION 5 - POLICY & OPERATIONS

Q13. Choosing an Eviction Policy: LRU vs LFU vs FIFO

ROI: ★★★★☆ Frequency: High

Short Answer

When a cache is full and a new entry needs to be admitted, the eviction policy decides who gets kicked out, and the right choice depends on the shape of your access pattern.

LRU (Least Recently Used) evicts the entry that has gone the longest without being accessed. It is cheap to implement (a hashmap plus a doubly linked list, or Redis's approximated sampling version for O(1) behavior at scale) and works well when "recently used" is a good predictor of "will be used again soon." Its well-known weakness is vulnerability to scans: a one-off bulk read of many keys can flush out genuinely hot data simply because those cold keys were touched most recently.

LFU (Least Frequently Used) evicts the entry with the lowest access count. It handles skewed, "some keys are always hot" access patterns better than LRU because a truly popular key cannot be evicted by a single burst of unrelated one-time reads. The cost is more bookkeeping (a counter per entry) and slower adaptation - a key that was hot yesterday but has gone cold today can linger with an inflated count unless the implementation decays old counts over time.

FIFO (First In, First Out) evicts whatever was inserted first, completely ignoring how often or how recently it was used. It is the simplest and cheapest to implement, but it generally gives the worst hit ratio of the three because it has no concept of "hot" at all.

In practice, production caches rarely use any of these in pure form. Redis approximates LRU via random sampling rather than tracking exact recency for every key, because exact LRU does not scale to millions of keys, and Caffeine's W-TinyLFU (Q6) blends a frequency sketch with a small LRU-like admission window specifically to get LFU's scan-resistance without its full bookkeeping cost.

Policy Evicts Strength Weakness
LRU Least recently accessed Cheap, good general default Fooled by one-off scans
LFU Lowest access count Protects durably hot keys More overhead, slow to adapt
FIFO Oldest inserted Simplest, no tracking No notion of "hot" at all

Interview Favorite

If asked to pick one, the safe senior answer is "LRU as a default, because it is cheap and matches most real workloads, but I'd reach for a frequency-aware policy like LFU or W-TinyLFU if the access pattern includes bulk scans that would otherwise flush genuinely hot data." That shows you know the failure mode LRU has, not just its name.

Q14. Sizing & Monitoring a Cache (Hit Ratio, Eviction Rate, Alerts)

ROI: ★★★★☆ Frequency: High

Short Answer

A cache you cannot see the metrics for is a cache you are guessing about. A handful of numbers tell you almost everything you need to know about whether it is healthy, undersized, or actively misconfigured.

Hit ratio (hits divided by hits plus misses) is the headline number: it tells you what fraction of traffic the cache is actually absorbing away from the source of truth. What counts as "good" depends entirely on the workload - a highly skewed read pattern might sustain 95%+, while a long-tail catalog might realistically top out lower - so the metric matters most as a trend, not an absolute target. Eviction rate tells you whether the cache is being forced to throw away entries before they would naturally expire; a high eviction rate relative to the hit rate usually means the cache is undersized for its working set, or the TTL is too aggressive, and entries are being pushed out by memory pressure rather than by going stale. Memory usage versus configured maximum matters especially for Redis, where the configured eviction policy determines what happens at the limit - with noeviction, writes start failing outright once memory is full, which is a very different (and much worse) failure mode than quietly evicting the least useful key.

For Redis specifically, watch used_memory, evicted_keys, keyspace_hits/keyspace_misses, connected client count, and replication lag if you run replicas. For an in-process Caffeine cache, recordStats() exposes hit rate, load time, and eviction counts directly.

On the alerting side, the signals worth paging on are: a sudden drop in hit ratio (often means an invalidation bug, a bad deploy that changed the key scheme, or a cache flush), a spike in eviction rate (undersized cache or a TTL that just got shorter than intended), and memory approaching the configured maximum on a cache set to noeviction (writes are about to start failing).

Metric What it tells you Alert on
Hit ratio Fraction of traffic absorbed by the cache Sudden drop vs. baseline
Eviction rate Entries forced out before natural expiry Sharp spike (undersized / bad TTL)
Memory used vs. max Headroom before eviction/failure Approaching max, especially with noeviction
Keyspace misses Raw miss volume hitting the source of truth Rising in absolute terms, not just ratio

Interview Gold Point

Tie the metrics back to business impact rather than reciting them: "cache metrics matter because they're a proxy for the load about to hit my database. A falling hit ratio isn't just a cache problem, it's an early warning that my source of truth is seconds away from getting hit a lot harder than usual." That framing is what separates someone who watches a dashboard from someone who understands why the dashboard exists.

QUICK REVISION SHEET

  • Caching buys latency reduction + load reduction + cost savings, paid for with staleness and complexity
  • Cache-aside: read checks cache then DB on miss and populates; write updates DB then evicts (never updates) the cache key
  • Write-through = warm cache, slower writes | write-behind = fast writes, durability risk | write-around = clean cache, guaranteed first-read miss
  • Invalidate with TTL (bounds staleness) + explicit eviction (immediate, needs discipline) + versioned keys (for immutable/static content)
  • In-process (Caffeine) = nanosecond, per-instance, no shared view; distributed (Redis) = shared, survives restarts, network hop
  • Caffeine evicts via size/time bounds using W-TinyLFU: a frequency sketch plus an LRU-like window, scan-resistant unlike plain LRU
  • Redis data structures: string (simple/counters), hash (objects), set (membership), sorted set (leaderboards, rate limits), HyperLogLog (approx cardinality)
  • Redis persistence: RDB = compact snapshot, fast restart, can lose the interval; AOF = command log, ~1s durability, slower restart; often both
  • Cache stampede = coordinated miss on a hot key's expiry; fix with locking/coalescing, TTL jitter, early recompute, or stale-while-revalidate
  • Spring: @Cacheable (cache-aside on read), @CachePut (always run, refresh cache), @CacheEvict (invalidate); backed by any CacheManager (Caffeine/Redis)
  • Multi-level: L1 Caffeine absorbs hot reads at nanosecond speed, L2 Redis gives the fleet a shared consistent view; bound L1 staleness with short TTL or pub/sub invalidation
  • Consistency: prefer write-invalidate over write-update to avoid races; use double-delete to catch stale reads racing a write against replica lag
  • LRU = cheap default, fooled by scans | LFU = protects hot keys, slower to adapt | FIFO = simplest, no notion of "hot" at all
  • Monitor hit ratio, eviction rate, and memory-vs-max; alert on a falling hit ratio or eviction spike, since both are early warnings for the source of truth
