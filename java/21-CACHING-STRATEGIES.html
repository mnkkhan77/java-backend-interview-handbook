SECTION 1 - FUNDAMENTALS

Q1. Why Caching Matters

ROI: ★★★★★ Frequency: Very High

Short Answer

Caching exists to trade a small amount of correctness risk (staleness) for a large amount of speed and headroom. There are three distinct benefits, and a strong answer names all three rather than just "it's faster."

Latency reduction. Reading a value from memory (or from Redis over a fast local network) is orders of magnitude cheaper than a disk-backed query, a join across several tables, or a call to a downstream service. Shaving a database round trip off a hot read path can turn a 40ms response into a 2ms one, and for a page that fires a dozen such reads, that difference compounds into the user-perceived latency budget.

Load reduction. Every request served from cache is a request the system of record never sees. This is arguably the more important benefit at scale: it is not just about making one request faster, it is about protecting your database from a traffic pattern it was never sized for. A cache with a 95% hit ratio means your database only has to handle 5% of the actual traffic, which is often the difference between a database that comfortably keeps up and one that falls over during a spike.

Cost. Fewer database reads means you can run a smaller, cheaper database tier (or fewer read replicas), and for anything backed by a metered external API, a cache directly cuts your bill. Cost is a legitimate driver on its own, independent of latency.

None of this is free. A cache introduces a second source of truth that can disagree with the first, and every caching decision is really a decision about how much staleness you can tolerate and for how long.

Interview Gold Point

State it as "cheaper, faster, safer" - faster responses, less load on the source of truth, lower infrastructure cost - and then immediately volunteer the cost: staleness and added complexity. Interviewers want to see that you reach for a cache deliberately, not reflexively, because you understand what you are giving up.

Q2. Cache-Aside (Lazy Loading) Pattern

ROI: ★★★★★ Frequency: Very High

Short Answer

Cache-aside (also called lazy loading) is the pattern where the application code owns the cache directly, rather than the caching layer sitting transparently in front of the database. On a read, the application first checks the cache; on a hit it returns the cached value; on a miss it reads from the database, stores the result in the cache, and then returns it. On a write, the application updates the database and then removes the corresponding cache entry rather than trying to update it in place.

This is the most common caching pattern in practice because it is simple, it only caches data that is actually requested (lazy population, so you never waste memory on cold data), and it is resilient to cache failures: if the cache is down, every request just falls through to the database and behaves as if there were no cache at all, which degrades gracefully instead of breaking the system.

The trade-offs are a guaranteed miss on the very first request for any key (which can matter for "cold start" scenarios), a brief inconsistency window between when the database changes and when the stale cache entry is evicted, and the fact that every write path in the codebase must remember to invalidate the cache, which is easy to miss in a large system with multiple write entry points. 

public Product getProduct(String id) {
    Product cached = cache.get(id);
    if (cached != null) {
        return cached; // cache hit
    }
    Product fromDb = productRepository.findById(id); // cache miss
    cache.put(id, fromDb, Duration.ofMinutes(10));
    return fromDb;
}

public void updateProduct(Product product) {
    productRepository.save(product); // write to source of truth
    cache.evict(product.getId());    // invalidate, don't update in place
}

Common Mistake

Updating the cache directly on write instead of deleting it. That looks like an optimization ("save a future read!") but it opens a race: if two writes interleave, or a slow read that started before the write finishes populates the cache after the write's cache-update, you can permanently strand a stale value. Delete-then-let-the-next-read-repopulate is simpler and safer, and it is the pattern almost every production system actually uses.

Q3. Write-Through vs Write-Behind vs Write-Around

ROI: ★★★★☆ Frequency: High

Short Answer

These three patterns answer the same question - "where does a write go first?" - with different priorities.

Write-through. The application writes to the cache, and the cache synchronously writes through to the database before the write is considered complete. The cache is always warm and consistent with the database, which is attractive, but every write now pays the latency of both the cache write and the database write.

Write-behind (write-back). The application writes to the cache only, and the cache asynchronously flushes the change to the database later, often batched. Writes are extremely fast because the caller does not wait on the database at all. The risk is data loss: if the cache crashes before the flush happens, that write is gone, so this pattern needs a durable buffer (a persistent queue or log) behind it to be safe, and it is usually reserved for workloads that can tolerate a small durability risk in exchange for very high write throughput.

Write-around. The application writes directly to the database and does not touch the cache at all. The cache only gets populated on a subsequent read (effectively cache-aside applied to the write path). This keeps the cache free of write-heavy, rarely-read data, but the first read after a write is guaranteed to miss, so it is a poor fit if the same record is read again immediately after being written.

Pattern Write latency Durability risk Best for
Write-through Higher (writes both) Low Read-heavy data that must stay consistent
Write-behind Lowest Higher (needs durable buffer) Very high write volume, brief loss tolerable
Write-around Same as plain DB write Low Write-heavy, rarely re-read data

Interview Favorite

The one-line comparison to use: "write-through keeps the cache warm at the cost of write latency, write-behind keeps writes fast at the cost of durability risk, write-around keeps the cache clean at the cost of a guaranteed miss on the next read." Naming the specific cost of each, not just the benefit, is what signals real experience.

SECTION 2 - INVALIDATION & DEPLOYMENT MODELS

Q4. Cache Invalidation Strategies (TTL, Explicit Eviction, Versioning)

ROI: ★★★★★ Frequency: Very High

Short Answer

Cache invalidation is famously one of the two hard problems in computer science, and interviewers ask it because "how do you populate a cache" is easy but "how do you make sure it never lies to you" is where the design actually lives. There are three complementary strategies, and a mature design usually combines more than one.

TTL (time-to-live) expiration. Every entry gets a maximum lifetime after which it is automatically removed or treated as expired. This is the simplest strategy and it bounds the worst-case staleness window even if you forget to invalidate explicitly, but it does not give you immediate consistency - a value can be wrong for up to the length of the TTL.

Explicit eviction (invalidate-on-write). The write path actively deletes (or updates) the affected cache key the moment the source of truth changes. This gives you near-immediate consistency, but it requires discipline: every place in the codebase that can mutate the underlying data has to remember to evict the right key, which gets harder as the number of write paths and services grows.

Versioning / cache-busting. Instead of deleting an old entry, you change the key itself, typically by embedding a version number or a content hash (user:v3:123, or a hashed filename for a static asset). The old entry is simply never looked up again and eventually falls out via TTL or normal LRU pressure. This is the standard approach for CDN-cached static assets (app.a1b2c3.js) because it sidesteps the need to actively purge anything - a new deploy just produces new keys. 

// TTL: bound staleness even if invalidation is missed
cache.put("product:" + id, product, Duration.ofMinutes(10));

// Explicit eviction: invalidate the instant the source changes
productRepository.save(product);
cache.evict("product:" + product.getId());

// Versioning: new deploy -> new key -> old entries just age out
String cacheKey = "user:v3:" + userId;

Common Mistake

Relying on TTL alone and calling invalidation "solved." A five-minute TTL means every write can be visibly stale for up to five minutes, which is fine for a product description and not fine for an account balance. The senior answer picks the strategy per data type: TTL as a safety net everywhere, explicit eviction for anything where correctness after a write matters, and versioning for immutable/versioned content like static assets.

Q5. In-Process vs Distributed Caching (Caffeine vs Redis)

ROI: ★★★★★ Frequency: Very High

Short Answer

This is a deployment-topology decision, and it is one of the first things worth clarifying when someone says "let's just cache it."

An in-process cache (Caffeine, Guava) lives inside the JVM heap of a single application instance. Reads are nanosecond-scale because there is no network hop and no serialization. The catch is that it is local: with five instances behind a load balancer, you effectively have five independent caches that can disagree with each other, and the cache is wiped every time that instance restarts or is redeployed.

A distributed cache (Redis, Memcached) runs as a separate service that every instance talks to over the network. All instances see the same data, so there is one consistent view across the fleet, and the cache survives an individual app instance restarting or being redeployed. The cost is a network round trip per access (still much faster than a database, but not free) and an extra piece of infrastructure to run, monitor, and fail over.

Use an in-process cache for small, extremely hot, per-instance data where a little inconsistency across nodes is tolerable - parsed configuration, compiled regular expressions, a feature-flag snapshot, or as the L1 layer in front of a distributed L2 (see Q11). Use a distributed cache when you need every instance to agree, when the cached data set is too large to duplicate in every instance's heap, or when the cache needs to survive deploys and restarts, such as user sessions or shopping carts.

Aspect In-Process (Caffeine) Distributed (Redis)
Latency Nanoseconds, no network Sub-millisecond, one network hop
Consistency across instances None (each instance independent) Single shared view
Survives restart/deploy No, wiped Yes
Capacity Bounded by one instance's heap Bounded by the cluster
Best for Small, very hot, per-node data Shared state, sessions, large datasets

Interview Gold Point

The framing that lands well: "in-process is the fastest cache you'll ever use, but it only knows about itself; distributed is the one source of shared truth across the fleet." Many production systems use both at once, which is exactly the multi-level pattern covered in Q11.

Q6. Caffeine Eviction & the W-TinyLFU Admission Policy

ROI: ★★★★☆ Frequency: High

Short Answer

Caffeine is the standard in-process Java cache, and it supports two independent eviction triggers plus a smarter-than-LRU admission policy underneath.

Size-based eviction bounds the cache by a maximum size or a maximum total weight (useful when entries vary a lot in memory footprint), evicting entries once the bound is exceeded. Time-based eviction comes in two flavors: expireAfterWrite removes an entry a fixed duration after it was inserted or updated regardless of how often it is read, while expireAfterAccess removes an entry a fixed duration after its last read, so a frequently accessed entry keeps renewing its lifetime.

Under the hood, Caffeine's default eviction policy is W-TinyLFU (Windowed Tiny Least Frequently Used), not plain LRU. Plain LRU has a well-known weakness: a burst of one-time-use keys (a large sequential scan, a batch job reading everything once) can flush out genuinely hot data simply because those cold keys were the most recent. W-TinyLFU keeps a compact frequency sketch (a Count-Min Sketch) of recently seen keys and uses it to decide whether a newly arriving key is popular enough to be admitted at all, ahead of evicting an existing entry with a stronger frequency history. A small admission window (LRU-like) absorbs bursts of new arrivals so genuinely emerging hot keys are not permanently locked out. The net effect is near-optimal hit ratios at very low memory and CPU overhead, which is why Caffeine consistently outperforms a naive LRU cache in benchmarks. 

Cache<String, Product> cache = Caffeine.newBuilder()
        .maximumSize(10_000)                 // size-based eviction
        .expireAfterWrite(Duration.ofMinutes(10)) // time-based eviction
        .recordStats()                       // exposes hit/miss/eviction metrics
        .build();

Product product = cache.get(id, key -> productRepository.findById(key));
// cache.get with a loading function also coalesces concurrent
// requests for the same missing key into a single load (see Q9)

Interview Favorite

Naming "W-TinyLFU" specifically, instead of saying "it's basically LRU," is a strong differentiator - it signals you have actually read how the library you use every day works. The one-line summary: "W-TinyLFU decides who gets in using frequency, then evicts using a windowed recency scheme, which makes it resistant to one-off scans that would poison a plain LRU cache."

SECTION 3 - REDIS DEEP DIVE

Q7. Redis Data Structures & Common Use Cases

ROI: ★★★★☆ Frequency: High

Short Answer

Redis is often described as a "key-value store," but the reason it is so widely used is that the value can be one of several rich data structures, each suited to a different access pattern, not just an opaque blob.

A string is the simplest type and covers plain cached values, serialized JSON blobs, and atomic counters via INCR (rate limiting, view counts). A hash stores field-value pairs under one key, which is a natural fit for representing an object (a user profile) where you want to read or update a single field without deserializing and re-serializing the whole record. A list is an ordered sequence, useful for a simple queue or a bounded "recent items" feed. A set stores unique unordered members and is ideal for membership checks and tag-like relationships (does this user have this role). A sorted set (ZSet) associates each member with a numeric score and keeps them ordered by that score, which powers leaderboards, priority queues, and sliding-window rate limiters. Redis also offers bitmaps for compact boolean flags at scale and HyperLogLog for approximate distinct-count cardinality (unique visitor counts) in a fixed, tiny memory footprint.

Structure Shape Typical use case
String Single value Simple cache entry, atomic counters (INCR)
Hash Field -> value map Object representation (user profile), partial updates
List Ordered sequence Simple queue, recent-activity feed
Set Unique unordered members Membership checks, tags, deduplication
Sorted Set Members ordered by score Leaderboards, sliding-window rate limits
HyperLogLog Probabilistic set Approximate unique-visitor counts at low memory

Interview Gold Point

The signal to send: "Redis isn't just a cache, it's a data-structure server, and picking the right structure often removes the need for application-side logic." A leaderboard implemented with a sorted set is a single ZADD/ZRANGE pair instead of an application maintaining sort order itself.

Q8. Redis Persistence: RDB vs AOF

ROI: ★★★☆☆ Frequency: Medium

Short Answer

Redis is in-memory, so persistence is about what happens if the process restarts or crashes, and Redis gives you two mechanisms that trade durability against performance and restart speed.

RDB (snapshotting) periodically writes the entire dataset to a compact binary file at a configured interval (for example, every 5 minutes if at least 100 keys changed). It produces small files, restarts quickly because it just loads one file, and has minimal performance overhead during normal operation. The downside is a durability gap equal to the snapshot interval: a crash right before a scheduled snapshot loses every write since the last one.

AOF (append-only file) logs every write command as it happens and replays the log on restart. With fsync set to everysec you lose at most one second of writes on a crash, and with always you lose essentially nothing at the cost of write throughput. The trade-off is a much larger file and a slower restart, since Redis has to replay the whole command log (mitigated by periodic AOF rewriting/compaction).

In practice, many teams enable both: RDB for fast, compact backups and quick restarts, AOF for tighter durability, and Redis merges them sensibly on restart. It is also worth remembering that if Redis is purely a disposable cache in front of a real database, persistence may deliberately be turned off or relaxed, because the source of truth already exists elsewhere and losing the cache on restart is just a cold-start cost, not data loss.

Aspect RDB (snapshot) AOF (append log)
File size Small, compact Larger, grows until rewritten
Durability Can lose the whole interval As low as ~1s (or none with fsync always)
Restart speed Fast (load one file) Slower (replay commands)
Runtime overhead Low Higher (writes every command)

Common Mistake

Assuming Redis is durable "like a database" without ever checking the persistence configuration or testing an actual restart/recovery. If Redis is holding anything you cannot afford to lose (sessions acting as the only session store, a rate-limiter's state that must survive a failover), you must consciously configure and test AOF, not just trust the defaults.

Q9. Cache Stampede / Thundering Herd & Mitigations

ROI: ★★★★★ Frequency: Very High

Short Answer

A cache stampede (thundering herd) happens when a single hot key expires and a large number of concurrent requests all miss at the same instant. Instead of one request recomputing the value, every one of those requests falls through to the database or origin service simultaneously, and a load that was previously smoothed out by the cache suddenly arrives at the source of truth all at once - often enough to take it down. This is one of the more dangerous caching failure modes precisely because the cache, which exists to protect the backend, becomes the trigger for overwhelming it.

There are several standard mitigations, usually combined. Locking / mutex: only the first request that misses acquires a lock (in Redis, a SET key value NX PX ttl) and recomputes the value; every other concurrent request either waits briefly and retries the cache, or is served a slightly stale value while the recompute is in flight. Request coalescing: within a single process, collapse concurrent loads for the same missing key into one in-flight computation that all callers await (Caffeine's loading cache does this automatically). TTL jitter: instead of a flat 10-minute TTL for every key, randomize it (for example 10 minutes plus or minus 2 minutes) so a batch of keys populated together does not all expire in the same instant. Probabilistic early recomputation: as a key's TTL approaches expiry, refresh it early with a probability that increases the closer it gets to expiring, so it is very unlikely that every request arrives after the hard deadline. Stale-while-revalidate: serve the (slightly) stale value immediately while asynchronously refreshing it in the background, trading a bounded amount of staleness for a guarantee that the backend never sees a stampede. 

// Distributed lock via Redis SET NX (only one caller recomputes)
Boolean acquired = redis.opsForValue()
        .setIfAbsent("lock:product:" + id, "1", Duration.ofSeconds(5));

if (Boolean.TRUE.equals(acquired)) {
    Product fresh = productRepository.findById(id);
    cache.put("product:" + id, fresh, jitteredTtl());
    redis.delete("lock:product:" + id);
    return fresh;
} else {
    // another request is already recomputing; serve stale or brief-wait
    return cache.getStale("product:" + id);
}

Interview Gold Point

The phrase that shows you have seen this in production: "the danger isn't the cache miss, it's the coordinated miss." A good design deliberately decorrelates expirations with jitter and ensures only one request ever pays the cost of a recompute, which is the difference between a cache that protects your database and one that occasionally attacks it.

SECTION 4 - SPRING & ARCHITECTURE

Q10. Spring's Caching Abstraction (@Cacheable, @CacheEvict, @CachePut, CacheManager)

ROI: ★★★★★ Frequency: Very High

Short Answer

Spring's caching abstraction lets you declare caching behavior with annotations instead of hand-writing cache-aside logic, and the same annotations work unchanged regardless of which cache implementation sits underneath - a ConcurrentMapCacheManager for quick tests, a CaffeineCacheManager for in-process, or a RedisCacheManager for distributed.

@Cacheable wraps a method with cache-aside behavior: on invocation, Spring computes a key (from the arguments, or an explicit SpEL expression), checks the named cache, returns the cached value on a hit, and otherwise runs the method body and stores its return value before returning it. @CachePut always executes the method, but writes the result into the cache afterward - it is used on write operations where you want to keep the cache warm with the fresh value rather than simply skip work on a hit. @CacheEvict removes an entry (or, with allEntries = true, clears the whole cache) and is typically placed on the method that deletes or invalidates the underlying record.

Under the hood this all works through a Spring AOP proxy, which matters for two very common gotchas: calling an @Cacheable method from another method in the same class bypasses the proxy entirely (self-invocation), so the caching annotation is silently ignored, and by default a thrown exception is not cached, but the method also does not get a "negative cache" entry, so a failing dependency can be hammered by every retry. 

@Service
public class ProductService {

    @Cacheable(cacheNames = "products", key = "#id")
    public Product getProduct(String id) {
        return productRepository.findById(id).orElseThrow();
    }

    @CachePut(cacheNames = "products", key = "#product.id")
    public Product updateProduct(Product product) {
        return productRepository.save(product); // cache stays warm
    }

    @CacheEvict(cacheNames = "products", key = "#id")
    public void deleteProduct(String id) {
        productRepository.deleteById(id);
    }
}

@Bean
public CacheManager cacheManager() {
    CaffeineCacheManager manager = new CaffeineCacheManager("products");
    manager.setCaffeine(Caffeine.newBuilder()
            .maximumSize(5_000)
            .expireAfterWrite(Duration.ofMinutes(10)));
    return manager;
}

Common Mistake

Caching a method that has side effects, returns non-deterministic data, or is called from within the same class (self-invocation) and expecting the annotation to fire. Also common: forgetting @EnableCaching on a configuration class, after which every caching annotation is silently a no-op and nobody notices until a load test reveals the database is taking full traffic.

Q11. Multi-Level Caching (L1 Caffeine + L2 Redis)

ROI: ★★★★☆ Frequency: High

Short Answer

Multi-level caching combines the strengths of Q5's two options instead of picking one: a small, fast in-process cache (L1, Caffeine) sits in front of a shared distributed cache (L2, Redis), which in turn sits in front of the database. The read path checks L1 first, falls through to L2 on an L1 miss, and falls through to the database only on a miss at both levels; on the way back up, the value is written into L2 and then L1 so subsequent reads on that instance are served at L1 speed.

The benefit is that the overwhelming majority of reads for genuinely hot keys never leave the JVM heap (L1 absorbs them at nanosecond latency with zero network cost), while L2 still gives every instance a consistent shared view and protects the database even for keys that are not hot enough to earn a spot in any single instance's small L1.

The hard part is L1 invalidation: because each instance's L1 is independent, a write on one instance does not automatically clear the stale entry sitting in another instance's L1. Production systems handle this either by keeping L1 TTLs short enough that staleness is bounded to a few seconds, or by publishing an invalidation message (Redis pub/sub, or a lightweight Kafka topic) that every instance subscribes to and uses to evict the key from its own L1 the moment a write happens anywhere in the fleet. 

public Product getProduct(String id) {
    Product v = l1Cache.getIfPresent(id);          // L1: Caffeine
    if (v != null) return v;

    v = l2Cache.get("product:" + id, Product.class); // L2: Redis
    if (v != null) {
        l1Cache.put(id, v);
        return v;
    }

    v = productRepository.findById(id);             // source of truth
    l2Cache.set("product:" + id, v, Duration.ofMinutes(10));
    l1Cache.put(id, v);
    return v;
}

// On write, evict locally AND broadcast so every instance's L1 clears too
redisTemplate.convertAndSend("cache-invalidate", "product:" + id);

Interview Gold Point

The trade-off to name unprompted: multi-level caching buys you the best of both latency profiles, but it means accepting a bounded window where different instances can briefly disagree, since L1 is only ever eventually consistent with L2. Say explicitly how you bound that window - short TTL, or an active invalidation broadcast - because "it's eventually consistent" alone sounds like hand-waving without a concrete mechanism attached.

Q12. Cache Consistency in Distributed Systems

ROI: ★★★★☆ Frequency: High

Short Answer

Once a cache is shared across services or instances, "the cache might be wrong" stops being a hypothetical and becomes a design constraint you must actively bound. There are two broad approaches to keeping a cache in line with its source of truth.

Write-invalidate. On every write to the source of truth, delete the corresponding cache entry rather than trying to update it. The next read is a guaranteed miss that repopulates from the fresh source. This is simpler and safer under concurrent writes because there is no "which write wins" race inside the cache itself - the cache is just empty until someone reads it again.

Write-update. On every write, push the new value directly into the cache. This keeps the cache warm (no forced miss), but it is riskier: if two writes to the same key are in flight concurrently, the slower one can finish last and overwrite the cache with a now-outdated value, even though the database itself ended up correct. Write-invalidate avoids this class of bug entirely, which is why it is the more common default.

A related, subtler race affects cache-aside: a read that misses, fetches from a (possibly lagging) database replica, and writes that stale value into the cache after a concurrent write's invalidation has already run - permanently stranding the stale value until the TTL expires. The standard fix is the "double-delete" pattern: delete the cache key before the write, perform the write, then delete it again a short delay afterward, which catches and clears out any stale value a straggling read managed to insert in between.

Ultimately, a cache is a deliberate trade of strict consistency for performance. The realistic goal is never "the cache is always exactly right," it is "the cache is wrong for a bounded, known amount of time, and that bound is small enough for the business requirement it serves."

Common Mistake

Assuming the cache and the database will always agree and being surprised when a race condition proves otherwise. The senior answer names the specific race (concurrent write vs. stale read repopulating the cache), names the fix (write-invalidate, plus double-delete for the replica-lag case), and states the staleness bound in plain terms rather than promising perfect consistency.

SECTION 5 - POLICY & OPERATIONS

Q13. Choosing an Eviction Policy: LRU vs LFU vs FIFO

ROI: ★★★★☆ Frequency: High

Short Answer

When a cache is full and a new entry needs to be admitted, the eviction policy decides who gets kicked out, and the right choice depends on the shape of your access pattern.

LRU (Least Recently Used) evicts the entry that has gone the longest without being accessed. It is cheap to implement (a hashmap plus a doubly linked list, or Redis's approximated sampling version for O(1) behavior at scale) and works well when "recently used" is a good predictor of "will be used again soon." Its well-known weakness is vulnerability to scans: a one-off bulk read of many keys can flush out genuinely hot data simply because those cold keys were touched most recently.

LFU (Least Frequently Used) evicts the entry with the lowest access count. It handles skewed, "some keys are always hot" access patterns better than LRU because a truly popular key cannot be evicted by a single burst of unrelated one-time reads. The cost is more bookkeeping (a counter per entry) and slower adaptation - a key that was hot yesterday but has gone cold today can linger with an inflated count unless the implementation decays old counts over time.

FIFO (First In, First Out) evicts whatever was inserted first, completely ignoring how often or how recently it was used. It is the simplest and cheapest to implement, but it generally gives the worst hit ratio of the three because it has no concept of "hot" at all.

In practice, production caches rarely use any of these in pure form. Redis approximates LRU via random sampling rather than tracking exact recency for every key, because exact LRU does not scale to millions of keys, and Caffeine's W-TinyLFU (Q6) blends a frequency sketch with a small LRU-like admission window specifically to get LFU's scan-resistance without its full bookkeeping cost.

Policy Evicts Strength Weakness
LRU Least recently accessed Cheap, good general default Fooled by one-off scans
LFU Lowest access count Protects durably hot keys More overhead, slow to adapt
FIFO Oldest inserted Simplest, no tracking No notion of "hot" at all

Interview Favorite

If asked to pick one, the safe senior answer is "LRU as a default, because it is cheap and matches most real workloads, but I'd reach for a frequency-aware policy like LFU or W-TinyLFU if the access pattern includes bulk scans that would otherwise flush genuinely hot data." That shows you know the failure mode LRU has, not just its name.

Q14. Sizing & Monitoring a Cache (Hit Ratio, Eviction Rate, Alerts)

ROI: ★★★★☆ Frequency: High

Short Answer

A cache you cannot see the metrics for is a cache you are guessing about. A handful of numbers tell you almost everything you need to know about whether it is healthy, undersized, or actively misconfigured.

Hit ratio (hits divided by hits plus misses) is the headline number: it tells you what fraction of traffic the cache is actually absorbing away from the source of truth. What counts as "good" depends entirely on the workload - a highly skewed read pattern might sustain 95%+, while a long-tail catalog might realistically top out lower - so the metric matters most as a trend, not an absolute target. Eviction rate tells you whether the cache is being forced to throw away entries before they would naturally expire; a high eviction rate relative to the hit rate usually means the cache is undersized for its working set, or the TTL is too aggressive, and entries are being pushed out by memory pressure rather than by going stale. Memory usage versus configured maximum matters especially for Redis, where the configured eviction policy determines what happens at the limit - with noeviction, writes start failing outright once memory is full, which is a very different (and much worse) failure mode than quietly evicting the least useful key.

For Redis specifically, watch used_memory, evicted_keys, keyspace_hits/keyspace_misses, connected client count, and replication lag if you run replicas. For an in-process Caffeine cache, recordStats() exposes hit rate, load time, and eviction counts directly.

On the alerting side, the signals worth paging on are: a sudden drop in hit ratio (often means an invalidation bug, a bad deploy that changed the key scheme, or a cache flush), a spike in eviction rate (undersized cache or a TTL that just got shorter than intended), and memory approaching the configured maximum on a cache set to noeviction (writes are about to start failing).

Metric What it tells you Alert on
Hit ratio Fraction of traffic absorbed by the cache Sudden drop vs. baseline
Eviction rate Entries forced out before natural expiry Sharp spike (undersized / bad TTL)
Memory used vs. max Headroom before eviction/failure Approaching max, especially with noeviction
Keyspace misses Raw miss volume hitting the source of truth Rising in absolute terms, not just ratio

Interview Gold Point

Tie the metrics back to business impact rather than reciting them: "cache metrics matter because they're a proxy for the load about to hit my database. A falling hit ratio isn't just a cache problem, it's an early warning that my source of truth is seconds away from getting hit a lot harder than usual." That framing is what separates someone who watches a dashboard from someone who understands why the dashboard exists.

SECTION 6 - REDIS CLUSTERING, REPLICATION & OPERATIONS

Q15. Redis Cluster & Hash Slots

ROI: ★★★★☆ Frequency: High

Short Answer

A single Redis instance is bounded by one machine's memory and one machine's CPU for command processing. Redis Cluster solves both by sharding the keyspace across multiple nodes, so the dataset and the request load are spread out rather than concentrated on one process.

Redis does not shard by consistent hashing over arbitrary node counts; it divides the entire keyspace into a fixed 16384 hash slots. Every key is mapped to a slot by taking CRC16(key) mod 16384, and each node in the cluster owns a contiguous range of those slots. A client that wants to read or write a key computes (or is told) which slot it belongs to, and talks directly to the node that owns that slot; if it asks the wrong node, that node replies with a MOVED redirect pointing at the right one. Because the total slot count is fixed at 16384 regardless of how many nodes you add, rebalancing (adding or removing a node) is just a matter of migrating a range of slots from one node to another, not rehashing the whole keyspace.

The sharp edge interviewers probe for is multi-key operations. A command that touches two keys (a MSET across keys, a Lua script, a transaction) only works if every key involved hashes to the same slot, because Redis Cluster does not coordinate a single command across multiple nodes. The fix is hash tags: wrapping the part of the key you want hashed in curly braces, for example {user:123}:profile and {user:123}:sessions, so only the substring inside the braces is hashed and both keys land on the same slot deliberately. 

// Without a hash tag these two keys can land on different nodes,
// making a single MGET or a Lua script across both impossible:
user:123:profile
user:123:sessions

// With a hash tag, only "user:123" is hashed -> same slot, same node:
{user:123}:profile
{user:123}:sessions

Interview Gold Point

The number to know cold is 16384 slots, and the one-sentence explanation of why: it is small enough that the slot-ownership map is cheap to gossip between nodes, and it never changes size, so scaling the cluster is slot migration, not a rehash of every key. Pairing that with "and multi-key operations need a hash tag to force co-location" shows you understand both the mechanism and its most common practical limitation.

Q16. Redis Replication: Master-Replica & Read Scaling

ROI: ★★★★☆ Frequency: High

Short Answer

Redis replication lets one or more replica nodes maintain a live copy of a primary node's dataset. The primary streams every write it accepts to its replicas asynchronously, and each replica applies those writes to keep its own copy in sync. This serves two purposes at once: it protects against data loss if the primary fails, and it lets you scale reads horizontally by pointing read-heavy traffic at replicas instead of the primary.

The critical word is asynchronous. The primary acknowledges a write to the client as soon as it is applied locally; it does not wait for any replica to confirm receipt. That means there is always a small replication lag window, and a replica can be milliseconds (or, under load or network trouble, much longer) behind the primary. Reading from a replica is therefore reading a slightly stale, eventually consistent view, which is fine for a product listing but wrong for "read your own write immediately after writing it" flows such as showing a user their own just-placed order.

If the primary fails, promoting a replica to take over does not happen automatically with plain replication alone - that is what Sentinel (Q17) or Cluster's built-in failover exists to automate. Without it, a primary failure means someone has to manually promote a replica and repoint clients, which is an outage, not a graceful failover.

Common Mistake

Routing a read to a replica immediately after the corresponding write and being surprised the value isn't there yet. If a flow genuinely needs read-your-writes consistency, either read from the primary for that specific path, or accept the staleness and design the UI around it (e.g. showing an optimistic client-side value rather than round-tripping to a lagging replica).

Q17. Redis Sentinel for High Availability & Automatic Failover

ROI: ★★★★☆ Frequency: High

Short Answer

Sentinel is a separate set of Redis processes whose only job is to watch a primary/replica group and automate failover when the primary dies, so an outage does not require a human to notice and manually promote a replica at 3 a.m.

Each Sentinel process continuously pings the primary and its replicas. When enough Sentinels (a configured quorum) independently agree that the primary is unreachable - this distinction matters, because a single Sentinel losing connectivity to the primary might just mean that Sentinel has a network problem, not that the primary is actually down - they elect a leader Sentinel among themselves, which then picks the best-positioned replica (least replication lag, highest priority) and promotes it to primary. Sentinel also updates its own view of "who is primary now" and reports that to clients that ask it, so applications configured to discover the primary through Sentinel (rather than a hardcoded address) automatically start talking to the newly promoted node.

Because the old primary's unacknowledged writes at the moment of failure are lost (replication is asynchronous, per Q16), Sentinel gives you automatic availability after a failure, not a guarantee of zero data loss during one. Running at least three Sentinels (an odd number, to avoid split-brain ties in the quorum vote) across separate failure domains is the standard production setup.

Interview Favorite

The line that shows real operational exposure: "Sentinel gives you automatic failover, not zero data loss - whatever writes hadn't replicated yet when the primary died are gone." Redis Cluster, when used, folds this same failure-detection-and-promotion responsibility into the cluster nodes themselves rather than needing separate Sentinel processes.

Q18. Pipelining for Throughput

ROI: ★★★☆☆ Frequency: Medium

Short Answer

Every Redis command normally pays one full network round trip: the client sends the command, waits for the server's reply, and only then sends the next one. If you need to issue a thousand small commands (say, warming a cache with a thousand keys), doing that one at a time means paying network latency a thousand times over, even though each command itself executes on the server in microseconds.

Pipelining removes the "wait for each reply" step: the client writes a whole batch of commands to the socket back-to-back without waiting for responses in between, and then reads all the responses off the socket afterward, in the same order the commands were sent. The server still processes them one at a time (Redis is still single-threaded for command execution), but the client no longer pays a round trip per command - it pays one round trip for the whole batch. This can turn a workload that was dominated by network latency into one dominated by actual server-side work, often a 10x or larger throughput improvement for bulk operations.

Pipelining is not a transaction: commands in a pipeline are not atomic as a group, and if one command in the middle fails, the others still execute independently. If you need atomicity across multiple commands, that is what MULTI/EXEC transactions or Lua scripting (Q19) are for; pipelining is purely a throughput optimization for the network layer. 

// Naive: N round trips
for (String id : ids) {
    redis.opsForValue().set("product:" + id, serialize(products.get(id)));
}

// Pipelined: 1 round trip for the whole batch
redis.executePipelined((RedisCallback<Object>) connection -> {
    for (String id : ids) {
        connection.set(("product:" + id).getBytes(),
                        serialize(products.get(id)));
    }
    return null;
});

Interview Gold Point

Frame it precisely: "pipelining collapses N round trips into 1, but the commands still execute independently on the server, so it buys throughput, not atomicity." Conflating pipelining with transactions is a common tell that a candidate hasn't actually used it under load.

Q19. Lua Scripting for Atomic Multi-Step Operations

ROI: ★★★★☆ Frequency: High

Short Answer

A lot of caching logic is "check something, then act on what you saw" - check a value before overwriting it, decrement a counter only if it is still positive, atomically move an item between two sets. Doing the "check" and the "act" as two separate round trips from the client is inherently racy: another client's command can slip in between your read and your write.

Redis solves this by letting you send a small Lua script to the server with EVAL, and the entire script runs atomically as a single operation - Redis will not process any other client's command while your script is executing. This turns a "read, decide, write" sequence that would otherwise need a distributed lock into a single, guaranteed-atomic round trip. It also cuts network overhead the same way pipelining does, since multiple logical steps become one request.

The classic textbook example is a rate limiter or a distributed lock's safe release: you should only delete a lock key if it still holds the token your process set, otherwise you risk deleting a lock that another process has since legitimately acquired after your own lock expired. Expressing "get, compare, then conditionally delete" as three separate Redis calls is racy; expressing it as one Lua script is not. 

-- Only delete the lock if we're still the owner (safe unlock)
if redis.call("get", KEYS[1]) == ARGV[1] then
    return redis.call("del", KEYS[1])
else
    return 0
end

Common Mistake

Releasing a distributed lock with a plain DEL after checking the value in a separate command. Between your `GET` and your `DEL`, the lock could have expired and been re-acquired by someone else - your `DEL` would then delete a lock you no longer own. The Lua script above is the standard fix, and recognizing why the two-step version is unsafe is exactly the kind of detail senior interviewers probe for.

SECTION 7 - REDIS AS MORE THAN A CACHE

Q20. Distributed Locks with Redis (SET NX PX)

ROI: ★★★★☆ Frequency: High

Short Answer

When multiple service instances might try to do the same exclusive piece of work at once - processing the same scheduled job, charging the same order - you need a lock that all instances agree on, and a single in-process lock (a synchronized block) only coordinates threads within one JVM. Redis is a natural place to put a cheap distributed lock because a single command can atomically create a key only if it doesn't already exist.

The idiom is SET lock:key unique-token NX PX 5000: NX means "only set if the key does not already exist" (so only one caller can ever successfully acquire it), and PX 5000 attaches a 5-second expiry so the lock is automatically released even if the holder crashes before explicitly unlocking, preventing a permanently stuck lock. The unique token (a UUID per acquisition attempt) is what makes the safe-release script from Q19 possible: only the holder that set that exact token is allowed to delete the key.

This single-node lock is good enough for most practical purposes - preventing duplicate cron execution, coordinating a rare exclusive operation - where the cost of an occasional double-execution is low. It is explicitly not a strong enough guarantee for anything where a violated lock causes real financial or correctness damage, which is exactly what Q21 gets into. 

String token = UUID.randomUUID().toString();
Boolean acquired = redis.opsForValue()
        .setIfAbsent("lock:job:daily-report", token, Duration.ofSeconds(5));

if (Boolean.TRUE.equals(acquired)) {
    try {
        runDailyReportJob();
    } finally {
        // release only if we still own it (Lua script from Q19)
        releaseLockIfOwner("lock:job:daily-report", token);
    }
}

Interview Gold Point

Name the failure mode this design accepts: the lock's TTL is a guess about how long the work will take. If the work runs longer than the TTL, the lock expires while the holder is still "working," a second instance acquires it, and now two instances are doing the same exclusive work concurrently. That single sentence is usually the bridge straight into the Redlock discussion.

Q21. Redlock and Its Critiques

ROI: ★★★☆☆ Frequency: Senior Favorite (System Design)

Short Answer

Redlock is Redis's own proposed algorithm for a stronger distributed lock: instead of trusting a single Redis node, the client tries to acquire the same lock key (with the same token and TTL) against N independent Redis instances (typically 5), and only considers the lock acquired if it got a majority (N/2 + 1) to agree within a tight time budget, accounting for the time already spent trying. The idea is that a single node crashing or having its clock skew shouldn't compromise the lock, because a majority of independent nodes would have to be wrong at once.

Redlock is also one of the more famous disagreements in distributed systems literature. Martin Kleppmann's widely cited critique argues that Redlock is unsafe as a "correctness" lock (the kind you'd use to guarantee, say, that only one process ever writes to a shared file) because it depends on real-time clock and process-pause assumptions that don't hold in practice: a client can acquire the lock, then experience a long GC pause or an unexpectedly slow network write, have its lock silently expire on the server side, and then resume and act as if it still safely holds the lock - all while another client has since legitimately acquired it. The lock's safety, in that critique, ultimately rests on assumptions about wall-clock time and process scheduling that a distributed system can't actually guarantee.

The practical senior answer is a spectrum, not a binary. A single-node Redis lock (Q20) is fine for "best-effort, avoid wasteful duplicate work" scenarios. Redlock across multiple nodes raises confidence further but is still not a substitute for a real consensus system (ZooKeeper, etcd, or a database-level fencing token) when correctness genuinely cannot be violated - for example, ensuring two processes never simultaneously write to the same file on shared storage. The universal mitigation regardless of lock implementation is a fencing token: a monotonically increasing number handed out with each lock acquisition, which the protected resource itself checks and rejects if it sees an older token arrive after a newer one, closing the gap that clock and pause assumptions leave open.

Interview Gold Point

Being able to state both sides - "Redlock raises the bar over a single-node lock, but Kleppmann's critique is that it still isn't safe for hard correctness guarantees because it leans on clock and pause assumptions, and the real fix for that class of problem is a fencing token, not more Redis nodes" - is one of the strongest signals of distributed-systems depth this chapter can test for.

Q22. Rate Limiting with Redis

ROI: ★★★★★ Frequency: Very High

Short Answer

Rate limiting needs a piece of shared, fast-to-update state - "how many requests has this key made recently" - visible to every instance behind a load balancer, which is exactly what Redis is good at. There are a few standard algorithms, each with a different accuracy/complexity trade-off.

Fixed window is the simplest: INCR a counter keyed by user and current minute, and reject once it exceeds the limit; the counter naturally expires via a TTL set on first increment. It is cheap but has a boundary bug - a burst right at the end of one window and right at the start of the next can let through nearly double the intended limit within a short span straddling the boundary. Sliding window log stores a timestamp per request in a Redis sorted set (ZSet), trims entries older than the window on each check, and counts what remains - accurate, but memory cost scales with request volume. Sliding window counter approximates the sliding log cheaply by weighting the previous fixed window's count based on how far into the current window you are, giving most of the accuracy of a sliding log at fixed-counter cost. Token bucket models a bucket that refills at a steady rate and is debited per request, naturally allowing controlled bursts up to the bucket's capacity while enforcing a steady average rate - Redis implements this efficiently with INCR/EXPIRE or a small Lua script for atomicity. 

-- Atomic fixed-window rate limit in one round trip (Lua)
local current = redis.call("INCR", KEYS[1])
if current == 1 then
    redis.call("EXPIRE", KEYS[1], ARGV[1]) -- window size in seconds
end
if current > tonumber(ARGV[2]) then       -- limit
    return 0 -- rejected
end
return 1     -- allowed

Common Mistake

Implementing "check the counter, then increment it" as two separate Redis calls from application code. That is racy under concurrent requests for the same key - both can read the count before either increments, letting more requests through than the limit allows. Doing the check-and-increment atomically, either via `INCR` alone (as above) or a Lua script for anything more elaborate than a single counter, is the correct approach.

Q23. Redis Pub/Sub

ROI: ★★★☆☆ Frequency: Medium

Short Answer

Redis Pub/Sub lets a publisher send a message to a named channel, and every client currently subscribed to that channel receives it in real time. It's the simplest possible fan-out mechanism: no setup beyond subscribing, extremely low latency, and no persistence overhead because Redis never stores the message anywhere.

That last point is also its defining limitation: Pub/Sub is fire-and-forget. If a subscriber is disconnected, restarting, or simply hasn't subscribed yet when a message is published, that message is gone forever - there is no backlog, no replay, no delivery guarantee whatsoever. This makes Pub/Sub a good fit for the exact use case that shows up earlier in this chapter (Q11): broadcasting a "this key changed, evict your local L1 copy" invalidation notice to every instance, where missing an occasional message just means a slightly longer staleness window rather than data loss, since the source of truth (the database, or L2) is unaffected either way.

It is the wrong tool the moment you need "every message must be processed, even if a consumer was briefly down" - for that, you want a durable log with consumer offsets, which is exactly what Redis Streams (Q24) or a real message broker provides.

Interview Favorite

The one-line test to apply: "if losing a message during a brief subscriber outage is acceptable, Pub/Sub is fine; if it isn't, you need Streams, Kafka, or a queue with acknowledgment and persistence." Cache invalidation broadcasts tolerate the former; order processing does not.

Q24. Redis Streams as a Message Broker vs Kafka/RabbitMQ

ROI: ★★★★☆ Frequency: High (System Design)

Short Answer

Redis Streams is an append-only log data structure (XADD/XREAD/XRANGE) built on top of Redis, and unlike Pub/Sub it persists entries and supports consumer groups: multiple consumers can cooperatively read a stream, each message delivered to exactly one consumer in the group, with acknowledgment (XACK) and the ability to inspect and reclaim messages that were delivered but never acknowledged (a consumer crashed mid-processing). That combination - persistence, consumer groups, at-least-once delivery - makes it a genuine lightweight message broker, not just a cache feature.

Where Streams stops being a good idea is exactly where Kafka or RabbitMQ's core strengths live. Kafka is built for very high sustained throughput with log compaction and long, cheap retention measured in days or weeks, replicated durably across brokers, and a rich ecosystem of stream-processing tooling (Kafka Streams, Connect) - Redis Streams retention is bounded by how much you're willing to keep in memory (or Redis's persistence to disk, which is comparatively much slower and less battle-tested for this exact workload than Kafka's log design). RabbitMQ offers much richer routing semantics (exchanges, topic/fanout/direct routing, per-message priority, dead-letter queues) that Streams simply doesn't have. Streams' honest niche is: you're already running Redis, you need durable pub/sub with consumer groups and moderate volume, and standing up a whole separate Kafka or RabbitMQ cluster would be over-engineering for the actual throughput and retention you need.

Aspect Redis Streams Kafka RabbitMQ
Primary strength Lightweight, already-have-Redis simplicity Massive sustained throughput, long retention Rich routing, per-message flexibility
Retention Bounded by memory/persistence config Days to weeks, cheap and durable Until consumed (queue-based)
Delivery semantics At-least-once via consumer groups At-least-once (exactly-once with care) At-least-once, flexible ack modes
Bad fit when Need very high volume + long retention Need complex per-message routing Need huge sustained throughput

Interview Gold Point

The senior framing: "Streams is a real message broker feature of Redis, not a toy - but reaching for it because 'we already have Redis' instead of because it actually fits the throughput and retention needs is a common overcorrection. If the workload looks like Kafka's sweet spot, use Kafka." Knowing when not to use the tool you already have running is the harder half of this question.

SECTION 8 - HTTP & CDN CACHING

Q25. CDN Caching and How It Composes with Application-Level Caching

ROI: ★★★★☆ Frequency: High

Short Answer

Everything discussed so far in this chapter - Caffeine, Redis - is caching inside your application's infrastructure. A CDN (Content Delivery Network) is a caching layer that sits in front of all of that, at edge locations geographically close to the end user, and it caches the actual HTTP response, not a database row or a domain object.

A full request path for a cacheable response typically looks like: browser (may have its own local HTTP cache) -> CDN edge node (may serve the response directly, never reaching your infrastructure at all) -> load balancer -> application -> application-level cache (Redis/Caffeine) -> database. Each layer exists to absorb load from the layer behind it, and each one is checked in order: a CDN hit means the request never even reaches your servers, which is the cheapest possible outcome both in latency and in infrastructure cost; only a CDN miss reaches the application, where the app-level cache then tries to avoid hitting the database.

The distinction that matters for interviews is what each layer is good at. CDNs are excellent for content that is the same for every user - static assets, and increasingly, public API responses or fully rendered pages that don't vary per user. They are a poor fit for personalized or per-user data (an account dashboard), which is exactly what application-level caching with a proper cache key (Q31) is for. A mature system uses both, deliberately, at different layers of the same request.

Interview Gold Point

State the layering explicitly rather than treating "caching" as one thing: "the CDN protects my origin from ever being hit for content that doesn't vary by user; Redis and Caffeine protect my database from being hit for content that does vary by user but is still expensive to compute." That distinction is what separates someone who has designed a real request path from someone who has only used @Cacheable.

Q26. HTTP Caching Headers: Cache-Control

ROI: ★★★★☆ Frequency: High

Short Answer

Cache-Control is the HTTP response header that tells every cache along the path - the browser, a CDN, an intermediate proxy - how and for how long it is allowed to reuse a response without going back to the origin. It is a set of directives, and the ones that come up constantly in interviews are worth knowing precisely rather than approximately.

max-age=N says the response is fresh for N seconds from when it was generated - conceptually the HTTP equivalent of a cache's TTL. no-cache is confusingly named: it does not mean "don't cache," it means "cache this, but revalidate with the origin (typically via ETag, Q27) before reusing it every single time," so it is about mandatory revalidation, not prohibition. no-store is the one that actually means "never cache this anywhere," appropriate for genuinely sensitive responses. private means only the end-user's own browser may cache the response - a shared cache (a CDN sitting between many users) must not store it, which matters enormously for personalized responses. public is the opposite: any cache, shared or private, may store it. s-maxage is like max-age but applies specifically to shared caches (CDNs, proxies), letting you set a different freshness lifetime for the CDN than for the end user's own browser.

Directive Meaning
max-age=N Fresh for N seconds from generation
no-cache May cache, but must revalidate before every reuse
no-store Never cache anywhere, by any cache
private / public Only end-user's browser / any shared cache may store it
s-maxage=N max-age override specifically for shared (CDN/proxy) caches

Common Mistake

Reading "no-cache" as "do not cache" in an interview answer. That single mix-up (it actually means "revalidate every time," while `no-store` is the true "never cache" directive) is a frequently used trap question precisely because so many engineers get it backwards from having only skimmed the header, never needed to rely on the distinction in production.

Q27. ETag & Conditional Requests

ROI: ★★★★☆ Frequency: High

Short Answer

An ETag is an opaque identifier (often a hash of the response body, or a version number) that the origin attaches to a response. It lets a cache that already holds a stale-by-TTL copy ask the origin "has anything actually changed since I last saw ETag X?" instead of blindly re-downloading the full response.

The flow is a conditional request: the client (or an intermediate cache) sends If-None-Match: <etag> along with its next request. If the resource hasn't changed, the origin responds with a bare 304 Not Modified and no body at all, and the cache is told it may keep serving its existing copy for another freshness period. If the resource has changed, the origin returns a normal 200 with the full new body and a new ETag. The win is bandwidth and origin CPU: revalidating is far cheaper than a full re-fetch, especially for large responses that change rarely.

This pairs naturally with Cache-Control: no-cache (Q26): "always check with me before reusing this, but checking is cheap because you can just send me the ETag and I'll usually just say 304." It's also the standard mechanism read-through caches (Q29) use internally to keep a long-lived cached copy honest without re-fetching the whole payload on every check. 

Client -> Server: GET /catalog/42
                   If-None-Match: "a1b2c3"

Server -> Client: 304 Not Modified   (unchanged: reuse cached body)
              -- or --
Server -> Client: 200 OK
                  ETag: "d4e5f6"
                  <new body>

Interview Gold Point

The precise framing: "ETag plus a conditional request lets a cache confirm freshness without paying the cost of re-downloading the payload - it turns a cache miss into a cheap 304 instead of a full re-fetch." That's a meaningfully different (and stronger) answer than just saying "ETag is for cache validation."

Q28. The Vary Header and Cache Key Fragmentation

ROI: ★★★☆☆ Frequency: Medium

Short Answer

A shared cache (a CDN, a reverse proxy) normally keys its cached responses purely by URL. That breaks the moment the same URL can legitimately produce different responses for different requests - the classic examples are content negotiation by Accept-Language (a localized homepage) or by Accept-Encoding (a gzip-compressed body vs. an uncompressed one), or an API that returns a different shape based on a custom header.

Vary tells the cache which request headers were part of the decision that produced this particular response, so the cache must fold those header values into its cache key rather than caching just by URL. Vary: Accept-Language means the cache must store a separate copy per distinct Accept-Language value it sees, and only serve a cached response back to a request whose relevant header matches the one that produced it.

The trade-off to be aware of is cache key fragmentation: the more headers you list in Vary, and the more distinct values those headers actually take across real traffic, the more separate cached copies you need, which directly lowers your effective hit ratio. Vary: User-Agent is a commonly cited anti-pattern for exactly this reason - real-world User-Agent strings are so varied that it can fragment the cache into effectively one entry per visitor, destroying the benefit of caching almost entirely.

Common Mistake

Adding a header to `Vary` without checking how many distinct values that header actually takes across real traffic. `Vary: Accept-Language` with a handful of supported locales is healthy; `Vary` on a header with effectively unbounded cardinality quietly turns a shared cache into a private one-copy-per-request cache, and the resulting drop in hit ratio is easy to miss unless you're watching the metric.

Q29. Read-Through vs Cache-Aside, Precisely Contrasted

ROI: ★★★★☆ Frequency: High

Short Answer

Cache-aside (Q2) and read-through solve the same problem - populate the cache lazily on a miss - but they differ in who owns the miss-handling logic, and interviewers use this distinction to check whether a candidate actually understands the pattern or is just pattern-matching the word "lazy loading."

In cache-aside, the application code is directly responsible: it checks the cache, and on a miss it explicitly calls the database itself and explicitly writes the result back into the cache. The caching library or infrastructure has no awareness of where the data comes from - it is purely a key-value store the application chooses to consult first.

In read-through, the cache itself is configured with a loader (a data-access function) and sits transparently in front of the data source. The application only ever asks the cache for a value; on a miss, the cache itself invokes the configured loader, populates itself, and returns the result - the application code never sees or writes the miss-handling branch at all. Caffeine's Cache.get(key, loadingFunction) and Spring's @Cacheable (Q10) are both read-through in spirit: the caller writes one line and the cache-populate-on-miss logic is hidden inside the abstraction, whereas raw cache-aside is the "if (cache.get() == null) { db call; cache.put() }" pattern spelled out by hand.

The practical implication: read-through centralizes miss-handling (one loader function, reused everywhere, and naturally gets request-coalescing for free, as in Q9), while hand-rolled cache-aside means every call site has to remember to implement the miss path and the invalidation correctly, which is exactly the discipline problem Q2 warns about.

Aspect Cache-Aside Read-Through
Who fetches on a miss Application code, explicitly The cache itself, via a configured loader
Where miss-handling logic lives Repeated at every call site Centralized once, in the loader
Example Hand-written if(null)-then-fetch-then-put Caffeine's get(key, loader); @Cacheable

Interview Gold Point

Many candidates use "cache-aside" and "read-through" interchangeably. The differentiator is naming who owns the fetch: "cache-aside is application-owned miss handling; read-through delegates that to the caching layer via a loader." Being able to also say that @Cacheable is a read-through implementation, despite Spring's own docs describing it loosely as cache-aside, shows you've thought about the mechanism, not just the label.

Q30. Stale-While-Revalidate as an HTTP Directive

ROI: ★★★☆☆ Frequency: Medium

Short Answer

Q9 introduced stale-while-revalidate as a general anti-stampede technique. HTTP formalizes it as an actual Cache-Control extension directive: Cache-Control: max-age=60, stale-while-revalidate=30.

This tells a supporting cache "treat this response as fresh for 60 seconds; for an additional 30 seconds after that, you may still serve the stale copy immediately while asynchronously re-fetching a fresh one in the background for next time." The user who happens to hit the cache during that 30-second revalidation window gets an instant response (from the stale copy) rather than waiting on a fresh fetch, and the cache is left warm again for the next request.

It solves exactly the coordinated-miss problem from Q9, but at the HTTP/CDN layer instead of the application-cache layer: without it, the instant a response's max-age expires, every concurrent request for that URL would otherwise trigger its own fetch to the origin at once. With it, the first request after expiry gets the stale copy immediately and quietly triggers exactly one background revalidation, and every other concurrent request during that window also just gets the (still being refreshed) stale copy, so the origin sees at most one fetch instead of a stampede.

Interview Gold Point

Tie it back explicitly: "stale-while-revalidate is the same idea as the anti-stampede technique from earlier in this chapter, just expressed as a standard HTTP directive that CDNs and browsers understand natively, rather than something you have to hand-build with a Redis lock." Drawing that connection across layers is a strong signal of synthesized understanding rather than memorized facts.

SECTION 9 - CACHE KEY DESIGN, NEGATIVE CACHING & WARMING

Q31. Cache Key Design: Namespacing & Avoiding Collisions

ROI: ★★★★☆ Frequency: High

Short Answer

A cache key is a contract, not just a string, and getting it wrong causes bugs that are unusually hard to trace because the symptom is "wrong data appears," not a crash. The two failure modes to design against are collisions between unrelated data and ambiguity about what a given cached value actually represents.

The standard convention is a colon-delimited namespace hierarchy: {service}:{entity}:{id}:{variant}, for example catalog:product:42:en-US or orders:summary:user:789. The service prefix matters most when multiple applications share one Redis instance (common in smaller organizations to save infrastructure cost) - without it, a "user:123" key from the Orders service and a "user:123" key from the Notifications service silently overwrite each other, because Redis has one flat keyspace with no built-in tenant isolation. The entity and id make the key's purpose self-documenting to anyone debugging it later, and the variant suffix (locale, currency, API version) prevents accidentally serving one variant's cached data for a request that actually wanted a different one.

A related discipline is never building a key by directly concatenating unsanitized user input - a product id containing a colon or an unexpected delimiter can accidentally reshape the key's structure. Using a fixed, well-documented key format (ideally generated by a single shared helper function rather than string concatenation scattered across the codebase) closes off both of these classes of bug at once. 

// Good: namespaced, self-documenting, variant-aware
String key = String.format("catalog:product:%s:%s", productId, locale);

// Risky: shared keyspace, no service prefix, no variant --
// collides with any other service's "user:123" key, and silently
// serves the wrong locale's cached copy if reused across variants
String key = "user:" + userId;

Common Mistake

Treating cache keys as an afterthought and letting each team or each call site invent its own ad hoc format against a shared Redis instance. The fix is boring but effective: one small shared key-building utility per service, a documented naming convention across the organization, and a hard rule that no service ever guesses at another service's key format directly.

Q32. Versioning Keys on Schema Change

ROI: ★★★☆☆ Frequency: Medium

Short Answer

When the shape of a cached object changes - a new field is added, a field's type changes, an enum gains a value your old deserializer doesn't know about - old cached entries serialized under the previous shape are still sitting in Redis after you deploy the new code. Deserializing them with the new code can throw, silently drop the new field's default, or worse, misinterpret bytes in a way that doesn't throw at all.

The standard fix mirrors the versioned-key idea from Q4's discussion of static assets: embed a schema version in the key itself, for example product:v2:42 instead of product:42. When you ship a breaking change to the cached shape, you bump the version segment to v3, and every subsequent read simply misses (because no v3 keys exist yet), naturally repopulating with the new shape. The old v2:* entries are never touched again and just age out via their existing TTL - there is no need to write a migration script or explicitly flush anything, and, crucially, there's no risk of a deploy racing a manual cache flush and momentarily deserializing old-shape data with new-shape code.

The trade-off is a guaranteed full cold cache immediately after a version bump, identical in shape to any cache-flush cold start (Q35) - which is a completely acceptable, predictable cost for the safety of never risking a deserialization mismatch in production.

Interview Gold Point

The senior instinct here is preferring a predictable, bounded cost (a cold cache for a while after deploy) over an unpredictable one (a deserialization exception, or silent data corruption, in production traffic). Say that trade-off explicitly rather than just describing the version-in-key mechanic.

Q33. Negative Caching

ROI: ★★★☆☆ Frequency: Medium

Short Answer

Most of this chapter assumes the interesting case is caching a value that exists. Negative caching is the deliberate choice to also cache the absence of a value - the fact that a lookup returned "not found" - for a short period, rather than treating every not-found lookup as uncacheable and hitting the database every single time.

Without it, a key that genuinely doesn't exist (a typo'd product id, a user probing for valid IDs, a client with a stale reference to a deleted record) causes a full database round trip on every single request, because a naive cache-aside implementation only populates the cache on a hit and does nothing on a "not found." If that non-existent key is requested repeatedly - which happens more than it sounds like it should, especially under scraping, retry loops on a client bug, or enumeration-style abuse - it becomes a permanent, un-cacheable hole that always reaches the database, defeating the entire purpose of the cache for that access pattern.

The fix is to cache a sentinel value (a specific marker object, or simply an empty result) for "not found" lookups too, typically with a noticeably shorter TTL than a real hit would get, since you want a newly created record to become visible reasonably quickly rather than being masked by a stale "not found" cached from moments before it was created. The trade-off to name explicitly: negative caching means a record created immediately after a failed lookup can appear to not exist for up to that short TTL, which is almost always an acceptable cost against the alternative of an unbounded amplification of database load from repeated not-found lookups. 

Product cached = cache.get(id);
if (cached != null) {
    return cached == NOT_FOUND_SENTINEL ? null : cached;
}
Optional<Product> fromDb = productRepository.findById(id);
if (fromDb.isPresent()) {
    cache.put(id, fromDb.get(), Duration.ofMinutes(10));
    return fromDb.get();
} else {
    cache.put(id, NOT_FOUND_SENTINEL, Duration.ofSeconds(30)); // shorter TTL
    return null;
}

Interview Gold Point

The scenario that makes this concrete: an attacker or a buggy client enumerating IDs that mostly don't exist can otherwise turn your cache into a complete no-op and hammer the database with a request pattern the cache was specifically supposed to absorb. Negative caching closes that gap, and naming it unprompted is a strong signal you've thought about caching from an abuse/resilience angle, not just a happy-path performance angle.

Q34. Cache Warming / Pre-Population Strategies

ROI: ★★★☆☆ Frequency: Medium

Short Answer

Every cache described so far in this chapter populates lazily: the first request for a key is always a miss. That's fine most of the time, but it's a real problem right after a fresh deploy, a cache flush, or a new instance joining the fleet with a cold local L1 - if the very first wave of real traffic all arrives as misses simultaneously, you get exactly the coordinated-load problem from Q9, just triggered by an operational event instead of a TTL expiry.

Cache warming means deliberately populating the cache with known-hot keys before real traffic starts arriving, rather than waiting for organic misses to do it. Common approaches: a warmup job that runs at deploy time and pre-loads the top N most-requested keys (from yesterday's access logs or a maintained "hot keys" list) directly into the new cache; replaying a sample of recent real traffic against the new instance in the background before it receives live traffic (common in blue-green deploys); or, for a distributed L2 cache that already has warm data, simply making sure a newly started instance's L1 doesn't need warming at all because it always falls through to the still-warm L2.

The judgment call is knowing what's actually worth warming: warming every possible key is often not worth the engineering effort, but warming the small set of keys that represent a disproportionate share of traffic (the classic long-tail distribution, where 1% of products account for a huge fraction of catalog page views) gives most of the benefit for a fraction of the cost.

Interview Gold Point

The framing that shows production experience: "warming isn't about eliminating every cold cache miss, it's about making sure the deploy-time or restart-time cold cache doesn't coincide with a traffic spike large enough to turn ordinary misses into a database-threatening stampede." Tie it explicitly back to Q9 rather than presenting it as an unrelated technique.

Q35. Cold-Start Cache-Miss Storms After a Deploy or Cache Flush

ROI: ★★★★☆ Frequency: High

Short Answer

This is the specific incident scenario that cache warming (Q34) exists to prevent, and it's worth understanding on its own because it's a common "tell me about a production incident" interview prompt: a deploy that rolls out a new version of the caching layer, an accidental full flush of Redis (FLUSHALL run against the wrong environment is a real, recurring war story), or a large batch of instances restarting together (an auto-scaling event, a Kubernetes rolling update with an aggressive rollout speed) can all instantly empty a cache that a live production system was depending on to absorb the bulk of its read traffic.

The moment that happens, every request that would have been a cache hit becomes a cache miss simultaneously, and all of that traffic - which the database was never sized to handle directly, because the cache's entire job was to keep it from ever seeing that volume - arrives at the database at once. This is functionally identical to the cache stampede in Q9, except the trigger is an operational event affecting the whole cache rather than one hot key's TTL expiring, which makes it both rarer and, when it does happen, far more severe because it affects every key at once instead of one.

Mitigations layer on top of everything already covered: cache warming before cutting traffic over to a fresh instance; a circuit breaker or request-shedding layer in front of the database so a sudden traffic multiplication degrades gracefully (serving errors or a fallback to some requests) rather than taking the database down entirely, which would then also break the write-through path that could otherwise repopulate the cache; and, operationally, restricting who can run destructive commands like `FLUSHALL` against production, and rolling deploys/restarts gradually rather than all at once so the surviving cache instances (or a warm L2 behind a cold L1 fleet) can still absorb load while the rest catch up.

Interview Gold Point

The strongest answer here connects three things this chapter already covers: "a cold-start storm is a full-cache version of the stampede in Q9, cache warming (Q34) is the preventive fix, and a circuit breaker plus graceful degradation (Q46) is the reactive fix if it happens anyway." Interviewers who ask "tell me about a caching incident" are specifically listening for whether you reach for exactly this kind of layered answer instead of a single silver bullet.

Q36. Choosing TTLs Per Data Type

ROI: ★★★☆☆ Frequency: Medium

Short Answer

A single TTL applied uniformly across an entire system is a sign the caching strategy wasn't actually designed, just defaulted. The right TTL for a piece of data is a function of how often it changes, how expensive it is to recompute, and how costly it is to the business if it's stale for that long - and those three factors are wildly different across data types in the same system.

Rarely-changing, expensive-to-compute reference data (a category tree, a pricing rule set) can tolerate a long TTL - hours - because staleness risk is low and the recompute cost saved is high. A product's stock count or price needs a short TTL, seconds to low minutes, because staleness there has direct business impact (overselling, showing a wrong price). Anything security- or session-relevant (a permission check, an auth token's validity) generally shouldn't rely on TTL alone at all and needs explicit invalidation the instant the underlying grant changes, since a stale "yes you're authorized" is a security bug, not a minor inconvenience. Highly volatile, cheap-to-recompute data (a live view counter) might not be worth caching for more than a few seconds, or might be better served by a different mechanism entirely (an in-memory counter flushed periodically) rather than a traditional cache.

The practical output of this thinking is a small, explicit policy table maintained alongside the codebase - not a single constant named DEFAULT_TTL reused everywhere - so that a new engineer adding a new cached value is prompted to actually think about which bucket it falls into rather than copy-pasting whatever TTL happened to be nearby.

Data type Change frequency Staleness cost Suggested TTL
Category tree / reference data Very low Low Hours
Product price / stock Moderate High (business impact) Seconds to a few minutes
Auth/permission state Low but security-critical Very high Explicit invalidation, not TTL alone
Live counters/metrics Very high Low (approximate is fine) Seconds, or a different mechanism entirely

Common Mistake

Copy-pasting a `Duration.ofMinutes(10)` from an existing `@Cacheable` annotation onto a brand-new cached value without asking whether ten minutes of staleness is acceptable for that specific data. The senior habit is treating TTL choice as a small design decision every time, not a default to inherit silently.

SECTION 10 - SESSION CACHING

Q37. Session Storage as a Caching Use Case

ROI: ★★★★☆ Frequency: High

Short Answer

A user's HTTP session (their logged-in identity, cart contents mid-checkout, in-progress multi-step form state) needs to be readable on essentially every request that user makes, which is exactly the access pattern caching is built for - except here the cached value often is the source of truth for that session's data, rather than a copy of something durably stored elsewhere. That distinction changes some of the trade-offs from earlier in this chapter: losing a cached product price just means a slightly slower next request; losing session data mid-checkout means the user's cart or login state is simply gone.

This is why session storage is usually treated with a heavier durability posture than a typical cache entry - either backed by a distributed cache configured with real persistence (Redis with AOF, Q8), or explicitly designed so the application can tolerate a session being lost occasionally (re-authentication, an empty cart) as an acceptable, bounded cost rather than a silent correctness bug. The choice of TTL also differs: a session's expiry is usually a genuine business rule (log the user out after 30 minutes of inactivity) rather than a staleness-tolerance decision, so the TTL is set by product requirements, not by cache-sizing considerations.

Interview Gold Point

Say the distinction plainly: "most of this chapter treats the cache as a copy of a source of truth that lives elsewhere; a session store often is the source of truth, which is why its durability and persistence configuration deserve more scrutiny than an ordinary read-through cache." That reframing is what separates a thoughtful answer from a rote "store sessions in Redis."

Q38. Sticky Sessions vs Externalized Session Store

ROI: ★★★★☆ Frequency: High

Short Answer

There are two fundamentally different ways to make sure a user's session data is available wherever their next request lands, and this decision has real implications for scaling, deployment, and failure behavior.

Sticky sessions keep the session in the memory of whichever application instance first handled that user, and configure the load balancer to route all of that user's subsequent requests back to the same instance (usually via a cookie or consistent hashing on client IP). This avoids any network hop to fetch session data - reads are as fast as an in-process cache because that's exactly what it is - but it directly reintroduces the in-process-cache weaknesses from Q5: that instance being restarted or redeployed wipes the session, and load balancing is no longer free to spread traffic evenly, since a user is pinned to one instance regardless of its current load.

An externalized session store (Redis-backed Spring Session, for example) keeps session data in a shared distributed store that every instance can read, so any instance can serve any user's request, the load balancer is free to balance purely on load, and a rolling deploy or instance crash doesn't lose anyone's session. The cost is the same one distributed caching always carries: a network hop per session read, and now the session store itself is a dependency whose availability directly gates every authenticated request in the system, making its own resilience (Q17's Sentinel, or a managed Redis with failover) a first-class concern rather than an afterthought.

Aspect Sticky Sessions Externalized Store (e.g. Redis)
Read latency In-process, fastest Network hop
Survives instance restart/deploy No Yes
Load balancing freedom Constrained (pinned per user) Full freedom
New single point of failure None additional The session store itself

Interview Gold Point

The modern default answer for most cloud-native systems is externalized session storage, precisely because it plays well with auto-scaling, rolling deploys, and container orchestration, none of which get along with sticky sessions. Say that as the default, but acknowledge sticky sessions still show up in legacy or simpler on-prem deployments where the operational simplicity of not running a shared session store is a deliberate trade.

Q39. Spring Session with Redis

ROI: ★★★★☆ Frequency: High

Short Answer

Spring Session is the piece that makes externalizing sessions to Redis nearly transparent to application code. Once spring-session-data-redis is on the classpath and configured, Spring replaces the container's default in-memory HttpSession implementation with one backed by Redis - existing code that calls request.getSession() and reads or writes session attributes keeps working unchanged, but the actual session data is now serialized into Redis under the hood instead of sitting in the servlet container's local memory.

This is what actually makes the externalized-session-store trade-off from Q38 practical to adopt without a rewrite: you get the "any instance can serve any user" property, and Spring Session further keeps sessions in sync across instances by using Redis Pub/Sub or keyspace notifications to propagate session expiration and destruction events (so, for example, an explicit logout on one instance correctly invalidates the session for requests that later land on a different instance).

The practical footguns are the same durability and sizing questions this chapter has already raised: session data should be reasonably small (large objects stuffed into the session serialize on every write, adding real latency and Redis memory pressure), and the Redis instance backing sessions needs the availability posture from Q38's discussion - if it's a single node with no replication, an outage there logs out or breaks every active session across the entire application simultaneously. 

@Configuration
@EnableRedisHttpSession(maxInactiveIntervalInSeconds = 1800) // 30 min
public class SessionConfig {
    // Spring Session transparently backs HttpSession with Redis;
    // existing request.getSession() code is unchanged.
}

Common Mistake

Storing large or frequently-mutated objects directly in the session (a full shopping cart with many line items, updated on every click) once it's Redis-backed, without considering that every session write now serializes and sends that whole object over the network. Keeping the session itself small - an id and a few flags - and storing the bulk of the data in a normal cache or database keyed by that id, scales far better.

Q40. What Should Never Go in a Shared Session Store

ROI: ★★★☆☆ Frequency: Medium

Short Answer

Once sessions live in a shared external store rather than isolated in one instance's process memory, it's worth being deliberate about what actually belongs there, because the failure modes of "this data leaked" or "this data was stale" are more severe for a shared store than for isolated in-memory state.

Highly sensitive raw secrets (a plaintext password, a full credit card number, a raw unencrypted API key) should never be placed in session data at all, session store or not - a session, wherever it lives, is not an appropriate place for anything that would be catastrophic if that Redis instance (or a misconfigured backup of it, or an operator with read access) were ever exposed. Large, rapidly-changing business objects (Q39's shopping-cart example) also don't belong there directly; store an identifier in the session and the actual data in a purpose-built cache or database table, both to control serialization cost and because that data likely needs its own consistency and durability story independent of session lifecycle. Anything that must survive strictly longer than the session's own lifetime (order history, a user's saved preferences) belongs in the database, not the session, since a session is explicitly designed to expire.

The general principle: a session should hold just enough to identify who the user is and a small amount of short-lived UI/flow state, with everything else looked up by that identity from its own properly-modeled store.

Interview Gold Point

The one-line test worth stating: "if this data would still need to exist after the session expires, or would be dangerous if this particular store were ever compromised, it doesn't belong in the session." That single heuristic covers most of the concrete examples an interviewer might probe for.

SECTION 11 - DEEPER CACHE CONSISTENCY PATTERNS

Q41. Cache-Then-DB Write Ordering Pitfalls

ROI: ★★★★☆ Frequency: High (Senior Favorite)

Short Answer

Q12 established that write-invalidate is generally safer than write-update, but even "delete the cache, then write the database" - which looks like the safe order at first glance - has a race that surprises people the first time they see it demonstrated concretely.

Consider two concurrent operations on the same key: a writer performing an update, and a reader performing a cache-aside read that happens to race with it. If the writer deletes the cache entry first and then writes the database, a reader that started just before the delete but reads the (still-old) database value just after the delete can repopulate the cache with the stale value - and it does so after the writer's delete already ran, so nothing evicts it again until the TTL. The system is left with a stale cache entry sitting indefinitely (or until TTL) right after what looked like a correctly-ordered write.

The safer discipline most production systems converge on is: write the database first, then delete the cache. This narrows the race window considerably (a reader would now have to read the pre-write database value and write it into the cache after the post-write delete has already run, which requires a much more precisely timed interleaving than the delete-then-write ordering above), but it does not eliminate the race entirely under replica lag, which is exactly what motivates the double-delete pattern in Q42.

Interview Gold Point

The concrete failure sequence - "reader starts, writer deletes cache, reader still reads stale DB row, reader repopulates cache with stale value, nothing ever evicts it again" - is worth being able to narrate step by step. Interviewers use this exact scenario to separate candidates who've internalized "write-invalidate is safe" as a slogan from those who understand the actual interleaving it's vulnerable to.

Q42. The Delayed Double-Delete Pattern in Depth

ROI: ★★★★☆ Frequency: High

Short Answer

Q12 introduced double-delete briefly; here is the mechanism in full, because interviewers who ask this expect the reasoning, not just the name. The pattern targets specifically the race where a straggling read - one that started before a write and reads from a lagging database replica - repopulates the cache with a stale value after the write's own invalidation has already run.

The sequence is: delete the cache key, perform the database write, then, after a short delay (long enough to reasonably exceed the replica's typical lag, and long enough for any read that was already in flight when the write started to have completed and potentially repopulated the cache with stale data), delete the cache key a second time. That second delete exists purely to clean up any stale value a straggling read managed to insert during the window between the first delete and the write actually being visible everywhere reads might come from.

The delay is typically implemented as a short asynchronous task (a delayed message, a scheduled job, or simply a background thread sleeping briefly) rather than blocking the write path on it, since the point is to protect future reads, not to slow down the write that's already completed correctly. The remaining honest caveat: this narrows the race window to something very unlikely rather than making it theoretically impossible - if the delay is shorter than some outlier read's actual duration, the race can still occur, just far more rarely. That's consistent with the overall philosophy of this chapter: caching consistency is about bounding the probability and duration of staleness, not eliminating it. 

cache.evict(key);                 // delete #1: clear the stale entry now
database.write(key, newValue);    // perform the write

scheduler.schedule(() -> {
    cache.evict(key);              // delete #2: catch any straggling
}, Duration.ofMillis(500));        // read that repopulated it meanwhile

Common Mistake

Treating double-delete as a guarantee rather than a probabilistic mitigation. The honest framing - "it makes the race window for a straggling stale read very small, not zero" - is the answer that reads as senior; claiming it fully solves cache consistency is the answer that reads as someone repeating a blog post without having reasoned through the timing themselves.

Q43. Why Write-Through With a Distributed Cache Still Isn't Race-Free

ROI: ★★★☆☆ Frequency: Medium

Short Answer

It's tempting to think write-through (Q3) sidesteps all of the consistency problems this chapter has been discussing, since the cache and the database are updated together as part of one logical write operation. In a distributed cache shared across multiple instances, that isn't quite true.

Two concurrent writers updating the same key can still interleave their cache and database writes out of order relative to each other: writer A writes the database, then writer B writes the database (B's value now correctly "wins" as the latest), but if their respective cache writes happen to be reordered by network timing so that A's cache write lands after B's, the cache ends up holding A's older value while the database correctly holds B's newer one - the two sources of truth disagree, and nothing about "write-through" per se prevents that, because write-through only guarantees the cache and database are updated together for a single write, not that concurrent writes to the same key stay ordered consistently across both.

The fixes are the same tools distributed systems reach for whenever ordering under concurrency matters: a version number or timestamp attached to each write, with the cache write including a conditional check ("only accept this write if its version is newer than what's currently cached"), or funneling writes to a given key through a single point of serialization (a per-key lock, or a single writer instance/partition responsible for that key) so concurrent writes to the same key can't race in the first place.

Interview Gold Point

The nuance to volunteer: "write-through keeps a single write's cache and database updates together, but it doesn't by itself impose an ordering guarantee across multiple concurrent writers to the same key - that needs versioning or serialized writes on top." This is one of the more advanced points in the chapter, and stating it unprompted signals real distributed-systems depth beyond the standard write-through/write-behind/write-around comparison.

Q44. Read-Repair & Reconciliation Jobs

ROI: ★★★☆☆ Frequency: Medium

Short Answer

Every pattern discussed so far tries to prevent the cache and the source of truth from ever disagreeing. Read-repair and reconciliation take the opposite, complementary stance: accept that despite your best invalidation logic, drift will occasionally happen anyway (a missed evict on some rarely-exercised write path, a bug, an operational mistake), and build a mechanism that detects and corrects it rather than assuming prevention is perfect.

Read-repair does this opportunistically, at read time: when a value is read from the cache, occasionally (at some sampling rate, not every single read, to keep the overhead low) also fetch the current value from the source of truth and compare. If they disagree, correct the cache immediately and, more importantly, log or alert on the mismatch, because a disagreement usually points to a real bug in an invalidation path somewhere that's worth finding and fixing, not just papering over. Reconciliation jobs take a scheduled, batch approach instead: a background job periodically walks a sample (or all) of cached keys, compares each against the source of truth, and corrects or evicts any that have drifted, independent of whether anyone happens to be reading them right now.

Neither of these replaces proper invalidation logic - they're a safety net, not a strategy - but a mature caching system in a large codebase, where dozens of engineers across teams can each introduce a write path that forgets to invalidate correctly, benefits enormously from having something that surfaces drift automatically rather than relying entirely on every invalidation path being written correctly forever.

Interview Gold Point

Position this correctly relative to everything else in the chapter: "TTL, explicit eviction, and versioning are the prevention layer; read-repair and reconciliation are the detection-and-correction layer for when prevention inevitably has a gap somewhere in a large system." Interviewers asking about "cache consistency at scale" are often specifically listening for whether a candidate thinks about detection, not just prevention.

SECTION 12 - PRODUCTION INCIDENT: CACHE OUTAGES & HOT KEYS

Q45. Case Study: A Redis Outage / Hot-Key Incident

ROI: ★★★★★ Frequency: Very High (System Design / Behavioral)

Short Answer

This is a common "walk me through a production incident" prompt, and even without having lived through the exact scenario, being able to reason through it convincingly is what's actually being tested. The setup: a service that reads Redis on essentially every request, with no fallback path coded for "what if Redis itself is unavailable," experiences a Redis outage - a node crash with no automatic failover configured (Q17 skipped), a network partition, or simply Redis being overwhelmed by one extremely hot key receiving a disproportionate share of traffic (a viral product, a celebrity's profile, a trending post).

Because the application code has no conditional path for "Redis call failed," every request that would normally hit the cache now either throws an exception that propagates up as a user-facing error, or blocks waiting on a timeout to that unresponsive Redis instance, consuming a thread or connection for the duration. If enough concurrent requests pile up waiting on those timeouts, the application's own thread pool or connection pool exhausts, and the incident escalates from "the cache is down" to "the whole application is down" - the exact cascading-failure shape covered for service-to-service calls elsewhere in this handbook, just with the cache itself as the failing dependency instead of a downstream service.

The postmortem-style fix, which is what an interviewer is really listening for, has three parts: put resilience around the cache call itself (a short timeout plus a circuit breaker, Q46) so a failing Redis doesn't consume the application's own resources; have an explicit fallback for what happens on a cache failure (usually: go straight to the database, accepting higher latency and load temporarily, rather than erroring); and address the specific trigger (add replication/Sentinel for node-failure resilience, or fix the hot-key problem specifically, Q48, if that's what caused the overload). Naming all three - resilience at the call site, a defined fallback behavior, and a root-cause fix - is what separates a strong answer from "we just restarted Redis."

Interview Gold Point

The single sentence that reframes the whole scenario correctly: "a cache is an optimization sitting in front of a source of truth, and a well-designed system should degrade to slower-but-correct when the cache disappears, not fail outright - if losing the cache takes down the whole service, the cache was accidentally load-bearing in a way it was never meant to be." That's the exact insight most incident postmortems in this space eventually arrive at.

Q46. Circuit Breaker Around the Cache & Graceful Degradation

ROI: ★★★★☆ Frequency: High

Short Answer

The general circuit breaker mechanics - CLOSED, OPEN, HALF-OPEN, tripping on a failure-rate threshold - are the same regardless of what's behind the breaker, and this handbook covers that pattern in full elsewhere for service-to-service calls. What's specific to applying it to a cache is what the OPEN state's fallback behavior should actually be, and why that answer is different (and simpler) than for a typical downstream service dependency.

For a normal downstream service call, there often isn't a good fallback beyond an error or a generic default, because that service usually holds data or does work nothing else can substitute for. For a cache sitting in front of a database, there almost always is a clean fallback: go straight to the database. That's precisely why cache-aside (Q2) degrades so gracefully on its own even without an explicit breaker - a cache client that simply treats a Redis timeout or connection error the same as a cache miss, and falls through to the database, gets most of this protection for free, as long as the timeout on that Redis call is short enough not to itself become the bottleneck.

Wrapping the cache client in an actual circuit breaker adds one further guarantee that "treat errors as misses" alone doesn't: once Redis is clearly down (failure rate over threshold), the breaker stops even attempting the call and fails fast to the fallback immediately, rather than paying a timeout on every single request while Redis is unresponsive. The database is now taking full traffic either way, but it's taking it at the application's normal request latency, not at "however long we wait for Redis to time out" latency stacked on top. 

@CircuitBreaker(name = "redisCache", fallbackMethod = "getProductFromDb")
public Product getProduct(String id) {
    return redisCache.get("product:" + id, Product.class);
}

private Product getProductFromDb(String id, Throwable t) {
    // Redis is down or the breaker is open: go straight to the
    // source of truth. Slower, but correct, and no thread pinned
    // waiting on an unresponsive cache.
    return productRepository.findById(id).orElseThrow();
}

Interview Gold Point

The key distinction to draw: "a circuit breaker around a typical service call usually has no great fallback; a circuit breaker around a cache almost always does - the database - which is exactly why cache-outage resilience is more tractable than a general service outage, as long as you've actually wired the fallback and a short timeout rather than assuming cache-aside's natural miss-handling covers you without one."

Q47. Local Fallback Cache When Redis Is Unreachable

ROI: ★★★☆☆ Frequency: Medium

Short Answer

Falling back to the database (Q46) is the safe, correct default when the distributed cache is unavailable, but it means the database now takes the cache's entire share of traffic for the outage's duration - which, for a database that was sized assuming a 95%+ cache hit ratio, can itself trigger a second failure on top of the first. A local fallback cache is a further layer of protection for exactly that scenario.

The idea is to keep a small, short-TTL in-process cache (Caffeine) alongside the normal Redis-backed path, populated opportunistically on every successful Redis read, purely as an emergency reserve - not as the multi-level L1/L2 architecture from Q11, which is about latency optimization in the normal case. When Redis becomes unavailable, the fallback path checks this local emergency cache before falling all the way through to the database: a slightly-stale local copy of frequently-accessed data is a far better outcome during an incident than every single request for that data reaching the database at once.

This trades a small amount of extra memory and code complexity (maintaining a second, rarely-exercised cache path) for meaningfully better behavior during the specific window of a distributed-cache outage. It's a defense-in-depth measure that most systems don't need until they've experienced the alternative once, which is why it tends to appear after an incident postmortem rather than in an initial design.

Common Mistake

Building this fallback cache but only testing the happy path, never actually simulating a Redis outage to confirm the fallback logic works end to end. A circuit breaker and a local fallback cache that have never been chaos-tested against a genuinely unreachable Redis are exactly the kind of code that turns out to have a bug the first time it's actually needed, during a real incident, when it matters most.

Q48. The Hot-Key Problem & Mitigations

ROI: ★★★★☆ Frequency: High (Senior Favorite)

Short Answer

A hot key is a single cache key receiving a wildly disproportionate share of a service's total traffic - a viral post, a celebrity's profile, a flash-sale product. This is a distinct problem from the cache stampede in Q9: a stampede is many different requests all missing at once when a key expires; a hot key is sustained overload from one specific key even while the cache is behaving completely normally and serving it correctly on every single request.

The problem is structural in Redis Cluster specifically (Q15): every request for that one key hashes to the same slot, which lives on exactly one node, so no amount of horizontally scaling the cluster helps - adding more nodes spreads out every other key, but the hot key's entire load still lands on a single node's single CPU core, which can genuinely saturate that one node while the rest of the cluster sits comfortably underutilized.

The standard mitigations: local caching of the hot key at the application layer (an in-process Caffeine cache with a very short TTL, even just a few seconds, for just that key) absorbs the bulk of the read traffic before it ever reaches Redis at all, since even a few seconds of local caching on a key receiving thousands of requests per second removes the overwhelming majority of that load from the shared cache. Key splitting / replication deliberately stores the same value under several key variants (product:42:copy0 through product:42:copy9) spread across different slots, and the application picks a variant at random (or round-robin) on each read, spreading what was one node's load across several. Client-side detection (tracking access frequency per key in the application, or using Redis's own hot-key detection tooling where available) is what identifies which keys need this special treatment in the first place, since applying key-splitting everywhere preemptively is unnecessary complexity for keys that were never actually hot.

Interview Gold Point

The distinction worth stating explicitly and unprompted: "a stampede is a timing problem - many keys or many requests colliding at one instant - and jitter or locking fixes it; a hot key is a distribution problem - one key's traffic exceeding what a single node or shard can serve - and no amount of cluster scaling helps until you either cache it locally or spread it across multiple keys." Conflating the two is a common but avoidable mistake.

Q49. Multi-Region Caching Considerations

ROI: ★★★☆☆ Frequency: Medium (System Design)

Short Answer

Everything in this chapter has implicitly assumed a single region. Once an application is deployed across multiple geographic regions for latency or disaster-recovery reasons, caching has to make an explicit choice about topology, because a single shared cache instance in one region defeats half the point of going multi-region in the first place - every request from a distant region would pay cross-region network latency just to check the cache, potentially costing more than the cache was saving.

The common pattern is a per-region cache: each region runs its own independent Redis (or Caffeine) cache, populated from that region's own traffic and its own (possibly regional read-replica of the) database. This keeps cache reads fast and local, at the cost of the same instances now having entirely independent, unsynchronized caches across regions - a write in one region does not automatically invalidate the cached copy sitting in another region, so cross-region staleness has to be bounded the same way single-instance L1 staleness was bounded in Q11: short TTLs, or an active cross-region invalidation broadcast (typically over the same event bus already carrying cross-region data replication, rather than a bespoke mechanism).

The practical guidance mirrors a theme from throughout this chapter: decide the acceptable staleness bound for cross-region cache consistency explicitly, as a product/business decision, rather than discovering it by accident during an incident. For most consumer-facing read-heavy data, "a write in Region A may take a few seconds to be reflected in Region B's cache" is a perfectly reasonable, explicit trade-off; for anything where a user could act on stale cross-region data in a way that causes real harm (inventory decisions during a flash sale sold globally), tighter cross-region invalidation, or routing that class of read back to a single authoritative region, is worth the added latency.

Interview Gold Point

Frame multi-region caching as "the L1/L2 staleness problem from Q11, at a larger geographic scale, with the same two tools - short TTLs or active invalidation - just now bounded by cross-region network latency instead of intra-datacenter latency." Recognizing it as the same underlying trade-off at a different scale, rather than a wholly new problem, is the mark of someone who has internalized the chapter's core ideas rather than memorized isolated facts.

SECTION 13 - ADVANCED CACHE SIZING & CAPACITY PLANNING

Q50. Estimating Working-Set Size

ROI: ★★★★☆ Frequency: High

Short Answer

Q14 covered monitoring an already-running cache; sizing it correctly in the first place - before it exists, or before a capacity-planning conversation with infrastructure - starts with estimating the working set: the set of distinct keys that are actually accessed frequently enough to be worth keeping resident, as opposed to the theoretical full size of every key that could ever exist.

The estimation approach: start from the access-frequency distribution of the data (most real-world traffic is heavily skewed - a Zipfian or similar long-tail curve, where a small fraction of keys account for the large majority of requests), and identify roughly how many distinct keys are needed to cover your target hit ratio. If 5,000 distinct products account for 95% of all catalog page views even though the full catalog has 2 million products, your working set for a 95% hit-ratio target is close to 5,000 entries, not 2 million - trying to size the cache for the full catalog wastes enormous memory for very little additional hit-ratio benefit, since that long tail is, by definition, rarely accessed.

In practice this data comes from either historical access logs (if the system already exists) or a reasoned estimate from the product's expected usage pattern (if sizing a brand-new system before launch), and it should be revisited periodically - a working set is not static, and a change in product behavior (a new recommendation algorithm surfacing more of the long tail, a marketing campaign driving traffic to previously-cold items) can shift it meaningfully.

Interview Gold Point

The key mental model to state: "size the cache for the working set implied by your traffic's access distribution and target hit ratio, not for the full size of the underlying dataset - for most real-world skewed access patterns, those two numbers can differ by orders of magnitude." That's a materially stronger answer than "make it as big as you can afford."

Q51. Memory Overhead Per Entry (Caffeine vs Redis)

ROI: ★★★☆☆ Frequency: Medium

Short Answer

"How many entries fit in X gigabytes" is never simply (memory) / (size of the value), because every cache entry carries bookkeeping overhead beyond the raw value bytes, and that overhead can dominate for small values.

For Caffeine, each entry effectively lives inside a concurrent hash map node plus Caffeine's own metadata for its eviction policy (the W-TinyLFU frequency sketch, access/write timestamps for time-based expiry, references for the LRU-like admission window) - for genuinely small values (a short string, a boolean flag), this per-entry overhead can be a substantial multiple of the value's own size, meaning the real capacity of a "10,000 entry" cache in terms of memory footprint depends heavily on what's actually being cached, not just the entry count.

For Redis, every key also carries overhead beyond the value: the key string itself, internal object headers, and structure-specific overhead that varies by data type (a hash with many small fields has substantially more per-field overhead than a single string value of the same total byte size). This is precisely why Redis's own documentation recommends techniques like hashing many small related fields together under one key (using a Redis hash) instead of storing each as its own top-level key, when the values are small - it can meaningfully reduce total memory overhead by amortizing the per-key bookkeeping cost across many fields instead of paying it once per field.

The practical takeaway for capacity planning: when sizing a cache for millions of small entries, measure actual memory usage with representative data (Redis's MEMORY USAGE command, or a load test against Caffeine with recordStats()) rather than trusting a back-of-envelope calculation based purely on value size, because the overhead-to-value ratio for small entries can make that calculation wrong by a large factor.

Common Mistake

Sizing a cache for millions of small values using only "value size times entry count" and being surprised when actual memory usage is several times higher. Per-entry overhead is not a rounding error for small values - it's frequently the dominant cost, and worth measuring directly rather than estimating.

Q52. maxmemory-policy for Redis vs Caffeine's Weigher/maximumSize

ROI: ★★★★☆ Frequency: High

Short Answer

Both Redis and Caffeine need to be told what to do once they hit a memory or size limit, but they expose that decision differently, and knowing the specific Redis configuration option by name is a frequent litmus test for "have you actually operated Redis, or only used it."

Redis's behavior at its memory limit is controlled by maxmemory-policy. The critical, easy-to-get-wrong default is noeviction: once maxmemory is reached, Redis stops accepting new writes entirely and returns an error to the client, rather than quietly evicting something to make room - appropriate only if Redis is being used as a primary datastore where silently losing data is worse than rejecting writes. For an actual cache, you almost always want an eviction-based policy instead: allkeys-lru (approximate LRU across every key), allkeys-lfu (approximate LFU across every key, better for skewed access patterns per Q13), or the volatile-* variants of each, which only consider keys that have an explicit TTL set as eviction candidates, leaving keys without a TTL untouched no matter how full memory gets - useful if the same Redis instance holds both genuinely-cacheable data and something that must never be silently evicted.

Caffeine's equivalent decision is made at build time rather than as a runtime policy switch: maximumSize bounds the cache by entry count, while maximumWeight combined with a custom Weigher bounds it by a computed "weight" per entry (letting a 10KB entry count for more of the budget than a 10-byte one), which matters when cached values vary significantly in size and a flat entry-count limit would let a few huge entries dominate the cache's actual memory footprint disproportionately.

System Mechanism Common choice for "it's a cache"
Redis maxmemory-policy (runtime config) allkeys-lru or allkeys-lfu (never noeviction)
Caffeine maximumSize or maximumWeight + Weigher (build-time) maximumWeight when entry sizes vary significantly

Interview Gold Point

Naming `noeviction` specifically as the dangerous default, and being able to say precisely why - "writes start failing outright instead of evicting" - is one of the highest-signal single facts in this whole chapter, precisely because it's the kind of thing that's easy to overlook until a cache actually fills up in production and starts rejecting writes instead of gracefully evicting.

Q53. Compression to Reduce Cache Memory Footprint

ROI: ★★★☆☆ Frequency: Medium

Short Answer

Once working-set size and per-entry overhead (Q50, Q51) still leave a cache too large or too expensive for available memory, compressing values before storing them is a lever that trades CPU time for memory - and, for a cache that's paying for expensive Redis memory or constrained JVM heap, that trade is often clearly worth it.

The trade-off is genuinely two-sided and worth stating precisely rather than treating compression as a free win: it reduces memory footprint (often substantially for text-heavy or repetitive payloads like JSON) and can reduce network transfer time for large values, but it costs CPU on every write (to compress) and every read (to decompress), and it makes the stored bytes opaque - you lose the ability to inspect a cached value directly in Redis with a simple `GET` for debugging without decompressing it first, which is a real (if minor) operational cost.

The practical judgment call is to compress selectively rather than universally: it's usually worth it for larger, text-heavy payloads (a rendered HTML fragment, a large JSON blob) where the memory savings are substantial and the values are read far less often than the CPU cost would suggest, and usually not worth it for small values, where the fixed overhead of compression can exceed any memory saved, or for extremely hot keys being read thousands of times per second, where the added CPU cost per read compounds into a real latency and throughput cost across that volume.

Common Mistake

Enabling compression uniformly across an entire cache "for safety" without measuring the actual CPU cost against the actual memory savings for that specific workload. The senior habit is treating this as a data-driven decision per data type, the same way TTL choice (Q36) is - not a single global switch.

SECTION 14 - CACHING SYSTEM DESIGN SCENARIOS

Q54. Design a Cache for a Product Catalog Page

ROI: ★★★★★ Frequency: Very High (System Design)

Short Answer

This is one of the most common caching system-design prompts precisely because a good answer has to pull together nearly everything in this chapter into one coherent design, rather than reciting patterns in isolation.

The access pattern: read-heavy, highly skewed toward a small set of popular products (Q50's working set), price and stock change more often than descriptions and images, and staleness of a few seconds to a couple of minutes is generally acceptable for a catalog page (unlike, say, a checkout total). That points toward a multi-level design (Q11): an L1 Caffeine cache per instance for the hottest products with a short TTL, backed by an L2 Redis cache shared across the fleet with a longer TTL, backed by the database. Cache-aside (Q2) populates both levels lazily. Different fields get different TTL treatment per Q36 - a coarse-grained "everything expires in 5 minutes" is worse than splitting cache entries so that price/stock have a short TTL while description/images (which change far less often) can have a much longer one, or are versioned (Q32) rather than TTL'd at all.

Layering in the rest of the chapter: TTL jitter and request coalescing (Q9) to avoid a stampede when a popular product's entry expires; negative caching (Q33) for invalid/deleted product IDs; a CDN in front of everything (Q25) for the fully-rendered page or its static assets, since much of a catalog page doesn't vary per user at all; and a circuit breaker with a database fallback (Q46) so a Redis blip degrades to slower-but-correct instead of an outage. The strongest answers explicitly justify each choice against the specific access pattern rather than applying every pattern reflexively "because this is the caching chapter."

Interview Gold Point

Structure the answer as: access pattern first, then which patterns that pattern implies, not "here are all the caching patterns I know." Interviewers running this as a system-design prompt are explicitly testing whether you can select and justify a subset rather than list everything you've memorized.

Q55. Design a Cache for a Real-Time Leaderboard

ROI: ★★★★☆ Frequency: High (System Design)

Short Answer

A leaderboard's access pattern is different enough from a catalog page that it deserves its own reasoning rather than reusing the same design by default: scores update very frequently (every game/match/action), and the read requirement isn't "fetch one item by id," it's "give me the top N, in order, right now," and often also "give me this specific user's current rank," both of which need efficient ordered access, not just key-value lookups.

This is exactly the shape Redis's sorted set (ZSet, from Q7) was built for: a single `ZADD` updates a player's score in O(log N), `ZREVRANGE` fetches the top N in ranked order directly, and `ZREVRANK` gets a specific member's current rank - all without the application maintaining its own sort order or scanning anything. Because the score itself lives directly in Redis as the source of truth for ranking purposes (rather than being a cached copy of a value computed elsewhere), this leans toward write-through in spirit: every score change goes directly into the ZSet as part of the write path, and there's no separate "cache miss, recompute" step for reads at all, since reading the top N or a rank is always just querying the live ZSet.

For extreme read volume (a leaderboard on a high-traffic public homepage), the top-N result itself can additionally be cached with a very short TTL (a few seconds) in front of the ZSet, since "exactly real-time to the millisecond" is rarely a real requirement for a leaderboard - a few seconds of staleness on the top-10 display is an easy, low-risk trade for absorbing enormous read volume without hitting the ZSet on every single page view. This is a good example of a design where the "cache" being discussed is layered on top of a Redis data structure that is itself already fast and already the source of truth, rather than in front of a slower database.

Interview Gold Point

The insight worth stating explicitly: "the interesting design decision here isn't cache-aside vs write-through in the abstract, it's recognizing that a sorted set turns 'give me the ranked top N' from an application-level sorting problem into a single Redis command - the caching layer and the correct data structure choice are the same decision for this access pattern."

Q56. Designing a Redis-Backed Rate Limiter End to End

ROI: ★★★★☆ Frequency: High (System Design)

Short Answer

Q22 covered the algorithmic options for Redis-based rate limiting; a full system-design answer needs to also address where the limiter sits, how it fails, and how it scales, which is what actually distinguishes a strong answer from a correct-but-incomplete one.

Placement: rate limiting almost always belongs at the API Gateway / edge layer rather than duplicated inside every individual backend service, both to enforce limits before wasted work happens downstream and to have one consistent, centrally-configurable policy rather than N slightly-different implementations. Algorithm choice from Q22 depends on the specific requirement - a hard cap with simple semantics favors fixed window with jitter-tolerant limits, a need to allow legitimate bursts favors token bucket, and precise fairness favors a sliding window - and should be a deliberate choice tied to the actual product requirement, not a default.

Failure mode is the part candidates most often skip: what happens to every request if the Redis instance backing the limiter is itself unavailable? Failing closed (reject all requests) turns a cache/limiter outage into a full outage of the entire API, which is rarely the right trade for a rate limiter specifically, since its job is abuse prevention, not core functionality. Failing open (allow all requests through when the limiter is unreachable) is the far more common choice - it means a brief window of unenforced rate limits during a Redis blip, which is a much smaller risk than an outright outage, paired with a circuit breaker (Q46) so requests fail fast to that open behavior rather than each one waiting out a timeout against a dead Redis. Scaling the limiter itself for very high request volume benefits from the pipelining and Lua-script atomicity from Q18/Q19, and, if it becomes a bottleneck, from partitioning limiter keys the same way a hot key would be split (Q48), since a globally popular endpoint's rate-limit key is itself a hot key by definition.

Interview Gold Point

The fail-open-vs-fail-closed decision is the single highest-signal part of this answer. Stating it explicitly - "for a rate limiter specifically, I'd fail open, because the limiter's job is to protect against abuse, and an outage of the abuse-prevention layer shouldn't become an outage of the product itself" - shows the kind of risk-weighing senior interviewers are actually screening for.

Q57. Caching a Third-Party API You Don't Control

ROI: ★★★★☆ Frequency: High

Short Answer

Caching your own database is fully within your control: you know exactly when data changes, because your own write path is what changes it, so explicit invalidation (Q4) is always available. Caching a third-party API response is different in one important way: you have no write path to hook into and no reliable signal for exactly when the upstream data changed, so the cache has to lean much harder on time-based and header-driven strategies rather than explicit invalidation.

The first thing to check is whether the third-party API itself sends standard HTTP caching headers (Q26, Q27) - `Cache-Control` with a `max-age`, or an `ETag` supporting conditional requests. If it does, respecting those headers directly (rather than inventing your own arbitrary TTL) is both the most correct approach and the one least likely to violate the provider's terms of service or rate limits, since it's exactly the mechanism the provider designed for this. If the API gives no caching guidance at all, the fallback is a TTL chosen conservatively based on how often you've empirically observed the data to change and how costly staleness is for your use case - erring toward a shorter TTL than you might for internal data, precisely because you have no invalidation escape hatch if you guess wrong and the underlying data changes sooner than expected.

Two additional considerations specific to third-party APIs: negative caching (Q33) matters even more here, since a slow or rate-limited third-party API makes every uncached "not found" or error response disproportionately expensive, and a stampede-prevention strategy (Q9) is often mandatory rather than optional, because many third-party APIs enforce hard rate limits, and a cache-miss stampede against an external API can mean your own service getting rate-limited or blocked entirely, not just extra latency.

Interview Gold Point

The framing to lead with: "without a write path into the third-party data, I've lost explicit invalidation as an option, so I lean on whatever caching headers the API actually provides, and treat rate-limit protection and stampede prevention as first-class requirements rather than nice-to-haves, since a badly-cached third-party integration can get your own service blocked." That reframes the whole problem correctly instead of defaulting to "just add a TTL."

Q58. When NOT to Cache at All

ROI: ★★★★☆ Frequency: High (Senior Favorite)

Short Answer

This chapter has spent a lot of time on how to cache well, which makes it easy to forget that reflexively adding a cache to every slow-looking read path is itself a mistake interviewers specifically probe for - the strongest closing signal in this whole topic is knowing when the honest answer is "don't."

Caching is a poor fit when data changes on essentially every read and staleness of even a few seconds causes real harm - a live account balance mid-transaction, an inventory count during the final seconds of a flash sale, anything where "the value I show is definitely current" is itself the requirement, not merely a preference. It's also often not worth it when the underlying read is already fast and cheap: caching adds real complexity (an extra failure mode, an extra thing to invalidate correctly, an extra piece of infrastructure to run and monitor) and that complexity needs to be justified by an actual latency, load, or cost problem it solves - caching a query that already takes two milliseconds and is rarely called adds risk for no measurable benefit. And it's the wrong tool when correctness must be strict and auditable (financial ledger entries, anything subject to regulatory audit trails) where "eventually consistent, wrong for a bounded window" - the honest description of what every caching strategy in this chapter actually provides - is not an acceptable characterization of the system's behavior at all.

The senior instinct, consistent with how this chapter opened in Q1, is to add a cache deliberately in response to a measured problem (an actual latency budget being missed, an actual database struggling under real load, an actual cost line item worth reducing), and to be equally willing to say a read path doesn't need one. Reaching for Redis or Caffeine by default, everywhere, "because caching is generally good," is exactly the reflexive behavior the opening question of this chapter warned against.

Interview Gold Point

Close with the same framing this chapter opened with: "I add a cache to solve a measured latency, load, or cost problem, and I'm equally comfortable saying a given read path doesn't have one of those problems and doesn't need a cache." That full-circle answer - deliberate adoption, not reflexive adoption - is consistently one of the strongest signals in this entire topic area.

  • Redis beyond caching: SET NX PX for locks (Redlock raises confidence but Kleppmann's critique says use fencing tokens for hard correctness); ZSET/Lua for rate limiting; Pub/Sub is fire-and-forget; Streams add persistence + consumer groups but aren't a Kafka/RabbitMQ replacement at scale
  • CDN caches whole HTTP responses at the edge, in front of app-level Redis/Caffeine; Cache-Control (no-cache = revalidate, no-store = never cache), ETag + conditional requests (304), and Vary (fragments the cache key) govern that layer
  • Read-through delegates miss-handling to the cache itself via a loader (Caffeine's get(key, loader), @Cacheable); cache-aside means the application writes that logic by hand at every call site
  • Namespace cache keys ({service}:{entity}:{id}:{variant}) to avoid collisions on a shared Redis; version keys on schema change; cache "not found" too (negative caching) to stop enumeration/retry storms from bypassing the cache entirely; warm hot keys before a deploy/flush to avoid a cold-cache stampede
  • Choose TTL per data type: long for rarely-changing reference data, short for price/stock, explicit invalidation (not TTL) for auth/permissions
  • Session storage often *is* the source of truth, not a copy - weigh durability accordingly; externalized stores (Spring Session + Redis) beat sticky sessions for auto-scaling/rolling deploys at the cost of a network hop and a new availability dependency
  • Write DB-then-delete-cache narrows (not eliminates) the stale-read race; delayed double-delete catches most of what's left; write-through across a distributed cache still needs versioning/serialization to stay ordered under concurrent writers; read-repair/reconciliation jobs detect drift prevention misses
  • A cache outage should degrade to slower-but-correct (DB fallback + circuit breaker + short timeout), never cascade into a full outage; hot keys are a distribution problem (fix with local caching or key-splitting), distinct from a stampede's timing problem
  • Size a cache for the working set implied by your access distribution and target hit ratio, not the full dataset; measure real per-entry memory overhead rather than estimating from value size alone; never leave Redis on maxmemory-policy noeviction for an actual cache
  • The best senior answer is knowing when *not* to cache: never for data where any staleness is unacceptable (balances, strict audit trails) or for reads that are already fast and rarely called - add a cache to solve a measured latency/load/cost problem, not by reflex
