26 - OBSERVABILITY & MONITORING INTERVIEW HANDBOOK

Observability shows up constantly in senior interviews because it is one of the clearest signals of real production experience versus resume-only buzzwords. Almost anyone can say "we use Prometheus and Grafana." Far fewer can explain why observability is a genuinely different mental model from classic monitoring, how metrics, logs and traces compose into a single investigative workflow, or how to design SLOs and alerts that page a human only when a human can actually do something about it. A junior engineer treats a dashboard as decoration; a senior engineer treats it as the mechanism by which an unknown failure mode, in a system nobody fully understands end to end, gets diagnosed in minutes instead of hours. SECTION 1 - FUNDAMENTALS

Q1. The Three Pillars of Observability: Metrics, Logs, Traces

ROI: ★★★★★ Frequency: Very High

Short Answer

"Three pillars" is the standard vocabulary, and interviewers expect you to know not just what each pillar is, but which question it is best at answering, because none of the three is sufficient alone.

Metrics are numeric measurements aggregated over time: request rate, error count, CPU usage, queue depth. They are cheap to store, cheap to query, and excellent at answering "what" and "how much" across a whole fleet: is latency elevated, is the error rate above threshold, is memory climbing. What they cannot tell you is why a single specific request failed, because the aggregation throws away per-request detail.

Logs are discrete, timestamped events with arbitrary detail: a stack trace, a request payload, a business decision. They are the richest source of "why," but they are also the most expensive to store and search at volume, and a raw unstructured log line is nearly useless once you have hundreds of service instances producing millions of lines a day.

Traces follow one request as it moves through multiple services, recording how long each hop took and how the hops nest. A trace answers "where in this distributed call chain did the time go," which neither a metric (too aggregated) nor an isolated log line (no cross-service context) can answer by itself.

The real skill is using them together in sequence: a metric dashboard tells you something is wrong right now (p99 latency spiked at 14:02), a trace for a slow request during that window shows you which downstream call is the bottleneck, and the logs for that specific trace id give you the exact exception or slow query behind it. Observability tooling increasingly links the three by a shared identifier so you can jump from a graph, to a trace, to the exact log lines, in three clicks.

Pillar Answers Granularity Typical store
Metrics What / how much, across the fleet Aggregated numeric series Prometheus, Micrometer
Logs Why, for one event Discrete, high detail ELK / Loki / CloudWatch Logs
Traces Where the time went, across services Per-request, spans nested Jaeger / Zipkin / Tempo

Interview Gold Point

State the workflow, not just the definitions: "metrics tell me something is wrong and roughly when; a trace for that window tells me where in the call graph; logs for that trace id tell me why." Naming the correlation id (usually the trace id) as the thread that ties all three together is exactly the detail that separates "I've heard of Grafana" from "I've actually debugged an incident with this stack."

Q2. Observability vs Monitoring (Known-Unknowns vs Unknown-Unknowns)

ROI: ★★★★★ Frequency: Very High

Short Answer

This distinction is the single most common "trap" question in this chapter, because most engineers use the two words interchangeably, and interviewers ask it specifically to see if you know they are not.

Monitoring is watching for failure modes you already anticipated. You decide up front which metrics matter (CPU, error rate, disk space), you set a threshold, and you get paged when the threshold is crossed. Monitoring answers questions you thought to ask in advance: these are known-unknowns, things you know you don't know the current value of, but you already know the question. Classic dashboards and static alert rules are monitoring.

Observability is a property of the system itself: how well can you infer its internal state purely from the telemetry it emits, including for failure modes nobody predicted. It is about unknown-unknowns, the class of production incident where you don't even know what question to ask yet ("why does checkout fail only for customers in one specific region, using one specific browser, only between 2pm and 3pm?"). A truly observable system lets you slice high-cardinality, high-dimensionality data on the fly to explore a question you never wrote a dashboard for, instead of forcing you to predict every future question in advance.

In practice the two are complementary rather than competing: you still want monitoring's cheap, predictable alerts for the failure modes you know about (disk full, pod crash-looping), and you additionally want observability's rich, explorable telemetry (structured logs, wide events, distributed traces with high-cardinality attributes) so that when something genuinely novel breaks, you are not stuck adding a new log line, redeploying, and waiting for it to happen again.

Interview Gold Point

The line that lands well: "monitoring tells you that something you predicted is broken; observability lets you ask why about something you never predicted, without shipping new code to find out." If pushed further, mention cardinality: dashboards built on a handful of predefined dimensions are monitoring; the ability to filter by arbitrary high-cardinality fields like user id or request id, after the fact, is what people mean by "observable."

SECTION 2 - METRICS: MICROMETER & PROMETHEUS

Q3. Micrometer as a Vendor-Neutral Metrics Facade

ROI: ★★★★☆ Frequency: High

Short Answer

Micrometer is to metrics what SLF4J is to logging: a single facade API that your application code depends on, with a pluggable registry that ships the data to whichever backend you actually run (Prometheus, Datadog, New Relic, CloudWatch, and others). You instrument your code once against Micrometer's MeterRegistry, and switching monitoring vendors becomes a dependency and configuration change, not a rewrite of every metrics call scattered through the codebase.

Spring Boot Actuator auto-configures a MeterRegistry the moment the right Micrometer registry dependency is on the classpath (for example micrometer-registry-prometheus), and it automatically publishes a broad set of built-in metrics out of the box: JVM memory and GC, thread pool utilization, HTTP request timings per endpoint, DataSource/HikariCP pool stats, and more. On top of the free metrics, you register your own business-level meters directly against the registry. 

@Service
public class OrderService {

    private final Counter ordersCreated;
    private final Timer paymentTimer;

    public OrderService(MeterRegistry registry) {
        // business counter, tagged for filtering later in PromQL/Grafana
        this.ordersCreated = Counter.builder("orders.created")
                .description("Total orders successfully created")
                .tag("channel", "web")
                .register(registry);

        this.paymentTimer = Timer.builder("payment.duration")
                .description("Time to process a payment")
                .publishPercentileHistogram() // enables histogram_quantile in PromQL
                .register(registry);
    }

    public void createOrder(Order order) {
        paymentTimer.record(() -> paymentGateway.charge(order));
        ordersCreated.increment();
    }
}

Interview Gold Point

Draw the SLF4J parallel explicitly; interviewers who have never used Micrometer directly will still recognize the pattern instantly. Also mention tags: a Micrometer meter is a name plus a set of key/value tags (like channel=web), and those tags become PromQL labels once scraped, which is exactly what lets you later slice "orders created" by channel, region, or status without creating a separate metric for every combination.

Q4. Metric Types: Counters, Gauges, Timers, Distribution Summaries

ROI: ★★★★☆ Frequency: High

Short Answer

Picking the wrong meter type is a common practical mistake, because using a gauge where you needed a counter (or vice versa) silently produces a metric that cannot answer the question you actually care about.

A Counter only ever goes up (or resets to zero on restart); it is for counting occurrences, like total requests served or total orders created. You never decrement a counter directly; if something can go down, it is not a counter. A Gauge is a single instantaneous value that can go up or down, like current queue depth, active thread count, or cache size right now; a gauge does not accumulate history, it just reports "what is the value at this instant." A Timer measures both the count and the duration distribution of short recurring events, like HTTP request latency or a database call; under the hood it is really a counter of occurrences plus a histogram or summary of how long each one took. A Distribution Summary is the same idea as a Timer but for a non-time quantity, like the size in bytes of an uploaded file or the number of items in a shopping cart.

Type Behaviour Example
Counter Monotonically increasing Total HTTP requests, orders created
Gauge Point-in-time value, up or down Active connections, queue size, heap used
Timer Count + duration distribution Request latency, DB call duration
Distribution Summary Count + magnitude distribution (non-time) Upload size, cart item count

Common Mistake

Wrapping a value that can decrease (queue depth, in-flight requests) in a Counter, which makes it impossible to see the current state, only a running total that never reflects reality. The rule of thumb to say out loud: "if it only ever grows and I care about the rate of growth, Counter; if it can go up or down and I care about the value right now, Gauge; if I care about how long or how big something was, Timer or DistributionSummary."

Q5. Prometheus's Pull Model & Scraping

ROI: ★★★★☆ Frequency: High

Short Answer

Prometheus is built around a pull model: instead of applications pushing metrics to a central collector, each application exposes its current metric values on an HTTP endpoint (Spring Boot Actuator exposes /actuator/prometheus), and the Prometheus server periodically scrapes that endpoint on a schedule, storing each observation as a timestamped sample in its own time-series database.

The pull model has real operational advantages that interviewers like to hear articulated. Prometheus itself controls the scrape interval and can back off or fail gracefully if a target is slow, rather than being flooded by a burst of pushes. A target simply being reachable on its metrics port is itself a liveness signal, Prometheus's "up" metric, with no extra code required. Because Prometheus decides who to scrape via service discovery (Kubernetes, Consul, static config, EC2 tags), you don't have to configure every application with the address of a central collector; you just make sure it exposes the right endpoint and is discoverable.

The trade-off is that pull requires the target to be network-reachable from Prometheus, which is awkward for short-lived batch jobs that may finish before a scrape happens; Prometheus's answer for that case is the Pushgateway, an intermediary that batch jobs push to and which Prometheus then scrapes instead. 

# prometheus.yml - scrape config for a Spring Boot app on Kubernetes
scrape_configs:
  - job_name: 'order-service'
    metrics_path: '/actuator/prometheus'
    scrape_interval: 15s
    kubernetes_sd_configs:
      - role: pod
    relabel_configs:
      - source_labels: [__meta_kubernetes_pod_label_app]
        action: keep
        regex: order-service

Interview Gold Point

Contrast pull vs push directly: "Prometheus pulls because it centralizes control of scrape frequency and load, and gets a free liveness check for the price of a reachable endpoint; systems like StatsD or CloudWatch push, which fits short-lived processes better but pushes the load-management problem onto the collector." Mentioning the Pushgateway as the pull model's escape hatch for batch jobs shows you understand the model's edges, not just its happy path.

Q6. PromQL Basics & Common Query Patterns

ROI: ★★★☆☆ Frequency: Medium

Short Answer

PromQL is Prometheus's query language, and interviewers rarely expect you to write complex queries from memory, but they do expect you to recognize and explain the handful of patterns that appear in nearly every real dashboard.

The single most important function is rate(), because raw counters are cumulative totals and are almost never useful directly; what you actually want is "how fast is this counter increasing per second," which is what rate() computes over a sliding time window, correctly handling counter resets (for example on a pod restart). A gauge, by contrast, you usually query as-is, or aggregate with avg/max/sum across instances.

For latency, Micrometer's Timer publishes a histogram of observed durations bucketed by upper bound, and histogram_quantile() estimates a percentile (like p99) from those buckets. This is why "publish percentile histogram" matters at instrumentation time: without histogram buckets exported to Prometheus, you cannot compute an accurate p99 centrally, only whatever percentiles the client pre-aggregated (which cannot be correctly averaged across instances). 

# Requests per second, by service, over the last 5 minutes
sum(rate(http_server_requests_seconds_count[5m])) by (service)

# Error rate as a percentage of total requests
sum(rate(http_server_requests_seconds_count{status=~"5.."}[5m]))
/
sum(rate(http_server_requests_seconds_count[5m]))

# p99 latency from a Micrometer/Prometheus histogram
histogram_quantile(0.99,
  sum(rate(http_server_requests_seconds_bucket[5m])) by (le, uri)
)

# Alert-style query: 5xx rate above 5% for 5 minutes
(sum(rate(http_server_requests_seconds_count{status=~"5.."}[5m]))
 / sum(rate(http_server_requests_seconds_count[5m]))) > 0.05

Interview Favorite

If asked "why can't I just average the p99 reported by each of my 10 instances?" the answer is: percentiles do not average meaningfully, a p99 of 100ms on one instance and 300ms on another is not a p99 of 200ms across both. You must aggregate at the histogram-bucket level first (sum by (le)) and only then call histogram_quantile, which is exactly what the query above does.

SECTION 3 - DASHBOARDS, LOGGING & TRACING

Q7. Grafana Dashboards & Alerting Rules

ROI: ★★★☆☆ Frequency: Medium

Short Answer

Grafana is a visualization and alerting layer that sits on top of one or more data sources, most commonly Prometheus, and turns PromQL (or equivalent) queries into panels: time series graphs, single-stat gauges, heatmaps for latency distributions, and tables. A dashboard is a collection of panels, usually organized so the golden-signal panels (traffic, errors, latency, saturation) are visible at the top, with drill-down panels below.

Two design habits distinguish a genuinely useful dashboard from a wall of graphs nobody reads. First, use template variables (for example a dropdown for service or environment) so one dashboard definition serves every service instead of hand-copying a dashboard per service. Second, design top-down: the top row should let an on-call engineer answer "is this bad, and roughly where" in ten seconds, with everything else existing purely to support a deeper dive once that first question is answered.

Grafana can also evaluate alerting rules directly (or you can define alerts in Prometheus's own Alertmanager); either way, a rule is a query plus a threshold plus a duration ("for" clause), and it fires a notification through a configured channel (Slack, PagerDuty, email) when the condition holds true continuously for that duration, which is what prevents a single noisy spike from paging someone. 

# Prometheus alerting rule - evaluated by Alertmanager, visible in Grafana
groups:
  - name: order-service-alerts
    rules:
      - alert: HighErrorRate
        expr: |
          sum(rate(http_server_requests_seconds_count{status=~"5..",service="order-service"}[5m]))
          /
          sum(rate(http_server_requests_seconds_count{service="order-service"}[5m]))
          > 0.05
        for: 5m
        labels:
          severity: page
        annotations:
          summary: "order-service 5xx rate above 5% for 5 minutes"
          runbook: "https://runbooks.internal/order-service-errors"

Interview Gold Point

Point out the for: 5m clause unprompted: it is the difference between "the query briefly crossed the threshold" and "this is a sustained problem worth waking someone up for." Also mention the runbook annotation; a senior engineer designs alerts so that the notification itself links to the remediation steps, instead of leaving the on-call person to reverse-engineer what to do from a bare metric name at 3am.

Q8. Structured Logging & Correlation/Trace IDs

ROI: ★★★★★ Frequency: Very High

Short Answer

Plain-text log lines like "Order 123 failed" are fine on a laptop and nearly useless once you have dozens of service instances shipping logs to a central aggregator, because you cannot reliably parse, filter, or correlate free text at scale. Structured logging emits each log entry as a machine-parseable record, almost always JSON, with consistent fields: timestamp, level, logger, message, and critically, contextual key/value fields like orderId, userId, and a correlation id.

A correlation id (often the same value as the distributed trace id) is generated once at the edge of the system, when a request first arrives, and is then threaded through every log statement, every downstream HTTP call header, and every message published, for the lifetime of that request. It is what lets you take one failed request and pull every log line it touched across every service it visited, out of a shared log index, with a single filter. Without it, correlating a single user's failure across five microservices means grepping timestamps and hoping nothing else happened concurrently.

In Spring Boot, the idiomatic mechanism is the SLF4J MDC (Mapped Diagnostic Context): a servlet filter or Micrometer Tracing's automatic instrumentation puts the trace id and span id into MDC at the start of a request, and every subsequent log statement on that thread automatically includes them, with zero change to individual log.info(...) call sites. 

// A filter that ensures every request has a correlation id in MDC and in the response
@Component
public class CorrelationIdFilter extends OncePerRequestFilter {

    protected void doFilterInternal(HttpServletRequest req, HttpServletResponse res,
                                     FilterChain chain) throws IOException, ServletException {
        String correlationId = Optional.ofNullable(req.getHeader("X-Correlation-Id"))
                .orElse(UUID.randomUUID().toString());
        MDC.put("correlationId", correlationId);
        res.setHeader("X-Correlation-Id", correlationId);
        try {
            chain.doFilter(req, res);
        } finally {
            MDC.clear(); // never leak context onto a reused thread-pool thread
        }
    }
}

{"timestamp":"2026-08-13T10:15:32.101Z","level":"ERROR","logger":"OrderService",
 "correlationId":"7d1e2f3a-...","traceId":"7d1e2f3a...","spanId":"a1b2c3",
 "message":"Payment declined","orderId":"123","reason":"insufficient_funds"}

Interview Gold Point

Emphasize the "why JSON" reasoning, not just "we use JSON logs": structured fields let your log aggregator (ELK, Loki, CloudWatch Insights) index and query on orderId or correlationId directly, the same way a database column beats parsing a CSV blob with regex. Also flag the MDC.clear() in the finally block as a common production bug: thread pools reuse threads, and forgetting to clear MDC leaks one request's correlation id into the next request that happens to land on the same thread.

Q9. Distributed Tracing Concepts (Spans, Trace Context Propagation)

ROI: ★★★★★ Frequency: Very High

Short Answer

A single incoming request in a microservices architecture might touch ten services before a response is returned. Distributed tracing reconstructs that entire call graph, with per-hop timing, as one connected picture, which is the only way to answer "where did the 800ms actually go" once the call chain crosses process boundaries.

The core unit is a span: a named operation with a start time and duration, such as "handle HTTP request" or "call payment-service" or "query orders table." A span can have child spans, forming a tree. All spans belonging to one logical request share the same trace id; each individual span additionally has its own span id, and (except for the root) a parent span id pointing at the span that called it. Rendered together, a trace looks like a waterfall: the root span spans the whole request, and nested bars underneath show each downstream call and how much of the parent's time it consumed.

The mechanism that makes this work across process boundaries is context propagation. When service A calls service B over HTTP, A injects the current trace id, span id (as the new parent), and sampling decision into outgoing request headers, using a standard format like the W3C traceparent header (or the older B3 headers). Service B's tracing instrumentation reads those headers, creates its own child span under the given parent, and, if it in turn calls service C, propagates the same trace id onward. The trace id is the one piece of context that survives the entire journey; everything else nests underneath it. 

Request --> [Service A: root span, trace=T1]
              |-- HTTP call w/ traceparent header (trace=T1, parent=spanA)
              v
            [Service B: child span, trace=T1, parent=spanA]
              |-- HTTP call w/ traceparent header (trace=T1, parent=spanB)
              v
            [Service C: child span, trace=T1, parent=spanB]

All three spans share trace id T1 -> one waterfall view in Jaeger/Tempo/Zipkin

Interview Gold Point

Name the propagation header explicitly (W3C traceparent, the modern default that OpenTelemetry uses) and state the failure mode when it is missing: if any hop in the chain drops or fails to forward the header (a hand-rolled HTTP client, an async hop through a message queue without header propagation), the trace breaks into two disconnected traces at that point, which is one of the most common real-world tracing bugs and a strong signal you've actually operated a traced system.

Q10. OpenTelemetry & Spring Boot Actuator / Micrometer Tracing Integration

ROI: ★★★★☆ Frequency: High

Short Answer

OpenTelemetry (OTel) is the vendor-neutral, CNCF-hosted standard for generating and exporting all three pillars: a common API/SDK for instrumenting code, a standard wire protocol (OTLP) for sending telemetry, and the OpenTelemetry Collector, a separate process that can receive, batch, transform and re-export telemetry to whichever backend you actually run (Jaeger, Tempo, Prometheus, a commercial vendor). The point of OTel is the same as Micrometer's: instrument once, remain free to swap backends later without touching application code.

Spring's story for tracing is Micrometer Tracing, which plays the same facade role for traces that Micrometer plays for metrics: your code (and Spring's own auto-instrumentation of MVC controllers, RestTemplate/WebClient, JDBC, and messaging) creates spans against the Micrometer Tracing API, and a pluggable bridge, either the OpenTelemetry bridge or the older Brave/Zipkin bridge, does the actual propagation and export. Spring Boot Actuator wires this together automatically: adding micrometer-tracing-bridge-otel plus an OTLP exporter dependency, with sampling and endpoint configuration in application.yml, is typically enough to get end-to-end traces with no custom code, because the instrumentation for common Spring components (web, WebClient, JDBC, Kafka) is automatic.

The piece worth calling out explicitly is sampling: tracing every single request in a high-throughput system is often too expensive to store, so most setups sample a percentage (say 10%) of traces, or sample adaptively (always trace errors and slow requests, sample the rest at a low rate). This is a deliberate cost/completeness trade-off you should be ready to discuss, not an oversight. 

# application.yml
management:
  tracing:
    sampling:
      probability: 0.1   # trace 10% of requests; always raise for errors via custom sampler
  otlp:
    tracing:
      endpoint: http://otel-collector:4318/v1/traces
  metrics:
    export:
      prometheus:
        enabled: true
  endpoints:
    web:
      exposure:
        include: health, prometheus, info

Interview Favorite

The clean one-liner: "Micrometer is the facade for metrics, Micrometer Tracing is the facade for traces, and OpenTelemetry is the increasingly standard implementation underneath both, plus the wire format and Collector that gets the data to whatever backend we run." If asked why not just call the OTel SDK directly, the answer is that Spring's auto-instrumentation and the Micrometer abstraction save you from manually wrapping every RestTemplate call and JDBC statement in span-creation boilerplate.

SECTION 4 - GOLDEN SIGNALS, SLOs & ALERTING

Q11. The Four Golden Signals & the RED / USE Methods

ROI: ★★★★★ Frequency: Very High

Short Answer

When you are staring at an unfamiliar service during an incident, or designing a dashboard for a brand-new one, you need a starting checklist rather than a blank page. Google's SRE book popularized the Four Golden Signals: Latency (how long requests take, split into successful vs failed since failed requests can be suspiciously fast), Traffic (how much demand the system is under, requests per second), Errors (rate of failed requests), and Saturation (how "full" the system is, CPU, memory, queue depth, connection pool usage, i.e. how close to its ceiling it is running).

RED (Rate, Errors, Duration) is essentially the request-centric subset of the golden signals, and it is the natural fit for any request-driven service: how many requests per second, what fraction error, how long do they take. USE (Utilization, Saturation, Errors) is the resource-centric counterpart, aimed at infrastructure and resources rather than requests: for a CPU, a disk, a connection pool, what fraction of it is busy (utilization), how much work is queued waiting for it (saturation), and how often does it produce errors.

The practical guidance interviewers want to hear: apply RED to your services (per-endpoint dashboards), and apply USE to the resources those services depend on (CPU, thread pools, DB connection pools, disks). Together they cover both "is the service itself healthy from the outside" and "is some resource underneath it about to become the bottleneck," which is exactly the golden signals' saturation dimension made concrete per-resource.

Framework Focus Signals
Golden Signals General-purpose, any service Latency, Traffic, Errors, Saturation
RED Request-driven services Rate, Errors, Duration
USE Resources (CPU, pools, disks) Utilization, Saturation, Errors

Interview Gold Point

If asked to design a dashboard for a service you've never seen before, say this out loud: "I'd start with RED for the service's own request handling, and USE for the resources it depends on underneath, since between them that's the golden signals fully covered." That framing shows you have a repeatable method, rather than needing to be told what to graph every time.

Q12. SLIs, SLOs, SLAs & Error Budgets

ROI: ★★★★★ Frequency: Very High

Short Answer

This trio (plus error budgets) is how SRE culture turns "reliability" from a vague feeling into a number you can make engineering decisions with, and interviewers use it to check whether you can reason about reliability quantitatively rather than just qualitatively.

An SLI (Service Level Indicator) is the actual measured metric: "the proportion of HTTP requests in the last 28 days that returned within 300ms and did not error." An SLO (Service Level Objective) is the internal target for that SLI: "99.9% of requests meet that bar over a rolling 28 days." An SLA (Service Level Agreement) is an external, usually contractual, commitment to a customer, typically set looser than the internal SLO with real financial or credit consequences for missing it, precisely so that missing the SLO internally still gives you room to fix things before you breach the customer-facing SLA.

The error budget is simply 100% minus the SLO, turned into a spendable allowance: at 99.9% availability, your error budget is 0.1% of requests (or 0.1% of time) per period, which at 28 days works out to roughly 40 minutes of full downtime-equivalent. The budget reframes the reliability conversation: as long as you have budget left, you can ship features and take calculated risk; once the budget is exhausted, the team's priority shifts to reliability work (freezing risky releases, paying down operational debt) until it recovers. This gives product and engineering a shared, numeric way to decide "can we ship this risky change this week" instead of an endless subjective argument.

Term Meaning Example
SLI The measured indicator % of requests < 300ms and successful
SLO Internal target for the SLI 99.9% over rolling 28 days
SLA External, contractual commitment 99.5% or customer gets a service credit
Error Budget Allowed failure = 1 - SLO 0.1% ≈ ~40 min/28 days

Interview Gold Point

The framing that signals seniority: "the error budget turns reliability into a resource the team spends deliberately, on either new features or on operational risk, rather than an unlimited expectation of perfection." Also be ready for the follow-up "why not just target 100%?": 100% is both practically unattainable and actively harmful, since it eliminates any budget for necessary risk like deploys, migrations, or experiments, and it costs disproportionately more for each additional nine of reliability.

Q13. Alerting Best Practices & Avoiding Alert Fatigue

ROI: ★★★★☆ Frequency: High

Short Answer

The failure mode every senior engineer has lived through is a pager full of alerts that fire constantly, are individually non-actionable, and eventually get ignored or muted, exactly when a real incident is happening among them. Good alerting design is as much a discipline as good code.

The first principle is alert on symptoms, not causes. Page on "users are experiencing errors or high latency" (a symptom visible from the golden signals), not on every individual internal cause that could theoretically lead there (a specific queue's depth crossing an arbitrary number, one pod's CPU ticking up). Symptom-based alerts fire only when something is actually user-impacting; cause-based alerts fire constantly for conditions that self-resolve or don't matter, which is the single biggest source of alert fatigue.

The second principle is that every page must be actionable: if a human receiving the alert at 3am cannot do anything about it right now, it should not page, it should at most log to a dashboard or ticket. Tie this to error budgets with burn-rate alerting: instead of a flat threshold, alert when the error budget is being consumed fast enough that it would be exhausted well before the period ends (for example, a fast-burn alert at a rate that would exhaust a 28-day budget in a few hours, pages immediately; a slow-burn alert that would exhaust it in a few days, can wait for business hours or even just a ticket). This makes the alert threshold reflect actual urgency rather than an arbitrary static number.

Practically: every page should link to a runbook, every alert should have a clear owner, alerts should be reviewed and pruned regularly (an alert that never leads to action should be deleted or downgraded), and severities should be genuinely different (a page that wakes someone up should be reserved for things that truly cannot wait until morning).

Anti-pattern Better practice
Alert on internal cause (CPU > 80%) Alert on user-facing symptom (error rate / latency SLO burn)
Flat static threshold Burn-rate alerting tied to the error budget
Alert with no runbook Every alert links to remediation steps
Everything pages immediately Severity tiers: page vs ticket vs dashboard-only

Common Mistake

Treating "more alerts" as "more safety." In reality, every low-value alert dilutes the signal of the high-value ones and trains on-call engineers to reflexively acknowledge-and-ignore, which is far more dangerous than having fewer, well-tuned alerts. The senior answer to "how do you reduce alert fatigue" is: alert on symptoms tied to the SLO, make every page actionable, and prune ruthlessly.

SECTION 5 - HEALTH CHECKS & KUBERNETES

Q14. Health Checks & Kubernetes Readiness/Liveness Probes

ROI: ★★★★☆ Frequency: High

Short Answer

Spring Boot Actuator exposes a /actuator/health endpoint that aggregates the status of registered HealthIndicators (database connectivity, disk space, message broker connectivity, and any custom indicator you add) into an overall UP/DOWN status. The interview-relevant nuance is that a single health endpoint is not enough for Kubernetes, because "is the app healthy" is actually two different questions with two different correct remediations, which is exactly why Kubernetes has two separate probes.

A liveness probe answers "is this process fundamentally broken and unrecoverable, such that restarting it is the right fix" (deadlocked, stuck in an infinite loop, JVM in a state it cannot escape). If liveness fails, Kubernetes kills and restarts the container. A readiness probe answers "is this instance currently able to correctly serve traffic" (perhaps it's still warming up a cache, or its database connection pool is temporarily exhausted, or it's mid-graceful-shutdown). If readiness fails, Kubernetes simply removes the pod from the Service's load-balanced endpoints, without restarting it, and adds it back once readiness passes again.

Conflating the two is a classic production incident: if you wire a downstream dependency check (say, "can I reach the database") into the liveness probe instead of readiness, then a transient database blip causes Kubernetes to restart every pod in the deployment simultaneously, which does nothing to fix the database and now also destroys your entire warm pool of running instances, turning a transient dependency issue into a full outage. That check belongs in readiness: take the pod out of rotation until the dependency recovers, but leave the process running so it can rejoin immediately once it does.

Spring Boot Actuator supports this natively via health groups: /actuator/health/liveness reflects only the application's own internal correctness (Spring's LivenessState), while /actuator/health/readiness includes dependency checks and Spring's ReadinessState, which the framework itself flips during graceful shutdown so in-flight requests can drain before the pod is killed. 

# application.yml
management:
  endpoint:
    health:
      probes:
        enabled: true
  health:
    livenessState:
      enabled: true
    readinessState:
      enabled: true

# Kubernetes deployment spec
livenessProbe:
  httpGet:
    path: /actuator/health/liveness
    port: 8080
  initialDelaySeconds: 20
  periodSeconds: 10
readinessProbe:
  httpGet:
    path: /actuator/health/readiness
    port: 8080
  initialDelaySeconds: 10
  periodSeconds: 5

Interview Gold Point

State the failure scenario unprompted: "if you put a database check on liveness instead of readiness, a temporary DB blip restarts every replica at once instead of just quietly draining traffic away from them, turning a recoverable dependency issue into a self-inflicted full outage." That single sentence usually proves you've actually operated Kubernetes, not just read the manifest syntax.

QUICK REVISION SHEET

  • Three pillars: metrics (what/how much), logs (why, per event), traces (where the time went across services) - use together via a shared correlation/trace id
  • Monitoring = known-unknowns, pre-defined thresholds; Observability = unknown-unknowns, explore high-cardinality data you never predicted
  • Micrometer = vendor-neutral metrics facade (like SLF4J for metrics); tags become PromQL labels for slicing later
  • Counter only ever grows (occurrences); Gauge is instantaneous and can go up/down; Timer/DistributionSummary = count + duration/size distribution
  • Prometheus pulls/scrapes an app's exposed metrics endpoint on a schedule; reachability doubles as a liveness signal; Pushgateway is the escape hatch for batch jobs
  • rate() turns a cumulative counter into per-second speed and survives restarts; histogram_quantile() needs bucket-level aggregation first, percentiles can't just be averaged
  • Grafana turns queries into dashboards/alerts; use template variables for reuse; alert rules need a "for" duration so a blip doesn't page anyone
  • Structured (JSON) logs + a correlation/trace id threaded via MDC let you pull every log line for one failed request across every service it touched
  • Tracing: spans nest under a shared trace id; context (traceparent header) is propagated hop-to-hop; a missing propagation hop splits one trace into two
  • OpenTelemetry = vendor-neutral instrumentation/export standard; Micrometer Tracing is Spring's facade over it; sample (e.g. 10%, always on errors) rather than tracing every request
  • Golden Signals = Latency, Traffic, Errors, Saturation; RED (Rate, Errors, Duration) for services; USE (Utilization, Saturation, Errors) for resources underneath them
  • SLI = measured indicator; SLO = internal target; SLA = external contractual promise (looser than SLO); Error budget = 1 - SLO, a spendable allowance for risk
  • Alert on user-facing symptoms tied to the SLO (burn-rate), not on internal causes; every page must be actionable and link a runbook, or it just causes alert fatigue
  • Liveness probe = "is this process unrecoverable, restart it"; Readiness probe = "can this instance serve traffic right now, otherwise pull it from the LB without restarting"
  • Never put a downstream dependency check on liveness - a transient DB blip would restart every replica at once instead of just draining traffic via readiness
