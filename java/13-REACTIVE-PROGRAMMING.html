13 - REACTIVE PROGRAMMING (PROJECT REACTOR & WEBFLUX) INTERVIEW HANDBOOK

The thread-per-request model that powers a typical Spring MVC / Tomcat application has a hard ceiling: every in-flight request holds a thread for its entire lifetime, and threads are expensive (roughly 1MB of stack each, plus context-switch overhead). When your service spends most of its time waiting on I/O, a downstream HTTP call, a database round trip, a message broker, that thread sits idle but still occupies memory and still counts against your pool size. Push enough concurrent slow requests through a fixed thread pool and the service falls over long before the CPU or the database is actually saturated. Reactive programming exists to break that coupling between "concurrent request" and "dedicated thread," which is exactly why senior interviews probe it so hard: it changes the programming model, the debugging story, and the operational profile of a service all at once. SECTION 1 - FUNDAMENTALS

Q1. What Problem Does Reactive Programming Solve?

ROI: ★★★★★ Frequency: Very High

Short Answer

Reactive programming exists to decouple the number of concurrent operations a service can handle from the number of OS threads it has available. In a traditional thread-per-request model (classic Spring MVC on Tomcat), every incoming request is assigned a dedicated thread that stays blocked for the full duration of the request, including all the time spent waiting on the network for a database, a downstream HTTP call, or a message broker to respond. Since threads are a scarce, heavyweight resource, a pool sized at, say, 200 threads can only have 200 requests in flight at once no matter how idle those threads actually are while waiting on I/O.

Most backend workloads are I/O-bound, not CPU-bound: the CPU is idle for the vast majority of a request's lifetime, waiting on a socket to return data. Reactive programming (non-blocking I/O plus an event-loop execution model) means a small, fixed number of threads can service thousands of concurrent in-flight operations, because a thread never blocks waiting for I/O. Instead, it registers a callback ("call me back when this data arrives") and immediately moves on to do other work. Throughput becomes bound by actual CPU work and I/O bandwidth rather than by thread-pool size, which is why reactive stacks shine specifically under high concurrency with slow, chatty downstream dependencies.

Interview Gold Point

Frame it as "threads are the scarce resource, not requests." Reactive programming does not make any individual request faster; a single request's latency is unchanged or even slightly worse due to the overhead of callbacks and context-switching between operators. What it buys you is handling far higher concurrency with a bounded, small thread count. If your service is CPU-bound or has low concurrency, this trade buys you nothing but complexity, a point interviewers want you to raise proactively (see Q13).

Q2. The Reactive Streams Spec: Publisher, Subscriber, Subscription, Processor

ROI: ★★★★☆ Frequency: High

Short Answer

Reactive Streams is a specification (not a library) that Project Reactor, RxJava, Akka Streams and the JDK's own java.util.concurrent.Flow all implement, which is why libraries built on different reactive stacks can interoperate. It defines four interfaces and, crucially, a backpressure protocol between them so that a fast producer cannot simply flood a slow consumer.

A Publisher<T> is a source of a potentially unbounded stream of T's; it emits items only when a subscriber asks for them. A Subscriber<T> consumes items and receives lifecycle callbacks: onSubscribe, then any number of onNext, terminated by exactly one onComplete or one onError. A Subscription is the contract object handed to the subscriber in onSubscribe; the subscriber calls subscription.request(n) to say "send me at most n more items" and subscription.cancel() to stop early. This request(n) call is the entire backpressure mechanism: nothing flows until the consumer asks for it. A Processor<T,R> is both a Subscriber and a Publisher at once, acting as a bridge/transformation stage in the middle of a pipeline. 

public interface Publisher<T> {
    void subscribe(Subscriber<? super T> s);
}

public interface Subscriber<T> {
    void onSubscribe(Subscription s);
    void onNext(T t);
    void onError(Throwable t);
    void onComplete();
}

public interface Subscription {
    void request(long n);  // pull-based backpressure signal
    void cancel();
}

Common Mistake

Describing Reactive Streams as "an async library." It is a low-level SPI that you almost never implement by hand; you consume it through a higher-level API like Reactor's Mono/Flux or RxJava's Observable, which implement Publisher for you and give you hundreds of composable operators. The interview-worthy detail is the pull-based request(n) protocol, that is the mechanism that separates Reactive Streams from a plain callback or an unbounded push-based Observer pattern.

Q3. Mono vs Flux - When to Use Each

ROI: ★★★★★ Frequency: Very High

Short Answer

Mono<T> and Flux<T> are Project Reactor's two Publisher implementations, and the difference is purely cardinality. A Mono emits at most one element followed by completion (or an error, or completion with zero elements); it is the reactive equivalent of Optional<T> or a CompletableFuture<T>. A Flux emits zero to N elements over time, potentially unbounded; it is the reactive equivalent of a Stream<T> or an async, backpressure-aware collection.

The choice is dictated entirely by the shape of the data. Fetching a single entity by id, a single row, the result of a single POST, is a Mono. Fetching a list of rows from a query, streaming server-sent events, or reading a paginated feed is a Flux. Getting this wrong shows up immediately in the type system: an operator like flatMap on a Mono still produces a Mono, so if you need "for each element, do an async call" over multiple items you need a Flux upstream, not a Mono wrapping a List (which reactively is still just one item: the whole list, arriving atomically with no element-by-element streaming or backpressure).

Aspect Mono<T> Flux<T>
Cardinality 0 or 1 element 0 to N elements (possibly infinite)
Analogy Optional<T> / CompletableFuture<T> Stream<T> / async Iterable<T>
Typical use findById, single POST result findAll, SSE stream, paginated feed
Blocking equivalent to unwrap mono.block() flux.collectList().block()

Interview Favorite

The crisp answer: "Mono is cardinality 0-1, Flux is cardinality 0-N; pick based on how many results the operation can produce, not based on habit." A good follow-up point to volunteer: both are cold by default, meaning nothing happens until something subscribes, which is a common source of "why didn't my side effect run" bugs when a Mono/Flux chain is built but never subscribed to.

Q4. Backpressure Strategies: Buffer, Drop, Latest, Error

ROI: ★★★★☆ Frequency: High

Short Answer

Backpressure is what happens when a producer emits items faster than a downstream consumer can process them. The Reactive Streams protocol makes the default behaviour "pull": the consumer requests exactly as many items as it can handle via request(n), and a well-behaved publisher never emits more than that. The hard cases are producers that cannot be told to slow down, a hot sensor feed, a UI event stream, an external push source, because the data exists whether or not anyone asked for it. For those, Reactor's onBackpressureXxx operators pick an overflow strategy.

Buffer. Queue the excess items in memory until the consumer catches up. Safe against data loss but risks unbounded memory growth and OutOfMemoryError if the consumer never catches up; you should cap the buffer size and choose an overflow behaviour once it is full. Drop. Silently discard the newest items that arrive while the consumer is still behind, keeping only what has already been requested. Appropriate when only recent-ish data matters and gaps are tolerable (metrics ticks). Latest. Keep only the single most recent item, discarding everything else in between; useful for things like a live price ticker where only the current value matters, not the history of values you missed. Error. Terminate the stream with an OverflowException the moment the consumer falls behind, which is the "fail loudly rather than silently lose or corrupt data" choice, appropriate when every item is business-critical (payment events).

Strategy Behaviour on overflow Best for
Buffer Queue items (bounded or unbounded) Bursty traffic, consumer briefly slower
Drop Discard newest arrivals Recent data only, gaps tolerable (metrics)
Latest Keep only the most recent item Live ticker / current-state feeds
Error Terminate with OverflowException Every item is critical (payments)

Interview Gold Point

The line to land: "Backpressure is not one thing, it is a policy decision about what you are willing to sacrifice when the producer outruns the consumer: memory (buffer), freshness (drop/latest), or availability (error)." Also mention that most of the time you never touch these operators directly, you just size your Schedulers and pipeline correctly so the consumer naturally keeps up; onBackpressureXxx is the escape hatch for genuinely unbounded, non-cooperative sources.

SECTION 2 - OPERATORS & THREADING

Q5. Key Operators: map vs flatMap vs concatMap

ROI: ★★★★★ Frequency: Very High

Short Answer

These three operators are the ones every reactive codebase leans on constantly, and confusing them is the single most common source of subtle bugs. map is a synchronous, 1-to-1 transformation: T -> R. It cannot be used to call another reactive/async operation, because it does not return a Publisher, it just transforms the value in place on the same emission.

flatMap is for when the transformation itself is asynchronous: it takes T -> Publisher<R>, subscribes to each inner publisher, and merges their emissions into the output stream as they arrive, meaning results can interleave and come back out of the original order. This is what you use to chain "for this order, look up the customer" where the lookup is itself a Mono/Flux. By default flatMap runs its inner publishers concurrently (with a configurable concurrency limit), which is exactly what makes it fast but also what makes ordering non-deterministic.

concatMap is flatMap's ordered sibling: it also maps to an inner Publisher, but subscribes to them strictly one at a time, in order, only moving to the next after the previous one completes. You trade throughput (no concurrency) for a guarantee that output order matches input order. Reach for concatMap when downstream ordering genuinely matters (writing rows to a file in sequence); reach for flatMap when it does not and you want maximum concurrency. 

// map: sync, 1-to-1, same thread/emission, order preserved trivially
Flux<String> upper = Flux.just("a", "b").map(String::toUpperCase);

// flatMap: async, inner publishers run concurrently, order NOT guaranteed
Flux<Customer> customers = orderIds
        .flatMap(id -> customerRepository.findByOrderId(id)); // may interleave

// concatMap: async, inner publishers run strictly in sequence, order guaranteed
Flux<Customer> orderedCustomers = orderIds
        .concatMap(id -> customerRepository.findByOrderId(id)); // slower, but ordered

Common Mistake

Using map with a method that secretly returns a Mono/Flux or, worse, blocks: map(id -> repo.findById(id).block()) compiles but reintroduces exactly the blocking-thread problem reactive programming was meant to avoid (see Q12). The rule of thumb: if the transformation is async, it must be flatMap or concatMap, never map. And if order matters, it must be concatMap (or flatMapSequential, which runs concurrently but re-buffers to restore order), never plain flatMap.

Q6. Schedulers & Thread Management: subscribeOn vs publishOn

ROI: ★★★★★ Frequency: Very High

Short Answer

By default a Reactor chain runs on whatever thread called subscribe(), it does not create threads for you. Schedulers are Reactor's abstraction over thread pools (Schedulers.parallel() for CPU-bound work sized to core count, Schedulers.boundedElastic() for blocking/IO-bound calls you cannot avoid, Schedulers.immediate() for no switch at all), and subscribeOn / publishOn are how you tell specific parts of the chain which scheduler to run on.

subscribeOn affects where the subscription itself, and therefore the source/upstream emission, happens. It only takes effect once per chain regardless of where you place it (the topmost one wins for the source), because subscription happens once, from the bottom of the chain up to the top. publishOn affects where execution happens for everything downstream of it, from that point in the chain onward, and you can place multiple publishOn calls to hop threads at different stages of the pipeline. The mental model: subscribeOn answers "which thread does the source start on," publishOn answers "which thread do subsequent operators run on from here down." 

Flux.range(1, 10)
    .subscribeOn(Schedulers.boundedElastic())   // source subscription happens here
    .map(this::step1)                            // still on boundedElastic
    .publishOn(Schedulers.parallel())            // hop threads from here down
    .map(this::step2)                            // now runs on parallel scheduler
    .subscribe(System.out::println);

Interview Gold Point

A question that separates people who read the docs from people who actually debugged this in production: "does the position of subscribeOn in the chain matter?" Answer: no, only one subscribeOn takes effect per subscription chain, and it governs the source, no matter where you write it. publishOn, by contrast, is position-sensitive and can appear multiple times. Also mention boundedElastic exists specifically so that unavoidable blocking calls (a legacy JDBC driver, a blocking SDK) can be quarantined onto a scheduler designed to absorb blocked threads, instead of starving the small, fixed event-loop pool.

SECTION 3 - WEBFLUX & R2DBC

Q7. WebFlux vs Spring MVC

ROI: ★★★★★ Frequency: Very High

Short Answer

Spring MVC runs on a Servlet container (typically embedded Tomcat) with a thread-per-request model: each request occupies one thread from a pool (default 200) for its entire lifecycle, blocking on any downstream I/O. It is synchronous, imperative, and easy to reason about with a debugger and a normal stack trace, which is a real advantage that gets underrated.

Spring WebFlux runs on Netty by default, using a small, fixed number of event-loop threads (typically one per CPU core). Requests are handled asynchronously and non-blockingly: a thread picks up a request, does non-blocking work until it would need to wait on I/O, registers a callback, and immediately moves to service other requests; when the I/O completes, a callback resumes the work, possibly on a different thread. WebFlux programming is built entirely around Mono/Flux and functional or annotated reactive controllers.

The trade-off is real, not just "WebFlux is strictly better." WebFlux shines under high concurrency with slow, I/O-heavy downstream calls, exactly the profile where thread-per-request runs out of threads. Spring MVC remains simpler to write, simpler to debug (a real, contiguous stack trace instead of one shredded across callbacks and schedulers), and is perfectly adequate, often preferable, for CRUD-heavy, low-to-moderate-concurrency services, especially if your database driver or key libraries are still blocking (in which case WebFlux buys you nothing end-to-end).

Aspect Spring MVC Spring WebFlux
Server Servlet container (Tomcat/Jetty) Netty (or Servlet 3.1+ async)
Concurrency model Thread-per-request, blocking Event loop, non-blocking
Threads under load Scales with concurrent requests (bounded by pool) Small, fixed (~1 per core)
Programming style Imperative, return T Reactive, return Mono<T>/Flux<T>
Debuggability Simple, contiguous stack traces Harder, stack traces span callbacks
Best fit CRUD, low/moderate concurrency, blocking drivers High concurrency, I/O-heavy, non-blocking drivers end-to-end

Interview Gold Point

The trap to avoid unprompted: "we switched to WebFlux and it got slower." That happens when the team keeps a blocking JDBC driver underneath and just wraps calls in Mono.fromCallable, which blocks an event-loop thread and can stall unrelated requests sharing that loop, worse than plain MVC because MVC's larger thread pool absorbs blocking far better than Netty's handful of loop threads. WebFlux only pays off when the entire call chain, web layer, database driver, HTTP client, is non-blocking end-to-end.

Q8. R2DBC - Reactive Relational Database Access

ROI: ★★★★☆ Frequency: High

Short Answer

JDBC is blocking by design, its API is built around synchronous calls that occupy the calling thread until the driver gets bytes back from the database socket, which makes it fundamentally incompatible with a non-blocking WebFlux pipeline: wrapping a JDBC call in a Mono still blocks whatever thread runs it. R2DBC (Reactive Relational Database Connectivity) is a separate driver-level SPI, implemented for Postgres, MySQL, SQL Server, H2 and others, that speaks to the database using non-blocking sockets and returns results as Publishers, so the entire path from controller to database can stay off the event loop.

Spring Data R2DBC gives you reactive repositories with the familiar ReactiveCrudRepository shape, returning Mono/Flux instead of the entity/List that Spring Data JPA returns. The catch: R2DBC is intentionally simpler than JPA, there is no first/second-level cache, no lazy loading, no dirty-checking, and its transaction and mapping story is less mature, so migrating an existing JPA-heavy codebase is a genuine rewrite, not a drop-in swap. 

public interface OrderRepository extends ReactiveCrudRepository<Order, Long> {
    Flux<Order> findByCustomerId(Long customerId);
}

@Service
class OrderService {
    private final OrderRepository repo;

    Mono<Order> place(Order order) {
        return repo.save(order)               // non-blocking write
                   .doOnNext(o -> log.info("saved {}", o.getId()));
    }

    Flux<Order> forCustomer(Long customerId) {
        return repo.findByCustomerId(customerId); // non-blocking, streams rows
    }
}

Common Mistake

Pairing WebFlux with plain Spring Data JPA "because it already works" and assuming you get end-to-end non-blocking behaviour. You do not: every repository call still blocks a thread under the hood. If you must keep JPA for its maturity, the honest architecture is either stay on Spring MVC, or explicitly offload the blocking JPA calls onto Schedulers.boundedElastic() from within the reactive pipeline, acknowledging you have a blocking island inside a reactive service, not a fully reactive stack.

SECTION 4 - ERROR HANDLING, TESTING & COMBINING STREAMS

Q9. Error Handling in Reactive Chains

ROI: ★★★★★ Frequency: Very High

Short Answer

In a reactive chain a try/catch around subscribe() does nothing useful, because the exception is thrown asynchronously on whatever thread the operator was running on, long after your calling code has moved past the subscribe call. Errors instead propagate as a terminal signal, onError, down the chain, and you handle them with dedicated operators, not exception handling syntax.

onErrorReturn supplies a static fallback value and completes the stream, use it when any failure has one reasonable default (return an empty result). onErrorResume lets you switch to an entirely different Publisher on error, for example falling back to a cache or a secondary service, giving you access to the actual exception to decide the recovery path. onErrorMap translates one exception type into another (a driver-specific exception into your own domain exception) without altering the stream's outcome. retry(n) / retryWhen(spec) resubscribes to the upstream on failure, ideally with a backoff spec (retryWhen with Retry.backoff), for transient failures like a brief network blip. 

Mono<Product> product = productClient.fetch(id)
        .timeout(Duration.ofSeconds(2))
        .retryWhen(Retry.backoff(3, Duration.ofMillis(200))
                        .filter(ex -> ex instanceof TimeoutException))
        .onErrorResume(ex -> cacheRepository.findById(id))   // fallback path
        .onErrorReturn(Product.unavailable());                // last-resort default

Interview Gold Point

The distinction interviewers probe: onErrorReturn vs onErrorResume. onErrorReturn gives you one fixed fallback value and no visibility into the actual exception at the call site; onErrorResume gives you the exception and lets you return a whole alternate Publisher, so it composes (you can chain another async fallback, log, or rethrow a translated error). Order matters too: place retryWhen before onErrorResume so the retry logic gets a chance to recover first, with the resume/return as the true last resort.

Q10. Testing Reactive Code with StepVerifier

ROI: ★★★★☆ Frequency: High

Short Answer

Reactive publishers are cold and asynchronous, so a plain JUnit assertion on a Mono/Flux object tells you nothing, the chain has not necessarily run yet, and if it has, you have no clean way to assert on the sequence of emissions or timing. Reactor Test's StepVerifier subscribes to the publisher itself and lets you declaratively assert on every signal it emits, in order, including completion and error.

It is the standard tool for unit-testing anything returning Mono/Flux, and it also has a withVirtualTime() mode that lets you fast-forward through operators like delayElements or timeouts without your test actually sleeping for real wall-clock time, which is what keeps a suite full of these tests fast. 

@Test
void emitsCustomersInOrder() {
    StepVerifier.create(orderIds.concatMap(customerRepository::findByOrderId))
                .expectNext(customerA)
                .expectNext(customerB)
                .expectComplete()
                .verify(Duration.ofSeconds(1));
}

@Test
void retriesThenFallsBackAfterVirtualTime() {
    StepVerifier.withVirtualTime(() -> flakyService.call().retryWhen(Retry.backoff(3, Duration.ofSeconds(1))))
                .thenAwait(Duration.ofSeconds(10))  // fast-forwarded, not real time
                .expectNextCount(1)
                .verifyComplete();
}

Common Mistake

Calling .block() on the publisher inside a test just to get a plain value to assert on with standard JUnit assertions. It "works" for simple cases but throws away the whole point of testing a reactive chain: you no longer verify emission order, backpressure behaviour, or that no more/no fewer elements than expected were produced, and it can mask bugs that only appear under proper subscription/request semantics. Reach for StepVerifier for anything beyond the most trivial single-value Mono.

Q11. Combining Streams: zip, merge, combineLatest

ROI: ★★★☆☆ Frequency: Medium

Short Answer

These three combine multiple publishers into one, and picking the wrong one produces subtly wrong pairing or timing behaviour. zip pairs up the Nth element of each source positionally, waiting until every source has produced its Nth item before emitting a combined tuple; it completes as soon as the shortest source completes. Use it when you need "the result of these N independent async calls, combined once all are ready," for example fetching a user profile and their preferences in parallel and combining both.

merge interleaves emissions from multiple sources as they arrive, with no pairing at all, you get a single Flux containing every item from every source, in whatever order they actually complete. Use it to fan multiple independent streams into one, for example merging log events from several services into one feed.

combineLatest emits a new combined value every time any one of the sources emits, always pairing it with the most recently seen value from each of the other sources. Use it for scenarios like recomputing a derived value (a total price) whenever any one of several inputs (quantity, discount, tax rate) changes, where you want the freshest combination, not a one-shot pairing. 

// zip: waits for one value from each, pairs positionally, completes at shortest
Mono<Pair> combined = Mono.zip(userClient.getProfile(id), userClient.getPrefs(id))
                            .map(t -> new Pair(t.getT1(), t.getT2()));

// merge: interleaves whatever arrives from either source, no pairing
Flux<LogEvent> allLogs = Flux.merge(serviceALogs, serviceBLogs);

// combineLatest: recompute whenever ANY source emits, using latest from others
Flux<BigDecimal> total = Flux.combineLatest(
        quantity, discount, (q, d) -> q.multiply(d));

Interview Favorite

One line that shows real fluency: "zip pairs by position and waits for all; merge just interleaves with no pairing; combineLatest re-pairs on every emission using the latest from each source." The most common mix-up is reaching for merge when zip was needed, which produces N separate uncombined items instead of the paired result the caller actually wanted.

SECTION 5 - PITFALLS & WHEN TO USE REACTIVE

Q12. Common Pitfall: Accidentally Blocking Inside a Reactive Chain

ROI: ★★★★★ Frequency: Very High

Short Answer

This is the single most damaging and most common reactive bug in production, and interviewers ask about it because it is exactly the kind of mistake that passes code review and even passes tests, then quietly degrades throughput or causes intermittent stalls under load. WebFlux runs on a small, fixed pool of event-loop threads (Netty's worker threads, typically one per CPU core). Any blocking call, a JDBC query, a synchronous HTTP client, a Thread.sleep, a synchronized block that waits, made from inside a reactive operator occupies one of those precious few threads until it returns. Because that same handful of threads services every other in-flight request on that event loop, one blocked call can stall unrelated requests that have nothing to do with the offending code path, an effect that is invisible in isolated testing and only shows up as mysterious latency spikes under real concurrent load.

Common disguises for this bug: calling .block() inside a map/flatMap instead of at the very edge of the application (a WebFlux app should ideally never call block() at all, except perhaps in a main method or a test); using a blocking JDBC repository from a reactive service without explicitly moving it to boundedElastic; or calling a legacy synchronous SDK (an old cloud storage or payment client) directly inside an operator. Reactor even ships a BlockHound instrumentation library specifically to detect blocking calls on non-blocking threads at test or runtime, because the bug is otherwise so easy to miss. 

// WRONG: blocks a Netty event-loop thread, can stall unrelated requests
Mono<Order> bad = Mono.fromCallable(() -> legacyBlockingRepo.findById(id));

// RIGHT: explicitly quarantine the unavoidable blocking call
Mono<Order> ok = Mono.fromCallable(() -> legacyBlockingRepo.findById(id))
                      .subscribeOn(Schedulers.boundedElastic());

Interview Gold Point

The senior framing: "In a WebFlux app, block() is a code smell everywhere except the outermost edge; every unavoidable blocking call must be explicitly wrapped and pushed onto boundedElastic, never left on the default execution context." Mentioning BlockHound by name, and that you would wire it into integration tests to fail the build on undeclared blocking calls, is a strong signal of production experience rather than tutorial-level familiarity.

Q13. When NOT to Use Reactive Programming

ROI: ★★★★☆ Frequency: High

Short Answer

Reactive programming is a genuine complexity tax: harder debugging (stack traces are shredded across schedulers and callbacks), a steeper learning curve for the whole team, fewer mature libraries and drivers (many blocking-only clients have no reactive equivalent), and code that is objectively harder to read for engineers who have not internalized the operator vocabulary. Paying that tax only makes sense when you are actually buying something with it, which is not always true.

Skip reactive when the workload is CPU-bound rather than I/O-bound: reactive buys you concurrency headroom on I/O waits, it does nothing for a service that is genuinely limited by computation, sorting, encryption, image processing, where more threads or better algorithms are the actual lever. Skip it for simple CRUD services with low-to-moderate concurrency and a blocking database driver already in place; the thread-per-request model handles that load just fine, and switching frameworks without switching the driver gains you nothing while adding risk. Skip it when the team is unfamiliar with the reactive style and the project timeline does not allow for the ramp-up, since debugging production incidents in an unfamiliar reactive stack under time pressure is a genuinely worse position than a simple, blocking codebase everyone understands. And skip it if key dependencies (a required SDK, an ORM you are committed to) are blocking-only, since a "reactive" web layer sitting on top of blocking calls is often worse than plain MVC (see Q7).

Common Mistake

Adopting WebFlux because it is "the modern way" without a concurrency problem to solve. The honest interview answer is a checklist, not a verdict: high concurrency + I/O-bound + non-blocking drivers available end-to-end + team has the appetite to learn it, only when most of those are true does reactive pay for itself. Otherwise you are trading a well-understood, debuggable stack for one that is harder to reason about, for no real throughput benefit.

Q14. Reactive vs Virtual Threads (Project Loom) - How Loom Changes the Calculus

ROI: ★★★★★ Frequency: Very High

Short Answer

Virtual threads (JEP 444, standard since Java 21) attack the exact same problem reactive programming solves, the thread-per-request ceiling, but from the opposite direction. Instead of rewriting your code to avoid blocking, Loom makes blocking cheap: a virtual thread is a lightweight, JVM-managed thread that, when it blocks on I/O, gets unmounted from its carrier OS thread automatically, freeing that OS thread to run other virtual threads. You write completely ordinary, imperative, blocking-looking code, a normal JDBC call, a normal synchronous HTTP client, and the JVM handles the thread multiplexing for you under the hood. You can spin up millions of virtual threads because each one is orders of magnitude cheaper than a platform thread.

This directly undercuts a large share of reactive programming's traditional justification for plain thread-per-request-shaped code: you get most of the concurrency benefit, escaping the OS-thread ceiling, without adopting Mono/Flux, operator chains, or schedulers, and you keep normal stack traces and normal debuggers. Spring's virtual-threads support (via a Tomcat/Jetty executor swap, one property in Spring Boot 3.2+) lets an existing, ordinary Spring MVC application scale to high concurrency essentially for free.

Reactive still has a place. Backpressure as a first-class concept (a slow consumer explicitly telling a fast producer to slow down) is not something virtual threads give you; that remains a Reactor/Reactive Streams concern. Rich stream composition and combination operators (zip, merge, windowing, complex operator pipelines) are still more expressive in Reactor than in blocking code, even blocking code running on virtual threads. And virtual threads do not help CPU-bound work at all, nor do they fix code that holds a synchronized monitor across a blocking call (pinning the virtual thread to its carrier). For a brand-new service whose only goal is "handle high concurrency of I/O-bound calls without adopting a whole new programming model," many teams in 2025/2026 now default to Spring MVC plus virtual threads over full WebFlux, reserving reactive for genuine streaming/backpressure needs.

Aspect Reactive (WebFlux/Reactor) Virtual Threads (Loom)
Programming style Functional, Mono/Flux, operators Ordinary imperative, blocking-looking code
Debuggability Harder, shredded stack traces Normal, contiguous stack traces
Solves thread ceiling? Yes, by never blocking Yes, by making blocking cheap
Native backpressure Yes, part of Reactive Streams No, not a first-class concept
Driver requirement Needs non-blocking drivers (R2DBC etc.) Works with existing blocking drivers (JDBC)
Adoption cost High: new paradigm, retrain team Low: swap executor, keep existing code

Interview Gold Point

The nuanced take interviewers want in 2026: "Loom does not make Reactor obsolete, it removes the main reason most teams reached for reactive in the first place, escaping the thread-per-request ceiling, so the remaining case for reactive narrows to genuine streaming/backpressure/complex-composition needs rather than 'we have a lot of concurrent I/O.'" Bringing up carrier-thread pinning (blocking inside a synchronized block still blocks the carrier, not just the virtual thread) shows you understand Loom's actual limitations rather than treating it as a silver bullet.

SECTION 6 - REACTOR INTERNALS: ASSEMBLY, SUBSCRIPTION & EXECUTION

Q15. Assembly Time vs Subscription Time vs Execution Time

ROI: ★★★★★ Frequency: Very High

Short Answer

A Reactor chain has three distinct phases that are easy to conflate, and interviewers use this question specifically to see whether you actually understand the "nothing happens until subscribe()" model or just recite it. Assembly time is when you call operators like map, filter, flatMap to build the chain; each operator call wraps the previous Publisher in a new Publisher and returns immediately. No data flows and no user code inside the operators executes yet, you are only constructing an object graph, a declarative recipe describing what should happen.

Subscription time begins when subscribe() is called (directly, or by a framework like WebFlux calling it on your returned Mono/Flux). This triggers a wave of onSubscribe calls that travels from the bottom of the chain (the final subscriber) up to the top (the original source), each operator's Subscriber requesting a Subscription from the operator above it. Execution time is when data actually flows: the source starts emitting, and each onNext/onComplete/onError signal travels back down from source to subscriber, running your operator lambdas (map functions, doOnNext callbacks) as it passes through each stage. 

Mono<String> mono = Mono.fromSupplier(() -> {
    System.out.println("side effect running"); // executes at EXECUTION time
    return "value";
}).map(s -> s.toUpperCase());                    // built at ASSEMBLY time

// nothing has printed yet - only a Publisher graph has been assembled
System.out.println("chain built");

mono.subscribe(System.out::println);
// NOW: subscription time (onSubscribe travels bottom-up)
// then: execution time ("side effect running" prints, then "VALUE")

Interview Gold Point

The line that shows real fluency: "assembly builds the recipe, subscription wires up the request(n) chain from the bottom up, execution runs the recipe from the top down." This model directly explains a whole class of bugs: a Mono/Flux built inside a method but never subscribed to (e.g. forgetting to return it, or assigning it to a variable and discarding the variable) silently does nothing, no exception, no log, because assembly happened but subscription never did.

Q16. Cold vs Hot Publishers

ROI: ★★★★☆ Frequency: High

Short Answer

A cold publisher re-runs its entire source logic independently for every subscriber; each subscription gets its own private sequence starting from the beginning. Most Reactor sources you build with Flux.just, Mono.fromCallable, a repository query, are cold: subscribe twice and the database query (or computation) runs twice, and each subscriber sees the full sequence regardless of when it subscribed.

A hot publisher runs its source once regardless of how many subscribers are attached, and broadcasts the same emissions to all of them; a subscriber that arrives late simply misses whatever was already emitted before it subscribed, unless the hot source explicitly replays history. Hot sources model things that happen whether or not anyone is listening: a live sensor feed, a shared WebSocket connection, an event bus. Getting this distinction wrong is a classic reactive bug: treating a cold Flux as if it were shared (assuming two subscribers see the same emissions, or assuming a side effect only runs once) when in fact each subscription triggers its own independent execution. 

Flux<Integer> cold = Flux.defer(() -> {
    System.out.println("source executed");
    return Flux.just(1, 2, 3);
});
cold.subscribe(); // prints "source executed"
cold.subscribe(); // prints "source executed" AGAIN - independent run

Sinks.Many<Integer> hotSink = Sinks.many().multicast().onBackpressureBuffer();
Flux<Integer> hot = hotSink.asFlux();
hot.subscribe(v -> System.out.println("A saw " + v));
hotSink.tryEmitNext(1);
hot.subscribe(v -> System.out.println("B saw " + v)); // B missed 1, joins late
hotSink.tryEmitNext(2); // both A and B see 2

Common Mistake

Assuming that calling .subscribe() a second time on the same Mono/Flux variable reuses the first subscription's results. For a cold publisher (the overwhelming majority of what you build day to day) it does not, it reruns the whole upstream, including any database call or side effect. If you need "run once, share the result with multiple subscribers," reach for cache() (cold source, replays cached result) or convert to hot with share()/a ConnectableFlux (see Q17).

Q17. ConnectableFlux and Flux.share()

ROI: ★★★☆☆ Frequency: Medium

Short Answer

publish() converts a cold Flux into a ConnectableFlux, a hot publisher that will not start emitting until you explicitly call .connect() on it, regardless of how many subscribers have already attached. This lets you gather multiple subscribers first, guaranteeing none of them misses early emissions, then start the single shared upstream execution on your own schedule. It is the tool of choice when you need precise control over exactly when a shared source begins running, for example coordinating several downstream consumers to all start from the same emission.

share() is the convenience version most code actually uses: it is shorthand for publish().refCount(1), meaning the upstream automatically connects as soon as the first subscriber arrives, and automatically disconnects (cancelling the upstream) when the last subscriber leaves. This gives you "multiple subscribers share one upstream execution" without manually managing a ConnectableFlux's connect/dispose lifecycle, at the cost of subscribers that arrive after the first one potentially missing emissions that already happened. 

Flux<Long> ticks = Flux.interval(Duration.ofSeconds(1)).share();
// first subscriber triggers the interval to start
ticks.subscribe(t -> log.info("consumer1 {}", t));
// second subscriber joins the SAME running interval, may miss earlier ticks
ticks.subscribe(t -> log.info("consumer2 {}", t));

Interview Favorite

A crisp answer: "publish() gives you a ConnectableFlux you connect manually for precise control; share() is publish().refCount(1), auto-connecting on the first subscriber and auto-disconnecting when the last one leaves." Mention replay() too if pressed further (Q18) — it is the variant that lets late subscribers catch up on some or all history instead of only seeing emissions from the moment they joined.

Q18. Flux.publish() vs Flux.replay()

ROI: ★★★☆☆ Frequency: Medium

Short Answer

Both turn a cold Flux into a shareable, connectable hot source, and both require an explicit .connect() (or an autoConnect/refCount variant) to actually start the upstream. The difference is what a late-arriving subscriber sees. With publish(), a subscriber only receives emissions that happen from the moment it subscribes onward; anything emitted before it joined is gone forever as far as that subscriber is concerned. With replay(), the ConnectableFlux buffers some or all past emissions (you can bound it by count, by time, or leave it unbounded) and replays that buffered history to every new subscriber before it starts receiving live emissions.

replay() trades memory for completeness: an unbounded replay buffer on a long-lived, high-volume Flux is a memory leak waiting to happen, so in practice you almost always bound it (replay(n) for the last n items, or replay(Duration) for a time window).

Common Mistake

Reaching for replay() "just in case" without bounding it. On a genuinely long-lived hot stream (an event bus running for the app's whole lifetime), an unbounded replay buffer grows without limit and eventually exhausts memory. Always bound it explicitly with a count or duration unless you can prove the stream is short-lived or low-volume.

Q19. Why "Nothing Happens Until subscribe()" Breaks Side-Effect Assumptions

ROI: ★★★★☆ Frequency: High

Short Answer

This is the single most common source of "my reactive code silently does nothing" bugs, and it directly follows from Q15's assembly/subscription/execution model. Because a Mono/Flux is a cold, lazy description of work rather than a running computation, building the chain and discarding the result (never subscribing, or never returning it to a caller like WebFlux that will subscribe on your behalf) means the described work simply never runs, with no exception thrown anywhere, because from the framework's point of view nothing went wrong: you just never asked for the result.

This shows up constantly in code that mixes imperative habits with reactive types: calling a repository's reactive save method inside a for loop or an if-branch as a "fire and forget" statement, the way you would call a void method, without chaining it into the returned pipeline or explicitly subscribing. The save is built (assembled) but never triggered, so nothing is ever persisted, and the bug is invisible until someone notices missing data days later. 

// WRONG: builds a Mono describing a save, but never subscribes to it - nothing happens
void badSave(Order order) {
    repository.save(order); // return value discarded, never subscribed
}

// RIGHT: return it so the framework (or caller) subscribes, or chain/subscribe explicitly
Mono<Order> goodSave(Order order) {
    return repository.save(order);
}

Interview Gold Point

The rule to state explicitly: "a Mono/Flux that is built but never subscribed to, directly or by returning it to something that will subscribe, is inert; it is not a command, it is a description of a command." This is exactly why linters/IDE inspections flag "reactive type is never consumed" and why code review in a reactive codebase must specifically check that every Mono/Flux returned from a repository or client call is actually wired into the response chain.

SECTION 7 - CONTEXT PROPAGATION

Q20. Why Doesn't ThreadLocal Work Across Reactive Async Boundaries?

ROI: ★★★★☆ Frequency: High

Short Answer

ThreadLocal works by attaching a value to whatever thread is currently executing, on the assumption that a single logical operation (a request) stays on one thread from start to finish. That assumption is exactly what a reactive pipeline breaks: a single Mono/Flux chain routinely hops across multiple threads, subscribeOn switches the source's thread, publishOn switches downstream execution, an async I/O callback resumes on a Netty event-loop thread that has nothing to do with whichever thread initiated the request. A value stashed in a ThreadLocal before a thread-hop is simply invisible after it, because a different thread is now running the rest of the chain and it has its own, unrelated ThreadLocal storage.

This directly breaks anything that leaned on ThreadLocal in the blocking world: SLF4J's MDC for structured logging (request id, user id), Spring Security's SecurityContextHolder in its default ThreadLocal-backed strategy, and any custom per-request context object. In a reactive app these patterns need a mechanism that travels with the data through the chain rather than living on whichever thread happens to be executing at a given moment, which is exactly what Reactor's Context solves.

Interview Gold Point

The framing that shows you understand the mechanism, not just the symptom: "ThreadLocal is a property of a thread; a reactive chain's identity is the subscription, not any one thread, since it can run on several threads over its lifetime. State needs to be attached to the subscription/signal, not the thread, which is what Reactor Context is for."

Q21. How Does Reactor's Context / ContextView Solve This?

ROI: ★★★★☆ Frequency: High

Short Answer

Reactor's Context is an immutable, key-value store that is attached to the subscription, not to any thread. Every Subscriber in the chain has access to the Context of the subscription it belongs to, and critically, Context is propagated from the bottom of the chain upward, and is visible to operators above the point where it was written, regardless of which thread ends up executing them. You write to it with .contextWrite(...) (placed anywhere in the chain, but only visible to operators upstream of that point) and read it inside an operator via Mono.deferContextual(...) / Flux.deferContextual(...), or through operators that expose a ContextView parameter directly.

Because Context lives on the subscription rather than the thread, it survives every subscribeOn/publishOn hop untouched, exactly the property ThreadLocal lacked. It is immutable by design, writing to it produces a new Context, so there is no risk of one part of the chain mutating state another part depends on, which also makes it inherently safe for the concurrent, multi-subscriber scenarios reactive code routinely creates. 

Mono<String> withCorrelationId = Mono.deferContextual(ctx ->
        callDownstream(ctx.get("correlationId")) // read: available to whatever thread runs this
    )
    .contextWrite(ctx -> ctx.put("correlationId", UUID.randomUUID().toString()));
    // write: visible only to operators ABOVE this point in the chain

Common Mistake

Expecting contextWrite to be visible downstream, the way a normal imperative variable assignment would be. Context propagation in Reactor flows upstream (from where it is written toward the source), which is the opposite of the data flow direction (which flows from source toward the subscriber). Placing contextWrite too low in the chain is a very common reason "the context value I set is null" bugs happen; it must be written at or below (closer to the subscriber than) every operator that needs to read it.

Q22. Practical Use Case: Propagating a Correlation ID Through a Reactive Chain

ROI: ★★★☆☆ Frequency: Medium

Short Answer

The most common real-world use of Reactor Context is distributed tracing and structured logging: a WebFlux filter extracts (or generates) a correlation/trace id from an incoming request, writes it into the Context at the top of the request-handling chain, and every downstream service call, repository query and log statement anywhere in that chain reads it back out, without needing to thread it through every method signature manually as an explicit parameter.

Because plain SLF4J MDC is ThreadLocal-backed and therefore unreliable across reactive thread-hops, teams either bridge Reactor Context into MDC at each operator boundary (Reactor's Hooks.onEachOperator combined with a Context read, or libraries like reactor-core's own logging integration, and Micrometer's Observation API and Micrometer Tracing now do a lot of this bridging automatically) or they simply log with the correlation id read explicitly out of the ContextView at each log statement rather than relying on MDC at all.

Interview Gold Point

Worth naming explicitly: Micrometer Tracing (and Spring Boot 3.x's default observability stack) already automates most of this Context-to-MDC bridging for standard span/trace ids, so in a modern Spring Boot 3 app you often get correlated logs "for free" and only need to reach for manual Context read/write when propagating your own custom, business-specific correlation data.

Q23. Common Context Pitfalls in Practice

ROI: ★★★☆☆ Frequency: Medium

Short Answer

Beyond the upstream-only visibility rule (Q21), two other pitfalls come up constantly. First, Context is per-subscription and immutable, so a common mistake is trying to mutate a mutable object stored inside the Context (a HashMap, say) instead of writing an entirely new Context with .put(); mutating a stored object works but defeats the safety guarantees Context is designed to provide and can create subtle sharing bugs across concurrent subscriptions.

Second, Context does not automatically cross a reactive-to-imperative-to-reactive boundary. If you call .block() partway through a pipeline, or hand off to a plain CompletableFuture-based library and later wrap its result back into a Mono, whatever Context existed on the original subscription is not implicitly threaded through that gap, since the imperative code in between has no notion of Reactor's Context at all. Any code path that leaves and re-enters the reactive world needs to explicitly re-attach whatever Context state it still needs.

Common Mistake

Assuming Context "just works" across every kind of boundary the way a ThreadLocal-based framework used to. It only works within an unbroken chain of Reactor operators on the same subscription; any drop into blocking code, a different async abstraction, or a manually created new subscription breaks the chain, and the Context must be re-threaded explicitly if it is still needed on the other side.

SECTION 8 - THE SINKS API

Q24. What Is the Sinks API and Why Does It Replace FluxProcessor?

ROI: ★★★★☆ Frequency: High

Short Answer

Before Reactor 3.4, the way to manually push values into a reactive stream (a "programmatic" source, as opposed to one derived from an existing Publisher) was to implement FluxProcessor directly, or implement the Reactive Streams Subscriber/Publisher interfaces yourself. Both approaches exposed far more surface area than most use cases needed, and made it easy to violate the Reactive Streams protocol by accident (calling onNext concurrently from multiple threads without synchronization, for example, which silently corrupts a Publisher's contract).

The Sinks API (Sinks.Many, Sinks.One, Sinks.Empty) is Reactor's purpose-built, much narrower replacement: it gives you exactly two operations, a way to push a value/error/completion in, and a way to get a Flux/Mono view out to subscribe to, with the framework handling the Reactive Streams protocol correctness for you. It explicitly separates the producer-facing side (Sinks.Many, which you call tryEmitNext on) from the consumer-facing side (the Flux you get from .asFlux(), which callers subscribe to), which is a cleaner separation of concerns than Processor's dual Subscriber-and-Publisher role. 

Sinks.Many<String> sink = Sinks.many().multicast().onBackpressureBuffer();
Flux<String> flux = sink.asFlux(); // consumer-facing view

flux.subscribe(System.out::println);
sink.tryEmitNext("hello"); // producer-facing push
sink.tryEmitComplete();

Common Mistake

Reaching for a hand-rolled Subscriber implementation, or the deprecated FluxProcessor/DirectProcessor/EmitterProcessor types, in new code. As of modern Reactor, Sinks is the documented, supported way to manually produce signals; the older Processor types are deprecated specifically because Sinks enforces correct concurrent-access semantics that hand-rolled implementations routinely got wrong.

Q25. Sinks.many() Variants: Unicast, Multicast, Replay

ROI: ★★★☆☆ Frequency: Medium

Short Answer

Sinks.many().unicast() supports exactly one subscriber; a second subscription attempt fails with an error, because a unicast sink's internal queue is designed to be drained by a single consumer and has no logic for distributing items across several. Use it for a strict single-producer/single-consumer bridge, for example adapting one callback-based connection into one reactive stream.

Sinks.many().multicast() supports multiple subscribers and broadcasts each emitted item to all of them (a hot-publisher shape), but by default a subscriber only receives items emitted after it subscribes, exactly like publish()'s late-subscriber semantics discussed in Q17/Q18. Sinks.many().replay() is the multicast variant that also buffers some or all history (bounded with .limit(n) or left effectively unbounded with .all()) and replays it to every new subscriber before they start receiving live emissions.

Variant Subscribers Late subscriber sees
unicast() Exactly one N/A - second subscriber errors
multicast() Many Only emissions from the moment it joins
replay() Many Buffered history, then live emissions

Interview Favorite

The concise version: "unicast is one consumer only; multicast broadcasts live only; replay broadcasts with a history buffer for late joiners." Also mention onBackpressureBuffer()/onBackpressureError() overflow qualifiers that most of these factory methods take, which decide what happens if a subscriber falls behind, mirroring the same buffer/drop/latest/error policy choice from Q4.

Q26. Emission Failure Handling: tryEmitNext vs emitNext

ROI: ★★★☆☆ Frequency: Medium

Short Answer

tryEmitNext(value) is the non-throwing, result-returning emission method: it returns a Sinks.EmitResult enum value (OK, FAIL_TERMINATED, FAIL_OVERFLOW, FAIL_NON_SERIALIZED, and others) describing exactly why the emission did or did not succeed, and it is the recommended default because it forces you to consciously decide what to do on failure rather than letting an exception propagate from an unexpected place.

emitNext(value, EmissionFailureHandler) is the alternative that takes a retry-strategy callback invoked on failure, letting you, for example, busy-spin briefly and retry on a transient concurrent-access failure (FAIL_NON_SERIALIZED, which happens if two threads call emit methods concurrently on a sink that requires serialized access) instead of dropping the value. The most commonly seen failure in practice is FAIL_NON_SERIALIZED, which is a strong signal that emissions are happening from multiple threads without external synchronization, since most Sinks.Many implementations require serialized (one-at-a-time) producer calls. 

Sinks.EmitResult result = sink.tryEmitNext(value);
if (result.isFailure()) {
    log.warn("emission failed: {}", result);
}

Common Mistake

Calling a sink's emit methods concurrently from multiple threads without any external synchronization and being surprised by FAIL_NON_SERIALIZED. Reactive Streams requires that onNext calls on a given Subscriber never happen concurrently; Sinks enforces this at the emission point rather than silently corrupting internal state, which is exactly the protocol-correctness benefit over a hand-rolled Subscriber that Q24 highlights.

Q27. Bridging a Callback-Based API Into Reactor Using Sinks

ROI: ★★★☆☆ Frequency: Medium

Short Answer

A very common real-world use of Sinks is adapting a legacy, callback-style API (a message listener, a WebSocket handler, an SDK that calls your registered callback whenever new data arrives) into a proper reactive Publisher that the rest of your pipeline can subscribe to with full backpressure support. You create a sink once, register its emit methods as the callback the legacy API invokes, and expose the sink's .asFlux()/.asMono() view to the rest of the application. 

Sinks.Many<Message> sink = Sinks.many().unicast().onBackpressureBuffer();

legacyMessageListener.onMessage(msg -> {
    Sinks.EmitResult result = sink.tryEmitNext(msg);
    if (result.isFailure()) {
        log.warn("dropped message, sink emission failed: {}", result);
    }
});

Flux<Message> messages = sink.asFlux(); // rest of the app subscribes to this

Interview Gold Point

A strong signal of hands-on experience: noting that for a simpler one-shot bridge (adapting a single async callback into exactly one value), Mono.create(sink -> ...) is often a lighter-weight fit than a full Sinks.One, while Sinks proper is what you reach for when you need to hold onto the producer-side handle across multiple calls (a long-lived listener registration), rather than a single inline callback.

SECTION 9 - SCHEDULERS IN DEPTH

Q28. Scheduler Types In Depth: parallel() vs boundedElastic() vs immediate() vs a Custom Scheduler

ROI: ★★★★★ Frequency: Very High

Short Answer

Schedulers.parallel() is a fixed-size pool sized to Runtime.availableProcessors(), intended strictly for short, non-blocking, CPU-bound work. Because it has exactly as many threads as CPU cores, blocking even one of them for any meaningful duration starves the rest of the application of CPU-bound processing capacity; this pool must never see a blocking call.

Schedulers.boundedElastic() is designed for exactly the opposite case: unavoidable blocking or I/O calls (a legacy JDBC driver, a blocking SDK, a synchronous file read) that you cannot make non-blocking. It maintains a bounded but large pool (by default 10x the CPU core count, with a bounded backlog queue beyond that), creating threads on demand and reclaiming idle ones, so it can absorb many concurrently blocked threads without the unbounded growth risk of the old, now-removed Schedulers.elastic().

Schedulers.immediate() performs no thread switch at all, running the operator on whatever thread called it; it is mostly used internally, or when you deliberately want to cancel out an upstream publishOn/subscribeOn for testing or composition reasons. A custom Scheduler, built with Schedulers.newBoundedElastic(...), Schedulers.newParallel(...), or wrapping your own ExecutorService via Schedulers.fromExecutorService(...), is appropriate when you need isolation, a dedicated, sized pool for one specific downstream dependency so that a problem with that dependency (say, a slow third-party API) cannot exhaust the shared boundedElastic pool and starve unrelated blocking calls elsewhere in the app.

Scheduler Sizing Use for
parallel() Fixed, = CPU cores Short CPU-bound work only, never blocking
boundedElastic() Bounded, elastic (~10x cores + queue) Unavoidable blocking/IO calls
immediate() No pool, runs on calling thread No-op thread switch, testing/composition
custom You define size and isolation Isolating one risky dependency from the shared pool

Interview Gold Point

The senior-level distinction to volunteer: boundedElastic is bounded and backpressure-aware (it queues excess tasks up to a configurable limit and then rejects), specifically as a reaction to the old unbounded elastic() scheduler having caused real production outages via unbounded thread creation. Knowing that history, and being able to name the default sizing (~10x cores, with a default 100k task queue), is a strong signal of production depth over tutorial-level knowledge.

Q29. The Classic Incident: A Blocking Call Scheduled on parallel()

ROI: ★★★★★ Frequency: Very High

Short Answer

This is one of the most common real production incidents in reactive systems, and it is a direct, more insidious cousin of the Q12 "accidental blocking on the event loop" bug: a developer explicitly calls .subscribeOn(Schedulers.parallel()) around a call they believe is CPU-bound or fast, but which actually blocks, a supposedly in-memory cache lookup that occasionally falls through to a blocking network call, a regex operation that pathologically backtracks, a JSON library that blocks on a lazy classloading step the first time it runs. Because parallel() has only as many threads as CPU cores, blocking even one of them removes a meaningful fraction of the entire application's CPU-bound processing capacity, not just capacity for that one call.

The failure mode is uniquely nasty because it degrades gradually and non-deterministically: under low load the blocked calls are rare and brief enough that nobody notices; under production load, several unrelated CPU-bound operations across the whole service start queueing behind the same small, saturated parallel() pool, producing service-wide latency spikes that look like "everything is slow" with no obvious single culprit, since the actual blocking call may be a small percentage of total traffic. 

// WRONG: assumed fast/CPU-bound, actually blocks occasionally - starves parallel() pool
Mono.fromCallable(() -> maybeBlockingCacheLookup(key))
    .subscribeOn(Schedulers.parallel());

// RIGHT: anything that can block, even rarely, belongs on boundedElastic
Mono.fromCallable(() -> maybeBlockingCacheLookup(key))
    .subscribeOn(Schedulers.boundedElastic());

Interview Gold Point

The senior framing: "parallel() should be treated as a hard invariant, never anything that can block, even occasionally or under rare conditions, because the blast radius of violating it is the entire pool, not just the caller." Mentioning BlockHound (Q12) as the tool that catches this class of bug automatically in CI/integration tests, by failing fast the moment a blocking call is detected on parallel() or an event-loop thread, is exactly the kind of detail that separates "read about it" from "got paged for it."

Q30. How Do You Size and Create a Custom Scheduler?

ROI: ★★★☆☆ Frequency: Medium

Short Answer

Reactor exposes factory methods for custom pools: Schedulers.newBoundedElastic(threadCap, queuedTaskCap, name) for a dedicated, bounded blocking pool with its own limits; Schedulers.newParallel(name, parallelism) for a dedicated fixed pool; and Schedulers.fromExecutorService(executorService) to wrap an existing, manually-configured ExecutorService if you need control the built-in factories don't expose (custom thread naming, custom rejection policy, a specific queue implementation).

Sizing a dedicated pool is about isolation, not raw throughput: the goal is usually to give one specific, potentially slow or unreliable downstream dependency (a third-party API known to have latency spikes, a batch job's blocking file I/O) its own bounded thread budget, so that if that dependency degrades, it saturates only its own dedicated pool and cannot starve unrelated blocking calls that would otherwise share the same default boundedElastic pool. 

private static final Scheduler THIRD_PARTY_API_SCHEDULER =
        Schedulers.newBoundedElastic(20, 200, "third-party-api");

Mono<Response> call = Mono.fromCallable(() -> blockingThirdPartyClient.call(req))
                           .subscribeOn(THIRD_PARTY_API_SCHEDULER);

Interview Favorite

The reusable principle: "share the default boundedElastic pool for well-behaved, fast blocking calls; carve out a dedicated, isolated custom scheduler for any dependency known to be slow, flaky, or capable of degrading independently of the rest of the system." This is essentially bulkheading applied at the scheduler level, the same isolation idea Resilience4j's bulkhead pattern applies at the call level.

Q31. How Do You Monitor and Diagnose Scheduler Saturation?

ROI: ★★★☆☆ Frequency: Medium

Short Answer

Reactor integrates with Micrometer to expose scheduler metrics, active thread count, queued task count, completed task count, when metrics are enabled via Schedulers.enableMetrics() (or automatically in a Spring Boot app with Micrometer on the classpath and Reactor's metrics integration active), and these show up as standard executor-family meters tagged by scheduler name in whatever monitoring backend (Prometheus, Datadog) you have wired up.

In practice, the diagnostic signal to watch for is a boundedElastic (or a custom) scheduler's queued-task count climbing steadily, or its active-thread count pinned at its configured cap, both of which indicate the pool is saturated and new work is queueing or being rejected, exactly the production symptom of the Q29 incident, just visible on a dashboard before it becomes a full outage.

Interview Gold Point

Worth stating directly: alerting on scheduler saturation metrics is the proactive version of the reactive debugging story, catching a slow downstream dependency choking a shared pool before it cascades into unrelated latency, rather than only discovering it after an incident via BlockHound or a stack-trace investigation.

SECTION 10 - RETRY STRATEGIES IN DEPTH

Q32. retry() vs retryWhen() - What's the Real Difference?

ROI: ★★★★☆ Frequency: High

Short Answer

retry(n) is the blunt instrument: it resubscribes to the upstream immediately, up to n times, on any error, with no delay and no way to inspect what actually failed. It is fine for a quick prototype or a genuinely instantaneous, always-safe-to-retry operation, but in production it is almost always the wrong tool, because it retries indiscriminately (including on errors that will never succeed on retry, like a validation failure) and hammers the failing dependency immediately with no backoff, which is exactly the behaviour that turns a brief blip into a self-inflicted retry storm.

retryWhen(Retry spec) is the composable, production-grade version: it takes a Retry strategy object (most commonly built via Retry.backoff(maxAttempts, minBackoff)) that controls delay between attempts, jitter, a maximum number of attempts, and, via .filter(predicate), exactly which exception types are worth retrying at all. This is the version every real reactive codebase should standardize on for anything touching a network call. 

// retry(n): blunt, no delay, retries everything, rarely correct for production
flakyCall.retry(3);

// retryWhen: backoff, jitter, and a filter for only-retryable errors
flakyCall.retryWhen(
    Retry.backoff(3, Duration.ofMillis(200))
         .maxBackoff(Duration.ofSeconds(2))
         .jitter(0.5)
         .filter(ex -> ex instanceof TimeoutException || ex instanceof ConnectException)
);

Interview Gold Point

The senior answer names the failure mode plain retry() causes at scale: a downstream dependency having a brief hiccup gets hit by every in-flight caller's immediate retry simultaneously, a "retry storm" or "thundering herd," which can turn a transient blip into a full outage. retryWhen with backoff and jitter exists specifically to spread those retries out in time and across callers.

Q33. Retry.backoff() With Jitter - Why Does Jitter Matter?

ROI: ★★★★☆ Frequency: High

Short Answer

Retry.backoff(maxAttempts, minBackoff) implements exponential backoff: the delay before each successive retry attempt roughly doubles (bounded by an optional .maxBackoff(...) ceiling), so the third or fourth retry waits meaningfully longer than the first, giving a struggling downstream dependency real breathing room to recover rather than being hit again almost immediately.

Jitter (.jitter(factor), a value between 0 and 1) adds a randomized variance to each computed backoff delay. Without jitter, every client that started calling a failing dependency at roughly the same moment computes the exact same backoff schedule and therefore retries at the exact same moments, in perfect lockstep, which recreates the thundering-herd problem backoff was meant to solve, just delayed and periodic instead of immediate. Jitter spreads those synchronized retry waves out across a window of time, so the failing dependency sees a smoothed-out trickle of retries instead of periodic synchronized spikes. 

Retry.backoff(5, Duration.ofMillis(100))
     .maxBackoff(Duration.ofSeconds(5))
     .jitter(0.75) // randomize up to 75% of the computed delay

Interview Favorite

A memorable one-liner: "backoff spaces out one client's own retries over time; jitter spaces out many clients' retries from each other." Both are needed together, backoff alone still produces synchronized retry waves across every client instance that failed at the same moment.

Q34. Retry Budgets and Distinguishing Retryable vs Non-Retryable Errors

ROI: ★★★☆☆ Frequency: Medium

Short Answer

Not every failure should be retried, and treating all exceptions as retryable is a common, damaging mistake. A validation error, a 400 Bad Request, an authentication failure, will fail identically no matter how many times you retry it; retrying it only adds latency and pointless load. The correct pattern is to explicitly filter which exception types or status codes are considered retryable (typically transient network failures: timeouts, connection resets, 503/429 responses) via Retry.backoff(...).filter(predicate), and let everything else fail fast and propagate immediately.

A retry budget is a further refinement used in higher-scale systems: rather than a fixed per-call retry count, the service tracks, over a rolling time window, what fraction of total outbound calls are retries, and stops issuing new retries once that fraction exceeds a threshold (e.g. retries may not exceed 10% of total call volume). This protects against the aggregate case where individually-reasonable per-call retry policies still sum up to overwhelming a struggling downstream dependency when a large fraction of a fleet's calls are failing simultaneously.

Interview Gold Point

Worth raising unprompted: retry budgets are the concept that scales the "should I retry this one call" decision (Retry.backoff().filter()) up to a fleet-wide "how much retry traffic can this dependency safely absorb right now" decision, and is exactly the kind of resilience thinking that separates someone who has only configured a Retry spec from someone who has operated a system at scale during a real dependency outage.

Q35. Handling Retry Exhaustion

ROI: ★★★☆☆ Frequency: Medium

Short Answer

When every configured retry attempt has been exhausted, Reactor's default behaviour for Retry.backoff(...) is to emit a Exceptions.RetryExhaustedException wrapping the last actual failure, rather than re-emitting the original exception directly. This distinction matters because downstream error handlers (onErrorResume, onErrorMap) written to check for the original exception type will not match unless they specifically account for the wrapper, or unless you call .onRetryExhaustedThrow((spec, signal) -> signal.failure()) to unwrap and rethrow the original cause instead.

The overall pattern in a production-grade chain typically composes retryWhen with a final fallback: retry a bounded number of times with backoff and jitter, filtered to only genuinely retryable errors, then fall back to a cached value, a degraded response, or a translated domain exception once retries are exhausted, exactly the layered structure shown in Q9's error-handling example, with retryWhen as the middle layer. 

flakyCall.retryWhen(
        Retry.backoff(3, Duration.ofMillis(200))
             .filter(ex -> ex instanceof TimeoutException)
             .onRetryExhaustedThrow((spec, signal) -> signal.failure()) // unwrap original cause
    )
    .onErrorResume(TimeoutException.class, ex -> fallbackService.call());

Common Mistake

Writing an onErrorResume(TimeoutException.class, ...) handler after a retryWhen and being confused when it never triggers on exhaustion, because by default the signal reaching it is a RetryExhaustedException, not a TimeoutException. Either match on RetryExhaustedException and unwrap its cause, or configure onRetryExhaustedThrow to rethrow the original exception so downstream handlers keyed on the original type continue to work.

SECTION 11 - DEBUGGING REACTIVE CHAINS

Q36. Why Is a Raw Reactor Stack Trace Nearly Useless?

ROI: ★★★★★ Frequency: Very High

Short Answer

In imperative code, a stack trace shows the actual call chain that led to an exception, each frame is a real method invocation still on the call stack. In a Reactor chain, execution is assembled from many small, generic operator classes (FluxMap, FluxFlatMap, MonoPeek, and so on) that get invoked asynchronously, often from a thread pool's worker thread that has no relationship to whichever thread originally assembled the chain. By the time an exception surfaces, the stack trace shows you Reactor's internal plumbing, callback invocation frames from whatever Scheduler happened to run it, not the sequence of your own application code that built the chain in the first place.

This is a direct consequence of the assembly/execution split from Q15: the trace at execution time reflects how the signal is being delivered right now, not where in your source code the operator was declared. For a chain with several flatMaps and scheduler hops, the resulting stack trace can be dozens of frames of Reactor internals with barely a hint of which line of your own code actually failed, which is precisely why interviewers ask this: it is a real, everyday pain point that separates people who have actually run Reactor in production from people who have only read the docs.

Interview Gold Point

The framing to lead with: "the cost of Reactor's async execution model is that you lose the free, built-in stack trace imperative code gives you for locating a failure's assembly site; checkpoint() and operator debug mode exist specifically to buy that information back, at a real performance cost, which is why they are opt-in rather than always-on."

Q37. Hooks.onOperatorDebug() and checkpoint()

ROI: ★★★★☆ Frequency: High

Short Answer

Hooks.onOperatorDebug() globally instruments every operator in the application to capture the assembly-time stack trace (where in your code the operator was actually declared) and attach it to any exception that later flows through that operator, effectively stitching an "Assembly trace" section onto the otherwise-useless execution-time stack trace. It works by wrapping every single operator's declaration with a stack-trace capture, which is exactly why it is expensive: enabling it globally in production adds real, measurable overhead to every single operator in every single chain in the application, since every one of them now pays the cost of a stack-trace capture regardless of whether it will ever actually fail.

.checkpoint() (and its labeled overload, .checkpoint("some description")) is the targeted, low-cost alternative: placed at specific points in a chain, it captures assembly-site information only for that one point, letting you selectively instrument the handful of chains or operators you actually suspect, rather than paying the cost everywhere. In practice, checkpoint() at strategically chosen points in a hot production chain, versus onOperatorDebug() only enabled temporarily in a lower-traffic environment or during active incident investigation, is the standard trade-off senior engineers make. 

Mono<Order> order = repository.findById(id)
        .checkpoint("findById lookup") // labeled assembly-site marker
        .flatMap(this::enrichWithCustomer)
        .checkpoint("enrichment step");

Interview Gold Point

Worth stating precisely: checkpoint() has a lightweight variant, checkpoint() with no message, that only records a marker without a full stack trace capture (cheaper), versus checkpoint(String) or the full-stack-trace-capturing overload, which trades more overhead for more detail. Knowing that this cost/detail dial exists, and choosing the cheaper option by default in hot paths, is exactly the kind of nuance interviewers are listening for.

Q38. Reactor Tools' ReactorDebugAgent and the Cost of Debug Mode

ROI: ★★★☆☆ Frequency: Medium

Short Answer

reactor-tools's ReactorDebugAgent is a bytecode instrumentation agent (installed via a Java agent or programmatically via ReactorDebugAgent.init() at application startup) that rewrites operator assembly call sites at class-load time to capture accurate assembly-site information far more cheaply than the runtime stack-trace capture Hooks.onOperatorDebug() performs on every single operator invocation. Because the instrumentation happens once, at class-load time, rather than on every operator assembly at runtime, it is the recommended way to get assembly-time debugging information with meaningfully lower steady-state overhead than the older, fully runtime-based debug hook.

Even with this cheaper approach, debug-mode instrumentation of any kind is still not something you leave permanently enabled in a high-throughput production service without measuring the impact first; it remains a tool you reach for during active investigation, in staging, or behind a feature flag you can flip on briefly in production during an incident, rather than a default-on setting.

Common Mistake

Enabling Hooks.onOperatorDebug() globally and leaving it on permanently in a production service "just in case," without measuring the throughput/latency impact. The safer default in 2026 production Reactor applications is targeted checkpoint() calls at suspect points, with ReactorDebugAgent or full operator debug mode reserved for genuine investigation windows, not steady-state operation.

Q39. A Practical Workflow for Debugging a Failing Reactive Chain

ROI: ★★★★☆ Frequency: High

Short Answer

A pragmatic, senior-level workflow, rather than reaching for full debug mode immediately, usually goes: first, read the execution-time stack trace anyway, it often still tells you the exception type and message even if the frame locations are unhelpful, which alone can narrow things down. Second, add targeted doOnError (or .log()) at a few candidate points in the suspect chain to bisect where in the pipeline the failure is actually originating, without any global instrumentation cost. Third, if that is not enough, add .checkpoint("label") at those same candidate points to get proper assembly-site information cheaply, scoped only to the chain under investigation. Only as a last resort, for genuinely elusive bugs that resist all of the above, reach for full Hooks.onOperatorDebug() or ReactorDebugAgent, ideally in a lower-traffic environment or a tightly time-boxed production window.

This graduated approach, cheap first, expensive only when necessary, mirrors how experienced teams actually operate reactive systems: debug tooling that is powerful but costly is treated as an escalation path, not a default-on setting.

Interview Gold Point

The signal to give: "I reach for .log()/doOnError first because it's free, checkpoint() second because it's cheap and targeted, and full operator debug mode last because it's expensive and global." That ordering, not just knowing the tools exist, is what shows real operational judgment.

SECTION 12 - WEBCLIENT DEEP DIVE

Q40. WebClient vs RestTemplate

ROI: ★★★★★ Frequency: Very High

Short Answer

RestTemplate is Spring's original, synchronous, blocking HTTP client; it has been in maintenance mode and officially marked for eventual deprecation-in-spirit (Spring's documentation has steered users away from it for new development for years, even where the class itself remains present for backward compatibility), specifically because every call blocks the calling thread until the full response is received, making it fundamentally incompatible with a non-blocking WebFlux pipeline.

WebClient is Spring's non-blocking, reactive HTTP client, built on Reactor Netty by default, returning Mono/Flux for both the request execution and the response body. It supports the same functional, composable operator style as the rest of Reactor, streaming response bodies, and works correctly inside a WebFlux request-handling chain without introducing a blocking call. It is also perfectly usable from a plain Spring MVC (blocking) application, either by calling .block() at the edge (acceptable there, since MVC threads are expected to block) or by embracing async, non-blocking calls even in an otherwise-blocking MVC app.

Interview Gold Point

Worth noting precisely: WebClient is the recommended HTTP client for all new Spring code regardless of whether the calling application itself is WebFlux or MVC; it is not "the WebFlux HTTP client," it is simply the modern, actively developed one, and RestTemplate should be treated as legacy in any codebase written from 2020 onward.

Q41. WebClient Connection Pooling and ConnectionProvider Tuning

ROI: ★★★★☆ Frequency: High

Short Answer

By default, WebClient (via Reactor Netty) reuses a shared, global connection pool sized with sensible defaults, but any service making a meaningful volume of outbound calls to a specific downstream dependency should configure a dedicated ConnectionProvider for that client, controlling the maximum number of connections, the pending-acquire timeout (how long a request waits for a free connection before failing), the pending-acquire max count (queue depth), and idle/max connection lifetime.

Under-provisioning this pool is a common, subtle production bottleneck: if the max connection count is too low for the actual concurrent call volume to a given host, requests start queueing on pendingAcquireTimeout and eventually fail with a pool-exhaustion error that looks like a downstream outage but is actually a self-inflicted client-side connection limit. 

ConnectionProvider provider = ConnectionProvider.builder("custom-pool")
        .maxConnections(200)
        .pendingAcquireTimeout(Duration.ofSeconds(5))
        .maxIdleTime(Duration.ofSeconds(30))
        .build();

HttpClient httpClient = HttpClient.create(provider);
WebClient client = WebClient.builder()
        .clientConnector(new ReactorClientHttpConnector(httpClient))
        .baseUrl("https://downstream-service")
        .build();

Common Mistake

Sharing the default global connection pool across many downstream dependencies with wildly different traffic profiles, then being unable to tell, when pool exhaustion happens, which dependency actually caused it. A dedicated ConnectionProvider (and a dedicated WebClient instance) per significant downstream dependency gives you isolation, exactly mirroring the scheduler-isolation argument from Q30, applied at the HTTP connection-pool layer instead.

Q42. WebClient Timeouts: Connect, Read, Write, and Response Timeout

ROI: ★★★★☆ Frequency: High

Short Answer

WebClient has no built-in default timeout on the overall response, an easy-to-miss fact that means, unconfigured, a call to a hung downstream dependency can wait indefinitely, tying up a subscription (and whatever it is downstream of) forever. Correctly configuring a production WebClient means setting timeouts at multiple layers, each catching a different failure mode: connect timeout (how long to wait to establish the TCP connection itself, set on the underlying Netty HttpClient), read timeout and write timeout (how long to wait for data once the connection is established, also Netty-level handlers), and a Reactor-level response timeout applied with .timeout(Duration) on the returned Mono/Flux, which is the catch-all covering the entire request/response exchange regardless of where it stalls. 

HttpClient httpClient = HttpClient.create()
        .option(ChannelOption.CONNECT_TIMEOUT_MILLIS, 3000)
        .doOnConnected(conn -> conn
                .addHandlerLast(new ReadTimeoutHandler(5, TimeUnit.SECONDS))
                .addHandlerLast(new WriteTimeoutHandler(5, TimeUnit.SECONDS)));

WebClient client = WebClient.builder()
        .clientConnector(new ReactorClientHttpConnector(httpClient))
        .build();

Mono<Response> result = client.get().uri("/data").retrieve()
        .bodyToMono(Response.class)
        .timeout(Duration.ofSeconds(6)); // overall Reactor-level safety net

Interview Gold Point

The point worth stressing: layered timeouts exist because each one catches a different stall point, connect timeout catches an unreachable host, read/write timeout catches a connection that opened but then stalled mid-transfer, and the Reactor .timeout() is the last-line-of-defense catch-all. Relying on only one of them leaves gaps; production WebClient configuration should set all of them deliberately, never rely on defaults.

Q43. Wrapping WebClient Calls With Reactive Resilience (Resilience4j)

ROI: ★★★★☆ Frequency: High

Short Answer

Resilience4j ships a reactor module (resilience4j-reactor) providing operators, CircuitBreakerOperator, RateLimiterOperator, BulkheadOperator, RetryOperator, that transform naturally into Reactor's Mono/Flux operator chain via .transformDeferred(...), letting you compose resilience patterns directly into a WebClient call without leaving the reactive world or blocking anywhere to check circuit state. This chapter's lens is specifically the reactive-mechanics side of this: how the resilience wrapper composes as a Reactor operator, not the internal state-machine mechanics of the circuit breaker pattern itself, which is covered in the microservices resilience material.

A circuit-breaker-wrapped WebClient call fails fast (short-circuits without even attempting the network call) once the downstream dependency's failure rate crosses the configured threshold, which is precisely what protects a shared boundedElastic pool or a limited outbound connection pool from being consumed entirely by calls that are very likely to fail anyway, complementing rather than replacing the timeout/retry mechanisms above. 

CircuitBreaker circuitBreaker = CircuitBreaker.ofDefaults("downstream-service");

Mono<Response> result = webClient.get().uri("/data").retrieve()
        .bodyToMono(Response.class)
        .transformDeferred(CircuitBreakerOperator.of(circuitBreaker))
        .timeout(Duration.ofSeconds(3))
        .onErrorResume(CallNotPermittedException.class, ex -> fallback());

Interview Gold Point

Worth naming precisely: a circuit breaker rejecting a call throws CallNotPermittedException, a distinct exception type from any actual network/timeout failure, so your onErrorResume/fallback logic needs to distinguish "the circuit is open, we deliberately did not call" from "we called and it failed," since they usually warrant different fallback behaviour and different alerting.

Q44. Common WebClient Pitfalls

ROI: ★★★☆☆ Frequency: Medium

Short Answer

The most common WebClient mistake is calling .retrieve() and then never subscribing to (or otherwise consuming) the resulting Mono/Flux; because WebClient's request is only actually sent once its response publisher is subscribed to (Q15's "nothing happens until subscribe" applies here too), a chain that builds the request but drops the result silently never sends it, exactly analogous to the reactive repository bug from Q19.

The other common pitfall is not properly draining or handling error response bodies: .retrieve() by default turns any 4xx/5xx status into a WebClientResponseException without you seeing the actual response body content unless you explicitly call .onStatus(...) to customize the handling, or reach for .exchangeToMono(...)/.exchangeToFlux(...) when you need full manual control over reading the response including its body on error paths (exchangeToMono/Flux, unlike retrieve, puts you on the hook for consuming the body yourself in every branch, including errors, to avoid leaking the connection).

Common Mistake

Reaching for exchangeToMono "for more control" and then forgetting to consume the response body on every code path, including error branches, which can leak the underlying connection back to the pool improperly. Unless you specifically need that level of control, .retrieve() with .onStatus(...) handlers is the safer, harder-to-misuse default.

SECTION 13 - SERVER-SENT EVENTS & STREAMING RESPONSES

Q45. Streaming Server-Sent Events From a WebFlux Controller

ROI: ★★★★☆ Frequency: High

Short Answer

Server-Sent Events (SSE) are a one-directional, long-lived HTTP streaming protocol, the server keeps the connection open and pushes a sequence of text-formatted events to the client over time, and they map onto WebFlux's reactive model almost perfectly: a controller method simply returns a Flux<ServerSentEvent<T>> (or a plain Flux<T> with the media type set to text/event-stream), and WebFlux keeps the underlying connection open, writing each emitted element to the response as it arrives, for as long as the Flux keeps emitting.

This is a genuinely different shape of endpoint from a normal request/response controller method returning a Mono, the response is not "complete" until the Flux itself completes (or the client disconnects), which could be seconds, minutes, or indefinitely for a live feed. Client disconnection is handled naturally too: when the client closes the connection, WebFlux cancels the underlying subscription, which propagates cancellation up through the Flux's operator chain exactly like any other subscriber cancellation, letting the server release any resources tied to that particular stream. 

@GetMapping(value = "/events", produces = MediaType.TEXT_EVENT_STREAM_VALUE)
public Flux<ServerSentEvent<String>> streamEvents() {
    return Flux.interval(Duration.ofSeconds(1))
               .map(seq -> ServerSentEvent.builder("tick " + seq)
                                          .id(String.valueOf(seq))
                                          .event("tick")
                                          .build());
}

Interview Gold Point

Worth calling out: because SSE endpoints are long-lived, they occupy a connection (and whatever resources back the Flux, a subscription to a message broker, a polling loop) for the connection's entire lifetime, so capacity planning for an SSE-heavy service is closer to planning for concurrent open connections than for request throughput, a genuinely different operational profile than a typical REST endpoint.

Q46. How Does Backpressure Propagate All the Way to an HTTP Client?

ROI: ★★★☆☆ Frequency: Medium

Short Answer

Reactive Streams backpressure inside a single JVM's operator chain is straightforward, the request(n) protocol from Q2, but WebFlux extends that same idea across the actual network connection: the underlying Netty channel only writes as much of the response as the client's TCP receive window and the channel's own writability allow, and Reactor Netty's HTTP response-writing machinery translates "the socket cannot currently accept more bytes" back into reduced request(n) signals up through your Flux's operator chain. Concretely, if a slow SSE client is not reading fast enough, TCP-level backpressure (a full receive window) eventually causes Reactor Netty to stop requesting more elements from your Flux, which naturally slows or pauses whatever is producing those elements upstream, all without you writing any explicit backpressure-handling code.

This is the genuine, often-cited advantage of a fully reactive stack for exactly this kind of streaming workload: a Spring MVC streaming endpoint (using a blocking OutputStream) has no equivalent mechanism, a slow client there either blocks the serving thread indefinitely or requires manual, application-level throttling logic that WebFlux gets essentially for free from the Reactive Streams protocol.

Interview Gold Point

The precise claim to make: "backpressure in WebFlux is not just an in-process operator concept, Reactor Netty bridges TCP-level flow control (the client's receive window) into Reactive Streams request(n) signals, so a slow HTTP client genuinely throttles your upstream Flux, not just the bytes sitting in a server-side buffer." This is a detail that clearly separates deep WebFlux experience from surface-level familiarity.

Q47. NDJSON and Streaming JSON Responses

ROI: ★★★☆☆ Frequency: Medium

Short Answer

Newline-Delimited JSON (NDJSON, media type application/x-ndjson) is WebFlux's other main streaming response shape besides SSE: instead of wrapping every element in an SSE event envelope with an id/event/data structure, each emitted element is serialized as a standalone JSON object followed by a newline, letting a client parse the stream incrementally, one JSON object per line, without needing to buffer the entire response before it can start processing. It is a natural fit for streaming a large or unbounded Flux of JSON entities (a bulk export endpoint, a live feed of domain objects) to a client that just wants a stream of typed objects rather than SSE's richer, browser-EventSource-oriented event metadata.

A controller method returns Flux<T> with the produces media type set to NDJSON, and WebFlux's Jackson integration streams each element as it is emitted rather than collecting the whole Flux into a single JSON array first, which is the key difference from a normal Flux<T> endpoint returning ordinary application/json: a plain JSON array response has to buffer the entire Flux before it can write the closing bracket, defeating the point of streaming for a large or slow-arriving dataset. 

@GetMapping(value = "/export", produces = "application/x-ndjson")
public Flux<Order> exportOrders() {
    return orderRepository.findAll(); // streamed one JSON object per line, no buffering
}

Common Mistake

Returning a large Flux<T> as plain application/json expecting streaming behaviour. A standard JSON array response must buffer every element to correctly emit the array's closing bracket, so it does not stream incrementally to the client the way NDJSON or SSE do; for genuinely large or slow-to-produce datasets, NDJSON (or SSE) is the correct media type choice, not a plain JSON array.

SECTION 14 - REACTIVE TRANSACTION MANAGEMENT WITH R2DBC

Q48. Why Do @Transactional's Usual Semantics Get Tricky With R2DBC?

ROI: ★★★★☆ Frequency: High

Short Answer

Classic Spring transaction management, the mechanism behind blocking @Transactional with JDBC/JPA, works by binding the current database connection (or EntityManager) to the current thread, via TransactionSynchronizationManager's ThreadLocal-based resource map, for the duration of the transaction; every repository call made from that same thread transparently reuses the same bound connection so all the operations participate in one transaction. This is exactly the pattern that breaks under reactive execution: as established in Q20, a reactive chain routinely hops across multiple threads mid-flight, so "bind the connection to the current thread" simply does not carry the connection through the rest of the chain the way it does in a single-threaded blocking call stack.

@Transactional itself still technically works with R2DBC in modern Spring versions, Spring bridges the transactional context through Reactor's Context (Q21) rather than ThreadLocal specifically to solve this, but the mechanism underneath is fundamentally different from the JDBC case, and understanding that it is Context-based, not ThreadLocal-based, is what lets you reason correctly about edge cases (a transaction boundary that spans a scheduler hop, or a chain that partially escapes the reactive world) that behave differently than their JDBC counterparts would.

Interview Gold Point

The precise statement to make: "R2DBC's @Transactional support works by propagating the transaction's bound connection through Reactor Context instead of ThreadLocal, which is why it still functions across scheduler hops, but it also means transaction propagation now inherits every one of Context's own rules and pitfalls, including the upstream-only visibility and the loss of propagation across any drop into blocking code, discussed in Q21/Q23."

Q49. TransactionalOperator and ReactiveTransactionManager

ROI: ★★★★☆ Frequency: High

Short Answer

ReactiveTransactionManager is R2DBC's reactive counterpart to the blocking PlatformTransactionManager, and TransactionalOperator is the explicit, programmatic way to demarcate a transaction boundary around a specific Mono/Flux chain, an alternative to the declarative @Transactional annotation that many teams actually prefer in reactive code because it makes the transaction boundary visible right at the call site, rather than implicit via a proxy (recall that @Transactional relies on AOP proxying, and self-invocation and similar proxy pitfalls apply here too).

TransactionalOperator.transactional(publisher) wraps a given Mono/Flux so that its execution runs within a transaction managed by the configured ReactiveTransactionManager, committing on successful completion and rolling back on error, exactly mirroring @Transactional's commit/rollback semantics but expressed as an explicit operator in the chain instead of an annotation applied to a method. 

@Bean
ReactiveTransactionManager transactionManager(ConnectionFactory cf) {
    return new R2dbcTransactionManager(cf);
}

@Service
class OrderService {
    private final TransactionalOperator txOperator;
    private final OrderRepository orders;
    private final InventoryRepository inventory;

    Mono<Order> placeOrder(Order order) {
        Mono<Order> work = orders.save(order)
                .flatMap(saved -> inventory.decrement(saved.getSku())
                                           .thenReturn(saved));
        return txOperator.transactional(work); // commits/rolls back the whole chain
    }
}

Interview Favorite

The clean comparison to draw: "@Transactional is declarative and relies on an AOP proxy, exactly like the JDBC case; TransactionalOperator is programmatic and wraps the publisher explicitly, avoiding proxy-related pitfalls like self-invocation at the cost of a slightly more verbose call site. Many reactive-first teams prefer TransactionalOperator specifically because the transaction boundary is visible in the code, not hidden behind a proxy."

Q50. Common Pitfalls With Reactive Transaction Boundaries

ROI: ★★★☆☆ Frequency: Medium

Short Answer

The most common mistake is calling .subscribeOn() or otherwise introducing a genuine subscription boundary (a separate subscribe() call, a cached/shared Mono reused across requests) in the middle of what is meant to be one transactional chain; because the transactional Context needs to flow continuously through a single, unbroken chain of operators bound to one subscription, splitting the work across separate subscriptions breaks the transaction boundary in ways that are easy to miss until a partial-commit bug shows up in production.

The other common pitfall is mixing a blocking call (a legacy JDBC-backed repository, invoked via Mono.fromCallable(...).subscribeOn(boundedElastic())) into what is otherwise an R2DBC-transactional chain, expecting it to participate in the same transaction. It will not: the blocking call runs against a completely separate connection obtained through a completely separate transaction manager, so there is no way for R2DBC's reactive transaction to span across it; if you must combine blocking and reactive data access in one logical operation, you need either two independent transactions (with the operational complexity of coordinating their outcomes yourself) or a genuine migration of the blocking piece to R2DBC.

Common Mistake

Assuming a reactive transaction can span a mixed R2DBC-and-JDBC data access chain just because both pieces eventually run "inside" the same overall Mono. Transaction managers operate on their own resource type; an R2DBC transaction manager has no visibility into (and cannot roll back) a JDBC connection's changes, and vice versa. Treat mixed blocking/reactive persistence as two separate transactional domains, not one.

SECTION 15 - ADVANCED TESTING: VIRTUAL TIME & TESTPUBLISHER

Q51. StepVerifier.withVirtualTime() - What It Actually Does and Its Limits

ROI: ★★★★☆ Frequency: High

Short Answer

StepVerifier.withVirtualTime(() -> publisherSupplier) swaps in Reactor's VirtualTimeScheduler as the default scheduler for the duration of the test, so that any time-based operator (delayElements, Mono.delay, timeout, an interval-based Flux) advances according to virtual, simulated time rather than actually sleeping the test thread for real wall-clock duration. Combined with .thenAwait(Duration) to fast-forward the virtual clock by a specific amount, this lets you write a test asserting the behaviour of, say, a 30-second timeout, or a stream that ticks once a minute for an hour, that runs in milliseconds of real time instead of actually waiting.

The important limitation to know: the publisher must be constructed inside the supplier lambda passed to withVirtualTime, not built beforehand and passed in as a plain value, because the VirtualTimeScheduler has to be installed as the default scheduler before any time-based operator is assembled; building the publisher too early captures a reference to the real scheduler instead, and the virtual-time trick silently does not apply, a very common gotcha when refactoring a test. 

@Test
void tickerEmitsHourlyWithoutRealWaiting() {
    StepVerifier.withVirtualTime(() ->
            Flux.interval(Duration.ofMinutes(1)).take(3)) // built INSIDE the supplier
        .expectSubscription()
        .expectNoEvent(Duration.ofMinutes(1))
        .expectNext(0L)
        .thenAwait(Duration.ofMinutes(2))
        .expectNext(1L, 2L)
        .verifyComplete();
}

Common Mistake

Building the Flux/Mono outside the supplier lambda (e.g. as a field or local variable computed before calling withVirtualTime) and passing a reference to it. The scheduler substitution only affects operators assembled after VirtualTimeScheduler is installed, so a publisher built too early quietly uses real time, and the test either passes for the wrong reason or actually sleeps for real, defeating the entire point of virtual time.

Q52. TestPublisher: Simulating Backpressure and Upstream Failures

ROI: ★★★☆☆ Frequency: Medium

Short Answer

TestPublisher<T> is Reactor Test's tool for the opposite side of what StepVerifier normally covers: instead of asserting on emissions coming out of a chain you already have, it lets you construct a controllable, hand-driven Publisher to feed into a chain you are testing, so you can simulate exactly the upstream conditions you want, a slow producer, a producer that violates the Reactive Streams protocol, an upstream that fails mid-stream, situations that are difficult or impossible to trigger reliably using a real repository or client as the source.

This is the tool of choice for testing your own operators, custom backpressure handling code, or resilience logic (retry, timeout, fallback) against upstream failure scenarios that would otherwise require an elaborate mock setup: you emit exactly the sequence of signals you want, including onNext, onError at a specific moment, or even protocol violations (via TestPublisher.createNoncompliant(...)) to verify your code degrades gracefully rather than crashing when fed a misbehaving Publisher. 

@Test
void fallsBackWhenUpstreamErrors() {
    TestPublisher<String> upstream = TestPublisher.create();

    StepVerifier.create(
                upstream.flux().onErrorResume(ex -> Flux.just("fallback")))
            .then(() -> upstream.emit("first"))
            .expectNext("first")
            .then(() -> upstream.error(new RuntimeException("boom")))
            .expectNext("fallback")
            .verifyComplete();
}

Interview Gold Point

Worth mentioning: TestPublisher can deliberately misbehave (emit after completion, emit without a preceding request, violate the spec in other ways) specifically so you can verify your own operators or resilience wrappers handle a non-compliant upstream defensively, something a well-behaved mock repository would never expose, but that a real third-party Publisher implementation occasionally does in production.

Q53. Testing Scheduler and Thread-Hop Behaviour

ROI: ★★★☆☆ Frequency: Medium

Short Answer

Asserting that a chain actually executes on the scheduler you configured (verifying a subscribeOn/publishOn placement is correct, or that a blocking call really is quarantined onto boundedElastic as intended from Q29) is one of the trickier things to unit test cleanly, because the assertion has to happen from inside the running chain, on whatever thread is currently executing, rather than from the test's own thread after the fact. The common pattern is a doOnNext (or a custom operator) that captures Thread.currentThread().getName() at the relevant point in the chain into a thread-safe holder (an AtomicReference), which the test then inspects after the StepVerifier has finished verifying the chain's emissions.

For genuinely deterministic thread-hop testing, some teams prefer injecting a named, dedicated test Scheduler (via Schedulers.newSingle("test-scheduler"), or a hand-rolled Scheduler wrapping a single-thread executor) into the code under test rather than the default Schedulers.parallel()/boundedElastic(), so the test can assert precisely "the operator ran on the thread belonging to this specific injected scheduler" rather than a fragile assertion based on default-scheduler naming conventions. 

@Test
void runsOnBoundedElastic() {
    AtomicReference<String> threadName = new AtomicReference<>();

    StepVerifier.create(
            Mono.fromCallable(() -> "value")
                .doOnNext(v -> threadName.set(Thread.currentThread().getName()))
                .subscribeOn(Schedulers.boundedElastic()))
        .expectNext("value")
        .verifyComplete();

    assertThat(threadName.get()).contains("boundedElastic");
}

Common Mistake

Asserting on Thread.currentThread() from the test method's own thread, after the StepVerifier call returns, rather than capturing it from inside the reactive chain while it is actually executing on the scheduled thread. By the time verify() returns, execution has already finished and the test thread was never the one running the operator in question, so the assertion has to be captured during execution, not afterward.

SECTION 16 - REACTIVE VS VIRTUAL THREADS: PRODUCTION DECISION-MAKING

Q54. A Decision Framework: WebFlux vs Virtual-Thread Spring MVC for a New Service

ROI: ★★★★★ Frequency: Very High

Short Answer

Building on Q14's foundational comparison, a concrete decision framework for a brand-new service in 2026 looks roughly like this: default to Spring MVC with virtual threads enabled (a one-line property in Spring Boot 3.2+) unless a specific, identifiable requirement points toward reactive. Virtual threads give you most of the concurrency-ceiling benefit reactive was originally adopted for, while keeping ordinary, debuggable, imperative code, existing blocking libraries and drivers, and a team that does not need to learn a new operator vocabulary.

Reach for WebFlux specifically when you have a genuine, first-class need for backpressure as a concept (a fast producer and a slow, network-connected consumer that must be able to signal "slow down," true streaming semantics rather than just "handle a lot of concurrent requests"), when you are building something that is fundamentally a stream-processing pipeline with rich composition needs (complex zip/merge/windowing across multiple live sources), or when you are already deeply invested in a reactive stack (R2DBC, reactive Kafka consumers) where introducing a blocking island would be worse than staying consistently reactive end-to-end. The single question worth asking out loud in a design review: "do we need backpressure and stream composition, or do we just need to handle a lot of concurrent I/O-bound requests?" Only the former genuinely justifies reactive's complexity tax over virtual threads.

Signal Points toward
Just need to handle high concurrency of I/O-bound calls Spring MVC + virtual threads
Team unfamiliar with Reactor, tight timeline Spring MVC + virtual threads
Existing blocking JDBC/JPA stack, no urgency to change Spring MVC + virtual threads
Genuine backpressure need (slow consumer, fast producer) WebFlux / Reactor
Streaming/SSE/complex multi-source composition WebFlux / Reactor
Already fully reactive stack (R2DBC, reactive Kafka) WebFlux / Reactor

Interview Gold Point

The 2026-appropriate framing: "reactive used to be the default answer to 'we have too much concurrent I/O,' virtual threads have taken over that specific use case, so reactive's remaining, genuinely justified niche is backpressure and stream composition, not raw concurrency. A team reaching for WebFlux purely for throughput in a new service in 2026, without a backpressure or streaming requirement, is very likely paying a complexity tax for a benefit virtual threads would have given them for free."

Q55. Is Migrating an Existing WebFlux Service Back to Virtual-Thread MVC Worth It?

ROI: ★★★★☆ Frequency: High

Short Answer

Almost always, no, at least not as a standalone project justified purely by "virtual threads exist now." A working, correctly-implemented WebFlux service already has its non-blocking drivers (R2DBC, reactive clients), its team already trained on the operator vocabulary, and its operational tooling (dashboards, alerting) already built around reactive-specific signals. Rewriting all of that back to a blocking model, re-introducing JDBC/JPA where R2DBC currently sits, retraining the team on blocking idioms, is a substantial rewrite with real regression risk, undertaken to relieve a debugging/complexity cost that the team has, by definition, already absorbed and is presumably already productive despite.

The calculus changes when the WebFlux adoption itself was a mistake in the first place, a genuinely CRUD-shaped service adopted reactive "because it seemed modern" (Q13's cautionary case) with no real backpressure or streaming need, is chronically understaffed with reactive expertise, and is paying an ongoing productivity/incident-frequency tax that outweighs the one-time migration cost. In that specific scenario, migrating to virtual-thread MVC is a legitimate simplification, not a fashion-driven rewrite, but the bar for justifying it should be concrete, measured pain (incident frequency, time-to-debug, onboarding friction), not simply "virtual threads are newer."

Common Mistake

Treating "virtual threads now exist" as sufficient justification on its own to migrate a healthy, working reactive service. Migration cost and regression risk are real and often underestimated; the decision should be driven by a measured, ongoing cost the current architecture is actually imposing on the team, not by the availability of a technically-interesting alternative.

Q56. Hybrid Architectures: Mixing Virtual-Thread MVC Services With Reactive Streaming Services

ROI: ★★★★☆ Frequency: High

Short Answer

In a microservices fleet, the two models are not mutually exclusive, and the pragmatic 2026 pattern in many organizations is genuinely hybrid: the majority of ordinary, CRUD-and-orchestration services run on Spring MVC with virtual threads, simple, debuggable, using whatever blocking drivers the team already knows, while a small number of services with a genuine streaming or backpressure requirement, a real-time notification/event-fan-out service, a bulk data export pipeline, an SSE-based live dashboard feed, are deliberately built on WebFlux and R2DBC, where the complexity investment is justified by an actual technical requirement, not organizational fashion.

This mirrors how most architectural decisions should be made at the service level rather than as a single organization-wide mandate: the choice between reactive and virtual-thread-blocking is a per-service decision driven by that service's actual I/O and streaming shape, not a company-wide "we are a reactive shop" or "we don't do reactive" policy that ignores the real variation in requirements across a fleet of services with genuinely different needs.

Interview Gold Point

The strongest answer treats this as an architectural maturity signal: "the mark of a team that actually understands both models is making this choice per-service based on concrete requirements, rather than a blanket organizational mandate in either direction. Most services in a typical fleet do not need reactive; a handful of genuinely streaming-shaped services do, and treating that as a case-by-case engineering decision, not a religious one, is the mature position."

Q57. What Concrete Signals Tell You a Service Actually Needs Reactive's Backpressure Model?

ROI: ★★★★☆ Frequency: High

Short Answer

Beyond the general framework in Q54, a few concrete, checkable signals reliably indicate a genuine backpressure need rather than just "a lot of concurrent requests": the service has a data source that can produce faster than any reasonable consumer can process (a market data feed, a high-frequency sensor stream, a change-data-capture stream from a database) where dropping, buffering, or explicitly slowing the producer is a real design decision the service must make, not a hypothetical. The service exposes a genuinely long-lived streaming endpoint to external clients (SSE, WebSocket, gRPC streaming) where a slow client must not be allowed to either stall the server or silently drop data without an explicit policy decision. Or the service's core logic is naturally expressed as composition over multiple live, ongoing streams (combining several real-time feeds with zip/merge/combineLatest) rather than as a sequence of discrete request/response calls.

If none of those apply, if the workload is fundamentally "receive a request, make a few downstream calls, return a response," even at very high concurrency and very high downstream call volume, that is precisely the shape virtual threads handle well without reactive's complexity, and the presence of high concurrency alone, without any of the above signals, is not by itself evidence that reactive is the right tool.

Interview Gold Point

The concise test to offer: "ask whether the service's core problem is 'too many concurrent things waiting on I/O' (virtual threads' sweet spot) or 'a producer and consumer moving at different speeds where that mismatch is itself part of the business problem' (reactive's actual differentiator). Conflating the two is exactly how teams end up adopting reactive for services that only ever needed the former."

QUICK REVISION SHEET

  • Reactive programming decouples concurrent operations from OS threads; it solves the thread-per-request ceiling for I/O-bound, not CPU-bound, workloads
  • Reactive Streams spec: Publisher/Subscriber/Subscription/Processor; backpressure is the pull-based request(n) protocol built into the spec itself
  • Mono = 0-1 element (Optional/Future-like); Flux = 0-N elements (Stream-like); both are cold until subscribed
  • Backpressure overflow strategies: buffer (queue, risk OOM), drop (discard newest), latest (keep newest only), error (fail loudly) - pick based on what you can sacrifice
  • map = sync 1-to-1; flatMap = async, concurrent, order not guaranteed; concatMap = async, sequential, order guaranteed but slower
  • subscribeOn sets the thread for the source/subscription (only the first one counts); publishOn switches threads for everything downstream from that point, and can appear multiple times
  • Spring MVC = thread-per-request on Tomcat, blocking, simple to debug; WebFlux = event loop on Netty, non-blocking, scales concurrency but only if the whole chain is non-blocking
  • R2DBC gives non-blocking DB access end-to-end; pairing WebFlux with blocking JPA/JDBC defeats the purpose unless explicitly offloaded to boundedElastic
  • Error handling: onErrorReturn = fixed fallback value; onErrorResume = fallback to another Publisher with access to the exception; retryWhen with backoff for transient failures
  • Test with StepVerifier (expectNext/expectError/expectComplete), not .block(); use withVirtualTime() to fast-forward delays/timeouts in tests
  • zip pairs by position and waits for all sources; merge interleaves with no pairing; combineLatest recomputes on every emission using the latest from each source
  • Never block inside a reactive operator: one blocking call on an event-loop thread can stall unrelated requests; quarantine unavoidable blocking calls on Schedulers.boundedElastic() and consider BlockHound in tests
  • Skip reactive for CPU-bound work, simple low-concurrency CRUD with blocking drivers, or teams without the ramp-up time; the complexity tax must buy real throughput
  • Virtual threads (Loom) make blocking cheap instead of avoiding it: ordinary blocking code scales past the thread ceiling with normal debuggability, narrowing reactive's case to real streaming/backpressure needs; watch for carrier-thread pinning on synchronized blocks
  • A Reactor chain has three phases: assembly (building operators, nothing runs), subscription (request(n) travels bottom-up), execution (signals travel top-down, your code actually runs) - a Mono/Flux built but never subscribed to is inert
  • Cold publishers rerun their source per subscriber; hot publishers run once and broadcast, late subscribers miss history unless replay() buffers it; share() = publish().refCount(1)
  • ThreadLocal breaks across reactive thread-hops; Reactor's Context is attached to the subscription (not a thread), is immutable, and propagates upstream only - contextWrite must sit at or below every reader
  • Sinks.Many/Sinks.One replace hand-rolled Subscriber/FluxProcessor implementations for manually pushing values; unicast = one subscriber, multicast = broadcast live only, replay = broadcast with history; prefer tryEmitNext and check the EmitResult
  • parallel() is fixed-size and must never block; boundedElastic() absorbs unavoidable blocking calls; a blocking call scheduled on parallel() by mistake starves the whole pool - isolate risky dependencies with a dedicated custom scheduler
  • retry(n) retries blindly with no delay; retryWhen(Retry.backoff(...).filter(...)) adds backoff, jitter (to avoid synchronized retry storms), and a filter for only genuinely retryable errors; exhausted retries surface as RetryExhaustedException unless unwrapped
  • Raw Reactor stack traces show scheduler plumbing, not your assembly site; escalate cheap-to-expensive: log()/doOnError, then checkpoint(), then Hooks.onOperatorDebug()/ReactorDebugAgent only during active investigation
  • WebClient replaces RestTemplate; tune its ConnectionProvider and layer connect/read/write/response timeouts explicitly (none are set by default); wrap calls with Resilience4j's reactive operators (transformDeferred) for circuit breaking
  • SSE (Flux<ServerSentEvent<T>>) and NDJSON stream responses incrementally; Reactor Netty bridges TCP-level flow control into request(n), so a slow HTTP client genuinely throttles the upstream Flux
  • R2DBC's @Transactional propagates the bound connection via Reactor Context, not ThreadLocal; prefer TransactionalOperator for an explicit boundary; a mixed R2DBC+JDBC chain is two separate transactional domains, never one
  • Test time-based operators with StepVerifier.withVirtualTime() (build the publisher inside the supplier lambda); use TestPublisher to simulate upstream backpressure/failure/protocol violations
  • 2026 decision framework: default new services to Spring MVC + virtual threads; reach for WebFlux only for a genuine backpressure/streaming/composition need or an already-reactive stack - most fleets end up hybrid, not all-in on one model
