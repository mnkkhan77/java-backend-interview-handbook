SECTION 1 - GIT FUNDAMENTALS

Q1. What is Git and how does a distributed VCS differ from a centralized one?

ROI: ★★★★☆ Frequency: High

Short Answer

Git is a distributed version control system (DVCS). Every clone is a full copy of the repository, including the entire history, not just the latest snapshot. This is the key difference from a centralized VCS like SVN or Perforce, where there is one canonical server and your checkout holds only the current files.

Because each developer has the full history locally, almost everything is fast and offline: commits, diffs, branching, viewing log and blame all happen without a network round-trip. The "remote" (GitHub, GitLab) is just another clone that the team agrees to treat as the source of truth.

AspectCentralized (SVN)Distributed (Git)
History locationCentral server onlyEvery clone has full history
CommitNeeds server connectionLocal, offline
BranchingExpensive, server-sideCheap, local pointer
Single point of failureYes (the server)No — any clone can restore

Interview Gold Point

Stress that in Git a "commit" and a "push" are separate steps. Centralized-VCS thinking assumes saving = publishing; the senior insight is that you commit locally as often as you like and only push when the work is shareable.

Q2. Explain the three areas: working directory, staging area, and repository.

ROI: ★★★★★ Frequency: Very High

Short Answer

Git tracks changes across three areas. Understanding them explains almost every confusing Git moment.

  • Working directory — the actual files on disk you edit.
  • Staging area (index) — a "draft" of your next commit. git add moves a snapshot of a change here.
  • Repository (the .git directory) — the committed history. git commit takes whatever is staged and records it permanently. HEAD is a pointer to the commit you currently have checked out.
# See all three at once
git status

# working dir -> staging area
git add UserService.java

# staging area -> repository
git commit -m "Add user lookup by email"

# inspect what is staged vs not staged
git diff            # working dir vs staging
git diff --staged   # staging vs last commit (HEAD)

Interview Favorite

The staging area is what lets you craft a clean commit from a messy working directory. Mention git add -p (patch mode) to stage only selected hunks of a file — a strong signal that you curate commits deliberately rather than blindly git add . everything.

Q3. What is a commit really? What does it store?

ROI: ★★★★☆ Frequency: Medium

Short Answer

A commit is an immutable snapshot of the entire tracked tree at a point in time — not a diff. Each commit object stores a pointer to a tree (the directory/file structure), the author and committer metadata, the message, and a pointer to its parent commit(s). A merge commit has two or more parents.

The full history is therefore a directed acyclic graph (DAG) of commits linked by parent pointers. Each commit is identified by a SHA-1 (now SHA-256) hash of its content, which is why history is tamper-evident: change anything and every downstream hash changes.

git cat-file -p HEAD
# tree 9f3a...        <- snapshot of files
# parent 4b1c...      <- previous commit
# author Nasir <n@x.io> 1718...
# committer ...
#
# Add user lookup by email

Common Mistake

Saying "a commit stores the changes/diff." Git stores full snapshots and computes diffs on demand. It deduplicates with content-addressable storage, so unchanged files just reuse the same blob — efficient, but conceptually still a snapshot.

Q4. What is the difference between git fetch and git pull?

ROI: ★★★★★ Frequency: Very High

Short Answer

git fetch downloads new commits and refs from the remote into your local remote-tracking branches (e.g. origin/main) but does not touch your working branch. It is safe and non-destructive — you can inspect before integrating.

git pull is effectively git fetch followed by an automatic merge (or rebase) of the remote branch into your current branch. It changes your working branch and can trigger conflicts immediately.

git pull                 # = git fetch + git merge origin/<branch>
git pull --rebase        # = git fetch + git rebase origin/<branch>

# Safer habit: look before you leap
git fetch origin
git log --oneline HEAD..origin/main   # what's new upstream
git merge origin/main                 # integrate when ready

Interview Gold Point

Many teams set pull.rebase = true to avoid noisy "Merge branch main" commits on every sync. Mentioning that you prefer fetch + review, or a rebasing pull, shows you care about keeping history linear and readable.

SECTION 2 - BRANCHING & INTEGRATION

Q5. What is a branch in Git, and why is it so cheap?

ROI: ★★★★☆ Frequency: High

Short Answer

A branch is simply a movable pointer to a commit — a 41-byte file under .git/refs/heads/ containing a SHA. Creating a branch does not copy any files; it just writes a new pointer. That is why branching is instant and weighs almost nothing, unlike older centralized systems.

When you commit on a branch, the branch pointer advances to the new commit. HEAD normally points at the current branch, which in turn points at the latest commit.

git branch feature/email-login   # create pointer at current commit
git switch feature/email-login   # move HEAD onto it (modern syntax)
git switch -c feature/email-login  # create + switch in one step

cat .git/refs/heads/feature/email-login   # just a SHA

Interview Favorite

Prefer git switch / git restore (introduced in Git 2.23) over the overloaded git checkout. Knowing that checkout historically did three unrelated jobs — switch branch, restore files, detach HEAD — and that the team split it for clarity, signals you keep current.

Q6. Merge vs rebase: what is the difference and when do you use each?

ROI: ★★★★★ Frequency: Very High

Short Answer

Merge combines two branches by creating a new merge commit with both branches as parents. It preserves the true history exactly as it happened, including the divergence — but produces a non-linear graph.

Rebase replays your commits on top of another branch's tip, rewriting them as new commits with new hashes. The result is a clean, linear history as if you had branched from the latest main all along.

# Bring my feature up to date with main, cleanly:
git switch feature/email-login
git rebase main          # replays feature commits onto main's tip

# Integrate finished work, preserving history:
git switch main
git merge feature/email-login
Use rebase whenUse merge when
Updating your local feature branch with mainIntegrating a feature into a shared branch
Cleaning up local commits before a PRYou want to preserve the real branch topology
You want linear, readable historyThe branch is shared / already pushed

Interview Gold Point

The golden rule: never rebase commits that others have already pulled (public/shared history). Rebasing rewrites hashes; teammates' history then diverges and they get nasty conflicts on the next pull. Rebase private/local work freely; merge to integrate shared work.

Q7. Fast-forward vs three-way merge — what is the difference?

ROI: ★★★★☆ Frequency: Medium

Short Answer

A fast-forward merge happens when the target branch has not diverged — the branch you are merging is strictly ahead. Git simply moves the pointer forward; no merge commit is created.

A three-way merge happens when both branches have new commits since they diverged. Git uses three inputs — the two branch tips and their common ancestor (merge base) — to compute the result, and records a merge commit with two parents.

# Force a merge commit even when a fast-forward is possible
git merge --no-ff feature/email-login

# Refuse to merge unless it can fast-forward (keeps history linear)
git merge --ff-only feature/email-login

Interview Favorite

Many teams use --no-ff for feature merges so each feature appears as one identifiable bubble in history (easy to revert as a unit), while using --ff-only on pulls to guarantee a linear mainline. Explaining the trade-off, not just the flags, is what scores points.

Q8. How do you resolve a merge conflict?

ROI: ★★★★★ Frequency: Very High

Short Answer

A conflict occurs when two branches change the same lines (or one edits a file the other deletes) and Git cannot auto-merge. Git pauses, marks the conflicting regions in the file with markers, and waits for you to decide.

You open each conflicted file, pick the correct combined result, remove the markers, stage the file, and continue the merge or rebase.

<<<<<<< HEAD
int timeout = 30;        // your change
=======
int timeout = 60;        // incoming change
>>>>>>> feature/email-login

# Workflow:
git status               # list conflicted files
# edit files, resolve, delete the <<< === >>> markers
git add UserService.java
git merge --continue     # or: git rebase --continue
git merge --abort        # bail out and return to pre-merge state

Interview Gold Point

Mention git rerere ("reuse recorded resolution") for repetitive rebase conflicts, and that the best conflict is the one you avoid — small PRs and frequent rebasing onto main keep conflicts tiny. Senior engineers manage conflict surface area, not just resolve conflicts.

SECTION 3 - HISTORY MANAGEMENT

Q9. Explain git reset --soft, --mixed, --hard versus git revert.

ROI: ★★★★★ Frequency: Very High

Short Answer

git reset moves the current branch pointer (and optionally the index/working tree) to a different commit — it rewrites history and is for local, unpushed work. git revert creates a new commit that undoes a previous commit's changes — it is safe for shared history because it adds rather than rewrites.

CommandMoves HEADStaging areaWorking dirUse for
reset --softYesKept (staged)KeptRecommit / squash last commits
reset --mixed (default)YesResetKeptUnstage but keep changes
reset --hardYesResetDiscardedThrow work away (dangerous)
revertNo (adds commit)——Undo a pushed commit safely
git reset --soft HEAD~1     # uncommit last commit, keep changes staged
git reset --mixed HEAD~1    # uncommit + unstage, keep file edits
git reset --hard HEAD~1     # destroy last commit AND its changes
git revert <sha>            # safe undo on a shared branch

Common Mistake

Using reset --hard on a branch others share. The rule: reset for private history, revert for public history. Also note git restore is the modern, focused way to discard working-directory changes without touching commits.

Q10. How do you squash commits and use interactive rebase?

ROI: ★★★★☆ Frequency: High

Short Answer

Interactive rebase lets you rewrite a series of local commits — reorder, combine, edit messages, or drop them — before sharing. Squashing collapses several work-in-progress commits ("wip", "fix typo", "oops") into one clean, meaningful commit for review.

git rebase -i HEAD~4

# An editor opens with the last 4 commits:
pick   a1b2c3  Add email login endpoint
squash d4e5f6  wip
squash 7890ab  fix validation
reword cdef01  add tests

# Commands you can use:
#   pick   = keep commit as-is
#   reword = keep changes, edit the message
#   squash = merge into the previous commit, combine messages
#   fixup  = like squash but discard this commit's message
#   drop   = delete the commit entirely

Interview Favorite

Tie this back to the rebase golden rule: squash before you push or merge, never on commits others already have. Also mention many platforms offer "Squash and merge" on the PR button, which keeps mainline clean without you rewriting locally.

Q11. What makes a good commit message, and how do tags / semantic versioning work?

ROI: ★★★★☆ Frequency: Medium

Short Answer

A good commit message has a concise (~50 char) imperative subject line ("Add retry to payment client"), a blank line, then a body explaining the why, not the what (the diff already shows what). Many teams adopt Conventional Commits (feat:, fix:, chore:) to drive automated changelogs and version bumps.

Tags mark a specific commit, typically a release. An annotated tag stores metadata and is the right choice for releases; a lightweight tag is just a pointer. Semantic Versioning is MAJOR.MINOR.PATCH: breaking change bumps MAJOR, backward-compatible feature bumps MINOR, bug fix bumps PATCH.

git tag -a v2.3.0 -m "Release 2.3.0: add OAuth login"
git push origin v2.3.0
git tag                       # list tags

# Conventional Commits map cleanly to SemVer:
#   fix:   -> PATCH (2.3.0 -> 2.3.1)
#   feat:  -> MINOR (2.3.1 -> 2.4.0)
#   feat!: / BREAKING CHANGE -> MAJOR (2.4.0 -> 3.0.0)

Interview Gold Point

Explain that disciplined commit messages and SemVer tags are not vanity — they let tools auto-generate changelogs, let consumers reason about upgrade risk, and make git bisect and incident forensics dramatically faster.

SECTION 4 - WORKFLOWS

Q12. Compare Git Flow, GitHub Flow, and trunk-based development.

ROI: ★★★★★ Frequency: High

Short Answer

These are branching strategies, and the right one depends on your release cadence and team maturity. The trend in high-performing teams is toward short-lived branches and frequent integration (trunk-based), which is what continuous delivery and DORA research favor.

StrategyBranchesBest fitTrade-off
Git Flowmain, develop, feature/*, release/*, hotfix/*Scheduled releases, versioned products, multiple supported versionsHeavy; many long-lived branches; merge pain
GitHub Flowmain + short feature branches via PRsWeb apps deploying continuously from mainAssumes strong CI and fast review
Trunk-basedmain + very short-lived branches; feature flagsCI/CD, mature teams, high deploy frequencyRequires flags, strong tests, discipline

Interview Gold Point

The senior answer is "it depends on release cadence." For a SaaS deploying many times a day, Git Flow's develop/release branches add overhead with little benefit — trunk-based with feature flags is the better fit. Knowing why long-lived branches cause integration pain (merge debt grows with divergence) is the differentiator.

Q13. Walk me through a pull request and code review workflow.

ROI: ★★★★☆ Frequency: High

Short Answer

A pull request (PR) is a request to merge a branch, plus a place for review, CI checks, and discussion. The flow: branch from main, commit focused changes, push, open a PR with a clear description and linked ticket, let CI run, address review comments, then merge (often squash-merge) and delete the branch.

git switch -c feature/JIRA-481-email-login
# ... commit work ...
git push -u origin feature/JIRA-481-email-login
# open PR in GitHub/GitLab UI

# keep the PR current without a messy merge commit:
git fetch origin
git rebase origin/main
git push --force-with-lease   # safe force: refuses if remote moved
  • Keep PRs small and single-purpose — easier to review, faster to merge.
  • Write a description: what, why, how to test.
  • Reviewers focus on correctness, design, edge cases — not style (let a linter do that).
  • Require green CI and at least one approval before merge.

Interview Favorite

Use git push --force-with-lease, never plain --force, after a rebase. --force-with-lease refuses to overwrite if someone else pushed in the meantime, protecting against clobbering a teammate's work — a hallmark of someone who has been burned and learned.

Q14. How do you undo common mistakes and recover with reflog?

ROI: ★★★★★ Frequency: Very High

Short Answer

Most "I broke Git" panics are recoverable because Git rarely deletes anything immediately. The reflog records every move of HEAD — even after a hard reset or a deleted branch — so you can find the lost commit's SHA and restore it.

# Undo the last commit but keep the changes
git reset --soft HEAD~1

# Unstage a file (keep edits)
git restore --staged config.yml

# Discard working-directory changes to a file
git restore config.yml

# Recover a "lost" commit or deleted branch
git reflog                       # find the SHA before the mistake
git reset --hard HEAD@{2}        # jump back to that state
git switch -c rescued <sha>      # rebuild a branch from a lost commit

Interview Gold Point

The line that lands: "Git almost never loses committed work — reflog and dangling objects keep it for ~30 days by default." Knowing the reflog exists separates people who fear Git from people who use it confidently.

SECTION 5 - PRACTICAL

Q15. Explain git stash, cherry-pick, .gitignore, hooks, and handling secrets / large binaries.

ROI: ★★★★☆ Frequency: High

Short Answer

These are the everyday practical tools that show day-to-day fluency.

  • git stash — shelve uncommitted changes to switch context (e.g. an urgent hotfix), then restore them.
  • git cherry-pick — apply a single commit from one branch onto another, e.g. backporting a fix to a release branch.
  • .gitignore — patterns for files Git should never track (build output, IDE files, secrets, dependencies like target/ or node_modules/).
  • Git hooks — scripts that fire on events; pre-commit can run linters/tests/secret-scanners before a commit is allowed.
git stash push -m "wip login form"
git switch hotfix/payments
# ... fix and commit ...
git switch feature/login
git stash pop                    # restore shelved work

git cherry-pick <sha>           # backport one commit to a release branch

# .gitignore example
target/
*.log
.env
.idea/

Secrets & large binaries: never commit secrets — once pushed, they live in history forever and must be treated as compromised (rotate the key, then scrub with git filter-repo or BFG). Use .env + a secrets manager and a pre-commit secret scanner. For large binaries, avoid bloating the repo (every clone pays for them forever) — use Git LFS or an artifact store instead.

Common Mistake

Thinking git rm --cached or a later commit "removes" a leaked secret. It is still in history and on every clone. The only correct response is: rotate the credential immediately, then rewrite history. Saying this out loud signals real security maturity.

SECTION 6 - GIT OBJECT MODEL & INTERNALS

Q16. Explain Git's object model: blobs, trees, commits, and tags.

ROI: ★★★★★ Frequency: High

Short Answer

Everything in Git's history is one of four object types, all stored under .git/objects and addressed by the SHA hash of their own content. A blob stores raw file content (no filename, no metadata). A tree stores a directory listing: a mapping of names to blob or tree SHAs plus file modes. A commit points at one tree (the snapshot) and one or more parent commits, plus author/committer/message metadata. An annotated tag is its own object pointing at a commit, carrying a message and optional GPG/SSH signature.

Notice what is missing: there is no "rename" object and no "diff" object. A file's name lives only in the tree that references its blob, which is why renaming a file whose content is unchanged creates zero new blob objects — the tree simply points the new name at the same existing blob SHA.

git cat-file -t HEAD^{tree}      # tree
git ls-tree HEAD                # name -> mode, type, SHA
100644 blob 8ab68f2   README.md
040000 tree 3fa91cd   src

git cat-file -p HEAD             # commit object
tree 3fa91cd...
parent 9b1e02f...
author Nasir <n@x.io> 1718...
committer ...

Add retry to payment client

Interview Gold Point

Say it plainly: "a commit is a pointer to a tree plus a pointer to its parent(s)." That one sentence explains why history is a DAG, why two commits with identical trees but different parents are different objects, and why Git can deduplicate identical file content across the entire repository automatically.

Q17. Why is Git called a content-addressable store, and how does that differ from a "diff-based" VCS?

ROI: ★★★★☆ Frequency: Medium

Short Answer

In a content-addressable store, an object's identity is the hash of its own content — store the same bytes twice and you get the same SHA, so it is only ever stored once. Older, diff-based systems (CVS, older SVN) instead store each revision as a delta against the previous one and must replay a chain of diffs to reconstruct any given version.

The practical consequences run deep: Git can jump straight to any historical snapshot without walking a chain (fast checkout of old commits), identical content anywhere in history is automatically deduplicated, and a corrupted object is immediately detectable because its hash no longer matches its content. Git does still apply delta compression — but only later, for storage efficiency in packfiles, never as the mechanism for reconstructing a snapshot.

Common Mistake

Saying Git "stores diffs like SVN, just distributed." It doesn't — it stores full-content objects keyed by hash and computes diffs on the fly for display. Confusing the storage model with the (later, optional) packing optimization is a common junior-level slip.

Q18. What are packfiles, and how does git gc keep large repositories fast?

ROI: ★★★★☆ Frequency: Medium

Short Answer

Every new commit initially creates loose objects — one zlib-compressed file per object under .git/objects/xx/. That is simple but wasteful at scale: lots of small files, no cross-object compression. git gc (triggered automatically by git gc --auto once loose-object counts cross a threshold, or run manually) collects loose objects into a single packfile plus an index (.pack / .idx), using delta compression between similar objects — e.g. successive versions of the same file are stored as a small delta against a chosen base rather than full copies.

git count-objects -v          # loose objects, size, packs
git gc                        # repack loose objects, prune unreachable
git gc --aggressive           # deeper repack, much slower, rarely needed

Interview Gold Point

Mention that this is also how the network protocol works: a git push/git fetch negotiates and transfers a packfile, not individual objects, which is why a repo with poor delta locality (e.g. lots of large, frequently-changed binaries) is slow to clone even before you touch local storage.

Q19. Loose objects vs packed objects — what's the difference and when does packing happen?

ROI: ★★★☆☆ Frequency: Medium

Short Answer

A loose object is one file, individually zlib-compressed, with no relationship to any other object on disk. A packed object lives inside a packfile alongside many others, frequently stored as a delta against a similar "base" object chosen by Git's packing heuristics, which is why packed storage is dramatically smaller for repositories with many similar revisions of the same files.

AspectLoose objectsPacked objects
StorageOne file per objectMany objects in one file + index
CompressionPer-object zlib onlyZlib + inter-object delta
Created byEvery new commit/addgit gc / git repack / push-fetch negotiation
Typical sizeLarger in aggregateMuch smaller in aggregate

Interview Favorite

Note that unreachable loose objects — the leftovers of a reset --hard, an amended commit, or an abandoned rebase — are exactly what makes reflog-based recovery possible. git gc respects gc.pruneExpire (default two weeks) before actually deleting them, which is the safety window behind "Git almost never loses committed work immediately."

Q20. How does Git detect file renames if it doesn't store them explicitly?

ROI: ★★★★☆ Frequency: Medium

Short Answer

Git never records a "rename" operation anywhere — a tree simply has a different name-to-blob mapping between two commits. Tools like git diff, git log --follow, and the merge machinery detect renames after the fact by similarity heuristics: they look for a path deleted in one tree and a path added in the other whose blob content is similar enough (by default at least 50% similar, tunable with -M<percent>) and present it as a rename.

git diff -M                     # detect renames explicitly in a diff
git log --follow -- OldName.java  # follow a single file across renames

Common Mistake

Assuming git log --follow works for a directory or multiple files — it only follows a single file path. Also, because rename detection is a similarity heuristic, heavily editing a file in the same commit as renaming it can push similarity below the threshold, and Git will present it as a plain delete + add instead of a rename.

Q21. What's stored in .git besides objects, and how do refs, HEAD, and the index fit together?

ROI: ★★★☆☆ Frequency: Medium

Short Answer

.git/objects is the content store described above. .git/refs/heads/* and .git/refs/tags/* are named pointers — plain text files (or entries in packed-refs once there are many) each holding a single commit SHA. HEAD is a symbolic reference: normally a pointer to the current branch ref (e.g. ref: refs/heads/main), which in turn points at a commit — two hops to get "the current commit." The index (.git/index) is a separate binary file representing the staging area: a flat list of paths, blob SHAs, and file-stat cache entries used to make git status and git diff fast without rehashing every file.

cat .git/HEAD                          # ref: refs/heads/main
cat .git/refs/heads/main               # a1b2c3d4...

git checkout a1b2c3d       # HEAD now points directly at a commit
cat .git/HEAD               # a1b2c3d4...   <- "detached HEAD"

Interview Gold Point

Use this to explain detached HEAD precisely: it is simply the state where HEAD holds a commit SHA directly instead of a symbolic ref to a branch. Any new commit made there has no branch pointer following it, so it becomes unreachable and eligible for GC unless you create a branch to hold onto it — exactly the scenario the reflog recovery workflow (Q14) is designed to rescue.

SECTION 7 - HISTORY FORENSICS & DEBUGGING TOOLS

Q22. How do you use git bisect to find the exact commit that introduced a regression?

ROI: ★★★★★ Frequency: High

Short Answer

git bisect performs a binary search over a commit range between a known-good and a known-bad commit. You mark each end, Git checks out the midpoint, you test it and report good or bad, and Git halves the remaining range each time — finding the culprit in roughly log2(n) steps instead of a linear crawl through history.

git bisect start
git bisect bad                 # current commit is broken
git bisect good v2.3.0         # this old tag was fine

# Git checks out a midpoint commit each time:
git bisect good     # or
git bisect bad
# ... repeat until Git reports the first bad commit ...

git bisect reset               # return to original branch when done

Interview Gold Point

The senior move is git bisect run <script>, automating the entire search with a script that exits 0 for good and non-zero for bad — turning a debugging session that could take a day of confused stepping through code into a few minutes of unattended CI-style execution.

Q23. What is git blame, and what are its limits for tracking down why a line of code exists?

ROI: ★★★★☆ Frequency: High

Short Answer

git blame <file> annotates every line with the commit, author, and date that last touched it — the standard way to answer "why is this weird timeout value 4500ms?" before you go bother a teammate. But blame only shows the last change to a line, not necessarily the original author or the real reason it exists; a wholesale reformat or a bulk rename can bury the meaningful history under a single "reformat code" commit.

git blame -w UserService.java         # ignore whitespace-only changes
git blame -C -C UserService.java      # detect moves/copies across files
git blame --ignore-revs-file .git-blame-ignore-revs UserService.java

Interview Favorite

Mention the .git-blame-ignore-revs convention (supported natively by GitHub/GitLab's blame view): list large reformat/auto-fix commit SHAs in that file so blame skips straight past them to the last meaningful change — a small habit that keeps blame useful forever after a big lint/format pass.

Q24. What do git log -p, --follow, and -S (the pickaxe) do?

ROI: ★★★★☆ Frequency: Medium

Short Answer

These are the log-forensics tools for "when and why did this text appear or disappear." -p shows the actual patch alongside each commit, not just the message. --follow continues a single file's history across renames (only works for one path at a time). -S"<string>" — the "pickaxe" — finds commits where the number of occurrences of a string changed, which is how you find exactly when a function, constant, or bug was introduced or removed, regardless of what the commit message says.

git log -p -- PaymentClient.java             # full diffs for one file
git log --follow -- PaymentClient.java       # history across renames
git log -S"retryTimeoutMs" --oneline         # when did this string's count change
git log -G"retry.*[Tt]imeout" --oneline      # regex match against diff content

Interview Gold Point

Distinguish -S from -G precisely: -S triggers only when the total occurrence count of the string changes (add one, remove one elsewhere in the same commit — count unchanged — and -S stays silent), while -G matches any commit whose diff contains a line matching the regex, regardless of count. Knowing which one to reach for is a real signal of hands-on log forensics experience.

Q25. What is git worktree, and how does it let you work on multiple branches simultaneously?

ROI: ★★★★☆ Frequency: Increasingly Common

Short Answer

git worktree checks out another branch into a separate working directory that shares the same underlying .git object store and refs — no second clone, no stashing your in-progress feature work just to jump onto an urgent hotfix. Each worktree has its own working directory and index, but a fetch or a new commit in one is immediately visible from the others because they share history.

git worktree add ../hotfix-payments hotfix/payments
cd ../hotfix-payments
# ... fix, commit, push, PR, all independent of the main working dir ...

git worktree list
git worktree remove ../hotfix-payments

Common Mistake

Trying to check the same branch out in two worktrees at once — Git refuses, since a branch pointer can only be "checked out" in one place at a time. Also remember to git worktree remove (not just rm -rf the directory) so Git's internal bookkeeping in .git/worktrees/ stays clean.

Q26. What is git rerere, and when is it worth enabling?

ROI: ★★★☆☆ Frequency: Medium

Short Answer

git rerere ("reuse recorded resolution") records how you manually resolved a merge conflict, and if the identical conflict shows up again — extremely common when repeatedly rebasing a long-lived branch onto a fast-moving main, or maintaining a fork with recurring upstream merges — Git reapplies the same resolution automatically instead of making you retype it.

git config --global rerere.enabled true
# resolve a conflict once as normal; next time the same hunk conflicts,
# rerere stages the previously recorded resolution automatically

Interview Gold Point

The strongest example: rebasing a big long-lived feature branch onto main day after day produces the same conflicting hunk in an unrelated file every single time. Without rerere you resolve it manually on every rebase; with it enabled once, every subsequent rebase resolves that hunk silently.

Q27. How do you automate a regression hunt with git bisect run?

ROI: ★★★☆☆ Frequency: Medium

Short Answer

git bisect run <script> hands the entire search loop to a script: exit code 0 means good, any code from 1-127 (except 125) means bad, and 125 means "skip this commit" — used when a given commit simply can't be tested (e.g. the build itself is broken there for an unrelated reason), so bisect steps around it instead of drawing a wrong conclusion.

git bisect start HEAD v2.3.0
git bisect run ./run-regression-test.sh
# Git walks the whole range unattended and reports the first bad commit

Interview Favorite

A regression-hunt script is only as good as its test's determinism — a flaky test will make bisect converge on the wrong commit. Mentioning that you'd first confirm the test script reliably reproduces the bug before trusting an automated bisect run is a mark of real debugging discipline.

SECTION 8 - SECURITY: COMMIT SIGNING & GIT HOOKS

Q28. Why and how do you sign commits, and what does a "Verified" badge mean on GitHub/GitLab?

ROI: ★★★★☆ Frequency: Medium-High

Short Answer

Anyone can set git config user.email "anyone@anywhere.com" — the author/committer fields are just claims, not proof of identity. Signing a commit (with GPG, or the simpler modern SSH-key based signing) attaches a cryptographic signature over the commit's content, proving it was created by whoever holds a specific private key. The platform verifies that signature against a public key registered to the account and shows a "Verified" badge — a much stronger identity guarantee than the plain author field.

git config --global gpg.format ssh
git config --global user.signingkey ~/.ssh/id_ed25519.pub
git config --global commit.gpgsign true

git log --show-signature -1        # inspect a signature

Interview Gold Point

Note that some orgs go further and enforce "Require signed commits" as a branch protection rule on protected branches — a server-side gate that rejects any push containing an unsigned commit, closing the identity-spoofing gap entirely rather than just displaying a badge.

Q29. Client-side vs server-side Git hooks — what's the difference?

ROI: ★★★★☆ Frequency: Medium

Short Answer

Client-side hooks (pre-commit, commit-msg, pre-push, post-checkout, and more) live under .git/hooks/ on each developer's own machine. Crucially, .git is not versioned content — hooks are not transferred by clone or push, so they cannot be centrally enforced without extra tooling (a setup script, or a framework like pre-commit). Server-side hooks (pre-receive, update, post-receive) run on the Git server itself when a push arrives, and — unlike client-side hooks — can actually reject the push. This is the real mechanism behind platform features like branch protection and required signed commits.

AspectClient-sideServer-side
Runs whereDeveloper's machineGit server / platform
Distributed by clone?NoN/A (server config)
Can be bypassed by dev?Yes (--no-verify)No
Used forFast local feedbackReal enforcement

Common Mistake

Treating a client-side pre-commit hook as a compliance control. It is a convenience for developers who have it installed; it enforces nothing for anyone who hasn't run the setup step or who passes --no-verify. Real enforcement always needs a server-side or CI-equivalent required check.

Q30. How do teams use pre-commit for linting and secret scanning?

ROI: ★★★★☆ Frequency: High

Short Answer

The pre-commit framework (or a hand-rolled .git/hooks/pre-commit script) runs fast checks — a formatter, a linter, a focused subset of unit tests, and, critically, a secret scanner (gitleaks, truffleHog, detect-secrets) — before a commit is even created. Catching an accidentally-pasted AWS key at commit time is dramatically cheaper than catching it after it has been pushed and is already permanently in history (see Q55/Q56).

# .pre-commit-config.yaml
repos:
  - repo: https://github.com/gitleaks/gitleaks
    rev: v8.18.0
    hooks:
      - id: gitleaks

Interview Gold Point

Always pair this with the honest caveat from Q29: hooks are per-developer opt-in and bypassable with --no-verify. Mature teams run the exact same secret-scan as a required CI check on every PR, so the local hook is a fast first line of defense and the CI check is the actual backstop.

Q31. Can Git hooks be bypassed, and how do teams enforce checks centrally despite that?

ROI: ★★★☆☆ Frequency: Medium

Short Answer

Yes — git commit --no-verify and git push --no-verify skip client-side hooks outright, and since hooks live only in the local, unversioned .git/hooks/ directory, there is no way to force every clone to have them installed. The reliable enforcement points are always server-side: a pre-receive hook on a self-hosted Git server, or — far more common today — required CI status checks combined with branch protection rules on GitHub/GitLab, which re-run the same linting and secret-scanning as an un-bypassable gate before a merge is even allowed.

Interview Favorite

The line that lands: "local hooks are a courtesy to the developer; the required CI check on the PR is the actual control." Interviewers ask this specifically to see whether you understand that developer tooling and enforcement are two different layers.

Q32. What is a commit-msg hook used for, e.g. enforcing Conventional Commits?

ROI: ★★★☆☆ Frequency: Medium

Short Answer

The commit-msg hook receives the path to the drafted commit message file and can validate it — for example, rejecting the commit unless the subject line matches a pattern like ^(feat|fix|chore|docs|refactor|test)(\(.+\))?: .+ — or rewrite it, such as appending a ticket ID parsed from the branch name. It is the standard local mechanism for enforcing a Conventional Commits format before the commit is even created.

#!/bin/sh
# .git/hooks/commit-msg
pattern='^(feat|fix|chore|docs|refactor|test|perf|build|ci)(\(.+\))?!?: .+'
if ! grep -qE "$pattern" "$1"; then
  echo "Commit message must follow Conventional Commits format." >&2
  exit 1
fi

Interview Gold Point

Since this hook is bypassable like any other (Q31), many teams instead (or additionally) validate the PR title and/or the final squashed commit in CI, since that is the message that actually lands on main and feeds the changelog tooling in Section 12.

SECTION 9 - .GITATTRIBUTES, LINE ENDINGS & GIT LFS

Q33. What does .gitattributes control, and how does core.autocrlf handle line endings?

ROI: ★★★★☆ Frequency: Medium

Short Answer

.gitattributes is a versioned, path-based configuration file — checked into the repo itself, unlike .git/config — that tells Git how to treat specific paths: text normalization, marking files binary, custom diff/merge drivers, export rules, and LFS tracking. The classic pain point it solves is line endings: Windows uses CRLF, Unix/macOS use LF, and without normalization every file looks changed to whichever teammate is on the other OS, generating noisy whole-file diffs.

# .gitattributes — normalize everything to LF in the repo,
# regardless of what any individual developer's OS checks out
* text=auto
*.bat text eol=crlf
core.autocrlf valueOn checkoutOn commitTypical use
trueLF → CRLFCRLF → LFWindows developers
inputNo conversionCRLF → LFMac/Linux developers
falseNo conversionNo conversionRepo-level `* text=auto` instead

Interview Gold Point

Prefer .gitattributes's * text=auto over relying on every developer setting core.autocrlf correctly — the attributes file travels with the repo and applies uniformly, while a local config setting is one more thing a new teammate can forget to configure.

Q34. How do you mark files as binary or plug in a custom diff driver via .gitattributes?

ROI: ★★★☆☆ Frequency: Low-Medium

Short Answer

*.png binary is shorthand for -diff -merge -text: it tells Git not to attempt a line-based diff or three-way merge (meaningless, and potentially corrupting, for binary content) and not to apply CRLF normalization. For formats where a meaningful diff is possible — Jupyter notebooks, Word documents, compiled Java classes — you can register a custom diff driver that runs the file through a text-conversion command first.

# .gitattributes
*.png binary
*.ipynb diff=jupyternb

# .git/config or ~/.gitconfig
[diff "jupyternb"]
    textconv = jupyter nbconvert --to script --stdout

Common Mistake

Forgetting to mark genuinely binary formats (fonts, compiled artifacts, images) as binary — without it, Git may attempt textual diff/merge heuristics on them, producing meaningless diff output or, worse, a corrupted merge result.

Q35. What problem does Git LFS solve, and how does it differ from committing binaries directly?

ROI: ★★★★☆ Frequency: Medium-High

Short Answer

Committing a large binary directly means every clone, fetch, and checkout carries every historical version of that file forever — Git's delta compression works well on text but poorly on most binary formats, so the repository balloons and never shrinks even after the file is later deleted (it is still reachable from history). Git LFS solves this by replacing the binary's content in Git with a tiny text "pointer" file (an object ID and size); the actual bytes live in a separate LFS store and are fetched on demand via smudge/clean filters as you check files out.

git lfs install
git lfs track "*.psd"
cat .gitattributes
# *.psd filter=lfs diff=lfs merge=lfs -text

git add design.psd .gitattributes
git commit -m "Add design mockup via LFS"

Interview Gold Point

Frame the trade-off honestly: LFS keeps the core Git repo small and fast, but it requires an LFS-compatible remote, adds a dependency (a plain git clone without LFS installed only gets pointer files, not usable binaries), and is one more piece of infrastructure to operate. It is worth it once binaries are large and change often; it's overkill for a handful of static images.

Q36. How do you migrate an existing repo to Git LFS after large files are already in history?

ROI: ★★★☆☆ Frequency: Medium

Short Answer

Adding an LFS track rule only affects files added going forward — it does nothing for binaries already committed as regular blobs in history, so the repository stays bloated. git lfs migrate rewrites history (the same fundamental operation as git filter-repo) to replace matching blobs with LFS pointers across every commit and branch, which changes every downstream commit hash.

git lfs migrate import --include="*.psd,*.zip" --everything
git push --force --all
git push --force --tags

Common Mistake

Running an LFS history migration without warning the team. Every commit hash changes, exactly like the secrets-scrubbing rewrite in Section 14 — it requires a coordinated force-push and every collaborator either hard-resetting to the new history or re-cloning.

SECTION 10 - SCALING GIT: MONOREPOS, SPARSE & PARTIAL CLONE

Q37. Monorepo vs polyrepo — what are the trade-offs?

ROI: ★★★★☆ Frequency: High

Short Answer

A monorepo keeps most or all of an organization's projects in one repository: cross-project refactors are a single atomic commit, tooling and CI conventions are shared, and code sharing needs no package-publishing step. The cost is that the repo's size, clone time, and CI load grow without bound unless you invest in scaling techniques (sparse/partial clone, a build system like Bazel that avoids rebuilding everything). A polyrepo keeps each project independent: small, fast, independently access-controlled repos — at the cost of coordinating a change across many repos and versioning dependencies between them explicitly.

AspectMonorepoPolyrepo
Cross-project changesOne atomic commitCoordinated PRs across repos
Clone size / CI loadGrows with the whole orgStays small per repo
Tooling investmentHigh (build system, partial clone)Lower per-repo, higher for cross-repo tooling
Access controlCoarser (path-based)Naturally per-repo

Interview Gold Point

The senior answer is not "monorepos are better" or "polyrepos are better" — it's an infrastructure investment decision. Monorepos pay off when cross-project changes are frequent enough to justify the tooling cost; polyrepos are the pragmatic default until that tooling investment is worth making.

Q38. What is a shallow clone (--depth), and what are its limitations?

ROI: ★★★★☆ Frequency: High

Short Answer

git clone --depth 1 fetches only the most recent commit(s), skipping the rest of history entirely — dramatically faster and smaller, which is exactly what most CI jobs need since they only build the current tip. The limitation is that git log, git blame, and git bisect are crippled or impossible beyond the shallow boundary, and computing a merge-base against a far-back commit can fail if that commit was never fetched. Extending later requires git fetch --unshallow or --deepen=<n>.

git clone --depth 1 https://example.com/repo.git
git fetch --unshallow          # convert to a full clone later if needed

Interview Gold Point

This is a brief, Git-mechanics note deliberately — the full design of checkout strategies per pipeline stage (Jenkins/GitHub Actions/GitLab CI specifics) belongs to the dedicated CI/CD pipelines chapter, not here.

Q39. What is sparse-checkout, and when do you use it?

ROI: ★★★☆☆ Frequency: Medium

Short Answer

git sparse-checkout populates only a chosen subset of the working directory tree from a repository, even though the full commit history and object set may still be present. In a monorepo where a given team only ever touches services/payments/, there is no reason to materialize the other thousands of unrelated files on disk. Modern "cone mode" restricts by whole directory prefixes and is fast even in huge trees.

git sparse-checkout init --cone
git sparse-checkout set services/payments shared/lib

Common Mistake

Assuming sparse-checkout alone shrinks a clone — it only controls what's materialized in the working directory. The objects/history are still fetched in full unless paired with a partial clone (Q40).

Q40. What is a partial clone (--filter=blob:none), and how does it differ from a shallow clone?

ROI: ★★★☆☆ Frequency: Medium

Short Answer

A shallow clone truncates history depth — fewer commits, but full file content for whatever it does fetch. A partial clone (git clone --filter=blob:none origin) does the opposite trade: it fetches the full commit graph — so log, blame, bisect, and merge-base all work normally across all of history — but omits file content (blobs), fetching them lazily on demand from the "promisor remote" only as you check out or diff a given path.

AspectShallow clonePartial cloneSparse checkout
Commit historyTruncatedFullFull (unaffected)
File content (blobs)Full, for fetched rangeLazy, on demandFull (unaffected)
Working directoryFull treeFull treeChosen subset only

Interview Gold Point

This is the technique behind large-repo hosting at scale: full history navigation without paying for every historical blob upfront. Combined with sparse-checkout, an engineer's local clone can have complete metadata history but only the file content for the paths they actually work in.

Q41. How do very large engineering orgs keep Git usable at monorepo scale?

ROI: ★★★☆☆ Frequency: Senior Favorite

Short Answer

Organizations running single monorepos with millions of files and commits (as at Google or Microsoft) combine several techniques: partial clone plus sparse checkout so a given engineer's clone carries full history metadata but only the blobs/paths they touch; a virtual filesystem layer (Microsoft's VFS for Git / Scalar) that lazily materializes files on first access rather than at checkout time; and server-side optimizations — commit-graph files and a multi-pack-index that make history traversal and object lookup fast even at that scale.

git maintenance start           # schedules background gc/repack/commit-graph jobs

Interview Gold Point

Mention git maintenance as the modern, background-scheduled replacement for manually cron'ing git gc — it runs incremental repacking, commit-graph updates, and loose-object cleanup automatically, which is exactly the kind of infrastructure investment that makes monorepo scale viable at all.

Q42. What's a practical checklist for choosing monorepo vs polyrepo for a growing org?

ROI: ★★★☆☆ Frequency: Medium

Short Answer

Rather than a stance, treat it as a checklist. How often do changes genuinely span multiple projects or services? Does the org already have (or is it willing to build) monorepo-capable tooling — Bazel, Nx, Turborepo — to avoid rebuilding everything on every change? How much CI contention will many teams sharing one repo's protected branches create? Do teams need independently enforced access control or visibility per project? Is there appetite to adopt partial clone and sparse checkout as the repo grows past a comfortable clone size?

Common Mistake

Treating this as a purity contest ("monorepos are the modern way" or "polyrepos are simpler, always"). The senior answer connects the choice to concrete signals — cross-project change frequency, tooling maturity, and team size — rather than a general philosophy.

SECTION 11 - BRANCH PROTECTION & PLATFORM-LEVEL WORKFLOWS

Q43. What are branch protection rules, and what do they typically enforce?

ROI: ★★★★★ Frequency: High

Short Answer

Branch protection locks down a branch — usually main or a release branch — with rules enforced server-side by the platform, entirely independent of any developer's local Git config or good intentions. Typical rules: require a pull request before merging (no direct pushes), require a minimum number of approvals, require specific status checks to pass, require the branch to be up to date with its base before merging, require signed commits, restrict who can push or force-push, and disallow deleting the branch.

Interview Gold Point

The framing that lands: client-side hooks and team conventions are advisory; branch protection is enforced. Any workflow discipline you actually need guaranteed (not just hoped for) belongs in branch protection or a required CI check, never in a local hook alone.

Q44. What is a CODEOWNERS file, and how does it interact with required reviews?

ROI: ★★★★☆ Frequency: Medium

Short Answer

A CODEOWNERS file maps file paths or patterns to individuals or teams, e.g. /payments/ @payments-team. Combined with a branch-protection rule requiring review from Code Owners, a PR touching a given path cannot merge until someone from the mapped team has approved — automating "the right domain expert must sign off" instead of relying on someone remembering to manually tag them.

# CODEOWNERS
/payments/          @payments-team
/infra/terraform/   @platform-team
*.sql                @data-team
Q45. What are required status checks and merge queues, and why do teams add a merge queue?

ROI: ★★★★☆ Frequency: Medium

Short Answer

Required status checks block merging until named CI jobs report success against the PR's latest commit. The subtlety is that this alone doesn't guarantee the merged result stays green: two PRs can each individually pass against the current main yet conflict semantically once both have landed back-to-back. A merge queue closes that gap by serializing merges, re-testing each PR against the very latest main immediately before (and if the queue changes, again during) the merge, so main never goes red from a race between two approved-but-untested-together PRs.

Interview Gold Point

Use the phrase "tested together, not just tested separately" — it is exactly the gap a merge queue closes and is a strong signal you understand why "all checks passed" on two individual PRs is not the same guarantee as the combined result passing.

Q46. Merge commit vs squash-merge vs rebase-merge on the PR "merge" button — what's the trade-off?

ROI: ★★★★☆ Frequency: High

Short Answer

A merge commit preserves every individual commit plus the real branch topology — complete, but noisy. Squash-merge collapses the entire PR into a single commit on main — clean mainline, but the intermediate commit-by-commit history (and the granularity that would help git bisect later) is lost. Rebase-merge replays the PR's individual commits directly onto main with no merge commit at all — linear and detailed, but only works well if the author already curated each commit to be independently sensible and buildable.

StrategyMainline historyBest when
Merge commitNon-linear, completeYou want the exact real topology preserved
Squash-mergeLinear, one commit per PRPR commits are "wip"/noise, not individually meaningful
Rebase-mergeLinear, full detailAuthor already curated a clean commit series

Common Mistake

Picking squash-merge as a blanket team default without ever using interactive rebase (Q10) locally to curate a genuinely meaningful commit series — squash-merge quietly hides that habit was never built, since it papers over messy history rather than teaching people to avoid it.

Q47. How does branch protection interact with a rebase + force-push PR workflow?

ROI: ★★★☆☆ Frequency: Medium

Short Answer

Branch protection commonly disallows force-pushing to the protected branch itself, but does not (and should not) block force-pushing to your own feature branch — which is exactly what git push --force-with-lease after a local rebase requires (Q13). Some platforms add "require linear history" alongside "require branches to be up to date before merging," which effectively forces every contributor to rebase (not merge) onto the latest main before the merge button is enabled — keeping mainline strictly linear even though the org still uses PR-based review.

SECTION 12 - CONVENTIONAL COMMITS & AUTOMATED RELEASES

Q48. What is the Conventional Commits format, in depth?

ROI: ★★★★☆ Frequency: Medium-High

Short Answer

The structure is <type>[optional scope]: <description>, optionally followed by a body and footer(s). Types include feat, fix, docs, style, refactor, perf, test, build, ci, chore, and revert. A breaking change is marked either with a ! right after the type/scope (feat!:) or with a BREAKING CHANGE: footer. This structured, machine-parseable format is what lets tooling classify every commit automatically instead of a human writing a changelog by hand after the fact.

feat(auth): add OAuth login via Google

Adds a new /oauth/google endpoint and wires it into the
existing login flow.

BREAKING CHANGE: LoginResponse no longer includes `legacyToken`.
Q49. How does automated changelog generation from commit history work?

ROI: ★★★★☆ Frequency: Medium

Short Answer

Tools like conventional-changelog, release-please, or semantic-release parse the commits (or, more robustly, the squashed PR titles, if those are the ones enforced to the format) between the last release tag and HEAD, group them by type — Features, Bug Fixes, Breaking Changes — and generate or prepend a CHANGELOG.md section automatically as part of the release CI job. This removes both the manual toil of writing release notes and the human error of forgetting to mention a change.

Q50. How do CI pipelines automate semantic-version bumps from commit messages?

ROI: ★★★☆☆ Frequency: Medium

Short Answer

A release tool inspects every commit since the last tag: any feat bumps MINOR, any fix bumps PATCH, and any breaking-change marker bumps MAJOR (the highest-precedence bump wins if a batch contains a mix). The tool then computes the new version, creates the annotated tag, generates the changelog, and often publishes the artifact — all triggered automatically by a merge to main, with no manual "what version should this be" judgement call, as long as commit discipline (Q48) was followed upstream.

Interview Gold Point

Tie this back explicitly to Q11's SemVer answer: this is the payoff for disciplined commit messages — they are not vanity, they are the input data that makes automated, trustworthy version bumps possible at all.

SECTION 13 - ADVANCED RECOVERY: DANGLING COMMITS & FSCK

Q51. How do you recover from a bad force-push that overwrote a colleague's commits on a shared branch?

ROI: ★★★★☆ Frequency: High

Short Answer

The fastest fix is checking whether anyone still has the old commit's SHA locally — anyone who fetched before the bad push retains it in their own branch or reflog, and a corrective force-push of git reset --hard <old-sha> restores the remote. If nobody has a local copy, most Git hosts retain unreferenced commits for a retention window and support can sometimes recover them. As a last resort, git fsck --lost-found on any clone that had fetched the old tip before it was overwritten can locate the dangling commit locally, even without it being referenced by any branch.

Interview Gold Point

This is exactly why git push --force-with-lease (Q13) matters so much in practice — it refuses to overwrite if the remote moved since your last fetch, which is precisely the scenario that causes this incident in the first place.

Q52. What is git fsck --lost-found, and what are "dangling" commits/blobs?

ROI: ★★★☆☆ Frequency: Medium

Short Answer

A commit becomes dangling when nothing references it anymore — no branch, no tag, and no (unexpired) reflog entry points to it — but the object is still physically present in .git/objects because git gc hasn't pruned it yet. git fsck --unreachable (and --lost-found, which additionally dumps candidates into .git/lost-found/commit/ and .git/lost-found/other/) walks every object and lists ones unreachable from any ref, so you can inspect them with git show <sha> and recover anything relevant with git branch rescued <sha>.

git fsck --full --unreachable
git fsck --lost-found
ls .git/lost-found/commit/
git show <dangling-sha>
git branch rescued <dangling-sha>
Q53. When doesn't even reflog help — what happens once entries expire and gc prunes?

ROI: ★★★☆☆ Frequency: Medium

Short Answer

Reflog entries expire — by default after 90 days for entries still reachable via some ref, and after only 30 days for entries that are already unreachable (gc.reflogExpireUnreachable). Once an entry expires, a subsequent git gc is free to actually delete the now-truly-unreferenced object, and at that point the commit is gone for good — verifiably, since git fsck will find nothing.

Common Mistake

Treating "Git never loses committed work" as an absolute guarantee. The honest answer is: not for a generous default window (weeks), but eventually yes, if truly nothing references the commit. It isn't magic — it's an object store with conservative default deletion, not a store that never deletes at all.

Q54. What's a practical incident playbook for "I think I just lost work"?

ROI: ★★★★☆ Frequency: High

Short Answer

Stop first — running anything further destructive (another reset --hard, git clean -f, or a fresh re-clone over the same directory) can make things worse before you've even looked. Then work outward from the cheapest recovery: git reflog on the branch in question and on any related worktree or clone; if it's a deleted branch, check git reflog show <sha> against any SHA fragment still visible in a terminal scrollback or IDE history; broaden to git fsck --lost-found if reflog shows nothing; check whether a teammate or a CI runner still has a stale clone or fetch holding the old tip; and, as an absolute last resort for a pushed-then-overwritten commit, ask the Git host's support about ref retention.

Interview Gold Point

Always name the one case none of this recovers: working-directory changes that were never committed at all. That's the honest limit of Git's safety net, and pointing it out unprompted is exactly the kind of precision senior interviewers are listening for.

SECTION 14 - SCRUBBING SECRETS & LARGE FILES FROM HISTORY

Q55. Why doesn't deleting a secret in a new commit remove it from history?

ROI: ★★★★★ Frequency: Very High

Short Answer

A new commit that deletes the offending line only changes the latest tree — every earlier commit's tree still points at the old blob containing the secret, and that blob remains a perfectly reachable object as long as any ancestor commit's tree references it, which every one of them does. Anyone with a clone (and every clone carries the entire history) can run git log -p or git show <old-sha>:path and read the secret straight out of an old commit — no undelete required, no special tooling needed.

Common Mistake

Believing git rm --cached or a follow-up commit "removes" a leaked secret. The single correct first action is always to treat the credential as compromised and rotate it immediately — history-scrubbing (Q56) is clean-up, never the fix itself.

Q56. How do git filter-repo and BFG Repo-Cleaner rewrite history to remove a secret or large file?

ROI: ★★★★☆ Frequency: Medium-High

Short Answer

Both tools rewrite every commit that touches the target path or content, producing new trees — and therefore new commit hashes — for that commit and every descendant. It's fundamentally the same mechanism as a rebase, just applied across the entire history instead of a recent range. git filter-repo is the modern, officially recommended tool (the older git filter-branch is deprecated, slow, and easy to misuse); it can strip a path entirely or replace matching strings/blobs. BFG Repo-Cleaner is a simpler, much faster, purpose-built tool for the common cases — delete files by name or size, replace text matching a patterns file — without filter-repo's more general scripting surface.

# git filter-repo: strip a path from all of history
git filter-repo --path secrets.env --invert-paths

# BFG: replace any text matching entries in a patterns file
bfg --replace-text passwords.txt
Q57. What's the full checklist after rewriting history to scrub a secret?

ROI: ★★★★☆ Frequency: Medium-High

Short Answer

Rewriting local history changes nothing until it reaches the remote and every collaborator. Rotate the leaked credential first, always — the rewrite is cleanup, not the fix. Then force-push every rewritten branch and tag (a plain, coordinated --force, not --force-with-lease, since every hash has changed on purpose). Tell every collaborator to stop pushing and either hard-reset their local branches to the new history or, if unsure, delete their clone and re-clone fresh. Expire the old objects server-side too — via the platform's support (GitHub) or git gc --prune=now on a self-hosted server — since a stale server-side cache or an existing fork can still carry the old blob. Finally, check CI caches, build artifacts, and any downloaded release tarballs that might have baked in the old history.

Interview Gold Point

The step people forget: forks and long-lived local clones that never re-synced still hold the secret in full. A history rewrite scrubs your canonical remote; it does not reach outward and scrub every copy that already exists in the world — which is exactly why credential rotation, not history rewriting, is the real fix.

SECTION 15 - GIT IN CI/CD PIPELINES

Q58. Why do CI pipelines almost always use a shallow clone, and what trade-off does that bring?

ROI: ★★★☆☆ Frequency: Medium

Short Answer

CI jobs typically only need to build and test the current commit, so --depth 1 (or a platform default like GitHub Actions' actions/checkout with fetch-depth: 1) drastically cuts checkout time on every single run, which adds up fast across hundreds of daily builds. The trade-off: any step that genuinely needs history — a diff against the merge-base, git describe, changelog generation, or a git bisect job — needs a deeper or full fetch (fetch-depth: 0), so a pipeline that needs those steps explicitly opts out of the shallow default for that job.

Interview Gold Point

This chapter covers the Git mechanics of the checkout, not pipeline design — full stage/runner/deployment-gate mechanics for Jenkins, GitHub Actions, and GitLab CI belong to the dedicated CI/CD pipelines chapter.

Q59. What's the difference in checkout strategy between a PR build and a main-branch build?

ROI: ★★★☆☆ Frequency: Medium

Short Answer

A PR build typically checks out the merge preview of the PR branch into the target branch (e.g. GitHub's refs/pull/N/merge) so CI tests what will actually land once merged, not just the feature branch in isolation — catching integration issues a standalone-branch build would miss. A main-branch build simply checks out the tip of main after a merge has already happened, and is often followed by tagging and deployment steps a PR build never runs at all.

Common Mistake

Getting this distinction wrong is a common, concrete cause of "it passed in the PR but broke main" — usually because a job was configured to check out the PR's source branch alone instead of its merge result.

Q60. Where does Git's role end and CI/CD pipeline design begin?

ROI: ★★★☆☆ Frequency: Low-Medium

Short Answer

This chapter covers Git the tool: how history, checkout strategy, and refs affect what a pipeline can do. The actual pipeline mechanics — Jenkins pipeline syntax, GitHub Actions workflow YAML, GitLab CI's .gitlab-ci.yml, stages, runners, artifacts, and deployment gates — are covered in depth in the dedicated CI/CD pipelines chapter. If asked to design a full pipeline in an interview, treat the Git checkout as one early, well-understood step in that larger system, not the whole answer.

QUICK REVISION SHEET

  • Git is distributed — every clone has full history; commit (local) and push (publish) are separate steps
  • Three areas: working directory → staging/index (git add) → repository (git commit); HEAD = current commit
  • A commit is an immutable snapshot + parent pointer(s), identified by a content hash — not a diff
  • fetch = download only (safe); pull = fetch + merge/rebase (touches your branch)
  • A branch is a movable pointer (~41 bytes) — branching is instant and cheap
  • Merge preserves history (merge commit); rebase rewrites for a linear history — never rebase shared/public history
  • Fast-forward = no divergence (just move pointer); three-way merge = both diverged, uses common ancestor + merge commit
  • Conflicts: edit markers <<< === >>>, git add, then --continue; small PRs reduce conflict surface
  • reset rewrites history (--soft keep staged, --mixed unstage, --hard destroy) — local only; revert = safe undo for pushed commits
  • Interactive rebase (git rebase -i): pick/reword/squash/fixup/drop to clean up commits before sharing
  • Good commits: imperative subject + why in body; annotated tags for releases; SemVer MAJOR.MINOR.PATCH
  • Workflows: Git Flow (scheduled releases), GitHub Flow (continuous deploy), trunk-based (CI/CD + feature flags)
  • PRs: small, single-purpose, green CI, one approval; rebase + push --force-with-lease (never plain --force)
  • reflog recovers lost commits/branches (~30 days); restore unstages/discards; reset --soft uncommits
  • stash (shelve work), cherry-pick (one commit), .gitignore (never track), pre-commit hooks; never commit secrets — rotate + scrub; use Git LFS for binaries
  • Objects are content-addressable (blob/tree/commit/tag by SHA) — not diffs; packfiles + git gc keep loose objects compact; unreachable objects survive ~2 weeks by default
  • git bisect binary-searches for a regression's first bad commit (automate with bisect run); git blame/-S/-G/--follow do log forensics; git worktree runs branches in parallel; git rerere replays past conflict resolutions
  • Client-side hooks (pre-commit, commit-msg) are local and bypassable (--no-verify); server-side hooks / branch protection / required CI checks are the real enforcement; sign commits (GPG/SSH) for verified identity
  • .gitattributes normalizes line endings (text=auto) and marks binary/diff drivers; Git LFS swaps large binaries for pointer files so history stays small
  • Shallow clone truncates history depth; partial clone (--filter=blob:none) keeps full history but lazy-loads blobs; sparse-checkout limits the working directory; pick monorepo vs polyrepo based on cross-project change frequency, not dogma
  • Branch protection + CODEOWNERS + required status checks/merge queues enforce review and "tested together" guarantees at the platform level; merge commit vs squash vs rebase-merge trades topology detail for a clean mainline
  • Conventional Commits (feat/fix/BREAKING CHANGE) drive automated changelogs and SemVer bumps in CI with no manual versioning judgement calls
  • A leaked secret isn't gone until history is rewritten (git filter-repo / BFG) AND the credential is rotated; recover "lost" work beyond reflog with git fsck --lost-found before assuming it's gone for good
