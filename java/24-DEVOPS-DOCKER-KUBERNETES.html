SECTION 1 - DOCKER

Q1. What Is Docker and Why Use It?

ROI: ★★★★★ Frequency: Extremely High

Docker packages an application together with its dependencies, runtime and configuration into a single portable image that runs identically anywhere a container engine exists. It solves the classic "works on my machine" problem.

Unlike a virtual machine, a container shares the host OS kernel and isolates only the process — so it starts in milliseconds and uses a fraction of the memory. That lightweight isolation is what makes containers ideal for microservices.

Aspect Container Virtual Machine
Isolation Process-level, shared kernel Full OS per VM
Startup Milliseconds Seconds to minutes
Size MBs GBs

Interview Gold Point

The key distinction: VMs virtualise hardware; containers virtualise the operating system. Containers are not "lightweight VMs" — they are isolated processes, which is why density and speed are so much higher.

Q2. What Is the Difference Between an Image and a Container?

ROI: ★★★★★ Frequency: Very High

An image is a read-only template (the blueprint) built from a Dockerfile. A container is a running instance of an image — you can start many containers from one image, just as you create many objects from one class.

Interview Favorite

The class-vs-object analogy lands well: image = class, container = object. Images are immutable and versioned by tag; containers are ephemeral and should be treated as disposable (any state worth keeping goes in a volume or external store).

Q3. Walk Through a Dockerfile for a Spring Boot App

ROI: ★★★★★ Frequency: Very High

A Dockerfile is the recipe for building an image. Each instruction describes a step: 

FROM eclipse-temurin:21-jre        # base image (Java 21 runtime)
WORKDIR /app                       # working directory inside image
COPY target/app.jar app.jar        # copy the built jar in
EXPOSE 8080                        # document the port
ENTRYPOINT ["java","-jar","app.jar"]  # command run on start

Interview Gold Point

Know the difference between ENTRYPOINT and CMD: ENTRYPOINT sets the fixed executable, CMD provides default arguments that are easy to override at docker run. Also use a slim jre base, not the full jdk, for a smaller production image.

Q4. What Is a Multi-Stage Build and Why Use It?

ROI: ★★★★☆ Frequency: High

A multi-stage build uses one stage to compile the app (with the full JDK and build tools) and a second, clean stage that copies only the resulting artifact into a tiny runtime image. The heavy build tooling never ships to production. 

# Stage 1: build
FROM maven:3.9-eclipse-temurin-21 AS build
WORKDIR /src
COPY . .
RUN mvn -q clean package -DskipTests

# Stage 2: runtime (small)
FROM eclipse-temurin:21-jre
WORKDIR /app
COPY --from=build /src/target/app.jar app.jar
ENTRYPOINT ["java","-jar","app.jar"]

Interview Favorite

The payoff is a dramatically smaller, more secure final image — less attack surface, faster pulls, no compilers or source code shipped to production. This is a standard senior-level best practice.

Q5. How Do Docker Image Layers and Caching Work?

ROI: ★★★★☆ Frequency: Medium-High

Each Dockerfile instruction creates a cached layer. On rebuild, Docker reuses cached layers up to the first instruction that changed, then rebuilds everything after it. Ordering instructions from least- to most-frequently-changed maximises cache hits.

Interview Gold Point

The practical tip: copy your dependency descriptor (pom.xml) and download dependencies before copying source code. Then a code change reuses the cached dependency layer instead of re-downloading the world — much faster builds.

Q6. What Is docker-compose?

ROI: ★★★★☆ Frequency: Medium-High

docker-compose defines and runs multi-container applications from a single YAML file — for example your Spring Boot service plus a Postgres database and Redis — started together with one command (docker compose up).

Interview Favorite

Compose is ideal for local development and integration tests (it pairs naturally with Testcontainers). It is not a production orchestrator — for production scale and self-healing you move to Kubernetes.

SECTION 2 - KUBERNETES

Q7. What Is Kubernetes and What Problem Does It Solve?

ROI: ★★★★★ Frequency: Very High

Kubernetes (K8s) is a container orchestrator. Once you have many containers across many machines, you need something to schedule them, restart failed ones, scale them up and down, roll out new versions safely, and route traffic to them. K8s does all of this declaratively.

You describe the desired state ("I want 3 replicas of this image") and Kubernetes continuously works to make reality match — restarting crashed pods and rescheduling them if a node dies. This self-healing is its core value.

Interview Gold Point

The phrase to use is "declarative desired-state reconciliation". You do not tell K8s how to do things step by step; you declare the end state and its control loop converges toward it.

Q8. Explain Pod vs Deployment vs Service

ROI: ★★★★★ Frequency: Very High

Object Role
Pod Smallest unit — one or more containers sharing network/storage
Deployment Manages a set of identical pods: replicas, rollouts, self-healing
Service Stable network endpoint + load balancing across the pods

Pods are ephemeral and get new IPs when recreated, so you never talk to a pod directly. A Service gives a stable DNS name and load-balances across whichever pods are currently healthy.

Interview Favorite

A common follow-up: "why not just run a container directly?" — because a bare pod is not recreated if it dies. A Deployment guarantees the declared number of replicas and handles rolling updates and rollbacks.

Q9. Liveness vs Readiness Probes

ROI: ★★★★★ Frequency: High

Both are health checks, but they trigger different actions:

  • Liveness probe — "is the app alive?" If it fails, Kubernetes restarts the container (recovers from deadlocks/hangs).
  • Readiness probe — "is the app ready to serve traffic?" If it fails, K8s stops routing requests to that pod but does not restart it.

Interview Gold Point

Spring Boot Actuator exposes /actuator/health/liveness and /actuator/health/readiness out of the box — tie this straight back to the Actuator content in your Spring Boot chapter. Getting the two probes mixed up causes restart loops or traffic sent to a not-yet-ready app, so the distinction matters in production.

Q10. What Are ConfigMaps and Secrets?

ROI: ★★★★☆ Frequency: Medium-High

Both externalise configuration out of the image so the same image runs in every environment. A ConfigMap holds non-sensitive config (URLs, feature flags). A Secret holds sensitive data (passwords, API keys, tokens) and is handled more carefully.

Interview Favorite

Be honest about Secrets: by default they are only base64-encoded, not encrypted. Production setups enable encryption-at-rest and often integrate an external vault (e.g. HashiCorp Vault, AWS Secrets Manager). Saying this shows real-world awareness.

Q11. How Does a Rolling Update Work?

ROI: ★★★★☆ Frequency: Medium-High

A rolling update replaces old pods with new ones gradually — spinning up new-version pods, waiting for their readiness probes to pass, then terminating old pods a few at a time. The service stays available throughout, and if the new version is unhealthy you can roll back.

Interview Gold Point

This is why readiness probes matter: K8s only shifts traffic to a new pod once it reports ready, guaranteeing zero-downtime deploys. kubectl rollout undo reverts to the previous version if something goes wrong.

Q12. Rolling vs Blue-Green vs Canary Deployments

ROI: ★★★★☆ Frequency: Medium-High

Strategy How It Works
Rolling Gradually replace old pods with new ones
Blue-Green Run two full environments; switch traffic all at once
Canary Send a small % of traffic to the new version, then ramp up

Blue-green gives instant rollback (just switch back) at the cost of double the infrastructure. Canary limits blast radius by exposing the new version to a few users first and watching metrics before a full rollout.

Interview Favorite

Match the strategy to risk: canary for high-risk changes where you want real-traffic validation, blue-green when you need an instant, clean cutover, rolling as the sensible low-cost default.

SECTION 3 - CI/CD & BUILD

Q13. What Is CI/CD?

ROI: ★★★★★ Frequency: Very High

CI (Continuous Integration) means every code push is automatically built and tested, so integration problems surface within minutes instead of at a painful end-of-sprint merge. CD (Continuous Delivery/Deployment) automates releasing that validated build to environments — delivery stops at a manual approval, deployment goes all the way to production automatically.

Typical Pipeline Stages

Commit -> Build -> Unit Tests -> Package (Docker image)
       -> Integration Tests -> Push to Registry
       -> Deploy to Staging -> Deploy to Production

Interview Gold Point

Name tools you have touched — Jenkins, GitHub Actions, GitLab CI. The core value to articulate: fast feedback, repeatable releases, and smaller, safer changes shipped frequently rather than big risky batches.

Q14. What Is the 12-Factor App / Externalised Configuration?

ROI: ★★★★☆ Frequency: Medium-High

The 12-Factor App is a set of principles for building cloud-native services. The one interviewers probe most is config in the environment: never hard-code environment-specific values (DB URLs, credentials) in the build — inject them at runtime via environment variables or config services.

This is what lets the same immutable image run in dev, staging and production, differing only by injected config. Other key factors: stateless processes, treat backing services as attached resources, and disposability (fast startup/graceful shutdown).

Interview Gold Point

Connect to Spring: profiles and application.yml overridden by environment variables, or Spring Cloud Config for centralised config, are exactly this principle in practice. "Build once, deploy anywhere with injected config" is the phrase to land.

Q15. Maven vs Gradle

ROI: ★★★☆☆ Frequency: Medium

Aspect Maven Gradle
Config XML (pom.xml), declarative Groovy/Kotlin DSL, flexible
Speed Slower Faster (incremental + build cache)
Learning curve Simpler, rigid lifecycle Steeper, more powerful

Both manage dependencies and the build lifecycle. Maven's rigid, convention-driven lifecycle (validate → compile → test → package → install → deploy) is predictable; Gradle trades some predictability for speed and scripting flexibility.

Interview Favorite

Know dependency scopes (Maven) / configurations (Gradle): compile/implementation, provided/compileOnly, test, runtime. A frequent follow-up is how transitive dependency conflicts are resolved and how to exclude a transitive dependency.

SECTION 4 - DOCKER NETWORKING, STORAGE & SECURITY

Q16. What Are Docker's Networking Modes?

ROI: ★★★★☆ Frequency: High

By default, Docker creates a bridge network (backed by a virtual switch, historically docker0) and attaches every container to it with its own private IP. Containers on the same user-defined bridge network can resolve each other by container name through Docker's embedded DNS, and you publish a container's port to the host with -p hostPort:containerPort so outside traffic can reach it through NAT.

Host mode removes the network namespace boundary entirely — the container shares the host's network stack directly, so there is no NAT and no port mapping, but also no isolation between the container's ports and the host's. None mode gives the container only a loopback interface and no external connectivity at all, useful for security-sensitive batch jobs that should never reach the network. Overlay networks span multiple Docker hosts (used by Docker Swarm) so containers on different physical machines can talk over a virtual Layer 2 network — conceptually the same problem Kubernetes solves with a CNI plugin (Calico, Cilium, Flannel) instead of Docker's own overlay driver.

Mode Isolation Typical Use
bridge (default/user-defined) Private virtual network, NAT to host Normal single-host multi-container apps
host None — shares host network stack Performance-sensitive or legacy apps needing host ports directly
none Fully isolated, loopback only Security-sensitive jobs with no network need
overlay Virtual network across multiple hosts Multi-host clusters (Swarm); K8s uses a CNI plugin instead

Interview Gold Point

Prefer a user-defined bridge network over the legacy default bridge. The default bridge has no automatic DNS resolution between containers (you'd need the deprecated --link flag); a user-defined bridge gives every container automatic name-based DNS resolution, which is exactly what docker-compose sets up for you behind the scenes.

Q17. Volumes vs Bind Mounts vs tmpfs

ROI: ★★★★☆ Frequency: High

Mechanism Where Data Lives Best For
Volume Managed by Docker under /var/lib/docker/volumes Persistent production data (DB files), portable across containers
Bind Mount An exact host path, mounted directly Local development (live-reload source code into a container)
tmpfs Host RAM only, never written to disk Ephemeral sensitive data (short-lived secrets, scratch space)

A volume is Docker-managed storage that outlives the container's lifecycle and is decoupled from any specific host directory structure, which is what makes it portable and safe to back with cloud storage drivers (EBS, EFS, Azure Disk) in production. A bind mount maps an exact path on the host filesystem into the container — simple and great for local development, but it couples the container to the host's directory layout and can leak host filesystem access if misconfigured.

tmpfs mounts exist only in memory: nothing is ever written to disk, and the data disappears the moment the container stops. That makes it a good fit for holding decrypted secrets or credentials briefly during a process's lifetime without leaving a forensic trace on disk.

Common Mistake

Bind-mounting host paths into a production image is a common junior mistake — it breaks the "build once, run anywhere" promise of a container because the container now depends on that exact host having that exact path populated. In production, use named volumes (or a cloud-backed persistent volume in Kubernetes), and reserve bind mounts for local development only.

Q18. What Are Docker Security Best Practices?

ROI: ★★★★★ Frequency: Very High

Never run the main process as root inside the container. Add a dedicated user in the Dockerfile with USER so that even if an attacker breaks out of the application, they land as an unprivileged user, not root. Prefer minimal base images — alpine or, better, a distroless image that contains only the application and its runtime with no shell, no package manager, no extra binaries an attacker could use. Fewer packages means fewer CVEs and a smaller attack surface to scan and patch.

Run image scanning (Trivy, Snyk, Docker Scout) as a gate in the CI pipeline before an image is allowed to be pushed to the registry, so known-vulnerable base images or dependencies are caught automatically rather than discovered in production. Never bake secrets into image layers — even if a later layer deletes a credentials file, the file still exists in the earlier, cached layer and can be extracted with docker history or by inspecting the layer's tarball. Secrets belong in a runtime secret store (Kubernetes Secrets, Vault, a cloud secrets manager) or, at build time, behind BuildKit's --mount=type=secret, which never persists the secret into a layer at all. 

FROM eclipse-temurin:21-jre-alpine
RUN addgroup -S app && adduser -S app -G app
WORKDIR /app
COPY --chown=app:app target/app.jar app.jar
USER app
ENTRYPOINT ["java","-jar","app.jar"]

Interview Gold Point

The classic gotcha to name: RUN echo secret > /tmp/key && ... && rm /tmp/key across a single RUN line still leaves the secret in that layer's diff if it was ever written by an earlier instruction in a different layer. Layers are additive and immutable — deleting a file in a later layer only hides it in the final filesystem view, it does not remove it from the image's history. This is exactly why BuildKit secret mounts and multi-stage builds exist.

Q19. How Do Container Resource Limits Work, and What Causes OOMKilled?

ROI: ★★★★☆ Frequency: High

Docker enforces resource limits using Linux cgroups. docker run --memory=512m --cpus=1 caps a container to 512 MB of RAM and one CPU core; the kernel accounts every process inside the container's cgroup against that ceiling. CPU limits are enforced by throttling (the container gets scheduled less often once it exceeds its quota), while memory is a hard boundary — there is no "throttling" equivalent for memory.

When a container tries to allocate more memory than its cgroup limit allows, the kernel's OOM killer steps in and kills the offending process, which Docker reports as exit code 137 (128 + SIGKILL's signal number 9). This is different from an application-level OutOfMemoryError: a JVM OOM is the JVM itself running out of heap and often produces a heap dump and stack trace; a container OOMKilled is the kernel forcibly terminating the whole process because the container's total memory footprint (heap + off-heap + metaspace + thread stacks) exceeded the cgroup limit, and there is no graceful log message — the process simply disappears.

Interview Gold Point

For a JVM specifically, always set -XX:MaxRAMPercentage (or an explicit -Xmx) comfortably below the container's memory limit. The JVM's heap is only part of its footprint — metaspace, thread stacks and native buffers also count against the cgroup limit, so a heap sized right up to the container limit will still get OOMKilled from non-heap memory pressure.

Q20. HEALTHCHECK in a Dockerfile vs Kubernetes Probes

ROI: ★★★☆☆ Frequency: Medium

Docker's HEALTHCHECK instruction runs a command on an interval and marks the container's status as healthy or unhealthy in docker ps. On its own, plain Docker does not restart an unhealthy container — it is purely informational unless something external (Swarm, a monitoring script) reacts to that status.

Kubernetes ignores the Dockerfile's HEALTHCHECK instruction completely. It has its own, richer probe model configured directly in the pod spec — liveness, readiness, and startup probes — each with its own action (restart the container, stop routing traffic, or delay the other two probes until a slow-starting app is ready). So when you move a workload from docker-compose to Kubernetes, the Dockerfile's HEALTHCHECK becomes redundant and is superseded by probe definitions in the Deployment YAML. 

HEALTHCHECK --interval=30s --timeout=3s --retries=3 \
  CMD curl -f http://localhost:8080/actuator/health || exit 1

SECTION 5 - KUBERNETES WORKLOAD CONTROLLERS

Q21. What Is a ReplicaSet, and How Does a Deployment Use It?

ROI: ★★★★☆ Frequency: High

A Deployment never manages Pods directly. It manages one or more ReplicaSets, and it is the ReplicaSet that watches a label selector and ensures the declared number of matching Pods exist. When you change a Deployment's pod template — most commonly a new image tag — Kubernetes does not edit pods in place; it creates a brand-new ReplicaSet with the updated template and then orchestrates shifting replica counts between the old ReplicaSet and the new one.

kubectl get rs after a few rollouts shows a history of ReplicaSets for one Deployment: the current one scaled to the full replica count, and previous ones scaled to zero but kept around (up to revisionHistoryLimit) so kubectl rollout undo has something to scale back up to.

Interview Gold Point

This is why a rollback in Kubernetes is fast: it is not a redeploy from scratch, it is scaling the previous ReplicaSet back up (its Pod template and image are already known) while scaling the current one down — the same mechanism as a forward rollout, just pointed backwards.

Q22. How Does a Rolling Update Actually Orchestrate Old vs New ReplicaSets?

ROI: ★★★★★ Frequency: High

The pace of a rolling update is governed by two fields on the Deployment's rolling update strategy: maxSurge (how many extra pods beyond the desired count are allowed to exist at once) and maxUnavailable (how many pods below the desired count are tolerated at once). The controller uses these two numbers as a budget: it scales the new ReplicaSet up by maxSurge, waits for those new pods' readiness probes to pass, then scales the old ReplicaSet down by up to maxUnavailable, and repeats until the new ReplicaSet reaches the full desired count and the old one reaches zero. 

spec:
  replicas: 6
  strategy:
    type: RollingUpdate
    rollingUpdate:
      maxSurge: 25%
      maxUnavailable: 25%

Interview Gold Point

If a new pod's readiness probe never passes, the rollout stalls at whatever point it reached — it does not automatically roll back. That is precisely why deployment automation (or a human) must watch kubectl rollout status and issue kubectl rollout undo on a stuck or unhealthy rollout; Kubernetes' default rolling update guarantees availability during the process, not correctness of the new version.

Q23. StatefulSets vs Deployments

ROI: ★★★★★ Frequency: High

A Deployment's pods are interchangeable and stateless from Kubernetes' point of view — any pod can be killed and replaced by an identical one with a new name and a new IP, and nothing about ordering matters. A StatefulSet is for workloads where identity matters: each replica gets a stable, predictable name (db-0, db-1, db-2, ...), a stable DNS entry, and its own dedicated persistent volume created from a volumeClaimTemplate that follows that specific pod across rescheduling.

StatefulSets also default to ordered, one-at-a-time creation, scaling and termination (pod 0 must be Running and Ready before pod 1 is created), because many stateful systems (databases, Kafka, ZooKeeper, Elasticsearch) need that ordering for cluster formation or leader election. This is the controller you reach for whenever a workload cannot simply be recreated from scratch on any node with a fresh empty disk.

Interview Favorite

A quick way to answer "when would you use a StatefulSet?": whenever losing or shuffling a pod's identity or its attached disk would break the application. A stateless Spring Boot service behind a Service is a Deployment; a self-hosted Postgres or Kafka broker is a StatefulSet.

Q24. What Is a DaemonSet For?

ROI: ★★★☆☆ Frequency: Medium

A DaemonSet ensures exactly one copy of a pod runs on every node (or every node matching a selector) in the cluster, and automatically schedules a new copy onto any node that joins later. This is the controller behind cluster-wide infrastructure concerns rather than application workloads: a log-shipping agent (Fluentd/Fluent Bit) that must read every node's container logs, a node-level metrics exporter (Prometheus node-exporter), or a CNI/network plugin that must be present on every node for pod networking to work at all.

Interview Gold Point

The distinguishing question versus a Deployment: "does this need to run on every node, once, regardless of how many nodes there are?" If yes, it's a DaemonSet, because a Deployment's replica count is a fixed number unrelated to the node count.

Q25. Jobs and CronJobs in Kubernetes

ROI: ★★★☆☆ Frequency: Medium

A Job runs one or more pods to completion rather than keeping them running forever — it is for a batch task (a data migration, a report generation, a one-off script) that should be retried up to backoffLimit times on failure and considered done once the required number of pods succeed. A CronJob wraps a Job template with a cron schedule, creating a new Job at each scheduled tick, and is the Kubernetes-native replacement for a crontab entry that used to live on a single server.

Interview Favorite

Contrast with a Deployment: a Deployment's pods are expected to run forever and be restarted if they exit; a Job's pods are expected to exit, and that exit (with a success code) is the signal that the work is done.

SECTION 6 - KUBERNETES SERVICES & SERVICE DISCOVERY

Q26. ClusterIP vs NodePort vs LoadBalancer

ROI: ★★★★★ Frequency: Very High

Service Type Reachable From Typical Use
ClusterIP (default) Only inside the cluster Internal service-to-service traffic
NodePort Any node's IP on a fixed high port Quick external access, dev/test, on-prem without a cloud LB
LoadBalancer An external IP provisioned by the cloud provider Production external entry point (usually fronted by an Ingress)

Every Service type builds on the one before it: a LoadBalancer Service provisions a cloud load balancer that forwards to a NodePort, which in turn forwards to a ClusterIP, which load-balances across the matching pods. Most internal microservice-to-microservice traffic only ever needs ClusterIP; NodePort is rarely used directly in production because it ties you to a fixed port range and requires clients to know node IPs; LoadBalancer is the standard way to expose a small number of edge entry points, but provisioning one per service gets expensive and unwieldy, which is exactly the gap an Ingress fills.

Q27. How Does DNS-Based Service Discovery Work Inside a Cluster?

ROI: ★★★★☆ Frequency: High

Kubernetes runs a cluster-internal DNS server, CoreDNS, and every Service automatically gets a DNS record of the form <service-name>.<namespace>.svc.cluster.local. A pod in the same namespace can reach another service with just its short name (order-service); a pod in a different namespace needs the namespace-qualified name (order-service.orders). Resolving that name returns the Service's stable ClusterIP, which the kube-proxy data path then load-balances across whichever pods currently pass their readiness probes.

Interview Gold Point

This is a deliberate architectural difference from a Spring Cloud/Netflix Eureka-style client-side service registry: Kubernetes gives you service discovery "for free" via DNS and a stable virtual IP, so a microservice moving from a Eureka-based stack to Kubernetes can usually delete its client-side discovery library entirely and just call the plain DNS name.

Q28. What Is a Headless Service, and Why Does a StatefulSet Need One?

ROI: ★★★☆☆ Frequency: Medium

A headless Service (clusterIP: None) skips load-balancing entirely: instead of returning one virtual IP, a DNS lookup on it returns the individual IPs of every matching pod, and when paired with a StatefulSet it also creates a stable per-pod DNS record (db-0.db.default.svc.cluster.local, db-1.db.default.svc.cluster.local, ...).

This matters because stateful clustered systems (Kafka brokers, Elasticsearch nodes, a Postgres primary/replica set) need to address a specific peer, not "any healthy instance" — a Kafka broker forming a cluster needs to reach broker-1 specifically to replicate a partition, not whichever broker a load-balanced ClusterIP happens to route to.

SECTION 7 - INGRESS & EDGE ROUTING

Q29. What Does an Ingress Add Over a Plain Service?

ROI: ★★★★☆ Frequency: High

An Ingress is a single, declarative set of HTTP(S) routing rules — host-based (api.example.com vs admin.example.com) and path-based (/orders vs /payments) — that fan traffic out to many different backend Services through one entry point, instead of provisioning a separate cloud LoadBalancer per service. It typically also handles TLS termination in one place.

Crucially, the Ingress resource is just declarative configuration — it does nothing on its own. You need an Ingress Controller (nginx-ingress, Traefik, or a cloud-managed one) actually running in the cluster to watch Ingress objects and program a real reverse proxy or load balancer to match. Creating an Ingress resource with no controller installed simply does nothing. 

apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: api-ingress
spec:
  rules:
  - host: api.example.com
    http:
      paths:
      - path: /orders
        pathType: Prefix
        backend:
          service:
            name: order-service
            port:
              number: 8080

Interview Gold Point

Newer clusters are increasingly moving to the Gateway API, a more expressive, role-oriented successor to Ingress (separate GatewayClass/Gateway/HTTPRoute objects, native support for weighted traffic splitting and richer header-based matching). Mentioning that Ingress is the older, simpler standard and Gateway API is where the ecosystem is heading is a strong signal of staying current.

SECTION 8 - SCHEDULING, RESOURCES & QOS

Q30. Resource Requests vs Limits

ROI: ★★★★★ Frequency: Very High

A request is what the scheduler guarantees a container will get and uses to decide which node has room for the pod — it is a reservation, not a cap. A limit is the hard ceiling the container is not allowed to exceed. Requests drive scheduling decisions; limits drive runtime enforcement (CPU throttling, or an OOM kill for memory). 

resources:
  requests:
    cpu: "250m"
    memory: "256Mi"
  limits:
    cpu: "500m"
    memory: "512Mi"

Interview Gold Point

Setting no requests at all is a common production mistake: the scheduler then has no idea how much room the pod actually needs, can over-pack a node, and that pod becomes the first candidate for eviction under node memory pressure since it has no guaranteed share.

Q31. What Are Kubernetes QoS Classes?

ROI: ★★★★☆ Frequency: High

QoS Class Condition Eviction Priority
Guaranteed Every container sets requests == limits for CPU and memory Evicted last
Burstable At least one request is set, but requests != limits Evicted after BestEffort, before Guaranteed
BestEffort No requests or limits set at all Evicted first

Kubernetes derives a pod's Quality of Service class automatically from how its requests and limits are set — there is no separate field to set it directly. Under node memory pressure, the kubelet evicts pods in QoS order (BestEffort first, then Burstable, then Guaranteed), so a pod's QoS class is effectively a production reliability decision, not just a resource-sizing one.

Interview Favorite

For anything that must not be evicted — a database, a payment service — set requests equal to limits to get Guaranteed QoS. Reserve BestEffort for genuinely disposable batch work you are happy to lose under pressure.

Q32. How Do the Scheduler and Node Pressure Eviction Use Requests and Limits?

ROI: ★★★★☆ Frequency: High

When placing a new pod, the scheduler only looks at requests: it filters out any node whose already-allocated requests plus the new pod's requests would exceed that node's allocatable capacity, then scores the remaining candidates (spreading load, respecting affinity/taints, etc.) and picks one. Limits play no part in the scheduling decision at all — a node can happily schedule pods whose limits, summed, exceed its capacity, because limits are only enforced if containers actually try to use that much at the same time.

Once pods are running, the kubelet on each node continuously monitors real resource pressure. If the node's actual free memory drops below an eviction threshold, the kubelet reclaims resources by evicting pods, choosing victims by QoS class first and then by how far a pod's actual usage exceeds its requests within that class.

Q33. How Does the Horizontal Pod Autoscaler (HPA) Work?

ROI: ★★★★★ Frequency: Very High

The HPA is a control loop, run by the controller manager, that periodically (every 15 seconds by default) reads current metrics — typically CPU or memory utilization from the metrics-server, but it can also read custom or external metrics (queue depth, requests-per-second via a metrics adapter) — and compares them to a target value on the HPA object. It then computes a desired replica count and updates the target Deployment's replicas field directly. 

apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: order-service-hpa
spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: order-service
  minReplicas: 2
  maxReplicas: 10
  metrics:
  - type: Resource
    resource:
      name: cpu
      target:
        type: Utilization
        averageUtilization: 70

Interview Gold Point

Because the HPA needs requests set to compute utilization percentages (70% of what CPU request, exactly?), an HPA on a pod with no CPU request configured simply cannot function. Also mention the stabilization window: Kubernetes deliberately dampens scale-down decisions to avoid flapping replicas up and down on noisy, short-lived traffic spikes.

SECTION 9 - AUTOSCALING, NAMESPACES & RBAC

Q34. Vertical Pod Autoscaler (VPA) vs HPA

ROI: ★★★☆☆ Frequency: Medium

Where the HPA scales out by changing the replica count, the Vertical Pod Autoscaler scales up by adjusting a pod's own CPU/memory requests and limits based on observed historical usage — useful for right-sizing a workload whose per-instance resource need is hard to guess up front, such as a batch job or a single-instance stateful service that cannot simply be replicated.

The two do not compose cleanly on the same metric: because changing a container's resource requests currently requires recreating the pod (in-place resize is only newly and partially available), a VPA acting in "Auto" mode causes pod restarts, and running both an HPA and a VPA targeting CPU on the same Deployment can fight each other. The common pattern is HPA on CPU/custom metrics for horizontal scale, VPA in "recommendation-only" mode to guide what requests/limits to hand-tune.

Q35. What Are Namespaces For?

ROI: ★★★★☆ Frequency: High

A Namespace is a logical partition inside one cluster — a way to divide resources (by team, environment, or application) so that names don't collide (order-service can exist once in staging and once in production) and so that policies like ResourceQuotas (cap total CPU/memory a namespace's pods may consume) and RBAC rules can be scoped per namespace.

Common Mistake

A namespace is not a network or security boundary by itself — by default, any pod in any namespace can reach any pod in any other namespace over the network. Real isolation requires NetworkPolicies on top of namespaces, not namespaces alone.

Q36. Kubernetes RBAC Basics

ROI: ★★★★☆ Frequency: High

RBAC controls who (or what) can call the Kubernetes API, and what they're allowed to do. A Role (namespace-scoped) or ClusterRole (cluster-wide) defines a set of permitted verbs (get, list, watch, create, update, delete) on specific resource types. A RoleBinding or ClusterRoleBinding then grants that role to a subject — a user, a group, or a ServiceAccount.

The ServiceAccount case matters most day to day: every pod runs as some ServiceAccount (the default one if none is specified), and if your application code calls the Kubernetes API from inside a pod (to read a ConfigMap, watch other pods, etc.) it authenticates as that ServiceAccount. Least-privilege practice is to give each workload its own narrowly-scoped ServiceAccount rather than relying on the namespace's default.

Q37. What Do NetworkPolicies Do?

ROI: ★★★★☆ Frequency: High

By default, Kubernetes networking is flat and fully open — any pod can reach any other pod's IP on any port, across namespaces. A NetworkPolicy is a declarative firewall rule, scoped by pod label selectors (and optionally namespace selectors), that restricts ingress and/or egress traffic to matching pods. Enforcement requires a CNI plugin that actually implements NetworkPolicy (Calico, Cilium) — some simpler CNIs silently ignore the objects. 

apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: allow-orders-from-gateway-only
spec:
  podSelector:
    matchLabels:
      app: order-service
  policyTypes: ["Ingress"]
  ingress:
  - from:
    - podSelector:
        matchLabels:
          app: api-gateway
    ports:
    - port: 8080

Interview Gold Point

Once a pod is selected by any NetworkPolicy for a direction (ingress or egress), that direction becomes default-deny for that pod except for what the policy explicitly allows. Forgetting this causes a common outage: adding one narrow policy can silently cut off traffic you never intended to restrict, unless you also add the other rules that traffic depends on.

Q38. How Do RBAC and NetworkPolicies Combine for Defense in Depth?

ROI: ★★★★☆ Frequency: Senior Favorite

RBAC and NetworkPolicies protect two different layers, and a senior candidate should keep them clearly separated. RBAC governs the control plane: who or what is allowed to call the Kubernetes API to create, read or modify cluster objects. NetworkPolicies govern the data plane: which pods are allowed to send network packets to which other pods. A workload can be perfectly locked down on one axis and wide open on the other — a pod with a minimal ServiceAccount and no API permissions can still accept unrestricted network traffic from every other pod in the cluster if no NetworkPolicy scopes it.

A defense-in-depth setup layers both: namespaces to segment by team/environment, ResourceQuotas to bound blast radius, RBAC so workloads and humans only hold the API permissions they actually need, NetworkPolicies so a compromised pod cannot freely reach unrelated services, and Secrets encryption at rest so a leaked etcd snapshot doesn't hand over plaintext credentials. Naming this layered picture, rather than a single control, is what distinguishes a senior answer here.

SECTION 10 - INIT CONTAINERS, SIDECARS & POD LIFECYCLE

Q39. What Are Init Containers, and When Do You Use Them?

ROI: ★★★★☆ Frequency: High

An init container runs to completion before any of a pod's main containers start, and multiple init containers run sequentially, each one waiting for the previous to succeed. They're the standard place for one-time setup a main container shouldn't have to do itself: waiting for a dependency to become reachable, running a database schema migration, downloading a config bundle or seed dataset into a shared volume the main container will read from. 

initContainers:
- name: wait-for-db
  image: busybox:1.36
  command: ['sh','-c','until nc -z postgres 5432; do sleep 2; done']
containers:
- name: app
  image: order-service:1.4.0

Interview Gold Point

If an init container fails, Kubernetes restarts it (per the pod's restart policy) and the main containers never start at all — this is a common cause of a pod that looks "stuck" with 0/1 ready and never even shows the main container in logs, because the main container has literally not been created yet.

Q40. Sidecar Containers and Their Lifecycle Relative to the Main Container

ROI: ★★★★☆ Frequency: High

A sidecar is a helper container that runs alongside the main application container for the whole lifetime of the pod — a service-mesh proxy (Envoy in Istio/Linkerd) that transparently handles mTLS and traffic routing, a log-forwarder tailing the app's log files, or a config-reloader watching a mounted ConfigMap for changes. Sidecars share the pod's network namespace and can share volumes with the main container, which is exactly how a mesh proxy intercepts all inbound/outbound traffic without the application code knowing it exists.

Historically, sidecars were just ordinary containers in the pod's containers list, which caused an awkward startup/shutdown ordering problem (nothing guaranteed the proxy sidecar was ready before the app's first request, or that it stayed alive until the app finished shutting down). Newer Kubernetes versions support native sidecars — an init container with restartPolicy: Always — which starts before the main container, is kept running for the pod's whole life, and is guaranteed to terminate only after the main container exits.

Q41. What Are the Pod Lifecycle Phases and Container Restart Policies?

ROI: ★★★☆☆ Frequency: Medium-High

Phase Meaning
Pending Accepted by the API server, not yet fully scheduled/running (image pulling, waiting for resources)
Running Bound to a node, at least one container running
Succeeded All containers terminated successfully (typical for Jobs)
Failed All containers terminated, at least one with failure
Unknown Node unreachable, pod state cannot be determined

Independent of the pod-level phase, each container has its own restartPolicy: Always (the default, used by Deployments — the kubelet restarts the container no matter how it exits), OnFailure (restart only on a non-zero exit code — the usual choice for Jobs), or Never. Restart policy is set once per pod and applies to all its containers.

Q42. How Does Graceful Shutdown Work in Kubernetes?

ROI: ★★★★☆ Frequency: High

When a pod is deleted (or a rolling update replaces it), Kubernetes first removes it from the Service's endpoint list (so no new traffic is routed to it), then sends SIGTERM to the container and runs any configured preStop hook. The application has terminationGracePeriodSeconds (30 seconds by default) to finish in-flight requests and shut down cleanly; if it hasn't exited by then, Kubernetes sends SIGKILL, which terminates it immediately with no further chance to clean up. 

lifecycle:
  preStop:
    exec:
      command: ["sh","-c","sleep 5"]
terminationGracePeriodSeconds: 30

Interview Gold Point

The preStop sleep is a well-known production trick: removing a pod from a Service's endpoints and the kubelet actually stopping routing to it are not perfectly instantaneous across the whole cluster (kube-proxy rule updates take a moment to propagate), so a short sleep in preStop before the app starts refusing connections avoids a small window of dropped requests during every rollout.

Q43. Common Multi-Container Pod Design Patterns

ROI: ★★★☆☆ Frequency: Medium

Pattern Purpose
Sidecar Extends/enhances the main container (log shipper, mesh proxy)
Ambassador Proxies outbound connections for the main container (e.g. simplifies talking to a sharded backend)
Adapter Normalizes the main container's output into a standard format (e.g. reshaping logs/metrics for a monitoring tool)

All three patterns share the same underlying mechanism — multiple containers in one pod sharing network and (optionally) storage — and differ only in intent: a sidecar adds a capability the main container doesn't have, an ambassador simplifies the main container's view of the outside world, and an adapter simplifies the outside world's view of the main container. Naming these three by name is a strong signal of hands-on Kubernetes design experience beyond just YAML syntax.

SECTION 11 - HELM & KUBERNETES PACKAGING

Q44. What Problem Does Helm Solve?

ROI: ★★★★☆ Frequency: High

Once an application's Kubernetes footprint grows past one Deployment and one Service, you end up with a pile of YAML files that differ only slightly between dev, staging and production — a different replica count, a different image tag, a different resource limit. Helm is a package manager for Kubernetes: it templates that YAML with variables (a chart) and lets you supply a small, environment-specific values.yaml to fill in the differences, then tracks each install/upgrade as a versioned release you can roll back as one atomic unit.

Interview Gold Point

The value isn't just templating — plenty of tools template YAML. It's that Helm tracks release history: every helm upgrade is a new revision, and helm rollback reverts the entire set of resources associated with a release to a prior revision in one command, the same way kubectl rollout undo does for a single Deployment but scoped to an entire application's worth of objects.

Q45. What Does a Helm Chart Look Like?

ROI: ★★★☆☆ Frequency: Medium-High

A chart is a directory with a fixed structure: Chart.yaml holds chart metadata (name, version); values.yaml holds the default configuration values; templates/ holds the actual Kubernetes manifest templates, written in Go template syntax, referencing values as {{ .Values.replicaCount }}; and an optional charts/ subdirectory holds dependency sub-charts. 

mychart/
  Chart.yaml
  values.yaml
  templates/
    deployment.yaml
    service.yaml
    _helpers.tpl
Q46. Helm vs Kustomize

ROI: ★★★☆☆ Frequency: Medium

Aspect Helm Kustomize
Approach Template with variables + values file Patch a base manifest per overlay (no templating language)
Release tracking Yes — versioned releases, built-in rollback No — it just renders final YAML, you apply it yourself
Best fit Distributing a reusable package (e.g. installing Prometheus) Managing your own app's per-environment overlays without a templating language

The two solve overlapping problems differently. Helm's templating is powerful but can turn into hard-to-read logic sprawled across .tpl files when overused. Kustomize takes a plain base manifest and applies structural patches per environment, keeping every file valid YAML with no template syntax, but has no concept of a tracked release or a one-command rollback of its own — it's purely a rendering step before kubectl apply.

Q47. Helm Release Lifecycle: Install, Upgrade, Rollback

ROI: ★★★☆☆ Frequency: Medium-High

helm install renders the chart's templates with the supplied values and applies the resulting manifests, recording revision 1 of a named release. helm upgrade re-renders with new values or a new chart version and applies the diff, recording the next revision. helm rollback <release> <revision> re-applies a previously recorded revision's rendered manifests, giving you an application-wide undo that spans every object the chart created, not just one Deployment.

Q48. Common Helm Anti-Patterns

ROI: ★★★☆☆ Frequency: Medium

The most common production mistake is putting real secrets in plaintext inside values.yaml and committing that file to source control — values files are just YAML, with no encryption, so secret material belongs in a Secret populated at deploy time (or via a tool like Sealed Secrets/SOPS), never directly in chart values. A second common issue is not pinning a dependency chart's version, so a re-install months later silently pulls a newer, breaking version of a sub-chart. A third is pushing so much conditional logic into .tpl helper templates that the chart becomes harder to reason about than the raw YAML it replaced — templating should reduce duplication, not hide complexity.

SECTION 12 - DEBUGGING KUBERNETES WORKLOADS

Q49. Walk Through Diagnosing a Pod Stuck in CrashLoopBackOff

ROI: ★★★★★ Frequency: Very High

CrashLoopBackOff means the container starts, exits, and Kubernetes is repeatedly restarting it with an exponentially increasing backoff delay between attempts. The diagnostic path is always the same sequence: first, kubectl describe pod <pod> to see the last exit code and the "Last State" / "Reason" fields (a 137 points to OOMKilled, a non-zero application exit code points to an application-level crash). Second, kubectl logs <pod> --previous to see the log output from the crashed instance, since a plain kubectl logs only shows the current (freshly restarted, possibly not-yet-crashed) instance.

Common root causes: a missing or misconfigured environment variable/ConfigMap the app fails to start without, a dependency (database, downstream service) that isn't reachable and the app fails fast rather than retrying, or a memory limit set too low for the app's actual footprint (visible as repeated OOMKilled in the "Last State" reason).

Q50. Walk Through Diagnosing a Pod Stuck in Pending

ROI: ★★★★☆ Frequency: High

Pending means the pod has been accepted by the API server but the scheduler has not yet been able to bind it to a node. kubectl describe pod again is the first step — its Events section directly states the scheduler's reason, most commonly "Insufficient cpu/memory" (no node has enough allocatable capacity left for this pod's requests), a node selector or affinity rule that no available node satisfies, or a taint on every candidate node that the pod lacks a matching toleration for.

The fix follows directly from the reason: scale the node pool or lower requests for insufficient capacity, correct a typo'd node selector/affinity label, or add the missing toleration. A pod can also sit Pending because its PersistentVolumeClaim cannot be bound (no matching PersistentVolume or storage class available) — worth checking kubectl get pvc alongside the pod events.

Q51. What Causes ImagePullBackOff?

ROI: ★★★☆☆ Frequency: Medium-High

ImagePullBackOff means the kubelet tried to pull the container image and failed, then backed off before retrying. The usual causes are a typo'd image name or tag, an image that was never actually pushed to the registry (a broken CI pipeline that reports success without pushing), a private registry requiring an imagePullSecret that is missing or misconfigured on the pod/ServiceAccount, or a registry rate limit being hit. kubectl describe pod shows the exact pull error message, which almost always names the specific problem directly (401 Unauthorized, manifest not found, etc.).

Q52. What's In Your kubectl Diagnostic Toolkit?

ROI: ★★★★☆ Frequency: High

Command What It Tells You
kubectl describe pod Events, last exit reason, scheduling failures, volume/probe config
kubectl logs --previous Logs from the last crashed instance, not the current one
kubectl get events --sort-by=.lastTimestamp Cluster-wide timeline of what happened, in order
kubectl exec -it <pod> -- sh A shell inside the running container, for live inspection
kubectl top pod / kubectl top node Live CPU/memory usage vs requests and limits
kubectl port-forward Reach a pod's port directly from your machine, bypassing the Service

These commands answer different layers of "why is this broken": describe and get events tell you what the control plane observed happening to the object; logs and exec let you inspect the application from the inside; top tells you whether the problem is resource pressure; port-forward lets you rule out the Service/Ingress layer by talking to the pod directly.

Q53. OOMKilled at the Kubernetes Level vs the Docker Level

ROI: ★★★☆☆ Frequency: Medium-High

The underlying mechanism is the same cgroup-enforced kernel OOM kill described for plain Docker, but Kubernetes surfaces it differently and adds a second, node-wide layer on top. At the container level, if a container exceeds its own resources.limits.memory, the kernel kills that one container's process, and kubectl describe pod shows "Last State: Terminated, Reason: OOMKilled, Exit Code: 137" for that specific container — the kubelet then restarts it per the restart policy.

At the node level, if overall node memory runs low regardless of any single container's limit (for example many BestEffort pods together over-consuming), the kubelet's node-pressure eviction can terminate entire pods before the kernel OOM killer even fires, choosing victims by QoS class as covered earlier. Distinguishing "this one container hit its own limit" from "the whole node was under memory pressure and this pod got evicted" is exactly the kind of nuance that separates a surface-level answer from a senior one.

SECTION 13 - PRODUCTION INCIDENTS & ROLLOUT SAFETY

Q54. Case Study: A Rollout That Passed Readiness Probes but Was Actually Broken

ROI: ★★★★★ Frequency: Senior Favorite

A common real incident: a new version is rolled out, every new pod reports Ready within seconds, the rollout completes with no errors — and minutes later the service is failing every request. The root cause is almost always that the readiness probe was checking the wrong thing. If /actuator/health/readiness (or a hand-rolled equivalent) just returns 200 as long as the HTTP listener is up, it will happily report Ready even if the new version can't actually reach its database, has a broken configuration, or throws an exception on every real request — the probe was shallow, so Kubernetes shifted 100% of production traffic onto a pod that looked healthy and wasn't.

The fix is two-fold. First, make readiness genuinely reflect the app's ability to serve traffic — check the things that would actually make a request fail (DB connectivity, critical downstream dependencies), while still keeping the check fast and avoiding a readiness probe that itself makes expensive calls able to cascade load onto a struggling dependency. Second, don't rely on probes alone for rollout safety at scale: pair the rolling update with a canary step and automated rollout analysis (Argo Rollouts, Flagger) that watches real error-rate and latency metrics for a few minutes before shifting all traffic, so a probe blind spot doesn't take down 100% of capacity at once.

Q55. How Do You Design Probes That Actually Catch Failure?

ROI: ★★★★★ Frequency: High

Keep the three probe types deliberately different in scope. The liveness probe should be extremely cheap and check only "is this process fundamentally alive and not deadlocked" — it should never call downstream dependencies, because a slow or failing dependency would then cause Kubernetes to restart a perfectly healthy process, potentially cascading a downstream outage into a restart storm of everything upstream. The readiness probe should check "am I, right now, in a state where I can correctly serve traffic," which can reasonably include a fast check of a critical dependency (a DB connection pool has at least one live connection), but with strict timeouts. The startup probe exists to give slow-starting applications (a JVM warming up a large cache) room to initialize without the liveness probe prematurely killing them before they've had a fair chance to become ready.

Interview Gold Point

A precise way to phrase the distinction: liveness answers "should this be restarted?", readiness answers "should this receive traffic right now?", and conflating the two — making liveness depend on external services — is one of the most common production probe-design mistakes.

Q56. What Is a PodDisruptionBudget For?

ROI: ★★★★☆ Frequency: Medium-High

A PodDisruptionBudget (PDB) protects against voluntary disruptions — a node drain for a cluster upgrade, a cluster-autoscaler removing an under-used node, someone running kubectl drain — as opposed to involuntary ones like a node crashing outright. It declares minAvailable or maxUnavailable for a set of pods, and the eviction API refuses any voluntary eviction that would push the group below that floor. 

apiVersion: policy/v1
kind: PodDisruptionBudget
metadata:
  name: order-service-pdb
spec:
  minAvailable: 2
  selector:
    matchLabels:
      app: order-service

Interview Gold Point

Without a PDB, a routine node drain during a cluster upgrade can legally evict every replica of a service that happens to be co-located on that node at once, causing an outage that has nothing to do with a bad deploy at all. A PDB is what makes cluster maintenance operations safe to run without manually checking where every workload's replicas currently sit.

Q57. What's a Solid Rollback and Monitoring Strategy During a Rollout?

ROI: ★★★★☆ Frequency: High

The baseline is kubectl rollout status to watch a rollout progress and kubectl rollout undo as the manual escape hatch, but a mature setup automates the decision rather than waiting for a human to notice a dashboard turn red. That typically means a canary or progressive-delivery step (a small percentage of traffic to the new version, or one new-version pod alongside the old ones) combined with an automated analysis step that queries real metrics — error rate, p99 latency, saturation — over a fixed window, and only continues the rollout if those metrics stay within threshold, automatically rolling back otherwise.

Tools like Argo Rollouts or Flagger implement exactly this loop on top of Kubernetes' native rolling update primitives: they still create ReplicaSets and shift traffic the same way a plain Deployment does, but they gate each step on a metrics query instead of only on readiness probes passing, closing the exact gap that let a "readiness-passing but actually broken" rollout described earlier reach 100% of traffic unchecked.
