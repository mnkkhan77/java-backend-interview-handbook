SECTION 1 - CONTROLLED VS UNCONTROLLED

Q1. What is the difference between a controlled and an uncontrolled input, and when would you use each?

ROI: ★★★★★ Frequency: Extremely High

Short Answer

A controlled input keeps its value in React state — you pass value and update it in onChange, so React is the single source of truth. An uncontrolled input keeps its value in the DOM itself; you read it on demand via a ref (or on submit). Controlled gives you instant, reactive access to every keystroke at the cost of a render per keystroke; uncontrolled is cheaper and closer to native HTML but harder to react to live.

Detailed Answer

The distinction is about who owns the value. In a controlled input the value flows down from state and every change flows back up through onChange — a classic unidirectional loop. Because the rendered value always equals state, you can validate, format, mask, disable a submit button, or mirror the value elsewhere in real time.

An uncontrolled input lets the browser hold the value. You give it an initial value with defaultValue and later pull the current value out of the DOM node. This is essentially how a plain HTML form works, and it is what libraries like React Hook Form lean on for performance.

When to reach for each

  • Controlled — when the UI must react to input live: enabling/disabling buttons, live character counts, input masking/formatting, conditional fields, or driving other components from the value.
  • Uncontrolled — simple forms where you only need values at submit time, large forms where per-keystroke re-renders hurt, file inputs (which are always uncontrolled), and when integrating with non-React code.

A key rule: an input must be consistently controlled or uncontrolled across its lifetime. Switching from value={undefined} to a defined value triggers React's warning: "A component is changing an uncontrolled input to be controlled." The fix is to always pass a defined value (e.g. value={name ?? ""}).

Code Example

// Controlled: React state is the source of truth
function ControlledName() {
  const [name, setName] = React.useState("");
  return (
    <input
      value={name}
      onChange={(e) => setName(e.target.value)}
    />
  );
}

// Uncontrolled: the DOM holds the value, read via ref
function UncontrolledName() {
  const inputRef = React.useRef<HTMLInputElement>(null);
  const handleSubmit = (e: React.FormEvent) => {
    e.preventDefault();
    console.log(inputRef.current?.value); // read on demand
  };
  return (
    <form onSubmit={handleSubmit}>
      <input defaultValue="" ref={inputRef} />
      <button>Submit</button>
    </form>
  );
}

Project Example

On a checkout page, the credit-card field is controlled so we can apply a "#### #### #### ####" mask and show the card-network logo as the user types. The optional "delivery notes" textarea, by contrast, is uncontrolled — nobody needs to react to it live, so we just read ref.current.value at submit and avoid re-rendering the whole form on each keystroke.

Senior Engineer Perspective

Interviewers use this to see whether you understand the render cost, not just the API. Weak answers say "controlled is the React way, always use it." A senior answer acknowledges that controlled inputs re-render on every keystroke, that React Hook Form deliberately embraces the uncontrolled model to avoid this, and that file inputs cannot be controlled at all. The follow-up trap is the "controlled to uncontrolled" warning — be ready to explain that it comes from passing value={undefined} and is fixed by defaulting to an empty string.

Q2. What is the difference between defaultValue and value (and defaultChecked vs checked)?

ROI: ★★★★☆ Frequency: High

Short Answer

value makes an input controlled — React enforces it on every render. defaultValue only sets the initial value and then lets the DOM take over, making the input uncontrolled. The same pairing exists for checkboxes/radios: checked (controlled) vs defaultChecked (uncontrolled).

Detailed Answer

If you pass value without an onChange, React makes the field read-only and logs a warning, because the value can never change from state. If you pass both value and defaultValue, value wins and defaultValue is ignored. Use defaultValue only when you want the browser to manage the field after seeding it — the typical uncontrolled pattern.

A common real bug: developers want to prefill a form from server data but keep it controlled, and they set defaultValue={user.name}. Because the data arrives asynchronously, the initial render has an empty default, and when data loads the DOM value never updates. The correct controlled approach is value={name} with state seeded from the fetched data (via useEffect or React Hook Form's reset()).

Code Example

// WRONG: async data won't populate an uncontrolled field after mount
<input defaultValue={user?.name} />   // stays blank if user loads later

// RIGHT (controlled): seed state once data arrives
const [name, setName] = React.useState("");
React.useEffect(() => {
  if (user) setName(user.name);
}, [user]);
<input value={name} onChange={(e) => setName(e.target.value)} />

// Checkbox equivalents
<input type="checkbox" defaultChecked />              // uncontrolled
<input type="checkbox" checked={agreed}
       onChange={(e) => setAgreed(e.target.checked)} /> // controlled

Senior Engineer Perspective

The trap here is async prefill. Interviewers love to ask "you set defaultValue from a fetch and it's blank — why?" The answer: defaultValue is only read on the first render, so a value that arrives later is ignored. Mention that React Hook Form solves exactly this with reset(serverData) or the values prop, which resyncs the form when async data lands.

Q3. How do you handle many inputs with a single change handler?

ROI: ★★★★☆ Frequency: High

Short Answer

Give each input a name that matches a key in a state object, then use one handler that reads e.target.name and e.target.value and updates the object with a functional setState. This scales to any number of fields without writing a handler per input.

Detailed Answer

Storing all fields in a single object is idiomatic and keeps handlers DRY. Use the functional updater form (prev => ...) so batched updates never read a stale snapshot, and read type so checkboxes contribute a boolean rather than the literal string "on".

Beware nested objects: a shallow spread only copies the top level, so nested fields need a nested spread or a helper like immer. For anything beyond a handful of fields with real validation, prefer a form library — hand-rolling this quickly becomes a maintenance burden.

Code Example

function ProfileForm() {
  const [form, setForm] = React.useState({
    firstName: "",
    email: "",
    subscribe: false,
  });

  const handleChange = (e: React.ChangeEvent<HTMLInputElement>) => {
    const { name, value, type, checked } = e.target;
    setForm((prev) => ({
      ...prev,
      [name]: type === "checkbox" ? checked : value,
    }));
  };

  return (
    <form>
      <input name="firstName" value={form.firstName} onChange={handleChange} />
      <input name="email" value={form.email} onChange={handleChange} />
      <input name="subscribe" type="checkbox"
             checked={form.subscribe} onChange={handleChange} />
    </form>
  );
}

Senior Engineer Perspective

The computed-key pattern [name]: value is the crux — many candidates hardcode a setter per field. Follow-ups probe edge cases: checkboxes (use checked, not value), multi-selects (read selectedOptions), and number inputs (e.target.value is always a string — coerce it). Mentioning that every keystroke re-renders the whole form here is a good segue into performance and why RHF exists.

SECTION 2 - PERFORMANCE OF CONTROLLED FORMS

Q4. Why do controlled forms re-render on every keystroke, and how do you mitigate it?

ROI: ★★★★★ Frequency: Extremely High

Short Answer

Because each keystroke calls setState, and a state change re-renders the component that owns the state — plus its children unless memoized. For small forms this is invisible; for large forms or expensive children it causes jank. Mitigate by isolating state, memoizing children, moving to uncontrolled inputs, or using React Hook Form, which subscribes to fields instead of re-rendering the whole tree.

Detailed Answer

The re-render itself is usually cheap — React diffing a few inputs is fast. The problem is when the form component also renders heavy children (a rich text editor, a big list, a chart) that re-run their render on every character. Diagnose with the React DevTools Profiler before optimizing.

Mitigation ladder (cheapest first)

  • Isolate state — push each input's state down into its own small component so only that field re-renders (state colocation).
  • Memoize expensive siblings — wrap heavy children in React.memo so they skip renders when their props are unchanged.
  • Go uncontrolled — read values via refs at submit; zero re-renders while typing.
  • Use React Hook Form — it registers inputs as uncontrolled and only re-renders components that subscribe to a given field.
  • Debounce derived work — keep the input controlled but debounce the expensive side effect (search, validation), not the keystroke itself.

Code Example

// State colocation: only SearchBox re-renders on each keystroke,
// not the expensive <HugeResultsList /> sibling.
function Page() {
  return (
    <>
      <SearchBox />
      <HugeResultsList />   {/* unaffected by typing in SearchBox */}
    </>
  );
}

function SearchBox() {
  const [q, setQ] = React.useState("");
  return <input value={q} onChange={(e) => setQ(e.target.value)} />;
}

Senior Engineer Perspective

Junior answers jump straight to "memoize everything." A senior first says "measure it — most forms don't need this." Then they distinguish the render (cheap) from expensive children (the real cost) and explain state colocation as the primary lever. Bonus points for noting that React 19's compiler auto-memoizes many of these cases, reducing the need for manual memo/useCallback, and that RHF's whole selling point is sidestepping this problem via uncontrolled registration.

SECTION 3 - FORM LIBRARIES

Q5. Why is React Hook Form so popular, and how does register work?

ROI: ★★★★★ Frequency: Extremely High

Short Answer

React Hook Form (RHF) is popular because it keeps inputs uncontrolled — it registers each field with a ref and reads values from the DOM — so typing doesn't re-render the form. register(name) returns the ref, name, onChange, and onBlur props you spread onto an input, wiring it into the form with almost no boilerplate.

Detailed Answer

RHF wins on three axes: performance (uncontrolled inputs, subscription-based re-renders), ergonomics (minimal boilerplate, built-in validation, first-class TypeScript inference), and bundle size (small, zero dependencies). You call useForm() once to get register, handleSubmit, formState, reset, watch, setValue, and control.

register("email", rules) attaches a ref to the input and tracks it internally. On submit, handleSubmit collects values from the registered refs, runs validation, and calls your callback with typed data only if validation passes. Because reads come from the DOM, RHF avoids the per-keystroke render churn that plagues large controlled forms.

The trade-off: native inputs work by spreading register, but custom/third-party components that don't forward a ref must be wired through Controller or useController (Q6). Also, watch() does subscribe to changes and will re-render — use it deliberately.

Code Example

import { useForm } from "react-hook-form";

type FormValues = { email: string; password: string };

function LoginForm() {
  const {
    register,
    handleSubmit,
    formState: { errors, isSubmitting },
  } = useForm<FormValues>();

  const onSubmit = async (data: FormValues) => {
    await api.login(data); // called only if validation passes
  };

  return (
    <form onSubmit={handleSubmit(onSubmit)}>
      <input
        {...register("email", {
          required: "Email is required",
          pattern: { value: /^\S+@\S+$/, message: "Invalid email" },
        })}
      />
      {errors.email && <span role="alert">{errors.email.message}</span>}

      <input type="password" {...register("password", { required: true })} />

      <button disabled={isSubmitting}>Log in</button>
    </form>
  );
}

Project Example

We migrated a 40-field onboarding form from hand-rolled useState to RHF. The old version re-rendered the entire step on every keystroke and stuttered on low-end devices; after the migration, typing caused zero form re-renders, validation was declarative, and we deleted roughly 300 lines of change-handler boilerplate.

Senior Engineer Perspective

Interviewers want to hear "uncontrolled by default" — that single phrase signals you understand why RHF is fast, not just that it is. Follow-ups: how does RHF handle a component that hides its ref? (Controller). Does watch() hurt performance? (Yes — it subscribes; prefer useWatch scoped to a subtree). How do you prefill from the server? (reset(data) or the values prop, not defaultValues after mount).

Q6. What is the difference between useForm, Controller, and useController?

ROI: ★★★★☆ Frequency: High

Short Answer

useForm is the top-level hook that creates the form instance. Controller is a render-prop wrapper you use to connect controlled third-party components (MUI, Ant Design, react-select) that don't expose a ref for register. useController is the hook version of Controller for building your own reusable controlled field components.

Detailed Answer

register works only when you can spread its props (including a ref) directly onto a native input. Many UI-library components are controlled and expect value/onChange instead — they don't forward a DOM ref. That's where Controller comes in: it bridges RHF's uncontrolled core to a controlled component by giving you a field object (value, onChange, onBlur, ref, name) to hand to the component.

useController is the same bridge as a hook, ideal when you're authoring a design-system input wrapper (e.g. <TextField>) so consumers can just drop it into any RHF form. Use Controller/useController only when necessary — every controlled field re-renders on change, so keep native inputs on plain register.

Code Example

import { useForm, Controller } from "react-hook-form";
import Select from "react-select";

function TagPicker() {
  const { control, handleSubmit } = useForm<{ tags: Option[] }>();

  return (
    <form onSubmit={handleSubmit(console.log)}>
      <Controller
        name="tags"
        control={control}
        rules={{ required: "Pick at least one tag" }}
        render={({ field, fieldState }) => (
          <>
            <Select {...field} isMulti options={options} />
            {fieldState.error && <span>{fieldState.error.message}</span>}
          </>
        )}
      />
    </form>
  );
}

Senior Engineer Perspective

The tell here is knowing why Controller exists: register needs a forwarded ref, and most controlled UI components don't give you one. If a candidate wraps every field in Controller, that's a smell — it re-introduces the per-render cost RHF avoids. Senior answer: native inputs via register, controlled third-party components via Controller/useController, and prefer building one reusable useController-based wrapper over scattering render props everywhere.

Q7. How does Formik compare to React Hook Form?

ROI: ★★★★☆ Frequency: High

Short Answer

Formik was the dominant form library before RHF. It is controlled by default — form state lives in Formik's React state, so every keystroke re-renders the form — which makes large forms slower. RHF is uncontrolled by default, smaller, and generally faster. For new projects most teams now choose RHF; Formik remains common in legacy codebases and is largely in maintenance mode.

Detailed Answer

AspectFormikReact Hook Form

Re-renders on keystrokeWhole form re-rendersIsolated / minimal
Bundle sizeLargerSmaller, zero deps
ValidationYup (built-in support), customAny schema via resolver, built-in rules

MomentumMaintenance modeActively developed, de facto standard

Formik's component-driven API (<Formik>, <Field>, <ErrorMessage>) reads nicely for small forms and pairs cleanly with Yup. But its controlled architecture is the reason RHF overtook it: on a large form, Formik's per-keystroke re-render becomes the bottleneck exactly where you feel it most.

Senior Engineer Perspective

Don't trash Formik — that reads as trend-chasing. The mature take: "Formik is fine and I'd keep it in an existing app; for greenfield I default to RHF for its uncontrolled model, smaller bundle, and TS inference." Being able to name the concrete architectural difference (controlled vs uncontrolled) rather than vague "RHF is better" is what separates the answers.

SECTION 4 - VALIDATION

Q8. How do you do schema validation with Zod or Yup, and what is the resolver pattern?

ROI: ★★★★★ Frequency: Extremely High

Short Answer

You define the form's shape and rules once as a schema (Zod or Yup), then plug it into the form library through a resolver — a small adapter that runs the schema and maps its errors into the library's error format. With Zod you also get a TypeScript type for free via z.infer, so the schema is the single source of truth for both runtime validation and static types.

Detailed Answer

Inline per-field rules (RHF's required, pattern) work but scatter validation logic and duplicate it against your types. A schema centralizes rules, supports cross-field constraints (e.g. "confirm password matches password"), and can be shared with the backend. RHF exposes this via @hookform/resolvers, which offers zodResolver, yupResolver, and adapters for Joi, Valibot, and others.

Zod vs Yup

  • Zod — TypeScript-first; the schema infers the type (z.infer<typeof schema>), so types and validation can never drift. Now the common default.
  • Yup — older, chainable API, deeply integrated with Formik historically; TypeScript support is decent but less seamless than Zod's inference.

The big payoff of Zod is that the schema drives the type. You write one signupSchema, derive type SignupForm = z.infer<typeof signupSchema>, and pass both into useForm — no manual interface to keep in sync.

Code Example

import { z } from "zod";
import { useForm } from "react-hook-form";
import { zodResolver } from "@hookform/resolvers/zod";

const signupSchema = z
  .object({
    email: z.string().email("Enter a valid email"),
    password: z.string().min(8, "At least 8 characters"),
    confirm: z.string(),
  })
  .refine((d) => d.password === d.confirm, {
    message: "Passwords must match",
    path: ["confirm"], // attach the error to the confirm field
  });

type SignupForm = z.infer<typeof signupSchema>;

function Signup() {
  const {
    register,
    handleSubmit,
    formState: { errors },
  } = useForm<SignupForm>({ resolver: zodResolver(signupSchema) });

  return (
    <form onSubmit={handleSubmit((data) => api.signup(data))}>
      <input {...register("email")} />
      {errors.email && <span role="alert">{errors.email.message}</span>}
      <input type="password" {...register("password")} />
      <input type="password" {...register("confirm")} />
      {errors.confirm && <span role="alert">{errors.confirm.message}</span>}
      <button>Create account</button>
    </form>
  );
}

Senior Engineer Perspective

The phrase interviewers listen for is "single source of truth." A senior answer highlights that Zod's z.infer unifies runtime validation and static types, and that the same schema can be reused on the server (e.g. in a Next.js route handler) so client and server agree on validity. Follow-up: cross-field validation — show you know .refine() with a path to attach the error to the right field. Know what a resolver actually is: an adapter mapping schema errors to formState.errors.

Q9. How do you handle asynchronous validation, such as checking username availability?

ROI: ★★★★☆ Frequency: High

Short Answer

Sync validation (format, length, required) runs instantly and locally. Async validation calls a server — e.g. "is this username taken?" — so it must be debounced, must handle out-of-order responses, and must show a pending state. In RHF you can return a Promise from a field's validate function, or run the check separately and set an error with setError.

Detailed Answer

Three problems define async validation quality:

  • Too many requests — validating on every keystroke hammers the server. Debounce (250–500ms) so you only check after the user pauses.
  • Race conditions — a slow response for "jo" can land after "john" and show the wrong result. Cancel stale requests (AbortController) or track a request id and ignore outdated ones. TanStack Query handles this for you if you validate through a query.
  • Feedback — show a spinner while checking and never block submit on an in-flight check without indicating it.

RHF supports a validate function that returns a Promise; it awaits the result and treats a returned string as the error message. For richer UX (debounce + spinner) many teams run the availability check as a separate debounced effect/query and call setError/clearErrors on the field.

Code Example

// Async field validation in React Hook Form
<input
  {...register("username", {
    required: "Username required",
    validate: async (value) => {
      const res = await fetch(`/api/username-available?u=${value}`);
      const { available } = await res.json();
      return available || "That username is taken";
    },
  })}
/>

// For debounce + race safety, prefer a query-based check:
const { data } = useQuery({
  queryKey: ["username", debouncedValue],
  queryFn: ({ signal }) => checkUsername(debouncedValue, signal), // aborts stale
  enabled: debouncedValue.length > 2,
});
// TanStack Query cancels superseded requests and caches results.

Senior Engineer Perspective

The differentiator is naming the race condition and its fix (AbortController / request id / a query cache), not just "debounce it." Interviewers also probe validation timing: async checks should typically fire on blur or after a debounce, not on every keystroke, and you should re-check server-side on submit because client validation is only UX — never trust it for correctness or security.

Q10. How do you debounce validation or expensive input-driven work?

ROI: ★★★☆☆ Frequency: Medium

Short Answer

Keep the input responsive (update state on every keystroke) but delay the expensive effect — validation, search, autosave — until the user pauses. Implement with a debounced value via useEffect + setTimeout cleanup, a reusable useDebouncedValue hook, or, in React 18+, useDeferredValue for render-deferral.

Detailed Answer

Debouncing separates "what the user sees" (instant) from "what the system does" (delayed). Never debounce the controlled value itself — that makes the input feel laggy. Instead debounce the derived value that feeds the effect.

Two modern tools: useDeferredValue lets React keep the input snappy while re-rendering an expensive dependent list at lower priority (no timer, concurrent-scheduling based). A classic timer-based debounce is still right for network calls, where you genuinely want to skip intermediate requests.

Code Example

function useDebouncedValue<T>(value: T, delay = 400): T {
  const [debounced, setDebounced] = React.useState(value);
  React.useEffect(() => {
    const id = setTimeout(() => setDebounced(value), delay);
    return () => clearTimeout(id); // cancel on the next keystroke
  }, [value, delay]);
  return debounced;
}

function Search() {
  const [q, setQ] = React.useState("");
  const debouncedQ = useDebouncedValue(q, 400);

  React.useEffect(() => {
    if (debouncedQ) runSearch(debouncedQ); // fires only after a pause
  }, [debouncedQ]);

  return <input value={q} onChange={(e) => setQ(e.target.value)} />;
}

Senior Engineer Perspective

The key insight is what you debounce: the side effect, not the input. Candidates who debounce the value make the field janky. Bonus depth: contrast timer-based debounce (best for network throttling) with useDeferredValue (best for keeping renders responsive), and note the cleanup function in useEffect is what actually cancels the pending timer.

Q11. How do you display validation errors accessibly?

ROI: ★★★★☆ Frequency: High

Short Answer

Associate the error message with its input using aria-describedby, mark the invalid field with aria-invalid="true", and put the message in a live region (role="alert" or aria-live) so screen readers announce it. Never signal errors with color alone, and move focus to the first invalid field on submit.

Detailed Answer

A visually shown error is invisible to a screen-reader user unless it's programmatically linked. The pattern:

  • Every input has a real <label> tied by htmlFor/id.
  • The error element has an id; the input references it with aria-describedby.
  • aria-invalid={!!error} exposes the invalid state to assistive tech.
  • The error container uses role="alert" (assertive) or aria-live="polite" so it's announced when it appears.
  • On a failed submit, move focus to the first error (RHF's setFocus or the shouldFocusError option does this).

Also validate at the right time: showing errors on every keystroke before the user finishes typing is hostile. A good default is validate on blur / on submit, then re-validate on change once a field already has an error (RHF: mode: "onTouched" with reValidateMode: "onChange").

Code Example

<label htmlFor="email">Email</label>
<input
  id="email"
  aria-invalid={errors.email ? "true" : "false"}
  aria-describedby={errors.email ? "email-error" : undefined}
  {...register("email")}
/>
{errors.email && (
  <p id="email-error" role="alert">
    {errors.email.message}
  </p>
)}

Senior Engineer Perspective

Accessibility is an easy way to stand out — most candidates render {error && <span>...</span>} and stop. A senior answer names aria-invalid, aria-describedby, and a live region, and adds the UX nuance of validation timing (onBlur/onSubmit, not aggressive onChange) plus focusing the first invalid field on submit. Mention that color-only error signaling fails WCAG.

SECTION 5 - ADVANCED PATTERNS & SUBMIT UX

Q12. How do you build dynamic forms with field arrays (add/remove rows)?

ROI: ★★★★☆ Frequency: High

Short Answer

Model the repeating section as an array in form state and render a row per item, each field namespaced by index (e.g. items.0.name). React Hook Form's useFieldArray gives you fields, append, remove, and move, and — crucially — a stable field.id to use as the React key so rows don't get mismatched on reorder.

Detailed Answer

Field arrays power invoices with line items, questionnaires, tag lists, and similar. The two hazards are (1) keys — never key rows by array index, because inserting/removing rows shifts indices and corrupts input state; use the library-provided stable id — and (2) validation, which the schema handles per element via z.array(itemSchema).

Hand-rolling this with useState is possible (setItems(prev => [...prev, blank])), but you must manage stable keys yourself. useFieldArray removes that footgun and integrates with RHF's validation and dirty-tracking.

Code Example

import { useForm, useFieldArray } from "react-hook-form";

function InvoiceForm() {
  const { register, control, handleSubmit } = useForm<{
    items: { name: string; qty: number }[];
  }>({ defaultValues: { items: [{ name: "", qty: 1 }] } });

  const { fields, append, remove } = useFieldArray({ control, name: "items" });

  return (
    <form onSubmit={handleSubmit(console.log)}>
      {fields.map((field, index) => (
        <div key={field.id}>  {/* stable id, NOT index */}
          <input {...register(`items.${index}.name`)} />
          <input type="number" {...register(`items.${index}.qty`)} />
          <button type="button" onClick={() => remove(index)}>Remove</button>
        </div>
      ))}
      <button type="button" onClick={() => append({ name: "", qty: 1 })}>
        Add item
      </button>
    </form>
  );
}

Senior Engineer Perspective

The interviewer is checking whether you know the React key rule under mutation. Using the array index as key here is the classic bug — remove row 1 and the value from row 2 appears to "stick" on the wrong row. Say explicitly: use field.id. Follow-up depth: nested field arrays, and the fact that append/remove mutate form state without re-rendering unrelated fields.

Q13. How do you build a multi-step form wizard, and where should the state live?

ROI: ★★★★☆ Frequency: High

Short Answer

Keep all form state in one place that outlives the individual steps — a single form instance or a shared store — and swap which step's fields are visible. Validate per step before advancing. Do not unmount a step and lose its data; either mount one form spanning all steps or persist each step's values into a parent/store as the user moves forward.

Detailed Answer

The core question is state ownership. Three common approaches:

  • Single RHF form across all steps — one useForm in a parent; each step renders a slice of the fields. State survives step changes automatically. Validate the current step's fields with trigger(["fieldA", "fieldB"]) before advancing.
  • Per-step form + lift on next — each step is its own form; on "Next" you validate and merge that step's values into parent state (or a context/Zustand store). Cleaner isolation, more plumbing.
  • Shared store (Zustand/context) — good when steps are far apart in the tree or you need to persist to localStorage for resume-later.

Persistence matters: wizards are long, so autosaving to localStorage or the server lets users resume. Also expose progress and allow going back without data loss — which is exactly why the state must live above the steps.

Code Example

function Wizard() {
  const methods = useForm<WizardData>({ defaultValues });
  const [step, setStep] = React.useState(0);

  const next = async () => {
    // validate only the current step's fields before advancing
    const fieldsByStep = [["name", "email"], ["address"], ["payment"]];
    const ok = await methods.trigger(fieldsByStep[step]);
    if (ok) setStep((s) => s + 1);
  };

  return (
    <FormProvider {...methods}>
      {step === 0 && <StepAccount />}
      {step === 1 && <StepAddress />}
      {step === 2 && <StepPayment />}
      {step > 0 && <button onClick={() => setStep((s) => s - 1)}>Back</button>}
      {step < 2
        ? <button onClick={next}>Next</button>
        : <button onClick={methods.handleSubmit(submitAll)}>Finish</button>}
    </FormProvider>
  );
}

Senior Engineer Perspective

"Where does the state live?" is the whole question. The junior mistake is a separate useState per step that gets wiped when the step unmounts. Senior answer: one form instance (or store) above the steps, per-step validation via trigger, and FormProvider/useFormContext so nested steps read the same form without prop drilling. Bonus: mention resume-later persistence and URL-synced step so refresh/back-button behave.

Q14. How do you handle file uploads in a React form?

ROI: ★★★☆☆ Frequency: Medium

Short Answer

File inputs are always uncontrolled — you cannot set a file input's value from React for security reasons, so you read e.target.files (or a ref) instead. Send the file with FormData and multipart/form-data, validate type/size on the client for UX, and always re-validate on the server. Track upload progress via XMLHttpRequest or a library, since fetch doesn't expose upload progress natively.

Detailed Answer

Key facts interviewers probe:

  • You can't do <input type="file" value={...}> — the browser blocks programmatic setting of the selected file, so file inputs are inherently uncontrolled. Read from files.
  • Use FormData and let the browser set the multipart/form-data boundary — do not manually set the Content-Type header.
  • Client-side checks (accepted extensions, max size, image dimensions via a preview) improve UX but are not security; the server must enforce limits.
  • For progress bars use XMLHttpRequest's upload.onprogress or a lib like axios; native fetch lacks upload progress.
  • Show a preview with URL.createObjectURL and revoke it on cleanup to avoid leaks.

In RHF, register the file input and read files in the submit handler, or validate size/type via a validate function.

Code Example

function AvatarUpload() {
  const { register, handleSubmit } = useForm<{ avatar: FileList }>();

  const onSubmit = async (data: { avatar: FileList }) => {
    const file = data.avatar[0];
    const body = new FormData();
    body.append("avatar", file);
    // Do NOT set Content-Type manually; the browser adds the boundary.
    await fetch("/api/upload", { method: "POST", body });
  };

  return (
    <form onSubmit={handleSubmit(onSubmit)}>
      <input
        type="file"
        accept="image/*"
        {...register("avatar", {
          validate: (list) =>
            !list?.[0] || list[0].size <= 2_000_000 || "Max 2 MB",
        })}
      />
      <button>Upload</button>
    </form>
  );
}

Q15. How do you handle submit UX — loading state, disabling, and optimistic updates?

ROI: ★★★★☆ Frequency: High

Short Answer

Track a submitting flag (RHF gives you formState.isSubmitting), disable the submit button and show a spinner while the request is in flight to prevent double submits, and re-enable on completion. For snappy UX you can apply an optimistic update — reflect the change in the UI immediately and roll back if the request fails.

Detailed Answer

Robust submit handling covers several concerns:

  • Prevent double submission — disable the button (or guard on isSubmitting) so an impatient user can't fire two requests.
  • Feedback — spinner/label change ("Saving…"), and on failure surface a server error, ideally mapped back onto fields via setError for 422-style validation responses.
  • Success — reset the form (reset()), navigate, or show a toast. Reset also clears the dirty state.
  • Optimistic update — update local/cache state before the server confirms; on error, roll back. TanStack Query's onMutate/onError/onSettled, or React 19's useOptimistic, standardize this.

Only make writes optimistic when failure is rare and rollback is cheap and unsurprising (e.g. toggling a like). For a payment, wait for confirmation.

const {

  handleSubmit,
  setError,
  formState: { isSubmitting },
} = useForm<FormValues>();

  } catch (err) {
    // Map a 422 field error back onto the form

  }
};

  {/* fields... */}
  <button disabled={isSubmitting}>
    {isSubmitting ? "Saving…" : "Save"}
  </button>
</form>

Q16. What are React 19 form actions, useActionState, and useFormStatus?

ROI: ★★★★☆ Frequency: High

Short Answer

React 19 lets you pass a function to a <form action={...}>. The action receives the submitted FormData, can be async, and integrates with pending/error state. useActionState wraps an action to expose its return value, an isPending flag, and a bound action. useFormStatus lets a nested component (like a submit button) read the parent form's pending state without prop drilling. With Server Components, actions can be Server Actions that run on the server.

Detailed Answer

Form actions are React's built-in answer to the boilerplate of "manage isSubmitting, call the API, handle the result." You attach a function to a form's action; React calls it with the FormData on submit, manages pending state, and resets uncontrolled fields on success.

  • useActionState(fn, initialState) — returns [state, formAction, isPending]. state is whatever the action returns (great for validation errors or messages), formAction is what you pass to <form action>, and isPending replaces manual submitting flags.
  • useFormStatus() — must be called from a component rendered inside the form; returns { pending, data, method }. Perfect for a reusable <SubmitButton> that disables itself during submission without the parent passing props down.
  • Server Actions (Next.js / RSC) — an action marked "use server" runs on the server; the form works even before hydration (progressive enhancement).

These are additive, not a replacement for React Hook Form. RHF still shines for complex client-side validation, field arrays, and rich interactivity; form actions shine for progressively-enhanced, server-driven mutations with minimal client code.

"use client";
import { useActionState } from "react";
import { useFormStatus } from "react-dom";

  await api.subscribe(email);
  return {};
}

  const { pending } = useFormStatus();           // reads parent form status
  return <button disabled={pending}>{pending ? "…" : "Subscribe"}</button>;
}

export function NewsletterForm() {

  return (
    <form action={formAction}>
      <input name="email" />
      {state.error && <p role="alert">{state.error}</p>}
      <SubmitButton />
    </form>
  );
}

Senior Engineer Perspective

Key nuances: useFormStatus only works in a child of the form (not the same component that renders the form) — a classic gotcha. useActionState was renamed from the experimental useFormState, and it lives in react while useFormStatus lives in react-dom. The mature framing: form actions don't replace RHF/Zod for heavy client forms — they excel at progressively-enhanced server mutations. Know when each fits.

Q17. What does formState actually track, and why must you destructure the specific fields you use from it?

ROI: ★★★★★ Frequency: Extremely High

Short Answer

formState is a proxy object tracking errors, isDirty, dirtyFields, touchedFields, isSubmitting, isSubmitted, isValid, and submitCount. RHF only re-renders the consuming component for the specific properties you actually read off it — read formState.isValid without ever destructuring it and the component simply won't update when validity changes.

Detailed Answer

RHF wraps formState in a JavaScript Proxy that records which properties a component accesses during render. On each internal state change, RHF checks whether any of the accessed properties changed value; if none did, it skips the re-render entirely. This is why the docs insist you destructure — const { errors } = formState — rather than passing the whole object around or accessing it lazily inside a callback, which the proxy can't observe at render time.

isValid deserves a callout: computing it requires validating the whole form, which by default only happens after submission unless you set mode to something that validates eagerly (e.g. onChange/onBlur). Relying on isValid to disable a submit button before the user has touched anything can therefore be misleading — it may report true simply because nothing has been validated yet.

Code Example

const {
  register,
  handleSubmit,
  formState: { errors, isDirty, isValid, touchedFields },
} = useForm<FormValues>({ mode: "onChange" }); // needed for live isValid

// WRONG: accessing formState.errors inside a plain variable defeats
// the proxy's dependency tracking in some render paths.
function BadButton({ formState }: { formState: any }) {
  return <button disabled={!formState.isValid}>Save</button>;
}

// RIGHT: destructure at the top of the component that needs it
function GoodButton() {
  const { formState: { isValid } } = useFormContext();
  return <button disabled={!isValid}>Save</button>;
}

Senior Engineer Perspective

This question filters candidates who've only used RHF at a surface level from those who've read how it's built. The proxy-based subscription is the mechanism behind RHF's "isolated re-renders" claim — being able to explain it, and the isValid-needs-a-validating-mode gotcha, shows real depth rather than memorized API calls.

Q18. How does watch() differ from useWatch(), and when would each cause performance problems?

ROI: ★★★★☆ Frequency: High

Short Answer

watch() is a method on the form instance that subscribes the calling component to changes and re-renders it on every update to the watched field(s). useWatch() is a separate hook that subscribes its own isolated component — so you can watch a value in a small child component without re-rendering the parent that owns useForm.

Detailed Answer

Calling watch("email") inside the same component that called useForm() re-renders that entire component (and everything under it that isn't memoized) every time the email field changes — which reintroduces exactly the per-keystroke re-render cost RHF is meant to avoid. This is fine for a small form but painful in a large one, especially if the watched value is used to conditionally render heavy children.

useWatch solves this by living in its own component subscribed only to the field(s) it names; the parent form doesn't re-render at all. The idiomatic pattern is to extract "live preview" or "conditional field" UI into a small leaf component that calls useWatch, keeping the re-render blast radius to that leaf.

Also note: calling watch() with no arguments subscribes to the entire form and re-renders on any change whatsoever — almost never what you want in a large form.

Code Example

// Anti-pattern: re-renders the whole 40-field form on every keystroke
function BigForm() {
  const { register, watch } = useForm();
  const email = watch("email"); // re-renders BigForm on every change
  return (
    <form>
      {/* ...40 fields... */}
      <p>Preview: {email}</p>
    </form>
  );
}

// Better: isolate the subscription in a leaf component
function EmailPreview({ control }: { control: Control<FormValues> }) {
  const email = useWatch({ control, name: "email" });
  return <p>Preview: {email}</p>; // only this component re-renders
}

Senior Engineer Perspective

A candidate who reaches for watch() without qualification and then complains "RHF is slow for live previews" hasn't learned the API's escape hatch. The senior move is naming useWatch unprompted and explaining that it exists specifically to decouple the subscribing component from the form-owning component's render cycle.

Q19. How do you reset a form correctly, and what's the difference between reset(), resetField(), and defaultValues vs the values prop?

ROI: ★★★★☆ Frequency: High

Short Answer

reset(newValues) replaces the entire form's values and clears dirty/touched/error state back to a fresh baseline. resetField(name) resets a single field. defaultValues only seeds the first render (often async, via a Promise); the values prop, by contrast, keeps the form in sync every time the passed-in data changes — the modern fix for the "async prefill never showed up" bug.

Detailed Answer

Three related but distinct tools:

  • defaultValues — read once when the form initializes. Can be a Promise (RHF awaits it and shows the form once resolved), but it does not resubscribe to later changes — if the same query refetches with new data, the form won't update.
  • values (RHF 7.32+) — a prop that RHF watches; whenever the object identity/content you pass changes, the form resets to match, ideal for "load then keep resynced with the server" scenarios such as a record being edited by multiple tabs.
  • reset(data, options) — an imperative call, typically after a successful submit (clear the form) or to programmatically load a new record. The options object controls whether to keep dirty state, keep errors, or keep the current values while just resetting flags.
  • resetField(name, options) — resets one field back to its default without touching the rest of the form; handy for a "clear this filter" button.

Code Example

// Modern async-prefill pattern: use `values`, not `defaultValues`
const { data: user } = useQuery({ queryKey: ["user", id], queryFn: () => fetchUser(id) });
const { register, handleSubmit } = useForm<UserForm>({
  values: user, // re-syncs whenever `user` changes, incl. refetches
});

// After a successful submit, clear the form back to blank defaults
const onSubmit = async (data: UserForm) => {
  await api.save(data);
  reset(); // clears values, errors, isDirty, isSubmitted
};

// Reset just one field, e.g. a "Clear coupon code" button
<button type="button" onClick={() => resetField("couponCode")}>Clear</button>

Senior Engineer Perspective

The defaultValues vs values distinction is a frequent real-world bug source — teams ship an edit form that silently goes stale after a background refetch because they used defaultValues. Naming values as the fix, and knowing reset()'s options object controls exactly what state survives, marks genuine hands-on RHF experience.

Q20. How does RHF's validation timing work — what do mode and reValidateMode actually control?

ROI: ★★★★☆ Frequency: High

Short Answer

mode controls when validation first runs for a field: onSubmit (default), onBlur, onChange, onTouched (blur once, then change), or all. reValidateMode (default onChange) controls how a field that already has an error gets re-checked afterward. Together they let you avoid the hostile UX of showing errors before a user has finished typing while still clearing errors promptly once they fix them.

Detailed Answer

The default (mode: "onSubmit") only validates when the form is submitted — nothing shows red until the user clicks Submit, which is often the desired first-pass UX. Once a field has an error, reValidateMode (still defaulting to onChange) means every keystroke re-checks that specific field so the error can clear the moment it's fixed, without re-validating every other untouched field.

A common, well-liked combination for longer forms is mode: "onTouched": a field isn't validated until the user leaves it for the first time (blur), avoiding "required" errors flashing while they're still typing their first character, but once touched it revalidates on every change so corrections are reflected immediately.

These settings are form-wide by default, but individual field rules (e.g. an async validate function) still run according to the same schedule — an expensive async check under mode: "onChange" will fire on every keystroke unless you separately debounce it.

Code Example

const { register, formState: { errors } } = useForm<FormValues>({
  mode: "onTouched",       // validate on first blur
  reValidateMode: "onChange", // then live-clear as they fix it
});

Senior Engineer Perspective

Interviewers use this to see if you think about UX, not just wiring. A candidate who defaults to mode: "onChange" everywhere is optimizing for "always correct" at the cost of aggressive, premature red errors. Naming onTouched as the balanced default for most consumer forms, and distinguishing it from reValidateMode, shows you've actually tuned this in production.

Q21. How do you use setValue and getValues correctly, and what pitfalls exist around their options?

ROI: ★★★☆☆ Frequency: Medium

Short Answer

setValue(name, value, options) imperatively updates a field outside the normal onChange flow — e.g. after an autocomplete selection — but by default it does not mark the field dirty, trigger validation, or re-render subscribers unless you pass { shouldDirty: true, shouldValidate: true, shouldTouch: true }. getValues() reads current values without subscribing to changes — useful in event handlers, dangerous if you expect a component to re-render from it.

Detailed Answer

The default-off options are a deliberate performance choice: if setValue always triggered a full re-validate, programmatically filling many fields (e.g. from a "copy shipping address to billing" button) would be needlessly expensive. But it means a very common bug is: a value visibly updates in the input, yet formState.isDirty stays false and the submit button (gated on isDirty) never enables.

getValues() is a snapshot read, not a subscription — calling it inside a component body will not cause that component to re-render when the value later changes (use watch/useWatch for that). It's the right tool inside a submit handler, a setValue callback, or any place you want "the value right now" without paying a subscription cost.

Code Example

// "Same as shipping address" checkbox: copy values but keep form reactive
const copyShippingToBilling = () => {
  const shipping = getValues("shippingAddress"); // snapshot read
  setValue("billingAddress", shipping, {
    shouldDirty: true,    // mark dirty so Save enables
    shouldValidate: true, // re-run validation on the new value
    shouldTouch: true,
  });
};

Senior Engineer Perspective

The "submit button never enables after setValue" bug is a classic RHF support-forum thread. Naming the three boolean options unprompted, and explaining why they default to false (avoiding wasted validation passes during bulk programmatic updates), is the kind of concrete detail that separates real usage from tutorial-level familiarity.

Q22. How do you integrate RHF with a third-party input that exposes only an onChange callback and no forwarded ref (e.g. a custom Slider)?

ROI: ★★★★☆ Frequency: High

Short Answer

Use Controller (or useController) and wire the third-party component's own value/onChange props to the field object RHF gives you — you never need a DOM ref for this, because Controller manages the value in RHF's internal state instead of reading the DOM.

Detailed Answer

register assumes it can attach a ref to a native form element and read its value directly from the DOM on submit. A component like a custom <Slider onChange={(n) => void}> that renders a <div> internally has no DOM value to read this way. Controller sidesteps the problem entirely: it hands you field.value and field.onChange to plug into the component's own props, and RHF stores the value in its internal form state rather than relying on the DOM.

The cost is that a Controller-wrapped field behaves like a controlled component — it re-renders on every change, same as manual useState would. For a handful of non-native fields this is a non-issue; wrapping every field in Controller "just in case" reintroduces the whole-form re-render cost RHF exists to avoid.

Code Example

import { Controller, useForm } from "react-hook-form";

function VolumeForm() {
  const { control, handleSubmit } = useForm<{ volume: number }>({
    defaultValues: { volume: 50 },

  return (
    <form onSubmit={handleSubmit(console.log)}>
      <Controller
        name="volume"
        control={control}
        rules={{ min: { value: 0, message: "Too low" } }}
        render={({ field: { value, onChange }, fieldState }) => (
          <>
            <CustomSlider value={value} onChange={onChange} />
            {fieldState.error && <span>{fieldState.error.message}</span>}
          </>
        )}
      />
    </form>
  );
}

Senior Engineer Perspective

The tell is recognizing that "no ref" is the trigger for Controller, not "it's a custom component" in general — some custom components do forward refs and work fine with register. Also worth mentioning: many UI libraries (MUI, Ant Design) ship components already designed around value/onChange, which is precisely the shape Controller's field object matches.

Q23. What is dirty/touched tracking, and how do you use it to warn a user about unsaved changes before they navigate away?

ROI: ★★★☆☆ Frequency: Medium

Short Answer

isDirty is true once any field's value differs from its default; dirtyFields tells you exactly which ones. touchedFields tracks which fields the user has focused and blurred, regardless of whether the value changed. Combine isDirty with a route-change guard (or the browser's beforeunload event) to prompt "You have unsaved changes" before the user leaves.

Detailed Answer

isDirty compares current values against defaultValues, so it's important that defaultValues genuinely reflects the saved/server state — if you seed the form with an empty object and fill it later via setValue without { shouldDirty: false }, every field will look "dirty" even though nothing meaningfully changed from the user's perspective. Using the values prop (Q19) alongside reset() keeps this baseline correct after a save.

For in-app navigation guards (e.g. React Router), you intercept the navigation attempt and check isDirty before allowing it. For a full page close/refresh, you need the native beforeunload event, which browsers restrict to showing a generic "leave site?" prompt — you cannot customize its text.

Code Example

const { register, formState: { isDirty } } = useForm<FormValues>();

// Native browser warning on tab close / refresh
React.useEffect(() => {
  const handler = (e: BeforeUnloadEvent) => {
    if (isDirty) {
      e.preventDefault();
      e.returnValue = ""; // required for the browser to show a prompt
    }
  };
  window.addEventListener("beforeunload", handler);
  return () => window.removeEventListener("beforeunload", handler);
}, [isDirty]);

Senior Engineer Perspective

A subtle but important nuance: isDirty is only as trustworthy as your defaultValues/values baseline. Candidates who've hit this in production know to reset the baseline after every successful save so the guard doesn't nag users about changes that are already persisted — a detail that's easy to miss and easy to demo live in an interview.

SECTION 7 - SCHEMA VALIDATION WITH ZOD/YUP

Q25. How do you write conditional validation with Zod — for example, different required fields depending on a "type" selector?

ROI: ★★★★★ Frequency: Extremely High

Short Answer

Use a discriminated union — z.discriminatedUnion("type", [...]) — with one object schema per variant, each sharing a literal type field. Zod picks the correct branch based on that discriminant and validates only the fields relevant to it, giving you both accurate runtime errors and a precise, narrowed TypeScript type.

Detailed Answer

A naive approach — one big object with every possible field marked optional, plus a .refine() checking combinations — works but produces mediocre error messages and a union-of-everything TypeScript type. A discriminated union instead models the domain accurately: "this is a payment schema, and payment is either card or bank_transfer, each with its own required shape."

Zod uses the discriminant to short-circuit which branch's rules apply, so a bank_transfer payload is never checked against card-only required fields, and the inferred type is a true union your component's switch/if can narrow on.

Code Example

import { z } from "zod";

const cardPayment = z.object({
  method: z.literal("card"),
  cardNumber: z.string().length(16),
  cvv: z.string().length(3),
});

const bankPayment = z.object({
  method: z.literal("bank_transfer"),
  accountNumber: z.string().min(8),
  routingNumber: z.string().length(9),
});

const paymentSchema = z.discriminatedUnion("method", [cardPayment, bankPayment]);
type Payment = z.infer<typeof paymentSchema>; // narrows cleanly on `method`

function summarize(payment: Payment) {
  if (payment.method === "card") return `Card ending ${payment.cardNumber.slice(-4)}`;
  return `Bank account ${payment.accountNumber}`;
}

Senior Engineer Perspective

Candidates who reach straight for a giant .refine() callback for every conditional case usually haven't seen discriminated unions. Naming them unprompted, and explaining that the payoff is a genuinely narrowed TypeScript type (not just correct runtime validation), signals real schema-design experience rather than "I've used .min() a few times."

Q26. How do you customize or localize Zod error messages, and produce field-level messages rather than generic ones?

ROI: ★★★★☆ Frequency: High

Short Answer

Every Zod validator accepts an optional message as its last argument (e.g. z.string().min(8, "At least 8 characters")). For cross-cutting customization — localization, a house error-message style — provide a global errorMap via z.setErrorMap() or the schema-level { message } / { error } option (Zod 4), rather than repeating strings on every field.

Detailed Answer

Per-field messages are the simplest lever and cover 90% of cases. For app-wide concerns — translating messages by locale, or overriding Zod's generic defaults ("Expected string, received number") with friendlier copy — a custom error map intercepts every issue Zod would otherwise generate and lets you return a locale-aware string based on the issue's code and path.

When using the resolver pattern (zodResolver), each schema issue's message lands directly on errors.fieldName.message, and its path determines which field it's attached to — which is exactly why .refine()'s path option (Q8) matters for cross-field checks: without it, the error attaches to the root and never shows up next to the relevant input.

Code Example

import { z } from "zod";

// Per-field custom messages
const schema = z.object({
  age: z.number({ message: "Age must be a number" }).min(18, "Must be 18 or older"),
});

// Global error map for locale-aware defaults
z.setErrorMap((issue, ctx) => {
  if (issue.code === "too_small" && issue.type === "string") {
    return { message: `Enter at least ${issue.minimum} characters` };
  }
  return { message: ctx.defaultError };
});

Senior Engineer Perspective

Interviewers listen for whether you know the difference between "sprinkle a message on every rule" (fine for small forms) versus a shared error map (necessary once you localize or standardize copy across dozens of forms). Mentioning that the resolver maps issue.path to the exact form field shows you understand the plumbing, not just the happy path.

Q27. How would you share a single Zod schema between client-side form validation and a server API route?

ROI: ★★★★★ Frequency: Extremely High

Short Answer

Put the schema in a module shared by both client and server bundles (a shared/ or schemas/ package in a monorepo, or just a plain file imported by both a Next.js client component and its route handler). The client uses it via zodResolver for instant UX feedback; the server uses schema.parse()/safeParse() on the incoming payload as the actual security boundary.

Detailed Answer

Client-side validation is UX only — a malicious or buggy client can always send an unvalidated payload directly to the API, so the server must independently validate every request regardless of what the form did. Sharing the schema means you write the rules exactly once, and the two validation passes can never silently drift apart, which is the more valuable half of "single source of truth" beyond the type inference itself.

In practice: export the schema (and its inferred type) from an isomorphic module with no client-only or server-only imports. On the server, call schema.safeParse(req.body) and return a 400 with the flattened Zod error if it fails; on the client, pass the same schema straight into zodResolver. Frameworks with server actions (Next.js) make this especially natural since the action function runs in the same codebase.

Code Example

// shared/schemas/signup.ts — imported by both client and server
export const signupSchema = z.object({
  email: z.string().email(),
  password: z.string().min(8),
});
export type SignupInput = z.infer<typeof signupSchema>;

// Client: React Hook Form
useForm<SignupInput>({ resolver: zodResolver(signupSchema) });

// Server: e.g. a Next.js route handler
export async function POST(req: Request) {
  const result = signupSchema.safeParse(await req.json());
  if (!result.success) {
    return Response.json({ errors: result.error.flatten() }, { status: 400 });
  }
  await createUser(result.data); // fully typed, guaranteed valid
}

Senior Engineer Perspective

The critical line to say out loud: "client validation is never a substitute for server validation — it's purely UX." Candidates who only mention type-sharing and skip the security angle are missing half the point. Bonus depth: mention error.flatten() or error.format() for turning a Zod error into a client-consumable shape, and returning a 400 (not 500) for validation failures.

Q28. How does yupResolver differ from zodResolver in practice, and what Yup type-coercion edge cases bite people?

ROI: ★★★☆☆ Frequency: Medium

Short Answer

Both resolvers run the schema and map failures onto formState.errors the same way. The practical difference is Yup's default type coercion — yup.number() will silently cast a non-empty string to a number (and an empty string to NaN) unless you disable it, whereas Zod is strict by default and expects you to transform/coerce explicitly.

Detailed Answer

Yup's casting is convenient for quick forms (a native <input> always emits strings, and yup.number() "just works") but has sharp edges: an empty numeric field casts to NaN, which can pass or fail validation confusingly depending on your rules, and yup.date() will accept ambiguous string formats a stricter library would reject. Calling .strict() disables casting but then you must feed it already-correct types.

Zod's philosophy is the opposite: nothing is coerced unless you explicitly opt in via z.coerce.number() or a .transform(), which is more verbose for simple numeric inputs but far less surprising, and is a large part of why it's become the default choice for new RHF projects.

Code Example

// Yup: implicit casting — "" becomes NaN, "42" becomes 42
import * as yup from "yup";
const yupSchema = yup.object({ age: yup.number().required() });

// Zod: explicit opt-in coercion required
import { z } from "zod";
const zodSchema = z.object({ age: z.coerce.number().min(0) });
// z.coerce.number() runs Number(value) explicitly, same result but visible in the schema

Senior Engineer Perspective

This is a "have you actually hit a production bug with this" question. The NaN-from-empty-string gotcha in Yup is a real, recurring issue teams discover the hard way. Being able to name it — and explain that Zod's explicit-coercion philosophy trades verbosity for predictability — shows hands-on schema-validation scars, not just familiarity with the docs.

Q30. When would you choose Valibot over Zod, and what's the trade-off?

ROI: ★★★☆☆ Frequency: Medium

Short Answer

Valibot offers a similar TypeScript-first, resolver-compatible API to Zod but is built around tree-shakeable functions instead of a chainable object API, producing dramatically smaller bundles for schema-heavy apps. The trade-off is a less mature ecosystem, fewer community resources, and a different (functional pipe-based) syntax your team has to learn.

Detailed Answer

Zod's chainable methods (z.string().min().email()) mean the whole Zod core tends to end up in your bundle even if you only use a handful of validators, because method chaining resists tree-shaking. Valibot instead exposes standalone functions (v.pipe(v.string(), v.minLength(8))) that bundlers can shake aggressively — teams shipping many small forms to a size-sensitive target (a widget embedded on customer sites, a mobile webview) sometimes see meaningful bundle-size wins.

For most product apps the difference is immaterial next to the rest of the bundle, and Zod's larger ecosystem (more resolvers, more community schemas, more Stack Overflow answers, first-class support in most starter templates) outweighs the size savings. The realistic answer is "default to Zod; consider Valibot specifically when bundle size for a schema-validation-heavy, size-constrained target is a measured, real concern" — not as a blanket recommendation.

Code Example

// Zod
const zodSchema = z.object({ email: z.string().email() });

// Valibot — functional, individually importable pieces
import * as v from "valibot";
const valibotSchema = v.object({
  email: v.pipe(v.string(), v.email("Invalid email")),
});

Senior Engineer Perspective

The mature answer avoids "Valibot is strictly better/worse" and instead frames it as a bundle-size vs ecosystem-maturity trade-off, made concretely on measured data rather than a blog post's benchmark. Candidates who've never heard of Valibot aren't penalized much here — this question mostly rewards knowing that alternatives to Zod exist and being able to reason about the actual axis (tree-shaking) rather than vague "it's newer/faster" claims.

Q31. How do you handle a schema that needs a cross-field, asynchronous rule — e.g. "email must be unique" — as part of Zod validation?

ROI: ★★★★☆ Frequency: High

Short Answer

Zod's .refine()/.superRefine() accept an async function and return a Promise, and schema.parseAsync()/safeParseAsync() await it — RHF's zodResolver supports this transparently. The catch: an async refine inside the full-form schema re-runs on every validation pass (e.g. every keystroke under mode: "onChange") unless you debounce or scope it carefully.

Detailed Answer

superRefine is preferred over a chain of separate .refine() calls when you need to attach multiple, possibly-async issues to different paths from one check. For a uniqueness check, you'd call your API inside the refine and push a custom issue if it fails.

Because this runs as part of full-schema validation, it's easy to accidentally fire it far more often than intended — e.g. on every keystroke if mode is eager. Two common mitigations: keep this specific check on a field-level RHF validate function (Q9) which you can time independently of the rest of the schema, rather than folding it into the Zod schema itself; or, if it must live in the schema, debounce the underlying network call and cache identical in-flight/recent results so retyping the same value doesn't re-hit the server.

Code Example

const signupSchema = z.object({
  email: z.string().email(),
}).superRefine(async (data, ctx) => {
  const taken = await isEmailTaken(data.email); // debounced/cached upstream
  if (taken) {
    ctx.addIssue({
      code: z.ZodIssueCode.custom,
      message: "Email already registered",
      path: ["email"],
    });
  }
});

useForm({ resolver: zodResolver(signupSchema), mode: "onBlur" }); // avoid onChange here

Senior Engineer Perspective

The key insight interviewers want is that folding async logic into the schema doesn't remove the need to think about validation timing — it just moves the debounce responsibility one layer up. Candidates who blindly async-refine inside an onChange-mode form and hammer the uniqueness endpoint on every keystroke are missing the same lesson as Q9/Q50, just at the schema layer instead of the field layer.

Q32. What is the difference between parse and safeParse in Zod, and why does the RHF resolver pattern rely on the safe variant?

ROI: ★★★☆☆ Frequency: Medium

Short Answer

schema.parse(data) throws a ZodError on failure; schema.safeParse(data) returns a discriminated { success: true, data } or { success: false, error } result instead of throwing. Resolvers use the safe variant because form validation failing is an expected, routine outcome — not an exceptional one — and returning a value avoids wrapping every validation call in try/catch.

Detailed Answer

Using exceptions for expected control flow (a user typing an invalid email is not exceptional — it's the normal case) is generally poor practice: it obscures the control flow and forces try/catch scaffolding everywhere validation happens. safeParse's result object lets calling code branch cleanly, and its error (when present) exposes .issues/.flatten()/.format() for turning Zod's internal error tree into whatever shape the consumer — a resolver, an API response, a CLI — needs.

parse still has its place: one-off assertions where an invalid shape genuinely represents a programmer error or corrupted data you want to fail loudly and immediately (e.g. validating your own app's config at startup), where a stack trace is actually useful.

Code Example

const result = signupSchema.safeParse(formData);
if (!result.success) {
  console.log(result.error.flatten().fieldErrors); // { email: ["Invalid email"] }
} else {
  await createUser(result.data); // fully typed and valid
}

// vs. parse — throws, appropriate for "this must never fail" cases
const config = configSchema.parse(process.env); // crash loudly at boot if misconfigured

Senior Engineer Perspective

This is a small but telling question about whether a candidate reaches for exceptions as control flow out of habit. The sharp answer distinguishes "expected failure" (form input, safeParse) from "must never happen" (config/invariant, parse) rather than treating the two functions as interchangeable stylistic choices.

Q33. How do you validate a deeply nested object (e.g. address.shipping.street) with RHF and Zod, and how do errors surface for nested paths?

Short Answer

Detailed Answer

RHF's internal store is a nested object mirroring your form shape, and register/setValue/getValues all accept a dotted-path string that it resolves against that structure (with TypeScript autocompleting valid paths when you type the form's generic). The Zod resolver's error tree already carries a matching path array for each issue (e.g. ["address","shipping","street"]), which RHF converts into the same nested error object shape so errors.address.shipping.street reads exactly like the value would.

The main practical gotcha is TypeScript strictness with deeply nested optional objects — if address itself can be undefined, you need optional chaining at every level when reading errors, which is why the pattern above uses ?. throughout rather than assuming the whole chain exists.

    city: z.string().min(1, "City required"),

const formSchema = z.object({ address: addressSchema });

}

Q34. How do you implement drag-to-reorder rows within a useFieldArray list?

ROI: ★★★☆☆ Frequency: Medium

Short Answer

Use useFieldArray's built-in move(from, to) to reorder the underlying form state, and pair it with a drag-and-drop library (dnd-kit is the common modern choice) that reports the source/target index on drop and calls move — you don't need to hand-roll the array-splicing logic yourself.

Detailed Answer

move reorders both the fields array (with stable field.ids preserved, so inputs don't lose their values mid-drag) and RHF's internal values, keeping everything consistent without you manually mutating arrays. The drag library only needs to be responsible for the interaction/animation layer — sensing the drag, showing a placeholder, and reporting indices — while move stays the single source of truth for what order the data is actually in.

A frequent bug: teams try to reorder by manipulating the fields array returned from useFieldArray directly (it's a snapshot, not mutable state) instead of calling move, which silently does nothing or desyncs the UI from the real form values.

Code Example

import { DndContext, closestCenter } from "@dnd-kit/core";
import { SortableContext, verticalListSortingStrategy } from "@dnd-kit/sortable";

function SortableItems() {
  const { fields, move } = useFieldArray({ control, name: "items" });

  const handleDragEnd = (event: DragEndEvent) => {
    const { active, over } = event;
    if (over && active.id !== over.id) {
      const oldIndex = fields.findIndex((f) => f.id === active.id);
      const newIndex = fields.findIndex((f) => f.id === over.id);
      move(oldIndex, newIndex); // RHF handles the reorder, ids stay stable
    }
  };

  return (
    <DndContext collisionDetection={closestCenter} onDragEnd={handleDragEnd}>
      <SortableContext items={fields.map((f) => f.id)} strategy={verticalListSortingStrategy}>
        {fields.map((field, index) => <SortableRow key={field.id} id={field.id} index={index} />)}
      </SortableContext>
    </DndContext>
  );
}

Senior Engineer Perspective

The insight worth surfacing is the separation of concerns: the drag library only computes "what moved where," and move() is the single place that actually mutates form state — candidates who conflate the two and try to reimplement array splicing themselves are missing the API RHF already gives you.

Q35. How do you handle a field array where each row itself contains a nested field array (e.g. Order to LineItems to Discounts)?

ROI: ★★★★☆ Frequency: High

Short Answer

Detailed Answer

This is the natural extension of "state colocation" into field arrays: a LineItemRow component receives its index as a prop and calls useFieldArray({ control, name: `items.${index}.discounts` }), giving it its own fields/append/remove for that row's discounts, independent of every other row's nested array. Sharing the same top-level control keeps everything part of one form and one submit, while componentizing per row keeps each nested array's re-renders scoped to that row.

Trying to manage both levels of nesting from the top-level component (mapping over items and, inside that map, manually splicing a discounts array with useState) quickly becomes unmanageable and reintroduces the index-as-key and stale-closure bugs useFieldArray exists to avoid.

      </button>

  );

Q36. What performance issues arise with very large field arrays (100+ rows), and how do you mitigate them?

ROI: ★★★★☆ Frequency: High

Short Answer

Even with RHF's uncontrolled model, a field array with hundreds of rows means hundreds of mounted DOM inputs, and any operation that touches the whole array (validation of the array shape, a full reset, computing a derived total) has to walk every row. Mitigate with row-level component memoization, virtualization of off-screen rows, and scoping validation/derived-value subscriptions to only the rows that changed.

Detailed Answer

The uncontrolled model solves per-keystroke re-renders of the *whole form*, but it doesn't make 500 simultaneously mounted <input> elements free — initial mount, layout, and any full-array validation pass still scale with row count. Concrete mitigations:

  • Memoize row components — wrap each row in React.memo keyed by its stable field.id so editing row 50 doesn't re-render rows 1-49.
  • Virtualize — render only the rows currently in the viewport (react-window/react-virtual) when the list is long and mostly scrolled past; this is the single biggest lever for very large arrays.
  • Scope derived computations — a running total shouldn't be computed in the top-level component subscribed to every field; compute it via a useWatch scoped to just the array, memoized, and ideally debounced if the calculation itself is expensive.
  • Avoid full-array re-validation on every row edit — where the schema allows, validate incrementally rather than the whole array on each keystroke.

Code Example

const LineItemRow = React.memo(function LineItemRow({ index, register }: RowProps) {
  return <input {...register(`items.${index}.name`)} />;
});

// Virtualized rendering for a very long field array
import { useVirtualizer } from "@tanstack/react-virtual";

function VirtualizedItems({ fields }: { fields: { id: string }[] }) {
  const parentRef = React.useRef<HTMLDivElement>(null);
  const rowVirtualizer = useVirtualizer({
    count: fields.length,
    getScrollElement: () => parentRef.current,
    estimateSize: () => 48,
  });
  return (
    <div ref={parentRef} style={{ height: 400, overflow: "auto" }}>
      <div style={{ height: rowVirtualizer.getTotalSize(), position: "relative" }}>
        {rowVirtualizer.getVirtualItems().map((v) => (
          <div key={fields[v.index].id} style={{ position: "absolute", top: v.start }}>
            <LineItemRow index={v.index} register={register} />
          </div>
        ))}
      </div>
    </div>
  );
}

Senior Engineer Perspective

A candidate who says "RHF is uncontrolled so it doesn't matter how many rows there are" hasn't actually stress-tested a huge array. The senior answer distinguishes per-keystroke cost (solved by uncontrolled inputs) from total-DOM-node and full-array-operation cost (not solved automatically), and reaches for virtualization as the concrete fix for the latter.

Q37. How do you pre-populate a field array from asynchronously loaded server data without losing stable row keys?

Q38. How do you conditionally show or hide fields based on another field's current value?

Short Answer

Two things must stay in sync: what's rendered, and what's validated. Q39. How do you validate that a field array has at least one item, or that its items are unique?

ROI: ★★★☆☆ Frequency: Medium

Short Answer

For "at least one," add .min(1, "message") to the z.array() itself (not the item schema). For uniqueness across items, use .superRefine() on the array to detect duplicates (e.g. by a key field) and attach an issue to the specific duplicate's path.

Detailed Answer

Array-level constraints belong on the array schema, distinct from per-item constraints on the item schema — conflating the two (e.g. trying to express "at least one" inside the item schema) doesn't work, since an item schema only ever validates one already-existing item. For uniqueness, superRefine gives you access to the whole array plus a ctx you can push multiple issues onto, one per offending index, so each duplicate row gets its own inline error rather than one vague array-level message.

On the RHF side, an array-level error (like the "at least one" case) surfaces at errors.items?.root?.message (or errors.items?.message depending on version) rather than on a specific row — render it once above the list, separately from per-row field errors.

Code Example

const itemsSchema = z.array(
  z.object({ sku: z.string().min(1) })
)
  .min(1, "Add at least one item")
  .superRefine((items, ctx) => {
    const seen = new Map<string, number>();

Q40. How do you compute a derived/aggregate value — like an invoice total — from field array data without causing excessive re-renders?

ROI: ★★★★☆ Frequency: High

Short Answer

Isolate the calculation in its own small component that subscribes via useWatch scoped to just the relevant array, and memoize the reduce itself with useMemo so it only recomputes when the watched values actually change — never compute this in the top-level form component that also renders every input.

Detailed Answer

The naive approach — watch("items") in the same component that renders all the row inputs — re-renders the entire row list on every keystroke in any row, defeating RHF's uncontrolled-input benefits. Moving the subscription into a dedicated <InvoiceTotal /> component that calls useWatch({ control, name: "items" }) means only that small component re-renders when quantities/prices change; the rows themselves stay untouched.

For expensive aggregate calculations (not usually the case for a simple sum, but relevant for something like recalculating tax across many line items with different rates), wrap the derived computation in useMemo keyed on the watched array so identical re-renders (from unrelated state elsewhere in the tree) don't redo the work.

Code Example

function InvoiceTotal({ control }: { control: Control<InvoiceForm> }) {
  const items = useWatch({ control, name: "items" }); // isolated subscription
  const total = React.useMemo(
    () => items?.reduce((sum, item) => sum + item.qty * item.price, 0) ?? 0,
    [items]
  );
  return <p>Total: ${total.toFixed(2)}</p>;
}

function InvoiceForm() {
  const { control, register } = useForm<InvoiceForm>();
  const { fields } = useFieldArray({ control, name: "items" });
  return (
    <form>
      {fields.map((f, i) => <input key={f.id} {...register(`items.${i}.qty`)} />)}
      <InvoiceTotal control={control} />  {/* only this re-renders on qty change */}
    </form>
  );
}

Senior Engineer Perspective

This is a direct application of state colocation (Q4, Q18) to field arrays specifically — interviewers use it to check whether a candidate applies the general principle to a new context rather than only reciting it for the simple single-field case. Q41. How do you validate only the current step's fields without triggering errors for fields on later, unvisited steps?

ROI: ★★★★★ Frequency: Extremely High

Short Answer

Call trigger(fieldNames) with an explicit array of just the current step's field names before advancing — trigger validates only the named fields and leaves the rest of the form's error state untouched, unlike handleSubmit, which always validates everything.

Detailed Answer

A single RHF instance spanning the whole wizard (Q13) needs a way to gate step transitions without prematurely flagging fields the user hasn't reached yet. trigger(["email", "password"]) runs validation for exactly those fields, returns a Promise resolving to whether they're all valid, and updates errors only for that subset — fields on step 3 stay untouched and error-free while the user is still on step 1.

Keep a small lookup — an array or object mapping step index to its field names — so the "Next" handler doesn't hardcode logic per step. If the schema is a single Zod object for the whole wizard, this still works: trigger operates against RHF's per-field validation regardless of whether the resolver validates the whole schema under the hood, though very strict cross-field .refine() rules spanning multiple steps need to be scoped carefully so they don't fire before all their dependent fields exist.

  0: ["fullName", "email"],
  1: ["address", "city", "zip"],
  2: ["cardNumber", "expiry"],
};

async function goNext(step: number, trigger: UseFormTrigger<WizardValues>) {

  return valid;
}

Senior Engineer Perspective

Candidates who don't know trigger often reach for handleSubmit on every step, which either validates the entire form prematurely or requires splitting into separate useForm instances per step (losing the single-source-of-truth benefit). Q42. How do you persist wizard progress to localStorage so a page refresh doesn't lose data, and what security/PII considerations apply?

ROI: ★★★★☆ Frequency: High

Short Answer

Subscribe to form changes (RHF's watch with a callback, debounced) and write the current values to localStorage as JSON, then read them back into defaultValues/values on mount. Never persist sensitive fields (passwords, full card numbers, SSNs) this way — localStorage is unencrypted, accessible to any script on the origin, and persists indefinitely unless explicitly cleared.

Detailed Answer

RHF exposes a subscription form of watch that takes a callback and returns an unsubscribe function, which is more efficient than watching everything for a render-triggering purpose — you're only using it as a side channel to persist data, not to drive UI. Debounce the writes (a few hundred ms) so you're not serializing the whole form on every keystroke.

On the read side, load the saved draft before the form renders (or feed it into defaultValues/values) and clear the saved draft key once the form successfully submits, so a stale draft doesn't reappear on the next visit. For sensitive data, either exclude those fields from the persisted object entirely (destructure them out before JSON.stringify) or persist only non-sensitive progress markers (which step they reached) and re-enter sensitive fields fresh each session.

Code Example

const DRAFT_KEY = "onboarding-draft";

  React.useEffect(() => {
    const subscription = watch(); // or control._subjects... in practice use `watch` callback form
  }, []);
}

// Practical debounced version using the callback form of watch:
function usePersistedDraft(watchFn: UseFormWatch<WizardValues>) {
  React.useEffect(() => {
    const { unsubscribe } = watchFn((values) => {

      }, 400);
    });
    return () => unsubscribe();
  }, [watchFn]);
}

The security angle is what separates a passable answer from a strong one — many candidates happily serialize the entire form including a credit card number into localStorage. Naming that as a hazard unprompted, and describing that the draft key must be cleared on successful submit (otherwise a returning user sees a "resume?" prompt for an already-completed form), shows production-grade thinking.

Q44. How would you implement a branching wizard where step 3's fields differ based on an answer given in step 1?

ROI: ★★★★☆ Frequency: High

Q45. How do you handle a wizard step whose fields depend on data fetched asynchronously mid-flow, such as address autocomplete suggestions?

Detailed Answer

The pattern is the same as any async-select integration: a debounced watch of the free-text input drives a query key, the query's result becomes the options for a combobox-style field, and selecting an option calls field.onChange with the structured value (not just the display string). Q48. What's the difference between a wizard driven by a single RHF instance versus one driven by a state machine like XState?

ROI: ★★★☆☆ Frequency: Medium

Short Answer

A single RHF instance treats the wizard as one form with a UI-level "which step is visible" concern layered on top — simple, low-ceremony, sufficient for mostly-linear flows. A state machine models steps and transitions explicitly as states and events, which shines once the flow has real branching, guards, and side effects per transition that would otherwise become scattered if statements.

Detailed Answer

With plain RHF + step index, "what step comes next," "can I leave this step," and "what happens on transition" all live as ad-hoc logic in event handlers and component conditionals (Q44). This is easy to reason about for a linear 3-5 step flow, but as branches, guards ("can't proceed to payment until KYC step's async check resolves"), and side effects (analytics events per transition, different guards per direction) multiply, that logic sprawls.

A state machine makes the same information declarative and inspectable: states, the events that transition between them, guard conditions on those transitions, and side effects (entry/exit actions) are all defined in one machine definition you can visualize and test as a graph, independent of any component. Form values still typically live in RHF (or the machine's context) — the state machine's job is orchestrating which step and why, not replacing field-level validation.

Code Example

// Conceptual XState sketch — the machine owns step orchestration,
// RHF (or machine context) still owns the actual field values.

const wizardMachine = createMachine({
  id: "onboarding",
  initial: "account",
  states: {
    account: { on: { NEXT: [
      { target: "businessDetails", guard: "isBusinessAccount" },
      { target: "personalDetails" },
    ] } },
    businessDetails: { on: { NEXT: "review", BACK: "account" } },
    personalDetails: { on: { NEXT: "review", BACK: "account" } },
    review: { on: { SUBMIT: "submitting", BACK: "account" } },
    submitting: { on: { SUCCESS: "done", FAILURE: "review" } },
    done: { type: "final" },
  },
});

Senior Engineer Perspective

The mature take avoids "always use a state machine" or "never need one" — it's a complexity threshold judgment. A candidate who reaches for XState on a straightforward 3-step signup is over-engineering; one who's still hand-rolling nested conditionals on a 12-step, heavily-branching application flow with async guards is under-tooled. Being able to articulate the threshold, not just name both options, is the real signal.

SECTION 10 - ASYNC & DEBOUNCED VALIDATION

Q49. How do you show a "checking availability..." pending state distinctly from an actual validation error?

ROI: ★★★★☆ Frequency: High

Short Answer

Track the async check's own loading state separately from formState.errors — typically local component state or a query's isFetching — and render three distinct visual states (idle, pending, error/success) rather than collapsing "checking" and "failed" into one boolean.

Detailed Answer

If you only have errors.username to key off, there's no way to show "we're checking" — the field is either erroring or not. Q50. How do you cancel an in-flight async validation request when the user keeps typing?

ROI: ★★★★☆ Frequency: High

Short Answer

Pass an AbortController's signal into the fetch and abort the previous controller whenever a new request starts (or let a query library like TanStack Query do this automatically via the signal argument it provides to queryFn), so a stale response for an earlier keystroke's value can never overwrite the result for what the user has since typed.

Detailed Answer

Without cancellation, typing "j", "jo", "joh", "john" fires four requests, and if "j"'s response happens to resolve last (a slow/retried request, an unlucky network), it can incorrectly show a result for a value the user no longer has typed. Two viable strategies: cancel-and-replace (abort the previous request when a new one starts — the common choice), or ignore-stale-response (let old requests finish but check, on resolution, whether their input still matches the current value before applying the result).

TanStack Query handles this for you: it aborts the previous queryFn call's signal automatically when the query key changes before the prior request settles, and it also deduplicates/caches identical concurrent keys — which is a large part of why teams prefer routing async validation through a query rather than a hand-rolled fetch in a RHF validate function.

Code Example

// Hand-rolled cancellation without a query library
function useUsernameCheck(value: string) {
  const [result, setResult] = React.useState<{ available: boolean } | null>(null);
  React.useEffect(() => {
    const controller = new AbortController();
    fetch(`/api/username-available?u=${value}`, { signal: controller.signal })
      .then((r) => r.json())
      .then(setResult)
      .catch((err) => { if (err.name !== "AbortError") throw err; });
    return () => controller.abort(); // cancels the previous request
  }, [value]);
  return result;
}

// With TanStack Query — cancellation is automatic via the `signal` param
useQuery({
  queryKey: ["username", value],
  queryFn: ({ signal }) => fetch(`/api/username-available?u=${value}`, { signal }).then((r) => r.json()),
});

Senior Engineer Perspective

Naming AbortController specifically — and the useEffect cleanup function as the place it's invoked — is the concrete detail that shows real experience versus "I'd debounce it" as a vague catch-all. Bonus depth: explaining that debouncing reduces the frequency of the race but doesn't eliminate it (a debounced-but-slow request can still be overtaken by a faster later one) — cancellation is what actually closes the gap.

Q51. How would you avoid re-running an expensive async validator on every re-render when the value hasn't actually changed?

ROI: ★★★☆☆ Frequency: Medium

Short Answer

Memoize the validator function itself (so RHF doesn't see a "new" function reference on every render and re-subscribe unnecessarily) and, more importantly, gate the actual expensive call on whether the debounced input value changed — a query library's cache keyed on the value naturally provides this for free, since an unchanged key returns cached data without a new network call.

Detailed Answer

Two distinct waste sources get conflated here: (1) the validator function reference changing every render, which can cause unnecessary internal bookkeeping in some patterns, and (2) the underlying expensive operation itself re-running on renders that don't reflect a real value change. For (1), wrap the validator in useCallback if it closes over changing values, or better, keep it a stable reference by reading current values via a ref. For (2), let a cache-based approach (TanStack Query keyed by the debounced value) be the actual guard — identical keys return cached data instantly rather than re-hitting the network, regardless of how many times the component re-renders.

In practice, the query-based approach (Q9, Q50) already solves both problems as a side effect of its design, which is a big part of why teams prefer it over inline validate functions for anything non-trivial.

Code Example

// Query cache naturally avoids redundant calls for an unchanged debounced value

  queryKey: ["username-available", debouncedValue],
  queryFn: () => checkUsername(debouncedValue),
  staleTime: 30_000, // treat a recent identical check as still fresh
  enabled: debouncedValue.length > 2,
});

Senior Engineer Perspective

The strongest answers reframe this as "don't hand-roll memoization for a problem a cache already solves" — reaching immediately for a query library's built-in caching/staleTime rather than manually engineering reference-equality guards around a bespoke validator function.

Q52. How do you validate a field only after the user has interacted with it, avoiding "required" errors on empty fields the moment the form mounts?

ROI: ★★★★☆ Frequency: High

Short Answer

Detailed Answer

This is the same mode/reValidateMode mechanism from Q20, applied to the specific and very common complaint of "the form shows every required field as an error before the user has typed anything." onTouched is usually the right default: nothing is marked invalid until the user has actually interacted with that specific field and left it, at which point subsequent edits re-validate live via the default reValidateMode: "onChange".

Watch out for one edge case: handleSubmit always validates the entire form on submission regardless of mode, which is correct (you must catch untouched-but-required fields before allowing submit) but means the very first submit attempt can surface a wave of new errors for fields the user never touched — that's expected and desired, distinct from validating prematurely during normal typing.

Q53. How do you combine synchronous schema validation (Zod) with an additional async check (e.g. username uniqueness) in one RHF form?

ROI: ★★★★☆ Frequency: High

Short Answer

Keep the Zod schema responsible for synchronous shape/format rules via zodResolver, and layer the async check on top with a separate field-level validate function (or a query-driven manual setError/clearErrors) rather than folding the async call into the Zod schema itself — this keeps each validation source independently timed and testable.

Detailed Answer

RHF supports multiple rule sources per field simultaneously: a resolver-driven schema handles synchronous format rules efficiently on every keystroke/blur per the configured mode, while a field's own validate option (or an external effect calling setError/clearErrors) handles the debounced, network-bound async part on its own schedule. Trying to jam both into one Zod superRefine (Q31) works but couples their timing together, which usually isn't what you want — you'd rather have instant sync feedback ("must be 3+ characters") separate from slower async feedback ("that name is taken").

In practice: register the field once with the resolver active for shape, then attach the async availability check as a separate debounced effect (or query) that calls setError("username", ...) on failure and clearErrors("username") on success/change — both error sources land in the same formState.errors.username, so the UI doesn't need to know which validator produced it.

Code Example

const schema = z.object({ username: z.string().min(3, "At least 3 characters") });

function SignupForm() {
  const { register, setError, clearErrors, formState: { errors } } = useForm({
    resolver: zodResolver(schema), // handles sync shape rules
  });
  const username = useWatch({ name: "username" });
  const debounced = useDebouncedValue(username, 400);

  React.useEffect(() => {
    if (!debounced || debounced.length < 3) return;
    let cancelled = false;
    checkUsername(debounced).then(({ available }) => {
      if (cancelled) return;
      if (!available) setError("username", { type: "manual", message: "Already taken" });
      else clearErrors("username"); // only clears if this was the manual error
    });
    return () => { cancelled = true; };
  }, [debounced]);

  return <input {...register("username")} />;
}

Senior Engineer Perspective

The strongest answers explicitly separate "instant, cheap, sync" from "slow, expensive, async" validation concerns and give each its own timing rather than forcing one mechanism to do both. Mentioning that both ultimately converge on the same formState.errors.username — so the rendering code doesn't care which layer produced the error — shows a clean mental model of how RHF's error state aggregates from multiple sources.

Q54. How would you rate-limit or throttle expensive validation calls beyond simple debouncing?

ROI: ★★★☆☆ Frequency: Medium

Short Answer

Debouncing handles "wait until they pause typing"; for a genuinely expensive backend check you may additionally want a minimum interval between calls regardless of pausing pattern (throttling), a client-side cache of recent results (so retyping an already-checked value is free), and/or server-side rate limiting as the actual enforcement layer — client-side measures are only ever a courtesy, not a guarantee.

Detailed Answer

Debounce and throttle solve different problems: debounce delays until activity stops (good for "user finished typing"), throttle caps the rate regardless of activity pattern (good for "never call this more than once per second even during continuous typing/scrolling"). For validation specifically, debounce is almost always the right primary tool since you genuinely want to wait for a pause; throttling matters more for continuous-input scenarios like drag-based or scroll-triggered validation, which is rarer for forms.

A results cache (a simple Map keyed by value, or a query library's built-in cache) means a user who types "john", deletes to "jo", then retypes "john" doesn't trigger a second network call — the second occurrence resolves instantly from cache. And because any client-side limiting can be bypassed by a modified client hitting the API directly, the actual protection against abuse belongs on the server as rate limiting, independent of what the form does.

Code Example

const cache = new Map<string, boolean>();

async function checkUsernameCached(value: string): Promise<boolean> {
  if (cache.has(value)) return cache.get(value)!; // instant, no network call
  const { available } = await fetch(`/api/username-available?u=${value}`).then((r) => r.json());
  cache.set(value, available);
  return available;
}
// A query library's default cache (staleTime/gcTime) gives you this for free.

Senior Engineer Perspective

The key distinction to draw unprompted is debounce vs throttle vs cache — three related but different tools that candidates frequently conflate. Also valuable: explicitly noting that client-side rate limiting is a UX/cost optimization, never a security control, and that real abuse prevention belongs server-side.

Q55. How do you test asynchronous, debounced validation logic without flaky, timing-dependent tests?

ROI: ★★★★☆ Frequency: High

Short Answer

Use fake timers (jest.useFakeTimers()/vi's equivalent) to deterministically advance past the debounce delay instead of real setTimeout waits, mock the network layer (MSW) so responses are controlled and instant, and use Testing Library's waitFor/findBy* to await the resulting UI state rather than a fixed sleep.

Detailed Answer

Real timers make tests slow (you have to actually wait out the debounce) and flaky (CI machines under load can miss tight timing windows). Faking timers and explicitly advancing them (jest.advanceTimersByTime(400)) makes the debounce deterministic and instant in test time. Combined with user-event's own timer-advancement helpers or wrapping advances in act(), you can simulate "type, wait past debounce, assert the network call fired" without any real delay.

Mock Service Worker (MSW) intercepting the actual network call (rather than mocking the module that wraps fetch) keeps tests closer to reality and reusable across unit and integration levels. Assertions should target user-visible outcomes (an error message appearing, a spinner disappearing) via findByText/waitFor, which poll until the condition is true or a timeout elapses — this avoids both fixed-sleep flakiness and depending on internal implementation details.

Code Example

import { render, screen, waitFor } from "@testing-library/react";
import userEvent from "@testing-library/user-event";

test("shows 'taken' after debounce resolves", async () => {
  jest.useFakeTimers();
  const user = userEvent.setup({ advanceTimers: jest.advanceTimersByTime });
  render(<SignupForm />);

  await user.type(screen.getByLabelText(/username/i), "john");
  jest.advanceTimersByTime(400); // deterministically skip the debounce wait

  await waitFor(() => expect(screen.getByText(/already taken/i)).toBeInTheDocument());
  jest.useRealTimers();
});

Senior Engineer Perspective

Teams that skip fake timers here usually end up with a "sometimes fails in CI" test suite. Naming fake timers plus MSW as the pairing, and waitFor/findBy* over arbitrary sleeps, shows this was learned from an actual flaky-test incident rather than textbook knowledge.

Q56. How do you handle a validation dependency chain where field B's validity depends on field A's async result?

ROI: ★★★☆☆ Frequency: Medium

Short Answer

Store field A's async result (not just its raw value) in state the form can read, make field B's validation depend on that resolved result rather than re-deriving it, and re-trigger field B's validation (trigger("fieldB")) whenever field A's result changes — don't let field B silently validate against a stale or still-pending upstream result.

Detailed Answer

A concrete example: a "country" field triggers an async fetch of valid states/provinces, and a "state" field's validity (is this a real state for the selected country?) depends on that fetch's result. The dependency should flow through resolved data, not the raw country string — field B's validate function needs access to the current fetched list, typically via a query's cache or a piece of shared state both fields can read.

Whenever field A changes, field B's previous value is likely now invalid (a state that belonged to the old country) — explicitly clear or re-validate field B (resetField("state") or trigger("state")) rather than leaving a stale, no-longer-applicable value sitting there showing an outdated error/non-error. This is essentially a manual "watch and cascade" pattern: watching A, and reacting to changes by both refetching B's dependent data and re-validating/resetting B.

Code Example

function CountryStateFields() {
  const { control, resetField, trigger } = useFormContext<AddressForm>();
  const country = useWatch({ control, name: "country" });

  const { data: states } = useQuery({
    queryKey: ["states", country],
    queryFn: () => fetchStates(country),
    enabled: !!country,
  });

  const prevCountry = React.useRef(country);
  React.useEffect(() => {
    if (prevCountry.current !== country) {
      resetField("state");       // old state is no longer meaningful
      prevCountry.current = country;
    }
  }, [country, resetField]);

  return (
    <Controller
      name="state"
      control={control}
      rules={{ validate: (v) => !states || states.includes(v) || "Invalid state for country" }}
      render={({ field }) => <StateSelect {...field} options={states ?? []} />}
    />
  );
}

Senior Engineer Perspective

The trap is leaving field B's stale value in place after field A changes, silently passing or failing validation against data that no longer applies. Naming the explicit reset-on-upstream-change step, not just "watch and re-validate," is what shows this pattern was actually built and debugged rather than reasoned about abstractly.

Q57. How do you build an accessible required-field indicator that also works for screen reader users, not just visually?

Short Answer

Detailed Answer

A common but incomplete pattern is <label>Email *</label> with the asterisk styled red — sighted users infer "required," but a screen reader just reads "Email star" with no semantic meaning attached, and a user with color-vision deficiency gets no signal from the color alone. Q59. How do you manage focus when a modal form opens and closes — focus trapping and focus restoration?

ROI: ★★★★☆ Frequency: High

Short Answer

On open, move focus into the modal (typically its first focusable element or a heading) and trap Tab navigation so it cycles only within the modal's contents; on close, restore focus to the element that triggered the modal. Use a maintained library (Radix, React Aria, or the native <dialog> element) rather than hand-rolling the trap logic, which has many easy-to-miss edge cases.

Detailed Answer

Three distinct behaviors are required for an accessible modal: (1) focus moves into the modal on open, so a keyboard/screen-reader user isn't left focused on a now-hidden trigger button; (2) Tab and Shift+Tab cycle only among the modal's focusable elements (a "focus trap") so the user can't tab out into the obscured background content; (3) on close, focus returns to the element that opened the modal, so the user's keyboard position isn't lost.

The native <dialog> element with showModal() now handles much of this natively in modern browsers (focus moves in, Escape closes, background is inert), which is why it's an increasingly common recommendation over a hand-rolled div-based modal. Headless UI libraries (Radix's Dialog, React Aria's useDialog) implement all three behaviors correctly across browsers and are the pragmatic choice for anything beyond the simplest case — hand-rolled focus traps routinely miss edge cases like dynamically added focusable elements or nested modals.

Code Example

function useModalFocus(isOpen: boolean) {
  const modalRef = React.useRef<HTMLDivElement>(null);
  const previouslyFocused = React.useRef<HTMLElement | null>(null);

  React.useEffect(() => {
    if (isOpen) {
      previouslyFocused.current = document.activeElement as HTMLElement;
      modalRef.current?.querySelector<HTMLElement>("[autofocus], input, button")?.focus();
    } else {
      previouslyFocused.current?.focus(); // restore focus to the trigger
    }
  }, [isOpen]);

  return modalRef;
}
// In practice: prefer <dialog>.showModal() or Radix/React Aria's Dialog,
// which implement the trap + restoration correctly out of the box.

Senior Engineer Perspective

A candidate who says "I'd use Radix/React Aria's Dialog rather than build the trap myself" is showing good judgment, not a lack of depth — hand-rolled focus traps are a well-known source of subtle accessibility bugs. Still being able to explain what the three behaviors are (trap in, cycle within, restore on close) demonstrates you understand what the library is actually doing for you.

Q60. How do you announce a successful form submission to screen reader users, given there's often no page navigation to signal success?

Render the success message inside a live region (role="status" or aria-live="polite") so assistive tech announces it automatically when it appears, and also move focus to the message (or a logical next heading) if the surrounding content changes substantially — a purely visual toast that appears and fades is invisible to a screen reader user with no other signal.

Detailed Answer

In a traditional multi-page form, a full page navigation to a "Thank you" page is itself a de facto success announcement — the screen reader announces the new page's title/heading. In an SPA where the form stays mounted and a toast or inline message appears instead, that content change is silent to assistive tech unless it's inside a live region, since live regions are the mechanism that tells screen readers "announce this content whenever it changes," independent of focus.

role="status" (equivalent to aria-live="polite") is right for non-urgent confirmations, giving the current announcement time to finish before interrupting; reserve role="alert" (assertive) for errors that genuinely need immediate attention. If the success state replaces the form entirely (e.g. the form area now shows a confirmation card), also consider moving focus to that new content's heading so keyboard users land somewhere sensible rather than on a now-removed input.

      )}

}

Q61. How would you make a custom multi-select or combobox component (not a native select) accessible?

The ARIA combobox pattern is one of the more error-prone patterns to hand-roll correctly: it requires precise coordination between DOM structure (input, an associated listbox, option elements), ARIA attributes that must update in lockstep with the visual state (aria-expanded when the popup opens, aria-activedescendant as arrow keys move the highlight, without moving actual DOM focus off the input), and keyboard handling for opening/closing, navigating options, selecting, and typing to filter — all while remaining screen-reader-testable across NVDA/JAWS/VoiceOver, which have historically had inconsistent combobox support.

Q63. How do you build an accessible error summary at the top of a long form that links down to each invalid field?

ROI: ★★★☆☆ Frequency: Medium

Short Answer

On a failed submit, render a summary region (role="alert" or a focus-managed heading) listing each error as a link (<a href="#fieldId">) that moves focus to the corresponding field when activated, and move focus to the summary itself immediately after the failed submit so screen reader and keyboard users land somewhere that describes what went wrong.

Detailed Answer

For long forms, per-field inline errors alone force a screen reader user to tab through the entire form to discover every problem — a summary gives them the full picture up front, in one place, similar to how sighted users can visually scan the whole page for red text at a glance. Each summary entry should be a real focusable link (or button) whose activation moves focus into the specific offending field — an href="#email" anchor works if the input has a matching id, or a click handler calling .focus() on a ref works equally well and avoids a URL hash side effect.

Move focus to the summary container itself right after a failed submit attempt (give it tabIndex={-1} so it's programmatically focusable even though it's not naturally interactive) so screen reader users are told immediately, rather than having focus remain on the submit button with no signal that anything happened. This pairs naturally with RHF's errors object — build the list by mapping over its keys.

Code Example

function ErrorSummary({ errors }: { errors: FieldErrors }) {
  const ref = React.useRef<HTMLDivElement>(null);
  const entries = Object.entries(errors);

  React.useEffect(() => {
    if (entries.length) ref.current?.focus(); // announce + move focus on failed submit
  }, [entries.length]);

  if (!entries.length) return null;
  return (
    <div ref={ref} tabIndex={-1} role="alert" aria-labelledby="error-summary-heading">
      <h2 id="error-summary-heading">Please fix the following:</h2>
      <ul>
        {entries.map(([name, error]) => (
          <li key={name}>
            <a href={`#${name}`} onClick={() => document.getElementById(name)?.focus()}>
              {error?.message as string}
            </a>
          </li>
        ))}
      </ul>
    </div>
  );
}

Senior Engineer Perspective

The differentiator is the focus-management detail — merely rendering a list of error text is a half-measure. Explicitly moving focus to the summary container itself on a failed submit (with a tabIndex={-1} trick, since it's not a naturally focusable element) is the part that makes the pattern actually work for screen reader and keyboard-only users, not just visually.

Q64. What accessibility issues are specific to touch and mobile forms — viewport zoom, input types, and autocomplete attributes?

ROI: ★★★☆☆ Frequency: Medium

Short Answer

Never disable pinch-zoom (avoid user-scalable=no / maximum-scale=1 in the viewport meta tag, which is a WCAG failure for low-vision users), use the correct type/inputmode per field so mobile keyboards show the right layout (numeric, email, tel), and set autocomplete attributes so browsers/password managers can autofill correctly — all of which are accessibility and usability wins simultaneously on mobile.

Detailed Answer

Disabling zoom to "prevent layout issues on focus" is a common but explicit WCAG 1.4.4 (Resize Text) violation and actively harms low-vision users who rely on pinch-zoom to read small text — the correct fix for the underlying problem (iOS auto-zooming on input focus) is ensuring inputs have a font-size of at least 16px, not disabling zoom outright.

Correct type/inputmode pairing reduces the taps needed to enter data and reduces input errors: type="email" surfaces an @ key, type="tel" or inputmode="numeric" surfaces a number pad, and type="text" inputmode="numeric" is the right choice for numeric-but-not-phone data like a card CVV, since type="number" itself brings unwanted spinner UI and awkward behavior for things like credit card numbers where leading zeros or non-arithmetic values matter. autocomplete values ("email", "tel", "cc-number", "current-password", "new-password") let password managers and the OS autofill correctly and are themselves an accessibility win for users with motor or cognitive disabilities who benefit most from not re-typing information.

Q65. How do you implement drag-and-drop file uploads with visual feedback for the drag-over state?

ROI: ★★★★☆ Frequency: High

Short Answer

Handle onDragEnter/onDragOver/onDragLeave/onDrop on a drop-zone container, calling e.preventDefault() on the drag events (the browser's default is to navigate to/open the dropped file, which must be suppressed), track a boolean for "is something being dragged over" to drive styling, and read files from e.dataTransfer.files on drop — while still rendering a real, keyboard-accessible file input as the non-drag-and-drop fallback.

Detailed Answer

Drag-and-drop needs several event handlers coordinated: onDragOver must call preventDefault() continuously (not just once) for onDrop to fire at all — this trips up many first implementations. onDragEnter/onDragLeave toggle the visual "drop here" state, but naive implementations flicker because these fire on every child element too; a common fix is tracking a counter (increment on enter, decrement on leave, active only when count > 0) rather than a plain boolean.

Drag-and-drop is inherently mouse/pointer-only — it has no native keyboard equivalent — so the drop zone must always additionally contain a real, visible-or-accessible <input type="file"> (a "click or drag" pattern) so keyboard and screen-reader users have an equally functional path, not a degraded one.

Code Example

function Dropzone({ onFiles }: { onFiles: (files: FileList) => void }) {
  const [dragCount, setDragCount] = React.useState(0);
  const inputRef = React.useRef<HTMLInputElement>(null);

  return (
    <div
      onDragEnter={(e) => { e.preventDefault(); setDragCount((c) => c + 1); }}
      onDragLeave={(e) => { e.preventDefault(); setDragCount((c) => c - 1); }}
      onDragOver={(e) => e.preventDefault()} // required for onDrop to fire
      onDrop={(e) => {
        e.preventDefault();
        setDragCount(0);
        onFiles(e.dataTransfer.files);
      }}
      data-active={dragCount > 0}
      onClick={() => inputRef.current?.click()}
    >
      Drag files here, or click to browse
      <input
        ref={inputRef}
        type="file"
        multiple
        style={{ position: "absolute", width: 1, height: 1, opacity: 0 }} // visually hidden, still focusable
        onChange={(e) => e.target.files && onFiles(e.target.files)}
      />
    </div>
  );
}

Senior Engineer Perspective

Two concrete tells: knowing onDragOver must call preventDefault() or the drop never fires, and knowing plain enter/leave booleans flicker on child elements without a counter. The accessibility framing — drag-and-drop is a bonus affordance layered on top of a always-present real file input, never a replacement for it — is the detail that shows product maturity beyond just making the demo work with a mouse.

Q66. How do you show upload progress for multiple files uploading in parallel?

ROI: ★★★☆☆ Frequency: Medium

Short Answer

Track progress per file in a keyed state object (file id/name to percent), update each entry independently from its own upload's progress event, and render one progress bar per file from that map — native fetch can't report upload progress, so use XMLHttpRequest's upload.onprogress (or a library like axios that wraps it) per file.

Detailed Answer

Each file's upload is an independent request with its own progress stream; the state shape should reflect that (a Record<string, number> or an array of { id, progress, status }) rather than one aggregate percentage, which loses information about which specific file is slow or has failed. Kick off all uploads concurrently (or with a small concurrency limit if there are many files, to avoid saturating the connection) and update only that file's entry as its own onprogress fires — this naturally keeps re-renders scoped if each file's progress bar is its own memoized component keyed by file id.

Handle partial failure explicitly: with several files uploading in parallel, some can succeed while others fail (network blip, server rejects one file's type) — the UI needs a per-file status (pending/uploading/done/error), not just a single boolean for the whole batch, and typically a retry action scoped to just the failed file(s).

Code Example

type UploadState = { progress: number; status: "uploading" | "done" | "error" };

function useMultiUpload() {
  const [uploads, setUploads] = React.useState<Record<string, UploadState>>({});

  const uploadFile = (file: File) => {
    const id = `${file.name}-${file.size}`;
    setUploads((u) => ({ ...u, [id]: { progress: 0, status: "uploading" } }));

    const xhr = new XMLHttpRequest();
    xhr.upload.onprogress = (e) => {
      if (e.lengthComputable) {
        const pct = Math.round((e.loaded / e.total) * 100);
        setUploads((u) => ({ ...u, [id]: { progress: pct, status: "uploading" } }));
      }
    };
    xhr.onload = () => setUploads((u) => ({ ...u, [id]: { progress: 100, status: "done" } }));
    xhr.onerror = () => setUploads((u) => ({ ...u, [id]: { progress: 0, status: "error" } }));

    const body = new FormData();
    body.append("file", file);
    xhr.open("POST", "/api/upload");
    xhr.send(body);
  };

  return { uploads, uploadFile };
}

Q67. How do you validate file type and size before upload, including checking actual file content rather than just the extension?

ROI: ★★★★☆ Frequency: High

Short Answer

Check file.size against a max and file.type (the browser-reported MIME type) against an allow-list immediately client-side for fast feedback, but treat both as UX only — a renamed file or spoofed MIME type sails through client checks trivially, so the server must independently verify content (e.g. by inspecting magic bytes / using a library that sniffs real file type) regardless of what the client claims.

Detailed Answer

accept="image/*" on the input is a UI filter for the OS file picker, not a validation mechanism — a user (or a script driving the input programmatically) can still supply a non-matching file. file.type is the browser's best guess based on the extension/OS association and is trivially wrong or spoofable (renaming malware.exe to photo.jpg can make file.type report image/jpeg in some cases) — it's a reasonable first UX filter but never a security boundary.

Real content verification requires either reading the file's initial bytes client-side (checking magic numbers — a JPEG starts with FF D8 FF, a PNG with a fixed 8-byte signature) for slightly stronger client-side UX, or — the only approach that's actually trustworthy — having the server open and sniff the uploaded file's real content with a dedicated library before accepting it, independent of any client-supplied metadata. Size limits should also be enforced server-side (and ideally at a reverse proxy/CDN layer too) since a client-side size check is just as bypassable as the type check.

Code Example

const MAX_SIZE = 5 * 1024 * 1024;
const ALLOWED_TYPES = ["image/jpeg", "image/png", "image/webp"];

function validateFile(file: File): string | null {
  if (file.size > MAX_SIZE) return "File is too large (max 5MB)";
  if (!ALLOWED_TYPES.includes(file.type)) return "Unsupported file type";
  return null; // client-side UX check only — server must re-verify
}

// Slightly stronger client check: read the magic bytes
async function looksLikeJpeg(file: File): Promise<boolean> {
  const buffer = await file.slice(0, 3).arrayBuffer();
  const bytes = new Uint8Array(buffer);
  return bytes[0] === 0xff && bytes[1] === 0xd8 && bytes[2] === 0xff;
}

Senior Engineer Perspective

The load-bearing sentence here is "client-side file validation is UX, never security" — candidates who present accept/file.type checks as sufficient are missing a real security gap (uploaded-file validation bypass is a common finding in security reviews). Q68. How would you implement direct-to-storage (presigned URL) uploads instead of routing files through your application server?

ROI: ★★★★☆ Frequency: High

Short Answer

Have your app server generate a short-lived, scoped presigned upload URL (e.g. S3's PutObject presigned URL) for a specific object key, return it to the client, and have the browser PUT/POST the file directly to storage using that URL — your server never touches the file's bytes, only issues and later confirms the upload, which removes a large bandwidth/memory bottleneck from your app tier.

Detailed Answer

Routing every file through your app server means your server's request handling capacity, memory, and bandwidth all scale with upload volume and file size — a real bottleneck for anything beyond small, infrequent uploads. Presigned URLs flip the flow: the client asks your server "I want to upload a file named X of type Y," your server (with credentials the client never sees) generates a time-limited, permission-scoped URL authorizing exactly that upload, and the browser then talks directly to the storage provider.

The server still needs to be in the loop at two points for correctness and security: issuing the presigned URL (where you can enforce naming conventions, size limits via presigned POST policies, and content-type restrictions), and afterward confirming/registering the completed upload (since the client could abandon the upload, or you want a database record only once the file genuinely exists) — often via a webhook from the storage provider or a client-side "confirm complete" call the server double-checks by querying the object's existence.

Code Example

// Server: issue a scoped, short-lived presigned URL
app.post("/api/uploads/presign", async (req, res) => {
  const key = `uploads/${req.user.id}/${crypto.randomUUID()}-${req.body.filename}`;
  const url = await s3.getSignedUrlPromise("putObject", {
    Bucket: "my-app-uploads",
    Key: key,
    ContentType: req.body.contentType,
    Expires: 60, // seconds
  });
  res.json({ url, key });
});

// Client: upload directly to storage, bypassing the app server
async function uploadDirect(file: File) {
  const { url, key } = await fetch("/api/uploads/presign", {
    method: "POST",
    body: JSON.stringify({ filename: file.name, contentType: file.type }),
  }).then((r) => r.json());

  await fetch(url, { method: "PUT", body: file, headers: { "Content-Type": file.type } });
  await fetch("/api/uploads/confirm", { method: "POST", body: JSON.stringify({ key }) });
}

Senior Engineer Perspective

The follow-up interviewers reach for is "how do you stop someone using a stolen presigned URL to upload something else, or an oversized file?" — the answer is scoping the URL tightly (fixed key, content-type, and, for S3, a presigned POST policy with a size range) and treating the "confirm" step as mandatory rather than trusting the client's word that the upload succeeded and was legitimate.

Q69. How would you implement resumable or chunked uploads for very large files?

ROI: ★★★☆☆ Frequency: Medium

Short Answer

Split the file into fixed-size chunks client-side (File.slice()), upload each chunk with its index and a session/upload id, track which chunks have been acknowledged so an interrupted upload can resume from the first missing chunk rather than restarting, and have the server reassemble (or use a storage provider's native multipart-upload API, e.g. S3 multipart upload) once all chunks arrive.

Detailed Answer

For files where a full re-upload after any network blip is unacceptable (large video files, on flaky mobile connections), the file is divided into chunks (commonly 5-10MB) up front, and an "upload session" is created server-side to track progress across chunk uploads which can happen in any order and be retried independently. On resume (after a page reload or a network drop), the client asks the server which chunk indices it has already received and only (re-)sends the missing ones, rather than restarting from byte zero.

Rather than hand-rolling this protocol, most storage providers have a native multipart-upload primitive (S3 Multipart Upload, GCS resumable uploads) purpose-built for exactly this, handling chunk reassembly and partial-failure retry server-side — and there are also open, provider-agnostic protocols (tus.io) with mature client libraries (tus-js-client) if you want resumability without being tied to one cloud provider's specific API.

Code Example

const CHUNK_SIZE = 8 * 1024 * 1024; // 8MB

async function uploadInChunks(file: File, uploadId: string) {
  const totalChunks = Math.ceil(file.size / CHUNK_SIZE);
  const { uploadedChunks } = await fetch(`/api/uploads/${uploadId}/status`).then((r) => r.json());

  for (let i = 0; i < totalChunks; i++) {
    if (uploadedChunks.includes(i)) continue; // already received — skip on resume
    const chunk = file.slice(i * CHUNK_SIZE, (i + 1) * CHUNK_SIZE);
    await fetch(`/api/uploads/${uploadId}/chunk/${i}`, { method: "PUT", body: chunk });
  }
  await fetch(`/api/uploads/${uploadId}/complete`, { method: "POST" });
}
// In practice: prefer S3 multipart upload, GCS resumable uploads, or tus.io
// over hand-rolling this protocol end-to-end.

Senior Engineer Perspective

The mature framing is "I'd reach for a provider's native multipart API or tus.io before hand-rolling a chunking protocol" — this is a well-solved problem with real edge cases (concurrent chunk uploads, partial chunk corruption, cleanup of abandoned sessions) that a bespoke implementation is likely to get subtly wrong. Knowing the resume-by-querying-uploaded-chunks mechanism is still worth being able to describe conceptually.

Q70. How do you preview an image before upload, and how do you avoid leaking memory from the preview mechanism?

ROI: ★★★☆☆ Frequency: Medium

Short Answer

Create a preview URL with URL.createObjectURL(file) and set it as an <img>'s src; critically, call URL.revokeObjectURL(url) once the preview is no longer needed (the file changes, or the component unmounts) — object URLs are not automatically garbage-collected and will otherwise leak memory for the page's lifetime.

Detailed Answer

createObjectURL registers a reference to the in-memory file data under a synthetic blob: URL that the browser keeps alive until you explicitly revoke it or the document is unloaded — unlike normal DOM garbage collection, the browser can't tell on its own when you're "done" with it. A form that lets users pick, preview, and swap several images in a row without revoking each previous URL steadily accumulates retained memory for the lifetime of the page/tab.

The correct lifecycle is a useEffect that creates the object URL when the file changes and returns a cleanup function that revokes it — this handles both "user selected a different file" (effect re-runs, previous URL is revoked) and "component unmounts" (cleanup fires) uniformly. An alternative for smaller files is FileReader.readAsDataURL, producing a base64 data URI instead of a blob URL — no explicit revocation needed, but noticeably heavier in memory and less efficient for larger images.

Code Example

function ImagePreview({ file }: { file: File | null }) {
  const [previewUrl, setPreviewUrl] = React.useState<string | null>(null);

  React.useEffect(() => {
    if (!file) { setPreviewUrl(null); return; }
    const url = URL.createObjectURL(file);
    setPreviewUrl(url);
    return () => URL.revokeObjectURL(url); // release on file change or unmount
  }, [file]);

  if (!previewUrl) return null;
  return <img src={previewUrl} alt="Selected file preview" width={120} />;
}

Senior Engineer Perspective

The "browsers don't auto-garbage-collect object URLs" fact is a genuine, non-obvious memory leak source that shows up in profiler sessions on long-lived SPAs with repeated file selection. Pairing createObjectURL with its useEffect cleanup unprompted is the concrete signal that this was learned from a real memory-profiling session, not just API familiarity.

Q71. How do you handle a form that submits both regular fields and a file upload together in one request?

ROI: ★★★☆☆ Frequency: Medium

Short Answer

Build a single FormData object, append both the plain field values and the file(s) to it, and send it as the request body with multipart/form-data (which the browser sets automatically when you don't manually specify Content-Type) — RHF's handleSubmit gives you the plain fields and the FileList together in one submit payload, ready to be assembled this way.

Detailed Answer

Because RHF treats a <input type="file"> as just another registered field, handleSubmit's data object naturally includes both text fields and the file(s) as one shape — you don't need a second, separate submit flow. The submit handler's job is converting that combined object into a FormData instance: append plain values as strings (or JSON.stringify a nested object under one key if the server expects structured non-file data as JSON alongside files), and append each file directly, which FormData knows how to serialize correctly as a file part.

Watch two details: never manually set the Content-Type header when sending FormData — the browser needs to generate the multipart boundary string itself, and overriding the header removes it; and if the server expects the non-file fields as a single JSON blob (common in some frameworks) rather than flat form fields, append that as one FormData entry containing the stringified JSON, read and parsed separately from the file parts on the server.

type ProfileForm = { displayName: string; bio: string; avatar: FileList };

Q73. Walk through migrating a mid-size Formik form to React Hook Form, step by step.

Detailed Answer

A safe migration order: (1) keep the existing Yup schema and wire it in via yupResolver so validation behavior doesn't change yet — this isolates the migration to the state-management layer first; (2) replace each native <Field name="x" /> with a plain <input {...register("x")} />; (3) for any field wrapping a UI-library component that Formik's <Field as={CustomInput}> handled, switch to Controller; (4) replace <FieldArray> with useFieldArray, watching for the array index vs stable-id key change (Q12); (5) replace isSubmitting/touched/errors reads from Formik's render props with the equivalent RHF formState fields; (6) once the form behaves identically, optionally swap the Yup schema for Zod as a separate follow-up change.

Migrate form-by-form in a codebase with many forms, starting with the highest-traffic or most-complained-about-performance form to get an early, visible win, rather than attempting every form in one PR — form libraries touch enough surface area that a big-bang migration is high-risk for low incremental benefit.

Q74. How does Formik's Field/FieldArray API compare structurally to RHF's register/useFieldArray?

ROI: ★★★☆☆ Frequency: Medium

Short Answer

Formik's <Field> is a component that reads/writes Formik's controlled state via context, rendering a native input by default or a custom component via its as/render-prop form; RHF's register is a function returning props you spread onto an uncontrolled input directly, with no context subscription for the plain case. <FieldArray> vs useFieldArray is the same component-vs-hook, controlled-vs-uncontrolled contrast applied to arrays.

Detailed Answer

Formik's <Field> being a component (not a hook) fits its era — it predates hooks being idiomatic — and works by reading/writing to Formik's context-provided state on every keystroke, which is why every <Field> re-renders alongside the rest of the controlled form. <FieldArray> similarly renders a component whose children receive helper functions (push, remove, swap) as render props, operating on the same controlled array state.

register/useFieldArray are hooks returning plain data/functions with no rendering of their own — register's returned object is spread directly onto whatever native element you render, and useFieldArray's fields/append/remove operate against RHF's uncontrolled, ref-based internal store. The net effect is the same author-facing capability (bind a field, manage an array), but Formik's approach necessarily re-renders through its component tree on each change while RHF's does not.

Q76. How do render performance characteristics actually differ under the hood between Formik and RHF, and why does Formik re-render more?

ROI: ★★★★☆ Frequency: High

Short Answer

Formik stores all values, touched, and errors in React state owned by the <Formik> component (or the object useFormik returns), so any keystroke updates that state and re-renders the entire form subtree via context, same as any controlled form. RHF stores values in an internal mutable ref-backed store outside React state, updates the DOM directly for uncontrolled fields, and only triggers a React re-render for the specific subscribers (via the formState proxy, watch/useWatch subscriptions) that actually need to reflect a given change.

Detailed Answer

Formik's context-based sharing means every <Field> consuming that context is a candidate for re-render whenever the context value changes, and because values/errors/touched typically live together in one state object, changing any one of them changes the whole context value's reference — even libraries with fine-grained context selectors still fundamentally start from "state lives in React and a change re-renders consumers."

RHF's architecture inverts this: the source of truth for a value is the DOM node itself (read via the registered ref) for the common case, and RHF's job is mostly bookkeeping — tracking which components have subscribed to which pieces of state via the Proxy-based formState and the watch/useWatch mechanisms — and notifying only those subscribers. This is why a 50-field RHF form typing in field #30 causes zero avoidable re-renders elsewhere, while the equivalent Formik form re-renders the whole tree (mitigated only by manual React.memo on each field, which RHF needs less of by default).

// RHF: values live outside React state, DOM is the source of truth

Q78. How do TypeScript ergonomics compare between Formik and React Hook Form for a complex, deeply nested form?

Formik's typing is workable but weaker in this specific respect — <Field name="a.b.c">'s name is typically just a plain string with no compile-time link back to your values' actual shape, so a typo or a renamed field silently fails at runtime instead of red-squiggling in the editor.

Detailed Answer

Q80. What other form libraries exist besides Formik and React Hook Form — TanStack Form, Final Form, Conform — and how do they differ philosophically?

ROI: ★★★☆☆ Frequency: Medium

Short Answer

Final Form (React Final Form) is a subscription-based, framework-agnostic core with a React binding, philosophically similar in spirit to RHF's "subscribe, don't re-render everything" goal but with a different API shape and less current momentum. TanStack Form is a newer, type-safe, framework-agnostic library from the TanStack family (Query, Table) aiming for best-in-class TypeScript inference and fine-grained reactivity across React/Vue/Solid/Angular. Conform is built specifically around React 19's native form actions and progressive enhancement, validating on the server by default and working even without JavaScript.

Detailed Answer

Each of these represents a different bet about where the ecosystem is heading. Final Form predates RHF's dominance and shares its subscription-based philosophy but never reached the same adoption; it's mostly seen in codebases that adopted it early and haven't had reason to migrate. TanStack Form leans into the same team's proven pattern from TanStack Query — deep TypeScript generics, framework-agnostic core, opt-in fine-grained subscriptions — and is gaining traction especially in teams already standardized on other TanStack libraries.

Conform is the most philosophically distinct: it's built around the assumption that forms should work via native HTML submission and server-side validation first, with client-side enhancement layered on top rather than assumed — a direct embrace of React/Next.js's server-actions direction (Q16) rather than the client-heavy validation model RHF/Formik both assume. Choosing among these is less about "which is fastest" (most converge on similar performance) and more about which philosophy — client-first uncontrolled forms, framework-agnostic type-safety, or server-first progressive enhancement — matches your app's actual architecture.

  }

}

Q81. How do you build a reusable TextField wrapper component compatible with RHF's Controller, forwarding refs correctly?

Short Answer

Detailed Answer

A design-system input wrapper typically needs to add a label, help text, and error display around a bare <input> — but if it doesn't forward its ref, register's returned ref has nothing to attach to, silently breaking RHF's ability to read/focus that field (a common early bug: "why doesn't setFocus work on my custom field"). forwardRef solves this by letting the wrapper accept a ref from its parent and manually attach it to the actual DOM element it renders.

The component should be usable two ways without extra glue: spread directly with register's output for the simple case (<TextField {...register("email")} />), and equally through Controller's field object when the form needs the controlled path — both ultimately deliver the same ref/onChange/onBlur/value/name shape, so the wrapper doesn't need to know or care which one is feeding it.

Code Example

type TextFieldProps = React.InputHTMLAttributes<HTMLInputElement> & {
  label: string;
  error?: string;
};

const TextField = React.forwardRef<HTMLInputElement, TextFieldProps>(
  ({ label, error, id, ...rest }, ref) => {
    const fieldId = id ?? rest.name;
    return (
      <div>
        <label htmlFor={fieldId}>{label}</label>
        <input
          id={fieldId}
          ref={ref}                         // forwarded all the way to the DOM node
          aria-invalid={!!error}
          aria-describedby={error ? `${fieldId}-error` : undefined}
          {...rest}                          // passes through onChange/onBlur/name from register or Controller
        />
        {error && <span id={`${fieldId}-error`} role="alert">{error}</span>}
      </div>
    );
  }
);

// Usage — works directly with register:
<TextField label="Email" {...register("email")} error={errors.email?.message} />

Q82. How do you design a form-field component's API so it supports both React Hook Form usage and plain controlled usage without a form library?

Detailed Answer

The trap is a component whose API only makes sense wired to RHF (e.g. accepting a name and an internal useController call baked in) — that couples every consumer to RHF even for a simple standalone form, and makes the component unusable in, say, a Storybook story or a non-RHF page. Q84. How do forwardRef and useImperativeHandle help when wrapping a third-party input that needs to expose a custom method, like focus()?

ROI: ★★★☆☆ Frequency: Medium

Short Answer

forwardRef lets your wrapper accept a ref from its parent; useImperativeHandle lets you customize exactly what that ref exposes — instead of forwarding the raw underlying DOM/library instance, you can hand back a curated object (e.g. just { focus, clear }) that hides internal implementation details while still letting RHF (or a parent) imperatively call .focus() on it, such as for error-driven focus management (Q63) on a component that doesn't naturally expose a plain DOM ref.

Detailed Answer

Some third-party inputs (a rich date picker, a custom rich-text editor) don't expose a single focusable DOM node the way a native <input> does — focus might need to move to an internal, nested element. useImperativeHandle lets your wrapper component decide what "the ref" means for consumers: rather than forwarding whatever ref the third-party library gives you as-is, you construct a small handle object with exactly the methods callers need (commonly just focus), internally delegating to whatever the underlying library's actual focus mechanism is.

This matters directly for RHF's setFocus/error-focus-on-submit behavior (Q11, Q63): RHF calls .focus() on the registered ref when it needs to move focus to an invalid field, so if your wrapper's ref doesn't expose a working focus method, that feature silently does nothing for that field even though it works for plain native inputs.

Code Example

type DatePickerHandle = { focus: () => void };

const CustomDatePicker = React.forwardRef<DatePickerHandle, DatePickerProps>(
  (props, ref) => {
    const internalInputRef = React.useRef<HTMLInputElement>(null);

    useImperativeHandle(ref, () => ({
      focus: () => internalInputRef.current?.focus(), // curated, minimal handle
    }));

    return <ThirdPartyDatePicker inputRef={internalInputRef} {...props} />;
  }
);

// RHF's error-focus-on-submit now works correctly on this custom component:
const dateRef = React.useRef<DatePickerHandle>(null);
<CustomDatePicker ref={dateRef} />
// setFocus("date") internally calls dateRef.current.focus()

Q88. How would you version and evolve a shared form-field component library without breaking every consuming form?

Detailed Answer

Because form-field components sit at the base of potentially dozens or hundreds of forms, an unannounced breaking change (a renamed prop, a changed default validation timing, a different error-display shape) can silently break many consuming forms at once, some of which may not have great test coverage to catch it. Automated visual regression testing (Chromatic/Storybook snapshots) or a shared component test suite run against consuming apps in CI catches unintended behavior changes before they ship, which matters more for a widely-shared field library than for an app-local component precisely because the blast radius of a regression is so much larger.

Q89. How do you implement autosave-to-localStorage for a draft form, including debouncing writes and clearing the draft on submit?

ROI: ★★★★☆ Frequency: High

Short Answer

Subscribe to form changes via RHF's callback form of watch, debounce the actual localStorage.setItem write (a few hundred ms) so rapid typing doesn't serialize the whole form on every keystroke, seed the form from the saved draft on mount, and call localStorage.removeItem the moment the form successfully submits so a stale draft never resurfaces.

Detailed Answer

This is the general version of the wizard-specific pattern from Q42, applicable to any long single-page form (a blog post editor, a detailed settings page). The subscription form of watch — const { unsubscribe } = watch(callback) — is preferable to a render-triggering watch() call here because the only purpose is a side effect (writing to storage), not driving UI, so there's no reason to also re-render the component on every change.

On mount, read any existing draft and feed it into the form (via values or a one-time reset) before the user starts interacting, and consider showing an explicit "Restored an unsaved draft from [time]" notice so the behavior isn't invisible/surprising. Clearing the draft key specifically on successful submission (not merely on unmount, since unmounting can also happen from simply navigating away mid-edit, where you still want the draft retained) is the detail that prevents a completed form from nagging the user with a stale "resume?" prompt on their next visit.

Code Example

const DRAFT_KEY = "post-editor-draft";

function usePostDraft(watch: UseFormWatch<PostForm>) {
  React.useEffect(() => {
    let timeoutId: ReturnType<typeof setTimeout>;
    const { unsubscribe } = watch((values) => {
      clearTimeout(timeoutId);
      timeoutId = setTimeout(() => {
        localStorage.setItem(DRAFT_KEY, JSON.stringify(values));
      }, 500);
    });
    return () => { unsubscribe(); clearTimeout(timeoutId); };
  }, [watch]);
}

function loadDraft(): Partial<PostForm> | undefined {
  const raw = localStorage.getItem(DRAFT_KEY);
  return raw ? JSON.parse(raw) : undefined;
}

// On successful submit:
const onSubmit = async (data: PostForm) => {
  await api.savePost(data);
  localStorage.removeItem(DRAFT_KEY); // don't resurface a completed draft
};

Senior Engineer Perspective

The detail interviewers listen for is distinguishing "clear on submit" from "clear on unmount" — clearing on unmount would wrongly discard a legitimate in-progress draft when a user simply navigates away to check something else and intends to come back, which defeats the whole point of the feature.

Q90. How do you avoid persisting sensitive fields — passwords, card numbers — when autosaving form drafts?

ROI: ★★★★☆ Frequency: High

Short Answer

Maintain an explicit deny-list (or, more safely, an allow-list) of field names and strip those out of the values object before serializing to storage — never persist the whole raw form object by default and assume it's fine, since it's easy to add a new sensitive field later and forget to exclude it from an existing autosave routine.

Detailed Answer

An allow-list (explicitly naming which fields are safe to persist) is structurally safer than a deny-list (naming which fields to exclude), because a newly added sensitive field defaults to "not persisted" under an allow-list but defaults to "persisted" under a deny-list until someone remembers to update it — the deny-list approach fails open on exactly the kind of change most likely to be forgotten under time pressure.

Beyond passwords and payment details, consider anything that's PII-adjacent or that the user would be surprised to find sitting in plaintext in their browser's storage indefinitely (SSNs, full dates of birth, security-question answers). For a form that's mostly sensitive fields with only a couple of safe ones, it may be simpler and safer to persist nothing at all and rely purely on a server-side draft (Q47) instead of local storage.

Code Example

// Allow-list: safer default — new fields are NOT persisted unless explicitly added
const PERSISTABLE_FIELDS = ["fullName", "email", "shippingAddress"] as const;

function toSafeDraft(values: CheckoutForm): Partial<CheckoutForm> {
  return PERSISTABLE_FIELDS.reduce((draft, key) => {
    if (values[key] !== undefined) draft[key] = values[key];
    return draft;
  }, {} as Partial<CheckoutForm>);
}

// cardNumber, cvv, ssn etc. are never written to localStorage,
// even if added to CheckoutForm later without updating this list.

Senior Engineer Perspective

Choosing allow-list over deny-list here is the specific, defensible engineering decision — a candidate who says "just exclude the password field" hasn't considered what happens when a card-number field is added six months later by someone unaware the autosave routine exists. Fail-safe defaults are the theme this question is checking for.

Q91. How do you minimize re-renders in a form with 100+ fields — what RHF-specific techniques apply beyond the uncontrolled default?

ROI: ★★★★★ Frequency: Extremely High

Short Answer

Beyond RHF's default uncontrolled behavior: avoid whole-form watch() calls (use scoped useWatch), keep any Controller-wrapped fields to the minimum necessary (each one re-renders like a controlled input), split the form into section-level components so a change in one section can't re-render unrelated sections, and be deliberate about validation mode since onChange validation on a schema-resolved form re-runs the whole schema on every keystroke by default.

Detailed Answer

A large form's real re-render risk isn't typing in a single native input (that's already isolated by RHF's uncontrolled model) — it's usually one of: (1) a top-level watch() call somewhere re-rendering the whole tree on any change; (2) many Controller-wrapped third-party fields, each behaving like a controlled input; (3) schema-based validation re-running against the entire form on every keystroke under an eager mode, which, depending on schema complexity, has real CPU cost even though it doesn't by itself cause extra React renders; and (4) heavy sibling components (a live preview, a chart) re-rendering alongside fields due to shared parent state, independent of RHF's own behavior.

Concrete techniques: componentize by section and pass down only control/register (both stable references) rather than derived values; prefer onBlur or onTouched modes over onChange for forms with expensive schemas; use useWatch scoped to individual subtrees rather than the whole form for any derived UI; and profile with React DevTools before optimizing further, since some "slow form" complaints turn out to be about the schema validation's CPU cost rather than React rendering at all.

Code Example

// Componentize by section — control/register are stable, don't force re-renders
function SettingsForm() {
  const { control, register, handleSubmit } = useForm<Settings>({ mode: "onBlur" });
  return (
    <form onSubmit={handleSubmit(onSubmit)}>
      <AccountSection register={register} />
      <NotificationsSection control={control} />
      <BillingSection register={register} control={control} />
    </form>
  );
}
// Each *Section only re-renders due to its own field subscriptions,
// not because a sibling section's field changed.

Senior Engineer Perspective

The nuance worth surfacing unprompted is that schema-validation CPU cost and React re-render cost are two separate performance concerns that both scale with form size — a candidate who only talks about re-renders and never mentions validation mode/cost is missing half of what actually makes very large RHF forms feel slow in practice.

Q92. How would you virtualize a very long form, or a long field array, for rendering performance?

ROI: ★★★☆☆ Frequency: Medium

Short Answer

Use a windowing library (react-window, TanStack Virtual) to render only the rows currently within (or near) the visible viewport, mapping virtual index back to the actual field-array index for register/Controller calls — the same technique used for any long list, applied carefully so scrolled-out rows' form values aren't lost, since virtualization only affects what's mounted in the DOM, not the underlying data.

Detailed Answer

The key property that makes this safe with RHF specifically: values live in RHF's internal store, not in the DOM nodes themselves in any way that survives unmounting anyway for the uncontrolled model conceptually — but in practice, an uncontrolled input's value genuinely does live in the DOM node until register's ref reads it, so unmounting a row (as virtualization does) before that value is captured would lose it unless you're careful. The safe pattern is ensuring each row's current value is synced into RHF state before it can be unmounted — either by using Controller for virtualized rows (so the value already lives in RHF state, not just the DOM) or by triggering a value read on scroll-out.

In practice, most virtualization-worthy field arrays (hundreds of rows) are also good candidates for pagination or a "load more" pattern instead — showing 500 editable rows at once is often a poor UX choice regardless of the performance question, and paginating the array client-side sidesteps the virtualization-vs-uncontrolled-input tension entirely while usually serving users better.

Code Example

// Safer virtualization: wrap virtualized rows in Controller so values
// live in RHF state proactively, not just in a DOM node that might unmount.
function VirtualizedRow({ index, control }: { index: number; control: Control<FormValues> }) {
  return (
    <Controller
      name={`items.${index}.name`}
      control={control}
      render={({ field }) => <input {...field} />}
    />
  );
}
// Consider pagination/"load more" as a simpler alternative to full virtualization
// for very large editable arrays.

Senior Engineer Perspective

The subtlety this question is fishing for is that virtualizing uncontrolled inputs risks losing values on unmount unless you're deliberate — a candidate who reaches straight for react-window without acknowledging this interaction with RHF's uncontrolled model is missing a real correctness bug, not just a performance nuance. Recommending pagination as a frequently-better alternative also shows good product judgment.

Q93. How do you profile a slow form to find which component or field is causing re-render overhead?

ROI: ★★★★☆ Frequency: High

Short Answer

Use the React DevTools Profiler to record a typing interaction and inspect the flame graph for which components re-rendered and why (it shows the triggering state/props change per component), and cross-check against RHF-specific suspects first — a stray whole-form watch(), an eagerly-validating mode, or heavy sibling components sharing a re-rendering parent — before assuming the form library itself is at fault.

Detailed Answer

The Profiler's "why did this render" information (available per commit) is the fastest way to confirm or rule out a suspicion rather than guessing — recording a single keystroke and looking at which components lit up tells you immediately whether the render is scoped to the field you expect or has spread further than it should. A wide, unexpected commit (many components re-rendering from one keystroke) points toward a shared subscription (a `watch()` at too high a level) rather than RHF's core behavior being at fault, since the uncontrolled default should keep this narrow.

Separately, since schema validation cost (Q91) doesn't show up as a React render in the Profiler at all, also check the browser's Performance tab / a plain console.time around the validation call if typing feels laggy but the Profiler shows minimal render activity — that combination points to CPU-bound validation work, not rendering, as the actual bottleneck, which needs a different fix (simplifying the schema, changing validation mode/timing) than anything render-related.

Q94. How do you handle a form where some fields are expensive to render — like a rich text editor — alongside many cheap fields?

ROI: ★★★★☆ Frequency: High

Short Answer

Isolate the expensive field in its own memoized component wired via Controller, and make sure nothing about typing in the cheap fields causes that component's props to change — React.memo only helps if the props passed to the expensive component are actually stable (same reference) across unrelated renders, which usually means passing control itself (stable) rather than a derived value recomputed each render.

Detailed Answer

A rich text editor (or a chart, a map, a syntax-highlighted code block) re-rendering on every keystroke of an unrelated sibling field is a classic large-form performance complaint, and the root cause is almost always that the editor's wrapping component receives a prop that changes on every parent render — often because the parent itself re-renders due to a `watch()` call or shared state, and the editor's props are recreated (a new inline object/function) each time even if their contents are logically the same.

The fix combines several techniques already covered: keep the parent from re-rendering unnecessarily in the first place (Q91's componentization), wrap the expensive component in React.memo as a second line of defense, and ensure whatever it's passed — typically just control via Controller — is a stable reference rather than a freshly computed value each render. If the editor's own internal typing performance (not React's re-render, but the editor library's own DOM/layout work) is the actual bottleneck, that's a separate problem specific to that library, unrelated to the form.

Code Example

const RichTextField = React.memo(function RichTextField({ control }: { control: Control<PostForm> }) {
  return (
    <Controller
      name="body"
      control={control}
      render={({ field }) => <RichTextEditor value={field.value} onChange={field.onChange} />}
    />
  );
});

function PostForm() {
  const { control, register } = useForm<PostForm>();
  return (
    <form>
      <input {...register("title")} />         {/* typing here shouldn't re-render the editor */}
      <RichTextField control={control} />        {/* control is a stable reference */}
    </form>
  );
}

Q95. How would you implement a native "unsaved changes" browser warning (beforeunload) tied to the form's dirty state, and what are its limitations?

ROI: ★★★☆☆ Frequency: Medium

Short Answer

Register a beforeunload listener that calls event.preventDefault() (and sets event.returnValue for older browser compatibility) only while formState.isDirty is true, and remove the listener once the form is saved/reset — but recognize this only guards full page unload/refresh/tab-close, not in-app client-side route navigation, which needs a separate router-level guard.

Detailed Answer

Browsers deliberately limit what beforeunload can do for security/spam reasons: you cannot set a custom message (all modern browsers show their own generic "Leave site? Changes may not be saved" text regardless of what you put in returnValue), and the handler must be synchronous — you can't await a confirmation or show your own custom modal from inside it. It also does not fire for in-app navigations handled by a client-side router (React Router, Next.js's router) since those don't trigger an actual browser unload — that requires the router's own navigation-blocking API, checked against the same isDirty flag, as a separate mechanism.

Keep the listener attached only while genuinely needed — attaching it unconditionally and just checking isDirty inside the handler is fine and simpler than adding/removing the listener on every dirty-state change, since the check itself is cheap and only matters at the moment of actual unload.

Code Example

function useUnsavedChangesWarning(isDirty: boolean) {
  React.useEffect(() => {
    const handler = (e: BeforeUnloadEvent) => {
      if (!isDirty) return;
      e.preventDefault();
      e.returnValue = ""; // browsers show their own generic text regardless
    };
    window.addEventListener("beforeunload", handler);
    return () => window.removeEventListener("beforeunload", handler);
  }, [isDirty]);
}

// Separately, for in-app navigation (e.g. React Router v6.4+):
// useBlocker(() => isDirty, [isDirty]) — a distinct mechanism from beforeunload.

Senior Engineer Perspective

The tell here is knowing beforeunload and in-app route blocking are two separate mechanisms that must both be wired up for complete coverage — candidates who implement only beforeunload and assume it also covers clicking an in-app "Cancel" link are missing half the actual requirement, a gap that surfaces immediately in QA.

Q96. What long-term architecture would you use for a form with hundreds of conditional fields, such as a dynamic insurance application?

ROI: ★★★★☆ Frequency: High

Short Answer

Model the form as data — a declarative field/section schema (often server-driven, so business rules can change without a client deploy) describing each field's type, visibility conditions, and validation rules — and render it through a generic field-renderer component that interprets that schema, rather than hand-writing hundreds of individual JSX field blocks and conditionals.

Detailed Answer

At the scale of hundreds of conditional fields (common in insurance, tax, and complex regulatory-compliance forms), hand-writing each field's JSX plus its visibility conditional becomes unmaintainable and error-prone — every business rule change requires a code deploy, and it's easy for the rendering condition and the validation condition for the same field to drift out of sync (Q38's problem, multiplied by hundreds of fields). A schema-driven approach — a JSON/config structure describing fields, their types, their visibleWhen conditions, and their validation rules — lets a single generic renderer walk the schema and produce the actual form, with the schema itself as the one place business logic lives.

This pairs naturally with a Zod (or JSON Schema) schema generated from or alongside that same field configuration, so validation and rendering conditions are derived from one source rather than maintained in two places by hand. It also enables non-engineers (product/compliance teams) to adjust field visibility and validation rules by editing configuration rather than requesting code changes for every rule tweak — a common real driver for choosing this architecture in regulated domains specifically.

Code Example

type FieldConfig = {
  name: string;
  type: "text" | "select" | "date";
  label: string;
  visibleWhen?: (values: Record<string, unknown>) => boolean;
  options?: { value: string; label: string }[];
};

const applicationSchema: FieldConfig[] = [
  { name: "hasVehicle", type: "select", label: "Do you own a vehicle?", options: [
    { value: "yes", label: "Yes" }, { value: "no", label: "No" },
  ] },
  { name: "vehicleMake", type: "text", label: "Vehicle make",
    visibleWhen: (values) => values.hasVehicle === "yes" },
  // ...hundreds more, driven from config, possibly fetched from a server
];

function DynamicForm({ schema }: { schema: FieldConfig[] }) {
  const { control, register } = useForm();
  const values = useWatch({ control });
  return (
    <>
      {schema
        .filter((f) => !f.visibleWhen || f.visibleWhen(values))
        .map((f) => <GenericField key={f.name} config={f} register={register} />)}
    </>
  );
}
