SECTION 1 - TS CORE

Q1. What is the difference between interface and type? When do you use each?

ROI: ★★★★★ Frequency: Extremely High

Short Answer

Both describe the shape of a value and are largely interchangeable for objects. interface is open — it supports declaration merging and reads naturally for object/class contracts. type is a general alias — it can name unions, intersections, tuples, primitives and mapped/conditional types, which interfaces cannot. A common team rule: use interface for public object shapes and component props, use type for everything else (unions, function types, utility compositions).

Detailed Answer

What only type can do

A type alias can name any type expression, not just object shapes: unions, tuples, primitives, template literals, and the output of conditional/mapped types. Interfaces are restricted to object and function shapes.

What only interface can do

Interfaces support declaration merging: declaring the same interface name twice merges the members. This is how you augment third-party or global types (e.g. extending Window). Type aliases throw a duplicate-identifier error instead.

Extension

Both compose. Interfaces use extends; types use & (intersection). Interface extends gives slightly better error messages and is cached by the compiler, so for large hot object shapes it can be marginally faster to type-check.

Capabilityinterfacetype
Object / function shapesYesYes
Union / tuple / primitive aliasNoYes
Declaration mergingYesNo
Extend / composeextends&
Mapped / conditional typesNoYes

Code Example

// type can express things interface cannot
type ID = string | number;                 // union
type Point = [number, number];             // tuple
type Handler = (e: MouseEvent) => void;    // function alias

// interface for object/prop shapes + extension
interface ButtonProps {
  label: string;
  onClick: () => void;
}
interface IconButtonProps extends ButtonProps {
  icon: string;
}

// declaration merging — impossible with `type`
interface Window {
  __APP_VERSION__: string;
}
window.__APP_VERSION__ = "1.4.0";

Project Example

In a real app I define component props with interface because IDEs surface them well and other engineers can augment them, but I reach for type when modelling an API response that is a discriminated union (type Result = Success | Failure) or when composing utility types (type FormValues = Partial<User>). Consistency matters more than the choice — pick a convention and lint it.

Senior Engineer Perspective

The interviewer wants to hear that you know the real functional differences (declaration merging, union aliasing) rather than the myth that "interfaces are for objects and types are for primitives" as if it were a hard rule. A classic trap: "Can an interface represent a union?" — no, and if you claim yes you're sunk. Another: performance — extending interfaces is generally faster for the checker than deep intersection chains, which matters in very large codebases but is irrelevant in small ones. Say that nuance out loud.

Q2. Explain union and intersection types. How do they behave differently?

ROI: ★★★★☆ Frequency: High

Short Answer

A union (A | B) means the value is one of the types — you can only access members common to all members until you narrow. An intersection (A & B) means the value satisfies all types at once — it has the combined members. Unions are "either/or"; intersections are "both/and".

Detailed Answer

The counterintuitive part is what happens to object types. With a union of objects, TypeScript only lets you access properties that exist on every branch (the intersection of properties), because it cannot know which branch you hold. To use branch-specific members you must narrow first (see type guards). With an intersection of objects you get the union of properties, since the value must satisfy both shapes simultaneously.

Intersecting incompatible primitives produces never (nothing can be both string and number), which is a subtle source of bugs when composing generics.

Code Example

type A = { id: number; a: string };
type B = { id: number; b: string };

type U = A | B;   // either A or B
type I = A & B;   // both A and B

function useUnion(x: U) {
  x.id;   // OK — common to both
  // x.a; // Error — might be B, which has no `a`
}

function useIntersection(x: I) {
  x.id; x.a; x.b;  // all available
}

// Intersecting incompatible primitives -> never
type Impossible = string & number;  // never

Senior Engineer Perspective

Interviewers probe the object-property surprise because juniors expect a union to expose all properties. The senior insight: a union widens the set of possible values but narrows the guaranteed API, while an intersection does the reverse. This is exactly why props modelled as unions force you to narrow before use — a good feature, not a limitation.

Q3. What is the difference between unknown, any, and never?

ROI: ★★★★★ Frequency: High

Short Answer

any disables type checking entirely — anything is assignable to it and from it, so it silently spreads and defeats the purpose of TS. unknown is the type-safe counterpart: any value is assignable to it, but you cannot use it until you narrow. never is the empty type — a value that can never occur (a function that always throws, or an exhausted union branch).

Detailed Answer

TypeAssign anything TO it?Use it without narrowing?Meaning
anyYesYes (unsafe)Opt out of checking
unknownYesNo — must narrowSafe top type
neverNo (nothing fits)N/AEmpty / impossible

Rule of thumb: prefer unknown at the boundaries of your program (JSON parsing, third-party callbacks, catch clauses in useUnknownInCatchVariables mode) and narrow inward. Use never to enforce exhaustive handling of unions — assign to a never variable in the default case so adding a new union member becomes a compile error.

Code Example

// unknown forces a check before use
function parse(json: string): unknown {
  return JSON.parse(json);
}
const data = parse("{}");
// data.id;                    // Error
if (typeof data === "object" && data !== null && "id" in data) {
  // now narrowed
}

// never for exhaustiveness
type Shape = { kind: "circle"; r: number } | { kind: "square"; s: number };
function area(shape: Shape): number {
  switch (shape.kind) {
    case "circle": return Math.PI * shape.r ** 2;
    case "square": return shape.s ** 2;
    default: {
      const _exhaustive: never = shape; // errors if a new kind is added
      return _exhaustive;
    }
  }
}

Senior Engineer Perspective

Saying "I use unknown instead of any at trust boundaries and lint any to a warning" instantly signals seniority. The never-in-default exhaustiveness trick is a favourite follow-up because it demonstrates you use the type system to catch future bugs, not just current ones. Watch the trap: in TS 4.4+, catch (e) gives unknown, not any — many candidates still write e.message and get burned.

Q4. What is type narrowing and how do you write a user-defined type guard?

ROI: ★★★★☆ Frequency: High

Short Answer

Narrowing is TypeScript refining a broad type to a more specific one within a code branch, using control-flow analysis. Built-in narrowing comes from typeof, instanceof, in, equality checks and truthiness. When those aren't enough you write a type guard: a function whose return type is a type predicate arg is Type.

Detailed Answer

Inside a guarded branch, TypeScript treats the variable as the narrowed type, so branch-specific members become accessible. A user-defined guard returns a boolean but its return annotation is a predicate, which teaches the compiler what a true result implies. This is the safe way to validate unknown data from the network. There is also asserts arg is Type for assertion functions that throw instead of returning a boolean.

Code Example

interface Cat { meow: () => void }
interface Dog { bark: () => void }

// user-defined type guard: return type is a predicate
function isCat(pet: Cat | Dog): pet is Cat {
  return "meow" in pet;
}

function speak(pet: Cat | Dog) {
  if (isCat(pet)) {
    pet.meow();   // narrowed to Cat
  } else {
    pet.bark();   // narrowed to Dog
  }
}

// assertion function variant
function assertString(v: unknown): asserts v is string {
  if (typeof v !== "string") throw new Error("not a string");
}

Senior Engineer Perspective

The danger with hand-written guards is that they are unchecked — the compiler trusts your predicate. If isCat returns true for a dog, TS will happily let you call .meow() and it crashes at runtime. That is why seniors validate with a schema library (Zod, Valibot) that generates both the runtime check and the inferred type from a single source, eliminating drift between the guard and the actual type.

Q5. What is a discriminated union and why is it so useful in React?

ROI: ★★★★★ Frequency: High

Short Answer

A discriminated (tagged) union is a union of object types that all share a common literal-typed field — the "discriminant". Checking that field narrows the whole object automatically. It's the idiomatic way to model mutually exclusive states like loading | success | error so that impossible combinations are unrepresentable.

Detailed Answer

The magic is the shared literal key. When you switch on it, TypeScript narrows to exactly the matching member, exposing only its valid fields. This kills the classic React bug of having isLoading, data and error as independent booleans/values where nothing stops isLoading === true alongside a populated error. With a discriminated union, data simply doesn't exist on the loading branch, so you cannot read it by mistake.

Code Example

type FetchState<T> =
  | { status: "idle" }
  | { status: "loading" }
  | { status: "success"; data: T }
  | { status: "error"; message: string };

function UserView({ state }: { state: FetchState<User> }) {
  switch (state.status) {
    case "idle":
    case "loading":
      return <Spinner />;
    case "success":
      return <Profile user={state.data} />; // data only exists here
    case "error":
      return <Error text={state.message} />;
  }
}

Senior Engineer Perspective

The senior framing is "make illegal states unrepresentable". Interviewers love asking you to critique a component that juggles three separate flags — the strong answer is to collapse them into one discriminated union. Combine it with the never exhaustiveness check from Q3 and you get a component that fails to compile when a new state is added but not handled. Note the discriminant must be a literal type, not string, for narrowing to work — a common mistake.

Q6. What do as const and literal types do, and when do you need them?

ROI: ★★★★☆ Frequency: Medium

Short Answer

A literal type is a single exact value used as a type, e.g. "admin" or 200. By default TypeScript widens literals (const x = "admin" stays "admin", but a property or array element widens to string). as const is a const assertion that freezes a value to its narrowest, readonly, literal form — deeply. It's essential for building discriminant fields, tuple return types, and typed config/enum-like objects.

Detailed Answer

Without as const, an object literal's status: "loading" is inferred as string, breaking discriminated-union narrowing. With it, every property becomes readonly and every value its literal type. It also turns arrays into readonly tuples, which is exactly what custom hooks need to return so destructuring gives correct types per position (see Q10). A frequent pattern is deriving a union type from an object with typeof + keyof, giving you enum-like unions without TS enum (which has runtime cost and awkward semantics).

Code Example

// widening problem
const a = { status: "loading" };       // status: string
const b = { status: "loading" } as const; // status: "loading" (readonly)

// enum-like union without `enum`
const ROLES = ["admin", "editor", "viewer"] as const;
type Role = typeof ROLES[number];  // "admin" | "editor" | "viewer"

const THEME = { light: "#fff", dark: "#000" } as const;
type ThemeKey = keyof typeof THEME; // "light" | "dark"

Senior Engineer Perspective

Interviewers use this to see whether you understand widening — the reason a seemingly correct discriminated union silently fails to narrow. The advanced answer: prefer as const object maps over TypeScript enum because enums emit runtime code, don't tree-shake well, and their numeric variant allows unexpected value assignments. Deriving unions from as const arrays keeps a single source of truth for both runtime iteration and compile-time types.

SECTION 2 - TYPING REACT

Q7. How do you type component props and children? What is ReactNode?

ROI: ★★★★★ Frequency: Extremely High

Short Answer

Define an interface/type for props and annotate the function's parameter directly — you rarely need React.FC anymore. For renderable children use React.ReactNode, which is the broadest "anything React can render" type (elements, strings, numbers, arrays, null, undefined, booleans). Use ReactElement only when you specifically require a single JSX element, and a function type when you use the render-props pattern.

Detailed Answer

The modern convention is to type props explicitly and return JSX, letting TypeScript infer the return type. React.FC fell out of favour because older versions implicitly added children to every component (even those that shouldn't have any), complicated generic components, and made the return type less flexible. In React 18 typings, FC no longer includes implicit children, so if you use it you must declare children yourself — at which point the explicit style is simpler.

ReactNodeAnything renderable (elements, strings, arrays, null…)
ReactElementA single JSX element only
JSX.ElementRoughly the same as ReactElement in practice
(x) => ReactNodeRender-prop / function-as-child

Code Example

interface CardProps {
  title: string;
  footer?: React.ReactNode;      // optional renderable
  children: React.ReactNode;     // declare children explicitly
}

function Card({ title, footer, children }: CardProps) {
  return (
    <section>
      <h2>{title}</h2>
      <div>{children}</div>
      {footer && <footer>{footer}</footer>}
    </section>
  );
}

// PropsWithChildren helper adds children for you
type BoxProps = React.PropsWithChildren<{ padding: number }>;

Senior Engineer Perspective

Expect "why not React.FC?" — the crisp answer is implicit children (pre-18), poor generic support, and enforced return type. Another probe: the difference between ReactNode and ReactElement; using ReactElement where you meant ReactNode rejects valid children like strings and arrays. For extending native elements, mention ComponentPropsWithoutRef<"button"> so your component transparently accepts all real DOM props.

Q8. How do you type useState, useRef, and useReducer?

ROI: ★★★★★ Frequency: Extremely High

Short Answer

useState usually infers from the initial value; provide an explicit generic when the value can be more than the initial type (e.g. useState<User | null>(null)). useRef has two modes: a mutable value ref (useRef<number>(0) → { current: number }) and a DOM ref (useRef<HTMLInputElement>(null) → readonly-ish, may be null). useReducer is typed by annotating the state and action types, ideally with a discriminated union of actions.

Detailed Answer

The useState gotcha is useState(null) or useState([]) — inference gives null or never[], which then rejects real values. Supply the generic. For useRef, if you initialise a DOM ref with null and pass it to a JSX ref attribute, use useRef<HTMLInputElement>(null); the resulting current is HTMLInputElement | null, forcing a null check because the element isn't attached until after render. For a mutable instance variable that you write to, initialise with a real value so current is non-nullable and writable. For useReducer, model actions as a discriminated union so the reducer's switch narrows the payload per action type.

Code Example

// useState — explicit generic when initial value is narrower
const [user, setUser] = useState<User | null>(null);
const [items, setItems] = useState<Item[]>([]);

// useRef — DOM ref (nullable) vs mutable value ref
const inputRef = useRef<HTMLInputElement>(null);
const renderCount = useRef<number>(0); // mutable, current: number
useEffect(() => { inputRef.current?.focus(); }, []);

// useReducer — discriminated union of actions
type State = { count: number };
type Action =
  | { type: "inc"; by: number }
  | { type: "reset" };

function reducer(state: State, action: Action): State {
  switch (action.type) {
    case "inc":   return { count: state.count + action.by };
    case "reset": return { count: 0 };
  }
}
const [state, dispatch] = useReducer(reducer, { count: 0 });

Senior Engineer Perspective

The useRef two-modes distinction separates seniors from juniors: passing null as the initial value makes current read-only for DOM refs but nullable, whereas a non-null initial value yields MutableRefObject. Interviewers may ask why current is nullable for DOM refs — because the ref is populated after commit, so you must guard with ?.. For reducers, the discriminated-union action type is the "correct" answer; a loose { type: string; payload?: any } throws away all safety.

Q9. How do you type event handlers in React?

ROI: ★★★★☆ Frequency: High

Short Answer

Use React's synthetic event generics, parameterised by the element that fires them: React.ChangeEvent<HTMLInputElement>, React.MouseEvent<HTMLButtonElement>, React.FormEvent<HTMLFormElement>, React.KeyboardEvent, and so on. If you write the handler inline in JSX, TypeScript infers the event type automatically — you only annotate when the handler is defined separately.

Detailed Answer

The element generic determines the type of e.target / e.currentTarget, so e.currentTarget.value is typed as string for an input. A frequent point of confusion: e.target is typed as the generic EventTarget-ish element for the whole event, while e.currentTarget is precisely the element the handler is attached to — prefer currentTarget for reliable typing. For a prop that is an event handler, you can type it as React.ChangeEventHandler<HTMLInputElement> instead of writing the function signature by hand.

Code Example

function SearchForm() {
  // inline handlers: event type is inferred, no annotation needed
  return (
    <form onSubmit={(e) => e.preventDefault()}>
      <input onChange={(e) => console.log(e.currentTarget.value)} />
    </form>
  );
}

// separate handler: annotate explicitly
const handleChange = (e: React.ChangeEvent<HTMLInputElement>) => {
  console.log(e.currentTarget.value);
};

const handleClick: React.MouseEventHandler<HTMLButtonElement> = (e) => {
  e.preventDefault();
};

Senior Engineer Perspective

The target vs currentTarget distinction is the classic gotcha — currentTarget is strongly typed to your element, target is whatever was actually clicked (could be a child). Mentioning the ...Handler alias types (ChangeEventHandler, MouseEventHandler) shows fluency. Also note these are React synthetic events, not native DOM events — using MouseEvent from lib.dom instead of React.MouseEvent is a subtle mismatch interviewers watch for.

Q10. How do you type a custom hook, especially one returning a tuple?

ROI: ★★★★☆ Frequency: High

Short Answer

Type the arguments and let the return be inferred where possible. For hooks that return a tuple (like useState), either annotate the return type explicitly or use as const — otherwise TypeScript widens the tuple to an array union ((T | Setter)[]), which breaks positional destructuring. For object-returning hooks, inference is usually fine.

Detailed Answer

If you return [value, setValue], TS infers Array<value | setValue>, so consumers destructuring by position get a union type on each slot. Two fixes: annotate the function's return type as a tuple, or append as const to the returned array (which also makes it readonly). Explicit annotation is generally clearer for a public hook. Prefer generics when the hook is reusable across value types (e.g. a useToggle vs a useLocalStorage<T>).

Code Example

// Generic hook with an explicit tuple return type
function useToggle(
  initial = false
): [boolean, () => void] {
  const [on, setOn] = useState(initial);
  const toggle = useCallback(() => setOn((o) => !o), []);
  return [on, toggle];              // typed as [boolean, () => void]
}

// Generic + as const alternative
function useLocalStorage<T>(key: string, initial: T) {
  const [value, setValue] = useState<T>(initial);
  // ... sync effect ...
  return [value, setValue] as const; // readonly [T, Dispatch<SetStateAction<T>>]
}

const [name, setName] = useToggle(); // correctly typed by position

Senior Engineer Perspective

The tuple-widening problem is the whole point of this question. Saying "I add as const or an explicit tuple annotation so destructuring keeps per-position types" nails it. A deeper follow-up: prefer returning an object from hooks with more than two values, because tuples rely on positional memory and readability degrades fast — tuples are best when consumers frequently rename (like useState). Show you choose the shape deliberately.

Q11. How do you type React Context correctly?

ROI: ★★★★☆ Frequency: High

Short Answer

Create the context with an explicit generic, then guard consumption so components never receive the default. The clean pattern is to default the context to undefined (typed Ctx | undefined) and expose a custom useX() hook that throws if the value is missing — this removes null checks from every consumer and enforces that the provider wraps the tree.

Detailed Answer

The naive approach passes a fake default object to createContext just to satisfy types, which silently hides the bug of consuming outside a provider. The robust pattern initialises with undefined and narrows inside a custom hook that throws a helpful error. Consumers then get a non-nullable, fully typed value with zero boilerplate. Also remember to memoise the provider's value so unrelated re-renders don't invalidate every consumer.

Code Example

interface AuthContextValue {
  user: User | null;
  login: (email: string) => Promise<void>;
  logout: () => void;
}

const AuthContext = createContext<AuthContextValue | undefined>(undefined);

export function AuthProvider({ children }: React.PropsWithChildren) {
  const [user, setUser] = useState<User | null>(null);
  const value = useMemo<AuthContextValue>(
    () => ({ user, login: async () => {}, logout: () => {} }),
    [user]
  );
  return <AuthContext.Provider value={value}>{children}</AuthContext.Provider>;
}

// custom hook removes the undefined from consumers
export function useAuth(): AuthContextValue {
  const ctx = useContext(AuthContext);
  if (!ctx) throw new Error("useAuth must be used within <AuthProvider>");
  return ctx;
}

Senior Engineer Perspective

Interviewers want the "throwing custom hook" pattern; supplying a fake default object is the anti-pattern because it defers a missing-provider bug to runtime confusion instead of a clear error. Bonus points for mentioning useMemo on the provider value (a real performance footgun) and for noting that a large context often should be split into state and dispatch contexts so components that only dispatch don't re-render on state changes.

SECTION 3 - ADVANCED TYPES

Q12. What are generics and what problem do they solve?

ROI: ★★★★★ Frequency: High

Short Answer

Generics are type parameters — placeholders that let a function, type, or component work over many types while preserving the relationship between input and output. They give you reuse without losing type information the way any would. A generic identity<T>(x: T): T guarantees the return type equals the argument type.

Detailed Answer

The alternative to generics is either duplicating a function per type or using any and losing safety. Generics preserve the link: whatever T is at the call site flows through. You can constrain a parameter with extends (e.g. <T extends { id: number }>) to require certain members, and provide defaults (<T = string>). TypeScript usually infers the type argument from usage, so callers rarely write it explicitly. Generics power almost every reusable abstraction: data-fetching hooks, form utilities, table components, and the utility types in Q13.

Code Example

// preserves the input/output relationship
function first<T>(arr: T[]): T | undefined {
  return arr[0];
}
const n = first([1, 2, 3]);      // number | undefined
const s = first(["a", "b"]);     // string  | undefined

// constrained generic
function getId<T extends { id: number }>(entity: T): number {
  return entity.id;
}

// generic with a default
interface ApiResponse<T = unknown> {
  data: T;
  status: number;
}

Senior Engineer Perspective

The tell of a mature answer is "generics let me stay type-safe across many types without any, and constraints let me require the minimum shape I need". Interviewers may push on over-genericising: adding type parameters that are used only once adds cognitive load with no benefit — a generic parameter should appear at least twice (input and output) to earn its place. Knowing when not to reach for generics is as senior as knowing how.

Q13. Explain the common utility types: Partial, Pick, Omit, Record, Required, Readonly.

ROI: ★★★★★ Frequency: High

Short Answer

These are built-in generic type transformers. Partial<T> makes all properties optional; Required<T> makes them all required; Readonly<T> makes them read-only; Pick<T, K> selects a subset of keys; Omit<T, K> removes keys; Record<K, V> builds an object type with keys K and values V. They let you derive types from a single source instead of hand-copying shapes.

Detailed Answer

UtilityEffectTypical use
Partial<T>All props optionalUpdate payloads, defaults merging
Required<T>All props requiredAfter validation / normalisation
Readonly<T>All props readonlyImmutable props / state
Pick<T, K>Keep only keys KNarrow props for a subcomponent
Omit<T, K>Remove keys KStrip id before create; extend DOM props
Record<K, V>Object of K→VLookup maps, dictionaries

Deriving types keeps them in sync: define User once and express "create input" as Omit<User, "id" | "createdAt">. When the base type changes, the derived types update automatically.

Code Example

interface User {
  id: string;
  name: string;
  email: string;
  createdAt: Date;
}

type CreateUser = Omit<User, "id" | "createdAt">;     // { name; email }
type UserPreview = Pick<User, "id" | "name">;         // { id; name }
type UserPatch = Partial<User>;                       // all optional
type FrozenUser = Readonly<User>;                     // all readonly
type UsersById = Record<string, User>;               // dictionary

// Omit is the idiomatic way to override a native prop's type
type InputProps = Omit<React.ComponentProps<"input">, "onChange"> & {
  onChange: (value: string) => void;
};

Senior Engineer Perspective

Interviewers check whether you derive or duplicate. The senior habit is "single source of truth" — a create-DTO is Omit of the entity, a patch is Partial. A subtle trap: Omit is not distributive over unions and doesn't preserve discriminated-union narrowing well, so on unions prefer Exclude/custom mapped types. Also know these are just mapped types under the hood — being able to reimplement Partial (Q14) proves real understanding.

Q14. What are keyof, mapped types, and conditional types?

ROI: ★★★★☆ Frequency: Medium

Short Answer

keyof T produces a union of T's property names. A mapped type iterates over those keys to build a new type ({ [K in keyof T]: ... }) — this is how Partial/Readonly are implemented. A conditional type is a type-level ternary (T extends U ? X : Y) that picks a type based on a relationship, and infer lets you extract a piece of a type inside the condition.

Detailed Answer

Together these are the engine behind the utility types. Combining keyof with indexed access (T[K]) lets you write a fully type-safe property getter. Mapped-type modifiers ? and readonly (and their removal via -? / -readonly) implement Partial/Required/Readonly. Conditional types with infer underpin ReturnType, Parameters, and Awaited, and distribute over unions when the checked type is a naked type parameter.

Code Example

interface User { id: string; name: string }

// keyof + indexed access -> type-safe getter
function getProp<T, K extends keyof T>(obj: T, key: K): T[K] {
  return obj[key];
}
getProp({ id: "1", name: "Ada" }, "name"); // string, "age" is rejected

// mapped type: reimplementing Partial
type MyPartial<T> = { [K in keyof T]?: T[K] };

// conditional type + infer: extract a function's return type
type MyReturn<F> = F extends (...args: any[]) => infer R ? R : never;
type R = MyReturn<() => User>; // User

Senior Engineer Perspective

Being able to reimplement Partial or ReturnType from scratch is the demarcation line for "knows TypeScript deeply" versus "uses TypeScript". Interviewers rarely need this daily, but asking it filters candidates. The pragmatic caveat to voice: heavy conditional/mapped type gymnastics hurt compile times and readability — use them for genuinely reusable library-grade utilities, not everyday app code where a plain type is clearer.

Q15. How do you write a generic (reusable) component?

ROI: ★★★★☆ Frequency: Medium

Short Answer

Declare a type parameter on the component function and use it in the props. TypeScript infers the concrete type from the props passed at the JSX call site, so a <List> knows its item type from the items array. This gives fully typed renderItem callbacks and key extractors without any.

Detailed Answer

Write the component as a generic function: function List<T>(props: ListProps<T>). Inference flows from the items: T[] prop into renderItem: (item: T) => ReactNode. Two caveats: (1) arrow-function components with generics need a trailing comma in .tsx (<T,>) to disambiguate from JSX, so a function declaration is cleaner; (2) generic components don't compose with React.FC, which is another reason the plain-function style won. This pattern powers reusable tables, selects, comboboxes and data lists.

Code Example

interface ListProps<T> {
  items: T[];
  keyOf: (item: T) => string | number;
  renderItem: (item: T) => React.ReactNode;
}

function List<T>({ items, keyOf, renderItem }: ListProps<T>) {
  return (
    <ul>
      {items.map((item) => (
        <li key={keyOf(item)}>{renderItem(item)}</li>
      ))}
    </ul>
  );
}

// T inferred as User — renderItem's param is fully typed
<List
  items={users}
  keyOf={(u) => u.id}
  renderItem={(u) => <span>{u.name}</span>}
/>;

Senior Engineer Perspective

The .tsx generic-arrow ambiguity (<T,> trailing comma) is a favourite "have you actually done this" check. Explain that inference from the items prop is what makes the callbacks type-safe — that's the payoff. A follow-up may ask how to constrain T (e.g. T extends { id: string }) so you can drop the keyOf prop; showing you can trade flexibility for ergonomics demonstrates design judgement.

Q16. How do you type a component that uses forwardRef?

ROI: ★★★★☆ Frequency: Medium

Short Answer

forwardRef takes two type parameters: the ref (element) type first, then the props type. So forwardRef<HTMLInputElement, InputProps>. Inside, the ref argument is typed as ForwardedRef<HTMLInputElement>. In React 19 this is simpler — ref can be a normal prop, and forwardRef is being phased out.

Note the parameter order is reversed from intuition: element type first, props second. This trips people up constantly. To expose an imperative API rather than the raw DOM node, combine forwardRef with useImperativeHandle and type the ref as your custom handle interface. As of React 19, function components can accept ref directly in their props (typed as Ref<T>), so new code often skips forwardRef entirely — worth mentioning to show you track the current API.

interface InputProps {

  value: string;
  onChange: (v: string) => void;
}

    </label>

Q17. How do you type a fetch / API layer safely?

ROI: ★★★★☆ Frequency: High

Short Answer

Never trust the network: fetch().json() returns any (effectively unsafe). Wrap it so the raw result is unknown, then validate at runtime with a schema (Zod/Valibot) and infer the TypeScript type from that single schema. A generic request<T> helper centralises error handling and typing so call sites are clean and safe.

Detailed Answer

A plain generic like request<User>(url) only asserts the shape — it lies if the server returns something different. The robust layer parses the response through a runtime schema so the compile-time type and the actual data can't drift; the inferred type comes from the schema via z.infer. This catches API contract changes at the boundary with a clear error instead of an undefined-property crash three components deep. Pair this with TanStack Query, whose useQuery infers its data type from the query function's return type.

Code Example

import { z } from "zod";

const UserSchema = z.object({
  id: z.string(),
  name: z.string(),
  email: z.string().email(),
});
type User = z.infer<typeof UserSchema>; // single source of truth

async function getUser(id: string): Promise<User> {
  const res = await fetch(`/api/users/${id}`);
  if (!res.ok) throw new Error(`HTTP ${res.status}`);
  const json: unknown = await res.json();   // untrusted
  return UserSchema.parse(json);             // validated + typed
}

// TanStack Query infers `data: User` from getUser's return type
// const { data } = useQuery({ queryKey: ["user", id], queryFn: () => getUser(id) });

Senior Engineer Perspective

The line interviewers listen for: "a generic fetch<T> is a type assertion, not a guarantee — it trusts data it never checked." Elevating to runtime validation with an inferred type shows you understand the gap between compile-time and runtime. Follow-ups often go to error typing (model errors as a discriminated result rather than throwing), and to keeping DTOs vs domain models separate so backend shape changes don't leak through the whole UI.

Q19. What are the most common TypeScript-with-React mistakes?

Short Answer

The recurring offenders: leaning on any (or casual as casts) instead of narrowing; forgetting the useState generic for null/empty initial values; typing API responses without runtime validation; using loose action types in reducers; misusing ReactElement vs ReactNode; and defining unstable object/array props inline that break memoisation.

Detailed Answer

  • as as a hammer: a type assertion silences the compiler without proving anything. Prefer narrowing or validation; reserve as for cases you genuinely know better than TS (and even then, as const or a guard is usually cleaner).

  • useState inference: useState(null) or useState([]) infers null/never[] and rejects real data.

  • Non-null assertion (!) abuse: ref.current!.focus() hides real null cases; guard with ?. instead.

// GOOD: narrow / validate / guard

// BAD: inference collapses to never[]

// GOOD
const [items2, setItems2] = useState<Item[]>([]);

SECTION 5 - GENERIC COMPONENTS & GENERIC CUSTOM HOOKS

Q20. How do you constrain a generic type parameter, and why does it matter for reusable components?

ROI: ★★★★☆ Frequency: High

Short Answer

A constraint (<T extends Shape>) restricts what T can be, so the compiler knows a minimum set of members are always present. Without a constraint, T defaults to unknown-like behaviour inside the function body — you can move values of type T around but cannot access any property on them. Constraints let a generic component require just enough shape to do its job while still accepting any concrete type that satisfies it.

Detailed Answer

Without extends, function getLabel<T>(item: T) cannot read item.label because nothing guarantees T has a label. Adding <T extends { label: string }> narrows the acceptable inputs to anything with at least a label: string field, while still preserving the rest of the concrete type through inference — callers passing a richer object don't lose their extra properties. Constraints can also reference other type parameters (<T, K extends keyof T>), which is exactly how Object.keys-style accessors and the built-in Pick/Record utilities stay safe.

Code Example

// no constraint — T is opaque, no property access allowed
function identity<T>(x: T): T {
  return x;
}

// constrained — guarantees the minimum shape needed
interface HasLabel {
  label: string;
}
function renderLabel<T extends HasLabel>(item: T) {
  return item.label.toUpperCase(); // safe: T is guaranteed to have label
}

renderLabel({ label: "Ada", id: 1 }); // extra props are fine and preserved

// constraint referencing another parameter
function pluck<T, K extends keyof T>(obj: T, key: K): T[K] {
  return obj[key];
}

Senior Engineer Perspective

Interviewers use this to check whether you reach for constraints instead of widening to any the moment a generic needs a property. The sharpest follow-up: "what's the narrowest constraint you should use?" — the answer is exactly the shape the function needs and nothing more, because an over-constrained generic rejects otherwise-valid callers. Also mention that a constraint is checked at the call site, not just inside the function, so misuse fails fast with a clear error.

Q21. How does TypeScript infer a generic type parameter from component props, and when do you need to pass it explicitly?

ROI: ★★★★☆ Frequency: Medium

Short Answer

TypeScript performs inference by looking at the arguments actually passed and working backward to find a T that satisfies every usage. For a generic component, that means the JSX props you pass at the call site. You only need to supply the type argument explicitly when there isn't enough information to infer it — for example, an empty array literal, or a generic component instantiated with no props that reference T at all.

Detailed Answer

Inference walks each parameter position where T appears and unifies the candidates into a single type (widening to a union if the positions disagree and there's no common supertype otherwise). If T only appears in the return type or nowhere in the parameters, inference has nothing to work from and falls back to the generic's default or unknown. In JSX you supply the type argument explicitly with <List<User> items={...} /> syntax — useful when an empty array would otherwise infer never.

Code Example

interface ListProps<T> {
  items: T[];
  renderItem: (item: T) => React.ReactNode;
}
function List<T>({ items, renderItem }: ListProps<T>) {
  return <ul>{items.map((it, i) => <li key={i}>{renderItem(it)}</li>)}</ul>;
}

// inferred from `items` — no explicit type argument needed
<List items={users} renderItem={(u) => u.name} />;

// nothing to infer from — an empty array gives T = never, must be explicit
<List<User> items={[]} renderItem={(u) => u.name} />;

Senior Engineer Perspective

The empty-array case is the practical trap most candidates haven't hit until they've actually shipped a generic list/table component with an initially-empty data set. Naming it unprompted is a strong signal. A deeper point: TypeScript does not do partial inference across a mixed explicit/implicit generic parameter list in older versions — if you must supply one type argument, historically you had to supply all of them (this was relaxed for trailing defaulted parameters in later releases), so ordering generic parameters from "most likely explicit" to "most likely inferred" is a real design decision.

Q22. How do you write a generic custom hook, e.g. useFetch<T>, and type its return value correctly?

ROI: ★★★★★ Frequency: High

Short Answer

Parameterise the hook function itself with <T>, thread it through the async result, and return a discriminated union (or an object with a status discriminant) so consumers narrow before touching data. The caller supplies T either explicitly (useFetch<User>(url)) or it's inferred from a validator/parser argument.

Detailed Answer

A naive useFetch that returns { data: T | null, error: string | null, loading: boolean } lets callers read data while loading is still true, producing the same "impossible state" bug as Q5. The stronger version returns a discriminated union keyed on a status field, so data is only reachable in the success branch. Internally, the hook still uses plain useState calls; the union is assembled in the return statement (or via useMemo) right before returning.

Code Example

type FetchResult<T> =
  | { status: "loading" }
  | { status: "error"; error: string }
  | { status: "success"; data: T };

function useFetch<T>(url: string): FetchResult<T> {
  const [state, setState] = useState<FetchResult<T>>({ status: "loading" });

  useEffect(() => {
    let cancelled = false;
    setState({ status: "loading" });
    fetch(url)
      .then((res) => res.json())
      .then((data: T) => { if (!cancelled) setState({ status: "success", data }); })
      .catch((err) => { if (!cancelled) setState({ status: "error", error: String(err) }); });
    return () => { cancelled = true; };
  }, [url]);

  return state;
}

// usage — data is only accessible after narrowing
const result = useFetch<User[]>("/api/users");
if (result.status === "success") {
  result.data.map((u) => u.name); // fully typed, no null checks needed
}

Senior Engineer Perspective

Interviewers want to see the same "make illegal states unrepresentable" instinct applied to hooks, not just components. A good follow-up is why the fetch result is asserted as T in .then((data: T) => ...) instead of validated — the honest answer is that this is still an assertion, and a production-grade version would run the raw JSON through a schema (Q69) before it's allowed to become T. Also mention the cancellation flag guarding against setting state after unmount or after a newer request has started (a request race condition).

Q23. How do you type a generic compound component, e.g. a Select<T> with generic Option<T> items?

ROI: ★★★☆☆ Frequency: Medium

Short Answer

The parent component owns the generic parameter T and threads it into every prop that touches an item of that type: the value, the change handler, and the render function for each option. Because compound components typically communicate through context, the trickiest part is that React.createContext cannot itself be generic in a way that lets each usage carry a different T — you work around it with a type assertion at the context boundary or a generic factory function that creates a fresh context per call.

Detailed Answer

A straightforward generic Select<T> without compound sub-components is simple: pass options: T[], value: T, onChange: (v: T) => void, and a getLabel: (v: T) => string. Once you introduce compound components (<Select.Option>) sharing state via context, the context has to be created once at module scope with a fixed type — commonly unknown — and consumers narrow or the provider casts to the actual T for that instance. This is one of the few well-known, accepted uses of a type assertion in React + TypeScript, because compound-component context is inherently generic-hostile.

Code Example

interface SelectContextValue<T> {
  value: T;
  onSelect: (v: T) => void;
}
// Context is created once with a fixed shape; each Select instance
// asserts its own T at the boundary.
const SelectContext = createContext<SelectContextValue<unknown> | undefined>(undefined);

function Select<T>({
  value,
  onChange,
  children,
}: React.PropsWithChildren<{ value: T; onChange: (v: T) => void }>) {
  const ctxValue = { value, onSelect: onChange } as SelectContextValue<unknown>;
  return <SelectContext.Provider value={ctxValue}>{children}</SelectContext.Provider>;
}

function Option<T>({ value, children }: React.PropsWithChildren<{ value: T }>) {
  const ctx = useContext(SelectContext);
  if (!ctx) throw new Error("Option must be used within Select");
  const selected = ctx.value === value;
  return (
    <li onClick={() => ctx.onSelect(value)} aria-selected={selected}>
      {children}
    </li>
  );
}

Senior Engineer Perspective

The honest answer here is that React Context and generics don't compose cleanly — say that directly rather than pretending there's a fully type-safe solution. What you can defend is where you place the necessary assertion (at the single boundary inside Select, not scattered through every consumer) so the unsafe surface is as small and auditable as possible. Mentioning libraries like Radix or Headless UI, which hit this exact limitation and solve it the same way, shows you've actually built compound components rather than just read about generics.

Q24. What is the "arrow function generic ambiguity" problem in .tsx files and how do you solve it?

ROI: ★★★★☆ Frequency: High

Short Answer

In a .tsx file, <T>(x: T) => x is ambiguous — the parser can't tell if <T> opens a JSX element or a generic parameter list, and by default it assumes JSX and errors. The fixes: add a trailing comma (<T,>(x: T) => x), add a constraint (<T extends unknown>(x: T) => x), or simply write the generic as a named function declaration instead of an arrow, which has no such ambiguity.

Detailed Answer

This only affects arrow functions in .tsx; plain .ts files never hit it because there's no JSX to disambiguate from. The trailing-comma trick works because <T,> is not valid JSX opening-tag syntax, so the parser is forced to treat it as a generic parameter list. The constraint trick works for the same reason — JSX tags cannot have an extends clause. Most teams standardise on function declarations for generic components and hooks precisely to sidestep this, reserving arrows for the non-generic case.

Code Example

// Error in .tsx: parser reads <T> as a JSX tag
// const identity = <T>(x: T): T => x;

// Fix 1 — trailing comma
const identity1 = <T,>(x: T): T => x;

// Fix 2 — constraint
const identity2 = <T extends unknown>(x: T): T => x;

// Fix 3 — function declaration (no ambiguity, most common in practice)
function identity3<T>(x: T): T {
  return x;
}

Senior Engineer Perspective

This is a "have you actually written generic React code" litmus test — it's obscure enough that copying from documentation rarely surfaces it, but anyone who has hit the compiler error remembers the fix instantly. If asked why teams prefer function declarations for generic hooks/components, the answer is exactly this ambiguity plus better hoisting and clearer stack traces, not just style preference.

Q25. How do you write a generic higher-order component (HOC) with correct prop typing?

ROI: ★★★☆☆ Frequency: Medium

Short Answer

A well-typed HOC is generic over the wrapped component's own props P, takes React.ComponentType<P>, and returns a new component whose prop type is P minus whatever the HOC injects, plus whatever new props it introduces. Getting the subtraction right (Omit<P, InjectedKeys>) is what lets consumers of the wrapped component skip the injected props while TypeScript still enforces everything else.

Detailed Answer

The classic mistake is having the HOC's returned component still require the injected props, forcing every consumer to pass a value the HOC was supposed to supply. The fix is to compute the public prop type as the original props with the injected keys omitted, then have the returned component accept exactly that public type internally, merging in the injected value before rendering the wrapped component. Since HOCs are largely superseded by hooks in modern React, this pattern shows up mostly in legacy codebases and cross-cutting concerns like error boundaries or analytics wrappers.

Code Example

interface WithUserProps {
  user: User;
}

function withUser<P extends WithUserProps>(
  Component: React.ComponentType<P>
) {
  // public props = P minus the injected `user` key
  type PublicProps = Omit<P, "user">;

  return function WithUser(props: PublicProps) {
    const user = useAuth().user; // injected value
    // the cast is required because TS can't prove PublicProps + { user }
    // structurally equals P for an arbitrary P extends WithUserProps
    return <Component {...(props as P)} user={user} />;
  };
}

interface ProfileProps extends WithUserProps {
  showEmail: boolean;
}
function Profile({ user, showEmail }: ProfileProps) { /* ... */ return null; }

const ProfileWithUser = withUser(Profile);
<ProfileWithUser showEmail />; // `user` is NOT required here — correctly injected

Senior Engineer Perspective

Interviewers expect you to name the one unavoidable assertion (spreading PublicProps back into P) and explain why it's unavoidable — TypeScript can't statically prove that adding back exactly the omitted keys reconstructs an arbitrary generic P. The stronger answer volunteers that this is a known, accepted limitation documented in the React TypeScript cheatsheet, and that most teams now prefer a hook (useUser() called directly inside Profile) over a HOC specifically because it avoids this whole class of typing friction.

Q26. How do default generic type parameters work, and when should you provide one?

ROI: ★★★☆☆ Frequency: Medium

Short Answer

<T = DefaultType> supplies a fallback used when the type argument can't be inferred and isn't given explicitly. It behaves like a default function parameter, but at the type level. Use it when there's a sensible common case (e.g. an API response defaulting to unknown, or a form hook defaulting its values type to Record<string, unknown>) so most call sites don't need to specify the generic at all.

Detailed Answer

Defaults only kick in when TypeScript has no other information to infer from — if the parameter also appears in a function argument, inference from the actual call always wins over the default. Defaults can also reference earlier type parameters in the same parameter list (<T, K extends keyof T = keyof T>), which is how several built-in utility signatures avoid forcing callers to repeat information. Overusing defaults can hide a genuine typing mistake, though — if a generic silently falls back to unknown because inference failed, that failure is often more useful surfaced as an error than swallowed by a default.

Code Example

interface ApiResponse<T = unknown> {
  data: T;
  status: number;
}

const raw: ApiResponse = { data: "anything", status: 200 };      // T = unknown (default)
const typed: ApiResponse<User> = { data: user, status: 200 };    // T = User (explicit)

// default referencing an earlier parameter
function pick<T, K extends keyof T = keyof T>(obj: T, keys?: K[]) {
  // keys defaults to "all keys of T" conceptually
}

Senior Engineer Perspective

The nuance worth stating: a default type parameter is a convenience for callers, not a safety net — it should represent a genuinely common case, not a way to silence "couldn't infer T" errors. A good follow-up is contrasting this with a constraint: a constraint says "T must be at least this," a default says "if you don't tell me, assume this." Confusing the two (e.g. constraining to unknown instead of defaulting to it) is a subtle but real bug that removes safety instead of adding convenience.

Q27. How do you type a generic reducer/store hook that needs multiple independent type parameters?

ROI: ★★★☆☆ Frequency: Medium

Short Answer

Declare one type parameter per independent concern — typically State and Action — and constrain Action to a minimal shape (like { type: string }) so the hook can still do generic bookkeeping (logging, devtools) without knowing the concrete union. The reducer function itself, supplied by the caller, is what actually ties State and Action together per call site.

Detailed Answer

A generic useStore<State, Action extends { type: string }>(reducer, initialState) lets every consumer bring its own concrete State/Action pair while the hook's internals (subscription list, dispatch wiring, middleware) stay written once. The constraint on Action is deliberately loose — just enough to let the hook log action.type generically — while the real per-app safety comes from the discriminated union the caller defines for their specific reducer. This is the same pattern Redux Toolkit and Zustand use internally.

Code Example

interface BaseAction {
  type: string;
}

function useStore<State, Action extends BaseAction>(
  reducer: (state: State, action: Action) => State,
  initialState: State
) {
  const [state, setState] = useState(initialState);
  const dispatch = useCallback(
    (action: Action) => {
      console.log("dispatch:", action.type); // generic bookkeeping — only needs `type`
      setState((prev) => reducer(prev, action));
    },
    [reducer]
  );
  return { state, dispatch };
}

// concrete instantiation ties State + Action together for this call site
type CartState = { items: string[] };
type CartAction = { type: "add"; item: string } | { type: "clear" };

function cartReducer(state: CartState, action: CartAction): CartState {
  switch (action.type) {
    case "add": return { items: [...state.items, action.item] };
    case "clear": return { items: [] };
  }
}
const { state, dispatch } = useStore(cartReducer, { items: [] });

Senior Engineer Perspective

The senior instinct here is minimal constraints on the generic infrastructure layer, maximal precision on the concrete per-feature layer — the store hook itself should know as little as possible about any specific app's actions. A good follow-up asks how you'd add typed middleware; the answer generalises further with a third parameter or a curried factory, but the same "constrain only what the generic layer truly needs" principle holds throughout.

SECTION 6 - UTILITY TYPES DEEP DIVE

Q28. What does Record<K, V> actually expand to, and what's a common misuse?

ROI: ★★★★☆ Frequency: High

Short Answer

Record<K, V> expands to the mapped type { [P in K]: V } — an object type whose keys are exactly the members of K and whose values are all V. The common misuse is reaching for Record<string, V> when you actually have a known, finite set of keys; that throws away the exhaustiveness checking a literal union of keys would give you.

Detailed Answer

When K is a literal union (e.g. "light" | "dark"), Record forces you to supply every key — omitting one is a compile error, which is exactly the exhaustiveness guarantee you want for things like theme maps or per-status label maps. When K is widened to string, that guarantee disappears and Record<string, V> becomes indistinguishable from a plain index signature — any key is allowed, none are required, and typos in key names go undetected.

Code Example

type Theme = "light" | "dark";

// Good: Record with a literal union enforces every key exists
const labels: Record<Theme, string> = {
  light: "Light mode",
  dark: "Dark mode",
  // missing a key here would be a compile error
};

// Misuse: Record<string, V> gives up exhaustiveness entirely
const loose: Record<string, string> = { lihgt: "typo — compiles fine" };

// Equivalent mapped-type expansion of Record<Theme, string>
type ThemeLabels = { [P in Theme]: string };

Senior Engineer Perspective

The differentiator is recognising that Record<string, V> and a literal-keyed Record solve completely different problems — one is a dictionary, the other is an exhaustiveness-checked map. Interviewers will often ask you to spot a bug where a key was renamed in one place but not another; if the map used Record<string, V> the renamed key silently vanishes, whereas a literal-keyed Record would fail to compile at the exact line that needs fixing.

Q29. How do Exclude, Extract, and NonNullable work, and how do they differ from Omit/Pick?

ROI: ★★★★☆ Frequency: Medium

Short Answer

Omit/Pick operate on object property keys. Exclude/Extract operate on the members of a union — Exclude<T, U> removes union members assignable to U, Extract<T, U> keeps only union members assignable to U. NonNullable<T> is just Exclude<T, null | undefined> under the hood, specialised for the extremely common "strip nullish" case.

Detailed Answer

All three are implemented as conditional types that distribute over a union (see Q53), which is exactly why they operate member-by-member rather than on an object's shape. This makes them the right tool for narrowing a discriminated union type down to a subset of its variants (Extract<Action, { type: "add" }>) or removing one variant entirely (Exclude<Status, "archived">) — something Omit cannot do, since Omit would try to remove object keys, not union members.

Code Example

type Status = "idle" | "loading" | "success" | "error";

type NotIdle = Exclude<Status, "idle">;         // "loading" | "success" | "error"
type Terminal = Extract<Status, "success" | "error">; // "success" | "error"

type MaybeUser = User | null | undefined;
type DefiniteUser = NonNullable<MaybeUser>;      // User

// Extract on a discriminated union — pulls out one variant's full shape
type Action =
  | { type: "add"; item: string }
  | { type: "remove"; id: string }
  | { type: "clear" };
type AddAction = Extract<Action, { type: "add" }>; // { type: "add"; item: string }

Senior Engineer Perspective

The key distinction to volunteer unprompted: "Pick/Omit work on keys of one object type, Extract/Exclude work on members of a union." Candidates who reach for Omit to try to remove a union variant will hit a confusing error, and recognising why is the actual signal. A strong follow-up is implementing NonNullable from scratch as Exclude<T, null | undefined> to prove you understand it's not a special primitive but a composition of the same conditional-type machinery.

Q30. What does ReturnType<T> do and how would you use it in a React codebase?

ROI: ★★★★☆ Frequency: High

Short Answer

ReturnType<T> extracts the return type of a function type T, letting you derive a type from a function's implementation instead of hand-writing (and duplicating) it. It's especially useful for deriving the shape of a custom hook's return value, or a selector/reducer's output, without maintaining a second, parallel type declaration that can drift out of sync.

Detailed Answer

Under the hood ReturnType<T> is a conditional type using infer: T extends (...args: any[]) => infer R ? R : never (see Q52). Using it on a hook means the hook's implementation is the single source of truth for its return shape — if you add a new field to what the hook returns, every consumer's derived type updates automatically. The common pairing is ReturnType<typeof useSomeHook>, since hooks are values (functions), not types, so you need typeof to get back to the type level first.

Code Example

function useCounter(initial = 0) {
  const [count, setCount] = useState(initial);
  const increment = () => setCount((c) => c + 1);
  const reset = () => setCount(initial);
  return { count, increment, reset };
}

// derive the type instead of duplicating { count, increment, reset }
type CounterApi = ReturnType<typeof useCounter>;

function CounterDisplay({ count, increment }: Pick<CounterApi, "count" | "increment">) {
  return <button onClick={increment}>{count}</button>;
}

Senior Engineer Perspective

The senior habit again is "derive, don't duplicate" — hand-writing a parallel CounterApi interface next to the hook means the two can silently drift the moment someone edits one and forgets the other. Interviewers may push further to Parameters<T> (the argument-side equivalent) and ask you to type a wrapper function that forwards arguments to useCounter — a natural use for Parameters<typeof useCounter>.

Q31. How would you implement Readonly<T> and a DeepReadonly<T> yourself?

ROI: ★★★☆☆ Frequency: Medium

Short Answer

Readonly<T> is a one-level mapped type: { readonly [K in keyof T]: T[K] }. It only freezes the top level — nested objects remain mutable. A DeepReadonly<T> recurses: for each property, if its type is itself an object, recursively apply DeepReadonly; otherwise leave it as-is. This is a recursive conditional/mapped type, and it needs a base case to avoid looping forever on primitives.

Detailed Answer

The built-in Readonly<T> is intentionally shallow because deep readonly is expensive to compute and not always what you want (e.g. you may want to reassign a nested object wholesale while its siblings stay readonly). Writing DeepReadonly requires distinguishing "this property is a primitive/function — stop recursing" from "this property is an object/array — recurse into it," which is exactly what a conditional type with infer or a direct object check does.

Code Example

// Built-in Readonly, reimplemented — shallow only
type MyReadonly<T> = { readonly [K in keyof T]: T[K] };

// DeepReadonly — recurses into nested objects and arrays
type DeepReadonly<T> = T extends (infer U)[]
  ? ReadonlyArray<DeepReadonly<U>>
  : T extends object
  ? { readonly [K in keyof T]: DeepReadonly<T[K]> }
  : T; // base case: primitives/functions stop recursing

interface Config {
  api: { url: string; retries: number };
  flags: string[];
}
type FrozenConfig = DeepReadonly<Config>;
// FrozenConfig.api.url = "x";       // Error — nested object is readonly too
// FrozenConfig.flags.push("x");    // Error — nested array is readonly too

Senior Engineer Perspective

The base case is the part candidates most often forget — without T extends object ? ... : T, the recursion either never terminates conceptually or incorrectly tries to map over primitives. Mention that libraries like Immer solve the "deep immutability" problem at the runtime level (structural sharing, draft proxies) rather than purely at the type level, and that DeepReadonly alone only stops you from writing code that mutates — it doesn't optimise or structurally share anything at runtime.

Q32. What are template literal types, and what problem do they solve in typing CSS/route/event-name strings?

ROI: ★★★★☆ Frequency: Medium

Short Answer

Template literal types let you build string literal types out of other literal types using the same `...${...}` syntax as template literals, but at the type level. They're the tool for modelling structured strings — route paths, CSS custom properties, event names — as precise unions instead of a loose string, so typos and malformed values are caught at compile time.

Detailed Answer

Combined with union types, a template literal type expands into the cross-product of all combinations — `on${Capitalize<"click" | "hover">}` produces "onClick" | "onHover". This underlies typed event-name systems, typed route builders (`/users/${string}` matches any user-id path but rejects /users alone), and typed CSS variable access (`--${string}`). TypeScript also ships the intrinsic string-manipulation types Uppercase, Lowercase, Capitalize, Uncapitalize specifically to compose with template literals.

Code Example

type EventName = "click" | "hover" | "focus";
type HandlerName = `on${Capitalize<EventName>}`; // "onClick" | "onHover" | "onFocus"

interface Props {
  onClick?: () => void;
  onHover?: () => void;
  onFocus?: () => void;
}

// Typed route matching
type UserRoute = `/users/${string}`;
const a: UserRoute = "/users/42";   // OK
// const b: UserRoute = "/users";   // Error — missing the required segment

// Typed CSS custom property access
function getCssVar(name: `--${string}`) {
  return getComputedStyle(document.documentElement).getPropertyValue(name);
}
getCssVar("--primary-color"); // OK
// getCssVar("primary-color"); // Error — missing leading --

Senior Engineer Perspective

Interviewers use this to gauge whether you know TypeScript features beyond React basics. The strongest answers tie it to a real bug class: a typo'd event name or CSS variable that a loose string type would never catch, caught instead at the exact call site. The trade-off worth naming: heavy template-literal unions (e.g. modelling every possible Tailwind class combination) can explode combinatorially and slow down the compiler — use them for genuinely small, structured string spaces, not open-ended ones.

Q33. How do you use Parameters<T> and ConstructorParameters<T>?

ROI: ★★★☆☆ Frequency: Medium

Short Answer

Parameters<T> extracts a function type's parameter list as a tuple. ConstructorParameters<T> does the same for a class's constructor. Both let you derive an argument shape from an existing function/class instead of re-declaring it, which is useful for wrapper functions, typed event-emitter subscriptions, and dependency-injection helpers.

Detailed Answer

Both are conditional types using infer over the parameter position: T extends (...args: infer P) => any ? P : never. Because the result is a tuple, you can destructure it, spread it, or index into it (Parameters<T>[0] for just the first argument's type). A common React use is a logging/analytics wrapper that must accept the exact same arguments as the function it wraps without re-typing them.

Code Example

function createUser(name: string, age: number, opts?: { admin: boolean }) {
  return { name, age, admin: opts?.admin ?? false };
}

type CreateUserArgs = Parameters<typeof createUser>;
// [name: string, age: number, opts?: { admin: boolean } | undefined]

function withLogging<F extends (...args: any[]) => any>(fn: F) {
  return (...args: Parameters<F>): ReturnType<F> => {
    console.log("calling with", args);
    return fn(...args);
  };
}
const loggedCreateUser = withLogging(createUser); // fully typed args + return

class ApiClient {
  constructor(public baseUrl: string, public timeoutMs: number) {}
}
type ApiClientArgs = ConstructorParameters<typeof ApiClient>; // [string, number]

Senior Engineer Perspective

The payoff to state clearly: a generic wrapper written with Parameters<F>/ReturnType<F> stays correctly typed forever as the wrapped function's signature changes — no manual sync required. A common follow-up asks you to write a typed debounce or memoize helper using exactly this pattern, which is a very realistic, shippable exercise rather than pure trivia.

Q34. What is the difference between Awaited<T> and just annotating a promise's resolved type manually?

ROI: ★★★☆☆ Frequency: Medium

Short Answer

Awaited<T> unwraps a (possibly nested) Promise type to its final resolved value, correctly handling promises that resolve to other promises (a "thenable" chain), which a naive single-level unwrap misses. It's what powers correct async/await typing and is the recommended way to derive "the type await would actually produce" instead of hand-guessing it.

Detailed Answer

A single-level unwrap like T extends Promise<infer U> ? U : T stops after one layer — if a function returns Promise<Promise<User>> (which can genuinely happen with chained async helpers), the naive version gives you Promise<User>, not User. Awaited<T> is defined recursively so it keeps unwrapping until it hits a non-promise, exactly matching what a real await expression does at runtime. It's most commonly combined with ReturnType to get the resolved data type of an async function: Awaited<ReturnType<typeof fetchUser>>.

Code Example

// naive, single-level unwrap — breaks on nested promises
type NaiveAwaited<T> = T extends Promise<infer U> ? U : T;

async function getUser(): Promise<User> {
  return fetchUserFromApi();
}

// The idiomatic combo: resolved type of an async function
type UserResult = Awaited<ReturnType<typeof getUser>>; // User

// Nested-promise case where the naive version would fail
type Nested = Promise<Promise<User>>;
type Correct = Awaited<Nested>; // User — fully unwrapped

Senior Engineer Perspective

The interviewer is checking whether you know Awaited exists as a built-in (added in TS 4.5 specifically to fix real bugs in Promise.all typings) rather than reaching for a hand-rolled single-level unwrap that quietly breaks on nested promises. The realistic follow-up is deriving the element type of a Promise.all result or a TanStack Query queryFn's data type — both go through Awaited<ReturnType<...>> in real codebases.

Q35. How do you compose multiple utility types together to model a form library's field state?

ROI: ★★★★☆ Frequency: Medium

Short Answer

Start from one domain type (e.g. User), then layer utility types to derive every form-related shape from it: Partial<User> for in-progress values, a mapped type over keyof User for per-field error/touched maps, and Pick/Omit for step-specific subsets. Composing keeps every derived shape locked to the single source of truth instead of five independently hand-written interfaces.

Detailed Answer

A realistic form needs at least: values (partial until submit), errors (per-field, optional), touched (per-field booleans), and possibly a step-scoped subset for multi-step forms. Each of these is a mechanical transformation of the same base type — which is precisely what mapped types combined with keyof are for. Writing them all by hand for every form in the app is the exact duplication utility types exist to eliminate, and it's a very typical senior-level "design this small type layer" interview exercise.

Code Example

interface User {
  name: string;
  email: string;
  age: number;
}

type FormValues<T> = Partial<T>;
type FormErrors<T> = { [K in keyof T]?: string };
type FormTouched<T> = { [K in keyof T]?: boolean };

interface FormState<T> {
  values: FormValues<T>;
  errors: FormErrors<T>;
  touched: FormTouched<T>;
}

// Step-scoped subset for a multi-step signup wizard
type ContactStep = Pick<User, "name" | "email">;
type ContactFormState = FormState<ContactStep>;

const initialState: FormState<User> = {
  values: {},
  errors: {},
  touched: {},
};

Senior Engineer Perspective

This question rewards showing the whole derivation chain out loud, not just the final answer — interviewers are grading whether you reach for composition automatically. A strong closer: mention that libraries like React Hook Form and Formik export exactly these generic helper types (FieldErrors<T>, DeepPartial<T>) so application code never redefines this layer per form — recognising that this is a solved, reusable problem is itself a signal of experience.

SECTION 7 - DISCRIMINATED UNIONS & TYPE NARROWING

Q36. How do you model a UI component with multiple mutually exclusive prop "variants" using discriminated unions?

ROI: ★★★★★ Frequency: High

Short Answer

Instead of one flat props interface with a pile of optional fields, split the props into a union of shapes, one per variant, each sharing a literal discriminant like variant. TypeScript then forces callers to supply exactly the fields valid for the variant they chose, and rejects invalid combinations (like passing an href to a variant: "button") at the JSX call site.

Detailed Answer

A flat props interface with everything optional (href?, onClick?, type?) can't stop a caller from supplying both href and onClick, or neither — the compiler has no way to express "exactly one of these combinations is valid." A discriminated union of prop shapes fixes this at the type level: the component's parameter type is the union, and inside the component you switch/if on the discriminant to render each variant, with full access to only that variant's fields.

Code Example

type ButtonProps =
  | { variant: "button"; onClick: () => void; label: string }
  | { variant: "link"; href: string; label: string; target?: "_blank" };

function Button(props: ButtonProps) {
  if (props.variant === "link") {
    return <a href={props.href} target={props.target}>{props.label}</a>;
  }
  return <button onClick={props.onClick}>{props.label}</button>;
}

<Button variant="link" href="/docs" label="Docs" />;
// <Button variant="link" onClick={() => {}} label="x" /> // Error — onClick invalid on "link"

Senior Engineer Perspective

This is a direct, practical extension of "make illegal states unrepresentable" (Q5) applied to component APIs rather than data/fetch state — interviewers specifically look for you to make that connection unprompted. A good follow-up: what happens as the number of variants grows to five or six? At that point each variant becomes worth extracting into its own named type and possibly its own sub-component, since a giant inline union hurts prop-hint readability in editors.

Q37. How do you implement exhaustiveness checking with never, and what happens if you forget the default branch?

ROI: ★★★★★ Frequency: High

Short Answer

In the default (or final else) branch of a switch/if chain over a discriminated union, assign the narrowed value to a variable typed never. If every variant was handled above, TypeScript has narrowed the remaining type to never and the assignment compiles; if a new variant is added to the union later and left unhandled, the remaining type is no longer never, and the assignment fails to compile — turning a runtime gap into a build-time error.

Detailed Answer

Without the never check, an unhandled case in a switch simply falls through silently (or returns undefined), and the bug surfaces later as a blank UI or a crash somewhere downstream, disconnected from the actual missing case. With the check, adding a new member to the union and forgetting to update every switch that consumes it becomes a compile error at exactly the switch statement that needs a new case — which is the entire value proposition, especially in large codebases where a union is consumed in a dozen different places.

Code Example

type Status = "idle" | "loading" | "success" | "error";

function label(status: Status): string {
  switch (status) {
    case "idle": return "Idle";
    case "loading": return "Loading…";
    case "success": return "Done";
    case "error": return "Failed";
    default: {
      const _exhaustive: never = status; // compiles only if all cases handled
      throw new Error(`Unhandled status: ${_exhaustive}`);
    }
  }
}

// Now imagine adding "cancelled" to Status but forgetting to update `label`:
// type Status = "idle" | "loading" | "success" | "error" | "cancelled";
// -> the `default` branch's `status` is now typed "cancelled", not never,
//    so `const _exhaustive: never = status;` fails to compile — caught immediately.

Senior Engineer Perspective

Interviewers frequently simulate the "forgot to update" scenario live: add a member to the union and ask what breaks. Walking through exactly why the never assignment fails (the narrowed type is no longer empty) proves real understanding versus memorised boilerplate. Also worth mentioning: some teams use a small assertNever(x: never): never helper function instead of inline variable assignment, which reads slightly cleaner at call sites and centralises the thrown error message.

Q38. What's the difference between narrowing via the in operator vs typeof vs instanceof vs a custom guard?

ROI: ★★★★☆ Frequency: High

Short Answer

typeof narrows primitives ("string", "number", "function", etc). instanceof narrows by prototype chain, so it only works for class instances, not plain object literals or union members that share a structural shape. The in operator narrows by checking whether a specific property key exists on the value, which works for plain objects without a discriminant field. A custom type guard (arg is Type) is the escape hatch for any check the built-in operators can't express.

Detailed Answer

Choosing the right one matters: instanceof fails silently-wrong on data that came from JSON.parse (parsed objects are never instances of your classes, even if they have the same shape), so it's only appropriate for values you know were actually constructed with new. in is the right tool for a union of plain object shapes that don't share a clean literal discriminant but do differ in which keys exist. typeof is limited to JS primitives and won't help distinguish between two object shapes at all. Custom guards are needed once the check involves multiple conditions, external validation, or logic that doesn't map onto a single operator.

Code Example

// typeof — primitives
function double(x: number | string) {
  return typeof x === "number" ? x * 2 : x.repeat(2);
}

// instanceof — class instances only
class ApiError extends Error {}
function handle(err: unknown) {
  if (err instanceof ApiError) { /* narrowed to ApiError */ }
}

// in — plain objects without a literal discriminant
type Cat = { meow: () => void };
type Dog = { bark: () => void };
function speak(pet: Cat | Dog) {
  if ("meow" in pet) pet.meow(); else pet.bark();
}

// custom guard — anything the above can't express
function isNonEmptyArray<T>(arr: T[]): arr is [T, ...T[]] {
  return arr.length > 0;
}

Senior Engineer Perspective

The trap interviewers set is asking you to narrow a value that came from JSON.parse using instanceof — the correct answer is that it will never match, because parsed data is a plain object, never a real class instance, regardless of how similar the shape looks. Picking the operator that matches the actual origin and shape of the data (not just whichever one compiles) is the real skill being tested.

Q39. How do you model a finite state machine (e.g. traffic light, wizard steps) with discriminated unions?

ROI: ★★★★☆ Frequency: Medium

Short Answer

Represent each state as a union member with a literal state discriminant plus only the data valid in that state, and represent transitions as a function that pattern-matches the current state and event to compute the next state. Because the union is exhaustive-checkable, an invalid transition (e.g. trying to go from "red" directly to "green") is something you can choose to make either a no-op or a compile-time-checked impossibility, depending on whether you model it in the type or the transition function.

Detailed Answer

This is the same discriminated-union pattern as fetch/loading state (Q5), applied to a machine with more than one dimension of variation and explicit transitions. Each state can carry state-specific data (a "wizard step 2" state might carry the data collected in step 1), which a set of independent booleans could never express safely. The transition function's return type should be the same union, and combined with the never exhaustiveness check (Q37), adding a new state without updating every transition site becomes a compile error.

Code Example

type TrafficLight =
  | { state: "red" }
  | { state: "green" }
  | { state: "yellow" };

type Event = { type: "TIMER" };

function transition(light: TrafficLight, event: Event): TrafficLight {
  switch (light.state) {
    case "red": return { state: "green" };
    case "green": return { state: "yellow" };
    case "yellow": return { state: "red" };
  }
}

// Wizard step carrying step-specific data
type WizardState =
  | { step: "account"; }
  | { step: "profile"; email: string }        // only valid after "account"
  | { step: "confirm"; email: string; name: string };

Senior Engineer Perspective

Interviewers may ask when to reach for a real library (XState) instead of hand-rolling this — the honest answer is once you need parallel states, history states, guarded/conditional transitions, or visual tooling; for a linear wizard or a handful of UI states, a hand-rolled discriminated union with a transition function is simpler, has zero dependencies, and is fully type-checked with tools you already have.

Q40. What is control flow analysis, and how does destructuring interact with narrowing (why can narrowing get lost)?

ROI: ★★★★☆ Frequency: Medium

Short Answer

Control flow analysis is how TypeScript tracks a variable's narrowed type through branches, based on the code path that reaches each point. It's tied to the exact variable (or property access expression) you checked — if you destructure a value into a new local before narrowing, or narrow one variable but read a property off a different (even structurally identical) object, the narrowing doesn't transfer, because the compiler is tracking the binding, not just the runtime value.

Detailed Answer

A very common real bug: you check if (props.state.status === "success"), then destructure const { data } = props.state on the next line — this works, because the destructuring happens after the narrowing check on the same expression. But if you destructure first (const { status, data } = props.state) and then check if (status === "success"), data is not narrowed, because narrowing tracks props.state's discriminant, and once destructured, status and data are independent bindings with no remembered relationship between them.

Code Example

type State = { status: "loading" } | { status: "success"; data: string };

function ok(state: State) {
  if (state.status === "success") {
    state.data; // fine — narrowing applies to `state`, checked right here
  }
}

function broken(state: State) {
  const { status, data } = state; // destructured BEFORE narrowing
  // data: string | undefined  — TS can't relate `status` back to `data`
  if (status === "success") {
    // data is still `string | undefined` here — narrowing was lost
  }
}

function fixed(state: State) {
  if (state.status === "success") {
    const { data } = state; // destructure AFTER narrowing — data: string
  }
}

Senior Engineer Perspective

This is a genuinely common, easy-to-miss real bug, which is exactly why it's a favourite interview probe — candidates who've never hit it usually guess that destructuring "shouldn't matter." The strong answer names the underlying mechanism (control flow analysis tracks specific expressions/bindings, not abstract runtime values) and gives the concrete fix: narrow first, destructure second, or destructure inside the narrowed branch rather than before it.

Q41. How do you narrow a discriminated union stored in an array or nested object?

ROI: ★★★☆☆ Frequency: Medium

Short Answer

Narrowing works the same way regardless of nesting depth — it operates on whatever expression you check, so items[0].status === "success" narrows items[0] at that point, but does not narrow every element of the array. To narrow every element you filter or map with a type guard, since array methods lose per-element narrowing across iterations unless you use a typed predicate.

Detailed Answer

A common mistake is checking a condition on one array element and assuming the rest of the array (or a later access via index) is also narrowed — TypeScript only narrows the exact expression checked, at the exact point checked, and array indices in particular are treated conservatively because the array could be mutated between the check and the later access. The practical fix for "give me only the success ones, correctly typed" is array.filter(isSuccess) where isSuccess is declared as a type predicate — Array.prototype.filter has an overload that preserves narrowing when the predicate itself is a type guard.

Code Example

type Result = { status: "loading" } | { status: "success"; data: string };

function isSuccess(r: Result): r is Extract<Result, { status: "success" }> {
  return r.status === "success";
}

function process(results: Result[]) {
  // filter with a type predicate narrows the whole resulting array
  const done = results.filter(isSuccess); // Extract<Result, {status:"success"}>[]
  done.forEach((r) => console.log(r.data)); // safe, no per-element check needed
}

// Nested object — narrowing applies to the exact accessed path
interface Wrapper { result: Result }
function handle(w: Wrapper) {
  if (w.result.status === "success") {
    w.result.data; // narrowed — same expression checked and read
  }
}

Senior Engineer Perspective

The filter-with-a-type-guard overload is one of the more underused corners of the standard library types — mentioning it unprompted signals real day-to-day fluency rather than textbook knowledge. A good follow-up: why doesn't TypeScript narrow every element after checking just one? Because arrays are mutable reference types — the compiler cannot assume other elements (or even the same index later) still hold what they held at check time.

Q42. What are branded/nominal types and how do you simulate nominal typing in TypeScript?

ROI: ★★★☆☆ Frequency: Medium

Short Answer

TypeScript uses structural typing — two types with the same shape are interchangeable, even if they mean different things (a UserId and an OrderId both typed as string are freely swappable). A branded (nominal) type attaches a unique, unused marker property to an otherwise identical primitive so the compiler treats it as a distinct type, preventing accidental mixing even though the runtime value is still a plain string or number.

Detailed Answer

The brand is a phantom property that never actually exists at runtime — it's added purely via a type assertion at the one place values of that type are legitimately created (a constructor function or a validated parser), and every other part of the codebase only receives already-branded values. This closes the specific gap where structural typing allows a raw string to silently satisfy a UserId parameter, which is exactly the class of bug template-literal ID typing (Q94) also targets from a different angle.

Code Example

type UserId = string & { readonly __brand: "UserId" };
type OrderId = string & { readonly __brand: "OrderId" };

function toUserId(raw: string): UserId {
  return raw as UserId; // the ONE place the assertion is allowed
}

function getUser(id: UserId) { /* ... */ }

const userId = toUserId("u_123");
getUser(userId);            // OK
// getUser("u_123");        // Error — plain string is not a UserId
// getUser(orderId);        // Error — OrderId and UserId are NOT interchangeable
//                            even though both are structurally `string`

Senior Engineer Perspective

Interviewers want to hear you correctly diagnose why this is needed — because TypeScript's structural typing would otherwise let a string masquerade as any string-based ID type, silently permitting exactly the bug class ("passed an order id where a user id was expected") that a nominal type system would catch automatically. Be upfront that this is a workaround, not a real nominal type system, and that discipline is required at the single creation boundary — nothing stops a rogue as UserId cast elsewhere in the codebase, which is why teams often lint against ad-hoc uses of the brand.

Q43. How do you handle discriminated unions with optional/shared fields across variants without losing safety?

ROI: ★★★☆☆ Frequency: Medium

Short Answer

Factor genuinely shared fields into a common base type and intersect it into each variant, rather than duplicating them per member or — worse — making them optional across the whole union. Fields that only make sense for some variants stay variant-specific; fields common to every variant belong in the shared base so a rename only has to happen once.

Detailed Answer

The tempting-but-wrong shortcut is to make a field optional at the union level just because one variant doesn't use it — that reopens exactly the "impossible state" problem discriminated unions exist to close, since now every consumer must re-check whether the field is present regardless of which variant they're in. The correct structure is type Variant = Base & ({ kind: "a"; extra: string } | { kind: "b" }), which keeps common fields universally present while variant-specific fields remain properly scoped.

Code Example

interface BaseEvent {
  id: string;
  timestamp: number;
}

// Shared fields via intersection with a union of variant-specific shapes
type AppEvent = BaseEvent &
  (
    | { kind: "click"; targetId: string }
    | { kind: "pageview"; url: string }
    | { kind: "logout" }
  );

function handle(event: AppEvent) {
  event.id;        // always present — shared base
  event.timestamp; // always present — shared base
  if (event.kind === "click") {
    event.targetId; // only here — variant-specific, still narrowed correctly
  }
}

Senior Engineer Perspective

This question is really testing type-modelling judgment under a slightly awkward real-world constraint (genuinely shared fields), not just knowledge of the discriminated-union syntax. The strongest answers explicitly reject the "just make it optional" shortcut and explain why it reintroduces the exact bug class the union was meant to prevent — that's the difference between knowing the pattern and knowing why it works.

SECTION 8 - TYPE-SAFE EVENT HANDLERS & REFS

Q44. How do you type a ref that can point to either a DOM element or a custom component instance?

ROI: ★★★☆☆ Frequency: Medium

Short Answer

Type the ref as a union of the possible targets, e.g. useRef<HTMLDivElement | CustomInstance>(null), and narrow with an instanceof/property check before calling target-specific members. In practice this is rare — it usually signals the component should expose a single, deliberately-shaped imperative handle via useImperativeHandle (Q46) instead of leaking a raw union of possible ref targets to consumers.

Detailed Answer

If a component conditionally renders either a plain <div> or a wrapped third-party widget with its own imperative API, callers of the ref need to know which one they got before calling any methods. A union ref type is honest about that ambiguity, but it pushes the narrowing burden onto every consumer. The cleaner alternative most codebases converge on is to normalise both cases behind one stable interface using useImperativeHandle, so the ref's public type is always the same regardless of which branch actually rendered.

Code Example

interface VideoPlayerHandle {
  play: () => void;
  pause: () => void;
}

// Union ref — consumer must narrow before use
function useEitherRef() {
  const ref = useRef<HTMLVideoElement | VideoPlayerHandle | null>(null);
  const play = () => {
    const el = ref.current;
    if (el instanceof HTMLVideoElement) el.play();
    else el?.play(); // custom handle — same method name, different call path
  };
  return { ref, play };
}

Senior Engineer Perspective

The strongest answer names the trade-off directly: a union ref type is technically correct but pushes complexity onto every consumer, whereas useImperativeHandle centralises the ambiguity once, inside the component that actually knows which branch rendered. Interviewers reward recognising when a "more precise" type is actually the wrong design choice compared to hiding the complexity behind a stable API.

Q45. How do you type a generic forwardRef component with a generic prop type T?

ROI: ★★★☆☆ Frequency: Medium

Short Answer

forwardRef's type signature is not itself generic over an arbitrary caller-supplied T in older React typings, so combining it with a generic component requires either a manual cast to a generic function type, or reaching for the newer forwardRef overload / React 19's direct-ref-as-prop approach, which sidesteps the problem entirely by not needing forwardRef at all.

Detailed Answer

The core issue: forwardRef<RefType, PropsType> returns a component whose props type is fixed to whatever PropsType you passed in — it does not preserve a generic parameter for callers to instantiate differently each time, unlike a plain generic function component. The common workaround is to write the implementation with forwardRef as usual and then cast the exported value to a hand-written generic function type that describes what you actually want callers to see.

Code Example

interface ListProps<T> {
  items: T[];
  renderItem: (item: T) => React.ReactNode;
}

// forwardRef itself can't stay generic across call sites, so the
// implementation is written normally and re-exposed with a cast.
function ListInner<T>(
  { items, renderItem }: ListProps<T>,
  ref: React.ForwardedRef<HTMLUListElement>
) {
  return <ul ref={ref}>{items.map((it, i) => <li key={i}>{renderItem(it)}</li>)}</ul>;
}

// re-expose with the generic signature callers actually need
const List = forwardRef(ListInner) as <T>(
  props: ListProps<T> & { ref?: React.ForwardedRef<HTMLUListElement> }
) => ReturnType<typeof ListInner>;

Senior Engineer Perspective

This is one of the sharper edges of React + TypeScript, and interviewers use it to separate people who've actually shipped a generic, ref-forwarding component from people who've only used forwardRef with concrete props. The strongest closing point: React 19's ability to pass ref as an ordinary prop on function components removes this friction entirely, since a plain generic function component can simply include ref in its own generic props type — worth naming as the forward-looking fix.

Q46. How do you correctly type useImperativeHandle to expose a custom imperative API?

ROI: ★★★★☆ Frequency: Medium

Short Answer

Define an interface describing exactly the methods you want to expose, use it as the type argument to both forwardRef<Handle, Props> and useImperativeHandle<Handle, Handle>, and return an object literal matching that interface. This deliberately narrows what a parent can call through the ref to a curated API instead of the full underlying DOM node.

Detailed Answer

useImperativeHandle takes the ref, a factory function returning the handle object, and a dependency array. The handle's type should be declared once and reused as both the forwardRef ref-type parameter and the useImperativeHandle generic, so the parent's ref.current is typed as exactly that curated interface — nothing more, nothing less — even though internally the component still has full access to the real DOM node via its own internal ref.

Code Example

interface InputHandle {
  focus: () => void;
  clear: () => void;
}

interface InputProps {
  label: string;
}

const CustomInput = forwardRef<InputHandle, InputProps>(({ label }, ref) => {
  const inputRef = useRef<HTMLInputElement>(null);

  useImperativeHandle<InputHandle, InputHandle>(ref, () => ({
    focus: () => inputRef.current?.focus(),
    clear: () => { if (inputRef.current) inputRef.current.value = ""; },
  }), []);

  return <label>{label}<input ref={inputRef} /></label>;
});

// Parent — ref.current is InputHandle, NOT HTMLInputElement
function Form() {
  const handleRef = useRef<InputHandle>(null);
  return (
    <>
      <CustomInput ref={handleRef} label="Name" />
      <button onClick={() => handleRef.current?.focus()}>Focus</button>
    </>
  );
}

Senior Engineer Perspective

Interviewers listen for the design justification, not just the syntax: exposing a curated handle instead of the raw DOM node is an encapsulation boundary, similar to a private field — it stops parents from reaching in and doing things the component didn't intend to support (like directly mutating an input's value outside React's render cycle). A good follow-up asks when this pattern is overkill; for a component that just needs .focus(), a plain forwarded DOM ref is simpler and this abstraction only earns its keep once the exposed API differs meaningfully from the raw element's.

Q47. How do you type keyboard/clipboard/drag events, and what's different about them vs mouse/change events?

ROI: ★★★☆☆ Frequency: Medium

Short Answer

Each React synthetic event has its own generic type parameterised by the element — React.KeyboardEvent<HTMLInputElement>, React.ClipboardEvent<HTMLDivElement>, React.DragEvent<HTMLDivElement> — following the same pattern as ChangeEvent/MouseEvent. What differs is which properties are available: keyboard events expose key/code/modifier flags, clipboard events expose clipboardData, and drag events expose dataTransfer plus a specific set of drag-lifecycle handler props (onDragStart, onDragOver, onDrop, etc).

Detailed Answer

A frequent mistake with keyboard events is checking deprecated properties (keyCode, which) instead of the modern key string, which TypeScript's types still technically allow (they're deprecated, not removed) but shouldn't be relied on. Drag-and-drop handlers need e.preventDefault() called specifically inside onDragOver for onDrop to fire at all — a runtime requirement that the types don't enforce but that every drag-and-drop implementation needs to get right.

Code Example

function onKeyDown(e: React.KeyboardEvent<HTMLInputElement>) {
  if (e.key === "Enter") submit();
  if (e.ctrlKey && e.key === "s") { e.preventDefault(); save(); }
}

function onPaste(e: React.ClipboardEvent<HTMLInputElement>) {
  const text = e.clipboardData.getData("text/plain");
  console.log(text);
}

function onDrop(e: React.DragEvent<HTMLDivElement>) {
  e.preventDefault();
  const files = Array.from(e.dataTransfer.files);
  console.log(files.map((f) => f.name));
}
function onDragOver(e: React.DragEvent<HTMLDivElement>) {
  e.preventDefault(); // required — allows onDrop to fire
}

Senior Engineer Perspective

The types will happily let you write buggy drag-and-drop code (they don't encode the "must call preventDefault in onDragOver" runtime requirement), so interviewers use this to test whether your knowledge of the DOM event model is real or just type-system deep. The same applies to keyboard handling: mentioning that key is the modern, correct property (locale-aware, human-readable) versus the deprecated numeric keyCode shows current, practical knowledge.

Q48. How do you type a callback ref (function ref) vs an object ref?

ROI: ★★★☆☆ Frequency: Medium

Short Answer

An object ref (from useRef) is typed as RefObject<T> or MutableRefObject<T> and exposes .current. A callback ref is just a function typed (instance: T | null) => void, called by React with the element on mount and with null on unmount — it has no persistent .current of its own, so any state it needs to remember must be captured via closure or written into a separate ref.

Detailed Answer

Callback refs are useful when you need to run logic exactly at attach/detach time — measuring a node's layout the instant it mounts, or managing a third-party library's imperative setup/teardown tied to the DOM node's lifecycle — rather than reading a value later inside an effect. Because a new inline callback-ref function is created every render by default, React treats it as a different ref and calls it with null then the element again on every render unless it's memoised with useCallback, which the object-ref pattern doesn't require.

Code Example

// Object ref
const boxRef = useRef<HTMLDivElement>(null);

// Callback ref — runs exactly at attach/detach time
const measuredRef = useCallback((node: HTMLDivElement | null) => {
  if (node !== null) {
    console.log("mounted with height", node.getBoundingClientRect().height);
  }
  // node is null here on unmount — good place for cleanup
}, []);

<div ref={measuredRef} />;

// Typing a reusable callback-ref-accepting prop
interface MeasureProps {
  onMeasure: (node: HTMLElement | null) => void;
}

Senior Engineer Perspective

The re-render footgun is the detail worth volunteering: an inline callback ref (ref={(node) => ...}) is a new function every render, so React calls it with null and then the node again on every single re-render — usually harmless, but expensive or buggy if the callback does non-trivial work. Wrapping it in useCallback is the fix, and knowing to reach for it unprompted is the senior signal here.

Q49. How do you type an event handler prop that should accept either a native event handler or a custom simplified signature?

ROI: ★★★☆☆ Frequency: Medium

Short Answer

Design the prop's function signature around what your component actually hands the caller, not around React's native event type by default — most reusable component libraries expose a simplified callback (e.g. onChange: (value: string) => void) rather than the raw ChangeEvent, translating the native event internally. If both native-event and simplified callers must be supported, type the prop as a union of the two function signatures and normalise inside the component.

Detailed Answer

Exposing the raw synthetic event type leaks an implementation detail (which underlying DOM element is used) into your component's public API, making it harder to swap that element later without a breaking change. The common, more ergonomic pattern is for the component to accept a simplified callback and do the unwrapping (e => onChange(e.currentTarget.value)) internally, so consumers of your design-system component never need to know or care that a native <input> is involved underneath.

Code Example

// Design-system component — simplified callback, no leaked DOM detail
interface TextFieldProps {
  value: string;
  onChange: (value: string) => void; // NOT React.ChangeEventHandler
}
function TextField({ value, onChange }: TextFieldProps) {
  return (
    <input
      value={value}
      onChange={(e) => onChange(e.currentTarget.value)} // unwraps internally
    />
  );
}

// Supporting both shapes when a prop must remain flexible
type FlexibleHandler =
  | ((value: string) => void)
  | React.ChangeEventHandler<HTMLInputElement>;

Senior Engineer Perspective

This is a design-system judgment call, and interviewers building or reviewing shared component libraries care about it a lot: a simplified callback is easier to test, easier to reuse outside a DOM context (e.g. in React Native or in a Storybook mock), and doesn't couple your public API to a specific underlying element. Leaking ChangeEvent<HTMLInputElement> through a reusable component's props is a common code-smell worth naming directly.

Q50. How do you type refs with useRef when working with a mutable "latest value" pattern (avoiding stale closures)?

ROI: ★★★★☆ Frequency: Medium

Short Answer

Use useRef<T>(initialValue) with a non-null initial value so .current is a plain, non-nullable T, update it inside an effect that runs on every render (or every time the tracked value changes), and read .current from inside a stable callback (created once via useCallback(..., [])) that would otherwise close over a stale value.

Detailed Answer

This "latest ref" pattern exists specifically to defeat stale closures: a callback that needs to run with a stable identity (so it doesn't retrigger effects or break memoisation) can't simply list every changing value in its dependency array, because that would change its identity every render. Instead, the changing value is written into a ref on every render, and the stable callback reads .current at call time — always getting the latest value without needing to be recreated. The type is simply MutableRefObject<T>, same as any value ref; the pattern is architectural, not a typing trick.

Code Example

function useLatest<T>(value: T): React.MutableRefObject<T> {
  const ref = useRef<T>(value);
  useEffect(() => { ref.current = value; }); // runs every render, keeps it current
  return ref;
}

function useEventListener(onScroll: (y: number) => void) {
  const latestOnScroll = useLatest(onScroll); // always current, stable identity

  useEffect(() => {
    const handler = () => latestOnScroll.current(window.scrollY);
    window.addEventListener("scroll", handler);
    return () => window.removeEventListener("scroll", handler);
  }, []); // empty deps — listener attaches ONCE, never sees a stale onScroll
}

Senior Engineer Perspective

This pattern is the practical bridge between "hooks rely on closures" (JS fundamentals) and real production code that needs a stable subscription with always-current behaviour — event listeners, WebSocket handlers, and intervals are the classic cases. Interviewers value candidates who can explain why the effect has an empty dependency array (the listener is attached once) while the callback it invokes is never stale (because it reads through a ref, not a closed-over variable).

Q51. How do you correctly type synthetic events on custom/wrapped input components that forward props?

ROI: ★★★☆☆ Frequency: Medium

Short Answer

Extend the native element's prop type with React.ComponentProps<"input"> (or ComponentPropsWithoutRef<"input"> if you also forward a ref separately) so every native prop — including correctly-typed native event handlers like onChange — passes through automatically, then use Omit to override any prop whose signature you want to change.

Detailed Answer

Manually re-declaring every native input prop your wrapper forwards is both tedious and a maintenance hazard — new HTML attributes or React prop additions won't automatically flow through a hand-written interface. ComponentProps<"input"> derives the full native prop set (including onChange: ChangeEventHandler<HTMLInputElement>, disabled, placeholder, ARIA attributes, and so on) directly from React's own JSX intrinsic element typings, so your wrapper's props stay in sync with React's types automatically as they evolve.

Code Example

// Forwards ALL native input props, correctly typed, with zero duplication
interface StyledInputProps extends React.ComponentPropsWithoutRef<"input"> {
  invalid?: boolean; // one new prop this wrapper adds
}

const StyledInput = forwardRef<HTMLInputElement, StyledInputProps>(
  ({ invalid, className, ...rest }, ref) => (
    <input
      ref={ref}
      className={`${className ?? ""} ${invalid ? "input-error" : ""}`}
      {...rest} // onChange, onFocus, disabled, etc. all correctly typed already
    />
  )
);

// Overriding one native prop's signature while keeping the rest
type CustomOnChange = Omit<React.ComponentPropsWithoutRef<"input">, "onChange"> & {
  onChange: (value: string) => void; // simplified, per Q49
};

Senior Engineer Perspective

Reaching for ComponentProps<"input">/ComponentPropsWithoutRef<"input"> instead of hand-listing native attributes is a strong, immediately recognisable signal of real component-library experience. SECTION 9 - ADVANCED TYPE INFERENCE & CONDITIONAL TYPES

Q52. What does the infer keyword do, and where does it commonly appear in library type definitions?

ROI: ★★★★☆ Frequency: Medium

Short Answer

infer introduces a new type variable inside the extends clause of a conditional type, letting you "capture" a piece of a matched type to reuse in the result. It's how nearly every built-in type-extraction utility works: ReturnType, Parameters, Awaited, and countless library-authored helpers all pattern-match a shape and pull one piece out with infer.

Detailed Answer

Think of infer as destructuring at the type level: T extends (...args: any[]) => infer R ? R : never reads as "if T matches the shape of a function, capture whatever its return type is into R and use that; otherwise fall back to never." You can place infer in any structural position — array element, promise payload, tuple slot, object property — anywhere TypeScript can match a piece of a larger shape.

Code Example

// Extract array element type
type ElementOf<T> = T extends (infer U)[] ? U : never;
type A = ElementOf<string[]>; // string

// Extract a promise's payload
type Unwrap<T> = T extends Promise<infer U> ? U : T;
type B = Unwrap<Promise<number>>; // number

// Extract the first parameter of a function
type FirstArg<T> = T extends (first: infer F, ...rest: any[]) => any ? F : never;
type C = FirstArg<(name: string, age: number) => void>; // string

Senior Engineer Perspective

Interviewers use infer exercises to separate "uses TypeScript" from "understands TypeScript's type system as a small functional language." The strongest answers describe it as pattern matching/destructuring rather than memorising the syntax, because that framing correctly predicts how it behaves in more exotic positions (nested generics, tuples, template literals) that a memorized snippet wouldn't cover.

Q53. What is a distributive conditional type, and when does distribution NOT happen?

ROI: ★★★★☆ Frequency: Medium

Short Answer

When the checked type in a conditional type is a "naked" type parameter (used bare, not wrapped in a tuple or object) and you pass it a union, TypeScript applies the conditional to each member of the union separately and unions the results — this is distribution. Wrapping the checked type in a tuple ([T]) or any other structural container suppresses distribution, so the whole union is checked as one unit instead.

Detailed Answer

This is exactly why Exclude/Extract/NonNullable (Q29) work member-by-member: their definitions use a naked T, so Exclude<"a" | "b", "a"> evaluates as Exclude<"a","a"> | Exclude<"b","a">, not as one check against the whole union. Sometimes you explicitly want the non-distributive behaviour — e.g. checking "is this union entirely assignable to X" as a single question — and the standard trick is wrapping both sides in a one-element tuple, which disables the per-member distribution.

Code Example

// Distributive — naked T, applied per union member
type ToArray<T> = T extends any ? T[] : never;
type Result1 = ToArray<string | number>; // string[] | number[]

// Non-distributive — wrapping in a tuple suppresses distribution
type ToArrayNonDist<T> = [T] extends [any] ? T[] : never;
type Result2 = ToArrayNonDist<string | number>; // (string | number)[]

// Why Exclude distributes:
type MyExclude<T, U> = T extends U ? never : T; // T is naked -> distributes
type WithoutA = MyExclude<"a" | "b" | "c", "a">; // "b" | "c"

Senior Engineer Perspective

This is one of the genuinely surprising corners of the type system, and getting bitten by it usually happens the first time someone writes a conditional type that unexpectedly explodes a union into a union of results instead of evaluating once. Interviewers may ask you to fix a conditional type that's "distributing when it shouldn't" — the tuple-wrapping trick, and knowing exactly why it works (the checked type is no longer naked), is the concrete, testable answer.

Q54. How would you write a conditional type that extracts the props type from a component?

ROI: ★★★☆☆ Frequency: Medium

Short Answer

React already ships this as React.ComponentProps<typeof MyComponent>, which is itself implemented with a conditional type using infer over the component's single props parameter. Reimplementing it is a good exercise: match against (props: infer P) => any for function components, or React.ComponentType<infer P> to also cover class components.

Detailed Answer

The practical use is deriving prop types from third-party or legacy components that don't export their prop interface directly — instead of duplicating (and risking drift from) an undocumented shape, you extract it straight from the component's own type. This is exactly the same "derive, don't duplicate" instinct as ReturnType (Q30), applied specifically to component prop shapes.

Code Example

// Simplified reimplementation of React.ComponentProps
type PropsOf<C> = C extends (props: infer P) => any
  ? P
  : C extends new (props: infer P) => any
  ? P
  : never;

function Button({ label, onClick }: { label: string; onClick: () => void }) {
  return <button onClick={onClick}>{label}</button>;
}

type ButtonProps = PropsOf<typeof Button>; // { label: string; onClick: () => void }

// Using it to extend a third-party component you don't own the types for
interface EnhancedButtonProps extends React.ComponentProps<typeof Button> {
  loading?: boolean;
}

Senior Engineer Perspective

Being able to hand-roll PropsOf demonstrates you understand what React.ComponentProps actually is under the hood rather than treating it as unexplainable magic. A realistic follow-up: how would you handle a component that's polymorphic (accepts an as prop to render as different elements)? That requires combining this pattern with a generic and conditional types keyed off the as value — a noticeably harder, more senior extension of the same idea.

Q55. What is the difference between T extends U ? X : Y evaluated with a union vs a single concrete type?

ROI: ★★★☆☆ Frequency: Medium

Short Answer

With a single concrete type, the conditional evaluates once and produces one result. With a union passed to a naked type parameter, it distributes (Q53) — evaluating once per member and unioning the results together. This means the "same" conditional type definition can behave completely differently depending on whether it's instantiated with one type or several, which is a common source of confusion when reasoning about generic utility types in isolation.

Detailed Answer

This matters most when a conditional type's two branches are asymmetric — e.g. one branch returns never. Because never is the identity element for union (unioning anything with never just gives that thing back), distributing over a union and filtering some members out to never effectively implements filtering the union, which is exactly the mechanism behind Exclude. Passing a single type sidesteps all of this — there's no union to distribute over, so the conditional just evaluates its condition directly.

Code Example

type IsString<T> = T extends string ? T : never;

type Single = IsString<"a">;          // "a" — evaluated once
type FromUnion = IsString<"a" | 1 | "b">; // "a" | "b" — distributed, non-strings filtered to never and dropped

// This is literally how Extract is implemented:
type MyExtract<T, U> = T extends U ? T : never;

Senior Engineer Perspective

The insight worth stating explicitly: distribution over a union combined with a never branch is not a special case syntactically, it's an emergent consequence of two simple rules (distribution + never vanishing from unions) composing together. Interviewers who ask you to "explain why Extract/Exclude work" are really asking whether you can derive this from first principles rather than having memorised it as a fact about two specific utility types.

Q56. How do recursive conditional types work (e.g. deep partial, flatten a nested array type)?

ROI: ★★★☆☆ Frequency: Medium

Short Answer

A conditional (or mapped) type can reference itself in one of its branches, causing the compiler to keep re-evaluating it against smaller and smaller pieces of the input type until it hits a base case that stops the recursion. This is exactly how DeepReadonly (Q31) and a "flatten nested arrays" type both work — recurse into the structure, bottom out on primitives.

Detailed Answer

TypeScript enforces a recursion depth limit (historically around 45–50, with looser limits for "tail-recursive" patterns in newer compiler versions) specifically to prevent runaway type computations from hanging the compiler on pathological inputs. Well-designed recursive types should always be structurally shrinking — recursing into a strictly smaller piece of the input each time — so that realistic, finite data structures terminate long before hitting that limit.

Code Example

// DeepPartial — recurse into nested objects, base case = non-object
type DeepPartial<T> = T extends object
  ? { [K in keyof T]?: DeepPartial<T[K]> }
  : T;

// Flatten an arbitrarily nested array type down to its element type
type Flatten<T> = T extends (infer U)[] ? Flatten<U> : T;
type F1 = Flatten<number[][][]>; // number

interface Nested { a: { b: { c: number } } }
type PartialNested = DeepPartial<Nested>; // a?.b?.c? all optional, recursively

Senior Engineer Perspective

Interviewers who ask this are checking whether you understand recursion has a real, practical ceiling in the type system — not infinite, and not free. A grounded answer names the depth limit and explains why it exists (protecting compiler performance from pathological or accidentally-infinite recursive types), rather than presenting recursive conditional types as an unlimited superpower.

Q57. What are variadic tuple types and how are they used to type function composition (pipe/compose)?

ROI: ★★★☆☆ Frequency: Medium

Short Answer

Variadic tuple types let you spread a type parameter that represents an arbitrary-length tuple into another tuple or parameter list ([first: A, ...rest: R]), and have the compiler track exactly how many elements and what types are in that "rest" portion. They're what makes it possible to type a function like concat, curry, or a type-safe pipe/compose without falling back to any[] and losing all argument/return tracking.

Detailed Answer

Before variadic tuples, typing a generic function that takes "some arguments, plus one more prepended" required either overload signatures for every arity or giving up and using any[]. With variadic tuples, function prepend<T, R extends unknown[]>(item: T, rest: [...R]): [T, ...R] preserves the exact shape and length of whatever tuple was passed. A fully type-safe pipe typically still needs a bounded set of overloads (one per practical arity, since fully generic type-level chaining of arbitrary functions is difficult to express precisely), but each overload itself relies on variadic tuple spreading to stay accurate.

Code Example

// Basic variadic tuple manipulation
type Prepend<T, R extends readonly unknown[]> = [T, ...R];
type P1 = Prepend<string, [number, boolean]>; // [string, number, boolean]

// A two-function pipe, fully typed via variadic tuples + infer
function pipe<A extends unknown[], B, C>(
  f: (...args: A) => B,
  g: (b: B) => C
): (...args: A) => C {
  return (...args: A) => g(f(...args));
}

const parseAndDouble = pipe(
  (s: string) => parseInt(s, 10), // A = [string], B = number
  (n: number) => n * 2            // C = number
);
parseAndDouble("21"); // 42, fully typed end to end

Senior Engineer Perspective

Interviewers probing this topic usually want to know whether you recognise the practical limit: a fully generic, arbitrary-arity pipe that stays perfectly typed for every chain length is genuinely difficult (libraries like fp-ts and lodash/fp lean on many stacked overloads for exactly this reason). The mature answer is naming that trade-off rather than claiming variadic tuples make arbitrary-length type-safe composition trivial — they make it possible for bounded, realistic arities, not free for any length.

Q58. How does TypeScript's control flow narrowing interact with generics (why can't you narrow a generic T inside a function)?

ROI: ★★★☆☆ Frequency: Medium

Short Answer

Inside a generic function body, T represents every possible type the caller could substitute, not one concrete type — so a runtime check like typeof value === "string" can't narrow value: T down to T & string the way it would narrow a real union, because the compiler must keep the code valid for all possible instantiations of T, including ones where that check could never be true.

Detailed Answer

This surprises people who expect narrowing to "just work" inside generic code the same way it does on concrete union types. The compiler's job inside a generic function is to type-check the body once, generically, for every possible caller — it cannot assume anything about T beyond its constraint. The practical workaround is casting after the runtime check (when you're confident it's safe), or restructuring the function to accept a concrete union instead of an unconstrained generic when narrowing is actually required.

Code Example

function processGeneric<T>(value: T) {
  if (typeof value === "string") {
    // value here is NOT narrowed to `string` in older/strict generic contexts
    // in practice modern TS does narrow some generic cases via typeof, but
    // the underlying rule remains: T could be instantiated as `unknown`-like,
    // so narrowing is best-effort, not guaranteed the way it is for real unions
    value.toUpperCase(); // may still require a cast in more complex generic bodies
  }
}

// The common, reliable workaround: accept a real union, not an unconstrained T
function processUnion(value: string | number) {
  if (typeof value === "string") {
    value.toUpperCase(); // fully narrowed, guaranteed
  }
}

Senior Engineer Perspective

This is a nuanced, easy-to-get-slightly-wrong area even for experienced engineers — TypeScript's narrowing inside generic bodies has improved release over release and behaves better than it used to in many common cases, but the underlying reason it's ever limited (the compiler must remain sound for every possible instantiation of T) is the answer interviewers actually want. Volunteering "generic code is checked once for all callers, so narrowing can't assume any specific instantiation" shows genuine understanding rather than a memorised gotcha.

Q59. What is "type-level programming" and where's the line where you should stop and use runtime code instead?

ROI: ★★★★☆ Frequency: Medium

Short Answer

Type-level programming is using TypeScript's conditional types, mapped types, and infer as a small, purely compile-time functional language to compute types from other types. The line to stop is whenever the logic actually needs to run against real, dynamic data (validating a value at runtime, transforming data received over the network) — types disappear entirely at compile time, so they can never substitute for actual runtime validation or logic.

Detailed Answer

Type-level code is extremely good at encoding structural relationships that are known statically — "this function's return type equals its first argument's property type," "this union excludes one member," "this string matches a template shape." It is the wrong tool the moment the answer depends on a value only known at runtime (user input, an API response, a feature flag read from a database), because there's no code left to execute once compilation finishes — tsc erases all types entirely. A team that over-invests in elaborate type-level gymnastics for something that's really a runtime concern usually ends up with slow, hard-to-debug compiler errors instead of a clear runtime error message.

Code Example

// Appropriate type-level programming — purely structural, known at compile time
type Keys<T> = keyof T;
type FirstArg<F> = F extends (arg: infer A, ...rest: any[]) => any ? A : never;

// Inappropriate — trying to "validate" a runtime value using only types
// (this compiles but proves NOTHING about the actual runtime JSON)
function unsafeParse<T>(json: string): T {
  return JSON.parse(json); // no real check ever happens — T is a lie here
}

// Correct — push the actual validation into runtime code (Zod et al.)
function safeParse<T>(schema: z.ZodType<T>, json: string): T {
  return schema.parse(JSON.parse(json)); // real runtime check backs the type
}

Senior Engineer Perspective

This question is really about engineering judgment, not TypeScript trivia — the strongest candidates can point to a specific past decision where they chose runtime validation over an elaborate type-only trick (or vice versa) and explain the trade-off in compile time, error message clarity, and actual safety. The line to draw crisply: types describe what the compiler assumes is true; only runtime code can make something actually true.

SECTION 10 - TYPING CONTEXT, REDUCERS & STATE MACHINES

Q60. How do you type a useReducer setup where actions carry different payload shapes per action type?

ROI: ★★★★★ Frequency: High

Short Answer

Model the actions as a discriminated union — one member per action type, each carrying only the payload fields that action actually needs — and let the reducer's switch narrow the payload per case automatically. This is the same discriminated-union technique from Q5/Q36 applied specifically to Redux/useReducer-style actions.

Detailed Answer

The anti-pattern is a single loose Action type like { type: string; payload?: any }, which compiles for literally any dispatched action regardless of whether the payload matches what that action actually needs — a typo'd action type or a missing required field is invisible to the compiler. With a discriminated union, dispatching an action with the wrong payload shape for its type is a compile error, and the reducer's switch gets per-branch payload narrowing for free, exactly like any other discriminated union.

Code Example

interface TodoState {
  items: { id: string; text: string; done: boolean }[];
}

type TodoAction =
  | { type: "add"; text: string }
  | { type: "toggle"; id: string }
  | { type: "remove"; id: string }
  | { type: "clear" };

function todoReducer(state: TodoState, action: TodoAction): TodoState {
  switch (action.type) {
    case "add":
      return { items: [...state.items, { id: crypto.randomUUID(), text: action.text, done: false }] };
    case "toggle":
      return { items: state.items.map((i) => i.id === action.id ? { ...i, done: !i.done } : i) };
    case "remove":
      return { items: state.items.filter((i) => i.id !== action.id) };
    case "clear":
      return { items: [] };
  }
}

const [state, dispatch] = useReducer(todoReducer, { items: [] });
dispatch({ type: "add", text: "Ship it" });
// dispatch({ type: "add" });          // Error — missing required `text`
// dispatch({ type: "toggle", text: "x" }); // Error — `text` invalid on "toggle"

Senior Engineer Perspective

This is one of the highest-value, most-tested applications of discriminated unions in the entire chapter because it's something almost every non-trivial React app actually has. Combine it with the never-default exhaustiveness check from Q37 for the strongest possible answer — mention that omitting it means a newly-added action type can silently fall through the switch with no compiler warning.

Q61. How do you avoid prop-drilling dispatch by typing a split state/dispatch context pair?

ROI: ★★★★☆ Frequency: High

Short Answer

Create two separate contexts — one for the state value, one for the dispatch function — instead of one combined context. Components that only need to dispatch (and never read state) subscribe to the dispatch context alone, which never changes identity across renders, so they don't re-render when unrelated state updates.

Detailed Answer

A single combined { state, dispatch } context forces every consumer to re-render whenever either half changes, even components that only call dispatch and never read state — because they're still subscribed to a context whose value object changes reference whenever state updates. Splitting into StateContext and DispatchContext (with dispatch from useReducer guaranteed stable across renders) means dispatch-only consumers never re-render due to state changes, since the dispatch context's value never changes identity.

Code Example

interface TodoState { items: string[] }
type TodoAction = { type: "add"; text: string };

const TodoStateContext = createContext<TodoState | undefined>(undefined);
const TodoDispatchContext = createContext<React.Dispatch<TodoAction> | undefined>(undefined);

function TodoProvider({ children }: React.PropsWithChildren) {
  const [state, dispatch] = useReducer(reducer, { items: [] });
  return (
    <TodoStateContext.Provider value={state}>
      <TodoDispatchContext.Provider value={dispatch}>
        {children}
      </TodoDispatchContext.Provider>
    </TodoStateContext.Provider>
  );
}

export function useTodoState() {
  const ctx = useContext(TodoStateContext);
  if (!ctx) throw new Error("useTodoState must be used within TodoProvider");
  return ctx;
}
export function useTodoDispatch() {
  const ctx = useContext(TodoDispatchContext);
  if (!ctx) throw new Error("useTodoDispatch must be used within TodoProvider");
  return ctx; // stable identity — dispatch-only consumers never re-render on state change
}

Senior Engineer Perspective

This directly extends Q11's "split state and dispatch contexts" hint into a fully worked pattern, and interviewers use it to see whether you can connect a performance concern (unnecessary re-renders) to a typing decision (two contexts instead of one). The follow-up worth anticipating: does this help if state itself contains multiple unrelated slices? At that point you'd split further into per-slice contexts, or reach for a selector-based state library that avoids the "any context consumer re-renders on any change" limitation entirely.

Q62. How do you type a reducer that needs access to props/config not part of state (extra argument pattern)?

ROI: ★★★☆☆ Frequency: Medium

Short Answer

useReducer's reducer signature is fixed to (state, action) => state — it can't accept extra arguments directly. The typed workaround is to close over the extra config in the reducer function itself (creating it inside the component, or via a factory function parameterised by the config), or to fold the config into the action payload for the one dispatch that needs it.

Detailed Answer

If a reducer occasionally needs a value that isn't really "state" (a feature flag, a config object from props, a stable ID generator), the cleanest typed solution is usually a reducer factory: a function that takes the config and returns a properly-typed reducer closing over it. This keeps the reducer's own signature untouched (still exactly (state, action) => state, satisfying useReducer's type) while giving it access to whatever extra context it needs via closure instead of an extra parameter.

Code Example

interface Config { maxItems: number }
interface State { items: string[] }
type Action = { type: "add"; item: string };

// Factory closes over config; returned reducer still matches useReducer's shape
function createReducer(config: Config) {
  return function reducer(state: State, action: Action): State {
    switch (action.type) {
      case "add":
        if (state.items.length >= config.maxItems) return state; // uses closed-over config
        return { items: [...state.items, action.item] };
    }
  };
}

function List({ maxItems }: { maxItems: number }) {
  // useMemo keeps the reducer identity stable across renders unless maxItems changes
  const reducer = useMemo(() => createReducer({ maxItems }), [maxItems]);
  const [state, dispatch] = useReducer(reducer, { items: [] });
}

Senior Engineer Perspective

The subtlety worth naming: memoising the factory-produced reducer with useMemo matters, because passing a differently-identitied reducer function to useReducer on every render is at best wasteful and at worst a source of confusing behaviour if code elsewhere assumes reducer identity stability. This is a good moment to show awareness that useReducer's reducer argument is typically expected to be referentially stable, similar to how useEffect callbacks are expected to be pure of unstable identities.

Q63. How would you type a lightweight state machine hook (states + events) similar to XState?

ROI: ★★★☆☆ Frequency: Medium

Short Answer

Model the machine as two discriminated unions — one for states, one for events — plus a transition table typed as a nested mapped type keyed first by state, then by event, so that only valid (state, event) pairs are even representable, and each pair's transition function returns the next state.

Detailed Answer

A hand-rolled machine doesn't need XState's full feature set (parallel states, history, actors) to get real value from typing — the core payoff is a transition map whose keys are literally constrained to valid state names and whose values are constrained to valid event names for that state, so an invalid transition request is caught at the call site rather than silently ignored at runtime. Partial transition tables (not every state handles every event) are naturally expressed with optional properties in the nested mapped type.

Code Example

type MachineState = "idle" | "running" | "paused" | "done";
type MachineEvent = "start" | "pause" | "resume" | "finish";

type TransitionTable = {
  [S in MachineState]?: {
    [E in MachineEvent]?: MachineState;
  };
};

const transitions: TransitionTable = {
  idle: { start: "running" },
  running: { pause: "paused", finish: "done" },
  paused: { resume: "running" },
};

function useMachine(initial: MachineState) {
  const [state, setState] = useState<MachineState>(initial);
  const send = (event: MachineEvent) => {
    const next = transitions[state]?.[event];
    if (next) setState(next); // invalid transitions are simply no-ops
  };
  return { state, send };
}

Senior Engineer Perspective

Interviewers use this to see whether you can scale the discriminated-union + exhaustiveness toolkit up into a genuinely useful piece of infrastructure, not just answer isolated syntax questions. A good follow-up is when to graduate to XState — once you need parallel/nested states, guarded transitions with side conditions, or visual state-chart tooling for non-engineers, a hand-rolled table like this starts costing more to maintain than the library it was avoiding.

Q64. How do you type multiple nested/composed contexts without excessive boilerplate?

ROI: ★★★☆☆ Frequency: Medium

Short Answer

Write one small generic factory function — createSafeContext<T>() — that returns a [Provider, useContextValue] pair with the "throw if missing" guard from Q11 built in once, and reuse that factory for every context in the app instead of hand-writing the boilerplate (context creation, undefined default, guard hook) for each one individually.

Detailed Answer

Q11's pattern (default to undefined, throw in a custom hook) is correct but repetitive across many contexts in a real app. Factoring it into a single generic helper means every feature context — auth, theme, feature flags, a shopping cart — gets the same safety guarantee with a single line of setup, and any future improvement to the pattern (better error messages, dev-mode warnings) only needs to be made in one place.

Code Example

function createSafeContext<T>(name: string) {
  const Context = createContext<T | undefined>(undefined);

  function useSafeContext(): T {
    const ctx = useContext(Context);
    if (ctx === undefined) throw new Error(`use${name} must be used within ${name}Provider`);
    return ctx;
  }

  return [Context.Provider, useSafeContext] as const;
}

interface AuthValue { user: User | null }
const [AuthProvider, useAuth] = createSafeContext<AuthValue>("Auth");

interface ThemeValue { mode: "light" | "dark" }
const [ThemeProvider, useTheme] = createSafeContext<ThemeValue>("Theme");

// Usage is identical and safe for every context created this way
function Toolbar() {
  const { mode } = useTheme();
  const { user } = useAuth();
}

Senior Engineer Perspective

This question rewards the same instinct as the utility-type composition questions earlier in the chapter — recognising repeated boilerplate and factoring it into one small, reusable, generic piece of infrastructure rather than copy-pasting the pattern per feature. Mentioning that this is essentially what libraries like constate or the use-context-selector pattern formalise further shows awareness that this is a known, solved problem shape, not a one-off trick.

Q65. How do you type a Context whose value changes shape depending on a loading/auth state?

ROI: ★★★★☆ Frequency: Medium

Short Answer

Type the context's value as a discriminated union over the loading/auth states themselves, not as one flat object with optional fields — so a consumer that reads user is forced to first check that the context is in the "authenticated" state, exactly the same discipline as Q5/Q60 applied to context values instead of fetch state or reducer actions.

Detailed Answer

A context typed as { user: User | null; isLoading: boolean } lets a consumer read user.name while isLoading is still true and user is actually null, exactly the impossible-state bug this whole chapter keeps returning to. A discriminated-union context value ({ status: "loading" } | { status: "authenticated"; user: User } | { status: "anonymous" }) makes that specific bug a compile error instead of a runtime crash, at the cost of consumers needing an explicit status check before reading user-specific fields — a cost worth paying for anything security- or correctness-sensitive.

Code Example

type AuthContextValue =
  | { status: "loading" }
  | { status: "authenticated"; user: User; logout: () => void }
  | { status: "anonymous"; login: (email: string) => Promise<void> };

const AuthContext = createContext<AuthContextValue | undefined>(undefined);

function useAuth() {
  const ctx = useContext(AuthContext);
  if (!ctx) throw new Error("useAuth must be used within AuthProvider");
  return ctx;
}

function Toolbar() {
  const auth = useAuth();
  if (auth.status === "loading") return <Spinner />;
  if (auth.status === "anonymous") return <button onClick={() => auth.login("a@b.com")}>Log in</button>;
  return <button onClick={auth.logout}>Log out {auth.user.name}</button>; // user only here
}

Senior Engineer Perspective

This is one of the more realistic, high-stakes applications of discriminated unions — an auth context is exactly the kind of shared state where an "impossible state" bug (rendering user-specific UI before auth actually resolves) has real security and UX consequences, not just cosmetic ones. Interviewers who ask this are often really asking "do you apply the discriminated-union discipline consistently, or only in the textbook fetch-state example?"

Q66. How do you type dispatch such that only valid actions can be dispatched (no accidental extra fields)?

ROI: ★★★☆☆ Frequency: Medium

Short Answer

As long as your Action type is a proper discriminated union (not a loose { type: string; [key: string]: any }), React.Dispatch<Action> already rejects both unknown extra fields and mismatched payloads on excess-property-checked object literals passed directly to dispatch — the safety comes from the action type's precision, not from anything special in how dispatch itself is typed.

Detailed Answer

TypeScript's excess property check applies to object literals passed directly as an argument, so dispatch({ type: "add", text: "x", extra: true }) is flagged immediately if the "add" variant doesn't declare an extra field — but only for a literal passed inline. If you build the action object in a variable first and then dispatch the variable, excess property checking does not apply (structural typing allows extra properties on named variables), which is a genuine gap worth knowing about rather than assuming dispatch is airtight in every case.

Code Example

type Action = { type: "add"; text: string } | { type: "clear" };
declare const dispatch: React.Dispatch<Action>;

dispatch({ type: "add", text: "x" });               // OK
// dispatch({ type: "add", text: "x", extra: true }); // Error — excess property, caught inline

const built = { type: "add" as const, text: "x", extra: true };
dispatch(built); // NOT flagged — excess property check doesn't apply to variables,
                  // only to object literals passed directly

Senior Engineer Perspective

The gap between inline-literal dispatch and variable-then-dispatch is a genuinely subtle detail that most engineers never notice because they dispatch inline literals the overwhelming majority of the time — surfacing it unprompted is a strong signal of deep, hands-on TypeScript experience rather than surface-level familiarity. The practical mitigation some teams use is a lint rule discouraging pre-built, untyped action variables in favour of inline dispatch calls specifically to keep this safety net intact.

Q67. How do you unit test the types of a reducer (type-level tests) to prevent silent regressions?

ROI: ★★★☆☆ Frequency: Low-Medium

Short Answer

Type-level tests assert relationships between types at compile time rather than checking runtime values — the common pattern is a small helper like Expect<T extends true ? true : false> combined with an Equal<A, B> type, used in a .test-d.ts-style file that never runs, only compiles. If the asserted relationship stops holding (a reducer's return type silently widens, an action variant's payload changes), the file fails to compile, which CI treats as a normal type-check failure.

Detailed Answer

Runtime unit tests check that a reducer behaves correctly for given inputs, but they don't catch a change that widens or narrows the reducer's type in a way that breaks consumers elsewhere, if no runtime test happens to exercise that exact path. Tools like tsd, Vitest's built-in expectTypeOf, or a hand-rolled Equal/Expect pair let you pin down "the reducer's return type for this action is exactly this shape" as a first-class, CI-checked assertion, independent of runtime behaviour.

Code Example

// Minimal hand-rolled type-testing primitives
type Equal<A, B> =
  (<T>() => T extends A ? 1 : 2) extends (<T>() => T extends B ? 1 : 2) ? true : false;
type Expect<T extends true> = T;

type TodoAction = { type: "add"; text: string } | { type: "clear" };

// Compile-time-only assertions — no runtime code executes, tsc IS the test runner
type _test1 = Expect<Equal<ReturnType<typeof todoReducer>, TodoState>>;
type _test2 = Expect<Equal<Parameters<typeof todoReducer>[1], TodoAction>>;

// With Vitest's expectTypeOf, the same idea reads more like a normal test:
// expectTypeOf(todoReducer).returns.toEqualTypeOf<TodoState>();

Senior Engineer Perspective

This question separates people who treat the type system as documentation from people who treat it as a testable contract. The realistic framing to offer: type-level tests are worth writing for shared, widely-consumed types (a reducer, a public hook's return type, a design-system component's props) where a silent type regression would ripple through many call sites, not for every internal helper in the codebase — the cost/benefit only tips in favour of them at genuine API boundaries.

SECTION 11 - TYPE-SAFE API LAYERS

Q68. How do you design a typed API client with generic request/response typing end to end?

ROI: ★★★★☆ Frequency: High

Short Answer

Centralise a single generic request<T>(config) function that every endpoint-specific helper calls, so error handling, headers, and base-URL logic live in exactly one place, and each endpoint function simply pins T to its own response type. This keeps individual call sites simple (getUser(id): Promise<User>) while the generic core stays reusable across every endpoint in the app.

Detailed Answer

The layered design typically has three levels: a generic request<T> that handles the actual HTTP call, status-code checking, and error normalisation; a set of endpoint functions (getUser, listOrders) that call request with a concrete T; and, for genuine safety rather than just type assertions, a runtime schema per endpoint that request or the endpoint function parses the raw response through before returning it as T (tying back to Q17/Q69).

Code Example

interface RequestConfig {
  method: "GET" | "POST" | "PUT" | "DELETE";
  path: string;
  body?: unknown;
}

async function request<T>(config: RequestConfig): Promise<T> {
  const res = await fetch(config.path, {
    method: config.method,
    body: config.body ? JSON.stringify(config.body) : undefined,
    headers: { "Content-Type": "application/json" },
  });
  if (!res.ok) throw new ApiError(res.status, await res.text());
  return res.json() as Promise<T>; // still an assertion — see Q69 for the validated version
}

// Endpoint layer — each function pins T once
function getUser(id: string): Promise<User> {
  return request<User>({ method: "GET", path: `/api/users/${id}` });
}
function createUser(input: CreateUserInput): Promise<User> {
  return request<User>({ method: "POST", path: "/api/users", body: input });
}

class ApiError extends Error {
  constructor(public status: number, message: string) { super(message); }
}

Senior Engineer Perspective

Interviewers want to see the layering reasoning explicitly: generic infrastructure once, concrete typed endpoints many times, with the assertion-vs-validation trade-off (Q17) named as a known, deliberate simplification rather than an oversight. A strong follow-up asks how you'd add typed retry/backoff or request cancellation via AbortController without breaking the generic T threading — both fit naturally into RequestConfig without touching the endpoint layer at all.

Q69. How do you use Zod (or io-ts) to validate and infer types from an API response in one step?

ROI: ★★★★★ Frequency: High

Short Answer

Define the shape once as a runtime schema (z.object({...})), derive the static TypeScript type from that same schema with z.infer<typeof Schema>, and call Schema.parse(rawJson) at the network boundary. This guarantees the compile-time type and the runtime check can never drift apart, because they both originate from the exact same schema definition.

Detailed Answer

Writing an interface User {...} by hand next to a separate runtime validator is the classic drift trap — a backend field rename updates one but not the other, and the mismatch surfaces as a confusing runtime bug far from its actual cause. With z.infer, there's only one artifact to update; the type is a byproduct of the schema, not a parallel declaration. .parse() throws a descriptive ZodError on mismatch (good for hard boundary failures); .safeParse() instead returns a discriminated { success: true; data } | { success: false; error } result, better when you want to handle malformed data gracefully rather than throw.

Code Example

import { z } from "zod";

const UserSchema = z.object({
  id: z.string(),
  name: z.string(),
  email: z.string().email(),
  role: z.enum(["admin", "member"]),
});
type User = z.infer<typeof UserSchema>; // derived, never hand-written

async function getUser(id: string): Promise<User> {
  const res = await fetch(`/api/users/${id}`);
  const json: unknown = await res.json();
  return UserSchema.parse(json); // throws ZodError with a precise path on mismatch
}

// safeParse — no throw, explicit discriminated result
const result = UserSchema.safeParse(json);
if (result.success) {
  result.data; // User, fully typed
} else {
  console.error(result.error.issues); // structured, per-field validation errors
}

Senior Engineer Perspective

The single-source-of-truth argument is the whole point here, and interviewers listen for you to state it precisely: type and validation drift is a real production bug class, not a theoretical concern, and schema-first typing eliminates it structurally rather than through developer discipline. A common follow-up is .parse() vs .safeParse() — the right answer depends on whether a validation failure should be an unrecoverable error (hard API boundary) or a recoverable one (user-submitted form data you want to show inline errors for).

Q70. How do you type paginated API responses generically?

ROI: ★★★★☆ Frequency: Medium

Short Answer

Wrap the item type in a generic envelope — Paginated<T> = { items: T[]; page: number; pageSize: number; total: number } — and reuse that single envelope type for every paginated endpoint in the app, parameterising only the item type per endpoint (Paginated<User>, Paginated<Order>).

Detailed Answer

Without a shared generic envelope, every paginated endpoint tends to reinvent slightly different field names (total vs totalCount, items vs data, page vs pageNumber), which makes generic pagination UI components impossible to write against a consistent contract. Standardising on one Paginated<T> shape (and validating it with a generic Zod schema factory, if runtime validation is in play) lets a single <Pagination /> component or usePaginatedQuery hook work across every list in the app without per-endpoint special-casing.

Code Example

interface Paginated<T> {
  items: T[];
  page: number;
  pageSize: number;
  total: number;
}

async function listUsers(page: number): Promise<Paginated<User>> {
  return request<Paginated<User>>({ method: "GET", path: `/api/users?page=${page}` });
}

// A generic Zod schema factory mirrors the generic TS type
function paginatedSchema<T extends z.ZodTypeAny>(item: T) {
  return z.object({
    items: z.array(item),
    page: z.number(),
    pageSize: z.number(),
    total: z.number(),
  });
}
const PaginatedUserSchema = paginatedSchema(UserSchema); // z.infer matches Paginated<User>

// One generic UI component works for every paginated list

}

Senior Engineer Perspective

The senior signal is standardisation: recognising that inconsistent pagination shapes across endpoints is an API design smell worth pushing back on with backend teams, not just something to individually type around on the frontend. Mentioning a generic schema factory that mirrors the generic TS type shows the same "derive, don't duplicate" discipline extended from pure types into runtime validation as well.

Q71. How do you model API errors as part of the type system rather than relying on try/catch alone?

ROI: ★★★★☆ Frequency: Medium

Short Answer

Represent the outcome of an API call as a discriminated Result<T, E> type — { ok: true; value: T } | { ok: false; error: E } — returned from the function instead of thrown, so error handling becomes a type-checked branch the caller cannot skip, rather than an exception whose possibility is invisible in the function's signature.

Detailed Answer

A function typed Promise<User> that actually throws on failure is lying about its full behaviour — nothing in its signature tells a caller that failure is even possible, let alone what shape the error takes, so it's easy to forget the try/catch entirely. A Result<User, ApiError> return type makes the failure case a first-class, visible part of the contract; TypeScript won't let you access .value without first checking .ok, the same discriminated-union discipline applied to error handling instead of loading state.

Code Example

type Result<T, E> = { ok: true; value: T } | { ok: false; error: E };

interface ApiError { status: number; message: string }

async function getUserSafely(id: string): Promise<Result<User, ApiError>> {
  try {
    const res = await fetch(`/api/users/${id}`);
    if (!res.ok) return { ok: false, error: { status: res.status, message: await res.text() } };
    return { ok: true, value: UserSchema.parse(await res.json()) };
  } catch (e) {
    return { ok: false, error: { status: 0, message: String(e) } };
  }
}

// Caller MUST check `ok` before reading either branch's payload
const result = await getUserSafely("42");
if (result.ok) {
  console.log(result.value.name);   // User — only reachable here
} else {
  console.log(result.error.message); // ApiError — only reachable here
}

Senior Engineer Perspective

This is essentially Rust/Haskell's Result/Either pattern adapted to TypeScript, and mentioning that lineage shows breadth. The realistic trade-off to name: this pattern adds ceremony to every call site (an explicit if (result.ok) check everywhere), so many teams reserve it for genuinely expected, recoverable failures (validation errors, 404s) while letting truly exceptional, unrecoverable failures (network outage, programming bugs) still throw and be caught by an error boundary or a top-level handler.

Q72. How do you type a fetch wrapper that supports multiple HTTP methods with different body/response shapes?

ROI: ★★★☆☆ Frequency: Medium

Short Answer

Use function overloads (or a discriminated config object) so each HTTP method's call signature can require or forbid a body independently — a GET shouldn't type-check with a body field, while a POST/PUT should require one — instead of one loose signature where every field is optional for every method.

Detailed Answer

Overloads let you declare several distinct call signatures for the same function name, each with its own parameter and return types, resolved by matching the actual call against them in order. This is the right tool when the relationship between arguments is genuinely one of a small number of fixed shapes (as HTTP methods are) rather than a single continuously-varying generic relationship, which would be better expressed with conditional types instead.

Code Example

interface HttpClient {
  request<T>(method: "GET", path: string): Promise<T>;
  request<T, B>(method: "POST" | "PUT", path: string, body: B): Promise<T>;
  request(method: "DELETE", path: string): Promise<void>;
}

declare const http: HttpClient;

http.request<User>("GET", "/api/users/1");                 // OK — no body param needed
http.request<User, CreateUserInput>("POST", "/api/users", input); // OK — body required
// http.request("GET", "/api/users/1", input); // Error — GET overload takes no body

Senior Engineer Perspective

The judgment call worth naming: overloads are readable and precise for a small, fixed number of shapes (as here, one per HTTP verb), but they don't scale gracefully — five or six overloads is fine, twenty becomes a maintenance burden better served by a conditional-type-based signature. Interviewers may ask you to justify choosing overloads over a single generic conditional signature here; the answer is that the HTTP-verb axis is small and fixed, which is exactly the case overloads are designed for.

Q73. How does TanStack Query infer types end-to-end, and where can that inference silently break?

ROI: ★★★★☆ Frequency: Medium

Short Answer

useQuery's data type is inferred directly from the queryFn's return type — there's usually no need to pass an explicit generic. Inference silently breaks (falling back to unknown or a wider type than intended) when the queryFn itself isn't precisely typed — e.g. it returns any because of an unvalidated res.json(), or its return type was accidentally widened by an early return path with a different shape.

Detailed Answer

Because queryFn's return type flows straight through to data's type via ordinary generic inference (the same mechanism as ReturnType), the entire chain is only as precise as the weakest link — usually the raw fetch().json() call at the very bottom, which types as any unless explicitly annotated or run through a validator. A silent break commonly looks like: the query "works" and shows correct data at runtime, but data is typed any, so a later property-name typo goes completely uncaught by the compiler despite everything appearing fine in the editor.

Code Example

// Silent break — res.json() is `any`, so `data` ends up `any` too
function useUsersLoose() {
  return useQuery({
    queryKey: ["users"],
    queryFn: async () => {
      const res = await fetch("/api/users");
      return res.json(); // any — infects the whole query's data type
    },
  });
}

// Fixed — validated queryFn return type flows through correctly
function useUsers() {
  return useQuery({
    queryKey: ["users"],
    queryFn: async () => {
      const res = await fetch("/api/users");
      const json: unknown = await res.json();
      return z.array(UserSchema).parse(json); // return type: User[]
    },
  });
}
const { data } = useUsers(); // data: User[] | undefined — precisely typed

Senior Engineer Perspective

This is a very realistic, very common real-world gap — a team adopts TanStack Query, sees data flowing correctly at runtime, and doesn't notice for months that half their queryFns silently return any because nobody validated the JSON. Naming that this can happen invisibly (the editor shows no red squiggles because any suppresses errors rather than raising them) is the exact senior-level insight interviewers are fishing for.

Q74. How do you keep your API/DTO types in sync with a backend contract (OpenAPI/GraphQL codegen)?

Short Answer

Hand-written DTO interfaces are exactly the same drift risk as Q69's hand-written-vs-schema-derived types, just at the scale of an entire API surface instead of one endpoint. // (illustrative — actual output is auto-generated, never hand-edited)

Senior Engineer Perspective

The organisational point matters as much as the technical one: codegen only pays off if it's wired into CI so a backend contract change that the frontend hasn't adapted to actually fails the build, rather than the generated file being manually regenerated (or forgotten) on an ad-hoc basis. Q75. How do you type WebSocket or SSE message handlers safely, given messages arrive as unknown/string?

ROI: ★★★☆☆ Frequency: Medium

Short Answer

Treat every incoming message the same way you'd treat any untrusted network payload: parse the raw string as unknown first, then validate it against a discriminated-union schema keyed by a message-type field, and dispatch to the correct handler only after that validation narrows the message to a known shape.

Detailed Answer

A raw WebSocket onmessage handler receives event.data typed as string (or Blob/ArrayBuffer depending on config) — there is no compile-time guarantee about its actual structure once parsed, since it originated outside the type system entirely. Modelling the set of possible message types as a Zod discriminated union (mirroring the same pattern as API responses) lets you validate once at the socket boundary and then work with a fully-typed, exhaustively-checkable union everywhere else in the app.

Code Example

const MessageSchema = z.discriminatedUnion("type", [
  z.object({ type: z.literal("chat"), text: z.string(), userId: z.string() }),
  z.object({ type: z.literal("presence"), userId: z.string(), online: z.boolean() }),
]);
type SocketMessage = z.infer<typeof MessageSchema>;

function handleMessage(raw: string) {
  const parsed = MessageSchema.safeParse(JSON.parse(raw));
  if (!parsed.success) {
    console.warn("Dropped malformed socket message", parsed.error);
    return;
  }
  const message = parsed.data; // SocketMessage, fully narrowed per variant below
  switch (message.type) {
    case "chat": console.log(message.userId, message.text); break;
    case "presence": console.log(message.userId, message.online); break;
  }
}

socket.addEventListener("message", (event: MessageEvent<string>) => handleMessage(event.data));

Senior Engineer Perspective

WebSocket/SSE payloads are, if anything, even more deserving of runtime validation than regular REST responses, because there's typically no HTTP status code or content-type header to lean on if the server sends something malformed or a client on an old app version sends a message shape the current handler doesn't expect. Interviewers want to hear that you treat every message as adversarial input by default — safeParse and drop/log on failure, rather than trusting the payload and letting a malformed message crash a long-lived connection handler.

Q76. Which tsconfig strict-family flags exist beyond strict: true, and what does each individually catch?

noImplicitAnyRequires explicit typing instead of silently falling back to any

// noUncheckedIndexedAccess catches this real bug:

// `undefined` explicitly to an optional prop can be flagged as an error
// depending on how the prop is declared, catching accidental `{...props}` spreads

Senior Engineer Perspective

Interviewers use this to see whether you treat strict: true as "done" or as a starting point. Q77. How do you configure path aliases (e.g. @/components) so both TypeScript and your bundler agree?

ROI: ★★★★☆ Frequency: High

Short Answer

Path aliases must be declared in two places that agree with each other: tsconfig.json's compilerOptions.paths (so the type checker and editor resolve imports correctly) and your bundler's own alias config (Vite's resolve.alias, webpack's resolve.alias) so the actual build resolves the same paths at runtime. TypeScript's paths alone only affects type-checking — it does not make the alias work at runtime unless the bundler is configured identically.

Detailed Answer

This is one of the most common "works in the editor, fails at build/runtime" gotchas in React projects — TypeScript happily type-checks an @/components/Button import because tsconfig.json knows where it maps to, but if the bundler was never told the same mapping, the actual bundled output tries to resolve a literal package named @/components and fails. Some tools (Vite with certain plugins, Next.js) read tsconfig.json's paths automatically and keep the two in sync for you; plain Vite/webpack setups generally require declaring the alias twice, once for each tool.

Code Example

// tsconfig.json — makes the type checker and editor happy
{
  "compilerOptions": {
    "baseUrl": ".",
    "paths": {
      "@/*": ["src/*"]
    }
  }
}

// vite.config.ts — makes the actual build/runtime resolve the SAME alias
import path from "path";
export default {
  resolve: {
    alias: {
      "@": path.resolve(__dirname, "./src"),
    },
  },
};

Senior Engineer Perspective

The interview-worthy insight is naming precisely why the split exists: tsc only performs type-checking, it never actually resolves or emits importable module paths for a bundler to consume, so a tsconfig.json-only alias setup is a half-measure that looks correct in the editor and then breaks the build. If asked to debug "the import works in VS Code but the build fails," the alias-config mismatch is the first thing a senior engineer checks.

Q78. What does isolatedModules do and why do Vite/esbuild/SWC require it?

ROI: ★★★★☆ Frequency: High

Short Answer

isolatedModules forces every file to be safely transpilable on its own, one file at a time, with no cross-file type information — because that's exactly how single-file transpilers like esbuild/SWC (used by Vite and many modern toolchains) actually work: they strip types and compile each file in isolation, without running the full TypeScript type-checker at build time.

Detailed Answer

Full tsc can look across your entire program to figure out, for example, whether an exported name is a type or a value (needed to correctly strip type-only exports) — a single-file transpiler cannot, since it never sees the exporting file. isolatedModules catches the patterns that would break under that constraint at type-check time, before they ever reach the bundler: re-exporting a type without export type, non-modules (files without any import/export), and const enum (which requires whole-program knowledge to inline correctly). Turning it on doesn't change how your code runs — it changes what the type checker is willing to let you write, matching what the actual build pipeline can safely handle.

Code Example

// user.ts
export interface User { id: string; name: string }

// BAD under isolatedModules — re-exporting a type as a normal export
// export { User } from "./user"; // Error: re-exporting a type-only symbol

// GOOD — explicit `export type` — a single-file transpiler can safely strip this
export type { User } from "./user";

// BAD — const enum requires whole-program inlining, unsafe for single-file transpilation
// const enum Direction { Up, Down } // Error under isolatedModules

// GOOD — regular enum or an as-const union instead
enum Direction { Up, Down }

Senior Engineer Perspective

Interviewers listen for the mechanism, not just "you need to turn this flag on for Vite" — the actual reason is that fast, modern build tools sacrifice whole-program type information for speed by compiling files independently, and isolatedModules is tsc's way of pre-emptively rejecting anything that assumption would break. Volunteering the export type and const enum specifics shows you've actually hit these errors, not just read the flag's description.

Q79. What's the difference between moduleResolution: "node" / "bundler" / "node16", and which should a React app use?

ROI: ★★★☆☆ Frequency: Medium

Short Answer

"node" (aka the classic/legacy resolution) mimics older CommonJS-era Node resolution rules and predates modern ESM interop nuances. "node16"/"nodenext" follows Node's actual modern dual CJS/ESM resolution rules exactly, including requiring explicit file extensions in relative ESM imports. "bundler" (added specifically for tools like Vite/webpack) mirrors how bundlers actually resolve modules — allowing extensionless imports and package "exports" conditions — without imposing Node's stricter ESM extension requirements. For a typical bundler-based React app, "bundler" is the correct, purpose-built choice.

Detailed Answer

The practical friction people hit is using "node16"/"nodenext" in a bundler-based React app and then being forced to write import "./Button.js" (with an explicit, and to a React developer unfamiliar-looking, .js extension) for a file that's actually named Button.tsx — because that mode faithfully replicates Node's actual ESM resolution requirements. "bundler" exists precisely to remove that friction for projects that will never actually run through Node's own module loader, since the bundler resolves imports at build time using its own, more permissive rules.

Code Example

// tsconfig.json for a typical Vite/webpack React app
{
  "compilerOptions": {
    "moduleResolution": "Bundler",
    "module": "ESNext",
    "esModuleInterop": true
  }
}

// With "bundler": extensionless imports work as expected
import { Button } from "./Button"; // resolves to Button.tsx, no extension needed

// With "node16"/"nodenext" you would instead be forced to write:
// import { Button } from "./Button.js"; // matches Node's real ESM resolution rules

Senior Engineer Perspective

The signal interviewers look for is knowing why the extension requirement exists under node16/nodenext (it mirrors what Node's actual module loader requires at runtime) rather than dismissing it as an arbitrary compiler quirk — and recognising that a bundler-based app never actually goes through Node's loader, which is exactly the mismatch "bundler" resolves. For an isomorphic app or a library also meant to run directly under Node ESM without a bundler, node16/nodenext is genuinely the more correct choice.

Q80. What does skipLibCheck trade off, and when is it risky to leave on?

ROI: ★★★☆☆ Frequency: Medium

Short Answer

skipLibCheck skips full type-checking of all .d.ts declaration files, including ones inside node_modules. It trades a small amount of safety (a genuinely broken or conflicting type declaration in a dependency won't be caught) for a large, often necessary build-speed win, and — in mixed dependency trees — for simply avoiding false-positive errors caused by two packages shipping incompatible versions of the same global types (a very common real occurrence with @types/react in particular).

Detailed Answer

Without skipLibCheck, tsc fully type-checks every declaration file it encounters, including deep inside node_modules — which is both slow (there can be thousands of such files in a large dependency tree) and fragile, since a single dependency shipping slightly malformed or duplicate global types can break your entire build even though your own application code is completely correct. It's almost universally enabled in real-world React projects for exactly this reason; the risk it trades away is narrow — a genuinely broken third-party type definition silently not being flagged — which in practice surfaces anyway the moment your code actually tries to use the broken part of that library incorrectly.

Code Example

// tsconfig.json
{
  "compilerOptions": {
    "skipLibCheck": true // near-universal in real-world React projects
  }
}

// Without it, a scenario like this (two deps pulling in conflicting
// @types/react versions transitively) can break your build with errors
// deep inside node_modules that have nothing to do with your own code:
// node_modules/dep-a/node_modules/@types/react/index.d.ts:123:5 - error ...

Senior Engineer Perspective

The mature framing: skipLibCheck isn't "turning off safety for no reason," it's acknowledging that you can't reasonably be held responsible for type-checking every dependency's internals, and that doing so mainly produces noise (dependency version conflicts) rather than signal (bugs in your own code). Interviewers occasionally probe whether you know the risk exists at all — a genuinely malformed type in a library you actually rely on won't be flagged — which is worth naming even while defending the flag as the right default.

Q81. How do project references / composite projects help in a monorepo with multiple React apps/packages?

ROI: ★★★☆☆ Frequency: Medium

Short Answer

Project references let you split a monorepo into multiple tsconfig.jsons (one per package/app) that explicitly declare dependencies on each other via references, so tsc --build only re-checks and re-emits the packages that actually changed (and whatever depends on them), instead of type-checking the entire monorepo from scratch on every build.

Detailed Answer

Each referenced project must set composite: true, which enables incremental build metadata (.tsbuildinfo) and enforces a few stricter constraints (like requiring every input file to be captured by include) that make safe incremental builds possible. In a large monorepo with a shared UI library, a shared types package, and several apps consuming both, project references mean editing the UI library only triggers a rebuild of the library and the apps that depend on it — not an unrelated app in the same repo that never imports it.

Code Example

// packages/ui/tsconfig.json
{
  "compilerOptions": { "composite": true, "outDir": "./dist" }
}

// apps/web/tsconfig.json
{
  "compilerOptions": { "composite": true },
  "references": [
    { "path": "../../packages/ui" }
  ]
}

// Build only what changed, respecting the dependency graph:
// tsc --build apps/web

Senior Engineer Perspective

This question is really about whether you've operated TypeScript at monorepo scale, where a full, non-incremental type-check across dozens of packages becomes a genuine CI bottleneck. The concrete payoff worth naming is the combination of faster local builds (via .tsbuildinfo incremental state) and an explicit, enforced dependency graph between packages that catches accidental circular dependencies between packages at the project-reference level, before they even become a runtime problem.

Q82. What are the most common tsconfig misconfigurations that cause "works on my machine" type errors in CI?

ROI: ★★★★☆ Frequency: High

Short Answer

The recurring offenders: a stale or missing .tsbuildinfo/incremental cache locally masking errors that a clean CI build surfaces; different TypeScript versions between a developer's editor and CI's installed version; an editor silently using a cached/older language-service instance instead of the project's actual configured version; and include/exclude globs that accidentally miss files locally (so they're never checked) but are picked up differently by whatever command CI actually runs.

Detailed Answer

The most common single cause is version skew: VS Code ships its own bundled TypeScript version by default, separate from the one in the project's node_modules, so a developer's editor can show zero errors using an older/newer bundled compiler while CI runs the project's actual pinned version and fails. The fix is explicitly selecting the workspace TypeScript version in the editor. The second most common cause is a broad include that accidentally never captures a file (a typo in a glob, a file outside the configured rootDir), so it's silently skipped by a fast local tsc --noEmit alias but caught by whatever exact command CI invokes.

Code Example

// A tsconfig `include` misconfiguration that silently skips files:
{
  "include": ["src/**/*.ts", "src/**/*.tsx"] // misses .test.tsx or config files
                                              // outside src/ entirely, e.g. vite.config.ts
}

// CI should always run the exact same command developers are expected to run,
// pinned to the exact same TS version as package.json — no separate "CI-only" script:
// package.json: "typecheck": "tsc --noEmit"
// CI step:      npm run typecheck   (never a hand-rolled variant with different flags)

Senior Engineer Perspective

Interviewers ask this to see if you've actually been the person debugging a "but it works locally!" CI failure, not just written application code. The single most valuable habit to mention: make the exact same tsc invocation the CI gate and the pre-commit/local check, with the workspace TypeScript version pinned and explicitly selected in the editor — eliminating both sources of divergence (different commands, different compiler versions) rather than treating each incident as a one-off mystery.

Q83. How do you write a .d.ts file to type an untyped third-party JS library?

ROI: ★★★★☆ Frequency: Medium

Short Answer

Create a .d.ts file that declares the module by its import path (declare module "library-name" { ... }) and describe the shape of whatever it exports — functions, classes, default export — using ordinary interface/type/function-signature syntax but with no implementation bodies, since declaration files contain only type information, never runtime code.

Detailed Answer

Place the file anywhere TypeScript's include picks it up (commonly src/types/*.d.ts), matching the exact string used to import the library. You describe the library's actual runtime API as precisely as you can infer from its documentation or source — a named export becomes an export function/export const declaration, a default export becomes export default. This is a stopgap: the honest, better long-term fix is either checking if a community @types/library-name package already exists, or contributing types upstream, since a hand-written .d.ts can drift from the real library's behaviour with no compiler-enforced link between the two.

Code Example

// src/types/some-untyped-lib.d.ts
declare module "some-untyped-lib" {
  export interface Options {
    debug?: boolean;
    retries?: number;
  }

  export function init(options?: Options): void;
  export function fetchData<T>(url: string): Promise<T>;

  const defaultExport: {
    version: string;
  };
  export default defaultExport;
}

// usage elsewhere in the app — fully typed, no `any`
import lib, { init, fetchData } from "some-untyped-lib";
init({ debug: true });

Senior Engineer Perspective

The important caveat to state unprompted: a hand-written .d.ts is only as accurate as your understanding of the library at the moment you wrote it, and nothing keeps it in sync if the library's actual behaviour changes on an upgrade — unlike z.infer-style derived types, there's no structural guarantee here. Before writing one, checking DefinitelyTyped for an existing @types/ package is the correct first step, and interviewers want to hear that ordering rather than jumping straight to "I'd write my own."

Q84. What is module augmentation and how do you use it to extend a library's existing types?

ROI: ★★★★☆ Frequency: Medium

Short Answer

Module augmentation reopens an already-typed module's declaration and merges additional members into it, using the same declare module "module-name" { ... } syntax as writing types from scratch, but for a module that already has types — the declarations merge instead of conflicting, as long as the augmented members don't collide with existing ones. This is exactly how you extend a theme type for styled-components/emotion, or add custom fields to Express's Request.

Detailed Answer

The mechanism is the same declaration merging interfaces support generally (Q1) — declare module for an already-declared module, combined with interface merging inside it, lets you add new members to a type you don't own without forking or patching the library itself. A very common real use in React apps is augmenting styled-components's empty default DefaultTheme interface with your app's actual theme shape, which then makes every styled.div\`${props => props.theme.colors.primary}\` call fully typed and autocompleted throughout the app.

Code Example

// src/types/styled.d.ts — augmenting styled-components' theme type
import "styled-components";

interface AppTheme {
  colors: { primary: string; background: string };
  spacing: (n: number) => string;
}

declare module "styled-components" {
  // merges into styled-components' own (originally empty) DefaultTheme interface
  export interface DefaultTheme extends AppTheme {}
}

// now fully typed and autocompleted everywhere in the app:
const Card = styled.div`
  background: ${(props) => props.theme.colors.background};
  padding: ${(props) => props.theme.spacing(2)};
`;

Senior Engineer Perspective

Interviewers like this question because it's a genuinely common, practical need (typed themes, extending Express's Request with an auth middleware's attached user) rather than an academic exercise. The detail worth mentioning: the augmenting file must actually be included in the TypeScript program (via a real import or being picked up by include) for the merge to take effect — an augmentation file that's never imported or included anywhere is silently ignored, a subtle and confusing failure mode worth flagging.

Q85. How do global/ambient declarations differ from regular module type declarations, and what does export {} at the bottom of a file do?

ROI: ★★★☆☆ Frequency: Medium

Short Answer

A regular module declaration types something you explicitly import. A declare global { ... } block instead adds types that are available everywhere, with no import needed — for genuinely global values like window augmentations or a global test helper. The stray export {} some files end with exists purely to force TypeScript to treat that file as a module (rather than a global script) — a requirement for using declare global at all, since augmenting the global scope from a "script" file behaves differently than from a module.

Detailed Answer

TypeScript treats any file with at least one top-level import or export as a module (its own isolated scope); a file with neither is treated as a global script whose top-level declarations leak into the global scope directly, with no explicit declare global needed. A pure .d.ts file that only contains a declare global {} block and nothing else would otherwise have no imports/exports of its own, making it ambiguous whether it's a module or a script — adding export {} (an export of literally nothing) is the idiomatic way to force "this is a module" without actually exporting any real value.

Code Example

// global.d.ts
declare global {
  interface Window {
    dataLayer: unknown[];       // usable as window.dataLayer anywhere, no import
  }
  // eslint-disable-next-line no-var
  var __APP_ENV__: "development" | "production"; // a true global variable
}

export {}; // forces this file to be treated as a module, required for declare global to work correctly

// usage anywhere in the app, no import needed:
window.dataLayer.push({ event: "page_view" });
console.log(__APP_ENV__);

Senior Engineer Perspective

The mechanical detail interviewers want stated precisely: export {} isn't a stylistic flourish, it's the specific trick that makes a file with no real exports still count as a module, which is what makes declare global behave correctly. Being able to explain why a plain declare global {} file without any import/export sometimes behaves unexpectedly (because it was accidentally being treated as a global script, not a module) shows you've actually debugged an ambient-typing issue, not just copied a boilerplate line.

Q86. How do you type environment variables (import.meta.env / process.env) safely?

ROI: ★★★★☆ Frequency: High

Short Answer

Augment the relevant ambient interface with your app's actual environment variable names and types — ImportMetaEnv for Vite, the ProcessEnv interface on NodeJS.Global for Node/webpack-based setups — so every access is typed and autocompleted instead of being an untyped, always-string | undefined index lookup with no compile-time knowledge of which variables actually exist.

Detailed Answer

By default, process.env.SOME_VAR types as string | undefined with no way for the compiler to know whether SOME_VAR is even a variable your app defines — a typo'd env var name compiles fine and returns undefined silently at runtime. Declaring the actual shape via module augmentation closes that gap: a typo'd or nonexistent variable name becomes a compile error, and the type reflects each variable's real presence/optionality. Since environment variables always arrive as raw strings even for booleans/numbers, this typing layer should be paired with a small parsing/validation step (often the same Zod pattern as Q69) at app startup, rather than trusting the raw string blindly.

Code Example

// vite-env.d.ts (Vite convention)
/// <reference types="vite/client" />

interface ImportMetaEnv {
  readonly VITE_API_URL: string;
  readonly VITE_ENABLE_ANALYTICS: string; // env vars are always strings at the type level
}
interface ImportMeta {
  readonly env: ImportMetaEnv;
}

// usage — typo'd names are now compile errors
const apiUrl = import.meta.env.VITE_API_URL; // string, autocompleted
// import.meta.env.VITE_API_URLL; // Error — no such property

// Parse/validate at startup rather than trusting the raw string
const EnvSchema = z.object({
  VITE_API_URL: z.string().url(),
  VITE_ENABLE_ANALYTICS: z.enum(["true", "false"]).transform((v) => v === "true"),
});
const env = EnvSchema.parse(import.meta.env);

Senior Engineer Perspective

The subtlety worth naming: augmenting ImportMetaEnv/ProcessEnv gets you compile-time protection against typo'd variable names, but every environment variable is still a raw string at runtime regardless of what the type declares — a boolean-looking env var config still needs an actual runtime "true"/"false" string comparison or transform. Interviewers who ask this are checking that you don't conflate "the type says boolean" with "the runtime value behaves like a boolean" — env vars are the sharpest example of that gap in the whole chapter.

Q87. How do you gradually migrate a large JS codebase to TS using allowJs and checkJs?

ROI: ★★★☆☆ Frequency: Medium

Short Answer

allowJs lets .js/.jsx files sit alongside .ts/.tsx files in the same TypeScript program, so you can rename and convert files incrementally rather than all at once. checkJs additionally turns on type-checking for those remaining .js files, using JSDoc comments as the source of type annotations, so you get real errors surfaced in untouched legacy files even before you've converted a single one to .ts.

Detailed Answer

A realistic migration path: enable allowJs first so new .ts files can freely import old .js ones (and vice versa) without the build breaking; optionally enable checkJs globally or per-file (via a // @ts-check comment at the top of just the files you're ready to fix) to start surfacing real bugs in legacy code using JSDoc-derived types, without committing to a full rewrite; then convert files to .ts/.tsx file by file, starting with leaf modules that have the fewest dependents, so each conversion's blast radius stays small and reviewable.

Code Example

// tsconfig.json — enables incremental JS+TS coexistence
{
  "compilerOptions": {
    "allowJs": true,
    "checkJs": false // start false; opt files in individually with // @ts-check first
  }
}

// legacy-utils.js — opted in individually before a full .ts conversion
// @ts-check

/**
 * @param {string} name
 * @param {number} age
 * @returns {{ name: string, age: number }}
 */
function createUser(name, age) {
  return { name, age };
}
// createUser(42, "Ada"); // @ts-check now flags this from JSDoc types alone

Senior Engineer Perspective

Interviewers evaluating migration strategy want to hear a staged, low-risk plan rather than "rewrite everything in TypeScript" as a single undifferentiated effort — the per-file // @ts-check + JSDoc step in particular is underused and lets a team surface real bugs in legacy code weeks or months before committing engineering time to full conversion. Naming "convert leaf modules first, working inward toward files with many dependents" shows you understand how to bound the blast radius of each incremental step.

Q88. How do you type a CSS-in-JS theme object so a library's theme prop is autocompleted?

ROI: ★★★☆☆ Frequency: Medium

Short Answer

This is a direct application of module augmentation (Q84): define your app's theme shape as a regular interface, then augment the CSS-in-JS library's own theme type (DefaultTheme for styled-components, the equivalent for emotion) to extend it, so every component using props.theme gets full autocompletion and type-checking without any extra generic parameters at each call site.

Detailed Answer

Both styled-components and emotion ship an intentionally empty default theme interface specifically so applications can augment it once, globally, rather than needing to pass a generic type argument to every single styled.div<Theme> call. Doing this once at app setup means the theme type flows correctly into every styled component, every useTheme() call, and every themed component created anywhere in the codebase, with zero additional per-component typing effort.

Code Example

// theme.ts — the actual theme object AND its type, single source of truth
export const theme = {
  colors: { primary: "#1f4e79", danger: "#c0392b" },
  spacing: (n: number) => `${n * 8}px`,
} as const;

type AppTheme = typeof theme;

// styled.d.ts — module augmentation, done once for the whole app
import "styled-components";
declare module "styled-components" {
  export interface DefaultTheme extends AppTheme {}
}

// every styled component and useTheme() call is now typed, no per-call generics
import { useTheme } from "styled-components";
function Badge() {
  const t = useTheme();
  return <span style={{ color: t.colors.primary }}>Active</span>; // autocompleted
}

Senior Engineer Perspective

The elegant detail worth pointing out: deriving AppTheme as typeof theme from the actual runtime theme object (rather than hand-writing a separate interface) means the theme's type and its real values can never drift apart — the same "derive, don't duplicate" instinct from utility types, applied to a config object instead of an API schema. Interviewers appreciate seeing that connection made explicitly across topics rather than treated as an unrelated trick.

Q89. What's the risk of writing an incorrect .d.ts for an untyped library, and how do you validate it?

ROI: ★★★☆☆ Frequency: Medium

Short Answer

A hand-written declaration file has zero enforced connection to the library's actual runtime behaviour — TypeScript will trust it completely, even if it's wrong, because there's no way for the compiler to check a .d.ts against the JavaScript it describes. An incorrect declaration produces confident, fully-typed code that still crashes at runtime exactly the way an unchecked type assertion would, just spread across every call site that trusted the wrong types.

Detailed Answer

The best available validation is indirect: write integration/runtime tests that actually exercise the library through your declared types, so a wrong declaration at least gets caught by a failing test rather than silently shipping. Cross-checking against the library's actual source code or official documentation (not just its README examples, which can be outdated) is essential before trusting a hand-written declaration for anything beyond the most trivial API surface. If the library later ships its own official types or gets community @types/ coverage, replacing your hand-written file with the maintained one closes this risk permanently rather than continuing to trust an unmaintained guess.

Code Example

// A wrong hand-written declaration — confidently, silently incorrect
declare module "legacy-lib" {
  export function fetchConfig(): { url: string }; // WRONG — actually returns a Promise
}

import { fetchConfig } from "legacy-lib";
const config = fetchConfig();
config.url; // "works" per the types... but config is actually a Promise<{url:string}>
            // at runtime — this compiles, and crashes: "Cannot read property 'url' of undefined"

// A runtime test is what actually catches this, not the type checker:
test("fetchConfig resolves to the expected shape", async () => {
  const result = await fetchConfig(); // if fetchConfig is sync per (wrong) types, this test itself reveals the mismatch
  expect(result).toHaveProperty("url");
});

Senior Engineer Perspective

This question is testing whether you understand a fundamental limit of the whole declaration-file system: types are trusted, never verified, against the JavaScript they describe. The mature answer treats a hand-written .d.ts the same way you'd treat any other unverified assumption in the codebase — worth a comment explaining its provenance, worth a test that actually exercises it, and worth replacing the moment a real, maintained alternative exists.

SECTION 14 - COMMON TYPESCRIPT PITFALLS IN REACT CODEBASES

Q90. What is "any creep" and how does it silently spread through a codebase?

ROI: ★★★★★ Frequency: High

Short Answer

"Any creep" is the way a single untyped or loosely-typed value — an unvalidated res.json(), a third-party callback with no types, one as any escape hatch — infects everything downstream that touches it, because any is contagious: any value derived from an any is itself any, silently, with no warning at any of the intermediate steps.

Detailed Answer

Unlike unknown, which blocks further use until narrowed, any disables checking for everything it touches from that point forward — property access, function calls, arithmetic, assignment to a more specific type, all pass silently. In practice this means one careless any at a data-fetching boundary can flow through several component layers, several prop-drilling hops, and a couple of utility functions, with the type checker offering zero protection the entire way, before finally surfacing as a runtime crash far from the actual source. This is exactly what Q73 describes happening with an unvalidated queryFn.

Code Example

async function fetchUser(id: string) {
  const res = await fetch(`/api/users/${id}`);
  return res.json(); // implicitly `any` — the source of the creep
}

// `any` silently flows through every layer below with zero errors anywhere:
function UserCard({ user }: { user: any }) {           // any creeps into props
  return <div>{user.nmae}</div>;                       // typo "nmae" — NOT caught
}

// The fix — validate at the boundary, stop the creep at its source:
async function fetchUserSafe(id: string): Promise<User> {
  const res = await fetch(`/api/users/${id}`);
  return UserSchema.parse(await res.json()); // User, not any — creep stopped here
}

Senior Engineer Perspective

Interviewers want a concrete story of where any creep bit a real project, not just the definition. The strongest answer names the compiler flag that catches the most common source unprompted — noImplicitAny — and adds that even with it on, explicit any (via : any annotations or as any casts) still slips through, which is why many teams additionally lint against explicit any with @typescript-eslint/no-explicit-any rather than relying on the compiler flag alone.

Q91. What are the most common incorrect prop-typing mistakes (optional vs required, function prop signatures)?

ROI: ★★★★☆ Frequency: High

Short Answer

The recurring ones: marking a prop optional (?) when the component actually behaves incorrectly without it, instead of giving it a real default; typing a callback prop's parameters too loosely (onChange: Function or (...args: any[]) => void) instead of the exact signature the component calls it with; and typing a prop as broader than what's actually used internally (value: any instead of the real union), which silently defeats every other type check inside the component.

Detailed Answer

A prop marked optional without a sensible internal default just moves a potential undefined crash from the type checker (which would have caught a missing required prop at the JSX call site) to a runtime code path deep inside the component. The generic Function type in particular is almost always wrong — it accepts any callable with any signature and any return type, providing essentially no safety at all; the fix is always the concrete function type the component actually invokes it as. Typing a prop wider than necessary "just to make an error go away" is functionally equivalent to sprinkling any into the props interface — it compiles, but every internal usage of that prop loses checking.

Code Example

// BAD — optional with no real default, Function is a near-total type escape
interface BadProps {
  label?: string;             // component crashes without it — should be required or defaulted
  onChange?: Function;        // accepts (a, b, c) => "anything" — no safety at all
}

// GOOD — required where truly required, defaulted where genuinely optional,
// exact function signature for the callback
interface GoodProps {
  label: string;                          // truly required — no default makes sense
  onChange: (value: string) => void;      // exact signature, not Function
}
function Field({ label, onChange }: GoodProps) { /* ... */ return null; }

// A genuinely optional prop SHOULD get a real default, not just `?`:
interface ButtonProps {
  variant?: "primary" | "secondary"; // optional AND has a sensible fallback below
}
function Button({ variant = "primary" }: ButtonProps) { /* ... */ return null; }

Senior Engineer Perspective

The judgment call interviewers are probing: "optional" should mean "the component has sensible behaviour without it," not "I don't want to fix every call site right now." A prop marked optional purely to silence errors at existing call sites is technical debt disguised as a type annotation — the honest fix is either giving it a real default or accepting the required-prop errors as a to-do list of call sites that genuinely need updating.

Q92. When is a type assertion (as) legitimate vs a code smell, and what's the safer alternative in each case?

ROI: ★★★★★ Frequency: High

Short Answer

A type assertion is legitimate when you genuinely know more than the compiler can prove from local information — narrowing a document.getElementById result you know exists, or the one accepted assertion boundary in a compound-component context (Q23). It's a smell when it's used to silence a type error about data whose actual shape you haven't verified — most commonly, asserting the shape of network data instead of validating it.

Detailed Answer

The test to apply: does this assertion encode a fact you've actually verified through code (a runtime check, a schema, an invariant enforced elsewhere), or is it purely wishful thinking about data whose real shape you don't control? Casting a DOM query result you know will exist in a specific, controlled markup context is defensible, if narrow. Casting an API response to skip validation is not — it's precisely the same "no runtime backing" problem as an unverified .d.ts (Q89), just localised to one call site instead of an entire library.

Code Example

// Smell — asserting unverified network data, no runtime backing at all
const user = (await res.json()) as User; // pure wishful thinking if the shape is wrong

// Safer alternative — validate, don't assert
const user2 = UserSchema.parse(await res.json()); // User, backed by a real runtime check

// Defensible — narrow scope, verified by the surrounding code's own invariant
const modal = document.getElementById("app-modal-root") as HTMLDivElement;
// (legitimate IF this element is guaranteed to exist by the app's own static HTML shell)

// Smell — silencing a real structural mismatch instead of fixing it
function render(props: { count: number }) {
  const bad = { name: "x" } as unknown as { count: number }; // hides a genuine bug
}

Senior Engineer Perspective

Interviewers use this question as a values check as much as a technical one — the strongest answers treat every as in a codebase as something that should be justifiable in a code review comment, not just something that compiles. A good closing point: a double assertion (as unknown as X) is an even stronger smell than a single one, since it exists specifically to bypass TypeScript's normal "these types aren't related enough to assert directly" safety check — seeing one in a PR is worth an immediate, specific question about what invariant justifies it.

Q93. How should you type children correctly for components that only accept specific child types (e.g. only <Tab> children)?

ROI: ★★★☆☆ Frequency: Medium

Short Answer

ReactNode is intentionally permissive and cannot restrict children to a specific component type — TypeScript's type system checks shapes, not "was this JSX element created by rendering exactly this function," so there's no fully sound compile-time way to say "only <Tab> elements are allowed here." The closest practical approaches are typing children as ReactElement<TabProps> | ReactElement<TabProps>[] (a soft signal, not a hard guarantee) or, more robustly, validating and warning at runtime via Children.forEach/Children.map combined with checking each child's type against the expected component reference.

Detailed Answer

The fundamental limitation: JSX elements are just objects with a type and props field at runtime, and TypeScript's structural typing has no special knowledge that <Tab /> and <OtherComponentWithSameProps /> are "different" if their prop shapes happen to match — a ReactElement<TabProps> annotation only checks the props shape, not which component function actually produced the element. Teams that need a hard guarantee typically enforce it at runtime (dev-mode warnings via Children.forEach checking child.type === Tab) rather than pretending the type system alone can fully close this gap.

Code Example

interface TabProps { label: string; children: React.ReactNode }
function Tab({ children }: TabProps) { return <div role="tabpanel">{children}</div>; }

interface TabsProps {
  // soft signal — checks props shape, NOT "was this actually created via <Tab>"
  children: React.ReactElement<TabProps> | React.ReactElement<TabProps>[];
}

function Tabs({ children }: TabsProps) {
  // runtime check — the actual enforcement, since types alone can't guarantee this
  React.Children.forEach(children, (child) => {
    if (React.isValidElement(child) && child.type !== Tab) {
      console.warn("Tabs only accepts <Tab> children, received:", child.type);
    }
  });
  return <div role="tablist">{children}</div>;
}

Senior Engineer Perspective

The mature answer states the limitation plainly rather than presenting a false sense of type safety: TypeScript can narrow props shape, not component identity, so "only <Tab> children" is fundamentally a runtime contract with an approximate compile-time hint layered on top, not a fully sound static guarantee. Interviewers who ask this are checking whether you'll honestly name a real gap in the type system rather than over-claiming what a clever-looking type annotation actually proves.

Q94. What's wrong with typing all IDs as string or number, and how do branded types fix it?

ROI: ★★★★☆ Frequency: Medium

Short Answer

Typing every ID as a plain string/number means the compiler treats a UserId, an OrderId, and a ProductId as fully interchangeable — nothing stops passing an order's id into a function that expects a user's id, since they're structurally identical. Branded types (Q42) close exactly this gap by giving each ID kind a distinct, non-interchangeable type while still compiling down to a plain string/number at runtime.

Detailed Answer

This is a very real, very common bug class in codebases with many entity types that all happen to use string or numeric IDs — a function signature like function transferOrder(userId: string, orderId: string) gives the compiler no way to catch the arguments being passed in the wrong order, because both are just string. Branding each ID type (UserId, OrderId) turns that exact mistake into a compile error at the call site, at the modest cost of needing an explicit conversion function at the one place each ID kind is legitimately created (usually right where it's parsed from an API response or a schema).

Code Example

// Without branding — this compiles and is a real, silent bug:
function transferOrder(userId: string, orderId: string) { /* ... */ }
transferOrder(order.id, user.id); // arguments swapped — compiles fine, wrong at runtime!

// With branding — the same mistake is now a compile error:
type UserId = string & { readonly __brand: "UserId" };
type OrderId = string & { readonly __brand: "OrderId" };

function transferOrderSafe(userId: UserId, orderId: OrderId) { /* ... */ }
// transferOrderSafe(order.id, user.id); // Error — types don't match their parameter positions

Senior Engineer Perspective

This question rewards connecting a very ordinary-looking typing choice (just string for every ID) to a concrete, realistic production bug (swapped-argument calls that compile without error). The honest caveat worth adding, echoing Q42: branding is a deliberate, disciplined workaround for TypeScript's structural typing, not a first-class nominal type system — it protects against accidental mixing at typed call sites, but nothing stops a careless as UserId cast from reintroducing the exact bug it was meant to prevent.

Q95. How do you catch typing regressions in CI (tsc --noEmit, type-check scripts, lint rules) as part of a PR pipeline?

ROI: ★★★★☆ Frequency: High

Short Answer

Run tsc --noEmit (or the equivalent build-tool type-check command) as its own required CI step, separate from and in addition to the bundler's own transpilation — because tools like Vite/esbuild/SWC intentionally skip type-checking for speed (Q78), so a broken build passing CI silently proves nothing about type correctness unless a real type-check step runs somewhere in the pipeline.

Detailed Answer

This is the direct, practical consequence of isolatedModules-style single-file transpilation (Q78): the fast build that ships to production never actually runs the full type checker, so relying on "the build succeeded" as a proxy for "the types are correct" is a false signal. A robust pipeline runs tsc --noEmit (or tsc --build for a project-references monorepo, Q81) as an explicit, required CI check, alongside ESLint rules that catch type-adjacent smells the compiler itself won't flag — no-explicit-any, no-non-null-assertion, no-unnecessary-type-assertion — and ideally type-level tests (Q67) for the most widely-shared types.

Code Example

// package.json
{
  "scripts": {
    "typecheck": "tsc --noEmit",
    "build": "vite build" // fast, but does NOT type-check — Q78
  }
}

# .github/workflows/ci.yml (illustrative)
jobs:
  verify:
    steps:
      - run: npm ci
      - run: npm run typecheck   # the ONLY step that actually catches type regressions
      - run: npm run lint        # no-explicit-any, no-non-null-assertion, etc.
      - run: npm run build       # fast, but type errors here are NOT guaranteed to surface

Senior Engineer Perspective

The specific insight interviewers want: a green build from Vite/esbuild is not proof the types are correct, because those tools strip types without checking them — treating npm run build succeeding as equivalent to "types are fine" is a false sense of safety that this whole chapter's isolatedModules discussion (Q78) directly explains. A mature CI setup makes tsc --noEmit its own required, clearly-labelled gate specifically so a type regression fails visibly and immediately, rather than shipping silently because the bundler never checked in the first place.

Q96. What's a realistic checklist for reviewing a PR's TypeScript quality beyond "does it compile"?

ROI: ★★★★★ Frequency: High

Short Answer

Compiling is the floor, not the bar. A real review checks for: unjustified any/type assertions, discriminated unions with exhaustiveness checks where the domain has mutually exclusive states, derived types over hand-duplicated ones, runtime validation at every external data boundary, and precise (not Function/object/loose) signatures for any newly-added public function, hook, or component prop.

Detailed Answer

Every question in this chapter maps to a concrete review checklist item: does new fetch/loading state use a discriminated union instead of independent booleans (Q5, Q22)? Is new reducer/action code exhaustively checked with a never default (Q37, Q60)? Is any new API-facing type derived from a schema rather than hand-written twice (Q69)? Is every new as assertion justifiable in a review comment, not just silencing an error (Q92)? Does any new ID-like field risk being swapped with another ID type (Q94)? A PR that compiles cleanly can still fail every one of these — "compiles" only means the code is internally consistent with whatever (possibly too-loose) types it declares, not that those types are actually meaningful.

Code Example

// A PR-review checklist worth keeping literally as a template comment:
//
// [ ] No unexplained `any` or `as` — each one has a one-line justification
// [ ] New fetch/loading/auth state uses a discriminated union, not flags
// [ ] New reducer actions are a discriminated union with a `never` exhaustiveness check
// [ ] New API-facing types are derived from a schema (z.infer), not hand-duplicated
// [ ] New callback props have an exact function signature, not `Function`/`any`
// [ ] New IDs use the existing branded ID types, not raw string/number
// [ ] tsc --noEmit passes as its own CI step, independent of the bundler build

Senior Engineer Perspective

This closing question is deliberately synthetic — it's where an interviewer checks whether you've internalised the chapter's throughline (make illegal states unrepresentable, derive don't duplicate, validate don't assert) as a reviewing habit, not just a set of isolated facts you can recite on demand. The strongest candidates answer this one not by listing new information, but by showing they can instantly map a code smell in a diff back to the specific principle it violates — that mapping is the senior skill this entire chapter has been building toward.
