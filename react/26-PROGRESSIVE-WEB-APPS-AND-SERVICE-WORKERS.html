SECTION 1 - PWA FUNDAMENTALS & THE WEB APP MANIFEST

Q1. What actually makes a web app "progressive"?

ROI: ★★★★☆ Frequency: High

Short Answer

"Progressive" does not describe one feature, it describes a philosophy: the app works for every visitor at a baseline level, and progressively enhances itself as the browser and network conditions allow. A PWA is not a different kind of app you build from scratch, it is a normal web app that has earned four properties - installable, reliable, fast, and engaging - by adopting a small set of web platform APIs on top of what you already ship.

Installable. With a valid manifest and a registered service worker, a compliant browser offers to add the app to the home screen or app drawer, so it launches like a native app, in its own window, with its own icon, no browser chrome.

Reliable. A service worker sits between the page and the network and can serve a working experience even when the network is flaky or absent, instead of the browser's default "no internet" dinosaur.

Fast. Precached app-shell assets and cached API responses mean repeat visits render instantly from cache rather than waiting on a cold network round trip, which also happens to be excellent for Core Web Vitals.

Engaging. Push notifications and background sync let the app bring users back and finish work they started offline, closing some of the gap with native app re-engagement mechanics.

Pillar Enabling mechanism User-visible benefit
Installable manifest.json + registered service worker + HTTPS home-screen icon, standalone window, no address bar
Reliable service worker fetch interception + cache works with flaky or no network
Fast precaching + cached responses instant repeat loads
Engaging Push API, Notifications API, Background Sync re-engagement, offline task completion

Interview Gold Point

The framing that separates a strong answer is "installability is a reward for reliability, not a feature you bolt on." Chrome's install prompt only fires once the browser can verify the service worker actually produces a usable offline response - so a candidate who leads with "you add a manifest and get an install button" is missing the point. Lead with reliability and offline-first thinking, then mention that installability, speed, and engagement fall out of it.

Q2. What goes in the Web App Manifest, and how does the add-to-home-screen flow actually work?

ROI: ★★★★☆ Frequency: High

Short Answer

The manifest is a JSON file, linked from the page with <link rel="manifest" href="/manifest.json">, that tells the browser how to present the app if it's installed: its name, icons, start URL, display mode, and theme colors. On its own the manifest does nothing visible - it becomes actionable once the browser also sees a registered service worker with a fetch handler, and the whole thing is served over HTTPS. Meeting those criteria is what makes Chrome fire a beforeinstallprompt event, which you can capture to show your own "Install app" button instead of relying on the browser's default UI.

Key manifest fields worth knowing cold: name/short_name (full vs home-screen label), start_url (what opens when launched from the home screen, often with a query param to distinguish installed launches in analytics), display (standalone hides browser chrome, fullscreen hides everything, browser is just a tab), scope (which URLs are considered "inside" the app), theme_color/background_color (status bar and splash-screen color), and icons (must include at least a 192x192 and 512x512 PNG; a purpose: "maskable" icon avoids ugly cropping on Android's adaptive icon shapes).

The beforeinstallprompt event is Chromium-specific (Safari and Firefox have no equivalent event, and iOS Safari has its own manual "Add to Home Screen" share-sheet flow with much weaker manifest support). Capturing the event and calling preventDefault() suppresses the automatic mini-infobar so you can trigger the real native prompt later, from your own UI, at a moment the user is more likely to say yes - a well-known best practice is not showing it on the very first page load. 

// manifest.json
{
  "name": "Acme Shop",
  "short_name": "Acme",
  "start_url": "/?source=pwa",
  "scope": "/",
  "display": "standalone",
  "background_color": "#ffffff",
  "theme_color": "#1f4e79",
  "orientation": "portrait",
  "icons": [
    { "src": "/icons/icon-192.png", "sizes": "192x192", "type": "image/png" },
    { "src": "/icons/icon-512.png", "sizes": "512x512", "type": "image/png", "purpose": "any maskable" }
  ]
}

// app.js - capture the install prompt and trigger it from your own UI
let deferredPrompt;

window.addEventListener("beforeinstallprompt", (e) => {
  e.preventDefault();          // suppress the default mini-infobar
  deferredPrompt = e;
  installButton.hidden = false; // show a custom "Install app" button
});

installButton.addEventListener("click", async () => {
  if (!deferredPrompt) return;
  deferredPrompt.prompt();
  const { outcome } = await deferredPrompt.userChoice; // "accepted" | "dismissed"
  deferredPrompt = null;
  installButton.hidden = true;
});

window.addEventListener("appinstalled", () => {
  analytics.track("pwa_installed");
});

Common Mistake

Assuming the manifest alone makes an app installable. Chrome's actual install heuristic requires the manifest, a registered service worker whose fetch handler produces a real 200 response for the start URL, HTTPS, and (historically) a minimum engagement threshold from the user. A candidate who ships a manifest, sees no install prompt, and can't explain why is exposing a gap - the fix is almost always "the service worker isn't registered yet, or its fetch handler doesn't actually respond."

SECTION 2 - SERVICE WORKER LIFECYCLE & CACHING STRATEGIES

Q3. Walk through the service worker lifecycle - install, activate, and fetch.

ROI: ★★★★★ Frequency: Very High

Short Answer

A service worker is a JavaScript file that runs on its own thread, separate from the page, with no DOM access and no shared global state guaranteed to survive - the browser can spin it down and wake it up per event at will, so every handler has to be self-contained and idempotent. It goes through three main events. install fires once, when the browser first sees a new or byte-different sw.js; this is where you open a cache and pre-populate it with the app shell. activate fires once the new worker takes control; this is where you clean up caches left by a previous version. fetch fires on every network request the page makes while the worker is in control, and is where you intercept the request and decide whether to answer from cache, from the network, or a mix of both.

The subtlety interviewers probe is the gap between installed and activated. A new service worker installs in the background even while an old one is still controlling open tabs, and by default it sits in a waiting state until every tab controlled by the old worker is closed - this exists specifically so that a page never has two different versions of your app logic and cache running simultaneously mid-session. self.skipWaiting() inside install bypasses that wait, and self.clients.claim() inside activate makes the new worker take control of already-open tabs immediately rather than waiting for the next navigation - both are opt-in precisely because skipping the safety wait has consequences (see Q8).

Every handler that does async work must be wrapped in event.waitUntil() (for install/activate) or event.respondWith() (for fetch) - these tell the browser "don't tear this worker down, and don't let the default network behavior happen, until this promise settles." Forgetting this is a classic bug: the cache population races with the browser considering install "done." 

const CACHE_NAME = "app-shell-v1";
const APP_SHELL = ["/", "/index.html", "/app.css", "/app.js"];

self.addEventListener("install", (event) => {
  event.waitUntil(
    caches.open(CACHE_NAME).then((cache) => cache.addAll(APP_SHELL))
  );
  // self.skipWaiting();  // opt-in only - see Q8 for why this needs care
});

self.addEventListener("activate", (event) => {
  event.waitUntil(
    caches.keys().then((keys) =>
      Promise.all(
        keys.filter((key) => key !== CACHE_NAME).map((key) => caches.delete(key))
      )
    )
  );
  // self.clients.claim();  // opt-in only - see Q8
});

self.addEventListener("fetch", (event) => {
  event.respondWith(
    caches.match(event.request).then((cached) => cached || fetch(event.request))
  );
});

Interview Gold Point

State the "why" behind the waiting phase explicitly: it exists so a user with an open tab never gets a mismatched combination of old page JS talking to a new cache, or vice versa, mid-session. Naming skipWaiting/clients.claim as deliberate escape hatches - not defaults - and connecting them to real consequences (Q8) is what separates "I copied this from MDN" from "I've operated this in production."

Q4. What are the main caching strategies a service worker can implement, and when do you pick each?

ROI: ★★★★★ Frequency: Very High

Short Answer

A caching strategy is just the policy your fetch handler applies to decide cache-vs-network for a given request, and the right choice depends entirely on how often that resource changes and how much staleness is acceptable. There is no single correct strategy for a whole app - production service workers almost always run different strategies for different request types, routed by URL pattern or request destination.

Cache-first - check the cache, serve it if present, only hit the network on a miss (and then populate the cache). Best for content-hashed, versioned static assets that never change once fetched - if the bytes at a URL never change, there's no reason to ever re-fetch them.

Network-first - try the network, and only fall back to the cache if the network fails or times out. Best for data where freshness matters more than instant response, but where offline access is still a nice-to-have - an HTML document, a news feed, a price.

Stale-while-revalidate - respond from the cache immediately (fast, feels instant) while simultaneously fetching from the network in the background and updating the cache for the next request. This is the pragmatic middle ground: the user never waits on the network, but the cache slowly heals itself, so it fits content that should feel instant without staying wrong forever.

Strategy Behavior Best for
Cache-first serve from cache; network only on miss hashed/versioned JS, CSS, fonts, icons
Network-first try network; fall back to cache on failure HTML shell, feeds, prices - freshness matters
Stale-while-revalidate serve cache instantly; refresh cache in background avatars, list pages - instant but self-healing
Network-only always network, never cached POST/mutating requests, analytics beacons
Cache-only always cache, never network assets guaranteed precached at install, immutable 
// Hand-rolled stale-while-revalidate for /api/* GET requests
self.addEventListener("fetch", (event) => {
  const { request } = event;
  if (request.method === "GET" && request.url.includes("/api/")) {
    event.respondWith(
      caches.open("api-cache").then(async (cache) => {
        const cached = await cache.match(request);
        const networkFetch = fetch(request).then((response) => {
          cache.put(request, response.clone());
          return response;
        });
        // Serve stale immediately if we have it; otherwise wait on the network.
        return cached || networkFetch;
      })
    );
  }
});

Interview Favorite

The one-line comparison to lead with: "cache-first for things that never change, network-first for things that should stay fresh but can survive being briefly stale, stale-while-revalidate when you want the speed of cache-first without the staleness of never re-checking." Then immediately volunteer that a real app runs several of these side by side, routed by request type - a single global strategy is a beginner tell.

Q5. What is Workbox, and how does it handle precaching build assets?

ROI: ★★★★☆ Frequency: High

Short Answer

Workbox is Google's library for writing service workers without hand-rolling cache-name bookkeeping, strategy logic, and expiration policy every time. It ships pre-built strategy classes (CacheFirst, NetworkFirst, StaleWhileRevalidate) that implement exactly the policies from Q4 correctly - including edge cases like opaque cross-origin responses and cache timeouts - so you route requests to a strategy instead of writing the caching logic by hand.

Its other major job is precaching with revisioning. A build plugin (workbox-webpack-plugin, or the equivalent in Vite via vite-plugin-pwa) scans your build output and injects a manifest array of every asset with either a content hash already in its filename or an explicit revision hash Workbox computes, then precacheAndRoute(self.__WB_MANIFEST) caches all of them at install time and - critically - only re-fetches the specific files whose hash actually changed on the next deploy, leaving unchanged assets untouched in the cache. This is the production-grade version of the cache-versioning problem discussed in Q8 and Q14: instead of you remembering to bump a cache name, the build tool guarantees a changed file always gets a new URL.

Runtime (non-precached) requests - API calls, images, fonts loaded on demand - are handled with registerRoute, matching a URL pattern or request type to one of the strategy classes, optionally combined with plugins like ExpirationPlugin (cap entries or age) or BackgroundSyncPlugin (Q7). 

// sw.js built with Workbox (e.g. via vite-plugin-pwa or workbox-webpack-plugin)
import { precacheAndRoute } from "workbox-precaching";
import { registerRoute } from "workbox-routing";
import { CacheFirst, NetworkFirst } from "workbox-strategies";
import { ExpirationPlugin } from "workbox-expiration";

// Injected at build time, one entry per hashed asset:
// [{ url: "/assets/app.8f3ac1.js", revision: null }, { url: "/assets/logo.png", revision: "a1b2c3" }, ...]
precacheAndRoute(self.__WB_MANIFEST);

registerRoute(
  ({ request }) => request.destination === "image",
  new CacheFirst({
    cacheName: "images",
    plugins: [new ExpirationPlugin({ maxEntries: 60, maxAgeSeconds: 30 * 24 * 60 * 60 })],
  })
);

registerRoute(
  ({ url }) => url.pathname.startsWith("/api/"),
  new NetworkFirst({ cacheName: "api-cache", networkTimeoutSeconds: 3 })
);

Interview Gold Point

The strongest signal here is connecting Workbox's revisioned precache manifest directly to the "stale bundle after deploy" failure mode - explain that hand-rolled service workers get this wrong constantly (fixed cache key, never re-fetches), while Workbox's build-time hashing means a code change is structurally guaranteed to produce a new cache entry. Mentioning that you'd reach for Workbox specifically to avoid re-implementing expiration and cross-origin edge cases correctly shows production judgment, not just API recall.

SECTION 3 - OFFLINE SUPPORT, BACKGROUND SYNC & UPDATES

Q6. How do you build offline support and a fallback page for navigation failures?

ROI: ★★★★☆ Frequency: High

Short Answer

Offline support is really two separate things: caching enough of the app shell and data that most navigations succeed from cache, and providing a deliberate, designed fallback for the requests that still fail - rather than letting the browser show its default disconnected-network error page. The standard pattern is the "app shell" model: precache the HTML skeleton, CSS, and JS so the UI frame always renders, then let individual API calls fail gracefully within that frame with cached or placeholder data.

For the case where even the shell request fails outright (a first-ever visit with no connectivity, or a deep link the shell never cached), you precache a small, self-contained offline.html at install time and register a "catch" handler that serves it whenever a navigation request throws. The fallback page should be genuinely offline-capable itself - no external fonts, no analytics scripts that will also fail and throw console noise, ideally under a few KB.

Detecting connectivity client-side (navigator.onLine, the online/offline window events) is a useful UX signal for showing a banner, but it is not reliable for deciding whether a fetch will actually succeed - a device can report "online" while connected to a captive portal or a network with no real route out, so the source of truth is always the fetch itself succeeding or failing, not the connectivity flag. 

import { precacheAndRoute } from "workbox-precaching";
import { registerRoute, setCatchHandler } from "workbox-routing";
import { NetworkFirst } from "workbox-strategies";

// Precache the fallback page itself so it's available with zero network.
precacheAndRoute([{ url: "/offline.html", revision: "1" }]);

registerRoute(({ request }) => request.mode === "navigate", new NetworkFirst());

// Runs when every registered route's strategy still throws (e.g. no cache, no network).
setCatchHandler(async ({ event }) => {
  if (event.request.destination === "document") {
    return caches.match("/offline.html");
  }
  return Response.error();
});

Common Mistake

Treating navigator.onLine as authoritative. It only reflects whether the OS reports a network interface as connected, not whether requests actually reach your servers - candidates who describe gating all fetch logic behind an onLine check are describing a UX enhancement, not a real offline strategy. The real strategy has to live in the service worker's fetch handling and catch logic, which experiences the actual failure directly.

Q7. How do Background Sync and Push Notifications work in a service worker?

ROI: ★★★☆☆ Frequency: Medium

Short Answer

Background Sync lets you defer a failed action (typically a POST that failed because the user was offline) and have the browser automatically retry it once connectivity returns, even if the user has closed the tab. The page calls registration.sync.register("tag-name") when a request fails; the browser fires a sync event on the service worker as soon as it detects connectivity, and you retry the queued request(s) there. Support is inconsistent - it's a Chromium feature with no Safari/Firefox support, which is why Workbox's BackgroundSyncPlugin (a durable IndexedDB-backed queue with automatic retry) is the practical way to use it, since it degrades safely on unsupported browsers rather than throwing.

Push Notifications are a separate, two-part system. First, the client subscribes via PushManager.subscribe() with a VAPID public key, which returns a subscription object (endpoint URL + keys) that you send to your backend and store per user. Later, your server sends a message to that endpoint (using a library like web-push, signed with your VAPID private key) via the browser vendor's push service - this works even if the site isn't open, because the browser itself, not your page, receives the push. The service worker's push event handler then calls self.registration.showNotification(...) to actually display it, and a notificationclick handler decides what happens when the user taps it (usually opening or focusing a specific URL).

Both features require the app to already be a registered, controlling service worker, and push additionally requires explicit user permission via the Notifications API - a permission prompt users are increasingly conditioned to reject if it's requested immediately on page load rather than after a meaningful interaction. 

// Queue a failed POST and retry automatically once back online (Workbox)
import { BackgroundSyncPlugin } from "workbox-background-sync";
import { registerRoute } from "workbox-routing";
import { NetworkOnly } from "workbox-strategies";

const ordersQueue = new BackgroundSyncPlugin("orders-queue", {
  maxRetentionTime: 24 * 60, // retry for up to 24 hours
});

registerRoute(
  ({ url }) => url.pathname === "/api/orders",
  new NetworkOnly({ plugins: [ordersQueue] }),
  "POST"
);

// Push notifications
self.addEventListener("push", (event) => {
  const data = event.data.json();
  event.waitUntil(
    self.registration.showNotification(data.title, {
      body: data.body,
      icon: "/icons/icon-192.png",
      data: { url: data.url },
    })
  );
});

self.addEventListener("notificationclick", (event) => {
  event.notification.close();
  event.waitUntil(self.clients.openWindow(event.notification.data.url));
});

Interview Gold Point

Volunteer the cross-browser reality without being asked: Background Sync is Chromium-only today, so any design relying on it needs a feature-detected fallback (retry-on-next-page-load, or a polling strategy). Naming Workbox's queue as the practical implementation, and explaining that push works while the site is fully closed because the browser vendor's push service - not your page - wakes the service worker, shows you understand the actual delivery mechanism rather than just the API surface.

Q8. How do service worker updates and cache versioning actually work, and how do you avoid serving a stale bundle after a deploy?

ROI: ★★★★★ Frequency: Very High

Short Answer

The browser re-checks sw.js for byte differences on every navigation (and at least every 24 hours in the background), never from cache - the file that registers your service worker is deliberately exempt from HTTP caching for exactly this reason. If it differs by even one byte, the browser installs the new worker in parallel with the old one, and - as covered in Q3 - the new one sits waiting until every tab controlled by the old worker closes, so a mid-session tab never gets old JS talking to a suddenly-new cache.

Cache versioning is the other half of the problem: the install handler shouldn't reuse the same cache name across deploys, or the new worker will keep serving whatever the old cache already had. The pattern is to bake a version (or, better, per-file content hashes via Workbox - Q5) into the cache name, populate the new versioned cache in install, and delete every other cache name in activate so old versions don't accumulate forever.

The remaining piece is user experience: skipWaiting() and clients.claim() let a new worker take over immediately instead of waiting for all tabs to close, but doing that silently can pull the rug out from under a user mid-interaction (a request in flight suddenly served by different logic). The safer pattern is to detect the waiting worker, show a "New version available - refresh" banner, and only call skipWaiting() in response to the user's explicit action. 

const CACHE_VERSION = "v3";
const CACHE_NAME = `app-shell-${CACHE_VERSION}`;

self.addEventListener("install", (event) => {
  event.waitUntil(caches.open(CACHE_NAME).then((c) => c.addAll(APP_SHELL_FILES)));
});

self.addEventListener("activate", (event) => {
  event.waitUntil(
    caches.keys()
      .then((keys) => Promise.all(keys.filter((k) => k !== CACHE_NAME).map((k) => caches.delete(k))))
      .then(() => self.clients.claim())
  );
});

// In the page: detect a waiting worker and let the USER opt into the update.
navigator.serviceWorker.register("/sw.js").then((reg) => {
  reg.addEventListener("updatefound", () => {
    const newWorker = reg.installing;
    newWorker.addEventListener("statechange", () => {
      if (newWorker.state === "installed" && navigator.serviceWorker.controller) {
        showUpdateBanner(() => newWorker.postMessage({ type: "SKIP_WAITING" }));
      }
    });
  });
});

// In sw.js: only skip waiting when the user asks for it, never automatically.
self.addEventListener("message", (event) => {
  if (event.data && event.data.type === "SKIP_WAITING") self.skipWaiting();
});

Common Mistake

Calling skipWaiting() and clients.claim() unconditionally in every service worker "to make updates apply faster," without also fixing cache versioning. That combination actually makes the stale-bundle problem worse, not better: it forces every open tab onto the new worker immediately, but if the cache name never changed, the new worker just takes over serving the same old cached assets sooner. Fix the cache-naming/revisioning problem first; only then does controlling updates via skipWaiting become safe to reach for.

SECTION 4 - CLIENT-SIDE STORAGE & QUALITY AUDITS

Q9. When and how do you use IndexedDB for client-side storage?

ROI: ★★★☆☆ Frequency: Medium

Short Answer

IndexedDB is the browser's built-in transactional, asynchronous, object-store database, and it's the right tool whenever localStorage stops being enough. localStorage is synchronous (blocks the main thread), string-only (everything gets JSON.stringify'd), capped around 5MB, and has no querying beyond a flat key lookup. IndexedDB is fully async (won't block rendering), stores structured data and blobs directly, supports much larger quotas (a meaningful percentage of available disk, browser-dependent), and lets you define indexes for querying by something other than the primary key.

In a PWA specifically, IndexedDB is where the "offline-first" data layer actually lives: cached API response bodies you want to query (not just replay byte-for-byte the way the Cache API does), a queue of pending writes waiting for connectivity (which is also what Workbox's Background Sync plugin uses under the hood), and any domain data a genuinely offline-capable app - a note-taking app, a todo app, an inventory scanner - needs to read and write with the network fully absent.

The raw IndexedDB API is callback-and-event based and notoriously painful to hand-write correctly (versioned upgrade transactions, cursor iteration, request/onsuccess/onerror boilerplate everywhere). In practice almost nobody uses it directly - the near-universal choice is Jake Archibald's idb library, which wraps the same API in promises with essentially no other behavior change. 

import { openDB } from "idb";

const dbPromise = openDB("shop-db", 1, {
  upgrade(db) {
    const store = db.createObjectStore("products", { keyPath: "id" });
    store.createIndex("by-category", "category");
  },
});

export async function cacheProduct(product) {
  const db = await dbPromise;
  await db.put("products", product);
}

export async function getProductsByCategory(category) {
  const db = await dbPromise;
  return db.getAllFromIndex("products", "by-category", category);
}

Interview Gold Point

The clean distinction to draw: the Cache API (used by the service worker) stores request/response pairs and is optimized for "replay this HTTP response," while IndexedDB stores structured, queryable JavaScript objects and is optimized for "let me actually read and filter this data offline." A mature PWA typically uses both - Cache API for assets and raw API responses, IndexedDB for the structured domain data and any write queue - and conflating the two is a common gap.

Q10. What does a Lighthouse PWA audit actually check, and which metrics matter?

ROI: ★★★☆☆ Frequency: Medium

Short Answer

Lighthouse audits a PWA along two related but distinct tracks: whether it satisfies the technical criteria to be installable at all, and whether it's optimized once installed. Since Lighthouse v10, the standalone "PWA" scored category was removed from the default report in favor of a manual/installability checklist plus folding the relevant checks into the broader audit - but the underlying checks (and the questions interviewers ask about them) haven't changed.

Installability checks verify the manifest is valid and reachable (name, a 192px and 512px icon, a sensible start_url), that a service worker is registered with a fetch handler that returns a 200 for a navigation while offline, and that the site is served over HTTPS. "PWA optimized" checks are softer polish items: a themed address bar via theme_color, a correctly configured splash screen, a viewport meta tag, and an apple-touch-icon for iOS home-screen icons (since iOS ignores most of the manifest).

The metrics that matter beyond the installability checklist are the Core Web Vitals - LCP, CLS, and INP (replacing TBT/FID in the current model) - because a technically "installable" PWA that's slow to render or janky to interact with fails the "fast" and "reliable" pillars from Q1 even with a perfect manifest. For CI, teams typically wire up lighthouse-ci to fail a build if a PR regresses these scores, rather than relying on someone remembering to run Lighthouse manually before shipping.

Audit area What it checks Why it matters
Installability valid manifest, icons (192/512), registered SW, HTTPS gates whether beforeinstallprompt can fire at all
PWA optimized theme_color, splash screen, viewport meta, apple-touch-icon polish affecting perceived install quality
Offline response navigation to start_url returns 200 while offline proves the SW serves something real, not just theory
Core Web Vitals LCP, CLS, INP an installable PWA that's slow still fails "fast/reliable"

Interview Favorite

A candidate who only recites "Lighthouse gives you a PWA score out of 100" is dating themselves to pre-v10 tooling. The stronger answer names the actual mechanics - installability criteria plus optimization checks plus Core Web Vitals - and mentions wiring lighthouse-ci into the pipeline so regressions fail a PR automatically instead of being caught (or missed) after a manual spot-check.

SECTION 5 - SECURITY, TRADEOFFS & DEBUGGING

Q11. What are the key security considerations for service workers - HTTPS and scope?

ROI: ★★★★☆ Frequency: High

Short Answer

A service worker is, by design, a programmable network proxy that can inspect, rewrite, or fabricate the response to any request in its scope - which is exactly why browsers refuse to register one on anything other than HTTPS (with an explicit exception for localhost/127.0.0.1 to make local development possible). Without that requirement, a service worker delivered over a compromised or intercepted HTTP connection would hand an attacker a persistent, silent man-in-the-middle position over every future request the site makes - far more dangerous than a single injected script, because it survives page reloads and new sessions.

Scope is the other core boundary: a service worker registered at /app/sw.js only controls requests under /app/ by default - it cannot see or intercept requests to /admin/ on the same origin. This can be widened by serving the script with a Service-Worker-Allowed response header naming a broader path, but the script itself must still be served from a path at or above what it's claiming - you can't have a script at /scripts/sw.js silently claim control of / without the server explicitly allowing it, which prevents one part of a site from unilaterally taking over another.

The remaining practical risk is what you put into the cache: a fetch handler that blindly caches whatever a response returns, including opaque cross-origin responses or responses it never validated the status of, can end up serving a cached error page as if it were valid content, or caching something an attacker controls if a proxied endpoint is compromised. Production code should check response.ok/response.type before writing anything to the Cache API.

Concern Why it exists Mitigation
HTTPS requirement SW can intercept/rewrite every response in scope - MITM-capable by design browsers block registration on non-HTTPS (localhost excepted)
Scope a SW at /app/sw.js defaults to controlling only /app/* widen deliberately via Service-Worker-Allowed, never by default
Cache poisoning anything cached is replayed with no further validation check response.ok/type before cache.put; distrust opaque responses
Persistent control a bad SW keeps intercepting until explicitly replaced/unregistered ship version checks and a documented forced-unregister path

Common Mistake

Treating HTTPS-for-service-workers as an arbitrary platform restriction rather than explaining the actual threat model. The strong answer names the specific danger - a persistent, silent request-rewriting position that outlives a single page load - because that's what distinguishes it from "any script needs HTTPS," and shows you understand why browser vendors specifically singled this API out.

Q12. PWA vs native app vs React Native - what are the real trade-offs?

ROI: ★★★★☆ Frequency: High

Short Answer

This is a distribution-and-capability trade-off, not a "which is objectively better" question, and a senior answer frames it that way. A PWA is a single web codebase, distributed via URL with an optional install step, that updates instantly on the next load and can reach any device with a modern browser - at the cost of limited access to native platform capabilities and generally weaker performance for anything animation- or graphics-heavy. React Native gives near-native performance and much deeper access to native APIs from a single JavaScript codebase that compiles to real iOS and Android apps, at the cost of still needing app store distribution, review delays for updates, and occasional native-module work when a capability isn't bridged. Fully native (Swift/Kotlin) gives the best possible performance and complete platform access, at the cost of maintaining two separate codebases and teams.

The decision in practice comes down to what the app actually needs. Content-heavy, broad-reach products where install friction and reach matter more than deep hardware access (a news site, a documentation portal, most e-commerce) are well served by a PWA, especially if budget or team size makes maintaining a second native codebase a real cost. Apps that live and die by camera/AR features, background location, deep OS integration, or that need App Store/Play Store presence for discoverability and trust lean toward React Native or native. It's also increasingly common to ship both - a PWA as the low-friction default and a thin native wrapper for users who specifically want the store listing or deeper OS hooks.

Aspect PWA React Native Fully Native
Distribution URL, optional install App Store / Play Store review App Store / Play Store review
Codebases one web codebase one JS codebase, compiles to both separate per platform
Native API access limited to exposed Web APIs near-native via bridge/native modules full, first-class
Performance good for content, weaker for heavy animation near-native, some bridge overhead best
Update model instant, next load / SW update store review + rollout store review + rollout
Offline manual, via SW + IndexedDB native storage, straightforward native storage, straightforward

Interview Favorite

The framing interviewers reward: "it's reach and update velocity versus platform depth and store presence, not good versus bad." Naming a concrete deciding factor - camera/AR-heavy, needs deep OS integration, or must appear in the App Store for discoverability, all push toward React Native/native - shows you'd actually make this call on a real product rather than reciting a feature list.

Q13. How do you debug a service worker using the DevTools Application tab?

ROI: ★★★☆☆ Frequency: Medium

Short Answer

Chrome/Edge DevTools' Application panel is the primary tool, and its Service Workers section is where most debugging starts: it lists every registration for the current origin, its status (activated, waiting, redundant), and gives direct controls that are hard to trigger otherwise - "Update on reload" forces a fresh install/activate cycle on every refresh during development (essential, since production update-checking is deliberately lazy), "Bypass for network" temporarily routes all requests around the service worker entirely so you can tell whether a bug is in the SW or the app itself, and "Offline" simulates zero connectivity without touching your OS network settings, which is the fastest way to test fallback pages and cache-first behavior.

The Cache Storage section under Application lets you inspect exactly what's in each named cache - which is often the fastest way to confirm a suspected stale-cache bug, by literally seeing an old cache name still present after a deploy that should have deleted it. The Network tab is useful alongside this: a request served by the service worker shows "(ServiceWorker)" in its Size/Source column instead of a real transfer size, confirming interception actually happened rather than the request silently going straight to network.

Less commonly known but genuinely useful: the DevTools console has a context dropdown that lets you execute code directly inside the service worker's own global scope rather than the page's - useful for calling self.clients.matchAll() or inspecting cache contents live without instrumenting the SW file itself. chrome://serviceworker-internals (and its per-origin equivalent) gives an even lower-level view for registrations that seem stuck.

Interview Gold Point

Mentioning "Update on reload" unprompted is a strong signal - it directly answers the practical annoyance every service worker developer hits ("why isn't my change showing up") by exposing that production update-checking is intentionally lazy (Q8), and that development needs to force it. Pairing that with "Bypass for network" as the tool for isolating "is this an SW bug or an app bug" shows a debugging methodology, not just a list of panel names.

Q14. What's the most common and costly PWA pitfall - a stale service worker serving an old JS bundle forever?

ROI: ★★★★★ Frequency: Very High

Short Answer

This is the failure mode every experienced PWA engineer has a war story about, and it's the natural convergence of everything in Section 2 and 3 going wrong at once. It happens when a fetch handler applies a cache-first strategy to the app's JS/CSS bundle using a fixed cache key or URL - /app.js, not /app.8f3ac1.js - and the activate handler never purges old cache entries because the cache name never changes between deploys. The very first time a user visits, their service worker caches whatever /app.js was at that moment, and because the URL and cache key are identical on every future deploy, the cache-first strategy finds a "hit" forever and never fetches the new bytes again - not next week, not next year, until the user manually clears site data or the browser evicts the cache under storage pressure.

What makes this especially nasty in production is that it's silent and inconsistent across your user base: new visitors get the new bundle, but existing users are frozen on whatever version they first cached, sometimes for months, with no error and no console warning - support tickets describe a bug you fixed two releases ago, and it takes someone specifically checking a user's Cache Storage in DevTools (Q13) to realize their client is running ancient code that hasn't been network-fetched since it was first installed.

The fix is the combination already covered piece by piece: build output must use content-hashed filenames (or Workbox's revisioned precache manifest) so a code change is structurally guaranteed to produce a new URL, never reuse a bare, unhashed cache key for anything cache-first, delete every cache name that isn't the current version inside activate, and - since a user could still be stuck on the old service worker itself if it never even notices the new one - make sure the app surfaces a "new version available" prompt (Q8) rather than assuming the browser's lazy update check will save you promptly. 

// BAD: cache-first on a URL that never changes, cache name that never changes
self.addEventListener("fetch", (event) => {
  if (event.request.url.endsWith("/app.js")) {
    event.respondWith(
      caches.match("/app.js").then((cached) => cached || fetch(event.request))
    );
  }
});
// Every deploy ships a new /app.js body, but the cache key never changes,
// so this SW serves the FIRST version it ever cached - indefinitely.

// GOOD: hashed filenames make the bug structurally impossible
// build output: /assets/app.8f3ac1.js  ->  next deploy: /assets/app.4d90e2.js
import { precacheAndRoute } from "workbox-precaching";
precacheAndRoute(self.__WB_MANIFEST); // each entry is revisioned by the build

self.addEventListener("activate", (event) => {
  event.waitUntil(
    caches.keys().then((keys) =>
      Promise.all(keys.filter((k) => !EXPECTED_CACHE_NAMES.includes(k)).map((k) => caches.delete(k)))
    )
  );
});

Common Mistake

Treating this as a rare edge case rather than the default outcome of the two most common shortcuts: hand-writing a cache-first fetch handler without content-hashed asset names, and never auditing what activate actually deletes. The interview-winning move is naming the fix before being asked "how would you prevent this" - content hashing plus revisioned precaching plus an activate-time purge is the standard answer, and it's exactly what Q5 and Q8 build up to.

QUICK REVISION SHEET

  • A PWA earns installability, it isn't granted it - the four pillars are installable, reliable, fast, and engaging, with reliability (offline-capable via SW) as the foundation the rest depends on
  • manifest.json (name, icons 192/512, start_url, display, scope) plus a registered SW with a working fetch handler plus HTTPS are what actually triggers beforeinstallprompt - a manifest alone does nothing
  • SW lifecycle: install (populate cache, wrap in waitUntil) -> activate (purge old caches, wrap in waitUntil) -> fetch (intercept every request); a new worker waits until old tabs close unless you opt into skipWaiting/clients.claim
  • Cache-first for immutable hashed assets, network-first for freshness-sensitive content with an offline fallback, stale-while-revalidate for instant-but-self-healing content; never one global strategy for everything
  • Workbox provides pre-built strategy classes plus build-time precache revisioning (content-hashed manifest), so a changed file is guaranteed a new cache entry instead of you remembering to bump a version
  • Offline support = app-shell precaching + a genuinely offline-capable fallback page served via a catch handler; navigator.onLine is a UX signal only, never the real source of truth for whether a fetch will succeed
  • Background Sync (Chromium-only, best used via Workbox's queue) retries a failed request once connectivity returns; Push works while the site is closed because the browser's push service - not your page - wakes the SW
  • Service worker updates check sw.js for byte differences on every navigation; cache versioning (or Workbox's revisioning) plus an activate-time purge is what actually prevents a stale bundle, not skipWaiting alone
  • IndexedDB is the async, structured, queryable client-side database for offline domain data and write queues; Cache API stores request/response pairs, IndexedDB stores objects you can actually filter
  • Lighthouse checks installability criteria + PWA-optimization polish + Core Web Vitals (LCP/CLS/INP); wire lighthouse-ci into the pipeline so regressions fail a PR instead of being missed
  • HTTPS is required because a SW is a persistent, silent request-rewriting proxy; scope defaults to the SW script's own path and only widens via an explicit Service-Worker-Allowed header
  • PWA vs React Native vs native is reach-and-update-velocity versus platform-depth-and-store-presence, not "better/worse" - pick based on how much native capability and store discoverability the product actually needs
