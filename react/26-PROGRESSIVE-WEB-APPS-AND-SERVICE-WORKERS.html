SECTION 1 - PWA FUNDAMENTALS & THE WEB APP MANIFEST

Q1. What actually makes a web app "progressive"?

ROI: ★★★★☆ Frequency: High

Short Answer

"Progressive" does not describe one feature, it describes a philosophy: the app works for every visitor at a baseline level, and progressively enhances itself as the browser and network conditions allow. A PWA is not a different kind of app you build from scratch, it is a normal web app that has earned four properties - installable, reliable, fast, and engaging - by adopting a small set of web platform APIs on top of what you already ship.

Installable. With a valid manifest and a registered service worker, a compliant browser offers to add the app to the home screen or app drawer, so it launches like a native app, in its own window, with its own icon, no browser chrome.

Reliable. A service worker sits between the page and the network and can serve a working experience even when the network is flaky or absent, instead of the browser's default "no internet" dinosaur.

Fast. Precached app-shell assets and cached API responses mean repeat visits render instantly from cache rather than waiting on a cold network round trip, which also happens to be excellent for Core Web Vitals.

Engaging. Push notifications and background sync let the app bring users back and finish work they started offline, closing some of the gap with native app re-engagement mechanics.

Pillar Enabling mechanism User-visible benefit
Installable manifest.json + registered service worker + HTTPS home-screen icon, standalone window, no address bar
Reliable service worker fetch interception + cache works with flaky or no network
Fast precaching + cached responses instant repeat loads
Engaging Push API, Notifications API, Background Sync re-engagement, offline task completion

Interview Gold Point

The framing that separates a strong answer is "installability is a reward for reliability, not a feature you bolt on." Chrome's install prompt only fires once the browser can verify the service worker actually produces a usable offline response - so a candidate who leads with "you add a manifest and get an install button" is missing the point. Lead with reliability and offline-first thinking, then mention that installability, speed, and engagement fall out of it.

Q2. What goes in the Web App Manifest, and how does the add-to-home-screen flow actually work?

ROI: ★★★★☆ Frequency: High

Short Answer

The manifest is a JSON file, linked from the page with <link rel="manifest" href="/manifest.json">, that tells the browser how to present the app if it's installed: its name, icons, start URL, display mode, and theme colors. On its own the manifest does nothing visible - it becomes actionable once the browser also sees a registered service worker with a fetch handler, and the whole thing is served over HTTPS. Meeting those criteria is what makes Chrome fire a beforeinstallprompt event, which you can capture to show your own "Install app" button instead of relying on the browser's default UI.

Key manifest fields worth knowing cold: name/short_name (full vs home-screen label), start_url (what opens when launched from the home screen, often with a query param to distinguish installed launches in analytics), display (standalone hides browser chrome, fullscreen hides everything, browser is just a tab), scope (which URLs are considered "inside" the app), theme_color/background_color (status bar and splash-screen color), and icons (must include at least a 192x192 and 512x512 PNG; a purpose: "maskable" icon avoids ugly cropping on Android's adaptive icon shapes).

The beforeinstallprompt event is Chromium-specific (Safari and Firefox have no equivalent event, and iOS Safari has its own manual "Add to Home Screen" share-sheet flow with much weaker manifest support). Capturing the event and calling preventDefault() suppresses the automatic mini-infobar so you can trigger the real native prompt later, from your own UI, at a moment the user is more likely to say yes - a well-known best practice is not showing it on the very first page load. 

// manifest.json
{
  "name": "Acme Shop",
  "short_name": "Acme",
  "start_url": "/?source=pwa",
  "scope": "/",
  "display": "standalone",
  "background_color": "#ffffff",
  "theme_color": "#1f4e79",
  "orientation": "portrait",
  "icons": [
    { "src": "/icons/icon-192.png", "sizes": "192x192", "type": "image/png" },
    { "src": "/icons/icon-512.png", "sizes": "512x512", "type": "image/png", "purpose": "any maskable" }
  ]
}

// app.js - capture the install prompt and trigger it from your own UI
let deferredPrompt;

window.addEventListener("beforeinstallprompt", (e) => {
  e.preventDefault();          // suppress the default mini-infobar
  deferredPrompt = e;
  installButton.hidden = false; // show a custom "Install app" button
});

installButton.addEventListener("click", async () => {
  if (!deferredPrompt) return;
  deferredPrompt.prompt();
  const { outcome } = await deferredPrompt.userChoice; // "accepted" | "dismissed"
  deferredPrompt = null;
  installButton.hidden = true;
});

window.addEventListener("appinstalled", () => {
  analytics.track("pwa_installed");
});

Common Mistake

Assuming the manifest alone makes an app installable. Chrome's actual install heuristic requires the manifest, a registered service worker whose fetch handler produces a real 200 response for the start URL, HTTPS, and (historically) a minimum engagement threshold from the user. A candidate who ships a manifest, sees no install prompt, and can't explain why is exposing a gap - the fix is almost always "the service worker isn't registered yet, or its fetch handler doesn't actually respond."

SECTION 2 - SERVICE WORKER LIFECYCLE & CACHING STRATEGIES

Q3. Walk through the service worker lifecycle - install, activate, and fetch.

ROI: ★★★★★ Frequency: Very High

Short Answer

A service worker is a JavaScript file that runs on its own thread, separate from the page, with no DOM access and no shared global state guaranteed to survive - the browser can spin it down and wake it up per event at will, so every handler has to be self-contained and idempotent. It goes through three main events. install fires once, when the browser first sees a new or byte-different sw.js; this is where you open a cache and pre-populate it with the app shell. activate fires once the new worker takes control; this is where you clean up caches left by a previous version. fetch fires on every network request the page makes while the worker is in control, and is where you intercept the request and decide whether to answer from cache, from the network, or a mix of both.

The subtlety interviewers probe is the gap between installed and activated. A new service worker installs in the background even while an old one is still controlling open tabs, and by default it sits in a waiting state until every tab controlled by the old worker is closed - this exists specifically so that a page never has two different versions of your app logic and cache running simultaneously mid-session. self.skipWaiting() inside install bypasses that wait, and self.clients.claim() inside activate makes the new worker take control of already-open tabs immediately rather than waiting for the next navigation - both are opt-in precisely because skipping the safety wait has consequences (see Q8).

Every handler that does async work must be wrapped in event.waitUntil() (for install/activate) or event.respondWith() (for fetch) - these tell the browser "don't tear this worker down, and don't let the default network behavior happen, until this promise settles." Forgetting this is a classic bug: the cache population races with the browser considering install "done." 

const CACHE_NAME = "app-shell-v1";
const APP_SHELL = ["/", "/index.html", "/app.css", "/app.js"];

self.addEventListener("install", (event) => {
  event.waitUntil(
    caches.open(CACHE_NAME).then((cache) => cache.addAll(APP_SHELL))
  );
  // self.skipWaiting();  // opt-in only - see Q8 for why this needs care
});

self.addEventListener("activate", (event) => {
  event.waitUntil(
    caches.keys().then((keys) =>
      Promise.all(
        keys.filter((key) => key !== CACHE_NAME).map((key) => caches.delete(key))
      )
    )
  );
  // self.clients.claim();  // opt-in only - see Q8
});

self.addEventListener("fetch", (event) => {
  event.respondWith(
    caches.match(event.request).then((cached) => cached || fetch(event.request))
  );
});

Interview Gold Point

State the "why" behind the waiting phase explicitly: it exists so a user with an open tab never gets a mismatched combination of old page JS talking to a new cache, or vice versa, mid-session. Naming skipWaiting/clients.claim as deliberate escape hatches - not defaults - and connecting them to real consequences (Q8) is what separates "I copied this from MDN" from "I've operated this in production."

Q4. What are the main caching strategies a service worker can implement, and when do you pick each?

ROI: ★★★★★ Frequency: Very High

Short Answer

A caching strategy is just the policy your fetch handler applies to decide cache-vs-network for a given request, and the right choice depends entirely on how often that resource changes and how much staleness is acceptable. There is no single correct strategy for a whole app - production service workers almost always run different strategies for different request types, routed by URL pattern or request destination.

Cache-first - check the cache, serve it if present, only hit the network on a miss (and then populate the cache). Best for content-hashed, versioned static assets that never change once fetched - if the bytes at a URL never change, there's no reason to ever re-fetch them.

Network-first - try the network, and only fall back to the cache if the network fails or times out. Best for data where freshness matters more than instant response, but where offline access is still a nice-to-have - an HTML document, a news feed, a price.

Stale-while-revalidate - respond from the cache immediately (fast, feels instant) while simultaneously fetching from the network in the background and updating the cache for the next request. This is the pragmatic middle ground: the user never waits on the network, but the cache slowly heals itself, so it fits content that should feel instant without staying wrong forever.

Strategy Behavior Best for
Cache-first serve from cache; network only on miss hashed/versioned JS, CSS, fonts, icons
Network-first try network; fall back to cache on failure HTML shell, feeds, prices - freshness matters
Stale-while-revalidate serve cache instantly; refresh cache in background avatars, list pages - instant but self-healing
Network-only always network, never cached POST/mutating requests, analytics beacons
Cache-only always cache, never network assets guaranteed precached at install, immutable 
// Hand-rolled stale-while-revalidate for /api/* GET requests
self.addEventListener("fetch", (event) => {
  const { request } = event;
  if (request.method === "GET" && request.url.includes("/api/")) {
    event.respondWith(
      caches.open("api-cache").then(async (cache) => {
        const cached = await cache.match(request);
        const networkFetch = fetch(request).then((response) => {
          cache.put(request, response.clone());
          return response;
        });
        // Serve stale immediately if we have it; otherwise wait on the network.
        return cached || networkFetch;
      })
    );
  }
});

Interview Favorite

The one-line comparison to lead with: "cache-first for things that never change, network-first for things that should stay fresh but can survive being briefly stale, stale-while-revalidate when you want the speed of cache-first without the staleness of never re-checking." Then immediately volunteer that a real app runs several of these side by side, routed by request type - a single global strategy is a beginner tell.

Q5. What is Workbox, and how does it handle precaching build assets?

ROI: ★★★★☆ Frequency: High

Short Answer

Workbox is Google's library for writing service workers without hand-rolling cache-name bookkeeping, strategy logic, and expiration policy every time. It ships pre-built strategy classes (CacheFirst, NetworkFirst, StaleWhileRevalidate) that implement exactly the policies from Q4 correctly - including edge cases like opaque cross-origin responses and cache timeouts - so you route requests to a strategy instead of writing the caching logic by hand.

Its other major job is precaching with revisioning. A build plugin (workbox-webpack-plugin, or the equivalent in Vite via vite-plugin-pwa) scans your build output and injects a manifest array of every asset with either a content hash already in its filename or an explicit revision hash Workbox computes, then precacheAndRoute(self.__WB_MANIFEST) caches all of them at install time and - critically - only re-fetches the specific files whose hash actually changed on the next deploy, leaving unchanged assets untouched in the cache. This is the production-grade version of the cache-versioning problem discussed in Q8 and Q14: instead of you remembering to bump a cache name, the build tool guarantees a changed file always gets a new URL.

Runtime (non-precached) requests - API calls, images, fonts loaded on demand - are handled with registerRoute, matching a URL pattern or request type to one of the strategy classes, optionally combined with plugins like ExpirationPlugin (cap entries or age) or BackgroundSyncPlugin (Q7). 

// sw.js built with Workbox (e.g. via vite-plugin-pwa or workbox-webpack-plugin)
import { precacheAndRoute } from "workbox-precaching";
import { registerRoute } from "workbox-routing";
import { CacheFirst, NetworkFirst } from "workbox-strategies";
import { ExpirationPlugin } from "workbox-expiration";

// Injected at build time, one entry per hashed asset:
// [{ url: "/assets/app.8f3ac1.js", revision: null }, { url: "/assets/logo.png", revision: "a1b2c3" }, ...]
precacheAndRoute(self.__WB_MANIFEST);

registerRoute(
  ({ request }) => request.destination === "image",
  new CacheFirst({
    cacheName: "images",
    plugins: [new ExpirationPlugin({ maxEntries: 60, maxAgeSeconds: 30 * 24 * 60 * 60 })],
  })
);

registerRoute(
  ({ url }) => url.pathname.startsWith("/api/"),
  new NetworkFirst({ cacheName: "api-cache", networkTimeoutSeconds: 3 })
);

Interview Gold Point

The strongest signal here is connecting Workbox's revisioned precache manifest directly to the "stale bundle after deploy" failure mode - explain that hand-rolled service workers get this wrong constantly (fixed cache key, never re-fetches), while Workbox's build-time hashing means a code change is structurally guaranteed to produce a new cache entry. Mentioning that you'd reach for Workbox specifically to avoid re-implementing expiration and cross-origin edge cases correctly shows production judgment, not just API recall.

SECTION 3 - OFFLINE SUPPORT, BACKGROUND SYNC & UPDATES

Q6. How do you build offline support and a fallback page for navigation failures?

ROI: ★★★★☆ Frequency: High

Short Answer

Offline support is really two separate things: caching enough of the app shell and data that most navigations succeed from cache, and providing a deliberate, designed fallback for the requests that still fail - rather than letting the browser show its default disconnected-network error page. The standard pattern is the "app shell" model: precache the HTML skeleton, CSS, and JS so the UI frame always renders, then let individual API calls fail gracefully within that frame with cached or placeholder data.

For the case where even the shell request fails outright (a first-ever visit with no connectivity, or a deep link the shell never cached), you precache a small, self-contained offline.html at install time and register a "catch" handler that serves it whenever a navigation request throws. The fallback page should be genuinely offline-capable itself - no external fonts, no analytics scripts that will also fail and throw console noise, ideally under a few KB.

Detecting connectivity client-side (navigator.onLine, the online/offline window events) is a useful UX signal for showing a banner, but it is not reliable for deciding whether a fetch will actually succeed - a device can report "online" while connected to a captive portal or a network with no real route out, so the source of truth is always the fetch itself succeeding or failing, not the connectivity flag. 

import { precacheAndRoute } from "workbox-precaching";
import { registerRoute, setCatchHandler } from "workbox-routing";
import { NetworkFirst } from "workbox-strategies";

// Precache the fallback page itself so it's available with zero network.
precacheAndRoute([{ url: "/offline.html", revision: "1" }]);

registerRoute(({ request }) => request.mode === "navigate", new NetworkFirst());

// Runs when every registered route's strategy still throws (e.g. no cache, no network).
setCatchHandler(async ({ event }) => {
  if (event.request.destination === "document") {
    return caches.match("/offline.html");
  }
  return Response.error();
});

Common Mistake

Treating navigator.onLine as authoritative. It only reflects whether the OS reports a network interface as connected, not whether requests actually reach your servers - candidates who describe gating all fetch logic behind an onLine check are describing a UX enhancement, not a real offline strategy. The real strategy has to live in the service worker's fetch handling and catch logic, which experiences the actual failure directly.

Q7. How do Background Sync and Push Notifications work in a service worker?

ROI: ★★★☆☆ Frequency: Medium

Short Answer

Background Sync lets you defer a failed action (typically a POST that failed because the user was offline) and have the browser automatically retry it once connectivity returns, even if the user has closed the tab. The page calls registration.sync.register("tag-name") when a request fails; the browser fires a sync event on the service worker as soon as it detects connectivity, and you retry the queued request(s) there. Support is inconsistent - it's a Chromium feature with no Safari/Firefox support, which is why Workbox's BackgroundSyncPlugin (a durable IndexedDB-backed queue with automatic retry) is the practical way to use it, since it degrades safely on unsupported browsers rather than throwing.

Push Notifications are a separate, two-part system. First, the client subscribes via PushManager.subscribe() with a VAPID public key, which returns a subscription object (endpoint URL + keys) that you send to your backend and store per user. Later, your server sends a message to that endpoint (using a library like web-push, signed with your VAPID private key) via the browser vendor's push service - this works even if the site isn't open, because the browser itself, not your page, receives the push. The service worker's push event handler then calls self.registration.showNotification(...) to actually display it, and a notificationclick handler decides what happens when the user taps it (usually opening or focusing a specific URL).

Both features require the app to already be a registered, controlling service worker, and push additionally requires explicit user permission via the Notifications API - a permission prompt users are increasingly conditioned to reject if it's requested immediately on page load rather than after a meaningful interaction. 

// Queue a failed POST and retry automatically once back online (Workbox)
import { BackgroundSyncPlugin } from "workbox-background-sync";
import { registerRoute } from "workbox-routing";
import { NetworkOnly } from "workbox-strategies";

const ordersQueue = new BackgroundSyncPlugin("orders-queue", {
  maxRetentionTime: 24 * 60, // retry for up to 24 hours
});

registerRoute(
  ({ url }) => url.pathname === "/api/orders",
  new NetworkOnly({ plugins: [ordersQueue] }),
  "POST"
);

// Push notifications
self.addEventListener("push", (event) => {
  const data = event.data.json();
  event.waitUntil(
    self.registration.showNotification(data.title, {
      body: data.body,
      icon: "/icons/icon-192.png",
      data: { url: data.url },
    })
  );
});

self.addEventListener("notificationclick", (event) => {
  event.notification.close();
  event.waitUntil(self.clients.openWindow(event.notification.data.url));
});

Interview Gold Point

Volunteer the cross-browser reality without being asked: Background Sync is Chromium-only today, so any design relying on it needs a feature-detected fallback (retry-on-next-page-load, or a polling strategy). Naming Workbox's queue as the practical implementation, and explaining that push works while the site is fully closed because the browser vendor's push service - not your page - wakes the service worker, shows you understand the actual delivery mechanism rather than just the API surface.

Q8. How do service worker updates and cache versioning actually work, and how do you avoid serving a stale bundle after a deploy?

ROI: ★★★★★ Frequency: Very High

Short Answer

The browser re-checks sw.js for byte differences on every navigation (and at least every 24 hours in the background), never from cache - the file that registers your service worker is deliberately exempt from HTTP caching for exactly this reason. If it differs by even one byte, the browser installs the new worker in parallel with the old one, and - as covered in Q3 - the new one sits waiting until every tab controlled by the old worker closes, so a mid-session tab never gets old JS talking to a suddenly-new cache.

Cache versioning is the other half of the problem: the install handler shouldn't reuse the same cache name across deploys, or the new worker will keep serving whatever the old cache already had. The pattern is to bake a version (or, better, per-file content hashes via Workbox - Q5) into the cache name, populate the new versioned cache in install, and delete every other cache name in activate so old versions don't accumulate forever.

The remaining piece is user experience: skipWaiting() and clients.claim() let a new worker take over immediately instead of waiting for all tabs to close, but doing that silently can pull the rug out from under a user mid-interaction (a request in flight suddenly served by different logic). The safer pattern is to detect the waiting worker, show a "New version available - refresh" banner, and only call skipWaiting() in response to the user's explicit action. 

const CACHE_VERSION = "v3";
const CACHE_NAME = `app-shell-${CACHE_VERSION}`;

self.addEventListener("install", (event) => {
  event.waitUntil(caches.open(CACHE_NAME).then((c) => c.addAll(APP_SHELL_FILES)));
});

self.addEventListener("activate", (event) => {
  event.waitUntil(
    caches.keys()
      .then((keys) => Promise.all(keys.filter((k) => k !== CACHE_NAME).map((k) => caches.delete(k))))
      .then(() => self.clients.claim())
  );
});

// In the page: detect a waiting worker and let the USER opt into the update.
navigator.serviceWorker.register("/sw.js").then((reg) => {
  reg.addEventListener("updatefound", () => {
    const newWorker = reg.installing;
    newWorker.addEventListener("statechange", () => {
      if (newWorker.state === "installed" && navigator.serviceWorker.controller) {
        showUpdateBanner(() => newWorker.postMessage({ type: "SKIP_WAITING" }));
      }
    });
  });
});

// In sw.js: only skip waiting when the user asks for it, never automatically.
self.addEventListener("message", (event) => {
  if (event.data && event.data.type === "SKIP_WAITING") self.skipWaiting();
});

Common Mistake

Calling skipWaiting() and clients.claim() unconditionally in every service worker "to make updates apply faster," without also fixing cache versioning. That combination actually makes the stale-bundle problem worse, not better: it forces every open tab onto the new worker immediately, but if the cache name never changed, the new worker just takes over serving the same old cached assets sooner. Fix the cache-naming/revisioning problem first; only then does controlling updates via skipWaiting become safe to reach for.

SECTION 4 - CLIENT-SIDE STORAGE & QUALITY AUDITS

Q9. When and how do you use IndexedDB for client-side storage?

ROI: ★★★☆☆ Frequency: Medium

Short Answer

IndexedDB is the browser's built-in transactional, asynchronous, object-store database, and it's the right tool whenever localStorage stops being enough. localStorage is synchronous (blocks the main thread), string-only (everything gets JSON.stringify'd), capped around 5MB, and has no querying beyond a flat key lookup. IndexedDB is fully async (won't block rendering), stores structured data and blobs directly, supports much larger quotas (a meaningful percentage of available disk, browser-dependent), and lets you define indexes for querying by something other than the primary key.

In a PWA specifically, IndexedDB is where the "offline-first" data layer actually lives: cached API response bodies you want to query (not just replay byte-for-byte the way the Cache API does), a queue of pending writes waiting for connectivity (which is also what Workbox's Background Sync plugin uses under the hood), and any domain data a genuinely offline-capable app - a note-taking app, a todo app, an inventory scanner - needs to read and write with the network fully absent.

The raw IndexedDB API is callback-and-event based and notoriously painful to hand-write correctly (versioned upgrade transactions, cursor iteration, request/onsuccess/onerror boilerplate everywhere). In practice almost nobody uses it directly - the near-universal choice is Jake Archibald's idb library, which wraps the same API in promises with essentially no other behavior change. 

import { openDB } from "idb";

const dbPromise = openDB("shop-db", 1, {
  upgrade(db) {
    const store = db.createObjectStore("products", { keyPath: "id" });
    store.createIndex("by-category", "category");
  },
});

export async function cacheProduct(product) {
  const db = await dbPromise;
  await db.put("products", product);
}

export async function getProductsByCategory(category) {
  const db = await dbPromise;
  return db.getAllFromIndex("products", "by-category", category);
}

Interview Gold Point

The clean distinction to draw: the Cache API (used by the service worker) stores request/response pairs and is optimized for "replay this HTTP response," while IndexedDB stores structured, queryable JavaScript objects and is optimized for "let me actually read and filter this data offline." A mature PWA typically uses both - Cache API for assets and raw API responses, IndexedDB for the structured domain data and any write queue - and conflating the two is a common gap.

Q10. What does a Lighthouse PWA audit actually check, and which metrics matter?

ROI: ★★★☆☆ Frequency: Medium

Short Answer

Lighthouse audits a PWA along two related but distinct tracks: whether it satisfies the technical criteria to be installable at all, and whether it's optimized once installed. Since Lighthouse v10, the standalone "PWA" scored category was removed from the default report in favor of a manual/installability checklist plus folding the relevant checks into the broader audit - but the underlying checks (and the questions interviewers ask about them) haven't changed.

Installability checks verify the manifest is valid and reachable (name, a 192px and 512px icon, a sensible start_url), that a service worker is registered with a fetch handler that returns a 200 for a navigation while offline, and that the site is served over HTTPS. "PWA optimized" checks are softer polish items: a themed address bar via theme_color, a correctly configured splash screen, a viewport meta tag, and an apple-touch-icon for iOS home-screen icons (since iOS ignores most of the manifest).

The metrics that matter beyond the installability checklist are the Core Web Vitals - LCP, CLS, and INP (replacing TBT/FID in the current model) - because a technically "installable" PWA that's slow to render or janky to interact with fails the "fast" and "reliable" pillars from Q1 even with a perfect manifest. For CI, teams typically wire up lighthouse-ci to fail a build if a PR regresses these scores, rather than relying on someone remembering to run Lighthouse manually before shipping.

A candidate who only recites "Lighthouse gives you a PWA score out of 100" is dating themselves to pre-v10 tooling. The stronger answer names the actual mechanics - installability criteria plus optimization checks plus Core Web Vitals - and mentions wiring lighthouse-ci into the pipeline so regressions fail a PR automatically instead of being caught (or missed) after a manual spot-check.

SECTION 5 - SECURITY, TRADEOFFS & DEBUGGING

Q11. What are the key security considerations for service workers - HTTPS and scope?

ROI: ★★★★☆ Frequency: High

Short Answer

A service worker is, by design, a programmable network proxy that can inspect, rewrite, or fabricate the response to any request in its scope - which is exactly why browsers refuse to register one on anything other than HTTPS (with an explicit exception for localhost/127.0.0.1 to make local development possible). Without that requirement, a service worker delivered over a compromised or intercepted HTTP connection would hand an attacker a persistent, silent man-in-the-middle position over every future request the site makes - far more dangerous than a single injected script, because it survives page reloads and new sessions.

Scope is the other core boundary: a service worker registered at /app/sw.js only controls requests under /app/ by default - it cannot see or intercept requests to /admin/ on the same origin. This can be widened by serving the script with a Service-Worker-Allowed response header naming a broader path, but the script itself must still be served from a path at or above what it's claiming - you can't have a script at /scripts/sw.js silently claim control of / without the server explicitly allowing it, which prevents one part of a site from unilaterally taking over another.

The remaining practical risk is what you put into the cache: a fetch handler that blindly caches whatever a response returns, including opaque cross-origin responses or responses it never validated the status of, can end up serving a cached error page as if it were valid content, or caching something an attacker controls if a proxied endpoint is compromised. Production code should check response.ok/response.type before writing anything to the Cache API.

Treating HTTPS-for-service-workers as an arbitrary platform restriction rather than explaining the actual threat model. The strong answer names the specific danger - a persistent, silent request-rewriting position that outlives a single page load - because that's what distinguishes it from "any script needs HTTPS," and shows you understand why browser vendors specifically singled this API out.

Q12. PWA vs native app vs React Native - what are the real trade-offs?

ROI: ★★★★☆ Frequency: High

Short Answer

This is a distribution-and-capability trade-off, not a "which is objectively better" question, and a senior answer frames it that way. A PWA is a single web codebase, distributed via URL with an optional install step, that updates instantly on the next load and can reach any device with a modern browser - at the cost of limited access to native platform capabilities and generally weaker performance for anything animation- or graphics-heavy. React Native gives near-native performance and much deeper access to native APIs from a single JavaScript codebase that compiles to real iOS and Android apps, at the cost of still needing app store distribution, review delays for updates, and occasional native-module work when a capability isn't bridged. Fully native (Swift/Kotlin) gives the best possible performance and complete platform access, at the cost of maintaining two separate codebases and teams.

The decision in practice comes down to what the app actually needs. Content-heavy, broad-reach products where install friction and reach matter more than deep hardware access (a news site, a documentation portal, most e-commerce) are well served by a PWA, especially if budget or team size makes maintaining a second native codebase a real cost. Apps that live and die by camera/AR features, background location, deep OS integration, or that need App Store/Play Store presence for discoverability and trust lean toward React Native or native. It's also increasingly common to ship both - a PWA as the low-friction default and a thin native wrapper for users who specifically want the store listing or deeper OS hooks.

The framing interviewers reward: "it's reach and update velocity versus platform depth and store presence, not good versus bad." Q13. How do you debug a service worker using the DevTools Application tab?

ROI: ★★★☆☆ Frequency: Medium

Short Answer

Chrome/Edge DevTools' Application panel is the primary tool, and its Service Workers section is where most debugging starts: it lists every registration for the current origin, its status (activated, waiting, redundant), and gives direct controls that are hard to trigger otherwise - "Update on reload" forces a fresh install/activate cycle on every refresh during development (essential, since production update-checking is deliberately lazy), "Bypass for network" temporarily routes all requests around the service worker entirely so you can tell whether a bug is in the SW or the app itself, and "Offline" simulates zero connectivity without touching your OS network settings, which is the fastest way to test fallback pages and cache-first behavior.

The Cache Storage section under Application lets you inspect exactly what's in each named cache - which is often the fastest way to confirm a suspected stale-cache bug, by literally seeing an old cache name still present after a deploy that should have deleted it. The Network tab is useful alongside this: a request served by the service worker shows "(ServiceWorker)" in its Size/Source column instead of a real transfer size, confirming interception actually happened rather than the request silently going straight to network.

Less commonly known but genuinely useful: the DevTools console has a context dropdown that lets you execute code directly inside the service worker's own global scope rather than the page's - useful for calling self.clients.matchAll() or inspecting cache contents live without instrumenting the SW file itself. chrome://serviceworker-internals (and its per-origin equivalent) gives an even lower-level view for registrations that seem stuck.

Interview Gold Point

Mentioning "Update on reload" unprompted is a strong signal - it directly answers the practical annoyance every service worker developer hits ("why isn't my change showing up") by exposing that production update-checking is intentionally lazy (Q8), and that development needs to force it. Pairing that with "Bypass for network" as the tool for isolating "is this an SW bug or an app bug" shows a debugging methodology, not just a list of panel names.

Q14. What's the most common and costly PWA pitfall - a stale service worker serving an old JS bundle forever?

ROI: ★★★★★ Frequency: Very High

Short Answer

This is the failure mode every experienced PWA engineer has a war story about, and it's the natural convergence of everything in Section 2 and 3 going wrong at once. It happens when a fetch handler applies a cache-first strategy to the app's JS/CSS bundle using a fixed cache key or URL - /app.js, not /app.8f3ac1.js - and the activate handler never purges old cache entries because the cache name never changes between deploys. The very first time a user visits, their service worker caches whatever /app.js was at that moment, and because the URL and cache key are identical on every future deploy, the cache-first strategy finds a "hit" forever and never fetches the new bytes again - not next week, not next year, until the user manually clears site data or the browser evicts the cache under storage pressure.

What makes this especially nasty in production is that it's silent and inconsistent across your user base: new visitors get the new bundle, but existing users are frozen on whatever version they first cached, sometimes for months, with no error and no console warning - support tickets describe a bug you fixed two releases ago, and it takes someone specifically checking a user's Cache Storage in DevTools (Q13) to realize their client is running ancient code that hasn't been network-fetched since it was first installed.

The fix is the combination already covered piece by piece: build output must use content-hashed filenames (or Workbox's revisioned precache manifest) so a code change is structurally guaranteed to produce a new URL, never reuse a bare, unhashed cache key for anything cache-first, delete every cache name that isn't the current version inside activate, and - since a user could still be stuck on the old service worker itself if it never even notices the new one - make sure the app surfaces a "new version available" prompt (Q8) rather than assuming the browser's lazy update check will save you promptly. 

// BAD: cache-first on a URL that never changes, cache name that never changes
self.addEventListener("fetch", (event) => {
  if (event.request.url.endsWith("/app.js")) {
    event.respondWith(
      caches.match("/app.js").then((cached) => cached || fetch(event.request))
    );
  }
});
// Every deploy ships a new /app.js body, but the cache key never changes,
// so this SW serves the FIRST version it ever cached - indefinitely.

// GOOD: hashed filenames make the bug structurally impossible
// build output: /assets/app.8f3ac1.js  ->  next deploy: /assets/app.4d90e2.js
import { precacheAndRoute } from "workbox-precaching";
precacheAndRoute(self.__WB_MANIFEST); // each entry is revisioned by the build

self.addEventListener("activate", (event) => {
  event.waitUntil(
    caches.keys().then((keys) =>
      Promise.all(keys.filter((k) => !EXPECTED_CACHE_NAMES.includes(k)).map((k) => caches.delete(k)))
    )
  );
});

Common Mistake

Treating this as a rare edge case rather than the default outcome of the two most common shortcuts: hand-writing a cache-first fetch handler without content-hashed asset names, and never auditing what activate actually deletes. The interview-winning move is naming the fix before being asked "how would you prevent this" - content hashing plus revisioned precaching plus an activate-time purge is the standard answer, and it's exactly what Q5 and Q8 build up to.

SECTION 6 - SERVICE WORKER LIFECYCLE DEEP DIVE

Q15. What exactly triggers a "new" service worker registration, and how does the browser decide two versions of sw.js differ?

ROI: ★★★★☆ Frequency: High

Short Answer

The browser re-fetches the registered script byte-for-byte and does a straight comparison against the version it already has installed. If the bytes are identical, nothing happens at all - no install event fires, no new worker enters the lifecycle. If even a single byte differs (a changed comment, a reordered import, whitespace from a different build), it is treated as a genuinely new version and the full install/waiting/activate dance begins.

This check runs on every navigation to a page in scope (throttled to roughly once every 24 hours if the site is visited constantly), on an explicit registration.update() call, and immediately before dispatching a push or sync event. Critically, the top-level SW script itself is exempt from normal HTTP caching for this fetch - browsers ignore Cache-Control headers on it since this exact staleness bug was common in the wild. Scripts pulled in via importScripts(), however, are not automatically exempt and can be served stale from HTTP cache unless you cache-bust them (Workbox-generated files include a hash in the precache manifest for exactly this reason).

Common Mistake

Assuming a deploy alone forces an update check. If a user never navigates and the tab stays open for days, the 24-hour background check is the only thing keeping them from running arbitrarily old code - which is one more argument for calling registration.update() proactively (e.g. on window focus) rather than relying purely on the browser's default cadence.

Q16. How do you communicate with a waiting service worker, given that navigator.serviceWorker.controller only points at the active one?

ROI: ★★★☆☆ Frequency: Medium

Short Answer

navigator.serviceWorker.controller is always the currently active worker - the one actually serving fetches - never the one sitting in waiting. To talk to a waiting worker (most commonly to tell it "the user clicked update, skip waiting now") you go through the registration object directly: registration.waiting.postMessage(...). Symmetrically, the worker listens for a message event on self and can call self.skipWaiting() in response, which is the safe, user-initiated version of the pattern shown in Q8.

For a true request/response conversation rather than one-way fire-and-forget messages, wrap the message in a MessageChannel: the page creates the channel, sends one port to the worker along with the message, and the worker replies on that port directly, letting the page await a specific answer instead of listening on a shared, ambiguous global message stream. 

// Page: ask the waiting worker to skip waiting, and wait for its ack
function activateUpdate(registration) {
  return new Promise((resolve) => {
    const channel = new MessageChannel();
    channel.port1.onmessage = () => resolve();
    registration.waiting.postMessage({ type: "SKIP_WAITING" }, [channel.port2]);
  });
}

// sw.js
self.addEventListener("message", (event) => {
  if (event.data?.type === "SKIP_WAITING") {
    self.skipWaiting();
    event.ports[0]?.postMessage({ type: "ACK" });
  }
});

Interview Gold Point

Naming the controller-vs-registration.waiting distinction unprompted is a strong signal - it's a real bug people hit ("why doesn't navigator.serviceWorker.controller.postMessage reach my new worker") that only makes sense once you understand controller always tracks the active worker.

Q17. What happens to an in-flight fetch event if the browser terminates the service worker mid-request?

ROI: ★★★☆☆ Frequency: Medium

Short Answer

Service workers are aggressively spun down when idle (commonly after roughly 30 seconds with no pending work, though the exact figure is implementation-defined and browsers tune it) to save memory - there's no guaranteed persistent process. The platform's answer to "won't that kill work in progress" is the extendable events contract: as long as a handler passes its promise to event.respondWith() (fetch) or event.waitUntil() (install/activate/sync/push), the browser guarantees it will not terminate the worker until that specific promise settles, however long it takes.

The danger is anything that happens outside that contract - a stray setTimeout, a "fire and forget" fetch() call not passed to waitUntil, a variable you intended to persist in module-level worker memory between events. None of that is protected; the worker can be killed the instant the current extendable event's promise resolves, and a freshly woken worker starts from a completely clean global scope with no memory of prior events. This is why service worker code must treat every event as though the worker had never run before - no relying on module-level caches surviving between fetches.

Common Mistake

Caching a value in a plain JS variable at the top of the SW file "to avoid recomputing it every fetch," and being surprised when it resets randomly. Anything that must survive across worker restarts belongs in IndexedDB or Cache Storage, not in module state - the worker's lifetime is per-event, not per-session.

Q18. What happens if cache.addAll() fails during install - say, one asset in the list 404s?

ROI: ★★★★☆ Frequency: High

Short Answer

cache.addAll() is all-or-nothing by design: it fetches every URL, and if any single one fails (a 404, a network error, even a valid-but-non-200 response) the entire call rejects, nothing gets written to the cache, and that rejection propagates up through your waitUntil() promise. The browser then considers install itself to have failed and discards the new worker entirely - the old worker (or no worker, on a first visit) keeps running unaffected. This is actually the safe failure mode: you never end up with a half-populated app shell silently missing a critical file.

The practical risk is a single typo or a renamed asset in a hand-maintained precache list silently blocking every future deploy from ever installing, with no user-facing error - which is exactly the class of bug Workbox's build-time-generated manifest (Q5) eliminates, since the list is derived from what the build actually produced rather than typed by hand. If you must hand-roll it, log failures explicitly rather than trusting a silent promise rejection to surface itself. 

self.addEventListener("install", (event) => {
  event.waitUntil(
    caches.open(CACHE_NAME).then(async (cache) => {
      const results = await Promise.allSettled(
        APP_SHELL.map((url) => fetch(url).then((res) => {
          if (!res.ok) throw new Error(`Bad response for ${url}: ${res.status}`);
          return cache.put(url, res);
        }))
      );
      const failed = results.filter((r) => r.status === "rejected");
      if (failed.length) console.error("SW install: failed to precache", failed);
      // Decide deliberately whether a partial shell is acceptable or should still fail install.
    })
  );
});

Interview Gold Point

Framing this as "fail loudly at install time rather than silently at runtime" is the senior answer - a broken precache list should block a bad deploy from ever taking over, not ship a service worker that 404s on some asset the first time a real user needs it.

Q19. Why do service workers have no DOM access, no synchronous XHR, and no localStorage - and what does that force architecturally?

ROI: ★★★☆☆ Frequency: Medium

Short Answer

A service worker runs in ServiceWorkerGlobalScope, a worker context with no window or document - it can outlive every page that registered it, run with no page open at all (a push event can wake it with zero tabs open), and potentially control multiple tabs simultaneously, so there is no single "the DOM" it could even mean. Synchronous XHR and localStorage are banned for a sharper reason: both are blocking APIs, and a service worker that blocks is a service worker that can't service any other in-flight request on the same event loop - unacceptable for something sitting in the network path of every fetch.

Architecturally this forces a clean separation: the service worker becomes a pure, async, DOM-free network-and-cache layer, and anything that needs the DOM, a synchronous read, or user-facing state lives in the page and talks to the worker only via postMessage/MessageChannel, or via the worker enumerating open pages with self.clients.matchAll(). Storage inside the worker is limited to fully async options - Cache API and IndexedDB - which is also exactly what you want given the worker can be torn down between any two operations (Q17).

Interview Gold Point

The strongest framing: these aren't arbitrary restrictions, they're the platform enforcing that a service worker can never become a single point of janky, blocking failure sitting between every page and the network. Connecting the restriction to the "can run with zero tabs open" reality (why there's no DOM to speak of) shows real understanding, not memorized trivia.

Q20. What is the "orphaned tab" problem, and how do you detect or mitigate it?

ROI: ★★★☆☆ Frequency: Medium

Short Answer

Because a new worker waits until every tab controlled by the old one closes (Q3), a single tab a user never closes - a pinned tab, a background tab left open for weeks, a kiosk display - can keep an old service worker version "stuck" indefinitely, blocking every subsequent deploy's worker from ever activating for that user, even though newer workers keep successfully installing and piling up in the waiting state behind it.

Detection is mostly about instrumentation: track, per client, how long a worker has been in waiting and alert if it crosses a threshold (a day, a week) that's unusual for your update cadence. Mitigation options trade user experience against currency: show an increasingly insistent "please refresh" banner the longer the wait drags on, set an internal policy of calling skipWaiting() automatically once a version has been waiting past some threshold (accepting the small risk of an active tab getting new logic mid-session), or - the middle ground many production apps land on - only auto-skip-waiting for non-breaking patch releases and always prompt for anything that changes the API contract between client and server.

Common Mistake

Treating this as purely theoretical. Any product with power users who keep dozens of tabs open for days (dashboards, admin panels, always-on internal tools) will hit this in practice, and "just call skipWaiting always" trades this problem for the mid-session-version-mismatch problem from Q8 - there is no fix that isn't a trade-off, and naming that trade-off is the interview-winning move.

Q21. What's the difference between self.clients.matchAll() and self.clients.claim(), and when would you reach for matchAll in real code?

ROI: ★★★☆☆ Frequency: Medium

Short Answer

They solve different problems entirely, and confusing them is a common tell. clients.claim() is about control - called once, inside activate, it makes the newly active worker take over already-open tabs immediately instead of waiting for their next navigation. clients.matchAll() is about enumeration and communication - it returns a promise resolving to every open window/tab the worker currently controls (or, with { includeUncontrolled: true }, every client in scope regardless of control), so you can loop over them and postMessage each one.

The most common production use of matchAll is exactly the "new version available" banner from Q8: once activate finishes, broadcast a message to every open client so each tab can independently decide whether to show a refresh prompt, rather than each page having to poll the registration's state on its own. 

self.addEventListener("activate", (event) => {
  event.waitUntil(
    (async () => {
      // ...cache cleanup from Q8...
      const allClients = await self.clients.matchAll({ type: "window" });
      allClients.forEach((client) =>
        client.postMessage({ type: "SW_UPDATED", version: CACHE_VERSION })
      );
    })()
  );
});

Interview Favorite

The one-line distinction to lead with: "claim takes control, matchAll takes attendance." Following it with the update-banner use case shows you've actually wired these two APIs together in a real feature, not just memorized their signatures.

Q22. How would you test service worker lifecycle logic - install/activate handlers - without a real browser?

ROI: ★★★☆☆ Frequency: Medium

Short Answer

Faithfully mocking self, caches, and clients in a Node/jsdom environment is possible but brittle and low-value - jsdom doesn't implement the service worker global scope at all, and hand-rolled mocks of the Cache API tend to drift from real browser semantics (especially around opaque responses and partial failures). The pragmatic split most teams land on: extract every piece of decision logic - "should this URL be cache-first or network-first," "is this response cacheable" - into small, pure, dependency-free functions that live outside the event-listener boilerplate, and unit test those directly with plain Jest/Vitest, no service worker APIs involved at all.

For the actual lifecycle wiring - does install really populate the cache, does activate really purge old ones, does the whole thing really produce a 200 offline - that's tested with real browser automation (Playwright has first-class support for registering a service worker, waiting for it to activate, going offline via page.context().setOffline(true), and asserting on the resulting network behavior) rather than mocked. Treat the SW file itself as a thin integration layer over logic you've already unit tested in isolation. 

// sw-logic.js - pure, testable, no service worker globals
export function pickStrategy(url) {
  if (url.pathname.startsWith("/api/")) return "network-first";
  if (/\.(js|css|woff2?)$/.test(url.pathname)) return "cache-first";
  return "stale-while-revalidate";
}

// sw-logic.test.js - plain Jest, zero SW mocking required
test("routes API calls to network-first", () => {
  expect(pickStrategy(new URL("https://x.com/api/orders"))).toBe("network-first");
});

// e2e.spec.ts - Playwright, the real thing
test("shell renders offline after first visit", async ({ page, context }) => {
  await page.goto("/");
  await page.waitForFunction(() => navigator.serviceWorker.controller !== null);
  await context.setOffline(true);
  await page.reload();
  await expect(page.locator("#app-shell")).toBeVisible();
});

Interview Gold Point

Naming the split explicitly - pure decision logic gets fast unit tests, actual browser behavior gets real Playwright automation - shows you understand why mocking self.caches by hand is a trap most teams eventually regret, rather than proposing it as the default approach.

SECTION 7 - CACHING STRATEGIES DEEP DIVE

Q23. How do you implement network-first with a timeout, falling back to cache if the network is too slow rather than only if it fails outright?

ROI: ★★★★☆ Frequency: High

Short Answer

Plain network-first only falls back to cache when the network request actually rejects - but a request that's technically "in flight" on a bad connection for 15 seconds is, from the user's perspective, just as broken as one that failed outright. The fix is racing the network fetch against a timer with Promise.race(): if the timer wins, serve from cache immediately (and let the slow network response, if it eventually arrives, still update the cache for next time); if the network wins, serve it and cache it as usual.

Workbox implements exactly this as a built-in option (networkTimeoutSeconds on NetworkFirst), which is the reason to prefer it over hand-rolling: the hand-rolled version below is correct but doesn't handle every edge case Workbox's does, like ensuring the late network response doesn't throw an unhandled rejection after the race has already resolved. 

async function networkFirstWithTimeout(request, cacheName, timeoutMs = 3000) {
  const cache = await caches.open(cacheName);
  const networkPromise = fetch(request).then((res) => {
    if (res.ok) cache.put(request, res.clone());
    return res;
  });
  const timeoutPromise = new Promise((resolve) =>
    setTimeout(() => resolve(undefined), timeoutMs)
  );
  const winner = await Promise.race([networkPromise, timeoutPromise]);
  if (winner) return winner;
  const cached = await cache.match(request);
  return cached || networkPromise; // no cache either - just wait it out
}

Interview Gold Point

Volunteering that Workbox's networkTimeoutSeconds already implements this is the strongest answer - it shows you know the pattern well enough to also know you shouldn't hand-roll it in production, only in an interview whiteboard.

Q24. What is an "opaque" response, and why is caching one blindly dangerous?

ROI: ★★★☆☆ Frequency: Medium

Short Answer

A request made in no-cors mode to a cross-origin server - which is what <img>, <script>, and similar tags issue by default, and what a service worker's fetch handler receives verbatim - returns an "opaque" response: the browser deliberately hides its status code, headers, and body from JavaScript as a security measure, so a script on your origin can't probe a response it shouldn't be able to read. From the Cache API's point of view, an opaque response looks exactly like a successful one (response.type === "opaque", but response.status reads as 0 and is unusable for your own status checks).

The danger: if that cross-origin request actually failed - a 404, a 500, a CDN outage - your code has no way to tell, because the real status is hidden. A naive cache-first handler will happily cache and forever replay that failed response as if it were the real asset. The mitigation is either avoiding no-cors for anything you cache (request in cors mode if the origin supports CORS, so you get a real, inspectable response) or accepting the risk deliberately and pairing it with a size/count limit so a bad opaque entry doesn't live forever.

Common Mistake

Caching every image request indiscriminately, including ones served cross-origin without CORS headers, and being unable to explain why a broken hotlinked image is being served from cache forever. This is one of the more subtle production PWA bugs precisely because nothing in the console flags it as an error.

Q25. How does Workbox's CacheableResponsePlugin prevent you from caching error responses?

ROI: ★★★☆☆ Frequency: Medium

Short Answer

By default, a naive cache-first or cache-then-network implementation will cache whatever fetch() resolves to, including a 404 or 500 - a fetch only rejects on a true network failure, not on an HTTP error status, so "the promise resolved" is not the same thing as "the response is good." CacheableResponsePlugin is a Workbox strategy plugin that inserts an explicit gate before anything gets written to the cache: you configure a set of acceptable status codes (by default [0, 200], where 0 deliberately allows opaque responses through since they can't be inspected) and it skips the cache.put() entirely for anything that doesn't match. 

import { registerRoute } from "workbox-routing";
import { CacheFirst } from "workbox-strategies";
import { CacheableResponsePlugin } from "workbox-cacheable-response";

registerRoute(
  ({ request }) => request.destination === "image",
  new CacheFirst({
    cacheName: "images",
    plugins: [
      new CacheableResponsePlugin({ statuses: [0, 200] }), // reject 404s/500s from being cached
    ],
  })
);

Interview Gold Point

Connecting this directly to Q24's opaque-response problem shows a full mental model: statuses: [0, 200] is explicitly allowing opaque responses through despite the risk, which is a deliberate, named trade-off Workbox makes rather than an oversight - and you should be able to say so.

Q26. How is Cache Storage partitioned per origin, and why can't one site read another's cache?

ROI: ★★★☆☆ Frequency: Medium

Short Answer

Cache Storage, like every other client-side storage API (IndexedDB, localStorage, cookies to a lesser extent), is scoped strictly to the origin (scheme + host + port) that created it - caches.open("app-shell") called from https://a.com and the identically-named call from https://b.com reference two entirely separate storage buckets with no cross-visibility whatsoever, enforced by the browser at the storage-partition level, not by any convention your code follows. This is a straightforward extension of the same-origin policy and exists for the obvious reason: without it, any site could read or poison another site's cached responses.

The practical corollary worth knowing: a service worker's scope (Q11) further partitions things within an origin by path, but that's a separate, additional restriction layered on top of the origin boundary, not a replacement for it - two different paths on the same origin can still read each other's Cache Storage entries by name if their respective service workers choose to, since Cache Storage itself isn't scope-restricted, only the service worker's ability to intercept requests is.

Common Mistake

Conflating "scope" (which controls which requests a service worker can intercept) with cache isolation (which is enforced at the origin level and has nothing to do with service worker scope at all). They're solving different problems and it's a common mix-up under interview pressure.

Q27. How would you design caching for a paginated API list endpoint where individual entries can be invalidated?

ROI: ★★★☆☆ Frequency: Medium

Short Answer

The Cache API stores whole request/response pairs keyed by URL, which is a poor match for "invalidate one entry inside a list response" - you'd have to re-fetch and re-cache the entire page just to reflect one changed item. The practical pattern splits responsibilities: cache the raw list responses in the Cache API keyed by their exact request URL (page number, filters, sort - all part of the cache key naturally, since they're part of the URL), for fast repeat-navigation, but treat that cache as disposable and short-lived (a stale-while-revalidate with a short max age) rather than authoritative.

For the "one entry changed, don't invalidate the whole page" requirement, the API cache alone isn't the right tool - that's what IndexedDB-backed normalized storage is for (Q56-Q58): store individual entities by ID in one object store, and have the UI compose list views from that normalized data plus a separately cached "which IDs are on which page" mapping, so an update to one entity is reflected everywhere it's rendered without touching the raw list response cache at all.

Interview Gold Point

The senior insight: the Cache API is a request/response replay cache, not a database, and reaching for entity-level invalidation inside it is fighting the tool. Recognizing when to escalate from "cache the HTTP response" to "normalize the data in IndexedDB" is exactly the judgment call this question is probing for.

Q28. What is "cache-then-network," and how does it differ from stale-while-revalidate?

ROI: ★★★☆☆ Frequency: Medium

Short Answer

Both strategies show the user cached content immediately while checking the network in the background, but they differ in who's in control of the "update." Stale-while-revalidate is entirely a service-worker-level concern: the SW serves the cache, kicks off a background fetch, and silently updates the cache for the next request - the current page never learns the fresh data even arrived. Cache-then-network is a page-level pattern (popularized by Jake Archibald) where the page itself issues two requests - one to the cache, one to the network - renders the cache result the instant it resolves, and then re-renders again if and when the network result comes back different, so the current view updates live rather than only the next visit benefiting.

In practice, cache-then-network needs your fetch layer or a library like TanStack Query to support "resolve with cache immediately, then patch in the fresher result" as a first-class idea, whereas stale-while-revalidate needs nothing from the page at all - it's invisible to application code. Choose cache-then-network when the current view genuinely benefits from updating live (a chat thread, a live dashboard); stale-while-revalidate is the simpler default for everything else.

Common Mistake

Using the two terms interchangeably. They look similar on a diagram but live at different layers of the stack, and a candidate who can't separate "service worker updates the cache for later" from "page re-renders live when fresher data lands" is missing a real distinction interviewers use to gauge depth.

Q29. How do you cap a growing cache's size, both hand-rolled and with Workbox?

ROI: ★★★★☆ Frequency: High

Short Answer

An unbounded runtime cache - images, API responses, anything cached as users browse rather than precached once - grows forever by default, since nothing ever removes an entry unless you tell it to. Left unmanaged, this eventually runs into the browser's storage quota (typically some percentage of free disk, enforced per-origin) and the browser starts evicting your cache entries itself, non-deterministically, which is worse than controlling it yourself.

Hand-rolled: track insertion order (or age) yourself, most simply via a "the Nth-oldest key gets deleted whenever you add a new one past the limit" LRU-ish loop. With Workbox, this is a one-line ExpirationPlugin config supporting both maxEntries (a hard count cap, oldest evicted first) and maxAgeSeconds (evict anything older than a TTL) together. 

// Hand-rolled: cap a cache at N entries, oldest-first
async function trimCache(cacheName, maxEntries) {
  const cache = await caches.open(cacheName);
  const keys = await cache.keys();
  if (keys.length > maxEntries) {
    await cache.delete(keys[0]); // Cache Storage preserves insertion order
    await trimCache(cacheName, maxEntries); // recurse until under the cap
  }
}

// Workbox: the same policy, declaratively
import { ExpirationPlugin } from "workbox-expiration";
new ExpirationPlugin({ maxEntries: 50, maxAgeSeconds: 7 * 24 * 60 * 60 });

Interview Gold Point

Mentioning that the browser will start silently evicting your cache under storage pressure if you don't manage size yourself reframes this from "nice to have" to "you will hit this in production eventually" - and naming ExpirationPlugin's dual count+age cap shows you know the real tool, not just the concept.

Q30. How do you decide a caching strategy for a GraphQL endpoint, where every request is a POST to the same URL?

ROI: ★★★☆☆ Frequency: Medium

Short Answer

Every strategy discussed so far implicitly assumes the request URL is a meaningful cache key - which is exactly what breaks with GraphQL, since every query and mutation is typically a POST to the same /graphql endpoint, and the Cache API only keys on the request (URL + method by default, body is ignored). A cache-first or network-first strategy applied naively to /graphql either caches nothing useful (every distinct query looks identical to the cache) or, worse, serves one query's cached response for a completely different query.

The fix is constructing a cache key manually from the meaningful parts of the request - typically the operation name plus a stable serialization of the variables - and using cache.put(new Request(customKey), response) / cache.match(customKey) instead of the raw request object. In practice, most teams skip hand-rolling this in the service worker at all and instead lean on the GraphQL client's own cache (Apollo's normalized cache, or persisting Apollo/urql's cache to IndexedDB) since it already understands query shape and variables natively - reserving the service worker for what it's actually good at: precached static assets and simple GET-based REST fallbacks.

Interview Gold Point

Recognizing that this is fundamentally a "wrong tool" situation - the service worker's request-URL-keyed cache model doesn't map cleanly onto POST-based GraphQL - and that the correct answer is usually "let the GraphQL client's own cache handle this, persisted to IndexedDB" rather than forcing a Cache API solution, is exactly the kind of judgment senior interviewers are listening for.

SECTION 8 - WEB APP MANIFEST DEEP DIVE

Q31. Beyond "manifest + service worker + HTTPS," what are the exact installability criteria Chromium checks today?

ROI: ★★★★☆ Frequency: High

Short Answer

Chromium's actual checklist is more specific than the folk version most people quote. It requires: the manifest is reachable and parses as valid JSON with, at minimum, name or short_name, icons including a 192px and a 512px entry, and a start_url that resolves; a registered service worker with a fetch event handler that produces a real response (historically this meant "responds while offline," relaxed over time but still checked in spirit); the site served over HTTPS (or localhost); and, for the automatic install prompt specifically (as opposed to a manual "Install app" menu entry, which has looser requirements), some minimum user engagement with the site - Chrome doesn't disclose the exact heuristic, but it's understood to require more than a single page load.

A subtlety worth naming: meeting the criteria makes the browser capable of offering install, it doesn't guarantee a beforeinstallprompt event fires automatically - Chrome has, over versions, moved toward requiring more deliberate user engagement before surfacing the automatic prompt, specifically to cut down on low-quality "please install me" popups appearing on first visit.

Common Mistake

Reciting only "manifest + service worker + HTTPS" and stopping there. Naming the icon-size specifics, the engagement heuristic, and that the automatic prompt and the manual install affordance have different bars is what separates "read the MDN page once" from "actually debugged why the prompt wasn't firing."

Q32. Explain maskable icons in depth - what's the "safe zone," and why do non-maskable icons get clipped?

ROI: ★★★☆☆ Frequency: Medium

Short Answer

Android's adaptive icon system lets the OS (or a custom launcher/theme) apply any mask shape it wants to a home-screen icon - circle, squircle, teardrop, rounded square - which means your icon's actual visible silhouette is decided at runtime by the device, not by you. A regular icon designed edge-to-edge (a square logo filling the full 512x512 canvas) gets its corners and edges cropped away arbitrarily depending on the mask, which is why square icons with important content near the edges look broken on many Android phones.

A maskable icon, declared with "purpose": "maskable" in the manifest's icon entry, tells the OS "this icon is designed to be safely cropped to any shape" - which only works if you actually designed it that way, keeping all meaningful content inside the safe zone: a centered circle covering roughly 80% of the icon's width/height (a widely used rule of thumb is a 40% radius from center on a 512px icon, leaving roughly 10% padding on each edge as sacrificial background that different masks may or may not show). Tools like Maskable.io let you preview your icon under several real mask shapes before shipping it. 

{
  "icons": [
    { "src": "/icons/icon-any.png", "sizes": "512x512", "type": "image/png", "purpose": "any" },
    { "src": "/icons/icon-maskable.png", "sizes": "512x512", "type": "image/png", "purpose": "maskable" }
  ]
}

Interview Gold Point

Naming the ~80%-safe-zone rule of thumb and a real tool (Maskable.io) shows this was actually implemented, not just read about - a common gap is shipping one icon marked "any maskable" that was never actually designed with a safe zone, which looks fine on iOS and gets clipped everywhere it's masked on Android.

Q33. What's the difference between display: standalone, minimal-ui, fullscreen, and the newer display_override?

ROI: ★★★☆☆ Frequency: Medium

Short Answer

These control how much browser UI survives once the app is launched as installed. browser is just a normal tab. standalone hides the address bar and browser chrome but keeps the OS status bar and a minimal system back/close affordance - the most common choice, since it reads as "app-like" without losing basic navigation cues. minimal-ui is a middle ground (a thin back/forward/reload bar remains) that most mobile browsers actually just treat as standalone in practice - it's rarely worth targeting deliberately. fullscreen hides everything, including the OS status bar, which is appropriate for games or media apps but disorienting for a typical content app since there's no visible way back to the OS without a gesture.

display_override is a newer array field that lets you request more specific modes - window-controls-overlay (draw your own UI into the title bar area on desktop, common for productivity PWAs that want a native-window feel) being the most notable - with the browser trying each value in order and falling back to the plain display field if none are supported. It exists because display alone couldn't express these newer, more specific modes without breaking older browsers that don't understand them.

Common Mistake

Reaching for fullscreen on a typical content app "to look more native." Without a deliberate in-app way back to normal browser UI, hiding the status bar entirely just makes the app feel like it's trapped - standalone is almost always the right default.

Q34. How do scope and start_url interact, and what happens if start_url falls outside scope?

ROI: ★★★☆☆ Frequency: Medium

Short Answer

scope defines the set of URLs the browser considers "inside" the installed app - any navigation within scope stays in the standalone app window, while a link that navigates outside scope typically pops out into a regular browser tab (the exact behavior is display-mode and browser dependent, but the intent is consistent). start_url is simply what opens when the app is launched from the home screen icon.

The manifest spec requires start_url to be within scope (scope defaults to the manifest's own directory if unset, and browsers will reject or auto-correct a manifest where start_url doesn't fall under it). Practically this matters most when start_url includes query params for analytics attribution (/?source=pwa) - that's still "within scope" as long as scope is the path prefix, not an exact string match, so query strings never break the containment check.

Common Mistake

Setting scope to a narrow subpath (say, /app/) while leaving start_url pointing at the site root /. Browsers will either reject the manifest outright or silently widen the effective scope to include start_url, producing behavior that doesn't match what you intended - always keep the two consistent deliberately.

Q35. What are manifest shortcuts, and how do they work?

shortcuts is a manifest array that lets an installed PWA expose jump-list-style actions directly from the OS icon - right-click on desktop, long-press on Android - the same way native apps show "New email," "New event," etc. Each entry names a label, a URL to open, and optionally its own icon; the OS renders these without your app needing to be running at all.

This is a small, low-frequency feature, but naming a concrete use case (jumping straight to "create new X" from the icon, skipping the app's normal landing page) shows practical familiarity rather than reciting a spec field nobody's actually used.

Q36. How does share_target let a PWA receive shared content from other apps?

ROI: ★★☆☆☆ Frequency: Low-Medium

Short Answer

Normally, sharing is one-directional from your PWA outward (via the Web Share API, navigator.share()). share_target in the manifest registers your installed PWA as a destination in the OS share sheet, so a user in a photo app, browser, or another app can choose your PWA as the target when sharing text, a URL, or files - the OS then navigates to (or POSTs to) the URL you declared, with the shared content attached as query params or a multipart form body. 

{

    "method": "POST",
    "enctype": "multipart/form-data",
    "params": {
      "title": "title",
      "text": "text",
      "url": "url",
      "files": [{ "name": "media", "accept": ["image/*"] }]

Forgetting that the receiving URL (/share-handler) must actually be handled - typically by a service worker's fetch handler that intercepts the POST, stores or forwards the payload, then redirects to a normal in-app URL, since a bare server-rendered response isn't how most SPAs want to handle this.

Q37. How does iOS Safari's manifest support differ from Android Chrome's, and what fallbacks do you still need?

ROI: ★★★★☆ Frequency: High

Short Answer

iOS Safari has historically implemented a meaningfully smaller subset of the manifest spec, and while support has improved over recent iOS versions, a defensive PWA still ships the older Apple-specific meta tags alongside the manifest rather than trusting it alone. Practically: apple-touch-icon link tags are still the most reliable way to guarantee a home-screen icon on iOS (some iOS versions ignore the manifest's icons array for the actual home-screen image), apple-mobile-web-app-capable and apple-mobile-web-app-status-bar-style control standalone-mode and status-bar appearance the way display and theme_color do elsewhere, and apple-mobile-web-app-title sets the home-screen label independently of short_name.

There is also no beforeinstallprompt event on iOS at all - install is entirely manual, via the Share sheet's "Add to Home Screen," which means any "Install app" button UX pattern (Q2) needs an iOS-specific fallback that shows instructions instead of triggering a prompt, since there is no programmatic install trigger to call. 

<link rel="manifest" href="/manifest.json">
<link rel="apple-touch-icon" href="/icons/icon-180.png">
<meta name="apple-mobile-web-app-capable" content="yes">
<meta name="apple-mobile-web-app-status-bar-style" content="black-translucent">
<meta name="apple-mobile-web-app-title" content="Acme">

Interview Gold Point

Naming that iOS has no beforeinstallprompt equivalent, so your custom "Install" UI needs a detect-iOS-and-show-instructions branch instead of silently doing nothing, is the detail that shows you've actually shipped this to iOS users, not just Android/desktop Chrome.

Q38. The manifest is a static JSON file fetched once - how do you theme it for light/dark mode dynamically?

ROI: ★★★☆☆ Frequency: Medium

Short Answer

You can't truly change a live manifest's theme_color/background_color per system theme after install - the manifest is read at install time and its splash-screen/theme values are effectively baked in for that installation. The two practical workarounds address different parts of the problem. First, the in-browser (non-installed) address-bar theming can respond to live theme changes via a separate, dynamic mechanism: multiple <meta name="theme-color"> tags with media attributes matching prefers-color-scheme, which the browser re-evaluates live and which is independent of the manifest entirely.

Second, for the actually-installed splash screen and OS chrome, since the manifest's colors are fixed at install time, most production PWAs simply pick a neutral, theme-agnostic background_color/theme_color (often close to the app's brand color rather than pure white or pure black) that reads acceptably in both modes, and let the in-app UI do the real light/dark theming once it's actually rendered - accepting that the split-second splash screen won't perfectly match a system-dark-mode user's expectation. 

<meta name="theme-color" content="#ffffff" media="(prefers-color-scheme: light)">
<meta name="theme-color" content="#121212" media="(prefers-color-scheme: dark)">

Common Mistake

Trying to solve this by regenerating and re-fetching manifest.json dynamically based on system theme. Browsers cache manifest data at install time and largely don't re-read it live for an already-installed app, so this approach quietly does nothing for existing installs - the dynamic meta[name=theme-color] trick only helps the in-browser, not-yet-installed experience.

SECTION 9 - PUSH NOTIFICATIONS

Q39. Walk through the complete push notification flow end to end, from subscribe to display.

ROI: ★★★★☆ Frequency: High

Short Answer

Five actors are involved, and naming all of them precisely is what separates a strong answer: your page, the browser's push service (run by the browser vendor - Google/Mozilla/Apple, not by you), your backend, the service worker, and the OS notification tray. First, the page asks the user for notification permission and, once granted, calls registration.pushManager.subscribe() with your VAPID public key; the browser talks to its push service and returns a subscription object containing an endpoint URL unique to that browser/device/user and a pair of encryption keys. Second, your page sends that subscription object to your backend, which stores it against the logged-in user.

Third - potentially days or weeks later, and even with zero tabs open - your server, using a library like web-push, encrypts a payload with the subscription's keys and POSTs it to the subscription's endpoint, signing the request with your VAPID private key so the push service can verify it's really you. Fourth, the browser vendor's push service delivers that message to the specific browser instance, which wakes the service worker (even if it was fully unloaded) and fires a push event. Fifth, the service worker's handler calls self.registration.showNotification(), which is the only way to actually put something in the OS notification tray from a worker with no page open.

Interview Gold Point

The detail that impresses: your server never talks to the browser directly - it talks to the browser vendor's push infrastructure, which is why push works with the site fully closed. Missing this and describing push as "the site sends a notification" is the most common shallow-answer tell.

Q40. What are VAPID keys, and why did they replace the older sender-ID model?

ROI: ★★★☆☆ Frequency: Medium

Short Answer

VAPID (Voluntary Application Server Identification) is a public/private key pair your server generates once and keeps for the life of the app. The public key is handed to pushManager.subscribe() so the browser's push service knows which application server is allowed to send to a given subscription; the private key signs every push request your server sends, letting the push service verify authenticity without you needing a vendor-specific account or API key per browser (Chrome, Firefox, etc. each used to require their own proprietary sender credentials - Chrome's old model required a Firebase/GCM sender ID tied to a Google account).

The practical benefit: one VAPID key pair works across every browser that implements the standard Push API, so you generate it once, store the private half securely on your server, and never touch vendor-specific push consoles again - a meaningful simplification over the pre-VAPID era. 

// One-time key generation (e.g. via the web-push npm package)
// npx web-push generate-vapid-keys

// Subscribing from the page
async function subscribe(registration) {
  return registration.pushManager.subscribe({
    userVisibleOnly: true, // required: every push must show a visible notification
    applicationServerKey: VAPID_PUBLIC_KEY, // base64url-encoded
  });
}

Common Mistake

Forgetting userVisibleOnly: true - Chrome requires it and will reject the subscription without it, since "silent push with no visible notification" was deemed a spam/tracking risk and is disallowed by policy on most platforms.

Q41. How do you handle a push subscription expiring or changing?

ROI: ★★★☆☆ Frequency: Medium

Short Answer

A subscription can become invalid for several reasons: the user cleared site data, the browser rotated the underlying push endpoint for privacy reasons, or - most commonly in practice - your server sent a push and got back a 404/410 from the push service, meaning that endpoint is dead. There's also a pushsubscriptionchange event some browsers fire on the service worker when a subscription is proactively renewed by the browser itself, which you should handle by immediately re-subscribing and sending the new subscription object to your backend.

The other half of the fix lives server-side: treat a 404/410 response from the push service as a signal to delete that stored subscription for the user rather than retrying it forever, since retrying a dead endpoint just wastes cycles and, at volume, can get your server flagged by the push service. 

self.addEventListener("pushsubscriptionchange", (event) => {
  event.waitUntil(
    self.registration.pushManager
      .subscribe({ userVisibleOnly: true, applicationServerKey: VAPID_PUBLIC_KEY })
      .then((sub) => fetch("/api/push/resubscribe", {
        method: "POST",
        body: JSON.stringify(sub),
        headers: { "Content-Type": "application/json" },
      }))
  );
});

Interview Gold Point

Naming that a 404/410 from the push service means "stop sending to this endpoint, delete the row" rather than "retry with backoff" shows you understand push subscriptions have a real, finite lifetime you have to actively clean up, not treat as permanent once stored.

Q42. What's the payload size limit for a push message, and how do you handle richer notification content?

ROI: ★★☆☆☆ Frequency: Low-Medium

Short Answer

The push payload itself is deliberately small - the spec caps encrypted payloads at 4KB, intended for a title, a short body, and small pieces of routing metadata, not for images or long content. If you need a richer notification (an image thumbnail, a longer body fetched at display time), the standard pattern is to send a minimal payload containing just enough to identify what happened (an ID, a type), and have the service worker's push handler make its own network request to fetch the fuller content before calling showNotification() - all still wrapped in event.waitUntil() so the worker isn't torn down mid-fetch. 

self.addEventListener("push", (event) => {
  const { notificationId } = event.data.json(); // tiny payload: just an ID
  event.waitUntil(
    fetch(`/api/notifications/${notificationId}`)
      .then((res) => res.json())
      .then((full) =>
        self.registration.showNotification(full.title, {
          body: full.body,
          image: full.imageUrl, // richer content fetched on demand
          icon: "/icons/icon-192.png",
        })
      )
  );
});

Common Mistake

Trying to cram a full rich payload - images, long text - directly into the encrypted push message and hitting the 4KB ceiling in production. Fetch-on-display is the standard workaround, and it also has the side benefit of always showing fresh content even if the push itself was delayed.

Q43. How do you design notification permission UX to avoid users permanently denying it?

ROI: ★★★★☆ Frequency: High

Short Answer

Once a user denies the browser's native notification permission prompt, most browsers will never show that prompt again for your origin - there's no programmatic way to re-ask, only a manual path through browser site settings that almost no user will ever find. This makes the timing and framing of the first (and only realistic) ask critical, unlike most permissions where a retry is cheap.

The established best practice is a two-step ask: first show your own UI - a banner, a modal, an inline prompt - explaining specifically what the user gets ("get notified when your order ships") and asking them to opt in there; only call the real Notification.requestPermission() after they've clicked "yes" on your own prompt. This filters out users who would reflexively dismiss a permission dialog they don't understand yet, and means a "no" on your own UI costs you nothing (you can ask again later), while the one-shot browser prompt is only spent on users who've already indicated real interest.

Interview Gold Point

The concrete, memorable framing: "you get infinite chances to ask your own UI, but effectively one chance to trigger the real browser prompt - spend it deliberately." This is one of the most commonly cited PWA UX best practices and interviewers listen for it explicitly.

Q44. How do you target push notifications to specific users or segments from the backend?

ROI: ★★★☆☆ Frequency: Medium

Short Answer

Targeting is entirely a backend data-modeling concern - the Push API itself has no concept of "segments," only individual subscription endpoints. The standard shape: a push_subscriptions table/collection storing one row per subscription object (endpoint + keys), foreign-keyed to a user ID, with the understanding that one user can have multiple active subscriptions (one per browser/device they've enabled notifications on). Sending "to a user" means fetching all their subscription rows and sending the same payload to each endpoint; sending "to a segment" means running whatever query defines that segment (users who abandoned a cart, users in a region) and fanning out sends across all matching users' subscriptions, typically via a queue/worker so a large segment doesn't block a web request. 

async function notifyUser(userId, payload) {
  const subs = await db.pushSubscriptions.findAllByUser(userId);
  await Promise.allSettled(
    subs.map((sub) =>
      webpush.sendNotification(sub, JSON.stringify(payload)).catch((err) => {
        if (err.statusCode === 404 || err.statusCode === 410) {
          return db.pushSubscriptions.delete(sub.id); // dead endpoint, per Q41
        }
        throw err;
      })
    )
  );
}

Common Mistake

Storing only one subscription per user and overwriting it on every new device/browser. A user with a phone and a laptop both opted in should get notified on both - modeling it as one-to-many from the start avoids a painful migration later.

Q45. What happens if the service worker's push handler throws, or never calls showNotification?

ROI: ★★★☆☆ Frequency: Medium

Short Answer

Because userVisibleOnly: true is required at subscribe time (Q40), Chrome and other Chromium browsers actively enforce that promise at runtime: if a push event's handler resolves without having called showNotification() at least once, the browser shows its own generic fallback notification (something like "This site has been updated in the background") on your behalf, specifically to prevent silent, invisible push being used for tracking. Repeatedly failing to show a real notification can also affect the site's standing with the browser's push/notification quality heuristics over time.

If the handler throws an unhandled error before ever calling showNotification, the same fallback-notification behavior applies - the browser doesn't distinguish "you chose not to show one" from "your code crashed," it just enforces the visible-notification contract either way. This is a strong argument for wrapping push handler logic in a try/catch that guarantees a fallback notification of your own design, so an error at least surfaces a message you control rather than the browser's generic one. 

self.addEventListener("push", (event) => {
  event.waitUntil(
    handlePush(event).catch(() =>
      self.registration.showNotification("Update available", { body: "Open the app to see what's new." })
    )
  );
});

Interview Gold Point

Naming that this enforcement exists specifically to prevent silent tracking-style push, and that a crashing handler is treated identically to a handler that deliberately shows nothing, demonstrates you understand the policy reasoning, not just the API surface.

Q46. How do you test push notifications locally without a real push service round trip?

ROI: ★★☆☆☆ Frequency: Low-Medium

Short Answer

The full round trip (backend → real push service → device) is slow and awkward to iterate on, so most of the actual notification-display logic is tested by skipping straight to the part that matters: the service worker's push event handler. Chrome DevTools' Application → Service Workers panel has a "Push" button that dispatches a synthetic push event directly at your worker with a payload you type in, with no real backend or push service involved at all - this is the fastest loop for iterating on notification content/actions/click handling.

For testing the server-side send path (VAPID signing, payload encryption, handling 404/410 responses) without spamming a real device, the web-push library works against any real subscription object you generate once in a throwaway browser tab and paste into a test script - there's no sandbox/mock push service, so this part is usually tested against the real infrastructure but with a disposable test subscription rather than production user data.

Common Mistake

Not realizing DevTools can synthesize a push event directly and instead standing up a full backend-to-device round trip for every iteration on notification copy or click behavior - a needlessly slow feedback loop for something DevTools solves in one click.

SECTION 10 - BACKGROUND SYNC & PERIODIC BACKGROUND SYNC

Q47. How does one-off Background Sync actually decide that "connectivity has returned"?

ROI: ★★★☆☆ Frequency: Medium

Short Answer

When a page calls registration.sync.register("tag"), the browser records that a sync is pending for that tag and takes over deciding when to fire it - your code doesn't control the timing directly. The browser combines its own network-state signals (the OS reporting an active connection, successful low-level connectivity probes) with heuristics about whether firing now is actually likely to succeed, rather than naively trusting navigator.onLine alone (which, as covered in Q6, is not a reliable success signal on its own). Once the browser's heuristic decides connectivity is probably real, it dispatches a sync event on the service worker, and your handler is responsible for actually retrying the queued work and resolving (or rejecting, which tells the browser to try again later with backoff) the promise passed to event.waitUntil().

Interview Gold Point

The key nuance: your code registers intent, the browser owns the scheduling decision. This is deliberately different from a simple window.addEventListener("online", retry) approach, which fires immediately on a flaky signal and doesn't survive the tab being closed - Background Sync is designed to work even with zero tabs open.

Q48. What is Periodic Background Sync, and why is its support even narrower than one-off Background Sync?

ROI: ★★☆☆☆ Frequency: Low-Medium

Short Answer

One-off Background Sync fires once, tied to a specific failed action waiting to be retried. Periodic Background Sync is a different, heavier-weight API intended for apps that want to refresh content in the background on a recurring interval (a news app pre-fetching the next batch of articles, a weather app updating its cache) even while closed - registered with a minimum interval, though the browser decides the actual cadence based on engagement, battery, and network conditions, and can skip cycles freely.

Support is meaningfully narrower than one-off sync: it's Chromium-only, and further gated behind the PWA actually being installed plus meeting an engagement heuristic (Chrome specifically requires a "high site engagement score," intended to prevent every random tab from registering background wake-ups). Safari and Firefox implement neither one-off nor periodic sync as of this writing, so any reliance on either needs a full fallback path, not just a lesser one. 

// Registering (only after checking support and permission)
async function registerPeriodicSync(registration) {
  const status = await navigator.permissions.query({ name: "periodic-background-sync" });
  if (status.state === "granted") {
    await registration.periodicSync.register("refresh-feed", { minInterval: 24 * 60 * 60 * 1000 });
  }
}

self.addEventListener("periodicsync", (event) => {
  if (event.tag === "refresh-feed") event.waitUntil(refreshFeedCache());
});

Common Mistake

Confusing the two APIs' purposes - reaching for Periodic Background Sync to retry a single failed POST (that's one-off sync's job), or reaching for one-off sync to "keep content fresh in the background" (that's periodic sync's job, and one-off sync gives no such recurring guarantee).

Q49. How do you build a fallback for Background Sync on browsers where the API doesn't exist at all?

ROI: ★★★★☆ Frequency: High

Short Answer

Feature-detect first ("sync" in registration), and when it's unavailable, replicate the essential behavior at the application layer instead of the platform layer: persist failed requests to IndexedDB yourself, and retry them from multiple triggers you can rely on cross-browser - the online window event firing (best-effort, not authoritative per Q6, but useful as a hint to try), the app regaining focus/visibility, and a periodic in-page timer while the app happens to be open. The key mental shift: without native Background Sync, you lose the "retry even with the tab fully closed" guarantee - the fallback can only retry while the page is at least loaded somewhere, which is a real capability gap, not just a syntax difference, and should be communicated honestly rather than papered over. 

const hasBackgroundSync = "SyncManager" in window;

async function queueFailedRequest(request) {
  await db.put("outbox", { url: request.url, body: await request.text(), createdAt: Date.now() });
  if (hasBackgroundSync) {
    const registration = await navigator.serviceWorker.ready;
    await registration.sync.register("flush-outbox");
  }
  // Fallback path: retry opportunistically while the app happens to be open.
  window.addEventListener("online", flushOutbox, { once: true });
  document.addEventListener("visibilitychange", () => {
    if (document.visibilityState === "visible") flushOutbox();
  });
}

Interview Gold Point

Being upfront that the fallback is strictly weaker - it cannot retry with the app fully closed the way native Background Sync can on Chromium - shows honest technical judgment rather than implying the fallback is an equivalent substitute.

Q50. How would you design a sync queue that preserves ordering - e.g., a "create" must apply before its later "update"?

ROI: ★★★★☆ Frequency: High

Short Answer

Background Sync (and any hand-rolled fallback) gives you "eventually retried," not "retried in order" for free - if you queue several independent mutations and let them fire in parallel, a later update can race ahead of the create it depends on and fail against a resource that doesn't exist yet server-side. The fix is modeling the queue as an ordered log, not a bag of independent jobs: store each entry with a monotonically increasing sequence number (an auto-incrementing IndexedDB key works well) and a reference to what it logically depends on, then process strictly sequentially - awaiting each request's real success before dequeuing and starting the next - rather than firing them all with Promise.all.

For truly related operations (an update to an entity that doesn't exist yet locally either), an even simpler pattern is coalescing: rather than queuing "create" then "update" as two network operations, merge them into a single queued "create-with-final-state" entry while offline, so there's only ever one request to replay and no ordering problem to solve at all. 

async function flushOutboxInOrder() {
  const entries = await db.getAllSorted("outbox", "sequence");
  for (const entry of entries) {
    try {
      await fetch(entry.url, { method: entry.method, body: entry.body });
      await db.delete("outbox", entry.id); // only dequeue on confirmed success
    } catch {
      break; // stop here - do NOT skip ahead and risk out-of-order application
    }
  }
}

Interview Gold Point

Naming coalescing ("merge create+update into one request while still offline") as an alternative to strict sequential replay shows you'd rather design the ordering problem away entirely than build careful-but-fragile sequencing logic to survive it.

Q51. What battery/data-usage constraints do browsers impose on background sync, and why?

ROI: ★★☆☆☆ Frequency: Low-Medium

Short Answer

Because both one-off and periodic sync can wake a service worker with zero user-visible activity, browsers deliberately throttle them to prevent PWAs from becoming a battery/data drain competing with native apps that go through the OS's own background-task budgeting. Concretely: periodic sync respects the requested minInterval only as a floor, not a guarantee - the browser can and will skip cycles under low battery, metered/cellular connections, or low site-engagement conditions; one-off sync retries with an increasing backoff if your handler's promise rejects, rather than hammering the network immediately and repeatedly.

The practical implication for design: never build a feature that assumes background sync fires promptly or on a strict schedule - treat every guarantee as "eventually, probably, if conditions are favorable," and make sure the product experience degrades gracefully (an in-app "last synced X ago" indicator) rather than assuming near-real-time background delivery.

Common Mistake

Designing a feature around Periodic Background Sync's minInterval as if it were a cron schedule. It's a lower bound the browser is free to exceed arbitrarily based on conditions you don't control or observe - treat it as a hint, not a contract.

Q52. How do you avoid duplicate submissions if a queued sync retries a request that actually succeeded server-side, but the client never got the response?

ROI: ★★★★★ Frequency: High

Short Answer

This is a classic at-least-once-delivery problem and it's common in offline sync: the request reaches the server and is processed, but the response is lost (connection drops right after), so the client's queue still thinks it failed and retries - now you risk two orders, two payments, two identical records. The standard fix is idempotency keys: the client generates a unique ID for the logical operation once, at the moment it's first queued (not on every retry), and sends it as a header or field on every attempt; the server persists which idempotency keys it has already processed and, on seeing a repeat, returns the original result instead of re-executing the mutation.

This has to be designed on both ends - a client-only fix (deduping in the queue) can't protect against the server having already applied the first attempt, and a server-only fix requires the client to actually send a stable key rather than generating a fresh one on every retry, which defeats the whole point. 

// Client: generate the key ONCE, when the entry is first queued
async function queueOrder(payload) {
  const idempotencyKey = crypto.randomUUID();
  await db.put("outbox", { payload, idempotencyKey, createdAt: Date.now() });
}

// Every retry reuses the SAME key
await fetch("/api/orders", {
  method: "POST",
  headers: { "Idempotency-Key": entry.idempotencyKey },
  body: JSON.stringify(entry.payload),
});

// Server: check-and-store before executing the mutation
if (await db.idempotencyKeys.exists(key)) {
  return db.idempotencyKeys.getStoredResponse(key); // replay, don't re-execute
}

Interview Gold Point

This question quietly tests whether a candidate understands "at-least-once delivery" as a general distributed-systems concept, not a PWA-specific quirk - background sync just happens to be a very common place frontend engineers first encounter it.

Q53. How does Periodic Background Sync's permission model differ from the regular Notification permission prompt?

ROI: ★★☆☆☆ Frequency: Low-Medium

Short Answer

Notification permission is an explicit, user-facing prompt - the browser shows a dialog, the user clicks allow/block, and the result is a durable, queryable permission state. Periodic Background Sync has no equivalent visible prompt at all; instead, access is gated silently behind the browser's own site-engagement scoring (how much the user actually interacts with the installed PWA over time) combined with the app being installed in the first place. There's no user-facing "allow periodic sync?" dialog to design UX around, and no way to explicitly request it beyond calling register() and checking whether navigator.permissions.query({ name: "periodic-background-sync" }) reports "granted" - which the browser decides unilaterally based on usage signals you can't directly observe or influence beyond generally driving engagement.

Common Mistake

Designing a permission-request UX flow for Periodic Background Sync the way you would for notifications. There is no dialog to trigger - the right move is simply checking the permission query result and silently falling back to on-demand refresh if it isn't granted, since there's nothing for the user to click either way.

Q54. How would you monitor background sync success/failure rates in production, given it happens with no open tab?

ROI: ★★★☆☆ Frequency: Medium

Short Answer

Standard page-load-based analytics is useless here by definition - the whole point of background sync is that it can run with nothing rendered. The service worker itself has to be the source of telemetry: inside the sync event handler, after attempting the queued work, send a lightweight beacon (a simple fetch() POST to an analytics endpoint, or navigator.sendBeacon if called from a page context) reporting success/failure/retry-count for that sync attempt, wrapped in the same waitUntil() as the retry logic so it isn't dropped if the worker gets torn down right after.

On the backend, this becomes an ordinary metrics problem once the events land: track sync success rate, average retry count before success, and how often entries exceed maxRetentionTime and get silently dropped (Q7's BackgroundSyncPlugin config) - that last number specifically tells you whether your offline queue is actually recovering, or quietly losing user data past the retention window. 

self.addEventListener("sync", (event) => {
  if (event.tag !== "flush-outbox") return;
  event.waitUntil(
    flushOutboxInOrder()
      .then(() => reportSyncMetric("success"))
      .catch((err) => reportSyncMetric("failure", err).then(() => Promise.reject(err)))
  );
});

function reportSyncMetric(status, err) {
  return fetch("/api/metrics/sync", {
    method: "POST",
    body: JSON.stringify({ status, message: err?.message, ts: Date.now() }),
  }).catch(() => {}); // never let telemetry failure mask the real sync result
}

Interview Gold Point

Naming "how often does an entry exceed max retention and get silently dropped" as the metric that actually matters shows you understand the failure mode that's invisible without instrumentation - a queue that quietly drops data past a retention window looks identical to a healthy one until someone measures it.

SECTION 11 - OFFLINE-FIRST ARCHITECTURE PATTERNS

Q55. What does "offline-first" mean architecturally, as distinct from merely "offline-tolerant"?

ROI: ★★★★★ Frequency: Very High

Short Answer

Offline-tolerant means the network is the primary source of truth and offline is a degraded fallback state you patch over with caching - the app works online-first and merely "survives" a dropped connection, often with a visibly worse experience. Offline-first inverts the assumption: every read and write goes through a local store (IndexedDB, in practice) first, the UI always renders from that local store regardless of connectivity, and syncing with the server is a background concern layered on top rather than the thing the UI directly waits on. The user never sees a fundamentally different app depending on whether the network happens to be up.

This is a genuinely different architecture, not just "add a service worker": writes are optimistic against the local store immediately, a sync engine reconciles the local store with the server asynchronously (Q56-Q57), and the UI subscribes to the local store's changes rather than to network responses directly. It's substantially more engineering effort than offline-tolerant caching, and is usually only justified for apps where working with zero or flaky connectivity is a core requirement (field service tools, note-taking, anything targeting users on unreliable networks) rather than a nice-to-have.

Interview Gold Point

The crisp distinction to lead with: "offline-tolerant treats the network as truth and offline as an exception to paper over; offline-first treats the local store as truth and the network as a background sync target." Naming the added engineering cost explicitly, and that it's only worth it for apps where offline is a core requirement, shows judgment rather than reflexive enthusiasm for the pattern.

Q56. How do you design a local-first write path - optimistic UI, IndexedDB write, queued sync, reconciliation?

ROI: ★★★★★ Frequency: Very High

Short Answer

The write path has four stages that all have to happen in the right order for the pattern to actually deliver its promise. First, the UI updates immediately and optimistically from the user's action, without waiting on anything network-related. Second, that same change is written to IndexedDB synchronously with the UI update (so a page refresh a millisecond later still shows the change) and tagged as "pending sync." Third, the change is enqueued for background delivery to the server - using Background Sync where available, a manual retry loop otherwise (Q49). Fourth, once the server confirms, the local record's "pending" flag clears; if the server instead rejects it (a validation error, a conflict), the reconciliation step decides whether to roll back the optimistic UI change, show an error, or attempt an automatic merge (Q57). 

async function createNoteOfflineFirst(note) {
  const localId = crypto.randomUUID();
  const record = { ...note, id: localId, status: "pending", createdAt: Date.now() };

  await db.put("notes", record);      // 1+2: local store is truth immediately
  renderNoteOptimistically(record);   // UI never waits on network

  queueSync({ type: "create-note", localId, payload: note }); // 3: background delivery

  return record;
}

async function onSyncConfirmed(localId, serverRecord) {
  await db.put("notes", { ...serverRecord, status: "synced" }); // 4: reconcile
}

Interview Gold Point

Explicitly separating "the UI update" from "the durable local write" from "the network sync" as three distinct steps - rather than one blended operation - is what distinguishes a real offline-first design from a hand-wavy description of one.

Q57. What conflict-resolution strategies exist when a queued offline write conflicts with a server-side change made in the meantime?

ROI: ★★★★☆ Frequency: High

Short Answer

Several strategies exist along a spectrum of simplicity versus correctness. Last-write-wins is the simplest - whichever write has the later timestamp overwrites the other unconditionally - and it's acceptable for low-stakes data (a UI preference, a draft note) but silently discards real work when two genuinely different edits collide. Field-level merge improves on this by diffing which specific fields each side actually changed and merging non-overlapping changes automatically, only surfacing a real conflict when both sides touched the same field. Manual/user-mediated merge punts the decision to the user when an automatic merge isn't safe - showing both versions and asking them to pick or combine, the way Git presents a merge conflict.

CRDTs (Conflict-free Replicated Data Types) are the most sophisticated option: data structures specifically designed so that concurrent edits from multiple sources can always be merged automatically and deterministically without a central authority resolving anything - text CRDTs power real-time collaborative editors, and counter/set CRDTs handle collaborative counting or tagging. They're powerful but add real complexity and are usually only worth adopting when true concurrent multi-writer editing (not just "one device was briefly offline") is a core product requirement.

Common Mistake

Reaching for CRDTs by default because they sound impressive. For the common offline-first case - one user, one device, briefly disconnected - last-write-wins or field-level merge is almost always sufficient and far simpler to reason about; CRDTs earn their complexity only under genuine concurrent multi-writer conditions.

Q58. How do you structure IndexedDB object stores and indexes to support a sync queue with retry and ordering?

ROI: ★★★★☆ Frequency: High

Short Answer

A practical schema separates domain data from sync bookkeeping rather than mixing "pending" flags scattered across every entity table. One store per entity type (notes, orders) holds the actual domain records, each with a lightweight syncStatus field ("synced" | "pending" | "error"). A separate outbox store holds one row per queued mutation - not per entity - with an auto-incrementing key (which IndexedDB naturally sorts by insertion order, giving you the ordering guarantee from Q50 for free), a reference to which entity/operation it represents, retry count, and last-attempted timestamp. An index on syncStatus in the entity stores lets the UI cheaply query "show me everything still pending" for a sync indicator (Q59) without scanning the outbox. 

const db = await openDB("app-db", 1, {
  upgrade(db) {
    const notes = db.createObjectStore("notes", { keyPath: "id" });
    notes.createIndex("by-syncStatus", "syncStatus");

    const outbox = db.createObjectStore("outbox", { keyPath: "seq", autoIncrement: true });
    outbox.createIndex("by-entity", "entityId");
  },
});

Interview Gold Point

Separating "domain data" from "sync bookkeeping" into different stores, rather than bolting sync metadata onto every entity ad hoc, is the schema decision that keeps a sync engine maintainable as more entity types get added later.

Q59. How do you communicate offline/sync state to the user without being silent or annoying?

ROI: ★★★☆☆ Frequency: Medium

Short Answer

Two failure modes to avoid at opposite ends: total silence (the user has no idea their edit hasn't actually reached the server yet, and closes the laptop assuming it's saved) and noise (a toast or spinner interrupting every single sync event, which trains users to ignore all of them, including the ones that matter). The middle ground most offline-first apps converge on is a small, persistent, low-key status indicator - a subtle "syncing…" / "all changes saved" / "N changes waiting to sync" element, usually near the top of the UI, that's always present but never modal or blocking.

For failures specifically (Q62), the bar for interrupting the user should be higher than for a normal pending-sync state - a change that's queued and simply hasn't gone out yet doesn't need an alert, but a change the server has actively rejected (a validation error, a real conflict) does need to surface somewhere the user will actually see it, since silently dropping a rejected edit is worse than any amount of "annoying" notification.

Common Mistake

Treating "pending, will sync eventually" and "failed, needs the user's attention" as the same UI state. Conflating them either buries real failures in routine sync noise, or trains users to panic at completely normal offline behavior.

Q60. How would you version your IndexedDB schema and migrate data across app updates?

ROI: ★★★★☆ Frequency: High

Short Answer

indexedDB.open(name, version) takes an explicit integer version number, and opening with a higher version than what's currently stored fires an upgrade callback (in the idb wrapper) with both the old and new version numbers, inside a special versionchange transaction where you're allowed to create/delete object stores and indexes and to read/write existing data to reshape it. Migrations should be written as a sequence of incremental steps gated by oldVersion, each one handling exactly one version bump, rather than one big "if newest version, do everything" block - that keeps a user upgrading from version 1 straight to version 4 running steps 1→2, 2→3, and 3→4 in order, correctly, rather than skipping intermediate transformations. 

const db = await openDB("app-db", 4, {
  upgrade(db, oldVersion) {
    if (oldVersion < 2) {
      db.createObjectStore("notes", { keyPath: "id" });
    }
    if (oldVersion < 3) {
      db.transaction.objectStore("notes").createIndex("by-syncStatus", "syncStatus");
    }
    if (oldVersion < 4) {
      // Backfill a new required field on every existing record.
      const store = db.transaction.objectStore("notes");
      store.openCursor().then(function walk(cursor) {
        if (!cursor) return;
        cursor.update({ ...cursor.value, syncStatus: cursor.value.syncStatus ?? "synced" });
        cursor.continue().then(walk);
      });
    }
  },
});

Common Mistake

Writing migrations as one unconditional block that assumes every user is coming from the immediately previous version. Real users skip versions (an app that wasn't opened for months), and unconditioned migration code silently corrupts or skips data for anyone who wasn't on exactly version - 1.

Q61. What's the role of a library like Dexie.js, RxDB, or PouchDB versus hand-rolling this with idb?

ROI: ★★★☆☆ Frequency: Medium

Short Answer

idb is a thin promise wrapper around raw IndexedDB - it removes the callback boilerplate but you still design and implement schema, querying, and sync yourself. Dexie.js goes further, adding a much friendlier query API (chained .where().equals() filters, compound indexes) and a well-regarded observable/live-query layer, but still leaves sync-with-a-server as your own responsibility to build. RxDB and PouchDB are a bigger step up the stack: they bake in an actual replication protocol (PouchDB famously syncs with CouchDB out of the box; RxDB supports several backends and a GraphQL replication plugin) plus built-in conflict-resolution primitives, essentially giving you a real offline-first sync engine rather than just a nicer local database API.

The trade-off is the usual one: a full sync-engine library saves enormous effort if your backend fits its expected replication model, but is a much bigger dependency and abstraction to adopt than idb/Dexie, and is a poor fit if your backend is a bespoke REST/GraphQL API that doesn't speak the library's replication protocol - in that case hand-rolling the queue-and-reconcile logic on top of a lighter local-database wrapper is often the more pragmatic choice.

Interview Gold Point

Framing this as "local-database-API" (idb, Dexie) versus "full replication engine" (RxDB, PouchDB) rather than treating all four as interchangeable options shows you understand they solve different-sized problems, and that the right choice depends on whether your backend can speak a replication protocol at all.

Q62. How do you handle partial sync failures, where some queued mutations succeed and others fail?

ROI: ★★★★☆ Frequency: High

Short Answer

Never let one failing entry block or corrupt the rest of the queue's processing state - a naive implementation that processes the outbox in a single transaction, or that stops all further syncing entirely on the first error, turns one bad mutation into a total sync outage. The pattern is to process each queued entry independently, dequeuing on individual success and leaving individual failures in place with their own retry count and last-error recorded, while continuing to attempt the rest of the queue (subject to the ordering constraint from Q50 for entries that are genuinely dependent on each other).

Failures also need a classification: transient failures (network error, 503, timeout) should retry with backoff; permanent failures (a 400 validation error, a 409 conflict the server will never auto-resolve) should stop retrying automatically and surface the error to the user or a manual-resolution UI instead, since retrying a request the server will reject every time just wastes cycles and delays the healthy entries behind it. 

async function flushOutbox() {
  const entries = await db.getAllSorted("outbox", "sequence");
  for (const entry of entries) {
    try {
      await sendMutation(entry);
      await db.delete("outbox", entry.id);
    } catch (err) {
      if (isPermanentFailure(err)) {
        await db.put("outbox", { ...entry, status: "failed", error: err.message });
        continue; // don't block the rest of the queue on a permanent failure
      }
      await db.put("outbox", { ...entry, retryCount: entry.retryCount + 1 });
      break; // transient failure: stop here to preserve ordering, retry next cycle
    }
  }
}

Interview Gold Point

The distinction between "permanent, stop retrying and surface to the user" and "transient, retry with backoff" is the piece candidates most often skip - treating every failure identically either spams retries against a request that will never succeed, or silently gives up on one that would have worked on the next attempt.

SECTION 12 - THE APP SHELL MODEL

Q63. What is the "app shell" model precisely, and how does it differ from just caching the whole page?

ROI: ★★★★★ Frequency: Very High

Short Answer

The app shell is the minimal HTML/CSS/JS needed to render the application's chrome - navigation, layout skeleton, header/footer, loading states - completely independent of any actual content, which is fetched separately and layered in afterward. The key architectural move is treating "the shell" and "the content" as two different cacheability profiles: the shell almost never changes and can be aggressively cache-first/precached (Q4-Q5), while content changes constantly and needs its own, usually much shorter-lived, caching or network-first strategy.

This is a meaningfully different thing from "cache the whole rendered page," which conflates shell and content into one blob - either you cache too aggressively (content goes stale because the whole page, including data, is treated as immutable) or not aggressively enough (the shell itself gets re-fetched over the network every time, just to render the same nav bar it rendered yesterday). Splitting them means the shell paints instantly on every repeat visit from cache, while the content underneath streams in fresh, independent of how the shell was served.

Interview Gold Point

The clean framing: "cache the skeleton like it's a static asset, fetch the content like it's dynamic data - because that's exactly what each one is." A candidate who describes app-shell as "cache the homepage" is missing the actual architectural insight.

Q64. How do you architect a React app's build so the shell is a separate, cacheable bundle from route-level content?

ROI: ★★★★☆ Frequency: High

Short Answer

Practically, this maps onto ordinary code-splitting done with the shell/content split in mind rather than purely by route. The layout components (nav, header, footer, app-level providers) and their styles should live in a bundle that's shared and stable across every route - bundlers naturally hoist genuinely shared code into a common chunk, but it helps to be deliberate about it (a dedicated AppShell component tree, imported by every route but never itself split per-route) so the bundler's chunk-splitting heuristics have an obvious, stable boundary to key off. Route-specific components and data-fetching logic are lazy-loaded per route via React.lazy/dynamic imports, so navigating to a new route only pulls in that route's chunk, never re-fetching the shell.

On the service worker side, this maps directly onto Q5's precaching: the shell's stable, hashed bundle goes into the Workbox precache manifest (fetched once, essentially never re-fetched until it actually changes), while route chunks are handled by runtime caching rules (cache-first once fetched, since they're also hash-named, but not proactively precached unless you know a route is critical enough to warrant it).

Common Mistake

Precaching every route's JS chunk at install time "to be thorough." This bloats the initial install (slower first visit, more storage used) for routes the user may never visit - runtime caching for anything beyond the shell and the most critical routes is usually the better trade-off.

Q65. How does the app shell model interact with SSR/Next.js, where the initial HTML already contains real content, not just a shell?

ROI: ★★★★☆ Frequency: High

Short Answer

The classic app-shell model was designed for client-rendered SPAs, where the first HTML response genuinely is just a near-empty skeleton. SSR breaks that assumption on purpose - the whole point of SSR is that the first response already contains real, rendered content, which is good for first-paint and SEO but means "cache the shell, fetch content separately" isn't a clean fit for the very first request.

In practice, an SSR/Next.js PWA applies the app-shell idea one layer up: the service worker uses network-first (or stale-while-revalidate) for the SSR'd HTML document itself, since that response mixes shell and content and freshness matters, while still aggressively cache-first precaching the truly static shell assets - the JS/CSS bundles, fonts, icons - that are shared across every server-rendered page and never change per-request. Client-side navigations after the first load behave much more like the classic SPA case (React hydration takes over, subsequent route transitions fetch only data/RSC payloads, not full documents), so the shell/content split reasserts itself naturally once you're past the initial SSR response.

Interview Gold Point

Recognizing that SSR doesn't invalidate the app-shell idea, it just moves where the split happens - shell-vs-content applies to the static assets and to post-hydration navigation, while the very first HTML response is handled with ordinary network-first/SWR caching - shows real architectural thinking rather than reciting the SPA-era version of the pattern unchanged.

Q66. What's the risk of an app shell cached too aggressively - stale navigation or branding surviving a rebrand or feature-flag flip?

ROI: ★★★☆☆ Frequency: Medium

Short Answer

Precisely because the shell is designed to be cached almost indefinitely, anything baked into it becomes sticky in a way that's easy to forget about - a nav item that should have been removed by a feature flag, an old logo after a rebrand, copyright text with last year's date. If the shell bundle's actual bytes didn't change (the flag check happens at runtime against a config the shell fetches separately, say), content-hashed cache-busting doesn't help at all, because from the cache's point of view nothing changed.

The fix is treating anything that needs to update independently of a full deploy - feature flags, remotely configurable copy, A/B test assignments - as data the shell fetches at runtime (ideally via a short-TTL or network-first request) rather than as something baked into the shell bundle itself; the shell's job is structural layout, not the specific dynamic values rendered inside it. Anything that genuinely is baked into the shell bundle (real branding, real nav structure) does get the benefit of the standard hashed-filename fix from Q5/Q8 - a rebrand ships a new bundle hash, and the update flow in Q8 takes it from there.

Common Mistake

Baking feature-flag-gated UI directly into the precached shell bundle and being surprised when disabling the flag server-side doesn't remove it for already-cached users. Anything meant to change without a full redeploy has to be fetched at runtime, not compiled into the aggressively cached shell.

Q67. How do you combine the app shell model with code-splitting so the shell loads instantly but route chunks are fetched on demand?

ROI: ★★★★☆ Frequency: High

Short Answer

The two techniques are complementary and meant to be layered: code-splitting decides what JS gets bundled together at build time, the app-shell caching strategy decides how each resulting bundle gets served at runtime, and they need to agree on the same boundary to actually pay off together. Concretely: the router-level split already isolates each route's code into its own chunk; the service worker's precache manifest includes only the shell chunk(s) (Q64), while route chunks are picked up by a runtime registerRoute rule matching the build's JS output pattern with a cache-first strategy (since they're hash-named, cache-first is safe and correct) plus an expiration cap (Q29) so chunks for routes the user visited once, long ago, don't accumulate forever.

The net effect: first visit pays for the shell plus whatever route it landed on; every subsequent navigation to a new route pays a real, small network cost once (fetching that route's chunk), but every repeat visit to any previously visited route is fully cache-first and instant, and the shell itself is never re-fetched across any of it.

Interview Gold Point

Naming that code-splitting and the caching strategy have to "agree on the same chunk boundary" to actually compound - splitting code one way while caching by a completely different URL pattern is a common gap that quietly defeats both optimizations.

Q68. How do you design a loading/skeleton state so the shell renders instantly on both first visit and repeat visit?

ROI: ★★★☆☆ Frequency: Medium

Short Answer

The two visits have genuinely different constraints and deserve different handling rather than one generic spinner. On a first visit, nothing is cached yet - the shell itself has to come over the network, so the very first paint should be an inline, zero-dependency skeleton (critical CSS inlined in the initial HTML, no separate JS/CSS fetch required to show something) so the user sees structure immediately rather than a blank white screen while the shell bundle downloads. On a repeat visit, the shell is already cache-first from Cache Storage, so it should paint essentially instantly with no visible loading state at all for the shell itself - only the content underneath (which is genuinely being fetched fresh) needs its own skeleton/loading indicator, scoped to the content area, not the whole page.

Conflating the two - showing a full-page skeleton on every visit regardless of whether the shell is actually cached - wastes the exact benefit the app-shell model is supposed to deliver: instant repeat visits.

Common Mistake

Reusing the same "cold start" loading UI on every visit regardless of cache state. If the shell is precached, showing a shell-level skeleton on a repeat visit is pure regression - the loading state belongs to the content region only, once the shell itself is reliably instant.

Q69. How do you test that your app shell actually renders correctly with zero network connectivity, as part of CI?

ROI: ★★★☆☆ Frequency: Medium

Short Answer

This has to be a real browser test, not a unit test - the whole claim being verified ("the shell renders with the network fully off") only means something if a real service worker actually intercepted a real navigation. Playwright is the practical tool: launch a real browser context, navigate normally so the service worker installs and activates for real, then flip context.setOffline(true), reload, and assert the shell's key structural elements are present and visible - nav, header, the app's root container - independent of whether any content data loaded successfully underneath. 

test("app shell renders with zero network", async ({ page, context }) => {
  await page.goto("/");
  await page.waitForFunction(() => navigator.serviceWorker.controller !== null);

  await context.setOffline(true);
  await page.reload();

  await expect(page.locator("nav[data-testid=app-nav]")).toBeVisible();
  await expect(page.locator("[data-testid=app-shell-root]")).toBeVisible();
  // Content area may legitimately show an offline/error state - that's a separate assertion.
});

Interview Gold Point

Explicitly scoping the assertion to the shell's structural elements, and treating the content area's offline behavior as a separate, distinct test, mirrors the shell/content split from Q63 - conflating them in one assertion is the same modeling mistake in test form.

Q70. What's the difference between the app shell model and "critical CSS inlining" - are they solving the same problem?

ROI: ★★★☆☆ Frequency: Medium

Short Answer

They're related but solve different halves of the same "avoid a blank screen" problem, and interviewers sometimes probe whether you conflate them. Critical CSS inlining addresses the very first paint of a single page load - extracting just the CSS needed to render above-the-fold content and inlining it directly in the HTML <head>, so the browser doesn't block first paint on a separate stylesheet round trip. It's a same-request optimization with no dependency on caching or service workers at all.

The app shell model addresses repeat visits and offline resilience by caching the layout/navigation structure itself so it doesn't need to be fetched (or fully re-rendered from scratch) again. They compose well together rather than compete: critical CSS gets the very first, uncached paint looking good as fast as possible, while the app shell's service-worker caching is what makes every visit after the first essentially free. Neither replaces the other - one is about the first millisecond of one page load, the other is about not repeating that work at all on return visits.

Common Mistake

Treating "we inline critical CSS" as evidence the app already has an app-shell architecture, or vice versa. They're independent techniques that happen to both target early-render performance, and a mature PWA typically uses both together, not one instead of the other.

SECTION 13 - PWA PERFORMANCE & LIGHTHOUSE AUDITS DEEP DIVE

Q71. Beyond installability, what PWA-specific anti-patterns does Lighthouse flag - like a redirect on start_url?

ROI: ★★★☆☆ Frequency: Medium

Short Answer

A few subtle ones come up repeatedly in real audits. A start_url that redirects (say, to a locale-specific path, or through an auth check) fails the installability check outright, because the manifest's start_url is required to resolve directly without a redirect hop - locale/auth logic needs to live inside the app after it loads, not as a server-side redirect on the URL the manifest points at. A service worker registered but scoped so narrowly it doesn't actually cover the page that registered it is flagged as ineffective. A manifest served with the wrong MIME type (not application/json or application/manifest+json) can be silently ignored by some browsers even though it "looks" correct in the network tab. And a viewport meta tag missing or misconfigured (no width=device-width) undermines the "PWA optimized" checks even when installability itself passes.

Interview Gold Point

Naming the redirect-on-start_url case specifically is a strong signal - it's one of the more common real-world reasons a PWA that "looks" correctly configured mysteriously fails Lighthouse's installability check, and it's not obvious unless you've actually debugged it.

Q72. How does a poorly written service worker fetch handler actively hurt LCP/INP, rather than just fail to help?

ROI: ★★★★☆ Frequency: High

Short Answer

Once a service worker is in control, it sits in the path of every request, including the very first document and asset requests that determine LCP - so a slow or badly-implemented handler doesn't just fail to help, it becomes new overhead the unregistered version of the site never had. Concretely: a fetch handler that does an unnecessary await chain before deciding cache-vs-network on every single request adds latency to everything, even requests that end up going to network anyway; a cache-first strategy applied to something that should be network-first can serve a stale LCP-candidate image or hero asset, technically painting fast but painting the wrong thing; and opening a fresh Cache Storage handle (caches.open()) inside the hot path of every fetch rather than reusing a resolved handle adds avoidable per-request overhead at scale.

The general principle: a service worker's fetch handler is now part of your critical rendering path for every resource, so its own code needs the same performance discipline as any other hot-path code - minimize branching cost, avoid redundant async work, and profile it (Q73) rather than assuming "it's just caching, it must be fast."

Common Mistake

Treating the service worker as pure upside because "it's just caching." A badly written fetch handler is squarely in the critical path and can regress Core Web Vitals for every user, cached or not - it needs performance scrutiny like any other code that runs on every request.

Q73. How do you profile a service worker's own performance - cache lookup latency, handler overhead - using DevTools?

ROI: ★★★☆☆ Frequency: Medium

Short Answer

Chrome DevTools' Performance panel records service worker activity on its own thread track, separate from the main thread, when you record a trace while the SW is intercepting requests - you can see individual fetch/install/activate event handlers as distinct entries with real wall-clock duration, which is the most direct way to spot a handler that's unexpectedly slow. Wrapping suspect sections of your own SW code in performance.mark()/performance.measure() calls (the Performance API is available inside a service worker, unlike many DOM-adjacent APIs) surfaces custom, named timings in that same trace, which is far more actionable than guessing from aggregate page-load numbers.

The Network panel's per-request timing breakdown, cross-referenced with which requests show "(ServiceWorker)" as their source (Q13), tells you specifically how much time is being added by interception versus how much would have happened anyway on a direct network request - the delta between a bypassed request (via "Bypass for network") and the same request normally intercepted is a clean before/after measurement of your fetch handler's actual overhead.

Interview Gold Point

Describing the "bypass vs normal" A/B comparison as a way to isolate the service worker's actual added latency shows a genuine measurement methodology, not just "open the Performance tab and look at it."

Q74. What's the risk of precaching too much at install time, and how does it show up in real metrics?

ROI: ★★★☆☆ Frequency: Medium

Short Answer

Every URL in the precache list has to actually be fetched during install before the worker is considered installed - so a precache manifest bloated with assets the user may never need (every route's JS chunk, every locale's translation file, high-res images "just in case") turns the very first visit into a much heavier one than the page itself required, competing for bandwidth with the resources actually needed to render that first visit. This shows up concretely as a worse Time to Interactive / LCP on first visit specifically (subsequent visits look fine, since by then everything's already cached) - a classic case of a metric regressing only for a subset of sessions, which makes it easy to miss in aggregate dashboards that blend first and repeat visits together.

The fix is being deliberate about what's genuinely shell-critical (Q64) versus what should be runtime-cached on demand instead - precache only what every user needs on every visit, and let route-specific or rarely-used assets earn their way into the cache the first time they're actually requested.

Common Mistake

Looking only at blended, aggregate LCP/TTI numbers and missing a first-visit-specific regression caused by an over-eager precache list. Segmenting performance metrics by first-visit versus repeat-visit is necessary to even see this class of problem.

Q75. How do you audit and fix "does not respond with 200 when offline" failures that aren't obvious from the code?

ROI: ★★★☆☆ Frequency: Medium

Short Answer

This check specifically simulates a navigation to start_url with the network off and expects a real 200 - and it can fail for reasons that don't show up just reading the fetch handler in isolation. Common real causes: the fetch handler only intercepts requests matching a narrower pattern than start_url actually resolves to (a trailing slash, a query string mismatch); the precache step genuinely failed silently on a previous deploy (Q18) and the cache is simply missing the shell; or the fetch handler's fallback logic has a bug that only triggers on navigation-mode requests specifically, which is easy to miss if you only manually tested non-navigation asset requests.

The direct way to audit it: open DevTools Application → Service Workers, tick "Offline," and manually navigate to the exact URL start_url resolves to, watching the Network panel for what actually gets served (or fails) - reproducing the exact check Lighthouse performs, rather than reasoning about the code abstractly.

Interview Gold Point

Naming that you'd reproduce the exact failing scenario manually via DevTools' offline toggle - rather than only re-reading the fetch handler source - shows a debugging instinct: verify the actual observed behavior first, then work backward to the code.

Q77. How does service worker caching interact with regular HTTP caching (Cache-Control headers) - which wins, and how can they conflict?

ROI: ★★★★☆ Frequency: High

Short Answer

They're two separate cache layers that a request can pass through, and understanding the order matters. A fetch() call issued from inside a service worker's handler still goes through the browser's normal HTTP cache first (respecting Cache-Control/ETag) before hitting the network - unless you explicitly opt out with { cache: "no-store" } or { cache: "reload" } on that fetch. This means "network-first" in your service worker can still return an HTTP-cache hit rather than a truly fresh network response, if the underlying resource's headers say it's still fresh - which is usually fine and even desirable (avoiding a redundant round trip), but can surprise you if you assumed "network-first" always means "definitely hit the server."

The conflict case worth knowing: if a resource is served with long-lived, aggressive HTTP Cache-Control headers and your service worker also cache-firsts it into Cache Storage, you effectively have two independent caches of the same content that can drift out of sync if invalidated differently (clearing one doesn't clear the other) - which is exactly why content-hashed filenames (Q5/Q8) are valuable at both layers simultaneously: a new hash means a new URL, which trivially busts both the HTTP cache and the service worker's Cache Storage at once, with no coordination required between them.

Interview Gold Point

Explaining that a service worker's fetch() still passes through the HTTP cache by default (unless overridden) is a detail many candidates miss - they describe the service worker's cache as the only cache in play, when in reality it's layered on top of the browser's existing HTTP caching.

Q78. How do RUM tools distinguish service-worker-served responses from network-served ones, and why does that distinction matter?

ROI: ★★★☆☆ Frequency: Medium

Short Answer

The Resource Timing API (PerformanceResourceTiming, what most RUM tools read from under the hood) exposes exactly this via the nextHopProtocol and transfer-size fields - a service-worker-served response typically reports transferSize: 0 and its timing entry reflects however long the service worker's own logic took to respond, not a real network transfer, letting RUM tooling separate "served instantly from cache by the SW" from "actually fetched over the wire" in the same metric stream.

The distinction matters because blending them produces misleading aggregate numbers: a page's median load time can look excellent purely because most sampled sessions were repeat visits served entirely from the service worker's cache, masking a real regression in the actual network-served, first-visit experience that a smaller fraction of your traffic - and every genuinely new user - actually has. Segmenting performance data by "served via SW" versus "served via network" (or equivalently, first-visit versus repeat-visit, per Q74) is necessary to see either population's real experience clearly.

Interview Gold Point

Connecting this back to Q74's first-visit-vs-repeat-visit blending problem shows the pattern recurring across the chapter: aggregate PWA metrics are almost always misleading unless segmented by cache-hit status, and RUM tooling needs to be configured with that in mind rather than trusted at face value.

SECTION 14 - UPDATING A PWA SAFELY

Q79. What's the decision tree for prompting a user to update versus forcing it silently?

ROI: ★★★★★ Frequency: Very High

Short Answer

The right call depends on what actually changed, not on a blanket policy. A purely additive, backward-compatible change (a new feature behind a flag, a visual tweak, a bug fix that doesn't touch any contract the old client relied on) is safe to activate silently via skipWaiting()/clients.claim() without asking, since there's no real risk of a mid-session mismatch causing breakage. A change that alters the API contract between client and server (a renamed field, a changed request shape, a removed endpoint the old JS still calls) is not safe to force silently - an old tab still running old JS against a new backend, or new JS suddenly active mid-session against state it wasn't expecting, is exactly the failure mode the waiting phase (Q3) exists to prevent, so this class of change should always go through the "new version available, click to refresh" prompt (Q8), giving the user (and their in-progress work) a clean boundary to update across.

A third category - a critical security fix or a fix for active data corruption - sometimes justifies forcing the update even more aggressively than a polite banner, up to and including a full-page interstitial blocking further use until refreshed, because the cost of staying on the old version outweighs the disruption of forcing it.

Change typeRecommended update strategy
Additive, backward-compatibleSilent skipWaiting/clients.claim, no prompt needed
Breaking API/contract change"New version available" banner, user-initiated refresh
Critical security/data-corruption fixForced refresh, even an interstitial if severe enough

Interview Gold Point

Naming three tiers rather than a single blanket "always prompt" or "always force" policy is what shows real production judgment - the right answer genuinely depends on what the release contains, not on a fixed rule applied uniformly to every deploy.

Q80. How do you deploy a breaking API change that requires the new service worker AND new client JS to ship in lockstep?

ROI: ★★★★☆ Frequency: High

Short Answer

The core danger is that a service worker update and a client-JS update aren't atomic together from the browser's point of view - a tab can end up running old application JS against a newly-activated service worker (or vice versa) for a window of time, which is exactly wrong if the two were only ever tested and designed to work as a matched pair. The safe pattern is backend-first, dual-compatibility rollout: ship the backend supporting both the old and new contract simultaneously first, then ship the new client+SW pair, force that pair to update together via the "new version available" prompt from Q79 (never split across two separate silent deploys), and only remove backend support for the old contract once telemetry confirms essentially no clients are still running the old pair.

The one thing to explicitly avoid is relying on "the service worker and the JS bundle happen to deploy in the same build, so they'll always update together" - they don't update atomically on the client just because they were built together; the waiting-phase mechanics (Q3) can still leave a tab on an old pairing for an arbitrary amount of time until it closes or the user accepts a refresh.

Common Mistake

Assuming that because the SW and the JS bundle were deployed in the same release, they'll always be consistent on the client. They can absolutely diverge if a tab is mid-update-cycle - backward/forward compatibility on the backend during the rollout window is what actually protects you, not an assumption about deploy atomicity.

Q81. How do you roll out a service worker update gradually - a canary - rather than to 100% of users at once?

ROI: ★★★☆☆ Frequency: Medium

Short Answer

Service workers don't have a native, platform-level percentage-rollout mechanism the way some app-store distribution channels do - the browser will offer the new version to whoever's sw.js byte-comparison detects a difference, with no built-in concept of "only some users." Canarying has to be built at the infrastructure layer in front of that: serve a different sw.js (and its associated build) to a percentage of traffic via your CDN/edge layer or load balancer, keyed by a sticky cookie or user-bucket hash so a given user consistently gets the same version across requests rather than flip-flopping between canary and stable on every navigation.

The practical risk to watch for specifically: because service worker scope is per-origin (Q11), you cannot canary by serving two different SWs to the same URL/scope for different users simultaneously in a naive way without very careful cache-key/versioning discipline - the safest implementation keys the cache names themselves (Q8) off the variant, so canary and stable users' caches never collide even while both are technically "active" for different segments of your traffic at the same time.

Interview Gold Point

Naming that canarying a service worker is an infrastructure/edge-routing problem, not something the Service Worker API supports natively, is the detail that shows you understand where the platform's capability actually ends and where you'd need to build the rest yourself.

Q82. What happens to a user's in-flight IndexedDB writes or queued background sync if you force-update the service worker mid-session?

ROI: ★★★★☆ Frequency: High

Short Answer

IndexedDB data itself is safe across a service worker update by default - it's origin-scoped storage, not tied to a specific worker version, so a new worker sees exactly the same database a moment after activating as the old worker saw a moment before. The real risk is around in-flight logic, not stored data: a queued background sync entry that the old worker's sync handler was written to process in one way might be picked up by the new worker's handler instead if the update completes between registration and firing - and if the new version changed the expected payload shape or the retry/dequeue logic, that queued entry could be misprocessed or silently dropped.

The mitigation is treating your outbox schema itself as a versioned contract (Q60) - a new service worker's sync handler should be defensive about entries queued by a previous version (checking a schema-version field on each entry and handling old shapes explicitly, or migrating them) rather than assuming every entry it ever processes was written by code from the same deploy.

Common Mistake

Assuming a queued sync entry will always be processed by the exact worker version that created it. Given the waiting/activation mechanics, that's not guaranteed - the outbox format needs to be forward-compatible across at least one version boundary.

Q83. How do you detect and recover from a service worker that's permanently broken in production - a "kill switch" pattern?

ROI: ★★★★☆ Frequency: High

Short Answer

If a bad service worker ships - one that throws on every fetch, or caches something that breaks the app for everyone who has it - you need a way to reach affected clients that doesn't depend on the broken worker itself cooperating. The standard "kill switch" pattern is a deliberately minimal, maximally defensive service worker version you can deploy as an emergency fix: its install handler clears every existing cache unconditionally, its activate handler calls clients.claim() immediately (skipping the normal cautious opt-in from Q8, since this is specifically an emergency), and its fetch handler does nothing but pass every request straight to the network - effectively returning the site to "no service worker" behavior for anyone who receives it, buying time to fix the real issue properly. 

// Emergency kill-switch sw.js - deploy this to unstick a broken worker
self.addEventListener("install", (event) => {
  event.waitUntil(
    caches.keys().then((keys) => Promise.all(keys.map((k) => caches.delete(k))))
  );
  self.skipWaiting();
});

self.addEventListener("activate", (event) => {
  event.waitUntil(self.clients.claim());
});

self.addEventListener("fetch", (event) => {
  event.respondWith(fetch(event.request)); // always network, no caching, no interception logic
});

// Once stabilized, optionally have this version self-unregister entirely:
// self.registration.unregister();

Interview Gold Point

Having a pre-written, tested "minimal, always-network, clears everything" service worker ready to deploy as a break-glass fix - rather than improvising one during an incident - is the kind of operational readiness senior interviewers specifically probe for with this question.

Q84. How do you avoid update loops where registration.update() keeps finding a "new" worker that's actually identical, due to non-deterministic build output?

ROI: ★★★☆☆ Frequency: Medium

Short Answer

Because the browser's update check is a raw byte comparison (Q15), a build pipeline that isn't fully deterministic - embedding a build timestamp, a random build ID, or non-stable object/module ordering directly into the compiled sw.js - produces a genuinely different file on every build even when nothing about the actual logic changed, which the browser correctly (from its own narrow point of view) treats as a real update every single time, triggering install/waiting cycles for no real reason and needlessly nudging every open tab toward an "update available" prompt on every deploy, including ones that changed nothing about the SW itself.

The fix is build-pipeline hygiene: ensure the service worker's own bundle output is reproducible given the same source (stable module ordering, no embedded wall-clock timestamps, using content hashes rather than build IDs for anything that needs a version identifier), and, if the SW file legitimately needs to reference a build identifier, keep that identifier itself content-derived (a hash of the actual precache manifest, say) rather than an incrementing counter or timestamp that changes even when nothing meaningful did.

Common Mistake

Embedding Date.now() or a random UUID directly into the built service worker file "for debugging" and not realizing it defeats the browser's own change-detection, turning every single deploy into a forced update cycle regardless of whether anything real changed.

Q85. How do you communicate a required hard refresh to users stuck on a very old, incompatible cached version?

ROI: ★★★☆☆ Frequency: Medium

Short Answer

For a user who's been offline or simply never triggered an update check for a long time, a soft "new version available, click to refresh" banner may not even be reachable - if their cached JS is old enough, it might not contain the code that shows that banner at all, or it might be calling backend endpoints that have since been removed entirely (past the compatibility window from Q80). The backend is the more reliable channel here: have API responses include a minimum-supported-client-version header or field, and have even old client code check for it as a baseline capability (this check itself needs to be simple and stable enough to have existed in every version you still consider "supported to detect its own obsolescence") - on detecting it's below the minimum, show a blocking "please refresh to continue" screen rather than letting the old code keep running against a backend that no longer fully supports it.

As a last resort for truly stuck clients (a service worker that itself is too broken to even check), the kill-switch pattern from Q83 combined with an explicit self.registration.unregister() in its activate handler forces a return to normal, uncontrolled network requests, which at least lets a subsequent plain page load reach current, unversioned server-rendered content that can then instruct the user to hard-refresh manually.

Interview Gold Point

Recognizing that a badly-stuck client might not even be capable of running the "please update" logic you'd normally rely on, and designing the minimum-version check to be backend-driven and deliberately simple enough to survive in even very old client code, shows you've thought about the actual worst case, not just the common one.

Q86. What monitoring would tell you your update strategy is actually working - percentage of clients on the latest SW version?

ROI: ★★★☆☆ Frequency: Medium

Short Answer

The single most useful metric is a version-adoption curve: have the client report its currently active service worker's version identifier (the cache-version string from Q8, or a build hash) on some regular cadence - page load, or a periodic beacon - and chart what percentage of active sessions are on the latest version versus each prior version, over time since the last deploy. A healthy update strategy shows that curve climbing quickly toward 100% within a reasonable window (hours to a few days, depending on your traffic's typical session frequency); a long tail that plateaus well below 100% and stays there is a direct signal of the orphaned-tab problem (Q20) or a broken update path affecting a real slice of users.

Pairing that with the "time since a client's SW was last confirmed active/updated" distribution (not just current version, but staleness) catches the case where a user is nominally "on the latest version" but only because they happened to refresh recently, versus a user whose tab has genuinely been open and unresponsive to updates for a long time - the latter is the population your orphaned-tab mitigations (Q20) should be aimed at.

Interview Gold Point

Proposing a version-adoption curve as a first-class production metric - not just "check for errors" - shows you think about service worker updates as an operational rollout to monitor over time, the same way you'd monitor any other staged deployment, rather than a fire-and-forget deploy step.

Q88. How does Trusted Web Activity (TWA) or PWABuilder let you ship a PWA through the Play Store while keeping one codebase?

ROI: ★★★☆☆ Frequency: Medium

Short Answer

A Trusted Web Activity is a thin native Android wrapper - essentially a full-screen Chrome instance with no browser UI at all - that launches your existing, already-deployed PWA inside it, verified against your domain via Digital Asset Links so Android trusts it's genuinely your content and not a spoofed wrapper. Critically, it's not a rewrite or a second codebase: the wrapped app still runs your actual web app, served from your actual servers, so a bug fix or feature shipped to your website is live inside the TWA-wrapped app instantly too, without a store review cycle - you only need to resubmit the wrapper itself for changes to the native shell (icon, permissions), which is rare.

PWABuilder (Microsoft's tool) automates generating this wrapper - and equivalent wrappers for iOS/Windows - from just your PWA's manifest URL, handling most of the store-submission boilerplate. This is the practical path many teams use to get store presence and discoverability (addressing part of the gap from Q87) while still maintaining exactly one web codebase as the source of truth.

Interview Gold Point

The key nuance to state explicitly: a TWA is a wrapper around your live website, not a compiled snapshot of it - so it gets your normal deploy cadence "for free" instead of being frozen at store-submission time, which is the detail that makes this a genuinely different proposition than a plain WebView-wrapped hybrid app.

Q89. Why has Apple/iOS Safari historically lagged in PWA API support, and what practical constraints does that put on strategy?

ROI: ★★★★☆ Frequency: High

Short Answer

Apple has been the slowest major browser vendor to adopt several PWA-relevant APIs - Background Sync and Periodic Background Sync remain unimplemented, push notifications only arrived relatively recently (and initially only for installed, home-screen PWAs, not regular Safari tabs), and manifest support has trailed Chromium's in completeness (Q37). The commonly cited (though not officially confirmed by Apple) motivation is that a fully-capable PWA ecosystem is somewhat in tension with the App Store's role as the primary, revenue-generating distribution and review gate for iOS apps - a PWA that can do everything a native app can, installed with no App Store review or revenue share at all, is a different competitive dynamic than one still meaningfully behind native in capability.

Practically, this means any cross-platform PWA strategy has to plan for a real, structural capability floor on iOS specifically, not just "slightly worse" - features like Periodic Background Sync simply cannot be relied on for iOS users at all, push notification UX needs iOS-specific handling and expectations, and "add to home screen" is manual with no beforeinstallprompt equivalent (Q37). Teams targeting a meaningful iOS user base with features that depend on the missing APIs often end up needing a native or React Native companion specifically to cover the iOS gap, even if the PWA is sufficient everywhere else.

Interview Gold Point

Framing the iOS gap as a real strategic planning constraint - not just a technical footnote - and naming that it can be the deciding factor pushing a team toward a native/React Native companion app specifically for iOS, shows you'd actually factor this into a real product decision.

Q90. How do you decide whether an app needs native features badly enough to justify wrapping a PWA with Capacitor/Cordova?

ROI: ★★★☆☆ Frequency: Medium

Short Answer

Capacitor (the modern, actively maintained choice; Cordova is largely legacy at this point) wraps your existing web app in a native shell and, critically, exposes a plugin bridge to real native APIs the open web platform doesn't have at all - full Bluetooth, native biometric auth, background geolocation, native share sheets, deep OS notification customization - while still letting you write the actual app logic once, in your existing web codebase. The decision test is specific and mechanical, not a vibe: list the exact native capabilities the product genuinely needs (not "might be nice"), check each one against what the current PWA/web-platform APIs already cover adequately (Q87's table), and if what's left over is a small, well-defined set of gaps, Capacitor plugins covering exactly those gaps is usually cheaper than either accepting the limitation or committing to a full separate native/React Native codebase.

The trade-off to name honestly: you gain the missing native capabilities, but you also take on real native-app maintenance overhead you didn't have as a pure web deploy - App Store review cycles for the wrapper (even though the web content updates instantly, plugin/permission changes still require resubmission), platform-specific bugs in the bridge layer, and two more build targets to keep working. It's the right move for "we need three or four specific native capabilities," and the wrong move if the actual gap list turns out to be extensive enough that you're really building a native app with extra steps.

Interview Gold Point

Proposing a concrete decision process - enumerate needed capabilities, check against what the web platform already covers, size the remaining gap - rather than a general "it depends" is what turns this into a strong, structured answer instead of a vague trade-off discussion.

Q91. What are the real discoverability and distribution differences between App Store search/ASO and web SEO, and how do they change growth strategy?

ROI: ★★★☆☆ Frequency: Medium

Short Answer

These are genuinely different growth channels with different mechanics, not just "two ways to get found." App Store Optimization (ASO) is a closed, ranked marketplace - users specifically go there intending to install something, search terms and keyword-stuffed metadata matter, ratings/reviews are a hard visible ranking and trust signal, and a well-optimized listing can drive install volume with comparatively little content marketing. Web SEO is open and content-driven - discovery happens through Google/Bing indexing actual page content, backlinks, and topical authority, which rewards a completely different kind of ongoing investment (content, structured data, page speed) and reaches users who weren't necessarily looking to "install" anything at all, often converting browsers into installs only after they've already found genuinely useful content.

The strategic upshot: a PWA-first product's growth loop tends to look like organic/content-driven traffic that gradually converts a fraction of engaged visitors into installs (a much lower-friction, lower-commitment funnel than requiring an App Store visit up front), while a store-distributed app's growth loop leans harder on ASO, paid store placement, and word-of-mouth "go download the app" referrals. Products that genuinely benefit from both audiences often run a PWA as the top-of-funnel, low-friction default and treat any native/TWA store presence (Q88) as a second, complementary channel rather than a replacement.

Common Mistake

Assuming "we shipped a PWA, so we don't need to think about store presence at all" or the reverse. The two channels reach genuinely different user intents and are complementary for most consumer products, not mutually exclusive strategies.

Q92. How do emerging web APIs - File System Access, Web Bluetooth, Web NFC - change this tradeoff, and what's their real browser-support reality?

ROI: ★★★☆☆ Frequency: Medium

Short Answer

These APIs are steadily narrowing the capability gap from Q87, but each comes with real, current-day caveats that matter for a production decision. The File System Access API (window.showOpenFilePicker() - real read/write access to the local filesystem with user permission, not just an <input type="file"> upload) is genuinely useful for PWAs that feel like desktop productivity tools, but is Chromium-only - no Safari or Firefox support at all, so any dependency on it needs a fallback to traditional file upload/download for those browsers. Web Bluetooth lets a page pair with and communicate with real Bluetooth Low Energy devices directly, which is powerful for IoT/hardware-adjacent products, but is also Chromium-only and entirely unsupported on iOS (Apple has stated no plans to implement it, citing security/privacy concerns similar to the reasoning behind their broader PWA API caution from Q89). Web NFC (tap-to-read/write NFC tags) is narrower still - Chromium on Android only, nothing on desktop or iOS at all.

The practical implication: these APIs are real and useful where they're supported, but none of them are "web platform now, universally available" the way Cache API or IndexedDB are - each one needs a genuine feature-detection-and-fallback strategy, and a product whose core functionality depends entirely on one of these (rather than being enhanced by it where available) is choosing to exclude a meaningful chunk of users on Safari/iOS, which circles back to the same platform-fragmentation constraint from Q89.

Interview Gold Point

Being specific about which browsers actually support each API - rather than treating "modern web APIs" as a uniform, always-available category - shows you'd actually check compatibility tables before betting a product's core feature on one of these, not just cite them as evidence "the web is catching up to native."

Q93. When would you specifically recommend a company invest in React Native or native, instead of doubling down on PWA capabilities?

ROI: ★★★★★ Frequency: Very High

Short Answer

This is the synthesis question the whole section builds toward, and the strongest answers give a short, specific checklist rather than a philosophical essay. Recommend React Native/native when: the product's core value proposition depends on a capability the web platform genuinely can't deliver reliably across both major platforms today (persistent background execution, deep OS widget/live-activity integration, hardware access that's Chromium-only or entirely unsupported per Q92); the target audience is disproportionately iOS, where the PWA capability floor is structurally lower (Q89), and the missing pieces are ones the product actually needs, not just nice-to-haves; App Store/Play Store presence is itself a business requirement (enterprise procurement often mandates it, or the product category's users simply expect and search for a store listing); or the team already has meaningful React Native/native expertise and the cross-platform-web savings wouldn't offset the cost of the team learning a materially different architecture anyway.

Conversely, stick with and invest further in a PWA when reach, low install friction, and instant update velocity matter more than the specific missing capabilities, when the team is web-native and would pay real "second stack" tax adopting React Native, or when the product is genuinely content/workflow-centric rather than hardware/background-execution-centric. The honest answer to "PWA or native" is almost never "PWA is inherently worse" - it's "does this specific product's requirements list include something on the real capability-gap list, and does that gap matter enough to justify a second codebase and its ongoing cost."

Interview Gold Point

Giving a short, concrete decision checklist rather than restating "it depends on the tradeoffs" is exactly what turns this into a senior-level closing answer - it shows you'd actually make this call, with real criteria, rather than just being able to list both sides.

Q94. How would you architect a system to share business logic between a PWA and a React Native app, minimizing duplicate work?

ROI: ★★★★☆ Frequency: High

Short Answer

The practical answer is extracting everything that isn't fundamentally about rendering into a shared, platform-agnostic package - API client code and data-fetching hooks (a TanStack Query setup with the same query keys/functions works essentially unchanged on both platforms), domain/business logic (validation rules, pricing calculations, permission checks - anything expressible as pure functions with no DOM or React Native primitive dependencies), state management (a Zustand or Redux store's logic is platform-agnostic by construction; only the components subscribing to it differ), and type definitions/schemas (a shared Zod schema validating API responses on both platforms guarantees they agree on shape). This typically lives in a monorepo (Turborepo/Nx) as an internal @app/core package that both the web PWA and the React Native app depend on.

What deliberately does not get shared: actual rendering components, since React DOM and React Native use fundamentally different primitives (<div> versus <View>) - trying to force shared UI components across both (beyond a thin subset using something like react-native-web, which has its own real trade-offs and limitations) usually costs more in abstraction complexity than it saves. Platform-specific concerns - the service worker/caching layer entirely (meaningless in React Native), versus React Native's own native module bridge and offline storage choices - are inherently platform-specific and shouldn't be forced into the shared package at all.
