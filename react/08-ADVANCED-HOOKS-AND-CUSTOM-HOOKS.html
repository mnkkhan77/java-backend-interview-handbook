SECTION 1 - CUSTOM HOOKS

Q1. What actually makes something a "custom hook"? What are the rules and conventions?

ROI: ★★★★★ Frequency: Extremely High

Short Answer

A custom hook is just a JavaScript function whose name starts with use and that calls one or more other hooks. There is no special API — it is a naming convention that lets React's linter and runtime enforce the Rules of Hooks. It exists to extract and reuse stateful logic, not markup. Two components using the same custom hook share the logic but each gets its own isolated state.

Detailed Answer

Three things define a custom hook:

  • Naming: it must start with use (e.g. useLocalStorage). This is not cosmetic — the eslint-plugin-react-hooks linter and React DevTools use the prefix to know that the Rules of Hooks apply. A function named getData that calls useState will not be linted correctly and will confuse readers.
  • It calls hooks: if a function never calls a built-in hook (or another custom hook), it is a plain utility, not a hook, and should not be prefixed with use.
  • It obeys the Rules of Hooks: called only at the top level of a component or another hook, never inside loops, conditions, or nested functions, and only from React function components or other hooks.

The critical mental model: state is not shared between components that use the same hook — only logic is. Each call to a custom hook is a fully isolated instance. Every useState and useEffect inside runs independently per calling component. This is the key difference from a module-level singleton or a React context.

A custom hook can return anything: a single value, a tuple (array) like useState does, or an object. Tuples are ergonomic when the consumer wants to rename values freely (const [x, setX] = useToggle()); objects are better when you return many values and want named access without positional coupling.

Code Example

// A minimal custom hook: extracts stateful logic, returns a tuple.
import { useState, useCallback } from "react";

function useCounter(initial = 0) {
  const [count, setCount] = useState(initial);

  const increment = useCallback(() => setCount((c) => c + 1), []);
  const decrement = useCallback(() => setCount((c) => c - 1), []);
  const reset = useCallback(() => setCount(initial), [initial]);

  return { count, increment, decrement, reset };
}

// Two components -> two independent counters. Logic shared, state is NOT.
function A() {
  const { count, increment } = useCounter();
  return <button onClick={increment}>A: {count}</button>;
}
function B() {
  const { count, increment } = useCounter(10);
  return <button onClick={increment}>B: {count}</button>;
}

Project Example

In a dashboard I extracted a useSelection hook to manage multi-row selection in a table (selected IDs, toggle, select-all, clear). Three different tables reused it. Because state is per-instance, each table tracked its own selection while sharing the exact same battle-tested logic — no copy-paste, and one place to fix bugs.

Senior Engineer Perspective

The interviewer is probing whether you understand that hooks share logic, not state — juniors often think two components calling useCounter will see the same count. A great follow-up trap: "How would you make them share state?" The answer is you must lift the state up into a context or an external store — a custom hook alone cannot do it. Also mention that the use prefix is load-bearing for the linter's exhaustive-deps and rules-of-hooks checks, and that a custom hook should have a single, clear responsibility rather than becoming a grab-bag.

Q2. Build a production-quality useLocalStorage hook. What are the gotchas?

ROI: ★★★★★ Frequency: High

Short Answer

useLocalStorage mirrors useState but persists to localStorage. The gotchas: lazy-initialize from storage (don't read on every render), guard against SSR (no window), handle JSON parse errors, support functional updates, and optionally sync across browser tabs via the storage event.

Detailed Answer

Naive implementations read/parse localStorage on every render and crash during server rendering. A robust version addresses:

  • Lazy init: pass a function to useState so the (synchronous, blocking) storage read runs once.
  • SSR safety: localStorage doesn't exist on the server. Guard with typeof window and fall back to the initial value; the value hydrates on the client.
  • Serialization errors: wrap JSON.parse/stringify in try/catch — corrupt or non-JSON values should not crash the app.
  • Functional updates: support setValue(prev => ...) like useState.
  • Cross-tab sync: listen for the storage event, which fires in other tabs when a key changes, so all tabs stay consistent.

Code Example

import { useState, useEffect, useCallback } from "react";

function useLocalStorage<T>(key: string, initialValue: T) {
  // Lazy initializer: reads storage only once, SSR-safe.
  const readValue = useCallback((): T => {
    if (typeof window === "undefined") return initialValue;
    try {
      const item = window.localStorage.getItem(key);
      return item ? (JSON.parse(item) as T) : initialValue;
    } catch {
      return initialValue;
    }
  }, [key, initialValue]);

  const [storedValue, setStoredValue] = useState<T>(readValue);

  const setValue = useCallback(
    (value: T | ((prev: T) => T)) => {
      setStoredValue((prev) => {
        const next = value instanceof Function ? value(prev) : value;
        try {
          window.localStorage.setItem(key, JSON.stringify(next));
        } catch {
          /* quota exceeded / private mode - ignore */
        }
        return next;
      });
    },
    [key]
  );

  // Keep other tabs in sync.
  useEffect(() => {
    const onStorage = (e: StorageEvent) => {
      if (e.key === key) setStoredValue(readValue());
    };
    window.addEventListener("storage", onStorage);
    return () => window.removeEventListener("storage", onStorage);
  }, [key, readValue]);

  return [storedValue, setValue] as const;
}

Project Example

Used for persisting UI preferences (theme, sidebar collapsed, table page-size). The cross-tab storage listener meant toggling dark mode in one tab instantly updated other open tabs — a small touch reviewers noticed.

Senior Engineer Perspective

Follow-up traps: (1) "What happens during SSR/hydration?" — the server renders the fallback, the client may read a different stored value, causing a hydration mismatch; a common fix is to render the fallback on first paint and update in an effect, or use suppressHydrationWarning deliberately. (2) "The storage event doesn't fire in the tab that made the change" — correct, only in other tabs; to react within the same tab you'd need a custom event or a shared store. (3) A truly robust version uses useSyncExternalStore to subscribe to storage so React 18 concurrent rendering never tears.

Q3. Build useDebounce. What's the difference between debouncing a value and debouncing a callback?

ROI: ★★★★☆ Frequency: High

Short Answer

useDebounce(value, delay) returns a copy of a value that only updates after the input has stopped changing for delay ms — ideal for debouncing derived state like a search query. A debounced callback hook instead returns a stable function that delays invocation. Both use a timer cleared on each change; the difference is whether you debounce state or a side effect.

Detailed Answer

The value approach is simplest and the most common interview answer: store the input in state, then run an effect that sets a delayed timer to copy it into debouncedValue; the effect cleanup clears the pending timer whenever value changes, so only the final value survives. Downstream effects (like a fetch) then depend on debouncedValue.

The callback approach is needed when you must debounce an action (e.g. auto-save) rather than a value. It must keep the latest callback in a ref to avoid stale closures, and return a stable, memoized function whose identity doesn't change every render.

Code Example

import { useState, useEffect, useRef, useCallback } from "react";

// 1) Debounce a VALUE.
function useDebounce<T>(value: T, delay = 300): T {
  const [debounced, setDebounced] = useState(value);
  useEffect(() => {
    const id = setTimeout(() => setDebounced(value), delay);
    return () => clearTimeout(id); // cancel if value changes first
  }, [value, delay]);
  return debounced;
}

// 2) Debounce a CALLBACK (stable identity, latest-callback ref).
function useDebouncedCallback<A extends unknown[]>(
  fn: (...args: A) => void,
  delay = 300
) {
  const fnRef = useRef(fn);
  useEffect(() => { fnRef.current = fn; }, [fn]);

  const timer = useRef<ReturnType<typeof setTimeout>>();
  useEffect(() => () => clearTimeout(timer.current), []);

  return useCallback((...args: A) => {
    clearTimeout(timer.current);
    timer.current = setTimeout(() => fnRef.current(...args), delay);
  }, [delay]);
}

// Usage: search-as-you-type
function Search() {
  const [q, setQ] = useState("");
  const debouncedQ = useDebounce(q, 400);
  useEffect(() => { if (debouncedQ) fetchResults(debouncedQ); }, [debouncedQ]);
  return <input value={q} onChange={(e) => setQ(e.target.value)} />;
}

Senior Engineer Perspective

Traps: forgetting the cleanup clearTimeout (the whole point — without it every keystroke fires). Using a stale callback without a ref, so the debounced function calls an old closure. And in React 18, an interviewer may ask "why not just use useDeferredValue?" — because useDeferredValue reduces render work by letting React deprioritize, but it does not throttle network calls; debouncing is still the right tool for rate-limiting side effects like API requests.

Q4. Build useFetch / useAsync correctly. What race conditions and cleanup issues must you handle?

ROI: ★★★★★ Frequency: High

Short Answer

A data-fetching hook returns { data, error, loading } and refetches when its inputs change. The two must-handle problems are race conditions (an older request resolving after a newer one and overwriting fresh data) and state updates after unmount. Solve both with an AbortController and/or a "stale request" flag in the effect cleanup. In real apps, prefer TanStack Query over hand-rolling this.

Detailed Answer

The classic bug: type "a" then "ab" quickly. Two fetches fire; if the "a" response arrives last, you show results for the wrong query. The fix is to invalidate stale responses. Two common techniques:

  • AbortController: abort the previous request in the effect cleanup. Cleanest, and also cancels the network call.
  • ignore flag: a local boolean set to true in cleanup; the resolved handler checks it before calling setState. This also prevents "can't update state on unmounted component" issues.

You should also reset loading/error on each new request and expose a manual refetch. Below combines both defenses.

Code Example

import { useState, useEffect, useCallback } from "react";

type State<T> = { data: T | null; error: Error | null; loading: boolean };

function useFetch<T>(url: string) {
  const [state, setState] = useState<State<T>>({
    data: null, error: null, loading: true,
  });

  const [nonce, setNonce] = useState(0);
  const refetch = useCallback(() => setNonce((n) => n + 1), []);

  useEffect(() => {
    const controller = new AbortController();
    let ignore = false;
    setState((s) => ({ ...s, loading: true, error: null }));

    fetch(url, { signal: controller.signal })
      .then((r) => {
        if (!r.ok) throw new Error(`HTTP ${r.status}`);
        return r.json();
      })
      .then((data: T) => { if (!ignore) setState({ data, error: null, loading: false }); })
      .catch((error: Error) => {
        if (error.name === "AbortError") return;     // superseded request
        if (!ignore) setState({ data: null, error, loading: false });
      });

    return () => { ignore = true; controller.abort(); }; // cancel on url change/unmount
  }, [url, nonce]);

  return { ...state, refetch };
}

Project Example

An early version of a search page had exactly the "stale response wins" bug reported by QA: fast typers saw results flicker to the wrong query. Adding the AbortController + ignore flag fixed it. We later migrated to TanStack Query for caching, dedup, and background refetch — the hand-rolled hook is fine for interviews and small apps but doesn't scale.

Senior Engineer Perspective

This is a favorite because the naive answer looks right but ships a race condition. Strong candidates volunteer the abort/ignore pattern unprompted and then say "in production I'd reach for TanStack Query / RTK Query rather than reinvent caching, deduplication, retries, and stale-while-revalidate." Mention that in React 19 / RSC, data fetching increasingly moves to Server Components and the new use() hook with Suspense, changing where this logic lives entirely.

Q5. Build usePrevious. Why does it need a ref instead of state?

ROI: ★★★★☆ Frequency: High

Short Answer

usePrevious(value) returns the value from the previous render. It uses a ref updated inside an effect: the effect runs after render, so during render you read the ref's still-old value, and only after commit does it advance. Using state instead would trigger an extra re-render and create an update loop.

Detailed Answer

The trick relies on effect timing. During render, ref.current holds the value stored during the previous commit — that's the "previous" value you return. The effect then writes the current value into the ref after the DOM has committed, ready to be read as "previous" on the next render. Because refs are mutable and don't cause re-renders, this is cheap and loop-free. State would re-render on every update and, if set during render, would loop.

Code Example

import { useRef, useEffect } from "react";

function usePrevious<T>(value: T): T | undefined {
  const ref = useRef<T>();
  useEffect(() => {
    ref.current = value; // runs AFTER render/commit
  }, [value]);
  return ref.current;     // returns value from the previous commit
}

// Usage: detect a change and animate / log a diff.
function Price({ amount }: { amount: number }) {
  const prev = usePrevious(amount);
  const direction = prev == null ? "" : amount > prev ? "up" : "down";
  return <span className={direction}>{amount}</span>;
}

Senior Engineer Perspective

The probe here is your grasp of render vs. commit timing and why refs exist. A good addendum: this returns the previous rendered value, not necessarily the previous distinct value. Also note React's docs suggest that if you're computing something based on a prop change, you can sometimes avoid usePrevious entirely by deriving state during render or using a key — reaching for usePrevious can be a smell that you're syncing when you could derive.

Q6. Build useToggle. What's the subtlety with returning a stable toggle function?

ROI: ★★★☆☆ Frequency: Medium

Short Answer

useToggle returns a boolean and a function that flips it, optionally accepting an explicit value. The subtlety: use the functional updater (setState(v => !v)) so the toggle doesn't depend on the current value, letting you memoize it with an empty dependency array for a stable identity — important when passing it to memoized children.

Code Example

import { useState, useCallback } from "react";

function useToggle(initial = false) {
  const [on, setOn] = useState(initial);

  // Stable identity: no dependency on `on` thanks to functional updater.
  const toggle = useCallback((value?: boolean) => {
    setOn((prev) => (typeof value === "boolean" ? value : !prev));
  }, []);

  return [on, toggle] as const;
}

// Usage
function Modal() {
  const [open, toggle] = useToggle();
  return (
    <>
      <button onClick={() => toggle()}>Toggle</button>
      <button onClick={() => toggle(false)}>Force close</button>
      {open && <Dialog />}
    </>
  );
}

Senior Engineer Perspective

The insight worth stating: because the toggle reads no reactive value directly (it uses the updater form), useCallback([]) is safe and the function reference is stable across renders. That stability matters when the consumer wraps children in React.memo or lists the callback in another effect's deps. A common mistake is useCallback(() => setOn(!on), [on]), which recreates the function every toggle and defeats memoization.

Q7. Build useOnClickOutside and a generic useEventListener.

ROI: ★★★★☆ Frequency: High

Short Answer

useOnClickOutside(ref, handler) fires a callback when a click/touch lands outside a referenced element — the backbone of dropdowns, modals, and popovers. It attaches a document-level listener and checks whether the event target is contained in the ref. A generic useEventListener abstracts adding/removing any listener on any target while always calling the latest handler via a ref.

Detailed Answer

Key details for useOnClickOutside: listen on document, guard against the ref being null, ignore clicks inside the element (ref.current.contains(target)), and typically listen to both mousedown and touchstart (mousedown avoids the "click that opened it also closes it" ordering issue). Keep the handler in a ref so you don't re-subscribe every render.

useEventListener generalizes the "latest handler in a ref, subscribe once" pattern so you never re-attach listeners just because the callback identity changed — a very common source of subtle bugs.

Code Example

import { useEffect, useRef, RefObject } from "react";

// Generic: always calls the latest handler, subscribes once per target/event.
function useEventListener<K extends keyof WindowEventMap>(
  eventName: K,
  handler: (e: WindowEventMap[K]) => void,
  target: Window | Document | HTMLElement = window
) {
  const savedHandler = useRef(handler);
  useEffect(() => { savedHandler.current = handler; }, [handler]);

  useEffect(() => {
    const listener = (e: Event) => savedHandler.current(e as WindowEventMap[K]);
    target.addEventListener(eventName, listener);
    return () => target.removeEventListener(eventName, listener);
  }, [eventName, target]);
}

// Click outside
function useOnClickOutside<T extends HTMLElement>(
  ref: RefObject<T>,
  handler: (e: MouseEvent | TouchEvent) => void
) {
  const savedHandler = useRef(handler);
  useEffect(() => { savedHandler.current = handler; }, [handler]);

  useEffect(() => {
    const listener = (e: MouseEvent | TouchEvent) => {
      const el = ref.current;
      if (!el || el.contains(e.target as Node)) return; // inside -> ignore
      savedHandler.current(e);
    };
    document.addEventListener("mousedown", listener);
    document.addEventListener("touchstart", listener);
    return () => {
      document.removeEventListener("mousedown", listener);
      document.removeEventListener("touchstart", listener);
    };
  }, [ref]);
}

Senior Engineer Perspective

Watch for: (1) using click instead of mousedown, which can immediately close a menu opened by the same click; (2) not storing the handler in a ref, causing constant re-subscription; (3) portals — a dropdown rendered in a portal is outside the ref's DOM subtree, so contains returns false and it closes unexpectedly; you must include the portal node in the check. For accessibility, note that click-outside should be paired with an Escape-key handler and proper focus management.

Q8. Custom hooks vs Higher-Order Components vs Render Props — when do you use each?

ROI: ★★★★☆ Frequency: High

Short Answer

All three share reusable logic. Custom hooks are the modern default: they compose without nesting, avoid wrapper hell, and don't collide on props. HOCs and render props were the pre-hooks patterns and still appear in class components or when you must inject behavior around a component you can't modify. For sharing stateful logic between function components, prefer hooks.

Detailed Answer

PatternHow it shares logicDownsides
Custom hookCall a use* function inside the componentOnly works in function components; can't wrap markup
HOCFunction that takes a component, returns an enhanced oneWrapper hell, prop name collisions, ref forwarding needed, opaque data flow
Render propsPass a function-as-child that receives the shared stateCallback nesting / "pyramid of doom" in JSX, extra re-renders

Hooks solve the two big pain points of HOCs and render props: no extra tree nesting (which broke DevTools readability and caused wrapper hell) and no prop namespace collisions when composing multiple behaviors. You can call ten hooks in one component with zero nesting; ten HOCs create ten wrappers.

HOCs and render props aren't dead: HOCs are still idiomatic for cross-cutting concerns like connect() (legacy Redux) or injecting into class components; render props remain useful in some component APIs (e.g. libraries exposing state via children functions). But new code sharing logic between function components should use hooks.

Code Example

// Same logic, three ways.

// Render prop (older)
<MouseTracker>{({ x, y }) => <p>{x},{y}</p>}</MouseTracker>

// HOC (older)
const WithMouse = withMouse(MyComponent); // injects x/y as props

// Custom hook (modern) - flat, composable, no wrapper
function Component() {
  const { x, y } = useMouse();
  const online = useOnlineStatus();     // compose freely, no nesting
  return <p>{x},{y} {online ? "on" : "off"}</p>;
}

Senior Engineer Perspective

The interviewer wants historical context and judgment. Say hooks replaced these patterns for logic reuse, then note the nuance: hooks can't do everything HOCs/render props did — you can't use a hook to conditionally wrap or replace rendering, and you can't add a hook to a class component. Error boundaries still require class components (or a library) because there's no hook equivalent of componentDidCatch yet. Show you know why hooks won (composition without nesting) rather than just parroting "hooks are better."

Q9. How do you test a custom hook?

ROI: ★★★★☆ Frequency: Medium

Short Answer

Because hooks can only run inside a component, you test them with renderHook from React Testing Library, which mounts a test harness component. Assert on the returned value, drive updates through act(), and use waitFor for async hooks. Prefer testing behavior through the returned API over implementation details.

Code Example

import { renderHook, act, waitFor } from "@testing-library/react";
import { useCounter } from "./useCounter";

test("increments", () => {
  const { result } = renderHook(() => useCounter(0));
  expect(result.current.count).toBe(0);

  act(() => result.current.increment());
  expect(result.current.count).toBe(1);
});

test("re-runs when props change", () => {
  const { result, rerender } = renderHook(
    ({ start }) => useCounter(start),
    { initialProps: { start: 5 } }
  );
  rerender({ start: 10 }); // simulate a prop change
  // ...assert reset behavior
});

Senior Engineer Perspective

Key points: wrap state-changing calls in act() or React warns; use renderHook's wrapper option to supply context providers a hook depends on; and for async hooks (useFetch) mock fetch/MSW and assert loading→data transitions with waitFor. Seniors also note that if a hook is trivial glue you often get more value testing the component that uses it, and that renderHook moved from @testing-library/react-hooks into @testing-library/react itself.

SECTION 2 - LESS-COMMON BUILT-IN HOOKS

Q10. When should you use useReducer over useState, and what reducer patterns matter?

ROI: ★★★★★ Frequency: Extremely High

Short Answer

Reach for useReducer when state is complex — multiple sub-values that update together, next state that depends on previous state, or transitions best described as named actions. It centralizes update logic in a pure reducer function, making state transitions testable and predictable, and lets you pass a stable dispatch down instead of many callbacks.

Detailed Answer

Signals you've outgrown useState:

  • Several pieces of state change together (e.g. loading, data, error).
  • The next state depends on the previous in nontrivial ways.
  • You keep passing many setter callbacks down the tree — one dispatch is cleaner and is stable, so it never breaks memoization.
  • You want to unit-test transitions in isolation — a reducer is a pure function, trivially testable without React.

Useful patterns: model state as a discriminated union of actions with a type; keep reducers pure (no fetching, no mutation — return new objects); use a state machine style (explicit states like idle | loading | success | error) to make impossible states unrepresentable; and combine useReducer with Context to build a lightweight store without Redux.

Code Example

import { useReducer } from "react";

type State =
  | { status: "idle" }
  | { status: "loading" }
  | { status: "success"; data: string[] }
  | { status: "error"; message: string };

type Action =
  | { type: "FETCH" }
  | { type: "SUCCESS"; data: string[] }
  | { type: "FAILURE"; message: string };

function reducer(state: State, action: Action): State {
  switch (action.type) {
    case "FETCH":   return { status: "loading" };
    case "SUCCESS": return { status: "success", data: action.data };
    case "FAILURE": return { status: "error", message: action.message };
    default:        return state;
  }
}

function List() {
  const [state, dispatch] = useReducer(reducer, { status: "idle" });
  // dispatch({ type: "FETCH" }) ... etc. Impossible states can't exist.
  return state.status === "loading" ? <Spinner /> : /* ... */ null;
}

Project Example

A multi-step checkout wizard: step index, per-step form data, validation errors, and submission status all interlock. A single reducer with actions like NEXT_STEP, SET_FIELD, SUBMIT made the flow readable and let us unit-test every transition without rendering. Passing one dispatch to deeply nested inputs avoided prop-drilling a dozen setters.

Senior Engineer Perspective

The strongest answer connects useReducer to state-machine thinking: enumerate valid states so you can't render a spinner and an error at once. Follow-ups: "Is dispatch stable?" — yes, React guarantees a stable identity, so it's safe in deps and great for Context. "reducer vs Redux?" — same mental model, but useReducer is local/component-scoped with no middleware or devtools out of the box; Redux Toolkit adds global store, middleware, and time-travel. "Can a reducer be async?" — no, keep it pure; do effects outside and dispatch the result.

Q11. Explain useImperativeHandle and forwardRef. When is imperative code the right call?

ROI: ★★★★☆ Frequency: Medium

Short Answer

forwardRef lets a parent pass a ref through to a child component; useImperativeHandle lets that child customize what the ref exposes — a curated imperative API (like focus(), scrollToTop()) instead of the raw DOM node. Use it sparingly for genuinely imperative actions React's declarative model can't express cleanly: focus, text selection, media playback, animations, scroll.

Detailed Answer

By default refs only attach to DOM elements. To let a parent hold a ref to a function component, wrap it in forwardRef. But exposing the raw DOM node leaks internals; useImperativeHandle lets you expose only a small, intentional API surface. This keeps the component's contract clean and prevents the parent from doing arbitrary DOM manipulation.

Reserve this for imperative operations that don't fit declarative props: programmatically focusing an input after an error, playing/pausing a <video>, triggering an animation, or resetting an uncontrolled form. If you can express it as state/props, do that instead — imperative handles are an escape hatch.

Note: in React 19, ref can be passed as a normal prop to function components, so forwardRef is being deprecated in favor of reading ref from props directly — but useImperativeHandle remains.

Code Example

import { forwardRef, useImperativeHandle, useRef } from "react";

type FancyInputHandle = { focus: () => void; clear: () => void };

const FancyInput = forwardRef<FancyInputHandle>((props, ref) => {
  const inputRef = useRef<HTMLInputElement>(null);

  useImperativeHandle(ref, () => ({
    focus: () => inputRef.current?.focus(),
    clear: () => { if (inputRef.current) inputRef.current.value = ""; },
  }), []); // expose only focus + clear, not the raw node

  return <input ref={inputRef} {...props} />;
});

function Form() {
  const ref = useRef<FancyInputHandle>(null);
  return (
    <>
      <FancyInput ref={ref} />
      <button onClick={() => ref.current?.focus()}>Focus</button>
    </>
  );
}

Senior Engineer Perspective

Interviewers probe whether you know this is an escape hatch — overusing imperative handles is a smell that you're fighting the declarative model. A good answer names concrete legitimate cases (focus management, media, animations, integrating a non-React library) and stresses exposing a minimal API. Mention the React 19 change (ref-as-prop deprecating forwardRef) to show you're current. Also note the dependency array of useImperativeHandle controls when the handle object is recreated.

Q12. What problem does useId solve? Why not just use a counter or Math.random?

ROI: ★★★☆☆ Frequency: Medium

Short Answer

useId generates a unique, stable ID that is consistent between server and client rendering, avoiding hydration mismatches. Its purpose is wiring up accessibility attributes (htmlFor/id, aria-describedby), not keys in lists. A random ID or a module counter would differ between server and client and break hydration.

Detailed Answer

In SSR, HTML is generated on the server then hydrated on the client. If you generate IDs with Math.random() or an incrementing counter, the server and client produce different values, causing a hydration mismatch warning and broken aria/label associations. useId produces the same deterministic ID on both sides by deriving it from the component's position in the tree.

Use it to connect labels and inputs, or an input to its error message. If you need several related IDs, call useId once and append suffixes. Do not use it as a React key in lists — keys should come from your data.

Code Example

import { useId } from "react";

function Field({ label }: { label: string }) {
  const id = useId();
  return (
    <div>
      <label htmlFor={id}>{label}</label>
      <input id={id} aria-describedby={`${id}-hint`} />
      <p id={`${id}-hint`}>Must be unique</p>
    </div>
  );
}

Senior Engineer Perspective

The trap is candidates who say "for list keys" — wrong; it's for SSR-safe accessibility IDs. Strong answers explain the hydration-mismatch root cause and mention that useId returns a string containing colons (e.g. :r0:) which is valid in HTML id but breaks document.querySelector/CSS selectors — a real gotcha. It replaced brittle patterns and libraries people used pre-React-18.

SECTION 3 - CONCURRENT & EXTERNAL-STORE HOOKS

Q13. Explain useTransition and useDeferredValue. How do they differ?

ROI: ★★★★★ Frequency: High

Short Answer

Both are React 18 concurrent features that keep the UI responsive by marking work as low priority. useTransition lets you mark a state update as non-urgent via startTransition, and gives you an isPending flag. useDeferredValue takes a value and returns a deferred copy that lags behind during heavy renders. Use useTransition when you own the update; useDeferredValue when you only receive a value (e.g. a prop).

Detailed Answer

Concurrent rendering lets React interrupt a low-priority render to handle urgent updates (like typing). Without it, filtering a huge list on every keystroke blocks the input. Both hooks solve the same class of problem — an urgent update (typing) and an expensive dependent render (a giant filtered list) — by deprioritizing the expensive part so the input stays snappy.

AspectuseTransitionuseDeferredValue
You wrapThe state update (startTransition(() => setX(...)))The value (const d = useDeferredValue(x))
Gives youisPending flag + startTransitionA lagging copy of the value
Best whenYou control the setState callYou only receive the value (prop) and can't touch the setter

startTransition can also be imported standalone (not from the hook) when you don't need isPending. In React 19, transitions can wrap async functions and integrate with actions.

Code Example

import { useState, useTransition, useDeferredValue, useMemo } from "react";

// useTransition: you own the setState
function Search({ items }: { items: string[] }) {
  const [query, setQuery] = useState("");
  const [results, setResults] = useState(items);
  const [isPending, startTransition] = useTransition();

  const onChange = (e: React.ChangeEvent<HTMLInputElement>) => {
    setQuery(e.target.value);                 // urgent: input updates now
    startTransition(() => {                    // non-urgent: heavy filter
      setResults(items.filter((i) => i.includes(e.target.value)));
    });
  };
  return <>{isPending && <Spinner />}<input value={query} onChange={onChange} /></>;
}

// useDeferredValue: you only have the value
function List({ query }: { query: string }) {
  const deferred = useDeferredValue(query);
  const items = useMemo(() => expensiveFilter(deferred), [deferred]);
  return <Rows items={items} />;
}

Senior Engineer Perspective

Common misconception: these debounce or throttle. They don't — there's no timer; React interrupts and re-prioritizes rendering. Debounce delays work by time; transitions delay by priority and can be interrupted. Another nuance: they only help with expensive rendering, not expensive network calls — you'd still debounce the fetch. And the deferred/transition work must be pure React rendering for React to interrupt it. Mentioning that both need React 18's concurrent root (createRoot) shows depth.

Q14. Why does useSyncExternalStore exist? What is "tearing"?

ROI: ★★★★☆ Frequency: Medium

Short Answer

useSyncExternalStore is the correct, concurrent-safe way to subscribe a component to an external (non-React) data source — a browser API, a Redux-like store, or a global event source. It exists because React 18's concurrent rendering can pause and resume, and a naive useEffect-based subscription can read inconsistent snapshots mid-render, producing "tearing": different parts of the UI showing different values of the same store in one commit.

Detailed Answer

Before React 18, state stores subscribed via useState + useEffect. With concurrent rendering, React can render a component, pause, let an external value change, then resume — meaning two components could read the store at different moments during one render pass and disagree. That inconsistency is tearing. useSyncExternalStore forces a synchronous, consistent read so React always renders one coherent snapshot.

It takes three arguments: subscribe (register a callback that re-renders on change; must return an unsubscribe), getSnapshot (return the current value synchronously — must return a cached, stable reference for equal state, or you loop), and an optional getServerSnapshot for SSR. Library authors (Redux, Zustand, Jotai) use it internally; app code mostly uses it for browser APIs like online status, media queries, or the URL.

Code Example

import { useSyncExternalStore } from "react";

// Subscribe to browser online/offline state - tear-free.
function useOnlineStatus() {
  return useSyncExternalStore(
    (callback) => {
      window.addEventListener("online", callback);
      window.addEventListener("offline", callback);
      return () => {
        window.removeEventListener("online", callback);
        window.removeEventListener("offline", callback);
      };
    },
    () => navigator.onLine,   // client snapshot
    () => true                // server snapshot (assume online in SSR)
  );
}

Senior Engineer Perspective

The killer follow-up: "Why not just useState + useEffect?" — because that works in blocking mode but can tear under concurrent features and misses SSR consistency. The subtle bug candidates hit: getSnapshot must return a referentially stable value for unchanged state; returning a fresh object each call causes an infinite render loop. Mention that libraries expose useSyncExternalStoreWithSelector for selecting a slice with a custom equality function. Knowing this hook signals you understand why React 18 concurrency needed a new subscription primitive.

Q15. Build useMediaQuery. Why is useSyncExternalStore a better fit than useEffect here?

ROI: ★★★★☆ Frequency: Medium

Short Answer

useMediaQuery("(min-width: 768px)") returns whether the query currently matches and updates on change. The clean implementation uses useSyncExternalStore: subscribe attaches a change listener on a MediaQueryList, and getSnapshot reads .matches. This is tear-free and handles SSR via a server snapshot, unlike an effect-based version that flashes the wrong value on first render.

Code Example

import { useSyncExternalStore, useCallback } from "react";

function useMediaQuery(query: string): boolean {
  const subscribe = useCallback((callback: () => void) => {
    const mql = window.matchMedia(query);
    mql.addEventListener("change", callback);
    return () => mql.removeEventListener("change", callback);
  }, [query]);

  const getSnapshot = () => window.matchMedia(query).matches;
  const getServerSnapshot = () => false; // no matchMedia on the server

  return useSyncExternalStore(subscribe, getSnapshot, getServerSnapshot);
}

// Usage
function Nav() {
  const isDesktop = useMediaQuery("(min-width: 768px)");
  return isDesktop ? <DesktopNav /> : <MobileNav />;
}

Senior Engineer Perspective

A useEffect version reads matchMedia only after mount, so the first paint uses a default and then flips — causing a visible flash and, in SSR, a hydration mismatch. useSyncExternalStore reads synchronously and provides a server snapshot, avoiding both. Gotchas to mention: older Safari used addListener/removeListener instead of addEventListener; and provide a sensible server default since layout decisions based on it will render server-side.

SECTION 4 - REACT 19 HOOKS

Q16. What are the new React 19 hooks: use(), useOptimistic, and useActionState?

ROI: ★★★★☆ Frequency: High

Short Answer

React 19 adds primitives centered on async data and form Actions. use() reads a promise or context during render and integrates with Suspense — and uniquely may be called conditionally. useOptimistic shows an immediate optimistic UI state while an async action is in flight, then reconciles. useActionState (formerly useFormState) manages the state, pending status, and result of a form Action.

Detailed Answer

use() — reads the value of a resource. Pass it a promise and React suspends until it resolves (works with Suspense/RSC); pass it a Context and it reads that context. Unlike other hooks, use() can be called inside conditions and loops, because it isn't tied to a fixed hook slot the same way.

useOptimistic — lets you render a temporary optimistic value immediately (e.g. show a sent message before the server confirms). React automatically reverts to the real state when the action completes or errors, so you don't manually roll back.

useActionState — wraps an async "action" function and returns [state, formAction, isPending]. Wire formAction to a <form action={...}>; React tracks the pending state and the returned result (e.g. validation errors) without manual useState. Complements useFormStatus for reading pending status from child components.

Code Example

import { use, useOptimistic, useActionState } from "react";

// use(): read a promise with Suspense
function Comments({ promise }: { promise: Promise<string[]> }) {
  const comments = use(promise); // suspends until resolved
  return <ul>{comments.map((c) => <li key={c}>{c}</li>)}</ul>;
}

// useActionState + useOptimistic: form action with instant feedback
function MessageForm({ send }: { send: (text: string) => Promise<void> }) {
  const [messages, setMessages] = useState<string[]>([]);
  const [optimistic, addOptimistic] = useOptimistic(
    messages,
    (state, newMsg: string) => [...state, newMsg]
  );

  const [, formAction, isPending] = useActionState(
    async (_prev: unknown, formData: FormData) => {
      const text = formData.get("text") as string;
      addOptimistic(text);        // show immediately
      await send(text);           // then persist
      setMessages((m) => [...m, text]);
      return null;
    },
    null
  );

  return (
    <form action={formAction}>
      {optimistic.map((m) => <p key={m}>{m}</p>)}
      <input name="text" />
      <button disabled={isPending}>Send</button>
    </form>
  );
}

Senior Engineer Perspective

Show you're tracking the current React landscape: these hooks pair with Server Components and Server Actions and represent React's shift toward first-class async and forms. Nuances worth naming: use() is the only hook allowed inside conditionals; you should not create the promise inline in a Client Component render (it creates a new promise each render) — the promise should come from a cached source or a Server Component. useActionState was renamed from useFormState and moved out of react-dom into react. Optimistic state auto-reverts on completion, so don't hand-roll rollback logic.

Q17. What are the three most common bugs people ship in custom hooks?

ROI: ★★★★☆ Frequency: High

Short Answer

(1) Stale closures — a hook captures an old value because a callback or effect isn't re-created and doesn't use a ref or the updater form. (2) Missing effect cleanup — timers, listeners, and subscriptions leak or cause race conditions/updates after unmount. (3) Unstable return values — returning a new object/array/function identity every render, breaking consumers' memoization or triggering infinite effect loops.

Detailed Answer

  • Stale closures: an event handler stored once reads the value from the render it was created in. Fixes: use the functional updater (setX(prev => ...)), keep the latest callback in a ref, or list correct dependencies.
  • Missing cleanup: every setInterval, addEventListener, subscription, or in-flight request needs teardown in the effect's return function. Without it you get memory leaks, duplicate listeners, and race conditions — and Strict Mode's double-invoke in dev surfaces these.
  • Unstable identities: returning { data, refetch } where refetch is a fresh function each render forces consumers to re-render or re-run effects that depend on it. Wrap functions in useCallback and derived objects in useMemo where identity matters.

Code Example

// BUG: stale closure + no cleanup
function useTickBad(onTick: () => void) {
  useEffect(() => {
    setInterval(() => onTick(), 1000); // captures first onTick, never cleared
  }, []);                              // missing dep + no cleanup
}

// FIX: latest callback via ref, proper cleanup
function useInterval(callback: () => void, delay: number) {
  const saved = useRef(callback);
  useEffect(() => { saved.current = callback; }, [callback]);
  useEffect(() => {
    const id = setInterval(() => saved.current(), delay);
    return () => clearInterval(id); // cleanup!
  }, [delay]);
}

Senior Engineer Perspective

This question tests debugging instincts. Tie the answers together: React 18 Strict Mode intentionally mounts, unmounts, and remounts effects in development precisely to catch missing cleanup — if your hook breaks under Strict Mode, it has a latent bug. Mention eslint-plugin-react-hooks' exhaustive-deps rule as your first line of defense against stale closures, and that "just disable the lint rule" is almost always the wrong fix. Dan Abramov's "useInterval" pattern (latest-callback ref) is the canonical solution worth naming.
