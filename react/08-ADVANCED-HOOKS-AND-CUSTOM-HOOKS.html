SECTION 1 - CUSTOM HOOKS

Q1. What actually makes something a "custom hook"? What are the rules and conventions?

ROI: ★★★★★ Frequency: Extremely High

Short Answer

A custom hook is just a JavaScript function whose name starts with use and that calls one or more other hooks. There is no special API — it is a naming convention that lets React's linter and runtime enforce the Rules of Hooks. It exists to extract and reuse stateful logic, not markup. Two components using the same custom hook share the logic but each gets its own isolated state.

Detailed Answer

Three things define a custom hook:

  • Naming: it must start with use (e.g. useLocalStorage). This is not cosmetic — the eslint-plugin-react-hooks linter and React DevTools use the prefix to know that the Rules of Hooks apply. A function named getData that calls useState will not be linted correctly and will confuse readers.
  • It calls hooks: if a function never calls a built-in hook (or another custom hook), it is a plain utility, not a hook, and should not be prefixed with use.
  • It obeys the Rules of Hooks: called only at the top level of a component or another hook, never inside loops, conditions, or nested functions, and only from React function components or other hooks.

The critical mental model: state is not shared between components that use the same hook — only logic is. Each call to a custom hook is a fully isolated instance. Every useState and useEffect inside runs independently per calling component. This is the key difference from a module-level singleton or a React context.

A custom hook can return anything: a single value, a tuple (array) like useState does, or an object. Tuples are ergonomic when the consumer wants to rename values freely (const [x, setX] = useToggle()); objects are better when you return many values and want named access without positional coupling.

Code Example

// A minimal custom hook: extracts stateful logic, returns a tuple.
import { useState, useCallback } from "react";

function useCounter(initial = 0) {
  const [count, setCount] = useState(initial);

  const increment = useCallback(() => setCount((c) => c + 1), []);
  const decrement = useCallback(() => setCount((c) => c - 1), []);
  const reset = useCallback(() => setCount(initial), [initial]);

  return { count, increment, decrement, reset };
}

// Two components -> two independent counters. Logic shared, state is NOT.
function A() {
  const { count, increment } = useCounter();
  return <button onClick={increment}>A: {count}</button>;
}
function B() {
  const { count, increment } = useCounter(10);
  return <button onClick={increment}>B: {count}</button>;
}

Project Example

In a dashboard I extracted a useSelection hook to manage multi-row selection in a table (selected IDs, toggle, select-all, clear). Three different tables reused it. Because state is per-instance, each table tracked its own selection while sharing the exact same battle-tested logic — no copy-paste, and one place to fix bugs.

Senior Engineer Perspective

The interviewer is probing whether you understand that hooks share logic, not state — juniors often think two components calling useCounter will see the same count. A great follow-up trap: "How would you make them share state?" The answer is you must lift the state up into a context or an external store — a custom hook alone cannot do it. Also mention that the use prefix is load-bearing for the linter's exhaustive-deps and rules-of-hooks checks, and that a custom hook should have a single, clear responsibility rather than becoming a grab-bag.

Q2. Build a production-quality useLocalStorage hook. What are the gotchas?

ROI: ★★★★★ Frequency: High

Short Answer

useLocalStorage mirrors useState but persists to localStorage. The gotchas: lazy-initialize from storage (don't read on every render), guard against SSR (no window), handle JSON parse errors, support functional updates, and optionally sync across browser tabs via the storage event.

Detailed Answer

Naive implementations read/parse localStorage on every render and crash during server rendering. A robust version addresses:

  • Lazy init: pass a function to useState so the (synchronous, blocking) storage read runs once.
  • SSR safety: localStorage doesn't exist on the server. Guard with typeof window and fall back to the initial value; the value hydrates on the client.
  • Serialization errors: wrap JSON.parse/stringify in try/catch — corrupt or non-JSON values should not crash the app.
  • Functional updates: support setValue(prev => ...) like useState.
  • Cross-tab sync: listen for the storage event, which fires in other tabs when a key changes, so all tabs stay consistent.

Code Example

import { useState, useEffect, useCallback } from "react";

function useLocalStorage<T>(key: string, initialValue: T) {
  // Lazy initializer: reads storage only once, SSR-safe.
  const readValue = useCallback((): T => {
    if (typeof window === "undefined") return initialValue;
    try {
      const item = window.localStorage.getItem(key);
      return item ? (JSON.parse(item) as T) : initialValue;
    } catch {
      return initialValue;
    }
  }, [key, initialValue]);

  const [storedValue, setStoredValue] = useState<T>(readValue);

  const setValue = useCallback(
    (value: T | ((prev: T) => T)) => {
      setStoredValue((prev) => {
        const next = value instanceof Function ? value(prev) : value;
        try {
          window.localStorage.setItem(key, JSON.stringify(next));
        } catch {
          /* quota exceeded / private mode - ignore */
        }
        return next;
      });
    },
    [key]
  );

  // Keep other tabs in sync.
  useEffect(() => {
    const onStorage = (e: StorageEvent) => {
      if (e.key === key) setStoredValue(readValue());
    };
    window.addEventListener("storage", onStorage);
    return () => window.removeEventListener("storage", onStorage);
  }, [key, readValue]);

  return [storedValue, setValue] as const;
}

Project Example

Used for persisting UI preferences (theme, sidebar collapsed, table page-size). The cross-tab storage listener meant toggling dark mode in one tab instantly updated other open tabs — a small touch reviewers noticed.

Senior Engineer Perspective

Follow-up traps: (1) "What happens during SSR/hydration?" — the server renders the fallback, the client may read a different stored value, causing a hydration mismatch; a common fix is to render the fallback on first paint and update in an effect, or use suppressHydrationWarning deliberately. (2) "The storage event doesn't fire in the tab that made the change" — correct, only in other tabs; to react within the same tab you'd need a custom event or a shared store. (3) A truly robust version uses useSyncExternalStore to subscribe to storage so React 18 concurrent rendering never tears.

Q3. Build useDebounce. What's the difference between debouncing a value and debouncing a callback?

ROI: ★★★★☆ Frequency: High

Short Answer

useDebounce(value, delay) returns a copy of a value that only updates after the input has stopped changing for delay ms — ideal for debouncing derived state like a search query. A debounced callback hook instead returns a stable function that delays invocation. Both use a timer cleared on each change; the difference is whether you debounce state or a side effect.

Detailed Answer

The value approach is simplest and the most common interview answer: store the input in state, then run an effect that sets a delayed timer to copy it into debouncedValue; the effect cleanup clears the pending timer whenever value changes, so only the final value survives. Downstream effects (like a fetch) then depend on debouncedValue.

The callback approach is needed when you must debounce an action (e.g. auto-save) rather than a value. It must keep the latest callback in a ref to avoid stale closures, and return a stable, memoized function whose identity doesn't change every render.

Code Example

import { useState, useEffect, useRef, useCallback } from "react";

// 1) Debounce a VALUE.
function useDebounce<T>(value: T, delay = 300): T {
  const [debounced, setDebounced] = useState(value);
  useEffect(() => {
    const id = setTimeout(() => setDebounced(value), delay);
    return () => clearTimeout(id); // cancel if value changes first
  }, [value, delay]);
  return debounced;
}

// 2) Debounce a CALLBACK (stable identity, latest-callback ref).
function useDebouncedCallback<A extends unknown[]>(
  fn: (...args: A) => void,
  delay = 300
) {
  const fnRef = useRef(fn);
  useEffect(() => { fnRef.current = fn; }, [fn]);

  const timer = useRef<ReturnType<typeof setTimeout>>();
  useEffect(() => () => clearTimeout(timer.current), []);

  return useCallback((...args: A) => {
    clearTimeout(timer.current);
    timer.current = setTimeout(() => fnRef.current(...args), delay);
  }, [delay]);
}

// Usage: search-as-you-type
function Search() {
  const [q, setQ] = useState("");
  const debouncedQ = useDebounce(q, 400);
  useEffect(() => { if (debouncedQ) fetchResults(debouncedQ); }, [debouncedQ]);
  return <input value={q} onChange={(e) => setQ(e.target.value)} />;
}

Senior Engineer Perspective

Traps: forgetting the cleanup clearTimeout (the whole point — without it every keystroke fires). Using a stale callback without a ref, so the debounced function calls an old closure. And in React 18, an interviewer may ask "why not just use useDeferredValue?" — because useDeferredValue reduces render work by letting React deprioritize, but it does not throttle network calls; debouncing is still the right tool for rate-limiting side effects like API requests.

Q4. Build useFetch / useAsync correctly. What race conditions and cleanup issues must you handle?

ROI: ★★★★★ Frequency: High

Short Answer

A data-fetching hook returns { data, error, loading } and refetches when its inputs change. The two must-handle problems are race conditions (an older request resolving after a newer one and overwriting fresh data) and state updates after unmount. Solve both with an AbortController and/or a "stale request" flag in the effect cleanup. In real apps, prefer TanStack Query over hand-rolling this.

Detailed Answer

The classic bug: type "a" then "ab" quickly. Two fetches fire; if the "a" response arrives last, you show results for the wrong query. The fix is to invalidate stale responses. Two common techniques:

  • AbortController: abort the previous request in the effect cleanup. Cleanest, and also cancels the network call.
  • ignore flag: a local boolean set to true in cleanup; the resolved handler checks it before calling setState. This also prevents "can't update state on unmounted component" issues.

You should also reset loading/error on each new request and expose a manual refetch. Below combines both defenses.

Code Example

import { useState, useEffect, useCallback } from "react";

type State<T> = { data: T | null; error: Error | null; loading: boolean };

function useFetch<T>(url: string) {
  const [state, setState] = useState<State<T>>({
    data: null, error: null, loading: true,
  });

  const [nonce, setNonce] = useState(0);
  const refetch = useCallback(() => setNonce((n) => n + 1), []);

  useEffect(() => {
    const controller = new AbortController();
    let ignore = false;
    setState((s) => ({ ...s, loading: true, error: null }));

    fetch(url, { signal: controller.signal })
      .then((r) => {
        if (!r.ok) throw new Error(`HTTP ${r.status}`);
        return r.json();
      })
      .then((data: T) => { if (!ignore) setState({ data, error: null, loading: false }); })
      .catch((error: Error) => {
        if (error.name === "AbortError") return;     // superseded request
        if (!ignore) setState({ data: null, error, loading: false });
      });

    return () => { ignore = true; controller.abort(); }; // cancel on url change/unmount
  }, [url, nonce]);

  return { ...state, refetch };
}

Project Example

An early version of a search page had exactly the "stale response wins" bug reported by QA: fast typers saw results flicker to the wrong query. Adding the AbortController + ignore flag fixed it. We later migrated to TanStack Query for caching, dedup, and background refetch — the hand-rolled hook is fine for interviews and small apps but doesn't scale.

Senior Engineer Perspective

This is a favorite because the naive answer looks right but ships a race condition. Strong candidates volunteer the abort/ignore pattern unprompted and then say "in production I'd reach for TanStack Query / RTK Query rather than reinvent caching, deduplication, retries, and stale-while-revalidate." Mention that in React 19 / RSC, data fetching increasingly moves to Server Components and the new use() hook with Suspense, changing where this logic lives entirely.

Q5. Build usePrevious. Why does it need a ref instead of state?

ROI: ★★★★☆ Frequency: High

Short Answer

usePrevious(value) returns the value from the previous render. It uses a ref updated inside an effect: the effect runs after render, so during render you read the ref's still-old value, and only after commit does it advance. Using state instead would trigger an extra re-render and create an update loop.

Detailed Answer

The trick relies on effect timing. During render, ref.current holds the value stored during the previous commit — that's the "previous" value you return. The effect then writes the current value into the ref after the DOM has committed, ready to be read as "previous" on the next render. Because refs are mutable and don't cause re-renders, this is cheap and loop-free. State would re-render on every update and, if set during render, would loop.

Code Example

import { useRef, useEffect } from "react";

function usePrevious<T>(value: T): T | undefined {
  const ref = useRef<T>();
  useEffect(() => {
    ref.current = value; // runs AFTER render/commit
  }, [value]);
  return ref.current;     // returns value from the previous commit
}

// Usage: detect a change and animate / log a diff.
function Price({ amount }: { amount: number }) {
  const prev = usePrevious(amount);
  const direction = prev == null ? "" : amount > prev ? "up" : "down";
  return <span className={direction}>{amount}</span>;
}

Senior Engineer Perspective

The probe here is your grasp of render vs. commit timing and why refs exist. A good addendum: this returns the previous rendered value, not necessarily the previous distinct value. Also note React's docs suggest that if you're computing something based on a prop change, you can sometimes avoid usePrevious entirely by deriving state during render or using a key — reaching for usePrevious can be a smell that you're syncing when you could derive.

Q6. Build useToggle. What's the subtlety with returning a stable toggle function?

ROI: ★★★☆☆ Frequency: Medium

Short Answer

useToggle returns a boolean and a function that flips it, optionally accepting an explicit value. The subtlety: use the functional updater (setState(v => !v)) so the toggle doesn't depend on the current value, letting you memoize it with an empty dependency array for a stable identity — important when passing it to memoized children.

Code Example

import { useState, useCallback } from "react";

function useToggle(initial = false) {
  const [on, setOn] = useState(initial);

  // Stable identity: no dependency on `on` thanks to functional updater.
  const toggle = useCallback((value?: boolean) => {
    setOn((prev) => (typeof value === "boolean" ? value : !prev));
  }, []);

  return [on, toggle] as const;
}

// Usage
function Modal() {
  const [open, toggle] = useToggle();
  return (
    <>
      <button onClick={() => toggle()}>Toggle</button>
      <button onClick={() => toggle(false)}>Force close</button>
      {open && <Dialog />}
    </>
  );
}

Senior Engineer Perspective

The insight worth stating: because the toggle reads no reactive value directly (it uses the updater form), useCallback([]) is safe and the function reference is stable across renders. That stability matters when the consumer wraps children in React.memo or lists the callback in another effect's deps. A common mistake is useCallback(() => setOn(!on), [on]), which recreates the function every toggle and defeats memoization.

Q7. Build useOnClickOutside and a generic useEventListener.

ROI: ★★★★☆ Frequency: High

Short Answer

useOnClickOutside(ref, handler) fires a callback when a click/touch lands outside a referenced element — the backbone of dropdowns, modals, and popovers. It attaches a document-level listener and checks whether the event target is contained in the ref. A generic useEventListener abstracts adding/removing any listener on any target while always calling the latest handler via a ref.

Detailed Answer

Key details for useOnClickOutside: listen on document, guard against the ref being null, ignore clicks inside the element (ref.current.contains(target)), and typically listen to both mousedown and touchstart (mousedown avoids the "click that opened it also closes it" ordering issue). Keep the handler in a ref so you don't re-subscribe every render.

useEventListener generalizes the "latest handler in a ref, subscribe once" pattern so you never re-attach listeners just because the callback identity changed — a very common source of subtle bugs.

Code Example

import { useEffect, useRef, RefObject } from "react";

// Generic: always calls the latest handler, subscribes once per target/event.
function useEventListener<K extends keyof WindowEventMap>(
  eventName: K,
  handler: (e: WindowEventMap[K]) => void,
  target: Window | Document | HTMLElement = window
) {
  const savedHandler = useRef(handler);
  useEffect(() => { savedHandler.current = handler; }, [handler]);

  useEffect(() => {
    const listener = (e: Event) => savedHandler.current(e as WindowEventMap[K]);
    target.addEventListener(eventName, listener);
    return () => target.removeEventListener(eventName, listener);
  }, [eventName, target]);
}

// Click outside
function useOnClickOutside<T extends HTMLElement>(
  ref: RefObject<T>,
  handler: (e: MouseEvent | TouchEvent) => void
) {
  const savedHandler = useRef(handler);
  useEffect(() => { savedHandler.current = handler; }, [handler]);

  useEffect(() => {
    const listener = (e: MouseEvent | TouchEvent) => {
      const el = ref.current;
      if (!el || el.contains(e.target as Node)) return; // inside -> ignore
      savedHandler.current(e);
    };
    document.addEventListener("mousedown", listener);
    document.addEventListener("touchstart", listener);
    return () => {
      document.removeEventListener("mousedown", listener);
      document.removeEventListener("touchstart", listener);
    };
  }, [ref]);
}

Senior Engineer Perspective

Watch for: (1) using click instead of mousedown, which can immediately close a menu opened by the same click; (2) not storing the handler in a ref, causing constant re-subscription; (3) portals — a dropdown rendered in a portal is outside the ref's DOM subtree, so contains returns false and it closes unexpectedly; you must include the portal node in the check. For accessibility, note that click-outside should be paired with an Escape-key handler and proper focus management.

Q8. Custom hooks vs Higher-Order Components vs Render Props — when do you use each?

ROI: ★★★★☆ Frequency: High

Short Answer

All three share reusable logic. Custom hooks are the modern default: they compose without nesting, avoid wrapper hell, and don't collide on props. HOCs and render props were the pre-hooks patterns and still appear in class components or when you must inject behavior around a component you can't modify. For sharing stateful logic between function components, prefer hooks.

Detailed Answer

PatternHow it shares logicDownsides
Custom hookCall a use* function inside the componentOnly works in function components; can't wrap markup
HOCFunction that takes a component, returns an enhanced oneWrapper hell, prop name collisions, ref forwarding needed, opaque data flow
Render propsPass a function-as-child that receives the shared stateCallback nesting / "pyramid of doom" in JSX, extra re-renders

Hooks solve the two big pain points of HOCs and render props: no extra tree nesting (which broke DevTools readability and caused wrapper hell) and no prop namespace collisions when composing multiple behaviors. You can call ten hooks in one component with zero nesting; ten HOCs create ten wrappers.

HOCs and render props aren't dead: HOCs are still idiomatic for cross-cutting concerns like connect() (legacy Redux) or injecting into class components; render props remain useful in some component APIs (e.g. libraries exposing state via children functions). But new code sharing logic between function components should use hooks.

Code Example

// Same logic, three ways.

// Render prop (older)
<MouseTracker>{({ x, y }) => <p>{x},{y}</p>}</MouseTracker>

// HOC (older)
const WithMouse = withMouse(MyComponent); // injects x/y as props

// Custom hook (modern) - flat, composable, no wrapper
function Component() {
  const { x, y } = useMouse();
  const online = useOnlineStatus();     // compose freely, no nesting
  return <p>{x},{y} {online ? "on" : "off"}</p>;
}

Senior Engineer Perspective

The interviewer wants historical context and judgment. Say hooks replaced these patterns for logic reuse, then note the nuance: hooks can't do everything HOCs/render props did — you can't use a hook to conditionally wrap or replace rendering, and you can't add a hook to a class component. Error boundaries still require class components (or a library) because there's no hook equivalent of componentDidCatch yet. Show you know why hooks won (composition without nesting) rather than just parroting "hooks are better."

Q9. How do you test a custom hook?

ROI: ★★★★☆ Frequency: Medium

Short Answer

Because hooks can only run inside a component, you test them with renderHook from React Testing Library, which mounts a test harness component. Assert on the returned value, drive updates through act(), and use waitFor for async hooks. Prefer testing behavior through the returned API over implementation details.

Code Example

import { renderHook, act, waitFor } from "@testing-library/react";
import { useCounter } from "./useCounter";

test("increments", () => {
  const { result } = renderHook(() => useCounter(0));
  expect(result.current.count).toBe(0);

  act(() => result.current.increment());
  expect(result.current.count).toBe(1);
});

test("re-runs when props change", () => {
  const { result, rerender } = renderHook(
    ({ start }) => useCounter(start),
    { initialProps: { start: 5 } }
  );
  rerender({ start: 10 }); // simulate a prop change
  // ...assert reset behavior
});

Senior Engineer Perspective

Key points: wrap state-changing calls in act() or React warns; use renderHook's wrapper option to supply context providers a hook depends on; and for async hooks (useFetch) mock fetch/MSW and assert loading→data transitions with waitFor. Seniors also note that if a hook is trivial glue you often get more value testing the component that uses it, and that renderHook moved from @testing-library/react-hooks into @testing-library/react itself.

SECTION 2 - LESS-COMMON BUILT-IN HOOKS

Q10. When should you use useReducer over useState, and what reducer patterns matter?

ROI: ★★★★★ Frequency: Extremely High

Short Answer

Reach for useReducer when state is complex — multiple sub-values that update together, next state that depends on previous state, or transitions best described as named actions. It centralizes update logic in a pure reducer function, making state transitions testable and predictable, and lets you pass a stable dispatch down instead of many callbacks.

Detailed Answer

Signals you've outgrown useState:

  • Several pieces of state change together (e.g. loading, data, error).
  • The next state depends on the previous in nontrivial ways.
  • You keep passing many setter callbacks down the tree — one dispatch is cleaner and is stable, so it never breaks memoization.
  • You want to unit-test transitions in isolation — a reducer is a pure function, trivially testable without React.

Useful patterns: model state as a discriminated union of actions with a type; keep reducers pure (no fetching, no mutation — return new objects); use a state machine style (explicit states like idle | loading | success | error) to make impossible states unrepresentable; and combine useReducer with Context to build a lightweight store without Redux.

Code Example

import { useReducer } from "react";

type State =
  | { status: "idle" }
  | { status: "loading" }
  | { status: "success"; data: string[] }
  | { status: "error"; message: string };

type Action =
  | { type: "FETCH" }
  | { type: "SUCCESS"; data: string[] }
  | { type: "FAILURE"; message: string };

function reducer(state: State, action: Action): State {
  switch (action.type) {
    case "FETCH":   return { status: "loading" };
    case "SUCCESS": return { status: "success", data: action.data };
    case "FAILURE": return { status: "error", message: action.message };
    default:        return state;
  }
}

function List() {
  const [state, dispatch] = useReducer(reducer, { status: "idle" });
  // dispatch({ type: "FETCH" }) ... etc. Impossible states can't exist.
  return state.status === "loading" ? <Spinner /> : /* ... */ null;
}

Project Example

A multi-step checkout wizard: step index, per-step form data, validation errors, and submission status all interlock. A single reducer with actions like NEXT_STEP, SET_FIELD, SUBMIT made the flow readable and let us unit-test every transition without rendering. Passing one dispatch to deeply nested inputs avoided prop-drilling a dozen setters.

Senior Engineer Perspective

The strongest answer connects useReducer to state-machine thinking: enumerate valid states so you can't render a spinner and an error at once. Follow-ups: "Is dispatch stable?" — yes, React guarantees a stable identity, so it's safe in deps and great for Context. "reducer vs Redux?" — same mental model, but useReducer is local/component-scoped with no middleware or devtools out of the box; Redux Toolkit adds global store, middleware, and time-travel. "Can a reducer be async?" — no, keep it pure; do effects outside and dispatch the result.

Q11. Explain useImperativeHandle and forwardRef. When is imperative code the right call?

ROI: ★★★★☆ Frequency: Medium

Short Answer

forwardRef lets a parent pass a ref through to a child component; useImperativeHandle lets that child customize what the ref exposes — a curated imperative API (like focus(), scrollToTop()) instead of the raw DOM node. Use it sparingly for genuinely imperative actions React's declarative model can't express cleanly: focus, text selection, media playback, animations, scroll.

Detailed Answer

By default refs only attach to DOM elements. To let a parent hold a ref to a function component, wrap it in forwardRef. But exposing the raw DOM node leaks internals; useImperativeHandle lets you expose only a small, intentional API surface. This keeps the component's contract clean and prevents the parent from doing arbitrary DOM manipulation.

Reserve this for imperative operations that don't fit declarative props: programmatically focusing an input after an error, playing/pausing a <video>, triggering an animation, or resetting an uncontrolled form. If you can express it as state/props, do that instead — imperative handles are an escape hatch.

Note: in React 19, ref can be passed as a normal prop to function components, so forwardRef is being deprecated in favor of reading ref from props directly — but useImperativeHandle remains.

Code Example

import { forwardRef, useImperativeHandle, useRef } from "react";

type FancyInputHandle = { focus: () => void; clear: () => void };

const FancyInput = forwardRef<FancyInputHandle>((props, ref) => {
  const inputRef = useRef<HTMLInputElement>(null);

  useImperativeHandle(ref, () => ({
    focus: () => inputRef.current?.focus(),
    clear: () => { if (inputRef.current) inputRef.current.value = ""; },
  }), []); // expose only focus + clear, not the raw node

  return <input ref={inputRef} {...props} />;
});

function Form() {
  const ref = useRef<FancyInputHandle>(null);
  return (
    <>
      <FancyInput ref={ref} />
      <button onClick={() => ref.current?.focus()}>Focus</button>
    </>
  );
}

Senior Engineer Perspective

Interviewers probe whether you know this is an escape hatch — overusing imperative handles is a smell that you're fighting the declarative model. A good answer names concrete legitimate cases (focus management, media, animations, integrating a non-React library) and stresses exposing a minimal API. Mention the React 19 change (ref-as-prop deprecating forwardRef) to show you're current. Also note the dependency array of useImperativeHandle controls when the handle object is recreated.

Q12. What problem does useId solve? Why not just use a counter or Math.random?

ROI: ★★★☆☆ Frequency: Medium

Short Answer

useId generates a unique, stable ID that is consistent between server and client rendering, avoiding hydration mismatches. Its purpose is wiring up accessibility attributes (htmlFor/id, aria-describedby), not keys in lists. A random ID or a module counter would differ between server and client and break hydration.

Detailed Answer

In SSR, HTML is generated on the server then hydrated on the client. If you generate IDs with Math.random() or an incrementing counter, the server and client produce different values, causing a hydration mismatch warning and broken aria/label associations. useId produces the same deterministic ID on both sides by deriving it from the component's position in the tree.

Use it to connect labels and inputs, or an input to its error message. If you need several related IDs, call useId once and append suffixes. Do not use it as a React key in lists — keys should come from your data.

Code Example

import { useId } from "react";

function Field({ label }: { label: string }) {
  const id = useId();
  return (
    <div>
      <label htmlFor={id}>{label}</label>
      <input id={id} aria-describedby={`${id}-hint`} />
      <p id={`${id}-hint`}>Must be unique</p>
    </div>
  );
}

Q13. Explain useTransition and useDeferredValue. How do they differ?

ROI: ★★★★★ Frequency: High

Short Answer

Both are React 18 concurrent features that keep the UI responsive by marking work as low priority. useTransition lets you mark a state update as non-urgent via startTransition, and gives you an isPending flag. useDeferredValue takes a value and returns a deferred copy that lags behind during heavy renders. Use useTransition when you own the update; useDeferredValue when you only receive a value (e.g. a prop).

Detailed Answer

Concurrent rendering lets React interrupt a low-priority render to handle urgent updates (like typing). Without it, filtering a huge list on every keystroke blocks the input. Both hooks solve the same class of problem — an urgent update (typing) and an expensive dependent render (a giant filtered list) — by deprioritizing the expensive part so the input stays snappy.

Q14. Why does useSyncExternalStore exist? What is "tearing"?

ROI: ★★★★☆ Frequency: Medium

Short Answer

useSyncExternalStore is the correct, concurrent-safe way to subscribe a component to an external (non-React) data source — a browser API, a Redux-like store, or a global event source. It exists because React 18's concurrent rendering can pause and resume, and a naive useEffect-based subscription can read inconsistent snapshots mid-render, producing "tearing": different parts of the UI showing different values of the same store in one commit.

Detailed Answer

Before React 18, state stores subscribed via useState + useEffect. With concurrent rendering, React can render a component, pause, let an external value change, then resume — meaning two components could read the store at different moments during one render pass and disagree. That inconsistency is tearing. useSyncExternalStore forces a synchronous, consistent read so React always renders one coherent snapshot.

It takes three arguments: subscribe (register a callback that re-renders on change; must return an unsubscribe), getSnapshot (return the current value synchronously — must return a cached, stable reference for equal state, or you loop), and an optional getServerSnapshot for SSR. Library authors (Redux, Zustand, Jotai) use it internally; app code mostly uses it for browser APIs like online status, media queries, or the URL.

Code Example

import { useSyncExternalStore } from "react";

// Subscribe to browser online/offline state - tear-free.
function useOnlineStatus() {
  return useSyncExternalStore(
    (callback) => {
      window.addEventListener("online", callback);
      window.addEventListener("offline", callback);
      return () => {
        window.removeEventListener("online", callback);
        window.removeEventListener("offline", callback);
      };
    },
    () => navigator.onLine,   // client snapshot
    () => true                // server snapshot (assume online in SSR)
  );
}

Senior Engineer Perspective

The killer follow-up: "Why not just useState + useEffect?" — because that works in blocking mode but can tear under concurrent features and misses SSR consistency. The subtle bug candidates hit: getSnapshot must return a referentially stable value for unchanged state; returning a fresh object each call causes an infinite render loop. Mention that libraries expose useSyncExternalStoreWithSelector for selecting a slice with a custom equality function. Knowing this hook signals you understand why React 18 concurrency needed a new subscription primitive.

Q15. Build useMediaQuery. Why is useSyncExternalStore a better fit than useEffect here?

ROI: ★★★★☆ Frequency: Medium

Short Answer

useMediaQuery("(min-width: 768px)") returns whether the query currently matches and updates on change. The clean implementation uses useSyncExternalStore: subscribe attaches a change listener on a MediaQueryList, and getSnapshot reads .matches. This is tear-free and handles SSR via a server snapshot, unlike an effect-based version that flashes the wrong value on first render.

Code Example

import { useSyncExternalStore, useCallback } from "react";

function useMediaQuery(query: string): boolean {
  const subscribe = useCallback((callback: () => void) => {
    const mql = window.matchMedia(query);
    mql.addEventListener("change", callback);
    return () => mql.removeEventListener("change", callback);
  }, [query]);

  const getSnapshot = () => window.matchMedia(query).matches;
  const getServerSnapshot = () => false; // no matchMedia on the server

  return useSyncExternalStore(subscribe, getSnapshot, getServerSnapshot);
}

// Usage
function Nav() {
  const isDesktop = useMediaQuery("(min-width: 768px)");
  return isDesktop ? <DesktopNav /> : <MobileNav />;
}

Senior Engineer Perspective

A useEffect version reads matchMedia only after mount, so the first paint uses a default and then flips — causing a visible flash and, in SSR, a hydration mismatch. useSyncExternalStore reads synchronously and provides a server snapshot, avoiding both. Gotchas to mention: older Safari used addListener/removeListener instead of addEventListener; and provide a sensible server default since layout decisions based on it will render server-side.

SECTION 4 - REACT 19 HOOKS

Q16. What are the new React 19 hooks: use(), useOptimistic, and useActionState?

ROI: ★★★★☆ Frequency: High

Short Answer

React 19 adds primitives centered on async data and form Actions. use() reads a promise or context during render and integrates with Suspense — and uniquely may be called conditionally. useOptimistic shows an immediate optimistic UI state while an async action is in flight, then reconciles. useActionState (formerly useFormState) manages the state, pending status, and result of a form Action.

Detailed Answer

use() — reads the value of a resource. Pass it a promise and React suspends until it resolves (works with Suspense/RSC); pass it a Context and it reads that context. Unlike other hooks, use() can be called inside conditions and loops, because it isn't tied to a fixed hook slot the same way.

useOptimistic — lets you render a temporary optimistic value immediately (e.g. show a sent message before the server confirms). React automatically reverts to the real state when the action completes or errors, so you don't manually roll back.

useActionState — wraps an async "action" function and returns [state, formAction, isPending]. Wire formAction to a <form action={...}>; React tracks the pending state and the returned result (e.g. validation errors) without manual useState. Complements useFormStatus for reading pending status from child components.

Code Example

import { use, useOptimistic, useActionState } from "react";

// use(): read a promise with Suspense
function Comments({ promise }: { promise: Promise<string[]> }) {
  const comments = use(promise); // suspends until resolved
  return <ul>{comments.map((c) => <li key={c}>{c}</li>)}</ul>;
}

// useActionState + useOptimistic: form action with instant feedback
function MessageForm({ send }: { send: (text: string) => Promise<void> }) {
  const [messages, setMessages] = useState<string[]>([]);
  const [optimistic, addOptimistic] = useOptimistic(
    messages,
    (state, newMsg: string) => [...state, newMsg]
  );

  const [, formAction, isPending] = useActionState(
    async (_prev: unknown, formData: FormData) => {
      const text = formData.get("text") as string;
      addOptimistic(text);        // show immediately
      await send(text);           // then persist
      setMessages((m) => [...m, text]);
      return null;
    },
    null
  );

  return (
    <form action={formAction}>
      {optimistic.map((m) => <p key={m}>{m}</p>)}
      <input name="text" />
      <button disabled={isPending}>Send</button>
    </form>
  );
}

Senior Engineer Perspective

Show you're tracking the current React landscape: these hooks pair with Server Components and Server Actions and represent React's shift toward first-class async and forms. Nuances worth naming: use() is the only hook allowed inside conditionals; you should not create the promise inline in a Client Component render (it creates a new promise each render) — the promise should come from a cached source or a Server Component. useActionState was renamed from useFormState and moved out of react-dom into react. Optimistic state auto-reverts on completion, so don't hand-roll rollback logic.

Q17. What are the three most common bugs people ship in custom hooks?

ROI: ★★★★☆ Frequency: High

Short Answer

(1) Stale closures — a hook captures an old value because a callback or effect isn't re-created and doesn't use a ref or the updater form. (2) Missing effect cleanup — timers, listeners, and subscriptions leak or cause race conditions/updates after unmount. (3) Unstable return values — returning a new object/array/function identity every render, breaking consumers' memoization or triggering infinite effect loops.

Detailed Answer

  • Stale closures: an event handler stored once reads the value from the render it was created in. Fixes: use the functional updater (setX(prev => ...)), keep the latest callback in a ref, or list correct dependencies.
  • Missing cleanup: every setInterval, addEventListener, subscription, or in-flight request needs teardown in the effect's return function. Without it you get memory leaks, duplicate listeners, and race conditions — and Strict Mode's double-invoke in dev surfaces these.
  • Unstable identities: returning { data, refetch } where refetch is a fresh function each render forces consumers to re-render or re-run effects that depend on it. Wrap functions in useCallback and derived objects in useMemo where identity matters.

Code Example

// BUG: stale closure + no cleanup
function useTickBad(onTick: () => void) {
  useEffect(() => {
    setInterval(() => onTick(), 1000); // captures first onTick, never cleared
  }, []);                              // missing dep + no cleanup
}

// FIX: latest callback via ref, proper cleanup
function useInterval(callback: () => void, delay: number) {
  const saved = useRef(callback);
  useEffect(() => { saved.current = callback; }, [callback]);
  useEffect(() => {
    const id = setInterval(() => saved.current(), delay);
    return () => clearInterval(id); // cleanup!
  }, [delay]);
}

Senior Engineer Perspective

This question tests debugging instincts. Tie the answers together: React 18 Strict Mode intentionally mounts, unmounts, and remounts effects in development precisely to catch missing cleanup — if your hook breaks under Strict Mode, it has a latent bug. Mention eslint-plugin-react-hooks' exhaustive-deps rule as your first line of defense against stale closures, and that "just disable the lint rule" is almost always the wrong fix. Dan Abramov's "useInterval" pattern (latest-callback ref) is the canonical solution worth naming.

SECTION 5 - BUILDING DATA-FETCHING CUSTOM HOOKS

Q18. What should the return shape of a data-fetching hook look like, and why is a single "status" field better than three booleans?

ROI: ★★★★★ Frequency: Extremely High

Short Answer

A naive shape is { data, loading, error } as three independent booleans/values. The problem is it allows impossible combinations — loading: true and error both set, or data and error both populated. A more robust shape models an explicit status discriminant (idle | loading | success | error) so the type system and the reducer make invalid states unrepresentable.

Detailed Answer

With three loose fields, every consumer has to defensively check combinations: "is it loading AND do we have stale data from before?" With a tagged union, the consumer switches on status and TypeScript narrows the other fields automatically — data only exists when status === "success", error only when status === "error". This also makes "stale-while-revalidate" explicit: you can add a status: "refetching" that still carries the previous data, rather than nulling it out and causing a UI flash.

Code Example

// Loose (allows impossible states)
type LooseState<T> = { data: T | null; loading: boolean; error: Error | null };

// Tagged union (impossible states unrepresentable)
type FetchState<T> =
  | { status: "idle" }
  | { status: "loading" }
  | { status: "success"; data: T }
  | { status: "refetching"; data: T }   // stale data kept visible while re-fetching
  | { status: "error"; error: Error };

function ResultView<T>({ state }: { state: FetchState<T> }) {
  switch (state.status) {
    case "idle":
    case "loading":
      return <Spinner />;
    case "error":
      return <ErrorBanner message={state.error.message} />;
    case "success":
    case "refetching":
      // TypeScript knows `data` exists here for both branches
      return <Table rows={state.data} dimmed={state.status === "refetching"} />;
  }
}

Senior Engineer Perspective

This question separates people who've only used useState three times from people who've shipped data-fetching hooks that survive real usage. The "dimmed while refetching" detail is the kind of UX polish interviewers want to hear volunteered — it's exactly what TanStack Query's isFetching vs isLoading distinction gives you for free, and re-deriving it by hand is a good way to demonstrate you understand why that library's API looks the way it does.

Q19. Walk through the exact race condition in a naive useFetch hook when the URL changes quickly, and the two standard fixes.

ROI: ★★★★★ Frequency: Extremely High

Short Answer

If a component fetches /search?q=a and then, before it resolves, re-renders with /search?q=ab, two requests are in flight. There is no guarantee the second (correct) request resolves after the first (stale) one — the network is not FIFO. Without protection, whichever response lands last wins, even if it's for the stale query. Fix with an AbortController per request, or an "ignore" flag set in the effect's cleanup.

Detailed Answer

Every render of the effect (triggered by url changing) starts a new request. React runs the previous effect's cleanup before the next effect body, so cleanup is the natural place to invalidate the outgoing request tied to the old url. Two approaches, often combined:

  • AbortController — actually cancels the underlying HTTP request (saves bandwidth, and fetch rejects with an AbortError you explicitly ignore).
  • ignore flag — a boolean closed over by the effect; even if you can't cancel the request (e.g. a legacy API without abort support), you can still refuse to apply its result.

The ignore flag is the more general/defensive of the two since not every async source is abortable, but AbortController is preferred when available because it also frees server resources.

Code Example

useEffect(() => {
  let ignore = false;
  const controller = new AbortController();

  setStatus("loading");
  fetch(url, { signal: controller.signal })
    .then((r) => r.json())
    .then((data) => {
      if (!ignore) setStatus({ status: "success", data }); // guard applies result
    })
    .catch((err) => {
      if (err.name === "AbortError") return;               // expected, not a real error
      if (!ignore) setStatus({ status: "error", error: err });
    });

  return () => {
    ignore = true;        // belt
    controller.abort();   // suspenders
  };
}, [url]);

Senior Engineer Perspective

Interviewers sometimes push further: "what if you can't abort because it's a mutation, not a GET?" Then you must not abort (aborting a POST mid-flight can leave the server in an unknown state) — rely purely on the ignore flag, or better, sequence mutations so a new one can't start until the previous settles. Mentioning that distinction (idempotent GETs are safe to abort, mutations need a different strategy) is a strong signal of production experience.

Q20. How do you add a simple in-hook cache so switching back to a previously-fetched URL doesn't re-fetch?

ROI: ★★★★☆ Frequency: High

Short Answer

Keep a module-level (or ref-held, if scoped per hook-tree) Map<url, result> outside component state. On fetch, check the cache first; if present, use it synchronously (optionally still revalidating in the background). This is the "stale-while-revalidate" pattern in miniature, and it's exactly the gap that pushes teams toward a real caching library once the requirements grow (cache invalidation, TTL, garbage collection, cross-component sharing).

Detailed Answer

A module-level Map persists across component mounts/unmounts (it lives in the module scope, not component state), so navigating away and back reuses the cached response instantly instead of showing a spinner. The key design decisions: what's the cache key (usually the URL + serialized params), do you cache promises (to dedupe concurrent identical requests) or resolved values, and how do entries get invalidated (manual, TTL, or on mutation).

Code Example

// Module-level cache: survives remounts, shared across every useFetch call.
const cache = new Map<string, Promise<unknown>>();

function useFetchCached<T>(url: string): FetchState<T> {
  const [state, setState] = useState<FetchState<T>>({ status: "loading" });

  useEffect(() => {
    let ignore = false;

    // Cache the PROMISE, not just the resolved value -- dedupes concurrent
    // requests for the same URL fired by different components in the same tick.
    if (!cache.has(url)) {
      cache.set(url, fetch(url).then((r) => r.json()));
    }

    setState({ status: "loading" });
    (cache.get(url) as Promise<T>)
      .then((data) => { if (!ignore) setState({ status: "success", data }); })
      .catch((error: Error) => {
        cache.delete(url); // don't poison the cache with a failed promise
        if (!ignore) setState({ status: "error", error });
      });

    return () => { ignore = true; };
  }, [url]);

  return state;
}

Senior Engineer Perspective

The strongest answer names the failure modes of hand-rolled caching before the interviewer has to: unbounded growth (no garbage collection — a real library prunes unused entries), no built-in invalidation on mutation, and no cross-tab or cross-request de-duplication beyond what you wrote. This is the natural bridge to "so in production I'd use TanStack Query" — showing the hand-rolled version proves you understand what the library is actually buying you rather than treating it as magic.

Q21. Your useFetch hook re-fetches on every render even though the URL "hasn't changed." What's the likely bug?

ROI: ★★★★☆ Frequency: High

Short Answer

Almost always: the dependency isn't actually the same value across renders even though it looks equal. Common culprits are passing an inline object/array as a "params" dependency ({ q: query } is a new object every render), or passing a function/config that's re-created each render. useEffect compares dependencies with Object.is, so a new object reference re-triggers the effect even if its contents are deep-equal.

Detailed Answer

This is a referential-equality bug, not a fetching bug. Fixes, in order of preference: (1) flatten the dependency to primitives (pass query and page separately instead of a params object); (2) memoize the object with useMemo keyed on its primitive inputs; (3) serialize it (JSON.stringify(params)) as the dependency when the shape is dynamic and flattening isn't practical — cheap and correct as long as key order is stable, though it costs a stringify on every render.

Code Example

// BUG: new object every render -> effect deps never "equal" -> re-fetches forever
function useSearch(query: string, page: number) {
  const params = { q: query, page };            // new reference each render
  useEffect(() => {
    fetchResults(params);
  }, [params]);                                   // always "changed"
}

// FIX 1: flatten to primitives
useEffect(() => { fetchResults({ q: query, page }); }, [query, page]);

// FIX 2: memoize
const params = useMemo(() => ({ q: query, page }), [query, page]);
useEffect(() => { fetchResults(params); }, [params]);

// FIX 3: serialize (when shape is dynamic / from a parent)
useEffect(() => { fetchResults(params); }, [JSON.stringify(params)]);

Senior Engineer Perspective

This is one of the highest-frequency real-world hook bugs, and interviewers use it to check whether you understand Object.is comparison versus deep equality. A sharp follow-up: "why not just disable the exhaustive-deps lint rule and pass []?" — because that silences the symptom (the infinite loop) while introducing a worse bug (the effect now never re-runs when query or page genuinely change), trading one bug for a subtler one.

Q22. How would you add retry-with-backoff to a fetch hook without blocking the UI thread or fighting React's render cycle?

ROI: ★★★☆☆ Frequency: Medium

Short Answer

Keep retry state (attempt count, next delay) inside the async function that the effect kicks off, not as component state that would re-render on every attempt. Use setTimeout (never a blocking loop) between attempts, respect the same AbortController/ignore-flag cancellation as the base fetch so an in-flight retry chain stops cleanly if the component unmounts or the URL changes, and cap both the attempt count and the maximum delay.

Code Example

function useFetchWithRetry<T>(url: string, maxAttempts = 3) {
  const [state, setState] = useState<FetchState<T>>({ status: "loading" });

  useEffect(() => {
    let cancelled = false;
    const controller = new AbortController();

    async function run() {
      for (let attempt = 1; attempt <= maxAttempts; attempt++) {
        try {
          const res = await fetch(url, { signal: controller.signal });
          if (!res.ok) throw new Error(`HTTP ${res.status}`);
          const data: T = await res.json();
          if (!cancelled) setState({ status: "success", data });
          return;
        } catch (err) {
          if ((err as Error).name === "AbortError" || cancelled) return;
          if (attempt === maxAttempts) {
            if (!cancelled) setState({ status: "error", error: err as Error });
            return;
          }
          // exponential backoff with a jitter, capped at 8s
          const delay = Math.min(1000 * 2 ** (attempt - 1), 8000) + Math.random() * 200;
          await new Promise((r) => setTimeout(r, delay));
        }
      }
    }

    setState({ status: "loading" });
    run();
    return () => { cancelled = true; controller.abort(); };
  }, [url, maxAttempts]);

  return state;
}

Senior Engineer Perspective

The trap is candidates reaching for setState per attempt (causing needless re-renders and, worse, a UI that flickers through intermediate "retrying" states) or forgetting the cancelled/abort check inside the retry loop — without it, an unmounted component's retry chain keeps running and can call setState on a ghost component. Mentioning jitter (randomizing the delay slightly) shows awareness of the "thundering herd" problem when many clients retry a failing endpoint in lockstep.

Q23. How do you handle pagination or infinite scroll cleanly inside a data-fetching hook?

ROI: ★★★★☆ Frequency: High

Short Answer

Model the accumulated pages as state that a reducer appends to, keep a separate "next cursor/page" pointer, and expose a fetchMore function distinct from the hook's initial-load effect. Critically, guard against firing fetchMore again while a page is already in flight (a common infinite-scroll bug is triggering three requests from one fast scroll).

Detailed Answer

Separate three concerns: (1) the *list* of accumulated items, (2) whether there's *more* to load (a cursor or hasNextPage), and (3) whether a fetch is *currently* in flight (to dedupe rapid triggers from an intersection observer). Resetting to page one should be a distinct action from appending a page, since a filter change needs to replace the list, not append to it.

Code Example

function usePaginatedList<T>(baseUrl: string) {
  const [items, setItems] = useState<T[]>([]);
  const [cursor, setCursor] = useState<string | null>(null);
  const [hasMore, setHasMore] = useState(true);
  const [isFetching, setIsFetching] = useState(false);

  const fetchMore = useCallback(async () => {
    if (isFetching || !hasMore) return;        // dedupe: ignore overlapping calls
    setIsFetching(true);
    const url = cursor ? `${baseUrl}?cursor=${cursor}` : baseUrl;
    const res = await fetch(url).then((r) => r.json());
    setItems((prev) => [...prev, ...res.items]); // append, don't replace
    setCursor(res.nextCursor);
    setHasMore(Boolean(res.nextCursor));
    setIsFetching(false);
  }, [baseUrl, cursor, hasMore, isFetching]);

  // Reset (e.g. when a filter changes) is a DIFFERENT action than appending.
  const reset = useCallback(() => {
    setItems([]); setCursor(null); setHasMore(true);
  }, []);

  return { items, hasMore, isFetching, fetchMore, reset };
}

Senior Engineer Perspective

Interviewers probe the intersection-observer trigger specifically: if you attach fetchMore directly to an observer callback without the isFetching guard, a slightly janky scroll can fire the callback multiple times before the first request resolves, appending duplicate pages. Also worth mentioning: pagination interacts badly with items being inserted/deleted upstream (cursor drift) — cursor-based (not offset-based) pagination is more resilient to that than page-number pagination.

Q24. Should a data-fetching hook fetch inside useEffect, or is there a better place in modern React?

ROI: ★★★★☆ Frequency: Medium

Short Answer

useEffect is the traditional (and still valid) place for client-driven fetches triggered by state changes. But the React team has been explicit that "fetch in an effect" is a pattern with real downsides (waterfalls, no SSR, race conditions you must hand-roll) and that, where available, Server Components, framework loaders (Next.js/Remix), or a dedicated data-fetching library are better defaults. In an interview, name the effect-based pattern correctly, then show you know its limits.

Detailed Answer

Fetching in useEffect means the component must first render (often with a loading state), then the effect fires, then the request resolves, then a re-render shows data — a "fetch-on-render" waterfall. If that component is nested inside another component that also fetches in an effect, you get sequential waterfalls instead of parallel requests. Alternatives: fetch at the router/loader level so data starts loading in parallel with rendering; use React Server Components so data fetching happens on the server, before any client JS runs; or use a library (TanStack Query, SWR) which still uses effects internally but adds caching, dedup, and prefetching to blunt the waterfall problem.

Code Example

// Effect-based (component-driven): waterfall risk if nested
function Profile({ userId }) {
  const { data: user } = useFetch(`/users/${userId}`);
  return user && <Posts userId={user.id} />; // Posts' fetch starts AFTER user resolves
}

// Loader-based (route-driven): fetches in parallel, before render
// (Remix / React Router data APIs, conceptually)
export async function loader({ params }) {
  const [user, posts] = await Promise.all([
    getUser(params.userId),
    getPosts(params.userId), // starts immediately, not gated on `user`
  ]);
  return { user, posts };
}

Senior Engineer Perspective

This question rewards nuance over dogma. The wrong answer is "never fetch in useEffect, it's an anti-pattern" — plenty of real apps (dashboards behind a login, client-only tools) fetch in effects correctly and it's fine. The right answer names the specific cost (render-then-fetch waterfalls, no SSR) and the specific mitigations (parallelizing with Promise.all, moving to loaders/RSC, or layering a cache/prefetch library on top) rather than treating "useEffect fetching" as universally forbidden.

Q25. How do you unit test a data-fetching hook's loading -> success and loading -> error transitions?

ROI: ★★★★☆ Frequency: Medium

Short Answer

Mock the network boundary (either global.fetch directly, or via MSW intercepting real requests), render the hook with renderHook, assert the initial loading state synchronously, then await waitFor(...) for the resolved state. Test both the happy path and a rejected/500 response to cover the error branch, and test unmounting mid-flight to confirm no "setState on unmounted component" warning.

Code Example

import { renderHook, waitFor } from "@testing-library/react";
import { useFetch } from "./useFetch";

beforeEach(() => {
  global.fetch = jest.fn();
});

test("resolves to success state", async () => {
  (fetch as jest.Mock).mockResolvedValueOnce({
    ok: true,
    json: async () => ({ id: 1, name: "Ada" }),
  });

  const { result } = renderHook(() => useFetch("/users/1"));
  expect(result.current.status).toBe("loading"); // synchronous initial state

  await waitFor(() => expect(result.current.status).toBe("success"));
  expect(result.current.data).toEqual({ id: 1, name: "Ada" });
});

test("resolves to error state on non-2xx", async () => {
  (fetch as jest.Mock).mockResolvedValueOnce({ ok: false, status: 500 });

  const { result } = renderHook(() => useFetch("/users/1"));
  await waitFor(() => expect(result.current.status).toBe("error"));
});

test("does not update state after unmount", async () => {
  let resolveFetch: (v: unknown) => void;
  (fetch as jest.Mock).mockReturnValueOnce(new Promise((r) => { resolveFetch = r; }));

  const { unmount } = renderHook(() => useFetch("/users/1"));
  unmount();
  resolveFetch!({ ok: true, json: async () => ({}) }); // resolves AFTER unmount
  // assert no console.error / act warning was logged
});

Senior Engineer Perspective

Strong candidates mention MSW (Mock Service Worker) over hand-mocking fetch for anything beyond a trivial test, because it intercepts at the network layer and exercises your actual request-building code (headers, query strings, serialization) rather than bypassing it. SECTION 6 - CUSTOM HOOK COMPOSITION PATTERNS

Q26. What does it mean for hooks to "compose," and how do you layer one custom hook on top of another?

ROI: ★★★★★ Frequency: High

Short Answer

Composition means a custom hook can call other hooks (built-in or custom) internally, and the calling component never needs to know that happened. This lets you build layered abstractions: a low-level useEventListener underlies useOnClickOutside, which might underlie a `useDropdown` hook, which a `Select` component calls — each layer adds behavior without the layer above needing to re-implement it.

Detailed Answer

Because hooks are just function calls (not components in a tree), composing them costs nothing structurally — no extra wrapper in DevTools, no extra DOM nesting, unlike composing HOCs. The design skill is choosing the right layer boundary: a low-level hook should do one primitive thing well (subscribe to an event, read a media query) and a higher-level hook should combine several primitives into a use-case-shaped API (`useDropdown` returns `{ isOpen, toggle, triggerProps, menuProps }`, not raw event handlers).

A common mistake is either under-layering (one giant hook that mixes fetching, timers, and DOM listeners with no separable pieces) or over-layering (a hook that does nothing but call one other hook with no added value, adding an indirection that doesn't pay for itself).

Code Example

// Layer 1: primitive - subscribe to any DOM event, latest handler.
function useEventListener(target, type, handler) { /* ...as in Q7... */ }

// Layer 2: use-case - click-outside built ONLY from the primitive above.
function useOnClickOutside(ref, onOutside) {
  useEventListener(document, "mousedown", (e) => {
    if (ref.current && !ref.current.contains(e.target)) onOutside(e);
  });
}

// Layer 3: component-shaped - a dropdown's full open/close/outside-click contract.
function useDropdown() {
  const [isOpen, setIsOpen] = useState(false);
  const ref = useRef<HTMLDivElement>(null);
  useOnClickOutside(ref, () => setIsOpen(false));

  return {
    isOpen,
    triggerProps: { onClick: () => setIsOpen((o) => !o) },
    menuRef: ref,
  };
}

// Component: knows NOTHING about event listeners or refs.
function Select() {
  const { isOpen, triggerProps, menuRef } = useDropdown();
  return (
    <div ref={menuRef}>
      <button {...triggerProps}>Options</button>
      {isOpen && <Menu />}
    </div>
  );
}

Senior Engineer Perspective

This is really a system-design question in miniature. The interviewer wants to see you reason about layering the way you would about services: each layer has a single clear responsibility, and higher layers depend on lower layers' public contract, never their internals. A good tell of seniority: naming that composed hooks still share the Rules of Hooks — you can't conditionally call `useOnClickOutside` inside `useDropdown` just because it's "internal now."

Q27. How do you share logic between two custom hooks without duplicating a useEffect, when neither hook should depend on the other directly?

ROI: ★★★★☆ Frequency: Medium

Short Answer

Extract the shared logic into its own lower-level hook (or a plain non-hook utility if it doesn't itself use React state/effects), and have both hooks call it. If the shared piece needs no hooks internally (pure computation), it doesn't need the use prefix at all — only wrap it as a hook if it actually calls other hooks.

Code Example

// Shared subscription logic extracted once.
function useWindowSize() {
  const [size, setSize] = useState({ w: window.innerWidth, h: window.innerHeight });
  useEffect(() => {
    const onResize = () => setSize({ w: window.innerWidth, h: window.innerHeight });
    window.addEventListener("resize", onResize);
    return () => window.removeEventListener("resize", onResize);
  }, []);
  return size;
}

// Both hooks build on the SAME shared primitive - no duplicated effect.
function useIsMobile() {
  const { w } = useWindowSize();
  return w < 768;
}

function useColumnCount() {
  const { w } = useWindowSize();
  if (w < 480) return 1;
  if (w < 1024) return 2;
  return 3;
}

Senior Engineer Perspective

The subtlety interviewers listen for: because useWindowSize is called independently inside useIsMobile and useColumnCount, each caller gets its own subscription and its own resize listener — that's fine for two callers, but if you had twenty consumers on one page, twenty resize listeners would attach. At that point you'd promote the subscription to a single shared external store (via useSyncExternalStore reading one global listener) rather than one-per-hook-instance. Knowing when to make that trade is the senior signal.

Q28. When should a custom hook accept a config object versus positional arguments, and how does that choice affect composition?

ROI: ★★★☆☆ Frequency: Medium

Short Answer

Positional arguments are fine for one or two required, order-obvious values (useState(initial), useDebounce(value, delay)). Once a hook has three or more parameters, several of which are optional, a config object is clearer at call sites and far more composable — callers can spread partial config, and adding a new option later doesn't break every existing call site's argument order.

Code Example

// Positional: fine for 2 obvious args
useDebounce(value, 300);

// Config object: clearer once there are several optional knobs,
// and composable - a wrapper hook can spread + override.
function useFetch(url: string, options: {
  method?: string;
  headers?: Record<string, string>;
  skip?: boolean;
  onSuccess?: (data: unknown) => void;
} = {}) { /* ... */ }

// A composing hook can layer its own defaults on top:
function useAuthedFetch(url: string, options: Parameters<typeof useFetch>[1] = {}) {
  const token = useAuthToken();
  return useFetch(url, {
    ...options,
    headers: { ...options.headers, Authorization: `Bearer ${token}` },
  });
}

Senior Engineer Perspective

This is really an API-design maturity check. A good answer notes the "spread and override" composability a config object gives you (as in useAuthedFetch above) that positional args can't — you can't cleanly "layer" three positional booleans the way you can merge two option objects. It also foreshadows the API-design anti-patterns section: a hook with five positional booleans (useThing(true, false, true)) is unreadable at the call site regardless of composition concerns.

Q29. Can one custom hook call another custom hook conditionally if the "outer" hook itself is always called unconditionally?

ROI: ★★★★☆ Frequency: Medium

Short Answer

No. The Rules of Hooks apply to every hook call at every level of composition — there is no exemption for calls made "inside" a custom hook. If useThing() conditionally calls useSubscription() only sometimes, that breaks the same fixed-call-order invariant as doing it directly in a component, because React tracks hook state by call order regardless of which function issued the call.

Detailed Answer

React doesn't know or care that a hook call happened "inside a custom hook" versus "inside a component" — from the reconciler's point of view, it's all one flat sequence of hook calls for that fiber. So a custom hook internally branching on a prop to decide whether to call useEffect is exactly as broken as a component doing the same thing. The fix is always the same: call the hook unconditionally and push the condition inside it (e.g. an early return inside the effect body, or an `enabled`/`skip` option).

Code Example

// BROKEN: conditional hook call, even though it's buried inside a custom hook
function useMaybeSubscribe(active: boolean) {
  if (active) {
    useEffect(() => { /* subscribe */ }, []); // call order varies -> crash/corruption
  }
}

// FIX: hook is always called; the CONDITION lives inside it
function useMaybeSubscribe(active: boolean) {
  useEffect(() => {
    if (!active) return;             // condition inside, not around, the hook
    const sub = subscribe();
    return () => sub.unsubscribe();
  }, [active]);
}

Senior Engineer Perspective

This question weeds out people who've memorized "don't call hooks in conditionals" as a rule about component code specifically, rather than understanding why the rule exists (React associates hook state with a fixed call-order "slot," not a name). A great answer also mentions that eslint-plugin-react-hooks catches this even across custom hook boundaries — it doesn't matter how many layers of custom hooks the conditional call is buried under, the lint rule (and the runtime bug) still applies.

Q30. How would you build a useAsyncFn hook — a generic wrapper that turns any async function into { execute, status, data, error } — and compose it under useFetch?

ROI: ★★★☆☆ Frequency: Medium

Short Answer

useAsyncFn wraps an arbitrary async function (not just fetch) and tracks its lifecycle generically: execute triggers it, status/data/error reflect the result. A URL-based useFetch can then be re-expressed as a thin layer that just supplies () => fetch(url).then(r => r.json()) to the generic hook — the async-lifecycle bookkeeping is written once and reused for fetches, form submissions, file uploads, anything async.

Code Example

function useAsyncFn<A extends unknown[], R>(fn: (...args: A) => Promise<R>) {
  const [state, setState] = useState<FetchState<R>>({ status: "idle" });
  const fnRef = useRef(fn);
  useEffect(() => { fnRef.current = fn; }, [fn]);

  const execute = useCallback((...args: A) => {
    setState({ status: "loading" });
    return fnRef.current(...args)
      .then((data) => { setState({ status: "success", data }); return data; })
      .catch((error: Error) => { setState({ status: "error", error }); throw error; });
  }, []);

  return { ...state, execute };
}

// useFetch composed ON TOP of the generic hook - zero duplicated bookkeeping.
function useFetch<T>(url: string) {
  const { execute, ...state } = useAsyncFn(
    useCallback(() => fetch(url).then((r) => r.json() as Promise<T>), [url])
  );
  useEffect(() => { execute(); }, [execute]); // auto-run on mount/url change
  return state;
}

Senior Engineer Perspective

This shows the payoff of the layering principle from Q26 concretely: form submission, file upload, and data fetching all share the exact same "idle/loading/success/error" bookkeeping, so writing it once in useAsyncFn and composing everything else on top eliminates a whole category of copy-pasted, subtly-inconsistent status-tracking code across a codebase.

Q31. How do you avoid an "infinite re-composition" bug where a composed hook's returned object changes identity every render and re-triggers effects in the caller?

ROI: ★★★★★ Frequency: High

Short Answer

If an inner hook returns a fresh object/array/function each render, and an outer hook or component puts that whole object in a dependency array, the effect re-runs every render forever (and if that effect itself calls a setter, you get an infinite loop). Fix by memoizing the returned object/functions inside the hook that produces them (useMemo/useCallback) so identity is stable across renders when the underlying values haven't changed.

Code Example

// BUG: `api` object is a new reference every render of useThing
function useThing() {
  const [count, setCount] = useState(0);
  const increment = () => setCount((c) => c + 1); // new function every render
  return { count, increment };                     // new object every render
}

function Caller() {
  const { increment } = useThing();
  useEffect(() => {
    increment();
  }, [increment]); // `increment` differs every render -> effect fires every render -> loop

  return null;
}

// FIX: stabilize the returned function AND (if needed) the object
function useThing() {
  const [count, setCount] = useState(0);
  const increment = useCallback(() => setCount((c) => c + 1), []); // stable
  return useMemo(() => ({ count, increment }), [count, increment]); // stable when count is unchanged
}

Senior Engineer Perspective

This is the composition-specific version of the "unstable identity" bug from the chapter's opening bugs question — it's worse in composed hooks because the instability can hide several layers deep, so the component author sees a loop and has to trace it back through two or three custom hooks to find the actual unstable reference. A senior debugging move: use useWhyDidYouUpdate (covered later in this chapter) or simply log dependency array contents to binary-search which layer introduced the instability.

Q32. What's the difference between a hook "wrapping" another hook and a hook "shadowing" its API, and why does shadowing hurt discoverability?

ROI: ★★★☆☆ Frequency: Low

Short Answer

Wrapping adds behavior on top of an inner hook's contract (e.g. useAuthedFetch adding a header to useFetch). Shadowing re-implements an inner hook's entire surface with a slightly different name/shape for no functional reason (e.g. a `useMyDebounce` that does exactly what `useDebounce` does with a renamed parameter). Shadowing hurts discoverability because engineers searching the codebase for "debounce" logic now have to know about two near-identical hooks and guess which one is canonical.

Code Example

// WRAPPING: adds real behavior (auth header), delegates the rest
function useAuthedFetch(url: string) {
  const token = useAuthToken();
  return useFetch(url, { headers: { Authorization: `Bearer ${token}` } });
}

// SHADOWING: adds nothing, just a renamed re-implementation
function useMyDebounce(val: string, ms: number) {
  // ...copy-pasted body identical to useDebounce, different name
}

Senior Engineer Perspective

This comes up in code review more than live interviews, but senior candidates bring it up unprompted when discussing hook libraries at a company: as a codebase grows, an un-owned `hooks/` folder tends to accumulate three slightly different `useDebounce` variants written by different people who didn't know one already existed. Naming this as a real maintenance cost — and the fix (a documented, owned shared-hooks package with a clear "check here first" convention) — signals you've worked in a codebase past the "one team, one repo" size.

Q33. How do you compose multiple independent custom hooks that each need to run cleanup in a specific order (e.g. hook B depends on a resource hook A creates)?

ROI: ★★★☆☆ Frequency: Low

Short Answer

Rather than trying to sequence two independent hooks' effects (React doesn't guarantee ordering between unrelated effects beyond "in the order the hooks were called"), fold the dependency into a single hook that owns both the resource and its dependents' setup/teardown in one effect. If A and B really are separate hooks, have B accept A's return value as an argument, so B's effect naturally depends on — and is scheduled after — A's.

Detailed Answer

React does guarantee that effects run in the order their hooks were declared within one component/hook, and cleanups run in reverse order on unmount — so if hook B is called after hook A, B's effect runs after A's, and on cleanup, B's cleanup runs before A's. That's usually enough. The danger case is when B's effect needs a *value* A produced (not just ordering) — then B must take that value as a parameter so the dependency is explicit and typed, rather than reaching into shared mutable state.

Code Example

// A creates a resource; B explicitly depends on what A returns.
function useSocketConnection(url: string) {
  const [socket, setSocket] = useState<WebSocket | null>(null);
  useEffect(() => {
    const s = new WebSocket(url);
    setSocket(s);
    return () => s.close();
  }, [url]);
  return socket;
}

// B receives A's output explicitly - no implicit ordering assumption needed.
function useSocketSubscription(socket: WebSocket | null, channel: string) {
  useEffect(() => {
    if (!socket) return;                 // A hasn't produced a socket yet
    const onMessage = (e: MessageEvent) => handle(channel, e.data);
    socket.addEventListener("message", onMessage);
    return () => socket.removeEventListener("message", onMessage);
  }, [socket, channel]);
}

function Chat({ url, channel }) {
  const socket = useSocketConnection(url);
  useSocketSubscription(socket, channel); // explicit dependency, not implicit ordering
}

Senior Engineer Perspective

The key insight to state explicitly: don't rely on "hooks run in declaration order" as your dependency mechanism between two hooks that both hold their own internal state — pass the actual value through instead, the same way you'd pass a prop between two components rather than relying on render order and a shared global. It's more verbose but makes the dependency visible in the type signature and in useEffect's dependency array, rather than an invisible ordering assumption that breaks the moment someone reorders the hook calls.

SECTION 7 - DEBOUNCE, THROTTLE & TIMING HOOKS

Q34. What's the actual difference between debounce and throttle, and how does that map onto which hook you'd reach for?

ROI: ★★★★★ Frequency: Extremely High

Short Answer

Debounce delays execution until activity has stopped for a period — useful when you only care about the final state (search-as-you-type, resize-end). Throttle guarantees execution happens at most once per interval while activity continues — useful when you need regular updates during continuous activity (scroll position tracking, mouse-move drag, analytics pings). Debounce can starve you of intermediate updates; throttle guarantees a steady drip of them.

Detailed Answer

Concretely: if a user scrolls continuously for 3 seconds, a 300ms debounced handler fires once, 300ms after scrolling stops. A 300ms throttled handler fires roughly every 300ms during the scroll (roughly 10 times), plus optionally once more at the end (trailing call) depending on implementation. Choosing wrong is a common real bug: debouncing a scroll-position indicator makes it look frozen until you stop scrolling; throttling a search box wastes requests on intermediate keystrokes you didn't need.

Code Example

// Debounce: fires ONCE, after activity settles
function useDebouncedValue<T>(value: T, delay: number): T {
  const [debounced, setDebounced] = useState(value);
  useEffect(() => {
    const id = setTimeout(() => setDebounced(value), delay);
    return () => clearTimeout(id);
  }, [value, delay]);
  return debounced;
}

// Throttle: fires AT MOST once per interval, even during continuous activity
function useThrottledValue<T>(value: T, interval: number): T {
  const [throttled, setThrottled] = useState(value);
  const lastRan = useRef(Date.now());

  useEffect(() => {
    const remaining = interval - (Date.now() - lastRan.current);
    if (remaining <= 0) {
      setThrottled(value);
      lastRan.current = Date.now();
    } else {
      const id = setTimeout(() => {
        setThrottled(value);
        lastRan.current = Date.now();
      }, remaining);
      return () => clearTimeout(id);
    }
  }, [value, interval]);

  return throttled;
}

Senior Engineer Perspective

The strongest answers give one wrong-tool example unprompted (e.g. "if you throttled a search box you'd still fire requests for half-typed queries; if you debounced a scroll progress bar it would visibly lag until the user stops scrolling"). That's a much stronger signal than reciting the textbook definitions, because it proves you've actually hit the wrong choice in practice, not just memorized the terms.

Q35. Build useThrottledCallback with both leading and trailing edge options. Why do libraries expose both?

ROI: ★★★★☆ Frequency: Medium

Short Answer

"Leading" fires immediately on the first call in a burst, then ignores calls until the interval passes. "Trailing" additionally (or instead) fires once more after the burst ends, using the last call's arguments, so you don't miss the "final" value. Libraries like Lodash expose both because different use cases need different guarantees: leading gives instant feedback (a button that shouldn't double-fire), trailing ensures you never lose the last state (a resize handler that must reflect the final size).

Code Example

function useThrottledCallback<A extends unknown[]>(
  fn: (...args: A) => void,
  interval: number,
  { leading = true, trailing = true } = {}
) {
  const fnRef = useRef(fn);
  useEffect(() => { fnRef.current = fn; }, [fn]);

  const lastRan = useRef<number>(0);
  const timer = useRef<ReturnType<typeof setTimeout>>();
  const pendingArgs = useRef<A | null>(null);

  useEffect(() => () => clearTimeout(timer.current), []);

  return useCallback((...args: A) => {
    const now = Date.now();
    const elapsed = now - lastRan.current;

    if (elapsed >= interval) {
      if (leading) { fnRef.current(...args); lastRan.current = now; }
      else { pendingArgs.current = args; } // still schedule a trailing call below
    } else {
      pendingArgs.current = args;
    }

    if (trailing && !timer.current) {
      timer.current = setTimeout(() => {
        timer.current = undefined;
        if (pendingArgs.current) {
          fnRef.current(...pendingArgs.current);
          lastRan.current = Date.now();
          pendingArgs.current = null;
        }
      }, interval - (elapsed > 0 ? elapsed % interval : 0));
    }
  }, [interval, leading, trailing]);
}

Senior Engineer Perspective

This is a good "can you actually implement it, not just describe it" filter — the timing bookkeeping (tracking both "when did we last run" and "what's the latest pending call") trips up most people who've only ever imported lodash.throttle. If you can't derive it from scratch, it's fine to say so honestly and instead explain clearly *why* leading/trailing exist and reach for the library — that's a more honest and still strong answer than fumbling a live derivation.

Q36. Build useInterval "done correctly." What's wrong with calling setInterval directly inside useEffect with an empty dependency array?

ROI: ★★★★★ Frequency: Extremely High

Short Answer

useEffect(() => { setInterval(callback, delay); }, []) captures whatever callback closed over at mount time and never updates it — every tick calls the original render's closure forever, even though the component has re-rendered dozens of times with fresh props/state since. This is the canonical "stale closure in setInterval" bug. Dan Abramov's fix: keep the latest callback in a ref, and have the interval's tick always call ref.current, so the interval itself is only ever created/destroyed when delay changes, not on every render.

Detailed Answer

Two separate effects do two separate jobs: one effect's only job is keeping a ref pointed at the latest callback (runs every render, cheap, no side effect beyond a ref write). The other effect's only job is creating and tearing down the actual setInterval, and it only needs to depend on delay — because the tick function calls through the ref, it always executes the freshest closure without needing to recreate the timer.

Code Example

// BROKEN: closure captured once, never updated, callback runs stale forever
function useIntervalBad(callback: () => void, delay: number) {
  useEffect(() => {
    const id = setInterval(callback, delay); // `callback` frozen at mount
    return () => clearInterval(id);
  }, []); // deps lie: this DOES depend on callback, just doesn't say so
}

// CORRECT: ref always holds the latest callback; timer only reacts to `delay`
function useInterval(callback: () => void, delay: number | null) {
  const savedCallback = useRef(callback);

  useEffect(() => {
    savedCallback.current = callback; // runs every render, cheap
  }, [callback]);

  useEffect(() => {
    if (delay === null) return;               // null delay = paused
    const id = setInterval(() => savedCallback.current(), delay);
    return () => clearInterval(id);
  }, [delay]); // timer only recreated when the INTERVAL itself changes
}

// Usage: callback can reference fresh state every tick, interval stays stable
function Clock() {
  const [count, setCount] = useState(0);
  useInterval(() => setCount(count + 1), 1000); // reads fresh `count` every render
  return <p>{count}</p>;
}

Senior Engineer Perspective

This exact pattern is one of the most-cited blog posts in the React ecosystem (Dan Abramov's "Making setInterval Declarative with React Hooks") precisely because it's such a common trap. A great follow-up you should anticipate: "why not just add callback to the second effect's deps and skip the ref entirely?" — because then every render that produces a new inline callback (which is most renders, unless the caller memoizes it) tears down and recreates the actual interval, resetting its timing and potentially causing visible jank; the ref decouples "the interval's lifecycle" from "which closure it happens to call."

Q37. Build useTimeout, and explain why clearing a timeout in cleanup matters even for a "one-shot" timer.

ROI: ★★★☆☆ Frequency: Medium

Short Answer

useTimeout(callback, delay) mirrors useInterval but with setTimeout/clearTimeout. Even though a timeout only fires once, you still must clear it in the effect's cleanup — otherwise, if the component unmounts (or delay changes) before it fires, the stale timeout still fires later and calls a closure over stale/unmounted state, which can throw or silently do the wrong thing.

Code Example

function useTimeout(callback: () => void, delay: number | null) {
  const savedCallback = useRef(callback);
  useEffect(() => { savedCallback.current = callback; }, [callback]);

  useEffect(() => {
    if (delay === null) return;
    const id = setTimeout(() => savedCallback.current(), delay);
    return () => clearTimeout(id); // cancel if we unmount/re-run before it fires
  }, [delay]);
}

// Usage: auto-dismiss toast after 3s, but cancel cleanly if it's dismissed early
function Toast({ onDismiss }: { onDismiss: () => void }) {
  useTimeout(onDismiss, 3000);
  return <div className="toast">Saved!</div>;
}

Senior Engineer Perspective

Candidates often assume cleanup is only about intervals/subscriptions that repeat, and skip it for "it only fires once anyway" timeouts. Push back on that: an uncancelled timeout is exactly how you get the classic warning about calling setState on an unmounted component — the fix isn't to suppress the warning, it's to actually cancel the pending work when it's no longer relevant, which is precisely what the effect cleanup contract is for.

Q38. Build a useCountdown hook (e.g. for an OTP resend timer) that stays accurate even if the tab is backgrounded.

ROI: ★★★☆☆ Frequency: Medium

Short Answer

A naive countdown decrements a counter once per second via setInterval — but browsers throttle timers in backgrounded tabs, so "one tick per second" silently becomes "one tick every several seconds," and the displayed countdown drifts from real elapsed time. The fix: store the target end timestamp (not a remaining-seconds counter) and, on each tick (or on visibility change), recompute remaining time as endTime - Date.now() — wall-clock math is immune to how many ticks were actually delivered.

Code Example

function useCountdown(totalSeconds: number) {
  const [remaining, setRemaining] = useState(totalSeconds);
  const endTimeRef = useRef(Date.now() + totalSeconds * 1000);

  useEffect(() => {
    endTimeRef.current = Date.now() + totalSeconds * 1000; // reset target on restart
  }, [totalSeconds]);

  useEffect(() => {
    const tick = () => {
      const secondsLeft = Math.max(0, Math.round((endTimeRef.current - Date.now()) / 1000));
      setRemaining(secondsLeft);
    };
    tick(); // sync immediately, don't wait a full second for the first paint
    const id = setInterval(tick, 250); // tick faster than 1s so drift self-corrects
    return () => clearInterval(id);
  }, []);

  return remaining;
}

Senior Engineer Perspective

This question tests whether you understand that setInterval's delay is a minimum, not a guarantee — background tab throttling (and even just event-loop congestion) means "tick every 1000ms" can silently become "tick every 4000ms." Deriving remaining time from a fixed end-timestamp rather than decrementing a counter is the general fix for any UI timer, and it's the same principle behind accurate stopwatch/progress-bar implementations.

Q39. How would you debounce a value whose delay itself changes dynamically (e.g. a "typing speed adaptive" search box)?

ROI: ★★☆☆☆ Frequency: Low

Short Answer

Since delay is already a dependency of the debounce effect, changing it takes effect on the next value change automatically — no special handling needed, as long as you didn't hardcode the delay as a constant closed over once. The subtlety is deciding whether an in-flight timer should be cancelled and restarted with the new delay immediately, or only apply the new delay to the next debounce cycle; usually the latter is what users expect (don't restart a timer that's about to fire).

Code Example

function useDebounce<T>(value: T, delay: number): T {
  const [debounced, setDebounced] = useState(value);
  useEffect(() => {
    const id = setTimeout(() => setDebounced(value), delay);
    return () => clearTimeout(id);
  }, [value, delay]); // delay IS reactive - a dynamic delay just works
  return debounced;
}

// Adaptive delay: fast typers get a shorter debounce, slow typers a longer one.
function useAdaptiveDebounce(value: string) {
  const lastKeyTime = useRef(Date.now());
  const [delay, setDelay] = useState(400);

  useEffect(() => {
    const now = Date.now();
    const gap = now - lastKeyTime.current;
    lastKeyTime.current = now;
    setDelay(gap < 150 ? 250 : 500); // fast typing -> shorter wait, slow -> longer
  }, [value]);

  return useDebounce(value, delay);
}

Senior Engineer Perspective

This is more of a design conversation than a hard technical trap — the interviewer wants to see you reason about the UX tradeoff (does changing the delay mid-flight restart the pending timer, extending the wait unexpectedly?) rather than just confirming the dependency array works mechanically. Flag that adaptive delays add real complexity for a marginal UX gain, and a fixed, well-chosen delay (usually 300-500ms) is the right default for almost all products.

Q40. Why does usePrevious rely on refs and effect timing rather than just diffing props directly during render?

ROI: ★★★★☆ Frequency: Medium

Short Answer

During render, React hasn't committed anything yet — there's no "before" to compare against except what you stored yourself from the last commit. A ref is the only tool that (a) persists across renders and (b) doesn't trigger a re-render when written, so it's the correct place to stash "what the value was last time," updated in an effect that runs strictly after the render that reads it.

Detailed Answer

You cannot correctly compute "previous value" purely during render by, say, comparing a prop to itself, because render has no memory across calls — each render call is a fresh function invocation with no persisted local variables. State could technically hold "previous," but writing to state during render to update it would either be disallowed (calling a setter during render for a value that changes every render causes an infinite loop unless carefully guarded) or would trigger an extra render pass. Refs sidestep both problems: mutate freely, no render triggered, value survives across renders.

Code Example

function usePrevious<T>(value: T): T | undefined {
  const ref = useRef<T>();
  useEffect(() => { ref.current = value; }, [value]); // write AFTER this render's read
  return ref.current;                                    // read: still holds LAST render's value
}

// A subtler variant: update the ref during render (not in an effect) when you
// need "previous" to be correct even before the browser paints (e.g. for a
// derived comparison used in the SAME render, not a later effect).
function usePreviousDuringRender<T>(value: T): T | undefined {
  const currentRef = useRef<T>(value);
  const previousRef = useRef<T>();
  if (currentRef.current !== value) {
    previousRef.current = currentRef.current;
    currentRef.current = value;
  }
  return previousRef.current;
}

Senior Engineer Perspective

The advanced follow-up here is the "update during render" variant — it's a legitimate, React-sanctioned pattern (documented as safe specifically for refs, unlike other render-time side effects) when you need the previous value available immediately in the same render rather than one render later via an effect. Knowing both versions, and precisely when each is needed, is a stronger answer than only knowing the effect-based one.

Q41. What are the cleanup and correctness pitfalls of building a useAnimationFrame hook for a smooth, continuous animation?

ROI: ★★★☆☆ Frequency: Low

Short Answer

requestAnimationFrame needs the same "latest callback via ref, single effect owns the loop lifecycle" treatment as setInterval, plus one extra concern: the loop must re-schedule itself (calling requestAnimationFrame again inside the callback) rather than being set up once, and must cancel via cancelAnimationFrame in cleanup using the exact id from the last scheduled frame, not a stale one.

Code Example

function useAnimationFrame(callback: (deltaMs: number) => void) {
  const callbackRef = useRef(callback);
  useEffect(() => { callbackRef.current = callback; }, [callback]);

  useEffect(() => {
    let frameId: number;
    let lastTime = performance.now();

    const loop = (time: number) => {
      const delta = time - lastTime;
      lastTime = time;
      callbackRef.current(delta);
      frameId = requestAnimationFrame(loop); // re-schedule itself every frame
    };

    frameId = requestAnimationFrame(loop);
    return () => cancelAnimationFrame(frameId); // cancel the LATEST scheduled frame
  }, []); // loop lifecycle is independent of the (possibly changing) callback
}

// Usage
function ProgressBar() {
  const [x, setX] = useState(0);
  useAnimationFrame((delta) => setX((prev) => (prev + delta * 0.1) % 100));
  return <div style={{ transform: `translateX(${x}px)` }} />;
}

Senior Engineer Perspective

The subtlety worth naming: frameId must be a local variable captured by the closure of that specific effect run, not a ref shared across runs — if the effect re-ran (which it shouldn't here, given empty deps, but could in more complex versions), an incorrectly shared id variable could cancel the wrong frame. Also mention that heavy work inside the callback (layout thrashing, synchronous DOM reads) will still jank the animation regardless of how clean the hook's lifecycle management is — the hook manages scheduling, not the cost of the work being scheduled.

SECTION 8 - AVOIDING STALE CLOSURES IN CUSTOM HOOKS

Q42. What exactly is a "stale closure" in React, mechanically — not just "old state," but why it happens?

ROI: ★★★★★ Frequency: Extremely High

Short Answer

Every render of a function component creates an entirely new function scope, with its own copies of props/state variables as they were at that render. Any function defined during that render (an event handler, an effect callback) closes over those specific variable bindings. If that function is handed to something long-lived — a timer, an event listener, a promise chain — and never replaced, it keeps referencing the values from the render it was created in, even after later renders have "moved on" with new values.

Detailed Answer

This isn't a React quirk — it's ordinary JavaScript closure behavior; React just creates the conditions for it constantly because every render is a fresh function call. The bug surfaces specifically when a closure is captured once and then invoked later, outside the normal render-driven flow: inside a setTimeout/setInterval callback, an event listener attached in an effect with an empty dependency array, or a promise .then() resolved long after the triggering render. The closure isn't "wrong" — it's doing exactly what JavaScript closures do; the bug is architectural: something was captured once when it needed to be captured fresh each time, or read through a mechanism (a ref) that doesn't go stale.

Code Example

function Counter() {
  const [count, setCount] = useState(0);

  useEffect(() => {
    const id = setInterval(() => {
      console.log(count); // closes over `count` AS OF THE RENDER THIS EFFECT RAN IN
    }, 1000);
    return () => clearInterval(id);
  }, []); // empty deps -> effect (and its closure) never re-created -> always logs 0

  return <button onClick={() => setCount((c) => c + 1)}>{count}</button>;
}

Senior Engineer Perspective

Interviewers use this as a "do you actually understand closures, or just pattern-match the fix" check. A strong answer explains the mechanism (fresh scope per render, closures over that scope's bindings) before jumping to the fix — that ordering is the tell. A weak answer jumps straight to "use a ref" without being able to explain why the bug happens in the first place, which falls apart under a follow-up like "why doesn't adding count to the deps array cause the SAME problem?"

Q43. Adding the "missing" dependency fixes the stale closure, but sometimes causes a different bug. What is it, and when does it happen?

ROI: ★★★★★ Frequency: High

Short Answer

Adding a fast-changing value to an effect's dependency array fixes staleness but makes the effect re-run on every change to that value — which, for something like a setInterval subscription, means tearing down and recreating the timer (and its underlying JS timer object) on every tick, potentially causing drift, flicker, or defeating the entire point of "one persistent interval." The fix-for-the-fix is the ref pattern: depend on the ref (which is stable) for subscription lifecycle, and let the ref's contents update every render via a separate, cheap effect.

Detailed Answer

This is exactly why useInterval's "correct" implementation (Q36) splits into two effects: one that updates a ref every render (fixing staleness without triggering the expensive effect) and one that owns the interval's actual lifecycle, keyed only on the truly structural dependency (delay). If you'd instead just added count to the interval effect's deps to silence the lint warning, you'd fix staleness but reset the timer every single tick, which for many timers (animations, network polling with backoff) is a worse bug than the one you started with.

Code Example

// "Fixed" staleness by adding the dep - but now recreates the interval every tick
useEffect(() => {
  const id = setInterval(() => console.log(count), 1000);
  return () => clearInterval(id);
}, [count]); // interval torn down + rebuilt every time count changes = every second

// Correct: subscription lifecycle is stable, only the READ VALUE is fresh
const countRef = useRef(count);
useEffect(() => { countRef.current = count; }, [count]); // cheap, no side effect
useEffect(() => {
  const id = setInterval(() => console.log(countRef.current), 1000);
  return () => clearInterval(id);
}, []); // interval created exactly once

Senior Engineer Perspective

This is the question that separates people who've internalized the ref pattern from people who apply it by rote. The core judgment call to articulate: "does this effect's identity (the subscription/timer/listener itself) need to depend on this value, or does only the logic inside need the latest value?" If it's the latter, the value belongs behind a ref, not in the dependency array.

Q44. What is the "useEffectEvent" pattern (aka useEvent), and what problem is it designed to solve that refs alone solve clumsily?

ROI: ★★★★☆ Frequency: Medium

Short Answer

The ref-based "latest callback" pattern works but requires writing the same two-effect boilerplate every time. useEffectEvent (an experimental React API, formerly discussed as useEvent) packages that exact pattern into one hook: it returns a stable function that always calls the latest version of the logic you passed in, without needing to be listed in a dependency array and without ever going stale — giving you "read the latest render's values" semantics without the effect re-running.

Detailed Answer

The mental model React's docs give: an "Effect Event" is non-reactive logic extracted out of an Effect — it can read the latest props/state (unlike a plain function closed over stale values) but, unlike a regular value, it is intentionally excluded from the dependency array and never causes the Effect to re-synchronize. This directly targets the Q43 problem: you want the interval's *lifecycle* to depend only on delay, but the tick logic to always see fresh state — which is precisely what an Effect Event is designed to express in one primitive instead of the two-effects-plus-ref workaround.

Code Example

// Conceptual usage (experimental API, naming may still change across React versions)
import { useEffect } from "react";
import { experimental_useEffectEvent as useEffectEvent } from "react";

function useInterval(callback: () => void, delay: number) {
  const onTick = useEffectEvent(() => {
    callback(); // always sees the LATEST `callback`, never stale
  });

  useEffect(() => {
    const id = setInterval(() => onTick(), delay);
    return () => clearInterval(id);
  }, [delay]); // onTick is intentionally NOT a dependency - it's non-reactive by design
}

// Roughly equivalent to (and today, in stable React, IMPLEMENTED as) the ref pattern:
function useIntervalRefVersion(callback: () => void, delay: number) {
  const ref = useRef(callback);
  useEffect(() => { ref.current = callback; });
  useEffect(() => {
    const id = setInterval(() => ref.current(), delay);
    return () => clearInterval(id);
  }, [delay]);
}

Senior Engineer Perspective

Be upfront about the API's status: as of the current stable React release this is still experimental/RFC-stage in most codebases, so most production code today still hand-rolls the ref pattern. Mentioning it shows you're tracking where React is heading (making "non-reactive read of the latest value" a first-class concept) without overclaiming it's shipped and stable everywhere — overstating an experimental API's availability is itself a red flag to a sharp interviewer.

Q45. A custom hook exposes a callback prop to a memoized child. The child stops receiving new data even though the parent's state clearly updated. What's the likely stale-closure bug?

ROI: ★★★★☆ Frequency: High

Short Answer

If the callback passed to the memoized child was memoized once with useCallback(fn, []) (empty deps) "to keep it stable," it now closes over the very first render's state forever — the identity is stable (good for React.memo) but the logic inside is stale (bad for correctness). The fix isn't removing memoization, it's fixing what the callback reads: either add correct dependencies (accepting the identity will change when they do) or use the functional-updater/ref pattern so the callback body reads fresh state without needing to be in the dependency array.

Code Example

// BUG: stable identity, but reads stale `items` forever
function Parent() {
  const [items, setItems] = useState<string[]>([]);

  const addItem = useCallback((item: string) => {
    setItems([...items, item]); // closes over `items` from mount - always starts from []
  }, []); // empty deps chosen "to keep it stable" - wrong tradeoff here

  return <MemoChild onAdd={addItem} />;
}

// FIX: use the functional updater - no need to read `items` from the closure at all
function ParentFixed() {
  const [items, setItems] = useState<string[]>([]);

  const addItem = useCallback((item: string) => {
    setItems((prev) => [...prev, item]); // reads CURRENT state at update time, not closure time
  }, []); // now correctly has no reactive dependencies - genuinely safe to memoize

  return <MemoChild onAdd={addItem} />;
}

Senior Engineer Perspective

The lesson to generalize: the functional updater form of a state setter isn't just a nice-to-have, it's often what makes an empty dependency array actually correct instead of merely lint-silenced. Before reaching for a ref or "just add the dependency," check whether the callback only needs to read the state it's about to update — if so, the updater form eliminates the closure problem entirely rather than working around it.

Q46. Does React's Strict Mode double-invoking effects in development help you find stale closure bugs? How?

ROI: ★★★☆☆ Frequency: Medium

Short Answer

Not directly for stale closures (that's more of an exhaustive-deps lint concern), but Strict Mode's mount → unmount → remount cycle in development is excellent at surfacing the closely-related bug of missing cleanup, which often travels together with stale closures in the same broken effect. If your effect leaks a listener/timer because cleanup is missing or wrong, Strict Mode's extra mount/unmount pass in dev will double up the leaked resource, making the bug loud instead of silent.

Detailed Answer

Strict Mode intentionally simulates what real-world remounting looks like (tab restoration, `key`-based remounts, future features like offscreen rendering) by running mount → cleanup → mount again in development only. An effect with a stale closure won't necessarily misbehave differently under this — the closure staleness is about which render's values it reads, not how many times it mounts. But an effect that's missing a cleanup function, or whose cleanup doesn't fully undo what setup did, will visibly double up its side effect (two intervals ticking, two listeners firing per event) under Strict Mode, which is your signal to go fix it — usually finding a stale-closure bug living right next to the missing-cleanup bug in the same effect.

Code Example

useEffect(() => {
  console.log("subscribing");     // logs TWICE in dev under StrictMode (mount, unmount, remount)
  const id = setInterval(tick, 1000);
  // return () => clearInterval(id);   <-- if commented out/missing,
  return () => clearInterval(id);      //     you'd see TWO intervals ticking - a loud, easy-to-spot bug
}, []);

Senior Engineer Perspective

Don't overclaim what Strict Mode catches — it's not a stale-closure detector, it's a cleanup-correctness detector, and the two bugs frequently co-occur because both stem from "this effect wasn't written to run more than once." The precise, honest framing (rather than "Strict Mode catches stale closures") is what separates a candidate who's read the React docs closely from one repeating a vague summary.

Q47. Build a useLatest(value) utility hook and explain how it generalizes the "ref holding the freshest value" pattern.

ROI: ★★★★☆ Frequency: Medium

Short Answer

useLatest is the minimal, reusable extraction of the ref-update pattern seen throughout this section: it takes any value (a callback, a piece of state, props) and returns a ref that's kept in sync every render, so any long-lived closure can read latestRef.current instead of the value directly and never go stale — without every hook re-deriving the "shadow ref + sync effect" boilerplate from scratch.

Code Example

function useLatest<T>(value: T) {
  const ref = useRef(value);
  ref.current = value; // updated DURING render - always current by the time anything reads it
  return ref;
}

// Every stale-closure fix in this section reduces to this one primitive:
function useInterval(callback: () => void, delay: number) {
  const latestCallback = useLatest(callback);
  useEffect(() => {
    const id = setInterval(() => latestCallback.current(), delay);
    return () => clearInterval(id);
  }, [delay, latestCallback]); // latestCallback (the ref object) is itself stable across renders
}

function useOnClickOutside(ref: RefObject<HTMLElement>, handler: (e: Event) => void) {
  const latestHandler = useLatest(handler);
  useEffect(() => {
    const listener = (e: Event) => {
      if (ref.current && !ref.current.contains(e.target as Node)) latestHandler.current(e);
    };
    document.addEventListener("mousedown", listener);
    return () => document.removeEventListener("mousedown", listener);
  }, [ref, latestHandler]);
}

Senior Engineer Perspective

Note the subtle but important detail: updating ref.current = value directly during render (rather than in a useEffect) is safe and is React's documented escape hatch for exactly this case, and it means the ref is current even for logic that runs synchronously during the same render (unlike the effect-based version, which lags one commit behind). Knowing you can mutate a ref during render — as long as you're not reading back a value you just wrote in a way that affects this render's output — is the kind of precise rule that shows real depth.

Q48. How do promise-based stale closures differ from timer-based ones, and what's the fix when a fetch resolves after the component has "moved on"?

ROI: ★★★★☆ Frequency: High

Short Answer

Same root cause (a closure captured at one render, invoked later) but the trigger is different: instead of a repeating timer, it's a one-shot async operation. The classic case: fetch data for id=1, the user quickly navigates to id=2 before the first request resolves, and the resolved handler — still closing over id=1's render — overwrites the now-current id=2 data. The fix is the same family as timers: check a ref/ignore-flag before applying the result, since you can't "add a dependency" to a promise the way you can to a `useEffect`.

Code Example

function useUserProfile(userId: string) {
  const [profile, setProfile] = useState<Profile | null>(null);

  useEffect(() => {
    let ignore = false;

    fetchUser(userId).then((data) => {
      // Without this check: a slow response for an OLD userId can still land
      // and overwrite the profile for whatever userId is CURRENT now.
      if (!ignore) setProfile(data);
    });

    return () => { ignore = true; }; // invalidate this closure's result once superseded
  }, [userId]);

  return profile;
}

Senior Engineer Perspective

The framing to offer: promises don't have a "dependency array" mechanism to re-run automatically, so the closure-freshness problem there can only be solved by invalidating stale results after the fact (ignore flag / AbortController) rather than "keeping the read fresh" the way a ref does for timers. Naming that distinction — proactive freshness (refs, for ongoing subscriptions) versus reactive invalidation (ignore flags, for one-shot async) — shows you understand these are related but not identical problems.

Q49. How would you unit test that a hook does NOT have a stale closure bug — i.e., prove a fix actually works rather than just eyeballing the code?

ROI: ★★★☆☆ Frequency: Medium

Short Answer

Use fake timers, advance them across multiple renders with changing props, and assert the effect used the value from the latest render, not the first one. The test should rerender the hook with a new value before advancing the timer, then confirm the eventual call used the new value — a naive stale-closure implementation will fail this by using the old one.

Code Example

import { renderHook } from "@testing-library/react";
import { useInterval } from "./useInterval";

test("interval always calls the LATEST callback, not the one from mount", () => {
  jest.useFakeTimers();
  const calls: number[] = [];

  const { rerender } = renderHook(
    ({ n }) => useInterval(() => calls.push(n), 1000),
    { initialProps: { n: 1 } }
  );

  jest.advanceTimersByTime(1000);       // tick #1: should record 1
  rerender({ n: 2 });                   // callback identity changes - value bumped to 2
  jest.advanceTimersByTime(1000);       // tick #2: SHOULD record 2, not 1, if fixed

  expect(calls).toEqual([1, 2]);        // a stale-closure bug would produce [1, 1]
  jest.useRealTimers();
});

Senior Engineer Perspective

This is a great "prove it" question for candidates who claim they know the ref pattern — writing the regression test forces you to think about what observable behavior actually distinguishes "fixed" from "broken," rather than just reciting the pattern. Mention that this exact test, run against the "broken" `useIntervalBad` from earlier in this section, is a fast way to demonstrate the bug concretely in a code review or a pairing session rather than arguing about it in the abstract.

SECTION 9 - PERFORMANCE-FOCUSED CUSTOM HOOKS

Q50. Build useWhyDidYouUpdate — a debugging hook that logs exactly which props changed and caused a re-render.

ROI: ★★★★☆ Frequency: High

Short Answer

Keep the previous render's props in a ref, and on every render compare each key against the previous value with Object.is. Log only the keys that actually differ, along with their before/after values — this immediately tells you whether a re-render was caused by a genuinely new value or by a referentially-new-but-logically-same object/function (the most common needless-re-render culprit).

Code Example

function useWhyDidYouUpdate(name: string, props: Record<string, unknown>) {
  const previousProps = useRef<Record<string, unknown>>();

  useEffect(() => {
    if (previousProps.current) {
      const allKeys = Object.keys({ ...previousProps.current, ...props });
      const changes: Record<string, { from: unknown; to: unknown }> = {};

      allKeys.forEach((key) => {
        if (!Object.is(previousProps.current![key], props[key])) {
          changes[key] = { from: previousProps.current![key], to: props[key] };
        }
      });

      if (Object.keys(changes).length) {
        console.log("[why-did-you-update]", name, changes);
      }
    }
    previousProps.current = props;
  });

  // NOTE: no dependency array - must run after EVERY render to compare consecutive ones.
}

// Usage: drop into any suspect component during a perf investigation
function ExpensiveRow(props: RowProps) {
  useWhyDidYouUpdate("ExpensiveRow", props);
  return /* ... */ null;
}

Senior Engineer Perspective

The detail worth calling out unprompted: this hook deliberately has no dependency array, because it needs to run after literally every render to compare it against the previous one — the one case where "missing deps" is intentional and correct, not a bug. Also mention this is dev-only tooling (strip it via process.env.NODE_ENV or a build-time flag) — shipping it to production adds overhead and noisy console logs for no benefit, and most teams reach for React DevTools' built-in "highlight updates" and Profiler tab first, using a hand-rolled version only when they need scriptable, per-prop diffing DevTools doesn't expose directly.

Q51. Build a useRenderCount hook. What legitimate uses does it have beyond curiosity, and what's the risk of leaving it in production code?

ROI: ★★★☆☆ Frequency: Medium

A one-line ref incremented every render, returned as the count. Legitimate uses: asserting in tests that a component doesn't re-render more than expected after a memoization fix, or surfacing a live render-count badge in a dev-only perf overlay. function useRenderCount() {

The interviewer is checking you understand this is a diagnostic, not a piece of business logic — the risk framing matters more than the one-line implementation. Q52. Write a hook wrapping useMemo that also logs when the memoized computation actually re-runs, to debug an under- or over-memoized value.

ROI: ★★★☆☆ Frequency: Medium

Wrap the factory function passed to useMemo so it logs on every actual invocation (not every render — useMemo already skips re-running the factory when deps are unchanged). Code Example

function useTracedMemo<T>(factory: () => T, deps: unknown[], label: string): T {

    }
    return factory();
  }, deps); // deps still control invalidation exactly as with plain useMemo
}

// Usage: suspect this expensive sort is re-running more than it should
function List({ items, sortKey }) {

  );

Tie this back to a real investigation: if the log fires on every render, the dependency (often items, if it's a new array reference from an upstream .filter() or .map() called inline every render) isn't actually stable, and memoizing the computation is masking — not fixing — an unstable upstream reference. The fix is usually upstream (memoize or stabilize items itself), not deeper memoization downstream. Q53. When does wrapping every returned function from a custom hook in useCallback actually help, and when is it pure overhead?

ROI: ★★★★★ Frequency: Extremely High

Short Answer

useCallback only pays for itself when the function's stable identity is actually consumed somewhere that cares — as a dependency of another useEffect/useMemo, or as a prop to a React.memo-wrapped child. If the function is only ever called inline (onClick={() => doThing()}) and never passed down or depended on, wrapping it in useCallback adds a comparison and a cache slot for zero benefit — you're paying overhead to stabilize an identity nobody reads.

Detailed Answer

The reflexive "wrap every function in useCallback" habit, common in codebases that over-apply lint auto-fixes, misunderstands what the hook buys you. useCallback doesn't make the function itself faster to create or call — creating a fresh closure each render is genuinely cheap in V8. Its entire value proposition is identity stability across renders, and that's only valuable when something downstream does an identity comparison against it. A custom hook's authors should ask, for each returned function: "would a consumer plausibly memo a child on this, or depend on it in an effect?" If yes, memoize; if it's just going to be inline-invoked, don't bother.

Code Example

function useCounter() {
  const [count, setCount] = useState(0);

  // WORTH memoizing: plausible this gets passed to a memoized child, or into
  // another hook's dependency array (e.g. useEffect(() => increment(), [increment])).
  const increment = useCallback(() => setCount((c) => c + 1), []);

  // Also worth memoizing for the SAME reason - consistency in a public hook API
  // callers will pass down as props matters more than any one function's cost.
  const reset = useCallback(() => setCount(0), []);

  return { count, increment, reset };
}

// Contrast: a function that's clearly only ever called inline within THIS component
function Widget() {
  const [open, setOpen] = useState(false);
  // No useCallback here - it's invoked directly, never passed anywhere, never a dep.
  const handleClick = () => setOpen((o) => !o);
  return <button onClick={handleClick}>Toggle</button>;
}

Senior Engineer Perspective

A subtlety worth stating: for a public custom hook whose consumers you don't control, it's often correct to memoize returned functions defensively even if the current call sites don't strictly need it — because you can't predict every future consumer, and changing a hook's return-value stability later is a breaking change for anyone who came to depend on it. Internal, single-use helper functions inside one component don't carry that same obligation. This is the kind of "it depends, and here's exactly what it depends on" answer that separates senior from rote-memorized "always/never" answers.

Q54. Build a useDeepCompareMemo (or useDeepCompareEffect) hook. Why is this usually a smell rather than a good solution?

ROI: ★★★☆☆ Frequency: Medium

Short Answer

Instead of comparing dependencies by reference (Object.is, what React does natively), a deep-compare variant serializes or recursively diffs them, so a new object with the same contents doesn't re-trigger the effect/memo. It solves the "unstable reference from upstream" problem without fixing it — which is exactly the smell: you're paying a real (and sometimes surprising, e.g. on huge objects) comparison cost every render to paper over an instability that's usually cheaper and more correct to fix at the source with `useMemo`/`useCallback` upstream.

Code Example

import { useRef } from "react";
import isEqual from "lodash/isEqual";

function useDeepCompareMemoize<T>(value: T): T {
  const ref = useRef<T>(value);
  if (!isEqual(value, ref.current)) {
    ref.current = value; // only update the ref when contents actually differ
  }
  return ref.current; // stable reference as long as CONTENTS are unchanged
}

function useDeepCompareEffect(effect: () => void | (() => void), deps: unknown[]) {
  useEffect(effect, [useDeepCompareMemoize(deps)]); // deep-compared, then treated as one dep
}

// Usage: params comes from a parent that recreates the object every render
function Report({ params }: { params: { from: string; to: string } }) {
  useDeepCompareEffect(() => {
    fetchReport(params);
  }, [params]); // won't re-fire just because `params` is a new (but equal) object
}

Senior Engineer Perspective

The strongest answer leads with the tradeoff, not the implementation: deep comparison cost scales with the size and depth of the object, can be surprisingly expensive on large payloads, and — worse — silently hides the real bug (an upstream component recreating an object every render for no reason) instead of fixing it. Reach for this only when you don't control the upstream code producing the unstable reference (a third-party library, a prop you can't change); when you do control it, flattening dependencies or memoizing upstream is almost always the better fix.

Q55. How would you build a hook that measures and reports a component's own render duration, without relying on React DevTools?

ROI: ★★★☆☆ Frequency: Low

Short Answer

Record a timestamp at the start of the function body (synchronously, during render) and compare it against a timestamp taken in a useLayoutEffect (which fires synchronously after DOM mutations, before paint) — the difference approximates render + commit time for that pass. This is a rough hand-rolled substitute for what React's built-in <Profiler> component already gives you more accurately and with less risk of the measurement itself skewing results.

Code Example

function useRenderTiming(label: string) {
  const renderStart = performance.now(); // captured fresh on every render, during render

  useLayoutEffect(() => {
    const duration = performance.now() - renderStart;
    if (duration > 16) { // slower than one 60fps frame budget - worth flagging
      console.warn(`[render-timing] ${label}: ${duration.toFixed(1)}ms`);
    }
  }); // no deps - must compare against THIS render's start every time
}

// Prefer React's built-in Profiler for anything beyond a quick local check:
<Profiler id="Dashboard" onRender={(id, phase, actualDuration) => {
  if (actualDuration > 16) console.warn(id, phase, actualDuration);
}}>
  <Dashboard />
</Profiler>

Senior Engineer Perspective

The honest answer here volunteers the built-in <Profiler> API and the DevTools Profiler tab as the correct first tool, and frames the hand-rolled version as a lightweight always-on dev-time tripwire rather than a replacement. A hand-rolled timer also can't distinguish "React's render phase" from "the commit/DOM-mutation phase" as cleanly as Profiler's actualDuration/baseDuration split does, which is worth naming as a known limitation.

Q56. Build a useStableCallback-style hook — one that guarantees a truly stable identity across renders while always executing the latest logic, without a dependency array at all.

ROI: ★★★★☆ Frequency: Medium

Short Answer

This is exactly the useLatest-backed pattern from the stale-closures section, packaged as its own named hook: store the callback in a ref updated every render, and return a memoized wrapper (created once, via useCallback with an empty array, or even a plain useRef holding a stable function) that simply forwards to ref.current. The wrapper's identity truly never changes, yet it always calls the freshest logic — solving the exact tension between "needs to be stable for memoization" and "needs to read current values" that a plain useCallback([deps]) can't satisfy simultaneously once the deps change often.

Code Example

function useStableCallback<A extends unknown[], R>(fn: (...args: A) => R) {
  const ref = useRef(fn);
  useLayoutEffect(() => { ref.current = fn; }); // sync before effects/paint, every render

  // Created exactly ONCE - true referential stability for the lifetime of the component.
  return useRef((...args: A) => ref.current(...args)).current;
}

// Usage: pass a stable identity to a memoized child, while the handler
// itself can freely close over ever-changing state.
function Parent() {
  const [count, setCount] = useState(0);
  const onClick = useStableCallback(() => setCount(count + 1)); // reads FRESH `count`
  return <MemoChild onClick={onClick} />; // onClick's identity NEVER changes
}

Senior Engineer Perspective

This is close to what the experimental useEffectEvent aims to standardize, and a sharp interviewer may ask exactly that: "how is this different from `useEffectEvent`?" The honest answer: functionally very similar for this use case, but `useStableCallback` here is usable directly as an event handler prop (not restricted to being called from inside Effects the way `useEffectEvent` currently is), while also carrying the same caveat — because it's stable-but-always-fresh, it deliberately breaks the assumption that a `useCallback` with real dependencies gives you (namely, that its identity changing is itself a meaningful signal to consumers).

Q57. A custom hook returns a large object of derived values, and every consumer re-renders whenever any single field changes — even fields they don't use. How would you fix that at the hook level?

ROI: ★★★★☆ Frequency: High

Short Answer

A single hook returning one big object forces every consumer to subscribe to the whole object's identity, so any field changing re-renders everyone — even a component that only reads one unrelated field. Fixes: split the hook into several smaller, focused hooks so consumers only subscribe to what they use; or, if the values come from a shared external store, use a selector-based subscription (as libraries like Zustand/Redux do) so a component only re-renders when the specific slice it selected actually changes.

Code Example

// PROBLEM: one hook, one object - EVERY consumer re-renders on ANY field's change
function useAppState() {
  const [user, setUser] = useState(null);
  const [theme, setTheme] = useState("light");
  const [notifications, setNotifications] = useState([]);
  return { user, setUser, theme, setTheme, notifications, setNotifications };
}
// A component reading only `theme` STILL re-renders when `notifications` changes.

// FIX 1: split into focused hooks - consumers subscribe only to what they need
function useUser() { /* own state, own re-render scope */ }
function useTheme() { /* own state, own re-render scope */ }
function useNotifications() { /* own state, own re-render scope */ }

// FIX 2: selector-based subscription over a SHARED external store (e.g. Zustand)
const useAppStore = create((set) => ({ user: null, theme: "light", notifications: [] }));
function ThemeToggle() {
  // only re-renders when `theme` SPECIFICALLY changes, not the whole store
  const theme = useAppStore((state) => state.theme);
  return <button>{theme}</button>;
}

Senior Engineer Perspective

This is the hook-level version of the classic "Context causes every consumer to re-render on any change" problem, and the fixes rhyme: split by concern, or add a selector layer. A senior answer connects the dots explicitly — "this is the same root cause as the Context over-re-rendering problem, just at the custom-hook layer instead of the Provider layer, and the same two remedies (splitting, or selector-based subscriptions) apply" — showing you recognize the pattern across different parts of React's API rather than treating each as an unrelated special case.

SECTION 10 - HOOKS VS HOCS VS RENDER PROPS: MIGRATION & ADVANCED PATTERNS

Q58. You've inherited a codebase with several HOCs (withAuth, withTheme, withLogging) wrapping components. Walk through migrating one to a custom hook safely.

ROI: ★★★★☆ Frequency: High

Short Answer

Extract the HOC's injected props into a hook that returns the same shape, call the hook directly inside the previously-wrapped component, and delete the wrapper — but do this one component at a time, verifying behavior (especially anything relying on the HOC's static methods, `displayName`, or ref-forwarding) rather than a blanket find-and-replace, since HOCs sometimes carry subtle extra behavior (hoisted static methods, prop interception) a naive hook conversion can silently drop.

Detailed Answer

Migration steps: (1) identify exactly what props the HOC injects and where they come from (context, an external store, a subscription); (2) write a hook that produces the same values; (3) in each wrapped component, replace the injected props with a direct call to the hook; (4) remove the export default withX(Component) wrapper, exporting the component directly; (5) check for anything relying on the HOC-specific machinery — hoist-non-react-statics usage (implies static methods were being carried through), ref forwarding through the wrapper, or props being renamed/filtered by the HOC (a consumer might depend on the HOC stripping certain internal props before they reach the DOM).

Code Example

// BEFORE: HOC injecting auth state as props
function withAuth(Component) {
  return function Wrapped(props) {
    const user = useContext(AuthContext); // HOC still uses a hook internally!
    return <Component {...props} user={user} />;
  };
}
const ProfilePage = withAuth(function ProfilePage({ user }) {
  return <h1>{user.name}</h1>;
});

// AFTER: direct hook call, wrapper deleted entirely
function useAuth() {
  return useContext(AuthContext);
}
function ProfilePage() {
  const user = useAuth();
  return <h1>{user.name}</h1>;
}

Senior Engineer Perspective

A detail that impresses interviewers: point out that the "before" HOC was already using a hook (`useContext`) internally — this is common in codebases that migrated partway, and it's good evidence that the HOC layer had become pure ceremony, adding a wrapper component and prop-passing indirection around logic that was hook-shaped all along. Also flag the DevTools tree win: removing HOC wrappers removes a layer of anonymous "Wrapped" components from the component tree, making it meaningfully easier to read during debugging.

Q59. Give a concrete example of prop collision in HOC composition, and explain why hooks structurally can't have the same problem.

ROI: ★★★★☆ Frequency: Medium

Short Answer

If two HOCs both inject a prop named data (say, withUser and withPosts both naming their injected prop data), composing them (withUser(withPosts(Component))) silently has the outer HOC's data clobber the inner one's — a naming collision resolved by composition order, invisibly. Hooks can't collide this way because each hook's return value is captured into a variable you name explicitly at the call site (const user = useUser(); const posts = usePosts();) — there's no shared "props bag" for two unrelated hooks to silently overwrite.

Code Example

// HOC composition: silent prop collision, order-dependent, easy to miss in review
const withUser = (C) => (props) => <C {...props} data={getUser()} />;
const withPosts = (C) => (props) => <C {...props} data={getPosts()} />;

const Enhanced = withUser(withPosts(Profile));
// Profile receives `data` = getUser() result - getPosts()'s `data` was silently overwritten.
// Swapping the composition order silently changes WHICH data wins. No error, no warning.

// Hooks: no shared namespace to collide in - each call site names its own binding
function Profile() {
  const user = useUser();   // explicitly named
  const posts = usePosts(); // explicitly named - can NEVER collide with `user`
  return /* ... */ null;
}

Senior Engineer Perspective

This is a genuinely underappreciated reason hooks won, beyond the commonly-cited "wrapper hell" — prop collisions in deep HOC composition chains are a real, hard-to-detect bug class (nothing errors, a value is just silently wrong), whereas hooks make every value's origin lexically explicit at the call site. Naming this specific failure mode (not just "wrapper hell" or "hard to read in DevTools") signals you've actually debugged HOC composition in a real codebase rather than just read about hooks replacing it.

Q60. Name a case where a render prop is still arguably the right API choice today, even in a hooks-first codebase.

ROI: ★★★☆☆ Frequency: Medium

Short Answer

When a library needs to hand the consumer a piece of JSX-shaped control over rendering — not just data — a render prop (or the modern equivalent, a component accepting a function-as-children) still fits naturally, because hooks can only return values, not dictate where or how markup is inserted into a specific slot in someone else's render tree. Virtualized-list libraries (react-window) and some drag-and-drop libraries still expose a render-prop-style API for exactly this reason: "here's the computed item, YOU render it however you want, in this exact position."

Code Example

// A hook alone can't say WHERE in the tree an item renders - it only returns values.
// A render prop naturally slots consumer-provided JSX into a specific position:
<FixedSizeList height={400} itemCount={1000} itemSize={35}>
  {({ index, style }) => (
    <div style={style}>Row {index}</div>   // consumer controls the markup, library controls positioning/virtualization
  )}
</FixedSizeList>

// Compare: a hook-only API could give you the computed geometry, but the consumer
// would still have to manually place it in JSX themselves - more boilerplate for
// this specific "library owns layout, consumer owns content" split.
const { virtualItems, totalHeight } = useVirtualizer({ count: 1000, itemSize: 35 });

Senior Engineer Perspective

Notice both real-world examples in this space (react-window's render-prop style, and modern virtualizer hooks like TanStack Virtual) actually coexist today — the ecosystem hasn't fully converged on one pattern for this exact use case, because "library controls layout/positioning, consumer controls content" is a genuinely different problem than "share stateful logic," which is what hooks are optimized for. A nuanced answer distinguishes these two problems rather than treating "hooks vs render props" as a single settled debate.

Q61. Why can't error boundaries be written as a hook, and what does that tell you about the limits of what hooks can replace?

ROI: ★★★★☆ Frequency: High

Short Answer

Catching a render error requires intercepting the React reconciler's error-handling during the render/commit phase itself — specifically the componentDidCatch / static getDerivedStateFromError class lifecycle methods, which run in a special error-recovery pathway with no hook equivalent. Hooks can only run as part of a component's own successful render; they have no mechanism to "catch" a *child* component throwing during *its* render, because that error unwinds past the parent's hooks before they'd get a chance to intervene.

Detailed Answer

This is a genuine, still-unfilled gap in the hooks API (as of the current React version) — not an oversight so much as a fundamentally different lifecycle: a hook is code that runs as part of rendering a specific component; an error boundary is code that runs instead of rendering a child that failed, at a different point in the tree. There's no "useErrorBoundary" hook in core React; you either write a small class component (often just once, reused everywhere, e.g. via the `react-error-boundary` package) or rely on a framework's built-in boundary (Next.js's `error.tsx`, React Router's `errorElement`).

Code Example

// Still requires a class - this is one of the few remaining legitimate uses for one.
class ErrorBoundary extends React.Component {
  state = { hasError: false };
  static getDerivedStateFromError() { return { hasError: true }; }
  componentDidCatch(error, info) { logToService(error, info); }
  render() {
    return this.state.hasError ? this.props.fallback : this.props.children;
  }
}

// Most teams wrap this ONCE (often via a library) and never hand-write it again:
import { ErrorBoundary } from "react-error-boundary";

<ErrorBoundary fallback={<ErrorScreen />} onError={logToService}>
  <Dashboard />
</ErrorBoundary>

Senior Engineer Perspective

This is one of the best interview questions to demonstrate you know hooks' actual boundaries, not just their happy path. The precise answer names both halves — why it's structurally impossible (error propagation happens outside the throwing component's own hook-execution context) and what the practical workaround is (one small class, usually from a well-maintained library, reused everywhere) — rather than either overclaiming "hooks can do everything now" or underclaiming "you need a lot of class components still."

Q62. A legacy HOC wraps a component purely to conditionally render it based on a feature flag (return null if disabled). What's the hook-era equivalent, and is a hook even the right tool?

ROI: ★★★☆☆ Frequency: Medium

Short Answer

A hook (useFeatureFlag(name)) can tell you whether the flag is on, but it cannot itself decide not to render — a hook only ever returns a value to the component that called it; it cannot intercept and short-circuit that component's render the way a wrapping HOC could. So the "hook equivalent" is: call the hook, then have the component itself do the conditional return — the decision moves from being wrapped-around-you to inside-your-own-render-function.

Code Example

// OLD: HOC decides FOR the component whether it renders at all
function withFeatureFlag(flagName) {
  return (Component) => (props) =>
    isEnabled(flagName) ? <Component {...props} /> : null;
}
const NewWidget = withFeatureFlag("new-widget")(Widget);

// NEW: hook only reports the value; the COMPONENT itself makes the render decision
function useFeatureFlag(name: string) {
  return useSyncExternalStore(subscribeToFlags, () => isEnabled(name));
}
function NewWidget(props) {
  const enabled = useFeatureFlag("new-widget");
  if (!enabled) return null;    // the component decides, a hook can't decide FOR it
  return <Widget {...props} />;
}

Senior Engineer Perspective

The precise point to make: this is a case where the HOC's "shape" (wrap and conditionally skip rendering) genuinely cannot be reproduced by a hook alone, because a hook has no way to prevent its own caller's render from happening — it can only return data the caller chooses to act on. The correct migration isn't "find the hook that replaces this HOC," it's recognizing the decision has to move into the component itself, which is a real (if small) behavioral difference worth calling out rather than glossing over.

Q63. How would you unit test that a migrated custom hook (previously a HOC) preserves the exact same behavior as the code it replaced?

ROI: ★★★☆☆ Frequency: Medium

Short Answer

Write (or keep) the same behavioral test suite against the component's rendered output and interactions — assert on what the user/consumer observes (rendered text, calls to injected callbacks, DOM structure) rather than on implementation details like "does this use a HOC or a hook." A test written against behavior shouldn't need to change at all when you swap the underlying implementation, which is itself a good acceptance criterion for "did I preserve behavior."

Code Example

// This test is IDENTICAL before and after the withAuth -> useAuth migration,

test("shows the logged-in user's name", () => {
  mockAuthContext({ user: { name: "Ada" } });

test("wraps ProfilePage with withAuth HOC", () => {

Senior Engineer Perspective

The deeper point: if your existing test suite for the HOC-based component needed significant rewriting to pass against the hook-based version, that's a signal the original tests were coupled to implementation details rather than behavior — a good outcome of a migration like this is often "our tests didn't need to change at all," and if they did, it's worth asking why they were written that way in the first place.

Q64. What happens to a HOC's displayName and how does that affect debugging — and does the hooks equivalent need anything similar?

A small but telling detail: forgetting displayName on a HOC is an extremely common real-world papercut that makes production error stack traces and DevTools trees full of "Wrapped" or "Anonymous" nodes — naming this unprompted, and contrasting it with hooks needing zero equivalent ceremony, is a good concrete example of the "less to get wrong" argument for hooks beyond the usual composability pitch.

Q65. Design a small internal library of hooks to replace a team's five most common HOCs. What ordering and naming conventions would you enforce?

One hook per concern (auth, theme, feature flags, analytics, permissions), each independently composable and independently testable, named consistently (`useAuth`, `useTheme`, `useFeatureFlag`, `useAnalytics`, `usePermission`), each documented with its exact return shape. function ProfilePage() {

SECTION 11 - TESTING CUSTOM HOOKS IN DEPTH

Q66. Why does React (and testing-library) warn about state updates "not wrapped in act()," and when is that warning actually pointing at a real bug versus just noise?

ROI: ★★★★★ Frequency: Extremely High

Short Answer

act() tells React "run this code, then flush all resulting state updates and effects before returning control to the test" — it exists so tests observe a component in a fully-settled state rather than mid-update. The warning fires when a state update happens outside that flush boundary — usually because an async operation (a timer, a promise, a fetch) resolved after the test's act() block already returned. It's real noise only when the update genuinely doesn't matter to the assertion; it's a real bug signal when it means your test isn't actually waiting for the async work it's supposedly testing.

Detailed Answer

renderHook and render from React Testing Library already wrap synchronous work in act() for you. The warning shows up specifically when something asynchronous — a setTimeout, an unresolved promise, a pending fetch — resolves and calls setState after the current act() scope has already closed. The fix is essentially never to manually silence it; it's to await the async work properly, usually with waitFor (which internally wraps polling assertions in act) rather than wrapping raw act(async () => {...}) around a bare timeout.

Code Example

// WRONG: causes the act() warning - test moves on before the async state settles
test("bad: fetch resolves after test already asserted", () => {
  const { result } = renderHook(() => useFetch("/data"));
  expect(result.current.status).toBe("success"); // still "loading" - assertion is WRONG too
});

// RIGHT: wait for the actual async transition, no act() warning, correct assertion
test("good: waits for the real async settle point", async () => {
  const { result } = renderHook(() => useFetch("/data"));
  await waitFor(() => expect(result.current.status).toBe("success"));
});

Senior Engineer Perspective

The strongest answer explicitly rejects "just wrap it in act() and move on" as the default fix — that pattern papers over a real test that isn't actually waiting for what it claims to test. act() warnings should be treated as "your test has a race condition with the code under test," and waitFor/findBy* queries (which poll and internally handle the act-wrapping correctly) are almost always the right tool over manual act(async () => ...) blocks.

Q67. How do you test a custom hook that depends on React Context (e.g. useAuth reading an AuthContext)?

ROI: ★★★★☆ Frequency: High

Short Answer

Pass a wrapper option to renderHook — a component that renders the relevant Provider(s) around children. This lets the hook read real context values during the test exactly as it would in the app, without needing to mock useContext itself, and lets you test different context values by rendering different wrapper configurations.

Code Example

import { renderHook } from "@testing-library/react";
import { AuthContext } from "./AuthContext";
import { useAuth } from "./useAuth";

function makeWrapper(user: User | null) {
  return function Wrapper({ children }: { children: React.ReactNode }) {
    return <AuthContext.Provider value={{ user }}>{children}</AuthContext.Provider>;
  };
}

test("returns the current user from context", () => {
  const { result } = renderHook(() => useAuth(), {
    wrapper: makeWrapper({ id: 1, name: "Ada" }),
  });
  expect(result.current.user?.name).toBe("Ada");
});

test("returns null when logged out", () => {
  const { result } = renderHook(() => useAuth(), { wrapper: makeWrapper(null) });
  expect(result.current.user).toBeNull();
});

Senior Engineer Perspective

A useful extension: if several tests across a suite need the same provider stack (auth + theme + query client, say), factor the wrapper into a shared renderHookWithProviders test utility rather than repeating the composition in every test file — this is the test-infrastructure equivalent of the "internal hooks library" discipline from the HOC-migration section, applied to test setup instead of production code.

Q68. How do you test a hook that uses setInterval/setTimeout without your test suite actually waiting in real time?

ROI: ★★★★☆ Frequency: High

Short Answer

Use fake timers (jest.useFakeTimers()) so the test controls the passage of time explicitly via jest.advanceTimersByTime(ms) instead of the test process actually blocking for real milliseconds. Wrap the timer advancement in act() (or use testing-library's async utilities) since advancing a fake timer that triggers a state update needs the same flush guarantee as any other state change.

Code Example

import { renderHook, act } from "@testing-library/react";
import { useCountdown } from "./useCountdown";

beforeEach(() => jest.useFakeTimers());
afterEach(() => jest.useRealTimers());

test("counts down from the given seconds", () => {
  const { result } = renderHook(() => useCountdown(10));
  expect(result.current).toBe(10);

  act(() => { jest.advanceTimersByTime(3000); }); // simulate 3 real seconds instantly
  expect(result.current).toBe(7);

  act(() => { jest.advanceTimersByTime(10000); }); // way past zero
  expect(result.current).toBe(0); // clamped, doesn't go negative
});

Senior Engineer Perspective

A common gotcha worth naming: jest.advanceTimersByTime only fires timers scheduled up to that point — if your hook's tick handler itself schedules a new timer inside its callback (as a recursive setTimeout loop does), you may need jest.advanceTimersByTime called repeatedly, or `jest.runOnlyPendingTimers()`/`runAllTimers()`, depending on whether the timer chain is finite or would loop forever with `runAllTimers` (which would hang the test on an interval that never stops itself).

Q69. How do you test that a hook correctly cleans up its subscription/listener/timer on unmount?

ROI: ★★★★☆ Frequency: High

Short Answer

Spy on the relevant teardown API (removeEventListener, clearInterval, an unsubscribe function) and call unmount() (returned by renderHook), then assert the spy was called with the same arguments/id the setup call used. This directly verifies the effect's cleanup function runs and does the right thing, rather than just trusting that it exists in the source.

Code Example

test("removes the event listener on unmount", () => {
  const addSpy = jest.spyOn(window, "addEventListener");
  const removeSpy = jest.spyOn(window, "removeEventListener");

  const { unmount } = renderHook(() => useEventListener("resize", jest.fn()));

  expect(addSpy).toHaveBeenCalledWith("resize", expect.any(Function));
  const registeredHandler = addSpy.mock.calls[0][1];

  unmount();

  // Assert cleanup removed the SAME handler reference that was added -
  // a common bug is removing a NEW function reference that doesn't match.
  expect(removeSpy).toHaveBeenCalledWith("resize", registeredHandler);
});

test("clears the interval on unmount", () => {
  jest.useFakeTimers();
  const clearSpy = jest.spyOn(global, "clearInterval");
  const { unmount } = renderHook(() => useInterval(jest.fn(), 1000));
  unmount();
  expect(clearSpy).toHaveBeenCalled();
});

Senior Engineer Perspective

The subtlety worth demonstrating: asserting removeEventListener was called with the exact same function reference that addEventListener received is a real, common bug catch — if the effect's cleanup accidentally creates a new inline function instead of removing the one it added, removeEventListener silently does nothing (the browser API requires reference equality), and this test is one of the few ways to catch that without manually re-reading the source closely.

Q70. How would you mock a dependency injected via module import (not a parameter) inside a custom hook, e.g. a hook that calls a shared apiClient singleton?

ROI: ★★★★☆ Frequency: High

Short Answer

Use the test runner's module-mocking facility (jest.mock("./apiClient")) to replace the entire module with a mock before the hook under test imports it, then configure each test's mock return value/rejection as needed. This works because the mock is applied at the module-resolution level, before the hook's own import statement runs — it doesn't require the hook to accept the client as a parameter, though accepting it as a parameter (dependency injection) is often the more testable design going forward.

Code Example

// useUser.ts
import { apiClient } from "./apiClient";
export function useUser(id: string) {
  const [user, setUser] = useState(null);
  useEffect(() => { apiClient.get(`/users/${id}`).then(setUser); }, [id]);

// useUser.test.ts
jest.mock("./apiClient", () => ({
  apiClient: { get: jest.fn() },

import { apiClient } from "./apiClient";
import { useUser } from "./useUser";

test("returns the fetched user", async () => {
  (apiClient.get as jest.Mock).mockResolvedValueOnce({ id: 1, name: "Ada" });
  const { result } = renderHook(() => useUser("1"));

Senior Engineer Perspective

A design point worth raising unprompted: module mocking works, but a hook that accepts its dependencies as parameters (or reads them from a context you can override in tests, as in Q67) is generally easier to test and reason about than one that reaches out to a module-level singleton — module mocking is a necessary tool for legacy code, but for new hooks, preferring injectable dependencies over hidden module imports is the better default.

Q71. How do you test a hook's behavior across multiple re-renders with changing arguments — e.g. that useDebounce actually resets its timer when the value changes mid-wait?

ROI: ★★★★☆ Frequency: Medium

Short Answer

Use rerender (returned by renderHook) to simulate the parent passing new props/args, interleaved with fake-timer advancement, to reproduce the exact "value changed before the delay elapsed" scenario. This is the only way to actually prove the debounce-resets-on-change behavior — testing with a single static render can't exercise the reset logic at all.

Code Example

test("debounce resets the timer if value changes before delay elapses", () => {
  jest.useFakeTimers();

  const { result, rerender } = renderHook(
    ({ value }) => useDebounce(value, 500),
    { initialProps: { value: "a" } }
  );

  act(() => { jest.advanceTimersByTime(300); }); // 300ms in, not yet debounced
  rerender({ value: "ab" });                       // value changes - should RESET the timer
  act(() => { jest.advanceTimersByTime(300); }); // another 300ms (total 600ms since "a")

  // If the timer correctly reset on rerender, only 300ms has elapsed since "ab" -
  // NOT yet debounced, even though 600ms has elapsed since the FIRST value.
  expect(result.current).toBe("a");

  act(() => { jest.advanceTimersByTime(200); }); // now 500ms since "ab"
  expect(result.current).toBe("ab");
});

Senior Engineer Perspective

This test is a great artifact to bring up in an interview because it directly encodes the exact behavior (cleanup-cancels-the-pending-timer) that's easy to get wrong in the implementation — writing this test *before* implementing useDebounce is a natural fit for TDD, since the test literally describes the "reset on change" requirement that a naive implementation (missing the cleanup's clearTimeout) would fail.

Q72. What's the difference between testing a custom hook in isolation with renderHook versus testing it indirectly through the component that uses it? When would you choose each?

ROI: ★★★★☆ Frequency: High

Short Answer

renderHook tests the hook's contract directly — fast, focused, and doesn't require rendering unrelated markup. Testing through the component instead exercises the hook the way a real user actually experiences it (via clicks, visible text, accessibility queries), which is more resilient to internal refactors but slower to pin down a specific edge case. The common guidance: prefer testing through the component for hooks that are tightly coupled to one component's UI; use renderHook directly for hooks that are genuinely reusable, general-purpose utilities (the ones a hook library would ship) where the "unit under test" really is the hook's API, not any specific UI.

Code Example

// Direct: fast, hook-focused - good for a general-purpose, reusable hook
test("useToggle flips the boolean", () => {
  const { result } = renderHook(() => useToggle(false));
  act(() => result.current[1]());
  expect(result.current[0]).toBe(true);
});

// Indirect: through the component - good when the hook only exists to serve ONE component
test("clicking the menu button opens the dropdown", async () => {
  render(<NavMenu />); // internally uses useDropdown - not tested in isolation at all
  await userEvent.click(screen.getByRole("button", { name: /menu/i }));
  expect(screen.getByRole("menu")).toBeVisible();

Senior Engineer Perspective

Kent C. Dodds' "Testing Trophy" philosophy is directly relevant here: favor tests that resemble how software is actually used (integration-style, through the component) over unit tests of internals, reserving direct hook unit tests for the cases where the hook truly is a standalone, publishable unit of behavior. Citing this framing shows you're choosing a testing strategy deliberately rather than defaulting to "test everything with renderHook because it's there."

Q73. A flaky test intermittently fails on a hook that fetches on mount. What are the top three causes to check, in order?

ROI: ★★★★☆ Frequency: High

Short Answer

(1) A missing await/`waitFor` — the assertion runs before the async state settles, and it "passes" only when the machine happens to be fast enough that microtask timing lines up, which is inherently non-deterministic. (2) Test isolation leakage — a mock (fetch, timers, a module) not reset between tests, so test order affects outcome. (3) Real timers mixed with fake ones, or a `setTimeout`/interval left running from a previous test's un-cleaned-up hook, bleeding into the next test.

Detailed Answer

Debug in that order because it's roughly cause-frequency order in practice. For (1), grep the test for a bare expect right after `render`/`renderHook` with no `waitFor`/`await` around anything async. For (2), check `beforeEach`/`afterEach` — are mocks reset (`jest.resetAllMocks()`/`clearAllMocks()`) and is `jest.useRealTimers()` called after any test that flips to fake timers? For (3), check that every hook under test properly cleans up on unmount (Q69) — a leftover interval from a previous test's un-unmounted renderHook result can fire callbacks into the next test's assertions.

Code Example

// A common root cause of (1): assertion races the microtask queue
test("flaky: no wait for the async update", () => {
  renderHook(() => useFetch("/data"));
  expect(screen.queryByText("loaded")).toBeInTheDocument(); // races the fetch's .then()
});

// Fix addresses (1) directly, and good hygiene addresses (2) and (3):
afterEach(() => {
  jest.clearAllMocks();     // (2) isolation between tests
  jest.useRealTimers();     // (3) don't leak fake-timer mode into the next test
});

test("fixed: waits for the real settle point", async () => {
  renderHook(() => useFetch("/data"));
  await waitFor(() => expect(screen.getByText("loaded")).toBeInTheDocument());
});

Senior Engineer Perspective

Flaky-test triage is a skill interviewers specifically probe for at senior levels because it signals production debugging maturity, not just "can you write a test." The strongest answers lead with "flaky almost never means 'random' — it means there's a real race condition, and the fix is finding what two things are racing," rather than reaching for retries or increased timeouts as the first move.

SECTION 12 - STATE-MACHINE-STYLE CUSTOM HOOKS

Q74. Build useToggle and then generalize it into a small useStateMachine hook that takes an explicit transition table. Why is the transition table version safer?

ROI: ★★★★★ Frequency: High

Short Answer

useToggle is a two-state machine with implicit transitions (any state can go to the other). A general useStateMachine hook takes an explicit table of { state: { event: nextState } } and only allows a transition if the table defines it for the current state — meaning invalid transitions (dispatching "SUBMIT" while already "submitting") are silently ignored or explicitly rejected, rather than a plain reducer's switch statement which will happily process an action that doesn't semantically make sense for the current state.

Detailed Answer

A plain useReducer reducer can transition to any state from any action, if you (the author) forget to guard against it — nothing structurally prevents a `"success"` state from processing another `"FETCH"` action and going back to `"loading"` incorrectly if the switch statement doesn't explicitly account for the current state. A transition-table-driven machine makes the *valid graph of states* the single source of truth: the table itself documents every legal transition, and anything not in the table for the current state is a no-op (or throws, if you want stricter enforcement) — turning "did I handle every case correctly" from a code-review question into a table you can eyeball.

Code Example

// Simple: useToggle - two states, transitions are implicit ("the other one")
function useToggle(initial = false) {
  const [on, setOn] = useState(initial);
  const toggle = useCallback(() => setOn((v) => !v), []);
  return [on, toggle] as const;
}

// General: explicit transition table - invalid transitions are structurally rejected
type Transitions<S extends string, E extends string> = Partial<Record<S, Partial<Record<E, S>>>>;

function useStateMachine<S extends string, E extends string>(
  initial: S,
  transitions: Transitions<S, E>
) {
  const [state, setState] = useState<S>(initial);

  const send = useCallback((event: E) => {
    setState((current) => transitions[current]?.[event] ?? current); // no entry -> no-op
  }, [transitions]);

  return [state, send] as const;
}

// Usage: a fetch machine where "SUCCESS" is only valid from "loading"
const [status, send] = useStateMachine("idle", {
  idle:    { FETCH: "loading" },
  loading: { SUCCESS: "success", FAILURE: "error" },
  success: { FETCH: "loading" },
  error:   { FETCH: "loading" },
});
// send("SUCCESS") while status is "idle" is a documented no-op, not a silent bad transition.

Senior Engineer Perspective

The framing that lands well: a transition table isn't just "a fancier reducer," it inverts where the correctness guarantee lives — from "the developer remembered to guard every branch in the switch statement" to "the data structure itself enumerates every legal edge, and anything not listed is definitionally illegal." This is the same idea underlying formal state machines (XState) implemented at a much smaller scale, and naming that connection explicitly shows you understand the *principle*, not just this one hook's code.

Q75. When does a hand-rolled useStateMachine hook stop being enough, and you should reach for a library like XState instead?

ROI: ★★★★☆ Frequency: High

Short Answer

A hand-rolled hook is fine for a handful of states with simple, flat transitions. Reach for XState (or a similar state-chart library) once you need: hierarchical/nested states (a sub-machine inside a state), parallel regions (two independent state machines that must stay in sync), guarded transitions with complex conditions, entry/exit actions, delayed transitions, or — critically — visual tooling and formal verification that your state chart has no unreachable states or missing transitions, which becomes hard to eyeball once a machine grows past a handful of states.

Detailed Answer

The hand-rolled version's simplicity is also its ceiling: it has no concept of hierarchy (a "loading" state that itself has sub-states like "loading.retrying"), no built-in way to express "run this side effect when entering a state" without manually wiring it into an effect elsewhere, and no visualizer. XState's statecharts formalism (based on David Harel's original statecharts work, predating React) directly addresses all of these, at the cost of a steeper learning curve and a dependency. The right team-level heuristic: start with the hand-rolled version; migrate to XState when the transition table itself becomes hard to reason about, not preemptively.

Code Example

// Where hand-rolled starts to strain: nested/hierarchical states
// "editing" has ITS OWN sub-states (dirty/clean) that a flat table can't express cleanly.
const [status, send] = useStateMachine("idle", {
  idle:    { EDIT: "editing" },
  editing: { SAVE: "saving" /* ...but what about "editing.dirty" vs "editing.clean"? */ },
  saving:  { SUCCESS: "idle", FAILURE: "editing" },
});

// XState expresses hierarchy, guards, and entry actions declaratively:
import { createMachine } from "xstate";
const formMachine = createMachine({
  initial: "idle",
  states: {
    idle:    { on: { EDIT: "editing" } },
    editing: {
      initial: "clean",
      states: { clean: { on: { CHANGE: "dirty" } }, dirty: {} },
      on: { SAVE: [{ target: "saving", guard: "isDirty" }] }, // guarded transition
    },
    saving: { on: { SUCCESS: "idle", FAILURE: "editing" } },
  },
});

Senior Engineer Perspective

A senior answer resists the urge to say "just always use XState" or "never use a library, hand-roll it" — the honest tradeoff is team familiarity and bundle size versus expressiveness and tooling. Mentioning that XState predates React (it's a general implementation of statecharts, usable with any framework) signals you understand it as a modeling discipline first, a React library second — which is exactly the kind of context that impresses an interviewer who's used it in production.

Q76. Build a useMultiStepForm hook using the state-machine pattern — steps, forward/back navigation, and per-step validation gating progress.

ROI: ★★★★★ Frequency: High

Short Answer

Model the current step as an index (or a named state), keep per-step form data in one object, and gate the "next" transition on that step's validation passing — the same "no entry in the table = no-op" discipline as a general state machine, applied specifically to "you cannot advance to step N+1 while step N is invalid."

Code Example

function useMultiStepForm<T extends Record<string, unknown>>(
  steps: { key: keyof T; validate: (data: T) => boolean }[]
) {
  const [stepIndex, setStepIndex] = useState(0);
  const [data, setData] = useState<T>({} as T);

  const currentStep = steps[stepIndex];
  const isLastStep = stepIndex === steps.length - 1;

  const updateField = useCallback(<K extends keyof T>(key: K, value: T[K]) => {
    setData((prev) => ({ ...prev, [key]: value }));
  }, []);

  const goNext = useCallback(() => {
    setData((currentData) => {
      // Read current validity synchronously against the LATEST data via updater form.
      if (currentStep.validate(currentData)) {
        setStepIndex((i) => Math.min(i + 1, steps.length - 1));
      }
      return currentData; // this updater is only used to READ, not to change data
    });
  }, [currentStep, steps.length]);

  const goBack = useCallback(() => {
    setStepIndex((i) => Math.max(i - 1, 0));
  }, []);

  return { stepIndex, currentStep, data, updateField, goNext, goBack, isLastStep };
}

Senior Engineer Perspective

Interviewers building on this often ask "what happens if a user hits the browser back button mid-flow?" — a strong answer notes that step state living only in React state is lost on refresh/back-navigation, and a production version would likely sync the step index (and maybe the form data) into the URL or `sessionStorage` so navigation and refresh don't silently reset progress. Volunteering that gap shows you're thinking about the feature holistically, not just the hook's internal mechanics.

Q77. How would you model a media player's state (idle/playing/paused/buffering/ended/error) as a hook, and what's the danger of NOT using a state machine here?

ROI: ★★★★☆ Frequency: Medium

Short Answer

Media player state is a textbook state-machine case because so many transitions are contextually invalid: you can't go from "ended" to "buffering" without first seeking or replaying, "error" should generally only be escapable via an explicit retry, and "paused" and "playing" are mutually exclusive with "buffering" often interrupting either. Modeling this with independent booleans (isPlaying, isBuffering, isPaused, hasError) invites impossible combinations (`isPlaying && isPaused` both true) that a tagged-union state machine makes structurally impossible.

Code Example

type PlayerState =
  | { status: "idle" }
  | { status: "playing" }
  | { status: "paused" }
  | { status: "buffering"; resumeTo: "playing" | "paused" } // remembers what to return to
  | { status: "ended" }
  | { status: "error"; message: string };

type PlayerEvent =
  | { type: "PLAY" } | { type: "PAUSE" } | { type: "BUFFER" }
  | { type: "BUFFER_DONE" } | { type: "END" } | { type: "ERROR"; message: string }
  | { type: "RETRY" };

function playerReducer(state: PlayerState, event: PlayerEvent): PlayerState {
  switch (event.type) {
    case "BUFFER":
      // Only playing/paused can transition to buffering, and it remembers WHICH.
      if (state.status === "playing" || state.status === "paused") {
        return { status: "buffering", resumeTo: state.status };
      }
      return state; // buffering from idle/ended/error is not a valid transition
    case "BUFFER_DONE":
      return state.status === "buffering" ? { status: state.resumeTo } : state;
    case "ERROR":
      return { status: "error", message: event.message };
    case "RETRY":
      return state.status === "error" ? { status: "idle" } : state;
    default:
      return state;
  }
}

function useMediaPlayer() {
  const [state, dispatch] = useReducer(playerReducer, { status: "idle" });
  return { state, dispatch };
}

Senior Engineer Perspective

The "resumeTo" field is the detail that shows real state-machine thinking: buffering needs to remember whether to return to "playing" or "paused" once it resolves, which a flat boolean model handles clumsily (usually with an extra ad-hoc variable that isn't part of the state model at all, and drifts out of sync with it). Calling out that specific design decision — carrying necessary context *inside* the state itself, rather than in a parallel untyped variable — is a strong senior signal.

Q78. How do you unit test every transition in a state-machine hook systematically, rather than just testing the happy path?

ROI: ★★★★☆ Frequency: Medium

Short Answer

Because the transition table is an explicit, enumerable data structure, you can generate tests directly from it: for every (state, event) pair, assert the resulting state matches the table, and — just as importantly — assert that events *not* listed for a given state leave it unchanged. This turns "did I test every case" into a mechanical, complete sweep rather than a list of test cases someone had to remember to write by hand.

Code Example

const transitions = {
  idle:    { FETCH: "loading" },
  loading: { SUCCESS: "success", FAILURE: "error" },
  success: { FETCH: "loading" },
  error:   { FETCH: "loading" },
};

test.each(
  Object.entries(transitions).flatMap(([state, events]) =>
    Object.entries(events).map(([event, nextState]) => [state, event, nextState])
  )
)("from %s, sending %s goes to %s", (state, event, nextState) => {
  const { result } = renderHook(() => useStateMachine(state as any, transitions));
  act(() => result.current[1](event as any));
  expect(result.current[0]).toBe(nextState);
});

test("an event not defined for the current state is a no-op", () => {
  const { result } = renderHook(() => useStateMachine("success", transitions));
  act(() => result.current[1]("SUCCESS" as any)); // not valid FROM "success"
  expect(result.current[0]).toBe("success"); // unchanged
});

Senior Engineer Perspective

Generating tests from the transition table itself (rather than hand-writing one test per scenario you happen to think of) is exactly the kind of "test the shape of the data, not just the cases I remembered" thinking senior engineers bring to state-heavy code — and it means adding a new transition to the table automatically gets test coverage the next time the suite runs, with zero extra test-writing effort.

Q79. Should a state machine hook expose its raw dispatch function, or wrapped named actions? What's the tradeoff?

ROI: ★★★★☆ Frequency: Medium

Short Answer

Exposing raw dispatch (or `send`) is flexible but leaks the internal event-shape contract to every consumer, coupling them to exact action names/payloads. Wrapping each valid transition in a named function (play(), pause(), retry()) gives a cleaner, more self-documenting call site and lets you change the internal event names later without touching every consumer — the same "curated API surface over raw imperative access" principle as `useImperativeHandle` exposing `focus()` instead of the raw DOM node.

Code Example

// Raw dispatch: flexible, but every consumer needs to know exact event shapes
const { state, dispatch } = useMediaPlayer();
dispatch({ type: "PLAY" }); // consumer must know the literal string and shape

// Wrapped: a curated, named API - the internal event shape is an implementation detail
function useMediaPlayer() {
  const [state, dispatch] = useReducer(playerReducer, { status: "idle" });
  return {
    state,
    play: useCallback(() => dispatch({ type: "PLAY" }), []),
    pause: useCallback(() => dispatch({ type: "PAUSE" }), []),
    retry: useCallback(() => dispatch({ type: "RETRY" }), []),
  };
}
const { state, play, pause } = useMediaPlayer();
play(); // reads like the domain, not like an internal implementation detail

Senior Engineer Perspective

The general principle to articulate: expose raw dispatch for a hook that's genuinely internal/private to one component (low cost, no external consumers to break), and wrap it in named actions the moment the hook becomes a shared/public API other teams or components depend on — because renaming an event type is a non-breaking internal refactor if it's hidden behind `play()`, but a breaking change for every consumer if they all call `dispatch({ type: "PLAY" })` directly.

Q80. How would you visualize or debug a running state machine hook in development — what would you build or reach for?

Q81. Can a state machine hook's reducer perform a side effect (like calling an API) directly inside a transition? Why or why not, and what's the correct pattern instead?

ROI: ★★★★★ Frequency: Extremely High

Short Answer

No — reducers (whether hand-written or driving a state machine hook) must stay pure: same inputs always produce the same output, no side effects, no mutation. React may invoke a reducer more than once per dispatched action under Strict Mode/concurrent rendering specifically to help you catch impurity, so an API call inside a reducer could fire multiple times for one user action. The correct pattern: the reducer only computes the *next state*; an effect (or an "action" in newer React/XState terminology) watches for the state that *implies* a side effect is needed and performs it there.

Detailed Answer

This mirrors why useMemo's factory and a state updater function must be pure — React's contract with these functions is that it's free to call, skip, or re-call them as an implementation detail of scheduling, and a side effect (network call, `console.log` with real consequences, mutating an external variable) breaks that contract observably. The idiomatic split: dispatch { type: "FETCH" }, the reducer transitions to `{ status: "loading" }` (pure), and a separate `useEffect` watching `state.status === "loading"` performs the actual fetch and dispatches `SUCCESS`/`FAILURE` when it resolves.

Code Example

// WRONG: side effect INSIDE the reducer - impure, may run more than once, untestable in isolation
function badReducer(state, action) {
  if (action.type === "FETCH") {
    fetch("/data").then((r) => r.json()); // side effect inside a "pure" function - broken contract
    return { status: "loading" };
  }
  return state;
}

// RIGHT: reducer stays pure; an effect watches the resulting state and performs the side effect
function reducer(state, action) {
  switch (action.type) {
    case "FETCH":   return { status: "loading" };
    case "SUCCESS": return { status: "success", data: action.data };
    case "FAILURE": return { status: "error", error: action.error };
    default:        return state;
  }
}

function useDataMachine(url: string) {
  const [state, dispatch] = useReducer(reducer, { status: "idle" });

  useEffect(() => {
    if (state.status !== "loading") return;
    let ignore = false;
    fetch(url).then((r) => r.json())
      .then((data) => { if (!ignore) dispatch({ type: "SUCCESS", data }); })
      .catch((error) => { if (!ignore) dispatch({ type: "FAILURE", error }); });
    return () => { ignore = true; };
  }, [state.status, url]);

  return [state, dispatch] as const;
}

Senior Engineer Perspective

This is one of the most reliable "do you actually understand the reducer contract, or just the syntax" questions. Strong candidates connect it to a concrete consequence — Strict Mode double-invoking reducers/state-updaters in development specifically to surface impurity bugs like this — rather than citing purity as an abstract rule. It's also directly relevant to XState, which formalizes this exact split via "actions" (fire-and-forget side effects triggered by a transition) that are conceptually separate from the pure transition function itself.

Q82. Implement useLocalStorage's cousin, useSessionStorage, and explain the one meaningful behavioral difference that changes the hook's design.

ROI: ★★★★☆ Frequency: High

Short Answer

The implementation is nearly identical to useLocalStorage (lazy init, SSR guard, try/catch around JSON parsing, functional updates) — swap window.localStorage for window.sessionStorage. The meaningful difference: sessionStorage is scoped per-tab, not shared across tabs, so the cross-tab storage event sync that matters for useLocalStorage is meaningless here — two tabs never share the same session storage, so there's nothing to keep in sync, and including that listener would be dead code.

Code Example

function useSessionStorage<T>(key: string, initialValue: T) {
  const [value, setValue] = useState<T>(() => {
    if (typeof window === "undefined") return initialValue;
    try {
      const item = sessionStorage.getItem(key);
      return item ? JSON.parse(item) : initialValue;
    } catch {
      return initialValue;
    }
  });

  const setStoredValue = useCallback((next: T | ((prev: T) => T)) => {
    setValue((prev) => {
      const resolved = next instanceof Function ? next(prev) : next;
      try { sessionStorage.setItem(key, JSON.stringify(resolved)); } catch { /* quota/private mode */ }
      return resolved;
    });
  }, [key]);

  // NOTE: deliberately NO cross-tab "storage" event listener here -
  // sessionStorage is per-tab by definition, there's nothing to sync.

  return [value, setStoredValue] as const;
}

Senior Engineer Perspective

A candidate who copy-pastes useLocalStorage, swaps the API name, and leaves the storage-event cross-tab listener in place hasn't actually understood why that listener existed in the first place — it's dead code for session storage, since the browser never fires cross-tab `storage` events for a per-tab store. Removing it deliberately (and explaining why) is a stronger answer than mechanically reusing the pattern.

Q83. Implement useOnClickOutside's real-world sibling, useHover, and useFocusWithin. What subtlety in event bubbling makes useFocusWithin harder than it looks?

ROI: ★★★★☆ Frequency: Medium

Short Answer

useHover is straightforward: mouseenter/mouseleave on a ref'd element. useFocusWithin ("is focus anywhere inside this subtree") is trickier because plain focus/blur don't bubble, so listening for them directly on a container never fires for descendants — you need either the bubbling variants focusin/focusout, or a `relatedTarget` check on `blur`'s capture phase, to correctly detect focus moving between two children of the same container without a false "focus left" blip.

Code Example

function useHover<T extends HTMLElement>(): [RefObject<T>, boolean] {
  const ref = useRef<T>(null);
  const [hovered, setHovered] = useState(false);

  useEffect(() => {
    const el = ref.current;
    if (!el) return;
    const onEnter = () => setHovered(true);
    const onLeave = () => setHovered(false);
    el.addEventListener("mouseenter", onEnter);
    el.addEventListener("mouseleave", onLeave);
    return () => {
      el.removeEventListener("mouseenter", onEnter);
      el.removeEventListener("mouseleave", onLeave);
    };
  }, []);

  return [ref, hovered];
}

function useFocusWithin<T extends HTMLElement>(): [RefObject<T>, boolean] {
  const ref = useRef<T>(null);
  const [focused, setFocused] = useState(false);

  useEffect(() => {
    const el = ref.current;
    if (!el) return;
    // focusin/focusout BUBBLE (unlike plain focus/blur) - required to detect
    // focus moving between two DIFFERENT descendants without a false blip.
    const onFocusIn = () => setFocused(true);
    const onFocusOut = (e: FocusEvent) => {
      // relatedTarget = where focus is GOING; if still inside el, it's not truly "out"
      if (!el.contains(e.relatedTarget as Node)) setFocused(false);
    };
    el.addEventListener("focusin", onFocusIn);
    el.addEventListener("focusout", onFocusOut);
    return () => {
      el.removeEventListener("focusin", onFocusIn);
      el.removeEventListener("focusout", onFocusOut);
    };
  }, []);

  return [ref, focused];
}

Senior Engineer Perspective

This is a genuinely obscure-but-real gotcha (`focus`/`blur` don't bubble, `focusin`/`focusout` do) that trips up even experienced engineers the first time they build a "does this container have focus anywhere inside it" widget — a naive attempt using `blur` on the container fires every time focus moves between two of its own children, causing a visible flicker in something like a combobox. Knowing the `relatedTarget` check is the fix (not just "use focusin/focusout") shows you've actually debugged this specific flicker before.

Q84. Implement useCopyToClipboard, including the fallback path for browsers/contexts where the async Clipboard API isn't available.

ROI: ★★★☆☆ Frequency: Medium

Short Answer

Prefer navigator.clipboard.writeText() (async, permission-gated, requires a secure context/HTTPS), and fall back to the legacy document.execCommand("copy") trick (creating a hidden, selected, off-screen textarea) for older browsers or insecure contexts where the modern API is unavailable. Track a transient "copied" boolean (auto-resetting after a couple seconds) so the UI can show brief "Copied!" feedback.

Code Example

function useCopyToClipboard(): [boolean, (text: string) => Promise<void>] {
  const [copied, setCopied] = useState(false);

  const copy = useCallback(async (text: string) => {
    try {
      if (navigator.clipboard?.writeText) {
        await navigator.clipboard.writeText(text); // modern path
      } else {
        // Legacy fallback: hidden, off-screen textarea + execCommand
        const textarea = document.createElement("textarea");
        textarea.value = text;
        textarea.style.position = "fixed";
        textarea.style.opacity = "0";
        document.body.appendChild(textarea);
        textarea.select();
        document.execCommand("copy");
        document.body.removeChild(textarea);
      }
      setCopied(true);
      setTimeout(() => setCopied(false), 2000); // auto-reset the "copied" flash
    } catch {
      setCopied(false);
    }
  }, []);

  return [copied, copy];
}

Senior Engineer Perspective

Two production gotchas worth naming: the modern Clipboard API requires a secure context (HTTPS or localhost) and, in some browsers, a recent user gesture — calling it from inside an unrelated `setTimeout` rather than directly inside a click handler can silently fail permission checks. Also mention the auto-reset timer itself needs cleanup if the component can unmount while it's pending (the same cleanup discipline from the timing-hooks section applies here too).

Q85. Implement useIntersectionObserver as a reusable hook (the primitive behind lazy-loading images and infinite scroll triggers). What are the performance traps in a naive version?

ROI: ★★★★★ Frequency: Extremely High

Short Answer

Wrap the native IntersectionObserver API: observe a ref'd element, store its intersection state, and disconnect on cleanup. The naive-version performance trap: creating a brand-new IntersectionObserver instance (with its own threshold/root config) for every single observed element, rather than sharing one observer across many elements when the options are identical — each observer instance carries real overhead, and a long list with hundreds of lazy-loaded images creating hundreds of separate observers is measurably worse than one shared observer watching all of them.

Code Example

function useIntersectionObserver<T extends HTMLElement>(
  options: IntersectionObserverInit = {}
): [RefObject<T>, boolean] {
  const ref = useRef<T>(null);
  const [isIntersecting, setIsIntersecting] = useState(false);

  // Stabilize options so the effect doesn't re-create the observer every render
  // just because an inline {} object was passed.
  const { root, rootMargin, threshold } = options;
  const stableOptions = useMemo(
    () => ({ root, rootMargin, threshold }),
    [root, rootMargin, threshold]
  );

  useEffect(() => {
    const el = ref.current;
    if (!el) return;

    const observer = new IntersectionObserver(([entry]) => {
      setIsIntersecting(entry.isIntersecting);
    }, stableOptions);

    observer.observe(el);
    return () => observer.disconnect(); // ALWAYS disconnect - a lingering observer leaks
  }, [stableOptions]);

  return [ref, isIntersecting];
}

// Usage: lazy-load an image only once it's near the viewport
function LazyImage({ src }: { src: string }) {
  const [ref, isVisible] = useIntersectionObserver<HTMLDivElement>({ rootMargin: "200px" });
  return <div ref={ref}>{isVisible && <img src={src} />}</div>;
}

Senior Engineer Perspective

The options-object-identity trap here is the exact same class of bug as Q21's fetch-params bug — an inline {} passed as `options` recreates the observer every render unless memoized. For genuinely large lists (hundreds+ of observed elements with identical thresholds), the next-level optimization libraries like `react-intersection-observer` apply is a single shared observer instance with an internal element-to-callback map, rather than one observer per hook instance — worth naming as the "if this becomes a bottleneck" escalation path.

Q86. Implement useKeyPress / useHotkeys — a hook that fires a callback on a specific key combo, correctly ignoring keystrokes typed into form fields.

ROI: ★★★★☆ Frequency: High

Short Answer

Attach a keydown listener at the document level, compare event.key (and modifier flags for combos) against the target combo, and — critically — check whether event.target is an editable element (`input`, `textarea`, `contenteditable`) before firing, so a global "delete" or "s" shortcut doesn't fire while a user is typing "delete" or "s" into a text field.

Code Example

function isEditableTarget(target: EventTarget | null): boolean {
  if (!(target instanceof HTMLElement)) return false;
  const tag = target.tagName;
  return tag === "INPUT" || tag === "TEXTAREA" || target.isContentEditable;
}

function useHotkey(
  combo: { key: string; ctrl?: boolean; shift?: boolean; meta?: boolean },
  handler: () => void,
  { ignoreInputs = true } = {}
) {
  const handlerRef = useRef(handler);
  useEffect(() => { handlerRef.current = handler; }, [handler]);

  useEffect(() => {
    const onKeyDown = (e: KeyboardEvent) => {
      if (ignoreInputs && isEditableTarget(e.target)) return; // don't hijack typing
      const matches =
        e.key.toLowerCase() === combo.key.toLowerCase() &&
        !!combo.ctrl === e.ctrlKey &&
        !!combo.shift === e.shiftKey &&
        !!combo.meta === e.metaKey;
      if (matches) {
        e.preventDefault();
        handlerRef.current();
      }
    };
    document.addEventListener("keydown", onKeyDown);
    return () => document.removeEventListener("keydown", onKeyDown);
  }, [combo.key, combo.ctrl, combo.shift, combo.meta, ignoreInputs]);
}

// Usage: Cmd/Ctrl+K opens a command palette, but not while typing in a text field
useHotkey({ key: "k", meta: true }, () => setCommandPaletteOpen(true));

Senior Engineer Perspective

The "ignore editable targets" guard is the single most-forgotten detail in hand-rolled hotkey implementations, and it's the difference between a shortcut hook that's pleasant to use and one that infuriates users by hijacking their typing. A senior answer also flags cross-platform modifier handling (Cmd on Mac vs Ctrl on Windows/Linux for "primary" shortcuts) as a real detail production hotkey libraries (`react-hotkeys-hook`, `mousetrap`) handle so you don't have to hand-roll it per-app.

Q87. Implement useWindowSize with performance in mind — what's wrong with updating state on every single "resize" event, and how do libraries like usehooks-ts address it?

ROI: ★★★★☆ Frequency: High

Short Answer

The browser fires resize continuously and rapidly while a user drags a window edge — updating React state on every single event triggers a re-render on every single event, which for a component high in the tree (re-rendering many descendants) can visibly jank the resize interaction. The standard fix is to throttle or debounce the state update itself (not the listener registration), so React only re-renders a handful of times during a drag, not hundreds.

Code Example

function useWindowSize(debounceMs = 150) {
  const [size, setSize] = useState({ width: window.innerWidth, height: window.innerHeight });

  useEffect(() => {
    let timeoutId: ReturnType<typeof setTimeout>;

    const onResize = () => {
      clearTimeout(timeoutId); // debounce: only commit the LAST size in a burst
      timeoutId = setTimeout(() => {
        setSize({ width: window.innerWidth, height: window.innerHeight });
      }, debounceMs);
    };

    window.addEventListener("resize", onResize);
    return () => {
      window.removeEventListener("resize", onResize);
      clearTimeout(timeoutId); // don't let a pending debounce fire after unmount
    };
  }, [debounceMs]);

  return size;
}

Senior Engineer Perspective

Point out the tradeoff explicitly: debouncing means the size reported during an active drag lags behind the real window size until the drag pauses, which is fine for "recompute a layout breakpoint" but wrong for "draw a resize handle that must track the cursor in real time" — the latter needs to read `window.innerWidth` directly in the event handler without going through React state/re-renders at all, since no amount of debouncing state updates removes the fundamental "React re-render" cost from the hot path.

Q88. Implement useIsFirstRender / useUpdateEffect — a version of useEffect that skips its first invocation and only runs on subsequent updates. What's it for?

ROI: ★★★★☆ Frequency: Medium

Short Answer

Sometimes you want an effect to react to a value changing, not to also fire on mount (e.g. "show a toast when the filter changes" shouldn't fire a toast on initial page load, only on subsequent user-driven changes). useUpdateEffect wraps useEffect with a ref flag that tracks whether this is the first render, and skips the callback body exactly once.

Code Example

function useUpdateEffect(effect: React.EffectCallback, deps?: React.DependencyList) {
  const isFirstRender = useRef(true);

  useEffect(() => {
    if (isFirstRender.current) {
      isFirstRender.current = false;
      return; // skip the callback (and any cleanup) on the VERY first run
    }
    return effect();
    // eslint-disable-next-line react-hooks/exhaustive-deps
  }, deps);
}

// Usage: notify on filter CHANGES, but not on initial mount
function ResultsList({ filter }: { filter: string }) {
  useUpdateEffect(() => {
    toast(`Filter changed to "${filter}"`);
  }, [filter]);
  return /* ... */ null;
}

Senior Engineer Perspective

Flag the honest downside: this pattern intentionally works around React's mental model (effects normally run consistently on mount and every relevant update, which is what makes them predictable), so it should be reached for deliberately and sparingly, not as a default replacement for `useEffect`. It's also one of the few legitimate places an exhaustive-deps eslint-disable comment is defensible, since the hook's whole contract is "pass deps through opaquely," and the linter can't see that.

Q89. Implement useOnScreen combined with useLocalStorage to build a "has the user ever scrolled past this banner" one-time-dismiss hook. What does composing two library-style hooks teach you about layering?

ROI: ★★★☆☆ Frequency: Low

Short Answer

Two independent, general-purpose hooks — one detecting visibility (`useIntersectionObserver`/`useOnScreen`), one persisting a flag (`useLocalStorage`) — combine into a specific feature ("mark this banner as seen forever, once it's been visible") without either hook knowing anything about the other. This is the composition principle from earlier in the chapter applied to two *library-style, publishable* hooks rather than app-internal ones — proof the layering discipline scales beyond hand-wavy examples.

Code Example

function useDismissOnceSeen(storageKey: string) {
  const [ref, isVisible] = useIntersectionObserver<HTMLDivElement>({ threshold: 0.5 });
  const [wasSeen, setWasSeen] = useLocalStorage(storageKey, false);

  useEffect(() => {
    if (isVisible && !wasSeen) setWasSeen(true); // persist the FIRST time it's seen
  }, [isVisible, wasSeen, setWasSeen]);

  return [ref, wasSeen] as const;
}

// Usage: banner never shows again once it's been scrolled into view once, EVER
function PromoBanner() {
  const [ref, alreadySeen] = useDismissOnceSeen("promo-banner-seen");
  if (alreadySeen) return null;
  return <div ref={ref} className="banner">Limited time offer!</div>;
}

Senior Engineer Perspective

The subtlety to flag: once alreadySeen becomes true, the component early-returns null — meaning the ref is no longer attached to any DOM node, and the intersection observer will be cleaned up automatically as an effect dependency of the (now-unmounted-from-that-branch) hook. Tracing through that lifecycle correctly, and confirming there's no dangling observer left watching a detached node, is exactly the kind of "does this actually clean up correctly in every branch" review a senior engineer runs before approving this pattern.

SECTION 14 - CUSTOM HOOK API DESIGN & ANTI-PATTERNS

Q90. What naming conventions should a team enforce for custom hooks beyond just "starts with use"?

ROI: ★★★★☆ Frequency: High

Short Answer

Beyond the mandatory use prefix: name the hook after the *capability it provides*, not its internal mechanism (`useAuth`, not `useAuthContextReducer`); keep it a noun-phrase-like verb (`useToggle`, `useDebounce`, `useFetch`) rather than a full sentence; and be consistent about whether the team's hooks return tuples or objects for a given "shape" of use case (see Q91) so consumers develop a reliable intuition for how to destructure any given hook without reading its source first.

Code Example

// Good: names the CAPABILITY, hides the mechanism
function useAuth() { /* internally: useContext + useReducer, consumer doesn't care */ }

// Bad: names the IMPLEMENTATION, leaks internals into the API surface
function useAuthContextReducerWithLocalStorageSync() { /* ... */ }

// Bad: reads like an instruction, not a capability
function useShouldComponentShowLoadingSpinnerBasedOnFetchState() { /* ... */ }

// Good: short, capability-named, consistent with the rest of the codebase's hooks
function useIsLoading() { /* ... */ }

Senior Engineer Perspective

The deeper principle: a hook's name is part of its public API and should be stable even if its implementation changes completely (swapping `useReducer` for an external store shouldn't force a rename) — naming after mechanism couples the API to an implementation detail that's likely to change, exactly the anti-pattern this whole design section is about avoiding.

Q91. Array/tuple return vs object return — walk through the concrete tradeoffs, not just "useState does a tuple."

ROI: ★★★★★ Frequency: Extremely High

Short Answer

Tuples (arrays) let the consumer freely rename on destructure (const [isOpen, toggle] = useToggle()) with zero ceremony, which is ideal when there are exactly two or three values and their meaning is obvious from position/context — exactly useState's case. Objects are self-documenting at the call site (const { data, error, loading } = useFetch()), support optional/partial destructuring without needing to skip positions with commas, and scale far better past three or four returned values, but force the consumer to rename with `as` syntax if they need a different local name and risk key-order-independent but still shape-coupled call sites.

Detailed Answer

The concrete rule of thumb most style guides converge on: 2 (occasionally 3) closely-related, positionally-obvious values with no natural names beyond "the thing" and "the setter for the thing" → tuple. Three or more values, especially with mixed types (some booleans, some data, some functions) where position doesn't self-explain meaning → object. Skipping values in a tuple (`const [, setValue] = useState()`) is a real but minor tuple downside; needing `{ data: userData }` renaming boilerplate is the equivalent object downside.

Code Example

// Tuple: 2 values, position is self-explanatory, free renaming - useState-shaped
const [isOpen, setIsOpen] = useToggle();
const [count, setCount] = useState(0);

// Object: several values, mixed meaning, self-documenting at the call site
const { data, error, isLoading, refetch } = useFetch(url);
// Compare the tuple version - much less clear what each position means:
const [data, error, isLoading, refetch] = useFetchTuple(url); // which one is which, again?

Senior Engineer Perspective

A great way to close this answer: "I'd apply the same heuristic React's own team applied — `useState` is a tuple because it's always exactly `[value, setter]` with an obvious pairing; `useFetch`-shaped hooks return objects in every mainstream library (`useQuery` from TanStack Query, SWR's `useSWR`) because the return shape has grown organically over time (add a `refetch`, add an `isStale`) in a way tuples can't accommodate without consumers renumbering every destructure at every call site." Naming that real-library precedent is a strong, concrete answer.

Q92. What does "a hook that does too much" look like in practice, and how do you refactor it?

ROI: ★★★★★ Frequency: High

Short Answer

A hook that does too much usually reveals itself by an ever-growing return object mixing unrelated concerns (fetching, form state, a modal's open/close, analytics) that different consumers use different slices of — a strong sign it should be split into several smaller hooks, each independently composable, rather than one hook everyone imports but only partially uses.

Detailed Answer

The tell in code review: look at a hook's return object and ask "does every consumer of this hook use every field it returns?" If different call sites destructure wildly different subsets, that's the same signal as a God object/God component — the hook has accreted multiple responsibilities that happened to be developed together but aren't conceptually one thing. The fix is almost always splitting along the boundaries revealed by which fields travel together across call sites, then optionally composing them back together in a higher-level hook for the one place that genuinely needs all of them (per the layering principle from earlier in this chapter).

Code Example

// TOO MUCH: one hook doing fetching + pagination + sorting + selection - unrelated concerns
function useProductTable(url) {
  // fetching state, pagination state, sort state, row-selection state, ALL tangled together
  return { data, error, isLoading, page, setPage, sortKey, setSortKey, selectedIds, toggleSelect };
}
// Consumer A only needs { data, isLoading }. Consumer B only needs { selectedIds, toggleSelect }.
// Both are forced to depend on the WHOLE hook's re-render behavior regardless.

// BETTER: split along the boundaries usage actually reveals
function useProductData(url) { return { data, error, isLoading }; }
function usePagination() { return { page, setPage }; }
function useSort(initialKey) { return { sortKey, setSortKey }; }
function useSelection() { return { selectedIds, toggleSelect }; }

// Compose them back together ONLY where the full set is genuinely needed:
function useProductTable(url) {
  return { ...useProductData(url), ...usePagination(), ...useSort("name"), ...useSelection() };
}

Senior Engineer Perspective

This question is really asking whether you apply single-responsibility thinking to hooks the same way you'd apply it to classes or modules — a hook is a unit of reusable logic, and the same code-smell instincts (a class doing too much, a component doing too much) transfer directly. The strongest answers describe a concrete diagnostic ("look at what each call site actually destructures") rather than a vague "keep hooks small" platitude.

Q93. What's the risk of "over-abstracting too early" — building a generic custom hook before you have two real call sites that need it?

ROI: ★★★★☆ Frequency: High

Short Answer

A hook extracted from a single use case is a guess at what's generic versus what's specific to that one call site — without a second, different consumer to validate the abstraction against, you risk baking in assumptions (specific option names, a specific return shape) that don't actually generalize, and then have to awkwardly bend the "generic" hook's API to fit the second real use case anyway, often worse than if you'd waited and extracted from two concrete examples at once.

Detailed Answer

This is the "Rule of Three" (or "wait for the second/third duplication before abstracting") applied specifically to hooks. The failure mode is a premature `useGenericThing(config)` with a config object shaped exactly like the one original call site's needs, that then needs three new optional flags bolted on on the very next feature that tries to reuse it — at which point the "generic" hook is really just the first use case with extra parameters, not a real abstraction. Two real call sites reveal what's actually shared versus what only felt shared from one example.

Code Example

// Extracted from ONE call site, guessing at what's "generic"
function useEntityForm(config: { fields: string[]; onSubmit: (data) => void }) {
  // shaped exactly like the ONE form that motivated writing this
}

// Second real use case doesn't fit cleanly - needs multi-step, conditional fields,
// a different validation strategy - the "generic" hook grows special-case flags:
function useEntityForm(config: {
  fields: string[];
  onSubmit: (data) => void;
  multiStep?: boolean;         // bolted on for use case #2
  conditionalFields?: unknown; // bolted on for use case #2
  validationStrategy?: "sync" | "async"; // bolted on for use case #2
}) { /* increasingly a pile of special cases, not a clean abstraction */ }

Senior Engineer Perspective

A senior engineer's default instinct here should be named explicitly: write the concrete, specific version inline for the first use case, resist extracting a hook at all until a second real (not hypothetical) consumer shows up, and then extract the abstraction from what's *actually* shared between the two real examples — not from imagining what a third, future consumer might someday need. Premature generality is a more expensive mistake to unwind than a small amount of duplication.

Q95. Is it an anti-pattern for a custom hook to return JSX? Why or why not, and is there a legitimate exception?

ROI: ★★★☆☆ Frequency: Medium

Short Answer

Generally yes — a hook returning JSX blurs the line between "reusable logic" (what hooks are for) and "reusable UI" (what components are for), and it breaks composability: you can't easily wrap, conditionally render, or pass returned JSX through the same tools (React.memo, Suspense boundaries) you'd apply to a component used normally in JSX. The common legitimate exception: a hook that returns a small piece of *tightly coupled* markup that's meaningless without the hook's state (e.g. a toast/notification hook returning both the trigger function and the rendered toast container) — even then, many teams prefer splitting it into a hook plus a sibling component instead.

Code Example

// QUESTIONABLE: hook returning JSX blurs "logic" and "UI" responsibilities
function useConfirmDialog() {
  const [isOpen, setIsOpen] = useState(false);
  const dialog = isOpen ? <ConfirmModal onClose={() => setIsOpen(false)} /> : null;
  return { open: () => setIsOpen(true), dialog }; // caller must remember to RENDER `dialog` somewhere
}

// PREFERRED: hook returns state/handlers only; a sibling component owns the markup
function useConfirmDialog() {
  const [isOpen, setIsOpen] = useState(false);
  return { isOpen, open: () => setIsOpen(true), close: () => setIsOpen(false) };
}
function ConfirmDialog({ isOpen, close }) {
  return isOpen ? <ConfirmModal onClose={close} /> : null; // ordinary component, composes normally
}

Senior Engineer Perspective

The sharpest articulation of "why": a hook returning JSX means the caller must remember to render the returned element *somewhere* in their tree, which is an easy-to-forget, easy-to-misplace obligation that a normal component (which you're always forced to place explicitly in JSX) doesn't have. Preferring "hook returns state/handlers, sibling component renders" keeps the two responsibilities — logic and markup — cleanly separable and independently testable, which is the entire reason hooks were introduced as a concept distinct from components in the first place.

Q96. How do you version or evolve a widely-used internal custom hook's API without breaking every consumer at once?

ROI: ★★★★☆ Frequency: Medium

Short Answer

Treat a shared hook exactly like a package's public API: additive changes (new optional fields/params with sensible defaults) are safe to ship directly; breaking changes (renaming a returned field, changing tuple order, changing default behavior) need either a new hook name (`useFetchV2`) migrated to incrementally, or a codemod, or a deprecation period where the old shape is still supported alongside a console warning pointing at the new one.

Code Example

// Additive change: safe, no consumer breaks, default preserves old behavior
function useFetch(url: string, options: { retries?: number } = {}) {
  const { retries = 0 } = options; // new capability, old call sites unaffected
  /* ... */
}

// Breaking change: rename the returned field shape - needs a migration path
function useFetch(url: string) {
  const result = { /* ... */ };
  if (process.env.NODE_ENV !== "production" && "loading" in result) {
    console.warn("useFetch: `loading` is renamed to `isLoading`, update your destructure.");
  }
  return { ...result, loading: result.isLoading }; // temporary back-compat shim
}

Senior Engineer Perspective

This question is testing whether you think about internal hooks as a real API contract with real consumers who don't control the timing of your changes — the same discipline as versioning any shared library. A senior answer distinguishes clearly between additive (safe, ship it) and breaking (needs a deliberate migration strategy) changes, rather than treating every hook change as equally low-risk just because it "lives in the same repo" as its consumers.

Q97. Review this hook and identify every API design anti-pattern in it: useUserSettings(userId, onSuccess, onError, cache, skipValidation, true).

ROI: ★★★★★ Frequency: High

Short Answer

Multiple problems at once: (1) too many positional parameters with no self-documenting names at the call site — the trailing bare true is completely unreadable without checking the signature; (2) mixing callbacks (`onSuccess`/`onError`) into hook parameters instead of returning a state shape the caller reads declaratively, which fights React's data-flow model and is easy to get stale-closure bugs from; (3) a `skipValidation` boolean parameter, which is usually a sign the hook is doing two different things (validated and unvalidated fetch) that should be two call sites or one clearer parameter, not a silent behavior-flipping flag; (4) an ambiguous `cache` parameter of unstated type/purpose.

Detailed Answer

The fix touches everything covered in this section: collapse the positional arguments into a named config object (Q28); replace `onSuccess`/`onError` callbacks with a returned state object the caller reads reactively (this chapter's data-fetching sections) rather than callbacks that risk closing over stale values; rename or eliminate the boolean flag in favor of either a clearer name (`validationMode: "strict" | "skip"`) or, better, two distinctly-named hooks if the behaviors are genuinely different enough to warrant it; and give `cache` an explicit, typed, documented shape rather than an ambiguous untyped parameter.

Code Example

// BEFORE: everything wrong with hook API design in one signature
useUserSettings(userId, onSuccess, onError, cache, skipValidation, true);
// What does the trailing `true` mean?? Nobody can tell without opening the source.

// AFTER: named config, returns state instead of taking callbacks, explicit types
type UseUserSettingsOptions = {
  cache?: Map<string, UserSettings>;
  validationMode?: "strict" | "skip";
  autoRefetch?: boolean; // replaces the mystery trailing `true`
};

function useUserSettings(
  userId: string,
  options: UseUserSettingsOptions = {}
): FetchState<UserSettings> {
  // returns { status, data, error } - caller reads it declaratively, no stale callbacks
}

// Call site is now self-documenting without opening the implementation:
const { status, data, error } = useUserSettings(userId, {
  validationMode: "skip",
  autoRefetch: true,
});

Senior Engineer Perspective

This question is a deliberate composite of nearly every anti-pattern discussed across this chapter's final section — positional-argument overload, callback-based APIs fighting React's declarative model, boolean flags hiding two behaviors in one function, and unclear typing — packed into one unreadable call site. Walking through each problem methodically (rather than a vague "this is bad API design") and mapping each fix back to a specific principle is exactly what demonstrates you've internalized the material rather than pattern-matched a single rule.
