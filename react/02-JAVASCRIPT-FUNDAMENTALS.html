SECTION 1 - TYPES & COERCION

Q1. What is the difference between var, let, and const, and what is the Temporal Dead Zone?

ROI: ★★★★★ Frequency: Extremely High

Short Answer

var is function-scoped and hoisted with an initial value of undefined. let and const are block-scoped and, although hoisted, they live in the Temporal Dead Zone (TDZ) until the line where they are declared — accessing them before that throws a ReferenceError. const additionally forbids reassignment of the binding (not deep immutability).

Detailed Answer

Scoping

var ignores block boundaries — a var declared inside an if or for block leaks to the enclosing function. let/const are confined to the nearest { } block, which is why they fixed the classic loop-closure bug where every callback captured the same var i.

The Temporal Dead Zone

All three are hoisted to the top of their scope, but they behave differently before initialization. var is initialized to undefined during hoisting, so reading it early is merely useless, not fatal. let/const bindings are created but left uninitialized; the span from the top of the block to the declaration line is the TDZ, and any access in that window throws. The TDZ exists deliberately — it turns silent bugs into loud errors and makes const semantically coherent (you can never observe a const before its one and only assignment).

const is not "immutable"

const freezes the binding, not the value. A const object can still have its properties mutated; only reassigning the variable itself is blocked. Use Object.freeze (shallow) if you need value-level immutability.

Featurevarletconst
ScopeFunctionBlockBlock
HoistedYes (= undefined)Yes (TDZ)Yes (TDZ)
ReassignableYesYesNo
Redeclarable in scopeYesNoNo

Code Example

console.log(a); // undefined  (var is hoisted & initialized)
var a = 1;

console.log(b); // ReferenceError: Cannot access 'b' before initialization
let b = 2;      // b was in the TDZ above this line

const obj = { n: 1 };
obj.n = 2;      // OK — mutating a property
// obj = {};    // TypeError — reassigning the const binding

Project Example

In React you almost always declare hooks and derived values with const (const [count, setCount] = useState(0)). It signals intent — this reference will not be reassigned within the render — and prevents accidental shadowing bugs. let shows up for accumulators inside a useMemo body; var should essentially never appear in modern code.

Senior Engineer Perspective

The interviewer wants to hear "TDZ" unprompted and to know that const is about the binding, not the value — juniors often claim const means immutable. A strong follow-up: "Why does typeof undeclaredVar return 'undefined' but typeof on a let in its TDZ throws?" Answer: typeof is the historical exception that safely handles never-declared names, but TDZ variables are declared, so even typeof throws for them.

Q2. Explain hoisting for variables and functions.

ROI: ★★★★☆ Frequency: High

Short Answer

Hoisting is the JS engine's compile phase moving declarations to the top of their scope before execution. Function declarations are hoisted whole (callable before their line). var declarations are hoisted and set to undefined. let/const and function expressions/arrow functions are hoisted but stay uninitialized (TDZ).

Detailed Answer

It helps to think of two phases. In the creation phase the engine scans the scope and registers bindings; in the execution phase it runs the code line by line. Only the declaration is hoisted, never the assignment. So var x = 5 is conceptually split into var x (hoisted) and x = 5 (stays in place).

Function declarations are special: the entire function object is available before its textual position, which is why you can call a helper defined lower in the file. A function expression assigned to a variable follows that variable's rules — a var holding a function is undefined until assigned, and a const arrow function is in the TDZ.

Code Example

greet();            // "hi" — declaration hoisted whole
function greet() { console.log("hi"); }

sayBye();           // TypeError: sayBye is not a function
var sayBye = function () { console.log("bye"); };
// var sayBye is hoisted as undefined; calling undefined() throws

Senior Engineer Perspective

The trap is the difference between ReferenceError (TDZ / undeclared) and TypeError (calling an undefined value). If a candidate says "everything gets moved to the top," push them: does the value move too? The precise answer — declarations are registered, initializations stay put — is the senior signal. In practice, rely on hoisting only for function declarations; write everything else before use.

Q3. What is the difference between == and === and when is coercion dangerous?

ROI: ★★★★★ Frequency: Extremely High

Short Answer

=== (strict equality) compares type and value with no conversion. == (loose equality) coerces the operands to a common type first, which produces surprising results. Rule of thumb: always use ===; the one pragmatic exception is x == null to test for both null and undefined at once.

Detailed Answer

== follows the abstract equality algorithm: if types differ it applies a chain of conversions — null and undefined are loosely equal to each other and nothing else; strings and numbers compare as numbers; booleans are converted to numbers; objects are converted to primitives via valueOf/toString. This is why 0 == "", 0 == false, and "" == false are all true, and why [] == ![] is true — a genuinely confusing surface.

The pragmatic exception is the loose null check. value == null is true for exactly null and undefined, which is a concise nullish guard many codebases (and ESLint configs) explicitly allow.

Code Example

0 == "";        // true  — both coerce to 0
0 == false;     // true
"" == false;    // true
null == undefined; // true
null === undefined; // false

0 === "";       // false — no coercion
NaN === NaN;    // false — use Number.isNaN()

// The accepted exception:
if (value == null) { /* runs for null OR undefined */ }

Senior Engineer Perspective

Expect a whiteboard trap like [] == ![]. Walk it: ![] is false, so it becomes [] == false, then [] == 0, then "" == 0, then 0 == 0 → true. You do not need to memorize the table, but you should demonstrate that you understand coercion happens in steps and that this is exactly why === is the default. Bonus: mention Object.is, which is like === but treats NaN as equal to itself and distinguishes +0 from -0.

Q4. Primitive vs reference types — how do copying and passing work?

ROI: ★★★★★ Frequency: Extremely High

Short Answer

Primitives (string, number, boolean, null, undefined, symbol, bigint) are copied and compared by value. Objects, arrays, and functions are held by reference — assigning or passing them copies the reference (a pointer), not the underlying data, so two variables can mutate the same object. Equality (===) compares primitives by value and objects by identity.

Detailed Answer

JavaScript is always "pass by value" — but for objects the value that is passed is the reference. So a function can mutate the properties of an object you passed in (the caller sees the change), yet reassigning the parameter to a brand-new object does not affect the caller. This distinction trips up many candidates.

This is the single biggest source of React state bugs: mutating an object or array in place does not change its reference, so React's Object.is bailout sees "no change" and skips the re-render. You must produce a new reference.

Code Example

let a = { n: 1 };
let b = a;          // b holds the SAME reference
b.n = 99;
console.log(a.n);   // 99 — same object

function replace(x) { x = { n: 0 }; } // reassigns local param only
replace(a);
console.log(a.n);   // 99 — caller unaffected

{ n: 1 } === { n: 1 }; // false — different identities

// React: WRONG (same reference, no re-render)
state.items.push(newItem); setState(state.items);
// RIGHT (new reference)
setState(prev => [...prev, newItem]);

Senior Engineer Perspective

The interviewer is really testing whether you understand why React needs immutable updates and why comparing objects with === checks identity, not contents. Strong candidates connect the language semantics directly to React.memo, dependency arrays, and Redux reducers. A common follow-up: "Why does useEffect fire on every render when a dependency is an object literal?" — because the literal is a new reference each render.

Q5. Name the most common type-coercion gotchas.

ROI: ★★★★☆ Frequency: High

Short Answer

The usual suspects: + concatenates when either operand is a string; typeof null is "object"; NaN !== NaN; [] + [] is "" and [] + {} is "[object Object]"; and falsy values (0, "", NaN, null, undefined, false) all coerce to false in boolean context.

Detailed Answer

The key mental model: + is overloaded — if either side is a string (or coerces to one), it concatenates; otherwise it adds numerically. Every other arithmetic operator (-, *, /) forces numeric coercion. That is why "5" - 1 is 4 but "5" + 1 is "51".

In React the falsy-coercion gotcha bites when you conditionally render with &&: {items.length && <List/>} renders a literal 0 on screen when the array is empty, because 0 is falsy and gets returned. Use items.length > 0 && ... or a ternary.

Code Example

1 + "2";        // "12"  (concatenation)
"5" - 1;        // 4     (numeric coercion)
typeof null;    // "object"  (historical bug)
typeof NaN;     // "number"
Number.isNaN(NaN); // true — the correct NaN test

// React footgun — renders "0" when empty:
{count && <Badge value={count} />}
// Fix:
{count > 0 && <Badge value={count} />}

Senior Engineer Perspective

The {0 && ...} JSX bug is a favourite because it connects raw language behaviour to a real React defect. If you volunteer it, you signal that you have shipped React and been burned. Also mention that String(x), Number(x), and Boolean(x) are explicit conversions you should prefer over relying on implicit coercion.

SECTION 2 - SCOPE & CLOSURES

Q6. What is a closure? Give real production use cases.

ROI: ★★★★★ Frequency: Extremely High

Short Answer

A closure is a function bundled together with references to the variables from the scope where it was defined. Because that scope stays alive as long as the inner function is reachable, the function "remembers" and can keep reading and updating those variables even after the outer function has returned.

Detailed Answer

Closures are the mechanism behind private state, function factories, and event handlers. In React, every hook relies on closures: the callback you pass to useState, useEffect, or an event handler closes over the props and state from the render in which it was created. This is also the source of the "stale closure" bug — an effect or interval captures an old value and never sees updates unless dependencies or a functional updater are used.

Real use cases

  • Private state / encapsulation: variables unreachable from outside, exposed only through returned methods.
  • Counters & ID generators: maintain a private tally across calls.
  • Memoization: a cache held in the enclosing scope, shared across invocations.
  • Currying & partial application: capturing earlier arguments.
  • Debounce / throttle: the timer handle lives in the closure.

Code Example

// Private state + counter
function createCounter() {
  let count = 0;                 // private, not accessible outside
  return {
    inc() { return ++count; },
    get() { return count; },
  };
}
const c = createCounter();
c.inc(); c.inc();
c.get();  // 2  — count survives via closure

// Memoization
function memoize(fn) {
  const cache = new Map();       // captured across calls
  return (arg) => {
    if (cache.has(arg)) return cache.get(arg);
    const result = fn(arg);
    cache.set(arg, result);
    return result;
  };
}

// Debounce
function debounce(fn, ms) {
  let timer;                     // handle lives in the closure
  return (...args) => {
    clearTimeout(timer);
    timer = setTimeout(() => fn(...args), ms);
  };
}

Project Example

A debounced search box in React: const debounced = useMemo(() => debounce(onSearch, 300), [onSearch]). The returned function closes over the timer so successive keystrokes reset it. The classic bug — an interval inside useEffect(() => setInterval(() => setCount(count + 1)), []) always logging 1 — is a stale closure; the fix is the functional updater setCount(c => c + 1).

Senior Engineer Perspective

Anyone can recite the definition. The senior differentiator is naming a concrete production use (memoization, debounce, private state) and connecting closures to React's stale-closure pitfall. Expect the loop question: why does for (var i...) setTimeout(() => log(i)) print the final value repeatedly, and how does let fix it? Because let creates a fresh binding per iteration, so each closure captures its own i.

Q7. Explain lexical scope and the scope chain.

ROI: ★★★★☆ Frequency: High

Short Answer

Lexical (static) scope means a variable's accessibility is determined by where it is written in the source, not by where the function is called. When resolving an identifier, the engine walks outward through the chain of enclosing scopes until it finds the binding or reaches the global scope.

Detailed Answer

Each function creates a new scope nested inside the scope where it was defined. Name lookup goes inner → outer (the scope chain); it never goes into sibling or caller scopes. This is precisely what makes closures predictable — a closure captures the lexical environment of its definition site, so you can reason about which variables it sees just by reading the code.

Contrast with dynamic scope (used by some other languages) where lookup would follow the call stack. JavaScript is lexically scoped for variables, but note that this is the exception — for ordinary functions this is bound dynamically at call time, which is why arrow functions (which capture this lexically) were introduced.

Code Example

const outer = "O";
function parent() {
  const mid = "M";
  function child() {
    const inner = "I";
    console.log(inner, mid, outer); // I M O — walks up the chain
  }
  child();
}
parent();
// child cannot be called from elsewhere and still see mid — scope is
// fixed by where child is DEFINED, not where it is called.

Senior Engineer Perspective

The distinction interviewers probe is "lexical vs dynamic scope" and the fact that variables are lexical while regular-function this is dynamic. If you nail that one sentence, you have separated yourself from candidates who conflate the two. It also sets up the next topic cleanly.

SECTION 3 - THIS & FUNCTIONS

Q8. How is this determined? Explain all five binding rules.

ROI: ★★★★★ Frequency: Extremely High

Short Answer

this is decided at call time by how a function is invoked, in this priority order: (1) new binding — a fresh object; (2) explicit binding via call/apply/bind; (3) implicit binding — the object left of the dot; (4) default binding — undefined in strict mode, else the global object. Arrow functions ignore all of these and inherit this lexically from their enclosing scope.

Detailed Answer

RuleHow this is setExample
Defaultundefined (strict) / global (sloppy)fn()
ImplicitThe object before the dotobj.fn()
ExplicitThe first arg to call/apply/bindfn.call(ctx)
newThe newly constructed objectnew Fn()
ArrowLexical — captured from definition() => this

The most common bug is losing implicit binding: passing obj.method as a callback strips the object off the left of the dot, so at call time it invokes as a bare function and this becomes undefined. Arrow functions solve this because they have no this of their own — they close over the surrounding scope's this, which is exactly why they are the default for React class-method handlers and array-callback bodies.

Code Example

const user = {
  name: "Ada",
  greet() { return "Hi " + this.name; },
  greetArrow: () => "Hi " + this.name, // this = enclosing (module) scope
};

user.greet();               // "Hi Ada" — implicit binding
const g = user.greet;
g();                        // "Hi undefined" — lost binding (default)
g.call(user);               // "Hi Ada" — explicit binding

// Arrow captures lexical this — fixes callbacks:
class Timer {
  seconds = 0;
  tick = () => { this.seconds++; }; // arrow keeps `this` = instance
}

Senior Engineer Perspective

Interviewers love "predict the output" chains that alternate methods, detached references, and arrows. Say out loud "this depends on the call site, not the definition site — except arrows." Then apply the priority order. A sharp follow-up: what does bind do if you also call the result with new? The new binding wins over the earlier bind for this, though bound leading arguments are preserved.

Q9. What do call, apply, and bind do, and how do they differ?

ROI: ★★★★☆ Frequency: High

Short Answer

All three set this explicitly. call invokes immediately with arguments listed individually; apply invokes immediately with arguments as an array; bind does not invoke — it returns a new function permanently bound to the given this (and optional preset arguments) for later use.

Detailed Answer

Mnemonic: apply takes an array; call takes a comma-separated list; bind gives you back a function. With modern spread syntax, apply is largely replaced by fn.call(ctx, ...args) or just fn(...args), but it still appears in older code and in interview questions. bind also supports partial application — you can pre-fill leading arguments.

Code Example

function intro(greeting, punct) {
  return greeting + ", " + this.name + punct;
}
const p = { name: "Lin" };

intro.call(p, "Hi", "!");         // "Hi, Lin!"
intro.apply(p, ["Hi", "!"]);      // "Hi, Lin!"  (args as array)
const bound = intro.bind(p, "Hi");// returns fn, not called yet
bound("!");                        // "Hi, Lin!"  (partial application)

// apply's classic use, now obsolete with spread:
Math.max.apply(null, [3, 1, 4]);  // 4
Math.max(...[3, 1, 4]);           // 4  (modern equivalent)

Senior Engineer Perspective

Be ready to hand-implement bind — it is a standard exercise and forces you to combine closures, apply, and the new-vs-bind priority. Also mention that in React with hooks you rarely reach for bind (arrows and useCallback handle context), but you must recognize it in legacy class components where handlers were bound in the constructor to fix this.

SECTION 4 - OBJECTS & PROTOTYPES

Q10. Explain prototypal inheritance and the prototype chain.

ROI: ★★★★☆ Frequency: High

Short Answer

Every object has a hidden link ([[Prototype]], exposed as __proto__) to another object. When you read a property that an object lacks, the engine walks up this chain of prototypes until it finds the property or reaches null. This is how objects share behaviour without copying — and it is what class syntax compiles down to.

Detailed Answer

A constructor function has a .prototype object; instances created with new get their [[Prototype]] pointed at it. Methods defined on the prototype are shared by all instances (one copy in memory) rather than duplicated per object. The lookup chain typically runs instance → Constructor.prototype → Object.prototype → null.

ES6 class is syntactic sugar over exactly this — extends sets up the prototype link, and super delegates up the chain. There is no separate "classical" inheritance under the hood. Writes always happen on the own object (they do not travel up), which is why setting a property shadows rather than mutates the prototype.

Code Example

function Animal(name) { this.name = name; }
Animal.prototype.speak = function () {
  return this.name + " makes a sound";
};

function Dog(name) { Animal.call(this, name); }        // inherit fields
Dog.prototype = Object.create(Animal.prototype);       // inherit methods
Dog.prototype.constructor = Dog;
Dog.prototype.speak = function () { return this.name + " barks"; };

const d = new Dog("Rex");
d.speak();                       // "Rex barks" (own prototype wins)
d.hasOwnProperty("name");        // true — found via Object.prototype

// Equivalent modern syntax:
class Animal2 { constructor(n){ this.name = n; } speak(){ return this.name; } }
class Dog2 extends Animal2 { speak(){ return this.name + " barks"; } }

Senior Engineer Perspective

The differentiator is stating that class is sugar over prototypes, not a different model, and knowing the difference between __proto__ (the instance's link) and .prototype (a property on constructor functions). A common follow-up: why put methods on the prototype instead of inside the constructor? Memory — one shared function versus one per instance. In day-to-day React you rarely author prototype chains, but understanding them explains instanceof, Object.create, and polyfills.

Q11. What does the new operator actually do, step by step?

ROI: ★★★☆☆ Frequency: Medium

Short Answer

new Fn(args) does four things: (1) creates a fresh empty object; (2) links its [[Prototype]] to Fn.prototype; (3) calls Fn with this bound to that new object; (4) returns the new object — unless the constructor explicitly returns its own (non-primitive) object, in which case that is returned instead.

Detailed Answer

Understanding these four steps demystifies constructors, explains why forgetting new leaks properties onto the global object (in sloppy mode) or throws (in strict mode), and lets you hand-write a myNew polyfill — a favourite interview exercise. The subtle step is the return rule: returning a primitive is ignored, but returning an object overrides the freshly created instance.

Code Example

function myNew(Constructor, ...args) {
  const obj = Object.create(Constructor.prototype); // steps 1 + 2
  const result = Constructor.apply(obj, args);      // step 3
  return (result !== null && typeof result === "object")
    ? result                                        // step 4 (explicit object)
    : obj;                                          // step 4 (default)
}

function Point(x, y) { this.x = x; this.y = y; }
const p = myNew(Point, 1, 2);   // Point { x: 1, y: 2 }

Senior Engineer Perspective

Reciting the four steps in order is the whole game here, plus the return-value edge case. If asked "what happens if you call a constructor without new?", answer: this falls back to default binding, so in strict mode you get a TypeError assigning to undefined, and in sloppy mode you silently pollute the global object — which is why new.target guards exist.

Q12. Shallow copy vs deep copy — and what is structuredClone?

ROI: ★★★★☆ Frequency: High

Short Answer

A shallow copy duplicates the top level but shares nested objects by reference ({...obj}, Object.assign, Array.slice). A deep copy recursively clones every level so nothing is shared. The modern built-in for deep cloning is structuredClone(value) (ES2021, in all evergreen browsers and Node 17+), which replaces the old JSON.parse(JSON.stringify(...)) hack.

Detailed Answer

The JSON round-trip technique is limited: it drops undefined, functions, and symbols, turns Date into a string, and throws on circular references. structuredClone handles Date, Map, Set, typed arrays, ArrayBuffer, and circular references — but it cannot clone functions, DOM nodes, or class instances' prototype chain (you get a plain object) and will throw on those.

In React you rarely need a full deep clone; the idiomatic approach is targeted immutable updates — spread only the levels along the path you are changing, which is cheaper and preserves referential equality for untouched branches (helping memo and re-render bailouts).

Code Example

const state = { user: { name: "A" }, tags: ["x"] };

const shallow = { ...state };
shallow.user.name = "B";
state.user.name;            // "B" — nested object was shared!

const deep = structuredClone(state);
deep.user.name = "C";
state.user.name;            // "B" — fully independent

// React idiom: copy only the path you change
setState(prev => ({
  ...prev,
  user: { ...prev.user, name: "New" }, // new refs only on this path
}));

Senior Engineer Perspective

Interviewers want you to (a) know why {...obj} is not enough for nested data, (b) reach for structuredClone over the JSON hack and name the JSON hack's failure modes, and (c) argue that in React you usually want surgical immutable updates, not blanket deep cloning, because preserving references for unchanged subtrees is what makes memoization work.

Q13. When should you use Map/Set instead of a plain object?

ROI: ★★★☆☆ Frequency: Medium

Short Answer

Use a Map when you need keys of any type (objects, not just strings/symbols), guaranteed insertion order, a clean size property, and frequent additions/removals. Use a Set for a collection of unique values with O(1) membership tests. Reach for a plain object for fixed-shape records and when you need JSON serialization.

Detailed Answer

Set gives a concise dedupe ([...new Set(arr)]) and fast lookups compared to Array.includes (O(1) vs O(n)). Note that both use SameValueZero equality, so object keys compare by identity, not by content.

Code Example

// Dedupe an array
const unique = [...new Set([1, 1, 2, 3, 3])]; // [1, 2, 3]

// Map with object keys (impossible with plain objects)
const meta = new Map();
const node = { id: 1 };
meta.set(node, { visited: true });
meta.get(node);           // { visited: true }
meta.size;                // 1

// Fast membership in a React filter
const selected = new Set(selectedIds);
const rows = all.filter(r => selected.has(r.id)); // O(1) per check

Senior Engineer Perspective

The senior nuance is prototype pollution and key flexibility: using a user-supplied string as an object key risks colliding with __proto__ or constructor, whereas a Map is immune. Also mention WeakMap/WeakSet for keying private data off objects without preventing garbage collection — useful for caches keyed by DOM nodes or component instances.

SECTION 5 - ES6+ FEATURES & FUNCTIONAL JS

Q14. How do destructuring, spread, rest, and default parameters work?

ROI: ★★★★★ Frequency: Extremely High

Short Answer

Destructuring unpacks values from arrays/objects into variables. Spread (... in a call or literal) expands an iterable/object into individual elements or properties. Rest (... in a parameter list or destructuring target) collects the remaining items into an array/object. Default parameters supply a fallback when an argument is undefined.

Detailed Answer

The same ... token is spread or rest depending on position: on the right of = or inside a call it spreads; on the left as a target or in a parameter list it collects. Object spread creates a shallow copy and is the workhorse of immutable React updates. Destructuring supports renaming, defaults, and nested patterns, which is why React props are almost always destructured in the function signature.

One gotcha: defaults trigger only for undefined, never for null or other falsy values. So function f(x = 5) uses 5 for f() and f(undefined), but keeps null, 0, and "".

Code Example

// Destructuring with rename + default
const { name, role = "guest" } = user;

// Array destructuring — the useState pattern
const [count, setCount] = useState(0);

// Rest collects the remainder
const [first, ...others] = [1, 2, 3];      // others = [2, 3]
function sum(...nums) { return nums.reduce((a, b) => a + b, 0); }

// Spread — merge / copy (shallow)
const merged = { ...defaults, ...overrides };
const cloned = [...items];

// Common React prop-forwarding idiom
function Button({ variant, ...rest }) {
  return <button className={variant} {...rest} />;
}

// Default only fires for undefined:
function greet(name = "friend") { return "Hi " + name; }
greet(null);       // "Hi null"  — null is NOT replaced

Senior Engineer Perspective

These appear in nearly every React file, so fluency is assumed, not impressive — the differentiator is knowing the edge cases: spread is shallow, defaults fire only on undefined, and rest must be the last parameter. A frequent follow-up: "How would you clone-and-update a nested object immutably?" — nested spread along the changed path, connecting back to Q12.

Q15. Explain optional chaining and nullish coalescing (ES2020).

ROI: ★★★★☆ Frequency: High

Short Answer

Optional chaining ?. short-circuits and returns undefined instead of throwing when a reference in the chain is null or undefined. Nullish coalescing ?? returns its right side only when the left is null or undefined — unlike ||, it does not treat 0, "", or false as missing.

Detailed Answer

Together they eliminate defensive a && a.b && a.b.c ladders and the || default-value bug. The classic || bug: const page = input.page || 1 wrongly overrides a legitimate 0; ?? 1 keeps 0. Optional chaining also works for method calls (obj.fn?.()) and dynamic keys (obj?.[key]). Note ?. short-circuits the whole rest of the chain the moment it hits nullish.

Code Example

const city = user?.address?.city;      // undefined if any link is nullish
const onClick = props.onClick?.();      // calls only if it exists

// ?? vs || — the key difference:
const count = data.count ?? 10;         // keeps 0
const bad   = data.count || 10;         // 0 becomes 10 (bug!)

// Common in React data fetching:
const items = response?.data?.items ?? [];

Senior Engineer Perspective

The expected insight is why ?? exists when we already had || — specifically the falsy-but-valid values 0, "", and false. Bonus: mention you cannot mix ?? with &&/|| without parentheses (a syntax error by design), and that optional chaining stops evaluating the rest of the chain but does not swallow errors thrown deeper in a called function.

Q16. What are pure functions, immutability, and higher-order functions?

ROI: ★★★★☆ Frequency: High

Short Answer

A pure function returns the same output for the same input and has no side effects. Immutability means never mutating existing data — you produce new values instead. A higher-order function takes a function as an argument and/or returns a function. These three ideas underpin React's rendering model, hooks, and state management.

Detailed Answer

React leans hard on these principles. A component's render should be pure — same props/state produce the same UI, no side effects during render (those belong in useEffect or event handlers). Immutable state updates are mandatory because React detects change by reference identity (Object.is); mutating in place defeats memo, useMemo, and reducer purity. Higher-order functions are everywhere: array methods, custom hooks that wrap other hooks, and the (now less common) higher-order component pattern.

Benefits: pure + immutable code is trivially testable, cacheable/memoizable, time-travel-debuggable (Redux DevTools relies on it), and safe under React's concurrent rendering, which may call render multiple times.

Code Example

// Pure — no external state touched, no mutation
const add = (a, b) => a + b;

// Impure — mutates argument (side effect)
const pushImpure = (arr, x) => { arr.push(x); return arr; };
// Pure alternative — returns new array
const pushPure = (arr, x) => [...arr, x];

// Higher-order function: takes and returns functions
const withLogging = (fn) => (...args) => {
  console.log("calling", fn.name, args);
  return fn(...args);
};
const loggedAdd = withLogging(add);

// Immutable Redux-style reducer
function reducer(state, action) {
  switch (action.type) {
    case "add": return { ...state, count: state.count + 1 };
    default: return state;
  }
}

Senior Engineer Perspective

Tie it explicitly to React: "components should be pure functions of props and state, and state must be updated immutably so React's reference comparison detects changes." Mention that React 18+ Strict Mode intentionally double-invokes renders and effects in development to surface impurity. That connection — language principle → framework guarantee — is what marks a senior answer rather than a textbook recital.

Q17. Explain map, filter, and reduce — and when is reduce the wrong tool?

ROI: ★★★★★ Frequency: Extremely High

Short Answer

map transforms each element into a new array of the same length; filter keeps elements matching a predicate; reduce folds the array into a single accumulated value. All three are pure (they return new values and do not mutate the source). Reduce is powerful but often abused — if map/filter/some/find express the intent more clearly, prefer them.

Detailed Answer

reduce is the right tool when you are genuinely collapsing a collection into one result — a sum, a lookup object, a group-by, or a min/max. It is the wrong tool when you are really just mapping or filtering, because a reduce that builds an array is harder to read than the equivalent map/filter and typically re-creates or spreads the accumulator each step (a hidden O(n²) if you spread inside it). Always pass an explicit initial value to reduce — omitting it uses the first element as the seed and throws on an empty array.

In React these show up constantly for rendering lists (items.map(...)), filtering data before display, and computing derived totals inside useMemo.

Code Example

const nums = [1, 2, 3, 4];

nums.map(n => n * 2);              // [2, 4, 6, 8]
nums.filter(n => n % 2 === 0);     // [2, 4]
nums.reduce((sum, n) => sum + n, 0); // 10  — always seed the accumulator

// Legit reduce: build a lookup / group-by
const byId = users.reduce((acc, u) => {
  acc[u.id] = u;                    // mutate the accumulator = O(n)
  return acc;
}, {});

// Reduce ABUSE — just a filter+map in disguise:
const bad = nums.reduce((acc, n) => (n > 1 ? [...acc, n * 2] : acc), []);
// Clearer AND faster (no per-step spread):
const good = nums.filter(n => n > 1).map(n => n * 2);

Project Example

Rendering a table: orders.filter(o => o.active).map(o => <Row key={o.id} {...o} />). Computing a cart total with useMemo(() => items.reduce((t, i) => t + i.price * i.qty, 0), [items]). Normalizing an API response into a keyed lookup with reduce so components can index by id in O(1).

Senior Engineer Perspective

The maturity signal is knowing when not to use reduce. Interviewers respect a candidate who says "I could reduce this, but a filter-then-map reads better and avoids spreading the accumulator every iteration." Also mention flatMap, and that all these methods skip holes in sparse arrays. If pushed on performance, note that chaining map().filter() creates intermediate arrays — fine for UI-sized lists, but for very large data a single loop or a transducer/generator may be warranted.
