SECTION 1 - GRAPHQL FUNDAMENTALS

Q1. Why GraphQL over REST — what specific problems does it solve?

ROI: ★★★★★ Frequency: Extremely High

Short Answer

GraphQL solves three concrete REST pain points: over-fetching (a REST endpoint returns a fixed shape, so a screen that needs only a user's name pulls down their entire profile), under-fetching (a screen needs data from three related resources, so you fire three or four round trips and stitch them together on the client, or the backend team adds a bespoke aggregate endpoint), and endpoint sprawl (every new UI variant tends to spawn a new REST endpoint or a new query-string dialect bolted onto an old one). GraphQL replaces that with a single endpoint and a query language where the client declares exactly the shape of data it needs, and the server returns exactly that shape — no more, no less.

Detailed Answer

REST ties the response shape to the resource, not to the screen. A GET /users/1 returns whatever the backend decided a "user" looks like — for a profile page that might be fine, but a header component that only needs name and avatarUrl still downloads bio, address, preferences, and a dozen other fields. Multiply that by mobile clients on metered connections and it becomes a real performance cost, not just a style complaint.

Under-fetching shows up on composite screens: a dashboard needs the current user, their five most recent orders, and account notifications — three separate REST resources, three requests, three waterfalls (or careful client-side Promise.all orchestration), and three failure/loading states to reconcile. GraphQL lets the client ask for all three in one query, resolved server-side, returned as one JSON payload with one loading state.

The single-endpoint model also changes how APIs evolve. In REST, "the mobile app needs less data than the web app" tends to produce either a bloated shared endpoint or parallel endpoints (/v2/users, /users/lite) that drift out of sync. In GraphQL, every consumer writes its own query against the same schema — the mobile team asks for less, the web team asks for more, and the server never has to guess who's calling.

None of this makes REST "wrong." REST's uniform interface, cacheability via HTTP semantics (ETags, Cache-Control), and simplicity for CRUD-shaped resources are real strengths GraphQL gives up by default (HTTP caching a GraphQL POST is nontrivial — this is part of why Apollo builds its own cache, see Q5). The honest interview answer names the trade-off, not just GraphQL's wins.

Interview Gold Point

Anchor the answer in the two named failure modes — over-fetching and under-fetching — because interviewers are listening for that exact vocabulary. Then immediately volunteer the trade-off: GraphQL gives up free HTTP caching and takes on client-side query complexity and a heavier client library (Apollo/urql) to get normalized caching back. Candidates who present GraphQL as strictly superior read as under-experienced; candidates who can say "one endpoint plus client-declared shape, at the cost of HTTP-level caching and a more complex client" sound like they've shipped it.

Q2. What are GraphQL schema, types, queries, mutations, and subscriptions, and how do they fit together?

ROI: ★★★★★ Frequency: Extremely High

Short Answer

The schema is the contract: a strongly typed description of every object, field, and operation the API supports, written in the GraphQL Schema Definition Language (SDL). Types describe the shape of data (User, Post) and how fields relate to each other. Queries read data, mutations write data (and, by convention, return the updated data so the client doesn't need a follow-up fetch), and subscriptions open a long-lived connection that pushes data to the client when something changes server-side. Every operation you send must satisfy the schema, or it's rejected before your resolver code even runs — that's the value of the type system.

Detailed Answer

Three special root types anchor a schema: Query, Mutation, and Subscription. Every field on Query is an entry point for reading; every field on Mutation is an entry point for writing. Ordinary object types (User, Post, Comment) describe the data graph and can reference each other, which is where "graph" in GraphQL comes from — a query can traverse from a user to their posts to each post's comments to each comment's author in one request.

Scalars (String, Int, Float, Boolean, ID) are the leaves. A trailing ! marks a field non-nullable (String!); a list is wrapped in brackets ([Post!]! means a non-null list of non-null posts). Getting nullability right in schema design matters more than it looks — marking something non-null when the resolver can legitimately fail to produce it causes the entire parent object to null out at runtime (GraphQL's error-propagation rule), which is a classic schema-design mistake interviewers probe (see Q14).

Mutations conventionally return the object they changed (or a payload wrapping it plus any errors), specifically so the client can merge the result straight into cache without an extra round trip — this is the seed of how Apollo's automatic cache updates work (Q6). Subscriptions are the odd one out: instead of request/response, the client keeps a socket open (typically via graphql-ws) and the server pushes a new payload every time the subscribed event fires.

Code Example

  id: ID!

}

  body: String!
  author: User!            # traversal: Post -> User (bidirectional graph)
}

  posts(limit: Int = 10): [Post!]!
}

}

    name
    posts {
      title
      body
    }
  }
}

  createPost(title: $title, body: $body) {
    id
    title
    body
  }
}

Common Mistake

Candidates often describe queries and mutations correctly but blank on why nullability matters — that a non-null field (!) whose resolver throws nulls out the parent object all the way up the tree, potentially wiping out an entire response for one flaky field. The stronger answer treats schema design as an API contract decision, not syntax: default to nullable for anything that can plausibly fail (a network call inside a resolver, an optional relation) and reserve non-null for fields truly guaranteed to resolve, like an object's own id.

SECTION 2 - APOLLO CLIENT CORE

Q3. What does Apollo Client setup and ApolloProvider actually wire up?

ROI: ★★★★☆ Frequency: High

Short Answer

ApolloClient bundles a network transport (a link, usually HttpLink pointed at your GraphQL endpoint) with an InMemoryCache instance, plus configuration like default fetch policies and type policies. <ApolloProvider client={client}> puts that client instance on React Context so every useQuery/useMutation/useSubscription call anywhere in the tree can reach it without prop drilling. In short: one client instance per app, one cache shared by every component, one provider at the root.

Detailed Answer

The link is Apollo's request pipeline — a chain of middleware that a request passes through before hitting the network and a response passes back through on the way to your component. HttpLink is the terminal link that actually makes the request; you commonly compose it with an authLink (attach a bearer token to headers) and an errorLink (centralized logging or retry-on-401) using ApolloLink.from([...]). This composability is a big part of why Apollo is heavier than a bare fetch wrapper — you get auth, retries, and error handling as first-class, testable pieces of the pipeline rather than scattered try/catch blocks.

The InMemoryCache is the other half, and it's not optional plumbing — it's the core value proposition (see Q5). You typically configure typePolicies here to tell Apollo how to identify and merge specific types, which matters the moment you have pagination or custom-keyed entities.

A subtlety worth naming: because the client is a single shared instance behind Context, all components reading the "same" query field are reading the same normalized cache entry — update it in one place (a mutation, a subscription push) and every subscribed component re-renders with the new value automatically. That shared-cache behavior is what most differentiates "using Apollo" from "just calling fetch in a hook."

Code Example

import {
  ApolloClient,
  ApolloProvider,
  InMemoryCache,
  HttpLink,
  ApolloLink,
} from "@apollo/client";
import { setContext } from "@apollo/client/link/context";

const httpLink = new HttpLink({ uri: "https://api.example.com/graphql" });

const authLink = setContext((_, { headers }) => {
  const token = localStorage.getItem("token");
  return {
    headers: {
      ...headers,
      authorization: token ? `Bearer ${token}` : "",
    },
  };
});

export const client = new ApolloClient({
  link: ApolloLink.from([authLink, httpLink]),
  cache: new InMemoryCache({
    typePolicies: {
      Query: {
        fields: {
          posts: { merge: false }, // replace, don't merge, on refetch
        },
      },
    },
  }),
  defaultOptions: {
    watchQuery: { fetchPolicy: "cache-and-network" },
  },
});

// app root
function App() {
  return (
    <ApolloProvider client={client}>
      <Dashboard />
    </ApolloProvider>
  );
}

Interview Favorite

Interviewers like to see that you know Apollo Client is fundamentally "network link + cache," not a data-fetching hook library that happens to also cache. Mentioning link composition (auth, error handling, retries as separate links you chain with ApolloLink.from) signals real production experience versus copy-pasted tutorial setup. The single-shared-instance-via-Context point is also the natural segue into cache normalization (Q5) if the interviewer probes further.

Q4. How do useQuery and useMutation work, and how do you handle their loading and error states?

ROI: ★★★★★ Frequency: Extremely High

Short Answer

useQuery(QUERY, options) fires (and re-fires, on variable changes or cache updates) a query and returns { data, loading, error, refetch, fetchMore }. useMutation(MUTATION) returns a tuple [mutate, { data, loading, error }] — the mutation does not run automatically; you call the returned function, typically from an event handler. Both hooks read from and write to the same shared cache, which is why a mutation's effects can show up in a completely unrelated component's useQuery result without any manual wiring.

Detailed Answer

The three states every component must handle deliberately: loading is true on the very first fetch (and, depending on fetch policy, on refetches too — see the notifyOnNetworkStatusChange option if you want loading to flip true again on refetch); error is a populated ApolloError if the request failed at either the network layer or the GraphQL layer (see Q9 for the distinction); data is undefined until the first successful response lands, then stays populated (even stale) across refetches unless you explicitly clear it. A common bug is rendering data.user.name before checking loading/error first — data can be undefined on the very first render.

useQuery accepts variables (re-runs the query when they change), skip (don't run at all — useful when a required variable isn't ready yet), and pollInterval (cheap "real-time-ish" updates via polling instead of a subscription). useMutation's second tuple element also exposes reset() to clear a stale error/data after a failed attempt, which matters for retry UX.

Because useMutation is imperative (you decide when it fires), it's also where you plug in the cache-update strategies from Q6 — refetchQueries, update, and optimisticResponse are all options passed to useMutation or to the mutate function call itself.

Code Example

import { useQuery, useMutation, gql } from "@apollo/client";

const GET_TODOS = gql`
  query GetTodos {
    todos {
      id
      text
      completed
    }
  }
`;

const TOGGLE_TODO = gql`
  mutation ToggleTodo($id: ID!) {
    toggleTodo(id: $id) {
      id
      completed
    }
  }
`;

function TodoList() {
  const { data, loading, error } = useQuery(GET_TODOS);
  const [toggleTodo, { loading: toggling }] = useMutation(TOGGLE_TODO);

  if (loading) return <Spinner />;
  if (error) return <ErrorBanner message={error.message} />;

  return (
    <ul>
      {data.todos.map((todo) => (
        <li key={todo.id}>
          <input
            type="checkbox"
            checked={todo.completed}
            disabled={toggling}
            onChange={() => toggleTodo({ variables: { id: todo.id } })}
          />
          {todo.text}
        </li>
      ))}
    </ul>
  );
}

Interview Gold Point

The tell of a candidate who has actually shipped Apollo: they mention that data being defined does not mean the query is "done" — after a refetch, loading stays false by default while data is stale, unless notifyOnNetworkStatusChange: true is set. They also know useMutation is opt-in/imperative by design (you don't want a POST firing on render), unlike useQuery, which is declarative and fires on mount/variable-change. That query-vs-mutation execution-model asymmetry is a favorite follow-up.

SECTION 3 - CACHING & DATA MANAGEMENT

Q5. How does Apollo's normalized cache work, and what do the fetch policies (cache-first, network-only, cache-and-network) actually control?

ROI: ★★★★★ Frequency: Extremely High

Short Answer

Apollo's InMemoryCache doesn't store responses keyed by query — it flattens every object into a normalized store keyed by a cache ID (default __typename:id), so the same User:1 entity fetched via three different queries lives in exactly one place. Every query result the client renders is a "view" reconstructed from that normalized store. Fetch policies control the trade-off between that cache and the network for a given query: cache-first (default) serves cache if present and only hits the network on a miss; network-only always hits the network but still writes the result into cache; cache-and-network serves whatever's cached immediately and fires a network request, updating the UI again when it resolves.

Detailed Answer

Normalization is what makes Apollo's cache genuinely powerful rather than just a response-memoization layer. Every object with a __typename and an id (or _id) gets flattened into a single entry, e.g. User:1, and queries store references to those entries rather than duplicating the data. Practical payoff: edit a user's name in one mutation, and every component on screen showing that user — a header avatar, a comment list, a profile card — re-renders with the new name, because they were all pointing at the same normalized entry, not separate copies.

The fetch policies, compared directly:

PolicyBehaviorUse when
cache-first (default)Return cache if it exists; only fetch on a cache missData that rarely changes; minimizing requests matters
cache-onlyNever hit the network; error if not cachedReading purely local/derived cache data
network-onlyAlways fetch, but still write the result to cacheData that must be fresh on this read (e.g. after navigating to a page that must reflect the latest state)
no-cacheAlways fetch; result is not written to cache at allOne-off reads you deliberately don't want polluting the shared cache
cache-and-networkReturn cache immediately (if any) AND fetch; UI updates twiceInstant paint from stale data, then reconcile with fresh data — the common "feels fast but stays correct" default

The classic interview trap is confusing network-only with no-cache: both always go to the network, but only no-cache skips writing the response into the store afterward. Get this backwards and you'll misdiagnose a "why isn't my cache updating" bug as a fetch-policy problem when it's actually a normalization/key problem (see Q6's follow-up on custom cache keys).

Common Mistake

Saying "Apollo caches by query" instead of "Apollo caches by normalized entity, and queries are views over that store" is the single most common gap. It matters practically: if you don't understand normalization, cache updates after a mutation (Q6) look like magic or like a bug, when they're really just "the entity changed, so every reference to it re-renders." Also be ready to name the difference between network-only and no-cache precisely — interviewers use it to filter out memorized-but-shallow answers.

Q6. How do you update the cache after a mutation — refetchQueries, the update function, and optimistic response?

ROI: ★★★★★ Frequency: Extremely High

Short Answer

Three mechanisms, in increasing order of manual effort and UX payoff: automatic normalization handles it for free when the mutation returns a field with the same cache ID as something already cached (edit-in-place cases). refetchQueries tells Apollo to re-run specific named queries after the mutation resolves — simplest, but an extra network round trip. The update function lets you imperatively write into the cache using the mutation's response, with no extra request — required for cases normalization can't handle alone, like adding a new item to a list. optimisticResponse layers a predicted result into the cache immediately (before the server responds), so the UI updates instantly and rolls back automatically if the mutation fails.

Detailed Answer

Why "just refetch everything" isn't the default answer: refetching is simple but expensive — it's a full network round trip for data you often already have enough information to construct locally. It also doesn't compose well: a mutation used in five places would need to know about all five queries to invalidate, tightly coupling components that should be independent.

Automatic cache updates happen for free precisely because of normalization (Q5): if a mutation returns a Post with id: "5" and you already have Post:5 cached, Apollo merges the returned fields straight into that entry — no update function needed. This covers most "edit an existing thing" mutations automatically.

Where automatic merging breaks down is adding or removing items from a list — a new Post has no existing cache entry to merge into, and no query result "knows" it should now include this new item. That's exactly what the update function is for: it hands you a proxy into the cache (cache.readQuery / cache.writeQuery, or the terser cache.modify) so you can manually splice the new item into the relevant list's cached result.

optimisticResponse is a UX technique layered on top of either approach: you supply a best-guess response shaped exactly like the real one (including a temporary client-generated ID prefixed with client: convention) and Apollo applies it to the cache — and re-renders the UI — immediately, before the network call resolves. When the real response arrives, Apollo reconciles (replaces the optimistic layer); if the mutation errors, Apollo automatically rolls the optimistic change back. This is how "instant" like buttons and toggle switches are built without actually waiting on the network.

Code Example

const ADD_TODO = gql`
  mutation AddTodo($text: String!) {
    addTodo(text: $text) {
      id
      text
      completed
    }
  }
`;

const GET_TODOS = gql`
  query GetTodos {
    todos {
      id
      text
      completed
    }
  }
`;

function AddTodoForm() {
  const [addTodo] = useMutation(ADD_TODO, {
    // Manually splice the new todo into the cached list — normalization
    // alone can't do this because the item didn't exist before.
    update(cache, { data: { addTodo } }) {
      const existing = cache.readQuery({ query: GET_TODOS });
      cache.writeQuery({
        query: GET_TODOS,
        data: { todos: [...existing.todos, addTodo] },
      });
    },
    // Instant UI feedback; rolled back automatically on failure
    optimisticResponse: (vars) => ({
      addTodo: {
        __typename: "Todo",
        id: `client:${Date.now()}`,
        text: vars.text,
        completed: false,
      },
    }),
  });

  return (
    <button onClick={() => addTodo({ variables: { text: "Ship the demo" } })}>
      Add
    </button>
  );
}

// The simpler, cheaper-to-write, more-network-costly alternative:
const [addTodo] = useMutation(ADD_TODO, {
  refetchQueries: [{ query: GET_TODOS }],
  awaitRefetchQueries: true,
});

Interview Gold Point

The layered answer wins: start with "normalization updates in-place edits for free," then "for adding/removing list items you need update," then "refetchQueries is the simple-but-costly escape hatch," then "optimisticResponse is orthogonal — it's about perceived latency, and it composes with either of the above." Naming the client:-prefixed temporary ID convention for optimistic inserts, and knowing Apollo auto-rolls-back a failed optimistic update, are the details that separate "read the docs once" from "debugged this in production."

Q7. How does pagination work in GraphQL — cursor-based (Relay-style) vs offset-based?

ROI: ★★★★☆ Frequency: High

Short Answer

Offset-based pagination passes a numeric offset/page and limit, mirroring classic SQL LIMIT/OFFSET — simple, but unstable if items are inserted or deleted between pages (items shift, causing skips or duplicates), and it gets slower on large offsets. Cursor-based pagination (formalized by the Relay connection spec) passes an opaque cursor (typically an encoded pointer to "the last item you saw") plus a count, and returns items after that cursor along with a pageInfo object (hasNextPage, endCursor) — stable under concurrent inserts/deletes, and the standard choice for infinite-scroll feeds. On the Apollo Client side, both are driven through fetchMore, but cursor-based pagination is what the ecosystem (and most interviewers) mean by "how do you paginate in GraphQL."

Detailed Answer

The Relay connection spec standardizes the shape: a field returns an edges array of { node, cursor } plus a pageInfo: { hasNextPage, hasPreviousPage, startCursor, endCursor }. Clients ask for the next page with first: N, after: $endCursor. Because the cursor identifies a specific item rather than a position, inserting a new item at the top of the list doesn't shift what "page 2" means — you're always asking for "everything after this specific item," which is what makes it stable for live-updating feeds.

On the Apollo Client side, fetchMore issues the next-page query and, via its updateQuery (legacy) or a cache merge field policy (current, preferred), appends the new edges to the existing list in the normalized cache. Configuring a merge function in typePolicies is the modern approach — it means every component reading that field, anywhere, sees the concatenated list automatically, rather than each call site having to hand-merge results.

Offset pagination is still reasonable for admin tables and anything with a fixed page-jump UI ("go to page 7") where cursor semantics ("go to page 7" has no natural cursor meaning) don't fit — the choice is genuinely use-case-dependent, not "cursor is always correct."

Code Example

const GET_POSTS = gql`
  query GetPosts($after: String) {
    posts(first: 10, after: $after) {
      edges {
        cursor
        node { id title }
      }
      pageInfo {
        hasNextPage
        endCursor
      }
    }
  }
`;

function PostFeed() {
  const { data, fetchMore } = useQuery(GET_POSTS);

  const loadMore = () =>
    fetchMore({
      variables: { after: data.posts.pageInfo.endCursor },
      // With a typePolicy merge function configured, Apollo appends
      // automatically — updateQuery below is the manual fallback.
      updateQuery: (prev, { fetchMoreResult }) => ({
        posts: {
          ...fetchMoreResult.posts,
          edges: [...prev.posts.edges, ...fetchMoreResult.posts.edges],
        },
      }),
    });

  return (
    <>
      {data?.posts.edges.map(({ node }) => <PostRow key={node.id} post={node} />)}
      {data?.posts.pageInfo.hasNextPage && (
        <button onClick={loadMore}>Load more</button>
      )}
    </>
  );
}

// typePolicy that merges pages automatically, so callers never
// hand-splice edges themselves
const cache = new InMemoryCache({
  typePolicies: {
    Query: {
      fields: {
        posts: {
          keyArgs: false,
          merge(existing, incoming) {
            return {
              ...incoming,
              edges: [...(existing?.edges ?? []), ...incoming.edges],
            };
          },
        },
      },
    },
  },
});

Interview Favorite

The concrete failure case sells this answer: with offset pagination, if a new item is inserted at the top while a user is scrolling, page 2's offset now points one item too early, either duplicating an item or skipping one entirely — cursor pagination sidesteps this because the cursor is anchored to an item, not a position. Bring up the merge field-policy pattern unprompted; it shows you've paginated in Apollo beyond the tutorial's manual updateQuery approach.

Q8. What are fragments, and how do they help with query reuse?

ROI: ★★★☆☆ Frequency: Medium

Short Answer

A fragment is a named, reusable selection set on a given type (fragment UserFields on User { id name avatarUrl }) that you can splice into any query needing those fields with ...UserFields. The payoff is colocation: a component can declare its own data requirements as a fragment sitting right next to its code, and a parent query just spreads that fragment in — so when the component changes what data it needs, the change lives in one file instead of requiring you to hunt down every parent query that duplicated those fields by hand.

Detailed Answer

Without fragments, every screen that renders a "user card" has to independently list the exact same five fields in its query, and if the card component later needs a new field, someone has to remember to update every query that feeds it — a classic drift bug. With fragments, the UserCard component exports UserCard.fragments.user, the parent query spreads it in, and adding a field to the fragment automatically flows to every parent that spreads it.

Fragments also interact with normalization (Q5): because a fragment's fields are attached to a specific normalized entity, using the same fragment consistently across queries means Apollo recognizes it's the "same" User:1 data shape being requested, which keeps cache reads/writes consistent instead of accidentally creating partial or conflicting entries for the same entity.

Two caveats interviewers may probe: fragments must be defined on a specific GraphQL type (or an interface/union, which introduces the need for ... on ConcreteType inline fragments to select type-specific fields), and over-using fragments for one-off queries just adds indirection — they earn their keep when a shape is genuinely reused across multiple queries or components.

Code Example

// UserCard.tsx — the fragment lives next to the component that needs it
import { gql } from "@apollo/client";

export const USER_CARD_FRAGMENT = gql`
  fragment UserCardFields on User {
    id
    name
    avatarUrl
  }
`;

function UserCard({ user }) {
  return (
    <div>
      <img src={user.avatarUrl} />
      <span>{user.name}</span>
    </div>
  );
}

// Dashboard.tsx — the parent spreads the fragment instead of
// re-listing name/avatarUrl by hand
const GET_DASHBOARD = gql`
  query GetDashboard {
    currentUser {
      ...UserCardFields
      notifications { id }
    }
  }
  ${USER_CARD_FRAGMENT}
`;

Common Mistake

A weak answer describes fragments as "just a way to avoid retyping fields." The stronger framing is colocation as an architectural pattern — the component owns its data requirements, the same way it owns its props and styles, which is the same instinct behind GraphQL Code Generator setups and Relay's compiler. Mention the interface/union inline-fragment case (... on Admin { permissions }) if the interviewer pushes into polymorphic schema design.

SECTION 4 - ERRORS, REAL-TIME & PERFORMANCE

Q9. How do you handle errors in GraphQL — and what's the difference between GraphQL errors and network errors?

ROI: ★★★★☆ Frequency: High

Short Answer

GraphQL has two structurally different failure modes, and Apollo's ApolloError distinguishes them. A network error means the HTTP request itself failed (timeout, DNS, 500, CORS) — no GraphQL response body was even produced. A GraphQL error means the HTTP request succeeded (typically still a 200) but one or more fields failed to resolve server-side, and the response contains both a partial data object and a populated errors array describing what went wrong and where. Apollo exposes both on error.networkError and error.graphQLErrors respectively, and you generally need to check both to build a correct error UI.

Detailed Answer

This dual-error model is one of GraphQL's most interview-tested quirks precisely because it violates the REST intuition that a 200 means success. A single query can partially succeed: it might fetch a user's name fine while the nested posts resolver throws (a permissions error, an upstream service outage) — the response comes back 200 with data.user.name populated, data.user.posts: null, and an errors array entry pointing at the posts path. A UI that only checks error before rendering can miss this: error is populated whenever either array is non-empty, but the correct handling (show the user's name, show a small inline error for the posts section) requires reading which specific field failed.

Q10. How do GraphQL subscriptions work, and how do you use them for real-time data with Apollo?

ROI: ★★★☆☆ Frequency: Medium

Short Answer

A subscription is a long-lived operation, typically over a WebSocket, where the client says "notify me every time X happens" and the server pushes a new payload each time that event fires — the inverse of the request/response model queries and mutations use. In Apollo Client, useSubscription(SUBSCRIPTION) opens the connection on mount and returns { data, loading, error } that update on every push, and the transport is configured via a separate GraphQLWsLink (using the graphql-ws library) split from your regular HttpLink using Apollo's split link based on operation type.

Detailed Answer

Wiring subscriptions in requires a second transport, because HTTP can't hold a connection open for server-initiated pushes. Apollo's split function inspects each outgoing operation and routes subscriptions to a WebSocket link while queries/mutations continue over the normal HTTP link — this is boilerplate every Apollo-plus-subscriptions setup needs, and forgetting it is the most common "why doesn't my subscription connect" bug.

In practice, subscriptions are used less often than you'd expect for "real-time" features, for a few honest reasons: they require infrastructure the REST/HTTP-only backend doesn't already have (a persistent WebSocket server, connection-count scaling concerns), and for many "real-time-ish" needs, pollInterval on a regular query is simpler and good enough (a dashboard that refreshes every 10 seconds doesn't need a live socket). Subscriptions earn their cost for genuinely event-driven UX — live chat, live cursors, a live order-status tracker — where the latency of polling would be unacceptable.

A common pattern is combining subscriptions with the cache-update techniques from Q6: a useSubscription callback (onData) writes the pushed item into the cache (e.g. appending a new chat message to an existing query result) rather than replacing an entire query, so the subscription behaves like a targeted, continuous mutation.

Code Example

import { GraphQLWsLink } from "@apollo/client/link/subscriptions";
import { createClient } from "graphql-ws";
import { split, HttpLink } from "@apollo/client";
import { getMainDefinition } from "@apollo/client/utilities";

const wsLink = new GraphQLWsLink(
  createClient({ url: "wss://api.example.com/graphql" })
);
const httpLink = new HttpLink({ uri: "https://api.example.com/graphql" });

// Route subscriptions over WS, everything else over HTTP
const splitLink = split(
  ({ query }) => {
    const def = getMainDefinition(query);
    return def.kind === "OperationDefinition" && def.operation === "subscription";
  },
  wsLink,
  httpLink
);

const client = new ApolloClient({ link: splitLink, cache: new InMemoryCache() });

// Component usage
const NEW_MESSAGE = gql`
  subscription OnNewMessage($chatId: ID!) {
    messageAdded(chatId: $chatId) { id text sender }
  }
`;

function ChatWindow({ chatId }) {
  const { data } = useSubscription(NEW_MESSAGE, {
    variables: { chatId },
    onData: ({ client, data }) => {
      // Append the pushed message into the existing query's cache result
      client.cache.updateQuery({ query: GET_MESSAGES, variables: { chatId } }, (prev) => ({
        messages: [...prev.messages, data.data.messageAdded],
      }));
    },
  });

  return null; // rendering driven by the GET_MESSAGES query elsewhere
}

Interview Favorite

Interviewers reward the honest scoping answer: know how to wire subscriptions (the split-link pattern is the concrete detail to name), but also know when not to reach for them — pollInterval or a simple refetch-on-focus often covers "keep this reasonably fresh" without the infrastructure cost of a persistent WebSocket layer. That judgment call is what separates "knows the API" from "knows when to use it."

Q11. What is the N+1 problem and DataLoader — and why should a client-side engineer even know about it?

ROI: ★★★★☆ Frequency: High

Short Answer

The N+1 problem is a server-side resolver performance bug: if a query fetches a list of N posts and each post's resolver independently fetches its author, naive resolver code issues 1 query for the posts plus N more queries (one per post) for authors — N+1 round trips to the database for data that could have been fetched in 2. DataLoader fixes this by batching and caching those per-request lookups so all N author-fetches inside one tick get coalesced into a single batched query. It's implemented server-side, but frontend engineers are asked about it constantly because GraphQL's client-declared, arbitrarily nested query shape is exactly what makes N+1 easy to trigger — the client's query structure directly causes or avoids the problem.

Detailed Answer

This is a "client engineers get asked server concepts" question, and the reason is legitimate: in REST, the backend team controls exactly what a given endpoint fetches, so N+1 is entirely their problem to notice. In GraphQL, the client writes the query shape — a client that nests three levels deep (users { posts { comments { author } } } ) is effectively choosing the resolver call pattern the server has to execute. A frontend engineer who understands N+1 writes flatter, more deliberate queries and knows to flag "why is this query taking 4 seconds" as likely an N+1 issue on the backend, rather than a frontend bug to chase.

DataLoader (originally from Facebook, same lineage as GraphQL itself) solves it with two techniques: batching — within a single tick of the event loop, all individual .load(id) calls are collected and sent to the underlying data source as one batched call (batchGetUsers([1, 2, 3]) instead of three separate calls) — and caching — within one request's lifetime, loading the same ID twice returns the cached promise instead of hitting the data source again. Both are scoped per-request (a fresh DataLoader instance per incoming GraphQL request) specifically so caching doesn't leak stale data across different users' requests.

For an interview, the useful framing is: "I don't write DataLoader, but I understand it exists because my query shape as a client author is what triggers or avoids N+1 resolver fan-out, and if I see suspiciously slow nested-list queries, DataLoader/batching on the backend is the first thing I'd ask about."

Code Example

// Server-side resolver WITHOUT DataLoader — N+1 triggered by a
// client query that nests posts -> author
const resolvers = {
  Post: {
    author: (post) => db.users.findById(post.authorId), // one DB call per post
  },
};

// WITH DataLoader — same client query, batched into one call
const userLoader = new DataLoader(async (ids) => {
  const users = await db.users.findByIds(ids); // one batched call for all ids
  return ids.map((id) => users.find((u) => u.id === id));
});

const resolvers = {
  Post: {
    author: (post) => userLoader.load(post.authorId), // batched + per-request cached
  },
};

# The client query that would trigger N+1 without batching —
# note the client controls this shape, not the server
query {
  posts(limit: 50) {
    title
    author { name }   # 50 posts -> 50 individual author lookups without DataLoader
  }
}

Common Mistake

Don't claim ownership you don't have — DataLoader is implemented in resolver code, which is usually a backend concern. The mistake to avoid is either blanking entirely ("that's not my layer") or overclaiming implementation details you haven't touched. The right answer demonstrates awareness of the mechanism and, critically, connects it back to something a frontend engineer does control: the shape and depth of the queries they write.

Q12. Apollo Client vs urql vs React Query for GraphQL — when should you choose which?

ROI: ★★★★☆ Frequency: High

Short Answer

Apollo Client is the full-featured, batteries-included option: a normalized cache, first-class subscriptions, a large ecosystem, and deep devtools — at the cost of bundle size and a learning curve around cache configuration. urql targets a similar problem with a smaller footprint and a more explicit, exchange-based (middleware) architecture; its default "document cache" is simpler than Apollo's normalized cache (though a normalized-cache addon, @urql/exchange-graphcache, closes that gap). React Query isn't GraphQL-specific at all — it's a generic async-state manager, so "using it for GraphQL" means you fire your own fetch/graphql-request call inside a useQuery, getting React Query's caching-by-query-key, retries, and stale-time model, but none of GraphQL-aware normalization out of the box.

Detailed Answer

The decision is really about how much you value GraphQL-specific cache normalization versus bundle size and mental model simplicity. If your app already thinks in Apollo's terms (heavy list pagination, real-time subscriptions, deeply relational data with entities appearing in many queries), Apollo's normalized cache pays for its complexity by keeping that data automatically consistent everywhere. If you want GraphQL's query language but a lighter runtime and don't need Apollo's full feature surface, urql is the well-supported middle ground. If your team already standardized on React Query for REST and is adding a handful of GraphQL calls, reusing React Query (with a thin graphql-request client) avoids introducing a second data-fetching paradigm — at the cost of losing automatic entity-level cache updates; you fall back to manual queryClient.invalidateQueries or setQueryData calls, much like the refetchQueries/update pattern in Apollo but without normalization backing it.

Q13. How do you test components that use Apollo Client, using MockedProvider?

ROI: ★★★★☆ Frequency: High

Short Answer

MockedProvider (from @apollo/client/testing) replaces the real ApolloProvider in tests with a client wired to a list of mocks — each mock declares an exact request (query + variables) and the result (or error) Apollo should return when a component fires that exact request. If a component fires a request that doesn't match any mock, the test fails loudly rather than silently hitting a real network — which is exactly the "mock at the boundary, run the real component code" philosophy applied to GraphQL.

Detailed Answer

The matching is strict by default: query document and variables must match exactly, which is a double-edged feature — it catches "the component sent the wrong variables" bugs, but it also means tests break if you reorder fields or the component's query changes even trivially. This is functionally the same trade-off as MSW for REST (see the Testing chapter): you're mocking the transport boundary, not the component's internals, so the component's actual query-building, loading/error rendering, and data-mapping logic all run for real.

A few practical patterns: use addTypename: false only if you're deliberately testing without the normalized cache typename injection (rare); prefer asserting on rendered output (screen.findByText(...)) after awaiting the mock resolves, exactly like async RTL patterns elsewhere; and test the error path by supplying error: new Error(...) on a mock instead of result, to verify your component's error UI without needing a real failing server.

For mutations, remember the mock's request.variables must match what the mutation is actually called with at runtime — a common flaky-test cause is a mock written before the component's mutation call was finalized, so the variables silently drift out of sync and the "no matching mock" error appears with a diff that's easy to misread as a rendering bug rather than a request-shape mismatch.

Code Example

import { render, screen } from "@testing-library/react";
import { MockedProvider } from "@apollo/client/testing";
import { GET_USER } from "./queries";
import UserProfile from "./UserProfile";

const happyMock = {
  request: { query: GET_USER, variables: { id: "1" } },
  result: {
    data: { user: { id: "1", name: "Ada Lovelace" } },
  },
};

const errorMock = {
  request: { query: GET_USER, variables: { id: "1" } },
  error: new Error("Network down"),
};

test("renders the loaded user", async () => {
  render(
    <MockedProvider mocks={[happyMock]} addTypename={false}>
      <UserProfile id="1" />
    </MockedProvider>
  );

  expect(await screen.findByText("Ada Lovelace")).toBeInTheDocument();
});

test("renders an error state on failure", async () => {
  render(
    <MockedProvider mocks={[errorMock]} addTypename={false}>
      <UserProfile id="1" />
    </MockedProvider>
  );

  expect(await screen.findByText(/something went wrong/i)).toBeInTheDocument();
});

Interview Gold Point

Frame MockedProvider the same way you'd frame MSW: "mock the network boundary, exercise the real component code." The specific detail interviewers listen for is the exact-match requirement on query + variables, and the debugging instinct that follows from it — an "unmatched mock" test failure is usually a request-shape drift bug, not a rendering bug, and knowing that saves real debugging time.

Q14. What are the common interview pitfalls around GraphQL — including how it can still be over-fetched, and typical schema design mistakes?

ROI: ★★★★★ Frequency: Extremely High

Short Answer

The biggest trap is treating "we use GraphQL" as automatic proof of efficient data fetching — GraphQL only prevents over-fetching if the query author is disciplined. A component that requests every field "just in case," or a page that spreads three unrelated fragments it doesn't fully use, is just as over-fetched as a bloated REST response — the mechanism moved from the server to the client, but the discipline problem didn't disappear. Beyond that, the recurring schema-design mistakes interviewers probe are: over-nesting types that force N+1-prone resolvers (Q11), getting nullability backwards (marking fragile fields non-null, so one failure nulls out a whole subtree — Q2), and designing mutations that don't return enough of the changed object for the client to update its cache without a manual refetch (Q6).

Detailed Answer

"GraphQL can still be over-fetched" is worth stating explicitly and unprompted, because it's the follow-up interviewers use to separate marketing-level knowledge from real experience. Common ways it happens in practice: a shared fragment grows over time as different components add fields to it, and eventually every consumer of that fragment pulls fields only one of them actually uses; a query is copy-pasted from a similar screen and never trimmed; or a component over-fetches "for the cache" (requesting fields so they're pre-warmed elsewhere), which quietly reintroduces the exact waste GraphQL was adopted to eliminate. The fix is the same discipline REST needed — audit what a component actually renders, keep fragments scoped to real reuse, and treat query size as a code-review concern, not a solved problem.

Schema design mistakes that come up repeatedly:

  • Wrong nullability defaults — marking fields non-null "for convenience" when the underlying resolver can genuinely fail; one flaky field then nulls out an entire parent object at runtime (Q2).
  • Deeply nested relational fields with no batching story — a schema that lets clients traverse three or four levels deep without the team having DataLoader/batching in place invites N+1 performance cliffs the moment a real client query exercises that depth (Q11).
  • Mutations that under-return — a mutation that only returns { success: true } instead of the created/updated object forces every caller into an extra refetchQueries round trip that a well-designed mutation payload would have avoided (Q6).
  • Leaking a "God query" root — a single enormous Query type with dozens of loosely related top-level fields, mirroring the REST "endpoint sprawl" problem GraphQL was meant to fix, just moved into schema fields instead of URLs.
  • No pagination story on list fields — a posts: [Post!]! field with no way to limit or page through results is a footgun the moment the list grows past a few hundred rows (Q7).

The meta-point worth landing in an interview: GraphQL moves several decisions (what data to fetch, how deep to nest, how to paginate) from the backend team to whoever writes each query — which is powerful, but it also moves the responsibility for avoiding waste and performance cliffs to that same person. A senior answer treats GraphQL as a tool that requires ongoing query and schema discipline, not a technology that solved data-fetching by being adopted.

Interview Favorite

Volunteering "GraphQL doesn't eliminate over-fetching, it just moves the responsibility for avoiding it to the query author" — without being asked — is one of the highest-signal single sentences you can say in this entire chapter. Pair it with one concrete schema-design mistake (nullability defaults or under-returning mutations are the two most commonly probed) to show the awareness goes beyond the client and into how you'd review a schema PR.

SECTION 6 - APOLLO CLIENT CACHE DEEP DIVE

Q15. What is a cache identifier (cache key), how does Apollo compute it by default, and what happens for types that don't have an id field?

ROI: ★★★★★ Frequency: Extremely High

Short Answer

Every normalized entity in Apollo's InMemoryCache is stored under a string key called a cache identifier, built by default as __typename:id (or __typename:_id) — e.g. User:42. Apollo derives this automatically as long as the query selects __typename (added transparently unless you disable it) and either id or _id. Types with no id/_id field, or types where the id isn't globally unique on its own, don't get a stable cache identifier by default — Apollo falls back to storing them embedded inside their parent object rather than as a separate normalized entity, which means updates to that nested object only apply wherever that exact parent happened to fetch it.

Detailed Answer

Normalization only works if Apollo can answer "is this the same real-world object I've seen before?" — that's exactly what the cache identifier encodes. For the common case (a User type with a globally unique id), User:42 is unambiguous. Problems show up in two recurring shapes: first, a type that has an id field but the id is only unique within its parent (e.g. a line-item's id that's really just its index inside one order) — two different orders' line item 1 would collide onto the same cache key and silently overwrite each other's data. Second, a genuinely id-less value type (an Address embedded in a User) has nothing to normalize on, so Apollo stores it inline as part of the parent's cache entry — which is usually the correct behavior for a value type, since an address isn't an entity with its own identity shared across other objects.

You fix the colliding-id case with a custom keyFields type policy that composes a truly unique key (e.g. ["orderId", "id"]), and you fix "I want this normalized but it has no id" by supplying a custom keyFields function that derives a key from whatever uniquely identifies it in context. Getting this wrong is one of the most common causes of "data from one record is bleeding into another" bugs in production Apollo apps — and it's a normalization/key problem, not a fetch-policy problem, which is exactly the kind of distinction interviewers use to separate surface familiarity from real debugging experience.

Code Example

const cache = new InMemoryCache({
  typePolicies: {
    LineItem: {
      // id alone collides across orders — compose a truly unique key
      keyFields: ["orderId", "id"],
    },
    Address: {
      // no natural id at all; embed rather than normalize (the default
      // for id-less types) OR give it a synthetic composite key if you
      // genuinely need to share/normalize address entities
      keyFields: false, // explicit: never normalize, always embed inline
    },
  },
});

// cache.identify() shows you exactly what key Apollo computed
cache.identify({ __typename: "User", id: "42" }); // -> "User:42"
cache.identify({ __typename: "LineItem", orderId: "9", id: "1" }); // -> "LineItem:{"orderId":"9","id":"1"}"

Senior Engineer Perspective

Name the failure mode concretely: "data bleeding between records" in an Apollo app is very often a keyFields collision, not a bug in the component. Knowing to reach for cache.identify() to inspect the actual computed key during debugging — rather than guessing — is a strong, specific signal of hands-on production experience with the normalized cache.

Q16. How do cache.readQuery and cache.writeQuery differ from cache.readFragment and cache.writeFragment?

ROI: ★★★★☆ Frequency: High

Short Answer

readQuery/writeQuery operate at the level of a whole named query (or a query document you construct ad hoc) — you're reading or writing "the result shape as if this query had been executed." readFragment/writeFragment operate directly on a single normalized entity by its cache identifier, independent of any specific query that fetched it. In practice, writeFragment is the more surgical, more reusable tool: you can update User:42's name field once, and every query anywhere that includes that user reflects the change — without needing to know or reconstruct any of those queries' full shapes.

Detailed Answer

writeQuery requires you to supply data matching the entire query's shape, which is awkward when you only want to touch one field deep inside a large result — you either have to readQuery first and spread most of it back unchanged, or risk writing an incomplete shape that corrupts the cached result for that query. writeFragment sidesteps this: you address the entity directly (cache.writeFragment({ id: cache.identify({ __typename: "User", id: "42" }), fragment: USER_NAME_FRAGMENT, data: { __typename: "User", id: "42", name: "New Name" } })), and because normalization means every query referencing that entity is really just holding a reference to it, the update propagates everywhere automatically — no need to touch the queries at all.

The practical rule of thumb: reach for writeQuery when you're dealing with the root Query shape itself (adding an item to a list under Query.todos, since lists aren't individually addressable entities) and reach for writeFragment/modify when you're updating fields on an entity that already has a cache identity. Q17 covers cache.modify, which is often the terser choice for both cases when you don't want to read-then-write manually.

Code Example

const USER_NAME_FRAGMENT = gql`
  fragment UserName on User {
    id
    name
  }
`;

// Update a single entity's field, wherever it's referenced
cache.writeFragment({
  id: cache.identify({ __typename: "User", id: "42" }),
  fragment: USER_NAME_FRAGMENT,
  data: { __typename: "User", id: "42", name: "Ada Lovelace" },
});

// Read it back directly, without needing the original query at all
const partial = cache.readFragment({
  id: cache.identify({ __typename: "User", id: "42" }),
  fragment: USER_NAME_FRAGMENT,
});

Interview Gold Point

The line that lands well: "writeQuery couples my update to a specific query's shape; writeFragment/modify couple it to the entity itself, which is what I actually want to change." That framing shows you understand normalization isn't just an implementation detail — it changes which cache API is the right tool for a given update.

Q17. How does cache.modify work, and when would you prefer it over writeQuery/writeFragment?

ROI: ★★★★★ Frequency: Extremely High

Short Answer

cache.modify lets you update one or more fields on a specific cache entity by supplying small functions that receive the field's current value and return its new value — no need to read the whole entity or reconstruct a fragment/query shape first. It's the most surgical, most commonly reached-for tool for mutation update functions in real codebases, especially for incrementing counters, toggling booleans, or splicing an item into a cached list by reference (toReference), all without an extra network round trip.

Detailed Answer

Where writeFragment requires you to compute and hand over the full new value, modify's field functions receive the existing cached value and a set of helpers (readField, toReference, DELETE sentinel, INVALIDATE sentinel) so you can express the update as a transformation: "likeCount + 1," "remove the item whose id matches this," "replace this reference." This is usually less code and less error-prone than reading, spreading, and rewriting an entire object.

A very common production pattern: after a "delete post" mutation, use cache.modify on the parent Query field to filter the deleted post's reference out of the cached list, returning the DELETE sentinel to also remove the now-orphaned Post:5 entity itself so it doesn't linger in the cache unreferenced. This combination — modifying the list field and deleting the orphaned entity — is the idiomatic way to handle deletions cleanly, versus a heavier full refetchQueries call.

Code Example

const [likePost] = useMutation(LIKE_POST, {
  update(cache, { data }) {
    cache.modify({
      id: cache.identify({ __typename: "Post", id: data.likePost.id }),
      fields: {
        likeCount(existing) {
          return existing + 1;
        },
      },
    });
  },
});

const [deletePost] = useMutation(DELETE_POST, {
  update(cache, { data }, { variables }) {
    // Remove the reference from the cached list
    cache.modify({
      fields: {
        posts(existingRefs = [], { readField }) {
          return existingRefs.filter(
            (ref) => readField("id", ref) !== variables.id
          );
        },
      },
    });
    // Evict the now-orphaned entity entirely
    cache.evict({ id: cache.identify({ __typename: "Post", id: variables.id }) });
    cache.gc();
  },
});

Interview Favorite

Pairing cache.modify for list-field filtering with an explicit cache.evict + cache.gc() call for the deleted entity itself is the detail that signals real depth — a lot of candidates only remove the reference and leave the orphaned entity sitting in the cache indefinitely, which is a subtle but real memory-and-correctness issue in long-lived SPA sessions.

Q18. How does Apollo garbage-collect the cache, and what's the role of cache.gc() and cache.evict()?

ROI: ★★★★☆ Frequency: High

Short Answer

cache.evict({ id }) removes a specific normalized entity (or one field on it) from the cache. It does not, by itself, remove entities that entity referenced — those become "dangling" but are only actually swept away when you call cache.gc(), which walks from every entity still reachable from an active query/watch and deletes anything no longer reachable, returning the list of evicted cache IDs. In short: evict marks something for removal, gc is the mark-and-sweep pass that reclaims anything that's now orphaned.

Detailed Answer

Apollo's cache doesn't automatically shrink as components unmount — data a component fetched stays cached indefinitely by default, which is usually the right trade-off (revisiting a screen should feel instant from cache) but can become a real memory concern in a long-running SPA with lots of transient, rarely-revisited data (e.g. a search-results cache that accumulates thousands of stale entities over a session). cache.gc() is the tool for that: it's a full mark-and-sweep over the entire cache, rooted at every entity reachable from currently active watchQuery subscriptions, so anything not reachable from an active query gets swept.

A practical caveat: gc() only removes entities unreachable from active watchers — if a component that reads a piece of data has already unmounted (so nothing is watching that query anymore), its data becomes eligible for collection; if it's still mounted, referenced data survives even if you'd prefer to force-evict it (which is exactly why targeted cache.evict() calls exist for cases where you want a specific piece of data gone regardless of what's watching it — e.g. purging a logged-out user's data on logout via cache.evict({ id: "ROOT_QUERY" }); cache.gc(); or the simpler client.clearStore() for a full wipe).

Code Example

// Full wipe on logout — clears the store and refetches active queries with new auth
await client.clearStore();

// Targeted: evict one entity's data, then reclaim anything it
// was the only thing keeping alive
cache.evict({ id: cache.identify({ __typename: "Post", id: "5" }) });
const removedIds = cache.gc();
console.log(removedIds); // e.g. ["Post:5", "Comment:12", "Comment:13"]

Common Mistake

A common misconception is that unmounting a component frees its cached data immediately — it doesn't. The cache is intentionally decoupled from component lifecycle so revisiting a screen is instant; explicit cleanup (evict + gc, or clearStore on logout) is something you opt into deliberately, not something that happens for free when a component goes away.

Q19. What are typePolicies and keyFields used for, and how do you handle entities that don't have a standard id field?

ROI: ★★★★☆ Frequency: High

Short Answer

typePolicies is where you teach the InMemoryCache anything it can't infer on its own about a specific GraphQL type: how to compute its cache key (keyFields), how to merge incoming field values with existing ones (merge/fields..merge), and how to read/compute derived field values (read). For types without a standard id/_id, a custom keyFields array or function tells Apollo which combination of fields uniquely identifies an instance so it can still be normalized instead of falling back to inline embedding.

Detailed Answer

Three common keyFields shapes cover most real cases: an array of field names composes a compound key (keyFields: ["tenantId", "sku"] for a product that's only unique within a tenant); a function lets you derive a key from nested or computed data (keyFields: (obj) => obj.slug ?? obj.id); and keyFields: false explicitly opts a type out of normalization entirely, forcing it to always be embedded inline in its parent — the right call for genuine value types (money amounts, addresses, coordinates) that don't have independent identity.

The merge option (seen in the pagination typePolicy in Q7) solves a different problem: by default, Apollo replaces a field's old cached value with whatever came back from the latest fetch. For fields where you want to combine old and new (appending paginated edges, merging a partially-updated nested object instead of overwriting it) you supply your own merge(existing, incoming, options) function. Getting merge wrong is a common cause of "my paginated list resets to page 1's data every time I fetch page 2" bugs — the field policy is silently falling back to full replacement instead of concatenation.

Code Example

const cache = new InMemoryCache({
  typePolicies: {
    Product: {
      // Unique only within a tenant — compound key
      keyFields: ["tenantId", "sku"],
    },
    Money: {
      // Value type — never give it independent cache identity
      keyFields: false,
    },
    Article: {
      // Prefer a human-readable slug as the identity when present
      keyFields: (obj) => (obj.slug ? `Article:${obj.slug}` : undefined),
    },
    Query: {
      fields: {
        // Custom merge so incoming pages append instead of replace
        searchResults: {
          keyArgs: ["query"],
          merge(existing = [], incoming) {
            return [...existing, ...incoming];
          },
        },
      },
    },
  },
});

Interview Gold Point

Volunteer the "my list resets on page 2" symptom unprompted — it's the single most common real-world bug traceable directly to a missing or default merge field policy, and naming the symptom-to-cause link demonstrates you've actually debugged Apollo caching issues rather than just configured a tutorial's typePolicies from memory.

Q20. What's the difference between cache.identify() and manually constructing a cache key string yourself?

ROI: ★★★☆☆ Frequency: Medium

Short Answer

cache.identify(object) runs the object through whatever keyFields policy is configured for its __typename and returns the exact cache ID string Apollo would use internally — it's the canonical, policy-aware way to compute a key. Manually writing `User:${id}` works only as long as no custom keyFields policy is configured for that type; the moment someone adds a compound key or a custom key function, every hand-written string breaks silently (cache reads/writes targeting the old, now-wrong key), while code using cache.identify() keeps working automatically.

Detailed Answer

This is a maintainability argument as much as a correctness one. cache.identify() centralizes the "how do we key this type" decision in one place — the typePolicy — so every call site (mutation update functions, manual cache reads, test helpers) that needs to reference an entity stays correct even as key policies evolve. Hard-coded key strings scattered across a codebase are exactly the kind of hidden coupling that turns "we added a tenant scope to Product's key" into a multi-file hunt for every `Product:${sku}` string that now needs to become `Product:${tenantId}:${sku}` (and even that manual reconstruction wouldn't match Apollo's actual internal serialization format for compound keys, which is JSON-based, not a simple colon-join).

The only place a raw string is unavoidable is when you're intentionally addressing the special ROOT_QUERY or ROOT_MUTATION pseudo-entities (as in the logout-wipe example in Q18) — those aren't derived from an object's fields, so there's nothing for identify() to compute from.

Code Example

// Fragile — breaks the moment Product's keyFields policy changes
const key = `Product:${sku}`;
cache.evict({ id: key });

// Robust — always matches whatever keyFields policy is active
const key = cache.identify({ __typename: "Product", tenantId, sku });
cache.evict({ id: key });

Common Mistake

Hand-rolled cache key strings are a code-smell worth flagging in review even when they happen to work today — they're a latent bug waiting for the next typePolicy change. Standardizing on cache.identify() everywhere a key is needed is a small, low-cost habit that avoids an entire category of "cache update silently stopped working" incidents.

Q21. How does field-level cache normalization handle arguments — what is keyArgs, and why does a paginated or filtered field need it?

ROI: ★★★★☆ Frequency: High

Short Answer

A field called with different arguments (posts(category: "tech") vs posts(category: "sports")) is, semantically, two different result sets — but by default Apollo stores field results keyed only by field name, which would make the second call silently overwrite the first's cached value. keyArgs tells the cache which arguments are part of the field's identity (so different values get separate cache storage slots) and which are "pagination-style" arguments that should be excluded from the key entirely so a merge function can combine successive pages into one growing list under a single storage slot.

Detailed Answer

Concretely: keyArgs: ["category"] means Apollo stores posts results separately per category value — posts({"category":"tech"}) and posts({"category":"sports"}) become two independent cache slots, each independently readable/mergeable, instead of one clobbering the other. For pagination arguments like after/first, you typically want the opposite: all pages of the same underlying list should collapse into one slot so your merge function can concatenate them — which is why the common pagination typePolicy sets keyArgs: false (or omits the paginating args from the key list) alongside a custom merge.

Getting this backwards produces two distinct, easily-confused bugs: forgetting to key on a real filter argument makes switching filters show stale data from the previous filter (because they're overwriting the same slot); and keying on a pagination argument by mistake makes every page look like a separate, unrelated list instead of one continuously growing one. Both are diagnosable by inspecting the raw cache with Apollo DevTools and seeing unexpectedly many (or unexpectedly few) storage slots for one field.

Code Example

const cache = new InMemoryCache({
  typePolicies: {
    Query: {
      fields: {
        posts: {
          // category is part of identity -> separate cache slot per category
          // first/after are pagination args -> excluded from the key
          keyArgs: ["category"],
          merge(existing, incoming, { args }) {
            const merged = existing ? existing.edges.slice(0) : [];
            merged.push(...incoming.edges);
            return { ...incoming, edges: merged };
          },
        },
      },
    },
  },
});

Interview Gold Point

The two-bug framing — "wrong keyArgs either bleeds unrelated filters together, or splits one continuous paginated list into disconnected fragments" — is the kind of precise, symptom-first explanation that shows real debugging mileage rather than recited documentation.

Q22. What issues arise from cache misses and partial cache data, and how does Apollo's "missing field" warning help you catch them?

ROI: ★★★☆☆ Frequency: Medium

Short Answer

A "cache miss" for a cache-first query just triggers a network fetch, which is usually harmless — but a partial cache hit (some fields for an entity are cached, others were never fetched) is subtler: Apollo can construct an incomplete result and, in dev mode, logs a "Missing field" console warning identifying exactly which field couldn't be satisfied from the cache alone. This usually means two different queries touched the same entity with different field selections, and something downstream assumed the entity was "fully loaded" when it was only partially loaded by an earlier, narrower query.

Detailed Answer

A concrete example: a list screen's query selects Post { id title }, populating Post:5 with only those two fields. Later, a detail screen's query for the same post selects Post { id title body author { name } } — the cache has to fetch that from the network (it's genuinely a cache miss for body/author), which is correct and expected behavior. The warning becomes actionable when a query with fetchPolicy: "cache-only" (which by design never hits the network) hits a genuinely missing field — that's a real bug: either the query was fired before the data it depends on was loaded, or a required field was simply never requested by anything that ran before it.

This is one of the concrete payoffs of understanding normalization deeply: instead of treating a "missing field" warning as noise to suppress, a senior engineer traces it to "which query under-selected this entity, and does some other part of the app now assume it's complete" — the same instinct used for the list-reset-to-page-1 bug in Q19 and the collision bug in Q15. All three are the same underlying category: a mismatch between what the cache actually knows and what a specific piece of UI assumes it knows.

Code Example

// Dev console warning example:
// Missing field 'body' while writing result {
//   "id": "5", "title": "Hello World"
// }

// A cache-only read exposing a genuine gap — this is the case worth
// investigating, versus a normal cache-first network fallback
const { data } = useQuery(GET_POST_BODY, {
  variables: { id: "5" },
  fetchPolicy: "cache-only", // will surface partial/missing data instead of fetching
});

Senior Engineer Perspective

Frame partial-data warnings as a diagnostic tool, not noise. The reusable mental model worth stating out loud in an interview: "every 'missing field' or 'stale merge' bug in Apollo traces back to a mismatch between what the normalized cache actually contains and what some component assumes it contains — the fix is almost always in the query shape or the typePolicy, not in the component's rendering logic."

SECTION 7 - FRAGMENT COLOCATION & MASKING

Q23. What is fragment colocation as an architectural pattern, and how does it map to component boundaries?

ROI: ★★★★★ Frequency: Extremely High

Short Answer

Fragment colocation means every component that renders GraphQL data declares its own data requirements as a fragment defined in its own file, right next to the component code — instead of a parent screen hand-listing every field every descendant needs. The parent's top-level query becomes mostly a tree of fragment spreads (...UserCardFields, ...PostRowFields) rather than a flat, manually maintained list of fields, so a component's data dependency lives and evolves in exactly one place: alongside the component itself.

Detailed Answer

Without colocation, a page-level query becomes a shared, ever-growing document that every component quietly depends on — add a field to UserCard, and someone has to remember to add it to every page-level query that renders a UserCard, anywhere in the app. That's the same "action at a distance" problem props drilling and global mutable state cause in component design, just expressed in query shape instead of JS state.

Colocation fixes it the same way component composition fixes prop drilling: the component that needs the data owns the declaration of what it needs. A parent doesn't need to know or care what fields UserCard internally requires — it just spreads UserCard.fragments.user into its query and passes the resulting object through. When UserCard changes what it renders, the fragment file changes, and every parent's query automatically requests the updated shape the next time it runs — no hunting through the codebase for every query that touches users.

The main organizational discipline this requires: components should accept the fragment's shape as their prop type (not a hand-picked subset), and should never reach for a field they didn't declare in their own fragment, even if it happens to be present on the object at runtime because some other component's fragment also touched the same entity. That discipline is exactly what fragment masking (Q24) turns into a compiler/type-level guarantee rather than a code-review convention.

Code Example

// PostRow.tsx
export const POST_ROW_FRAGMENT = gql`
  fragment PostRowFields on Post {
    id
    title
    excerpt
  }
`;
function PostRow({ post }) {
  return <div>{post.title}</div>;
}

// UserCard.tsx
export const USER_CARD_FRAGMENT = gql`
  fragment UserCardFields on User {
    id
    name
    avatarUrl
  }
`;
function UserCard({ user }) {
  return <div>{user.name}</div>;
}

// FeedPage.tsx — mostly fragment spreads, not hand-listed fields
const GET_FEED = gql`
  query GetFeed {
    currentUser { ...UserCardFields }
    posts { ...PostRowFields }
  }
  ${USER_CARD_FRAGMENT}
  ${POST_ROW_FRAGMENT}
`;

Interview Gold Point

Draw the explicit parallel to component composition: "colocated fragments are to query shape what component boundaries are to UI structure — the entity that needs the data owns the declaration of what it needs, and callers just compose those declarations together." That analogy tends to land well because it reframes what sounds like a GraphQL-specific trick as a general software-architecture principle you already apply elsewhere.

Q24. What is fragment masking, and why did Apollo Client add it as a first-class feature?

ROI: ★★★★☆ Frequency: High

Short Answer

Fragment masking restricts a component to only the fields its own fragment selected, even if the actual object at runtime has more fields present because some other fragment or the parent query also fetched them. Without masking, a component can accidentally read a field it never declared (because it happens to exist on the object today), which breaks the entire point of colocation the moment that other fragment is later removed and the field silently disappears — a runtime bug with no compile-time warning. With masking (available via codegen-generated types, or natively with GraphQL Code Generator's client preset / Relay), TypeScript itself refuses to let a component read a field outside its declared fragment.

Detailed Answer

The failure mode masking prevents is genuinely subtle and easy to introduce by accident: UserCard declares a fragment selecting { id name avatarUrl }, but a sibling component on the same page also happens to select bio on the same User. Because both fragments' results get merged onto the same normalized User:42 object, user.bio is technically present and TypeScript (without masking) can't tell it apart from a field UserCard actually declared — so a developer refactoring UserCard might start reading user.bio "because it's there," silently coupling UserCard to a field it never declared. Months later, the sibling component is removed, its fragment goes with it, bio stops being fetched, and UserCard breaks with zero compile errors — the type system had no way to know the dependency existed.

Masking closes this gap by giving each fragment's consumer an opaque type (conceptually a branded/nominal type) that must be "unmasked" via a helper (useFragment in Relay-style APIs, or the generated FragmentType unwrap helper in GraphQL Code Generator's masking mode) before its fields become accessible — and that unmasking only exposes the fields the component's own fragment actually selected, hiding anything else that happens to be present on the underlying object. It's the same idea as encapsulation in OOP applied to data shape: components can't accidentally depend on data another component fetched.

Code Example

// Without masking — TypeScript can't stop this even though PostRow
// never declared it needs `viewCount`
function PostRow({ post }: { post: PostRowFieldsFragment }) {
  return <div>{post.title} - {post.viewCount}</div>; // compiles, but undeclared coupling
}

// With masking — `post` is an opaque FragmentType until unmasked,
// and unmasking only yields the fields PostRow's OWN fragment selected
import { useFragment } from "./gql";

function PostRow({ postRef }: { postRef: FragmentOf<typeof POST_ROW_FRAGMENT> }) {
  const post = useFragment(POST_ROW_FRAGMENT, postRef);
  return <div>{post.title}</div>; // post.viewCount would be a compile error here
}

Common Mistake

Candidates often describe fragment colocation well but assume the type system automatically enforces the boundary — it doesn't, unless masking is explicitly enabled via codegen or Relay's compiler. Naming that gap ("colocation is a convention; masking is what makes it a compiler-enforced guarantee") is exactly the kind of nuance that separates having read about the pattern from having hit the bug it prevents.

Q25. How do you handle fragments on interfaces and unions — inline fragments vs fragment spreads?

ROI: ★★★☆☆ Frequency: Medium

Short Answer

A named fragment defined on an interface or union (fragment NodeFields on Node { id }) can only select fields common to every possible concrete type. To select a field that only exists on one specific concrete type, you need an inline fragment with a type condition — ... on Admin { permissions } — which the server only includes in the response when the runtime object's concrete type matches. Both forms can be freely mixed and nested inside the same selection set, and both still benefit from colocation: a component that only cares about the Admin case can define its inline fragment right alongside itself.

Detailed Answer

Interfaces/unions exist in GraphQL schemas precisely to model polymorphism — a SearchResult union might resolve to User | Post | Comment, and a client has no way to know in advance which concrete type a given result will be. The response always includes __typename for exactly this reason: client code branches on it (result.__typename === "User" ? ... : ...) to decide which inline fragment's fields are actually present on a given item.

A common structuring choice: define a small named fragment per concrete type (UserResultFields, PostResultFields) and spread each one inside its own inline fragment condition at the union site — this keeps the per-type field lists colocated with whichever component renders that type, exactly like Q23's pattern, while the inline fragment syntax is just the mechanism for telling the server "only include these fields when the runtime type matches."

Code Example

const SEARCH_RESULT_FRAGMENT = gql`
  fragment SearchResultFields on SearchResult {
    __typename
    ... on User {
      id
      name
    }
    ... on Post {
      id
      title
    }
    ... on Comment {
      id
      body
    }
  }
`;

function SearchResultRow({ result }) {
  switch (result.__typename) {
    case "User":
      return <UserRow user={result} />;
    case "Post":
      return <PostRow post={result} />;
    case "Comment":
      return <CommentRow comment={result} />;
    default:
      return null;
  }
}

Interview Favorite

Mention that __typename is what makes this pattern possible client-side — without it, a client receiving a polymorphic result would have no reliable way to know which inline fragment's fields actually apply to a given item, since it can't be inferred purely from which fields happen to be non-null.

Q26. What's the risk of fragment field name collisions, and how do aliases help?

ROI: ★★★☆☆ Frequency: Medium

Short Answer

When two fragments (or a fragment and the parent query) select the same field name but with different arguments — e.g. two differently-filtered calls to the same field, or the same field name meaning something different in two inline fragments on different types — GraphQL requires them to be either identical or explicitly disambiguated with an alias (renamedField: fieldName(args)), otherwise the request is rejected as invalid before it even reaches a resolver. Aliases give each selection a distinct key in the response JSON, so both can coexist without one overwriting the other.

Detailed Answer

This shows up concretely in colocated-fragment codebases the moment two independently-written fragments both need the same field with different arguments on the same object in the same query — say, a Post.comments(limit: 3) preview fragment for a card view and a Post.comments(limit: 50) fragment for a detail view, both spread into the same query for some composite screen. GraphQL's validation rules require these to be aliased (previewComments: comments(limit: 3), allComments: comments(limit: 50)) because both selections target the same field name with conflicting arguments, and the response object can only have one key per field name unless you rename one.

This is one of the few places where full fragment independence breaks down slightly — two "independently developed" fragments can still produce a validation error when composed together, so a component author needs at least a lightweight awareness that its fragment's field+argument combination should be distinct from what a sibling might request. In practice this is rare enough that it's mostly a "know it exists" answer rather than something to defensively engineer around from day one.

Code Example

# Invalid without aliases — same field, different args, same query
query {
  post(id: "1") {
    comments(limit: 3) { id }   # from CardPreview's fragment
    comments(limit: 50) { id }  # from DetailView's fragment - CONFLICT
  }
}

# Valid — aliased so both selections get distinct response keys
query {
  post(id: "1") {
    previewComments: comments(limit: 3) { id }
    allComments: comments(limit: 50) { id }
  }
}

Common Mistake

Treating fragment colocation as guaranteeing total independence between fragments is slightly too strong a claim — field+argument collisions across sibling fragments are a real, if uncommon, seam. The stronger answer acknowledges that colocation is "mostly" independent and names the specific case (same field, different args, composed together) where aliasing becomes necessary.

Q27. How do you compose deeply nested fragments across a tree of components without over-fetching?

ROI: ★★★★☆ Frequency: High

Short Answer

Each level of the component tree spreads only its direct children's fragments, never reaching down to grandchildren's fields directly — FeedPage spreads PostCard's fragment, and PostCard's own fragment spreads AuthorAvatar's fragment inside it. This keeps each fragment's size bounded to "what this component and its direct children need," and because fragments compose by spreading rather than by re-listing fields, the total requested shape naturally stays exactly as large as the union of what's actually rendered — no smaller, no larger.

Detailed Answer

Over-fetching creeps in specifically when this discipline slips — a mid-tree component "reaches past" its children and selects a grandchild's fields directly (to "save a fragment definition"), which works today but re-couples components the same way un-colocated queries did, and it means removing the grandchild later requires knowing to prune fields the mid-tree component technically doesn't render itself. The fix is mechanical: every component, no matter how deep, only ever spreads its immediate children's exported fragments, never their fields directly.

This composability is also what keeps fragment colocation practical at scale — a fragment three levels deep changing its selection doesn't require touching the two levels above it at all, because they only reference it by name (...ChildFragment), not by its contents. This is structurally identical to how a well-composed component tree lets a leaf component change its internal rendering without its ancestors needing any changes.

Code Example

// AuthorAvatar.tsx (leaf)
export const AUTHOR_AVATAR_FRAGMENT = gql`
  fragment AuthorAvatarFields on User {
    id
    avatarUrl
  }
`;

// PostCard.tsx (middle) — spreads the CHILD's fragment, doesn't
// re-list avatarUrl itself
export const POST_CARD_FRAGMENT = gql`
  fragment PostCardFields on Post {
    id
    title
    author { ...AuthorAvatarFields }
  }
  ${AUTHOR_AVATAR_FRAGMENT}
`;

// FeedPage.tsx (root) — spreads PostCard's fragment; never sees
// avatarUrl mentioned anywhere in its own query text
const GET_FEED = gql`
  query GetFeed {
    posts { ...PostCardFields }
  }
  ${POST_CARD_FRAGMENT}
`;

Senior Engineer Perspective

Frame it as a discipline, not a library feature: "the rule I enforce in review is that a component only ever spreads its direct children's fragments, never reaches past them to grandchildren's fields — that one rule is what keeps a fragment tree over-fetch-free as it grows, without needing any tooling to enforce it."

Q28. How does Relay's compiler-enforced fragment masking differ from Apollo's approach?

ROI: ★★★☆☆ Frequency: Medium

Short Answer

Relay makes fragment masking mandatory and compiler-enforced from the ground up: every component that reads fragment data must call useFragment, and Relay's build-time compiler generates the artifacts that make an unmasked read a type error, with no opt-out. Apollo Client historically had no masking at all (any field on the merged object was readable by anyone), and only added optional masking support later, via codegen tooling (GraphQL Code Generator's client preset) rather than a mandatory compiler step — so an Apollo team can adopt masking, but it's a deliberate choice, not the default.

Detailed Answer

This difference reflects each library's broader philosophy (elaborated in Q79-Q81): Relay treats colocation and masking as core to correctness and is willing to require a build step and stricter conventions to guarantee it uniformly across a codebase — every Relay app gets masking, whether the team would have remembered to configure it or not. Apollo prioritizes flexibility and incremental adoption — you can start with zero fragments, add them gradually, and later opt into masking without a wholesale migration, but that also means an Apollo codebase without masking enabled is one dropped code-review comment away from the undeclared-coupling bug described in Q24.

The practical trade-off for an interview answer: Relay's mandatory approach trades flexibility for guaranteed consistency across a whole team/codebase; Apollo's optional approach trades guaranteed consistency for an easier onboarding ramp and the ability to retrofit onto an existing codebase without a big-bang rewrite.

Interview Favorite

This question is really testing whether you understand that "masking" is a design philosophy question, not just an API detail — the strongest answers connect it back to each library's stance on convention-over-configuration versus flexibility, which is the same axis Q79 asks about directly.

Q29. How do you test a component that only consumes a fragment, not a full query?

ROI: ★★★☆☆ Frequency: Medium

Short Answer

You don't need MockedProvider or a full query mock at all — since the component only depends on data shaped like its fragment, you can pass a plain object matching that fragment's fields (including __typename) directly as a prop in a normal render test, exactly like testing any other presentational component. This is one of colocation's underrated testing benefits: a component's tests only need to construct data the size of what it actually declared, not a full page-level query response.

Detailed Answer

Because the component's contract is "give me an object shaped like UserCardFields," a unit test can construct that object by hand (or via a small fixture/factory function) without ever touching Apollo, MockedProvider, or the network layer — it's functionally the same as testing a component that takes a plain user: { name, avatarUrl } prop. This decoupling is a direct payoff of colocation: the smaller and more self-contained a component's data dependency, the smaller and simpler its unit tests can be, and the less its tests need to know about the rest of the app's query structure.

Where you do still need MockedProvider is testing the component that actually issues the query/mutation (the container/page-level component), since that's where the network boundary genuinely lives — the pattern from Q13. Fragment-only leaf components and query-issuing container components end up needing meaningfully different test setups, which is itself a useful signal for where to draw component boundaries.

Code Example

import { render, screen } from "@testing-library/react";
import UserCard from "./UserCard";

test("renders the user's name and avatar", () => {
  // No MockedProvider, no gql — just a plain object shaped like the fragment
  const user = {
    __typename: "User",
    id: "1",
    name: "Ada Lovelace",
    avatarUrl: "https://example.com/ada.png",
  };

  render(<UserCard user={user} />);

  expect(screen.getByText("Ada Lovelace")).toBeInTheDocument();
  expect(screen.getByRole("img")).toHaveAttribute("src", user.avatarUrl);
});

Interview Gold Point

Point out the testing payoff as evidence colocation is working correctly: "if I find myself needing a full page-level query mock just to test a small presentational component, that's usually a sign the component is reaching for data outside its own declared fragment — the test setup complexity is a decent proxy for whether the data-dependency boundary is actually well drawn."

Q30. What's the tradeoff of fragment colocation vs a single "God query" defined at the page level?

ROI: ★★★★☆ Frequency: High

Short Answer

A single page-level query with every field hand-listed is simpler to read as one document and produces exactly one network request with an obviously predictable shape — but it tightly couples every component on the page to that one shared query, so any component's changing data needs requires editing a file the component doesn't own. Colocated fragments decouple that (each component owns its own requirements) at the cost of the actual query becoming a tree of spreads that's less immediately readable in one glance, and — without care — can occasionally produce a larger combined request than a hand-tuned God query would, if fragments aren't kept tight to what's genuinely rendered (the discipline from Q27).

Detailed Answer

The God-query approach tends to work fine for small apps or a small number of screens with low component reuse — there's less indirection, and a reviewer can see the entire data shape for a page in one place. It breaks down as an app grows: the same UserCard rendered on five different pages means five separately-maintained field lists that must all be kept manually in sync, and it's exactly the kind of hidden coupling that produces "why did this field disappear from the profile page" bugs when someone edits a shared query without realizing three other pages also depend on that exact field list.

Colocation is the standard recommendation once an app has meaningful component reuse and more than a couple of contributors, precisely because it scales the way component composition scales — but it's genuinely a trade-off, not a strictly-better choice, and a senior answer says so rather than treating colocation as dogma. Some teams land on a middle ground: colocate fragments for genuinely reused components, but allow simple, rarely-reused, page-specific screens to just inline their fields directly without the ceremony of a dedicated fragment file.

Senior Engineer Perspective

The balanced answer avoids treating either extreme as correct: "I colocate fragments for components that are reused or owned by a team boundary; for a one-off page-specific field, I don't always bother creating a fragment file just for the sake of the pattern." That kind of pragmatic scoping is exactly what a senior-level answer should sound like, versus reciting colocation as an unconditional best practice.

SECTION 8 - ADVANCED PAGINATION PATTERNS

Q31. How do you implement bidirectional (forward and backward) pagination with Relay-style connections?

ROI: ★★★★☆ Frequency: High

Short Answer

The Relay connection spec defines both directions symmetrically: first/after page forward from a cursor, and last/before page backward from one, with pageInfo exposing hasNextPage/hasPreviousPage and startCursor/endCursor for both ends of the currently-loaded window. A client that supports "load newer" and "load older" (a chat window loading history upward and new messages downward is the canonical case) issues forward-direction fetches when scrolling toward the end and backward-direction fetches when scrolling toward the beginning, merging each into the correct side of the cached list.

Detailed Answer

The subtlety is in the cache merge function: a forward page should be appended after the existing edges, while a backward page should be prepended before them — a single generic "concatenate incoming after existing" merge function (the common pagination example) is wrong for the backward case, since it would put older messages after newer ones instead of before them. The merge function needs to inspect which arguments were used for this particular fetch (via the options.args parameter Apollo passes in) to decide which end to attach the incoming edges to.

This is exactly the pattern chat and social-feed UIs need: infinite-scroll-down for "older" content mixed with a live-updating "newer" stream at the top. Getting the merge direction right is what keeps scroll position stable — prepending correctly-ordered older messages above the currently visible viewport, rather than at the bottom, is what avoids the classic "infinite scroll jumps the user back to the top" bug.

Code Example

const cache = new InMemoryCache({
  typePolicies: {
    Query: {
      fields: {
        messages: {
          keyArgs: ["chatId"],
          merge(existing, incoming, { args }) {
            if (!existing) return incoming;
            if (args?.before) {
              // Backward page: prepend older messages
              return {
                ...incoming,
                edges: [...incoming.edges, ...existing.edges],
                pageInfo: { ...existing.pageInfo, hasPreviousPage: incoming.pageInfo.hasPreviousPage },
              };
            }
            // Forward page: append newer messages
            return {
              ...incoming,
              edges: [...existing.edges, ...incoming.edges],
              pageInfo: { ...incoming.pageInfo, hasPreviousPage: existing.pageInfo.hasPreviousPage },
            };
          },
        },
      },
    },
  },
});

Interview Gold Point

The scroll-position detail is the concrete, production-tested insight to volunteer: correctly distinguishing forward vs backward merges isn't just a data-correctness concern, it directly determines whether the user's scroll position visually jumps when older content loads above their current view.

Q32. How do you dedupe items when merging paginated results in the cache, e.g. when pages overlap?

ROI: ★★★★☆ Frequency: High

Short Answer

Overlap happens when new items are inserted into the underlying list between page fetches, or when a client retries/refetches a page it already has — the naive "concatenate incoming after existing" merge would then produce visible duplicates. The fix is to dedupe by the item's stable id (or cursor) inside the merge function itself, typically by building a Map keyed on id from the existing edges, then only appending incoming edges whose id isn't already present.

Detailed Answer

Cursor-based pagination is more resistant to this than offset-based pagination (Q7), but not immune — a cursor anchors to "everything after this specific item," which avoids skip/duplicate errors from insertions before the cursor, but a client that fetches the same page twice (a retried request after a flaky network blip, or a user rapidly double-clicking "load more") can still produce two overlapping responses that need deduping on the client side regardless of how good the server's cursor semantics are.

A dedupe-aware merge function is cheap to write and worth including by default in any paginated typePolicy, precisely because the failure mode (a visually duplicated row, or a React key warning if `id` is reused) is easy to overlook in initial development and only shows up under real network conditions or fast user interaction — exactly the kind of thing that's much easier to build in from the start than to retrofit once duplicate rows start showing up in production.

Code Example

merge(existing = { edges: [] }, incoming, { readField }) {
  const seen = new Set(existing.edges.map((e) => readField("id", e.node)));
  const deduped = incoming.edges.filter(
    (e) => !seen.has(readField("id", e.node))
  );
  return {
    ...incoming,
    edges: [...existing.edges, ...deduped],
  };
}

Common Mistake

Assuming cursor-based pagination is automatically duplicate-free is a common overstatement — cursors solve the insertion/shift problem cleanly, but they don't protect against a retried or double-fired fetch producing the same page twice. A dedupe step in the merge function is cheap insurance worth having regardless of how well-behaved the pagination strategy otherwise is.

Q33. How do you handle "load more" (append) vs "jump to a specific page" (replace) on the same paginated field?

ROI: ★★★☆☆ Frequency: Medium

Short Answer

These need genuinely different merge semantics on the same field — "load more" should append to the existing cached edges, while a fresh navigation to page 1 (e.g. after changing a filter, or the user explicitly resetting the view) should replace the cached result entirely rather than append to stale data. You distinguish the two inside the merge function by checking whether the incoming fetch's arguments represent "continuing from where we were" (an after cursor matching the existing data's end) versus "starting fresh" (no cursor, or a cursor that doesn't match, signaling a new/reset session), or more simply by passing an explicit flag through the fetch call itself.

Detailed Answer

The simplest and most robust approach is often not to infer intent purely from arguments, but to make the call site explicit: fetchMore for the append case, and a plain refetch(newVariables) — or a fresh useQuery execution with different variables entirely — for the replace case, combined with a merge function that always replaces when the incoming page's starting cursor doesn't logically follow the existing cached data (a strong signal this is a "new" request, not a continuation). Some teams instead reset by calling cache.evict on the field before triggering a fresh fetch, which sidesteps the need for the merge function to guess intent at all.

Whichever mechanism you choose, the important design decision to name explicitly in an interview is that "append" and "replace" are not properties of the field — they're properties of the specific fetch, and the merge function (or the calling code) needs an explicit signal to distinguish them, because Apollo's default merge behavior can't infer user intent from arguments alone.

Code Example

// Explicit reset: evict the field, then fetch fresh — avoids ambiguity
function ResetAndRefetch({ client, refetch }) {
  return (
    <button
      onClick={() => {
        client.cache.evict({ fieldName: "posts" });
        client.cache.gc();
        refetch({ after: null });
      }}
    >
      Apply new filter
    </button>
  );
}

Senior Engineer Perspective

The mental model worth stating plainly: "merge functions are good at combining data, not at guessing intent — whenever a UI needs both 'continue' and 'start over' behavior on the same field, I make that distinction explicit at the call site rather than trying to infer it purely from cursor arguments inside the cache layer."

Q34. What are the offset-vs-cursor tradeoffs in concrete, production terms — beyond the basic definition?

ROI: ★★★★☆ Frequency: High

Short Answer

Beyond the textbook "cursor is stable, offset shifts under mutation" answer: offset pagination degrades in raw database performance on large tables, because OFFSET 100000 typically still requires the database to scan and discard the first 100,000 rows before returning the next page — a cost that grows with the offset. Cursor pagination backed by an indexed column (WHERE id > :cursor ORDER BY id LIMIT N) stays roughly constant-time regardless of how deep into the list you are, because it's an indexed range scan, not a skip-then-read.

Detailed Answer

Offset pagination does retain two genuine, non-workaround-able advantages cursor pagination gives up: direct page-jump ("go to page 47") has no natural cursor equivalent (a cursor only knows "before/after this item," not "the 470th item"), and a stable, computable total-page-count for UI like "Page 3 of 12" is trivial with offset/limit but awkward with cursors (Q35 covers exactly this gap). So the honest trade-off table is: cursor wins on stability-under-mutation and large-offset performance; offset wins on arbitrary page-jump UX and cheap total-count display.

In practice, many production systems use a hybrid: cursor-based pagination for the actual data-fetching mechanism (getting the stability and performance benefits), paired with an approximate, separately-computed or cached total count for display purposes only — accepting that the displayed total might be slightly stale rather than trying to make cursors do something they're not designed for.

Q35. How do you show a total count alongside cursor pagination, and why can it be inconsistent?

ROI: ★★★☆☆ Frequency: Medium

Short Answer

The Relay connection spec allows an optional totalCount field on the connection type, computed by a separate (often more expensive) count query the server runs alongside the paginated fetch. Because it's computed independently of the specific page's cursor window, it can drift from what the user perceives as "correct" if items are added or removed between the moment the total was computed and the moment the user has scrolled through some of the list — the count and the visible items are technically two separate reads that aren't transactionally consistent with each other.

Detailed Answer

This inconsistency is usually an acceptable, even invisible, trade-off for typical UI ("Showing 1-20 of ~4,382 results") where users don't expect or need exact real-time precision — but it's worth understanding the mechanism rather than treating totalCount as an always-exact number. For genuinely high-write-volume lists, some APIs deliberately return an approximate count (label it "About 4,300 results," mirroring how search engines phrase result counts) rather than implying false precision, or omit the total entirely and switch the UI to "load more" without ever displaying a page-of-N total.

Fetching an exact COUNT(*) on a large, frequently-written table can itself be a meaningful performance cost server-side (depending on the database and whether the count can use an index-only scan), which is another reason some schemas deliberately make totalCount optional or approximate rather than a mandatory exact field on every connection.

Code Example

query GetPosts($after: String) {
  posts(first: 20, after: $after) {
    totalCount   # a separately-computed, potentially-stale approximation
    edges { node { id title } }
    pageInfo { hasNextPage endCursor }
  }
}

Common Mistake

Treating totalCount as a strongly-consistent, always-accurate number is the mistake to avoid naming as if it were fact — the correct framing acknowledges it's a best-effort, separately-computed value, and that's usually a perfectly reasonable trade-off for UI purposes as long as everyone building against it understands that.

Q36. How do you implement infinite scroll with fetchMore and an IntersectionObserver in React + Apollo?

ROI: ★★★★☆ Frequency: High

Short Answer

A sentinel element (an empty div) is placed at the bottom of the rendered list, and an IntersectionObserver watches when it scrolls into the viewport — at which point you call fetchMore with the current endCursor. Guard against firing multiple overlapping fetchMore calls while one is already in flight (e.g. from fast scrolling triggering the observer repeatedly), and stop observing once hasNextPage is false so the sentinel doesn't keep firing pointless fetches at the bottom of a fully-loaded list.

Detailed Answer

IntersectionObserver is preferred over a scroll-event listener because it's asynchronous and doesn't run on every scroll tick — the browser notifies you only when the intersection state actually changes, which avoids the classic scroll-handler performance trap of doing work on every single pixel of scroll movement. The observer callback should be guarded with an in-flight flag (or checking the query's own loading/networkStatus state) so a burst of rapid scrolling doesn't fire several concurrent fetchMore calls for the same next page.

Cleanup matters here as much as setup: the observer must be disconnected on unmount (React's useEffect cleanup function), or it keeps a reference to a detached DOM node and can fire on a component that's no longer part of the tree — a real, if usually harmless, memory-leak pattern.

Code Example

function PostFeed() {
  const { data, fetchMore, loading } = useQuery(GET_POSTS);
  const sentinelRef = useRef(null);
  const hasNextPage = data?.posts.pageInfo.hasNextPage;

  useEffect(() => {
    if (!hasNextPage || !sentinelRef.current) return;

    const observer = new IntersectionObserver(
      ([entry]) => {
        if (entry.isIntersecting && !loading) {
          fetchMore({ variables: { after: data.posts.pageInfo.endCursor } });
        }
      },
      { rootMargin: "200px" } // start fetching slightly before it's visible
    );

    observer.observe(sentinelRef.current);
    return () => observer.disconnect(); // cleanup on unmount / dep change
  }, [hasNextPage, loading, data, fetchMore]);

  return (
    <>
      {data?.posts.edges.map(({ node }) => <PostRow key={node.id} post={node} />)}
      {hasNextPage && <div ref={sentinelRef} style={{ height: 1 }} />}
    </>
  );
}

Interview Gold Point

Two specific details separate a solid infinite-scroll implementation from a naive one: guarding against duplicate concurrent fetchMore calls during fast scrolling, and disconnecting the observer on cleanup. Both are easy to omit in a first pass and both cause real, reproducible bugs (duplicate page fetches, or a leaked observer callback) once the component is used in a real scrolling list rather than a demo.

Q37. What issues arise when paginating a field that's also filtered or sorted, and how do keyArgs handle it?

ROI: ★★★★☆ Frequency: High

Short Answer

A field that's both filtered and paginated (posts(category: "tech", first: 10, after: $cursor)) needs keyArgs to include the filter/sort arguments (so different categories get separate cache storage) while excluding the pagination arguments (so pages within one category still merge into a single growing list) — getting this split wrong produces either cross-category data bleeding (filter args excluded from the key) or a fresh, disconnected cache slot per page (pagination args mistakenly included in the key).

Detailed Answer

This is the composition of two concerns from Q19 and Q21 that becomes genuinely tricky once they interact on the same field: you need the cache to treat "tech posts" and "sports posts" as entirely separate paginated lists (each with their own growing set of merged edges), while still treating page 1 and page 2 of "tech posts" specifically as one continuous list to be concatenated. The keyArgs array is exactly the mechanism for expressing that split — list the filter/sort args explicitly, and simply omit the pagination args (first/after) from the list entirely, since anything not named in keyArgs is automatically excluded from the cache key.

A related, easy-to-miss requirement: changing the sort/filter needs to reset the pagination cursor to the beginning (Q38 covers this explicitly) — otherwise a stale endCursor from the previous filter gets sent along with the new filter's request, which is at best a wasted round trip and at worst a request the server can't meaningfully satisfy (a cursor computed against a different, now-irrelevant ordering).

Code Example

const cache = new InMemoryCache({
  typePolicies: {
    Query: {
      fields: {
        posts: {
          // category/sortBy define identity; first/after are excluded
          // by simply not being listed here
          keyArgs: ["category", "sortBy"],
          merge(existing, incoming) {
            return {
              ...incoming,
              edges: [...(existing?.edges ?? []), ...incoming.edges],
            };
          },
        },
      },
    },
  },
});

Senior Engineer Perspective

The mental checklist worth stating out loud: "does this argument change WHICH list we're looking at (goes in keyArgs) or WHERE we are within that same list (stays out of keyArgs, handled by merge)?" That one-sentence heuristic resolves the vast majority of keyArgs design questions correctly without needing to memorize specific field examples.

Q38. How do you reset pagination state when filters or sort change, without leaking the previous filter's merged results?

ROI: ★★★★☆ Frequency: High

Short Answer

If keyArgs correctly includes the filter/sort arguments (Q37), each distinct filter value already gets its own separate cache storage slot, so switching filters doesn't leak data between them at the cache level — but the component's local "current cursor" state (whatever variable tracks after for fetchMore calls) still needs to be explicitly reset to null/undefined when the filter changes, or the next fetch will incorrectly try to continue from the old filter's cursor position instead of starting a fresh first page for the new filter.

Detailed Answer

This is a case where the cache and the component each hold half of the "current pagination position" state, and both halves need to agree. Changing the query's variables to a new filter value while forgetting to also reset a locally-tracked cursor variable is a common source of a subtle bug: the UI shows a first page of new-filter results (because the query's own data updated correctly), but scrolling down to trigger the next fetchMore silently reuses a stale cursor computed under the old filter/sort order, which either 404s, returns empty, or — worse — returns technically valid but semantically wrong data if the old cursor happens to still resolve to something under the new ordering.

The cleanest fix is to derive the "current cursor for fetchMore" directly from the query's own live data.posts.pageInfo.endCursor rather than tracking it as separate component state at all — since that field is inherently scoped to whatever filter's cache slot is currently being read, it can never go stale relative to the active filter the way an independently-tracked local variable can.

Code Example

function FilterablePosts() {
  const [category, setCategory] = useState("tech");
  const { data, fetchMore } = useQuery(GET_POSTS, { variables: { category, first: 10 } });

  // Derive the cursor from live data instead of tracking it separately —
  // it's automatically correct for whichever filter is currently active
  const loadMore = () =>
    fetchMore({ variables: { category, after: data.posts.pageInfo.endCursor } });

  return (
    <>
      <select value={category} onChange={(e) => setCategory(e.target.value)}>
        <option value="tech">Tech</option>
        <option value="sports">Sports</option>
      </select>
      {/* Changing category re-runs useQuery with a fresh cursor naturally,
          since first-page fetches never pass an `after` value at all */}
      {data?.posts.edges.map(({ node }) => <PostRow key={node.id} post={node} />)}
      <button onClick={loadMore}>Load more</button>
    </>
  );
}

Common Mistake

Tracking the pagination cursor as independent component state (a useState alongside the filter) invites exactly this class of bug. Deriving it directly from the current query's own cached pageInfo instead removes an entire category of "forgot to reset the cursor on filter change" mistakes, because there's no separate piece of state that could ever drift out of sync with the active filter in the first place.

Q39. How do you design optimisticResponse for a mutation whose exact return shape depends on server-computed fields you can't predict?

ROI: ★★★★☆ Frequency: High

Short Answer

You accept that the optimistic value is a best guess, not a guarantee — for fields you genuinely can't predict (a server-generated timestamp, a computed rank, a moderation status), you either omit them from the optimistic response if the UI can tolerate them briefly being absent/default, or you supply a reasonable placeholder (client-side Date.now() for a timestamp) that gets silently replaced the instant the real response arrives and reconciles the cache. The point isn't perfect prediction — it's giving the user immediate, plausible feedback that self-corrects within one round trip.

Detailed Answer

The UI needs to be resilient to the optimistic guess being wrong for those unpredictable fields specifically — which usually means not building any critical logic (permissions checks, conditional rendering that would look jarring if it flips) on top of a field you know is a guess. A common pattern: use the real, predictable fields (the text the user typed, the item being liked) for anything the UI displays prominently, and treat server-computed fields as "will appear/update shortly" rather than something the optimistic layer needs to nail exactly.

For genuinely important server-computed values where a flicker on reconciliation would be jarring (e.g. a computed price total after tax), it's often better to skip optimisticResponse for that specific mutation and accept the real network latency, rather than show a plausible-but-wrong number for even a fraction of a second — the decision to use optimistic UI should be per-mutation based on how tolerant the specific UI is to a brief, self-correcting misprediction, not applied uniformly to every mutation in the app.

Code Example

const [addComment] = useMutation(ADD_COMMENT, {
  optimisticResponse: (vars) => ({
    addComment: {
      __typename: "Comment",
      id: `temp:${Date.now()}`,       // predictable, self-corrects
      text: vars.text,                 // known exactly — from user input
      createdAt: new Date().toISOString(), // best-guess placeholder
      moderationStatus: "PENDING",     // reasonable default, not a guarantee
    },
  }),
});

Senior Engineer Perspective

The judgment call to name explicitly: optimistic UI is a per-mutation decision based on how forgiving the specific screen is to a brief, self-correcting misprediction — not a blanket policy applied to every mutation. A senior engineer can point to a specific mutation in a past project where they deliberately skipped optimistic response because the reconciliation flicker would have been worse than the wait.

Q40. How does Apollo roll back an optimistic update on error, mechanically?

ROI: ★★★★☆ Frequency: High

Short Answer

Apollo applies an optimistic response as a separate, temporary "layer" on top of the cache rather than writing it as a permanent change — internally it's tracked in an optimistic data layer distinct from the base cache. If the real mutation later resolves successfully, that optimistic layer is discarded and replaced with the real response's data written normally. If the mutation errors, the optimistic layer is simply discarded with nothing to replace it — the cache reverts to exactly what it looked like before the optimistic write, and every component watching that data re-renders back to its pre-mutation state automatically.

Detailed Answer

This layering is what makes rollback "automatic" and safe: because the optimistic data was never merged into the base cache in the first place, there's no need to compute or track a diff to undo — removing the layer is sufficient. This is architecturally similar to a database transaction that's rolled back rather than one that requires manually reversing each individual write; the cache doesn't need to remember what it looked like before, because the optimistic layer was additive and separable the whole time.

One practical implication worth knowing: while an optimistic layer is active, reads from the cache (via useQuery or readQuery) see the optimistic value merged on top, but the "real," non-optimistic cache underneath is untouched — so if two overlapping mutations both apply optimistic updates to the same field, Apollo layers them and unwinds them in a defined order as each resolves or fails, rather than one silently corrupting the other's base data.

Code Example

const [toggleLike] = useMutation(TOGGLE_LIKE, {
  optimisticResponse: { toggleLike: { __typename: "Post", id, liked: true, likeCount: current + 1 } },
  update(cache, { data }) {
    // On success, this permanently writes the REAL response,
    // replacing the discarded optimistic layer
    cache.modify({
      id: cache.identify({ __typename: "Post", id }),
      fields: { liked: () => data.toggleLike.liked, likeCount: () => data.toggleLike.likeCount },
    });
  },
  onError() {
    // No manual rollback code needed here — Apollo already discarded
    // the optimistic layer the instant the mutation promise rejected
    showToast("Couldn't like this post — please try again.");
  },
});

Interview Gold Point

The layering metaphor is the concrete mental model worth stating: "the optimistic value was never actually merged into the base cache — it's a temporary overlay, so 'rollback' isn't undoing a write, it's just removing an overlay that was never permanent in the first place." That distinction is what makes automatic rollback safe and correct rather than a heuristic best-effort undo.

Q41. How do you handle optimistic UI for a delete mutation (removing an item) vs a create mutation (adding one)?

ROI: ★★★★☆ Frequency: High

Short Answer

Optimistic create needs a temporary client-generated id (conventionally prefixed, e.g. client: or temp:) and an update function that splices the new item into the relevant cached list — covered in Q6. Optimistic delete is arguably simpler at the data level (there's no new id to invent) but riskier at the UX level: you're removing something from view before you're certain the deletion actually succeeded server-side, so the update function should filter the item out of the cached list optimistically, and the rollback path (on error) needs the item to convincingly reappear, ideally without a jarring flash back into existence.

Detailed Answer

For delete, a common refinement beyond a bare optimistic removal is a brief "undo" affordance — remove the row immediately (optimistic), but hold the actual mutation call for a short window (a "toast with an Undo button" pattern) so a mis-click can be reversed without ever hitting the server, and only fire the real mutation once that window elapses. This isn't Apollo-specific machinery; it's a UX pattern layered on top of the same optimistic-update primitives, and it further reduces how often a user experiences the rollback-flash case at all.

A subtlety specific to delete: unlike create (where the optimistic id is temporary and gets replaced), delete's optimistic effect is the absence of something — if the mutation fails and Apollo's automatic rollback restores the pre-mutation cache state, the previously-hidden item reappearing is often more visually jarring than a create's flicker, because the user has typically already moved their attention elsewhere by the time an error surfaces. Some teams choose not to make delete optimistic at all for exactly this UX reason, preferring a brief "deleting..." disabled state over an optimistic-then-possibly-reappearing row.

Code Example

const [deleteTodo] = useMutation(DELETE_TODO, {
  optimisticResponse: { deleteTodo: { __typename: "Todo", id } },
  update(cache) {
    cache.modify({
      fields: {
        todos(existingRefs = [], { readField }) {
          return existingRefs.filter((ref) => readField("id", ref) !== id);
        },
      },
    });
  },
  onError() {
    // The item reappears automatically via Apollo's rollback;
    // pair with a toast so the user isn't confused by the flash-back
    showToast("Delete failed — item restored.");
  },
});

Common Mistake

Treating "make every mutation optimistic" as a uniform best practice misses the asymmetry between create and delete UX: an optimistic create that fails just removes something the user hasn't fully processed yet, while an optimistic delete that fails brings back something the user has already mentally dismissed — worth naming as a genuine UX design decision, not just an implementation detail.

Q42. What's the difference between the update function and onQueryUpdated?

ROI: ★★★☆☆ Frequency: Medium

Short Answer

update is where you imperatively write the mutation's result into the cache (via cache.modify/writeQuery/writeFragment). onQueryUpdated is a separate, later hook that fires once per active watched query whose cached data was touched by that same update function — it gives you a chance to decide, per query, whether to let the default re-render happen, force a full refetch of that specific query instead, or skip updating it, based on the query's own name/variables. It's a more surgical alternative to broad refetchQueries when you need per-query control after a cache write.

Detailed Answer

The typical use case for onQueryUpdated is when a mutation's cache write is "good enough" for most active queries observing that data, but one specific query's derived/computed field (something the cache can't recompute just from the entity change, like a server-side aggregate) genuinely needs a real refetch to stay correct — onQueryUpdated lets you force a refetch for just that one query by name/variables, while every other affected query is left to update from the cache write alone, avoiding the blanket cost of refetching everything via refetchQueries: "all".

This is a relatively advanced, less commonly reached-for API compared to update — most mutations never need it — but it's worth knowing it exists specifically for the "cache write handles 95% of affected queries correctly, but this one query needs an actual network refetch" case, since without it the common fallback is over-broadly refetching everything.

Code Example

const [archiveThread] = useMutation(ARCHIVE_THREAD, {
  update(cache, { data }) {
    cache.modify({
      id: cache.identify({ __typename: "Thread", id: data.archiveThread.id }),
      fields: { archived: () => true },
    });
  },
  onQueryUpdated(observableQuery) {
    // ThreadStats has a server-computed aggregate the cache write
    // above can't recompute — force just that one query to refetch
    if (observableQuery.queryName === "ThreadStats") {
      return observableQuery.refetch();
    }
    return true; // let every other affected query update from cache normally
  },
});

Interview Favorite

Naming onQueryUpdated unprompted, and specifically describing it as "per-query control after a cache write, for the rare case where one query's data can't be derived purely from the mutation's returned entity," is a good signal of having gone beyond the standard update/refetchQueries pair most tutorials stop at.

Q43. How do you batch multiple mutations, e.g. reordering a list, without causing cache thrashing or visual flicker?

ROI: ★★★★☆ Frequency: High

Short Answer

Firing one mutation per moved item (as a naive drag-and-drop reorder handler might) causes multiple separate cache writes and re-renders in quick succession, each potentially showing an intermediate, briefly-inconsistent order. The fix is to design the mutation itself to accept the whole new order in one call (reorderItems(itemIds: [ID!]!)) so there's exactly one network request and one cache write reflecting the final, correct state — pushing the "batch these into one operation" responsibility to the schema/mutation design rather than trying to coalesce many small client-side mutation calls after the fact.

Detailed Answer

When the schema genuinely can't be changed to accept a batched shape (a third-party or legacy API only exposes single-item move operations), a client-side technique is to apply one combined optimistic response representing the fully-reordered list immediately, then fire all the individual mutations in the background without individually re-triggering UI updates per response — effectively decoupling "what the user sees" (updated instantly and correctly via one optimistic write) from "what actually happens on the wire" (potentially several sequential real requests). This requires care with the `update` functions of the individual mutations to avoid each one re-deriving and re-writing an intermediate order that momentarily conflicts with the optimistic one.

The broader principle: cache thrashing is almost always a symptom of an operation that's conceptually "one user action" being modeled as multiple separate network operations. Whenever possible, push for the mutation API itself to match the actual unit of user intent (one reorder action, one mutation call) rather than trying to paper over a mismatched API shape with client-side coordination tricks.

Code Example

# Schema designed around the real unit of user intent —
# one call for the whole reorder, not N calls for N moved items
mutation ReorderItems($listId: ID!, $orderedItemIds: [ID!]!) {
  reorderItems(listId: $listId, orderedItemIds: $orderedItemIds) {
    id
    items { id position }
  }
}

Senior Engineer Perspective

The reusable principle worth stating: "cache thrashing is usually a signal that the mutation granularity doesn't match the actual unit of user intent — the fix is almost always to push for a coarser-grained mutation on the schema, not to build increasingly clever client-side coalescing around a mismatched API."

Q44. How do you handle a mutation that needs to invalidate or refetch queries it doesn't know about at compile time?

ROI: ★★★☆☆ Frequency: Medium

Short Answer

refetchQueries normally takes an explicit list of query documents/names, which requires the mutation's author to know in advance which queries are affected — brittle in a large app where a mutation's effects ripple into screens the mutation's author didn't write. The alternative is refetchQueries: "active" (or the older include: "all"), which tells Apollo to refetch every currently-active watched query instead of a hardcoded list — trading precision (you refetch things that might not actually need it) for decoupling (the mutation doesn't need compile-time knowledge of every consumer).

Detailed Answer

This is the same coupling trade-off from Q6's "why isn't refetching the default answer" discussion, pushed to its logical extreme: an explicit query list is precise but couples the mutation to specific consumers; "active" decouples completely but refetches indiscriminately, including queries whose data genuinely wasn't affected — a real network and rendering cost if the app has many unrelated active queries at once. In practice, teams often land in between: name the queries that are reliably, always affected explicitly, and use cache-level tools (cache.modify, type policies) for the rest, reserving broad "active" refetching for rare, genuinely-hard-to-predict invalidation cases (a mutation with wide-reaching, hard-to-enumerate side effects, like a permissions change that could affect visibility across many unrelated screens).

A schema-level alternative worth naming: some GraphQL APIs expose a dedicated invalidation/tag system (similar to REST's cache-tag headers) where a mutation's response includes which cache "tags" it affected, and the client maps tags to queries — shifting the "what did this affect" knowledge to the server, which often has better visibility into a mutation's true blast radius than the client does.

Code Example

const [updatePermissions] = useMutation(UPDATE_PERMISSIONS, {
  // Broad, hard-to-predict blast radius — reach for "active" deliberately,
  // not as a default habit
  refetchQueries: "active",
  awaitRefetchQueries: true,
});

const [renameFile] = useMutation(RENAME_FILE, {
  // Well-understood, narrow blast radius — name it explicitly instead
  refetchQueries: [{ query: GET_FOLDER_CONTENTS, variables: { folderId } }],
});

Common Mistake

Reaching for refetchQueries: "active" as a default habit to avoid thinking through a mutation's real blast radius is a performance anti-pattern that's easy to slip into — it "just works" in development with a handful of active queries, then quietly gets expensive as the app grows more screens with more concurrently-active queries.

Q45. How do you test optimistic UI behavior, including the rollback path, in unit tests?

ROI: ★★★☆☆ Frequency: Medium

Short Answer

With MockedProvider, supply a mock whose result resolves after a small artificial delay (or simply hasn't resolved yet at the point you assert) so you can capture and assert on the intermediate, optimistic-only render — the UI state that exists after the optimistic write but before the real response lands. For the rollback path, supply an error mock instead of a result and assert that the UI returns to its pre-mutation state once the mocked promise rejects.

Detailed Answer

Testing library's act()/async utilities (or explicit await waitFor(...) assertions timed against specific renders) let you assert on the sequence of states rather than just the final one: render the optimistic state immediately after the mutation call and before awaiting the mock's resolution, then await resolution and assert the final, reconciled state separately. This kind of test genuinely does add value beyond a happy-path test, because optimistic UI's entire value proposition is that intermediate state — a bug where the optimistic response never actually applies (e.g. a typo in a field name so the shape doesn't match the real query, silently failing to render) would pass a naive "eventually shows the right data" test while completely missing the point of adding optimistic UI in the first place.

For the rollback assertion specifically, the useful thing to verify isn't just "the error message shows" — it's that the previously-optimistic data (the temporarily-added row, the flipped toggle) has actually reverted in the rendered output, since that's the behavior automatic rollback is specifically supposed to guarantee.

Code Example

test("shows optimistic state immediately, then reconciles", async () => {
  const mocks = [{
    request: { query: ADD_TODO, variables: { text: "Ship it" } },
    result: { data: { addTodo: { __typename: "Todo", id: "real-1", text: "Ship it", completed: false } } },
    delay: 50, // gives us a window to assert the optimistic render first
  }];

  render(
    <MockedProvider mocks={mocks} addTypename={false}>
      <TodoForm />
    </MockedProvider>
  );

  fireEvent.click(screen.getByText("Add"));

  // Optimistic render — appears before the mocked network delay resolves
  expect(await screen.findByText("Ship it")).toBeInTheDocument();

  // Reconciled render — same text, but now backed by the real id
  await waitFor(() => expect(screen.queryByText("Ship it")).toBeInTheDocument());
});

Interview Gold Point

The key insight to state explicitly: a test that only asserts the final, settled state can't actually verify optimistic UI is working — it needs to assert on the intermediate render specifically, since that's the entire behavior optimistic UI adds. Naming this distinction shows you understand what you're actually testing, not just that "there's a test for the mutation."

Q46. What race conditions can occur between an optimistic update and a fast-following real response, and how do you avoid UI flicker?

ROI: ★★★★☆ Frequency: High

Short Answer

If the real response arrives extremely fast (a low-latency network, or a mocked/local backend in dev), the optimistic layer and the real data can both apply in very quick succession, causing a visible double-render or brief flicker even when both ultimately show the same or similar data — especially if the optimistic guess and the real response differ even slightly (a formatted timestamp, a normalized string) in ways invisible to the user's intent but visible as a re-render. A second race: if a user fires a second mutation on the same entity before the first's real response has landed, the two optimistic layers and their eventual real reconciliations can apply out of order relative to each other if not handled carefully.

Detailed Answer

The flicker-from-fast-response case is best minimized by making the optimistic guess match the real response's shape as closely as possible — if the server would trim/normalize a string, normalize it client-side in the optimistic response too, so reconciliation doesn't introduce a visible diff even though functionally nothing "wrong" happened. Where a visible diff is unavoidable (a server-computed field, per Q39), accept the brief flicker as an acceptable cost of the pattern rather than over-engineering around it — it's rarely worth the complexity to eliminate entirely for genuinely unpredictable fields.

The double-mutation race (rapid double-click, or two rapid edits to the same field) is the more serious one to guard against deliberately: disable the triggering control while a mutation is in flight (useMutation's own loading flag is exactly for this), or debounce the action, so a second optimistic layer never gets applied on top of a first one that hasn't resolved yet — stacking optimistic layers for the same field is exactly the scenario where "which layer wins on rollback" becomes genuinely ambiguous and can produce cache states that don't correspond to anything the server ever actually returned.

Code Example

function LikeButton({ post }) {
  const [toggleLike, { loading }] = useMutation(TOGGLE_LIKE, {
    optimisticResponse: {
      toggleLike: { __typename: "Post", id: post.id, liked: !post.liked },
    },
  });

  return (
    <button
      disabled={loading} // prevents a second optimistic layer stacking
      onClick={() => toggleLike({ variables: { id: post.id } })}
    >
      {post.liked ? "Unlike" : "Like"}
    </button>
  );
}

Senior Engineer Perspective

The practical guardrail worth naming unprompted: disabling the triggering control (or debouncing) while a mutation with an optimistic response is in flight isn't just a UX nicety against accidental double-submits — it specifically prevents the harder-to-reason-about case of two stacked optimistic layers on the same entity, which is a real source of hard-to-reproduce cache-state bugs if left unguarded.

SECTION 10 - LOCAL STATE WITH APOLLO CLIENT

Q47. What is Apollo's client-side schema / local-only fields, and when would you model UI state this way instead of useState?

ROI: ★★★☆☆ Frequency: Medium

Short Answer

Apollo lets you define fields that exist only on the client — never sent to or resolved by the server — and query them with the same useQuery/gql machinery as remote fields, marked with the @client directive. This is worth reaching for specifically when a piece of UI state is naturally attached to a GraphQL entity already in the cache (e.g. "is this specific cached Post currently expanded in the UI") and you want reading/writing it to go through the same query layer as the rest of that entity's data, rather than maintaining a completely separate piece of component or global state that has to be manually kept in sync with which entity it refers to.

Detailed Answer

The honest scoping: for state that's genuinely local to one component and doesn't need to be read anywhere else (a form input's current value, whether a dropdown is open), plain useState remains simpler and more idiomatic — reaching for Apollo's client-side schema there just adds indirection for no benefit. Client-side schema fields earn their keep specifically when the state is naturally keyed by an entity that's already normalized in the Apollo cache and needs to be read by multiple, potentially distant components (a "selected" flag on a list item that both the list and a detail panel elsewhere need to read consistently), because then it inherits the cache's existing normalization and reactivity for free.

This pattern has become less commonly reached for since reactive variables (Q48) were introduced as a simpler alternative for most "client-only state that a few components need to share" cases — client-side schema/local resolvers still exist and are documented, but Apollo's own guidance has shifted toward reactive variables plus type policies for new code, reserving the older local-resolver-style API mostly for legacy codebases or cases needing state genuinely attached per-entity in the normalized store.

Code Example

const IS_EXPANDED_FIELD = gql`
  query GetPostExpanded($id: ID!) {
    post(id: $id) @client {
      isExpanded
    }
  }
`;

const cache = new InMemoryCache({
  typePolicies: {
    Post: {
      fields: {
        isExpanded: {
          read(existing = false) {
            return existing; // local-only field, never sent to the server
          },
        },
      },
    },
  },
});

// Writing it — through the same normalized entity as the rest of Post's data
cache.writeFragment({
  id: cache.identify({ __typename: "Post", id: "5" }),
  fragment: gql`fragment PostExpand on Post { isExpanded }`,
  data: { __typename: "Post", id: "5", isExpanded: true },
});

Common Mistake

Reaching for client-side schema fields for state that's genuinely local to one component (a form field, a toggle only one component reads) is unnecessary indirection — the decision criterion worth stating is "does this state need to be attached to an already-normalized entity and shared across distant components," not "is this GraphQL-adjacent state in general."

Q48. What are reactive variables (makeVar), and how do they interact with the cache and useQuery re-renders?

ROI: ★★★★☆ Frequency: High

Short Answer

A reactive variable, created with makeVar(initialValue), is a small piece of state that lives outside the normalized cache entirely but can be read from a @client field's read function and, crucially, automatically triggers a re-render of every useQuery that reads it whenever the variable is updated via its setter (myVar(newValue)) — no dispatch, no reducer, no manual subscription wiring. It's Apollo's lightweight answer to "I need a small piece of global-ish state and I don't want to add Redux/Zustand just for this."

Detailed Answer

The mechanism: makeVar returns a function that's both a getter (call it with no arguments) and a setter (call it with a new value). Any InMemoryCache field policy whose read function calls the reactive variable's getter is automatically registered as a dependent of that variable — so calling the setter anywhere in the app (completely outside of any React component, even in a plain event handler or a WebSocket callback) causes every active query reading that field to re-run its read function and re-render with the new value, exactly like a cache write would.

This makes reactive variables genuinely useful for cross-cutting UI state that isn't naturally tied to one specific entity — a "current theme," a "selected locale," a "logged-in user's client-only preferences" — state that previously might have justified pulling in Context or a small global store, but that can instead live in the same reactive graph as the rest of the app's Apollo-backed data, with the same automatic re-render guarantees.

Code Example

import { makeVar, useReactiveVar } from "@apollo/client";

export const themeVar = makeVar<"light" | "dark">("light");

const cache = new InMemoryCache({
  typePolicies: {
    Query: {
      fields: {
        theme: {
          read() {
            return themeVar(); // reading the reactive variable's current value
          },
        },
      },
    },
  },
});

// Anywhere, even outside React — e.g. a settings service
themeVar("dark");

// In a component — re-renders automatically whenever themeVar() changes
function ThemeToggle() {
  const theme = useReactiveVar(themeVar);
  return (
    <button onClick={() => themeVar(theme === "light" ? "dark" : "light")}>
      Current theme: {theme}
    </button>
  );
}

Interview Gold Point

The detail that shows real familiarity: reactive variables can be read and set completely outside of React (a plain module-level function call), yet still trigger correct React re-renders wherever they're consumed — because the reactivity lives in Apollo's cache subscription system, not in React's own state machinery. That's the mechanism that makes them feel like "global state, but free," without wiring up a separate store.

Q49. How do you migrate away from the deprecated local resolvers API to reactive variables plus type policies?

ROI: ★★★☆☆ Frequency: Medium

Short Answer

The old local-resolvers API (a resolvers object passed to ApolloClient, mirroring server-side resolver shape) is replaced field-by-field: each local resolver function becomes a read function in the corresponding type's typePolicies entry, and any piece of state the resolver used to compute from (component-triggered writes via client.writeQuery) becomes a makeVar-backed reactive variable read from inside that read function. The @client directive in queries stays exactly the same — only the implementation backing those fields changes.

Detailed Answer

The main mechanical difference during migration: local resolvers received (parent, args, context, info) like server resolvers and typically wrote results back via imperative cache.writeQuery calls scattered wherever the mutation happened; the type-policy-plus-reactive-variable approach centralizes both the "how do I compute this field's current value" (the read function) and "how do I change it" (the reactive variable's setter, callable from anywhere) into two clearly separated, more testable pieces, rather than one resolver function doing both.

Apollo's own docs frame this as the recommended direction for new code — local resolvers still work and Apollo hasn't removed them, but reactive variables are simpler to reason about (no context/info boilerplate, no need to mimic server-resolver signatures for state that was never going over the network anyway) and are the pattern most current documentation and community examples demonstrate.

Code Example

// OLD: local resolvers
const resolvers = {
  Query: {
    isLoggedIn: () => !!localStorage.getItem("token"),
  },
  Mutation: {
    setLoggedIn: (_, { value }, { cache }) => {
      cache.writeQuery({ query: IS_LOGGED_IN, data: { isLoggedIn: value } });
      return null;
    },
  },
};

// NEW: reactive variable + type policy
export const isLoggedInVar = makeVar(!!localStorage.getItem("token"));

const cache = new InMemoryCache({
  typePolicies: {
    Query: {
      fields: { isLoggedIn: { read: () => isLoggedInVar() } },
    },
  },
});

// Setting it is now just a direct function call, no mutation needed
isLoggedInVar(true);

Common Mistake

Don't claim local resolvers have been "removed" — they're deprecated in guidance/recommendation, not removed from the library. The precise, accurate framing ("still supported, but reactive variables are the recommended direction for new code") is the kind of detail that avoids overstating a fact an interviewer might know is wrong.

Q50. How do you combine remote and local fields in the same query using the @client directive?

ROI: ★★★☆☆ Frequency: Medium

Short Answer

A single query document can freely mix ordinary remote fields with @client-directed local-only fields — Apollo splits the query internally, sends only the non-@client parts to the server, resolves the @client fields locally from cache/type-policy read functions, and stitches both results back into one combined object your component reads normally, with no visible difference in how you consume data.

Detailed Answer

This is genuinely convenient for UI state that's conceptually "attached to" server data — e.g. a cart item's server-provided price/name alongside a purely client-side isSelectedForCheckout flag — since the component doesn't need two separate hooks/queries and two separate loading states to assemble one coherent view; one useQuery call gives back both pieces merged. The loading/error states reported still reflect only the network portion, since local fields resolve synchronously and can't themselves fail at the network layer (though a read function can still throw, which surfaces as a client-side error).

One caveat worth knowing: because the server never sees @client fields at all, there's no schema validation tying them to anything server-side — a typo in a local field name fails silently or produces an unexpected undefined rather than the loud "field doesn't exist on type" error a genuine schema mismatch would produce for a remote field, so local fields benefit even more than remote ones from generated types (Q71) catching mistakes at compile time instead of at runtime.

Code Example

const GET_CART_ITEM = gql`
  query GetCartItem($id: ID!) {
    product(id: $id) {
      id
      name        # remote — fetched from the server
      price       # remote
      isSelected @client   # local-only — resolved from a reactive variable
    }
  }
`;

function CartRow({ id }) {
  const { data } = useQuery(GET_CART_ITEM, { variables: { id } });
  // data.product has BOTH remote and local fields merged into one object
  return (
    <div>
      {data?.product.name} — ${data?.product.price}
      {data?.product.isSelected && " (selected)"}
    </div>
  );
}

Senior Engineer Perspective

The unified-shape benefit is worth naming as the actual payoff: mixing @client and remote fields means a component consuming one merged object doesn't need to know or care which parts came from the network and which came from local state — that boundary is entirely Apollo's concern, not the component's.

Q51. When should you NOT use Apollo local state, preferring Redux/Zustand/useState instead?

ROI: ★★★★☆ Frequency: High

Short Answer

Skip Apollo local state for anything that's genuinely local to one component (form inputs, a modal's open/closed flag) — plain useState is simpler and doesn't need cache/type-policy ceremony. Also skip it if your app has substantial non-GraphQL-related global state (a complex, multi-step wizard's state machine, undo/redo history, offline queueing logic) — forcing that into Apollo's cache-and-reactive-variable model just to have "one state system" adds friction without a corresponding benefit, since Apollo's caching model is optimized around normalized GraphQL entities, not arbitrary application state shapes.

Detailed Answer

The strongest case for Apollo local state is specifically state that's naturally entangled with server data already flowing through Apollo — a UI flag attached to a cached entity, cross-cutting state a few distant components need to read consistently. The moment state either (a) doesn't relate to any GraphQL entity at all, or (b) needs sophisticated update logic (reducers with complex transitions, middleware, time-travel debugging) that a dedicated state library is specifically built for, Apollo's local-state tools are the wrong hammer — reactive variables are intentionally simple (get/set, no reducer pattern, no middleware pipeline) and don't try to replace a full state-management library's feature set.

A useful heuristic to state directly: "if I'd naturally reach for useState or Context for this without GraphQL in the picture at all, I still reach for that even in an Apollo app — Apollo local state is additive tooling for the specific overlap between UI state and cached entities, not a mandate to route all state through the Apollo client."

Interview Favorite

This question rewards restraint over enthusiasm — the strongest answers actively argue for not using a feature they clearly understand, which is a more convincing signal of engineering judgment than describing every feature as broadly applicable. Interviewers specifically probe "when would you NOT use X" questions to filter for exactly this kind of restraint.

Q52. How do reactive variables handle SSR / server-rendering concerns, given they're shared module-level state across requests?

ROI: ★★★☆☆ Frequency: Medium

Short Answer

A reactive variable created with a plain module-level makeVar(initial) call is shared across every request handled by the same server process in an SSR setup — exactly the same class of bug as any other module-level mutable state in a Node server (accidentally leaking one user's data into another concurrent request's render). The fix is the same as for any per-request server state: construct a fresh ApolloClient instance (and therefore fresh reactive variables, since they'd be created inside a per-request factory function) for every incoming request, rather than sharing one client/cache/variable set across the whole server process.

Detailed Answer

This is easy to get wrong specifically because reactive variables are usually introduced in examples as a simple top-level export const themeVar = makeVar(...) — which is perfectly fine for a client-only SPA (one variable, one user, one browser tab) but becomes a cross-request data leak the moment the same module is reused by a long-lived Node server process handling many users' requests concurrently. The correct SSR pattern wraps client (and any reactive variables it depends on) construction in a function called fresh per request, so no state persists between different users' render passes.

This is really a specific instance of a more general SSR principle every experienced engineer should already carry over from other tools: any module-level mutable singleton is a request-isolation hazard in a server context, whether it's a reactive variable, a database connection pool configured incorrectly, or a naive in-memory cache — the fix pattern (factory-per-request instead of shared-module-singleton) is the same regardless of which specific piece of state triggered the question.

Code Example

// WRONG for SSR — one shared variable leaks across concurrent requests
export const userPrefsVar = makeVar(defaultPrefs);

// RIGHT for SSR — fresh client (and fresh reactive variables) per request
export function createApolloClient(req) {
  const userPrefsVar = makeVar(getPrefsFromRequest(req));
  return new ApolloClient({
    ssrMode: true,
    cache: new InMemoryCache({
      typePolicies: {
        Query: { fields: { userPrefs: { read: () => userPrefsVar() } } },
      },
    }),
    link: createHttpLink(req),
  });
}

Common Mistake

Copy-pasting a client-side-only reactive variable example directly into an SSR codebase without recognizing it's now module-level shared state across concurrent requests is a genuinely dangerous, hard-to-catch-in-dev bug (it often only manifests under real concurrent traffic, not local single-request testing) — worth flagging explicitly as an SSR-specific gotcha rather than assuming the client-only pattern transfers unchanged.

Q53. How do you unit test components that read reactive variables?

ROI: ★★★☆☆ Frequency: Medium

Short Answer

Call the reactive variable's setter directly before or during the test to put it into the state you want to assert against — since a reactive variable is just a plain function reference exported from a module, tests can import it directly and call it like any other function, without needing MockedProvider, a cache, or any GraphQL machinery at all, as long as the component under test is wrapped in whatever minimal provider its useReactiveVar/cache reads require.

Detailed Answer

Because reactive variables aren't part of any specific mock/query response, a common mistake is trying to set their value via a MockedProvider mock's result data — that doesn't work, since the variable's value isn't sourced from a query response at all. The straightforward, correct approach is exactly what makes reactive variables simple in the first place: import the variable, call it with the desired test value, render, and assert — then reset it (or use a fresh variable per test if the module supports that) between tests to avoid one test's mutated value leaking into the next, since the variable's underlying value persists across tests within the same module instance unless explicitly reset.

This reset-between-tests concern is a smaller-scale version of the same SSR shared-state hazard from Q52 — a reactive variable used carelessly across tests can leak state between test cases just as it can leak state between concurrent server requests if not scoped/reset correctly.

Code Example

import { render, screen } from "@testing-library/react";
import { themeVar } from "./theme";
import ThemeToggle from "./ThemeToggle";

afterEach(() => {
  themeVar("light"); // reset to avoid leaking state into the next test
});

test("renders the current theme from the reactive variable", () => {
  themeVar("dark"); // set directly — no mock needed at all

  render(
    <MockedProvider mocks={[]}>
      <ThemeToggle />
    </MockedProvider>
  );

  expect(screen.getByText(/dark/i)).toBeInTheDocument();
});

Common Mistake

Trying to seed a reactive variable's value through a MockedProvider mock's result field is a common confusion — reactive variables live outside the query-response system entirely, so the correct approach is calling the variable's setter directly, and remembering to reset it between tests to avoid cross-test leakage.

Q54. How do you persist a reactive variable's value across reloads, e.g. a theme toggle, alongside the Apollo cache?

ROI: ★★★☆☆ Frequency: Medium

Short Answer

Reactive variables aren't part of Apollo's cache persistence story (tools like apollo3-cache-persist only persist the normalized cache, not module-level reactive variable state) — so persisting one across reloads is a manual, two-part job: read the persisted value from localStorage (or wherever) to seed the variable's initial value at module load time, and subscribe to changes (or just call storage-write code alongside every setter call) to keep storage updated whenever the variable changes.

Detailed Answer

A clean pattern wraps the raw makeVar in a small helper that reads an initial value from storage, and wraps the setter so every write also persists to storage — centralizing the persistence concern in one small module rather than scattering "don't forget to also write to localStorage" calls at every call site that updates the variable, which is easy to forget at some call sites and not others as the codebase grows.

This is a good moment to reiterate scope: for genuinely simple, single-value persisted preferences (theme, locale), this lightweight pattern is proportionate. For anything requiring more complex persistence semantics — versioned schema migrations of stored state, selective persistence of only part of a larger state shape — a dedicated state library's persistence middleware (Redux Persist, Zustand's persist middleware) is doing meaningfully more work than this pattern is designed for, which is itself a signal for when reactive variables have been stretched past their intended scope (echoing Q51's broader restraint principle).

Code Example

function makePersistedVar<T>(key: string, initial: T) {
  const stored = localStorage.getItem(key);
  const v = makeVar<T>(stored ? JSON.parse(stored) : initial);

  const set = (value: T) => {
    localStorage.setItem(key, JSON.stringify(value));
    return v(value);
  };

  return [v, set] as const;
}

export const [themeVar, setTheme] = makePersistedVar("theme", "light");

// Component code calls setTheme(...) instead of themeVar(...) directly,
// so persistence can never be accidentally skipped
setTheme("dark");

Senior Engineer Perspective

Wrapping the setter so persistence is baked into the only way to update the value (rather than trusting every call site to remember a separate localStorage.setItem call) is the kind of small API-design discipline that prevents an entire class of "the theme didn't stick after reload, but only sometimes" bugs from ever being introduced.

SECTION 11 - ERROR HANDLING DEEP DIVE

Q55. What are Apollo's errorPolicy options (none, ignore, all) on useQuery/useMutation, and how do they change what lands in data vs error?

ROI: ★★★★★ Frequency: Extremely High

Short Answer

errorPolicy: "none" (the default) treats any GraphQL error as making the whole result an error — data is set to undefined even if some fields technically resolved. "all" gives you both: data retains whatever partial result did resolve, and error is still populated with the GraphQL errors, letting you render the partial success and the error simultaneously (the pattern from Q9). "ignore" discards the errors entirely — error stays undefined, only the partial data is surfaced — appropriate only when you're confident the specific failing fields are non-critical and you don't want to build any UI acknowledging the failure at all.

Detailed Answer

The default ("none") is deliberately conservative — it protects against a component accidentally rendering a partially-populated object as if it were complete, at the cost of throwing away potentially-useful partial data on any error, however minor. This is the right default for most queries, but it's actively wrong for the specific "one nested field failed, the rest of the query is fine and worth showing" scenario from Q9 — for exactly those cases, opting into "all" at the individual query level is the correct, deliberate choice, not a global setting to flip everywhere.

A common mistake is setting errorPolicy: "all" globally via defaultOptions without auditing whether every query in the app is actually prepared to handle a coexisting partial-data-plus-error state correctly — a query that's never been designed with that in mind might render broken or misleading UI from unexpectedly-partial data it now receives instead of cleanly failing into an error state as it did before. The safer rollout is opting in per-query, specifically for queries whose components have been deliberately built to render partial results gracefully.

Code Example

// Opt in per-query, not globally — this component is specifically
// built to render partial data alongside a visible error
const { data, error } = useQuery(GET_USER_WITH_POSTS, {
  errorPolicy: "all",
});

return (
  <div>
    {data?.user?.name && <h1>{data.user.name}</h1>}
    {!data?.user?.posts && error && <p>Couldn't load posts.</p>}
  </div>
);

Interview Gold Point

The distinction worth stating precisely: errorPolicy controls what Apollo hands your component (whether partial data survives an error), while what your component actually does with that partial data is a separate design decision — a lot of candidates conflate "set errorPolicy to all" with "now my partial-data UI automatically works," when the component still needs to be explicitly built to render gracefully around potentially-missing nested fields.

Q56. How do you build a global retry policy for transient network errors using RetryLink?

ROI: ★★★★☆ Frequency: High

Short Answer

RetryLink (from @apollo/client/link/retry) sits in the link chain and automatically retries a failed operation according to configurable delay and attempt-count settings, with an optional predicate function deciding whether a given error is worth retrying at all — typically retrying network-layer failures (timeouts, connection resets) while explicitly not retrying GraphQL-layer errors (a validation error or a permission denial will fail identically no matter how many times you resend it).

Detailed Answer

The critical design decision is the retry predicate: blindly retrying every failure is actively harmful for two categories of error — GraphQL errors that represent a genuine, deterministic failure (retrying won't change the outcome, it just delays the user seeing the real error) and mutations that aren't naturally idempotent (retrying a "create order" mutation after an ambiguous timeout risks creating the order twice if the first attempt actually succeeded server-side but the response was lost in transit). A safe default retry predicate checks specifically for network errors (not GraphQL errors) and, for mutations, ideally only retries operations the backend has explicitly marked or documented as idempotent.

Exponential backoff (rather than fixed-interval retries) is the standard delay strategy, since it reduces load on a struggling backend rather than hammering it with a burst of retries at a fixed interval right when it's already failing. Combining RetryLink with a max-attempts cap and backoff is usually configured once, globally, in the link chain — individual components and mutations don't need to know retry logic exists at all, which is exactly the value of handling this cross-cutting concern at the link layer instead of scattering try/catch-and-retry logic through component code.

Code Example

import { RetryLink } from "@apollo/client/link/retry";

const retryLink = new RetryLink({
  delay: { initial: 300, max: 5000, jitter: true }, // exponential-ish backoff
  attempts: {
    max: 3,
    retryIf: (error, operation) => {
      // Only retry genuine network failures, never GraphQL-layer errors,
      // and skip mutations unless explicitly marked idempotent
      const isNetworkError = !!error && !error.result;
      const isIdempotent = operation.getContext().idempotent === true;
      return isNetworkError && (operation.query.definitions[0].operation !== "mutation" || isIdempotent);
    },
  },
});

const client = new ApolloClient({
  link: ApolloLink.from([retryLink, authLink, httpLink]),
  cache: new InMemoryCache(),
});

Interview Gold Point

The idempotency concern is the detail that separates a naive "just retry on failure" answer from a production-aware one: retrying a non-idempotent mutation after an ambiguous network failure can create duplicate side effects, so a real retry policy needs to know (or be told via context) whether a given operation is actually safe to retry blindly.

Q57. How do you distinguish a GraphQL "not found" business error from a schema/validation error, and how should each be modeled?

ROI: ★★★★☆ Frequency: High

Short Answer

A validation error (malformed query, wrong argument type, unknown field) means the request itself was invalid and typically never even reaches resolver code — it should stay in GraphQL's errors array, since it's a client-code bug, not a business outcome. A business "not found" (the user searched for an order that doesn't exist) is an entirely expected, normal outcome of a valid request and is better modeled as part of the schema's actual type design — a nullable field that resolves to null, or a union/result type explicitly including a "not found" case — rather than as a GraphQL-level error, because it isn't actually exceptional or a client mistake.

Detailed Answer

This distinction matters because GraphQL's errors array is semantically meant for "something went wrong" — a business outcome like "no order matches this id" isn't wrong, it's a valid, fully-expected answer to the question asked, and treating it as an error forces every consumer to write error-handling code for what's really just a normal branch of business logic (the UI equivalent of a REST API returning a 500 for a resource that legitimately doesn't exist, when a 404 — a normal, modeled response — would be correct instead).

Two common, better-typed schema patterns for expected "failure" outcomes: a simply nullable field (order(id: ID!): Order — a null is a completely normal, valid answer meaning "not found," and the client checks for null the same way it'd check any other conditional field) and, for cases with more than one distinct "why didn't this work" outcome, a result union (OrderResult = Order | OrderNotFoundError | OrderAccessDeniedError) that forces the client to explicitly handle each named business outcome via inline fragments, giving richer, more specific information than a bare null while still keeping it entirely inside data rather than the errors array.

Code Example

# Pattern 1: simple nullable field — null IS the expected "not found" answer
type Query {
  order(id: ID!): Order   # no bang — null means "not found", not an error
}

# Pattern 2: explicit result union for richer, distinguishable outcomes
union OrderResult = Order | OrderNotFoundError | OrderAccessDeniedError

type OrderNotFoundError { message: String! }
type OrderAccessDeniedError { message: String! }

type Query {
  orderResult(id: ID!): OrderResult!
}

# Client handles each business outcome as a normal data branch,
# never touching error.graphQLErrors for this at all
query {
  orderResult(id: "5") {
    __typename
    ... on Order { id total }
    ... on OrderNotFoundError { message }
    ... on OrderAccessDeniedError { message }
  }
}

Senior Engineer Perspective

The one-sentence framing that reads as senior: "GraphQL's errors array is for things that went wrong with the request itself, not for expected business outcomes — a 'not found' or 'access denied' that's a normal part of the domain belongs in the schema's type design, not the error channel." This is exactly the kind of schema-design judgment call Q14's pitfalls question is probing for from a different angle.

Q58. How do you handle authentication errors (expired token) globally via the error link, including retrying the original operation after refresh?

ROI: ★★★★★ Frequency: Extremely High

Short Answer

An onError/errorLink checks for an auth-failure signal (a specific error.extensions.code === "UNAUTHENTICATED", or a 401 on the underlying network error) and, when found, triggers a token refresh, then re-executes the original failed operation with the new token by returning a new observable from the link chain (forward(operation) after updating the auth header) — so from the calling component's perspective, the request either eventually succeeds transparently or fails only after a refresh attempt has genuinely also failed, without every individual component needing its own retry-after-refresh logic.

Detailed Answer

The tricky part is concurrency: if five queries fire simultaneously and all hit an expired token at once, a naive implementation would trigger five separate, redundant token-refresh requests. The standard fix is to deduplicate the refresh itself — track an in-flight refresh promise, and have every failing operation await that same promise rather than kicking off its own, so five simultaneous 401s result in exactly one refresh call, with all five original operations retried once it resolves.

After a successful refresh, the retried operation needs its context updated with the new token before being forwarded again — typically by updating whatever the authLink reads from (a module-level variable, a reactive variable) so the retried request picks up the fresh token the normal way, rather than needing special-cased header-injection logic just for the retry path. If the refresh itself fails (refresh token also expired), that's the actual point to redirect to a login screen — not on the first 401, since that would incorrectly log the user out for what might just be a normal, refreshable expiry.

Code Example

import { onError } from "@apollo/client/link/error";
import { fromPromise } from "@apollo/client";

let refreshPromise: Promise<string> | null = null;

function refreshToken() {
  if (!refreshPromise) {
    refreshPromise = fetchNewAccessToken().finally(() => { refreshPromise = null; });
  }
  return refreshPromise; // dedupes concurrent refresh attempts
}

const errorLink = onError(({ graphQLErrors, operation, forward }) => {
  const isAuthError = graphQLErrors?.some((e) => e.extensions?.code === "UNAUTHENTICATED");
  if (!isAuthError) return;

  return fromPromise(
    refreshToken().then((newToken) => {
      operation.setContext(({ headers = {} }) => ({
        headers: { ...headers, authorization: `Bearer ${newToken}` },
      }));
    }).catch(() => {
      redirectToLogin(); // refresh itself failed — genuinely unauthenticated
      throw new Error("Session expired");
    })
  ).flatMap(() => forward(operation)); // retry the original operation
});

Interview Gold Point

Deduplicating concurrent refresh attempts is the detail that most reliably separates a candidate who's implemented this in production from one reciting the general pattern — without it, a page that fires several queries on mount and hits an expired token produces a burst of redundant, race-prone refresh calls, a bug that's easy to miss in development (usually only one or two queries) but very visible under real production load.

Q59. How do error extensions (error.extensions.code) let you build typed, machine-readable error handling instead of string-matching messages?

ROI: ★★★★☆ Frequency: High

Short Answer

The GraphQL spec's errors array entries can include an arbitrary extensions object alongside the human-readable message — by convention, most GraphQL servers (and Apollo Server specifically) populate extensions.code with a stable, machine-readable identifier ("UNAUTHENTICATED", "FORBIDDEN", "BAD_USER_INPUT") that client code should branch on, instead of pattern-matching against the free-text message string, which is meant for humans and can change wording without warning.

Detailed Answer

String-matching error messages (if (error.message.includes("not authorized"))) is a fragile anti-pattern for exactly the reason UI copy changes are considered "safe, non-breaking" changes by most teams — a copywriter or backend engineer rewording an error message for clarity has no reason to know that some frontend code depends on the exact substring, and that dependency is invisible until it silently breaks. extensions.code exists specifically to give client code a contract to depend on that's explicitly meant to be stable, separate from the human-facing message that's explicitly not meant to be a stable contract.

This pairs naturally with the business-error-modeling discussion in Q57 — for errors that genuinely belong in the errors array (auth failures, rate limiting, genuine server faults), a well-designed API documents its set of extensions.code values the same way a REST API documents its status codes, and client error-handling code should be written against that documented code set, never against message text.

Code Example

const errorLink = onError(({ graphQLErrors }) => {
  graphQLErrors?.forEach((err) => {
    switch (err.extensions?.code) {
      case "UNAUTHENTICATED":
        return handleAuthError();
      case "FORBIDDEN":
        return showToast("You don't have permission to do that.");
      case "BAD_USER_INPUT":
        return showToast(`Invalid input: ${err.message}`); // message OK to display, not to match on
      default:
        return logUnexpectedError(err);
    }
  });
});

Common Mistake

Matching against error.message substrings for control flow is a fragile habit worth actively calling out as wrong in an interview, not just avoiding silently — messages are explicitly not a stable API surface, while extensions.code (or an equivalent structured field) is designed to be exactly that.

Q60. How do partial errors interact with fragments — if a fragment's field errors, does it null out just the fragment's fields or affect sibling data too?

ROI: ★★★☆☆ Frequency: Medium

Short Answer

GraphQL's null-propagation rule (from Q2) operates on the response tree, not on fragment boundaries — a fragment is purely a client-side authoring convenience, invisible to how the server nulls out failures. If a non-null field inside a fragment throws, the null propagates up to the nearest nullable ancestor in the actual response shape, which may well include sibling fields selected by a completely different fragment spread at the same level, if that ancestor object itself was marked non-null.

Detailed Answer

Concretely: if Post is a non-null field on Query, and one fragment spread into that Post selection has a non-null field that throws, the entire Post object nulls out in the response — including fields contributed by an entirely unrelated fragment spread at the same level, which had nothing wrong with it. This is a sharp edge worth understanding precisely: fragment composition feels modular at the authoring level (each fragment "owns" its own fields), but null propagation happens at the response-tree level, which doesn't know or care about fragment boundaries at all — it only knows about nullability in the schema.

The practical implication reinforces the nullability-discipline point from Q2 and Q14: composing multiple fragments onto the same object is exactly the scenario where getting nullability defaults right matters most, because a single fragment's overly-strict non-null field can blow away every other fragment's otherwise-successful data at that same level, purely due to schema design, with the fragment authors having no way to see or prevent that interaction from their own file in isolation.

Code Example

# If Post.title is non-null and its resolver throws...
type Post {
  title: String!   # non-null — risky if this resolver can fail
  author: User
}

fragment TitleFields on Post { title }        # written by team A
fragment AuthorFields on Post { author { name } } # written by team B, unrelated

query {
  post(id: "5") {
    ...TitleFields   # this fragment's field throws...
    ...AuthorFields  # ...and this ENTIRELY UNRELATED fragment's data
                      # is lost too, because the null propagates to
                      # the whole `post` object, not just TitleFields
  }
}

Interview Gold Point

The precise fact to state: "fragments are a client-authoring construct; null propagation happens on the actual response tree, which has no concept of fragment boundaries — so one fragment's non-null field failing can take down sibling data contributed by a completely unrelated fragment." This is a genuinely subtle interaction most candidates haven't thought through, and stating it unprompted is a strong signal.

Q61. How would you design a global ErrorBoundary + Apollo error link combination to catch both React render errors and GraphQL errors consistently?

ROI: ★★★★☆ Frequency: High

Short Answer

These two mechanisms cover genuinely different failure classes and don't substitute for each other: a React ErrorBoundary catches JavaScript exceptions thrown during rendering (a component crashing on unexpected data shape, a null-reference bug), while Apollo's error handling (errorPolicy, error link) covers failures that happen at the data-fetching layer before rendering even starts. A robust setup uses both together: the error link/errorPolicy layer for GraphQL/network failures (rendering deliberate, designed error UI), and an ErrorBoundary as the last-resort safety net for anything that still crashes during render — including, notably, a component that mishandles a GraphQL error state and throws while trying to render it.

Detailed Answer

The connective tissue between them is worth naming explicitly: a component that assumes data.user.name is always present, and doesn't check loading/error first (the exact mistake flagged in Q4), throws a real JavaScript exception the moment it tries to read a property off undefined — and that's precisely the kind of error a well-placed ErrorBoundary around GraphQL-data-driven sections of the UI is meant to catch as a safety net, even though the root cause was really a missing GraphQL-layer guard rather than a "real" unexpected crash.

The layered defense worth describing in an interview: deliberate GraphQL error UI (via error/errorPolicy) for the failure modes you've explicitly designed for, and ErrorBoundaries as a blast-radius-limiting safety net for anything that slips through that design — placed at reasonably granular boundaries (per major page section, not just one boundary around the entire app) so one section's unexpected crash doesn't take down the whole page's UI.

Code Example

function PostSection({ id }) {
  return (
    <ErrorBoundary fallback={<p>Something went wrong loading this section.</p>}>
      <PostDetail id={id} />
    </ErrorBoundary>
  );
}

function PostDetail({ id }) {
  const { data, loading, error } = useQuery(GET_POST, { variables: { id } });

  if (loading) return <Spinner />;
  if (error) return <p>Couldn't load this post.</p>; // handled explicitly —
  // never reaches the ErrorBoundary for this expected case

  return <article>{data.post.title}</article>; // ErrorBoundary is the safety
  // net if this line throws for some unforeseen reason
}

Senior Engineer Perspective

Frame the two mechanisms by what they're each responsible for, not as interchangeable "error handling": "GraphQL error handling is for failures I've designed for and want specific UI for; ErrorBoundaries are the safety net for failures I haven't specifically designed for — a well-built app leans heavily on the first and rarely needs the second to actually fire in practice."

Q62. What are common mistakes teams make when swallowing GraphQL errors silently, and how do you catch that in code review?

ROI: ★★★★☆ Frequency: High

Short Answer

The most common silent-swallow pattern: a component checks if (loading) return ... but never checks error at all, so a failed query simply renders as if data were empty/default (an empty list, a missing section) with zero indication to the user or to logs/monitoring that anything went wrong — the UI looks "fine" but is quietly wrong. A close second: an onError handler that only logs to the console (invisible in production) without also surfacing anything user-facing or reporting to an error-tracking service, so failures are technically "handled" in code but functionally invisible to everyone who'd need to know about them.

Detailed Answer

In code review, the concrete thing to check for on every useQuery/useMutation call: is error either explicitly checked and rendered, or explicitly and deliberately ignored with a comment explaining why ignoring it is safe for this specific case (genuinely optional, non-critical data) — an unconsidered absence of any error handling at all should read as a gap, not a stylistic choice. The same applies to onError callbacks on mutations: logging to console.error alone is a reasonable addition to, but not a replacement for, both user-facing feedback and integration with whatever error-monitoring tool (Sentry, Datadog) the team already uses for visibility into production failures.

A useful team-level practice beyond individual code review: centralizing error reporting in the errorLink (Q9, Q56, Q58) means every GraphQL error gets reported to monitoring exactly once, regardless of whether any individual component remembered to add its own reporting call — shifting "did we forget to log this error" from a per-component discipline problem to a solved, structural one. Components are then free to focus purely on user-facing error UI, since the systemic visibility concern is already handled upstream.

Code Example

// Silent-swallow smell — no error check at all
function BadExample() {
  const { data, loading } = useQuery(GET_ITEMS);
  if (loading) return <Spinner />;
  return <List items={data?.items ?? []} />; // fails silently as "empty list"
}

// Explicit, reviewable handling
function GoodExample() {
  const { data, loading, error } = useQuery(GET_ITEMS);
  if (loading) return <Spinner />;
  if (error) return <ErrorBanner message="Couldn't load items." />; // visible, deliberate
  return <List items={data.items} />;
}

// Centralized reporting — every GraphQL error reaches monitoring
// exactly once, regardless of component-level diligence
const errorLink = onError(({ graphQLErrors, networkError, operation }) => {
  Sentry.captureException(networkError ?? graphQLErrors?.[0], {
    extra: { operationName: operation.operationName },
  });
});

Interview Gold Point

Naming the specific code-review checklist item — "does every query/mutation either handle error explicitly or have a comment justifying why it's safe to ignore" — is concrete, actionable, and shows this isn't abstract knowledge but something you'd actually enforce day to day. Pairing it with "centralize reporting in the error link so visibility doesn't depend on every component remembering" completes the answer with both a review practice and a structural fix.

Q63. How do you handle reconnection and message replay/gap-filling when a WebSocket subscription drops and reconnects?

ROI: ★★★★☆ Frequency: High

Short Answer

graphql-ws's client handles the raw reconnect (retrying the socket connection with backoff) automatically, but reconnecting the socket does not automatically recover events that were published while the connection was down — a subscription is a live stream, not a durable queue, so anything the server pushed during the gap is simply missed unless you explicitly account for it. The standard mitigation is to re-fetch a fresh snapshot via a regular query immediately after reconnection (rather than trusting the subscription alone to have a complete picture), effectively treating "reconnected" the same as "just mounted."

Detailed Answer

This is a fundamental property of most subscription transports, not a configuration mistake — GraphQL subscriptions over WebSocket are push-based and ephemeral, with no built-in replay/offset mechanism the way something like Kafka or a message queue would have. Some backends layer their own gap-recovery on top (a "give me everything since sequence number N" resync query, or a subscription payload that includes enough context for the client to detect it missed something), but that's an application-level design choice, not something GraphQL subscriptions provide out of the box.

Practically, the safe pattern is: on the subscription hook's connection-status change (or the WS client's own reconnect event), trigger a refetch() of whatever regular query represents the "current state" this subscription is meant to keep live — so a dropped connection results in, at worst, a brief gap in live updates followed by a full resync, rather than a permanently stale, silently-incomplete view that looks fine but has quietly missed data.

Code Example

import { createClient } from "graphql-ws";

const wsClient = createClient({
  url: "wss://api.example.com/graphql",
  retryAttempts: Infinity,
  on: {
    connected: () => {
      // Fires on initial connect AND every reconnect —
      // treat both the same: resync from a source of truth
      refetchCurrentState();
    },
  },
});

function refetchCurrentState() {
  apolloClient.refetchQueries({ include: ["GetLiveOrderStatus"] });
}

Interview Gold Point

The precise fact worth stating: "a reconnected WebSocket doesn't imply a complete event history — subscriptions are a live stream, not a durable log, so any real-time feature needs an explicit resync-on-reconnect strategy, not just reconnection logic for the socket itself." This distinction between "connection recovered" and "data recovered" is exactly the kind of nuance production real-time features have to account for.

Q64. How do you merge a subscription push into a paginated list without duplicating items already fetched via fetchMore?

ROI: ★★★★☆ Frequency: High

Short Answer

Same dedupe discipline as Q32's overlapping-pages problem: before appending a subscription-pushed item into a cached paginated list, check whether an item with that id is already present (the item might have arrived via a regular page fetch moments before the subscription push for the same event landed), and skip the insert if so. This is most robustly handled inside the same cache.modify/merge-based update logic used for the rest of the list's mutations, rather than as separate, parallel logic living only in the subscription's onData handler.

Detailed Answer

The overlap risk here is genuinely likely, not a rare edge case: a client that both polls/paginates a list AND subscribes to "new item added" events for that same list will very plausibly receive the same new item from both channels — a fast page-2 fetch might already include an item that also triggers a subscription push moments later, or vice versa, depending on exact timing. Treating both the mutation's own optimistic/update-function insert and the subscription's push-triggered insert as going through one shared "insert this item into the list, if not already present" helper function keeps the dedupe logic in exactly one place instead of duplicating (and potentially inconsistently implementing) it in two.

This is a good example of why designing the cache update logic around the entity and the list field (via cache.modify) rather than around "the mutation" or "the subscription" specifically pays off — the actual invariant you want ("this list contains each item exactly once, regardless of how it arrived") doesn't care which code path triggered the insert.

Code Example

function insertPostIfAbsent(cache, newPost) {
  cache.modify({
    fields: {
      posts(existingRefs = [], { readField }) {
        const alreadyPresent = existingRefs.some(
          (ref) => readField("id", ref) === newPost.id
        );
        if (alreadyPresent) return existingRefs;
        const newRef = cache.writeFragment({
          data: newPost,
          fragment: gql`fragment NewPost on Post { id title }`,
        });
        return [...existingRefs, newRef];
      },
    },
  });
}

// Called identically from a mutation's update() AND a subscription's onData
useSubscription(POST_CREATED, {
  onData: ({ client, data }) => insertPostIfAbsent(client.cache, data.data.postCreated),
});

Senior Engineer Perspective

The reusable design principle: write cache-mutation logic against the invariant you actually want ("no duplicates in this list, regardless of source"), and call that same logic from every code path that can insert into the list — mutations, subscriptions, or fetchMore — rather than writing per-trigger insert logic that each has to separately remember to dedupe correctly.

Q65. How do you authenticate a WebSocket subscription connection (connectionParams) vs an HTTP query, and why is it different?

ROI: ★★★★☆ Frequency: High

Short Answer

HTTP requests (queries/mutations) authenticate per-request via headers, which authLink attaches fresh on every call. A WebSocket connection authenticates once, at connection-establishment time, via connectionParams passed to graphql-ws's createClient — there's no per-message header mechanism in the WebSocket protocol the way there is for HTTP, so the server must validate auth during the connection handshake and then trust that connection for its entire lifetime (or implement its own in-band token-refresh message protocol on top of the raw WebSocket, which is a real added complexity most simple setups skip).

Detailed Answer

This creates a real operational gap worth naming: if a user's access token expires while a WebSocket connection is still open, the connection typically keeps working (since re-validation only happened at connect time) until it's closed and reconnected for some other reason — unlike HTTP requests, which would immediately start failing with a 401 on the very next call once a token expires. Some teams accept this gap as low-risk (a subscription connection naturally cycles often enough, or the data it streams isn't sensitive enough to warrant tighter enforcement); others implement a server-side connection-lifetime cap (force-closing sockets after N minutes regardless of activity) specifically to bound how long an expired-but-still-open connection can keep streaming data.

connectionParams itself can be a static object or a function re-evaluated on each (re)connection attempt — using a function is important if the token can change during the app's lifetime (a refresh happened since the last connection), since a static object captured once at client-construction time would keep sending a stale token on every reconnect attempt indefinitely.

Code Example

import { createClient } from "graphql-ws";

const wsClient = createClient({
  url: "wss://api.example.com/graphql",
  connectionParams: () => ({
    // A function, not a static object — re-evaluated on every
    // (re)connect attempt, so it always sends the CURRENT token
    authorization: `Bearer ${getCurrentAccessToken()}`,
  }),
});

Interview Gold Point

The "connectionParams should be a function, not a static object" detail is a small but very concrete, easy-to-verify fact that separates a candidate who's actually wired up WS auth in production from one who's only read the happy-path example — a static object silently sends a stale token forever after the first token refresh, a bug that only manifests hours into a session.

Q66. What's the difference between "live queries" (polling-based re-execution) and true subscriptions, and when is polling actually the better choice?

ROI: ★★★★☆ Frequency: High

Short Answer

A "live query" (via pollInterval) re-runs the same request on a timer and diffs the result against the cache, giving eventually-consistent freshness bounded by the poll interval — simple, uses ordinary HTTP, but has an inherent latency floor (you'll never see an update faster than the poll interval) and issues requests even when nothing has changed. A true subscription pushes data the instant an event fires, with effectively no latency floor, but requires a persistent connection, server-side pub/sub infrastructure, and more moving parts to build, deploy, and scale.

Detailed Answer

Polling is frequently the better engineering choice specifically because it's simpler, not despite it — for a dashboard that's acceptable to be "up to 10 seconds stale," a pollInterval: 10000 is far less infrastructure to build, operate, and debug than a WebSocket subscription server, and it degrades gracefully (a missed poll just means the next one catches up, with none of the reconnection/gap-filling complexity from Q63). Subscriptions earn their added complexity specifically for genuinely latency-sensitive, event-driven UX — live chat, collaborative cursors, real-time bidding — where even a few seconds of staleness is a materially worse user experience, not just a mild inconvenience.

A useful interview framing: treat "should this be a subscription or a poll" as a cost-benefit question, not a "subscriptions are the more advanced/correct choice" assumption — the honest engineering answer is that polling is usually the pragmatic default, and subscriptions are reached for only when the specific UX genuinely can't tolerate the latency floor polling imposes. Teams sometimes overbuild subscription infrastructure for features that would have been perfectly well served by a 5-second poll, at a real ongoing infrastructure and complexity cost.

Q67. How do you handle subscription fan-out cost at scale (many clients, few events) — the server-side considerations a frontend engineer should still know?

ROI: ★★★☆☆ Frequency: Medium

Short Answer

Fan-out cost is the cost of delivering one server-side event to potentially thousands of subscribed clients simultaneously — each open WebSocket connection consumes server memory/resources just by existing, and a single event that needs to reach many subscribers requires the server's pub/sub layer to actually deliver it to every one of those connections, which doesn't scale for free just because subscriptions "feel" lightweight from the client's point of view. This is the same client-triggers-server-cost relationship as N+1 (Q11): the client's decision to subscribe to something has a real, sometimes-significant server-side cost that the client-side code itself never has to think about unless it's specifically informed of it.

Detailed Answer

The specific pattern worth being aware of as a frontend engineer, even without implementing the server side: subscribing too granularly (e.g. a separate subscription per individual chat message thread across an app with millions of threads) multiplies the number of live connections and the routing complexity the pub/sub backend has to maintain, versus subscribing more coarsely (one subscription per user's "inbox," server-side filtering to the relevant threads) and letting the client filter further if needed. This granularity decision is genuinely a client-and-server co-design question — the client's subscription shape directly determines the server's fan-out topology, the same way a client's query shape determines resolver fan-out in the N+1 case.

For an interview, the useful posture is the same one from Q11: you're not implementing the pub/sub infrastructure, but understanding that subscription granularity has real server cost lets you ask better questions when designing a real-time feature ("should this be one subscription per user, or one per item they're viewing?") instead of reflexively subscribing at the most granular level that happens to be convenient client-side.

Common Mistake

Treating subscriptions as a free, purely client-side concern is the mistake to avoid — the honest answer acknowledges you don't own the backend's pub/sub scaling, but that doesn't mean the client's subscription design choices are cost-free; granularity decisions made client-side directly shape the server's fan-out burden.

Q68. How do you test components using useSubscription, mocking push events over time?

ROI: ★★★☆☆ Frequency: Medium

Short Answer

MockedProvider supports subscription mocks the same way it supports query mocks, but with a key difference: you can supply an array of results (or a generator) for a single subscription mock, and the mocked link delivers them one at a time as if they were separate pushes — letting a test assert on the component's rendered state after each individual push, not just after "the subscription eventually fired once."

Detailed Answer

Because a real subscription can push many times over its lifetime, a thorough test typically wants to verify the component handles a sequence of pushes correctly — that a second push correctly merges with (rather than replaces) whatever the first push already inserted, mirroring exactly the dedupe/merge logic from Q64 that would otherwise only be exercised by real, hard-to-reproduce production traffic timing. Testing Library's act() combined with awaiting each mocked push resolving lets a test drive the component through multiple discrete "the subscription just fired again" states deterministically.

A subtlety worth handling in test setup: subscriptions don't naturally "complete" the way a query resolves once — a mocked subscription observable needs to either explicitly signal it won't push again, or the test needs to avoid asserting on "did it ever stop," since a real subscription simply stays open indefinitely until the component unmounts.

Code Example

const mocks = [
  {
    request: { query: NEW_MESSAGE, variables: { chatId: "1" } },
    result: { data: { messageAdded: { id: "m1", text: "Hello" } } },
  },
  // A second entry with the SAME request simulates a second push,
  // consumed by MockedProvider in order
  {
    request: { query: NEW_MESSAGE, variables: { chatId: "1" } },
    result: { data: { messageAdded: { id: "m2", text: "World" } } },
  },
];

test("renders each subscription push as it arrives", async () => {
  render(
    <MockedProvider mocks={mocks}>
      <ChatWindow chatId="1" />
    </MockedProvider>
  );

  expect(await screen.findByText("Hello")).toBeInTheDocument();
  expect(await screen.findByText("World")).toBeInTheDocument();
});

Interview Favorite

Testing a sequence of pushes, not just a single mocked event, is the detail that actually exercises the merge/dedupe logic a real subscription feature depends on — a test that only ever mocks one push can pass even if the component would double-insert or overwrite on a second push, which is exactly the bug most likely to show up in production under real, repeated event traffic.

Q69. How do you unsubscribe/cleanup properly to avoid leaking WebSocket connections across route changes?

ROI: ★★★★☆ Frequency: High

Short Answer

useSubscription automatically unsubscribes when the component unmounts — that part is handled for you by the hook's own cleanup effect. What's easy to get wrong is the underlying WebSocket connection itself: if the last active subscription on a socket ends, graphql-ws's client will close the socket by default (after a configurable idle delay), but a badly structured app that keeps re-creating subscriptions on routes that shouldn't need one, or subscribes at a component level far broader than necessary (e.g. at the app root instead of the specific page that needs it), can end up holding a connection open far longer than the feature actually requires.

Detailed Answer

The practical guidance: place useSubscription calls as close as possible to the component that actually needs the live data, not hoisted up to a layout or app-root component "for convenience" — hoisting keeps the subscription (and its underlying socket activity) alive for the entire time that ancestor is mounted, which in a typical SPA layout is the entire session, regardless of whether the user ever navigates to the page that actually cares about that data. Scoping subscriptions to the specific page/component keeps the connection's lifetime naturally tied to when the feature is actually in view.

Also worth checking explicitly: whether the WS client's lazy option is enabled (it typically is by default) — a lazy client doesn't open the socket at all until the first subscription actually starts, and closes it again once the last one ends (subject to a configurable keep-alive delay), so a properly lazy, properly-scoped setup naturally avoids holding an idle connection open when nothing on the current screen actually needs it.

Code Example

// Scoped to the specific page that needs it — not hoisted to a layout
function ChatPage({ chatId }) {
  // Subscription lifetime is naturally tied to this page being mounted
  const { data } = useSubscription(NEW_MESSAGE, { variables: { chatId } });
  return <ChatWindow messages={data} />;
}

const wsClient = createClient({
  url: "wss://api.example.com/graphql",
  lazy: true,          // don't open the socket until first subscribed
  keepAlive: 10_000,    // ping interval to detect dead connections
});

Common Mistake

Hoisting a subscription to a layout/root component "so it's always available" is a common but costly convenience — it turns a feature-scoped concern into an app-lifetime one, keeping a socket connection open for the entire session regardless of whether the user is anywhere near the feature that needs it.

Q70. How do you combine a subscription with an initial query (subscribe-then-merge) instead of relying on the subscription alone for initial state?

ROI: ★★★★☆ Frequency: High

Short Answer

A subscription only delivers events that fire after it connects — it has no memory of anything that happened before the client subscribed, so relying on it alone for a screen's initial state means the UI starts genuinely empty until the first live event happens to arrive, which could be seconds or hours. The standard pattern is: fire a normal useQuery to fetch the current state immediately on mount, and run useSubscription alongside it purely to receive and merge in updates after that initial snapshot — never using the subscription as the sole source of the first render's data.

Detailed Answer

This is closely related to the reconnection-resync pattern from Q63 — in both cases, a subscription is treated as strictly additive to a separately-established source of truth (the initial query result, or a post-reconnect refetch), never as a complete, self-sufficient state source on its own. The mental model worth internalizing: subscriptions answer "what's changed since I started listening," and a regular query answers "what's the current state right now" — a real-time feature needs both questions answered, and conflating them (expecting the subscription to also answer the second question) is the root cause of a large fraction of "the screen was empty until something happened" bugs in subscription-based features.

The merge logic itself (Q64's dedupe-aware insert) needs to handle the moment the initial query result and the subscription's onData handler are both active — a message that arrives via the subscription microseconds after the initial query already fetched an overlapping data set needs the same "is this already present" check either way.

Code Example

function ChatWindow({ chatId }) {
  const { data: initial } = useQuery(GET_MESSAGES, { variables: { chatId } });

  useSubscription(NEW_MESSAGE, {
    variables: { chatId },
    onData: ({ client, data }) =>
      insertMessageIfAbsent(client.cache, chatId, data.data.messageAdded),
  });

  // `initial` (from the query) establishes the baseline; the subscription
  // only ever adds to it via cache writes — never replaces it wholesale
  return <MessageList messages={initial?.messages ?? []} />;
}

Interview Gold Point

The two-questions framing — "a query answers 'what's the state now,' a subscription answers 'what's changed since I started listening'" — is a clean, memorable way to explain why every real production real-time feature pairs a subscription with an initial query, and it directly explains the otherwise-confusing symptom of a real-time screen appearing empty until something happens to occur after the user opens it.

SECTION 13 - GRAPHQL CODEGEN & TYPE SAFETY

Q71. What does GraphQL Code Generator do, and what's the practical payoff of typed hooks over untyped gql template literals?

ROI: ★★★★★ Frequency: Extremely High

Short Answer

GraphQL Code Generator reads your schema plus every gql query/mutation/subscription document in your codebase and generates matching TypeScript types — and, with the React/Apollo plugin, fully-typed useXQuery/useXMutation hooks — so data, variables, and mutation inputs are all statically typed to exactly what that specific operation actually requests, instead of an untyped/loosely-typed any that a raw gql template literal plus a generic useQuery<any> call would otherwise give you.

Detailed Answer

Without codegen, a query written as a plain gql template literal carries no compile-time connection to the schema at all — TypeScript has no way to know what data.user.name actually resolves to unless you manually write and maintain a matching interface yourself, which drifts out of sync with the actual query text the moment either one changes without the other being updated to match. Codegen closes that gap completely: the generated types are derived mechanically from the query text and schema, so they're always accurate by construction, and any mismatch between a query and the schema becomes a build-time TypeScript error instead of a runtime "why is this field undefined" surprise (elaborated further in Q73).

The generated typed hooks also eliminate an entire class of copy-paste mistakes — passing a query document into the wrong generic type parameter, or manually specifying a variables shape that's subtly wrong — since the hook itself is generated already bound to the correct query and correct variable/return types, with no manual wiring required at each call site.

Code Example

# codegen.yml
schema: https://api.example.com/graphql
documents: "src/**/*.tsx"
generates:
  src/gql/:
    preset: client
    plugins: []

// Before codegen — no compile-time connection to the schema at all
const GET_USER = gql`query GetUser($id: ID!) { user(id: $id) { name } }`;
const { data } = useQuery(GET_USER, { variables: { id: "1" } }); // data: any

// After codegen — generated, fully-typed hook
import { useGetUserQuery } from "./gql/graphql";
const { data } = useGetUserQuery({ variables: { id: "1" } });
// data?.user?.name is now a real, checked `string` — or a compile
// error if the query is changed to no longer select `name`

Interview Gold Point

The strongest framing: "codegen turns 'is my query still valid against the schema' from a runtime discovery into a build-time guarantee." That one sentence captures the entire value proposition and is exactly the kind of high-signal, compressed answer interviewers reward for a topic that could otherwise turn into a long tooling-configuration ramble.

Q72. How do you set up codegen for React + Apollo (client preset) in a monorepo with a shared schema?

ROI: ★★★★☆ Frequency: High

Short Answer

The client preset is the current recommended configuration for React/Apollo projects — it generates a single graphql() function (rather than one hook per operation) that you call with your query text, returning a fully-typed document you pass straight into useQuery/useMutation, plus it enables fragment masking by default. In a monorepo, the schema is typically pointed at a shared .graphql SDL file (or introspected from a running dev server / schema registry) that every package's codegen config references, so every app package generates types against the exact same schema source of truth rather than each maintaining its own possibly-drifted copy.

Detailed Answer

The practical monorepo pattern: a shared codegen.yml (or a shared base config each package extends) points schema: at one canonical location — often a committed SDL file kept in sync via a CI check against the actual running server (Q75), rather than every package independently introspecting a live server, which would be fragile in CI and slower in local dev. Each package's documents: glob then only scans that package's own source files, so codegen runs are scoped and fast, while all packages share one schema truth.

The client preset specifically differs from the older typescript-react-apollo plugin (which generates one named hook per operation, e.g. useGetUserQuery) by generating a single, more flexible graphql() tag function used inline — a deliberate design choice by the GraphQL Code Generator team to better support fragment masking and colocation patterns, at the cost of slightly less "IDE-discoverable" named hooks. Both approaches are actively used in real codebases; the choice is largely about whether fragment masking (Q24, Q76) is a priority for the team.

Code Example

# codegen.ts — shared across a monorepo's packages
import { CodegenConfig } from "@graphql-codegen/cli";

const config: CodegenConfig = {
  schema: "../../schema.graphql", // one canonical schema source
  documents: ["src/**/*.tsx"],     // scoped per-package
  generates: {
    "./src/gql/": {
      preset: "client",
      presetConfig: { fragmentMasking: true },
    },
  },
};
export default config;

Common Mistake

Letting each package in a monorepo introspect its own copy of a live dev server for its schema (instead of sharing one committed SDL file) invites subtle drift — one package generating types against a slightly newer or older running instance than another. Centralizing on one committed schema file, kept in sync via CI, avoids that entire category of "types don't match between packages" confusion.

Q73. How does codegen catch a query mismatch — a field renamed or removed on the schema — at build time instead of at runtime?

ROI: ★★★★★ Frequency: Extremely High

Short Answer

Codegen validates every query/mutation document against the schema as part of generating types — if a query selects a field that no longer exists (renamed, removed, or its type changed incompatibly), codegen itself fails with a clear validation error naming the exact offending field and location, before any application code even runs. This converts "a field was silently renamed on the backend and some screen quietly broke in production" into "the build fails immediately, pointing at exactly which query and field are now invalid."

Detailed Answer

Without codegen, a renamed field is often invisible until either a human notices broken UI, or (in the worst case) the field's old name simply resolves to undefined at runtime with no error at all — GraphQL's response for a field that doesn't exist on the schema is a hard error only if you actually send that invalid query to the server, but plenty of real bugs come from typo'd or renamed local field references inside component code that never gets re-validated against the live query text until codegen (or a runtime error) catches it.

This validation-at-build-time property is exactly why running codegen as a required CI step (not just a local dev convenience) matters — a developer who forgets to run codegen locally after a schema change would otherwise ship code that compiles against stale generated types and only breaks once it actually talks to the updated live schema, which is precisely the gap Q75's "fail the build if generated output is stale" CI check is designed to close.

Code Example

# Schema changes: `name` renamed to `fullName` on User
type User {
  id: ID!
  fullName: String!   # was `name`
}

# Existing query, unchanged:
query GetUser($id: ID!) {
  user(id: $id) {
    name   # codegen fails here — "Cannot query field 'name' on type 'User'.
           # Did you mean 'fullName'?" — caught at build time, not in prod
  }
}

Interview Gold Point

The concrete before/after story — "a renamed field either silently breaks in production with no error, or fails the build immediately with codegen naming the exact field" — is the single clearest, most persuasive argument for adopting codegen, and it's worth having ready as a specific example rather than an abstract "type safety is good" statement.

Q74. What's the difference between codegen's "typed document node" approach and separately generated React hooks?

ROI: ★★★☆☆ Frequency: Medium

Short Answer

A typed document node is a DocumentNode (the same runtime object gql normally produces) with TypeScript type parameters attached (TypedDocumentNode<ResultType, VariablesType>) — it carries type information but is framework-agnostic, so it plugs into useQuery, a manual client.query() call, or any other GraphQL client's API that accepts a document, all inferring the correct types automatically from the document itself. Separately generated hooks (useGetUserQuery) bake the operation directly into a ready-to-call React hook, which is more convenient at the call site but ties the generated artifact specifically to React/Apollo's hook API.

Detailed Answer

The typed-document-node approach (which the client preset's graphql() function produces) is the more portable choice — the exact same generated document works whether you're calling it from a React component via useQuery, from a non-React script via client.query(), or even from a different GraphQL client library entirely that happens to also understand TypedDocumentNode's type-parameter convention (several client libraries, including Apollo and urql, support this pattern). Generated per-operation hooks are less portable (they assume you're using Apollo's specific hook API) but arguably nicer at a React call site, since there's no need to separately import both a document and a generic hook and wire them together yourself.

Neither is strictly "more correct" — it's a trade-off between call-site convenience (generated hooks) and portability/flexibility (typed document nodes), and the choice often comes down to whether the team anticipates using the generated operations outside of React/Apollo hook call sites at all, or plans to eventually support fragment masking, which the client preset's document-node approach was specifically designed around.

Code Example

// Typed document node — portable across client.query(), useQuery(), etc.
const GetUserDocument: TypedDocumentNode<GetUserQuery, GetUserQueryVariables> =
  graphql(`query GetUser($id: ID!) { user(id: $id) { name } }`);

useQuery(GetUserDocument, { variables: { id: "1" } }); // types inferred automatically

// Generated per-operation hook — React/Apollo-specific, ready to call
const { data } = useGetUserQuery({ variables: { id: "1" } });

Senior Engineer Perspective

Framing this as portability-vs-convenience, rather than one approach being objectively better, signals awareness that tooling choices in this space are genuinely trade-offs tied to a team's specific priorities (fragment masking adoption, multi-client-library flexibility) rather than a settled "best practice" with one universally correct answer.

Q75. How do you keep generated types in sync in CI — failing the build if generated output is stale vs the schema/queries?

ROI: ★★★★☆ Frequency: High

Short Answer

The standard CI check regenerates the codegen output fresh in the CI environment and then diffs it against whatever was actually committed to the repository — if there's any difference, the build fails with a message telling the developer to run codegen locally and commit the result. This ensures the committed generated files (which the rest of the codebase imports and type-checks against) can never silently drift out of sync with the current schema and query documents.

Detailed Answer

Committing generated files at all (rather than generating them fresh on every build) is itself a deliberate choice most teams make for two reasons: faster CI builds (no need to introspect a schema and regenerate on every run just to type-check), and so that a PR's diff visibly shows exactly what generated-type changes a given code change produced, which is useful context during review. The trade-off is exactly the staleness risk this CI check exists to close — committed generated files can rot if a contributor edits a query or the schema changes and they forget to regenerate before committing.

The check itself is mechanically simple and cheap to add: run the codegen command, then git diff --exit-code (or equivalent) against the generated output directory — a non-zero diff means someone forgot to regenerate, and the build should fail loudly with a clear, actionable message rather than letting stale types silently ship and only surface as a confusing type error (or worse, a silent runtime mismatch) somewhere downstream.

Code Example

# .github/workflows/ci.yml
- name: Check generated GraphQL types are up to date
  run: |
    npm run codegen
    git diff --exit-code -- src/gql/ || (
      echo "Generated types are stale — run 'npm run codegen' and commit the result." && exit 1
    )

Interview Gold Point

Naming the specific mechanism — "regenerate in CI, diff against what's committed, fail if they differ" — rather than a vague "we make sure types stay in sync" is a concrete, verifiable detail that shows you've actually set this up rather than described it in the abstract.

Q76. How do you handle codegen for fragments with fragment masking types — the opaque FragmentType wrapper?

ROI: ★★★☆☆ Frequency: Medium

Short Answer

With masking enabled, codegen generates each fragment's consumer-facing type as an opaque FragmentType<typeof MyFragment> rather than a plain object type with the fragment's fields directly accessible — a component receiving this opaque type must call the generated useFragment helper to "unmask" it into the actual field-accessible shape, which only exposes exactly the fields that specific fragment declared (enforcing the boundary from Q24 at the type level, not just as a convention).

Detailed Answer

This changes how you type component props: instead of a prop typed as the fragment's result shape directly, it's typed as FragmentType<typeof USER_CARD_FRAGMENT> — an opaque reference that carries the type information needed to unmask it, but doesn't itself expose any fields to read. Inside the component, useFragment(USER_CARD_FRAGMENT, propRef) performs the actual unmasking and returns the genuinely field-accessible object, at which point (and only at which point) property access on it type-checks normally.

The main adjustment teams need to make when adopting masking via codegen: props and function signatures throughout the fragment-consuming tree need updating to pass the opaque FragmentType reference through (not the unmasked object) until it reaches the component that actually owns and unmasks that specific fragment — parent components that only pass fragment data further down the tree should never unmask it themselves, since doing so would let them "see" fields that belong to a descendant's fragment, defeating the purpose of masking.

Code Example

// UserCard.tsx
const USER_CARD_FRAGMENT = graphql(`
  fragment UserCardFields on User { id name avatarUrl }
`);

function UserCard(props: { userRef: FragmentType<typeof USER_CARD_FRAGMENT> }) {
  const user = useFragment(USER_CARD_FRAGMENT, props.userRef); // unmask HERE, at the owning component
  return <div>{user.name}</div>;
}

// Dashboard.tsx — passes the opaque ref through WITHOUT unmasking it itself
function Dashboard({ data }) {
  return <UserCard userRef={data.currentUser} />; // data.currentUser is opaque here
}

Common Mistake

Unmasking a fragment reference in an intermediate component "just to pass the data down more conveniently" defeats the entire purpose of masking — the discipline is that only the component that owns a given fragment should ever call useFragment on it; every intermediate component should pass the opaque reference straight through untouched.

Q77. What are the tradeoffs of codegen-driven development vs a schema-first / contract-first approach with manually written types?

ROI: ★★★☆☆ Frequency: Medium

Short Answer

Codegen-driven development derives client types mechanically from the schema and your actual query documents — always accurate, zero manual maintenance, but requires a codegen step in the toolchain and produces generated files that are sometimes awkward to read directly during debugging. Manually written types (hand-authored interfaces matching what you expect the API to return) require no tooling step and can be written before a real schema even exists (useful for contract-first API design, mocking against an agreed-upon shape before the backend is built) — but they can silently drift from the real schema over time, with nothing to automatically catch the mismatch the way codegen's build-time validation does (Q73).

Detailed Answer

These approaches aren't mutually exclusive across a project's lifecycle: a contract-first phase (hand-authoring an expected shape, mocking against it, aligning frontend and backend teams on an agreed API before either side has fully built their part) is a reasonable and common way to unblock parallel frontend/backend development early in a feature's life — and then switching to codegen once a real schema exists gets you the ongoing accuracy guarantee without needing to keep hand-maintaining types as the schema stabilizes and evolves.

The tooling cost of codegen (a build step, generated files to review in diffs, a slight ramp-up learning the masking/preset conventions) is a real, non-zero cost worth naming honestly rather than presenting codegen as a free upgrade — for a very small project, or a short-lived prototype where the schema is expected to change constantly and types would be regenerated dozens of times a day anyway, hand-written loose types might genuinely be the pragmatic choice, at least temporarily.

Senior Engineer Perspective

The balanced, experience-signaling answer names both a real benefit and a real cost of codegen rather than treating it as an unconditional best practice: "codegen removes an entire class of drift bugs, but it's a genuine tooling investment — I still think it's worth it for anything beyond a short-lived prototype, but I wouldn't present it as free."

Q78. How do you generate types for GraphQL scalars that aren't part of the default scalar set, e.g. DateTime or JSON?

ROI: ★★★☆☆ Frequency: Medium

Short Answer

GraphQL's built-in scalars (String, Int, Float, Boolean, ID) map to obvious TypeScript primitives automatically, but a custom scalar (DateTime, JSON, Upload) has no default mapping codegen can infer — without configuration it falls back to any, quietly reintroducing the exact type-safety gap codegen exists to close. You explicitly configure a scalars mapping in the codegen config, telling it which TypeScript type each custom scalar should generate as (a DateTime scalar is commonly mapped to string, since that's what actually crosses the wire in JSON — the ISO-8601-formatted value — even though your application code might parse it into a real Date object after receiving it).

Detailed Answer

Choosing string rather than Date for a DateTime scalar's generated type is deliberate and important to get right: the actual value flowing over the wire in a JSON GraphQL response is always a string (JSON has no native date type), so mapping the generated type to string accurately reflects what the field literally contains at the point your component receives it — parsing that string into a real Date object is a separate, explicit step your own code performs afterward, not something codegen should paper over by generating a misleadingly-typed Date that isn't actually what's present until you've done that parsing yourself.

Some teams go further and configure custom scalar mappings to point at their own branded/wrapper types (rather than a bare string) specifically to prevent accidentally treating an un-parsed date string as if it were already a usable Date — a small type-safety investment that pays off by making "did I remember to parse this" a compile-time-visible distinction rather than a runtime surprise.

Code Example

# codegen.ts
generates:
  src/gql/:
    preset: client
    config:
      scalars:
        DateTime: string   # accurately reflects the wire format
        JSON: "Record<string, unknown>"
        Upload: File

// Application code does the actual parsing explicitly, at the boundary
const post = data.post;
const createdAt: Date = new Date(post.createdAt); // post.createdAt is `string`, by design

Common Mistake

Leaving a custom scalar unmapped (silently falling back to any) reintroduces exactly the type-safety hole codegen is meant to eliminate, just for that one field — it's an easy thing to miss when a schema introduces its first custom scalar, and worth specifically checking for whenever a new scalar type is added to a schema a codegen setup depends on.

SECTION 14 - APOLLO VS URQL VS RELAY TRADEOFFS

Q79. What philosophy separates Relay from Apollo/urql — compiler-driven optimization vs runtime-configured caching?

ROI: ★★★★☆ Frequency: High

Short Answer

Relay is built around a build-time compiler that statically analyzes every query and fragment in your codebase ahead of time, generating optimized artifacts and enforcing conventions (colocation, masking, specific naming patterns) as compile errors — correctness and performance are pushed as early as possible, at the cost of a mandatory build step and stricter rules. Apollo and urql are runtime-configured: the cache behavior, normalization keys, and merge logic are all set up as JavaScript configuration objects evaluated when the app runs, which is more flexible and has a lower barrier to entry, but pushes some classes of mistake (a missing keyArgs, an inconsistent fragment) to runtime discovery rather than compile time.

Detailed Answer

This is the single deepest philosophical divide between the three libraries, and it explains most of their other differences as downstream consequences: Relay's compiler can guarantee every component only reads the exact fields its own fragment declared (mandatory masking, Q28) because it's statically verifying that at build time across the whole codebase; Apollo's typePolicies are just objects you configure, which means correctness properties like "every field with variable-dependent behavior has consistent keyArgs" are conventions the team has to maintain by discipline and code review, not something the tooling can mechanically enforce the way Relay's compiler enforces its conventions.

The trade-off in practice: Relay's approach pays off enormously at large scale with many contributors, where compiler-enforced consistency prevents an entire category of "someone didn't follow the convention" bugs across dozens of teams — but the mandatory build step, GraphQL-schema-relative import conventions, and steeper learning curve are real costs that don't pay for themselves on a smaller team or a smaller codebase. Apollo/urql's runtime flexibility is easier to adopt incrementally and has a gentler learning curve, at the cost of correctness properties that rely on team discipline rather than tooling guarantees.

Senior Engineer Perspective

Anchor the answer in "when does compiler-enforced consistency start paying for its own cost" — that's the real question underlying every Relay-vs-Apollo comparison, and naming it directly signals you understand this is an organizational/scale trade-off, not a simple feature checklist comparison.

Q80. Why does Relay require every component to declare its data needs via useFragment, and what does that buy you that Apollo's colocation convention doesn't enforce?

ROI: ★★★★☆ Frequency: High

Short Answer

In Apollo, colocating fragments is a convention a team chooses to follow — nothing stops a developer from bypassing it and reading a field directly off a merged object that some unrelated part of the query happened to fetch (the exact gap Q24 describes). In Relay, useFragment is the only way to read fragment data at all, and Relay's compiler statically verifies, for every component, that it only requests a fragment it explicitly declared — making the discipline a structural guarantee of the framework rather than a code-review-enforced convention that any individual PR could quietly violate.

Detailed Answer

This matters most as a codebase and team scales: a convention that depends on every contributor remembering to follow it (Apollo's colocation-by-discipline) tends to erode gradually as team size grows and institutional knowledge about "why we do it this way" spreads thinner — a new hire unfamiliar with the convention can introduce the undeclared-coupling bug without any tooling stopping them. Relay's mandatory useFragment boundary makes that specific mistake structurally impossible to introduce, regardless of how many people are contributing or how well they understand the underlying rationale — which is precisely the kind of guarantee that becomes more valuable, not less, as an organization scales.

The cost side of this trade-off is real too: Relay's rigidity means a component genuinely can't take a shortcut even when a developer might have a legitimate, well-reasoned exception in mind — Apollo's flexibility allows for pragmatic exceptions (at the risk of those exceptions eroding into an unmanaged mess if overused). Neither stance is objectively correct; it's a bet about whether a team benefits more from enforced consistency or from flexibility to make case-by-case judgment calls.

Interview Favorite

Framing this as "convention vs. structural guarantee, and which one a specific team/org size actually needs" — rather than "Relay is stricter, therefore better" — is the answer that reads as genuinely thought-through rather than repeating a marketing talking point from either library's documentation.

Q81. What is Relay's "data masking," and how does it differ from Apollo's newer fragment masking feature?

ROI: ★★★☆☆ Frequency: Medium

Short Answer

Relay's data masking has been a core, mandatory, non-optional part of the framework since early versions — there has never been a way to read fragment data in Relay except through the masked useFragment boundary. Apollo's fragment masking (Q24) is the same underlying idea implemented much later, as an opt-in feature layered on top of an ecosystem (GraphQL Code Generator's client preset) that predates and exists independently of masking — meaning an Apollo codebase can be fully functional, well-structured, and colocated without ever adopting masking at all, which is never true for Relay.

Detailed Answer

This difference in "mandatory from day one" vs "optional, added later" has a real practical consequence for adoption: a team migrating an existing, large, un-masked Apollo codebase to enable masking has to actually go through and update every fragment-consuming component's prop types and add useFragment calls throughout the tree — a genuine, potentially large migration effort. A team starting a new Relay project never faces that migration at all, because there was never a pre-masking state to migrate away from; masking was there from the very first component.

For an interview, the useful distinction to draw is temporal and adoption-related, not purely technical — the underlying mechanism (opaque fragment references, an unmask step) is conceptually the same idea in both libraries; what differs is whether it was baked in from inception (Relay) or retrofitted as an opt-in enhancement onto an already-mature ecosystem (Apollo).

Common Mistake

Describing Apollo's masking as "just like Relay's" without noting the mandatory-vs-optional and inception-vs-retrofit distinction misses the part of the answer that actually explains why adoption looks so different in practice between a greenfield Relay project and an existing Apollo codebase considering masking.

Q82. How do urql's "exchanges" compare architecturally to Apollo's "links," and what does that mean for extensibility?

ROI: ★★★☆☆ Frequency: Medium

Short Answer

Both are middleware-pipeline architectures conceptually — a request passes through a chain of composable units before hitting the network, and the response passes back through them in reverse. Apollo's links are the older, Observable-based implementation of this idea; urql's exchanges are built on a more explicit, generator/stream-based (wonka) model that urql's maintainers designed to be simpler to reason about and lighter-weight than Apollo's link architecture, while covering the same core use cases (auth injection, error handling, retries, caching).

Detailed Answer

The practical extensibility story is similar in both: you compose a pipeline of small, focused, independently-testable units (an auth exchange/link, an error-handling exchange/link, a caching exchange/link, the terminal HTTP-fetching exchange/link) rather than one monolithic network layer — this composability is genuinely one of the strongest shared architectural decisions across both libraries, and it's a large part of why both are considered production-grade rather than toy GraphQL clients. The difference is more about implementation elegance and bundle-size than capability: urql's exchange model is often cited as conceptually simpler to trace through and debug (fewer abstraction layers, a more directly-observable request/response flow), which aligns with urql's broader "lighter-weight, more explicit" positioning relative to Apollo (echoed in Q12's original comparison).

Neither architecture is a hard constraint on what's achievable — nearly anything you can build as an Apollo link (custom retry logic, request batching, response transformation) has an equivalent urql exchange, and vice versa; the real-world choice between them tends to be driven more by which client's overall feature set and cache model (Q12) fits the project, with the middleware architecture underneath being a secondary, mostly-equivalent consideration.

Senior Engineer Perspective

Don't overstate the practical difference here — both architectures achieve the same composability goals, and the honest answer is that this is a smaller factor in a real client-library decision than the cache model or bundle size differences covered in Q12 and Q84. Naming that relative weighting shows judgment about which differences actually matter for a real decision.

Q83. When would a team specifically choose Relay despite its steeper learning curve and stricter conventions?

ROI: ★★★★☆ Frequency: High

Short Answer

Relay earns its cost specifically at large scale — a big team, a big codebase, heavy component reuse, and a genuine need for compiler-enforced consistency across many contributors who can't realistically all internalize and follow the same conventions purely through discipline and code review. It's also the natural choice when a team's product genuinely leans into Relay's specific strengths: aggressive, statically-verified query optimization, and a schema design that's already built around (or willing to adopt) the Relay connection spec and object-identification conventions Relay assumes throughout.

Detailed Answer

The organizations that famously use Relay in production (Facebook/Meta, where it originated, and other very large engineering orgs) share a common shape: hundreds of engineers touching the same GraphQL-backed product surface, where the cost of even a small percentage of contributors not following an unenforced convention compounds into real, frequent bugs at that scale. For a five-person startup building an MVP, that calculus flips — the mandatory build step and stricter conventions are pure overhead relative to a codebase small enough that the whole team can informally agree on and enforce Apollo-style colocation conventions through normal code review, without needing a compiler to guarantee it.

A second, more product-shaped reason: teams whose schema is already deeply Relay-spec-aligned (global object identification via a Node interface, connection-spec pagination throughout) get more of Relay's automatic optimization "for free," since much of what the Relay compiler optimizes assumes those schema conventions are already in place — a schema that wasn't designed with Relay in mind would need meaningful schema-level changes to fully benefit, which is itself a cost worth weighing against simply using Apollo/urql against the existing schema as-is.

Interview Gold Point

Naming team size and schema alignment as the two concrete deciding factors — rather than "Relay is more powerful" — is a substantive, decision-relevant answer. It also naturally invites a good follow-up conversation about the specific team's actual constraints, which is exactly the kind of question a senior candidate can turn into a two-way technical discussion rather than a one-way recitation.

Q84. How do the three libraries differ in bundle size, and what practical effect does that have on a mobile-heavy product?

ROI: ★★★★☆ Frequency: High

Short Answer

Roughly ordered smallest to largest: urql's core is the smallest and most modular (you opt into exchanges/features individually, so an app using minimal features ships less code); Relay's runtime is moderate but comes with a mandatory build step that shifts some cost from runtime bundle size to build-time compilation; Apollo Client is generally the heaviest out-of-the-box baseline, since its normalized cache, devtools integration hooks, and broad feature surface are largely present whether or not a given app uses all of it, though tree-shaking and careful imports reduce this somewhat.

Detailed Answer

For a mobile-heavy product — especially one targeting markets with slower networks or lower-end devices, where every extra kilobyte of JavaScript has a measurable effect on time-to-interactive — bundle size differences that look academic on a fast desktop connection become a real, user-visible product concern. This is one of the more concrete, less philosophy-driven reasons a team might lean toward urql specifically: its smaller, more opt-in footprint can matter meaningfully for exactly this kind of product, independent of any preference around Apollo's richer feature set or Relay's compiler guarantees.

It's worth caveating any specific number claims in an interview — exact bundle sizes shift between library versions and depend heavily on which features/exchanges/plugins an app actually imports, so the durable, interview-safe claim is the relative ordering and the reasoning behind it (feature surface and opt-in-ness), not a specific KB figure that's likely to already be stale by the time it's checked.

Common Mistake

Quoting a specific, memorized bundle-size number for any of these libraries is risky — the ordering and the underlying reasoning (feature surface, opt-in modularity, tree-shaking friendliness) age much better than a specific KB figure, which changes across versions and depends on what a given app actually imports.

Q85. How do the three libraries differ in how they handle pagination out of the box?

ROI: ★★★★☆ Frequency: High

Short Answer

Relay mandates the connection spec (edges/node/pageInfo/cursor) for any paginated field and provides usePaginationFragment as a built-in, batteries-included hook that handles fetching, merging, and loading-more state automatically, as long as the schema follows the spec Relay expects. Apollo treats pagination as opt-in configuration — you write your own merge/keyArgs typePolicy (Q7, Q19, Q21) by hand, giving flexibility to support any pagination shape a schema happens to use, at the cost of needing to write and maintain that merge logic yourself. urql's default document cache doesn't handle pagination merging at all without adding @urql/exchange-graphcache, which then lets you configure resolvers roughly analogous to Apollo's typePolicy merge functions.

Detailed Answer

This ordering — mandated-and-automatic (Relay) vs opt-in-and-manual (Apollo) vs requires-an-addon (urql's base setup) — mirrors each library's broader philosophy exactly: Relay's willingness to require a specific schema shape in exchange for eliminating an entire category of hand-written merge logic; Apollo's flexibility to work with whatever pagination shape a schema already has, at the cost of every team writing similar merge-function boilerplate independently; urql's minimal-core-plus-addons approach, where pagination-aware caching is a deliberate opt-in rather than a default feature.

For a team evaluating this specific axis: if a schema already follows (or can be made to follow) the Relay connection spec, Relay's built-in pagination handling removes real, recurring hand-written-merge-function maintenance burden that Apollo and urql both otherwise require per paginated field. If the schema uses a non-standard pagination shape that can't reasonably be changed, Apollo/urql's flexibility to accommodate that shape via custom merge logic is the more pragmatic fit, since Relay's compiler would otherwise fight against a non-conforming schema.

Senior Engineer Perspective

Tie this back to the schema, not just the client library choice: "which pagination handling is 'better' here depends heavily on whether the schema already follows or can adopt the Relay connection spec — the client library decision and the schema design decision aren't actually independent of each other on this specific axis."

Q86. If migrating an existing large Apollo codebase to Relay (or vice versa), what's the realistic scope of that migration and where does the pain concentrate?

ROI: ★★★☆☆ Frequency: Medium

Short Answer

This is realistically a full-rewrite-scale migration for any codebase of meaningful size, not an incremental swap — every component that touches GraphQL data needs its data-fetching hooks rewritten (useQuery/useMutation vs Relay's usePreloadedQuery/useMutation/useFragment APIs are meaningfully different shapes), every fragment needs restructuring around Relay's mandatory masking and naming conventions, and — often the biggest hidden cost — the schema itself may need changes to conform to Relay's expected conventions (global object identification, connection-spec pagination) if it doesn't already follow them.

Detailed Answer

The pain concentrates in three places, roughly in order of how often teams underestimate them: first, the schema conformance work (adding a Node interface with globally unique IDs, converting ad hoc list fields to the connection spec) is genuinely backend work, not just a frontend migration, and it's easy to scope a "client library migration" without accounting for the fact that it's really a joint frontend-and-backend project. Second, Relay's build tooling (the compiler, its specific project-config expectations) needs to be integrated into the existing build pipeline, which can surface friction with whatever bundler/monorepo setup already exists. Third, and often most time-consuming in raw hours: the sheer number of individual components that need their data-fetching code rewritten, one at a time, in a large app — this part scales roughly linearly with codebase size and doesn't have much of a shortcut.

The realistic, honest scoping to give in an interview (or in a real migration proposal) is that this is rarely worth doing purely for its own sake — it's usually only justified when a team has hit real, specific pain that Relay's guarantees would concretely solve (the scale/consistency problems from Q83), not as a "let's modernize our stack" initiative, given how large the actual engineering cost turns out to be once schema and tooling work is properly accounted for.

Interview Gold Point

Naming the schema-conformance work as a joint frontend/backend cost — not just a frontend refactor — is the detail that shows real awareness of how large this kind of migration actually is in practice, versus an answer that treats it as "swap the client library and update some hooks."

Q87. What is query batching, and how does Apollo's BatchHttpLink combine multiple operations into one HTTP request?

ROI: ★★★★☆ Frequency: High

Short Answer

When several components fire independent queries within a short window (common on a page mount where five widgets each run their own useQuery), BatchHttpLink collects operations that occur within a small time window (default 10ms) and sends them as a single HTTP request carrying an array of operations, rather than one HTTP request per query — the server (with batching support enabled) processes all of them and returns a matching array of responses, which Apollo then distributes back to each original caller transparently.

Detailed Answer

The win is reducing HTTP overhead — connection setup, TLS handshake reuse aside, each separate HTTP request still carries its own headers and round-trip latency — by trading N small requests for 1 slightly larger one. This is most valuable specifically on high-latency connections (mobile, satellite, generally poor connectivity) where per-request latency dominates total time far more than payload size does; on a fast, low-latency connection the benefit is much smaller and sometimes not worth the added complexity.

The trade-off to know: batching couples the response timing of all batched operations together — if one operation in the batch is slow (a heavy resolver), every other operation in that same batch waits for the whole batch to resolve before any of them can return, even if some were individually fast. This is the mirror image of the "one slow query blocks nothing else" property you get with separate requests, and it's why batching windows are kept deliberately short (milliseconds) — to only batch things that were already happening at effectively the same moment, not to artificially delay unrelated requests hoping to catch more into one batch.

Code Example

import { BatchHttpLink } from "@apollo/client/link/batch-http";

const batchLink = new BatchHttpLink({
  uri: "https://api.example.com/graphql",
  batchMax: 10,       // don't let a single batch grow unbounded
  batchInterval: 10,   // ms — how long to wait collecting operations
});

const client = new ApolloClient({
  link: ApolloLink.from([authLink, batchLink]),
  cache: new InMemoryCache(),
});

Interview Gold Point

The head-of-line-blocking trade-off — one slow operation in a batch delaying every other operation in that same batch — is the detail that shows you understand batching isn't a free win; it's a genuine latency-vs-request-count trade-off that needs the batching window tuned deliberately short to avoid coupling unrelated operations' response times together.

Q88. What are persisted queries (Automatic Persisted Queries), and what problem do they solve?

ROI: ★★★★☆ Frequency: High

Short Answer

A GraphQL query's full text can be large — deeply nested queries with many fragments spread in can easily reach several kilobytes — and sending that full text on every single request is wasted bandwidth once the server has already seen that exact query before. Automatic Persisted Queries (APQ) solve this: the client sends a hash of the query instead of the full text; if the server recognizes the hash (it's seen this exact query before), it executes it directly; if not, the server asks for the full query text once, caches it against that hash, and every subsequent request for the same operation can use the short hash alone.

Detailed Answer

The mechanics: the client's createPersistedQueryLink computes a SHA-256 hash of the query document and sends only the hash on the first attempt; if the server doesn't recognize it (a cache miss on its hash-to-query-text store, or the very first time this operation has ever been sent), it responds with a specific "PersistedQueryNotFound" error, and the client automatically retries that one request with the full query text included alongside the hash, letting the server register it — every subsequent call from any client using the same query only ever needs to send the short hash.

Beyond raw bandwidth savings, this unlocks a genuinely valuable secondary benefit: because persisted query requests can be sent as HTTP GET requests with the hash as a query parameter (rather than a POST with a body), they become cacheable by a CDN or browser HTTP cache the same way any other GET request would be — something a normal POST-based GraphQL request can't easily get for free, tying back to the "GraphQL gives up HTTP-level caching" trade-off named in Q1.

Code Example

import { createPersistedQueryLink } from "@apollo/client/link/persisted-queries";
import { sha256 } from "crypto-hash";

const persistedQueryLink = createPersistedQueryLink({ sha256 });

const client = new ApolloClient({
  link: ApolloLink.from([persistedQueryLink, httpLink]),
  cache: new InMemoryCache(),
});

// First request for a given query: { extensions: { persistedQuery: { sha256Hash } } }
// only, no query text — falls back to sending full text ONLY if the
// server responds PersistedQueryNotFound, then succeeds on retry

Interview Favorite

The GET-request-and-CDN-caching side benefit is worth volunteering unprompted — it directly reconnects to the very first trade-off named in this chapter (GraphQL gives up free HTTP caching), and shows APQ isn't just a bandwidth optimization but a way to partially reclaim some of that lost HTTP-caching benefit for identical, repeated operations.

Q89. How does Apollo deduplicate identical in-flight queries fired from multiple components simultaneously?

ROI: ★★★★☆ Frequency: High

Short Answer

If two components mount around the same time and both call useQuery with the exact same query document and variables, Apollo's default request deduplication recognizes this is genuinely the same in-flight request and sends only one network request, fanning the single response out to both callers — rather than firing two separate identical HTTP requests for data that's, by definition, going to be identical anyway. This is on by default and requires no special configuration to benefit from.

Detailed Answer

Deduplication happens at the "in-flight request" level, not the cache level — it's specifically about not sending the same request twice while it's still pending, which is a distinct concern from normal caching (which is about not re-sending a request whose result you've already received and stored). It matters most for exactly the concurrent-mount scenario: a page that renders several components at once, some of which happen to need the same query (a header and a sidebar both querying the current user, say), would otherwise fire duplicate simultaneous requests purely from the coincidence of both needing the same data at roughly the same moment.

This can be disabled per-query (useQuery(QUERY, { fetchPolicy: ..., context: { queryDeduplication: false } })) for the rare case where you genuinely want two calls to the same query with the same variables to be treated as independent requests — some polling or real-time-sensitive edge cases might want this, but it's an intentional opt-out from a sensible default, not something to disable casually.

Code Example

// Both components mount at roughly the same time, both call this
// exact query/variables combination — Apollo sends ONE request,
// not two, by default
function Header() {
  const { data } = useQuery(GET_CURRENT_USER);
  return <span>{data?.currentUser.name}</span>;
}
function Sidebar() {
  const { data } = useQuery(GET_CURRENT_USER); // deduped against Header's request
  return <div>{data?.currentUser.email}</div>;
}

Common Mistake

Conflating request deduplication with caching is a common imprecision — deduplication is about not sending the same request twice while one is still in flight; caching is about not sending a request again once a previous one has already completed and been stored. Both reduce network traffic, but they solve genuinely different timing problems and are worth naming as distinct mechanisms.

Q90. How do you avoid overfetching when different components on the same page need overlapping-but-not-identical shapes of the same entity?

ROI: ★★★★☆ Frequency: High

Short Answer

This is exactly what colocated fragments (Q23, Q27) are designed to solve at the query-authoring level: each component spreads only its own fragment, and GraphQL's execution naturally deduplicates overlapping field selections across fragments on the same object into one actual server-side resolution per field — so two components needing overlapping-but-different subsets of the same User don't cause the server to compute any field twice, and the client ends up requesting the union of what's genuinely needed, no more.

Detailed Answer

The mechanism worth understanding precisely: when a query spreads two fragments that both select, say, id on the same object, that's not "fetched twice" — GraphQL's execution model resolves each distinct field on a given object exactly once per query, regardless of how many different fragments happened to select it, and the response naturally contains one value for that field, referenced by both fragments' consumers. So combining fragments from multiple components onto the same query is inherently efficient at the field level; the "overfetching" risk isn't from combining fragments, it's from any individual fragment requesting more than its component actually renders (Q30's discipline point).

Where this gets trickier is nested list fields with different pagination needs per consumer (one component wants the first 5 comments as a preview, another wants full pagination) — that's the aliasing case from Q26, since the same field with genuinely different arguments per consumer can't be silently deduplicated the way identical field selections can.

Code Example

# Both fragments select `id` — this does NOT cause it to be fetched
# twice; GraphQL resolves each field once per query execution
fragment CardFields on User { id name avatarUrl }
fragment DetailFields on User { id bio joinedAt }

query Dashboard {
  currentUser {
    ...CardFields
    ...DetailFields
  }
}
# Response has exactly one `id` value, shared by both fragments' consumers

Interview Gold Point

The precise fact worth stating: "combining fragments on the same object doesn't multiply resolver work for overlapping fields — GraphQL execution naturally coalesces identical field selections. The overfetching risk is entirely about any one fragment requesting more than its own component renders, not about combining multiple fragments together."

Q91. How do you profile or measure whether a GraphQL query is a real performance bottleneck — client-side query complexity vs network vs render?

ROI: ★★★★☆ Frequency: High

Short Answer

Separate the measurement into the three genuinely distinct stages a slow-feeling screen could be bottlenecked in: network (time from request sent to response received — visible in browser devtools' network tab, or Apollo's own timing if instrumented), server resolution (time the server actually spent computing the response — visible via server-side tracing/APM, not something client tooling alone can see), and client render (time spent turning the received data into painted UI — visible via React Profiler or performance marks around the component tree). A slow screen is often blamed on "the GraphQL query" by default when the actual bottleneck is in a completely different one of these three stages.

Detailed Answer

Apollo DevTools' network/timing panel and the browser's own network tab together isolate the pure network-transfer time; if that's fast but the screen still feels slow to become interactive, the bottleneck is very likely render-side — a common trap is a query that returns quickly but whose result feeds an expensive, unmemoized render of a large list (exactly the concerns from the rendering-performance chapters), which no amount of query optimization would fix. Conversely, a query that's slow specifically at the server-resolution stage (visible via response timing being large relative to payload size, or confirmed via backend APM/tracing if you have access to it) points toward exactly the N+1/DataLoader concerns from Q11 — a client-side fix wouldn't help there either, since the bottleneck genuinely lives server-side.

The interview-relevant discipline is refusing to guess: before proposing any specific fix (smaller query, better memoization, backend batching), actually isolate which of the three stages is dominant using the appropriate tool for that stage, since the fix for a network-bound problem (reduce payload, add persisted queries/CDN caching), a resolution-bound problem (add DataLoader batching, optimize a resolver), and a render-bound problem (memoize, virtualize a list) are all completely different and mostly don't help each other's actual bottleneck.

Code Example

// A quick client-side timing split, useful as a first diagnostic pass
// before reaching for full profiling tools
function useTimedQuery(query, options) {
  const start = useRef(performance.now());
  const result = useQuery(query, options);
  useEffect(() => {
    if (!result.loading) {
      console.log(`Network+resolution: ${performance.now() - start.current}ms`);
    }
  }, [result.loading]);
  return result;
}

Senior Engineer Perspective

The habit worth naming explicitly: "before I touch anything, I isolate whether this is network, server-resolution, or render-bound — because the fix for each is completely different, and guessing wrong means shipping a change that doesn't actually address the real bottleneck." That diagnostic discipline is a stronger signal than knowing any individual optimization technique.

Q92. How do you handle very large lists rendered from a GraphQL query without re-rendering the entire list on every cache write?

ROI: ★★★★☆ Frequency: High

Short Answer

The standard risk: a parent component's useQuery re-renders whenever any field it selected changes in the cache, and if that parent maps a large array into child components inline, every one of those children re-renders too, even if only one item's data actually changed. The fix is to give each list item its own narrower subscription to just its own entity — either via a small per-item useFragment-style read, or simply wrapping each row in React.memo keyed on props that only change when that specific item's data changes — so a write to one entity only triggers a re-render of the one row actually affected, not the whole list.

Detailed Answer

This is a specific instance of a broader React performance principle (component granularity determines re-render granularity) applied to Apollo's cache-driven re-rendering: a single useQuery at the top of a large list ties the re-render scope to "anything in this entire query changed," while pushing data subscription down to individual row components (each reading just its own entity, e.g. via Apollo's newer field-level useFragment hook, distinct from Relay's identically-named hook but conceptually similar) ties the re-render scope to "did THIS entity change" — a much narrower, more efficient granularity for large lists where updates to one item are common and updates to every item simultaneously are rare.

This granularity technique compounds well with the pagination/virtualization techniques from earlier chapters — a virtualized list already limits how many rows are mounted at once, and per-row fine-grained cache subscriptions further limit how much re-render work happens even among the rows that are mounted, when a cache write only actually affects one of them.

Code Example

import { useFragment } from "@apollo/client";

const POST_ROW_FRAGMENT = gql`fragment PostRowFields on Post { id title likeCount }`;

// Each row subscribes ONLY to its own entity — a like-count update on
// post #500 doesn't re-render posts #1 through #499
function PostRow({ postId }) {
  const { data: post } = useFragment({
    fragment: POST_ROW_FRAGMENT,
    from: { __typename: "Post", id: postId },
  });
  return <div>{post.title} ({post.likeCount})</div>;
}

function PostList({ postIds }) {
  return postIds.map((id) => <PostRow key={id} postId={id} />);
  // parent only re-renders if the LIST OF IDS changes, not on
  // every field-level write to any individual post
}

Interview Gold Point

Naming Apollo's field-level useFragment hook specifically as the mechanism for "subscribe to one entity instead of a whole query result" is a strong, precise, and relatively recent-feature-aware answer — it demonstrates you've kept up with how Apollo's re-render granularity story has evolved beyond the basic useQuery-at-the-top pattern most tutorials stop at.

Q93. What's the performance impact of over-broad typePolicies merge functions, and how do you keep them efficient at scale?

ROI: ★★★☆☆ Frequency: Medium

Short Answer

A merge function runs on every single cache write for that field — for a frequently-updated, large paginated list, a naive merge function that does something O(n) or worse on every call (re-scanning and deduplicating the entire accumulated list every time one new page arrives, say) can become a genuine performance cost as the list grows into the thousands of items, since that cost compounds with every additional page fetched, not just the most recent one.

Detailed Answer

The dedupe-by-id pattern from Q32, done naively with an array .some()/.filter() scan against the full existing list on every merge, is exactly this trap — it's O(n) per incoming page against an ever-growing n, so merging page 50 into an already-large list is meaningfully slower than merging page 2 was. The straightforward fix is switching the internal dedupe check from an array scan to a Set/Map lookup (O(1) per item instead of O(n)), which keeps merge cost proportional to the size of the incoming page rather than the size of the entire accumulated list.

More broadly, merge functions should be treated with the same performance awareness as any other hot-path code that runs on a tight, frequently-triggered loop — because they execute synchronously as part of cache writes (which themselves happen on every network response and every optimistic update), an inefficient merge function directly adds latency to the exact moment a user is waiting for a UI update, making it one of the less obvious but genuinely real places GraphQL client performance work can pay off.

Code Example

// O(n) per merge — existing.edges grows, and .some() rescans it every time
merge(existing = { edges: [] }, incoming) {
  const deduped = incoming.edges.filter(
    (e) => !existing.edges.some((x) => x.node.id === e.node.id) // O(n) scan, repeated per item
  );
  return { edges: [...existing.edges, ...deduped] };
}

// O(1) per item — a Set lookup instead of a linear scan
merge(existing = { edges: [] }, incoming, { readField }) {
  const seen = new Set(existing.edges.map((e) => readField("id", e.node)));
  const deduped = incoming.edges.filter((e) => !seen.has(readField("id", e.node)));
  return { edges: [...existing.edges, ...deduped] };
}

Common Mistake

Writing a merge function's dedupe logic with an array scan is easy to overlook when a list is small during development and only becomes visibly slow once real production data grows the list well beyond what local testing ever exercised — worth treating merge function complexity as a code-review concern specifically for any field expected to accumulate a large number of items over a session.

Q94. How would you design a GraphQL query strategy for a slow mobile network — what specific techniques reduce time-to-interactive?

ROI: ★★★★★ Frequency: Extremely High

Short Answer

Combine several of this chapter's techniques deliberately, layered together: persisted queries (Q88) to shrink request payload size and unlock CDN/GET caching; tight, colocation-disciplined fragments (Q23, Q27, Q30) to request only what's genuinely rendered; a cache-and-network fetch policy (Q5) so a returning user sees an instant, cached paint while a fresh response is still in flight; and prioritizing the query for above-the-fold content first (a smaller initial query for what's immediately visible, with additional data fetched lazily as the user scrolls or interacts) rather than one large query blocking the entire first paint on everything the page could possibly need.

Detailed Answer

On a slow, high-latency mobile connection, request count and request latency matter more than they do on a fast connection, where a slightly-too-large payload is barely noticeable — this reframes several earlier "nice to have" techniques as genuinely load-bearing for a mobile-first product: batching (Q87) reduces round trips at the cost of some head-of-line blocking risk, persisted queries reduce payload size, and request deduplication (Q89) prevents redundant simultaneous requests from a page with several data-needing components mounting at once — all compounding to reduce the total network burden a slow connection has to carry.

Beyond pure network optimization, the query-shape decision of "what's needed for first paint vs what can be deferred" often has the single largest perceived-performance impact: a query scoped tightly to only what's above the fold, paired with a second, lazily-triggered query for content that loads as the user scrolls (mirroring the infinite-scroll pattern from Q36, but applied to initial-load prioritization rather than pagination), gets a user to something interactive far faster than a single comprehensive query that blocks the first render on data for content they haven't scrolled to yet, and might never scroll to at all.

Code Example

// Tight, above-the-fold-only initial query
const GET_ARTICLE_HEADER = gql`
  query GetArticleHeader($id: ID!) {
    article(id: $id) {
      id
      title
      heroImageUrl
      author { name }
    }
  }
`;

// Deferred, triggered only once the user actually scrolls toward it —
// never blocks the initial paint
const GET_ARTICLE_COMMENTS = gql`
  query GetArticleComments($id: ID!) {
    article(id: $id) {
      comments(first: 20) { edges { node { id body } } }
    }
  }
`;

function ArticlePage({ id }) {
  const { data } = useQuery(GET_ARTICLE_HEADER, {
    variables: { id },
    fetchPolicy: "cache-and-network", // instant paint from cache, then reconcile
  });
  const [loadComments, { data: comments }] = useLazyQuery(GET_ARTICLE_COMMENTS);

  return (
    <article>
      <ArticleHeader data={data} />
      <CommentsSentinel onVisible={() => loadComments({ variables: { id } })} />
      {comments && <CommentsList data={comments} />}
    </article>
  );
}

Interview Gold Point

Bringing together several previously-separate techniques into one coherent mobile-network strategy — rather than naming them as isolated facts — is exactly the kind of synthesis a senior-level system-design-flavored question is testing for. Explicitly prioritizing "what's needed for first paint" over "what the page could theoretically need" as the single highest-leverage decision is the strongest closing point to make.

QUICK REVISION SHEET

  • GraphQL vs REST: one endpoint, client-declared shape — fixes over-fetching and under-fetching, but gives up free HTTP caching in exchange for a heavier client-side cache.
  • Schema/types/queries/mutations/subscriptions: the schema is the typed contract; queries read, mutations write (and should return the changed object), subscriptions push over a long-lived connection; get nullability defaults right or one failing field nulls out its whole parent.
  • Apollo Client setup: a client is a link (network pipeline: auth, error handling, HTTP transport) plus an InMemoryCache, shared app-wide via ApolloProvider and Context — not just a fetch wrapper.
  • useQuery/useMutation: useQuery is declarative and auto-fires; useMutation is imperative and you call it — always guard on loading/error before touching data, since data can be undefined on first render.
  • Normalized cache & fetch policies: Apollo caches by entity (typename:id), not by query; cache-first/network-only/cache-and-network/no-cache trade off freshness vs requests — know that network-only still writes to cache but no-cache does not.
  • Cache updates after mutations: in-place edits merge automatically via normalization; new list items need the update function; refetchQueries is the simple-but-costly fallback; optimisticResponse gives instant UI with automatic rollback on failure.
  • Pagination: cursor-based (Relay connections: edges/pageInfo/endCursor) stays stable under concurrent inserts/deletes; offset-based is simpler but breaks under list mutation — Apollo drives both through fetchMore plus a cache merge field policy.
  • Fragments: colocate a component's data requirements as a named, reusable selection set spread into parent queries, so one field addition updates every consumer instead of requiring hand-edited duplication.
  • Error handling: a GraphQL response can be 200 OK and still contain per-field errors alongside partial data — check both graphQLErrors and networkError, and render what resolved while flagging only what failed.
  • Subscriptions: long-lived WebSocket pushes via useSubscription, requiring a separate GraphQLWsLink split from HTTP by operation type; reach for pollInterval instead when true push semantics aren't worth the infrastructure cost.
  • N+1 & DataLoader: a server-side batching/caching fix for resolver fan-out, but the client's query shape and nesting depth is what triggers or avoids it — know the mechanism even though you don't implement it.
  • Apollo vs urql vs React Query: choose based on how much GraphQL-aware normalized caching you need versus bundle size and whatever data-fetching paradigm the team already standardized on.
  • Testing with MockedProvider: mock the network boundary with exact query+variables matches and let the real component logic run; an "unmatched mock" failure usually means the request shape drifted, not that rendering broke.
  • Common pitfalls: GraphQL only prevents over-fetching if queries stay disciplined — bloated shared fragments and copy-pasted queries reintroduce the same waste; watch for nullability mistakes, under-returning mutations, unpaginated list fields, and "God query" schemas.
