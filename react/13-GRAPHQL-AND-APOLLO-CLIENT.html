SECTION 1 - GRAPHQL FUNDAMENTALS

Q1. Why GraphQL over REST — what specific problems does it solve?

ROI: ★★★★★ Frequency: Extremely High

Short Answer

GraphQL solves three concrete REST pain points: over-fetching (a REST endpoint returns a fixed shape, so a screen that needs only a user's name pulls down their entire profile), under-fetching (a screen needs data from three related resources, so you fire three or four round trips and stitch them together on the client, or the backend team adds a bespoke aggregate endpoint), and endpoint sprawl (every new UI variant tends to spawn a new REST endpoint or a new query-string dialect bolted onto an old one). GraphQL replaces that with a single endpoint and a query language where the client declares exactly the shape of data it needs, and the server returns exactly that shape — no more, no less.

Detailed Answer

REST ties the response shape to the resource, not to the screen. A GET /users/1 returns whatever the backend decided a "user" looks like — for a profile page that might be fine, but a header component that only needs name and avatarUrl still downloads bio, address, preferences, and a dozen other fields. Multiply that by mobile clients on metered connections and it becomes a real performance cost, not just a style complaint.

Under-fetching shows up on composite screens: a dashboard needs the current user, their five most recent orders, and account notifications — three separate REST resources, three requests, three waterfalls (or careful client-side Promise.all orchestration), and three failure/loading states to reconcile. GraphQL lets the client ask for all three in one query, resolved server-side, returned as one JSON payload with one loading state.

The single-endpoint model also changes how APIs evolve. In REST, "the mobile app needs less data than the web app" tends to produce either a bloated shared endpoint or parallel endpoints (/v2/users, /users/lite) that drift out of sync. In GraphQL, every consumer writes its own query against the same schema — the mobile team asks for less, the web team asks for more, and the server never has to guess who's calling.

None of this makes REST "wrong." REST's uniform interface, cacheability via HTTP semantics (ETags, Cache-Control), and simplicity for CRUD-shaped resources are real strengths GraphQL gives up by default (HTTP caching a GraphQL POST is nontrivial — this is part of why Apollo builds its own cache, see Q5). The honest interview answer names the trade-off, not just GraphQL's wins.

Interview Gold Point

Anchor the answer in the two named failure modes — over-fetching and under-fetching — because interviewers are listening for that exact vocabulary. Then immediately volunteer the trade-off: GraphQL gives up free HTTP caching and takes on client-side query complexity and a heavier client library (Apollo/urql) to get normalized caching back. Candidates who present GraphQL as strictly superior read as under-experienced; candidates who can say "one endpoint plus client-declared shape, at the cost of HTTP-level caching and a more complex client" sound like they've shipped it.

Q2. What are GraphQL schema, types, queries, mutations, and subscriptions, and how do they fit together?

ROI: ★★★★★ Frequency: Extremely High

Short Answer

The schema is the contract: a strongly typed description of every object, field, and operation the API supports, written in the GraphQL Schema Definition Language (SDL). Types describe the shape of data (User, Post) and how fields relate to each other. Queries read data, mutations write data (and, by convention, return the updated data so the client doesn't need a follow-up fetch), and subscriptions open a long-lived connection that pushes data to the client when something changes server-side. Every operation you send must satisfy the schema, or it's rejected before your resolver code even runs — that's the value of the type system.

Detailed Answer

Three special root types anchor a schema: Query, Mutation, and Subscription. Every field on Query is an entry point for reading; every field on Mutation is an entry point for writing. Ordinary object types (User, Post, Comment) describe the data graph and can reference each other, which is where "graph" in GraphQL comes from — a query can traverse from a user to their posts to each post's comments to each comment's author in one request.

Scalars (String, Int, Float, Boolean, ID) are the leaves. A trailing ! marks a field non-nullable (String!); a list is wrapped in brackets ([Post!]! means a non-null list of non-null posts). Getting nullability right in schema design matters more than it looks — marking something non-null when the resolver can legitimately fail to produce it causes the entire parent object to null out at runtime (GraphQL's error-propagation rule), which is a classic schema-design mistake interviewers probe (see Q14).

Mutations conventionally return the object they changed (or a payload wrapping it plus any errors), specifically so the client can merge the result straight into cache without an extra round trip — this is the seed of how Apollo's automatic cache updates work (Q6). Subscriptions are the odd one out: instead of request/response, the client keeps a socket open (typically via graphql-ws) and the server pushes a new payload every time the subscribed event fires.

Code Example

# schema.graphql — SDL

type User {
  id: ID!
  name: String!
  email: String!
  posts: [Post!]!          # traversal: User -> Post
}

type Post {
  id: ID!
  title: String!
  body: String!
  author: User!            # traversal: Post -> User (bidirectional graph)
}

type Query {
  user(id: ID!): User
  posts(limit: Int = 10): [Post!]!
}

type Mutation {
  createPost(title: String!, body: String!): Post!
}

type Subscription {
  postCreated: Post!
}

# A query traversing the graph in one round trip
query GetUserWithPosts($id: ID!) {
  user(id: $id) {
    name
    posts {
      title
      body
    }
  }
}

# A mutation that returns the created object for cache merging
mutation CreatePost($title: String!, $body: String!) {
  createPost(title: $title, body: $body) {
    id
    title
    body
  }
}

Common Mistake

Candidates often describe queries and mutations correctly but blank on why nullability matters — that a non-null field (!) whose resolver throws nulls out the parent object all the way up the tree, potentially wiping out an entire response for one flaky field. The stronger answer treats schema design as an API contract decision, not syntax: default to nullable for anything that can plausibly fail (a network call inside a resolver, an optional relation) and reserve non-null for fields truly guaranteed to resolve, like an object's own id.

SECTION 2 - APOLLO CLIENT CORE

Q3. What does Apollo Client setup and ApolloProvider actually wire up?

ROI: ★★★★☆ Frequency: High

Short Answer

ApolloClient bundles a network transport (a link, usually HttpLink pointed at your GraphQL endpoint) with an InMemoryCache instance, plus configuration like default fetch policies and type policies. <ApolloProvider client={client}> puts that client instance on React Context so every useQuery/useMutation/useSubscription call anywhere in the tree can reach it without prop drilling. In short: one client instance per app, one cache shared by every component, one provider at the root.

Detailed Answer

The link is Apollo's request pipeline — a chain of middleware that a request passes through before hitting the network and a response passes back through on the way to your component. HttpLink is the terminal link that actually makes the request; you commonly compose it with an authLink (attach a bearer token to headers) and an errorLink (centralized logging or retry-on-401) using ApolloLink.from([...]). This composability is a big part of why Apollo is heavier than a bare fetch wrapper — you get auth, retries, and error handling as first-class, testable pieces of the pipeline rather than scattered try/catch blocks.

The InMemoryCache is the other half, and it's not optional plumbing — it's the core value proposition (see Q5). You typically configure typePolicies here to tell Apollo how to identify and merge specific types, which matters the moment you have pagination or custom-keyed entities.

A subtlety worth naming: because the client is a single shared instance behind Context, all components reading the "same" query field are reading the same normalized cache entry — update it in one place (a mutation, a subscription push) and every subscribed component re-renders with the new value automatically. That shared-cache behavior is what most differentiates "using Apollo" from "just calling fetch in a hook."

Code Example

import {
  ApolloClient,
  ApolloProvider,
  InMemoryCache,
  HttpLink,
  ApolloLink,
} from "@apollo/client";
import { setContext } from "@apollo/client/link/context";

const httpLink = new HttpLink({ uri: "https://api.example.com/graphql" });

const authLink = setContext((_, { headers }) => {
  const token = localStorage.getItem("token");
  return {
    headers: {
      ...headers,
      authorization: token ? `Bearer ${token}` : "",
    },
  };
});

export const client = new ApolloClient({
  link: ApolloLink.from([authLink, httpLink]),
  cache: new InMemoryCache({
    typePolicies: {
      Query: {
        fields: {
          posts: { merge: false }, // replace, don't merge, on refetch
        },
      },
    },
  }),
  defaultOptions: {
    watchQuery: { fetchPolicy: "cache-and-network" },
  },
});

// app root
function App() {
  return (
    <ApolloProvider client={client}>
      <Dashboard />
    </ApolloProvider>
  );
}

Interview Favorite

Interviewers like to see that you know Apollo Client is fundamentally "network link + cache," not a data-fetching hook library that happens to also cache. Mentioning link composition (auth, error handling, retries as separate links you chain with ApolloLink.from) signals real production experience versus copy-pasted tutorial setup. The single-shared-instance-via-Context point is also the natural segue into cache normalization (Q5) if the interviewer probes further.

Q4. How do useQuery and useMutation work, and how do you handle their loading and error states?

ROI: ★★★★★ Frequency: Extremely High

Short Answer

useQuery(QUERY, options) fires (and re-fires, on variable changes or cache updates) a query and returns { data, loading, error, refetch, fetchMore }. useMutation(MUTATION) returns a tuple [mutate, { data, loading, error }] — the mutation does not run automatically; you call the returned function, typically from an event handler. Both hooks read from and write to the same shared cache, which is why a mutation's effects can show up in a completely unrelated component's useQuery result without any manual wiring.

Detailed Answer

The three states every component must handle deliberately: loading is true on the very first fetch (and, depending on fetch policy, on refetches too — see the notifyOnNetworkStatusChange option if you want loading to flip true again on refetch); error is a populated ApolloError if the request failed at either the network layer or the GraphQL layer (see Q9 for the distinction); data is undefined until the first successful response lands, then stays populated (even stale) across refetches unless you explicitly clear it. A common bug is rendering data.user.name before checking loading/error first — data can be undefined on the very first render.

useQuery accepts variables (re-runs the query when they change), skip (don't run at all — useful when a required variable isn't ready yet), and pollInterval (cheap "real-time-ish" updates via polling instead of a subscription). useMutation's second tuple element also exposes reset() to clear a stale error/data after a failed attempt, which matters for retry UX.

Because useMutation is imperative (you decide when it fires), it's also where you plug in the cache-update strategies from Q6 — refetchQueries, update, and optimisticResponse are all options passed to useMutation or to the mutate function call itself.

Code Example

import { useQuery, useMutation, gql } from "@apollo/client";

const GET_TODOS = gql`
  query GetTodos {
    todos {
      id
      text
      completed
    }
  }
`;

const TOGGLE_TODO = gql`
  mutation ToggleTodo($id: ID!) {
    toggleTodo(id: $id) {
      id
      completed
    }
  }
`;

function TodoList() {
  const { data, loading, error } = useQuery(GET_TODOS);
  const [toggleTodo, { loading: toggling }] = useMutation(TOGGLE_TODO);

  if (loading) return <Spinner />;
  if (error) return <ErrorBanner message={error.message} />;

  return (
    <ul>
      {data.todos.map((todo) => (
        <li key={todo.id}>
          <input
            type="checkbox"
            checked={todo.completed}
            disabled={toggling}
            onChange={() => toggleTodo({ variables: { id: todo.id } })}
          />
          {todo.text}
        </li>
      ))}
    </ul>
  );
}

Interview Gold Point

The tell of a candidate who has actually shipped Apollo: they mention that data being defined does not mean the query is "done" — after a refetch, loading stays false by default while data is stale, unless notifyOnNetworkStatusChange: true is set. They also know useMutation is opt-in/imperative by design (you don't want a POST firing on render), unlike useQuery, which is declarative and fires on mount/variable-change. That query-vs-mutation execution-model asymmetry is a favorite follow-up.

SECTION 3 - CACHING & DATA MANAGEMENT

Q5. How does Apollo's normalized cache work, and what do the fetch policies (cache-first, network-only, cache-and-network) actually control?

ROI: ★★★★★ Frequency: Extremely High

Short Answer

Apollo's InMemoryCache doesn't store responses keyed by query — it flattens every object into a normalized store keyed by a cache ID (default __typename:id), so the same User:1 entity fetched via three different queries lives in exactly one place. Every query result the client renders is a "view" reconstructed from that normalized store. Fetch policies control the trade-off between that cache and the network for a given query: cache-first (default) serves cache if present and only hits the network on a miss; network-only always hits the network but still writes the result into cache; cache-and-network serves whatever's cached immediately and fires a network request, updating the UI again when it resolves.

Detailed Answer

Normalization is what makes Apollo's cache genuinely powerful rather than just a response-memoization layer. Every object with a __typename and an id (or _id) gets flattened into a single entry, e.g. User:1, and queries store references to those entries rather than duplicating the data. Practical payoff: edit a user's name in one mutation, and every component on screen showing that user — a header avatar, a comment list, a profile card — re-renders with the new name, because they were all pointing at the same normalized entry, not separate copies.

The fetch policies, compared directly:

PolicyBehaviorUse when
cache-first (default)Return cache if it exists; only fetch on a cache missData that rarely changes; minimizing requests matters
cache-onlyNever hit the network; error if not cachedReading purely local/derived cache data
network-onlyAlways fetch, but still write the result to cacheData that must be fresh on this read (e.g. after navigating to a page that must reflect the latest state)
no-cacheAlways fetch; result is not written to cache at allOne-off reads you deliberately don't want polluting the shared cache
cache-and-networkReturn cache immediately (if any) AND fetch; UI updates twiceInstant paint from stale data, then reconcile with fresh data — the common "feels fast but stays correct" default

The classic interview trap is confusing network-only with no-cache: both always go to the network, but only no-cache skips writing the response into the store afterward. Get this backwards and you'll misdiagnose a "why isn't my cache updating" bug as a fetch-policy problem when it's actually a normalization/key problem (see Q6's follow-up on custom cache keys).

Common Mistake

Saying "Apollo caches by query" instead of "Apollo caches by normalized entity, and queries are views over that store" is the single most common gap. It matters practically: if you don't understand normalization, cache updates after a mutation (Q6) look like magic or like a bug, when they're really just "the entity changed, so every reference to it re-renders." Also be ready to name the difference between network-only and no-cache precisely — interviewers use it to filter out memorized-but-shallow answers.

Q6. How do you update the cache after a mutation — refetchQueries, the update function, and optimistic response?

ROI: ★★★★★ Frequency: Extremely High

Short Answer

Three mechanisms, in increasing order of manual effort and UX payoff: automatic normalization handles it for free when the mutation returns a field with the same cache ID as something already cached (edit-in-place cases). refetchQueries tells Apollo to re-run specific named queries after the mutation resolves — simplest, but an extra network round trip. The update function lets you imperatively write into the cache using the mutation's response, with no extra request — required for cases normalization can't handle alone, like adding a new item to a list. optimisticResponse layers a predicted result into the cache immediately (before the server responds), so the UI updates instantly and rolls back automatically if the mutation fails.

Detailed Answer

Why "just refetch everything" isn't the default answer: refetching is simple but expensive — it's a full network round trip for data you often already have enough information to construct locally. It also doesn't compose well: a mutation used in five places would need to know about all five queries to invalidate, tightly coupling components that should be independent.

Automatic cache updates happen for free precisely because of normalization (Q5): if a mutation returns a Post with id: "5" and you already have Post:5 cached, Apollo merges the returned fields straight into that entry — no update function needed. This covers most "edit an existing thing" mutations automatically.

Where automatic merging breaks down is adding or removing items from a list — a new Post has no existing cache entry to merge into, and no query result "knows" it should now include this new item. That's exactly what the update function is for: it hands you a proxy into the cache (cache.readQuery / cache.writeQuery, or the terser cache.modify) so you can manually splice the new item into the relevant list's cached result.

optimisticResponse is a UX technique layered on top of either approach: you supply a best-guess response shaped exactly like the real one (including a temporary client-generated ID prefixed with client: convention) and Apollo applies it to the cache — and re-renders the UI — immediately, before the network call resolves. When the real response arrives, Apollo reconciles (replaces the optimistic layer); if the mutation errors, Apollo automatically rolls the optimistic change back. This is how "instant" like buttons and toggle switches are built without actually waiting on the network.

Code Example

const ADD_TODO = gql`
  mutation AddTodo($text: String!) {
    addTodo(text: $text) {
      id
      text
      completed
    }
  }
`;

const GET_TODOS = gql`
  query GetTodos {
    todos {
      id
      text
      completed
    }
  }
`;

function AddTodoForm() {
  const [addTodo] = useMutation(ADD_TODO, {
    // Manually splice the new todo into the cached list — normalization
    // alone can't do this because the item didn't exist before.
    update(cache, { data: { addTodo } }) {
      const existing = cache.readQuery({ query: GET_TODOS });
      cache.writeQuery({
        query: GET_TODOS,
        data: { todos: [...existing.todos, addTodo] },
      });
    },
    // Instant UI feedback; rolled back automatically on failure
    optimisticResponse: (vars) => ({
      addTodo: {
        __typename: "Todo",
        id: `client:${Date.now()}`,
        text: vars.text,
        completed: false,
      },
    }),
  });

  return (
    <button onClick={() => addTodo({ variables: { text: "Ship the demo" } })}>
      Add
    </button>
  );
}

// The simpler, cheaper-to-write, more-network-costly alternative:
const [addTodo] = useMutation(ADD_TODO, {
  refetchQueries: [{ query: GET_TODOS }],
  awaitRefetchQueries: true,
});

Interview Gold Point

The layered answer wins: start with "normalization updates in-place edits for free," then "for adding/removing list items you need update," then "refetchQueries is the simple-but-costly escape hatch," then "optimisticResponse is orthogonal — it's about perceived latency, and it composes with either of the above." Naming the client:-prefixed temporary ID convention for optimistic inserts, and knowing Apollo auto-rolls-back a failed optimistic update, are the details that separate "read the docs once" from "debugged this in production."

Q7. How does pagination work in GraphQL — cursor-based (Relay-style) vs offset-based?

ROI: ★★★★☆ Frequency: High

Short Answer

Offset-based pagination passes a numeric offset/page and limit, mirroring classic SQL LIMIT/OFFSET — simple, but unstable if items are inserted or deleted between pages (items shift, causing skips or duplicates), and it gets slower on large offsets. Cursor-based pagination (formalized by the Relay connection spec) passes an opaque cursor (typically an encoded pointer to "the last item you saw") plus a count, and returns items after that cursor along with a pageInfo object (hasNextPage, endCursor) — stable under concurrent inserts/deletes, and the standard choice for infinite-scroll feeds. On the Apollo Client side, both are driven through fetchMore, but cursor-based pagination is what the ecosystem (and most interviewers) mean by "how do you paginate in GraphQL."

Detailed Answer

The Relay connection spec standardizes the shape: a field returns an edges array of { node, cursor } plus a pageInfo: { hasNextPage, hasPreviousPage, startCursor, endCursor }. Clients ask for the next page with first: N, after: $endCursor. Because the cursor identifies a specific item rather than a position, inserting a new item at the top of the list doesn't shift what "page 2" means — you're always asking for "everything after this specific item," which is what makes it stable for live-updating feeds.

On the Apollo Client side, fetchMore issues the next-page query and, via its updateQuery (legacy) or a cache merge field policy (current, preferred), appends the new edges to the existing list in the normalized cache. Configuring a merge function in typePolicies is the modern approach — it means every component reading that field, anywhere, sees the concatenated list automatically, rather than each call site having to hand-merge results.

Offset pagination is still reasonable for admin tables and anything with a fixed page-jump UI ("go to page 7") where cursor semantics ("go to page 7" has no natural cursor meaning) don't fit — the choice is genuinely use-case-dependent, not "cursor is always correct."

Code Example

const GET_POSTS = gql`
  query GetPosts($after: String) {
    posts(first: 10, after: $after) {
      edges {
        cursor
        node { id title }
      }
      pageInfo {
        hasNextPage
        endCursor
      }
    }
  }
`;

function PostFeed() {
  const { data, fetchMore } = useQuery(GET_POSTS);

  const loadMore = () =>
    fetchMore({
      variables: { after: data.posts.pageInfo.endCursor },
      // With a typePolicy merge function configured, Apollo appends
      // automatically — updateQuery below is the manual fallback.
      updateQuery: (prev, { fetchMoreResult }) => ({
        posts: {
          ...fetchMoreResult.posts,
          edges: [...prev.posts.edges, ...fetchMoreResult.posts.edges],
        },
      }),
    });

  return (
    <>
      {data?.posts.edges.map(({ node }) => <PostRow key={node.id} post={node} />)}
      {data?.posts.pageInfo.hasNextPage && (
        <button onClick={loadMore}>Load more</button>
      )}
    </>
  );
}

// typePolicy that merges pages automatically, so callers never
// hand-splice edges themselves
const cache = new InMemoryCache({
  typePolicies: {
    Query: {
      fields: {
        posts: {
          keyArgs: false,
          merge(existing, incoming) {
            return {
              ...incoming,
              edges: [...(existing?.edges ?? []), ...incoming.edges],
            };
          },
        },
      },
    },
  },
});

Interview Favorite

The concrete failure case sells this answer: with offset pagination, if a new item is inserted at the top while a user is scrolling, page 2's offset now points one item too early, either duplicating an item or skipping one entirely — cursor pagination sidesteps this because the cursor is anchored to an item, not a position. Bring up the merge field-policy pattern unprompted; it shows you've paginated in Apollo beyond the tutorial's manual updateQuery approach.

Q8. What are fragments, and how do they help with query reuse?

ROI: ★★★☆☆ Frequency: Medium

Short Answer

A fragment is a named, reusable selection set on a given type (fragment UserFields on User { id name avatarUrl }) that you can splice into any query needing those fields with ...UserFields. The payoff is colocation: a component can declare its own data requirements as a fragment sitting right next to its code, and a parent query just spreads that fragment in — so when the component changes what data it needs, the change lives in one file instead of requiring you to hunt down every parent query that duplicated those fields by hand.

Detailed Answer

Without fragments, every screen that renders a "user card" has to independently list the exact same five fields in its query, and if the card component later needs a new field, someone has to remember to update every query that feeds it — a classic drift bug. With fragments, the UserCard component exports UserCard.fragments.user, the parent query spreads it in, and adding a field to the fragment automatically flows to every parent that spreads it.

Fragments also interact with normalization (Q5): because a fragment's fields are attached to a specific normalized entity, using the same fragment consistently across queries means Apollo recognizes it's the "same" User:1 data shape being requested, which keeps cache reads/writes consistent instead of accidentally creating partial or conflicting entries for the same entity.

Two caveats interviewers may probe: fragments must be defined on a specific GraphQL type (or an interface/union, which introduces the need for ... on ConcreteType inline fragments to select type-specific fields), and over-using fragments for one-off queries just adds indirection — they earn their keep when a shape is genuinely reused across multiple queries or components.

Code Example

// UserCard.tsx — the fragment lives next to the component that needs it
import { gql } from "@apollo/client";

export const USER_CARD_FRAGMENT = gql`
  fragment UserCardFields on User {
    id
    name
    avatarUrl
  }
`;

function UserCard({ user }) {
  return (
    <div>
      <img src={user.avatarUrl} />
      <span>{user.name}</span>
    </div>
  );
}

// Dashboard.tsx — the parent spreads the fragment instead of
// re-listing name/avatarUrl by hand
const GET_DASHBOARD = gql`
  query GetDashboard {
    currentUser {
      ...UserCardFields
      notifications { id }
    }
  }
  ${USER_CARD_FRAGMENT}
`;

Common Mistake

A weak answer describes fragments as "just a way to avoid retyping fields." The stronger framing is colocation as an architectural pattern — the component owns its data requirements, the same way it owns its props and styles, which is the same instinct behind GraphQL Code Generator setups and Relay's compiler. Mention the interface/union inline-fragment case (... on Admin { permissions }) if the interviewer pushes into polymorphic schema design.

SECTION 4 - ERRORS, REAL-TIME & PERFORMANCE

Q9. How do you handle errors in GraphQL — and what's the difference between GraphQL errors and network errors?

ROI: ★★★★☆ Frequency: High

Short Answer

GraphQL has two structurally different failure modes, and Apollo's ApolloError distinguishes them. A network error means the HTTP request itself failed (timeout, DNS, 500, CORS) — no GraphQL response body was even produced. A GraphQL error means the HTTP request succeeded (typically still a 200) but one or more fields failed to resolve server-side, and the response contains both a partial data object and a populated errors array describing what went wrong and where. Apollo exposes both on error.networkError and error.graphQLErrors respectively, and you generally need to check both to build a correct error UI.

Detailed Answer

This dual-error model is one of GraphQL's most interview-tested quirks precisely because it violates the REST intuition that a 200 means success. A single query can partially succeed: it might fetch a user's name fine while the nested posts resolver throws (a permissions error, an upstream service outage) — the response comes back 200 with data.user.name populated, data.user.posts: null, and an errors array entry pointing at the posts path. A UI that only checks error before rendering can miss this: error is populated whenever either array is non-empty, but the correct handling (show the user's name, show a small inline error for the posts section) requires reading which specific field failed.

AspectNetwork ErrorGraphQL Error

Centralizing this logic in an errorLink (part of the link chain from Q3) is the production pattern: log every graphQLErrors entry with its path, handle 401s from networkError globally (redirect to login), and let component-level error UI stay simple because the systemic cases are already handled upstream.

Code Example

import { onError } from "@apollo/client/link/error";

const errorLink = onError(({ graphQLErrors, networkError }) => {
  if (graphQLErrors) {
    graphQLErrors.forEach(({ message, path }) =>
      console.error(`[GraphQL error] path: ${path}, message: ${message}`)
    );
  }
  if (networkError) {
    console.error(`[Network error]: ${networkError}`);
    // e.g. redirect to /login on a 401
  }
});

// In a component: partial data + partial errors can coexist
function UserProfile() {
  const { data, error } = useQuery(GET_USER_WITH_POSTS);

  return (
    <div>
      {data?.user?.name && <h1>{data.user.name}</h1>}
      {data?.user?.posts ? (
        <PostList posts={data.user.posts} />
      ) : (
        error?.graphQLErrors.some((e) => e.path?.includes("posts")) && (
          <p>Couldn't load posts right now.</p>
        )
      )}
    </div>
  );
}

Interview Gold Point

The single fact that separates strong candidates: "a GraphQL response can be 200 OK and still contain errors, because errors are per-field, not per-request." Following that up with the partial-data-plus-partial-errors UI pattern — rendering what resolved and flagging only what didn't, rather than discarding the whole response on any error — demonstrates you've actually built resilient GraphQL UI, not just handled the happy path.

Q10. How do GraphQL subscriptions work, and how do you use them for real-time data with Apollo?

ROI: ★★★☆☆ Frequency: Medium

Short Answer

A subscription is a long-lived operation, typically over a WebSocket, where the client says "notify me every time X happens" and the server pushes a new payload each time that event fires — the inverse of the request/response model queries and mutations use. In Apollo Client, useSubscription(SUBSCRIPTION) opens the connection on mount and returns { data, loading, error } that update on every push, and the transport is configured via a separate GraphQLWsLink (using the graphql-ws library) split from your regular HttpLink using Apollo's split link based on operation type.

Detailed Answer

Wiring subscriptions in requires a second transport, because HTTP can't hold a connection open for server-initiated pushes. Apollo's split function inspects each outgoing operation and routes subscriptions to a WebSocket link while queries/mutations continue over the normal HTTP link — this is boilerplate every Apollo-plus-subscriptions setup needs, and forgetting it is the most common "why doesn't my subscription connect" bug.

In practice, subscriptions are used less often than you'd expect for "real-time" features, for a few honest reasons: they require infrastructure the REST/HTTP-only backend doesn't already have (a persistent WebSocket server, connection-count scaling concerns), and for many "real-time-ish" needs, pollInterval on a regular query is simpler and good enough (a dashboard that refreshes every 10 seconds doesn't need a live socket). Subscriptions earn their cost for genuinely event-driven UX — live chat, live cursors, a live order-status tracker — where the latency of polling would be unacceptable.

A common pattern is combining subscriptions with the cache-update techniques from Q6: a useSubscription callback (onData) writes the pushed item into the cache (e.g. appending a new chat message to an existing query result) rather than replacing an entire query, so the subscription behaves like a targeted, continuous mutation.

Code Example

import { GraphQLWsLink } from "@apollo/client/link/subscriptions";
import { createClient } from "graphql-ws";
import { split, HttpLink } from "@apollo/client";
import { getMainDefinition } from "@apollo/client/utilities";

const wsLink = new GraphQLWsLink(
  createClient({ url: "wss://api.example.com/graphql" })
);
const httpLink = new HttpLink({ uri: "https://api.example.com/graphql" });

// Route subscriptions over WS, everything else over HTTP
const splitLink = split(
  ({ query }) => {
    const def = getMainDefinition(query);
    return def.kind === "OperationDefinition" && def.operation === "subscription";
  },
  wsLink,
  httpLink
);

const client = new ApolloClient({ link: splitLink, cache: new InMemoryCache() });

// Component usage
const NEW_MESSAGE = gql`
  subscription OnNewMessage($chatId: ID!) {
    messageAdded(chatId: $chatId) { id text sender }
  }
`;

function ChatWindow({ chatId }) {
  const { data } = useSubscription(NEW_MESSAGE, {
    variables: { chatId },
    onData: ({ client, data }) => {
      // Append the pushed message into the existing query's cache result
      client.cache.updateQuery({ query: GET_MESSAGES, variables: { chatId } }, (prev) => ({
        messages: [...prev.messages, data.data.messageAdded],
      }));
    },
  });

  return null; // rendering driven by the GET_MESSAGES query elsewhere
}

Interview Favorite

Interviewers reward the honest scoping answer: know how to wire subscriptions (the split-link pattern is the concrete detail to name), but also know when not to reach for them — pollInterval or a simple refetch-on-focus often covers "keep this reasonably fresh" without the infrastructure cost of a persistent WebSocket layer. That judgment call is what separates "knows the API" from "knows when to use it."

Q11. What is the N+1 problem and DataLoader — and why should a client-side engineer even know about it?

ROI: ★★★★☆ Frequency: High

Short Answer

The N+1 problem is a server-side resolver performance bug: if a query fetches a list of N posts and each post's resolver independently fetches its author, naive resolver code issues 1 query for the posts plus N more queries (one per post) for authors — N+1 round trips to the database for data that could have been fetched in 2. DataLoader fixes this by batching and caching those per-request lookups so all N author-fetches inside one tick get coalesced into a single batched query. It's implemented server-side, but frontend engineers are asked about it constantly because GraphQL's client-declared, arbitrarily nested query shape is exactly what makes N+1 easy to trigger — the client's query structure directly causes or avoids the problem.

Detailed Answer

This is a "client engineers get asked server concepts" question, and the reason is legitimate: in REST, the backend team controls exactly what a given endpoint fetches, so N+1 is entirely their problem to notice. In GraphQL, the client writes the query shape — a client that nests three levels deep (users { posts { comments { author } } } ) is effectively choosing the resolver call pattern the server has to execute. A frontend engineer who understands N+1 writes flatter, more deliberate queries and knows to flag "why is this query taking 4 seconds" as likely an N+1 issue on the backend, rather than a frontend bug to chase.

DataLoader (originally from Facebook, same lineage as GraphQL itself) solves it with two techniques: batching — within a single tick of the event loop, all individual .load(id) calls are collected and sent to the underlying data source as one batched call (batchGetUsers([1, 2, 3]) instead of three separate calls) — and caching — within one request's lifetime, loading the same ID twice returns the cached promise instead of hitting the data source again. Both are scoped per-request (a fresh DataLoader instance per incoming GraphQL request) specifically so caching doesn't leak stale data across different users' requests.

For an interview, the useful framing is: "I don't write DataLoader, but I understand it exists because my query shape as a client author is what triggers or avoids N+1 resolver fan-out, and if I see suspiciously slow nested-list queries, DataLoader/batching on the backend is the first thing I'd ask about."

Code Example

// Server-side resolver WITHOUT DataLoader — N+1 triggered by a
// client query that nests posts -> author
const resolvers = {
  Post: {
    author: (post) => db.users.findById(post.authorId), // one DB call per post
  },
};

// WITH DataLoader — same client query, batched into one call
const userLoader = new DataLoader(async (ids) => {
  const users = await db.users.findByIds(ids); // one batched call for all ids
  return ids.map((id) => users.find((u) => u.id === id));
});

const resolvers = {
  Post: {
    author: (post) => userLoader.load(post.authorId), // batched + per-request cached
  },
};

# The client query that would trigger N+1 without batching —
# note the client controls this shape, not the server
query {
  posts(limit: 50) {
    title
    author { name }   # 50 posts -> 50 individual author lookups without DataLoader
  }
}

Common Mistake

Don't claim ownership you don't have — DataLoader is implemented in resolver code, which is usually a backend concern. The mistake to avoid is either blanking entirely ("that's not my layer") or overclaiming implementation details you haven't touched. The right answer demonstrates awareness of the mechanism and, critically, connects it back to something a frontend engineer does control: the shape and depth of the queries they write.

Q12. Apollo Client vs urql vs React Query for GraphQL — when should you choose which?

ROI: ★★★★☆ Frequency: High

Short Answer

Apollo Client is the full-featured, batteries-included option: a normalized cache, first-class subscriptions, a large ecosystem, and deep devtools — at the cost of bundle size and a learning curve around cache configuration. urql targets a similar problem with a smaller footprint and a more explicit, exchange-based (middleware) architecture; its default "document cache" is simpler than Apollo's normalized cache (though a normalized-cache addon, @urql/exchange-graphcache, closes that gap). React Query isn't GraphQL-specific at all — it's a generic async-state manager, so "using it for GraphQL" means you fire your own fetch/graphql-request call inside a useQuery, getting React Query's caching-by-query-key, retries, and stale-time model, but none of GraphQL-aware normalization out of the box.

Detailed Answer

The decision is really about how much you value GraphQL-specific cache normalization versus bundle size and mental model simplicity. If your app already thinks in Apollo's terms (heavy list pagination, real-time subscriptions, deeply relational data with entities appearing in many queries), Apollo's normalized cache pays for its complexity by keeping that data automatically consistent everywhere. If you want GraphQL's query language but a lighter runtime and don't need Apollo's full feature surface, urql is the well-supported middle ground. If your team already standardized on React Query for REST and is adding a handful of GraphQL calls, reusing React Query (with a thin graphql-request client) avoids introducing a second data-fetching paradigm — at the cost of losing automatic entity-level cache updates; you fall back to manual queryClient.invalidateQueries or setQueryData calls, much like the refetchQueries/update pattern in Apollo but without normalization backing it.

AspectApollo ClienturqlReact Query (+ fetch/graphql-request)
Cache modelNormalized by entity, automaticDocument cache by default; normalized via graphcache exchangeKeyed by query key; no entity normalization
Bundle sizeLargerSmallerSmall (already likely present for REST)
SubscriptionsFirst-class, matureSupportedNot applicable — you'd hand-roll it
Best fitGraphQL-native apps with complex relational dataTeams wanting GraphQL with a lighter, more explicit clientTeams standardized on React Query already, GraphQL is incidental

Note the framing isn't "Apollo is best" — it's "pick based on how much GraphQL-aware caching you actually need versus what data-fetching paradigm your team has already standardized on."

Interview Favorite

The strongest answers avoid a tool-tribalism take and instead frame it as "what does normalized entity caching buy me here, and what does it cost." Naming React Query's lack of GraphQL-aware normalization as a real trade-off (not a dismissal) — you keep one fetching paradigm across REST and GraphQL, but lose automatic cross-query consistency — shows you understand the underlying mechanism these libraries are wrapping, not just their marketing pages.

Q13. How do you test components that use Apollo Client, using MockedProvider?

ROI: ★★★★☆ Frequency: High

Short Answer

MockedProvider (from @apollo/client/testing) replaces the real ApolloProvider in tests with a client wired to a list of mocks — each mock declares an exact request (query + variables) and the result (or error) Apollo should return when a component fires that exact request. If a component fires a request that doesn't match any mock, the test fails loudly rather than silently hitting a real network — which is exactly the "mock at the boundary, run the real component code" philosophy applied to GraphQL.

Detailed Answer

The matching is strict by default: query document and variables must match exactly, which is a double-edged feature — it catches "the component sent the wrong variables" bugs, but it also means tests break if you reorder fields or the component's query changes even trivially. This is functionally the same trade-off as MSW for REST (see the Testing chapter): you're mocking the transport boundary, not the component's internals, so the component's actual query-building, loading/error rendering, and data-mapping logic all run for real.

A few practical patterns: use addTypename: false only if you're deliberately testing without the normalized cache typename injection (rare); prefer asserting on rendered output (screen.findByText(...)) after awaiting the mock resolves, exactly like async RTL patterns elsewhere; and test the error path by supplying error: new Error(...) on a mock instead of result, to verify your component's error UI without needing a real failing server.

For mutations, remember the mock's request.variables must match what the mutation is actually called with at runtime — a common flaky-test cause is a mock written before the component's mutation call was finalized, so the variables silently drift out of sync and the "no matching mock" error appears with a diff that's easy to misread as a rendering bug rather than a request-shape mismatch.

Code Example

import { render, screen } from "@testing-library/react";
import { MockedProvider } from "@apollo/client/testing";
import { GET_USER } from "./queries";
import UserProfile from "./UserProfile";

const happyMock = {
  request: { query: GET_USER, variables: { id: "1" } },
  result: {
    data: { user: { id: "1", name: "Ada Lovelace" } },
  },
};

const errorMock = {
  request: { query: GET_USER, variables: { id: "1" } },
  error: new Error("Network down"),
};

test("renders the loaded user", async () => {
  render(
    <MockedProvider mocks={[happyMock]} addTypename={false}>
      <UserProfile id="1" />
    </MockedProvider>
  );

  expect(await screen.findByText("Ada Lovelace")).toBeInTheDocument();
});

test("renders an error state on failure", async () => {
  render(
    <MockedProvider mocks={[errorMock]} addTypename={false}>
      <UserProfile id="1" />
    </MockedProvider>
  );

  expect(await screen.findByText(/something went wrong/i)).toBeInTheDocument();
});

Interview Gold Point

Frame MockedProvider the same way you'd frame MSW: "mock the network boundary, exercise the real component code." The specific detail interviewers listen for is the exact-match requirement on query + variables, and the debugging instinct that follows from it — an "unmatched mock" test failure is usually a request-shape drift bug, not a rendering bug, and knowing that saves real debugging time.

Q14. What are the common interview pitfalls around GraphQL — including how it can still be over-fetched, and typical schema design mistakes?

ROI: ★★★★★ Frequency: Extremely High

Short Answer

The biggest trap is treating "we use GraphQL" as automatic proof of efficient data fetching — GraphQL only prevents over-fetching if the query author is disciplined. A component that requests every field "just in case," or a page that spreads three unrelated fragments it doesn't fully use, is just as over-fetched as a bloated REST response — the mechanism moved from the server to the client, but the discipline problem didn't disappear. Beyond that, the recurring schema-design mistakes interviewers probe are: over-nesting types that force N+1-prone resolvers (Q11), getting nullability backwards (marking fragile fields non-null, so one failure nulls out a whole subtree — Q2), and designing mutations that don't return enough of the changed object for the client to update its cache without a manual refetch (Q6).

Detailed Answer

"GraphQL can still be over-fetched" is worth stating explicitly and unprompted, because it's the follow-up interviewers use to separate marketing-level knowledge from real experience. Common ways it happens in practice: a shared fragment grows over time as different components add fields to it, and eventually every consumer of that fragment pulls fields only one of them actually uses; a query is copy-pasted from a similar screen and never trimmed; or a component over-fetches "for the cache" (requesting fields so they're pre-warmed elsewhere), which quietly reintroduces the exact waste GraphQL was adopted to eliminate. The fix is the same discipline REST needed — audit what a component actually renders, keep fragments scoped to real reuse, and treat query size as a code-review concern, not a solved problem.

Schema design mistakes that come up repeatedly:

  • Wrong nullability defaults — marking fields non-null "for convenience" when the underlying resolver can genuinely fail; one flaky field then nulls out an entire parent object at runtime (Q2).
  • Deeply nested relational fields with no batching story — a schema that lets clients traverse three or four levels deep without the team having DataLoader/batching in place invites N+1 performance cliffs the moment a real client query exercises that depth (Q11).
  • Mutations that under-return — a mutation that only returns { success: true } instead of the created/updated object forces every caller into an extra refetchQueries round trip that a well-designed mutation payload would have avoided (Q6).
  • Leaking a "God query" root — a single enormous Query type with dozens of loosely related top-level fields, mirroring the REST "endpoint sprawl" problem GraphQL was meant to fix, just moved into schema fields instead of URLs.
  • No pagination story on list fields — a posts: [Post!]! field with no way to limit or page through results is a footgun the moment the list grows past a few hundred rows (Q7).

The meta-point worth landing in an interview: GraphQL moves several decisions (what data to fetch, how deep to nest, how to paginate) from the backend team to whoever writes each query — which is powerful, but it also moves the responsibility for avoiding waste and performance cliffs to that same person. A senior answer treats GraphQL as a tool that requires ongoing query and schema discipline, not a technology that solved data-fetching by being adopted.

Interview Favorite

Volunteering "GraphQL doesn't eliminate over-fetching, it just moves the responsibility for avoiding it to the query author" — without being asked — is one of the highest-signal single sentences you can say in this entire chapter. Pair it with one concrete schema-design mistake (nullability defaults or under-returning mutations are the two most commonly probed) to show the awareness goes beyond the client and into how you'd review a schema PR.

QUICK REVISION SHEET

  • GraphQL vs REST: one endpoint, client-declared shape — fixes over-fetching and under-fetching, but gives up free HTTP caching in exchange for a heavier client-side cache.
  • Schema/types/queries/mutations/subscriptions: the schema is the typed contract; queries read, mutations write (and should return the changed object), subscriptions push over a long-lived connection; get nullability defaults right or one failing field nulls out its whole parent.
  • Apollo Client setup: a client is a link (network pipeline: auth, error handling, HTTP transport) plus an InMemoryCache, shared app-wide via ApolloProvider and Context — not just a fetch wrapper.
  • useQuery/useMutation: useQuery is declarative and auto-fires; useMutation is imperative and you call it — always guard on loading/error before touching data, since data can be undefined on first render.
  • Normalized cache & fetch policies: Apollo caches by entity (typename:id), not by query; cache-first/network-only/cache-and-network/no-cache trade off freshness vs requests — know that network-only still writes to cache but no-cache does not.
  • Cache updates after mutations: in-place edits merge automatically via normalization; new list items need the update function; refetchQueries is the simple-but-costly fallback; optimisticResponse gives instant UI with automatic rollback on failure.
  • Pagination: cursor-based (Relay connections: edges/pageInfo/endCursor) stays stable under concurrent inserts/deletes; offset-based is simpler but breaks under list mutation — Apollo drives both through fetchMore plus a cache merge field policy.
  • Fragments: colocate a component's data requirements as a named, reusable selection set spread into parent queries, so one field addition updates every consumer instead of requiring hand-edited duplication.
  • Error handling: a GraphQL response can be 200 OK and still contain per-field errors alongside partial data — check both graphQLErrors and networkError, and render what resolved while flagging only what failed.
  • Subscriptions: long-lived WebSocket pushes via useSubscription, requiring a separate GraphQLWsLink split from HTTP by operation type; reach for pollInterval instead when true push semantics aren't worth the infrastructure cost.
  • N+1 & DataLoader: a server-side batching/caching fix for resolver fan-out, but the client's query shape and nesting depth is what triggers or avoids it — know the mechanism even though you don't implement it.
  • Apollo vs urql vs React Query: choose based on how much GraphQL-aware normalized caching you need versus bundle size and whatever data-fetching paradigm the team already standardized on.
  • Testing with MockedProvider: mock the network boundary with exact query+variables matches and let the real component logic run; an "unmatched mock" failure usually means the request shape drifted, not that rendering broke.
  • Common pitfalls: GraphQL only prevents over-fetching if queries stay disciplined — bloated shared fragments and copy-pasted queries reintroduce the same waste; watch for nullability mistakes, under-returning mutations, unpaginated list fields, and "God query" schemas.
