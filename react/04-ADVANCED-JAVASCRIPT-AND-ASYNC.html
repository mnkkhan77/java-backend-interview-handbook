SECTION 1 - THE EVENT LOOP

Q1. How does the JavaScript event loop work? Explain the call stack, task queue, and microtask queue.

ROI: ★★★★★ Frequency: Extremely High

Short Answer

JavaScript runs on a single thread with one call stack. Synchronous code executes frame by frame on that stack. Asynchronous work (timers, network, DOM events) is handed off to the host (the browser or Node), which pushes a callback into a queue when the work completes. The event loop is the loop that, whenever the call stack is empty, drains all pending microtasks (promise reactions, queueMicrotask, MutationObserver) and then takes exactly one macrotask (a timer callback, an I/O callback, a UI event) before repeating.

Detailed Answer

The crucial mental model is: JavaScript itself has no concept of "later." The language spec only knows how to run a job to completion on the call stack. Everything asynchronous is provided by the host environment — Web APIs in the browser, libuv in Node — which owns the timers, the network stack, and the queues. The event loop is the choreography between the engine and the host.

The pieces

  • Call stack — the LIFO stack of function frames currently executing. Only one thing runs at a time. If a function never returns (an infinite loop), the whole page freezes because the loop can never advance.
  • Macrotask queue (a.k.a. task queue) — callbacks from setTimeout, setInterval, I/O, and UI events. One macrotask is processed per loop iteration.
  • Microtask queue — callbacks from resolved/rejected promises (.then/.catch/.finally), await continuations, queueMicrotask, and MutationObserver. The entire microtask queue is drained after every task and before the next task or a render.

One iteration of the loop

  1. Run the current script / one macrotask to completion (until the stack empties).
  2. Drain all microtasks — including any microtasks those microtasks schedule. This can starve rendering if you keep scheduling microtasks.
  3. The browser may perform layout/paint (roughly aligned to requestAnimationFrame at ~60fps).
  4. Pick the next macrotask and repeat.

The single most important consequence for interviews: a promise callback (microtask) always runs before a setTimeout callback (macrotask) that was scheduled in the same tick, even a setTimeout(fn, 0). Microtasks are the fast lane.

Code Example

console.log("1: sync start");

setTimeout(() => console.log("2: setTimeout (macrotask)"), 0);

Promise.resolve().then(() => console.log("3: promise (microtask)"));

queueMicrotask(() => console.log("4: queueMicrotask (microtask)"));

console.log("5: sync end");

// Output:
// 1: sync start
// 5: sync end
// 3: promise (microtask)
// 4: queueMicrotask (microtask)
// 2: setTimeout (macrotask)
//
// All synchronous code runs first (1, 5). The stack empties, so the loop
// drains ALL microtasks (3, 4) before touching the macrotask queue (2).

Project Example

In React this explains why state updates inside an event handler are batched and flushed asynchronously, and why useEffect cleanup + re-run ordering feels the way it does. It also explains a classic bug: doing heavy synchronous work (parsing a large JSON blob, sorting 100k rows) inside a click handler freezes the UI, because that work sits on the single call stack and no paint can happen until it returns. The fix is to yield — chunk the work across macrotasks, move it to a Web Worker, or use startTransition.

Senior Engineer Perspective

The interviewer is checking whether you understand that JS concurrency is cooperative, not preemptive — nothing interrupts a running function. Common traps: (1) claiming setTimeout(fn, 0) runs "immediately" — it runs after the current task and after all microtasks; (2) not knowing that await desugars into a microtask, so code after an await is scheduled like a .then; (3) not realising an infinite chain of microtasks can starve rendering and macrotasks entirely. A senior answer names the host environment as the owner of the queues, not "JavaScript."

Q2. "Trace the output." What does this log, and in what order?

ROI: ★★★★★ Frequency: High

Short Answer

You must classify every line as synchronous, microtask, or macrotask, and remember that the microtask queue is fully drained between each macrotask. The trick is that async function bodies run synchronously up to the first await, and everything after an await is a microtask.

Detailed Answer

Walk through it deterministically. Never guess — build the queues on paper.

Code Example

console.log("A");

setTimeout(() => console.log("B"), 0);

async function run() {
  console.log("C");            // sync — runs when run() is called
  await null;                  // suspends; rest becomes a microtask
  console.log("D");            // microtask
}

run();

Promise.resolve()
  .then(() => console.log("E"))
  .then(() => console.log("F"));

console.log("G");

// Reasoning:
//   Sync pass:  A, C (inside run before await), G
//   run() hits `await null` -> schedules "D" as a microtask
//   Promise chain schedules "E" as a microtask
//   Microtask drain: D, E ... then .then(F) is queued during E, so F runs next
//   Microtask drain continues: F
//   Macrotask: B
//
// FINAL OUTPUT:
// A
// C
// G
// D
// E
// F
// B

Subtle point on D vs E ordering: both are queued as microtasks, but run() is called before the Promise.resolve().then(...) line executes, so await null's continuation ("D") is enqueued first, then "E". Chained .thens do not all queue at once — the second .then callback is only enqueued once the first resolves, which is why "F" comes after "E" but the whole chain still finishes before the macrotask "B".

Senior Engineer Perspective

These puzzles look like trivia but they test a real skill: reasoning about ordering when you have a race between a promise and a timer, which is exactly what causes flaky tests and "sometimes the spinner flashes" bugs. The two mistakes that sink candidates are (a) forgetting that the code before the first await is synchronous, and (b) assuming a whole .then().then() chain is enqueued in one go. State your rule out loud — "drain all microtasks, then one macrotask" — before you trace.

Q3. requestAnimationFrame vs setTimeout — which should you use for animation and why?

ROI: ★★★☆☆ Frequency: Medium

Short Answer

Use requestAnimationFrame (rAF) for anything visual. The browser calls your rAF callback right before the next repaint, synchronised to the display's refresh rate (~60fps, or 120fps on high-refresh screens) and automatically paused when the tab is hidden. setTimeout is unaware of the paint cycle, drifts, keeps firing in background tabs, and produces janky animation.

Detailed Answer

AspectrequestAnimationFramesetTimeout(fn, 16)
TimingJust before next repaint, refresh-syncedBest-effort after ~16ms, not paint-aligned
Background tabPaused (saves CPU/battery)Keeps firing (throttled to ~1s)
Frame budgetCallback gets a high-res timestampNo timing info
Refresh rateAdapts to 60/120/144 HzFixed guess, drifts over time

Because setTimeout delays are a minimum, not a guarantee, repeated timers accumulate drift and land in the wrong part of the frame, causing tearing and dropped frames. rAF hands control back exactly when the browser is ready to paint.

Code Example

// Smooth scroll-to-top using rAF
function animateTo(target, duration = 300) {
  const start = window.scrollY;
  const startTime = performance.now();

  function frame(now) {
    const t = Math.min(1, (now - startTime) / duration);
    const eased = 1 - Math.pow(1 - t, 3);      // ease-out cubic
    window.scrollTo(0, start + (target - start) * eased);
    if (t < 1) requestAnimationFrame(frame);   // keep going until done
  }
  requestAnimationFrame(frame);
}

Senior Engineer Perspective

The nuance: rAF is for visual updates; for precise timing (audio, game logic) you want a fixed timestep decoupled from rendering. Also note that in React you rarely hand-roll rAF loops — you reach for CSS transitions/transforms (GPU-composited, off the main thread) or a library like Framer Motion. Mention that setTimeout is throttled to ~1s in background tabs — candidates who know this understand why their "keep-alive polling" behaves oddly when the tab is hidden.

SECTION 2 - PROMISES

Q4. What are the three states of a Promise, and how does chaining actually work?

ROI: ★★★★★ Frequency: Extremely High

Short Answer

A promise is a placeholder for a future value in one of three states: pending, fulfilled (resolved with a value), or rejected (with a reason). It's settled once it moves to fulfilled or rejected, and that transition is one-way and permanent. Each .then() returns a new promise, which is why chains work — the return value of one callback becomes the resolution value of the next.

Detailed Answer

The behaviour that trips people up is how .then flattens return values:

  • If a .then callback returns a plain value, the next promise fulfils with that value.
  • If it returns another promise, the chain waits for that promise to settle and adopts its result (this is "thenable assimilation" — no nested Promise<Promise>).
  • If it throws, the next promise rejects with the thrown error, skipping subsequent .then callbacks until a .catch.

.catch(fn) is just sugar for .then(undefined, fn), and .finally(fn) runs regardless of outcome and passes the settlement through untouched (its return value is ignored unless it throws or returns a rejected promise).

Code Example

Promise.resolve(1)
  .then(x => x + 1)                 // returns 2  -> next fulfils with 2
  .then(x => Promise.resolve(x * 10)) // returns a promise -> waits, adopts 20
  .then(x => { throw new Error("boom at " + x); }) // rejects
  .then(x => console.log("skipped", x))            // skipped
  .catch(err => console.log("caught:", err.message)) // caught: boom at 20
  .finally(() => console.log("cleanup runs regardless"));

// Output:
// caught: boom at 20
// cleanup runs regardless

Senior Engineer Perspective

Probes: "What does .then return?" (a new promise — this is the whole basis of chaining). "Can a settled promise change state?" (no, it's immutable once settled). A subtle trap is that .finally does not receive the value and does not alter it — juniors sometimes try to transform data in .finally. Also worth mentioning: an unhandled rejection now surfaces as an unhandledrejection event / process warning, so a chain without a terminal .catch is a real bug, not just style.

Q5. Promise.all vs Promise.allSettled vs Promise.race vs Promise.any — when do you use each?

ROI: ★★★★★ Frequency: High

Short Answer

All four take an iterable of promises and return one promise, but they differ in when they settle and how they treat failures. Use all for "I need everything and want to fail fast," allSettled for "run everything and tell me each outcome," race for "first to settle wins (success or failure)," and any for "first success wins, ignore failures until all fail."

Detailed Answer

MethodFulfils whenRejects whenResult shape
Promise.allALL fulfilANY rejects (fails fast)Array of values
Promise.allSettledALL settleNever rejectsArray of {status, value|reason}
Promise.raceFirst settles (fulfilled)First settles (rejected)Single value/reason
Promise.anyFirst fulfilsALL reject (AggregateError)Single value

Promise.all rejects the instant one input rejects — but note the other promises keep running; they aren't cancelled, you just stop waiting for them. That's why for a "load everything, show partial results" dashboard you want allSettled, which never rejects and gives you a per-item verdict.

race settles on the first to finish regardless of outcome, which makes it ideal for timeouts. any is its optimistic cousin — it resolves on the first success and only rejects (with an AggregateError containing all reasons) if every input fails, perfect for "hit whichever mirror responds first."

Code Example

// Fail-fast fan-out
const [user, orders] = await Promise.all([
  fetchUser(id),
  fetchOrders(id),
]); // rejects if EITHER fails

// Resilient dashboard: never throws, inspect each result
const results = await Promise.allSettled([fetchA(), fetchB(), fetchC()]);
const ok = results.filter(r => r.status === "fulfilled").map(r => r.value);
const failed = results.filter(r => r.status === "rejected");

// Timeout pattern with race
function withTimeout(promise, ms) {
  const timeout = new Promise((_, reject) =>
    setTimeout(() => reject(new Error("timeout")), ms)
  );
  return Promise.race([promise, timeout]);
}

// Fastest successful mirror wins
const fastest = await Promise.any([
  fetch("https://mirror1/data"),
  fetch("https://mirror2/data"),
]);

Senior Engineer Perspective

Follow-ups: "With Promise.all, if one rejects, do the others stop?" (No — promises can't be cancelled from the outside; use AbortController for real cancellation.) "Difference between race and any?" (race settles on first settle including rejection; any settles on first fulfilment.) A senior nuance: Promise.all preserves input order in the result array even though the promises finish in arbitrary order — the array index maps to the input index, not completion order.

Q6. How do you correctly handle errors in promise chains and async/await?

ROI: ★★★★☆ Frequency: High

Short Answer

In promise chains, attach a terminal .catch — a rejection propagates down the chain until something catches it. In async/await, wrap awaited calls in try/catch. The most common bug is a floating promise with no error handler, producing an unhandled rejection; the second most common is swallowing errors by catching too broadly and doing nothing.

Detailed Answer

Rejections behave like exceptions travelling down the chain. A single .catch at the end handles a rejection from any earlier step. But there are traps:

  • Errors inside a .then callback after the .catch aren't caught by that catch — position matters.
  • Not returning the inner promise inside a callback breaks the chain, so its rejection escapes handling ("fire and forget" inside a chain).
  • A try/catch around an async call without await catches nothing — the function returns a pending promise before it can reject.

Code Example

// BUG: try/catch without await catches nothing
async function bad() {
  try {
    fetchData();          // missing await -> rejection escapes this try
  } catch (e) {
    console.log("never reached", e);
  }
}

// CORRECT
async function good() {
  try {
    const data = await fetchData();
    return process(data);
  } catch (e) {
    logger.error("fetchData failed", e);
    throw new AppError("Could not load data", { cause: e }); // rethrow with context
  } finally {
    hideSpinner();
  }
}

// Chain equivalent
fetchData()
  .then(process)
  .catch(e => { logger.error(e); throw e; }); // catch, log, rethrow to caller

Senior Engineer Perspective

Interviewers love the "try/catch without await" trap because it exposes whether you understand that an async function's rejection only materialises at the await point. Strong candidates also mention the { cause } option on Error for preserving the original error, and the difference between recoverable errors (catch, show a toast, retry) and programmer errors (let them bubble to an error boundary / crash reporter). Blanket catch blocks that silently swallow are worse than no catch at all.

Q7. How do you convert a callback-based API into a promise?

ROI: ★★★☆☆ Frequency: Medium

Short Answer

Wrap the call in new Promise((resolve, reject) => ...) and call resolve/reject from inside the callback. For Node-style (err, result) callbacks, use util.promisify; for custom shapes, write the wrapper by hand. Crucially, call the executor exactly once and never mix a callback and a promise for the same operation.

Code Example

// Promisify a Node-style callback: fn(...args, (err, result) => ...)
function promisify(fn) {
  return (...args) =>
    new Promise((resolve, reject) => {
      fn(...args, (err, result) => {
        if (err) reject(err);
        else resolve(result);
      });
    });
}

const readFileAsync = promisify(fs.readFile);
const text = await readFileAsync("./config.json", "utf8");

// Wrap an event-based API (e.g. an image load)
function loadImage(src) {
  return new Promise((resolve, reject) => {
    const img = new Image();
    img.onload = () => resolve(img);
    img.onerror = () => reject(new Error("Failed to load " + src));
    img.src = src;
  });
}

Senior Engineer Perspective

Gotchas the interviewer listens for: the Promise executor runs synchronously; resolve/reject after the first call are no-ops (the promise is already settled), so double-settling is a silent bug, not an error. Also, throwing synchronously inside the executor automatically rejects the promise. Bonus points for mentioning that this pattern is a "boundary adapter" — you promisify once at the edge and keep the rest of the codebase promise-native.

SECTION 3 - ASYNC / AWAIT

Q8. What is async/await really doing under the hood?

ROI: ★★★★★ Frequency: Extremely High

Short Answer

async/await is syntactic sugar over promises and (conceptually) generators. An async function always returns a promise. await pauses the function, yielding control back to the event loop, and schedules the code after it as a microtask that resumes when the awaited value settles. It does not block the thread — it suspends just that one function.

Detailed Answer

When you call an async function, it runs synchronously until the first await. At that point it returns a pending promise to the caller and "parks" its remaining body. When the awaited promise settles, the continuation is queued as a microtask, the function resumes with the resolved value (or throws the rejection reason at the await expression, which is why try/catch works), and eventually the returned promise settles.

Two facts flow from this: (1) an async function that returns a value x actually resolves with Promise.resolve(x), so returning a promise doesn't double-wrap; (2) await on a non-promise value still defers to a microtask (await 5 is not free — the rest of the function runs later).

Code Example

async function demo() {
  console.log("1"); // sync
  const v = await Promise.resolve("resolved");
  console.log("2", v); // microtask continuation
  return "done";       // resolves the returned promise with "done"
}

console.log("start");
demo().then(r => console.log("3", r));
console.log("end");

// Output:
// start
// 1
// end
// 2 resolved
// 3 done

Senior Engineer Perspective

Say clearly: "await does not block the thread, it suspends the function and lets the event loop keep running." Juniors describe it as "waiting/blocking," which betrays a wrong model — if it truly blocked, the UI would freeze. Follow-up: "Is return await x different from return x?" Functionally usually identical, but return await keeps the frame on the stack one extra microtask (relevant for stack traces and for try/finally — inside a try, return await ensures rejections are caught locally).

Q9. Sequential vs parallel awaits — why is my async code slow, and how do I fix it?

ROI: ★★★★★ Frequency: High

Short Answer

Because await pauses the function, writing awaits back-to-back runs the operations sequentially — each waits for the previous to finish even when they're independent. If the tasks don't depend on each other, start them all first (or pass them to Promise.all) so they run in parallel, then await the combined result.

Detailed Answer

This is one of the most impactful real-world performance bugs. Three independent 300ms requests awaited in sequence take 900ms; in parallel they take ~300ms. The fix is to kick off the promises (which begins their work immediately) before awaiting. Only serialise when there's a genuine data dependency — e.g. the second call needs the first call's result.

Code Example

// SLOW — sequential: ~900ms total
async function slow(id) {
  const user = await fetchUser(id);       // 300ms
  const posts = await fetchPosts(id);     // waits, then 300ms
  const stats = await fetchStats(id);     // waits, then 300ms
  return { user, posts, stats };
}

// FAST — parallel: ~300ms total (independent calls)
async function fast(id) {
  const [user, posts, stats] = await Promise.all([
    fetchUser(id),
    fetchPosts(id),
    fetchStats(id),
  ]);
  return { user, posts, stats };
}

// Genuine dependency -> sequential is CORRECT
async function dependent(id) {
  const user = await fetchUser(id);
  const org  = await fetchOrg(user.orgId); // needs user.orgId
  return org;
}

Senior Engineer Perspective

A subtle intermediate form worth knowing: you can start the promises without await, do other work, then await them later — const p1 = fetchUser(id); const p2 = fetchPosts(id); const user = await p1; const posts = await p2; — this is also parallel because the requests fire on the assignment lines, not the await lines. The interviewer may push on error handling: with Promise.all a single failure rejects the whole thing; if you want partial success switch to allSettled. This is exactly the trade-off from Q5, applied.

Q10. How do you loop over async work — and what's the trap with forEach?

ROI: ★★★☆☆ Frequency: Medium

Short Answer

Array.prototype.forEach ignores the promise your async callback returns, so it does not wait — your surrounding code runs before the iterations finish. Use a for...of loop with await for sequential processing, or map + Promise.all for parallel processing.

Code Example

// BUG: forEach does not await -> "done" logs before any item finishes
async function broken(items) {
  items.forEach(async (item) => {
    await save(item);
  });
  console.log("done"); // runs immediately, saves still pending
}

// Sequential (one at a time, ordered) — for rate limits or ordering
async function sequential(items) {
  for (const item of items) {
    await save(item);
  }
  console.log("done"); // truly after all saves
}

// Parallel (all at once) — fastest for independent items
async function parallel(items) {
  await Promise.all(items.map(item => save(item)));
  console.log("done");
}

Senior Engineer Perspective

Beyond the forEach trap, seniors talk about concurrency control: firing 10,000 requests in parallel with Promise.all will hammer the server and blow rate limits. The mature answer is a bounded pool (e.g. process N at a time with something like p-limit, or chunk the array). Mention that for streaming/backpressure scenarios, for await...of over an async iterable is the idiomatic tool.

SECTION 4 - ADVANCED PATTERNS

Q11. Implement debounce from scratch. When do you use it?

ROI: ★★★★★ Frequency: Extremely High

Short Answer

Debounce delays invoking a function until it has stopped being called for a given wait period — it "collapses" a burst of calls into one, executed after the burst ends. It's the go-to for search-as-you-type, autosave, and resize handlers, where you only care about the final state after activity settles.

Detailed Answer

The mechanism: every call clears the previous pending timer and sets a new one. Only when wait ms pass with no new calls does the timer fire. So typing "react" fires once, wait ms after the last keystroke, not five times.

Code Example

function debounce(fn, wait) {
  let timer = null;
  function debounced(...args) {
    clearTimeout(timer);              // cancel the pending call
    timer = setTimeout(() => {
      timer = null;
      fn.apply(this, args);           // preserve `this` and latest args
    }, wait);
  }
  debounced.cancel = () => { clearTimeout(timer); timer = null; };
  return debounced;
}

// Usage: only search after the user pauses typing for 300ms
const search = debounce((q) => api.search(q), 300);
input.addEventListener("input", (e) => search(e.target.value));

Senior Engineer Perspective

Interviewers push on: preserving this and arguments (use a regular function + fn.apply, not an arrow that loses this); a cancel method (needed for React cleanup); and a leading/immediate option to fire on the first call instead of the last. In React, a common bug is creating a new debounced function on every render — you must wrap it in useMemo/useRef (or use useDebouncedCallback) or the timer resets each render and never fires.

Q12. Implement throttle. How is it different from debounce?

ROI: ★★★★★ Frequency: Extremely High

Short Answer

Throttle guarantees a function runs at most once per interval no matter how often it's called — it enforces a steady maximum rate. Debounce waits for silence before firing once; throttle fires regularly during activity. Use throttle for scroll position, mousemove, drag, and analytics pings; use debounce for "act after the user stops."

Detailed Answer

DebounceThrottle
FiresOnce, after calls stopAt most once per interval, during calls
Rapid burst of 100 calls / 1s (wait 200ms)1 call total~5 calls, evenly spaced
Best forSearch box, autosave, resize-endScroll, mousemove, drag, rate-limited pings

Code Example

function throttle(fn, interval) {
  let last = 0;
  let timer = null;
  return function (...args) {
    const now = Date.now();
    const remaining = interval - (now - last);
    if (remaining <= 0) {
      // enough time has passed -> run immediately (leading edge)
      last = now;
      fn.apply(this, args);
    } else if (!timer) {
      // schedule a trailing call so the final event isn't dropped
      timer = setTimeout(() => {
        last = Date.now();
        timer = null;
        fn.apply(this, args);
      }, remaining);
    }
  };
}

const onScroll = throttle(() => updateScrollProgress(), 100);
window.addEventListener("scroll", onScroll);

Senior Engineer Perspective

The distinguishing follow-up is the trailing call: a naive throttle that only fires on the leading edge can drop the final event, so the UI ends up one frame stale (e.g. scroll progress that never reaches 100%). The implementation above handles both edges. Also expect: "How would you throttle with rAF instead of a timer?" — for pure visual updates, gating on requestAnimationFrame naturally caps you at the refresh rate and avoids doing work between paints.

Q13. Explain currying and partial application. Implement a curry helper.

ROI: ★★★☆☆ Frequency: Medium

Short Answer

Currying transforms a function of N arguments into N nested unary functions: f(a, b, c) becomes f(a)(b)(c). Partial application is fixing some arguments now and getting a function that takes the rest later. Both are ways to build specialised functions from general ones and to make functions more composable.

Detailed Answer

Partial application (often via Function.prototype.bind or a closure) pre-fills arguments; currying is the stricter form that hands arguments one at a time. They matter in functional pipelines and in React for creating reusable handler factories.

Code Example

// Partial application
const multiply = (a, b) => a * b;
const double = multiply.bind(null, 2); // fix a = 2
double(5); // 10

// A flexible curry that accepts args in groups
function curry(fn) {
  return function curried(...args) {
    if (args.length >= fn.length) return fn.apply(this, args);
    return (...next) => curried.apply(this, args.concat(next));
  };
}

const add = curry((a, b, c) => a + b + c);
add(1)(2)(3);   // 6
add(1, 2)(3);   // 6
add(1)(2, 3);   // 6

// Practical: a handler factory in React
const onFieldChange = (field) => (e) =>
  setForm((f) => ({ ...f, [field]: e.target.value }));
<input onChange={onFieldChange("email")} />

Senior Engineer Perspective

The interviewer wants you to distinguish the two terms crisply (many candidates conflate them) and to relate fn.length (arity) to how the curry helper knows when it has enough arguments. A senior note: over-currying hurts readability and, in React, factory functions like onFieldChange("email") create a new function each render — usually fine, but worth knowing when you're chasing referential-equality re-renders with React.memo.

Q14. What are generators and iterators, and where are they actually useful?

ROI: ★★★☆☆ Frequency: Medium

Short Answer

An iterator is any object with a next() method returning { value, done }; the iterable protocol (a Symbol.iterator method) is what lets for...of and spread work. A generator (function*) is a factory for iterators — yield pauses the function and hands a value out, resuming where it left off on the next next() call. They shine for lazy sequences, custom iteration, and modelling async flows.

Detailed Answer

Generators give you pausable functions with preserved local state — which is precisely the machinery async/await is built on (an async function is essentially a generator that yields promises and is auto-driven). Practically, they're great for infinite/lazy sequences (you compute values on demand, not all upfront), for making your own objects iterable, and they power libraries like Redux-Saga where yielded "effects" describe side effects declaratively.

Code Example

// Lazy infinite sequence — nothing is computed until you pull
function* idGenerator() {
  let id = 1;
  while (true) yield id++;
}
const ids = idGenerator();
ids.next().value; // 1
ids.next().value; // 2

// Make a custom object iterable
const range = {
  from: 1, to: 3,
  *[Symbol.iterator]() {
    for (let i = this.from; i <= this.to; i++) yield i;
  },
};
[...range];            // [1, 2, 3]
for (const n of range) console.log(n); // 1, 2, 3

// Two-way communication: next() can send a value back into the generator
function* chat() {
  const name = yield "What's your name?";
  yield `Hello, ${name}!`;
}
const c = chat();
c.next().value;        // "What's your name?"
c.next("Ada").value;   // "Hello, Ada!"

Senior Engineer Perspective

The connection interviewers fish for: "How does await relate to generators?" — async/await is generators + a promise-driving runtime. Bonus: async function* creates async generators consumed with for await...of, the clean way to model streaming/paginated APIs with backpressure. Be honest that in day-to-day React app code you rarely hand-write generators — but understanding them demystifies async/await and iteration protocols.

Q15. Implement a memoize higher-order function. What are the caveats?

ROI: ★★★★☆ Frequency: High

Short Answer

Memoization caches a function's results keyed by its arguments so repeated calls with the same inputs return instantly. It's a classic space-for-time trade-off, valid only for pure functions (same input → same output, no side effects). The hard parts are key generation, cache invalidation, and unbounded memory growth.

Code Example

function memoize(fn, keyFn = (...a) => JSON.stringify(a)) {
  const cache = new Map();
  return function (...args) {
    const key = keyFn(...args);
    if (cache.has(key)) return cache.get(key);
    const result = fn.apply(this, args);
    cache.set(key, result);
    return result;
  };
}

const slowFib = (n) => (n < 2 ? n : slowFibM(n - 1) + slowFibM(n - 2));
const slowFibM = memoize(slowFib); // turns O(2^n) into O(n)
slowFibM(40); // fast

Senior Engineer Perspective

Caveats to raise proactively: (1) JSON.stringify keys fail for functions, undefined, circular refs, and are order-sensitive for object args; (2) an unbounded Map is a memory leak — real caches need an LRU bound or a TTL; (3) memoizing across object identity for single-arg functions is better done with a WeakMap so entries are GC'd when the key object dies. Tie it to React: useMemo, useCallback, and React.memo are memoization, and the same "is this actually pure / do the deps really change?" reasoning applies.

Q16. AbortController — how do you cancel a fetch or any async operation?

ROI: ★★★★☆ Frequency: High

Short Answer

AbortController exposes a signal you pass to fetch (and many other APIs). Calling controller.abort() triggers the signal, causing the fetch to reject with an AbortError. It's the standard way to cancel in-flight requests — essential for cancelling stale requests when a component unmounts or a search term changes.

Detailed Answer

Promises themselves can't be cancelled, so the platform added AbortSignal as an out-of-band cancellation channel. Beyond fetch, you can listen to signal.addEventListener("abort", ...) to make your own async work abortable, and you can pass the same signal to addEventListener to auto-remove listeners on abort. In React 18, the classic use is aborting a fetch in a useEffect cleanup to avoid setting state on an unmounted component and to prevent race conditions between fast-changing requests.

Code Example

useEffect(() => {
  const controller = new AbortController();

  fetch(`/api/search?q=${query}`, { signal: controller.signal })
    .then(res => res.json())
    .then(setResults)
    .catch(err => {
      if (err.name === "AbortError") return; // expected on cancel — ignore
      setError(err);
    });

  // Cleanup: abort the previous request when query changes / unmount
  return () => controller.abort();
}, [query]);

// Abort on a timeout with the built-in helper
const res = await fetch(url, { signal: AbortSignal.timeout(5000) });

Senior Engineer Perspective

Key points that mark seniority: an aborted fetch rejects with an AbortError you must deliberately swallow, not treat as a failure; aborting stops you waiting and lets the browser cancel the request, but doesn't guarantee the server didn't process it (so it's not a substitute for idempotency); and the real reason to abort in React is the race condition — without it, a slow earlier request can resolve after a faster later one and overwrite fresh results with stale data. Note that AbortSignal.timeout() and AbortSignal.any() are the modern conveniences.

Q17. ES Modules vs CommonJS — what are the differences and why do they matter for tree-shaking?

ROI: ★★★★☆ Frequency: High

Short Answer

CommonJS (require/module.exports) is synchronous, dynamic, and resolved at runtime — Node's original module system. ES Modules (import/export) are the standard, statically analysable, asynchronously loaded, and support live bindings. Because ESM imports are static, bundlers can determine exactly which exports are used and drop the rest — that's tree-shaking, which CommonJS largely defeats.

Detailed Answer

AspectCommonJSES Modules
Syntaxrequire / module.exportsimport / export
LoadingSynchronous, runtimeAsync, parsed statically
BindingsCopy of value at require timeLive, read-only bindings
Tree-shakeableNo (dynamic)Yes (static analysis)
Top-level awaitNoYes
this at top levelmodule.exportsundefined

Tree-shaking is dead-code elimination based on static import/export analysis. Because ESM tells the bundler at parse time exactly what each module exports and imports, a bundler like Vite/Rollup/webpack can keep only the reachable exports. This is why importing import { debounce } from "lodash-es" can ship just that function, while const _ = require("lodash") tends to pull the whole library. It relies on modules being side-effect-free — hence the "sideEffects": false field in package.json.

Code Example

// CommonJS — dynamic, evaluated at runtime, hard to tree-shake
const { debounce } = require("lodash");
module.exports = { helper };

// ESM — static, live bindings, tree-shakeable
import { debounce } from "lodash-es";
export function helper() { /* ... */ }

// Live binding demo (ESM): importers see updates to the exported variable
// counter.js
export let count = 0;
export const inc = () => count++;
// main.js
import { count, inc } from "./counter.js";
inc();
console.log(count); // 1  — a live view, NOT a stale copy

Senior Engineer Perspective

Deep follow-ups: "Why can't CommonJS be tree-shaken?" (imports are dynamic expressions resolvable only at runtime, so the bundler can't prove an export is unused). "What breaks tree-shaking in ESM?" (side effects at module top level, re-export barrels, and "sideEffects" not set correctly). Also mention live bindings — the fact that ESM imports are live read-only views, not value copies, is a favourite distinguishing question, and it's why you can't reassign an import.

Q18. How does garbage collection work, and what causes memory leaks in a JS/React app?

ROI: ★★★★★ Frequency: High

Short Answer

JS engines use a mark-and-sweep collector: starting from roots (global object, current call stack), they mark everything reachable and sweep away the rest. You never free() manually. A "leak" is therefore always the same thing — an object stays reachable when you no longer need it. The four classic culprits are lingering timers/listeners, closures capturing large state, detached DOM nodes, and ever-growing caches/global collections.

Detailed Answer

Reachability is the whole model: as long as any chain of references from a root reaches an object, it can't be collected. Leaks happen when you accidentally keep such a chain alive.

  • Forgotten event listeners / subscriptions: addEventListener, WebSocket handlers, store subscriptions, and setInterval that are never removed keep their callbacks — and everything the callbacks close over — alive. In React, always clean these up in the useEffect return function.
  • Closures capturing large data: a long-lived callback that closes over a big array pins that array in memory even if you only needed one field.
  • Detached DOM nodes: you remove a node from the document but a JS variable (or a listener) still references it — the node and its subtree can't be freed.
  • Unbounded caches / module-level Maps: a global Map you keep set-ting into but never evict grows forever.

Code Example

// LEAK: interval + listener never cleaned up; closure keeps `data` alive
function LeakyComponent({ data }) {
  useEffect(() => {
    const id = setInterval(() => process(data), 1000);
    window.addEventListener("resize", onResize);
    // no cleanup -> interval + listener survive unmount
  }, []);
}

// FIXED: cleanup on unmount frees everything
function CleanComponent({ data }) {
  useEffect(() => {
    const id = setInterval(() => process(data), 1000);
    window.addEventListener("resize", onResize);
    return () => {
      clearInterval(id);
      window.removeEventListener("resize", onResize);
    };
  }, [data]);
}

Project Example

A dashboard that mounts/unmounts many chart widgets is the classic offender: each widget subscribes to a resize observer and a data store. If a widget forgets to unsubscribe on unmount, navigating around the app slowly climbs in the DevTools Memory profiler and the app gets sluggish over a long session. You catch it by taking heap snapshots before/after repeated mount-unmount cycles and looking for a growing count of "detached" nodes or retained component instances.

Senior Engineer Perspective

Say "reachability" and "mark-and-sweep" explicitly — that's the vocabulary. Then demonstrate the debugging workflow: Chrome DevTools → Memory → heap snapshots and the "detached DOM tree" view, or the Performance/Memory timeline showing a sawtooth that never returns to baseline. The senior insight is that in React nearly every leak traces back to a missing useEffect cleanup or a stale closure — knowing the framework-level fix is what they want, not just the CS-101 definition.

Q19. What are WeakMap, WeakSet, and WeakRef, and what problem do they solve?

ROI: ★★★☆☆ Frequency: Medium

Short Answer

WeakMap/WeakSet hold weak references to their keys/values: if the only thing referencing an object is the WeakMap, that object can still be garbage-collected, and its entry disappears automatically. This makes them the leak-proof choice for associating metadata with objects you don't own the lifecycle of. WeakRef is a lower-level, explicit weak reference to a single object.

Detailed Answer

A normal Map keeps its keys reachable forever, so caching against DOM nodes or component instances in a plain Map leaks. A WeakMap's keys are held weakly, so when the DOM node is removed and nothing else references it, both the node and its WeakMap entry are collected. Constraints: keys must be objects (not primitives), and WeakMaps are not iterable and have no size — precisely because their contents can vanish at any time, so exposing enumeration would be non-deterministic.

WeakRef (and its companion FinalizationRegistry) let you hold an object without preventing its collection; you call ref.deref() to get the object or undefined if it's gone. It's a sharp tool for advanced caches — the spec explicitly warns against relying on GC timing.

Code Example

// Associate private metadata with objects — auto-cleaned when the key dies
const metadata = new WeakMap();

function tag(node, info) {
  metadata.set(node, info); // node held weakly
}
// When `node` is removed from the DOM and dereferenced elsewhere,
// the WeakMap entry is GC'd automatically — no manual cleanup, no leak.

// WeakRef: cache without pinning the object in memory
const cache = new WeakRef(expensiveObject);
const obj = cache.deref(); // the object, or undefined if collected

Senior Engineer Perspective

The contrast question is "why not just use a Map?" — answer: a Map's strong keys prevent GC and leak. The follow-up trap is "iterate a WeakMap" — you can't, and explaining why (non-deterministic contents) shows real understanding. On WeakRef, a senior signals caution: it's rarely needed, GC timing is unspecified so you must not build correctness on it, and reaching for it usually means an ordinary bounded/LRU cache would be simpler and more predictable.
