SECTION 1 - THE EVENT LOOP

Q1. How does the JavaScript event loop work? Explain the call stack, task queue, and microtask queue.

ROI: ★★★★★ Frequency: Extremely High

Short Answer

JavaScript runs on a single thread with one call stack. Synchronous code executes frame by frame on that stack. Asynchronous work (timers, network, DOM events) is handed off to the host (the browser or Node), which pushes a callback into a queue when the work completes. The event loop is the loop that, whenever the call stack is empty, drains all pending microtasks (promise reactions, queueMicrotask, MutationObserver) and then takes exactly one macrotask (a timer callback, an I/O callback, a UI event) before repeating.

Detailed Answer

The crucial mental model is: JavaScript itself has no concept of "later." The language spec only knows how to run a job to completion on the call stack. Everything asynchronous is provided by the host environment — Web APIs in the browser, libuv in Node — which owns the timers, the network stack, and the queues. The event loop is the choreography between the engine and the host.

The pieces

  • Call stack — the LIFO stack of function frames currently executing. Only one thing runs at a time. If a function never returns (an infinite loop), the whole page freezes because the loop can never advance.
  • Macrotask queue (a.k.a. task queue) — callbacks from setTimeout, setInterval, I/O, and UI events. One macrotask is processed per loop iteration.
  • Microtask queue — callbacks from resolved/rejected promises (.then/.catch/.finally), await continuations, queueMicrotask, and MutationObserver. The entire microtask queue is drained after every task and before the next task or a render.

One iteration of the loop

  1. Run the current script / one macrotask to completion (until the stack empties).
  2. Drain all microtasks — including any microtasks those microtasks schedule. This can starve rendering if you keep scheduling microtasks.
  3. The browser may perform layout/paint (roughly aligned to requestAnimationFrame at ~60fps).
  4. Pick the next macrotask and repeat.

The single most important consequence for interviews: a promise callback (microtask) always runs before a setTimeout callback (macrotask) that was scheduled in the same tick, even a setTimeout(fn, 0). Microtasks are the fast lane.

Code Example

console.log("1: sync start");

setTimeout(() => console.log("2: setTimeout (macrotask)"), 0);

Promise.resolve().then(() => console.log("3: promise (microtask)"));

queueMicrotask(() => console.log("4: queueMicrotask (microtask)"));

console.log("5: sync end");

// Output:
// 1: sync start
// 5: sync end
// 3: promise (microtask)
// 4: queueMicrotask (microtask)
// 2: setTimeout (macrotask)
//
// All synchronous code runs first (1, 5). The stack empties, so the loop
// drains ALL microtasks (3, 4) before touching the macrotask queue (2).

Project Example

In React this explains why state updates inside an event handler are batched and flushed asynchronously, and why useEffect cleanup + re-run ordering feels the way it does. It also explains a classic bug: doing heavy synchronous work (parsing a large JSON blob, sorting 100k rows) inside a click handler freezes the UI, because that work sits on the single call stack and no paint can happen until it returns. The fix is to yield — chunk the work across macrotasks, move it to a Web Worker, or use startTransition.

Senior Engineer Perspective

The interviewer is checking whether you understand that JS concurrency is cooperative, not preemptive — nothing interrupts a running function. Common traps: (1) claiming setTimeout(fn, 0) runs "immediately" — it runs after the current task and after all microtasks; (2) not knowing that await desugars into a microtask, so code after an await is scheduled like a .then; (3) not realising an infinite chain of microtasks can starve rendering and macrotasks entirely. A senior answer names the host environment as the owner of the queues, not "JavaScript."

Q2. "Trace the output." What does this log, and in what order?

ROI: ★★★★★ Frequency: High

Short Answer

You must classify every line as synchronous, microtask, or macrotask, and remember that the microtask queue is fully drained between each macrotask. The trick is that async function bodies run synchronously up to the first await, and everything after an await is a microtask.

Detailed Answer

Walk through it deterministically. Never guess — build the queues on paper.

Code Example

console.log("A");

setTimeout(() => console.log("B"), 0);

async function run() {
  console.log("C");            // sync — runs when run() is called
  await null;                  // suspends; rest becomes a microtask
  console.log("D");            // microtask
}

run();

Promise.resolve()
  .then(() => console.log("E"))
  .then(() => console.log("F"));

console.log("G");

// Reasoning:
//   Sync pass:  A, C (inside run before await), G
//   run() hits `await null` -> schedules "D" as a microtask
//   Promise chain schedules "E" as a microtask
//   Microtask drain: D, E ... then .then(F) is queued during E, so F runs next
//   Microtask drain continues: F
//   Macrotask: B
//
// FINAL OUTPUT:
// A
// C
// G
// D
// E
// F
// B

Subtle point on D vs E ordering: both are queued as microtasks, but run() is called before the Promise.resolve().then(...) line executes, so await null's continuation ("D") is enqueued first, then "E". Chained .thens do not all queue at once — the second .then callback is only enqueued once the first resolves, which is why "F" comes after "E" but the whole chain still finishes before the macrotask "B".

Senior Engineer Perspective

These puzzles look like trivia but they test a real skill: reasoning about ordering when you have a race between a promise and a timer, which is exactly what causes flaky tests and "sometimes the spinner flashes" bugs. The two mistakes that sink candidates are (a) forgetting that the code before the first await is synchronous, and (b) assuming a whole .then().then() chain is enqueued in one go. State your rule out loud — "drain all microtasks, then one macrotask" — before you trace.

Q3. requestAnimationFrame vs setTimeout — which should you use for animation and why?

ROI: ★★★☆☆ Frequency: Medium

Short Answer

Use requestAnimationFrame (rAF) for anything visual. The browser calls your rAF callback right before the next repaint, synchronised to the display's refresh rate (~60fps, or 120fps on high-refresh screens) and automatically paused when the tab is hidden. setTimeout is unaware of the paint cycle, drifts, keeps firing in background tabs, and produces janky animation.

Detailed Answer

AspectrequestAnimationFramesetTimeout(fn, 16)
TimingJust before next repaint, refresh-syncedBest-effort after ~16ms, not paint-aligned
Background tabPaused (saves CPU/battery)Keeps firing (throttled to ~1s)
Frame budgetCallback gets a high-res timestampNo timing info
Refresh rateAdapts to 60/120/144 HzFixed guess, drifts over time

Because setTimeout delays are a minimum, not a guarantee, repeated timers accumulate drift and land in the wrong part of the frame, causing tearing and dropped frames. rAF hands control back exactly when the browser is ready to paint.

Code Example

// Smooth scroll-to-top using rAF
function animateTo(target, duration = 300) {
  const start = window.scrollY;
  const startTime = performance.now();

  function frame(now) {
    const t = Math.min(1, (now - startTime) / duration);
    const eased = 1 - Math.pow(1 - t, 3);      // ease-out cubic
    window.scrollTo(0, start + (target - start) * eased);
    if (t < 1) requestAnimationFrame(frame);   // keep going until done
  }
  requestAnimationFrame(frame);
}

Senior Engineer Perspective

The nuance: rAF is for visual updates; for precise timing (audio, game logic) you want a fixed timestep decoupled from rendering. Also note that in React you rarely hand-roll rAF loops — you reach for CSS transitions/transforms (GPU-composited, off the main thread) or a library like Framer Motion. Mention that setTimeout is throttled to ~1s in background tabs — candidates who know this understand why their "keep-alive polling" behaves oddly when the tab is hidden.

SECTION 2 - PROMISES

Q4. What are the three states of a Promise, and how does chaining actually work?

ROI: ★★★★★ Frequency: Extremely High

Short Answer

A promise is a placeholder for a future value in one of three states: pending, fulfilled (resolved with a value), or rejected (with a reason). It's settled once it moves to fulfilled or rejected, and that transition is one-way and permanent. Each .then() returns a new promise, which is why chains work — the return value of one callback becomes the resolution value of the next.

Detailed Answer

The behaviour that trips people up is how .then flattens return values:

  • If a .then callback returns a plain value, the next promise fulfils with that value.
  • If it returns another promise, the chain waits for that promise to settle and adopts its result (this is "thenable assimilation" — no nested Promise<Promise>).
  • If it throws, the next promise rejects with the thrown error, skipping subsequent .then callbacks until a .catch.

.catch(fn) is just sugar for .then(undefined, fn), and .finally(fn) runs regardless of outcome and passes the settlement through untouched (its return value is ignored unless it throws or returns a rejected promise).

Code Example

Promise.resolve(1)
  .then(x => x + 1)                 // returns 2  -> next fulfils with 2
  .then(x => Promise.resolve(x * 10)) // returns a promise -> waits, adopts 20
  .then(x => { throw new Error("boom at " + x); }) // rejects
  .then(x => console.log("skipped", x))            // skipped
  .catch(err => console.log("caught:", err.message)) // caught: boom at 20
  .finally(() => console.log("cleanup runs regardless"));

// Output:
// caught: boom at 20
// cleanup runs regardless

Senior Engineer Perspective

Probes: "What does .then return?" (a new promise — this is the whole basis of chaining). "Can a settled promise change state?" (no, it's immutable once settled). A subtle trap is that .finally does not receive the value and does not alter it — juniors sometimes try to transform data in .finally. Also worth mentioning: an unhandled rejection now surfaces as an unhandledrejection event / process warning, so a chain without a terminal .catch is a real bug, not just style.

Q5. Promise.all vs Promise.allSettled vs Promise.race vs Promise.any — when do you use each?

ROI: ★★★★★ Frequency: High

Short Answer

All four take an iterable of promises and return one promise, but they differ in when they settle and how they treat failures. Use all for "I need everything and want to fail fast," allSettled for "run everything and tell me each outcome," race for "first to settle wins (success or failure)," and any for "first success wins, ignore failures until all fail."

Detailed Answer

MethodFulfils whenRejects whenResult shape
Promise.allALL fulfilANY rejects (fails fast)Array of values
Promise.allSettledALL settleNever rejectsArray of {status, value|reason}
Promise.raceFirst settles (fulfilled)First settles (rejected)Single value/reason
Promise.anyFirst fulfilsALL reject (AggregateError)Single value

Promise.all rejects the instant one input rejects — but note the other promises keep running; they aren't cancelled, you just stop waiting for them. That's why for a "load everything, show partial results" dashboard you want allSettled, which never rejects and gives you a per-item verdict.

race settles on the first to finish regardless of outcome, which makes it ideal for timeouts. any is its optimistic cousin — it resolves on the first success and only rejects (with an AggregateError containing all reasons) if every input fails, perfect for "hit whichever mirror responds first."

Code Example

// Fail-fast fan-out
const [user, orders] = await Promise.all([
  fetchUser(id),
  fetchOrders(id),
]); // rejects if EITHER fails

// Resilient dashboard: never throws, inspect each result
const results = await Promise.allSettled([fetchA(), fetchB(), fetchC()]);
const ok = results.filter(r => r.status === "fulfilled").map(r => r.value);
const failed = results.filter(r => r.status === "rejected");

// Timeout pattern with race
function withTimeout(promise, ms) {
  const timeout = new Promise((_, reject) =>
    setTimeout(() => reject(new Error("timeout")), ms)
  );
  return Promise.race([promise, timeout]);
}

// Fastest successful mirror wins
const fastest = await Promise.any([
  fetch("https://mirror1/data"),
  fetch("https://mirror2/data"),
]);

Senior Engineer Perspective

Follow-ups: "With Promise.all, if one rejects, do the others stop?" (No — promises can't be cancelled from the outside; use AbortController for real cancellation.) "Difference between race and any?" (race settles on first settle including rejection; any settles on first fulfilment.) A senior nuance: Promise.all preserves input order in the result array even though the promises finish in arbitrary order — the array index maps to the input index, not completion order.

Q6. How do you correctly handle errors in promise chains and async/await?

ROI: ★★★★☆ Frequency: High

Short Answer

In promise chains, attach a terminal .catch — a rejection propagates down the chain until something catches it. In async/await, wrap awaited calls in try/catch. The most common bug is a floating promise with no error handler, producing an unhandled rejection; the second most common is swallowing errors by catching too broadly and doing nothing.

Detailed Answer

Rejections behave like exceptions travelling down the chain. A single .catch at the end handles a rejection from any earlier step. But there are traps:

  • Errors inside a .then callback after the .catch aren't caught by that catch — position matters.
  • Not returning the inner promise inside a callback breaks the chain, so its rejection escapes handling ("fire and forget" inside a chain).
  • A try/catch around an async call without await catches nothing — the function returns a pending promise before it can reject.

Code Example

// BUG: try/catch without await catches nothing
async function bad() {
  try {
    fetchData();          // missing await -> rejection escapes this try
  } catch (e) {
    console.log("never reached", e);
  }
}

// CORRECT
async function good() {
  try {
    const data = await fetchData();
    return process(data);
  } catch (e) {
    logger.error("fetchData failed", e);
    throw new AppError("Could not load data", { cause: e }); // rethrow with context
  } finally {
    hideSpinner();
  }
}

// Chain equivalent
fetchData()
  .then(process)
  .catch(e => { logger.error(e); throw e; }); // catch, log, rethrow to caller

Senior Engineer Perspective

Interviewers love the "try/catch without await" trap because it exposes whether you understand that an async function's rejection only materialises at the await point. Strong candidates also mention the { cause } option on Error for preserving the original error, and the difference between recoverable errors (catch, show a toast, retry) and programmer errors (let them bubble to an error boundary / crash reporter). Blanket catch blocks that silently swallow are worse than no catch at all.

Q7. How do you convert a callback-based API into a promise?

ROI: ★★★☆☆ Frequency: Medium

Short Answer

Wrap the call in new Promise((resolve, reject) => ...) and call resolve/reject from inside the callback. For Node-style (err, result) callbacks, use util.promisify; for custom shapes, write the wrapper by hand. Crucially, call the executor exactly once and never mix a callback and a promise for the same operation.

Code Example

// Promisify a Node-style callback: fn(...args, (err, result) => ...)
function promisify(fn) {
  return (...args) =>
    new Promise((resolve, reject) => {
      fn(...args, (err, result) => {
        if (err) reject(err);
        else resolve(result);
      });
    });
}

const readFileAsync = promisify(fs.readFile);
const text = await readFileAsync("./config.json", "utf8");

// Wrap an event-based API (e.g. an image load)
function loadImage(src) {
  return new Promise((resolve, reject) => {
    const img = new Image();
    img.onload = () => resolve(img);
    img.onerror = () => reject(new Error("Failed to load " + src));
    img.src = src;
  });
}

Senior Engineer Perspective

Gotchas the interviewer listens for: the Promise executor runs synchronously; resolve/reject after the first call are no-ops (the promise is already settled), so double-settling is a silent bug, not an error. Also, throwing synchronously inside the executor automatically rejects the promise. Bonus points for mentioning that this pattern is a "boundary adapter" — you promisify once at the edge and keep the rest of the codebase promise-native.

SECTION 3 - ASYNC / AWAIT

Q8. What is async/await really doing under the hood?

ROI: ★★★★★ Frequency: Extremely High

Short Answer

async/await is syntactic sugar over promises and (conceptually) generators. An async function always returns a promise. await pauses the function, yielding control back to the event loop, and schedules the code after it as a microtask that resumes when the awaited value settles. It does not block the thread — it suspends just that one function.

Detailed Answer

When you call an async function, it runs synchronously until the first await. At that point it returns a pending promise to the caller and "parks" its remaining body. When the awaited promise settles, the continuation is queued as a microtask, the function resumes with the resolved value (or throws the rejection reason at the await expression, which is why try/catch works), and eventually the returned promise settles.

Two facts flow from this: (1) an async function that returns a value x actually resolves with Promise.resolve(x), so returning a promise doesn't double-wrap; (2) await on a non-promise value still defers to a microtask (await 5 is not free — the rest of the function runs later).

Code Example

async function demo() {
  console.log("1"); // sync
  const v = await Promise.resolve("resolved");
  console.log("2", v); // microtask continuation
  return "done";       // resolves the returned promise with "done"
}

console.log("start");
demo().then(r => console.log("3", r));
console.log("end");

// Output:
// start
// 1
// end
// 2 resolved
// 3 done

Senior Engineer Perspective

Say clearly: "await does not block the thread, it suspends the function and lets the event loop keep running." Juniors describe it as "waiting/blocking," which betrays a wrong model — if it truly blocked, the UI would freeze. Follow-up: "Is return await x different from return x?" Functionally usually identical, but return await keeps the frame on the stack one extra microtask (relevant for stack traces and for try/finally — inside a try, return await ensures rejections are caught locally).

Q9. Sequential vs parallel awaits — why is my async code slow, and how do I fix it?

ROI: ★★★★★ Frequency: High

Short Answer

Because await pauses the function, writing awaits back-to-back runs the operations sequentially — each waits for the previous to finish even when they're independent. If the tasks don't depend on each other, start them all first (or pass them to Promise.all) so they run in parallel, then await the combined result.

Detailed Answer

This is one of the most impactful real-world performance bugs. Three independent 300ms requests awaited in sequence take 900ms; in parallel they take ~300ms. The fix is to kick off the promises (which begins their work immediately) before awaiting. Only serialise when there's a genuine data dependency — e.g. the second call needs the first call's result.

Code Example

// SLOW — sequential: ~900ms total
async function slow(id) {
  const user = await fetchUser(id);       // 300ms
  const posts = await fetchPosts(id);     // waits, then 300ms
  const stats = await fetchStats(id);     // waits, then 300ms
  return { user, posts, stats };
}

// FAST — parallel: ~300ms total (independent calls)
async function fast(id) {
  const [user, posts, stats] = await Promise.all([
    fetchUser(id),
    fetchPosts(id),
    fetchStats(id),
  ]);
  return { user, posts, stats };
}

// Genuine dependency -> sequential is CORRECT
async function dependent(id) {
  const user = await fetchUser(id);
  const org  = await fetchOrg(user.orgId); // needs user.orgId
  return org;
}

Senior Engineer Perspective

A subtle intermediate form worth knowing: you can start the promises without await, do other work, then await them later — const p1 = fetchUser(id); const p2 = fetchPosts(id); const user = await p1; const posts = await p2; — this is also parallel because the requests fire on the assignment lines, not the await lines. The interviewer may push on error handling: with Promise.all a single failure rejects the whole thing; if you want partial success switch to allSettled. This is exactly the trade-off from Q5, applied.

Q10. How do you loop over async work — and what's the trap with forEach?

ROI: ★★★☆☆ Frequency: Medium

Short Answer

Array.prototype.forEach ignores the promise your async callback returns, so it does not wait — your surrounding code runs before the iterations finish. Use a for...of loop with await for sequential processing, or map + Promise.all for parallel processing.

Code Example

// BUG: forEach does not await -> "done" logs before any item finishes
async function broken(items) {
  items.forEach(async (item) => {
    await save(item);
  });
  console.log("done"); // runs immediately, saves still pending
}

// Sequential (one at a time, ordered) — for rate limits or ordering
async function sequential(items) {
  for (const item of items) {
    await save(item);
  }
  console.log("done"); // truly after all saves
}

// Parallel (all at once) — fastest for independent items
async function parallel(items) {
  await Promise.all(items.map(item => save(item)));
  console.log("done");
}

Senior Engineer Perspective

Beyond the forEach trap, seniors talk about concurrency control: firing 10,000 requests in parallel with Promise.all will hammer the server and blow rate limits. The mature answer is a bounded pool (e.g. process N at a time with something like p-limit, or chunk the array). Mention that for streaming/backpressure scenarios, for await...of over an async iterable is the idiomatic tool.

SECTION 4 - ADVANCED PATTERNS

Q11. Implement debounce from scratch. When do you use it?

ROI: ★★★★★ Frequency: Extremely High

Short Answer

Debounce delays invoking a function until it has stopped being called for a given wait period — it "collapses" a burst of calls into one, executed after the burst ends. It's the go-to for search-as-you-type, autosave, and resize handlers, where you only care about the final state after activity settles.

Detailed Answer

The mechanism: every call clears the previous pending timer and sets a new one. Only when wait ms pass with no new calls does the timer fire. So typing "react" fires once, wait ms after the last keystroke, not five times.

Code Example

function debounce(fn, wait) {
  let timer = null;
  function debounced(...args) {
    clearTimeout(timer);              // cancel the pending call
    timer = setTimeout(() => {
      timer = null;
      fn.apply(this, args);           // preserve `this` and latest args
    }, wait);
  }
  debounced.cancel = () => { clearTimeout(timer); timer = null; };
  return debounced;
}

// Usage: only search after the user pauses typing for 300ms
const search = debounce((q) => api.search(q), 300);
input.addEventListener("input", (e) => search(e.target.value));

Senior Engineer Perspective

Interviewers push on: preserving this and arguments (use a regular function + fn.apply, not an arrow that loses this); a cancel method (needed for React cleanup); and a leading/immediate option to fire on the first call instead of the last. In React, a common bug is creating a new debounced function on every render — you must wrap it in useMemo/useRef (or use useDebouncedCallback) or the timer resets each render and never fires.

Q12. Implement throttle. How is it different from debounce?

ROI: ★★★★★ Frequency: Extremely High

Short Answer

Throttle guarantees a function runs at most once per interval no matter how often it's called — it enforces a steady maximum rate. Debounce waits for silence before firing once; throttle fires regularly during activity. Use throttle for scroll position, mousemove, drag, and analytics pings; use debounce for "act after the user stops."

Detailed Answer

DebounceThrottle
FiresOnce, after calls stopAt most once per interval, during calls
Rapid burst of 100 calls / 1s (wait 200ms)1 call total~5 calls, evenly spaced
Best forSearch box, autosave, resize-endScroll, mousemove, drag, rate-limited pings

Code Example

function throttle(fn, interval) {
  let last = 0;
  let timer = null;
  return function (...args) {
    const now = Date.now();
    const remaining = interval - (now - last);
    if (remaining <= 0) {
      // enough time has passed -> run immediately (leading edge)
      last = now;
      fn.apply(this, args);
    } else if (!timer) {
      // schedule a trailing call so the final event isn't dropped
      timer = setTimeout(() => {
        last = Date.now();
        timer = null;
        fn.apply(this, args);
      }, remaining);
    }
  };
}

const onScroll = throttle(() => updateScrollProgress(), 100);
window.addEventListener("scroll", onScroll);

Senior Engineer Perspective

The distinguishing follow-up is the trailing call: a naive throttle that only fires on the leading edge can drop the final event, so the UI ends up one frame stale (e.g. scroll progress that never reaches 100%). The implementation above handles both edges. Also expect: "How would you throttle with rAF instead of a timer?" — for pure visual updates, gating on requestAnimationFrame naturally caps you at the refresh rate and avoids doing work between paints.

Q13. Explain currying and partial application. Implement a curry helper.

ROI: ★★★☆☆ Frequency: Medium

Short Answer

Currying transforms a function of N arguments into N nested unary functions: f(a, b, c) becomes f(a)(b)(c). Partial application is fixing some arguments now and getting a function that takes the rest later. Both are ways to build specialised functions from general ones and to make functions more composable.

Detailed Answer

Partial application (often via Function.prototype.bind or a closure) pre-fills arguments; currying is the stricter form that hands arguments one at a time. They matter in functional pipelines and in React for creating reusable handler factories.

Code Example

// Partial application
const multiply = (a, b) => a * b;
const double = multiply.bind(null, 2); // fix a = 2
double(5); // 10

// A flexible curry that accepts args in groups
function curry(fn) {
  return function curried(...args) {
    if (args.length >= fn.length) return fn.apply(this, args);
    return (...next) => curried.apply(this, args.concat(next));
  };
}

const add = curry((a, b, c) => a + b + c);
add(1)(2)(3);   // 6
add(1, 2)(3);   // 6
add(1)(2, 3);   // 6

// Practical: a handler factory in React
const onFieldChange = (field) => (e) =>
  setForm((f) => ({ ...f, [field]: e.target.value }));
<input onChange={onFieldChange("email")} />

Senior Engineer Perspective

The interviewer wants you to distinguish the two terms crisply (many candidates conflate them) and to relate fn.length (arity) to how the curry helper knows when it has enough arguments. A senior note: over-currying hurts readability and, in React, factory functions like onFieldChange("email") create a new function each render — usually fine, but worth knowing when you're chasing referential-equality re-renders with React.memo.

Q14. What are generators and iterators, and where are they actually useful?

ROI: ★★★☆☆ Frequency: Medium

Short Answer

An iterator is any object with a next() method returning { value, done }; the iterable protocol (a Symbol.iterator method) is what lets for...of and spread work. A generator (function*) is a factory for iterators — yield pauses the function and hands a value out, resuming where it left off on the next next() call. They shine for lazy sequences, custom iteration, and modelling async flows.

Detailed Answer

Generators give you pausable functions with preserved local state — which is precisely the machinery async/await is built on (an async function is essentially a generator that yields promises and is auto-driven). Practically, they're great for infinite/lazy sequences (you compute values on demand, not all upfront), for making your own objects iterable, and they power libraries like Redux-Saga where yielded "effects" describe side effects declaratively.

Code Example

// Lazy infinite sequence — nothing is computed until you pull
function* idGenerator() {
  let id = 1;
  while (true) yield id++;
}
const ids = idGenerator();
ids.next().value; // 1
ids.next().value; // 2

// Make a custom object iterable
const range = {
  from: 1, to: 3,
  *[Symbol.iterator]() {
    for (let i = this.from; i <= this.to; i++) yield i;
  },
};
[...range];            // [1, 2, 3]
for (const n of range) console.log(n); // 1, 2, 3

// Two-way communication: next() can send a value back into the generator
function* chat() {
  const name = yield "What's your name?";
  yield `Hello, ${name}!`;
}
const c = chat();
c.next().value;        // "What's your name?"
c.next("Ada").value;   // "Hello, Ada!"

Senior Engineer Perspective

The connection interviewers fish for: "How does await relate to generators?" — async/await is generators + a promise-driving runtime. Bonus: async function* creates async generators consumed with for await...of, the clean way to model streaming/paginated APIs with backpressure. Be honest that in day-to-day React app code you rarely hand-write generators — but understanding them demystifies async/await and iteration protocols.

Q15. Implement a memoize higher-order function. What are the caveats?

ROI: ★★★★☆ Frequency: High

Short Answer

Memoization caches a function's results keyed by its arguments so repeated calls with the same inputs return instantly. It's a classic space-for-time trade-off, valid only for pure functions (same input → same output, no side effects). The hard parts are key generation, cache invalidation, and unbounded memory growth.

Code Example

function memoize(fn, keyFn = (...a) => JSON.stringify(a)) {
  const cache = new Map();
  return function (...args) {
    const key = keyFn(...args);
    if (cache.has(key)) return cache.get(key);
    const result = fn.apply(this, args);
    cache.set(key, result);
    return result;
  };
}

const slowFib = (n) => (n < 2 ? n : slowFibM(n - 1) + slowFibM(n - 2));
const slowFibM = memoize(slowFib); // turns O(2^n) into O(n)
slowFibM(40); // fast

Senior Engineer Perspective

Caveats to raise proactively: (1) JSON.stringify keys fail for functions, undefined, circular refs, and are order-sensitive for object args; (2) an unbounded Map is a memory leak — real caches need an LRU bound or a TTL; (3) memoizing across object identity for single-arg functions is better done with a WeakMap so entries are GC'd when the key object dies. Tie it to React: useMemo, useCallback, and React.memo are memoization, and the same "is this actually pure / do the deps really change?" reasoning applies.

Q16. AbortController — how do you cancel a fetch or any async operation?

ROI: ★★★★☆ Frequency: High

Short Answer

AbortController exposes a signal you pass to fetch (and many other APIs). Calling controller.abort() triggers the signal, causing the fetch to reject with an AbortError. It's the standard way to cancel in-flight requests — essential for cancelling stale requests when a component unmounts or a search term changes.

Detailed Answer

Promises themselves can't be cancelled, so the platform added AbortSignal as an out-of-band cancellation channel. Beyond fetch, you can listen to signal.addEventListener("abort", ...) to make your own async work abortable, and you can pass the same signal to addEventListener to auto-remove listeners on abort. In React 18, the classic use is aborting a fetch in a useEffect cleanup to avoid setting state on an unmounted component and to prevent race conditions between fast-changing requests.

Code Example

useEffect(() => {
  const controller = new AbortController();

  fetch(`/api/search?q=${query}`, { signal: controller.signal })
    .then(res => res.json())
    .then(setResults)
    .catch(err => {
      if (err.name === "AbortError") return; // expected on cancel — ignore
      setError(err);
    });

  // Cleanup: abort the previous request when query changes / unmount
  return () => controller.abort();
}, [query]);

// Abort on a timeout with the built-in helper
const res = await fetch(url, { signal: AbortSignal.timeout(5000) });

Senior Engineer Perspective

Key points that mark seniority: an aborted fetch rejects with an AbortError you must deliberately swallow, not treat as a failure; aborting stops you waiting and lets the browser cancel the request, but doesn't guarantee the server didn't process it (so it's not a substitute for idempotency); and the real reason to abort in React is the race condition — without it, a slow earlier request can resolve after a faster later one and overwrite fresh results with stale data. Note that AbortSignal.timeout() and AbortSignal.any() are the modern conveniences.

Q17. ES Modules vs CommonJS — what are the differences and why do they matter for tree-shaking?

ROI: ★★★★☆ Frequency: High

Short Answer

CommonJS (require/module.exports) is synchronous, dynamic, and resolved at runtime — Node's original module system. ES Modules (import/export) are the standard, statically analysable, asynchronously loaded, and support live bindings. Because ESM imports are static, bundlers can determine exactly which exports are used and drop the rest — that's tree-shaking, which CommonJS largely defeats.

Detailed Answer

Q18. How does garbage collection work, and what causes memory leaks in a JS/React app?

ROI: ★★★★★ Frequency: High

Short Answer

JS engines use a mark-and-sweep collector: starting from roots (global object, current call stack), they mark everything reachable and sweep away the rest. You never free() manually. A "leak" is therefore always the same thing — an object stays reachable when you no longer need it. The four classic culprits are lingering timers/listeners, closures capturing large state, detached DOM nodes, and ever-growing caches/global collections.

Detailed Answer

Reachability is the whole model: as long as any chain of references from a root reaches an object, it can't be collected. Leaks happen when you accidentally keep such a chain alive.

  • Forgotten event listeners / subscriptions: addEventListener, WebSocket handlers, store subscriptions, and setInterval that are never removed keep their callbacks — and everything the callbacks close over — alive. In React, always clean these up in the useEffect return function.
  • Closures capturing large data: a long-lived callback that closes over a big array pins that array in memory even if you only needed one field.
  • Detached DOM nodes: you remove a node from the document but a JS variable (or a listener) still references it — the node and its subtree can't be freed.
  • Unbounded caches / module-level Maps: a global Map you keep set-ting into but never evict grows forever.

Code Example

// LEAK: interval + listener never cleaned up; closure keeps `data` alive
function LeakyComponent({ data }) {
  useEffect(() => {
    const id = setInterval(() => process(data), 1000);
    window.addEventListener("resize", onResize);
    // no cleanup -> interval + listener survive unmount
  }, []);
}

// FIXED: cleanup on unmount frees everything
function CleanComponent({ data }) {
  useEffect(() => {
    const id = setInterval(() => process(data), 1000);
    window.addEventListener("resize", onResize);
    return () => {
      clearInterval(id);
      window.removeEventListener("resize", onResize);
    };
  }, [data]);
}

Project Example

A dashboard that mounts/unmounts many chart widgets is the classic offender: each widget subscribes to a resize observer and a data store. If a widget forgets to unsubscribe on unmount, navigating around the app slowly climbs in the DevTools Memory profiler and the app gets sluggish over a long session. You catch it by taking heap snapshots before/after repeated mount-unmount cycles and looking for a growing count of "detached" nodes or retained component instances.

Senior Engineer Perspective

Say "reachability" and "mark-and-sweep" explicitly — that's the vocabulary. Then demonstrate the debugging workflow: Chrome DevTools → Memory → heap snapshots and the "detached DOM tree" view, or the Performance/Memory timeline showing a sawtooth that never returns to baseline. The senior insight is that in React nearly every leak traces back to a missing useEffect cleanup or a stale closure — knowing the framework-level fix is what they want, not just the CS-101 definition.

Q19. What are WeakMap, WeakSet, and WeakRef, and what problem do they solve?

ROI: ★★★☆☆ Frequency: Medium

Short Answer

WeakMap/WeakSet hold weak references to their keys/values: if the only thing referencing an object is the WeakMap, that object can still be garbage-collected, and its entry disappears automatically. This makes them the leak-proof choice for associating metadata with objects you don't own the lifecycle of. WeakRef is a lower-level, explicit weak reference to a single object.

Detailed Answer

A normal Map keeps its keys reachable forever, so caching against DOM nodes or component instances in a plain Map leaks. A WeakMap's keys are held weakly, so when the DOM node is removed and nothing else references it, both the node and its WeakMap entry are collected. Constraints: keys must be objects (not primitives), and WeakMaps are not iterable and have no size — precisely because their contents can vanish at any time, so exposing enumeration would be non-deterministic.

WeakRef (and its companion FinalizationRegistry) let you hold an object without preventing its collection; you call ref.deref() to get the object or undefined if it's gone. It's a sharp tool for advanced caches — the spec explicitly warns against relying on GC timing.

Code Example

// Associate private metadata with objects — auto-cleaned when the key dies
const metadata = new WeakMap();

function tag(node, info) {
  metadata.set(node, info); // node held weakly
}
// When `node` is removed from the DOM and dereferenced elsewhere,
// the WeakMap entry is GC'd automatically — no manual cleanup, no leak.

// WeakRef: cache without pinning the object in memory
const cache = new WeakRef(expensiveObject);
const obj = cache.deref(); // the object, or undefined if collected

Senior Engineer Perspective

The contrast question is "why not just use a Map?" — answer: a Map's strong keys prevent GC and leak. The follow-up trap is "iterate a WeakMap" — you can't, and explaining why (non-deterministic contents) shows real understanding. On WeakRef, a senior signals caution: it's rarely needed, GC timing is unspecified so you must not build correctness on it, and reaching for it usually means an ordinary bounded/LRU cache would be simpler and more predictable.

SECTION 6 - ADVANCED PROMISE PATTERNS

Q20. What is a "thenable" and how does the promise resolution procedure handle it?

ROI: ★★★☆☆ Frequency: Medium

Short Answer

A thenable is any object with a callable .then(onFulfilled, onRejected) method — it doesn't need to be an actual Promise instance. The spec's internal [[Resolve]] procedure treats anything thenable as "promise-like" and assimilates it: instead of resolving immediately with the thenable itself, it calls the thenable's .then and waits for it to settle, so chains never end up with a promise wrapping another promise.

Detailed Answer

This matters because promises are interoperable across libraries by duck typing, not by inheritance — jQuery deferreds, older Angular $q promises, and native promises can all be awaited or chained together as long as they expose a spec-shaped .then. It also means you can accidentally create an infinite loop if a thenable's .then resolves with itself, and it means resolving with a "thenable" always costs at least one extra microtask tick compared to resolving with a plain value, because the engine must call out to the thenable's .then to find out how it settles.

Code Example

// A thenable with no relation to the Promise class at all
const weirdThenable = {
  then(resolve, reject) {
    setTimeout(() => resolve("assimilated!"), 10);
  },
};

Promise.resolve(weirdThenable).then(v => console.log(v)); // "assimilated!"

// await works on ANY thenable, not just real Promises
async function demo() {
  const value = await weirdThenable; // engine calls .then() under the hood
  console.log(value); // "assimilated!"
}

// Danger: a thenable that resolves with itself hangs forever
const cyclic = { then(resolve) { resolve(cyclic); } };
// Promise.resolve(cyclic) would recurse trying to unwrap it (spec guards
// against infinite sync recursion but the promise never settles in practice)

Senior Engineer Perspective

Interviewers ask this to see whether you understand promises as a protocol, not a class. A great follow-up is "can await work on a non-Promise object?" — yes, as long as it's thenable, which is exactly why libraries could adopt async/await before native promises existed everywhere. Mention that this duck-typing is also a minor security/robustness concern: a malicious or buggy .then that calls its callback twice, or throws, is guarded against by the spec (a promise can only settle once), but hand-rolled thenables in the wild don't always get that right.

Q21. Implement a simplified version of Promise.all from scratch.

ROI: ★★★★☆ Frequency: High

Short Answer

Promise.all needs to: run every input concurrently, preserve result order by input index (not completion order), resolve once every input has resolved, and reject immediately as soon as any input rejects. The implementation is a counter plus a results array pre-sized to the input length.

Code Example

function myPromiseAll(promises) {
  return new Promise((resolve, reject) => {
    const items = Array.from(promises);
    const results = new Array(items.length);
    let remaining = items.length;

    if (remaining === 0) return resolve(results); // edge case: empty input

    items.forEach((item, i) => {
      Promise.resolve(item).then((value) => {
        results[i] = value;         // index preserved regardless of order
        remaining -= 1;
        if (remaining === 0) resolve(results);
      }, reject);                    // first rejection wins, fails fast
    });
  });
}

const results = await myPromiseAll([
  fetch("/a"), fetch("/b"), Promise.resolve(42),
]);

Senior Engineer Perspective

The details interviewers check for: wrapping each item in Promise.resolve() so plain (non-promise) values are accepted, handling the empty-array edge case (should resolve immediately with [], not hang), and writing to results[i] by index rather than pushing, since promises can settle out of order. A strong candidate also notes that once one promise rejects, reject is called immediately but the other promises are NOT cancelled — they keep running in the background, exactly like the native implementation.

Q22. What are the common pitfalls in promise chaining that turn readable code into a mess?

ROI: ★★★★☆ Frequency: High

Short Answer

The big three: forgetting to return a promise from inside a .then (breaking the chain so the outer chain resolves before the inner work finishes); nesting .then callbacks instead of chaining flat ("promise pyramid of doom"); and mixing .then() with await in the same function, which makes error handling inconsistent and hard to reason about.

Detailed Answer

Every .then callback's return value becomes the next link's resolution value. If you call an async operation inside a .then but don't return it, the outer chain doesn't wait for it — it resolves with undefined on the next tick while the un-returned promise keeps running orphaned in the background, its errors unhandled. Nesting is the same underlying mistake taken further: each new async call is nested inside the previous callback instead of returned and chained, producing deeply indented code that reads inner-to-outer instead of top-to-bottom.

Code Example

// BUG 1: forgotten return — chain moves on before saveLog finishes
fetchUser(id)
  .then(user => {
    saveLog(user);              // missing `return` — orphaned promise
    return user;
  })
  .then(user => render(user)); // runs before saveLog's write completes

// FIXED
fetchUser(id)
  .then(user => saveLog(user).then(() => user))
  .then(user => render(user));

// BUG 2: pyramid of doom
fetchUser(id).then(user => {
  fetchOrders(user.id).then(orders => {
    fetchInvoices(orders[0].id).then(invoices => {
      render(user, orders, invoices); // three levels deep, hard to read
    });
  });
});

// FIXED: flatten with async/await
async function loadAll(id) {
  const user = await fetchUser(id);
  const orders = await fetchOrders(user.id);
  const invoices = await fetchInvoices(orders[0].id);
  render(user, orders, invoices);
}

Senior Engineer Perspective

Interviewers want to hear the diagnostic instinct: "if a .then callback does async work, it must return that promise or the chain silently desynchronizes." On the mixing point, a senior rule of thumb is to pick one style per function — either all .then chains or all async/await — because a try/catch around await won't catch a rejection from a sibling .then callback that forgot to propagate its error.

Q23. How do you make a non-abortable async operation cancellable using AbortController?

ROI: ★★★★☆ Frequency: Medium

Short Answer

Wrap the operation in a promise that also races against the abort signal: listen for the signal's "abort" event and reject immediately when it fires, regardless of whether the underlying API understands AbortSignal natively. This gives every async primitive — a timer, a custom event emitter, even a third-party SDK callback — a consistent cancellation contract.

Detailed Answer

True cancellation of work already in flight isn't always possible (you can't un-send a network packet), so "cancelling" usually means: stop waiting for the result and ignore it if it arrives late. The pattern below is the general-purpose adapter — it turns any promise-returning or callback-based function into one that respects an AbortSignal, which is the same contract fetch uses, so it composes cleanly with code that already expects a signal.

Code Example

function cancellableDelay(ms, signal) {
  return new Promise((resolve, reject) => {
    if (signal?.aborted) return reject(new DOMException("Aborted", "AbortError"));

    const id = setTimeout(resolve, ms);

    const onAbort = () => {
      clearTimeout(id);                       // stop the underlying work
      reject(new DOMException("Aborted", "AbortError"));
    };
    signal?.addEventListener("abort", onAbort, { once: true });
  });
}

const controller = new AbortController();
cancellableDelay(5000, controller.signal)
  .then(() => console.log("finished"))
  .catch(e => {
    if (e.name === "AbortError") console.log("cancelled early");
  });

setTimeout(() => controller.abort(), 1000); // cancel after 1s

Senior Engineer Perspective

The senior detail is throwing a real DOMException("Aborted", "AbortError") rather than a plain Error — this matches what fetch throws, so calling code can check err.name === "AbortError" uniformly whether the cancellation came from a native fetch or your own wrapper. Also mention cleaning up the listener ({ once: true } here) so aborting after the operation already resolved doesn't leak a dangling listener, and that AbortSignal.any([sig1, sig2]) lets you combine a caller's signal with an internal timeout signal.

Q24. How would you implement request deduplication so concurrent calls for the same resource share one in-flight promise?

ROI: ★★★★☆ Frequency: High

Short Answer

Keep a cache of pending promises keyed by request identity. If a call comes in for a key that's already in flight, return the existing promise instead of firing a new network request; once it settles, remove the key so the next call starts fresh. This collapses N simultaneous callers into a single network round trip.

Detailed Answer

This is distinct from result caching (which stores the resolved value) — deduplication only prevents redundant concurrent requests for the same in-flight key, which is exactly the problem when several components mount at once and all call useUser(id) for the same id, or when a fast typist triggers a search before the previous one resolves. Data-fetching libraries like React Query and SWR build this in by default.

Code Example

const inFlight = new Map();

function dedupedFetch(key, fetcher) {
  if (inFlight.has(key)) {
    return inFlight.get(key);     // join the existing request
  }
  const promise = fetcher()
    .finally(() => inFlight.delete(key)); // always clean up, success or failure
  inFlight.set(key, promise);
  return promise;
}

// Three simultaneous callers for the same id -> ONE actual network call
const [a, b, c] = await Promise.all([
  dedupedFetch("user:1", () => fetch("/api/users/1").then(r => r.json())),
  dedupedFetch("user:1", () => fetch("/api/users/1").then(r => r.json())),
  dedupedFetch("user:1", () => fetch("/api/users/1").then(r => r.json())),
]);

Senior Engineer Perspective

The critical detail is using .finally to evict the key regardless of success or failure — forgetting the failure path means one failed request permanently "poisons" the key, and every subsequent caller gets the same stale rejection forever. Distinguish this clearly from result caching (TTL-based, survives after the promise settles) in your answer; conflating the two is a common mistake that signals shallow understanding of how libraries like React Query layer both together.

Q25. Implement a retry-with-exponential-backoff-and-jitter wrapper for a flaky async operation.

ROI: ★★★★★ Frequency: High

Short Answer

Retry the operation up to N times, doubling the delay each attempt (exponential backoff) and adding a small random offset (jitter) so many clients retrying at once don't all hammer the server in lockstep. Stop retrying — and rethrow — once attempts are exhausted or the error is clearly non-retryable (e.g. a 4xx client error).

Code Example

async function retry(fn, { retries = 3, baseMs = 200, isRetryable = () => true } = {}) {
  let attempt = 0;
  while (true) {
    try {
      return await fn();
    } catch (err) {
      attempt += 1;
      if (attempt > retries || !isRetryable(err)) throw err; // give up

      const backoff = baseMs * 2 ** (attempt - 1);           // 200, 400, 800...
      const jitter = Math.random() * backoff * 0.3;          // +/- up to 30%
      await new Promise(r => setTimeout(r, backoff + jitter));
    }
  }
}

const data = await retry(
  () => fetch("/api/flaky").then(r => {
    if (!r.ok) throw new Error(`HTTP ${r.status}`);
    return r.json();
  }),
  { retries: 4, isRetryable: (e) => !e.message.includes("4") } // skip 4xx
);

Senior Engineer Perspective

Interviewers listen for "jitter" unprompted — without it, a fleet of clients that all failed at the same moment (e.g. after a brief outage) retry in perfect unison and create a "thundering herd" that re-triggers the outage. Also raise the retryable-error distinction: retrying a 400 Bad Request forever is pointless and can amplify load; only retry transient failures (timeouts, 429, 502/503/504). A senior answer also caps total elapsed time, not just attempt count, so a caller with its own deadline doesn't wait indefinitely.

Q26. What exactly does Promise.resolve(x) do for a plain value, an existing promise, and a thenable?

ROI: ★★★☆☆ Frequency: Medium

Short Answer

If x is already a native promise, Promise.resolve(x) returns that exact same promise instance — no new wrapper. If x is a thenable, it returns a new promise that assimilates it (waits for x.then to settle). If x is a plain value, it returns a new promise immediately fulfilled with that value.

Code Example

const p = Promise.resolve(1);
Promise.resolve(p) === p;              // true — no double-wrapping

const t = { then(res) { res("hi"); } };
Promise.resolve(t) !== t;              // true — a NEW real promise is created

Promise.resolve(5).then(v => console.log(v)); // 5, after one microtask tick

Senior Engineer Perspective

The identity check (Promise.resolve(p) === p) is a favourite gotcha — many candidates assume every call returns a fresh object. It matters in practice when you write a defensive helper like function toPromise(x) { return Promise.resolve(x); } to normalize inputs that might be sync values, thenables, or real promises: knowing it's a no-op for real promises tells you it's cheap to call defensively everywhere.

Q27. Implement simplified versions of Promise.race and Promise.any from scratch.

ROI: ★★★☆☆ Frequency: Medium

Short Answer

race settles with whichever input settles first, fulfilled or rejected. any settles with the first fulfillment only, and rejects with an AggregateError collecting every reason once all inputs have rejected. Both need to attach handlers to every input up front; the difference is purely in how rejections are treated.

Code Example

function myRace(promises) {
  return new Promise((resolve, reject) => {
    for (const p of promises) {
      Promise.resolve(p).then(resolve, reject); // first to call wins, others ignored
    }
  });
}

function myAny(promises) {
  return new Promise((resolve, reject) => {
    const items = Array.from(promises);
    const errors = new Array(items.length);
    let remaining = items.length;

    if (remaining === 0) {
      return reject(new AggregateError([], "All promises were rejected"));
    }

    items.forEach((item, i) => {
      Promise.resolve(item).then(resolve, (err) => {   // any fulfillment wins immediately
        errors[i] = err;
        remaining -= 1;
        if (remaining === 0) reject(new AggregateError(errors, "All promises were rejected"));
      });
    });
  });
}

Senior Engineer Perspective

The subtlety in race: once resolve or reject is called for the first settled promise, subsequent calls are silent no-ops because a promise can only settle once — you don't need to explicitly "cancel" the losing promises, the executor's resolve/reject functions just become inert. For any, the key test is whether a candidate remembers it needs to track every rejection to build the AggregateError, not just the count — a common shortcut mistake is rejecting with only the last error.

Q28. requestIdleCallback vs requestAnimationFrame vs setTimeout — how do you choose for low-priority background work?

ROI: ★★★☆☆ Frequency: Medium

Short Answer

Use requestAnimationFrame for anything that must be visually synced to the next paint. Use requestIdleCallback for genuinely low-priority work you want to run only when the browser has spare time before the next frame, without ever delaying rendering or input. Use setTimeout only when you need a specific delay and don't care about paint alignment or idle time.

Detailed Answer

requestIdleCallback callbacks receive a deadline object with timeRemaining(), so well-behaved idle work checks the remaining budget and yields back (re-scheduling itself for the next idle period) instead of hogging the slice. It's ideal for analytics batching, prefetching off-screen data, or background cache warming — work the user must never notice waiting on. Its major caveat: it isn't in Safari, and it can be starved indefinitely on a busy page, so time-sensitive work should never depend on it (there's an optional timeout option to force execution eventually).

Code Example

function processInIdleTime(items, processItem) {
  let i = 0;
  function step(deadline) {
    while (i < items.length && deadline.timeRemaining() > 0) {
      processItem(items[i]);
      i += 1;
    }
    if (i < items.length) {
      requestIdleCallback(step);           // more to do, wait for next idle slice
    }
  }
  requestIdleCallback(step, { timeout: 2000 }); // force-run within 2s even if busy
}

Senior Engineer Perspective

Mention that React's Fiber scheduler was directly inspired by requestIdleCallback's time-slicing idea (React ships its own polyfill/scheduler rather than relying on the browser API directly, for cross-browser consistency and finer control). A sharp follow-up: "why not just use it for all of React's scheduling?" — because idle callbacks can be starved arbitrarily on a busy page, and React needs more predictable prioritization than the browser API guarantees.

Q29. How does Node.js's event loop differ from the browser's, and what are its phases?

ROI: ★★★★☆ Frequency: High

Short Answer

Node's event loop (via libuv) runs in distinct ordered phases each iteration — timers, pending callbacks, poll (I/O), check (setImmediate), and close callbacks — whereas the browser model is simpler (one task queue plus one microtask queue). Both share the same core rule that microtasks (promises, plus Node's own process.nextTick queue) drain completely between phases/tasks.

Detailed Answer

PhaseHandles
TimerssetTimeout / setInterval callbacks whose delay has elapsed
Pending callbacksDeferred I/O callbacks (some system-level errors)
PollFetching new I/O events; executes I/O callbacks (file, network)
ChecksetImmediate callbacks — always after poll, before timers of the next loop
Close callbackssocket.on("close", ...) and similar cleanup

Critically, after every callback in every phase, Node drains process.nextTick callbacks first, then the promise microtask queue, before moving to the next callback or phase — this is stricter than the browser, where microtasks drain once per task, not once per phase-internal callback.

Code Example

setTimeout(() => console.log("timeout"), 0);
setImmediate(() => console.log("immediate"));
// Order is NOT guaranteed at the top level (depends on process startup timing),
// but INSIDE an I/O callback, setImmediate always fires before setTimeout(0):
const fs = require("fs");
fs.readFile(__filename, () => {
  setTimeout(() => console.log("timeout in I/O"), 0);
  setImmediate(() => console.log("immediate in I/O")); // always first here
});

Senior Engineer Perspective

The classic trap is claiming setTimeout(fn, 0) and setImmediate(fn) have a fixed ordering — they don't at the top level, but the ordering becomes deterministic (setImmediate first) once you're inside an I/O callback, because the poll phase always transitions to check before circling back to timers. Also flag process.nextTick as higher priority than promise microtasks in Node — it's a separate, even-higher-priority queue drained first, which is a Node-specific detail that trips up browser-only engineers.

Q30. What is process.nextTick and how does its priority compare to promise microtasks?

ROI: ★★★☆☆ Frequency: Medium (Node-heavy roles)

Short Answer

process.nextTick(fn) queues fn on a Node-specific queue that runs before the promise microtask queue, and it is fully drained (including any nextTicks queued during draining) before promises get a turn. It's not part of the standard microtask spec at all — it's Node's own even-higher-priority mechanism, historically used to defer work "until right after the current operation" without a full event-loop tick.

Code Example

Promise.resolve().then(() => console.log("promise microtask"));
process.nextTick(() => console.log("nextTick"));
// Output (Node):
// nextTick
// promise microtask

Senior Engineer Perspective

Warn about the overuse danger explicitly documented by Node itself: recursively calling process.nextTick can starve the event loop entirely — I/O and even promise callbacks never get a turn — which is a real production incident category ("my server stopped responding to requests"). This is the Node equivalent of the browser's "recursive microtask starves rendering" problem from Q19/Q21, just with an even sharper edge because nextTick jumps the whole queue.

Q31. Trace this harder ordering puzzle mixing nested setTimeouts, async functions, and .then chains.

ROI: ★★★★★ Frequency: High

Short Answer

Build the queues on paper in strict passes: run all synchronous code; drain the microtask queue completely, including any new microtasks scheduled while draining; run exactly one macrotask; drain microtasks again; repeat. The only way to reliably get these right under interview pressure is mechanical bookkeeping, not intuition.

Code Example

console.log("1");

setTimeout(() => {
  console.log("2");
  Promise.resolve().then(() => console.log("3"));
}, 0);

async function run() {
  console.log("4");
  await Promise.resolve();
  console.log("5");
  setTimeout(() => console.log("6"), 0);
  await Promise.resolve();
  console.log("7");
}
run();

Promise.resolve().then(() => console.log("8"));

console.log("9");

// Reasoning:
//   Sync pass:            1, 4 (inside run(), before its first await), 9
//   Microtask drain 1:    5 (run()'s first await continuation) -- queued
//                         before 8 because run() was called before the
//                         standalone .then() line executed
//                         then 8
//   run() continues sync after "5" until its NEXT await, scheduling
//   setTimeout("6") as a NEW macrotask, then suspending again
//   Macrotask 1: "2" (first setTimeout), which schedules "3" as a microtask
//   Microtask drain 2: 3
//   Macrotask 2: "6" (second setTimeout, scheduled later, runs after macrotask 1)
//   Microtask drain 3: 7 (run()'s second await continuation, was pending
//                         since before macrotask 1)
//
// FINAL OUTPUT: 1, 4, 9, 5, 8, 2, 3, 6, 7

Senior Engineer Perspective

Note the subtlety at the end: "7" resumes from an await that was scheduled before either macrotask ran, but it doesn't print until after both macrotasks — because a suspended async function's continuation is only enqueued once its awaited promise settles, and Promise.resolve() settles on the next microtask checkpoint, which only arrives after the currently-running macrotask finishes. Interviewers use puzzles like this specifically to see if you narrate a consistent rule rather than pattern-matching to a memorized answer.

Q32. What is a "microtask checkpoint" and when exactly does the browser perform one?

ROI: ★★★☆☆ Frequency: Medium

Short Answer

A microtask checkpoint is the spec-defined moment where the engine drains the microtask queue to empty before continuing. It happens whenever the JS call stack becomes empty — after the currently running script/task/callback returns — not just "once per event loop iteration" as a casual description implies; there can be many checkpoints within processing a single task if the host performs them between sub-steps.

Detailed Answer

In browsers, a checkpoint also happens between separate callback invocations within the same task in some cases (e.g. between each entry of a batch of DOM event dispatches), which is why you can observe promise callbacks interleaving with things you might expect to be "one atomic task." The practical takeaway for React/DOM code: you cannot assume no microtasks run between two statements just because they're "in the same tick" — only between two statements in the same synchronous function frame with no await/promise scheduling between them is that guaranteed.

Code Example

button.addEventListener("click", () => {
  console.log("handler A start");
  Promise.resolve().then(() => console.log("microtask from A"));
  console.log("handler A end");
});
button.addEventListener("click", () => {
  console.log("handler B");
});
// A single click dispatches both listeners as one task, but the microtask
// queued inside A resolves before B runs in most modern engines, because a
// checkpoint occurs between the two listener invocations:
// "handler A start", "handler A end", "microtask from A", "handler B"

Senior Engineer Perspective

Most engineers only learn "one task, then drain microtasks" as a single macro rule and are surprised when microtasks interleave mid-task. If asked to defend the exact browser behavior, be honest that fine-grained checkpoint timing is implementation-defined in places — the reliable, spec-guaranteed contract to lean on in real code is simply: "a microtask you schedule will run before the next macrotask, and before the next paint," not a stronger promise about exactly which line it interleaves with.

Q33. What is main-thread "task starvation" or a "long task," and how do you detect and fix it?

ROI: ★★★★☆ Frequency: High

Short Answer

A long task is any piece of synchronous work that keeps the call stack busy for a noticeable stretch (commonly flagged past 50ms), during which the browser can't process input, run timers, or paint. You detect it with the PerformanceObserver "longtask" entry type or the DevTools Performance panel's red-flagged blocks; you fix it by breaking the work into chunks that yield back to the event loop, or by moving it off the main thread entirely.

Detailed Answer

"Yielding" means voluntarily returning control to the event loop mid-computation so pending input/paint/microtasks get a chance to run, then resuming. Options, roughly cheapest-to-most-robust: chunk the loop across several setTimeout(fn, 0) calls, use the newer scheduler.yield() / isInputPending() APIs where available, or hand the whole computation to a Web Worker so it runs on a separate thread and never touches the main call stack.

Code Example

// Detect long tasks
new PerformanceObserver((list) => {
  for (const entry of list.getEntries()) {
    console.warn("Long task:", entry.duration, "ms");
  }
}).observe({ type: "longtask", buffered: true });

// Fix: chunk a big synchronous loop so the UI stays responsive
function processChunked(items, processItem, chunkSize = 200) {
  let i = 0;
  function chunk() {
    const end = Math.min(i + chunkSize, items.length);
    for (; i < end; i++) processItem(items[i]);
    if (i < items.length) setTimeout(chunk, 0); // yield, then resume
  }
  chunk();
}

Project Example

A "sort and re-render 50,000 rows" click handler that freezes a data grid for 400ms is a textbook long task. Splitting the sort into a Web Worker (which returns just the sorted id order) and re-rendering with React's startTransition keeps typing in a nearby filter box responsive throughout, because neither the worker thread nor a transition-marked update blocks the main thread's input handling.

Senior Engineer Perspective

Be ready to connect this to Core Web Vitals — long tasks are the direct cause of poor INP (Interaction to Next Paint), the metric that replaced FID. A senior answer distinguishes "make the work faster" (algorithmic fix) from "make the work not block" (yielding/threading fix) — both are valid, but interviewers want you to reach for measurement (the PerformanceObserver, not guesswork) before reaching for a fix.

Q34. Where does MutationObserver fit in the task/microtask model?

ROI: ★★☆☆☆ Frequency: Low

Short Answer

MutationObserver callbacks are queued as microtasks, batched per "microtask checkpoint" — so a burst of synchronous DOM mutations fires the observer callback once with an array of all the accumulated mutation records, right after the current synchronous code finishes, before the next macrotask or paint.

Code Example

const observer = new MutationObserver((mutations) => {
  console.log("batched mutations:", mutations.length);
});
observer.observe(document.body, { childList: true, subtree: true });

// Three synchronous DOM changes...
document.body.appendChild(document.createElement("div"));
document.body.appendChild(document.createElement("span"));
document.body.appendChild(document.createElement("p"));
console.log("sync code done");

// Output:
// sync code done
// batched mutations: 3       (one microtask callback, not three)

Senior Engineer Perspective

This batching-as-a-microtask behavior is precisely why React's legacy DOM mutation observation and various "detect external DOM changes" utilities never see a flicker of intermediate state — by the time your callback runs, all synchronous mutations from that turn have already landed. It's a good example that "microtask" isn't just "promise callback" — it's a general scheduling priority several browser APIs opt into.

Q35. How does the event loop model relate to React's concurrent rendering and time slicing?

ROI: ★★★★☆ Frequency: High

Short Answer

React's concurrent renderer builds its own cooperative scheduler on top of the same single-threaded event loop — it can't get a second thread, so instead it breaks rendering work into small units and periodically yields back to the browser (similar in spirit to requestIdleCallback), letting input events, layout, and paint interleave with an in-progress render.

Detailed Answer

Before React 18, rendering a tree was one long synchronous call stack — a big update was itself a "long task." Concurrent features (startTransition, useDeferredValue, Suspense-driven rendering) let React mark some updates as low priority and process the fiber tree in chunks, checking a time budget and yielding via the scheduler package (which internally uses MessageChannel postMessage tricks, not setTimeout, because MessageChannel messages are treated as macrotasks but with less browser throttling/clamping). This means a low-priority re-render can be interrupted mid-way by a high-priority update (like a keystroke), discarded, and restarted — something impossible with truly synchronous rendering.

Code Example

function SearchPage() {
  const [query, setQuery] = useState("");
  const [results, setResults] = useState([]);

  function handleChange(e) {
    setQuery(e.target.value);           // urgent: keep the input responsive
    startTransition(() => {
      setResults(computeResults(e.target.value)); // low priority, interruptible
    });
  }
  // Typing stays instantaneous even while `computeResults` re-renders a big list,
  // because React can yield back to the event loop mid-render and pick the
  // urgent `query` update up first.
}

Senior Engineer Perspective

The connection interviewers want: concurrency in React is cooperative scheduling on one thread, not real parallelism — it's built from the exact same primitives (yielding via the task queue) covered in this section, not some special browser feature. A great follow-up: "does startTransition make the computation faster?" No — it makes the page feel faster by letting more urgent work cut in line; the total CPU work is the same or slightly more (due to possible restarts).

SECTION 8 - ASYNC ITERATORS & GENERATORS IN PRACTICE

Q36. What is the async iterator protocol, and how does for await...of consume it?

ROI: ★★★★☆ Frequency: High

Short Answer

An async iterator is an object whose next() method returns a promise of { value, done } instead of the value directly — the async counterpart of the sync iterator protocol. for await...of is the loop construct that automatically awaits each next() call, letting you iterate over data that arrives over time (streamed chunks, paginated pages, WebSocket messages) with ordinary loop syntax.

Code Example

const asyncIterable = {
  [Symbol.asyncIterator]() {
    let i = 0;
    return {
      next() {
        i += 1;
        if (i > 3) return Promise.resolve({ value: undefined, done: true });
        return new Promise((resolve) =>
          setTimeout(() => resolve({ value: i, done: false }), 100)
        );
      },
    };
  },
};

for await (const n of asyncIterable) {
  console.log(n); // 1, 2, 3 — each ~100ms apart, loop awaits automatically
}

Senior Engineer Perspective

Point out that for await...of also works directly on an array of promises (it awaits each element), and that many web platform streams already implement Symbol.asyncIterator — a ReadableStream, an fetch response body reader, and Node.js streams can all be consumed with plain for await. Knowing this saves you from hand-rolling manual .read() loops.

Q37. Write an async generator function and explain how it differs from a regular generator.

ROI: ★★★★☆ Frequency: High

Short Answer

async function* combines both worlds: like a regular generator it can yield multiple times and be paused/resumed, and like an async function it can await inside its body. Calling it returns an async iterable (implements Symbol.asyncIterator) whose next() always returns a promise, so you consume it with for await...of rather than plain for...of.

Code Example

async function* fetchPages(baseUrl) {
  let page = 1;
  while (true) {
    const res = await fetch(`${baseUrl}?page=${page}`);
    const data = await res.json();
    if (data.items.length === 0) return;   // stop condition
    yield data.items;                       // hand a page back to the consumer
    page += 1;
  }
}

for await (const items of fetchPages("/api/products")) {
  console.log("got page with", items.length, "items");
}

Senior Engineer Perspective

The distinguishing insight: a regular generator's yield pauses synchronously and is pulled with plain .next(); an async generator's yield can be preceded by an await, and pulling it (.next()) always returns a promise even if no internal await happened. This makes async generators the natural abstraction for "lazily produce values that each require I/O," which is exactly what cursor-based pagination is.

Q38. Build an async data pipeline that streams, transforms, and filters paginated API results lazily.

ROI: ★★★★☆ Frequency: Medium

Short Answer

Chain async generators together the same way you'd chain array methods: a source generator yields raw pages, a transform generator consumes it item-by-item and yields mapped/filtered results, and the caller pulls from the final generator with for await...of — nothing downstream is computed until it's actually requested, so you never hold the whole dataset in memory.

Code Example

async function* flatten(pagesGenerator) {
  for await (const page of pagesGenerator) {
    yield* page;                     // yield each item individually
  }
}

async function* filterAsync(source, predicate) {
  for await (const item of source) {
    if (predicate(item)) yield item;
  }
}

async function* mapAsync(source, fn) {
  for await (const item of source) {
    yield fn(item);
  }
}

// Compose the pipeline — nothing runs until consumed below
const pipeline = mapAsync(
  filterAsync(flatten(fetchPages("/api/products")), (p) => p.inStock),
  (p) => ({ id: p.id, name: p.name })
);

for await (const product of pipeline) {
  console.log(product);              // processed one item at a time, lazily
  if (product.id === "stop-here") break; // remaining pages are never fetched
}

Senior Engineer Perspective

The payoff to articulate: laziness means break-ing out of the consumer loop early genuinely stops further network requests, because the upstream generators are only pulled on demand — unlike Promise.all(pages.map(fetchAndProcess)), which would have already kicked off every request regardless. This pattern scales to arbitrarily large or infinite paginated APIs with constant memory.

Q39. Implement a simple async queue (channel) using generators/promises for producer-consumer coordination.

ROI: ★★★☆☆ Frequency: Medium

Short Answer

An async queue lets a "producer" push values whenever they're ready and a "consumer" pull them whenever it's ready, in either order, by keeping two internal buffers: pending values (if the producer got ahead) and pending waiters (if the consumer got ahead) — whichever side arrives first gets matched immediately, otherwise it waits.

Code Example

function createAsyncQueue() {
  const values = [];
  const waiters = [];

  return {
    push(value) {
      if (waiters.length) {
        waiters.shift()(value);         // a consumer was already waiting
      } else {
        values.push(value);             // buffer it for a future consumer
      }
    },
    async next() {
      if (values.length) return values.shift();
      return new Promise((resolve) => waiters.push(resolve));
    },
    async *[Symbol.asyncIterator]() {
      while (true) yield await this.next();
    },
  };
}

const queue = createAsyncQueue();
socket.onmessage = (e) => queue.push(JSON.parse(e.data)); // producer

(async () => {
  for await (const msg of queue) {      // consumer
    console.log("received", msg);
  }
})();

Senior Engineer Perspective

This is the pattern that underlies async message channels in libraries like RxJS subjects or Node's stream backpressure primitives, distilled to its essence. A strong follow-up is "how would you add backpressure (a max buffer size)?" — you'd make push itself return a promise that only resolves once the buffer drops below a threshold, forcing a fast producer to slow down to match a slow consumer.

Q40. Symbol.iterator vs Symbol.asyncIterator — when does using the wrong loop throw, and how?

ROI: ★★★☆☆ Frequency: Medium

Short Answer

An object implementing only Symbol.iterator works with plain for...of but not for await...of alone — actually for await...of falls back gracefully to a sync iterable and awaits each yielded value. The real throw happens the other way around: passing an object that implements only Symbol.asyncIterator (no Symbol.iterator) to a plain for...of throws a TypeError ("is not iterable"), because for...of never looks for the async protocol.

Code Example

const asyncOnly = {
  [Symbol.asyncIterator]() {
    let i = 0;
    return { next: () => Promise.resolve({ value: ++i, done: i > 2 }) };
  },
};

for await (const n of asyncOnly) console.log(n); // OK: 1, 2

try {
  for (const n of asyncOnly) console.log(n);     // TypeError
} catch (e) {
  console.log(e.message); // "asyncOnly is not iterable"
}

Senior Engineer Perspective

Also mention that for await...of works fine on a plain array of promises (or plain values) even though arrays only implement Symbol.iterator — it awaits whatever each iteration step yields, sync or async. The precise rule: for await checks for Symbol.asyncIterator first and falls back to Symbol.iterator; plain for...of only ever checks Symbol.iterator.

Q41. How do you break out of a for await...of loop early, and does the generator get cleaned up?

ROI: ★★★☆☆ Frequency: Medium

Short Answer

A plain break, return, or an uncaught throw inside the loop body causes the loop to automatically call the generator's .return() method, which runs any pending finally blocks inside the generator — this is how you release resources (close a file handle, unsubscribe a socket) even when the consumer stops early.

Code Example

async function* readLines(connection) {
  try {
    while (true) {
      const line = await connection.read();
      if (line === null) return;
      yield line;
    }
  } finally {
    console.log("cleaning up connection"); // runs on early break too
    connection.close();
  }
}

for await (const line of readLines(conn)) {
  console.log(line);
  if (line === "STOP") break;   // triggers generator.return() -> finally runs
}

Senior Engineer Perspective

This is a favourite "gotcha" question because many engineers assume breaking a loop just stops iteration with no side effects. The correct mental model: the loop machinery is contractually obligated to call .return() on early exit, so any cleanup you need belongs in a finally block inside the generator, not scattered around every call site that might break early.

Q42. How can generators model cooperative cancellation / coroutine-like control flow (the Redux-Saga approach)?

ROI: ★★★☆☆ Frequency: Low-Medium

Short Answer

Instead of a generator yielding raw values, it can yield plain descriptive objects ("effects") that describe an intended side effect (call this function, wait for this action, race these operations) without performing it — a separate driver/runtime pulls each yielded effect, performs it, and feeds the result back in via .next(result). Because the saga is just data plus pauses, the runtime can inspect, cancel, or fork it without the saga code needing any awareness of cancellation itself.

Code Example

// Effect creators — plain data, no execution yet
const call = (fn, ...args) => ({ type: "CALL", fn, args });
const take = (actionType) => ({ type: "TAKE", actionType });

function* checkoutSaga() {
  yield take("CHECKOUT_STARTED");
  const order = yield call(submitOrder, currentCart());
  yield call(showConfirmation, order);
}

// A tiny driver that interprets the effects
async function runSaga(saga) {
  const it = saga();
  let input;
  while (true) {
    const { value: effect, done } = it.next(input);
    if (done) return;
    if (effect.type === "CALL") input = await effect.fn(...effect.args);
    if (effect.type === "TAKE") input = await waitForAction(effect.actionType);
  }
}

Senior Engineer Perspective

The insight interviewers want: separating "describe what should happen" (the yielded effect object) from "actually perform it" (the driver) makes saga code trivially unit-testable with no mocking — you assert on the plain objects a generator yields, step by step, instead of mocking network calls. This is the exact mechanism that made Redux-Saga's testability a selling point over plain thunks, and it's a real-world, production-grade use of generators beyond textbook lazy sequences.

SECTION 9 - ADVANCED CLOSURES & MEMORY

Q43. Explain the classic "closures in a loop" bug in depth, and every way to fix it.

ROI: ★★★★★ Frequency: Extremely High

Short Answer

With var, a for loop creates one shared binding for the whole loop, so every closure created inside captures the same variable and sees its final value after the loop ends. let fixes this because the spec creates a fresh binding per iteration, so each closure captures its own independent copy of the loop variable.

Detailed Answer

Before let existed, the fix was to force a new scope per iteration manually — either an IIFE that takes the current value as a parameter, or .forEach/.map, whose callback parameter is a fresh binding on every call. All of these achieve the same thing let now does natively: giving each iteration's closures something private to close over instead of one shared mutable cell.

Code Example

// BUG: var is function-scoped -- one shared `i` for all three callbacks
for (var i = 0; i < 3; i++) {
  setTimeout(() => console.log("var:", i), 10);
}
// Output: var: 3, var: 3, var: 3   (loop finished before any timeout fires)

// FIX 1: let -- a fresh binding is created for each iteration
for (let j = 0; j < 3; j++) {
  setTimeout(() => console.log("let:", j), 10);
}
// Output: let: 0, let: 1, let: 2

// FIX 2 (pre-ES6): IIFE captures the current value as its own parameter
for (var k = 0; k < 3; k++) {
  (function (captured) {
    setTimeout(() => console.log("iife:", captured), 10);
  })(k);
}
// Output: iife: 0, iife: 1, iife: 2

// FIX 3: forEach's callback parameter is a fresh binding per call
[0, 1, 2].forEach((n) => setTimeout(() => console.log("forEach:", n), 10));

Senior Engineer Perspective

Interviewers want the precise spec-level explanation — "a new lexical environment per iteration" — not just "let is block-scoped, var isn't," because the loop-closure bug is really about per-iteration bindings, a slightly different and more specific mechanism than ordinary block scoping. Being able to demonstrate the IIFE fix from memory signals you understand why let works, not just that it does.

Q44. What is an IIFE, and what problems did it solve before ES modules existed?

ROI: ★★★☆☆ Frequency: Medium

Short Answer

An Immediately Invoked Function Expression — (function () { ... })() — creates a private function scope and runs it once, right away. Before let/const and ES modules, it was the standard way to avoid polluting the global scope: every library variable lived inside the IIFE's closure instead of on window, and only whatever was deliberately returned/attached became public.

Code Example

var MyLibrary = (function () {
  let privateCounter = 0;              // invisible outside this IIFE

  function increment() { return ++privateCounter; }
  function reset() { privateCounter = 0; }

  return { increment, reset };          // only these are exposed
})();

MyLibrary.increment();  // 1
MyLibrary.privateCounter; // undefined -- truly private

Senior Engineer Perspective

Know when NOT to reach for this today: ES modules already give every file its own private top-level scope, so IIFEs for scope-hiding are largely legacy pattern now, mostly seen in older bundled libraries, UMD wrappers, and the loop-closure fix from Q43. Still expect to recognize and explain it when reading older code, and to know the related "module pattern" it enabled — Q49 in this chapter builds on exactly this idea.

Q45. How exactly do closures cause memory leaks, beyond the general "reachability" explanation?

ROI: ★★★★☆ Frequency: High

Short Answer

A closure keeps its entire enclosing lexical environment reachable for as long as the closure itself is reachable — not just the specific variables it references. If that closure is handed to something long-lived (a global event listener, an interval, a module-level cache), every variable in its enclosing scope, including large ones the closure never actually touches, is pinned in memory for the life of that listener.

Detailed Answer

Modern V8 does apply some pruning — if a variable is provably never referenced by any closure created in that scope, it can be excluded from the retained environment. But once any variable in a scope is captured, other variables declared in sibling closures over the same scope can still end up retained together in practice, depending on engine internals you shouldn't rely on. The safe engineering rule is: assume everything in scope when a long-lived closure is created can be retained, and structure code so long-lived callbacks close over the smallest possible scope.

Code Example

function setupWidget(hugeDataset) {
  const summary = summarize(hugeDataset);       // small, cheap to keep
  // BUG: this listener's closure scope includes `hugeDataset` even though
  // the callback only reads `summary` -- some engines retain the whole
  // enclosing scope, keeping the huge dataset alive for the listener's life
  window.addEventListener("resize", () => render(summary));
}

// SAFER: narrow what the closure can see by extracting to its own scope
function setupWidgetSafe(hugeDataset) {
  const summary = summarize(hugeDataset);
  attachResizeHandler(summary);                 // hugeDataset is out of scope here
}
function attachResizeHandler(summary) {
  window.addEventListener("resize", () => render(summary));
}

Project Example

A dashboard component that processes a large API response, then registers a resize/scroll listener referencing only a small derived value, can still leak the original large payload for the component's entire lifetime if the listener's closure was created in the same function scope as the raw data and never cleaned up on unmount. Splitting the derivation into its own function (as above) and always removing the listener in the useEffect cleanup addresses both causes at once.

Senior Engineer Perspective

The senior nuance here is knowing the engine's behavior is an implementation detail you shouldn't lean on — the actionable, portable advice is "keep long-lived closures' enclosing scope small" and "always clean up listeners/timers," not "trust V8 to optimize it away." Bring up the DevTools workflow from Q18/Q48: heap snapshots comparing before/after repeated mount-unmount cycles are how you'd actually verify this in a real app rather than reason about it in the abstract.

Q46. Implement private object state using WeakMap instead of closures. What's the trade-off?

ROI: ★★★★☆ Frequency: Medium

Short Answer

Instead of closing over a private variable per instance, keep a single module-level WeakMap keyed by the instance object, storing its private data as the value. Because WeakMap keys are held weakly, the private data is automatically garbage-collected the moment the instance itself becomes unreachable — no manual cleanup, and no risk of the closure-retention issue from Q45.

Code Example

const privateData = new WeakMap();

class BankAccount {
  constructor(initialBalance) {
    privateData.set(this, { balance: initialBalance }); // keyed by instance
  }
  deposit(amount) {
    const data = privateData.get(this);
    data.balance += amount;
    return data.balance;
  }
  get balance() {
    return privateData.get(this).balance;
  }
}

const acc = new BankAccount(100);
acc.deposit(50);
acc.balance;              // 150
acc.dataUnknown;          // undefined -- balance isn't a visible property at all

Senior Engineer Perspective

The trade-off to name explicitly: this pattern predates native #private class fields and is more verbose, but it's still relevant for two cases — attaching private metadata to objects you don't control the class definition of (e.g. tagging third-party objects), and situations where you need the encapsulation to survive across multiple cooperating classes/modules that all share the same WeakMap. For a single class's own fields, native #private (Q47) is simpler and should be preferred today.

Q47. Compare native #private class fields to WeakMap-based privacy. When would you still reach for WeakMap?

ROI: ★★★☆☆ Frequency: Medium

Short Answer

#field syntax is true language-level privacy — enforced by the engine, not by convention — and is simpler to read and write than a WeakMap for straightforward per-instance state. WeakMap-based privacy is still useful when the "private" data needs to be shared or manipulated across several classes/functions that aren't all methods of the same class, since #fields are only accessible from inside the exact class body that declares them.

Code Example

class Counter {
  #count = 0;                 // truly private -- inaccessible outside the class
  increment() { return ++this.#count; }
}
const c = new Counter();
c.increment();               // 1
c.#count;                    // SyntaxError outside the class body

// WeakMap gives external code (e.g. a decorator/mixin function) access
// that a native #field never allows, because the field is scoped to
// the class body lexically, not to the instance's data:
const auditLog = new WeakMap();
function withAuditing(instance) {
  auditLog.set(instance, []);
}

Senior Engineer Perspective

A crisp answer names the concrete deciding factor: is the private data accessed only by methods physically written inside one class body (use #field), or does it need to be read/written by external functions cooperating with the instance, like mixins, decorators, or test-only inspection utilities (use WeakMap)? Also mention #field in obj "ergonomic brand checks" (ES2022) for safely testing whether an arbitrary object is an instance of your class without throwing.

Q49. Explain the Revealing Module Pattern built from closures, and why ES modules mostly replaced it.

ROI: ★★☆☆☆ Frequency: Low-Medium

Short Answer

The Revealing Module Pattern uses an IIFE to build a private scope, defines everything (state and functions) privately inside, and returns an object literal that "reveals" only the specific references you want public, pointing at the already-defined private functions rather than redefining them inline. ES modules (native import/export) provide the same private-by-default, explicit-export behavior at the language level, so this pattern is rarely hand-rolled today.

Code Example

const counterModule = (function () {
  let count = 0;                          // private state

  function increment() { count += 1; }    // private function
  function decrement() { count -= 1; }
  function getCount() { return count; }

  return {                                // revealed public API
    increment,
    getCount,
    // decrement intentionally NOT revealed -- stays private
  };
})();

counterModule.increment();
counterModule.getCount();   // 1
counterModule.decrement;    // undefined -- never exposed

// Modern equivalent -- an ES module does this natively:
// counter.js
let count = 0;
export function increment() { count += 1; }
export function getCount() { return count; }
// decrement stays module-private simply by NOT being exported

Senior Engineer Perspective

The point to make explicitly: this pattern was solving a problem — controlled, explicit public surface area with everything else private — that the language didn't natively support before ES modules. Recognizing it in legacy code (jQuery plugins, older utility libraries) and explaining what it maps to in modern syntax is the useful skill; writing new code with hand-rolled IIFE modules today is generally an anti-pattern once a real module system is available.

SECTION 10 - FUNCTIONAL PROGRAMMING PATTERNS

Q50. What is function composition? Implement compose and pipe utilities.

ROI: ★★★★☆ Frequency: High

Short Answer

Composition combines several single-purpose functions into one by feeding each function's output into the next. pipe runs functions left-to-right (the intuitive reading order for a data pipeline); compose runs them right-to-left (the traditional mathematical f(g(x)) convention). Both are implemented with reduce over the function list.

Code Example

const pipe = (...fns) => (x) => fns.reduce((acc, fn) => fn(acc), x);
const compose = (...fns) => (x) => fns.reduceRight((acc, fn) => fn(acc), x);

const trim = (s) => s.trim();
const toLower = (s) => s.toLowerCase();
const removeSpaces = (s) => s.replace(/\s+/g, "-");

const slugify = pipe(trim, toLower, removeSpaces);
slugify("  Hello World  ");   // "hello-world"

// compose reads right-to-left -- same three steps, opposite declaration order
const slugifyC = compose(removeSpaces, toLower, trim);
slugifyC("  Hello World  ");  // "hello-world"

Senior Engineer Perspective

Be ready to point out the practical trade-off: pipe reads in execution order top-to-bottom, which most teams find easier to follow in application code, while compose mirrors mathematical function notation and is more common in functional-programming libraries (Redux's own compose for middleware is the classic example every React engineer has encountered). Neither handles multi-argument functions or async functions out of the box — see Q57 for the async variant.

Q51. What is point-free style, and what are its readability/debugging trade-offs?

ROI: ★★★☆☆ Frequency: Medium

Short Answer

Point-free (a.k.a. "tacit") style defines a function without ever naming its arguments explicitly — it's built purely by composing other functions, so the data flows through implicitly. It can produce very terse, declarative-looking code, but at the cost of losing meaningful intermediate variable names, which makes both reading and debugging harder when something goes wrong.

Code Example

// Pointed (explicit argument, easy to add a breakpoint/console.log to)
const getActiveUserNames = (users) =>
  users.filter((u) => u.active).map((u) => u.name);

// Point-free (no named argument for `users` at all)
const getActiveUserNamesPF = pipe(
  (users) => users.filter((u) => u.active),
  (users) => users.map((u) => u.name)
);
// Fully point-free requires curried, unary utility functions:
const filterActive = (users) => users.filter((u) => u.active);
const mapToNames = (users) => users.map((u) => u.name);
const getActiveUserNamesPF2 = pipe(filterActive, mapToNames);

Senior Engineer Perspective

A senior answer avoids being dogmatic in either direction: point-free composition is genuinely elegant for short, well-named pipelines, but chaining several anonymous point-free functions can make stepping through a debugger painful, because there's no local variable holding the intermediate value to inspect at a breakpoint. The practical guideline: keep point-free chains short and give each composed step a well-named function (as above), rather than inlining anonymous lambdas into a long pipe(...) call.

Q52. Implement a curry function that supports placeholder arguments for skipping positions.

ROI: ★★★☆☆ Frequency: Medium

Short Answer

Beyond the basic curry from Q13, a placeholder-aware curry lets you fill later arguments before earlier ones — you pass a sentinel value (often _) to mean "skip this slot for now, I'll supply it in a later call," which is essential for currying functions where you want to fix a middle or last argument first.

Code Example

const _ = Symbol("placeholder");

function curryWithPlaceholder(fn) {
  return function curried(...args) {
    const hasPlaceholder = args.includes(_);
    const complete = args.length >= fn.length && !hasPlaceholder;
    if (complete) return fn(...args);

    return (...next) => {
      const merged = args.map((a) => (a === _ ? next.shift() : a)).concat(next);
      return curried(...merged);
    };
  };
}

const between = curryWithPlaceholder((min, val, max) => val >= min && val <= max);
const isPercentage = between(0, _, 100);  // fix min and max, skip the middle
isPercentage(50);   // true
isPercentage(150);  // false

Senior Engineer Perspective

This is a meaningfully harder exercise than plain curry because you must handle merging placeholders across multiple partial-application calls, not just a single one. If the interviewer pushes further, mention that libraries like Ramda ship this exact feature (R.__) precisely because real-world argument orders don't always let you fill left-to-right.

Q53. Explain, in practical JS terms, what a "Maybe"/"Option" pattern buys you over null checks.

ROI: ★★★☆☆ Frequency: Low-Medium

Short Answer

A Maybe/Option wraps a value that might be absent in a small container with a consistent .map-style API, so you chain transformations without ever writing an explicit if (x != null) guard at every step — the container itself "does nothing" safely when the underlying value is absent, similar in spirit to how optional chaining (?.) short-circuits, but composable across your own custom transformation functions, not just property access.

Code Example

function Maybe(value) {
  return {
    map: (fn) => (value == null ? Maybe(null) : Maybe(fn(value))),
    getOrElse: (fallback) => (value == null ? fallback : value),
  };
}

const city = Maybe(user)
  .map((u) => u.address)
  .map((a) => a.city)
  .map((c) => c.toUpperCase())
  .getOrElse("UNKNOWN");
// Every .map is skipped safely the moment any link in the chain is null --
// no step needs its own null check.

Senior Engineer Perspective

Keep the answer honest and pragmatic: in plain JS, optional chaining plus nullish coalescing (Q15 in the fundamentals chapter) already covers the property-access case far more idiomatically, so hand-rolling a Maybe type is rarely justified for simple lookups. Where it genuinely earns its keep is chaining custom fallible transformations (parsing, validation, business rules) where you want uniform "stop on empty" behavior across steps that aren't just property access — which is exactly the gap libraries like fp-ts or Rust's/Haskell's Option/Maybe types fill more rigorously.

Q54. What is a transducer, and how does it let you process a large array with a single pass instead of several?

ROI: ★★★☆☆ Frequency: Low-Medium

Short Answer

Chaining array.filter(...).map(...).filter(...) creates a full intermediate array at every step. A transducer composes the "step" logic of each operation into a single reducer function that runs in one pass over the source, with no intermediate arrays allocated at all — the composition happens on the operations, not on the data.

Code Example

// Naive: three full intermediate arrays over a large dataset
const result = bigArray
  .filter((n) => n % 2 === 0)
  .map((n) => n * 10)
  .filter((n) => n < 500);

// Transducer-style: one pass, no intermediate arrays
const mapping = (fn) => (reducer) => (acc, val) => reducer(acc, fn(val));
const filtering = (pred) => (reducer) => (acc, val) =>
  pred(val) ? reducer(acc, val) : acc;

const xf = compose(
  filtering((n) => n % 2 === 0),
  mapping((n) => n * 10),
  filtering((n) => n < 500)
);

const push = (acc, val) => (acc.push(val), acc);
const combined = xf(push);                      // the fused single-pass reducer
const transduced = bigArray.reduce(combined, []); // ONE pass over bigArray

Senior Engineer Perspective

Be candid that transducers are a niche, advanced technique — reach for them only when profiling shows the intermediate-array allocations from a long .filter().map().filter() chain over genuinely large datasets (tens of thousands+ of elements, run frequently) actually matter, not by default. For UI-sized arrays (hundreds of rows), plain chained array methods are more readable and the performance difference is noise; over-engineering this in a typical React list is a code smell interviewers will probe for.

Q55. Refactor an imperative accumulation loop into a declarative functional pipeline. What's actually gained?

ROI: ★★★★☆ Frequency: High

Short Answer

Imperative code describes how to compute a result step by step with mutable local state; declarative/functional code describes what the result is as a composition of pure transformations. The gain isn't raw performance (imperative is often marginally faster) — it's fewer places a mutation bug can hide, easier unit-testing of each individual step, and code that reads closer to the business requirement itself.

Code Example

// Imperative
function getTopSpendersImperative(orders) {
  const totals = {};
  for (const order of orders) {
    if (!totals[order.userId]) totals[order.userId] = 0;
    totals[order.userId] += order.amount;
  }
  const result = [];
  for (const userId in totals) {
    if (totals[userId] > 1000) result.push({ userId, total: totals[userId] });
  }
  result.sort((a, b) => b.total - a.total);
  return result;
}

// Declarative / functional
function getTopSpenders(orders) {
  const totals = orders.reduce((acc, o) => {
    acc[o.userId] = (acc[o.userId] || 0) + o.amount;
    return acc;
  }, {});

  return Object.entries(totals)
    .map(([userId, total]) => ({ userId, total }))
    .filter((entry) => entry.total > 1000)
    .sort((a, b) => b.total - a.total);
}

Senior Engineer Perspective

A mature answer resists the temptation to claim the functional version is unconditionally "better" — it's a readability/maintainability trade for a small constant-factor performance cost from intermediate arrays (tie this back to Q54's transducer discussion for when that cost actually matters). The strongest framing: prefer declarative pipelines by default for typical UI-scale data because bugs from forgotten mutable state (the imperative version's easiest-to-miss failure mode) are more expensive than the performance difference.

Q56. What is referential transparency, and why does it matter for memoization and testing?

ROI: ★★★★☆ Frequency: Medium

Short Answer

An expression is referentially transparent if it can be replaced by its resulting value everywhere it appears without changing the program's behavior — which is only true for pure function calls with no hidden dependency on outside mutable state. This is precisely the property memoization exploits (caching "the call" is safe only if the call is guaranteed to always mean "the value"), and it's why pure functions need no mocking to test — same input always means same, directly assertable output.

Code Example

// Referentially transparent -- can be replaced with its return value anywhere
const tax = (amount) => amount * 0.08;
tax(100); // always 8, everywhere, forever -- safe to memoize, trivial to test

// NOT referentially transparent -- depends on hidden external state
let taxRate = 0.08;
const taxImpure = (amount) => amount * taxRate; // same input, different output over time
taxRate = 0.10;
taxImpure(100); // 10 now, was 8 before -- caching this would be WRONG

// Also not referentially transparent -- reads the current time as a side input
const isExpired = (token) => token.expiresAt < Date.now();

Senior Engineer Perspective

Connect this directly back to the memoize helper from Q15/Q46 of earlier chapters: memoizing a function that isn't referentially transparent produces genuinely wrong results, not just stale-but-harmless ones — this is the theoretical justification for the "only memoize pure functions" rule stated there. In React, this is also exactly why useMemo/useCallback dependency arrays must include every value the function actually reads — omitting one breaks referential transparency silently.

Q57. Implement a pipe/compose utility that works for a sequence of async (promise-returning) functions.

ROI: ★★★★☆ Frequency: Medium

Short Answer

The plain synchronous pipe from Q50 breaks the moment one step is async, because reduce's accumulator would become a promise passed as-is into the next function instead of being awaited first. The fix is an async-aware version whose reducer awaits the accumulator before calling the next function, so it works uniformly whether each step is sync or async.

Code Example

const pipeAsync = (...fns) => (input) =>
  fns.reduce(
    (accPromise, fn) => accPromise.then((value) => fn(value)),
    Promise.resolve(input)
  );

const fetchUser = (id) => fetch(`/api/users/${id}`).then((r) => r.json());
const enrichWithOrders = async (user) => ({
  ...user,
  orders: await fetchOrders(user.id),
});
const formatForDisplay = (user) => ({ name: user.name, orderCount: user.orders.length });

const loadUserSummary = pipeAsync(fetchUser, enrichWithOrders, formatForDisplay);
const summary = await loadUserSummary(42); // works even though steps mix sync/async

Senior Engineer Perspective

The key implementation detail to get right: seeding the reduce with Promise.resolve(input) rather than the raw input, so every step in the chain uniformly deals with a promise via .then, regardless of whether the specific function passed in happens to be sync or async. Mention that this pattern is effectively what middleware pipelines (Express, Redux) implement under slightly different names, and that it composes cleanly with the retry (Q25) and dedup (Q24) wrappers from earlier in this chapter — each pipeline step can itself be wrapped before being passed into pipeAsync.

SECTION 11 - PROXY & REFLECT META-PROGRAMMING

Q58. What is a Proxy, and what are the most commonly used traps?

ROI: ★★★★☆ Frequency: High

Short Answer

A Proxy wraps a target object with a "handler" of trap functions that intercept fundamental operations — get (property read), set (property write), has (the in operator), deleteProperty, and others — letting you run custom logic (validation, logging, computed properties) transparently, without the code using the object even knowing it's wrapped.

Code Example

const target = { name: "Ada", age: 30 };

const proxy = new Proxy(target, {
  get(obj, prop) {
    console.log("reading", prop);
    return Reflect.get(obj, prop);
  },
  set(obj, prop, value) {
    console.log("writing", prop, "=", value);
    return Reflect.set(obj, prop, value); // must return true on success
  },
  has(obj, prop) {
    console.log("checking 'in' for", prop);
    return Reflect.has(obj, prop);
  },
  deleteProperty(obj, prop) {
    console.log("deleting", prop);
    return Reflect.deleteProperty(obj, prop);
  },
});

proxy.name;             // logs "reading name", returns "Ada"
proxy.age = 31;          // logs "writing age = 31"
"name" in proxy;         // logs "checking 'in' for name"
delete proxy.age;        // logs "deleting age"

Senior Engineer Perspective

Interviewers want to see that traps are completely transparent to consuming code — proxy.name looks like any other property access to the caller. Note that every trap that mutates or removes state must return a boolean indicating success (set/deleteProperty/defineProperty), and returning the wrong truthy/falsy value silently breaks strict-mode assignment semantics (it can throw a TypeError in strict mode if you return false from set).

Q59. Implement a validation proxy that enforces types and ranges on an object's properties.

ROI: ★★★★☆ Frequency: Medium

Short Answer

Intercept the set trap, look up a validation rule for the property being written, and throw (or reject the write) if the incoming value fails validation — this centralizes validation logic in one place instead of scattering manual checks through every place the object's properties are assigned.

Code Example

function createValidated(target, schema) {
  return new Proxy(target, {
    set(obj, prop, value) {
      const rule = schema[prop];
      if (rule && !rule.validate(value)) {
        throw new TypeError(`Invalid value for "${prop}": ${rule.message}`);
      }
      return Reflect.set(obj, prop, value);
    },
  });
}

const user = createValidated(
  {},
  {
    age: { validate: (v) => Number.isInteger(v) && v >= 0 && v <= 150, message: "must be 0-150" },
    email: { validate: (v) => typeof v === "string" && v.includes("@"), message: "must be a valid email" },
  }
);

user.age = 30;         // OK
user.email = "a@b.com"; // OK
user.age = -5;          // throws TypeError: Invalid value for "age": must be 0-150

Senior Engineer Perspective

This pattern is the meta-programming counterpart to runtime validation libraries like Zod/Yup — the trade-off worth stating is that a proxy intercepts assignment at the object level (great for guarding against accidental invalid mutation anywhere in the codebase), while schema libraries validate at explicit boundaries (form submit, API response parsing). In practice most teams use schema validation at boundaries and reserve proxies for internal invariant enforcement or debugging aids, since proxies add a small per-access overhead everywhere, forever.

Q60. How would you build a minimal reactive system (like Vue 3's reactivity) using Proxy?

ROI: ★★★★☆ Frequency: Medium

Short Answer

Wrap a plain object in a Proxy whose get trap records "this property was read during this specific computation/render" (dependency tracking), and whose set trap re-runs every computation/render that previously read the changed property — this is exactly the mechanism Vue 3's reactivity system (and, at a conceptual level, what makes signals-based libraries reactive) is built from.

Code Example

let activeEffect = null;
const targetMap = new WeakMap(); // target -> Map<prop, Set<effect>>

function reactive(target) {
  return new Proxy(target, {
    get(obj, prop) {
      track(obj, prop);
      return Reflect.get(obj, prop);
    },
    set(obj, prop, value) {
      const result = Reflect.set(obj, prop, value);
      trigger(obj, prop);
      return result;
    },
  });
}

function track(target, prop) {
  if (!activeEffect) return;
  if (!targetMap.has(target)) targetMap.set(target, new Map());
  const depsMap = targetMap.get(target);
  if (!depsMap.has(prop)) depsMap.set(prop, new Set());
  depsMap.get(prop).add(activeEffect);
}

function trigger(target, prop) {
  const effects = targetMap.get(target)?.get(prop);
  effects?.forEach((effect) => effect());
}

function effect(fn) {
  activeEffect = fn;
  fn();               // run once now to register dependencies via track()
  activeEffect = null;
}

const state = reactive({ count: 0 });
effect(() => console.log("count is", state.count)); // logs "count is 0", tracks `count`
state.count++;                                        // logs "count is 1" automatically

Senior Engineer Perspective

The core insight to articulate: reactivity here is entirely a byproduct of the get trap running during the tracked computation (so it knows which effect is "listening") and the set trap running after (so it knows what changed) — no polling, no manual subscriptions. Contrast this with React's model, which deliberately does NOT do fine-grained reactive tracking like this — React re-renders whole components and relies on the virtual DOM diff plus memoization, a very different trade-off that avoids the proxy-wrapping overhead but re-computes more per update.

Q61. What is the Reflect API, and why do Proxy traps typically call the matching Reflect method?

ROI: ★★★☆☆ Frequency: Medium

Short Answer

Reflect exposes the same fundamental object operations that Proxy traps intercept (Reflect.get, Reflect.set, Reflect.has, Reflect.deleteProperty, etc.) as plain functions instead of operators/statements. Calling Reflect.X inside a trap is the correct way to "perform the default behavior" — it correctly forwards the receiver (this) for getters/setters and inherited property chains, which manually reimplementing the operation would get subtly wrong.

Code Example

// WRONG-ish: obj[prop] = value loses the correct receiver in edge cases
// involving inherited accessor properties and proxies-of-proxies
const badProxy = new Proxy(target, {
  set(obj, prop, value) {
    obj[prop] = value;   // works for simple cases, but not equivalent to Reflect.set
    return true;
  },
});

// CORRECT: Reflect.set forwards the receiver correctly
const goodProxy = new Proxy(target, {
  set(obj, prop, value, receiver) {
    return Reflect.set(obj, prop, value, receiver); // preserves `this` semantics
  },
});

Senior Engineer Perspective

The nuance interviewers listen for: the fourth receiver argument matters specifically when the target has an inherited setter/getter defined via Object.defineProperty — passing it through via Reflect.set(obj, prop, value, receiver) ensures this inside that inherited setter refers to the proxy/receiver, not the raw target, matching what would happen without the proxy in the way. Most engineers never need this edge case explicitly, but knowing why the convention is "always delegate to the matching Reflect method" (rather than "usually it doesn't matter, so skip it") is the senior signal.

Q62. Implement a transparent logging/tracing proxy that wraps a function's every call.

ROI: ★★★☆☆ Frequency: Medium

Short Answer

Proxy the function itself (functions are objects, so they can be proxied) and intercept the apply trap, which fires whenever the proxy is called — log the arguments before calling through with Reflect.apply, and log the result (or thrown error) after, all without the caller or the wrapped function needing any awareness of the instrumentation.

Code Example

function traced(fn, label = fn.name) {
  return new Proxy(fn, {
    apply(target, thisArg, args) {
      console.log(`-> ${label}(${args.map(JSON.stringify).join(", ")})`);
      try {
        const result = Reflect.apply(target, thisArg, args);
        console.log(`<- ${label} returned`, result);
        return result;
      } catch (err) {
        console.log(`x  ${label} threw`, err.message);
        throw err;
      }
    },
  });
}

function add(a, b) { return a + b; }
const tracedAdd = traced(add);
tracedAdd(2, 3);
// -> add(2, 3)
// <- add returned 5

Senior Engineer Perspective

This is a genuinely useful debugging technique in a real codebase — wrapping a suspect function with a tracing proxy for a session, without touching its source at all, then removing the wrapper once you've found the bug. Mention that this generalizes to auto-instrumenting an entire module's exports in a loop for temporary profiling/logging, which is more surgical than sprinkling console.log through library code you don't own.

Q63. What are the limitations and pitfalls of Proxy that make it unsuitable for everything?

ROI: ★★★★☆ Frequency: Medium

Short Answer

Proxies can't wrap primitives (only objects/functions), every trapped operation carries real per-access performance overhead compared to a plain object, some invariants are enforced by the engine regardless of your trap's logic (e.g. you can't report a non-configurable own property as deletable), identity checks (===) treat a proxy and its target as different objects, and JSON.stringify/many built-ins interact with traps in ways that surprise people who haven't tested them directly.

Detailed Answer

A "revocable" proxy (Proxy.revocable(target, handler)) is worth knowing specifically: it returns { proxy, revoke }, and calling revoke() makes every subsequent operation on the proxy throw — useful for handing out a capability that can be permanently cut off (e.g. give a plugin access to an object, then revoke it entirely when the plugin unloads), which a plain object reference can never support.

Code Example

const target = { data: 1 };
const p = new Proxy(target, {});
p === target;          // false -- proxy has its own identity

// Invariant enforcement the trap CANNOT override:
Object.freeze(target);
const frozenProxy = new Proxy(target, {
  get() { return "hijacked"; } // engine still enforces the frozen invariant
});
frozenProxy.data;      // TypeError in strict contexts, or the trap is
                       // simply not honored for non-configurable frozen props

// Revocable proxy -- a capability you can permanently cut off
const { proxy, revoke } = Proxy.revocable({ secret: 42 }, {});
proxy.secret;   // 42
revoke();
proxy.secret;   // TypeError: Cannot perform 'get' on a proxy that has been revoked

Senior Engineer Perspective

Interviewers use this question to see if you've actually shipped a Proxy-based feature versus only read about the API — the invariant-enforcement gotcha (frozen/non-configurable properties bypassing your trap) is exactly the kind of thing that only surfaces once you try to build something like a "deep freeze with a custom error message" utility and it silently doesn't work as expected. Revocable proxies are the standout advanced feature — mention them for "give and later fully revoke access" scenarios like plugin sandboxing.

Q64. Use Proxy to implement negative array indexing (Python-style arr[-1]) and a default-value object.

ROI: ★★★☆☆ Frequency: Low-Medium

Short Answer

Both are small, focused uses of the get trap: for negative indexing, detect when the requested "index" is a negative number-like string and remap it to length + index before delegating; for default values, detect a missing key in get and return a computed fallback instead of undefined.

Code Example

function withNegativeIndices(arr) {
  return new Proxy(arr, {
    get(target, prop, receiver) {
      if (typeof prop === "string" && /^-\d+$/.test(prop)) {
        const index = target.length + Number(prop);
        return Reflect.get(target, index, receiver);
      }
      return Reflect.get(target, prop, receiver);
    },
  });
}
const arr = withNegativeIndices([10, 20, 30]);
arr[-1];  // 30 -- last element, Python-style

function withDefault(defaultValue) {
  return new Proxy(
    {},
    {
      get(target, prop) {
        return prop in target ? target[prop] : defaultValue;
      },
      set(target, prop, value) {
        target[prop] = value;
        return true;
      },
    }
  );
}
const counts = withDefault(0);
counts.apples += 1;   // reads default 0, then sets to 1 -- no manual initialization needed
counts.apples;        // 1
counts.oranges;       // 0 -- never explicitly set, still returns the default

Senior Engineer Perspective

These are the kind of "show me you can actually design a trap, not just recite the API" exercises interviewers use to separate memorized definitions from real understanding. A sharp addition: mention that both examples are illustrative rather than something you'd necessarily ship to production — negative-index proxies on hot-path array access add per-element overhead that a plain arr.at(-1) (the native, standard method for exactly this) avoids entirely, so know the built-in alternative before reaching for a proxy.

SECTION 12 - ADVANCED THIS BINDING & EDGE CASES

Q65. Implement Function.prototype.bind from scratch (a "myBind" polyfill).

ROI: ★★★★☆ Frequency: High

Short Answer

bind must return a new function that, when called, invokes the original with a fixed this and any pre-supplied leading arguments concatenated with whatever arguments the bound function is later called with. The tricky part is the new interaction: if the bound function is itself called with new, the fixed this must be ignored in favor of the newly constructed instance.

Code Example

Function.prototype.myBind = function (thisArg, ...boundArgs) {
  const targetFn = this; // the function myBind was called on

  function bound(...callArgs) {
    const isNewCall = this instanceof bound;
    return targetFn.apply(
      isNewCall ? this : thisArg,        // `new` wins over the bound `this`
      [...boundArgs, ...callArgs]
    );
  }

  bound.prototype = Object.create(targetFn.prototype || Object.prototype);
  return bound;
};

function greet(greeting, punct) { return `${greeting}, ${this.name}${punct}`; }
const bound = greet.myBind({ name: "Ada" }, "Hi");
bound("!");             // "Hi, Ada!"

function Point(x, y) { this.x = x; this.y = y; }
const BoundPoint = Point.myBind({ ignored: true }, 5);
const p = new BoundPoint(10);   // `new` wins -- `this` is the new instance, not the bound object
p instanceof Point;      // true
p.x;                     // 5

Senior Engineer Perspective

The this instanceof bound check is the whole crux of the exercise — it's how the polyfill detects "was I invoked with new?" without any dedicated API for that (in real engines, new.target would be the modern, more explicit way to check). Forgetting to set up bound.prototype correctly means new BoundPoint() would produce an instance that fails instanceof Point checks — a subtle but real bug in a naive implementation.

Q66. How do arrow-function class fields solve the classic "this is undefined" bug in React class components?

ROI: ★★★★☆ Frequency: High (legacy codebases)

Short Answer

A regular class method passed as an event handler (onClick={this.handleClick}) loses its implicit binding the moment it's detached from the instance — calling it later invokes it as a bare function, so this is undefined in strict mode (class bodies are always strict). An arrow function assigned as a class field captures this lexically from the constructor's scope at instance-creation time, so it's permanently bound to that instance regardless of how it's later called.

Code Example

class Toggle extends React.Component {
  state = { on: false };

  // BUG: a normal method loses `this` when detached as a callback
  handleClick() {
    this.setState((s) => ({ on: !s.on })); // TypeError: this is undefined
  }

  // FIX 1: arrow function class field -- `this` is captured permanently
  handleClickFixed = () => {
    this.setState((s) => ({ on: !s.on })); // always bound to this instance
  };

  // FIX 2 (older, pre-class-fields): bind explicitly in the constructor
  constructor(props) {
    super(props);
    this.handleClick = this.handleClick.bind(this);
  }

  render() {
    return <button onClick={this.handleClickFixed}>{String(this.state.on)}</button>;
  }
}

Senior Engineer Perspective

Know both historical fixes (constructor .bind, arrow class fields) because you'll encounter both in real legacy codebases, and be ready to explain the trade-off: constructor binding creates the bound function once per instance in the constructor explicitly, while arrow class fields do the same thing more tersely but create a new function per instance implicitly at class-field-initialization time — functionally equivalent, syntax sugar aside. In modern function-component code with hooks, this entire category of bug doesn't exist because there's no persistent this to lose in the first place.

Q67. What happens to `this` inside a regular function callback passed to forEach/map, versus an arrow function, inside a method?

ROI: ★★★★★ Frequency: Extremely High

Short Answer

Array callback methods invoke your callback as a plain function call (unless you pass a thisArg as the method's second argument) — so a regular function callback inside a method loses the method's this and sees undefined (strict mode) instead. An arrow function callback has no this of its own, so it transparently inherits the enclosing method's this, which is almost always what you actually want.

Code Example

class ShoppingCart {
  items = [{ price: 10 }, { price: 20 }];
  taxRate = 0.08;

  // BUG: regular function callback -- `this` inside it is undefined
  totalWithTaxBroken() {
    return this.items.reduce(function (sum, item) {
      return sum + item.price * (1 + this.taxRate); // TypeError: this is undefined
    }, 0);
  }

  // FIXED: arrow function callback inherits `this` from totalWithTax()
  totalWithTax() {
    return this.items.reduce((sum, item) => {
      return sum + item.price * (1 + this.taxRate); // `this` = the ShoppingCart instance
    }, 0);
  }
}

new ShoppingCart().totalWithTax(); // 32.4

// The historical fix before arrow functions: capture `this` in a variable
totalWithTaxOldStyle() {
  const self = this; // a.k.a. "that" -- common pre-ES6 workaround
  return this.items.reduce(function (sum, item) {
    return sum + item.price * (1 + self.taxRate);
  }, 0);
}

Senior Engineer Perspective

Mention the thisArg second parameter that forEach/map/filter/reduce's callback... — actually note reduce uniquely does NOT accept a thisArg, unlike forEach/map/filter/find, which do: this.items.forEach(function(item){...}, this) is a valid, if dated, alternative fix. Knowing that inconsistency across array methods is a nice detail that shows real familiarity rather than a surface-level "just use arrows" answer.

Q68. How does `this` differ between strict mode and sloppy mode at the top level and in a bare function call?

ROI: ★★★☆☆ Frequency: Medium

Short Answer

In sloppy (non-strict) mode, a function called without any receiver (fn()) gets this defaulted to the global object (window in browsers). In strict mode — which is automatic inside ES modules, classes, and any code with "use strict" — that same call leaves this as undefined, on purpose, so accidental global pollution through this throws immediately instead of silently succeeding.

Code Example

function sloppyFn() {
  return this; // sloppy mode: `this` === globalThis (e.g. window)
}
sloppyFn() === window; // true (non-module script, non-strict)

function strictFn() {
  "use strict";
  return this; // strict mode: `this` === undefined
}
strictFn(); // undefined

// ES modules are ALWAYS strict mode implicitly -- no directive needed
// module.js
export function fn() { return this; } // undefined, always, in a module

Senior Engineer Perspective

Tie this to a real bug class: in sloppy mode, forgetting to bind a method and accidentally writing to this.someProperty inside a detached call silently creates a global variable instead of throwing — a much harder bug to track down than the loud TypeError: Cannot set properties of undefined strict mode gives you immediately. This is one of the concrete reasons ES modules (always strict) and modern tooling default to strict mode everywhere.

Q69. How does `this` behave inside a getter/setter, a static class method, and a class field initializer?

ROI: ★★★☆☆ Frequency: Medium

Short Answer

A getter/setter's this is the object the property was accessed on (implicit binding, same as any method). A static method's this is the class itself, not an instance. A class field initializer's this is the instance currently being constructed — which is exactly why arrow-function class fields (Q66) can close over the correct instance.

Code Example

class Circle {
  #radius;
  constructor(radius) { this.#radius = radius; }

  get area() {                       // getter -- `this` is the instance read from
    return Math.PI * this.#radius ** 2;
  }
  set radius(value) {                // setter -- same `this` rule
    this.#radius = value;
  }

  static unitCircle() {              // static -- `this` is the CLASS, not an instance
    return new this(1);              // `this` here === Circle
  }

  label = `Circle(r=${this.#radius})`; // class field init -- `this` is the new instance
}

const c = new Circle(2);
c.area;                 // 12.566... -- getter's `this` was `c`
Circle.unitCircle();    // new Circle(1) -- static's `this` was the Circle class

Senior Engineer Perspective

The static-method detail is the one most candidates miss: this inside a static method is the class constructor itself, which is genuinely useful for factory methods (as shown) because new this(...) correctly returns a subclass instance if the static method is inherited and called on a subclass — plain new Circle(...) hardcoded inside the static method would not have that property.

Q70. Trace this tricky "this" quiz combining call, bind, new, and an arrow function.

ROI: ★★★★★ Frequency: High

Short Answer

Apply the priority order from the fundamentals chapter (Q8 there) line by line: new beats explicit binding beats implicit beats default, and arrow functions opt out of the whole system entirely by capturing this lexically at definition time, immune to every later call/apply/bind/new.

Code Example

const globalObj = { name: "global" };

function Person(name) {
  this.name = name;
  this.regularGreet = function () { return "Hi " + this.name; };
  this.arrowGreet = () => "Hi " + this.name; // captures Person instance's `this` forever
}

const a = new Person("Ada");
const b = { name: "Bo" };

a.regularGreet();                 // "Hi Ada"          -- implicit binding
a.regularGreet.call(b);           // "Hi Bo"           -- explicit binding wins
const bound = a.regularGreet.bind(b);
new bound();                      // `new` wins over `bind` for `this`...
                                   // but arrow-less function called with new
                                   // creates a NEW empty object as `this`,
                                   // ignoring both `b` AND `a` -- result: "Hi undefined"

a.arrowGreet();                   // "Hi Ada" -- always, no matter how it's called
a.arrowGreet.call(b);             // "Hi Ada" -- .call cannot override an arrow's `this`
const detachedArrow = a.arrowGreet;
detachedArrow();                  // "Hi Ada" -- still Ada, even fully detached

Senior Engineer Perspective

The single most important line to get right and explain out loud is new bound() — many candidates assume bind "locks" this permanently, but new on a bound function still constructs a fresh object and uses it as this, completely overriding the bound value (only the pre-filled arguments from bind survive a new call). Pair that with the arrow function's total immunity to call/apply/bind to show you understand both ends of the binding-priority spectrum.

Q71. Why can't you rebind an arrow function's `this` with call/apply/bind, and what actually happens if you try?

ROI: ★★★☆☆ Frequency: Medium

Short Answer

Arrow functions have no internal [[ThisMode]] binding of their own to set — by design, they never create a local this, arguments, or super binding, and instead resolve all three lexically from the enclosing scope at the moment they're defined. Calling .call/.apply/.bind on an arrow function still works as a normal function call (you can pass arguments through), but the thisArg you provide is silently ignored for the purposes of what this resolves to inside the arrow.

Code Example

const obj = { name: "Real Object" };

const arrow = () => this?.name; // top-level `this` -- undefined in a module/strict script

arrow.call(obj);   // NOT "Real Object" -- the call's thisArg is ignored
arrow.apply(obj);  // same -- ignored
const boundArrow = arrow.bind(obj);
boundArrow();       // still ignored -- bind cannot affect an arrow's `this`

// Arguments DO still pass through normally, only `this` is immune:
const sum = (...args) => args.reduce((a, b) => a + b, 0);
sum.call(obj, 1, 2, 3); // 6 -- arguments work fine, only `this` binding is inert

Senior Engineer Perspective

The precise spec framing — arrow functions lack the internal slots that this-binding operations mutate, rather than "arrow functions just ignore it as a special case" — signals real depth. A good follow-up to preempt: "so how do you give an arrow function a different `this`?" — you can't; you have to define it fresh in a scope where the lexical this is already what you want, which is exactly the constraint that makes arrow class fields (Q66) reliable in the first place.

SECTION 13 - WEB WORKERS & CONCURRENCY MODEL

Q72. What is a Web Worker, and when should you actually reach for one?

ROI: ★★★★☆ Frequency: High

Short Answer

A Web Worker runs JavaScript on a genuinely separate OS thread with its own event loop, global scope, and call stack — no shared memory with the main thread by default, communication happens only through message-passing. Reach for one when you have real, sustained CPU-bound work (parsing/transforming large payloads, image/video processing, complex client-side calculations) that would otherwise block the main thread long enough to hurt input responsiveness (tie back to Q33's "long task" discussion) — not for routine async I/O, which already doesn't block the main thread.

Detailed Answer

A worker cannot touch the DOM directly — no document, no direct access to the parent page's variables — which is precisely the constraint that makes it safe to run genuinely in parallel: there's no shared mutable state to race on. The trade-offs are real: spinning up a worker has startup cost, message-passing data (unless transferred, see Q74) is copied via structured clone, and debugging across the thread boundary is harder than single-threaded code.

Code Example

// main.js
const worker = new Worker("./sort-worker.js");
worker.postMessage({ type: "SORT", payload: hugeArray });
worker.onmessage = (e) => {
  console.log("sorted result:", e.data.payload);
};

// sort-worker.js -- runs on its own thread, main thread stays responsive
self.onmessage = (e) => {
  if (e.data.type === "SORT") {
    const sorted = e.data.payload.slice().sort((a, b) => a - b);
    self.postMessage({ type: "SORTED", payload: sorted });
  }
};

Senior Engineer Perspective

The maturity signal is knowing when NOT to use a worker: most "my app feels slow" complaints are actually rendering/re-render problems (fixed with memoization, virtualization, code-splitting) or genuine long tasks better solved by chunking (Q33), not something needing a whole new thread. Workers earn their complexity specifically when the computation is heavy enough, and self-contained enough (no DOM access needed), that offloading it is worth the message-passing overhead and added architectural complexity.

Q73. How do you communicate with a worker, and what data can and can't be sent via postMessage?

ROI: ★★★★☆ Frequency: Medium

Short Answer

postMessage sends data by structured clone by default — a deep copy algorithm that handles most built-in types (objects, arrays, Map, Set, Date, typed arrays, even circular references) but cannot clone functions, DOM nodes, or class instances (they arrive stripped down to a plain object, losing their prototype/methods).

Code Example

// This works -- structured-cloneable data
worker.postMessage({
  numbers: [1, 2, 3],
  date: new Date(),
  map: new Map([["a", 1]]),
  nested: { deep: { value: 42 } },
});

// This THROWS a DataCloneError -- functions can't be cloned
worker.postMessage({ callback: () => console.log("nope") });

// This "works" but silently loses behavior -- class instances lose their prototype
class Point { constructor(x, y) { this.x = x; this.y = y; } distance() { /* ... */ } }
worker.postMessage(new Point(1, 2));
// Inside the worker, e.data is a PLAIN OBJECT { x: 1, y: 2 } -- .distance is gone

Senior Engineer Perspective

The class-instance gotcha catches people who assume message-passing is "just like calling a function with these arguments" — it isn't; everything is deep-cloned into plain data, so any methods or prototype behavior must be reconstructed on the receiving side (e.g. re-wrap the plain object with Object.assign(new Point(0,0), receivedData) or a dedicated deserializer) if you need it. This is exactly why worker-based architectures tend to pass plain serializable messages (often typed as a discriminated union with a type field) rather than rich objects.

Q74. What are Transferable objects, and how do they avoid the copy cost of structured clone?

ROI: ★★★☆☆ Frequency: Medium

Short Answer

Structured clone normally deep-copies data crossing the worker boundary, which is expensive for large binary buffers. A Transferable (an ArrayBuffer, MessagePort, or similar) can instead be handed over by reference transfer — ownership moves to the receiving context in O(1) time regardless of size, and the sending side's reference becomes unusable (its byte length becomes 0) rather than being copied.

Code Example

const buffer = new ArrayBuffer(64 * 1024 * 1024); // 64MB
const view = new Uint8Array(buffer);
view.fill(42);

// Pass the SECOND argument to postMessage to transfer, not copy
worker.postMessage({ payload: buffer }, [buffer]);

console.log(buffer.byteLength); // 0 -- ownership moved, this side can no longer use it

// Inside the worker:
self.onmessage = (e) => {
  const receivedBuffer = e.data.payload; // full 64MB, transferred in O(1), not copied
  console.log(receivedBuffer.byteLength); // 67108864
};

Senior Engineer Perspective

The trade-off to state clearly: transfer is dramatically faster for large binary payloads (image data, audio buffers, large typed arrays used for numerical work) but it's a genuine move, not a copy — if your code on the sending side still needs the data after posting it, you must copy it yourself first (buffer.slice()) before transferring, or restructure so the sender doesn't need it anymore. Forgetting this produces confusing bugs where a buffer mysteriously reads as empty after being "sent."

Q75. What is SharedArrayBuffer and Atomics, and why were they briefly disabled across browsers?

ROI: ★★★☆☆ Frequency: Low-Medium

Short Answer

SharedArrayBuffer is genuinely shared memory between the main thread and workers — both sides read/write the same underlying bytes with no copying or transferring at all, and Atomics provides the synchronization primitives (atomic read/write/compare-and-swap, Atomics.wait/notify) needed to coordinate access safely without classic race conditions. Browsers disabled it fleet-wide in 2018 in response to the Spectre side-channel vulnerability, since high-resolution shared memory timing is exactly the primitive Spectre-style attacks need; it was re-enabled afterward but gated behind stricter cross-origin isolation headers (Cross-Origin-Opener-Policy / Cross-Origin-Embedder-Policy).

Code Example

// Requires the page to be served with COOP/COEP headers for cross-origin isolation
const sab = new SharedArrayBuffer(4);
const view = new Int32Array(sab);

worker.postMessage(sab); // NOT a copy -- both sides see the SAME memory

// Main thread
Atomics.store(view, 0, 42);

// Inside the worker -- reads the value the main thread just wrote, same memory
console.log(Atomics.load(view, 0)); // 42

// Atomics.wait/notify let a worker block (efficiently) until a value changes --
// impossible with regular postMessage, which is always async

Senior Engineer Perspective

Be upfront that this is genuinely rare in typical React application code — it shows up in WebAssembly threading, high-performance audio/video processing, and specialized libraries, not day-to-day feature work. What signals seniority is knowing the Spectre connection and the COOP/COEP requirement by name, since "why isn't crossOriginIsolated true on my page" is a real, if uncommon, support question this knowledge directly answers.

Q76. Walk through offloading a CPU-heavy operation (e.g. client-side image resizing) from a React component into a worker.

ROI: ★★★★☆ Frequency: Medium

Short Answer

Wrap the worker's message-passing in a promise-based helper so the rest of the component can await it like any other async call, dispatch the heavy work (e.g. decode + resize an image via OffscreenCanvas) inside the worker, and update component state only once the result comes back — the main thread never blocks on the pixel-crunching itself.

Code Example

// useImageResizer.js -- a custom hook wrapping a worker as a promise-based API
function useImageResizer() {
  const workerRef = useRef();
  if (!workerRef.current) workerRef.current = new Worker("./resize-worker.js");

  const resize = useCallback((file, targetWidth) => {
    return new Promise((resolve, reject) => {
      const worker = workerRef.current;
      const handleMessage = (e) => {
        worker.removeEventListener("message", handleMessage);
        if (e.data.error) reject(new Error(e.data.error));
        else resolve(e.data.blob);
      };
      worker.addEventListener("message", handleMessage);
      worker.postMessage({ file, targetWidth });
    });
  }, []);

  useEffect(() => () => workerRef.current?.terminate(), []); // cleanup on unmount

  return resize;
}

// Component usage -- looks like any other async operation
function ImageUploader() {
  const resize = useImageResizer();
  async function handleFile(file) {
    setLoading(true);
    const resizedBlob = await resize(file, 800); // main thread stays responsive throughout
    setPreview(URL.createObjectURL(resizedBlob));
    setLoading(false);
  }
}

Senior Engineer Perspective

The two details that separate a working prototype from a production-ready pattern: terminating the worker in the effect cleanup (otherwise it leaks for the component's whole app lifetime, tying back to Q18's memory-leak discussion), and wrapping the raw message-event API in a promise so consuming code reads like ordinary async/await rather than manual event-listener bookkeeping scattered through the component.

Q77. What's the difference between a dedicated worker, a shared worker, and a service worker?

ROI: ★★★★☆ Frequency: Medium

Short Answer

A dedicated worker is owned by exactly one page/tab that created it. A shared worker can be connected to by multiple tabs/windows from the same origin simultaneously, communicating over ports, useful for coordinating state across tabs. A service worker is a special background worker that sits between the page and the network, can intercept and respond to fetch requests, survives even when no tab is open, and is the foundation of offline support and push notifications in PWAs.

Detailed Answer

Shared workers, by contrast, are the least commonly used of the three in practice and have inconsistent browser support, so mention them but don't over-index on them.

Q78. How do you handle errors and clean termination of a Web Worker gracefully?

ROI: ★★★☆☆ Frequency: Medium

Short Answer

Listen for the worker's error event (uncaught exceptions inside the worker) and messageerror event (a message failed to deserialize), and always call worker.terminate() when you're done with it — from the main thread's side, or self.close() from inside the worker itself — so the OS thread and its memory are actually released rather than lingering for the rest of the page's life.

Code Example

const worker = new Worker("./risky-worker.js");

worker.onerror = (event) => {
  console.error("Worker crashed:", event.message, "at", event.filename, ":", event.lineno);
  worker.terminate();          // an errored worker should usually be torn down
};

worker.onmessageerror = (event) => {
  console.error("Message could not be deserialized:", event);
};

// Always terminate when the feature that needed it goes away
function cleanup() {
  worker.terminate();          // frees the thread immediately, no graceful shutdown handshake
}

// Inside the worker, an uncaught error still surfaces to the main thread's onerror,
// but the worker keeps running afterward unless explicitly terminated or it calls:
// self.close();

Senior Engineer Perspective

The detail worth flagging: unlike a crashed process in most other environments, a worker that throws an uncaught error does NOT automatically terminate itself — it keeps running and can keep receiving messages unless you explicitly call terminate() in the onerror handler. Treating an errored worker as "probably in a bad, unknown state" and tearing it down (recreating a fresh one if the feature is needed again) is the safer default than trying to keep using a worker that just threw.

SECTION 14 - ERROR HANDLING IN ASYNC CODE

Q79. What is an unhandled promise rejection, and how do you catch it globally?

ROI: ★★★★☆ Frequency: High

Short Answer

A promise rejects, but by the time the microtask queue finishes draining, nothing has attached a .catch (or a second argument to .then) to handle it — the runtime considers this an unhandled rejection and reports it, in browsers via the window.unhandledrejection event and in Node via the process.on("unhandledRejection", ...) event, both useful as a last-resort safety net for logging errors that slipped through your normal error handling.

Detailed Answer

Crucially, "unhandled" is determined once a microtask checkpoint finishes draining, not the instant of rejection — if you attach a .catch asynchronously but still within the same tick (a common pattern in some libraries), the rejection is retroactively considered handled and a matching rejectionhandled event fires. In Node, unhandled rejections are treated increasingly seriously by the runtime itself — recent versions terminate the process by default unless handled, matching how an uncaught synchronous exception behaves.

Code Example

// Browser: global safety net
window.addEventListener("unhandledrejection", (event) => {
  console.error("Unhandled rejection:", event.reason);
  reportToErrorTracking(event.reason);
  event.preventDefault(); // suppress the default browser console warning, optional
});

// Node.js equivalent
process.on("unhandledRejection", (reason, promise) => {
  console.error("Unhandled rejection at:", promise, "reason:", reason);
});

// The bug this catches: a floating promise with no .catch anywhere
function loadPreferences() {
  fetchPreferences(); // no .then/.catch, no await -- if this rejects, it's unhandled
}

Senior Engineer Perspective

Frame this correctly as a safety net, not a substitute for real error handling — logging an unhandled rejection tells you something went wrong somewhere, but by then you've usually lost the context to recover gracefully (show a specific error message, retry, fall back). The senior instinct is to use ESLint's no-floating-promises/require-await rules (Q85) to catch these at write-time, and reserve the global handler purely for defense-in-depth logging in production.

Q80. How do try/catch/finally interact with async/await inside loops and alongside Promise.all?

ROI: ★★★★☆ Frequency: High

Short Answer

A try/catch wrapped around a loop of sequential awaits catches the first failure and stops the loop entirely (subsequent iterations never run). Wrapping Promise.all in a single try/catch catches whichever input rejects first, but by design tells you nothing about which of the other inputs also failed or succeeded — for that you need per-item try/catch or Promise.allSettled (Q5).

Code Example

// try/catch around a sequential loop -- one failure stops everything after it
async function processAllStopOnError(ids) {
  const results = [];
  try {
    for (const id of ids) {
      results.push(await processItem(id)); // 3rd item fails -> loop stops here
    }
  } catch (err) {
    console.error("stopped early:", err);
  }
  return results; // only contains items processed BEFORE the failure
}

// Per-item try/catch -- keeps going, collects both successes and failures
async function processAllContinueOnError(ids) {
  const results = [];
  for (const id of ids) {
    try {
      results.push({ id, value: await processItem(id) });
    } catch (err) {
      results.push({ id, error: err.message }); // record failure, keep looping
    }
  }
  return results;
}

// try/catch around Promise.all -- catches the FIRST rejection only
try {
  await Promise.all(ids.map(processItem));
} catch (err) {
  console.error("at least one failed, don't know which others also did:", err);
}

Senior Engineer Perspective

The decision interviewers want you to articulate explicitly: do you need "stop at the first failure" semantics (fail-fast, use a shared try/catch or plain Promise.all), or "process everything, report all outcomes" semantics (per-item try/catch, or Promise.allSettled)? Conflating these two and being surprised that a shared try/catch silently drops the remaining items is a common real-world bug in batch-processing code.

Q81. How do you design a custom error class hierarchy for async operations, and why use the { cause } option?

ROI: ★★★★☆ Frequency: High

Short Answer

Extend the built-in Error class into a small hierarchy (AppError as a base, then NetworkError, ValidationError, NotFoundError, etc.) so calling code can branch on error type with instanceof instead of parsing message strings. When you catch a low-level error and rethrow a higher-level, more meaningful one, attach the original as { cause: originalError } so the full failure chain survives for logging, instead of discarding the root cause.

Code Example

class AppError extends Error {
  constructor(message, options) {
    super(message, options);      // forwards { cause } to the base Error
    this.name = this.constructor.name;
  }
}
class NetworkError extends AppError {}
class ValidationError extends AppError {
  constructor(message, fieldErrors, options) {
    super(message, options);
    this.fieldErrors = fieldErrors;
  }
}

async function loadUser(id) {
  try {
    const res = await fetch(`/api/users/${id}`);
    if (!res.ok) throw new Error(`HTTP ${res.status}`);
    return await res.json();
  } catch (err) {
    throw new NetworkError(`Failed to load user ${id}`, { cause: err }); // preserves original
  }
}

try {
  await loadUser(42);
} catch (err) {
  if (err instanceof NetworkError) {
    console.error(err.message, "caused by:", err.cause); // full chain available
  } else if (err instanceof ValidationError) {
    console.error(err.fieldErrors);
  }
}

Senior Engineer Perspective

Interviewers want two things here: knowing that custom error classes let calling code branch on type rather than brittle string matching on err.message, and knowing that the ES2022 { cause } option is the standardized way to preserve a full error chain across abstraction boundaries — before it existed, teams either lost the original error entirely or hand-rolled their own .originalError property, which error-tracking tools didn't understand as well as the now-standard cause chain.

Q82. Distinguish operational errors from programmer errors in async code, and how each should be handled.

ROI: ★★★★☆ Frequency: High

Short Answer

Operational errors are expected failures in a correctly-written program interacting with the outside world — a network timeout, a 404, invalid user input, a rate limit. They should be caught, handled gracefully (retry, show a message, fall back), and are a normal part of control flow. Programmer errors are bugs — calling a function with the wrong type, a null-reference from a logic mistake — and should generally NOT be caught and silently continued; they should surface loudly (crash reporter, error boundary, process exit) so they get fixed.

Code Example

async function fetchOrder(orderId) {
  if (typeof orderId !== "string") {
    // Programmer error -- a caller passed the wrong type. Don't "handle" this
    // gracefully with a fallback value; let it fail loudly during development/testing.
    throw new TypeError("orderId must be a string");
  }

  try {
    const res = await fetch(`/api/orders/${orderId}`);
    if (res.status === 404) {
      // Operational error -- entirely expected, handle it as real application logic
      return null; // "order not found" is a valid, anticipated outcome
    }
    if (!res.ok) throw new NetworkError(`HTTP ${res.status}`); // operational, but unexpected -- rethrow for caller to decide
    return await res.json();
  } catch (err) {
    if (err instanceof NetworkError) {
      logger.warn("order fetch failed, will retry", err);
      throw err; // let the caller decide: retry, show a toast, etc.
    }
    throw err; // don't swallow anything you don't specifically understand
  }
}

Senior Engineer Perspective

The failure mode this question is really probing for is the blanket catch (e) { /* ignore */ } anti-pattern, which treats every error — including genuine bugs — as equally safe to swallow. A senior engineer's catch blocks are deliberately narrow: catch the specific operational errors you know how to recover from, and let everything else (especially programmer errors) propagate to a level that can log it properly and fail visibly, rather than hiding it behind a falsely "working" UI.

Q83. Why can't a React Error Boundary catch an error thrown inside an event handler or a setTimeout callback?

ROI: ★★★★☆ Frequency: High

Short Answer

Error boundaries only catch errors thrown during rendering (and in lifecycle methods/constructors of the tree below them) — they work by wrapping React's own render call stack. An error thrown inside a setTimeout callback, a promise rejection, or a DOM event handler happens on a completely separate call stack, outside of anything React's render process is watching, so it's a plain uncaught JS exception (or unhandled rejection) instead.

Code Example

class Boundary extends React.Component {
  state = { hasError: false };
  static getDerivedStateFromError() { return { hasError: true }; }
  render() {
    return this.state.hasError ? <p>Something broke</p> : this.props.children;
  }
}

function Buggy() {
  function handleClick() {
    throw new Error("boom"); // NOT caught by the Boundary above -- separate call stack
  }
  useEffect(() => {
    setTimeout(() => { throw new Error("also boom"); }, 100); // ALSO not caught
  }, []);

  // This one IS caught -- it throws during rendering itself
  if (someCondition) throw new Error("thrown during render");

  return <button onClick={handleClick}>Click</button>;
}

Senior Engineer Perspective

The correct fix for event-handler and async errors is ordinary JavaScript error handling — wrap the handler body in try/catch and set local error state yourself, or use a global window.onerror/unhandledrejection listener for last-resort logging (Q79). React 19's new root-level onUncaughtError/onCaughtError options refine this reporting story further, but the fundamental rule stays the same: error boundaries are a rendering-time safety net, not a general try/catch replacement for your whole application.

Q84. How do you aggregate multiple independent errors when several parallel async operations can each fail on their own?

ROI: ★★★☆☆ Frequency: Medium

Short Answer

Run the operations with Promise.allSettled so every outcome (success or failure) is captured individually, then collect the rejected ones and wrap them in a single AggregateError if you want to surface "here's everything that went wrong" as one throwable, catchable unit rather than only reporting the first failure.

Code Example

async function validateAll(validators) {
  const results = await Promise.allSettled(validators.map((v) => v()));
  const errors = results
    .filter((r) => r.status === "rejected")
    .map((r) => r.reason);

  if (errors.length > 0) {
    throw new AggregateError(errors, `${errors.length} validation(s) failed`);
  }
}

try {
  await validateAll([validateEmail, validatePassword, validateAge]);
} catch (err) {
  if (err instanceof AggregateError) {
    err.errors.forEach((e) => console.error("-", e.message)); // every failure, not just the first
  }
}

Senior Engineer Perspective

This is exactly the pattern used inside the native Promise.any implementation internally (Q27) — recognizing that AggregateError isn't just a Promise.any-only feature, but a general-purpose "here are N related failures, treat them as one error" primitive, is what separates a candidate who's memorized Promise.any's signature from one who understands the underlying pattern well enough to reuse it elsewhere, like a form with several independent field validators.

Q85. What is a "floating promise" anti-pattern, and how do lint rules like no-floating-promises prevent it?

ROI: ★★★★☆ Frequency: High

Short Answer

A floating promise is one that's created (by calling an async function or a promise-returning API) but never awaited, returned, or given a .catch — its result and any rejection are simply discarded, silently, at compile time indistinguishable from intentional fire-and-forget. Lint rules like @typescript-eslint/no-floating-promises flag every promise-returning expression used as a bare statement, forcing you to explicitly mark intentional fire-and-forget calls (usually by prefixing with void) so accidental ones stand out as lint errors instead.

Code Example

// Flagged by no-floating-promises -- looks intentional but silently drops errors
function handleSubmit() {
  saveForm(data); // async call, result and rejection both discarded
}

// FIX 1: await it if the caller can be async
async function handleSubmit() {
  await saveForm(data); // errors now propagate normally
}

// FIX 2: explicitly mark a genuinely-intentional fire-and-forget
function handleSubmit() {
  void saveForm(data).catch((err) => logger.error("save failed", err));
  // `void` signals "yes, I meant to not await this" to both the linter and readers
}

Senior Engineer Perspective

The senior framing: this isn't stylistic pedantry — a floating promise is precisely the mechanism behind the unhandled-rejection bugs from Q79 and the "forgot to await" race conditions from earlier in this chapter. Enabling no-floating-promises project-wide converts an entire class of silent async bugs into build-time lint failures, which is a much cheaper place to catch them than production error monitoring.

SECTION 15 - DEBUGGING & PERFORMANCE OF ASYNC CODE

Q86. Why do async stack traces look broken or truncated, and how does "async stack trace" reconstruction help?

ROI: ★★★☆☆ Frequency: Medium

Short Answer

A synchronous stack trace reflects the literal chain of function calls still on the call stack — but an await suspends the function and returns control to the event loop, so by the time it resumes (potentially several macrotasks later), the original synchronous caller's stack frame is long gone; a naive trace would show only the immediate async continuation with no history. Modern engines and DevTools reconstruct a synthetic "async stack trace" by tracking the promise chain across suspension points, stitching together the logical call history even though it was never actually on the real call stack at any single instant.

Code Example

async function level3() { throw new Error("boom"); }
async function level2() { await level3(); }
async function level1() { await level2(); }

level1().catch((err) => console.error(err.stack));
// Modern V8/DevTools output (with async stack traces enabled, the default today):
// Error: boom
//     at level3 (file.js:1)
//     at async level2 (file.js:2)   <- "async" frames reconstructed across the await
//     at async level1 (file.js:3)
// Older engines / without this feature: you'd only see "at level3", with the
// rest of the logical call chain lost because it wasn't on the literal stack.

Senior Engineer Perspective

Mention that this reconstruction has a real runtime cost (the engine has to retain extra bookkeeping to stitch the chain together), which is why some environments make it opt-in or limit its depth — and that it's most fragile across genuine macrotask boundaries (a callback fired much later from an unrelated setTimeout) versus microtask/promise chains, where the connection is easier for tooling to preserve. Knowing this explains why some production stack traces are still frustratingly short despite the feature existing.

Q87. How do you profile async operations to find slow awaits and request waterfalls using Chrome DevTools?

Short Answer

The Network panel's waterfall view visually shows each request's start time and duration on a shared timeline — a genuine waterfall (each request starting only after the previous one finishes) is immediately visible as a staircase pattern, versus true parallel requests overlapping in time. The Performance panel's flame chart additionally shows exactly where time is spent between requests — script execution, layout, or idle waiting — which the Network panel alone doesn't reveal.

// Instrument manually alongside DevTools for custom async timing
async function loadDashboard(userId) {

  performance.mark("user-loaded");

Senior Engineer Perspective

The diagnostic instinct interviewers want: seeing a staircase in the Network waterfall is the trigger to go check the source for exactly the "sequential awaits that should be parallel" bug from Q9 — this question ties the debugging tool directly back to the fix, which is the difference between a candidate who can operate DevTools and one who can actually resolve the underlying performance issue they reveal.

Q88. Diagnose and fix a race condition where two fetches update the same piece of state out of order.

ROI: ★★★★★ Frequency: Extremely High

Short Answer

If a component fires a new request every time a dependency (like a search query) changes, a slower earlier request can resolve after a faster later one, overwriting fresh data with stale data. Detect it by watching state flicker/revert when typing quickly; fix it either with AbortController to cancel stale requests (Q16) or by tagging each request with an identifier and ignoring any response that isn't from the most recent one.

Code Example

// BUG: no protection against out-of-order responses
useEffect(() => {
  fetchResults(query).then(setResults); // a stale, slow response can win the race
}, [query]);

// FIX: ignore any response that isn't from the latest effect run
useEffect(() => {
  let isCurrent = true;
  fetchResults(query).then((data) => {
    if (isCurrent) setResults(data); // stale runs silently no-op instead of overwriting
  });
  return () => { isCurrent = false; }; // cleanup marks this run as stale
}, [query]);

// FIX (preferred): actually cancel the stale request with AbortController
useEffect(() => {
  const controller = new AbortController();
  fetchResults(query, { signal: controller.signal })
    .then(setResults)
    .catch((e) => { if (e.name !== "AbortError") throw e; });
  return () => controller.abort();
}, [query]);

Senior Engineer Perspective

Explain the trade-off between the two fixes: the isCurrent flag stops the state update but the request itself keeps running to completion on the network (wasted bandwidth/server load), while AbortController actually tells the browser to cancel the in-flight request. Also mention that data-fetching libraries (React Query, SWR, RTK Query) solve this class of bug for you automatically — knowing when to reach for a library instead of hand-rolling this every time is itself a signal of experience.

Q89. How do you measure async operation duration precisely using performance.mark, performance.measure, and console.time?

ROI: ★★★☆☆ Frequency: Medium

Short Answer

console.time/console.timeEnd is the quick-and-dirty option for local dev debugging — a labeled stopwatch printed straight to the console. performance.mark/performance.measure is the production-grade option: marks are named timestamps, measures compute durations between two marks, and both show up in the DevTools Performance panel's timeline and can be read programmatically for real user monitoring (RUM) — useful for shipping actual timing data, not just local debugging.

Code Example

// Quick local debugging
console.time("loadUser");
const user = await fetchUser(id);
console.timeEnd("loadUser"); // "loadUser: 243.12ms"

// Production-grade instrumentation, queryable and visible in DevTools
performance.mark("fetch-start");
const data = await fetchUser(id);
performance.mark("fetch-end");
performance.measure("user-fetch-duration", "fetch-start", "fetch-end");

const [measure] = performance.getEntriesByName("user-fetch-duration");

Senior Engineer Perspective

The distinction to draw: console.time never leaves your local dev session, while the Performance/User Timing API entries are inspectable by any tool (DevTools, Lighthouse, third-party RUM SDKs) and can be piped into real analytics — which is why serious performance monitoring in production always uses marks/measures, never console timers left in shipped code.

Q90. What's the difference between a request "waterfall" and true parallelism, and how do you spot and fix a waterfall in a React app?

ROI: ★★★★★ Frequency: High

Short Answer

A waterfall is a chain of requests where each one only starts once the previous one (or a component depending on it) has finished — visible as a descending staircase in the Network panel. True parallel requests overlap in time because nothing forces one to wait on another. In React specifically, waterfalls commonly hide inside nested components each fetching independently in their own useEffect, where a child's data fetch can't even start until the parent has rendered and mounted it.

Code Example

// WATERFALL: child's fetch can't start until Parent has rendered and mounted Child,
// even though child's data doesn't actually depend on parent's data
function Parent({ id }) {
  const [parentData, setParentData] = useState(null);
  useEffect(() => { fetchParent(id).then(setParentData); }, [id]);
  if (!parentData) return <Spinner />;
  return <Child id={id} />; // Child doesn't even mount until parentData exists
}
function Child({ id }) {
  const [childData, setChildData] = useState(null);
  useEffect(() => { fetchChild(id).then(setChildData); }, [id]); // starts LATE
  return childData ? <div>{childData.name}</div> : <Spinner />;
}

// FIXED: hoist both fetches to start together, independent of render order
function ParentFixed({ id }) {
  const [parentData, setParentData] = useState(null);
  const [childData, setChildData] = useState(null);
  useEffect(() => {
    fetchParent(id).then(setParentData);   // both start
    fetchChild(id).then(setChildData);     // at the same time
  }, [id]);
  // render can show partial data as each piece arrives, no artificial waterfall
}

Senior Engineer Perspective

Tie this to modern data-layer patterns: React Query/SWR's cache plus prefetching, or React 19 Server Components/Suspense with parallel data fetching at route level, exist specifically to avoid the "fetch-on-render" waterfall that naive component-local useEffect fetching produces. A senior answer recognizes that the fix is architectural (fetch data as high and as early as possible, independent of the component tree's mount order) rather than a one-off Promise.all patch.

Q91. How do you unit test async code using fake timers to avoid real waiting?

ROI: ★★★★☆ Frequency: High

Short Answer

Testing frameworks (Jest, Vitest) provide fake timers that replace setTimeout/setInterval with a controllable virtual clock — you call something like jest.advanceTimersByTime(ms) to instantly "fast-forward" past a delay instead of the test actually waiting in real time, which makes debounce/throttle/retry-with-backoff tests run in milliseconds instead of the real-world seconds they'd otherwise need.

Code Example

// Vitest / Jest-style fake timer test for the debounce implementation from Q11
test("debounce only calls fn once after the wait period", () => {
  vi.useFakeTimers();
  const fn = vi.fn();
  const debounced = debounce(fn, 300);

  debounced(); debounced(); debounced(); // three rapid calls
  expect(fn).not.toHaveBeenCalled();      // nothing yet -- still within the wait window

  vi.advanceTimersByTime(299);
  expect(fn).not.toHaveBeenCalled();      // still not quite there

  vi.advanceTimersByTime(1);
  expect(fn).toHaveBeenCalledTimes(1);    // fires exactly once, at the 300ms mark

  vi.useRealTimers();                     // always restore afterward
});

// Testing a promise-based delay without a real wait
test("retry waits with exponential backoff between attempts", async () => {
  vi.useFakeTimers();
  const attempt = vi.fn()
    .mockRejectedValueOnce(new Error("fail"))
    .mockResolvedValueOnce("ok");

  const promise = retry(attempt, { retries: 1, baseMs: 100 });
  await vi.advanceTimersByTimeAsync(150); // fast-forward past the backoff delay
  await expect(promise).resolves.toBe("ok");
});

Senior Engineer Perspective

The common trap to flag: mixing fake timers with real promise microtasks can deadlock a test if you forget to also flush microtasks (modern test runners' advanceTimersByTimeAsync/runAllTimersAsync variants handle this correctly; the older sync-only APIs can leave a test "waiting" on a promise that never gets a chance to resolve). Always pair useFakeTimers() with a matching useRealTimers() cleanup so one test's fake clock doesn't leak into the next test file.

Q92. Walk through diagnosing a "component re-rendered with stale data" bug caused by an out-of-order async response.

ROI: ★★★★★ Frequency: Extremely High

Short Answer

Reproduce it deterministically first (throttle the network in DevTools, or add artificial variable delays to different endpoints, to force responses to land out of order reliably instead of relying on flaky timing). Then confirm the hypothesis by logging the request's input alongside its resolved response — if you see a response for query "a" arriving and being applied to state after a response for query "ab" already rendered, you've confirmed the exact race from Q88, not some unrelated re-render issue.

Detailed Answer

A disciplined diagnostic sequence: (1) rule out a plain re-render/memoization bug first by checking whether the component even re-fetches when you expect it to (React DevTools Profiler, or a simple render-count log); (2) once confirmed it IS an async data issue, log every request's start input and its corresponding response, with timestamps, to see the actual arrival order; (3) once the race is confirmed, apply the fix from Q88 (AbortController or an "is this still current" guard) rather than reaching for an unrelated fix like adding a debounce, which only reduces the frequency of the race without eliminating it.

Code Example

// Diagnostic logging -- add temporarily to see the real arrival order
useEffect(() => {
  const requestId = query; // capture what THIS effect run is fetching
  console.log("fetch started for:", requestId, performance.now());

  fetchResults(query).then((data) => {
    console.log("fetch resolved for:", requestId, "at", performance.now(),
                "-- current query is now:", query); // compare requestId to current query
    setResults(data);
  });
}, [query]);
// If "resolved for: a" logs AFTER "resolved for: ab" but the effect's closed-over
// `query` for the "a" run doesn't match the CURRENT input value, you've proven
// the race and can now apply the AbortController/isCurrent fix with confidence.

Senior Engineer Perspective

The meta-skill being tested is diagnostic discipline: confirm the actual mechanism with evidence (logs, network throttling, timestamps) before reaching for a fix, rather than pattern-matching "flaky async bug" to "just add a debounce" or "just add a loading spinner," neither of which addresses the root cause and both of which can mask the bug intermittently rather than eliminate it. This chapter's real throughline — sequencing, cancellation, and race conditions — all converges in exactly this kind of bug, which is why it's one of the most commonly asked practical debugging questions for a mid-to-senior frontend role.
