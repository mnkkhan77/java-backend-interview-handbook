29 - FRONTEND SYSTEM DESIGN

Target Audience: Frontend / React Engineer (3–6 Years) Goal: Not just answer questions, but survive follow-up grilling from experienced interviewers.

Frontend system design is now a standard round at senior level. Unlike backend system design (databases, sharding, queues), it's about client architecture: component structure, state and data flow, rendering strategy, performance budgets, accessibility, and resilience — plus the ability to reason about trade-offs out loud. This chapter gives you a repeatable framework and then walks three canonical case studies (news feed, typeahead, chat) end to end.

SECTION 1 - THE FRAMEWORK

Q1. How do you approach a frontend system design interview?

ROI: ★★★★★ Frequency: Extremely High

Short Answer

Follow a structured flow: (1) clarify requirements and scope, (2) define the data model and API contract, (3) sketch the component architecture, (4) design state and data flow, (5) address cross-cutting concerns (performance, accessibility, error handling), and (6) discuss trade-offs. Drive the conversation and state assumptions explicitly.

Detailed Answer

1. Clarify & scope (don't skip this)

Ask about functional requirements (what features), non-functional ones (scale, devices, offline, latency, SEO needs), and constraints. Nail down scope — "are we designing just the feed, or posting too?" Interviewers deduct points for candidates who start drawing before understanding the problem.

2. Data model & API

Define the shape of the entities and the API you'll consume (REST/GraphQL, pagination style, real-time channel). This anchors everything downstream.

3. Component architecture

Break the UI into a component tree; identify container vs presentational boundaries, shared/reusable pieces, and where state lives.

4. State & data flow

Classify state (server state, global client state, local UI, URL) and pick the tool for each. Show how data flows from API → cache → components.

5. Cross-cutting concerns

Performance (virtualization, code splitting, Web Vitals), accessibility, i18n, error/empty/loading states, and offline/resilience.

6. Trade-offs

Every choice has a cost. Verbalize alternatives and why you chose one — that's the actual signal being measured.

Senior Engineer Perspective

The number-one differentiator is driving the conversation with structure and thinking out loud, not producing a perfect diagram. Time-box each phase, check in ("does that scope sound right?"), and always tie decisions to requirements. Silence and jumping straight to code are the two biggest red flags.

Q2. How do you design a reusable component / component API?

ROI: ★★★★☆ Frequency: High

Short Answer

Design the API from the consumer's perspective: sensible defaults, controlled/uncontrolled support, composition over configuration (use children and compound components rather than a giant props list), accessible by default, and styleable without leaking internals. Keep it predictable and hard to misuse.

Detailed Answer

  • Composition over config — a <Select> with <Option> children scales better than 20 boolean props. Compound components share state via context.
  • Controlled & uncontrolled — support both value/onChange (controlled) and defaultValue (uncontrolled) so it fits any usage.
  • Sensible defaults, escape hatches — works out of the box, but allows className, asChild/polymorphic as, and ref forwarding for advanced cases.
  • Accessible by default — correct roles, keyboard support, focus management baked in (see headless libraries like Radix/React Aria).
  • Predictable — no surprising side effects; typed props; clear error messages.

Senior Engineer Perspective

Reference the "headless component" trend (Radix, React Aria, Headless UI): they provide behavior + accessibility, you provide styles. Designing for a design system means versioning, documentation (Storybook), and visual regression tests. Mention that a good API is "easy to use correctly, hard to use incorrectly."

Q3. How do you architect state and data flow at scale?

ROI: ★★★★★ Frequency: High

Short Answer

Categorize state and use the right tool for each: server state (TanStack Query / RTK Query — caching, sync), global client state (Zustand / Redux Toolkit / Context), local UI state (useState/useReducer), and URL state (router/search params). Avoid dumping everything in one global store.

Detailed Answer

State typeExamplesTool
Server stateAPI data, lists, entitiesTanStack Query / RTK Query / SWR
Global client stateAuth user, theme, cartZustand / Redux Toolkit / Context
Local UI stateModal open, input value, tabuseState / useReducer
URL stateFilters, page, search queryRouter / useSearchParams

The biggest architectural mistake is treating fetched API data as global client state (manually stuffing it into Redux). Server state has caching, staleness, refetching, and dedup needs that a dedicated data layer handles far better. Keep client state minimal, colocate local state near where it's used, and lift only when genuinely shared.

Senior Engineer Perspective

The senior take: "most 'global state' problems disappear once you move server data into a query cache and keep the rest local." That framing — server state vs client state as distinct problems — is exactly what distinguishes a modern architecture from the 2018 "everything in Redux" era.

Q4. How do you design the data-fetching layer (caching, normalization, optimistic UI)?

ROI: ★★★★☆ Frequency: High

Short Answer

Use a query/cache library keyed by query params, with configurable staleness and background refetch. Normalize entities (store by ID) when the same object appears across many views to avoid duplication and keep them in sync. Use optimistic updates for mutations so the UI feels instant, with rollback on error.

Detailed Answer

  • Caching & keys — cache responses by a stable key (['posts', { page }]); dedupe concurrent identical requests; serve cache instantly and revalidate in the background (stale-while-revalidate).
  • Normalization — for highly relational data reused across screens (a user shown in a feed, a profile, and a comment), store entities by ID once and reference them, so an edit updates everywhere. TanStack Query keeps a document cache; RTK Query and Apollo (GraphQL) offer normalized caches.
  • Optimistic UI — apply the expected result immediately, roll back if the server rejects. Great for likes, toggles, sends.
  • Invalidation — after a mutation, invalidate affected queries so they refetch.

Code Example

// Optimistic like with TanStack Query
useMutation({
  mutationFn: likePost,
  onMutate: async (postId) => {
    await qc.cancelQueries({ queryKey: ['post', postId] });
    const prev = qc.getQueryData(['post', postId]);
    qc.setQueryData(['post', postId], (p) => ({ ...p, liked: true, likes: p.likes + 1 }));
    return { prev };
  },
  onError: (_e, postId, ctx) => qc.setQueryData(['post', postId], ctx.prev), // rollback
  onSettled: (_d, _e, postId) => qc.invalidateQueries({ queryKey: ['post', postId] }),
});

Senior Engineer Perspective

Know when NOT to normalize — for mostly-independent lists, a document cache is simpler and enough; normalization pays off with heavy entity reuse and real-time edits. Interviewers probe whether you'd add complexity you don't need. Always mention rollback and invalidation with optimistic updates, or it's incomplete.

Q5. How do you choose a rendering strategy (CSR / SSR / SSG / ISR)?

ROI: ★★★★☆ Frequency: High

Short Answer

Match the strategy to the content: SSG/ISR for mostly-static, SEO-critical pages (marketing, blogs, product pages); SSR for personalized, SEO-relevant, frequently-changing pages; CSR for private, highly-interactive app shells behind auth (dashboards). Modern frameworks let you mix per route, and RSC blurs the line further.

Detailed Answer

StrategyBest forSEOFreshness
SSGDocs, blog, marketingExcellentBuild-time
ISRLarge catalogs (product pages)ExcellentRevalidated periodically
SSRPersonalized, dynamic, SEO pagesExcellentPer request
CSRAuth'd dashboards, app shellsPoorClient-fetched

Trade-offs: SSR improves first paint and SEO but costs server compute and TTFB; CSR shifts work to the client (slower first paint, cheaper server) but is fine behind a login where SEO doesn't matter. With Next.js App Router + React Server Components you render static shells on the server and hydrate only interactive islands, getting SEO + performance with less client JS.

Senior Engineer Perspective

The strong answer is "per-route, not per-app" — a real product mixes SSG marketing pages, SSR personalized pages, and a CSR dashboard. Tie the choice to concrete needs (SEO? personalization? change frequency? server budget?) rather than picking a favourite. Reference streaming SSR and partial prerendering as the current frontier.

Q6. How do you keep a large frontend codebase scalable?

ROI: ★★★★☆ Frequency: Medium-High

Short Answer

Organize by feature/domain rather than by file type, enforce clear module boundaries (a feature exposes a public API, hides internals), colocate related code (component + styles + tests + hooks), share cross-cutting code via a well-defined shared/ui layer, and enforce conventions with linting and CI. For very large orgs, consider a monorepo or micro-frontends.

Detailed Answer

src/
  features/
    feed/            # everything about the feed, colocated
      components/
      hooks/
      api.ts
      index.ts       # public API of the feature
    auth/
  shared/            # cross-feature: ui kit, utils, types
    ui/
    lib/
  app/               # routing, providers, composition
  • Feature folders keep churn local; a change to the feed touches only features/feed.
  • Boundaries — features import from each other only through public index.ts barrels; enforce with lint rules (e.g. eslint-plugin-boundaries) so you don't get spaghetti imports.
  • Micro-frontends — split an app into independently deployable pieces (Module Federation) when multiple teams need autonomy; adds significant complexity, so reserve for genuine org-scale needs.

Senior Engineer Perspective

"Group by feature, not by type" is the single most valuable structural advice — the old components/ hooks/ utils/ split scatters one feature across the tree. Be honest that micro-frontends solve an organizational problem (team autonomy, independent deploys), not a technical one, and come with real overhead (shared deps, routing, consistency).

Q7. How do you treat accessibility, i18n, and resilience as first-class concerns?

ROI: ★★★★☆ Frequency: Medium

Short Answer

Bake them in, don't bolt them on: semantic HTML + keyboard support + ARIA where needed for a11y; a translation layer with locale-aware formatting and RTL support for i18n; and explicit loading/empty/error states, retries, error boundaries, and offline handling for resilience.

Detailed Answer

  • Accessibility — semantic elements, focus management on route/modal changes, color contrast, announced dynamic updates (aria-live); test with axe and keyboard-only navigation.
  • i18n — externalize strings (react-i18next / FormatJS), format dates/numbers/currency per locale (Intl), support pluralization and RTL, and design layouts that tolerate text expansion.
  • Resilience — every async view has loading, empty, and error states; use error boundaries to contain crashes; retry transient failures with backoff; degrade gracefully offline (cache, queue mutations).

Senior Engineer Perspective

Volunteering these unprompted signals maturity — juniors design the happy path only. The three states (loading/empty/error) for every data view is a concrete habit that interviewers love to hear. For i18n, mentioning text expansion and RTL layout (not just string translation) shows real experience.

SECTION 2 - CASE STUDIES

Q8. Case study: design a news feed with infinite scroll (e.g. a social feed).

ROI: ★★★★★ Frequency: Extremely High

Short Answer

Fetch paginated posts with cursor-based pagination, render them in a virtualized list, trigger the next page via an IntersectionObserver sentinel, cache pages with an infinite-query, and handle optimistic interactions (like/comment). Address media loading, layout shift, and accessibility.

Detailed Answer

Data & pagination

Use cursor-based pagination (?after=cursor), not offset — offset breaks when items are inserted/deleted and duplicates/skips rows. TanStack Query's useInfiniteQuery caches pages keyed by cursor and exposes fetchNextPage.

Rendering & performance

  • Virtualization (react-virtuoso / @tanstack/react-virtual) so 10k posts don't create 10k DOM nodes. Prefer a windowing lib that supports variable heights (posts differ in size).
  • Trigger loading with an IntersectionObserver sentinel near the list end (with rootMargin to prefetch early), not a scroll listener.
  • Media — lazy-load images (loading="lazy"), reserve dimensions to avoid CLS, use responsive srcset.

Interactions & state

Likes/bookmarks use optimistic updates with rollback. New posts can be prepended via polling or websockets ("show N new posts" button to avoid jarring jumps).

Resilience & a11y

Skeleton loaders per page, error state with retry for a failed page (don't lose the whole feed), and preserve scroll position on back-navigation. Ensure virtualization sets aria-* row counts and keyboard focus isn't lost.

Code Example

const { data, fetchNextPage, hasNextPage, isFetchingNextPage } = useInfiniteQuery({
  queryKey: ['feed'],
  queryFn: ({ pageParam }) => getFeed({ after: pageParam }),
  initialPageParam: null,
  getNextPageParam: (last) => last.nextCursor ?? undefined,
});

// Sentinel triggers next page
const ref = useRef(null);
useEffect(() => {
  const io = new IntersectionObserver(([e]) => {
    if (e.isIntersecting && hasNextPage) fetchNextPage();
  }, { rootMargin: '600px' });
  if (ref.current) io.observe(ref.current);
  return () => io.disconnect();
}, [hasNextPage, fetchNextPage]);

Senior Engineer Perspective

The details that win: cursor over offset (and why), variable-height virtualization, prefetch via rootMargin, and the "new posts" pill instead of auto-prepending (which would shift the user's reading position). Also mention restoring scroll on back-nav — a real UX pain point interviewers look for.

Q9. Case study: design an autocomplete / typeahead.

ROI: ★★★★★ Frequency: Extremely High

Short Answer

Debounce the input, cancel stale in-flight requests, cache results by query, guard against out-of-order responses (race conditions), render an accessible listbox with full keyboard support, and handle loading/empty/error states. Minimum query length and caching reduce request volume.

Detailed Answer

Requests

  • Debounce keystrokes (~250–300ms) so you query on pause, not every letter.
  • Cancel superseded requests with AbortController to save bandwidth.
  • Race conditions — a slow response for "re" must not overwrite the newer "react" results. Either rely on the query library keying by query (so only the latest key's data renders) or track the latest request id and ignore stale ones.
  • Cache by query string so re-typing a previous term is instant; set a min length (e.g. 2 chars).

Accessibility (critical here)

Implement the ARIA combobox pattern: input with role="combobox", aria-expanded, aria-controls; results as role="listbox" with role="option" items; aria-activedescendant to move the visual highlight while focus stays in the input; arrow keys to navigate, Enter to select, Escape to close. Announce result counts to screen readers.

Code Example

const debounced = useDebounce(query, 300);
const { data, isFetching } = useQuery({
  queryKey: ['search', debounced],
  queryFn: ({ signal }) => search(debounced, { signal }), // AbortController via signal
  enabled: debounced.length >= 2,
  placeholderData: (prev) => prev, // keep previous results while fetching
});
// Keying by `debounced` means only the latest query's data is rendered -> no race bug.

Senior Engineer Perspective

The three things that separate a senior answer: (1) explicitly naming the race condition and how keying/abort solves it, (2) the full keyboard + ARIA combobox pattern (most candidates forget a11y entirely), and (3) caching + min-length to cut load. Mentioning that a headless lib (Downshift / React Aria useComboBox) exists to get a11y right shows pragmatism.

Q10. Case study: design a real-time chat application.

ROI: ★★★★☆ Frequency: High

Short Answer

Use a WebSocket for bidirectional real-time messaging (with reconnect + heartbeat), optimistically render sent messages with a pending→sent→failed status, reconcile server acknowledgements by client-generated id, order messages deterministically, virtualize the message list, and handle offline queuing and history pagination.

Detailed Answer

Transport

WebSocket for low-latency two-way traffic (SSE if server→client only). Handle connection lifecycle: automatic reconnect with exponential backoff, heartbeat/ping to detect dead connections, and re-subscribe/replay missed messages on reconnect (using a last-seen message id).

Sending & optimistic UI

Generate a client-side temp id, render the message immediately as "sending", then reconcile with the server's ack (swap temp id for the real id, mark "sent"); on failure mark "failed" with a retry affordance. This makes sending feel instant.

Ordering & consistency

Don't trust arrival order — order by server timestamp/sequence number, and de-duplicate by message id (the same message can arrive via your own optimistic insert and the socket broadcast). Handle clock skew with server-assigned sequence.

List rendering & history

Virtualize the message list; load older history with reverse/upward infinite scroll (prepend without jumping the scroll position — anchor to a stable element). Show typing indicators and read receipts via lightweight socket events.

Offline & resilience

Queue outgoing messages while offline and flush on reconnect; persist unsent messages locally (IndexedDB) so a refresh doesn't lose them.

Code Example

function sendMessage(text) {
  const tempId = crypto.randomUUID();
  addMessage({ id: tempId, text, status: 'sending', ts: Date.now() }); // optimistic
  socket.emit('message', { tempId, text }, (ack) => {
    if (ack.ok) updateMessage(tempId, { id: ack.id, status: 'sent', ts: ack.ts });
    else updateMessage(tempId, { status: 'failed' });
  });
}
// Incoming broadcast: de-dupe by id so our own optimistic message isn't doubled.
socket.on('message', (msg) => upsertMessageById(msg));

Senior Engineer Perspective

The high-signal points: client-generated ids for optimistic reconciliation, de-duplication (your optimistic message vs the echoed broadcast), ordering by server sequence not arrival, and reconnect/replay logic. Mentioning offline queueing with IndexedDB and scroll anchoring on history load shows you've thought past the happy path — exactly what senior chat design demands.

SECTION 3 - MORE ON THE FRAMEWORK

Q11. How do you build performance budgets into a design as a constraint from day one?

ROI: ★★★★☆ Frequency: Medium-High

Short Answer

Define measurable performance budgets (LCP, INP, CLS, bundle size, TTFB) as part of the design spec before writing code, enforce them in CI (Lighthouse CI / bundlesize) as acceptance criteria, and make every architectural decision — rendering strategy, library choice, code-splitting boundaries — accountable to those numbers instead of discovering regressions after ship.

Detailed Answer

Why budgets, not vibes

"Make it fast" isn't actionable in a design review; "LCP < 2.5s on 4G / mid-tier Android for the product page" is. A budget gives the team a shared, testable target and lets you say no to a feature or dependency that would blow it, instead of discovering the regression in production three months later.

What to budget

  • Core Web Vitals thresholds per template/route — a marketing page and an authenticated dashboard have very different acceptable numbers.
  • JS bundle size per route (e.g. initial JS < 150KB gzipped), and a "cost" attached to every new dependency — is that date library worth 70KB?
  • Request count / critical-rendering-path depth for the initial render.

Enforcing it

A CI gate (Lighthouse CI, bundlesize/size-limit) fails the build when a budget is exceeded, so the regression is caught in the PR, not after deploy. RUM tracks the same budget against real traffic and real devices — synthetic lab runs can pass while the P75 user on a slow network/old phone fails, so you need both signals, not just one. Assign a budget owner per route/team so it doesn't silently rot.

How it shapes earlier decisions

Budgets push you toward code-splitting by route, lazy-loading below-the-fold widgets, choosing a lighter charting library, deferring non-critical third-party scripts, and picking SSR/streaming when TTFB/LCP matters more than raw client interactivity. Treat the budget as a design constraint the same way you'd treat an API rate limit — something the architecture has to satisfy, not a cleanup task for later.

Senior Engineer Perspective

Bring numbers, not adjectives — "we're budgeting 2.5s LCP for the logged-out first visit and enforcing it via Lighthouse CI on every PR" is materially stronger than "we care about performance." Also distinguish synthetic from RUM explicitly: synthetic catches regressions early and consistently every PR; RUM tells you what's actually happening to real users in the field — a synthetic pass can still hide a real-world failure at the tail.

Q12. How do you design a feature-flag and progressive-rollout architecture for frontend features?

ROI: ★★★★☆ Frequency: Medium-High

Short Answer

Decouple deploy from release by gating new UI behind flags evaluated once per request, support percentage-based/targeted rollouts plus an instant kill switch, and make sure the evaluation point is consistent between server and client (no hydration mismatch) and doesn't silently poison a shared CDN cache.

Detailed Answer

Why flags belong in the architecture, not just config

Flags let you ship code to production continuously while controlling exposure independently — a percentage rollout, an internal-only flag, an incident kill switch — without a redeploy. The system-design angle isn't "what's a flag," it's where is it evaluated, and how that interacts with caching and rendering.

Evaluation point & SSR/hydration consistency

If flags are evaluated server-side, the client must hydrate with the exact same resolved values, or React throws a hydration mismatch. Resolve the flag set once per request on the server, serialize it into the initial payload, and have the client read that same resolved value rather than re-evaluating from scratch.

Caching interaction

A CDN/edge cache keyed only by URL will serve identical HTML to every user regardless of their flag bucket. Either fragment the cache key by the relevant cohort (real but bounded cache-hit-rate cost) or keep the bulk of the page cacheable and push the flag-gated content to a small dynamic client-rendered island. This trade-off — full personalization vs cache hit rate — is the crux of the question.

Rollout mechanics

Percentage rollout by a stable hash of user/session id (not per-request random, or a user flips in and out between refreshes); target by attributes (region, plan tier, internal staff); and support an instant kill switch — flipping to 0% without a deploy — which is the actual incident-response tool that justifies most of this infrastructure.

Cleanup

Every flag is a branch in the codebase, and a stale flag is a liability. Schedule flag removal once a rollout reaches 100%/0% and treat "flag debt" as tracked work, not an afterthought.

Code Example

// Server: resolve once per request, serialize into the initial payload
const flags = await resolveFlags({ userId, cohortSeed: userId });
res.send(
  renderToString(<App flags={flags} />) +
  `<script>window.__FLAGS__=${JSON.stringify(flags)}</script>`
);

// Client: hydrate reading the SAME resolved flags — never re-evaluate
const flags = window.__FLAGS__;
hydrateRoot(document.getElementById('root'), <App flags={flags} />);

Senior Engineer Perspective

The differentiator is naming the caching interaction explicitly — most candidates describe flag evaluation but miss that a flag which changes served HTML breaks a shared CDN cache unless you fragment the key or push the variance to the client. Also worth stating: a kill-switch flag needs a deliberate fail-open/fail-closed default — a broken flag-service call should never crash the render, it should degrade to the safe state.

Q13. How do you design frontend observability — error tracking, RUM, and knowing when the UI breaks for real users?

ROI: ★★★★☆ Frequency: Medium-High

Short Answer

Combine three signals — error tracking (captured exceptions with source maps and session context), real-user monitoring (Web Vitals plus custom timings from actual sessions), and structured breadcrumbs — through a lightweight client SDK that samples intelligently, so you learn about breakage from telemetry, not from support tickets.

Detailed Answer

Error tracking

A global handler (window.onerror, unhandledrejection, plus React error boundaries) captures exceptions with stack traces mapped through uploaded source maps back to original source, tagged with release version and user/session context, and enriched with breadcrumbs — recent navigations, clicks, network calls — leading up to the error. Group by fingerprint so 10,000 occurrences of the same bug are one actionable issue, not 10,000 tickets.

Real-user monitoring (RUM)

Capture Web Vitals (LCP, INP, CLS) from the field via the web-vitals library, plus custom timings for business-critical interactions (e.g. "time to first search result rendered"), attributed by route, device class, connection type, and build version — so a regression can be bisected to a specific deploy rather than a vague "it feels slow."

Sampling & volume control

At scale you can't ship every event for every user — sample (e.g. 100% of errors but 10% of RUM sessions, or adaptive sampling that favors low-traffic-but-critical routes) and rate-limit noisy repeat errors client-side before they hit the network, or a single bad release can effectively DDoS your own telemetry pipeline.

Closing the loop

Observability is only useful if it's actionable: alert on error-rate or Web Vitals regressions tied to a specific deploy so a bad release can be rolled back fast, and correlate frontend errors with backend traces via a shared request/trace id so you debug across the stack instead of in a frontend-only silo.

Senior Engineer Perspective

The strongest answer distinguishes "monitoring" (did anything break) from "observability" (why, for whom, since when) — tying an error spike to a specific release and a specific segment (Safari on iOS 15, after last night's deploy) is what actually lets you respond fast. Also flag the self-inflicted-DDoS risk of unthrottled error reporting explicitly — it's a real production incident pattern, and naming it shows you've been on call.

Q14. How do you version a frontend's API contract and keep the client backward compatible as the backend evolves?

ROI: ★★★★☆ Frequency: Medium

Short Answer

Treat the API contract as something that changes out from under you — validate responses defensively with safe defaults for missing/unknown fields, avoid coupling the UI to backend internals, support multiple concurrent API versions during migration, and design the client to degrade gracefully rather than crash when a field is missing, renamed, or an unrecognized enum value shows up.

Detailed Answer

Why this is a frontend concern too

In any org shipping backend and frontend independently, a client built today keeps running against a backend that evolves next month — and a stale cached bundle can be served to some users for days after a backend change. Backward compatibility means the currently-deployed frontend must survive a backend change it was never built to know about.

Defensive parsing

Validate/parse responses at the boundary (zod/io-ts) rather than trusting types blindly; default optional/missing fields instead of letting null flow deep into a component and crash; treat an unrecognized enum value as "unknown/other" in the UI rather than throwing, since the backend may ship a new status/category before the frontend supports it.

Versioning strategies

Options: URL/header-based API versioning (run v1 and v2 concurrently during migration), additive-only changes (never remove or rename a field, only add — operationally simplest, but requires backend discipline), or client capability negotiation (the client declares what it understands, the server adapts response shape). GraphQL sidesteps some of this since a client only requests fields it knows about, but schema deprecations still need a migration window.

Rollout coordination & the stale-bundle problem

When a breaking change is unavoidable, stage it: ship a frontend that supports both old and new shapes first, then flip the backend, then remove the old-shape handling once telemetry shows no old clients remain. Cached service workers and old bundles linger far longer than teams expect, so "remove the old path" should be a data-driven decision, not a guess.

Senior Engineer Perspective

The senior framing: "the contract will drift, so the client's job is to not crash when it does" — additive-only backend changes plus defensive client parsing covers most real incidents. Naming the stale-bundle problem explicitly — a user on an old cached SPA build hitting a backend that's moved on — is a subtle, often-missed failure mode that signals real production experience.

SECTION 4 - MORE CASE STUDIES

Q15. Case study: design a collaborative rich-text/document editor (Google Docs-style).

ROI: ★★★★☆ Frequency: Medium-High

Short Answer

Model the document as a CRDT rather than a single mutable blob, broadcast local edits to other collaborators over a real-time channel that merges concurrent edits deterministically, render other users' cursors/selections as ephemeral presence state kept separate from durable content, and keep local edits fully optimistic so typing never waits on the network.

Detailed Answer

Conflict resolution: OT vs CRDT

Two established approaches to concurrent edits. Operational Transformation transforms each incoming remote operation against locally-applied-but-unacknowledged operations so they compose correctly — Google Docs' original approach — but requires a central server to sequence operations and careful transform functions per operation type. CRDTs (Conflict-free Replicated Data Types) make each edit a self-describing operation that merges deterministically regardless of arrival order, work well peer-to-peer, and are what libraries like Yjs/Automerge implement for rich text. At interview depth: know that OT needs a central authority for ordering, while CRDTs trade some memory/metadata overhead for merge-without-a-server and simpler correctness reasoning — most new products now reach for a CRDT library rather than hand-rolling OT.

Local editing model

The editor (ProseMirror/Slate/Lexical) maintains its own local document model and emits granular change events; those translate into CRDT updates and broadcast out, while the local view renders immediately, never blocked on a round trip. The CRDT merge reconciles what other collaborators are doing into your local view without your own cursor jumping.

Presence & cursors

Cursor position, selection range, and collaborator identity/color are ephemeral, high-frequency state — don't route them through the same durable-persistence path as document content. Broadcast over a lightweight channel (Yjs's "awareness" protocol), keyed by connection and expired automatically on disconnect, and transform cursor positions through the same operational mapping as document edits so a remote cursor doesn't drift after a concurrent insert before it.

Persistence & offline

Periodically snapshot the CRDT state to the server for durability and fast cold loads — replaying the full operation history from scratch doesn't scale. Support offline editing by queuing local updates and merging on reconnect; this is precisely what CRDTs make tractable, since merge order doesn't matter.

Performance at document scale

A very large document needs virtualization of the rendered DOM (only render visible blocks) decoupled from the full in-memory document model, plus debounced/batched network sync so every keystroke doesn't trigger a message.

import * as Y from 'yjs';
import { WebsocketProvider } from 'y-websocket';

const ydoc = new Y.Doc();
const provider = new WebsocketProvider('wss://collab.example.com', 'doc-123', ydoc);
const ytext = ydoc.getText('content');

// Bind ytext to the editor (ProseMirror/Lexical binding) — edits merge automatically.
provider.awareness.setLocalStateField('cursor', { anchor, head, name, color });

Senior Engineer Perspective

The single most important thing to say out loud: "OT needs a server to order operations; CRDTs merge without one — that's why CRDTs have become the default choice for new collaborative editors." Naming Yjs/Automerge by name, and being explicit that presence/cursor state is ephemeral and shouldn't share a path with durable content, are the two signals that separate someone who's actually built one of these from someone reciting the concept.

Q16. Case study: design a spreadsheet UI.

ROI: ★★★★☆ Frequency: Medium

Short Answer

Virtualize in two dimensions so only the visible rows and columns render, isolate re-renders to individual cells rather than the whole grid, model formulas as a dependency graph so an edit only recomputes and re-renders cells that actually depend on it, and keep the data store separate from the rendering grid so large datasets don't get funneled through React state cell-by-cell.

Detailed Answer

2D virtualization

Unlike a list (1D virtualization), a spreadsheet needs to window both rows and columns simultaneously — render only cells intersecting the visible viewport (plus a small overscan buffer), recycle DOM nodes as the user scrolls in either direction, and keep row/column headers virtualized and synced to the same scroll offset. Frozen panes complicate this further, since header rows/columns must stay pinned while the body scrolls.

Cell-level render isolation

The core anti-pattern is one big grid component that re-renders entirely on every cell edit. Instead, each cell subscribes only to its own data — a fine-grained store with selector-based subscriptions keyed by coordinate — so editing A1 doesn't re-render the other tens of thousands of rendered-but-off-screen cells; combine with memoization keyed by stable cell coordinates.

Formula dependency graph

Parse formulas into an AST and build a directed dependency graph (cell → cells it reads from). On edit, recompute only the downstream dependents in topological order — not the whole sheet — and detect circular references at graph-construction time rather than infinite-looping at runtime. This same graph drives which cells need to re-render after a recompute.

Data model & interaction

Keep the source of truth as a sparse structure indexed by coordinate, not a dense 2D array, since sheets are mostly blank; selection/range state (for copy-paste, fill-handle, multi-cell formatting) is its own concern layered on top of cell data, not stored per-cell.

Performance at scale

Push heavy aggregate recalculation to a Web Worker so typing doesn't block the main thread, debounce autosave rather than persisting on every keystroke, and consider column-oriented storage if bulk column operations (sort/filter a column) are common.

Code Example

// Sparse, per-cell store with fine-grained subscriptions
const cells = new Map(); // "r,c" -> { value, formula, listeners: Set }

function setCell(key, value) {
  cells.get(key).value = value;
  const order = topoSortFrom(key, dependencyGraph); // only downstream cells
  for (const dep of order) recompute(dep);
}
// Each <Cell> subscribes only to its own key -> editing A1 never
// re-renders the other 50,000 rendered cells.

Senior Engineer Perspective

What distinguishes a strong answer is naming the two-dimensional virtualization problem explicitly — most candidates only know 1D list virtualization — and the dependency-graph recompute, since the naive "recompute everything on every edit" approach falls over almost immediately on a real sheet. Mentioning Web Workers for heavy recalculation shows awareness that spreadsheet-scale computation doesn't belong on the main thread next to input handling.

Q17. Case study: design a Kanban / drag-and-drop board (e.g. Trello).

ROI: ★★★★★ Frequency: High

Short Answer

Model card position with a sortable rank (fractional/lexicographic indexing, not array position) so reorders touch only the moved card, apply the move optimistically the instant the drag ends, sync the change to the server and other connected clients in real time, and reconcile conflicting concurrent moves with last-write-wins on the rank plus a periodic resync.

Detailed Answer

Drag-and-drop state management

Use a dedicated DnD library (dnd-kit, Pragmatic drag-and-drop) rather than hand-rolling pointer events — they solve cross-browser pointer/touch handling, accessible keyboard-based reordering, and auto-scroll near viewport edges. During a drag, track in-progress state (dragged card id, hovered column/index) separately from committed board state so the visual preview doesn't require committing to the data model on every pixel of movement.

Optimistic reordering & position encoding

Don't store cards in an array where reordering means rewriting every card's index. Assign each card a sortable rank — fractional indexing: a string that sorts lexicographically and lets you insert between any two existing ranks without renumbering (e.g. "a0", "a1" → insert "a0m" between them). A drop event computes a new rank between its new neighbors, updates local optimistic state immediately, and sends only that one card's new rank to the server.

Real-time multi-user sync

Broadcast card moves over WebSocket to other viewers of the same board; apply incoming remote moves through the same reducer path as local ones so the two can't drift apart. Two users dragging the same card at once is rare but possible — resolve with last-write-wins on rank plus a periodic full-column resync to correct drift, rather than building true operational transform for a Kanban board, which is over-engineering for the actual risk.

Resilience & accessibility

On a failed persist, roll back the optimistic move and surface a toast rather than silently reverting after the user has moved on. Keyboard-operable reordering (grab/move/drop via keys, per the DnD library's accessible mode) is not optional — mouse-only drag-and-drop excludes keyboard and screen-reader users entirely, and it's one of the first things a good interviewer probes on this case study.

Code Example

function rankBetween(a, b) {
  // fractional indexing: produce a key that sorts lexicographically between a and b
  return midpointKey(a ?? MIN_KEY, b ?? MAX_KEY);
}

function onDrop(cardId, beforeCard, afterCard) {
  const newRank = rankBetween(beforeCard?.rank, afterCard?.rank);
  moveCardOptimistic(cardId, newRank);          // instant local update
  api.updateCardRank(cardId, newRank).catch(() =>
    rollbackCardMove(cardId)                    // revert + toast on failure
  );
  socket.emit('card:move', { cardId, rank: newRank });
}

Senior Engineer Perspective

The rank-based positioning trick (vs. reindexing an array) is the concrete detail that shows real experience — it's the difference between an O(1) move and rewriting every card's index and broadcasting it all, which falls over with many concurrent users. Equally, volunteering keyboard-accessible reordering unprompted — not just mouse drag — is exactly the first-class-a11y signal senior interviewers listen for on this specific case study.

Q18. Case study: design a notification system (in-app + push).

ROI: ★★★★☆ Frequency: Medium-High

Short Answer

Deliver notifications over a real-time channel for in-app and Web Push for out-of-app, maintain one source of truth for read/unread state that survives across tabs and devices, deduplicate by notification id at both the transport and rendering layer, and derive badge counts from that shared state rather than incrementing a counter per event.

Detailed Answer

Delivery & channels

In-app real-time delivery uses a persistent connection (WebSocket, or SSE if server→client is enough) so a new notification appears without polling; push notifications (Web Push API + service worker, backed by FCM/APNs) cover the case where the tab/app isn't open. These are two delivery mechanisms for the same logical event — a well-designed system fans one event out to both without duplicating business logic across them.

State model: read/unread & cross-tab sync

Treat notification state as server state — fetched, cached, and authoritative — not local UI state; an unread count computed purely from locally-seen events will drift the moment a second tab or device marks something read. Use a shared cache (BroadcastChannel, or shared query-cache invalidation across tabs) so marking-as-read in one tab updates the badge everywhere immediately, and reconcile with the server on reconnect/focus to correct any drift.

Deduplication

The same notification can arrive twice — once via real-time delivery, once via a poll/reconnect-replay fallback — so every notification carries a stable server-issued id and the client upserts by id rather than appending. Apply the same dedup logic whether it's rendered in a dropdown or contributes to the badge count.

Badge counts & grouping

Compute the badge as a derived value — count of unread in the authoritative cache — never as a counter mutated by individual events; a derived value self-corrects after a resync, an incrementing counter accumulates drift forever. For high-volume sources ("12 people liked your post"), group related notifications server-side into one aggregated item instead of flooding the feed with 12 entries.

Code Example

const bc = new BroadcastChannel('notifications');

function upsertNotification(n) {
  store.set(n.id, n);              // upsert by id -> naturally de-dupes
  bc.postMessage({ type: 'sync', unreadCount: computeUnread(store) });
}
bc.onmessage = (e) => { if (e.data.type === 'sync') setBadge(e.data.unreadCount); };

socket.on('notification', upsertNotification);
socket.on('reconnect', () =>
  fetchSince(lastSeenId).then((list) => list.forEach(upsertNotification))
);

Senior Engineer Perspective

Cross-tab consistency is the part most candidates miss entirely — badge count and read state have to be shared client state, not per-tab local state, or reading a notification in one tab won't clear it in another. Also strong: deriving the badge count from the deduplicated unread set instead of incrementing/decrementing a counter — the derived approach self-heals after any missed event, the incremented one just drifts.

Q19. Case study: design a large sortable/filterable data table for 100k+ rows.

ROI: ★★★★★ Frequency: High

Short Answer

Push filtering, sorting, and pagination to the server once the dataset exceeds what's reasonable to ship client-side, virtualize whatever page of rows renders, keep per-column state (sort, filter, width, visibility) in the URL so views are shareable/bookmarkable, and isolate row/cell re-renders so toggling one row's selection doesn't re-render the whole table.

Detailed Answer

Server-side vs client-side operations

At 100k+ rows you cannot ship the full dataset to the client — sorting/filtering/pagination must happen server-side, with the client sending the current sort/filter/page as query params and rendering only the returned page. Below some threshold (a few thousand rows already fetched), client-side sort/filter over the in-memory set is fine and feels more responsive. The design decision is picking that threshold deliberately, not defaulting to one approach everywhere.

Virtualization of rendered rows

Even a single "page" of a few hundred rows benefits from row virtualization so the DOM only holds visible rows — pair a headless table library (for sort/filter/column state logic) with a row virtualizer, rather than a table that renders every row's DOM node.

Column-level state & shareability

Sort column/direction, active filters, column visibility/order, and page number are all state a user expects to survive a refresh and be shareable via URL — encode them into search params rather than only in-memory component state, so a bookmarked/shared link reproduces the exact view.

Render isolation

Row selection, inline-edit, and hover state shouldn't force a re-render of the entire table — scope that state per row (a Set of selected ids checked per row) and memoize row components so toggling one checkbox doesn't recompute every rendered row's cells.

Interaction & resilience

Debounce filter-input-driven server requests; keep showing stale data with a subtle loading indicator on sort/filter changes rather than blanking the table; handle empty-filtered-result and error states explicitly; and guard against the same race-condition risk as the typeahead case study — a slow filter request must not overwrite a newer one's results.

Code Example

const [params, setParams] = useSearchParams();
const sort = params.get('sort') ?? 'createdAt:desc';
const page = Number(params.get('page') ?? 1);
const filters = parseFilters(params.get('filters'));

const { data, isFetching } = useQuery({
  queryKey: ['rows', sort, page, filters],
  queryFn: () => fetchRows({ sort, page, filters }),
  placeholderData: (prev) => prev, // keep stale rows visible while refetching
});
// Rendered rows are windowed by a row virtualizer regardless of page size.

Senior Engineer Perspective

Drawing the server-side/client-side line deliberately — and explaining what tips it, 100k rows vs 2k rows change the answer — separates a thought-out design from a reflexive "always virtualize, always paginate server-side." Also strong: recognizing this shares the exact race-condition risk from the typeahead case study, and that encoding table state in the URL is what makes a filtered/sorted view shareable, a frequently-missed requirement in real data-table products.

Q20. Case study: design a multi-step checkout / payment flow.

ROI: ★★★★★ Frequency: High

Short Answer

Persist form state across steps so back/forward and refresh don't lose progress, validate progressively rather than only at final submit, make the final submission idempotent via a client-generated idempotency key so a retried or double-clicked submit can't double-charge, and treat any redirect to/from a third-party payment provider as an interruption the client must resume from, not a normal in-app navigation.

Detailed Answer

Multi-step form state

Model the flow as one source-of-truth form state, not one local state per step, so navigating back to step 1 doesn't discard step 2's inputs; persist it to sessionStorage/URL so a mid-checkout refresh doesn't lose progress. Validate each step's fields as the user completes it, but keep a final holistic validation pass before submission, since cross-step invariants (billing address required only for certain payment methods) can't always be checked step-locally.

Idempotent submission

Generate a client-side idempotency key when the user starts the payment step and send it with the charge request; the backend uses that key to guarantee a retried request — a double-click on a slow connection, a client retry after a timed-out response whose charge actually succeeded server-side — is a no-op rather than a second charge. This is the single most important correctness property of a payment flow, worth naming explicitly and early.

Third-party redirects & webhooks

Many payment providers (3D Secure, bank redirects) take the user off-site and back — persist enough state (the pending order id) before the redirect to resume correctly on return, and never assume the redirect-return query params are the final word on payment status. The provider's webhook to your backend is the authoritative source, since the user could close the tab mid-redirect or the return could be spoofed/delayed. Show a "confirming payment" state and poll/subscribe for authoritative order status after returning, rather than declaring success from client-side params alone.

Resilience & error states

Distinguish retryable failures (network blip, provider timeout — offer retry) from terminal ones (card declined — the user must change details) in both copy and recovery path; disable the submit button and show a clear pending state during the request as a UI-level guard alongside the idempotency key, since UI disabling alone isn't sufficient — a fast second tap or a client retry bypasses it.

Accessibility & trust

A checkout flow is high-stakes and often used under stress — clear step indicators, inline errors tied to their field, and never silently clearing entered payment details on an error.

Code Example

const idempotencyKey = useMemo(() => crypto.randomUUID(), []); // once per checkout attempt

async function submitPayment(details) {
  setStatus('pending');
  const res = await api.charge(details, { idempotencyKey });
  if (res.requiresRedirect) {
    sessionStorage.setItem('pendingOrderId', res.orderId); // survive the redirect
    window.location.href = res.redirectUrl;
    return;
  }
  await pollOrderStatus(res.orderId); // authoritative status, not local state
}

// On return from the provider redirect:
const pendingId = sessionStorage.getItem('pendingOrderId');
if (pendingId) await pollOrderStatus(pendingId); // never trust query params alone

Senior Engineer Perspective

The idempotency key is the detail that signals real payments experience — without it, "what happens if the user double-clicks pay or the network times out after the charge actually succeeded" has no good answer. Equally important: treating redirect-return query params as advisory rather than authoritative, and waiting for the backend's confirmed order status before declaring success, is exactly the trust-boundary reasoning senior interviewers probe for on payment flows.

Q21. Case study: design a live-updating analytics dashboard with many widgets.

ROI: ★★★★☆ Frequency: Medium-High

Short Answer

Treat each widget's data as an independently-cached query keyed by its exact parameters, deduplicate/share requests across widgets that need the same underlying data instead of each fetching independently, poll or subscribe at an interval appropriate to how "live" each metric actually needs to be, and persist per-user layout/widget configuration separately from the data itself.

Detailed Answer

Data refresh strategy per widget

Not every widget needs the same freshness — a "requests per second" tile might poll every few seconds while a "monthly active users" tile is fine refreshing every few minutes. Let each widget declare its own refresh interval rather than refreshing the whole dashboard in lockstep, which wastes bandwidth on widgets that don't need it and under-refreshes the ones that do.

Avoiding redundant requests across widgets

Multiple widgets often derive from overlapping underlying data (a "total sales" tile and a "sales by region" chart both need the same date-ranged sales query) — route requests through a shared query cache keyed by the actual parameters (metric, date range, filters) so two widgets requesting the same data in the same render dedupe into one request, and a widget added later that happens to need the same slice gets a cache hit for free instead of a bespoke new endpoint.

Rendering performance with many widgets

A dashboard with 20+ independently-refreshing widgets needs each one isolated — its own component subscribing to its own query — so one widget's refresh doesn't re-render its neighbors; for expensive chart rendering, consider deferring/virtualizing widgets that are below the fold or on an inactive tab, and debounce layout-driven re-renders (resizing/dragging a widget) separately from data-driven ones.

Layout persistence & configuration

Widget positions/sizes (often via a grid layout library) and per-widget configuration (which metric, date range, filters) are user-preference state — persist per-user/per-dashboard to the backend so a customized layout survives across sessions and devices, kept as a concern distinct from the live data those widgets render.

Resilience

One widget's data source failing (a flaky downstream metrics service) shouldn't blank the whole dashboard — isolate errors per widget via per-query error states or per-widget error boundaries, and back off polling for a widget that's repeatedly failing rather than hammering a downstream service that's already struggling.

Code Example

// Two widgets requesting overlapping data dedupe via the same query key
function useMetric(metric, range, filters) {
  return useQuery({
    queryKey: ['metric', metric, range, filters],
    queryFn: () => fetchMetric(metric, range, filters),
    refetchInterval: metric.isLive ? 5000 : 120000, // per-widget cadence
  });
}
// TotalSalesTile and SalesByRegionChart both call useMetric('sales', range, {})
// -> one request serves both, and both share the same refresh timer.

Senior Engineer Perspective

The detail that shows real dashboard-building experience is the shared-query-cache-across-widgets point — teams that skip it end up with N widgets independently hammering the same endpoint with the same parameters, then "solve" it with ad hoc bespoke aggregation endpoints instead of just deduplicating at the data layer. Equally, per-widget error isolation and per-widget refresh cadence — not a single dashboard-wide poll — are what distinguish a dashboard architecture that scales to dozens of widgets from one that visibly falls over.
