SECTION 1 - ROUTING BASICS

Q1. How does client-side routing differ from server-side routing in a single-page app?

ROI: ★★★★★ Frequency: Extremely High

Short Answer

With server-side routing, every URL change triggers a full HTTP request and the server returns a brand-new HTML document. With client-side routing, JavaScript intercepts navigation, updates the URL via the History API (pushState), and swaps the rendered component tree without a full page reload. React Router is a client-side router: one HTML shell is loaded once, then routing happens in the browser.

Detailed Answer

A traditional multi-page app maps each URL to a document on the server. Clicking a link means: request → server renders HTML → browser tears down the current page and paints a new one. State is lost between navigations, and the network round-trip is visible as a flash/reload.

A single-page app loads one shell document plus a JS bundle. React Router registers a listener on the History API and on link clicks. When you navigate, it:

  • Prevents the browser's default full-page navigation.
  • Calls history.pushState to change the URL bar without a request.
  • Matches the new URL against your route config and renders the matching component.

The popstate event lets the router respond to the browser's Back/Forward buttons so navigation still feels native. This gives instant transitions and preserves in-memory state (e.g. a form, a cart), at the cost of a larger initial JS payload and the need for SEO/first-paint strategies like SSR.

A strong answer also notes the trade-offs client routing forces: SEO and first-contentful-paint suffer because the initial HTML is empty, which is exactly why frameworks like Next.js and Remix add SSR/streaming on top of a router. Mention that pushState vs replaceState controls whether an entry is added to the history stack — relevant for redirects.

Q2. How do you set up React Router v6+ — Routes/Route vs createBrowserRouter?

ROI: ★★★★★ Frequency: Extremely High

Short Answer

There are two idioms. The classic JSX approach wraps the app in <BrowserRouter> and declares <Routes> with nested <Route> elements. The newer data router (v6.4+) uses createBrowserRouter with a route-object array and a <RouterProvider>, which unlocks loaders, actions, and errorElement. New apps should prefer the data router.

Detailed Answer

Both describe the same route tree; the difference is what capabilities you get. <Routes>/<Route> is purely declarative rendering. The data router lets React Router own data fetching and mutations before a component renders, which is why loaders/actions only exist there.

Feature<BrowserRouter> + <Routes>createBrowserRouter
Loaders / actionsNoYes
errorElement + useRouteErrorNoYes
Route config shapeJSX elementsPlain objects (or JSX via helper)
Best forSimple/legacy appsNew apps, data-driven routing

Code Example

// --- Classic JSX approach ---
import { BrowserRouter, Routes, Route } from "react-router-dom";

function App() {
  return (
    <BrowserRouter>
      <Routes>
        <Route path="/" element={<Home />} />
        <Route path="/users/:id" element={<UserPage />} />
      </Routes>
    </BrowserRouter>
  );
}

// --- Data router (v6.4+, recommended) ---
import { createBrowserRouter, RouterProvider } from "react-router-dom";

const router = createBrowserRouter([
  { path: "/", element: <Home /> },
  {
    path: "/users/:id",
    element: <UserPage />,
    loader: async ({ params }) => fetchUser(params.id),
    errorElement: <RouteError />,
  },
]);

export default function App() {
  return <RouterProvider router={router} />;
}

Project Example

Migrating an admin panel from <Routes> to createBrowserRouter let us move per-page fetches into loaders, so the page component received ready data via useLoaderData and we deleted a pile of in-component useEffect + loading-flag boilerplate.

Senior Engineer Perspective

Interviewers probe whether you know why the data router exists, not just that it does. Key line: loaders/actions/errorElement are only available under createBrowserRouter/RouterProvider because the router needs to control the render lifecycle to fetch before rendering and to catch thrown responses. Note also that React Router 7 merges Remix, so the data router idiom is the future direction — a good detail to drop.

Q3. How do route params work, and how do you read them with useParams?

ROI: ★★★★★ Frequency: Extremely High

Short Answer

A colon segment in a path (/users/:id) is a dynamic param. React Router matches any value in that position and exposes it via the useParams() hook as a string keyed by the param name. Params are always strings, so coerce numbers yourself.

Detailed Answer

You can have multiple params (/org/:orgId/users/:userId) and optional params in v6.4+ using a trailing ? (/files/:name?). A * segment is a "splat"/catch-all that captures the rest of the path, useful for nested file-tree style routes and 404s.

Because every param is a string, validate and convert. A common defect is passing a string id where an API or numeric comparison expects a number.

Code Example

import { useParams } from "react-router-dom";

// Route: <Route path="/users/:id" element={<UserPage />} />
function UserPage() {
  const { id } = useParams();          // id: string | undefined
  const userId = Number(id);
  if (Number.isNaN(userId)) return <NotFound />;
  // ...fetch by userId
}

// TypeScript: type the params
const { orgId, userId } = useParams<{ orgId: string; userId: string }>();

// Splat / catch-all
// <Route path="/docs/*" element={<Docs />} />
// useParams()["*"] holds the remaining path segment

Senior Engineer Perspective

The trap here is the "params are strings" gotcha and forgetting that useParams returns string | undefined in TypeScript even when the route guarantees the param — because the type can't know which route rendered the component. Seniors validate/parse and handle the malformed-id case rather than trusting the URL. Mention that changing only the param (e.g. /users/1 → /users/2) reuses the same component instance, so data-fetching effects must key on the param or you'll show stale data.

SECTION 2 - DYNAMIC & NESTED ROUTES

Q4. What are nested routes and how does Outlet render child routes?

ROI: ★★★★★ Frequency: Extremely High

Short Answer

Nested routes let a parent route render shared UI while a child route fills a placeholder. The parent component renders <Outlet />, and React Router substitutes the matched child route's element there. This composes URLs and UI together: /dashboard renders the dashboard layout, /dashboard/settings renders that layout with the settings panel in the outlet.

Detailed Answer

Outlet is the nested-routing equivalent of children. The parent stays mounted across child navigations, so shared state (open sidebar, tab selection) persists. Child paths are relative — a child path="settings" under path="/dashboard" resolves to /dashboard/settings. Deeply nested trees can chain outlets at each level.

Code Example

import { Outlet } from "react-router-dom";

function DashboardLayout() {
  return (
    <div className="dashboard">
      <Sidebar />
      <main>
        <Outlet />   {/* child route renders here */}
      </main>
    </div>
  );
}

const router = createBrowserRouter([
  {
    path: "/dashboard",
    element: <DashboardLayout />,
    children: [
      { index: true, element: <Overview /> },       // /dashboard
      { path: "settings", element: <Settings /> },   // /dashboard/settings
      { path: "users/:id", element: <UserDetail /> }, // /dashboard/users/42
    ],
  },
]);

Project Example

A settings area with a persistent left-nav (Profile / Billing / Security) is a textbook nested-route case: one SettingsLayout with an <Outlet />, and each tab is a child route. The nav highlight and scroll position of the layout survive tab switches.

Senior Engineer Perspective

A frequent mistake is forgetting the <Outlet /> — the child route matches but nothing renders. Another is using absolute paths for children (leading slash), which breaks the nesting. Seniors emphasise that the parent persisting across child navigations is the whole point: it's how you avoid re-mounting expensive layout shells and losing state.

Q5. What is an index route and when do you need one?

ROI: ★★★★ Frequency: High

Short Answer

An index route is the default child rendered into a parent's <Outlet /> when the URL matches the parent exactly with no further segment. You declare it with index: true (or <Route index />) instead of a path. It answers "what shows at /dashboard itself?"

Detailed Answer

Without an index route, visiting the parent path renders the layout with an empty outlet. The index route fills that gap. It has no path of its own — it shares the parent's URL. You cannot give an index route a path; that's a common syntax error.

Code Example

<Route path="/dashboard" element={<DashboardLayout />}>
  <Route index element={<Overview />} />        {/* /dashboard */}
  <Route path="reports" element={<Reports />} /> {/* /dashboard/reports */}
</Route>

Senior Engineer Perspective

Interviewers use this to check you understand outlet defaults. Contrast the index route with a redirect: some teams redirect /dashboard → /dashboard/overview using <Navigate> instead of an index route. Both work; the index route keeps the canonical URL clean, while the redirect makes the landing tab explicit in the URL.

SECTION 3 - NAVIGATION

Q6. What is the difference between Link, NavLink, and useNavigate?

ROI: ★★★★★ Frequency: Extremely High

Short Answer

Link renders an accessible anchor that does client-side navigation on click. NavLink is a Link that knows whether it points to the active route, so you can style the current nav item. useNavigate returns an imperative function to navigate from code (after a submit, on a timer, in an effect).

Detailed Answer

Prefer Link/NavLink for anything a user clicks: they render a real <a href>, so middle-click/open-in-new-tab, right-click, and screen readers all work. useNavigate is for programmatic transitions where there's no natural anchor. Never fake navigation with an onClick on a div — you lose accessibility and SEO.

NavLink exposes an isActive (and isPending in the data router) flag through a render-prop-style className/style function.

Code Example

import { Link, NavLink, useNavigate } from "react-router-dom";

// Simple link
<Link to="/users/42">View user</Link>

// Active-aware nav item
<NavLink
  to="/reports"
  className={({ isActive }) => (isActive ? "tab tab--active" : "tab")}
>
  Reports
</NavLink>

// Programmatic navigation after an action
function LoginForm() {
  const navigate = useNavigate();
  async function onSubmit(data) {
    await login(data);
    navigate("/dashboard", { replace: true }); // no back-to-login
  }
}

Senior Engineer Perspective

The accessibility point separates seniors: Link renders a semantic anchor, so don't reinvent it with click handlers. Follow-up traps: navigate(-1) for back, and the { replace: true } option to avoid trapping users in a back-button loop after redirects (e.g. after login or a successful form submit). Mention that NavLink matches by prefix for nested paths unless you pass end, a classic "why is my Home tab always active?" bug.

Q7. How do you perform programmatic navigation and redirects?

ROI: ★★★★ Frequency: High

Short Answer

In components, call the function from useNavigate(): navigate("/path"), navigate(-1) to go back, or navigate(to, { replace: true, state }). Declaratively you render <Navigate to="/login" replace />. In loaders/actions you throw or return redirect("/login"), which is the correct place for auth redirects in the data router.

Detailed Answer

  • useNavigate — imperative, for event handlers and effects.
  • <Navigate> — declarative, render it conditionally to redirect during render.
  • redirect() — for loaders/actions; returns a Response the router honours before rendering.

Use replace to overwrite the current history entry instead of pushing a new one — essential so the Back button doesn't return the user to a page they were redirected away from. You can pass state to carry data (e.g. the originally requested URL) without exposing it in the URL.

Code Example

// Declarative redirect during render
if (!user) return <Navigate to="/login" replace />;

// Imperative, carrying "where they wanted to go"
const navigate = useNavigate();
const location = useLocation();
navigate("/login", { replace: true, state: { from: location.pathname } });

// In a data-router loader/action (preferred for auth):
import { redirect } from "react-router-dom";
export async function loader() {
  const user = await getUser();
  if (!user) throw redirect("/login");
  return user;
}

Senior Engineer Perspective

The nuance interviewers hunt for: don't call navigate() directly in the render body — it must run in an effect or event handler, or you'll get warnings and re-render loops; for render-time redirects use <Navigate>. And in the data router, redirecting inside a loader beats redirecting inside the component because it happens before any render, avoiding a flash of protected content.

Q8. How do you read and update query params with useSearchParams?

ROI: ★★★★ Frequency: High

Short Answer

useSearchParams() returns a [searchParams, setSearchParams] pair, analogous to useState but backed by the URL. searchParams is a read-only URLSearchParams object; setSearchParams updates the query string (and thus navigates). It's the right tool for filters, pagination, sort order, and tabs you want shareable and bookmarkable.

Detailed Answer

Because state lives in the URL, it survives refresh, is shareable, and participates in the back/forward history. Read with searchParams.get("q") (returns string | null). Write by passing an object or a URLSearchParams; pass { replace: true } for high-frequency updates (like a search-as-you-type box) so you don't flood the history stack.

Code Example

import { useSearchParams } from "react-router-dom";

function ProductList() {
  const [searchParams, setSearchParams] = useSearchParams();
  const page = Number(searchParams.get("page") ?? "1");
  const q = searchParams.get("q") ?? "";

  function onSearch(text) {
    // functional update preserves other params
    setSearchParams(prev => {
      prev.set("q", text);
      prev.set("page", "1");
      return prev;
    }, { replace: true });
  }

  return <input value={q} onChange={e => onSearch(e.target.value)} />;
}

Senior Engineer Perspective

Interviewers probe whether you keep filter state in the URL rather than local useState — URL state is the "single source of truth" that makes links shareable and back-button correct. Traps: values are always strings (coerce), and blindly replacing the whole search string wipes unrelated params — use the functional updater or spread existing entries. For rapid updates, debounce and use replace to keep history clean.

Q9. What does useLocation give you and when do you need it?

ROI: ★★★ Frequency: Medium

Short Answer

useLocation() returns the current location object: pathname, search, hash, state, and a unique key. It's how you react to URL changes (analytics page-views), read navigation state, or remember where a user came from before a redirect.

Detailed Answer

Common uses: firing a page-view analytics event in an effect keyed on location.pathname; reading location.state?.from to send a user back after login; and driving scroll restoration. The key is a stable id per history entry, handy for animations and per-page scroll memory.

Code Example

import { useLocation } from "react-router-dom";
import { useEffect } from "react";

function usePageViews() {
  const location = useLocation();
  useEffect(() => {
    analytics.track("page_view", { path: location.pathname + location.search });
  }, [location.pathname, location.search]);
}

// After login, return the user to where they were
const location = useLocation();
const from = location.state?.from ?? "/dashboard";
navigate(from, { replace: true });

Senior Engineer Perspective

The subtlety: depend on location.pathname/search, not the whole location object, when you only care about the URL — otherwise a new key on identical URLs can retrigger effects. Seniors also know location.state is ephemeral (it lives in the history entry, not the URL) so it survives back/forward but is gone on a fresh load — don't rely on it for anything critical.

SECTION 4 - DATA & GUARDS

Q10. How do you build a protected/guarded route with an auth redirect?

ROI: ★★★★★ Frequency: Extremely High

Short Answer

Two patterns. In the classic router, wrap protected routes in a guard component that checks auth and either renders <Outlet /> or <Navigate to="/login" />. In the data router, do the check in a loader and throw redirect("/login") — this runs before render, avoiding a flash of protected content.

Detailed Answer

The guard-component pattern uses a layout route: the guard is the parent element and all protected pages are its children, so one check covers the whole subtree. Capture the requested URL in location so you can return the user there after login.

Remember client-side guards are a UX convenience, not security — the API must authorize every request independently. A savvy user can bypass client routing.

Code Example

// --- Guard component (classic) ---
function RequireAuth() {
  const { user } = useAuth();
  const location = useLocation();
  if (!user) {
    return <Navigate to="/login" replace state={{ from: location }} />;
  }
  return <Outlet />;
}

<Route element={<RequireAuth />}>
  <Route path="/dashboard" element={<Dashboard />} />
  <Route path="/settings" element={<Settings />} />
</Route>

// --- Loader guard (data router, preferred) ---
async function protectedLoader({ request }) {
  const user = await getUser();
  if (!user) {
    const url = new URL(request.url);
    throw redirect("/login?next=" + encodeURIComponent(url.pathname));
  }
  return user;
}

Senior Engineer Perspective

The line that lands: "client-side route guards are UX, not security — the server must still authorize." Follow-ups probe the flash-of-content problem (loader redirect solves it because it runs before render) and the redirect-back-after-login flow (store the intended URL in state or a ?next= param). Also mention handling the loading state while auth is being determined, so you don't bounce the user to /login before the session resolves.

Q11. What are loaders and actions in the v6.4+ data router?

ROI: ★★★★ Frequency: High

Short Answer

A loader is a per-route async function that fetches data before the route renders; the component reads it with useLoaderData(). An action handles mutations (form submits) for that route and is invoked by <Form>/useSubmit. Together they move data fetching and mutation out of components and into the route layer, eliminating fetch-on-render waterfalls.

Detailed Answer

Because loaders run in parallel as soon as a navigation starts (not after a component mounts), you avoid the classic useEffect fetch waterfall and its loading-flag/race-condition boilerplate. React Router revalidates loaders automatically after an action succeeds, keeping the UI in sync with mutations. useNavigation() exposes the pending state for global spinners/optimistic UI.

Code Example

import { useLoaderData, Form, redirect } from "react-router-dom";

const router = createBrowserRouter([
  {
    path: "/users/:id",
    element: <UserPage />,
    loader: async ({ params }) => {
      const res = await fetch("/api/users/" + params.id);
      if (!res.ok) throw new Response("Not Found", { status: 404 });
      return res.json();
    },
    action: async ({ request, params }) => {
      const form = await request.formData();
      await updateUser(params.id, Object.fromEntries(form));
      return redirect("/users/" + params.id); // triggers revalidation
    },
  },
]);

function UserPage() {
  const user = useLoaderData();      // data is already here — no loading flag
  return (
    <Form method="post">
      <input name="name" defaultValue={user.name} />
      <button>Save</button>
    </Form>
  );
}

Senior Engineer Perspective

Interviewers want the "why": loaders kick off fetching at navigation time, so parallel routes load together and you avoid render-triggered waterfalls. Be ready to compare with TanStack Query — loaders are great for route-critical data and integrate with caching libraries (you can call the query client inside a loader). A thrown Response is caught by the nearest errorElement, which is how loaders surface 404s and failures cleanly.

Q12. How do errorElement and useRouteError handle route-level errors?

ROI: ★★★★ Frequency: High

Short Answer

In the data router, if a loader/action throws or a component errors during render, React Router renders the nearest route's errorElement instead of the normal element. Inside it, useRouteError() returns the thrown value. This is a route-scoped error boundary that also handles thrown Response objects (e.g. 404/500).

Detailed Answer

Errors bubble to the closest ancestor route that defines an errorElement, so you can have a granular boundary per section and a catch-all at the root. Use isRouteErrorResponse(error) to distinguish a thrown HTTP-style Response (with status/statusText) from an unexpected JS Error, and render 404 vs generic-crash UI accordingly.

Code Example

import { useRouteError, isRouteErrorResponse } from "react-router-dom";

function RouteError() {
  const error = useRouteError();
  if (isRouteErrorResponse(error)) {
    if (error.status === 404) return <h1>Page not found</h1>;
    return <h1>{error.status} {error.statusText}</h1>;
  }
  return <h1>Something went wrong</h1>;
}

const router = createBrowserRouter([
  {
    path: "/",
    element: <Root />,
    errorElement: <RouteError />,   // catches errors from Root and its children
    children: [/* ... */],
  },
]);

Senior Engineer Perspective

The distinction interviewers want: errorElement replaces manual <ErrorBoundary> plumbing for route-level failures and, crucially, catches loader/action errors — which a regular React error boundary cannot, because they happen outside render. Put a root-level errorElement as a safety net and add finer boundaries where you want to keep the surrounding layout alive. Mention isRouteErrorResponse to branch on HTTP status.

SECTION 5 - ADVANCED

Q13. What are layout routes and how do they reduce duplication?

ROI: ★★★★ Frequency: High

Short Answer

A layout route is a parent route with an element (rendering shared chrome + an <Outlet />) but often no path of its own — a "pathless" route. It groups children under a common layout or guard without adding a URL segment, so you define shared UI once.

Detailed Answer

Pathless layout routes are ideal for: an authenticated shell vs a public shell, a marketing layout vs an app layout, or wrapping a group of routes in one guard. Because the layout route contributes no path segment, /dashboard and /settings can share a layout without becoming /app/dashboard. You can nest multiple layout routes for compound chrome.

Code Example

const router = createBrowserRouter([
  {
    element: <AuthenticatedLayout />,   // pathless: no `path`
    loader: protectedLoader,             // one guard for the whole group
    children: [
      { path: "/dashboard", element: <Dashboard /> },
      { path: "/settings", element: <Settings /> },
    ],
  },
  {
    element: <PublicLayout />,
    children: [
      { path: "/login", element: <Login /> },
      { path: "/about", element: <About /> },
    ],
  },
]);

Senior Engineer Perspective

The insight interviewers reward: a layout route can be pathless, letting you share chrome and guards across sibling URLs without polluting the path. Combined with a loader on the layout route, it's the cleanest way to protect an entire section with one check. Contrast with just importing a Layout component into each page — the route approach keeps the layout mounted across child navigations and centralises the guard.

Q14. How do you lazy-load routes for code splitting?

ROI: ★★★★ Frequency: High

Short Answer

Split each route into its own bundle so the initial download is small. Classically you use React.lazy() + <Suspense> around the routed component. In the data router you use the route's lazy property, which can code-split the element, loader, and action together and doesn't require a Suspense wrapper.

Detailed Answer

Route-based splitting is the highest-impact place to code-split: users only download the JS for pages they visit. With React.lazy, wrap the lazy element in <Suspense fallback>. With the data-router lazy option, the module exports the route pieces and React Router loads them on demand while showing pending UI via useNavigation. Pair with Await/defer for streaming slow data.

Code Example

// --- React.lazy + Suspense ---
import { lazy, Suspense } from "react";
const Reports = lazy(() => import("./Reports"));

<Route
  path="/reports"
  element={
    <Suspense fallback={<Spinner />}>
      <Reports />
    </Suspense>
  }
/>

// --- Data-router lazy (splits element + loader together) ---
{
  path: "/reports",
  lazy: async () => {
    const { Reports, reportsLoader } = await import("./reports");
    return { element: <Reports />, loader: reportsLoader };
  },
}

Senior Engineer Perspective

Interviewers check that you split at the route boundary (best cost/benefit) and that you handle the loading fallback. Advanced follow-ups: prefetch the next likely bundle on link hover/focus to hide the network cost, and be careful not to over-split (too many tiny chunks add request overhead). Note the data-router lazy is superior for routes because it also splits the loader/action, not just the component.

Q15. How do you handle scroll restoration and 404s in React Router?

ROI: ★★★★ Frequency: High

Short Answer

SPAs don't reset scroll on navigation the way the browser does for full page loads. Render <ScrollRestoration /> (data router) to restore/reset scroll per navigation. For 404s, add a catch-all route with path="*" that renders your NotFound component; in loaders, throw new Response(..., { status: 404 }) to hit the error UI.

Detailed Answer

ScrollRestoration restores position on back/forward and scrolls to top on new navigations; you can customise with getKey (e.g. key by pathname so filter changes don't reset scroll). Without the data router, a small useEffect-on-pathname that calls window.scrollTo(0,0) is the manual equivalent.

The catch-all path="*" must be the last/lowest-priority match. Use it for a friendly 404 page and analytics on broken links.

Code Example

import { ScrollRestoration } from "react-router-dom";

function Root() {
  return (
    <>
      <Outlet />
      <ScrollRestoration />  {/* render once at the top of the tree */}
    </>
  );
}

// 404 catch-all — keep it last
const router = createBrowserRouter([
  { path: "/", element: <Root />, children: [
    { index: true, element: <Home /> },
    { path: "*", element: <NotFound /> },   // matches anything unmatched
  ]},
]);

// Manual scroll reset without the data router
useEffect(() => { window.scrollTo(0, 0); }, [pathname]);

Senior Engineer Perspective

The gotcha seniors call out: scroll restoration is a real UX gap in SPAs because the browser's native restore doesn't fire without full loads. Know that ScrollRestoration's getKey lets you preserve scroll across param-only changes. For 404s, distinguish "no route matched" (path="*") from "route matched but the resource doesn't exist" (loader throws a 404 Response to the errorElement) — they're different failures with different UX.

Q16. How does React Router compare with Next.js file-based routing?

ROI: ★★★★ Frequency: High

Short Answer

React Router uses an explicit, code-defined route config and is primarily client-side (a library you add to any React app). Q17. What problem do loaders solve that useEffect-based data fetching doesn't?

ROI: ★★★★★ Frequency: Extremely High

Short Answer

A useEffect fetch only starts after the component has mounted, which means: render (with no data) → effect fires → fetch starts → re-render with data. That's a fetch-on-render waterfall, and it's worse across nested routes because each layer's effect waits for its parent to mount first. Loaders start fetching at the moment a navigation is matched, before any component renders, so parallel routes fetch in parallel and the component receives data already resolved via useLoaderData() — no loading flag, no empty first paint.

Detailed Answer

Consider a nested route /orgs/:orgId/projects/:projectId where both the org layout and the project page each need their own fetch. With useEffect, the org layout mounts, its effect fires, and only once it renders children does the project page mount and fire its own effect — a serial waterfall even though the two requests have no dependency on each other. React Router's data router matches the whole route branch up front and calls every matched route's loader concurrently with Promise.all-style parallelism, so both requests go out immediately.

It also collapses a whole category of component state: no more isLoading/error/data triplet duplicated in every page. The router owns that lifecycle and exposes it globally through useNavigation() for pending UI, and per-route through useLoaderData()/errorElement.

Code Example

// Before: fetch-on-render waterfall
function ProjectPage() {
  const { projectId } = useParams();
  const [project, setProject] = useState(null);
  const [loading, setLoading] = useState(true);
  useEffect(() => {
    setLoading(true);
    fetchProject(projectId).then(p => { setProject(p); setLoading(false); });
  }, [projectId]);
  if (loading) return <Spinner />;
  return <ProjectView project={project} />;
}

// After: loader fetches before render, in parallel with sibling/parent loaders
{
  path: "/orgs/:orgId",
  element: <OrgLayout />,
  loader: ({ params }) => fetchOrg(params.orgId),
  children: [
    {
      path: "projects/:projectId",
      element: <ProjectPage />,
      loader: ({ params }) => fetchProject(params.projectId),
    },
  ],
}

function ProjectPage() {
  const project = useLoaderData(); // already resolved
  return <ProjectView project={project} />;
}

Senior Engineer Perspective

Name the waterfall explicitly and quantify it: N nested routes each fetching in useEffect is N sequential round-trips in the worst case, while loaders make it one concurrent batch. Also flag the race-condition tax that disappears: with useEffect fetching keyed on a param, a fast user changing params mid-flight can let a stale response land after a newer one unless you carefully cancel/ignore it; the data router handles this for you by tracking navigation generations and discarding stale loader results.

Q18. How do useLoaderData and useActionData differ, and when does each fire?

ROI: ★★★★★ Frequency: Extremely High

Short Answer

useLoaderData() returns whatever the current route's loader returned, and re-runs on every navigation to (or revalidation of) that route. useActionData() returns whatever the route's action returned from the most recent form submission, and is undefined until a submission has happened — it's how you get validation errors or a success payload back to the component without changing the URL.

Detailed Answer

Think of loaders as GET-shaped (read) and actions as POST/PUT/DELETE-shaped (write). Submitting a <Form> calls the route's action; if the action returns a value (rather than a redirect), that value becomes useActionData() in the component that rendered the form — commonly used to surface field-level validation errors returned from the server without a full navigation. After a successful action, React Router automatically revalidates the route's loaders, so useLoaderData() reflects the mutation without you manually refetching.

Code Example

export async function action({ request }) {
  const formData = await request.formData();
  const errors = validate(formData);
  if (errors) return { errors };           // becomes useActionData()
  await createProject(formData);
  return redirect("/projects");            // no useActionData — we navigated away
}

export async function loader() {
  return listProjects();                    // becomes useLoaderData()
}

function NewProjectForm() {
  const actionData = useActionData();       // undefined until a submit happens
  return (
    <Form method="post">
      <input name="name" />
      {actionData?.errors?.name && <p className="error">{actionData.errors.name}</p>}
      <button>Create</button>
    </Form>
  );
}

Senior Engineer Perspective

Interviewers check that you know useActionData is scoped to the route that owns the <Form> and resets on the next navigation — it's not a general global-state mechanism. A strong point: returning validation errors from an action instead of throwing keeps the form on the page with the user's input intact (a thrown error would go to errorElement and lose the form), so "return, don't throw" for expected validation failures, and "throw" for exceptional/unexpected failures.

Q19. How do you defer slow data with defer() and stream it in with Await?

ROI: ★★★★ Frequency: High

Short Answer

defer() lets a loader return immediately with some data resolved eagerly and other properties as unresolved promises. The route renders right away using the eager data, and each deferred promise is rendered with <Suspense> + <Await>, which shows a fallback until that specific promise settles. This avoids blocking the whole page on the slowest piece of data.

Detailed Answer

Without defer, a loader's returned promise is awaited in full before the route renders — one slow field in the payload delays everything. defer flips that: the navigation completes as soon as the critical data is ready, and slow fields stream in behind independent <Suspense> boundaries. <Await> also exposes the eventual rejection to the nearest error boundary via errorElement, and supports a render-prop-free API where children receive the resolved value directly.

Code Example

import { defer, Await, useLoaderData } from "react-router-dom";
import { Suspense } from "react";

export async function loader({ params }) {
  const criticalData = await fetchProjectHeader(params.id); // awaited: needed for first paint
  const slowStats = fetchProjectStats(params.id);            // NOT awaited: a promise
  return defer({ header: criticalData, stats: slowStats });
}

function ProjectPage() {
  const { header, stats } = useLoaderData();
  return (
    <>
      <ProjectHeader data={header} />
      <Suspense fallback={<StatsSkeleton />}>
        <Await resolve={stats} errorElement={<p>Failed to load stats</p>}>
          {(resolvedStats) => <StatsPanel stats={resolvedStats} />}
        </Await>
      </Suspense>
    </>
  );
}

Senior Engineer Perspective

The pattern to articulate: split loader data into "must have before paint" vs "nice to stream in," and only defer the latter. Follow-ups probe abort handling — if the user navigates away before a deferred promise resolves, React Router cancels it via the loader's request.signal, so your fetch should honor that signal to avoid wasted work and memory leaks. Also mention this is the same streaming SSR idea Suspense enables server-side in frameworks like Next.js/Remix, just applied client-side here.

Q20. How does revalidation work after an action, and how do you opt out of it?

ROI: ★★★★ Frequency: High

Short Answer

After any action completes (without throwing), React Router automatically re-runs the loaders for every currently rendered route, so the UI reflects the mutation — this is "revalidation." You opt a specific route out with shouldRevalidate, which receives the current/next arguments and returns a boolean deciding whether that route's loader should re-run.

Detailed Answer

Automatic revalidation is what makes loaders+actions feel like a self-updating cache without you writing any invalidation code: create a project via an action, and the project list loader re-runs and the UI updates. But it re-runs every loader on the page by default, which can be wasteful for a route whose data never changes based on that mutation (e.g., a static "help" panel loader). shouldRevalidate lets you skip needless refetches, and is also where you'd opt back in to revalidating on param changes if you've disabled it.

Code Example

export async function shouldRevalidate({ currentUrl, nextUrl, formMethod, defaultShouldRevalidate }) {
  // Skip revalidation for GET navigations that only change a query param this route ignores
  if (formMethod == null && currentUrl.pathname === nextUrl.pathname) {
    return false;
  }
  return defaultShouldRevalidate; // fall back to the router's default behavior otherwise
}

export const helpPanelRoute = {
  path: "help",
  element: <HelpPanel />,
  loader: fetchStaticHelpContent,
  shouldRevalidate: () => false, // this content never changes after a mutation elsewhere
};

Senior Engineer Perspective

Interviewers want you to know revalidation is "revalidate everything currently rendered" by default, and that shouldRevalidate is a targeted opt-out, not a general cache invalidation API — there's no fine-grained "invalidate just this key" the way there is in TanStack Query. A senior answer flags that combining loaders with an external cache (e.g. calling queryClient.fetchQuery inside a loader) gives you both: router-driven revalidation timing plus a real cache with tag-based invalidation.

Q21. How do you handle loading/pending UI during navigation with useNavigation?

ROI: ★★★★ Frequency: High

Short Answer

useNavigation() returns the router's global navigation state: state ("idle" | "loading" | "submitting"), location of the pending navigation, and formData if it's a submission. It's how you show a top-level spinner, disable a submit button, or render optimistic UI while a loader/action is in flight, without wiring per-component loading flags.

Detailed Answer

Because navigation state is global and router-owned, one component (often near the root) can render a progress indicator for any in-flight navigation, no matter which route triggered it. state === "submitting" specifically means a form action is running, letting you distinguish "loading a page" from "saving a form" and build optimistic UI (render the assumed end-state immediately, using navigation.formData to read what was submitted before the server confirms it).

Code Example

import { useNavigation } from "react-router-dom";

function RootLayout() {
  const navigation = useNavigation();
  const isLoading = navigation.state === "loading";
  return (
    <>
      {isLoading && <TopProgressBar />}
      <Outlet />
    </>
  );
}

function SaveButton() {
  const navigation = useNavigation();
  const isSaving =
    navigation.state === "submitting" &&
    navigation.formData?.get("intent") === "save";
  return <button disabled={isSaving}>{isSaving ? "Saving..." : "Save"}</button>;
}

Senior Engineer Perspective

A depth signal: mention that navigation.state === "loading" also fires for plain link clicks (not just submissions), so a naive global spinner will flash on every navigation — seniors debounce it (e.g. only show after 200-300ms of pending state) to avoid a flicker on fast responses. Also worth noting: useNavigation reflects the next location during a pending navigation, which is useful for highlighting the nav item the user is heading toward before it finishes loading.

Q22. How do you type loader and action data safely in TypeScript?

ROI: ★★★★ Frequency: High

Short Answer

useLoaderData() and useActionData() are untyped (unknown/any-ish) by default because the router can't statically know which loader produced the data for the component reading it. The common pattern is to export a typed loader function and wrap the hook call with as unknown as ReturnType<typeof loader> resolved, or use a small helper generic that infers the awaited return type of your loader.

Detailed Answer

Because a component and its loader are only connected by a route config object, not by a direct function call, TypeScript has no structural link between them out of the box. The idiomatic fix is a typed helper: infer the loader's resolved return type and cast useLoaderData's result to it. React Router v7 (and its typegen tooling) improves this significantly with generated route types, but the manual pattern below is the v6.4-era baseline every interviewer expects you to know.

Code Example

import { useLoaderData } from "react-router-dom";

async function projectLoader({ params }: LoaderFunctionArgs) {
  const project = await fetchProject(params.projectId!);
  return { project }; // shape is inferred here
}

// Helper to extract and await the loader's return type
type LoaderData<T extends (...args: any) => any> = Awaited<ReturnType<T>>;

function useTypedLoaderData<T extends (...args: any) => any>() {
  return useLoaderData() as LoaderData<T>;
}

function ProjectPage() {
  const { project } = useTypedLoaderData<typeof projectLoader>();
  return <h1>{project.name}</h1>; // fully typed, no `any`
}

Senior Engineer Perspective

Interviewers reward knowing why the types don't flow automatically (loaders and components are connected only through a route config, not a direct import graph) rather than just reciting the cast. Mention the tradeoff: the manual generic helper is a convention your team must apply consistently, whereas React Router 7's route-module typegen closes this gap at the framework level by generating types from the route file structure itself.

Q23. How do you fetch data without navigating, using useFetcher?

ROI: ★★★★ Frequency: High

Short Answer

useFetcher() lets a component call a route's loader or action without changing the URL or triggering a full navigation — perfect for things like a "mark as read" button, an inline edit, or an autocomplete dropdown that needs server data. It returns its own independent state, data, and a Form/load/ submit API scoped to that one fetcher instance.

Detailed Answer

Regular navigations and submissions are inherently URL-changing; useFetcher is the escape hatch for mutations/reads that are logically page-local. Multiple components can each have their own fetcher (e.g. a "like" button per list item), each tracking its own pending state independently, so one item showing a spinner doesn't affect the others. A successful fetcher action still triggers the same automatic revalidation as a normal action, keeping loader data in sync.

Code Example

import { useFetcher } from "react-router-dom";

function LikeButton({ postId, initiallyLiked }) {
  const fetcher = useFetcher();
  // Optimistic: trust the pending submission's intent over server state while in flight
  const liked = fetcher.formData
    ? fetcher.formData.get("liked") === "true"
    : initiallyLiked;

  return (
    <fetcher.Form method="post" action={`/posts/${postId}/like`}>
      <input type="hidden" name="liked" value={String(!liked)} />
      <button type="submit" disabled={fetcher.state !== "idle"}>
        {liked ? "♥ Liked" : "♡ Like"}
      </button>
    </fetcher.Form>
  );
}

Senior Engineer Perspective

The signal interviewers look for: recognizing that a list of 50 "like" buttons each need independent pending state, which a shared useNavigation() cannot provide (it's global) — that's exactly the gap useFetcher fills. Also mention fetcher.load(href) for imperative reads (e.g. populating a combobox on focus) and that fetchers participate in the same revalidation system as top-level actions, so state stays consistent across the whole page.

Q24. What are the tradeoffs of loaders vs a client-side cache library like TanStack Query?

ROI: ★★★★ Frequency: High

Short Answer

Loaders are great at when to fetch (tied to navigation, run in parallel, block or defer render) but weak at caching — by default there's no cross-navigation cache, no stale-while-revalidate, no background refetch-on-focus. TanStack Query is the opposite: a powerful cache with dedup, retries, and background refetching, but no built-in notion of "route navigation." The common senior pattern is to use both together: call the query client inside a loader.

Detailed Answer

Without a cache layer, navigating away from and back to a route re-runs its loader and refetches from scratch every time — no memory of the previous result. TanStack Query's fetchQuery/ensureQueryData called inside a loader gives you the best of both: the router still fetches before render and can defer/parallelize, but the actual network call is deduped and cached by the query client, and components can still use useQuery for background refetching after the initial load.

Code Example

import { QueryClient } from "@tanstack/react-query";
const queryClient = new QueryClient();

const projectQuery = (id) => ({
  queryKey: ["project", id],
  queryFn: () => fetchProject(id),
});

// Loader ensures data is cached before render; component still uses useQuery for the cache
export async function loader({ params }) {
  await queryClient.ensureQueryData(projectQuery(params.id));
  return null;
}

function ProjectPage() {
  const { id } = useParams();
  const { data: project } = useQuery(projectQuery(id)); // reads the warmed cache instantly
  return <h1>{project.name}</h1>;
}

Senior Engineer Perspective

The framing that earns credit: loaders own navigation timing, query libraries own data lifecycle (caching, dedup, invalidation, background sync) — they're complementary, not competing. A plain-loader app is fine for simple CRUD; an app with heavy cross-page data reuse, optimistic mutations, and background sync benefits from layering a query client underneath the loader, rather than reinventing a cache with shouldRevalidate alone.

SECTION 7 - NESTED ROUTES & LAYOUT ROUTES DEEP DIVE

Q25. What's the difference between relative and absolute paths in nested route children?

ROI: ★★★★ Frequency: High

Short Answer

A child route's path without a leading slash is relative — it's appended to the parent's matched path. A path with a leading slash is absolute and ignores nesting entirely, matching from the root. Mixing them up is one of the most common nested-routing bugs: a child intended to be /dashboard/settings written as path="/settings" instead matches only the top-level /settings.

Detailed Answer

React Router v6 deliberately changed this from v5, where every route's path had to be written in full. In v6, nested <Route> children compose their paths from their ancestors, so path="settings" under a parent path="/dashboard" is exactly /dashboard/settings — you never repeat the parent prefix. An absolute child path escapes this composition, which is occasionally intentional (a child route that should match regardless of where it's nested) but far more often a copy-paste mistake.

Code Example

{
  path: "/dashboard",
  element: <DashboardLayout />,
  children: [
    { path: "settings", element: <Settings /> },   // relative: /dashboard/settings (correct)
    { path: "/settings", element: <Settings /> },  // absolute: /settings (bug if unintended!)
  ],
}

Senior Engineer Perspective

Interviewers listen for "v6 made child paths relative by default, unlike v5" — that's the historical context that explains why this trips up engineers migrating an old codebase. Mention that this same relative/absolute distinction carries into Link to="" and navigate() calls, so understanding it here also explains a whole class of "link goes to the wrong place" bugs elsewhere.

Q26. How do relative Link/NavLink "to" values resolve inside deeply nested routes?

ROI: ★★★★ Frequency: High

Short Answer

A relative to value on <Link>/<NavLink> resolves against the route's matched path (not the raw URL), following familiar filesystem-style rules: to="edit" appends a segment, to=".." goes up one routing level, and to="." refers to the current route. Since v6.4+, "up one level" means up one nested route, not necessarily one URL segment — which matters when a route's path itself has multiple segments.

Detailed Answer

This route-relative (rather than URL-relative) resolution is a deliberate v6 change: it means refactoring a route's URL (e.g. renaming a path segment) doesn't break every relative link inside it, because the links resolve against the route tree structure, not string concatenation of the current pathname. You can opt into the older, URL-segment-based relative resolution with the relative="path" prop when you specifically want that behavior.

Code Example

// Route tree: /projects/:id (ProjectLayout) -> "edit" (ProjectEdit)
function ProjectLayout() {
  return (
    <>
      <Link to="edit">Edit</Link>      {/* -> /projects/42/edit */}
      <Outlet />
    </>
  );
}

function ProjectEdit() {
  return (
    <>
      <Link to="..">Back to project</Link>         {/* -> /projects/42 (route-relative) */}
      <Link to=".." relative="path">Back</Link>     {/* -> /projects (path-relative, up one URL segment) */}
    </>
  );
}

Senior Engineer Perspective

This is a favorite "gotcha" question precisely because the route-relative default surprises people coming from plain URL math. A senior answer distinguishes the two resolution modes by name (route default vs path opt-in) and gives a concrete example of when route-relative resolution silently does the "wrong" thing — e.g. a layout route whose path spans two segments makes to=".." jump up more than one visible URL segment.

Q27. How do you share a layout route's loader data with its children via useOutletContext?

ROI: ★★★★ Frequency: High

Short Answer

A layout route renders <Outlet context={value} />, and any descendant route can read that value with useOutletContext() — no prop drilling, no separate React Context provider needed. It's commonly used to hand a parent's already-fetched loader data (e.g. the current org, fetched once by the layout) down to whichever child route is currently rendered.

Detailed Answer

This is distinct from each child route having its own loader: the parent fetches once, and every child reuses that single result without redundant network calls. It's a lighter-weight alternative to standing up a React Context provider purely to pass route-scoped data down — though for data needed outside the route tree (e.g. in a modal rendered via a portal) a real Context is still the right tool.

Code Example

function OrgLayout() {
  const org = useLoaderData();           // fetched once for the whole org subtree
  return (
    <>
      <OrgHeader org={org} />
      <Outlet context={{ org }} />
    </>
  );
}

function ProjectsTab() {
  const { org } = useOutletContext();    // no re-fetch, no prop drilling
  return <ProjectList orgId={org.id} />;
}

Senior Engineer Perspective

Interviewers check that you know the difference between "route-scoped shared data" (outlet context — cheap, tied to the route tree, gone once you leave it) and "app-wide shared data" (React Context/global store — persists independent of routing). Using outlet context for the former avoids an unnecessary global provider, but reaching for it to smuggle data far outside the route tree is a misuse — that's what Context or a store is for.

Q28. How do you render multiple independent sections of a layout that each need their own routed content?

ROI: ★★★ Frequency: Medium

Short Answer

React Router (unlike Next.js App Router) has a single <Outlet /> per matched route branch — there's no built-in "parallel routes" concept for two independently routable panels on the same page. To fake it, teams either drive the second panel from useSearchParams/route state instead of a nested route, or render two separate <Routes> trees (one per independently-controlled region).

Detailed Answer

A common real case: a list page with a detail panel that opens as a route (/inbox/:messageId) while a persistent "compose" modal can also be open, independent of which message is selected. Since one route tree only has one active leaf per branch, the modal's open/closed state is usually modeled as a query param (?compose=1) read by a component sitting alongside the <Outlet />, not as a second nested route matched against the same path.

Code Example

function InboxLayout() {
  const [searchParams] = useSearchParams();
  const composing = searchParams.get("compose") === "1";
  return (
    <div className="inbox">
      <MessageList />
      <Outlet />                          {/* /inbox/:messageId renders here */}
      {composing && <ComposeModal />}     {/* independent of the outlet's route */}
    </div>
  );
}

Senior Engineer Perspective

This question separates people who've only used the basic router from people who've hit its limits in a real product. The honest, senior answer names the gap plainly — "React Router doesn't have first-class parallel routes like Next's App Router" — and explains the workaround (query params or independent UI state) rather than trying to force a nested-route solution where it doesn't fit.

Q29. How do you handle a layout route whose outlet has no matching child route?

ROI: ★★★ Frequency: Medium

Short Answer

If a URL matches a parent layout route but no child route matches the remaining path segment, the <Outlet /> simply renders nothing (unless the parent path itself doesn't fully match, in which case the whole branch 404s). To always show something at the bare parent URL, add an index route; to catch any unmatched sub-path, add a child path="*".

Detailed Answer

These are two different gaps and need two different fixes. Visiting exactly /dashboard with no index route renders the layout with an empty outlet — not an error, just a blank slot. Visiting /dashboard/nonexistent with no catch-all child also renders an empty outlet inside the dashboard chrome, which is usually worse UX than a proper "not found" message, since the user sees a mostly-working page with a blank panel instead of clear feedback.

Code Example

{
  path: "/dashboard",
  element: <DashboardLayout />,
  children: [
    { index: true, element: <Overview /> },              // fixes the bare-URL gap
    { path: "settings", element: <Settings /> },
    { path: "*", element: <SectionNotFound /> },          // fixes the unmatched-subpath gap
  ],
}

Senior Engineer Perspective

The interviewer is testing whether you distinguish "outlet renders nothing" (a silent gap) from "the app crashed" (loud) — many candidates assume an unmatched nested path is automatically an error, when in fact it's just an empty render unless you explicitly guard for it. A thorough answer always pairs an index route with a scoped catch-all inside any layout route that has children.

Q30. What's the difference between an index route and a route with path=""?

ROI: ★★★ Frequency: Medium

Short Answer

They're not interchangeable — path="" on a non-index route is invalid/behaves unpredictably in v6's route object API; index: true is the only correct way to say "render this when the parent's path matches exactly." An index route also cannot have its own children, because by definition there is no further path segment left for a child to match.

Detailed Answer

Conceptually, index isn't a path at all — it's a boolean flag meaning "no further segment." Trying to combine it with a path or children is a config error the router will complain about (or silently ignore) because those concepts are mutually exclusive: index routes are always leaves, always pathless, always scoped to matching the parent exactly.

Code Example

// Correct
{ index: true, element: <Overview /> }

// Invalid combination — index routes cannot declare children
{ index: true, element: <Overview />, children: [ /* ... */ ] } // config error

// Invalid — don't mix path with index
{ index: true, path: "overview", element: <Overview /> } // nonsensical, avoid

Senior Engineer Perspective

This is a quick sanity check interviewers use to see if you've actually configured a route tree yourself versus only read about it. The crisp line: "index is a flag, not a path — it means zero additional segments, so it can't coexist with a path or with children."

Q31. How do you structure deeply nested route trees to avoid duplication and prop-drilling?

ROI: ★★★★ Frequency: High

Short Answer

Push shared concerns (auth checks, org-level data, breadcrumbs, layout chrome) as high as possible in the tree as pathless or path-bearing layout routes, so every descendant inherits them for free instead of re-implementing them per page. Use useOutletContext or a scoped Context provider at the layout level rather than passing data down through many manually-threaded props.

Detailed Answer

A well-factored tree reads almost like an org chart of responsibilities: an outermost pathless route handles global auth, a middle layout route handles "current org" data fetching and chrome, and leaf routes only worry about their own page content. Each layer should own exactly one cross-cutting concern. Anti-pattern: a single giant page component that fetches org, project, and task data all at once and manually passes slices down through five levels of props — that's what nested layout routes with their own loaders exist to eliminate.

Code Example

const router = createBrowserRouter([
  {
    element: <RequireAuth />,               // layer 1: auth, pathless
    children: [
      {
        path: "/orgs/:orgId",
        element: <OrgLayout />,              // layer 2: org data + chrome
        loader: ({ params }) => fetchOrg(params.orgId),
        children: [
          {
            path: "projects/:projectId",
            element: <ProjectLayout />,       // layer 3: project data + tabs
            loader: ({ params }) => fetchProject(params.projectId),
            children: [
              { index: true, element: <ProjectOverview /> },
              { path: "tasks", element: <ProjectTasks /> },
            ],
          },
        ],
      },
    ],
  },
]);

Senior Engineer Perspective

What separates a senior answer here is talking about the route tree as an architectural tool, not just a URL-matching mechanism — each nesting level is a place to attach exactly one concern (auth, org context, project context) so leaf pages stay small and don't re-derive data their ancestors already fetched. Also flag the failure mode of over-nesting: too many layout levels for trivial pages adds indirection without payoff, so match nesting depth to genuinely shared concerns, not just visual indentation.

SECTION 8 - PROTECTED ROUTES & AUTH GUARDS

Q32. How do you implement role-based route guards (admin vs regular user)?

ROI: ★★★★★ Frequency: Extremely High

Short Answer

Extend the basic "is authenticated" guard with a role check: a guard component (or loader) receives the required role(s) as a parameter, compares against the current user's role, and redirects to either a login page (unauthenticated) or a 403/"not authorized" page (authenticated but wrong role) — those are two distinct failure states with two distinct destinations.

Detailed Answer

Treat "not logged in" and "logged in but forbidden" as separate branches, not one generic redirect-to-login — sending an admin-only page's unauthorized regular user to the login screen is confusing since they're already logged in. Parameterize the guard so the same component protects many routes with different role requirements, rather than writing a bespoke guard per role.

Code Example

function RequireRole({ role }: { role: string }) {
  const { user } = useAuth();
  const location = useLocation();

  if (!user) {
    return <Navigate to="/login" replace state={{ from: location }} />;
  }
  if (!user.roles.includes(role)) {
    return <Navigate to="/403" replace />;   // distinct from "not logged in"
  }
  return <Outlet />;
}

<Route element={<RequireRole role="admin" />}>
  <Route path="/admin/users" element={<AdminUsers />} />
  <Route path="/admin/billing" element={<AdminBilling />} />
</Route>

// Data-router loader equivalent
async function requireRoleLoader(role: string) {
  return async () => {
    const user = await getUser();
    if (!user) throw redirect("/login");
    if (!user.roles.includes(role)) throw redirect("/403");
    return user;
  };
}

Senior Engineer Perspective

Interviewers look for the "two failure modes, two destinations" distinction as the sign of real production experience versus tutorial-level auth. Also worth raising: role checks belong on the server for every mutating request regardless of what the client-side guard shows — the guard's job is UX (don't render a page the user can't act on), never the actual authorization boundary.

Q33. How do you handle an async auth check without flashing the wrong UI?

ROI: ★★★★★ Frequency: Extremely High

Short Answer

Model auth status as three states, not two: "loading" | "authenticated" | "unauthenticated". While it's "loading" (e.g. verifying a token on app boot), render a neutral loading state instead of guessing — guessing "unauthenticated" flashes a login redirect that then reverses once the check resolves, and guessing "authenticated" briefly exposes protected content to someone who turns out not to be logged in.

Detailed Answer

The bug this prevents: on a hard refresh of a protected page, your auth context often starts with user: null before an async session check resolves. A two-state guard (if (!user) redirect) treats "not yet known" identically to "definitely not logged in," so it redirects to login and then, once the check finishes and confirms the user IS logged in, has to redirect back — a jarring flash. Explicitly tracking a third "loading" state fixes this: the guard renders a spinner (or nothing) while loading, and only makes the redirect decision once the check has actually settled.

Code Example

function useAuth() {
  const [status, setStatus] = useState<"loading" | "authed" | "guest">("loading");
  const [user, setUser] = useState(null);

  useEffect(() => {
    verifySession().then((u) => {
      setUser(u);
      setStatus(u ? "authed" : "guest");
    });
  }, []);

  return { status, user };
}

function RequireAuth() {
  const { status } = useAuth();
  const location = useLocation();

  if (status === "loading") return <FullPageSpinner />;      // don't guess yet
  if (status === "guest") return <Navigate to="/login" replace state={{ from: location }} />;
  return <Outlet />;
}

Senior Engineer Perspective

The phrase interviewers want to hear is "don't collapse 'unknown' into 'false'" — treating an in-flight auth check as a definite "not authenticated" is the root cause of the classic login-flash bug. In the data router, the equivalent fix is awaiting the session check inside the guarding route's loader so the redirect decision happens before any render at all, which sidesteps the three-state dance entirely.

Q34. How do you redirect back to the originally requested URL after login?

ROI: ★★★★ Frequency: High

Short Answer

When the guard redirects to /login, capture the location the user was trying to reach — either via state={{ from: location }} on <Navigate> or a ?next= query param on the redirect URL. After a successful login, read that stored location and navigate(from, { replace: true }) instead of hardcoding a redirect to a default page like /dashboard.

Detailed Answer

Two viable carriers, with different tradeoffs. History state keeps the intended destination out of the URL (cleaner, but lost if the user bookmarks/shares the login link or opens it in a new tab). A ?next= query param survives sharing and reloads but exposes the destination in the URL and needs validation — never blindly redirect to an arbitrary next value without checking it's a same-origin relative path, or you've built an open-redirect vulnerability.

Code Example

// Guard: capture intended destination
if (!user) {
  return <Navigate to="/login" replace state={{ from: location.pathname + location.search }} />;
}

// Login page: return the user where they were headed
function LoginPage() {
  const navigate = useNavigate();
  const location = useLocation();
  const from = location.state?.from ?? "/dashboard";

  async function onSubmit(credentials) {
    await login(credentials);
    navigate(from, { replace: true });
  }
}

// Query-param variant — validate before trusting it!
function isSafeRedirect(path: string) {
  return path.startsWith("/") && !path.startsWith("//"); // same-origin relative path only
}
const next = new URLSearchParams(location.search).get("next");
navigate(isSafeRedirect(next ?? "") ? next! : "/dashboard", { replace: true });

Senior Engineer Perspective

The security detail that separates senior candidates: if you use a query-param next, you must validate it's a safe, same-origin, relative path before redirecting — otherwise an attacker can craft a login link with ?next=https://evil.example.com and use your trusted login flow to bounce a user to a phishing site (an "open redirect"). state-based carriers avoid this exposure entirely since the value never touches the URL.

Q35. How do you guard nested routes so children inherit a parent's auth check exactly once?

ROI: ★★★★ Frequency: High

Short Answer

Put the guard as a single pathless (or path-bearing) layout route wrapping every protected child, rather than repeating the check inside each page component. The guard runs once per matched branch; every descendant route simply assumes it already passed, keeping individual page components free of auth logic entirely.

Detailed Answer

This is the same "push shared concerns up the tree" principle nested layouts are built for. A guard placed at the top of a subtree protects everything beneath it with zero duplication; adding a new protected page is just adding a new child route under that guard, with no per-page boilerplate. Contrast with guarding inside each page component, which duplicates the check N times and risks someone adding a new page and forgetting the guard.

        ],
      },
    ],
  },

Senior Engineer Perspective

Interviewers are checking for architectural instinct: guard once at the boundary, not per-leaf. Q36. How do you handle token expiry and silent refresh during navigation?

ROI: ★★★★ Frequency: High

Short Answer

Centralize token refresh in one place — typically an HTTP client interceptor or a loader wrapper — that detects a 401, attempts a silent refresh (using a refresh token/cookie), retries the original request once, and only redirects to login if the refresh itself fails. Route guards and loaders should call through this shared client rather than each reimplementing refresh logic.

Detailed Answer

A naive guard that redirects to login on any 401 will boot a user mid-session just because their short-lived access token expired, even though a valid refresh token exists. Centralizing the refresh-and-retry logic in the fetch layer means every loader/action automatically benefits without individually handling expiry, and it also protects against a "thundering herd" of simultaneous refresh calls if multiple loaders 401 at once (dedupe with an in-flight refresh promise).

Code Example

let refreshPromise: Promise<void> | null = null;

async function apiFetch(url: string, init?: RequestInit) {
  let res = await fetch(url, init);
  if (res.status === 401) {
    refreshPromise ??= refreshAccessToken().finally(() => { refreshPromise = null; });
    try {
      await refreshPromise;              // dedupes concurrent refresh attempts
      res = await fetch(url, init);      // retry once with the fresh token
    } catch {
      throw redirect("/login");          // refresh itself failed — truly logged out
    }
  }
  return res;
}

// Loaders just call apiFetch and never think about expiry themselves
export async function projectLoader({ params }) {
  const res = await apiFetch(`/api/projects/${params.id}`);
  return res.json();
}

Senior Engineer Perspective

What earns credit here: naming the "thundering herd" problem — several parallel loaders all hitting 401 at once and each independently trying to refresh — and solving it by deduping concurrent refresh attempts behind a single shared promise. Also worth mentioning: this logic belongs in the fetch/HTTP layer, not scattered across guards, so every caller (loaders, actions, fetchers) gets it uniformly.

Q37. How do you prevent an authenticated user from seeing login/signup routes?

ROI: ★★★ Frequency: Medium

Short Answer

Without this, a logged-in user who navigates back to /login (browser back button, an old bookmark, a stale link) sees a confusing login form while already authenticated, and submitting it again is at best redundant and at worst triggers odd session handling. Q39. What security mistakes do people make trusting client-side route guards?

ROI: ★★★★★ Frequency: Extremely High

Short Answer

The core mistake: treating a client-side guard as the security boundary. It's trivially bypassable — disable JavaScript's routing checks, call the API directly with dev tools, or edit local state — so every protected mutation or sensitive read must be authorized again on the server, independent of whatever the client's route guard decided.

Detailed Answer

Common concrete mistakes: shipping sensitive data in a route's loader response and trusting the guard to have prevented an unauthorized user from reaching it (the network response is visible in dev tools regardless of what renders); storing the "is admin" flag purely in client state with no server-side verification per request; and assuming a hidden/unlinked route is "protected" through obscurity. The fix is always the same: the client guard is a UX layer that avoids rendering UI the user can't use; the server enforces the actual authorization on every request, checking the real session/token, not a client-asserted role.

Code Example

// WRONG mental model: "the guard protects this data"
export async function loader() {
  // If this endpoint doesn't itself check the caller's permissions server-side,
  // the client guard around the route does nothing to stop a direct API call.
  return fetch("/api/admin/all-users").then(r => r.json());
}

// Server-side (the actual boundary) — pseudocode
app.get("/api/admin/all-users", requireRole("admin"), (req, res) => {
  res.json(getAllUsers());
});

Senior Engineer Perspective

This is a favorite "do you actually understand security boundaries" question. The line that lands: "client-side routing decides what renders; the server decides what's allowed — conflating the two means your real security is whatever the API happens to enforce, and the router contributed nothing." A senior candidate volunteers the concrete attack (calling the API directly, bypassing the SPA) unprompted.

SECTION 9 - PROGRAMMATIC NAVIGATION PATTERNS

Q40. When should you use useNavigate vs Link, precisely?

ROI: ★★★★★ Frequency: Extremely High

Short Answer

Use Link/NavLink whenever a user directly clicks something to go somewhere — it renders a real anchor, so keyboard focus, middle-click/new-tab, right-click "copy link," and screen readers all work for free. Use useNavigate only when navigation is a side effect of something else: after a successful form submit, after a timer, after an API call resolves, or inside an effect reacting to state.

Detailed Answer

The dividing line is "is there a natural link a user is clicking?" If yes, it should be an anchor — even a styled button-look-alike should still render as <Link>/<a> under the hood for accessibility and right-click behavior. If navigation happens as a consequence of logic (validation passed, a save completed, a redirect rule fired), there's no anchor to click, so useNavigate's imperative call is correct and there's no accessibility loss because nothing was ever "clickable" in the first place.

Code Example

// Correct: user-initiated, should be a Link
<Link to="/products/42">View product</Link>

// WRONG: reinventing Link with a click handler — loses href, right-click, a11y
<div onClick={() => navigate("/products/42")}>View product</div>

// Correct: navigation as a side-effect of logic, not a direct click target
async function onSubmit(data) {
  const result = await saveOrder(data);
  if (result.ok) navigate(`/orders/${result.id}`, { replace: true });
}

Senior Engineer Perspective

The anti-pattern interviewers want you to call out unprompted: a clickable <div onClick={() => navigate(...)}> styled to look like a link. It breaks middle-click-to-open-in-new-tab, breaks "copy link address," and fails screen readers, all to avoid using the element built for exactly this purpose. If you need custom styling, style the <Link> itself — don't replace its semantics.

Q41. What is the difference between push and replace navigation, and when do you pick each?

ROI: ★★★★★ Frequency: Extremely High

Short Answer

Push (the default) adds a new entry to the history stack, so the Back button returns to the previous page. Replace ({ replace: true }) swaps the current history entry in place — Back skips over it entirely. Use replace for redirects the user shouldn't be able to "undo" into (post-login, post-logout, wizard steps, error redirects) and push for anything the user should be able to back out of.

Detailed Answer

The canonical replace use case: redirecting an unauthenticated user from /dashboard to /login. If that redirect used push, pressing Back from the login page would send the user right back to /dashboard, which the guard immediately bounces again — a broken, looping Back button. Replace fixes it: Back from login goes to wherever the user was before attempting to reach the dashboard, skipping the failed attempt entirely. The same logic applies to a multi-step form wizard's "step complete, move on" transitions — you usually don't want Back to return to a step that's already been submitted.

Code Example

// Redirect-on-guard-failure: use replace so Back doesn't loop
if (!user) return <Navigate to="/login" replace />;

// After successful login: replace so Back doesn't return to the login form
navigate("/dashboard", { replace: true });

// Normal user-initiated navigation: push (default) so Back works naturally
navigate("/products/42"); // equivalent to navigate("/products/42", { replace: false })

// Wizard step completed: replace this step with the next one
navigate("/checkout/payment", { replace: true }); // Back skips the completed shipping step

Senior Engineer Perspective

The strongest way to answer this is with the specific broken-Back-button symptom (login-redirect-loop) as the motivating example, because it's the bug that makes teams discover replace exists in the first place. Also mention: <Navigate replace> and navigate(to, { replace: true }) are the declarative and imperative forms of exactly the same mechanism.

Q42. How do you pass state through navigation without putting it in the URL?

ROI: ★★★★ Frequency: High

Short Answer

Pass a state object as the second argument to navigate(to, { state }) or as a prop on <Link state={...}>. The receiving route reads it with useLocation().state. It's attached to the history entry, not the URL, so it stays invisible to the address bar and to anyone the link is shared with.

Detailed Answer

Good uses: passing a "came from" location for a post-login redirect, passing an already- fetched object from a list view to a detail view so the detail page can render instantly without a redundant fetch (falling back to a fetch if state is absent, e.g. on a direct load/refresh), or flagging "just submitted successfully" so the destination page can show a one-time toast. Because it lives in history state, it survives back/forward navigation within the session but is gone on a hard refresh or a freshly opened tab — never store anything there that the page can't function without.

Code Example

// From a list, hand the already-loaded item forward to avoid a redundant fetch
<Link to={`/products/${product.id}`} state={{ product }}>
  {product.name}
</Link>

function ProductPage() {
  const location = useLocation();
  const { id } = useParams();
  const [product, setProduct] = useState(location.state?.product ?? null);

  useEffect(() => {
    if (!product) {
      fetchProduct(id).then(setProduct); // fallback for direct load / refresh
    }
  }, [id, product]);

  if (!product) return <Spinner />;
  return <ProductDetail product={product} />;
}

Senior Engineer Perspective

The trap interviewers probe: relying on location.state as the only source of data means a hard refresh or a shared link breaks the page, because state doesn't survive those. A senior answer always pairs state-passed data with a fallback fetch keyed on the URL param, treating the passed state purely as an optimization, never as the sole source of truth.

Q43. How do you navigate after a successful form submission without a double-submit bug?

ROI: ★★★★ Frequency: High

Short Answer

Disable the submit control while the request is in flight (tracked via a useState flag, or useNavigation().state === "submitting" in the data router) so a second click can't fire a second request, and navigate away only after the mutation resolves successfully — using replace so the form page isn't left sitting in history for Back to return the user to a stale, already-submitted form.

Detailed Answer

Double submits usually come from either impatient double-clicking or a slow network making a user think the first click didn't register. The data router's <Form> + action pattern handles this well structurally: React Router serializes concurrent submissions to the same action and exposes navigation.state so you disable the button declaratively rather than managing your own flag. For classic (non-data-router) forms, you own the in-flight flag yourself.

Code Example

// Data router: derive "is submitting" from the router itself
function OrderForm() {
  const navigation = useNavigation();
  const submitting = navigation.state === "submitting";
  return (
    <Form method="post">
      {/* fields */}
      <button type="submit" disabled={submitting}>
        {submitting ? "Placing order..." : "Place order"}
      </button>
    </Form>
  );
}

// Classic: own the flag yourself
function OrderForm() {
  const [submitting, setSubmitting] = useState(false);
  const navigate = useNavigate();

  async function onSubmit(e) {
    e.preventDefault();
    if (submitting) return;               // guard against a second click
    setSubmitting(true);
    try {
      const order = await placeOrder(new FormData(e.target));
      navigate(`/orders/${order.id}`, { replace: true }); // no stale form in history
    } finally {
      setSubmitting(false);
    }
  }
}

Senior Engineer Perspective

Two things interviewers listen for: disabling the trigger during the in-flight window (not just after the first click fires) and using replace on the post-submit navigation so a completed form doesn't linger as a Back-button destination. Mention that the data router's action queue already serializes rapid resubmits for you, which is one more reason to prefer it over hand-rolled submit handlers for anything beyond a trivial form.

Q44. How do you build a "confirm before leaving" prompt for unsaved changes?

ROI: ★★★★ Frequency: High

Short Answer

For in-app navigation (clicking a different link/route while a form is dirty), use React Router's useBlocker (data router) to intercept the transition and show your own confirmation UI. For a hard browser close/refresh/external navigation, that's outside the router's control — you need the native beforeunload event, which only supports the browser's generic "leave site?" prompt, not custom UI.

Detailed Answer

These are two genuinely different mechanisms because they intercept two different kinds of navigation. useBlocker only sees router-driven transitions (Link clicks, navigate() calls, Back/Forward within the SPA) — it cannot stop a tab close or an address-bar URL change, which is the browser's job via beforeunload. A complete "unsaved changes" guard wires up both: useBlocker for a nice custom modal on in-app navigation, and beforeunload for the native browser prompt on close/refresh/external nav.

Code Example

import { useBlocker } from "react-router-dom";

function EditForm({ isDirty }) {
  const blocker = useBlocker(isDirty); // blocks in-app router transitions while dirty

  // Native browser prompt for tab close / refresh / address-bar navigation
  useEffect(() => {
    function handler(e) {
      if (isDirty) { e.preventDefault(); e.returnValue = ""; }
    }
    window.addEventListener("beforeunload", handler);
    return () => window.removeEventListener("beforeunload", handler);
  }, [isDirty]);

  return (
    <>
      {blocker.state === "blocked" && (
        <ConfirmModal
          onConfirm={() => blocker.proceed()}
          onCancel={() => blocker.reset()}
        />
      )}
      {/* form fields */}
    </>
  );
}

Senior Engineer Perspective

The distinction interviewers reward: "in-app navigation and leaving the tab entirely are two different browser mechanisms, and you need to hook both separately — the router only owns the first one." Also flag that modern browsers ignore any custom message text passed to beforeunload for security reasons (to prevent phishing via fake dialogs), so you cannot brand or customize that native prompt at all.

Q45. How do you navigate relative to the current route (e.g., "../sibling")?

Q46. How do you handle navigation cancellation when a user navigates away mid-fetch?

ROI: ★★★★ Frequency: High

Short Answer

In the data router, every loader/action receives an AbortSignal via request.signal, which the router automatically aborts if the user navigates away before that loader/action settles. Pass it into your fetch calls so the in-flight request is actually cancelled at the network level, not just ignored in the UI.

Detailed Answer

Without honoring the signal, a fetch keeps running to completion even after the user has navigated to a different route — wasting bandwidth and, worse, risking a stale response being applied to state if you're not careful. Passing signal through to fetch means the browser itself cancels the request, and any .then() after an aborted fetch throws an AbortError you can safely ignore (it's not a real failure, just an abandoned navigation).

Code Example

export async function projectLoader({ params, request }) {
  const res = await fetch(`/api/projects/${params.id}`, {
    signal: request.signal,           // cancelled automatically if the user navigates away
  });
  if (!res.ok) throw new Response("Not found", { status: 404 });
  return res.json();
}

// Manual useEffect fetch (classic router) needs its own AbortController
useEffect(() => {
  const controller = new AbortController();
  fetch(`/api/projects/${id}`, { signal: controller.signal })
    .then((r) => r.json())
    .then(setProject)
    .catch((err) => { if (err.name !== "AbortError") throw err; });
  return () => controller.abort();   // cancel on unmount / param change
}, [id]);

Senior Engineer Perspective

Interviewers reward knowing that this cancellation is built into the data router's contract for free (via request.signal) — you just have to remember to actually forward it into your fetch call, which is the part people skip. In the classic router, point out you'd have to build this yourself with an AbortController in a useEffect cleanup, which is exactly the boilerplate loaders remove.

SECTION 10 - ROUTE-BASED CODE SPLITTING

Q47. How do you prefetch a route's chunk on link hover/focus before the user clicks?

ROI: ★★★★ Frequency: High

Short Answer

Call the same dynamic import() the route's lazy loader uses, but trigger it early — on onMouseEnter/onFocus of the link — so the JS chunk is already downloading (or cached) by the time the user actually clicks. This hides the network latency of code-splitting behind the user's natural hover/focus-before-click behavior.

Detailed Answer

Because import() is idempotent and the browser/webpack module cache dedupes repeated calls, prefetching on hover costs nothing if the user does click through (the actual navigation's import() just resolves instantly from cache) and costs only a speculative download if they don't. Q48. How do you avoid a layout-shift/flash when a lazy route resolves quickly?

ROI: ★★★ Frequency: Medium

Short Answer

A Suspense fallback that pops in and immediately out for a fast-resolving chunk causes a visible flash. Detailed Answer

Two separate techniques address two separate symptoms. A delayed-fallback wrapper (render nothing for the first N ms, then show the spinner only if still pending) fixes the "spinner flash" for fast loads. A skeleton sized/shaped like the eventual content (rather than a centered spinner) fixes layout shift, since the page's height/structure doesn't jump once the real content mounts.

Code Example

function DelayedFallback({ delay = 200, children }) {
  const [show, setShow] = useState(false);
  useEffect(() => {
    const t = setTimeout(() => setShow(true), delay);
    return () => clearTimeout(t);
  }, [delay]);
  return show ? children : null;
}

<Suspense fallback={<DelayedFallback><ReportsSkeleton /></DelayedFallback>}>
  <Reports />
</Suspense>

// ReportsSkeleton mirrors Reports' real layout dimensions to avoid shifting content below it

  return <div style={{ minHeight: 420 }} className="skeleton" />;
}

Q51. What's the difference between route-based splitting and component-based splitting, and when should you use each?

ROI: ★★★★ Frequency: High

Short Answer

Route-based splitting draws chunk boundaries at whole pages — the highest-leverage place to split, since a user visiting one route never pays for another route's code. Component-based splitting draws boundaries within a route, for expensive pieces that aren't always needed on that page (a modal, a rarely-opened settings panel, a heavy chart behind a tab). Start with route-based splitting always; add component-based splitting only for genuinely heavy, conditionally-rendered pieces.

Detailed Answer

Over-splitting at the component level has real costs: too many tiny chunks means too many HTTP requests and more waterfall-y loading, especially without HTTP/2 multiplexing tuned well. The rule of thumb is to reserve component-level splitting for pieces that are (a) genuinely large in bundle size and (b) not always rendered on that route — e.g., a rich text editor that only mounts once a user clicks "edit," not for every small subcomponent.

function SettingsPage() {

Interviewers want a decision rule, not just "both exist." Q52. How do you handle a lazy-loaded route failing to load, e.g. a stale chunk after a deploy?

Short Answer

Catch this specific failure (the dynamic import() rejects) and force a full page reload — which fetches the fresh index.html and the current chunk manifest — rather than showing a generic error.

In the data router, a failed lazy import throws, which surfaces to the route's errorElement; you detect this specific case (often by checking the error message for chunk-load-failure patterns, which vary by bundler) and respond with window.location.reload() instead of a normal "something went wrong" message, since the real fix is just getting a fresh copy of the app. Some teams add a version-check mechanism (poll a small endpoint or compare a build id) to proactively prompt "a new version is available, refresh to update" before the user even hits a broken chunk.

function isChunkLoadError(error: unknown) {

Q53. How do you preload routes based on predicted user intent, not just hover?

This trades some wasted bandwidth (prefetching chunks a user might not actually visit) for faster perceived navigation for the common path. Good candidates: the single most likely next route from a landing page, or a "prefetch the next page of a paginated flow" pattern in a checkout/wizard. function shouldPreload() {

  if (conn.saveData) return false;                     // user opted into data saving
  if (["slow-2g", "2g"].includes(conn.effectiveType)) return false;
  return true;
}

SECTION 11 - URL STATE MANAGEMENT

Q54. How do you keep multiple independent filters in the URL without clobbering each other?

ROI: ★★★★★ Frequency: Extremely High

Short Answer

Always update searchParams through the functional-updater form of setSearchParams, mutating a copy of the existing URLSearchParams rather than constructing a brand-new object from scratch. Passing a plain new object (setSearchParams({ q: text })) silently drops every other param that was in the URL — a very common bug when a page has several independent filters (search text, category, sort, page).

Detailed Answer

The failure mode: a filter panel has "search," "category," and "page" controls, each calling setSearchParams({ theirOwnKey: value }) independently. Every call replaces the entire query string with just that one key, so selecting a category wipes out the active search text. The fix is to always read the previous params (via the functional updater), mutate only the key you care about, and return the same object — preserving every param you didn't explicitly touch.

Code Example

const [searchParams, setSearchParams] = useSearchParams();

// WRONG — replaces the whole query string, dropping every other filter
function onCategoryChange(category: string) {
  setSearchParams({ category }); // "q" and "sort" params are now gone!
}

// CORRECT — functional updater preserves existing params
function onCategoryChange(category: string) {
  setSearchParams((prev) => {
    const next = new URLSearchParams(prev);
    next.set("category", category);
    next.set("page", "1");   // reset pagination when a filter changes
    return next;
  });
}

Senior Engineer Perspective

This is one of the highest-frequency real bugs in URL-state-driven UIs, so interviewers use it as a quick "have you actually built this" filter. The tell of real experience: mentioning that changing one filter often needs to reset a different param (like resetting page back to 1 whenever a filter changes), which only the functional-updater pattern makes easy to express correctly in one place.

Q55. How do you sync pagination state with the URL while keeping the component fast?

ROI: ★★★★ Frequency: High

Short Answer

Read the current page from searchParams.get("page"), coerce it to a number with a sane default/fallback, and drive your data-fetching (or loader) off that value directly instead of mirroring it into a separate useState. Update the URL (via setSearchParams, typically with replace: true) when the user changes pages, and let the URL remain the single source of truth rather than syncing two copies of the same state.

Detailed Answer

A common anti-pattern is mirroring the URL param into component state (useState initialized from the param, then synced with a useEffect) — this creates two sources of truth that can drift, and doubles the code needed to keep them aligned. Just read directly from searchParams on every render; React re-renders naturally when the URL changes, so there's no need for a shadow copy. Use replace: true for pagination since each page turn isn't usually a navigation the user wants to individually Back through.

Code Example

function ProductList() {
  const [searchParams, setSearchParams] = useSearchParams();
  const page = Math.max(1, Number(searchParams.get("page")) || 1); // URL is the source of truth

  const { data } = useQuery({
    queryKey: ["products", page],
    queryFn: () => fetchProducts(page),
  });

  function goToPage(next: number) {
    setSearchParams((prev) => {
      const copy = new URLSearchParams(prev);
      copy.set("page", String(next));
      return copy;
    }, { replace: true }); // page turns don't each need their own Back-button stop
  }

  return <Pagination page={page} onChange={goToPage} items={data} />;
}

Senior Engineer Perspective

The signal interviewers want: "don't mirror the URL into local state — read it directly on every render and let the URL be the only source of truth." Bringing up replace for pagination specifically (vs push for, say, opening a detail page) shows you're thinking about what belongs in the Back-button history and what doesn't.

Q56. How do you validate and sanitize search params that a user could hand-edit?

ROI: ★★★★ Frequency: High

Short Answer

Never trust a query param's raw value — a user can type anything into the address bar. Parse numbers with a guarded fallback, validate enums against an allowlist (falling back to a default for anything unrecognized), and clamp ranges (e.g. a page number can't be negative or absurdly large) before using the value to drive a fetch or render logic.

Detailed Answer

Treat search params exactly like any other untrusted external input — because they are: a query string is fully user-editable and can be shared/bookmarked in a malformed state. Beyond just crash-prevention, validating against an allowlist (e.g. sort must be one of a known set of values) also closes off using the param as an injection vector into a backend query if you ever pass it through unsanitized.

Code Example

const ALLOWED_SORTS = ["price_asc", "price_desc", "newest"] as const;
type Sort = (typeof ALLOWED_SORTS)[number];

function useValidatedFilters() {
  const [searchParams] = useSearchParams();

  const rawSort = searchParams.get("sort");
  const sort: Sort = (ALLOWED_SORTS as readonly string[]).includes(rawSort ?? "")
    ? (rawSort as Sort)
    : "newest"; // safe default for anything unrecognized

  const rawPage = Number(searchParams.get("page"));
  const page = Number.isFinite(rawPage) ? Math.min(Math.max(1, rawPage), 500) : 1; // clamp

  return { sort, page };
}

Senior Engineer Perspective

The framing that lands: "query params are user input, full stop — validate them exactly as rigorously as a form field, because a URL is even easier to hand-edit than a form." Bonus point for mentioning that if a validated/sanitized value differs from what was in the URL, it's good UX to also correct the URL itself (via a replace-navigation) so the address bar reflects the actually-applied filter, not the malformed one.

Q57. How do you keep a controlled form's state in sync with the URL for deep-linking?

ROI: ★★★★ Frequency: High

Short Answer

Initialize the form's controlled fields from searchParams on first render, and write changes back to the URL (typically debounced, with replace: true) as the user edits — rather than treating the URL as write-only or the form state as the sole source of truth. This makes the exact filter combination shareable and bookmarkable, and restores correctly on a fresh load of the URL.

Detailed Answer

The tension to manage: form inputs need to feel instant (typing shouldn't lag), but URL updates on every keystroke would flood history and cause excess re-renders/re-fetches. Debounce the URL write (a few hundred ms after the user stops typing) while keeping the input itself fully responsive via local component state that's merely initialized from and synced to the URL, not driven by it on every keystroke.

Code Example

function SearchFilterForm() {
  const [searchParams, setSearchParams] = useSearchParams();
  const [query, setQuery] = useState(searchParams.get("q") ?? ""); // local, responsive typing

  useEffect(() => {
    const timeout = setTimeout(() => {
      setSearchParams((prev) => {
        const next = new URLSearchParams(prev);
        if (query) next.set("q", query); else next.delete("q");
        return next;
      }, { replace: true });
    }, 300); // debounce the URL write, not the input itself
    return () => clearTimeout(timeout);
  }, [query]);

  return <input value={query} onChange={(e) => setQuery(e.target.value)} />;
}

Senior Engineer Perspective

Interviewers listen for the debounce-the-URL-not-the-input distinction — a naive implementation that writes to searchParams on every keystroke both floods history (if not using replace) and can visibly lag on slower devices since each keystroke triggers a navigation. Decoupling "what the input shows" from "what's synced to the URL" is the key insight.

Q58. How do you debounce URL updates for a live search box without breaking back/forward?

ROI: ★★★ Frequency: Medium

Short Answer

Debounce the writes (not the reads), and use replace: true for the debounced updates so intermediate keystrokes don't each create a new history entry — otherwise the Back button would have to be pressed once per keystroke to undo a single search, which is unusable. Only use a push (non-replace) update for a deliberate "commit" action, like pressing Enter or a Search button.

Detailed Answer

Without replace, a debounced-but-still-frequent update (say, once every 300ms while typing a long query) still creates a new history entry per update, polluting the stack. replace collapses all those intermediate states into overwrites of the same entry, so Back from the search results goes to wherever the user was before they started searching at all — not back through every individual keystroke's URL state.

Code Example

// Debounced, replace-based updates while typing — Back skips over every keystroke
setSearchParams((prev) => {
  const next = new URLSearchParams(prev);
  next.set("q", query);
  return next;
}, { replace: true });

// A deliberate "save this search" action: push instead, so it IS a real Back-able step
function onPressEnter() {
  setSearchParams((prev) => {
    const next = new URLSearchParams(prev);
    next.set("q", query);
    return next;
  }); // no replace — this commit is worth its own history entry
}

Senior Engineer Perspective

The nuance worth surfacing: not every URL update should behave the same way in history — transient/incremental updates (typing) should replace, while deliberate commits (submitting a search, applying a filter panel) can reasonably push. Conflating the two either floods history or makes deliberate actions un-undoable via Back, so the right call depends on the semantic weight of the change, not a blanket rule.

Q59. How do you serialize complex state (arrays, objects) into the query string?

ROI: ★★★★ Frequency: High

Short Answer

URLSearchParams only natively supports flat string key/value pairs (with repeatable keys for simple arrays). For arrays, use repeated keys (?tag=a&tag=b) or a delimited string (?tags=a,b,c); for nested objects, either flatten them into dotted/bracketed keys or serialize the whole thing as one JSON string param and JSON.parse it back out — trading URL readability for simplicity.

Detailed Answer

The right tradeoff depends on how much you value a human-readable, hand-editable URL versus implementation simplicity. Repeated keys (getAll("tag")) are the most idiomatic for simple string-array filters and read naturally. A single JSON-encoded param is simplest to implement for deeply nested shapes but produces an ugly, URL-encoded blob that's hard to read or hand-edit, and needs try/catch around the parse for malformed/tampered input.

Code Example

// Repeated keys for a simple array — human-readable, idiomatic
const params = new URLSearchParams();
["red", "blue"].forEach((tag) => params.append("tag", tag));
// -> ?tag=red&tag=blue
const tags = searchParams.getAll("tag"); // ["red", "blue"]

// Delimited string — compact, but you own the split/join and escaping of the delimiter itself
searchParams.set("tags", ["red", "blue"].join(","));
const tags2 = (searchParams.get("tags") ?? "").split(",").filter(Boolean);

// JSON blob — simplest for nested shapes, least readable, needs defensive parsing
searchParams.set("filters", JSON.stringify({ price: { min: 10, max: 50 } }));
function readFilters() {
  try { return JSON.parse(searchParams.get("filters") ?? "{}"); }
  catch { return {}; } // never trust user-editable JSON
}

Senior Engineer Perspective

A senior answer frames this as a genuine tradeoff (readability/shareability vs implementation ease) rather than one "correct" technique, and always wraps any JSON-in-URL parsing in a try/catch — a hand-edited or corrupted URL must degrade to sensible defaults, not crash the page.

Q60. How do you migrate from local component state to URL-driven state safely?

ROI: ★★★ Frequency: Medium

Short Answer

Do it incrementally: keep the existing useState-based behavior working, add URL sync as a layer on top (read the initial value from searchParams if present, otherwise fall back to the current default), verify parity in production, then remove the standalone state once the URL is confirmed as the sole source of truth. Never flip an entire filter panel to pure URL state in one risky rewrite.

Detailed Answer

The safe migration path mirrors any state-management migration: introduce the new source of truth alongside the old one, make the old one derive from the new one (not vice versa) as soon as it's proven correct, then delete the old one. Concretely: replace useState(defaultValue) with a value computed from searchParams with the old default only as a fallback for when the param is absent — this way, existing bookmarks and shared links without the new param still behave exactly as before.

const [sort, setSort] = useState("newest");

// Step 1: read from the URL with the old default as fallback — non-breaking
const [searchParams, setSearchParams] = useSearchParams();
const sort = searchParams.get("sort") ?? "newest"; // old behavior preserved when param absent

    const copy = new URLSearchParams(prev);
    copy.set("sort", next);
    return copy;
  });
}

Senior Engineer Perspective

What interviewers want here is migration discipline, not just the end-state code: preserve the old default as the fallback for an absent param so you don't break existing bookmarks or shared links during the transition, and roll it out one filter/control at a time rather than rewriting an entire filter panel's state model in a single risky change.

Q61. What's the difference between useSearchParams and manually parsing window.location.search?

ROI: ★★★ Frequency: Medium

Short Answer

useSearchParams is reactive — it re-renders your component when the URL's query string changes via router navigation — and its setter updates the URL through the router (respecting push/replace, integrating with the history stack correctly). Manually reading window.location.search is a one-time snapshot with no reactivity, and manually calling history.pushState to change it bypasses the router entirely, desyncing it from what the router thinks the current location is.

Detailed Answer

Reading window.location.search directly inside a component gives you the value at render time only — it won't trigger a re-render if the query string changes without some other state update forcing one, and doesn't hook into React's render cycle at all. Writing via raw history.pushState instead of the router's navigation API is worse: the router maintains its own internal notion of the current location, and bypassing it means that internal state drifts out of sync with the real URL, breaking things like useNavigation, blockers, and revalidation that assume all navigation goes through the router.

Code Example

// Anti-pattern: reads a snapshot, no reactivity, and bypasses the router on write
function BadFilter() {
  const params = new URLSearchParams(window.location.search); // stale after route changes
  function setFilter(value: string) {
    const next = new URLSearchParams(window.location.search);
    next.set("filter", value);
    window.history.pushState(null, "", `?${next}`); // router doesn't know this happened
  }
}

// Correct: reactive read, router-aware write
function GoodFilter() {
  const [searchParams, setSearchParams] = useSearchParams(); // reactive
  function setFilter(value: string) {
    setSearchParams((prev) => {
      const next = new URLSearchParams(prev);
      next.set("filter", value);
      return next;
    }); // router stays in sync
  }
}

Senior Engineer Perspective

The concrete failure interviewers want named: manually calling history.pushState outside the router creates a URL change the router's internal state doesn't know about, so router-driven features (blockers, revalidation, even Back/Forward handling in some setups) can desync from the address bar. Always go through the router's own navigation primitives for anything the router also needs to be aware of.

SECTION 12 - SCROLL RESTORATION & NAVIGATION UX

Q62. How do you customize ScrollRestoration's scroll key to preserve scroll across filter changes?

ROI: ★★★★ Frequency: High

Short Answer

By default, <ScrollRestoration> keys saved scroll positions by location.key, which changes on every navigation — including a query-param-only change like paging or filtering. Pass a custom getKey that derives its key from location.pathname alone (ignoring search) so scroll position is preserved across param changes on what's conceptually "the same page."

Detailed Answer

The default behavior makes sense for genuinely different pages (each gets its own remembered scroll spot for Back/Forward) but is often wrong for a list page where the user changes a filter or sort order — by default that's treated as a brand-new "page" for scroll purposes and jumps back to the top, which is jarring if the user was scrolled deep into a long list when they tweaked a filter. Keying on pathname only groups all query-string variants of the same route together for scroll-memory purposes.

Code Example

import { ScrollRestoration, useLocation } from "react-router-dom";

function Root() {
  return (
    <>
      <Outlet />
      <ScrollRestoration
        getKey={(location) => location.pathname} // ignore search params in the scroll key
      />
    </>
  );
}

Senior Engineer Perspective

Interviewers reward knowing this is configurable at all — many candidates assume scroll restoration is all-or-nothing. The nuance to add: keying purely by pathname is itself a tradeoff — you lose per-filter scroll memory (switching filters and coming back won't restore a filter-specific scroll spot), so pick the granularity that matches your actual UX intent rather than reaching for the most aggressive "ignore everything" key by default.

Q63. How do you scroll to a specific element/anchor after navigating (e.g., #section-2)?

ROI: ★★★ Frequency: Medium

Short Answer

Read location.hash via useLocation(), find the matching element by id, and call element.scrollIntoView() in an effect keyed on the hash — React Router doesn't automatically scroll to hash anchors the way a full page navigation would, since there's no browser-native anchor-jump for client-side route changes.

Detailed Answer

Because the whole point of client-side routing is skipping the browser's native navigation, you also skip its native hash-anchor scrolling behavior — this is a deliberate gap you fill yourself. Do this after the target content has actually rendered (the effect should run after the relevant data is loaded, not before), or the element you're trying to scroll to won't exist in the DOM yet.

Q64. How do you preserve scroll position inside a scrollable list/panel across route changes?

ROI: ★★★★ Frequency: High

Short Answer

<ScrollRestoration> only manages window scroll — it has no awareness of an internally-scrolling <div> (a common pattern for a master-detail layout with its own scrollable list panel). You have to manually save that panel's scrollTop (e.g. in a ref or a small map keyed by route) before navigating away, and restore it after navigating back.

Detailed Answer

A common pattern: store scroll positions in a Map keyed by the list's identity (e.g. the current filter/page), read from it when the panel mounts, and write to it in a scroll listener (throttled) or on unmount. This is conceptually the same problem ScrollRestoration solves for the window, just applied manually to an element that isn't the window.

Code Example

const scrollPositions = new Map<string, number>();

function MessageListPanel({ scrollKey }: { scrollKey: string }) {
  const ref = useRef<HTMLDivElement>(null);

  useEffect(() => {
    const el = ref.current;
    if (el) el.scrollTop = scrollPositions.get(scrollKey) ?? 0; // restore on mount
    return () => {
      if (el) scrollPositions.set(scrollKey, el.scrollTop);      // save on unmount
    };
  }, [scrollKey]);

  return <div ref={ref} className="scrollable-panel">{/* list items */}</div>;
}

Q65. How do you show a top-of-page progress bar during slow navigations?

Detailed Answer

This is the same underlying signal used for other pending-state UI, just applied to a different visual treatment. A common library for the actual bar visuals is nprogress or a small custom CSS width-animated div; the interesting part isn't the visual, it's correctly wiring its start/stop to the router's global navigation state rather than to individual component-level loading flags, so it works uniformly across every route.

Code Example

import { useNavigation } from "react-router-dom";
import { useEffect, useRef } from "react";

function TopProgressBar() {
  const navigation = useNavigation();
  const timeoutRef = useRef<number>();
  const [visible, setVisible] = useState(false);

  useEffect(() => {
    if (navigation.state === "loading" || navigation.state === "submitting") {

      setVisible(false);
    }
    return () => clearTimeout(timeoutRef.current);
  }, [navigation.state]);

  return <div className="top-progress-bar" />;
}

Q66. How do you avoid scroll-restoration flicker when a route also lazy-loads?

Short Answer

If the real content is taller, the saved scroll offset (computed against the old, taller page) overshoots against the temporarily shorter one. Giving fallbacks a similar height to their eventual content minimizes this mismatch.

Q67. How do you handle scroll restoration in a virtualized list across navigation?

ROI: ★★★ Frequency: Medium

Short Answer

A virtualized list (react-window, react-virtual/TanStack Virtual) only renders items near the viewport, so restoring "scrollTop" alone isn't enough if the list has since unmounted/remounted — you need the virtualizer's own API to scroll to a specific index/offset, and you need to persist that index (not just a raw pixel offset) since item sizes can differ across mounts if data changed.

Detailed Answer

Raw pixel scroll offsets are fragile for virtualized content because the virtualizer may compute different item heights on remount (e.g. dynamic row heights, or a slightly different data set). The robust approach is to persist the topmost visible item index (or a stable item id) and use the virtualization library's imperative scrollToIndex/scrollToItem API to restore position by identity, not by a brittle pixel number.

Code Example

import { useRef } from "react";
import { FixedSizeList } from "react-window";

const lastIndexByRoute = new Map<string, number>();

function VirtualizedResults({ routeKey, items }) {
  const listRef = useRef<FixedSizeList>(null);

  function handleItemsRendered({ visibleStartIndex }) {
    lastIndexByRoute.set(routeKey, visibleStartIndex); // save by index, not pixel offset
  }

  const initialIndex = lastIndexByRoute.get(routeKey) ?? 0;

  return (
    <FixedSizeList
      ref={listRef}
      height={600}
      itemCount={items.length}
      itemSize={48}
      initialScrollOffset={initialIndex * 48}
      onItemsRendered={handleItemsRendered}
    >
      {({ index, style }) => <div style={style}>{items[index].name}</div>}
    </FixedSizeList>
  );
}

Senior Engineer Perspective

The depth signal: explicitly rejecting a raw pixel-offset approach in favor of an index/identity-based one, because virtualized content's actual rendered height is a derived, potentially-changing quantity — pixel offsets computed against yesterday's data can point to the wrong row entirely after a remount with slightly different content.

Q69. How do you decide between one root errorElement and many nested ones?

ROI: ★★★★★ Frequency: Extremely High

Short Answer

Placing a boundary at each major layout level means a failure in, say, a project's detail loader shows an inline error inside the still-functional dashboard shell — the sidebar and top nav remain usable, and the user can navigate away from the broken page without a refresh.

Q70. How do you distinguish a 404 from a 500 inside a shared errorElement?

ROI: ★★★★★ Frequency: Extremely High

Short Answer

Use isRouteErrorResponse(error) from useRouteError() to check whether the thrown value is a router-recognized HTTP-style Response (has status/statusText/data) versus an arbitrary JS Error. Branch on error.status for the former (404 vs 401 vs 500) and treat the latter as an unexpected crash with a generic message.

Detailed Answer

Loaders/actions that throw new Response(body, { status }) (or the router's own internal errors, like a route genuinely not matching) produce a "route error response" that carries real HTTP semantics. A loader that throws a plain Error (a bug, a network exception, an unexpected null) does not carry a status — treat that branch as "something went wrong" without pretending to know more than you do. This distinction lets one shared boundary component serve very different messages (friendly "page not found" vs "please try again / contact support") from the same code path.

Code Example

import { useRouteError, isRouteErrorResponse } from "react-router-dom";

function SharedErrorBoundary() {
  const error = useRouteError();

  if (isRouteErrorResponse(error)) {
    switch (error.status) {
      case 404: return <h1>This page doesn't exist.</h1>;
      case 401: return <h1>You need to sign in to view this.</h1>;
      case 403: return <h1>You don't have access to this.</h1>;
      default:  return <h1>{error.status} {error.statusText}</h1>;
    }
  }

  // Not an HTTP-shaped error — an unexpected bug/exception
  console.error(error);
  return <h1>Something went wrong. Please try again.</h1>;
}

Senior Engineer Perspective

Interviewers want the precise function name (isRouteErrorResponse) and the reasoning for why it exists: without it, you'd be guessing at the shape of an unknown-typed thrown value, and a JS Error object doesn't reliably have a status field the way an intentionally-thrown Response does. A senior answer also logs/reports the non-HTTP branch since that's the one representing a real bug worth investigating, unlike an expected 404.

Q71. How do you log/report errors caught by errorElement to a monitoring service?

ROI: ★★★★ Frequency: High

Short Answer

Inside the error boundary component, call useRouteError() and report it to your monitoring tool (Sentry, Datadog, etc.) as a side effect — typically in a useEffect so it fires exactly once per render of that error state, not on every re-render. Skip reporting for expected, non-exceptional statuses like a legitimate 404, and report everything else.

Detailed Answer

Not every caught "error" is a bug — a 404 for a genuinely missing resource is expected behavior and shouldn't spam your error-tracking dashboard the same way an actual 500 or an unexpected JS exception should. Filter by isRouteErrorResponse and status before deciding whether to report, and include route context (which path/params were active) in the report payload, since that's often the fastest way to reproduce the failure later.

Code Example

import { useRouteError, isRouteErrorResponse, useLocation } from "react-router-dom";
import * as Sentry from "@sentry/react";

function ReportingErrorBoundary() {
  const error = useRouteError();
  const location = useLocation();

  useEffect(() => {
    const isExpected404 = isRouteErrorResponse(error) && error.status === 404;
    if (!isExpected404) {
      Sentry.captureException(error, { extra: { pathname: location.pathname } });
    }
  }, [error, location.pathname]);

  return isRouteErrorResponse(error) && error.status === 404
    ? <NotFoundPage />
    : <GenericErrorPage />;
}

The signal interviewers want: filtering out expected statuses before reporting, so your monitoring tool's signal-to-noise stays useful — a dashboard flooded with routine 404s for bots/typos buries the real 500s you actually need to act on. Q72. How does errorElement interact with React's own render-error boundaries?

ROI: ★★★★ Frequency: High

Short Answer

They overlap but aren't identical: errorElement catches loader/action errors (which happen outside React's render phase entirely — a regular componentDidCatch-style boundary cannot see those) and catches render errors thrown by the route's own component tree, since React Router wraps each routed element in its own internal error boundary. Where a traditional boundary is still relevant is for errors in code that lives outside any specific route's tree — e.g., in the app shell rendered before the router, or intentionally scoped around a specific widget for reasons unrelated to routing (like isolating a risky third-party embed).

The precise claim to make: "errorElement is a superset for anything inside its route — it replaces the need for a separate render-error boundary per route." Q73. How do you retry a failed loader from the error UI without a full page reload?

Short Answer

Call useRevalidator().revalidate() from within (or near) the error boundary. It re-runs the current route's loaders without a full navigation or page reload — if the underlying transient failure (a flaky network blip) has resolved, the route re-renders normally with fresh data; if it fails again, the error boundary shows again.

This is the loader-era equivalent of a "try again" button in a traditional React error boundary that resets its internal error state — except here you're specifically asking the router to re-invoke the data-fetching step, not just re-rendering with stale/cached data. It's the right tool for transient failures (network blips, a backend briefly returning 500) where simply trying the exact same request again is likely to succeed.

Senior Engineer Perspective

The naming precision matters here: useRevalidator re-runs loaders (the data-fetching step) as opposed to a plain component re-render, which is exactly what's needed when the failure was in the fetch itself, not in rendering. Q74. How do you handle partial failures when a route has multiple independent data sources?

ROI: ★★★★ Frequency: High

Short Answer

Don't let one optional data source's failure take down the whole page via a thrown error in the loader. Fetch independent pieces with individual try/catch (or Promise.allSettled) inside the loader, returning a per-field success/error marker so the component can render the parts that succeeded and show a small inline failure for just the part that didn't.

Detailed Answer

A loader that awaits several unrelated fetches with a plain Promise.all fails the entire loader (and thus the entire route, via errorElement) if any single one rejects — even if the other data succeeded and could have rendered fine on its own. Promise.allSettled (or individual try/catch blocks) lets you distinguish "core data failed, the whole page is meaningless" from "a secondary widget's data failed, show the rest of the page with a small inline error for that one piece."

Code Example

export async function loader({ params }) {

    fetchProfile(params.userId),    // critical — if this fails, the page is meaningless
    fetchRecentActivity(params.userId), // optional — fine to show as a small inline error
  ]);

  if (profileResult.status === "rejected") {
    throw new Response("Profile not found", { status: 404 }); // core failure: full errorElement
  }

  return {
    profile: profileResult.value,
    activity: activityResult.status === "fulfilled" ? activityResult.value : null, // partial failure
  };
}

function ProfilePage() {
  const { profile, activity } = useLoaderData();

      {activity ? <ActivityFeed items={activity} /> : <p>Couldn't load recent activity.</p>}
    </>
  );
}

Senior Engineer Perspective

The judgment call interviewers are probing for: classifying each data dependency as "critical" (its failure should legitimately take out the page) versus "optional" (its failure should degrade gracefully). A blanket Promise.all treats everything as critical by default, which is often too aggressive for pages composed of several independently-useful widgets.

The detail interviewers check for: constructing a real FormData-backed Request instead of a loosely-typed fake object, since that's what actually exercises request.formData() the same way the router calls it in production. Also testing the redirect branch by inspecting the Response's status/headers, treating redirect()'s return value as the real contract rather than assuming it "just works."

Q80. How do you write an integration test that clicks a link and asserts the next route rendered?

ROI: ★★★★ Frequency: High

Short Answer

Render the relevant slice of your route tree in a MemoryRouter, use userEvent.click on the link's accessible role/name (not a CSS selector), and assert the new route's content is present while the old route's content is gone. This exercises the whole click-to-navigate-to-render pipeline the way a real user experiences it.

Detailed Answer

Prefer screen.getByRole("link", { name: /view profile/i }) over a brittle class-name or test-id selector where possible, since it also verifies the link is accessible (has the right role and discoverable text) as a side effect of the test. Assert both directions — the destination content appears AND the origin content disappears — to catch bugs where a route incorrectly renders alongside its sibling instead of replacing it.

Code Example

test("clicking the profile link navigates to the profile route", async () => {
  render(
    <MemoryRouter initialEntries={["/"]}>
      <Routes>
        <Route path="/" element={<HomePage />} />
        <Route path="/profile" element={<ProfilePage />} />
      </Routes>
    </MemoryRouter>
  );

  await userEvent.click(screen.getByRole("link", { name: /view profile/i }));

  expect(await screen.findByRole("heading", { name: /your profile/i })).toBeInTheDocument();
  expect(screen.queryByRole("heading", { name: /welcome home/i })).not.toBeInTheDocument();
});

Senior Engineer Perspective

Interviewers look for role-based queries over implementation-detail selectors, and for asserting the negative case too (old content gone) — a test that only checks the new content appeared would pass even if a routing bug rendered both routes' content simultaneously.

Q81. How do you test a protected route redirecting unauthenticated users, end to end?

ROI: ★★★★ Frequency: High

Short Answer

This is the same pattern as Q38, extended to also cover the reverse path: with an authenticated mock, confirm the protected content renders; with an unauthenticated mock, confirm the login page renders instead — both through a real router config seeded at the protected path, so the guard's actual redirect logic executes rather than being assumed.

Detailed Answer

A thorough test suite for a guard covers at minimum: unauthenticated → redirected to login; authenticated with correct role → sees protected content; authenticated with wrong role (if role-based) → redirected to a 403 page, distinct from the login redirect. Testing all three branches through the real guard component (not a stubbed-out version of it) is what actually proves the guard logic is correct end to end.

Code Example

function renderProtectedApp(initialPath: string) {
  const router = createMemoryRouter(
    [
      { path: "/login", element: <div>Login</div> },
      { path: "/403", element: <div>Forbidden</div> },
      {
        element: <RequireRole role="admin" />,
        children: [{ path: "/admin", element: <div>Admin Panel</div> }],
      },
    ],
    { initialEntries: [initialPath] }
  );
  return render(<RouterProvider router={router} />);
}

test("unauthenticated user is redirected to login", () => {
  vi.mocked(useAuth).mockReturnValue({ user: null });
  renderProtectedApp("/admin");
  expect(screen.getByText("Login")).toBeInTheDocument();
});

test("authenticated non-admin is redirected to 403", () => {
  vi.mocked(useAuth).mockReturnValue({ user: { roles: ["member"] } });
  renderProtectedApp("/admin");
  expect(screen.getByText("Forbidden")).toBeInTheDocument();
});

test("admin sees the protected panel", () => {
  vi.mocked(useAuth).mockReturnValue({ user: { roles: ["admin"] } });
  renderProtectedApp("/admin");
  expect(screen.getByText("Admin Panel")).toBeInTheDocument();
});

Senior Engineer Perspective

Interviewers want to see all the guard's branches enumerated and tested, not just the happy path — especially the "authenticated but wrong role" branch, which is the one most often left untested because it's easy to forget it's a distinct case from "not logged in at all."

Q82. How do you test useSearchParams-driven UI (filters, pagination)?

ROI: ★★★★ Frequency: High

Short Answer

Seed the router's initialEntries with a URL that already contains the query params you want to test ("/products?category=shoes&page=2") to verify initial read behavior, and simulate user interaction (clicking a filter) to verify the component correctly updates the URL — which you can assert on by rendering a small router-state display, or by checking the resulting DOM state that depends on the new params.

Detailed Answer

Two things worth testing separately: (1) given a URL with certain params, does the component render the correct initial state (the read side), and (2) does interacting with the UI produce the correct new URL and corresponding re-render (the write side). For asserting the actual URL changed, either expose it via a test-only component that reads and displays useLocation().search, or assert on the resulting rendered state that depends on it (simpler and usually sufficient).

Code Example

test("renders products filtered by the category in the URL", () => {
  render(
    <MemoryRouter initialEntries={["/products?category=shoes"]}>
      <Routes><Route path="/products" element={<ProductList />} /></Routes>
    </MemoryRouter>
  );
  expect(screen.getByText(/showing: shoes/i)).toBeInTheDocument();
});

test("clicking a category filter updates the results", async () => {
  render(
    <MemoryRouter initialEntries={["/products"]}>
      <Routes><Route path="/products" element={<ProductList />} /></Routes>
    </MemoryRouter>
  );
  await userEvent.click(screen.getByRole("button", { name: /shoes/i }));
  expect(screen.getByText(/showing: shoes/i)).toBeInTheDocument(); // reflects the URL update
});

Senior Engineer Perspective

The framing interviewers want: test the read side and the write side of URL state separately and explicitly, rather than one vague test that conflates both. Preferring to assert on rendered, user-visible state over reaching into router internals keeps the test resilient to internal implementation changes.

Q83. What testing anti-patterns commonly show up in routed-component tests?

ROI: ★★★★★ Frequency: Extremely High

Short Answer

The recurring ones: mocking useNavigate/router hooks entirely instead of using a real (memory) router, which tests implementation rather than behavior; asserting on router internals (path strings, history length) instead of rendered UI; forgetting to test both branches of a guard; and testing loaders/actions only through a full component render instead of also unit-testing them directly as plain functions.

Detailed Answer

Each of these has a concrete cost. Over-mocking router hooks makes tests brittle to refactors that don't change user-visible behavior (e.g. switching a redirect from imperative to declarative). Asserting on internals couples the test to the router's implementation details rather than what a user actually sees. Skipping a guard's negative-case branch means the exact case most likely to regress (someone loosens a permission check) goes untested. And skipping isolated loader/action tests means every data-fetching edge case has to be reproduced through a slow, harder-to-set-up full render.

Code Example

// Anti-pattern: testing that navigate() was CALLED, not that navigation actually happened
test("bad: implementation-coupled", () => {
  const navigateMock = vi.fn();
  vi.mocked(useNavigate).mockReturnValue(navigateMock);
  // ...
  expect(navigateMock).toHaveBeenCalledWith("/success"); // fragile, tests internals
});

// Better: render both routes for real, assert on what the user actually sees
test("good: behavior-focused", async () => {
  render(
    <MemoryRouter initialEntries={["/checkout"]}>
      <Routes>
        <Route path="/checkout" element={<CheckoutForm />} />
        <Route path="/success" element={<div>Order placed!</div>} />
      </Routes>
    </MemoryRouter>
  );
  await userEvent.click(screen.getByRole("button", { name: /place order/i }));
  expect(await screen.findByText("Order placed!")).toBeInTheDocument();
});

Senior Engineer Perspective

This question is really asking "have you maintained a test suite through refactors," since every one of these anti-patterns only reveals itself as pain once code changes and brittle tests start failing for the wrong reasons. A strong answer names the underlying principle — test behavior visible to the user, not the specific mechanism producing it — and applies it consistently across all the routing-testing scenarios above.

Q84. What are the real tradeoffs between client-side routing and framework/server-driven routing?

ROI: ★★★★★ Frequency: Extremely High

Short Answer

Client-side routing (plain React + React Router) gives you full control and no framework lock-in, at the cost of owning SSR/SEO/first-paint concerns yourself. Framework routing (Next.js App Router, Remix/React Router 7) gives you SSR, streaming, and file-based conventions out of the box, at the cost of adopting the framework's build system, deployment model, and opinions. Neither is universally "better" — the right choice depends on whether SEO and first-paint matter for the product.

Detailed Answer

ConcernClient-side (React Router SPA)Framework-driven (Next/Remix)
Initial HTMLEmpty shell; content renders after JS loadsPopulated HTML on first response
SEONeeds extra work (prerendering, SSR add-on)Built in
DeploymentStatic hosting + SPA fallback is enoughNeeds a Node/edge runtime (or SSG export)
FlexibilityHigh — bring your own everythingLower — follow the framework's conventions
Best forInternal tools, dashboards, authenticated apps behind a login wallPublic, content-heavy, SEO-sensitive sites

A dashboard sitting entirely behind a login wall has essentially nothing to gain from SSR/SEO — nobody's Google-searching their way into your authenticated billing page — which is exactly the case where a plain client-side SPA with React Router is the pragmatic, lower-overhead choice. A public marketing/content site is the opposite case.

Project Example

A B2B internal admin tool stayed on plain React Router for years because every page sits behind auth — SEO was irrelevant, and the team valued not being tied to a framework's release cadence and deployment model. Meanwhile the same company's public marketing site used Next.js, because organic search traffic was the entire point of that surface.

Senior Engineer Perspective

The strongest answer here is decision-framework shaped, not a loyalty statement: name the concrete axes (SEO need, first-paint sensitivity, deployment constraints, team's appetite for framework lock-in) and map a real product decision onto them, rather than declaring one approach universally superior. Interviewers are testing judgment, not tribal preference.

Q85. How do you plan a migration from React Router v5 to v6+?

ROI: ★★★★ Frequency: High

Short Answer

The biggest breaking changes are: <Switch> → <Routes>, every child route path becomes relative by default (no more repeating the full path per route), useHistory is replaced by useNavigate, and <Route render/component> props are replaced by a single element prop. Plan the migration route-by-route rather than attempting a big-bang rewrite, since v6's codemod coverage is incomplete and much of this needs manual verification.

Detailed Answer

v5v6+
<Switch><Routes>
<Route path="/a" component={A} /><Route path="/a" element={<A />} />
useHistory().push(x)useNavigate()(x)
Nested route paths written in fullNested route paths are relative to parent
<Redirect to="/x" /><Navigate to="/x" />

Because relative paths are the default in v6 (a v5 nested route had to repeat its parent's full path), a naive find-and-replace of component names without also flattening/adjusting path strings produces broken routes that silently don't match anymore. Budget real QA time per section of the app, not just a mechanical API rename pass.

Code Example

// v5
import { Switch, Route, useHistory, Redirect } from "react-router-dom";
function App() {
  const history = useHistory();
  return (
    <Switch>
      <Route exact path="/dashboard" component={Dashboard} />
      <Route path="/dashboard/settings" component={Settings} /> {/* full path repeated */}
      <Redirect from="/old" to="/new" />
    </Switch>
  );
}

// v6+
import { Routes, Route, useNavigate, Navigate } from "react-router-dom";
function App() {
  const navigate = useNavigate();
  return (
    <Routes>
      <Route path="/dashboard" element={<DashboardLayout />}>
        <Route index element={<Dashboard />} />
        <Route path="settings" element={<Settings />} />  {/* relative now */}
      </Route>
      <Route path="/old" element={<Navigate to="/new" replace />} />
    </Routes>
  );
}

Senior Engineer Perspective

The point that shows real migration experience: the relative-paths default change is the subtlest and most bug-prone part, because it's a silent behavioral shift, not a compile error — a leftover full path from v5 doesn't crash, it just quietly stops matching. Recommend migrating and thoroughly testing one section/feature at a time rather than a single sweeping rename across the whole app.

Q86. How do you migrate from the classic Routes API to createBrowserRouter incrementally in an existing app?

ROI: ★★★★ Frequency: High

Short Answer

You can't run both <BrowserRouter> and <RouterProvider> at once — they're two different router implementations — so this migration is a one-time cutover, not a gradual side-by-side rollout. Reduce risk by first converting the route tree to the plain-object shape it needs (which works under either API, since <Routes> can also consume objects via useRoutes), verifying that's correct, then swapping the top-level provider in a single, well-tested change.

Detailed Answer

The practical strategy: first extract your JSX route tree into an equivalent array-of-objects structure and render it via useRoutes(routeObjects) under the still-classic <BrowserRouter> — this is a no-behavior-change refactor you can verify safely. Once that's solid, swap <BrowserRouter></BrowserRouter> + useRoutes for createBrowserRouter(routeObjects) + <RouterProvider> — now the route tree shape hasn't changed at all, only the provider has, which narrows the actual risky change to the smallest possible diff. Only after that cutover do you start incrementally adding loaders/actions/errorElement per route.

Code Example

// Step 1: extract to route objects, still under the classic provider — safe, verifiable
const routeObjects = [
  { path: "/", element: <Home /> },
  { path: "/users/:id", element: <UserPage /> },
];

function App() {
  return (
    <BrowserRouter>
      {useRoutes(routeObjects)}  {/* same tree, still classic provider */}
    </BrowserRouter>
  );
}

// Step 2: swap the provider — the route tree itself is unchanged
const router = createBrowserRouter(routeObjects);
function App() {
  return <RouterProvider router={router} />;
}

// Step 3 (only after the cutover is stable): start adding loaders/actions per route

Senior Engineer Perspective

What distinguishes a thoughtful migration plan: recognizing the provider swap is genuinely a hard cutover (not gradual), and de-risking it by first doing the object-shape refactor under the OLD provider where it's easy to verify nothing changed, so the actual provider swap is a minimal, mechanical, low-risk final step rather than one giant simultaneous change.

Q87. When should a team reach for Next.js/Remix's router instead of React Router in a plain SPA?

ROI: ★★★★ Frequency: High

Short Answer

Reach for a meta-framework's router when SEO, first-paint performance, or server-driven data fetching are core product requirements — public marketing pages, content sites, storefronts. Stay on plain React Router when the app is entirely behind auth, when you need maximum control over the build/deploy pipeline, or when the team has deep existing SPA infrastructure a framework migration would disrupt for little practical benefit.

Detailed Answer

The decision compounds with existing constraints: a team already deployed on a static CDN with no server runtime pays a real infrastructure cost adopting SSR. A team that has invested heavily in a custom build pipeline may find a framework's opinions actively fight their setup. Conversely, a greenfield public-facing product gets SSR/streaming/SEO essentially for free by starting on a framework, and retrofitting that onto a mature SPA later is far more expensive than choosing it up front.

Code Example

// Decision checklist (talk through, not code to memorize):
// 1. Does this app need to rank in search engines or have fast first paint for anonymous users?
//    -> Yes: lean framework (Next.js App Router / React Router 7 framework mode)
// 2. Is the entire app behind auth, with no public/SEO-relevant pages?
//    -> Yes: plain React Router SPA is simpler and sufficient
// 3. Is there an existing large SPA with significant custom infra?
//    -> Migrating wholesale is expensive; weigh against incremental SSR only where it matters

Senior Engineer Perspective

Interviewers are testing for pragmatic, context-aware reasoning rather than a framework preference. The strongest answers bring up sunk infrastructure cost and migration risk as real factors, not just greenfield feature comparisons — architecture decisions in a mature codebase are rarely "which is technically superior in a vacuum."

Q88. How do you decide route structure for a large app with many teams (micro-frontends, module federation)?

ROI: ★★★ Frequency: Medium

Short Answer

Draw route ownership boundaries along the same lines as team/domain boundaries — each team owns a top-level path prefix (/billing/*, /inventory/*) as a self-contained route subtree, ideally lazy-loaded and independently deployable (e.g. via module federation) so one team's release doesn't require coordinating a deploy with every other team.

Detailed Answer

A shell app typically owns the top-level router and global chrome (auth, nav shell), while each domain team's routes are registered as a lazily-loaded subtree under their own path prefix — often literally a separately built and deployed bundle exposed through module federation, so the routing layer becomes the seam where independently-shipped applications compose into one experience. This mirrors the "one concern per nesting level" principle from earlier, just applied at an organizational rather than a purely technical level.

Code Example

// Shell app owns the top-level router; each team's app is a lazily-loaded remote
const router = createBrowserRouter([
  { element: <AppShell />, children: [
    { path: "billing/*", lazy: () => import("billingApp/routes") },     // team A, own deploy
    { path: "inventory/*", lazy: () => import("inventoryApp/routes") }, // team B, own deploy
  ]},
]);

Senior Engineer Perspective

This question is really about organizational scaling, and interviewers who ask it are checking whether you've operated in a multi-team codebase, not just a single-team app. The signal to give: route prefixes as team ownership boundaries let deploys and releases decouple, which is usually the actual business reason micro-frontend architectures get adopted, more so than any purely technical routing concern.

Q89. What are the performance implications of a very large, deeply nested route tree?

ROI: ★★★ Frequency: Medium

Short Answer

Route matching itself (checking a URL against hundreds of route definitions) is rarely the bottleneck — React Router's matcher is efficient even at real-world scale. The actual performance risk is in what each route pulls into the bundle: an unsplit giant route config file, or a tree where every route eagerly imports its component instead of using lazy, means the "route config" itself becomes a large synchronous import even before any page-specific code runs.

Detailed Answer

Where large trees genuinely hurt: if route definitions (not their lazy-loaded components) import heavy dependencies at the top of the same file — e.g. a shared "all routes" file that statically imports every page component for convenience — you accidentally bundle the whole app into one chunk regardless of how well-organized the nesting looks. The fix is always the same discipline from the code-splitting section: keep route definitions lightweight, and let each route's actual component/data code live behind its own lazy import.

Code Example

// Anti-pattern: the route config file itself statically imports everything
import Dashboard from "./Dashboard";
import Billing from "./Billing";
import Inventory from "./Inventory"; // ...and 50 more — all now in one bundle regardless of route

// Better: the route config stays tiny; each route's real code is behind its own dynamic import
const routes = [
  { path: "/dashboard", lazy: () => import("./Dashboard") },
  { path: "/billing", lazy: () => import("./Billing") },
  { path: "/inventory", lazy: () => import("./Inventory") },
];

Senior Engineer Perspective

The correction interviewers want you to make: people assume "large route tree" means "slow matching," when the real-world performance risk is almost always accidental bundle bloat from how routes are defined, not the matching algorithm itself. Naming that distinction directly signals you've actually profiled a real app rather than reasoning about it in the abstract.

Q90. How do you version and evolve URL structures without breaking bookmarks and external links?

ROI: ★★★★ Frequency: High

Short Answer

Treat URLs as a public API with a backward-compatibility contract: when you rename or restructure a path, add a redirect route from the old path to the new one rather than simply deleting the old route, and keep those redirects around indefinitely for anything that could plausibly be bookmarked, shared, or indexed by search engines.

Detailed Answer

The cost of skipping this is invisible until it isn't: old bookmarks, shared Slack links, email links, and search-engine-indexed URLs all silently 404 the moment a path changes without a redirect. A catch-all path="*" 404 page catches the symptom but doesn't fix the underlying broken link — a deliberate redirect route for each renamed/moved path is the actual fix, and is cheap to add compared to the cost of every user who follows an old link hitting a dead end.

Code Example

const router = createBrowserRouter([
  { path: "/settings/profile", element: <ProfileSettings /> }, // new canonical path

  // Old path preserved as a redirect, not deleted — protects bookmarks/external links
  { path: "/account/profile", element: <Navigate to="/settings/profile" replace /> },

  // Or, in a loader-driven redirect for a param-carrying old route:
  {
    path: "/users/:id/edit",     // old
    loader: ({ params }) => redirect(`/settings/users/${params.id}`), // new
  },
]);

Senior Engineer Perspective

The framing that separates senior candidates: "URLs are a public API contract, and breaking them silently breaks every bookmark, shared link, and search index entry pointing at the old path." A concrete, memorable line to use: never delete a route people could have linked to — replace it with a redirect, and only remove the redirect itself after a long, deliberate deprecation window, if ever.
