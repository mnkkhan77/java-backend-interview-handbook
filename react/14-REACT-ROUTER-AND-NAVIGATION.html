SECTION 1 - ROUTING BASICS

Q1. How does client-side routing differ from server-side routing in a single-page app?

ROI: ★★★★★ Frequency: Extremely High

Short Answer

With server-side routing, every URL change triggers a full HTTP request and the server returns a brand-new HTML document. With client-side routing, JavaScript intercepts navigation, updates the URL via the History API (pushState), and swaps the rendered component tree without a full page reload. React Router is a client-side router: one HTML shell is loaded once, then routing happens in the browser.

Detailed Answer

A traditional multi-page app maps each URL to a document on the server. Clicking a link means: request → server renders HTML → browser tears down the current page and paints a new one. State is lost between navigations, and the network round-trip is visible as a flash/reload.

A single-page app loads one shell document plus a JS bundle. React Router registers a listener on the History API and on link clicks. When you navigate, it:

  • Prevents the browser's default full-page navigation.
  • Calls history.pushState to change the URL bar without a request.
  • Matches the new URL against your route config and renders the matching component.

The popstate event lets the router respond to the browser's Back/Forward buttons so navigation still feels native. This gives instant transitions and preserves in-memory state (e.g. a form, a cart), at the cost of a larger initial JS payload and the need for SEO/first-paint strategies like SSR.

BrowserRouter vs HashRouter

RouterURL formWhen to use
BrowserRouter/users/42Default. Needs server configured to serve index.html for all paths (SPA fallback).
HashRouter/#/users/42Static hosting with no server rewrite control; the part after # is never sent to the server.

Code Example

// The server MUST fall back to index.html for unknown paths,
// otherwise a hard refresh on /users/42 returns a 404.

// Example: Vite / Express SPA fallback
app.get("*", (req, res) => {
  res.sendFile(path.join(__dirname, "dist", "index.html"));
});

// vercel.json rewrite for an SPA
{
  "rewrites": [{ "source": "/(.*)", "destination": "/index.html" }]
}

Project Example

In a dashboard app, moving between /overview and /reports feels instant and keeps the sidebar mounted. The classic bug: it works in dev but a production refresh on a deep link 404s — because the static host wasn't configured with the SPA fallback rewrite.

Senior Engineer Perspective

The interviewer wants to hear the History API named explicitly and the SPA-fallback gotcha. A strong answer also notes the trade-offs client routing forces: SEO and first-contentful-paint suffer because the initial HTML is empty, which is exactly why frameworks like Next.js and Remix add SSR/streaming on top of a router. Mention that pushState vs replaceState controls whether an entry is added to the history stack — relevant for redirects.

Q2. How do you set up React Router v6+ — Routes/Route vs createBrowserRouter?

ROI: ★★★★★ Frequency: Extremely High

Short Answer

There are two idioms. The classic JSX approach wraps the app in <BrowserRouter> and declares <Routes> with nested <Route> elements. The newer data router (v6.4+) uses createBrowserRouter with a route-object array and a <RouterProvider>, which unlocks loaders, actions, and errorElement. New apps should prefer the data router.

Detailed Answer

Both describe the same route tree; the difference is what capabilities you get. <Routes>/<Route> is purely declarative rendering. The data router lets React Router own data fetching and mutations before a component renders, which is why loaders/actions only exist there.

Feature<BrowserRouter> + <Routes>createBrowserRouter
Loaders / actionsNoYes
errorElement + useRouteErrorNoYes
Route config shapeJSX elementsPlain objects (or JSX via helper)
Best forSimple/legacy appsNew apps, data-driven routing

Code Example

// --- Classic JSX approach ---
import { BrowserRouter, Routes, Route } from "react-router-dom";

function App() {
  return (
    <BrowserRouter>
      <Routes>
        <Route path="/" element={<Home />} />
        <Route path="/users/:id" element={<UserPage />} />
      </Routes>
    </BrowserRouter>
  );
}

// --- Data router (v6.4+, recommended) ---
import { createBrowserRouter, RouterProvider } from "react-router-dom";

const router = createBrowserRouter([
  { path: "/", element: <Home /> },
  {
    path: "/users/:id",
    element: <UserPage />,
    loader: async ({ params }) => fetchUser(params.id),
    errorElement: <RouteError />,
  },
]);

export default function App() {
  return <RouterProvider router={router} />;
}

Project Example

Migrating an admin panel from <Routes> to createBrowserRouter let us move per-page fetches into loaders, so the page component received ready data via useLoaderData and we deleted a pile of in-component useEffect + loading-flag boilerplate.

Senior Engineer Perspective

Interviewers probe whether you know why the data router exists, not just that it does. Key line: loaders/actions/errorElement are only available under createBrowserRouter/RouterProvider because the router needs to control the render lifecycle to fetch before rendering and to catch thrown responses. Note also that React Router 7 merges Remix, so the data router idiom is the future direction — a good detail to drop.

Q3. How do route params work, and how do you read them with useParams?

ROI: ★★★★★ Frequency: Extremely High

Short Answer

A colon segment in a path (/users/:id) is a dynamic param. React Router matches any value in that position and exposes it via the useParams() hook as a string keyed by the param name. Params are always strings, so coerce numbers yourself.

Detailed Answer

You can have multiple params (/org/:orgId/users/:userId) and optional params in v6.4+ using a trailing ? (/files/:name?). A * segment is a "splat"/catch-all that captures the rest of the path, useful for nested file-tree style routes and 404s.

Because every param is a string, validate and convert. A common defect is passing a string id where an API or numeric comparison expects a number.

Code Example

import { useParams } from "react-router-dom";

// Route: <Route path="/users/:id" element={<UserPage />} />
function UserPage() {
  const { id } = useParams();          // id: string | undefined
  const userId = Number(id);
  if (Number.isNaN(userId)) return <NotFound />;
  // ...fetch by userId
}

// TypeScript: type the params
const { orgId, userId } = useParams<{ orgId: string; userId: string }>();

// Splat / catch-all
// <Route path="/docs/*" element={<Docs />} />
// useParams()["*"] holds the remaining path segment

Senior Engineer Perspective

The trap here is the "params are strings" gotcha and forgetting that useParams returns string | undefined in TypeScript even when the route guarantees the param — because the type can't know which route rendered the component. Seniors validate/parse and handle the malformed-id case rather than trusting the URL. Mention that changing only the param (e.g. /users/1 → /users/2) reuses the same component instance, so data-fetching effects must key on the param or you'll show stale data.

SECTION 2 - DYNAMIC & NESTED ROUTES

Q4. What are nested routes and how does Outlet render child routes?

ROI: ★★★★★ Frequency: Extremely High

Short Answer

Nested routes let a parent route render shared UI while a child route fills a placeholder. The parent component renders <Outlet />, and React Router substitutes the matched child route's element there. This composes URLs and UI together: /dashboard renders the dashboard layout, /dashboard/settings renders that layout with the settings panel in the outlet.

Detailed Answer

Outlet is the nested-routing equivalent of children. The parent stays mounted across child navigations, so shared state (open sidebar, tab selection) persists. Child paths are relative — a child path="settings" under path="/dashboard" resolves to /dashboard/settings. Deeply nested trees can chain outlets at each level.

Code Example

import { Outlet } from "react-router-dom";

function DashboardLayout() {
  return (
    <div className="dashboard">
      <Sidebar />
      <main>
        <Outlet />   {/* child route renders here */}
      </main>
    </div>
  );
}

const router = createBrowserRouter([
  {
    path: "/dashboard",
    element: <DashboardLayout />,
    children: [
      { index: true, element: <Overview /> },       // /dashboard
      { path: "settings", element: <Settings /> },   // /dashboard/settings
      { path: "users/:id", element: <UserDetail /> }, // /dashboard/users/42
    ],
  },
]);

Project Example

A settings area with a persistent left-nav (Profile / Billing / Security) is a textbook nested-route case: one SettingsLayout with an <Outlet />, and each tab is a child route. The nav highlight and scroll position of the layout survive tab switches.

Senior Engineer Perspective

A frequent mistake is forgetting the <Outlet /> — the child route matches but nothing renders. Another is using absolute paths for children (leading slash), which breaks the nesting. Seniors emphasise that the parent persisting across child navigations is the whole point: it's how you avoid re-mounting expensive layout shells and losing state.

Q5. What is an index route and when do you need one?

ROI: ★★★★ Frequency: High

Short Answer

An index route is the default child rendered into a parent's <Outlet /> when the URL matches the parent exactly with no further segment. You declare it with index: true (or <Route index />) instead of a path. It answers "what shows at /dashboard itself?"

Detailed Answer

Without an index route, visiting the parent path renders the layout with an empty outlet. The index route fills that gap. It has no path of its own — it shares the parent's URL. You cannot give an index route a path; that's a common syntax error.

Code Example

<Route path="/dashboard" element={<DashboardLayout />}>
  <Route index element={<Overview />} />        {/* /dashboard */}
  <Route path="reports" element={<Reports />} /> {/* /dashboard/reports */}
</Route>

Senior Engineer Perspective

Interviewers use this to check you understand outlet defaults. Contrast the index route with a redirect: some teams redirect /dashboard → /dashboard/overview using <Navigate> instead of an index route. Both work; the index route keeps the canonical URL clean, while the redirect makes the landing tab explicit in the URL.

SECTION 3 - NAVIGATION

Q6. What is the difference between Link, NavLink, and useNavigate?

ROI: ★★★★★ Frequency: Extremely High

Short Answer

Link renders an accessible anchor that does client-side navigation on click. NavLink is a Link that knows whether it points to the active route, so you can style the current nav item. useNavigate returns an imperative function to navigate from code (after a submit, on a timer, in an effect).

Detailed Answer

Prefer Link/NavLink for anything a user clicks: they render a real <a href>, so middle-click/open-in-new-tab, right-click, and screen readers all work. useNavigate is for programmatic transitions where there's no natural anchor. Never fake navigation with an onClick on a div — you lose accessibility and SEO.

NavLink exposes an isActive (and isPending in the data router) flag through a render-prop-style className/style function.

Code Example

import { Link, NavLink, useNavigate } from "react-router-dom";

// Simple link
<Link to="/users/42">View user</Link>

// Active-aware nav item
<NavLink
  to="/reports"
  className={({ isActive }) => (isActive ? "tab tab--active" : "tab")}
>
  Reports
</NavLink>

// Programmatic navigation after an action
function LoginForm() {
  const navigate = useNavigate();
  async function onSubmit(data) {
    await login(data);
    navigate("/dashboard", { replace: true }); // no back-to-login
  }
}

Senior Engineer Perspective

The accessibility point separates seniors: Link renders a semantic anchor, so don't reinvent it with click handlers. Follow-up traps: navigate(-1) for back, and the { replace: true } option to avoid trapping users in a back-button loop after redirects (e.g. after login or a successful form submit). Mention that NavLink matches by prefix for nested paths unless you pass end, a classic "why is my Home tab always active?" bug.

Q7. How do you perform programmatic navigation and redirects?

ROI: ★★★★ Frequency: High

Short Answer

In components, call the function from useNavigate(): navigate("/path"), navigate(-1) to go back, or navigate(to, { replace: true, state }). Declaratively you render <Navigate to="/login" replace />. In loaders/actions you throw or return redirect("/login"), which is the correct place for auth redirects in the data router.

Detailed Answer

  • useNavigate — imperative, for event handlers and effects.
  • <Navigate> — declarative, render it conditionally to redirect during render.
  • redirect() — for loaders/actions; returns a Response the router honours before rendering.

Use replace to overwrite the current history entry instead of pushing a new one — essential so the Back button doesn't return the user to a page they were redirected away from. You can pass state to carry data (e.g. the originally requested URL) without exposing it in the URL.

Code Example

// Declarative redirect during render
if (!user) return <Navigate to="/login" replace />;

// Imperative, carrying "where they wanted to go"
const navigate = useNavigate();
const location = useLocation();
navigate("/login", { replace: true, state: { from: location.pathname } });

// In a data-router loader/action (preferred for auth):
import { redirect } from "react-router-dom";
export async function loader() {
  const user = await getUser();
  if (!user) throw redirect("/login");
  return user;
}

Senior Engineer Perspective

The nuance interviewers hunt for: don't call navigate() directly in the render body — it must run in an effect or event handler, or you'll get warnings and re-render loops; for render-time redirects use <Navigate>. And in the data router, redirecting inside a loader beats redirecting inside the component because it happens before any render, avoiding a flash of protected content.

Q8. How do you read and update query params with useSearchParams?

ROI: ★★★★ Frequency: High

Short Answer

useSearchParams() returns a [searchParams, setSearchParams] pair, analogous to useState but backed by the URL. searchParams is a read-only URLSearchParams object; setSearchParams updates the query string (and thus navigates). It's the right tool for filters, pagination, sort order, and tabs you want shareable and bookmarkable.

Detailed Answer

Because state lives in the URL, it survives refresh, is shareable, and participates in the back/forward history. Read with searchParams.get("q") (returns string | null). Write by passing an object or a URLSearchParams; pass { replace: true } for high-frequency updates (like a search-as-you-type box) so you don't flood the history stack.

Code Example

import { useSearchParams } from "react-router-dom";

function ProductList() {
  const [searchParams, setSearchParams] = useSearchParams();
  const page = Number(searchParams.get("page") ?? "1");
  const q = searchParams.get("q") ?? "";

  function onSearch(text) {
    // functional update preserves other params
    setSearchParams(prev => {
      prev.set("q", text);
      prev.set("page", "1");
      return prev;
    }, { replace: true });
  }

  return <input value={q} onChange={e => onSearch(e.target.value)} />;
}

Senior Engineer Perspective

Interviewers probe whether you keep filter state in the URL rather than local useState — URL state is the "single source of truth" that makes links shareable and back-button correct. Traps: values are always strings (coerce), and blindly replacing the whole search string wipes unrelated params — use the functional updater or spread existing entries. For rapid updates, debounce and use replace to keep history clean.

Q9. What does useLocation give you and when do you need it?

ROI: ★★★ Frequency: Medium

Short Answer

useLocation() returns the current location object: pathname, search, hash, state, and a unique key. It's how you react to URL changes (analytics page-views), read navigation state, or remember where a user came from before a redirect.

Detailed Answer

Common uses: firing a page-view analytics event in an effect keyed on location.pathname; reading location.state?.from to send a user back after login; and driving scroll restoration. The key is a stable id per history entry, handy for animations and per-page scroll memory.

Code Example

import { useLocation } from "react-router-dom";
import { useEffect } from "react";

function usePageViews() {
  const location = useLocation();
  useEffect(() => {
    analytics.track("page_view", { path: location.pathname + location.search });
  }, [location.pathname, location.search]);
}

// After login, return the user to where they were
const location = useLocation();
const from = location.state?.from ?? "/dashboard";
navigate(from, { replace: true });

Senior Engineer Perspective

The subtlety: depend on location.pathname/search, not the whole location object, when you only care about the URL — otherwise a new key on identical URLs can retrigger effects. Seniors also know location.state is ephemeral (it lives in the history entry, not the URL) so it survives back/forward but is gone on a fresh load — don't rely on it for anything critical.

SECTION 4 - DATA & GUARDS

Q10. How do you build a protected/guarded route with an auth redirect?

ROI: ★★★★★ Frequency: Extremely High

Short Answer

Two patterns. In the classic router, wrap protected routes in a guard component that checks auth and either renders <Outlet /> or <Navigate to="/login" />. In the data router, do the check in a loader and throw redirect("/login") — this runs before render, avoiding a flash of protected content.

Detailed Answer

The guard-component pattern uses a layout route: the guard is the parent element and all protected pages are its children, so one check covers the whole subtree. Capture the requested URL in location so you can return the user there after login.

Remember client-side guards are a UX convenience, not security — the API must authorize every request independently. A savvy user can bypass client routing.

Code Example

// --- Guard component (classic) ---
function RequireAuth() {
  const { user } = useAuth();
  const location = useLocation();
  if (!user) {
    return <Navigate to="/login" replace state={{ from: location }} />;
  }
  return <Outlet />;
}

<Route element={<RequireAuth />}>
  <Route path="/dashboard" element={<Dashboard />} />
  <Route path="/settings" element={<Settings />} />
</Route>

// --- Loader guard (data router, preferred) ---
async function protectedLoader({ request }) {
  const user = await getUser();
  if (!user) {
    const url = new URL(request.url);
    throw redirect("/login?next=" + encodeURIComponent(url.pathname));
  }
  return user;
}

Senior Engineer Perspective

The line that lands: "client-side route guards are UX, not security — the server must still authorize." Follow-ups probe the flash-of-content problem (loader redirect solves it because it runs before render) and the redirect-back-after-login flow (store the intended URL in state or a ?next= param). Also mention handling the loading state while auth is being determined, so you don't bounce the user to /login before the session resolves.

Q11. What are loaders and actions in the v6.4+ data router?

ROI: ★★★★ Frequency: High

Short Answer

A loader is a per-route async function that fetches data before the route renders; the component reads it with useLoaderData(). An action handles mutations (form submits) for that route and is invoked by <Form>/useSubmit. Together they move data fetching and mutation out of components and into the route layer, eliminating fetch-on-render waterfalls.

Detailed Answer

Because loaders run in parallel as soon as a navigation starts (not after a component mounts), you avoid the classic useEffect fetch waterfall and its loading-flag/race-condition boilerplate. React Router revalidates loaders automatically after an action succeeds, keeping the UI in sync with mutations. useNavigation() exposes the pending state for global spinners/optimistic UI.

Code Example

import { useLoaderData, Form, redirect } from "react-router-dom";

const router = createBrowserRouter([
  {
    path: "/users/:id",
    element: <UserPage />,
    loader: async ({ params }) => {
      const res = await fetch("/api/users/" + params.id);
      if (!res.ok) throw new Response("Not Found", { status: 404 });
      return res.json();
    },
    action: async ({ request, params }) => {
      const form = await request.formData();
      await updateUser(params.id, Object.fromEntries(form));
      return redirect("/users/" + params.id); // triggers revalidation
    },
  },
]);

function UserPage() {
  const user = useLoaderData();      // data is already here — no loading flag
  return (
    <Form method="post">
      <input name="name" defaultValue={user.name} />
      <button>Save</button>
    </Form>
  );
}

Senior Engineer Perspective

Interviewers want the "why": loaders kick off fetching at navigation time, so parallel routes load together and you avoid render-triggered waterfalls. Be ready to compare with TanStack Query — loaders are great for route-critical data and integrate with caching libraries (you can call the query client inside a loader). A thrown Response is caught by the nearest errorElement, which is how loaders surface 404s and failures cleanly.

Q12. How do errorElement and useRouteError handle route-level errors?

ROI: ★★★★ Frequency: High

Short Answer

In the data router, if a loader/action throws or a component errors during render, React Router renders the nearest route's errorElement instead of the normal element. Inside it, useRouteError() returns the thrown value. This is a route-scoped error boundary that also handles thrown Response objects (e.g. 404/500).

Detailed Answer

Errors bubble to the closest ancestor route that defines an errorElement, so you can have a granular boundary per section and a catch-all at the root. Use isRouteErrorResponse(error) to distinguish a thrown HTTP-style Response (with status/statusText) from an unexpected JS Error, and render 404 vs generic-crash UI accordingly.

Code Example

import { useRouteError, isRouteErrorResponse } from "react-router-dom";

function RouteError() {
  const error = useRouteError();
  if (isRouteErrorResponse(error)) {
    if (error.status === 404) return <h1>Page not found</h1>;
    return <h1>{error.status} {error.statusText}</h1>;
  }
  return <h1>Something went wrong</h1>;
}

const router = createBrowserRouter([
  {
    path: "/",
    element: <Root />,
    errorElement: <RouteError />,   // catches errors from Root and its children
    children: [/* ... */],
  },
]);

Senior Engineer Perspective

The distinction interviewers want: errorElement replaces manual <ErrorBoundary> plumbing for route-level failures and, crucially, catches loader/action errors — which a regular React error boundary cannot, because they happen outside render. Put a root-level errorElement as a safety net and add finer boundaries where you want to keep the surrounding layout alive. Mention isRouteErrorResponse to branch on HTTP status.

SECTION 5 - ADVANCED

Q13. What are layout routes and how do they reduce duplication?

ROI: ★★★★ Frequency: High

Short Answer

A layout route is a parent route with an element (rendering shared chrome + an <Outlet />) but often no path of its own — a "pathless" route. It groups children under a common layout or guard without adding a URL segment, so you define shared UI once.

Detailed Answer

Pathless layout routes are ideal for: an authenticated shell vs a public shell, a marketing layout vs an app layout, or wrapping a group of routes in one guard. Because the layout route contributes no path segment, /dashboard and /settings can share a layout without becoming /app/dashboard. You can nest multiple layout routes for compound chrome.

Code Example

const router = createBrowserRouter([
  {
    element: <AuthenticatedLayout />,   // pathless: no `path`
    loader: protectedLoader,             // one guard for the whole group
    children: [
      { path: "/dashboard", element: <Dashboard /> },
      { path: "/settings", element: <Settings /> },
    ],
  },
  {
    element: <PublicLayout />,
    children: [
      { path: "/login", element: <Login /> },
      { path: "/about", element: <About /> },
    ],
  },
]);

Senior Engineer Perspective

The insight interviewers reward: a layout route can be pathless, letting you share chrome and guards across sibling URLs without polluting the path. Combined with a loader on the layout route, it's the cleanest way to protect an entire section with one check. Contrast with just importing a Layout component into each page — the route approach keeps the layout mounted across child navigations and centralises the guard.

Q14. How do you lazy-load routes for code splitting?

ROI: ★★★★ Frequency: High

Short Answer

Split each route into its own bundle so the initial download is small. Classically you use React.lazy() + <Suspense> around the routed component. In the data router you use the route's lazy property, which can code-split the element, loader, and action together and doesn't require a Suspense wrapper.

Detailed Answer

Route-based splitting is the highest-impact place to code-split: users only download the JS for pages they visit. With React.lazy, wrap the lazy element in <Suspense fallback>. With the data-router lazy option, the module exports the route pieces and React Router loads them on demand while showing pending UI via useNavigation. Pair with Await/defer for streaming slow data.

Code Example

// --- React.lazy + Suspense ---
import { lazy, Suspense } from "react";
const Reports = lazy(() => import("./Reports"));

<Route
  path="/reports"
  element={
    <Suspense fallback={<Spinner />}>
      <Reports />
    </Suspense>
  }
/>

// --- Data-router lazy (splits element + loader together) ---
{
  path: "/reports",
  lazy: async () => {
    const { Reports, reportsLoader } = await import("./reports");
    return { element: <Reports />, loader: reportsLoader };
  },
}

Senior Engineer Perspective

Interviewers check that you split at the route boundary (best cost/benefit) and that you handle the loading fallback. Advanced follow-ups: prefetch the next likely bundle on link hover/focus to hide the network cost, and be careful not to over-split (too many tiny chunks add request overhead). Note the data-router lazy is superior for routes because it also splits the loader/action, not just the component.

Q15. How do you handle scroll restoration and 404s in React Router?

ROI: ★★★★ Frequency: High

Short Answer

SPAs don't reset scroll on navigation the way the browser does for full page loads. Render <ScrollRestoration /> (data router) to restore/reset scroll per navigation. For 404s, add a catch-all route with path="*" that renders your NotFound component; in loaders, throw new Response(..., { status: 404 }) to hit the error UI.

Detailed Answer

ScrollRestoration restores position on back/forward and scrolls to top on new navigations; you can customise with getKey (e.g. key by pathname so filter changes don't reset scroll). Without the data router, a small useEffect-on-pathname that calls window.scrollTo(0,0) is the manual equivalent.

The catch-all path="*" must be the last/lowest-priority match. Use it for a friendly 404 page and analytics on broken links.

Code Example

import { ScrollRestoration } from "react-router-dom";

function Root() {
  return (
    <>
      <Outlet />
      <ScrollRestoration />  {/* render once at the top of the tree */}
    </>
  );
}

// 404 catch-all — keep it last
const router = createBrowserRouter([
  { path: "/", element: <Root />, children: [
    { index: true, element: <Home /> },
    { path: "*", element: <NotFound /> },   // matches anything unmatched
  ]},
]);

// Manual scroll reset without the data router
useEffect(() => { window.scrollTo(0, 0); }, [pathname]);

Senior Engineer Perspective

The gotcha seniors call out: scroll restoration is a real UX gap in SPAs because the browser's native restore doesn't fire without full loads. Know that ScrollRestoration's getKey lets you preserve scroll across param-only changes. For 404s, distinguish "no route matched" (path="*") from "route matched but the resource doesn't exist" (loader throws a 404 Response to the errorElement) — they're different failures with different UX.

Q16. How does React Router compare with Next.js file-based routing?

ROI: ★★★★ Frequency: High

Short Answer

React Router uses an explicit, code-defined route config and is primarily client-side (a library you add to any React app). Next.js infers routes from the filesystem — files/folders in app/ (or pages/) become routes — and is a full framework with built-in SSR, RSC, and server data fetching. React Router = flexible library; Next.js = opinionated framework with routing baked in.

Conceptually they've converged: Next's layout.tsx + page.tsx mirror layout routes + index routes, and Next's Server Component data fetching parallels React Router's loaders. React Router 7 (which merges Remix) narrows the gap further by offering SSR and file-based conventions as an option.

Senior Engineer Perspective

Interviewers want a framework-vs-library framing, not tribalism. Pick React Router when you have an existing CSR SPA or need routing without adopting a whole framework; pick Next.js when you want SSR/RSC, SEO, and file conventions out of the box. The strongest answer notes the convergence — loaders ≈ server data fetching, <Outlet /> ≈ layout.tsx — and that React Router 7 blurs the line by absorbing Remix's server-side capabilities.
