09 - STATE MANAGEMENT

Target Audience: Frontend / React Engineer (3–6 Years) Goal: Not just answer questions, but survive follow-up grilling from experienced interviewers.

State management is the topic where interviewers separate people who "reach for Redux by reflex" from engineers who first ask what kind of state is this? The single most valuable insight in this chapter is that "state" is not one thing — local UI state, global client state, server cache, URL state and form state each have a different lifecycle and a different correct tool. Most bloated, hard-to-debug React apps are the result of forcing all five categories into one global store. Modern React (18/19) plus a small purpose-built store (Zustand/Jotai) plus a server-cache library (TanStack Query) has made "everything in Redux" an anti-pattern for greenfield apps — but you must be able to explain Redux precisely, because it still runs enormous production codebases.

SECTION 1 - STATE CATEGORIES

Q1. What are the different categories of state in a React app, and how do you match a tool to each?

ROI: ★★★★★ Frequency: Extremely High

Short Answer

State falls into roughly five categories: local/UI state (a toggle, an input's value), global client state (theme, auth session, cart), server state (data fetched from an API), URL state (filters, page number, selected tab) and form state. Each has a different lifecycle, so each has a different correct tool. The senior move is to categorize the state first, then pick the tool — not the other way around.

Detailed Answer

Treating all state as one uniform blob is the root cause of most over-engineered React apps. Once you separate the categories, the tool choices become almost obvious:

CategoryExamplesLifecycleRecommended tool
Local / UIDropdown open, hover, input value, current stepLives and dies with the componentuseState / useReducer
Global clientTheme, auth user, feature flags, cartApp-wide, changes rarelyContext (rare change) or Zustand/Jotai/Redux
ServerProduct list, profile, dashboard dataOwned by the server; a cache on the clientTanStack Query / RTK Query / SWR
URLFilters, sort, page, active tab, search queryShareable, bookmarkable, survives reloadRouter (searchParams) — the URL is the store
FormField values, validation, dirty/touchedEphemeral, high-frequency updatesReact Hook Form / Formik (or local state for tiny forms)

The two categories people most often mishandle are server state (stuffing API responses into Redux and hand-writing loading/error/cache-invalidation logic) and URL state (keeping the active filter in a store instead of the query string, so the page can't be shared or reloaded). Fixing just those two typically deletes most of a legacy global store.

Senior Engineer Perspective

The interviewer is checking whether you default to Redux for everything. A junior answer is "use Redux for global state." A senior answer names the categories and points out that server state is fundamentally different from client state — it's asynchronous, shared between clients, and can become stale, so it needs caching, deduplication and revalidation, not a plain setter. Follow-up trap: "Where does the currently selected row of a table go?" The right answer is usually the URL if it should survive reload/sharing, otherwise local component state — almost never a global store.

Q2. When do you actually need a global store? How do you avoid unnecessary global state?

ROI: ★★★★★ Frequency: Extremely High

Short Answer

You need a global store only when non-trivial client state must be read and written by many components spread across unrelated parts of the tree, and lifting state up plus passing props has become painful. Before reaching for one, exhaust: local state, lifting state up, composition (children), the URL, and a server-cache library. Most "we need global state" situations are actually server state or URL state in disguise.

Detailed Answer

The decision ladder I use, in order:

  1. Can it be local? If only one component and its descendants care, keep it in useState/useReducer. Do not globalize a modal's open flag.
  2. Can I lift it up or compose? If two siblings need it, lift to the nearest common parent. "Prop drilling" three levels is fine; component composition (passing JSX as children) often removes the drilling entirely without any store.
  3. Is it server data? Then it belongs in a query cache, not a store.
  4. Should it be in the URL? Filters, tabs, pagination — put them in searchParams so they're shareable and survive reload.
  5. Only now, for genuinely cross-cutting client state (auth session, theme, cart, a wizard shared across routes), introduce a store.

The cost of unnecessary global state is real: everything becomes implicitly coupled, testing requires provider setup, and you get re-renders and bugs from stale global values. Global state also makes components non-portable — you can't reuse them without dragging the store along.

Senior Engineer Perspective

Interviewers love the follow-up: "Isn't prop drilling a good reason to use Redux?" The strong answer is that prop drilling is usually a component design smell, not a state smell — composition and moving state to where it's actually used solves it more often than a store does. Mentioning that "global state is a liability you pay for on every render and every test" signals maturity. The anti-pattern to call out: apps where 80% of the Redux store is cached API responses that a query library would manage for free.

Q3. Is server data really "state"? Why shouldn't it live in Redux?

ROI: ★★★★★ Frequency: High

Short Answer

Server data isn't state you own — it's a cache of state that lives on the server and can change without your app knowing. Putting it in Redux means you hand-write loading flags, error handling, caching, deduplication, refetching and invalidation. A server-cache library (TanStack Query, RTK Query, SWR) gives you all of that declaratively, so server data usually should not sit in a general-purpose client store.

Detailed Answer

Client state and server state have opposite properties. Client state is synchronous, owned by your app, and only your app can change it. Server state is asynchronous, owned elsewhere, shared across users/tabs, and can go stale the instant you fetch it. Managing it like local state forces you to reinvent an entire caching layer, and it's the single biggest source of Redux boilerplate.

What a query library gives you that a plain store does not:

  • Automatic caching keyed by a query key, with configurable staleness.
  • Request deduplication — ten components asking for the same data trigger one fetch.
  • Background refetching, refetch-on-focus, retries, and pagination/infinite-scroll helpers.
  • Built-in isLoading/isError/data status without manual reducers.
  • Cache invalidation after mutations, plus optimistic updates.

Code Example

// Server state with TanStack Query — no reducers, no loading booleans in a store
import { useQuery, useMutation, useQueryClient } from "@tanstack/react-query";

function useProducts() {
  return useQuery({
    queryKey: ["products"],
    queryFn: () => fetch("/api/products").then((r) => r.json()),
    staleTime: 30_000, // treat data as fresh for 30s
  });
}

function ProductList() {
  const { data, isLoading, isError } = useProducts();
  if (isLoading) return <Spinner />;
  if (isError) return <Error />;
  return <ul>{data.map((p) => <li key={p.id}>{p.name}</li>)}</ul>;
}

Senior Engineer Perspective

This is a modern-thinking litmus test. The phrase "server state is a cache, not state" scores points. The follow-up trap: "But we need the fetched user in fifty components." Answer: keep it in the query cache and read it with useQuery(["me"]) anywhere — it's already global and deduplicated, you don't need to copy it into a store. The only reason to mirror server data into a client store is when you must derive heavy client-side transforms from it, and even then you keep the source of truth in the cache.

SECTION 2 - CONTEXT

Q4. How does the Context API work, and why is it not really a state manager?

ROI: ★★★★★ Frequency: Extremely High

Short Answer

Context is a dependency-injection / transport mechanism: it lets a provider pass a value to any descendant without prop drilling. It does not store or update state by itself — you combine it with useState/useReducer. It has no selectors, so any consumer re-renders whenever the context value changes. That makes it great for low-frequency, app-wide values (theme, locale, auth) and poor for high-frequency updates.

Detailed Answer

Three pieces: createContext creates the channel, a <Context.Provider value={...}> supplies a value to the subtree, and useContext reads the nearest provider's value. The state itself still lives in a hook somewhere; Context just carries it down.

The reason it isn't a full state manager is subscription granularity. When the provider's value changes, every component that calls useContext for that context re-renders — you cannot subscribe to "just the part I care about." Redux, Zustand and Jotai all give you selective subscriptions; Context does not. So Context shines for values that change rarely and are read widely.

Code Example

const ThemeContext = createContext<"light" | "dark">("light");

function App() {
  const [theme, setTheme] = useState<"light" | "dark">("light");
  return (
    <ThemeContext.Provider value={theme}>
      <Toolbar />
      <button onClick={() => setTheme((t) => (t === "light" ? "dark" : "light"))}>
        Toggle
      </button>
    </ThemeContext.Provider>
  );
}

function DeepChild() {
  const theme = useContext(ThemeContext); // no prop drilling
  return <div className={theme}>...</div>;
}

Senior Engineer Perspective

The trap here is the candidate who says "Context replaces Redux." It replaces Redux only for low-frequency global values. Say clearly: "Context solves prop drilling, not performance." A great follow-up answer is that Context and a state manager are orthogonal — libraries like React Redux and Zustand actually use Context internally to hold a stable store reference, then bypass Context's re-render behavior with their own subscription mechanism.

Q5. Why does Context cause re-render storms, and how do you fix them?

ROI: ★★★★★ Frequency: High

Short Answer

Two problems compound. First, a new object/array passed as value on every render is a new reference, so all consumers re-render even when the data is identical — fix by memoizing the value. Second, Context has no selectors, so even a legitimately changed value re-renders every consumer regardless of which field changed — fix by splitting one big context into several small ones (or use a store with selectors).

Detailed Answer

The classic bug: value={{ user, setUser }}. That object literal is recreated on every parent render, so React sees a new context value and re-renders all consumers. Wrap it in useMemo and stabilize functions.

Even with memoization, a single context holding { user, theme, cart } re-renders a component that only reads theme whenever cart changes. Solutions:

  • Split contexts by change frequency and concern — a ThemeContext, an AuthContext, a CartContext — so consumers subscribe only to what they use.
  • Separate state and dispatch into two contexts. Components that only dispatch (never read state) then never re-render when state changes, because dispatch is stable.
  • Memoize the value and wrap leaf components in React.memo.
  • For high-frequency data, don't use raw Context at all — use Zustand/Jotai/Redux, which subscribe at the selector level.

Code Example

// BAD: new object every render -> every consumer re-renders
<UserContext.Provider value={{ user, setUser }}>

// GOOD: memoize the value
const value = useMemo(() => ({ user, setUser }), [user]);
<UserContext.Provider value={value}>

// BETTER: split state and dispatch so dispatch-only consumers stay stable
const StateContext = createContext(null);
const DispatchContext = createContext(null);

function Provider({ children }) {
  const [state, dispatch] = useReducer(reducer, initial);
  return (
    <StateContext.Provider value={state}>
      <DispatchContext.Provider value={dispatch}>{children}</DispatchContext.Provider>
    </StateContext.Provider>
  );
}

Senior Engineer Perspective

Interviewers probe: "Your theme toggle re-renders the whole app — why?" The answer must hit both causes (unstable value reference and lack of selectors). Bonus signal: mention that useContext cannot bail out of a re-render even if the value you read is unchanged — this is a known React limitation, which is exactly why dedicated stores exist. Some teams reach for use-context-selector to add selector semantics to Context, but at that point a real store is usually cleaner.

Q6. How do you build a mini-store with useReducer + Context?

ROI: ★★★★ Frequency: High

Short Answer

Put a useReducer in a provider and expose its state and dispatch through Context (ideally two separate contexts). You get Redux-style predictable, action-driven updates with zero dependencies — perfect for medium-sized, low-to-moderate-frequency global state where you don't want to install a library.

Detailed Answer

The pattern gives you the good parts of Redux — a single reducer describing all transitions, actions as plain objects, and a predictable state shape — while staying inside React. Its ceiling is performance: because it rides on Context, it inherits the "all consumers re-render" behavior, so it's not suited to state that updates many times per second (e.g., dragging, live cursors). For a cart, a multi-step form, or a small feature module, it's an excellent middle ground.

Code Example

type State = { count: number };
type Action = { type: "inc" } | { type: "dec" } | { type: "set"; value: number };

function reducer(state: State, action: Action): State {
  switch (action.type) {
    case "inc": return { count: state.count + 1 };
    case "dec": return { count: state.count - 1 };
    case "set": return { count: action.value };
    default: return state;
  }
}

const StateCtx = createContext<State | null>(null);
const DispatchCtx = createContext<React.Dispatch<Action> | null>(null);

export function CounterProvider({ children }: { children: React.ReactNode }) {
  const [state, dispatch] = useReducer(reducer, { count: 0 });
  return (
    <StateCtx.Provider value={state}>
      <DispatchCtx.Provider value={dispatch}>{children}</DispatchCtx.Provider>
    </StateCtx.Provider>
  );
}

export const useCount = () => useContext(StateCtx)!;
export const useCountDispatch = () => useContext(DispatchCtx)!;

Senior Engineer Perspective

Great answer to "How would you do global state without a library?" Show the two-context split so the interviewer sees you understand the re-render cost. The honest follow-up: "When does this stop scaling?" — when you need memoized selectors, middleware/async orchestration, or the update frequency is high. That's the natural on-ramp to Zustand or Redux Toolkit, and knowing exactly where the wall is signals seniority.

SECTION 3 - REDUX TOOLKIT

Q7. Explain Redux core concepts and unidirectional data flow.

ROI: ★★★★★ Frequency: Extremely High

Short Answer

Redux is a predictable state container built on three principles: a single immutable store as the source of truth, state that is read-only and changed only by dispatching actions (plain objects describing "what happened"), and pure reducers (state, action) => newState that compute the next state. Data flows one way: UI dispatches an action → reducer produces new state → store notifies subscribers → UI re-renders.

Detailed Answer

  • Store: one object tree holding all app state; the single source of truth.
  • Action: a plain object with a type and optional payload, describing an event ("what happened"), not "how to change state."
  • Reducer: a pure function that takes current state + an action and returns the next state without mutating the old one. Purity is what enables time-travel debugging and predictable tests.
  • Dispatch: the only way to trigger a state change — store.dispatch(action).
  • Selector: a function that reads a slice of state for a component.

The strict unidirectional cycle — dispatch → reducer → new state → subscribers → render — is Redux's core value: every change is traceable to an action, so behavior is reproducible and debuggable. That predictability is the reason to accept the ceremony.

Senior Engineer Perspective

Say "actions describe what happened, reducers decide how state changes" — that phrasing shows you grasp the separation. Common trap: "Why must reducers be pure?" Because Redux compares references to detect changes and relies on determinism for dev tools, undo/redo and SSR hydration; a reducer that mutates state or does I/O breaks all of that. Note that raw Redux like this is now considered legacy style — you'd write it with Redux Toolkit (next question).

Q8. What is Redux Toolkit and why is hand-written Redux discouraged now?

ROI: ★★★★★ Frequency: Extremely High

Short Answer

Redux Toolkit (RTK) is the official, batteries-included way to write Redux. It collapses the old boilerplate — action-type constants, action creators, switch-statement reducers, hand-written immutable updates, store setup — into createSlice and configureStore. It uses Immer so you can "mutate" state safely, ships good defaults (Redux DevTools, thunk middleware, serializability checks), and includes RTK Query for data fetching. Hand-written Redux is discouraged because it's verbose, error-prone, and RTK is now the recommended standard.

Detailed Answer

Classic Redux forced you to hand-write and keep in sync: a constant, an action creator, a case in a reducer, and a manual immutable spread — for every action. That's a lot of ceremony and a lot of places to make mistakes. RTK's createSlice auto-generates action creators and action types from your reducer functions, and lets you write mutating-looking code that Immer turns into immutable updates.

configureStore wires up the store with sane defaults: it combines reducers, enables the Redux DevTools extension, adds redux-thunk, and turns on development checks that warn if you accidentally put non-serializable values or mutate state outside a reducer.

Code Example

import { createSlice, configureStore } from "@reduxjs/toolkit";

const counterSlice = createSlice({
  name: "counter",
  initialState: { value: 0 },
  reducers: {
    // "mutating" code — Immer makes it immutable under the hood
    increment: (state) => { state.value += 1; },
    incrementBy: (state, action) => { state.value += action.payload; },
  },
});

export const { increment, incrementBy } = counterSlice.actions;

export const store = configureStore({
  reducer: { counter: counterSlice.reducer },
});

// In a component:
// const value = useSelector((s) => s.counter.value);
// const dispatch = useDispatch();
// dispatch(incrementBy(5));

Senior Engineer Perspective

If a candidate writes 40 lines of ACTION_TYPE constants in 2026, that's a red flag. Interviewers want to hear "RTK is the standard; raw Redux is legacy." The nuance follow-up: "Doesn't state.value += 1 break immutability?" — No, because createSlice wraps reducers in Immer's produce, which records your mutations against a draft and returns a new immutable object. The trap is trying that mutation in a reducer outside RTK, where it's a genuine bug.

Q9. What is immutability in Redux and how does Immer help?

ROI: ★★★★ Frequency: High

Short Answer

Redux requires reducers to return a new state object rather than mutating the existing one, because change detection is done by reference equality (oldState !== newState). Immer lets you write natural "mutating" code against a draft; it tracks the mutations and produces a correctly copied, immutable next state — eliminating fragile deep-spread code and accidental mutation bugs. RTK bakes Immer in by default.

Detailed Answer

Why immutability matters: React and React Redux decide whether to re-render by comparing references. If you mutate state in place, the reference doesn't change, so components don't update — a classic "the store changed but the UI didn't" bug. Immutability also enables time-travel debugging, cheap memoized selectors, and reliable SSR hydration.

The problem is that manual immutable updates for nested data are painful and easy to get wrong:

Code Example

// Manual immutable update — verbose and error-prone for deep nesting
return {
  ...state,
  user: {
    ...state.user,
    address: { ...state.user.address, city: action.payload },
  },
};

// With Immer (what RTK uses): write it like a mutation
import { produce } from "immer";

const next = produce(state, (draft) => {
  draft.user.address.city = action.payload; // safe: Immer copies what changed
});

Senior Engineer Perspective

Follow-up trap: "What actually happens if you mutate Redux state directly?" — the reference stays the same, connected components skip re-rendering, and dev tools/time-travel become unreliable; RTK's serializability/immutability middleware will also warn you in development. Bonus: Immer uses copy-on-write with structural sharing, so unchanged branches of the tree keep the same reference, which is exactly what makes memoized selectors efficient.

Q10. What are selectors, and why do you need reselect / memoized selectors?

ROI: ★★★★ Frequency: High

Short Answer

A selector is a function that extracts a slice of state for a component. If a selector derives data (filters, sorts, computes totals), it returns a new object/array on every call, which defeats reference equality and causes needless re-renders. reselect's createSelector memoizes derived results — it recomputes only when its inputs change — keeping renders cheap and derived logic reusable.

Detailed Answer

Selectors give you two wins: they decouple components from the store's shape (change the shape, update the selector, not every component), and they let you keep derived data out of the store — you store minimal source state and compute the rest. The catch: useSelector re-renders whenever the selected value changes by reference. A selector like (s) => s.items.filter(...) creates a brand-new array each render, so the component re-renders every time anything in the store changes.

createSelector fixes this by caching: given the same inputs, it returns the exact same output reference, so the derived array is stable until its inputs actually change.

Code Example

import { createSelector } from "@reduxjs/toolkit"; // re-exports reselect

const selectItems = (state) => state.cart.items;
const selectFilter = (state) => state.cart.filter;

// Recomputes ONLY when items or filter change
const selectVisibleItems = createSelector(
  [selectItems, selectFilter],
  (items, filter) => items.filter((i) => i.category === filter)
);

// Component: stable reference until inputs change -> no needless re-render
const visible = useSelector(selectVisibleItems);

Senior Engineer Perspective

Interviewers ask: "Your list re-renders on unrelated store changes — why?" The answer is an un-memoized deriving selector returning a new reference. Nuance for senior points: default reselect has a cache size of one, so a selector used by many components with different args can thrash — that's when you reach for createSelector with per-instance memoization or the newer weakMapMemoize. Also note RTK's useSelector supports a custom equality function (e.g., shallowEqual) as an escape hatch.

Q11. What is middleware, and what problem do thunks solve?

ROI: ★★★ Frequency: High

Short Answer

Middleware sits between dispatch and the reducer, letting you intercept actions to add cross-cutting behavior — logging, crash reporting, and especially async work. Reducers must be pure, so they can't do API calls; a thunk is a middleware that lets you dispatch a function instead of a plain object, and that function can run async logic and dispatch real actions when it completes.

Detailed Answer

Because reducers must be pure and synchronous, side effects need a home. Middleware is that home. redux-thunk (included by RTK) is the simplest option: dispatch a function (dispatch, getState) => { ... }, do your fetch, then dispatch success/failure actions. RTK's createAsyncThunk standardizes this, auto-generating pending, fulfilled and rejected action types you handle in extraReducers. For complex async flows (debounce, cancellation, sagas of events) teams sometimes use redux-saga or the RTK listener middleware, but thunks cover most cases.

Code Example

import { createAsyncThunk, createSlice } from "@reduxjs/toolkit";

export const fetchUser = createAsyncThunk("user/fetch", async (id: string) => {
  const res = await fetch(`/api/users/${id}`);
  return res.json();
});

const userSlice = createSlice({
  name: "user",
  initialState: { data: null, status: "idle" },
  reducers: {},
  extraReducers: (builder) => {
    builder
      .addCase(fetchUser.pending,   (s) => { s.status = "loading"; })
      .addCase(fetchUser.fulfilled, (s, a) => { s.status = "done"; s.data = a.payload; })
      .addCase(fetchUser.rejected,  (s) => { s.status = "error"; });
  },
});

Senior Engineer Perspective

The sharp follow-up: "If you're using createAsyncThunk to fetch data, aren't you back to managing server state by hand?" — Yes, and that's precisely why RTK Query (next question) exists. A senior answer positions thunks for orchestration and side effects, not for routine data fetching, which belongs in a caching layer. Knowing middleware is just a store => next => action function chain also demonstrates real depth.

Q12. What is RTK Query, and how does it compare to TanStack Query?

ROI: ★★★★ Frequency: Medium

Short Answer

RTK Query is Redux Toolkit's built-in data-fetching and caching layer. You define an "API slice" with endpoints, and it auto-generates hooks (useGetPostsQuery, useAddPostMutation) that handle caching, deduplication, loading/error state, and tag-based invalidation — storing the cache inside the Redux store. TanStack Query is a framework-agnostic library that does the same job but is independent of Redux. Pick RTK Query if you're already invested in Redux; pick TanStack Query if you're not.

Detailed Answer

Both solve server-state caching declaratively. RTK Query's advantage is integration: cache lives in Redux, so DevTools, middleware and existing slices all interoperate, and there's zero extra state library if you already use RTK. TanStack Query's advantage is that it's lighter-weight to adopt in a non-Redux app, has a very rich feature set (infinite queries, prefetching, offline support), and doesn't require any global store at all.

AspectRTK QueryTanStack Query
Requires ReduxYes (part of the store)No
Cache locationInside the Redux storeIts own QueryClient cache
Invalidation modelTag-basedQuery-key based
Best fitApps already on Redux ToolkitAny app; no store needed

Senior Engineer Perspective

The point that impresses: both tools reflect the industry moving server state out of hand-written reducers. If asked "which would you pick for a new app?", a defensible answer is "TanStack Query for server state plus a small client store (Zustand) if I need one — I only reach for RTK Query when the team has already standardized on Redux." Avoid dogmatism; interviewers want to see you weigh existing investment against greenfield freedom.

SECTION 4 - MODERN STORES

Q13. What is Zustand, and why has it become so popular?

ROI: ★★★★★ Frequency: High

Short Answer

Zustand is a tiny (~1KB) hook-based store. You create a store with create, and components subscribe by passing a selector to the returned hook — so a component re-renders only when the exact slice it selected changes. It has almost no boilerplate (no providers, actions, or reducers required), works outside React, and offers middleware for persistence and devtools. It became popular as the pragmatic middle ground between Context's simplicity and Redux's power.

Detailed Answer

What makes Zustand attractive:

  • Selector subscriptions — the thing raw Context lacks. Reading useStore((s) => s.count) re-renders only when count changes.
  • No provider required — the store is a module-level hook, so there's no tree-wrapping and no Context re-render pitfalls.
  • Minimal boilerplate — state and the functions that update it live together; you call set to update.
  • Middleware — persist, devtools, and Immer integration are opt-in.

Code Example

import { create } from "zustand";

type CounterStore = {
  count: number;
  increment: () => void;
  reset: () => void;
};

const useCounter = create<CounterStore>((set) => ({
  count: 0,
  increment: () => set((s) => ({ count: s.count + 1 })),
  reset: () => set({ count: 0 }),
}));

function Counter() {
  // subscribes ONLY to count -> no re-render when other fields change
  const count = useCounter((s) => s.count);
  const increment = useCounter((s) => s.increment);
  return <button onClick={increment}>{count}</button>;
}

Senior Engineer Perspective

Interviewers ask "Why Zustand over Redux?" — because for pure client state it gives you selective subscriptions and DevTools with a fraction of the code and no boilerplate. But be balanced: Redux's strict action log and huge ecosystem still win for very large teams that need enforced conventions and deep time-travel debugging. Gotcha to mention: selecting an object/array in Zustand needs a shallow-equality comparator (useShallow) or you reintroduce needless re-renders — the same reference-equality lesson as reselect.

Q14. What are atoms? Explain Jotai / Recoil briefly.

ROI: ★★★ Frequency: Medium

Short Answer

Jotai and Recoil use an atomic model: instead of one big store, state is split into many tiny independent units called atoms. A component subscribes to the specific atoms it uses, so only those consumers re-render. Derived atoms compute values from other atoms (like built-in selectors). It's a bottom-up model, in contrast to Redux's single top-down store. Jotai is the actively maintained, minimal choice; Recoil (Meta) is largely unmaintained now.

Detailed Answer

The mental model: an atom is a piece of state you read/write with a hook, and atoms can be composed into derived atoms. Because subscriptions are per-atom, the atomic approach naturally avoids both prop drilling and over-rendering without you writing selectors. It's especially nice for state that's granular and independent (many small pieces) where a single store would either over-render or need lots of selector plumbing.

Code Example

import { atom, useAtom } from "jotai";

const countAtom = atom(0);
const doubledAtom = atom((get) => get(countAtom) * 2); // derived atom

function Counter() {
  const [count, setCount] = useAtom(countAtom);
  const [doubled] = useAtom(doubledAtom);
  return (
    <button onClick={() => setCount((c) => c + 1)}>
      {count} / {doubled}
    </button>
  );
}

Senior Engineer Perspective

You mainly need to articulate the philosophical difference: Redux is top-down (one store, select down into it), atomic libraries are bottom-up (compose small atoms up). If asked which to use, note Recoil is effectively dead (Meta stopped active development), so recommend Jotai if you want the atomic model. Also flag async atoms — Jotai atoms can be async and integrate with Suspense, which is a genuinely elegant feature but adds conceptual overhead.

Q15. Context vs Redux vs Zustand — when do you choose which?

ROI: ★★★★★ Frequency: Extremely High

Short Answer

Use Context for low-frequency, app-wide values (theme, locale, auth) — it's a transport, not a manager. Use Zustand (or Jotai) as the default for real client state that changes often and needs selective subscriptions, with minimal boilerplate. Use Redux Toolkit for large apps or big teams that need strict conventions, a serialized action log, powerful DevTools/time-travel, and a mature ecosystem. And use a query library for server state regardless of which of the above you pick.

A pragmatic 2026 default for a new app: TanStack Query for server state, the URL for URL state, React Hook Form for forms, local useState for UI, and Zustand only if there's genuine cross-cutting client state. Reach for Redux Toolkit when organizational needs (convention enforcement, audit-style action logs, a large existing ecosystem) outweigh its verbosity.

Senior Engineer Perspective

The mistake juniors make is treating these as competitors for the same job. They're not: Context is transport, Redux/Zustand/Jotai are client-state managers, and query libraries are server-state managers. The strongest answer frames the decision around update frequency, team size, and whether the state is really server state. If asked "would you migrate a working Redux app to Zustand?" the mature answer is usually no — there's little ROI in rewriting working code; you choose deliberately for new features.

Q16. How do you persist state across reloads, and what are the traps?

ROI: ★★★ Frequency: Medium

Short Answer

Persistence means saving state to localStorage/sessionStorage/IndexedDB and rehydrating it on load. Every major store has a helper — Zustand's persist middleware, redux-persist for Redux. The traps: never persist sensitive data (tokens) in localStorage, always version and migrate the persisted shape, persist only the slices you need, and beware SSR hydration mismatches because the server has no access to localStorage.

Detailed Answer

Key considerations:

  • Storage choice: localStorage (persists across sessions, ~5MB, synchronous), sessionStorage (per-tab), IndexedDB (large/async). Cookies only if the server needs the value.
  • Security: localStorage is readable by any JS on the page, so it's vulnerable to XSS — never store access tokens or PII there; prefer httpOnly cookies for auth.
  • Versioning & migration: your state shape evolves; persisted old shapes must be migrated or they'll crash or silently corrupt. RTK persist and Zustand persist both support a version and a migrate function.
  • Partial persistence: persist only durable slices (cart, preferences), not transient UI or server cache.
  • SSR: on Next.js the server render can't read localStorage, so naive persistence causes hydration mismatches — gate rehydration to the client or render a stable initial value first.

Code Example

import { create } from "zustand";
import { persist } from "zustand/middleware";

const useSettings = create(
  persist(
    (set) => ({
      theme: "light",
      setTheme: (theme: string) => set({ theme }),
    }),
    {
      name: "settings",              // localStorage key
      version: 2,                    // bump when shape changes
      partialize: (s) => ({ theme: s.theme }), // persist only what you need
      migrate: (persisted, from) => persisted, // handle old versions
    }
  )
);

Senior Engineer Perspective

The follow-up that catches people: "You persisted the auth token in localStorage — what's wrong?" The answer is XSS exposure; tokens belong in httpOnly cookies. The second trap is forgetting migration: shipping a new state shape without a migration silently breaks returning users whose browser still holds the old blob. Mentioning the SSR hydration mismatch shows you've actually shipped persistence in a Next.js app, not just read the docs.
