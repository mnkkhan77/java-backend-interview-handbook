SECTION 1 - HOW THE BROWSER WORKS

Q1. What happens when you type a URL and press Enter?

ROI: ★★★★★ Frequency: Extremely High

Short Answer

The browser resolves the domain via DNS to an IP, opens a TCP connection and negotiates TLS (for HTTPS), sends an HTTP request, receives the HTML response, then parses HTML into the DOM, fetches and applies CSS/JS/images, builds the render tree, lays it out, paints, and composites — while JavaScript can further mutate the page.

Detailed Answer

  1. URL parse — scheme, host, path. Check HSTS (force HTTPS).
  2. DNS resolution — domain → IP, using caches (browser, OS, resolver) before hitting a DNS server.
  3. TCP handshake — SYN / SYN-ACK / ACK (skipped/streamlined with HTTP/3 over QUIC/UDP).
  4. TLS handshake — for HTTPS, negotiate keys and verify the certificate.
  5. HTTP request — browser sends GET with headers (cookies, accept, user-agent).
  6. Server response — status + headers + HTML body (possibly served from a CDN edge).
  7. Parsing & rendering — HTML → DOM, CSS → CSSOM, JS executes (may block), render tree → layout → paint → composite.
  8. Subresources — images, fonts, scripts fetched (respecting caching and priorities).

Senior Engineer Perspective

Interviewers use this as an open-ended depth probe — you can go as deep as you like (DNS caching layers, TCP slow start, TLS 1.3 0-RTT, HTTP/2 multiplexing). Structure the answer in phases and offer to zoom into any. Tie it back to frontend: this is why we use CDNs, preconnect, and SSR — to shorten this chain to first paint.

Q2. Explain the critical rendering path.

ROI: ★★★★★ Frequency: High

Short Answer

The critical rendering path is the sequence the browser follows to turn HTML, CSS, and JS into pixels: parse HTML → DOM, parse CSS → CSSOM, combine into the render tree, compute layout (geometry), paint (pixels per layer), then composite layers to the screen. CSS is render-blocking and synchronous scripts are parser-blocking.

Detailed Answer

  • DOM — HTML parsed into a tree of nodes.
  • CSSOM — CSS parsed into a tree of style rules. CSS is render-blocking: the browser won't paint until it has the CSSOM, to avoid a flash of unstyled content.
  • Render tree — DOM + CSSOM merged, excluding non-visual nodes (display:none, <head>).
  • Layout (reflow) — compute each node's exact size and position.
  • Paint — fill in pixels (text, colors, borders, shadows) per layer.
  • Composite — assemble layers (some GPU-accelerated) into the final image.

To optimize: minimize and inline critical CSS, defer non-critical CSS/JS, use async/defer on scripts, and reduce the number of render-blocking resources so first paint happens sooner.

Senior Engineer Perspective

Connect this to Core Web Vitals: LCP is largely determined by how fast the critical path reaches the largest element. A synchronous <script> in the <head> stalls parsing; that's why bundlers inject scripts with defer and why SSR frameworks inline critical CSS.

Q3. Reflow vs repaint — and how do you minimize them?

ROI: ★★★★☆ Frequency: Medium-High

Short Answer

A reflow (layout) recomputes element geometry (positions/sizes) and is expensive because it can cascade to the whole document. A repaint redraws pixels without changing layout (e.g. color change) — cheaper. Changing transform/opacity can skip both and only re-composite.

Detailed Answer

Reflow is triggered by changing dimensions, position, adding/removing DOM nodes, or reading layout properties after a write (forced synchronous layout / "layout thrashing"). Repaint is triggered by visual-only changes (background, color, visibility). Compositing-only changes (transform, opacity) are the cheapest.

To minimize:

  • Batch DOM reads then writes; avoid interleaving (prevents forced reflow).
  • Animate transform/opacity, not width/top/margin.
  • Change classes instead of many inline style writes.
  • Take heavy DOM work off-screen (document fragment) then insert once.
  • Use content-visibility: auto to skip rendering off-screen content.

Senior Engineer Perspective

In React you rarely touch the DOM, but the same physics apply to what React's commit produces and to ref/animation code. Naming the read-then-write batching rule and the transform/opacity fast path is the senior signal.

SECTION 2 - DOM & EVENTS

Q4. What is the DOM, and how does it relate to the virtual DOM?

ROI: ★★★★☆ Frequency: High

Short Answer

The DOM (Document Object Model) is the browser's live, in-memory tree representation of the page that JavaScript can read and mutate. The virtual DOM is React's lightweight JS-object copy of what the UI should look like; React diffs the new virtual tree against the previous one and applies the minimal set of real DOM mutations.

Detailed Answer

Real DOM operations are relatively expensive (they can trigger layout/paint), and hand-writing minimal, correct mutations for a complex UI is error-prone. React's virtual DOM lets you describe the whole UI declaratively for a given state; React computes the difference and batches efficient updates. The virtual DOM is not "faster than the DOM" in a vacuum — it's a programming model that makes writing efficient, declarative updates practical and predictable.

Senior Engineer Perspective

Correct the common myth: the virtual DOM isn't magically fast; a hand-tuned direct DOM update can beat it. Its value is the declarative model plus batching. Note that newer frameworks (Svelte, Solid) skip the virtual DOM entirely by compiling to targeted updates — showing you understand the trade-off, not just the React talking point.

Q5. Explain event bubbling, capturing, and delegation.

ROI: ★★★★★ Frequency: High

Short Answer

Events travel in three phases: capture (root → target), target, then bubble (target → root). By default handlers fire on the bubbling phase. Event delegation exploits bubbling by attaching one listener to a common ancestor and reading event.target, instead of one listener per child.

Detailed Answer

When you click a button inside a list, the event first descends from document to the button (capture), reaches the button (target), then bubbles back up. addEventListener(type, fn, true) listens in capture; the default (false) is bubble. stopPropagation() halts travel; preventDefault() cancels the default browser action (they're independent).

Delegation is the practical payoff: attach one listener to the <ul> and handle clicks for all current and future <li> children — fewer listeners, works for dynamically added items.

Code Example

// Event delegation: one listener for the whole list
list.addEventListener('click', (e) => {
  const li = e.target.closest('li');
  if (!li) return;
  select(li.dataset.id);
});

Senior Engineer Perspective

React's synthetic event system historically used delegation — it attached listeners at a root container (the document pre-17, the app root container in React 17+) rather than on each node, which is exactly this pattern. Knowing React's own delegation model and that e.stopPropagation() on a synthetic event doesn't necessarily stop native listeners is a strong follow-up answer.

Q6. How does the browser event loop work?

ROI: ★★★★★ Frequency: High

Short Answer

JavaScript runs on a single thread with a call stack. Async callbacks are queued and run only when the stack is empty. There are two queues: microtasks (promises, queueMicrotask, MutationObserver) which drain completely after each task, and macrotasks (timers, I/O, events) which run one per loop iteration. Rendering happens between them.

Detailed Answer

Each loop iteration: run one macrotask → drain ALL microtasks → possibly render (rAF callbacks, style, layout, paint) → next macrotask. This ordering explains why a Promise callback runs before a setTimeout(…, 0) even if the timer was scheduled first.

Code Example

console.log('1');
setTimeout(() => console.log('2'), 0);   // macrotask
Promise.resolve().then(() => console.log('3')); // microtask
console.log('4');
// Output: 1, 4, 3, 2
// sync first, then all microtasks (3), then the macrotask (2)

Senior Engineer Perspective

The trap: a runaway microtask chain (a promise that keeps queueing more microtasks) can starve rendering and timers, because microtasks must fully drain before the loop moves on. Also tie in that requestAnimationFrame runs right before paint — the correct place for visual updates, unlike setTimeout.

SECTION 3 - NETWORKING

Q7. HTTP essentials: methods, status codes, and HTTP/1.1 vs 2 vs 3.

ROI: ★★★★☆ Frequency: High

Short Answer

Methods: GET (read), POST (create), PUT (replace), PATCH (partial update), DELETE. Status classes: 2xx success, 3xx redirect, 4xx client error, 5xx server error. HTTP/2 adds multiplexing over one connection (no head-of-line blocking at the app layer) and header compression; HTTP/3 runs over QUIC/UDP, eliminating TCP head-of-line blocking and speeding connection setup.

Detailed Answer

200 / 201 / 204OK / Created / No Content
301 / 302 / 304Moved Permanently / Found / Not Modified (cache)
400 / 401 / 403 / 404Bad Request / Unauthorized / Forbidden / Not Found

GET should be safe and idempotent; PUT and DELETE are idempotent; POST is not. HTTP/1.1 suffered from limited parallel connections and head-of-line blocking; HTTP/2 multiplexes many streams over one TCP connection; HTTP/3 moves to QUIC so a lost packet on one stream doesn't stall the others.

Senior Engineer Perspective

Know the 401 vs 403 distinction (not authenticated vs authenticated-but-not-allowed) — it's asked constantly. And that HTTP/2 multiplexing reduced the value of old frontend hacks like domain sharding and sprite sheets. Mentioning that shows you connect protocol evolution to frontend practice.

Q8. What is CORS and how do you fix a CORS error?

ROI: ★★★★★ Frequency: Extremely High

Short Answer

CORS (Cross-Origin Resource Sharing) is a browser security mechanism that blocks JS from reading responses from a different origin unless the server explicitly opts in with Access-Control-Allow-Origin headers. You fix it on the server by sending the right CORS headers — not in the frontend, and not by disabling browser security.

Detailed Answer

The same-origin policy stops app.com's JS from reading api.other.com's responses (origin = scheme + host + port). CORS lets the server relax this. For "non-simple" requests (custom headers, methods like PUT/DELETE, JSON content-type), the browser first sends a preflight OPTIONS request; the server must answer with allowed origins, methods, and headers before the real request is sent.

Fixes (server-side):

  • Access-Control-Allow-Origin: https://app.com (avoid * in production, especially with credentials).
  • Access-Control-Allow-Methods and Access-Control-Allow-Headers for preflight.
  • Access-Control-Allow-Credentials: true if sending cookies (and you cannot use * for origin then).

In development, a dev proxy (Vite/Next rewrite) routes API calls through the same origin to sidestep CORS locally.

Code Example

// vite.config.js — dev proxy so the browser sees a same-origin request
export default {
  server: {
    proxy: { '/api': { target: 'https://api.other.com', changeOrigin: true } }
  }
};

Senior Engineer Perspective

The mistake juniors make is trying to "fix CORS in React" — you can't; it's enforced by the browser based on server headers. Say clearly: CORS is server-configured; the proxy is a dev convenience; and CORS is not authentication (Q relates to security chapter). That precision is exactly what's being tested.

SECTION 4 - STORAGE & CACHING

Q9. How does browser caching work (Cache-Control, ETag)?

ROI: ★★★★☆ Frequency: Medium-High

Short Answer

Servers control caching with response headers. Cache-Control sets freshness (max-age, no-cache, immutable). When a cached response goes stale, the browser revalidates using ETag/If-None-Match or Last-Modified/If-Modified-Since; if unchanged the server returns 304 Not Modified with no body, saving bandwidth.

Detailed Answer

  • Cache-Control: max-age=31536000, immutable — cache for a year, never revalidate. Used for content-hashed assets (app.4f3a.js).
  • Cache-Control: no-cache — cache but always revalidate before use.
  • Cache-Control: no-store — never cache (sensitive data).
  • ETag — a fingerprint of the resource; the browser sends it back in If-None-Match, and the server replies 304 if it still matches.

The frontend build strategy that ties this together: hash filenames so assets can be cached forever (immutable), and serve index.html with no-cache so new deploys are picked up immediately (the fresh HTML references the new hashed asset URLs).

Senior Engineer Perspective

The "cache the hashed assets forever, never cache the HTML" strategy is the canonical SPA deploy pattern — stating it shows real production experience. Also distinguish the HTTP cache from the browser's disk/memory cache and from a Service Worker cache (Q11), which you control programmatically.

Q11. What are Service Workers and PWAs?

ROI: ★★★★☆ Frequency: Medium

Short Answer

A Service Worker is a script that runs in the background, separate from the page, acting as a programmable network proxy: it can intercept fetch requests and serve responses from a cache, enabling offline support, custom caching strategies, background sync, and push notifications. A PWA (Progressive Web App) is a web app that uses a Service Worker plus a manifest to be installable and app-like.

Detailed Answer

The Service Worker sits between the app and the network. On fetch events you choose a strategy: cache-first (fast, for static assets), network-first (fresh data, fall back to cache offline), or stale-while-revalidate (serve cache instantly, update in background). It has its own lifecycle (install → activate → fetch) and cannot access the DOM. A PWA also needs a manifest.json (name, icons, theme, start URL) and HTTPS.

Code Example

// Simplified fetch handler: cache-first
self.addEventListener('fetch', (event) => {
  event.respondWith(
    caches.match(event.request).then(
      (cached) => cached || fetch(event.request)
    )
  );
});

Senior Engineer Perspective

Warn about the classic Service Worker footgun: a badly-scoped or overly-aggressive cache can "trap" users on a stale version after deploy. Mention versioned caches, skipWaiting/clients.claim, and that tools like Workbox (and Vite PWA plugin) encode safe strategies so you don't hand-roll it.

Q12. What are Web Workers and when do you use them?

ROI: ★★★★☆ Frequency: Medium

Short Answer

A Web Worker runs JavaScript on a background thread, separate from the main UI thread, so heavy computation doesn't block rendering or user interaction. They communicate with the main thread via postMessage and have no DOM access. Use them for CPU-intensive work: parsing large files, image/data processing, cryptography, heavy calculations.

Detailed Answer

JavaScript is single-threaded, so a long synchronous task freezes the whole UI (INP suffers, the page becomes unresponsive). A Web Worker offloads that work to another thread; you send input via postMessage and receive results via a message event. Data is copied (structured clone) unless you use Transferable objects or SharedArrayBuffer.

Code Example

// main.js
const worker = new Worker(new URL('./heavy.js', import.meta.url), { type: 'module' });
worker.postMessage(bigData);
worker.onmessage = (e) => setResult(e.data);

// heavy.js
onmessage = (e) => {
  const result = expensiveComputation(e.data); // off the main thread
  postMessage(result);
};

Senior Engineer Perspective

Distinguish the three worker types: Web Workers (compute), Service Workers (network proxy/offline), Worker threads (Node). In React, libraries like Comlink make worker messaging feel like async function calls. Mention that most apps don't need workers — reach for one only when the profiler shows main-thread-blocking computation.

Q13. What are IntersectionObserver and requestIdleCallback?

ROI: ★★★★☆ Frequency: Medium

Short Answer

IntersectionObserver asynchronously notifies you when an element enters or leaves the viewport (or a root) — the efficient way to do lazy loading, infinite scroll, and reveal-on-scroll without scroll-event thrashing. requestIdleCallback schedules low-priority work to run during the browser's idle periods, so it doesn't compete with rendering or input.

Detailed Answer

Before IntersectionObserver, "is this element visible?" meant listening to scroll and calling getBoundingClientRect() constantly — expensive and janky (forced reflow). IntersectionObserver does the visibility math off the main thread and fires a callback only on threshold crossings.

requestIdleCallback(cb, { timeout }) runs cb when the main thread is idle, giving you the remaining frame budget — good for analytics beacons, prefetching, or non-urgent work. It falls back to a setTimeout polyfill where unsupported.

Code Example

const io = new IntersectionObserver((entries) => {
  entries.forEach((entry) => {
    if (entry.isIntersecting) {
      loadImage(entry.target);
      io.unobserve(entry.target);
    }
  });
}, { rootMargin: '200px' }); // start loading 200px early
images.forEach((img) => io.observe(img));

Senior Engineer Perspective

IntersectionObserver is the backbone of most infinite-scroll and lazy-load implementations (and libraries like react-intersection-observer wrap it). Using rootMargin to preload just before entry is the detail that shows you've shipped it. Note native loading="lazy" handles the common image case with zero JS.

Q14. script: async vs defer — what's the difference?

ROI: ★★★★☆ Frequency: Medium

Short Answer

A plain <script> blocks HTML parsing while it downloads and executes. async downloads in parallel and executes as soon as it's ready (order not guaranteed, can still interrupt parsing). defer downloads in parallel but executes only after HTML parsing completes, in document order. For app bundles, defer (or a module script) is the right default.

Use async for independent scripts that don't depend on the DOM or each other (analytics). Use defer for app code and scripts that need the DOM and a predictable order. Note <script type="module"> is deferred by default.

Senior Engineer Perspective

This is why every bundler injects the main bundle with defer (or as a module) at the end of <head>/<body>: non-blocking download, DOM-ready execution, correct order. Mentioning that ES modules are deferred by default, and that a render-blocking script in <head> is a classic performance bug, closes the loop nicely.

SECTION 5 - THE CRITICAL RENDERING PATH DEEP DIVE

Q15. Walk through exactly how the browser parses HTML into the DOM (tokenizer, tree construction, the preload scanner).

ROI: ★★★★☆ Frequency: Medium-High

Short Answer

HTML parsing has two stages: a tokenizer turns the byte stream into tokens (start tag, end tag, text, comment), and a tree construction stage consumes tokens to build the DOM using a stack of open elements and insertion-mode rules. In parallel, a preload scanner speculatively scans upcoming markup for resources (scripts, images, stylesheets) so it can start network requests before the main parser even reaches them.

Detailed Answer

The tokenizer is a state machine (HTML5 spec defines it precisely — "data state," "tag open state," etc.) that emits tokens one at a time. The tree builder maintains a stack of open elements and applies insertion-mode logic to handle HTML's famously permissive syntax (implicit tag closing, table-specific rules, foster parenting for misplaced elements). This is why malformed HTML like unclosed <p> tags still produces a sensible DOM — the algorithm has explicit recovery rules, not just "fail."

The main parser blocks on synchronous <script> tags because a script can call document.write and mutate what's already been parsed. To hide this latency, browsers run a lightweight preload scanner ahead of the main parser that doesn't build the DOM — it just looks for resource URLs (src, href) and kicks off fetches early, so by the time the main parser reaches a blocking script, its download may already be complete.

Senior Engineer Perspective

The preload scanner is why a synchronous script tag still doesn't fully stall network activity — only execution. Interviewers use this to test whether you understand that "parser-blocking" and "network-blocking" are different things. Mentioning that document.write is exactly the (rare, legacy) case that forces the parser to be so conservative is a strong closing detail.

Q16. Why is CSS render-blocking, and how do you avoid blocking on non-critical CSS?

ROI: ★★★★★ Frequency: High

Short Answer

CSS is render-blocking because the browser refuses to paint until it has the full CSSOM — painting with partial styles would cause a flash of unstyled or incorrectly-styled content. You avoid blocking on non-critical CSS by inlining the small amount needed for above-the-fold content and loading the rest asynchronously (media-attribute trick or rel="preload" swapped to stylesheet).

Detailed Answer

A <link rel="stylesheet"> in <head> blocks rendering (not parsing — the HTML parser keeps building the DOM) until that CSS file downloads and is parsed into the CSSOM, because the render tree needs both DOM and CSSOM. For non-critical CSS (below the fold, print styles, rarely-used component styles), you can defer:

  • A <link rel="stylesheet" media="print" onload="this.media='all'"> trick — the browser fetches it without blocking render since media="print" doesn't apply to screen rendering, then it's swapped to apply once loaded.
  • <link rel="preload" as="style" onload="this.rel='stylesheet'"> — fetch with preload priority, apply once ready.
  • Code-splitting CSS per route so only the CSS a route needs ships with it.

Senior Engineer Perspective

Frame this around the trade-off: inlining critical CSS eliminates a network round trip for the first paint but increases HTML payload and loses the CSS file's own long-term cache; async-loading the rest avoids FOUC risk if you get the "critical" subset wrong. Frameworks like Next.js and styled-components/critters automate the extraction — knowing the automated tool exists, plus the manual technique it replaces, is the senior signal.

Q17. What is the preload scanner and how does it interact with resource hints?

ROI: ★★★☆☆ Frequency: Medium

Short Answer

The preload scanner (also called the "speculative parser") runs ahead of the main HTML parser, looking only for resource references, so downloads can start before the main parser reaches those tags — critical for hiding the latency of render-blocking scripts and stylesheets. Resource hints (preload, preconnect, prefetch) work with, not against, this mechanism by telling the browser about resources it can't discover by scanning (e.g. a font referenced only inside CSS, or a cross-origin API host).

Detailed Answer

The preload scanner can already find most obvious resources: <img>, <script src>, <link rel="stylesheet">. What it can't discover ahead of time is anything hidden behind another resource — a @font-face URL inside a CSS file, or a large hero image applied via a CSS background-image, or an API host the JS bundle will call. That's exactly what explicit resource hints fill in.

Code Example

<!-- Tell the browser to fetch this font before CSS parsing reveals it's needed -->
<link rel="preload" href="/fonts/inter.woff2" as="font" type="font/woff2" crossorigin>

<!-- Warm up the connection to an API host used later by JS -->
<link rel="preconnect" href="https://api.example.com">

<!-- Hint that the user will likely navigate here next -->
<link rel="prefetch" href="/next-page.js">

Senior Engineer Perspective

Overusing preload is a real anti-pattern: it competes for bandwidth with resources the preload scanner would have found anyway, and unused preloads trigger a console warning and wasted bytes. The senior answer names the four hints (preload, preconnect, prefetch, dns-prefetch), their priority implications, and warns against blanket use.

Q18. How do web fonts affect the critical rendering path, and how does font-display control FOIT vs FOUT?

ROI: ★★★★☆ Frequency: Medium-High

By default, browsers hide text using a custom font until it downloads (a "flash of invisible text," FOIT), which can delay the largest contentful paint if the font is slow. font-display lets you choose the trade-off: swap shows a fallback font immediately and swaps in the web font when ready (FOUT — flash of unstyled text), while optional gives up on the web font entirely if it's not fast enough.

Q19. What is Largest Contentful Paint (LCP), and how does the critical rendering path determine it?

ROI: ★★★★★ Frequency: High

Short Answer

LCP is a Core Web Vital measuring when the largest visible content element (usually a hero image, a large block of text, or a background image) finishes rendering. It's directly downstream of the critical rendering path: every render-blocking resource, slow server response, and late-discovered image pushes LCP later.

Detailed Answer

LCP is commonly broken into four sub-parts for diagnosis: TTFB (server response time), resource load delay (time until the browser starts fetching the LCP resource — often the biggest lever, e.g. an image only discoverable after JS runs), resource load time (download duration), and render delay (time from load to actual paint, often blocked by long tasks on the main thread).

Common fixes per phase: reduce TTFB with SSR/edge caching; eliminate resource load delay by making the LCP image discoverable in the initial HTML (not injected by JS) and preloading it with fetchpriority="high"; compress/right-size the image for load time; and keep the main thread free of long tasks so paint isn't delayed once the resource is ready.

Senior Engineer Perspective

A frequent anti-pattern that hurts LCP: lazy-loading the hero image with loading="lazy" — the very technique that helps below-the-fold images hurts the one image that most determines LCP. Naming the "don't lazy-load the LCP element, do preload it" rule is a concrete, checkable senior signal.

Q21. What's the difference between the DOMContentLoaded and load events?

ROI: ★★★☆☆ Frequency: Medium

Short Answer

DOMContentLoaded fires once the HTML is fully parsed and the DOM tree is built, without waiting for images, stylesheets (mostly), or iframes to finish loading. load fires later, once every subresource (images, CSS, fonts, iframes) has finished loading.

Detailed Answer

Deferred and module scripts execute before DOMContentLoaded, in order, which is why frameworks hook their bootstrap logic to run around that point rather than waiting for load. load is the right event for "everything is fully rendered and settled" work — e.g. measuring final layout, or hiding a loading spinner that should persist until images are visible.

Code Example

document.addEventListener('DOMContentLoaded', () => {
  // DOM ready, scripts (defer/module) have run — safe to query elements
});

window.addEventListener('load', () => {
  // Every image, stylesheet, and iframe has finished loading
});

Senior Engineer Perspective

Note that neither of these correlates well with user-perceived performance metrics like LCP or FCP — a page can fire load quickly while still being visually incomplete, or vice versa with lazy content. Distinguishing "technical load events" from "Core Web Vitals" shows you know these are different measurement systems built for different purposes.

Q22. How does inlining critical CSS help performance, and what are the trade-offs?

ROI: ★★★★☆ Frequency: Medium-High

Short Answer

Inlining the CSS needed for above-the-fold content directly in a <style> tag in <head> removes a network round trip from the critical rendering path — the browser has everything it needs to paint the first screen as soon as the HTML and inline CSS are parsed, with no external stylesheet request blocking it.

Detailed Answer

The trade-off is real: inlined CSS bloats the HTML document itself (which isn't cached the same way a separate CSS file with a hashed filename is — HTML is usually served with no-cache so it's revalidated every visit), and it duplicates bytes across every page unless your SSR/build tool extracts exactly the CSS actually used per route. Getting the "critical" subset wrong (too little) causes a flash of unstyled content when the rest of the CSS loads; too much erases the benefit entirely.

Senior Engineer Perspective

This is an automated concern in modern frameworks — Next.js extracts critical CSS per route automatically with its built-in CSS handling, and tools like critical/critters exist for other stacks. Knowing when to reach for the automation versus when it's not worth the build complexity (a small app with one small CSS bundle) is the practical, senior-level answer.

SECTION 6 - BROWSER STORAGE DEEP DIVE

Q23. Deep dive on localStorage internals — why is it synchronous, and what does that cost you?

ROI: ★★★★☆ Frequency: High

Short Answer

localStorage's API (getItem/setItem) is fully synchronous and runs on the main thread, storing only strings, scoped per origin (scheme+host+port), with no built-in expiry. Because it's synchronous, a large read or write blocks rendering and input handling — it's fine for small config/preference blobs, risky for anything large or frequent.

Detailed Answer

Every value must be a string, so objects require JSON.stringify/JSON.parse — and parsing a large JSON blob synchronously on every read is itself a main-thread cost. Capacity is roughly 5-10MB per origin depending on the browser, and exceeding it throws a QuotaExceededError. There is no native expiry or eviction policy — data persists until explicitly cleared or the user clears site data.

Code Example

// Storing/reading structured data — note the manual serialize/deserialize cost
localStorage.setItem('prefs', JSON.stringify({ theme: 'dark', fontSize: 14 }));
const prefs = JSON.parse(localStorage.getItem('prefs') ?? '{}');

// Listening for changes made in OTHER tabs (does not fire in the tab that made the change)
window.addEventListener('storage', (e) => {
  console.log(e.key, e.oldValue, e.newValue);
});

Senior Engineer Perspective

A detail that separates candidates: the storage event fires in other tabs/windows of the same origin, never in the tab that made the write — a common source of "why isn't my listener firing" bugs. Also flag the synchronous-blocking cost as the reason large caches belong in IndexedDB instead.

Q24. How does sessionStorage differ from localStorage beyond "it clears when the tab closes"?

ROI: ★★★☆☆ Frequency: Medium

Short Answer

sessionStorage is scoped per tab (technically per top-level browsing context), not just per origin — two tabs open to the same site each get their own isolated sessionStorage, even though they'd share the same localStorage. It survives a reload of that tab but not opening the same URL in a new tab, and it's cleared when the tab is closed.

Detailed Answer

A subtlety: sessionStorage is copied to a new tab opened via "duplicate tab" or a link with target="_blank" in some browsers (it inherits the opener's session storage at the moment of opening), but from then on the two are independent copies, not shared. This makes it suited for per-tab wizard/flow state (a multi-step checkout) that shouldn't leak between tabs, unlike localStorage or cookies which are origin-wide.

Senior Engineer Perspective

The tab-duplication inheritance quirk is an easy trap in interviews and in real bugs — candidates who've hit it in production can describe exactly when sessionStorage is and isn't shared. Framing sessionStorage as "per browsing-context session" rather than "per tab" more precisely captures this.

Q25. Explain IndexedDB — object stores, transactions, indexes — and when it beats localStorage.

ROI: ★★★★☆ Frequency: Medium-High

Short Answer

IndexedDB is an asynchronous, transactional, NoSQL object database built into the browser: data is organized into object stores (like tables) holding structured JS values (not just strings), with optional indexes for querying by a field other than the primary key. Reach for it over localStorage whenever you need large amounts of data, structured queries, or you must not block the main thread.

Detailed Answer

Everything happens inside a transaction scoped to specific object stores and a mode (readonly/readwrite); the transaction auto-commits when its event loop microtask queue empties, unlike a SQL transaction you explicitly commit. The raw API is callback/event-based and notoriously verbose, which is why most real apps use a thin wrapper (idb, Dexie) that promisifies it.

Code Example

const req = indexedDB.open('app-db', 1);
req.onupgradeneeded = (e) => {
  const db = e.target.result;
  const store = db.createObjectStore('notes', { keyPath: 'id' });
  store.createIndex('by_updatedAt', 'updatedAt'); // secondary index
};
req.onsuccess = (e) => {
  const db = e.target.result;
  const tx = db.transaction('notes', 'readwrite');
  tx.objectStore('notes').put({ id: 1, text: 'hi', updatedAt: Date.now() });
};

Senior Engineer Perspective

Explaining that IndexedDB transactions auto-commit once the current microtask turn finishes draining (so you can't await an unrelated promise mid-transaction without the transaction closing early) is a deep, easy-to-miss detail that shows real hands-on experience — it's the single most common IndexedDB footgun.

Q26. Cookies deep dive — explain Secure, HttpOnly, and the SameSite=Strict/Lax/None distinction.

ROI: ★★★★★ Frequency: High

Short Answer

Secure means the cookie is only sent over HTTPS. HttpOnly means client-side JS can't read it (mitigates XSS token theft). SameSite controls cross-site sending: Strict never sends on cross-site requests, Lax (the modern default) sends on top-level navigations but not on cross-site subrequests/POSTs, and None (requires Secure) sends everywhere, needed for legitimate third-party/embedded use cases.

The layered defense senior engineers describe: HttpOnly stops XSS from reading the cookie, SameSite=Lax/Strict stops CSRF from sending it cross-site, and Secure stops it leaking over plaintext HTTP — three different threat models, three different attributes, and none of them substitutes for the others.

Q27. How does the Cache API relate to the HTTP cache, localStorage, and IndexedDB?

ROI: ★★★☆☆ Frequency: Medium

Short Answer

The Cache API (used by Service Workers) stores actual Request/Response object pairs — full HTTP responses, including headers and bodies — and you control it programmatically. The HTTP cache is managed automatically by the browser based on Cache-Control/ETag headers. localStorage/IndexedDB store arbitrary data you put there, unrelated to network responses, unless you build that mapping yourself.

Detailed Answer

Think of it as a spectrum of control: HTTP cache is "the browser decides, guided by your headers"; the Cache API is "you decide entirely, in JavaScript, which responses to store and when to serve them" — it's the mechanism behind every offline-first strategy. IndexedDB is the general-purpose database for structured app data (not necessarily tied to network responses at all), and localStorage is the small synchronous key-value store for simple flags/preferences.

Senior Engineer Perspective

A well-designed offline-first app often uses all three together: HTTP cache for static assets, Cache API (via a Service Worker) for API responses/app shell, and IndexedDB for structured application data that needs querying. Naming how they compose, rather than treating them as competing options, is what a senior answer looks like.

Q28. How do storage quotas and eviction work, and how do you check/request persistence?

ROI: ★★★☆☆ Frequency: Low-Medium

Short Answer

Browsers allocate a shared storage quota per origin (often a percentage of free disk space) covering IndexedDB, Cache API, and other origin storage together. Under disk pressure, "best-effort" storage can be evicted (usually LRU across origins) without warning; you can call navigator.storage.persist() to request exemption from automatic eviction, and navigator.storage.estimate() to check usage/quota.

Detailed Answer

"Best-effort" mode is the default: the browser can clear your origin's storage entirely if the device runs low on space, typically evicting the least-recently-used origin first. "Persistent" mode (granted via persist(), sometimes auto-granted for installed PWAs or bookmarked/frequently-visited sites, sometimes requiring a user prompt) protects storage from that automatic eviction — the user must explicitly clear site data to remove it.

Code Example

const estimate = await navigator.storage.estimate();
console.log(`${estimate.usage} of ${estimate.quota} bytes used`);

const isPersisted = await navigator.storage.persisted();
if (!isPersisted) {
  const granted = await navigator.storage.persist();
}

Senior Engineer Perspective

This matters concretely for offline-first apps: a user who hasn't "installed" your PWA or visited it often enough can lose their entire offline cache silently under disk pressure. Mentioning that persistence eligibility differs by browser (some grant automatically based on engagement, others require an explicit permission prompt) shows you've actually shipped an offline feature, not just read the spec.

Q29. Design decision: you need offline-capable form drafts (autosave while typing, survive a crash/refresh). Which storage, and why?

ROI: ★★★★☆ Frequency: Medium-High

Short Answer

For small forms, debounce writes to localStorage — simple, synchronous, good enough. For larger forms (rich text, file attachments, many fields, or you want per-draft history), use IndexedDB so writes don't block the main thread and you get real query/structure. Avoid cookies (sent needlessly on every request) and sessionStorage (lost on tab close, defeating "survive a crash").

Detailed Answer

The concrete plan: debounce keystroke-driven saves (e.g. every 500ms-1s of inactivity, not every keystroke) to avoid excessive writes; namespace the key by form/draft id; store a timestamp so you can show "draft saved 2 minutes ago" and detect staleness; and on load, check for an existing draft and prompt the user to restore or discard it. If the form includes file uploads, those belong in IndexedDB (as Blobs) — localStorage can't store binary data efficiently.

Code Example

function useDraft(formId, values) {
  useEffect(() => {
    const id = setTimeout(() => {
      localStorage.setItem(`draft:${formId}`, JSON.stringify({
        values, savedAt: Date.now(),
      }));
    }, 750);
    return () => clearTimeout(id);
  }, [formId, values]);
}

Senior Engineer Perspective

This is a favorite system-design-style follow-up because it forces you to weigh capacity, synchronicity, and binary support against real product requirements instead of reciting a comparison table. Explicitly ruling out cookies and sessionStorage with a reason, not just naming the "right" answer, is what shows genuine understanding.

Q30. How does storage behave differently inside a third-party iframe, and what is cookie partitioning (CHIPS)?

ROI: ★★★☆☆ Frequency: Low-Medium

Short Answer

Browsers increasingly restrict or partition storage for third-party contexts (an iframe embedded from a different origin) to prevent cross-site tracking: Safari's ITP and Firefox's ETP have long partitioned or blocked third-party storage, and Chrome is moving the same direction, including via CHIPS (Cookies Having Independent Partitioned State) — cookies explicitly opted into being partitioned per top-level site.

Detailed Answer

Under storage partitioning, a third-party embed (e.g. a widget served from widget.com embedded on both siteA.com and siteB.com) gets a separate storage bucket per top-level site it's embedded in, rather than one shared bucket — so it can no longer correlate a user across the two host sites via storage. CHIPS lets a cookie opt in to this via the Partitioned attribute, explicitly trading "works across sites" for "works, but isolated per site" instead of being blocked outright. The Storage Access API (document.requestStorageAccess()) is the escape hatch for legitimate cases (e.g. an embedded video player that needs its login cookie) to request permission.

Senior Engineer Perspective

This is a fast-moving area, and interviewers at companies with embeds/widgets/SSO-across-subdomains care whether you're aware it exists at all, even without memorizing every browser's exact rollout state. Framing it as "the privacy-driven wind-down of third-party storage as we knew it, with CHIPS and the Storage Access API as the sanctioned exceptions" is enough depth for most interviews.

SECTION 7 - HTTP/NETWORKING FUNDAMENTALS FOR FRONTEND ENGINEERS

Q31. Cache-Control directives deep dive — max-age vs s-maxage vs stale-while-revalidate.

ROI: ★★★★☆ Frequency: High

Short Answer

max-age sets freshness for any cache (browser or shared). s-maxage overrides max-age specifically for shared caches (CDN/proxy), letting you cache longer at the edge than in the browser. stale-while-revalidate lets a cache serve a stale response immediately while it revalidates in the background, so the user never waits on a synchronous refetch.

Detailed Answer

Cache-Control: max-age=60, s-maxage=3600, stale-while-revalidate=86400

Reading this: browsers treat the response fresh for 60 seconds; CDNs/shared caches treat it fresh for an hour; and for up to a day after going stale, a cache can serve the stale copy instantly while fetching a fresh one in the background for the next request. This pattern is exactly how many CDNs and frameworks (Next.js ISR-style caching, Cloudflare) deliver "instant" responses that still stay reasonably fresh.

Senior Engineer Perspective

Knowing that s-maxage lets you decouple "how long the CDN caches this" from "how long the browser caches this" is a strong signal — it's exactly how you'd serve a personalized-looking page from a shared edge cache safely (short browser max-age, long s-maxage, or vice versa) depending on personalization needs.

Q32. Explain HTTP/2 multiplexing and HPACK header compression — how do they change frontend bundling strategy?

ROI: ★★★★☆ Frequency: Medium-High

Short Answer

HTTP/2 multiplexes many request/response streams over a single TCP connection, eliminating the old "6 connections per host" bottleneck, and HPACK compresses headers (which are highly repetitive across requests) to cut overhead. Together they mean the old trick of concatenating everything into one giant bundle to minimize requests is often counterproductive — many small, cacheable, parallel-loadable chunks can now perform better.

Detailed Answer

Under HTTP/1.1, each origin was limited to roughly 6 parallel connections, so bundling JS/CSS into one file and spriting images were legitimate optimizations to reduce request count. HTTP/2 removes that ceiling (streams are cheap and multiplexed), so code-splitting into many small chunks lets the browser fetch them in parallel and lets unchanged chunks stay cached across deploys — better than invalidating one monolithic bundle on every change. HPACK further reduces the cost of the many small requests by compressing repeated header fields (cookies, user-agent, accept headers) across the connection.

Senior Engineer Perspective

This is why modern bundlers default to aggressive code-splitting rather than "one bundle to rule them all," and why sprite sheets and domain sharding are now considered legacy techniques that can actively hurt performance under HTTP/2+. Framing the answer as "the protocol changed, so the bundling strategy had to change with it" demonstrates you understand cause and effect, not just current best practice by rote.

Q33. Why does HTTP/3 run over QUIC/UDP, and how does that eliminate TCP head-of-line blocking?

ROI: ★★★★☆ Frequency: Medium

Short Answer

TCP guarantees in-order delivery of the entire byte stream, so one lost packet stalls every multiplexed HTTP/2 stream sharing that connection, even ones unaffected by the loss — this is head-of-line blocking at the transport layer. QUIC (built on UDP) implements its own per-stream reliability and ordering, so a lost packet only stalls the one stream it belongs to; the others keep flowing.

Detailed Answer

QUIC also folds the TCP handshake and TLS 1.3 handshake into fewer round trips (often 1-RTT, or 0-RTT for resumed connections), and it supports connection migration — a connection identified by a connection ID (not the traditional IP:port tuple) can survive a network change, like a phone switching from WiFi to cellular, without a full reconnect. Because it's implemented at the application/user-space layer rather than the OS kernel, it's also easier to evolve than TCP.

Senior Engineer Perspective

The connection migration point is the one interviewers most enjoy hearing described concretely — for mobile-heavy products it's a real, user-visible reliability win, not just a protocol trivia fact. Pairing it with the head-of-line-blocking explanation shows you understand why HTTP/3 exists, not just that it's "the new one."

Q34. What is a CDN, and how does it interact with your caching headers?

ROI: ★★★★☆ Frequency: High

Short Answer

A CDN (Content Delivery Network) is a distributed network of edge servers that cache and serve your content from a location physically close to the user, cutting latency and offloading your origin server. It respects (and can be configured to override) your Cache-Control headers — particularly s-maxage, which targets shared caches like CDNs specifically.

Detailed Answer

On a cache miss at the edge, the CDN fetches from your origin, stores the response according to the caching headers (or its own override rules/purge API), and serves subsequent requests from the edge without hitting the origin at all. Static, hashed assets are ideal CDN citizens (cache essentially forever); dynamic/personalized responses require careful Vary headers or bypassing the CDN cache entirely (Cache-Control: private, no-store).

Senior Engineer Perspective

A common production incident: forgetting a correct Vary header (e.g. Vary: Accept-Encoding or Vary: Cookie) causes a CDN to serve one user's cached (possibly personalized or wrongly-encoded) response to a different user. Being able to describe this failure mode concretely is worth more than reciting "CDNs make things faster."

Q35. Explain content negotiation — Accept, Accept-Encoding, and the Vary header.

ROI: ★★★☆☆ Frequency: Medium

Short Answer

Content negotiation lets a client and server agree on the best representation of a resource: Accept negotiates format (JSON vs XML vs HTML), Accept-Encoding negotiates compression (gzip, br/Brotli). The server must echo which request headers affected its response via the Vary header, so caches know not to serve a gzip'd response to a client that only accepts identity encoding.

Detailed Answer

Brotli (br) generally compresses better than gzip for text assets (JS/CSS/HTML) and is supported by all modern browsers; a server (or CDN) should serve whichever the client's Accept-Encoding allows, best compression first. Without a correct Vary: Accept-Encoding, an intermediate cache could store a Brotli response and later serve it to a client/proxy that can't decode Brotli — a real, hard-to-diagnose bug.

Senior Engineer Perspective

Interviewers use this to check whether you understand that caching correctness depends on which request headers matter, not just the response body — the Vary header is the mechanism that keeps content negotiation and caching from silently conflicting.

Q36. Explain keep-alive connections and connection pooling, and why domain sharding is now an anti-pattern.

ROI: ★★★☆☆ Frequency: Medium

Short Answer

Connection: keep-alive (default in HTTP/1.1) reuses one TCP connection for multiple sequential requests instead of opening a new one each time, avoiding repeated handshake overhead. Domain sharding (splitting assets across fake subdomains to get more parallel HTTP/1.1 connections) is now an anti-pattern under HTTP/2+, because a single multiplexed connection already parallelizes better than several separate ones, and sharding adds extra DNS/TLS setup cost per shard.

Detailed Answer

Under HTTP/1.1's per-host connection cap, sites used to serve assets from static1.example.com, static2.example.com, etc., to trick the browser into opening more simultaneous connections. HTTP/2's single-connection multiplexing removes the reason for this hack — and worse, each extra domain now costs an additional DNS lookup and TLS handshake, actively slowing things down. Modern guidance: consolidate onto as few origins as reasonably possible and let HTTP/2+ multiplexing do the parallelization.

Senior Engineer Perspective

Recognizing a legacy performance "best practice" that has flipped to an anti-pattern (domain sharding) is exactly the kind of nuance senior interviewers probe for — it shows you keep pace with protocol evolution instead of reciting a decade-old checklist.

Q37. What is TTFB, and how do you diagnose and reduce it?

ROI: ★★★★☆ Frequency: Medium-High

Short Answer

TTFB (Time to First Byte) measures from navigation start to when the browser receives the first byte of the response — it bundles DNS, connection setup, TLS, and server processing time. A slow TTFB delays everything downstream (parsing, LCP), so it's usually the first thing to check when a page "just feels slow."

Detailed Answer

Diagnose it by breaking TTFB down in the Network tab's timing waterfall: DNS lookup, initial connection, TLS negotiation, then "waiting" (server processing/queueing) — each phase points to a different fix. Reduce it via: a CDN/edge serving cached or edge-rendered content closer to the user; server-side caching (avoid recomputing the same response); reducing redirect chains (each redirect adds a full round trip before the real request even starts); and moving expensive server-side data fetching/rendering work off the hot path (parallelizing DB calls, caching SSR output).

Senior Engineer Perspective

A frequent, easy-to-miss TTFB killer: an unnecessary redirect chain (HTTP→HTTPS, then www→non-www, then trailing-slash normalization) that adds two or three full round trips before the real request begins — worth naming explicitly as a quick, high-leverage fix.

Q38. What does the fetchpriority attribute do, and how does it interact with the browser's default resource prioritization?

ROI: ★★★☆☆ Frequency: Medium

Short Answer

Browsers already assign an internal priority to each resource (CSS and fonts high, below-the-fold images low, etc.) based on heuristics. fetchpriority="high"/"low" on <img>, <link>, and <script> lets you override those heuristics explicitly — most commonly to mark the LCP image as high priority so it competes properly against other early requests.

Detailed Answer

Without a hint, a large hero <img> discovered late in the HTML, or one whose priority the browser under-guesses, can be scheduled behind less-important resources, delaying LCP. Marking it explicitly fixes this without resorting to a full preload tag.

Code Example

<img src="/hero.jpg" fetchpriority="high" alt="Hero">
<img src="/thumbnail.jpg" fetchpriority="low" loading="lazy" alt="Thumbnail">

Senior Engineer Perspective

Pairing fetchpriority="high" on the LCP image with not lazy-loading it is a small, concrete, high-signal optimization that shows up in real Core Web Vitals audits — a good, specific example to bring up when asked "tell me about a performance fix you shipped."

Q40. Which requests are "simple" (no preflight) and which trigger a CORS preflight?

ROI: ★★★★☆ Frequency: High

Short Answer

A "simple" request needs no preflight: method is GET/HEAD/POST, only a small allow-listed set of headers is used, and the Content-Type (for POST) is one of text/plain, application/x-www-form-urlencoded, or multipart/form-data. Anything else — PUT/DELETE/PATCH, custom headers like Authorization, or a JSON content type — triggers a preflight OPTIONS request first.

Detailed Answer

This is exactly why a typical JSON REST API call (fetch(url, { method: 'POST', headers: { 'Content-Type': 'application/json' }, body })) always triggers a preflight — application/json is not in the simple-request allow-list. The browser sends the real request only after the preflight OPTIONS response confirms it's permitted, adding one extra round trip per unique method/header/URL combination (though browsers cache preflight results for a configurable duration via Access-Control-Max-Age).

Senior Engineer Perspective

Mentioning Access-Control-Max-Age as the way to cache preflight results (avoiding a redundant OPTIONS round trip on every request) is the concrete performance-aware detail that distinguishes "knows CORS exists" from "has actually optimized an API's CORS behavior."

Q42. How do credentialed CORS requests work, and why can't you use a wildcard origin with them?

ROI: ★★★★★ Frequency: High

Short Answer

By default, cross-origin fetch/XHR requests don't send cookies. Setting credentials: 'include' makes the browser send cookies cross-origin — but the server must respond with a specific Access-Control-Allow-Origin (not *) and Access-Control-Allow-Credentials: true, or the browser blocks the response entirely.

Detailed Answer

This restriction exists because Access-Control-Allow-Origin: * combined with credentials would let any site on the internet make authenticated requests on behalf of a logged-in user and read the response — effectively defeating the same-origin policy's protection entirely. Requiring an explicit origin forces the server to make a deliberate allow-list decision rather than a blanket one.

Code Example

// Client
fetch('https://api.example.com/me', { credentials: 'include' });

// Server MUST respond with a specific origin, never '*', when credentials are used
// Access-Control-Allow-Origin: https://app.example.com
// Access-Control-Allow-Credentials: true

Senior Engineer Perspective

This is one of the highest-value CORS facts to know cold, because it's also a security control, not just a networking rule — an engineer who reflexively "fixes" a CORS error by setting Allow-Origin: * and Allow-Credentials: true together (which browsers actually reject) reveals they don't understand why the restriction exists.

Q43. What are the most common CORS misconfigurations, and how do you fix each?

ROI: ★★★★★ Frequency: High

Short Answer

Three recurring mistakes: (1) using Access-Control-Allow-Origin: * together with credentials (browser rejects it — must use a specific origin), (2) blindly reflecting whatever Origin header the request sends back as the allowed origin (accidentally allows every site, defeating the purpose), and (3) a CDN/proxy caching a CORS response without Vary: Origin, so one origin's allowed response gets served to a different, disallowed origin.

Detailed Answer

  • Wildcard + credentials: fix by listing the specific allowed origin(s), never *, whenever Allow-Credentials: true is set.
  • Naive origin reflection: Access-Control-Allow-Origin: <request Origin header, unchecked> — fix by validating the incoming Origin against an explicit allow-list before echoing it back.
  • Missing Vary: Origin: if your CORS headers vary by requester, tell caches so — add Vary: Origin so a CDN doesn't serve origin-A's allowed response to origin-B.
  • Preflight not handled: forgetting to implement/allow the OPTIONS method on a route entirely, causing every non-simple request to fail with no real request ever sent.

Senior Engineer Perspective

This question is really testing whether you treat CORS as a security boundary rather than an annoyance to silence. Being able to name the "reflect origin without validating" mistake specifically — a real vulnerability class, not just a bug — is the strongest possible answer here.

Q44. Is CORS related to CSRF? Explain how they interact.

ROI: ★★★★☆ Frequency: Medium-High

Short Answer

They address different problems and neither substitutes for the other. CORS controls whether cross-origin JavaScript can read the response of a request. CSRF is about a request being sent at all (e.g. via a plain HTML form or image tag, which isn't subject to CORS) with the victim's ambient credentials (cookies) attached, without the attacker ever needing to read the response.

Detailed Answer

A classic CSRF attack (a hidden auto-submitting form on an attacker's site that POSTs to your bank's transfer endpoint) doesn't need to read the response at all — it just needs the browser to attach the victim's session cookie, which it does automatically for a plain form submission regardless of CORS. That's why CORS headers offer zero CSRF protection by themselves; CSRF is defended with SameSite cookies, CSRF tokens, and checking the Origin/Referer header server-side.

Senior Engineer Perspective

This is one of the most commonly confused pairs in frontend security interviews. Stating plainly "CORS is about response readability, CSRF is about request forgery with ambient credentials, and they need entirely separate defenses" is exactly the crisp distinction interviewers are fishing for.

Q45. How does postMessage enable safe cross-origin communication, and why does targetOrigin matter?

ROI: ★★★★☆ Frequency: Medium

Short Answer

window.postMessage(message, targetOrigin) lets two windows/iframes of different origins communicate safely, bypassing the same-origin policy's DOM-access restriction in a controlled way. Specifying a precise targetOrigin (not *) ensures the message is only delivered if the receiving window's actual origin matches — otherwise a redirect or an embed on an unexpected page could leak the message to the wrong origin.

Detailed Answer

On the receiving side, you must validate event.origin yourself inside the message listener — the browser won't do it for you on receipt, only on send (via targetOrigin). Skipping that check means any embedded or malicious frame could send you a crafted message and you'd process it as trusted.

Code Example

// Sender (in the parent), restricts delivery to the exact expected origin
iframe.contentWindow.postMessage({ type: 'RESIZE', height: 400 }, 'https://widget.example.com');

// Receiver — MUST validate event.origin, the API does not do it for you
window.addEventListener('message', (event) => {
  if (event.origin !== 'https://trusted-parent.com') return; // reject anything else
  handleMessage(event.data);
});

Senior Engineer Perspective

The two-sided nature of this safety mechanism trips people up: targetOrigin protects the sender from leaking to the wrong recipient, while the receiver still must manually check event.origin to protect itself from unwanted senders. Naming both halves is the complete answer.

Q46. How do X-Frame-Options and the CSP frame-ancestors directive control who can iframe your site?

ROI: ★★★☆☆ Frequency: Medium

Short Answer

Both are response headers that prevent your page from being embedded in an iframe on other sites (defending against clickjacking). X-Frame-Options: DENY/SAMEORIGIN is the older, simpler mechanism; Content-Security-Policy: frame-ancestors 'self' https://trusted.com is the modern, more flexible replacement that supports an allow-list of multiple origins.

Detailed Answer

Clickjacking works by overlaying an invisible iframe of a legitimate site (e.g. a banking "confirm transfer" button) over an attacker's page, tricking the user into clicking it. These headers stop the browser from rendering the frame at all when the embedding page's origin isn't allowed. frame-ancestors is preferred going forward since CSP directives are more expressive and X-Frame-Options only supports a single allowed origin (or none/same-origin), not a list.

Senior Engineer Perspective

Note these protect your site from being embedded elsewhere — the reverse direction of CORS, which protects data your site fetches from other origins. Interviewers sometimes conflate the two directions to see if you'll correct them; doing so cleanly is a good signal.

SECTION 9 - SERVICE WORKERS & THE CACHE API DEEP DIVE

Q47. Walk through the Service Worker lifecycle — install, waiting, activate — and explain skipWaiting/clients.claim.

ROI: ★★★★★ Frequency: High

Short Answer

A new Service Worker registration goes through install (pre-cache assets), then sits in waiting until every open tab controlled by the old worker is closed (to avoid mixing old/new logic mid-session), then activates and starts controlling pages. self.skipWaiting() forces immediate activation without waiting for tabs to close; clients.claim() makes the new worker take control of already-open pages immediately, instead of only new navigations.

Detailed Answer

This staged rollout exists so a page doesn't have some resources served by an old cache/logic and others by new mid-session — a real correctness concern, not just caution. Calling skipWaiting() + clients.claim() together is the common pattern for apps that want updates to apply as fast as possible (at the cost of a currently-open tab suddenly switching Service Worker versions underneath it).

Code Example

self.addEventListener('install', (event) => {
  self.skipWaiting(); // don't wait for old tabs to close
  event.waitUntil(caches.open('v2').then((cache) => cache.addAll(ASSETS)));
});

self.addEventListener('activate', (event) => {
  event.waitUntil(clients.claim()); // control open tabs immediately
});

Senior Engineer Perspective

The classic footgun this lifecycle causes: users get "stuck" on an old version because a tab never closes (e.g. left open overnight), and the new worker sits waiting indefinitely. Knowing the trade-off between forcing immediate updates (skipWaiting/clients.claim, risk of mid-session inconsistency) versus the safer default (wait for a full close) is exactly the kind of judgment senior engineers are expected to have.

Q48. Explain the Cache API's Cache and CacheStorage interfaces, and how you'd version caches across deploys.

ROI: ★★★★☆ Frequency: Medium-High

Short Answer

caches (CacheStorage) is a top-level, origin-scoped registry of named caches; caches.open(name) returns a Cache object with methods like put, match, addAll, and delete for storing actual Request/Response pairs. Versioning caches by name (e.g. app-v3) and deleting old-named caches during activate is the standard way to avoid serving stale assets forever.

Detailed Answer

const CACHE_NAME = 'app-v3';

self.addEventListener('activate', (event) => {
  event.waitUntil(
    caches.keys().then((names) =>
      Promise.all(
        names
          .filter((name) => name !== CACHE_NAME) // drop old versions
          .map((name) => caches.delete(name))
      )
    )
  );
});

Without this cleanup step, every deploy accumulates a new named cache forever, silently consuming the origin's storage quota.

Senior Engineer Perspective

Forgetting the cache-cleanup-on-activate step is a real production bug pattern — storage usage grows unbounded across deploys until quota eviction kicks in unpredictably. Naming this concrete failure mode, not just "you should version your caches," is what shows hands-on experience.

Q49. Give code for each major offline strategy: cache-first, network-first, and stale-while-revalidate.

ROI: ★★★★★ Frequency: High

Short Answer

Cache-first: check cache, fall back to network — best for immutable static assets. Network-first: try network, fall back to cache on failure — best for data that should be as fresh as possible but must degrade gracefully offline. Stale-while-revalidate: return the cached response instantly while fetching a fresh one in the background for next time — a good default for most API responses.

Detailed Answer

// Cache-first
async function cacheFirst(request) {
  const cached = await caches.match(request);
  return cached || fetch(request);
}

// Network-first
async function networkFirst(request) {
  try {
    const response = await fetch(request);
    const cache = await caches.open('api-v1');
    cache.put(request, response.clone());
    return response;
  } catch {
    return caches.match(request);
  }
}

// Stale-while-revalidate
async function staleWhileRevalidate(request) {
  const cache = await caches.open('api-v1');
  const cached = await cache.match(request);
  const networkPromise = fetch(request).then((response) => {
    cache.put(request, response.clone());
    return response;
  });
  return cached || networkPromise; // serve stale now, update cache in background
}

Senior Engineer Perspective

Being able to write these three strategies from memory, unprompted, is one of the highest-leverage things to rehearse for this chapter — it's asked constantly and candidates who can only describe them in prose (not code) stand out negatively. Also mention response.clone() is required because a Response body stream can only be consumed once.

Q50. What is the Background Sync API, and what problem does it solve?

ROI: ★★★☆☆ Frequency: Low-Medium

Short Answer

Background Sync lets you register a deferred task (e.g. "send this queued POST") that the browser retries automatically once connectivity is restored, even if the user has closed the tab — the Service Worker wakes up to run it. It solves the problem of an action failing offline and being silently lost instead of eventually completing.

Detailed Answer

// Page: queue a sync when a request fails due to being offline
navigator.serviceWorker.ready.then((reg) => reg.sync.register('send-queued-posts'));

// Service worker: runs when connectivity returns, even without an open tab
self.addEventListener('sync', (event) => {
  if (event.tag === 'send-queued-posts') {
    event.waitUntil(flushQueuedRequestsFromIndexedDB());
  }
});

Support is uneven (notably absent in Safari for a long time), so it's typically used as a progressive enhancement on top of a working "retry on next app open" fallback, not a sole mechanism.

Senior Engineer Perspective

The honest, senior answer flags the browser support gap directly rather than presenting Background Sync as a universally available tool — knowing when a platform API needs a fallback strategy (queue in IndexedDB regardless, flush on next launch as a baseline) is more valuable than reciting the ideal-case API.

Q51. What cache invalidation strategies do you use for a Service Worker-backed app, beyond just versioned names?

ROI: ★★★★☆ Frequency: Medium

Short Answer

Beyond naming caches by version, common strategies include: content-hashed filenames (so a changed asset is simply a new URL, no invalidation needed), a manifest/precache-list diff (only re-fetch changed entries, à la Workbox precaching), TTL-based expiration for API response caches, and an explicit "update available" prompt that lets the user opt into activating the new Service Worker immediately.

Detailed Answer

Content-hashed filenames make cache invalidation nearly free — you never need to "invalidate" app.a1b2c3.js, you just stop referencing it once the manifest points to app.d4e5f6.js, and the old cache entry becomes unreferenced dead weight cleaned up at the next activate. For API data cached by the Service Worker, an expiration timestamp stored alongside the cached response (checked before returning it) implements a simple TTL layer on top of the Cache API, which has no built-in expiry.

Senior Engineer Perspective

The strongest answer connects this back to the "cache immutable hashed assets forever, never cache the HTML shell" strategy from the browser HTTP caching section — Service Worker caching for an app shell should follow the same philosophy, just implemented in JS instead of HTTP headers.

Q52. How do Service Workers enable push notifications?

ROI: ★★★☆☆ Frequency: Low-Medium

Short Answer

The Push API lets a server send a message to a Service Worker even when no tab is open, via a push subscription (endpoint URL + keys) the browser generates; the Service Worker's push event handler then uses the Notifications API to actually display a system notification to the user.

Detailed Answer

// Page: subscribe (requires user permission + a VAPID public key from your server)
const subscription = await registration.pushManager.subscribe({
  userVisibleOnly: true,
  applicationServerKey: VAPID_PUBLIC_KEY,
});
// send `subscription` to your backend to store and use for sending pushes later

// Service worker: react to an incoming push, must show a notification
self.addEventListener('push', (event) => {
  const data = event.data.json();
  event.waitUntil(self.registration.showNotification(data.title, { body: data.body }));
});

Senior Engineer Perspective

Note the two separate permissions/pieces involved: the Push API (server-to-browser message delivery, works even without an open tab) and the Notifications API (actually displaying UI) — conflating them is a common mistake. Also mention that userVisibleOnly: true is effectively mandatory in Chrome; silent pushes without a visible notification are disallowed to prevent abuse.

Q53. How do you debug Service Worker issues in production — the update flow, common pitfalls?

ROI: ★★★★☆ Frequency: Medium

Short Answer

Use the Application tab in DevTools to inspect the registration state, force an update, or unregister; the most common real-world pitfall is users being stuck on a stale version because the browser only checks for a new Service Worker script on navigation (and byte-for-byte identical scripts are treated as "no update"), so caching the Service Worker file itself with a long max-age silently prevents updates from ever being seen.

Detailed Answer

The browser re-fetches sw.js on every navigation (bypassing HTTP cache for that one file specifically per spec, but proxies/CDNs in front of it can still cache it incorrectly if misconfigured) and compares byte-for-byte against the currently installed worker; only a difference triggers the install/waiting/activate cycle. Debugging checklist: confirm the Service Worker file itself isn't cached long-term by a CDN, check "Update on reload" in DevTools during development, and use chrome://serviceworker-internals or the Application panel to inspect/force-unregister a stuck worker.

Senior Engineer Perspective

The "Service Worker file cached by a CDN with a long max-age" bug is a real, recurring production incident — being able to describe exactly why it happens (the byte-diff update check never sees new bytes because the CDN keeps serving the old file) is a strong, specific story to have ready.

Q54. Why do most production apps use Workbox instead of hand-rolling Service Worker logic?

ROI: ★★★☆☆ Frequency: Medium

Short Answer

Workbox provides battle-tested implementations of the caching strategies (cache-first, network-first, stale-while-revalidate), automatic precache manifest generation tied to your build output, and safe cache versioning/cleanup — all the easy-to-get-subtly-wrong parts of hand-rolled Service Worker code, with far less boilerplate and fewer footguns.

Detailed Answer

Hand-rolling correctly requires getting the lifecycle (skipWaiting/clients.claim trade-offs), cache versioning/cleanup, strategy selection per route, and background revalidation all right simultaneously — easy to get partially wrong in ways that only surface as intermittent "stale content" bug reports. Workbox (often wired in automatically by the Vite PWA plugin or Create React App's PWA template) encodes these as declarative route-matching rules instead.

Code Example

import { registerRoute } from 'workbox-routing';
import { StaleWhileRevalidate, CacheFirst } from 'workbox-strategies';

registerRoute(({ request }) => request.destination === 'image', new CacheFirst());
registerRoute(({ url }) => url.pathname.startsWith('/api/'), new StaleWhileRevalidate());

Senior Engineer Perspective

The mature answer isn't "always use Workbox" — for a tiny, single-strategy Service Worker, hand-rolling is simpler to reason about and debug. Knowing when the abstraction earns its complexity (multiple routes/strategies, precache manifest management tied to a build) versus when it's overkill is the actual judgment being tested.

SECTION 10 - WEB WORKERS REVISITED FROM A PLATFORM ANGLE

Q55. What is the structured clone algorithm, and what can't it clone?

ROI: ★★★★☆ Frequency: Medium-High

Short Answer

The structured clone algorithm is how data is copied when passed via postMessage (to a Worker, another tab via BroadcastChannel, or into IndexedDB) — it deep-copies most JS values (objects, arrays, Maps, Sets, Dates, ArrayBuffers, Blobs) but cannot clone functions, DOM nodes, or values with prototype chains it doesn't recognize (like class instances with methods — only their own enumerable data properties survive, and the prototype/methods are lost).

Detailed Answer

Circular references are actually handled correctly (unlike JSON.stringify, which throws on them) — this is a common thing people get backwards, assuming structured clone is strictly weaker than JSON serialization. What it truly can't handle: functions/closures, Error objects (partially supported, inconsistently across engines), DOM elements, and any object relying on identity/prototype methods rather than plain data.

Senior Engineer Perspective

The circular-reference detail is a great correction to offer if an interviewer implies structured clone is "just like JSON.stringify but for postMessage" — it's actually more capable in that specific respect, which shows precise, non-superficial knowledge.

Q56. What are Transferable objects, and how do they enable zero-copy messaging?

ROI: ★★★★☆ Frequency: Medium

Short Answer

By default, postMessage copies data via structured clone, which is expensive for large payloads (e.g. a big ArrayBuffer). Marking an object as transferable moves ownership of its underlying memory to the receiving context instead of copying it — the sending side's reference becomes unusable (detached), but the transfer itself is near-instant regardless of size.

Detailed Answer

const buffer = new ArrayBuffer(64 * 1024 * 1024); // 64MB
// Second argument lists objects to TRANSFER rather than clone
worker.postMessage(buffer, [buffer]);
console.log(buffer.byteLength); // 0 — detached, no longer usable here

// worker.js
onmessage = (e) => {
  const buffer = e.data; // now owned here, full 64MB, no copy was made
};

ArrayBuffer, MessagePort, ImageBitmap, and OffscreenCanvas are transferable. Typed arrays (Uint8Array etc.) are not directly transferable — you transfer their underlying .buffer.

Senior Engineer Perspective

The detached-buffer gotcha (the sending side's variable becomes a zero-length, unusable reference after transfer) is a real bug source if code assumes it can still read the buffer after posting it — worth mentioning unprompted as the trade-off for the zero-copy performance win.

Q57. What is SharedArrayBuffer, and why is it gated behind COOP/COEP headers?

ROI: ★★★☆☆ Frequency: Low-Medium

Short Answer

SharedArrayBuffer gives multiple threads (main thread and Workers) true shared memory — both sides read/write the same underlying bytes with no copying, coordinated via Atomics for safe concurrent access. It's restricted to "cross-origin isolated" pages (requiring Cross-Origin-Opener-Policy and Cross-Origin-Embedder-Policy headers) because unrestricted shared memory with high-resolution timing enabled a practical Spectre side-channel attack, which is why browsers disabled it broadly after Spectre was disclosed and only re-enabled it under this stricter isolation.

Detailed Answer

Cross-origin isolation (COOP+COEP) guarantees no cross-origin document/resource shares the same process/memory space unless it explicitly opts in (via CORP/CORS), closing the side-channel that made shared, precisely-timed memory dangerous. This is a meaningful deployment cost — every subresource must be either same-origin or explicitly opt in with Cross-Origin-Resource-Policy, which breaks some third-party embeds/ads until they update.

Senior Engineer Perspective

Knowing the Spectre connection (not just "you need special headers") demonstrates you understand this isn't an arbitrary API restriction but a direct, security-driven response to a real hardware-level vulnerability class — a good example of platform security shaping API availability.

Q58. What's the difference between a dedicated Worker and a SharedWorker?

ROI: ★★★☆☆ Frequency: Low-Medium

Short Answer

A dedicated Worker is owned by exactly one script/tab that created it. A SharedWorker can be connected to from multiple tabs/scripts of the same origin simultaneously, communicating over a MessagePort per connection — useful for coordinating state or a single shared resource (e.g. one WebSocket connection) across many open tabs instead of duplicating it per tab.

Detailed Answer

// Each tab connects to the SAME shared worker instance
const worker = new SharedWorker('shared.js');
worker.port.postMessage('hello');
worker.port.onmessage = (e) => console.log(e.data);

// shared.js — one instance serving all connected tabs
onconnect = (e) => {
  const port = e.ports[0];
  port.onmessage = (event) => port.postMessage('echo: ' + event.data);
};

SharedWorker support and debuggability is notably weaker/less consistent across browsers than dedicated Workers, which limits its real-world adoption despite the useful cross-tab-coordination use case.

Senior Engineer Perspective

Mentioning that BroadcastChannel often solves the "coordinate across tabs" use case more simply than SharedWorker (at the cost of each tab still doing its own work rather than sharing one instance) shows you'd pick the pragmatic tool rather than the most powerful one by default.

Q59. How do you manage Worker lifecycle and avoid memory leaks from workers?

ROI: ★★★★☆ Frequency: Medium

Short Answer

A Worker you create with new Worker(...) keeps running (and holding memory) until you explicitly call worker.terminate() or the owning page unloads — React unmounting a component does not automatically kill a worker it created, so cleanup must be done manually, typically in a useEffect cleanup function.

Detailed Answer

useEffect(() => {
  const worker = new Worker(new URL('./heavy.js', import.meta.url));
  worker.onmessage = (e) => setResult(e.data);
  worker.postMessage(input);
  return () => worker.terminate(); // MUST clean up, or it leaks
}, [input]);

Beyond forgetting to terminate, a subtler leak: closures captured in onmessage handlers can retain references to large objects/component state even after the component unmounts, if the worker itself is kept alive elsewhere (e.g. hoisted to module scope for reuse across mounts) without being told to stop referencing stale callbacks.

Senior Engineer Perspective

"Workers don't die with the component that spawned them" is exactly the kind of non-obvious lifecycle fact interviewers use to separate people who've actually shipped worker-based features from people who've only read the API docs.

Q60. What problem does Comlink solve, and how does it change the ergonomics of Worker messaging?

ROI: ★★★☆☆ Frequency: Low-Medium

Short Answer

Raw postMessage/onmessage is callback-based, stringly-typed by message shape, and gets unwieldy once you need multiple concurrent request/response pairs (matching replies to requests, error propagation, etc.). Comlink wraps a Worker in a JS Proxy so calling a function on it looks and behaves like a normal async function call, handling the message-passing plumbing underneath.

Detailed Answer

// worker.js
import { expose } from 'comlink';
const api = { heavyCompute: (data) => /* ... */ };
expose(api);

// main.js
import { wrap } from 'comlink';
const worker = wrap(new Worker('worker.js'));
const result = await worker.heavyCompute(data); // reads like a normal async call

Senior Engineer Perspective

Framing Comlink as "an ergonomics layer over postMessage, not a different messaging model" is the correct level of understanding — it still incurs the same structured-clone/transfer costs underneath; it just hides the message-matching boilerplate, which matters for maintainability on any non-trivial worker integration.

Q61. What is OffscreenCanvas, and why does it matter for rendering performance?

ROI: ★★★☆☆ Frequency: Low-Medium

Short Answer

OffscreenCanvas lets you render to a <canvas> from inside a Web Worker instead of the main thread, so heavy drawing (complex charts, games, image processing) doesn't compete with the main thread for layout/paint/input handling — the canvas's bitmap is later composited to the visible <canvas> element without blocking user interactions.

Detailed Answer

// main.js
const canvas = document.querySelector('canvas');
const offscreen = canvas.transferControlToOffscreen(); // canvas control moves to worker
worker.postMessage({ canvas: offscreen }, [offscreen]); // transferable

// worker.js
onmessage = (e) => {
  const ctx = e.data.canvas.getContext('2d');
  // heavy drawing loop here, off the main thread entirely
};

Senior Engineer Perspective

This is the concrete answer to "how would you keep a data-heavy real-time chart from janking scroll/input on the main thread" — pairing OffscreenCanvas with the earlier Transferable-objects concept (the canvas handle itself is transferred, not copied) ties this whole section together nicely.

Q62. When do Web Workers hurt more than they help?

ROI: ★★★★☆ Frequency: Medium

Short Answer

Workers add real overhead: spinning one up has non-trivial startup cost, and every message crossing the boundary pays a structured-clone serialization cost unless you use transferables. For small or infrequent tasks, that overhead can exceed whatever main-thread time you were trying to save — workers are a tool for genuinely expensive, chunky computation, not a blanket "move everything off the main thread" strategy.

Detailed Answer

Concretely: spawning a worker per small task (rather than reusing a pool), passing large non-transferable objects back and forth repeatedly, or offloading work that's already fast (a few milliseconds) all tend to net negative once you account for worker startup and message-passing latency. The right trigger to reach for a worker is a profiler showing a genuinely long main-thread task (dozens to hundreds of ms), not a hunch.

Senior Engineer Perspective

This question tests restraint, not just knowledge — the strongest engineers explicitly say "I'd profile first, confirm the task is actually blocking the main thread meaningfully, and only then introduce a worker (or a worker pool for repeated small tasks) given its non-zero fixed costs."

Q63. How do you read a flamechart in the Performance tab to find what's blocking the main thread?

ROI: ★★★★★ Frequency: High

Short Answer

The flamechart shows the call stack over time: each horizontal bar is a function call, its width is duration, and stacking downward shows nested calls. You look for wide bars (long-running functions) and specifically for red-flagged bars over 50ms, which the DevTools UI marks as "Long Tasks" — these are the ones that block input responsiveness.

The "Bottom-Up" and "Call Tree" tabs beneath the flamechart let you aggregate self-time across many calls to the same function, which a single flamechart glance can miss if the cost is spread across many small invocations rather than one big one.

Senior Engineer Perspective

The most common mistake is stopping at the widest bar in the flamechart without checking "Bottom-Up" for aggregate self-time — a function that's individually cheap but called 10,000 times can dominate total time despite never showing up as a single wide bar. Mentioning both views shows real profiling experience, not just "I looked at the flamechart once."

Q65. How do you use the Memory tab to hunt down a leak, and what's a "detached DOM node"?

ROI: ★★★★☆ Frequency: Medium-High

Short Answer

Take two heap snapshots before and after a suspected-leaky action repeated several times, then use the "Comparison" view to see which object types grew and didn't shrink back. A detached DOM node is a DOM element removed from the visible tree but still referenced by JS (a stale closure, an event listener, a cached reference), so the garbage collector can't reclaim it.

Detailed Answer

Practical workflow: (1) take snapshot A, (2) perform the suspect action (open/close a modal, navigate a route) several times, forcing GC between each via the trash-can icon, (3) take snapshot B, (4) filter the comparison for "Detached" in the class filter to directly surface orphaned DOM subtrees. Common causes: an event listener attached to window/document never removed on unmount, a setInterval holding a closure over component state, or a third-party library caching a DOM reference internally.

Senior Engineer Perspective

In React specifically, the number one source of this is a useEffect that subscribes/attaches a listener without a matching cleanup function — describing that exact cause-and-fix pair, having actually done this walk in DevTools, is what distinguishes real debugging experience from textbook knowledge.

Q66. What does the Coverage tab tell you, and how do you act on it?

ROI: ★★★☆☆ Frequency: Medium

Short Answer

The Coverage tab (Cmd/Ctrl+Shift+P → "Show Coverage") records which lines of loaded JS and CSS actually executed/applied during a session, showing a percentage of unused bytes per file — a direct signal for what to code-split, lazy-load, or remove.

Detailed Answer

High "unused bytes" on a large vendor bundle usually means: a library is imported wholesale when only a small part is used (tree-shaking opportunity), a route's code is bundled into the main chunk when it should be lazily loaded, or dead CSS (from an old design system, or a CSS-in-JS setup emitting unused variants) is shipping unconditionally. Recording coverage across multiple page interactions (not just initial load) avoids false positives for code that's used later, just not on that page.

Senior Engineer Perspective

The nuance to raise: coverage is session-specific — code unused on the page you tested might be critical on another route, so treat it as a lead for investigation (code-splitting candidates), not an automatic "delete this" signal. That caution is what keeps this from being a naive answer.

Q67. Lighthouse/PageSpeed Insights — what's the difference between lab data and field data, and how does that affect which Core Web Vitals you trust?

ROI: ★★★★★ Frequency: High

Short Answer

Lighthouse produces lab data — a single simulated run on a controlled device/network profile, useful for debugging and reproducibility but not representative of real users. Detailed Answer

Senior Engineer Perspective

A senior answer catches the common mistake of chasing a perfect Lighthouse score (a lab artifact, single run, single device profile) while field data (real users, real devices, real networks) tells a different story — and specifically that INP cannot be meaningfully lab-tested at all, only measured in the field.

Q71. IntersectionObserver deep dive — how do thresholds work, and can one element have multiple observers?

ROI: ★★★★☆ Frequency: Medium-High

Short Answer

threshold controls at what intersection ratio (0 to 1) the callback fires — a single number fires once crossing that ratio, an array fires once per ratio crossed in either direction, enabling fine-grained "how much of this element is visible" tracking. Yes, one element can be observed by multiple independent IntersectionObserver instances simultaneously, each with its own root/threshold/callback.

Detailed Answer

// Fires at 0%, 25%, 50%, 75%, 100% visibility — great for scroll-progress-style effects
const io = new IntersectionObserver((entries) => {
  entries.forEach((entry) => {
    console.log(entry.intersectionRatio, entry.isIntersecting);
  });
}, { threshold: [0, 0.25, 0.5, 0.75, 1] });

The root option lets you observe intersection against a scrollable ancestor instead of the viewport (default null = viewport) — essential for lazy-loading inside a scrollable panel rather than the whole page.

Senior Engineer Perspective

A common bug: forgetting that the callback fires on both entering and leaving a threshold — checking only entry.isIntersecting without also checking direction/ratio can cause logic meant for "just became visible" to also fire on "just became invisible." Calling this out shows real usage, not just API familiarity.

Q72. What is ResizeObserver, and what does it solve that media queries can't?

ROI: ★★★★☆ Frequency: Medium-High

Short Answer

ResizeObserver notifies you when a specific element's size changes, regardless of why it changed (viewport resize, sibling content changing, a flex/grid reflow, font loading) — media queries only know about the viewport, not an individual element's actual rendered size. This is exactly what "container queries" for JS-driven responsive components need: a card in a sidebar should respond to its own width, not the page's.

Detailed Answer

const ro = new ResizeObserver((entries) => {
  for (const entry of entries) {
    const { width } = entry.contentRect;
    element.classList.toggle('compact', width < 300);
  }
});
ro.observe(cardElement);

Since native CSS Container Queries (@container) shipped broadly, many purely-visual "resize this element's layout" use cases have moved back to CSS — ResizeObserver remains the right tool when the response needs actual JS logic (recalculating a canvas, virtualized list row heights, chart re-layout), not just CSS rule switching.

Senior Engineer Perspective

Naming the overlap and hand-off with CSS Container Queries — "use @container for pure styling responses, ResizeObserver only when you need to run actual JavaScript on resize" — shows you're not reaching for a JS API where a simpler, cheaper CSS primitive now exists.

Q73. What is MutationObserver, and what are its performance considerations?

ROI: ★★★★☆ Frequency: Medium

Short Answer

MutationObserver watches a DOM subtree for changes (child list, attributes, text content) and delivers batched mutation records asynchronously as a microtask — far cheaper than the deprecated, synchronous "Mutation Events" it replaced. Use cases: integrating with third-party widgets that mutate the DOM outside your control, implementing a rich-text editor's change detection, or detecting when a class/attribute injected by another script appears.

Detailed Answer

const mo = new MutationObserver((mutations) => {
  for (const m of mutations) {
    if (m.type === 'childList') handleChildrenChanged(m);
  }
});
mo.observe(container, { childList: true, subtree: true, attributes: true });

Because it observes at the DOM level rather than the framework level, using it inside a React app to react to React's own DOM output is usually a smell — you're watching the effect (DOM) instead of the cause (state/props) that a useEffect would already give you cleanly. Legitimate uses are almost always about DOM changes outside React's control (a third-party script, browser extension, or a non-React widget embedded in the page).

Senior Engineer Perspective

Flagging "if you're reaching for MutationObserver inside a React component to detect your own component's DOM changes, you probably want a useEffect dependency instead" is the kind of react-vs-platform judgment senior interviewers want to hear, since the correct layer to observe change at matters more than the API's existence.

Q74. How do you use matchMedia to respond to media queries in JavaScript?

ROI: ★★★☆☆ Frequency: Medium

Short Answer

window.matchMedia(query) returns a live MediaQueryList object with a .matches boolean and a change event, letting JS react to the same breakpoints/media features CSS uses (viewport width, prefers-color-scheme, prefers-reduced-motion) without polling window.innerWidth on every resize.

Detailed Answer

const mql = window.matchMedia('(prefers-reduced-motion: reduce)');
function applyMotionPref(e) {
  document.body.classList.toggle('no-animations', e.matches);
}
applyMotionPref(mql); // check initial state
mql.addEventListener('change', applyMotionPref); // react to OS-level changes

This is the right tool specifically for user/OS preference media features (reduced motion, color scheme, reduced data) that a component needs to branch JS logic on (e.g. skip a heavy animation library entirely), rather than just changing CSS — for pure styling, a media query in CSS is simpler and doesn't need JS at all.

Senior Engineer Perspective

Respecting prefers-reduced-motion via matchMedia to conditionally skip a JS-driven animation library (not just a CSS transition) is a concrete accessibility-performance win worth naming — it shows the API used for an actual product requirement, not a syntax demo.

Q75. What is the BroadcastChannel API, and how does it enable cross-tab communication?

ROI: ★★★☆☆ Frequency: Medium

const channel = new BroadcastChannel('auth');

// Tab A: user logs out

// Tab B, C, ...: react instantly
channel.onmessage = (event) => {

Q76. What is the Page Visibility API, and what real problems does it solve?

ROI: ★★★★☆ Frequency: Medium

Short Answer

document.addEventListener('visibilitychange', () => {
  if (document.visibilityState === 'hidden') {
    pausePolling();
  } else {
    resumePollingAndRefetch(); // catch up on anything missed while backgrounded
  }
});

This directly underlies TanStack Query's/SWR's "refetch on window focus" default behavior, and is the correct way to pause a polling interval instead of relying on the inaccurate assumption that backgrounded tabs are simply throttled (they may be, browser-dependent and inconsistent — this API tells you definitively).

Q77. How does the Clipboard API work, and what are its permission/security constraints?

ROI: ★★★☆☆ Frequency: Medium

Short Answer

navigator.clipboard.writeText()/readText() is the modern, promise-based replacement for the old document.execCommand('copy') hack. Writing generally requires the action to originate from a genuine user gesture (a click handler); reading is more tightly gated and often requires an explicit permission prompt, since silently reading clipboard contents is a real privacy risk.

Detailed Answer

async function copyToClipboard(text) {
  try {
    await navigator.clipboard.writeText(text);
  } catch {
    // Fallback for older browsers / non-secure contexts
    const el = document.createElement('textarea');
    el.value = text;
    document.body.appendChild(el);
    el.select();
    document.execCommand('copy');
    document.body.removeChild(el);
  }
}

The API requires a secure context (HTTPS or localhost) and, for writes, is typically only allowed synchronously within a trusted user-initiated event handler — calling it after an await inside that handler can silently fail in some browsers because the "user gesture" context has expired by then.

Senior Engineer Perspective

The "user gesture expires across an await" gotcha is a real, specific bug people hit when they add an async step (e.g. fetching text to copy) before calling writeText — flagging it unprompted, along with keeping a legacy fallback for older browsers, shows production battle scars.

Q78. What is the Web Share API, and how should you feature-detect it?

ROI: ★★★☆☆ Frequency: Low-Medium

Short Answer

navigator.share() invokes the operating system's native share sheet (the same one native apps use) to share a URL/text/files to other installed apps — well supported on mobile browsers, historically inconsistent on desktop. Because support varies, you always feature-detect (if ('share' in navigator)) and provide a manual fallback (copy-link button, custom share menu) rather than assuming availability.

Detailed Answer

async function shareOrFallback(data) {
  if (navigator.share) {
    try {
      await navigator.share(data); // { title, text, url } — must be from a user gesture
    } catch (err) {
      if (err.name !== 'AbortError') console.error(err); // user cancelling isn't an error
    }
  } else {
    showCustomShareMenu(data); // manual fallback UI
  }
}

Senior Engineer Perspective

Handling AbortError distinctly (thrown when the user simply cancels the native share sheet, not a real failure) rather than logging it as an error is a small correctness detail that's easy to get wrong and shows careful, tested error handling rather than a copy-pasted snippet.

SECTION 13 - THE RENDERING PIPELINE: LAYOUT, PAINT, COMPOSITE

Q79. Which CSS property changes are cheap (compositor-only) vs expensive (trigger layout)?

ROI: ★★★★★ Frequency: High

Short Answer

Changing transform and opacity can skip both layout and paint entirely, handled purely by the GPU compositor — the cheapest possible visual change. Changing colors/shadows/visibility triggers a repaint but not layout. Changing anything that affects geometry — width, height, top/left, margin, padding, font size — triggers a full layout (reflow), the most expensive path.

Detailed Answer

ChangeLayout?Paint?Composite?
transform, opacityNoNoYes only
color, background, box-shadow, visibilityNoYesYes
width, height, top, left, margin, font-size, displayYesYesYes

This is why performant animations always animate transform: translate/scale/rotate instead of left/top/width, and animate opacity instead of visibility/display toggling wherever the visual effect can be achieved either way.

Senior Engineer Perspective

Being able to name this table cold — not just "transform is fast" as a slogan, but which specific properties fall in each bucket and why (geometry vs paint-only vs pure compositing) — is one of the single highest-ROI facts in this entire chapter for any frontend performance conversation.

Q80. What is a compositor "layer," and how do you (intentionally, carefully) promote an element to its own layer?

ROI: ★★★★☆ Frequency: Medium-High

Short Answer

A layer is a separate surface the GPU can composite independently, letting the browser animate/transform it without repainting the rest of the page. will-change: transform (or an existing transform/opacity animation, fixed-position elements, video/canvas elements) hints the browser to promote an element to its own layer ahead of time.

Detailed Answer

.modal {
  will-change: transform; /* hint: this will animate, promote it now */
}

Layer promotion isn't free: each layer consumes GPU memory, and too many layers ("layer explosion") can cause worse performance than no promotion at all, especially on memory-constrained mobile devices. will-change should be applied shortly before the animation starts and removed after, not left on every element "just in case" — leaving it permanently defeats its purpose and wastes memory indefinitely.

Senior Engineer Perspective

The "layer explosion" failure mode — sprinkling will-change everywhere actually degrading performance — is the crucial caveat that separates someone who's read a blog post from someone who's actually profiled a real regression caused by over-promoting layers.

Q81. What is layout thrashing, and how does the FastDOM read/write batching pattern fix it?

ROI: ★★★★★ Frequency: High

Short Answer

Layout thrashing happens when code interleaves DOM writes and layout-triggering reads in a loop — each read after a write forces the browser to synchronously recompute layout early (instead of batching it once before the next paint), and doing this repeatedly in a loop can make an operation dozens of times slower. The fix is to batch all reads first, then all writes, so only one forced layout happens instead of N.

Detailed Answer

// BAD: read-write-read-write interleaved — forces layout on every iteration
elements.forEach((el) => {
  const height = el.offsetHeight;   // READ (forces layout if a write is pending)
  el.style.height = height * 2 + 'px'; // WRITE (invalidates layout again)
});

// GOOD: batch all reads, then all writes
const heights = elements.map((el) => el.offsetHeight); // all READS first
elements.forEach((el, i) => { el.style.height = heights[i] * 2 + 'px'; }); // all WRITES after

Properties like offsetHeight, offsetWidth, getBoundingClientRect(), and getComputedStyle() all force a synchronous layout recalculation if the layout is currently "dirty" from a prior write — that's the specific mechanism behind the slowdown.

Senior Engineer Perspective

Naming the exact list of layout-forcing read properties (offsetHeight, getBoundingClientRect, getComputedStyle, etc.) — not just "reading after writing is bad" — is what shows you've actually diagnosed this in a profiler rather than repeating advice you read once.

Q82. What are the risks of over-using GPU compositing (too many layers)?

ROI: ★★★☆☆ Frequency: Medium

Short Answer

Each composited layer consumes its own GPU texture memory, and compositing many overlapping layers requires the GPU to blend them together every frame — beyond a certain count (and especially on lower-end/mobile GPUs), this "layer explosion" causes memory pressure and can make compositing itself the bottleneck, ironically worse than a simpler, non-layered repaint would have been.

Detailed Answer

This typically happens from over-applying will-change/transform: translateZ(0) hacks broadly (a once-common "force GPU acceleration" trick applied indiscriminately), or from many small animated elements each getting their own layer. DevTools' "Layers" panel (under More Tools) visualizes exactly which elements have their own composited layer and why, letting you spot unintentional/excessive promotion.

Senior Engineer Perspective

Bringing up the DevTools Layers panel specifically as the tool to verify layer count (rather than guessing) shows you'd diagnose this empirically instead of applying "GPU acceleration" as folklore — a good, concrete answer to "how would you know if you've over-promoted layers?"

Q83. What causes Cumulative Layout Shift (CLS), and how do you prevent it?

ROI: ★★★★★ Frequency: High

Short Answer

CLS measures unexpected layout movement — most commonly caused by images/ads/embeds without reserved dimensions (content pops in and pushes everything down), web fonts swapping to a different-metric fallback, or content being injected above existing content (a banner appearing at the top of the page after load). Prevent it by always reserving space (explicit width/height or aspect-ratio) for anything that loads asynchronously.

Detailed Answer

<!-- Reserve space via aspect-ratio so the image doesn't cause a shift when it loads -->
<img src="hero.jpg" width="1200" height="600" style="aspect-ratio: 1200/600; width:100%; height:auto;">
  • Always set explicit dimensions (or aspect-ratio) on images, videos, and embeds/iframes.
  • Reserve space for ads/dynamic content with a fixed-size container rather than letting content push the layout as it loads.
  • Use font-display: optional or metric-matched fallback fonts to avoid a font-swap-driven shift.
  • Never insert new content above existing content unless it's in response to a direct user interaction.

Senior Engineer Perspective

The "never insert content above existing content except in response to a user interaction" rule is the one most people forget — CLS is only penalized for unexpected shifts, so a shift caused directly by a user's own click (expanding an accordion) isn't counted against you, but an ad loading in above the fold unprompted is.

Q84. How do the content-visibility and contain CSS properties improve rendering performance?

ROI: ★★★★☆ Frequency: Medium-High

Short Answer

content-visibility: auto tells the browser to skip layout/paint work entirely for an element's contents while it's off-screen, dramatically speeding up initial render for very long pages — the browser only does the work once the element scrolls near the viewport. contain (layout/paint/size/style) tells the browser an element's internals won't affect the outside layout, letting it scope layout/paint recalculation to just that subtree instead of the whole document.

Detailed Answer

.long-list-item {
  content-visibility: auto;
  contain-intrinsic-size: 0 120px; /* placeholder size so scrollbar doesn't jump */
}

Without contain-intrinsic-size, an off-screen content-visibility: auto element collapses to zero height until rendered, which can throw off scrollbar size and scroll-position calculations — pairing the two properties is the correct usage pattern. contain: layout alone (without skipping paint) is useful for isolating a component's internal layout changes from triggering a reflow of unrelated siblings, a lighter-weight tool than full virtualization.

Senior Engineer Perspective

Framing content-visibility: auto as "a cheap, CSS-only alternative to full list virtualization" for long lists/pages, with the caveat that it needs contain-intrinsic-size to avoid scrollbar jumpiness, is a strong, currently-relevant performance answer that many candidates haven't caught up on yet.

Q85. requestAnimationFrame vs CSS animations/transitions — which should drive a given animation, and why?

ROI: ★★★★☆ Frequency: Medium-High

Short Answer

CSS animations/transitions (especially of transform/opacity) can run on the compositor thread, unaffected by main-thread JS work, and are the default choice for most UI animation. requestAnimationFrame is for animations that need per-frame JavaScript logic (physics, canvas drawing, syncing to scroll position, complex interpolation) — it still runs on the main thread but is scheduled correctly, right before the browser's next paint.

Detailed Answer

function animate(timestamp) {
  const progress = computeProgress(timestamp);
  element.style.transform = `translateX(${progress}px)`; // still cheap: transform-only
  if (progress < target) requestAnimationFrame(animate);
}
requestAnimationFrame(animate);

Because requestAnimationFrame callbacks run on the main thread, a long synchronous task elsewhere can delay or drop frames — CSS-driven compositor animations don't have this weakness since they run independent of main-thread JS congestion. The rule of thumb: prefer CSS for simple enter/exit/hover transitions; reach for requestAnimationFrame (or a library like Framer Motion/GSAP built on it) only when the animation genuinely needs JS-computed values per frame.

Senior Engineer Perspective

The key differentiator to state clearly: CSS compositor animations are immune to main-thread jank, requestAnimationFrame is not — so an app with heavy main-thread work (data processing, large re-renders) will see CSS animations stay smooth while rAF-driven ones stutter, which is a real, diagnosable production distinction.

Q86. What does contain: paint (or strict/content) actually isolate, and when would you reach for it?

ROI: ★★★☆☆ Frequency: Low-Medium

Short Answer

contain: paint clips an element's descendants to its own bounding box and guarantees nothing inside it paints outside those bounds, letting the browser scope repaint calculations to just that element instead of re-checking siblings/ancestors. contain: strict combines layout, paint, size, and style containment for maximum isolation — the strongest guarantee, most appropriate for self-contained widgets (a chat message, a card in a grid) whose internal changes should never affect anything outside them.

Detailed Answer

This matters most for components that update frequently and independently — a live chat panel where new messages append constantly benefits from contain: layout paint on each message so the browser doesn't have to reason about whether adding one message could ripple into unrelated layout elsewhere on the page. It's a lighter-weight sibling to content-visibility: auto — containment scopes recalculation without skipping the work for off-screen content entirely.

Senior Engineer Perspective

Distinguishing contain (scopes/limits recalculation to a subtree, still does the work) from content-visibility: auto (skips the work entirely while off-screen) is the precise technical distinction that shows you understand these as two different tools on the same spectrum, not interchangeable performance hints.

SECTION 14 - BROWSER COMPATIBILITY & PROGRESSIVE ENHANCEMENT STRATEGIES

Q87. Why does feature detection beat user-agent sniffing, and how do you do it correctly?

ROI: ★★★★★ Frequency: High

Short Answer

Feature detection checks whether a specific API/property actually exists at runtime before using it; UA sniffing parses the (unreliable, spoofable, constantly-changing) navigator.userAgent string to guess capabilities indirectly. Feature detection is correct by construction — if the check passes, the feature genuinely works, regardless of which browser or version you're on, including ones that didn't exist when the code was written.

Detailed Answer

// Feature detection: directly asks "does this exist / work?"
if ('IntersectionObserver' in window) { /* use it */ }
if (CSS.supports('aspect-ratio', '1/1')) { /* use it in JS-driven logic */ }

// UA sniffing: fragile, breaks on new browser versions, spoofable, and often just wrong
if (navigator.userAgent.includes('Chrome')) { /* assume some feature works — unreliable */ }

UA strings are also actively becoming less reliable by design — the User-Agent Client Hints API and browsers "freezing"/genericizing parts of the UA string for privacy reasons mean UA-string-based branching is increasingly broken even for browsers it once worked for.

Senior Engineer Perspective

Mentioning that browsers are deliberately reducing UA string fidelity (client hints, UA freezing) for privacy reasons — meaning UA sniffing isn't just old-fashioned but actively getting worse over time — shows you're tracking platform direction, not just repeating "sniffing is bad" as received wisdom.

Q88. What's the philosophical difference between progressive enhancement and graceful degradation?

ROI: ★★★★☆ Frequency: Medium-High

Short Answer

Progressive enhancement starts from a minimal, working baseline (semantic HTML, works with no JS/CSS) and layers on enhancements for capable browsers. Graceful degradation starts from the full-featured experience and tries to make it not break too badly on less-capable browsers. The former guarantees a working floor; the latter guarantees a working ceiling and hopes the floor isn't too broken.

Detailed Answer

Concretely: a form built progressive-enhancement-style submits via a real HTML <form action="..."> that works with JS disabled, then JS intercepts submission for a smoother SPA-style experience when available. A graceful-degradation-style form might be built entirely dependent on JS/fetch, with a fallback message shown ("JavaScript required") if it fails — functional, but there's no true no-JS baseline, just an apology.

Senior Engineer Perspective

Modern frontend heavily favors progressive enhancement for the parts that matter most (critical paths like checkout/auth), even in JS-heavy SPAs, because it also happens to align with better resilience to network failures and slow JS execution, not just old-browser support — reframing this as a resilience strategy, not just a legacy-browser concern, is the senior angle.

Q89. What is the module/nomodule pattern for differential serving, and is polyfilling still necessary today?

ROI: ★★★☆☆ Frequency: Medium

Short Answer

The module/nomodule pattern serves a modern, smaller ES module bundle to browsers that support <script type="module"> (which implies broad modern-JS support) and a transpiled, polyfilled legacy bundle to everything else via <script nomodule>, which modern browsers simply ignore. Whether you still need this (or any polyfilling) depends entirely on your actual analytics-verified browser support matrix — many teams today can drop legacy bundles/polyfills entirely if their real users are on evergreen browsers.

Detailed Answer

<script type="module" src="app.modern.js"></script>
<script nomodule src="app.legacy.js"></script>

Modern browsers download and execute only the module script and ignore the nomodule one entirely; legacy browsers that don't understand type="module" ignore that script and run the nomodule fallback instead — pure browser-native branching, no server-side UA detection needed. Strategic polyfilling means loading polyfills conditionally (via a service like polyfill.io historically, or a build-time check) only for browsers that actually lack the feature, rather than shipping every polyfill to every user unconditionally.

Senior Engineer Perspective

The senior answer is data-driven, not dogmatic: check your actual analytics for real legacy-browser traffic before deciding to maintain a dual-bundle build at all — many teams have simplified their build entirely by dropping IE11/legacy support once data showed near-zero real usage, removing significant build complexity for negligible user impact.

Q90. How do CSS @supports feature queries work, and how do they compare to JS feature detection?

ROI: ★★★★☆ Frequency: Medium

Short Answer

@supports (property: value) lets CSS itself branch on whether a browser supports a given property/value pair, providing a fallback rule set for browsers that don't — the CSS equivalent of JS feature detection, and just as reliable (it tests actual support, not a UA guess).

Detailed Answer

.grid {
  display: flex; /* fallback for browsers without grid support */
}

@supports (display: grid) {
  .grid {
    display: grid; /* used instead, only where actually supported */
  }
}

This is more elegant than a JS-detected class toggle for purely-visual fallbacks, since it requires no JavaScript at all and evaluates before first paint — no flash of incorrect layout while JS detection runs. Q92. What's a solid cross-browser testing strategy, including visual regression?

ROI: ★★★★☆ Frequency: Medium

Short Answer

Layer automated checks: unit/integration tests run once (browser-agnostic where possible), then a smaller set of true cross-browser E2E tests (via Playwright/BrowserStack/Sauce Labs) covering critical user flows across your actual target browser matrix, plus visual regression testing (Percy, Chromatic, Playwright's screenshot comparison) to catch unintended pixel-level CSS/layout differences that functional tests miss entirely.

Detailed Answer

Functional E2E tests confirm behavior works, but they don't catch a broken CSS grid on Safari or a subtly wrong font rendering on Firefox — visual regression tools screenshot key pages/components per browser and diff them against a baseline, flagging pixel changes for human review. Running the full cross-browser matrix on every commit is often too slow/expensive, so a common pattern is: fast checks (linting, unit tests, one-browser E2E) on every PR, full cross-browser + visual regression suite on merge to main or nightly.

Senior Engineer Perspective

The pragmatic, cost-aware framing — tiering test suites by speed/cost rather than running the full cross-browser matrix on every single commit — is what shows real ownership of a CI pipeline's economics, not just theoretical knowledge that cross-browser testing tools exist.

Q94. How do you build a resilient app that works reasonably well on older browsers/devices without over-engineering for them?

ROI: ★★★★☆ Frequency: Medium

Short Answer

Combine progressive enhancement for the critical path (core content/actions work with minimal JS/CSS assumptions), feature detection with graceful fallbacks for enhancements, and — most importantly — a data-driven decision about exactly how much legacy support is actually worth the engineering cost, based on your real analytics rather than a hypothetical worst case.

Detailed Answer

Practical checklist: server-render or provide real HTML fallbacks for critical content rather than requiring JS to render anything at all; feature-detect and gracefully skip non-essential enhancements (fancy animations, advanced APIs) rather than crashing when they're unavailable; set an explicit, documented support matrix (e.g. "last 2 versions of evergreen browsers, no IE11") so the team isn't guessing case-by-case; and monitor real-user error rates/analytics by browser to catch regressions for whatever tail of older browsers you do support, rather than assuming.

Senior Engineer Perspective

The trap to avoid on both sides: under-supporting real users (silently breaking for a browser your analytics show matters) and over-engineering for browsers with negligible real traffic (maintaining legacy polyfills/bundles for users who don't exist). The senior answer is explicitly a cost/benefit calibration exercise grounded in actual data, not a fixed rule applied uniformly to every project.
