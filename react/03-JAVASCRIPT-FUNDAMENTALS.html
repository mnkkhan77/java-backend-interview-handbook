SECTION 1 - TYPES & COERCION

Q1. What is the difference between var, let, and const, and what is the Temporal Dead Zone?

ROI: ★★★★★ Frequency: Extremely High

Short Answer

var is function-scoped and hoisted with an initial value of undefined. let and const are block-scoped and, although hoisted, they live in the Temporal Dead Zone (TDZ) until the line where they are declared — accessing them before that throws a ReferenceError. const additionally forbids reassignment of the binding (not deep immutability).

Detailed Answer

Scoping

var ignores block boundaries — a var declared inside an if or for block leaks to the enclosing function. let/const are confined to the nearest { } block, which is why they fixed the classic loop-closure bug where every callback captured the same var i.

The Temporal Dead Zone

All three are hoisted to the top of their scope, but they behave differently before initialization. var is initialized to undefined during hoisting, so reading it early is merely useless, not fatal. let/const bindings are created but left uninitialized; the span from the top of the block to the declaration line is the TDZ, and any access in that window throws. The TDZ exists deliberately — it turns silent bugs into loud errors and makes const semantically coherent (you can never observe a const before its one and only assignment).

const is not "immutable"

const freezes the binding, not the value. A const object can still have its properties mutated; only reassigning the variable itself is blocked. Use Object.freeze (shallow) if you need value-level immutability.

Code Example

console.log(a); // undefined  (var is hoisted & initialized)
var a = 1;

console.log(b); // ReferenceError: Cannot access 'b' before initialization
let b = 2;      // b was in the TDZ above this line

const obj = { n: 1 };
obj.n = 2;      // OK — mutating a property
// obj = {};    // TypeError — reassigning the const binding

Project Example

In React you almost always declare hooks and derived values with const (const [count, setCount] = useState(0)). It signals intent — this reference will not be reassigned within the render — and prevents accidental shadowing bugs. let shows up for accumulators inside a useMemo body; var should essentially never appear in modern code.

Senior Engineer Perspective

The interviewer wants to hear "TDZ" unprompted and to know that const is about the binding, not the value — juniors often claim const means immutable. A strong follow-up: "Why does typeof undeclaredVar return 'undefined' but typeof on a let in its TDZ throws?" Answer: typeof is the historical exception that safely handles never-declared names, but TDZ variables are declared, so even typeof throws for them.

Q2. Explain hoisting for variables and functions.

ROI: ★★★★☆ Frequency: High

Short Answer

Hoisting is the JS engine's compile phase moving declarations to the top of their scope before execution. Function declarations are hoisted whole (callable before their line). var declarations are hoisted and set to undefined. let/const and function expressions/arrow functions are hoisted but stay uninitialized (TDZ).

Detailed Answer

It helps to think of two phases. In the creation phase the engine scans the scope and registers bindings; in the execution phase it runs the code line by line. Only the declaration is hoisted, never the assignment. So var x = 5 is conceptually split into var x (hoisted) and x = 5 (stays in place).

Function declarations are special: the entire function object is available before its textual position, which is why you can call a helper defined lower in the file. A function expression assigned to a variable follows that variable's rules — a var holding a function is undefined until assigned, and a const arrow function is in the TDZ.

Code Example

greet();            // "hi" — declaration hoisted whole
function greet() { console.log("hi"); }

sayBye();           // TypeError: sayBye is not a function
var sayBye = function () { console.log("bye"); };
// var sayBye is hoisted as undefined; calling undefined() throws

Senior Engineer Perspective

The trap is the difference between ReferenceError (TDZ / undeclared) and TypeError (calling an undefined value). If a candidate says "everything gets moved to the top," push them: does the value move too? The precise answer — declarations are registered, initializations stay put — is the senior signal. In practice, rely on hoisting only for function declarations; write everything else before use.

Q3. What is the difference between == and === and when is coercion dangerous?

ROI: ★★★★★ Frequency: Extremely High

Short Answer

=== (strict equality) compares type and value with no conversion. == (loose equality) coerces the operands to a common type first, which produces surprising results. Rule of thumb: always use ===; the one pragmatic exception is x == null to test for both null and undefined at once.

Detailed Answer

== follows the abstract equality algorithm: if types differ it applies a chain of conversions — null and undefined are loosely equal to each other and nothing else; strings and numbers compare as numbers; booleans are converted to numbers; objects are converted to primitives via valueOf/toString. This is why 0 == "", 0 == false, and "" == false are all true, and why [] == ![] is true — a genuinely confusing surface.

The pragmatic exception is the loose null check. value == null is true for exactly null and undefined, which is a concise nullish guard many codebases (and ESLint configs) explicitly allow.

Code Example

0 == "";        // true  — both coerce to 0
0 == false;     // true
"" == false;    // true
null == undefined; // true
null === undefined; // false

0 === "";       // false — no coercion
NaN === NaN;    // false — use Number.isNaN()

// The accepted exception:
if (value == null) { /* runs for null OR undefined */ }

Senior Engineer Perspective

Expect a whiteboard trap like [] == ![]. Walk it: ![] is false, so it becomes [] == false, then [] == 0, then "" == 0, then 0 == 0 → true. You do not need to memorize the table, but you should demonstrate that you understand coercion happens in steps and that this is exactly why === is the default. Bonus: mention Object.is, which is like === but treats NaN as equal to itself and distinguishes +0 from -0.

Q4. Primitive vs reference types — how do copying and passing work?

ROI: ★★★★★ Frequency: Extremely High

Short Answer

Primitives (string, number, boolean, null, undefined, symbol, bigint) are copied and compared by value. Objects, arrays, and functions are held by reference — assigning or passing them copies the reference (a pointer), not the underlying data, so two variables can mutate the same object. Equality (===) compares primitives by value and objects by identity.

Detailed Answer

JavaScript is always "pass by value" — but for objects the value that is passed is the reference. So a function can mutate the properties of an object you passed in (the caller sees the change), yet reassigning the parameter to a brand-new object does not affect the caller. This distinction trips up many candidates.

This is the single biggest source of React state bugs: mutating an object or array in place does not change its reference, so React's Object.is bailout sees "no change" and skips the re-render. You must produce a new reference.

Code Example

let a = { n: 1 };
let b = a;          // b holds the SAME reference
b.n = 99;
console.log(a.n);   // 99 — same object

function replace(x) { x = { n: 0 }; } // reassigns local param only
replace(a);
console.log(a.n);   // 99 — caller unaffected

{ n: 1 } === { n: 1 }; // false — different identities

// React: WRONG (same reference, no re-render)
state.items.push(newItem); setState(state.items);
// RIGHT (new reference)
setState(prev => [...prev, newItem]);

Senior Engineer Perspective

The interviewer is really testing whether you understand why React needs immutable updates and why comparing objects with === checks identity, not contents. Strong candidates connect the language semantics directly to React.memo, dependency arrays, and Redux reducers. A common follow-up: "Why does useEffect fire on every render when a dependency is an object literal?" — because the literal is a new reference each render.

Q5. Name the most common type-coercion gotchas.

ROI: ★★★★☆ Frequency: High

Short Answer

The usual suspects: + concatenates when either operand is a string; typeof null is "object"; NaN !== NaN; [] + [] is "" and [] + {} is "[object Object]"; and falsy values (0, "", NaN, null, undefined, false) all coerce to false in boolean context.

Detailed Answer

The key mental model: + is overloaded — if either side is a string (or coerces to one), it concatenates; otherwise it adds numerically. Every other arithmetic operator (-, *, /) forces numeric coercion. That is why "5" - 1 is 4 but "5" + 1 is "51".

In React the falsy-coercion gotcha bites when you conditionally render with &&: {items.length && <List/>} renders a literal 0 on screen when the array is empty, because 0 is falsy and gets returned. Use items.length > 0 && ... or a ternary.

Code Example

1 + "2";        // "12"  (concatenation)
"5" - 1;        // 4     (numeric coercion)
typeof null;    // "object"  (historical bug)
typeof NaN;     // "number"
Number.isNaN(NaN); // true — the correct NaN test

// React footgun — renders "0" when empty:
{count && <Badge value={count} />}
// Fix:
{count > 0 && <Badge value={count} />}

Senior Engineer Perspective

The {0 && ...} JSX bug is a favourite because it connects raw language behaviour to a real React defect. If you volunteer it, you signal that you have shipped React and been burned. Also mention that String(x), Number(x), and Boolean(x) are explicit conversions you should prefer over relying on implicit coercion.

SECTION 2 - SCOPE & CLOSURES

Q6. What is a closure? Give real production use cases.

ROI: ★★★★★ Frequency: Extremely High

Short Answer

A closure is a function bundled together with references to the variables from the scope where it was defined. Because that scope stays alive as long as the inner function is reachable, the function "remembers" and can keep reading and updating those variables even after the outer function has returned.

Detailed Answer

Closures are the mechanism behind private state, function factories, and event handlers. In React, every hook relies on closures: the callback you pass to useState, useEffect, or an event handler closes over the props and state from the render in which it was created. This is also the source of the "stale closure" bug — an effect or interval captures an old value and never sees updates unless dependencies or a functional updater are used.

Real use cases

  • Private state / encapsulation: variables unreachable from outside, exposed only through returned methods.
  • Counters & ID generators: maintain a private tally across calls.
  • Memoization: a cache held in the enclosing scope, shared across invocations.
  • Currying & partial application: capturing earlier arguments.
  • Debounce / throttle: the timer handle lives in the closure.

Code Example

// Private state + counter
function createCounter() {
  let count = 0;                 // private, not accessible outside
  return {
    inc() { return ++count; },
    get() { return count; },
  };
}
const c = createCounter();
c.inc(); c.inc();
c.get();  // 2  — count survives via closure

// Memoization
function memoize(fn) {
  const cache = new Map();       // captured across calls
  return (arg) => {
    if (cache.has(arg)) return cache.get(arg);
    const result = fn(arg);
    cache.set(arg, result);
    return result;
  };
}

// Debounce
function debounce(fn, ms) {
  let timer;                     // handle lives in the closure
  return (...args) => {
    clearTimeout(timer);
    timer = setTimeout(() => fn(...args), ms);
  };
}

Project Example

A debounced search box in React: const debounced = useMemo(() => debounce(onSearch, 300), [onSearch]). The returned function closes over the timer so successive keystrokes reset it. The classic bug — an interval inside useEffect(() => setInterval(() => setCount(count + 1)), []) always logging 1 — is a stale closure; the fix is the functional updater setCount(c => c + 1).

Senior Engineer Perspective

Anyone can recite the definition. The senior differentiator is naming a concrete production use (memoization, debounce, private state) and connecting closures to React's stale-closure pitfall. Expect the loop question: why does for (var i...) setTimeout(() => log(i)) print the final value repeatedly, and how does let fix it? Because let creates a fresh binding per iteration, so each closure captures its own i.

Q7. Explain lexical scope and the scope chain.

ROI: ★★★★☆ Frequency: High

Short Answer

Lexical (static) scope means a variable's accessibility is determined by where it is written in the source, not by where the function is called. When resolving an identifier, the engine walks outward through the chain of enclosing scopes until it finds the binding or reaches the global scope.

Detailed Answer

Each function creates a new scope nested inside the scope where it was defined. Name lookup goes inner → outer (the scope chain); it never goes into sibling or caller scopes. This is precisely what makes closures predictable — a closure captures the lexical environment of its definition site, so you can reason about which variables it sees just by reading the code.

Contrast with dynamic scope (used by some other languages) where lookup would follow the call stack. JavaScript is lexically scoped for variables, but note that this is the exception — for ordinary functions this is bound dynamically at call time, which is why arrow functions (which capture this lexically) were introduced.

Code Example

const outer = "O";
function parent() {
  const mid = "M";
  function child() {
    const inner = "I";
    console.log(inner, mid, outer); // I M O — walks up the chain
  }
  child();
}
parent();
// child cannot be called from elsewhere and still see mid — scope is
// fixed by where child is DEFINED, not where it is called.

Senior Engineer Perspective

The distinction interviewers probe is "lexical vs dynamic scope" and the fact that variables are lexical while regular-function this is dynamic. If you nail that one sentence, you have separated yourself from candidates who conflate the two. It also sets up the next topic cleanly.

SECTION 3 - THIS & FUNCTIONS

Q8. How is this determined? Explain all five binding rules.

ROI: ★★★★★ Frequency: Extremely High

Short Answer

this is decided at call time by how a function is invoked, in this priority order: (1) new binding — a fresh object; (2) explicit binding via call/apply/bind; (3) implicit binding — the object left of the dot; (4) default binding — undefined in strict mode, else the global object. Arrow functions ignore all of these and inherit this lexically from their enclosing scope.

Detailed Answer

RuleHow this is setExample
Defaultundefined (strict) / global (sloppy)fn()
ImplicitThe object before the dotobj.fn()
ExplicitThe first arg to call/apply/bindfn.call(ctx)
newThe newly constructed objectnew Fn()
ArrowLexical — captured from definition() => this

The most common bug is losing implicit binding: passing obj.method as a callback strips the object off the left of the dot, so at call time it invokes as a bare function and this becomes undefined. Arrow functions solve this because they have no this of their own — they close over the surrounding scope's this, which is exactly why they are the default for React class-method handlers and array-callback bodies.

Code Example

const user = {
  name: "Ada",
  greet() { return "Hi " + this.name; },
  greetArrow: () => "Hi " + this.name, // this = enclosing (module) scope
};

user.greet();               // "Hi Ada" — implicit binding
const g = user.greet;
g();                        // "Hi undefined" — lost binding (default)
g.call(user);               // "Hi Ada" — explicit binding

// Arrow captures lexical this — fixes callbacks:
class Timer {
  seconds = 0;
  tick = () => { this.seconds++; }; // arrow keeps `this` = instance
}

Senior Engineer Perspective

Interviewers love "predict the output" chains that alternate methods, detached references, and arrows. Say out loud "this depends on the call site, not the definition site — except arrows." Then apply the priority order. A sharp follow-up: what does bind do if you also call the result with new? The new binding wins over the earlier bind for this, though bound leading arguments are preserved.

Q9. What do call, apply, and bind do, and how do they differ?

ROI: ★★★★☆ Frequency: High

Short Answer

All three set this explicitly. call invokes immediately with arguments listed individually; apply invokes immediately with arguments as an array; bind does not invoke — it returns a new function permanently bound to the given this (and optional preset arguments) for later use.

Detailed Answer

Mnemonic: apply takes an array; call takes a comma-separated list; bind gives you back a function. With modern spread syntax, apply is largely replaced by fn.call(ctx, ...args) or just fn(...args), but it still appears in older code and in interview questions. bind also supports partial application — you can pre-fill leading arguments.

Code Example

function intro(greeting, punct) {
  return greeting + ", " + this.name + punct;
}
const p = { name: "Lin" };

intro.call(p, "Hi", "!");         // "Hi, Lin!"
intro.apply(p, ["Hi", "!"]);      // "Hi, Lin!"  (args as array)
const bound = intro.bind(p, "Hi");// returns fn, not called yet
bound("!");                        // "Hi, Lin!"  (partial application)

// apply's classic use, now obsolete with spread:
Math.max.apply(null, [3, 1, 4]);  // 4
Math.max(...[3, 1, 4]);           // 4  (modern equivalent)

Senior Engineer Perspective

Be ready to hand-implement bind — it is a standard exercise and forces you to combine closures, apply, and the new-vs-bind priority. Also mention that in React with hooks you rarely reach for bind (arrows and useCallback handle context), but you must recognize it in legacy class components where handlers were bound in the constructor to fix this.

SECTION 4 - OBJECTS & PROTOTYPES

Q10. Explain prototypal inheritance and the prototype chain.

ROI: ★★★★☆ Frequency: High

Short Answer

Every object has a hidden link ([[Prototype]], exposed as __proto__) to another object. When you read a property that an object lacks, the engine walks up this chain of prototypes until it finds the property or reaches null. This is how objects share behaviour without copying — and it is what class syntax compiles down to.

Detailed Answer

A constructor function has a .prototype object; instances created with new get their [[Prototype]] pointed at it. Methods defined on the prototype are shared by all instances (one copy in memory) rather than duplicated per object. The lookup chain typically runs instance → Constructor.prototype → Object.prototype → null.

ES6 class is syntactic sugar over exactly this — extends sets up the prototype link, and super delegates up the chain. There is no separate "classical" inheritance under the hood. Writes always happen on the own object (they do not travel up), which is why setting a property shadows rather than mutates the prototype.

Code Example

function Animal(name) { this.name = name; }
Animal.prototype.speak = function () {
  return this.name + " makes a sound";
};

function Dog(name) { Animal.call(this, name); }        // inherit fields
Dog.prototype = Object.create(Animal.prototype);       // inherit methods
Dog.prototype.constructor = Dog;
Dog.prototype.speak = function () { return this.name + " barks"; };

const d = new Dog("Rex");
d.speak();                       // "Rex barks" (own prototype wins)
d.hasOwnProperty("name");        // true — found via Object.prototype

// Equivalent modern syntax:
class Animal2 { constructor(n){ this.name = n; } speak(){ return this.name; } }
class Dog2 extends Animal2 { speak(){ return this.name + " barks"; } }

Senior Engineer Perspective

The differentiator is stating that class is sugar over prototypes, not a different model, and knowing the difference between __proto__ (the instance's link) and .prototype (a property on constructor functions). A common follow-up: why put methods on the prototype instead of inside the constructor? Memory — one shared function versus one per instance. In day-to-day React you rarely author prototype chains, but understanding them explains instanceof, Object.create, and polyfills.

Q11. What does the new operator actually do, step by step?

ROI: ★★★☆☆ Frequency: Medium

Short Answer

new Fn(args) does four things: (1) creates a fresh empty object; (2) links its [[Prototype]] to Fn.prototype; (3) calls Fn with this bound to that new object; (4) returns the new object — unless the constructor explicitly returns its own (non-primitive) object, in which case that is returned instead.

Detailed Answer

Understanding these four steps demystifies constructors, explains why forgetting new leaks properties onto the global object (in sloppy mode) or throws (in strict mode), and lets you hand-write a myNew polyfill — a favourite interview exercise. The subtle step is the return rule: returning a primitive is ignored, but returning an object overrides the freshly created instance.

Code Example

function myNew(Constructor, ...args) {
  const obj = Object.create(Constructor.prototype); // steps 1 + 2
  const result = Constructor.apply(obj, args);      // step 3
  return (result !== null && typeof result === "object")
    ? result                                        // step 4 (explicit object)
    : obj;                                          // step 4 (default)
}

function Point(x, y) { this.x = x; this.y = y; }
const p = myNew(Point, 1, 2);   // Point { x: 1, y: 2 }

Senior Engineer Perspective

Reciting the four steps in order is the whole game here, plus the return-value edge case. If asked "what happens if you call a constructor without new?", answer: this falls back to default binding, so in strict mode you get a TypeError assigning to undefined, and in sloppy mode you silently pollute the global object — which is why new.target guards exist.

Q12. Shallow copy vs deep copy — and what is structuredClone?

ROI: ★★★★☆ Frequency: High

Short Answer

A shallow copy duplicates the top level but shares nested objects by reference ({...obj}, Object.assign, Array.slice). A deep copy recursively clones every level so nothing is shared. The modern built-in for deep cloning is structuredClone(value) (ES2021, in all evergreen browsers and Node 17+), which replaces the old JSON.parse(JSON.stringify(...)) hack.

Detailed Answer

The JSON round-trip technique is limited: it drops undefined, functions, and symbols, turns Date into a string, and throws on circular references. structuredClone handles Date, Map, Set, typed arrays, ArrayBuffer, and circular references — but it cannot clone functions, DOM nodes, or class instances' prototype chain (you get a plain object) and will throw on those.

In React you rarely need a full deep clone; the idiomatic approach is targeted immutable updates — spread only the levels along the path you are changing, which is cheaper and preserves referential equality for untouched branches (helping memo and re-render bailouts).

Code Example

const state = { user: { name: "A" }, tags: ["x"] };

const shallow = { ...state };
shallow.user.name = "B";
state.user.name;            // "B" — nested object was shared!

const deep = structuredClone(state);
deep.user.name = "C";
state.user.name;            // "B" — fully independent

// React idiom: copy only the path you change
setState(prev => ({
  ...prev,
  user: { ...prev.user, name: "New" }, // new refs only on this path
}));

Senior Engineer Perspective

Interviewers want you to (a) know why {...obj} is not enough for nested data, (b) reach for structuredClone over the JSON hack and name the JSON hack's failure modes, and (c) argue that in React you usually want surgical immutable updates, not blanket deep cloning, because preserving references for unchanged subtrees is what makes memoization work.

Q13. When should you use Map/Set instead of a plain object?

ROI: ★★★☆☆ Frequency: Medium

Use a Map when you need keys of any type (objects, not just strings/symbols), guaranteed insertion order, a clean size property, and frequent additions/removals. Use a Set for a collection of unique values with O(1) membership tests. Reach for a plain object for fixed-shape records and when you need JSON serialization.

The senior nuance is prototype pollution and key flexibility: using a user-supplied string as an object key risks colliding with __proto__ or constructor, whereas a Map is immune. Also mention WeakMap/WeakSet for keying private data off objects without preventing garbage collection — useful for caches keyed by DOM nodes or component instances.

SECTION 5 - ES6+ FEATURES & FUNCTIONAL JS

Q14. How do destructuring, spread, rest, and default parameters work?

ROI: ★★★★★ Frequency: Extremely High

Short Answer

Destructuring unpacks values from arrays/objects into variables. Spread (... in a call or literal) expands an iterable/object into individual elements or properties. Rest (... in a parameter list or destructuring target) collects the remaining items into an array/object. Default parameters supply a fallback when an argument is undefined.

Detailed Answer

The same ... token is spread or rest depending on position: on the right of = or inside a call it spreads; on the left as a target or in a parameter list it collects. Object spread creates a shallow copy and is the workhorse of immutable React updates. Destructuring supports renaming, defaults, and nested patterns, which is why React props are almost always destructured in the function signature.

One gotcha: defaults trigger only for undefined, never for null or other falsy values. So function f(x = 5) uses 5 for f() and f(undefined), but keeps null, 0, and "".

Code Example

// Destructuring with rename + default
const { name, role = "guest" } = user;

// Array destructuring — the useState pattern
const [count, setCount] = useState(0);

// Rest collects the remainder
const [first, ...others] = [1, 2, 3];      // others = [2, 3]
function sum(...nums) { return nums.reduce((a, b) => a + b, 0); }

// Spread — merge / copy (shallow)
const merged = { ...defaults, ...overrides };
const cloned = [...items];

// Common React prop-forwarding idiom
function Button({ variant, ...rest }) {
  return <button className={variant} {...rest} />;
}

// Default only fires for undefined:
function greet(name = "friend") { return "Hi " + name; }
greet(null);       // "Hi null"  — null is NOT replaced

Senior Engineer Perspective

These appear in nearly every React file, so fluency is assumed, not impressive — the differentiator is knowing the edge cases: spread is shallow, defaults fire only on undefined, and rest must be the last parameter. A frequent follow-up: "How would you clone-and-update a nested object immutably?" — nested spread along the changed path, connecting back to Q12.

Q15. Explain optional chaining and nullish coalescing (ES2020).

ROI: ★★★★☆ Frequency: High

Short Answer

Optional chaining ?. short-circuits and returns undefined instead of throwing when a reference in the chain is null or undefined. Nullish coalescing ?? returns its right side only when the left is null or undefined — unlike ||, it does not treat 0, "", or false as missing.

Detailed Answer

Together they eliminate defensive a && a.b && a.b.c ladders and the || default-value bug. The classic || bug: const page = input.page || 1 wrongly overrides a legitimate 0; ?? 1 keeps 0. Optional chaining also works for method calls (obj.fn?.()) and dynamic keys (obj?.[key]). Note ?. short-circuits the whole rest of the chain the moment it hits nullish.

Code Example

const city = user?.address?.city;      // undefined if any link is nullish
const onClick = props.onClick?.();      // calls only if it exists

// ?? vs || — the key difference:
const count = data.count ?? 10;         // keeps 0
const bad   = data.count || 10;         // 0 becomes 10 (bug!)

// Common in React data fetching:
const items = response?.data?.items ?? [];

Senior Engineer Perspective

The expected insight is why ?? exists when we already had || — specifically the falsy-but-valid values 0, "", and false. Bonus: mention you cannot mix ?? with &&/|| without parentheses (a syntax error by design), and that optional chaining stops evaluating the rest of the chain but does not swallow errors thrown deeper in a called function.

Q16. What are pure functions, immutability, and higher-order functions?

ROI: ★★★★☆ Frequency: High

Short Answer

A pure function returns the same output for the same input and has no side effects. Immutability means never mutating existing data — you produce new values instead. A higher-order function takes a function as an argument and/or returns a function. These three ideas underpin React's rendering model, hooks, and state management.

Detailed Answer

React leans hard on these principles. A component's render should be pure — same props/state produce the same UI, no side effects during render (those belong in useEffect or event handlers). Immutable state updates are mandatory because React detects change by reference identity (Object.is); mutating in place defeats memo, useMemo, and reducer purity. Higher-order functions are everywhere: array methods, custom hooks that wrap other hooks, and the (now less common) higher-order component pattern.

Benefits: pure + immutable code is trivially testable, cacheable/memoizable, time-travel-debuggable (Redux DevTools relies on it), and safe under React's concurrent rendering, which may call render multiple times.

Code Example

// Pure — no external state touched, no mutation
const add = (a, b) => a + b;

// Impure — mutates argument (side effect)
const pushImpure = (arr, x) => { arr.push(x); return arr; };
// Pure alternative — returns new array
const pushPure = (arr, x) => [...arr, x];

// Higher-order function: takes and returns functions
const withLogging = (fn) => (...args) => {
  console.log("calling", fn.name, args);
  return fn(...args);
};
const loggedAdd = withLogging(add);

// Immutable Redux-style reducer
function reducer(state, action) {
  switch (action.type) {
    case "add": return { ...state, count: state.count + 1 };
    default: return state;
  }
}

Senior Engineer Perspective

Tie it explicitly to React: "components should be pure functions of props and state, and state must be updated immutably so React's reference comparison detects changes." Mention that React 18+ Strict Mode intentionally double-invokes renders and effects in development to surface impurity. That connection — language principle → framework guarantee — is what marks a senior answer rather than a textbook recital.

Q17. Explain map, filter, and reduce — and when is reduce the wrong tool?

ROI: ★★★★★ Frequency: Extremely High

Short Answer

map transforms each element into a new array of the same length; filter keeps elements matching a predicate; reduce folds the array into a single accumulated value. All three are pure (they return new values and do not mutate the source). Reduce is powerful but often abused — if map/filter/some/find express the intent more clearly, prefer them.

Detailed Answer

reduce is the right tool when you are genuinely collapsing a collection into one result — a sum, a lookup object, a group-by, or a min/max. It is the wrong tool when you are really just mapping or filtering, because a reduce that builds an array is harder to read than the equivalent map/filter and typically re-creates or spreads the accumulator each step (a hidden O(n²) if you spread inside it). Always pass an explicit initial value to reduce — omitting it uses the first element as the seed and throws on an empty array.

In React these show up constantly for rendering lists (items.map(...)), filtering data before display, and computing derived totals inside useMemo.

Code Example

const nums = [1, 2, 3, 4];

nums.map(n => n * 2);              // [2, 4, 6, 8]
nums.filter(n => n % 2 === 0);     // [2, 4]
nums.reduce((sum, n) => sum + n, 0); // 10  — always seed the accumulator

// Legit reduce: build a lookup / group-by
const byId = users.reduce((acc, u) => {
  acc[u.id] = u;                    // mutate the accumulator = O(n)
  return acc;
}, {});

// Reduce ABUSE — just a filter+map in disguise:
const bad = nums.reduce((acc, n) => (n > 1 ? [...acc, n * 2] : acc), []);
// Clearer AND faster (no per-step spread):
const good = nums.filter(n => n > 1).map(n => n * 2);

Project Example

Rendering a table: orders.filter(o => o.active).map(o => <Row key={o.id} {...o} />). Computing a cart total with useMemo(() => items.reduce((t, i) => t + i.price * i.qty, 0), [items]). Normalizing an API response into a keyed lookup with reduce so components can index by id in O(1).

Senior Engineer Perspective

The maturity signal is knowing when not to use reduce. Interviewers respect a candidate who says "I could reduce this, but a filter-then-map reads better and avoids spreading the accumulator every iteration." Also mention flatMap, and that all these methods skip holes in sparse arrays. If pushed on performance, note that chaining map().filter() creates intermediate arrays — fine for UI-sized lists, but for very large data a single loop or a transducer/generator may be warranted.

SECTION 6 - EVENT LOOP & ASYNCHRONOUS EXECUTION ORDER

Q18. What is the event loop and how does it coordinate the call stack, Web APIs, and task queues?

ROI: ★★★★★ Frequency: Extremely High

Short Answer

JavaScript runs on a single thread with one call stack. The event loop is the mechanism that lets it stay non-blocking: when the stack is empty, the loop pulls the next task off a queue and pushes it onto the stack. Slow work (timers, network calls, DOM events) is delegated to Web APIs / the runtime (browser or Node), which push a callback onto a queue once the work finishes, rather than blocking the stack.

Detailed Answer

Four pieces cooperate: the call stack (synchronous execution), Web APIs / runtime APIs (timers, fetch, DOM events — implemented outside the JS engine), the callback/task queues (where finished async work waits), and the event loop itself, which repeatedly checks "is the stack empty?" and if so, dequeues the next task and runs it to completion. Because the loop only moves to the next task once the stack is fully empty, one long synchronous function blocks everything else — timers, renders, input handling — which is why heavy computation on the main thread causes jank.

Code Example

console.log("1: sync");
setTimeout(() => console.log("2: macrotask"), 0);
Promise.resolve().then(() => console.log("3: microtask"));
console.log("4: sync");
// Output: 1, 4, 3, 2
// Sync code always finishes first; then ALL microtasks; then one macrotask.

Senior Engineer Perspective

Interviewers want the mental model, not just the queue names: single thread, one stack, non-blocking via delegation. A strong follow-up is "why does a giant synchronous loop freeze the UI?" — because the stack never empties, so the loop never gets a chance to process input events, repaints, or timers. This is exactly why expensive computations are moved off the main thread with Web Workers or chunked with setTimeout/requestIdleCallback.

Q19. Microtasks vs macrotasks — what is the difference and which runs first?

ROI: ★★★★★ Frequency: Extremely High

Short Answer

Macrotasks (a.k.a. "tasks") are things like setTimeout, setInterval, I/O, and UI events — one is processed per event-loop tick. Microtasks are promise callbacks (.then/.catch/.finally), queueMicrotask, and async/await continuations. After every single macrotask (and after the initial synchronous script), the engine drains the entire microtask queue — including any new microtasks queued while draining — before moving to the next macrotask or repainting.

Detailed Answer

The ordering guarantee is: run current synchronous code to completion → drain microtask queue completely (fully, even if it grows) → run one macrotask → drain microtasks again → (browser may paint) → repeat. This means microtasks always run before the next macrotask, even a setTimeout(fn, 0) queued earlier. It also means a microtask that keeps re-queuing itself can starve macrotasks and rendering indefinitely — the loop never gets to "next task" because the microtask queue is never empty.

SourceQueueDrained

queueMicrotaskMicrotaskFully, before next macrotask
async/await continuationMicrotaskFully, before next macrotask
setTimeout / setIntervalMacrotaskOne per loop tick
UI events, I/O callbacksMacrotaskOne per loop tick

Code Example

console.log("A");
setTimeout(() => console.log("B - macrotask"), 0);
Promise.resolve()
  .then(() => console.log("C - microtask 1"))
  .then(() => console.log("D - microtask 2 (queued during drain)"));
console.log("E");
// Order: A, E, C, D, B
// Both microtasks (C then D) finish before the macrotask B runs.

Senior Engineer Perspective

This is one of the most common whiteboard exercises. State the rule out loud — "drain microtasks fully before the next macrotask" — then trace line by line. A great follow-up: can microtasks starve rendering? Yes — a recursive chain of .then calls that never stops queuing will block paint and macrotasks forever, which is a real production incident category, not just trivia.

Q20. Trace the exact output order for a mix of sync code, nested setTimeout, and chained promises.

ROI: ★★★★★ Frequency: Extremely High

Short Answer

Work through it in passes: first execute all synchronous code top to bottom, then drain the microtask queue in FIFO order (including microtasks created while draining), then run the earliest-queued macrotask, then drain microtasks again, and so on. Nested timers get re-queued as new macrotasks each time they fire.

Detailed Answer

The trick candidates miss is that a .then callback that itself schedules another .then keeps executing within the same microtask-draining phase, before any macrotask runs — but a .then callback that schedules a new setTimeout pushes work to a future macrotask tick, after other pending macrotasks queued earlier.

Code Example

console.log("1");
setTimeout(() => {
  console.log("2");
  Promise.resolve().then(() => console.log("3"));
}, 0);
Promise.resolve().then(() => {
  console.log("4");
  setTimeout(() => console.log("5"), 0);
});
console.log("6");
// Order: 1, 6, 4, 2, 3, 5
// 1,6 sync -> 4 microtask -> 2 macrotask(timeout) -> 3 its microtask -> 5 next macrotask

Senior Engineer Perspective

Narrate your reasoning step by step rather than guessing the answer — interviewers grade the process. If you get lost, fall back to the two rules: "sync first, then all microtasks, then one macrotask, repeat" and "code inside a callback only runs once its queue slot is reached."

Q21. What is queueMicrotask and when would you reach for it directly?

ROI: ★★★☆☆ Frequency: Medium

Short Answer

queueMicrotask(fn) schedules fn to run in the microtask queue, the same queue promise callbacks use — without needing to create a throwaway Promise.resolve().then(...). It is useful when you want to defer work until after the current synchronous block finishes, but strictly before any macrotask (timer, I/O, render).

Detailed Answer

A common use case is batching: you want several synchronous calls in the same tick to collapse into a single deferred action (e.g., flushing a batch of subscriber notifications) without waiting a full macrotask like setTimeout(fn, 0) would. Because microtasks run before rendering, they are also useful for guaranteeing "run before the next paint but after the current script," which matters for measuring layout or coordinating with other promise-based code.

Code Example

function batchNotify(fn) {
  let scheduled = false;
  const pending = new Set();
  return (listener) => {
    pending.add(listener);
    if (!scheduled) {
      scheduled = true;
      queueMicrotask(() => {
        pending.forEach((l) => l());
        pending.clear();
        scheduled = false;
      });
    }
  };
}

Senior Engineer Perspective

Know the trade-off: queueMicrotask runs sooner than setTimeout(fn, 0) (before rendering, before other macrotasks) but for that same reason is more dangerous to overuse — recursively scheduling microtasks can starve the UI. Mention it is the modern replacement for the old Promise.resolve().then() "microtask hack."

Q22. How does async/await desugar to promises, and where exactly does an await point yield control?

ROI: ★★★★★ Frequency: Extremely High

Short Answer

async/await is syntactic sugar over promises and generators: an async function always returns a promise, and each await pauses the function, subscribes a continuation to the awaited promise's .then, and returns control to the caller immediately. When the awaited promise settles, the continuation resumes as a microtask.

Detailed Answer

Conceptually, await expr compiles to something like Promise.resolve(expr).then(value => { /* rest of function */ }). Crucially, the code after an await never runs synchronously — even if the awaited value is already a resolved promise or a plain value, resuming happens on the microtask queue, at least one tick later. This is why an async function that "looks synchronous" still yields control back to its caller at the very first await, letting other synchronous code after the call site run first.

Code Example

async function demo() {
  console.log("A");
  await null;              // yields here — rest resumes as a microtask
  console.log("B");
}
console.log("start");
demo();
console.log("end");
// Order: start, A, end, B
// "B" runs after the synchronous script, as a microtask.

Senior Engineer Perspective

A favorite trap: "does await Promise.resolve(1) run synchronously?" No — even an already-settled promise defers resumption to a microtask. This matters in real code: an async function called inside a loop still lets the loop's remaining synchronous statements run before the first await's continuation fires.

Q23. What happens when an error is thrown inside a Promise executor vs inside a .then callback?

ROI: ★★★★☆ Frequency: High

Short Answer

A synchronous throw inside the new Promise((resolve, reject) => {...}) executor is automatically caught and turns the promise into a rejection — you do not need a manual try/catch there. A throw inside a .then/.catch callback is likewise caught by the promise machinery and converted into a rejection of the promise returned by that .then, propagating to the next .catch in the chain.

Detailed Answer

Promises exist precisely to normalize both synchronous throws and asynchronous rejections into the same rejection channel, so consumers only need one .catch at the end of a chain regardless of where the failure originated. The one exception is a throw happening outside the promise machinery entirely — e.g., in a callback passed to setTimeout inside the executor — that is a normal uncaught exception, not a promise rejection, because it happens on a separate turn of the event loop with no wrapping try/catch.

Code Example

new Promise((resolve, reject) => {
  throw new Error("boom");     // auto-caught -> rejection
}).catch((e) => console.log("caught:", e.message)); // "caught: boom"

Promise.resolve(1)
  .then((v) => { throw new Error("in then"); })
  .catch((e) => console.log("caught:", e.message)); // "caught: in then"

// NOT caught — throws outside the promise machinery:
new Promise((resolve) => {
  setTimeout(() => { throw new Error("uncaught!"); }, 0);
});

Senior Engineer Perspective

The nuance interviewers probe for is the "outside the executor's synchronous scope" exception — many candidates assume the promise wrapper is magic and catches everything. Point out that only errors thrown synchronously within code the promise machinery directly calls get converted to rejections.

Q24. Explain Promise.all vs Promise.allSettled vs Promise.race vs Promise.any.

ROI: ★★★★★ Frequency: Extremely High

Short Answer

Promise.all resolves when every promise resolves (array of values), but rejects immediately if any one rejects. Promise.allSettled always resolves once every promise has settled, giving you a status/value or status/reason for each. Promise.race settles as soon as the first promise settles, whether fulfilled or rejected. Promise.any resolves as soon as the first promise fulfills, and only rejects (with an AggregateError) if all of them reject.

Detailed Answer

MethodResolves whenRejects when
allevery promise fulfillsany one rejects (fail-fast)
allSettledevery promise settles (always)never
racefirst to settle, if it fulfilledfirst to settle, if it rejected
anyfirst to fulfillonly if ALL reject (AggregateError)

Use all when every result is required and any failure should abort the batch. Use allSettled when partial success is acceptable (e.g., loading independent widgets on a dashboard — one failing shouldn't blank the page). Use race for timeouts (race a fetch against a timer). Use any when you have redundant sources and only need the fastest success (e.g., multiple CDN mirrors).

Code Example

const results = await Promise.allSettled([fetchA(), fetchB(), fetchC()]);
results.forEach((r) => {
  if (r.status === "fulfilled") console.log(r.value);
  else console.warn("failed:", r.reason);
});

// Timeout pattern with race
function withTimeout(promise, ms) {
  const timeout = new Promise((_, reject) =>
    setTimeout(() => reject(new Error("timeout")), ms)
  );
  return Promise.race([promise, timeout]);
}

Project Example

A dashboard that renders several independent widgets uses Promise.allSettled so one failed API call shows an error card without blanking the whole page — versus Promise.all, which is right for a checkout flow where every step (validate cart, charge card, reserve inventory) must succeed together.

Senior Engineer Perspective

Interviewers want you to map each combinator to a real scenario, not just recite definitions. The most commonly forgotten one is any — be ready to explain the AggregateError it throws when everything fails.

Q25. What is "callback hell" and how do promises and async/await solve it?

ROI: ★★★☆☆ Frequency: Medium

Short Answer

Callback hell is the deeply nested "pyramid of doom" that results from chaining async operations by passing each the next step as a callback. Promises flatten this into a linear .then chain with a single error channel; async/await flattens it further into code that reads like synchronous, top-to-bottom logic while remaining non-blocking.

Detailed Answer

Beyond readability, the deeper problem with raw callbacks is inversion of control (you hand a function to a library and trust it to call it correctly — once, with the right arguments) and fragmented error handling (every callback needs its own error-first check). Promises fix both: they are a first-class value you can pass around, compose, and attach exactly one rejection handler to, regardless of how many steps are chained.

Code Example

// Callback hell
getUser(id, (user) => {
  getPosts(user.id, (posts) => {
    getComments(posts[0].id, (comments) => {
      console.log(comments);
    }, onError);
  }, onError);
}, onError);

// Promise chain
getUser(id)
  .then((user) => getPosts(user.id))
  .then((posts) => getComments(posts[0].id))
  .then((comments) => console.log(comments))
  .catch(onError);

// async/await — flat and linear
async function run() {
  try {
    const user = await getUser(id);
    const posts = await getPosts(user.id);
    const comments = await getComments(posts[0].id);
    console.log(comments);
  } catch (err) {
    onError(err);
  }
}

Senior Engineer Perspective

Go beyond "it's nested and ugly" — name the real engineering problems (inversion of control, scattered error handling, hard-to-compose parallelism) and how promises solve each. Mention that async/await still needs care for parallelism: sequential await calls that don't depend on each other should be started together and awaited with Promise.all, not awaited one at a time.

Q26. How does setTimeout(fn, 0) actually behave, and why isn't the delay really 0?

ROI: ★★★☆☆ Frequency: Medium

Short Answer

setTimeout(fn, 0) does not run immediately — it queues fn as a macrotask, which only runs after the current synchronous script and all pending microtasks have finished. Browsers also clamp nested timeouts: after a chain of nested timers (historically 5+ levels deep), the minimum delay is forced up to about 4ms, even if you requested 0.

Detailed Answer

The "0ms" delay really means "as soon as possible, but only after the current call stack empties and microtasks drain, and only after waiting your turn behind other macrotasks." It is commonly used to break up long synchronous work into chunks that yield to the event loop between chunks, letting the UI stay responsive — though queueMicrotask, requestIdleCallback, or MessageChannel-based schedulers are often better tools for that job depending on the desired priority.

Code Example

console.log("1");
setTimeout(() => console.log("2"), 0);
console.log("3");
// Output: 1, 3, 2 — the timeout callback waits for the sync script to finish

// Chunking heavy work so the UI can breathe:
function processInChunks(items, chunkSize, worker) {
  let i = 0;
  function step() {
    const end = Math.min(i + chunkSize, items.length);
    for (; i < end; i++) worker(items[i]);
    if (i < items.length) setTimeout(step, 0); // yield between chunks
  }
  step();
}

Senior Engineer Perspective

Interviewers probe whether you understand "0ms" is a minimum, not a guarantee — actual delay depends on the queue and browser clamping rules. A senior answer connects this to real performance work: chunking a large synchronous render or data transform with timeouts to avoid blocking input handling and painting.

Q27. What is requestAnimationFrame and how does it fit into the event loop relative to microtasks and rendering?

ROI: ★★★☆☆ Frequency: Medium

Short Answer

requestAnimationFrame(fn) schedules fn to run right before the browser's next repaint, ideally synced to the display's refresh rate (~60fps). It sits between "microtasks drained" and "paint" in the loop: sync code and microtasks always run first, then queued animation-frame callbacks run, then the browser paints.

Detailed Answer

Unlike setTimeout, requestAnimationFrame callbacks are throttled to the display refresh and automatically paused when the tab is backgrounded, making it the right tool for visual updates (animations, reading layout, canvas drawing) rather than setInterval, which fires on a fixed clock regardless of whether the frame is actually going to be painted, wasting work.

Code Example

function animate(el) {
  let start;
  function frame(timestamp) {
    if (start === undefined) start = timestamp;
    const elapsed = timestamp - start;
    el.style.transform = `translateX(${Math.min(elapsed / 5, 200)}px)`;
    if (elapsed < 1000) requestAnimationFrame(frame);
  }
  requestAnimationFrame(frame);
}

Senior Engineer Perspective

Know the ordering: microtasks always run before the next animation frame and before paint, so heavy microtask chains can delay visible updates even though "the code already ran." In React, this underlies why layout-measuring effects use useLayoutEffect (runs synchronously before paint) rather than useEffect (runs after paint, asynchronously).

Q28. How do rendering and painting interact with the event loop in a browser?

ROI: ★★★☆☆ Frequency: Medium

Short Answer

A browser frame roughly goes: run macrotask → drain microtasks → run any requestAnimationFrame callbacks → recalculate style/layout if needed → paint/composite → wait for next frame trigger. The browser tries to paint once per macrotask "tick" if enough time remains and something actually changed, but it is not obligated to paint after every single task.

Detailed Answer

This is why long-running synchronous JavaScript — even wrapped nicely in promises — can freeze the visible page: the browser cannot paint mid-script, and it will not interleave paint work between microtasks (paint only gets a chance once the microtask queue is empty). Excessive DOM reads/writes interleaved (causing "layout thrashing") also forces synchronous style recalculation, which is why batching DOM reads before writes (or using requestAnimationFrame to schedule writes) matters for smooth UI.

Code Example

// Layout thrashing — read, write, read, write forces repeated reflow
els.forEach((el) => {
  const h = el.offsetHeight;     // read (forces layout)
  el.style.height = h + 10 + "px"; // write
});

// Better — batch all reads, then all writes
const heights = els.map((el) => el.offsetHeight); // all reads
els.forEach((el, i) => { el.style.height = heights[i] + 10 + "px"; }); // all writes

Senior Engineer Perspective

Connecting event-loop timing to real rendering performance (layout thrashing, forced synchronous layout) separates candidates who memorized queue trivia from those who have debugged jank in production.

Q29. Can a chain of microtasks starve macrotasks and rendering indefinitely? Show how.

ROI: ★★★☆☆ Frequency: Medium

Short Answer

Yes. Because the engine must fully drain the microtask queue — including microtasks scheduled by other microtasks — before running the next macrotask or repainting, a promise chain that keeps re-queuing itself forever will starve setTimeout callbacks, user input handling, and rendering, effectively freezing the page even though the CPU shows activity.

Detailed Answer

This is a real production failure mode: recursive .then loops, or libraries that internally recurse via promises instead of macrotasks, can produce a page that looks "hung" with no single long synchronous frame in the profiler — the pattern shows as thousands of tiny microtask executions back to back. The fix is to periodically yield with a macrotask (setTimeout) or an idle callback instead of chaining purely with microtasks.

Code Example

// DANGEROUS — never yields to macrotasks/rendering
function loopForever() {
  Promise.resolve().then(loopForever); // re-queues a microtask, forever
}
// loopForever(); // would freeze the tab

// SAFE — yields periodically via a macrotask
function politeLoop(i = 0) {
  if (i >= 1_000_000) return;
  // do a chunk of work here
  if (i % 1000 === 0) {
    setTimeout(() => politeLoop(i + 1), 0); // yield to the event loop
  } else {
    Promise.resolve().then(() => politeLoop(i + 1));
  }
}

Senior Engineer Perspective

This question tests whether you truly understand the microtask-drains-fully rule or just memorized "microtasks run before macrotasks." Being able to construct the starvation example from first principles is a strong signal.

Q30. How would you implement an async retry-with-exponential-backoff utility?

ROI: ★★★★☆ Frequency: High

Short Answer

Wrap the operation in a loop that awaits it, catches failures, and — up to a max attempt count — waits an exponentially increasing delay (often with jitter) before retrying, re-throwing the last error once attempts are exhausted.

Detailed Answer

Key details interviewers look for: the delay must actually be awaited (via a promise-wrapped setTimeout), the backoff should grow (e.g., base * 2^attempt) to avoid hammering a struggling service, adding random jitter avoids synchronized retry storms across clients, and there must be a cap on total attempts so it doesn't retry forever.

Code Example

function delay(ms) {
  return new Promise((resolve) => setTimeout(resolve, ms));
}

async function retryWithBackoff(fn, { retries = 3, baseMs = 200 } = {}) {
  let lastError;
  for (let attempt = 0; attempt <= retries; attempt++) {
    try {
      return await fn();
    } catch (err) {
      lastError = err;
      if (attempt === retries) break;
      const jitter = Math.random() * baseMs;
      await delay(baseMs * 2 ** attempt + jitter);
    }
  }
  throw lastError;
}

// Usage
const data = await retryWithBackoff(() => fetch("/api/data").then(r => {
  if (!r.ok) throw new Error("bad status " + r.status);
  return r.json();
}));

Senior Engineer Perspective

Expect a follow-up on which errors should be retried (network/5xx) versus not (4xx validation errors — retrying those is wasted work), and how you'd avoid retrying a non-idempotent mutation twice by accident.

SECTION 7 - ITERATORS, GENERATORS & SYMBOL.ITERATOR

Q31. What is the difference between an iterable and an iterator? What is the iterator protocol?

ROI: ★★★★☆ Frequency: High

Short Answer

An iterable is any object that implements Symbol.iterator, a method returning an iterator. An iterator is an object with a next() method that returns { value, done } on each call. Arrays, strings, Maps, Sets, and NodeLists are built-in iterables; for...of, spread, and destructuring all consume the iterator protocol under the hood.

Detailed Answer

The protocol is deliberately minimal: calling obj[Symbol.iterator]() must return an object whose next() returns { value: any, done: boolean }, with done: true signaling exhaustion (value is then typically ignored). Many built-in iterators are also themselves iterable (their own Symbol.iterator returns this), which is why you can pass an iterator directly to for...of.

Code Example

const arr = [10, 20, 30];
const it = arr[Symbol.iterator]();
it.next(); // { value: 10, done: false }
it.next(); // { value: 20, done: false }
it.next(); // { value: 30, done: false }
it.next(); // { value: undefined, done: true }

// Plain objects are NOT iterable by default:
const obj = { a: 1 };
// for (const x of obj) {} // TypeError: obj is not iterable

Senior Engineer Perspective

Precisely separating "iterable" (has Symbol.iterator) from "iterator" (has next) is the signal here. A common trick question: why can't you use for...of directly on a plain object? Because plain objects don't implement Symbol.iterator — for...in is the (different, key-only, prototype-walking) alternative for those.

Q32. How does Symbol.iterator power for...of, spread, and destructuring?

ROI: ★★★★☆ Frequency: High

Short Answer

All three language features are sugar over the iterator protocol: for...of, array/parameter spread ([...x], fn(...x)), and array destructuring each call x[Symbol.iterator]() and repeatedly invoke next() until done is true, rather than indexing directly.

Detailed Answer

This is why they work uniformly on arrays, strings, Maps, Sets, and any custom iterable, but not on plain objects (which lack Symbol.iterator) or array-likes without an iterator (like older arguments in some engines, or a raw {0:'a',1:'b',length:2}). Object spread ({...obj}) is a different mechanism entirely — it copies own enumerable properties and does not use the iterator protocol at all.

Code Example

const set = new Set([1, 2, 3]);
[...set];              // [1, 2, 3] — uses Symbol.iterator
const [first, second] = set; // destructuring also uses the iterator

for (const v of set) console.log(v); // 1, 2, 3

// Object spread is NOT iterator-based — it copies own enumerable props:
const o = { a: 1, b: 2 };
const copy = { ...o }; // works even though `o` has no Symbol.iterator

Senior Engineer Perspective

The nuance to volunteer: object spread and array/iterable spread look similar syntactically but rest on completely different mechanisms (enumerable own properties vs the iterator protocol). Confusing the two is a common junior mistake when asked "why can't I spread a plain object with for...of?"

Q33. How do you make a custom object iterable?

ROI: ★★★☆☆ Frequency: Medium

Short Answer

Implement a [Symbol.iterator]() method on the object that returns an iterator object with a next() method following the protocol. The simplest way to write that method body is as a generator function, since generators automatically satisfy the iterator protocol.

Detailed Answer

Once an object implements Symbol.iterator, it immediately gains support for for...of, spread, destructuring, and any API that expects an iterable (like Array.from or the spread inside new Set(iterable)) — for free, with no other changes.

Code Example

class Range {
  constructor(start, end) { this.start = start; this.end = end; }
  [Symbol.iterator]() {
    let current = this.start;
    const end = this.end;
    return {
      next() {
        return current <= end
          ? { value: current++, done: false }
          : { value: undefined, done: true };
      },
    };
  }
}

[...new Range(1, 5)]; // [1, 2, 3, 4, 5]
for (const n of new Range(1, 3)) console.log(n); // 1, 2, 3

// Same thing, far less boilerplate, using a generator:
class RangeGen {
  constructor(start, end) { this.start = start; this.end = end; }
  *[Symbol.iterator]() {
    for (let i = this.start; i <= this.end; i++) yield i;
  }
}

Senior Engineer Perspective

Show both the manual next() version and the generator shortcut — knowing that a generator method automatically implements the protocol (so you rarely hand-write next() in real code) is the senior move.

Q34. What are generator functions and what does yield actually do?

ROI: ★★★★☆ Frequency: High

Short Answer

A generator function (function*) returns a generator object — an iterator — instead of running to completion immediately. Calling .next() runs the body until the next yield, pauses execution there, and returns { value, done: false }; the paused state (local variables, position) is preserved until the next .next() call resumes it.

Detailed Answer

yield is a two-way communication point: the value after yield is sent out to the caller via next()'s return value, and whatever is passed into the next call to .next(arg) becomes the result of that yield expression inside the generator. This lets generators pause arbitrarily deep in a call — something regular functions cannot do — which is what makes them useful for lazy sequences, cooperative coroutine-style flows, and (historically) flattening async code before async/await existed.

Code Example

function* counter() {
  console.log("start");
  const a = yield 1;      // pauses here, sends out 1
  console.log("received", a);
  const b = yield 2;      // pauses here, sends out 2
  console.log("received", b);
  return "done";
}

const gen = counter();
gen.next();        // logs "start", returns { value: 1, done: false }
gen.next("x");      // logs "received x", returns { value: 2, done: false }
gen.next("y");      // logs "received y", returns { value: "done", done: true }

Senior Engineer Perspective

Emphasize the two-way channel — many candidates only know that yield produces values outward and miss that .next(arg) sends values back in. This bidirectional pausing is exactly what generator-based coroutine libraries (and redux-saga) exploit.

Q35. How do generators implement lazy, potentially infinite sequences?

ROI: ★★★★☆ Frequency: High

Short Answer

Because a generator only computes up to the next yield when asked, it can model an infinite sequence (natural numbers, Fibonacci) without ever materializing the whole thing in memory — values are produced lazily, one at a time, only as the consumer pulls them.

Detailed Answer

This is fundamentally different from returning an array: an array-based "infinite sequence" would have to be capped up front and computed eagerly, while a generator computes strictly on demand. Combine a lazy generator with a take(n) helper (or just break out of a for...of loop) to safely consume a finite prefix of infinite data.

Code Example

function* naturals() {
  let n = 1;
  while (true) yield n++;   // infinite — safe because it's lazy
}

function take(iterable, n) {
  const result = [];
  const it = iterable[Symbol.iterator]();
  for (let i = 0; i < n; i++) {
    const { value, done } = it.next();
    if (done) break;
    result.push(value);
  }
  return result;
}

take(naturals(), 5); // [1, 2, 3, 4, 5] — never loops forever

function* fibonacci() {
  let [a, b] = [0, 1];
  while (true) { yield a; [a, b] = [b, a + b]; }
}

Senior Engineer Perspective

A good follow-up: how would you cancel/stop consuming an infinite generator safely mid-stream in a UI (e.g., a component unmounts)? Simply stop calling .next() and let the generator (and its closure) become garbage-collectable, or call .return() to run any finally cleanup inside it.

Q36. What is yield* and how does generator delegation work?

ROI: ★★★☆☆ Frequency: Medium

Short Answer

yield* delegates iteration to another iterable (often another generator): it forwards every value the inner iterable yields out to the outer consumer, and forwards .next(arg)/.throw()/.return() calls into the inner generator, until the inner one finishes — whose final return value becomes the result of the yield* expression itself.

Detailed Answer

This lets you compose generators the way you compose functions — a large generator can be built out of smaller ones without manually re-looping over each inner generator's values with for...of + yield.

Code Example

function* inner() {
  yield "a";
  yield "b";
  return "inner-result";
}

function* outer() {
  yield 1;
  const result = yield* inner(); // delegates — forwards "a", "b"
  console.log(result);           // "inner-result"
  yield 2;
}

[...outer()]; // [1, "a", "b", 2]  (the returned value isn't in the spread)

Senior Engineer Perspective

Point out that the inner generator's return value is not yielded (so it doesn't appear in a spread/for-of), but it IS captured as the value of the yield* expression — a detail that trips people up when composing generators for tree traversal (e.g., recursively delegating to child-node generators).

Q37. How were generators historically used to flatten async control flow before async/await existed?

ROI: ★★★☆☆ Frequency: Medium

Short Answer

A "co-routine runner" would call a generator's .next(), receive a yielded promise, wait for it to resolve, then feed the resolved value back in via .next(value) — repeating until the generator was done. This let async code inside the generator read top-to-bottom with yield somePromise standing in for what later became await somePromise.

Detailed Answer

Libraries like co popularized this pattern, and it directly inspired the design of async/await — an async function is essentially this exact runner built into the language, with the engine driving the generator-like state machine instead of user code. Understanding this history explains why redux-saga still uses raw generators: it needs full control over pausing, cancelling, and racing effects, which a runner can implement by choosing when (or whether) to call .next().

Code Example

function run(genFn) {
  const gen = genFn();
  function step(nextVal) {
    const { value, done } = gen.next(nextVal);
    if (done) return Promise.resolve(value);
    return Promise.resolve(value).then(step); // wait, then feed result back in
  }
  return step();
}

function* fetchFlow() {
  const user = yield fetch("/api/user").then(r => r.json());
  const posts = yield fetch(`/api/posts?user=${user.id}`).then(r => r.json());
  return posts;
}

run(fetchFlow).then((posts) => console.log(posts));

Senior Engineer Perspective

Knowing this history signals depth beyond "I use async/await" — it shows you understand why the language grew this feature and can reason about libraries (like redux-saga) that deliberately still use raw generators for cancellable, testable effect sequences.

Q38. What is the difference between a generator's next, return, and throw methods?

ROI: ★★★☆☆ Frequency: Medium

Short Answer

next(value) resumes execution, injecting value as the result of the paused yield. return(value) forces the generator to finish immediately as if a return value statement executed at the paused point (running any finally blocks first) and marks it done. throw(error) resumes the generator by throwing error at the paused yield, which the generator can catch internally with try/catch or let propagate out.

Detailed Answer

return() and throw() are what make generators safely cancellable and are exactly how a for...of loop that breaks out early cleans up: the loop implicitly calls .return() on the iterator, giving any pending finally block a chance to release resources (like closing a file handle or clearing a subscription).

Code Example

function* resourceUser() {
  try {
    yield "using resource";
    yield "still using resource";
  } finally {
    console.log("cleanup ran"); // guaranteed even on early return()
  }
}

const gen = resourceUser();
gen.next();          // { value: "using resource", done: false }
gen.return("bye");   // logs "cleanup ran", returns { value: "bye", done: true }

// for...of automatically calls .return() on break:
for (const v of resourceUser()) {
  console.log(v);
  break; // triggers cleanup via .return() under the hood
}

Senior Engineer Perspective

Knowing that for...of calling break implicitly invokes .return() (and therefore runs finally blocks) is a detail most candidates miss — it is exactly how generator-based resource management stays leak-free even when consumers stop early.

Q39. What problem do async iterators and for await...of solve?

ROI: ★★★★☆ Frequency: High

Short Answer

Regular iterators produce values synchronously, but many real sequences arrive asynchronously — paginated API results, streamed file chunks, WebSocket messages. Async iterators implement Symbol.asyncIterator and return promises of { value, done }; for await...of consumes them, awaiting each step automatically.

Detailed Answer

Without async iterators you would hand-roll a loop that awaits each page/chunk and manually tracks a "done" flag. for await...of makes consuming an asynchronous sequence look exactly like consuming a synchronous one, and it works uniformly across async generators, streaming Response bodies, and any custom object implementing Symbol.asyncIterator.

Code Example

async function* paginate(fetchPage) {
  let page = 0;
  while (true) {
    const { items, hasMore } = await fetchPage(page++);
    yield items;
    if (!hasMore) return;
  }
}

async function loadAll(fetchPage) {
  const all = [];
  for await (const items of paginate(fetchPage)) {
    all.push(...items);
  }
  return all;
}

Senior Engineer Perspective

Connect this to real streaming APIs — ReadableStream readers and, in Node, fs.createReadStream, are consumable with for await...of. Mention that for await...of also works on an array of plain (non-async) promises, awaiting each in turn.

Q40. How do you write and consume an async generator function?

ROI: ★★★☆☆ Frequency: Medium

Short Answer

Declare it with async function*. Inside, you can use both await (to pause for a promise) and yield (to emit a value out to the consumer). Calling it returns an async generator object, consumed with for await...of or by manually calling .next(), which now returns a promise of { value, done }.

Detailed Answer

Async generators combine everything: laziness (values computed on demand), asynchrony (each step can await I/O), and the standard iterator ergonomics (break in a for await...of loop still triggers cleanup via .return(), now awaited too).

Code Example

async function* streamLines(url) {
  const response = await fetch(url);
  const reader = response.body.getReader();
  const decoder = new TextDecoder();
  let buffer = "";
  while (true) {
    const { value, done } = await reader.read();
    if (done) break;
    buffer += decoder.decode(value, { stream: true });
    const lines = buffer.split("\n");
    buffer = lines.pop();
    for (const line of lines) yield line;
  }
  if (buffer) yield buffer;
}

for await (const line of streamLines("/logs.txt")) {
  console.log(line);
}

Senior Engineer Perspective

A strong candidate mentions real use cases: streaming and incrementally parsing large responses, paginated APIs, or reading a large file line-by-line without loading it entirely into memory — the async generator only holds one chunk/line at a time.

Q41. What is the difference between Array.prototype.entries/keys/values and writing a custom iterator?

ROI: ★★★☆☆ Frequency: Medium

Short Answer

arr.keys(), arr.values(), and arr.entries() are built-in methods that return standard iterators over indices, values, or [index, value] pairs respectively — no custom code needed. A custom iterator is only necessary when you need to iterate over something that isn't already an array/Map/Set, or when you want non-default traversal (e.g., skipping, reversing, or lazily computing values).

Detailed Answer

All three return the same kind of iterator object described by the iterator protocol, so they compose with for...of and spread exactly like any other iterable. They are useful when you specifically need indices alongside values without a separate counter variable, which forEach((v, i) => ...) already covers for simple cases, but entries() shines when combined directly with destructuring in a for...of loop.

Code Example

const arr = ["a", "b", "c"];

for (const [index, value] of arr.entries()) {
  console.log(index, value); // 0 a, 1 b, 2 c
}

[...arr.keys()];    // [0, 1, 2]
[...arr.values()];  // ["a", "b", "c"]

// A Map's default iterator already yields [key, value] entries:
const m = new Map([["x", 1], ["y", 2]]);
for (const [k, v] of m) console.log(k, v); // x 1, y 2

Senior Engineer Perspective

Interviewers check whether you reach for these built-ins before hand-rolling an iterator — a senior engineer knows the standard library well enough to avoid unnecessary custom code, reserving hand-written iterators for genuinely novel traversal logic.

Q42. When would you choose a generator over returning a plain array from a data-fetching helper in a React app?

ROI: ★★★☆☆ Frequency: Medium

Short Answer

Choose a generator (or async generator) when the full result set is large or unbounded and you want to start rendering/processing before everything has loaded — for example, incrementally rendering search results as pages arrive rather than waiting for every page. Choose a plain array/promise when the data set is small and bounded, since arrays are simpler to store in state and re-render from.

Detailed Answer

Generators do not compose naturally with React state (which wants immutable snapshots to diff), so in practice a component consumes an async generator inside an effect, pushing each yielded chunk into state incrementally (setItems(prev => [...prev, ...chunk])) rather than storing the generator itself in state. This gives a streaming UX (progressive rendering) without needing a full custom streaming protocol.

Code Example

function useStreamedList(streamFactory) {
  const [items, setItems] = React.useState([]);
  React.useEffect(() => {
    let cancelled = false;
    setItems([]);
    (async () => {
      for await (const chunk of streamFactory()) {
        if (cancelled) return;
        setItems((prev) => [...prev, ...chunk]);
      }
    })();
    return () => { cancelled = true; };
  }, [streamFactory]);
  return items;
}

Senior Engineer Perspective

The maturity signal is recognizing that the generator is an implementation detail of the data-fetching layer, not something you store directly in React state — state should stay a plain, diffable snapshot, while the generator drives incremental updates to it.

SECTION 8 - MEMORY MANAGEMENT & GARBAGE COLLECTION

Q43. How does JavaScript's garbage collector decide what to reclaim?

ROI: ★★★★☆ Frequency: High

Short Answer

Modern engines use a "mark-and-sweep" style algorithm based on reachability, not reference counting. Starting from a set of "roots" (global object, currently executing call stack, active closures), the collector marks everything reachable by following references transitively; anything left unmarked is unreachable and gets swept (its memory reclaimed).

Detailed Answer

This means an object is eligible for collection the moment nothing reachable from a root points to it — even if two objects still reference each other (a cycle), they are both collected once nothing else external reaches either one, unlike naive reference counting which would leak cycles forever. V8 additionally uses generational collection: most objects die young (the "young generation"), so it runs cheap, frequent minor GCs there and less frequent, more expensive major GCs across the whole ("old") generation.

Code Example

let a = { name: "a" };
let b = { name: "b" };
a.ref = b;
b.ref = a;          // a and b reference each other (a cycle)

a = null;
b = null;           // both refs from roots are gone
// Even though a and b still reference each other, neither is reachable
// from any root anymore, so mark-and-sweep collects both.

Senior Engineer Perspective

The classic trap question is "does JS use reference counting?" — no, precisely because reference counting cannot collect cycles without extra help; mark-and-sweep handles cycles naturally. Mentioning generational GC and why it exists (most allocations are short-lived, like objects created during a single render) shows deeper systems knowledge.

Q44. What are the classic causes of memory leaks in JavaScript applications?

ROI: ★★★★☆ Frequency: High

Short Answer

The recurring pattern is: something a root can still reach (a global variable, a long-lived closure, an active timer, a registered event listener, a cache) keeps pointing at an object long after it should logically be discarded. Common sources: forgotten setInterval/event listeners, accidental globals, detached DOM nodes still referenced from JS, and unbounded caches/maps that only ever grow.

Detailed Answer

  • Uncleared timers/intervals: a running setInterval closure keeps everything it references alive indefinitely.
  • Unremoved event listeners: a listener attached to a long-lived target (like window) that closes over a component's data keeps that data alive after the component is gone.
  • Detached DOM nodes: removing a node from the document but still holding a JS reference to it (and everything it, in turn, references) keeps the whole subtree alive.
  • Unbounded caches/maps: a Map or object used as a cache that never evicts entries grows forever.
  • Accidental globals: forgetting a declaration in sloppy mode attaches a variable to the global object, which never gets collected.

Code Example

// Leak: interval never cleared, keeps `bigData` alive forever
function start(bigData) {
  setInterval(() => console.log(bigData.length), 1000);
}

// Fix: keep the handle and clear it when done
function start2(bigData) {
  const id = setInterval(() => console.log(bigData.length), 1000);
  return () => clearInterval(id);
}

Senior Engineer Perspective

Interviewers want a checklist you can name from memory and, ideally, a story about diagnosing one in production. Tie each cause back to "something reachable is still pointing at it" — that single sentence is the unifying idea behind every leak category.

Q45. How can closures cause memory leaks?

ROI: ★★★★☆ Frequency: High

Short Answer

A closure keeps its entire enclosing scope alive for as long as the closure itself is reachable — not just the variables it actually uses. If a long-lived closure (e.g., an event handler or timer callback) is created inside a scope that also holds a large object, that large object cannot be collected even if the closure never touches it.

Detailed Answer

Modern V8 optimizes this somewhat — it can avoid retaining variables a closure provably never references — but you should not rely on that optimization across all engines and code shapes. The safer mental model: anything declared in the same scope as a long-lived closure is at risk of being retained. This is exactly why "attach a listener that closes over big props/state and never remove it" is such a common React leak — the handler function outlives the component that created it.

Code Example

function setup() {
  const hugeBuffer = new Array(1_000_000).fill("x"); // large
  const smallFlag = true;

  // This closure only uses smallFlag, but naively could retain hugeBuffer too
  window.addEventListener("resize", function onResize() {
    if (smallFlag) console.log("resized");
  });
  // If onResize is never removed, its retained scope (and, depending on
  // engine analysis, hugeBuffer) stays alive for the lifetime of the page.
}

Senior Engineer Perspective

Bring this back to React: a useEffect callback closes over whatever it references from render; if it subscribes to something long-lived (a global event bus, window) without a cleanup function, that closure — and everything reachable through it — outlives the component. This is the exact reason useEffect cleanup functions exist.

Q46. What is a detached DOM node and why is it a common leak in single-page apps?

ROI: ★★★★☆ Frequency: High

Short Answer

A detached DOM node is one that has been removed from the visible document tree but is still referenced by JavaScript (a variable, a closure, an event listener, a cache) — so the browser cannot reclaim it even though it no longer renders. In a long-lived SPA, this accumulates over time as components mount/unmount thousands of times without those references being released.

Detailed Answer

A typical cause: code caches a reference to a DOM element (const el = document.getElementById(...)) inside a module-level variable or closure, and later the framework removes that element from the tree during a re-render — but the cached reference is never cleared, so the detached node (and its subtree, and any data attached to it via expando properties) stays in memory.

Code Example

let cachedHeader; // module-level — outlives any single render

function cacheHeader() {
  cachedHeader = document.querySelector("#app-header");
}
// Later, React removes/re-creates #app-header during a re-render.
// `cachedHeader` still points to the OLD node — now detached but retained.

// Fix: don't cache raw DOM nodes outside the component/ref lifecycle;
// re-query when needed, or use a React ref which is cleared on unmount.

Senior Engineer Perspective

Mention how you would actually find this in production: Chrome DevTools → Memory → heap snapshot, filter by "Detached", and inspect retainers to see which JS reference is keeping the node alive. Being able to describe the diagnostic workflow, not just the definition, is the senior signal.

Q47. What is WeakMap and how does it differ from Map regarding garbage collection?

ROI: ★★★★☆ Frequency: High

Short Answer

WeakMap holds its keys weakly — an object used as a key does not keep that object alive. If nothing else references the key object, it (and its associated value) can be garbage collected, and the entry silently disappears from the map. A regular Map holds strong references to its keys, so entries live as long as the map itself does, even if nothing else points to the key.

Detailed Answer

WeakMap keys must be objects (not primitives), and it is deliberately non-enumerable — no size, no keys()/forEach — precisely because its contents can change at any moment due to GC, which would make iteration unpredictable. This makes it ideal for attaching metadata to an object (caches, private fields, DOM-node-keyed data) without preventing that object from being collected when nothing else needs it.

Q48. What is WeakSet and when would you use it?

ROI: ★★★☆☆ Frequency: Medium

Short Answer

WeakSet is to Set what WeakMap is to Map: a collection of objects (only objects, no primitives) held weakly, non-enumerable, with no size. It is used to mark or tag objects — e.g., "has this object already been processed?" — without preventing them from being garbage collected.

Detailed Answer

A typical use: tracking which objects have already been visited during a traversal (to detect cycles or avoid reprocessing) without needing to add a marker property directly onto the object itself, and without leaking memory if the objects are later discarded elsewhere.

Code Example

const visited = new WeakSet();

function processOnce(obj) {
  if (visited.has(obj)) return;
  visited.add(obj);
  // ... do work with obj ...
}

const item = { id: 1 };
processOnce(item);
processOnce(item); // no-op, already visited
// item = null; -> entry can be GC'd, no manual cleanup needed

Senior Engineer Perspective

Note the trade-off versus a plain marker property (obj._visited = true): mutating the object itself can have side effects (shows up in JSON.stringify, for...in, equality checks elsewhere) whereas a WeakSet keeps the marker entirely external and leak-free.

Q49. What are WeakRef and FinalizationRegistry, and why are they rarely needed?

ROI: ★★★☆☆ Frequency: Medium

Short Answer

WeakRef holds a weak reference to an object, letting you access it via .deref() while it is still alive, without preventing collection. FinalizationRegistry lets you register a callback to run (at some unspecified future point) after an object has been garbage collected. Both are low-level, advanced tools — the spec explicitly discourages relying on them for core program logic because GC timing is non-deterministic and callback execution is not guaranteed.

Detailed Answer

They exist for niche cases like caches that should not prevent eviction, or bridging to external/native resources that need cleanup notification. Because finalizer timing is unpredictable (it may run late, or in some edge cases not at all before the process exits), you must never use FinalizationRegistry for correctness-critical cleanup (like releasing a lock) — only as a backstop/diagnostic alongside explicit cleanup (like a dispose() method or useEffect cleanup).

Code Example

const registry = new FinalizationRegistry((heldValue) => {
  console.log("collected:", heldValue); // NOT guaranteed to run promptly
});

let obj = { data: "big" };
const ref = new WeakRef(obj);
registry.register(obj, "obj-label");

obj = null; // eligible for collection
// later: ref.deref() returns undefined once obj has actually been collected

Senior Engineer Perspective

The correct senior stance is caution: know these exist and what problem they solve, but flag that they should almost never be reached for in application code — explicit lifecycle management (cleanup functions, dispose methods) is always more reliable than hoping a finalizer runs.

Q50. How do event listeners cause leaks in React components, and how do you avoid them?

ROI: ★★★★★ Frequency: Extremely High

Short Answer

If a component attaches a listener to a long-lived target (window, document, an event bus, a WebSocket) inside useEffect but never removes it, the listener's closure (and everything it references — props, state, sometimes the whole fiber) stays alive after the component unmounts, because the long-lived target still holds a strong reference to the callback.

Detailed Answer

The fix is always the same shape: return a cleanup function from useEffect that removes exactly what was added, using the same reference. A common subtle bug is passing a fresh inline arrow function to both addEventListener and (a different) one to removeEventListener — removal silently fails because function references are compared by identity, not by "looks the same."

Code Example

// LEAK — no cleanup, and cleanup would fail anyway (different function refs)
useEffect(() => {
  window.addEventListener("resize", () => console.log(window.innerWidth));
}, []);

// CORRECT — same reference added and removed, cleanup runs on unmount
useEffect(() => {
  function handleResize() { console.log(window.innerWidth); }
  window.addEventListener("resize", handleResize);
  return () => window.removeEventListener("resize", handleResize);
}, []);

Senior Engineer Perspective

This is one of the highest-frequency real bugs in production React code. State the rule crisply: "whatever you subscribe to in the effect body, unsubscribe in the returned cleanup, using the identical function reference." Also mention React 18 Strict Mode intentionally mounts, unmounts, and remounts effects in development specifically to surface missing cleanup like this.

Q51. How do closures inside setInterval or stale effects retain outdated references, and how does cleanup prevent leaks?

ROI: ★★★★☆ Frequency: High

Short Answer

A closure created in one render (e.g., inside setInterval started in useEffect) captures that render's props/state by reference. If the interval is never cleared when the component re-renders or unmounts, the old closure — and the stale data it references — stays alive and keeps running, doubling up with the new one and leaking memory each time.

Detailed Answer

Without a dependency array or cleanup, every re-render that re-runs the effect creates a brand-new interval while the old one keeps ticking in the background — both retaining their own closed-over state snapshot, compounding both the "stale value" bug and a genuine memory/CPU leak. The fix is always to clear the previous timer/subscription in the effect's cleanup function before the next one is created.

Code Example

// LEAKY + STALE: a new interval every render, old ones never cleared
useEffect(() => {
  setInterval(() => {
    console.log(count); // closes over stale `count` from this render
  }, 1000);
}); // no dependency array -> runs after every render

// CORRECT: single interval, cleared on unmount/dependency change,
// and uses a functional update to avoid the stale-closure problem entirely
useEffect(() => {
  const id = setInterval(() => {
    setCount((c) => c + 1); // always operates on the latest state
  }, 1000);
  return () => clearInterval(id);
}, []);

Senior Engineer Perspective

Two distinct bugs are often conflated here: the stale closure (wrong value read) and the leak (old interval never stopped). A senior answer separates them and shows that the functional updater fixes staleness while clearInterval in cleanup fixes the leak — you typically need both.

Q52. How would you use Chrome DevTools to find a memory leak?

ROI: ★★★★☆ Frequency: High

Short Answer

Take heap snapshots at two points in time (before and after the suspected leaking action, repeated a few times), then use the "Comparison" view in the Memory panel to see which object types grew and never shrank. Filter for "Detached" to spot orphaned DOM trees, and inspect an object's "Retainers" to trace exactly which reference is keeping it alive.

Detailed Answer

A reliable workflow: (1) open DevTools → Memory → Heap snapshot; (2) perform the suspected leaking action once and take a snapshot (let things settle, force a GC first); (3) repeat the action several more times and take another snapshot; (4) use the "Comparison" mode between the two — objects whose count keeps growing across repeated identical actions are strong leak candidates; (5) click into one, view its retainer chain, and read upward to find the root that should have let go but didn't.

Code Example

// Example of code you'd catch this way: a subscription added on every
// mount of a modal, never removed, so repeated open/close cycles grow
// the retained-object count indefinitely in the heap comparison view.
function Modal({ onClose }) {
  useEffect(() => {
    analytics.on("event", trackEvent); // never removed -> leak
  }, []);
  // ...
}

Senior Engineer Perspective

Being able to describe this workflow concretely — repeated snapshots, comparison view, retainer chain — signals you have actually debugged a production leak, not just read the definition. Also mention the Performance Monitor's live "JS Heap size" graph as a quick first signal that something is growing unbounded.

Q53. Does setting a variable to null immediately free the memory it referenced?

ROI: ★★★☆☆ Frequency: Medium

Short Answer

No. Setting x = null only removes that reference. The underlying object's memory is freed only later, whenever the garbage collector runs its next cycle and determines the object is unreachable from every root — and only if no other reference to it still exists anywhere else in the program.

Detailed Answer

Garbage collection in JS is non-deterministic and asynchronous relative to your code — there is no way to force an immediate synchronous free (unlike manual memory management in C). Nulling a reference is a hint that helps the collector conclude reachability sooner, but it is not a "free() call." This also means "did nulling this variable fix my leak?" is not something you can verify by observing memory immediately after — you need a heap snapshot after GC has actually run.

Code Example

let big = new Array(1_000_000).fill(0);
let alias = big;

big = null;      // one reference gone
console.log(alias.length); // 1000000 — still fully alive via `alias`!

alias = null;     // NOW no reachable reference remains
// The actual memory reclaim still happens at the GC's own schedule.

Senior Engineer Perspective

This question filters out candidates who think of nulling a variable as a manual free. The correct framing: you can only make an object unreachable; you can never force reclamation timing, and other lingering references anywhere in the program will keep it alive regardless of how many variables you clear.

Q54. How do global variables and unbounded caches contribute to memory growth over time?

ROI: ★★★★☆ Frequency: High

Short Answer

A global variable is always reachable from a root for the entire lifetime of the page, so anything stored in it (or transitively reachable through it) can never be collected until you explicitly clear it. An unbounded cache (a Map/object that only ever adds entries and never evicts) behaves the same way — it grows monotonically as long as the app runs, which is especially dangerous in a long-lived SPA that never does a full page reload.

Detailed Answer

The fix pattern is bounding growth deliberately: an LRU cache with a max size, a TTL-based eviction, or a WeakMap when the cache should be tied to the lifetime of its keys rather than the app's lifetime. This is a genuinely common production issue in SPAs — a memoization cache or a "recently viewed items" store that seemed harmless in testing (short session) but grows unbounded over an hour-long user session.

Code Example

// Unbounded — grows forever across a long session
const cache = new Map();
function getOrCompute(key, compute) {
  if (!cache.has(key)) cache.set(key, compute(key));
  return cache.get(key);
}

// Bounded LRU-style cache
class LRUCache {
  constructor(maxSize) { this.maxSize = maxSize; this.map = new Map(); }
  get(key) {
    if (!this.map.has(key)) return undefined;
    const val = this.map.get(key);
    this.map.delete(key);
    this.map.set(key, val); // move to "most recent" position
    return val;
  }
  set(key, val) {
    if (this.map.has(key)) this.map.delete(key);
    else if (this.map.size >= this.maxSize) {
      this.map.delete(this.map.keys().next().value); // evict oldest
    }
    this.map.set(key, val);
  }
}

Senior Engineer Perspective

Interviewers want you to proactively flag that "cache" and "leak" are often the same code viewed at different time scales — a cache is only safe once it has an explicit bound (size, TTL, or weak keys). Naming LRU eviction or WeakMap as the fix shows you've actually shipped and maintained a long-running client app.

SECTION 9 - MODULES: ES MODULES, COMMONJS & BUNDLING

Q55. What is the difference between ES Modules (ESM) and CommonJS (CJS)?

ROI: ★★★★★ Frequency: Extremely High

Short Answer

ESM (import/export) is the standardized, static module system built into the language — imports/exports are resolved at parse time, before any code runs, which enables tree-shaking and top-level await. CommonJS (require/module.exports) is Node's original, dynamic, runtime module system — require is just a function call that can appear anywhere, evaluated synchronously as the code runs.

Detailed Answer

AspectESMCommonJS
Syntaximport / exportrequire / module.exports
ResolutionStatic (parse time)Dynamic (runtime)
LoadingCan be asyncAlways synchronous
BindingsLive referencesCopied value (snapshot)
Tree-shakingYes — static shapeHard — dynamic shape
this at top levelundefinedmodule.exports

Because ESM imports/exports must appear at the top level with static names, a bundler can build an exact dependency graph without running any code — which is the foundation of tree-shaking, static analysis, and code-splitting. CommonJS's require can be called conditionally or with a computed string, so bundlers generally have to include the whole module, since they cannot always prove which exports are used ahead of time.

Code Example

// ESM
export const add = (a, b) => a + b;
export default function Main() {}
import Main, { add } from "./math.js";

// CommonJS
function add(a, b) { return a + b; }
module.exports = { add };
const { add } = require("./math.js");

Senior Engineer Perspective

Be ready to explain why a modern React app almost always ships ESM to the bundler (for tree-shaking) even though its dependencies or Node tooling may still be CommonJS, and why interop between the two (Q66) is a routine source of build configuration headaches.

Q56. Are ES module imports live bindings or copies? What does that mean in practice?

ROI: ★★★★☆ Frequency: High

Short Answer

ESM imports are live bindings, not copies: if the exporting module later reassigns an exported variable, every importer sees the updated value automatically, because the import is a read-only reference into the exporting module's own binding — not a snapshot taken at import time. CommonJS, in contrast, copies the value of module.exports at the moment require runs; later reassignment in the source module is invisible to already-imported copies (for primitives).

Detailed Answer

This live-binding behavior is exactly how it is possible for two modules to import each other (a circular dependency) and still, eventually, see the correct values — the binding exists before evaluation completes, it just isn't initialized until the exporting code runs that line. Note you cannot reassign an imported binding yourself from the importing module — only the module that owns the export can update it.

Code Example

// counter.js
export let count = 0;
export function increment() { count++; }

// main.js
import { count, increment } from "./counter.js";
console.log(count); // 0
increment();
console.log(count); // 1 — live binding sees the update automatically

// count = 5; // SyntaxError — imported bindings are read-only

Senior Engineer Perspective

This trips up engineers coming from CommonJS, where destructuring a required value copies it once. Being able to state precisely "ESM bindings are live views, CJS gives you a value snapshot" — and explain why that matters for circular dependencies — is a strong signal.

Q57. What is the difference between named exports and a default export, and when should you use each?

ROI: ★★★★☆ Frequency: High

Short Answer

A module can have any number of named exports, each imported by its exact name (optionally renamed with as), which keeps names consistent across the codebase and enables precise tree-shaking. A module can have at most one default export, imported under whatever name the importer chooses — convenient for a module's single "main" thing, but it loses the tree-shaking-friendly static name and makes renaming/refactoring harder to track with tooling.

Detailed Answer

Many teams standardize on named exports even for a component's main export, specifically because IDEs, ESLint, and bundlers can more reliably rename/trace named exports, and because a stray default export renamed inconsistently at each import site makes searching the codebase for usages harder. Named exports also let you export several related things from one file (a component plus its prop types/hooks) without arbitrary bundling into a default object.

Code Example

// Named exports — explicit names, multiple per module
export function Button() {}
export function IconButton() {}
import { Button, IconButton as IconBtn } from "./buttons.js";

// Default export — one per module, importer names it freely
export default function Button() {}
import AnyNameYouWant from "./Button.js"; // no enforced consistency

// Mixed — common in React component files
export default function Card() {}
export const CardHeader = () => {};

Senior Engineer Perspective

A senior nuance: default exports interact poorly with some tooling (auto-import may suggest an inconsistent local name, and re-exporting a default requires special syntax). Many modern style guides (including Airbnb's older stance, though it has evolved) discourage default exports for exactly this reason.

Q58. What is tree-shaking, and what makes code tree-shakeable vs not?

ROI: ★★★★★ Frequency: Extremely High

Short Answer

Tree-shaking is dead-code elimination performed by a bundler: it analyzes the static import/export graph and strips exports that are never actually imported anywhere, shrinking the final bundle. It relies on ESM's static structure — imports/exports whose names and existence can be determined without executing code.

Detailed Answer

Code stays tree-shakeable when: exports are static (no module.exports = computeSomething()), imports use named bindings rather than importing an entire namespace object and accessing properties dynamically, and the module has no observable side effects at the top level that the bundler can't safely skip (a side-effecting top-level statement forces the whole module to be included even if nothing imports from it). This is also why importing an entire library's default export (import _ from "lodash") often bundles the whole library, while importing a specific named function from an ESM-native build tree-shakes down to just that function.

Code Example

// utils.js — statically analyzable, tree-shakeable
export function used() { return 1; }
export function unused() { return 2; } // dropped if nothing imports it

// main.js
import { used } from "./utils.js"; // bundler can prove `unused` is dead

// NOT tree-shakeable — dynamic export shape
export default (function () {
  return Math.random() > 0.5 ? { a: 1 } : { b: 2 };
})();

// Side effect at module top level forces inclusion regardless of usage:
console.log("module loaded"); // bundler can't safely drop this module

Senior Engineer Perspective

Interviewers like a concrete story: switching from import _ from "lodash" to import debounce from "lodash/debounce" (or lodash-es) to cut bundle size. Mention that a bundle analyzer (webpack-bundle-analyzer, source-map-explorer) is the practical tool for verifying tree-shaking actually happened.

Q59. Why does CommonJS mostly defeat tree-shaking?

ROI: ★★★★☆ Frequency: High

Short Answer

Because require and module.exports are ordinary runtime operations rather than a static declared structure, a bundler generally cannot prove — without actually executing the module — which properties of module.exports will exist or be used. So the safe, conservative default is to include the entire module.

Detailed Answer

require can be called conditionally, inside a function, with a computed path, or the exported object can be built up dynamically across the file — all things static analysis cannot fully resolve. Some bundlers apply heuristics to partially tree-shake simple, well-behaved CommonJS modules, but this is best-effort, not guaranteed, which is why ESM-native ("dual" or "ESM-first") package builds are preferred for anything performance-sensitive.

Code Example

// CommonJS — bundler must assume anything could be used
if (process.env.FEATURE_X) {
  module.exports.featureX = require("./feature-x");
}
module.exports.core = require("./core");
// A bundler can't safely prove featureX is unused without running this code.

// ESM equivalent forces a static shape — always analyzable:
export { core } from "./core.js";
export { featureX } from "./feature-x.js"; // static, always present

Senior Engineer Perspective

A sharp follow-up: "so should you ever ship CommonJS to the browser?" Generally no for app code — but many npm packages still publish CJS as their primary build for Node compatibility, which is exactly why package.json's "module"/"exports" fields (Q64) exist, to let bundlers pick an ESM build when available.

Q60. What is a circular dependency, and how do ESM and CommonJS handle it differently?

ROI: ★★★☆☆ Frequency: Medium

Short Answer

A circular dependency is when module A imports from module B, and B (directly or transitively) imports from A. CommonJS resolves this by returning whatever partial module.exports the in-progress module has built up so far when the cycle is detected — often an incomplete object. ESM handles it more gracefully via live bindings and hoisted declarations: the binding exists (even if not yet initialized) before either module finishes evaluating, so as long as you don't use the value synchronously at the top of the cycle, it resolves correctly once both modules finish loading.

Detailed Answer

In both systems, circular dependencies are still a code smell worth avoiding via refactoring (extracting shared code into a third module) — ESM just fails less silently/confusingly than CJS, because live bindings mean a function defined later in a cyclic import will work correctly by the time it's actually called, even if it wasn't ready at import time.

Code Example

// CommonJS — a.js and b.js require each other
// a.js
const b = require("./b.js");
module.exports.name = "a";
module.exports.getBName = () => b.name; // deferred access — safe

// b.js
const a = require("./a.js"); // `a` here is the PARTIAL exports of a.js
module.exports.name = "b";
console.log(a.name); // may be undefined if b.js loads before a.js finishes

// ESM handles the same shape more predictably via live bindings,
// as long as values are read inside functions, not at the top level.

Senior Engineer Perspective

The strongest answer treats circular dependencies primarily as an architecture smell — the module-system behavior is a secondary detail. Mention extracting shared types/utilities into a separate module to break the cycle as the real fix, rather than relying on either system's partial-resolution behavior.

Q61. What are dynamic imports (import()), and when should you use them in a React app?

ROI: ★★★★★ Frequency: Extremely High

Short Answer

import("./module.js") is an expression (usable anywhere, including conditionally) that asynchronously loads a module and returns a promise resolving to its exports. Bundlers recognize this syntax and automatically split the imported module into a separate chunk, loaded on demand rather than bundled into the initial payload — the mechanism behind route-based and component-based code-splitting.

Detailed Answer

Use it for anything not needed on initial page load: routes the user hasn't navigated to yet, heavy modals/editors, or large third-party libraries only needed behind a specific interaction. React.lazy is built directly on top of dynamic import(), pairing it with Suspense to show a fallback while the chunk downloads.

Code Example

// Conditional dynamic import — only loads the heavy chart lib if needed
async function renderChartIfNeeded(showChart) {
  if (showChart) {
    const { renderChart } = await import("./chartLib.js");
    renderChart();
  }
}

// React.lazy / Suspense — component-level code-splitting
const HeavyEditor = React.lazy(() => import("./HeavyEditor.js"));

function App() {
  return (
    <React.Suspense fallback={<Spinner />}>
      <HeavyEditor />
    </React.Suspense>
  );
}

Project Example

A dashboard route splits its rarely-visited "Admin Settings" page behind React.lazy(() => import("./AdminSettings")) so the main bundle stays small for the 95% of users who never visit it — measurably improving first-load performance without any change to how the component itself is written.

Senior Engineer Perspective

Expect to discuss trade-offs: too many tiny chunks means more round-trips and waterfall delays, so code-splitting boundaries should align with real user navigation patterns (route-level is the most common granularity) rather than splitting every component individually.

Q62. Why do bundlers care about type-only imports, and how do they differ from regular imports in a TypeScript codebase?

ROI: ★★★☆☆ Frequency: Medium

Short Answer

TypeScript's import type { Foo } from "./foo" tells the compiler this import exists purely for type-checking and must be completely erased at compile time — no runtime require/import is emitted for it. This matters for bundlers because a regular import { Foo } where Foo happens to only be a type can otherwise leave a real (and sometimes side-effecting, or circular-dependency-causing) runtime import in the compiled output.

Detailed Answer

Without explicit type-only imports, a transpiler that processes files one at a time (like Babel's TypeScript plugin, or isolatedModules mode) cannot always tell whether an imported name is a type or a value, since that normally requires full cross-file type information. Marking it explicitly with import type removes the ambiguity, guarantees the import is erased, and can break otherwise-harmless circular import chains that only exist for type purposes.

Code Example

// types.ts
export interface User { id: number; name: string; }

// component.tsx
import type { User } from "./types"; // erased entirely at compile time
import { formatUser } from "./utils"; // real runtime import, kept

function Greeting({ user }: { user: User }) {
  return formatUser(user);
}

Senior Engineer Perspective

Mention isolatedModules: true and why tools like Babel and esbuild require it — they compile one file at a time with no cross-file type knowledge, so they need explicit import type to safely erase type-only imports rather than guessing.

Q63. What does "sideEffects": false in package.json do, and why can it be dangerous if misconfigured?

ROI: ★★★☆☆ Frequency: Medium

Short Answer

Setting "sideEffects": false in a package's package.json is a promise to the bundler: "every module in this package is safe to drop entirely if none of its exports are used — none of them do anything observable just by being imported." This unlocks more aggressive tree-shaking across module boundaries, beyond what static analysis alone could prove.

Detailed Answer

It is dangerous precisely because it is a manual, unenforced promise: if any module in the package actually does have a top-level side effect (registers a global, polyfills something, attaches a CSS import), and the flag falsely claims otherwise, the bundler will happily strip that module out — producing a build that's missing behavior it silently depended on, often only noticed in production. The safer, granular alternative is listing an array of specific files that DO have side effects (e.g., CSS imports) rather than a blanket boolean.

Code Example

{
  "name": "my-lib",
  "sideEffects": false
}

// More precise — most files are side-effect free, but these aren't:
{
  "name": "my-lib",
  "sideEffects": ["./src/polyfills.js", "*.css"]
}

// A module that WOULD be wrongly stripped under a false "sideEffects: false":
// registers something globally just by being imported
window.myGlobalPlugin = { init() {} };

Senior Engineer Perspective

A great story here: debugging a production bug where a CSS import or polyfill silently disappeared after a dependency added "sideEffects": false incorrectly. It shows you understand tree-shaking isn't purely mechanical — it depends on package authors telling the truth.

Q64. How do bundlers resolve module specifiers — what are the "main", "module", and "exports" fields for?

ROI: ★★★☆☆ Frequency: Medium

Short Answer

"main" points to the legacy CommonJS entry point (used by Node and older tools). "module" is a community convention (not in the Node spec) pointing bundlers to an ESM build so they can tree-shake. "exports" is the modern, standardized field that lets a package precisely declare which entry points are public, and can map different files per environment (Node vs browser, ESM vs CJS, dev vs prod) — and, unlike the other two, it also restricts deep imports that aren't explicitly listed.

Detailed Answer

Resolution order/priority is tool-specific, but the general idea: a bundler targeting the browser prefers an ESM build (via "exports"'s "import" condition, or the older "module" field) for tree-shaking, while Node itself (and tools resolving CJS consumers) uses "main" or the "require" condition inside "exports". "exports" taking precedence over both is why some older tooling that doesn't understand it can fail to resolve packages that only define "exports".

Code Example

{
  "name": "my-lib",
  "main": "./dist/index.cjs.js",
  "module": "./dist/index.esm.js",
  "exports": {
    ".": {
      "import": "./dist/index.esm.js",
      "require": "./dist/index.cjs.js"
    },
    "./styles.css": "./dist/styles.css"
  }
}

Senior Engineer Perspective

A common real-world pain point: "why does deep-importing my-lib/dist/utils suddenly break after upgrading a dependency?" — because the package added an "exports" field that only allows the listed subpaths, closing off previously-working (but unofficial) deep imports.

Q65. What is code-splitting, and how does React.lazy tie into dynamic imports?

ROI: ★★★★☆ Frequency: High

Short Answer

Code-splitting is dividing a bundle into multiple smaller chunks that load on demand instead of all upfront, reducing the initial download/parse cost. React.lazy(() => import(...)) is React's built-in way to mark a component as a split point: the bundler emits it as a separate chunk, and React coordinates loading it with Suspense, showing a fallback until the chunk resolves.

Detailed Answer

Under the hood, React.lazy takes a function returning a dynamic import() promise; when React first needs to render that component and the promise hasn't resolved yet, it "suspends," walking up to find the nearest Suspense boundary to show its fallback, then re-renders the real component once the promise resolves. This is the same underlying mechanism (dynamic import + bundler chunking) as Q61, applied specifically as a first-class React API.

Code Example

const Settings = React.lazy(() => import("./Settings"));
const Reports = React.lazy(() => import("./Reports"));

function App({ route }) {
  return (
    <React.Suspense fallback={<Spinner />}>
      {route === "settings" ? <Settings /> : <Reports />}
    </React.Suspense>
  );
}

Senior Engineer Perspective

Mention prefetching as the natural follow-up optimization: triggering import("./Settings") on hover/focus of a nav link before the user actually clicks, so the chunk is already in flight (or cached) by the time React.lazy needs it, hiding the network latency.

Q66. What happens when you import a CommonJS module from an ESM file (interop)?

ROI: ★★★★☆ Frequency: High

Short Answer

Node and bundlers apply an interop shim: module.exports from the CJS module is generally treated as the ESM default export, and, where the tool can statically analyze the CJS module's shape, its named properties are synthesized as named exports too. This works well for simple, static module.exports = { a, b } shapes but can fail or behave inconsistently for dynamically-built exports objects.

Detailed Answer

This interop is a major source of "why is this import undefined" bugs when mixing ecosystems — for example, some CJS packages export a function as module.exports = fn with properties attached to it (fn.helper = ...), and depending on the tool/interop mode, import fn, { helper } from "pkg" may or may not correctly pick up helper as a named export. The safe fallback that always works is importing the whole thing as a default/namespace and accessing properties off it manually: import pkg from "pkg"; pkg.helper().

Code Example

// cjs-lib.js (CommonJS)
function core() { return "core"; }
core.helper = () => "helper";
module.exports = core;

// esm-consumer.mjs
import core from "cjs-lib";       // usually works — default export interop
core.helper();                     // may or may not be picked up as named,
                                    // depending on the bundler's CJS interop
// Safer / always-correct fallback:
import * as cjsLib from "cjs-lib";
cjsLib.default.helper();

Senior Engineer Perspective

If you've hit a real "named import is undefined" bug caused by CJS/ESM interop, describe it — it is one of the most common real build-tooling issues in mixed codebases, and knowing the default-export fallback as a guaranteed workaround is genuinely useful day-to-day knowledge.

SECTION 10 - ERROR HANDLING PATTERNS

Q67. How does try/catch/finally control flow work, especially with a return inside finally?

ROI: ★★★★☆ Frequency: High

Short Answer

finally always runs — whether the try block completed normally, threw, or hit a return/break/continue. Critically, if finally itself contains a return (or throws), it overrides whatever the try/catch was about to do — including swallowing a pending exception or replacing a pending return value.

Detailed Answer

This override behavior is a common source of subtle bugs: a return in finally silently discards an exception that was in the process of propagating out of the catch (or even out of the try, if there was no catch), and there is no way for the caller to ever see that original error. The rule of thumb: never return from a finally block — use it purely for cleanup (releasing resources, clearing timers), not for control flow.

Code Example

function example() {
  try {
    throw new Error("original");
  } finally {
    return "overridden"; // swallows the error entirely — no rethrow happens
  }
}
example(); // "overridden" — the Error is silently lost, never thrown

function example2() {
  try {
    return "from try";
  } finally {
    console.log("cleanup"); // runs, but does NOT override since no return here
  }
}
example2(); // "from try" — finally's side effect doesn't change the result

Senior Engineer Perspective

Interviewers use this to check whether you truly understand completion semantics versus just knowing "finally always runs." State plainly: "a return/throw in finally overrides the try/catch outcome" and that this is exactly why finally should be reserved for cleanup only.

Q68. How do you create a custom Error subclass, and why does extending Error correctly matter?

ROI: ★★★★★ Frequency: Extremely High

Short Answer

Extend the built-in Error class, call super(message) to set up the standard message/stack properties, and set this.name to your subclass name. This gives you a distinct error type you can check with instanceof, carry structured extra data on, and still have it behave like a real Error (correct stack trace, works with logging tools that expect Error shape).

Detailed Answer

Historically, subclassing built-ins like Error transpiled through Babel's older ES5 target could break instanceof checks, because the compiled output didn't correctly set up the prototype chain for native classes. Modern tooling targeting real ES6 classes (or with the fix applied) handles this correctly, but it is worth knowing as a historical gotcha if you ever see instanceof MyError failing unexpectedly on an older build pipeline.

Code Example

class ValidationError extends Error {
  constructor(message, field) {
    super(message);
    this.name = "ValidationError";
    this.field = field;
    // Captures a clean stack trace starting from here (V8-specific, optional)
    if (Error.captureStackTrace) Error.captureStackTrace(this, ValidationError);
  }
}

function validateAge(age) {
  if (age < 0) throw new ValidationError("Age cannot be negative", "age");
}

try {
  validateAge(-1);
} catch (err) {
  if (err instanceof ValidationError) {
    console.log(err.field, err.message); // "age" "Age cannot be negative"
  }
}

Senior Engineer Perspective

Interviewers want to see structured, typed errors carrying context (a field, an HTTP status, an error code) rather than throwing bare strings or generic Error instances everywhere — this is what makes centralized error handling (a single top-level catch that branches on error type) tractable.

Q69. What is the difference between operational errors and programmer errors?

ROI: ★★★★☆ Frequency: High

Short Answer

Operational errors are expected runtime failures in a correctly-written program — a network request failing, invalid user input, a file not found. They should be caught and handled gracefully (retry, show a message, fall back). Programmer errors are bugs — calling a function with the wrong type, a typo, a broken invariant. They generally should NOT be caught and silently continued; the program is in an unknown state, and the right response is usually to fail loudly (or crash/restart, in a server context) so the bug gets fixed.

Detailed Answer

Conflating the two is a common anti-pattern: wrapping large swaths of code in try/catch and silently swallowing everything "just in case" hides real bugs and makes them far harder to diagnose later, because the program keeps running in a corrupted state instead of surfacing the problem immediately. The healthier pattern is to catch specifically the operational errors you anticipate (by type or code) and let genuinely unexpected errors propagate to a top-level handler (an error boundary in React, a global process.on('uncaughtException') in Node) that logs and fails safely.

Code Example

async function fetchUser(id) {
  if (typeof id !== "number") {
    throw new TypeError("id must be a number"); // programmer error — a real bug
  }
  const res = await fetch(`/api/users/${id}`);
  if (!res.ok) {
    throw new ApiError(`User fetch failed: ${res.status}`); // operational — expected
  }
  return res.json();
}

try {
  await fetchUser(id);
} catch (err) {
  if (err instanceof ApiError) {
    showToast("Could not load user, please retry.");
  } else {
    throw err; // programmer error — don't swallow it, let it surface
  }
}

Senior Engineer Perspective

This distinction (popularized in Node.js error-handling guidance) is a strong differentiator — most candidates just say "wrap it in try/catch." A senior engineer explains WHICH errors deserve to be caught-and-handled versus caught-and-rethrown (or not caught at all), tying it to actual production incident response.

Q70. How does error handling differ between synchronous code, promises, and async/await?

ROI: ★★★★★ Frequency: Extremely High

Short Answer

Synchronous errors are caught with a regular try/catch wrapping the call. Promise rejections are handled with .catch() (or the second argument to .then), and an uncaught rejection does not crash synchronously — it fires an unhandledrejection event later. async/await lets you catch promise rejections using ordinary try/catch syntax, because await re-throws a rejected promise's reason at the await point.

Detailed Answer

The unifying insight: await converts an asynchronous rejection into something that behaves exactly like a synchronous throw at that line, which is why try/catch "just works" around await calls. The common mistake is mixing styles incorrectly — wrapping an async function call in try/catch but forgetting to await it, so the try/catch's stack frame has already exited by the time the promise rejects, and the error escapes as an unhandled rejection instead of being caught.

Code Example

// Sync
try {
  JSON.parse("not json"); // throws synchronously
} catch (e) { console.log("caught sync:", e.message); }

// Promise
fetchData().catch((e) => console.log("caught promise:", e.message));

// async/await
async function run() {
  try {
    await fetchData(); // rejection becomes a synchronous-style throw here
  } catch (e) {
    console.log("caught async:", e.message);
  }
}

// THE TRAP — missing await means try/catch can't see the rejection:
async function broken() {
  try {
    fetchData(); // no await! rejection escapes as unhandled
  } catch (e) {
    console.log("never runs for the async failure");
  }
}

Senior Engineer Perspective

The missing-await-inside-try/catch trap is extremely common in real code review. Say it explicitly: "try/catch can only catch a promise rejection if you await it (or return it) inside the try block — otherwise the promise rejects independently, after the function has already moved on."

Q71. What happens to an unhandled promise rejection, and how do you catch it globally?

ROI: ★★★★☆ Frequency: High

Short Answer

If a promise rejects and nothing ever attaches a .catch (or an awaiting try/catch) to it, the runtime eventually fires a global unhandledrejection event (browser) or 'unhandledRejection' event (Node), typically also logging a warning to the console. It does not crash a browser tab, but in Node, depending on version/config, it may terminate the process.

Detailed Answer

This is the promise equivalent of a global window.onerror handler for synchronous exceptions, and it is the right last line of defense for logging/reporting errors that slipped through application-level handling — but it should never be the primary error-handling strategy; it exists to catch bugs, not to replace intentional .catch calls at the call sites that know how to recover.

Code Example

// Browser
window.addEventListener("unhandledrejection", (event) => {
  console.error("Unhandled rejection:", event.reason);
  reportToMonitoring(event.reason);
  event.preventDefault(); // optional: suppress the default console warning
});

// Node.js
process.on("unhandledRejection", (reason, promise) => {
  console.error("Unhandled rejection at:", promise, "reason:", reason);
});

// This rejection is never caught anywhere -> triggers the handler above
Promise.reject(new Error("oops"));

Senior Engineer Perspective

Mention that this global handler is where you'd wire up production error monitoring (Sentry, Datadog) as a safety net — but the interview signal is understanding it's a last resort, not a substitute for handling errors close to where they can meaningfully be recovered from.

Q72. How do you handle errors differently with Promise.all vs Promise.allSettled?

ROI: ★★★★☆ Frequency: High

Short Answer

Promise.all rejects as soon as any single promise rejects, discarding the results of the others (even ones that later succeed) — you get exactly one error to handle. Promise.allSettled never rejects; it resolves with a result for every input, each tagged fulfilled or rejected, so you must inspect each entry individually to separate successes from failures.

Detailed Answer

Choosing between them is an error-handling design decision, not just a syntax choice: use all when a partial result is meaningless (e.g., a form submission with three dependent writes — if one fails, you want to know immediately and treat the whole operation as failed). Use allSettled when independent, partial success is useful (loading several unrelated widgets where one failure shouldn't block the others from rendering).

Code Example

// Promise.all — one failure aborts the whole batch
try {
  const [a, b, c] = await Promise.all([taskA(), taskB(), taskC()]);
} catch (err) {
  console.error("at least one task failed:", err); // only the FIRST rejection
}

// Promise.allSettled — inspect each result independently
const results = await Promise.allSettled([taskA(), taskB(), taskC()]);
const succeeded = results.filter((r) => r.status === "fulfilled").map(r => r.value);
const failed = results.filter((r) => r.status === "rejected").map(r => r.reason);

Senior Engineer Perspective

A sharp point to raise unprompted: with Promise.all, the OTHER promises that were still in flight are not cancelled just because one rejected — they keep running in the background (and their eventual rejections, if unhandled elsewhere, can themselves become unhandled rejections you need to account for).

Q73. What is the error boundary pattern in React, and why can't hooks or try/catch handle render errors?

ROI: ★★★★★ Frequency: Extremely High

Short Answer

An error boundary is a class component implementing static getDerivedStateFromError and/or componentDidCatch, which catches JavaScript errors thrown anywhere in its child component tree during rendering, in lifecycle methods, and in constructors — and renders a fallback UI instead of unmounting the whole app. There is no hook equivalent (as of current React versions) because error boundaries need to intercept errors thrown by React's own rendering machinery as it works through the tree, not errors inside your own function body, which try/catch can't reach into.

Detailed Answer

Wrapping a component's own render logic in a manual try/catch only protects that specific synchronous code path in your own function — it cannot catch an error thrown by a child component several levels down, because by the time your code runs, React's own tree-walking is what's actually invoking child renders, outside your try block's scope. Error boundaries also do NOT catch errors in event handlers (those need a plain try/catch at the handler), asynchronous code (a setTimeout callback or a rejected promise), server-side rendering, or errors thrown in the boundary itself.

Code Example

class ErrorBoundary extends React.Component {
  state = { hasError: false };
  static getDerivedStateFromError(error) {
    return { hasError: true };
  }
  componentDidCatch(error, info) {
    logErrorToService(error, info.componentStack);
  }
  render() {
    if (this.state.hasError) return <h2>Something went wrong.</h2>;
    return this.props.children;
  }
}

function App() {
  return (
    <ErrorBoundary>
      <Dashboard />
    </ErrorBoundary>
  );
}

// Event handlers still need their own try/catch — boundaries don't cover this:
function Button() {
  const onClick = () => {
    try {
      riskyOperation();
    } catch (err) {
      console.error(err); // must handle here; boundary won't see it
    }
  };
  return <button onClick={onClick}>Click</button>;
}

Senior Engineer Perspective

Precisely listing what error boundaries do NOT catch (event handlers, async code, SSR, errors in the boundary itself) is the differentiator — most candidates only know the happy path. Mention react-error-boundary as the common library wrapper that adds a useErrorHandler-style escape hatch for manually reporting async errors into the nearest boundary.

Q74. How does the Error.cause property (ES2022) help with error chaining?

ROI: ★★★☆☆ Frequency: Medium

Short Answer

new Error(message, { cause }) lets you attach the original lower-level error as the new error's .cause, preserving the full failure chain when you wrap/re-throw a more specific or user-friendly error on top of a lower-level one — instead of losing the original stack trace and message.

Detailed Answer

Before cause existed, wrapping errors (e.g., turning a raw network error into a domain-specific OrderProcessingError) meant either losing the original error entirely or inventing ad-hoc conventions (a custom .originalError property) to preserve it. cause standardizes this, and modern logging/monitoring tools understand it natively, printing the full chain when they format an uncaught error.

Code Example

async function processOrder(orderId) {
  try {
    await chargeCard(orderId);
  } catch (err) {
    throw new Error(`Failed to process order ${orderId}`, { cause: err });
  }
}

try {
  await processOrder(42);
} catch (err) {
  console.log(err.message);       // "Failed to process order 42"
  console.log(err.cause.message); // the original low-level error's message
}

Senior Engineer Perspective

Mention that this matters most in layered architectures (data layer → service layer → UI layer) where each layer wants to throw a meaningful error for its own context without discarding the root cause needed for debugging — cause gives you both without custom plumbing.

Q75. What are common mistakes when catching errors inside async functions?

ROI: ★★★★☆ Frequency: High

Short Answer

The most common: forgetting to await a promise inside a try block, so its eventual rejection happens after the try/catch has already exited and is never caught there. Others: catching too broadly and swallowing programmer errors alongside expected ones; forgetting that a `.forEach` callback that is itself `async` does not make the outer `forEach` wait, so errors inside it become unhandled rejections; and re-throwing without preserving the original error/cause.

Detailed Answer

The forEach-with-async-callback trap deserves special attention: array.forEach(async (item) => { await doWork(item); }) fires all the async callbacks essentially in parallel and immediately returns — forEach itself does not await anything, has no way to, and doesn't propagate any of the callbacks' rejections to a surrounding try/catch. Use a plain for...of loop with await (for sequential) or Promise.all(array.map(...)) (for parallel) instead.

Code Example

// MISTAKE 1 — missing await, rejection escapes the try/catch
async function bad1() {
  try {
    doAsyncWork(); // no await — rejection is not caught here
  } catch (e) { /* never runs for doAsyncWork's failure */ }
}

// MISTAKE 2 — forEach with an async callback doesn't wait or propagate errors
async function bad2(items) {
  try {
    items.forEach(async (item) => { await process(item); }); // fire-and-forget
  } catch (e) { /* never sees errors from `process` */ }
}

// CORRECT — sequential
async function good1(items) {
  for (const item of items) {
    await process(item); // errors propagate normally to the surrounding try
  }
}

// CORRECT — parallel, still catchable
async function good2(items) {
  try {
    await Promise.all(items.map((item) => process(item)));
  } catch (e) { console.error("a process() call failed:", e); }
}

Senior Engineer Perspective

The forEach + async trap is one of the most common real bugs in production JS/TS codebases — code review catches this constantly. Naming it unprompted, with the for...of or Promise.all(map(...)) fix, is a strong, concrete signal of real-world experience.

Q76. How would you design a Result/Either-style pattern to avoid throwing in hot paths?

ROI: ★★★☆☆ Frequency: Medium

Short Answer

Instead of throwing, a function returns a tagged union object representing either success or failure — e.g., { ok: true, value } or { ok: false, error } — forcing callers to explicitly branch on the outcome rather than relying on exception propagation. This avoids the (comparatively higher) cost and control-flow surprises of exceptions for expected, frequent "failure" cases, and makes the possible failure paths visible in a function's return type.

Detailed Answer

This pattern (borrowed from Rust's Result, Haskell's Either) is most valuable for validation-heavy or parsing-heavy code where "failure" is a completely normal, expected outcome, not an exceptional one — throwing for something that happens routinely makes call sites harder to reason about and, in tight loops, can carry real performance cost from stack unwinding. It composes well with TypeScript's discriminated unions, since the compiler forces you to narrow the type before accessing .value.

Code Example

function parseAge(input) {
  const n = Number(input);
  if (Number.isNaN(n) || n < 0) {
    return { ok: false, error: "Invalid age: " + input };
  }
  return { ok: true, value: n };
}

const result = parseAge("abc");
if (result.ok) {
  console.log(result.value);
} else {
  console.warn(result.error); // handled explicitly, no try/catch needed
}

// Composable helper
function mapResult(result, fn) {
  return result.ok ? { ok: true, value: fn(result.value) } : result;
}

Senior Engineer Perspective

Be balanced: this pattern adds verbosity and doesn't compose as automatically as exception propagation across many layers (you have to manually check and forward the failure at every level). It's a good fit for validation/parsing boundaries, not a wholesale replacement for exceptions everywhere in a codebase.

Q77. What is the difference between throwing and returning a rejected promise inside an async function?

ROI: ★★★☆☆ Frequency: Medium

Short Answer

They end up behaviorally equivalent from the caller's point of view: an async function always returns a promise, and both throw new Error() and return Promise.reject(new Error()) result in that returned promise being rejected with the given error. The difference is purely stylistic/mechanical — throw works naturally with try/catch inside the function body, while explicitly returning a rejected promise is more relevant in plain (non-async) functions that manually build a promise chain.

Detailed Answer

Inside an async function specifically, prefer throw — it is idiomatic, works with try/catch inside the function, and reads clearly. Manually returning Promise.reject(...) from within an async function is redundant and slightly unusual style, though not incorrect. The distinction matters more in a plain (non-async) function that returns a promise chain, where you don't have try/catch semantics and must explicitly return a rejected promise to signal failure through the chain.

Code Example

// Equivalent from the caller's perspective:
async function withThrow() {
  throw new Error("fail");
}
async function withReject() {
  return Promise.reject(new Error("fail"));
}

withThrow().catch((e) => console.log(e.message));  // "fail"
withReject().catch((e) => console.log(e.message)); // "fail"

// In a NON-async function, you must explicitly reject — there's no throw sugar:
function plainFn(ok) {
  if (!ok) return Promise.reject(new Error("not ok"));
  return Promise.resolve("done");
}

Senior Engineer Perspective

A sharp point: inside a plain .then() callback, a synchronous throw also becomes a rejection of the resulting promise (per Q23) — so the "must explicitly reject" rule really only applies at the top level of a non-async, non-promise-callback function.

Q78. Does a 404 or 500 HTTP response cause the fetch() promise to reject?

ROI: ★★★★★ Frequency: Extremely High

Short Answer

No. fetch() only rejects on genuine network failure (DNS failure, no connectivity, CORS block, request aborted) — it resolves normally for HTTP error statuses like 404 or 500, with response.ok set to false. You must explicitly check response.ok (or response.status) and throw yourself if you want error statuses to be treated as failures.

Detailed Answer

This is one of the most common real-world bugs with fetch: code that only wraps the call in try/catch (expecting HTTP errors to throw, the way many other HTTP client libraries like Axios do by default) silently treats a 500 error response as a "successful" response and tries to parse/use its body as if it were valid data. The fix is a small wrapper that checks ok and throws an appropriate error before returning.

Code Example

// BUG — treats every non-network-error response as success
async function getUserBuggy(id) {
  try {
    const res = await fetch(`/api/users/${id}`);
    return await res.json(); // runs even for a 404/500 body!
  } catch (e) {
    console.error(e); // only triggered by actual network failures
  }
}

// CORRECT — explicitly check status and throw
async function getUser(id) {
  const res = await fetch(`/api/users/${id}`);
  if (!res.ok) {
    throw new Error(`Request failed: ${res.status} ${res.statusText}`);
  }
  return res.json();
}

try {
  await getUser(999); // a real 404 now properly throws
} catch (e) {
  console.error(e.message); // "Request failed: 404 Not Found"
}

Senior Engineer Perspective

This is a nearly universal "gotcha" question for anyone who has shipped real fetch-based code. Stating it unprompted — "fetch only rejects on network failure, never on HTTP error status" — and showing the response.ok check is one of the highest-signal, lowest-effort answers in this whole chapter.

Q79. What are toSorted, toReversed, toSpliced, and with — and how do they differ from their mutating counterparts?

ROI: ★★★★☆ Frequency: High

Short Answer

These are ES2023 array methods that perform the same operation as sort, reverse, splice, and index assignment (arr[i] = x) — but return a new array instead of mutating the original. They exist specifically to give immutable equivalents of the classic mutating array methods, without needing to manually copy first ([...arr].sort()).

Detailed Answer

MutatingImmutable equivalent
sort()toSorted()
reverse()toReversed()
splice()toSpliced()
arr[i] = xarr.with(i, x)

Before these existed, the idiomatic immutable pattern was [...arr].sort(...) (spread to copy, then mutate the copy) — these methods make that pattern unnecessary and the intent clearer. Browser/runtime support is recent (2023+), so check your target environments before relying on them without a polyfill.

Code Example

const nums = [3, 1, 2];

const sorted = nums.toSorted();      // [1, 2, 3]
console.log(nums);                    // [3, 1, 2] — original untouched

const reversed = nums.toReversed();  // [2, 1, 3]
const spliced = nums.toSpliced(1, 1, 99); // [3, 99, 2] — replace at index 1
const updated = nums.with(0, 100);   // [100, 1, 2] — replace index 0

// React state update — no spread-then-mutate needed:
setItems((prev) => prev.toSorted((a, b) => a.value - b.value));

Senior Engineer Perspective

Knowing these exist (and that they're recent additions) shows you keep up with the language. The classic trap they fix: arr.sort() mutates AND returns the same array, so setItems(items.sort(...)) in React silently mutates state in place — items.toSorted(...) avoids that footgun entirely.

Q80. What does Object.freeze actually do, why is it only shallow, and how do you deep-freeze?

ROI: ★★★★☆ Frequency: High

Short Answer

Object.freeze(obj) prevents adding, removing, or reassigning own properties on obj, and marks them non-configurable/non-writable. It is shallow: if a property's value is itself an object, that nested object is NOT frozen and remains fully mutable. Deep-freezing requires recursively calling Object.freeze on every nested object yourself (or a utility that does it).

Detailed Answer

In non-strict mode, attempting to mutate a frozen object silently fails (no error, the assignment is just a no-op); in strict mode (including inside ES modules and classes, which are always strict), it throws a TypeError. Object.isFrozen(obj) checks the state. Because freezing is genuinely shallow, a common bug is assuming Object.freeze(state) makes an entire nested state tree immutable when only the top level is actually protected.

Code Example

"use strict";
const config = Object.freeze({ env: "prod", limits: { max: 10 } });

config.env = "dev";        // TypeError (strict mode) — top level IS frozen
config.limits.max = 999;   // works! — nested object is NOT frozen
console.log(config.limits.max); // 999

function deepFreeze(obj) {
  Object.getOwnPropertyNames(obj).forEach((key) => {
    const value = obj[key];
    if (value && typeof value === "object" && !Object.isFrozen(value)) {
      deepFreeze(value);
    }
  });
  return Object.freeze(obj);
}

const trulyFrozen = deepFreeze({ a: { b: { c: 1 } } });
// trulyFrozen.a.b.c = 2; // now throws in strict mode, at every level

Senior Engineer Perspective

The shallow-freeze gotcha is the whole question. Also mention the performance trade-off: deep-freezing every Redux/state object recursively on every update is expensive at scale, which is why most apps rely on convention (never mutate) plus tooling (Immer, ESLint rules) rather than runtime Object.freeze enforcement everywhere.

Q81. What are common pitfalls with the spread operator when copying objects/arrays?

ROI: ★★★★★ Frequency: Extremely High

Short Answer

Spread only copies one level deep (nested objects/arrays remain shared references), it copies only own enumerable properties (inherited/prototype properties and non-enumerable properties are dropped), and it converts accessor properties (getters/setters) into plain data properties on the copy, capturing the getter's current return value rather than preserving live getter/setter behavior.

Detailed Answer

Spreading a class instance also silently loses its prototype — {...instance} produces a plain object, not another instance of the class, so instanceof checks and class methods are gone from the copy. Spreading a Map or Set with object spread doesn't work at all the way you'd expect (they have no own enumerable properties to copy) — you need array spread over their iterator ([...map]) or new Map(map) instead.

Code Example

// 1. Shallow — nested objects still shared
const state = { user: { name: "A" } };
const copy = { ...state };
copy.user.name = "B";
console.log(state.user.name); // "B" — shared reference!

// 2. Getters become static snapshots
const obj = { get value() { return Math.random(); } };
const snap = { ...obj }; // `value` is now a plain number, not a live getter

// 3. Class instances lose their prototype
class Point { constructor(x) { this.x = x; } getX() { return this.x; } }
const p = new Point(5);
const plain = { ...p };
plain instanceof Point;   // false
// plain.getX();          // TypeError — getX doesn't exist on the plain copy

// 4. Map/Set need their own copy mechanism, not object spread
const m = new Map([["a", 1]]);
const mCopy = new Map(m); // correct — NOT { ...m }

Senior Engineer Perspective

The class-instance-losing-its-prototype pitfall is the one most candidates miss. It matters in practice whenever a codebase mixes classes (Date objects, custom domain classes, Map/Set) with naive spread-based "immutable update" helpers — those helpers silently downgrade rich objects to plain data.

Q82. How does structuredClone relate to immutability patterns compared to a library like Immer?

ROI: ★★★★☆ Frequency: High

Short Answer

structuredClone gives you a completely independent deep copy in one call, useful when you genuinely need to duplicate an entire structure. Immer takes the opposite approach: you write code that looks like direct mutation on a special "draft" proxy, and Immer computes a new, structurally-shared immutable value behind the scenes — reusing (not copying) any subtree you didn't touch.

Detailed Answer

The key difference is structural sharing: structuredClone duplicates everything, which is wasteful if you only changed one small nested field in a huge state tree, while Immer's produce only creates new objects along the path you actually mutated, keeping every untouched branch's reference identical to the original — which is exactly what React's memo/reference-equality optimizations need to keep working efficiently after an update.

Code Example

import { produce } from "immer";

const state = { user: { name: "A", settings: { theme: "dark" } }, count: 0 };

// Immer — write "mutating" code, get back an immutable result
const next = produce(state, (draft) => {
  draft.user.name = "B"; // looks like mutation, isn't
});

next !== state;                       // true — top level is new
next.user !== state.user;             // true — the changed path is new
next.user.settings === state.user.settings; // true — untouched branch REUSED
next.count === state.count;                 // same primitive value, of course

// structuredClone — everything is duplicated, nothing is shared
const cloned = structuredClone(state);
cloned.user.settings === state.user.settings; // false — fully independent copy

Senior Engineer Perspective

The structural-sharing distinction is the senior-level insight: Immer's real value isn't "mutation syntax," it's that it produces the minimal set of new references needed, which is precisely what makes memoized child components correctly skip re-rendering for branches that didn't change.

Q83. How does Immer's produce achieve mutable-looking immutable updates under the hood?

ROI: ★★★★☆ Frequency: High

Short Answer

produce(base, recipe) wraps base in a Proxy ("draft"). As your recipe function reads and writes properties on the draft, the Proxy's get/set traps intercept every access: reads are forwarded (and nested objects are lazily wrapped in their own draft proxies too), while writes are recorded rather than applied to the original — Immer builds a new object only for the branches that were actually written to, then freezes and returns that new tree, leaving base completely untouched.

Detailed Answer

This is a direct, practical application of the Proxy trap mechanism (covered in Section 12): the set trap is where Immer marks a path as "modified" and triggers copy-on-write for that path and all its ancestors up to the root, while any subtree the recipe never touched is returned by reference, unchanged. This is also why Immer requires either a genuine ES2015 Proxy environment or falls back to a slower ES5 mode using getters/setters on older engines that lack Proxy.

Code Example

// Conceptual sketch of what produce() does internally (simplified)
function produce(base, recipe) {
  const modified = new Set();
  const draft = new Proxy(base, {
    get(target, key) {
      const value = target[key];
      return (value && typeof value === "object")
        ? produce(value, () => {}) // wrap nested objects lazily (simplified)
        : value;
    },
    set(target, key, value) {
      modified.add(key);
      target[key] = value; // in real Immer, this writes to a COPY, not target
      return true;
    },
  });
  recipe(draft);
  return modified.size ? { ...base } : base; // simplified copy-on-write idea
}

Senior Engineer Perspective

Being able to sketch "it's a Proxy that records writes and does copy-on-write per path" — even in simplified pseudocode — demonstrates you understand both Proxy mechanics and why Immer is fast (only touched paths are copied) rather than treating it as a black box.

Q84. Object.assign vs spread for merging objects — what are the edge cases?

ROI: ★★★★☆ Frequency: High

Short Answer

Both perform a shallow merge of own enumerable properties, later sources overriding earlier ones, and both trigger getters on the source and create plain data properties on the result — functionally near-identical for object literals. The practical difference is syntax and mutation target: Object.assign(target, ...sources) mutates and returns target (so Object.assign({}, a, b) is the non-mutating form), while spread {...a, ...b} always produces a brand-new object and cannot accidentally mutate an existing one.

Detailed Answer

Both also share the same edge cases: symbol-keyed own properties ARE copied (a common misconception is that they aren't), non-enumerable properties are NOT copied, and neither performs a deep merge — a shared nested object property from a source simply overwrites the target's reference to a different nested object, it doesn't recursively merge the two. Spread is generally preferred in modern code for its safety (impossible to forget and mutate the first argument by accident, unlike a stray Object.assign(a, b) without an empty target).

Code Example

const target = { a: 1 };
const source = { b: 2 };

// Object.assign mutates its FIRST argument — easy to misuse:
Object.assign(target, source);
console.log(target); // { a: 1, b: 2 } — target itself was mutated!

// Spread never mutates an existing object:
const merged = { ...target, ...source }; // always a new object

// Neither deep-merges — nested objects are replaced, not combined:
const a = { user: { name: "A", age: 1 } };
const b = { user: { name: "B" } };
{ ...a, ...b }; // { user: { name: "B" } } — a.user.age is GONE, not merged

Senior Engineer Perspective

The "neither deep-merges" trap is the most valuable thing to volunteer — engineers frequently assume spreading two objects with a shared nested key merges the nested objects too, when really the second one completely replaces the first's.

Q85. What do Array.prototype.flat and flatMap do, and when do they replace nested reduce/map chains?

ROI: ★★★☆☆ Frequency: Medium

Short Answer

arr.flat(depth = 1) flattens nested arrays up to the given depth (use Infinity for fully flat) into a new array. arr.flatMap(fn) maps each element with fn and then flattens the result by exactly one level — equivalent to (but more efficient than) arr.map(fn).flat(), since it avoids building the intermediate un-flattened array.

Detailed Answer

flatMap is the clean tool whenever a mapping function can produce zero, one, or several results per input element — a pattern that otherwise tempts people into an awkward reduce that manually concatenates arrays. Returning an empty array from the callback effectively filters an element out, and returning a multi-element array expands it — giving you filter+map+flatten in a single readable pass.

Code Example

[[1, 2], [3, [4, 5]]].flat();        // [1, 2, 3, [4, 5]] — depth 1
[[1, 2], [3, [4, 5]]].flat(Infinity); // [1, 2, 3, 4, 5] — fully flat

// flatMap: expand each sentence into its words, in one pass
const sentences = ["hello world", "foo bar baz"];
sentences.flatMap((s) => s.split(" "));
// ["hello", "world", "foo", "bar", "baz"]

// flatMap as filter+map: drop invalid entries, transform valid ones
const raw = [1, -2, 3, -4];
raw.flatMap((n) => (n > 0 ? [n * 10] : [])); // [10, 30]

// Equivalent, less efficient (builds an intermediate nested array first):
raw.map((n) => (n > 0 ? [n * 10] : [])).flat();

Senior Engineer Perspective

Recognizing "map that sometimes returns nothing, sometimes returns multiple things" as a flatMap signature — instead of reaching for a manually-concatenating reduce — is exactly the kind of standard-library fluency interviewers reward.

Q86. How do Object.entries and Object.fromEntries let you transform objects functionally?

ROI: ★★★★☆ Frequency: High

Short Answer

Object.entries(obj) converts an object into an array of [key, value] pairs, letting you use all the array methods (map, filter, reduce) on an object's contents. Object.fromEntries(pairs) does the reverse, rebuilding an object from an array (or any iterable) of pairs — together they form a round-trip that makes "transform an object like you'd transform an array" possible without a manual accumulator.

Detailed Answer

This pattern is commonly used for renaming/filtering keys, transforming values, or converting between a Map and a plain object (Object.fromEntries(map) and, in reverse, new Map(Object.entries(obj))), replacing more verbose manual-accumulator reduce code with clearer map/filter chains.

Code Example

const prices = { apple: 1, banana: 2, cherry: 3 };

// Filter an object by value
const cheap = Object.fromEntries(
  Object.entries(prices).filter(([, price]) => price < 3)
); // { apple: 1, banana: 2 }

// Transform all values
const doubled = Object.fromEntries(
  Object.entries(prices).map(([key, value]) => [key, value * 2])
); // { apple: 2, banana: 4, cherry: 6 }

// Convert Map <-> plain object
const map = new Map(Object.entries(prices));
const backToObject = Object.fromEntries(map);

Senior Engineer Perspective

Show that you reach for entries/fromEntries + map/filter before writing a manual reduce accumulator for object transforms — it's clearer, and interviewers view unnecessary manual accumulation as a readability smell once the built-in exists.

Q87. What is the difference between find, findIndex, findLast, and findLastIndex?

ROI: ★★★☆☆ Frequency: Medium

Short Answer

find returns the first element matching a predicate (or undefined); findIndex returns its index (or -1). findLast/findLastIndex (ES2023) do the same but scan from the end, returning the last matching element/index — useful when you specifically want the most recent match without manually reversing the array first.

Detailed Answer

Before findLast existed, finding the last match required either [...arr].reverse().find(...) (wasteful — copies and fully reverses the array even if the match is near the end) or a manual backward loop. findLast scans directly from the end and stops at the first match, making it both clearer and more efficient.

Code Example

const users = [
  { id: 1, active: true },
  { id: 2, active: false },
  { id: 3, active: true },
];

users.find((u) => u.active);       // { id: 1, active: true }
users.findIndex((u) => u.active);  // 0
users.findLast((u) => u.active);      // { id: 3, active: true }
users.findLastIndex((u) => u.active); // 2

// Old way to get the last match — works but wasteful:
[...users].reverse().find((u) => u.active);

Senior Engineer Perspective

A minor but real signal: knowing findLast/findLastIndex exist (they're newer, ES2023) shows active engagement with the evolving standard library, versus defaulting to the reverse-then-find pattern out of habit.

Q88. Why does typeof fail to detect arrays, and how does Array.isArray solve it?

ROI: ★★★★☆ Frequency: High

Short Answer

typeof reports arrays as "object", indistinguishable from a plain object, a Map, a Date, or null's notorious "object" result — it only reflects the language's low-level type tag, not the specific constructor. Array.isArray(value) is the correct, reliable check: it specifically tests whether the value is a genuine Array exotic object, and unlike instanceof Array, it works correctly even across different realms (iframes, workers, vm contexts) where arrays created in one realm aren't instanceof the other realm's Array constructor.

Detailed Answer

The realm issue is a subtle but real production bug: an array passed from an <iframe> or a separate JS execution context has its own global Array constructor, so arr instanceof Array can be false for a perfectly genuine array from another realm, while Array.isArray(arr) still correctly returns true because it checks the internal array exotic-object tag directly, not the prototype chain against a specific constructor.

Code Example

typeof [];               // "object" — useless for detecting arrays
typeof {};                // "object" — same result, ambiguous
typeof null;               // "object" — the classic historical bug

Array.isArray([]);        // true
Array.isArray({});        // false
Array.isArray("string");  // false

// instanceof can fail across realms (e.g., an array from an iframe):
// iframeArray instanceof Array        -> may be false
// Array.isArray(iframeArray)          -> always true, correctly

Senior Engineer Perspective

The cross-realm nuance is what separates a memorized answer from a deep one — most candidates know Array.isArray exists but few know exactly why it's more robust than instanceof Array, or that this specifically matters when data crosses iframe/worker boundaries.

Q89. What are the pitfalls of comparing arrays/objects for equality, and how do libraries implement deep equality?

ROI: ★★★★☆ Frequency: High

Short Answer

=== and Object.is compare objects/arrays by reference identity, never by content — two arrays with identical elements are never === unless they're literally the same object in memory. Deep-equality libraries (lodash's isEqual, fast-deep-equal) instead recursively walk both structures, comparing primitive leaves by value and handling special cases (Dates, RegExps, Maps, Sets, circular references) explicitly.

Detailed Answer

A naive recursive deep-equal implementation must handle several edge cases correctly: different key counts/orders, values that are functions (usually treated as unequal unless identical reference, since function equality by "behavior" isn't decidable), circular references (needs a visited-pairs set to avoid infinite recursion), and type-specific comparisons for Date (compare timestamps), RegExp (compare source/flags), Map/Set (compare entries regardless of insertion order).

Code Example

[1, 2, 3] === [1, 2, 3]; // false — different array instances
{ a: 1 } === { a: 1 };    // false — different object instances

function isEqual(a, b, seen = new WeakMap()) {
  if (Object.is(a, b)) return true;
  if (typeof a !== "object" || typeof b !== "object" || !a || !b) return false;
  if (seen.get(a) === b) return true; // handles circular references
  seen.set(a, b);

  const keysA = Object.keys(a), keysB = Object.keys(b);
  if (keysA.length !== keysB.length) return false;
  return keysA.every((key) =>
    Object.prototype.hasOwnProperty.call(b, key) && isEqual(a[key], b[key], seen)
  );
}

isEqual({ a: [1, 2] }, { a: [1, 2] }); // true

Senior Engineer Perspective

Tie this back to React directly: this is exactly why React.memo's default shallow comparison (and useMemo/useEffect dependency arrays using Object.is) won't detect that two content-identical objects are "the same" — either keep references stable, or pass an explicit deep-equality comparator, which itself has a real runtime cost proportional to structure size.

Q90. How do you safely and efficiently remove a property from an object immutably?

ROI: ★★★★☆ Frequency: High

Short Answer

The idiomatic immutable-delete pattern is object destructuring with a rest pattern: const { keyToRemove, ...rest } = obj gives you rest as a brand-new object with every property except keyToRemove, without mutating obj. The mutating alternative, delete obj.key, changes the object in place and should be avoided on React state or any shared/frozen object.

Detailed Answer

The destructuring-rest approach is O(n) in the number of own properties (it must copy all the others), which is fine for typical object sizes but worth knowing if you're doing this in a hot loop over very wide objects. Also note: this removes an own enumerable property; if the key doesn't exist, it's simply a no-op copy — no error is thrown either way.

Code Example

const state = { id: 1, name: "A", temp: "delete me" };

// Immutable removal — new object, original untouched
const { temp, ...rest } = state;
console.log(rest);   // { id: 1, name: "A" }
console.log(state);  // unchanged: { id: 1, name: "A", temp: "delete me" }

// React reducer example
function reducer(state, action) {
  switch (action.type) {
    case "REMOVE_FIELD": {
      const { [action.key]: _removed, ...next } = state;
      return next;
    }
    default: return state;
  }
}

// Mutating alternative — AVOID on shared/React state:
delete state.temp; // mutates in place, breaks reference-equality checks

Senior Engineer Perspective

Mention the dynamic-key variant (const { [dynamicKey]: _, ...rest } = obj) since interviewers sometimes specifically ask how to do this when the key to remove isn't known statically — and reiterate why delete is dangerous specifically on anything React uses for reference-equality bailouts.

Q91. What are the core regex flags (g, i, m, s, u, y) and what does each change?

ROI: ★★★★☆ Frequency: High

Short Answer

g (global) finds all matches instead of stopping at the first. i makes matching case-insensitive. m (multiline) makes ^/$ match at the start/end of each line rather than only the whole string. s (dotAll) makes . also match newline characters. u enables full Unicode-aware matching (correct handling of surrogate pairs / code points beyond the BMP). y (sticky) anchors matching to start exactly at lastIndex, with no scanning forward.

Detailed Answer

The g and y flags both make the regex stateful — the object tracks a lastIndex property between calls to exec/test, which is a common source of bugs when the same regex literal is reused (or accidentally shared) across multiple unrelated calls without resetting lastIndex. The u flag matters whenever you match against strings that may contain characters outside the Basic Multilingual Plane (many emoji, some scripts) — without it, a surrogate pair can be incorrectly split and matched as two separate characters.

Code Example

"Cat cat CAT".match(/cat/gi);       // ["Cat", "cat", "CAT"]

const multiline = "line1\nline2";
multiline.match(/^line/gm);         // ["line", "line"] — matches per-line start

"a\nb".match(/a.b/s);                // matches — `s` lets . cross newlines

// Unicode: without `u`, an emoji (surrogate pair) can mismatch length checks
[..."😀"].length;                    // 1 — spread is Unicode-aware
"😀".length;                          // 2 — UTF-16 code units, not "characters"
/^.$/u.test("😀");                   // true — `u` treats it as one character
/^.$/.test("😀");                    // false — without `u`, sees 2 units

Senior Engineer Perspective

The stateful lastIndex gotcha with g/y is the trap interviewers love: reusing a global regex literal across calls to .test() in a loop can alternate between true/false unexpectedly because each call advances lastIndex. Always create a fresh regex (or reset lastIndex = 0) when reusing a global-flagged pattern.

Q92. What is the difference between test, exec, match, matchAll, and replace/replaceAll with regex?

ROI: ★★★★☆ Frequency: High

Short Answer

regex.test(str) returns a boolean. regex.exec(str) returns the next match's details (with capture groups) and, for global regexes, advances lastIndex so repeated calls step through all matches. str.match(regex) returns either the first match's details (no g flag) or a plain array of all matched substrings without capture-group detail (with g). str.matchAll(regex) (requires g) returns an iterator of full match-detail objects for every match, including capture groups. replace/replaceAll substitute matched text, optionally using a callback.

Detailed Answer

The most common source of confusion is that match with the g flag throws away capture-group data, only returning matched substrings — if you need both "all matches" and their capture groups, matchAll is the correct tool, not match. replace (without g) only replaces the first occurrence with a string pattern; replaceAll (ES2021) replaces every occurrence with a plain string, while replace with a g-flagged regex also replaces every occurrence.

Code Example

const re = /(\w+)@(\w+)/g;
const text = "a@x b@y";

re.test(text);          // true (boolean only)

// match with `g` loses capture groups — just matched substrings:
text.match(re);         // ["a@x", "b@y"]

// matchAll keeps full detail, including groups, per match:
[...text.matchAll(re)].map((m) => m[1]); // ["a", "b"] — the username groups

// replace with a callback function
text.replace(/(\w+)@(\w+)/g, (full, user, domain) => `${user}[at]${domain}`);
// "a[at]x b[at]y"

"a-b-c".replaceAll("-", "_"); // "a_b_c" — plain string, all occurrences

Senior Engineer Perspective

Precisely explaining why match with the global flag drops capture groups (and reaching for matchAll instead) is the detail that separates "has used regex" from "understands the API surface deeply."

Q93. How do capture groups and named capture groups work, and how do you reference them in a replacement?

ROI: ★★★★☆ Frequency: High

Short Answer

Parentheses (...) create a numbered capture group, accessible via match[1], match[2], etc., or as $1, $2 in a string replacement. Named groups, (?<name>...), let you access the same captured text by a readable name via match.groups.name, or $<name> in a replacement string — far more maintainable than tracking numeric positions as a pattern grows.

Detailed Answer

Named groups shine especially when parsing structured text (dates, log lines, URLs) where numeric indices become fragile the moment someone reorders or adds a group — renaming/reordering doesn't break code that references groups by name. Named groups are also available inside the pattern itself via a backreference, \k<name>, to match the same text again later in the same pattern.

Code Example

// Numbered groups
const m1 = "2026-08-17".match(/(\d{4})-(\d{2})-(\d{2})/);
m1[1]; // "2026" (year)
m1[2]; // "08" (month)

// Named groups — clearer and reorder-safe
const re = /(?<year>\d{4})-(?<month>\d{2})-(?<day>\d{2})/;
const m2 = "2026-08-17".match(re);
m2.groups.year;  // "2026"
m2.groups.month; // "08"

// Using named groups in a replacement
"2026-08-17".replace(re, "$<day>/$<month>/$<year>"); // "17/08/2026"

// Backreference to a named group within the same pattern
/(?<tag>\w+)=\k<tag>/.test("x=x"); // true — same value repeated

Senior Engineer Perspective

Recommend named groups by default for any pattern with more than one or two capture groups in real (non-throwaway) code — the maintainability win is significant, and most senior engineers reach for them automatically once a pattern needs to be read again six months later.

Q94. What is a non-capturing group, and when would you use one?

ROI: ★★★☆☆ Frequency: Medium

Short Answer

(?:...) groups a sub-pattern for applying a quantifier or alternation without creating a numbered capture entry in the match result. Use it whenever you need grouping purely for precedence/repetition, not because you actually want to extract that piece of text later — it keeps capture-group numbering clean and avoids unnecessary memory/bookkeeping overhead in the regex engine.

Detailed Answer

A common case: matching an optional prefix (like "http://" or "https://") that you group only to apply ? to the whole alternation, but never actually need to reference afterward. Using a non-capturing group there keeps match[1] referring to the URL's real path component you actually care about, instead of accidentally shifting all your numbered groups by one.

Code Example

// Capturing (unwanted) — group 1 is the useless "http(s)://" bit
/(https?:\/\/)?(\w+\.\w+)/.exec("example.com")[2]; // still works, but numbering is fragile

// Non-capturing — only the part you care about is captured
const re = /(?:https?:\/\/)?(\w+\.\w+)/;
re.exec("https://example.com")[1]; // "example.com" — group 1 is clean

// Alternation grouped without capturing
/(?:cat|dog|bird)s?/.test("dogs"); // true

Senior Engineer Perspective

This is a small but telling detail — using non-capturing groups deliberately (rather than every parenthesis capturing by default) signals attention to regex hygiene, especially in patterns maintained by a team where numeric group drift is a real source of bugs.

Q95. What are lookahead and lookbehind assertions, and what's a practical use case?

ROI: ★★★★☆ Frequency: High

Short Answer

Lookahead ((?=...) positive, (?!...) negative) and lookbehind ((?<=...) positive, (?<!...) negative) assert that a pattern does or doesn't appear immediately after/before the current position — without consuming those characters as part of the match. This lets you match text conditioned on nearby context that you don't want included in the actual matched result.

Detailed Answer

A classic practical case is password strength validation: requiring at least one digit AND one uppercase letter anywhere in the string, in any order, using several lookaheads chained at the start of the pattern, each checking a condition without advancing the match position — something that's awkward to express without lookahead, since a normal pattern must match characters in a fixed left-to-right sequence.

Code Example

// Lookahead: match a number only if followed by "px" (without consuming "px")
"width: 24px".match(/\d+(?=px)/)[0]; // "24" — "px" isn't part of the match

// Negative lookahead: match "foo" NOT followed by "bar"
/foo(?!bar)/.test("foobaz"); // true
/foo(?!bar)/.test("foobar"); // false

// Lookbehind: match a number only if preceded by "$"
"$50".match(/(?<=\$)\d+/)[0]; // "50"

// Password validation via chained lookaheads (order-independent requirements)
const strong = /^(?=.*\d)(?=.*[A-Z])(?=.*[a-z]).{8,}$/;
strong.test("Passw0rd"); // true — has digit, uppercase, lowercase, length 8+

Senior Engineer Perspective

Being able to write the multi-lookahead password-validation pattern from memory is a genuinely common practical exercise. Also mention that lookbehind support, while now widespread, was added to engines later than lookahead — worth a quick compatibility check for very old target environments.

Q96. Why is naive regex input validation risky, and what is ReDoS (catastrophic backtracking)?

ROI: ★★★★☆ Frequency: High

Short Answer

Certain regex patterns — typically ones with nested or overlapping repetition, like (a+)+ or (a|a)* — can cause the backtracking engine to try an exponential number of ways to match a failing input, freezing the thread for seconds or minutes on a moderately long malicious string. This is a real denial-of-service vector (ReDoS) if user input is ever matched against such a pattern, especially on a server.

Detailed Answer

The danger comes from ambiguity: when a repeated group can match the same substring in multiple different ways, and the overall match ultimately fails, the backtracking engine explores combinatorially many partial matches before giving up. Mitigations: avoid nested quantifiers on the same characters, prefer possessive-like rewrites or atomic grouping where supported, impose a maximum input length before matching, use well-audited validation libraries instead of hand-rolled patterns for things like email, and consider linear-time regex engines (like RE2, which forgoes backtracking-dependent features such as backreferences) for untrusted input at scale.

Code Example

// DANGEROUS — nested quantifiers cause catastrophic backtracking
const evil = /^(a+)+$/;
// evil.test("a".repeat(30) + "!"); // can hang the process for a long time

// A famously risky "validate email" style pattern with nested repetition
// (illustrative only — real email regexes are usually more careful)
const riskyEmail = /^([a-zA-Z0-9]+)+@[a-zA-Z]+\.[a-zA-Z]+$/;

// Mitigation: cap input length before ever running a risky pattern
function safeTest(re, input, maxLen = 254) {
  if (input.length > maxLen) return false;
  return re.test(input);
}

Senior Engineer Perspective

ReDoS is a genuine, exploitable production vulnerability class (it has its own CVEs across major libraries), not academic trivia — mentioning length caps, avoiding nested quantifiers, and preferring vetted validation libraries over hand-written email/URL regexes shows security awareness beyond "regex works in my testing."

Q97. What is the Proxy object, and what are traps?

ROI: ★★★★★ Frequency: Extremely High

Short Answer

new Proxy(target, handler) creates a wrapper object that intercepts fundamental operations on target — property reads, writes, deletion, existence checks (in), enumeration, and more — by delegating each operation to a corresponding "trap" function defined on handler (get, set, deleteProperty, has, ownKeys, etc.), if provided; any trap you don't define falls through to the default behavior on target.

Detailed Answer

This makes Proxy the mechanism behind "reactive" object systems (Vue 3's reactivity, Immer's drafts — see Q83), validation layers, and API mocking/logging wrappers, because it lets you observe or intercept arbitrary property access without the consuming code needing to know it's talking to a wrapped object instead of the real thing — the Proxy is (mostly) transparent.

Code Example

const target = { name: "Ada", age: 30 };

const logged = new Proxy(target, {
  get(obj, prop) {
    console.log(`GET ${String(prop)}`);
    return obj[prop];
  },
  set(obj, prop, value) {
    console.log(`SET ${String(prop)} = ${value}`);
    obj[prop] = value;
    return true; // must return true to indicate success
  },
});

logged.name;         // logs "GET name", returns "Ada"
logged.age = 31;      // logs "SET age = 31"

Senior Engineer Perspective

Interviewers want to see you connect Proxy to something concrete — Vue 3's move from Object.defineProperty to Proxy-based reactivity (Q100), or Immer's draft mechanism (Q83) — rather than reciting the API in isolation.

Q98. How would you use a Proxy to implement validation or simple reactive-object behavior?

ROI: ★★★★☆ Frequency: High

Short Answer

Implement the set trap to validate an incoming value before allowing (or rejecting) the assignment, and/or to trigger side effects (like notifying subscribers) whenever a property changes — this is the core mechanism behind reactive state systems that let you write plain obj.prop = value and have the framework automatically know something changed.

Detailed Answer

A validating Proxy can throw (or return false, which throws a TypeError in strict mode) from set when a value fails a check, enforcing invariants at the point of mutation rather than scattering manual checks across every place that writes to the object. A reactive Proxy instead records which "effects" read which properties (during get) and re-runs exactly those effects when the corresponding property is later written (during set) — a simplified version of what Vue 3's reactivity and signal-based libraries do.

Code Example

// Validation proxy
function createValidated(target, rules) {
  return new Proxy(target, {
    set(obj, prop, value) {
      if (rules[prop] && !rules[prop](value)) {
        throw new TypeError(`Invalid value for ${String(prop)}: ${value}`);
      }
      obj[prop] = value;
      return true;
    },
  });
}
const user = createValidated({ age: 0 }, { age: (v) => typeof v === "number" && v >= 0 });
user.age = 25;      // OK
// user.age = -1;   // throws TypeError

// Minimal reactive object
function reactive(target, onChange) {
  return new Proxy(target, {
    set(obj, prop, value) {
      const changed = obj[prop] !== value;
      obj[prop] = value;
      if (changed) onChange(prop, value);
      return true;
    },
  });
}
const state = reactive({ count: 0 }, (prop, value) => console.log(`${prop} -> ${value}`));
state.count = 1; // logs "count -> 1"

Senior Engineer Perspective

Being able to build a minimal reactive object live in an interview — a `set` trap plus a subscriber callback — demonstrates real understanding rather than name-dropping "Vue uses Proxy." Mention the trade-off: Proxy-based reactivity can't observe destructured/detached primitive values, only property access through the proxy itself.

Q99. What is Reflect, and why does it usually pair with Proxy?

ROI: ★★★★☆ Frequency: High

Short Answer

Reflect is a built-in object providing the same set of fundamental operations as Proxy traps (Reflect.get, Reflect.set, Reflect.has, Reflect.deleteProperty, etc.) as plain functions instead of operators/syntax. Inside a Proxy trap, calling the matching Reflect method to forward the default behavior is the recommended way to fall through to "normal" behavior, correctly preserving the original this/receiver semantics — safer than manually reimplementing what the trap should default to.

Detailed Answer

The subtlety Reflect handles correctly is the "receiver" — when a trap's get is triggered via inheritance (an object whose prototype is the Proxy), Reflect.get(target, prop, receiver) ensures further prototype-chain lookups and any nested getters resolve this against the original receiver, not the raw target — manually writing target[prop] instead loses this correctness in inheritance scenarios.

Code Example

const handler = {
  get(target, prop, receiver) {
    console.log("accessing", prop);
    return Reflect.get(target, prop, receiver); // correct receiver forwarding
  },
  set(target, prop, value, receiver) {
    return Reflect.set(target, prop, value, receiver);
  },
};

const p = new Proxy({ x: 1 }, handler);
p.x; // logs "accessing x", returns 1

// Reflect also gives cleaner alternatives to old operator-based idioms:
Reflect.has(p, "x");          // like `"x" in p`, but as a function
Reflect.ownKeys(p);            // like Object.getOwnPropertyNames + symbols combined

Senior Engineer Perspective

Knowing specifically WHY Reflect.get(target, prop, receiver) is safer than target[prop] inside a trap (correct this binding through inheritance) — not just "you're supposed to use Reflect with Proxy" — is what separates surface familiarity from real understanding.

Q100. Proxy-based reactivity vs Object.defineProperty-based reactivity (Vue 3 vs Vue 2) — what changed and why?

ROI: ★★★★☆ Frequency: High

Short Answer

Vue 2 made objects reactive by walking every existing property at initialization time and replacing each with a getter/setter pair via Object.defineProperty — which meant properties added later, or array index/length changes, were invisible to the reactivity system unless routed through special APIs (Vue.set, wrapped array methods). Vue 3 wraps the whole object in a Proxy instead, whose get/set/deleteProperty/has traps intercept operations on ANY property — including ones added after the fact — with no special-casing needed.

Detailed Answer

The core limitation of Object.defineProperty is that it must be applied per-property, upfront — it cannot retroactively intercept a property that doesn't exist yet, nor can it observe array index assignment or length changes without wrapping the array's mutating methods individually. A Proxy, by contrast, intercepts at the object level: any property access — existing, newly added, or deleted — passes through the same trap, which is exactly why Vue 3 no longer needs the Vue.set/Vue.delete escape hatches Vue 2 required.

Code Example

// Vue-2-style: must know every property in advance
function defineReactive(obj, key) {
  let value = obj[key];
  Object.defineProperty(obj, key, {
    get() { track(); return value; },
    set(newVal) { value = newVal; trigger(); },
  });
}
const data = { a: 1 };
defineReactive(data, "a");
data.b = 2; // NOT reactive — was never wrapped, added after the fact

// Vue-3-style: any property, including future ones, is intercepted
function reactiveProxy(obj) {
  return new Proxy(obj, {
    get(target, key, receiver) { track(); return Reflect.get(target, key, receiver); },
    set(target, key, value, receiver) { const r = Reflect.set(target, key, value, receiver); trigger(); return r; },
  });
}

state.b = 2; // fully reactive — the Proxy intercepts the new property too

Q101. Can a Proxy trap implement negative array-index access (e.g., Python-style arr[-1])?

ROI: ★★★☆☆ Frequency: Medium

Short Answer

Yes — a get trap can inspect the requested property key, detect that it looks like a negative-number string (property keys are always strings or symbols, even for array access), and redirect it to the corresponding positive index counted from the end (length + n), falling through to normal behavior for every other key.

Detailed Answer

This works because arr[-1] is, under the hood, just a property access with the key "-1" — arrays don't have any special negative-index behavior built in, so a Proxy can freely reinterpret that specific key pattern while leaving every normal numeric/string/symbol key untouched via Reflect.get.

Code Example

function negativeIndexArray(arr) {
  return new Proxy(arr, {
    get(target, prop, receiver) {
      if (typeof prop === "string" && /^-\d+$/.test(prop)) {
        const index = target.length + Number(prop);
        return target[index];
      }
      return Reflect.get(target, prop, receiver);
    },
  });
}

const arr = negativeIndexArray([10, 20, 30]);
arr[-1]; // 30 — last element
arr[-2]; // 20
arr[0];  // 10 — normal access still works
arr.length; // 3 — normal properties/methods pass through untouched

Q102. What invariants must Proxy traps respect, and what happens if you violate one?

ROI: ★★★☆☆ Frequency: Medium

Short Answer

Proxy traps cannot lie about certain facts that JavaScript's object model guarantees must stay consistent — for example, a get trap can't report a different value than the target's actual value for a non-configurable, non-writable own property; a deleteProperty trap can't report success for a non-configurable property; and ownKeys must include every non-configurable own key of the target. Violating one of these throws a TypeError at the moment the operation is attempted, not at trap-definition time.

Detailed Answer

These invariants exist so that code relying on fundamental language guarantees (like "a non-configurable property can never actually be deleted") can trust those guarantees hold even when talking to an arbitrary Proxy, rather than needing every consumer to defensively re-verify basic object semantics. This is a deliberate design trade-off: it limits how "magical" a Proxy can be, in exchange for keeping the rest of the language's invariants sound.

Code Example

const target = {};
Object.defineProperty(target, "locked", {
  value: 42, writable: false, configurable: false,
});

const p = new Proxy(target, {
  get() { return 999; }, // lies about a non-configurable, non-writable prop
});

// p.locked; // throws TypeError: invariant violation — must report 42

Senior Engineer Perspective

Knowing that Proxy has hard limits — it cannot arbitrarily override every operation regardless of the target's actual property descriptors — shows you understand Proxy as a carefully-specified mechanism, not an unconstrained meta-programming hook.

Q103. How would you build a simple observable store for a React app using Proxy, without a state-management library?

ROI: ★★★★☆ Frequency: High

Short Answer

Wrap a plain state object in a Proxy whose set trap notifies a set of subscriber callbacks after every mutation; a custom hook subscribes a component to that store on mount, forces a re-render whenever notified, and unsubscribes on cleanup — giving you Proxy-based "reactive" global state with no external dependency.

Detailed Answer

This is a simplified illustration of the same idea used by real Proxy-based state libraries (like Valtio): the Proxy makes ordinary property mutation syntax (store.count++) automatically notify subscribers, and a useSyncExternalStore-based hook (React's official API for subscribing to external mutable state) bridges that notification into a React re-render, without needing to route every update through setState or a reducer dispatch.

Code Example

function createStore(initial) {
  const listeners = new Set();
  const state = new Proxy(initial, {
    set(target, prop, value, receiver) {
      const changed = target[prop] !== value;
      const result = Reflect.set(target, prop, value, receiver);
      if (changed) listeners.forEach((l) => l());
      return result;
    },
  });
  return {
    state,
    subscribe(listener) {
      listeners.add(listener);
      return () => listeners.delete(listener);
    },
  };
}

const store = createStore({ count: 0 });

function useStore() {
  return React.useSyncExternalStore(store.subscribe, () => store.state);
}

function Counter() {
  const state = useStore();
  return (
    <button onClick={() => { store.state.count++; }}>
      {state.count}
    </button>
  );
}

Senior Engineer Perspective

The senior-level detail is reaching for useSyncExternalStore specifically — it exists precisely to safely subscribe React components to external mutable state (like this Proxy store) with correct behavior under concurrent rendering, rather than hand-rolling a `forceUpdate`-style pattern that can tear under React 18's concurrent features.
