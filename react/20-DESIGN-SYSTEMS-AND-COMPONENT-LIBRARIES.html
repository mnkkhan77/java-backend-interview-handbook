SECTION 1 - FOUNDATIONS: SYSTEM THINKING & DESIGN TOKENS

Q1. What is a design system, and how does it differ from "just a component library"?

ROI: ★★★★★ Frequency: Very High

Short Answer

A component library is code: a package of Button, Modal, Select, and so on. A design system is bigger than that — it is the single source of truth that ties together design principles, design tokens (the atomic values), the component library that implements them, usage guidelines, accessibility standards, and the process/governance that keeps design and engineering in sync over time. The component library is the most visible artifact of a design system, but a design system without shared tokens, documentation, and governance is just a pile of components that will drift out of sync with the Figma files the moment either side changes independently.

Detailed Answer

Think of it in layers, roughly bottom-up:

  • Foundations / tokens — the raw design decisions: color palette, spacing scale, type scale, radii, shadows, motion durations. These are values, not components.
  • Components — the coded (and Figma-componentized) building blocks that consume those tokens: buttons, inputs, cards, modals.
  • Patterns — recipes built from components for recurring problems: a form layout, an empty state, a data table with pagination.
  • Guidelines & governance — when to use what, accessibility requirements, contribution process, versioning policy.

The "single source of truth" framing is the key interview phrase: without it, designers hand-pick colors in Figma while engineers hardcode slightly different hex values in CSS, and the two drift apart within a quarter. A design system's job is to make sure a color, a spacing value, or a component's behavior is defined once and consumed everywhere — by both disciplines.

Common Mistake

Candidates who answer "it's a Storybook full of buttons" are describing the component library, not the system. The stronger answer names all three legs — tokens, components, governance — and explicitly calls out that a design system is a process as much as a codebase: it has to survive the original authors leaving, new teams joining, and dozens of PRs a month without silently rotting. Bringing up Figma-to-code sync (tokens shared as Figma variables that map 1:1 onto the same tokens in code) is a strong signal of hands-on experience.

Q2. What are design tokens, and how do they flow from a design tool into shipped code?

ROI: ★★★★★ Frequency: Very High

Short Answer

Design tokens are named, platform-agnostic values — colors, spacing, font sizes, radii, shadows, durations — that encode a design decision as data instead of a hardcoded literal scattered across stylesheets. They typically live in a neutral format (JSON/YAML) that both a design tool (Figma variables) and a build pipeline (Style Dictionary, or a custom transform) can read, and a build step compiles them into platform-specific outputs: CSS custom properties for web, a JS/TS object for React Native, XML resources for Android, and so on. Change one token value once, rebuild, and every consuming surface updates.

Detailed Answer

Mature token systems use a tiered structure rather than one flat list, because it separates "what the raw value is" from "what it means":

  • Global / reference tokens — raw values with no semantic meaning: blue-500: #2563eb, space-4: 16px.
  • Alias / semantic tokens — reference tokens given a purpose: color-bg-primary: {blue-500}, color-text-danger: {red-600}. Components should only ever reference semantic tokens, never raw values, so that a global rebrand or a dark-mode swap only requires re-pointing aliases.
  • Component tokens — the most specific tier, scoped to one component: button-bg-primary: {color-bg-primary}. This lets a single component be re-themed without touching the rest of the system.

The pipeline typically looks like: Figma variables (source of design truth) → exported/synced into a token JSON file → a build tool like Style Dictionary reads that JSON and generates per-platform output files → those generated files (CSS variables, a TS const tokens object, iOS/Android resources) are imported by the actual components. This is what makes "change once, apply everywhere" real instead of aspirational — no engineer is hand-copying hex codes from a Figma inspector panel.

Code Example

// tokens/color.json — source of truth
{
  "color": {
    "blue": { "500": { "value": "#2563eb" } },
    "bg":   { "primary": { "value": "{color.blue.500.value}" } }
  }
}

// style-dictionary.config.js
module.exports = {
  source: ["tokens/**/*.json"],
  platforms: {
    css: {
      transformGroup: "css",
      buildPath: "build/css/",
      files: [{ destination: "tokens.css", format: "css/variables" }]
    },
    js: {
      transformGroup: "js",
      buildPath: "build/js/",
      files: [{ destination: "tokens.js", format: "javascript/es6" }]
    }
  }
};

// Generated build/css/tokens.css
:root {
  --color-blue-500: #2563eb;
  --color-bg-primary: var(--color-blue-500);
}

// Component consumes the semantic token, never the raw value
.button-primary {
  background: var(--color-bg-primary);
}

Interview Gold Point

Naming the three-tier model (global → alias/semantic → component) and explaining why the semantic tier exists — so a rebrand or theme swap is a one-line alias change, not a find-and-replace across hundreds of files — is what separates a senior answer from "tokens are just CSS variables." Mentioning Style Dictionary (or an equivalent transform pipeline) by name, and that Figma variables can be the actual upstream source, shows you've lived through keeping design and code in sync rather than just reading about it.

SECTION 2 - COMPONENT ARCHITECTURE & THEMING

Q3. How do you build composable, reusable components — compound components and slot patterns?

ROI: ★★★★★ Frequency: Very High

Short Answer

The core idea is to favor composition over configuration. Instead of one monolithic component that grows a new boolean prop for every layout variant (showIcon, iconPosition, hasFooter, footerAlign...), you expose a small family of subcomponents that share implicit state through React Context — a compound component — so the consumer controls layout and content directly with JSX, while the parent still owns the shared logic (state, keyboard handling, accessibility wiring). This is the same pattern native HTML uses: <select> and <option>, or <table>/<tr>/<td>.

Detailed Answer

A compound component works by having a parent create a piece of shared state (or a ref to imperative behavior) and pass it down via Context, so its children can read and update it without any prop drilling from the consumer's side. The consumer is free to reorder, omit, or wrap the children — the components only care that they're rendered somewhere inside the parent's provider.

The related slot pattern is simpler: instead of a rigid internal layout, a component accepts children (or named props like header/footer) as "holes" the consumer fills with arbitrary content — <Card><Card.Header>...</Card.Header><Card.Body>...</Card.Body></Card> — instead of a title: string prop that can never contain a badge or an icon next to it.

The payoff: a design-system component stays flexible for content-level customization (any JSX in the slots) while keeping the parts consumers must never get wrong — focus management, ARIA attributes, open/close state — centralized and untouchable.

Code Example

// A minimal compound component: Tabs
const TabsContext = React.createContext(null);

function Tabs({ defaultValue, children }) {
  const [value, setValue] = React.useState(defaultValue);
  return (
    <TabsContext.Provider value={{ value, setValue }}>
      <div className="tabs">{children}</div>
    </TabsContext.Provider>
  );
}

function TabList({ children }) {
  return <div role="tablist">{children}</div>;
}

function Tab({ value, children }) {
  const ctx = React.useContext(TabsContext);
  const selected = ctx.value === value;
  return (
    <button
      role="tab"
      aria-selected={selected}
      onClick={() => ctx.setValue(value)}
    >
      {children}
    </button>
  );
}

function TabPanel({ value, children }) {
  const ctx = React.useContext(TabsContext);
  if (ctx.value !== value) return null;
  return <div role="tabpanel">{children}</div>;
}

Tabs.List = TabList;
Tabs.Tab = Tab;
Tabs.Panel = TabPanel;

// Consumer composes freely — no giant config prop
<Tabs defaultValue="profile">
  <Tabs.List>
    <Tabs.Tab value="profile">Profile</Tabs.Tab>
    <Tabs.Tab value="billing">Billing</Tabs.Tab>
  </Tabs.List>
  <Tabs.Panel value="profile">...</Tabs.Panel>
  <Tabs.Panel value="billing">...</Tabs.Panel>
</Tabs>

Interview Gold Point

Name the failure mode explicitly: a component that started with three props ends up with thirty, each one interacting with the others in undocumented ways ("prop explosion"), until nobody can safely add a new layout variant. Compound components sidestep this because new layouts are expressed by rearranging JSX, not by adding another prop combination the maintainer has to test. Mentioning that this mirrors native HTML elements (<select>/<option>) grounds the pattern in something the interviewer already trusts.

Q4. Headless UI libraries (Radix, Headless UI) vs fully-styled libraries (MUI, Chakra) — what are the tradeoffs?

ROI: ★★★★☆ Frequency: High

Short Answer

Headless libraries (Radix Primitives, Headless UI, React Aria) ship behavior, state machines, and accessibility wiring — focus trapping, roving tabindex, correct ARIA attributes, keyboard interaction — with zero visual opinion, leaving 100% of the CSS to you. Fully-styled libraries (MUI, Chakra, Ant Design) ship both the behavior and a ready-made visual theme, so you get a usable UI immediately but inherit their design language, their theming API, and often a heavier bundle. The choice comes down to whether you are building a design system (headless is almost always right, because you don't want to fight someone else's opinionated CSS while building your own) or you need to ship a product fast with no dedicated design system investment (fully-styled wins).

Detailed Answer

Headless libraries solved a real, hard-won problem: building fully accessible interactive primitives (a combobox, a dialog, a menu with correct roving focus) from scratch is deceptively difficult and easy to get subtly wrong. Radix and similar libraries let a design system team stop reinventing that logic and instead spend their effort on the visual layer and the token system — the part that's actually differentiated for their product.

Fully-styled libraries are optimized for a different goal: get a consistent, decent-looking UI shipped with minimal effort. The cost shows up later — re-skinning MUI or Chakra to not look like MUI or Chakra takes real work, their theming APIs are large surface areas to learn, and you're coupled to their release cadence and any breaking changes in their internals.

Interview Favorite

The sharpest framing: "headless libraries let you own the design, fully-styled libraries let you borrow one." Interviewers like hearing that most serious in-house design systems today are built on top of a headless primitives library rather than from scratch — you get Radix's accessibility and interaction correctness for free and spend your actual engineering time on tokens, theming, and the visual layer that makes the product feel like your product, not somebody else's design system.

Q5. How do you support theming and dark mode in a component library?

ROI: ★★★★☆ Frequency: High

Short Answer

Theming should be implemented through the semantic token layer (see Q2), not hardcoded colors baked into individual components. Dark mode is then just an alternate value set for the same semantic tokens — color-bg-primary resolves to a light value in one theme and a dark value in the other — swapped globally by toggling a data-theme attribute (or class) on the document root, never by re-implementing every component per theme. Components should reference var(--color-bg-primary), never a raw hex code, so a theme switch is a single attribute flip that cascades through CSS with no re-render of component logic required.

Detailed Answer

Two theming needs typically coexist: pure CSS switching (fast, no JS re-render, works even before hydration) and a JS-aware theme value (needed when a component has to branch logic based on theme, or on non-web targets like React Native that have no CSS cascade). The CSS-variable approach handles the first; a lightweight ThemeProvider Context handles the second, and the two can read from the same underlying token source so they never disagree.

Practical details that come up in interviews:

  • Detect the user's OS preference with prefers-color-scheme, but let the user override it manually, persisting the choice (localStorage) so it survives reloads.
  • Set the theme attribute as early as possible (an inline script in <head>) to avoid a flash of the wrong theme on load.
  • Every component must be visually tested in both themes — this is exactly what Storybook + Chromatic (Q7, Q9) are for.
  • Never hardcode a color literal inside a component's stylesheet; if you can grep for a raw hex code in component CSS, dark mode support is incomplete.

Code Example

/* tokens.css — same variable names, different values per theme */
:root {
  --color-bg-primary: #ffffff;
  --color-text-primary: #111827;
}

[data-theme="dark"] {
  --color-bg-primary: #0b1120;
  --color-text-primary: #e5e7eb;
}

/* Component never hardcodes a color — only references the semantic token */
.card {
  background: var(--color-bg-primary);
  color: var(--color-text-primary);
}

// Toggling the theme — a single attribute flip, no component re-render needed
function setTheme(theme: "light" | "dark") {
  document.documentElement.setAttribute("data-theme", theme);
  localStorage.setItem("theme", theme);
}

// Respect OS preference on first load, then let the user override
const stored = localStorage.getItem("theme");
const preferred = window.matchMedia("(prefers-color-scheme: dark)").matches
  ? "dark"
  : "light";
setTheme(stored ?? preferred);

Common Mistake

A frequent trap is components that "support dark mode" by accepting a darkMode boolean prop and branching internally with conditional class names or inline styles — this duplicates every color decision per component and guarantees drift. The correct signal is: components should be completely unaware that theming exists; they just consume semantic CSS variables, and the theme is swapped entirely outside the component tree. Also worth mentioning: flash-of-wrong-theme is a real UX bug, fixed by setting the theme attribute synchronously before first paint, not in a useEffect.

Q6. Controlled vs uncontrolled components, and prop drilling vs composition — how do you design a good component API?

ROI: ★★★★★ Frequency: Very High

Short Answer

A controlled component has its state owned entirely by the consumer — it receives value and onChange and renders whatever it's told, which lets the consumer validate, sync with a form library, or drive the value from a URL/query param. An uncontrolled component manages its own internal state and simply notifies the consumer of changes via defaultValue and onChange, which is simpler for the common case but less flexible. A well-designed design-system component supports both by accepting an optional value/onChange pair that, when omitted, falls back to internal state — the same pattern native <input> elements use.

Detailed Answer

This dual support is usually implemented with a small shared hook — often called useControllableState — that checks whether value was passed. If it was, the hook treats the component as controlled and always renders the prop; if not, it manages its own useState and treats defaultValue as the seed. Either way it calls onChange so the consumer always finds out about changes, whether or not they're driving the state.

The second half of this question — prop drilling vs composition — connects directly back to Q3. When a compound component's subcomponents need to share state (an open/closed flag, a selected value), the naive approach threads that state down through props at every level, which gets unwieldy fast and breaks the moment a consumer reorders the tree. The composition-first fix is Context: the parent owns the state and provides it, and each subcomponent reads what it needs directly, with no prop drilling and no dependency on tree depth or ordering.

Other API design principles worth citing: give every prop a sensible default so the "happy path" needs the fewest props possible; expose an escape hatch for advanced consumers (Radix's asChild pattern lets a consumer render the component's behavior onto their own element instead of a hardcoded <button>); and resist boolean-prop explosion by preferring a small enum (variant: "primary" | "secondary" | "danger") over several independent booleans that can combine into invalid states.

Code Example

function useControllableState<T>({
  value,
  defaultValue,
  onChange,
}: {
  value?: T;
  defaultValue: T;
  onChange?: (next: T) => void;
}) {
  const [internal, setInternal] = React.useState(defaultValue);
  const isControlled = value !== undefined;
  const current = isControlled ? value : internal;

  const setValue = (next: T) => {
    if (!isControlled) setInternal(next);
    onChange?.(next);
  };

  return [current, setValue] as const;
}

// Works both ways for the consumer:
// Uncontrolled: <Switch defaultValue={false} onChange={log} />
// Controlled:   <Switch value={checked} onChange={setChecked} />
function Switch({ value, defaultValue = false, onChange }: SwitchProps) {
  const [checked, setChecked] = useControllableState({ value, defaultValue, onChange });
  return <button role="switch" aria-checked={checked} onClick={() => setChecked(!checked)} />;
}

Interview Gold Point

The strongest signal is recognizing that native HTML already models this dual API (<input value onChange> vs <input defaultValue>), and that a design-system component should honor the same convention so it feels familiar to React developers. Bonus points for naming the asChild/render-prop escape hatch — it shows you understand that a good component API isn't just about the 80% case, it's about not blocking the 20% of consumers who need something the API didn't anticipate.

SECTION 3 - TOOLING, ACCESSIBILITY & VISUAL QUALITY

Q7. What is Storybook for, and how does it become living documentation?

ROI: ★★★★☆ Frequency: High

Short Answer

Storybook isolates a single component outside the app so you can develop and visually verify every state — default, loading, error, empty, disabled, hovered, long-text overflow — without wiring up routing, data fetching, or the rest of the app. Each state is written as a story, and because stories are just code that renders the real component with real props, they double as always-up-to-date, living documentation: instead of a wiki page that goes stale, the docs literally cannot lie about how the component renders, because they run the component.

Detailed Answer

Storybook is also the substrate several other design-system practices build on: the a11y addon runs automated accessibility checks against every story as you author it; autodocs generates a documentation page per component straight from its stories and TypeScript prop types; play functions let a story script an interaction (click, type) and assert on the result, effectively giving you a component-level integration test that runs inside Storybook's own test runner; and — critically for a design system — Chromatic (Q9) snapshots every story to catch visual regressions.

Modern Storybook uses CSF3 (Component Story Format 3): a story is an object with args, and Storybook's controls panel lets a consumer (or a designer) live-edit those args in the browser to explore every prop combination without touching code — a genuinely useful design/engineering handoff tool, not just an engineering one.

Code Example

// Button.stories.tsx — CSF3
import type { Meta, StoryObj } from "@storybook/react";
import { expect } from "@storybook/test";
import { within, userEvent } from "@storybook/testing-library";
import { Button } from "./Button";

const meta: Meta<typeof Button> = {
  title: "Components/Button",
  component: Button,
  tags: ["autodocs"],
  argTypes: {
    variant: { control: "select", options: ["primary", "secondary", "danger"] },
  },
};
export default meta;

type Story = StoryObj<typeof Button>;

export const Primary: Story = { args: { variant: "primary", children: "Save" } };
export const Disabled: Story = { args: { variant: "primary", disabled: true, children: "Save" } };

// A play function: script an interaction and assert on it
export const ClickFiresOnClick: Story = {
  args: { children: "Save" },
  play: async ({ canvasElement, args }) => {
    const canvas = within(canvasElement);
    await userEvent.click(canvas.getByRole("button", { name: /save/i }));
    await expect(args.onClick).toHaveBeenCalled();
  },
};

Interview Gold Point

The phrase that lands well: "Storybook docs can't go stale because they're not prose describing the component — they're the component, running." Mentioning the a11y addon and play functions shows you use Storybook as a quality gate, not just a component gallery, and connecting it forward to Chromatic demonstrates you understand the full pipeline: author a story once, get documentation, accessibility linting, interaction tests, and visual regression coverage all from that same artifact.

Q8. Why must accessibility be a first-class design system concern, not an afterthought?

ROI: ★★★★★ Frequency: Very High

Short Answer

Because every consuming team inherits whatever accessibility level a shared component ships with, fixing accessibility once in the design system fixes it for the entire organization simultaneously — whereas leaving it to each app team means the same bug (missing focus trap, wrong ARIA role, insufficient color contrast) gets "fixed," or more likely not fixed, N different times across N different apps. A design system is a leverage point: it's the cheapest place in the whole org to buy accessibility correctness, because the cost is paid once and the benefit compounds across every product surface that uses it.

Detailed Answer

Concretely, a design system earns that leverage through a few practices:

  • Build on accessible primitives — using a headless library like Radix (Q4) for the genuinely hard problems (focus trapping in a modal, roving tabindex in a menu, correct aria-* wiring) instead of re-solving them per component, and definitely instead of leaving each feature team to solve them per app.
  • Bake contrast into tokens — semantic color tokens (Q2) should be authored and validated to meet WCAG AA contrast ratios (4.5:1 for normal text) at the token level, so no component or app can accidentally combine two tokens into an unreadable pairing.
  • Automate the check, don't rely on memory — jest-axe in unit tests and the Storybook a11y addon in CI catch missing labels, invalid ARIA, and contrast violations before a component ever ships, turning a11y from a code-review nitpick into a build-breaking gate.
  • Document the contract — every component's docs should state its keyboard interaction model (what Tab, Enter, Escape, and arrow keys do) so consuming teams don't have to guess or reverse-engineer it.

Code Example

// Automated a11y check as part of the component's own test suite
import { render } from "@testing-library/react";
import { axe, toHaveNoViolations } from "jest-axe";
import { Modal } from "./Modal";

expect.extend(toHaveNoViolations);

test("Modal has no accessibility violations", async () => {
  const { container } = render(
    <Modal isOpen title="Delete item?">
      Are you sure you want to delete this item?
    </Modal>
  );
  const results = await axe(container);
  expect(results).toHaveNoViolations();
});

Interview Gold Point

The framing that resonates: "a design system turns accessibility from a per-app tax into a one-time engineering investment." Naming the leverage argument explicitly — one fix in Button.tsx propagates to every app that imports it, versus twenty copy-pasted buttons each needing their own fix — is exactly the kind of systems-thinking answer senior interviewers are listening for. Mentioning automated gates (jest-axe, Storybook a11y addon) shows you don't rely on manual review catching every regression.

Q9. What is visual regression testing, and how does a tool like Chromatic fit in?

ROI: ★★★★☆ Frequency: High

Short Answer

Visual regression testing renders each component state — usually every Storybook story — takes a pixel-level screenshot, and diffs it against an approved baseline on every pull request, catching unintended visual changes (a padding shift, a color that drifted, a font that stopped loading) that unit tests and RTL cannot see, because those tools only inspect the DOM and accessibility tree, never actual paint output. Chromatic (built by the Storybook team) is the most common implementation: it snapshots every story across configured browsers/viewports in the cloud, and a human reviews and approves any visual diff before it can merge, turning "did this refactor silently change 40 components' spacing" from an unanswerable question into a reviewable diff.

Detailed Answer

Because a design system's whole value proposition is visual consistency, this is one of the highest-leverage test types it can have — a shared token or base component change can silently ripple into dozens of consuming components, and only a pixel-level diff will actually catch that. Chromatic's TurboSnap feature narrows CI time by only re-snapshotting stories affected by the current diff (via a dependency graph), rather than re-rendering the entire library on every PR.

The recurring practical challenge is flakiness: web fonts loading asynchronously, CSS animations mid-frame, and "today's date" rendered into a snapshot all produce false-positive diffs. The fix is disciplined story setup — disable animations in the test environment, wait for fonts before snapshotting, and mock dates/times so a story renders identically today and next month. Alternatives exist (Percy, or rolling your own Playwright screenshot comparisons), but the mechanism is the same: render, screenshot, diff, and require human sign-off on any visual change.

Code Example

// package.json — running Chromatic in CI
{
  "scripts": {
    "chromatic": "chromatic --exit-zero-on-changes --only-changed"
  }
}

// .github/workflows/chromatic.yml (excerpt)
// - uses: chromaui/action@v1
//   with:
//     projectToken: ${{ secrets.CHROMATIC_PROJECT_TOKEN }}
//     onlyChanged: true   // TurboSnap: only re-test affected stories

Common Mistake

A frequent gap is treating a failing visual diff as a blocking test failure to "fix," when in most workflows it's a prompt for human review — the diff might be an intentional design update that just needs approving, not a bug. The strong answer distinguishes visual regression testing (catches unintended pixel changes, needs human judgment to approve/reject) from functional testing (RTL/Jest — catches broken behavior, purely pass/fail), and explains why a design system needs both: one guards behavior, the other guards the visual consistency that's the whole point of the system.

SECTION 4 - STYLING, PACKAGING & VERSIONING

Q10. CSS-in-JS vs CSS Modules vs Tailwind — which styling approach fits a library consumed by many teams?

ROI: ★★★★☆ Frequency: High

Short Answer

This decision looks different for a shared library than for a single app, because whatever you choose becomes a dependency every consuming team inherits. Runtime CSS-in-JS (styled-components, Emotion) gives great colocation and dynamic theming but adds a runtime cost and — worse for a library — version-coupling risk: if your library ships styled-components v6 and a consuming app is still on v5, you can end up with two runtime instances, mismatched theme contexts, or duplicated CSS-in-JS engines in the bundle. CSS Modules have zero runtime cost and predictable, build-time scoping, but are less dynamic and need consumers to support CSS imports in their build. Tailwind is extremely fast to author in, but baking utility classes into a published library forces every consuming app to either also adopt Tailwind (and a compatible config) or accept a large, unpurgeable slab of utility CSS shipped alongside the package — a real problem when the library is meant to be dropped into apps with their own, different Tailwind setups.

Detailed Answer

The safest general answer for a library consumed by many teams with heterogeneous stacks is plain CSS / CSS Modules (or a zero-runtime CSS-in-JS tool like vanilla-extract or Linaria) combined with CSS custom properties for theming — because it has no version-coupling risk, imposes no build-tool opinion on the consumer, and pays no runtime styling cost. Zero-runtime CSS-in-JS is increasingly the industry's compromise: you keep the TypeScript-colocated authoring experience of CSS-in-JS, but the styles are extracted to static CSS files at build time, so consumers get plain CSS with no runtime dependency at all.

Interview Gold Point

The insight that shows real experience is naming the version-coupling failure mode specifically: a design system that ships styled-components as a dependency (not a peer dependency) can end up bundled twice inside one consuming app if that app also uses styled-components at a different version — two runtimes, two theme contexts, styles that silently fail to apply. The mature answer is either to keep styling frameworks out of the shared package entirely (CSS Modules / vanilla-extract) or, if CSS-in-JS is required, declare it as a strict peer dependency and document the supported version range clearly.

Q11. How do you version and publish a component library — monorepo, npm, semver?

ROI: ★★★★☆ Frequency: High

Short Answer

A design system package should follow strict semantic versioning — patch for bug fixes with no API change, minor for new, backward-compatible components or props, major for anything breaking (API or significant visual change) — and be built/published from a monorepo (commonly Turborepo or Nx, with separate packages like @acme/tokens, @acme/react, @acme/icons) using an automated release tool such as Changesets, since dozens of consuming apps pin to specific versions and need predictable, changelog-documented upgrades rather than surprise breakage.

Detailed Answer

The Changesets workflow is the de facto standard in this space: every PR that changes a published package includes a small changeset file describing the change and its semver bump (patch/minor/major). A bot then opens a standing "Version Packages" PR that aggregates all pending changesets, bumps the relevant package.json versions, and writes the CHANGELOG.md entries automatically. Merging that PR triggers the actual npm publish in CI. This removes "what version should this be" from a human's memory and makes every release traceable back to the PRs that produced it.

Monorepo structure matters for a design system specifically because it's rarely just one package — tokens, the React component package, an icon package, and sometimes framework-specific adapters (React, Vue) usually version somewhat independently, and a monorepo with workspace tooling (pnpm/Yarn workspaces + Turborepo/Nx for build caching and task orchestration) lets them share tooling and CI while still publishing separately.

Code Example

// .changeset/fuzzy-lions-jump.md — added by a contributor in their PR
---
"@acme/react": minor
---

Add a new `Combobox` component built on Radix's Popover + Command primitives.

// package.json (excerpt) — publishing config for the React package
{
  "name": "@acme/react",
  "version": "4.3.0",
  "peerDependencies": {
    "react": ">=18.0.0"
  },
  "exports": {
    ".": { "import": "./dist/index.mjs", "require": "./dist/index.cjs" }
  }
}

// CI: changesets publish workflow (conceptual)
// 1. PR merges with a changeset file
// 2. changesets/action opens/updates a "Version Packages" PR
// 3. Merging that PR bumps versions, writes CHANGELOG.md, and runs `changeset publish`

Interview Favorite

Naming Changesets by name and describing the two-PR flow (contributor PR with a changeset → automated "Version Packages" PR → publish on merge) is a strong, concrete signal that you've actually operated a published package, not just consumed one. It's also worth mentioning that strict semver discipline is what lets consuming teams safely use caret ranges (^4.3.0) in their own package.json — the entire promise of semver collapses the first time a "minor" release quietly breaks an existing prop's behavior.

Q12. How do you manage breaking changes and deprecations in a widely-consumed library?

ROI: ★★★★☆ Frequency: High

Short Answer

Because a breaking change to a shared component ripples across every consuming team at once, you never ship one silently inside a minor or patch release. Instead you deprecate first: keep the old API working, emit a development-only warning pointing at the replacement, and document the migration path. Give consumers a real runway — often spanning one to two major-version cycles — provide an automated codemod where the change is mechanical, and reserve the actual removal for a major version bump that consumers opt into deliberately.

Detailed Answer

A healthy deprecation lifecycle has distinct, clearly communicated stages rather than a single abrupt cutover:

StageWhat happensConsumer impact
1. AnnounceChangelog entry + migration guide published; new API ships alongside oldNone yet — both APIs work
2. WarnOld API emits a dev-only console.warn pointing at the replacementVisible in dev console, no runtime break
3. CodemodAn automated codemod (jscodeshift) is offered to mechanically rewrite call sitesTeams can migrate in minutes, not manually
4. RemoveOld API deleted in the next major versionBreaking — but only for teams who opted into the major bump

The deprecation warning itself should be cheap and unmistakable — logged once per component instance in development builds only (stripped from production to avoid bloating consumer bundles or console noise for end users) — and the migration guide should be linked directly from the warning message, not just from a changelog nobody reads. For genuinely mechanical renames (a prop renamed, a component split into two), a codemod removes the single biggest reason large migrations stall: manual, repetitive, error-prone find-and-replace across dozens of consuming repos.

Code Example

// Deprecation warning: keep the old prop working, but nudge toward the new one
function Button({ size, variant, ...props }: ButtonProps) {
  if (process.env.NODE_ENV !== "production" && variant === undefined && size !== undefined) {
    console.warn(
      "[@acme/react] Button's `size` prop is deprecated and will be removed in v5. " +
      "Use `variant` instead. See migration guide: https://acme.design/migrate/button-size"
    );
  }
  const resolvedVariant = variant ?? mapLegacySizeToVariant(size);
  return <button className={variantClass(resolvedVariant)} {...props} />;
}

Common Mistake

The disqualifying answer is "we just bump the major version and update the changelog." The strong answer treats a breaking change as a communication and tooling problem as much as a code problem: warn before you remove, give a real runway measured in months not days, automate the mechanical parts of migration with a codemod, and only ever land the actual removal behind a major version so adoption is opt-in. Mentioning that the warning must be stripped from production builds (so end users never see internal API noise) is a small detail that signals real production experience.

SECTION 5 - GOVERNANCE & ADOPTION

Q13. How do you drive cross-team adoption and govern a design system?

ROI: ★★★★☆ Frequency: High

Short Answer

Good components alone don't get adopted — a design system also needs a governance model (who can propose, review, and approve new components or changes) and real incentives that make the shared library the path of least resistance compared to a team rolling its own. The two common governance models are centralized (one platform team owns everything — highest consistency, but slower and a bottleneck as demand grows) and federated / contribution-based (feature teams contribute components upstream through an RFC and review process owned by a small core team — scales better, but needs discipline to avoid quality drift). Most mature organizations land on a hybrid: a small core team owns the foundations and review bar, while feature teams contribute components they need through a defined process.

Detailed Answer

Adoption is fundamentally a people problem wearing a technical costume. Practices that actually move the needle:

  • Treat consuming teams as customers — a support channel (Slack, office hours) and a real SLA on bug fixes, not a black-box team that ships and disappears.
  • Design system champions embedded in feature teams who know the system well enough to unblock their own team and feed real usage feedback back to the core team.
  • A public, visible roadmap and backlog so teams can see what's coming and don't route around the system out of impatience.
  • An RFC process for new components or breaking changes, so decisions are documented and reviewable rather than made ad hoc in one engineer's PR.

The most common failure mode is a design system built in isolation by a platform team with no early adopter buy-in: by the time it's "done," feature teams have already built their own versions of the same components and see no reason to migrate. The fix is involving real consuming teams from the earliest components — even at the cost of a slower initial build — so the system solves problems teams actually have, not problems the platform team imagined they have.

Interview Gold Point

Naming both governance models (centralized vs federated/contribution) and their tradeoffs, then landing on "most mature orgs run a hybrid," shows you understand this isn't a solved, one-size-fits-all problem. The single strongest point to make, though, is that adoption fails on people and process, not code quality — a beautifully engineered library that launches without early adopter involvement will lose to teams' existing, working, ad hoc components almost every time.

Q14. How do you measure whether a design system is actually succeeding?

ROI: ★★★☆☆ Frequency: Medium

Short Answer

Success is not "we shipped a component library" — it's measured across three dimensions: adoption (what fraction of screens/PRs use design-system components instead of one-off custom UI), consistency (fewer visual/UX inconsistencies surfaced in design QA or user research), and velocity (how much faster teams can build a new screen, and how many fewer UI bugs and duplicate one-off components show up over time). A design system that nobody uses, or that everybody uses but constantly has to override, is failing on the metric that actually matters regardless of how polished its Storybook looks.

Detailed Answer

Concrete, trackable metrics teams actually use:

CategoryConcrete MetricHow it's measured
AdoptionComponent adoption rateLint rule / codebase scan for library imports vs raw HTML elements in feature code
AdoptionOverride frequencyHow often consumers add custom CSS/style overrides on top of a library component (a proxy for API gaps)
ConsistencyDesign QA defect rateNumber of visual-inconsistency tickets filed per release cycle
VelocityTime-to-ship a new screenBefore/after comparison for teams that migrated to the library
HealthSupport responsivenessTime-to-resolution on design-system bug reports/issues
HealthConsumer satisfactionPeriodic survey/NPS of engineers and designers using the system

A useful distinction to raise: some of these are leading indicators (adoption rate, override frequency — they predict future health) and some are lagging (defect rate, satisfaction survey — they confirm what already happened). A design system team that only tracks lagging indicators finds out something is wrong months after it started going wrong; tracking adoption and override frequency continuously catches API gaps and low-adoption components while they're still cheap to fix.

Interview Gold Point

The answer that stands out ties metrics back to the earlier sections of this chapter rather than listing them in a vacuum: a high override-frequency on one component is really an API design signal (Q6) — it means the component's props don't cover a real use case, the same way a low adoption rate is really a governance/adoption signal (Q13). Framing metrics as diagnostic tools that feed back into the system's roadmap, rather than a scoreboard for a slide deck, is what separates a senior answer here.

QUICK REVISION SHEET

  • Design system vs component library: the library is the code artifact; the system is tokens + components + guidelines + governance — the whole single source of truth.
  • Design tokens: named values in a tiered structure (global → semantic → component) compiled by a tool like Style Dictionary into CSS variables/JS objects for every platform.
  • Composable components: favor compound components (shared Context, flexible JSX composition) and slots over one component with dozens of boolean props.
  • Headless vs fully-styled: headless (Radix, Headless UI) gives behavior + a11y with zero visual opinion — right choice when building your own design system; fully-styled (MUI, Chakra) trades re-skinning effort for speed.
  • Theming/dark mode: swap semantic CSS custom properties via a root data-theme attribute; components never hardcode colors or branch on a theme prop.
  • Controlled vs uncontrolled: support both via a shared useControllableState hook, mirroring how native <input> already works; use Context, not prop drilling, for shared compound-component state.
  • Storybook: isolates components into stories that double as living docs, an a11y check surface, an interaction-test runner (play functions), and the input to visual regression testing.
  • Accessibility as first-class: fixing a11y once in a shared component fixes it for every consuming app at once — the design system is the cheapest leverage point in the org for accessibility.
  • Visual regression testing: Chromatic snapshots every Storybook story and requires human review of pixel-level diffs, catching what unit/RTL tests structurally cannot see.
  • Styling for a shared library: CSS Modules or zero-runtime CSS-in-JS (vanilla-extract) plus CSS variables is safest for many heterogeneous consumers; runtime CSS-in-JS risks version-coupling across apps.
  • Versioning/publishing: strict semver, a monorepo (Turborepo/Nx), and Changesets to automate version bumps, changelogs, and npm publishing traceably.
  • Breaking changes: announce → warn (dev-only console warning) → offer a codemod → remove only in the next major version; never ship a silent break in a minor/patch.
  • Adoption & governance: centralized vs federated/contribution models, both needing champions, an RFC process, and treating consuming teams as customers with real support SLAs.
  • Measuring success: track adoption rate and override frequency (leading indicators) alongside consistency and velocity impact (lagging indicators) — not just "we shipped a library."
