SECTION 1 - BUNDLERS

Q1. Why do we need a bundler / build tool at all?

ROI: ★★★★★ Frequency: High

Short Answer

Modern apps are split across hundreds of modules and use syntax (JSX, TypeScript, newer JS) and assets (CSS, images) the browser can't run directly. A bundler resolves the module graph, transpiles/compiles everything to browser-compatible code, optimizes it (minify, tree-shake, split into chunks), and outputs a small set of cacheable files.

Detailed Answer

Shipping raw source has problems: too many network requests, unsupported syntax (JSX/TS), no minification, no dead-code elimination, and no dependency resolution for node_modules. A bundler/build tool solves all of these:

  • Module resolution — follows imports to build the dependency graph.
  • Transpilation — JSX/TS/modern JS → browser-compatible JS.
  • Asset handling — CSS, images, fonts imported into the graph.
  • Optimization — minification, tree-shaking, code splitting, content hashing for caching.

Senior Engineer Perspective

A nuance worth mentioning: native ES modules and HTTP/2 mean the browser can load many modules directly in dev (that's how Vite's dev server works), but production still benefits from bundling to reduce requests and enable aggressive optimization. So "do we still need bundlers?" is "less in dev, still yes in prod."

Q2. Explain Webpack's core concepts.

ROI: ★★★★☆ Frequency: High

Short Answer

Webpack builds a dependency graph from one or more entry points, transforms non-JS files with loaders, extends the build with plugins, and writes the result to output. Module resolution decides how import paths map to files.

Detailed Answer

  • Entry — where the graph starts (e.g. src/index.tsx).
  • Output — where bundles are written and how they're named (usually with content hashes).
  • Loaders — transform files as they're imported: babel-loader (JS/TS/JSX), css-loader/style-loader, asset loaders. Loaders are the "how do I understand this file type" layer.
  • Plugins — hook into the whole build lifecycle for broader tasks: HtmlWebpackPlugin, MiniCssExtractPlugin, DefinePlugin (env injection), bundle analysis.
  • Mode — development vs production presets (minification, source maps).

Code Example

// webpack.config.js (essence)
module.exports = {
  entry: './src/index.tsx',
  output: { filename: '[name].[contenthash].js', path: __dirname + '/dist' },
  module: {
    rules: [
      { test: /\.[jt]sx?$/, use: 'babel-loader', exclude: /node_modules/ },
      { test: /\.css$/, use: ['style-loader', 'css-loader'] },
    ],
  },
  plugins: [new HtmlWebpackPlugin({ template: './index.html' })],
};

Senior Engineer Perspective

The clean mental model to state: loaders transform individual files; plugins act on the whole bundle/lifecycle. Candidates who blur those two look shallow. Webpack is still huge in existing codebases even as new projects choose Vite, so knowing it is not optional.

Q3. Why is Vite so fast, and how does it differ from Webpack?

ROI: ★★★★★ Frequency: Extremely High

Short Answer

In dev, Vite doesn't bundle — it serves your source as native ES modules on demand and pre-bundles dependencies with esbuild (Go, extremely fast), so startup is near-instant and HMR is per-module regardless of app size. For production it bundles with Rollup to get optimized, tree-shaken, code-split output. Webpack bundles everything up front even in dev, which gets slow as the app grows.

Detailed Answer

Webpack's dev server builds the entire bundle before serving, so cold start and rebuild time scale with project size. Vite flips this: modern browsers support ES modules natively, so in dev Vite serves each file as an ES module when the browser requests it — no upfront bundling. Dependencies (which don't change and may be CommonJS) are pre-bundled once with esbuild and cached. The result: server start is basically constant time, and HMR only re-processes the changed module.

For production, unbundled ESM would mean too many requests, so Vite uses Rollup to produce a proper optimized build (minify, tree-shake, chunk, hash).

Senior Engineer Perspective

The subtle point interviewers reward: Vite uses two different tools — esbuild for speed in dev, Rollup for optimization in prod — because their goals differ (fast iteration vs best output). Knowing that (and that this dev/prod difference can occasionally cause "works in dev, breaks in build" surprises) is senior-level.

SECTION 2 - TRANSPILATION

Q4. What is Babel and why do we transpile? What are SWC and esbuild?

ROI: ★★★★☆ Frequency: High

Short Answer

Babel is a JavaScript compiler that converts modern JS/JSX/TS into code older browsers understand, using presets (@babel/preset-env, preset-react) and plugins. Transpilation is needed because you write cutting-edge syntax but must support a range of browsers. SWC (Rust) and esbuild (Go) are much faster alternatives that do the same transpilation, which is why modern toolchains (Next.js, Vite) use them instead of Babel.

Detailed Answer

Two related jobs: syntax transpilation (arrow functions, optional chaining, JSX → React.createElement/jsx runtime) and polyfilling (adding runtime implementations of missing APIs like Promise, Array.flat via core-js). @babel/preset-env + a browserslist config decides how much to transpile/polyfill based on which browsers you target — set it too broadly and you ship bloated, over-transpiled code.

Babel is written in JS, so it's slower. SWC and esbuild are compiled languages and are 10–100× faster for the same transforms, which is why Next.js swapped Babel for SWC and Vite uses esbuild. Babel still wins on its huge plugin ecosystem and custom AST transforms.

Senior Engineer Perspective

Distinguish transpilation from polyfilling — a common confusion. Transpilation changes syntax; polyfills add missing APIs. And browserslist is the single knob that controls both scope and bundle size; naming it shows you've tuned a real build. Note that supporting very old browsers via polyfills penalizes modern users unless you use differential serving.

Q5. How do code splitting and chunking work at the bundler level?

ROI: ★★★★☆ Frequency: Medium-High

Short Answer

The bundler emits separate output files ("chunks") so the browser loads only what's needed. Dynamic import() creates an on-demand chunk (usually per route); common dependencies can be split into a shared vendor chunk. This shrinks the initial download and improves caching.

Detailed Answer

  • Dynamic import — import('./Chart') tells the bundler to emit Chart as its own chunk loaded lazily.
  • Vendor/common splitting — libraries shared across pages can be split out so they're cached once and not re-downloaded per route (Webpack's splitChunks, Rollup's manualChunks).
  • Content hashing — chunk filenames include a hash so long-term caching is safe; only changed chunks get new names.

The caching benefit: if your vendor chunk (React, etc.) rarely changes, users keep it cached across deploys while your app chunk updates.

Senior Engineer Perspective

Warn against over-splitting: too many tiny chunks add HTTP overhead and can hurt more than help. The sweet spot is route-level splitting plus a stable vendor chunk. Also note that a naive vendor chunk that changes whenever any dependency changes defeats caching — modern tooling hashes per-module to keep unchanged code cacheable.

Q6. What is tree-shaking and what breaks it?

ROI: ★★★★☆ Frequency: High

Short Answer

Tree-shaking is dead-code elimination that removes exports you never import. It works because ES modules are statically analyzable. It breaks with CommonJS (dynamic require), with modules that have side effects, and with import patterns that pull in an entire package.

Detailed Answer

Because import/export are static, the bundler knows at build time exactly which bindings are used and can drop the rest. Things that defeat it:

  • CommonJS (module.exports, dynamic require) — not statically analyzable.
  • Side effects — a module that does work on import (mutates globals, registers polyfills) can't be safely dropped; authors declare purity with "sideEffects": false in package.json.
  • Whole-package imports — import _ from 'lodash' pulls everything; use lodash-es with named imports or per-method imports.
  • Re-export barrels that force evaluating a whole index.

Senior Engineer Perspective

The practical wisdom: prefer ESM dependencies, import narrowly, and verify with a bundle analyzer rather than trusting that tree-shaking "just works." A concrete story ("the analyzer showed the full icon set; switching to per-icon imports cut 200KB") is far stronger than the definition alone.

Q7. What are source maps and HMR?

ROI: ★★★★☆ Frequency: Medium

Short Answer

A source map maps minified/transpiled output back to your original source so DevTools shows real file names, lines, and variables when debugging. Hot Module Replacement (HMR) swaps updated modules into the running app during development without a full page reload, preserving component state.

Detailed Answer

Source maps: production code is minified and transpiled, so a stack trace points at a.4f3.js:1:88213. The .map file lets the browser (and error trackers like Sentry) reconstruct the original location. In production you typically generate them but don't serve them publicly (upload to your error tracker instead, to avoid exposing source).

HMR: instead of reloading the whole page on save, the dev server pushes only the changed module over a WebSocket and the framework re-renders just that part, keeping your form inputs and app state intact. React Fast Refresh is the React-specific implementation that preserves component state across edits.

Senior Engineer Perspective

Know the source-map types trade-off (e.g. eval-source-map fast but bulky for dev vs source-map accurate for prod) and that you should NOT ship source maps to end users for proprietary code. On HMR, mention Fast Refresh's limits: it can't always preserve state (e.g. when you change a hook's shape), and it full-reloads on non-component exports.

Q8. How do you handle environment variables and build modes?

ROI: ★★★☆☆ Frequency: Medium

Short Answer

Build tools inject env vars at build time by string-replacing references in your code (Vite's import.meta.env, Webpack's DefinePlugin, Next's process.env). Only variables with a public prefix (VITE_, NEXT_PUBLIC_) are exposed to the browser — everything else stays server-only.

Detailed Answer

Because the frontend bundle is public, any env var baked into it is visible to users. That's why frameworks require an explicit prefix to expose a variable to client code, and keep unprefixed vars server-side (used in SSR, API routes, build scripts). Modes (development, production, test) load different .env files (.env.production) and toggle optimizations.

Code Example

// .env
VITE_API_URL=https://api.example.com   # exposed (VITE_ prefix)
DB_PASSWORD=secret                      # NOT exposed to the browser

// usage in client code
const url = import.meta.env.VITE_API_URL;

Senior Engineer Perspective

The security point matters: never put secrets (API keys with write access, DB creds) in a client-exposed variable — they ship in the bundle. Real secrets belong on the server (API routes, edge functions). Interviewers slip this in to see if you understand the client bundle is public.

SECTION 3 - CODE QUALITY

Q9. ESLint vs Prettier — what does each do?

ROI: ★★★★★ Frequency: High

Short Answer

ESLint is a linter — it finds code-quality and correctness problems (unused vars, missing hook deps, accessibility issues) and can auto-fix many. Prettier is a formatter — it enforces consistent style (spacing, quotes, line length) with no opinions about correctness. They're complementary: ESLint for rules, Prettier for formatting.

Detailed Answer

ESLint catches bugs and enforces conventions via rules and plugins: eslint-plugin-react-hooks (rules of hooks, exhaustive deps), eslint-plugin-jsx-a11y (accessibility), TypeScript rules via typescript-eslint. Prettier reformats code deterministically so the team never argues about style in reviews.

Historically Prettier ran through ESLint, but the recommended setup now runs them separately and uses eslint-config-prettier to turn off ESLint's stylistic rules so the two don't conflict. Modern ESLint uses "flat config" (eslint.config.js).

Senior Engineer Perspective

The clean framing: "ESLint = code quality/correctness, Prettier = formatting; disable ESLint's format rules with eslint-config-prettier so they don't fight." Mention the flat-config migration (current ESLint default) — it dates your knowledge as recent. The most valuable ESLint rule for React is react-hooks/exhaustive-deps.

Q10. How do you enforce quality with Husky / lint-staged?

ROI: ★★★★☆ Frequency: Medium

Short Answer

Husky manages Git hooks (like pre-commit). lint-staged runs linters/formatters only on the files staged for commit, so checks are fast. Together they block commits that fail lint/format/type checks, catching issues before they reach CI.

Detailed Answer

Running ESLint/Prettier on the whole repo on every commit would be slow, so lint-staged scopes the work to just the staged files. Husky wires a pre-commit hook that invokes lint-staged; you can also add a commit-msg hook (commitlint) to enforce conventional commit messages, and a pre-push hook to run tests/typecheck.

Code Example

// package.json
{
  "lint-staged": {
    "*.{ts,tsx}": ["eslint --fix", "prettier --write"],
    "*.{css,md}": ["prettier --write"]
  }
}
// .husky/pre-commit  ->  npx lint-staged

Senior Engineer Perspective

Pre-commit hooks are a fast local gate, but they can be bypassed (--no-verify), so they're a convenience, not a guarantee — CI must run the same checks authoritatively. Keep pre-commit hooks fast (staged files, fixable rules) and push slow work (full test suite, type-check) to pre-push or CI so you don't frustrate developers.

SECTION 4 - PACKAGE & MONOREPO MANAGEMENT

Q11. npm vs yarn vs pnpm — what are the differences?

ROI: ★★★★☆ Frequency: Medium-High

Short Answer

All three install dependencies and produce a lockfile for reproducible installs. pnpm is the modern favourite: it uses a global content-addressable store and symlinks, so installs are fast and disk-efficient, and it enforces stricter dependency isolation (no accidental access to undeclared packages). npm is the default bundled with Node; yarn (Classic/Berry) pioneered lockfiles and workspaces.

Detailed Answer

Lockfilepackage-lock.jsonyarn.lockpnpm-lock.yaml
node_modulesFlat (hoisted)Flat (hoisted)Symlinked from a global store
Disk usageHigh (copies per project)HighLow (shared store, hard links)
StrictnessPermissive (phantom deps)PermissiveStrict (only declared deps)

The key insight: npm/yarn hoist dependencies into a flat node_modules, which lets you accidentally import a package you never declared ("phantom dependency") — it works until that transitive dep changes. pnpm's symlinked layout only exposes what you declared, catching those bugs, while its shared store saves gigabytes across projects.

The lockfile pins exact resolved versions and hashes so every machine/CI installs identical trees — always commit it.

Senior Engineer Perspective

Naming "phantom dependencies" and the content-addressable store is the senior differentiator. Also note npm's ci command installs strictly from the lockfile (deterministic, for CI) vs install which may update it. Reproducible builds hinge on committing and respecting the lockfile.

Q12. What is a monorepo and when is it worth it?

ROI: ★★★★☆ Frequency: Medium

Short Answer

A monorepo keeps multiple projects/packages (apps, shared UI library, utils) in one repository, managed with workspaces (npm/yarn/pnpm) and a task runner like Turborepo or Nx that adds caching and orchestrates builds across packages. It's worth it when projects share code and need coordinated changes; it adds tooling overhead you don't need for a single small app.

Detailed Answer

Benefits: shared code without publishing to npm, atomic cross-package changes (update a component and its consumers in one PR), consistent tooling/versions, and one place for CI. The cost: you need workspace tooling, and naive builds rebuild everything, so you add a task runner with caching (Turborepo/Nx cache task outputs and skip unchanged packages) and affected detection (only build/test what a change touches).

Senior Engineer Perspective

The honest take interviewers appreciate: monorepos shine for design systems and multiple related apps sharing packages, but they're overkill for one app — the caching/affected tooling is what makes them scale, without it CI time explodes. Contrast with polyrepo (independent repos, versioned via npm) and its versioning friction.

Q13. Explain semantic versioning and dependency ranges.

ROI: ★★★★☆ Frequency: Medium

Short Answer

SemVer is MAJOR.MINOR.PATCH: MAJOR = breaking changes, MINOR = backward-compatible features, PATCH = backward-compatible fixes. In package.json, ^1.2.3 allows minor+patch updates (<2.0.0), ~1.2.3 allows patch updates only (<1.3.0), and an exact 1.2.3 pins it.

Detailed Answer

SemVer is a promise, not a guarantee — publishers sometimes ship breaking changes in a minor. That's why the lockfile matters and why you review updates (Dependabot/Renovate PRs) and run tests before bumping. Pre-1.0 (0.x), the caret behaves differently (minor bumps are treated as breaking), a detail that trips people up.

Q14. ESM vs CommonJS — what's the difference and how do they interop?

ROI: ★★★★☆ Frequency: Medium

Short Answer

CommonJS (CJS) is Node's original module system — synchronous require()/module.exports, resolved at runtime. ES Modules (ESM) — import/export — are the standard, statically analyzable, and support tree-shaking and top-level await. Interop is imperfect: ESM can import CJS, but CJS can't statically require ESM (it needs dynamic import()).

Detailed Answer

Because ESM is static (imports resolved before execution), bundlers can tree-shake it; CJS is dynamic (you can require conditionally), which is flexible but not analyzable. Node picks the mode from "type": "module" in package.json or the file extension (.mjs/.cjs). Many packages ship both via the "exports" field with conditional entry points.

Common friction: named imports from a CJS package sometimes only work as a default import; ESM's async loading can't be required synchronously from CJS. Bundlers smooth much of this over, which is why you rarely feel it in app code but hit it when authoring libraries or configs.

Senior Engineer Perspective

The "dual package" story — shipping both ESM and CJS via package.json#exports — is what library authors deal with, and the source of many "cannot use import statement outside a module" errors. Framing ESM as the tree-shakeable, standard future while CJS remains for legacy Node shows current, accurate understanding.

SECTION 5 - MODERN BUNDLERS & BUILD ENGINES

Q15. What problem does Turbopack solve, and how is it different from Webpack?

ROI: ★★★★☆ Frequency: Medium

Short Answer

Turbopack is a Rust-based bundler built by the Next.js/Vercel team, designed as an eventual Webpack replacement with incremental, function-level caching so large apps get fast dev-server startup and HMR that doesn't degrade as the codebase grows. It's integrated first into Next.js (behind a flag, then increasingly the default) rather than being a general-purpose standalone tool.

Detailed Answer

Webpack's whole-graph model recomputes more than necessary on each change in a large app, so cold start and rebuild time scale with project size. Turbopack pursues the same "stop paying for the whole app on every change" goal as Vite, but through a different mechanism: instead of skipping bundling in dev like Vite does (serving native ESM), Turbopack still bundles, but caches work at a granular function/module level on disk so incremental rebuilds are close to constant-time regardless of app size. This matters specifically for a framework like Next.js, which needs a consistent, server-renderable module graph (SSR/RSC) that "just serve raw ESM" doesn't cleanly provide.

Code Example

// package.json
{
  "scripts": {
    "dev": "next dev --turbo"
  }
}

Senior Engineer Perspective

Know that Turbopack is Next.js-specific (an opt-in flag, still stabilizing for full production builds, starting with the dev server) rather than a drop-in Webpack replacement for any project. The strong answer contrasts the strategy, not just the speed: Vite skips bundling in dev entirely; Turbopack still bundles but caches incrementally, because SSR/RSC frameworks need a coherent server-renderable graph that unbundled native ESM doesn't give you.

Q16. What is Rspack and why does it exist alongside Vite and Turbopack?

ROI: ★★★☆☆ Frequency: Low-Medium

Short Answer

Rspack is a Rust reimplementation of Webpack's architecture — largely compatible with existing Webpack loaders, plugins, and config — that aims for near drop-in compatibility while getting a 5–10x speed boost from native code. Unlike Vite or Turbopack, which use fundamentally different dev models, Rspack's pitch is "keep your existing Webpack setup, just make the core fast."

Detailed Answer

Migrating a mature Webpack app to Vite or Turbopack can require rewriting substantial config and swapping plugins, since ecosystem plugin APIs differ across tools. Rspack targets organizations with large, working Webpack configs who want speed without a rewrite: it implements Webpack's loader/plugin interfaces in Rust so most existing webpack.config.js setups run with minimal changes, just dramatically faster. It's used by frameworks like Rspress and Modern.js, and has its own Module Federation implementation.

Senior Engineer Perspective

The interview-worthy framing: there are three distinct strategies to the "make bundling fast" problem, not one race. Vite skips bundling in dev via native ESM. Turbopack bundles but caches incrementally at a granular level (Next.js-specific). Rspack keeps Webpack's exact API surface and rewrites only the slow core in Rust (compatibility-first). Naming which problem each one actually solves is stronger than saying "they're all fast alternatives to Webpack."

Q17. Explain Module Federation in depth — how does it let independently-deployed apps share code at runtime?

ROI: ★★★★☆ Frequency: Medium

Short Answer

Module Federation lets one app (a "host") load modules exposed by another independently built and deployed app (a "remote") at runtime, over the network — as if they were locally imported — with shared dependencies (like React) deduplicated between them. This is the core mechanism behind most micro-frontend architectures: each remote deploys on its own schedule, and the host picks up its latest version without a host rebuild.

Detailed Answer

A remote's Webpack/Rspack config declares exposes (which of its own modules other apps may consume) and shared (which dependencies should be deduplicated with whoever consumes it, e.g. a singleton React). A host declares remotes (URLs to other apps' federation manifests) and can then import() a remote's exposed module dynamically, fetched and executed in the host's runtime at that moment. This is fundamentally different from ordinary npm-package code sharing: an npm dependency is fixed at the host's own build time, while a federated remote can change the moment its own team redeploys it — no host rebuild required.

Failure modes to know: a version mismatch in a "shared" singleton dependency between host and remote (Module Federation negotiates a compatible version at runtime, but incompatible majors can still break); the remote being unreachable/down at runtime (needs an error boundary and a fallback UI, since this failure can't be caught at build time); and misconfigured "shared" settings causing the framework itself to be duplicated, defeating the whole point.

Code Example

// remote app's webpack.config.js
new ModuleFederationPlugin({
  name: 'checkout',
  filename: 'remoteEntry.js',
  exposes: { './CheckoutForm': './src/CheckoutForm' },
  shared: { react: { singleton: true, requiredVersion: '^18.0.0' } },
});

// host app's webpack.config.js
new ModuleFederationPlugin({
  name: 'shell',
  remotes: { checkout: 'checkout@https://checkout.example.com/remoteEntry.js' },
  shared: { react: { singleton: true, requiredVersion: '^18.0.0' } },
});

// host usage
const CheckoutForm = React.lazy(() => import('checkout/CheckoutForm'));

Senior Engineer Perspective

Module Federation is an architecture decision with real operational cost, not just a bundler feature — independent deploy pipelines per team, contract/version compatibility testing across team boundaries, and error-boundary strategy for a remote that's down or mismatched. A candidate who frames it purely as "code splitting across apps" is missing the runtime-negotiation and organizational-boundary aspects that make it worth reaching for (or worth avoiding) in the first place.

Q18. What are import maps, and how do they enable native ESM without a bundler?

ROI: ★★★☆☆ Frequency: Low-Medium

Short Answer

Import maps let the browser resolve bare specifiers (import React from 'react') natively, by mapping package names to actual URLs in a <script type="importmap"> tag — solving, at the browser level, the exact "how do I resolve a bare import" problem bundlers have historically solved at build time.

Detailed Answer

Without an import map, a browser encountering import React from 'react' in a native <script type="module"> has no idea what "react" refers to — ES module specifiers must normally be full or relative URLs. An import map is a JSON block the browser reads before executing modules, mapping specifiers to URLs (often CDN-hosted ESM builds, e.g. from esm.sh or jspm). This enables genuinely bundler-free apps: write standard import statements, ship no build step, and let the browser fetch and link modules itself.

Code Example

<script type="importmap">
{
  "imports": {
    "react": "https://esm.sh/react@18",
    "react-dom/client": "https://esm.sh/react-dom@18/client"
  }
}
</script>
<script type="module">
  import React from 'react';
  import { createRoot } from 'react-dom/client';
</script>

Senior Engineer Perspective

Import maps are a resolution mechanism, not a bundler replacement — you still give up bundling optimizations (minification, tree-shaking, single-request loading) which matters at production scale. They're genuinely useful for prototypes, no-build tools, and cases where a CDN-hosted, widely shared dependency benefits from being cached once across many sites — but for anything beyond a small app, you still want a real build step for production.

Q19. When does it actually make sense to skip a bundler entirely?

ROI: ★★★☆☆ Frequency: Low

Short Answer

It's reasonable for small internal tools/prototypes, apps whose whole dependency graph is small enough that native ESM plus import maps perform fine, or contexts targeting only modern browsers where a CDN and native modules deliver acceptable load performance without build complexity.

Detailed Answer

Arguments for skipping a bundler: faster iteration (no build step to wait on), simpler debugging (the code that runs is literally the code you wrote — no source maps needed to make sense of a stack trace), and less tooling surface to maintain. Arguments against: TypeScript/JSX still need some transform (though this can be a tiny standalone script rather than a full bundler), tree-shaking/code-splitting savings disappear, and the npm ecosystem still has plenty of CommonJS-only packages that don't play well with pure native ESM.

Senior Engineer Perspective

This is judgment-call territory, and the strong answer treats it as a spectrum rather than all-or-nothing — some transform is almost always still needed somewhere. It ties back to the very first question in this chapter: bundlers matter less in dev at small scale, but the case for them in production strengthens as the app, its dependency graph, and its user base grow.

SECTION 6 - CSS & ASSET PIPELINE

Q20. CSS Modules vs CSS-in-JS vs Tailwind's JIT engine — how does each integrate with the bundler's pipeline?

ROI: ★★★★☆ Frequency: Medium-High

Q21. What do PostCSS and autoprefixer do, and how do critical CSS and CSS code splitting work?

ROI: ★★★☆☆ Frequency: Medium

Short Answer

PostCSS is a plugin-based CSS transform pipeline — the CSS equivalent of Babel — and autoprefixer is its most common plugin, adding vendor prefixes based on a browserslist target. Critical CSS extracts the above-the-fold styles needed for first paint and inlines them in <head>; CSS code splitting emits a separate CSS file per async chunk so a route's unused styles aren't downloaded upfront.

Detailed Answer

PostCSS sits in the CSS loader chain (postcss-loader in Webpack; built into Vite's CSS handling by default) and can run nesting support, custom-property fallbacks, and minification (cssnano) in addition to autoprefixer — the same browserslist config that drives Babel's transpilation scope also drives which prefixes autoprefixer adds. Critical CSS tooling (e.g. critters, or Next.js's built-in critical CSS handling) automates extracting just the styles needed for the initial viewport; modern bundlers split CSS per async chunk by default, mirroring their JS code-splitting behavior.

Senior Engineer Perspective

Most teams don't hand-roll critical CSS extraction anymore — frameworks automate it — but understanding the tradeoff (inlining critical CSS improves first paint at the cost of that inlined CSS no longer being cacheable separately) is what separates a senior discussion from reciting a tool name.

Q22. How do image optimization pipelines work in a modern build?

ROI: ★★★★☆ Frequency: Medium-High

Short Answer

Image pipelines resize images into responsive srcsets, convert them to modern formats (WebP/AVIF) with fallbacks, and lazy-load below-the-fold images. Frameworks like Next.js provide an image component/loader abstraction that automates this (on-demand or at build time); plain bundlers need it wired explicitly via plugins (imagemin, sharp-based loaders) or an external image CDN.

Detailed Answer

The core idea is a "loader" — a function that, given a source image, returns URLs for various sizes/formats — so the browser can request only the size and format it actually needs (via srcset/sizes, and format negotiation for WebP/AVIF with an original-format fallback for unsupported browsers). This can happen at build time (fine for a small, known set of static images) or on-demand at request time via a server/CDN function (necessary for user-uploaded or CMS-driven content, since you can't pre-generate every variant of every image at build time). Self-hosting on-demand optimization is real, ongoing compute cost with its own caching/invalidation concerns — it's not free just because it's automated.

Code Example

import Image from 'next/image';

<Image
  src="/hero.jpg"
  width={1200}
  height={600}
  alt="Hero"
  priority
/>
// next/image generates a responsive srcset, serves AVIF/WebP where supported,
// and lazy-loads by default unless `priority` is set for above-the-fold images.

Senior Engineer Perspective

Image optimization is often the single biggest lever on LCP (Largest Contentful Paint). Know the difference between build-time static optimization (fine for a small known image set) and runtime/on-demand optimization (needed for dynamic content) — and that choosing to self-host the latter is a genuine infrastructure decision, not just a config flag.

Q23. What are the key font loading strategies, and what does font-display control?

ROI: ★★★☆☆ Frequency: Medium

Short Answer

Fonts can block or delay text rendering unless handled carefully. Strategies include self-hosting fonts (avoiding a render-blocking third-party request), preloading critical fonts, subsetting to only needed glyphs, and the CSS font-display property, which controls how the browser behaves while a web font is still loading (invisible text vs a fallback font shown immediately).

Detailed Answer

font-display: swap shows a fallback font immediately, then swaps to the web font once loaded — fast text, but can cause a visible reflow/layout shift if the fallback and web font have different metrics. font-display: optional gives the browser permission to skip the web font entirely on a slow connection, prioritizing layout stability (best CLS) over guaranteed use of the custom font. Preloading (<link rel="preload" as="font">) tells the browser to fetch a critical font earlier than it would discover it naturally through CSS parsing.

Build-time font optimization tools (e.g. Next.js's next/font) automate self-hosting plus a further technique: adjusting the fallback font's metrics (size-adjust, ascent/descent overrides) so the fallback-then-swap transition causes minimal or no layout shift, rather than only picking a font-display value and hoping.

Senior Engineer Perspective

Font loading is a Cumulative Layout Shift concern as much as a load-time concern. The modern technique worth naming explicitly is matching fallback font metrics to the web font via size-adjust/ascent-override — that's what tools like next/font automate, and it's a stronger answer than just reciting the font-display values.

Q24. How does SVG handling work in the build — asset import vs SVGR?

ROI: ★★★☆☆ Frequency: Low-Medium

Short Answer

SVGs can be imported three ways: as a URL/file reference (an asset loader — cheap, one cacheable HTTP request or an inlined data URI), inlined raw for CSS use, or transformed into a React component via SVGR (every <path> becomes JSX, enabling props like fill/className, and per-icon tree-shaking when imported individually rather than from a giant icon barrel).

Detailed Answer

Webpack configures this via asset modules (asset/resource vs asset/inline) or the @svgr/webpack loader; Vite via vite-plugin-svgr or a ?react query suffix on the import path. SVGR components are convenient — styleable via normal React props — but add a build step and a slightly larger output (a React component wrapper) compared to a plain <img src="icon.svg">, which is cacheable as its own independent network resource.

Senior Engineer Perspective

For large icon sets, importing per-icon (not a barrel re-exporting the whole set) matters for tree-shaking, directly echoing Q6's whole-package-import pitfall. Sprite-sheet approaches are a legacy alternative still seen for very large icon sets where per-icon HTTP requests would be excessive.

Q25. How do you read a bundle analyzer report (webpack-bundle-analyzer / rollup-plugin-visualizer)?

ROI: ★★★★☆ Frequency: Medium-High

Short Answer

These tools generate an interactive treemap of your actual output bundle, where each box's size represents a module's real (parsed/gzip) contribution to bundle size — letting you visually spot which dependency or chunk is unexpectedly large.

Detailed Answer

Enable via webpack-bundle-analyzer as a plugin producing a static HTML report, rollup-plugin-visualizer for Rollup/Vite builds, or source-map-explorer as an alternative that reads existing source maps. When reading the report, look for: duplicate copies of the same library at different nested versions (two boxes for what should be one dependency), an unexpectedly large single dependency (classic example: moment.js bundling all its locale data by default), or an entire icon/utility library pulled in from one non-tree-shaken import.

Senior Engineer Perspective

Run this on every significant PR touching dependencies, or gate it in CI (Q27), rather than only investigating after a user complaint about load time. A bundle analyzer is a profiler you use routinely, not a one-time audit tool.

Q26. How do you find and fix bundle bloat from duplicate dependencies and unintended polyfills?

ROI: ★★★★☆ Frequency: Medium

Short Answer

Two common, hard-to-spot bloat sources: duplicate copies of the same library at different versions pulled in transitively (often from lockfile/hoisting quirks), and unintended polyfills injected because a browserslist target is broader than intended, or because a dependency ships pre-transpiled modern syntax that then gets redundantly re-transpiled and polyfilled on top.

Detailed Answer

  • Finding duplicates — the bundle analyzer treemap shows two boxes for what should be one package; npm ls <pkg> / pnpm why <pkg> shows the resolution tree causing it.
  • Fixing duplicates — a resolutions/overrides field forcing a single version, or the bundler's own dedupe options.
  • Unintended polyfills — check your browserslist config isn't stuck on an old default (e.g. still targeting IE11) and check whether a dependency ships modern syntax your Babel config re-processes unnecessarily.

Senior Engineer Perspective

This is where genuine "the analyzer showed X, so I did Y" interview stories come from. An interviewer asking about bundle bloat wants a concrete diagnostic example, not a definition of tree-shaking recited back at them.

Q27. How do you enforce performance budgets in CI (size-limit, bundlesize)?

Tools like size-limit or bundlesize run in CI, compare the built output's size against a configured threshold, and fail the build (or post a size-delta comment on the PR) when a change grows a bundle past budget — turning "don't regress bundle size" from a policy into an enforced gate.

Configuration specifies paths and limits per entry point; CI integration typically posts a before/after size diff as a PR comment. Always budget on compressed size (gzip/brotli) since raw size is a misleading proxy for real network transfer. The complementary tool is Lighthouse CI, which budgets actual runtime performance metrics rather than just byte counts.

Budgets should be scoped per-entry/route (a shared vendor chunk budget differs from a lazily-loaded route chunk budget) and treated like test-coverage gates — a failing budget should require an explicit, reviewed justification to override, not a quiet bump of the number whenever it's inconvenient.

Q28. How do duplicate dependency versions cause bugs beyond just bundle size — e.g. duplicate React copies?

ROI: ★★★★☆ Frequency: Medium

Short Answer

Some libraries — React chief among them — must be a true runtime singleton because of internal shared state (React's dispatcher). Two copies of React loaded at once don't just bloat the bundle; they break hooks and context outright, typically surfacing as a confusing "Invalid hook call" error that has nothing to do with violating the rules of hooks.

Detailed Answer

This happens when a dependency ends up with its own nested copy of React in its own node_modules, because of a version mismatch or a hoisting quirk. Diagnose with npm ls react or pnpm why react to see the full resolution tree and find where the duplicate is coming from. Fix it by ensuring the offending library correctly declares React as a peerDependency (Q35) rather than a regular dependency, or by forcing a single resolved version via overrides/resolutions. In a Module Federation setup, this is exactly what the shared singleton config (Q17) exists to prevent.

Senior Engineer Perspective

Checking for duplicate React copies is one of the strongest diagnostic habits to name when asked "you get 'Invalid hook call' but the code looks correct — what do you check?" It's a much more common real-world cause than an actual rules-of-hooks violation once a codebase has any nontrivial dependency tree.

SECTION 8 - TYPESCRIPT IN THE BUILD PIPELINE

Q29. How does tsc type-checking relate to Babel/SWC/esbuild transpilation — why are they run as separate steps?

ROI: ★★★★★ Frequency: High

Short Answer

Modern pipelines split two jobs that used to be conflated: transpilation (stripping type annotations and compiling syntax — done fast by Babel/SWC/esbuild, which do not validate types, only erase them) and type-checking (done by tsc --noEmit as an independent, slower, whole-program step, usually only in CI, pre-commit, or the editor — not on the hot dev-reload path).

Detailed Answer

tsc's type-checker is comparatively slow because it's whole-program — it needs to resolve types across many files. Single-file transpilers (esbuild, SWC, Babel's TypeScript preset) only look at one file at a time, strip the annotations, and emit JS — fast, but a successful build from these tools says nothing about whether your types are actually valid. The recommended setup uses esbuild/SWC/Babel for the fast dev transpile and bundling, while tsc --noEmit runs in parallel (CI, pre-commit, editor) as the actual type-safety guarantee.

Code Example

// package.json
{
  "scripts": {
    "dev": "vite",
    "typecheck": "tsc --noEmit"
  }
}
// tsconfig.json
{
  "compilerOptions": { "isolatedModules": true }
}

Senior Engineer Perspective

Name the failure mode explicitly: someone breaks a type, the dev server keeps hot-reloading fine (esbuild never checked types), and it's only caught later in CI or by another developer's editor. That gap is what "type-checking is a separate, parallel step" really means. Also mention isolatedModules — it exists precisely because single-file transpilers can't support certain TypeScript features (like const enum) that need whole-program information, so it forces your code to stay compatible with a transpile-only pipeline.

Q30. What are incremental builds and project references, and why do large TypeScript codebases need them?

ROI: ★★★☆☆ Frequency: Medium

Short Answer

tsc --incremental caches per-file build info (in a .tsbuildinfo file) so later type-checks only re-check changed files and their dependents. Project references split a large codebase into smaller linked TypeScript projects, each with its own tsconfig.json, so tsc can build/check them independently and incrementally — essential once a single flat tsc run across a whole monorepo takes minutes.

Detailed Answer

A composite project declares a references array pointing at the projects it depends on; tsc -b (build mode) orchestrates checking/building them in dependency order, skipping anything unaffected. This pairs naturally with monorepo task runners (Turborepo/Nx, Q40) caching each package's typecheck output independently. Without project references, a single flat tsconfig.json covering the whole repo forces a full re-check on any change, anywhere.

Code Example

// packages/ui/tsconfig.json
{
  "compilerOptions": { "composite": true, "declaration": true },
  "references": [{ "path": "../shared-types" }]
}

Senior Engineer Perspective

Project references require each referenced project to emit declaration files that dependents consume, which adds real constraints: no circular project references, and compiler options must stay consistent enough across projects for this to work. That's worth naming as the cost of the speed win, rather than presenting project references as a free upgrade.

Q31. What are declaration files, and why does type-check speed matter at scale?

ROI: ★★★☆☆ Frequency: Low-Medium

Short Answer

When publishing a library or using project references, tsc emits .d.ts declaration files describing the public API's types — what lets a consuming TypeScript project get autocomplete and type-checking against your compiled JS without re-checking your source. Slow type-checking/declaration generation directly taxes CI time and editor responsiveness as a codebase grows.

Detailed Answer

Declaration emit (tsc --emitDeclarationOnly, or a bundling tool like tsup/rollup-plugin-dts that rolls all declarations into one file) is what makes a compiled JS library still feel type-safe to consumers. A missing or broken .d.ts produces "implicitly has an any type" errors downstream. Tools like API Extractor go further, validating and rolling up a library's entire public API surface. skipLibCheck is a common pragmatic speed lever — it skips re-checking dependencies' own .d.ts files, since you rarely need to validate a third-party library's types, only your own code against them.

Senior Engineer Perspective

A senior engineer profiles tsc (via --extendedDiagnostics or --generateTrace) rather than guessing at what's slow before reaching for skipLibCheck or project references — knowing the profiling tools exist, not just the mitigations, is the differentiator.

Q32. How do target, module, and lib in tsconfig interact with your actual bundler?

ROI: ★★★☆☆ Frequency: Medium

Short Answer

target controls what JS syntax level tsc assumes/emits, module controls module syntax (commonjs/esnext/nodenext), and lib controls which built-in type definitions (DOM, ES2022, etc.) are available. Misconfiguring these against what your bundler actually does is a common source of confusing build errors, because in a bundler-driven setup tsc is usually only there to type-check, not to produce the shipped JS.

Detailed Answer

Concrete mismatches: setting target too low causes tsc to downlevel syntax the bundler is going to transform again anyway (wasted or conflicting work); module: commonjs in a project actually bundled as ESM by Vite can cause spurious import.meta errors; a missing "DOM" in lib causes false errors on browser globals in a project that also targets Node APIs. The modern recommendation: let the bundler (esbuild/SWC/Babel) own actual syntax transpilation entirely, set tsc to noEmit, and pick target/lib to roughly match your real runtime — since in this setup tsc exists purely for type-checking (Q29), not for producing shipped output.

Senior Engineer Perspective

Asking a candidate to trace exactly where JSX or optional chaining actually gets compiled in their last project is a great way to test whether they understand their own pipeline versus having copy-pasted a tsconfig. "Who actually transpiles this file" should have one clear answer, not "both tsc and the bundler, hopefully consistently."

SECTION 9 - PUBLISHING LIBRARIES

Q33. What do the package.json exports, main, module, and types fields do?

ROI: ★★★★☆ Frequency: Medium-High

Short Answer

main is the legacy CommonJS entry point, module is the (non-standard but widely respected) ESM entry point bundlers use for tree-shaking, types points at the root .d.ts, and exports is the modern, standards-based field that maps subpaths to conditional entry points (import/require/types) — and critically, restricts what a consumer can import to exactly what's listed.

Detailed Answer

When present, exports takes priority over main/module in modern Node and bundlers, and supports multiple conditions per subpath so a single specifier resolves differently depending on whether the consumer is doing import or require. It also enforces encapsulation: a consumer can no longer do a deep import like import 'lib/dist/internal/util' unless that subpath is explicitly exposed — a real, breaking change for any existing consumer relying on deep imports.

Code Example

{
  "name": "my-lib",
  "main": "./dist/index.cjs",
  "module": "./dist/index.mjs",
  "types": "./dist/index.d.ts",
  "exports": {
    ".": {
      "types": "./dist/index.d.ts",
      "import": "./dist/index.mjs",
      "require": "./dist/index.cjs"
    },
    "./styles.css": "./dist/styles.css"
  }
}

Senior Engineer Perspective

Adding an exports field to a previously exports-less package is technically a breaking change for anyone deep-importing internals — library authors ship it in a major version bump, and often keep a legacy main/module fallback for older tooling that doesn't yet understand exports conditions.

Q34. How do you produce dual ESM+CJS output for a library, and how does that differ from bundling an app?

ROI: ★★★★☆ Frequency: Medium

Short Answer

A library must work across many unknown consumer environments (old CJS-only scripts, modern ESM bundlers, browsers), so authors bundle with tools purpose-built for that — Rollup or the Rollup/esbuild-powered tsup — configured to emit both CJS and ESM builds. An app bundler (Webpack/Vite) instead optimizes for one known deployed target, so it bundles once, code-splits, and targets specific browsers.

Detailed Answer

A library bundler must produce clean, tree-shakeable output in multiple module formats simultaneously, and — critically — must keep the library's own dependencies external (not inlined), letting the consumer's own bundler resolve them, rather than bundling your own React copy into your output (a classic cause of the duplicate-React bug from Q28). tsup is esbuild-powered and is the fast, low-config modern default for this; Rollup remains common when you need finer output control.

Code Example

// tsup.config.ts
export default {
  entry: ['src/index.ts'],
  format: ['cjs', 'esm'],
  dts: true,
  external: ['react', 'react-dom'],
};

Senior Engineer Perspective

The concept to name explicitly is "externalize your dependencies" — bundling your own copy of a singleton dependency into published output is a classic mistake, and it's exactly what causes duplicate React instances downstream.

Q35. Peer dependencies vs regular dependencies — how do you decide, and what goes wrong if you get it wrong?

ROI: ★★★★☆ Frequency: Medium

Short Answer

dependencies are packages your library needs and can safely have its own copy of. peerDependencies declare a package your library expects the consuming app to already provide a single shared copy of (React, react-dom). Getting this wrong for a singleton dependency causes duplicate-instance bugs, or unnecessarily bloats every consumer's install.

Detailed Answer

npm's behavior around peer dependencies changed over time — older npm only warned about unmet peers, npm 7+ auto-installs them — and peerDependenciesMeta lets you mark a peer as optional. The rule of thumb: anything with meaningful singleton/shared state (React, a router's context, a CSS-in-JS runtime) → peerDependency; anything purely internal, implementation-detail (a small utility, a specific parser) → regular dependency.

Senior Engineer Perspective

Tie this directly back to Q28's duplicate-React bug — the root cause is very often a library author using a regular dependency instead of peerDependency for React, so every consumer of that library silently gets its own bundled React copy.

Q36. How do you bundle a component library while keeping React external?

ROI: ★★★★☆ Frequency: Medium

Short Answer

Mark React (and other singletons) as external in the bundler config (Rollup's external, Webpack's externals) so the output references the consumer's own React instead of embedding a copy — combined with declaring React as a peerDependency (Q35) so npm enforces that a compatible shared version actually gets installed.

Detailed Answer

Forgetting to externalize is the single most common reason a published component library breaks a consumer's app with "invalid hook call" or "multiple React instances" errors — and it's especially insidious because it works fine inside the library's own dev/test environment, where there's naturally only one React, and only breaks once actually consumed by an app that brings its own.

Code Example

// rollup.config.js
export default {
  external: ['react', 'react-dom'],
  output: {
    format: 'umd',
    globals: { react: 'React', 'react-dom': 'ReactDOM' },
  },
};

Senior Engineer Perspective

Test a library via npm link, a local Verdaccio registry, or yalc against a real consumer app before publishing — specifically to catch externalization mistakes, since unit tests inside the library's own repo will never surface this class of bug.

Q37. What does the sideEffects field do, and how does it interact with a library's CSS file?

ROI: ★★★☆☆ Frequency: Medium

Short Answer

A published library should set "sideEffects": false so consuming bundlers can safely tree-shake unused exports — but if the library also ships a CSS file (imported like import 'mylib/dist/style.css'), that file must be excluded from the blanket false (listed explicitly), since importing it has an intentional visual effect the bundler must never eliminate.

Detailed Answer

This connects directly to Q6's tree-shaking mechanics: a consumer bundler trusts the sideEffects field at face value. Declaring false when a file actually has side effects (global CSS, a polyfill import) causes the bundler to silently drop needed code — a bug that typically only shows up in a consumer's production build, since dev builds often skip the more aggressive tree-shaking passes that trigger it.

Code Example

{
  "sideEffects": ["*.css", "./src/polyfills.js"]
}

Senior Engineer Perspective

This is a subtle but real production-breaking mistake. A senior candidate mentions testing an actual production build of a real consumer app before shipping a sideEffects change, not just relying on the library's own test suite.

SECTION 10 - MONOREPO TOOLING DEEP DIVE

Q38. What does the workspace: protocol do, and how does it interact with version management?

ROI: ★★★★☆ Frequency: Medium

Short Answer

The workspace: protocol (npm/pnpm/yarn workspaces) lets one package depend on a sibling package by always resolving to the local on-disk version instead of fetching from the registry — workspace:* always uses the local version, while workspace:^ gets rewritten to a real semver range at publish time.

Detailed Answer

Without this, package A depending on sibling package B would need B published to npm and version-bumped before A could pick up a change — defeating the point of a monorepo's atomic cross-package commits. At publish time, release tooling (Changesets, Q39) rewrites workspace: ranges into real semver ranges so the published package.json is valid outside the monorepo.

Senior Engineer Perspective

workspace: is a monorepo-local convenience only — a published package.json must never literally contain workspace:*. Forgetting that the publish step is responsible for this rewrite breaks installs for anyone consuming your package outside the monorepo.

Q39. How does Changesets version and publish multiple interdependent packages together?

ROI: ★★★★☆ Frequency: Medium

Short Answer

Each PR that changes a package adds a small markdown "changeset" declaring which packages changed and at what bump level (patch/minor/major). A release step aggregates pending changesets, bumps each affected package's version, updates its changelog, rewrites workspace: ranges to real versions, and publishes — solving "how do we version and release N interdependent packages together" without hand-tracking every consumer's bump.

Detailed Answer

The workflow: a contributor runs a CLI to add a changeset alongside their PR; on merge, a bot/CI job aggregates pending changesets into a "Version Packages" PR showing every pending bump; merging that PR triggers the actual npm publish. Changesets also propagates bumps automatically — if package A depends on package B and B gets a patch, A may need at least a patch too to remain valid, and Changesets computes this dependency-aware cascade for you.

Code Example

---
"ui-components": minor
"design-tokens": patch
---

Add a new `Tooltip` component and fix token rounding.

Senior Engineer Perspective

Contrast this with a single repo-wide version number, which is fine for an app monorepo where every package deploys together, versus independently-versioned published packages, which genuinely need this kind of per-package semver tracking. Knowing which model your monorepo actually needs is the judgment call interviewers are probing for.

Q41. What hoisting/resolution pitfalls are specific to workspaces (as opposed to a single-package project)?

ROI: ★★★☆☆ Frequency: Medium

Short Answer

Workspace package managers hoist shared dependencies to the repo root node_modules, which can let one package accidentally resolve a dependency actually declared only by a sibling package — a workspace-level phantom dependency. It works locally until hoisting shifts (the dependency is removed elsewhere in the repo) and the "borrowing" package suddenly breaks.

Detailed Answer

pnpm's stricter workspace linking (each package only sees its own declared dependencies plus true root hoists, not accidental sibling dependencies) catches this class of bug much earlier than npm/yarn's more permissive hoisting. The safe practice: every package should explicitly declare every dependency it imports, even ones "obviously" present because a sibling package happens to use them.

Senior Engineer Perspective

This is exactly why pnpm has become the default choice for new monorepos specifically — stricter workspace dependency isolation — reinforcing Q11's earlier point, but now scoped to the monorepo-specific failure mode rather than a single-project one.

SECTION 11 - CI BUILD PERFORMANCE

Q42. How do you cache dependencies and build outputs across CI runs?

ROI: ★★★★☆ Frequency: Medium-High

Short Answer

CI systems can cache the package manager's store/node_modules keyed by a hash of the lockfile, and separately cache build outputs (e.g. .next/cache, tsc's .tsbuildinfo) keyed by relevant source hashes — so a run that doesn't change dependencies or that source skips the expensive install/build step entirely.

Detailed Answer

Cache key design matters most: hash the lockfile for the dependency cache so it invalidates exactly when dependencies change, not on every commit. pnpm's content-addressable store caches especially well since identical package versions across many restores are literally the same files on disk. Watch for cache poisoning — a corrupted cache silently reused across runs — and include a cache-busting version segment in the key you can bump manually when needed.

Code Example

- uses: actions/cache@v4
  with:
    path: ~/.pnpm-store
    key: pnpm-${{ hashFiles('**/pnpm-lock.yaml') }}

Senior Engineer Perspective

Caching only pays off if invalidation is correct. A strong answer includes a specific incident: a stale or bad cache caused a confusing CI failure, and how the key strategy was fixed — this connects directly to Q51's "works locally, fails in CI" debugging.

Q43. What are matrix builds, and when are they worth the extra CI cost?

ROI: ★★★☆☆ Frequency: Medium

Short Answer

A CI matrix runs the same job across a cartesian product of dimensions (Node versions, OSes, browser targets) in parallel, catching environment-specific breakage — a Node bump breaking a native dependency, a Windows-only path bug — that a single-environment CI run would never surface.

Detailed Answer

The tradeoff is cost: a matrix multiplies CI minutes by every combination. Teams commonly scope the full matrix to main/release branches or a nightly schedule, and run a reduced single-environment check on every PR for speed. Fail-fast behavior and flaky tests interact badly with large matrices — one flaky test now fails N times instead of once, amplifying noise.

Code Example

strategy:
  matrix:
    node-version: [18, 20, 22]
    os: [ubuntu-latest, windows-latest]

Senior Engineer Perspective

Matrices are for catching environment-specific bugs, not a substitute for making CI itself fast. Teams that need both often run a fast single-config check on every push and reserve the full matrix for a schedule or pre-release gate.

Q44. Mechanically, how do monorepo task runners skip unaffected packages in a specific CI run?

ROI: ★★★★☆ Frequency: Medium

Short Answer

Turborepo/Nx diff the current branch against a base ref (usually the merge-base with main), map the changed files to owning packages, walk the dependency graph forward to find dependents that also need re-checking, then intersect that set with the requested task (e.g. only test) — combined with remote caching, a CI run touching one leaf package can skip building/testing dozens of unrelated packages entirely.

Detailed Answer

Step by step: git diff against the base branch → map changed files to the packages that own them → walk the project graph forward to include every dependent that could be affected → intersect with the task actually being requested → execute exactly that subset, pulling cached results for everything else. Contrast this with a naive CI script that just runs npm test in every package unconditionally, which scales linearly (or worse) with repo size regardless of a change's actual blast radius.

Senior Engineer Perspective

Name a concrete failure mode teams hit early: an "affected" calculation that's too narrow silently skips a package that should have been tested, usually because of an implicit runtime dependency (like a shared config file) the graph doesn't model. Validate the affected-detection logic itself occasionally — don't just trust it blindly.

Q45. How do task-graph parallelism and test sharding differ as CI parallelization strategies?

ROI: ★★★☆☆ Frequency: Low-Medium

Short Answer

Task-graph parallelism (a monorepo task runner runs independent packages' builds/tests concurrently, respecting only real dependency-order constraints) exploits your repo's dependency structure; test sharding (splitting one large test suite's files across N CI workers that run concurrently, then merging results) exploits your test suite's independence — a different axis entirely, often combined.

Detailed Answer

A task runner decides what can run in parallel by looking at which tasks have no unmet dependsOn edge. A test runner shard (Jest's --shard, Vitest's equivalent) statically or dynamically distributes test files across workers to balance wall-clock time — timing-based shard balancing (using historical test durations) is more effective than a naive file-count split, since test files vary wildly in how long they take.

Senior Engineer Perspective

Sharding only helps if your CI infrastructure can actually provision that many parallel machines cheaply. Below a certain team/repo size, the coordination and infra overhead of many shards isn't worth it compared to simply making the test suite itself faster.

SECTION 12 - MODULE RESOLUTION

Q46. How does Node's module resolution algorithm differ from a bundler's?

ROI: ★★★★☆ Frequency: Medium-High

Short Answer

Both resolve an import specifier to a file, but differ on extension handling (Node ESM requires exact extensions; bundlers auto-resolve extensionless imports), and on package.json exports conditions (Node understands "node"/"import"/"require"/"default"; bundlers add their own conditions, like "browser", that Node doesn't know about).

Detailed Answer

Under native Node ESM, you must write import './util.js' with the exact extension — Node will not guess it. Webpack/Vite instead try a configured list of extensions (.tsx, .ts, .jsx, .js, .json) against an extensionless import. Both walk up parent node_modules directories the same way when resolving a bare specifier. On exports conditions, bundlers let you configure which conditions to prefer (resolve.conditions) beyond what Node itself recognizes, since a bundler may need to pick a browser-targeted entry point Node never would.

Senior Engineer Perspective

This explains a genuinely common confusion: code that runs fine bundled (the bundler guessed the extension) fails when run directly under Node — e.g. a build script, or an SSR entry executed without a bundler — with an exact "Cannot find module './util'" error, because Node ESM doesn't guess extensions the way a bundler does.

Q47. What are the most common root causes of a "cannot find module" error, beyond a plain typo?

ROI: ★★★★☆ Frequency: High

Short Answer

Beyond a genuine typo: a missing file extension under strict ESM resolution (Q46), a package's exports field not exposing the subpath you're importing, a case mismatch between the import string and the actual filename (fails only on case-sensitive filesystems), and a dependency simply not installed — a stale lockfile, or a phantom dependency (Q11/Q41) that resolved before a hoisting change and now doesn't.

Detailed Answer

  • Typo or wrong relative path.
  • Case sensitivity — works on your machine (macOS/Windows), fails in a Linux Docker/CI environment.
  • Missing extension in a strict ESM context.
  • Trying to deep-import a subpath a library's exports field blocks (Q33).
  • A phantom dependency that happened to resolve before a hoisting change.
  • Mixed module systems — a CJS-only tool trying to require() an ESM-only package.

Senior Engineer Perspective

This question tests debugging methodology, not memorized trivia. A strong answer walks the checklist roughly in order of likelihood rather than guessing randomly, and mentions reproducing the failure in the actual failing environment (e.g. a matching Docker image) rather than only debugging locally.

Q48. How do tsconfig path aliases relate to your bundler's alias config, and why can they drift apart?

ROI: ★★★★☆ Frequency: Medium

Short Answer

Path aliases (e.g. @/components/Button) are a pure editor/type-checking construct in tsconfig's paths — TypeScript doesn't rewrite anything at runtime — so the actual bundler (Webpack's resolve.alias, Vite/Rollup's resolve.alias) must be configured separately with the equivalent mapping, or the code type-checks fine but fails to resolve at build/run time.

Detailed Answer

tsconfig paths only affects tsc's type resolution and editor autocomplete — it has zero effect on Babel, esbuild, SWC, or the bundler's own module resolution. Teams either configure both places manually in parallel (error-prone, easy to drift when one is updated and the other forgotten) or use a plugin that reads tsconfig paths and auto-derives the bundler config from it (vite-tsconfig-paths, tsconfig-paths-webpack-plugin) so there's one source of truth.

Code Example

// tsconfig.json
{
  "compilerOptions": {
    "paths": { "@/*": ["./src/*"] }
  }
}

// vite.config.ts — must be kept in sync manually, OR use vite-tsconfig-paths
export default {
  resolve: { alias: { '@': '/src' } },
};

Senior Engineer Perspective

"Why does this alias work in my editor but throw at runtime" is a real, common bug this question is testing for. Naming the single-source-of-truth plugin approach is the stronger answer over "just configure both manually and remember to keep them in sync."

Q49. How do circular dependencies get detected and resolved?

ROI: ★★★☆☆ Frequency: Medium

Short Answer

A circular dependency (A imports B, B imports A) can work or silently break depending on evaluation order and what's accessed at module-init time. Bundler/lint plugins (eslint-plugin-import's no-cycle, Webpack's circular-dependency-plugin) can detect cycles, but generally can't fix them for you — the fix is structural.

Detailed Answer

The concrete failure: module A, while initializing, imports a named export from B; B hasn't finished initializing yet (because B's own top-level code imports A, and we're already inside evaluating A) so the export is temporarily undefined. This typically surfaces as "cannot read property of undefined" only in certain call orders, making it look flaky. ESM's live-binding semantics tolerate more circularity than CJS's snapshot-at-require-time semantics, but both can hit this. Fixes: extract the shared piece both modules need into a third module neither has a cycle with, or defer the cross-reference to inside a function body (lazy access at call time) instead of at module top level.

Senior Engineer Perspective

Circular dependencies are usually a sign of unclear module boundaries/responsibilities, not just a technical resolution puzzle. The durable fix is restructuring (extracting shared code) rather than reordering imports and hoping — reordering just moves the fragility around instead of removing it.

Q50. Why do case-sensitivity issues in module resolution only appear on some machines?

ROI: ★★★☆☆ Frequency: Medium

Short Answer

macOS and Windows filesystems are case-insensitive (or case-preserving-but-insensitive) by default, so an import with the wrong casing (import './Button' when the file is button.tsx) resolves fine locally — but Linux CI/production containers are case-sensitive, so the same import fails there. It's one of the most common "works on my machine, fails in CI" causes.

Detailed Answer

It's insidious specifically because the bug is invisible in local dev on the two most common developer OSes, only surfacing once code reaches a case-sensitive environment. Mitigation: an ESLint rule (eslint-plugin-import's no-unresolved paired with a case-sensitive resolver, or a dedicated plugin like eslint-plugin-case-sensitive-paths) that enforces exact-case imports even on a case-insensitive dev machine, catching it before CI does.

Senior Engineer Perspective

Recommend actually testing locally inside the same Linux container image CI/prod use, rather than relying solely on lint rules — it's the fastest way to catch this whole class of CI-only filesystem/OS difference, not just casing specifically.

SECTION 13 - DEBUGGING BUILD FAILURES

Q51. What are the most common causes of "it works locally but fails in CI"?

ROI: ★★★★★ Frequency: High

Short Answer

The recurring culprits: case-sensitive filesystem differences (Q50), a stale or manually-edited lockfile that doesn't match package.json (CI installs with --frozen-lockfile/npm ci and fails loudly where a local npm install would silently update it), missing environment variables/secrets present in your local .env but not configured in CI, and Node/package-manager version mismatches between your machine and the CI image.

Detailed Answer

  • Lockfile drift — always run the exact CI install command locally (npm ci, not npm install) before pushing, to catch it early.
  • Missing env vars — keep a committed .env.example and a CI secrets checklist.
  • Node version mismatch — pin via the engines field plus a .nvmrc/Volta config the CI workflow reads from, so CI and local always agree on the exact version.

Code Example

// package.json
{ "engines": { "node": ">=20.0.0 <21.0.0" } }

// GitHub Actions
- uses: actions/setup-node@v4
  with:
    node-version-file: '.nvmrc'

Senior Engineer Perspective

The meta-skill interviewers want to hear: make local reproduce CI exactly (same install command, same Node version, ideally the same container image) rather than debugging blind by pushing commits and waiting on CI logs. That iteration loop is what separates fast debugging from slow guessing.

Q52. How do you debug a production build that breaks while the dev build works fine?

ROI: ★★★★☆ Frequency: Medium-High

Short Answer

Production-only failures usually trace to minification renaming something relied on by name (e.g. a class/function name string-matched by some library), dead-code elimination stripping something with a side effect the bundler didn't know about, or a mode-specific code path (Q8, Q54) that's simply never exercised in dev.

Detailed Answer

Debugging approach: reproduce with a local production build served by a static server (not the dev server) first. If minification is suspected, temporarily disable it (or use a "readable" production mode) to get a legible stack trace via the shipped source map. Check for code relying on Function.prototype.name, class names, or reflection that minification would rename. Check for NODE_ENV-gated code paths — many libraries, React included, historically behave differently or strip warnings specifically in production builds.

Senior Engineer Perspective

Always keep source maps available — even if not publicly served, uploaded to an error tracker — specifically so a prod-only bug's real stack trace is recoverable instead of a wall of minified single-letter variable names.

Q53. How do you pin and enforce a consistent Node version across a team and CI?

ROI: ★★★☆☆ Frequency: Medium

Short Answer

The engines field in package.json declares a supported Node (and package manager) version range that npm/pnpm can warn or hard-fail on if mismatched. An actual version manager — Volta or nvm — reads a version file (or Volta's own package.json pin) to switch the active Node version per-project, preventing drift between developers' machines and CI.

Detailed Answer

engines is declarative — it doesn't itself change what Node you're running, only checks it. Volta pins and auto-switches the real running binary the moment you cd into the project; nvm requires manually running nvm use, which is easy to forget. For teams, Volta is generally recommended because it removes the manual-switch step entirely, eliminating the "I forgot to switch Node versions" class of bug.

Senior Engineer Perspective

Pair this with CI directly — the CI workflow's Node setup step should read the same version source (engines or .nvmrc) rather than hardcoding a separate version in the CI YAML, otherwise the two configs drift independently over time and you're back to the original problem.

Q54. Why can an app behave differently between a dev build and a production build, beyond just being slower?

ROI: ★★★★☆ Frequency: Medium

Short Answer

Many libraries — React chief among them — ship code gated on process.env.NODE_ENV checks (extra warnings, dev-only invariants) that bundlers string-replace and then dead-code-eliminate in production builds. A dev-only warning disappearing in prod is expected; a genuine behavior difference (a bug that reproduces only in one mode) needs to be traced to the specific NODE_ENV-gated branch causing it.

Detailed Answer

Mechanically: DefinePlugin/import.meta.env string-replaces process.env.NODE_ENV with the literal "production", then the minifier's dead-code elimination sees if (false) { ... } and removes the whole block. This is also why forgetting to set NODE_ENV correctly in a custom deploy pipeline is a classic bug — React left running in "development" mode in production is slower, prints verbose console warnings, and can even behave incorrectly if some code assumes development-only branches were stripped.

Senior Engineer Perspective

A fast, concrete first check: React DevTools visibly flags an app running in development mode with a warning banner — confirming or ruling out this whole class of bug takes seconds and should happen before diving into deeper debugging.

SECTION 14 - SERVER/CLIENT BUNDLING & MODERN TEST TOOLING

Q55. How does a framework like Next.js enforce the server/client bundling boundary at build time?

ROI: ★★★★★ Frequency: High

Short Answer

A full-stack React framework builds separate bundles from the same codebase — a server bundle (can use Node APIs, database clients, secrets) and a client bundle (ships to the browser, must exclude anything server-only) — enforced via conventions like the "use client" directive marking a boundary, and a package like server-only that throws a build error if its import ever reaches the client graph.

Detailed Answer

Everything is a Server Component by default in the app router. "use client" at the top of a file marks that module — and everything it imports — as belonging to the client graph from that point down. The bundler does a static analysis pass to keep server-only code (direct database queries, fs access, secrets read via unprefixed process.env) out of the client bundle. The server-only package adds a trip-wire beyond the framework's own static analysis, throwing immediately if it's ever accidentally imported client-side.

Code Example

// app/actions.ts
import 'server-only';
export async function getSecretConfig() {
  return process.env.DB_PASSWORD; // safe: this file can never reach the client bundle
}

// app/Counter.tsx
'use client';
export default function Counter() { /* interactive component */ }

Senior Engineer Perspective

This is a build-enforced security boundary, not just an organizational convention. A leaked secret from confusing this boundary — e.g. importing a server config module from a client component through a shared barrel file — is a real, shipped-to-production class of bug the framework works hard to catch at build time, but it isn't foolproof against every pattern.

Q56. What are the build implications of React Server Components?

ROI: ★★★★☆ Frequency: Medium-High

Short Answer

RSC means the build pipeline produces output for two different execution environments from one component tree — a server environment that renders Server Components to a serialized "flight" wire format (element trees plus references to client components, not HTML), and a client environment that hydrates only the client-component islands within that stream.

Detailed Answer

This changes what "one build" means: the build produces a server bundle capable of executing Server Components — which never ship their code to the client at all, contributing genuinely zero bytes to the client bundle — and a separate client bundle containing only Client Components' code plus the runtime needed to hydrate/interleave them with the streamed server output. This is fundamentally different from traditional SSR, where the server renders HTML from the same component code that then fully re-runs on the client during hydration.

Senior Engineer Perspective

The concrete "why this matters" answer is bundle size, not architectural taste: Server Components let you ship substantially less client JS for content-heavy trees, since data-fetching components that never need interactivity contribute zero bytes to the client bundle. Contrast this clearly with old SSR's "same code runs twice" model when asked to explain the actual performance motivation.

Q57. Why do Vite projects default to Vitest instead of Jest, from a build-tooling perspective?

ROI: ★★★★☆ Frequency: Medium

Short Answer

Vitest reuses your existing vite.config.ts — same plugins, same esbuild-powered transform, same aliasing/env handling — so a Vite project's test runner shares its transform pipeline with its dev/build pipeline. Jest, historically paired with Babel/ts-jest, needs its own separate transform configuration that can drift from your actual build config over time. (Testing mechanics — matchers, mocking APIs, RTL patterns — are largely Jest-compatible and covered in depth elsewhere; this is purely the build/config-sharing angle.)

Detailed Answer

The practical payoff: import.meta.env, path aliases, JSX transform, and CSS handling all "just work" the same way in tests as in the app, because Vitest literally reuses vite.config.ts — versus Jest needing a parallel babel-jest/ts-jest config that can silently diverge from the app's real Babel/SWC setup as the project evolves (a plugin added to the app build but never mirrored into the Jest config, for instance).

Senior Engineer Perspective

Know the one real gotcha: Vitest still runs in Node (or a simulated jsdom/happy-dom environment), not an actual browser — the same fundamental limitation Jest has. This is purely a build/config-sharing win, not a "tests now run in a real browser" win; genuine browser-environment testing requires a separate tool like Playwright or Cypress component testing.

Q58. What bundling constraints does an edge or serverless runtime impose?

ROI: ★★★☆☆ Frequency: Medium

Short Answer

Edge runtimes (Vercel Edge, Cloudflare Workers) and serverless functions impose constraints beyond a normal Node server: no full Node.js API surface (edge runtimes expose only a Web-standard-API subset — no fs/net), strict cold-start-driven bundle size limits, and every function needing its own self-contained bundle rather than sharing dependencies in memory the way a monolithic server would.

Detailed Answer

The build has to change accordingly: a per-route/per-function bundling step traces exactly which files each server function needs via its module graph and produces a minimal standalone bundle per function, rather than shipping the whole node_modules. Dependencies using Node-only APIs either need edge-compatible alternatives or force that route back onto a Node.js (not edge) runtime. Oversized function bundles hit hard platform size limits and materially worsen cold start time even while still under the limit.

Senior Engineer Perspective

"Can I run this on the edge" really means "does every dependency in this route's module graph avoid Node-only APIs" — often not obvious until the build fails or a deploy is rejected for size. Check a library's edge-runtime compatibility explicitly rather than assuming it, especially for anything touching crypto, streams, or file access.

Q59. What are framework-specific build outputs like standalone output and per-route serverless functions, and why do they exist?

ROI: ★★★☆☆ Frequency: Medium

Short Answer

Modern full-stack React frameworks shape their build output around the deployment target, not just "a bundle." Next.js's standalone output traces the minimal set of files/dependencies actually needed to run the server (for a small Docker image), and can additionally emit one bundle per serverless/edge function (one per route needing server rendering) rather than one monolithic server bundle.

Detailed Answer

The practical motivation: a naive Docker image copying the entire node_modules can be hundreds of megabytes and slow to build and deploy. Standalone output uses build-time dependency tracing (the same underlying mechanism as Q58's per-function tracing) to copy only what's actually reachable at runtime, dramatically shrinking image size. Per-route function splitting lets a platform scale and cold-start each route independently, instead of one huge cold-starting bundle for the entire app.

Code Example

// next.config.js
module.exports = {
  output: 'standalone',
};
// produces .next/standalone with a minimal server.js and only the
// dependencies actually traced as reachable at runtime.

Senior Engineer Perspective

This closes the loop on Q1 and Q3's theme — bundlers exist to shape what ships and how it loads — but applied at the deployment/runtime granularity rather than the browser-loading granularity. A senior engineer recognizes that build tooling's job doesn't stop at "produce a bundle for the browser"; it now also shapes server and edge deployment artifacts directly.
