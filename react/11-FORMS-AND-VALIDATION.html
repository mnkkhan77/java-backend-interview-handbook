SECTION 1 - CONTROLLED VS UNCONTROLLED

Q1. What is the difference between a controlled and an uncontrolled input, and when would you use each?

ROI: ★★★★★ Frequency: Extremely High

Short Answer

A controlled input keeps its value in React state — you pass value and update it in onChange, so React is the single source of truth. An uncontrolled input keeps its value in the DOM itself; you read it on demand via a ref (or on submit). Controlled gives you instant, reactive access to every keystroke at the cost of a render per keystroke; uncontrolled is cheaper and closer to native HTML but harder to react to live.

Detailed Answer

The distinction is about who owns the value. In a controlled input the value flows down from state and every change flows back up through onChange — a classic unidirectional loop. Because the rendered value always equals state, you can validate, format, mask, disable a submit button, or mirror the value elsewhere in real time.

An uncontrolled input lets the browser hold the value. You give it an initial value with defaultValue and later pull the current value out of the DOM node. This is essentially how a plain HTML form works, and it is what libraries like React Hook Form lean on for performance.

When to reach for each

  • Controlled — when the UI must react to input live: enabling/disabling buttons, live character counts, input masking/formatting, conditional fields, or driving other components from the value.
  • Uncontrolled — simple forms where you only need values at submit time, large forms where per-keystroke re-renders hurt, file inputs (which are always uncontrolled), and when integrating with non-React code.

A key rule: an input must be consistently controlled or uncontrolled across its lifetime. Switching from value={undefined} to a defined value triggers React's warning: "A component is changing an uncontrolled input to be controlled." The fix is to always pass a defined value (e.g. value={name ?? ""}).

Code Example

// Controlled: React state is the source of truth
function ControlledName() {
  const [name, setName] = React.useState("");
  return (
    <input
      value={name}
      onChange={(e) => setName(e.target.value)}
    />
  );
}

// Uncontrolled: the DOM holds the value, read via ref
function UncontrolledName() {
  const inputRef = React.useRef<HTMLInputElement>(null);
  const handleSubmit = (e: React.FormEvent) => {
    e.preventDefault();
    console.log(inputRef.current?.value); // read on demand
  };
  return (
    <form onSubmit={handleSubmit}>
      <input defaultValue="" ref={inputRef} />
      <button>Submit</button>
    </form>
  );
}

Project Example

On a checkout page, the credit-card field is controlled so we can apply a "#### #### #### ####" mask and show the card-network logo as the user types. The optional "delivery notes" textarea, by contrast, is uncontrolled — nobody needs to react to it live, so we just read ref.current.value at submit and avoid re-rendering the whole form on each keystroke.

Senior Engineer Perspective

Interviewers use this to see whether you understand the render cost, not just the API. Weak answers say "controlled is the React way, always use it." A senior answer acknowledges that controlled inputs re-render on every keystroke, that React Hook Form deliberately embraces the uncontrolled model to avoid this, and that file inputs cannot be controlled at all. The follow-up trap is the "controlled to uncontrolled" warning — be ready to explain that it comes from passing value={undefined} and is fixed by defaulting to an empty string.

Q2. What is the difference between defaultValue and value (and defaultChecked vs checked)?

ROI: ★★★★☆ Frequency: High

Short Answer

value makes an input controlled — React enforces it on every render. defaultValue only sets the initial value and then lets the DOM take over, making the input uncontrolled. The same pairing exists for checkboxes/radios: checked (controlled) vs defaultChecked (uncontrolled).

Detailed Answer

If you pass value without an onChange, React makes the field read-only and logs a warning, because the value can never change from state. If you pass both value and defaultValue, value wins and defaultValue is ignored. Use defaultValue only when you want the browser to manage the field after seeding it — the typical uncontrolled pattern.

A common real bug: developers want to prefill a form from server data but keep it controlled, and they set defaultValue={user.name}. Because the data arrives asynchronously, the initial render has an empty default, and when data loads the DOM value never updates. The correct controlled approach is value={name} with state seeded from the fetched data (via useEffect or React Hook Form's reset()).

Code Example

// WRONG: async data won't populate an uncontrolled field after mount
<input defaultValue={user?.name} />   // stays blank if user loads later

// RIGHT (controlled): seed state once data arrives
const [name, setName] = React.useState("");
React.useEffect(() => {
  if (user) setName(user.name);
}, [user]);
<input value={name} onChange={(e) => setName(e.target.value)} />

// Checkbox equivalents
<input type="checkbox" defaultChecked />              // uncontrolled
<input type="checkbox" checked={agreed}
       onChange={(e) => setAgreed(e.target.checked)} /> // controlled

Senior Engineer Perspective

The trap here is async prefill. Interviewers love to ask "you set defaultValue from a fetch and it's blank — why?" The answer: defaultValue is only read on the first render, so a value that arrives later is ignored. Mention that React Hook Form solves exactly this with reset(serverData) or the values prop, which resyncs the form when async data lands.

Q3. How do you handle many inputs with a single change handler?

ROI: ★★★★☆ Frequency: High

Short Answer

Give each input a name that matches a key in a state object, then use one handler that reads e.target.name and e.target.value and updates the object with a functional setState. This scales to any number of fields without writing a handler per input.

Detailed Answer

Storing all fields in a single object is idiomatic and keeps handlers DRY. Use the functional updater form (prev => ...) so batched updates never read a stale snapshot, and read type so checkboxes contribute a boolean rather than the literal string "on".

Beware nested objects: a shallow spread only copies the top level, so nested fields need a nested spread or a helper like immer. For anything beyond a handful of fields with real validation, prefer a form library — hand-rolling this quickly becomes a maintenance burden.

Code Example

function ProfileForm() {
  const [form, setForm] = React.useState({
    firstName: "",
    email: "",
    subscribe: false,
  });

  const handleChange = (e: React.ChangeEvent<HTMLInputElement>) => {
    const { name, value, type, checked } = e.target;
    setForm((prev) => ({
      ...prev,
      [name]: type === "checkbox" ? checked : value,
    }));
  };

  return (
    <form>
      <input name="firstName" value={form.firstName} onChange={handleChange} />
      <input name="email" value={form.email} onChange={handleChange} />
      <input name="subscribe" type="checkbox"
             checked={form.subscribe} onChange={handleChange} />
    </form>
  );
}

Senior Engineer Perspective

The computed-key pattern [name]: value is the crux — many candidates hardcode a setter per field. Follow-ups probe edge cases: checkboxes (use checked, not value), multi-selects (read selectedOptions), and number inputs (e.target.value is always a string — coerce it). Mentioning that every keystroke re-renders the whole form here is a good segue into performance and why RHF exists.

SECTION 2 - PERFORMANCE OF CONTROLLED FORMS

Q4. Why do controlled forms re-render on every keystroke, and how do you mitigate it?

ROI: ★★★★★ Frequency: Extremely High

Short Answer

Because each keystroke calls setState, and a state change re-renders the component that owns the state — plus its children unless memoized. For small forms this is invisible; for large forms or expensive children it causes jank. Mitigate by isolating state, memoizing children, moving to uncontrolled inputs, or using React Hook Form, which subscribes to fields instead of re-rendering the whole tree.

Detailed Answer

The re-render itself is usually cheap — React diffing a few inputs is fast. The problem is when the form component also renders heavy children (a rich text editor, a big list, a chart) that re-run their render on every character. Diagnose with the React DevTools Profiler before optimizing.

Mitigation ladder (cheapest first)

  • Isolate state — push each input's state down into its own small component so only that field re-renders (state colocation).
  • Memoize expensive siblings — wrap heavy children in React.memo so they skip renders when their props are unchanged.
  • Go uncontrolled — read values via refs at submit; zero re-renders while typing.
  • Use React Hook Form — it registers inputs as uncontrolled and only re-renders components that subscribe to a given field.
  • Debounce derived work — keep the input controlled but debounce the expensive side effect (search, validation), not the keystroke itself.

Code Example

// State colocation: only SearchBox re-renders on each keystroke,
// not the expensive <HugeResultsList /> sibling.
function Page() {
  return (
    <>
      <SearchBox />
      <HugeResultsList />   {/* unaffected by typing in SearchBox */}
    </>
  );
}

function SearchBox() {
  const [q, setQ] = React.useState("");
  return <input value={q} onChange={(e) => setQ(e.target.value)} />;
}

Senior Engineer Perspective

Junior answers jump straight to "memoize everything." A senior first says "measure it — most forms don't need this." Then they distinguish the render (cheap) from expensive children (the real cost) and explain state colocation as the primary lever. Bonus points for noting that React 19's compiler auto-memoizes many of these cases, reducing the need for manual memo/useCallback, and that RHF's whole selling point is sidestepping this problem via uncontrolled registration.

SECTION 3 - FORM LIBRARIES

Q5. Why is React Hook Form so popular, and how does register work?

ROI: ★★★★★ Frequency: Extremely High

Short Answer

React Hook Form (RHF) is popular because it keeps inputs uncontrolled — it registers each field with a ref and reads values from the DOM — so typing doesn't re-render the form. register(name) returns the ref, name, onChange, and onBlur props you spread onto an input, wiring it into the form with almost no boilerplate.

Detailed Answer

RHF wins on three axes: performance (uncontrolled inputs, subscription-based re-renders), ergonomics (minimal boilerplate, built-in validation, first-class TypeScript inference), and bundle size (small, zero dependencies). You call useForm() once to get register, handleSubmit, formState, reset, watch, setValue, and control.

register("email", rules) attaches a ref to the input and tracks it internally. On submit, handleSubmit collects values from the registered refs, runs validation, and calls your callback with typed data only if validation passes. Because reads come from the DOM, RHF avoids the per-keystroke render churn that plagues large controlled forms.

The trade-off: native inputs work by spreading register, but custom/third-party components that don't forward a ref must be wired through Controller or useController (Q6). Also, watch() does subscribe to changes and will re-render — use it deliberately.

Code Example

import { useForm } from "react-hook-form";

type FormValues = { email: string; password: string };

function LoginForm() {
  const {
    register,
    handleSubmit,
    formState: { errors, isSubmitting },
  } = useForm<FormValues>();

  const onSubmit = async (data: FormValues) => {
    await api.login(data); // called only if validation passes
  };

  return (
    <form onSubmit={handleSubmit(onSubmit)}>
      <input
        {...register("email", {
          required: "Email is required",
          pattern: { value: /^\S+@\S+$/, message: "Invalid email" },
        })}
      />
      {errors.email && <span role="alert">{errors.email.message}</span>}

      <input type="password" {...register("password", { required: true })} />

      <button disabled={isSubmitting}>Log in</button>
    </form>
  );
}

Project Example

We migrated a 40-field onboarding form from hand-rolled useState to RHF. The old version re-rendered the entire step on every keystroke and stuttered on low-end devices; after the migration, typing caused zero form re-renders, validation was declarative, and we deleted roughly 300 lines of change-handler boilerplate.

Senior Engineer Perspective

Interviewers want to hear "uncontrolled by default" — that single phrase signals you understand why RHF is fast, not just that it is. Follow-ups: how does RHF handle a component that hides its ref? (Controller). Does watch() hurt performance? (Yes — it subscribes; prefer useWatch scoped to a subtree). How do you prefill from the server? (reset(data) or the values prop, not defaultValues after mount).

Q6. What is the difference between useForm, Controller, and useController?

ROI: ★★★★☆ Frequency: High

Short Answer

useForm is the top-level hook that creates the form instance. Controller is a render-prop wrapper you use to connect controlled third-party components (MUI, Ant Design, react-select) that don't expose a ref for register. useController is the hook version of Controller for building your own reusable controlled field components.

Detailed Answer

register works only when you can spread its props (including a ref) directly onto a native input. Many UI-library components are controlled and expect value/onChange instead — they don't forward a DOM ref. That's where Controller comes in: it bridges RHF's uncontrolled core to a controlled component by giving you a field object (value, onChange, onBlur, ref, name) to hand to the component.

useController is the same bridge as a hook, ideal when you're authoring a design-system input wrapper (e.g. <TextField>) so consumers can just drop it into any RHF form. Use Controller/useController only when necessary — every controlled field re-renders on change, so keep native inputs on plain register.

Code Example

import { useForm, Controller } from "react-hook-form";
import Select from "react-select";

function TagPicker() {
  const { control, handleSubmit } = useForm<{ tags: Option[] }>();

  return (
    <form onSubmit={handleSubmit(console.log)}>
      <Controller
        name="tags"
        control={control}
        rules={{ required: "Pick at least one tag" }}
        render={({ field, fieldState }) => (
          <>
            <Select {...field} isMulti options={options} />
            {fieldState.error && <span>{fieldState.error.message}</span>}
          </>
        )}
      />
    </form>
  );
}

Senior Engineer Perspective

The tell here is knowing why Controller exists: register needs a forwarded ref, and most controlled UI components don't give you one. If a candidate wraps every field in Controller, that's a smell — it re-introduces the per-render cost RHF avoids. Senior answer: native inputs via register, controlled third-party components via Controller/useController, and prefer building one reusable useController-based wrapper over scattering render props everywhere.

Q7. How does Formik compare to React Hook Form?

ROI: ★★★★☆ Frequency: High

Short Answer

Formik was the dominant form library before RHF. It is controlled by default — form state lives in Formik's React state, so every keystroke re-renders the form — which makes large forms slower. RHF is uncontrolled by default, smaller, and generally faster. For new projects most teams now choose RHF; Formik remains common in legacy codebases and is largely in maintenance mode.

Detailed Answer

AspectFormikReact Hook Form
ModelControlled (state in React)Uncontrolled (refs / DOM)
Re-renders on keystrokeWhole form re-rendersIsolated / minimal
Bundle sizeLargerSmaller, zero deps
ValidationYup (built-in support), customAny schema via resolver, built-in rules
API styleComponents / render props (<Field>, <Formik>)Hooks (useForm)
TypeScriptWorkableExcellent inference
MomentumMaintenance modeActively developed, de facto standard

Formik's component-driven API (<Formik>, <Field>, <ErrorMessage>) reads nicely for small forms and pairs cleanly with Yup. But its controlled architecture is the reason RHF overtook it: on a large form, Formik's per-keystroke re-render becomes the bottleneck exactly where you feel it most.

Senior Engineer Perspective

Don't trash Formik — that reads as trend-chasing. The mature take: "Formik is fine and I'd keep it in an existing app; for greenfield I default to RHF for its uncontrolled model, smaller bundle, and TS inference." Being able to name the concrete architectural difference (controlled vs uncontrolled) rather than vague "RHF is better" is what separates the answers.

SECTION 4 - VALIDATION

Q8. How do you do schema validation with Zod or Yup, and what is the resolver pattern?

ROI: ★★★★★ Frequency: Extremely High

Short Answer

You define the form's shape and rules once as a schema (Zod or Yup), then plug it into the form library through a resolver — a small adapter that runs the schema and maps its errors into the library's error format. With Zod you also get a TypeScript type for free via z.infer, so the schema is the single source of truth for both runtime validation and static types.

Detailed Answer

Inline per-field rules (RHF's required, pattern) work but scatter validation logic and duplicate it against your types. A schema centralizes rules, supports cross-field constraints (e.g. "confirm password matches password"), and can be shared with the backend. RHF exposes this via @hookform/resolvers, which offers zodResolver, yupResolver, and adapters for Joi, Valibot, and others.

Zod vs Yup

  • Zod — TypeScript-first; the schema infers the type (z.infer<typeof schema>), so types and validation can never drift. Now the common default.
  • Yup — older, chainable API, deeply integrated with Formik historically; TypeScript support is decent but less seamless than Zod's inference.

The big payoff of Zod is that the schema drives the type. You write one signupSchema, derive type SignupForm = z.infer<typeof signupSchema>, and pass both into useForm — no manual interface to keep in sync.

Code Example

import { z } from "zod";
import { useForm } from "react-hook-form";
import { zodResolver } from "@hookform/resolvers/zod";

const signupSchema = z
  .object({
    email: z.string().email("Enter a valid email"),
    password: z.string().min(8, "At least 8 characters"),
    confirm: z.string(),
  })
  .refine((d) => d.password === d.confirm, {
    message: "Passwords must match",
    path: ["confirm"], // attach the error to the confirm field
  });

type SignupForm = z.infer<typeof signupSchema>;

function Signup() {
  const {
    register,
    handleSubmit,
    formState: { errors },
  } = useForm<SignupForm>({ resolver: zodResolver(signupSchema) });

  return (
    <form onSubmit={handleSubmit((data) => api.signup(data))}>
      <input {...register("email")} />
      {errors.email && <span role="alert">{errors.email.message}</span>}
      <input type="password" {...register("password")} />
      <input type="password" {...register("confirm")} />
      {errors.confirm && <span role="alert">{errors.confirm.message}</span>}
      <button>Create account</button>
    </form>
  );
}

Senior Engineer Perspective

The phrase interviewers listen for is "single source of truth." A senior answer highlights that Zod's z.infer unifies runtime validation and static types, and that the same schema can be reused on the server (e.g. in a Next.js route handler) so client and server agree on validity. Follow-up: cross-field validation — show you know .refine() with a path to attach the error to the right field. Know what a resolver actually is: an adapter mapping schema errors to formState.errors.

Q9. How do you handle asynchronous validation, such as checking username availability?

ROI: ★★★★☆ Frequency: High

Short Answer

Sync validation (format, length, required) runs instantly and locally. Async validation calls a server — e.g. "is this username taken?" — so it must be debounced, must handle out-of-order responses, and must show a pending state. In RHF you can return a Promise from a field's validate function, or run the check separately and set an error with setError.

Detailed Answer

Three problems define async validation quality:

  • Too many requests — validating on every keystroke hammers the server. Debounce (250–500ms) so you only check after the user pauses.
  • Race conditions — a slow response for "jo" can land after "john" and show the wrong result. Cancel stale requests (AbortController) or track a request id and ignore outdated ones. TanStack Query handles this for you if you validate through a query.
  • Feedback — show a spinner while checking and never block submit on an in-flight check without indicating it.

RHF supports a validate function that returns a Promise; it awaits the result and treats a returned string as the error message. For richer UX (debounce + spinner) many teams run the availability check as a separate debounced effect/query and call setError/clearErrors on the field.

Code Example

// Async field validation in React Hook Form
<input
  {...register("username", {
    required: "Username required",
    validate: async (value) => {
      const res = await fetch(`/api/username-available?u=${value}`);
      const { available } = await res.json();
      return available || "That username is taken";
    },
  })}
/>

// For debounce + race safety, prefer a query-based check:
const { data } = useQuery({
  queryKey: ["username", debouncedValue],
  queryFn: ({ signal }) => checkUsername(debouncedValue, signal), // aborts stale
  enabled: debouncedValue.length > 2,
});
// TanStack Query cancels superseded requests and caches results.

Senior Engineer Perspective

The differentiator is naming the race condition and its fix (AbortController / request id / a query cache), not just "debounce it." Interviewers also probe validation timing: async checks should typically fire on blur or after a debounce, not on every keystroke, and you should re-check server-side on submit because client validation is only UX — never trust it for correctness or security.

Q10. How do you debounce validation or expensive input-driven work?

ROI: ★★★☆☆ Frequency: Medium

Short Answer

Keep the input responsive (update state on every keystroke) but delay the expensive effect — validation, search, autosave — until the user pauses. Implement with a debounced value via useEffect + setTimeout cleanup, a reusable useDebouncedValue hook, or, in React 18+, useDeferredValue for render-deferral.

Detailed Answer

Debouncing separates "what the user sees" (instant) from "what the system does" (delayed). Never debounce the controlled value itself — that makes the input feel laggy. Instead debounce the derived value that feeds the effect.

Two modern tools: useDeferredValue lets React keep the input snappy while re-rendering an expensive dependent list at lower priority (no timer, concurrent-scheduling based). A classic timer-based debounce is still right for network calls, where you genuinely want to skip intermediate requests.

Code Example

function useDebouncedValue<T>(value: T, delay = 400): T {
  const [debounced, setDebounced] = React.useState(value);
  React.useEffect(() => {
    const id = setTimeout(() => setDebounced(value), delay);
    return () => clearTimeout(id); // cancel on the next keystroke
  }, [value, delay]);
  return debounced;
}

function Search() {
  const [q, setQ] = React.useState("");
  const debouncedQ = useDebouncedValue(q, 400);

  React.useEffect(() => {
    if (debouncedQ) runSearch(debouncedQ); // fires only after a pause
  }, [debouncedQ]);

  return <input value={q} onChange={(e) => setQ(e.target.value)} />;
}

Senior Engineer Perspective

The key insight is what you debounce: the side effect, not the input. Candidates who debounce the value make the field janky. Bonus depth: contrast timer-based debounce (best for network throttling) with useDeferredValue (best for keeping renders responsive), and note the cleanup function in useEffect is what actually cancels the pending timer.

Q11. How do you display validation errors accessibly?

ROI: ★★★★☆ Frequency: High

Short Answer

Associate the error message with its input using aria-describedby, mark the invalid field with aria-invalid="true", and put the message in a live region (role="alert" or aria-live) so screen readers announce it. Never signal errors with color alone, and move focus to the first invalid field on submit.

Detailed Answer

A visually shown error is invisible to a screen-reader user unless it's programmatically linked. The pattern:

  • Every input has a real <label> tied by htmlFor/id.
  • The error element has an id; the input references it with aria-describedby.
  • aria-invalid={!!error} exposes the invalid state to assistive tech.
  • The error container uses role="alert" (assertive) or aria-live="polite" so it's announced when it appears.
  • On a failed submit, move focus to the first error (RHF's setFocus or the shouldFocusError option does this).

Also validate at the right time: showing errors on every keystroke before the user finishes typing is hostile. A good default is validate on blur / on submit, then re-validate on change once a field already has an error (RHF: mode: "onTouched" with reValidateMode: "onChange").

Code Example

<label htmlFor="email">Email</label>
<input
  id="email"
  aria-invalid={errors.email ? "true" : "false"}
  aria-describedby={errors.email ? "email-error" : undefined}
  {...register("email")}
/>
{errors.email && (
  <p id="email-error" role="alert">
    {errors.email.message}
  </p>
)}

Senior Engineer Perspective

Accessibility is an easy way to stand out — most candidates render {error && <span>...</span>} and stop. A senior answer names aria-invalid, aria-describedby, and a live region, and adds the UX nuance of validation timing (onBlur/onSubmit, not aggressive onChange) plus focusing the first invalid field on submit. Mention that color-only error signaling fails WCAG.

SECTION 5 - ADVANCED PATTERNS & SUBMIT UX

Q12. How do you build dynamic forms with field arrays (add/remove rows)?

ROI: ★★★★☆ Frequency: High

Short Answer

Model the repeating section as an array in form state and render a row per item, each field namespaced by index (e.g. items.0.name). React Hook Form's useFieldArray gives you fields, append, remove, and move, and — crucially — a stable field.id to use as the React key so rows don't get mismatched on reorder.

Detailed Answer

Field arrays power invoices with line items, questionnaires, tag lists, and similar. The two hazards are (1) keys — never key rows by array index, because inserting/removing rows shifts indices and corrupts input state; use the library-provided stable id — and (2) validation, which the schema handles per element via z.array(itemSchema).

Hand-rolling this with useState is possible (setItems(prev => [...prev, blank])), but you must manage stable keys yourself. useFieldArray removes that footgun and integrates with RHF's validation and dirty-tracking.

Code Example

import { useForm, useFieldArray } from "react-hook-form";

function InvoiceForm() {
  const { register, control, handleSubmit } = useForm<{
    items: { name: string; qty: number }[];
  }>({ defaultValues: { items: [{ name: "", qty: 1 }] } });

  const { fields, append, remove } = useFieldArray({ control, name: "items" });

  return (
    <form onSubmit={handleSubmit(console.log)}>
      {fields.map((field, index) => (
        <div key={field.id}>  {/* stable id, NOT index */}
          <input {...register(`items.${index}.name`)} />
          <input type="number" {...register(`items.${index}.qty`)} />
          <button type="button" onClick={() => remove(index)}>Remove</button>
        </div>
      ))}
      <button type="button" onClick={() => append({ name: "", qty: 1 })}>
        Add item
      </button>
    </form>
  );
}

Senior Engineer Perspective

The interviewer is checking whether you know the React key rule under mutation. Using the array index as key here is the classic bug — remove row 1 and the value from row 2 appears to "stick" on the wrong row. Say explicitly: use field.id. Follow-up depth: nested field arrays, and the fact that append/remove mutate form state without re-rendering unrelated fields.

Q13. How do you build a multi-step form wizard, and where should the state live?

ROI: ★★★★☆ Frequency: High

Short Answer

Keep all form state in one place that outlives the individual steps — a single form instance or a shared store — and swap which step's fields are visible. Validate per step before advancing. Do not unmount a step and lose its data; either mount one form spanning all steps or persist each step's values into a parent/store as the user moves forward.

Detailed Answer

The core question is state ownership. Three common approaches:

  • Single RHF form across all steps — one useForm in a parent; each step renders a slice of the fields. State survives step changes automatically. Validate the current step's fields with trigger(["fieldA", "fieldB"]) before advancing.
  • Per-step form + lift on next — each step is its own form; on "Next" you validate and merge that step's values into parent state (or a context/Zustand store). Cleaner isolation, more plumbing.
  • Shared store (Zustand/context) — good when steps are far apart in the tree or you need to persist to localStorage for resume-later.

Persistence matters: wizards are long, so autosaving to localStorage or the server lets users resume. Also expose progress and allow going back without data loss — which is exactly why the state must live above the steps.

Code Example

function Wizard() {
  const methods = useForm<WizardData>({ defaultValues });
  const [step, setStep] = React.useState(0);

  const next = async () => {
    // validate only the current step's fields before advancing
    const fieldsByStep = [["name", "email"], ["address"], ["payment"]];
    const ok = await methods.trigger(fieldsByStep[step]);
    if (ok) setStep((s) => s + 1);
  };

  return (
    <FormProvider {...methods}>
      {step === 0 && <StepAccount />}
      {step === 1 && <StepAddress />}
      {step === 2 && <StepPayment />}
      {step > 0 && <button onClick={() => setStep((s) => s - 1)}>Back</button>}
      {step < 2
        ? <button onClick={next}>Next</button>
        : <button onClick={methods.handleSubmit(submitAll)}>Finish</button>}
    </FormProvider>
  );
}

Senior Engineer Perspective

"Where does the state live?" is the whole question. The junior mistake is a separate useState per step that gets wiped when the step unmounts. Senior answer: one form instance (or store) above the steps, per-step validation via trigger, and FormProvider/useFormContext so nested steps read the same form without prop drilling. Bonus: mention resume-later persistence and URL-synced step so refresh/back-button behave.

Q14. How do you handle file uploads in a React form?

ROI: ★★★☆☆ Frequency: Medium

Short Answer

File inputs are always uncontrolled — you cannot set a file input's value from React for security reasons, so you read e.target.files (or a ref) instead. Send the file with FormData and multipart/form-data, validate type/size on the client for UX, and always re-validate on the server. Track upload progress via XMLHttpRequest or a library, since fetch doesn't expose upload progress natively.

Detailed Answer

Key facts interviewers probe:

  • You can't do <input type="file" value={...}> — the browser blocks programmatic setting of the selected file, so file inputs are inherently uncontrolled. Read from files.
  • Use FormData and let the browser set the multipart/form-data boundary — do not manually set the Content-Type header.
  • Client-side checks (accepted extensions, max size, image dimensions via a preview) improve UX but are not security; the server must enforce limits.
  • For progress bars use XMLHttpRequest's upload.onprogress or a lib like axios; native fetch lacks upload progress.
  • Show a preview with URL.createObjectURL and revoke it on cleanup to avoid leaks.

In RHF, register the file input and read files in the submit handler, or validate size/type via a validate function.

Code Example

function AvatarUpload() {
  const { register, handleSubmit } = useForm<{ avatar: FileList }>();

  const onSubmit = async (data: { avatar: FileList }) => {
    const file = data.avatar[0];
    const body = new FormData();
    body.append("avatar", file);
    // Do NOT set Content-Type manually; the browser adds the boundary.
    await fetch("/api/upload", { method: "POST", body });
  };

  return (
    <form onSubmit={handleSubmit(onSubmit)}>
      <input
        type="file"
        accept="image/*"
        {...register("avatar", {
          validate: (list) =>
            !list?.[0] || list[0].size <= 2_000_000 || "Max 2 MB",
        })}
      />
      <button>Upload</button>
    </form>
  );
}

Senior Engineer Perspective

The one-line tell: "file inputs can't be controlled." If a candidate tries to bind value to a file input, that's a red flag. Follow-ups drill into FormData and the Content-Type mistake, upload progress (fetch can't do it — XHR can), and object-URL cleanup. Senior candidates also mention large-file strategies: presigned S3 URLs / direct-to-storage uploads and chunked/resumable uploads instead of routing big files through the app server.

Q15. How do you handle submit UX — loading state, disabling, and optimistic updates?

ROI: ★★★★☆ Frequency: High

Short Answer

Track a submitting flag (RHF gives you formState.isSubmitting), disable the submit button and show a spinner while the request is in flight to prevent double submits, and re-enable on completion. For snappy UX you can apply an optimistic update — reflect the change in the UI immediately and roll back if the request fails.

Detailed Answer

Robust submit handling covers several concerns:

  • Prevent double submission — disable the button (or guard on isSubmitting) so an impatient user can't fire two requests.
  • Feedback — spinner/label change ("Saving…"), and on failure surface a server error, ideally mapped back onto fields via setError for 422-style validation responses.
  • Success — reset the form (reset()), navigate, or show a toast. Reset also clears the dirty state.
  • Optimistic update — update local/cache state before the server confirms; on error, roll back. TanStack Query's onMutate/onError/onSettled, or React 19's useOptimistic, standardize this.

Only make writes optimistic when failure is rare and rollback is cheap and unsurprising (e.g. toggling a like). For a payment, wait for confirmation.

Code Example

const {
  register,
  handleSubmit,
  setError,
  formState: { isSubmitting },
} = useForm<FormValues>();

const onSubmit = async (data: FormValues) => {
  try {
    await api.save(data);          // isSubmitting is true while this awaits
  } catch (err) {
    // Map a 422 field error back onto the form
    setError("email", { message: "Email already in use" });
  }
};

<form onSubmit={handleSubmit(onSubmit)}>
  {/* fields... */}
  <button disabled={isSubmitting}>
    {isSubmitting ? "Saving…" : "Save"}
  </button>
</form>

Senior Engineer Perspective

Candidates often forget the double-submit guard entirely. Emphasize deriving the loading state from isSubmitting rather than a hand-rolled boolean that can desync. Follow-up: how do you show server-side validation errors? (setError, mapping a 422 payload to fields). And know when not to be optimistic — payments and irreversible actions should wait for the server.

Q16. What are React 19 form actions, useActionState, and useFormStatus?

ROI: ★★★★☆ Frequency: High

Short Answer

React 19 lets you pass a function to a <form action={...}>. The action receives the submitted FormData, can be async, and integrates with pending/error state. useActionState wraps an action to expose its return value, an isPending flag, and a bound action. useFormStatus lets a nested component (like a submit button) read the parent form's pending state without prop drilling. With Server Components, actions can be Server Actions that run on the server.

Detailed Answer

Form actions are React's built-in answer to the boilerplate of "manage isSubmitting, call the API, handle the result." You attach a function to a form's action; React calls it with the FormData on submit, manages pending state, and resets uncontrolled fields on success.

  • useActionState(fn, initialState) — returns [state, formAction, isPending]. state is whatever the action returns (great for validation errors or messages), formAction is what you pass to <form action>, and isPending replaces manual submitting flags.
  • useFormStatus() — must be called from a component rendered inside the form; returns { pending, data, method }. Perfect for a reusable <SubmitButton> that disables itself during submission without the parent passing props down.
  • Server Actions (Next.js / RSC) — an action marked "use server" runs on the server; the form works even before hydration (progressive enhancement).

These are additive, not a replacement for React Hook Form. RHF still shines for complex client-side validation, field arrays, and rich interactivity; form actions shine for progressively-enhanced, server-driven mutations with minimal client code.

Code Example

"use client";
import { useActionState } from "react";
import { useFormStatus } from "react-dom";

type State = { error?: string };

async function subscribe(_prev: State, formData: FormData): Promise<State> {
  const email = formData.get("email") as string;
  if (!email.includes("@")) return { error: "Invalid email" };
  await api.subscribe(email);
  return {};
}

function SubmitButton() {
  const { pending } = useFormStatus();           // reads parent form status
  return <button disabled={pending}>{pending ? "…" : "Subscribe"}</button>;
}

export function NewsletterForm() {
  const [state, formAction, isPending] = useActionState(subscribe, {});
  return (
    <form action={formAction}>
      <input name="email" />
      {state.error && <p role="alert">{state.error}</p>}
      <SubmitButton />
    </form>
  );
}

Senior Engineer Perspective

Being current here signals you track the ecosystem. Key nuances: useFormStatus only works in a child of the form (not the same component that renders the form) — a classic gotcha. useActionState was renamed from the experimental useFormState, and it lives in react while useFormStatus lives in react-dom. The mature framing: form actions don't replace RHF/Zod for heavy client forms — they excel at progressively-enhanced server mutations. Know when each fits.
