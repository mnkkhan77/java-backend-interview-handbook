SECTION 1 - JSX & COMPONENTS

Q1. What is React, and what does "declarative UI" actually mean?

ROI: ★★★★★ Frequency: Extremely High

Short Answer

React is a JavaScript library for building user interfaces out of composable components. It is declarative: you describe what the UI should look like for a given state, and React figures out the DOM operations needed to get there. You never manually append, remove, or mutate DOM nodes — you change state, and React reconciles the output.

Detailed Answer

The core mental model is a pure function: UI = f(state). Your component returns a description of the UI (a tree of elements) as a function of its current props and state. When state changes, React re-runs that function, produces a new element tree, diffs it against the previous one (reconciliation), and applies the minimal set of DOM mutations.

Declarative vs Imperative

In an imperative world (vanilla DOM, jQuery) you write the steps: "find the node, read its text, if the count changed update it, toggle this class." Every branch of state is a manual instruction, and keeping the DOM in sync with data is the source of most bugs.

In a declarative world you write the destination: "when count is N, the label reads N." React owns the transition from the old picture to the new one. This removes an entire class of "the screen says one thing but the data says another" bugs because there is a single source of truth (state) and one place that renders it.

Why it matters

  • Predictability — the UI is a deterministic projection of state.
  • Composability — components nest like functions call functions.
  • The Virtual DOM — React batches and minimizes real DOM writes, which are the expensive part.

Code Example

// Imperative (vanilla) — you describe every step
const btn = document.querySelector("#like");
let liked = false;
btn.addEventListener("click", () => {
  liked = !liked;
  btn.textContent = liked ? "Liked" : "Like"; // manual sync
  btn.classList.toggle("active", liked);
});

// Declarative (React) — you describe the result for a given state
function LikeButton() {
  const [liked, setLiked] = React.useState(false);
  return (
    <button
      className={liked ? "active" : ""}
      onClick={() => setLiked(!liked)}
    >
      {liked ? "Liked" : "Like"}
    </button>
  );
}

Project Example

On a dashboard I built, a filter panel controlled a table of results. Declaratively, the table simply rendered rows.filter(matchesFilters). Adding a new filter meant adding one predicate — I never touched the DOM, wrote no "clear old rows / append new rows" code, and there was no way for the table to drift out of sync with the filter chips.

Senior Engineer Perspective

Interviewers use this to check whether you actually understand the paradigm or just memorized "Virtual DOM = fast." The honest nuance: the Virtual DOM is not inherently faster than hand-optimized imperative DOM code — a skilled engineer can beat React on a single widget. React's win is maintainability at scale: it makes correct UI the default and keeps a large app's state and view coherent. If you claim "React is fast because of the Virtual DOM," expect a follow-up like "faster than what?" — and the correct answer is "faster and safer than the imperative code most teams would otherwise write, by minimizing and batching DOM writes."

Q2. What is JSX, and what does it compile to?

ROI: ★★★★★ Frequency: Extremely High

Short Answer

JSX is a syntax extension that looks like HTML but is really sugar for function calls. A build step (Babel, SWC, esbuild, TypeScript) compiles each JSX element into a call — historically React.createElement(...), and since React 17 into the automatic JSX runtime (jsx / jsxs from react/jsx-runtime). Those calls return plain JavaScript objects called React elements. The browser never sees JSX.

Detailed Answer

JSX is not HTML and it is not a template language — it is expressions. Anything in { } is arbitrary JavaScript. Because it compiles to function calls, JSX obeys JavaScript rules: components must be capitalized (lowercase compiles to a string tag like "div", capitalized to a variable reference), attributes are camelCased (className, onClick), and a component must return a single root (an element, a Fragment, or an array).

The two compile targets

  • Classic runtime (pre-17): each element becomes React.createElement(type, props, ...children). This is why you had to import React in every file even if you didn't reference it — the compiled code did.
  • Automatic runtime (17+): the compiler injects imports from react/jsx-runtime and emits _jsx(type, props) / _jsxs(...) for multiple children. You no longer need import React just to use JSX.

A React element is a lightweight, immutable description — roughly { type, key, props }. It is not a DOM node and not a component instance; it is a plain object React later reconciles into DOM.

Code Example

// What you write
const el = (
  <button className="primary" onClick={handleClick}>
    Hello {name}
  </button>
);

// Classic runtime (React.createElement)
const el = React.createElement(
  "button",
  { className: "primary", onClick: handleClick },
  "Hello ",
  name
);

// Automatic runtime (React 17+), roughly:
import { jsx as _jsx } from "react/jsx-runtime";
const el = _jsx("button", {
  className: "primary",
  onClick: handleClick,
  children: ["Hello ", name],
});

// The element is just an object:
// { type: "button", key: null, props: { className, onClick, children } }

Project Example

Understanding that JSX is "just function calls returning objects" paid off when I built a config-driven form: instead of writing JSX by hand, I mapped a JSON schema to an array of elements and rendered them. Knowing elements are plain objects made it obvious that I could generate, filter, and compose them programmatically — something that feels impossible if you think JSX is magic HTML.

Senior Engineer Perspective

The trap here is candidates who say "JSX is HTML in JavaScript." It isn't — it's expressions that compile to calls. A strong follow-up: "Why must component names be capitalized?" Answer: because JSX compiles the tag name literally; lowercase becomes the string "div" (a host element), while capitalized becomes a variable reference to your component. Another sharp follow-up: "Why doesn't <MyComp /> re-run when I only mutate a prop object in place?" — because elements are immutable snapshots; React compares by reference and value, not by watching your object.

Q3. Function components vs class components — why did functions win?

ROI: ★★★★☆ Frequency: High

Short Answer

Both produce UI, but function components + hooks (React 16.8+) became the standard because they let you reuse stateful logic without wrapper hell, avoid the this-binding footguns of classes, and colocate related logic instead of scattering it across lifecycle methods. New React features (concurrent rendering, most modern APIs) are built for functions. Classes still work but are legacy for new code.

Detailed Answer

A class component extends React.Component, holds state in this.state, and reacts to lifecycle via methods like componentDidMount. A function component is just a function that returns JSX and uses hooks (useState, useEffect, …) for state and side effects.

ConcernClassFunction + Hooks
Statethis.state / setStateuseState / useReducer
Side effectsSplit across componentDidMount, componentDidUpdate, componentWillUnmountUnified in useEffect
this bindingManual (constructor or arrow methods)No this at all
Logic reuseHOCs / render props (nesting hell)Custom hooks (flat, composable)
Concurrent featuresLimitedFirst-class

The killer reason functions won is stateful logic reuse. In the class era, sharing "subscribe to window resize" logic meant HOCs or render props, which produced deeply nested "wrapper hell" and made the tree hard to read. A custom hook packages that same logic into a plain function you call — flat, testable, and composable.

The second reason is that lifecycle methods split related code (a subscription set up in componentDidMount and torn down in componentWillUnmount) and merged unrelated code (two features both living in componentDidUpdate). Effects group by concern instead.

Code Example

// Class
class Counter extends React.Component {
  state = { count: 0 };
  increment = () => this.setState(s => ({ count: s.count + 1 }));
  componentDidMount() { document.title = `Count ${this.state.count}`; }
  componentDidUpdate() { document.title = `Count ${this.state.count}`; }
  render() {
    return <button onClick={this.increment}>{this.state.count}</button>;
  }
}

// Function + hooks — same behaviour, less ceremony, effect colocated
function Counter() {
  const [count, setCount] = React.useState(0);
  React.useEffect(() => {
    document.title = `Count ${count}`;
  }, [count]);
  return <button onClick={() => setCount(c => c + 1)}>{count}</button>;
}

Senior Engineer Perspective

Don't say "functions are faster" — they aren't meaningfully faster; the win is ergonomics and logic reuse. Know the two things classes can still technically do that hooks can't natively: error boundaries require a class (componentDidCatch / getDerivedStateFromError), and there is no hook equivalent yet. Also be ready for "isn't useEffect just componentDidMount?" — no: effects run after paint, can run multiple times, and their dependency array + cleanup semantics don't map one-to-one to lifecycle methods. Conflating the two is the classic junior mistake.

Q4. What are Fragments and why do they exist?

ROI: ★★★★☆ Frequency: High

Short Answer

A component must return a single root node, but you often don't want an extra wrapper <div> in the DOM. A Fragment lets you group children without adding any node. Use <>...</> shorthand, or <React.Fragment> when you need a key (e.g. in a list).

Detailed Answer

Wrapper divs cause real problems: they break CSS layouts that depend on direct parent-child relationships (flexbox, grid, tables), they pollute the DOM, and they can break semantics (you can't wrap <td> elements in a <div> inside a <tr>). Fragments solve this by grouping siblings with zero DOM footprint.

The shorthand <></> cannot take attributes. When you render a list of grouped elements and need a key, you must use the explicit <React.Fragment key={id}> form.

Code Example

// No wrapper div in the output
function Columns() {
  return (
    <>
      <td>Name</td>
      <td>Email</td>
    </>
  );
}

// Keyed fragment in a list — shorthand can't hold a key
function Definitions({ items }) {
  return (
    <dl>
      {items.map((item) => (
        <React.Fragment key={item.id}>
          <dt>{item.term}</dt>
          <dd>{item.desc}</dd>
        </React.Fragment>
      ))}
    </dl>
  );
}

Senior Engineer Perspective

Interviewers like the table example because it exposes whether you understand that "div soup" isn't just ugly — it breaks valid HTML and CSS. A good follow-up answer: mention that unnecessary wrapper divs also make styling and accessibility harder (extra layers screen readers must traverse) and can subtly change flex/grid behaviour. Knowing that the shorthand can't take a key is a small detail that signals real hands-on experience.

Q5. Explain the children prop and component composition.

ROI: ★★★★☆ Frequency: High

Short Answer

Whatever you nest between a component's opening and closing tags is passed to it as props.children. This enables composition — building flexible, reusable "container" components (cards, modals, layouts) that don't need to know what they wrap. React's answer to "inheritance vs composition" is: strongly prefer composition, and children is the primary tool.

Detailed Answer

A generic Card shouldn't hardcode its contents. By rendering {children}, it becomes a shell any caller can fill. You can also accept multiple "slots" by passing elements as named props (e.g. header, footer) — sometimes called the slots pattern.

Composition beats inheritance in React because components are functions, not class hierarchies. Instead of a FancyButton extends Button chain, you compose: a specialized component renders a generic one and passes props/children through. This keeps components loosely coupled and avoids brittle hierarchies.

Code Example

// Container that doesn't care what it wraps
function Card({ title, children }) {
  return (
    <section className="card">
      <h3>{title}</h3>
      <div className="card-body">{children}</div>
    </section>
  );
}

// Composition via children + a "slot" prop
function Dialog({ footer, children }) {
  return (
    <div className="dialog">
      <div className="content">{children}</div>
      <div className="actions">{footer}</div>
    </div>
  );
}

// Usage
<Card title="Profile">
  <Avatar user={user} />
  <p>{user.bio}</p>
</Card>

Senior Engineer Perspective

A frequent follow-up: "How would you avoid prop drilling deep composition?" — answer with Context for cross-cutting values, but note that passing components as children is itself a powerful way to sidestep drilling: the parent that has the data renders the child directly and hands the tree down. This is also the basis of the "children as a performance boundary" trick — a child passed via children doesn't re-render when the parent's own state changes, because its element was created by the grandparent. Mentioning that shows depth.

SECTION 2 - PROPS & STATE

Q6. Props vs state — what is the real difference?

ROI: ★★★★★ Frequency: Extremely High

Short Answer

Props are inputs passed into a component by its parent; they are read-only from the component's perspective. State is data a component owns and manages internally over time. Props flow down and are immutable to the receiver; state is local, mutable via a setter, and triggers re-renders when it changes.

Detailed Answer

PropsState
Owned byParentThe component itself
Mutable?No (read-only to receiver)Yes, via setter (useState)
PurposeConfigure / pass data downTrack changing internal data
Triggers re-renderWhen parent passes new valuesWhen you call the setter

A useful test: "Can this value be computed from props or other state?" If yes, it should not be state (derive it during render instead). "Does it change over the component's life due to user interaction or async data?" If yes, it's state. "Is it given by a parent?" Then it's a prop.

Treat props as immutable — never assign to props.x. If a component needs to change a value it received, it should either lift that decision to the owner (call a callback prop) or copy the initial value into its own state.

Code Example

// `label` and `onClick` are PROPS (from parent, read-only here)
// `count` is STATE (owned here, changes over time)
function Counter({ label }) {
  const [count, setCount] = React.useState(0);

  // Derived value — NOT state, computed each render
  const isEven = count % 2 === 0;

  return (
    <button onClick={() => setCount(c => c + 1)}>
      {label}: {count} ({isEven ? "even" : "odd"})
    </button>
  );
}

Senior Engineer Perspective

The single most common junior mistake this question exposes is redundant state — copying a prop into state and then wondering why it "doesn't update" when the prop changes (because useState's initial value is only read on the first render). Say clearly: derive whenever possible, and only mirror a prop into state when you deliberately want to "fork" it (e.g. an editable form initialized from a server value). Interviewers probe "what would you never make state?" — answer: anything derivable, because duplicated sources of truth drift apart.

Q7. What is one-way data flow, and why does React enforce it?

ROI: ★★★★☆ Frequency: High

Short Answer

Data in React flows in a single direction: down from parent to child via props. A child cannot reach up and mutate its parent's data directly; instead the parent passes callbacks down, and the child calls them to request a change. This unidirectional flow makes state changes predictable and traceable.

Detailed Answer

State lives in one place (the owner), and that owner passes the current value down as props and passes handlers down for changes. When a child triggers a handler, the owner updates its state, which re-renders and pushes fresh props down. The loop is: state → props → view → event → callback → new state.

Compare this to two-way binding (older Angular, Knockout) where a view field and a model auto-sync in both directions. Two-way binding is convenient for small forms but makes it hard to answer "who changed this value and when?" in a large app. One-way flow trades a little verbosity for a clear, debuggable audit trail — there is always exactly one owner of any piece of state.

Code Example

// Parent owns the state; child receives value + a way to request change
function Parent() {
  const [name, setName] = React.useState("");
  return <NameInput value={name} onChange={setName} />;
}

function NameInput({ value, onChange }) {
  // Child never mutates parent directly — it calls the callback
  return (
    <input
      value={value}
      onChange={(e) => onChange(e.target.value)}
    />
  );
}

Senior Engineer Perspective

Expect "but isn't a controlled input two-way binding?" The sharp answer: it looks two-way but is implemented as two one-way flows — value flows down, change events flow up as function calls; React never silently syncs anything. That distinction is the whole point. Interviewers also like to ask what breaks one-way flow: mutating props, mutating state objects in place, or lifting shared state too late. A senior engineer frames one-way flow as the property that makes time-travel debugging and predictable renders possible.

Q8. What does "lifting state up" mean, and when do you do it?

ROI: ★★★★☆ Frequency: High

Short Answer

When two or more components need to share or stay in sync with the same data, you move that state up to their closest common ancestor and pass it back down as props. The ancestor becomes the single source of truth; the children become controlled by it.

Detailed Answer

Suppose two sibling components need the same value — say a temperature entered in Celsius should reflect in a Fahrenheit field. If each holds its own state, they drift. The fix: lift the temperature into their parent, which passes value and onChange to both. Now there is one owner and both views are always consistent.

The heuristic: state should live at the lowest common ancestor of all components that read or write it — no higher (which causes needless re-renders and prop drilling), no lower (which causes duplication and drift). If lifting produces excessive prop drilling across many layers, that's the signal to reach for Context or a state library — but lifting is always the first move.

Code Example

// State lifted to the parent so both children stay in sync
function TemperatureCalculator() {
  const [celsius, setCelsius] = React.useState(20);
  const fahrenheit = celsius * 9 / 5 + 32;

  return (
    <>
      <TempInput scale="C" value={celsius}
        onChange={setCelsius} />
      <TempInput scale="F" value={fahrenheit}
        onChange={(f) => setCelsius((f - 32) * 5 / 9)} />
    </>
  );
}

function TempInput({ scale, value, onChange }) {
  return (
    <label>
      {scale}: <input value={value}
        onChange={(e) => onChange(Number(e.target.value))} />
    </label>
  );
}

Senior Engineer Perspective

The follow-up is almost always "and when does lifting become a problem?" — when the common ancestor is many levels up and you drill props through components that don't care about them. That's the cue for Context (for low-frequency, cross-cutting state like theme/auth) or a dedicated store (Redux Toolkit, Zustand) for complex, frequently-updated shared state. A senior answer sequences the tools: derive → lift → Context → store, escalating only when the previous tool hurts.

Q9. Why must you update state immutably instead of mutating it?

ROI: ★★★★★ Frequency: Extremely High

Short Answer

React decides whether to re-render (and whether memoized children changed) by comparing references with Object.is. If you mutate an object or array in place, the reference doesn't change, so React may skip the re-render and the UI goes stale. You must produce a new object/array so the reference differs.

Detailed Answer

State updates in React are shallow-compared by reference. state.items.push(x) mutates the same array — same reference — and setItems(state.items) tells React "nothing changed." Even if a re-render does happen for another reason, React.memo, useMemo, and effect dependency arrays all rely on reference equality and will misbehave.

The rule: always create new containers. Use spread ([...arr, item], { ...obj, key: val }), array methods that return new arrays (map, filter, concat — not push/splice/sort in place), and the functional updater form setX(prev => ...) when the next value depends on the previous one.

For deeply nested state, manual spreading gets painful — that's where useReducer plus Immer (which lets you "mutate" a draft that produces an immutable result) shines.

Code Example

const [todos, setTodos] = React.useState([]);

// WRONG — mutates same array, same reference, React may skip render
function addWrong(text) {
  todos.push({ id: Date.now(), text });
  setTodos(todos); // same reference!
}

// RIGHT — new array, new reference
function addRight(text) {
  setTodos((prev) => [...prev, { id: Date.now(), text }]);
}

// RIGHT — updating one item immutably
function toggle(id) {
  setTodos((prev) =>
    prev.map((t) => (t.id === id ? { ...t, done: !t.done } : t))
  );
}

Senior Engineer Perspective

This is a top filter question. The strongest answer connects it to Object.is reference comparison and names the concrete failure modes: skipped re-renders, stale React.memo, and effects that don't fire because their dependency reference didn't change. A common follow-up: "why does the functional updater setX(prev => ...) matter?" — because in batched updates or closures, x may be stale; reading prev guarantees you build on the latest committed value. If asked about deep updates, mention Immer rather than hand-rolling five levels of spread.

SECTION 3 - RENDERING & LISTS

Q10. When and why do React components re-render?

ROI: ★★★★★ Frequency: Extremely High

Short Answer

A component re-renders when (1) its own state changes, (2) its parent re-renders, or (3) a Context it consumes changes value. "Re-render" means React calls the component function again to produce a new element tree; it does not necessarily mean DOM changes — reconciliation still diffs and only touches the DOM where output actually differs.

Detailed Answer

The crucial and counter-intuitive part: when a component re-renders, all of its children re-render by default — regardless of whether their props changed. React does not bail out automatically. It re-runs the whole subtree and relies on reconciliation to keep DOM edits minimal.

Re-rendering is usually cheap and not a problem; premature optimization here is a classic mistake. But when a subtree is expensive, you opt into skipping with:

  • React.memo(Component) — skips re-render if props are shallowly equal.
  • useMemo — memoizes an expensive computed value.
  • useCallback — stabilizes a function reference so memoized children don't see it as "new."

Note that props "changing" is judged by reference — which is exactly why immutable updates (Q9) and stable references matter for these optimizations to work.

Code Example

function Parent() {
  const [count, setCount] = React.useState(0);
  return (
    <>
      <button onClick={() => setCount(c => c + 1)}>{count}</button>
      {/* Re-renders every time Parent does, even though its
          props never change — unless wrapped in React.memo */}
      <ExpensiveChild />
    </>
  );
}

const ExpensiveChild = React.memo(function ExpensiveChild() {
  // now skipped when props are shallow-equal
  return <div>...</div>;
});

Senior Engineer Perspective

The mistake juniors make is believing "props changed → re-render, props same → no re-render." Reality: parent render → child renders regardless, unless memoized. Interviewers push on "so should you wrap everything in React.memo?" — no; the comparison itself costs, and most renders are cheap. Profile first. A senior also mentions a free win: passing an expensive subtree via children so it isn't re-created by the state-holding component. And they'll note that React 19's compiler aims to auto-memoize, reducing manual useMemo/useCallback.

Q11. Why do lists need keys, and why are index keys dangerous?

ROI: ★★★★★ Frequency: Extremely High

Short Answer

Keys give each list item a stable identity so React's reconciler can tell which items were added, removed, or reordered — instead of re-rendering the whole list. Use a stable, unique ID from your data. Using the array index as a key is dangerous because the index changes when items are inserted, removed, or reordered, causing React to associate the wrong DOM/state with the wrong item.

Detailed Answer

During reconciliation React matches old and new children by key. With stable keys, inserting an item at the top adds one node and leaves the rest untouched. Without keys (or with index keys), React matches by position: inserting at the top makes every index shift, so React thinks every item changed and either re-renders everything or — worse — keeps stale internal state attached to the wrong item.

The classic bug: a list of inputs keyed by index. Type into the first input, then prepend a new item. Because the DOM nodes are matched by position, your typed text and focus "stick" to position 0 and now belong to the wrong logical item. The same corruption hits uncontrolled inputs, animations, and component state inside list items.

Index keys are only acceptable when the list is static, never reordered, and items are never inserted/removed in the middle — and even then a real ID is safer.

Code Example

// DANGEROUS — index key breaks on reorder/insert/delete
{items.map((item, i) => (
  <li key={i}>
    <input defaultValue={item.name} />
  </li>
))}

// CORRECT — stable identity from the data
{items.map((item) => (
  <li key={item.id}>
    <input defaultValue={item.name} />
  </li>
))}

Project Example

On a drag-and-drop task board I once used the index as a key and shipped a maddening bug: reordering cards would keep an edit-in-progress textarea's content on the card that used to be in that slot. Switching to the task's UUID as the key fixed it instantly — a textbook demonstration of why keys are about identity, not position.

Senior Engineer Perspective

This question sorts people who've read docs from people who've been burned. Nail the why: keys are React's mechanism for preserving component identity and state across renders, not just to "silence a warning." Follow-ups: "Why not Math.random() as a key?" — because it changes every render, so React remounts every item every time (destroying state and killing performance). "Where must the key go?" — on the outermost element returned by map, and it only needs to be unique among siblings, not globally.

Q12. What are the common conditional rendering patterns in JSX?

ROI: ★★★☆☆ Frequency: Medium

Short Answer

Since JSX is expressions, you render conditionally with plain JavaScript: the ternary cond ? a : b for either/or, the logical && for "render or nothing," early return null to render nothing, and variables or helper functions for complex branches. There's no special template syntax.

Detailed Answer

  • Ternary — when you need one of two outputs: {isLoading ? <Spinner/> : <List/>}.
  • Logical AND — when you render something or nothing: {error && <Error/>}. Watch the gotcha below.
  • Early return — if (!user) return null; keeps the main JSX clean.
  • Extracted variable / function — for 3+ branches, compute the element above the return, or use a small helper / lookup map keyed by status.

The && falsy trap: {count && <Badge/>} renders the literal 0 when count is 0, because 0 is falsy but is a valid React child. Guard with a real boolean: {count > 0 && <Badge/>} or {!!count && ...}.

Code Example

// Ternary
{isLoading ? <Spinner /> : <Results data={data} />}

// Logical AND — but beware falsy 0
{items.length > 0 && <Count n={items.length} />}   // safe
{items.length && <Count />}                          // BUG: renders 0

// Lookup map for many states — cleaner than nested ternaries
const views = {
  loading: <Spinner />,
  error: <ErrorPanel />,
  empty: <EmptyState />,
  ready: <List data={data} />,
};
return views[status];

Senior Engineer Perspective

The 0 rendering trap is a favorite gotcha — many candidates have hit "why is there a random 0 in my UI?" in production. Mention it unprompted; it signals experience. Also worth saying: deeply nested ternaries hurt readability, so prefer early returns or a status-to-view map for multi-state components (loading/error/empty/ready), which also documents every state explicitly.

SECTION 4 - EVENTS & FORMS BASICS

Q13. How does event handling work in React, and what is a synthetic event?

ROI: ★★★★☆ Frequency: High

Short Answer

You attach handlers with camelCase props (onClick, onChange) and pass a function reference. React wraps the native browser event in a cross-browser SyntheticEvent to give consistent behaviour across browsers. In React 17+, React attaches one listener at the root container (not the document) and uses delegation, rather than binding a listener to each DOM node.

Detailed Answer

A SyntheticEvent has the same interface as the native event (preventDefault, stopPropagation, target, etc.) but normalizes quirks across browsers. You always pass a function, not call it: onClick={handleClick}, not onClick={handleClick()} (the latter calls it during render). To pass arguments, wrap in an arrow: onClick={() => handleClick(id)}.

React uses event delegation: instead of one listener per element, it attaches a single listener at the app root and dispatches events through its own synthetic system. This is a performance and consistency win. (Pre-React 17 it delegated at document; React 17 moved it to the root container, which fixed issues with multiple React versions and nested apps.)

Historical note you may be asked about: React used to pool synthetic events (reuse the object and null its fields after the handler), so accessing the event asynchronously required e.persist(). Event pooling was removed in React 17, so this is no longer a concern — but interviewers still ask.

Code Example

function Form() {
  function handleSubmit(e) {
    e.preventDefault();          // synthetic event API
    console.log("submitted");
  }
  return (
    <form onSubmit={handleSubmit}>
      {/* pass a reference, not a call */}
      <button onClick={() => console.log("clicked")}>Go</button>
    </form>
  );
}

Senior Engineer Perspective

Two follow-ups recur. First: "Is onClick the same as addEventListener?" — no; it's a synthetic wrapper dispatched via React's delegated root listener, so e.stopPropagation() stops React-tree propagation but a native listener on document may still fire. Second: "Does inline onClick={() => ...} hurt performance by creating a new function each render?" — usually negligible, but it can defeat React.memo on a child, which is when useCallback earns its place. Mentioning that event pooling was removed in 17 signals you keep current.

Q15. How do you pass data from a child up to a parent?

ROI: ★★★★☆ Frequency: High

Short Answer

You can't pass data "up" directly — data only flows down. Instead the parent passes a callback function down as a prop, and the child calls it with the data. The parent receives the value in that callback and updates its own state. This is the inverse-flow pattern that keeps data flow one-directional.

Detailed Answer

The parent owns the state and defines a handler like handleSelect(item). It passes onSelect={handleSelect} to the child. When the user interacts, the child invokes props.onSelect(theData). The parent's handler runs, updates state, re-renders, and the new data flows back down as props. Nothing violates one-way flow — the child merely requests a change by calling a function the parent gave it.

This is the foundation of controlled inputs (Q7/Q14), form submission, selection lists, and virtually every interactive component. For deeply nested children where threading callbacks becomes tedious, Context or a reducer can centralize the handler.

Code Example

function ProductList({ products }) {
  const [selected, setSelected] = React.useState(null);
  return (
    <>
      {products.map((p) => (
        // parent hands down a callback
        <ProductRow key={p.id} product={p} onSelect={setSelected} />
      ))}
      <p>Selected: {selected?.name ?? "none"}</p>
    </>
  );
}

function ProductRow({ product, onSelect }) {
  // child calls up with data
  return <button onClick={() => onSelect(product)}>{product.name}</button>;
}

Senior Engineer Perspective

The common follow-up: "Isn't passing callbacks down just prop drilling?" — for one or two levels it's fine and explicit; when it spans many layers, that's the signal to lift into Context or a store, or restructure with composition. Another probe: "Does passing a new arrow function each render cause problems?" — only when the child is memoized, where useCallback stabilizes it. A senior frames child→parent communication as "events bubbling up via function calls," mirroring the DOM's own event model.

Q16. How is the component lifecycle expressed with hooks vs class methods?

ROI: ★★★★☆ Frequency: High

Short Answer

In classes, lifecycle is explicit methods: componentDidMount, componentDidUpdate, componentWillUnmount. In function components, you express all of these through useEffect by controlling its dependency array and returning a cleanup function. But the mental model differs: hooks think in terms of synchronizing with external state, not "moments in a lifecycle."

Detailed Answer

Class lifecycleHook equivalent
componentDidMountuseEffect(fn, []) — runs once after first paint
componentDidUpdateuseEffect(fn, [deps]) — runs when deps change
componentWillUnmountthe cleanup function returned from useEffect
every renderuseEffect(fn) — no dependency array

The dependency array is the control: [] runs the effect once (mount) and cleanup on unmount; [a, b] re-runs when a or b change (running cleanup for the previous values first); omitting it runs after every render.

The important shift: the React team advises you not to think "this is my mount handler." Think "this effect synchronizes X (a subscription, the document title, a network request) with these dependencies." When a dependency changes, React tears down the old sync (cleanup) and sets up a new one. This model naturally handles updates that the class approach made awkward.

Also note effects run after the browser paints. If you need to read layout or mutate the DOM before paint (to avoid a visible flicker), use useLayoutEffect, which fires synchronously after DOM mutations but before paint.

Code Example

function ChatRoom({ roomId }) {
  React.useEffect(() => {
    const conn = createConnection(roomId);
    conn.connect();                 // "mount" + on roomId change
    return () => conn.disconnect();  // cleanup: "unmount" + before re-sync
  }, [roomId]);                      // re-sync whenever roomId changes

  return <h1>Welcome to {roomId}</h1>;
}

Senior Engineer Perspective

Many candidates recite the mapping table but miss the paradigm shift. Interviewers reward "effects are about synchronization, not lifecycle timing." Expect the trap "what if you forget the dependency array?" — the effect runs every render (often an infinite loop if it sets state). And "what if you leave a dependency out?" — stale closures reading old props/state. Bonus depth: mention that many things people put in effects (derived data, event responses) shouldn't be effects at all — the modern guidance is "you might not need an effect."

Q17. What is StrictMode, and why do things run twice in development?

ROI: ★★★★☆ Frequency: High

Short Answer

<React.StrictMode> is a development-only wrapper that helps you catch bugs early. In React 18, it deliberately double-invokes component render functions, and mounts→unmounts→remounts each component once, running effects twice. This surfaces impure renders and missing effect cleanup. It has zero effect in production builds.

Detailed Answer

StrictMode runs certain functions twice on purpose to expose code that isn't resilient to it:

  • Double-rendered components — reveals side effects during render (renders must be pure; running twice should produce the same result with no observable side effects).
  • Effects run twice (setup → cleanup → setup) — reveals effects that don't clean up properly (e.g. a subscription created but never torn down leaks or duplicates).
  • Also flags deprecated/legacy APIs.

The intent is to make your components robust for React's concurrent features, where React may mount, unmount, and remount components (preserving state) to optimize rendering. If your effect assumes "setup happens exactly once forever," concurrent React can break it — StrictMode forces you to fix that now. This is why the fix is almost always "add proper cleanup," not "disable StrictMode."

Critically, this double-invocation happens only in development. Production runs each once.

Code Example

// index.jsx — wraps the app in dev
root.render(
  <React.StrictMode>
    <App />
  </React.StrictMode>
);

// This effect is StrictMode-safe: cleanup makes the
// double setup→cleanup→setup harmless (one net subscription)
React.useEffect(() => {
  const id = setInterval(tick, 1000);
  return () => clearInterval(id); // without this, dev leaks a timer
}, []);

Senior Engineer Perspective

The tell of inexperience is "my API call fires twice, so I removed StrictMode." The senior response: the double-fire is a signal, not the bug — it reveals an effect without cleanup (cancel the request via AbortController in cleanup, or move data fetching to a library like TanStack Query that dedupes). Expect "why doesn't it double in production?" — because it's a dev-only correctness aid with a cost React won't pay in prod. Knowing that state is preserved across the dev remount (it's not a full remount from the user's view) is a nice detail.

Q18. What are refs and portals, and when do you reach for them?

ROI: ★★★☆☆ Frequency: Medium

Short Answer

A ref (useRef) is an escape hatch to hold a mutable value that persists across renders without triggering a re-render — most commonly a reference to a DOM node (to focus an input, measure size, or integrate a non-React library). A portal (createPortal) renders children into a DOM node outside the parent's DOM hierarchy while keeping them in the React tree — ideal for modals, tooltips, and toasts that must escape overflow/z-index containers.

Detailed Answer

Refs

useRef(initial) returns a stable object { current }. Mutating ref.current does not cause a re-render, and the value survives renders. Two uses: (1) attach to a DOM element via the ref attribute to imperatively call things like .focus() or read layout; (2) store any mutable instance value (a timer ID, previous value, a WebSocket) that shouldn't be state because rendering doesn't depend on it. Rule of thumb: if changing it should update the UI, it's state; if not, it may be a ref.

Portals

createPortal(children, domNode) renders children into a different DOM container (say a top-level #modal-root), which visually escapes parent overflow: hidden or z-index stacking contexts. Crucially, the portal stays in the React tree, so context, state, and — importantly — event bubbling still flow through the React parent even though the DOM position differs.

Code Example

// Ref to a DOM node — imperative focus
function SearchBox() {
  const inputRef = React.useRef(null);
  React.useEffect(() => {
    inputRef.current?.focus();   // focus on mount
  }, []);
  return <input ref={inputRef} />;
}

// Portal — modal rendered into #modal-root, escaping overflow/z-index
import { createPortal } from "react-dom";

function Modal({ children, onClose }) {
  return createPortal(
    <div className="overlay" onClick={onClose}>
      <div className="dialog" onClick={(e) => e.stopPropagation()}>
        {children}
      </div>
    </div>,
    document.getElementById("modal-root")
  );
}

Senior Engineer Perspective

For refs, the key nuance: they're an escape hatch — prefer declarative state; reach for a ref only for imperative DOM work React can't express (focus, scroll, measure, media playback) or for non-rendering mutable values. A follow-up favorite: "why not just use a module-level variable instead of a ref?" — because a ref is per-instance, whereas a module variable is shared across all instances. For portals, the counter-intuitive fact interviewers love: events still bubble through the React parent, not the DOM parent — so a click inside a portaled modal can trigger a handler on the logical React ancestor even though it lives elsewhere in the DOM.

SECTION 6 - JSX DEEP DIVE & THE BABEL TRANSFORM

Q19. What are the JSX expression rules, and why must a component return a single root?

ROI: ★★★★☆ Frequency: High

Short Answer

Anything inside { } in JSX must be a single JavaScript expression — something that evaluates to a value — never a statement. That's why if, for, and variable declarations can't sit directly inside JSX braces. A component must return one root because JSX compiles to a single function call per element; return <A/><B/> would be two separate calls with nowhere to attach them, so the compiler (and React) requires one wrapping element, Fragment, or array.

Detailed Answer

JSX braces accept expressions because they compile straight into arguments of a function call — _jsx(type, { children: EXPRESSION }). A function call argument can only be an expression, so {if (x) {...}} is a syntax error the same way foo(if (x) {...}) would be in plain JS. Ternaries, logical &&/||, function calls, IIFEs, and array .map() all work because they are expressions that produce a value.

The single-root rule follows directly: JSX is sugar for return _jsx(...) — one call, one return value. Historically you needed a wrapper <div>; Fragments removed the DOM cost of that wrapper while keeping the "one thing is returned" constraint. Since React 16, a component may also return an array of elements (each needing a key) or a string/number directly, which technically isn't "one element" but is still one returned value.

Code Example

function Panel({ isOpen, items }) {
  // OK — expressions
  const label = isOpen ? "Open" : "Closed";
  return (
    <div>
      {label}
      {items.map((i) => <span key={i.id}>{i.name}</span>)}
      {/* {if (isOpen) { return 
x
; }}  <- SyntaxError: statement, not expression */}
      {(() => { if (isOpen) return <p>Open now</p>; return null; })()}
    </div>
  );
}

// Multiple roots require a Fragment/array — bare siblings don't compile
function Bad() {
  return <h1>A</h1><p>B</p>; // SyntaxError
}
function Good() {
  return (
    <>
      <h1>A</h1>
      <p>B</p>
    </>
  );
}

Senior Engineer Perspective

Interviewers like asking "why can't I write a for-loop inside JSX?" — the crisp answer is "because JSX braces hold expressions, and a for loop is a statement with no value." Show you know the escape hatches: compute the loop's result above the return with .map(), or wrap statements in an IIFE (rare, usually a smell). Mentioning that returning an array of elements is legal but requires keys on each item is a good depth signal.

Q20. Why isn't JSX a templating language, and what does that imply for logic inside markup?

ROI: ★★★☆☆ Frequency: Medium

Short Answer

Templating languages (Handlebars, EJS, Angular templates) define their own mini-language with special directives ({{#if}}, *ngFor) that a template engine interprets at render time. JSX has no special syntax of its own beyond the { } escape into JavaScript — there is no <For> or <If> tag built into the language. Every piece of "logic" you see in JSX is just JavaScript, which means you already know the whole language: no separate template DSL to learn, and no separate limitations to work around.

Detailed Answer

This has real consequences. Conditionals are ternaries or &&, not a v-if directive. Loops are .map(), not a *ngFor. Because it's just JS, you get the full power of the language for free — you can call any function, use destructuring, compose helper components — but you also don't get templating-engine conveniences like automatic loop index variables or built-in "else" branches; you build those yourself with plain JS constructs.

It also means static analysis tools (TypeScript, ESLint) understand JSX natively as code, not as a string blob to be specially parsed — you get real type-checking on props and real "unused variable" warnings inside markup, something string-based templates historically couldn't offer without a custom compiler pass.

Code Example

  return (

        <li key={item.id}>{item.name}</li>
      ))}
    </ul>
  );
}

    Senior Engineer Perspective

    A strong answer contrasts "logic-less templates" (Mustache/Handlebars intentionally restrict logic to force separation of concerns) against JSX's philosophy: React deliberately colocates markup and logic in the same file, because the team decided that separating templates from the rendering logic that drives them was the wrong axis of separation — components (not template-vs-script) are the real unit of concern. That's a nuanced, senior-level framing beyond "JSX = HTML in JS."

    Q22. Why must JSX attribute names be camelCase, and which HTML attributes get renamed?

    ROI: ★★★☆☆ Frequency: Medium

    Short Answer

    JSX attributes become keys on a plain JavaScript props object, and several HTML attribute names collide with reserved words or established DOM property naming conventions — class is a JS reserved word (hence className), for is also reserved (hence htmlFor), and multi-word attributes follow JS's camelCase convention (onclick → onClick, tabindex → tabIndex) to match how the DOM's own JavaScript API already names them.

    Detailed Answer

    React props aren't really "HTML attributes" — they're arguments to a JavaScript function that eventually sets DOM properties (not raw HTML attribute strings) for most host elements. Since DOM properties in the JavaScript API were already camelCase (element.tabIndex, element.className), JSX matches that existing convention rather than the HTML-attribute spelling. A handful of exceptions exist for real-world compatibility: data-* and aria-* attributes stay hyphenated because they're not part of a fixed DOM property list and can be arbitrary.

    This also explains why passing a raw string like style="color:red" doesn't work — style expects a JS object of camelCase CSS properties ({ color: "red", backgroundColor: "blue" }), not a CSS string, because it's set via element.style properties, not the attribute.

    Code Example

    // HTML attribute -> JSX prop
<label className="title" htmlFor="email" tabIndex={0} onClick={handleClick}>
  Email
</label>

// style takes an object of camelCase properties, not a CSS string
<div style={{ backgroundColor: "papayawhip", fontSize: 14 }} />

// data-* and aria-* stay hyphenated (not fixed DOM properties)
<button data-testid="submit-btn" aria-pressed={isActive}>Save</button>

    Senior Engineer Perspective

    The differentiator answer is "React props map to DOM properties, not HTML attribute strings" — that single sentence explains className, htmlFor, the style-object requirement, and camelCase event names all at once, instead of memorizing them as unrelated exceptions. A sharp follow-up: "why do data-*/aria-* stay lowercase-hyphenated?" — because they're arbitrary custom/accessibility attributes without a corresponding fixed camelCase DOM property, so React passes them through as literal HTML attributes.

    Q23. How does JSX handle whitespace, comments, and boolean attributes?

    ROI: ★★★☆☆ Frequency: Medium

    Short Answer

    JSX trims leading/trailing whitespace on each line and collapses blank lines between elements, but preserves single spaces between inline text and elements on the same line. Comments must be JavaScript expressions inside braces ({/* ... */}) — HTML-style <!-- --> comments don't work. Boolean attributes shorthand to true when written without a value, matching HTML's boolean-attribute convention.

    Detailed Answer

    JSX's whitespace rule: it removes whitespace at the boundaries of each line, removes blank lines, and converts new-lines adjacent to tags into nothing, but a single space between text and an inline element on the same line is preserved (which is why <p>Hello {name}!</p> renders "Hello John!" with a space, not "HelloJohn!"). This trips people up when text wraps across lines in source — the renderer strips that line-wrap whitespace, so an explicit {" "} is sometimes needed to force a space.

    Because JSX comments must be expressions, {/* comment */} works (a comment inside a JS expression position), while a bare // comment on its own line inside JSX (outside braces) becomes literal rendered text.

    For boolean attributes, JSX mirrors JS: <input disabled /> is shorthand for disabled={true}, matching how HTML itself treats the mere presence of an attribute as truthy. Passing disabled={false} (or null/undefined) properly omits it, unlike raw HTML where writing disabled="false" would still count as present.

  return (
    <div>
      {/* this is a valid JSX comment */}
      <p>Hello</p>
    </div>
  );
}

// Whitespace: line-wrap whitespace is stripped; force a space with {" "}
<p>
  Hello
  {" "}
  {name}
</p>

// Boolean attribute shorthand

<input disabled={false} />  {/* attribute omitted entirely */}

    Senior Engineer Perspective

    The whitespace rule is a real bug source when text wraps across multiple JSX lines and a space silently disappears in production but was present in a one-line dev edit. Knowing the {" "} fix (or wrapping in a template literal) signals hands-on experience. On booleans, the sharp detail: unlike vanilla HTML where disabled="false" is still truthy (any string value means present), JSX/React respects the actual JS boolean value, which is a common source of confusion for engineers coming from plain HTML.

    Q24. What happens if you render an array, object, or plain string as JSX children?

    ROI: ★★★★☆ Frequency: High

    Short Answer

    Strings and numbers render as text nodes directly. Arrays of valid children (elements, strings, numbers) render each item in sequence — React will warn if items lack a key. Plain objects are not valid children and throw "Objects are not valid as a React child" at render time, because React has no idea how to serialize an arbitrary object into a DOM node.

    Detailed Answer

    React children resolve recursively: null, undefined, and booleans render nothing (which is exactly why {cond && <X/>} works — a false result is silently skipped), strings/numbers become text nodes, and elements/arrays are traversed. An array is fine as long as every entry is itself a valid child — this is precisely what .map() returns, so returning it directly into JSX (with keys) is completely standard, not a special case you need to wrap in anything.

    A raw object thrown into JSX (e.g. accidentally rendering {user} instead of {user.name}) is a runtime error, not a silent no-op — a valuable safety net that catches a whole class of "forgot to unwrap the field" bugs immediately in development, with a clear error naming the offending value's keys.

    Code Example

    function List({ items }) {
  // Array of elements — perfectly valid, just needs keys
  return <ul>{items.map((i) => <li key={i.id}>{i.name}</li>)}</ul>;
}

function Bad({ user }) {
  return <div>{user}</div>;
  // Error: Objects are not valid as a React child
  // (found: object with keys {name, email}).
}

function Fixed({ user }) {
  return <div>{user.name}</div>; // render a primitive field instead
}

// null/undefined/boolean render nothing — this is intentional and safe:

    Senior Engineer Perspective

    The "objects are not valid as a React child" error is one of the most common runtime errors juniors hit — usually from rendering an API response object directly, or forgetting to call a function that returns JSX. A senior answer explains why this is a hard error rather than a silent stringification: {}.toString() would produce the useless "[object Object]", so React fails loudly instead of shipping a broken UI. Also worth mentioning: this is one reason console.log-driven debugging inside JSX ({console.log(x)}) breaks — console.log returns undefined, which is safely a no-op child.

    Q25. How do JSX spread props work, and what are the risks of over-spreading?

    ROI: ★★★★☆ Frequency: High

    Short Answer

    {...props} inside a JSX tag spreads every key of an object as an individual prop, and is commonly used to forward "everything I didn't explicitly destructure" to an underlying element. It's convenient for wrapper components, but over-spreading (blindly forwarding an entire object, including unrelated fields, event handlers, or an id/key you didn't intend) can leak unwanted DOM attributes, override props unpredictably, or defeat memoization by passing a fresh object reference every render.

    Detailed Answer

    Order matters: later spread/explicit props override earlier ones. <Btn {...props} className="fixed" /> lets className win even if props.className exists; reversing the order lets the caller's spread silently clobber your intended default. This is a frequent source of "why isn't my className applying?" bugs.

    Passing an entire props/data object straight to a host DOM element (<div {...user} />) risks forwarding non-DOM attributes, which React will warn about (unknown attribute) or worse, silently pass through as a stray HTML attribute. The idiomatic pattern is to destructure the fields you own, and spread only the acknowledged "rest" onto the underlying element — exactly the prop-forwarding pattern used for wrapper/design-system components.

    Code Example

    // Safe: destructure what you own, forward the rest explicitly
function Button({ variant, children, ...rest }) {
  return (
    <button className={`btn btn-${variant}`} {...rest}>
      {children}
    </button>
  );
}
// <Button variant="primary" onClick={save} data-testid="save">Save</Button>
// -> onClick and data-testid flow through via {...rest}

// Order matters — later props win
<Button {...userStyles} className="always-wins" />   // className fixed
<Button className="may-be-overridden" {...userStyles} /> // risky

// Risky: spreading a raw data object straight onto a host element
<div {...product} />  // may leak unknown attrs like "price", "sku" onto the DOM

    Senior Engineer Perspective

    A design-system interview question almost always probes prop forwarding: "how do you let consumers pass arbitrary HTML attributes to your wrapped component without hardcoding every one?" — the rest-spread pattern shown above is the expected answer, along with knowing that spread order determines override precedence. Also flag the performance angle: spreading a freshly-created object (e.g. {...{ style: { color: "red" } }}) each render creates a new reference every time, which can defeat a memoized child even though the "same" values are being passed logically.

    Q26. Why can't you use an if statement directly inside JSX, and what are the workarounds?

    ROI: ★★★☆☆ Frequency: Medium

    Short Answer

    Because { } in JSX holds an expression, and if is a statement — it doesn't evaluate to a value the surrounding _jsx() call could use as a child. The workarounds are: use an expression-based equivalent (ternary, &&), move the branching above the return into a variable, or use an early return from the component function itself (which is a statement, but lives outside the JSX expression).

    Detailed Answer

    The cleanest style guidance: reach for the ternary/&& only for simple, single-branch decisions embedded in otherwise-static markup. For anything with 3+ branches, or logic that's hard to read inline, compute a variable (or call a small helper function) before the return statement — this is plain JavaScript, executed as normal statements, and then only the resulting value is dropped into JSX as an expression. For "should this component render at all," an early return null; (or return <Fallback/>;) at the top of the function body is idiomatic and keeps the main JSX tree free of top-level conditionals.

    Code Example

    function OrderStatus({ status, total }) {
  // Statement-based branching happens OUTSIDE the JSX expression
  if (!status) return null;               // early return, a statement, is fine here

  let banner;
  if (status === "error") banner = <ErrorBanner />;
  else if (status === "empty") banner = <EmptyState />;
  else banner = <OrderSummary total={total} />;

  return (
    <div>
      {banner}                                  {/* expression: a variable */}
      {status === "shipped" && <Tracking />}     {/* expression: && */}
    </div>
  );
}

    Senior Engineer Perspective

    Interviewers use this to see if a candidate reaches for readable patterns under pressure instead of nesting ternaries three levels deep. The senior answer names the real constraint precisely ("statements aren't expressions") rather than vaguely saying "JSX doesn't support if" — and demonstrates the idiom of computing branches as plain variables above the return, which scales far better than inline logic once a component has more than two conditional states.

    SECTION 7 - COMPONENT COMPOSITION VS INHERITANCE

    Q27. Why does React documentation explicitly favor composition over inheritance?

    ROI: ★★★★☆ Frequency: High

    Short Answer

    React never introduced a component class hierarchy mechanism for sharing UI behavior — there's no "specialized component extends generic component" idiom for props/rendering the way OOP inheritance works for objects. Every code-reuse need the React team has encountered (specialization, "has-a" containment, cross-cutting concerns) has been solvable with composition — passing components as props/children — which stays flexible and avoids the deep, fragile hierarchies that plague inheritance-based UI frameworks.

    Detailed Answer

    Inheritance couples a subclass tightly to its parent's implementation details — change a base class and every subclass may silently break ("fragile base class" problem). It also forces a single dimension of variation: a class can only extend one parent, so combining two independent behaviors (say, "sortable" and "resizable") requires awkward multiple-inheritance workarounds or deep hierarchies.

    Composition sidesteps both problems. A component that needs another component's behavior simply renders it, passing whatever data/callbacks it needs as props, or accepts pieces of UI as children/named prop "slots." Specialization ("this button, but bigger and blue") becomes a thin wrapper that renders the generic version with different props — not a subclass overriding methods. Cross-cutting concerns (logging, feature flags, data fetching) became custom hooks, which compose by calling one hook inside another — completely flat, no class hierarchy at all.

    Code Example

    // NOT how React does specialization (no such thing as component inheritance in practice)
// class FancyButton extends Button { ... }  // discouraged, rarely used, fragile

// Composition instead: FancyButton just renders Button with different props
function Button({ variant = "default", children, ...rest }) {
  return <button className={`btn btn-${variant}`} {...rest}>{children}</button>;
}
function FancyButton(props) {
  return <Button variant="fancy" {...props} />;
}

// "Has-a" containment via children, not a shared base class
function Panel({ children }) {
  return <section className="panel">{children}</section>;
}
<Panel>
  <FancyButton>Click me</FancyButton>
</Panel>

    Senior Engineer Perspective

    The trap is candidates who reflexively describe OOP inheritance patterns as if they map onto React. The strongest answer states plainly: "React components are functions, and functions compose by calling each other — there is no meaningful equivalent of extending behavior the way classes do, and every problem inheritance solves in OOP has a flatter, more flexible composition solution in React." Naming a concrete case (HOCs, render props, hooks, slots) as evidence you've actually applied this, not just recited it, is what separates a senior answer.

    Q28. What is the "render props" pattern, and why has it fallen out of favor?

    ROI: ★★★★☆ Frequency: High

    Short Answer

    A render prop is a component that accepts a function as a prop (often literally named render or passed as children) and calls that function with some internal state/data, letting the caller decide what UI to render with it. It was the pre-hooks way to share stateful logic across components without inheritance. It's fallen out of favor because custom hooks do the same job with far less nesting and better readability.

    Detailed Answer

    Before hooks (pre-16.8), if you wanted to share "track the mouse position" or "manage a toggle" logic across unrelated components, you couldn't extract it into a plain function — a component needed to actually own state and re-render. Render props solved this: a component owns the state/logic internally and exposes it by calling a function prop with the current value, letting each consumer decide the markup independently.

    The downside was structural: using two or three render-prop providers together produced deeply nested "wrapper hell" — indentation pyramids of callbacks that were hard to read and step through. Hooks solved the exact same reuse problem — sharing stateful logic — with a flat function call (const { x, y } = useMousePosition();), no nesting, no extra component in the tree, and full TypeScript inference. Render props still appear in some libraries (certain UI/animation libraries, and cases needing to control exactly what re-renders), but for new code, a custom hook is almost always the better fit.

    Code Example

    // Render-prop pattern (pre-hooks style)
class MouseTracker extends React.Component {
  state = { x: 0, y: 0 };
  handleMove = (e) => this.setState({ x: e.clientX, y: e.clientY });
  render() {
    return (
      <div onMouseMove={this.handleMove}>
        {this.props.render(this.state)}  {/* caller decides the UI */}
      </div>
    );
  }
}
// Usage — starts the nesting problem once you combine a few of these:
<MouseTracker render={({ x, y }) => <p>{x}, {y}</p>} />

// Modern equivalent: a custom hook, flat, no wrapper component
function useMousePosition() {
  const [pos, setPos] = React.useState({ x: 0, y: 0 });
  React.useEffect(() => {
    const handler = (e) => setPos({ x: e.clientX, y: e.clientY });
    window.addEventListener("mousemove", handler);
    return () => window.removeEventListener("mousemove", handler);
  }, []);
  return pos;
}
function Cursor() {
  const { x, y } = useMousePosition();  // no nesting, just a function call
  return <p>{x}, {y}</p>;
}

    Senior Engineer Perspective

    Expect "have you seen wrapper hell?" — describe stacking three or four render-prop providers and how the resulting indentation obscured the actual UI tree. The senior insight is naming exactly what hooks fixed: reusing stateful logic without needing an extra component instance in the tree and without the nesting cost. Also worth knowing: render props are still the right tool in a few places — e.g. when a library must control precisely which subset of the tree re-renders on each internal state tick (some virtualization/animation libraries still use them for that reason).

    Q29. How do you replace a render-prop component with a custom hook?

    ROI: ★★★☆☆ Frequency: Medium

    Short Answer

    Move the class's state and lifecycle logic into a function named useX, replace this.setState with useState/useReducer, replace lifecycle methods with a useEffect, and return the values the render prop used to receive as arguments. Every call site drops the wrapper component and calls the hook directly.

    Detailed Answer

    The migration is mechanical once you see the mapping: the render-prop component's state becomes the hook's useState; the render-prop component's lifecycle methods (subscribe on mount, unsubscribe on unmount) become a single useEffect with cleanup; the values passed into render(state) become the hook's return value. The consuming component no longer needs to be structured around "a function-as-child" — it just destructures the hook's return value directly in its own body, which also means the consumer only re-renders itself, not through an extra wrapper component's render cycle.

    Code Example

    // BEFORE: render-prop component
class WindowSize extends React.Component {
  state = { width: window.innerWidth };
  onResize = () => this.setState({ width: window.innerWidth });
  componentDidMount() { window.addEventListener("resize", this.onResize); }
  componentWillUnmount() { window.removeEventListener("resize", this.onResize); }
  render() { return this.props.children(this.state); }
}
// <WindowSize>{({ width }) => <p>{width}</p>}</WindowSize>

// AFTER: custom hook — same logic, no wrapper component, no nesting
function useWindowWidth() {
  const [width, setWidth] = React.useState(window.innerWidth);
  React.useEffect(() => {
    const onResize = () => setWidth(window.innerWidth);
    window.addEventListener("resize", onResize);
    return () => window.removeEventListener("resize", onResize);
  }, []);
  return width;
}
function Page() {
  const width = useWindowWidth();
  return <p>{width}</p>;
}

    Senior Engineer Perspective

    This is a realistic legacy-migration question at companies with older codebases. The strong answer walks the mapping out loud (state → useState, lifecycle → useEffect, render(state) → return value) rather than just producing the end code, because interviewers are checking whether you understand why the transformation is safe, not just that you've memorized the "modern" syntax. Mention that this migration also removes an extra component from the React DevTools tree and from the render-commit cycle.

    Q30. What is a Higher-Order Component (HOC), and what pitfalls does it introduce?

    ROI: ★★★★☆ Frequency: High

    Short Answer

    A HOC is a function that takes a component and returns a new, enhanced component — const Enhanced = withX(MyComponent). It's a composition pattern for injecting props or behavior (auth checks, data fetching, theming) into any component without modifying its source. Pitfalls: prop naming collisions, wrapper-hell in the component tree/DevTools, ref forwarding requires explicit handling, and static methods on the original component don't automatically carry over to the wrapped one.

    Detailed Answer

    A HOC is literally a higher-order function applied to components: it accepts a component type and returns another component type that typically renders the original with extra/derived props. Common historical examples: connect() from Redux, withRouter() from React Router.

    Pitfalls in practice:

    • Naming collisions — if the HOC injects a prop named data and the wrapped component also receives a caller-provided data prop, one silently overwrites the other depending on merge order.
    • Wrapper hell in DevTools — stacking several HOCs (withAuth(withTheme(withData(Component)))) produces a deep, hard-to-read component tree, and debugging requires you to mentally unwrap each layer.
    • Refs don't pass through automatically — a ref attached to the wrapped export attaches to the outer HOC wrapper, not the inner component, unless the HOC explicitly uses React.forwardRef.
    • Static methods are lost — if the original component had static properties, the returned component doesn't inherit them unless you manually hoist them (e.g. via hoist-non-react-statics).

    Custom hooks solve most of these use cases today without any of these structural costs, which is why HOCs are largely legacy for new code — though they still appear in some library APIs and for cases genuinely about wrapping the rendered output (not just sharing logic).

    Code Example

    function withLoading(Component) {
  return function WithLoading({ isLoading, ...rest }) {
    if (isLoading) return <Spinner />;
    return <Component {...rest} />;
  };
}
const UserListWithLoading = withLoading(UserList);

// Ref pitfall — needs explicit forwardRef to pass through
function withLogger(Component) {
  return React.forwardRef(function WithLogger(props, ref) {
    console.log("rendering", Component.name);
    return <Component ref={ref} {...props} />;
  });
}

    Senior Engineer Perspective

    Interviewers who've maintained Redux/React Router-era code enjoy this question because it separates people who've felt the pain from people who've only read about hooks. Naming the naming-collision bug and the ref-forwarding gotcha unprompted is a strong signal. A good closing line: "HOCs are still fine as a pattern for wrapping rendered output (e.g. an error boundary wrapper), but for sharing stateful logic, a hook is strictly better — flatter, typed more easily, and doesn't add a node to the component tree."

    Q31. How do "slot" patterns work in React when you need multiple content areas?

    ROI: ★★★☆☆ Frequency: Medium

    Short Answer

    React has no built-in "named slot" syntax (unlike Vue), but the same effect is achieved by accepting multiple elements as separate props — header, footer, sidebar — alongside the default children slot. Each named prop is just a value of type "React node" that the layout component renders wherever it chooses.

    Detailed Answer

    Because JSX elements are plain values, any prop can hold one — there's nothing structurally different between passing a string, a number, or a fully-built <Toolbar/> element as a prop. This makes multi-slot layouts trivial: the layout component destructures each named prop and places it in the right spot in its own markup, while children remains the conventional "default/main" slot.

    A more advanced variant uses compound components (Q32) with sub-components like <Layout.Header>/<Layout.Sidebar> that the parent detects and rearranges — but for most layouts, simple named-prop slots are enough and far easier to reason about.

    Code Example

    function PageLayout({ header, sidebar, children, footer }) {
  return (
    <div className="page">
      <header>{header}</header>
      <div className="body">
        <aside>{sidebar}</aside>
        <main>{children}</main>  {/* default slot */}
      </div>
      <footer>{footer}</footer>
    </div>
  );
}

// Usage — each slot is just a prop holding an element
<PageLayout
  header={<TopNav />}
  sidebar={<FilterPanel />}
  footer={<Copyright />}
>
  <ProductGrid />
</PageLayout>

    Senior Engineer Perspective

    The follow-up worth anticipating: "why doesn't React need a special slot syntax like Vue's <template #header>?" — because props already are that mechanism; there's no separate concept needed since any prop can be a rendered element. A senior also flags the trade-off: too many named slots on one component (six or seven) is a smell that the component is trying to do too much layout orchestration — often better split into smaller composed pieces the caller assembles directly with JSX.

    Q32. What is the "compound components" pattern, and when do you reach for it?

    ROI: ★★★★☆ Frequency: High

    Short Answer

    Compound components are a set of components that work together and share implicit state (usually via Context), where the parent renders as a group of related children (<Tabs><Tabs.List>...<Tabs.Panel>...</Tabs>) instead of taking one giant configuration-object prop. It's the go-to pattern for flexible, composable UI widgets — tabs, accordions, menus, selects — where the caller controls layout/order/styling of the pieces while the parent manages shared behavior.

    Detailed Answer

    Compare two API styles for a Tabs widget: a monolithic <Tabs items={[{label, content}, ...]} /> forces all data through one prop and constrains layout to whatever the component author anticipated. A compound-component API instead exposes Tabs, Tabs.List, Tabs.Tab, and Tabs.Panel as separate pieces that communicate through a shared Context created by the outer Tabs — the caller freely arranges, styles, or conditionally renders any piece while the parent still owns which tab is active.

    This buys huge flexibility (want an icon next to only one tab? Add it directly in JSX) without exploding the parent's prop surface into dozens of render-prop-like configuration options. The cost is slightly more setup code (a Context + sub-components) and an implicit coupling — the sub-components only work when rendered inside the correct parent, which needs a runtime guard/clear error message if misused.

    Code Example

    const TabsContext = React.createContext(null);

function Tabs({ defaultValue, children }) {
  const [active, setActive] = React.useState(defaultValue);
  return (
    <TabsContext.Provider value={{ active, setActive }}>
      <div className="tabs">{children}</div>
    </TabsContext.Provider>
  );
}
function useTabsContext() {
  const ctx = React.useContext(TabsContext);
  if (!ctx) throw new Error("Tabs.* must be rendered inside ");
  return ctx;
}
Tabs.Tab = function Tab({ value, children }) {
  const { active, setActive } = useTabsContext();
  return (
    <button
      className={active === value ? "tab active" : "tab"}
      onClick={() => setActive(value)}
    >
      {children}
    </button>
  );
};
Tabs.Panel = function Panel({ value, children }) {
  const { active } = useTabsContext();
  return active === value ? <div className="panel">{children}</div> : null;
};

// Usage — caller freely arranges the pieces
<Tabs defaultValue="profile">
  <Tabs.Tab value="profile">Profile</Tabs.Tab>
  <Tabs.Tab value="billing">Billing</Tabs.Tab>
  <Tabs.Panel value="profile">Profile form...</Tabs.Panel>
  <Tabs.Panel value="billing">Billing form...</Tabs.Panel>
</Tabs>

    Senior Engineer Perspective

    This is a favorite senior/staff-level question because it directly tests judgment on API design, not just React mechanics. The strongest answers explain the trade-off explicitly: compound components buy layout flexibility at the cost of an implicit contract between parent and children (they must be rendered together), and mention guarding that contract with a context-null check that throws a clear error rather than failing silently. Bonus: mention that this is exactly how headless UI libraries (Radix, Headless UI, React Aria) are built — logic/accessibility in the parent, full rendering freedom in the consumer.

    Q33. How do you type or constrain children when you need more than "any renderable node"?

    ROI: ★★★☆☆ Frequency: Medium

    Short Answer

    In TypeScript, children?: React.ReactNode is the general-purpose type for "anything renderable." When a component only makes sense with a specific shape of children (e.g. only <Tabs.Tab> elements, or exactly one function), you narrow the type to React.ReactElement, a function-as-children signature, or validate/filter the actual children at runtime with React.Children utilities.

    Detailed Answer

    React.Children.map/forEach/count/only/toArray exist specifically because props.children can be a single node, an array, or nested fragments — inconsistent shapes that plain array methods can't safely traverse. React.Children.only throws unless there is exactly one child, useful for components (like forwardRef wrappers or certain animation libraries) that structurally require a single element to clone/attach a ref to. React.Children.map safely flattens and iterates regardless of whether children is one node or many.

    For "render prop as children" (function-as-children), the type is simply a function signature: children: (state: T) => React.ReactNode. For a compound-component parent that only wants to accept its own sub-components, most codebases rely on convention plus a runtime guard rather than trying to statically forbid other children — TypeScript can't easily express "only children of type X" beyond loose ReactElement<typeof Tab> unions.

    Code Example

    import type { ReactNode, ReactElement } from "react";

// General case — anything renderable
function Card({ children }: { children: ReactNode }) {
  return <div className="card">{children}</div>;
}

// Exactly one child required (e.g. to clone a ref onto it)
function SingleChildWrapper({ children }: { children: ReactElement }) {
  const only = React.Children.only(children); // throws if not exactly one
  return React.cloneElement(only, { className: "wrapped" });
}

// Function-as-children (render prop) signature
function DataProvider({ children }: { children: (data: string[]) => ReactNode }) {
  const data = ["a", "b"];
  return <>{children(data)}</>;
}

// Iterate safely regardless of single node vs array vs fragment
function Toolbar({ children }: { children: ReactNode }) {
  return (
    <div className="toolbar">
      {React.Children.map(children, (child, i) => (
        <div key={i} className="toolbar-item">{child}</div>
      ))}
    </div>
  );
}

    Senior Engineer Perspective

    Interviewers building design systems will ask why React.Children.map exists instead of just calling children.map — the answer is that children isn't guaranteed to be an array (a single child is passed as a bare value, not a one-item array), so naive array methods throw. Mentioning React.Children.only's use for ref-cloning wrapper components (common in animation libraries like react-transition-group) is a strong, specific signal of real design-system experience.

    Q34. When is inheritance (extending a class component) still technically used, if ever?

    ROI: ★★☆☆☆ Frequency: Low

    Short Answer

    Practically never for sharing behavior between your own components — that's what composition and hooks are for. The one legitimate remaining use of extends React.Component is defining an error boundary, since getDerivedStateFromError/componentDidCatch currently have no hook equivalent. Extending someone else's component to override its methods is discouraged and rare even in legacy code.

    Detailed Answer

    You will still write class X extends React.Component once in most modern codebases — for the app's error boundary — because there is no useErrorBoundary hook (as of React 19). Beyond that single case, "inheriting" from a component to specialize its rendering is almost never seen even in older React code; the community's actual historical pattern for logic reuse in the class era was HOCs/render props (composition), not literal class Fancy extends Plain chains, because class inheritance for UI components suffers from exactly the fragile-base-class problems described in Q27.

    Some teams wrap the error-boundary class once and never touch it again, using a small library (react-error-boundary) that exposes a component API without requiring the team to hand-write the class themselves.

    Code Example

    // One of the only remaining legitimate uses of class + inheritance:
class AppErrorBoundary extends React.Component {
  state = { hasError: false };
  static getDerivedStateFromError() { return { hasError: true }; }
  componentDidCatch(error, info) { logToService(error, info); }
  render() {
    if (this.state.hasError) return <h1>Something went wrong.</h1>;
    return this.props.children;
  }
}
// Everything else in a modern codebase is function components + hooks + composition.

    Senior Engineer Perspective

    This question tests whether a candidate over-claims "inheritance is completely dead in React." The precise, defensible answer names the one real exception (error boundaries) rather than a blanket absolute, and explains why that exception exists (no hook API for it yet) rather than treating it as arbitrary. It's also a chance to mention libraries like react-error-boundary that let a team never hand-write that one class themselves.

    SECTION 8 - CONTROLLED VS UNCONTROLLED COMPONENTS DEEP DIVE

    Q35. How do you handle file inputs in React, and why are they always uncontrolled?

    ROI: ★★★★☆ Frequency: High

    Short Answer

    A file input's value can only ever be set to an empty string by JavaScript (for security reasons — a page must never be able to script in an arbitrary file path to auto-upload something the user didn't explicitly pick). Since React can't set the DOM value to the selected file, <input type="file"> is structurally uncontrolled: you read the selected file(s) from e.target.files in the change handler, or via a ref, and store the File object(s) in state yourself.

    Detailed Answer

    The browser enforces this restriction regardless of framework — it's not a React limitation. What you store in React state is not the input's "value" but the File/FileList object(s) extracted from the change event, which you then use for validation (size, type), preview (via URL.createObjectURL), or upload (via FormData). To reset the visible filename in the UI (e.g. after a successful upload), you cannot set value — you must either uncontrolled-reset via ref.current.value = "", or remount the input entirely by changing its key.

    Code Example

    function FileUpload() {
  const inputRef = React.useRef(null);
  const [file, setFile] = React.useState(null);

  function handleChange(e) {
    setFile(e.target.files[0] ?? null);
  }

  function clear() {
    setFile(null);
    if (inputRef.current) inputRef.current.value = ""; // only way to reset the visible name
  }

  return (
    <>
      <input type="file" ref={inputRef} onChange={handleChange} accept="image/*" />
      {file && <p>{file.name} ({Math.round(file.size / 1024)} KB)</p>}
      <button onClick={clear}>Clear</button>
    </>
  );
}

    Senior Engineer Perspective

    The key insight interviewers want: this is a browser security constraint, not a React design choice — no framework can make file inputs controlled. A strong follow-up: "how do you reset a file input?" — either via a ref's .value = "", or the cleaner React-idiomatic trick of changing the input's key prop, which forces React to unmount and remount a fresh DOM node (and thus a genuinely empty input) instead of fighting the DOM directly.

    Q36. How do you build a "reset to default" feature for an uncontrolled form?

    ROI: ★★★☆☆ Frequency: Medium

    Short Answer

    Since uncontrolled fields hold their own value in the DOM, resetting them means either (1) calling the native <form>.reset() method, which restores every field to its defaultValue/defaultChecked, or (2) forcing a remount by changing a key on the form/fields, which throws away the old DOM nodes (and their in-progress values) and creates fresh ones initialized from the current defaultValue props.

    Detailed Answer

    form.reset() is the standard, cheap approach and works exactly like a plain HTML form reset button — it doesn't require React state at all, since uncontrolled fields' "source of truth" is the DOM's own default-value bookkeeping. The key-remount trick is more powerful: it's necessary when the "default" itself needs to change dynamically (e.g. resetting to a newly-fetched server record rather than the field's original static defaultValue), since changing a key forces React to discard the whole subtree and build it fresh from the current props.

    Code Example

    // Approach 1: native form.reset() — works with defaultValue fields
function ProfileForm() {
  const formRef = React.useRef(null);
  return (
    <form ref={formRef}>
      <input name="name" defaultValue="Ada" />
      <input name="email" defaultValue="ada@example.com" />
      <button type="button" onClick={() => formRef.current.reset()}>
        Reset
      </button>
    </form>
  );
}

// Approach 2: key-remount — needed when the "default" itself changed
function EditableRecord({ record }) {
  const [resetToken, setResetToken] = React.useState(0);
  return (
    <form key={`${record.id}-${resetToken}`}>
      <input name="name" defaultValue={record.name} />
      <button type="button" onClick={() => setResetToken((n) => n + 1)}>
        Discard changes
      </button>
    </form>
  );
}

    Senior Engineer Perspective

    Interviewers use this to see whether you reach for the framework's escape hatches sensibly instead of over-engineering state tracking for something the DOM already does natively. Volunteer both techniques and the distinction between them: form.reset() for static defaults, key-remount for dynamic defaults that can change after the initial render — that distinction is the senior-level nuance most candidates miss.

    Q37. What are the trade-offs of controlled checkboxes/radio groups vs uncontrolled?

    ROI: ★★★☆☆ Frequency: Medium

    Short Answer

    Controlled checkboxes/radios (checked + onChange) let you enforce constraints in real time — e.g. "at most 3 selected," mutually-exclusive groups spanning multiple physical radio inputs, or syncing a "select all" master checkbox with individual children. Uncontrolled ones (defaultChecked, read via ref/FormData on submit) are simpler and cheaper when you only need the final selection at submit time, like a native form.

    Detailed Answer

    A classic controlled use case is a "select all" checkbox that must reflect an indeterminate state when some but not all children are checked — that partial state can only be driven by React because it depends on aggregating sibling state, something the DOM's native radio-group behavior can't express on its own. Controlled checkbox lists also make live validation trivial (disable further selection once a max count is hit).

    For a simple form of independent checkboxes submitted together (like a settings page saved with one Save button), uncontrolled is perfectly fine and avoids a re-render per click — you just read new FormData(formEl) on submit, which natively collects every checked box's name/value.

    Code Example

    // Controlled: enforce "max 3 selected" and a synced select-all
function TagPicker({ tags }) {
  const [selected, setSelected] = React.useState([]);
  const maxReached = selected.length >= 3;

  function toggle(tag) {
    setSelected((prev) =>
      prev.includes(tag) ? prev.filter((t) => t !== tag)
        : maxReached ? prev : [...prev, tag]
    );
  }

  return tags.map((tag) => (
    <label key={tag}>
      <input
        type="checkbox"
        checked={selected.includes(tag)}
        disabled={maxReached && !selected.includes(tag)}
        onChange={() => toggle(tag)}
      />
      {tag}
    </label>
  ));
}

// Uncontrolled: read everything at submit time via FormData
function Settings() {
  function handleSubmit(e) {
    e.preventDefault();
    const data = new FormData(e.target);
    console.log(data.getAll("notifications")); // native aggregation
  }
  return (

    Q38. How does React Hook Form achieve performance using uncontrolled inputs?

    ROI: ★★★★☆ Frequency: High

    Short Answer

    React Hook Form registers each field via a ref ({...register("email")}) instead of driving its value from React state, so keystrokes update the DOM directly without triggering a React re-render on every character. It reads current values on demand (validation, submit) directly off the DOM nodes via their refs, giving you form-state benefits (validation, dirty/touched tracking) without paying a re-render per keystroke across the whole form.

    Detailed Answer

    In a fully controlled form with many fields, every keystroke in any field re-renders the whole form component (unless every field is individually memoized) because the state lives at the top and updates its setter on each change. React Hook Form flips the ownership: the DOM node itself is the source of truth during typing (uncontrolled), and the library subscribes to native input events via the registered ref to track values internally without funneling every keystroke through React state/re-renders. Re-renders happen only for fields explicitly subscribed to (e.g. via watch) or when validation errors need to be displayed for a specific field.

    The trade-off: you give up the always-fresh reactive value in the render for most fields, which is why "watching" a field for e.g. a live preview does trigger a subscription and a targeted re-render — you opt into controlled behavior only where you actually need it.

    Q39. What is a hybrid controlled/uncontrolled pattern, and when would you use one?

    ROI: ★★★☆☆ Frequency: Medium

    Short Answer

    A hybrid ("uncontrolled with an optional controlled override") component supports an internal defaultValue/self-managed state for simple usage, but also accepts an optional value/onChange pair that — when provided — makes the parent the source of truth instead. This is the pattern most headless UI libraries (Radix, React Aria) use so a component works standalone out of the box, yet can be fully controlled when an app needs to synchronize it with external state.

    Detailed Answer

    The implementation checks whether a value prop was supplied: if it was, the component's internal state is ignored and every read/write goes through the caller's value/onChange; if not, it falls back to an internal useState seeded from defaultValue. This is exactly how native HTML form elements already behave (uncontrolled by default via defaultValue, but you can drive them via scripted .value assignment), and mirrors it for a custom component's public API.

    The tricky part is deciding "controlled-ness" once and sticking with it — switching a component between controlled and uncontrolled mid-life is exactly the anti-pattern from Q41, so a robust hybrid implementation checks this on the first render and warns (or asserts) if a caller flips modes later.

  const current = isControlled ? value : internal;

    if (!isControlled) setInternal(next);
    onChange?.(next); // always notify the caller, controlled or not
  }
  return [current, setValue];
}

    Q40. How do you validate input in real time without re-rendering on every keystroke?

    ROI: ★★★☆☆ Frequency: Medium

    Short Answer

    Keep the field itself uncontrolled (or controlled but cheap), and run validation on the blur event (or a debounced change) instead of on every onChange. Only commit the error message to state when validation actually needs to display something — most keystrokes shouldn't produce a state update at all if the field is currently valid.

    Detailed Answer

    A naive implementation calls setError(validate(value)) in every onChange, which re-renders the field (and often the whole form) on every keystroke regardless of whether the error message actually changed. A better approach validates on blur for "did you make a mistake" feedback (the common UX pattern: don't yell at users mid-typing), and only re-validates on change once a field has already been touched and previously had an error — so a user actively fixing a mistake gets immediate positive feedback, but a user still typing their first pass isn't interrupted every keystroke.

    Debouncing async validation (e.g. "is this username taken?") is the other half — wrap the check in a debounce so a network call only fires after typing pauses, not on every character.

    Code Example

    function EmailField() {
  const [email, setEmail] = React.useState("");
  const [touched, setTouched] = React.useState(false);
  const [error, setError] = React.useState("");

  function validate(value) {
    return /\S+@\S+\.\S+/.test(value) ? "" : "Enter a valid email";
  }

  function handleChange(e) {
    const value = e.target.value;
    setEmail(value);
    if (touched) setError(validate(value)); // only re-validate live once already touched
  }

  function handleBlur() {
    setTouched(true);
    setError(validate(email)); // first validation happens on blur, not per keystroke
  }

  return (
    <>
      <input value={email} onChange={handleChange} onBlur={handleBlur} />
      {touched && error && <span className="error">{error}</span>}
    </>
  );
}

    Senior Engineer Perspective

    The senior distinction is UX-driven, not just performance-driven: validating on every keystroke before the user has even finished typing feels hostile, while validating only on blur the first time (then live once touched) matches how most polished production forms behave.     Q41. What breaks when you conditionally switch an input between controlled and uncontrolled?

    ROI: ★★★★☆ Frequency: High

    Q42. How would you implement a debounced controlled search input correctly?

    ROI: ★★★★☆ Frequency: High

    Short Answer

    Keep the input itself fully controlled and responsive on every keystroke (so typing never feels laggy), but debounce the expensive side effect — the API call or filter — in a separate piece of state/effect. Never debounce the input's own value/onChange, or the visible text will lag behind what the user is typing.

    Detailed Answer

    The input's local state updates immediately and synchronously on every change — this is cheap and must stay instant for good UX. Debouncing belongs in the code that reacts to the value (a search request, a heavy computation), typically via a useEffect whose dependency is the raw query, using a setTimeout/cleanup pair, or a useDeferredValue for purely render-cost (not network) debouncing in React 18+. The cleanup function is what makes this correct — each keystroke cancels the previous pending timer, so only the value after the user pauses actually fires the expensive work.

    Code Example

  }, [query, onSearch]);

  return (
    <input
      value={query}                              // always reflects every keystroke instantly
      onChange={(e) => setQuery(e.target.value)}
      placeholder="Search..."
    />
  );
}

    SECTION 9 - KEYS & RECONCILIATION BASICS

    Q43. Walk through React's diffing algorithm at a high level — how does it avoid O(n^3) tree diff?

    ROI: ★★★★★ Frequency: Extremely High

    Short Answer

    A generic tree-diff algorithm is O(n³) in the number of nodes, which is unusable for UI trees with thousands of nodes. React's reconciler makes it O(n) by applying two heuristics: (1) elements of different types at the same position produce entirely different trees — React tears down the old subtree and builds a new one rather than trying to diff their contents; (2) elements of the same type are diffed by comparing props and recursing into children, and for lists specifically, key tells React which children are "the same" across renders so it only needs to compare siblings, never search the whole tree for a match.

    Detailed Answer

    Without any heuristics, matching two arbitrary trees optimally (finding the minimum edit distance between them) is prohibitively expensive at UI scale. React's reconciler trades a small amount of "sometimes rebuilds slightly more than the true minimum" for a huge constant-time-per-node win, by assuming: different component/element types at the same tree position are unrelated (no cross-type diffing attempted — a <div> that becomes a <span> just unmounts the div's whole subtree and mounts a fresh span subtree, discarding all its state); and within a list, key equality — not index position — determines identity across renders.

    These two rules turn an O(n³) general problem into an O(n) single pass: at each level, React only ever compares a node against its counterpart at the same position (or same key within a keyed list), never against arbitrary other nodes elsewhere in the tree.

    Code Example

    // Rule 1: different type at the same position -> full unmount/remount,
// even though visually similar, state is NOT preserved
{isEditing ? <input value={text} /> : <span>{text}</span>}
// Switching isEditing destroys/rebuilds the DOM node each time (different types)

// Rule 2: same type -> React diffs props/attributes and recurses into children,
// preserving the underlying DOM node and any internal component state
{isPrimary ? <button className="primary">Go</button>
           : <button className="secondary">Go</button>}
// Same "button" type -> same DOM node reused, only className prop patched

    Senior Engineer Perspective

    Interviewers use this to separate people who've read the reconciliation docs from people who've internalized the trade-off. The precise framing to give: React deliberately accepts a heuristic, not an optimal diff, because optimal tree diffing doesn't scale to real UI sizes. A great follow-up: "does this mean type changes are always expensive?" — yes, a type change at a given tree position always discards and rebuilds that subtree's DOM and component state, which is exactly why toggling between two structurally similar elements (like the input/span example) can cause visible flicker or lost focus unless you deliberately keep the type stable.

    Q44. What specifically happens during reconciliation when a key changes but the type doesn't (or vice versa)?

    ROI: ★★★★☆ Frequency: High

    Short Answer

    React treats (type, key) together as an element's identity at a given position. If the type changes, React unmounts the old subtree and mounts a new one regardless of key. If only the key changes but the type stays the same, React still unmounts the old instance and mounts a fresh one — a changed key is an explicit signal "this is a different logical item," even if it happens to render the same component type.

    Detailed Answer

    This is why "change the key to force a remount" is a legitimate, commonly used pattern (Q45) — it deliberately exploits the fact that key is part of identity, not just a list-diffing hint. Conversely, if both type and key stay the same across a render, React preserves the DOM node and the component's internal state (hooks, refs) and only patches whatever props actually changed — this is the "same identity, updated props" path that makes most re-renders cheap and non-destructive.

    Q47. How should keys behave with paginated or infinite-scrolling lists?

    ROI: ★★★☆☆ Frequency: Medium

    Short Answer

    Keys only need to be unique among current siblings, not globally across the whole app or across pages — so as pages are appended, continue keying by each item's own stable id; you don't need to prefix keys with a page number unless the same id can legitimately appear twice across different pages (a data bug, not a React concern). The real risk in paginated/infinite lists is accidental key collisions when a "loading" placeholder row or a duplicate item from an overlapping page slips in without a truly unique id.

    Detailed Answer

    As new pages are appended to the array driving the list, each new item still gets keyed by its own id — React simply extends the existing keyed list with new keyed entries, which is the cheap "insert at the end" case reconciliation handles efficiently regardless of list length.     Q48. Can two sibling elements share the same key? What actually happens?

    ROI: ★★★☆☆ Frequency: Medium

    Short Answer

    Q50. What's the difference between reconciliation and "rendering" vs "committing"?

    ROI: ★★★★☆ Frequency: High

    Short Answer

    "Rendering" is React calling your component functions to produce a new element tree — pure computation, no DOM touched yet. "Reconciliation" is the diffing step that compares the new tree against the previous one to figure out the minimal set of changes. "Committing" is the phase where React actually applies those changes to the real DOM (and runs effects). Render and reconcile can, in concurrent React, be paused/abandoned/restarted; the commit phase is always synchronous and uninterruptible once it starts.

    Detailed Answer

    • Render phase — component functions run, hooks execute, a new element tree is produced. This phase must be pure (no DOM mutation, no visible side effects) precisely because React may call it more than once per commit under concurrent features (and always twice in development under StrictMode).
    • Reconciliation — technically part of the render phase's bookkeeping: the new tree is diffed against the last committed tree using the type/key rules (Q43/Q44) to compute an internal list of DOM operations.
    • Commit phase — React applies the computed DOM mutations, attaches refs, and runs layout effects synchronously, then browser paints, then passive effects (useEffect) run. This phase cannot be interrupted — once commit starts, it runs to completion.

    This split is exactly what makes concurrent rendering possible: React can start rendering a new tree, pause partway through if something more urgent comes in (a click), throw away or resume the in-progress work, all without the user ever seeing a half-applied DOM — because nothing touches the real DOM until the uninterruptible commit phase.

    Code Example

    function Counter() {
  console.log("render phase — pure computation only");
  const [count, setCount] = React.useState(0);

  React.useLayoutEffect(() => {
    console.log("commit phase — DOM already updated, runs before paint");
  });

  React.useEffect(() => {
    console.log("after commit + paint — passive effect");
  });

  return <button onClick={() => setCount(c => c + 1)}>{count}</button>;
}
// Order per update: render (may run twice in StrictMode) -> reconcile -> commit
// (DOM mutations + useLayoutEffect) -> browser paints -> useEffect

    Senior Engineer Perspective

    This three-way split is core to understanding React 18's concurrent features, and interviewers use it to gauge whether a candidate can reason about why render must be pure — not just recite "don't cause side effects in render" as a rule handed down from documentation. The strongest answers explain the causal chain: render/reconcile are interruptible and repeatable, so they must be side-effect-free; commit is where it's finally safe to touch the real world, which is why refs are only guaranteed attached and DOM measurements only reliable after commit (in useLayoutEffect or later).

    SECTION 10 - PORTALS & FRAGMENTS

    Q51. What are the concrete use cases for createPortal beyond modals?

    ROI: ★★★★☆ Frequency: High

    Short Answer

    Anything that must visually escape a parent's clipping/stacking context while staying logically part of the React tree: tooltips and popovers (which need to render above everything, unclipped by a scrollable ancestor), toast/notification stacks (rendered once at the app root regardless of which component triggered them), context menus, dropdown menus that must overlay a table with overflow: hidden, and drag-preview layers.

    Detailed Answer

    The common thread across all these cases is the same problem modals have: an ancestor with overflow: hidden, a fixed z-index stacking context, or `position: relative` clipping would otherwise trap the element visually, even though logically it belongs deep in a specific component's tree (e.g. a tooltip attached to one specific button inside a scrollable card). A portal renders the actual DOM node at the document root (or another dedicated container) while keeping the JSX — and therefore the component's state, context, and event handlers — exactly where it's authored in the tree.

    A second, less obvious use: rendering into an iframe's own document, or into a DOM node managed by a non-React library the app is embedded inside (a legacy widget host), where React needs to inject UI into a foreign container it doesn't otherwise control.

    Code Example

    import { createPortal } from "react-dom";

function Tooltip({ anchorRect, children }) {
  // Escapes any ancestor's overflow:hidden/z-index by rendering at the body root
  return createPortal(
    <div
      className="tooltip"
      style={{ position: "fixed", top: anchorRect.bottom, left: anchorRect.left }}
    >
      {children}
    </div>,
    document.body
  );
}

function ToastStack({ toasts }) {
  // One shared container, filled by toasts triggered from anywhere in the tree
  return createPortal(
    <div className="toast-stack">
      {toasts.map((t) => <div key={t.id} className="toast">{t.message}</div>)}
    </div>,
    document.getElementById("toast-root")
  );
}

    Senior Engineer Perspective

    The unifying principle to state clearly: "portals solve a CSS/stacking-context problem, not a state-management problem — they exist purely so DOM position and React-tree position can differ." That framing lets you recognize new use cases (an iframe, a third-party widget container) without needing them explicitly listed. Also worth mentioning: portals don't change anything about data flow — props, context, and state work identically whether or not the output is portaled, which is precisely why they're safe to introduce late in a component's life without restructuring its logic.

    Q52. How does event bubbling actually work through a portal, step by step?

    ROI: ★★★★☆ Frequency: High

    Short Answer

    React dispatches events according to the React component tree, not the DOM tree. So when a native event fires inside a portaled node, it still bubbles up through the ancestors of where the portal was rendered from in your JSX — not through the DOM ancestors of the portal's actual target container. A click inside a modal portaled to document.body can still trigger an onClick handler on a logical React parent, even though that parent's real DOM node doesn't physically contain the modal.

    Detailed Answer

    React's single root listener (Q13) captures the native event at the actual DOM location where it occurred, then walks up the React fiber tree (the internal representation of your component tree) — not the DOM — dispatching synthetic events to each ancestor's handler in turn. Since a portaled child's fiber is still parented under the component that called createPortal (only its rendered DOM node lives elsewhere), the synthetic event bubbling honors that logical parent-child relationship, ignoring where the DOM node physically sits.

    This is why a portaled dropdown or modal can still be closed by a parent's "click outside to dismiss" handler implemented via bubbling, and why e.stopPropagation() inside the portal stops the event from reaching React ancestors, even though, at the raw DOM level, the event never physically passed through those ancestors' DOM nodes at all.

    Code Example

    function App() {
  // This handler fires for clicks inside the portal too — React bubbling
  // follows the component tree, not the DOM tree.
  return (
    <div onClick={() => console.log("App-level click handler fired")}>
      <Modal />
    </div>
  );
}

function Modal() {
  return createPortal(
    <div className="overlay">
      {/* DOM-wise this button lives in document.body, NOT inside App's div.
          Yet clicking it still logs "App-level click handler fired". */}
      <button>Click me</button>
    </div>,
    document.body
  );
}

    Senior Engineer Perspective

    This is one of the most counter-intuitive facts in React and a favorite "gotcha" interview question precisely because it contradicts how native DOM bubbling would behave for the same markup. State it explicitly: "React events bubble through the fiber tree, native events bubble through the DOM tree — portals are the case where these two diverge visibly." A great follow-up: "does e.stopPropagation() inside a portal stop native listeners attached directly to document with addEventListener?" — no, because that stops React's synthetic dispatch, not the underlying native DOM event, which already bubbled through the real DOM ancestors before React's delegated listener even ran.

    Q53. What are the SSR limitations of portals, and how do you work around them?

    ROI: ★★★☆☆ Frequency: Medium

    Short Answer

    createPortal requires a real DOM node to render into, and during server-side rendering there is no DOM at all — document doesn't exist on the server. Calling it during SSR either throws or must be guarded so it never executes server-side; the common pattern is to only render the portal after the component has mounted on the client (checking a "hasMounted" flag set in useEffect), accepting that the portaled content simply isn't part of the initial server-rendered HTML.

    Detailed Answer

    Since useEffect never runs on the server (it's a client/browser-only hook), gating the portal render behind a piece of state that only flips to true inside an effect guarantees the portal call happens exclusively client-side, after hydration. This means the portaled content (e.g. a modal) is simply absent from the server HTML and appears an instant after hydration — usually fine for something like a modal that starts closed anyway, but worth being deliberate about for anything that should be visible/indexable on first paint (SEO-relevant content should generally not live inside a portal-gated-by-mount pattern).

    Code Example

    function ClientOnlyPortal({ children, selector }) {
  const [mounted, setMounted] = React.useState(false);
  React.useEffect(() => setMounted(true), []); // only true after client mount

  if (!mounted) return null; // renders nothing during SSR and first client render
  const target = document.querySelector(selector);
  return target ? createPortal(children, target) : null;
}

// Usage — safe in a Next.js / SSR app
function Modal({ children }) {
  return (
    <ClientOnlyPortal selector="#modal-root">
      <div className="overlay">{children}</div>
    </ClientOnlyPortal>
  );
}

    Senior Engineer Perspective

    A precise answer names the actual mechanism — no DOM on the server, so gate portal creation behind a client-mount effect — rather than a vague "portals don't work with SSR." A good follow-up: "does this cause a hydration mismatch?" — no, because the portal renders null on both the server output and the very first client render (before the effect fires), so the initial client render matches the server output exactly; the portal only appears on the render after that, which is a normal client-side update, not a hydration mismatch.

    Q54. Fragment vs returning an array of elements — what's the difference today?

    ROI: ★★★☆☆ Frequency: Medium

    Short Answer

    Both let a component produce multiple sibling elements without a wrapper DOM node. A <>...</> Fragment is the idiomatic, readable JSX way and needs no explicit keys unless it holds a list. Returning a raw array (return [<A key="a"/>, <B key="b"/>]) is the older, pre-Fragment-syntax mechanism that requires every element to carry an explicit key — Fragments were introduced specifically to make this common case ergonomic and remove the mandatory key requirement for the simple case.

    Detailed Answer

    Before Fragments existed (React 16 introduced them), the only way to return multiple root elements was an array, and every array child needed a key — even for a fixed, small, non-list set of siblings, which felt like unnecessary ceremony. Fragments removed that requirement for the common "just group these elements" case. Arrays are still exactly what .map() naturally produces, so they remain the correct return type for actual dynamic lists (where keys are genuinely necessary for identity, not just to satisfy a syntax requirement) — the two aren't really competing today so much as suited to different scenarios: Fragment for static grouping, array for dynamic lists (which is what a keyed Fragment inside a .map() effectively becomes anyway, per Q4).

    Code Example

    // Fragment — clean syntax for a fixed, non-list group of elements
function Row() {
  return (
    <>
      <td>Name</td>
      <td>Email</td>
    </>
  );
}

// Array — the natural output of .map(), still needs keys (this hasn't changed)
function List({ items }) {
  return items.map((item) => <li key={item.id}>{item.name}</li>);
  // equivalent in spirit to wrapping each in a keyed Fragment
}

    Senior Engineer Perspective

    The historical context is the interesting part: Fragments exist specifically because the array-with-keys requirement felt heavy-handed for the extremely common "group a fixed handful of elements" case. Knowing that a keyed Fragment and an array of keyed elements are functionally near-identical to the reconciler (both are just a list of children needing identity) shows you understand Fragments as sugar over the same underlying mechanism, not an unrelated feature.

    Q55. How do you manage focus and accessibility for a portaled modal?

    ROI: ★★★★☆ Frequency: High

    Short Answer

    A portal only solves DOM placement — it does nothing for accessibility on its own. You must still: move keyboard focus into the modal when it opens (usually to the first focusable element or the modal container itself), trap focus inside the modal while it's open (Tab/Shift+Tab cycle within it, not escape to the page behind), restore focus to the triggering element on close, mark the modal with the correct ARIA role/attributes (role="dialog", aria-modal="true", aria-labelledby), and hide the rest of the page from assistive tech (aria-hidden or the inert attribute on background content) while it's open.

    Detailed Answer

    None of this is automatic just because the markup is visually correct — a portal changes where the DOM node lives, not how a screen reader or keyboard user perceives page structure. In practice, most teams don't hand-roll focus trapping; they lean on a battle-tested primitive (Radix's Dialog, React Aria's useDialog/FocusScope, or focus-trap-react) because correctly handling every edge case (nested modals, dynamically added focusable content, Escape-to-close, clicking the overlay to dismiss) is surprisingly easy to get subtly wrong by hand.

    Code Example

    function Modal({ isOpen, onClose, children, titleId }) {
  const ref = React.useRef(null);
  const previouslyFocused = React.useRef(null);

  React.useEffect(() => {
    if (!isOpen) return;
    previouslyFocused.current = document.activeElement; // remember to restore later
    ref.current?.focus();                                // move focus into the modal

    function handleKeyDown(e) {
      if (e.key === "Escape") onClose();
      // (a full focus trap would also intercept Tab/Shift+Tab here)
    }
    document.addEventListener("keydown", handleKeyDown);
    return () => {
      document.removeEventListener("keydown", handleKeyDown);
      previouslyFocused.current?.focus();                 // restore focus on close
    };
  }, [isOpen, onClose]);

  if (!isOpen) return null;
  return createPortal(
    <div className="overlay">
      <div
        ref={ref}
        role="dialog"
        aria-modal="true"
        aria-labelledby={titleId}
        tabIndex={-1}
      >
        {children}
      </div>
    </div>,
    document.body
  );
}

    Senior Engineer Perspective

    The point interviewers are probing: does the candidate know that a portal is purely a rendering-location mechanism, with zero built-in accessibility behavior — many engineers assume "modal" implies accessible-by-default. Naming the specific ARIA attributes, the focus-trap requirement, and focus restoration on close (not just "trap focus," but the equally important "give it back afterward") demonstrates real accessibility experience, not textbook knowledge. Mentioning that most teams reach for Radix/React Aria rather than hand-rolling this is also the pragmatic, senior answer.

    Q56. Can you nest multiple portals, and does React handle z-index/stacking for you?

    ROI: ★★★☆☆ Frequency: Medium

    Short Answer

    Yes, portals can nest (a portal rendered inside another portal's subtree) and React handles the event-bubbling/context correctly regardless of nesting depth. But React does not manage visual stacking for you — z-index, layering order, and which overlay sits on top of another is entirely a CSS concern you must design deliberately (e.g. a single shared "layer" root with a defined stacking convention, or a dedicated overlay-manager library).

    Detailed Answer

    A common real scenario: a dropdown menu (portaled) opened from within a modal (also portaled) — both DOM nodes end up as siblings at the document root (or wherever their respective targets are), and their relative stacking is purely determined by DOM order and z-index, not by which one is "logically nested" in the React tree. If the dropdown's portal target was appended to the DOM before the modal's, it may render underneath the modal overlay despite being logically "on top" in the user's interaction flow — a purely CSS/DOM-order bug, unrelated to React's own bookkeeping, which stays entirely correct.

    Production apps typically solve this with a single shared overlay-root convention (one container per "layer" — tooltip layer, modal layer, toast layer — each with an explicit, intentionally ordered z-index), or delegate the whole problem to a library that manages an overlay stack (tracking which overlay opened most recently and always rendering it last/topmost).

    Code Example

    // Two independent portal targets with an intentional, explicit stacking order
<div id="app-root"></div>
<div id="modal-root" style={{ zIndex: 100 }}></div>
<div id="dropdown-root" style={{ zIndex: 200 }}></div>  {/* always above modals */}
<div id="toast-root" style={{ zIndex: 300 }}></div>     {/* always above everything */}

// A dropdown opened from inside a modal still portals correctly and nests fine —
// React's event bubbling and context both still work across the nested portals.
function Modal() {
  return createPortal(
    <div className="overlay">
      <Dropdown /> {/* this renders its own nested portal into #dropdown-root */}
    </div>,
    document.getElementById("modal-root")
  );
}

    Senior Engineer Perspective

    The key distinction to draw sharply: "React's bookkeeping (events, context, effects) is entirely correct across nested portals — stacking order is a pure CSS/DOM-order problem React has no opinion on." Interviewers appreciate hearing that this is why serious component libraries (Radix, MUI) ship an explicit layering system or portal-target convention rather than leaving z-index management to ad hoc per-component guesses.

    Q57. How do you clean up a portal's target DOM node correctly?

    ROI: ★★★☆☆ Frequency: Medium

    Short Answer

    If a component creates its own portal target node dynamically (rather than portaling into a static element already in index.html), it must remove that node in a useEffect cleanup function when it unmounts — otherwise every mount/unmount cycle leaks a detached DOM element into the document, growing memory usage and potentially leaving stray empty containers behind.

    Detailed Answer

    Two portal-target strategies exist: (1) a static container already present in the HTML shell (e.g. <div id="modal-root"> in index.html) that every modal in the app shares and nothing ever removes — no cleanup needed; (2) a dynamically created element (document.createElement("div")) appended to document.body specifically for one component instance — this must be created in an effect and explicitly removed in that same effect's cleanup, mirroring exactly the subscribe/unsubscribe pattern from Q16, just applied to a DOM node instead of an event listener.

    Code Example

    function DynamicPortal({ children }) {
  const elRef = React.useRef(null);
  if (!elRef.current) {
    elRef.current = document.createElement("div"); // created once, lazily
  }

  React.useEffect(() => {
    const el = elRef.current;
    document.body.appendChild(el);
    return () => {
      document.body.removeChild(el); // cleanup — prevents leaking detached nodes
    };
  }, []);

  return createPortal(children, elRef.current);
}

    Senior Engineer Perspective

    This is a good chance to connect back to the general "effects are about synchronizing an external system" mental model from Q16 — a dynamically created DOM node is just as much an external resource needing cleanup as a WebSocket or a timer, and StrictMode's double-invoke in development (mount → unmount → remount) is precisely what would expose a missing cleanup here, manifesting as two stray container divs appearing in the DOM inspector instead of one.

    Q58. What is the shorthand Fragment's biggest limitation and how did that shape the API?

    ROI: ★★★☆☆ Frequency: Medium

    Short Answer

    The <>...</> shorthand cannot accept any attributes at all — not even key — because it isn't sugar for a component reference the compiler can attach props to; it compiles to a distinct, attribute-less Fragment call. Whenever a Fragment needs a key (rendering grouped siblings inside a .map()), you must fall back to the explicit <React.Fragment key={...}> form, which is the one and only prop it supports.

    Detailed Answer

    This design was intentional: the shorthand exists purely for the extremely common "wrap a few static elements with zero DOM footprint" case, and adding attribute support would have added parsing complexity for a form meant to stay minimal. React.Fragment the explicit component supports exactly one prop — key — deliberately, not a general props API, because a Fragment renders nothing itself; there's no DOM node to apply a className or event handler to, so any prop besides key (which is a reconciliation concern, not a rendering concern) simply wouldn't have anywhere to go.

    Code Example

    // Shorthand — cannot take a key, only fine outside of a list context
function Pair() {
  return (
    <>
      <dt>Term</dt>
      <dd>Definition</dd>
    </>
  );
}

// Explicit form — required the moment a key is needed (inside .map())
function DefinitionList({ items }) {
  return (
    <dl>
      {items.map((item) => (

          <dt>{item.term}</dt>
          <dd>{item.desc}</dd>
        </React.Fragment>
      ))}
    </dl>
  );
}

    Senior Engineer Perspective

    A crisp way to phrase the underlying design principle: "the shorthand is sugar for the zero-config case; the moment you need any prop, even just key, you've stepped outside what sugar was meant to cover, so you spell out the full component." This is a small detail, but volunteering it unprompted (rather than only recalling it when asked "does the shorthand support key?") signals genuine hands-on familiarity with list rendering.

    SECTION 11 - ERROR BOUNDARIES

    Q59. What is an error boundary, and exactly which errors does it catch?

    ROI: ★★★★★ Frequency: Extremely High

    Short Answer

    An error boundary is a class component that catches JavaScript errors thrown during rendering, in lifecycle methods, and in constructors anywhere in its child tree, and renders a fallback UI instead of letting the error unmount the whole app. It works exactly like a try/catch for a subtree of the component tree — but only for errors that occur in that specific set of React-managed code paths.

    Detailed Answer

    Without an error boundary, an uncaught error thrown anywhere during render unmounts the entire component tree React was managing — a single broken child can blank the whole page. An error boundary contains the damage: it catches the error, prevents the unmount from propagating further up, and swaps its own subtree for a fallback, leaving the rest of the app (siblings of the boundary, everything above it) fully intact and interactive.

    It catches errors specifically in: rendering, lifecycle methods (componentDidMount, componentDidUpdate, etc.), and constructors of the components below it in the tree. It explicitly does not catch errors in event handlers, asynchronous code (promises, setTimeout), server-side rendering, or errors thrown in the boundary component itself (a boundary can't catch its own errors — you need a boundary above it for that).

    Code Example

    class ErrorBoundary extends React.Component {
  state = { hasError: false };
  static getDerivedStateFromError(error) {
    return { hasError: true }; // triggers the fallback render
  }
  componentDidCatch(error, info) {
    console.error("Caught by boundary:", error, info.componentStack);
    logToMonitoring(error, info);
  }
  render() {
    if (this.state.hasError) return this.props.fallback;
    return this.props.children;
  }
}

// Contains damage to just this subtree — the rest of the app keeps working
<App>
  <Header />
  <ErrorBoundary fallback={<p>Widget failed to load.</p>}>
    <FlakyWidget />
  </ErrorBoundary>
  <Footer />
</App>

    Senior Engineer Perspective

    The precise scope — render/lifecycle/constructor only — is the detail that separates a memorized answer from an understood one. Expect the immediate follow-up "does it catch a bug in an onClick handler?" — no, and knowing exactly why (error boundaries model React's own rendering pipeline, not arbitrary JS execution) sets up the rest of this section's questions cleanly. Emphasize the blast-radius framing: a well-placed boundary turns "one broken widget crashes the page" into "one broken widget shows an error message."

    Q60. Walk through getDerivedStateFromError vs componentDidCatch — why do you need both?

    ROI: ★★★★☆ Frequency: High

    Short Answer

    getDerivedStateFromError(error) is a static method used purely to update state synchronously so the fallback UI renders on the very next render — it must be pure, with no side effects, and runs during the render phase. componentDidCatch(error, info) runs during the commit phase and is where you're allowed to perform side effects — logging the error to a monitoring service, sending analytics, or anything that touches the outside world. You typically implement both: one to update UI, one to report the error.

    Detailed Answer

    This split mirrors the render/commit separation from Q50 exactly. getDerivedStateFromError is called during the (potentially repeated, must-be-pure) render phase, so React forbids side effects there — no logging, no network calls, just returning a state update. componentDidCatch is called once, during commit, specifically so it's safe to perform impure work like calling Sentry.captureException(error) or posting to a logging endpoint, exactly the same reasoning that puts data fetching in useEffect rather than in the render body of a function component.

    In practice almost every production error boundary implements both: getDerivedStateFromError to flip a hasError flag (driving the fallback render), and componentDidCatch purely for reporting — neither one alone gives you both "show a fallback" and "know an error happened" cleanly.

    Code Example

    class ErrorBoundary extends React.Component {
  state = { hasError: false };

  // Render-phase, pure — ONLY updates state, no side effects allowed
  static getDerivedStateFromError(error) {
    return { hasError: true };
  }

  // Commit-phase — side effects belong here
  componentDidCatch(error, errorInfo) {
    reportErrorToMonitoring({
      message: error.message,
      stack: error.stack,
      componentStack: errorInfo.componentStack,
    });
  }

  render() {
    return this.state.hasError ? this.props.fallback : this.props.children;
  }
}

    Senior Engineer Perspective

    A sharp follow-up: "could you just do the logging inside getDerivedStateFromError and skip componentDidCatch entirely?" — technically you could get away with it in many cases, but it violates the render-phase purity contract (this method can, in principle, be invoked more than once for the same error under certain React internals, and is not the sanctioned place for side effects), so the correct, forward-compatible answer is always to split responsibilities exactly as designed: state update in one, side effects in the other.

    Q61. Why are there no hook-based error boundaries, and how do you use one from a function component tree?

    ROI: ★★★★☆ Frequency: High

    Short Answer

    There is no useErrorBoundary hook because error boundaries rely on two class-only lifecycle capabilities (getDerivedStateFromError, componentDidCatch) that catch errors thrown by React itself while unwinding a failing subtree — a mechanism hooks currently have no equivalent for. In practice this is a non-issue: you write the error boundary class once (or install a tiny library), and every other component in the app stays a plain function component that simply renders as a child of that boundary.

    Detailed Answer

    The reason hooks can't replicate this: a hook only runs within the component that calls it, and if that same component's render throws, the hook's own code has already been abandoned along with the rest of that failing render — there's no "catch" mechanism available at the hook level analogous to a class's special lifecycle methods, which React's internals specifically know how to invoke when unwinding a crashed subtree. Because of this, the community consensus (and the React team's own guidance) is: write exactly one small class-based ErrorBoundary component (or use react-error-boundary's <ErrorBoundary>, which wraps this for you with a nicer function-friendly API), and never touch class syntax again anywhere else in the app.

    Code Example

    import { ErrorBoundary } from "react-error-boundary"; // hides the class internally

function Fallback({ error, resetErrorBoundary }) {
  return (
    <div role="alert">
      <p>Something went wrong: {error.message}</p>
      <button onClick={resetErrorBoundary}>Try again</button>
    </div>
  );
}

// Everything below this line can be pure function components + hooks —
// you never need to write the class yourself.
function App() {
  return (
    <ErrorBoundary FallbackComponent={Fallback} onError={logError}>
      <Dashboard />
    </ErrorBoundary>
  );
}

    Senior Engineer Perspective

    The strongest answer treats this as a settled, low-stakes gap rather than a real pain point: "you write or install one class, once, and never think about class components again." Interviewers sometimes push with "will hooks ever get this?" — an honest answer is that as of React 19 there's no such hook, and the React team hasn't signaled a firm timeline; the pragmatic move today is react-error-boundary, which most production codebases already reach for instead of hand-rolling the class.

    Q62. What errors does an error boundary NOT catch, and how do you handle those instead?

    ROI: ★★★★★ Frequency: Extremely High

    Short Answer

    Error boundaries do not catch: errors inside event handlers (a throw in an onClick is a normal synchronous JS error — use a plain try/catch), errors in asynchronous code (a rejected promise, a setTimeout callback — these need their own .catch()/try/catch), server-side rendering errors, and errors thrown in the boundary component's own code. Each of these needs its own explicit handling mechanism; error boundaries only cover the render/lifecycle/constructor path.

    Detailed Answer

    The reasoning: error boundaries work by React catching an exception while it's actively managing the call stack for rendering a subtree — they're implemented as part of React's own reconciliation machinery. An event handler runs completely outside of that machinery (React just called your function in response to a DOM event; if it throws, that's a normal uncaught exception in ordinary JS execution, unrelated to any render in progress). The same applies to anything that happens later, asynchronously — by the time a promise rejects or a timer fires, the render that triggered it has long since finished, so there's no active React "unwind" for a boundary to intercept.

    The practical fix: wrap event-handler logic in your own try/catch and set local error state to render a message, and handle async errors with .catch() / try/catch around await, again setting state to reflect the failure — which then does flow through a normal render and could even be re-thrown deliberately during render to let a boundary catch it, if you want to unify handling.

    Code Example

    function Buyer() {
  const [error, setError] = React.useState(null);

  async function handleBuy() {
    try {
      await purchaseItem(); // async error — boundary can't see this
    } catch (err) {
      setError(err); // capture it into state instead
    }
  }

  if (error) {
    // Optionally re-throw DURING RENDER so an ancestor ErrorBoundary can catch it
    throw error;
  }

  function handleClickThatThrows() {
    try {
      riskyClickLogic(); // event-handler error — boundary can't see this either
    } catch (err) {
      setError(err);
    }
  }

  return <button onClick={handleBuy}>Buy</button>;
}

    Senior Engineer Perspective

    This is one of the highest-value questions in the whole error-handling topic because the gap is a real production trap: teams add an error boundary, assume "we're covered," and then ship an app that still white-screens on an unhandled promise rejection inside a click handler. The senior move — catching an async/event error and re-throwing it during the next render so an existing boundary can still handle it uniformly — is a neat trick worth naming explicitly, since it lets you centralize fallback UI logic in one place instead of duplicating error UI at every call site.

    Q63. How do you design a good error boundary fallback UI and retry mechanism?

    ROI: ★★★★☆ Frequency: High

    Short Answer

    A good fallback tells the user something went wrong without technical jargon, offers a clear recovery action (usually a "Try again" button), and — critically — actually resets the boundary's internal error state when that button is pressed, so retrying re-renders the children fresh instead of staying stuck on the fallback forever. Scope boundaries narrowly enough that "try again" can plausibly fix the specific failure (e.g. retry a data fetch), not just wrap the whole app in one giant catch-all.

    Detailed Answer

    The retry mechanism needs the boundary to expose a way to clear hasError and re-mount its children — typically implemented by keeping a "reset key" in state that, when changed, is used as the key of the children (forcing a fresh mount, discarding whatever state caused the crash) alongside flipping hasError back to false. Without this, a "Try again" button that only sets hasError: false but re-renders the exact same broken subtree with the exact same broken state will often just throw the identical error again immediately.

    Placement matters as much as the UI: a single top-level boundary means any failure blanks the entire app with one generic message; several targeted boundaries around independent features (a dashboard widget, a comments section) let the rest of the page keep working and let "try again" genuinely retry just the failed piece.

    Code Example

    class ErrorBoundary extends React.Component {
  state = { hasError: false, resetKey: 0 };
  static getDerivedStateFromError() { return { hasError: true }; }
  componentDidCatch(error, info) { logError(error, info); }

  handleRetry = () => {
    this.setState((s) => ({ hasError: false, resetKey: s.resetKey + 1 }));
  };

  render() {
    if (this.state.hasError) {
      return (
        <div role="alert">
          <p>This section couldn't load.</p>
          <button onClick={this.handleRetry}>Try again</button>
        </div>
      );
    }
    // key forces a genuine remount of children on retry — clears whatever
    // internal state triggered the crash, not just hiding the same error again
    return <div key={this.state.resetKey}>{this.props.children}</div>;
  }
}

    Senior Engineer Perspective

    The subtlety interviewers look for: merely flipping hasError back to false without also forcing a fresh mount of the children often just replays the same crash instantly, because the underlying broken state or props never changed. Explaining the key-remount trick (tying directly back to Q45) as the fix for a genuinely working retry button is the kind of detail that shows you've actually shipped and debugged an error boundary in production, not just copied one from the docs.

    Q64. How do third-party libraries like react-error-boundary improve on the raw API?

    ROI: ★★★☆☆ Frequency: Medium

    Short Answer

    react-error-boundary wraps the class-based mechanics behind a component API that feels native to a function-components-and-hooks codebase: a FallbackComponent prop (a normal function component, receiving the error and a reset callback as props), a built-in, correct reset mechanism via resetErrorBoundary, an optional resetKeys array that automatically resets the boundary when specific values change (e.g. a route param), and a useErrorBoundary hook to manually trigger the nearest boundary from event handlers or async code — directly solving the Q62 gap.

    Detailed Answer

    The resetKeys feature is the standout: instead of manually wiring a key-remount trick (Q63) by hand, you declare "reset this boundary automatically whenever any of these values change" (e.g. resetKeys={[userId]}), and the library handles clearing the error state and remounting the subtree for you whenever the user navigates to a different record. The library's useErrorBoundary() hook also directly addresses Q62's async/event-handler gap — calling showBoundary(error) from inside a catch block explicitly triggers the nearest ancestor boundary's fallback, without needing the somewhat hacky "re-throw during the next render" pattern.

    Code Example

    import { ErrorBoundary, useErrorBoundary } from "react-error-boundary";

function Fallback({ error, resetErrorBoundary }) {
  return (
    <div role="alert">
      <p>{error.message}</p>
      <button onClick={resetErrorBoundary}>Try again</button>
    </div>
  );
}

function UserProfile({ userId }) {
  return (
    <ErrorBoundary FallbackComponent={Fallback} resetKeys={[userId]}>
      <ProfileDetails userId={userId} />
    </ErrorBoundary>
  );
  // resetKeys automatically clears the error + remounts children when userId changes
}

function BuyButton() {
  const { showBoundary } = useErrorBoundary(); // hook API — solves the async-error gap
  async function handleBuy() {
    try {
      await purchaseItem();
    } catch (err) {
      showBoundary(err); // triggers the nearest ErrorBoundary's fallback directly
    }
  }
  return <button onClick={handleBuy}>Buy</button>;
}

    Senior Engineer Perspective

    Knowing this library exists and specifically what problem each feature solves (not just "it's a nicer wrapper") is the differentiator — cite resetKeys for the retry-on-data-change use case and useErrorBoundary/showBoundary for surfacing async errors through the same fallback UI as render errors, unifying error handling across the whole app instead of scattering ad hoc error states everywhere.

    Q65. Where should you place error boundaries in a large app — one global boundary or many?

    ROI: ★★★★☆ Frequency: High

    Short Answer

    Both, at different granularities: one top-level boundary as a last line of defense (so a truly unanticipated crash never white-screens the whole app), plus several targeted boundaries around independent, self-contained features (a chat widget, a comments section, a single dashboard card) so a failure in one feature doesn't take down unrelated ones, and each feature's fallback can offer a retry scoped to just that feature.

    Detailed Answer

    The guiding principle is "blast radius": place a boundary around any subtree whose failure shouldn't be allowed to affect its siblings. A page made of independent widgets (recent orders, recommendations, account summary) benefits enormously from per-widget boundaries — one flaky third-party recommendations API failing shouldn't blank the user's order history too. Route-level boundaries are another common granularity — wrapping each route/page so navigating elsewhere in the app after a crash still works, rather than the whole SPA being stuck.

    Over-granular boundaries (one per tiny component) add ceremony without much benefit; too few (only one, global) means every failure looks the same to the user and offers no scoped retry. Most production apps land on: one global boundary at the root, one per route, and a few extra around genuinely independent, third-party-data-dependent widgets.

    Code Example

    function App() {
  return (
    <ErrorBoundary FallbackComponent={GlobalFallback}> {/* last line of defense */}
      <Layout>
        <ErrorBoundary FallbackComponent={WidgetFallback}>
          <RecentOrders />
        </ErrorBoundary>
        <ErrorBoundary FallbackComponent={WidgetFallback}>
          <Recommendations />  {/* third-party data — isolate its blast radius */}
        </ErrorBoundary>
        <ErrorBoundary FallbackComponent={WidgetFallback}>
          <AccountSummary />
        </ErrorBoundary>
      </Layout>
    </ErrorBoundary>
  );
}

    Senior Engineer Perspective

    The "blast radius" framing is exactly the kind of language a staff/senior engineer uses to reason about resilience, and interviewers reward it because it generalizes beyond React (it's the same thinking behind circuit breakers and bulkheads in backend systems). A good closing point: boundaries around third-party or less-trusted data sources (ads, embeds, recommendations widgets) are especially high-value, since those are disproportionately likely to throw unexpected shapes of data your components didn't anticipate.

    Q66. How do error boundaries interact with Suspense and concurrent rendering?

    ROI: ★★★★☆ Frequency: High

    Short Answer

    Suspense and error boundaries are complementary, not competing: Suspense handles the "still loading" state (a component that "throws" a pending promise instead of an error, caught by the nearest <Suspense fallback=.../>), while an error boundary handles the "failed" state (a component that throws a real Error). Data-fetching libraries built for Suspense (React Query's useSuspenseQuery, Relay) typically throw the promise while loading and throw an actual error on failure, so you nest both around the same subtree to cover both outcomes.

    Detailed Answer

    Mechanically, Suspense works by a component "throwing" a special thenable (an in-flight promise) during render; React catches that specific throw and shows the nearest Suspense boundary's fallback until the promise resolves, then re-renders the subtree. If that same data-fetching call instead throws a genuine Error (network failure, a 500 response), it is a completely ordinary render-phase error, and only an error boundary — not Suspense — can catch it. This is precisely why the standard pattern nests both: <ErrorBoundary><Suspense fallback=...><DataComponent/></Suspense></ErrorBoundary>, so the loading state is handled by Suspense and any eventual failure is caught by the boundary wrapping it.

    Code Example

    function ProfilePage({ userId }) {
  return (
    <ErrorBoundary FallbackComponent={ErrorFallback}>   {/* catches real errors */}
      <React.Suspense fallback={<Spinner />}>            {/* catches "still loading" */}
        <UserProfile userId={userId} />
      </React.Suspense>
    </ErrorBoundary>
  );
}

// A Suspense-integrated data hook throws a promise while pending,
// and throws (or returns) a real Error on failure — two different signals,
// each caught by the matching boundary type.
function UserProfile({ userId }) {
  const user = useSuspenseQuery(["user", userId], fetchUser); // may suspend or throw
  return <h1>{user.name}</h1>;
}

    Senior Engineer Perspective

    The cleanest way to state the relationship: "Suspense and error boundaries both work by intercepting a throw during render, but they intercept two different kinds of throws — a pending promise versus a real error — which is why they're designed to nest together rather than substitute for one another." A great follow-up: "what happens if you forget the error boundary?" — an actual fetch failure would propagate up as an uncaught render error exactly like any other uncaught throw (Q59), potentially unmounting a much larger part of the tree than intended.

    SECTION 12 - CONTEXT API FUNDAMENTALS

    Q67. Walk through createContext, Provider, and useContext end to end.

    ROI: ★★★★★ Frequency: Extremely High

    Short Answer

    createContext(defaultValue) creates a context object. A <Context.Provider value={...}> wraps a subtree and supplies a value that overrides the default for every descendant. Any descendant calls useContext(Context) to read the nearest ancestor Provider's current value — without that value being threaded through every intermediate component as a prop. It's React's built-in mechanism for cross-cutting, "many components need this" data: theme, current user, locale, feature flags.

    Detailed Answer

    Without a matching Provider above it, useContext returns the defaultValue passed to createContext — useful both as a genuine fallback and, in development, as an early warning sign that a component was rendered outside its expected Provider tree. Multiple Providers of the same context can nest; a consumer always reads the value from its nearest ancestor Provider, not some outer one — which lets you override a value for a specific subtree (e.g. a "compact" theme just for one section of the page).

    Context solves exactly the problem prop drilling creates: passing a value through five layers of components that don't themselves use it, purely to hand it to a deeply nested consumer. Context lets that consumer read the value directly, regardless of how deep it is, without every intermediate component needing to know the value exists.

    Code Example

    const ThemeContext = React.createContext("light"); // default value if no Provider found

function App() {
  const [theme, setTheme] = React.useState("dark");
  return (
    <ThemeContext.Provider value={theme}>
      <Toolbar />   {/* doesn't need to know about theme at all */}
    </ThemeContext.Provider>
  );
}

function Toolbar() {
  return <ThemedButton />; // passes nothing — no prop drilling
}

function ThemedButton() {
  const theme = React.useContext(ThemeContext); // reads nearest Provider's value: "dark"
  return <button className={theme}>Click</button>;
}

    Senior Engineer Perspective

    The follow-up almost every interviewer asks: "is Context a state management library, like Redux?" — no, and the precise distinction matters: Context is a plumbing mechanism for passing a value down without props at every level; it has no built-in concept of actions, reducers, middleware, or time-travel debugging. You typically pair it with useState/useReducer to actually hold and update the value (Q71) — Context alone only solves "how does the value get to where it's needed," not "how is the value managed."

    Q68. Why does every consumer of a context re-render when the value changes, and how granular is that?

    ROI: ★★★★★ Frequency: Extremely High

    Short Answer

    Whenever a Provider's value prop changes (by reference — Object.is comparison, exactly like props/state elsewhere), every component that calls useContext on that context re-renders, no matter how deeply nested and regardless of whether that specific consumer cares about the part of the value that actually changed. Context has no field-level granularity — it's all-or-nothing per context object, which is the single biggest performance gotcha in naive Context usage.

    Detailed Answer

    If a Provider's value is an object { user, theme, locale } and only theme changes, but the object is recreated each render (a fresh literal), every consumer — including ones that only read user and never touch theme — re-renders anyway, because React can only compare the whole value reference, not inspect which of its fields a given consumer actually used. This is fundamentally different from, and worse than, prop-based updates, where a child only re-renders if the specific props it receives change (and even then, only if not memoized).

    The practical mitigation (elaborated in Q69) is splitting one large, frequently-changing context into several smaller, independently-updated ones, so a consumer only subscribes to (and re-renders from) the specific slice it actually needs.

    Code Example

    const AppContext = React.createContext();

function App() {
  const [user, setUser] = React.useState(null);
  const [theme, setTheme] = React.useState("light");

  // BUG: a fresh object every render — even an UNRELATED theme change
  // re-renders every consumer of AppContext, including ones only reading `user`.
  return (
    <AppContext.Provider value={{ user, theme, setTheme }}>
      <Dashboard />
    </AppContext.Provider>
  );
}

function UserBadge() {
  const { user } = React.useContext(AppContext); // re-renders on EVERY theme toggle too
  return <span>{user?.name}</span>;
}

    Senior Engineer Perspective

    This is the single most common Context performance question, and the crisp answer is: "Context re-renders are all-or-nothing per context object — there is no field-level subscription like a store's selector gives you." Volunteering that useMemo-wrapping the Provider's value object only prevents re-renders caused by the Provider's own re-render (an unrelated parent re-rendering), not re-renders caused by an actual field in the value changing, shows you understand the difference between "stabilizing a reference" and "reducing what changed."

    Q69. How do you split contexts to avoid unnecessary re-renders?

    ROI: ★★★★☆ Frequency: High

    Short Answer

    Instead of one context holding everything, create separate contexts for pieces of state that change independently and at different rates — e.g. a rarely-changing UserContext and a frequently-toggled ThemeContext — so a component that only reads UserContext never re-renders just because the theme toggled. A further refinement splits "value" from "setter" into two contexts, since the setter function reference is stable (from useState) and consumers that only need to trigger updates don't need to re-render when the value itself changes.

    Detailed Answer

    The value/setter split matters because a component that only calls setTheme (e.g. a toggle button) doesn't actually need to know the current theme value — if it subscribes to a combined context, it re-renders every time the theme changes even though its own output never depends on that value. Separating ThemeValueContext from ThemeSetterContext means the toggle button subscribes only to the setter (which never changes reference across renders when produced by useState), so it never re-renders due to theme changes at all.

    Code Example

    // Split by concern AND by value vs setter
const ThemeValueContext = React.createContext("light");
const ThemeSetterContext = React.createContext(() => {});

function ThemeProvider({ children }) {
  const [theme, setTheme] = React.useState("light"); // setTheme's reference is stable
  return (
    <ThemeSetterContext.Provider value={setTheme}>
      <ThemeValueContext.Provider value={theme}>
        {children}
      </ThemeValueContext.Provider>
    </ThemeSetterContext.Provider>
  );
}

function ThemeToggleButton() {
  const setTheme = React.useContext(ThemeSetterContext); // never re-renders on theme change
  return <button onClick={() => setTheme((t) => (t === "light" ? "dark" : "light"))}>Toggle</button>;
}

function ThemedText() {
  const theme = React.useContext(ThemeValueContext); // only this one re-renders on toggle
  return <p className={theme}>Hello</p>;
}

    Senior Engineer Perspective

    Splitting value from setter is a genuinely underused trick most mid-level engineers haven't seen, and volunteering it demonstrates real Context-performance experience rather than book knowledge. A good closing note: if a codebase needs finer-grained subscriptions than "split into more contexts" can practically offer (many independently-changing fields), that's usually the signal to move to a proper external store (Zustand, Jotai, Redux with selectors) rather than fighting Context's all-or-nothing re-render model further.

    Q70. What is the default value of a context actually for, and when is it used?

    ROI: ★★★☆☆ Frequency: Medium

    Short Answer

    The value passed to createContext(defaultValue) is used only when a component calls useContext and there is no matching Provider anywhere above it in the tree — it is not a fallback for "Provider exists but its value happens to be undefined." It's most useful for components meant to work both standalone (in tests, in Storybook) and inside a real Provider, and as a way to catch "used outside its Provider" mistakes early.

    Detailed Answer

    A frequent misconception: passing createContext(null) and later checking if (!context) to detect "missing Provider" works fine — but it also fires if a real Provider legitimately supplies null as its value, which is indistinguishable from "no Provider was found" using only the returned value. To reliably guard against a missing Provider, wrap useContext in a small custom hook that throws a clear error when the context equals a sentinel default (often undefined, deliberately never a value a real Provider would supply) — a common, well-regarded pattern (seen in Q32's compound-component example) for surfacing a misuse mistake immediately instead of the consumer silently rendering with wrong/missing data.

    Code Example

    // Sentinel default (undefined) purely to detect a missing Provider
const AuthContext = React.createContext(undefined);

function useAuth() {
  const ctx = React.useContext(AuthContext);
  if (ctx === undefined) {
    throw new Error("useAuth must be used within an ");
  }
  return ctx; // guaranteed to be the real Provider's value from here on
}

function AuthProvider({ children }) {
  const [user, setUser] = React.useState(null); // a legitimate null value — fine, not confused with "missing"
  return <AuthContext.Provider value={{ user, setUser }}>{children}</AuthContext.Provider>;
}

    Senior Engineer Perspective

    The nuance interviewers want: "default value" and "no Provider present" are the same case only when nobody ever legitimately supplies a value equal to the default — which is exactly why picking a sentinel (often undefined, paired with an explicit throw in a custom hook) is safer than trying to infer "missing" from an ordinary falsy value like null or 0 that a real Provider might supply on purpose.

    Q71. How do you combine Context with useReducer to build a lightweight store?

    ROI: ★★★★☆ Frequency: High

    Short Answer

    A reducer centralizes "how state changes" into one pure function keyed by dispatched actions; Context distributes the current state and the dispatch function to any component in the subtree without prop drilling. Together they form a minimal Redux-like store using only built-in React: components read state via useContext and trigger changes by dispatching plain action objects, with all the update logic living in one auditable reducer function.

    Detailed Answer

    This pattern scales better than scattering many independent useState calls across a Provider once state updates start depending on each other (e.g. "clearing the cart also resets the applied discount code") — a reducer's single switch (or lookup-table) keeps every valid transition in one place, which is easier to reason about, test in isolation (pure function, no React needed to unit test it), and debug (log every dispatched action). Following Q69's value/setter split, it's common to also split the state context from the dispatch context, since dispatch from useReducer is referentially stable across renders — components that only dispatch actions (never read state) won't re-render when state changes.

    Code Example

    const CartStateContext = React.createContext();
const CartDispatchContext = React.createContext();

function cartReducer(state, action) {
  switch (action.type) {
    case "add": return { ...state, items: [...state.items, action.item] };
    case "remove": return { ...state, items: state.items.filter((i) => i.id !== action.id) };
    case "clear": return { items: [], discountCode: null }; // related resets, centralized
    default: return state;
  }
}

function CartProvider({ children }) {
  const [state, dispatch] = React.useReducer(cartReducer, { items: [], discountCode: null });
  return (
    <CartDispatchContext.Provider value={dispatch}>  {/* stable reference */}
      <CartStateContext.Provider value={state}>
        {children}
      </CartStateContext.Provider>
    </CartDispatchContext.Provider>
  );
}

function useCartState() { return React.useContext(CartStateContext); }
function useCartDispatch() { return React.useContext(CartDispatchContext); }

function AddToCartButton({ item }) {
  const dispatch = useCartDispatch(); // never re-renders when cart items change
  return <button onClick={() => dispatch({ type: "add", item })}>Add</button>;
}

    Senior Engineer Perspective

    This is the honest answer to "when do you not need Redux/Zustand" — a Context + reducer store covers a genuinely large swath of app-level state needs without an external dependency. The senior caveat to volunteer: this pattern still inherits Context's all-or-nothing re-render behavior (Q68) for anything reading the state context — for very large, high-frequency-update stores, a dedicated library with true selector-based subscriptions (only re-rendering components that read the specific slice that changed) eventually wins on performance, which is exactly the boundary where you'd recommend graduating off this DIY pattern.

    Q72. What is "context selector" and why doesn't React provide one natively?

    ROI: ★★★☆☆ Frequency: Medium

    Short Answer

    A "selector" is a function that reads only a specific slice of a larger state object and re-renders the subscribing component only when that particular slice changes — the field-level granularity Context inherently lacks (Q68). React doesn't ship this natively because implementing true selector-based subscriptions requires subscribing outside of React's normal render cycle (typically via an external store with its own change-listener system), which is exactly the architecture state-management libraries (Zustand, Redux, Jotai) are built around, and isn't a natural fit for Context's simple "re-render every consumer" broadcast model.

    Detailed Answer

    Libraries like Zustand or Redux achieve selector-based subscriptions by keeping the actual state outside React (in a plain JS object/store with its own subscribe/publish mechanism), and using a hook (useSyncExternalStore, the officially sanctioned React 18+ primitive for exactly this) that re-renders a component only when the specific selected slice's value actually changes, comparing old vs new selection results rather than relying on Context's coarse "provider value changed" broadcast. Context, by contrast, is deliberately simple — it's built directly into React's render/props model, which is precisely why it can't offer this granularity without extra machinery layered on top (libraries like use-context-selector exist specifically to add it, working around React's normal Context behavior).

    Code Example

    // Manual "selector" workaround pattern — subscribe via useSyncExternalStore,
// bypassing Context's broadcast-to-everyone behavior entirely
function createStore(initialState) {
  let state = initialState;
  const listeners = new Set();
  return {
    getState: () => state,
    setState: (partial) => { state = { ...state, ...partial }; listeners.forEach((l) => l()); },
    subscribe: (listener) => { listeners.add(listener); return () => listeners.delete(listener); },
  };
}

function useStoreSelector(store, selector) {
  return React.useSyncExternalStore(store.subscribe, () => selector(store.getState()));
}

// A component using this only re-renders when its SPECIFIC selected slice changes —
// exactly the granularity plain Context can't offer.
const cartStore = createStore({ items: [], discountCode: null });
function ItemCount() {
  const count = useStoreSelector(cartStore, (s) => s.items.length);
  return <span>{count}</span>;
}

    Senior Engineer Perspective

    Name-dropping useSyncExternalStore correctly here is a strong signal — it's the actual React 18 primitive built specifically to let external stores (not Context) subscribe to slices of state safely under concurrent rendering, and it's exactly what libraries like Zustand use internally. The precise, senior-level framing: "Context re-renders are a render-tree broadcast; true selectors need an external subscription model, which is architecturally a different mechanism — that's not a missing feature so much as a different problem Context was never designed to solve."

    Q73. When should you NOT reach for Context (i.e. when is prop drilling actually fine)?

    ROI: ★★★★☆ Frequency: High

    Short Answer

    Prop drilling through one or two levels is completely fine — it's explicit, traceable with a simple "find references," and doesn't introduce an implicit dependency that's harder to trace than a prop. Reach for Context only once drilling genuinely spans many unrelated layers, or the same value is needed by many, disparate parts of the tree — not as a reflexive first move the moment you pass a prop down more than one level.

    Detailed Answer

    Context has real costs that make it a worse default than people assume: it couples a consumer to an implicit, non-obvious dependency (you can't tell what a deeply nested component needs just by reading its parent's JSX — you have to go find the Provider), it introduces the all-or-nothing re-render behavior of Q68, and it makes components harder to reuse in isolation (Storybook, tests) since they now silently require a specific Provider ancestor rather than declaring their needs via props. Passing two or three props down two or three levels is more explicit, more testable, and more refactor-friendly (a "find references" on a prop name works; tracing "who reads this context" across a large app is often harder).

    A useful sequencing, echoing Q8's guidance: derive → lift state up → pass as props (even through a couple of levels) → only reach for Context once prop drilling is demonstrably painful (many layers, many unrelated consumers) — not as a rule applied preemptively.

    Code Example

    // Fine — two levels of prop drilling, explicit and easy to trace
function Page({ user }) {
  return <Header user={user} />;
}
function Header({ user }) {
  return <UserMenu user={user} />;
}
function UserMenu({ user }) {
  return <span>{user.name}</span>;
}

// Reasonable candidate for Context — needed by MANY, deeply nested,
// unrelated consumers scattered across the whole app (auth, theme, locale)
const AuthContext = React.createContext();

    Senior Engineer Perspective

    This is a judgment question, and the strongest answer resists the "Context is always better than prop drilling" reflex some junior engineers pick up from tutorials. State plainly: "explicit props through a couple of levels are more debuggable than an implicit context dependency; I only introduce Context once drilling actually causes pain across many layers or many unrelated consumers, and I still evaluate whether composition (rendering the deeply-nested component higher up and passing it via children) solves the problem without Context at all."

    Q74. How does Context interact with React.memo — does memo block context updates?

    ROI: ★★★★☆ Frequency: High

    Short Answer

    No — React.memo only skips a re-render caused by the parent re-rendering with unchanged props; it has no effect on re-renders triggered by a context value that component consumes changing. A memoized component that calls useContext will still re-render whenever that context's value changes, regardless of its memo status, because the context subscription is a completely separate re-render trigger from props.

    Detailed Answer

    This surprises people who expect memo to be a universal "skip re-render" switch. memo's shallow prop comparison simply has nothing to do with context — React tracks context subscriptions independently, and any component (memoized or not) that reads a context via useContext is re-rendered whenever that Provider's value reference changes, bypassing memo's props check entirely, because the actual re-render trigger isn't "new props from the parent" at all.

    The practical implication: wrapping a component in memo to "protect" it from a chatty parent does nothing to shield it from a chatty context — if that memoized component also consumes a frequently-changing context, it'll re-render on every context update regardless. The fix, again, is addressing the context's own re-render granularity (splitting contexts, memoizing the Provider's value, or moving to a selector-based store), not adding more memoization around the consumer.

    Code Example

    const CountContext = React.createContext(0);

// memo protects against re-renders from unchanged PROPS from a parent —
// it does NOT protect against context changes at all.
const Display = React.memo(function Display({ label }) {
  const count = React.useContext(CountContext); // still re-renders on every count change
  console.log("Display rendered");
  return <p>{label}: {count}</p>;
});

function App() {
  const [count, setCount] = React.useState(0);
  return (
    <CountContext.Provider value={count}>
      {/* Display re-renders every time count changes, even though it's memoized —
          the label prop never changes, but the context value does. */}
      <Display label="Count" />
      <button onClick={() => setCount((c) => c + 1)}>+1</button>
    </CountContext.Provider>
  );
}

    Senior Engineer Perspective

    Q75. useRef vs createRef — what's the difference and why does it matter for function components?

    ROI: ★★★★☆ Frequency: High

    Short Answer

    useRef creates a ref object once and returns the exact same object on every subsequent render of that component instance — its .current persists across renders. createRef creates a brand-new ref object every single time it's called, which makes it fundamentally unsuitable for use inside a function component's body (a new, empty ref every render defeats the whole point of persisting a value) — it exists for, and is still used in, class components, where it's typically assigned once in the constructor.

    Detailed Answer

    Calling React.createRef() directly inside a function component's body would recreate a fresh { current: null } object on every render, discarding whatever was previously stored in .current — so any DOM reference or mutable value you tried to persist would be silently reset each render, making it useless for the "survive across renders" use case refs exist for. useRef solves this specifically for function components: React internally stores the ref object in the component's fiber and returns that same object reference every render, which is also why useRef, like all hooks, follows the Rules of Hooks (can't be called conditionally/in a loop) while createRef has no such restriction, since it's just a plain function call, not a hook.

    Code Example

    // WRONG in a function component — createRef makes a NEW object every render
function BadInput() {
  const ref = React.createRef(); // fresh { current: null } every single render!
  return <input ref={ref} />;    // .current set on mount is lost by the next render
}

// RIGHT — useRef persists the same object across renders
function GoodInput() {
  const ref = React.useRef(null); // same object identity every render
  React.useEffect(() => {
    console.log(ref.current); // reliably the <input> DOM node
  });
  return <input ref={ref} />;
}

// createRef's actual home: class components, assigned once in the constructor
class LegacyInput extends React.Component {
  inputRef = React.createRef(); // created once per instance, in the class field/constructor
  render() { return <input ref={this.inputRef} />; }
}

    Senior Engineer Perspective

    The trap here is candidates who describe useRef and createRef as "basically interchangeable" — the precise, correct framing is that they solve the same conceptual problem in two different component paradigms, and using createRef directly inside a function body is an actual bug, not just an outdated style choice. A crisp one-liner that lands well: "useRef is a hook because persisting a value across renders is exactly the kind of per-instance state hooks are built to manage; createRef predates hooks and belongs to a world where the class instance itself was the thing persisting across renders."

    Q76. What is forwardRef, and why couldn't you just pass ref as a normal prop (pre-React 19)?

    ROI: ★★★★☆ Frequency: High

    Short Answer

    Before React 19, ref (like key) was a reserved, special prop that React intercepted itself rather than passing through to your component's props object — attempting to read props.ref inside a function component always yielded undefined. React.forwardRef((props, ref) => ...) was the required wrapper that let a function component explicitly receive the ref as a second argument and forward it to whichever inner DOM node or component it chose.

    Detailed Answer

    The reason ref was special-cased rather than a plain prop: React needed a stable, framework-owned way to know "this is a request for an imperative handle to the underlying instance," reserved so it couldn't collide with an app's own arbitrarily-named props and so React's reconciler could apply consistent, predictable ref-attachment/detachment timing (attaching on commit, detaching before the next commit or on unmount) regardless of what a component chose to call its other props. Without forwardRef, attaching a ref directly to a custom function component (rather than a host DOM element) simply did nothing useful — the ref's .current stayed null, silently, since there was no path for it to reach the inner DOM node.

}
// const ref = useRef(); <FancyInput ref={ref} />  -- ref.current stays null

  return <input className="fancy" ref={ref} {...props} />;

  React.useEffect(() => inputRef.current?.focus(), []);

    Senior Engineer Perspective

    A precise answer distinguishes "reserved by React" from "just not passed for no reason" — ref (and key) needed guaranteed, predictable framework-level semantics that an arbitrary prop name couldn't offer.     Q77. What changed with refs as a prop in React 19?

    ROI: ★★★★☆ Frequency: High

    Short Answer

    React 19 lets function components receive ref as a plain, ordinary prop — no forwardRef wrapper required. You simply add ref to the component's props parameter and use it exactly like any other prop, which removes an entire category of boilerplate (and the two-argument `(props, ref)` signature) that every reusable, ref-forwarding component previously needed.

    Detailed Answer

    forwardRef still works in React 19 (nothing breaks), but it's now considered legacy for new code — the React team's stated direction is to eventually deprecate it once the ecosystem has broadly migrated, since the special-casing it worked around no longer exists for plain function components.     Q78. What is useImperativeHandle, and when is exposing an imperative API justified?

    ROI: ★★★★☆ Frequency: High

    Short Answer

    useImperativeHandle(ref, () => ({ ... })) lets a component customize exactly what a parent's ref exposes, instead of handing over the raw underlying DOM node. It's justified when a component needs to expose a deliberately narrow, purpose-built imperative API (e.g. focus(), scrollToTop(), reset()) while hiding its actual internal DOM structure — protecting encapsulation so the parent can't reach in and mutate arbitrary internals directly.

    Detailed Answer

    Without it, forwarding a ref straight to an inner DOM node exposes the entire DOM API to the parent — every property and method a raw <input> element has, including ones the component author never intended callers to touch (arbitrary style mutation, removing children, etc.). useImperativeHandle lets the component instead expose a small, curated object with only the specific methods it wants to support, keeping the internal markup free to change later without breaking every consumer that grabbed a ref.

    This should be reached for sparingly — most components should stay fully declarative (state + props drive everything). The legitimate cases are narrow: a custom input that needs to expose focus()/reset() without exposing the raw DOM node, a video player wrapper exposing play()/pause(), or a modal exposing open()/close() to an imperative caller that can't easily drive it via props alone.

    Code Example

    const CustomInput = React.forwardRef(function CustomInput(props, ref) {
  const inputRef = React.useRef(null);

  React.useImperativeHandle(ref, () => ({
    focus: () => inputRef.current.focus(),
    clear: () => { inputRef.current.value = ""; },
    // note: NOT exposing inputRef.current itself — only these two curated methods
  }));

  return <input ref={inputRef} {...props} />;
});

function Form() {
  const customInputRef = React.useRef(null);
  return (
    <>
      <CustomInput ref={customInputRef} />
      <button onClick={() => customInputRef.current.focus()}>Focus</button>
      <button onClick={() => customInputRef.current.clear()}>Clear</button>
      {/* customInputRef.current.style, .remove(), etc. are NOT exposed — encapsulated */}
    </>
  );
}

    Senior Engineer Perspective

    The encapsulation framing is the key insight: "a raw forwarded ref leaks your entire internal DOM API to every caller forever; useImperativeHandle lets you define a stable, minimal public contract instead." A strong follow-up: "isn't this just re-inventing an imperative API in a declarative framework?" — yes, deliberately, for the narrow set of interactions (focus, media playback, scroll) that are genuinely imperative by nature even in the DOM itself, where forcing a fully declarative prop-driven API would be more awkward than the native primitive it wraps.

    Q79. What is a callback ref, and how does it differ from an object ref?

    ROI: ★★★★☆ Frequency: High

    Short Answer

    Instead of passing a ref object (from useRef) to the ref attribute, you can pass a function — React calls it with the DOM node when the element mounts, and calls it again with null when it unmounts (in React 19+, the function can also return its own cleanup function instead of relying on the null call). Callback refs are useful when you need to run code exactly at attach/detach time — like measuring an element the instant it appears — rather than just holding a reference to read later.

    Detailed Answer

    An object ref (useRef) is passive: React sets .current, but nothing runs automatically when that happens — you have to separately check it inside an effect. A callback ref is active: the function you provide runs immediately as an attach/detach event, which is exactly what's needed for measuring layout the instant a node appears (no need for a follow-up effect that has to re-check whether the ref is populated yet) or managing a list of dynamically-mounted node references (e.g. building a Map of item-id → DOM node as list items mount and unmount).

    A common pitfall: defining the callback ref inline as a new arrow function every render (ref={(node) => ...}) causes React to call it with null then the new node on every single re-render (since it's technically a "different" ref function each time) — for expensive attach logic, memoizing the callback (useCallback) avoids that unnecessary detach/reattach churn.

    Code Example

    function MeasuredBox() {
  const [height, setHeight] = React.useState(0);

  // Runs immediately on mount/unmount — no separate effect needed to "check" the ref
  const measureRef = React.useCallback((node) => {
    if (node !== null) {
      setHeight(node.getBoundingClientRect().height);
    }
  }, []); // memoized so React doesn't detach/reattach on every render

  return <div ref={measureRef}>Content of unknown height</div>;
}

// Building a live Map of DOM nodes for a dynamic list
function List({ items }) {
  const nodeMap = React.useRef(new Map());
  return items.map((item) => (
    <li
      key={item.id}
      ref={(node) => {
        if (node) nodeMap.current.set(item.id, node);
        else nodeMap.current.delete(item.id); // called with null on unmount
      }}
    >
      {item.name}
    </li>
  ));
}

    Senior Engineer Perspective

    The differentiator is knowing callback refs fire synchronously at attach/detach time rather than needing an effect to "notice" a ref populated — a genuinely useful distinction for measuring layout on mount without an extra render round-trip. The inline-function pitfall (unnecessary detach/reattach churn from a non-memoized callback ref) is a great detail to volunteer unprompted; it demonstrates you've actually profiled ref behavior rather than just read the API shape.

    Q80. Why do refs not trigger re-renders, and what problem does that cause if you use one incorrectly?

    ROI: ★★★★★ Frequency: Extremely High

    Short Answer

    A ref's .current is designed as a mutable "escape hatch" value that lives outside React's rendering model entirely — mutating it is deliberately invisible to React, which is precisely why it doesn't schedule a re-render. If you store something in a ref that the UI actually needs to reflect (anything the user should see update on screen), the component simply won't re-render when it changes — the classic bug of "I updated a ref but the screen didn't update."

    Detailed Answer

    State (useState) and refs (useRef) both persist a value across renders, but they exist for opposite purposes: state changes are supposed to be visible in the rendered UI, so setting state schedules a re-render; refs are for values a component needs to remember but that have no bearing on what should currently be rendered (a timer id, a previous value for comparison, a DOM node reference, a flag to prevent a duplicate async call) — so mutating .current is intentionally silent. The rule of thumb: if changing a value should ever cause the screen to update, it must be state; if a value is purely bookkeeping that render doesn't need to reflect, a ref is correct and appropriately invisible to the render cycle.

    Code Example

    // BUG: storing something the UI needs to reflect in a ref — screen never updates
function BrokenCounter() {
  const countRef = React.useRef(0);
  return (
    <button onClick={() => { countRef.current++; }}>
      {countRef.current} {/* stays frozen at 0 in the rendered output forever */}
    </button>
  );
}

// CORRECT: use state for anything the UI must reflect
function WorkingCounter() {
  const [count, setCount] = React.useState(0);
  return <button onClick={() => setCount((c) => c + 1)}>{count}</button>;
}

// CORRECT ref usage: bookkeeping the render doesn't need to reflect
function SearchWithAbort() {
  const latestRequestId = React.useRef(0); // pure bookkeeping — no UI depends on this value directly
  async function search(query) {
    const id = ++latestRequestId.current;
    const results = await fetchResults(query);
    if (id === latestRequestId.current) setResults(results); // ignore stale responses
  }
}

    Senior Engineer Perspective

    The one-sentence framing that nails this: "state is for values the render output depends on; refs are for values a component needs to remember that render doesn't depend on — mixing the two up in either direction is the bug." A great follow-up: "why not just always use state to be safe?" — because state updates schedule re-renders, so using state for high-frequency bookkeeping (mouse position tracked every animation frame, a request-id counter) would cause needless re-renders for a value the UI was never actually going to display, wasting render cycles the ref-based approach avoids entirely.

    Q81. How do you measure a DOM node's size/position reliably (ResizeObserver, useLayoutEffect)?

    ROI: ★★★★☆ Frequency: High

    Short Answer

    For a one-time measurement right after mount/update (before the browser paints, avoiding a visible flicker), use useLayoutEffect with a ref to call getBoundingClientRect(). For tracking size changes over time (a resizable panel, a responsive container), use the native ResizeObserver API attached via a callback ref or inside an effect, since useLayoutEffect/useEffect alone only run on React-driven re-renders, not on arbitrary browser-triggered layout changes like a user dragging a resize handle or the window resizing.

    Detailed Answer

    The reason useLayoutEffect (not useEffect) matters for one-shot measurement: it runs synchronously after DOM mutations but before the browser paints, so if you measure and then immediately set state to adjust layout based on that measurement, the user never sees the "wrong" intermediate layout flash — useEffect runs after paint, so a measure-then-adjust pattern there can produce a visible jump. For continuous tracking, ResizeObserver is the correct primitive because it fires on any layout change to the observed element regardless of whether React caused it (CSS transitions, user-driven resizing, font loading shifting layout) — something React's own render cycle has no visibility into on its own.

    Code Example

    // One-shot, flicker-free measurement before paint
function Tooltip({ children }) {
  const ref = React.useRef(null);
  const [width, setWidth] = React.useState(0);

  React.useLayoutEffect(() => {
    setWidth(ref.current.getBoundingClientRect().width); // measured before paint
  }, []);

  return <div ref={ref} style={{ marginLeft: -width / 2 }}>{children}</div>;
}

// Continuous tracking of size changes the render cycle can't see on its own
function ResponsiveChart() {
  const containerRef = React.useRef(null);
  const [size, setSize] = React.useState({ width: 0, height: 0 });

  React.useEffect(() => {
    const el = containerRef.current;
    const observer = new ResizeObserver(([entry]) => {
      const { width, height } = entry.contentRect;
      setSize({ width, height });
    });
    observer.observe(el);
    return () => observer.disconnect(); // cleanup — avoids leaking the observer
  }, []);

  return <div ref={containerRef}><Chart {...size} /></div>;
}

    Senior Engineer Perspective

    The precise distinction to draw: useLayoutEffect solves "measure and adjust before the user sees a flicker" for changes React itself caused; ResizeObserver solves "detect layout changes React has no way of knowing about" for changes the browser/user caused independently of any React render. Conflating the two, or reaching for useLayoutEffect polling in a loop instead of ResizeObserver for continuous tracking, is a common performance mistake worth calling out unprompted.

    Q82. Name concrete situations where reaching for a ref is an anti-pattern.

    ROI: ★★★★☆ Frequency: High

    Short Answer

    Common misuses: storing a value in a ref that the rendered UI actually needs to reflect (Q80's bug); using a ref to "read the latest props/state" inside a stale closure instead of fixing the dependency array; imperatively mutating a child's DOM (styles, text content, class list) via a ref instead of expressing that same result declaratively through props/state; and using a ref purely to avoid understanding why an effect re-runs, papering over a dependency-array problem instead of solving it properly.

    Detailed Answer

    A frequent anti-pattern: reaching for ref.current.style.display = "none" to hide an element, when a declarative {isVisible && <Element/>} or a style={{ display: isVisible ? "block" : "none" }} prop would let React own that piece of UI state consistently — imperative DOM mutation via refs bypasses React's model of "the DOM reflects state," meaning React's next re-render might not know to reconcile the DOM back to what it expects, causing drift between what React "thinks" the DOM looks like and what it actually looks like.

    Another common misuse: keeping the "latest" version of a prop/state in a ref (latestCallback.current = callback) purely to dodge fixing a useEffect dependency array that's producing stale-closure bugs — this "ref as an escape hatch from the Rules of Hooks" pattern works, but it's usually treating a symptom; the more correct fix is almost always including the real dependency (possibly wrapping the callback in useCallback, or restructuring the effect) rather than routing around the linter's warning.

    Code Example

    // ANTI-PATTERN: imperative DOM mutation via ref instead of declarative state
function BadToggle() {
  const boxRef = React.useRef(null);
  function hide() { boxRef.current.style.display = "none"; } // bypasses React's model
  return (
    <>
      <div ref={boxRef}>Content</div>
      <button onClick={hide}>Hide</button>
    </>
  );
}

// CORRECT: let state drive the DOM declaratively
function GoodToggle() {
  const [visible, setVisible] = React.useState(true);
  return (
    <>
      {visible && <div>Content</div>}
      <button onClick={() => setVisible(false)}>Hide</button>
    </>
  );
}

// ANTI-PATTERN: ref used to dodge a real stale-closure dependency-array fix
function BadTimer({ onTick }) {
  const onTickRef = React.useRef(onTick);
  onTickRef.current = onTick; // "papers over" fixing the dependency properly
  React.useEffect(() => {
    const id = setInterval(() => onTickRef.current(), 1000);
    return () => clearInterval(id);
  }, []); // empty deps "works" only because of the ref workaround
}

    Senior Engineer Perspective

    The senior framing to lead with: "refs are an escape hatch for things outside React's data flow — the moment you use one to mutate something React itself renders, or to silence a dependency-array warning instead of understanding it, you've reintroduced exactly the imperative, hard-to-reason-about code React's declarative model was meant to eliminate." Naming the "ref-as-latest-value" pattern specifically, and being honest that it's sometimes a legitimate, deliberate trade-off (e.g. inside certain custom hooks) rather than always wrong, shows nuanced judgment rather than dogma.

    Q83. Besides double-invoking effects, what else does StrictMode check for?

    ROI: ★★★★☆ Frequency: High

    Short Answer

    Beyond double-invoking render functions and effects, StrictMode also: double-invokes state initializer functions and reducer functions (to catch impure logic hiding there too), warns about usage of deprecated/legacy lifecycle methods and legacy APIs (like the old string ref API and legacy context), and — in newer React versions — simulates offscreen/prerendering behavior to catch components that don't tolerate being hidden and shown again with state preserved.

    Detailed Answer

    The state-initializer double-invocation catches a subtle purity bug: if you pass a function to useState(() => expensiveInit()) or a reducer to useReducer, StrictMode calls that initializer/reducer twice on the relevant render to make sure it has no hidden side effects (e.g. incrementing a module-level counter, mutating a global) — exactly the same purity contract that render functions themselves must uphold. It also flags legacy patterns during the transition eras between React versions — e.g. warning if a component still uses the old string-based ref="myRef" API instead of useRef/callback refs, or legacy context (contextTypes) instead of createContext.

    Code Example

    function ExpensiveList({ rawData }) {
  // StrictMode calls this initializer TWICE in dev to verify it's pure —
  // if computeInitialItems has a hidden side effect, it'll fire twice.
  const [items] = React.useState(() => computeInitialItems(rawData));
  return <ul>{items.map((i) => <li key={i.id}>{i.name}</li>)}</ul>;
}

function computeInitialItems(rawData) {
  // BAD: a side effect hidden inside a "pure" initializer
  // analyticsCounter++; // <- StrictMode double-invocation would expose this as a bug
  return rawData.map((d) => ({ id: d.id, name: d.name.toUpperCase() }));
}

    Senior Engineer Perspective

    Most candidates only know "effects run twice" — naming the state-initializer/reducer double-invocation as well shows you've read past the headline behavior. The unifying theme worth stating explicitly: "StrictMode's job is finding anywhere your code assumes it will run exactly once when React's contract never actually promised that" — render functions, initializers, and reducers are all supposed to be pure and idempotent, and StrictMode is the tool that verifies it in development.

    Q84. Why does StrictMode intentionally call reducers and initializer functions twice?

    ROI: ★★★★☆ Frequency: High

    Short Answer

    Reducers and lazy state initializers are supposed to be pure functions — same input, same output, no side effects — exactly like render itself. Calling them twice and discarding one of the results is a deliberate stress test: if a reducer or initializer secretly depends on or mutates something outside its own arguments, running it twice will expose inconsistent behavior (a different result the second time, or an observable side effect firing twice) that would otherwise stay hidden until it broke something under React's concurrent rendering, which may legitimately re-invoke these functions multiple times for a single committed update.

    Detailed Answer

    Concurrent React's ability to prepare multiple versions of upcoming UI (and throw away the ones it doesn't use) fundamentally relies on renders, reducers, and initializers being safe to call more than once, or to abandon partway through, without corrupting anything. If a reducer's case "increment" did something like fetch("/log-increment") as a side effect, React calling that reducer twice during a StrictMode dev check (or, in the future, legitimately twice under some real concurrent scenario) would fire that network call twice — a bug StrictMode is specifically designed to surface early, in development, rather than let it ship and manifest as a rare, hard-to-reproduce double-request in production.

    Code Example

    // BAD: reducer with a side effect — StrictMode's double-invocation exposes this
function cartReducer(state, action) {
  if (action.type === "checkout") {
    trackAnalyticsEvent("checkout"); // side effect inside a reducer — impure!
    return { ...state, checkedOut: true };
  }
  return state;
}

// GOOD: reducer stays pure; the side effect moves to where side effects belong
function cartReducer(state, action) {
  if (action.type === "checkout") {
    return { ...state, checkedOut: true }; // purely computes next state
  }
  return state;
}
// The actual analytics call belongs in a useEffect keyed off checkedOut becoming true

    Senior Engineer Perspective

    The precise framing: "StrictMode isn't inventing a new rule — reducers and initializers were always supposed to be pure; it's just the first time misusing that contract gets caught immediately instead of manifesting as an obscure concurrent-rendering bug months later." A good follow-up: "have you ever hit this in practice?" — a strong, specific answer names a reducer that accidentally called an API or mutated a ref as a side effect, and how StrictMode's double-firing behavior in development surfaced it immediately as a duplicate network call.

    Q85. What is a concrete StrictMode-triggered bug you'd expect in an interview scenario?

    ROI: ★★★★★ Frequency: Extremely High

    Short Answer

    The textbook example: a useEffect that opens a WebSocket/subscribes to something on mount but has no (or an incomplete) cleanup function. In production this "leaks" silently across real remounts; under StrictMode's dev-only mount→unmount→remount cycle, it becomes immediately visible as two active connections, duplicate log lines, or a "connection already open" error the very first time the component renders.

    Detailed Answer

    Walk the sequence explicitly: StrictMode mounts the component (effect runs, subscription A opens), immediately unmounts it (cleanup should run and close subscription A), then remounts it (effect runs again, subscription B opens). If the cleanup function is missing or wrong, subscription A never actually closes, so now both A and B are live — visible as duplicated data, doubled log output, or a server-side "second connection from the same client" error. The fix is always adding (or fixing) the effect's cleanup function, never suppressing StrictMode, since the identical bug would eventually surface for real users whenever the component legitimately unmounts and remounts (navigating away and back, a parent's key changing, etc.).

    Code Example

    // BUG: no cleanup — StrictMode's mount/unmount/remount exposes a doubled connection
function ChatRoom({ roomId }) {
  React.useEffect(() => {
    const socket = new WebSocket(`wss://chat/${roomId}`);
    socket.onmessage = handleMessage;
    // missing: return () => socket.close();
  }, [roomId]);
}

// FIXED: proper cleanup makes the StrictMode double-invoke harmless
function ChatRoom({ roomId }) {
  React.useEffect(() => {
    const socket = new WebSocket(`wss://chat/${roomId}`);
    socket.onmessage = handleMessage;
    return () => socket.close(); // StrictMode: open -> close -> open = net one connection
  }, [roomId]);
}

    Senior Engineer Perspective

    This is close to the single most commonly asked StrictMode question, precisely because it's the exact bug most teams hit the first time they upgrade to React 18. The strongest answer walks the mount/unmount/remount sequence explicitly rather than vaguely saying "effects run twice," and states clearly that the fix is always proper cleanup, never disabling StrictMode — disabling it just hides the bug in development while leaving it fully present (and eventually user-visible) in production.

    Q86. How do you debug "my effect runs twice in dev" without just disabling StrictMode?

    ROI: ★★★★☆ Frequency: High

    Short Answer

    Treat the double-run as expected and correct, then ask "is my cleanup function actually undoing everything my effect's setup did?" — add logging to both the setup and cleanup to confirm they pair up cleanly (one setup, one matching cleanup, one setup again), and verify the net effect after the double-invocation is identical to running it once. If the double-run produces a visible duplicate side effect (two API calls, two subscriptions), the cleanup is incomplete or missing, not React malfunctioning.

    Detailed Answer

    A concrete debugging technique: temporarily add console.log("setup") at the top of the effect and console.log("cleanup") at the top of the returned function, then look at the browser console on mount — you should see setup, cleanup, setup in development (StrictMode's dance) and just setup in production. If instead you see two real side effects happening (e.g. two separate network requests actually completing, not just two log lines), that's the signal the cleanup isn't correctly reversing whatever the setup did — often because the setup captured something (a subscription object, a request) that the cleanup never referenced or cancelled.

    Code Example

    function useDebugEffect(name, effect, deps) {
  React.useEffect(() => {
    console.log(`[${name}] setup`);
    const cleanup = effect();
    return () => {
      console.log(`[${name}] cleanup`);
      cleanup?.();
    };
  }, deps);
}

function SearchResults({ query }) {
  useDebugEffect("search", () => {

    Q87. Does StrictMode affect class components differently than function components?

    ROI: ★★★☆☆ Frequency: Medium

    Short Answer

    Yes — StrictMode's double-invocation behavior is specifically about function components and hooks (render function, effects, state initializers, reducers). For class components, StrictMode instead focuses on flagging deprecated/unsafe lifecycle methods (componentWillMount, componentWillReceiveProps, componentWillUpdate) with console warnings, and double-invokes the constructor, render, and shouldComponentUpdate — but it does not double-invoke componentDidMount/componentDidUpdate the way it double-invokes a function component's useEffect.

    Detailed Answer

    The unsafe-lifecycle warnings exist because those specific methods (the UNSAFE_-prefixed ones today) are fundamentally incompatible with concurrent rendering — they can be called multiple times before commit in ways that make them unsafe for side effects, so StrictMode calls them out explicitly to push codebases toward the newer, concurrent-safe lifecycle methods (getDerivedStateFromProps, getSnapshotBeforeUpdate) instead. Since most modern codebases are function-components-first, this class-specific behavior mainly matters for legacy code being gradually migrated, or for the one remaining common class use case — error boundaries (Q59) — which are unaffected by these particular warnings since they don't use the deprecated lifecycle methods.

    Code Example

    class LegacyWidget extends React.Component {
  componentWillMount() {  // StrictMode logs a deprecation warning for this
    this.setupSubscription();
  }
  componentDidMount() {   // NOT double-invoked by StrictMode (unlike useEffect)
    console.log("mounted once");
  }
  render() { return <div />; }
}

// Modern equivalent avoids the warning entirely
class ModernWidget extends React.Component {
  componentDidMount() {
    this.setupSubscription(); // safe, concurrent-compatible lifecycle method
  }
  render() { return <div />; }
}

    Senior Engineer Perspective

    This is a good "have you actually migrated a legacy codebase" signal — most engineers who've only worked in function-components-first codebases assume StrictMode's double-invocation behavior is universal. The precise answer distinguishes what's double-invoked (function component renders/effects/initializers, and class constructor/render/shouldComponentUpdate) from what's merely warned-about (unsafe legacy lifecycle methods) versus what's untouched (componentDidMount/componentDidUpdate run exactly once even under StrictMode).

    Q88. How does StrictMode relate to "offscreen"/prerendering behavior in concurrent React?

    ROI: ★★★☆☆ Frequency: Medium

    Short Answer

    Concurrent React has an internal capability to keep a component "offscreen" — rendered and mounted, but visually hidden and deprioritized — so it can be shown instantly later without a full remount (used for things like tab switching or back/forward cache-style navigation preserving scroll and form state). StrictMode's mount→unmount→remount dev simulation exists specifically to make sure components tolerate being hidden and later re-shown with their state intact, which is exactly the same tolerance offscreen rendering needs, just simulated deterministically in development ahead of that feature becoming more widely used.

    Detailed Answer

    The connection is forward-looking: React's team wants apps to eventually benefit from being able to prerender parts of the UI (e.g. the next likely screen in a tab set) without committing to fully mounting them, and to preserve state when hiding/showing a subtree instead of destroying and rebuilding it. Both capabilities require exactly the same guarantee StrictMode is drilling into developers today — that effects clean up correctly and components don't assume "mount happens exactly once, ever." By forcing this discipline now, via a visible, deterministic dev-time double-invocation, React ensures the ecosystem's components will already be compatible once these offscreen-rendering features become more broadly available.

    Code Example

    // A component correctly written to survive hide/show (offscreen) cycles
// is EXACTLY a component that already correctly survives StrictMode's
// mount -> unmount -> remount simulation. There's no separate rule to learn.
function VideoPlayer({ src }) {
  const videoRef = React.useRef(null);
  React.useEffect(() => {
    const video = videoRef.current;
    video.addEventListener("timeupdate", saveProgress);
    return () => video.removeEventListener("timeupdate", saveProgress); // clean teardown
  }, []);
  return <video ref={videoRef} src={src} />;
}
// This component is already "offscreen-ready" because it's already StrictMode-safe.

    Senior Engineer Perspective

    This is a forward-looking, staff-level answer that most candidates won't volunteer — connecting StrictMode's seemingly annoying dev-mode double-invocation to a genuine, concrete future capability (offscreen prerendering, preserved-state hide/show) reframes it from "an inconvenience to work around" to "free insurance for a feature React is building toward." It's a strong way to close out the StrictMode topic by showing you understand the "why" behind the mechanism, not just the mechanism itself.

    Q89. Should you enable StrictMode for the entire app or selectively? What's the trade-off?

    Short Answer

    Enable it for the whole app by default — it's development-only, catches real bugs early, and costs nothing in production.     Detailed Answer

    Since StrictMode has zero production runtime cost (the double-invocation behavior is stripped in production builds), there's essentially no downside to leaving it on everywhere during development — the "cost" is purely that it surfaces bugs you now have to fix, which is exactly the point.     Q90. What's the difference between early-return conditional rendering and inline conditional rendering, in terms of readability and testability?

    ROI: ★★★★☆ Frequency: High

    Short Answer

    An early return (if (!user) return null; at the top of a component) keeps the main JSX tree flat and focused on the "normal" case, and makes each distinct state (loading, empty, error, ready) trivially readable as a separate guarded branch. Inline conditionals (ternaries, &&) embedded throughout the JSX are better suited for small, localized decisions inside an otherwise-static tree, but sprinkling many of them across a large return statement makes it hard to see, at a glance, which combinations of conditions produce which output.

    Detailed Answer

    Early returns are easier to unit test in isolation too — a test for "renders null when there's no user" only needs to assert the return value for that one guard, without also having to construct props that pass through a nested conditional tree correctly. As a component accumulates more than two or three "entirely different UI for this state" branches, early returns for each whole-component state (loading/error/empty) combined with inline conditionals only for small, local decisions within the main render path (a badge that's shown/hidden based on one flag) tends to stay the most readable structure.

    Code Example

    // Early returns for whole-component states — clean, testable, one branch per case
function UserProfile({ status, user }) {
  if (status === "loading") return <Spinner />;
  if (status === "error") return <ErrorMessage />;
  if (!user) return null;

  // Main path — only small, LOCAL inline conditionals from here on
  return (
    <div>
      <h1>{user.name}</h1>
      {user.isVerified && <VerifiedBadge />}  {/* a local, small decision — fine inline */}
    </div>
  );
}

    Senior Engineer Perspective

    The judgment to communicate: neither style is universally "correct" — early returns for distinct whole-component states, inline conditionals for small local decisions within an otherwise stable tree. A candidate who reflexively nests five ternaries inside one return to avoid "multiple returns" is optimizing for the wrong thing; readability and testability should drive the choice, not a style rule about return statement count.

    Q91. How do you render a list of heterogeneous item types (e.g. a feed with cards, ads, dividers)?

    ROI: ★★★★☆ Frequency: High

    Short Answer

    Map each data item to the right component using a lookup (a type-to-component object/registry, or a switch) rather than a long chain of inline ternaries — each item in the array carries its own type field, and a small dispatcher function/component picks the right renderer, still keyed by the item's own stable id regardless of type.

    Detailed Answer

    A registry/lookup keeps the mapping from data shape to component declarative and easy to extend — adding a new feed-item type means adding one entry to the map, not editing a growing conditional chain scattered through the render. Each item still needs a stable key regardless of which component renders it, and the key should come from the underlying data's own id, not from the item's position in the mixed list (the same list-reordering risks from Q46 apply equally to heterogeneous lists).

    Code Example

    const FEED_COMPONENTS = {
  post: PostCard,
  ad: AdCard,
  divider: DividerRow,
};

function Feed({ items }) {
  return (
    <div>
      {items.map((item) => {
        const Component = FEED_COMPONENTS[item.type];
        if (!Component) return null; // unknown type — fail gracefully, not silently crash
        return <Component key={item.id} {...item} />;
      })}
    </div>
  );
}

    Senior Engineer Perspective

    A registry/lookup-map pattern is the scalable answer interviewers want over a long if/else or ternary chain — it's the same "lookup instead of branching" idea from Q12's status-view map, applied to lists. Mentioning the graceful-fallback branch for an unrecognized type (rather than letting an unhandled type silently render nothing without any indication, or crash) shows defensive, production-minded thinking, especially relevant for feeds fed by a backend that might introduce a new item type before the frontend has shipped support for it.

    Q92. How do you avoid re-creating array/object literals inside JSX that defeat memoization?

    ROI: ★★★★☆ Frequency: High

    Short Answer

    Any object, array, or arrow function literal written directly inside JSX (style={{...}}, data={[1,2,3]}, onClick={() => ...}) is a brand-new reference on every render, which defeats a memoized child's shallow-prop comparison even though the "content" looks unchanged. Hoist these out with useMemo (for objects/arrays) or useCallback (for functions) when the value is passed to a component wrapped in React.memo, or define genuinely static literals outside the component entirely so they're created once, ever.

    Detailed Answer

    This only matters when it actually matters: for a plain, unmemoized child, a new object reference each render is harmless — the child re-renders anyway whenever its parent does (Q10), so a fresh literal costs nothing extra. The problem is specific to a child wrapped in React.memo: its whole purpose is to skip re-rendering when props are shallowly equal, and a freshly-created object/array/function prop is never shallowly equal to the previous render's, so the memoization silently does nothing — the child re-renders every time regardless, and the team gets no benefit from having added memo at all.

    Code Example

    // Truly static — hoist outside the component so it's created exactly once, ever
const DEFAULT_STYLE = { padding: 8, borderRadius: 4 };

function Parent({ count }) {
  // BUG: new array + new function every render — defeats ExpensiveChild's memo
  return (
    <ExpensiveChild
      items={[1, 2, 3]}                 // new array reference every render
      onSelect={(id) => console.log(id)} // new function reference every render
      style={DEFAULT_STYLE}              // FIX: hoisted, stable reference
    />
  );
}

function ParentFixed({ count }) {
  const items = React.useMemo(() => [1, 2, 3], []);        // stable across renders
  const onSelect = React.useCallback((id) => console.log(id), []); // stable across renders
  return <ExpensiveChild items={items} onSelect={onSelect} style={DEFAULT_STYLE} />;
}

const ExpensiveChild = React.memo(function ExpensiveChild({ items, onSelect, style }) {
  console.log("ExpensiveChild rendered");
  return <div style={style}>{items.length} items</div>;
});

    Senior Engineer Perspective

    The precise scoping is the senior detail: this optimization only has payoff for children wrapped in memo — applying useMemo/useCallback everywhere "just in case" adds overhead (the memoization machinery itself has a cost) with no benefit for unmemoized children that would re-render anyway. A great way to close: "I only reach for this after profiling shows a memoized child re-rendering unexpectedly, tracing it back to an inline literal passed as one of its props" — optimization driven by evidence, not superstition.

    Q93. What's the cleanest pattern for a multi-branch loading/error/empty/success UI?

    ROI: ★★★★☆ Frequency: High

    Short Answer

    Model the data-fetching state as a single, explicit discriminated status ("loading" | "error" | "empty" | "success") rather than several independent booleans, and dispatch on that one status with an early-return chain or a status-to-view lookup map. A single status value makes every possible UI state exhaustive and mutually exclusive by construction, instead of relying on booleans that could theoretically combine into impossible or contradictory states.

    Detailed Answer

    The common anti-pattern is tracking isLoading, isError, and data as three separate independent booleans/values — nothing prevents isLoading and isError from both being true simultaneously (a bug, but the type system/state shape doesn't forbid it), forcing the render logic to guess which one "wins." Collapsing these into one status field (or, more robustly, a discriminated union in TypeScript where each status carries only the fields relevant to it) makes invalid states unrepresentable — there's no way to be simultaneously loading and errored, because status can only hold one value at a time.

    Code Example

    // Anti-pattern: independent booleans can contradict each other
// const [isLoading, setIsLoading] = useState(false);
// const [isError, setIsError] = useState(false);
// const [data, setData] = useState(null);
// -- nothing stops isLoading=true AND isError=true at once

// Better: one discriminated status, impossible states are unrepresentable
function useFetchStatus(url) {
  const [state, setState] = React.useState({ status: "loading" });
  React.useEffect(() => {
    setState({ status: "loading" });
    fetch(url).then((r) => r.json())
      .then((data) => setState(
        data.length === 0 ? { status: "empty" } : { status: "success", data }
      ))
      .catch((error) => setState({ status: "error", error }));
  }, [url]);
  return state;
}

function List({ url }) {
  const state = useFetchStatus(url);
  switch (state.status) {
    case "loading": return <Spinner />;
    case "error": return <ErrorMessage error={state.error} />;
    case "empty": return <EmptyState />;
    case "success": return <ul>{state.data.map((i) => <li key={i.id}>{i.name}</li>)}</ul>;
  }
}

    Senior Engineer Perspective

    "Make impossible states unrepresentable" is a well-known phrase (from Elm/functional-programming circles) worth using verbatim — it signals you think about state shape, not just state values. A great follow-up: "how does TypeScript help here?" — a proper discriminated union ({ status: "success"; data: T[] } | { status: "error"; error: Error } | ...) lets the compiler itself enforce that you can only access state.data after narrowing to the "success" branch, catching a whole class of "assumed data was loaded but it wasn't" bugs at compile time.

    Q94. How do you paginate or virtualize a very long list, and why do keys still matter there?

    ROI: ★★★★☆ Frequency: High

    Short Answer

    For very long lists, avoid rendering every item's DOM node at once — either paginate (render only the current page's slice of data) or virtualize (render only the items currently visible in the viewport, using a library like react-window or @tanstack/react-virtual, which recycles a small pool of DOM nodes as the user scrolls). Keys still matter in both cases: React still needs stable identity per rendered item to reconcile correctly across data updates, and virtualization libraries additionally use keys internally to correctly recycle/reposition their pooled DOM nodes as the visible window shifts.

    Detailed Answer

    Rendering thousands of DOM nodes at once is expensive regardless of how well-optimized the React code is — the bottleneck becomes the browser's own layout/paint cost for that many elements, which React's reconciliation efficiency can't fix. Virtualization sidesteps this by only ever mounting a small constant number of DOM nodes (enough to fill the visible viewport plus a small buffer) and reusing them as the user scrolls, swapping the underlying data each pooled node displays rather than mounting/unmounting thousands of real nodes. Because the pool is reused across different logical items as scrolling happens, a stable, correct key (still the item's own id, never the scroll-position index) is what lets React (and the virtualization library's own internal bookkeeping) correctly track which logical item a given pooled node currently represents, especially when the underlying data set changes mid-scroll (an item inserted/removed while the user is scrolled partway through).

    Code Example

    import { useVirtualizer } from "@tanstack/react-virtual";

function VirtualizedList({ items }) {
  const parentRef = React.useRef(null);
  const virtualizer = useVirtualizer({
    count: items.length,
    getScrollElement: () => parentRef.current,
    estimateSize: () => 40, // px per row
  });

  return (
    <div ref={parentRef} style={{ height: 400, overflow: "auto" }}>
      <div style={{ height: virtualizer.getTotalSize(), position: "relative" }}>
        {virtualizer.getVirtualItems().map((virtualRow) => {
          const item = items[virtualRow.index];
          return (
            <div
              key={item.id}                         {/* still the item's stable id */}
              style={{ position: "absolute", top: virtualRow.start, height: virtualRow.size }}
            >
              {item.name}
            </div>
          );
        })}
      </div>
    </div>
  );
}

    Senior Engineer Perspective

    The insight worth stating plainly: "virtualization solves a DOM-node-count problem the browser has, not a React reconciliation-efficiency problem" — even a perfectly optimized React app chokes on tens of thousands of live DOM nodes because layout/paint cost is fundamentally proportional to DOM size. A good follow-up: "does virtualization change how you think about keys?" — no, the rule stays the same (stable, data-derived identity), but the cost of getting it wrong is arguably higher, since a broken key can cause the recycled DOM pool to display stale or duplicated content as the user scrolls, a more visually jarring failure than the equivalent bug in a fully-rendered list.

    Q95. What's the risk of rendering deeply nested ternaries, and how do you refactor them?

    ROI: ★★★★☆ Frequency: High

    Short Answer

    A chain of nested ternaries (a ? x : b ? y : c ? z : w) inside JSX becomes hard to parse visually, easy to misplace a parenthesis in, and hard to add a new branch to safely — a small edit can silently change which condition a given branch actually belongs to. The fix is almost always the same one used throughout this section: extract the decision into a variable or a lookup map above the return, or convert to an early-return chain, so each branch is a clearly separated, independently readable statement rather than a fragment embedded in one large expression.

    Detailed Answer

    Nested ternaries are especially risky because JSX's whitespace/formatting doesn't enforce indentation the way a switch or chained if/else would — a deeply nested ternary can be reformatted by an auto-formatter in a way that visually obscures which condition guards which branch, and a missing/misplaced parenthesis silently changes behavior rather than throwing an obvious syntax error. Refactoring options, in order of preference for most cases: (1) a lookup object/map keyed by a discriminant value (Q93's pattern) for exhaustive, mutually-exclusive states; (2) an early-return chain when each state genuinely represents a totally different UI for the whole component; (3) as a last resort, a small local helper function that encapsulates the branching logic and returns the appropriate JSX, callable from a single {getStatusView()} in the main return.

    Code Example

    // Hard to read and easy to misedit — which condition guards which branch?
function Badge({ score }) {
  return (
    <span>
      {score > 90 ? "A" : score > 80 ? "B" : score > 70 ? "C" : score > 60 ? "D" : "F"}
    </span>
  );
}

// Refactored: extracted, readable, easy to extend with a new grade band
function getGrade(score) {
  if (score > 90) return "A";
  if (score > 80) return "B";
  if (score > 70) return "C";
  if (score > 60) return "D";
  return "F";
}
function Badge({ score }) {
  return <span>{getGrade(score)}</span>;
}

    Senior Engineer Perspective

    This is a code-review-flavored question, and a senior answer treats it as a readability/maintainability issue, not a performance one (nested ternaries aren't slower, they're just error-prone to edit). Volunteering a specific refactor pattern (lookup map for discriminated states, early returns for whole-component states, a named helper function for anything in between) rather than a vague "I'd clean it up" shows you have a concrete toolkit for this exact, extremely common code smell.

    Q96. How do you conditionally render based on multiple boolean flags without a combinatorial explosion of branches?

    ROI: ★★★★☆ Frequency: High

    Short Answer

    Rather than branching on every combination of independent flags (which grows exponentially — 2ⁿ branches for n flags), render each flag's effect independently wherever it's relevant in the tree (each flag guards its own small piece of UI), and reserve combined branching only for cases where flags are genuinely not independent — i.e. where one flag's meaning depends on another's value.

    Detailed Answer

    Most real-world "multiple flags" scenarios are actually independent concerns that don't need to be cross-multiplied at all: whether to show a badge, whether a button is disabled, whether a banner is visible are each usually orthogonal and can each be a small, local inline conditional guarding just their own piece of markup, rather than combined into one giant conditional that enumerates every combination. True combinatorial logic only arises when flags interact (e.g. "disabled" should override "loading" visually) — and even then, computing a single derived value (like Q93's discriminated status) that resolves the interaction once, in one place, is more maintainable than branching on the raw flags directly in the JSX every time they're needed.

    Code Example

    // BAD: manually cross-multiplying independent flags into named branches
function Panel({ isExpanded, isPinned, isEditable, hasError }) {
  if (isExpanded && isPinned && isEditable && !hasError) { /* ... */ }
  if (isExpanded && isPinned && !isEditable && hasError) { /* ... */ }
  // 2^4 = 16 possible combinations if continued this way — unmaintainable
}

// GOOD: each independent flag guards only its own piece of UI, locally
function Panel({ isExpanded, isPinned, isEditable, hasError }) {
  return (
    <div className={isPinned ? "panel pinned" : "panel"}>
      {isExpanded && <PanelBody editable={isEditable} />}
      {hasError && <ErrorIcon />}
    </div>
  );
}

// A genuine INTERACTION between flags gets resolved once, centrally:
function getButtonState({ isLoading, isDisabled }) {
  if (isDisabled) return "disabled";       // disabled always wins over loading
  if (isLoading) return "loading";
  return "enabled";
}

    Senior Engineer Perspective

    The senior insight is recognizing which flags are genuinely independent (render each locally, no combined branching needed) versus which actually interact (resolve the interaction once into a single derived value, rather than branching on raw flags everywhere they're used). A candidate who reflexively tries to enumerate every combination as separate named branches is missing that most "multi-flag" UI logic doesn't actually require combinatorial thinking at all — it just looks like it does until you localize each independent concern to its own small conditional.

    Q97. What are common accessibility mistakes in conditional rendering (e.g. focus loss, missing live regions)?

    ROI: ★★★★☆ Frequency: High

    Short Answer

    Common mistakes: unmounting the element that currently has keyboard focus (e.g. conditionally hiding a panel that contained the focused button) without deliberately moving focus somewhere sensible, leaving assistive-tech users' focus "lost" in the document; and swapping content dynamically (search results updating, a form validation message appearing) without an ARIA live region, so a screen-reader user gets no announcement that anything changed at all, since the DOM change happened silently outside their current focus point.

    Detailed Answer

    When a conditionally-rendered element that had focus disappears, the browser's default behavior is to move focus to document.body — from a screen-reader user's perspective, this is disorienting: keyboard navigation context is silently reset to the top of the page with no explanation. The fix is to explicitly move focus to a sensible location right when the conditional removes the previously-focused element — typically the element that triggered the change, or the next logical focus target (mirroring the same "restore focus" discipline error boundaries and modals need, per Q55).

    For content that updates without any focus change at all (a live search-result count, an inline validation error appearing after a blur), sighted users see the change immediately, but a screen-reader user has no notification unless the changed region is marked with aria-live="polite" (or "assertive" for urgent messages) — without it, conditionally rendering an error message is accessible to no one using a screen reader unless they happen to re-navigate past that exact spot.

    Code Example

    // BUG: closing a panel that had focus leaves focus lost at document.body
function CollapsiblePanel({ isOpen, onClose }) {
  return isOpen ? (
    <div>
      <button onClick={onClose}>Close</button> {/* if this had focus, closing loses it */}
      <PanelContent />
    </div>
  ) : null;
}

// FIXED: explicitly restore focus to a sensible target on close
function CollapsiblePanelFixed({ isOpen, onClose, triggerRef }) {
  function handleClose() {
    onClose();
    triggerRef.current?.focus(); // move focus back to whatever opened the panel
  }
  return isOpen ? (
    <div>
      <button onClick={handleClose}>Close</button>
      <PanelContent />
    </div>
  ) : null;
}

// Announcing a dynamically-appearing message to screen readers
function EmailField({ error }) {
  return (
    <>
      <input aria-invalid={!!error} />
      <span role="alert" aria-live="assertive">
        {error /* appearing/disappearing here is now announced automatically */}
      </span>
    </>
  );
}

    Senior Engineer Perspective

    This question rewards accessibility experience beyond "add alt text" trivia — focus management on conditional unmount and live-region announcements for dynamic content are the two mistakes that show up constantly in real audits and are almost invisible to sighted, mouse-driven manual testing, which is exactly why they slip through so often. A strong closing point: test conditional-rendering changes with a screen reader (or at minimum, keyboard-only navigation) specifically around the moment content appears/disappears — that's precisely the interaction sighted, mouse-based QA is least likely to catch.
