23 - END-TO-END TESTING (CYPRESS & PLAYWRIGHT) INTERVIEW HANDBOOK

Target Audience: Frontend / React Engineer (3–6 Years) Goal: Not just answer questions, but survive follow-up grilling from experienced interviewers.

This chapter builds directly on Chapter 21 (Testing with Jest & React Testing Library). That chapter covers unit and integration/component testing — rendering components in jsdom, mocking modules, and asserting behavior without a real browser. This chapter is about the layer above that: end-to-end (E2E) testing — driving a real browser (Chromium, Firefox, WebKit) against your actual running application, clicking through complete user journeys the way a real user would. If Chapter 21 answers "does this component behave correctly in isolation," this chapter answers "does the whole system — routing, network, auth, real DOM rendering — actually work together." Expect overlap in vocabulary (locators, auto-waiting, mocking) but a different set of tradeoffs: E2E is slower, more expensive, and more prone to flakiness, so the interview conversation is as much about restraint and reliability engineering as it is about API syntax.

SECTION 1 - TESTING PYRAMID & ARCHITECTURE

Q1. Where does E2E testing fit in the testing pyramid, relative to unit and integration tests?

ROI: ★★★★★ Frequency: Very High

Short Answer

E2E sits at the top of the pyramid: it drives a real, running application through a real browser, exercising real routing, real network calls (or realistically stubbed ones), cookies, redirects, and multi-page flows — everything unit and component tests fake or skip entirely. That's what makes it the highest-confidence layer: a passing E2E test means an actual user journey works, not just that a component renders correctly in isolation. It's also the slowest and most brittle layer, so the rule every senior engineer repeats is "few E2E tests, covering only business-critical happy paths" — login, checkout, signup, the flows that lose the company money if they break.

Detailed Answer

Chapter 21 covered the testing trophy: static analysis at the bottom, a thin layer of unit tests, a thick layer of integration/component tests (RTL rendering a component tree in jsdom, mocking only the network boundary), and E2E as a thin cap on top. The reason E2E can't replace that middle layer, and shouldn't try to, comes down to what jsdom (RTL's simulated DOM) cannot do:

  • No real browser engine — jsdom approximates the DOM; it doesn't do real layout, real CSS cascade, real paint, or real viewport behavior. Visual bugs, CSS overflow, z-index stacking issues are invisible to RTL.
  • No real navigation — jsdom doesn't actually navigate between pages; RTL tests usually render one route tree with a mocked router. E2E clicks a link and the browser actually navigates, with real URL changes, real back/forward, real redirects.
  • No real network — RTL mocks fetch/MSW at the JS layer. E2E can run against a real (or realistically seeded) backend, catching integration bugs between frontend and backend contracts that unit tests, by design, cannot see.
  • Cross-cutting concerns — auth cookies/session persistence across page loads, multi-tab flows, file uploads/downloads, browser permissions (geolocation, notifications) — all things only a real browser context can exercise.

The cost side is why you don't push everything up here: spinning up a browser and a full app (frontend + backend + database) per test is orders of magnitude slower than rendering a component in-process, and a full stack introduces more places for tests to flake (network timing, animation timing, third-party scripts, test data collisions). The pyramid's shape — narrow at the top — is a direct response to that cost/confidence tradeoff, not an aesthetic preference.

LayerWhat runsSpeedConfidenceTypical volume
Unit (Jest)Pure functions, reducers, hooksMillisecondsLow-mediumHundreds-thousands
Integration (RTL)Component tree in jsdom, network mocked (MSW)~10s of msMedium-highMajority of the suite
E2E (Cypress/Playwright)Real browser, real app, real/seeded backendSeconds per testHighestDozens — critical paths only

Project Example

On a subscription product, the E2E suite was deliberately kept to about 20 tests: sign up, add a card, upgrade a plan, cancel, and a couple of permission-gated flows. Everything else — form validation, empty states, error banners, pagination — lived in the RTL integration suite, which ran in under a minute versus the E2E suite's ten. When the E2E suite did fail, it was almost always a real, ship-blocking bug (a broken redirect after payment), which kept the team trusting red E2E runs instead of habitually re-running and ignoring them.

Senior Engineer Perspective

Interviewers use this question to check whether you understand E2E as a deliberate, expensive tool rather than "the real tests, everything else is fake." The strong answer explicitly ties E2E's value (real browser, real integration, highest confidence) to its cost (slow, flaky, expensive to maintain) and states the resulting policy: cover only critical journeys, seed data deterministically, and let cheaper layers catch the long tail of edge cases. A red flag answer treats E2E coverage percentage as a goal in itself — that's how teams end up with a two-hour, perpetually-flaky E2E suite that everyone learns to ignore.

Q2. How does Cypress's architecture differ from Playwright's, and why does that distinction matter?

ROI: ★★★★★ Frequency: Very High

Short Answer

Cypress runs its test code inside the browser, in the same run loop as your application — it injects itself into the page and executes commands from within that context. Playwright runs outside the browser entirely: it's a Node.js (or other language) process that drives the browser via each engine's native automation protocol (the DevTools Protocol for Chromium, and equivalent remote-debugging protocols for Firefox and WebKit). This single architectural choice explains most of the practical differences between the two tools — multi-tab and multi-origin support, true multi-browser coverage, and how each achieves auto-waiting.

Detailed Answer

Cypress: in-browser. Test code, the Cypress driver, and your application share the same browser tab and JavaScript execution context (the app runs inside an iframe that Cypress controls). This gives Cypress excellent visibility into what's happening — it can hook into network requests, timers, and the DOM directly from the inside, which is part of why its time-travel debugger (a snapshot of the DOM at every command) is so good. The tradeoff is real constraints: historically no true multi-tab support (a new tab opens outside Cypress's control), and cross-origin navigation was restricted for years because the injected-iframe model assumes a single origin (modern Cypress has loosened this with cy.origin(), but it's still an explicit workaround, not the default).

Playwright: out-of-process automation. Playwright launches a real browser binary and talks to it over each engine's automation protocol from a separate process. Because it isn't trapped inside a single page's execution context, it can drive multiple tabs, multiple browser contexts (isolated "incognito" sessions), and multiple origins natively, and it ships first-class drivers for Chromium, Firefox, and WebKit — not just Chromium-family browsers. This is also why Playwright can offer bindings in multiple languages (TypeScript/JavaScript, Python, Java, .NET) using the same underlying protocol layer, whereas Cypress's in-browser model ties it to JavaScript.

AspectCypressPlaywright
Execution modelInside the browser, same JS context as the appOut-of-process, drives the browser via protocol
BrowsersChromium family + Firefox (experimental WebKit)Chromium, Firefox, WebKit — all first-class
Multi-tab / multi-originLimited; needs cy.origin() workaroundsNative — multiple pages/contexts out of the box
LanguagesJavaScript/TypeScript onlyTS/JS, Python, Java, .NET
DebuggabilityTime-travel DOM snapshots per command (best-in-class UX)Trace viewer with timeline, DOM snapshots, network
Parallel/shardingBuilt into the runner; free tier limited on the dashboardBuilt-in, free, sharding flag on the CLI

Neither architecture is strictly "better" — they optimize for different things. Cypress's in-browser model buys unmatched interactive debugging (you watch your app react to each command, live, in a real browser window with time-travel). Playwright's out-of-process model buys breadth (real cross-browser coverage, multi-tab/multi-origin, multi-language) at a small cost in that debugging-in-the-browser feel, offset by its own strong trace viewer.

Senior Engineer Perspective

The answer that separates candidates who've actually used both tools from those reciting marketing copy: connect the architecture to a concrete symptom. "Cypress struggles with a payment flow that redirects to a different origin (Stripe checkout) because it's designed around a single injected iframe — you either restructure the test with cy.origin() or stub the redirect. Playwright handles that natively because it isn't living inside the page at all." That level of specificity signals real production experience, not just reading two feature-comparison tables.

SECTION 2 - WRITING TESTS

Q3. How do you write a basic Cypress test — cy.visit, cy.get, and assertions?

ROI: ★★★★☆ Frequency: High

Short Answer

A Cypress test opens the app with cy.visit(url), locates elements with cy.get(selector) (or the Testing-Library-style cy.findByRole/cy.findByText plugin queries), and asserts with a chained .should(...) — Cypress's commands are asynchronous under the hood but written to read synchronously, and every command automatically retries until it succeeds or times out, which is the foundation of Cypress's low-flake reputation.

Detailed Answer

Cypress tests live in describe/it blocks (Mocha syntax, familiar from Jest). The key mental model shift from Jest: Cypress commands don't return values directly — they queue onto a command chain that Cypress executes and retries internally. You never await a Cypress command; instead you chain .then() if you need the resolved value, and let .should() do the assertion-with-retry.

cy.get() uses CSS selectors by default. The official @testing-library/cypress plugin adds cy.findByRole, cy.findByText, etc., mirroring RTL's query priority (see Q5) — the recommended way to select elements in new Cypress test suites, for the same resilience reasons RTL recommends them for component tests.

Configuration lives in cypress.config.js, where you set the baseUrl (so cy.visit('/login') resolves relative to your dev/staging server) and register any plugins (like cy.intercept helpers or the Testing Library queries).

Code Example

// cypress.config.js
const { defineConfig } = require("cypress");

module.exports = defineConfig({
  e2e: {
    baseUrl: "http://localhost:3000",
    setupNodeEvents(on, config) {
      // register plugins/tasks here
    },
  },
});

// cypress/e2e/login.cy.js
describe("login flow", () => {
  beforeEach(() => {
    cy.visit("/login");           // navigate to a real running app
  });

  it("logs in with valid credentials", () => {
    cy.findByLabelText(/email/i).type("a@b.com");
    cy.findByLabelText(/password/i).type("secret1");
    cy.findByRole("button", { name: /log in/i }).click();

    // .should() retries automatically until the assertion passes or times out
    cy.findByRole("heading", { name: /dashboard/i }).should("be.visible");
    cy.url().should("include", "/dashboard");
  });

  it("shows an error for a wrong password", () => {
    cy.findByLabelText(/email/i).type("a@b.com");
    cy.findByLabelText(/password/i).type("wrong");
    cy.findByRole("button", { name: /log in/i }).click();

    cy.findByText(/invalid credentials/i).should("be.visible");
  });
});

Senior Engineer Perspective

The thing to demonstrate is understanding that Cypress commands are queued and retried, not immediately executed — that's why you never see await in a Cypress test and why chaining cy.get(...).should(...) is the retry mechanism, not just syntax. A common junior mistake is trying to store a command's return value in a regular variable (const el = cy.get(...) — this is undefined, not the element); the correct pattern is .then(el => ...) or an alias with .as()/cy.get('@alias').

Q4. How do you write a basic Playwright test — page.goto, locators, and expect?

ROI: ★★★★☆ Frequency: High

Short Answer

A Playwright test navigates with await page.goto(url), finds elements with a locator (e.g. page.getByRole(...)), and asserts with expect(locator).toHaveText(...) (or similar) from @playwright/test's web-first assertion library, which — like Cypress's .should() — automatically retries until the condition is true or the timeout elapses. Unlike Cypress, everything is genuinely asynchronous, so you await every action and assertion.

Detailed Answer

Playwright's test runner (@playwright/test) injects a page fixture (and context, browser, request) into each test function — no manual browser setup required. A locator (created with page.getByRole, getByLabel, getByTestId, etc.) is a lazy, re-queryable reference to an element: it doesn't find the element until you act on it or assert against it, and it re-finds it every time, which is what makes Playwright resilient to elements that re-render between the locator being created and the action running.

Assertions from expect(locator).toBeVisible(), .toHaveText(), .toHaveValue(), etc. are "web-first": they poll the locator until the condition holds or the timeout (default 5s) expires, rather than checking once and failing immediately. This is the direct Playwright analog to Cypress's .should() retry-ability and to RTL's findBy/waitFor.

Configuration lives in playwright.config.ts, where you set baseURL, the browsers/projects to run against (Q10), retries, and reporters.

Code Example

// playwright.config.ts
import { defineConfig } from "@playwright/test";

export default defineConfig({
  testDir: "./tests",
  use: {
    baseURL: "http://localhost:3000",
    trace: "on-first-retry",       // capture a trace only when a test needs a retry
  },
});

// tests/login.spec.ts
import { test, expect } from "@playwright/test";

test.describe("login flow", () => {
  test.beforeEach(async ({ page }) => {
    await page.goto("/login");
  });

  test("logs in with valid credentials", async ({ page }) => {
    await page.getByLabel("Email").fill("a@b.com");
    await page.getByLabel("Password").fill("secret1");
    await page.getByRole("button", { name: /log in/i }).click();

    // web-first assertion: polls until true or times out
    await expect(page.getByRole("heading", { name: /dashboard/i })).toBeVisible();
    await expect(page).toHaveURL(/.*dashboard/);
  });

  test("shows an error for a wrong password", async ({ page }) => {
    await page.getByLabel("Email").fill("a@b.com");
    await page.getByLabel("Password").fill("wrong");
    await page.getByRole("button", { name: /log in/i }).click();

    await expect(page.getByText(/invalid credentials/i)).toBeVisible();
  });
});

Senior Engineer Perspective

Interviewers listen for the word "lazy" when you describe a locator — the distinction between "an object that finds the element right now" (which can go stale) and "an object that re-finds the element every time you use it" (Playwright's model) is exactly why Playwright tests survive re-renders that would break a naive document.querySelector reference captured too early. Also worth naming: Playwright ships a codegen tool (npx playwright codegen) that records your clicks and generates locator-based test code, useful for scaffolding but not a substitute for understanding what it generates.

Q5. What locator strategies should you use, and how do you avoid flaky selectors?

ROI: ★★★★★ Frequency: Very High

Short Answer

Both tools converge on the same recommendation Chapter 21 gave for RTL: prefer selecting elements the way a user (or assistive technology) would — role, accessible name, label text, visible text — over brittle implementation details like CSS class names, tag hierarchy, or nth-child position. Reserve data-testid as an explicit escape hatch for elements with no meaningful role or stable text, not as the default strategy. The reasoning is identical across unit, integration, and E2E layers: selectors coupled to markup structure break on every refactor; selectors coupled to user-facing meaning survive them.

Detailed Answer

The failure mode this question is really probing: a team writes hundreds of E2E tests using cy.get('.btn-primary.mt-2') or page.locator('div > div:nth-child(3) > button'), then a designer changes a class name or a developer reorders a wrapper div, and dozens of unrelated tests fail — not because behavior changed, but because the selector was coupled to styling or DOM shape instead of meaning.

PriorityCypressPlaywrightWhy
1 (best)cy.findByRolepage.getByRoleRole + accessible name — stable, tests accessibility for free
2cy.findByLabelTextpage.getByLabelBest for form fields
3cy.findByTextpage.getByTextNon-interactive content; breaks on copy changes, use sparingly
4 (escape hatch)cy.get('[data-testid=...]')page.getByTestIdNo accessible role/text available
avoidcy.get('.class-name')page.locator('.class-name')Coupled to styling, not meaning; breaks on refactors

Two nuances worth surfacing in an interview: first, data-testid isn't "bad" — it's appropriate for elements that genuinely have no user-facing role or stable text (a chart canvas, a drag handle, a purely decorative wrapper); the mistake is reaching for it as the default instead of the fallback. Second, text-based selectors are the most fragile against legitimate product change (marketing rewrites a button label) — role + accessible name is more stable because the role ("button", "the primary CTA") rarely changes even when its wording does.

Code Example

// Avoid: coupled to styling/DOM structure
cy.get(".btn.btn-primary.submit-btn");
page.locator("form > div:nth-child(2) > button");

// Prefer: coupled to user-facing meaning
cy.findByRole("button", { name: /submit order/i });
page.getByRole("button", { name: /submit order/i });

// Escape hatch, used deliberately (no accessible role/text exists)
cy.get('[data-testid="revenue-chart"]');
page.getByTestId("revenue-chart");

Senior Engineer Perspective

The strongest answer explicitly connects this back to the RTL query priority from Chapter 21 — it's the same principle applied one layer up, which shows you understand testing philosophy as a coherent whole rather than tool-specific trivia. Mention that both Cypress (via the Testing Library plugin) and Playwright ship these queries as first-class citizens precisely because the ecosystem converged on this lesson after years of brittle CSS-selector-based suites.

SECTION 3 - RELIABILITY, ASYNC BEHAVIOR & NETWORK

Q6. How do Cypress and Playwright handle async UI, and why are explicit sleeps an anti-pattern?

ROI: ★★★★★ Frequency: Very High

Short Answer

Both frameworks build auto-waiting into their core commands: before clicking or asserting, they retry the underlying check (element exists, is visible, is not covered, is not disabled/animating) until it succeeds or a timeout is hit. This is the E2E-layer equivalent of RTL's findBy/waitFor from Chapter 21. A hardcoded cy.wait(2000) or page.waitForTimeout(2000) is an anti-pattern because it's both slower than necessary (you always pay the full delay) and still flaky (if the real operation takes longer than your guess, the test fails anyway; if it's the wrong number for a slower CI machine, it's flaky "sometimes").

Detailed Answer

Cypress retries most commands and all .should() assertions automatically for up to defaultCommandTimeout (4 seconds by default). cy.get('.spinner').should('not.exist') polls until the spinner is gone rather than checking once. Cypress also has built-in "actionability" checks before interacting with an element — it waits for the element to be visible, not disabled, not animating, and not covered by another element before firing a click, which quietly prevents a whole class of "clicked but nothing happened" flakiness.

Playwright does the same thing under the name auto-waiting: every action (click, fill, etc.) waits for the target to be attached, visible, stable (not still animating), enabled, and able to receive events before acting. Its web-first assertions (expect(locator).toBeVisible()) poll the same way Cypress's .should() does.

Why fixed sleeps are strictly worse: a hardcoded delay encodes a guess about how long an async operation takes. Too short, and the test is flaky on a slow CI runner or under load. Too long, and every test run pays the tax even when the condition was met instantly — multiplied across hundreds of tests, this is where "our E2E suite takes 45 minutes" comes from. Waiting for a condition (element visible, network idle, specific response received) is both faster in the common case and correct in the slow case, because it waits exactly as long as needed and no longer.

Code Example

// Anti-pattern: guessing at a delay
cy.wait(2000);                       // Cypress — hardcoded, always slow or wrong
await page.waitForTimeout(2000);     // Playwright — same problem

// Correct: wait for the actual condition
cy.get(".spinner").should("not.exist");             // Cypress: retries until true
cy.findByText(/order confirmed/i).should("be.visible");

await expect(page.locator(".spinner")).toBeHidden(); // Playwright: polls until true
await expect(page.getByText(/order confirmed/i)).toBeVisible();

// Waiting on a specific network response instead of a timer
cy.intercept("POST", "/api/orders").as("createOrder");
cy.findByRole("button", { name: /place order/i }).click();
cy.wait("@createOrder");             // waits for THIS request, not a guessed duration

const [response] = await Promise.all([
  page.waitForResponse("**/api/orders"),
  page.getByRole("button", { name: /place order/i }).click(),
]);

Senior Engineer Perspective

This is one of the highest-signal questions in the whole chapter because "never use a fixed sleep, wait for a condition" is the single most repeated rule across every testing layer (RTL's waitFor, Cypress's retry-ability, Playwright's auto-wait) — an interviewer who hears you generalize the principle across layers, rather than memorize one API, is hearing a senior answer. A good follow-up point: cy.wait('@alias') and page.waitForResponse(...) are the right tools when you need to wait on a specific network call rather than a visible DOM change — still condition-based, just a different condition.

Q7. How do you intercept and mock network requests — cy.intercept vs page.route?

ROI: ★★★★★ Frequency: Very High

Short Answer

Cypress uses cy.intercept(method, url, response) to stub, spy on, or modify network requests made by the app under test; Playwright uses the equivalent page.route(url, handler). Both let you run E2E tests against deterministic, controlled API responses instead of a real (and possibly flaky, rate-limited, or stateful) backend — the same motivation as MSW in Chapter 21, applied at the browser-automation layer instead of inside the JS test process.

Detailed Answer

Network mocking in E2E serves two distinct purposes, and good answers distinguish them: (1) determinism — forcing a specific response (an error, an empty list, a specific edge-case payload) that would be hard or slow to reproduce against a real backend, and (2) isolation/speed — removing a real network dependency so tests run fast and don't depend on a shared staging environment being up and correctly seeded.

cy.intercept can stub a response outright, assert that a request was made with the right body (spy-only, letting the real request through), or use a fixture file for the response body. Aliasing the intercept with .as('name') lets you later cy.wait('@name') — combining network mocking with the condition-based waiting from Q6.

Playwright's page.route works similarly: you register a handler for a URL pattern, and inside it you call route.fulfill(...) to stub a response, route.continue(...) to let it through (optionally modified), or route.abort() to simulate a network failure. Playwright also exposes page.waitForResponse(...) for asserting a specific request happened, independent of routing.

A frequent senior-level distinction: don't mock everything. Mocking every endpoint turns an E2E test into an expensive integration test that no longer verifies the real frontend-backend contract — which was much of E2E's point in the first place (Q1). The pragmatic middle ground many teams land on: run a handful of true E2E tests against a real, seeded backend for the critical happy path, and use network mocking more liberally for edge cases (error states, empty states, slow responses) that would be impractical or flaky to reproduce for real.

Code Example

// Cypress: cy.intercept
cy.intercept("GET", "/api/orders", { fixture: "orders.json" }).as("getOrders");
cy.intercept("POST", "/api/orders", (req) => {
  req.reply({ statusCode: 201, body: { id: "ord_1", status: "confirmed" } });
}).as("createOrder");

cy.visit("/orders");
cy.wait("@getOrders");
cy.findByRole("button", { name: /place order/i }).click();
cy.wait("@createOrder").its("request.body").should("include", { itemId: "sku_1" });

// Simulating a server error
cy.intercept("GET", "/api/orders", { statusCode: 500 }).as("getOrdersFailed");
cy.visit("/orders");
cy.findByText(/something went wrong/i).should("be.visible");

// Playwright: page.route
await page.route("**/api/orders", async (route) => {
  if (route.request().method() === "GET") {
    await route.fulfill({ path: "fixtures/orders.json" });
  } else {
    await route.continue(); // let POSTs go through untouched
  }
});

await page.goto("/orders");
await page.route("**/api/orders", (route) =>
  route.fulfill({ status: 500, body: JSON.stringify({ message: "boom" }) })
);
await expect(page.getByText(/something went wrong/i)).toBeVisible();

Senior Engineer Perspective

Interviewers reward the callback to MSW: "same idea as intercepting at the network layer in Chapter 21, just applied to real browser requests instead of jsdom's fetch." Also worth stating explicitly: over-mocking defeats the purpose of E2E. If your entire E2E suite stubs every endpoint, you've built a slow, flaky version of your integration suite — the honest answer distinguishes "mock the rare edge cases" from "mock everything for speed," and explains the tradeoff rather than picking one dogmatically.

Q8. What is visual regression testing, and how does it fit alongside functional E2E tests?

ROI: ★★★☆☆ Frequency: Medium

Short Answer

Visual regression testing captures a screenshot of a page or component and compares it, pixel-by-pixel (or via perceptual diffing), against a stored baseline image, flagging any unexpected visual change — a broken CSS rule, an unintended layout shift, a font that failed to load. It catches an entirely different class of bug than functional E2E assertions: a page can pass every toBeVisible() and should('be.visible') check while looking completely broken (overlapping elements, invisible text, a missing background), because functional assertions check the DOM/accessibility tree, not rendered pixels.

Detailed Answer

Playwright has this built in: expect(page).toHaveScreenshot() captures a screenshot and diffs it against a checked-in baseline, failing if the pixel difference exceeds a configurable threshold. Cypress doesn't ship this natively but integrates with dedicated visual-testing services (Percy, Applitools, Chromatic) or a plugin (cypress-image-snapshot) that does the same capture-and-diff workflow.

The operational challenges are what separate a good answer from a superficial one:

  • Baseline management — every intentional design change requires updating the baseline image, which (like Jest snapshots in Chapter 21) can degrade into "press update without looking" if the team isn't disciplined about reviewing diffs.
  • Environment sensitivity — font rendering, anti-aliasing, and GPU differences mean screenshots taken on a developer's laptop rarely match CI exactly; teams typically run visual tests only inside a fixed Docker image or a hosted service to get consistent rendering.
  • Non-determinism — animations, video, dynamic timestamps, and loading spinners must be frozen, hidden, or masked before the screenshot, or every run diffs against itself.
  • Where it lives — most teams run visual regression as a separate, smaller job from functional E2E (or scope it to key marketing/landing pages and a design-system's Storybook), rather than screenshotting every E2E test, because storage and review overhead scale with the number of baselines.

Code Example

// Playwright — built-in visual regression
import { test, expect } from "@playwright/test";

test("pricing page matches baseline", async ({ page }) => {
  await page.goto("/pricing");
  // mask dynamic content so it doesn't cause false diffs
  await expect(page).toHaveScreenshot("pricing.png", {
    mask: [page.locator(".live-visitor-count")],
    maxDiffPixelRatio: 0.02,
  });
});

// Updating baselines deliberately, after a reviewed design change:
// npx playwright test --update-snapshots

Senior Engineer Perspective

A senior answer treats this like Chapter 21's snapshot-testing discussion: valuable when narrowly scoped and reviewed, corrosive when it becomes noise nobody reads. The strongest point to make is naming the specific non-determinism sources (fonts, animation, dynamic data) and how you neutralize them (masking, disabling animations, fixed test data) — that's the part that actually gets asked as a follow-up, because it's where real visual-testing suites fail in practice.

SECTION 4 - SCALE, CI & CROSS-BROWSER

Q9. How do you parallelize E2E tests and integrate them into CI — what does sharding mean here?

ROI: ★★★★☆ Frequency: High

Short Answer

Sharding splits your test suite into N independent groups that run concurrently — on separate CI machines/containers — instead of one machine running every test sequentially. Both Cypress and Playwright support this natively: Playwright via a simple --shard=1/4-style CLI flag, Cypress via its own parallelization flag combined with either the paid Cypress Cloud dashboard (for automatic load-balancing across machines) or a CI matrix you configure yourself. The payoff is direct: a 40-minute suite split four ways finishes in roughly 10 minutes of wall-clock time, which matters enormously for how often a team is willing to run E2E at all (on every PR vs only nightly).

Detailed Answer

Playwright sharding is a first-class CLI feature: npx playwright test --shard=1/4 tells that process to run only its 1-of-4 slice of the total test files, determined by Playwright's own load-balancing across the total file list. You run this same command four times (once per shard index) across four parallel CI jobs, typically via a CI matrix, and merge the resulting reports/artifacts at the end.

Cypress parallelization requires either the Cypress Cloud dashboard service (which dynamically balances specs across available machines based on prior run duration — the "smart" option, but a paid feature) or manually splitting spec files across a CI matrix yourself, similar to Playwright's manual approach but without Playwright's built-in fair-splitting flag.

CI integration beyond parallelism itself typically includes: running against a preview/staging deployment URL (not localhost) so the test genuinely exercises what will ship; uploading trace/video artifacts on failure so a flaky or broken run is debuggable without reproducing locally; and gating merges on the suite passing while keeping it fast enough that developers don't start ignoring or skipping it. A common CI pattern is to run the fast unit/integration suite on every commit and the slower E2E suite only before merge to main or on a schedule, trading a bit of feedback latency for not blocking every push on a 10-minute browser suite.

Code Example

# GitHub Actions — Playwright sharded across 4 jobs
jobs:
  e2e:
    strategy:
      matrix:
        shard: [1, 2, 3, 4]
    steps:
      - uses: actions/checkout@v4
      - run: npm ci
      - run: npx playwright install --with-deps
      - run: npx playwright test --shard=${{ matrix.shard }}/4
      - uses: actions/upload-artifact@v4
        if: failure()
        with:
          name: playwright-report-${{ matrix.shard }}
          path: playwright-report/

# Cypress — manual spec splitting across a matrix (no dashboard)
jobs:
  e2e:
    strategy:
      matrix:
        containers: [1, 2, 3, 4]
    steps:
      - uses: cypress-io/github-action@v6
        with:
          record: false
          parallel: false   # true + --record requires Cypress Cloud

Senior Engineer Perspective

The follow-up interviewers love here: "what happens when one shard has all the slow tests and finishes last, dragging the whole job?" Playwright's built-in sharding load-balances by historical duration data when available; naive manual splitting (alphabetical, or by file count) can produce exactly this imbalance. Mentioning that you've had to actively rebalance shards, or that Cypress Cloud's paid tier exists specifically to solve this dynamically, shows you've operated a real CI pipeline rather than just read the docs.

Q10. How does Playwright achieve cross-browser testing — Chromium, Firefox, and WebKit in one API?

ROI: ★★★★☆ Frequency: High

Short Answer

Playwright ships patched builds of Chromium, Firefox, and WebKit that it controls through each engine's own automation protocol, all exposed behind one identical API — you write a test once against page, and the same test runs unmodified against any of the three engines by declaring multiple "projects" in the config. This is the practical payoff of the out-of-process architecture from Q2: because Playwright never depends on being injected into a single browser's page context, it can drive fundamentally different browser engines through the same abstraction.

Detailed Answer

Firefox and Safari (WebKit) together still represent a meaningful slice of real-world traffic, and each has genuine rendering and API quirks — Safari/WebKit in particular is notorious for JS API gaps and different behavior around things like date inputs, IndexedDB, or intersection observers. Cross-browser E2E exists to catch "works in Chrome, silently broken in Safari" bugs before users find them, which unit/integration tests (running in a single simulated or headless-Chromium-based environment) typically can't.

Playwright configures this via the projects array in playwright.config.ts — each project pairs a name with a browser type, and running npx playwright test with no filter runs every spec against every project. CI can also run projects in parallel matrix jobs, combining this with the sharding from Q9 (shard within a browser, and run browsers in parallel across jobs).

Cypress historically was Chromium-and-Electron-first, with Firefox support added later and WebKit still experimental/limited — a genuine practical gap versus Playwright for teams that need guaranteed Safari coverage, and one of the concrete reasons cited in the tool-choice discussion in Q14.

Code Example

// playwright.config.ts
import { defineConfig, devices } from "@playwright/test";

export default defineConfig({
  projects: [
    { name: "chromium", use: { ...devices["Desktop Chrome"] } },
    { name: "firefox",  use: { ...devices["Desktop Firefox"] } },
    { name: "webkit",   use: { ...devices["Desktop Safari"] } },
    { name: "mobile-safari", use: { ...devices["iPhone 13"] } },
  ],
});

// Run every project:            npx playwright test
// Run just one engine:          npx playwright test --project=webkit

Senior Engineer Perspective

Strong candidates mention a real WebKit-specific bug they've hit — date/time input rendering, IndexedDB quirks, or scroll-behavior differences — because it grounds "cross-browser testing matters" in something concrete rather than a platitude. Also worth noting: cross-browser E2E multiplies your total run time by the number of engines, so teams often run the full matrix only on a merge-to-main or nightly schedule, and Chromium-only on every PR, as a pragmatic cost/coverage tradeoff.

Q11. How do you handle test data setup and teardown — fixtures, API-driven seeding vs UI-driven setup?

ROI: ★★★★☆ Frequency: High

Short Answer

The fast, reliable pattern is to seed and tear down test data through a direct API or database call (a backend seeding endpoint, a fixture-loading script, or direct DB access) rather than by driving the UI to create that state (e.g. clicking "sign up" through five screens before every single test). UI-driven setup is legitimate exactly once — as the subject of the signup test itself — but using it as scaffolding for every other test multiplies run time and multiplies the number of places a flaky click can break an otherwise-unrelated test.

Detailed Answer

Both frameworks provide hooks for this outside the UI layer. Cypress offers cy.request() (a raw HTTP call, bypassing the browser UI entirely) and cy.task() (running arbitrary Node code — direct DB writes, resetting a test database) inside before/beforeEach. Playwright's equivalent is its request fixture (an API testing client available inside any test, no browser needed) plus test.beforeEach/global setup files, and dedicated globalSetup/globalTeardown config hooks for once-per-run seeding (e.g. resetting an entire test database before the suite starts).

The deeper principle: test independence. Each test should set up exactly the data it needs and not depend on state left over from a previous test or a specific run order — shared, accumulating test-environment state is one of the top causes of "passes alone, fails in CI" flakiness (the E2E-scale version of the mock-state-leakage problem from Chapter 21's Jest section). Seeding via API/fixtures makes this cheap enough to actually do per-test; seeding via seed data checked into a shared staging environment, by contrast, tends to rot into tests that quietly depend on "whatever's currently in staging."

Teardown matters just as much as setup: leaving created records/users behind pollutes the environment for the next run and can cause name/email collisions (a Cypress or Playwright test that "signs up user a@b.com" will fail the second time it runs if that user still exists from the last run). The reliable pattern is to seed with a unique identifier per test run (timestamp/UUID in the email or slug) and/or clean up in an afterEach/teardown hook.

Code Example

// Cypress: seed via a real API call, bypassing the UI entirely
beforeEach(() => {
  cy.request("POST", "/api/test/seed-user", {
    email: `user_${Date.now()}@test.com`,
    plan: "pro",
  }).then((res) => {
    cy.wrap(res.body.userId).as("userId");
  });
});

afterEach(function () {
  cy.request("DELETE", `/api/test/users/${this.userId}`); // cleanup
});

// Playwright: the built-in `request` fixture, no browser needed for setup
import { test, expect } from "@playwright/test";

test("pro user sees the upgraded dashboard", async ({ page, request }) => {
  const seed = await request.post("/api/test/seed-user", {
    data: { email: `user_${Date.now()}@test.com`, plan: "pro" },
  });
  const { userId, authToken } = await seed.json();

  await page.goto("/dashboard");
  await page.context().addCookies([{ name: "session", value: authToken, url: "http://localhost:3000" }]);
  await expect(page.getByText(/pro features/i)).toBeVisible();

  await request.delete(`/api/test/users/${userId}`); // teardown
});

Senior Engineer Perspective

The signal to give: "only drive the UI for the thing you're actually testing; everything else is a shortcut through the API." A strong candidate also names the collision problem directly — unique per-run identifiers and explicit teardown — because that's the specific failure mode ("works locally, fails the second time CI runs it") that reveals whether someone has actually operated an E2E suite at scale versus written a handful of demo tests.

SECTION 5 - PATTERNS & CHOOSING A TOOL

Q12. What is the Page Object Model, and how does component-level testing fit alongside full E2E?

ROI: ★★★★☆ Frequency: High

Short Answer

The Page Object Model (POM) wraps the locators and interactions for a given page (or a reusable piece of UI) inside a class, so tests call readable methods like loginPage.login(email, password) instead of repeating raw locator chains in every test. When the UI changes, you update the locator in one place — the page object — instead of hunting through every test file that touched that element. Separately, Playwright also supports component testing (@playwright/experimental-ct-react and equivalents), which mounts a single component in a real browser without a full app or server, sitting architecturally between RTL's jsdom-based component tests and full E2E.

Detailed Answer

POM's value is almost entirely about maintenance cost as a suite grows, not about individual test readability. Without it, a locator change (say, a login button's accessible name changes from "Log in" to "Sign in") means grepping across every spec file that clicks that button. With a page object, exactly one method's internals change, and every test that calls loginPage.login(...) keeps working. This becomes essential once a suite passes roughly 30-50 tests — below that, some teams find POM's extra indirection isn't yet worth it, and colocated locators are still readable.

A common critique worth voicing: overly deep POM hierarchies (base page classes with multiple levels of inheritance, page objects wrapping page objects) can become their own maintenance burden — the pattern should reduce duplication, not introduce a second codebase to maintain. A pragmatic middle ground many teams use instead of full class-based POM is simple locator-returning functions or Playwright's fixtures mechanism, which achieves the same reuse with less ceremony.

Component testing (Playwright's experimental component test runners, or Cypress's long-standing Component Testing mode) mounts one component — real browser, real CSS, real event handling — without booting the whole application or a backend. This sits between RTL (jsdom, no real browser, fastest) and full E2E (real browser, full app, slowest): you get real-browser fidelity for one component's visual/interactive behavior at a fraction of full E2E's cost, which is attractive for testing a complex, highly interactive component (a rich date picker, a drag-and-drop board) in isolation.

Code Example

// Playwright — a page object
export class LoginPage {
  constructor(private page: Page) {}

  async goto() {
    await this.page.goto("/login");
  }

  async login(email: string, password: string) {
    await this.page.getByLabel("Email").fill(email);
    await this.page.getByLabel("Password").fill(password);
    await this.page.getByRole("button", { name: /log in/i }).click();
  }
}

// The test reads at the level of intent, not locators
test("logs in successfully", async ({ page }) => {
  const loginPage = new LoginPage(page);
  await loginPage.goto();
  await loginPage.login("a@b.com", "secret1");
  await expect(page.getByRole("heading", { name: /dashboard/i })).toBeVisible();
});

// Playwright component testing — mounts ONE component, real browser, no full app
import { test, expect } from "@playwright/experimental-ct-react";
import { Counter } from "./Counter";

test("increments in a real browser", async ({ mount }) => {
  const component = await mount(<Counter />);
  await component.getByRole("button", { name: /increment/i }).click();
  await expect(component.getByText("Count: 1")).toBeVisible();
});

Senior Engineer Perspective

The nuanced answer names both the benefit and the trap: POM reduces the blast radius of a locator change, but a deep, over-abstracted page-object hierarchy can become harder to maintain than the duplication it replaced. On component testing, the sharp point to make is placing it correctly on the spectrum — real browser fidelity like E2E, but scoped to one component like RTL — and that it's most valuable for complex interactive components where jsdom's simulated DOM genuinely can't reproduce real browser behavior (drag events, real CSS layout, actual focus management).

Q13. How do you diagnose flaky E2E tests, and what retry strategies actually help?

ROI: ★★★★★ Frequency: Very High

Short Answer

Flaky tests almost always trace back to one of a small set of root causes: races against async UI that auto-waiting didn't fully cover (an element that's technically visible but a click handler hasn't attached yet), test data collisions/shared state, timing-sensitive animations, or genuine environment nondeterminism (network latency, third-party scripts). Blind retries (just re-running a failed test until it passes) are a blunt, last-resort mitigation that hides symptoms — the senior move is to use built-in tracing/video artifacts to find the actual race, fix the underlying wait condition, and reserve retries for genuine, irreducible environment flakiness rather than as a substitute for a correct test.

Detailed Answer

Root causeSymptomReal fix
Race with async UIClick "does nothing" intermittentlyWait for the specific readiness signal (network response, element enabled) instead of assuming visible = interactive
Shared/leftover test dataPasses alone, fails in the full suite or on rerunUnique seed data per test + explicit teardown (Q11)
Animation/transition timingElement "not clickable" or screenshot mismatchDisable CSS transitions in test mode, or wait for the animation-end state explicitly
Test order dependencyFails only when run after test XFull test isolation — no test should assume another ran first
Real network/environment flakeRare, non-reproducible locallyA narrow, logged retry — plus alerting if retry rate climbs

Both tools give you the artifacts to actually diagnose these rather than guess: Cypress records a video and a DOM snapshot at every command by default on failure; Playwright's trace viewer captures a full timeline — DOM snapshots, network requests, console logs, and screenshots — for any failed (or retried) test, and is generally regarded as the more powerful debugging artifact of the two for reconstructing exactly what the page looked like at the moment of failure.

On retries specifically: both frameworks support a retries config (rerun a failed test N times before marking it failed). This is a legitimate tool for irreducible flakiness (a genuinely occasional network blip) but a dangerous one if used to paper over a real, reproducible race condition — a test that needs 3 retries to pass reliably is telling you something is actually racy, not that the infrastructure is unlucky. The healthy team practice is tracking retry rate per test over time and treating a consistently-retrying test as a bug to fix, not a fact of life to accept.

Code Example

// playwright.config.ts — retries + tracing for diagnosis
export default defineConfig({
  retries: process.env.CI ? 2 : 0,   // retry only in CI, never locally (don't hide local flake)
  use: {
    trace: "on-first-retry",          // capture full trace only when something needed a retry
    video: "retain-on-failure",
  },
});

// cypress.config.js — equivalent retry config
module.exports = defineConfig({
  retries: { runMode: 2, openMode: 0 },
  video: true,
});

// Fixing a real race instead of retrying around it:
// Bad — assumes visible means interactive
await page.getByRole("button", { name: /submit/i }).click();

// Good — wait for the actual precondition (button enabled once form is valid)
await expect(page.getByRole("button", { name: /submit/i })).toBeEnabled();
await page.getByRole("button", { name: /submit/i }).click();

Senior Engineer Perspective

The line that lands well: "retries are a bandage, not a cure — I use them for genuine environment noise, and I track retry rate so a test that needs retries every run gets flagged and fixed." Interviewers specifically probe whether candidates reach immediately for "just add retries" (a red flag suggesting they've never had to actually maintain suite health) versus naming the trace/video tooling and describing how they'd use it to find the real race — that's the differentiator between someone who's written a few E2E tests and someone who's owned a suite in production.

Q14. Cypress vs Playwright — how do you choose the right tool for a new project?

ROI: ★★★★★ Frequency: Very High

Short Answer

For a brand-new project today, Playwright is the more common default: free built-in parallelization, genuine multi-browser support (including WebKit/Safari), multi-tab and multi-origin support out of the box, and a best-in-class trace viewer, all with no paid tier required for CI parallelism. Cypress remains a strong, defensible choice — particularly where the team already has deep Cypress expertise, values its unmatched interactive time-travel debugging experience during local development, or is JavaScript-only and doesn't need Playwright's multi-language bindings.

Detailed Answer

This question isn't really asking "which tool is better" — it's asking whether you can reason about tradeoffs instead of reciting a preference. The honest, defensible framing:

Decision factorFavors CypressFavors Playwright
Need real Safari/WebKit coverage—Yes — first-class WebKit support
Multi-tab / multi-origin flows (e.g. OAuth redirects, Stripe checkout)Workarounds needed (cy.origin)Yes — native support
Free parallel CI runsNeeds Cypress Cloud (paid) or manual matrixYes — built into the CLI
Team is JS-only, wants the most polished interactive debuggerYes — mature time-travel UITrace viewer is strong but different UX
Need non-JS language bindings (Python/Java/.NET)No — JS/TS onlyYes
Existing large, working Cypress suiteMigration cost usually not worth itOnly if hitting a real Cypress limitation

Two follow-up traps to be ready for. First: "what would make you migrate an existing Cypress suite to Playwright?" — the honest answer is a concrete limitation you've actually hit (needing Safari coverage, needing free parallelism, a multi-origin flow Cypress can't cleanly express), not "Playwright is newer." Second: "does the choice matter as much as people think?" — a mature answer notes that the underlying testing discipline (auto-wait over sleeps, role-based locators, seeded test data, small critical-path suites, real trace artifacts for debugging) is identical regardless of which tool you pick, echoing the same point Chapter 21 made about Jest vs Vitest: the runner is an implementation detail, the testing philosophy is what actually transfers.

Senior Engineer Perspective

The answer that scores best names Playwright as the current default for new projects while explaining precisely why (parallelism, cross-browser, multi-origin) rather than treating it as received wisdom, and is equally ready to defend keeping an existing, healthy Cypress suite rather than churning a migration for its own sake. The failure mode to avoid is tool tribalism in either direction — interviewers are listening for judgment about tradeoffs, not brand loyalty.

QUICK REVISION SHEET

  • Q1 — Pyramid placement: E2E drives a real browser against the real app for highest confidence, but it's slow and flaky, so cover only critical happy paths; unit/integration (Ch. 21) handles the breadth.
  • Q2 — Architecture: Cypress runs inside the browser (great time-travel debugging, weaker multi-tab/cross-origin); Playwright runs out-of-process via each engine's protocol (native multi-tab, multi-origin, true multi-browser, multi-language).
  • Q3 — Cypress basics: cy.visit + cy.get/cy.findByRole + .should(...); commands queue and retry automatically — never await them, use .then() for values.
  • Q4 — Playwright basics: page.goto + locators (getByRole, etc.) + await expect(locator)...; locators are lazy and re-query on every action, which is why they survive re-renders.
  • Q5 — Locators: prefer role/label/text queries over CSS classes or DOM position; reserve data-testid as a fallback for elements with no accessible role — same priority order as RTL, one layer up.
  • Q6 — Auto-waiting: both tools retry actions/assertions against a real condition; fixed sleeps (cy.wait(2000), waitForTimeout) are both slower on average and still flaky — always wait on a condition.
  • Q7 — Network mocking: cy.intercept / page.route stub or spy on requests for deterministic edge cases; don't mock everything or you lose the real frontend-backend contract check E2E exists to provide.
  • Q8 — Visual regression: pixel-diffs a screenshot against a baseline to catch bugs functional assertions miss; needs disciplined baseline review and masking of dynamic content (timestamps, animations) to avoid false diffs.
  • Q9 — Parallelization: sharding splits the suite across CI machines to cut wall-clock time; Playwright has a built-in --shard flag, Cypress needs Cypress Cloud or a manual CI matrix.
  • Q10 — Cross-browser: Playwright's out-of-process design lets one API drive Chromium, Firefox, and WebKit via config "projects" — real Safari coverage that Cypress only offers experimentally.
  • Q11 — Test data: seed/teardown via a direct API call or DB task, not by clicking through the UI for every test; use unique per-run identifiers and explicit cleanup to avoid data collisions between runs.
  • Q12 — POM & component testing: Page Object Model centralizes locators so a UI change touches one file, not every spec — but avoid deep inheritance hierarchies; Playwright/Cypress component testing mounts one component in a real browser, between RTL and full E2E on the cost/confidence spectrum.
  • Q13 — Flaky tests: diagnose with trace/video artifacts first, fix the real race (data collisions, animation timing, missed wait conditions); use retries sparingly for genuine environment noise, not as a substitute for a correct test.
  • Q14 — Tool choice: Playwright is the common default for new projects (free parallelism, real multi-browser, multi-origin support); Cypress remains defensible for existing suites or teams valuing its interactive debugger — the underlying testing discipline matters more than the tool.
