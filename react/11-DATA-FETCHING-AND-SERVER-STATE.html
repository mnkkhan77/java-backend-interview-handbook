SECTION 1 - FETCHING BASICS

Q1. How do you fetch data with useEffect + fetch, and what is actually wrong with it?

ROI: ★★★★★ Frequency: Extremely High

Short Answer

The classic pattern is a useEffect that calls fetch, stores the result in useState, and tracks loading/error flags. It works for a single simple request, but it has serious flaws: race conditions when the dependency changes faster than requests resolve, no caching or deduplication so every mount refetches, no request cancellation, and it encourages waterfalls where child components fetch sequentially. It is fine for a demo and dangerous as an app-wide data layer.

Detailed Answer

Here is the pattern nearly everyone writes first:

Race conditions

If the effect depends on a prop like userId and the user clicks quickly (or types in a search box), you fire request A then request B. If A resolves after B, you overwrite the correct newer data with stale older data. The UI shows results for the wrong query. This is the single most common bug in hand-rolled fetching.

No caching or deduplication

Every time the component mounts — a route change, a tab switch, a parent re-render that remounts — you refetch from scratch and show a spinner again. Two components that need the same data fire two identical requests. There is no shared cache, so the network and the server do redundant work and the UI flickers.

No cancellation

When the component unmounts mid-flight, the promise still resolves and calls setState on an unmounted component (a wasted update, and historically a warning). Worse, without cancellation you cannot reliably abandon a superseded request.

Waterfalls

If a parent fetches, renders a child, and the child then fetches, the two requests run sequentially instead of in parallel. Deeply nested components create long chains of dependent round-trips that add latency the user feels.

Boilerplate and correctness

You end up re-implementing loading flags, error handling, retry, and stale-data logic in every component — inconsistently. This is exactly the boilerplate that server-state libraries eliminate.

Code Example

// The naive pattern — works, but read the comments
function UserProfile({ userId }: { userId: string }) {
  const [data, setData] = useState<User | null>(null);
  const [loading, setLoading] = useState(true);
  const [error, setError] = useState<Error | null>(null);

  useEffect(() => {
    setLoading(true);
    fetch(`/api/users/${userId}`)
      .then((res) => {
        if (!res.ok) throw new Error(`HTTP ${res.status}`);
        return res.json();
      })
      .then((json) => setData(json))   // RACE: an older request can win
      .catch((err) => setError(err))
      .finally(() => setLoading(false));
  }, [userId]);
  // No cache: remount = refetch. No cancel: unmount = setState leak.

  if (loading) return <Spinner />;
  if (error) return <ErrorBanner error={error} />;
  return <h1>{data?.name}</h1>;
}

Project Example

On a customer dashboard I built, a search-as-you-type field used exactly this pattern. Typing "serv" then "servana" fired two requests; the slower "serv" response landed last and the results list showed the wrong matches roughly one time in ten on a slow connection. The fix was an AbortController plus a stale-response guard — and eventually moving the whole data layer to TanStack Query so the cache key handled it for free.

Senior Engineer Perspective

The interviewer wants to hear you name the race condition unprompted. Juniors describe the happy path; seniors immediately say "and this races on fast dependency changes, and there's no cache." A strong answer ends with: "For anything beyond one throwaway request, I reach for TanStack Query or SWR rather than re-solving caching, dedup, cancellation, and retries by hand in every component." If they push on async directly in useEffect, note that the effect callback cannot be async (it would return a promise, not a cleanup function) — you define an inner async function or use .then.

Q2. How do you cancel an in-flight request with AbortController, and why does it matter?

ROI: ★★★★☆ Frequency: High

Short Answer

Create an AbortController, pass its signal to fetch, and call controller.abort() in the effect's cleanup function. This cancels the network request and rejects the promise with an AbortError, which you ignore. It fixes the race condition (the superseded request is aborted) and prevents state updates from stale responses. Cancellation is the primary reason effects return a cleanup function here.

Detailed Answer

The cleanup function runs before the effect re-runs (dependency changed) and on unmount. Aborting there means: when userId changes, the previous request is cancelled before the new one starts, so only the latest can complete. You must swallow the AbortError — it is expected, not a real failure.

Two nuances:

  • Alternative to abort — a "stale" flag. If a fetch client does not support signals, you can capture a local let active = true and set active = false in cleanup, then only call setState if active. This does not cancel the network request but prevents the stale update. Aborting is strictly better because it also frees the socket.
  • Timeouts. AbortSignal.timeout(ms) gives you a signal that auto-aborts, and AbortSignal.any([...]) combines a user-cancel signal with a timeout signal.

Server-state libraries do this for you: TanStack Query passes an AbortSignal into your query function automatically, so wiring it through to fetch gets cancellation of superseded queries for free.

Code Example

useEffect(() => {
  const controller = new AbortController();

  (async () => {
    try {
      const res = await fetch(`/api/users/${userId}`, {
        signal: controller.signal,
      });
      if (!res.ok) throw new Error(`HTTP ${res.status}`);
      setData(await res.json());
    } catch (err) {
      if (err instanceof DOMException && err.name === "AbortError") return; // expected
      setError(err as Error);
    }
  })();

  return () => controller.abort(); // cancels the previous request
}, [userId]);

// TanStack Query hands you the signal — just forward it:
useQuery({
  queryKey: ["user", userId],
  queryFn: ({ signal }) => fetch(`/api/users/${userId}`, { signal }).then(r => r.json()),
});

Senior Engineer Perspective

A common trap: candidates abort but forget to swallow the AbortError, so cancelling a request lights up the error UI. Mention that abort rejects the promise. Also know that abort() does not guarantee the server stops processing — it stops the client from waiting and lets the browser tear down the connection. For non-idempotent mutations, cancelling the client does not roll back a write that already committed server-side.

Q3. What is "server state" and why is it fundamentally different from client state?

ROI: ★★★★★ Frequency: Extremely High

Short Answer

Client state is data your app owns and fully controls — form inputs, a modal's open/closed flag, the current theme. It is synchronous and always up to date. Server state is data that lives on a remote server and is only cached on the client: you do not own it, it can change without you, it is asynchronous, and your copy can go stale. Treating server state like client state (dumping it in Redux/useState) is the root cause of most data-layer pain.

Detailed Answer

The distinction, popularized by Tanner Linsley (TanStack Query), is the single most important mental model in this chapter.

PropertyClient stateServer state
OwnershipYou own it exclusivelyRemote server owns it
FreshnessAlways currentCan be stale the instant you receive it
AccessSynchronousAsynchronous (network)
SharedLocal to the appShared across users/tabs/devices
NeedsJust store & update itCaching, dedup, revalidation, retries, pagination

Because server state can change under you, the interesting problems are all about synchronization: when is my cached copy stale, when do I refetch, how do I dedupe concurrent requests, how do I optimistically update then reconcile with the server's truth. General-purpose state managers (Redux, Zustand, Context) solve none of this — they are excellent for client state and a poor fit for server state. That is precisely the gap TanStack Query and SWR fill.

Project Example

A team I worked with kept the entire API response tree in Redux with hand-written thunks, reducers, and isLoading flags per entity — hundreds of lines. Migrating server data to TanStack Query and leaving only genuine client state (filters, selected rows, UI toggles) in Zustand deleted most of the store and eliminated a class of "stale data after mutation" bugs, because invalidation became a one-liner.

Senior Engineer Perspective

This is a philosophy question disguised as a definition. The senior signal is saying "I don't put server data in Redux." If asked "so is Redux dead?" — no: it is still great for complex client state (multi-step wizards, cross-cutting UI state, undo/redo). The modern architecture is server state in a query library, client state in a light store or Context. Naming that split is the answer they want.

Q4. How do you model loading, error, and empty states correctly?

ROI: ★★★★☆ Frequency: High

Short Answer

Represent the request as a small state machine — idle | loading | success | error — rather than a soup of independent booleans, because independent flags allow impossible combinations (e.g. loading && error). Distinguish an initial load (show a skeleton) from a background refetch (keep old data, show a subtle indicator), and treat an empty successful result as its own "empty" UI, not an error.

Detailed Answer

Three refinements separate a polished answer from a junior one:

  • Discriminated unions over boolean triples. With loading, error, and data as three separate values you can express contradictory states. A single status field makes illegal states unrepresentable and forces you to render every branch.
  • Initial load vs background refetch. On first load there is no data, so show a skeleton. On a refetch (stale data being revalidated) you already have data — keep showing it and add a small "refreshing" spinner. Query libraries expose this as isLoading (first fetch) vs isFetching (any fetch, including background).
  • Empty state. A 200 response with an empty array is success, not an error. Design a distinct empty state ("No results found") so users are not staring at a blank screen wondering if it broke.

Also handle the difference between a network failure and an HTTP error status. fetch only rejects on network failure; a 404 or 500 resolves with res.ok === false, so you must check it explicitly (axios throws on non-2xx by default — a common source of "why isn't my catch firing").

Code Example

type RequestState<T> =
  | { status: "idle" }
  | { status: "loading" }
  | { status: "success"; data: T }
  | { status: "error"; error: Error };

function render(state: RequestState<User[]>) {
  switch (state.status) {
    case "idle":
    case "loading":
      return <Skeleton />;
    case "error":
      return <ErrorBanner error={state.error} onRetry={refetch} />;
    case "success":
      return state.data.length === 0
        ? <EmptyState message="No users yet" />   // empty != error
        : <UserList users={state.data} />;
  }
}

// With TanStack Query the machine is given to you:
const { data, isLoading, isError, error, isFetching } = useQuery(/* ... */);

Senior Engineer Perspective

Interviewers probe the isLoading vs isFetching distinction because flickering skeletons on every background refetch is a telltale sign someone doesn't understand it. Bonus points for mentioning placeholderData/keepPreviousData so paginated lists don't collapse to a spinner between pages, and for treating error UI as retryable rather than a dead end.

SECTION 2 - SERVER STATE LIBRARIES

Q5. What problems does TanStack Query solve, and how do queries and query keys work?

ROI: ★★★★★ Frequency: Extremely High

Short Answer

TanStack Query (formerly React Query) is a server-state cache. You describe what you want with a queryKey and how to fetch it with a queryFn, and it handles caching, deduplication, background revalidation, retries, pagination, and garbage collection. The query key is the cache identity: same key = shared cached entry; change any value in the key and it is a different query that refetches. Keys are serializable arrays like ["todos", { status: "done" }].

Detailed Answer

You wrap the app in a QueryClientProvider and call useQuery in components. What you get out of the box:

  • Caching by key — two components using ["user", 5] share one cache entry and one in-flight request (dedup).
  • Background revalidation — stale data is shown instantly, then refetched silently (stale-while-revalidate).
  • Automatic refetch triggers — on window focus, network reconnect, and component remount.
  • Retries with backoff, request cancellation via signal, and garbage collection of unused cache entries.

Query keys are dependency arrays for your cache

Treat the key like a useEffect dependency array: every external value the query depends on (ids, filters, pagination, search term) belongs in the key. When it changes, the query automatically refetches — you never write imperative "when X changes, refetch" code. Keys must be serializable; object property order does not matter (they are hashed deterministically).

Code Example

// setup
const queryClient = new QueryClient();
<QueryClientProvider client={queryClient}><App /></QueryClientProvider>

// a query
function Todos({ status }: { status: string }) {
  const { data, isLoading, isError } = useQuery({
    queryKey: ["todos", { status }],           // identity + dependencies
    queryFn: ({ signal }) =>
      fetch(`/api/todos?status=${status}`, { signal }).then((r) => r.json()),
  });

  if (isLoading) return <Skeleton />;
  if (isError) return <ErrorBanner />;
  return <List items={data} />;
}
// Changing `status` -> new key -> automatic refetch, previous entry cached.

Senior Engineer Perspective

The follow-up is almost always "what goes in the query key?" The wrong answer is a bare string; the right answer is a structured array containing every input the fetch depends on. Mention query key factories (a small module exporting todoKeys.list(filters), todoKeys.detail(id)) to keep keys consistent across queries and invalidations — this is what separates a codebase that scales from one riddled with typo'd keys.

Q6. How do mutations and cache invalidation work?

ROI: ★★★★★ Frequency: Extremely High

Short Answer

useMutation handles writes (POST/PUT/PATCH/DELETE). Because a write changes server data, your cached queries are now stale, so in onSuccess you call queryClient.invalidateQueries({ queryKey }) to mark them stale and trigger a refetch — or setQueryData to write the new value directly. Queries are for reading and cached by key; mutations are for writing and are not cached, but they are the thing that drives cache updates.

Detailed Answer

The read/write split is deliberate. Queries subscribe to cached data; mutations perform a side effect and expose mutate, isPending, isError, and lifecycle callbacks (onMutate, onSuccess, onError, onSettled).

After a successful write you keep the cache consistent one of two ways:

  • Invalidate (refetch) — invalidateQueries marks matching queries stale; active ones refetch immediately. Simplest and safest: the server remains the source of truth. Invalidation is fuzzy by prefix, so invalidating ["todos"] invalidates ["todos", {status:"done"}] too.
  • Direct cache write — setQueryData patches the cache with the response (e.g. append the created item), avoiding a round-trip. Faster but you own correctness.

Use onSettled for logic that must run regardless of success/failure (e.g. closing a dialog, always invalidating to reconcile).

Code Example

function AddTodo() {
  const queryClient = useQueryClient();

  const mutation = useMutation({
    mutationFn: (title: string) =>
      fetch("/api/todos", {
        method: "POST",
        headers: { "Content-Type": "application/json" },
        body: JSON.stringify({ title }),
      }).then((r) => r.json()),

    onSuccess: () => {
      // mark every ["todos", ...] query stale -> active ones refetch
      queryClient.invalidateQueries({ queryKey: ["todos"] });
    },
  });

  return (
    <button
      disabled={mutation.isPending}
      onClick={() => mutation.mutate("Write handbook chapter")}
    >
      {mutation.isPending ? "Saving..." : "Add"}
    </button>
  );
}

Senior Engineer Perspective

Expect "invalidate vs setQueryData — when do you use each?" Answer: invalidate by default (server stays authoritative); use setQueryData when you already have the full new entity and want to skip a refetch, or for optimistic updates. A subtle trap: invalidateQueries resolves once refetch completes, so if you await it in the mutation you can defer closing a modal until the list is fresh. Also note invalidation only refetches active (mounted) queries immediately; inactive ones refetch on next mount.

Q7. staleTime vs gcTime (cacheTime) — what is the difference?

ROI: ★★★★★ Frequency: Extremely High

Short Answer

staleTime is how long data is considered fresh; while fresh, the query is served from cache with no background refetch. After it, data is stale and will be revalidated on the next trigger (mount, focus, reconnect). gcTime (garbage-collection time, formerly cacheTime) is how long an inactive query — one with no mounted observers — is kept in memory before being deleted. staleTime governs refetching; gcTime governs eviction. Defaults: staleTime: 0, gcTime: 5 minutes.

Detailed Answer

These two are the most misunderstood knobs in the library, and interviewers love the confusion.

staleTimegcTime (cacheTime)
Question it answers"Is my data fresh enough to skip refetching?""How long do I keep unused data before deleting it?"
Applies whileQuery is being usedQuery is inactive (no observers)
Default0 (immediately stale)5 minutes
Effect of raising itFewer background refetchesCache survives longer between mounts

Because the default staleTime is 0, data is stale the moment it arrives, so TanStack Query refetches on the next focus/mount — this is why beginners think it "fetches too much." The fix is to set a sensible staleTime for data that does not change every second (e.g. 30s–5min for a user profile). gcTime only starts counting when the last component using a query unmounts; if the user returns before it elapses, they instantly see cached data (then a background refresh if stale). Set gcTime < staleTime is a smell — the data would be evicted before it even goes stale.

Code Example

useQuery({
  queryKey: ["profile", userId],
  queryFn: fetchProfile,
  staleTime: 5 * 60 * 1000, // fresh for 5 min: no refetch on focus/mount within window
  gcTime: 10 * 60 * 1000,   // keep in memory 10 min after it goes unused
});

// Global defaults:
new QueryClient({
  defaultOptions: { queries: { staleTime: 60_000, gcTime: 5 * 60_000 } },
});

Senior Engineer Perspective

The killer follow-up: "My data refetches every time I switch tabs — why, and how do I stop it?" The answer is staleTime: 0 default plus refetchOnWindowFocus; raise staleTime. Do not "fix" it by disabling refetch globally — you would throw away the stale-while-revalidate behavior that keeps data current. Know the rename: cacheTime became gcTime in v5. Saying "cacheTime" is fine but knowing the new name signals you are current.

Q8. Give an overview of SWR and how it compares to TanStack Query.

ROI: ★★★★☆ Frequency: High

Short Answer

SWR (by Vercel) is a lightweight data-fetching hook named after the stale-while-revalidate cache strategy: return cached data immediately, revalidate in the background, and update when fresh data arrives. Its API is a single useSWR(key, fetcher) hook. It is smaller and simpler than TanStack Query but has a thinner mutation/invalidation story. TanStack Query is the more feature-complete choice for complex apps (infinite queries, robust mutations, devtools, framework-agnostic core); SWR shines for read-heavy apps, especially inside the Next.js ecosystem.

Detailed Answer

AspectSWRTanStack Query
Core APIuseSWR(key, fetcher)useQuery / useMutation
Bundle sizeSmallerLarger (more features)
Mutationsmutate() / useSWRMutation — lighterFirst-class useMutation with lifecycle hooks
Infinite / paginationuseSWRInfiniteuseInfiniteQuery (richer)
DevtoolsCommunityOfficial, excellent

Best fitRead-heavy, Next.js appsComplex client apps with heavy writes

Both share the same philosophy — server state is a cache to be revalidated, not owned — and both do focus refetch, dedup, and stale-while-revalidate. The decision is rarely about capability for a simple app; it is about how much mutation/caching machinery you need. For a dashboard with optimistic updates, complex invalidation, and infinite lists, TanStack Query's ergonomics win. For a mostly-read content site, SWR's minimalism is a feature.

Code Example

import useSWR from "swr";

const fetcher = (url: string) => fetch(url).then((r) => r.json());

function Profile({ id }: { id: string }) {
  const { data, error, isLoading, mutate } = useSWR(`/api/users/${id}`, fetcher, {
    revalidateOnFocus: true,
    dedupingInterval: 2000,
  });

  if (isLoading) return <Skeleton />;
  if (error) return <ErrorBanner />;
  return <h1>{data.name}</h1>;
}
// mutate() revalidates or writes the cache — analogous to invalidate/setQueryData.

Senior Engineer Perspective

Do not turn this into a tribal "X is better" answer — interviewers want to see you choose by requirements. The strongest line: "They solve the same problem with the same philosophy; I default to TanStack Query for write-heavy apps because of its mutation and invalidation ergonomics and devtools, and I'm comfortable with SWR for read-heavy or Next.js-native projects." Bonus: note that in the App Router era, React Server Components and fetch caching cover many read cases server-side, shrinking what you need a client library for.

SECTION 3 - CACHING & SYNC

Q9. How do background refetch, window-focus refetch, and request deduplication work?

ROI: ★★★★☆ Frequency: High

Short Answer

These are the three behaviors that make cached data feel live. Background refetch is stale-while-revalidate: show cached data instantly, silently refetch, swap in fresh data. Window-focus refetch re-runs stale queries when the user returns to the tab (also on network reconnect), so data is current after they've been away. Deduplication collapses multiple simultaneous requests for the same key into one in-flight request shared by all subscribers.

Detailed Answer

  • Stale-while-revalidate. When a stale query mounts, the user sees cached data with zero delay; a refetch runs in the background and, on success, the UI updates. This is why isFetching exists separately from isLoading — the background refresh should not blank the screen.
  • Refetch triggers. By default TanStack Query refetches stale queries on mount, on window focus (refetchOnWindowFocus), and on reconnect (refetchOnReconnect). All are gated by staleTime — fresh data is never refetched. You tune or disable these per query or globally.
  • Deduplication. If ten components request ["config"] at once, one network request fires and all ten receive the result. SWR calls this dedupingInterval. This eliminates the redundant-request problem of hand-rolled fetching entirely.

Code Example

useQuery({
  queryKey: ["dashboard"],
  queryFn: fetchDashboard,
  staleTime: 30_000,             // fresh 30s -> focus within 30s does NOT refetch
  refetchOnWindowFocus: true,    // default; refetch stale data when tab regains focus
  refetchOnReconnect: true,      // refetch after the network comes back
});
// 10 components with this key => 1 request (dedup), 10 subscribers.

Senior Engineer Perspective

Interviewers use focus-refetch as a litmus test: candidates who don't know it exists are surprised by "phantom" refetches; candidates who do explain it as a feature and control it with staleTime. Mention that for truly static reference data (country lists, enums) you set staleTime: Infinity to opt out of revalidation entirely, and for financial or dashboard data you might combine a short staleTime with polling.

Q10. How do you implement optimistic updates safely?

ROI: ★★★★☆ Frequency: High

Short Answer

An optimistic update applies the expected result to the cache before the server confirms, so the UI feels instant. In TanStack Query you do it in the mutation's onMutate: cancel outgoing refetches, snapshot the current cache, write the optimistic value, and return the snapshot as context. In onError you roll back to the snapshot; in onSettled you invalidate to reconcile with the server's real value. The rollback is the part people forget — without it a failed write leaves the UI lying.

Detailed Answer

The four-step recipe:

  1. onMutate: cancelQueries so an in-flight refetch doesn't clobber your optimistic write; snapshot with getQueryData; apply the change with setQueryData; return { snapshot }.
  2. onError(err, vars, context): restore context.snapshot via setQueryData.
  3. onSettled: invalidateQueries to fetch the authoritative server state (in case your optimistic value differed — e.g. server-generated id or timestamp).

Use optimism where the write almost always succeeds and latency is the enemy: toggling a like, checking a todo, reordering a list. Avoid it for writes that frequently fail validation or where showing a wrong intermediate state is dangerous (payments). v5 also offers a simpler UI-only variant reading mutation.variables while pending, without touching the cache.

Code Example

useMutation({
  mutationFn: (todo: Todo) => api.updateTodo(todo),

  onMutate: async (newTodo) => {
    await queryClient.cancelQueries({ queryKey: ["todos"] });
    const snapshot = queryClient.getQueryData<Todo[]>(["todos"]);
    queryClient.setQueryData<Todo[]>(["todos"], (old = []) =>
      old.map((t) => (t.id === newTodo.id ? newTodo : t))
    );
    return { snapshot }; // context passed to onError/onSettled
  },

  onError: (_err, _vars, context) => {
    if (context?.snapshot) queryClient.setQueryData(["todos"], context.snapshot); // rollback
  },

  onSettled: () => {
    queryClient.invalidateQueries({ queryKey: ["todos"] }); // reconcile with server
  },
});

Senior Engineer Perspective

The two things interviewers check: (1) do you cancelQueries first — otherwise a resolving background fetch overwrites your optimistic value and it flickers; (2) do you roll back on error. If you nail those, mention the reconcile step handles server-authored fields (ids, updatedAt) that your optimistic guess couldn't know. Weakest answers describe optimism as "just call setState early" with no rollback — that ships a UI that silently disagrees with the backend.

Q11. How does retry, exponential backoff, and error handling work?

ROI: ★★★☆☆ Frequency: Medium

Short Answer

TanStack Query retries failed queries automatically — by default 3 times with exponential backoff — before surfacing the error. You control it with retry (a count, boolean, or predicate) and retryDelay (a function of attempt index). Crucially, you should not retry non-retryable errors: a 404 or 401 will never succeed on retry, so return false for 4xx and only retry transient failures (network errors, 5xx, 429). Mutations do not retry by default, which is the safe choice for writes.

Detailed Answer

Exponential backoff spaces retries out (e.g. 1s, 2s, 4s, capped) so you don't hammer a struggling server — the same principle as backend retry policies. The default delay is Math.min(1000 * 2 ** attempt, 30000).

Best practices:

  • Don't retry client errors. Inspect the error and skip retries for 4xx (except 408/429). Retrying a 401 just delays showing the login prompt.
  • Mutations off by default. Blindly retrying a non-idempotent POST can create duplicate records. Enable retry only for idempotent operations or with an idempotency key.
  • Error surfaces. After retries are exhausted, isError/error populate. Pair with a React error boundary (via throwOnError) for render-time error handling, or handle inline.

Code Example

useQuery({
  queryKey: ["report", id],
  queryFn: fetchReport,
  retry: (failureCount, error) => {
    const status = (error as ApiError).status;
    if (status >= 400 && status < 500) return false; // don't retry 4xx
    return failureCount < 3;                          // retry transient up to 3x
  },
  retryDelay: (attempt) => Math.min(1000 * 2 ** attempt, 30_000), // backoff
});

Senior Engineer Perspective

The trap is "I set retries high to be robust." Retrying a 401/403/404 or a validation error wastes time and hides the real problem from the user. Seniors gate retries on error class and know mutations shouldn't blindly retry. Extra credit: mention request deduplication already handles the "double click" case, and that adding jitter to backoff avoids thundering-herd retries when many clients fail at once.

SECTION 4 - ADVANCED

Q12. What is a request waterfall, how does it differ from parallel fetching, and where does prefetching fit?

ROI: ★★★★☆ Frequency: High

Short Answer

A waterfall is a chain of sequential, dependent requests: the app can't start request B until request A returns, so latencies add up. Parallel fetching fires independent requests at the same time so total time is the slowest one, not the sum. Waterfalls come from two sources — genuine data dependencies (B needs A's id) and accidental structure (a child component fetches only after its parent renders). Prefetching starts a fetch before the component needs it (on hover, on route intent), hiding latency behind user actions.

Detailed Answer

Independent data should be fetched in parallel. With plain promises use Promise.all; with TanStack Query use useQueries (or just call multiple useQuery hooks — they run concurrently). The accidental waterfall — parent fetches, renders child, child fetches — is a structural problem: hoist the fetches up, or prefetch on the route so both start together.

Prefetching techniques:

  • queryClient.prefetchQuery on hover/focus of a link so the detail page's data is warm before the user clicks.
  • Route-level loaders (React Router loader, TanStack Router, Next.js) that kick off fetches as navigation begins, in parallel with code loading.
  • In the App Router / RSC world, fetching on the server eliminates the client waterfall entirely for initial load.

For genuine dependencies use enabled to make a query wait for its input — a controlled waterfall — rather than firing with an undefined id.

Code Example

// Parallel: both fire immediately
const results = useQueries({
  queries: [
    { queryKey: ["user", id], queryFn: () => fetchUser(id) },
    { queryKey: ["posts", id], queryFn: () => fetchPosts(id) },
  ],
});

// Dependent (intentional waterfall): posts wait for the user's teamId
const { data: user } = useQuery({ queryKey: ["user", id], queryFn: () => fetchUser(id) });
const { data: team } = useQuery({
  queryKey: ["team", user?.teamId],
  queryFn: () => fetchTeam(user!.teamId),
  enabled: !!user?.teamId,          // don't run until we have the id
});

// Prefetch on hover
<Link
  onMouseEnter={() =>
    queryClient.prefetchQuery({ queryKey: ["user", id], queryFn: () => fetchUser(id) })
  }
/>

Senior Engineer Perspective

Interviewers love drawing a network waterfall diagram and asking "how do you flatten this?" The senior move is distinguishing necessary waterfalls (real data dependency) from accidental ones (component structure), then attacking the accidental ones with parallel fetching, hoisting, route loaders, or server-side fetching. Naming that RSC and route loaders solve initial-load waterfalls structurally — not just per-query — signals current knowledge.

Q13. Pagination vs infinite queries — how do you implement each?

ROI: ★★★★☆ Frequency: High

Short Answer

Paginated lists show one page at a time (page 1, 2, 3); each page is its own query keyed by page number. The gotcha is the UI collapsing to a spinner between pages — fix it with placeholderData: keepPreviousData so the old page stays visible while the next loads. Infinite lists accumulate pages into one growing list ("load more" / infinite scroll); use useInfiniteQuery, which manages an array of pages and a getNextPageParam function that derives the next cursor from the last page.

Detailed Answer

Cursor vs offset. Offset pagination (?page=2) is simple but drifts when items are inserted/deleted between reads. Cursor pagination (?after=<id>) is stable under mutation and preferred for infinite feeds — getNextPageParam returns the cursor from the last page, or undefined when there's no more.

useInfiniteQuery gives you data.pages (array of page results), fetchNextPage, hasNextPage, and isFetchingNextPage. You typically flatten pages for rendering and trigger fetchNextPage from an IntersectionObserver sentinel at the bottom of the list.

Code Example

// Classic pagination — keep the current page visible while the next loads
const { data } = useQuery({
  queryKey: ["todos", page],
  queryFn: () => fetchTodos(page),
  placeholderData: keepPreviousData, // no spinner flash between pages
});

// Infinite (cursor-based)
const {
  data, fetchNextPage, hasNextPage, isFetchingNextPage,
} = useInfiniteQuery({
  queryKey: ["feed"],
  queryFn: ({ pageParam }) => fetchFeed({ cursor: pageParam }),
  initialPageParam: null,
  getNextPageParam: (lastPage) => lastPage.nextCursor ?? undefined, // undefined = end
});

const items = data?.pages.flatMap((p) => p.items) ?? [];

Senior Engineer Perspective

Two probes: "why keepPreviousData?" (avoid the jarring spinner-collapse and layout shift between pages) and "offset or cursor?" (cursor for stability under concurrent writes and for infinite scroll; offset only for small, static, jump-to-page tables). Mention windowing/virtualization (@tanstack/react-virtual) for very long infinite lists so the DOM doesn't grow unbounded — that's the detail that shows you've shipped one at scale.

Q14. How does Suspense for data fetching change the model?

ROI: ★★★★☆ Frequency: High

Short Answer

With Suspense, a component "suspends" while its data is loading by throwing a promise; the nearest <Suspense fallback> boundary shows the fallback until the promise resolves. This moves loading state out of the component — you write the success path only, no if (isLoading) branches — and lets you declare loading UI structurally with boundaries. Errors are caught by an error boundary. TanStack Query supports it via useSuspenseQuery; React 19 adds the use() hook to unwrap a promise directly.

Detailed Answer

The mental shift: instead of each component rendering its own spinner, you compose boundaries. A <Suspense> boundary catches loading; an error boundary catches failure. The child assumes data is present.

  • Co-located loading. Wrap sections of the tree so a slow widget shows its own fallback without blocking the rest. Nesting boundaries gives granular loading UI.
  • Streaming SSR / RSC. On the server, Suspense enables streaming: the shell renders immediately and slower data streams in as boundaries resolve. This is core to the Next.js App Router.
  • useSuspenseQuery returns data as always-defined (no undefined to guard), because the component only renders after data is ready. Beware: naively converting parallel useQuery calls to useSuspenseQuery can reintroduce waterfalls — use useSuspenseQueries to keep them parallel.
  • React 19 use() can unwrap a promise (often created on the server and passed to the client) inside render, suspending until it resolves — a lighter primitive than a full query library for some cases.

Code Example

// Boundary owns loading + error; child assumes data exists
<ErrorBoundary fallback={<ErrorBanner />}>
  <Suspense fallback={<Skeleton />}>
    <Profile id={id} />
  </Suspense>
</ErrorBoundary>

function Profile({ id }: { id: string }) {
  // data is guaranteed defined here — no isLoading branch
  const { data } = useSuspenseQuery({
    queryKey: ["user", id],
    queryFn: () => fetchUser(id),
  });
  return <h1>{data.name}</h1>;
}

// React 19 use() unwrapping a promise
function Comments({ promise }: { promise: Promise<Comment[]> }) {
  const comments = use(promise); // suspends until resolved
  return <List items={comments} />;
}

Senior Engineer Perspective

The trap interviewers set: "does Suspense make my requests parallel?" No — Suspense governs rendering, not fetch scheduling. If you fetch inside a child that only mounts after the parent's data resolves, you still have a waterfall; Suspense just changes where the spinner lives. Seniors pair Suspense with prefetching or hoisted/parallel queries and mention streaming SSR. Also flag that you never call use() conditionally in a way that breaks the promise's stability across renders.

Q16. How do you handle auth tokens and token refresh in a fetch layer?

ROI: ★★★★☆ Frequency: High

Short Answer

Centralize it in one HTTP client (an axios instance or a fetch wrapper) rather than sprinkling headers everywhere. A request interceptor attaches the access token; a response interceptor catches 401, refreshes the token once, and retries the failed request. The critical detail is a single-flight refresh: when many requests 401 at once, queue them behind one in-progress refresh instead of firing N concurrent refreshes. Store tokens carefully — httpOnly cookies are safest against XSS; if you must use JS-accessible storage, keep the access token short-lived.

Detailed Answer

  • One client. All requests go through a single module so auth, base URL, error normalization, and refresh live in one place. Query libraries call into this client from their queryFn/mutationFn.
  • Refresh flow. On a 401, call the refresh endpoint to exchange the refresh token for a new access token, update it, and replay the original request. If refresh itself fails, clear auth and redirect to login.
  • Single-flight / queuing. Hold a module-level promise for the in-progress refresh; concurrent 401s await the same promise, then retry. Without this you get a refresh stampede and possibly rotate refresh tokens against yourself.
  • Storage trade-offs. httpOnly, Secure, SameSite cookies are not readable by JS (mitigates XSS token theft) but require CSRF protection. localStorage is convenient but XSS-exposed. A common hybrid: refresh token in an httpOnly cookie, short-lived access token in memory.
  • Proactive refresh. Optionally refresh shortly before expiry (from the JWT exp) to avoid the 401-retry round trip on the critical path.

Code Example

const api = axios.create({ baseURL: "/api" });

// attach access token on every request
api.interceptors.request.use((config) => {
  const token = getAccessToken();
  if (token) config.headers.Authorization = `Bearer ${token}`;
  return config;
});

let refreshing: Promise<string> | null = null; // single-flight guard

api.interceptors.response.use(
  (res) => res,
  async (error) => {
    const original = error.config;
    if (error.response?.status === 401 && !original._retry) {
      original._retry = true;
      refreshing ??= refreshAccessToken().finally(() => { refreshing = null; });
      const newToken = await refreshing;          // concurrent 401s share this
      original.headers.Authorization = `Bearer ${newToken}`;
      return api(original);                        // replay original request
    }
    return Promise.reject(error);
  }
);

Senior Engineer Perspective

The make-or-break follow-up is "what happens when ten requests 401 simultaneously?" A junior refreshes ten times (and may invalidate the refresh token via rotation, logging the user out). A senior describes the single-flight promise that queues them behind one refresh. Expect a security tangent: articulate the httpOnly-cookie vs localStorage XSS/CSRF trade-off, the value of short-lived access tokens plus rotating refresh tokens, and never logging or embedding tokens in query keys/URLs. Bonus: with cookie-based auth you set credentials: "include" and often skip the Authorization header entirely.

Q17. What is the QueryClient and QueryClientProvider, and which configuration options matter most in production?

ROI: ★★★★★ Frequency: Extremely High

Short Answer

The QueryClient is the actual cache — it holds every query and mutation, their state, subscribers, and timers. QueryClientProvider puts one instance on Context so every useQuery/useMutation in the tree can reach it. In production you almost always set defaultOptions.queries (a sane global staleTime, retry policy, refetchOnWindowFocus) so you are not repeating the same options on every call site.

Detailed Answer

Create exactly one QueryClient per app (per request, in SSR) — creating a new one on every render would wipe the cache and defeat the whole point. A common mistake is instantiating it inline in a component body without useState/module scope, causing a fresh cache on every re-render.

  • defaultOptions.queries — set a non-zero global staleTime (many teams default to 30s–1min instead of the library default of 0) so you don't refetch everything on every focus.
  • defaultOptions.mutations — a global onError (e.g. toast a generic message) so individual mutations only need to handle the cases they care about.
  • QueryCache / MutationCache global callbacks — passed to the QueryClient constructor, useful for centralized logging/telemetry across every query regardless of component.
  • One client per request in SSR — server-rendering must create a new QueryClient per incoming request (inside the request handler), never a module-level singleton, or you leak data between users.

Code Example

const queryClient = new QueryClient({
  defaultOptions: {
    queries: {
      staleTime: 60_000,
      retry: 2,
      refetchOnWindowFocus: false, // opt out globally, opt in per-query if needed
    },
    mutations: {
      onError: (error) => toast.error(getErrorMessage(error)),
    },
  },
});

function App() {
  return (
    <QueryClientProvider client={queryClient}>
      <Routes />
    </QueryClientProvider>
  );
}

Senior Engineer Perspective

Interviewers probe whether you understand the client is a singleton with real memory and timers — "what happens if you create a new QueryClient inside your component function without memoizing it?" (answer: cache resets every render, every query looks "loading" forever in effect). For SSR/Next.js, know that the client must be request-scoped, typically created with useState(() => new QueryClient()) on the client and freshly per-request on the server.

Q18. What are query key factories and why do teams adopt them?

ROI: ★★★★☆ Frequency: High

Short Answer

A query key factory is a small module of functions that build query keys consistently — todoKeys.all, todoKeys.lists(), todoKeys.list(filters), todoKeys.detail(id) — instead of hand-typing arrays like ["todos", filters] at every call site. It eliminates typos that silently create a second, disconnected cache entry, and it makes broad invalidation (invalidateQueries({ queryKey: todoKeys.all })) safe and discoverable.

Detailed Answer

Query keys are matched by structural equality and prefix, so ["todos"] matches (invalidates) ["todos", { status: "done" }]. That fuzzy-matching is powerful but fragile if keys are typed freehand across a large codebase — one typo ("todo" vs "todos") creates a silently orphaned cache entry that never gets invalidated. A factory gives you:

  • Single source of truth for the shape of every key, so useQuery call sites and invalidateQueries call sites can never drift apart.
  • A hierarchy — all → lists()/details() → list(filters)/detail(id) — so you can invalidate at exactly the right granularity (every todo query, just list queries, just one detail).
  • Type safety — TypeScript can infer the exact tuple shape, catching a caller who passes the wrong filter shape.

Code Example

export const todoKeys = {
  all: ["todos"] as const,
  lists: () => [...todoKeys.all, "list"] as const,
  list: (filters: TodoFilters) => [...todoKeys.lists(), filters] as const,
  details: () => [...todoKeys.all, "detail"] as const,
  detail: (id: string) => [...todoKeys.details(), id] as const,
};

useQuery({ queryKey: todoKeys.list({ status: "done" }), queryFn: () => fetchTodos({ status: "done" }) });
useQuery({ queryKey: todoKeys.detail(id), queryFn: () => fetchTodo(id) });

// Invalidate everything under "todos" after a mutation that could affect any of them:
queryClient.invalidateQueries({ queryKey: todoKeys.all });
// Invalidate only list queries, leaving cached detail views alone:
queryClient.invalidateQueries({ queryKey: todoKeys.lists() });

Senior Engineer Perspective

A strong signal is explaining the invalidation granularity trade-off unprompted: invalidating too broadly (todoKeys.all) causes extra refetches; too narrowly and you miss stale views. Factories make this a deliberate choice per mutation instead of guesswork. Mention that this pattern scales to any resource (users, orders, comments) and is usually colocated with the feature's API module.

Q20. How does the "select" option work, and when should you use it?

ROI: ★★★★☆ Frequency: High

Short Answer

select transforms the cached data on the way out to the component, without altering what's actually stored in the cache. It's used for deriving a subset or reshaped view (e.g. just the count, or a sorted slice) so the component only re-renders when that derived value changes, not on every change to the raw cached object — a targeted performance and ergonomics win.

Detailed Answer

Without select, every component subscribing to a query re-renders whenever the query's data reference changes, even if all it reads is data.length. With select, TanStack Query memoizes the transform and only notifies the component if the selected value is structurally different, using its own shallow-equality check on the selector's output.

  • Shared query, different views. One ["todos"] query can back a component that needs the full list and another that only needs todos.filter(t => !t.done).length — each uses its own select, both share the same underlying fetch/cache.
  • Keep the selector stable. Define it outside render (or wrap in useCallback) so identity doesn't change every render and defeat the memoization.
  • Not a replacement for the query key. select only reshapes data already fetched under a given key — it does not change what's requested from the server.

Code Example

function usePendingCount() {
  return useQuery({
    queryKey: todoKeys.list({}),
    queryFn: fetchAllTodos,
    select: (todos) => todos.filter((t) => !t.done).length, // re-renders only when this number changes
  });
}

function IncompleteBadge() {
  const { data: count } = usePendingCount();
  return <Badge>{count}</Badge>;
}

Senior Engineer Perspective

The follow-up trap: "does select reduce network requests?" No — it only reduces re-renders on the client by narrowing what a component subscribes to; the underlying fetch is identical for every consumer of the key. Mention wrapping selectors in a custom hook (as above) so the transform logic is reused and testable in isolation from any component.

Q22. How do you share or derive query state across components without prop drilling?

ROI: ★★★☆☆ Frequency: Medium

Short Answer

You don't need Context or a global store for server data — every component that calls useQuery with the same key automatically subscribes to the same cache entry. State is "shared" implicitly through the key, not by threading props. For derived values, wrap the query in a custom hook (useUser(id), usePendingCount()) and call that hook from any component that needs it.

Detailed Answer

This is one of the biggest mental-model shifts from Redux-style thinking: you never need to lift server state up and pass it down, because the query cache is the shared store, addressed by key rather than by component tree position.

  • Custom hooks as the API. Wrap each query/mutation in a named hook (useTodo(id)) so call sites don't repeat the key/fetcher, and so you have one place to change caching options later.
  • No provider needed per feature. Two sibling components anywhere in the tree calling useTodo(5) get the exact same data, loading state, and refetch function — no Context required beyond the single top-level QueryClientProvider.
  • When you DO need Context. For truly cross-cutting client state derived from server data (e.g. "currently selected row," a UI-only concept), a small Context or Zustand store is still appropriate — the split is: server data via query hooks, UI state via Context/store.

Code Example

function useTodo(id: string) {
  return useQuery({ queryKey: todoKeys.detail(id), queryFn: () => fetchTodo(id) });
}

// Both components share one cache entry and one network request, no prop drilling:
function TodoTitle({ id }: { id: string }) {
  const { data } = useTodo(id);
  return <h2>{data?.title}</h2>;
}
function TodoBadge({ id }: { id: string }) {
  const { data } = useTodo(id);
  return data?.done ? <Badge>Done</Badge> : null;
}

Senior Engineer Perspective

Watch for candidates who reflexively reach for Redux/Context to "share" server data across the tree — that's the anti-pattern this question is designed to surface. The strong answer names the query cache itself as the sharing mechanism and reserves Context for genuinely local UI state.

Q23. How does query cancellation work internally, and what is queryClient.cancelQueries used for?

ROI: ★★★☆☆ Frequency: Medium

Short Answer

Every queryFn receives an AbortSignal that TanStack Query fires when the query is cancelled — because it's superseded by a refetch, unmounted with no other observers, or explicitly cancelled. queryClient.cancelQueries({ queryKey }) imperatively cancels any in-flight fetch for matching keys; it's most commonly used inside onMutate of an optimistic update, so a resolving background refetch can't overwrite your optimistic write.

Detailed Answer

If your queryFn forwards the signal to fetch (or an axios signal option), cancellation actually aborts the network request; if you ignore the signal, TanStack Query still stops listening for the result (so it won't update the cache with a stale response) even though the request keeps running on the wire.

  • Automatic cancellation happens when a query's key changes before the previous fetch resolves, or when the last observer unmounts (configurable via the query's own logic — quick remounts within the same tick don't cancel).
  • Manual cancellation via cancelQueries is the correct first step of every optimistic update: without it, a refetch that was already in flight when the mutation started can resolve after your optimistic setQueryData and clobber it with pre-mutation data.
  • Return value — cancelQueries returns a promise that resolves once cancellation is applied; awaiting it before snapshotting the cache avoids a narrow race.

Code Example

useQuery({
  queryKey: ["report", id],
  queryFn: ({ signal }) => fetch(`/api/reports/${id}`, { signal }).then((r) => r.json()),
});

useMutation({
  mutationFn: updateTodo,
  onMutate: async (updated) => {
    await queryClient.cancelQueries({ queryKey: todoKeys.detail(updated.id) }); // stop any in-flight refetch first
    const previous = queryClient.getQueryData(todoKeys.detail(updated.id));
    queryClient.setQueryData(todoKeys.detail(updated.id), updated);
    return { previous };
  },
});

Senior Engineer Perspective

The strongest answer connects cancellation to a concrete bug: "without cancelQueries in onMutate, I've seen an optimistic update flicker back to stale data because a focus-triggered background refetch that started a moment earlier resolved right after the optimistic write." That's the exact race this API exists to prevent.

  initialData: () => queryClient.getQueryData<Todo[]>(todoKeys.lists())?.find((t) => t.id === id),
  initialDataUpdatedAt: () => queryClient.getQueryState(todoKeys.lists())?.dataUpdatedAt,
});

// placeholderData: show last page's data while the next page is genuinely being fetched
useQuery({
  queryKey: ["todos", page],
  queryFn: () => fetchTodos(page),
  placeholderData: keepPreviousData, // display-only, still triggers a real fetch for `page`
});

Senior Engineer Perspective

Interviewers check whether you know initialData can suppress a needed fetch if used carelessly — pairing it with initialDataUpdatedAt lets the library correctly judge freshness against your real staleTime instead of always treating it as brand-new. Confusing the two options is a common source of "why isn't my data refreshing" bugs.

SECTION 6 - SWR DEEP DIVE

Q25. Explain SWR's stale-while-revalidate model in detail — what actually happens step by step?

ROI: ★★★★☆ Frequency: High

Short Answer

"Stale-while-revalidate" is an HTTP caching strategy SWR applies client-side: (1) if a cache entry exists for the key, return it synchronously — instant, possibly stale; (2) simultaneously fire a revalidation request in the background; (3) when it resolves, update the cache and re-render subscribers with fresh data. The user never waits on a spinner for data they've seen before — they see something immediately, then it corrects itself.

Detailed Answer

Walking through a concrete sequence for useSWR("/api/user", fetcher):

  1. First mount, no cache entry: data is undefined, isLoading is true, the fetcher runs.
  2. Fetcher resolves: data is written to SWR's global cache, keyed by the key string (or the result of a key function); every hook using that key re-renders with the new data.
  3. Component unmounts and remounts later (e.g. tab revisited): the cache entry is returned instantly (no loading flash), and — if a revalidation trigger fires (focus, reconnect, interval, or manual) — a fresh request goes out in the background.
  4. If the background fetch returns different data, subscribers re-render again; if it errors, the previously good cached data is generally preserved while error is also set (configurable).

This is functionally the same idea TanStack Query implements, just under a different name and a lighter API surface — the key mental model (serve stale instantly, reconcile in the background) is shared across both libraries.

Code Example

import useSWR from "swr";
const fetcher = (url: string) => fetch(url).then((r) => r.json());

function Profile() {
  const { data, error, isLoading } = useSWR("/api/user", fetcher);
  // First visit: isLoading true, then data populates.
  // Later visits within the same session: data appears instantly from cache,
  // then silently updates if focus/reconnect/interval triggers a revalidation.
  if (isLoading) return <Skeleton />;
  if (error) return <ErrorBanner />;
  return <h1>{data.name}</h1>;
}

Senior Engineer Perspective

Interviewers want the words "instant stale data, then background reconciliation" — not just "it caches things." Bonus: note SWR's cache is a simple key→value map (a Map by default, swappable), much less structured than TanStack Query's query/observer model, which is exactly why SWR's API surface is smaller.

Q26. How do you write custom fetchers in SWR, including auth headers and error shaping?

ROI: ★★★☆☆ Frequency: Medium

Short Answer

SWR is fetcher-agnostic — the second argument to useSWR is just a function (key) => Promise<T>. You typically write one shared fetcher that attaches auth headers, checks res.ok, and throws a rich Error object (with a status/info attached) on failure, since SWR treats any thrown error as the query's error state.

Detailed Answer

fetch does not throw on 4xx/5xx — it resolves with ok: false — so a shared fetcher must check this explicitly and throw, or SWR will treat a 404 page body as "successful data."

  • Attach context to the thrown error (status code, parsed error body) so components can branch on error.status without re-parsing the response.
  • Provide it once via SWRConfig so individual useSWR calls don't repeat it — pass just the key.
  • Array keys for multi-argument fetchers — when a fetch needs more than a URL (e.g. an id and a query param), pass a key as [url, params] and destructure it in the fetcher; SWR uses deep-equality on array keys for cache identity, same idea as TanStack Query's array keys.

Code Example

async function fetcher(url: string) {
  const res = await fetch(url, {
    headers: { Authorization: `Bearer ${getAccessToken()}` },
  });
  if (!res.ok) {
    const info = await res.json().catch(() => ({}));
    const error = new Error("Request failed") as Error & { status?: number; info?: unknown };
    error.status = res.status;
    error.info = info;
    throw error; // SWR surfaces this as `error`
  }
  return res.json();
}

// Provide once globally:
<SWRConfig value={{ fetcher }}>
  <App />
</SWRConfig>

// Multi-argument key:
useSWR(["/api/search", { q: query, page }], ([url, params]) =>
  fetch(`${url}?q=${params.q}&page=${params.page}`).then((r) => r.json())
);

Senior Engineer Perspective

The trap: candidates forget fetch doesn't throw on HTTP error status and are surprised when a 500 renders as "successful" empty data. Naming this explicitly, and showing the array-key pattern for multi-argument fetchers, both signal real hands-on SWR experience rather than a five-minute skim of the README.

Q28. How does SWRConfig compare to TanStack Query's QueryClient defaultOptions?

Q29. How do you do conditional / dependent fetching in SWR?

ROI: ★★★★☆ Frequency: High

Short Answer

Pass null, undefined, or false as the key (or throw inside a function key) to tell SWR "don't fetch yet." SWR treats a falsy key as "this query is disabled" — no request fires, and the hook resolves later once the key becomes truthy, exactly mirroring TanStack Query's enabled option but expressed through the key itself rather than a separate flag.

Detailed Answer

Two idiomatic ways to express "wait until I have what I need":

  • Falsy key. useSWR(userId ? `/api/users/${userId}` : null, fetcher) — simplest and most common.
  • Function key that throws/returns falsy. useSWR(() => `/api/orders/${user.id}`, fetcher) — if accessing user.id throws because user is undefined, SWR catches it and treats the query as not ready. This is handy for chained dependent data without an explicit ternary at every level.

Both approaches naturally express dependent-query chains: fetch the user, and only once you have it, key the next query off a field of it.

Code Example

function useOrders(userId: string | undefined) {
  return useSWR(userId ? `/api/orders?user=${userId}` : null, fetcher);
}

// Function-key form for a deeper dependency chain
function useTeamStats(user: User | undefined) {
  return useSWR(
    () => `/api/teams/${user!.teamId}/stats`, // throws if user is undefined -> treated as "not ready"
    fetcher
  );
}

Senior Engineer Perspective

Interviewers compare this directly to TanStack Query's enabled flag — the strong answer is recognizing they solve the identical problem with a different ergonomic (falsy key vs boolean option) and picking whichever the codebase already uses consistently, rather than mixing both idioms.

Q30. useSWRMutation vs the classic mutate() approach — when do you use each?

ROI: ★★★☆☆ Frequency: Medium

Short Answer

The bound mutate returned by useSWR (or the global mutate import) is primarily for revalidating or manually writing the cache for an existing query — it doesn't manage a separate "in-flight write" lifecycle. useSWRMutation is a dedicated hook for triggering a remote mutation on demand (not automatically on render) with its own trigger, isMutating, data, and error — closer to TanStack Query's useMutation.

Detailed Answer

  • mutate(key, updater, options) — revalidate a query (refetch and update the cache) or write a value into the cache directly, optionally with optimisticData/rollbackOnError for optimistic UI. It doesn't itself perform the "send a POST" side effect — you do that yourself and then call mutate to sync the cache.
  • useSWRMutation(key, fetcher) — pairs the actual network call with the cache update in one hook: it exposes trigger(arg) to fire the request only when called (unlike useSWR, which fetches on render), tracks isMutating, and can auto-populate the corresponding useSWR cache entry on success via its own populateCache/revalidate options.
  • When to reach for which. Simple "refetch this after a write I did elsewhere" → plain mutate. A full write flow with pending/error state and optimistic data tied to the mutation itself → useSWRMutation.

Code Example

// Classic: perform the write yourself, then sync the cache
async function toggleTodo(id: string) {
  await fetch(`/api/todos/${id}/toggle`, { method: "POST" });
  mutate("/api/todos"); // revalidate the list
}

// useSWRMutation: the hook owns the write + isMutating state
function useCreateTodo() {
  return useSWRMutation("/api/todos", async (url, { arg }: { arg: { title: string } }) => {
    const res = await fetch(url, { method: "POST", body: JSON.stringify(arg) });
    return res.json();
  });
}

function AddTodo() {
  const { trigger, isMutating } = useCreateTodo();
  return (
    <button disabled={isMutating} onClick={() => trigger({ title: "New" })}>
      {isMutating ? "Saving..." : "Add"}
    </button>
  );
}

Senior Engineer Perspective

Point out that useSWR fetches eagerly on render while useSWRMutation only fires on trigger() — conflating the two (calling useSWR for a POST-on-click flow) is a beginner mistake that either fires requests too early or requires awkward manual gating.

Q31. How does SWR handle request deduplication internally, and what does dedupingInterval control?

ROI: ★★★☆☆ Frequency: Medium

Short Answer

SWR keeps a map of in-flight promises keyed by the same cache key used for data. If a second useSWR call (or trigger, like focus) requests the same key while a request for it is already in flight, SWR returns the existing promise instead of firing a new network call — every subscriber gets the same resolved result. dedupingInterval extends this window after a request completes too, so rapid repeat triggers within that many milliseconds are skipped entirely, not just concurrent ones.

Detailed Answer

  • Concurrent dedup. Ten components mounting useSWR("/api/config", fetcher) in the same tick produce exactly one network request; all ten hooks resolve from that single promise.
  • Time-window dedup. Even after the first request finishes, any revalidation trigger (focus, reconnect, remount) for the same key within dedupingInterval (default 2000ms) is skipped — this is what prevents a "rapid alt-tabbing" focus storm from firing a new request on every tab switch.
  • Not the same as caching duration. Deduping only suppresses new requests in a short window; it says nothing about how long data is considered acceptable to show without any revalidation at all (SWR doesn't have a direct staleTime equivalent — it leans on the revalidation triggers plus dedupingInterval instead).

Code Example

// Both components mount in the same render pass — one network request, shared result
function Header() {
  const { data } = useSWR("/api/config", fetcher);
  return <nav>{data?.appName}</nav>;
}
function Footer() {
  const { data } = useSWR("/api/config", fetcher); // deduped against Header's request
  return <footer>{data?.appName}</footer>;
}

useSWR("/api/config", fetcher, { dedupingInterval: 10_000 }); // suppress repeat fetches for 10s

Senior Engineer Perspective

Contrast this with TanStack Query for a complete answer: TanStack Query dedupes concurrent requests the same way, but expresses "how long is this acceptable without revalidating" via an explicit staleTime, whereas SWR leans more heavily on dedupingInterval plus toggling individual revalidation triggers. Knowing there's no exact one-to-one option mapping — and why — is the senior-level nuance here.

SECTION 7 - OPTIMISTIC UPDATES

Q32. Walk through the full onMutate / onError / onSettled lifecycle in detail, including TypeScript context typing.

ROI: ★★★★★ Frequency: Extremely High

Short Answer

onMutate runs synchronously before the mutation fires, is where you cancel conflicting refetches, snapshot the current cache, and write the optimistic value; whatever it returns becomes the context argument of both onError and onSettled. onError receives (error, variables, context) and rolls back using that snapshot. onSettled receives (data, error, variables, context) and runs regardless of outcome — the natural place to reconcile with the server via invalidateQueries.

Detailed Answer

Typing the context correctly prevents a whole class of "property does not exist on unknown" errors and, more importantly, forces you to think about what actually needs to survive a rollback.

  • Generic parameters. useMutation<TData, TError, TVariables, TContext> — supplying TContext explicitly gives you typed context in every callback.
  • onMutate is synchronous-first, async-capable. It can be async (e.g. to await cancelQueries) — the mutation itself waits for it to settle before actually calling mutationFn... in practice both can run concurrently depending on version, so don't rely on strict ordering beyond "onMutate starts before the network call."
  • onSuccess vs onSettled. onSuccess only fires on a successful mutation (good for toasts); onSettled fires on both success and failure, so it's the right hook for "always reconcile with the server" logic that must run either way.

Code Example

type Context = { previous?: Todo[] };

useMutation<Todo, Error, Todo, Context>({
  mutationFn: (todo) => api.updateTodo(todo),

  onMutate: async (newTodo): Promise<Context> => {
    await queryClient.cancelQueries({ queryKey: todoKeys.lists() });
    const previous = queryClient.getQueryData<Todo[]>(todoKeys.lists());
    queryClient.setQueryData<Todo[]>(todoKeys.lists(), (old = []) =>
      old.map((t) => (t.id === newTodo.id ? newTodo : t))
    );
    return { previous }; // typed context
  },

  onError: (_err, _newTodo, context) => {
    if (context?.previous) queryClient.setQueryData(todoKeys.lists(), context.previous);
  },

  onSettled: () => {
    queryClient.invalidateQueries({ queryKey: todoKeys.lists() }); // reconcile regardless of outcome
  },
});

Senior Engineer Perspective

Interviewers check whether you actually type the context or leave it as implicit any/unknown — sloppy typing here is a real-world source of "rollback silently did nothing" bugs when a refactor renames a snapshot field. Also mention that onSettled is the one guaranteed-to-run hook, which is why reconciliation belongs there, not in onSuccess.

Q33. How do you do optimistic updates for a list (add/remove/reorder) vs a single entity?

ROI: ★★★★☆ Frequency: High

Short Answer

A single-entity optimistic update replaces one cached object. A list update must produce a new array (never mutate in place) using map for edits, filter for removal, and array reconstruction (splice-free reordering) for reordering — plus a temporary client-generated id for optimistic creates, which you must reconcile once the server returns the real id.

Detailed Answer

  • Add. Generate a temporary id (a UUID or a negative counter) so the optimistic item is distinguishable, insert it into the cached array, then in onSuccess replace the temp item with the server's real one (matching by the temp id you stashed in context/variables) rather than blindly invalidating (which would briefly show a duplicate or a flash of removal).
  • Remove. Filter the item out immediately; snapshot the full previous array in onMutate so a failed delete restores it exactly, including its original position.
  • Reorder. Compute the new order client-side, write the reordered array to the cache immediately, and send the new order (or a single moved-item delta) to the server; on failure restore the snapshot so the list "snaps back."

Code Example

useMutation({
  mutationFn: (title: string) => api.createTodo(title),

  onMutate: async (title) => {
    await queryClient.cancelQueries({ queryKey: todoKeys.lists() });
    const previous = queryClient.getQueryData<Todo[]>(todoKeys.lists()) ?? [];
    const tempId = `temp-${crypto.randomUUID()}`;
    queryClient.setQueryData<Todo[]>(todoKeys.lists(), [...previous, { id: tempId, title, done: false }]);
    return { previous, tempId };
  },

  onSuccess: (created, _title, context) => {
    // swap the temp item for the server's real one, avoiding a duplicate/flash
    queryClient.setQueryData<Todo[]>(todoKeys.lists(), (old = []) =>
      old.map((t) => (t.id === context.tempId ? created : t))
    );
  },

  onError: (_err, _title, context) => {
    if (context?.previous) queryClient.setQueryData(todoKeys.lists(), context.previous);
  },
});

Senior Engineer Perspective

The trap is naively invalidating after an optimistic add instead of reconciling the temp id — that causes a visible flicker (temp item disappears, then the real one appears a beat later). Handling the temp-id swap in onSuccess is the detail that distinguishes someone who's actually shipped this from someone reciting the four-step recipe.

Q34. How do you implement optimistic updates in SWR (optimisticData / rollbackOnError)?

ROI: ★★★☆☆ Frequency: Medium

Short Answer

SWR's mutate(key, updateFnOrData, options) takes optimisticData (or a function computing it from the current cache), rollbackOnError (default true — reverts automatically on failure), and populateCache/revalidate to control what happens once the real request settles. It's functionally the same recipe as TanStack Query's onMutate/onError, just packaged as options on one call instead of separate lifecycle callbacks.

Detailed Answer

  • optimisticData — the value (or updater function) to show immediately, written to the cache before the promise resolves.
  • rollbackOnError — true by default; SWR automatically restores the pre-optimistic value if the promise passed to mutate rejects. Can be a function to roll back only for certain errors.
  • populateCache — controls whether the mutation's resolved value replaces the cache entry (true, or a function to merge it) once the real request finishes, versus leaving the cache alone and letting a separate revalidation handle it.
  • revalidate — whether to trigger a background refetch after the mutation settles, to reconcile any server-side fields the optimistic guess couldn't know.

Code Example

async function toggleTodo(todo: Todo) {
  const updated = { ...todo, done: !todo.done };
  await mutate(
    "/api/todos",
    async (current: Todo[] = []) => {
      const res = await fetch(`/api/todos/${todo.id}`, {
        method: "PATCH",
        body: JSON.stringify({ done: updated.done }),
      });
      if (!res.ok) throw new Error("Failed to toggle");
      return current.map((t) => (t.id === todo.id ? updated : t));
    },
    {
      optimisticData: (current: Todo[] = []) =>
        current.map((t) => (t.id === todo.id ? updated : t)),
      rollbackOnError: true,   // auto-restore previous list if the promise rejects
      populateCache: true,     // write the resolved value into the cache
      revalidate: false,       // trust the resolved value; skip an extra refetch
    }
  );
}

Senior Engineer Perspective

The direct comparison interviewers want: TanStack Query spreads the recipe across three callbacks (onMutate/onError/onSettled) tied to useMutation; SWR bundles the same four concerns as options to a single mutate call. Both require you to explicitly opt into rollback and explicitly decide whether to trust the optimistic guess or re-verify with the server afterward.

Q35. What race conditions can occur with optimistic updates, and how do you guard against them?

ROI: ★★★★☆ Frequency: High

Short Answer

The classic race: a background refetch that was already in flight when you started the optimistic update resolves after your optimistic write and overwrites it with stale pre-mutation data. A second race: firing the same optimistic mutation twice in quick succession (double-click) stacks two optimistic writes and two rollback snapshots, and an out-of-order rollback can restore the wrong intermediate state. Guard with cancelQueries before writing, and disable the trigger (button) while a mutation is pending.

Detailed Answer

  • Refetch-clobbers-optimism. Solved by always calling await queryClient.cancelQueries({ queryKey }) as the first line of onMutate, so any in-flight fetch for that key is aborted before you snapshot and write.
  • Rapid repeated mutations on the same entity. If a user double-clicks "like," two mutations run concurrently, each snapshotting a slightly different "previous" state. If the first fails and rolls back after the second has already applied its own optimistic write, the rollback can undo the second mutation's optimistic change too. Mitigate by disabling the control while isPending, or by keying mutations so a second call cancels/replaces the first rather than racing it.
  • Stale closures in callbacks. Capturing an outdated variable (e.g. an old array reference) inside onMutate's updater instead of using the function form of setQueryData can silently drop a concurrent optimistic change from a different mutation. Always use the updater-function form ((old) => ...) rather than reading a variable captured earlier.

Code Example

useMutation({
  mutationFn: likePost,
  onMutate: async (postId) => {
    await queryClient.cancelQueries({ queryKey: ["post", postId] }); // guard #1
    const previous = queryClient.getQueryData(["post", postId]);
    queryClient.setQueryData(["post", postId], (old: Post) => ({ ...old, liked: true, likes: old.likes + 1 }));
    return { previous };
  },
  onError: (_e, postId, ctx) => queryClient.setQueryData(["post", postId], ctx?.previous),
});

// Guard #2 — disable the control while pending, don't rely purely on the cache race guard
<button disabled={mutation.isPending} onClick={() => mutation.mutate(postId)}>Like</button>

Senior Engineer Perspective

Naming cancelQueries as the fix for the refetch race is table stakes; naming the double-submission race and its UI-level mitigation (disable while pending) is the deeper answer that shows you've actually debugged this in production, not just read the four-step recipe.

Q36. How do you show optimistic UI without touching the cache at all (the mutation.variables pattern)?

ROI: ★★★☆☆ Frequency: Medium

Short Answer

Instead of writing to the query cache in onMutate, you read mutation.variables (or mutation.isPending) directly in the component while the mutation is in flight, and render the "optimistic" version purely in the UI layer. Once the mutation settles, you invalidate/refetch and the temporary UI-only state disappears in favor of real cached data. This avoids ever writing a value to the cache that might be wrong.

Detailed Answer

This is a lighter-weight alternative to the full cancel/snapshot/rollback recipe, appropriate when the optimistic change is simple and localized to one component render rather than needing to appear consistently across every consumer of the cache.

  • No cache mutation, no rollback bookkeeping. Because nothing was written to the shared cache, there's nothing to roll back — on error you simply stop rendering the optimistic branch and show an error state instead.
  • Scope. It only affects the component that reads mutation.variables; if three components need the optimistic value simultaneously, the full cache-mutation approach is a better fit since it updates the one shared source every consumer reads from.
  • Multiple concurrent mutations. If you need to render several in-flight optimistic items at once (e.g. several new comments being submitted concurrently), use useMutationState to read all mutations matching a mutationKey and render each by its variables.

Code Example

function AddComment({ postId }: { postId: string }) {
  const mutation = useMutation({
    mutationKey: ["addComment", postId],
    mutationFn: (text: string) => api.addComment(postId, text),
    onSettled: () => queryClient.invalidateQueries({ queryKey: ["comments", postId] }),
  });

  return (
    <>
      <CommentList postId={postId} />
      {mutation.isPending && (
        <Comment text={mutation.variables} pending />   // rendered from variables, cache untouched
      )}
      <CommentForm onSubmit={(text) => mutation.mutate(text)} />
    </>
  );
}

Senior Engineer Perspective

This pattern is newer and less universally known than the cache-write recipe, so naming it demonstrates you've kept up with v5. The trade-off to articulate: it's simpler and avoids rollback bugs, but it's local to the rendering component rather than globally consistent across every place the data appears — pick based on how many places need to see the optimistic state simultaneously.

Q37. How do you show optimistic updates across multiple related queries at once?

ROI: ★★★★☆ Frequency: High

Short Answer

When one write logically affects several cached queries (e.g. marking a todo done should update both the detail view and every list/filtered view containing it), snapshot and update each affected query in onMutate, and roll each one back individually in onError. queryClient.setQueriesData lets you update every query matching a key prefix or predicate in one call instead of enumerating them by hand.

Detailed Answer

React Query has no automatic cross-query normalization (unlike Apollo's normalized cache) — you are responsible for knowing which queries need to change and updating each. The practical approach:

  • Enumerate affected keys explicitly in the mutation's logic (detail view, "all" list, any filtered list the entity could appear in) rather than guessing at invalidation time.
  • setQueriesData({ queryKey }, updater) applies an updater function to every currently cached query whose key matches the given prefix/predicate — much less error-prone than looping over getQueryCache().findAll() yourself.
  • Snapshot per query. Store an array/map of { queryKey, data } snapshots in context so onError can restore each one precisely, not just one.

Code Example

useMutation({
  mutationFn: (todo: Todo) => api.updateTodo(todo),

  onMutate: async (updated) => {
    await queryClient.cancelQueries({ queryKey: todoKeys.all });

    // snapshot every cached todos query (list, filtered lists, detail) before touching any
    const snapshots = queryClient.getQueriesData<Todo[] | Todo>({ queryKey: todoKeys.all });

    queryClient.setQueriesData<Todo[]>({ queryKey: todoKeys.lists() }, (old) =>
      old?.map((t) => (t.id === updated.id ? updated : t))
    );
    queryClient.setQueryData(todoKeys.detail(updated.id), updated);

    return { snapshots };
  },

  onError: (_err, _updated, context) => {
    context?.snapshots.forEach(([queryKey, data]) => queryClient.setQueryData(queryKey, data));
  },

  onSettled: () => queryClient.invalidateQueries({ queryKey: todoKeys.all }),
});

Senior Engineer Perspective

Interviewers probe whether you'll reach for setQueriesData or hand-loop every query — the former is what "knowing the library well" looks like. Also flag the honest limitation: without a normalized cache, this enumeration is manual and can drift as new views are added, which is a real argument some teams make for a normalized client like Apollo when entities appear in many disparate views.

Q38. What's the risk of optimistic updates for non-idempotent operations, and how do you mitigate it?

ROI: ★★★☆☆ Frequency: Medium

Short Answer

Optimism assumes the write will very likely succeed exactly as predicted. For a non-idempotent operation — "charge this card," "send this email," "decrement this limited-stock counter" — showing a false success (or letting a retry fire the side effect twice) can mislead the user or actually duplicate a real-world effect. Mitigate by not making these optimistic at all, or by using an idempotency key so a retried request is safely deduplicated server-side even if the client can't prevent a double-submit.

Detailed Answer

  • Reserve optimism for low-stakes, easily-reversible, high-success-rate writes — likes, checkbox toggles, drag-reorder. These fail rarely and a wrong guess costs nothing but a visual flicker.
  • Avoid optimism for payments, irreversible deletes, or anything with real-world side effects — show a genuine pending/spinner state and wait for server confirmation instead of guessing.
  • Idempotency keys. For mutations that must never be retried into duplicate effects, generate a client-side idempotency key (a UUID) per logical action and send it with the request; the server recognizes a repeat key and returns the original result instead of re-executing. This protects you even if retries or double-clicks happen despite UI-level guards.
  • Disable retry for mutations by default (TanStack Query already does this) — never blindly retry a non-idempotent POST.

Code Example

// High-stakes write: no optimism, explicit pending state, idempotency key to survive a retry/double-click
function useChargeCard() {
  return useMutation({
    mutationFn: ({ amount }: { amount: number }) =>
      fetch("/api/charge", {
        method: "POST",
        headers: { "Idempotency-Key": crypto.randomUUID() },
        body: JSON.stringify({ amount }),
      }).then((r) => r.json()),
    retry: false, // never auto-retry a payment
  });
}

Senior Engineer Perspective

This is as much a backend-collaboration question as a frontend one — the strongest answers mention that idempotency keys require server-side support (a dedupe table keyed by the header), and that the frontend's job is to generate the key once per logical user action and reuse it across retries of that same action, not generate a new one each retry.

Q39. How do you test optimistic update logic?

ROI: ★★★☆☆ Frequency: Medium

Short Answer

Render the component with a fresh QueryClient and a mocked network layer (MSW is the standard choice), pre-seed the cache with initial data, trigger the mutation, and assert two things: the UI updates immediately (before the mocked request resolves) to prove optimism happened, and — separately — that it rolls back correctly when the mock responds with an error.

Detailed Answer

  • Mock Service Worker (MSW) intercepts the actual fetch/axios calls at the network level, so your component and query hooks run unmodified — you're testing real integration between the mutation and the cache, not a mocked hook.
  • Assert the optimistic phase. Delay the mock response (or use MSW's manual response control) so you can assert the UI already shows the optimistic value before resolving it — this is what actually proves the optimism, as opposed to just testing the final settled state.
  • Assert the rollback phase. In a second test, mock an error response and assert the UI reverts to the original value after the mutation settles — this is the test most teams skip and where regressions hide.
  • Disable retries in tests. Set retry: false on the test's QueryClient defaults so a test that intentionally errors doesn't hang waiting through backoff delays.

Q40. Offset vs cursor pagination — deep technical comparison including database implications.

ROI: ★★★★★ Frequency: Extremely High

Short Answer

Offset pagination (?page=3&pageSize=20, or LIMIT 20 OFFSET 40) is simple and lets you jump to any page number, but it drifts under concurrent writes — inserting or deleting a row shifts every subsequent page — and gets slower on large offsets since the database must still scan and discard the skipped rows. Cursor pagination (?after=<opaque-id>, translating to WHERE id > ? ORDER BY id LIMIT 20) is stable under concurrent mutation and stays fast at any depth because it seeks directly via an index, but it can't jump to an arbitrary page number.

The cursor itself should be an opaque, stable, unique, monotonically ordered value — often a composite of a timestamp and id (to break ties when two rows share a timestamp) — never a raw row count, or you've just reinvented offset with extra steps.

Senior Engineer Perspective

The killer follow-up: "a user deletes item 5 while you're on offset page 2 — what happens?" Every item after it shifts up one position, so page 2 now shows what used to be on page 3's boundary, and the user can see a duplicate or miss an item entirely. Cursor pagination sidesteps this because each page is anchored to a real, stable key rather than a shifting numeric position. Mention that some APIs offer both — page-number for admin tables where jump-to-page matters, cursor for public feeds.

Q41. How do you implement bi-directional infinite scroll using both getNextPageParam and getPreviousPageParam?

Short Answer

You call fetchNextPage() and fetchPreviousPage() independently, and TanStack Query maintains data.pages in the correct prepend/append order along with separate hasNextPage/hasPreviousPage flags.

Detailed Answer

This is the shape a chat app or a "jump to today, scroll both ways" calendar feed needs: you start in the middle of the dataset (e.g. the most recent messages), then let the user scroll up for history and down for anything newer that arrives.

  • Initial page param. initialPageParam sets where you start (e.g. "latest"); the first fetch returns both a nextCursor (older) and a previousCursor (newer, likely empty at first if you started at "latest").
  • Independent fetch functions. fetchNextPage() appends onto data.pages; fetchPreviousPage() prepends to the start — both trigger the same queryFn with the appropriate direction's cursor.
  • Loading flags per direction. isFetchingNextPage and isFetchingPreviousPage let you show a spinner at the correct side of the list without conflating the two.

const {

Q42. How do you preserve scroll position when navigating away from and back to an infinite list?

ROI: ★★★★☆ Frequency: High

Short Answer

The cache alone doesn't save you — the browser resets scroll on remount by default, and if the list virtualizes (recycling DOM nodes) you lose the visual position entirely even with the same data. The fix has two parts: keep the query's data cached (long staleTime/gcTime, or don't unmount the list at all) so returning doesn't refetch from page one, and separately persist the actual scroll offset (or the id of the topmost visible item) and restore it on remount.

Detailed Answer

  • Keep the data. A high gcTime for the infinite query (or navigating with a router that keeps the component alive, e.g. via a layout route) means the already-fetched pages are still there when the user returns — no re-fetching from the first page and no losing pages 2–5 they had scrolled through.
  • Persist the scroll anchor. Store either the raw pixel offset or, more robustly, the id of the item at the top of the viewport, in session storage or router state, when the user navigates away; on remount, scroll to that offset or to that item's position once the list has re-rendered with cached data.
  • Virtualization complicates it further. Libraries like @tanstack/react-virtual need the anchor to be an index/id (not a raw pixel value) since row heights and the recycled DOM can differ between mounts — restore by scrolling the virtualizer to that index.

Code Example

// Persist the topmost visible item id on navigation-away
function useScrollRestoration(listRef: React.RefObject<HTMLElement>, key: string) {
  useEffect(() => {
    const el = listRef.current;
    return () => {
      if (el) sessionStorage.setItem(`scroll:${key}`, String(el.scrollTop));
    };
  }, [key]);

  useLayoutEffect(() => {
    const saved = sessionStorage.getItem(`scroll:${key}`);
    if (saved && listRef.current) listRef.current.scrollTop = Number(saved);
  }, [key]); // runs once data (cached, already present) has rendered
}

// Keep the infinite query's pages alive across navigation
useInfiniteQuery({
  queryKey: ["feed"],
  queryFn: fetchFeedPage,
  gcTime: 30 * 60 * 1000, // survive a round trip to a detail page and back
});

Senior Engineer Perspective

Interviewers use this to check whether you conflate "data is cached" with "the UI looks the same as before" — they are different problems solved by different mechanisms. The strongest answers name virtualization explicitly as the part that makes a naive pixel-offset restore unreliable, and propose anchoring to an item id/index instead.

Q43. How do you implement a "load more" button vs auto-infinite-scroll with IntersectionObserver?

ROI: ★★★★☆ Frequency: High

Short Answer

A "load more" button calls fetchNextPage() directly on click — simple, explicit, and accessible by default. Auto-infinite-scroll places an invisible sentinel element at the bottom of the list and uses an IntersectionObserver to call fetchNextPage() the moment it scrolls into view, so more content appears without an explicit action. Both use the exact same useInfiniteQuery underneath — the difference is purely the trigger.

Detailed Answer

  • Load-more button — easiest to implement, easiest to make accessible (a real, focusable, keyboard-activatable button), and gives users control over how much they load; well suited to data-heavy pages where unbounded auto-loading could hurt performance or cost.
  • IntersectionObserver sentinel — a near-zero-height div at (or slightly before) the bottom of the list; when it intersects the viewport, fire fetchNextPage(), guarded by hasNextPage && !isFetchingNextPage to avoid duplicate triggers. Set the observer's rootMargin to a positive value (e.g. "200px") to start loading slightly before the user hits bottom, hiding latency.
  • Accessibility trade-off. Pure auto-scroll can be disorienting for screen-reader and keyboard users (content appears with no explicit action, and focus/scroll position can jump); many production UIs offer a button as a fallback/progressive enhancement alongside the observer, or auto-load only after the user has already scrolled near the bottom manually.

Code Example

function InfiniteList() {
  const { data, fetchNextPage, hasNextPage, isFetchingNextPage } = useInfiniteQuery({
    queryKey: ["feed"],
    queryFn: fetchFeedPage,
    initialPageParam: null,
    getNextPageParam: (last) => last.nextCursor,
  });

  const sentinelRef = useRef<HTMLDivElement>(null);

  useEffect(() => {
    const el = sentinelRef.current;
    if (!el) return;
    const observer = new IntersectionObserver(
      ([entry]) => {
        if (entry.isIntersecting && hasNextPage && !isFetchingNextPage) fetchNextPage();
      },
      { rootMargin: "200px" } // start loading before the user reaches the very bottom
    );
    observer.observe(el);
    return () => observer.disconnect();
  }, [hasNextPage, isFetchingNextPage, fetchNextPage]);

  return (
    <>
      {data?.pages.map((page) => <Page key={page.cursor} page={page} />)}
      <div ref={sentinelRef} />
      {hasNextPage && (
        <button onClick={() => fetchNextPage()} disabled={isFetchingNextPage}>
          {isFetchingNextPage ? "Loading..." : "Load more"}
        </button>
      )}
    </>
  );
}

Senior Engineer Perspective

Mentioning the rootMargin pre-load trick and the accessibility trade-off separates a candidate who's copy-pasted an infinite-scroll tutorial from one who's shipped it. A good closing point: offering both (a visible button plus observer-driven auto-load) is a common production compromise that satisfies both power users and accessibility needs.

Q44. How do you handle infinite query cache invalidation when a new item is created that should appear on page 1?

ROI: ★★★☆☆ Frequency: Medium

Short Answer

Invalidating an infinite query by default refetches every already-loaded page (to keep the whole accumulated list consistent), which is often overkill and re-requests data the user already has. For "a new item was created and belongs at the top," it's usually cheaper and smoother to manually prepend it to the first page in the cache with setQueryData rather than invalidating and re-fetching N pages.

Detailed Answer

  • Default invalidation behavior. invalidateQueries on an infinite query's key marks the whole query (all its pages) stale; on next access it refetches starting from the first page param and only refetches subsequent pages if they're still being observed — but this can mean re-requesting several pages just to reflect one new row.
  • Manual prepend (preferred for "new item at the top"). Directly edit data.pages[0].items to unshift the new item via setQueryData's updater function, preserving every other page untouched — no extra network requests, and correct as long as your cursor logic tolerates the extra item (usually fine since cursors are typically by id/time, not by count).
  • Cap pages. If you prepend repeatedly, consider trimming with maxPages (see the related question) so the in-memory list doesn't grow unbounded from a long session.

Code Example

useMutation({
  mutationFn: (title: string) => api.createTodo(title),
  onSuccess: (created) => {
    queryClient.setQueryData(
      ["todos", "infinite"],
      (old: InfiniteData<{ items: Todo[]; nextCursor?: string }> | undefined) => {
        if (!old) return old;
        const [firstPage, ...rest] = old.pages;
        return {
          ...old,
          pages: [{ ...firstPage, items: [created, ...firstPage.items] }, ...rest],
        };
      }
    );
  },
});

Senior Engineer Perspective

The nuance interviewers want: understanding that invalidating an infinite query is more expensive than a regular query because it can refetch multiple pages, and that a targeted setQueryData prepend is usually the better trade-off for "one new item appeared" versus a full invalidate for "the underlying data changed in a way I can't easily patch by hand" (e.g. filters changed server-side).

Q45. How do you virtualize a long infinite list to keep DOM size bounded?

ROI: ★★★★☆ Frequency: High

Short Answer

Without virtualization, an infinite list that's grown to thousands of loaded items renders thousands of real DOM nodes, degrading scroll performance and memory. A virtualizer (@tanstack/react-virtual, react-window) renders only the handful of rows currently visible (plus a small overscan buffer), recycling DOM nodes as the user scrolls, while a spacer element fakes the full scrollable height.

Detailed Answer

  • Flatten pages, virtualize the flat list. Combine data.pages.flatMap(p => p.items) into one array and pass its length/estimated row height to the virtualizer; it tells you which index range is currently visible.
  • Trigger fetchNextPage from the virtualizer's visible range, not a separate DOM sentinel — check if the last virtual item's index is near the tail of the flattened array and fire fetchNextPage() if so.
  • Variable row heights. If rows aren't fixed height, use a measuring variant (measureElement in @tanstack/react-virtual) so the virtualizer's height estimates self-correct as real rows render.
  • Scroll restoration gets harder with virtualization since DOM nodes are recycled — anchor restoration to an index, not a raw pixel offset (see the scroll-position question).

Code Example

import { useVirtualizer } from "@tanstack/react-virtual";

function VirtualFeed() {
  const { data, fetchNextPage, hasNextPage, isFetchingNextPage } = useInfiniteQuery({
    queryKey: ["feed"], queryFn: fetchFeedPage, initialPageParam: null,
    getNextPageParam: (last) => last.nextCursor,
  });
  const items = data?.pages.flatMap((p) => p.items) ?? [];

  const parentRef = useRef<HTMLDivElement>(null);
  const virtualizer = useVirtualizer({
    count: hasNextPage ? items.length + 1 : items.length, // +1 renders a loading row
    getScrollElement: () => parentRef.current,
    estimateSize: () => 72,
    overscan: 8,
  });

  useEffect(() => {
    const last = virtualizer.getVirtualItems().at(-1);
    if (last && last.index >= items.length - 1 && hasNextPage && !isFetchingNextPage) {
      fetchNextPage();
    }
  }, [virtualizer.getVirtualItems(), items.length, hasNextPage, isFetchingNextPage, fetchNextPage]);

  return (
    <div ref={parentRef} style={{ height: 600, overflow: "auto" }}>
      <div style={{ height: virtualizer.getTotalSize(), position: "relative" }}>
        {virtualizer.getVirtualItems().map((v) => (
          <div key={v.key} style={{ position: "absolute", top: v.start, height: v.size, width: "100%" }}>
            {items[v.index] ? <Row item={items[v.index]} /> : <Spinner />}
          </div>
        ))}
      </div>
    </div>
  );
}

Senior Engineer Perspective

Interviewers who ask this are usually checking whether you've actually shipped a list with tens of thousands of rows, not a demo with fifty. The signal is knowing that the fetch trigger moves from a DOM sentinel to the virtualizer's own visible-range calculation, and that variable row heights need a measuring pass rather than a fixed estimate.

Q46. How do you implement page-number based pagination with URL sync (deep-linkable to page N)?

ROI: ★★★★☆ Frequency: High

Short Answer

Store the current page number in the URL (a search param, e.g. ?page=3) rather than component state, read it with your router's search-param hook, and pass it straight into the query key. This makes the page reloadable, bookmarkable, and back/forward-button-navigable, and it keeps the query cache and the URL as two views of the same single source of truth instead of two states that can drift apart.

Q47. How does the maxPages option work in useInfiniteQuery, and why would you cap it?

ROI: ★★★☆☆ Frequency: Medium

Short Answer

maxPages (v5) caps how many pages an infinite query keeps in memory at once — once the limit is reached, fetching a new page at one end evicts the oldest page at the other end, using a sliding-window approach instead of accumulating every page ever fetched for the life of the session. It bounds memory and render cost for very long scroll sessions, at the cost of losing direct access to evicted pages (the user would refetch them by scrolling back).

Detailed Answer

  • Without it, a user who scrolls through a thousand pages of a feed keeps every one of those pages in the query's data.pages array for as long as the query stays mounted — fine for shorter sessions, a real memory/render concern for long-lived, heavily-scrolled feeds (social timelines, chat).
  • With maxPages: N, fetching a new page beyond the cap drops the oldest page from the opposite end, keeping a sliding window of at most N pages resident. Combined with getNextPageParam/getPreviousPageParam, this supports both directions dropping their own oldest end.
  • Trade-off. Scrolling back past an evicted page triggers a genuine refetch of it (correct, but a real network cost) rather than an instant cache hit — acceptable for most feeds where users rarely scroll back that far, since it's usually paired with virtualization anyway.

Code Example

useInfiniteQuery({
  queryKey: ["feed"],
  queryFn: ({ pageParam }) => fetchFeedPage(pageParam),
  initialPageParam: null,
  getNextPageParam: (last) => last.nextCursor,
  maxPages: 5, // keep at most 5 pages resident; older pages are evicted and refetched if revisited
});

Senior Engineer Perspective

This is a fairly new (v5) option, so bringing it up unprompted signals you track the library's evolution. Pair it with virtualization in your answer — capping pages controls memory for the data, virtualization controls it for the DOM; a truly long-lived feed (think Twitter-scale) needs both.

SECTION 9 - REQUEST DEDUPLICATION & CACHING STRATEGIES

Q48. How exactly does request deduplication work under the hood when multiple components mount the same query concurrently?

ROI: ★★★★☆ Frequency: High

Short Answer

Internally, each unique query key maps to one "query" object in the QueryClient's cache, and every component using that key registers as an observer of the same object rather than creating an independent fetch. When a fetch is triggered while the query already has one in flight, the existing promise is reused instead of a new network call being made — all observers subscribe to that one promise's resolution and re-render together.

Detailed Answer

  • Query cache vs observers. The QueryCache stores one entry per unique serialized key, holding data, status, and the current fetch promise if any. Each useQuery call creates a lightweight QueryObserver that subscribes to that entry — ten components with the same key are ten observers of one entry, not ten independent fetch cycles.
  • In-flight sharing. If observer #2 mounts while observer #1's fetch is still pending, the query object already has a promise recorded; #2 attaches to that same promise rather than calling queryFn again.
  • Key hashing. Keys are hashed deterministically (object key order doesn't matter) so ["todos", { status: "done", page: 1 }] and ["todos", { page: 1, status: "done" }] resolve to the same cache entry.
  • Why this matters for perf. This is what makes "just call useQuery in every component that needs the data" a safe default — you never have to manually hoist a fetch up to avoid duplicate requests, unlike the naive useEffect pattern.

Code Example

// Header, Sidebar, and Footer each independently call this hook.
// TanStack Query fires exactly ONE network request for "currentUser"
// no matter how many components mount it in the same render pass.
function useCurrentUser() {
  return useQuery({ queryKey: ["currentUser"], queryFn: fetchCurrentUser });
}

Senior Engineer Perspective

The distinction interviewers listen for is "query cache entry" vs "observer" — candidates who only say "it caches by key" miss the deeper mechanism of multiple observers sharing one entry and one in-flight promise, which is what actually explains why ten mounts produce one request rather than ten.

Q49. How do you manually update the cache with setQueryData for nested or related data?

ROI: ★★★★☆ Frequency: High

Short Answer

queryClient.setQueryData(queryKey, updater) lets you write directly into a cached entry — either replacing it outright or, more commonly, passing an updater function that receives the current value and returns a new (immutable) one. For nested data (an item inside a list, a field inside an object graph) you write the same kind of pure transform you'd write in a reducer: locate the item, produce a new object/array with the change, never mutate in place.

Detailed Answer

  • Updater function over static value. Passing a function (old) => next is safer than a static value because it reads the current cache state at write time, avoiding stale-closure bugs if other code updated the cache in between.
  • Immutability matters. React Query compares references to decide whether to notify observers — mutating a cached array/object in place (e.g. old.push(item)) can fail to trigger a re-render, or worse, corrupt data shared with other observers still holding the old reference.
  • Nested updates. For a deeply nested shape, use small immutable-update helpers (spread, or a library like Immer's produce) rather than hand-writing long chains of spreads — this is the same discipline as updating nested Redux state.
  • Type safety. Always parametrize setQueryData<T> so the updater's old parameter is properly typed instead of unknown.

Code Example

// Update one field of one item inside a cached list, immutably
queryClient.setQueryData<Order[]>(["orders"], (old = []) =>
  old.map((order) =>
    order.id === orderId
      ? { ...order, items: order.items.map((i) => (i.sku === sku ? { ...i, qty: newQty } : i)) }
      : order
  )
);

// With Immer, the same nested update reads like a mutation but stays immutable under the hood
import { produce } from "immer";
queryClient.setQueryData<Order[]>(["orders"], (old = []) =>

Q50. What is cache normalization, does React Query do it automatically, and how do you approximate it?

ROI: ★★★★☆ Frequency: High

Short Answer

Normalization means storing each entity once, keyed by its id, and having every view (list, detail, nested reference) point at that single copy — the way Apollo Client or Redux Toolkit's createEntityAdapter work. TanStack Query does not normalize automatically: each query key holds its own independent copy of whatever shape you fetched, so the same entity can exist in several places in the cache simultaneously (a list's copy and a detail view's copy), and you are responsible for keeping them in sync.

Detailed Answer

This is a deliberate design trade-off, not an oversight: TanStack Query is a query cache (keyed by request shape), not an entity cache (keyed by id). Consequences and mitigations:

  • Duplication is expected. A todo can appear in ["todos", "list"] and ["todos", "detail", id] as two separate cached values. Updating one does not automatically update the other.
  • Approximating normalization. Use setQueriesData with a predicate matching every query that could contain the entity, and update all of them together in one mutation's success handler (see the multi-query optimistic-update question) — this is a manual, per-mutation version of what a normalized cache gives you for free.
  • select as a partial answer. Deriving detail-view data from a list query via select (rather than a separate detail query) means there's only one real copy to keep in sync, at the cost of always needing the list loaded.
  • When to reach for a normalized client instead. If your app has deeply interlinked entities referenced from many unrelated views (a social graph, a CRM with cross-referenced records), a normalized cache (Apollo, URQL with normalized cache, or RTK Query's entity adapters) removes this manual-sync burden structurally — that's a legitimate reason to choose it over TanStack Query for that specific app.

Code Example

// Manual "normalization" for one mutation: update every place this todo could be cached
onSuccess: (updated: Todo) => {
  queryClient.setQueriesData<Todo[]>({ queryKey: todoKeys.lists() }, (old) =>
    old?.map((t) => (t.id === updated.id ? updated : t))
  );
  queryClient.setQueryData(todoKeys.detail(updated.id), updated);
}

Senior Engineer Perspective

The strongest answer frames this as a conscious trade-off TanStack Query makes for simplicity, not a missing feature — and names Apollo/normalized caches as the alternative when an app's entity graph is complex enough that manual multi-query updates become error-prone and repetitive.

Q51. How do you share cache data between a list view and a detail view to avoid refetching on navigation?

ROI: ★★★★☆ Frequency: High

Short Answer

When the list query already contains the full shape the detail view needs, seed the detail query's cache with initialData sourced from the list — the detail view renders instantly with no loading state, and (if it's still fresh per staleTime) skips the network call entirely. If the list only has a partial shape, use the list data as placeholderData instead, showing it while a real detail fetch still happens in the background.

Detailed Answer

  • Full shape available → initialData. If clicking into a detail page needs exactly the fields already present in the list row, use initialData: () => queryClient.getQueryData(listKey)?.find(...) plus initialDataUpdatedAt so freshness is judged correctly against the list's own fetch time.
  • Partial shape → placeholderData. If the detail view needs more fields than the list row has (e.g. a full description, comments), show the partial data as a placeholder while a real fetch for the full detail runs — the user sees something immediately, then it fills in.
  • Prefetch on intent is the complementary technique: prefetch the detail query on hover/focus of the list row, so by the time the user clicks, the network round trip is already done (see the prefetching section).

Code Example

function useTodoDetail(id: string) {
  return useQuery({
    queryKey: todoKeys.detail(id),
    queryFn: () => fetchTodoDetail(id),
    initialData: () => {
      const list = queryClient.getQueryData<Todo[]>(todoKeys.lists());
      return list?.find((t) => t.id === id); // instant if the list already has it
    },
    initialDataUpdatedAt: () =>
      queryClient.getQueryState(todoKeys.lists())?.dataUpdatedAt,
  });
}

Senior Engineer Perspective

The follow-up interviewers ask: "what if the list data is stale — do you still trust it?" Answer: initialDataUpdatedAt makes the library evaluate the seeded data's age against your real staleTime, so if it's actually stale, a background refetch still kicks in automatically — you get instant paint plus correctness, not one or the other.

Q52. How do you invalidate a broad set of related queries safely without over-fetching?

ROI: ★★★★☆ Frequency: High

Short Answer

Invalidate at the narrowest key prefix that's guaranteed to cover everything actually affected — not the broadest one "to be safe." A query-key factory with a clear hierarchy (all → lists → list(filters), all → details → detail(id)) lets you target exactly "all list views" or "just this one detail" instead of nuking every cached query for a resource on every write.

Detailed Answer

  • Prefix matching is fuzzy by default. invalidateQueries({ queryKey: ["todos"] }) invalidates every query whose key starts with "todos" — lists, details, filtered variants, all of it. Convenient, but wasteful if the mutation only actually affected one list variant.
  • Exact matching — pass { exact: true } to invalidate only the query matching the full key precisely, not its descendants; use this when you know precisely which cached entry changed.
  • Predicate-based invalidation — { predicate: (query) => ... } gives full control for cases the key hierarchy can't express cleanly (e.g. "any list query whose filter includes this status").
  • refetchType option. invalidateQueries({ queryKey, refetchType: "active" }) (the default) only immediately refetches currently-mounted queries; "none" just marks everything stale without an immediate network call, useful when you know the user isn't looking at the affected view right now.

Code Example

// Narrow: only list views, leave cached detail pages alone
queryClient.invalidateQueries({ queryKey: todoKeys.lists() });

// Exact: only this precise key, not its children
queryClient.invalidateQueries({ queryKey: todoKeys.list({ status: "done" }), exact: true });

// Predicate: anything matching a custom condition the key hierarchy can't express
queryClient.invalidateQueries({
  predicate: (query) =>
    query.queryKey[0] === "todos" &&
    typeof query.queryKey[1] === "object" &&
    (query.queryKey[1] as any)?.status === "done",
});

Senior Engineer Perspective

Interviewers push on "isn't invalidating broadly just simpler and safer?" — the honest answer is it's simpler but not free: over-broad invalidation causes redundant network traffic and flickers in unrelated views on every write. Naming exact, predicates, and refetchType shows you've had to actually tune this in a real app rather than always reaching for the widest possible key.

Q53. How do you use getQueryData and setQueriesData for bulk cache reads/updates matching a predicate?

ROI: ★★★☆☆ Frequency: Medium

Short Answer

getQueryData(key) reads one specific cached entry synchronously (returns undefined if not cached — it does not trigger a fetch). getQueriesData({ queryKey/predicate }) and setQueriesData({ queryKey/predicate }, updater) operate on every matching entry at once — read or write across all of them in a single call, instead of looping over getQueryCache().findAll() yourself.

Detailed Answer

  • getQueryData vs useQuery. getQueryData is an imperative, one-off read (e.g. inside an event handler or another query's initialData) — it does not subscribe the caller to future updates and does not fetch if the entry is missing. Use useQuery when you need the component to re-render on changes.
  • getQueriesData returns an array of [queryKey, data] tuples for every entry matching a key prefix or predicate — handy for snapshotting several related queries before a multi-entity optimistic update.
  • setQueriesData applies an updater to every matching entry and returns the same tuple array of what changed — this is the bulk counterpart to setQueryData used when one mutation could affect several distinct cached views at once (see the multi-query optimistic-update question).

// One-off imperative read, no subscription
const cachedUser = queryClient.getQueryData<User>(["user", id]);

// Snapshot every matching entry before a broad update (for rollback)
const snapshots = queryClient.getQueriesData<Todo[]>({ queryKey: todoKeys.lists() });

// Bulk update every matching entry in one call
queryClient.setQueriesData<Todo[]>({ queryKey: todoKeys.lists() }, (old) =>
  old?.filter((t) => t.id !== deletedId)
);

Senior Engineer Perspective

A common mix-up is calling getQueryData expecting it to trigger a fetch if the data isn't cached — it won't; that's what ensureQueryData/fetchQuery are for. Being crisp about "read without subscribing/fetching" vs "read-and-subscribe" vs "read-or-fetch" is exactly the kind of precision that separates surface familiarity from real fluency with the API.

Q54. What's the difference between refetch() and invalidateQueries() for a currently-mounted query?

ROI: ★★★★☆ Frequency: High

Short Answer

refetch() (from a specific useQuery result) forces that one query to re-fetch immediately, regardless of whether it's stale — it's a direct, local, imperative action. invalidateQueries({ queryKey }) marks matching queries as stale globally through the QueryClient, and only actively mounted ones refetch right away; inactive/unmounted ones simply refetch the next time they're used. Use refetch for "this one query, right now, no matter what"; use invalidateQueries for "this data changed somewhere, let every relevant view know."

The trap answer treats these as interchangeable "refresh the data" tools. The distinguishing detail interviewers want is the scope difference — one component's manual refresh button vs. a mutation announcing "this class of data changed" to the whole app — and that only invalidateQueries correctly reaches other components observing related-but-different keys.

Q55. How do you persist the query cache across page reloads?

ROI: ★★★☆☆ Frequency: Medium

Short Answer

The @tanstack/query-persist-client-core / persistQueryClient plugin serializes the entire cache to a storage backend (localStorage, IndexedDB via idb-keyval) on change, and restores it on the next page load before your components mount — so a returning user sees data instantly instead of a blank loading state, with a background revalidation confirming it's still current.

Detailed Answer

  • Persister interface. A persister just needs persistClient/restoreClient/removeClient methods; the library ships a createSyncStoragePersister for synchronous storage (localStorage) and an async variant for IndexedDB.
  • maxAge and buster. Configure a maxAge so persisted data older than that is discarded on restore rather than trusted indefinitely, and a buster string you bump on app deploys so an old persisted shape (from a previous schema) doesn't get restored into a newer app version.
  • Not every query should persist. Use dehydrateOptions.shouldDehydrateQuery to exclude sensitive or highly volatile queries (e.g. anything containing tokens, or live/real-time data) from being written to disk at all.
  • Security note. localStorage is readable by any script on the page (XSS-exposed) — never persist auth tokens or sensitive PII through this mechanism; scope it to non-sensitive, reconstructable data.

Code Example

import { persistQueryClient } from "@tanstack/react-query-persist-client";
import { createSyncStoragePersister } from "@tanstack/query-sync-storage-persister";

const persister = createSyncStoragePersister({ storage: window.localStorage });

persistQueryClient({
  queryClient,
  persister,
  maxAge: 24 * 60 * 60 * 1000, // discard persisted data older than a day on restore
  buster: process.env.APP_VERSION, // bump on deploy to invalidate old persisted shapes
  dehydrateOptions: {
    shouldDehydrateQuery: (query) => query.queryKey[0] !== "sensitiveReport",
  },
});

Senior Engineer Perspective

Interviewers check whether you'll blindly persist everything, including anything sensitive — flagging the XSS exposure of localStorage and deliberately excluding sensitive queries via shouldDehydrateQuery is the security-conscious answer. Also mention this is purely an instant-paint optimization: a background revalidation should still run so restored data is confirmed current, not trusted forever.

SECTION 10 - ERROR & RETRY HANDLING

Q56. How do you design a retry policy that distinguishes retryable from non-retryable errors, in depth?

ROI: ★★★★★ Frequency: Extremely High

Short Answer

Classify errors by whether retrying can plausibly change the outcome. Retryable: network failures, timeouts, 502/503/504 (upstream/service unavailable), and 429 (rate-limited, ideally respecting a Retry-After header). Non-retryable: 400 (bad request), 401/403 (auth — retrying without fixing the token does nothing), 404 (won't appear by retrying), 422 (validation — the input itself is wrong). Encode this as a retry function that inspects the error's status rather than a flat retry count.

Detailed Answer

Status/errorRetryable?Why
Network failure / timeoutYesTransient — the request may simply not have reached the server
408 Request TimeoutYesServer explicitly signals a timeout, often transient
429 Too Many RequestsYes, with backoff (ideally honoring Retry-After)Rate limiting is inherently temporary
500 Internal Server ErrorCautiously — depends on idempotency of the operationMay be transient, may be a real bug that repeats identically
502/503/504YesUpstream/gateway/service unavailable — classic transient infra issue
400/404/422NoThe request itself is wrong; retrying sends the identical bad request again
401/403No (without a token refresh first)Retrying the same request with the same invalid/expired credential can't succeed

Also cap total retries and cap the backoff ceiling — unbounded exponential growth eventually delays error surfacing to the user by an absurd amount; a max delay (e.g. 30s) and a max attempt count (e.g. 3-5) are standard.

Code Example

const RETRYABLE_STATUSES = new Set([408, 429, 502, 503, 504]);

useQuery({
  queryKey: ["report", id],
  queryFn: fetchReport,
  retry: (failureCount, error) => {
    const status = (error as ApiError).status;
    if (status && !RETRYABLE_STATUSES.has(status) && status < 500) return false; // 4xx: don't retry
    return failureCount < 3;
  },
  retryDelay: (attempt, error) => {
    const retryAfter = (error as ApiError).retryAfterMs;
    return retryAfter ?? Math.min(1000 * 2 ** attempt, 30_000); // honor Retry-After if the server sent one
  },
});

Senior Engineer Perspective

Interviewers love a live edge case: "should a 500 retry?" There's no single right answer — the honest response is "it depends on whether the operation is idempotent and whether 500s at this endpoint tend to be transient (a flaky downstream dependency) or deterministic (a bug that will 500 identically every time)." Naming that nuance, rather than a blanket yes/no, is what a senior actually says.

Q57. How do you implement global error handling with QueryCache/MutationCache onError callbacks?

ROI: ★★★★☆ Frequency: High

Short Answer

Pass a QueryCache/MutationCache instance (each accepting an onError callback) into the QueryClient constructor to centralize cross-cutting error handling — logging to an error-tracking service, showing a generic toast — in one place, instead of duplicating onError in every individual useQuery/useMutation call. Per-call onError/meta handlers still run for anything that needs component-specific behavior.

Detailed Answer

  • QueryCache/MutationCache constructor callbacks fire for every query/mutation error in the app, regardless of whether that individual call site defined its own handler — ideal for telemetry (Sentry, Datadog) that should see every failure exactly once.
  • meta for per-query context. Attach a meta: { errorMessage: "..." } (or any custom shape) to individual queries/mutations, and read query.meta/mutation.meta inside the global onError to customize behavior (e.g. only toast for queries that opted in) without needing a handler at every call site.
  • Layering, not replacing. A component's own onError (passed to useMutation) still runs in addition to the global one — use the global handler for "always do this" (log it) and the local one for "and also do this specific UI thing here."

Code Example

const queryClient = new QueryClient({
  queryCache: new QueryCache({

      logErrorToSentry(error, { queryKey: query.queryKey });
      if (query.meta?.showErrorToast) toast.error(query.meta.errorMessage as string ?? "Something went wrong");
    },
  }),
  mutationCache: new MutationCache({
    onError: (error, _vars, _ctx, mutation) => {
      logErrorToSentry(error, { mutationKey: mutation.options.mutationKey });
    },
  }),
});

// Opt one query into the toast via meta, without a local onError handler:
useQuery({
  queryKey: ["report", id],
  queryFn: fetchReport,
  meta: { showErrorToast: true, errorMessage: "Couldn't load the report" },
});

Senior Engineer Perspective

The signal here is recognizing meta as the bridge between a truly global handler and per-query customization — without it, teams either duplicate onError everywhere (defeating the point of centralizing) or the global handler becomes a giant if/else keyed on query key strings (brittle). Knowing meta exists for exactly this purpose is a strong signal of real usage.

Q58. How do you integrate an ErrorBoundary with React Query using throwOnError?

ROI: ★★★★☆ Frequency: High

Short Answer

By default, a query's error surfaces as data (isError/error on the hook result) — you handle it inline. Setting throwOnError: true (or a predicate function) makes the query instead throw the error during render, which the nearest React ErrorBoundary catches — letting you declare error UI structurally at a boundary, the same way useSuspenseQuery declares loading UI via Suspense.

Detailed Answer

  • Predicate form. throwOnError: (error) => error.status >= 500 lets you throw only for genuinely exceptional failures (server errors) while still handling expected ones (e.g. a 404 "not found" state) inline as normal error state — a common, pragmatic middle ground rather than an all-or-nothing switch.
  • Boundary placement. Just like Suspense, nest ErrorBoundarys at the granularity you want — a boundary around one widget contains that widget's failure without white-screening the whole page.

Q59. How do you handle partial failures in a useQueries array where some succeed and some fail?

ROI: ★★★☆☆ Frequency: Medium

Short Answer

useQueries returns an array of independent results — each with its own status, data, and error — so a failure in one query never blocks or clears the others. Render each result according to its own state (loading/error/success) rather than gating the whole UI on every query succeeding, unless the feature genuinely requires all of them.

Detailed Answer

const results = useQueries({

    widgets: results.filter((r) => r.isSuccess).map((r) => r.data),

Q60. How do you show a global "you're offline" banner and pause/resume queries with networkMode?

ROI: ★★★☆☆ Frequency: Medium

Short Answer

TanStack Query tracks online/offline status itself (via the browser's online/offline events by default) and, with the default networkMode: "online", automatically pauses queries and mutations while offline instead of letting them fail repeatedly — they resume automatically on reconnect. You render a global banner from the library's own useIsRestoring/online manager or a simple navigator.onLine-driven hook, and rely on networkMode to keep the data layer from thrashing against a dead network.

Detailed Answer

  • networkMode: "online" (default) — queries pause (go into a "paused" fetch status) rather than erroring when the browser is offline, and automatically resume when connectivity returns, honoring refetchOnReconnect.
  • networkMode: "always" — ignore online/offline state entirely and always attempt the fetch (appropriate for queries hitting a local cache/service worker that doesn't need real network).
  • networkMode: "offlineFirst" — attempt the first request regardless of the reported online status (useful when the browser's online flag is unreliable, e.g. behind a captive portal that reports "online" but isn't actually reachable), only pausing subsequent retries if it genuinely fails.
  • Custom online manager. You can override how "online" is detected (onlineManager.setEventListener) if navigator.onLine isn't reliable enough for your app's needs (e.g. actively pinging a health endpoint).

Code Example

function useOnlineStatus() {
  const [online, setOnline] = useState(navigator.onLine);
  useEffect(() => {
    const goOnline = () => setOnline(true);
    const goOffline = () => setOnline(false);
    window.addEventListener("online", goOnline);
    window.addEventListener("offline", goOffline);
    return () => {
      window.removeEventListener("online", goOnline);
      window.removeEventListener("offline", goOffline);
    };
  }, []);
  return online;
}

function OfflineBanner() {
  const online = useOnlineStatus();
  return online ? null : <Banner>You're offline — changes will sync once reconnected</Banner>;
}

Q61. How do you implement circuit-breaker-like behavior to stop retrying after a service outage?

ROI: ★★★☆☆ Frequency: Medium

Short Answer

TanStack Query's per-query retry/backoff is a "smart retry," not a circuit breaker — it doesn't share failure state across different queries or stop trying after repeated systemic failures. To approximate a circuit breaker, track consecutive failures (or a failure rate) for a given endpoint outside individual queries — e.g. in the QueryCache's global onError, or a small module-level counter — and short-circuit further attempts (skip retries, or disable the affected queries) once a threshold is crossed, resetting after a cooldown or a successful probe request.

Detailed Answer

  • Why per-query retry isn't enough. If an entire backend service is down, each of N different queries hitting it independently retries its own 3 attempts with its own backoff — that's still N × 3 requests hammering a dead service, and there's no shared "give up for now" signal between them.
  • Shared failure state. Maintain a simple state machine (closed/open/half-open) keyed by service or endpoint prefix, incremented in the global QueryCache.onError; once "open," set affected queries' enabled: false or short-circuit their retry to false immediately rather than each independently backing off.
  • Half-open probing. After a cooldown, allow exactly one query through as a probe; if it succeeds, reset to "closed" (normal operation resumes for all); if it fails, extend the cooldown.
  • This is genuinely more backend-pattern than frontend-pattern — many teams instead implement circuit breaking at an API gateway or backend-for-frontend layer, where it belongs more naturally, and keep the client simple.

Code Example

const breaker = { failures: 0, openUntil: 0 };
const THRESHOLD = 5;
const COOLDOWN_MS = 30_000;

const queryClient = new QueryClient({
  queryCache: new QueryCache({
    onError: () => {
      breaker.failures += 1;
      if (breaker.failures >= THRESHOLD) breaker.openUntil = Date.now() + COOLDOWN_MS;
    },
    onSuccess: () => { breaker.failures = 0; breaker.openUntil = 0; },
  }),
  defaultOptions: {
    queries: {
      retry: () => Date.now() >= breaker.openUntil, // no retries while the breaker is open
      enabled: () => Date.now() >= breaker.openUntil,
    },
  },
});

Senior Engineer Perspective

The mature answer acknowledges this is somewhat outside what TanStack Query is designed for and is honest about the trade-off: a hand-rolled client-side breaker adds real complexity, and for many apps it's better solved server-side (gateway-level circuit breaking, load shedding) than duplicated per-frontend. Interviewers respect "this is possible but I'd push for it at the API layer first" more than an over-engineered client-only solution.

Q62. How do you differentiate a validation error (422) from a transient error in the UI?

ROI: ★★★★☆ Frequency: High

Short Answer

A validation error (422, or 400 with a structured error body) is the user's/input's fault and is never fixed by retrying — it needs to surface as field-level or form-level messages so the user can correct their input. A transient error (network failure, 503) is nobody's fault right now and should surface as a generic "something went wrong, try again" with a retry action. Branch on the error shape (status code plus a structured error payload) rather than showing one generic error banner for everything.

Detailed Answer

  • Design the error type up front. Have your API return a consistent shape for validation failures — e.g. { status: 422, fieldErrors: { email: "Invalid format" } } — so the client can reliably distinguish it from a generic 500/network error without string-matching messages.
  • Never retry 422s. They're a poor fit for useQuery's retry policy entirely (return false immediately) — the fix is the user changing their input, not the client trying again.
  • Route to the right UI. Validation errors map to inline field messages (ideally integrated with your form library's error state, e.g. React Hook Form's setError); transient errors map to a toast/banner with a retry button, not inline field messages, since there's no specific field to blame.
  • Mutations, specifically. This distinction matters most for form-submitting mutations — a 422 from a "create user" mutation should populate the form's field errors, while a 503 from the same mutation should show a generic "please try again" and re-enable the submit button, not blank out the form.

Code Example

type ApiError = {
  status: number;
  fieldErrors?: Record<string, string>;
};

useMutation({
  mutationFn: createUser,
  retry: false, // never retry a form submission blindly
  onError: (error: ApiError) => {
    if (error.status === 422 && error.fieldErrors) {
      Object.entries(error.fieldErrors).forEach(([field, message]) =>
        form.setError(field as keyof FormValues, { message })
      );
    } else {
      toast.error("Something went wrong — please try again.");
    }
  },
});

Senior Engineer Perspective

Interviewers check whether you'll blur every failure into one generic red banner — that's a poor UX for validation errors specifically, since the user has no idea which field to fix. The strong answer starts from API contract design (a consistent error shape) rather than trying to parse ad hoc error strings on the client.

Q63. How do you handle errors in mutations that must roll back multiple related cache entries?

ROI: ★★★★☆ Frequency: High

Short Answer

Snapshot every affected query (not just one) in onMutate — typically as an array of [queryKey, data] pairs from getQueriesData — and restore each one in onError by iterating that array back through setQueryData. Treat it the same way you'd treat a database transaction rollback: capture the full "before" state up front so you can undo everything atomically, not just the one entry you happened to remember to snapshot.

Detailed Answer

  • Snapshot broadly, restore precisely. Use getQueriesData({ queryKey: prefix }) to capture every currently-cached query under a resource's prefix in one call, rather than manually listing each key you think might be relevant (which is exactly where entries get missed as the app grows).
  • Restore in onError, reconcile in onSettled. Roll back to the exact snapshot on failure; then, regardless of success or failure, invalidate the same prefix in onSettled so the final state always converges on the server's truth rather than trusting the rollback (or the optimistic write) indefinitely.
  • Order matters for dependent entities. If entity B's cached shape embeds a reference to entity A (e.g. an order embedding line items), make sure your rollback restores both in an order that never leaves the cache in an inconsistent intermediate shape mid-render.

Code Example

type Context = { snapshots: Array<[QueryKey, unknown]> };

useMutation<Order, Error, OrderUpdate, Context>({
  mutationFn: (update) => api.updateOrder(update),

  onMutate: async (update) => {
    await queryClient.cancelQueries({ queryKey: ["orders"] });
    const snapshots = queryClient.getQueriesData({ queryKey: ["orders"] }); // every affected entry, in one call

    queryClient.setQueryData(["orders", "detail", update.id], (old: Order) => ({ ...old, ...update }));
    queryClient.setQueriesData<Order[]>({ queryKey: ["orders", "list"] }, (old) =>
      old?.map((o) => (o.id === update.id ? { ...o, ...update } : o))
    );

    return { snapshots };
  },

  onError: (_err, _update, context) => {
    context?.snapshots.forEach(([queryKey, data]) => queryClient.setQueryData(queryKey, data));
  },

  onSettled: () => queryClient.invalidateQueries({ queryKey: ["orders"] }),
});

Senior Engineer Perspective

The interviewer is probing for whether you'll snapshot ad hoc (and inevitably miss an affected query as the codebase grows) or snapshot systematically via a prefix-based getQueriesData call. The latter scales as new views on the same resource get added later without anyone remembering to update the rollback logic by hand.

SECTION 11 - MUTATIONS & CACHE SYNCHRONIZATION

Q64. How do you queue dependent mutations so they execute in order rather than concurrently?

ROI: ★★★★☆ Frequency: High

Short Answer

By default, calling mutate multiple times in quick succession fires each mutation concurrently — there's no built-in ordering guarantee. To serialize dependent writes (B must apply after A succeeds), either chain them explicitly with await mutateAsync() in sequence, or give mutations that touch the same resource a shared mutationKey/scope (v5) so the library itself queues them.

Detailed Answer

  • Explicit chaining. The simplest and most predictable approach: await mutation.mutateAsync(a); await mutation.mutateAsync(b); inside an async function — each waits for the previous to fully settle before the next starts, and you can bail out early on failure.
  • scope (v5). useMutation({ scope: { id: "order-123" } }) tells TanStack Query to run mutations sharing that scope id sequentially rather than in parallel, even if triggered from different components — useful when several UI elements can each trigger a write to the same underlying resource and you want to guarantee they never race each other.
  • When NOT to serialize. Independent mutations to unrelated resources should stay concurrent — over-serializing unrelated writes just adds latency for no correctness benefit. Reserve queuing for writes that are genuinely dependent or touch the same entity.

Code Example

// Explicit sequential chaining
async function checkout(cart: Cart) {
  const order = await createOrderMutation.mutateAsync(cart);
  await chargePaymentMutation.mutateAsync({ orderId: order.id, amount: order.total });
  await sendConfirmationMutation.mutateAsync({ orderId: order.id });
}

// scope: mutations sharing an id are queued, not run in parallel
function useUpdateOrder(orderId: string) {
  return useMutation({
    mutationFn: (patch: Partial<Order>) => api.updateOrder(orderId, patch),
    scope: { id: `order-${orderId}` }, // two components editing the same order won't race
  });
}

Senior Engineer Perspective

The follow-up interviewers love: "what happens today, without scope, if two different form fields for the same order each fire their own mutation on blur?" Without serialization, a slower "name" update could resolve after a faster "status" update and silently overwrite it depending on how the mutation functions are implemented (e.g. a PUT sending the whole object) — scope is the newer, built-in fix for exactly this class of bug.

Q65. How do you prevent duplicate submissions (double-click) at the mutation layer?

ROI: ★★★★☆ Frequency: High

Short Answer

Disable the triggering control while mutation.isPending is true — this is the primary, UI-level defense. As a backstop against network-level retries or race conditions the UI guard might miss, attach a client-generated idempotency key to the request so the server can recognize and dedupe a duplicate even if two requests do reach it.

Detailed Answer

  • UI guard. <button disabled={mutation.isPending}> is simple, catches the overwhelming majority of real-world double-clicks, and gives the user visible feedback (a disabled/loading button) that their first click registered.
  • Why it's not sufficient alone. A very fast double-click before React re-renders, a retried request after a flaky network blip, or a user opening the same form in two tabs can all still produce two requests reaching the server — the UI guard doesn't cover every case.
  • Idempotency key as the real backstop. Generate a key once per logical submission attempt (not per request/retry) and send it with the mutation; the server stores recently-seen keys and returns the original result for a repeat instead of re-executing the write. This is the same technique used for the non-idempotent-operations question, applied generally to any "must not double-submit" mutation.
  • mutation.reset() clears a mutation's state (data/error/status) — useful to call after a successful submission so a subsequent legitimate resubmission isn't blocked by stale isPending/isSuccess flags from the last attempt.

Code Example

function CheckoutButton() {
  const idempotencyKey = useRef(crypto.randomUUID()); // stable for this logical attempt

  const mutation = useMutation({
    mutationFn: (cart: Cart) =>
      fetch("/api/checkout", {
        method: "POST",
        headers: { "Idempotency-Key": idempotencyKey.current },
        body: JSON.stringify(cart),
      }),
    onSuccess: () => { idempotencyKey.current = crypto.randomUUID(); }, // fresh key for the next real attempt
  });

  return (
    <button disabled={mutation.isPending} onClick={() => mutation.mutate(cart)}>
      {mutation.isPending ? "Processing..." : "Checkout"}
    </button>
  );
}

Senior Engineer Perspective

Weak answers stop at "disable the button." The senior answer explicitly names the gap between UI-level and network-level duplicate prevention, and reaches for an idempotency key as the layer that actually guarantees correctness regardless of what the client does — because the client can't fully control every path to a duplicate request (retries, multiple tabs, flaky connections).

Q66. How do you use a mutation queue or scope to serialize writes to the same resource across different components?

ROI: ★★★☆☆ Frequency: Medium

Short Answer

When two unrelated components can each independently trigger a write to the same entity (e.g. an inline-editable field in a table row and a detail panel open for the same row), giving both mutations the same scope.id makes TanStack Query queue them — the second mutation waits for the first to fully settle before it starts — instead of letting them race and potentially apply out of order.

Detailed Answer

  • Same entity, different components. scope is keyed by whatever string/object you choose — typically the entity's id — so any component anywhere in the tree that constructs a mutation with a matching scope id automatically joins the same queue, without needing to share a single mutation instance or lift state up.
  • Order of application. Mutations in the same scope run strictly one after another (FIFO) — the second one's mutationFn doesn't even start until the first's onSettled has completed, which also means its onMutate sees the cache state after the first mutation's effects, not a stale pre-first-mutation snapshot.
  • Alternative without v5's scope: maintain your own promise chain in a small module (a per-entity Map<id, Promise>) and have each mutation's function await the previous promise for that id before proceeding — more code, same effect, useful if you're on an older version.

Code Example

// InlineEdit.tsx
function useInlineUpdate(rowId: string) {
  return useMutation({
    mutationFn: (patch: Partial<Row>) => api.updateRow(rowId, patch),
    scope: { id: `row-${rowId}` },
  });
}

// DetailPanel.tsx — different component, same scope id -> queued behind InlineEdit's mutation
function useDetailUpdate(rowId: string) {
  return useMutation({
    mutationFn: (patch: Partial<Row>) => api.updateRow(rowId, patch),
    scope: { id: `row-${rowId}` }, // joins the same queue automatically
  });
}

Senior Engineer Perspective

This question distinguishes candidates who know useMutation only at the single-component level from those who've hit the cross-component race in a real app — a table with inline edit AND a side panel for the same row is a very common real-world layout where this bites.

Q67. How do you keep multiple related queries in sync after a single mutation touches several entities?

ROI: ★★★★☆ Frequency: High

Short Answer

Enumerate every entity/query the write actually affects and update or invalidate each explicitly — TanStack Query has no automatic cross-entity propagation. A "move a todo to a different project" mutation, for instance, touches the todo's own detail query, the old project's todo list, and the new project's todo list — all three need attention in onSuccess/onSettled, not just the todo itself.

Detailed Answer

  • Map out the blast radius before writing the mutation. Ask "what views does this write change the truth of?" as a design step — it's easy to remember the obvious primary entity and forget a secondary list that also needs updating.
  • Mix invalidation and direct writes as appropriate. Directly patch the entity you have full data for (setQueryData for the todo's new state); invalidate broader/derived views you don't want to hand-compute (both project list queries, and possibly an aggregate "todo counts per project" query).
  • Centralize this logic per-resource, e.g. in a single useMoveTodo hook that owns the full set of side effects, rather than leaving each call site to remember all three updates itself.

Code Example

function useMoveTodo() {
  return useMutation({
    mutationFn: ({ todoId, fromProjectId, toProjectId }: MoveTodoArgs) =>
      api.moveTodo(todoId, toProjectId),

    onSuccess: (updatedTodo, { fromProjectId, toProjectId }) => {
      queryClient.setQueryData(todoKeys.detail(updatedTodo.id), updatedTodo);
      // both project lists changed membership -- invalidate rather than hand-patch the arrays
      queryClient.invalidateQueries({ queryKey: projectKeys.todos(fromProjectId) });
      queryClient.invalidateQueries({ queryKey: projectKeys.todos(toProjectId) });
      // an aggregate that can't be cheaply hand-computed client-side
      queryClient.invalidateQueries({ queryKey: projectKeys.counts() });
    },
  });
}

Senior Engineer Perspective

The best answers describe this as a deliberate "what's the blast radius of this write" exercise done once per mutation, and point out that missing one of the affected queries is the single most common source of "stale UI after a save" bug reports in real apps using TanStack Query.

Q68. What is mutationKey used for, and how does mutation persistence/resumption after a reload work?

ROI: ★★★☆☆ Frequency: Medium

Short Answer

mutationKey identifies a mutation the way queryKey identifies a query — it's what MutationCache filters/matches on (e.g. to find "all in-flight mutations for this order" via useMutationState), and what scope/persistence features key off of. Paired with the persistence plugin, a mutation that was still in flight when the page was closed/reloaded can be serialized to storage and resumed (re-executed) on the next load, so a write the user made isn't silently lost.

Detailed Answer

  • Matching/inspection. useMutationState({ filters: { mutationKey: ["addComment", postId] } }) reads the state of every mutation matching that key from anywhere in the tree — this is what backs the "show several pending optimistic items" pattern from the mutation.variables question.
  • Resumable mutations. persistQueryClient can also persist paused/in-flight mutations (those that were interrupted by the page closing or going offline) and, on the next app load, resume them via queryClient.resumePausedMutations() — so a write attempted while offline actually completes once the user comes back online and reopens the app, rather than being silently dropped.
  • Must be serializable. Persisted mutation variables must be JSON-serializable (no File objects, functions, etc.) since they're written to storage as-is — a real constraint to design mutation payloads around if you want this resumability.
  • Idempotency matters here too. A resumed mutation is effectively a retry across a page reload — pair it with the same idempotency-key discipline as any other retried write.

Code Example

useMutation({
  mutationKey: ["addComment", postId],
  mutationFn: (text: string) => api.addComment(postId, text),
});

// Elsewhere, observe every pending mutation for this post (e.g. to render optimistic items):
const pending = useMutationState({
  filters: { mutationKey: ["addComment", postId], status: "pending" },
  select: (m) => m.state.variables as string,
});

// On app init, after restoring a persisted client:
await queryClient.resumePausedMutations(); // replay any mutation interrupted by a reload/offline gap

Senior Engineer Perspective

This is a good "how deep does your knowledge go" question — most candidates know query keys well but have never touched mutationKey/useMutationState/mutation resumption. Naming the JSON-serializability constraint on persisted mutation variables shows you've actually thought through the mechanics, not just the existence of the feature.

Q69. How do you test mutations and their cache side effects?

ROI: ★★★★☆ Frequency: High

Short Answer

Render the component with a real, fresh QueryClient and MSW mocking the network, pre-seed any queries the mutation should update, trigger the mutation through the UI (a click, not calling the mutation function directly), and assert on the rendered output afterward — both the mutation's own success/error UI and any other component reading the same cache that should now reflect the update.

Detailed Answer

  • Test through the UI, not the hook in isolation. Triggering via fireEvent.click/userEvent and asserting on rendered DOM exercises the real integration between the mutation, the cache update, and every component observing it — closer to how the feature actually behaves for a user than calling mutation.mutate() directly in a hook-testing harness.
  • Assert cross-component cache effects. If a mutation on one component should update a list rendered by a sibling, render both in the test and assert the sibling's output changes after the mutation settles — this is what actually validates your invalidateQueries/setQueryData side effects, not just that the mutation itself resolved.
  • Use waitFor for anything async (the mutation resolving, a subsequent refetch) rather than asserting immediately — mutations and their cache effects are asynchronous even against a mocked network.
  • A fresh QueryClient per test (created in a beforeEach) avoids state leaking between tests and flaky order-dependent failures.

Code Example

test("completing a todo updates both the detail view and the list count", async () => {
  server.use(http.patch("/api/todos/:id", () => HttpResponse.json({ id: "1", done: true })));

      <TodoItem id="1" />

    </QueryClientProvider>
  );

  expect(screen.getByText("1 pending")).toBeInTheDocument();
  fireEvent.click(screen.getByRole("checkbox"));

});

Senior Engineer Perspective

Weak test suites test the mutation in a vacuum (does it call the right endpoint) and never assert that other parts of the app actually observe the update. Rendering a second, independent consumer of the same cache in the test and asserting it reflects the change is the detail that proves the cache-synchronization logic — not just the network call — actually works.

Q70. What do invalidateQueries' refetchType options control, and when do you use 'none'?

ROI: ★★★☆☆ Frequency: Medium

Short Answer

refetchType controls which matched queries actually trigger an immediate network refetch when invalidated: "active" (default) refetches only currently-mounted/observed queries right away; "inactive" refetches only unmounted-but-cached ones; "all" does both; "none" just marks everything stale without fetching anything immediately — the next time any of them is observed, it will refetch normally because it's stale.

Detailed Answer

  • Default ("active") is usually right. You typically want the screen the user is looking at to update immediately after a related mutation; queries for screens they're not currently viewing don't need to burn a network request until the user actually navigates there.
  • "none" use case. If you know a mutation affects a huge number of queries but the user is nowhere near most of the affected views right now, marking them all stale without an immediate storm of refetches avoids wasting bandwidth/server load on data nobody's about to look at — they'll refetch naturally on next mount.
  • "inactive" is the rarer case — deliberately warming background/cached-but-unmounted queries (e.g. a tab the user recently left) without touching the ones they're actively viewing, perhaps because you're batching or rate-limiting active refetches separately.

Code Example

// Only refetch what's on screen right now; leave everything else marked stale for later
queryClient.invalidateQueries({ queryKey: todoKeys.all, refetchType: "active" }); // default

// A mutation with a very wide blast radius and mostly-unmounted affected views:
queryClient.invalidateQueries({ queryKey: ["reports"], refetchType: "none" });
// Nothing refetches immediately -- each report view fetches fresh data next time it's opened.

Senior Engineer Perspective

This is a fine-grained option most candidates have never needed to reach for — bringing it up unprompted, with a concrete "wide blast radius, mostly off-screen" scenario, signals real production tuning rather than default-options familiarity.

Q71. How do you implement a "save draft" pattern with debounced mutations?

ROI: ★★★★☆ Frequency: High

Short Answer

Debounce the trigger, not the mutation itself: keep the input's value in local component state for instant typing responsiveness, and fire the save mutation only after the user pauses typing for some interval (e.g. 500ms–1s), cancelling any pending debounced call if they keep typing. Track "saving"/"saved"/"error" status derived from the mutation's own state so the user gets feedback without a save firing on every keystroke.

Detailed Answer

  • Local state for the input, mutation for persistence. The text field should never wait on the network to update visually — bind it to local state, and let a debounced effect (or a debounced callback from a utility like use-debounce or a hand-rolled useRef timer) trigger the actual mutate call.
  • Cancel superseded saves. If a new keystroke resets the debounce timer, any previous timer must be cleared so you don't fire two saves in quick succession for the same field — same principle as debouncing a search input, applied to writes instead of reads.
  • Out-of-order responses. If saves can somehow still overlap (e.g. a very short debounce plus a slow network), guard against an older save's response landing after a newer one by including a monotonically increasing version/timestamp in each save and ignoring a response older than the latest one applied.
  • Status feedback. Derive "Saving…" from mutation.isPending, "Saved" from a brief window after onSuccess, and an inline error indicator from mutation.isError — all without blocking further typing.

Code Example

function useDraftField(noteId: string, initial: string) {
  const [value, setValue] = useState(initial);
  const saveMutation = useMutation({ mutationFn: (text: string) => api.saveDraft(noteId, text) });

  const debouncedSave = useMemo(
    () => debounce((text: string) => saveMutation.mutate(text), 800),
    [saveMutation]
  );

  const onChange = (text: string) => {
    setValue(text);       // instant local update, no network wait
    debouncedSave(text);  // fires once typing pauses; supersedes any pending call
  };

  useEffect(() => () => debouncedSave.cancel(), [debouncedSave]); // cleanup on unmount

  return { value, onChange, status: saveMutation.isPending ? "saving" : saveMutation.isSuccess ? "saved" : "idle" };
}

Senior Engineer Perspective

Interviewers probe the out-of-order-response edge case specifically: "what if the debounce is short and the network is slow enough that two saves overlap?" A thorough answer versions each save (or simply always trusts the latest debounced call and treats it as the pending source of truth) rather than assuming saves always resolve in the order they were sent.

SECTION 12 - SERVER STATE VS CLIENT STATE PHILOSOPHY

Q72. Why do general-purpose state managers like Redux or Zustand fall short for server state? Give a deep technical account.

ROI: ★★★★★ Frequency: Extremely High

Short Answer

Redux/Zustand are excellent at storing and updating values you own synchronously, but they have no built-in concept of "this data can go stale," "this data should refetch on some trigger," "these ten components asking for the same data should share one request," or "this data expired and should be evicted." Every one of those behaviors — the actual hard part of server data — has to be hand-built with thunks, middleware, and manual bookkeeping, which is exactly the boilerplate TanStack Query/SWR exist to eliminate.

Detailed Answer

Concretely, here is what you'd have to build by hand in a plain Redux store to match what a query library gives you for free:

  • Freshness tracking — a lastFetchedAt timestamp per entity/list, plus logic everywhere that reads it to decide whether to refetch.
  • Deduplication — a manual "is a fetch already in flight for this key" flag checked before every dispatch, to avoid firing the same request from two components.
  • Background revalidation triggers — window-focus and reconnect listeners wired to dispatch refetch actions, written and maintained by your team.
  • Garbage collection — logic to notice when no component needs a piece of cached data anymore and evict it, or the store just grows unbounded for the life of the session.
  • Retry/backoff, cancellation, pagination/infinite-list accumulation — all separately hand-rolled, all separately tested, all separately debugged when they inevitably have edge-case bugs.

None of this is impossible in Redux — it's just reinventing, one bug fix at a time, exactly what a purpose-built server-state cache already solved and battle-tested. The architectural insight is that server state isn't really "state" in the Redux sense at all; it's a local, disposable cache of remote truth, and caches have fundamentally different concerns (staleness, eviction, dedup) than state (ownership, mutation, history).

Project Example

A team I worked with had roughly 3,000 lines of Redux Toolkit slices, thunks, and selectors purely for server data — normalized entities, isLoading flags per resource, manually dispatched refetch-on-focus logic. Migrating that layer to TanStack Query, while leaving genuinely local UI state (selected tab, open modal, filter drafts) in a couple of small Zustand stores, deleted roughly 70% of that code and, more importantly, fixed a long-standing class of "list shows stale data after editing an item" bugs, because invalidation replaced several different hand-written cache-busting code paths.

Senior Engineer Perspective

This is the single highest-leverage philosophical question in the whole data-fetching space, and interviewers use it to gauge whether a candidate has actually internalized why these libraries exist, versus just knowing their API surface. The strongest answers walk through 3-4 concrete behaviors (staleness, dedup, background refetch, GC) rather than a vague "Redux is for client state, Query is for server state" one-liner.

Q73. What are common anti-patterns of mixing server and client state in one store?

ROI: ★★★★☆ Frequency: High

Short Answer

The most common anti-pattern is copying fetched data into a global client store (Redux/Zustand/Context) "just to have it available everywhere," then building ad hoc sync logic to keep that copy current with the server — recreating cache invalidation badly, by hand, without meaning to. A close second is deriving client-only UI state (a filtered/sorted view) and storing the derived result instead of the filter/sort criteria, so it drifts out of sync when the underlying server data changes.

Detailed Answer

  • Duplicating server data into a global store "for convenience." Once a copy exists in two places (the query cache and a Redux slice), someone eventually updates one without the other, and now the UI shows two different values for the same entity depending on which component reads which source.
  • Storing derived values instead of derivation inputs. Storing "the sorted list" (a snapshot) instead of "the sort key" plus a selector that sorts the live query data means the sorted view goes stale the moment the underlying data refetches, unless you remember to re-run the derivation everywhere it was stored — storing the input and deriving on read (or via select) avoids this entirely.
  • Putting loading/error flags for server requests in a global store by hand (state.isLoadingUsers) instead of reading them directly off the query hook — this duplicates exactly the bookkeeping the query library already does correctly, and it's easy to forget to reset a flag on one code path.
  • Treating form input state as server state. The inverse anti-pattern: wiring every keystroke of a form through a mutation/query cache round trip instead of keeping it as plain local/form-library state until an explicit save — server-state tools aren't built for per-keystroke synchronous updates.

Code Example

// Anti-pattern: duplicating + hand-syncing server data in Redux
// dispatch(setUsers(await fetchUsers())); // now two sources of truth to keep in sync

// Better: server data lives only in the query cache; the store holds just the UI concern
const sortKey = useUiStore((s) => s.userSortKey); // client state: which field to sort by
const { data: users } = useQuery({
  queryKey: ["users"],
  queryFn: fetchUsers,
  select: (data) => [...data].sort((a, b) => a[sortKey].localeCompare(b[sortKey])), // derived, always current
});

Senior Engineer Perspective

Ask a candidate to spot the bug in "we store the sorted list in Redux and re-sort it in a useEffect whenever the query refetches" — the effect is exactly the kind of manual sync-plumbing that select or a plain derived-on-render calculation removes entirely, and it's a very common real anti-pattern in codebases that adopted a query library without fully letting go of the old Redux-everything habits.

Q74. How do you decide what state belongs in the URL vs a client store vs the server cache?

ROI: ★★★★☆ Frequency: High

Short Answer

Ask three questions about a piece of state: Does it come from the server and represent remote truth? → server cache (query library). Should it survive a refresh and be shareable/bookmarkable? → URL. Is it purely ephemeral UI state local to the current session that no one needs to link to or persist? → a lightweight client store or component state.

Detailed Answer

Server cache (TanStack Query/SWR)Anything fetched from or written to a remote APIUser profile, todo list, search results

function ProductList() {
  const [searchParams, setSearchParams] = useSearchParams();

Q75. Should form state be server state or client state? Where does React Hook Form fit?

ROI: ★★★★☆ Frequency: High

Short Answer

In-progress form input is client state — it's local, synchronous, and owned entirely by the browser until submission; running it through a server-state cache on every keystroke would be both the wrong tool and far too slow. React Hook Form (or similar) manages that local, uncontrolled-by-default form state efficiently; a query/mutation library only enters the picture at the boundaries — fetching initial values to populate the form, and submitting the final values as a mutation.

Detailed Answer

  • Initial values: server state. Populate a form for editing an existing entity via a useQuery, then pass the fetched data into the form library's defaultValues (often via reset() once the query resolves, since the form typically mounts before the data arrives).
  • In-flight editing: client state. Every keystroke, checkbox toggle, and validation error while the user is filling out the form is local — React Hook Form deliberately keeps most fields uncontrolled and out of React's render cycle entirely for performance, which is the opposite of "sync every change to a cache."
  • Submission: a mutation. The final submit calls a useMutation, and its onSuccess/onError maps naturally onto the form's own success/error UI (see the validation-vs-transient-error question for mapping a 422 response onto React Hook Form's setError).
  • Draft-saving is the nuanced middle ground — a "save draft as you type" feature genuinely does synchronize form state to the server, but debounced and explicitly, not on every keystroke (see the debounced-mutation question) — it doesn't contradict the general rule so much as add an explicit, deliberate bridge between the two layers.

Code Example

function EditUserForm({ userId }: { userId: string }) {
  const { data: user } = useQuery({ queryKey: ["user", userId], queryFn: () => fetchUser(userId) });
  const { register, handleSubmit, reset, setError } = useForm<UserFormValues>();

  useEffect(() => { if (user) reset(user); }, [user, reset]); // server data seeds the form once

  const mutation = useMutation({
    mutationFn: (values: UserFormValues) => api.updateUser(userId, values),
    onSuccess: (updated) => queryClient.setQueryData(["user", userId], updated),
    onError: (error: ApiError) => {
      if (error.fieldErrors) Object.entries(error.fieldErrors).forEach(([f, m]) => setError(f as any, { message: m }));
    },
  });

  return <form onSubmit={handleSubmit((values) => mutation.mutate(values))}>{/* fields via register() */}</form>;
}

Senior Engineer Perspective

A subtle trap: candidates sometimes try to wire a form field directly to queryClient.setQueryData on every change, effectively using the cache as form state. That's backwards — it fights the form library's performance model and gives you no benefit, since the "cache" behavior (staleness, refetch, dedup) is irrelevant to data that hasn't even been saved yet.

Q77. Is Context a replacement for a server-state library? Why or why not?

ROI: ★★★★☆ Frequency: High

Short Answer

No — Context is a plumbing mechanism for passing a value down the tree without prop drilling; it has zero opinions about caching, staleness, refetching, deduplication, or garbage collection. Fetching data in a useEffect and exposing it via Context gives you the same naive-useEffect problems (races, no dedup, no cache) discussed at the start of this chapter, just moved one level up — Context solves "sharing," not "fetching correctly."

Detailed Answer

  • What Context actually does. Re-renders every consumer when the provided value changes, and lets nested components read a value without it being threaded through every intermediate component's props. That's it — a distribution mechanism, not a data-fetching or caching mechanism.
  • What it's missing for server state. No automatic refetch-on-focus, no deduplication of concurrent requests for the same data (a naive Context provider fetching in useEffect fetches once per provider instance, not once per unique key across the whole app), no stale/fresh distinction, no built-in retry/backoff, no garbage collection of unused data.
  • Where Context legitimately still fits alongside a query library. Distributing genuinely global, low-frequency-changing client state (theme, feature flags already fetched once, the current authenticated user object after it's been fetched via a query) — Context can wrap a query result for convenience, but the query library underneath is still doing the actual data-management work.
  • Performance trap. A single Context value re-renders every consumer on any change; a query cache's per-key subscription model (each component only re-renders for the specific key/selected slice it reads) is far more surgical — another reason not to funnel broad server data through one big Context value.

Code Example

// Anti-pattern: reinventing (badly) what a query library already solved
const UserContext = createContext<User | null>(null);
function UserProvider({ children }: { children: React.ReactNode }) {
  const [user, setUser] = useState<User | null>(null);
  useEffect(() => { fetchCurrentUser().then(setUser); }, []); // no cache, no dedup, no refetch, no retry
  return <UserContext.Provider value={user}>{children}</UserContext.Provider>;
}

// Better: let the query library manage the data; Context (if used at all) just wraps the result
function useCurrentUser() {
  return useQuery({ queryKey: ["currentUser"], queryFn: fetchCurrentUser, staleTime: 5 * 60_000 });
}

Q78. How do you avoid "prop drilling" server state without reaching for a global store?

ROI: ★★★☆☆ Frequency: Medium

Short Answer

You generally don't need to — any component anywhere in the tree can call the same query hook with the same key and get the same cached data instantly, without it being passed down as a prop at all. "Prop drilling server state" is usually a sign the data is being fetched once at a high level and threaded down, when instead each component that needs it should just fetch (i.e., read from cache) it itself via its own useQuery call.

Detailed Answer

  • Re-fetching isn't re-requesting. The instinct to avoid "wasteful" duplicate fetches by lifting one fetch to a common ancestor and passing the result down as props is a leftover habit from before shared caching existed — with a query cache, calling the same hook in five different components produces one network request (via dedup) and five instances of a component each independently, trivially accessing the same data.
  • Wrap in a named hook per resource (useCurrentUser(), useOrder(id)) so any component can import and call it directly, rather than needing the data threaded in from a parent that happens to have fetched it first.
  • When you genuinely do need a single shared instance of something computed from server data (e.g. a single WebSocket connection, not per-component), that's a case for a Context provider around the *connection*, while the data it produces still flows through the query cache as normal.

Code Example

// Instead of fetching once at the top and drilling `user` through five components:
function useCurrentUser() {
  return useQuery({ queryKey: ["currentUser"], queryFn: fetchCurrentUser, staleTime: 5 * 60_000 });
}

// Any component, at any depth, just calls the hook directly -- one shared cache entry, one request:
function Avatar() {
  const { data: user } = useCurrentUser();
  return <img src={user?.avatarUrl} />;
}
function SettingsGreeting() {
  const { data: user } = useCurrentUser(); // deduped against Avatar's request automatically
  return <p>Welcome back, {user?.name}</p>;
}

Senior Engineer Perspective

This question catches candidates still thinking in pre-query-cache patterns — the tell is proposing a Context provider purely to avoid "an extra fetch," when the query cache already makes that concern moot. The correct instinct is "let each component ask for what it needs" rather than "fetch once and pass it down."

Q79. How do you implement adaptive polling that backs off when the tab is hidden and speeds up on activity?

ROI: ★★★★☆ Frequency: High

Short Answer

Make refetchInterval a function of the query's own state (and, via a small piece of external state, page visibility) instead of a fixed number — poll fast while the tab is visible and the data is actively relevant, and slow way down or stop entirely while the tab is hidden, resuming normal speed the moment it becomes visible again. Combine this with refetchIntervalInBackground: false (the default) so background tabs don't burn requests at all.

Detailed Answer

  • refetchIntervalInBackground — false by default, meaning the interval simply pauses while the document is hidden (per the Page Visibility API) and TanStack Query already handles catching back up via refetchOnWindowFocus when it becomes visible again; explicitly setting it true is only for cases that genuinely need background polling (rare, and battery/data-costly).
  • Function-based interval for adaptive speed. refetchInterval: (query) => ... receives the current query state, so you can poll every 2s while a job is "processing," switch to every 30s once it's "queued" (lower urgency), and return false entirely once it's "done."
  • Activity-based speed-up. For "poll faster while the user is actively interacting" (e.g. a live-updating comment thread they're currently scrolled into), combine the interval function with a small piece of external state (an IntersectionObserver flag for "is this widget in view") captured in a ref the interval function can read.

Code Example

function useJobStatus(jobId: string) {
  return useQuery({
    queryKey: ["job", jobId],
    queryFn: () => fetchJob(jobId),
    refetchInterval: (query) => {
      const status = query.state.data?.status;
      if (status === "done" || status === "failed") return false; // stop entirely
      if (status === "processing") return 2_000;                  // urgent: poll fast
      return 30_000;                                              // queued/idle: poll slowly
    },
    refetchIntervalInBackground: false, // default -- pause while the tab is hidden
  });
}

Senior Engineer Perspective

The signal interviewers want is treating polling frequency as a function of actual urgency and visibility, not a single hardcoded number for the whole lifecycle — a fixed 2-second poll running for a job that's sitting in a queue for 20 minutes, or continuing at full speed in a hidden background tab, is a real, common source of unnecessary backend load.

Q80. How do you integrate Server-Sent Events (SSE) with a query cache in detail?

ROI: ★★★★☆ Frequency: High

Short Answer

Open an EventSource connection (typically in a top-level provider or a dedicated hook, not per-component), and on each message write the update into the relevant query's cache via setQueryData — the same cache that ordinary fetches populate — so every component reading that query re-renders with the pushed data automatically, with no separate "realtime state" to keep in sync. EventSource reconnects automatically on a dropped connection, which is one of SSE's built-in advantages over raw WebSockets.

Detailed Answer

  • Connection lifecycle. Open in a useEffect (or a module/context-level singleton if many components would otherwise each open their own connection to the same stream), close in cleanup. A single shared connection per logical stream, feeding the cache, is preferable to one connection per component.
  • Message → cache write. Parse each message event's payload and route it to the correct query key's cache entry via setQueryData, typically merging/appending rather than replacing wholesale (e.g. appending a new notification to a cached list).
  • Auto-reconnect is built in to EventSource — the browser retries with its own backoff on a dropped connection, and you can read event.lastEventId to support resuming from where you left off if your server supports the Last-Event-ID header for gap recovery.
  • Named event types. SSE supports distinct event names (addEventListener("notification", ...) vs the default message) so a single connection can carry several logical update types, each routed to a different cache key.

Code Example

function useNotificationStream() {
  const queryClient = useQueryClient();
  useEffect(() => {
    const source = new EventSource("/api/notifications/stream");

    source.addEventListener("notification", (event) => {
      const notification: Notification = JSON.parse(event.data);
      queryClient.setQueryData<Notification[]>(["notifications"], (old = []) => [notification, ...old]);
    });

    source.onerror = () => {
      // EventSource auto-reconnects on its own; log/telemetry only, no manual retry needed here
      console.warn("Notification stream disconnected, browser will retry");
    };

    return () => source.close();
  }, [queryClient]);
}

Senior Engineer Perspective

Interviewers check whether you'll build a parallel realtime state store instead of routing pushed updates through the same cache ordinary queries use — the strong answer is explicit that the cache is the single source of truth regardless of whether data arrived via fetch or push, so every component behaves identically either way.

Q81. How do you integrate WebSockets with reconnect/backoff and resubscription logic?

ROI: ★★★★☆ Frequency: High

Short Answer

Unlike EventSource, raw WebSockets don't reconnect automatically — you must detect onclose/onerror, reconnect with exponential backoff, and, once reconnected, re-send any subscription messages the server needs (e.g. "subscribe to room 123") since a fresh connection starts with no server-side subscription state. Route incoming messages into the query cache exactly as with SSE.

Detailed Answer

  • Manual reconnect loop. On onclose, schedule a reconnect attempt with backoff (same exponential-with-cap principle as query retries), and track a "give up after N attempts, show an offline indicator" ceiling rather than retrying forever silently.
  • Resubscription after reconnect. A new WebSocket connection is a blank slate server-side — any "subscribe to this room/channel" message you sent on the old connection must be resent on the new one, typically tracked in a small local set of "currently subscribed channels" that gets replayed on every successful (re)connection.
  • Gap detection. If messages can be missed while disconnected, include a sequence number or version per message and, on reconnect, either request a resync (a REST call for "give me the current state" to reconcile) or accept the small gap for low-stakes data.
  • Many teams use a library (e.g. reconnecting-websocket, socket.io's client) that already implements this reconnect/backoff/resubscribe machinery rather than hand-rolling it, reserving custom code for the cache-integration layer on top.

Code Example

function useRoomSocket(roomId: string) {
  const queryClient = useQueryClient();
  useEffect(() => {
    let ws: WebSocket;
    let attempt = 0;
    let closedByCleanup = false;

    function connect() {
      ws = new WebSocket(`wss://api.example.com/rooms/${roomId}`);

      ws.onopen = () => {
        attempt = 0;
        ws.send(JSON.stringify({ type: "subscribe", roomId })); // resubscribe on every (re)connect
      };

      ws.onmessage = (e) => {
        const msg: Message = JSON.parse(e.data);
        queryClient.setQueryData<Message[]>(["messages", roomId], (old = []) => [...old, msg]);
      };

      ws.onclose = () => {
        if (closedByCleanup) return;
        const delay = Math.min(1000 * 2 ** attempt++, 15_000); // manual backoff, WebSocket has none built in
        setTimeout(connect, delay);
      };
    }

    connect();
    return () => { closedByCleanup = true; ws.close(); };
  }, [roomId, queryClient]);
}

Senior Engineer Perspective

The detail that separates a real answer from a surface one: naming resubscription explicitly. Many candidates handle reconnect but forget that a brand-new socket has no memory of what channels the old one had subscribed to — without resending that subscribe message, a "successfully reconnected" UI can silently receive zero further messages.

Q82. How do you reconcile out-of-order realtime messages using a version or sequence number?

ROI: ★★★☆☆ Frequency: Medium

Short Answer

Network reordering, retried sends, or reconnect-replay can deliver realtime messages out of the order they were produced. Attach a monotonically increasing sequence number (or a server timestamp) to every message, and when applying an update to the cache, compare it against the last-applied version for that entity — discard (or hold and reorder) any message whose version is not newer than what's already applied.

Detailed Answer

  • Per-entity version tracking. Store the last-applied sequence number alongside the entity itself (or in a small parallel map) so an incoming message can be checked against exactly the right baseline, not a single global counter that doesn't reflect per-entity update order.
  • Discard vs buffer-and-reorder. For most UI purposes (a live counter, a status field), simply discarding an out-of-order message that's older than what's already shown is sufficient and simple — the entity's true current value will arrive in a subsequent message anyway. For strict ordering requirements (a chat transcript), buffer out-of-order messages briefly and insert them once the gap is filled, or request a resync.
  • Combine with polling/REST fallback. If a gap is detected (sequence jumped from 5 to 9), it's often simpler to trigger a plain invalidateQueries to refetch the authoritative current state via REST than to try to reconstruct the missing messages 6-8 from the realtime channel alone.

Code Example

function applyRealtimeUpdate(queryClient: QueryClient, update: { entityId: string; version: number; data: Entity }) {
  queryClient.setQueryData<Entity & { __version?: number }>(
    ["entity", update.entityId],
    (old) => {
      if (old?.__version && old.__version >= update.version) return old; // stale/out-of-order, ignore
      return { ...update.data, __version: update.version };
    }
  );
}

Senior Engineer Perspective

This question probes whether a candidate assumes realtime messages always arrive in order — a dangerous assumption. Naming a concrete strategy (per-entity version comparison, discard-if-stale) rather than "usually it's fine" is the mark of someone who's actually debugged a flickering realtime UI in production.

Q83. How do you avoid render thrashing when realtime updates arrive rapidly?

ROI: ★★★☆☆ Frequency: Medium

Short Answer

Calling setQueryData (which notifies observers and triggers a re-render) on every single incoming message during a burst — dozens per second from a busy chat room or a live trading feed — can overwhelm the render pipeline. Batch incoming messages over a short window (e.g. via requestAnimationFrame or a small debounce/throttle) and apply them to the cache as one combined update instead of one cache write per message.

Detailed Answer

  • Buffer, then flush. Accumulate incoming messages in a ref-backed array as they arrive, and flush the buffer into the cache on a fixed interval or via requestAnimationFrame (aligning writes with the browser's paint cycle) rather than synchronously on every message.
  • React's automatic batching helps for updates that happen within the same synchronous task (React 18+ batches these by default), but messages arriving as separate WebSocket event callbacks over time are each their own task and are not batched together automatically — hence the need for your own buffering layer for a true high-frequency stream.
  • Virtualize the rendered list (see the infinite-list virtualization question) so that even once the cache does update, only the visible rows actually re-render, bounding the cost regardless of how large the underlying dataset has grown.
  • Consider dropping intermediate states for data where only the latest value matters (a live price ticker) — you don't need to render every tick, only the most recent one at your target frame rate.

Code Example

function useBatchedMessageStream(roomId: string) {
  const queryClient = useQueryClient();
  const bufferRef = useRef<Message[]>([]);

  useEffect(() => {
    const ws = new WebSocket(`wss://api.example.com/rooms/${roomId}`);
    ws.onmessage = (e) => { bufferRef.current.push(JSON.parse(e.data)); }; // just buffer, don't write yet

    let rafId: number;
    const flush = () => {
      if (bufferRef.current.length > 0) {
        const batch = bufferRef.current;
        bufferRef.current = [];
        queryClient.setQueryData<Message[]>(["messages", roomId], (old = []) => [...old, ...batch]); // one write for the whole batch
      }
      rafId = requestAnimationFrame(flush);
    };
    rafId = requestAnimationFrame(flush);

    return () => { ws.close(); cancelAnimationFrame(rafId); };
  }, [roomId, queryClient]);
}

Senior Engineer Perspective

Interviewers use this to distinguish "I've built a realtime demo" from "I've built a realtime feature under real load" — a chat demo with occasional messages never surfaces this problem, but a busy trading floor or high-traffic chat room will visibly stutter without batching. Naming requestAnimationFrame-aligned flushing specifically (versus a naive fixed-ms debounce) shows attention to actual frame-budget performance.

Q84. How do you combine a polling fallback with a WebSocket primary channel for graceful degradation?

ROI: ★★★☆☆ Frequency: Medium

Short Answer

Try to establish the WebSocket connection; while it's connected and healthy, disable/pause polling entirely (since push updates make it redundant). If the socket fails to connect, repeatedly disconnects, or the environment blocks WebSockets (a restrictive corporate proxy), fall back to polling at a reasonable interval so the feature still works, just with higher latency — and keep attempting to re-establish the socket in the background so you can drop back to push-based updates once possible.

Detailed Answer

  • Single source of truth regardless of channel. Both the WebSocket handler and the polling query write into the exact same cache key — components never know or care which channel produced the current data, they just read the query result.
  • State machine for channel selection. Track a small enum ("connecting" | "connected" | "degraded-polling") driving whether refetchInterval is active: enabled while degraded/connecting, effectively disabled (false, or a very long interval) while the socket is confirmed connected and healthy.
  • Avoid double-updates while both are briefly active during the transition (e.g. right as the socket reconnects but a poll is still in flight) — a version/sequence check (see the out-of-order question) naturally protects against a stale poll response overwriting fresher socket-delivered data or vice versa.

Q85. How do you test components that rely on polling or realtime data?

Q86. How do you prefetch on route transition using React Router or TanStack Router loaders?

ROI: ★★★★★ Frequency: Extremely High

Short Answer

Route loaders let you start fetching a route's data the moment navigation begins — in parallel with the route's code chunk downloading — rather than waiting for the destination component to mount and only then firing its useQuery. In React Router, a route's loader function can call queryClient.ensureQueryData; TanStack Router integrates even more tightly, treating the query cache as the loader's data source directly.

Detailed Answer

  • Why this beats component-mount fetching. Without a loader, the sequence is: navigate → download route's JS chunk → mount component → useQuery fires → request starts. With a loader, the data request and the JS chunk download happen concurrently, shaving a full round trip off perceived load time.
  • ensureQueryData in a loader. It returns cached data immediately if fresh, or fetches and caches it if missing/stale — exactly the semantics a loader wants (don't refetch if we already prefetched this on hover, but do fetch if this is a cold navigation).
  • Component still uses useQuery normally with the same key the loader used — because it's the same cache entry, the component receives the already-resolved data instantly instead of loading twice.
  • TanStack Router's tighter integration lets loaders be defined per-route with typed params flowing directly into query key builders, reducing the boilerplate of keeping the loader's key and the component's key manually in sync.

Code Example

// React Router v6.4+ data router
const routes = [
  {
    path: "/todos/:id",
    loader: async ({ params }) =>
      queryClient.ensureQueryData({
        queryKey: todoKeys.detail(params.id!),
        queryFn: () => fetchTodo(params.id!),
      }),
    Component: TodoDetail,
  },
];

function TodoDetail() {
  const { id } = useParams();
  // Same key as the loader -> already resolved by the time this mounts, no loading flash
  const { data } = useQuery({ queryKey: todoKeys.detail(id!), queryFn: () => fetchTodo(id!) });
  return <h1>{data?.title}</h1>;
}

Senior Engineer Perspective

The follow-up interviewers ask: "doesn't the component's useQuery refetch anyway?" No — because it uses the identical query key, it reads the same cache entry the loader already populated, subject to normal staleTime rules, so there's no redundant request unless the data is genuinely stale by the time the component reads it.

Q87. How do you prefetch on hover/focus intent, and what's the cost/benefit tradeoff?

ROI: ★★★★☆ Frequency: High

Short Answer

Call queryClient.prefetchQuery in an onMouseEnter/onFocus handler on a link, so the network request for the destination's data starts the moment the user shows intent to navigate — well before the actual click. The trade-off: it costs extra requests for hovers that never turn into clicks, so it's best applied to cheap, likely-to-be-followed links (not every row in a 500-item table) and should be debounced against rapid mouse movement across many links.

Detailed Answer

  • Debounce the trigger. A user's mouse passing over ten list rows on the way to the one they actually want to click shouldn't fire ten prefetches — add a short delay (e.g. 100-200ms) before firing, cancelled if the pointer leaves before it elapses.
  • Respect staleTime to avoid wasted requests. prefetchQuery already checks freshness — if the data is still fresh from a previous fetch, it won't refetch, so hovering the same link repeatedly doesn't repeatedly hit the network.
  • Cost side. Every prefetch that never leads to a click is a wasted request — on metered connections or expensive endpoints, weigh this against the perceived-latency win. Reserve aggressive hover-prefetching for high-intent surfaces (a search-results list) rather than blanket-applying it everywhere.
  • Focus, not just hover, matters for keyboard/touch users who never trigger a mouse hover event — pairing onFocus with onMouseEnter covers both input modes.

Code Example

function PrefetchLink({ id, children }: { id: string; children: React.ReactNode }) {
  const queryClient = useQueryClient();
  const timeoutRef = useRef<number>();

  const prefetch = () => {
    timeoutRef.current = window.setTimeout(() => {
      queryClient.prefetchQuery({ queryKey: todoKeys.detail(id), queryFn: () => fetchTodo(id) });
    }, 150); // debounce against rapid pointer movement
  };
  const cancelPrefetch = () => window.clearTimeout(timeoutRef.current);

  return (
    <Link to={`/todos/${id}`} onMouseEnter={prefetch} onMouseLeave={cancelPrefetch} onFocus={prefetch}>
      {children}
    </Link>
  );
}

Q88. How do you use useSuspenseQueries to keep suspense-based fetching parallel?

ROI: ★★★★☆ Frequency: High

Short Answer

Calling multiple separate useSuspenseQuery hooks in the same component creates a waterfall, because each one suspends the component's render before the next hook even executes — the second query doesn't start until the component re-attempts rendering after the first resolves. useSuspenseQueries takes an array of query configs and fires all of them concurrently, suspending once until every one of them has resolved.

Detailed Answer

  • Why sequential useSuspenseQuery calls waterfall. The component function itself doesn't run past the first hook that suspends — React throws the pending promise and unmounts/retries the component later, meaning any hook calls textually after the suspended one simply haven't executed yet, so their fetches haven't started.
  • useSuspenseQueries fixes this by issuing every query's fetch immediately, together, and suspending the component only once — when the render resumes, all results are ready simultaneously.
  • Same fix, non-suspense world. This mirrors exactly why plain useQueries (not suspense) is preferred over multiple separate useQuery calls when you specifically want to guarantee parallelism for a dynamic list — the suspense and non-suspense APIs have a matching "batch these together" escape hatch.

Code Example

// WRONG under Suspense: this waterfalls -- the posts query doesn't start until user resolves
function Profile({ userId }: { userId: string }) {
  const { data: user } = useSuspenseQuery({ queryKey: ["user", userId], queryFn: () => fetchUser(userId) });
  const { data: posts } = useSuspenseQuery({ queryKey: ["posts", userId], queryFn: () => fetchPosts(userId) });
  return <ProfileView user={user} posts={posts} />;
}

// CORRECT: both fetches fire together, one suspension for both
function Profile({ userId }: { userId: string }) {
  const [{ data: user }, { data: posts }] = useSuspenseQueries({
    queries: [
      { queryKey: ["user", userId], queryFn: () => fetchUser(userId) },
      { queryKey: ["posts", userId], queryFn: () => fetchPosts(userId) },
    ],
  });
  return <ProfileView user={user} posts={posts} />;
}

Senior Engineer Perspective

This is one of the sharpest "do you actually understand Suspense mechanics" questions in the whole chapter — many candidates assume Suspense automatically parallelizes independent fetches simply because it "handles loading," when in fact naive sequential useSuspenseQuery calls are a textbook waterfall that useSuspenseQueries exists specifically to prevent.

Q89. How do you combine Next.js SSR hydration with TanStack Query using dehydrate/hydrate?

ROI: ★★★★☆ Frequency: High

Short Answer

On the server, create a request-scoped QueryClient, prefetch the queries the page needs, then serialize its cache with dehydrate(queryClient) and embed that in the HTML response. On the client, wrap the app in <HydrationBoundary state={dehydratedState}>, which seeds a fresh client-side QueryClient with that exact server-fetched data — so the first client render already has the data with zero loading flash, and normal client-side revalidation takes over from there.

Detailed Answer

  • Request-scoped client on the server. Never reuse a single module-level QueryClient across requests on the server — each request needs its own, or you leak one user's cached data into another user's response.
  • Prefetch, then dehydrate. Call queryClient.prefetchQuery(...) for each query the page needs before rendering, then pass dehydrate(queryClient) to the page/component tree as the serialized snapshot.
  • HydrationBoundary merges, not replaces. On the client, it seeds the client's QueryClient with the dehydrated data as if those queries had just been fetched — subsequent client-side useQuery calls with matching keys see that data immediately, and normal staleTime-driven revalidation applies from that point forward exactly as it would for any client-fetched data.
  • Only serializable data survives dehydration — errors, functions, and non-JSON-safe values in query data need special handling or exclusion, same caveat as persisted-cache serialization.

Code Example

// Server component (Next.js App Router)
export default async function Page({ params }: { params: { id: string } }) {
  const queryClient = new QueryClient(); // fresh, request-scoped

  await queryClient.prefetchQuery({
    queryKey: todoKeys.detail(params.id),
    queryFn: () => fetchTodo(params.id),
  });

  return (
    <HydrationBoundary state={dehydrate(queryClient)}>
      <TodoDetailClient id={params.id} />
    </HydrationBoundary>
  );
}

// Client component -- same key, data already present, no loading flash
"use client";
function TodoDetailClient({ id }: { id: string }) {
  const { data } = useQuery({ queryKey: todoKeys.detail(id), queryFn: () => fetchTodo(id) });
  return <h1>{data?.title}</h1>;
}

Senior Engineer Perspective

The critical detail interviewers check: a fresh QueryClient per server request. Reusing a singleton across requests on the server is a real, serious bug class (cross-user data leakage) — candidates who haven't shipped SSR data-fetching sometimes miss this entirely and reach for a module-level client out of habit from the client-side singleton pattern.

Q90. How do you prefetch data for the next page of a paginated list before the user clicks "next"?

ROI: ★★★★☆ Frequency: High

Short Answer

After the current page's data loads, fire a queryClient.prefetchQuery for page + 1 in the background (e.g. in a useEffect keyed on the current page), so by the time the user clicks "next," that page is already warm in the cache and the transition — combined with placeholderData: keepPreviousData — feels instantaneous rather than showing a fresh loading state.

Detailed Answer

  • Only prefetch when you have a next page. Guard with whatever "is there a next page" signal your API provides (a hasMore flag or a known totalPages) so you don't waste a request prefetching past the last page of the data.
  • Respect the same staleTime. prefetchQuery checks freshness like any other fetch — if page 2 was already prefetched and is still fresh, navigating forward and back repeatedly doesn't refire the request each time.
  • Combine with keepPreviousData. Prefetching removes the loading spinner for forward navigation; placeholderData: keepPreviousData keeps the current page's content visible during the brief moment between click and the (often already-resolved) next page rendering — together they make pagination feel seamless.

Code Example

function TodoListPage() {
  const [page, setPage] = useState(1);
  const queryClient = useQueryClient();

  const { data } = useQuery({
    queryKey: ["todos", "page", page],
    queryFn: () => fetchTodos(page),
    placeholderData: keepPreviousData,
  });

  useEffect(() => {
    if (data?.hasMore) {
      queryClient.prefetchQuery({
        queryKey: ["todos", "page", page + 1],
        queryFn: () => fetchTodos(page + 1),
      });
    }
  }, [page, data?.hasMore, queryClient]);

  return <TodoTable todos={data?.items} onNext={() => setPage((p) => p + 1)} />;
}

Q91. What's the interaction between Suspense, ErrorBoundary, and retry — how do you avoid an infinite fallback loop?

ROI: ★★★☆☆ Frequency: Medium

Short Answer

useSuspenseQuery always throws on error (there's no opt-out), so it must always be paired with an ErrorBoundary, not just a Suspense boundary — a suspense-only setup with no error boundary above it will crash the app on any query failure. Retries happen automatically before the error is thrown to the boundary (per the query's retry option) — so by the time the boundary actually sees an error, retries are already exhausted; a naive "retry" button that just re-renders the same children without resetting the query's error state will re-throw immediately, looking like an infinite loop.

Detailed Answer

  • Ordering: retries happen inside the query, before the throw. The library exhausts retry attempts first; only after all retries fail does useSuspenseQuery actually throw the error for the boundary to catch. So an ErrorBoundary firing means genuine, retry-exhausted failure, not a transient blip.
  • The "infinite loop" isn't really infinite — it's a stuck error. If a user clicks "retry" in the fallback and the boundary just re-renders its children, the underlying query is still in its error status (nothing told it to try again), so useSuspenseQuery throws the same stale error immediately — it looks like the retry button does nothing, or "loops," because no new fetch attempt actually happened.
  • The fix is QueryErrorResetBoundary (introduced earlier in this chapter for throwOnError) — its reset() clears the query's error state before the boundary's fallback resets, so the subsequent re-render genuinely re-suspends and re-fetches instead of re-throwing the same cached error.

Code Example

<QueryErrorResetBoundary>
  {({ reset }) => (
    <ErrorBoundary
      onReset={reset}                       // clears the query's error state, not just the boundary's
      fallbackRender={({ resetErrorBoundary }) => (
        <div>
          <p>Something went wrong.</p>
          <button onClick={resetErrorBoundary}>Retry</button>
        </div>
      )}
    >
      <Suspense fallback={<Skeleton />}>
        <Report id={id} />   {/* useSuspenseQuery inside -- always throws on exhausted-retry error */}
      </Suspense>
    </ErrorBoundary>
  )}
</QueryErrorResetBoundary>

Senior Engineer Perspective

This question is really testing whether a candidate has actually debugged a "my retry button does nothing" bug — the root cause (the query's own error state persisting until explicitly reset) is subtle and not obvious from the API surface alone, which is exactly why interviewers use it to separate hands-on experience from surface-level familiarity.

Q92. How do you use queryClient.ensureQueryData vs prefetchQuery?

ROI: ★★★☆☆ Frequency: Medium

Short Answer

Both fetch-and-cache a query if it's missing/stale, but prefetchQuery returns a promise that resolves to void — it's fire-and-forget, meant for warming the cache without needing the result right there (hover prefetch, side-channel warming). ensureQueryData returns a promise that resolves with the actual data, awaited synchronously by the caller — the right choice inside a route loader, where you genuinely need the data (or at least need to guarantee it's cached) before proceeding.

Detailed Answer

  • prefetchQuery — "start this fetch and cache it, I don't need the result in this scope." Perfect for hover/focus intent-prefetching and next-page prefetching, where the calling code doesn't consume the data directly, only warms the cache for a component that will read it later via its own useQuery.
  • ensureQueryData — "give me this data, fetching it if necessary, but don't refetch if it's already fresh in the cache." Ideal for loaders, where the loader function's return value often feeds directly into the route (or is simply awaited to guarantee the cache is populated before the component mounts).
  • Both respect staleTime. Neither refetches unnecessarily if the cached data is still fresh — the difference is purely about whether the caller needs the resolved value or just needs the caching side effect.

Code Example

// Fire-and-forget warming -- caller doesn't need the value
function TodoLink({ id }: { id: string }) {
  const queryClient = useQueryClient();
  return (
    <Link
      to={`/todos/${id}`}
      onMouseEnter={() => queryClient.prefetchQuery({ queryKey: todoKeys.detail(id), queryFn: () => fetchTodo(id) })}
    >
      View
    </Link>
  );
}

// Loader genuinely needs the resolved value (or at minimum, to guarantee it's cached before continuing)
const loader = async ({ params }: LoaderFunctionArgs) =>
  queryClient.ensureQueryData({ queryKey: todoKeys.detail(params.id!), queryFn: () => fetchTodo(params.id!) });

Senior Engineer Perspective

A precise answer distinguishes "I need the value" from "I just need the cache warmed" as the actual deciding factor, rather than treating the two APIs as interchangeable synonyms — that precision is what interviewers are listening for on an API-nuance question like this.

Q93. How do you architect prefetching in a component library / design system context via headless prefetch hooks?

ROI: ★★★☆☆ Frequency: Medium

Short Answer

A shared component library can't hardcode app-specific query keys or fetch functions, so expose prefetching as a configurable hook/callback the consuming app supplies — the library's <Link>-like component calls an injected onIntent callback on hover/focus, and each consuming app wires that callback to its own queryClient.prefetchQuery call with its own keys. This keeps the design system decoupled from any specific data-fetching library or schema.

Detailed Answer

  • Inversion of control. The library-level component exposes an onHoverIntent/onFocusIntent prop (or a headless hook returning event handlers to spread onto any element) rather than importing a specific QueryClient or knowing about TanStack Query at all — this keeps the design system usable in apps that use SWR, Apollo, or nothing.
  • Debounce lives in the library, keys live in the app. The shared component can own generic UX concerns (the intent-detection debounce timing) while remaining agnostic about what actually happens when intent fires — a clean separation between "when should we signal intent" (library concern) and "what do we fetch" (app concern).
  • Composable with existing patterns. Each app's usage of the shared component just plugs in the same prefetchQuery call it would have written directly — the shared component adds structure (consistent debounce, consistent event wiring) without dictating a specific data layer.

Code Example

// design-system package: no knowledge of TanStack Query, just an intent callback
function usePrefetchOnIntent(onIntent: () => void, delay = 150) {
  const timeoutRef = useRef<number>();
  return {
    onMouseEnter: () => { timeoutRef.current = window.setTimeout(onIntent, delay); },
    onMouseLeave: () => window.clearTimeout(timeoutRef.current),
    onFocus: onIntent,
  };
}

// consuming app: supplies the actual query key/fetcher
function TodoLink({ id }: { id: string }) {
  const queryClient = useQueryClient();
  const intentHandlers = usePrefetchOnIntent(() =>
    queryClient.prefetchQuery({ queryKey: todoKeys.detail(id), queryFn: () => fetchTodo(id) })
  );
  return <Link to={`/todos/${id}`} {...intentHandlers}>View</Link>;
}
