SECTION 1 - COMPOSITION PATTERNS

Q1. What does "composition over inheritance" mean in React, and why does React strongly favour it?

ROI: ★★★★★ Frequency: Extremely High

Short Answer

React components reuse behaviour by containing or combining other components and by receiving children/props — not by subclassing. React deliberately offers no first-class inheritance mechanism for components because composition is more flexible, avoids fragile base-class hierarchies, and maps cleanly onto the "UI is a function of props" mental model. When you need to share non-visual logic, you extract a custom hook rather than a base class.

Detailed Answer

In classical OOP you might reach for inheritance to share behaviour: a Dialog extends a Modal extends a Overlay. React explicitly steers you away from this. The React team has stated they have never found a use case where inheritance across components was superior to composition.

The three levers of composition

  • Containment — a generic component (a Card, a Panel) does not know its children ahead of time and simply renders props.children.
  • Specialization — a specific component renders a generic one with preset props (a WelcomeDialog renders a Dialog with a fixed title). This is what inheritance would have given you, done with composition instead.
  • Logic reuse via hooks — shared stateful behaviour (useToggle, usePagination) lives in a function, not a superclass.

Why this wins: inheritance couples the child to the internal structure of the parent class (the "fragile base class" problem). Composition couples only to a public prop contract, which is far easier to reason about and refactor. It also composes without limit — you can wrap, slot, and nest freely, whereas a class can only extend one parent.

Code Example

// Containment: the generic component doesn't know what goes inside
function Card({ title, children }: { title: string; children: React.ReactNode }) {
  return (
    <section className="card">
      <h3>{title}</h3>
      <div className="card-body">{children}</div>
    </section>
  );
}

// Specialization: instead of `class UserCard extends Card`, we compose
function UserCard({ user }: { user: User }) {
  return (
    <Card title={user.name}>
      <Avatar src={user.avatar} />
      <p>{user.bio}</p>
    </Card>
  );
}

Project Example

On a dashboard I built, every metric widget shared a chrome (title bar, loading skeleton, error state, refresh button). The junior instinct was a BaseWidget class the others extend. Instead we made a <Widget> that took title, onRefresh and children, and each concrete widget (RevenueWidget, UsersWidget) composed it. Adding a new widget became a five-line file, and changing the chrome touched exactly one component.

Senior Engineer Perspective

The interviewer wants to hear you say the words "custom hook" for logic reuse and "children / props" for markup reuse — many candidates conflate the two. A common trap follow-up: "But what if two components share a huge amount of logic AND markup?" The senior answer is a compound/headless component plus a hook, not a base class. Also flag that "composition" in React does not mean React.Children gymnastics by default — reach for the simplest lever (children) first.

Q2. Explain the container/presentational (smart/dumb) component split. Is it still relevant?

ROI: ★★★★☆ Frequency: High

Short Answer

The pattern splits a component into a container that owns data-fetching and state, and a presentational component that only receives props and renders UI. It was hugely popular in the class-component era (circa 2015, popularised by Dan Abramov) to separate concerns and make presentational components easy to test and reuse. Hooks largely dissolved the hard rule: you can now colocate logic in a custom hook without a wrapper component, so the strict split is less emphasized today, though the underlying principle — separate data concerns from rendering — is still sound.

Detailed Answer

The original motivation: in the class era there was no clean way to reuse stateful logic, so people isolated it into "container" classes and kept a pool of pure, props-only "presentational" components that were trivial to test and Storybook.

AspectContainerPresentational
ConcernHow things work (data, state)How things look (markup, styles)
Data sourceFetches, subscribes, dispatchesReceives via props
StateOwns app/server stateAt most UI-local state
ReusabilityLow (tied to a feature)High (generic)

Why it faded

Dan Abramov himself added a note to his original article saying he no longer recommends splitting it as a rule, precisely because Hooks let you extract stateful logic without an artificial container component. Today the equivalent is: a leaf component that renders, plus a useUsers() hook it calls, plus data libraries like TanStack Query that make "container" boilerplate disappear.

What survives is the discipline: keep components that talk to the network or a store thin, keep rendering components easy to test with plain props, and don't scatter fetch calls through your JSX tree.

Code Example

// OLD: explicit container + presentational split
function UserListContainer() {
  const [users, setUsers] = useState<User[]>([]);
  useEffect(() => { fetchUsers().then(setUsers); }, []);
  return <UserList users={users} />;        // presentational
}
function UserList({ users }: { users: User[] }) {
  return <ul>{users.map(u => <li key={u.id}>{u.name}</li>)}</ul>;
}

// MODERN: logic lives in a hook, no wrapper component needed
function useUsers() {
  return useQuery({ queryKey: ['users'], queryFn: fetchUsers });
}
function UserList() {
  const { data: users = [], isLoading } = useUsers();
  if (isLoading) return <Spinner />;
  return <ul>{users.map(u => <li key={u.id}>{u.name}</li>)}</ul>;
}

Senior Engineer Perspective

Say clearly that the pattern is not "wrong," it's just no longer a mandate — that nuance separates seniors from candidates repeating a 2016 blog post as gospel. The trap: interviewers may ask "so is the split useless now?" No — the boundary is still valuable at scale (a design-system component library should stay presentational/props-only so it's portable and Storybook-able). What changed is you rarely create a component solely to hold state; hooks do that job.

Q3. What is a Higher-Order Component (HOC)? Build one, and discuss its pros and cons.

ROI: ★★★★☆ Frequency: High

Short Answer

A Higher-Order Component is a function that takes a component and returns a new component with extra props or behaviour injected — withAuth(Dashboard). It was the dominant cross-cutting-concern pattern before hooks (think connect() from React-Redux). It still appears for wrapping/enhancing (analytics, error boundaries, theming) but for pure logic sharing hooks have replaced it because HOCs cause wrapper hell, prop-name collisions and opaque prop origins.

Detailed Answer

An HOC is just the decorator pattern for components. It never mutates the input component; it composes a new one around it.

Pros

  • Can wrap the rendering of a component (add a boundary, inject a provider, conditionally render) — something hooks alone cannot do because a hook can't decide to render a different tree around its caller.
  • Works with any component, including third-party ones you can't edit.
  • Good for cross-cutting structural concerns applied uniformly.

Cons

  • Wrapper hell — withA(withB(withC(X))) bloats the tree and the React DevTools view.
  • Prop collisions — two HOCs both inject a data prop.
  • Opaque source — you can't tell where a prop came from by reading the component.
  • Static methods and refs need manual forwarding (hoist-non-react-statics, forwardRef).

Rule of thumb: if the concern is "share stateful logic," use a hook. If the concern is "wrap the component's render output or lifecycle uniformly," an HOC (or a wrapper component) can still be the right tool.

Code Example

// A typed HOC that injects the current user and gates rendering
function withAuth<P extends object>(
  Wrapped: React.ComponentType<P & { user: User }>
) {
  function WithAuth(props: P) {
    const user = useCurrentUser();          // could also come from context
    if (!user) return <Redirect to="/login" />;
    return <Wrapped {...props} user={user} />;
  }
  // preserve a readable name in DevTools
  WithAuth.displayName = `withAuth(${Wrapped.displayName ?? Wrapped.name})`;
  return WithAuth;
}

const ProtectedDashboard = withAuth(Dashboard);

Project Example

We migrated a legacy app off connect() HOCs to useSelector/useDispatch. The win was visible immediately: the DevTools tree lost three or four Connect(...) wrappers per screen, and props that had mysteriously appeared "from Redux" now had an explicit hook call at the top of the component. We kept exactly one HOC — withErrorBoundary — because that one genuinely needs to wrap the render tree.

Senior Engineer Perspective

The strongest answer names a concrete legacy HOC (connect, withRouter, Relay's createFragmentContainer) and explains that the whole ecosystem moved to hook equivalents. Expect the follow-up "so are HOCs dead?" — say no: React.memo and forwardRef are technically HOCs, and render-wrapping concerns still fit them. Bonus points for mentioning ref forwarding and static hoisting as the classic HOC footguns.

Q4. What is the render props pattern? How does it compare to HOCs and hooks?

ROI: ★★★★☆ Frequency: High

Short Answer

A render prop is a component that takes a function as a prop (often children) and calls that function with internal state to decide what to render. It inverts control: the reusable component owns behaviour, the consumer owns markup. It solved the same logic-sharing problem as HOCs without wrapper hell, but hooks have superseded it for most cases because hooks share logic without adding any nesting at all.

Detailed Answer

Before hooks, if you had reusable stateful logic (mouse position, form state, a toggle) you needed a way to hand that state to arbitrary JSX. Render props did that by passing a function down and invoking it with the state.

Compared to HOCs, render props keep the prop origin explicit (you see the function receiving the values right there in JSX) and avoid name collisions. The downside is the "pyramid of doom" when you nest several render-prop components, and creating a new closure on every render (a minor perf concern).

Hooks made both patterns mostly obsolete for logic reuse: a useMousePosition() hook returns the same values with zero extra tree nesting. But render props are far from dead — they shine when the reusable component needs to control where and whether to render, e.g. virtualization libraries, <Formik>, Downshift, headless charting (Recharts <ResponsiveContainer>), and the "children as a function" idiom (covered later).

Code Example

// Render-prop component: owns the logic, defers the markup
function MousePosition({ children }: {
  children: (pos: { x: number; y: number }) => React.ReactNode;
}) {
  const [pos, setPos] = useState({ x: 0, y: 0 });
  useEffect(() => {
    const handler = (e: MouseEvent) => setPos({ x: e.clientX, y: e.clientY });
    window.addEventListener('mousemove', handler);
    return () => window.removeEventListener('mousemove', handler);
  }, []);
  return <>{children(pos)}</>;
}

// Consumer decides the markup
<MousePosition>
  {({ x, y }) => <p>Cursor at {x}, {y}</p>}
</MousePosition>

// The hook equivalent — no nesting
function useMousePosition() { /* same effect */ return pos; }

Senior Engineer Perspective

The clean narrative interviewers love: "HOCs and render props were two solutions to the same problem — sharing stateful logic — each with a nesting/opacity tax; hooks solved it without a tax." Then the nuance: render props are still the right tool when the library must drive rendering, which a hook can't. If you only recite "hooks replaced render props," you'll get dinged on the follow-up "then why does Formik/react-window still use them?"

Q5. What is the "children as a function" pattern, and when is it preferable to plain children?

ROI: ★★★☆☆ Frequency: Medium

Short Answer

It's render props using the children prop specifically: instead of passing JSX, you pass a function and the component calls it with internal state. You reach for it when the parent has data or state that the child markup needs but the parent shouldn't dictate how that data is rendered.

Detailed Answer

Plain children is static JSX — the parent renders whatever you handed it. children-as-a-function is dynamic — the parent computes values (a virtualized row index, a scroll offset, form field state) and passes them into your function so your markup can use them. It reads slightly more naturally than a named render prop because the function sits between the component's tags.

Use it when the values genuinely originate in the parent and vary per render — list virtualization (react-window gives you an index and style), a <Toggle> handing down on and toggle, or data-fetch wrappers handing down data/loading/error. Avoid it when static children work — it's more indirection than needed for simple cases.

Code Example

type ToggleApi = { on: boolean; toggle: () => void };

function Toggle({ children }: { children: (api: ToggleApi) => React.ReactNode }) {
  const [on, setOn] = useState(false);
  return <>{children({ on, toggle: () => setOn(v => !v) })}</>;
}

// Consumer fully controls markup, gets state injected
<Toggle>
  {({ on, toggle }) => (
    <button aria-pressed={on} onClick={toggle}>
      {on ? 'ON' : 'OFF'}
    </button>
  )}
</Toggle>

Senior Engineer Perspective

Mention the two costs: a new function identity each render (usually irrelevant, but it can defeat memoization if the child is expensive) and reduced readability when nested. Interviewers sometimes ask why not just use a hook — the answer is the same as render props: use the function-child form when the component must control the surrounding render (like a virtualized window), not merely hand you values.

SECTION 2 - REUSE PATTERNS

Q6. Build a compound component (e.g. Tabs or Accordion) using Context. Why is this pattern powerful?

ROI: ★★★★★ Frequency: Extremely High

Short Answer

Compound components are a set of components that work together and share implicit state through Context, exposing an expressive, HTML-like API: <Tabs><Tab/><TabPanel/></Tabs>. The parent holds the state; the children read/update it via a shared context instead of prop drilling. It's powerful because the consumer composes the pieces freely (order, wrapping, extra markup) while the components coordinate behind the scenes — flexible API, zero prop-passing boilerplate.

Detailed Answer

Think of native HTML: <select> and <option> are meaningless apart but coordinate implicitly. Compound components bring that ergonomics to React. The wrapper (Tabs) owns the active-index state and provides it via Context; sub-components (TabList, Tab, TabPanel) consume it. The consumer never manually wires "which tab is active" between pieces.

Benefits

  • Flexible layout — the consumer can wrap tabs in a div, add icons, reorder, insert anything, without the component breaking.
  • Clean API — no giant config object of tabs={[...]}; structure is expressed as JSX.
  • Encapsulation — shared state stays internal.

The main trade-off is that free composition means you must handle cases like a Tab rendered outside a Tabs — throw a clear error from the context hook. Also, deeply-nested consumers still work because Context ignores tree depth.

Code Example

import { createContext, useContext, useState, useId } from 'react';

type TabsCtx = { active: string; setActive: (id: string) => void };
const TabsContext = createContext<TabsCtx | null>(null);

function useTabs() {
  const ctx = useContext(TabsContext);
  if (!ctx) throw new Error('Tabs.* must be used inside <Tabs>');
  return ctx;
}

function Tabs({ defaultTab, children }: { defaultTab: string; children: React.ReactNode }) {
  const [active, setActive] = useState(defaultTab);
  return (
    <TabsContext.Provider value={{ active, setActive }}>
      <div className="tabs">{children}</div>
    </TabsContext.Provider>
  );
}

function TabList({ children }: { children: React.ReactNode }) {
  return <div role="tablist">{children}</div>;
}

function Tab({ id, children }: { id: string; children: React.ReactNode }) {
  const { active, setActive } = useTabs();
  return (
    <button
      role="tab"
      aria-selected={active === id}
      onClick={() => setActive(id)}
    >
      {children}
    </button>
  );
}

function TabPanel({ id, children }: { id: string; children: React.ReactNode }) {
  const { active } = useTabs();
  if (active !== id) return null;
  return <div role="tabpanel">{children}</div>;
}

// Attach as namespaced API — nice discoverability
Tabs.List = TabList;
Tabs.Tab = Tab;
Tabs.Panel = TabPanel;

// Usage
<Tabs defaultTab="profile">
  <Tabs.List>
    <Tabs.Tab id="profile">Profile</Tabs.Tab>
    <Tabs.Tab id="billing">Billing</Tabs.Tab>
  </Tabs.List>
  <Tabs.Panel id="profile">Profile content</Tabs.Panel>
  <Tabs.Panel id="billing">Billing content</Tabs.Panel>
</Tabs>

Project Example

Our design system shipped <Accordion>, <Menu> and <Tabs> exactly this way. Product teams loved that they could drop a tooltip or a badge next to a tab label without us adding a tabBadge prop for every new need — free composition removed a whole class of feature requests. The useTabs() guard caught a real bug where someone rendered a stray <Tab> in a Storybook story outside the provider.

Senior Engineer Perspective

Two follow-ups are almost guaranteed. First: "How do children get the state — do you use React.cloneElement?" Older tutorials cloned children to inject props; the modern, robust answer is Context, because cloneElement breaks the moment a child is nested one level deeper. Say that explicitly. Second: "How do you handle accessibility?" Mention roles (tablist/tab/tabpanel), aria-selected, roving tabindex and arrow-key navigation — real compound components own the a11y so consumers don't have to.

Q7. What are prop getters, and what problem do they solve?

ROI: ★★★☆☆ Frequency: Medium

Short Answer

A prop getter is a function a component (or hook) exposes that returns a bundle of props you spread onto your own element — <button {...getToggleButtonProps()}>. It lets a headless component wire up behaviour (event handlers, ARIA attributes, ids) onto your markup while safely composing with any props/handlers you also pass. It's the pattern behind Downshift and most headless UI libraries.

Detailed Answer

The problem: a headless component gives you full control of markup, but it still needs to attach handlers and accessibility attributes to specific elements. If it just told you "add onClick={toggle} and aria-expanded and id and role yourself," you'd get it wrong and it wouldn't compose with your own onClick.

A prop getter solves this by returning all those props as one object and merging in anything you pass — most importantly composing event handlers so both the library's handler and yours run. You spread it; the component keeps ownership of behaviour; you keep ownership of markup.

Code Example

function useToggle() {
  const [on, setOn] = useState(false);
  const toggle = () => setOn(v => !v);

  // Prop getter: merges caller props, composes onClick
  function getTogglerProps<T extends { onClick?: (e: any) => void }>(props?: T) {
    return {
      'aria-pressed': on,
      ...props,
      onClick: (e: React.MouseEvent) => {
        props?.onClick?.(e);   // run the caller's handler first
        toggle();              // then our behaviour
      },
    };
  }
  return { on, getTogglerProps };
}

// Consumer keeps their own onClick AND gets toggle behaviour
const { on, getTogglerProps } = useToggle();
<button {...getTogglerProps({ onClick: () => console.log('clicked') })}>
  {on ? 'On' : 'Off'}
</button>

Senior Engineer Perspective

The insight interviewers probe: why not just return the handlers directly? Because you'd lose handler composition and force the consumer to remember every ARIA attribute. Prop getters centralise "correct wiring" while preserving consumer overrides. Name-drop Downshift (Kent C. Dodds popularised the term) and note the modern relative: Radix/React Aria's useX hooks return prop bundles for the same reason.

Q8. What is the "slots via props" pattern for passing JSX into components?

ROI: ★★★☆☆ Frequency: Medium

Short Answer

When a component needs several distinct regions of custom content — not one generic children — you accept JSX through named props: header, footer, sidebar. These are React's answer to Vue/Web-Component "named slots." Because props can hold any ReactNode, you just pass elements.

Detailed Answer

children handles the single-hole case. But a <Layout> with a header, main area and sidebar has three holes. Rather than parse children looking for special components, you expose named props that each take JSX. This is explicit, type-safe (each prop is ReactNode), and avoids the fragility of inspecting children by type.

Two competing conventions exist: named-prop slots (shown below) and compound-component slots (<Card.Header>). Prop slots are simpler and better when the set of regions is fixed and small; compound components win when you want free composition and ordering. Both are valid — choose by how flexible the layout must be.

Code Example

type ShellProps = {
  header: React.ReactNode;
  sidebar?: React.ReactNode;
  children: React.ReactNode;   // the "default slot"
};

function AppShell({ header, sidebar, children }: ShellProps) {
  return (
    <div className="shell">
      <header>{header}</header>
      {sidebar && <aside>{sidebar}</aside>}
      <main>{children}</main>
    </div>
  );
}

<AppShell
  header={<TopBar user={user} />}
  sidebar={<NavMenu />}
>
  <Dashboard />
</AppShell>

Senior Engineer Perspective

A subtle follow-up: "Why pass a rendered element and not a component reference?" Passing header={<TopBar/>} lets the consumer close over props at the call site; passing headerComponent={TopBar} defers rendering but forces you to funnel props through. Prefer element props for slots unless you need to control render timing. Also mention that named-prop slots make DevTools cleaner than children-sniffing with React.Children.map, which is brittle and discouraged.

Q9. Explain controlled vs uncontrolled components and the "control props" pattern.

ROI: ★★★★★ Frequency: Extremely High

Short Answer

A controlled component's value lives in the parent's state and is passed down via a value prop with an onChange callback — React is the single source of truth. An uncontrolled component manages its own internal state and you read it via a ref (or defaultValue). The control props pattern lets a reusable component support both: it uses internal state by default but defers to a value prop when one is supplied — exactly how <input> itself behaves.

Detailed Answer

ControlledUncontrolled
Source of truthReact state (parent)The DOM / internal state
Read valuevalue propref.current.value
Set initialvaluedefaultValue
EnablesValidation, formatting, conditional disabling on each keystrokeSimplicity, less re-render, easy integration with non-React code

When designing your own component (a custom <Toggle>, <Combobox>, <Rating>), the control props pattern makes it flexible: consumers who don't care pass nothing and get sensible internal behaviour; consumers who need to drive it pass value + onChange. You detect which mode you're in by whether value is undefined. This is the same "controllable" contract React's built-in inputs use, and it's what libraries like Radix and MUI implement.

Gotcha: never switch a component between controlled and uncontrolled at runtime (going from value={undefined} to value="x") — React warns because it can't tell which source of truth to trust.

Code Example

// A controllable Toggle: works controlled OR uncontrolled
function Toggle({
  value,                       // controlled value (optional)
  defaultValue = false,        // uncontrolled initial
  onChange,
}: {
  value?: boolean;
  defaultValue?: boolean;
  onChange?: (next: boolean) => void;
}) {
  const [internal, setInternal] = useState(defaultValue);
  const isControlled = value !== undefined;
  const on = isControlled ? value : internal;

  const toggle = () => {
    const next = !on;
    if (!isControlled) setInternal(next);  // only manage state when uncontrolled
    onChange?.(next);                       // always notify
  };

  return <button aria-pressed={on} onClick={toggle}>{on ? 'On' : 'Off'}</button>;
}

// Uncontrolled: <Toggle defaultValue />
// Controlled:   <Toggle value={isOn} onChange={setIsOn} />

Project Example

Our design-system <DatePicker> shipped as controllable. Simple forms used it uncontrolled and read the value on submit; the complex booking flow needed to reset the date when the destination changed, so it drove the picker with value/onChange. One component, two integration styles, no forked code path — that's the payoff of the control props pattern.

Senior Engineer Perspective

Interviewers use this to test whether you understand "single source of truth." The killer follow-up is the controlled↔uncontrolled switch warning — be ready to explain that you must decide the mode once (guard with value !== undefined captured consistently). Bonus: for large forms, note that fully controlled inputs re-render on every keystroke, which is why libraries like React Hook Form lean uncontrolled (refs) for performance and only subscribe where needed.

Q10. What is the provider pattern, and how do you design a good one?

ROI: ★★★★☆ Frequency: High

Short Answer

The provider pattern wraps React.createContext in a dedicated <XProvider> component that owns the state and exposes a custom useX() hook for consumers. It encapsulates the context so consumers never touch createContext directly, gives you a single place for logic, and lets the hook throw a helpful error if used outside the provider.

Detailed Answer

A naive Context usage scatters useContext(ThemeContext) everywhere and exposes the raw context object. The provider pattern packages three things together:

  • A private context (not exported).
  • A Provider component that holds state/logic and memoizes its value.
  • A useX() hook that reads the context and guards against misuse.

Key design points: memoize the value (an object literal in the value prop re-renders every consumer on each parent render), and consider splitting state and dispatch into two contexts so components that only dispatch don't re-render when state changes. For heavy global state, this pattern is how you build a lightweight store without Redux.

Code Example

const ThemeContext = createContext<ThemeCtx | null>(null);   // private

export function ThemeProvider({ children }: { children: React.ReactNode }) {
  const [theme, setTheme] = useState<'light' | 'dark'>('light');

  // memoize so consumers don't re-render on unrelated parent renders
  const value = useMemo(
    () => ({ theme, toggle: () => setTheme(t => (t === 'light' ? 'dark' : 'light')) }),
    [theme]
  );

  return <ThemeContext.Provider value={value}>{children}</ThemeContext.Provider>;
}

export function useTheme() {
  const ctx = useContext(ThemeContext);
  if (!ctx) throw new Error('useTheme must be used within <ThemeProvider>');
  return ctx;
}

Senior Engineer Perspective

The classic gotcha they hunt for: forgetting to memoize the context value, which silently re-renders the whole subtree. Mention it unprompted. Next-level answer: Context is not a state manager — it has no selector, so any value change re-renders all consumers; for high-frequency updates use useSyncExternalStore, split contexts, or a real store (Zustand/Redux Toolkit). Also note the state/dispatch split as a cheap optimization.

Q11. What principles guide designing a good component API?

ROI: ★★★★☆ Frequency: High

Short Answer

Aim for an API that's hard to misuse and easy to compose: prefer composition (children/slots) over a pile of boolean props, keep props orthogonal, mirror native HTML conventions (value/onChange, disabled), forward ...rest and refs to the root element, provide sensible defaults, and make illegal states unrepresentable with discriminated union prop types.

Detailed Answer

Concrete principles

  • Composition over configuration — a growing list of showHeader, headerColor, headerIcon booleans is a smell; accept a header slot instead.
  • Follow platform conventions — name callbacks onX, use value/defaultValue, support disabled — so the API feels familiar.
  • Spread rest props & forward refs — let consumers pass className, data-*, aria-* and get a ref to the DOM node.
  • Make impossible states impossible — model variants with unions so TypeScript rejects invalid combinations rather than validating at runtime.
  • Sensible defaults — the zero-config usage should already be correct and accessible.
  • Controllable where it matters — support controlled/uncontrolled for stateful inputs.

Code Example

// Discriminated union makes illegal prop combos a compile error
type ButtonProps =
  | { variant: 'link'; href: string; onClick?: never }
  | { variant: 'button'; onClick: () => void; href?: never };

// Forward rest + ref so consumers can extend the root element
const Button = React.forwardRef<HTMLButtonElement, ButtonProps &
  React.ButtonHTMLAttributes<HTMLButtonElement>>(
  ({ variant, className, ...rest }, ref) => (
    <button ref={ref} className={`btn btn--${variant} ${className ?? ''}`} {...rest} />
  )
);

Senior Engineer Perspective

This question separates people who've maintained a component library from those who've only consumed one. SECTION 3 - STRUCTURE & BOUNDARIES

Q12. What is an error boundary, and why are they still class components in 2024/2025?

ROI: ★★★★★ Frequency: Extremely High

Short Answer

An error boundary is a component that catches JavaScript errors thrown during rendering, in lifecycle methods, and in constructors of its child tree, then renders a fallback UI instead of crashing the whole app. They must be class components because the catching mechanism — static getDerivedStateFromError and componentDidCatch — has never been given a hook equivalent. In practice you use the react-error-boundary library so you write it once.

Detailed Answer

Without a boundary, a render-time error unmounts the entire React tree (since React 16), leaving a blank page. A boundary scopes the blast radius: wrap a widget and only that widget shows a fallback while the rest of the app keeps working.

Two methods

  • static getDerivedStateFromError(error) — returns new state to render the fallback (runs during render, must be pure).
  • componentDidCatch(error, info) — side effects like logging to Sentry.

What they do NOT catch

Event handlers, asynchronous code (setTimeout, promises), server-side rendering, and errors thrown in the boundary itself. For event handlers you use a normal try/catch. This surprises many candidates.

Why still classes

The React team has said a hooks-based API is planned but not shipped; there is no useErrorBoundary to define a boundary. So either write the class or — the pragmatic choice — use react-error-boundary, which wraps the class and adds onReset, resetKeys, a FallbackComponent prop, and a useErrorBoundary() hook for imperatively triggering/resetting from child function components.

Code Example

class ErrorBoundary extends React.Component<
  { fallback: React.ReactNode; children: React.ReactNode },
  { hasError: boolean }
> {
  state = { hasError: false };

  static getDerivedStateFromError() {
    return { hasError: true };            // render fallback next
  }
  componentDidCatch(error: Error, info: React.ErrorInfo) {
    logToSentry(error, info.componentStack);   // side effect
  }
  render() {
    return this.state.hasError ? this.props.fallback : this.props.children;
  }
}

// Preferred in real apps — react-error-boundary
import { ErrorBoundary } from 'react-error-boundary';

<ErrorBoundary
  FallbackComponent={ErrorFallback}
  onReset={() => queryClient.clear()}
  resetKeys={[userId]}
>
  <Dashboard />
</ErrorBoundary>

Project Example

Each fallback offered a "Retry" button wired to resetErrorBoundary, and resetKeys tied to the selected date range so navigating away auto-cleared a stuck error. Pairing it with Sentry via componentDidCatch gave us component stacks, not just JS stacks.

Senior Engineer Perspective

The must-know trap: error boundaries do NOT catch errors in event handlers or async code — say this before they ask. Second signal: where you place boundaries — one at the app root for a global crash screen, plus granular ones around risky/independent subtrees. Third: mention that boundaries and Suspense are the same architectural idea (declarative fallback for an exceptional child state) — errors vs pending. Knowing that react-error-boundary exists signals real-world experience.

Q13. What is Suspense, and how does it act as a "boundary"?

ROI: ★★★★☆ Frequency: High

Short Answer

<Suspense fallback={...}> is a boundary that declaratively shows a fallback (a spinner/skeleton) while any component inside it is "suspended" — waiting on a lazy-loaded chunk or, with a Suspense-enabled data source, on data. Like error boundaries catch thrown errors, Suspense catches thrown promises, letting you express loading states structurally instead of threading isLoading flags through every component.

Detailed Answer

Mechanically, a suspending component throws a promise; the nearest Suspense boundary catches it, renders the fallback, and re-renders the children when the promise resolves. The two mainstream triggers today are React.lazy (code-splitting) and frameworks / libraries that support Suspense for data (Next.js App Router with RSC, TanStack Query's useSuspenseQuery, Relay).

Why it's powerful: loading state becomes composable and hoistable. You decide the granularity by where you place boundaries — one big fallback for a whole page, or many small ones for independent regions that stream in. React 18's concurrent features (startTransition, streaming SSR) build directly on Suspense so the UI stays responsive while content loads.

Code Example

// Nested boundaries give independent loading regions
<Suspense fallback={<PageSkeleton />}>
  <Header />
  <Suspense fallback={<WidgetSkeleton />}>
    <SlowRevenueWidget />      {/* streams in on its own */}
  </Suspense>
</Suspense>

// Combine with an error boundary — the two-boundary sandwich
<ErrorBoundary FallbackComponent={ErrorFallback}>
  <Suspense fallback={<Spinner />}>
    <Profile userId={id} />   {/* uses useSuspenseQuery */}
  </Suspense>
</ErrorBoundary>

Senior Engineer Perspective

Show you know the pairing idiom: wrap Suspense in an ErrorBoundary so success/pending/error are all declarative. Watch for the trap "can I use Suspense for data fetching in any app?" — only with a Suspense-aware source; you can't just wrap a raw fetch in an effect. Bonus depth: mention useTransition to avoid a fallback flashing when updating already-visible content, and RSC streaming where Suspense boundaries define HTML flush points.

Q14. What are portals, and why are they the right tool for modals and tooltips?

ROI: ★★★★☆ Frequency: High

Short Answer

ReactDOM.createPortal(children, domNode) renders children into a DOM node outside the parent's DOM hierarchy while keeping them in the React tree. This escapes CSS problems — overflow: hidden clipping, z-index stacking contexts, and transform containment — that plague modals, tooltips, dropdowns and toasts, which need to visually sit above everything regardless of where they're declared.

Detailed Answer

If you render a modal inside a deeply nested card that has overflow: hidden or its own stacking context, the modal gets clipped or trapped behind other content no matter how high its z-index. A portal moves the actual DOM output to, say, a <div id="modal-root"> at the end of <body>, sidestepping all ancestor CSS.

Crucially, the portal content is still logically inside the React tree: it keeps its place in the component hierarchy, so Context still flows in, and events bubble through the React tree (not the DOM tree) — a click inside a portalled modal bubbles to the React parent that rendered the portal, which can surprise people expecting DOM-based bubbling.

You still owe accessibility: focus trapping, role="dialog", aria-modal, restoring focus on close, and Escape handling. Portals solve the DOM-placement problem, not the a11y problem — which is why most teams use Radix Dialog / React Aria rather than hand-rolling.

Code Example

import { createPortal } from 'react-dom';

function Modal({ open, onClose, children }: {
  open: boolean; onClose: () => void; children: React.ReactNode;
}) {
  if (!open) return null;
  return createPortal(
    <div className="overlay" onClick={onClose}>
      <div className="dialog" role="dialog" aria-modal="true"
           onClick={(e) => e.stopPropagation()}>
        {children}
      </div>
    </div>,
    document.getElementById('modal-root')!    // node outside the app root
  );
}

Senior Engineer Perspective

The killer follow-up: "If it's rendered in body, does a click inside bubble to the component that rendered it?" Yes — event bubbling follows the React tree, not the DOM tree. Candidates who don't know this write buggy outside-click handlers. Also expect "why not just a high z-index?" — because a z-index only competes within its stacking context; an ancestor transform or overflow:hidden defeats it, and a portal is the robust fix.

Q15. How does lazy loading with React.lazy and Suspense work, and what are the pitfalls?

ROI: ★★★★☆ Frequency: High

Short Answer

React.lazy(() => import('./X')) defers loading a component's code until it first renders, producing a separate bundle chunk. You must render it inside a <Suspense> boundary that provides a fallback while the chunk downloads. It's the primary route- and feature-level code-splitting tool, cutting initial bundle size.

Detailed Answer

React.lazy takes a function returning a dynamic import() and returns a component that suspends until the module resolves. The bundler (Vite, webpack) sees the dynamic import and splits that module into its own chunk. The most common use is route-based splitting so each page loads on demand.

Pitfalls

  • Must be a default export — lazy expects the module's default; for named exports, re-map in the import.
  • Needs a Suspense boundary — otherwise React throws.
  • Chunk-load failures — after a deploy, old clients may request a hashed chunk that no longer exists; wrap in an error boundary and offer a reload.
  • Waterfalls — lazy-loading too granularly creates sequential fetches; prefetch on hover/intent for likely-next routes.
  • Don't lazy-load tiny components — the network round-trip costs more than the bytes saved.

);

Q16. What is state colocation, and how do you solve prop drilling without over-reaching for global state?

ROI: ★★★★★ Frequency: Extremely High

Short Answer

State colocation means keeping state as close as possible to where it's used — push it down to the component that needs it, or lift it only as high as the nearest common ancestor. Prop drilling (threading a prop through many intermediate components that don't use it) is a symptom, and the fix ladder is: colocate/lift → component composition (children/slots) → Context (for truly cross-cutting values) → a state library (for high-frequency or app-wide state). Jumping straight to global state is the anti-pattern.

Detailed Answer

The colocation principle

Global state that only one leaf uses causes unnecessary re-renders and coupling. Ask "who reads this?" and place it at their nearest common ancestor — often much lower than the app root. Colocated state re-renders a smaller subtree and keeps components portable.

The prop-drilling fix ladder

  • Composition first — a lot of drilling disappears if you pass JSX as children/slots instead of passing data down to build that JSX. The intermediate component just renders children and never sees the prop.
  • Context — for values that are genuinely cross-cutting and low- frequency: theme, current user, locale, auth. Not for everything.
  • State libraries — Zustand/Jotai/Redux Toolkit for app-wide, frequently-updated, or selector-driven state; TanStack Query for server state, which shouldn't live in your global client store at all.

A key modern distinction: much of what people call "global state" is actually server state (fetched data). Moving it to TanStack Query/RTK Query eliminates a huge amount of drilling and manual caching, leaving only genuine UI state to manage.

Code Example

// PROBLEM: drilling `user` through Layout & Sidebar that don't use it
<Layout user={user}>
  <Sidebar user={user} />      // Sidebar only forwards it onward
</Layout>

// FIX 1 — composition: pass rendered JSX as children, no drilling
function Layout({ children }: { children: React.ReactNode }) {
  return <div className="layout">{children}</div>;
}
<Layout>
  <Sidebar>
    <UserBadge user={user} />   // built at the top, where `user` already lives
  </Sidebar>
</Layout>

// FIX 2 — Context for a truly cross-cutting value
const user = useCurrentUser();   // reads from AuthProvider, no drilling

Senior Engineer Perspective

The mistake juniors make is treating "prop drilling → put it in Redux/Context" as the only move. Seniors reach for composition first — Michael Jackson's "just pass children" insight — because it removes drilling without any new machinery or re-render cost. Be ready for "when is Context the wrong choice?": when the value changes often, since Context re-renders all consumers with no selector. And separate server state from client state — conflating them is the root cause of most bloated global stores.

SECTION 4 - COMPOUND COMPONENTS PATTERN, DEEPER

Q17. What is "implicit state sharing" in a compound component, and how does it differ from passing explicit props to every child?

ROI: ★★★★★ Frequency: Extremely High

Short Answer

Implicit state sharing means the sub-components of a compound component read shared state from a Context provided by the parent, rather than the consumer manually passing that state as a prop to each child. The consumer writes <Accordion><Accordion.Item/></Accordion> and never touches activeId at all — the wiring is invisible to them, which is exactly the point.

Detailed Answer

Contrast two ways the same accordion could be built. An "explicit props" API forces the consumer to own and thread the state themselves:

// Explicit: consumer must manage and pass state manually
const [openId, setOpenId] = useState<string | null>(null);
<AccordionItem id="a" isOpen={openId === 'a'} onToggle={() => setOpenId('a')} />
<AccordionItem id="b" isOpen={openId === 'b'} onToggle={() => setOpenId('b')} />

This works, but every consumer re-derives the same open/close bookkeeping. A compound component with implicit sharing moves that bookkeeping inside the component family, using Context as the invisible wire between parent and children:

// Implicit: state lives inside Accordion, children just read it
<Accordion>
  <Accordion.Item id="a">First</Accordion.Item>
  <Accordion.Item id="b">Second</Accordion.Item>
</Accordion>

The trade-off is discoverability vs. flexibility. Explicit props are fully visible in the JSX — you can see exactly what drives behaviour by reading the call site. Implicit sharing hides that behind Context, so a new team member has to open the component's source to understand how children coordinate. The payoff is that the consumer's code stays clean and can't get the wiring wrong — there is no openId to forget to pass.

Senior Engineer Perspective

A good interviewer will ask "so is implicit always better?" — say no. For a two-piece component (a labeled input, say) explicit props are perfectly discoverable and simpler to trace; compound components earn their complexity when there are three or more coordinating pieces with variable arrangement (Tabs, Accordion, Menu, Select). Reach for implicit sharing when the "shape" of composition should be free; reach for explicit props when the shape is fixed and small.

Q18. Build a compound Accordion that supports both single-open and multi-open modes. How do you design the Context value for that?

ROI: ★★★★☆ Frequency: High

Short Answer

Keep the "which ids are open" question entirely inside the root component and expose only two functions through Context: isOpen(id) and toggle(id). Whether the root stores a single id or a Set of ids is an internal detail — the mode is controlled by one type: 'single' | 'multiple' prop on the root, and the Item/Trigger/Panel children never need to know which mode is active.

Detailed Answer

The key design decision is to expose a capability (open/close/check) through Context rather than the raw data structure (a string vs. a Set). That keeps the children's code identical in both modes and lets you change the internal representation later without touching consumers.

Code Example

type AccordionCtx = {
  isOpen: (id: string) => boolean;
  toggle: (id: string) => void;
};
const AccordionContext = createContext<AccordionCtx | null>(null);

function useAccordionCtx() {
  const ctx = useContext(AccordionContext);
  if (!ctx) throw new Error('Accordion.* must be used inside <Accordion>');
  return ctx;
}

function Accordion({
  type = 'single',
  children,
}: { type?: 'single' | 'multiple'; children: React.ReactNode }) {
  const [openIds, setOpenIds] = useState<Set<string>>(new Set());

  const toggle = (id: string) =>
    setOpenIds((prev) => {
      if (type === 'single') return prev.has(id) ? new Set() : new Set([id]);
      const next = new Set(prev);
      next.has(id) ? next.delete(id) : next.add(id);
      return next;
    });

  const value = useMemo(
    () => ({ isOpen: (id: string) => openIds.has(id), toggle }),
    [openIds]
  );

  return <AccordionContext.Provider value={value}>{children}</AccordionContext.Provider>;
}

function AccordionItem({ id, children }: { id: string; children: React.ReactNode }) {
  return <div data-accordion-item={id}>{children}</div>;
}

function AccordionTrigger({ id, children }: { id: string; children: React.ReactNode }) {
  const { isOpen, toggle } = useAccordionCtx();
  return (
    <button aria-expanded={isOpen(id)} onClick={() => toggle(id)}>
      {children}
    </button>
  );
}

function AccordionPanel({ id, children }: { id: string; children: React.ReactNode }) {
  const { isOpen } = useAccordionCtx();
  return isOpen(id) ? <div role="region">{children}</div> : null;
}

Accordion.Item = AccordionItem;
Accordion.Trigger = AccordionTrigger;
Accordion.Panel = AccordionPanel;

Senior Engineer Perspective

Expect "why not just store an array/index instead of a Set?" — a Set gives O(1) membership checks per item render instead of an O(n) .includes() scan, which matters once an accordion has dozens of items each calling isOpen. Also flag that memoizing the context value on openIds only (not recreating toggle every render) keeps re-renders scoped to items whose open state actually changed, if you further split isOpen per-item via a selector-like helper.

Q19. How do you enforce, at compile time, that a compound sub-component (e.g. `Tabs.Tab`) can only be used inside its parent?

ROI: ★★★☆☆ Frequency: Medium

Short Answer

TypeScript cannot enforce JSX nesting position at compile time — there is no type that means "must be a descendant of X." The practical answer is a runtime guard: the shared useTabsCtx() hook throws a clear error if the context is null, which fails fast in development and in tests, effectively catching misuse before it reaches production.

Detailed Answer

This is a common trick question because candidates assume "TypeScript can enforce anything." Structural typing describes shapes of values, not tree position, so nothing stops <Tabs.Tab id="x"> from being typed correctly while being rendered outside <Tabs>. What you can do:

  • Runtime guard (the standard fix) — throw from the context hook. Combined with error boundaries and tests, this catches the mistake immediately.
  • Lint rules — an eslint rule (like some design systems ship) that statically flags Tabs.Tab used outside a Tabs JSX block; this is project-specific tooling, not the type system.
  • Restrict children types (partial) — you can type the parent's children prop narrowly (e.g. only accept elements whose type is one of the known sub-components) but this is brittle, defeats fragments/conditionals, and is rarely done in practice.

Code Example

function useTabsCtx() {
  const ctx = useContext(TabsContext);
  if (!ctx) {
    throw new Error(
      '<Tabs.Tab> / <Tabs.Panel> must be rendered inside <Tabs>. ' +
      'Did you forget to wrap them?'
    );
  }
  return ctx;
}

Senior Engineer Perspective

The strongest answer explicitly says "TypeScript types describe shape, not tree position — this needs a runtime check," rather than fumbling for a generic-types trick that doesn't exist. Bonus points for mentioning that this same guard pattern doubles as living documentation: the error message itself teaches the correct usage to whoever hits it.

Q20. What is the flexibility vs. discoverability trade-off in compound components, and how do component libraries mitigate the discoverability cost?

ROI: ★★★★☆ Frequency: High

Short Answer

Compound components maximize flexibility — you can reorder, wrap, and inject arbitrary markup between pieces — but they cost discoverability: a consumer opening <Select> in their editor doesn't automatically see that Select.Option, Select.Group and Select.Trigger exist unless documented. Libraries mitigate this by attaching sub-components as static properties (Select.Option = ...) so autocomplete surfaces them, and by shipping strong TypeScript types plus Storybook/MDX docs colocated with the component.

Detailed Answer

Namespacing sub-components as properties of the root (Tabs.Tab rather than a separately-imported Tab) is not just aesthetic — it means typing Tabs. in an editor with IntelliSense lists every valid piece, turning an undiscoverable API into a self-documenting one. This is why Radix, Headless UI and Chakra all use the dotted-property convention rather than exporting a dozen standalone named exports.

A second mitigation is exporting a single default composition alongside the raw parts — e.g. a <SimpleSelect options={...}/> built from the compound pieces for the 80% case, while power users drop down to the full Select/Select.Option/Select.Group API when they need custom layouts. This gives you the discoverability of a simple prop-driven API for common cases without sacrificing the flexibility of composition for edge cases.

Code Example

// Namespacing sub-components for editor discoverability
function Select({ children }: { children: React.ReactNode }) { /* ... */ }
Select.Trigger = SelectTrigger;
Select.Option  = SelectOption;
Select.Group   = SelectGroup;

// A convenience wrapper for the common case, built from the compound pieces
function SimpleSelect({ options, ...rest }: { options: { value: string; label: string }[] } & SelectProps) {
  return (
    <Select {...rest}>
      <Select.Trigger />
      {options.map((o) => <Select.Option key={o.value} value={o.value}>{o.label}</Select.Option>)}
    </Select>
  );
}

Senior Engineer Perspective

Interviewers building a design system care a lot about this trade-off. The senior framing: "flexible primitives + one or two opinionated convenience wrappers" beats choosing only one extreme — pure compound components punish the common case with boilerplate, and pure prop-driven APIs eventually explode into unmaintainable configuration objects.

Q21. How would you build a compound `Select` component whose `Option` children need to register themselves with the parent (e.g. for keyboard navigation order)?

ROI: ★★★★☆ Frequency: Medium-High

Short Answer

Each Option registers its id with the parent's Context on mount (inside a useEffect) and deregisters on unmount, so the parent always has an ordered list of currently-rendered options to drive arrow-key navigation — without the parent needing to parse its own children tree.

Detailed Answer

A naive approach tries to read navigation order from React.Children.toArray(children) in the parent, but that breaks the moment an Option is nested inside a wrapper (a <Fragment>, a conditionally-rendered group, a mapped list wrapped in a styled div) — the parent can no longer "see" it directly as a child. The robust fix inverts the relationship: children announce themselves to the parent via a registration callback exposed through Context, and the parent maintains the list.

Code Example

type SelectCtx = {
  register: (id: string) => void;
  unregister: (id: string) => void;
  activeId: string | null;
  setActiveId: (id: string) => void;
};
const SelectContext = createContext<SelectCtx | null>(null);

function Select({ children }: { children: React.ReactNode }) {
  const orderRef = useRef<string[]>([]);
  const [activeId, setActiveId] = useState<string | null>(null);

  const register = (id: string) => {
    if (!orderRef.current.includes(id)) orderRef.current.push(id);
  };
  const unregister = (id: string) => {
    orderRef.current = orderRef.current.filter((x) => x !== id);
  };

  const value = useMemo(() => ({ register, unregister, activeId, setActiveId }), [activeId]);

  return <SelectContext.Provider value={value}>{children}</SelectContext.Provider>;
}

function Option({ id, children }: { id: string; children: React.ReactNode }) {
  const ctx = useContext(SelectContext)!;
  useEffect(() => {
    ctx.register(id);
    return () => ctx.unregister(id);   // works even if wrapped, mapped, or conditional
  }, [id]);

  return (
    <div
      role="option"
      aria-selected={ctx.activeId === id}
      onClick={() => ctx.setActiveId(id)}
    >
      {children}
    </div>
  );
}

Project Example

We hit this exact issue building a searchable dropdown: options were grouped under Select.Group headers, so React.Children traversal saw groups, not flat options, and arrow-key navigation skipped items. Switching to a registration effect fixed navigation regardless of how deeply an option was nested under a group wrapper.

Senior Engineer Perspective

The insight to state explicitly: React.Children APIs only see the immediate children passed to a component, not descendants past an intermediate wrapper — so any pattern relying on children introspection is fragile under composition. Self-registration inverts control and is immune to arbitrary nesting. Mention cleanup on unmount is essential, or removed options linger as "phantom" stops in keyboard navigation.

Q22. Can you build a compound component without Context, using `React.cloneElement`? Why is that approach usually discouraged today?

ROI: ★★★☆☆ Frequency: Medium

Short Answer

Yes — the pre-Context (pre-16.3) technique iterates props.children with React.Children.map and injects extra props into each child via React.cloneElement. It's discouraged today because it only reaches one level of direct children, breaking the moment a consumer wraps a child in another element, and it silently fails (props just don't arrive) rather than throwing a helpful error.

Detailed Answer

cloneElement creates a copy of a React element with some props overridden. Combined with React.Children.map, older tutorials used this to hand state down to each direct JSX child without Context:

function Tabs({ activeId, children }) {
  return React.Children.map(children, (child) =>
    React.cloneElement(child, { isActive: child.props.id === activeId })
  );
}

This looks elegant for a flat list of children, but breaks the instant a consumer does anything realistic — wraps a Tab in a styled div for spacing, maps over an array to generate tabs, or conditionally renders one with && wrapped in a fragment nested one level deep. In all these cases cloneElement never reaches the actual Tab, and the injected prop silently vanishes — no error, just a subtly broken tab.

Context has none of these limits: it flows to any depth regardless of what's in between, consumers can freely restructure markup, and a missing provider can be turned into a loud, helpful error via the custom hook guard. This is why virtually every modern compound component (Radix, Headless UI, Reach UI) is Context-based, and cloneElement-based compound components are now considered a legacy anti-pattern.

Senior Engineer Perspective

Naming the exact failure mode — "wrap a child in a div and the clone-based prop injection silently stops working" — is what separates someone who has actually maintained a cloneElement-based component from someone reciting "Context is better." Mention that cloneElement still has valid, narrow uses (e.g. a single icon-decorated button component tweaking one direct child), just not as the backbone of a multi-piece compound API.

Q23. How do you type a compound component's namespaced sub-components in TypeScript (e.g. `Menu.Item`) so consumers get full autocomplete and prop checking?

ROI: ★★★☆☆ Frequency: Medium

Short Answer

Declare each sub-component as its own typed function component, then attach them to the root as properties and widen the root's type with an intersection so TypeScript knows the function and its attached properties both exist: type MenuComponent = typeof MenuImpl & { Item: typeof MenuItem; ... }.

Detailed Answer

Simply doing Menu.Item = MenuItem in JavaScript works at runtime but TypeScript won't know Menu.Item exists unless the declared type of Menu includes it. The common fix is to cast the assembled object once, in one place, so every consumer gets accurate types without extra ceremony.

Code Example

function MenuImpl({ children }: { children: React.ReactNode }) {
  return <div role="menu">{children}</div>;
}

function MenuItem({ children, onSelect }: { children: React.ReactNode; onSelect: () => void }) {
  return <div role="menuitem" onClick={onSelect}>{children}</div>;
}

function MenuGroup({ label, children }: { label: string; children: React.ReactNode }) {
  return (
    <div role="group" aria-label={label}>
      {children}
    </div>
  );
}

// Compose the public type once, cast once
type MenuComponent = typeof MenuImpl & {
  Item: typeof MenuItem;
  Group: typeof MenuGroup;
};

const Menu = MenuImpl as MenuComponent;
Menu.Item = MenuItem;
Menu.Group = MenuGroup;

export { Menu };
// Consumers now get full autocomplete on Menu.Item and Menu.Group,
// with correctly-typed props on each.

Senior Engineer Perspective

Interviewers testing TS depth want to see that you know the difference between "works at runtime" and "typechecks." Q24. How do compound components handle server-side rendering and hydration — is there anything special about Context-driven state in that scenario?

ROI: ★★★☆☆ Frequency: Medium

Short Answer

Nothing about Context itself is SSR-unsafe — it renders on the server exactly like any other state, producing HTML that matches the client's first render as long as the initial state is derived identically on both sides (e.g. a passed-in defaultTab prop, not Math.random() or window access). The real risk is when a compound component reads a browser-only API (viewport width, a portal target, localStorage) to compute its initial open/active id — that produces a hydration mismatch because the server has no such value.

Detailed Answer

React's hydration compares the server-rendered markup to what the client would render on first pass; any difference in initial output throws a hydration mismatch warning (or worse, a UI flash from React blowing away and re-rendering the mismatched subtree). For a compound component this typically bites when:

  • Initial state depends on window.innerWidth or matchMedia (e.g. "default the accordion open on desktop, closed on mobile").
  • Initial state depends on localStorage/cookies read directly during render rather than in an effect.
  • An id is generated with Math.random() instead of the SSR-safe useId() hook — React guarantees useId produces matching values on server and client.

The fix pattern: render a deterministic default on the server and first client render (e.g. always start closed, or accept the default from a prop), then correct it in a useEffect after mount, which only runs client-side and naturally happens after hydration completes.

Code Example

function Accordion({ children }: { children: React.ReactNode }) {
  // Deterministic on server AND first client render — no mismatch
  const [openId, setOpenId] = useState<string | null>(null);

  useEffect(() => {
    // Runs only in the browser, after hydration — safe to diverge here
    if (window.matchMedia('(min-width: 1024px)').matches) {
      setOpenId('first');
    }
  }, []);

  // ...
}

Senior Engineer Perspective

The strongest signal here is naming useId() specifically — many compound-component internals generate ids to wire aria-controls/ aria-labelledby between a trigger and its panel, and doing that with Math.random() or a module-level counter is a classic SSR hydration bug. Mention that the fix is always "defer the browser-only decision to an effect," never "just suppress the hydration warning."

Q25. Implement a render-prop `DataFetcher` component from scratch, handling loading, error and success states.

ROI: ★★★★☆ Frequency: High

Short Answer

The component owns a fetch effect and a small state machine (idle/loading/success/error), and calls its children function with that state on every render so the caller decides what markup corresponds to each phase.

Code Example

type FetchState<T> =
  | { status: 'loading' }
  | { status: 'error'; error: Error }
  | { status: 'success'; data: T };

function DataFetcher<T>({
  url,
  children,
}: {
  url: string;
  children: (state: FetchState<T>) => React.ReactNode;
}) {
  const [state, setState] = useState<FetchState<T>>({ status: 'loading' });

  useEffect(() => {
    let cancelled = false;
    setState({ status: 'loading' });
    fetch(url)
      .then((r) => r.json())
      .then((data) => { if (!cancelled) setState({ status: 'success', data }); })
      .catch((error) => { if (!cancelled) setState({ status: 'error', error }); });
    return () => { cancelled = true; };   // avoid setting state after unmount / stale url
  }, [url]);

  return <>{children(state)}</>;
}

// Usage — caller owns 100% of the markup for every phase
<DataFetcher<User[]> url="/api/users">
  {(state) => {
    if (state.status === 'loading') return <Spinner />;
    if (state.status === 'error') return <ErrorMessage error={state.error} />;
    return <UserList users={state.data} />;
  }}
</DataFetcher>

Senior Engineer Perspective

Discriminated union state (rather than three separate booleans like loading/error/data) is the detail that signals seniority — it makes impossible combinations (loading and error both true) unrepresentable. Also flag the cancelled guard: without it, a fast url change followed by a slow first response can overwrite fresher state with stale data — a real race condition, not just cosmetic.

Q26. What is the "pyramid of doom" problem with render props, and how would you flatten multiple render-prop components?

ROI: ★★★☆☆ Frequency: Medium

Short Answer

Nesting several render-prop components to combine their state produces deeply indented JSX — each one adds a function-child level. You flatten it either by converting the shared logic to hooks (the modern fix, zero nesting) or, if you must stay render-prop-based, by writing a small "compose" helper that chains multiple render props into one callback.

Detailed Answer

The pyramid appears whenever a component needs values from more than one render-prop source:

<MousePosition>
  {(mouse) => (
    <WindowSize>
      {(size) => (
        <Scroll>
          {(scroll) => (
            <Chart mouse={mouse} size={size} scroll={scroll} />
          )}
        </Scroll>
      )}
    </WindowSize>
  )}
</MousePosition>

The pragmatic fix in modern code is simply "don't build these as render props" — expose useMousePosition(), useWindowSize(), useScroll() hooks instead, and call all three flat at the top of Chart, with zero nesting. If you're stuck maintaining an existing render-prop library, a compose utility collapses the pyramid syntactically without touching the underlying components.

Code Example

  const mouse = useMousePosition();
  const size = useWindowSize();
  const scroll = useScroll();

Q27. When does a library still choose render props over a custom hook, even today? Give concrete examples.

ROI: ★★★★☆ Frequency: High

Short Answer

When the component must control whether, what, and where something renders — not just hand back values. A hook can only return data; it can't decide to skip rendering a row, inject a wrapper element, or manage a portal target. Anything in that category (list virtualization, formik-style field arrays, headless render-as-you-scroll libraries) still uses render props or the closely related "render function" prop.

Detailed Answer

  • react-window / react-virtualized — the list only renders the rows currently in the viewport; the render prop receives { index, style } per visible row because the library, not your code, decides which rows exist in the DOM at all. A hook returning "the visible range" would still leave you to manually loop and position rows — the library does that positioning work for you via the callback.
  • React Router's <Routes> render function historically, and libraries like react-flip-toolkit — need to wrap your output in DOM measurement logic that runs around your render, not just before it.
  • Formik's <Field> render prop — lets Formik decide exactly when to re-render a single field in isolation for performance, something a global hook subscription can't scope as tightly per-JSX-usage.

The unifying theme: hooks are for "give me data/behaviour," render props are for "let the library drive part of the render tree around or instead of what I'd normally write."

Q28. What is the difference between a "render prop" named `render` and using `children` as the function? Are there reasons to prefer one over the other?

ROI: ★★★☆☆ Frequency: Medium

Short Answer

They're functionally identical — both pass a function that receives internal state and returns JSX. The only difference is which prop carries the function. children-as-function reads more naturally in JSX (the function sits between the tags); a named render prop is clearer when the component also needs a real children for something else, or when self-closing syntax (<X render={...} />) is preferred.

Detailed Answer

// children-as-function — reads naturally with JSX between the tags
<Toggle>{(api) => <button onClick={api.toggle}>{api.on ? 'On' : 'Off'}</button>}</Toggle>

// named render prop — useful if you ALSO want to accept normal children
<Toggle render={(api) => <button onClick={api.toggle}>{api.on ? 'On' : 'Off'}</button>}>
  <p>A caption rendered alongside, unrelated to toggle state</p>
</Toggle>

In practice, prefer children-as-function unless you have a concrete reason to keep children free for something else — it's the more idiomatic, more common convention (Downshift, react-window's item renderer aside, most headless libs use this form).

Senior Engineer Perspective

A quick, correct answer here ("no real difference, pick based on whether children is already spoken for") is enough — this is a knowledge check, not a design debate, and over-explaining signals you don't realize how minor the distinction is.

Q29. Does using a render prop hurt performance? Walk through what actually happens on each render.

ROI: ★★★★☆ Frequency: High

Short Answer

A render-prop function is usually a new inline closure on every parent render, so the child component (the one calling children(...)) can't React.memo its way out of re-rendering based on "did children change" — a new function reference always looks different. In practice this rarely matters because the render-prop component's own state change is what's driving the update anyway, but it becomes a real cost if the rendered output is expensive and the parent re-renders for unrelated reasons.

Detailed Answer

Walk through it concretely: <Toggle>{(api) => <ExpensiveChart api={api} />}</Toggle>. Every time the component containing this JSX re-renders (for any reason — a sibling state change, a context update elsewhere), a brand-new arrow function is created and passed as children. If Toggle itself re-renders (say, its internal on state didn't change but its parent forced a re-render), it calls the new function, which mounts a fresh ExpensiveChart element — React.memo around ExpensiveChart can't help because the element identity depends on the render-prop closure, not stable props.

Mitigations, in order of how often you actually need them: usually none — do nothing, React's reconciliation of same-type elements is already fast. If profiling shows a real problem, memoize the callback with useCallback at the call site (helps only if its own dependencies are stable), or — the more robust fix — convert the underlying logic to a hook so there is no function-as-child indirection to worry about at all.

Senior Engineer Perspective

The trap is stating this as a certainty ("render props are slow") without profiling — interviewers want "it's a theoretical cost that's rarely the actual bottleneck; I'd measure with the Profiler before optimizing it away," which is the mature, evidence-based answer.

Q31. What happens if a render prop function is recreated every render and is passed to a memoized child that itself calls the function conditionally — can you get stale closures?

ROI: ★★★☆☆ Frequency: Medium

Short Answer

No — unlike a callback stored in a ref or captured once in an effect, a render prop is invoked synchronously during the current render, so it always closes over the current render's variables. Stale closures happen when a function is captured and called later (in an effect, a timeout, an event listener) without being part of the current render's dependency chain — render props don't have that problem because they're called inline, every render, with no caching in between.

Detailed Answer

This question tests whether you conflate "recreated every render" (a performance question) with "captures stale values" (a correctness question). They're independent:

  • A new function every render is wasteful only if it defeats a memoization boundary — it is never incorrect, because it's always the newest closure being called.
  • Stale closures arise specifically when a function is captured once (e.g. inside a useEffect with an empty dependency array, or stored in a ref) and invoked after the component has re-rendered with new values the old closure can't see.

Render props sidestep the second problem entirely because the parent re-creates and re-passes the function on every render, and the child calls it immediately during that same render — there's no "later" for it to go stale in.

Senior Engineer Perspective

A precise answer here — distinguishing "wasted allocation" from "wrong data" — is a strong signal of real understanding of React's render model, and it's a common trap question precisely because "new function every render" sounds alarming out of context.

Q32. Implement a `withErrorBoundary` HOC and explain why static hoisting matters when wrapping a component that exposes static members.

ROI: ★★★★☆ Frequency: High

Short Answer

The HOC wraps the target in an error-boundary class and returns the wrapper. If the wrapped component had its own static properties (MyForm.validate, MyForm.propTypes), those live on the original function/class, not the new wrapper function the HOC returns — so any code doing WrappedForm.validate() breaks unless you copy statics across with a utility like hoist-non-react-statics.

Code Example

import hoistNonReactStatics from 'hoist-non-react-statics';

function withErrorBoundary<P extends object>(
  Wrapped: React.ComponentType<P>,
  Fallback: React.ComponentType<{ error: Error }>
) {
  class WithErrorBoundary extends React.Component<P, { error: Error | null }> {
    state = { error: null as Error | null };
    static getDerivedStateFromError(error: Error) { return { error }; }
    componentDidCatch(error: Error, info: React.ErrorInfo) {
      logToSentry(error, info.componentStack);
    }
    render() {
      if (this.state.error) return <Fallback error={this.state.error} />;
      return <Wrapped {...this.props} />;
    }
  }

  WithErrorBoundary.displayName = `withErrorBoundary(${Wrapped.displayName ?? Wrapped.name})`;
  // Without this, WithErrorBoundary.validate would be undefined even though
  // Wrapped.validate exists — statics don't automatically transfer.
  hoistNonReactStatics(WithErrorBoundary, Wrapped);
  return WithErrorBoundary;
}

Q33. Write an HOC that forwards refs through to the wrapped component. Why doesn't a ref "just work" without this?

ROI: ★★★★★ Frequency: Extremely High

Short Answer

A ref attached to <WithLogging ref={r}/> attaches to the HOC's own wrapper component, not to whatever DOM node or component instance the inner component exposes — ref is not a regular prop and is never passed through automatically. To forward it, the HOC must explicitly wrap itself in React.forwardRef and pass the ref down as an argument.

Detailed Answer

React intentionally special-cases ref: it never appears in props, and it never flows through a component the way className or onClick would. A plain HOC like function withLogging(Wrapped) { return (props) => <Wrapped {...props}/> } silently drops any ref the consumer attaches, because ref isn't in props to spread in the first place — it attaches to the outer function component itself, which (being a function component) has no instance to attach to, producing a console warning and a null ref.

Code Example

function withLogging<P extends object, R>(
  Wrapped: React.ComponentType<P & React.RefAttributes<R>>
) {
  const WithLogging = React.forwardRef<R, P>((props, ref) => {
    useEffect(() => { console.log('mounted', Wrapped.name); }, []);
    return <Wrapped {...(props as P)} ref={ref} />;   // ref explicitly threaded through
  });
  WithLogging.displayName = `withLogging(${Wrapped.displayName ?? Wrapped.name})`;
  return WithLogging;
}

// Now a consumer's ref reaches the real underlying input DOM node
const LoggedInput = withLogging(Input);
const ref = useRef<HTMLInputElement>(null);
<LoggedInput ref={ref} />   // ref.current is the actual <input> DOM node

This is one of the highest-frequency "gotcha" questions about HOCs specifically because it's the single most common production bug from hand-rolled HOCs — a parent's ref mysteriously being null. Say the mechanism precisely: ref is not a prop, so {...props} spreads never carry it, and forwardRef exists specifically to plug this hole.

Q34. Two HOCs both inject a prop named `data` onto the wrapped component. What happens, and how do you design HOCs to avoid this class of bug?

ROI: ★★★★☆ Frequency: High

Short Answer

Whichever HOC is applied last (the outermost wrapper) wins — its data prop silently overwrites the inner one's, because each HOC just spreads {...props} data={...} onto its child, and object spread is last-write-wins. You avoid the collision by namespacing injected props (a nested object like auth={{user}} instead of a bare top-level prop), or by not using an HOC at all for logic that returns a value — a hook avoids collisions entirely since two hooks return two independently-named variables you control at the call site.

Detailed Answer

const withUser = (C) => (props) => <C {...props} data={useCurrentUser()} />;
const withTheme = (C) => (props) => <C {...props} data={useTheme()} />;

const Enhanced = withTheme(withUser(Profile));
// Profile receives props.data = theme, NOT the user — withTheme is outermost
// and its spread + override runs last. This bug is completely silent —
// no error, no warning, just the wrong value at runtime.

Two real mitigations: namespace props by HOC identity (userData/themeData, or better, a nested object per concern so collisions are visually obvious in code review), or replace with hooks, where const user = useCurrentUser(); const theme = useTheme(); makes both values simultaneously available under names the consuming component chooses itself — there's no shared prop namespace to collide in at all.

Q36. Name three HOCs that are still idiomatic in modern React (not legacy holdovers) and explain why each one couldn't just be a hook.

ROI: ★★★★☆ Frequency: High

Short Answer

React.memo, React.forwardRef, and library-provided wrappers like withErrorBoundary (from react-error-boundary) are all still genuinely HOCs in current React, because each one changes how a component is rendered or referenced by its parent — something a hook, which only runs inside the component it's called from, structurally cannot do.

Detailed Answer

  • React.memo(Component) — returns a new component type that skips re-rendering when props are shallow-equal. A hook can't intercept "should this component's render function even run" from the outside; that requires wrapping the component itself.
  • React.forwardRef(render) — changes how the component receives a special, non-prop argument (ref). Hooks have no access to a component's own incoming ref without this wrapping mechanism.
  • withErrorBoundary(Component, options) — must physically wrap the component in a boundary in the tree so it can catch errors thrown during that subtree's render; a hook cannot catch a render error from its own component (if the component throws, the hook never finishes running either), so this concern is structurally a wrapping problem, not a logic-sharing one.

The unifying rule: hooks solve "share stateful logic that runs alongside my render"; HOCs solve "change what happens around or before my render, from the outside."

Senior Engineer Perspective

Interviewers ask this specifically to catch candidates who parrot "HOCs are dead." The sharpest possible answer explicitly reframes the pattern's status: not deprecated, just demoted from "default tool for logic reuse" to "the correct tool for a smaller, specific set of render-wrapping concerns."

Q38. Convert `React-Redux`-style `connect(mapStateToProps)(Component)` HOC usage to hooks. What is lost and what is gained in the conversion?

  // ...
}

Q39. Can an HOC and a custom hook be combined — e.g. an HOC that internally uses hooks to implement its behaviour? When would you do this?

// internally it's just calling a hook to get the data.

      if (user === null) navigate('/login');

  }
  WithAuth.displayName = `withAuth(${Wrapped.displayName ?? Wrapped.name})`;
  return WithAuth;
}

Q40. Design the prop API for a custom `` component so it matches native input conventions (`value`/`defaultValue`/`onChange`). What should the `onChange` signature look like?

ROI: ★★★★★ Frequency: Extremely High

Short Answer

Mirror the platform: value for controlled usage, defaultValue for uncontrolled initial value, and onChange(newValue) — not onChange(event) — because a <Rating> isn't backed by a single native input, so there's no real DOM event to hand back; passing the value directly is more useful and is the convention most custom-input libraries (MUI, Ant Design, Radix) converge on for non-native controls.

Native HTML inputs pass an Event to onChange because that's what the DOM API provides; you then read event.target.value. A custom component has no such constraint — it's calling onChange itself, so it can hand back exactly what's useful: the new rating number. Matching value/defaultValue naming (rather than inventing selectedRating/initialRating) means any React developer already knows the API without reading docs — that familiarity is the entire point of "match native conventions."

type RatingProps = {

  defaultValue?: number;      // uncontrolled initial
  onChange?: (value: number) => void;   // hands back the value directly, not an Event
  max?: number;
  disabled?: boolean;
};

}

Q41. What warning does React give when a component switches between controlled and uncontrolled, and what exactly triggers it?

ROI: ★★★★★ Frequency: Extremely High

Short Answer

React warns: "A component is changing a controlled input to be uncontrolled" (or vice versa). It's triggered when the value prop is undefined on the first render (uncontrolled) but becomes a defined value on a later render, or the reverse — React detects the input's "mode" by whether value was present on mount, and can't safely change modes mid-life because it would mean silently switching the source of truth.

Detailed Answer

The classic cause is initializing state from an API call that resolves after first render:

function Form() {
  const [name, setName] = useState();      // undefined initially — uncontrolled!
  useEffect(() => { fetchUser().then((u) => setName(u.name)); }, []);
  return <input value={name} onChange={(e) => setName(e.target.value)} />;
  // First render: value={undefined} -> uncontrolled.
  // After fetch resolves: value="Ada" -> controlled. React warns.
}

The fix is to guarantee value is never undefined across the component's life — initialize with an empty string, not undefined:

const [name, setName] = useState('');   // always a string -> always controlled

The same applies to any prop-driven controlled component you author yourself: decide the mode once, on mount, and never let value flip between undefined and defined afterward.

Senior Engineer Perspective

This is one of the single most commonly hit real-world React warnings, so a crisp, exact explanation (not just "keep it consistent") is a strong signal. Mention the concrete fix — seed state with the input's empty value, never undefined — rather than a vague "always initialize state properly."

Q42. How do you implement a controlled/uncontrolled hybrid without duplicating the update logic in two branches? Show the `isControlled` guard pattern cleanly.

ROI: ★★★★☆ Frequency: High

Short Answer

Compute a single derived "current value" that reads from props when controlled and from internal state otherwise, and route every update through one function that conditionally updates internal state (only when uncontrolled) but always calls the consumer's callback — that keeps the branching to one small, centralized spot instead of scattering if (isControlled) checks through every event handler.

Code Example

function useControllableState<T>({
  value,
  defaultValue,
  onChange,
}: {
  value?: T;
  defaultValue: T;
  onChange?: (value: T) => void;
}) {
  const [internal, setInternal] = useState(defaultValue);
  const isControlled = value !== undefined;
  const current = isControlled ? (value as T) : internal;

  // One function, used everywhere the component would otherwise update state
  const setValue = (next: T) => {
    if (!isControlled) setInternal(next);
    onChange?.(next);
  };

  return [current, setValue] as const;
}

// Reused across ANY controllable component — Toggle, Rating, Tabs, Select...
function Toggle({ value, defaultValue = false, onChange }: ToggleProps) {
  const [on, setOn] = useControllableState({ value, defaultValue, onChange });
  return <button aria-pressed={on} onClick={() => setOn(!on)}>{on ? 'On' : 'Off'}</button>;
}

Senior Engineer Perspective

Extracting this into a reusable useControllableState hook (which is essentially what Radix's internal useControllableState does) is the senior move — it turns a pattern you'd otherwise reimplement per-component into a one-line dependency every controllable component in your design system shares.

Q43. Should a controllable component still fire `onChange` when it's fully controlled and the parent's `value` prop doesn't actually change afterward? Walk through the expected contract.

ROI: ★★★☆☆ Frequency: Medium

Short Answer

Yes — onChange should fire on every user interaction regardless of whether the parent chooses to update value in response. A controlled component's contract is "notify on interaction, render whatever value you're told," not "notify only if the value will change" — the latter would make the component silently swallow user actions whenever the parent (correctly or incorrectly) ignores the callback.

Detailed Answer

This mirrors how a native controlled input behaves: typing into <input value={x} onChange={...}/> always fires onChange, even if the parent's handler is a no-op and x never updates — the input will simply appear "stuck" showing the old value, but the event still fired. This is intentional: it's how a parent can implement validation that rejects some keystrokes (e.g. a numeric-only field) by calling onChange but conditionally not updating value, effectively vetoing certain inputs while still being told about every attempt.

Code Example

// A controlled numeric input that "vetoes" non-numeric keystrokes
function NumericField({ value, onChange }: { value: string; onChange: (v: string) => void }) {
  return (
    <input
      value={value}
      onChange={(e) => {
        const next = e.target.value;
        if (/^\d*$/.test(next)) onChange(next);   // only forwards valid changes
        // invalid keystrokes: onChange isn't called, so `value` (and the input) doesn't move
      }}
    />
  );
}

Senior Engineer Perspective

This question probes whether you understand controlled components as "the parent has veto power," a subtle but important mental model — the component's job is to report intent, the parent's job is to decide what's reflected back. Say this explicitly rather than assuming onChange and "the value actually changing" are the same event.

Q44. How would you support an `onValueChange` callback alongside a native-feeling `value`/`onChange` pair, the way Radix does for some primitives? Why offer both?

Q45. How do uncontrolled components interact with `ref`-based form libraries like React Hook Form, and why do those libraries prefer uncontrolled inputs?

ROI: ★★★★☆ Frequency: High

Short Answer

React Hook Form registers a ref on each input and reads/writes values directly on the DOM node rather than storing every keystroke in React state, so most fields never trigger a React re-render while typing — only a validated/subscribed field does. This is why it favors uncontrolled inputs: performance for large forms, since re-rendering the whole form on every keystroke of a 40-field form is real, measurable jank.

Detailed Answer

A fully controlled form (every field's value in React state, updated via onChange) re-renders the entire form component tree on every keystroke in any field, unless you've carefully split fields into isolated child components. React Hook Form sidesteps this by calling register('fieldName'), which returns { name, ref, onChange, onBlur } — the ref lets RHF read the DOM input's value on demand (at submit time, or when a validation rule needs it) via ref.current.value, without React ever storing that value in state.

The trade-off: since the value doesn't live in React state, you can't reactively derive other UI from it without opting into a subscription — RHF exposes watch() or useWatch() for exactly the fields that need to be reactive, letting you pay the re-render cost only where you actually need live updates.

Code Example

function SignupForm() {
  const { register, handleSubmit, watch } = useForm();
  const password = watch('password');   // opt-in reactivity, only for this one field

  return (
    <form onSubmit={handleSubmit(onSubmit)}>
      <input {...register('email')} />          {/* uncontrolled — no re-render per keystroke */}
      <input {...register('password')} type="password" />
      {password && <PasswordStrength value={password} />}   {/* only this subtree re-renders */}
    </form>
  );
}

Senior Engineer Perspective

The strongest answer names the actual mechanism — ref + reading .value on demand instead of state-per-keystroke — and connects it to the concrete win (large forms don't re-render globally), rather than a vague "RHF is more performant."

Q47. What is the difference between a "controlled" component and a component that is simply "derived from props with no internal state at all"? Give an example where the distinction matters.

// Genuinely controlled — has an interaction loop that must be reported back

Q48. What is "provider hell," and how do you flatten five or six nested `` wrappers at the app root?

ROI: ★★★★★ Frequency: Extremely High

Short Answer

Provider hell is the same nesting problem as callback pyramids, but at the app root: <ThemeProvider><AuthProvider><QueryClientProvider><I18nProvider>...</></></></>. You flatten it with a small utility component — often called <AppProviders> — that composes an array of providers with reduceRight, or simply hand-writes one flat wrapper component so the app's actual root JSX has a single line instead of a pyramid.

Detailed Answer

Each provider needs to wrap everything below it, so nesting is structurally required — but the nesting doesn't need to be visible at every usage site. Two common flattening strategies:

// Strategy 1: one hand-written component, most readable for a small/fixed set
function AppProviders({ children }: { children: React.ReactNode }) {
  return (
    <ThemeProvider>
      <AuthProvider>
        <QueryClientProvider client={queryClient}>
          <I18nProvider>
            {children}
          </I18nProvider>
        </QueryClientProvider>
      </AuthProvider>
    </ThemeProvider>
  );
}
// <AppProviders><App /></AppProviders> — one line at the real root

// Strategy 2: generic composer for a dynamic/larger list of providers
function composeProviders(...providers: React.ComponentType<{ children: React.ReactNode }>[]) {
  return function Composed({ children }: { children: React.ReactNode }) {
    return providers.reduceRight(
      (acc, Provider) => <Provider>{acc}</Provider>,
      children
    );
  };
}
const AppProviders = composeProviders(ThemeProvider, AuthProvider, I18nProvider);

Strategy 1 is usually preferred for a small, stable set (readable, each provider's props are visible); Strategy 2 pays off when the provider list is long, dynamic (e.g. feature-flag driven), or shared across multiple apps.

Senior Engineer Perspective

Interviewers want to see you recognize this as the exact same "pyramid of doom" shape as render props, just at the app-composition level, and that a one-time wrapper component is a near-zero-cost fix. Mention the ordering matters: providers that depend on each other (an AuthProvider that needs QueryClientProvider to fetch the session) must nest in the correct dependency order, which is a real constraint on how far you can "just reorder" a composed list.

Q49. Two contexts — `ThemeContext` and `LocaleContext` — are both needed by a component. Do you combine them into one Context, or keep them separate? What are the trade-offs?

ROI: ★★★★☆ Frequency: High

Short Answer

Keep them separate unless they change together in lockstep. Separate contexts mean a consumer that only reads theme doesn't re-render when locale changes (and vice versa); a combined context re-renders every consumer of the merged value on any change to either piece, because Context has no field-level selector — any change to the value object invalidates every subscriber.

Detailed Answer

Context re-renders are all-or-nothing per Provider: when a Provider's value changes identity, every component calling useContext on it re-renders, regardless of which part of the value it actually reads. Combining unrelated concerns into one context maximizes unnecessary re-renders; splitting by "what changes together" minimizes them.

The one real reason to combine is when two pieces of state are conceptually one unit and always update together (e.g. a single reducer driving both x and y coordinates) — splitting those would be artificial. Theme and locale are unrelated concerns that change independently and rarely, so they should be two contexts (and, per Q10/Q48's provider pattern, two separate useTheme()/useLocale() hooks).

Code Example

// Separate — a locale-only consumer never re-renders when theme toggles
const theme = useTheme();     // subscribes to ThemeContext only
const locale = useLocale();   // subscribes to LocaleContext only

// A component using BOTH simply calls both hooks — no combined context required
function Header() {
  const { theme } = useTheme();
  const { locale } = useLocale();
  return <div className={theme}>{locale === 'fr' ? 'Bonjour' : 'Hello'}</div>;
}

Senior Engineer Perspective

The key phrase to use: "Context re-renders are all-or-nothing per provider, with no built-in selector" — that's the mechanical reason splitting helps, not just "it's cleaner." Also mention that a component needing both isn't a reason to merge contexts — it just calls both hooks, which composes fine.

Q50. Design a `ThemeProvider` that lets a nested part of the tree override the theme locally (e.g. a "dark section" inside a light-mode page). How does Context nesting/overriding actually work?

ROI: ★★★★☆ Frequency: High

Short Answer

Context consumers always read the nearest ancestor Provider, so nesting a second <ThemeProvider theme="dark"> deeper in the tree automatically overrides the outer one for everything inside it — no special merging logic needed, this is built into how Context resolution works.

Detailed Answer

This surprises people who assume Context is "global" — it isn't; it's tree-scoped. useContext walks up the tree from the calling component and returns the value from the closest Provider above it, exactly like CSS cascade/specificity by DOM proximity. Nesting providers is a first-class, intentional pattern, not a workaround.

Code Example

const ThemeContext = createContext<'light' | 'dark'>('light');

function ThemeProvider({ theme, children }: { theme: 'light' | 'dark'; children: React.ReactNode }) {
  return (
    <ThemeContext.Provider value={theme}>
      <div className={`theme-${theme}`}>{children}</div>
    </ThemeContext.Provider>
  );
}

function ThemedPage() {
  return (
    <ThemeProvider theme="light">
      <Header />                 {/* reads "light" */}
      <ThemeProvider theme="dark">
        <PromoBanner />          {/* reads "dark" — nearest provider wins */}
      </ThemeProvider>
      <Footer />                  {/* back to "light" — outside the nested provider */}
    </ThemeProvider>
  );
}

Senior Engineer Perspective

A sharp follow-up: "does the inner provider need to know the outer value to merge it?" Only if you want inheritance-like merging of a partial value (e.g. overriding just one field of a larger theme object) — in that case, read the outer context with useContext inside the inner provider and spread/merge it before providing the combined value. Otherwise, a full override (as above) needs nothing special.

Q51. How do you avoid re-rendering every Context consumer when only the "dispatch" side of a reducer-backed context is used? Explain the state/dispatch context split.

ROI: ★★★★★ Frequency: Extremely High

Short Answer

Provide state and dispatch through two separate Contexts instead of one combined object. dispatch from useReducer has a stable identity across renders, so a component that only calls dispatch and never reads state can subscribe to the dispatch-only context and never re-render when state changes — impossible if state and dispatch are bundled into a single context value.

Detailed Answer

If you provide { state, dispatch } as one context value, that object is a new reference every time state changes (even memoized, its identity must change because state did) — so every consumer re-renders on every state change, even the ones that only ever call dispatch to fire an action and never read state at all (a "Add Item" button, for instance). Splitting into StateContext and DispatchContext lets each component subscribe to only what it needs.

Code Example

const StateContext = createContext<State | null>(null);
const DispatchContext = createContext<React.Dispatch<Action> | null>(null);

function CartProvider({ children }: { children: React.ReactNode }) {
  const [state, dispatch] = useReducer(cartReducer, initialState);
  return (
    <StateContext.Provider value={state}>
      <DispatchContext.Provider value={dispatch}>   {/* dispatch's identity never changes */}
        {children}
      </DispatchContext.Provider>
    </StateContext.Provider>
  );
}

function useCartState() { return useContext(StateContext)!; }
function useCartDispatch() { return useContext(DispatchContext)!; }

// This button NEVER re-renders when cart items change — it only reads dispatch
function AddToCartButton({ item }: { item: Item }) {
  const dispatch = useCartDispatch();
  return <button onClick={() => dispatch({ type: 'add', item })}>Add</button>;
}

Senior Engineer Perspective

This is one of the highest-value, most concrete Context optimizations you can name, and it's specific enough (relying on dispatch's referential stability from useReducer) that it strongly distinguishes candidates who've actually optimized a Context-based store from those who've only used useMemo on a combined value.

Q52. What is a "selector" and why can't plain `useContext` provide one? How do libraries like `use-context-selector` or Zustand work around this?

ROI: ★★★★☆ Frequency: High

Short Answer

A selector is a function that picks out one slice of state so a component only re-renders when that slice changes, not the whole store. Built-in Context has no such mechanism — useContext always subscribes to the entire value and React has no way to know you "only care about `state.user.name`." Libraries work around this either by bypassing React Context entirely (Zustand subscribes components directly to a store object outside React, using useSyncExternalStore) or by patching Context's subscription model with a mutable ref plus manual re-render triggering (use-context-selector).

Detailed Answer

The structural limitation: Context's Provider value= is a single opaque value; React's Context implementation re-renders every consumer whenever that reference changes, full stop — there's no hook into "did the part you're subscribed to actually change." Zustand sidesteps the whole mechanism: your store is a plain object outside React, components call useStore(selector), which uses useSyncExternalStore to subscribe directly and re-render only when the selected slice's reference changes (comparing old vs. new selected value on every store update). This is why Zustand/Jotai feel like "Context with selectors" — they're not built on Context at all; they use React's lower-level external-store subscription API instead.

Code Example

// Zustand — selector means this component only re-renders when `user.name` changes,
// not on every store update
const useStore = create<{ user: { name: string; age: number } }>(() => ({
  user: { name: 'Ada', age: 30 },
}));

function NameLabel() {
  const name = useStore((s) => s.user.name);   // selector — scoped subscription
  return <span>{name}</span>;
}

Senior Engineer Perspective

Naming useSyncExternalStore specifically is the detail that shows you understand how Zustand achieves selector-based subscriptions rather than treating it as unexplained magic — it's the React 18 primitive purpose-built for external stores to subscribe outside the Context re-render model.

Q54. A `` at the app root re-renders on every route change because it's declared inside a component that re-renders on navigation. What's the fix, and why does provider placement matter?

Placement matters because every re-render of the component holding the provider risks constructing a new value object, which cascades to every consumer below.

Q55. When should cross-cutting concerns use Context vs. simply being passed as a prop from a layout component? Walk through a concrete decision.

ROI: ★★★★☆ Frequency: High

Short Answer

Use Context when the value is needed by components at unpredictable, varying depths that you can't enumerate at the layout level (theme, auth, locale — used by dozens of leaf components scattered across the tree). Use a plain prop from a layout/parent when the set of consumers is small, fixed, and close to the top — passing two or three props down one or two levels is simpler to trace than introducing a context for something so narrow.

Detailed Answer

Concretely: if currentUser is read by a header avatar, a settings page, a billing page, an admin gate deep in a nested route, and a dozen other places you can't predict in advance, Context is the right call — enumerating and threading that prop through every intermediate layout component would be exactly the prop-drilling problem Context exists to solve. But if a <PageHeader title, onBack> only ever gets its props from the one route component that renders it directly, wrapping that in Context is pure overhead — a prop is simpler, more discoverable (visible in the JSX), and doesn't carry Context's all-consumers-re-render cost for something that's already local.

The rule of thumb: prop for depth-1/2 and a known, small consumer set; Context for unpredictable depth and a broad, cross-cutting consumer set.

Senior Engineer Perspective

Watch for candidates who reach for Context reflexively for everything "shared" — the strongest answer explicitly pushes back and asks "how deep, and how many consumers?" before reaching for Context, treating it as a tool with real costs (re-render scope, indirection), not a default.

SECTION 9 - CONTAINER/PRESENTATIONAL SPLIT IN A HOOKS WORLD

Q56. In a codebase that uses hooks for everything, where does the container/presentational boundary actually live now?

ROI: ★★★★☆ Frequency: High

Short Answer

The boundary moved from "two components" to "a hook and a component": the custom hook (useUserProfile()) plays the old container's role — owning fetching, caching, derived state — while the component that calls it plays the presentational role, receiving the hook's return value the same way it used to receive props from a container. The component itself is often still fully presentational in spirit; it just gets its data from a hook call instead of a wrapping component's props.

Detailed Answer

This distinction matters for testability and reuse in exactly the way the old pattern intended: you can test useUserProfile() in isolation with renderHook, and you can test/Storybook the presentational half by passing it plain mock props — you've simply removed the extra wrapper component that used to exist solely to own state. The discipline (separate "how data is fetched" from "how it's rendered") is unchanged; only the syntactic vehicle changed from a component to a function.

Code Example

// The hook is the "container" — owns fetching/derived state
function useUserProfile(userId: string) {
  const { data: user, isLoading, error } = useQuery({
    queryKey: ['user', userId],
    queryFn: () => fetchUser(userId),
  });
  const initials = user ? user.name.split(' ').map((n) => n[0]).join('') : '';
  return { user, initials, isLoading, error };
}

// The component is the "presentational" half — pure given its inputs
function UserProfile({ userId }: { userId: string }) {
  const { user, initials, isLoading, error } = useUserProfile(userId);
  if (isLoading) return <Spinner />;
  if (error) return <ErrorMessage error={error} />;
  return <ProfileCard name={user.name} initials={initials} avatar={user.avatar} />;
}

// ProfileCard itself is 100% presentational and Storybook-able with plain props
function ProfileCard({ name, initials, avatar }: { name: string; initials: string; avatar: string }) { /* ... */ }

Senior Engineer Perspective

The strongest framing: "the split didn't disappear, its syntax changed" — a hook plus a render function is structurally the same separation of concerns as a container plus a presentational component, just without a superfluous wrapper component in the tree. Bonus: note that ProfileCard staying fully props-only (no hooks of its own) is what keeps it trivially reusable in Storybook and design-system contexts.

Q57. How do you unit test the data-fetching "container" logic separately from the rendering logic when both live in the same component via a hook?

ROI: ★★★★☆ Frequency: High

Short Answer

Extract the data logic into its own named hook (not inlined in the component) and test it directly with @testing-library/react's renderHook, mocking the network layer. Test the rendering component separately by passing it plain, hand-constructed props (or rendering it with a mocked hook return value) — exactly the same two-test strategy the old container/presentational split enabled, just targeting a hook instead of a container component.

Q58. Should a component library (design system) still enforce a strict presentational-only rule for its components? Why might that still matter even though app code has relaxed it?

ROI: ★★★★☆ Frequency: High

Short Answer

Yes — a design system's components are meant to be portable across many apps and contexts, so keeping them strictly props-only (no data fetching, no app-specific Context reads) is what makes them reusable, Storybook-able, and framework-agnostic in the first place. App-level feature components can reasonably blend data and rendering via hooks because they're inherently tied to one app's data layer; a shared Button/Modal/Table component should never be.

Detailed Answer

The reason the container/presentational rule "faded" was specifically about feature components inside a single app, where hooks removed the need for an artificial wrapper. A design system component has a different job: it's consumed by potentially many apps, each with different data sources, routers, and auth systems. If a <Table> component reached into a specific app's useCurrentUser() hook, it could never be dropped into a different app or a Storybook sandbox without dragging that app's entire context setup along with it.

So the modern rule is contextual, not universal: presentational purity is a hard requirement for shared/library components, and a relaxed, hook-friendly blend is fine for app-specific feature components that will never be reused outside their one app.

Senior Engineer Perspective

This question tests whether a candidate can hold two seemingly contradictory truths at once — "the strict split faded" and "the strict split still matters here" — and correctly explain why the boundary is different for library code vs. app code, rather than picking one blanket answer.

Q59. What does "separating data-fetching from rendering logic" buy you concretely, beyond testability? Discuss caching, request deduplication, and reuse.

ROI: ★★★★☆ Frequency: High

Short Answer

Beyond easier testing, it lets multiple components reuse the exact same data hook (and, with TanStack Query, the exact same cache entry and in-flight request) without duplicating fetch logic, and it means swapping the data source (REST to GraphQL, or adding optimistic updates) touches one hook instead of every component that renders that data.

Detailed Answer

If three different components on a page all call useUser(userId) built on useQuery, TanStack Query deduplicates the underlying network request (one fetch for that queryKey, regardless of how many components ask for it) and serves all three from the same cache entry. If fetching were inlined per-component with raw useEffect + fetch, each component would issue its own redundant request, and there'd be no shared cache to invalidate consistently after a mutation.

Reuse is the other win: useUser can be called from a profile page, a settings page, and a header avatar — all get the same data-fetching behaviour, loading/error states, and caching semantics for free, with zero duplicated logic.

Code Example

// One hook, reused by three unrelated components — one shared cache entry
function useUser(userId: string) {
  return useQuery({ queryKey: ['user', userId], queryFn: () => fetchUser(userId) });
}

function ProfilePage({ userId }: { userId: string }) {
  const { data: user } = useUser(userId);       // dedupes with the calls below
  return <h1>{user?.name}</h1>;
}
function HeaderAvatar({ userId }: { userId: string }) {
  const { data: user } = useUser(userId);       // same cache entry, no extra request
  return <img src={user?.avatar} />;
}

Q60. A "presentational" component starts calling `useState` internally for a dropdown's open/closed state. Does this violate the container/presentational split? Where's the line?

ROI: ★★★★☆ Frequency: High

Short Answer

No — the split was always about data/business logic versus rendering, not about banning all local state. Purely visual, ephemeral UI state (is a dropdown open, is an accordion expanded, is an input focused) is squarely presentational concern: it doesn't come from a server, doesn't need to be shared, and doesn't affect the component's reusability. The line is whether the state represents application/domain data (a fetched user, a saved preference) versus transient UI state local to how the component displays itself.

Detailed Answer

The original container/presentational articles sometimes got over-read as "presentational components must have zero state," which was never quite the intent — even in the class era, a presentational component could hold trivial UI-only state. The actual test: if you deleted this component and rebuilt it in a totally different app with different data sources, would this state still make sense to keep exactly as-is? A dropdown's open/closed flag: yes, obviously. A fetched list of users: no, that's tied to this app's data layer and belongs in a hook, not baked into the presentational shell.

Code Example

// Still presentational — internal state is purely visual/UI, not domain data
function Dropdown({ label, options, onSelect }: DropdownProps) {
  const [open, setOpen] = useState(false);   // fine: purely UI state
  return (
    <div>
      <button onClick={() => setOpen((o) => !o)}>{label}</button>
      {open && (
        <ul>{options.map((o) => <li key={o.id} onClick={() => onSelect(o)}>{o.label}</li>)}</ul>
      )}
    </div>
  );
}

Senior Engineer Perspective

The crisp test to state out loud: "would this state still make sense if I dropped this component into an unrelated app?" UI state passes that test; domain/fetched state doesn't. This reframing shows you understand the intent behind the old rule rather than a literal, overly rigid reading of it.

Q61. How would you refactor a component that mixes fetching, business logic, and rendering all in one 200-line function into a clean container/presentational-equivalent split using hooks?

ROI: ★★★★★ Frequency: Extremely High

Short Answer

The refactor is almost mechanical: identify every useEffect/useState/computation block that isn't directly about "what JSX do I return," and lift it into a hook with a descriptive name.

Detailed Answer

  const [loading, setLoading] = useState(true);
  useEffect(() => {
    fetchOrder(orderId).then((o) => { setOrder(o); setLoading(false); });
  }, [orderId]);

  // ...50 lines of tax/discount/shipping calculations inline...
  // ...100 lines of JSX...
}

// AFTER: logic extracted into named hooks, component stays thin
function useOrder(orderId: string) {
  return useQuery({ queryKey: ['order', orderId], queryFn: () => fetchOrder(orderId) });
}

  return useMemo(() => {
    if (!order) return null;
    const subtotal = order.items.reduce((s, i) => s + i.price * i.qty, 0);

    const shipping = computeShipping(order);
    return { subtotal, tax, shipping, total: subtotal + tax + shipping };

Q63. When migrating a large legacy app off explicit `*Container.tsx`/`*View.tsx` file pairs, what risks should you watch for, and how do you validate the refactor didn't change behaviour?

ROI: ★★★★☆ Frequency: Medium-High

Short Answer

The main risk is subtly changing re-render timing or effect ordering while moving logic from a container's lifecycle methods into hooks — effects and lifecycle methods aren't a 1:1 mapping. Validate with existing integration/snapshot tests run before and after, and by diffing the component's render output and network call sequence in a staging environment before merging, not just by trusting the refactor "looks equivalent."

Detailed Answer

  • Effect timing differences — componentDidMount runs once; a useEffect(() => {...}, []) is the closest equivalent, but if the container had logic split across componentDidMount and componentDidUpdate reacting to the same prop, merging that into one effect with a dependency array can subtly change how many times it fires during the transition period if dependencies aren't listed correctly.
  • Loss of `shouldComponentUpdate`/`PureComponent` optimizations — if the container relied on these for performance, the hook-based rewrite needs an equivalent (React.memo, useMemo) or you can silently regress performance.
  • Test coverage gaps — container/view splits often had container tests mocking the view and view tests using shallow rendering; hook-based code needs renderHook-based tests as a direct replacement, not just fewer tests overall.

The validation strategy that actually catches regressions: run the existing test suite unchanged against the refactored code first (proving external behaviour is preserved before touching tests), then modernize the tests separately as a follow-up, not the same commit.

Senior Engineer Perspective

The strongest answer treats this as a behaviour-preserving refactor with a specific validation gate — old tests must pass unmodified first — rather than a rewrite where tests and implementation change together, which makes it impossible to tell whether a passing suite is testing the same guarantees as before.

SECTION 10 - POLYMORPHIC COMPONENTS

Q64. What is a polymorphic component, and what problem does the `as` prop solve?

ROI: ★★★★★ Frequency: Extremely High

Short Answer

A polymorphic component renders as a different underlying element or component depending on an as prop, while keeping its own styling and behaviour — <Text as="h1"> renders an <h1>, <Text as="p"> renders a <p>, both styled identically by the same component. It solves the problem of needing a separate component per HTML tag (Heading1, Heading2, Paragraph...) just to vary the rendered element, while preserving semantic HTML and correct prop typing for whichever element is chosen.

Detailed Answer

Without polymorphism, a design system either duplicates styling logic across many tag-specific components, or forces every use of a styled text component into one fixed tag (usually a <div> or <span>), sacrificing semantic HTML. The as prop pattern — popularized by styled-components, Chakra UI, and Radix's asChild — lets one component own the visual styling while the caller controls which real DOM element or custom component it renders as, keeping both style consistency and semantic correctness.

Code Example

function Text({ as: Component = 'span', children, ...rest }: {
  as?: React.ElementType;
  children: React.ReactNode;
} & React.HTMLAttributes<HTMLElement>) {
  return <Component className="text-styles" {...rest}>{children}</Component>;
}

<Text as="h1">Page Title</Text>      {/* renders <h1 class="text-styles"> */}
<Text as="p">Body copy</Text>         {/* renders <p class="text-styles"> */}
<Text as={Link} to="/home">Home</Text> {/* renders a router Link, styled like Text */}

Senior Engineer Perspective

Name concrete real-world users: styled-components' as prop, Chakra UI's polymorphic as, and Radix's asChild (a related but distinct mechanism using Slot/cloning rather than a dynamic tag). Knowing the difference between "renders a different tag" (as) and "merges props onto a single child you provide" (asChild) signals real exposure to modern design-system code.

Q65. Correctly type a polymorphic component in TypeScript so that when `as="a"`, the component accepts `href`, and when `as="button"`, it accepts `onClick`/`disabled` — with no `any`.

ROI: ★★★★★ Frequency: Extremely High

Short Answer

Make the component generic over the element type C extends React.ElementType, and intersect your own props with React.ComponentPropsWithoutRef<C> so TypeScript infers the correct attribute set (href, onClick, etc.) based on whatever as is set to at each call site.

Detailed Answer

React.ElementType covers both string tag names ('a', 'button') and component types. ComponentPropsWithoutRef<C> resolves to the exact prop set for whatever C is — the full JSX.IntrinsicElements['a'] shape for 'a', or a custom component's own prop type if C is a component. Making the component itself generic (not just its props type) lets TypeScript re-infer this per call site.

Code Example

type PolymorphicProps<C extends React.ElementType, Props = {}> = Props & {
  as?: C;
} & Omit<React.ComponentPropsWithoutRef<C>, keyof Props | 'as'>;

type ButtonOwnProps = { variant?: 'primary' | 'secondary' };

function Button<C extends React.ElementType = 'button'>({
  as,
  variant = 'primary',
  ...rest
}: PolymorphicProps<C, ButtonOwnProps>) {
  const Component = as || 'button';
  return <Component className={`btn btn--${variant}`} {...rest} />;
}

// Renders a <button> — onClick/disabled are correctly typed, href would be a type error
<Button onClick={() => save()} disabled={saving}>Save</Button>

// Renders an <a> — href is now correctly required/typed, onClick still allowed,
// TypeScript infers this entirely from `as="a"`
<Button as="a" href="/docs">Docs</Button>

Senior Engineer Perspective

This is a genuinely hard TypeScript pattern and a strong differentiator — most candidates either give up and type as as any/string, or forget ComponentPropsWithoutRef and instead reach for React.HTMLProps, which doesn't correctly discriminate per-tag attributes. Mentioning that libraries like Radix and Chakra ship this exact generic pattern (often with an added ref forwarding layer) shows you've seen it done for real, not just invented a toy version.

Q66. How do you additionally forward a `ref` correctly on a polymorphic component, given that the underlying DOM node type changes depending on `as`?

ROI: ★★★★☆ Frequency: High

Short Answer

Wrap the component in React.forwardRef with a generic ref type derived from C via React.ComponentPropsWithRef<C>['ref'] or React.ElementRef<C>, so the ref's type correctly switches between, say, HTMLButtonElement and HTMLAnchorElement depending on what as resolves to at each call site — forwardRef itself isn't naturally generic over multiple call sites, so most implementations cast once internally and rely on a separate exported type helper for consumer-facing inference.

Detailed Answer

This is the point where polymorphic + ref-forwarding typing gets genuinely gnarly, because forwardRef's own type signature isn't generic-friendly across arbitrary call sites the way a plain function component's generic type parameter is. The pragmatic, widely-used solution (used by Radix's internal Polymorphic types) is to define the component as a generic function, cast the ref internally, and export a helper type for the component's public generic signature so consumers still get correct inference despite the internal cast.

Code Example

type PolymorphicRef<C extends React.ElementType> = React.ComponentPropsWithRef<C>['ref'];

type ButtonProps<C extends React.ElementType> = PolymorphicProps<C, { variant?: 'primary' | 'secondary' }>;

type ButtonComponent = <C extends React.ElementType = 'button'>(
  props: ButtonProps<C> & { ref?: PolymorphicRef<C> }
) => React.ReactElement | null;

const Button = React.forwardRef(function Button<C extends React.ElementType = 'button'>(
  { as, variant = 'primary', ...rest }: ButtonProps<C>,
  ref?: PolymorphicRef<C>
) {
  const Component = as || 'button';
  return <Component ref={ref} className={`btn btn--${variant}`} {...rest} />;
}) as ButtonComponent;   // one internal cast; consumer-facing type stays fully generic

// Consumers get a correctly-typed ref for whichever `as` they pass
const linkRef = useRef<HTMLAnchorElement>(null);
<Button as="a" href="/docs" ref={linkRef}>Docs</Button>

Senior Engineer Perspective

Almost nobody derives this cold in an interview, and that's fine — the strong signal is recognizing why it's hard (forwardRef's signature resists per-call-site generics) and knowing the standard workaround is a single controlled internal cast plus an exported generic function type, rather than sprinkling any throughout. Mentioning you'd reach for a battle-tested utility type (many teams vendor Radix's or Reach UI's polymorphic type helpers) rather than hand-rolling this from scratch is a mature, pragmatic answer.

Q67. What real-world component libraries use the `as` prop pattern, and what convention does Radix use instead (`asChild`)? Compare the two mechanisms.

ROI: ★★★★☆ Frequency: High

Short Answer

styled-components, Chakra UI, and Reach UI use as to swap the rendered tag. Radix instead uses asChild, which doesn't take a tag name at all — it tells the component "don't render your own wrapper element; merge your props onto the single child element I gave you instead," implemented internally with a Slot component that clones the child and merges props/refs/event handlers.

Detailed Answer

// as prop — you tell the component WHAT tag to become
<Text as="h1">Title</Text>

// asChild — you tell the component to merge its behaviour onto YOUR OWN child element
<Tooltip.Trigger asChild>
  <MyCustomButton>Hover me</MyCustomButton>
</Tooltip.Trigger>
// Tooltip.Trigger doesn't render its own <button> — it merges its onMouseEnter/
// aria-describedby etc. directly onto <MyCustomButton> via Radix's <Slot>

The practical difference: as is simplest when you just want a different tag with the same props shape. asChild is more powerful when the consumer's element is a whole separate component (with its own, possibly very different, prop API) that the wrapping component needs to attach behaviour to without knowing or caring about that component's internals — it avoids the "what if my custom component doesn't accept the exact same props as a native tag" problem that a naive as implementation would hit.

Senior Engineer Perspective

Being able to articulate that asChild solves a problem as doesn't — attaching behaviour to a consumer's own arbitrary component, not just swapping a tag name — shows deeper exposure to headless UI internals than reciting "Radix uses asChild" as a fact without explaining the mechanism.

Q68. What runtime pitfalls exist with polymorphic components — e.g. passing an invalid prop through to a DOM element when `as` is a native tag?

ROI: ★★★★☆ Frequency: High

Short Answer

Because a polymorphic component typically spreads ...rest onto whatever as resolves to, a prop that's valid for a custom component but not for a native DOM tag (e.g. passing variant straight through instead of consuming it) leaks onto the DOM node, producing React's "unknown DOM attribute" warning and invalid HTML. The fix is destructuring every component-specific prop out of rest before spreading, so only genuinely native/forwarded attributes reach the DOM.

Detailed Answer

// BUG: `variant` isn't destructured out, so it leaks onto whatever `as` becomes
function Button({ as: Component = 'button', ...rest }) {
  return <Component {...rest} />;   // rest still includes `variant`!
}
<Button as="a" href="/x" variant="primary">Go</Button>
// -> renders <a href="/x" variant="primary"> — React warns: unknown DOM attribute "variant"

// FIX: destructure every component-owned prop before spreading the remainder
function Button({ as: Component = 'button', variant = 'primary', ...rest }) {
  return <Component className={`btn--${variant}`} {...rest} />;   // rest is now DOM-safe
}

A second, subtler pitfall: when as is a custom component rather than a native tag, that custom component might not accept the same prop shape at all (e.g. it expects label instead of children) — spreading blindly assumes prop-shape compatibility across every possible as target, which isn't guaranteed and needs to be a documented contract for the polymorphic component to be used safely.

Senior Engineer Perspective

The specific failure mode — "own props leak onto the DOM node as invalid attributes" — is exactly the kind of thing that shows up as a console warning in real apps using this pattern, and naming it precisely (rather than a vague "watch your props") demonstrates hands-on debugging experience.

Q69. Why might a design system deliberately choose NOT to offer a polymorphic `as` prop on some components, even though it's technically possible?

ROI: ★★★☆☆ Frequency: Medium

Short Answer

Polymorphism trades type safety and predictability for flexibility — every additional valid as target multiplies the prop combinations a component must support and test, and it lets consumers render semantically wrong combinations (e.g. <Heading as="button">) that a fixed-tag component would simply prevent by construction. Some teams intentionally restrict as to a small allow-list, or omit it entirely for components where the semantic element genuinely should never vary (a <Checkbox> should probably always be an <input type="checkbox">).

Detailed Answer

Polymorphism is a real cost: the TypeScript types get considerably more complex (as seen in Q65/Q66), the component must handle a wider matrix of prop shapes, and misuse becomes possible in ways a monomorphic component structurally rules out. For components where the rendered tag is part of the component's identity and correctness (form controls, semantic landmarks like <nav>), many design systems deliberately skip as and instead offer a small, explicit set of variant props, or a restricted union like as?: 'h1' | 'h2' | 'h3' rather than the fully open React.ElementType.

Code Example

// Restricted polymorphism — only headings are valid, not arbitrary elements
type HeadingProps = { as?: 'h1' | 'h2' | 'h3' | 'h4' | 'h5' | 'h6' } & React.HTMLAttributes<HTMLHeadingElement>;

Senior Engineer Perspective

This question rewards restraint over cleverness — the ability to say "I could make this fully polymorphic, but I'd deliberately narrow it here" shows design judgment, not just technical capability. It's a good pairing with Q69's own topic and the earlier component API design principles question.

Q70. How would you test a polymorphic component to make sure it behaves correctly for every supported `as` value, without writing near-duplicate test files per tag?

ROI: ★★★☆☆ Frequency: Medium

Short Answer

Parametrize the test with test.each (or your framework's equivalent) over the list of supported as values, asserting the invariants that must hold regardless of tag (renders the expected tag name, applies the shared className, forwards ...rest), then add a small number of tag-specific tests only for behaviour that genuinely differs (e.g. an <a> needs an href).

Code Example

const asValues: React.ElementType[] = ['button', 'a', 'div'];

  render(<Button as={as} data-testid="btn">Click</Button>);
  const el = screen.getByTestId('btn');
  expect(el.tagName.toLowerCase()).toBe(as);

Q72. Compare React's named-prop slots to Vue's named `` template syntax conceptually. What does React lack that Vue provides natively, and how do you compensate?

ROI: ★★★☆☆ Frequency: Medium

Short Answer

This is actually a strength in disguise — because slots are just props, they compose with the rest of JavaScript (conditionals, loops, generics) without any special-case syntax to learn.

Q74. What happens if you pass BOTH `children` and a function-as-children prop to the same component — how do you decide which one takes precedence, and is offering both ever a good idea?

ROI: ★★★☆☆ Frequency: Medium

Short Answer

If a component wants to support both static JSX children and a function that receives state, it needs two separate named props (e.g. children for static content, plus a distinct render prop for the dynamic case) — otherwise the component must inspect typeof children === 'function' at runtime and branch, which works but is a slightly unusual API to document and discover.

Q76. How would you type a "children as a function" prop in TypeScript when the function can optionally return `null` for conditional rendering, and ensure callers can't accidentally pass plain JSX by mistake?

Short Answer

type ToggleProps = {

};

function Toggle({ children }: ToggleProps) {
  const [on, setOn] = useState(false);
  return <>{children({ on, toggle: () => setOn((o) => !o) })}</>;
}

// Compile error — plain JSX isn't assignable to a function type

// Correct usage — a function returning JSX (or null)

Point out explicitly that this is a case where TypeScript's structural typing actively helps catch a common consumer mistake (passing static JSX to a render-prop component) at compile time rather than producing a confusing runtime error like "children is not a function" deep inside the component.

Q77. What's the performance implication of children-as-a-function when the parent component that owns the state re-renders frequently (e.g. tracking mouse position on every `mousemove`)? How would you scope re-renders?

ROI: ★★★★☆ Frequency: High

Short Answer

Every state update in the render-prop owner re-invokes the children function and re-renders whatever it returns — for a high-frequency source like mouse position, that means re-rendering the consumer's markup on every single mousemove event, which can be expensive if that markup is non-trivial. You scope this by pushing the expensive rendering into a child that's wrapped in React.memo and only re-renders when the specific derived value it cares about changes, or by throttling/debouncing the underlying state updates so fewer renders happen in the first place.

Detailed Answer

// Every mousemove re-renders the ENTIRE consumer tree via the function-child
<MousePosition>
  {(pos) => <ExpensiveVisualization x={pos.x} y={pos.y} />}
</MousePosition>

// Mitigation 1: memoize the expensive piece — still re-renders on every move,
// but at least avoids re-rendering unrelated sibling output outside this subtree
const MemoVisualization = React.memo(ExpensiveVisualization);

// Mitigation 2: throttle updates at the source, reducing how often ANY render happens
function useThrottledMousePosition(ms: number) {
  const [pos, setPos] = useState({ x: 0, y: 0 });
  useEffect(() => {
    const handler = throttle((e: MouseEvent) => setPos({ x: e.clientX, y: e.clientY }), ms);
    window.addEventListener('mousemove', handler);
    return () => window.removeEventListener('mousemove', handler);
  }, [ms]);
  return pos;
}

The deeper point: this cost is inherent to the data source's update frequency, not specific to render props — a hook-based useMousePosition() called directly in a component has the exact same re-render frequency problem. Render props don't make this worse; they just make the coupling between "state changes" and "consumer re-renders" more visually obvious in the JSX.

Senior Engineer Perspective

The critical correction to make explicitly: this isn't a render-prop-specific cost, it's a high-frequency-state cost that would exist with hooks too — conflating the two is a common mistake. The fix (throttle/debounce at the source, or memoize the expensive consumer) applies identically either way.

Q78. How do "slots" interact with server components (RSC)? Can a Server Component pass a function-as-children to a Client Component?

Q80. What does "headless" mean in "headless component/UI library," and how does it differ from a normal component library like MUI or Bootstrap?

ROI: ★★★★★ Frequency: Extremely High

Getting dropdown keyboard navigation, focus trapping, and ARIA attributes exactly right is genuinely hard and easy to get subtly wrong; headless libraries let you depend on a well-tested implementation of that behaviour while keeping full control of markup and CSS, so the result looks exactly like your design system rather than "obviously MUI with a color override."

Q81. Build a headless `useDropdown()` hook that returns prop getters for the trigger and menu, with keyboard navigation (arrow keys, Escape, Enter) and no rendered markup at all.

ROI: ★★★★★ Frequency: Extremely High

Short Answer

The hook owns open/closed and highlighted-index state and exposes prop getters (getTriggerProps, getMenuProps, getItemProps) that attach the correct event handlers and ARIA attributes to whatever markup the consumer renders — the hook itself renders nothing, which is what makes it "headless."

Code Example

function useDropdown(itemCount: number) {
  const [isOpen, setIsOpen] = useState(false);
  const [highlightedIndex, setHighlightedIndex] = useState(-1);

  const getTriggerProps = () => ({
    'aria-haspopup': 'listbox' as const,
    'aria-expanded': isOpen,
    onClick: () => setIsOpen((o) => !o),
    onKeyDown: (e: React.KeyboardEvent) => {
      if (e.key === 'ArrowDown') { e.preventDefault(); setIsOpen(true); setHighlightedIndex(0); }
    },
  });

  const getMenuProps = () => ({
    role: 'listbox' as const,
    onKeyDown: (e: React.KeyboardEvent) => {
      if (e.key === 'ArrowDown') { e.preventDefault(); setHighlightedIndex((i) => Math.min(i + 1, itemCount - 1)); }
      if (e.key === 'ArrowUp')   { e.preventDefault(); setHighlightedIndex((i) => Math.max(i - 1, 0)); }
      if (e.key === 'Escape')    { setIsOpen(false); }
      if (e.key === 'Enter')     { setIsOpen(false); }
    },
  });

  const getItemProps = (index: number) => ({
    role: 'option' as const,
    'aria-selected': index === highlightedIndex,
    onMouseEnter: () => setHighlightedIndex(index),
    onClick: () => setIsOpen(false),
  });

  return { isOpen, highlightedIndex, getTriggerProps, getMenuProps, getItemProps };
}

// Consumer owns 100% of the markup; the hook owns 100% of the behaviour
function CountryDropdown({ countries }: { countries: string[] }) {
  const { isOpen, highlightedIndex, getTriggerProps, getMenuProps, getItemProps } = useDropdown(countries.length);
  return (
    <div>
      <button {...getTriggerProps()}>Select country</button>
      {isOpen && (
        <ul {...getMenuProps()}>
          {countries.map((c, i) => <li key={c} {...getItemProps(i)} style={{ background: i === highlightedIndex ? '#eef' : undefined }}>{c}</li>)}
        </ul>
      )}
    </div>
  );
}

Q83. What accessibility responsibilities does a headless library take on that you would almost certainly get wrong (or skip) if you hand-rolled a dropdown yourself?

ROI: ★★★★★ Frequency: Extremely High

Short Answer

Focus management (moving focus into the menu on open, returning it to the trigger on close), full keyboard support (arrow keys, Home/End, type-ahead search by typing letters), correct ARIA roles and relationships (role="listbox"/option, aria-activedescendant vs. actually moving DOM focus), and screen-reader announcements for state changes — each is individually a well-known, non-obvious amount of work that's easy to under-scope when estimating "just build a dropdown."

Detailed Answer

  • Focus vs. `aria-activedescendant` — a common naive implementation moves actual DOM focus to each highlighted option; the correct pattern for a listbox often keeps focus on the input/trigger and uses aria-activedescendant to tell assistive tech which option is "virtually" focused, so typing keeps working normally. Getting this wrong breaks the experience for screen-reader and keyboard-only users in ways that are invisible if you only test with a mouse.
  • Type-ahead — typing letters while a listbox is open should jump to the matching option; implementing debounced multi-character type-ahead correctly (not just single-letter) is more involved than it looks.
  • Focus return on close — closing a dropdown/modal must restore focus to the element that opened it, or keyboard users lose their place entirely.
  • Live region announcements — screen readers need to be told "5 results available" or "option selected" via aria-live, something visual-only testing never surfaces as missing.

Senior Engineer Perspective

This question specifically tests whether you've ever actually used a screen reader to test your own component, or only clicked through it with a mouse. Q85. What's the difference between a headless *component* (e.g. Downshift's `` render-prop component) and a headless *hook* (e.g. `useCombobox`)? Is there ever a reason to prefer the component form today?

Detailed Answer

Class components are the clearest concrete case: a hook simply cannot be called inside a class component's render() — hooks only work in function components. If a legacy class component needs headless dropdown behaviour, the render-prop/component form is the only option available, since it's just a normal React element being rendered, not a hook call.

Q87. Build your own minimal headless `Tooltip` (no styling) that handles hover delay, keyboard focus, and dismissing on Escape, without any library. What's genuinely hard about getting this right?

ROI: ★★★★☆ Frequency: High

Short Answer

The genuinely hard parts are timing (a show delay so tooltips don't flash on incidental mouse passes, and a hide delay so moving toward the tooltip itself doesn't dismiss it), making it work identically for keyboard focus (not just hover — a keyboard-only user tabbing to the trigger must see the tooltip too), and dismissing on Escape without stealing focus from the trigger element.

Code Example

function useTooltip({ showDelay = 300, hideDelay = 100 } = {}) {
  const [open, setOpen] = useState(false);
  const showTimer = useRef<ReturnType<typeof setTimeout>>();
  const hideTimer = useRef<ReturnType<typeof setTimeout>>();

  const show = () => {
    clearTimeout(hideTimer.current);
    showTimer.current = setTimeout(() => setOpen(true), showDelay);
  };
  const hide = () => {
    clearTimeout(showTimer.current);
    hideTimer.current = setTimeout(() => setOpen(false), hideDelay);
  };

  const getTriggerProps = () => ({
    onMouseEnter: show,
    onMouseLeave: hide,
    onFocus: () => setOpen(true),      // keyboard focus shows immediately, no delay
    onBlur: () => setOpen(false),
    onKeyDown: (e: React.KeyboardEvent) => { if (e.key === 'Escape') setOpen(false); },
  });

  const getTooltipProps = () => ({
    role: 'tooltip' as const,
    onMouseEnter: () => clearTimeout(hideTimer.current),   // moving onto the tooltip cancels hide
    onMouseLeave: hide,
  });

  useEffect(() => () => { clearTimeout(showTimer.current); clearTimeout(hideTimer.current); }, []);

  return { open, getTriggerProps, getTooltipProps };
}

Project Example

A hand-rolled tooltip we shipped initially only handled hover — QA flagged that keyboard users tabbing through the toolbar got zero tooltip feedback at all, and Escape didn't dismiss it either. Adding onFocus/onBlur parity with the hover handlers, and the Escape handler, fixed both, but it took an accessibility pass to even notice the gaps — they're invisible if you only test with a mouse.

Senior Engineer Perspective

The single most valuable thing to say unprompted: "hover and keyboard focus need to be fully parallel triggers, not just hover with focus as an afterthought" — most naive tooltip implementations only wire up mouse events and silently fail every keyboard-only user, and interviewers specifically probe for whether you catch that gap yourself.

Q88. A component has grown to accept 15 boolean props (`showHeader`, `compact`, `rounded`, `bordered`, `dense`, ...). Walk through how you'd refactor its API, and what signals tell you it's time to split the component instead of adding another prop.

ROI: ★★★★★ Frequency: Extremely High

Short Answer

Group related booleans into a single variant or config object where the combinations are actually meaningful together (density: 'compact' | 'comfortable' instead of separate dense/compact booleans), replace booleans that gate entire regions of markup with composition (slots/children) instead, and split the component into two when the prop growth reflects genuinely different use cases rather than variations of the same one — the signal for splitting is when props start being mutually exclusive or only make sense in specific combinations, meaning you're really modeling several components crammed into one API.

Detailed Answer

Refactor moves, roughly in order of impact

  • Collapse mutually-exclusive booleans into one enum prop — compact/comfortable/spacious booleans that can only have one true at a time should be density: 'compact' | 'comfortable' | 'spacious', which also makes illegal combinations (two "true" at once) impossible.
  • Replace "does this component show region X" booleans with composition — showHeader becomes simply: pass a header slot or don't; there's no boolean needed at all if the slot's presence/absence is the signal.
  • Watch for props that only make sense together — if bordered only has visual effect when rounded is also true, that's a sign these aren't independent toggles but a single design decision that should be one prop (or a fixed visual variant).

Signals it's time to split into separate components

When you find yourself writing "if variant === 'modal', ignore props a/b/c and only d/e apply" — that conditional prop relevance is the tell. At that point you have two components sharing some markup, not one flexible component; extract the shared parts into a base/hook and split the public API in two.

Code Example

// BEFORE: boolean explosion, unclear valid combinations
<Card showHeader compact bordered rounded dense hoverable clickable />

// AFTER: enums for mutually exclusive states, composition for optional regions
<Card density="compact" appearance="bordered" interactive>
  {header && <Card.Header>{header}</Card.Header>}
  <Card.Body>...</Card.Body>
</Card>

Senior Engineer Perspective

The strongest signal is naming the specific tell for "split, don't add a prop": conditional prop relevance, where some props only matter for certain values of another prop. That's the concrete, teachable heuristic — far more useful in an interview than a vague "boolean props are bad."

Q89. What naming conventions do you follow for event-handler props, and why does `onChange`/`onClick` win over alternatives like `changeHandler` or `handleChange`?

ROI: ★★★★☆ Frequency: High

Short Answer

Prop names describing an event a component fires should read onX (onChange, onSelect, onOpenChange) to match React's own native-element convention, so consumers never have to learn a component-specific naming scheme. handleX is reserved, by convention, for the function the consumer defines to pass into that prop — keeping on- vs. handle- distinct on each side of the boundary makes it instantly clear, reading any file, which side owns which name.

Detailed Answer

// Convention: the PROP is onX, the consumer's own function is handleX
function Modal({ onClose }: { onClose: () => void }) { /* ... */ }

function Page() {
  const handleClose = () => { analytics.track('modal_closed'); setModalOpen(false); };
  return <Modal onClose={handleClose} />;
}

This isn't just style preference — it directly matches how native DOM elements already work (<input onChange={...}>), so any React developer's existing intuition transfers immediately to your custom component with zero documentation needed. Breaking the convention (changeHandler, onChangeCallback) adds friction for no benefit.

Senior Engineer Perspective

This is a small question but a real signal — engineers who've maintained a shared component library for multiple consuming teams have all had the "wait, is it onSelect or onSelected or selectHandler" conversation and land firmly on the onX/ handleX split precisely because consistency compounds across dozens of components.

Q90. When should a component's prop be a discriminated union versus several optional properties? Rewrite an ambiguous props type as a discriminated union.

ROI: ★★★★★ Frequency: Extremely High

Short Answer

Use a discriminated union whenever two or more props are only valid together or are mutually exclusive — plain optional properties let TypeScript accept invalid combinations silently, while a union with a shared literal "tag" field makes the compiler reject any combination that isn't one of the modeled valid shapes.

Detailed Answer

// AMBIGUOUS: nothing stops passing both href AND onClick, or neither
type LinkButtonProps = {
  href?: string;
  onClick?: () => void;
  external?: boolean;    // does this even make sense without href?
};
<LinkButton onClick={save} external />   // typechecks, but `external` is meaningless here!

// DISCRIMINATED UNION: only valid combinations compile
type LinkButtonProps =
  | { variant: 'link'; href: string; external?: boolean; onClick?: never }
  | { variant: 'button'; onClick: () => void; href?: never; external?: never };

function LinkButton(props: LinkButtonProps) {
  if (props.variant === 'link') {
    return <a href={props.href} target={props.external ? '_blank' : undefined}>...</a>;
  }
  return <button onClick={props.onClick}>...</button>;
}
// <LinkButton variant="button" onClick={save} external /> -> compile error: `external` doesn't exist here

The tell that you need a union rather than optional props: ask "does prop B only make sense when prop A has a specific value, or are A and B mutually exclusive?" If yes to either, a flat optional-props type is actively hiding invalid states that a union would surface at compile time instead of at runtime (or never, if nobody tests that combination).

Senior Engineer Perspective

"Making illegal states unrepresentable" (a phrase from Yaron Minsky, widely repeated in the TypeScript community) is the exact concept being tested here. A strong answer names the principle and demonstrates it with a concrete before/after, rather than only reciting the union syntax.

Q91. What does "forward refs and spread rest props to the root DOM element" actually enable for consumers, concretely? Show a case where skipping this breaks a real use case.

ROI: ★★★★★ Frequency: Extremely High

Short Answer

It lets a component drop seamlessly into any layout or integration that expects to attach a ref (measuring size, focus management, animation libraries, third-party DOM libraries) or pass through arbitrary DOM attributes (className for spacing utilities, data-testid for tests, aria-* for accessibility overrides) — without those capabilities, your component silently can't be used in situations that are extremely common in real apps.

Detailed Answer

// WITHOUT forwardRef/rest spreading — brittle, closed API
function Button({ label, onClick }: { label: string; onClick: () => void }) {
  return <button onClick={onClick}>{label}</button>;
}
// Broken use cases:
// - Can't attach a ref: <Button ref={btnRef} /> silently does nothing (or warns)
// - Can't add a test id: no data-testid prop exists, tests can't target it reliably
// - Can't add spacing via a utility class: no className prop accepted
// - A focus-management library (e.g. react-focus-lock) can't find the DOM node at all

// WITH forwardRef + rest spreading — composes with the rest of the ecosystem
const Button = React.forwardRef<HTMLButtonElement, {
  label: string; onClick: () => void;
} & React.ButtonHTMLAttributes<HTMLButtonElement>>(
  ({ label, onClick, className, ...rest }, ref) => (
    <button ref={ref} className={`btn ${className ?? ''}`} onClick={onClick} {...rest}>
      {label}
    </button>
  )
);
// Now: refs, data-testid, aria-*, and style all pass through correctly

Project Example

A design-system <Button> without ref forwarding silently broke a tooltip-on-hover feature added later — the tooltip library needed a ref to the actual button DOM node to position itself, and got null instead. Adding forwardRef was a one-line fix once diagnosed, but the bug looked like a tooltip library problem until someone checked what ref.current actually was.

Senior Engineer Perspective

Concrete failure scenarios (a positioning library needing a real DOM ref, a test needing data-testid) land far better than an abstract "it's good practice." This is exactly the kind of default that should be baked into every base component in a design system from day one, since retrofitting it later means auditing every existing consumer.

Q92. What is "designing for extensibility without over-engineering"? Give an example of a component API that over-engineered flexibility nobody needed, versus one that under-engineered and had to be rewritten.

ROI: ★★★★☆ Frequency: High

Short Answer

Over-engineering means building generic escape hatches (render props for every internal piece, a plugin system, deeply configurable theming) for flexibility nobody has asked for yet, at the cost of a harder-to-learn API and more surface area to maintain. Under-engineering means hardcoding assumptions so tightly that the very first real variation forces a breaking rewrite. The balance point: build the simplest API that solves today's known use cases, but leave the internal implementation structured (small composable pieces) so it's cheap to add flexibility later without a rewrite.

Detailed Answer

Over-engineered example: a <Table> component that accepts a render-prop for every single cell, every header, every row wrapper, plus a plugin registration system for "future" features like sorting/filtering that no consumer has asked for yet. Nobody uses 90% of the surface, but everyone pays the cost of learning it and every change risks breaking one of the many extension points.

Under-engineered example: a <Table columns, data> that hardcodes rendering every cell as a plain string with no way to customize a single column's display — the first real requirement ("show an avatar in the user column") forces either an ugly hack or a full API rewrite, because there was no extension point designed in at all.

The balanced middle: <Table columns, data> where each column definition accepts an optional render(row) function for that column's cell content — solves the actual, common "customize this column's display" need with one small extension point, without building a whole plugin architecture speculatively.

Code Example

// Balanced: one targeted extension point per column, not a whole plugin system
type Column<T> = {
  key: keyof T;
  header: string;
  render?: (row: T) => React.ReactNode;   // optional — falls back to plain value
};

function Table<T>({ columns, data }: { columns: Column<T>[]; data: T[] }) {
  return (
    <table>
      <thead><tr>{columns.map((c) => <th key={String(c.key)}>{c.header}</th>)}</tr></thead>
      <tbody>
        {data.map((row, i) => (
          <tr key={i}>
            {columns.map((c) => <td key={String(c.key)}>{c.render ? c.render(row) : String(row[c.key])}</td>)}
          </tr>
        ))}
      </tbody>
    </table>
  );
}

Senior Engineer Perspective

The YAGNI (You Aren't Gonna Need It) principle applied to component API design is exactly what's being tested here. The strongest answers give a rule of thumb: build the extension point when you have two or three real, current use cases that need it — not one hypothetical future one — and keep the internal implementation composable so adding a targeted extension point later is cheap.

Q93. How do you decide default prop values, and why can defaulting a prop to a new object or array literal in the function signature be a subtle performance bug?

ROI: ★★★★☆ Frequency: High

Short Answer

Good defaults make the zero-config case already correct and commonly desired. The subtle bug: function List({ items = [] }: Props) creates a brand-new array every render where items is omitted, so if that array is later used as a useEffect dependency or passed to a React.memo'd child, it appears to "change" every render even though conceptually it's always "the empty list" — breaking memoization or causing effects to re-run unnecessarily.

Detailed Answer

// BUG: a new [] every render when `items` is omitted defeats memo/effect deps
function List({ items = [] }: { items?: Item[] }) {
  useEffect(() => {
    console.log('items changed');   // fires every render if items is omitted — [] !== []
  }, [items]);
  return <MemoizedGrid items={items} />;  // MemoizedGrid re-renders every time too
}

// FIX: hoist the default to a stable, module-level constant
const EMPTY_ITEMS: Item[] = [];
function List({ items = EMPTY_ITEMS }: { items?: Item[] }) {
  useEffect(() => { console.log('items changed'); }, [items]);  // stable reference when omitted
  return <MemoizedGrid items={items} />;
}

This is a small, very real gotcha because default parameter values in JavaScript are re-evaluated on every call — a literal default isn't cached across renders. Hoisting object/ array/function defaults to a module-level constant (or memoizing with useMemo if the default genuinely depends on other props) fixes the identity instability.

Senior Engineer Perspective

This is exactly the kind of subtle, real production bug that separates someone who's debugged unexpected re-renders with the Profiler from someone who hasn't. The fix — hoist to a module-level constant — is a one-line change but requires first recognizing that default parameter values aren't memoized by JavaScript itself.

Q94. A consumer asks for a new prop that only they need for one specific screen. How do you decide whether it belongs on the shared component or should be handled by composition instead?

ROI: ★★★★☆ Frequency: High

Short Answer

Ask whether the need is a variation of the component's core purpose (belongs as a prop) or a one-off customization specific to a single consumer's context (belongs as composition — wrap the shared component locally, or use an existing slot/children API rather than growing the shared component's surface for a single caller).

Detailed Answer

A useful heuristic: if you can't picture at least one other consumer wanting this same behaviour within the next few features, it's a strong sign the request should be solved locally rather than by adding a permanent prop to a shared component that every future consumer will now see and have to understand, even though it exists for one screen's edge case. Composition is usually available even when it looks like it isn't:

// Request: "Can <Card> add a `showBetaLabel` prop just for our screen?"

// Instead of growing the shared component for one caller...
<Card showBetaLabel />   // now every Card consumer sees this prop forever

// ...compose locally, using the existing header slot
<Card header={<>{title} <BetaBadge /></>}>
  {content}
</Card>

If the request turns out to recur across several teams, that's exactly the signal to promote it into the shared component's real API later — but starting local and promoting once justified is far cheaper than growing the shared surface speculatively and later having to deprecate an unused, single-consumer prop.

Senior Engineer Perspective

This is a governance/process question as much as a technical one, and it's exactly the kind of decision a design-system maintainer makes weekly. The strongest answer references the "rule of three" instinct (wait for a third real consumer before generalizing) rather than accommodating every one-off request immediately.
