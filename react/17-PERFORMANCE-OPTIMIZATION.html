SECTION 1 - RE-RENDER OPTIMIZATION

Q1. What actually triggers a re-render in React?

ROI: ★★★★★ Frequency: Extremely High

Short Answer

A component re-renders when: (1) its own state changes (setState/dispatch), (2) its parent re-renders, or (3) a context it consumes changes. Props changing do not independently trigger a render — a child re-renders because its parent rendered, and that happens to pass new props.

Detailed Answer

The single most common misconception is "my component re-rendered because its props changed." In reality, by default React re-renders a component whenever its parent renders, regardless of whether the props changed. React does not diff props to decide whether to run your component function — it runs the function and then diffs the resulting element tree against the previous one to decide what to touch in the real DOM.

The three real causes

  • State update in the component itself.
  • Parent re-rendered, so all its children functions are called again (unless memoized).
  • Consumed context value changed — every consumer of that context re-renders.

"Re-render" means React calls your component function again and reconciles. That is usually cheap. The DOM is only mutated where the diff finds a real difference — so a re-render is not automatically a performance problem. The problem is expensive renders (big trees, heavy computation) firing more often than needed.

Code Example

function Parent() {
  const [count, setCount] = useState(0);
  // Every click re-renders Parent AND <Child /> below,
  // even though Child receives no changing props.
  return (
    <div>
      <button onClick={() => setCount(c => c + 1)}>{count}</button>
      <Child />
    </div>
  );
}

Senior Engineer Perspective

The trap here is jumping straight to "I'd memo the Child." A senior answer first says a re-render is not a bug — reconciliation of a leaf component is microseconds. You optimize when the profiler shows a render is actually expensive or on a hot path. Say that and you've signalled you won't scatter memo everywhere.

Q2. How do you diagnose an unnecessary re-render?

ROI: ★★★★★ Frequency: High

Short Answer

Use the React DevTools Profiler (record an interaction, look at what rendered and why), enable "Highlight updates when components render," and for stubborn cases add the why-did-you-render library which logs the exact prop/state that changed.

Detailed Answer

React DevTools Profiler

Record a session, then read the flame graph: bar width = time spent rendering that component. DevTools also shows "Why did this render?" (props changed, state changed, parent rendered, hooks changed) when you enable that setting. This tells you what is slow before you guess at fixes.

Highlight updates

The "Highlight updates when components render" toggle flashes a border around every component that renders. If typing in one input flashes the whole page, you've found a state-colocation problem.

why-did-you-render

For memoized components that still re-render, @welldone-software/why-did-you-render logs which prop is a new reference each time — usually an inline object or callback.

Senior Engineer Perspective

"Measure first" must come out of your mouth before any fix. Interviewers deliberately leave the question open to see if you optimize blindly. Mention that the Profiler's "ranked" view surfaces the components costing the most total time — that's where you spend your effort, not on the component that renders most often but cheaply.

Q3. When does React.memo help — and when does it hurt?

ROI: ★★★★★ Frequency: Extremely High

Short Answer

React.memo skips a component's re-render if its props are shallow-equal to the previous props. It helps when a component is expensive to render or is rendered many times, and its parent re-renders often with the same props. It hurts when props change on almost every render anyway — then you pay the comparison cost plus the render.

Detailed Answer

memo does a shallow comparison of props. If every prop is referentially equal, React reuses the previous render output and skips reconciliation for that subtree. The catch: shallow equality means {} !== {}. If the parent passes an inline object, array, or arrow function, the prop is a new reference every render and memo never bails out — you've added overhead for nothing.

So memo only works if the props are stable, which usually means the callbacks are wrapped in useCallback and objects in useMemo. That is why "just memo it" is often incomplete.

Use memo whenSkip memo when
Component renders a large/expensive subtreeComponent is a cheap leaf (few DOM nodes)
It's rendered in a big listIts props change on nearly every parent render
Parent re-renders frequently with stable propsYou haven't measured a problem

Code Example

const Row = React.memo(function Row({ item, onSelect }) {
  // Re-renders only when `item` or `onSelect` reference changes.
  return <li onClick={() => onSelect(item.id)}>{item.name}</li>;
});

// Parent must keep onSelect stable, or memo is useless:
const onSelect = useCallback((id) => dispatch(select(id)), [dispatch]);

Senior Engineer Perspective

The senior insight: memo is a contract between parent and child. It's worthless unless the parent cooperates by stabilizing references. Many teams sprinkle memo on children while the parent still passes style={{color:'red'}} inline — zero benefit. Mention the upcoming React Compiler (Q13) which makes most manual memoization unnecessary.

Q4. useMemo vs useCallback — when are they actually worth it?

ROI: ★★★★★ Frequency: Extremely High

Short Answer

useMemo caches a computed value; useCallback caches a function reference (it's useMemo returning a function). Use them for (1) genuinely expensive computations, or (2) preserving referential identity so a memoized child or a dependency array doesn't see a new reference every render.

Detailed Answer

There are exactly two legitimate reasons to reach for these hooks:

  • Expensive computation: filtering/sorting a large array, parsing, heavy math. useMemo avoids redoing it when inputs are unchanged.
  • Referential stability: a value/function is passed to a memo'd child or used in another hook's dependency array. Keeping the reference stable prevents downstream re-renders or effect re-runs.

What they are not for: wrapping every trivial value. useMemo(() => a + b, [a, b]) is slower than just a + b because you pay for the hook, the dependency check, and the closure. Memoization is a cache, and caches have overhead.

useCallback(fn, deps) is literally useMemo(() => fn, deps). It exists because passing callbacks to memoized children and to effect dependencies is so common.

Code Example

// Worth it: expensive derived data
const sorted = useMemo(
  () => hugeList.slice().sort((a, b) => a.score - b.score),
  [hugeList]
);

// Worth it: stable reference for a memoized child / effect dep
const handleSave = useCallback(() => api.save(id), [id]);

// NOT worth it: trivial value
const total = useMemo(() => price * qty, [price, qty]); // just do price * qty

Senior Engineer Perspective

Interviewers love the follow-up "does useMemo guarantee the value is cached?" — no. React may discard memoized values to free memory; treat it as a performance hint, not a semantic guarantee. Never put logic in useMemo that must run (like a side effect) — that's what effects are for.

Q5. Why does passing a new object, array, or function break memoization?

ROI: ★★★★☆ Frequency: High

Short Answer

Because React (and memo) compares props by reference for objects/arrays/functions. An inline {}, [], or () => {} creates a brand-new reference on every render, so the shallow comparison always reports "changed," defeating any memoization downstream.

Detailed Answer

JavaScript compares objects by identity, not structure: {a:1} === {a:1} is false. React's shallow prop comparison uses Object.is per prop. So if a parent renders: 

<MemoChild config={{ theme: 'dark' }} onClick={() => doThing()} />

both config and onClick are new references each render, and MemoChild re-renders every time despite being wrapped in memo. Fixes: hoist static objects out of the component, wrap dynamic ones in useMemo, and wrap callbacks in useCallback. The same rule applies to useEffect dependency arrays — a new object dependency re-runs the effect every render.

Senior Engineer Perspective

This is the root cause behind ~80% of "my memo isn't working" bugs. A strong candidate connects it back to referential equality and notes that primitives (string, number, boolean) compare by value, so those are always safe to pass. Bonus: mention that this is exactly the class of bug the React Compiler eliminates automatically.

Q6. The "children as a prop" / lift-content-up trick

ROI: ★★★★☆ Frequency: Medium

Short Answer

If a component holds fast-changing state but wraps expensive children, pass those children in as the children prop from a parent. React reuses the same child element objects across the wrapper's re-renders, so the expensive subtree doesn't re-render — no memo needed.

Detailed Answer

When a component re-renders, React re-runs its function — but elements passed into it as props (including children) were created by the parent and are not recreated by the re-rendering component. So moving the stateful boundary above the expensive content isolates the churn.

Code Example

// BAD: ExpensiveTree re-renders on every mousemove
function App() {
  const [pos, setPos] = useState(0);
  return (
    <div onMouseMove={e => setPos(e.clientX)}>
      <ExpensiveTree />
    </div>
  );
}

// GOOD: state lives in a wrapper; ExpensiveTree is passed as children
function MoveTracker({ children }) {
  const [pos, setPos] = useState(0);
  return <div onMouseMove={e => setPos(e.clientX)}>{children}</div>;
}
function App() {
  return (
    <MoveTracker>
      <ExpensiveTree />   {/* created once by App, not recreated by MoveTracker */}
    </MoveTracker>
  );
}

Senior Engineer Perspective

This "structural" fix impresses more than another memo, because it shows you understand that element identity is preserved across renders when the element is created by a stable ancestor. Also mention the sibling trick: moving fast-changing state down into a small dedicated component so it doesn't re-render its parent's siblings.

Q7. How do you render a list of 10,000 rows without freezing the UI?

ROI: ★★★★★ Frequency: High

Short Answer

Windowing / virtualization: only render the rows currently visible in the viewport (plus a small overscan buffer) instead of all 10,000 DOM nodes. Libraries: react-window, @tanstack/react-virtual, react-virtuoso.

Detailed Answer

Rendering 10,000 rows means 10,000+ DOM nodes: huge memory, slow layout, janky scroll. Virtualization keeps a fixed-size window of DOM nodes (say 20 visible + 10 overscan) and recycles them as you scroll, translating them with absolute positioning inside a tall spacer that fakes the full scroll height.

Combine with: stable keys, memoized row components, avoiding inline row callbacks, and pagination/infinite-loading from the server so you never hold the whole dataset. For variable-height rows, use a virtualizer that supports dynamic measurement.

Code Example

import { FixedSizeList } from 'react-window';

<FixedSizeList height={600} itemCount={items.length} itemSize={40} width="100%">
  {({ index, style }) => (
    <div style={style}>{items[index].name}</div>
  )}
</FixedSizeList>

Senior Engineer Perspective

Follow-up traps: accessibility (virtualized lists break screen-reader row counts unless you set aria-setsize/aria-rowcount), and Ctrl+F in-page search failing because off-screen rows aren't in the DOM. A senior answer names these trade-offs rather than presenting virtualization as free.

SECTION 2 - BUNDLE & LOADING

Q8. What is code splitting and how do you do it in React?

ROI: ★★★★★ Frequency: Extremely High

Short Answer

Code splitting breaks the bundle into smaller chunks loaded on demand, so users download only what the current view needs. In React you split with dynamic import() plus React.lazy and a <Suspense> fallback — most commonly per route.

Detailed Answer

A single giant bundle means the user waits to download and parse code for pages they may never visit. The bundler (Vite/Webpack) sees a dynamic import() and emits a separate chunk that's fetched lazily. Route-based splitting is the highest-leverage version: each route becomes its own chunk.

Guidelines: split at route boundaries first, then heavy below-the-fold or rarely-used widgets (charts, editors, modals). Don't over-split tiny components — each chunk has a network round-trip cost. Preload the next likely chunk on hover/intent to hide latency.

Code Example

const Dashboard = React.lazy(() => import('./Dashboard'));

<Suspense fallback={<Spinner />}>
  <Dashboard />
</Suspense>

// Route-based (React Router v6):
{ path: 'reports', lazy: () => import('./Reports') }

Senior Engineer Perspective

Mention that lazy-loading a component that's needed immediately just adds a spinner and a round-trip — split what's deferred, not what's critical. In Next.js the App Router splits by route automatically; you use next/dynamic for component-level splitting and can disable SSR for client-only widgets.

Q9. How does tree-shaking work, and how do you keep bundles small?

ROI: ★★★★☆ Frequency: High

Short Answer

Tree-shaking is dead-code elimination based on ES module static analysis: the bundler keeps only the exports you actually import. It relies on import/export syntax and side-effect-free modules. Keep bundles small by importing narrowly, avoiding heavy dependencies, and analyzing the bundle.

Detailed Answer

Because ES modules are static (imports resolved at build time, not runtime), the bundler can build a dependency graph and drop unreferenced exports. It can't shake CommonJS reliably, and it won't drop modules marked as having side effects. Package authors declare purity via "sideEffects": false in package.json.

Practical levers:

  • Prefer named imports from tree-shakeable libraries: import { debounce } from 'lodash-es', not the whole lodash.
  • Watch for accidental barrel-file imports pulling in a whole module.
  • Run a bundle analyzer (rollup-plugin-visualizer, webpack-bundle-analyzer, source-map-explorer) to see what's actually big — often moment.js, a full icon set, or a duplicated dependency.
  • Set a realistic browserslist so Babel doesn't over-polyfill.

Senior Engineer Perspective

The strongest signal is naming a real culprit you've fixed: "we shipped both moment and date-fns, and a full @mui icon barrel — the analyzer showed 300KB we deleted." Concrete numbers beat theory.

Q10. How do you lazy-load images and heavy assets?

ROI: ★★★☆☆ Frequency: Medium

Short Answer

Use native loading="lazy" on <img>/<iframe>, serve responsive images with srcset/sizes and modern formats (AVIF/WebP), reserve space with width/height to avoid layout shift, and defer offscreen work with IntersectionObserver. In Next.js use next/image, which handles most of this.

Detailed Answer

Images are usually the largest bytes on a page and the biggest LCP factor. Strategy:

  • Defer offscreen images with loading="lazy" so the browser skips them until near the viewport.
  • Right-size with srcset + sizes so phones don't download desktop-sized images.
  • Modern formats (WebP/AVIF) cut bytes dramatically.
  • Reserve dimensions (explicit width/height or aspect-ratio) to prevent Cumulative Layout Shift.
  • Prioritize the LCP image — do NOT lazy-load the hero; mark it fetchpriority="high" or priority in next/image.

Code Example

<img
  src="hero-800.webp"
  srcSet="hero-400.webp 400w, hero-800.webp 800w, hero-1600.webp 1600w"
  sizes="(max-width: 600px) 400px, 800px"
  width="800" height="450"
  loading="lazy" decoding="async" alt="Dashboard preview" />

Senior Engineer Perspective

The classic mistake is lazy-loading the above-the-fold hero, which hurts LCP. Senior answer: lazy-load below the fold, eager-load and preload the LCP resource. Reserving dimensions is the cheapest CLS win there is.

SECTION 3 - RUNTIME & WEB VITALS

Q11. What is useTransition and useDeferredValue, and when do you use them?

ROI: ★★★★☆ Frequency: Medium-High

Short Answer

Both are React 18 concurrent features that mark work as low-priority so urgent updates (typing, clicking) stay responsive. useTransition lets you wrap a state update in startTransition to mark it non-urgent; useDeferredValue gives you a lagging copy of a value that updates after the urgent render.

Detailed Answer

Classic problem: a search box filters a huge list. Typing updates the input (urgent) but re-filtering thousands of items (expensive) makes keystrokes lag. Concurrent rendering lets React keep the input responsive and render the expensive list at lower priority, interrupting it if you type again.

  • useTransition — you control the dispatch: startTransition(() => setQuery(value)), and isPending lets you show a subtle loading state.
  • useDeferredValue — you don't control the source; you derive a deferred version: const deferredQuery = useDeferredValue(query) and render the heavy list off that.

Code Example

const [isPending, startTransition] = useTransition();
function onChange(e) {
  setText(e.target.value);              // urgent: input stays snappy
  startTransition(() => setList(filter(e.target.value))); // deferred
}

Senior Engineer Perspective

These do NOT make the work faster — they change its priority so the main thread yields to user input. If the expensive render itself is the bottleneck, you still need memoization or virtualization. Interviewers probe whether you understand it's about perceived responsiveness, not raw speed.

Q12. What are Core Web Vitals, and how do frontend choices affect LCP, CLS, and INP?

ROI: ★★★★★ Frequency: High

Short Answer

Core Web Vitals are Google's user-centric metrics: LCP (Largest Contentful Paint — loading, target < 2.5s), CLS (Cumulative Layout Shift — visual stability, < 0.1), and INP (Interaction to Next Paint — responsiveness, < 200ms). INP replaced FID in 2024.

Know that INP is the newest and most JS-sensitive — heavy React re-renders and long event handlers hurt it directly, which is exactly why the runtime optimizations in this chapter matter for SEO, not just feel. Mention lab vs field distinction; it's a common follow-up.

Q13. What is the React Compiler, and does it make manual memoization obsolete?

ROI: ★★★★☆ Frequency: Rising (Modern)

Short Answer

The React Compiler (formerly "React Forget") is a build-time tool that automatically memoizes components and values, so you generally no longer need to hand-write useMemo, useCallback, or React.memo. It analyzes your code and inserts fine-grained caching that skips re-computation and re-renders when inputs are unchanged.

Detailed Answer

Manual memoization is error-prone: developers forget dependencies, over-memoize, or break it with unstable references (Q5). The Compiler shifts this to build time. It relies on your components following the Rules of React (pure render, no mutation of props/state), which is why the eslint-plugin-react-hooks / React Compiler ESLint rules matter — the compiler bails out safely on code it can't prove is safe.

It doesn't replace algorithmic optimization (virtualization, code splitting, reducing payloads). It removes the referential-equality busywork.

Senior Engineer Perspective

Positioning matters: say "it automates the memoization tax, but writing correct, pure components and choosing the right data-fetching and rendering strategy is still on us." That shows you see the compiler as removing a category of micro-optimization, not as a silver bullet for architecture.

SECTION 4 - MEASURING & DIAGNOSING

Q14. How do you measure React application performance end to end?

ROI: ★★★★☆ Frequency: High

Short Answer

Lab tools: Lighthouse and the Chrome DevTools Performance panel for load and main-thread analysis; React DevTools Profiler for render cost. Field tools: the web-vitals library reporting real-user metrics to your analytics/RUM. Bundle: a bundle analyzer. Always compare a baseline before/after a change.

Detailed Answer

  • Lighthouse — synthetic score + Web Vitals + opportunities (unused JS, render-blocking resources).
  • Performance panel — flame chart of the main thread; find long tasks (> 50ms), forced reflows, and scripting vs rendering time.
  • React Profiler — which components render and how long; the "ranked" chart.
  • web-vitals / RUM — real users on real devices/networks; the truth that lab can't capture.
  • Bundle analyzer — where the bytes go.

The discipline that matters: define the metric, measure a baseline, make one change, re-measure. Otherwise you can't prove the optimization worked.

Senior Engineer Perspective

Test on a throttled CPU (4–6x slowdown) and slow network — your M-series laptop hides the problems your users on mid-range Android phones feel. Interviewers respect "I profile on throttled devices" because it shows empathy for real conditions.

Q15. What is layout thrashing and how do you avoid it?

ROI: ★★★☆☆ Frequency: Medium

Short Answer

Layout thrashing (forced synchronous reflow) happens when you interleave DOM reads (like offsetHeight) and writes in a loop, forcing the browser to recalculate layout repeatedly in a single frame. Avoid it by batching all reads, then all writes, and using requestAnimationFrame for visual updates.

Detailed Answer

The browser normally batches layout and computes it once per frame. But reading a layout property (offsetTop, getBoundingClientRect, scrollHeight) after a write forces it to flush layout now to give you a fresh value. Do that in a loop and you get N forced reflows — the page janks.

Code Example

// BAD: read, write, read, write... forces reflow each iteration
els.forEach(el => { el.style.width = el.offsetWidth + 10 + 'px'; });

// GOOD: batch reads, then batch writes
const widths = els.map(el => el.offsetWidth);   // all reads
els.forEach((el, i) => { el.style.width = widths[i] + 10 + 'px'; }); // all writes

Senior Engineer Perspective

In React you rarely touch the DOM directly, but this bites in useLayoutEffect measurement code, animation libraries, and ref-based logic. Mention that prefer transforms/opacity for animations (composited, no layout) over animating width/top (triggers layout/paint).

SECTION 5 - PROFILING WITH REACT DEVTOOLS PROFILER

Q16. What does the React DevTools Profiler actually record, and how do you read a flamegraph?

ROI: ★★★★★ Frequency: High

Short Answer

The Profiler records every "commit" — a batch of DOM mutations React applied after rendering — during the time you're recording. The flamegraph shows one row per commit; within a commit, each bar is a component, its width proportional to render duration, and its color (gray to yellow/orange) proportional to relative cost. Click a commit in the timeline at the top to inspect it.

Detailed Answer

A "commit" happens whenever React flushes a set of updates to the DOM — it can be triggered by one setState call or by several batched together. The Profiler's commit selector (the little bar chart at the top) lets you jump between commits and see how long each took. Inside a commit, the flamegraph is a tree: a parent bar contains its children's bars, so a wide bar with wide children means the whole subtree is expensive, while a wide parent with thin children means the parent's own body (not its rendering of children) is the cost — often a synchronous computation before the return statement.

Hovering a bar shows exact render duration and why it rendered (props changed, state changed, hooks changed, parent rendered — enable "Record why each component rendered" in settings). Components that didn't render in a commit are grayed out or absent depending on the view.

Senior Engineer Perspective

A strong answer explicitly separates "this component rendered" from "this component is slow." A component can render in 0.1ms and still show a wide bar if its children are slow — width aggregates the whole subtree. Interviewers probe this: they'll ask "the bar for ComponentX is wide, is ComponentX the problem?" and want to hear "not necessarily — expand it and look at whether the width comes from its own body or from a child."

Q17. What is the "Ranked" chart view, and when do you use it instead of the flamegraph?

ROI: ★★★★☆ Frequency: Medium

Short Answer

The Ranked view lists every component that rendered in the selected commit sorted by render duration, longest first, ignoring the parent-child tree shape. Use it when you want a flat "top offenders" list instead of hunting through nested bars — it's the fastest way to answer "what's actually eating time in this commit."

Detailed Answer

The flamegraph is great for understanding structure — which subtree contains the cost — but it's slow for scanning when a tree is deep, because the cost of a slow leaf is spread visually across all its ancestors' bars. Ranked strips the hierarchy and just sorts by self-time-ish duration, so a component that's individually expensive (e.g., it does a heavy synchronous computation in its body) jumps straight to the top regardless of how deep it's nested.

Workflow: use Ranked first to find the worst offenders across the whole commit, then switch to the flamegraph for the specific one to understand why it rendered (its ancestors, its props) before deciding to memoize, split, or restructure.

Senior Engineer Perspective

Mentioning "Ranked for triage, flamegraph for diagnosis" signals a systematic workflow rather than randomly clicking around DevTools during a live debugging session — which is exactly the impression you want to give in an interview about performance methodology.

Q18. What exactly counts toward a commit's duration, and what doesn't?

ROI: ★★★★☆ Frequency: Medium

Short Answer

A commit's duration in the Profiler covers the "render" phase (calling component functions and reconciling) plus the "commit" phase (applying DOM mutations and running layout effects). It does not include work outside React's control — passive effects (useEffect) run asynchronously after paint and are not part of the commit bar, nor is time spent in the browser's own layout/paint/composite after React hands off the DOM.

Detailed Answer

React's work splits into phases: render (pure, can be interrupted/discarded in concurrent mode — components run, JSX is diffed), and commit (impure, synchronous — refs attached, DOM mutated, useLayoutEffect callbacks fire). The Profiler's timing for a commit covers both of those. useEffect callbacks are scheduled after the browser has painted, specifically so they don't block visual updates — so a slow useEffect won't show up as a wide bar in the commit you're looking at; it shows up as a gap before the next commit, or as a separate slow task in the Chrome Performance panel.

Code Example

useLayoutEffect(() => {
  // Runs synchronously before paint — DOES extend this commit's duration
  el.current.style.transform = measure();
}, [dep]);

useEffect(() => {
  // Runs after paint — does NOT extend this commit's duration in the Profiler
  logAnalytics(dep);
}, [dep]);

Senior Engineer Perspective

This distinction trips people up when a page "feels" janky but the Profiler shows fast commits. The fix is to correlate the React Profiler timeline with the Chrome DevTools Performance panel, where you can see the actual main-thread timeline including effects, timers, and browser layout/paint work that React's own numbers don't capture.

Q19. How do you find "wasted renders" with the Profiler, and what actually counts as wasted?

ROI: ★★★★★ Frequency: High

Short Answer

A wasted render is a component re-rendering and producing an output identical to what's already on screen — time spent for zero visible change. In the Profiler, enable "Record why each component rendered," then look for components that rendered because "the parent rendered" with no props/state actually changing anything meaningful, or context consumers re-rendering because of an unrelated field in a shared context object.

Detailed Answer

Not every render that produces no DOM change is worth fixing — the fix (memoization) has its own cost (Q4 in Section 1, and the whole of Section 8 in this chapter). A render is worth eliminating when it's both frequent and non-trivial (has a meaningfully-sized subtree or does real work in its body) and is provably unnecessary — same props, same state, same output.

Method: pick a slow interaction, record it, then in the flamegraph look at leaf components rendered many times. Hover to see "why did this render" — if the answer is "parent rendered" and the component's actual props (compare via React DevTools' component inspector, not just the profiler note) are unchanged, that's a real candidate for memo. If props genuinely changed every time, it's not waste — it's a correctly reactive render, and the fix (if needed) is elsewhere (debouncing the source of the change, virtualizing, etc.).

Senior Engineer Perspective

The interview-winning line: "wasted" is a data question, not a vibe — I check that props are actually unchanged before reaching for memo, because memoizing a component whose props change every time just adds a shallow-compare cost on top of the render you were trying to avoid.

Q20. Why is a development build unusable for judging real-world performance, and how do you profile a production build?

ROI: ★★★★☆ Frequency: Medium-High

Short Answer

Development builds carry extra work — prop-type-like validation, extra warnings, and (in React 18+) StrictMode's intentional double-invoking of renders and effects — that inflates timings by multiples. Always measure on a production build. React DevTools also ships a special "profiling" production build (react-dom/profiling) that keeps Profiler instrumentation while running production-speed code, for when you need Profiler data outside of `npm run dev`.

Detailed Answer

A default production build strips the Profiler's timing hooks for extra speed, so `` and the DevTools Profiler tab show no useful commit data against it. The profiling build is a middle ground: production-level minification and no dev-only warnings, but with the small overhead needed to still emit timing data. Most bundlers let you alias react-dom to react-dom/profiling and set NODE_ENV=production for a one-off profiling session, then switch back.

Separately, StrictMode in development intentionally renders components (and runs certain effect cycles) twice to surface impure side effects — this is diagnostic, not a real perf number, and should never be reported as "this component takes 8ms" without checking whether StrictMode doubled it.

Code Example

// vite.config.ts — swap in the profiling build for a session
export default defineConfig({
  resolve: {
    alias: {
      'react-dom/client': 'react-dom/profiling',
    },
  },
});

Senior Engineer Perspective

Reporting a dev-build number as a performance finding is a red flag interviewers watch for. Naming the profiling build specifically ("I alias react-dom to the profiling build rather than trust dev-mode numbers") signals you've actually done this in production incident triage, not just read about the Profiler tab.

Q21. What is the <Profiler> API component, and how does it differ from the DevTools Profiler panel?

ROI: ★★★☆☆ Frequency: Medium

Short Answer

<Profiler> is a component you wrap around part of your tree in code; it calls an onRender callback with timing data on every commit inside it. It's programmatic and always-on (in a profiling build), which makes it useful for shipping real-user render-timing telemetry, whereas the DevTools panel is an interactive, manual, developer-machine-only tool.

Detailed Answer

Because it's just a component, you can nest multiple <Profiler id="..."> boundaries around suspect areas and pipe onRender's actualDuration, baseDuration, and phase ("mount" or "update") into your analytics/RUM pipeline. This is how teams get render-cost telemetry from real users on real devices, which lab profiling on a developer's machine can never fully represent.

Code Example

import { Profiler } from 'react';

function onRenderCallback(id, phase, actualDuration) {
  if (actualDuration > 16) {
    analytics.track('slow_render', { id, phase, actualDuration });
  }
}

<Profiler id="Dashboard" onRender={onRenderCallback}>
  <Dashboard />
</Profiler>

Senior Engineer Perspective

Mention the cost trade-off: <Profiler> requires the profiling build in production, which has nonzero overhead, so teams typically gate it behind a sampling flag (e.g., 1% of sessions) rather than running it for every user all the time.

Q22. How do you correlate the React Profiler with the Chrome DevTools Performance panel for a full picture?

ROI: ★★★★☆ Frequency: Medium-High

Short Answer

The React Profiler tells you which components are expensive and why they rendered; the Chrome Performance panel tells you what the browser's main thread was doing overall — including work React's own numbers don't capture, like layout, paint, garbage collection, and non-React JavaScript. Record the same interaction in both and line up the timestamps.

Detailed Answer

Since React 18, React's own work shows up labeled in the Chrome Performance panel's flame chart (look for entries prefixed with component names when using a profiling build), so you can see React's render/commit work in context alongside style recalculation, layout, and paint — the steps that happen after React hands off the DOM mutation. This matters because a "fast" React commit can still be followed by an expensive synchronous layout recalculation (e.g., triggered by a useLayoutEffect measuring the DOM) that the React Profiler doesn't attribute clearly.

Practical workflow: record the interaction once in the Performance panel with CPU throttled to 4-6x slowdown, find the long task (>50ms), then separately record the same interaction in the React Profiler to identify the specific component causing it.

Senior Engineer Perspective

Interviewers respect candidates who don't treat the React Profiler as the only source of truth. Say plainly that render cost and "why did the page feel slow" are related but different questions, and the Performance panel is what answers the second one — especially for INP, which cares about the entire main-thread task, not just React's slice of it.

Q23. What are common false positives when reading a flamegraph — cases that look like a performance bug but aren't?

ROI: ★★★☆☆ Frequency: Medium

Short Answer

The two classics: StrictMode double-rendering in development (inflates numbers, isn't real), and Suspense/concurrent rendering showing a component rendering more than once for the same visible update (React may render a tree, throw it away, and render again — "wasted" by the raw numbers but part of how concurrent features work correctly).

Detailed Answer

Other traps: (1) A commit triggered by React DevTools itself while you have it open — the extension's own instrumentation adds overhead, so always compare relative timings, not absolute ones, and never quote a DevTools-measured number as the real user-facing number. (2) Initial mount commits are naturally slower than update commits — comparing a mount's duration to a later update's duration as if they're the same kind of event is misleading. (3) A component that appears to render "for no reason" may actually be reacting to a context change several levels up that isn't visible in the immediate flamegraph view — check the "rendered because" note rather than assuming a bug.

Senior Engineer Perspective

Naming these traps proactively — rather than waiting for the interviewer to point out "but doesn't StrictMode double render?" — is exactly the kind of anticipation that distinguishes someone who has actually debugged production performance from someone reciting Profiler documentation.

SECTION 6 - VIRTUALIZATION FOR LONG LISTS

Q24. What's the core mechanism behind list virtualization — how does a library render 100,000 items without 100,000 DOM nodes?

ROI: ★★★★★ Frequency: High

Short Answer

A virtualizer tracks scroll position and, given each row's (estimated or measured) height, computes which index range is currently visible plus an overscan buffer, then renders only those rows. It fakes the full scrollable height with a spacer element sized to the total content height, and positions the rendered rows with transform: translateY(...) or absolute top offsets so the scrollbar behaves as if all items exist.

Detailed Answer

Three moving parts: (1) an outer scroll container with a fixed viewport height and overflow: auto; (2) an inner spacer whose height equals the sum of all row heights, so native scrolling and the scrollbar thumb size are correct; (3) the currently-visible rows, absolutely positioned or transformed to their correct offset within the spacer. On every scroll event (usually throttled via requestAnimationFrame), the virtualizer recomputes the visible index range from scrollTop and re-renders only that slice.

Overscan (rendering a few extra rows above/below the viewport) hides the flash of blank space during fast scrolling and gives the browser a head start on layout for rows about to enter view.

Senior Engineer Perspective

A senior answer distinguishes "windowing" (what's described here) from lazy-loading/pagination — they solve different problems and are often combined: pagination limits how much data you fetch/hold in memory, windowing limits how many DOM nodes you render from what you already have.

Q25. Fixed-size vs variable-size (dynamic) row virtualization — what changes, and why is dynamic height harder?

ROI: ★★★★★ Frequency: High

Short Answer

Fixed-size virtualization (e.g., react-window's FixedSizeList) can compute any row's offset with simple multiplication — O(1), no measurement needed. Variable-size rows require either upfront known heights (e.g., from server metadata) or runtime measurement via ResizeObserver/getBoundingClientRect after a row first renders, which means the total scroll height and offsets are estimates that get corrected as rows are measured — causing scrollbar "jump" if not handled carefully.

Detailed Answer

With unknown heights, the virtualizer initially guesses (an average/estimated row height), renders a batch, measures the actual rendered heights, and patches its internal offset cache. If the user has already scrolled past estimated rows before they're measured, correcting the estimate shifts the scroll position — libraries like @tanstack/react-virtual and react-virtuoso handle this by measuring just-in-time and adjusting scrollTop compensation so the visible content doesn't visibly jump.

The practical takeaway: if row height is knowable ahead of time (e.g., all rows are 48px, or a server sends a height field), always prefer fixed/known sizing — it's simpler, faster, and jump-free. Only reach for dynamic measurement when content genuinely varies (chat messages, comments with varying text length).

Code Example

import { useVirtualizer } from '@tanstack/react-virtual';

function DynamicList({ items }: { items: Item[] }) {
  const parentRef = useRef<HTMLDivElement>(null);
  const virtualizer = useVirtualizer({
    count: items.length,
    getScrollElement: () => parentRef.current,
    estimateSize: () => 60, // initial guess, corrected after measuring
    overscan: 6,
  });

  return (
    <div ref={parentRef} style={{ height: 600, overflow: 'auto' }}>
      <div style={{ height: virtualizer.getTotalSize(), position: 'relative' }}>
        {virtualizer.getVirtualItems().map((row) => (
          <div
            key={row.key}
            data-index={row.index}
            ref={virtualizer.measureElement}
            style={{ position: 'absolute', top: 0, transform: `translateY(${row.start}px)` }}
          >
            {items[row.index].text}
          </div>
        ))}
      </div>
    </div>
  );
}

Senior Engineer Perspective

Naming the scroll-jump problem and the just-in-time measurement + compensation fix unprompted is a strong signal — it's the detail that separates "I've read the react-window docs" from "I've shipped a virtualized chat list and dealt with the jank."

react-window is the smallest and fastest for simple fixed/known-size lists and grids but gives you the least out of the box. @tanstack/react-virtual is a headless, unopinionated primitive (you build the markup) with strong dynamic-sizing support and framework-agnostic core. react-virtuoso is the most "batteries-included" — auto-sizing, grouping, sticky headers, reverse/chat-style scrolling, table support — at the cost of a larger bundle and more opinionated markup.

Don't present this as "which is best" — present it as a fit question. Q27. What accessibility problems does virtualization introduce, and how do you mitigate them?

ROI: ★★★★☆ Frequency: Medium-High

Short Answer

Screen readers rely on the DOM to know a list's true size and a row's position, but virtualization removes off-screen rows from the DOM entirely — breaking "item 40 of 5000" announcements, and breaking in-page browser find (Ctrl+F) and print, since content that isn't rendered can't be found or printed. Mitigate with ARIA (aria-setsize, aria-posinset, role="listbox"/role="row" with aria-rowcount/aria-rowindex) and by accepting the browser-find trade-off or providing an in-app search as a substitute.

Detailed Answer

For a virtualized listbox/grid, apply aria-setsize (total item count) and aria-posinset (this item's 1-based position) on each rendered item so assistive technology can announce "item 12 of 5000" even though items 1-11 and 13-5000 aren't currently in the DOM. For table-like grids use role="grid" with aria-rowcount/aria-colcount on the container and aria-rowindex/aria-colindex on cells.

Keyboard navigation needs special handling too: arrow-key movement past the rendered window must trigger the virtualizer to scroll and render the next row before moving focus to it, or focus silently falls off a cliff. Most mature virtualization libraries provide a hook or example for this; rolling your own keyboard nav on a virtualized list is a common source of a11y bugs.

Senior Engineer Perspective

Interviewers in accessibility-conscious orgs specifically probe this because it's the part teams skip. Saying "virtualization is not accessibility-neutral — I budget explicit ARIA and keyboard-navigation work into the estimate" is the answer that signals maturity, versus presenting virtualization as a drop-in performance win with no cost.

Q28. How do you virtualize a two-dimensional grid (rows and columns both scroll)?

ROI: ★★★☆☆ Frequency: Medium

Short Answer

Apply the same windowing idea on both axes independently: compute the visible row range from scrollTop and the visible column range from scrollLeft, then render only the intersection (visible rows × visible columns) plus overscan on each axis. Libraries expose this as a dedicated grid component (react-window's FixedSizeGrid/VariableSizeGrid, TanStack Virtual's two independent virtualizer instances).

Detailed Answer

The complexity jump from a list to a grid isn't conceptual — it's the interaction between the two axes and their independent scroll positions, plus sticky elements (frozen header row, frozen first column) that must stay rendered regardless of scroll offset, effectively as a virtualization exemption for specific cells. Frozen headers/columns are typically implemented as a separate, always-rendered layer positioned on top of the scrolling grid, kept in sync with the opposite axis's scroll offset via a transform.

Performance-sensitive spreadsheet-like UIs (large data grids) often reach for a dedicated data-grid library (AG Grid, Glide Data Grid, TanStack Table + virtualizer) rather than hand-rolling 2D virtualization, because frozen panes, resizing, and cell-level virtualization interact in ways that are easy to get subtly wrong.

Senior Engineer Perspective

Knowing when to reach for a dedicated grid library instead of hand-rolling 2D virtualization is itself a signal of experience — this is a case where "don't build it yourself" is usually the senior answer, not a cop-out.

Q29. How do you combine virtualization with infinite scrolling / incremental data loading?

ROI: ★★★★☆ Frequency: Medium-High

Short Answer

Virtualization controls how many DOM nodes exist for data you already have; infinite scrolling controls how much data you've fetched at all. Combine them by having the virtualizer's rendered-range callback trigger a fetch for the next page when the user scrolls near the tail of currently-loaded items, and feeding new pages into the same array the virtualizer is windowing over.

Detailed Answer

A common pattern with TanStack Query's useInfiniteQuery plus @tanstack/react-virtual: the virtualizer exposes the last rendered index on each scroll; when that index gets within some threshold of the total loaded count, trigger fetchNextPage. Show a loading row/skeleton at the tail while the next page loads, and update count passed to the virtualizer as new pages arrive.

Code Example

const rowVirtualizer = useVirtualizer({
  count: hasNextPage ? allRows.length + 1 : allRows.length, // +1 = loading sentinel row
  getScrollElement: () => parentRef.current,
  estimateSize: () => 56,
});

useEffect(() => {
  const [lastItem] = [...rowVirtualizer.getVirtualItems()].reverse();
  if (lastItem && lastItem.index >= allRows.length - 1 && hasNextPage && !isFetchingNextPage) {
    fetchNextPage();
  }
}, [rowVirtualizer.getVirtualItems(), hasNextPage, isFetchingNextPage, allRows.length]);

Senior Engineer Perspective

Flag the memory trade-off: infinite scroll without ever evicting old pages still grows an unbounded array in memory (even if the DOM is windowed). For truly huge datasets (tens of thousands of rows loaded over a long session), consider evicting far-off-screen pages from the data array too, not just from the DOM.

Q30. What is "overscan" and how do you tune it correctly?

ROI: ★★★☆☆ Frequency: Medium

Short Answer

Overscan is the number of extra rows rendered just outside the visible viewport, in the direction of likely scroll. It trades a bit of extra render cost for eliminating the flash of blank space during fast scrolling or the delay of mounting a row exactly when it enters view. Too little overscan causes visible blanking on fast scroll; too much overscan defeats the purpose of virtualizing at all.

Detailed Answer

The right value depends on row complexity and expected scroll speed: a simple text row can afford overscan of 10-20 with negligible cost, while a row with images or nested components should stay closer to 3-6 to keep the rendered set cheap. Fling-scrolling (fast trackpad/touch flicks) benefits from directional overscan — rendering more rows ahead in the scroll direction than behind it, which some libraries support natively.

Senior Engineer Perspective

The trap is treating overscan as a "bigger is safer" dial. State the trade-off explicitly and mention you'd tune it empirically against the actual row component's render cost measured in the Profiler, not guess a number.

Q31. When is virtualization the wrong tool, and what would you use instead?

ROI: ★★★★☆ Frequency: Medium

Short Answer

Virtualization is overkill for short lists (a few hundred simple rows render fine unvirtualized), and it's the wrong fix when the real problem is that each row itself is too expensive to render — windowing hides the symptom under normal scrolling but the first render of a page (mount) still pays for every visible row's cost, and jump-to-item / search-within-page UX gets harder. In those cases, fix the row's render cost first (simplify markup, memoize expensive per-row computation, lazy-render below-the-fold row content) before adding virtualization.

Detailed Answer

Rule of thumb: measure first (Section 5). If the Profiler shows the list itself renders fast even at hundreds of items, virtualizing adds complexity (accessibility work, scroll-jump edge cases, broken Ctrl+F) for no measurable win. Virtualization earns its complexity budget specifically when item count is in the thousands-plus and rows are simple enough that the bottleneck really is DOM node count, not per-row logic.

Also consider: if the underlying need is "show a huge dataset to the user," sometimes the better fix is server-side pagination/filtering so the client never holds more than a page's worth of data at all — reducing both DOM nodes and memory/network, whereas virtualization alone still requires having fetched everything (unless combined with Q29's infinite-loading pattern).

Senior Engineer Perspective

This question is really testing whether you reach for virtualization reflexively. The strongest answer leads with "how many rows, and have we measured the unvirtualized case" before proposing a library — exactly the same "measure first" discipline this chapter opened with.

SECTION 7 - CODE SPLITTING & BUNDLE ANALYSIS

Q32. Beyond routes, what are the highest-leverage places to split a bundle?

ROI: ★★★★☆ Frequency: High

Short Answer

After route-level splitting, the next-highest leverage is: heavy third-party widgets used on a minority of views (rich text editors, chart libraries, PDF/CSV generators, maps), modal/dialog content that isn't visible on initial paint, and anything gated behind a permission or feature flag that most users never see.

Detailed Answer

The pattern to look for is "code that exists in the initial bundle but isn't needed for the initial render." A rich-text editor (Slate, TipTap, Draft.js) can be 50-150KB gzipped by itself — if it only renders inside an "edit" modal, it should never be in the main chunk. Same for charting libraries (Recharts, Chart.js, D3-heavy visualizations) used on a single analytics tab, and admin-only screens shipped to every user regardless of role.

The technique is the same React.lazy + Suspense as route splitting, just applied at the component level, often triggered by a user action (click "Edit," open a modal) rather than navigation — so the chunk fetch overlaps with the user's decision time instead of blocking anything visible.

Code Example

const RichTextEditor = React.lazy(() => import('./RichTextEditor'));

function PostBody({ isEditing }: { isEditing: boolean }) {
  if (!isEditing) return <ReadOnlyBody />;
  return (
    <Suspense fallback={<EditorSkeleton />}>
      <RichTextEditor />
    </Suspense>
  );
}

Senior Engineer Perspective

Naming a concrete class of dependency (editor, charts, PDF generation) rather than saying "split heavy components" shows you've actually looked at a bundle analyzer output and made this call on a real project.

Q33. How do you read a webpack-bundle-analyzer / source-map-explorer treemap, and what are you looking for?

ROI: ★★★★★ Frequency: High

Short Answer

The treemap sizes each rectangle by that module's contribution to the final bundle (usually gzipped size). You're hunting for: unexpectedly large single dependencies, the same library appearing twice at different versions (duplicate deps), a large chunk that's actually a barrel-file re-export pulling in far more than what's used, and polyfills that shouldn't be needed for your target browsers.

Detailed Answer

Generate it with source-map-explorer (works off real source maps, attributes minified code back to original files accurately) or webpack-bundle-analyzer/rollup-plugin-visualizer for the bundler's own module graph view. Then look for these specific smells:

  • Duplicate versions — e.g., lodash at two versions because two dependencies pin different ranges; dedupe via lockfile resolutions/overrides.
  • Whole-library imports — importing from a package's root instead of its submodule pulls in everything even if tree-shaking is theoretically possible, especially with CommonJS packages.
  • Icon sets — importing an entire icon library instead of the 12 icons actually used.
  • Polyfills for browsers you don't support — check your browserslist/.babelrc targets against actual analytics.
  • Moment.js and its locale files — a classic multi-hundred-KB offender; date-fns or Luxon with explicit locale imports are far lighter.

Senior Engineer Perspective

Giving a specific before/after number ("the analyzer showed moment.js plus every locale at 230KB gzipped; date-fns with only the locales we ship brought it to 12KB") is far more convincing than describing the tool in the abstract — have a real number ready if you've done this.

Q34. What is a "barrel file" and why can it defeat tree-shaking?

ROI: ★★★★☆ Frequency: Medium-High

Short Answer

A barrel file (an index.ts that re-exports everything from a directory: export * from './Button'; export * from './Modal'; ...) makes imports convenient (import { Button } from '@/components') but can force the bundler to evaluate — and sometimes include — every module in the barrel even if you only import one export, especially with CommonJS interop or side-effectful modules.

Detailed Answer

Modern bundlers (Rollup, Vite's Rollup-based build, esbuild) are generally good at tree-shaking pure ESM barrels, but the risk grows with: (1) any module in the barrel that has a top-level side effect (registers something globally, runs on import) — the bundler can't prove it's safe to drop, so it keeps the whole file; (2) deep barrels re-exporting other barrels, multiplying the graph the bundler must analyze; (3) libraries shipped as CommonJS, where static analysis for tree-shaking is far weaker. The practical fix is importing directly from the specific file (import { Button } from '@/components/Button') for anything performance-sensitive, and reserving barrels for convenience in less critical code, or configuring "sideEffects": false in the package's package.json so bundlers can shake it confidently.

Senior Engineer Perspective

This is a real, measurable issue some teams have hit hard enough to build ESLint rules banning barrel imports for large icon/component libraries. Mentioning you've seen a bundle analyzer show a barrel pulling in an entire component library from one icon import demonstrates you've actually diagnosed this rather than repeating a blog post.

Q35. How do dynamic imports interact with Suspense — what happens if the import fails (network error)?

ROI: ★★★☆☆ Frequency: Medium

Short Answer

React.lazy(() => import(...)) returns a component whose underlying promise, if rejected (chunk failed to load — offline, deployed-over stale HTML referencing an old chunk hash, ad blocker), throws during render. That error propagates to the nearest error boundary, not to the Suspense fallback — Suspense only handles the "still loading" state, not the "failed to load" state.

Detailed Answer

A common production bug: you deploy a new version, a user has an old tab open referencing chunk main.abc123.js, that file no longer exists on the server/CDN after the deploy, and their next lazy-loaded route 404s on the chunk fetch. Without an error boundary around the lazy boundary, this crashes to a blank screen. The fix is to always pair Suspense with an error boundary that catches chunk-load failures and offers a "reload the page" prompt (which fetches the fresh HTML/manifest and resolves the issue).

Code Example

<ErrorBoundary fallback={<ChunkLoadError onRetry={() => window.location.reload()} />}>
  <Suspense fallback={<Spinner />}>
    <LazyRoute />
  </Suspense>
</ErrorBoundary>

Senior Engineer Perspective

This is a great "have you actually shipped this" filter question. Candidates who haven't hit it in production usually don't know Suspense and error boundaries are two separate concerns here. Mentioning versioned/immutable chunk filenames plus a service-worker or "new version available" banner as a more proactive fix shows even deeper production experience.

Q36. What's the difference between prefetching and preloading a chunk, and when do you use each?

ROI: ★★★★☆ Frequency: Medium-High

Short Answer

Preload (<link rel="preload"> / webpack's /* webpackPreload */) tells the browser to fetch a resource now, at high priority, because it's needed very soon — used for a chunk on the current page you know will be needed imminently. Prefetch (rel="prefetch" / /* webpackPrefetch */) fetches at low priority during idle time, for a resource likely needed for a future navigation — e.g., the next route the user will probably click into.

Detailed Answer

Practical pattern: prefetch a route's chunk on link hover/focus (intent signal) so that by the time the user actually clicks, the chunk is already cached and the navigation feels instant instead of showing a spinner. Frameworks like Next.js do this automatically for <Link> components in the viewport. Preload is for something you already know is coming this render — e.g., a chunk that Suspense is about to need — so it doesn't wait for the render to discover the import() before starting the network request.

Code Example

// Webpack magic comments
const Reports = React.lazy(() => import(/* webpackPrefetch: true */ './Reports'));

// Manual hover-prefetch
function NavLink({ to, chunkImport, children }) {
  return (
    <Link to={to} onMouseEnter={() => chunkImport()}>
      {children}
    </Link>
  );
}

Senior Engineer Perspective

Interviewers may push: "doesn't prefetching waste bandwidth for users who never click?" Good answer: prefetch only fires during idle time and is deprioritized by the browser under contention, and you can gate it behind navigator.connection.saveData/effective type checks for constrained networks — showing you think about the cost, not just the win.

Q37. How do you set and enforce a bundle-size budget so a PR can't silently regress it?

ROI: ★★★★☆ Frequency: Medium-High

Short Answer

Define a max size per chunk (e.g., "main chunk ≤ 180KB gzipped") using a tool like bundlesize, size-limit, or a bundler plugin's built-in performance budgets, run it in CI on every PR, and fail the build if a chunk exceeds its budget — turning "the bundle grew" from a silent, discovered-months-later problem into a blocking CI check.

Detailed Answer

This is covered in depth in the CI-performance-gates section of this chapter (Section 13); the short version here: pick per-entry-point budgets based on your current baseline plus a small margin, store them in config (size-limit's config array or similar), and wire a CI step that builds and checks against them. Report the delta on the PR itself (many tools post a comment with old vs. new size) so the author sees the cost of their change before merge, not after a user complains.

Senior Engineer Perspective

The senior framing: a budget isn't there to punish growth — legitimate features cost bytes — it's there to make the cost visible and intentional instead of accidental, so a team can consciously decide "this feature is worth 15KB" rather than discovering six months of unnoticed creep at once.

Q38. Client-side dependency A costs 40KB, but a competing library B costs 8KB and does 90% of what you need — how do you decide?

ROI: ★★★☆☆ Frequency: Medium

Short Answer

It's not purely a size decision — weigh bundle cost against feature completeness, maintenance/API ergonomics, TypeScript support, community size/bus-factor, and how the missing 10% would have to be built in-house (which has its own bytes and maintenance cost). If the missing 10% is core to the feature and would take real engineering time to replicate, the 40KB library may be cheaper overall despite the bytes.

Detailed Answer

A structured way to make this call: (1) confirm the size difference is real and comparable — check both gzipped, both including their actual runtime dependencies, using an analyzer, not a marketing "X KB" claim; (2) list what the missing 10% actually is and whether your product needs it now or ever; (3) check whether the smaller library is actively maintained (security patches, React 19 compatibility) — a "small but abandoned" dependency is a liability regardless of size; (4) if the feature is only used on one route, the size question is moot if you code-split it — the 32KB gap may not matter if it's not in the initial bundle at all.

Senior Engineer Perspective

This question tests whether you treat bundle size as the only axis. A senior engineer says "let me check if this is even in the critical path first — if it's behind a lazy boundary, the size difference may not matter for the metric we actually care about."

Q39. What's the difference between analyzing bundle size and analyzing "unused JavaScript actually shipped to the browser" (Lighthouse's coverage report)?

ROI: ★★★☆☆ Frequency: Medium

Short Answer

A bundle analyzer shows what's in your build output — static, build-time. Chrome DevTools' Coverage tab (and Lighthouse's "Reduce unused JavaScript" audit) shows what code actually executed during a real page load — runtime. A module can be small in the bundle but still be 90% dead code for a given page, or conversely be large but fully utilized.

Detailed Answer

Coverage is measured per-session: open DevTools' Coverage panel, reload, and it highlights (in the Sources panel) which bytes of each loaded file were executed vs. never touched. This catches a different class of waste than a static analyzer: e.g., a component library where you use 5 of its 40 components but its CSS/JS for all 40 loads anyway because it wasn't code-split per-component; or a polyfill bundle where 95% of the polyfills target browsers with near-zero traffic in your analytics.

The fix for a bundle-analyzer finding is usually "stop importing this" or "split this out"; the fix for a coverage finding is usually "load this conditionally" (feature-detect and polyfill only when needed) or "this component library needs per-component imports/code-splitting, not a monolithic chunk."

Senior Engineer Perspective

Bringing up Coverage as a distinct tool from a bundle analyzer — and explaining what each catches that the other doesn't — shows a more complete performance-analysis toolkit than most candidates who stop at "I'd run webpack-bundle-analyzer."

SECTION 8 - MEMOIZATION PITFALLS & WHEN NOT TO MEMOIZE

Q40. What does useMemo/useCallback actually cost, and when does that cost exceed the savings?

ROI: ★★★★★ Frequency: High

Short Answer

Each memoization hook allocates a slot in the component's fiber to store the cached value/deps, runs a comparison across the dependency array on every render, and closes over its inputs. For a cheap computation (simple arithmetic, a small object literal), this bookkeeping is more expensive than just redoing the computation — you're trading a near-free calculation for a guaranteed array comparison plus memory retention.

Detailed Answer

Concretely: useMemo(() => a + b, [a, b]) does an Object.is comparison on two dependencies, plus hook bookkeeping, to save re-running one addition — strictly slower every single render. The break-even point depends on both the cost of the computation and how often the component re-renders with unchanged inputs; there's no universal number, which is exactly why the correct process is "measure, don't guess" rather than memorizing a threshold.

The retained-memory cost matters too: every memoized value lives in the fiber until the component unmounts or the deps change, so memoizing many values in a component that renders thousands of times (e.g., a virtualized row) can add up to real memory pressure for negligible CPU savings.

Senior Engineer Perspective

The line that lands well: "memoization is a cache, and every cache has a read cost, a write cost, and a memory cost — I only pay it when the thing being cached is provably more expensive than those three combined." This reframes the whole topic away from "always/never memoize" toward a cost model.

Q41. Give a concrete example of memoization that looks like an optimization but actually makes things slower.

ROI: ★★★★☆ Frequency: High

Short Answer

Wrapping a component that receives new/changing props on almost every render in React.memo: you now pay a shallow prop comparison on every render (the check itself), and it still re-renders because props did change — so you've added cost with zero chance of ever skipping the render.

Detailed Answer

This happens constantly with list rows bound to frequently-changing data (a live price ticker, a progress percentage) — someone wraps Row in memo reflexively because "it's in a list," but the row's value prop changes every tick, so the comparison always fails and the render happens anyway, plus the comparison overhead on top. The tell in the Profiler: a memo'd component that still shows up rendering on every commit, with "why did this render: props changed" every time — that's the signal the memoization is pure overhead.

Code Example

// Looks safe, actually pure overhead: `value` changes every tick
const PriceRow = React.memo(function PriceRow({ symbol, value }) {
  return <tr><td>{symbol}</td><td>{value}</td></tr>;
});
// If `value` updates on every tick for every row, memo never bails out —
// remove it, or restructure so only the changed cell re-renders.

Senior Engineer Perspective

The strongest version of this answer includes the diagnostic step — "I'd check the Profiler's why-did-it-render note across a few commits before deciding memo is even helping" — because it shows you'd catch this in review rather than leaving it in the codebase indefinitely.

Q42. Why can a wrong or incomplete dependency array in useMemo/useCallback be worse than not memoizing at all?

ROI: ★★★★★ Frequency: High

Short Answer

A missing dependency means the memoized value/function silently keeps referencing stale data — it's not just a missed optimization, it's a correctness bug (a stale closure) that can be much harder to find than a slow render, because the code runs without error, it just uses outdated values.

Detailed Answer

Because the cached result is only recomputed when a listed dependency changes, any value the function/computation actually reads but that isn't in the array becomes frozen at whatever it was when the memo was first created (or last recomputed). This is especially dangerous with useCallback wrapping an event handler that reads component state directly (rather than via a setter's updater function) — the handler keeps firing with the old state value forever, producing bugs that only show up under specific timing and are hard to reproduce.

The eslint-plugin-react-hooks exhaustive-deps rule exists specifically to catch this class of bug; disabling it with an inline comment (// eslint-disable-next-line) to silence a "false positive" is one of the most common sources of real production bugs in React codebases.

Code Example

function Counter() {
  const [count, setCount] = useState(0);
  // BUG: missing `count` dep — this callback closes over count=0 forever
  const logCount = useCallback(() => {
    console.log(count);
  }, []); // eslint-disable-line react-hooks/exhaustive-deps

  // FIX: either include the dep, or avoid needing it via the updater form
  const increment = useCallback(() => setCount(c => c + 1), []); // no dep needed
}

Senior Engineer Perspective

This is a favorite senior-level trap question because many engineers treat exhaustive-deps as a nuisance linter rule rather than a correctness guardrail. Saying "I've been bitten by a disabled exhaustive-deps rule in production" and explaining the stale-closure mechanism precisely is a strong, specific answer.

Q43. Does useMemo guarantee the cached value survives to the next render? What are the implications?

ROI: ★★★☆☆ Frequency: Medium

Short Answer

No. The React docs are explicit that useMemo is a performance hint, not a semantic guarantee — React may choose to discard memoized values (e.g., to free memory for offscreen components) and recompute them on a future render. Code must be correct even if the memoization "doesn't happen" that time.

Detailed Answer

This means you must never put a required side effect inside useMemo — if you write useMemo(() => { analytics.track(...); return value; }, [dep]), that tracking call might fire more or fewer times than you expect if React discards and recomputes the cache, or it might not fire "reliably once" the way an effect would. Side effects belong in useEffect/event handlers; useMemo is exclusively for pure, re-derivable values.

This guarantee-lessness is also why the React Compiler's automatic memoization is described as behaviorally equivalent regardless of whether it decides to memoize a given expression — because correct code shouldn't depend on whether memoization actually happened.

Senior Engineer Perspective

This is a good "do you actually understand the mental model or just the API" filter. Bring up offscreen/Suspense-driven cache discarding specifically if asked for a mechanism — it shows the guarantee-lessness isn't hypothetical, it's tied to real concurrent-rendering behavior.

Q44. When does React.memo's shallow prop comparison itself become the bottleneck?

ROI: ★★★☆☆ Frequency: Medium

Short Answer

When a component takes many props, or a custom comparator does a deep/expensive comparison (e.g., comparing large arrays element-by-element) to try to catch more bail-out cases, the comparison cost itself can rival or exceed the render it's trying to avoid — especially if the component's actual render is cheap.

Detailed Answer

React.memo's default comparator is shallow and fast (a fixed number of Object.is checks equal to the prop count) — that's rarely the bottleneck itself. The real danger is when developers pass a custom arePropsEqual second argument that does deep equality (e.g., via lodash.isEqual) on a large object or array prop to "make memo work better." That deep comparison runs on every render regardless of outcome, and for large structures can cost more than just re-rendering a modest component would have.

Code Example

// Risky: deep-compares a potentially large array on every render
const Table = React.memo(TableImpl, (prev, next) =>
  isEqual(prev.rows, next.rows)
);

// Usually better: keep the array reference stable at the source
// (useMemo where rows are derived) and use the default shallow comparator
const Table = React.memo(TableImpl);

Senior Engineer Perspective

The senior fix isn't "write a smarter comparator" — it's "make the reference stable upstream so the default shallow comparator just works." Reaching for deep-equality comparators is usually a sign the real problem (unstable references at the source) wasn't fixed.

Q45. How do you decide whether to measure before or after adding a memoization — what's the actual workflow?

ROI: ★★★★★ Frequency: High

Short Answer

Always measure before and after: record a baseline Profiler trace of the real interaction, add the targeted memoization, record again, and compare actual commit durations — not just "it stopped re-rendering in the highlight-updates view." A render disappearing doesn't tell you how much time it actually saved; only the duration comparison does.

Detailed Answer

A disciplined loop: (1) define the user interaction that feels slow (typing in a filter box, opening a modal); (2) record it in the Profiler on a production/profiling build with the CPU throttled; (3) identify the specific expensive component via the Ranked view; (4) form a hypothesis (e.g., "Row re-renders because onSelect is a new function each time"); (5) apply the single targeted fix; (6) re-record the same interaction and diff commit durations. Changing more than one thing between measurements makes it impossible to attribute the improvement (or regression) to a specific change.

Senior Engineer Perspective

This entire question is really asking "do you have a methodology, or do you cargo-cult memo." Walking through the numbered loop above, unprompted, is the single highest-signal answer in this whole section — it's the difference between reciting API knowledge and having actually run a performance investigation.

Q46. Is it true that "the React Compiler makes useMemo/useCallback/memo obsolete"? What's the nuance?

ROI: ★★★★☆ Frequency: Rising (Modern)

Short Answer

Mostly, for the common case — the compiler inserts equivalent fine-grained memoization automatically at build time, following the same rules a careful engineer would apply by hand, without the risk of a wrong dependency array. The nuance: it requires code that follows the Rules of React (pure renders, no mutating props/state, no relying on render order for side effects); on code it can't statically prove safe, it bails out and leaves that part unmemoized, silently.

Detailed Answer

Practical implications: you still benefit from understanding why memoization matters (referential stability, the cost/benefit trade-off) because (1) not every codebase or dependency has adopted the compiler yet, (2) the compiler bailing out on non-compliant code means you still need to recognize and fix Rules-of-React violations, and (3) it only addresses re-render/recomputation waste — it does nothing for bundle size, virtualization, or network waterfall problems, which are separate categories entirely covered elsewhere in this chapter.

Senior Engineer Perspective

Good positioning: "it removes the tedious, error-prone 80% of manual memoization, but doesn't remove the need to understand render behavior — if anything it raises the bar, because now correctness bugs from broken purity rules are the main way memoization goes wrong, not a forgotten dependency array."

Q47. A candidate says "I always wrap every component in React.memo and every function in useCallback, just in case." How do you respond in an interview, and what's actually wrong with that?

ROI: ★★★★☆ Frequency: Medium-High

Short Answer

"Just in case" memoization is net-negative in the common case: most components are cheap leaves where the comparison overhead outweighs any savings, and blanket useCallback without also memoizing the objects/values that callback closes over often achieves nothing (Q5, Section 1) while adding a dependency array that's another place to introduce the stale-closure bug from Q42. It also makes code harder to read and review, obscuring which memoizations are load-bearing.

Detailed Answer

The correct default is the opposite: write plain, unmemoized code first, and add memoization only at a proven hot spot identified by the Profiler (Section 5) — with a comment explaining what it's protecting against, since future maintainers need to know it's load-bearing and not decorative. Blanket memoization also creates a false sense of safety: a team that memoizes everything "just in case" often stops profiling entirely, and misses the actual hot spots that need a structural fix (virtualization, code-splitting, moving state down) rather than a memo.

Senior Engineer Perspective

This question is as much about engineering judgment as React knowledge. The strongest answer reframes performance work as a targeted, evidence-driven practice — "optimize the 5% that's measurably slow, not the 100% that might theoretically be" — which is the thesis of this entire chapter distilled into one sentence.

SECTION 9 - WEB VITALS DEEP DIVE IN REACT APPS

Q48. In a client-rendered React SPA, what typically becomes the LCP element, and what makes it slow?

ROI: ★★★★★ Frequency: High

Short Answer

In a pure CSR SPA, the LCP element is usually whatever renders once your JS bundle finishes downloading, parsing, executing, fetching data, and rendering — often the hero image, a heading, or (worst case) a full-page loading spinner that gets replaced later, in which case the final content's paint, not the spinner's, is what's measured, and it can be very late.

Detailed Answer

The CSR waterfall that delays LCP: download HTML shell → download JS bundle → parse/execute JS → React renders → (often) a useEffect fires a data fetch → loading state shows → data arrives → real content renders. Each arrow is sequential latency stacked before the LCP element paints. This is why CSR-only apps often score poorly on LCP compared to SSR/SSG equivalents — the browser can't paint anything meaningful until JS has run and, frequently, until a client-side fetch has resolved.

Fixes within a CSR architecture: fetch data as early as possible (start the request before/during render, not in a useEffect that fires after mount — e.g., router loaders that fetch in parallel with code-loading), avoid a full-page spinner as the "first meaningful paint" strategy since it just delays the real LCP further, and preload the LCP image/font so it's not discovered only after JS executes.

Senior Engineer Perspective

The strongest answer contrasts CSR's fetch-after-render waterfall with SSR/streaming's ability to have content in the initial HTML — this is precisely why LCP is one of the metrics most improved by moving from pure CSR toward SSR/SSG for content-heavy pages (see Section 12 of this chapter).

Q49. How does React specifically hurt or help INP, compared to a non-framework page?

ROI: ★★★★★ Frequency: High

Short Answer

React can hurt INP when an event handler triggers a large, synchronous render (updating state that cascades through a big unmemoized tree) that blocks the main thread past the interaction — the render itself is the "long task." React can help INP through concurrent features (startTransition, useDeferredValue) that let React yield to the browser between chunks of low-priority work, keeping the thread free to paint the immediate visual feedback for a click/keystroke.

Detailed Answer

INP measures the latency from a user interaction to the next paint that reflects it — three phases: input delay (main thread busy with something else when the click happens), processing time (your handler + the render it causes), and presentation delay (browser painting the result). React's render phase, if large and synchronous, directly inflates the processing-time component. Automatic batching (React 18+) helps by coalescing multiple state updates from one event into a single render/commit instead of several, reducing total work per interaction.

The concurrent-rendering tools matter specifically for INP: wrapping the expensive part of an update in startTransition lets React interrupt that work if a new, more urgent update (another keystroke) comes in, and lets the browser paint the urgent part (the input's own value) without waiting for the expensive part to finish first.

Senior Engineer Perspective

Tie this explicitly back to Section 3's useTransition/useDeferredValue content and Section 1's re-render optimization — INP is the metric that makes all of that render-cost work concretely matter for a number product/SEO teams track, rather than an abstract "feels faster."

Q50. How do you instrument the web-vitals library in a React app and report field data?

ROI: ★★★★☆ Frequency: Medium-High

Short Answer

Import the onLCP/onCLS/onINP (and optionally onFCP/onTTFB) functions from the web-vitals package, register callbacks once at app startup, and send each metric's value plus its attribution data to your analytics/RUM endpoint — typically via navigator.sendBeacon so the report survives page unload.

Detailed Answer

Field measurement matters because it captures real devices, real networks, and real user behavior — a metric a developer's fast laptop on a fast connection will never surface. The library's "attribution" build (web-vitals/attribution) additionally reports which element was the LCP target or which event caused the worst INP, turning a bare number into something actionable without needing to reproduce the issue locally.

Code Example

import { onCLS, onINP, onLCP } from 'web-vitals/attribution';

function sendToAnalytics(metric) {
  const body = JSON.stringify({
    name: metric.name,
    value: metric.value,
    id: metric.id,
    target: metric.attribution?.largestShiftTarget ?? metric.attribution?.eventTarget,
  });
  navigator.sendBeacon('/vitals', body);
}

onCLS(sendToAnalytics);
onINP(sendToAnalytics);
onLCP(sendToAnalytics);

Senior Engineer Perspective

Mention that you'd segment the reported data by route, device class, and connection type before drawing conclusions — an aggregate p75 across all traffic can hide that one route or one device tier is dragging the average down while everything else is fine.

Q51. What causes CLS specifically in React apps beyond images — name React-specific culprits.

ROI: ★★★★☆ Frequency: Medium-High

Short Answer

React-specific CLS culprits: content that swaps from a skeleton/loading state to real content with a different height (common with data-fetching components), client-side-only content (ads, embeds, dynamically-injected banners) that mounts after initial layout and pushes content down, web fonts loading late and reflowing text (FOIT/FOUT) if not handled, and conditionally-rendered banners/notifications inserted above existing content instead of reserving space for them.

Detailed Answer

The skeleton-to-content shift is the most common one to catch in review: a skeleton loader sized differently from the real content it precedes causes a shift the instant data arrives — fix by sizing the skeleton to match the real content's dimensions (or reserving a min-height) rather than letting it be an arbitrary placeholder box. For fonts, font-display: optional avoids a layout shift entirely at the cost of possibly not showing the custom font on a slow connection, while swap shows a shift but never blocks text from displaying — the choice depends on how much you value font branding vs. layout stability. For third-party embeds, always reserve a fixed-size container (aspect-ratio or explicit height) before the embed's own JS has run.

Senior Engineer Perspective

Calling out the skeleton-height mismatch specifically is a strong, concrete signal — it's a bug that exists in a large fraction of production React apps and most engineers have never connected it to their CLS score even though they've all built a skeleton loader.

Q52. What's the difference between lab data (Lighthouse) and field data (CrUX/RUM) for Web Vitals, and why can they disagree?

ROI: ★★★★☆ Frequency: Medium-High

Short Answer

Lab data is a single synthetic run under controlled, simulated conditions (fixed network/CPU throttle, no real user variance); field data aggregates real users' real sessions across every device, network, and usage pattern. They disagree whenever your real user base skews toward conditions the lab simulation doesn't match — e.g., a large share of low-end Android traffic that a lab run on a simulated "mid-tier mobile" profile doesn't capture accurately.

Detailed Answer

Google's ranking signal for Core Web Vitals uses field data (via the Chrome UX Report, aggregated as p75 over a rolling 28-day window), not lab scores — so a Lighthouse score of 100 with poor field INP is not actually "passing" for search purposes. Field data also captures interaction patterns lab data structurally can't: real click/scroll/type behavior, real cache states (repeat visitors vs. first-time), and real geographic network latency.

Practical workflow: use Lighthouse in CI to catch regressions before merge (Section 13), but treat field data (via web-vitals reporting or CrUX) as the actual truth for whether users are having a good experience, and reconcile discrepancies by checking whether your lab throttle profile matches your real traffic's device/network mix.

Senior Engineer Perspective

Knowing that Google ranks on field p75, not lab score, is a specific, checkable fact that signals real SEO-performance crossover experience rather than generic "performance is good" talk.

Q53. A single-page app's route transitions don't trigger a full page load — how do Web Vitals even apply to client-side navigations?

ROI: ★★★☆☆ Frequency: Medium

Short Answer

Classic Web Vitals are defined per full page load/navigation, so out of the box they only measure the very first page a user lands on in an SPA — subsequent client-side route changes aren't automatically re-measured. To get visibility into SPA route transitions, you either treat each route change as a "soft navigation" and manually re-run the metric observers, or rely on the web-vitals library's experimental soft-navigation support, or track your own custom timing (e.g., time from route-change intent to the new view's meaningful content paint).

Detailed Answer

This is a genuinely unresolved area of the Web Vitals spec (the Soft Navigations API is still experimental in Chrome), which means most teams today instrument a custom metric for SPA route-change responsiveness rather than relying on LCP/CLS/INP resetting cleanly per route. A common pattern: mark the timestamp when a navigation starts (router's onNavigate or a click handler), then mark when the new route's primary content has painted (e.g., via a useLayoutEffect in the route's top-level component, or a PerformanceObserver for a specific paint), and report the delta as a custom "route transition time" metric.

Code Example

// Custom SPA transition timing (simplified)
function useRouteTransitionTiming(routeKey) {
  const start = useRef(performance.now());
  useLayoutEffect(() => {
    const duration = performance.now() - start.current;
    analytics.track('route_transition', { routeKey, duration });
  }, [routeKey]);
}

Senior Engineer Perspective

Acknowledging this is a real gap in the standard — rather than confidently claiming "web-vitals just handles SPA routing" — is more credible. It shows you've actually tried to measure SPA transitions and hit the limitation, rather than assuming the tooling is more mature than it is.

Q54. How does React 18/19's automatic batching and concurrent rendering change how you should think about TBT/long tasks?

ROI: ★★★☆☆ Frequency: Medium

Short Answer

Automatic batching reduces the number of separate render/commit cycles per interaction (fewer, larger tasks instead of many tiny ones), which generally helps. Concurrent rendering, when you opt in via startTransition, lets React break a large render into smaller, interruptible units of work processed across multiple frames instead of one uninterruptible long task — directly reducing Total Blocking Time / long-task duration for the parts of an update you've marked as non-urgent.

Detailed Answer

Without concurrent features, a large state update still renders synchronously in one go — big enough, and it's a single long task blocking the main thread (bad for TBT/INP) regardless of batching. Batching helps a different problem (redundant work across multiple state updates in one event), not task size itself. Only explicitly marking work as a transition gives React permission to chunk and interrupt it. This is why "we're on React 18" alone doesn't fix INP — you still have to identify the expensive update and wrap it in startTransition/useDeferredValue for the chunking behavior to kick in.

Senior Engineer Perspective

The trap in this question is assuming "React 18 has concurrent rendering, so it's automatically better." Correcting that — concurrent features are opt-in per update, not a free global upgrade — shows precise understanding rather than marketing-level familiarity with React 18's headline features.

Q55. How would you set up a Web Vitals monitoring dashboard that actually helps you catch regressions, not just report a score?

ROI: ★★★☆☆ Frequency: Medium

Short Answer

Report p75 (the percentile Google's thresholds are defined against, not the average) per route and per device/connection segment, track it over time with deploy markers overlaid so a regression can be traced to a specific release, and set alerting thresholds tied to the official good/needs-improvement/poor bands rather than an arbitrary internal number.

Detailed Answer

Averages hide the tail that Web Vitals thresholds actually target — a route can have a great average LCP while its p75 is well into "poor" because of a long tail of slow sessions (bad network, old devices), which is exactly the population most affected by a real performance regression. Segmenting by route matters because a single global aggregate can mask a regression on one high-traffic page offset by improvement elsewhere. Overlaying deploy timestamps on the trend graph turns "vitals got worse sometime last month" into "vitals got worse the day we shipped PR #4211," which is the difference between a dashboard people glance at and one that actually drives fixes.

Senior Engineer Perspective

The strongest answer connects the dashboard directly to the CI performance-gate discussion (Section 13) — a dashboard catches regressions that already reached production; a CI gate prevents some of them from reaching production at all. Mentioning both, and that they're complementary rather than redundant, shows the full picture.

SECTION 10 - IMAGE & ASSET LOADING PERFORMANCE

Q56. How do you decide which images to eager-load vs. lazy-load on a given page?

ROI: ★★★★★ Frequency: High

Short Answer

Anything above the fold, and specifically anything that could be the LCP element, should be eager-loaded (and ideally preloaded/high-priority) — never loading="lazy". Everything below the fold should be lazy-loaded via native loading="lazy" or an IntersectionObserver, since deferring their fetch doesn't delay anything the user is currently looking at, and it saves bandwidth for images they may never scroll to.

Detailed Answer

The most common real-world mistake is applying loading="lazy" uniformly to every <img> for consistency, which then lazy-loads the hero image too — directly delaying LCP, since the browser now waits until it evaluates layout before even discovering it should fetch the hero. The fix is deliberate, not automatic: identify the one or two images likely to be the LCP candidate (usually the largest above-the-fold image) and explicitly mark them loading="eager" (the default) with fetchpriority="high", while everything else defaults to lazy.

Code Example

{/* LCP candidate: eager + high priority, never lazy */}
<img src="/hero.webp" fetchPriority="high" loading="eager"
     width={1200} height={600} alt="Hero" />

{/* Below the fold: lazy */}
<img src="/card-3.webp" loading="lazy" decoding="async"
     width={400} height={300} alt="Product card" />

Senior Engineer Perspective

Bring up this exact anti-pattern unprompted — "lazy-loading everything by default is a common way teams accidentally regress their own LCP" — because it demonstrates you've caught this specific bug in a real codebase, not just read the lazy-loading attribute's docs.

Q57. How does next/image (or a similar framework image component) actually optimize images, beyond just lazy loading?

ROI: ★★★★☆ Frequency: Medium-High

Short Answer

It auto-generates and serves properly sized/format-converted images on demand (resizing to the rendered dimensions, converting to WebP/AVIF when the browser supports it), enforces explicit width/height (or fill with a defined container) to prevent CLS, defers offscreen images automatically, and supports a blur-up/placeholder pattern while the real image loads — all without you hand-building a responsive srcset.

Detailed Answer

Under the hood it typically runs through an image-optimization endpoint (built-in in Next.js, or a CDN/edge function elsewhere) that takes the source image plus requested width/quality/format as parameters, caches the result, and returns it — so the browser only downloads a version sized for its actual viewport/DPR instead of one oversized master image. The priority prop is the framework's way of marking an image as the LCP candidate (Q56) — setting it disables lazy-loading and adds a preload hint automatically, which is why forgetting it on the hero image is a very common Lighthouse-flagged mistake.

Senior Engineer Perspective

Knowing the specific mechanism (an on-demand resize/format endpoint, not just an <img> wrapper) and naming the priority prop's actual effect shows you've used it deliberately rather than just dropping it in because "it's the recommended component."

Q58. What font-loading strategy would you use to avoid both FOIT and layout shift?

ROI: ★★★★☆ Frequency: Medium-High

Short Answer

Self-host fonts (or use a fast font CDN with preconnect), preload the critical font file, use font-display: swap to avoid invisible text (FOIT) while accepting a brief visible swap, and mitigate the resulting layout shift with a matched fallback font stack sized via size-adjust/ascent-override (or a manually tuned fallback) so the fallback and web font occupy nearly the same space.

Detailed Answer

FOIT (Flash of Invisible Text, from font-display: block or the old default) hides text until the font loads — bad for perceived performance and can itself delay text-based LCP. FOUT (Flash of Unstyled Text, from swap) shows a fallback immediately then swaps to the real font, which is usually better for perceived speed but can shift layout if the fallback and target font have different metrics (different x-height/character widths). Modern CSS's size-adjust, ascent-override, and descent-override on a @font-face fallback declaration let you tune a system font to closely match the web font's box model, minimizing the shift when the swap happens. font-display: optional is the zero-shift choice — it uses the fallback and only swaps to the custom font on a subsequent load if there's time budget, never shifting a rendered page — appropriate when brand fidelity on first paint matters less than stability.

Code Example

@font-face {
  font-family: 'Inter';
  src: url('/fonts/inter.woff2') format('woff2');
  font-display: swap;
}
@font-face {
  font-family: 'Inter Fallback';
  src: local('Arial');
  size-adjust: 107%;
  ascent-override: 90%;
}
body { font-family: 'Inter', 'Inter Fallback', sans-serif; }

Senior Engineer Perspective

Naming size-adjust/metric-override fallbacks specifically (rather than just "use font-display: swap") is a relatively recent, high-signal detail — most candidates stop at the display property and don't know the metric-matching technique exists.

Q59. How do you use IntersectionObserver to build a custom lazy-loading behavior React's native loading="lazy" doesn't cover?

ROI: ★★★★☆ Frequency: Medium

Short Answer

Native loading="lazy" only works on <img>/<iframe> and gives you no control over the trigger distance or what happens (just defers the fetch). For anything else — lazy-mounting a heavy component, lazy-loading a background-image via CSS, firing an analytics "viewed" event, infinite-scroll triggers — wrap the target in an IntersectionObserver and mount/fetch/fire only once it's within a configurable root margin of the viewport.

Detailed Answer

The general pattern: a ref on the placeholder element, an observer created once (via useRef/useEffect, or a small reusable useInView hook), and state that flips to true the first time the target intersects — after which you can disconnect the observer since you typically only need the one-time signal (unless you're doing repeated visibility tracking, e.g., for analytics dwell time).

Code Example

function useInView(rootMargin = '200px') {
  const ref = useRef<HTMLDivElement>(null);
  const [inView, setInView] = useState(false);

  useEffect(() => {
    if (!ref.current || inView) return;
    const observer = new IntersectionObserver(
      ([entry]) => {
        if (entry.isIntersecting) {
          setInView(true);
          observer.disconnect();
        }
      },
      { rootMargin }
    );
    observer.observe(ref.current);
    return () => observer.disconnect();
  }, [inView, rootMargin]);

  return { ref, inView };
}

function LazySection() {
  const { ref, inView } = useInView('300px');
  return <div ref={ref}>{inView ? <HeavyChart /> : <ChartSkeleton />}</div>;
}

Senior Engineer Perspective

Point out the rootMargin tuning trade-off: too small and the component/image pops in visibly right as it reaches the viewport edge; too large and you've partly defeated the purpose of deferring it. This detail shows practical tuning experience, not just knowing the API exists.

Q60. How do you handle responsive images across a range of device pixel ratios and viewport widths correctly with srcset/sizes?

ROI: ★★★★☆ Frequency: Medium

Short Answer

srcset lists candidate image widths (image-400.jpg 400w, image-800.jpg 800w, ...); sizes tells the browser what CSS width the image will actually render at across breakpoints ((max-width: 600px) 100vw, 50vw). The browser combines sizes with the viewport width and the device's pixel ratio to pick the smallest candidate that's still sharp — you never need JS or manual DPR detection for this.

Detailed Answer

The two attributes answer two different questions: srcset says "here are the resolutions available," sizes says "here is how big the image will actually display" so the browser's own algorithm (no author control over exactly which candidate wins) can select appropriately for both viewport size and DPR (a 2x/3x retina screen at a small CSS width may still pick a larger file than a 1x screen at the same CSS width). Getting sizes wrong is the most common bug — if it doesn't match your actual CSS layout, the browser picks based on the wrong assumption and either over- or under-serves resolution.

Senior Engineer Perspective

A sharp follow-up is "what happens if you set srcset but omit sizes?" — the browser then assumes the image renders at 100vw, which is wrong for anything narrower and causes over-fetching. Knowing this default is a good specific detail to have ready.

Q61. How would you decide between AVIF, WebP, and JPEG/PNG for a given image, and how do you serve the right one to each browser?

ROI: ★★★☆☆ Frequency: Medium

Short Answer

AVIF generally compresses best (smallest files) but has the highest encode cost and slightly narrower legacy-browser support; WebP is broadly supported and a solid default improvement over JPEG/PNG; PNG stays only for images that need lossless transparency where WebP's lossless mode isn't preferable. Serve the best format each browser supports using the <picture> element with multiple <source> entries, letting the browser pick — never sniff the user agent manually.

Detailed Answer

Most modern pipelines (an image CDN, next/image, a build-time image plugin) handle the format negotiation for you via the Accept header or automatic <picture> generation, so hand-writing multiple <source> tags is mostly needed for static, non-framework-managed images. When you do it manually, order matters: list the most-preferred, smallest format first, ending with a universally-supported fallback.

Code Example

<picture>
  <source srcSet="/photo.avif" type="image/avif" />
  <source srcSet="/photo.webp" type="image/webp" />
  <img src="/photo.jpg" alt="Product photo" width={800} height={600} />
</picture>

Senior Engineer Perspective

Mentioning that AVIF's higher encode cost matters for build-time image pipelines (slower CI builds, more expensive on-demand transforms) — not just its output size — shows you've thought about the operational cost side, not only the end-user byte savings.

Q62. How do you prevent a third-party script (analytics, chat widget, ads) from blocking your app's interactivity?

ROI: ★★★★☆ Frequency: Medium-High

Short Answer

Load third-party scripts with async or defer (never a blocking synchronous <script> in the <head>), delay non-critical ones until after the page is interactive (on load, on idle via requestIdleCallback, or on a user interaction signal), and use next/script's (or an equivalent) strategy options to control exactly when each script executes relative to hydration.

Detailed Answer

Third-party scripts are a frequent, underestimated INP/TBT cost because they run arbitrary, often unoptimized JS on your page's main thread, competing with your own app's work — a chat widget or ad script can single-handedly cause the "long tasks" a Lighthouse audit flags, with no direct code of yours to blame. Strategy: next/script's strategy="lazyOnload" (load after everything else, on idle) for genuinely non-critical widgets, "afterInteractive" for things needed soon but not blocking initial paint, and reserve synchronous/blocking loading only for scripts that must run before first paint (rare, and usually a sign to reconsider the vendor).

Senior Engineer Perspective

A concrete story lands well here: "our Lighthouse score was capped by a support-chat widget's script; moving it to load on idle/after interaction recovered N points without any code change to our own app" — this is a very common real-world finding worth having ready.

Q63. What's the performance impact of SVG icons rendered inline as React components vs. as external image/sprite references, at scale?

ROI: ★★★☆☆ Frequency: Medium

Short Answer

Inline SVG-as-React-components (e.g., via SVGR) add each icon's markup to your JS bundle and to the DOM tree directly — fine in small numbers, but importing an entire icon library's worth of components (or a barrel import of hundreds of icons, see Q34) bloats the bundle. External sprite sheets or <img>-referenced SVGs keep the JS bundle smaller and are browser-cacheable independently, at the cost of losing easy per-icon CSS styling (fill/stroke via props) that inline SVG gives you for free.

Detailed Answer

At small scale (a few dozen icons used across the app) the difference is negligible either way. At large scale (an icon library with hundreds of entries, or many repeated icon instances in a huge list), the trade-offs sharpen: inline SVG duplicates the same markup structure in the DOM for every instance (real memory/DOM-node cost in a big virtualized list, though sprite <use> references share a single definition), while a sprite sheet referenced via <svg><use href="#icon-id"/></svg> keeps one shared definition and a tiny per-instance reference, at the cost of needing a build step to generate/maintain the sprite.

Senior Engineer Perspective

The strongest signal here is recognizing this as a genuine trade-off rather than a universal "inline is always better/worse" — the right choice depends on icon count, repetition frequency (e.g., inside a virtualized list of thousands of rows each with an icon), and how much per-icon dynamic styling you actually need.

SECTION 11 - REDUCING UNNECESSARY RE-RENDERS

Q64. What is "state colocation," and how does it reduce re-renders without any memoization?

ROI: ★★★★★ Frequency: High

Short Answer

State colocation means keeping a piece of state in the lowest/smallest component that actually needs it, instead of hoisting it to a shared ancestor "just in case." If only one small component reads and writes a value, putting it there means only that component (and its descendants) re-renders when it changes — its siblings and ancestors never see the update at all.

Detailed Answer

A common anti-pattern: a form's field-level UI state (like whether a password field is currently showing plaintext, or a dropdown's open/closed flag) lives in the top-level page component "because that's where all the state lives," which means every keystroke or toggle re-renders the entire page and everything below it. Moving that state down into the specific field/dropdown component confines the re-render to that subtree — zero memoization required, because the re-render simply doesn't propagate upward or sideways in the first place.

Code Example

// BAD: dropdown's open state lives at the page level — every toggle
// re-renders the whole page, including unrelated siblings
function Page() {
  const [isOpen, setIsOpen] = useState(false);
  return (
    <div>
      <Header />
      <Dropdown isOpen={isOpen} onToggle={() => setIsOpen(o => !o)} />
      <UnrelatedExpensiveWidget />
    </div>
  );
}

// GOOD: state colocated inside Dropdown — Page and its siblings never re-render
function Dropdown() {
  const [isOpen, setIsOpen] = useState(false);
  return <div><button onClick={() => setIsOpen(o => !o)}>Toggle</button>{isOpen && <Menu />}</div>;
}

Senior Engineer Perspective

This is the highest-leverage, lowest-cost re-render fix in the entire chapter, and it's worth leading with in any "how do you optimize re-renders" answer before mentioning memo/useMemo at all — it requires no library, no comparison overhead, and no risk of stale-closure bugs, it's purely a matter of where you declare the useState call.

Q65. How does splitting one large context into several smaller ones reduce re-renders, and what's the trade-off?

ROI: ★★★★★ Frequency: High

Short Answer

A single context bundling unrelated values ({ user, theme, cart, notifications }) re-renders every consumer whenever any field changes, since Context has no field-level subscriptions. Splitting into UserContext, ThemeContext, CartContext, etc. means a component only re-renders when the specific context it actually reads changes. The trade-off is more providers to wire up and slightly more boilerplate/nesting.

Detailed Answer

This is the same underlying cause discussed for state management (Context re-render storms) but framed specifically as a performance technique here: granularity of subscription is the lever. If a component only cares about theme, it should call useContext(ThemeContext), not useContext(AppContext).theme — the latter subscribes it to the entire combined object's identity, defeating the purpose of splitting even after you've split the underlying state, if you still expose it through one combined context. For very high-frequency values, even multiple small contexts aren't enough — that's when a selector-based external store (Zustand, Jotai, Redux with reselect) becomes worth the added dependency, since those give true field-level subscriptions without React re-rendering the whole consumer tree.

Senior Engineer Perspective

A precise way to frame the ceiling here: "Context splitting fixes coarse-grained over-subscription, but it's still all-or-nothing per context — for state that changes many times a second, I'd reach for a store with real selectors rather than keep slicing contexts thinner and thinner."

Q66. Why do inline object/array literals as JSX props keep showing up as a re-render cause, and what's the systematic fix across a codebase?

ROI: ★★★★★ Frequency: High

Short Answer

Every style={{...}}, options={[...]}, or onClick={() => ...} written directly in JSX creates a new reference on every render of the component that renders that JSX — regardless of whether the underlying values are the same. This silently defeats any memo on the receiving component. The systematic fix is a lint rule plus a habit: hoist static literals outside the component (module scope), and wrap dynamic ones in useMemo/useCallback only where they cross into a memoized child or a dependency array.

Detailed Answer

Not every inline literal needs fixing — if the receiving component isn't memoized and doesn't use the value in a dependency array, the new reference costs nothing beyond the normal render. The fix is targeted: identify components that are memoized (or children passed to memo'd components) and check whether their inline-literal props are the reason memoization isn't paying off. A static object that never changes (style={{ display: 'flex' }}) should simply be hoisted to a module-level constant — this needs no hook at all, just moving the object outside the component function so it's created once, ever.

Code Example

// Hoisted — created once at module load, never a new reference
const flexRowStyle = { display: 'flex', gap: 8 };

function Toolbar({ children }) {
  return <div style={flexRowStyle}>{children}</div>;
}

Senior Engineer Perspective

The senior distinction to make explicit: static literals get hoisted (free, no hook needed), dynamic ones that feed a memoized child get useMemo/useCallback (paid, targeted), and dynamic ones that feed a non-memoized child get left alone (not worth touching). Treating all three the same way is the mistake to call out.

Q67. How does an unstable/wrong `key` prop cause extra re-renders or remounts in a list?

ROI: ★★★★☆ Frequency: High

Short Answer

React uses key to match list items across renders. Using array index as the key when the list can reorder, filter, or have items inserted/removed in the middle causes React to match the wrong element to the wrong data — leading to stale local state bleeding between rows, unnecessary full remounts (losing focus, animation state, uncontrolled input values), and extra DOM work as React "updates" elements it should have recognized as unchanged, or discards and recreates elements it should have reused.

Detailed Answer

When the key changes for what is conceptually the same item, React unmounts the old element and mounts a brand-new one instead of updating it — that's strictly more expensive than an update, and it destroys anything tied to component identity (a text input's cursor position/focus, a CSS transition in progress, local state like "is this row expanded"). The correct key is a stable, unique identifier tied to the actual data (item.id), not its position in the array, precisely because position changes independently of identity when the list is filtered, sorted, or mutated.

Code Example

// BAD: index key — reordering/filtering causes rows to "swap" identities
{items.map((item, i) => <Row key={i} item={item} />)}

// GOOD: stable identity key — React correctly tracks each row across renders
{items.map((item) => <Row key={item.id} item={item} />)}

Senior Engineer Perspective

A good follow-up to raise unprompted: using a stable key is also how you can intentionally force a remount when you want one — changing the key on purpose (e.g., keying a form by a record's id) is a legitimate pattern to reset all internal state when switching to a genuinely different record, distinct from the accidental-remount bug this question is mainly about.

Q68. How do you stop a fast-changing value (like mouse position or scroll offset) from re-rendering a large subtree, without losing responsiveness?

ROI: ★★★★☆ Frequency: Medium-High

Short Answer

Keep the fast-changing value out of React state entirely where possible — write it directly to a ref and mutate the DOM imperatively (via style or a CSS variable) inside the event handler, bypassing React's render cycle altogether. When you do need it in React state for rendering logic, isolate the component that reads it as small as possible (state colocation, Q64) so the re-render blast radius is minimal.

Detailed Answer

Mouse-move, scroll, and drag handlers can fire dozens of times per second; running a full React re-render on each event for a value that only affects, say, one element's transform is wasteful. The imperative-ref pattern trades React's declarative model for raw DOM writes in the hot path, which is a deliberate escape hatch — appropriate specifically because the update is purely visual/presentational and doesn't need to flow through reconciliation.

Code Example

function DraggableDot() {
  const dotRef = useRef<HTMLDivElement>(null);

  function onMouseMove(e: React.MouseEvent) {
    // Direct DOM write — no setState, no re-render, no reconciliation
    if (dotRef.current) {
      dotRef.current.style.transform = `translate(${e.clientX}px, ${e.clientY}px)`;
    }
  }

  return <div onMouseMove={onMouseMove}><div ref={dotRef} className="dot" /></div>;
}

Senior Engineer Perspective

Frame this explicitly as an escape hatch, not a default style: "I'd only bypass React's render cycle for genuinely high-frequency, purely visual updates where reconciliation offers no value — for anything that affects layout, other components, or business logic, I keep it in React state despite the render cost."

Q69. How do selector-based stores (Zustand/Redux+reselect) avoid the re-render problem Context has, at a mechanical level?

ROI: ★★★★☆ Frequency: Medium-High

Short Answer

Instead of a component subscribing to "the whole context value" the way useContext does, a selector-based store lets each component subscribe to a specific slice via a selector function, and the store's own subscription mechanism (outside React's context re-render propagation) only notifies — and re-renders — components whose selected slice actually changed, checked by comparing the selector's return value across store updates.

Detailed Answer

Concretely, Zustand's useStore(selector) subscribes to the store directly (via a custom hook built on useSyncExternalStore), runs the selector against the new state on every store update, and only triggers a re-render of that particular component if the selector's result differs (by reference or a custom equality function) from last time — entirely independent of whether other, unrelated slices of the store changed. Redux with reselect-style memoized selectors achieves the same effect on top of a single global store: useSelector also compares the selector's output before re-rendering, so a component selecting state.cart.items doesn't re-render when state.user.profile changes, even though both live in the same store.

Senior Engineer Perspective

Naming useSyncExternalStore as the underlying primitive these libraries build on (rather than Context) is a precise, high-signal detail — it shows you understand these stores are architecturally a different subscription model from Context, not "Context with extra steps."

Q70. A parent passes a stable, memoized object down through three layers of components before it reaches the component that actually needs it — does that cause extra re-renders in the middle layers?

ROI: ★★★★☆ Frequency: Medium

Short Answer

Yes — unless every intermediate component is itself memoized (or the value is passed as opaque children/composition rather than props each layer re-derives), each intermediate layer still re-renders whenever its own parent re-renders, independent of whether the passed-through prop is stable. Prop stability only prevents extra renders caused by that specific prop; it does nothing about renders triggered by other state/props changing at each layer.

Detailed Answer

This is a common misconception: "I memoized the value, so passing it through many layers is free." Memoizing the value prevents a memoized consumer from re-rendering due to that value's reference changing — it does not stop the intermediate pass-through components from re-rendering for unrelated reasons (their own state, their own other props, their parent re-rendering). If the intermediate layers are cheap, this doesn't matter in practice. If they're expensive and purely act as pass-through plumbing, the real fixes are: use Context to skip the intermediate layers entirely (Q4 in Section 1's peer chapter), use composition/children to avoid re-creating the pass-through layer's JSX, or memoize each intermediate layer too.

Senior Engineer Perspective

This question is testing whether you conflate "prop is referentially stable" with "the whole prop-drilling chain is free." Distinguishing them precisely — and naming Context or composition as the actual fix for deep, expensive pass-through chains — is the answer that separates a nuanced understanding from a memorized rule.

Q71. How would you refactor a component that re-renders 200 times per second during a drag interaction, given a Profiler trace showing the drag handler's setState is the trigger?

ROI: ★★★★★ Frequency: Medium-High

Short Answer

First check whether the position actually needs to be in React state at all for correctness (business logic, persistence) or only for visuals — if purely visual, switch to the imperative-ref/direct-DOM-write pattern (Q68) and stop calling setState on every mousemove entirely. If the value genuinely needs to be React state (e.g., other components must react to it), throttle/rAF-batch the updates and colocate the state in the smallest possible component so the 200/sec re-renders are confined to a tiny subtree instead of a large one.

Detailed Answer

A concrete decision tree: (1) Does anything besides this element's own visual position depend on the live value during the drag? If no, go imperative — no React state, no re-renders, just DOM mutation in the handler. (2) If yes, but only a small subtree needs it, colocate the state there and pass the final (drop) value up via a callback only once the drag ends, rather than streaming every intermediate position through a shared ancestor. (3) If many components genuinely need the live value during the drag, batch updates to animation-frame cadence with requestAnimationFrame instead of firing a state update per raw mouse event, cutting the update rate from potentially 200+/sec (mouse event rate) to a display-synced ~60/sec ceiling.

Code Example

function useRafThrottledState<T>(value: T) {
  const [throttled, setThrottled] = useState(value);
  const frame = useRef<number>();
  useEffect(() => {
    frame.current = requestAnimationFrame(() => setThrottled(value));
    return () => cancelAnimationFrame(frame.current!);
  }, [value]);
  return throttled;
}

Senior Engineer Perspective

This is a synthesis question pulling together the whole section — leading with "does this need to be React state at all" before reaching for throttling or memoization shows the same measure-first, minimal-intervention discipline this chapter has emphasized from Section 1 onward.

SECTION 12 - SERVER-SIDE RENDERING PERFORMANCE

Q72. What is "hydration," and why is it expensive?

ROI: ★★★★★ Frequency: High

Short Answer

Hydration is the process of attaching React's event handlers and internal state to server-rendered HTML that's already visible in the DOM, so it becomes interactive. It's expensive because React must walk the entire rendered tree, re-run component render logic to build its internal fiber tree, and reconcile it against the existing DOM to verify it matches — all of that JavaScript work happens on the client's main thread, and until it finishes, clicks/inputs on server-rendered content don't do anything yet.

Detailed Answer

This is the source of a well-known SSR paradox: the page is visibleinteractive (poor INP/TBT if hydration is slow), because the browser must still download, parse, and execute the full JS bundle and run every component's render function again on the client to build up React's tree before attaching listeners. For a large page, this hydration pass can be a genuinely long main-thread task, and any click during that window either does nothing or queues until hydration catches up.

Senior Engineer Perspective

The precise framing interviewers want: SSR moves the "when is content visible" problem to the server, but it doesn't remove the "when is content interactive" problem — that's still gated on client-side JS execution, and for JS-heavy pages hydration cost can be substantial enough to matter for INP even though LCP looks great. This tension is exactly what streaming and selective hydration (next two questions) exist to address.

Q73. What is selective/progressive hydration, and how does React 18+ enable it?

ROI: ★★★★☆ Frequency: Medium-High

Short Answer

Instead of hydrating the entire page in one blocking pass, selective hydration hydrates each <Suspense> boundary independently and prioritizes whichever part the user actually interacts with first — if a user clicks inside a not-yet-hydrated section, React can jump ahead and hydrate that section before others, rather than processing strictly top-to-bottom.

Detailed Answer

React 18's concurrent renderer, combined with <Suspense> boundaries around independent sections of a page, lets hydration itself be split into interruptible units of work instead of one big synchronous pass. Practically: wrap slower-to-hydrate or lower-priority sections (a comments section, a related-products widget) in their own Suspense boundary so the primary content (main article, checkout form) hydrates and becomes interactive first, without waiting for the whole tree. If the user clicks into the not-yet-hydrated section, React detects the interaction and prioritizes hydrating just that boundary.

Code Example

function ProductPage() {
  return (
    <>
      <MainProductInfo />   {/* hydrates first / eagerly */}
      <Suspense fallback={<CommentsSkeleton />}>
        <Comments />          {/* hydrates independently, can be deprioritized */}
      </Suspense>
      <Suspense fallback={<RelatedSkeleton />}>
        <RelatedProducts />   {/* hydrates independently */}
      </Suspense>
    </>
  );
}

Senior Engineer Perspective

The key structural insight to state explicitly: Suspense boundaries are what make sections independently hydratable at all — without them, the whole page is one hydration unit and "selective" hydration has nothing to select between. So the practical lever a candidate controls is deciding where to place Suspense boundaries based on priority, not a config flag.

Q74. What is streaming SSR, and how does it reduce Time To First Byte / improve perceived load compared to traditional SSR?

ROI: ★★★★★ Frequency: High

Short Answer

Traditional SSR must fully render the entire page on the server — including waiting on every data dependency — before sending any HTML, so a slow data fetch anywhere on the page delays the first byte for the whole response. Streaming SSR (React's renderToPipeableStream/renderToReadableStream with Suspense) sends the shell and fast-ready content immediately, then streams in additional HTML chunks for slower sections as their data resolves — the browser starts painting long before the slowest part of the page is ready.

Detailed Answer

Wrapping a slow section in <Suspense fallback={...}> tells the streaming renderer "send a placeholder for this now, and stream in the real content plus a small inline script to swap it in once it's ready." This means TTFB reflects the shell's readiness, not the slowest data dependency on the page — a page with one fast section and one section waiting on a slow third-party API no longer makes users wait for the slow API before seeing anything at all.

Code Example

// Server (simplified, Node stream API)
import { renderToPipeableStream } from 'react-dom/server';

const { pipe } = renderToPipeableStream(<App />, {
  onShellReady() {
    res.statusCode = 200;
    res.setHeader('Content-Type', 'text/html');
    pipe(res); // shell + fast content flush immediately
  },
});

// App.tsx
<Layout>
  <FastAboveTheFoldContent />
  <Suspense fallback={<Skeleton />}>
    <SlowRecommendations />  {/* streamed in once its data resolves */}
  </Suspense>
</Layout>

Senior Engineer Perspective

A precise distinction worth making: streaming improves TTFB/perceived load and lets the browser start downloading assets and painting the shell sooner, but the streamed-in sections still need to hydrate once their JS/data is ready — streaming and hydration are separate problems that happen to be solved by the same Suspense-boundary mechanism, which is exactly why Suspense shows up in both this question and Q73.

Q75. What's the performance trade-off between SSR, SSG (static generation), and CSR for a given page, and how do you choose per-route?

ROI: ★★★★★ Frequency: High

Short Answer

SSG is fastest for LCP/TTFB (pages are pre-built HTML served straight from a CDN, no server render or data fetch at request time) but only fits content that doesn't need to be fresh per-request. SSR gives you fresh, personalized-per-request HTML at the cost of a server render (and often a data fetch) on every request, adding latency SSG doesn't have. CSR defers everything to the client and is simplest to reason about but has the worst baseline LCP/TTI for content-heavy pages (Q48). Most real apps mix all three per route based on how personalized and how fresh each page needs to be.

Detailed Answer

A practical decision framework: content that's identical for every visitor and changes infrequently (marketing pages, blog posts, docs) → SSG, optionally with incremental static regeneration to refresh periodically without a full rebuild. Content that's per-user or must reflect real-time data (a personalized dashboard, a live inventory count) → SSR, since baking it into a static build is either impossible or immediately stale. Content that's heavily interactive, behind auth, and doesn't need to be crawlable/fast-first-paint (an internal admin tool, a settings panel reached only after login) → CSR is often acceptable since the SEO/first-paint pressure that justifies SSR/SSG mostly doesn't apply.

Senior Engineer Perspective

Push back gently on any framing that treats this as one global app-wide choice — modern frameworks (Next.js App Router, Remix) let you make this decision per route, and a mature architecture mixes SSG marketing pages, SSR personalized pages, and CSR-heavy authenticated tools within the same app. Naming that per-route granularity is itself a strong signal.

Q76. Why can SSR sometimes make Time To First Byte *worse* than CSR, and how do you fix it?

ROI: ★★★★☆ Frequency: Medium-High

Short Answer

A CSR app can return its (mostly empty) HTML shell instantly since there's no server-side work to do — the delay shows up later, in JS execution and client-side fetching. SSR moves data-fetching and rendering work to the server, in the critical path before the first byte is even sent, so a slow database query, a slow third-party API call, or an overloaded/cold-starting server function directly inflates TTFB. Fix by parallelizing data fetches on the server, caching aggressively, using streaming (Q74) so slow parts don't block the whole response, and addressing serverless cold starts.

Detailed Answer

This is a genuine trade-off, not a flaw unique to bad SSR implementations: SSR's whole value proposition (send fully-formed HTML) requires doing the work that produces that HTML somewhere, and "somewhere" is now on the critical request path instead of deferred to the client after the shell already painted. The mitigations are specific: fetch independent data sources in parallel rather than serially (waterfalls on the server are just as bad as waterfalls on the client), put a cache (in-memory, edge, CDN with short TTL) in front of expensive/slow-changing server-side data fetches, and use streaming so a genuinely slow section doesn't hold up the entire response's first byte. For serverless/edge deployments, cold-start latency is its own separate TTFB tax worth measuring independently from render/fetch time.

Senior Engineer Perspective

This question specifically tests whether a candidate treats SSR as a strictly-better default. The mature answer: "SSR isn't free — it trades client-side waterfall latency for server-side critical-path latency, and if your server-side data layer is slow, SSR can genuinely regress TTFB versus a CSR app that at least ships its shell instantly."

Q77. How do React Server Components change the performance calculus compared to traditional SSR of client components?

ROI: ★★★★☆ Frequency: Rising (Modern)

Short Answer

Server Components render entirely on the server and send their output as a serialized description (not as component code) to the client — meaning their implementation code, and any dependencies they use, never ship to the browser at all, directly shrinking the JS bundle. Traditional SSR still sends full component code to the client for hydration even though it also rendered on the server; Server Components remove that duplication for the parts of the tree that don't need client-side interactivity.

Detailed Answer

The performance win is specifically bundle size and hydration cost: a Server Component that fetches data and renders static markup (say, a blog post body, or a product description) never needs its own JS on the client and never needs to hydrate, because it has no client-side interactivity to attach. Only Client Components (marked "use client") ship JS and hydrate. This lets a page mix heavy server-only logic/data-fetching with a smaller, more surgical set of interactive islands, rather than shipping and hydrating the entire tree's worth of component code as traditional SSR does.

The trade-off: Server Components can't use hooks like useState/useEffect or browser APIs, so the architecture requires deliberately drawing the client/server boundary, and a request still needs a round trip to the server for any Server Component re-render triggered by navigation or a Server Action.

Senior Engineer Perspective

The sharpest framing: "traditional SSR answers 'how do we get HTML to the browser fast,' Server Components additionally answer 'how do we avoid shipping and hydrating JS for parts of the page that were never interactive in the first place' — they're solving overlapping but distinct problems, and you generally want both together, not one instead of the other."

Q78. How do you avoid a client/server data-fetching waterfall in an SSR or Server Components app?

ROI: ★★★★☆ Frequency: Medium-High

Short Answer

A waterfall happens when a parent component must finish fetching before a child component even starts its own fetch (because the child is only rendered/mounted after the parent's data resolves), turning what could be parallel network requests into a serial chain. Fix by starting all independent fetches as early and in parallel as possible — hoist fetches above the point where they'd otherwise be gated by an unrelated parent, or use patterns (parallel data loaders, Promise.all, prefetching before render) that kick off requests without waiting on each other.

Detailed Answer

In a Server Components tree, if Page awaits its own data fetch before rendering <Sidebar />, and Sidebar only starts its own independent fetch once it renders, the two requests run serially even though they don't depend on each other — pure wasted time. The fix is to kick off both fetches at the same point in the tree (in the common parent, or via a router-level parallel-routes/loader pattern) and pass the resulting promises down, letting each component await its own promise independently rather than gating on an unrelated sibling's data. React's use() hook combined with Suspense allows exactly this: start the fetch early, pass the promise down, and let the consuming component suspend on it only when it actually needs the resolved value.

Code Example

// BAD: Sidebar's fetch only starts after Page's own await resolves
async function Page() {
  const page = await getPageData();     // Sidebar's fetch hasn't started yet
  return (
    <>
      <Main data={page} />
      <Sidebar />                      {/* starts its own fetch only now */}
    </>
  );
}

// GOOD: kick off both fetches in parallel, before either await
function Page() {
  const pagePromise = getPageData();
  const sidebarPromise = getSidebarData(); // starts immediately, in parallel
  return (
    <>
      <Main dataPromise={pagePromise} />
      <Sidebar dataPromise={sidebarPromise} />
    </>
  );
}

Senior Engineer Perspective

Waterfalls are one of the most common, most invisible SSR performance bugs because each individual fetch looks reasonable in isolation — the problem only shows up when you trace the actual request timeline (server logs, or a waterfall view in the browser's network panel for hybrid apps) and see requests that should overlap running back-to-back instead.

Q79. How do you performance-test SSR specifically — what's different from testing a CSR app?

ROI: ★★★☆☆ Frequency: Medium

Short Answer

SSR performance testing must include server-side load: how render time and TTFB behave under concurrent request volume, not just a single Lighthouse run against an idle server — a page that's fast for one request can degrade badly at realistic concurrency if server-side rendering is CPU-bound and the server has limited capacity. CSR testing, by contrast, is almost entirely about the client (bundle size, execution time, client-side data-fetch timing) since the server just serves static files.

Detailed Answer

Practical additions for SSR: load-test the render path itself (a tool like k6 or Artillery hitting the actual SSR endpoint at realistic concurrent user levels) to find the point where server-side render time starts degrading — this reveals CPU-bound bottlenecks in render logic or serialization that a single-request Lighthouse audit will never surface. Also test cold-start latency separately from warm request latency if deployed on serverless/edge functions, since the two can differ by an order of magnitude and a lab test run against an already-warm function will systematically understate real-world TTFB for low-traffic routes. And measure hydration cost (Q72) on real mid-tier devices under CPU throttling, since a fast server render says nothing about how long the client then takes to become interactive.

Senior Engineer Perspective

The distinguishing insight: "for CSR, my performance budget is almost entirely about the client; for SSR, I have to budget and test server-side render time and capacity too — it's a genuinely different testing surface, not just 'run Lighthouse against the SSR URL instead of the CSR one.'"

SECTION 13 - PERFORMANCE BUDGETS & CI PERFORMANCE GATES

Q80. What is a performance budget, and what should it actually be defined against?

ROI: ★★★★★ Frequency: High

Short Answer

A performance budget is an explicit, agreed-upon ceiling for a measurable quantity — bundle size for a given chunk, a Web Vital's p75, a Lighthouse category score, or a specific timing (TTFB, hydration time) — that a change is not allowed to exceed without a deliberate decision to raise the budget. It should be defined against real user-facing metrics and realistic segments (a slow device/network profile, p75 not average) rather than an arbitrary round number, so exceeding it actually corresponds to a user-noticeable regression.

Detailed Answer

Budgets work best layered at different points: bundle-size budgets per entry point/chunk (catch bloat before it ships), Lighthouse score/Web-Vitals budgets in CI (catch regressions in a simulated but standardized environment), and field p75 alerting in production (catch what actually happened to real users, since lab budgets can miss things real traffic surfaces). A budget with no clear real-world basis just becomes noise the team routinely overrides — set thresholds based on your current baseline, the Web Vitals "good" thresholds, and your actual user device/network mix, not an arbitrary industry number that may not fit your product.

Senior Engineer Perspective

The trap to avoid: presenting a budget purely as "we picked 200KB because that felt reasonable." A senior answer ties the number back to something measurable and user-relevant — "our current p75 LCP is 2.1s and industry good threshold is 2.5s, so we budgeted for at most a 200ms regression before the gate blocks a merge."

Q81. How do you wire Lighthouse CI into a pull-request pipeline so a regression blocks merge?

ROI: ★★★★★ Frequency: High

Short Answer

Run @lhci/cli (Lighthouse CI) against a deployed preview build or a locally-served production build on every PR, assert against a config of budgets/score thresholds (lighthouserc.json's assertions), and fail the CI job — which blocks merge via branch protection — if any assertion fails. Optionally post the report as a PR comment so the diff is visible to the author before they even check CI status.

Detailed Answer

Key setup details that matter in practice: run against a production build, never dev mode, since dev-mode timing is meaningless for a budget (Q20). Run multiple times per PR (numberOfRuns: 3+) and use the median, since a single Lighthouse run has real variance from machine noise — a flaky one-shot check that sometimes fails for unrelated reasons erodes trust in the gate fast. Point Lighthouse at a stable environment (a preview deployment with fixed CPU/network throttling settings) rather than an ephemeral CI runner whose CPU allocation can vary between jobs, which would make budgets inconsistent from run to run.

Code Example

// lighthouserc.json
{
  "ci": {
    "collect": {
      "url": ["https://pr-preview.example.com/"],
      "numberOfRuns": 3
    },
    "assert": {
      "assertions": {
        "largest-contentful-paint": ["error", { "maxNumericValue": 2500 }],
        "cumulative-layout-shift": ["error", { "maxNumericValue": 0.1 }],
        "total-blocking-time": ["error", { "maxNumericValue": 300 }],
        "categories:performance": ["error", { "minScore": 0.85 }]
      }
    },
    "upload": { "target": "temporary-public-storage" }
  }
}

Senior Engineer Perspective

Naming the flakiness/variance problem and the fix (median of multiple runs against a stable preview environment) unprompted is the detail that separates "I've read about Lighthouse CI" from "I've actually maintained a Lighthouse CI gate that a team trusted enough not to routinely bypass."

Q82. How do you enforce a bundle-size budget in CI with size-limit or a similar tool, and what should trigger a failure vs. just a warning?

ROI: ★★★★☆ Frequency: High

Short Answer

Configure per-entry-point size limits (e.g., via size-limit's config array, one entry per route/chunk that matters), run it as a CI step that builds the project and checks the output against those limits, and fail the build on a hard budget breach. A softer warning tier (e.g., "grew by more than 5% but still under budget") can post a PR comment without blocking, so small legitimate growth is visible without becoming a merge blocker every time.

Detailed Answer

The two-tier approach (hard fail vs. soft warning) matters because not every size increase is bad — shipping a genuinely needed feature costs bytes, and a gate that blocks every single-KB increase either gets routinely overridden (eroding the gate's authority) or forces engineers to fight the tool instead of shipping. A workable policy: fail only on breaching the absolute budget ceiling; warn (via a bot comment showing the size delta) on any increase at all, so the author consciously acknowledges the cost even when it's still within budget.

Code Example

// package.json (size-limit config)
"size-limit": [
  {
    "name": "main bundle",
    "path": "dist/assets/index-*.js",
    "limit": "180 KB"
  },
  {
    "name": "checkout route chunk",
    "path": "dist/assets/checkout-*.js",
    "limit": "60 KB"
  }
]

# CI step
- run: npx size-limit --json > size-report.json
- run: node scripts/post-size-comment.js size-report.json  # comments delta on PR

Senior Engineer Perspective

Bring up the "hard fail vs. soft warning" distinction unprompted — it shows you've thought about gate design as a socio-technical problem (a gate people trust and don't route around), not just a script that exits non-zero.

Q83. A legitimate feature needs to add 25KB to the main bundle, blowing the budget. What's the right process, versus just quietly raising the limit?

ROI: ★★★★☆ Frequency: Medium-High

Short Answer

First verify the 25KB is actually necessary in the main bundle at all — can it be code-split so it only loads for the users/routes that need it, rather than shipped to everyone? If it genuinely must be in the main bundle, raising the budget should be a deliberate, reviewed decision (a small PR to the budget config itself, ideally with a one-line justification), not something that happens implicitly because the gate was disabled or ignored for one PR.

Detailed Answer

The process that keeps a budget meaningful over time: (1) challenge the premise — does this code need to be in the initial bundle, or can React.lazy/dynamic import defer it to only the users who trigger the feature (Section 7)? (2) if it's unavoidable, quantify the trade-off explicitly (25KB for what user-facing capability, affecting what fraction of sessions) so the team is making an informed call, not an invisible one; (3) update the budget in its own reviewed change so the new ceiling is intentional and visible in git history, rather than a one-off CI override that quietly resets to the old number next time and re-flags identical code.

Senior Engineer Perspective

This question is really testing engineering judgment and process discipline, not React knowledge. The strongest answer treats "raise the budget" as a legitimate, sometimes-correct outcome — the failure mode to avoid is doing it silently/reflexively rather than as a conscious, reviewed trade-off.

Q84. How do you performance-test a React app under realistic conditions in CI — throttled CPU/network — rather than on a fast CI runner?

ROI: ★★★★☆ Frequency: Medium-High

Short Answer

Lighthouse CI (and Chrome DevTools Protocol-based tools generally) support explicit CPU throttling multipliers and network throttling presets (e.g., simulated "Slow 4G") that you configure in the collect step, so the measurement reflects a realistic mid-tier device/network rather than the CI runner's own (often quite fast, and inconsistent between runs) hardware.

Detailed Answer

Without explicit throttling, two problems compound: CI runners are frequently faster than real user devices, so passing scores in CI can still correspond to a poor real-world experience; and CI runner CPU allocation itself can vary between jobs/providers, making unthrottled numbers noisy and non-reproducible. Setting an explicit throttling profile (rather than relying on Lighthouse's default simulated throttling, which estimates rather than actually constrains the CPU) gives more consistent, comparable numbers run-to-run — some teams instead run against actual throttled hardware or a device farm for the highest-fidelity results, reserving Lighthouse's simulated throttling for the fast, cheap check on every PR.

Code Example

// lighthouserc.json — explicit throttling instead of relying on defaults
{
  "ci": {
    "collect": {
      "settings": {
        "throttlingMethod": "devtools",
        "throttling": {
          "cpuSlowdownMultiplier": 4,
          "requestLatencyMs": 150,
          "downloadThroughputKbps": 1600
        }
      }
    }
  }
}

Senior Engineer Perspective

Mentioning that unthrottled CI numbers can pass while real users on mid-range Android hardware suffer is the same "measure like your users" discipline from Section 5's profiling-on-throttled-devices point — bringing that connection up explicitly ties this section back to the rest of the chapter's core thesis.

Q85. How do you prevent a performance gate from becoming so noisy/flaky that engineers start ignoring or bypassing it?

ROI: ★★★★☆ Frequency: Medium-High

Short Answer

Reduce variance at the source (median of multiple runs, fixed/explicit throttling, a stable measurement environment rather than shared noisy CI infra), set thresholds with real margin above your actual baseline rather than the tightest number that happened to pass once, and make failures actionable (show exactly what regressed and by how much, ideally with a direct link to a trace) rather than a bare pass/fail with no diagnostic trail.

Detailed Answer

A gate that fails intermittently for reasons unrelated to the actual PR trains engineers to reflexively re-run CI or request an override rather than investigate — at that point the gate has lost its authority even though it's technically still "on." Concretely: pin the gate to run on isolated/dedicated infrastructure if the CI provider's shared runners have variable CPU allocation; store a rolling baseline (not a single hardcoded number) so the budget adapts sanely as the app legitimately grows, rather than becoming stale and requiring constant manual bumps; and always report which specific metric and by how much failed, not just "performance check failed," so a real regression is fast to diagnose and an obviously-noise failure is fast to recognize and re-run with confidence.

Senior Engineer Perspective

This is fundamentally a trust/process question dressed as a technical one. The answer that lands: "a gate only works as long as people believe a red result means a real problem — every design decision here should be in service of keeping that belief true, because the moment it isn't, the gate is dead weight regardless of what the YAML says."

Q86. How would you set up regression tracking so you can tell exactly which commit caused a performance regression discovered a week later?

ROI: ★★★☆☆ Frequency: Medium

Short Answer

Store every CI performance run's results (bundle sizes, Lighthouse scores, key Web Vitals) tagged with the commit SHA in a time-series-queryable store, and overlay deploy markers on your field-data dashboards (Q55) — combined, this lets you binary-search or directly correlate "the metric moved on this date" with "these commits shipped on this date" instead of re-testing old commits from scratch after the fact.

Detailed Answer

Without per-commit historical data, diagnosing a regression discovered later means re-checking out old commits and re-running Lighthouse manually — slow and error-prone, especially if the regression is gradual (death by a thousand small increases) rather than one dramatic commit. Lighthouse CI's server component (or a similar dashboard) stores every run's metrics against its commit, so you can plot a metric over time and see exactly where the trend line bends. This is complementary to — not a replacement for — the pre-merge gate (Q81-Q85): the gate stops known-bad changes from merging at all, while historical tracking catches subtler regressions (small enough to individually pass a hard threshold, but adding up) and pinpoints the responsible commit after the fact.

Senior Engineer Perspective

Distinguishing "the CI gate prevents big obvious regressions" from "historical tracking catches death-by-a-thousand-cuts regressions that individually pass the gate" shows a more complete mental model of how performance actually degrades in a long-lived codebase — it rarely regresses in one dramatic commit, more often it's gradual erosion.

Q87. Should performance budgets be the same for every route/page in an app, or does that need to vary — and how do you decide per-route budgets?

ROI: ★★★☆☆ Frequency: Medium

Short Answer

Budgets should vary per route based on that route's actual purpose and audience — a marketing landing page (first-time visitors, SEO-critical, no auth) warrants a tight LCP/bundle budget, while an internal admin tool used daily by logged-in employees on known hardware can reasonably tolerate a looser budget, since the cost/benefit of tight optimization differs sharply between the two.

Detailed Answer

A single app-wide budget either over-constrains low-traffic/internal routes (wasted engineering effort chasing marginal gains nobody will notice) or under-constrains the routes that matter most for conversion/SEO (a landing page budget that's "fine on average" but too loose for what actually drives revenue). Segmenting budgets by route type — and setting them against each route's realistic audience (a public marketing page's field data likely skews toward more varied devices/networks than an internal tool's) — produces a gate that actually reflects where performance work pays off, rather than treating every route as equally important.

Senior Engineer Perspective

The senior framing here mirrors Q75's per-route SSR/SSG/CSR decision: performance policy, like rendering strategy, is rarely a single app-wide constant — the strongest answers throughout this whole chapter default to "it depends on the route's actual purpose and audience," and this question is a direct extension of that same instinct into the CI/process layer.

SECTION 14 - REAL-WORLD PERFORMANCE DEBUGGING METHODOLOGY

Q88. A user reports "the app feels slow" with no other detail. What's your first step, before opening any dev tool?

ROI: ★★★★★ Frequency: Extremely High

Short Answer

Turn the vague report into a specific, reproducible scenario: which page, which action, on what device/browser/network, and roughly when it started (did it correlate with a recent deploy?). "Slow" could mean initial load, a specific button's response, scroll jank, or a stale-feeling UI — each points to a completely different investigation, so narrowing the report is the actual first step, not a tool.

Detailed Answer

A structured intake checklist: (1) Which specific page/route and which specific interaction? (2) Slow compared to what — always, or did it regress recently? (3) What device/browser/network — this alone often explains a report that never reproduces on the reporter's fast office wifi and top-tier laptop; (4) Is it reproducible by you, or only under specific data conditions (e.g., only for accounts with a huge dataset)? (5) Check field data/RUM (Q50, Q55) for that route/segment before assuming the report is representative — one user's anecdote might be an outlier, or might be the tip of a real p75 regression affecting many.

Senior Engineer Perspective

Interviewers ask this precisely because many engineers jump straight to "let me open the Profiler" on a vague report and waste an hour reproducing nothing. Leading with structured triage questions before touching any tool is the single most senior-sounding thing you can say in this whole chapter.

Q89. Once you have a reproducible slow interaction, what's your exact diagnostic sequence — which tool first, and why that order?

ROI: ★★★★★ Frequency: Extremely High

Short Answer

(1) Chrome Performance panel with CPU/network throttled, to see the whole picture — is the bottleneck scripting, rendering, layout, or network — before assuming it's React at all; (2) if scripting/React shows up as the cost, switch to the React Profiler to identify which component and why it rendered; (3) form a specific hypothesis about the cause; (4) apply one targeted fix; (5) re-measure both tools to confirm the fix actually worked and didn't just move the cost elsewhere.

Detailed Answer

The reason to start broad (Performance panel) rather than narrow (React Profiler) is that "slow" often isn't React's fault at all — it can be a slow network request, an expensive CSS selector causing style recalculation, layout thrashing from a third-party script, or main-thread contention from an unrelated tab/extension. Jumping straight to the React Profiler risks tunnel vision: you might optimize a component that was never the actual bottleneck. Only once the broad view confirms "yes, this is scripting time, and it's attributable to component render work" does narrowing into the React Profiler's flamegraph/ranked view (Section 5) become the right next step.

Senior Engineer Perspective

This question is testing whether "performance debugging" in your mental model equals "open the React Profiler" by reflex. Explicitly widening the first step to the browser-level view before narrowing to React-specific tools is what a methodical senior engineer does differently from a mid-level one who's only ever been taught the React-specific tools.

Q90. How do you distinguish "this got slower after a recent deploy" (a regression) from "this has always been this slow, nobody measured it before"?

ROI: ★★★★☆ Frequency: High

Short Answer

Check historical performance data (Q86's per-commit tracking, or field-data dashboards with deploy markers, Q55) against the timeframe of the complaint — if a trend line shows a step change lining up with a specific deploy, it's a regression with a findable cause via that commit's diff; if the metric has been flat-but-poor for a long time with no recent inflection point, it's a pre-existing issue that simply wasn't measured or reported until now.

Detailed Answer

Without historical data, this distinction is genuinely hard to make from a single report, which is exactly why Q86's historical tracking and Q55's dashboard-with-deploy-markers matter beyond just "nice to have" — they turn "did this regress" from a guess into a lookup. If historical data doesn't exist for this specific metric/route, the pragmatic fallback is checking recent deploys/git log for the affected area (new dependency added, a data-fetching pattern changed, a new heavy component introduced) as circumstantial evidence, then confirming by testing against a build from before that suspected change.

Senior Engineer Perspective

Connecting this directly back to the CI/monitoring infrastructure discussed in Section 13 — "this is exactly why per-commit performance tracking matters, otherwise every 'is this a regression' question turns into forensic guesswork" — ties the whole chapter together rather than treating debugging methodology as disconnected from the earlier tooling sections.

Q91. You find the bottleneck is a component re-rendering excessively, but memoizing it doesn't help. What do you check next?

ROI: ★★★★★ Frequency: High

Short Answer

Verify the props actually being passed are stable — a memo that "doesn't help" almost always means an unstable prop reference is defeating the shallow comparison (Section 1, Section 8), not that memoization is the wrong approach. Use why-did-you-render or manually log props across renders to find exactly which prop differs when it "shouldn't."

Detailed Answer

The debugging sequence: (1) confirm with logging/why-did-you-render exactly which prop's reference changed on the render you didn't expect; (2) trace that prop back to where it's created — is it an inline object/array/function literal, or the result of a hook whose own dependencies are unstable? (3) fix at the source (hoist, useMemo/useCallback with correct deps, or restructure via composition/state colocation) rather than adding a custom deep-equality comparator to memo, which treats the symptom and adds its own cost (Q44). If after all that the component genuinely re-renders because its data genuinely changed every time, the render isn't wasted at all — the actual fix has to be elsewhere (virtualization, debouncing the source of change, or accepting the render as correct and looking for a cheaper way to render it).

Senior Engineer Perspective

Naming "maybe this render isn't actually wasted" as a legitimate possible conclusion — not every re-render has a bug behind it — prevents you from chasing a fix that doesn't exist and shows the same measurement discipline the whole chapter has emphasized.

Q92. How do you validate that your fix actually worked, in a way that would convince a skeptical senior reviewer?

ROI: ★★★★★ Frequency: High

Short Answer

Re-run the exact same measurement methodology you used to find the problem (same interaction, same throttling profile, same tool) before and after the fix, on the same build type (production/profiling build), and report the actual before/after numbers — not "it feels faster" and not just "the highlighted-updates flashing stopped." If the metric that motivated the investigation was a field metric (real-user p75), ideally confirm the field number improved post-deploy too, since lab improvements don't always translate 1:1 to field impact.

Detailed Answer

A rigorous validation avoids two common false confidences: (1) "it stopped showing up as a wasted render in DevTools' highlight-updates view" doesn't tell you how much time was actually saved — always compare Profiler commit durations, not just render-count/highlighting; (2) a lab-measured improvement (Lighthouse, throttled Profiler trace) is a reasonable proxy but the real confirmation is the field metric moving, because lab conditions can miss effects that only show up under real device/network diversity. Where possible, ship behind a flag or to a subset of traffic and compare field p75 before/after as the final word.

Senior Engineer Perspective

This closes the loop the whole chapter has been building toward: measure a baseline, form a hypothesis, apply one change, re-measure with the same method, and where possible confirm in the field — not lab theater. Stating this loop explicitly, unprompted, as your closing step is the strongest way to end an interview answer on performance methodology.

Q93. How do you prioritize which of several identified performance issues to fix first, when you don't have time to fix them all?

ROI: ★★★★☆ Frequency: Medium-High

Short Answer

Prioritize by (impact × how many users/sessions it affects) ÷ effort to fix — a change that shaves 2 seconds off a rarely-visited internal page ranks below one that shaves 200ms off a high-traffic checkout flow's INP, even though the first number sounds bigger in isolation. Weight further by whether the metric affects a business-critical funnel (checkout, signup) where even small latency has measurable conversion impact.

Detailed Answer

Concrete inputs to that prioritization: field data segmented by route (Q55) to know actual traffic/impact, not assumptions; known conversion-rate sensitivity to latency for revenue-critical flows (many companies have internal data tying, e.g., a 100ms LCP regression to a measurable checkout drop-off — use that if it exists); and engineering effort/risk of each fix, since a one-line prop-stability fix that resolves a moderate issue often beats a multi-week virtualization rewrite that resolves a slightly bigger one. The output should be a ranked list with a one-line justification per item, not just a flat bug list — that justification is what lets a non-engineering stakeholder understand why item 3 comes before item 1's "bigger" number.

Senior Engineer Perspective

This question probes whether you can operate beyond pure technical diagnosis into engineering-management judgment. Framing prioritization around business impact and traffic volume — not just "which bug looks scariest in the flamegraph" — is what a staff-level performance conversation actually sounds like.

Q94. Walk through a full example: a dashboard page takes 4 seconds to become interactive after a recent release. Describe your investigation end to end.

ROI: ★★★★★ Frequency: High

Short Answer

Confirm and scope the regression against historical data (Q90); reproduce with throttled CPU/network while recording both the Chrome Performance panel and the React Profiler (Q89); identify from the Performance panel whether the 4 seconds is dominated by network (waterfall of requests), scripting (long tasks), or render/layout; narrow further with the React Profiler if scripting/React is implicated; form and test a specific hypothesis; apply the minimal fix; re-measure the same way to confirm.

Detailed Answer

A plausible full trace-through: historical tracking shows the regression lines up with the release that added a new widget to the dashboard. Recording the Performance panel under throttling shows a request waterfall where three independent API calls run serially instead of in parallel (a data-fetching waterfall, Q78) before anything renders, accounting for 2 of the 4 seconds; the remaining time is a single long task during React's render, which the Profiler's Ranked view attributes to the new widget doing a synchronous, unmemoized heavy computation (sorting/filtering a large array) on every render caused by a parent re-render further up the tree, unrelated to the widget's own data (Q19's "wasted render," Q40's memoization cost analysis). The fix: parallelize the three fetches (kick them off together instead of sequentially awaiting), and wrap the widget's expensive computation in useMemo keyed to its actual data dependency, verified by re-recording both tools and confirming the interactive time drops back toward the pre-regression baseline.

Senior Engineer Perspective

This synthesis question is designed to see whether you can chain every earlier section's concepts together into one coherent investigation, rather than only being able to answer each topic in isolation when asked directly. Walking through distinct, independent root causes (a network waterfall and a render-cost issue) in the same investigation — rather than assuming there's exactly one bottleneck — reflects how real performance regressions usually actually look.

Q95. After fixing a performance issue, what do you put in place so the same class of regression doesn't silently come back?

ROI: ★★★★☆ Frequency: Medium-High

Short Answer

Turn the specific fix into a durable guardrail: a CI performance budget/gate scoped to the affected route or bundle (Section 13) if one didn't already cover it, a regression test or lint rule if the root cause was a recognizable code pattern (e.g., an ESLint rule flagging sequential awaits that could be parallelized, or exhaustive-deps enforcement), and a note in the historical performance dashboard so a future regression in the same area is immediately visible against this fix's baseline rather than requiring rediscovery from scratch.

Detailed Answer

The instinct to resist is treating a performance fix as done once the metric recovers — without a guardrail, the same class of issue (an unstabilized prop, a re-introduced sequential fetch, a new heavy dependency) tends to recur because the underlying incentive/process that let it happen the first time is usually still in place. Concrete guardrails per common root cause: unstable references reappearing → an ESLint rule or code-review checklist item; bundle bloat reappearing → a size budget scoped tightly enough to actually catch it (Section 13); a data-fetching waterfall reappearing → a lint rule or code-review pattern flagging sequential awaits of independent promises; a slow render reappearing → adding that interaction to whatever ongoing Lighthouse-CI/synthetic-monitoring coverage exists so it's checked on every future PR, not just the one that fixed it this time.

Senior Engineer Perspective

This closing question is deliberately about process maturity, not another technical trick — it signals whether you think about performance as a one-time fire-drill or as a property of the system that needs ongoing structural protection. Ending the whole chapter on "how do you make sure it stays fixed" is exactly the senior instinct interviewers are listening for.
