SECTION 1 - RE-RENDER OPTIMIZATION

Q1. What actually triggers a re-render in React?

ROI: ★★★★★ Frequency: Extremely High

Short Answer

A component re-renders when: (1) its own state changes (setState/dispatch), (2) its parent re-renders, or (3) a context it consumes changes. Props changing do not independently trigger a render — a child re-renders because its parent rendered, and that happens to pass new props.

Detailed Answer

The single most common misconception is "my component re-rendered because its props changed." In reality, by default React re-renders a component whenever its parent renders, regardless of whether the props changed. React does not diff props to decide whether to run your component function — it runs the function and then diffs the resulting element tree against the previous one to decide what to touch in the real DOM.

The three real causes

  • State update in the component itself.
  • Parent re-rendered, so all its children functions are called again (unless memoized).
  • Consumed context value changed — every consumer of that context re-renders.

"Re-render" means React calls your component function again and reconciles. That is usually cheap. The DOM is only mutated where the diff finds a real difference — so a re-render is not automatically a performance problem. The problem is expensive renders (big trees, heavy computation) firing more often than needed.

Code Example

function Parent() {
  const [count, setCount] = useState(0);
  // Every click re-renders Parent AND <Child /> below,
  // even though Child receives no changing props.
  return (
    <div>
      <button onClick={() => setCount(c => c + 1)}>{count}</button>
      <Child />
    </div>
  );
}

Senior Engineer Perspective

The trap here is jumping straight to "I'd memo the Child." A senior answer first says a re-render is not a bug — reconciliation of a leaf component is microseconds. You optimize when the profiler shows a render is actually expensive or on a hot path. Say that and you've signalled you won't scatter memo everywhere.

Q2. How do you diagnose an unnecessary re-render?

ROI: ★★★★★ Frequency: High

Short Answer

Use the React DevTools Profiler (record an interaction, look at what rendered and why), enable "Highlight updates when components render," and for stubborn cases add the why-did-you-render library which logs the exact prop/state that changed.

Detailed Answer

React DevTools Profiler

Record a session, then read the flame graph: bar width = time spent rendering that component. DevTools also shows "Why did this render?" (props changed, state changed, parent rendered, hooks changed) when you enable that setting. This tells you what is slow before you guess at fixes.

Highlight updates

The "Highlight updates when components render" toggle flashes a border around every component that renders. If typing in one input flashes the whole page, you've found a state-colocation problem.

why-did-you-render

For memoized components that still re-render, @welldone-software/why-did-you-render logs which prop is a new reference each time — usually an inline object or callback.

Senior Engineer Perspective

"Measure first" must come out of your mouth before any fix. Interviewers deliberately leave the question open to see if you optimize blindly. Mention that the Profiler's "ranked" view surfaces the components costing the most total time — that's where you spend your effort, not on the component that renders most often but cheaply.

Q3. When does React.memo help — and when does it hurt?

ROI: ★★★★★ Frequency: Extremely High

Short Answer

React.memo skips a component's re-render if its props are shallow-equal to the previous props. It helps when a component is expensive to render or is rendered many times, and its parent re-renders often with the same props. It hurts when props change on almost every render anyway — then you pay the comparison cost plus the render.

Detailed Answer

memo does a shallow comparison of props. If every prop is referentially equal, React reuses the previous render output and skips reconciliation for that subtree. The catch: shallow equality means {} !== {}. If the parent passes an inline object, array, or arrow function, the prop is a new reference every render and memo never bails out — you've added overhead for nothing.

So memo only works if the props are stable, which usually means the callbacks are wrapped in useCallback and objects in useMemo. That is why "just memo it" is often incomplete.

Use memo whenSkip memo when
Component renders a large/expensive subtreeComponent is a cheap leaf (few DOM nodes)
It's rendered in a big listIts props change on nearly every parent render
Parent re-renders frequently with stable propsYou haven't measured a problem

Code Example

const Row = React.memo(function Row({ item, onSelect }) {
  // Re-renders only when `item` or `onSelect` reference changes.
  return <li onClick={() => onSelect(item.id)}>{item.name}</li>;
});

// Parent must keep onSelect stable, or memo is useless:
const onSelect = useCallback((id) => dispatch(select(id)), [dispatch]);

Senior Engineer Perspective

The senior insight: memo is a contract between parent and child. It's worthless unless the parent cooperates by stabilizing references. Many teams sprinkle memo on children while the parent still passes style={{color:'red'}} inline — zero benefit. Mention the upcoming React Compiler (Q13) which makes most manual memoization unnecessary.

Q4. useMemo vs useCallback — when are they actually worth it?

ROI: ★★★★★ Frequency: Extremely High

Short Answer

useMemo caches a computed value; useCallback caches a function reference (it's useMemo returning a function). Use them for (1) genuinely expensive computations, or (2) preserving referential identity so a memoized child or a dependency array doesn't see a new reference every render.

Detailed Answer

There are exactly two legitimate reasons to reach for these hooks:

  • Expensive computation: filtering/sorting a large array, parsing, heavy math. useMemo avoids redoing it when inputs are unchanged.
  • Referential stability: a value/function is passed to a memo'd child or used in another hook's dependency array. Keeping the reference stable prevents downstream re-renders or effect re-runs.

What they are not for: wrapping every trivial value. useMemo(() => a + b, [a, b]) is slower than just a + b because you pay for the hook, the dependency check, and the closure. Memoization is a cache, and caches have overhead.

useCallback(fn, deps) is literally useMemo(() => fn, deps). It exists because passing callbacks to memoized children and to effect dependencies is so common.

Code Example

// Worth it: expensive derived data
const sorted = useMemo(
  () => hugeList.slice().sort((a, b) => a.score - b.score),
  [hugeList]
);

// Worth it: stable reference for a memoized child / effect dep
const handleSave = useCallback(() => api.save(id), [id]);

// NOT worth it: trivial value
const total = useMemo(() => price * qty, [price, qty]); // just do price * qty

Senior Engineer Perspective

Interviewers love the follow-up "does useMemo guarantee the value is cached?" — no. React may discard memoized values to free memory; treat it as a performance hint, not a semantic guarantee. Never put logic in useMemo that must run (like a side effect) — that's what effects are for.

Q5. Why does passing a new object, array, or function break memoization?

ROI: ★★★★☆ Frequency: High

Short Answer

Because React (and memo) compares props by reference for objects/arrays/functions. An inline {}, [], or () => {} creates a brand-new reference on every render, so the shallow comparison always reports "changed," defeating any memoization downstream.

Detailed Answer

JavaScript compares objects by identity, not structure: {a:1} === {a:1} is false. React's shallow prop comparison uses Object.is per prop. So if a parent renders: 

<MemoChild config={{ theme: 'dark' }} onClick={() => doThing()} />

both config and onClick are new references each render, and MemoChild re-renders every time despite being wrapped in memo. Fixes: hoist static objects out of the component, wrap dynamic ones in useMemo, and wrap callbacks in useCallback. The same rule applies to useEffect dependency arrays — a new object dependency re-runs the effect every render.

Senior Engineer Perspective

This is the root cause behind ~80% of "my memo isn't working" bugs. A strong candidate connects it back to referential equality and notes that primitives (string, number, boolean) compare by value, so those are always safe to pass. Bonus: mention that this is exactly the class of bug the React Compiler eliminates automatically.

Q6. The "children as a prop" / lift-content-up trick

ROI: ★★★★☆ Frequency: Medium

Short Answer

If a component holds fast-changing state but wraps expensive children, pass those children in as the children prop from a parent. React reuses the same child element objects across the wrapper's re-renders, so the expensive subtree doesn't re-render — no memo needed.

Detailed Answer

When a component re-renders, React re-runs its function — but elements passed into it as props (including children) were created by the parent and are not recreated by the re-rendering component. So moving the stateful boundary above the expensive content isolates the churn.

Code Example

// BAD: ExpensiveTree re-renders on every mousemove
function App() {
  const [pos, setPos] = useState(0);
  return (
    <div onMouseMove={e => setPos(e.clientX)}>
      <ExpensiveTree />
    </div>
  );
}

// GOOD: state lives in a wrapper; ExpensiveTree is passed as children
function MoveTracker({ children }) {
  const [pos, setPos] = useState(0);
  return <div onMouseMove={e => setPos(e.clientX)}>{children}</div>;
}
function App() {
  return (
    <MoveTracker>
      <ExpensiveTree />   {/* created once by App, not recreated by MoveTracker */}
    </MoveTracker>
  );
}

Senior Engineer Perspective

This "structural" fix impresses more than another memo, because it shows you understand that element identity is preserved across renders when the element is created by a stable ancestor. Also mention the sibling trick: moving fast-changing state down into a small dedicated component so it doesn't re-render its parent's siblings.

Q7. How do you render a list of 10,000 rows without freezing the UI?

ROI: ★★★★★ Frequency: High

Short Answer

Windowing / virtualization: only render the rows currently visible in the viewport (plus a small overscan buffer) instead of all 10,000 DOM nodes. Libraries: react-window, @tanstack/react-virtual, react-virtuoso.

Detailed Answer

Rendering 10,000 rows means 10,000+ DOM nodes: huge memory, slow layout, janky scroll. Virtualization keeps a fixed-size window of DOM nodes (say 20 visible + 10 overscan) and recycles them as you scroll, translating them with absolute positioning inside a tall spacer that fakes the full scroll height.

Combine with: stable keys, memoized row components, avoiding inline row callbacks, and pagination/infinite-loading from the server so you never hold the whole dataset. For variable-height rows, use a virtualizer that supports dynamic measurement.

Code Example

import { FixedSizeList } from 'react-window';

<FixedSizeList height={600} itemCount={items.length} itemSize={40} width="100%">
  {({ index, style }) => (
    <div style={style}>{items[index].name}</div>
  )}
</FixedSizeList>

Senior Engineer Perspective

Follow-up traps: accessibility (virtualized lists break screen-reader row counts unless you set aria-setsize/aria-rowcount), and Ctrl+F in-page search failing because off-screen rows aren't in the DOM. A senior answer names these trade-offs rather than presenting virtualization as free.

SECTION 2 - BUNDLE & LOADING

Q8. What is code splitting and how do you do it in React?

ROI: ★★★★★ Frequency: Extremely High

Short Answer

Code splitting breaks the bundle into smaller chunks loaded on demand, so users download only what the current view needs. In React you split with dynamic import() plus React.lazy and a <Suspense> fallback — most commonly per route.

Detailed Answer

A single giant bundle means the user waits to download and parse code for pages they may never visit. The bundler (Vite/Webpack) sees a dynamic import() and emits a separate chunk that's fetched lazily. Route-based splitting is the highest-leverage version: each route becomes its own chunk.

Guidelines: split at route boundaries first, then heavy below-the-fold or rarely-used widgets (charts, editors, modals). Don't over-split tiny components — each chunk has a network round-trip cost. Preload the next likely chunk on hover/intent to hide latency.

Code Example

const Dashboard = React.lazy(() => import('./Dashboard'));

<Suspense fallback={<Spinner />}>
  <Dashboard />
</Suspense>

// Route-based (React Router v6):
{ path: 'reports', lazy: () => import('./Reports') }

Senior Engineer Perspective

Mention that lazy-loading a component that's needed immediately just adds a spinner and a round-trip — split what's deferred, not what's critical. In Next.js the App Router splits by route automatically; you use next/dynamic for component-level splitting and can disable SSR for client-only widgets.

Q9. How does tree-shaking work, and how do you keep bundles small?

ROI: ★★★★☆ Frequency: High

Short Answer

Tree-shaking is dead-code elimination based on ES module static analysis: the bundler keeps only the exports you actually import. It relies on import/export syntax and side-effect-free modules. Keep bundles small by importing narrowly, avoiding heavy dependencies, and analyzing the bundle.

Detailed Answer

Because ES modules are static (imports resolved at build time, not runtime), the bundler can build a dependency graph and drop unreferenced exports. It can't shake CommonJS reliably, and it won't drop modules marked as having side effects. Package authors declare purity via "sideEffects": false in package.json.

Practical levers:

  • Prefer named imports from tree-shakeable libraries: import { debounce } from 'lodash-es', not the whole lodash.
  • Watch for accidental barrel-file imports pulling in a whole module.
  • Run a bundle analyzer (rollup-plugin-visualizer, webpack-bundle-analyzer, source-map-explorer) to see what's actually big — often moment.js, a full icon set, or a duplicated dependency.
  • Set a realistic browserslist so Babel doesn't over-polyfill.

Senior Engineer Perspective

The strongest signal is naming a real culprit you've fixed: "we shipped both moment and date-fns, and a full @mui icon barrel — the analyzer showed 300KB we deleted." Concrete numbers beat theory.

Q10. How do you lazy-load images and heavy assets?

ROI: ★★★☆☆ Frequency: Medium

Short Answer

Use native loading="lazy" on <img>/<iframe>, serve responsive images with srcset/sizes and modern formats (AVIF/WebP), reserve space with width/height to avoid layout shift, and defer offscreen work with IntersectionObserver. In Next.js use next/image, which handles most of this.

Detailed Answer

Images are usually the largest bytes on a page and the biggest LCP factor. Strategy:

  • Defer offscreen images with loading="lazy" so the browser skips them until near the viewport.
  • Right-size with srcset + sizes so phones don't download desktop-sized images.
  • Modern formats (WebP/AVIF) cut bytes dramatically.
  • Reserve dimensions (explicit width/height or aspect-ratio) to prevent Cumulative Layout Shift.
  • Prioritize the LCP image — do NOT lazy-load the hero; mark it fetchpriority="high" or priority in next/image.

Code Example

<img
  src="hero-800.webp"
  srcSet="hero-400.webp 400w, hero-800.webp 800w, hero-1600.webp 1600w"
  sizes="(max-width: 600px) 400px, 800px"
  width="800" height="450"
  loading="lazy" decoding="async" alt="Dashboard preview" />

Senior Engineer Perspective

The classic mistake is lazy-loading the above-the-fold hero, which hurts LCP. Senior answer: lazy-load below the fold, eager-load and preload the LCP resource. Reserving dimensions is the cheapest CLS win there is.

SECTION 3 - RUNTIME & WEB VITALS

Q11. What is useTransition and useDeferredValue, and when do you use them?

ROI: ★★★★☆ Frequency: Medium-High

Short Answer

Both are React 18 concurrent features that mark work as low-priority so urgent updates (typing, clicking) stay responsive. useTransition lets you wrap a state update in startTransition to mark it non-urgent; useDeferredValue gives you a lagging copy of a value that updates after the urgent render.

Detailed Answer

Classic problem: a search box filters a huge list. Typing updates the input (urgent) but re-filtering thousands of items (expensive) makes keystrokes lag. Concurrent rendering lets React keep the input responsive and render the expensive list at lower priority, interrupting it if you type again.

  • useTransition — you control the dispatch: startTransition(() => setQuery(value)), and isPending lets you show a subtle loading state.
  • useDeferredValue — you don't control the source; you derive a deferred version: const deferredQuery = useDeferredValue(query) and render the heavy list off that.

Code Example

const [isPending, startTransition] = useTransition();
function onChange(e) {
  setText(e.target.value);              // urgent: input stays snappy
  startTransition(() => setList(filter(e.target.value))); // deferred
}

Senior Engineer Perspective

These do NOT make the work faster — they change its priority so the main thread yields to user input. If the expensive render itself is the bottleneck, you still need memoization or virtualization. Interviewers probe whether you understand it's about perceived responsiveness, not raw speed.

Q12. What are Core Web Vitals, and how do frontend choices affect LCP, CLS, and INP?

ROI: ★★★★★ Frequency: High

Short Answer

Core Web Vitals are Google's user-centric metrics: LCP (Largest Contentful Paint — loading, target < 2.5s), CLS (Cumulative Layout Shift — visual stability, < 0.1), and INP (Interaction to Next Paint — responsiveness, < 200ms). INP replaced FID in 2024.

Detailed Answer

MetricMeasuresFrontend levers
LCPTime to render the largest element (hero image/heading)Preload the LCP asset, SSR/SSG, CDN, optimize/right-size images, reduce render-blocking CSS/JS
CLSUnexpected layout shiftsSet width/height on images, reserve space for ads/embeds, avoid inserting content above existing content, use font-display: optional/swap carefully
INPLatency from interaction to next paintBreak up long tasks, reduce JS on the main thread, debounce, use concurrent features/web workers

Measure field data with the web-vitals library or Chrome UX Report; measure lab data with Lighthouse. Field (real users) is what Google ranks on.

Senior Engineer Perspective

Know that INP is the newest and most JS-sensitive — heavy React re-renders and long event handlers hurt it directly, which is exactly why the runtime optimizations in this chapter matter for SEO, not just feel. Mention lab vs field distinction; it's a common follow-up.

Q13. What is the React Compiler, and does it make manual memoization obsolete?

ROI: ★★★★☆ Frequency: Rising (Modern)

Short Answer

The React Compiler (formerly "React Forget") is a build-time tool that automatically memoizes components and values, so you generally no longer need to hand-write useMemo, useCallback, or React.memo. It analyzes your code and inserts fine-grained caching that skips re-computation and re-renders when inputs are unchanged.

Detailed Answer

Manual memoization is error-prone: developers forget dependencies, over-memoize, or break it with unstable references (Q5). The Compiler shifts this to build time. It relies on your components following the Rules of React (pure render, no mutation of props/state), which is why the eslint-plugin-react-hooks / React Compiler ESLint rules matter — the compiler bails out safely on code it can't prove is safe.

It doesn't replace algorithmic optimization (virtualization, code splitting, reducing payloads). It removes the referential-equality busywork.

Senior Engineer Perspective

Positioning matters: say "it automates the memoization tax, but writing correct, pure components and choosing the right data-fetching and rendering strategy is still on us." That shows you see the compiler as removing a category of micro-optimization, not as a silver bullet for architecture.

SECTION 4 - MEASURING & DIAGNOSING

Q14. How do you measure React application performance end to end?

ROI: ★★★★☆ Frequency: High

Short Answer

Lab tools: Lighthouse and the Chrome DevTools Performance panel for load and main-thread analysis; React DevTools Profiler for render cost. Field tools: the web-vitals library reporting real-user metrics to your analytics/RUM. Bundle: a bundle analyzer. Always compare a baseline before/after a change.

Detailed Answer

  • Lighthouse — synthetic score + Web Vitals + opportunities (unused JS, render-blocking resources).
  • Performance panel — flame chart of the main thread; find long tasks (> 50ms), forced reflows, and scripting vs rendering time.
  • React Profiler — which components render and how long; the "ranked" chart.
  • web-vitals / RUM — real users on real devices/networks; the truth that lab can't capture.
  • Bundle analyzer — where the bytes go.

The discipline that matters: define the metric, measure a baseline, make one change, re-measure. Otherwise you can't prove the optimization worked.

Senior Engineer Perspective

Test on a throttled CPU (4–6x slowdown) and slow network — your M-series laptop hides the problems your users on mid-range Android phones feel. Interviewers respect "I profile on throttled devices" because it shows empathy for real conditions.

Q15. What is layout thrashing and how do you avoid it?

ROI: ★★★☆☆ Frequency: Medium

Short Answer

Layout thrashing (forced synchronous reflow) happens when you interleave DOM reads (like offsetHeight) and writes in a loop, forcing the browser to recalculate layout repeatedly in a single frame. Avoid it by batching all reads, then all writes, and using requestAnimationFrame for visual updates.

Detailed Answer

The browser normally batches layout and computes it once per frame. But reading a layout property (offsetTop, getBoundingClientRect, scrollHeight) after a write forces it to flush layout now to give you a fresh value. Do that in a loop and you get N forced reflows — the page janks.

Code Example

// BAD: read, write, read, write... forces reflow each iteration
els.forEach(el => { el.style.width = el.offsetWidth + 10 + 'px'; });

// GOOD: batch reads, then batch writes
const widths = els.map(el => el.offsetWidth);   // all reads
els.forEach((el, i) => { el.style.width = widths[i] + 10 + 'px'; }); // all writes

Senior Engineer Perspective

In React you rarely touch the DOM directly, but this bites in useLayoutEffect measurement code, animation libraries, and ref-based logic. Mention that prefer transforms/opacity for animations (composited, no layout) over animating width/top (triggers layout/paint).
