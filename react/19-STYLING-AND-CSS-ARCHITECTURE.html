SECTION 1 - CSS CORE FOR INTERVIEWS

Q1. How does CSS specificity and the cascade decide which rule wins?

ROI: ★★★★★ Frequency: Extremely High

Short Answer

When multiple rules target the same element, the winner is decided by (1) importance/origin, (2) specificity, then (3) source order. Specificity is a tuple counting inline styles, IDs, classes/attributes/pseudo-classes, and elements/pseudo-elements — higher tuple wins; ties go to whichever rule appears last.

Detailed Answer

Specificity tuple (a, b, c, d)

  • a — inline style="" (1 or 0)
  • b — number of IDs
  • c — number of classes, attribute selectors, pseudo-classes
  • d — number of element/pseudo-element selectors

Compare left to right: #nav .item (0,1,1,0) beats .header .item a (0,0,2,1) because the ID component wins before classes are even considered. !important overrides normal declarations (and should be a last resort). The universal selector * and combinators (>, +, ~) add nothing to specificity.

The cascade order: (1) origin & importance (author !important > author normal > user-agent), (2) specificity, (3) order of appearance. Modern CSS adds layers (@layer) which sit above specificity within the same origin, letting you control precedence explicitly.

Code Example

<a class="link" id="cta">Buy</a>

a          { color: black; }   /* (0,0,0,1) */
.link      { color: blue; }    /* (0,0,1,0) wins over element */
#cta       { color: red; }     /* (0,1,0,0) wins over class -> RED */

Senior Engineer Perspective

The senior point is that high specificity is a smell — ID selectors and !important create escalation wars. Modern architectures (BEM, utility classes, CSS Modules) deliberately keep specificity flat (mostly single classes) so overriding is predictable. Mention @layer and the new :where() (which has zero specificity) as tools for taming it.

Q2. Explain the box model and box-sizing.

ROI: ★★★★☆ Frequency: High

Short Answer

Every element is a box: content, then padding, then border, then margin. With the default box-sizing: content-box, width sets only the content width, so padding and border are added on top. With box-sizing: border-box, width includes content + padding + border, which is far more intuitive.

Detailed Answer

With content-box, a 200px box with 20px padding and 2px border actually occupies 244px — the source of endless layout surprises. That's why almost every codebase sets: 

*, *::before, *::after { box-sizing: border-box; }

so width: 200px means the box is exactly 200px including padding/border. Margins are always outside the box and can collapse vertically between block siblings (the larger of the two adjacent margins is used, not the sum) — a frequent gotcha.

Senior Engineer Perspective

Margin collapsing is a favourite follow-up: it happens between vertical block margins, not horizontal, and is prevented by padding/border between them, or by a fl/ grid container (flex/grid items don't collapse). Knowing this signals real CSS depth.

Q3. What do the different CSS position values do?

ROI: ★★★★☆ Frequency: High

Short Answer

static (default, in normal flow), relative (offset from its normal spot, still occupies original space, becomes a positioning context), absolute (removed from flow, positioned relative to the nearest positioned ancestor), fixed (relative to the viewport), and sticky (relative until a scroll threshold, then fixed within its container).

Detailed Answer

ValueIn flow?Positioned relative toTypical use

relativeYes (keeps space)Its own normal positionNudge + create anchor for absolute children
absoluteNoNearest ancestor with position != staticTooltips, dropdowns, badges

The key relationship: absolute looks up the ancestor chain for the first element that is not static. That's why you set position: relative on a parent to "contain" an absolutely-positioned child.

Senior Engineer Perspective

sticky silently fails if the parent has overflow: hidden/auto or no defined height — a very common real bug. And position (other than static) plus a z-index creates a stacking context (Q7). Connecting these shows you understand the interactions, not just the definitions.

Q4. Flexbox: explain main vs cross axis and give common recipes.

ROI: ★★★★★ Frequency: Extremely High

Short Answer

Flexbox lays items along a main axis (set by flex-direction) and aligns them on the perpendicular cross axis. justify-content distributes along the main axis; align-items aligns along the cross axis. It's ideal for one-dimensional layouts (a row or a column).

Detailed Answer

With flex-direction: row (default), main axis is horizontal, cross axis is vertical. Switch to column and they swap — which is why beginners get confused about why justify-content suddenly controls vertical spacing.

  • justify-content: flex-start / center / space-between / space-around / space-evenly (main axis)
  • align-items: stretch / center / flex-start / flex-end / baseline (cross axis)
  • flex: 1 = flex-grow:1; flex-shrink:1; flex-basis:0 — item grows to fill
  • gap: modern spacing between items (no more margin hacks)
  • flex-wrap: wrap: allow items to flow onto new lines

Code Example

/* Navbar: logo left, links right, vertically centered */
.nav { display: flex; justify-content: space-between; align-items: center; gap: 16px; }

/* Perfect centering */
.center { display: flex; justify-content: center; align-items: center; min-height: 100vh; }

/* Card that fills remaining space next to a fixed sidebar */
.layout { display: flex; }
.sidebar { flex: 0 0 240px; }   /* fixed */
.main    { flex: 1; }           /* grows */

Senior Engineer Perspective

Know that flex-basis beats width in flex containers, and that min-width: auto (the default) is why flex items refuse to shrink below their content — the fix for "my text overflows the flex item" is min-width: 0. That one gotcha comes up constantly in real work.

Q5. Grid vs Flexbox — when do you use each?

ROI: ★★★★☆ Frequency: High

Short Answer

Flexbox is one-dimensional (content flows along a single axis and wraps); Grid is two-dimensional (you define rows and columns simultaneously). Use Flexbox for components (toolbars, button groups, nav) and Grid for page/section layouts (dashboards, card grids, complex templates).

Detailed Answer

Rule of thumb: Flexbox is content-out (items size themselves and distribute in the available space), Grid is layout-in (you define the structure and place items into it). They compose — a grid cell often contains a flex container.

Code Example

/* Responsive card grid — auto-fit is the killer feature */
.cards {
  display: grid;
  grid-template-columns: repeat(auto-fit, minmax(240px, 1fr));
  gap: 16px;
}

/* Named-area page layout */
.app {
  display: grid;
  grid-template-columns: 240px 1fr;
  grid-template-rows: 56px 1fr;
  grid-template-areas: "sidebar header" "sidebar main";
}
.header { grid-area: header; }

Senior Engineer Perspective

The repeat(auto-fit, minmax(...)) pattern gives you a responsive grid with zero media queries — mentioning it signals modern CSS fluency. Also note auto-fit vs auto-fill: auto-fit collapses empty tracks (items stretch), auto-fill keeps them (items stay their min size).

Q6. px vs em vs rem — which do you use and why?

ROI: ★★★★☆ Frequency: High

Short Answer

px is an absolute, fixed unit. em is relative to the current element's font-size (compounds through nesting). rem is relative to the root font-size (no compounding). Prefer rem for font sizes and spacing so the whole UI scales with the user's browser font setting; use px for things that should never scale (hairline borders).

Detailed Answer

Accessibility is the real reason this matters: users who set a larger default font in their browser get a UI that scales if you use rem, but a UI frozen at your hard-coded sizes if you use px everywhere. em is useful for things that should scale relative to their own text (padding inside a button that grows with the button's font-size), but its compounding — a 1.2em inside a 1.2em is 1.44em — makes it unpredictable for global sizing.

Modern responsive typography often uses clamp(): font-size: clamp(1rem, 2.5vw, 1.5rem) for fluid, bounded scaling.

Senior Engineer Perspective

Don't set html { font-size: 62.5% } (the old "1rem = 10px" hack) blindly — it can fight user zoom expectations. The strongest answer ties unit choice to accessibility and to a spacing scale expressed in rem tokens.

Q7. How does z-index really work? (stacking contexts)

ROI: ★★★★☆ Frequency: Medium-High

Short Answer

z-index only works on positioned elements (and flex/grid items) and only orders elements within the same stacking context. A high z-index inside one stacking context can never poke above a sibling context — so "my modal with z-index 9999 is still behind the header" is almost always a stacking-context problem, not a number problem.

Detailed Answer

A new stacking context is created by, among others: the root element; position other than static + a z-index; opacity < 1; transform, filter, will-change; isolation: isolate. Once an element forms a stacking context, its children's z-indexes are only compared against each other — the whole subtree stacks as one unit relative to outside elements.

This is why a parent with transform or opacity can trap a child modal beneath other content. The fix is usually to render the modal via a React portal at the document root, escaping the trapping context entirely.

Senior Engineer Perspective

The senior move: instead of a z-index arms race, portal overlays to document.body and keep a small, documented z-index scale (e.g. dropdown 1000, sticky 1100, modal 1300, toast 1400). Mention isolation: isolate as a way to deliberately contain z-index within a component.

Q8. How do you center an element? (all the ways)

ROI: ★★★☆☆ Frequency: Medium

Short Answer

Modern default: Flexbox (display:flex; justify-content:center; align-items:center) or Grid (display:grid; place-items:center). For a block with known width, margin: 0 auto centers horizontally. Absolute centering uses top/left:50% + transform: translate(-50%,-50%).

Code Example

/* Grid — shortest */
.wrap { display: grid; place-items: center; min-height: 100vh; }

/* Absolute (when you can't touch the parent's display) */
.box {
  position: absolute;
  top: 50%; left: 50%;
  transform: translate(-50%, -50%);
}

Senior Engineer Perspective

This used to be a "gotcha" question in the float/table era; today it's a warm-up. Score points by naming place-items: center as the one-liner and mentioning that the transform trick works without knowing the element's dimensions, unlike negative-margin centering.

SECTION 2 - STYLING REACT

Q9. Compare the main styling approaches in React and their trade-offs.

ROI: ★★★★★ Frequency: Extremely High

Short Answer

The main families are: plain CSS / CSS Modules (scoped classes at build time), CSS-in-JS (styled-components/Emotion — styles co-located in JS, dynamic props, runtime cost), utility-first (Tailwind — compose atomic classes), and zero-runtime CSS-in-JS (vanilla-extract, Linaria, or PandaCSS — CSS-in-JS ergonomics extracted to static CSS at build time).

Detailed Answer

ApproachScopingDynamic stylesRuntime costNotes
Plain CSS / globalManual (BEM)Via class togglesNoneSimple, but easy to leak
CSS ModulesAutomatic (hashed)Class togglesNone (build-time)Great default, no runtime
CSS-in-JS (styled/Emotion)AutomaticExcellent (props)Runtime style injectionDX great; RSC/SSR friction
TailwindN/A (atomic)Conditional class stringsNone (JIT purges)Fast to ship, verbose markup

The modern trend, especially with React Server Components, moves away from runtime CSS-in-JS (styled-components has friction in RSC because it needs client context) toward CSS Modules, Tailwind, or zero-runtime solutions that produce static CSS.

Senior Engineer Perspective

Don't declare one "best." Frame it by constraints: "For a Next.js App Router app I'd lean Tailwind or CSS Modules to avoid runtime CSS-in-JS in Server Components; for a heavily-themed design system I might pick vanilla-extract for typed tokens with zero runtime." That contextual reasoning is what they're testing.

Q10. How do you scope styles and avoid global CSS leaks?

ROI: ★★★★☆ Frequency: High

Short Answer

Use a scoping mechanism so class names can't collide: CSS Modules (build-time hashed names like Button_root__x7f2), CSS-in-JS (auto-generated unique classes), or a naming convention like BEM in plain CSS. Avoid broad element selectors and deeply nested global rules.

Detailed Answer

Plain global CSS has one namespace, so .button defined in two files fights, and generic selectors (div > p) leak into places you never intended. The failure mode is a change in one component silently breaking another. Solutions in order of guarantee:

  • CSS Modules — import styles from './Button.module.css'; the bundler rewrites class names to be unique. Zero runtime, strongest default.
  • CSS-in-JS — styles are generated with unique hashes automatically.
  • BEM — block__element--modifier discipline in plain CSS; works but relies on humans.
  • Cascade layers / :where() — keep specificity low so overrides are predictable.

Code Example

/* Button.module.css */
.root { padding: 8px 16px; border-radius: 6px; }

// Button.tsx
import styles from './Button.module.css';
export function Button(props) {
  return <button className={styles.root} {...props} />;
}

Senior Engineer Perspective

Global CSS still has a legitimate place: resets, CSS custom properties (design tokens), typography base, and third-party overrides. The senior answer is "scope component styles, keep a small deliberate global layer for tokens and resets" — not "never use global."

SECTION 3 - RESPONSIVE & THEMING

Q11. What are CSS custom properties, and how do you build theming / dark mode with them?

ROI: ★★★★★ Frequency: High

Short Answer

CSS custom properties (variables) are runtime values declared with --name and read with var(--name). They cascade and can be overridden per scope, which makes theming trivial: define color tokens on :root, override them under a [data-theme="dark"] selector, and every component that reads the tokens updates instantly — no JS re-render, no duplicate stylesheets.

Detailed Answer

Unlike Sass variables (compiled away at build), CSS custom properties are live in the browser: you can change them at runtime and they re-cascade. That's exactly what you want for theming. The pattern:

  1. Define semantic tokens on :root (--color-bg, --color-text, --color-accent).
  2. Override them in a dark scope.
  3. Components reference only tokens, never raw hex.
  4. Toggle the theme by setting an attribute/class on <html>; persist the choice in localStorage and respect prefers-color-scheme as the default.

Code Example

:root {
  --color-bg: #ffffff;
  --color-text: #111827;
  --color-accent: #2563eb;
}
:root[data-theme="dark"] {
  --color-bg: #0f172a;
  --color-text: #e2e8f0;
}
body { background: var(--color-bg); color: var(--color-text); }

// React: toggle + persist
const [theme, setTheme] = useState(
  () => localStorage.getItem('theme')
     ?? (matchMedia('(prefers-color-scheme: dark)').matches ? 'dark' : 'light')
);
useEffect(() => {
  document.documentElement.dataset.theme = theme;
  localStorage.setItem('theme', theme);
}, [theme]);

Senior Engineer Perspective

Two senior points: (1) avoid the dark-mode "flash of wrong theme" on load by setting the attribute in an inline script before first paint (in Next.js, a small blocking script or next-themes). (2) Prefer semantic tokens (--color-bg) over literal ones (--gray-900) so themes can remap meaning, not just values.

Q12. Responsive design: media queries vs container queries?

ROI: ★★★★☆ Frequency: Medium-High

Short Answer

Media queries respond to the viewport (or device features); container queries respond to the size of a component's container. Container queries let a component adapt based on where it's placed, making it truly reusable — a card can switch to a horizontal layout whenever its container is wide enough, regardless of screen size.

Detailed Answer

Media queries are still the backbone of page-level responsiveness (breakpoints for phone/tablet/desktop) and for feature detection (prefers-color-scheme, prefers-reduced-motion, hover, pointer). Their limitation: a component only knows the viewport width, not how much room it actually has — the same card in a sidebar vs a wide main area can't adapt independently.

Container queries (now broadly supported) fix this: mark an element as a container with container-type, then query it with @container.

Code Example

/* Media query — viewport based */
@media (min-width: 768px) { .grid { grid-template-columns: 1fr 1fr; } }

/* Container query — component based */
.card-wrap { container-type: inline-size; }
@container (min-width: 400px) {
  .card { display: grid; grid-template-columns: 120px 1fr; }
}

/* Respect motion preferences */
@media (prefers-reduced-motion: reduce) { * { animation: none !important; } }

Senior Engineer Perspective

Adopting a mobile-first approach (base styles for small screens, min-width queries to layer on larger) keeps CSS cleaner. Mention prefers-reduced-motion unprompted — it signals accessibility awareness, which senior interviewers weight heavily.

Q13. How do you build and maintain a design system with tokens?

ROI: ★★★★☆ Frequency: Medium

Short Answer

Define design tokens — named, single-source-of-truth values for color, spacing, typography, radii, shadows, z-index — and express them once (CSS variables, a Tailwind theme config, or typed constants). Every component consumes tokens, never raw values. Layer semantic tokens (--color-danger) on top of primitive tokens (--red-600) so intent is decoupled from value.

Detailed Answer

A scalable system typically has three tiers of tokens: primitive (raw palette and scale: --blue-500, --space-4), semantic (meaning: --color-accent, --color-surface), and component (--button-bg). Themes and brands remap the semantic layer without touching components. Pair this with a spacing scale (e.g. 4px base: 4, 8, 12, 16, 24, 32) so spacing is consistent and not arbitrary.

Tools: Tailwind's theme config, Style Dictionary (to generate tokens for web/iOS/Android from one source), vanilla-extract for typed tokens, and Storybook to document and visually test components in isolation.

Senior Engineer Perspective

The differentiator is the semantic layer. Junior systems hard-code color: var(--blue-500) everywhere; when the brand changes you touch hundreds of files. With semantic tokens you change one mapping. Mention Storybook + visual regression testing (Chromatic) as how you keep a system from drifting.

Q14. What are the performance implications of the different styling approaches?

ROI: ★★★★☆ Frequency: Medium

Short Answer

Build-time solutions (CSS Modules, Tailwind, zero-runtime CSS-in-JS) ship static CSS with no runtime cost. Runtime CSS-in-JS (styled-components/Emotion) serializes and injects styles during render, adding JS work and potential re-render/serialization overhead, plus SSR complexity. For large apps, extracting critical CSS and avoiding runtime style generation matters for LCP and INP.

Detailed Answer

  • Runtime CSS-in-JS: styles computed per render; dynamic props re-generate classes; SSR needs to collect and inline styles to avoid a flash. Fine for most apps, but a measurable tax at scale and awkward in Server Components.
  • Tailwind: JIT generates only used classes and purges the rest; the resulting stylesheet is small and cacheable. Atomic classes also dedupe repeated declarations.
  • CSS Modules / zero-runtime: plain .css files, cached and parsed by the browser once, no JS involvement.

Cross-cutting wins regardless of approach: minimize unused CSS, split critical vs non-critical CSS, avoid huge global stylesheets, and let the browser cache CSS separately from JS.

Senior Engineer Perspective

The industry moved off runtime CSS-in-JS for new large projects partly for these reasons plus RSC compatibility (styled-components can't run in Server Components without a client boundary). Framing the shift accurately — "not that CSS-in-JS is bad, but the constraints changed with RSC" — reads as current and balanced.

Q15. Animations: CSS vs Framer Motion, and what's cheap to animate?

ROI: ★★★★☆ Frequency: Medium

Short Answer

Animate transform and opacity — they're handled by the compositor (GPU) and skip layout and paint, so they hit 60fps. Avoid animating width, height, top, left, or margin, which trigger layout on every frame. Use plain CSS transitions/keyframes for simple state changes; reach for Framer Motion (motion/react) for orchestrated, gesture-driven, layout, or enter/exit animations.

Detailed Answer

The browser's rendering pipeline is layout → paint → composite. Animating geometric properties forces layout + paint every frame (expensive); animating transform/opacity only re-composites (cheap). This is the single most important animation-performance rule.

CSS handles hover, focus, and simple transitions with zero JS. Framer Motion adds: spring physics, AnimatePresence for exit animations (which CSS can't do when a component unmounts), shared-layout/FLIP animations, drag gestures, and scroll-linked effects — all declaratively. The cost is bundle size and JS on the main thread, so use it where it earns its keep.

Code Example

/* Cheap CSS transition — composited */
.card { transition: transform .2s ease, opacity .2s ease; }
.card:hover { transform: translateY(-4px); }

// Framer Motion enter/exit
import { motion, AnimatePresence } from 'motion/react';
<AnimatePresence>
  {open && (
    <motion.div
      initial={{ opacity: 0, y: 8 }}
      animate={{ opacity: 1, y: 0 }}
      exit={{ opacity: 0, y: 8 }}
    />
  )}
</AnimatePresence>

Senior Engineer Perspective

Always gate animation behind prefers-reduced-motion for accessibility. And know will-change is a hint to promote an element to its own layer — useful sparingly, harmful if overused (memory, too many layers). Naming the composited-properties rule unprompted is the strongest signal here.
