SECTION 1 - RULES & useState

Q1. What are the Rules of Hooks, and why does call order matter?

ROI: ★★★★★ Frequency: Extremely High

Short Answer

There are two rules: only call hooks at the top level (never inside conditions, loops, or nested functions), and only call them from React function components or custom hooks. They matter because React does not identify hooks by name — it identifies them by call order. React keeps an ordered list of hook "slots" per component instance, and on every render it walks that list in the same sequence. Break the order and React hands you the wrong state.

Detailed Answer

Internally, a component's hooks are stored as a linked list attached to its fiber. There is no key like "count" or "user" — the first useState you call is slot 0, the second is slot 1, and so on. On the next render React resets a pointer to the head of the list and reads slots back in the exact order you call them.

Why conditional hooks break this

If you wrap a hook in an if, then on renders where the condition is false, one slot is skipped. Every hook after it shifts by one position, so React returns state that belongs to a different hook. This is why the linter rule react-hooks/rules-of-hooks is effectively non-negotiable.

  • Top level only — no hooks inside if, for, while, ternaries, or callbacks.
  • Function components / custom hooks only — not class components, not plain utility functions, not event handlers.
  • Order must be identical on every render — the count and sequence of hook calls must be stable.

The correct pattern is to always call the hook unconditionally and put the condition inside the hook logic, or to split into two components so each renders a fixed set of hooks.

Code Example

// WRONG — hook order changes between renders
function Profile({ userId }: { userId?: string }) {
  if (userId) {
    const [user, setUser] = useState(null); // slot 0 only sometimes exists
  }
  const [theme, setTheme] = useState("light"); // slot shifts!
  // ...
}

// RIGHT — always call unconditionally, branch inside
function Profile({ userId }: { userId?: string }) {
  const [user, setUser] = useState<User | null>(null);
  const [theme, setTheme] = useState("light");

  useEffect(() => {
    if (!userId) return;      // condition lives INSIDE the hook
    fetchUser(userId).then(setUser);
  }, [userId]);
  // ...
}

Project Example

A classic bug: a settings panel that conditionally called useMemo only when a feature flag was on. When the flag toggled at runtime, every hook below it read the wrong slot and the form silently reset. Moving the flag check inside the memo factory fixed it instantly.

Senior Engineer Perspective

Interviewers want to hear "call order / slot-based storage", not just "the linter says so". If you can explain why React can't use names (it would need a compiler pass or explicit keys, which hurts composition), you demonstrate you understand the reconciler, not just the API. A strong follow-up: "Could early return before a hook break the rules?" — yes, because it skips subsequent hooks on some renders. The React Compiler (React 19) auto-memoizes but does not relax these rules; the linear model still holds.

Q2. How does useState work — functional updates, lazy initialization, and batching in React 18?

ROI: ★★★★★ Frequency: Extremely High

Short Answer

useState returns a value and a setter. The setter can take either a new value or an updater function prev => next, which is the correct form whenever the next state depends on the previous one. Pass a function to useState for lazy initialization when the initial value is expensive to compute. In React 18, all state updates — including those inside promises, timeouts, and native events — are automatically batched into a single re-render.

Detailed Answer

Functional updates

State setters are asynchronous with respect to the current render: the count variable in scope is a snapshot. Calling setCount(count + 1) three times in a row all read the same stale count and only bump it once. The updater form setCount(c => c + 1) queues each update against the latest queued value, so three calls bump it three times.

Lazy initialization

The initializer argument runs on every render but its result is only used on the first. If it's expensive (parsing localStorage, building a big structure), pass a function instead — React only calls it once, on mount.

Batching in React 18

Before React 18, updates were only batched inside React event handlers. Updates in setTimeout, promises, or async callbacks each triggered their own render. React 18's automatic batching groups all of them, regardless of source. You can opt out with flushSync if you truly need a synchronous DOM update between two state changes.

Code Example

// Functional updates — required when next depends on prev
function Counter() {
  const [count, setCount] = useState(0);

  const addThree = () => {
    setCount(c => c + 1);   // queued: 0 -> 1
    setCount(c => c + 1);   // queued: 1 -> 2
    setCount(c => c + 1);   // queued: 2 -> 3  ✅ result is 3
    // setCount(count + 1) x3 would all read 0 and land on 1
  };
  return <button onClick={addThree}>{count}</button>;
}

// Lazy init — parse runs once, not on every render
const [prefs, setPrefs] = useState(() =>
  JSON.parse(localStorage.getItem("prefs") ?? "{}")
);

// React 18 automatic batching — ONE re-render, not two
setTimeout(() => {
  setLoading(false);
  setData(payload);   // batched together in React 18
}, 0);

Senior Engineer Perspective

The trap here is claiming setState is "synchronous" or that it "returns the new value" — it does neither. A senior answer connects functional updates to closures: setCount(count + 1) fails in loops and rapid handlers precisely because count is captured. Expect the follow-up "when would you use flushSync?" — the honest answer is "almost never; only when you must read layout between two updates," because it forces a synchronous render and hurts performance.

Q3. Why can't you call hooks conditionally, and how do you handle logic that really is conditional?

ROI: ★★★★ Frequency: High

Short Answer

You can't because it changes the number/order of hook calls between renders and desyncs React's slot list. When logic genuinely needs to be conditional, keep the hook call unconditional and put the branch inside it, use conditional values as arguments, or extract the conditional part into a separate child component that either mounts or doesn't.

Detailed Answer

The most common patterns for "conditional hooks":

  • Branch inside the effect: always call useEffect, and return early inside it if the condition is false.
  • Conditional query enabling: data libraries expose an enabled flag (e.g. TanStack Query's enabled: !!id) so the hook always runs but does nothing until ready.
  • Component split: render {isOpen && <Modal />}. The parent's hook set is stable; the child mounts/unmounts, and its hooks are consistent for its own lifetime.

The component-split approach is usually the cleanest because "this feature only exists sometimes" is naturally expressed as "this component sometimes renders."

Code Example

// Instead of conditionally calling a hook, conditionally render the component
function Page({ showChart }: { showChart: boolean }) {
  return (
    <div>
      <Header />
      {showChart && <Chart />}   {/* Chart owns its own hooks safely */}
    </div>
  );
}

Senior Engineer Perspective

The tell of a junior answer is trying to be clever with useState wrapped in a helper that's "sometimes" called. Seniors reach for the component boundary because it also localizes state lifetime and cleanup. Mentioning the enabled pattern signals you've used a real data layer, not just raw effects.

SECTION 2 - useEffect DEEP DIVE

Q4. Explain the full mental model of useEffect: when does it run across mount, update, and unmount?

ROI: ★★★★★ Frequency: Extremely High

Short Answer

useEffect runs after the browser has painted the committed render. On mount it runs the effect once. On each subsequent commit, if any dependency changed, React first runs the previous effect's cleanup, then runs the new effect. On unmount it runs cleanup one final time. The dependency array is what decides whether an update re-runs the effect at all.

Detailed Answer

Stop thinking of effects as "lifecycle methods". The right mental model is: an effect synchronizes an external system with your current render's props and state. Every render produces a snapshot of values, and the effect describes what should be true of the outside world for that snapshot.

The three dependency-array modes

DepsWhen the effect runs
[a, b]After mount, and after any commit where a or b changed (by Object.is).
[]Only after the initial mount (and cleanup only on unmount).
omittedAfter every single commit. Almost always a mistake.

Ordering within a commit

React commits the DOM, the browser paints, then effects fire. For an update, the sequence is: run last render's cleanup → run this render's effect. This "cleanup then re-run" is why subscriptions and event listeners don't leak: each run undoes the previous one.

Code Example

useEffect(() => {
  console.log("effect runs with roomId =", roomId);
  const conn = createConnection(roomId);
  conn.connect();

  return () => {
    console.log("cleanup for roomId =", roomId);
    conn.disconnect();
  };
}, [roomId]);

// Mount (roomId="a"): "effect runs a"
// Update to "b":       "cleanup a" then "effect runs b"
// Unmount:             "cleanup b"

Project Example

A chat feature keyed on roomId: when the user switches rooms, the effect cleans up the old socket and opens a new one automatically. No manual "did roomId change?" comparison is needed — the dependency array is that comparison.

Senior Engineer Perspective

The phrase to land is "synchronization, not lifecycle." Interviewers probe whether you know effects run after paint (that's why useLayoutEffect exists for pre-paint work). A great follow-up answer: the cleanup captures the values from the render that created it — the closure over roomId in the example logs "a" on cleanup even though the component is heading to "b". That closure behavior is the root of most effect confusion.

Q5. What is a stale closure in useEffect, and how do you fix it?

ROI: ★★★★★ Frequency: Extremely High

Short Answer

A stale closure happens when an effect (often one with [] deps) captures a value from its first render and keeps using that frozen value even after state changes. The fixes, in order of preference: add the value to the dependency array; use the functional updater form so you never read stale state; or, for values you deliberately don't want to re-subscribe on, store them in a ref that you keep current.

Detailed Answer

Because each render creates fresh function closures over that render's variables, an effect that runs only on mount closes over the mount-time values forever. A setInterval callback set up with [] deps will keep seeing count === 0 no matter how many times you increment.

  • Add the dep — correct but re-runs the effect (tears down and rebuilds the interval each tick, usually undesirable here).
  • Functional updater — setCount(c => c + 1) never reads the captured count, so the stale value is irrelevant. Best fix for counters.
  • Ref mirror — keep the latest value in a ref (latest.current = value) updated each render; read latest.current inside the effect. Use when you want the freshest value without re-subscribing.

Code Example

// BUG — captures count = 0 forever, logs 0 every second
useEffect(() => {
  const id = setInterval(() => console.log(count), 1000);
  return () => clearInterval(id);
}, []); // eslint-disable-line — the classic smell

// FIX A — functional updater, no stale read needed
useEffect(() => {
  const id = setInterval(() => setCount(c => c + 1), 1000);
  return () => clearInterval(id);
}, []);

// FIX B — ref mirror keeps latest value without re-subscribing
const countRef = useRef(count);
useEffect(() => { countRef.current = count; });
useEffect(() => {
  const id = setInterval(() => console.log(countRef.current), 1000);
  return () => clearInterval(id);
}, []);

Senior Engineer Perspective

Never say "just disable the exhaustive-deps lint rule" as your primary answer — that's the exact move that hides stale closures. Interviewers love watching a candidate reason about why the interval sees 0: because the closure was built once. Mentioning the ref-mirror pattern (the basis of libraries' useEvent / useEffectEvent) shows depth. React's experimental useEffectEvent formalizes exactly this "read latest, don't re-subscribe" need.

Q6. Why does my useEffect loop forever? Walk through debugging it.

ROI: ★★★★★ Frequency: Extremely High

Short Answer

An effect loops when it updates state that (directly or indirectly) is one of its own dependencies, or when a dependency is a value re-created on every render — an object, array, or function literal — so Object.is always sees it as "changed". The fix is to remove the self-triggering update, or stabilize the offending dependency with useMemo/useCallback, or move it out of the render.

Detailed Answer

The loop mechanics: effect runs → calls setState → triggers re-render → dependency looks different → effect runs again → forever. There are three recurring culprits.

Culprit 1 — the effect sets state it depends on

Reading a value, deriving from it, and setting state, with that value in deps.

Culprit 2 — a new object/array/function in deps every render

useEffect(fn, [{ id }]) or [options] where options = {} is defined in the component body. A fresh reference each render means the dep is never equal.

Culprit 3 — a non-memoized callback prop in deps

Parent passes onDone={() => ...} (new function each render); child lists it in deps.

Debug procedure: (1) log inside the effect to confirm it's re-firing; (2) log each dependency's identity; (3) find which one changes every render; (4) either stop creating it fresh, memoize it, or drop it from deps if it doesn't belong there.

Code Example

// LOOP 1 — sets a dep it reads
useEffect(() => {
  setTotal(items.reduce((s, i) => s + i.price, 0)); // total isn't a dep, but...
}, [items, total]); // total in deps + setTotal each run = infinite loop
// FIX: don't store derived data — compute during render (see Q13),
// or drop `total` from deps: }, [items]);

// LOOP 2 — new object identity every render
const filters = { status: "open" };          // fresh object each render
useEffect(() => { fetchTasks(filters); }, [filters]); // never equal -> loops
// FIX: useMemo(() => ({ status: "open" }), []) or depend on [status]

// LOOP 3 — unstable callback prop
useEffect(() => { subscribe(onData); }, [onData]); // onData new each parent render
// FIX: wrap onData in useCallback in the parent

Project Example

A dashboard that took a config object prop and fetched on [config] hammered the API on every parent render. The parent was building config inline in JSX. Wrapping it in useMemo (keyed on the actual scalar inputs) stopped the storm without touching the child.

Senior Engineer Perspective

This is a live-debugging favorite. Interviewers want a procedure, not a guess: confirm it loops, then isolate the unstable dependency by identity. The senior insight is that the real root cause is usually "we're depending on a reference we recreate every render" — and that the deeper fix is often not memoizing harder but restructuring (depend on primitives, or don't store derived state). Blaming the linter for "making me add the dep" is a red flag; the linter surfaced a real reference-identity problem.

Q7. Why do effects run twice in React 18 StrictMode, and what does it teach you?

ROI: ★★★★ Frequency: High

Short Answer

In development only, StrictMode intentionally mounts each component, runs its effects, runs cleanup, and mounts again — so effects fire twice. It's a stress test that surfaces effects which aren't resilient to being set up and torn down repeatedly (leaked subscriptions, duplicate requests, missing cleanup). It does not happen in production, and the correct response is to write proper cleanup, not to suppress the double-run.

Detailed Answer

React's concurrent features can mount, unmount, and remount components (for example, when restoring state on tab switching). StrictMode simulates that up front so you build effects that survive a remount. If your effect is a correct "setup / cleanup" pair, running it twice is harmless: connect → disconnect → connect leaves exactly one live connection.

The symptoms of an effect that fails the test: two network requests on load, two socket connections, a subscription registered twice. The fix is almost always adding or correcting the cleanup function, or moving one-time non-idempotent work (like an analytics "session start" event) outside the effect or guarding it appropriately.

Code Example

// Passes the StrictMode double-invoke because cleanup undoes setup
useEffect(() => {
  const controller = new AbortController();
  fetch(`/api/users/${id}`, { signal: controller.signal })
    .then(r => r.json())
    .then(setUser)
    .catch(err => { if (err.name !== "AbortError") throw err; });

  return () => controller.abort(); // second mount aborts the first request
}, [id]);

Senior Engineer Perspective

The wrong instinct — "I'll add a useRef guard so it only runs once" — is a trap answer that hides the real weakness. Seniors say: "The double-run is a feature; if it breaks my effect, my cleanup is wrong." Mentioning AbortController for fetches and disconnect for sockets shows you build idempotent, self-cleaning effects. Note it's dev-only and gated by <StrictMode>.

Q8. useEffect vs useLayoutEffect — when do you reach for each?

ROI: ★★★★ Frequency: High

Short Answer

Both have identical APIs and dependency semantics. The difference is timing: useEffect runs asynchronously after the browser paints; useLayoutEffect runs synchronously after the DOM mutation but before paint. Default to useEffect. Reach for useLayoutEffect only when you must read layout (measure a node) and synchronously re-render before the user sees a flicker.

Detailed Answer

 useEffectuseLayoutEffect
TimingAfter paint (async)Before paint (sync, blocking)
Blocks visual update?NoYes
Use forData fetching, subscriptions, logging, most side effectsMeasuring DOM, positioning tooltips/popovers, preventing flicker
SSRFineWarns — no DOM on the server

Because useLayoutEffect blocks painting, overusing it hurts responsiveness. The canonical valid use: measure an element's size/position and adjust another element synchronously so the user never sees the intermediate state (e.g., a tooltip that must flip above the trigger when there's no room below).

Code Example

// Measure then reposition before paint — no visible jump
function Tooltip({ targetRect }: { targetRect: DOMRect }) {
  const ref = useRef<HTMLDivElement>(null);
  const [flipUp, setFlipUp] = useState(false);

  useLayoutEffect(() => {
    const el = ref.current;
    if (!el) return;
    const { height } = el.getBoundingClientRect();
    setFlipUp(targetRect.bottom + height > window.innerHeight);
  }, [targetRect]);

  return <div ref={ref} className={flipUp ? "above" : "below"} />;
}

Senior Engineer Perspective

Interviewers listen for "before vs after paint" and the SSR warning. A subtle senior point: because useLayoutEffect is synchronous and blocking, it can starve React's concurrent rendering and cause jank if misused. If your only reason is "it feels more reliable," that's the junior answer — reliability isn't the difference, paint timing is.

Q9. How do you correctly clean up subscriptions, timers, and listeners?

ROI: ★★★★ Frequency: High

Short Answer

Return a cleanup function from useEffect that reverses whatever the effect set up: clear the timer, remove the listener, unsubscribe, close the socket, or abort the request. React runs it before each re-run and on unmount. Every effect that creates an ongoing resource must have a matching cleanup, or you leak.

Detailed Answer

The mental checklist: "what does this effect start, and how do I stop exactly that instance?" The cleanup closes over the specific resource from that render, so it always tears down the right one. Common pairs:

  • addEventListener ↔ removeEventListener (same function reference!)
  • setInterval/setTimeout ↔ clearInterval/clearTimeout
  • subscribe() ↔ the returned unsubscribe()
  • new WebSocket ↔ socket.close()
  • fetch ↔ AbortController.abort()

A subtle listener bug: passing an inline arrow to both add and remove removes nothing, because they're different function references. Define the handler once.

Code Example

useEffect(() => {
  const onResize = () => setWidth(window.innerWidth); // one stable reference
  window.addEventListener("resize", onResize);
  const id = setInterval(tick, 1000);

  return () => {
    window.removeEventListener("resize", onResize); // same ref -> actually removed
    clearInterval(id);
  };
}, []);

Senior Engineer Perspective

Interviewers may hand you code with a memory leak and ask you to spot it. The two classic ones: no cleanup at all (listener accumulates on every mount), and add/remove with different function references. Tie this back to StrictMode (Q7): a correct cleanup is exactly what makes an effect survive the dev double-invoke.

SECTION 3 - MEMOIZATION HOOKS

Q10. useMemo vs useCallback — what's the difference and when do they actually help?

ROI: ★★★★★ Frequency: Extremely High

Short Answer

useMemo caches the result of a computation; useCallback caches a function definition. In fact useCallback(fn, deps) is just useMemo(() => fn, deps). Both recompute only when their dependencies change. They genuinely help in two cases: skipping an expensive calculation, and preserving a stable reference so a memoized child (React.memo) or a dependency array doesn't see a "change" every render. Everywhere else they add cost, not value.

Detailed Answer

When useMemo helps

  • The computation is genuinely expensive (sorting/filtering thousands of rows, heavy transforms).
  • The result is an object/array passed as a prop to a React.memo child, or used in a dependency array — you need referential stability.

When useCallback helps

  • The function is passed to a React.memo child that would otherwise re-render on every parent render.
  • The function is a dependency of another hook (useEffect/useMemo) and must stay stable to avoid re-running it.

When they DON'T help (and hurt)

Memoizing a trivial calculation, or memoizing a callback passed to a plain (non-memoized) child, buys nothing — the child re-renders anyway — while adding a closure, a deps array, and a cache slot. Memoization has real overhead; wrapping everything "just in case" makes code slower and noisier.

Code Example

// useMemo — skip expensive work + stable reference for a memoized child
const sortedRows = useMemo(
  () => [...rows].sort((a, b) => a.score - b.score),
  [rows]
);

// useCallback — stable handler so <Row> (React.memo) doesn't re-render
const handleSelect = useCallback((id: string) => {
  setSelected(id);
}, []); // no deps -> identity never changes

const Row = React.memo(function Row({ onSelect }: RowProps) {
  return <button onClick={() => onSelect(row.id)} />;
});

// POINTLESS — child isn't memoized, so it re-renders regardless
const noop = useCallback(() => {}, []); // just overhead here

Project Example

A virtualized table rendered 10k memoized rows. Every keystroke in an unrelated search box re-rendered all rows because the row's onClick was a fresh closure. Wrapping the handler in useCallback and the row in React.memo cut re-renders to just the changed rows. But we only did it after profiling proved the cost — not preemptively.

Senior Engineer Perspective

The senior differentiator is knowing that both hooks are useless without the corresponding React.memo boundary or dependency-array consumer — a memoized callback handed to a non-memoized child does nothing. Also expect: "The React Compiler (React 19) auto-memoizes — does that make these obsolete?" Largely yes for hand-written cases, but you should still understand referential equality because the compiler's whole job is automating it, and legacy code is everywhere. Never claim "useMemo makes it faster" as a blanket truth.

Q11. What does referential equality have to do with re-renders?

ROI: ★★★★ Frequency: High

Short Answer

React compares props and dependencies with Object.is (reference equality for objects). Objects, arrays, and functions created during render are brand-new references every time, even if their contents are identical. That fresh identity is why React.memo children re-render, why useEffect deps "change" unexpectedly, and why memoization exists — to preserve a stable reference across renders.

Detailed Answer

Primitives (string, number, boolean) compare by value, so "open" === "open" is stable across renders for free. But {} !== {} and () => {} !== () => {}. Three places this bites you:

  • React.memo does a shallow prop compare; a new object/function prop defeats it.
  • Dependency arrays re-fire effects/memos when a reference changes (the infinite-loop cause from Q6).
  • Context value — a new provider value object re-renders all consumers (Q12).

Practical guidance: depend on primitives where possible (list [status] not [filters]), and only memoize the references you actually pass across a memo boundary or into a deps array.

Code Example

function Parent({ query }: { query: string }) {
  // New object EVERY render — defeats React.memo on Child
  const style = { padding: 8 };

  // Stable across renders unless `query` changes
  const params = useMemo(() => ({ q: query, page: 1 }), [query]);

  return <Child style={style} params={params} />;
}

Senior Engineer Perspective

This underlies most "why is this re-rendering / looping" questions. The strongest answers reframe the fix as "depend on primitives" rather than "memoize harder" — memoization is a patch over a reference-identity problem, and sometimes the cleaner fix is to not create the object in render at all. Knowing it's Object.is (not ===, which differs for NaN and -0) is a nice precision point.

SECTION 4 - useRef, useContext & useReducer

Q12. What is useRef for beyond accessing the DOM?

ROI: ★★★★★ Frequency: Extremely High

Short Answer

useRef gives you a mutable container — { current: value } — that persists across renders and, crucially, does not trigger a re-render when you change it. Two uses: (1) attaching to a DOM node via the ref attribute, and (2) storing any mutable instance value you want to survive renders without being render output — timer IDs, previous values, the latest state for a stale-closure fix, or a "has this run" flag.

Detailed Answer

The defining property: mutating ref.current is invisible to React's render cycle. Use state when a value should appear on screen and cause a re-render; use a ref when a value is bookkeeping the render doesn't need.

 useStateuseRef
Triggers re-render on change?YesNo
Value persists across renders?YesYes
Read during render?Yes, safelyAvoid — mutation during render is impure
Use forAnything shown in UIDOM nodes, timers, previous values, flags

Because writing a ref doesn't re-render, don't read a ref during rendering to produce output — the UI won't update when it changes. Read/write refs in effects and event handlers.

Code Example

// 1) DOM access — focus an input on mount
function SearchBox() {
  const inputRef = useRef<HTMLInputElement>(null);
  useEffect(() => { inputRef.current?.focus(); }, []);
  return <input ref={inputRef} />;
}

// 2) Mutable instance value — store a timer id (no re-render needed)
function Stopwatch() {
  const timerRef = useRef<number | null>(null);
  const start = () => {
    timerRef.current = window.setInterval(tick, 1000);
  };
  const stop = () => {
    if (timerRef.current) clearInterval(timerRef.current);
  };
  // ...
}

// 3) Previous value pattern
function usePrevious<T>(value: T) {
  const ref = useRef<T>();
  useEffect(() => { ref.current = value; });
  return ref.current; // last render's value
}

Senior Engineer Perspective

The line to say: "state is for what you render; refs are for what you remember." A common trap is candidates using refs to avoid re-renders for values that should be visible — that just breaks the UI. Expect the follow-up on forwardRef/useImperativeHandle for exposing a child's imperative API (though React 19 lets you pass ref as a normal prop, softening forwardRef). Also note initializing a ref lazily with an expensive object should be guarded (if (!ref.current) ref.current = ...) since useRef has no lazy-init form.

Q13. How does useContext work, and what are its re-render pitfalls?

ROI: ★★★★★ Frequency: Extremely High

Short Answer

useContext reads the nearest matching Provider's value and subscribes the component to it. When the provider's value changes (by Object.is), every consumer re-renders — there's no partial subscription. The main pitfalls: passing a fresh object as value every render (re-renders all consumers constantly), and putting too much unrelated state in one context so unrelated updates cascade.

Detailed Answer

Context is a dependency-injection / broadcast mechanism, not a state manager and not a performance optimization. Key behaviors:

  • Consumers re-render when the provider value's reference changes — regardless of whether they use the part that changed.
  • React.memo does not stop a re-render caused by context; the consumer subscribes directly.
  • Providing an inline object (value={{ user, setUser }}) creates a new reference every render, so wrap it in useMemo.

Mitigations for the "everything re-renders" problem: memoize the value; split into multiple contexts (a stable-dispatch context + a value context is a common pattern, since dispatch never changes); or reach for a library (Redux Toolkit, Zustand, Jotai) that supports selector-based subscriptions when the state is large and hot.

Code Example

const AuthContext = createContext<AuthValue | null>(null);

function AuthProvider({ children }: { children: React.ReactNode }) {
  const [user, setUser] = useState<User | null>(null);

  // Memoize so consumers don't re-render on unrelated parent renders
  const value = useMemo(() => ({ user, setUser }), [user]);

  return <AuthContext.Provider value={value}>{children}</AuthContext.Provider>;
}

function useAuth() {
  const ctx = useContext(AuthContext);
  if (!ctx) throw new Error("useAuth must be used within AuthProvider");
  return ctx;
}

Project Example

A theme + auth + locale mega-context re-rendered the entire app on every auth token refresh. Splitting it into separate contexts (and memoizing each value) meant a token refresh only touched components reading auth, cutting render churn dramatically.

Senior Engineer Perspective

The trap answer is "use context to avoid prop drilling and for global state" without acknowledging the all-consumers-re-render cost. Seniors say context is great for low-frequency, widely-read values (theme, current user, locale) but poor for high-frequency state (form fields, cursor position) — that's where selector-based stores win. Bonus: useContext does not support selectors natively, which is precisely the gap external state libraries fill.

Q14. useReducer vs useState — when do you switch?

ROI: ★★★★ Frequency: High

Short Answer

Use useState for independent, simple values. Switch to useReducer when state is complex or when the next state depends on the previous one through many related transitions — multiple sub-values that update together, or state whose updates follow clear "actions". A reducer centralizes update logic in one pure function, making transitions testable and predictable, and the dispatch reference is stable so it's cheap to pass down.

Detailed Answer

Signals it's time to reach for useReducer:

  • Several pieces of state change together in response to one event (e.g., a fetch: set loading, clear error, then set data or error).
  • Update logic is branching and spread across many handlers — a reducer pulls it into one place.
  • You want to log/replay/test transitions, or the next state is a function of the current one in non-trivial ways.

dispatch is guaranteed stable across renders, so passing it through context or to memoized children never causes re-renders — a real advantage over passing many setX functions. The reducer must be a pure function of (state, action).

Code Example

type State = { status: "idle" | "loading" | "done" | "error"; data?: User; error?: string };
type Action =
  | { type: "FETCH" }
  | { type: "SUCCESS"; data: User }
  | { type: "FAILURE"; error: string };

function reducer(state: State, action: Action): State {
  switch (action.type) {
    case "FETCH":   return { status: "loading" };
    case "SUCCESS": return { status: "done", data: action.data };
    case "FAILURE": return { status: "error", error: action.error };
    default:        return state;
  }
}

function UserCard({ id }: { id: string }) {
  const [state, dispatch] = useReducer(reducer, { status: "idle" });

  useEffect(() => {
    dispatch({ type: "FETCH" });
    fetchUser(id)
      .then(data => dispatch({ type: "SUCCESS", data }))
      .catch(e => dispatch({ type: "FAILURE", error: String(e) }));
  }, [id]);
  // render based on state.status
}

Senior Engineer Perspective

Don't say "useReducer is for large state" — the real criterion is how state changes (coordinated transitions / action semantics), not size. A single boolean toggled many ways can justify a reducer; three unrelated values rarely do. Mention that reducer + context is the built-in "Redux-lite" pattern, and that dispatch's stable identity is an underrated performance and ergonomics win.

SECTION 5 - WHEN NOT TO USE useEffect

Q15. When should you NOT use useEffect?

ROI: ★★★★★ Frequency: Extremely High

Short Answer

Don't use an effect to transform data for rendering (compute it during render instead), to handle a user event (put that logic in the event handler), or to reset/adjust state based on props (derive it, or use a key to reset). Effects are for synchronizing with external systems. If no external system is involved, you probably don't need an effect.

Detailed Answer

1. Deriving state — just compute during render

Storing derived data in state and syncing it with an effect creates a redundant render and a source-of-truth split. Compute it inline (memoize only if expensive).

2. Responding to user events — use the handler

"When the user submits, send analytics and POST." That's caused by an event, not by rendering. Put it in onSubmit, not in an effect watching a flag. Effects run because the component rendered, which loses the "why did this happen" information.

3. Resetting state when a prop changes — use a key

To reset all state when, say, userId changes, render the component with key={userId}. React remounts it fresh — no effect that watches the prop and calls a pile of setters.

4. Data fetching — move to a query library (see Q16)

Code Example

// ANTI-PATTERN — deriving state in an effect (extra render, bug-prone)
const [fullName, setFullName] = useState("");
useEffect(() => { setFullName(first + " " + last); }, [first, last]);

// FIX — compute during render
const fullName = first + " " + last;

// ANTI-PATTERN — event logic hidden in an effect
useEffect(() => {
  if (submitted) sendAnalytics(); // why did this fire? unclear
}, [submitted]);

// FIX — do it where the event happens
function handleSubmit() {
  sendAnalytics();
  postForm();
}

Project Example

A form kept a filteredItems state synced from items + search via an effect. It double-rendered and occasionally showed stale results for one frame. Replacing it with a computed const filtered = items.filter(...) during render removed the bug and a whole state variable.

Senior Engineer Perspective

This question separates people who "reach for useEffect reflexively" from those who understand it. The mental test the React docs teach: "Is this caused by a particular event, or by the component simply being displayed/synchronized?" Event → handler. Display/external sync → effect. Deriving state in effects is the single most common React anti-pattern, and naming the key-reset trick signals real fluency.

Q16. How do you fetch data with hooks, and why is useEffect the wrong long-term home for it?

ROI: ★★★★★ Frequency: Extremely High

Short Answer

You can fetch in useEffect — with an AbortController, an ignore flag to drop stale responses, loading/error state, and re-fetch on dependency change. But doing it by hand means re-implementing caching, deduplication, retries, race-condition handling, and revalidation in every component. That's why production apps move fetching to a data library like TanStack Query (React Query) or SWR, or to server components / a router loader.

Detailed Answer

The problems with raw effect-based fetching:

  • Race conditions — a slow request for the old id can resolve after the new one; you need to ignore stale responses.
  • No caching or dedup — two components asking for the same data fire two requests.
  • No revalidation — stale-while-revalidate, refetch-on-focus, polling all become manual.
  • Waterfalls — fetching in child effects after parents mount serializes requests.

TanStack Query solves all of these with a cache keyed by queryKey, automatic dedup, background refetch, and built-in loading/error state. The enabled option cleanly handles conditional fetching (Q3). In app-router / RSC setups, fetching moves to the server (or a route loader) entirely, and effects aren't involved.

Code Example

// Hand-rolled — note the race-condition guard and cleanup
function useUser(id: string) {
  const [state, setState] = useState<{ loading: boolean; data?: User }>({ loading: true });

  useEffect(() => {
    let ignore = false;               // guard against stale responses
    const controller = new AbortController();
    setState({ loading: true });

    fetch(`/api/users/${id}`, { signal: controller.signal })
      .then(r => r.json())
      .then(data => { if (!ignore) setState({ loading: false, data }); });

    return () => { ignore = true; controller.abort(); };
  }, [id]);

  return state;
}

// Production — TanStack Query handles cache, dedup, retries, race conditions
function useUserQuery(id: string) {
  return useQuery({
    queryKey: ["user", id],
    queryFn: ({ signal }) => fetch(`/api/users/${id}`, { signal }).then(r => r.json()),
    enabled: !!id,
  });
}

Senior Engineer Perspective

Interviewers want to see you know the manual version's pitfalls (especially the race condition — this is the classic follow-up) and that you wouldn't ship it. Saying "I'd reach for TanStack Query / SWR, or fetch on the server with RSC / a router loader" shows current, production-grade judgment. The React docs themselves recommend against manual effect fetching for exactly these reasons. A red flag is defending hand-rolled fetching as "simpler" without mentioning caching, dedup, or races.

Q17. What's the difference between useEffect deps missing vs. an empty array vs. no array?

ROI: ★★★ Frequency: Medium

Short Answer

No array at all → the effect runs after every render. An empty array [] → runs only once on mount (cleanup on unmount). A populated array [a, b] → runs on mount and whenever a listed value changes. "Missing deps" usually means you have an array but left out a value the effect actually uses — that causes stale closures, and the exhaustive-deps lint rule flags it.

Detailed Answer

FormBehaviorTypical use
no arrayEvery renderRare; usually a bug
[]Mount only + unmount cleanupOne-time setup that reads nothing reactive
[a, b]Mount + when a or b changesSync with specific reactive values

The trap is using [] while the effect reads props/state — it "works" on mount but silently uses stale values forever (Q5). The lint rule exists to force you to either list every used reactive value or restructure (functional updater, ref, or move the value out). Don't blind-disable it; treat a warning as "you have a stale-closure or reference-identity issue to resolve."

Senior Engineer Perspective

The nuance seniors add: an empty array isn't "run once because I want it once" — it's a claim that the effect depends on nothing reactive. If that claim is false, you have a bug, not a shortcut. The right way to "run truly once with fresh values" is often a functional updater or a ref, not lying to the deps array.

Q18. How do you share stateful logic between components without duplication?

ROI: ★★★★ Frequency: High

Short Answer

Write a custom hook — a function named useSomething that calls other hooks and returns values. It lets you reuse logic (subscriptions, form handling, fetching) without sharing state: each component that calls the hook gets its own independent state. Custom hooks replaced the old render-props and higher-order-component patterns for logic reuse.

Detailed Answer

A custom hook is just a function that (a) starts with use so the linter enforces the Rules of Hooks inside it, and (b) uses one or more built-in hooks. Crucially, extracting logic into a hook does not share state between callers — every call site gets a fresh, isolated instance of that hook's state. What's shared is the behavior, not the data.

Good custom-hook candidates: useLocalStorage, useDebounce, useMediaQuery, useOnlineStatus, form logic, and wrappers around a data layer. Keep them focused and return a stable, ergonomic API.

Code Example

function useDebounce<T>(value: T, delay = 300): T {
  const [debounced, setDebounced] = useState(value);

  useEffect(() => {
    const id = setTimeout(() => setDebounced(value), delay);
    return () => clearTimeout(id); // cancel on change/unmount
  }, [value, delay]);

  return debounced;
}

// Each component gets its OWN debounced state — logic shared, state isolated
function Search() {
  const [text, setText] = useState("");
  const debounced = useDebounce(text, 400);
  useEffect(() => { if (debounced) runSearch(debounced); }, [debounced]);
  return <input value={text} onChange={e => setText(e.target.value)} />;
}

Senior Engineer Perspective

The most common misconception is that a custom hook shares state across components — it doesn't; it shares logic, and each caller has independent state. If you need shared state, that's context or an external store, not a plain custom hook. Interviewers also probe naming: the use prefix isn't cosmetic — it's what lets the linter and React apply the Rules of Hooks. Mentioning that custom hooks superseded HOCs/render props for cross-cutting logic dates your knowledge to modern React.

SECTION 6 - ADVANCED useEffect PATTERNS & PITFALLS

Q19. Can the function you pass to useEffect be async? Why not directly, and how do you handle async work inside an effect?

ROI: ★★★★★ Frequency: Extremely High

Short Answer

No — useEffect requires its callback to return either nothing or a cleanup function. An async function always returns a Promise, so React would try to treat that Promise as a cleanup value, which is both meaningless and triggers a dev warning. Instead, define an async function inside the effect and call it immediately, keeping the outer callback itself synchronous.

Detailed Answer

This trips people up because it "looks like it should work" — useEffect(async () => { await fetch(...) }, []) runs, the fetch happens, but React logs "Warning: useEffect must not return anything besides a function, which is used for clean-up. You returned a Promise." The real cleanup function you may have wanted never gets registered, which silently breaks any teardown behavior.

The fix keeps the effect's own contract intact: declare an inner async function, invoke it, and return the synchronous cleanup separately. Combine it with a stale-response guard (an ignore flag or AbortController) exactly as in the manual fetching pattern from Q16, since async work inside an effect is almost always a network call subject to race conditions.

Code Example

// WRONG — the outer callback itself is async, so it returns a Promise
useEffect(async () => {
  const res = await fetch(`/api/users/${id}`);
  setUser(await res.json());
}, [id]); // ⚠️ "useEffect must not return anything besides a function"

// RIGHT — inner async function, outer callback stays synchronous
useEffect(() => {
  let ignore = false;

  async function load() {
    const res = await fetch(`/api/users/${id}`);
    const data = await res.json();
    if (!ignore) setUser(data); // guard against a stale response
  }

  load();
  return () => { ignore = true; }; // synchronous cleanup, as React expects
}, [id]);

Senior Engineer Perspective

Interviewers use this to check you actually understand the effect's return-value contract rather than pattern-matching "effects do async stuff." Tie it back to Q16: the inner-async-function pattern is exactly the shape you'd hand-roll before reaching for a data-fetching library, and the ignore/AbortController guard is what makes it safe under StrictMode's double-invoke (Q7).

Q20. What order do multiple useEffect calls run in within one component, and what order do their cleanups run in?

ROI: ★★★★ Frequency: High

Short Answer

Within a single component, sibling effects run in the exact order they're declared — top to bottom — both for the effects themselves and for their cleanups. This is different from a "stack unwind" you might expect from other languages: React does not reverse the order for a single component's own effects. Across the component tree, though, cleanup does cascade bottom-up — a child's effects clean up before its parent's when a subtree unmounts.

Detailed Answer

Because hooks are stored as an ordered linked list per fiber (Q1), React simply walks that list in order twice per commit conceptually: once to run cleanups for effects whose deps changed (in declared order), then again to run the new effects (also in declared order). So if a component declares useEffect A then useEffect B, an update runs: cleanup A → cleanup B → effect A → effect B.

The tree-level behavior is different: when a parent unmounts, React tears down the subtree depth-first, so a child's cleanup functions run before the parent's — mirroring how a child is logically "still alive" while its parent is unmounting around it.

Code Example

function Widget({ id }) {
  useEffect(() => {
    console.log("effect A", id);
    return () => console.log("cleanup A", id);
  }, [id]);

  useEffect(() => {
    console.log("effect B", id);
    return () => console.log("cleanup B", id);
  }, [id]);
}
// Update id: "cleanup A" -> "cleanup B" -> "effect A" -> "effect B"
// (declared order preserved both times — not reversed)

Senior Engineer Perspective

A lot of engineers assume cleanup order mirrors LIFO stack unwinding purely by analogy to other lifecycle systems — being able to say "no, sibling effects preserve declared order" while also knowing the tree-level unmount is bottom-up shows you've actually read the reconciler's behavior, not just guessed from experience.

Q21. How do you run an effect only after the first render — skipping the initial mount?

ROI: ★★★ Frequency: Medium

Short Answer

There's no built-in "skip on mount" option. The common workaround is a ref flag that starts true, flips to false the first time the effect runs, and returns early on that first pass — so the effect body only does real work from the second run onward.

Detailed Answer

This need usually comes from wanting to react to a value changing (e.g., show a toast when filters change) without firing that reaction on the initial mount too. It's a legitimate but narrow escape hatch — the React docs themselves note this as one of the rare valid ref-in-render-adjacent uses, precisely because it's bookkeeping about renders, not something that should appear in the UI.

Code Example

function FilterPanel({ filters }) {
  const isFirstRender = useRef(true);

  useEffect(() => {
    if (isFirstRender.current) {
      isFirstRender.current = false;
      return; // skip the mount-time run
    }
    showToast(`Filters updated: ${summarize(filters)}`);
  }, [filters]);
  // ...
}

Senior Engineer Perspective

Flag this pattern honestly as fighting the framework a little. Often a cleaner fix is to move the toast into the event handler that actually changes the filters (Q15's "is this caused by an event?" test) rather than inferring "this was a change, not the initial value" from inside an effect.

Q22. How do you debounce a side effect using useEffect and its cleanup function, without a library?

ROI: ★★★★ Frequency: High

Short Answer

Start a timer inside the effect and clear it in the cleanup. Because cleanup runs before every re-run of the effect (Q4), each new keystroke cancels whatever timer the previous keystroke started — that cleanup/re-run cycle is debouncing, for free, with no extra library.

Detailed Answer

This is the mechanism behind the useDebounce custom hook from Q18, just written inline instead of extracted. Note that this pattern naturally produces debouncing (wait for a pause in changes), not throttling (guarantee at most once per interval) — throttling needs a ref that tracks "last time fired" and compares against it, since there's no cleanup-driven cancellation involved.

Code Example

function SearchBox() {
  const [text, setText] = useState("");

  useEffect(() => {
    const id = setTimeout(() => {
      if (text) runSearch(text);
    }, 400);
    return () => clearTimeout(id); // cancels the PREVIOUS pending search
  }, [text]);

  return <input value={text} onChange={e => setText(e.target.value)} />;
}

Senior Engineer Perspective

Interviewers like this because it tests whether "cleanup runs before the next effect" (Q4) is a working mental model for you, not just a memorized fact — debouncing is a direct, elegant consequence of it. Contrast with throttling to show you know these aren't the same thing.

Q23. What happens if an effect returns something other than a function or undefined?

ROI: ★★★ Frequency: Medium

Short Answer

React expects an effect to return either nothing (undefined) or a cleanup function. Returning anything else — an object, a value, or a Promise (the async-effect mistake from Q19) — triggers a development warning telling you the return value isn't a valid cleanup, and no real cleanup runs.

Detailed Answer

In production builds this is silently ignored rather than crashing, which is exactly why it's dangerous — a bug like this can ship unnoticed if you only look at the console in a build where warnings are stripped. Always keep effect bodies explicit: end them with either nothing, or a clearly-named cleanup function.

Code Example

// BUG — accidentally returns the fetch's Promise
useEffect(() => {
  return fetch("/api/ping"); // ⚠️ not a valid cleanup value
}, []);

// FIX — don't return the async call's result at all
useEffect(() => {
  fetch("/api/ping");
}, []);

Senior Engineer Perspective

A sharp answer connects this straight back to Q19's async pitfall — both are instances of "the effect's return value isn't what I meant it to be." Naming the dev-only warning and the production silent-ignore behavior shows you've actually seen this in a console, not just read about it.

Q24. How do you depend on an object's actual content rather than its reference, without disabling exhaustive-deps?

ROI: ★★★★ Frequency: High

Short Answer

Prefer restructuring first: depend on the specific primitive fields you actually use, or a derived string (like JSON.stringify of the relevant subset) instead of the whole object. Only reach for a deep-compare custom hook as a last resort when you truly don't control the object's shape — it's an O(n) comparison on every render and a workaround, not a fix for the underlying reference-identity problem from Q11.

Detailed Answer

The cleanest fix is almost always "depend on primitives" — list [filters.status, filters.page] instead of [filters]. When the object truly is opaque (e.g., handed to you by a third-party library that recreates it every call), a small "stabilize by content" hook can hold the last logically-equal value behind a ref, only updating the reference when a comparison says the content actually changed.

Code Example

// PREFERRED — depend on the primitives you actually use
useEffect(() => {
  fetchTasks({ status: filters.status, page: filters.page });
}, [filters.status, filters.page]);

// LAST RESORT — stabilize an opaque object by content
function useStableValue<T>(value: T, isEqual: (a: T, b: T) => boolean): T {
  const ref = useRef(value);
  if (!isEqual(ref.current, value)) ref.current = value;
  return ref.current;
}

const stableFilters = useStableValue(filters, (a, b) => JSON.stringify(a) === JSON.stringify(b));
useEffect(() => { fetchTasks(stableFilters); }, [stableFilters]);

Senior Engineer Perspective

The trap is reaching for a deep-compare hook as the first move. Senior engineers reach for it last, after confirming they genuinely can't restructure the dependency to a primitive — and they say so out loud, because it signals awareness of the real cost (a full comparison every render) rather than treating it as a free fix.

Q25. Does a slow useEffect delay what the user sees on screen? Explain effect timing relative to paint.

ROI: ★★★★ Frequency: High

Short Answer

No — useEffect callbacks are scheduled to run after the browser has already painted the committed DOM changes, so a slow effect doesn't delay what the user visually sees. It can still delay subsequent interactions, though, because it executes on the same main JS thread and blocks further work until it finishes.

Detailed Answer

This is precisely the opposite of useLayoutEffect (Q8), which runs synchronously before paint and therefore does block the visual update. Passive effects (useEffect) are deferred slightly so the browser gets a chance to paint first — this is what makes them safe for expensive, non-visual work like logging or fetching without introducing visible lag, while still running soon enough that users perceive it as "immediate."

Code Example

useEffect(() => {
  // This runs AFTER the browser has painted the current commit,
  // so a slow computation here won't delay the visible update —
  // it will delay how soon the NEXT interaction gets handled.
  const start = performance.now();
  heavyAnalyticsComputation();
  console.log("effect took", performance.now() - start, "ms — after paint");
});

Senior Engineer Perspective

Interviewers use this to see if you can precisely place useEffect on a timeline relative to commit and paint, not just recite "it runs after render." Pairing it with Q8's layout-effect contrast in the same answer is what separates a memorized fact from an understood model.

Q26. Is it ever safe to intentionally omit a dependency from useEffect's array without lying to the linter?

ROI: ★★★★ Frequency: High

Short Answer

Yes — React guarantees that set functions from useState and dispatch from useReducer have a stable identity for the lifetime of the component, so it's genuinely safe to omit them from a dependency array; the linter itself special-cases this and won't warn. Anything else you omit is a real risk of a stale closure (Q5), not a safe exception.

Detailed Answer

The exhaustive-deps rule is a static analysis (Q81 goes deeper on this) that flags every closed-over reactive identifier — but it knows, as a built-in exception, that setters and dispatchers never change, so listing them is optional and purely stylistic. Beyond that carve-out, the rule is a reliable signal: if it says a value is missing, that value genuinely can change between renders and your effect is reading a stale copy of it if you don't list it.

Code Example

function Counter() {
  const [count, setCount] = useState(0);

  useEffect(() => {
    const id = setInterval(() => setCount(c => c + 1), 1000);
    return () => clearInterval(id);
  }, []); // ✅ setCount omitted safely — its identity never changes
}

Senior Engineer Perspective

The failure mode here is candidates generalizing "setters are safe to omit" into "I can omit whatever I judge to be safe," which is exactly the reasoning that produces stale closures. Keep the exception narrow and named: setters and dispatch, nothing else, ever.

SECTION 7 - useLayoutEffect vs useEffect DEEP DIVE

Q27. Give a concrete example where a naive useEffect causes a visible flash of incorrect content, and show how useLayoutEffect fixes it.

ROI: ★★★★★ Frequency: Extremely High

Short Answer

A tooltip that measures its own height to decide whether to render above or below its trigger is the classic case. If that measurement and the resulting position update happen in useEffect, the browser has already painted the tooltip in its default (wrong) position for one frame before the effect corrects it — a visible flicker. Doing the same measurement in useLayoutEffect runs before paint, so the corrected position is what the user sees from the first frame.

Detailed Answer

The failure mode is subtle because it "looks fine" in a fast dev environment — the flicker is a single frame and easy to miss unless you're specifically looking for it or testing on a throttled device. It becomes very visible for anything measuring layout to decide how to render: tooltips flipping direction, "read more" truncation based on measured text height, or auto-sizing a textarea to its content.

Code Example

// FLICKERS — user briefly sees the un-flipped position
function Tooltip({ targetRect }) {
  const ref = useRef(null);
  const [flipUp, setFlipUp] = useState(false);

  useEffect(() => { // runs AFTER paint — one visible wrong frame
    const { height } = ref.current.getBoundingClientRect();
    setFlipUp(targetRect.bottom + height > window.innerHeight);
  }, [targetRect]);

  return <div ref={ref} className={flipUp ? "above" : "below"} />;
}

// NO FLICKER — corrected before the browser ever paints
function Tooltip({ targetRect }) {
  const ref = useRef(null);
  const [flipUp, setFlipUp] = useState(false);

  useLayoutEffect(() => { // runs BEFORE paint
    const { height } = ref.current.getBoundingClientRect();
    setFlipUp(targetRect.bottom + height > window.innerHeight);
  }, [targetRect]);

  return <div ref={ref} className={flipUp ? "above" : "below"} />;
}

Senior Engineer Perspective

Interviewers want a real, specific scenario — not just "useLayoutEffect avoids flicker" as an abstract slogan. Naming the exact measure-then-adjust mechanics (get layout, compute a decision, synchronously re-render before paint) proves you understand why the timing difference matters, not just that it exists.

Q28. Why is overusing useLayoutEffect dangerous for performance, and how would you detect it's happening?

ROI: ★★★★ Frequency: High

Short Answer

Because it's synchronous and blocking — the browser cannot paint until every useLayoutEffect in the commit finishes. Heavy computation there directly delays the next frame, causing visible jank, unlike passive effects which never block paint. You'd detect it via React DevTools Profiler's flame graph (time attributed to layout effects) or the browser's performance panel showing a long task right before a paint.

Detailed Answer

This matters more as an app scales: one expensive layout effect is rarely noticeable, but several components each doing "just one more measurement" in useLayoutEffect compounds into a real, measurable delay before the frame renders. The fix is almost always to ask "does this specific piece of work need to happen before paint," and move anything that doesn't back to useEffect.

Senior Engineer Perspective

A senior answer references concrete tooling (Profiler flame graph, Performance panel long tasks) rather than a vague "it can be slow." Being able to point at where in DevTools this shows up demonstrates you've actually diagnosed this class of bug, not just read about it.

Q29. How do you write an SSR-safe layout effect — the useIsomorphicLayoutEffect pattern?

ROI: ★★★★ Frequency: High

Short Answer

On the server there's no DOM, so useLayoutEffect logs a warning ("useLayoutEffect does nothing on the server"). Libraries like Redux and Framer Motion work around this with a tiny wrapper hook that uses useLayoutEffect in the browser and falls back to useEffect during server rendering, checked via typeof window.

Detailed Answer

The check has to happen once, outside any component (at module scope), since hooks can't be called conditionally per-render (Q1) — you're choosing which hook function the alias points to, not branching inside a hook call.

Code Example

const useIsomorphicLayoutEffect =
  typeof window !== "undefined" ? useLayoutEffect : useEffect;

function Measured() {
  const ref = useRef(null);

Q30. How would you implement an auto-scroll-to-bottom chat window, and why does it need useLayoutEffect rather than useEffect?

ROI: ★★★★ Frequency: High

Short Answer

After a new message is appended to the DOM, you must set scrollTop before the browser paints, or the user briefly sees the old scroll position (the previous bottom) before it jumps — a visible stutter. useLayoutEffect runs synchronously right after the DOM mutation and before paint, so the scroll adjustment is invisible.

Code Example

function ChatWindow({ messages }) {
  const listRef = useRef(null);

  useLayoutEffect(() => {
    const el = listRef.current;
    if (el) el.scrollTop = el.scrollHeight; // before paint — no visible jump
  }, [messages]);

  return (
    <div ref={listRef} className="chat-list">
      {messages.map(m => <Message key={m.id} {...m} />)}
    </div>
  );
}

Senior Engineer Perspective

A common gap: candidates get the scrolling logic right but reach for useEffect by habit, missing the actual point of the question. Naming the visible-jump failure mode unprompted is what shows you understand the timing distinction, not just the scrolling API.

Q31. requestAnimationFrame vs useLayoutEffect for animations — which do you reach for, and why?

ROI: ★★★★ Frequency: High

Short Answer

useLayoutEffect fires once per commit, tied to a specific render's output — right for a one-time synchronous measure-and-adjust. requestAnimationFrame fires once per display frame independent of React commits, throttled to the refresh rate — right for a continuous animation loop. A common combination: measure in useLayoutEffect, then drive the ongoing animation with an rAF loop, cancelling it in cleanup.

Code Example

function Marquee({ text }) {
  const ref = useRef(null);
  const posRef = useRef(0);

  useEffect(() => {
    let frameId;
    const tick = () => {
      posRef.current -= 1;
      if (ref.current) ref.current.style.transform = `translateX(${posRef.current}px)`;
      frameId = requestAnimationFrame(tick); // per-frame, not per-commit
    };
    frameId = requestAnimationFrame(tick);
    return () => cancelAnimationFrame(frameId);
  }, []);

  return <div ref={ref}>{text}</div>;
}

Senior Engineer Perspective

The distinction to land: one is "per render commit," the other is "per display frame." Confusing the two leads to either janky animations (trying to animate via re-renders and layout effects) or wasted synchronous work (trying to use useLayoutEffect as an animation loop).

Q33. "I'll just use useLayoutEffect everywhere to be safe" — why is this the wrong instinct?

SECTION 8 - useReducer PATTERNS

Q34. How do you lazily initialize a reducer's state using useReducer's third argument, and why would you?

ROI: ★★★★ Frequency: High

Short Answer

useReducer(reducer, initialArg, init) — when a third argument is supplied, React calls init(initialArg) exactly once, on mount, and uses its result as the starting state, mirroring lazy useState initialization. It's useful for expensive initial computations (parsing localStorage, building a default from props) and, notably, lets a "RESET" action reuse the very same init function to recompute a fresh default.

Code Example

function init(initialCount) {
  return { count: initialCount, history: [] };
}

function reducer(state, action) {
  switch (action.type) {
    case "increment": return { count: state.count + 1, history: [...state.history, state.count] };
    case "reset":      return init(action.initialCount); // reuse the initializer
    default:           return state;
  }
}

function Counter({ startAt }) {
  const [state, dispatch] = useReducer(reducer, startAt, init);
  // ...
}

Senior Engineer Perspective

The "reuse init for RESET" trick is the detail that separates a memorized signature from real usage — it's the reducer equivalent of not duplicating your default-state logic in two places.

Q35. How do you build a "mini-Redux" with useReducer + useContext, and what are its real limitations vs actual Redux?

ROI: ★★★★★ Frequency: Extremely High

Short Answer

Create a state context and a separate dispatch context, wire a single useReducer in a Provider component, and expose useAppState/useAppDispatch custom hooks. It gives you centralized, action-based state without a library — but it lacks Redux's middleware ecosystem (thunks/sagas for async orchestration), built-in DevTools time-travel debugging, and — critically — selector-based fine-grained subscriptions, so every consumer of the state context re-renders on any change unless you split contexts further.

Detailed Answer

Splitting state and dispatch into two contexts (Q41 explains why) means components that only dispatch never re-render when state changes. What you don't get for free is what Redux's connect/selectors or a library like Zustand give you: subscribing to a slice of state so unrelated updates don't re-render you. For a small-to-medium app this pattern is often enough; for large, hot, frequently-updated global state, a real store with selectors usually wins.

Code Example

const StateContext = createContext(null);
const DispatchContext = createContext(null);

function AppProvider({ children }) {
  const [state, dispatch] = useReducer(reducer, initialState);
  return (
    <StateContext.Provider value={state}>
      <DispatchContext.Provider value={dispatch}> {/* dispatch is stable — see Q41 */}
        {children}
      </DispatchContext.Provider>
    </StateContext.Provider>
  );
}

function useAppState() { return useContext(StateContext); }
function useAppDispatch() { return useContext(DispatchContext); }

Senior Engineer Perspective

The strongest answers name the specific gaps (no selectors, no middleware, no devtools) rather than treating this as a drop-in Redux replacement. That precision is what interviewers are actually listening for — "I know what this pattern buys me and what it doesn't."

Q36. Why doesn't dispatching trigger a re-render if the reducer returns the same state reference?

ROI: ★★★★★ Frequency: Extremely High

Short Answer

React bails out of re-rendering when the new state is Object.is-equal to the previous state — the same optimization useState uses. A common bug: a reducer case that mutates in place (state.items.push(x)) and returns the same object — React sees an unchanged reference and skips the render even though the array's contents actually changed.

Code Example

// BUG — mutates and returns the SAME reference; React bails out, UI never updates
case "ADD_ITEM":
  state.items.push(action.item);
  return state;

// FIX — return a new object/array reference
case "ADD_ITEM":
  return { ...state, items: [...state.items, action.item] };

Senior Engineer Perspective

This is a favorite "spot the bug" prompt precisely because it looks correct at a glance — the data really did change. Naming the exact mechanism (Object.is bail-out on the reducer's return value, not on the array's contents) is what shows real understanding versus "I guess React didn't notice."

Q37. How do you compose multiple reducers for different state slices, similar to Redux's combineReducers?

ROI: ★★★ Frequency: Medium

Short Answer

If the slices are truly independent, just use multiple useReducer calls side by side. When you want one dispatch and one combined shape (mirroring Redux's root reducer), write a small helper that runs each slice reducer against its own piece of state and rebuilds the combined object.

Code Example

function combineReducers(slices) {
  return (state, action) =>
    Object.fromEntries(
      Object.entries(slices).map(([key, reducer]) => [key, reducer(state[key], action)])
    );
}

const rootReducer = combineReducers({ user: userReducer, cart: cartReducer });
const [state, dispatch] = useReducer(rootReducer, { user: initialUser, cart: initialCart });

Senior Engineer Perspective

Being able to write this helper from first principles (rather than just naming "combineReducers exists in Redux") demonstrates you understand a reducer is just a plain function — nothing about it is special to Redux or to useReducer specifically.

Q38. How would you unit test a reducer function in isolation, and why is that better than testing it only through a rendered component?

ROI: ★★★★ Frequency: High

Short Answer

A reducer is a pure function of (state, action) => state — call it directly with a starting state and an action, and assert on the returned state. No rendering, no act(), no DOM, which makes it fast and lets you exhaustively cover every action/branch without wiring up a whole component tree.

Code Example

test("ADD_ITEM appends without mutating the original state", () => {
  const initial = { items: [{ id: 1 }] };
  const next = reducer(initial, { type: "ADD_ITEM", item: { id: 2 } });

  expect(next.items).toHaveLength(2);
  expect(initial.items).toHaveLength(1); // original untouched
  expect(next).not.toBe(initial);        // new reference, per Q36
});

Senior Engineer Perspective

Testing the reducer directly and asserting the original state object wasn't mutated is a nice two-for-one: it verifies the transition logic and guards against the exact Q36 mutation bug regressing later.

Q39. How do you keep reducer updates immutable without hand-writing spreads everywhere, using Immer?

ROI: ★★★★ Frequency: High

Short Answer

Wrap your reducer with Immer's produce, which lets you write code that looks mutating against a "draft" proxy, while Immer converts it into a properly immutable update with structural sharing behind the scenes. This removes the whole class of Q36-style bugs, since you no longer hand-write spreads that are easy to get wrong at nested depths.

Code Example

import { produce } from "immer";

const reducer = produce((draft, action) => {
  switch (action.type) {
    case "ADD_ITEM":
      draft.items.push(action.item); // looks mutating — Immer makes it immutable
      break;
    case "TOGGLE_DONE":
      draft.items[action.index].done = !draft.items[action.index].done;
      break;
  }
});

const [state, dispatch] = useReducer(reducer, initialState);

Senior Engineer Perspective

Being able to explain why this is safe (structural sharing via a Proxy, not actual mutation of your real state object) rather than just "Immer handles it" is the difference between using a library and understanding it — useful when someone asks "so it really does mutate under the hood, right?" (no, it doesn't touch the original).

Q40. How do you add logging middleware around a plain useReducer's dispatch, without a library?

ROI: ★★★ Frequency: Medium

Short Answer

Wrap the dispatch function returned by useReducer in your own function that logs the action before forwarding it, memoized with useCallback so its identity stays stable for consumers that depend on it.

Code Example

const [state, dispatch] = useReducer(reducer, initialState);

const loggedDispatch = useCallback((action) => {
  console.log("dispatch:", action, "prev state:", state);
  dispatch(action);
}, [dispatch, state]);

Senior Engineer Perspective

A subtlety worth naming: because loggedDispatch closes over state to log the "before" snapshot, it's no longer as stable as raw dispatch — it changes identity whenever state does. That's an acceptable trade for a logging middleware, but worth flagging if loggedDispatch itself is passed to a memoized child expecting a stable reference.

Q41. Does passing dispatch down through context cause re-renders in components that only dispatch and never read state?

ROI: ★★★★★ Frequency: Extremely High

Short Answer

No — dispatch from useReducer is guaranteed to have a stable identity for the component's lifetime, exactly like a state setter. A component that only calls dispatch (and doesn't subscribe to the state context) won't re-render when state changes. This is exactly why splitting a dispatch context from a state context (Q35) is a real, not theoretical, performance win.

Senior Engineer Perspective

This closes the loop on the whole section: reducers give you a stable dispatch identity for free, and architecting around that stability (separate contexts) is a concrete pattern, not a hand-wavy "context is for global state" claim.

SECTION 9 - useMemo & useCallback: MISUSE & EDGE CASES

Q42. Why is memoizing a primitive value with useMemo usually pointless?

ROI: ★★★★ Frequency: High

Short Answer

Because the computation itself — say, adding two numbers — is cheaper than the memoization machinery: allocating a dependency array, running the comparison, and holding a cache slot. useMemo only pays for itself when the computed value is genuinely expensive, or when you need a stable reference for a downstream memo boundary — caching a number, string, or boolean gains neither.

Code Example

// POINTLESS — the "expensive" work is cheaper than the memoization itself
const total = useMemo(() => price * quantity, [price, quantity]);

// Just compute it — same cost as reading two variables
const total = price * quantity;

Senior Engineer Perspective

A senior candidate volunteers this unprompted when discussing Q10 rather than needing it drawn out — "memoize because it's expensive or needs a stable reference, not by default" is the whole point, and primitives satisfy neither condition.

Q43. Does useMemo do a deep comparison of its returned value's contents, or of its dependency array?

ROI: ★★★★ Frequency: High

Short Answer

Neither is a deep comparison of the returned value — useMemo only does a shallow, per-item Object.is comparison of the dependency array you give it. If the deps are unchanged, it returns the exact same reference it returned last time, so anything nested inside that value (including functions) is automatically stable too — there's no separate deep-equality step happening on the output.

Senior Engineer Perspective

The common confusion runs backwards: people assume useMemo deep-compares the value it produces to decide whether to "actually" recompute, when in fact it only ever looks at the deps array — precision on this point signals you've read past the API surface into how it actually decides to recompute.

Q44. Does useMemo/useCallback remember every past input, like a full memoization cache (e.g. lodash.memoize)?

ROI: ★★★★ Frequency: High

Short Answer

No. React (pre-Compiler) only remembers the single most recent set of dependencies and value at each call site — effectively a cache of size one, not an LRU or a full table keyed by every distinct input you've ever seen. If deps flip back and forth between two previously-seen values across renders, it recomputes every single time; it does not "remember" the earlier value.

Code Example

// If `mode` alternates "a", "b", "a", "b"... this recomputes EVERY render,
// even though it saw both values before — useMemo has no history, only "last".
const result = useMemo(() => expensiveCompute(mode), [mode]);

Senior Engineer Perspective

This is a favorite "gotcha" because the word "memoization" evokes caching in the general CS sense (multi-entry, keyed lookup), and useMemo deliberately isn't that — naming the "cache of size one" model precisely is a strong, specific answer.

Q45. How do you memoize a value whose real inputs are stable in content but not in reference, without a full deep-equal library?

ROI: ★★★★ Frequency: High

Short Answer

First choice: restructure to depend on primitives (join ids into a string, or destructure the specific fields you use) — this is almost always possible and avoids the problem entirely. Only when you truly don't control the shape (a third-party prop that's rebuilt every call) do you reach for a small ref-based "stabilize by comparison" hook, accepting that the comparison itself costs something every render.

Code Example

function useStableValue(value, isEqual) {
  const ref = useRef(value);
  if (!isEqual(ref.current, value)) ref.current = value;
  return ref.current;
}

// Only reach for this when you can't restructure the upstream prop's shape
const stableOptions = useStableValue(thirdPartyOptions, shallowEqual);
const result = useMemo(() => buildQuery(stableOptions), [stableOptions]);

Senior Engineer Perspective

This mirrors Q24's effect-dependency answer almost exactly, and interviewers notice when a candidate connects the two — the underlying issue (reference identity vs content) is the same whether it shows up in an effect's deps or a memo's deps.

Q46. If useCallback wraps a function that closes over an unstable value, does memoizing it actually help?

ROI: ★★★★ Frequency: High

Short Answer

Not by itself. If the function correctly lists every value it reads in its dependency array (as exhaustive-deps requires), and one of those values is itself a fresh reference every render (say, an object from a parent), then useCallback's output changes identity just as often as if you hadn't memoized at all — the instability has simply moved up one level in the chain. Fixing it requires stabilizing the whole chain, not just the outermost wrapper.

Code Example

function Parent({ query }) {
  const config = { query };            // new reference every render

  // Looks memoized, but changes identity every render anyway —
  // because `config` (a correctly-listed dependency) is never stable.
  const handleSearch = useCallback(() => runSearch(config), [config]);

  return <SearchButton onClick={handleSearch} />;
}

// FIX — stabilize the upstream value first
const config = useMemo(() => ({ query }), [query]);
const handleSearch = useCallback(() => runSearch(config), [config]); // now genuinely stable

Senior Engineer Perspective

This question catches candidates who treat useCallback as a magic stability guarantee rather than a pass-through of its dependencies' stability. The fix (memoize the whole dependency chain, not just the leaf) is the real insight interviewers are listening for.

Q47. What's the real distinction between memoizing at the component boundary (React.memo) versus the value boundary (useMemo/useCallback)?

ROI: ★★★★ Frequency: High

Short Answer

React.memo decides whether a component re-renders, based on a shallow comparison of its next props. useMemo/useCallback decide whether a value keeps the same reference across renders. You need React.memo alone when a child's props are all naturally-stable primitives. You need value memoization alone when a computed value only feeds another hook's dependency array, never a rendered child. You need both together specifically when a memoized component receives an object, array, or function prop.

Senior Engineer Perspective

The trap is treating these as interchangeable "performance hooks." Being explicit about which boundary each one guards is what turns a vague "use memoization" answer into something an interviewer can't poke a hole in.

Q48. How would you use the React DevTools Profiler to justify adding a useMemo/useCallback, rather than guessing?

ROI: ★★★★ Frequency: High

Short Answer

Record a profiling session, interact with the UI in the way you suspect causes wasted work, and inspect the flame graph: React DevTools shows why each component rendered (which props/state/hooks changed) and its self-time. Only add memoization where the profiler shows a component with real render cost re-rendering because of a prop-identity change you can actually stabilize — otherwise you're optimizing on a hunch, and per Q10, memoization has real overhead of its own.

Senior Engineer Perspective

Naming the "why did this render" panel specifically (not just "I'd profile it") shows hands-on tool familiarity. It also reinforces the section's throughline: memoization is a targeted fix for a measured problem, not a reflex.

Q49. Dependency arrays are compared with Object.is per item — what edge cases does that produce with NaN and -0?

ROI: ★★★ Frequency: Medium

Short Answer

Object.is(NaN, NaN) is true (unlike ===, where NaN !== NaN) — so a dependency that evaluates to NaN on two consecutive renders is correctly treated as unchanged, avoiding an infinite-loop trap a naive ===-based comparison would cause. Conversely, Object.is(0, -0) is false while 0 === -0 is true — so a dependency that flips between 0 and -0 (rare, but possible from certain math operations) is seen by React as "changed" even though ==/=== would call them equal.

Senior Engineer Perspective

This is trivia-level, but precise knowledge of exactly which comparison operator backs the dependency array (Object.is, not ===) is the kind of detail that distinguishes a candidate who's read the actual React source/docs from one who's only used the API casually.

SECTION 10 - useImperativeHandle & forwardRef

Q50. What problem does forwardRef solve, and why can't you just pass ref as a normal prop to a function component?

ROI: ★★★★ Frequency: High

Short Answer

Historically, React intercepted the ref attribute at the JSX level rather than forwarding it into a function component's regular props object — a plain function component simply never received it. forwardRef((props, ref) => ...) is the wrapper that receives the ref as an explicit second argument, so the component can attach it to an inner DOM node or hand it to useImperativeHandle. React 19 changes this by letting function components read ref as an ordinary prop, but forwardRef remains fully supported.

Senior Engineer Perspective

Mentioning the React 19 change unprompted, while still correctly explaining why the historical restriction existed, shows both depth and currency — a common trap is only knowing one era of the API.

Q51. What does useImperativeHandle actually do, and why use it instead of forwarding the raw DOM ref?

ROI: ★★★★★ Frequency: Extremely High

Short Answer

It lets a component customize what value a forwarded ref exposes to its parent — instead of handing over the raw DOM node (and every native method on it), you expose a curated object of intentional methods, hiding internal structure. It's the function-component analog of a class component's public instance methods.

Code Example

const FancyInput = forwardRef(function FancyInput(props, ref) {
  const inputRef = useRef(null);

  useImperativeHandle(ref, () => ({
    focus: () => inputRef.current?.focus(),
    clear: () => { if (inputRef.current) inputRef.current.value = ""; },
  }));

  return <input ref={inputRef} {...props} />;
});

Senior Engineer Perspective

The key phrase is "encapsulation" — a parent holding ref.current can only call focus()/clear(), not reach into the DOM node directly (change its style, remove it, etc.), which keeps the component's internals genuinely private.

Q52. Walk through exposing focus() and clear() from a custom text input to a parent form, without exposing the raw DOM node.

ROI: ★★★★ Frequency: High

Short Answer

Same pattern as Q51, applied to a real scenario: a form-level "Clear all" button or a validation error that needs to programmatically focus the first invalid field, without the parent form component needing to know anything about the input's internal DOM structure.

Code Example

function SignupForm() {

    e.preventDefault();

      emailRef.current.focus(); // calls the curated API, not raw DOM methods

    // ...
  }

A strong answer notes that this is exactly the "escape hatch reserved for genuinely imperative actions" the docs call out (Q56) — focus management is one of the few things that doesn't map cleanly to a declarative prop.

Q55. How does React 19 change forwardRef and ref handling — do you still need forwardRef going forward?

ROI: ★★★★ Frequency: High

Q56. When is using useImperativeHandle a smell — i.e., when should you prefer props/state instead of an imperative API?

SECTION 11 - CONCURRENT HOOKS: useTransition & useDeferredValue

Q58. What problem do useTransition and useDeferredValue solve that a plain state update can't?

ROI: ★★★★★ Frequency: Extremely High

Short Answer

Both let you tell React "this particular update is less urgent than others," so an expensive re-render — like re-filtering ten thousand rows — doesn't block urgent feedback like the character you just typed appearing in an input. Without them, React treats every update with equal priority, so a big synchronous re-render blocks the main thread and typing feels laggy.

Detailed Answer

This is the concrete payoff of React's concurrent rendering: work can be interrupted and prioritized. useTransition marks a state update as non-urgent (you own the setState call). useDeferredValue marks a value as allowed to lag (useful when you only receive a value, not the update that produced it — e.g., a prop from a parent, or third-party state you don't control).

Senior Engineer Perspective

Framing this as "priority, not parallelism" up front heads off the most common follow-up trap in this whole section (Q64) — these hooks change scheduling order on the same thread, they don't offload work anywhere.

Q59. What is the useTransition API, and what does isPending give you?

ROI: ★★★★★ Frequency: Extremely High

Short Answer

const [isPending, startTransition] = useTransition(); — wrap a state update in startTransition(() => setState(...)) to mark it non-urgent. isPending is true while that transition's render is still being prepared, letting you show a pending indicator (a spinner, dimmed opacity) without blocking the currently-visible UI.

Code Example

function TabContainer() {
  const [tab, setTab] = useState("home");
  const [isPending, startTransition] = useTransition();

  function selectTab(next) {
    startTransition(() => setTab(next)); // non-urgent — won't block the click's own UI feedback
  }

  return (
    <>
      <TabButton onClick={() => selectTab("posts")} />
      {isPending && <Spinner />}
      <TabContent tab={tab} />
    </>
  );
}

Senior Engineer Perspective

Point out that isPending is what makes transitions genuinely useful in practice — without a pending indicator, users have no feedback that anything is happening while the non-urgent render is still in flight.

Q60. How does useDeferredValue differ from useTransition — is it applied to a value or to an action?

ROI: ★★★★★ Frequency: Extremely High

Short Answer

useDeferredValue takes a value and gives back a version of it that lags behind during urgent updates — you use it where you only have the value (a prop, or state you don't directly control the setter of). useTransition marks the state update itself as non-urgent — you use it where you own the actual setState call inside an event handler.

Code Example

function SearchResults({ query }) {
  const deferredQuery = useDeferredValue(query); // lags during urgent typing updates
  const results = useMemo(() => expensiveFilter(deferredQuery), [deferredQuery]);
  return <ResultsList results={results} />;
}

Senior Engineer Perspective

The clean litmus test to state out loud: "do I own the setState call?" Yes → useTransition. No, I only receive the value → useDeferredValue. That single question resolves most "which one do I use" confusion.

Q62. What does "interruptible rendering" mean for a transition, and how does a later urgent update affect an in-progress transition render?

ROI: ★★★★ Frequency: High

Short Answer

A transition's render work is done in a way React can pause and abandon if a higher-priority update (like the next keystroke) arrives before it finishes. React discards the stale, in-progress transition render and starts a fresh one with the latest state — so the UI never commits an intermediate, already-outdated expensive render; only the most current one ever reaches the screen.

Senior Engineer Perspective

This is the mechanism that makes transitions safe under rapid input — without it, a user typing quickly could see a flurry of increasingly-stale "final" renders flash by instead of one clean jump to the latest state.

Q63. useTransition/useDeferredValue vs manual debouncing — what's the actual trade-off?

ROI: ★★★★ Frequency: High

Short Answer

Debouncing delays the update by a fixed timer regardless of device speed, always showing stale results for at least that window even on a fast machine. Transitions let React use real-time signals — is there other urgent work pending right now — to decide priority, so on a fast device the "expensive" update can resolve almost immediately, while a slow device naturally yields more, with no arbitrary timer to tune. The two aren't mutually exclusive: debounce actual network calls, and transition/defer the local expensive rendering that follows.

Senior Engineer Perspective

Naming that they compose ("debounce the fetch, defer the render") rather than picking one as universally superior is the answer that reads as production experience rather than textbook recall.

Q64. Does startTransition move work off the main thread, e.g., into a Web Worker?

ROI: ★★★★★ Frequency: Extremely High

Short Answer

No — this is a common and important misconception. React's concurrent scheduler is still cooperative, single-threaded time-slicing on the main JS thread. A transition only lets React interrupt or deprioritize that specific render relative to other pending updates, yielding back to the browser between chunks of work. It does not parallelize anything or move computation off-thread; if the computation itself is genuinely heavy in absolute terms (not just "many components re-rendering"), you may still need an actual Web Worker.

Senior Engineer Perspective

This is close to the single most important correction to make unprompted in this section — candidates who say "transitions run it in the background/off the main thread" are revealing they've only read the marketing framing, not the actual scheduling model.

Q65. Does Suspense integrate with transitions — what happens if a startTransition update would cause a component to suspend?

ROI: ★★★★ Frequency: High

Short Answer

If a transitioned update would cause a component to suspend — for example, navigating to a route whose data isn't loaded yet — React keeps showing the old UI (not the Suspense fallback) while the new content loads in the background, avoiding a jarring flash to a loading spinner. A non-transitioned update, by contrast, immediately unmounts to the nearest Suspense fallback the moment something suspends.

Senior Engineer Perspective

This is one of the strongest concrete motivations for transitions in a Suspense-enabled app (React Router, Next.js route transitions) — naming it shows you understand these features were designed to work together, not as two unrelated concurrent-mode add-ons.

SECTION 12 - useSyncExternalStore

Q66. Why does useSyncExternalStore exist — what's the "tearing" problem it solves?

ROI: ★★★★ Frequency: High

Short Answer

Concurrent rendering can render different parts of the tree at different times. If two components subscribe to a mutable external store (not React state) via a naive useEffect + useState pattern, they can each capture a different snapshot of that store mid-update — part of the UI reflects the old value, part reflects the new one. That inconsistency is called "tearing." useSyncExternalStore guarantees every consumer sees a consistent snapshot for a given render, even under concurrent features.

Senior Engineer Perspective

Naming "tearing" specifically (not just "it can be inconsistent") is the term interviewers are listening for — it's the exact word React's own RFC and docs use, and it signals you've read the actual motivation rather than guessed at one.

Q67. What is the API shape of useSyncExternalStore, and what does each argument do?

ROI: ★★★★ Frequency: High

Short Answer

useSyncExternalStore(subscribe, getSnapshot, getServerSnapshot?) — subscribe(callback) registers a listener with the store and returns an unsubscribe function; getSnapshot() synchronously returns the current value, compared with Object.is to decide whether to re-render; the optional getServerSnapshot() supplies the value during server rendering and hydration.

Code Example

function useStoreValue(store) {
  return useSyncExternalStore(
    store.subscribe,
    () => store.getState(),
    () => store.getInitialState() // server snapshot
  );
}

Senior Engineer Perspective

Being able to name all three parameters and their purpose from memory, rather than just "you pass it a subscribe function," is what separates "I've seen this hook" from "I've implemented a store binding with it."

Q68. Build a custom hook for the browser's online/offline status using useSyncExternalStore, contrasted with a naive useEffect+useState version.

ROI: ★★★★ Frequency: High

Code Example

function subscribe(callback) {
  window.addEventListener("online", callback);
  window.addEventListener("offline", callback);
  return () => {
    window.removeEventListener("online", callback);
    window.removeEventListener("offline", callback);
  };
}

function useOnlineStatus() {
  return useSyncExternalStore(
    subscribe,
    () => navigator.onLine,      // client snapshot
    () => true                  // server snapshot — no navigator on the server
  );
}

The naive useEffect + useState version (subscribe in an effect, call setOnline in the listener) risks tearing under concurrent rendering and has no SSR story at all — navigator doesn't exist on the server, so getServerSnapshot filling in a sensible default is a real gap the hand-rolled version doesn't address.

Senior Engineer Perspective

This is a strong "build it live" prompt — walking through why each of the three arguments is necessary here (not just supplying them) demonstrates you understand the hook rather than having memorized a snippet.

Q69. How do state libraries like Redux or Zustand use useSyncExternalStore internally?

ROI: ★★★★ Frequency: High

Short Answer

Both migrated their React bindings to call useSyncExternalStore under the hood for selector-based subscriptions — the store's existing pub/sub mechanism becomes the subscribe argument, and getSnapshot runs the user's selector against current store state. This gives them concurrent-safe, tearing-free, selective subscriptions without requiring every consumer to go through React Context.

Senior Engineer Perspective

Knowing that this hook exists specifically because library authors (not just app developers) needed a safe primitive is useful context — it explains why the API looks the way it does (low-level, unopinionated) rather than shipping as a higher-level "useStore" hook.

Q70. What's a common mistake in getSnapshot that causes an infinite render loop?

ROI: ★★★★ Frequency: High

Short Answer

Returning a brand-new object or array from getSnapshot on every call — e.g. () => ({ ...store.state }) — means Object.is never matches between calls, so React concludes the store changed every single time it checks, causing continuous re-renders. The fix is to return a cached, stable reference that only changes when the underlying value genuinely changes — recompute and cache the derived snapshot as part of the store's own update logic, not fresh inside every getSnapshot call.

Code Example

// BUG — new object every call, Object.is never matches, infinite loop
const getSnapshot = () => ({ ...store.state });

// FIX — snapshot is only rebuilt when the store's own update logic runs,
// getSnapshot just returns the cached reference
let cached = store.state;
store.onChange(() => { cached = { ...store.state }; });
const getSnapshot = () => cached;

Senior Engineer Perspective

This mirrors the Q70/Q6-style "reference identity causes an infinite loop" pattern from earlier in the chapter, now surfacing inside a lower-level primitive — recognizing it as the same root cause in a new location is exactly the kind of pattern transfer interviewers hope to see.

Q71. How does getServerSnapshot support SSR, and what happens if you omit it for a browser-only store?

ROI: ★★★ Frequency: Medium

Short Answer

getServerSnapshot supplies a fixed value to use during server rendering and initial hydration, since a browser-only store's subscribe/getSnapshot (like the online-status example) wouldn't work in a server environment at all. If you omit it while genuinely rendering on the server, React throws, because it has no way to produce an initial snapshot without a browser.

Senior Engineer Perspective

Framing this as "the hook forces you to have an explicit SSR answer" rather than "it's an optional extra parameter" reflects the actual design intent — it's there specifically so this class of bug can't be silently forgotten.

Q72. What specifically breaks under concurrent rendering with the old useEffect+useState store-subscription pattern that didn't break with the legacy synchronous renderer?

ROI: ★★★★ Frequency: High

Short Answer

In the legacy renderer, all rendering was synchronous, so there was never a window where two components could observe two different store values mid-render — the effect+state pattern was safe by accident of always running start-to-finish uninterrupted. Under concurrent rendering, React can pause a render, do other work, and resume later; if the external store mutates during that pause, a component that already rendered with the old value can commit alongside one that reads the new value — that's tearing. useSyncExternalStore fixes this by having React re-check the snapshot right before committing and force a synchronous re-render if it changed during the concurrent work.

Senior Engineer Perspective

This ties the whole section together: the "why" is entirely about concurrent rendering's ability to pause and resume, which is a new capability the legacy renderer never had — so a pattern that was fine for a decade can become subtly broken purely by opting into React 18's concurrent features.

SECTION 13 - useId & UTILITY HOOKS

Q73. What problem does useId solve, and why can't you just use Math.random() or a module-level counter?

ROI: ★★★★ Frequency: High

Short Answer

useId generates a stable, unique id per component instance that's guaranteed to match between server-rendered HTML and the client's hydration pass. Math.random() produces a different value every time it's called, and a module-level counter can drift between server and client (different render orders, or a fresh module instance per request on the server) — both cause a hydration mismatch and can break aria-* associations that depend on the id being consistent.

  return (
    <>
      <label htmlFor={id}>{label}</label>
      <input id={id} />
    </>
  );
}

Senior Engineer Perspective

Connecting this directly to hydration mismatches (not just "ids need to be unique") is the part interviewers actually want — useId exists because of SSR specifically, not because generating a unique string is otherwise hard.

Q75. Why shouldn't you use useId as a React list key?

ROI: ★★★★ Frequency: High

Short Answer

useId's output is a stable per-component-instance identifier meant for accessibility attributes — it stays the same across re-renders (which is exactly what makes it good for aria), but it has no relationship to the identity of your data. Using it as a key would give every render the same key regardless of which item the component is currently displaying, defeating the entire purpose of keys as a hint tied to data identity (React Fundamentals Q7/Q8's territory) — keys must come from a stable, data-derived id, not a UI-focused hook.

This question checks whether a candidate actually understands what a key is for (tracking data identity across reorders) versus pattern-matching "useId gives me an id, keys need an id, so use it here" — a surface-level but common mistake.

Q78. How does useId guarantee stable ids across server render and client hydration, at a conceptual level?

Senior Engineer Perspective

The key insight to surface: this avoids needing any cross-environment coordination at all — it's a purely structural/positional derivation, which is precisely why it survives the server/client boundary where a counter wouldn't.

SECTION 14 - RULES OF HOOKS: THE INTERNALS

Q80. Describe the fiber "linked list of hooks" model in more depth — what does each hook's memoizedState actually store?

ROI: ★★★★ Frequency: High

Short Answer

Each fiber — the internal per-component-instance object React's reconciler tracks — has a memoizedState field pointing to the head of a singly linked list of "Hook" objects, one per hook call. Each node stores its own memoizedState (for useState: the current value plus any queued updates; for useEffect: the effect object with its deps and cleanup function; for useRef: the { current } box) plus a next pointer to the following hook's node. On render, React walks this list with a cursor, matching call N in your function body to node N in the list.

Senior Engineer Perspective

This is the deepest layer of Q1's "call order" explanation — being able to describe the actual data structure (a linked list on the fiber, not an array, not a map keyed by name) shows you've gone past the surface rule into the mechanism that enforces it.

Q81. What specifically does eslint-plugin-react-hooks's exhaustive-deps rule statically analyze, and what are its real limits?

ROI: ★★★★ Frequency: High

Short Answer

It performs a compile-time analysis of the effect/memo callback's AST, collecting every identifier referenced from the outer scope, then compares that set against the literal contents of the dependency array — warning on mismatches. It has no visibility into your actual runtime values or whether a reference is "logically" stable; it reasons purely about lexical scope and syntax. That's why it can be fooled by indirection — stashing a value in a ref bypasses its detection entirely, since ref.current isn't itself treated as reactive.

Senior Engineer Perspective

Explaining the linter's actual mechanism (static AST analysis, not runtime tracking) is what lets you correctly judge the rare legitimate case for a disable-comment, versus reflexively distrusting or reflexively obeying every warning.

Q82. Why do custom hooks composing other hooks still satisfy the Rules of Hooks, even though the outer component doesn't "see" the inner calls directly?

ROI: ★★★★ Frequency: High

Short Answer

Because React doesn't care about hook names at all — it only cares about the flattened, ordered sequence of low-level hook calls that actually execute during one render of one fiber. A custom hook's internal hooks get spliced into that same linked list wherever the custom hook is called, so as long as the custom hook itself always calls the same hooks in the same order (enforced recursively by the same Rules of Hooks inside it), the outer component's overall call sequence stays consistent render over render.

Senior Engineer Perspective

This resolves a question candidates sometimes worry about unprompted — "does using custom hooks somehow break the ordering guarantee?" — and being able to answer confidently that it doesn't, and explain why, shows genuine understanding rather than trust-by-convention.

Q83. What happens to a component's hook state if the component throws during render — does React preserve or discard the fiber's hook list?

ROI: ★★★ Frequency: Medium

Short Answer

If a render throws and is caught by the nearest error boundary, React discards that broken render attempt along with its fiber's in-progress hook state, and never commits it — the previously committed instance (from before the throwing render) is what remains until the error boundary decides how to recover. There's no "partially updated" hook state; a failing render is all-or-nothing with respect to what gets committed.

Senior Engineer Perspective

This is a good check for whether a candidate conflates "render" with "commit" — the throw happens during the render phase, and React's separation of render from commit is exactly what makes discarding the broken attempt clean and safe.

Q84. How do hooks interact with Suspense when a component "throws a promise" to suspend — does that corrupt the hook list?

ROI: ★★★★ Frequency: High

Short Answer

No — suspending is implemented as literally throwing the pending promise from render, which React specifically catches and treats differently from an application error, showing the nearest Suspense fallback while retaining the fiber's identity. When the promise resolves, React re-renders that same fiber from scratch, re-running every hook from the top in the same order as before — a clean re-render on retry, not a special or corrupted state.

Senior Engineer Perspective

Connecting this to Q83 — "suspending is also a throw during render, but a specially-recognized one, so it gets the same clean all-or-nothing treatment" — shows you see the underlying mechanism as one coherent system rather than two unrelated facts.

Q85. List a couple of concrete Rules-of-Hooks eslint errors, and explain what each is telling you.

ROI: ★★★★ Frequency: High

Detailed Answer

  • "React Hook 'useState' is called conditionally. React Hooks must be called in the exact same order in every component render" — a hook sits inside an if, ternary, or after an early return.
  • "React Hook useEffect has a missing dependency: 'x'. Either include it or remove the dependency array" — exhaustive-deps has found a closed-over reactive value that isn't listed (Q5's stale-closure risk).
  • "React Hook 'useMemo' is called inside a callback. React Hooks must be called in a React function component or a custom Hook function" — a hook called from somewhere that's neither a component nor a use...-named function (inside .map(), a plain helper, an event handler).

Senior Engineer Perspective

Being able to recite the actual error text (not just a paraphrase) signals you've hit these in real projects and fixed them, rather than only knowing the rules in the abstract.

Q86. Can you call a hook from a regular helper function invoked during render that isn't itself named useXxx or a component?

ROI: ★★★★ Frequency: High

Short Answer

The runtime doesn't literally check the function's name at the call site, so it might appear to work the first time syntactically — but the linter can't verify Rules-of-Hooks compliance for it, since its heuristic is name-based (useXxx or PascalCase component), so it will either flag it or simply fail to protect you from a future accidental violation. The naming convention isn't decorative — it's the contract that lets the linter (and the React Compiler's static analysis, Q87) reason about your code's safety at all.

Senior Engineer Perspective

The phrase to land: "the use prefix is load-bearing, not stylistic." Treating it as optional style is exactly the mistake that quietly disables the tooling meant to catch Rules-of-Hooks violations before they ship.

Q87. How does the Rules of Hooks constraint relate to the React Compiler's ability to auto-memoize in React 19?

ROI: ★★★★ Frequency: High

Short Answer

The Compiler statically analyzes each component/hook's source to infer dependencies and insert memoization automatically — effectively doing what you'd hand-write with useMemo/useCallback. That static analysis is only sound if hook calls are structurally predictable (fixed order, no conditional calls), which is exactly what the Rules of Hooks already require. Violating the rules doesn't just risk a runtime bug anymore — it can also produce incorrect or skipped compiler-generated memoization, since the Compiler's guarantees rest on the same call-order assumption the reconciler has always relied on.

Senior Engineer Perspective

This is a genuinely forward-looking answer: the Rules of Hooks used to matter "only" for correctness; now they're also a precondition for a whole class of automatic performance optimization, which raises the cost of getting them wrong rather than lowering it.

SECTION 15 - TESTING HOOKS

Q88. How do you test a custom hook in isolation using renderHook from React Testing Library?

ROI: ★★★★★ Frequency: Extremely High

Short Answer

renderHook mounts a hook inside a minimal hidden test component and gives you back result.current, which always reflects the hook's latest return value after each render. State-changing calls need to be wrapped in act() so React flushes the resulting updates before your assertions run.

Code Example

import { renderHook, act } from "@testing-library/react";

function useCounter(initial = 0) {
  const [count, setCount] = useState(initial);
  const increment = useCallback(() => setCount(c => c + 1), []);
  return { count, increment };
}

test("increments the counter", () => {
  const { result } = renderHook(() => useCounter());
  expect(result.current.count).toBe(0);

  act(() => result.current.increment());
  expect(result.current.count).toBe(1);
});

Senior Engineer Perspective

Testing a hook in isolation like this is the direct payoff of the custom-hooks discussion in Q18 — because the hook doesn't depend on any specific rendered markup, you can assert purely on its returned values.

Q89. Why do state-updating calls inside a hook test need to be wrapped in act(), and what warning appears if you forget?

ROI: ★★★★ Frequency: High

Short Answer

act() ensures every state update, effect, and re-render triggered by your interaction is fully flushed and applied before your assertions run — mirroring the guarantee React's own event handling provides in the browser. Forgetting it produces "Warning: An update to TestComponent inside a test was not wrapped in act(...)" and can lead to assertions running against a stale result.current snapshot captured before the update actually applied.

Senior Engineer Perspective

Framing act() as "the same synchronization guarantee the browser gives you for free" rather than "a testing-library quirk" is a subtle but real distinction that shows deeper understanding.

Q91. How do you test a custom hook with asynchronous behavior, such as a hook that fetches data?

Q92. What's a common pitfall when testing a hook that uses setInterval/setTimeout, and how do fake timers help?

ROI: ★★★★ Frequency: High

Short Answer

Using real timers makes tests slow and occasionally flaky, since you're literally waiting real wall-clock time. Jest's fake timers let you advance time deterministically and instantly — wrap the advance in act(), since it synchronously triggers state updates React needs to flush.

Q93. How do you test that a custom hook throws correctly for invalid usage, like useAuth called outside its Provider?

ROI: ★★★ Frequency: Medium

Short Answer

Wrap the renderHook call in an expectation of a thrown error: expect(() => renderHook(() => useAuth())).toThrow(/must be used within/). React also logs its own console error for an uncaught throw during render in tests, which you may want to spy on and silence to keep test output clean without hiding the actual assertion.

Senior Engineer Perspective

Mentioning the console-error noise (and deliberately silencing it rather than being surprised by it in CI logs) shows you've actually run this kind of test, not just written it once and moved on.

Q94. When would you choose to test a hook via renderHook in isolation vs. testing it through the component(s) that consume it?

ROI: ★★★★ Frequency: High

Short Answer

Test in isolation when the hook has non-trivial internal logic — a reducer-like state machine, retry/backoff behavior, memoized derived values — that's easiest to exercise directly without also asserting on markup. Test through the consuming component when the hook is a thin wrapper whose entire value is how it affects what's rendered — testing the user-visible behavior through the component better reflects what consumers actually experience and is more resilient to internal refactors of the hook itself.

Senior Engineer Perspective

This is a judgment question, not a rule-recall one — the strongest answers give both directions with a concrete criterion for each, rather than declaring one approach universally correct.

Q95. What's the pitfall of over-mocking in hook tests — e.g., mocking away the very external system the hook exists to manage?

ROI: ★★★★ Frequency: High

Short Answer

If a hook's entire purpose is coordinating with an external store or API — say, a useSyncExternalStore wrapper around a real subscription — fully mocking that subscription can make the test pass while missing a bug in exactly the piece the hook is responsible for: the subscribe/unsubscribe wiring, cleanup correctness, or race conditions specific to that environment (including surviving StrictMode's double-invoke from Q7). Prefer light fakes that still exercise the real subscribe/unsubscribe symmetry — a minimal fake event emitter, for instance — and reserve hard mocks for genuinely outer layers, like swapping the actual fetch implementation rather than your own hook's fetching logic.

Senior Engineer Perspective

This closes the chapter on the same theme it opened with: a hook's job is to correctly manage a piece of state or an external system, and a test suite that mocks away the exact thing being managed gives you false confidence — the same trap as testing a reducer by mocking the reducer.
